NFSD Callback Statistics: Netlink and Per-Net Namespace Preferred Over /proc

Summary

NFSD: Exposing Callback Statistics – Interface and Scope Debated

This week, Dai Ngo proposed a patch to expose NFSv4 callback (backchannel) statistics via /proc/net/rpc/nfsd. The discussion highlighted significant concerns regarding the choice of interface (/proc vs. netlink) and the scope of the statistics (system-wide vs. per-net-namespace).

Patch Intent and Initial Feedback

Dai Ngo's patch aimed to make existing backchannel statistics visible during normal operation, noting that "developers typically have to inspect a vmcore" to view them currently. The patch added system-wide counters for each callback operation and per-client statistics in a format similar to mountstats(8).

Chuck Lever immediately questioned the use of the /proc interface, describing it as legacy:

"The commit message needs to justify why you are modifying a legacy /proc interface. I assume it is because you want these metrics to appear in an existing NFS administrative tool like nfsstat ?"

Neil Brown raised concerns about the scope of the statistics:

"Why system-wide rather than per-net-namespace?"

Clarification and Architectural Recommendations

Dai Ngo clarified that the patch was intended for developer use only and did not plan to extend nfsstat(8) at this time. He explained that the counters were currently embedded in a global cb_program structure:

"These counters are currently embedded in cb_program which is defined globally and not in nfsd_net."

Neil Brown, upon realizing these were existing statistics being exported rather than new ones, advised against exporting global statistics:

"So I change my comment to: please don't do that. I don't think it is appropriate to export global statistics. We should only export per-net-namespace statistics. So place convert the statistics collect to per-net-namespace, then export them."

Chuck Lever agreed with Neil's assessment, adding a "+1" to the request for per-net-namespace statistics.

The Case for Netlink

Jeff Layton suggested moving away from /proc entirely in favor of netlink, citing existing infrastructure:

"We have a new netlink commands for nfsd that give us request status. It would be good to either extend that or add a new command that allows statistics. Netlink is much better suited for this since it's a lot easier to extend than dealing with procfiles."

He reinforced this point given Dai's clarification about the target audience:

"Even more reason to use netlink then."

Conclusion

The patch was not accepted in its current form. The consensus among the maintainers and reviewers is twofold:

  1. Scope: Statistics should be collected and exposed on a per-net-namespace basis, requiring changes to how they are currently stored in the global cb_program.
  2. Interface: /proc is considered a legacy interface for this purpose. The preferred approach is to utilize or extend the existing netlink commands for NFSD, which offer better extensibility and are more suitable for developer-focused diagnostic tools.

This discussion underscores the ongoing evolution of NFS server diagnostics towards more modern, flexible interfaces like netlink, while adhering to kernel best practices regarding namespace isolation.
