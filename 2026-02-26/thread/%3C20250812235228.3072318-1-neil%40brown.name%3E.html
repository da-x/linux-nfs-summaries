VFS Dentry Hashing Refactor: NFS Client Implications for d_splice_alias and atomic_open

Summary

VFS Dentry Hashing: NFS Client Implications in Directory Locking Refactor

Overview

This thread, originally initiated in August 2025, concerns a proposed VFS-level change to allow d_splice_alias() and d_add() to operate on hashed dentries — a prerequisite for NeilBrown's broader directory locking refactor. After a six-month hiatus following Al Viro's initial review, Neil Brown revived the discussion this week with two messages on February 26, 2026, focusing specifically on how filesystems like NFS should handle dentry instantiation in atomic_open and mkdir contexts.

This is primarily a protocol/VFS interface change with significant implications for NFS client development, rather than a discrete bug fix. The goal is to eliminate the need for filesystems to call d_drop() (unhashing) before invoking d_splice_alias(), which conflicts with proposed locking changes that require dentries to remain hashed during directory operations.

Background (Prior Weeks)

The original patch series ([PATCH 08/11] VFS: allow d_splice_alias() and d_add() to work on hashed dentries)[id://20250812235228.3072318-9-neil@brown.name] proposed modifying d_splice_alias() and d_add() to accept hashed dentries, removing explicit d_drop() calls from several filesystems including NFS (fs/nfs/dir.c and fs/nfs/nfs4proc.c).

Al Viro responded with concerns about code clarity. He argued against making all callers of d_splice_alias() and d_add() ambiguous regarding hash state, stating:

"The problem I have with that is the loss of information. That is to say, 'is it hashed here' is hard to deduce from code. I would rather add d_splice_alias_hashed() and d_add_hashed(), and then see what's going on in specific callers."

Viro emphasized the need for upfront analysis:

"I realize that it's no fun at all - in particular, I'd never been able to get ceph folks to explain what is and what is not possible there. I would really hate to have that expand by order of magnitude - in effect, you make all calls of d_splice_alias() and d_add() similar mysteries."

This Week's Activity (February 26, 2026)

After six months of silence, Neil Brown returned to the thread with renewed analysis. He noted:

"I'm picking this up at last ... only 6 months later."

Key Technical Arguments

1. The atomic_open Distinction

Neil identified that atomic_open is called in two distinct states:

  • With a d_in_lookup() dentry (unhashed, still being looked up)
  • With a negative hashed dentry (already in the hash table but without an inode)

He observed that most filesystems providing atomic_open check for d_in_lookup() and perform a lookup to obtain a hashed dentry. However, three filesystems stand out as exceptions: ceph, smb/client, and NFS. These filesystems call d_drop() (conditionally for ceph, unconditionally for smb and nfs) and then invoke d_splice_alias().

Neil proposed a cleaner approach for these cases:

"So I could change these to:

 if (d_in_lookup(de))
    d_splice_alias(de, inode);
 else
    d_instantiate(de, inode);
```"

He also suggested enhancing d_instantiate to handle the d_in_lookup() case automatically:

"Could we enhance d_instantiate to do d_splice_alias() in the case where the dentry is d_in_lookup()?"

2. The Directory Case (mkdir) Complication

In a follow-up message, Neil corrected his earlier assertion that there were no cases where d_splice_alias() is called with a directory inode and a hashed dentry:

"There are of course... mkdir() is given a hashed negative dentry and may need to use d_splice_alias() if there is any chance the inode was accessible (e.g. by fhandle) before the splice can happen."

This reveals a critical NFS-specific concern: file handles (fhandle) can make inodes accessible through alternative paths before the dentry splice occurs, necessitating careful handling.

Neil outlined three distinct cases that generic "create object" code inside a filesystem must handle:

  1. d_in_lookup() — use d_splice_alias()
  2. Otherwise if non-directory — use d_instantiate()
  3. Otherwise (directory) — use some new d_add_or_obtain (a name borrowed from NFS internals) which handles directories correctly

He concluded with the core motivation:

"Currently most d_drop() and use d_splice_alias() but I need to avoid the d_drop()."

Implications for NFS Client Development

This discussion is directly relevant to NFS client developers because:

  1. NFS currently calls d_drop() unconditionally before d_splice_alias() in its atomic_open implementation, a pattern that must change under the proposed locking model.
  2. The NFS-specific d_add_or_obtain semantics for directory creation may need to be elevated to a VFS-level interface or carefully adapted.
  3. File handle accessibility is a unique concern for network filesystems like NFS, where inodes can be reached via multiple paths (e.g., through open_by_handle_at), making the race conditions around dentry splicing particularly important.

Final Conclusions

No definitive resolution was reached this week. The discussion remains open-ended, with Neil Brown proposing potential API simplifications (enhancing d_instantiate or introducing a new interface) while acknowledging the complexity introduced by directory creation scenarios. The key takeaway is that the NFS client's current pattern of unconditional d_drop() followed by d_splice_alias() must be replaced with state-aware logic distinguishing between d_in_lookup(), hashed non-directory, and hashed directory cases — all without calling d_drop().
