NFS/NFSD: nfs4_acl Passthru RFC Discussion Continues - API Design Debate and Rebase Request

Summary

NFS/NFSD: Continued Discussion on nfs4_acl Passthru for NFSv4 Reexport

Classification: New Feature / Protocol Enhancement (RFC)
Participants: Mike Snitzer, Chuck Lever
Key Message IDs:

  • Chuck Lever's clarification on passthru goal
  • Chuck Lever's concerns about cross-subsystem patches
  • Chuck Lever's technical feedback on API design
  • Mike Snitzer's response to feedback
  • Chuck Lever's request for rebased series

Overview

This week's discussion continues the review of Mike Snitzer's 11-patch RFC series introducing nfs4_acl passthru support for NFSv4 reexport scenarios. The feature aims to bypass NFSD's lossy NFSv4 ACL-to-POSIX ACL conversion mechanism when re-exporting filesystems that natively support NFSv4.1 ACLs (DACL and SACL). This is particularly important for environments requiring Kerberos authentication and strict ACL preservation across NFS version boundaries.

Technical Arguments

Clarification of Passthru Goal

Chuck Lever clarified his understanding of the patchset's objective:

"So what you are really looking for is a mechanism that bypasses NFSD's NFSv4 ACL <-> local POSIX ACL rewriting mechanism only for NFS re-exports. Fair enough!" [id://3bc90d32-cc8f-468a-9cb5-968865dd6768@oracle.com]

This confirms the feature's narrow scope: enabling raw nfs4_acl structures to pass through the re-export layer without conversion when the backend filesystem supports full NFSv4.1 ACL semantics.

Cross-Subsystem Patch Concerns

Chuck Lever reiterated his concerns about patch sets that modify both the NFS client and NFSD server subsystems:

"I haven't been a fan of these double-subsystem patch sets... Aside from the added complications and compromises needed to manage a merge for two independently maintained subsystems, the API boundary between the two subsystems is already ragged and rather /ad hoc/." [id://377ab826-ff0b-4793-a2ab-999db9ccc99f@oracle.com]

He noted that sharing XDR definitions would become increasingly complex as NFSD transitions to xdrgen, emphasizing his goal to minimize merge effort and long-term maintenance costs.

API Design Debate: Inode Operations vs Export Operations

A significant technical discussion emerged regarding whether .setacl and .getacl operations should be implemented as inode operations or remain as export operations:

Chuck Lever questioned the current design:

"Wondering, though, if plumbing .setacl and .getacl through the export ops is the right way to go. These seem like inode ops to me, not export ops. Shouldn't they work like an inode's existing POSIX ACL ops?" [id://fbdf4c2b-6d3b-45bc-ae2e-48316dd16eeb@app.fastmail.com]

Mike Snitzer responded by explaining his pragmatic approach:

"I didn't even consider this... I try not to game out hypotheticals too much. But I do welcome suggestions like this that offer experienced vision for being mindful of exposing interfaces that lend themselves to standing the test of time." [id://aZtbbJ-dxkw-V4NU@kernel.org]

Snitzer preferred keeping these operations tightly coupled to NFSD for immediate passthrough needs, rather than exposing them more generically as inode operations. He asked about ZFS's implementation of NFSv4 ACLs to understand if there were relevant insights for Linux:

"Relative to NFSD, its purely about passing through the nfs4_acl pages that it got off the wire directly down to FS that has 'native file system NFSv4 ACL support'." [id://aZtbbJ-dxkw-V4NU@kernel.org]

Scope Clarification: NFSv4 Minor Version Combinations

Chuck Lever sought clarification on which NFSv4 minor version combinations the patchset supports:

"It made me wonder -- is re-exporting NFSv4.2 on an NFSv4.1 mount the only configuration that we want NFSD to support? I would think that any combination of NFSv4 minor versions could be supported." [id://fbdf4c2b-6d3b-45bc-ae2e-48316dd16eeb@app.fastmail.com]

Mike Snitzer clarified that the example given was just one scenario:

"My '(e.g. when NFSD 4.1 reexports NFS 4.2)' was only an example. The code should work fine with any NFSv4 combination -- though obviously 4.0 won't understand nfs4 acl utils --dacl and --sacl flags." [id://aZtbbJ-dxkw-V4NU@kernel.org]

Framing: "Native File System NFSv4 ACL Support"

Chuck Lever suggested reframing the feature more broadly:

"I would like to think about this in terms of 'native file system NFSv4 ACL support' rather than 'NFSD pass through'. So, the NFS client's NFSv4 inodes have it, and this series doesn't need to add it anywhere else for now." [id://fbdf4c2b-6d3b-45bc-ae2e-48316dd16eeb@app.fastmail.com]

Snitzer agreed with the framing but cautioned against over-engineering:

"Sounds fine to frame it in those terms, but may cause make-work for some future consumer that'll never actually materialize." [id://aZtbbJ-dxkw-V4NU@kernel.org]

Evolution of Discussion

The discussion evolved from initial clarification of the patchset's goals (last week) to deeper technical debates about API design and scope this week. Key developments include:

  1. Goal Clarification: Chuck Lever confirmed his understanding that the passthru mechanism specifically bypasses NFSD's ACL conversion for re-export scenarios.
  2. Structural Concerns: Ongoing concerns about cross-subsystem patch complexity were reiterated, with no resolution yet on splitting the series.
  3. API Design Debate: A substantive discussion emerged about whether .setacl/.getacl should be inode operations (Chuck Lever's preference based on POSIX ACL precedent) or remain as export operations (Mike Snitzer's pragmatic choice for immediate NFSD passthrough needs).
  4. Scope Confirmation: The patchset is confirmed to support various NFSv4 minor version combinations, not just 4.1 re-exporting 4.2.
  5. Next Steps: Chuck Lever requested a rebased series with a publicly available commit hash or tag in the next cover letter.

Final Conclusions

This week's discussion did not result in formal acceptance or rejection of the RFC, but rather clarified several important design points:

  1. Passthru Mechanism Confirmed: The feature is necessary for re-export scenarios involving NFSv4.1 ACLs due to knfsd's lossy mapping behavior, as established last week.
  2. API Design Open Question: Whether .setacl/.getacl should be inode operations or export operations remains an open design question, with Chuck Lever advocating for inode operations based on precedent and extensibility, while Mike Snitzer favors export operations for immediate, tightly-coupled NFSD functionality.
  3. Rebase Required: Mike Snitzer acknowledged that the series needs rebasing against a more current tree due to conflicting changes from Chuck Lever:

"Given what you found, I'm missing some of your latest conflicting changes. So it'll need a rebase." [id://aZtbbJ-dxkw-V4NU@kernel.org]

Chuck Lever's final request set the stage for the next iteration:

"Anything publicly available will work. Rebase, then just toss the tag or commit hash in your next cover-letter." [id://7ee56c30-f635-4de9-a4c1-8a5eaf7e491b@app.fastmail.com]

This feature represents a significant enhancement for NFS re-export architectures, particularly for environments requiring Kerberos authentication and strict ACL preservation across NFS version boundaries. The ongoing API design discussion reflects broader architectural considerations about how to best integrate NFSv4 ACL support into the Linux VFS layer.
