NFSv4.0 Replay Cache: Dynamic Allocation for Oversized Responses

Summary

NFSv4.0 Replay Cache: Dynamic Allocation for Oversized Responses

Type: Bug fix / Protocol compliance enhancement
Component: NFS Server (nfsd)
Key Participants: Chuck Lever, Jeff Layton

Overview

This thread addresses a regression in the NFS server's handling of LOCK operation replays under NFSv4.0. A previous security fix inadvertently introduced a protocol violation where retransmitted LOCK operations with large lockowner names would return malformed XDR responses. Chuck Lever proposed a patch to restore full correctness via dynamic memory allocation, sparking a brief discussion on whether such rigor is warranted for the legacy NFSv4.0 protocol.

The Problem: A Fix That Broke Compliance

The root cause traces back to commit 1e8e9913672a ("nfsd: fix heap overflow in NFSv4.0 LOCK replay cache"). That commit capped the replay cache copy at NFSD4_REPLAY_ISIZE (112 bytes) to prevent a heap overflow. However, when an encoded response exceeded this inline buffer, the code set rp_buflen to zero.

As Chuck Lever explained in his initial patch submission:

"A retransmitted LOCK reaching the replay path then produced only a status code with no operation body, resulting in a malformed XDR response."

This meant that while the server avoided a crash or overflow, it violated the NFS protocol by sending incomplete responses to clients retrying legitimate operations.

The Proposed Solution

Lever's patch introduces dynamic allocation for oversized replay caches:

"When the encoded response exceeds the 112-byte inline rp_ibuf, a buffer is kmalloc'd to hold it. If the allocation fails, rp_buflen remains zero, preserving the behavior from the capped-copy fix."

The allocated buffer is freed when the stateowner is released or when a subsequent operation's response fits in the inline buffer again. This approach ensures that even large lockowner names are handled correctly during replay, maintaining protocol compliance without risking memory exhaustion (graceful degradation on allocation failure).

Discussion: Is NFSv4.0 Worth the Effort?

Jeff Layton, who authored the original heap overflow fix, questioned the necessity of this additional complexity for NFSv4.0:

"Certainly a reasonable approach if we care about full correctness when dealing with a large lockowner on NFSv4.0. Do we?"

Lever acknowledged the narrow scope of the issue but emphasized protocol compliance:

"Admittedly this is a narrow corner case for a minor version that is destined for the scrap heap."

He suggested two paths forward: either backport only Layton's original fix (accepting the malformed response behavior) or squash both fixes together for full correctness.

Layton conceded that he had considered dynamic allocation during his original fix but deemed it "not worthwhile" at the time:

"I doubt any legitimate user will ever care."

However, Lever countered with a compliance-focused argument:

"My concern is handling replay compliantly."

Conclusion and Consensus

Layton ultimately endorsed Lever's approach, noting that dynamic allocation was preferable to the alternative of increasing NFSD4_REPLAY_ISIZE:

"I think that the only other way is to grow NFSD4_REPLAY_ISIZE, and doing dynamic allocation is preferable to that, IMO."

He gave his explicit approval:

"To be clear: I don't have a problem with your patch. It just didn't seem worthwhile to me. If you think it's worth fixing though, then go for it."

The thread concluded with mutual agreement that while the use case is rare and NFSv4.0 is legacy, maintaining protocol correctness is valuable. The patch represents a defensive improvement ensuring that edge cases in LOCK replay handling do not produce malformed responses, even if real-world impact is minimal.
