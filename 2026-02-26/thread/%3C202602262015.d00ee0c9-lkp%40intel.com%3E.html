KCSAN Data Race Report: VFS atime_needs_update / touch_atime Regression

Overview

Classification: Bug report — automated KCSAN (Kernel Concurrency Sanitizer) data race detection in VFS atime handling, triggered by a recent commit. This is not an NFS-specific issue, but rather a VFS-level regression that affects all filesystems, including NFS.

This thread consists of a single automated message from the Intel 0-DAY CI kernel test robot, reporting a newly introduced data race detected by KCSAN in the atime update path. The report carries no human follow-up or discussion within this week's window.

Technical Details

On February 26, the kernel test robot reported a KCSAN data race triggered by commit 761475268fa8e322fe6b80bcf557dc65517df71e ("fs: refactor ->update_time handling"). The robot noted:

"it seems to us this change causes the stats changes for various (random) KCSAN issues. just FYI what we observed in tests."

The Data Race

The core finding is a data race between atime_needs_update (reader) and touch_atime (writer) on the inode's atime-related state:

  • Write side (touch_atime): Task 23711 on CPU 0 wrote 4 bytes to address 0xffff8881005bf140, originating from a call chain through pick_link → step_into_slowpath → open_last_lookups → path_openat → do_filp_open → do_open_execat → open_exec → load_elf_binary → exec_binprm → kernel_execve → call_usermodehelper_exec_async.

  • Read side (atime_needs_update): Task 23712 on CPU 1 read 4 bytes from the same address, following an identical call chain through pick_link → step_into_slowpath → open_last_lookups.

The KCSAN report shows:

"value changed: 0x2160ec00 -> 0x22921900"

Both tasks were executing ELF binary loads via call_usermodehelper_exec_async, exercising concurrent path lookup and atime update on the same inode.

Significance for NFS Client Development

While this report originates from a VFS-level change and is not NFS-specific, it is relevant to NFS client developers because:

  1. NFS atime semantics: The NFS client implements custom atime handling through its ->update_time inode operation. Any VFS-level refactoring of the atime update path can interact with NFS's timestamp caching and attribute invalidation logic.

  2. Concurrency in path lookup: The race was triggered during concurrent execve operations — a workload pattern that NFS clients commonly encounter when multiple processes execute binaries from NFS-mounted directories.

  3. VFS contract stability: The commit "fs: refactor ->update_time handling" modifies the VFS interface that filesystems like NFS implement. Changes to locking or synchronization assumptions in this path could affect NFS client correctness.

Final Conclusions

This is an automated bug report with no human discussion within the current week's window. Key takeaways:

  1. A regression has been identified: Commit 761475268f ("fs: refactor ->update_time handling") introduced new KCSAN-detected data races in the atime update path, most notably between atime_needs_update and touch_atime.

  2. The race is in core VFS code (fs/inode.c), not in any filesystem-specific implementation, meaning all filesystems — including NFS — are potentially affected.

  3. No fix or acknowledgment has been posted yet. The report serves as a notification for VFS and filesystem maintainers to investigate the concurrency issue introduced by the refactoring.
