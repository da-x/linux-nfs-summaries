NFS 7.0 Pull: Bisect-ability Regression from KConfig Restructuring

Summary

NFS 7.0 Pull: KConfig Bisect-ability Regression Highlighted

Overview

Discussion type: Bug fix / regression report (KConfig design affecting kernel bisect workflows).

This week's activity on the NFS client pull request thread consisted of a single but significant contribution from Mike Snitzer, who identified an additional problem with the CONFIG_NFS_V4_0 restructuring introduced in Anna Schumaker's Linux 7.0 pull request. While last week's discussion focused on a boot-critical regression where make olddefconfig silently disabled NFS v4.0 (breaking root filesystem mounts), Snitzer highlighted a different but related issue: the KConfig changes break kernel bisect workflows when navigating between kernel versions.

Evolution of the Discussion

Prior Context (Weeks of 2026-02-12 and 2026-02-19)

Anna Schumaker's GIT PULL request for Linux 7.0 introduced a major KConfig restructuring: splitting NFS v4.0 into its own configurable option (CONFIG_NFS_V4_0) and merging CONFIG_NFS_V4_1 with CONFIG_NFS_V4. This was intended to allow administrators to disable legacy NFS v4.0 support while making v4.1 the default.

Last week, Niklas Cassel reported that this change caused a critical boot failure: make olddefconfig silently disabled CONFIG_NFS_V4_0, breaking systems using nfsvers=4 on the kernel command line. Anna acknowledged the oversight, stating:

"This is what I intended, actually. I don't know how the missing 'default y' slipped through the cracks for this long. Thanks for pointing it out, I'll get this fixed up!"

This Week: Bisect-ability Concerns

On February 23, Mike Snitzer — who had previously contributed NFS/localio fixes to the same pull request — reported a separate but related problem he encountered while performing a git bisect between Linux 7.0-rc1 and 6.19:

"Another related problem I just encountered, when doing a bisect that pivoted from 7.0-rc1 back down to 6.19, is that 'make olddefconfig' using the 7.0-rc1's .config as starting point against 6.19 kernel results in:

CONFIG_NFS_V4_1 is not set

CONFIG_NFS_V4_2 is not set

CONFIG_PNFS_FLEXFILE_LAYOUT=m doesn't exist, etc."

Snitzer emphasized the practical impact on developer workflows:

"So this change seriously breaks NFS bisect-ability."

His concern is that when developers use a .config from 7.0-rc1 (which uses the new CONFIG_NFS_V4_0 symbol) as input to make olddefconfig against an older kernel like 6.19 (which still uses the old CONFIG_NFS_V4_1 and CONFIG_NFS_V4_2 symbols), the configuration silently drops NFS v4.1 and v4.2 support, along with pNFS FlexFile Layout. This makes it impossible to reliably bisect bugs that span across the 7.0 merge window boundary while maintaining consistent NFS client capabilities.

Key Technical Argument

Snitzer proposed a design alternative:

"Feels like the new CONFIG_NFS_V4_0 control should be standalone and CONFIG_NFS_V4_1 shouldn't be removed."

The core of his argument is that the KConfig restructuring should preserve backward compatibility in configuration symbols to ensure that .config files remain portable across kernel versions. By removing CONFIG_NFS_V4_1 as a distinct symbol (merging it into CONFIG_NFS_V4), the change creates a one-way incompatibility: configurations from newer kernels cannot be cleanly applied to older kernels without losing NFS functionality.

This is a classic kernel development dilemma: refactoring for cleaner architecture versus preserving configuration compatibility for bisect and long-term maintenance workflows.

Significance for NFS Client Development

This thread underscores two important lessons for NFS client development:

  1. KConfig changes have ripple effects beyond boot-time behavior. The initial regression (missing default y) affected end users at boot time, while Snitzer's report highlights the impact on developer tooling — specifically, the ability to bisect regressions across kernel version boundaries. Both are critical for maintaining a healthy development ecosystem.

  2. NFS v4.0 deprecation must be handled carefully. The community's move toward making NFS v4.1 the default and allowing v4.0 to be disabled is architecturally sound, given that v4.0 lacks essential features like state renewal and session management. However, the transition must preserve configuration compatibility to avoid breaking bisect workflows and existing build systems.

Conclusion

This week's thread added an important dimension to the ongoing discussion about the NFS KConfig restructuring. While Anna Schumaker had already committed to fixing the missing default y for CONFIG_NFS_V4_0, Mike Snitzer's report highlights a broader concern: the removal of CONFIG_NFS_V4_1 as a distinct symbol breaks backward compatibility for .config files, undermining kernel bisect workflows. The discussion remains open-ended, with no final resolution posted this week, but it sets the stage for further refinement of the KConfig design in upcoming patches.
