NFS Server: Regression in nfsd_permission() Breaks File Locking

Summary

NFS Server: Regression in nfsd_permission() Breaks File Locking for NFSv3 Clients

Classification: Bug Fix (NFS Server / nfsd Permission Checks)

Summary

This thread reports a regression in the NFS server (nfsd) that causes file locking operations to fail with -ENOLCK ("No locks available") on NFSv3 clients. The issue was discovered in production infrastructure and traced back to a specific upstream commit that removed critical permission checks from nfsd_permission().

Technical Context

The Regression

Tj reported the issue on February 24, identifying two commits as the source of the regression:

"Upstream commit 4cc9b9f2bf4dfe13fe573 'nfsd: refine and rename NFSD_MAY_LOCK' and stable v6.12.54 commit 18744bc56b0ec (re)moves checks from fs/nfsd/vfs.c::nfsd_permission()."

The removed checks caused NFS clients attempting to acquire file locks via flock() or fcntl() to receive -ENOLCK errors, effectively breaking file locking functionality over NFSv3 mounts.

Real-World Impact

The bug was discovered on the Debian openQA infrastructure, where worker hosts pass NFSv3-mounted ISO images to QEMU for virtual machine testing:

"This was discovered on the Debian openQA infrastructure server when upgrading kernel from v6.12.48 to later v6.12.y where worker hosts (with any earlier or later kernel version) pass NFSv3 mounted ISO images to qemu-system-x86_64 and it reports: !!! : qemu-system-x86_64: -device scsi-cd,id=cd0-device,drive=cd0-overlay0,serial=cd0: Failed to get 'consistent read' lock: No locks available"

QEMU requires "consistent read" locks on disk images to prevent corruption, and this regression broke that capability entirely.

Reproduction

Tj provided a clear reproducer using NFSv3 with NLM (Network Lock Manager) authentication:

# Server exports:
/srv/NAS/test fdff::/64(fsid=0,rw,no_root_squash,sync,no_subtree_check,auth_nlm)

# Client mount:
mount -t nfs [fdff::2]:/srv/NAS/test /srv/NAS/test -o proto=tcp6,ro,fsc,soft

# Trigger:
flock -e -w 4 /srv/NAS/test/debian-13.3.0-amd64-netinst.iso sleep 1
flock: /srv/NAS/test/debian-13.3.0-amd64-netinst.iso: No locks available

A custom test program calling fcntl() with the same arguments QEMU uses also failed identically, confirming the issue is at the NFS server level rather than a client-side problem.

Proposed Fix

Tj identified a straightforward resolution:

"Keeping the check in nfsd_permission() whilst also copying it to fs/nfsd/nfsfh.c::__fh_verify() resolves the issue."

This suggests that the permission check removed from nfsd_permission() needs to be restored there and additionally duplicated in __fh_verify() to cover all code paths.

Call Trace Analysis

In a follow-up message, Tj added dump_stack() to nfsd_permission() and revealed the two call paths that trigger the issue:

  1. NFSv4 path: nfsd_permission → nfsd_access → nfsd4_proc_compound → nfsd_dispatch
  2. NFSv3 path: nfsd_permission → nfsd_access → nfsd3_proc_access → nfsd_dispatch

Both paths flow through nfsd_access, confirming that the regression affects both NFSv3 and NFSv4 clients when they perform access/permission checks related to locking operations.

Evolution of Discussion

This week's activity was limited to Tj's initial report and follow-up with stack traces. The thread continued beyond this week (as seen in the full message list) with responses from Thorsten Leemhuis, Salvatore Bonaccorso, Olga Kornievskaia, Sasha Levin, NeilBrown, Jeff Layton, Chuck Lever, and Ben Hutchings — indicating that the NFS maintainers engaged with the report in subsequent weeks. The discussion eventually evolved into a patch series titled "[PATCH] lockd: fix TEST handling when not all permissions are available" by NeilBrown, suggesting the root cause analysis led to a fix in the lockd subsystem rather than simply reverting the original commit.

Key Technical Takeaway

This regression highlights the fragility of permission-check refactoring in the NFS server codebase. The removal of checks from nfsd_permission() during the "refine and rename NFSD_MAY_LOCK" commit inadvertently broke the locking infrastructure for NFS clients relying on NLM. The fact that both NFSv3 and NFSv4 paths are affected through the common nfsd_access function underscores how central permission checks are to the NFS server's locking protocol implementation.
