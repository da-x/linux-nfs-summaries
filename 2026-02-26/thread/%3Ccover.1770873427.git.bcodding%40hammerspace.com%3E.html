Technical Overview (from Cover Letter)

The series introduces signed filehandles to kNFSD, a security feature designed to defend against filehandle guessing attacks. As explained in the cover letter:

"Filehandles are easy to guess because they are well-formed... Because the handle is well-formed, its easy to fabricate filehandles that match other files within the same filesystem."

The solution appends an 8-byte Message Authentication Code (MAC) using SipHash-2-4 to filehandles. Key design points include:

  • The signing key is a 128-bit secret configured via netlink and persisted across reboots.
  • The key can be set only once and cannot be changed afterward, ensuring long-term validity of signed filehandles.
  • Exports must explicitly enable the sign_fh export option to activate signing.
  • Invalid or unsigned filehandles for signed exports are rejected with NFS error _STALE.

Coddington noted a limitation regarding filehandle size:

"There could be some filesystems with 40-byte fileid and 24-byte fsid which would break NFSv3's 64-byte filehandle maximum with an 8-byte MAC appended. The server should refuse to export those filesystems when 'sign_fh' is requested."

However, due to export cache behavior, this check cannot be performed at export time. Instead:

"the server will refuse to give out filehandles at mount time and emit a pr_warn()."

Significance for NFS Development

This feature represents a new security enhancement for the NFS server rather than a bug fix. It addresses a genuine vulnerability where remote clients could potentially guess valid filehandles to bypass directory permission restrictions. The use of SipHash-2-4 provides a "low 1 in 2^64 chance of forgery," making brute-force attacks practically infeasible.

The feature complements the ongoing migration from /proc/fs/nfsd to netlink for NFSD configuration, as evidenced by related work on nfsdctl module loading committed to nfs-utils 2.8.6-rc1 this same week.
