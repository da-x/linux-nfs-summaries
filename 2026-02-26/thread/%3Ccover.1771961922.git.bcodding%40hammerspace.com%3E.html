kNFSD Signed Filehandles v7 Applied with Build Fix Required

Summary

kNFSD Signed Filehandles (v7) Applied to nfsd-testing

Summary

Discussion type: New security feature for the NFS server (NFSD), with a post-merge bug fix.

This week, Benjamin Coddington submitted version 7 of his series to enable signed filehandles in the Linux NFS server (kNFSD). The series was applied by maintainer Chuck Lever to the nfsd-testing tree, but a subsequent build failure reported by Jeff Layton revealed a duplicate function definition that required a resend from Coddington.

Bridge from Prior Weeks

The signed filehandle feature has evolved through seven iterations since its initial posting. Key historical developments include:

  • A shift from encryption to signing (MAC) based on feedback from Eric Biggers.
  • Numerous fixes for endianness, export flags, and protocol error returns driven by Chuck Lever, NeilBrown, and others.
  • The addition of a netlink interface for setting the signing key, replacing earlier procfs approaches.

The prior summary (2026-02-19 thread) covered related nfs-utils work, including the nfsdctl module loading improvement, which complements the netlink-based key management introduced in this series.

This Week's Activity

Submission and Application

On February 24, Benjamin Coddington posted the v7 cover letter, explaining the security motivation:

"Filehandles are easy to guess because they are well-formed... Simple testing confirms that the correct generation number can be found within ~1200 minutes using open_by_handle_at() over NFS on a local system and it is estimated that adding network delay with genuine NFS calls may only increase this to around 24 hours."

Coddington noted that unlike local open_by_handle_at(2), which requires CAP_DAC_READ_SEARCH, the NFS server cannot verify remote caller privileges, necessitating additional protection. The proposed solution appends an 8-byte SipHash-2-4 MAC to filehandles for exports with the sign_fh option.

The series consists of three patches:

  1. Add a key for signing filehandles: Introduces a 128-bit secret key configurable via netlink, persisted across reboots.
  2. Add sign_fh export option: Adds the NFSEXP_SIGN_FH flag to enable signing per-export.
  3. Sign filehandles: Implements SipHash-2-4 signing and verification, returning NFS_STALE for invalid or unsigned filehandles on signed exports.

Chuck Lever applied the series to nfsd-testing:

"Applied to nfsd-testing, thanks!"

Post-Merge Bug Report

On February 25, Jeff Layton reported a build failure:

"I get build failures with this patch in place. This function is defined here... and here, and the compiler doesn't seem to like that."

Layton identified a duplicate definition of fh_append_mac() in patch 3/3.

Coddington acknowledged the error:

"I did that thing again where I fixed the tree and didn't regenerate the patch. I will resend this."

Technical Arguments and Design Decisions

Security Model

The series addresses a fundamental weakness in NFS: filehandles are opaque but structurally predictable (e.g., inode + generation number). Without signing, an attacker with network access can brute-force valid filehandles to bypass directory permissions. The 8-byte SipHash-2-4 MAC provides approximately 1 in 2^64 resistance to forgery.

Key Management

The signing key is set once via netlink and cannot be changed afterward, ensuring long-lived filehandles remain valid across server restarts. Coddington explained:

"Because filehandles are long-lived, and there's no method for expiring them, the server's key should be set once and not changed. It also should be persisted across restarts."

Filehandle Size Concerns

Coddington addressed potential overflow of NFSv3's 64-byte filehandle limit:

"The server will refuse to give out filehandles at mount time and emit a pr_warn()."

This approach was chosen because export cache mechanics prevent validation at export time.

Final Conclusions

  • Status: The v7 series has been applied to nfsd-testing, but requires a resend due to a duplicate function definition bug identified by Jeff Layton.
  • Feature Type: New security feature (filehandle signing) for NFSD, not a client-side change.
  • Client Impact: NFS clients will need to handle the extended filehandle format (8-byte MAC appended). Clients receiving unsigned filehandles on signed exports will receive NFS_STALE errors.
  • Next Steps: Coddington indicated he would resend the corrected patch series.

Significance for NFS Development

While this feature targets the server side, it has implications for NFS client development:

  • Clients must accommodate larger filehandles when communicating with servers using signed exports.
  • The NFS_STALE error response for invalid MACs may require client-side retry or fallback logic.
  • This work complements the ongoing netlink transition for NFSD configuration, as demonstrated by the related nfsdctl improvements in nfs-utils 2.8.6-rc1.
