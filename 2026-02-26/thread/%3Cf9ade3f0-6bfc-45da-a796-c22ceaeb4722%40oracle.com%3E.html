NFS v4.2 WRITE_SAME: Status Update — Pivot to fallocate(FALLOC_FL_ZERO_RANGE)

Summary

NFS v4.2 WRITE_SAME: Status Update — Pivot to fallocate(FALLOC_FL_ZERO_RANGE)

Overview

Discussion type: Feature implementation status update (new feature, not a bug fix).

This thread is a brief revival of a discussion that originally began in January 2025 at LSF/MM/BPF. Anna Schumaker had proposed implementing the NFS v4.2 WRITE_SAME operation — a protocol feature that allows a client to write a repeating pattern of data efficiently, reducing network bandwidth and accelerating certain write workloads. The original question was whether such an interface should be exposed through the VFS (making it available to local filesystems as well) or kept internal to NFS via an ioctl().

After a lively debate among kernel developers last year — involving Dave Chinner, Darrick J. Wong, Matthew Wilcox, Christoph Hellwig, Theodore Ts'o, and others — the consensus leaned against a full WRITE_SAME implementation in favor of simpler alternatives. This week's two messages serve as a status update closing the loop on that earlier discussion.

This Week's Activity

Dan Shelton Inquires About Progress

On February 23, Dan Shelton reached out to Anna Schumaker, asking what had become of the WRITE_SAME proposal:

"Anna, what happened with this? Even a pure software implementation (no SCSI acceleration) would be a win, as less space is used on the network wire. For a sample implementation you can use at nfs-ganesha."

Dan Shelton's inquiry highlights the continued interest from the broader NFS community in this optimization, particularly for workloads that write repetitive data patterns. He also offered a reference implementation from nfs-ganesha as a potential starting point.

Anna Schumaker Clarifies the Outcome

Anna responded shortly after, explaining that she had presented the topic at LSF last year but was "talked out of doing a full WRITE_SAME implementation." Instead, she pursued an alternative approach:

"I presented this at LSF last year, and was talked out of doing a full WRITE_SAME implementation. Instead, I did a fallocate(FALLOC_FL_ZERO_RANGE) implementation built on top of NFS v4.2 ALLOCATE and DEALLOCATE calls."

Anna Schumaker's response reveals that the work has pivoted toward fallocate(FALLOC_FL_ZERO_RANGE), which leverages NFS v4.2's ALLOCATE and DEALLOCATE operations — features already supported in the Linux NFS client for sparse file management. This approach addresses a subset of the use case (zero-filling ranges efficiently over the network) without the complexity of a full WRITE_SAME implementation.

Evolution of the Discussion

The original January 2025 thread attracted significant attention from VFS and filesystem maintainers. Key concerns raised included:

  • VFS integration vs. NFS-specific ioctl: Whether such an interface should be generic enough to benefit local filesystems or remain NFS-specific.
  • Protocol complexity: The NFS v4.2 WRITE_SAME operation involves "application data block" structures with offset and length fields that may not map cleanly to a simple VFS API.
  • Practical value vs. implementation cost: Several participants questioned whether the benefit justified the added complexity, particularly given existing alternatives like fallocate.

The decision to pivot toward fallocate(FALLOC_FL_ZERO_RANGE) reflects this deliberation — delivering tangible performance benefits for zero-fill workloads while avoiding the architectural debate over a new VFS-level API.

Significance for NFS Client Development

While this thread does not introduce new patches or bug fixes, it provides valuable context on the direction of NFS v4.2 feature development:

  1. WRITE_SAME is effectively shelved in its original form. The community feedback at LSF led to a reassessment of priorities.
  2. fallocate(FALLOC_FL_ZERO_RANGE) via ALLOCATE/DEALLOCATE represents the chosen path forward for efficient zero-fill operations over NFS. This builds on existing NFS v4.2 sparse file infrastructure already present in the Linux client.
  3. Continued community interest: Dan Shelton's follow-up demonstrates that users and administrators still value network-efficient write patterns, suggesting that further optimizations in this area may be warranted in future development cycles.

Conclusion

This week's brief exchange serves as a postscript to a longer architectural discussion from January 2025. The NFS v4.2 WRITE_SAME operation will not be implemented as originally proposed; instead, the work has been redirected toward fallocate(FALLOC_FL_ZERO_RANGE) using existing NFS v4.2 ALLOCATE and DEALLOCATE calls. This pragmatic pivot delivers real-world benefits for zero-fill workloads while sidestepping the complexities of a new VFS-level API.
