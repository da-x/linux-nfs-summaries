xprtrdma: Fix Receive Queue Drain Hang on Early Exit Paths

Classification

Bug Fix – NFS Client / RPC over RDMA (xprtrdma) subsystem.

Summary

This week, Eric Badger (Pure Storage) submitted a critical bug fix for the xprtrdma subsystem that addresses a potential kernel hang during transport disconnection under memory pressure conditions. The patch was quickly reviewed and approved by Chuck Lever (Oracle).

The Problem: A Hung Task in rpcrdma_xprt_drain()

Eric Badger identified a race condition in the receive queue management logic of the RPC over RDMA client. Specifically, when rpcrdma_post_recvs() fails to create a work request—potentially due to memory allocation failure—or exits early for other reasons, the counter ep->re_receiving was not being decremented.

As Badger explained in his patch description:

"In the event that rpcrdma_post_recvs() fails to create a work request (due to memory allocation failure, say) or otherwise exits early, we should decrement ep->re_receiving before returning. Otherwise we will hang in rpcrdma_xprt_drain() as re_receiving will never reach zero and the completion will never be triggered."

This bug manifests on systems experiencing high memory pressure. The result is a kernel task stuck in an uninterruptible sleep state (D-state), waiting indefinitely for a completion that will never arrive. Badger provided a representative hung task trace showing kworker blocked for over 120 seconds:

"On a system with high memory pressure, this can appear as the following hung task... INFO: task kworker/u385:17:8393 blocked for more than 122 seconds."

The call trace highlights the blockage in rpcrdma_xprt_disconnect, which is called during the autoclose sequence of the transport.

The Fix and History

The patch modifies net/sunrpc/xprtrdma/verbs.c to ensure that re_receiving is decremented on all early exit paths within rpcrdma_post_recvs(). This ensures that the drain logic in rpcrdma_xprt_drain() can properly detect when all receive work requests have been completed or cancelled, allowing the transport disconnection to proceed.

Badger noted that this issue was introduced by a previous change:

"Fixes: 15788d1d1077 ("xprtrdma: Do not refresh Receive Queue while it is draining")"

That prior commit attempted to prevent receive queue refreshes during drain, but inadvertently created a path where the counter could become inconsistent with the actual state of posted work requests.

Review and Acceptance

Chuck Lever, a primary maintainer of the NFS client subsystem, provided a swift review:

"Reviewed-by: Chuck Lever chuck.lever@oracle.com"

The quick turnaround suggests that the bug's impact and the fix's correctness were clear to the maintainers. This patch is important for NFS clients using RDMA transports in environments where memory pressure can cause allocation failures, preventing system hangs during transport cleanup.

Key Technical Arguments

  1. Counter Consistency: The core argument is that ep->re_receiving must accurately reflect the number of outstanding receive work requests. Any early exit from rpcrdma_post_recvs() that does not successfully post a work request must decrement this counter to maintain consistency.
  2. Drain Logic Dependency: The rpcrdma_xprt_drain() function relies on re_receiving reaching zero to signal completion. If the counter is stuck above zero due to an unposted work request, the drain process hangs indefinitely.
  3. Memory Pressure Trigger: The bug is particularly relevant under memory pressure, where allocation failures in ib_post_recv or similar functions are more likely, triggering the early exit paths that lacked the decrement.

Conclusion

This thread represents a straightforward but critical bug fix for the NFS client's RDMA transport layer. By ensuring proper counter management on error paths, the patch prevents kernel hangs during transport disconnection, improving the robustness of NFS over RDMA in resource-constrained environments. The fix was reviewed and accepted without controversy, highlighting the collaborative efficiency of the NFS development community.
