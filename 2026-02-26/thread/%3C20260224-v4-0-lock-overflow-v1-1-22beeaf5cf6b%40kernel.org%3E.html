nfsd: Fix heap overflow in NFSv4.0 LOCK replay cache

Summary

nfsd: Fix Heap Overflow in NFSv4.0 LOCK Replay Cache

Classification

Bug Fix (Security/Stability) – Critical heap corruption vulnerability in the NFS server (nfsd) replay cache mechanism for NFSv4.0 LOCK operations.

Summary

Jeff Layton submitted a patch to address a slab-out-of-bounds write vulnerability in the NFSv4.0 LOCK replay cache. The issue stems from an undersized inline buffer that fails to accommodate large lock owner strings when a LOCK operation is denied due to conflicts. Chuck Lever accepted the fix and applied it to the nfsd-testing tree.

Technical Details

The Vulnerability

The NFSv4.0 replay cache utilizes a fixed 112-byte inline buffer (rp_ibuf[NFSD4_REPLAY_ISIZE]) to store encoded operation responses. As Jeff Layton explained, this size was originally calculated based on OPEN responses and "does not account for LOCK denied responses, which include the conflicting lock owner as a variable-length field up to 1024 bytes (NFS4_OPAQUE_LIMIT)."

When a LOCK operation is denied because it conflicts with an existing lock that has a large owner string, nfsd4_encode_operation() copies the full encoded response into this undersized buffer via read_bytes_from_xdr_buf() without performing bounds checks. This results in:

"a slab-out-of-bounds write of up to 944 bytes past the end of the buffer, corrupting adjacent heap memory."

Attack Vector

The vulnerability can be triggered remotely by an unauthenticated attacker using two cooperating NFSv4.0 clients:

  1. One client sets a lock with a large owner string.
  2. The second client requests a conflicting lock to provoke the denial response.

Layton noted that this bug likely predates the move to git, suspecting it was introduced when support for LOCK and LOCKT was added, and recommended it "should probably go to all stable kernels."

The Fix

Instead of increasing NFSD4_REPLAY_ISIZE (which would increase the size of every stateowner despite most lockowners being small), Layton proposed a bounds-checking approach:

"fix this by checking the encoded response length against NFSD4_REPLAY_ISIZE before copying into the replay buffer. If the response is too large, set rp_buflen to 0 to skip caching the replay payload. The status is still cached, and the client already received the correct response on the original request."

This ensures that while the error status is preserved for replay purposes, the potentially oversized payload is not stored in the undersized inline buffer, preventing heap corruption.

Discussion Evolution

The thread was brief and efficient:

  1. Patch Submission: Jeff Layton submitted the fix, detailed the vulnerability, and credited Nicholas Carlini for reporting and testing the issue.
  2. Acceptance: Chuck Lever applied the patch to nfsd-testing with the commit hash 1e8e9913672a31c6fdd0d237cd3cec88435bd66e.

Conclusion

This fix addresses a critical security and stability issue in the NFS server's replay cache. By implementing bounds checking before copying encoded responses into the inline buffer, the patch prevents heap corruption without imposing unnecessary memory overhead on typical operations. The fix is recommended for backporting to all stable kernels.
