NFSD Buffer Page Management Optimization RFC

Summary

This week, Chuck Lever submitted an RFC patch series titled "[RFC PATCH 0/6] Optimize NFSD buffer page management" Cover Letter. The series addresses two primary issues in the NFS server (NFSD) implementation:

  1. NFSv4 Compound Message Size: Unlike NFSv3, where request and response sizes are complementary, NFSv4 COMPOUNDs can simultaneously have large request and response payloads, potentially exceeding the maximum transport payload size.
  2. CPU Overhead in Page Refilling: With support for payloads larger than 1MB, the alloc_bulk_pages() function walks through a significantly larger array to reset page entries after each RPC. Since most NFS requests consume only a few pages, traversing the entire array is inefficient.

Proposed Changes The series introduces architectural changes to decouple request and reply buffer management:

  • Separate Reply Page Array: Patch 2/6 allocates a distinct rq_respages array for replies, eliminating the complex boundary arithmetic previously required when sharing a single rq_pages array.
  • Optimized Refilling: Patch 5/6 introduces tracking of consumed page entries (rq_pages_nfree) to allow svc_alloc_arg() to refill only the necessary slots rather than scanning the full array (e.g., ~259 slots for 1MB messages).

Discussion and Feedback Neil Brown reviewed the patches, expressing appreciation for the conceptual clarity of splitting the arrays but raising concerns about memory overhead. He noted:

"I don't like that you now allocate twice as many pages. This could have a significant impact on a smaller server... For NFSv3, this is complete waste."

Brown suggested alternative approaches, such as allocating reply pages on-demand or stealing them from the request buffer to avoid the static overhead. He also questioned whether rq_pages was the correct array being tracked for consumption in Patch 5/6, suggesting it might be rq_respages.

Developer Response Chuck Lever responded to these concerns in his reply, defending the design choices:

  • Memory Overhead: He argued that the memory cost is manageable and controlled by the administrator via the number of nfsd threads. With dynamic thread counts, idle servers minimize this impact. "For 16 threads and 1MB maximum payload size, that's an extra 16MB of nailed memory... I don't think it's that significant."
  • NFSv3 Waste: Lever explained that nfsd threads are fungible and must handle all NFS versions, making separate arrays necessary even if NFSv3 doesn't strictly require them.
  • On-Demand Allocation: He rejected on-demand allocation or page stealing, stating: "If NFSD starts stealing pages out of rq_pages for building the reply, then alloc_bulk_pages() will have to walk the entire array to ensure all pages are filled, and that's something I'd like to avoid." He also highlighted the contention costs of on-demand allocation in I/O paths.

Conclusion The discussion remains in the RFC stage. While Neil Brown highlighted valid concerns regarding memory efficiency for smaller servers and NFSv3 workloads, Chuck Lever justified the trade-off as necessary for CPU performance optimization in high-throughput NFSv4 scenarios. No final consensus or merge decision was reached this week; further refinement or benchmarking data may be needed to address the memory overhead concerns.
