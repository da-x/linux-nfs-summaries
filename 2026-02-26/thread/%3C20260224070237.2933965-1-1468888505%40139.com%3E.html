NFS: Fix a Deadlock in nfs_release_folio() During State Recovery

Overview

This week, the Linux NFS mailing list saw the submission of an important bug fix addressing a critical deadlock scenario in the NFS client. The patch, submitted by Li hongliang and authored by Trond Myklebust, targets the stable kernel branch 6.6.y and backports an upstream resolution to a race condition involving memory reclaim and NFSv4.1 state recovery.

Technical Context: The Deadlock

The issue was reported by Wang Zhaolong from Huawei Cloud, who encountered a deadlock where NFSv4.1 state recovery was waiting on kthreadd, while kthreadd itself was blocked attempting to reclaim memory via nfs_release_folio().

As explained in the patch description submitted by Li hongliang:

"Wang Zhaolong reports a deadlock involving NFSv4.1 state recovery waiting on kthreadd, which is attempting to reclaim memory by calling nfs_release_folio(). The latter cannot make progress due to state recovery being needed."

This circular dependency created a system-hanging scenario:

  1. Memory pressure triggers kthreadd to invoke nfs_release_folio() to free pages.
  2. Releasing the folio requires writing back dirty data, which may depend on NFS server state.
  3. If the NFS client is in the middle of state recovery (e.g., after a server reboot or network partition), it cannot proceed with normal I/O operations.
  4. State recovery itself may be blocked waiting for resources that kthreadd holds or for memory reclaim to complete.

The Fix

The resolution, originally upstreamed as commit cce0be6eb4971456b703aaeafd571650d314bcca, modifies the behavior of nfs_release_folio() to avoid blocking on state recovery. Instead of waiting synchronously for writeback completion, the patch introduces an asynchronous approach:

"It seems that the only safe thing to do here is to kick off a writeback of the folio, without waiting for completion, or else kicking off an asynchronous commit."

Key changes include:

  • Modifications to fs/nfs/file.c and fs/nfs/write.c to implement non-blocking folio release logic.
  • Addition of tracing support in fs/nfs/nfstrace.h to aid in debugging similar issues.
  • A new helper or flag in include/linux/nfs_fs.h to support the asynchronous commit path.

The patch fixes a regression introduced by commit 96780ca55e3c, which had attempted to improve page release behavior but inadvertently created this deadlock potential under state recovery conditions.

Significance for NFS Client Development

This fix is critical for production environments using NFSv4.1, particularly in cloud or virtualized settings where server reboots and network interruptions are more common. The deadlock could lead to:

  • Complete system hangs during memory pressure events.
  • Inability to recover from server failures gracefully.
  • Data loss risks if processes are killed due to OOM conditions that cannot be resolved.

By decoupling the folio release from synchronous state recovery dependencies, the NFS client becomes more resilient to concurrent stress scenarios involving both memory pressure and network/server instability.

Conclusion

This week's activity highlights the ongoing effort to harden the NFS client against complex race conditions in production environments. The fix represents a careful balance between memory management requirements and protocol semantics, ensuring that neither subsystem can starve the other during critical recovery operations.
