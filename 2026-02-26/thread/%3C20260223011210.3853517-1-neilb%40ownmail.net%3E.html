Centralizing Directory Locking for Name Ops: VFS, NFSd, and OverlayFS Refactoring

Summary

Overview

Neil Brown submitted version 2 of a 15-patch series titled "Further centralising of directory locking for name ops" 00/15. This series is part of a broader initiative to refactor VFS locking mechanisms, aiming eventually to lock individual names rather than entire directories during name operations. The immediate goal of this series is to consolidate all explicit directory locking (using inode_lock(), lock_rename(), etc.) into new centralized interfaces (start_creating(), start_removing(), etc.), thereby preparing the codebase for future locking rule changes.

The series touches multiple subsystems, including VFS, procfs, libfs, AppArmor, SELinux, NFSd, cachefiles, and significantly, OverlayFS.

Key Technical Arguments and Evolution

Centralization of Locking Interfaces

The core argument driving this series is the elimination of scattered explicit locking calls in favor of unified VFS helpers. Neil Brown noted that previous passes missed several locations where explicit locking remained 00/15.

  • NFSd Changes: Patch 07/15 switches nfsd's purge_old() function to use start_removing_noperm() and end_removing() wrappers, removing explicit locking 07/15. This simplifies the NFS server code and aligns it with the new VFS patterns.
  • SELinux Fix: Chris Mason identified a bug in Patch 06/15 where simple_start_creating() returns -EEXIST instead of ERR_PTR(-ENOMEM), potentially masking the actual error code. Paul Moore acknowledged this, stating:

    "Good catch Chris, yes, please change this Neil and feel free to preserve my ACK." Re: 06/15

OverlayFS Locking and Race Condition Concerns

The most significant changes occur in OverlayFS (patches 09-14/15), where explicit locking is removed in favor of new lookup-and-lock interfaces.

  • TOCTOU Debate: Chris Mason raised a concern regarding Patch 09/15 (ovl: Simplify ovl_lookup_real_one()), which removes inode_lock_nested during the lookup and validation phase. He flagged a potential Time-of-Check-Time-of-Use (TOCTOU) race:

    "The new lockless pattern creates a window where... A concurrent unlink/remove operation unhashes this... The function returns an unhashed dentry." Re: 09/15

    Mason argued that the old code serialized with unhash operations, whereas the new pattern might miss a race where the dentry is unhashed but its d_parent pointer remains valid.

  • Resolution: Amir Goldstein countered this concern, explaining that the lock in the old code was on the overlayfs inode, not the underlying filesystem's inode. Therefore, the check of real->d_parent was never strictly protected against concurrent operations on the underlying fs:

    "The lock not taken on 'dir' which is the overlayfs inode and the checked 'real' dentry is on the underlying fs... it is a mere best effort sanity check, so I think there is no added risk here." Re: 09/15

    Neil Brown agreed with Amir's assessment, confirming that the validation is a point-in-time sanity check and does not require strict serialization for correctness in this context.

Documentation and Cleanup

  • Patch 01/15 improves documentation for try_lookup_noperm() and related functions to clarify that they can return error pointers, not just NULL 01/15.
  • Patch 15/15 unexports lock_rename(), lock_rename_child(), and unlock_rename() as they are now only used internally within fs/namei.c 15/15.

Final Conclusions

The discussion concluded with a consensus that the series is sound, with minor adjustments:

  1. SELinux: Neil Brown agreed to fix the error code preservation issue in Patch 06/15 as requested by Paul Moore and Chris Mason.
  2. OverlayFS: The concern regarding the TOCTOU race in Patch 09/15 was dismissed as a non-issue due to the nature of the sanity check and the scope of the locks involved. Amir Goldstein provided Reviewed-by tags for the OverlayFS patches Re: 09/15, Re: 11/15, and Re: 12/15.
  3. NFSd: The changes to NFSd were accepted without controversy, simplifying the recovery code path.

Neil Brown indicated that this series is expected to land in vfs/ shortly, paving the way for subsequent patches that will implement the actual locking rule changes (locking names instead of directories) in the next merge window 00/15.
