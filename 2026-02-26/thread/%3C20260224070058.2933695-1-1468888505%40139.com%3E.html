NFS: Fix unsafe folio length access in trace events (stable 6.6.y backport)

Summary

NFS Trace Event Safety Fix Backported to Stable 6.6.y

Overview

This week, Li hongliang submitted a two-patch series (this thread covers patch 1/2) backporting an important bug fix to the stable Linux kernel branch 6.6.y. The patch addresses a latent crash in NFS client trace events caused by unsafe use of nfs_folio_length() without proper locking.

Technical Background

The original upstream commit (fada32ed6dbc748f447c8d050a961b75d946055a) was authored by Christoph Hellwig and merged into the mainline kernel, with Anna Schumaker as maintainer. The bug was originally reported by Chuck Lever.

The core issue: the NFS client's trace events for folio operations were calling nfs_folio_length() without holding the folio lock or checking for a NULL ->f_mapping. This is unsafe because:

"nfs_folio_length is unsafe to use without having the folio locked and a check for a NULL ->f_mapping that protects against truncations and can lead to kernel crashes." Li hongliang

The crash scenario was reproducible when running the xfstests generic/065 test with all NFS trace points enabled — a common debugging configuration that exposed the latent race condition.

The Fix

Rather than adding locking around the trace event calls (which would be problematic in tracing contexts), the patch follows the established model used by XFS tracepoints: pass explicit offset and length parameters to the trace events instead of computing them dynamically via nfs_folio_length().

The patch modifies four files:

  • fs/nfs/file.c — 5 lines changed
  • fs/nfs/nfstrace.h — 36 lines changed (the bulk of the work, updating tracepoint definitions)
  • fs/nfs/read.c — 8 lines changed
  • fs/nfs/write.c — 10 lines changed

This approach has a secondary benefit noted in the commit message:

"This has the additional benefit that these values can be more accurate as some of the users touch partial folio ranges." Li hongliang

Bug Classification

This is a bug fix, not a new feature or protocol change. It addresses commit eb5654b3b89d ("NFS: Enable tracing of nfs_invalidate_folio() and nfs_launder_folio()"), which introduced the unsafe tracepoint usage. The fix resolves kernel crashes that occur under specific testing conditions when NFS tracing is enabled.

Significance for NFS Client Development

This patch highlights an important quality-of-implementation concern in the NFS client: trace infrastructure must be robust even under heavy debugging workloads. Tracing should never itself cause crashes, as it is a primary tool developers and administrators use to diagnose problems. The fact that enabling all NFS tracepoints could trigger kernel crashes during standard xfstest runs represents a significant reliability gap for systems running with diagnostics enabled.

The fix also demonstrates the Linux kernel's practice of harmonizing subsystem implementations — by following the XFS model for tracepoint parameter passing, the NFS client benefits from battle-tested patterns already proven in another major filesystem.

Conclusion

This is a clean, well-targeted backport with no discussion thread attached. The patch was submitted directly to the 6.6.y stable tree with minor conflict resolution noted by Li hongliang. Given that this is only patch 1/2 of the series, a companion patch (likely addressing related trace event changes) would be expected in the same submission window.

The fix closes a real crash vector for NFS client debugging scenarios and improves the accuracy of trace data — important for anyone relying on ftrace or similar tools to diagnose NFS performance or correctness issues in production environments.
