SELinux Patch Integration Coordination for VFS Directory Locking Centralization

Summary

This week's activity on Neil Brown's 13-patch series "Further centralising of directory locking for name ops" was brief but procedurally significant: Paul Moore (SELinux maintainer) and Neil Brown coordinated the integration path for patch 05/13, which converts SELinux to use simple_start_creating() / simple_done_creating(). The discussion resolved a merge-dependency concern that could have blocked downstream VFS work.

Context: Prior Weeks

As summarized in prior weeks, this series is a VFS refactoring effort aimed at transitioning directory locking from whole-directory locks to per-name locking. Patch 05/13 specifically converts SELinux security module code to the new API. The NFS server impact (patch 06/13) was already reviewed by Jeff Layton in the initial round, and overlayfs patches generated substantial technical debate around lock reacquisition semantics.

This Week: Merge Path Coordination

On February 20, Paul Moore raised a practical question about whether he could take just patch 05/13 into the SELinux tree independently after the merge window closes:

"Unless I'm missing something, there is no reason why I couldn't take just this patch into the SELinux tree once the merge window closes, yes?" As mentioned by Paul Moore

Neil Brown confirmed this was feasible but revealed a critical dependency: a subsequent batch of patches depends on the new start_creating API being used universally. For VFS maintainer Christian Brauner to apply that follow-up work, he would need to pull this SELinux patch from Paul Moore's tree:

"Once this series lands (hopefully soon - I will resend after -rc1 is out) I have another batch which depends on the new start_creating etc API being used everywhere. So for Christian to be able to apply that, he will need to pull in this patch from the SELinux tree." As mentioned by Neil Brown

Brown requested that Moore apply the patch to a branch and make it available for merging with the VFS work:

"So if you could apply just this patch to some branch and merge that branch with your other work however works best for you, and make the branch available, then I think Christian will be happy to merge that with whatever vfs branch he includes my work in, and all should be good." As mentioned by Neil Brown

Paul Moore acknowledged the dependency and provided his formal approval:

"Okay, thanks for letting me know. I was curious about something like that based on the cover letter, but the timing wasn't clear." As mentioned by Paul Moore

"Acked-by: Paul Moore paul@paul-moore.com" As mentioned by Paul Moore

Neil Brown thanked him, closing the exchange.

Classification and Significance

This discussion is about merge coordination for a VFS refactoring, not a new feature, protocol change, or bug fix. The SELinux patch itself is an API migration with no functional changes to security behavior. Its importance lies in unblocking downstream VFS work: without this patch landing in the SELinux tree, Christian Brauner cannot integrate the subsequent batch of patches that depend on universal adoption of the new start_creating API.

NFS Client Relevance

This thread has no direct impact on NFS client development. The NFS server component (patch 06/13, converting purge_old() in nfs4recover.c) was reviewed and approved in prior weeks. No bug fixes or client-facing changes were discussed this week.

Conclusion

The SELinux integration path for patch 05/13 is now clear: Paul Moore will take the patch into the SELinux tree, and the branch will be made available for Christian Brauner to merge alongside the broader VFS directory locking centralization work. This coordination removes a potential blocker for the follow-up patch series that depends on universal adoption of the new API.
