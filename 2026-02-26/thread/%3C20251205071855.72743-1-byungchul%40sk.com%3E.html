DEPT v18: Finalizing Type Safety and Rust Helper Conventions

Overview

This thread is part of Byungchul Park's 42-patch v18 series introducing DEPT (DEPendency Tracker), a new kernel subsystem designed to detect deadlock possibilities by tracking wait/event dependencies rather than lock acquisition order — complementing the existing Lockdep infrastructure. This discussion is classified as a new feature (kernel infrastructure), not an NFS-specific change or bug fix. However, DEPT has potential future relevance for NFS client/server deadlock detection, given the complex wait/event patterns in NFS code paths (e.g., RPC call completions, delegation recall handling).

Prior Context (Bridged Briefly)

In prior weeks, Petr Pavlu (SUSE) provided detailed review of patch 34/42 (module support for struct dept_event_site and dept_event_site_dep), raising concerns about type safety, section lifetime optimization, coding style (extern usage), and whether "used" checks could be performed at build time rather than runtime. Dirk Behme reviewed patch 31/42 (assigning unique dept_key to each distinct wait_for_completion() caller), suggesting the addition of the __rust_helper attribute to a new Rust helper function. Byungchul Park responded on February 13, agreeing to most suggestions and asking clarifying questions about pointer counting with typed declarations. Petr followed up on February 18 with concrete code examples for properly typed array declarations, drawing parallels to the initcalls mechanism.

This Week's Activity (Feb 20–27)

This week saw two brief acknowledgment messages from Byungchul Park on February 23, resolving the outstanding review items.

Agreement on Type-Safe Function Signatures (Patch 34/42)

In response to Petr Pavlu's February 18 clarification, Byungchul confirmed he understood the proposed type-safe approach for dept_mark_event_site_used():

"I got what you meant. I will. Thanks." Byungchul Park

Petr's suggestion was to change the function signature from accepting generic void* pointers to properly typed struct dept_event_site_init ** parameters:

void dept_mark_event_site_used(struct dept_event_site_init **start,
			       struct dept_event_site_init **end)

This enables compiler-enforced type checking, catching mismatches between the function arguments and the module::dept_event_sites section. Petr had explained that initcalls already follow this pattern with properly typed array declarations in include/linux/init.h. Byungchul's acknowledgment signals acceptance of this refinement for the next patch revision.

Agreement on Rust Helper Convention (Patch 31/42)

In response to Dirk Behme's February 15 suggestion, Byungchul agreed to add the __rust_helper attribute to the new Rust helper function in patch 31/42:

"I will. Thanks." Byungchul Park

Dirk had referenced a recent commit in linux-next that established the __rust_helper convention for Rust helper functions, ensuring consistency with kernel-wide Rust integration practices.

Significance for NFS Development

While this thread does not directly involve NFS code, the DEPT subsystem's maturation has indirect importance:

  1. Deadlock detection for complex wait patterns: NFS client operations involve intricate wait/event dependencies (RPC completions, page lock waits, delegation recalls) that are invisible to Lockdep. DEPT could eventually help uncover latent deadlock conditions in these paths.
  2. Module support correctness: The reviewed patch ensures DEPT works properly with loadable kernel modules — essential since many filesystems and network stacks are modularized.
  3. Rust integration readiness: As the kernel expands Rust support, proper helper conventions (as discussed in patch 31/42) lay groundwork for future Rust-based NFS subsystem components.

Conclusion

This week's activity was brief but conclusive: Byungchul Park acknowledged and accepted both of the outstanding review items — Petr Pavlu's type-safety refinement for module event site marking and Dirk Behme's Rust helper attribute convention. These represent the final known review comments on these two patches as of this window. The DEPT series continues its iterative refinement toward eventual merge, with no blocking objections remaining on these specific patches.
