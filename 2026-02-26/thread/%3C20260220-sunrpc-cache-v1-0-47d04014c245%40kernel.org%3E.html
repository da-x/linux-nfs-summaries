Summary

sunrpc: Cache Infrastructure Scalability Improvements and Bug Fixes

This week, Jeff Layton introduced a three-patch series aimed at improving the scalability of the SUNRPC cache infrastructure, primarily to facilitate future work on retrofitting netlink upcalls. The patches were quickly applied by Chuck Lever, but Neil Brown’s review uncovered two issues: unnecessary spinlock usage in the new code and a pre-existing bug in reader count handling that was exposed by the refactoring.

Discussion Evolution

Initial Proposal

Jeff Layton introduced the series on February 20, noting that the existing cache infrastructure relied on a global spinlock and waitqueue, which created contention across different cache instances (e.g., auth.unix.ip vs. nfsd.fh).

The series consisted of:

  1. Converting queue_lock from a global spinlock to a per-cache_detail lock.
  2. Converting queue_wait from a global waitqueue to a per-cache_detail waitqueue.
  3. Splitting the single interleaved cache_detail->queue into two dedicated lists: one for cache requests and one for cache readers, using a sequence number mechanism to track reader positions.

Layton stated:

"I've been working on trying to retrofit a netlink upcall into the sunrpc cache infrastructure. While crawling over that code, I noticed that it relies on both a global spinlock and waitqueue."

He requested consideration for the v7.1 kernel release.

Rapid Acceptance

Chuck Lever applied the series to the nfsd-testing tree on the same day, acknowledging the cleanups and scalability benefits.

Review and Bug Discovery

Neil Brown reviewed Patch 3/3 on February 21, identifying two issues:

  1. Unnecessary Spinlocks: Brown noted that the new code retained spinlock acquisitions around operations that no longer required them due to the structural changes. He pointed out:

    "I don't think we need the spin_lock here any more."

  2. Pre-existing Bug in Reader Counting: Brown observed that when decrementing the ->readers count, the code failed to check if it reached zero and clear CACHE_PENDING, a pattern present elsewhere in the codebase. He remarked:

    "Hmm.. The other place where we decrement ->readers we then check if it is zero and if CACHE_PENDING is clear - and do something. I suspect we should do that here. This bug (if I'm right and it is a bug) if there before you patch, but now might be a good time to fix it?"

Resolution

Jeff Layton acknowledged both points on February 23, agreeing that the spinlock removals were valid and confirming the bug fix was necessary. He planned to release a v2 of the series:

"Good catch. I'll add a patch to fix that preceding these patches, so it can go to stable (if we think that's worthwhile)... Thanks for the review! I'll send a v2 with the spinlock fixes and the above bugfix."

Key Technical Arguments

  • Scalability: The primary motivation was reducing contention by eliminating global locks and waitqueues in the SUNRPC cache layer, which is critical for high-concurrency NFS client and server operations.
  • Code Simplification: Splitting the queue into request and reader lists simplified the logic for tracking reader positions using sequence numbers instead of list traversal.
  • Bug Fix: The identified bug involved improper handling of the ->readers count, which could lead to stale cache entries not being cleaned up properly when the last reader detached.

Final Conclusions

The initial v1 series was applied but will be superseded by a v2 that addresses Neil Brown’s feedback. The v2 will include:

  • Removal of unnecessary spinlock acquisitions in cache_read.
  • A fix for the pre-existing bug where CACHE_PENDING was not cleared when the last reader detached, ensuring proper cache entry lifecycle management.

This work represents an important step in modernizing the SUNRPC cache infrastructure, paving the way for netlink-based upcalls and improving overall NFS client/server scalability.
