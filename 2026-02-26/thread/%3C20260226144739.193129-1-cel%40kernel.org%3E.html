NFSD Buffer Page Management: v2 of Chuck Lever's SUNRPC page-array series posted

Summary

NFSD Buffer Page Management: v2 Posted (SUNRPC server-side)

What happened this week

On Thursday, 2026-02-26, Oracle's Chuck Lever re-posted his six-patch series "[PATCH v2 0/6] Optimize NFSD buffer page management" Cover Letter to linux-nfs. This is the second iteration of a series that first appeared as an RFC earlier this same week (2026-02-22), where it drew review comments from Neil Brown. No replies landed within this reporting window — the next substantive review activity (from Jeff Layton) came on 2026-03-10, outside the scope of this summary.

Classification: server-side optimization + latent bug hardening

Although this thread lives on the NFS list and touches client-visible behavior (large NFSv4 COMPOUNDs), the work is squarely in NFSD / SUNRPC server code (net/sunrpc/svc.c, svc_xprt.c, svcsock.c, xprtrdma/*). It combines:

  • a protocol-capability fix: NFSD's buffer sizing must accommodate NFSv4 COMPOUNDs whose combined request+response footprint exceeds the maximum transport payload size;
  • a performance optimization: stop scanning whole page arrays on every RPC; and
  • several correctness/robustness fixes (tightened bounds checks, NULL-entry handling).

The two problems Lever sets out to solve

The cover letter frames the motivation crisply. First, the buffer-sizing problem:

"NFSv3 operations have complementary Request and Response sizes... The sum of the two message sizes is never more than the maximum transport payload size. So NFSD could get away with maintaining a single array of pages, split between the RPC send and Receive buffer."

"NFSv4 is not as cut and dried. An NFSv4 client may construct an NFSv4 COMPOUND that is arbitrarily complex, mixing operations that can have large Request size with operations that have a large Response size. The resulting server-side buffer size requirement can be larger than the maximum transport payload size."

Second, the CPU-cost problem:

"Due to the above, and because NFSD can now handle payload sizes considerably larger than 1MB, the number of array entries that alloc_bulk_pages() walks through to reset the rqst page arrays after each RPC completes has increased dramatically."

"But we observe that the mean size of NFS requests remains smaller than a few pages... The CPU cost of walking these arrays is noticeable in 'perf' captures."

Patch-by-patch walkthrough

  1. Tighten bounds checking in svc_rqst_replace_page — A correctness fix that also paves the way for the architectural change. The reply-building path validated rq_next_page against the entire rq_pages array, but the true valid range is narrower:

    "The bounds check validates rq_next_page against the full rq_pages array, but the valid range for rq_next_page is [rq_respages, rq_page_end]. Use those bounds instead."

    Lever notes this is safe today only because both pointers index into rq_pages, and it "prepares for a subsequent change that separates the Reply page array from rq_pages."

  2. Allocate a separate Reply page array — The architectural centerpiece. Today struct svc_rqst uses one dynamic rq_pages array for both the incoming Call and outgoing Reply, with rq_respages as a sliding boundary pointer that each transport receive path must compute:

    "This boundary tracking is a source of confusion and bugs, and prevents an RPC transaction from having both a large Call and a large Reply simultaneously."

    The fix allocates rq_respages as its own array, "following the precedent set by rq_bvec (a separate dynamically-allocated array for I/O vectors)." Lever is candid about the cost — "Each svc_rqst now pins twice as many pages as before. For a server running 16 threads with a 1MB maximum payload, the additional cost is roughly 16MB of pinned memory" — and pre-empts alternatives:

    "We've considered several alternatives to maintaining a full second array. Each alternative reintroduces either boundary logic complexity or I/O-path allocation pressure."

  3. Handle NULL entries in svc_rqst_release_pages — A defensive fix for a state the next patches will create: after preserving rq_next_page (patch 4), the range [rq_respages, rq_next_page) "can contain NULL entries where pages have already been transferred to a send context." The release path is changed to iterate entry-by-entry, skipping NULLs.

  4. svcrdma: preserve rq_next_page in svc_rdma_save_io_pages — Removes a workaround. The RDMA send path used to reset rq_next_page back to rq_respages, "hiding the NULL region from svc_rqst_release_pages()." Now that NULLs are handled, dropping the reset preserves the invariant that [rq_respages, rq_next_page) "accurately describes how many response pages were consumed."

  5. Track consumed rq_pages entries — The first half of the CPU optimization. Two transport receive paths NULL out rq_pages entries (TCP multi-fragment reassembly via svc_tcp_save_pages(), and RDMA via svc_rdma_clear_rqst_pages()). A new rq_pages_nfree field records how many were nulled so svc_alloc_arg() "refill[s] only those entries rather than scanning the full rq_pages array... instead of the full ~259 slots (for 1MB messages)."

  6. Optimize rq_respages allocation in svc_alloc_arg — The second half: svc_alloc_arg() was calling alloc_pages_bulk() with the full rq_maxpages count "causing a full-array scan despite most slots holding valid pages." Since only [rq_respages, rq_next_page) contains NULLs after each RPC, the fill is now limited to that range.

Evolution from RFC → v2 and open items

The v2 cover letter documents what changed since the RFC: "Clarify a number of comments based on review (NeilBrown)" and, notably, flags an unresolved point — "Possible NFSv3 waste is still open for discussion." That echoes Neil Brown's earlier concern that pinning twice as many pages is "complete waste" for NFSv3-only servers; Lever's v2 keeps the design but leans on the dynamic svc thread count facility to keep idle-server overhead minimal.

Status

As of the end of this week, the series is at v2 with no in-window review replies. The discussion is a server-side performance/correctness effort rather than a client bug fix; the nearest client-visible impact is that NFSD can now safely serve arbitrarily large NFSv4 COMPOUNDs. Watch for Jeff Layton's reviews (posted 2026-03-10, next week) and any resolution of the open NFSv3 memory-waste question.
