OPENAT2_REGULAR Flag Proposal for openat2 (v4)

Summary

OPENAT2_REGULAR Flag: New Security-Oriented openat2 Feature Proposal

Overview

This week, Dorjoy Chowdhury submitted version 4 of a patch series introducing a new OPENAT2_REGULAR flag for the openat2() system call. This is a new feature request originating from the uapi-group's kernel feature suggestions, aimed at improving security by allowing programs to explicitly require that opened paths are regular files, thereby preventing accidental or malicious opening of device nodes with special semantics.

The series touches multiple filesystems, including NFS, and introduces a new error code EFTYPE for cases where a non-regular file is encountered when the flag is specified.

Key Technical Arguments

The OPENAT2_REGULAR Flag

The core patch introduces the OPENAT2_REGULAR flag, which Chowdhury describes as:

"This flag indicates the path should be opened if it's a regular file. This is useful to write secure programs that want to avoid being tricked into opening device nodes with special semantics while thinking they operate on regular files."

Key behaviors defined in the patch:

  • If openat2() is called on a non-regular file (e.g., /dev/null) with OPENAT2_REGULAR, it returns -EFTYPE.
  • When combined with O_CREAT, either a regular file is created, or if the path already exists, it is opened only if it is a regular file; otherwise, -EFTYPE is returned.
  • Combining OPENAT2_REGULAR with O_DIRECTORY returns -EINVAL, as Chowdhury notes:

"it doesn't make sense to open a path that is both a directory and a regular file."

NFS Client Impact

The patch series updates the NFS client's atomic_open codepath in fs/nfs/dir.c to handle the new flag. In the cover letter, Chowdhury states:

"In this version, I have tried to properly update the filesystems that provide atomic_open (fs/ceph, fs/nfs, fs/smb, fs/gfs2, fs/fuse, fs/vboxsf, fs/9p) for the new OPENAT2_REGULAR flag."

The NFS-specific change modifies fs/nfs/dir.c with 4 insertions and 1 deletion, ensuring that the NFS client respects the OPENAT2_REGULAR constraint during atomic open operations. Chowdhury notes that some filesystems (FUSE, vboxsf, 9p) did not require changes because they "always create new file which is a regular file" in their O_CREAT code paths.

Architecture-Specific Cleanup

Two additional patches convert O_* flag macros from hex to octal for SPARC and MIPS architectures, aligning them with the convention used in include/uapi/asm-generic/fcntl.h.

Testing

A kselftest patch adds a "happy path" test for the new flag, though Chowdhury admits limited testing scope:

"I only tested this new flag on my local system (fedora btrfs)."

Evolution of the Discussion

This is version 4 of the series. The cover letter outlines the progression through previous versions:

  • v1: Initial submission with O_REGULAR and ENOTREGULAR.
  • v2: Renamed error code to ENOTREG, defined it in architecture-specific errno headers, and handled flag clashes on alpha, SPARC, and parisc.
  • v3: Added motivation regarding security against device node tricks, fixed a commit message error referencing the wrong error code, corrected a flag value on parisc, and added architecture cleanup patches.
  • v4: Renamed O_REGULAR to OPENAT2_REGULAR, ensured the flag does not affect O_PATH, updated all atomic_open codepaths, and included the uapi-group URL in the commit message.

Chowdhury also notes that a previous v4 submission was ignored because it lacked proper maintainer CCs:

"Note that I had submitted a v4 previously (that had -EINVAL for the atomic_open code paths) but did not do a get_maintainers.pl. It didn't get any review and please ignore that one anyway."

Delivery Issues

In a follow-up message, Chowdhury expressed concern about the patch series appearing incomplete on lore.kernel.org:

"I am not sure if my patch series made it properly to the mailing lists. https://lore.kernel.org/linux-fsdevel/ is showing a broken series, only the 2/4, 3/4, 4/4 and I don't see cover-letter or 1/4."

He questioned whether there are limitations on sending patches with large CC lists via Gmail and asked if he should prune the list and resend.

Final Conclusions

As of this week's window, no external review or feedback has been received on this patch series. The thread consists solely of Chowdhury's submission and his follow-up regarding delivery issues. Key takeaways:

  1. Feature scope: The OPENAT2_REGULAR flag is a security-enhancing feature that allows applications to ensure they only open regular files, preventing unintended interaction with device nodes.
  2. NFS client changes: The NFS client's atomic_open implementation in fs/nfs/dir.c has been updated to respect the new flag, ensuring consistency across filesystems.
  3. Awaiting review: The series is pending maintainer and community feedback. Chowdhury's concerns about delivery may affect visibility and timely review.
