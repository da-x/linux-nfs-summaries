Debate Over xattr-Based Ownership Side-Channel for NFS ID-Mappings

Summary

This week's activity in the [LSF/MM/BPF TOPIC] VFS idmappings support in NFS thread centered on a heated debate about alternative implementation strategies for supporting UID/GID remapping in NFS. The discussion, which began last week with Alexander Mikhalitsyn's proposal and use-case clarifications from LXC/Incus and Kubernetes communities, evolved this week into a technical disagreement between Demi Marie Obenour and Christian Brauner over whether extended attributes (xattrs) should be used as an ownership side-channel.

Discussion Overview

Last week concluded with agreement on a phased approach: starting with simple AUTH_SYS cases where UID conversion could happen at the RPC client layer without protocol extensions, while acknowledging that AUTH_GSS and NFSv4 idmapping would require more sophisticated solutions. This week, Demi Marie Obenour entered the conversation with an alternative proposal for handling ownership information when servers cannot store files with the VFS-mapped UIDs/GIDs.

Key Technical Arguments

The xattr Proposal

Demi Marie Obenour proposed a workaround originally developed for virtiofsd: storing mapped UID and GID values as user.* extended attributes (xattrs). As quoted by Christian Brauner in his response 1:

"I proposed a workaround for virtiofsd [1] that I will also propose here: store the mapped UID and GID as a user.* xattr. This requires no special permissions, and so it completely solves this problem. It is also the only solution I know of that scales to NFS servers"

This approach addresses the fundamental problem that NFS servers (and virtiofsd) "simply will not (and, for security reasons, must not) allow" storing files with UIDs/GIDs that differ from what the VFS layer expects.

Christian Brauner's Strong Opposition

Christian Brauner responded on February 24 with an emphatic rejection of using xattrs as an ownership side-channel:

"xattrs as an ownership side-channel are an absolute clusterfuck. The kernel implementation for POSIX ACLs and filesystem capabilities that slap ownership information that the VFS must consume on arbitraries inodes should be set on fire." 1

Brauner outlined several technical concerns:

  1. Performance: Fetching ownership data from disk, caching it in a global format, and performing in-place translation adds significant overhead.
  2. Complexity: Permission checking becomes "a completely nightmare" due to the need to parse ownership out of binary data stored alongside the inode.
  3. Brittleness: The approach "won't nest, performance will suck, and it will be brittle to get this right imho."

However, Brauner clarified that his opposition was specifically regarding kernel-space consumption of xattr-based ownership:

"Nowever, if userspace wants to consume ownership information by storing arbitrary ownership information as user.* xattrs then I obviously couldn't care less" 1

Idmapped Mounts Without User Namespaces

Brauner also clarified that idmapped mounts are already decoupled from user namespaces and can support features like ID squashing:

"It's easy to support idmapped mounts without user namespaces. They're completely decoupled from them already for that purpose so they can support id squashing and so on going forward. The only thing that's needed is to extend the api so that we can specific mappings to be used for a mount." 1

He noted this capability is also valuable for local filesystems that need to expose files with different ownership at different locations without involving namespaces.

Evolution of the Discussion

The thread progressed from last week's consensus on a phased implementation approach to this week's debate over alternative solutions:

  1. Last Week: Agreement to start with AUTH_SYS cases, handling UID conversion at the RPC client layer as summarized in the prior week.
  2. This Week (Feb 21): Demi Marie Obenour proposed the xattr-based workaround 1, arguing it scales to NFS servers where other approaches fail.
  3. This Week (Feb 24): Christian Brauner strongly opposed the xattr approach for kernel-space use but acknowledged its viability for userspace consumption 1.
  4. This Week (Feb 24): Demi Marie Obenour responded, though the content of this message was not available in plain text 1.

Final Conclusions

This week's discussion did not reach a definitive conclusion but clarified important boundaries:

  1. xattrs for userspace: Brauner acknowledged that using xattrs as an ownership side-channel is acceptable if consumed only by userspace, though he warned of performance and nesting issues.
  2. Idmapped mount API extension: Brauner suggested extending the mount API to specify mappings directly, which would support id squashing and other features without relying on user namespaces.
  3. No consensus on NFS implementation path: The debate highlights the tension between practical workarounds (xattrs) that scale to existing NFS servers and kernel-design principles that favor cleaner, more performant solutions.

The discussion remains focused on feature development rather than bug fixes, with implications for NFS client development in containerized environments where UID/GID remapping is essential for security isolation.
