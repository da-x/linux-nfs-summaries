NFSv4 State Revocation on Unmount: Pivot to fsnotify

Summary

Automatic NFSv4 State Revocation on Filesystem Unmount: VFS Mechanism Debate

Overview

This week, Chuck Lever submitted version 3 of a patch series aimed at automating the revocation of NFSv4 state when an underlying filesystem is unmounted. The primary goal is to eliminate EBUSY errors during unmount operations caused by client-held opens, locks, and delegations, thereby improving automation workflows for containerized NFS servers and orchestration systems.

The discussion this week focused heavily on the VFS mechanism proposed in Patch 1/3: a new SRCU-based umount notifier chain. VFS maintainers raised significant concerns regarding namespace isolation and the proliferation of ad-hoc notifiers, leading to a pivot toward using existing fsnotify infrastructure instead.

Key Technical Arguments

The Problem: Manual State Revocation

Chuck Lever highlighted that manual intervention via /proc/fs/nfsd/unlock_fs is "tedious, error-prone" and breaks automation. The series aims to automatically revoke opens, locks, delegations, and cancel async COPY operations upon unmount, sending NFS4ERR_ADMIN_REVOKED to clients As mentioned by Chuck Lever.

Concern 1: Namespace Isolation and Event Flooding

Al Viro and Christian Brauner identified a critical flaw in the proposed per-mount notifier chain: it does not adequately account for mount namespaces.

"So anyone can force that just with unshare -U -m date? Creates a new namespace, populated by clones of all mounts you see... At that point all cloned mounts are released, each triggering your notifier chain..." Al Viro

Christian Brauner expanded on this, warning that common operations like systemd service spawns or container runtime starts could flood the system with notifications:

"I'm pretty sure that is not what you want and that is defo not what the VFS should do..." Christian Brauner

Concern 2: Ad-hoc Notifiers vs. Unified Infrastructure

Brauner argued against adding another custom notification mechanism to the VFS, describing ad-hoc notifiers as "horrific." He proposed extending fsnotify to allow filesystems to register "internal watches" on mounts and superblocks:

"Can we extend fsnotify so that it's possible for a filesystem to register 'internal watches' on relevant objects such as mounts and superblocks and get notified and execute blocking stuff if needed. Then we don't have to add another set of custom notification mechanisms but have it available in a single subsystem and uniformely available." Christian Brauner

The Proposed Solution: Leveraging fsnotify

Amir Goldstein and Jan Kara supported the fsnotify approach. Amir noted that FS_UNMOUNT events are already sent to inodes during unmount and suggested that NFSD could register for these events on the export root path:

"I don't see a problem with nfsd registering for FS_UNMOUNT event on sb (once we add it). As a matter of fact, I think that nfsd can already add an inode mark on the export root path for FS_UNMOUNT event." Amir Goldstein

Jan Kara confirmed this direction:

"Yeah, then as Amir writes placing a mark with FS_UNMOUNT event on the export root path and handling the event in nfsd_file_fsnotify_handle_event() should do what you need?" Jan Kara

Evolution and Conclusion

Chuck Lever accepted the feedback, agreeing with Al Viro's namespace concerns and expressing willingness to adopt the mechanism preferred by VFS maintainers:

"I agree with Al's earlier comment and have added some protection there for the next revision of the series... I'm happy to try whatever mechanism VFS maintainers are most comfortable with." Chuck Lever

Final Status: The discussion concluded with a consensus to replace the proposed SRCU umount notifier chain with an fsnotify-based solution using FS_UNMOUNT events on the export root inode. This avoids namespace flooding issues and aligns with existing VFS infrastructure. The NFSD-specific patches (2/3 and 3/3) regarding state revocation and file cache cleanup remain largely intact but will depend on the revised VFS hook in the next version of the series.
