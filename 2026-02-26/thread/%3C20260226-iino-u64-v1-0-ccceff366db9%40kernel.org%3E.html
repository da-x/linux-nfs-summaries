vfs: change inode->i_ino from unsigned long to u64 (61-patch series)

Summary

vfs: Widen inode->i_ino to u64 — A 61-Patch Overhaul Lands on the List

Overview

On February 26, 2026, Jeff Layton posted a sweeping 61-patch series titled "vfs: change inode->i_ino from unsigned long to u64" announced in the cover letter. The series touches 195 files with 1,101 insertions and 1,166 deletions, spanning VFS core, tracepoints, and virtually every filesystem in the kernel. This is a protocol/architecture change rather than a bug fix: it eliminates a long-standing limitation where 32-bit architectures could only store a 32-bit inode number in struct inode, forcing filesystems like NFS, CIFS, XFS, Ceph, and FUSE to implement XOR-folding hacks.

Motivation and Background

Layton kicked off the series with an explicit nod to Christian Brauner's earlier green light:

"Christian said [1] to 'just do it' when I proposed this, so here we are!"

The core problem is historical: inode->i_ino has been unsigned long for decades, meaning it's only 32 bits on 32-bit architectures. This forced filesystems to "implement hacks to hash a 64-bit identifier into a 32-bit field, and deprives us of a universal identifier field for an inode."

Layton also noted that much of the mechanical work was LLM-assisted:

"Much of this set was generated by LLM, but I attributed it to myself since I consider this to be in the 'menial tasks' category of LLM usage."

NFS Client Impact (Patches 08–11)

The NFS client is one of the primary beneficiaries. The series includes four dedicated patches:

  • PATCH 08/61 simplifies nfs_fileid_to_ino_t() to return u64 directly and updates format strings across fs/nfs/dir.c, file.c, inode.c, nfs4proc.c, pnfs.c, and the flexfiles/filelayout modules.
  • PATCH 09/61 removes nfs_fattr_to_ino_t() and nfs_fileid_to_ino_t() entirely, since they become trivial identity functions.
  • PATCH 10/61 removes nfs_compat_user_ino64(), the XOR-folding hack that truncated 64-bit inode numbers for 32-bit userspace. The VFS stat path now handles narrowing to 32-bit st_ino with -EOVERFLOW natively.
  • PATCH 11/61 removes the now-obsolete enable_ino64 module parameter, which previously controlled whether NFS presented 64-bit or XOR-folded 32-bit inode numbers.

This is a significant cleanup for NFS client users on 32-bit platforms who have long dealt with truncated or folded inode numbers in stat() output and directory listings.

Key Technical Discussion Points

Patch Structure and Bisection

Matthew Wilcox raised the first substantive question about the patch organization:

"Why are the format strings all done as separate patches? Don't we get bisection hazards by splitting it apart this way?"

Layton responded pragmatically:

"One big patch would be Yuuuuge. We could certainly do it that way, but it'll be nightmare if we ever do have to revert part of it."

VFS Core API Changes (Patch 01)

Jan Kara reviewed PATCH 01/61 which widens the inode hash/lookup functions (hash(), find_inode_fast(), iget_locked(), ilookup5(), etc.) to accept u64 parameters. He initially gave a "Reviewed-by" but then suggested an alternative approach:

"Thinking some more about this (and also seeing the discussion about patch 2) - maybe instead of using explicit u64 we should typedef kino_t as u64 and use that?"

Damien Le Moal raised a structural concern about patch ordering:

"the type of ino in struct inode is changed in patch 2, not this patch. So this feels incorrect. Why not just squash patch 2 in here?"

Trace Event Concerns (Patch 03)

Steven Rostedt provided detailed feedback on PATCH 03/61, warning about binary trace format changes on 32-bit systems:

"on 32 bit systems, this will likely cause 'holes' in a lot of these events."

He recommended reordering fields so that u64 fields come before smaller types to avoid padding:

"Might be better to reorder any of these that have int first. u64 inode; int obj; Will be packed tighter than: int obj; u64 inode;"

Jan Kara also flagged unnecessary explicit casts in the trace definitions, and Layton acknowledged: "Good catch. I'll clean those up." Damien Le Moal similarly noted redundant (unsigned long long) casts before giving his Reviewed-by.

NFS Server (nfsd) Format Strings (Patch 12)

Chuck Lever reviewed PATCH 12/61 and suggested consistency:

"Let's use the %llu format specifier consistently for inode->i_ino, which is unsigned."

Layton agreed: "Good plan. I'll have claude do a pass for that in the next set."

Missed Format Strings (Patches 17, 51, 57)

Several reviewers caught missed spots:

  • Viacheslav Dubeyko flagged nilfs2's inode=%lu placeholders that print a local le64_to_cpu() value rather than i_ino directly. Layton explained these were intentionally left for a later cleanup pass to keep the series focused.
  • Paul Moore noted that SELinux hooks had additional pr_notice_ratelimited() and pr_warn() calls printing inode numbers that needed updating.
  • Eric Biggers caught a more subtle bug: "check_for_busy_inodes() needs to be updated too. It copies i_ino to a local variable of type 'unsigned long', then prints it with %lu. Seems that there needs to be a search for other code that copies i_ino to a local variable, as this issue is unlikely to be unique to here."

Conclusions and Next Steps

The thread is in active review with positive momentum. Key takeaways:

  1. This is an architecture-level change, not a bug fix, though it effectively fixes the long-standing 32-bit inode truncation problem for NFS and other network filesystems.
  2. NFS client cleanup is substantial: removal of nfs_compat_user_ino64(), the enable_ino64 module parameter, and the folding helpers represents a significant simplification of the NFS client codebase.
  3. A v2 is expected to address: unnecessary casts in trace events, field reordering for 32-bit alignment, consistent %llu usage, missed format strings (SELinux, fscrypt), and possibly the kino_t typedef suggestion from Jan Kara.
  4. The series was explicitly scoped to be minimal: Layton deferred inode structure shrinkage (e.g., eliminating nfs_inode.fileid) to follow-up work: "I'd rather leave that sort of cleanups for later just to keep this simple."
