VFS Lease Opt-In Series: Post-Application Quiet Period

Summary

Overview

This week saw minimal activity on Jeff Layton's 24-patch series to require filesystems to explicitly opt-in to lease support. The sole message was from Mike Snitzer on February 25, which contained no substantive technical content — essentially a silent acknowledgment or empty reply to the final patch in the series (patch 24/24: "fs: remove simple_nosetlease()").

Classification

This thread concerns a VFS protocol/architectural change — not a bug fix or new feature per se, but a structural improvement to prevent future regressions in lease and delegation handling. The change has significant implications for NFS client and server development, as NFS and SMB are the primary consumers of kernel file leases and delegations.

Prior Weeks Bridge (January 8 – February 19)

The 24-patch series was originally posted on January 8 by Jeff Layton, who explained the motivation:

"For historical reasons, when ->setlease() file_operation is set to NULL, the default is to use the kernel-internal lease implementation. This means that if you want to disable them, you need to explicitly set the ->setlease() file_operation to simple_nosetlease() or the equivalent."

The series was applied to the vfs-7.0.leases branch on January 12 by Christian Brauner, following reviews and acknowledgments from Al Viro, Christoph Hellwig, Jan Kara, and numerous filesystem maintainers. On February 17, a patchwork-bot notification confirmed final application to jaegeuk/f2fs.git (dev).

A significant side discussion emerged about whether NFS export itself should become an explicit opt-in feature for filesystems — a topic identified as a potential LSF/MM item but left unresolved. Key participants (Brauner, Layton, Goldstein, Lever) agreed that the current model of equating export_operations with NFS exportability is problematic for filesystems like cgroupfs, pidfs, and nsfs.

This Week: Silence After Landing

The only message this week was from Mike Snitzer on February 25, replying to patch 24/24 ("fs: remove simple_nosetlease()"). The message contained no substantive technical content, suggesting the discussion has effectively concluded following the series' application.

Impact on NFS Client Development

Although no new technical discussion occurred this week, the implications of this change for NFS client development remain significant:

  1. Lease correctness for NFS-exported filesystems: By requiring explicit opt-in, the VFS prevents future regressions where new filesystems inadvertently support leases without proper implementation — a critical concern for NFS delegation correctness and data consistency.

  2. NFS client lease behavior: The NFS client itself already implements custom ->setlease() handlers (via nfs4_setlease()), so this change does not directly affect the NFS client's own lease handling. However, it affects what underlying filesystems the NFS server can safely export.

  3. New filesystem integration: Any new filesystem intended to be NFS-exportable must now explicitly set ->setlease to generic_setlease() (or a custom implementation) to support NFS leases and delegations.

  4. NFS export opt-in discussion: The broader conversation about making NFS export itself an explicit opt-in feature remains open, with consensus that the current implicit model is problematic. Further work on this front was deferred to LSF/MM.

Final Conclusions

The 24-patch lease opt-in series has been fully applied across all relevant trees (vfs-7.0.leases and jaegeuk/f2fs.git (dev)). The immediate goal — making VFS lease support explicit opt-in — is complete. This change will flow through linux-next into the v7.0 merge window, representing a welcome improvement for NFS server correctness and delegation safety.

The thread has entered its quiet post-application phase, with no further technical discussion this week. The broader NFS export control conversation remains unresolved but has established clear consensus that future work is needed on this front.
