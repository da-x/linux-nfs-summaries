kNFSD Signed Filehandles: Hardening Against Guessing Attacks

Summary

kNFSD Signed Filehandles: A New Defense Against Filehandle Guessing

This week, the Linux NFS server (kNFSD) received a significant security enhancement with the application of Benjamin Coddington's patch series "kNFSD Signed Filehandles" (v7). The series addresses a long-standing vulnerability where NFS clients could potentially bypass directory permissions by guessing filehandles.

The Problem: Well-Formed Filehandles Are Easy to Guess

As detailed in the cover letter by Benjamin Coddington, filesystems generate filehandles through encode_fh operations. These handles are often "well-formed," consisting of predictable structures like inode numbers and generation numbers.

"Filehandles are easy to guess because they are well-formed... You can simply insert inode numbers and iterate on the generation number. Eventually you'll be able to access the file using open_by_handle_at(2)."

While local systems protect against this via CAP_DAC_READ_SEARCH for open_by_handle_at(2), the NFS server cannot trust remote callers in the same way. Coddington noted that simple testing confirmed a generation number could be found within ~1200 minutes on a local system, estimating that network delay might only extend this to around 24 hours over genuine NFS calls.

The Solution: Signing Filehandles with SipHash

The proposed solution is to append an 8-byte Message Authentication Code (MAC) to filehandles using SipHash-2-4. This cryptographic signature ensures that a client cannot fabricate a valid filehandle without knowing the server's secret key.

"We propose to sign filehandles by appending an 8-byte MAC which is the siphash of the filehandle from a key set from the nfs-utilities... The NFS server performs optional signing by possessing a key set from userspace and having the 'sign_fh' export option."

Key Technical Components

The three-patch series introduces the following changes:

  1. Key Management: A new netlink interface allows userspace (via nfs-utils) to set a 128-bit secret key for signing filehandles. This key persists across reboots, ensuring filehandles remain valid after server restarts. Patch 1/3 adds the fh_key attribute to the netlink spec and implements the storage in the network namespace.

  2. Export Option: A new sign_fh export option is added in Patch 2/3. When set, the server signals that filehandles for this export should be signed.

  3. Signing and Verification: Patch 3/3 implements the actual signing logic in fs/nfsd/nfsfh.c.

    • Outgoing filehandles are appended with the 8-byte SipHash MAC.
    • Incoming filehandles are verified; if the MAC does not match, or if an unsigned filehandle is presented to a signed export, the server returns NFS_STALE.

Evolution and Refinements

This v7 series represents the culmination of extensive review and refinement over several versions:

  • From Encryption to Signing: Early versions proposed encrypting filehandles, but Eric Biggers suggested signing instead, which is more appropriate for authentication without hiding the filehandle structure.
  • Endianness and Bug Fixes: Multiple rounds of feedback from Chuck Lever and others addressed endianness issues, memcmp usage, and error handling paths.
  • Interface Changes: The method for setting the key evolved from procfs to a netlink attribute, allowing for better integration with rpc.nfsd.

Conclusion

Chuck Lever applied the series to nfsd-testing, marking a successful conclusion to this development cycle.

"Applied to nfsd-testing, thanks!" Chuck Lever

This feature provides a robust, opt-in mechanism for NFS server administrators to harden their exports against filehandle guessing attacks, significantly raising the bar for potential attackers while maintaining compatibility with existing clients (who will receive STALE errors if they attempt to use guessed handles on signed exports).
