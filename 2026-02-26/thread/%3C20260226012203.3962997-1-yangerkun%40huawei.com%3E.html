Summary

RFC: protect NFS file-lock list traversal with nfsi->rwsem

This week at a glance

This week the thread is still in its infancy. Huawei's Yang Erkun opened it on 2026-02-26 with an RFC patch aimed at a long-standing locking bug in the NFS client's file-lock handling, and then came back a few hours later to nudge the list for review. No reviewer has weighed in yet within this window — the substantive back-and-forth (notably with Jeff Layton) only begins later, so the discussion's evolution is still to come.

What kind of change is this?

This is a bug fix on the NFS client side, not a new feature or a protocol change. It targets the locking discipline used while walking the per-inode file-lock list, and it carries a Fixes: tag pointing at an earlier commit:

"Fixes: c69899a17ca4 ("NFSv4: Update of VFS byte range lock must be atomic with the stateid update")"

The core technical argument

The bug, originally reported by Li Lingfeng (Huawei), is a use-after-free (UAF) hazard in file locks. As Erkun frames it, there is a fundamental tension between holding a lock long enough to safely traverse the list and the fact that some traversal paths must call into code that can block for a very long time:

"Generally, we cannot release flc_lock while iterating over the file lock list to avoid use-after-free (UAF) problems with file locks. However, functions like nfs_delegation_claim_locks and nfs4_reclaim_locks cannot adhere to this rule because recover_lock or nfs4_lock_delegation_recall may take a long time."

His proposed remedy is to switch the protection for that traversal from flc_lock to the inode-level read-write semaphore nfsi->rwsem. He notes the reclaim path already does this:

"To resolve this, NFS switches to using nfsi->rwsem for the same protection, and nfs_reclaim_locks follows this approach."

The patch then extends that same discipline to two spots that were out of line:

  1. nfs_delegation_claim_locks. Erkun argues its current guard is insufficient because a single inode can carry more than one state object:

    "Although nfs_delegation_claim_locks uses so_delegreturn_mutex instead, this is inadequate since a single inode can have multiple nfs4_state instances. Therefore, the fix is to also use nfsi->rwsem in this case."

  2. nfs4_locku_done / nfs4_lock_done. These were introduced/affected by commit c69899a17ca4 and call locks_lock_inode_wait without holding nfsi->rwsem, breaking the same rule. Rather than simply grabbing the semaphore (which, he warns, "could cause many deadlocks"), the patch relocates the VFS lock call:

    "the call to locks_lock_inode_wait is moved into _nfs4_proc_setlk."

Why the old bug is considered already handled

A key part of the justification is showing that moving locks_lock_inode_wait does not regress the original problem c69899a17ca4 set out to fix (keeping the VFS byte-range lock update atomic with the stateid update). Erkun argues two later changes closed that window:

"Regarding the bug fixed by commit c69899a17ca4 ... it has been resolved after commit 0460253913e5 ("NFSv4: nfs4_do_open() is incorrectly triggering state recovery") because all slots are drained before calling nfs4_do_reclaim, which prevents concurrent stateid changes along this path."

He adds that the delegation-claim path cannot reintroduce the race either, because when _nfs4_proc_setlk runs with NFS_DELEGATED_STATE no RPC is sent and nfs4_lock_done is never invoked:

"Therefore, nfs4_lock_delegation_recall from nfs_delegation_claim_locks is the first time the stateid is set."

The patch itself

The change is small and surgical, touching three files (19 insertions, 13 deletions): fs/nfs/delegation.c, fs/nfs/nfs4proc.c, and a one-line removal from include/linux/nfs_xdr.h. It closes two earlier report threads from Li Lingfeng (April 2025 and July 2025), underscoring that this is a re-attempt at a problem the list has been aware of for roughly a year.

Where things stand

As of the close of this week, the patch is an unreviewed RFC. Erkun's follow-up makes his eagerness clear:

"This issue has been known for a long time now, and I am really looking forward to some discussion on this problem and the solution I have proposed."

The ball is now in the maintainers' court; given the deadlock-sensitive reasoning around locks_lock_inode_wait and the stateid-atomicity argument, expect the eventual review to focus on whether nfsi->rwsem is a safe substitute for flc_lock across all the reclaim/delegation paths.
