Kernel Panic on Repeated Failed NFSv4 mTLS Mounts

Summary

This week, Debian maintainer Salvatore Bonaccorso forwarded a critical kernel panic report to the linux-nfs mailing list, originating from Debian bug tracker entry #1126957. The issue involves a kernel crash when repeatedly attempting to mount an NFSv4 share using mutual TLS (mTLS) with mismatched certificates.

"Norbert Zentai reported in Debian at https://bugs.debian.org/1126957"

The bug manifests as a NULL pointer dereference within the RCU subsystem, specifically in rcu_do_batch, following repeated failed mount attempts. Bonaccorso provided a detailed reproducing script derived from the ktls-utils package tests. The scenario involves a server configured with a CA-signed certificate and a client presenting a self-signed certificate, causing authentication to fail repeatedly:

"I was able to trigger the kernel panic with a somehow pathological case derived from our test in the ktls-utils package, with client with a valid self-signed certificate"

The reproducer continuously attempts to mount the share using mount -t nfs -o nodev,nosuid,xprtsec=mtls. Before the panic, high CPU usage is observed from udev-worker and systemd-udevd processes. The kernel oops trace indicates a supervisor instruction fetch error at address 0x0:

"BUG: kernel NULL pointer dereference, address: 0000000000000000" "Call Trace: ... rcu_do_batch+0x1bc/0x560 ..."

This report highlights a significant stability issue in the NFS client's handling of mTLS transport security failures, potentially leading to system crashes under pathological conditions. As of this week's activity, the bug has been successfully reproduced and documented, but no patch or resolution has yet been proposed in this thread. Further investigation into the interaction between the NFS client, TLS handshake failures, and RCU cleanup routines is required to address this regression.
