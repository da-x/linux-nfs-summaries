Fixing RISC-V Build Warnings in NFS Client and MACB Driver

Summary

Fixing RISC-V Build Warnings in NFS Client and MACB Driver

This week, Sean Chang submitted a two-patch series aimed at resolving compiler warnings encountered during RISC-V kernel builds. The series was split into subsystem-specific commits: one addressing unused variable warnings in the NFS client code and another fixing a format-truncation warning in the Cadence MACB ethernet driver. While both patches are bug fixes, the discussion surrounding them reveals interesting insights into configuration-dependent code paths and toolchain diagnostics.

NFS Client: Unused Variable Warnings

The first patch, [PATCH v2 1/2] nfs: fix unused variable warnings [id://20260216174950.455244-2-seanwascoding@gmail.com], targets three files within the NFS subsystem:

  • fs/nfs/flexfilelayout/flexfilelayout.c
  • fs/nfs/flexfilelayout/flexfilelayoutdev.c
  • fs/nfs/nfs4proc.c

The fix involves adding the __maybe_unused attribute to variables that are only referenced within debug macros. Andrew Lunn questioned the necessity of this change, noting that there was no explicit #ifdef guarding the code in question:

"There is no #ifdef'ery here. How is ptr not used? Is status always true, so the goto it always taken? But then rpcdata should also be unused?" [id://2e3bf4db-cea6-4f55-a82b-4e99bb3f44fe@lunn.ch]

Sean Chang clarified that the issue arises when CONFIG_SUNRPC_DEBUG is disabled. In this configuration, the dprintk macro expands to a no-op (do {} while (0)), effectively removing all references to variables used exclusively within those debug statements. For instance, in nfs4_proc_create_session, the variable ptr is only read inside a dprintk call:

"If CONFIG_SUNRPC_DEBUG is not enabled, dprintk expands to do {} while (0) during preprocessing. This means unsigned *ptr has no remaining references in the function, as its only 'read' was inside the macro." [id://CAAb=EJVmDS7vKHsw77SARnD9uff-9vBrg97jo3tbYJS-z1KAgw@mail.gmail.com]

Sean also explained why other variables like rpcdata did not trigger similar warnings: the compiler's unused-variable check considers all possible code paths. Since rpcdata is used in a function call that is reachable under normal execution, it does not generate a warning, whereas ptr becomes completely unreferenced when debug output is disabled.

MACB Driver: Format-Truncation Warning

The second patch, [PATCH v2 2/2] net: macb: fix format-truncation warning [id://20260216174950.455244-3-seanwascoding@gmail.com], addresses a warning in the MACB ethernet driver related to string truncation. The original code used snprintf to populate a 32-byte buffer (ETH_GSTRING_LEN) with ethtool statistics strings. Andrew Lunn pointed out that these strings are special: they are fixed-length, not null-terminated, and should ideally be handled using helpers from linux/ethtool.h:

"These strings are special, in that they are fixed length, 32 bytes long, and not \0 terminated. There are some helpers at the end of linux/ethtool.h for dealing with these strings. You might want to use them." [id://f71cdfa7-25f8-487d-b727-39ae962401a4@lunn.ch]

Andrew also raised concerns about the buffer size and questioned why only RISC-V builds were triggering this warning:

"Also, it looks like stat_string might be one byte too short. snprintf() will \0 terminate, so you need it big enough to hold the \0, and then this memcpy() will discard it. I also wonder, why is just one architecture complaining about this?" [id://f71cdfa7-25f8-487d-b727-39ae962401a4@lunn.ch]

Sean Chang responded by switching to ethtool_sprintf(), which properly handles the 32-byte ethtool string boundaries without manual snprintf and memcpy calls. He also investigated the architecture-specific nature of the warning, discovering that it was not unique to RISC-V but rather dependent on kernel configuration:

"I also found that the x86_64 defconfig does not enable CONFIG_MACB because it requires CONFIG_COMMON_CLK (which is also disabled by default on x86), whereas the RISC-V defconfig has both enabled." [id://CAAb=EJXQjraL=VEod0N8Pm5tuQ5UE9UbrdxdZQ+ArKVhDUT83w@mail.gmail.com]

Further testing confirmed that the warning appeared on ARM and ARM64 builds as well when CONFIG_MACB was enabled:

"It proves that even if I switch to a different platform, like arm, arm32, x86_64, riscv64, it still shows the same warning." [id://CAAb=EJUSEwrYrUWGcxwn+kQXAzzFO9_VHaVxAq738PtOYEraYw@mail.gmail.com]

Andrew Lunn agreed that using ethtool_sprintf() was the correct approach but emphasized the importance of documenting the rationale in the commit message:

"I do agree ethtool_sprintf() is better. But we want the commit message to reflect why we are making this change. Is it because ethtool_sprintf() is better, or are we working around toolchain bugs?" [id://00ebdd77-d6ef-48f2-a25d-8d8b3c7dc7a8@lunn.ch]

Sean concluded that the change should be framed as an improvement to prevent data truncation and properly handle ethtool string boundaries, rather than merely a workaround for toolchain-specific warnings.

Conclusion

This thread highlights two distinct types of bug fixes in the Linux kernel:

  1. NFS Client: A configuration-dependent issue where debug macros cause variables to become unused when CONFIG_SUNRPC_DEBUG is disabled. The fix involves adding __maybe_unused attributes to silence compiler warnings.
  2. MACB Driver: A potential data truncation issue in ethtool statistics string handling, resolved by adopting the standardized ethtool_sprintf() helper function.

Both fixes underscore the importance of considering various build configurations and toolchain behaviors when addressing compiler warnings. The discussion also demonstrates the collaborative effort between developers to ensure that patches are not only technically correct but also well-documented and justified.
