Reworking Encryption Type Handling in rpc.gssd to Fix XDR Decoding Failures

Summary

Reworking Encryption Type Handling in rpc.gssd to Fix XDR Decoding Failures

Overview

Scott Mayhew from Red Hat submitted a four-patch RFC series aimed at resolving a critical bug in the NFS client's Kerberos authentication subsystem (rpc.gssd). The issue, tracked as Debian Bug #1120598, manifests as input/output errors (specifically -EIO / -5) during readdir() operations on NFSv4 clients using SHA-2 based encryption types.

This is primarily a bug fix with significant implications for NFS client stability in environments using constrained delegation via gssproxy. The series also includes cleanup of deprecated functionality.

The Core Problem: Enctype Mismatch Between Machine and User Credentials

The root cause lies in how the MIT Kerberos library handles Ticket-Granting Service (TGS) requests when referrals are enabled. As Mayhew explains in the cover letter PATCH RFC 0/4:

"The core issue is that when the krb5 library does a TGS request, it initially does so with referrals enabled, disregarding the enctypes list supplied by the requesting application. It still checks the resulting ticket to ensure that it's using one of the requested enctypes, but it may not [be] the highest priority enctype from our list."

This behavior creates a discrepancy when:

  1. The machine credential is set up (using the krb5 library's default enctype selection during referral processing).
  2. A user credential is subsequently set up via constrained delegation through gssproxy (which may not trigger the same referral logic).

The result is that the machine credential and user credential can end up using different encryption types, leading to XDR decoding failures in the kernel when it attempts to process security contexts with mismatched enctypes.

Patch Breakdown

Patch 1/4: Remove Deprecated limit-to-legacy-enctypes Option

PATCH RFC 1/4 removes support for single-DES encryption types, which were deprecated by RFC 6649 in July 2012. Mayhew notes:

"Support for single-DES encryption types was removed from the MIT KRB5 library in May 2019, and from kernel's RPCSEC_GSS KRB5 mechanism in June 2023."

This cleanup removes dead code and configuration options that no longer serve a functional purpose.

Patch 2/4: Add enctypes_list_to_string() Helper

PATCH RFC 2/4 introduces a utility function to convert encryption type lists into human-readable strings for debugging purposes. This aids in diagnosing enctype-related issues by providing clearer log output.

Patch 3/4: Query krb5 Library for Permitted Enctypes on Startup

PATCH RFC 3/4 adds functionality to retrieve the list of encryption types permitted by the krb5 library at startup. This allows rpc.gssd to cross-reference three sources:

  1. The allowed-enctypes option from nfs.conf.
  2. The enctypes passed in the upcall from the kernel.
  3. The enctypes actually permitted by the krb5 library.

Patch 4/4: Determine Correct Enctype Set for limit_krb5_enctypes()

PATCH RFC 4/4 is the key fix. It introduces a helper function that computes the intersection of the three enctype lists mentioned above, ensuring the final list passed to limit_krb5_enctypes() is ordered according to the krb5 library's preferences. Mayhew explains:

"The best way to combat this [to] configure the krb5 library's permitted_enctypes list to have the same order as the kernel's gss_krb5_prepare_enctype_priority_list (which is set at build time), but not all distros do that. The second best way is to make sure our list is ordered according to the krb5 library's list, which can be accomplished via the helper function added by this patch."

Technical Significance

This series addresses a subtle but critical race condition in enctype selection that affects NFS clients using Kerberos with constrained delegation. By ensuring that the encryption type ordering in rpc.gssd aligns with the krb5 library's internal preferences, the patches prevent the mismatch between machine and user credentials that leads to XDR decoding failures.

The fix is particularly important for distributions like Debian, where this bug has been reported as causing filesystem access failures. The series also modernizes the codebase by removing support for cryptographically weak single-DES encryption types.

Status

As an RFC (Request for Comments) submission, this series is seeking feedback from the NFS community before formal acceptance. No replies were recorded within the current week's window, suggesting the discussion may continue in subsequent weeks or that the patches are awaiting review.
