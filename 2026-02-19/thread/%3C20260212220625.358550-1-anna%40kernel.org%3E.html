NFS 7.0 Pull Merged; KConfig Regression Fix for NFS v4.0 Default

Summary

NFS Client Linux 7.0 Pull: Merge Confirmation and KConfig Regression Fix

Overview

Discussion type: Bug fix (regression in KConfig defaults following a merge).

This week's activity on the NFS client pull request thread focused on two events: confirmation that Anna Schumaker's **[GIT PULL] Please Pull NFS Client Updates for Linux 7.0](https://lore.kernel.org/linux-nfs/20260212220625.358550-1-anna@kernel.org/) had been successfully merged into Linus Torvalds' tree, and the discovery of a regression in the new CONFIG_NFS_V4_0 KConfig option that broke NFS root filesystem mounts for some users.

Merge Confirmation

On February 13, the PR tracker bot confirmed that the pull request had been accepted:

"The pull request you sent on Thu, 12 Feb 2026 17:06:25 -0500: git://git.linux-nfs.org/projects/anna/linux-nfs.git tags/nfs-for-7.0-1 has been merged into torvalds/linux.git"

The merge was confirmed by the bot, closing the formal pull request cycle for this update batch.

Regression Report: NFS Root Mount Failure

On February 16, Niklas Cassel reported a critical boot failure caused by one of the commits in the merged pull request. His system failed to mount its root filesystem via NFS, resulting in a kernel panic:

"VFS: Unable to mount root fs via NFS." "Kernel panic - not syncing: No working init found."

Niklas performed a git bisect and identified the culprit commit:

"commit 4e0269352534715915aae3fb84dd4d3bb3ff3738 Author: Anna Schumaker anna.schumaker@oracle.com NFS: Add a way to disable NFS v4.0 via KConfig"

The issue stemmed from how make olddefconfig handled the new CONFIG_NFS_V4_0 option. Niklas explained:

"Before commit above my config has: CONFIG_NFS_V4=y, CONFIG_NFS_V4_1=y, CONFIG_NFS_V4_2=y after commit above (with make olddefconfig), my config has: CONFIG_NFS_FS=y, CONFIG_NFS_V4=y, # CONFIG_NFS_V4_0 is not set, CONFIG_NFS_V4_1=y, CONFIG_NFS_V4_2=y"

His kernel command line used nfsvers=4, which he had assumed would select the best available NFS v4.x version. However, as Niklas noted:

"So AFAICT, it seems that nfsvers=4 actually means nfsvers=4.0 I am probably not the only person to who has 'nfsvers=4' on the kernel command line."

When he explicitly specified nfsvers=4.2, the mount succeeded with the same configuration where NFS v4.0 was disabled.

Proposed Solutions and Resolution

Niklas proposed two possible fixes:

  1. Change CONFIG_NFS_V4_0 to have default y so it remains enabled by default for existing configurations.
  2. Modify the behavior of nfsvers=4 to mean "use whatever highest NFS 4.x version supported by the kernel" rather than strictly v4.0.

Anna Schumaker responded on February 18, confirming that the first option was indeed her original intent:

"This is what I intended, actually. I don't know how the missing 'default y' slipped through the cracks for this long. Thanks for pointing it out, I'll get this fixed up!"

Anna acknowledged the oversight and committed to issuing a fix.

Significance for NFS Client Development

This incident highlights an important lesson in kernel configuration management: when introducing new KConfig symbols that split existing functionality, ensuring sensible defaults is critical to avoid breaking existing user configurations — particularly for boot-critical paths like NFS root mounts.

The regression affected users who relied on the shorthand nfsvers=4 on their kernel command line, a common practice for systems expecting automatic version negotiation within the v4 family. While Anna's restructuring of NFS v4.0 into a separately configurable component was architecturally sound (allowing administrators to disable legacy v4.0 support entirely), the missing default y caused make olddefconfig to silently disable v4.0 for existing configurations, breaking systems that depended on it.

The fix — adding default y to CONFIG_NFS_V4_0 — will restore backward compatibility while preserving the new capability to explicitly disable NFS v4.0 for users who want a leaner kernel configuration focused on v4.1 and later.

Conclusion

This week's thread concluded with a straightforward resolution: Anna Schumaker acknowledged the missing default in the CONFIG_NFS_V4_0 KConfig option and pledged to issue a corrective patch. The incident underscores the importance of careful default handling when refactoring kernel configuration options, especially those affecting boot-critical subsystems like NFS root filesystem support.
