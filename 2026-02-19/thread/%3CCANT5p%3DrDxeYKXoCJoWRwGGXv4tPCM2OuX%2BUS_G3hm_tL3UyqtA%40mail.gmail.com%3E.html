NFS Community Consensus: Migrating from usermodehelper to Namespace-Aware Netlink Upcalls

Summary

Namespace-Aware Upcalls for Kernel Filesystems: Moving Away from usermodehelper

Classification: Architectural Discussion / Protocol Evolution (NFS Client & Server Infrastructure)

Overview

This week, the Linux NFS and filesystem community engaged in a significant architectural discussion regarding how kernel filesystems perform upcalls to userspace. Initiated by Shyam Prasad N, the thread addresses a critical limitation of the current usermodehelper-based keyring upcall mechanism: its lack of namespace awareness. This deficiency poses challenges for containerized environments, where host-namespace binaries are undesirable or prohibited.

The consensus emerging from the discussion is a strong preference for migrating towards netlink-based control interfaces, which are inherently namespace-aware, and potentially deprecating the older usermodehelper approach for new features.

Key Technical Arguments

The Problem: Host-Namespace Lock-in

Shyam Prasad N opened the thread by highlighting that filesystems like NFS and SMB rely on the kernel keys subsystem for tasks such as DNS resolution, authentication, and ID mapping.

"Filesystems like SMB and NFS clients use the kernel keys subsystem for some of these... However, this upcall mechanism is not namespace aware and upcalls to the host namespaces (namespaces of the init process)." Shyam Prasad N

This forces container services to host upcall handlers in the host namespace, creating security and operational friction. Shyam noted his previous unsuccessful attempt to prototype a namespace-aware keyring upcall and sought alternative approaches, including using device files or file descriptors registered from within containers.

The Proposed Solution: Netlink Control Interfaces

Chuck Lever responded by pointing to an existing, more modern pattern already adopted by parts of the NFS stack: netlink.

"Hello Shyam, we've been introducing netlink control interfaces, which are namespace-aware. The kernel TLS handshake mechanism now uses this approach, as does the new NFSD netlink protocol." Chuck Lever

Chuck clarified that net/handshake/netlink.c demonstrates using netlink for kernel-initiated TLS handshakes, a mechanism already adopted by:

  • NFSD (via the new nfsdctl tool in nfs-utils)
  • The NFS client
  • NVMe over TCP drivers
  • Planned in-kernel QUIC implementations

Security Concerns with Namespace Switching

David Leadbeater raised important security considerations regarding simply switching namespaces for upcalls. He argued that entering the correct namespace is insufficient for safe execution within a container context.

"Entering the right namespaces isn't enough to safely run code within a container. The container runtime may have set up seccomp or other limits which this upcall won't respect." David Leadbeater

He advocated for a registration-based approach that preserves backward compatibility, noting that MergerFS (his project) currently uses custom callback code to manage these complexities.

Consensus: Deprecating usermodehelper

Jeff Layton synthesized the discussion, identifying the core architectural issue: the Linux kernel lacks a "container object" that associates namespaces with one another in a way that usermodehelper can exploit safely.

"I think the consensus at this point is to move away from usermodehelper as an upcall mechanism. The Linux kernel lacks a container object that allows you to associate namespaces with one another, so you need an already-running userspace process to do that association in userland." Jeff Layton

He explained that netlink upcalls are bound to a network namespace, and the presence of a running daemon in that namespace naturally ties it to other namespaces (like mount or PID namespaces). This led to a concluding question about the future of the old mechanism:

"So, a related discussion we should have is whether and how we should deprecate the old usermodehelper upcalls, given that they are problematic in this way." Jeff Layton

Evolution and Conclusions

The discussion evolved from a specific problem statement (namespace-aware keyring upcalls for NFS/SMB) to a broader architectural review of userspace interaction patterns in the kernel.

  1. Initial Proposal: Shyam sought reviews on namespace-aware keyring upcalls or FD-based alternatives.
  2. Alternative Identification: Chuck Lever identified netlink as the modern, namespace-aware standard already in use for NFSD and NFS client TLS.
  3. Security Refinement: David Leadbeater highlighted that simple namespace switching is insecure due to seccomp profiles, favoring registration models.
  4. Architectural Consensus: Jeff Layton confirmed that the community is moving away from usermodehelper for new upcall needs, citing the lack of kernel-side container association logic.

Final Conclusion: The NFS client and server communities are aligning on netlink-based upcalls as the preferred mechanism for namespace-aware userspace interactions. This approach leverages existing infrastructure (like ktls-utils and nfsdctl) and avoids the security pitfalls of host-namespace usermodehelper calls. Future work may involve formally deprecating usermodehelper for new filesystem upcall features in favor of netlink or similar daemon-bound interfaces.
