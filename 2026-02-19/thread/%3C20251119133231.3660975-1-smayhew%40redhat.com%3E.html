SUNRPC GSS Slack Fix Shifted to rpc.gssd Encryption Type Rework

Summary

SUNRPC GSS Slack Estimate Issue — Shift to rpc.gssd Fix

Classification: Bug fix (GSS/Kerberos authentication, NFS client-side)

This thread tracks the ongoing resolution of Debian bug #1120598 ("NFS: readdir(/) returns -5"), which manifests as XDR decoding failures when a Kerberos-protected NFSv4 client uses SHA2-based encryption types. The root cause involves mismatched encryption types (enctypes) between machine credentials and user credentials, leading to incorrect slack estimates in the SUNRPC layer.

Background (Prior Weeks)

The thread originated with Scott Mayhew's November 2025 kernel patch titled "SUNRPC: Check if we need to recalculate slack estimates," which attempted to address the issue within the kernel by adding logic to recalculate slack variables when the incoming GSS verifier exceeded previously recorded sizes. As noted in the January 2026 summary, Chuck Lever reviewed the patch but concluded:

"After further consideration, we concluded the above change is not an adequate repair for this issue."

The kernel-side approach was deemed insufficient, prompting a search for a more fundamental solution.

This Week's Activity (February 13–14, 2026)

Strategic Pivot to rpc.gssd

On February 13, Scott Mayhew responded to Debian maintainer Salvatore Bonaccorso's earlier inquiry, explaining the new direction after deeper investigation:

"I think it would be better to try to address this from the rpc.gssd side instead of trying to make the kernel cope with having to bounce around between different encryption types."

Mayhew then pointed to a new RFC patch series for nfs-utils titled "[nfs-utils PATCH RFC 0/4] Rework the handling of encryption types in rpc.gssd."

The New Approach: Fixing Encryption Type Handling in rpc.gssd

The four-patch series addresses the core issue at its source — within rpc.gssd, the userspace daemon responsible for Kerberos credential management. The problem, as described by Mayhew, is that when the krb5 library performs a TGS (Ticket Granting Service) request, it initially does so with referrals enabled, disregarding the enctypes list supplied by the application:

"The core issue is that when the krb5 library does a TGS request, it initially does so with referrals enabled, disregarding the enctypes list supplied by the requesting application. It still checks the resulting ticket to ensure that it's using one of the requested enctypes, but it may not the highest priority enctype from our list."

This discrepancy can cause the machine credential and user credentials (particularly in constrained-delegation scenarios via gssproxy) to use different encryption types, leading to XDR decoding failures. The patches aim to ensure that the enctype list passed to limit_krb5_enctypes() matches the ordering of the default list in the krb5 library.

The series includes:

  1. gssd: remove the limit-to-legacy-enctypes option — Cleans up deprecated single-DES encryption type support (deprecated by RFC 6649 in 2012).
  2. gssd: add enctypes_list_to_string() — Adds a helper for human-readable enctype listing.
  3. gssd: get the permitted enctypes from the krb5 library on startup — Retrieves the library's permitted enctypes at initialization.
  4. gssd: add a helper to determine the set of encryption types to pass to limit_krb5_enctypes() — Implements logic to properly order and filter enctypes across three sources: allowed-enctypes from nfs.conf, kernel upcall enctypes, and library-permitted enctypes.

Community Response

Salvatore Bonaccorso acknowledged the update on February 14:

"Thank you for the notice, I will watch the thread there with the new patches."

Significance for NFS Client Development

This represents a notable architectural decision: rather than patching the kernel's SUNRPC layer to handle edge cases in verifier sizing, the fix is being pursued at the userspace rpc.gssd level. This approach addresses the root cause — inconsistent encryption type selection between machine and user credentials — rather than treating symptoms in the kernel. For NFS client deployments using Kerberos security (sec=krb5/krb5i/krb5p), particularly with constrained delegation via gssproxy, this fix is critical to resolving I/O errors caused by XDR decoding failures.

Status

In progress. The kernel patch remains unmerged and has been superseded by the nfs-utils RFC series. The community awaits review and feedback on the new approach. Debian users tracking bug #1120598 should monitor the nfs-utils thread for further developments.
