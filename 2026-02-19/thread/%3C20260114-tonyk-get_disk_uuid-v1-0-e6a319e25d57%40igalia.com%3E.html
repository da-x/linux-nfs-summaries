overlayfs: uuid=off Patch Confirmed Useful; Pull Request Sent

Summary

This week concluded a six-week discussion on extending overlayfs's uuid=off mount option to support cross-filesystem setups — specifically targeting SteamOS A/B partitioning with btrfs cloned images. After André Almeida confirmed the patch worked for his workload, Amir Goldstein submitted the pull request to the overlayfs maintainer.

Background (Brief)

This thread originated from Almeida's rejected 3-patch series proposing to repurpose export_operations::get_uuid() for overlayfs origin file handles. Christoph Hellwig opposed that approach, arguing it served pNFS block layout exclusively. The discussion pivoted to extending overlayfs's existing uuid=off mount option — originally created for Virtuozzo container disk copying. Over five prior weeks, Goldstein developed a patch lifting uuid=off's same-filesystem restriction, clarified its semantics, and tested it internally. Last week, Goldstein explained the fundamental limitation that uuid=off cannot solve btrfs clone file handle instability (different root_objectid values across clones), ruling out any "fileid=off" option.

Key Technical Arguments This Week

André Almeida: Workload Validation Confirmed

Responding to Goldstein's earlier request for confirmation that the patch serves a real workload, Almeida provided his definitive assessment [id://8bec19de-6e6e-418a-a256-5918bd835d98@igalia.com]:

"I can confirm that this is useful for my workload. After correctly setting this flag for every mount, everything is working good and we can bypass the random UUID issues. Thank you for your help!"

This message represents a significant milestone: after weeks of debugging, clarification about consistent uuid=off usage across all mounts (not just the first), and understanding the btrfs clone limitations, Almeida confirmed that the patch successfully resolves the SteamOS use case — at least for the UUID instability component. The phrase "after correctly setting this flag for every mount" acknowledges Goldstein's earlier insistence that uuid=off must be applied consistently on all mounts, not just the initial one.

Amir Goldstein: Pull Request Submitted

With Almeida's confirmation in hand, Goldstein fulfilled his conditional promise to submit the patch [id://CAOQ4uxhpB-D+DaCVZ6-uZGM8WnsZ9Bkxdd4+f_EkvYnQ8xpvqQ@mail.gmail.com]:

"OK, PR sent."

This brief but decisive message marks the culmination of the thread. Goldstein had previously stated he would not submit the patch "without knowing that someone finds this useful for their workload" [id://CAOQ4uxgzK7qYDFWYT62jH_zq8JkLGussD5ro4cKDqSNQqBiVUA@mail.gmail.com]. Almeida's confirmation satisfied that condition, and the pull request was dispatched.

Evolution of the Discussion

The thread's trajectory over its full six-week lifespan:

  • Weeks 1–2 (Jan 14–22): Almeida's original approach rejected; discussion pivoted to uuid=off as an existing mechanism.
  • Week 3 (Jan 23–29): Almeida misused uuid=off; Goldstein clarified it must be enabled from the first mount and provided documentation improvements.
  • Week 4 (Feb 5): Almeida reported initial success but a remaining reboot issue; recommended deferral to 7.1.
  • Week 5 (Feb 6–12): Goldstein clarified that uuid=off cannot solve the btrfs clone file handle problem, ruled out any "fileid=off" option, and confirmed the patch was queued for potential 7.0 submission pending workload confirmation.
  • Week 6 (Feb 13–19, this week): Almeida confirmed the patch works for his workload; Goldstein submitted the pull request.

Final Conclusions

  1. The patch is accepted and submitted. With Almeida's workload validation, Goldstein sent the pull request to the overlayfs maintainer tree [id://CAOQ4uxhpB-D+DaCVZ6-uZGM8WnsZ9Bkxdd4+f_EkvYnQ8xpvqQ@mail.gmail.com]. The change lifts uuid=off's same-filesystem restriction, allowing cross-filesystem overlayfs setups where UUID verification would otherwise fail.

  2. The SteamOS use case is resolved — partially. Almeida confirmed that "everything is working good and we can bypass the random UUID issues" [id://8bec19de-6e6e-418a-a256-5918bd835d98@igalia.com]. However, this only addresses UUID instability. As Goldstein clarified last week, file handle instability from btrfs clones (different root_objectid values) remains unsolved by uuid=off, and no "fileid=off" option will be added.

  3. Operational requirement: consistent uuid=off usage. The patch requires that uuid=off be specified on every mount of the overlayfs, not just the first one. Failure to do so results in mount denial by overlayfs.

  4. Alternative for full btrfs clone support: index=off. For users who need to mount an overlayfs created in one btrfs clone from another (where both UUID and file handle change), the only option is to disable the overlayfs index entirely with index=off — sacrificing performance and correctness guarantees for flexibility.

Classification

Type: Feature extension (overlayfs uuid=off support for cross-filesystem setups)

NFS Client Relevance: Indirect. This is fundamentally an overlayfs discussion, though it touches on file handle encoding semantics that are foundational to NFS exports and the exportfs subsystem. The original get_uuid() infrastructure served pNFS block layout, and Hellwig previously noted that "encoding the uuid into the file handle in the kernel is the right thing for NFS as well."
