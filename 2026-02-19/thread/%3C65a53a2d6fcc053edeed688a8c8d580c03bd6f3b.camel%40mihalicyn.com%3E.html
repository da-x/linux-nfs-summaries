VFS ID-Mappings Support in NFS: Use Cases and Implementation Strategies

Summary

VFS ID-Mappings Support in NFS: Use Cases and Implementation Strategies

This week, the Linux NFS mailing list saw a significant discussion regarding the integration of VFS (Virtual File System) id-mappings with the NFS client. The thread, initiated as an LSF/MM/BPF topic, explores how NFS can support user namespace remapping, a feature critical for modern containerized environments like LXC/Incus and Kubernetes.

Discussion Overview

The conversation began with Alexander Mikhalitsyn proposing VFS id-mapping support for NFS 1. Jeff Layton and Trond Myklebust, key NFS maintainers, sought to clarify the specific use cases and technical challenges involved. The discussion evolved from understanding basic AUTH_SYS scenarios to addressing the complexities of AUTH_GSS and NFSv4 idmapping.

Key Technical Arguments

Use Case Clarification

Jeff Layton requested a concrete example to understand the problem better:

"Could you lay out an example of how you would use them with NFS in a real environment so I understand the problem better? I'd start by assuming a simple setup with AUTH_SYS and no NFSv4 idmapping involved, since that case should be fairly straightforward." 2

Alexander Mikhalitsyn explained the LXC/Incus use case, where idmapped mounts allow delegating filesystems to containers without remapping between container user namespaces and the superblock's user namespace:

"At the same time host's system administrator wants to avoid remapping between container's user ns and sb->s_user_ns (which is init_user_ns for those filesystems). [motivation here is that in many cases you may want to have the same subtree to be shared with other containers and even host users too and you want UIDs to be "compatible", i.e UID 1000 in one container and UID 1000 in another container should land as UID 1000 on the filesystem's inode]" 3

Kohei Sugihara from Preferred Networks later added the Kubernetes use case, highlighting the need for ReadWriteMany (RWX) access mode with consistent UID/GID views across multiple pods:

"Our goal is here: 1: Mount the same NFS export as a persistent volume from multiple Kubernetes Pods running on different compute nodes... 3: We can access the export from the container as 1000:1000. At minimum, ownership should be consistent from the container view" 10

Technical Challenges with Authentication

Trond Myklebust raised concerns about strong authentication methods:

"As the NFS and RPC protocols stand today, strong authentication will defeat any client side idmapping scheme, because the server can't know what uids or gids the client is using on its end; it just knows about the account that was used to authenticate." 4

He suggested that a generic implementation would require protocol extensions:

"I think if you do want to implement something generic, you're going to have to consider how the client and server can exchange (and store) the information needed to allow the client to perform the mapping of file owners/group owners on its end... It would be a very different security model than the one used by NFS today, and almost certainly require protocol extensions." 4

Proposed Implementation Approaches

Jeff Layton suggested that for simple AUTH_SYS cases, the conversion could happen at the RPC client layer without protocol extensions:

"So in this case, it sounds like you would need just do that conversion (maybe at the RPC client layer?) when issuing an RPC. You don't really need a protocol extension for that case." 7

NeilBrown provided additional insights on handling different authentication and NFS versions:

"If you use krb5 and NFSv3 then you really want the mapping between krb5 identity and uid to be the same on client and server, so then when an application creates a file and the stats it, it sees that it owns it." 9

For NFSv4 with idmapper, he suggested:

"With NFSv4 and the idmapper you wouldn't need (or want) the kernel idmapping to be used at all. You would want the idmapper deamon to run in the user-namespace and map from on-the-wire names to the appropriate app-level uids." 9

Evolution of the Discussion

The thread progressed from initial proposal to detailed use case explanations, then to technical feasibility analysis. Key milestones included:

  1. Initial Proposal: Alexander Mikhalitsyn introduced the topic 1
  2. Use Case Clarification: Jeff Layton requested concrete examples, leading to explanations from both LXC/Incus and Kubernetes perspectives 2, 3, 10
  3. Technical Challenges: Trond Myklebust highlighted authentication-related complexities 4
  4. Implementation Strategies: The group discussed potential approaches, with consensus forming around starting with simple AUTH_SYS cases 7, 8

Final Conclusions

The discussion concluded with agreement on a phased approach:

  1. Start Simple: Focus initially on AUTH_SYS without NFSv4 idmapping, as suggested by Jeff Layton 2
  2. Client-Side Implementation: For simple cases, UID conversion can happen at the RPC client layer without protocol extensions 7
  3. Iterative Development: Alexander Mikhalitsyn offered to prepare RFC patches for the simple case before LSF/MM/BPF 8
  4. Future Complexity: AUTH_GSS and NFSv4 idmapping will require more sophisticated solutions, potentially involving protocol extensions or changes to how the idmapper daemon operates 4, 9

Kohei Sugihara emphasized the importance of this work for container security:

"Kubernetes and the container community actively work on host isolation using the Linux user namespace feature. Recently they experienced RCE vulnerabilities on container runtime but it could be mitigated by host isolation using the user namespace isolation" 10

This thread represents an important step toward improving NFS compatibility with modern containerized environments, balancing security requirements with operational simplicity.
