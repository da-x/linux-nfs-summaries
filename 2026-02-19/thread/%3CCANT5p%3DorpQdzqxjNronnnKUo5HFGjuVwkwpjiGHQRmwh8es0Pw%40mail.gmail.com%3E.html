Proposal to Split Superblocks During Remount

Summary

Support to Split Superblocks During Remount

Overview

This LSF/MM/BPF topic proposes a VFS-level feature to allow filesystems to split superblocks during remount operations. The discussion is about a new VFS feature/protocol change rather than a bug fix, though it addresses a practical problem affecting NFS and other network filesystems.

Key Technical Arguments

The Problem Statement

Shyam Prasad N opened the thread by describing how filesystems currently use sget/sget_fc at mount time to share superblocks when possible, with sharing decisions often based on mount options:

"Filesystems today use sget/sget_fc at the time of mount to share superblocks when possible to reuse resources. Often the reuse of superblocks is a function of the mount options supplied." Shyam Prasad N

The core issue is that remount operations are associated with a mount point, not the superblock itself. When mount options change during a remount, those changes can inadvertently affect all mounts sharing the same superblock — even if the user only intended to modify one mount point.

Shyam proposed that the VFS mount API should provide filesystems an option to call sget to obtain a new superblock (which could also be shared) and perform a put_super on the old superblock during remount:

"Ideally, during remount, the mount API needs to provide the filesystem an option to call sget to get a new superblock (that can also be shared) and do a put_super on the old superblock." Shyam Prasad N

He acknowledged the complexity involved:

"I do realize that there are challenges here about how to transparently failover resources (files, inodes, dentries etc) to the new superblock. I would still like to understand if this is an idea worth pursuing?" Shyam Prasad N

Response from Aleksa Sarai

Aleksa Sarai responded within the week, sharing a link to an external resource (https://www.cyphar.com/) for further context. Shyam acknowledged this in a follow-up message outside the weekly window:

"Thanks for sharing this. Will go over the details shared to understand more about what you said." Shyam Prasad N

Evolution of the Discussion (Beyond This Week)

Although the substantive replies from VFS core maintainers fell outside this week's window, they are critical to understanding the trajectory of this proposal:

  • Al Viro expressed strong skepticism, noting that a fundamental assumption throughout the kernel is that struct inode, struct dentry, and struct mount instances belong to the same superblock for their entire lifetime. He warned that relaxing this invariant would be extremely costly:

"That's putting it way too mildly. A lot of places rely upon the following: any struct inode instance belongs to the same superblock through the entire lifetime." Al Viro

"Exclusion that would required to cope with the possibility of the above being violated would cost far too much, and that's without going into the amount of analysis needed to make sure that things wouldn't break." Al Viro

  • Christian Brauner echoed this concern:

"I'm very very skeptical about all of this and would really do everything we can do avoid this..." Christian Brauner

  • Shyam Prasad N clarified that the affected filesystems include AFS, Btrfs, Ceph, FUSE, GFS2, NFS, UBIFS, and SMB/client — all of which use sget* with test functions and can share superblocks. He emphasized that NFS and SMB clients in particular use mount options to decide whether to share a superblock, and these options can change during remount:

"Side effect of such remounts is that changes to mount options will apply to all mounts that share the superblock, whether the user intended to do that or not." Shyam Prasad N

Significance for NFS Client Development

This topic is directly relevant to NFS client development because:

  1. The NFS client uses sget_fc with test functions that consider mount options when deciding whether to share superblocks.
  2. When remount options change, those changes currently propagate to all mounts sharing the same superblock — an unintended side effect.
  3. Filesystems lack visibility into other mounts sharing a superblock, making it impossible to safely reject problematic remounts.

Final Conclusions (as of this week)

Within this week's window, no definitive conclusion was reached. The proposal was introduced and received initial engagement. However, the subsequent responses from VFS core maintainers (outside this week) indicate significant resistance to the approach due to the fundamental kernel assumptions about superblock lifetime invariants. The discussion remains open but faces substantial technical hurdles.
