NFSD: Layout Recall Timeout and Lease Manager Fencing Integration Applied

Summary

NFSD: Layout Recall Timeout and Lease Manager Fencing Integration Applied

This week, the long-standing effort to harden NFSv4.1/pNFS block layout recall handling reached a milestone with the application of patch v12 by Chuck Lever. The patch addresses a critical scalability and correctness issue in the NFS server (nfsd) where excessive threads could be blocked during layout recalls, potentially starving the server of resources.

Background and Problem Statement

As outlined by Dai Ngo in the initial submission PATCH v12 1/1, the core issue was that when a layout conflict triggered a recall, there was no enforced timeout. This could lead to "excessive nfsd threads from being blocked in __break_lease ensuring the server continues servicing incoming requests efficiently."

The patch introduces a new callback, lm_breaker_timedout, within the lease_manager_operations structure. This allows the lease manager (specifically the NFSD implementation) to handle timeouts gracefully, including triggering fencing operations for clients that fail to return their layouts in time.

Key Technical Arguments and Evolution

The patch has evolved through 12 versions, reflecting significant refinement in how fencing is handled asynchronously and how lease state is managed during these operations.

Asynchronous Fencing and Lease State Management

A central design decision highlighted by Dai Ngo was the separation of concerns between the fence worker and the core lease code:

"I experimented with having the fence worker handle lease disposal after fencing the client. However, this requires the lease code to export the lease_dispose_list function, and for the fence worker to acquire the flc_lock in order to perform the disposal. This approach adds unnecessary complexity and reduces code clarity... Instead, the lm_breaker_timedout operation should simply notify the lease code about how to handle a lease that times out during a lease break, rather than directly manipulating the lease list."

To ensure data integrity during this asynchronous process:

  1. Reference Counting: The patch uses refcount_inc_not_zero on the layout stateid before starting the fence worker to ensure the state remains valid.
  2. Lease Retention: "While the fencing operation is in progress, the conflicting file_lease remains on the flc_list until fencing is complete. This guarantees that no other clients can access the file, and the client with exclusive access is properly blocked before disposal."

Retry Logic and Back-off

The fencing mechanism includes robust retry logic:

  • Exponential Back-off: The fence worker uses exponential back-off when retrying operations.
  • Delay Limits: The maximum delay was capped at 3 minutes to prevent indefinite stalling.
  • Logging: Unique client identifiers are included in fence log messages, with logging limited to once per failure to avoid spamming logs.

Documentation Updates

The patch also updated administrative documentation (pnfs-block-server.rst and pnfs-scsi-server.rst) to include recovery procedures for administrators dealing with fenced clients.

Conclusion and Application

Chuck Lever reviewed the patch and applied it to the nfsd-testing tree with minor adjustments:

"Applied to nfsd-testing, thanks! I made a couple of small adjustments, please review the result." [id://177109154296.57968.985044750836996107.b4-ty@oracle.com]

Dai Ngo confirmed the changes were acceptable, noting a technical detail regarding the use of delayed_work_pending() instead of a custom flag:

"The adjustments look fine to me. Just a note that the reason we need the call to mod_delayed_work() and cancel_delayed_work() in nfsd4_layout_fence_worker() is because we use delayed_work_pending() in nfsd4_layout_lm_breaker_timedout(), instead of the ls_fence_in_progress flag." [id://561ad2b4-6612-455f-8b47-c8bdc1fc6e04@oracle.com]

Significance for NFS Client Development

While this patch is server-side (nfsd), it has profound implications for NFS clients, particularly those using pNFS block layouts:

  1. Predictable Behavior: Clients can expect that if they fail to respond to a layout recall within the timeout period, they will be fenced from the underlying storage device. This prevents data corruption scenarios where multiple clients might access the same block device concurrently.
  2. Server Stability: By preventing thread starvation on the server during recalls, overall latency and reliability for all clients improve, especially under heavy load or when dealing with unresponsive clients.
  3. Recovery Procedures: The updated documentation provides clear guidance for administrators on how to recover fenced clients, aiding in operational stability.

This patch represents a significant step forward in the robustness of pNFS block layout implementations in the Linux kernel, ensuring that server resources are protected and client behavior is strictly enforced during conflict resolution.
