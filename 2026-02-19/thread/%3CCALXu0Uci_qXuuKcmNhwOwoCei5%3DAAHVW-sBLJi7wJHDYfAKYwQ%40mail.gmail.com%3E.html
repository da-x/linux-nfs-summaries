Case-Sensitivity Mount Option: Referral Complications Raised

Summary

Mount Option to Enforce Case-Sensitivity Expectations: Referral Complications Raised

Overview

This thread, originally opened by Cedric Blancher on January 14, proposes a new feature for the Linux NFS client: a mount option that would cause mount.nfs(8) to reject a mount if the server's reported case-sensitivity behavior does not match the administrator's expectation. The goal is to prevent silent misconfiguration where software requiring a specific case-sensitivity model (e.g., case-insensitive) operates on a mismatched filesystem.

Prior Context

In the January 15 summary, Blancher's initial proposal was recorded with no responses from maintainers. The idea was to add a validation step at mount time — for example, a require_case_insensitive option that would fail the mount if the NFSv4 server's FSINFO response indicated the export was case-sensitive.

Activity This Week

After a month of silence, two messages arrived in this reporting window.

Follow-Up Nudge

On February 18, Cedric Blancher posted a brief follow-up to his original message:

"Anyone?"

Cedric's nudge was essentially a ping to see if the proposal had garnered any attention from NFS client developers.

Dan Shelton Raises Referral Concerns

The substantive technical response came the next day from Dan Shelton, who engaged with the proposal by highlighting a significant complication: NFSv4 referrals.

Shelton questioned whether enforcing case-sensitivity at mount time is sufficient when the mounted filesystem may contain referrals to other filesystems that do not share the same properties:

"So /sbin/mount should fail if the spec (e.g. filesystem must be case insensitive) is not met? What about if it matches, /sbin/mount succeeds, but a NFSv4 referral refers to a filesystem which does not match that spec?"

Dan Shelton's concerns cut to the heart of a practical implementation challenge. If a mount is validated at the root export but later traverses into a referred filesystem with different case-sensitivity behavior, the client would need to handle that mismatch at runtime — potentially returning an error during operations like cd or open() that cross the referral boundary.

Shelton further pressed on the semantics of such failures:

"Which ERRNO should be returned if you do a cd new-referred-fs123, or a open() which crosses the referal?"

This question underscores that a mount-time check alone may not provide the safety net Blancher envisions. The enforcement would need to extend into path traversal logic, raising questions about error semantics and user-space application compatibility.

Status and Conclusions

The discussion remains open with no resolution. No NFS client maintainers (such as Chuck Lever or Trond Myklebust) have weighed in during this window. The key takeaway is that while the proposal addresses a legitimate operational concern — preventing silent case-sensitivity mismatches — Dan Shelton's referral scenario exposes a non-trivial design challenge:

  • A mount-time check alone is insufficient if referrals can lead to mismatched filesystems.
  • Extending enforcement to runtime traversal introduces complexity around error reporting and application compatibility.

Future discussion would likely need to address whether the feature should be limited to non-referral mounts, how to handle referral crossings gracefully, and what semantics applications should expect when encountering case-sensitivity mismatches mid-traversal.
