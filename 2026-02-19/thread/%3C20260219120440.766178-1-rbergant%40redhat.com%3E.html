NFS: Fix EISDIR return on directory alias in nfs3_proc_create

Summary

NFS Client Fix: Prevent Oops on Directory Collision During nfs3_proc_create

Overview

This week, Roberto Bergantinos Corpas submitted a targeted bug fix for the NFSv3 client addressing a kernel oops that occurs when directory and file creation race conditions result in a negative dentry being passed to do_dentry_open. The patch, titled "[PATCH] nfs: return EISDIR on nfs3_proc_create if d_alias is a dir," was submitted with reviews from Olga Kornievskaia and Scott Mayhew.

Technical Context and Problem Description

The issue arises in the NFSv3 atomic open path (nfs_atomic_open_v23 / finish_open). As described by Roberto Bergantinos Corpas:

"If we found an alias through nfs3_do_create/nfs_add_or_obtain/d_splice_alias which happens to be a dir dentry, we don't return any error, and simply forget about this alias, but the original dentry we were adding and passed as parameter remains negative."

This scenario was observed in high-concurrency environments:

"This has been observed running lustre-racer, where dirs and files are created/removed concurrently with the same name and O_EXCL is not used to open files (frequent file redirection)."

The root cause is that d_splice_alias may return a directory alias, but the original code did not explicitly check whether the resulting dentry represented a directory. Consequently, a negative dentry was supplied to do_dentry_open, triggering a kernel oops because file operations were attempted on what should have been recognized as a directory inode.

The Fix

The patch introduces an explicit d_is_dir() check in fs/nfs/nfs3proc.c within the nfs3_proc_create function. When a directory alias is detected, the code now returns -EISDIR instead of silently discarding the alias and proceeding with a negative dentry.

As Roberto notes:

"While d_splice_alias typically returns a directory alias or NULL, we explicitly check d_is_dir() to ensure that we don't attempt to perform file operations (like finish_open) on a directory inode, which triggers the observed oops."

The fix traces back to commit 7c6c5249f061, which introduced atomic open support for NFSv3 to handle O_TRUNC correctly. This earlier change inadvertently left a gap in error handling for the directory collision case.

Conclusion

This is a bug fix addressing a stability issue in the NFS client. The patch:

  • Prevents kernel oopses during concurrent create/remove operations with naming collisions.
  • Properly returns EISDIR when a directory alias is encountered during file creation.
  • Has received positive reviews from key NFS maintainers (Olga Kornievskaia and Scott Mayhew).

The fix is minimal (6 insertions, 1 deletion in fs/nfs/nfs3proc.c) and targets a specific race condition observed under heavy concurrent I/O workloads such as those generated by lustre-racer. This underscores the importance of robust dentry state validation in the NFS client's atomic open path, particularly for NFSv3 where such edge cases can lead to kernel panics rather than graceful error returns.
