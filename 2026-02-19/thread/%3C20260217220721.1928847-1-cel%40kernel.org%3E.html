NLMv4 XDR Modernization: 29-Patch xdrgen Conversion Series (v3)

Summary

NLMv4 XDR Modernization: 29-Patch xdrgen Conversion Series (v3)

Classification: Infrastructure Refactoring / Protocol Implementation Improvement

Overview

Chuck Lever submitted version 3 of a 29-patch series titled [PATCH v3 00/29] Convert lockd to use xdrgen for NLMv4 20260217220721.1928847-1-cel@kernel.org, aimed at modernizing the NFS Lock Manager (NLM) version 4 XDR layer in the Linux kernel's lockd subsystem.

This is a refactoring effort, not a bug fix or new feature. The series replaces hand-written XDR encoding and decoding functions with code generated by the xdrgen tool, improving memory safety, type correctness, and maintainability of the NLMv4 server-side implementation.

Evolution from v2 to v3

The previous version (v2, submitted January 2026) was a larger 42-patch series titled "Clarify module API boundaries" that combined two distinct goals:

  1. API boundary cleanup (patches 01–13): Separating lockd's public API from internal implementation details.
  2. NLMv4 xdrgen conversion (patches 14–42): Converting NLMv4 XDR handling to use generated code.

In v3, Chuck Lever decoupled these concerns. As he notes in the cover letter:

"Changes since v2: Pre-requisite changes have been applied to nfsd-testing"

This means the API boundary patches (previously 01–13) were merged separately into the nfsd-testing branch, allowing this v3 series to focus exclusively on the NLMv4 xdrgen conversion. The series shrank from 29 xdrgen-related patches in v2 (out of 42 total) to a standalone 29-patch series.

Jeff Layton had reviewed the v2 series positively, stating:

"I went through the series and it looks good overall. I definitely like moving away from hand-rolled XDR handling."

He also cautioned:

"It's a big change so it'd be good to have a nice long test cycle with it."

Technical Details

Goals of xdrgen Migration

As Chuck Lever explains in patch 01/29:

"The goals of replacing hand-written XDR functions with ones that are tool-generated are to improve memory safety and make XDR encoding and decoding less brittle to maintain."

He further emphasizes the correctness guarantee:

"Unlike hand-written code that can inadvertently diverge from the specification, xdrgen guarantees that the generated code matches the specification exactly."

The series also looks toward future Rust integration:

"We would eventually like xdrgen to generate Rust code as well, making the conversion of the kernel's NFS stacks to use Rust just a little easier for us."

Patch Breakdown

The 29 patches systematically convert all NLMv4 server-side procedures from hand-rolled XDR to xdrgen-generated functions:

Foundation (Patches 01–02):

  • Patch 01/29: Adds the RPC language description of NLM version 4 (Documentation/sunrpc/xdr/nlm4.x), an amalgam of RFC 1813 and the Open Group's XNFS specification. This file is processed by xdrgen to produce type definitions and encode/decode functions.
  • Patch 02/29: Converts the NLMv4 NULL procedure as a straightforward starting point (no arguments or results).

Core Lock Operations (Patches 03–07):

  • Patch 03/29: TEST procedure — introduces reusable helper functions nlm4svc_lookup_host() and nlm4svc_lookup_file() for host and file lookups, establishing patterns for subsequent conversions.
  • Patch 04/29: LOCK procedure — the primary lock acquisition operation.
  • Patch 05/29: CANCEL procedure — allows clients to cancel outstanding blocked lock requests.
  • Patch 06/29: UNLOCK procedure — releases locks acquired via LOCK.
  • Patch 07/29: GRANTED procedure — server-to-client notification when a previously blocked lock request has been granted, completing the asynchronous lock request flow.

Callback Refactoring (Patch 08):

  • Patch 08/29: Refactors nlm4svc_callback() to move host lookup logic into each of the five MSG procedure handlers, enabling xdrgen's distinct argument structures per procedure.

Asynchronous MSG Procedures (Patches 09–13):

  • Patch 09/29: TEST_MSG — non-blocking lock availability check.
  • Patch 10/29: LOCK_MSG — asynchronous lock request that may block.
  • Patch 11/29: CANCEL_MSG — cancel pending lock requests asynchronously.
  • Patch 12/29: UNLOCK_MSG — asynchronous unlock notification.
  • Patch 13/29: GRANTED_MSG — asynchronous grant notification.

Callback RES Procedures (Patches 14–18):

  • Patch 14/29: TEST_RES — client sends test lock results back to server.
  • Patch 15/29: LOCK_RES — client sends lock results back to server.
  • Patch 16/29: CANCEL_RES — client sends cancel results back to server.
  • Patch 17/29: UNLOCK_RES — client sends unlock results back to server.
  • Patch 18/29: GRANTED_RES — client sends grant results back to server.

Additional Procedures (Patches 19–26):

  • Patch 19/29: SM_NOTIFY — state manager notification procedure.
  • Patch 20/29: Converts server-side undefined procedures to xdrgen.
  • Patch 21/29: Hoists file_lock init out of nlm4svc_decode_shareargs().
  • Patch 22/29: Prepares share helpers for xdrgen conversion.
  • Patch 23/29: SHARE procedure — file sharing operations.
  • Patch 24/29: UNSHARE procedure — release file shares.
  • Patch 25/29: NM_LOCK procedure — network manager lock operations.
  • Patch 26/29: FREE_ALL procedure — release all locks for a host.

Cleanup (Patches 27–29):

  • Patch 27/29: Adds LOCKD_SHARE_SVID constant for DOS sharing mode.
  • Patch 28/29: Removes C macros no longer used after xdrgen conversion.
  • Patch 29/29: Removes dead code from fs/lockd/xdr4.c.

Key Architectural Patterns

Wrapper Structures: The series introduces wrapper structures (e.g., nlm4_testargs_wrapper, nlm4_lockargs_wrapper) that bridge between xdrgen-generated types and the legacy nlm_lock representation still used by core lockd logic. This maintains compatibility while incrementally modernizing the XDR layer.

Elimination of Defensive Initialization: A recurring theme across patches is the removal of early memset operations:

"The pc_argzero field is set to zero because xdrgen decoders reliably initialize all arguments in the argp->xdrgen field, making the early defensive memset unnecessary."

This reflects a key benefit of xdrgen: guaranteed initialization eliminates entire classes of potential uninitialized memory bugs.

Bug Fixes Embedded: Patches 14 and 15 also correct placeholder values in pc_xdrressize fields that previously contained incorrect values for TEST_RES and LOCK_RES procedures.

File Impact

The series touches 14 files with a net change of +2,474 insertions and -964 deletions:

  • New files: Documentation/sunrpc/xdr/nlm4.x, fs/lockd/nlm4xdr_gen.c, fs/lockd/nlm4xdr_gen.h, include/linux/sunrpc/xdrgen/nlm4.h
  • Deleted files: fs/lockd/xdr4.c, fs/lockd/xdr4.h (hand-written XDR code removed)
  • Major modifications: fs/lockd/svc4proc.c (+1,773 lines), reflecting the bulk of procedure handler conversions

Jeff Layton provided a Reviewed-by tag for all patches in the v2 series, and Chuck Lever indicated his intention to merge the prerequisite API boundary patches into nfsd-testing before this xdrgen conversion series.

Significance for NFS Client Development

While this series primarily targets the NFS server-side lockd implementation, it has implications for NFS client developers:

  1. Protocol Correctness: By guaranteeing that generated XDR code matches the NLMv4 specification exactly, the series reduces the risk of subtle wire-format bugs that could affect interoperability between Linux NFS clients and servers.

  2. Memory Safety Improvements: The elimination of hand-written XDR decoders removes potential sources of buffer overflows, uninitialized memory reads, and other memory safety issues in the lockd subsystem.

  3. Future Rust Integration: Chuck Lever's stated goal of eventually generating Rust code from xdrgen suggests a long-term path toward rewriting parts of the NFS stack in Rust, which would benefit both client and server implementations.

  4. No Client-Side Changes: This series does not modify any NFS client code directly; all changes are confined to the server-side lockd subsystem (fs/lockd/).

Conclusions

This 29-patch v3 series represents a significant infrastructure modernization of the NLMv4 XDR layer in the Linux kernel's lockd subsystem. Key takeaways:

  1. Decoupled from API cleanup: Unlike v2, which combined API boundary refactoring with xdrgen conversion, v3 focuses exclusively on XDR modernization after prerequisite changes were merged separately.

  2. Comprehensive coverage: All NLMv4 server-side procedures (NULL, TEST, LOCK, CANCEL, UNLOCK, GRANTED, their MSG and RES variants, SM_NOTIFY, SHARE, UNSHARE, NM_LOCK, FREE_ALL) are converted to xdrgen-generated code.

  3. Correctness by construction: The generated code is guaranteed to match the protocol specification, eliminating divergence risks inherent in hand-written XDR implementations.

  4. Awaiting review: As of this week's cutoff, no feedback has been received on v3. Given Jeff Layton's positive review of v2 and his recommendation for extended testing, the series is expected to undergo a thorough test cycle before integration.

  5. Foundation for future work: This conversion paves the way for eventual Rust code generation from xdrgen, supporting the broader goal of modernizing the kernel's NFS stacks.
