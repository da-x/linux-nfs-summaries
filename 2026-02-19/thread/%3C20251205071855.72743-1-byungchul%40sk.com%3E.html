DEPT Module Support: Type Safety Review and Rust Helper Convention

Summary

DEPT Module Support: Continued Review of Event Site Integration

Overview

This thread is part of Byungchul Park's 42-patch v18 series introducing DEPT (DEPendency Tracker), a new kernel subsystem designed to detect deadlock possibilities by tracking wait/event dependencies rather than lock acquisition order — complementing the existing Lockdep infrastructure. The series was originally posted on December 5, 2025 (cover letter).

This week's activity focuses on two patches within the series: patch 34/42 (module support for struct dept_event_site and dept_event_site_dep) and patch 31/42 (assigning unique dept_key to each distinct wait_for_completion() caller). This is classified as a new feature (kernel infrastructure), not an NFS-specific change or bug fix. The DEPT subsystem has broad kernel-wide applicability, including potential future use in NFS client/server deadlock detection, but this particular discussion deals with core module loading mechanics and Rust helper integration.

Prior Context

In the January 8 summary window, Petr Pavlu (SUSE) posted detailed review comments on patch 34/42 from the module loader perspective, addressing coding style (extern usage), type safety concerns around .dept.event_sites section declarations, section lifetime optimization (.init prefixing), an indirection design question, and whether "used" checks could be performed at build time rather than runtime.

This Week's Activity

Byungchul Park Responds to Petr Pavlu's Review (Feb 13)

After a six-week gap — which Byungchul attributed to personal matters (As mentioned):

"Sorry about the late reply. I've been going through some major life changes lately. :("

Byungchul responded point-by-point to Petr's January review:

1. extern Keyword Removal: Byungchul agreed to remove extern from function declarations per kernel coding style guidelines.

"I will remove 'extern's. Thanks." Byungchul Park

2. Type Safety and Pointer Counting: Petr had suggested that dept_mark_event_site_used() take pointers to dept_event_site_init rather than generic void*. Byungchul defended his current approach, comparing it to the initcalls mechanism:

"IMO, this is the easiest way to get all the pointers from start to the end, or I can't get the number of the pointers. It's similar to the initcalls section for device drivers." Byungchul Park

However, he remained open to Petr's suggestion and asked how pointer counting would work with typed declarations:

"How can I get the number of the pointers?" Byungchul Park

3. Section Lifetime and Indirection: Byungchul agreed to explore Petr's suggestions regarding .init prefixing for the section and storing dept_event_site_init directly in the .dept.event_sites section:

"Maybe yes. I will try." Byungchul Park "Maybe yes. I will try to store dept_event_site_init in the .dept.event_sites section directly." Byungchul Park

4. Build-Time vs Runtime Checking: On Petr's question about whether objtool/modpost could handle the "used" check at build time, Byungchul acknowledged his choice was driven by familiarity but expressed openness to better alternatives:

"You are right. I picked what I'm used to the most, among all the candidate methods. However, I will try to use a better way if you suggest what you think it should be." Byungchul Park

Petr Pavlu Clarifies Type-Safety Suggestion (Feb 18)

Petr followed up with a concrete proposal to resolve the type-safety debate. He clarified that his suggestion was not about changing the overall architecture but about proper typing:

"This was a minor suggestion.. The idea is to simply change the function signature to:" Petr Pavlu

void dept_mark_event_site_used(struct dept_event_site_init **start,
			       struct dept_event_site_init **end)

"This way, the compiler can provide proper type checking to ensure that correct pointers are passed to dept_mark_event_site_used(). It would catch the type mismatch with module::dept_event_sites." Petr Pavlu

For the pointer counting question, Petr pointed out that initcalls already use properly typed array declarations:

"Similarly here, changing the code to:" Petr Pavlu

extern struct dept_event_site_init *__dept_event_sites_start[], *__dept_event_sites_end[];

"It is the same for the initcalls you mentioned. The declarations of their start/end symbols are also already properly typed as initcall_entry_t[] in include/linux/init.h." Petr Pavlu

Dirk Behme's Rust Helper Suggestion (Feb 15)

Dirk Behme reviewed patch 31/42, which assigns unique dept_key values to each distinct wait_for_completion() caller. He noted that the patch adds a new Rust helper function rust_helper_wait_for_completion() and suggested adding the __rust_helper attribute:

"Please add __rust_helper:" Dirk Behme

He referenced a recent commit in linux-next that established this convention for Rust helper functions.

Significance for NFS Development

While this thread is not directly about NFS, the DEPT subsystem has implications for NFS client and server development:

  1. Deadlock detection: NFS operations involve complex wait/event patterns (e.g., RPC call completions, page lock waits, delegation recall handling) that are difficult to track with Lockdep alone. DEPT could help uncover latent deadlock conditions in NFS code paths.

  2. Module support: The reviewed patch ensures DEPT works correctly with loadable kernel modules — critical since many filesystems and network stacks are modularized.

  3. Rust integration: Patch 31/42's interaction with Rust helpers is notable as the Linux kernel continues to expand its Rust support, which may eventually be leveraged by NFS subsystems.

Conclusion

This week saw productive back-and-forth between Byungchul Park and Petr Pavlu on refining patch 34/42's module integration design. Byungchul agreed to most of Petr's suggestions (removing extern, exploring direct storage in .dept.event_sites, considering .init prefixing) and remained open to build-time checking alternatives. Petr provided concrete code examples for proper type-safe declarations, drawing parallels to the initcalls mechanism. Dirk Behme contributed a minor but important suggestion regarding Rust helper conventions. The discussion reflects the careful iterative refinement typical of major kernel infrastructure introductions. No final conclusions were reached this week; Byungchul is expected to incorporate feedback in a future patch revision.
