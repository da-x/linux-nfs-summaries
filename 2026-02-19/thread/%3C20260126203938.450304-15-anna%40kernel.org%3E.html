Post-Merge Review: NFS CONFIG_NFS_V4_1 Merge and Kconfig Defaults

Summary

NFS: Post-Merge Review of CONFIG_NFS_V4_1 Merge Patch

Summary

This thread captures a post-merge review comment on Anna Schumaker's patch series to make NFS v4.0 KConfig-urable, specifically focusing on the final patch ([PATCH v2 14/14] NFS: Merge CONFIG_NFS_V4_1 with CONFIG_NFS_V4). The patch was already merged upstream as commit 7537db24806fdc3d when Geert Uytterhoeven raised concerns about Kconfig default values and defconfig updates.

Classification

This discussion concerns a code refactoring / configuration change in the NFS client, not a bug fix or protocol modification. The original series restructured the NFS client to allow compile-time exclusion of NFS v4.0 support while promoting NFS v4.1 as the default baseline.

Background (Prior Weeks)

As summarized in last month's coverage, Anna Schumaker submitted a 14-patch v2 series to:

  • Extract NFS v4.0-specific code into dedicated nfs40* files
  • Introduce KConfig gating for v4.0 support
  • Merge CONFIG_NFS_V4_1 into CONFIG_NFS_V4, making v4.1 the always-enabled default

The series was motivated by a desire to eventually deprecate NFS v4.0, a topic raised at the October Bake-a-thon. Anna wrote:

"Compiling the NFSv4 module without any minorversion support doesn't make much sense, so this patch sets NFS v4.1 as the default, always enabled NFS version allowing us to replace all the CONFIG_NFS_V4_1s scattered throughout the code with CONFIG_NFS_V4."

This Week's Activity

On February 13, Geert Uytterhoeven posted a review of the now-merged patch here, raising two specific concerns about the Kconfig changes:

1. Default Value for "If unsure"

Geert questioned whether the default recommendation should have been updated:

"And out of context:

If unsure, say Y.

Shouldn't that become "N", cfr. the old NFS_V4_1 below?"

His point is that if v4.1 is now always enabled with CONFIG_NFS_V4, and v4.0 can be optionally disabled, then users who are unsure might prefer to disable the legacy v4.0 support entirely rather than keeping it enabled by default.

2. Defconfig Updates

Geert also flagged a potential maintenance issue:

"And shouldn't all configs currently enabling CONFIG_NFS_V4, but not CONFIG_NFS_V4_1, be updated to disable CONFIG_NFS_V4?"

This raises the question of whether existing architecture-specific defconfigs that previously enabled CONFIG_NFS_V4 without CONFIG_NFS_V4_1 (a now-obsolete combination) need to be audited and updated. Since CONFIG_NFS_V4_1 no longer exists as a separate option, any defconfig that referenced it would need adjustment.

Evolution of the Discussion

This thread represents a late-stage review comment on an already-merged patch. The original series was submitted in January (v2 on January 26) and had been merged by early February. Geert's feedback comes after the fact, suggesting either:

  1. He discovered the merge while reviewing unrelated changes, or
  2. His review arrived after the merge window closed

The discussion is limited to this single message from Geert, with no replies from Anna Schumaker or other NFS developers within this week's window.

Key Technical Arguments

Geert's concerns focus on two aspects of Kconfig hygiene:

  1. User guidance: The "If unsure" default should reflect the recommended stance for typical users. If the goal is to encourage migration away from v4.0, the default might favor disabling it.

  2. Defconfig consistency: Architecture-specific defconfigs may need updates to account for the removal of CONFIG_NFS_V4_1 as a distinct option. This is a maintenance burden that could affect embedded and specialized systems.

Conclusion

This thread highlights an important post-merge review concern about Kconfig defaults and defconfig maintenance following a significant NFS client refactoring. While the patch has already been merged, Geert's questions about default values and defconfig updates remain open issues that may require follow-up patches. The discussion underscores the importance of considering configuration implications when restructuring kernel subsystems, particularly for embedded systems where every kilobyte of code matters.

No resolution was reached within this week's window; further action would depend on whether Anna Schumaker or other NFS maintainers address Geert's concerns in a subsequent patch.
