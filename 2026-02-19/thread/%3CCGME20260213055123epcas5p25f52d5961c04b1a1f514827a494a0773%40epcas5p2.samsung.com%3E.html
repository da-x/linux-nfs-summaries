NFS Client Cleanup: Removing Direct Writeback Internal References

Summary

Avoiding Filesystem References to Writeback Internals: NFS Client Cleanup

Classification: Code Refactoring / API Cleanup (NFS Client)

This thread covers a four-patch series from Kundan Kumar (Samsung) that introduces new writeback helper APIs and converts several filesystems — including NFS, f2fs, and gfs2 — to stop accessing kernel writeback internals directly. For the NFS client, this represents a targeted cleanup rather than a functional change or bug fix.

The Patch Series

On 2026-02-13, Kundan Kumar submitted [PATCH v2 0/4] Avoid filesystem references to writeback internals 20260213054634.79785-1-kundan.kumar@samsung.com, describing the motivation:

"The series introduces writeback helper APIs and converts f2fs, gfs2 and nfs to stop accessing writeback internals directly."

Kundan noted that this work follows earlier guidance from Christoph Hellwig:

"As suggested by Christoph [1], filesystem code that directly accesses writeback internals is split out"

He emphasized that the changes are purely structural:

"No functional changes intended."

NFS-Specific Changes

The fourth patch in the series — nfs: stop using writeback internals for WB_WRITEBACK accounting — modifies two files within the NFS client:

  • fs/nfs/internal.h (2 lines changed)
  • fs/nfs/write.c (3 lines changed, net -1 line)

The goal is to have the NFS client use the new helper APIs for writeback accounting instead of reaching into internal writeback structures. This aligns with a broader kernel-wide effort to encapsulate writeback internals and prepare for upcoming parallel writeback patches.

Changes Since v1

Kundan documented two key revisions from v1, both driven by Christoph Hellwig's feedback:

  1. Cgroup writeback disclaimer: A comment was added clarifying that the new helper functions should not be used by filesystems supporting cgroup writeback.
  2. Inode-based accounting: The patch now passes an inode instead of a backing device info (bdi) pointer when modifying writeback accounting stats. Kundan explained this design choice:

"Pass inode instead of bdi for modifying writeback accounting stats, will make it easier to select proper wb context for the upcoming parallel writeback patches."

Review and Conclusion

Christoph Hellwig reviewed the series promptly, responding less than an hour later:

"Looks good:" 20260213062435.GA27228@lst.de

He provided a Reviewed-by tag, signaling approval for the series.

Significance for NFS Client Development

While this thread does not address a bug or introduce new NFS functionality, it is part of an important kernel-wide architectural cleanup with implications for NFS client maintainability:

  1. Encapsulation: By removing direct references to writeback internals from filesystem code, the kernel reduces coupling between the VFS/writeback layer and individual filesystem implementations.
  2. Future-proofing: The inode-based API design explicitly prepares for upcoming parallel writeback patches, ensuring the NFS client will be compatible with those changes without further refactoring.
  3. Consistency: Aligning NFS with f2fs and gfs2 on this pattern establishes a uniform approach across multiple filesystems.

The series touches six files total (19 insertions, 7 deletions), with the NFS-specific changes being minimal but meaningful in terms of long-term code health.
