LSF/MM Proposal: Distributed File Locking API Improvements

Summary

[LSF/MM ATTEND] distributed file locking

Overview

This thread consists of a single proposal posted by Alexander Aring (Red Hat) to the LSF/MM ATTEND conference, cross-posted to linux-nfs. The discussion is about a new feature/API design rather than a bug fix or protocol change. It addresses long-standing limitations in the Linux kernel's file locking API when used in distributed filesystem contexts.

Key Technical Arguments

Alexander Aring opened the proposal by highlighting a fundamental design limitation:

"Initially the file locking API, used from the user space via flock() or fcntl(), was not designed for distributed locking. There are known issues e.g. specifying a process id but missing additional information about the distributed entity where the process is running."

The core problem identified is that the existing file_operations locking API lacks the ability to convey distributed context — such as which node or distributed lock manager backend a lock request originates from. This affects multiple distributed filesystems, including NFS, CIFS, and DLM (Distributed Lock Manager).

Aring proposed two complementary approaches:

  1. Opt-in extensions: Allow users to opt into additional distributed locking extensions that provide specific distributed locking information via the existing API.
  2. New virtual filesystem approach: A recent proposal referenced in the message suggested offering the file locking API through a virtual filesystem, using DLM as the initial backend. This would serve as an experimental sandbox:

"The filesystem's concept can be extended to offer other backends and allow experiments with new 'distributed' file locking API extensions until the community agrees on and proposes a stable API."

NFS Client Relevance

While this proposal is not NFS-specific, it directly impacts NFS client development. NFS relies on distributed lock management (NLM for NFSv3, stateful locking for NFSv4), and the current kernel locking API's inability to express distributed context creates friction in implementing robust locking semantics. Any improvements to the VFS-layer distributed locking infrastructure would benefit the NFS client stack.

Evolution and Conclusions

There was no further discussion within this week's window. The thread contains only the initial proposal from Alexander Aring posted on 2026-02-13. No replies, reviews, or counter-proposals were recorded.

Aring acknowledged the scope and difficulty of the problem:

"This proposal discusses an exotic and very specific topic: distributed file locking, which tries to map to the existing file locking API. Users working on distributed file systems are aware of the challenges involved. Solving those long-standing challenges will be a lengthy process. It might be time to start improving this situation."

Summary

This is an early-stage LSF/MM proposal seeking community awareness and input on redesigning or extending the kernel's file locking API for distributed filesystems. No concrete patches, bug fixes, or protocol changes were presented. The NFS client community may wish to monitor this discussion as it could eventually affect how NFS implements lock management in the kernel.
