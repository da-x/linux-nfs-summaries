VFS Lease Opt-In Series Applied to f2fs Tree

Summary

VFS Lease Opt-In Series: Final Landing Notification

Overview

This week saw only one message in this thread: a patchwork-bot notification confirming that Jeff Layton's 24-patch series to require filesystems to explicitly opt-in to lease support was applied to jaegeuk/f2fs.git (dev) by Christian Brauner. This serves as the final landing notice for a VFS architectural change that has been under review since January 8.

Classification

This thread concerns a VFS protocol/architectural change — not a bug fix or new feature per se, but a structural improvement to prevent future regressions in lease and delegation handling. The change has significant implications for NFS client and server development, as NFS and SMB are the primary consumers of kernel file leases and delegations.

Prior Week Bridge (January 8–15)

The full 24-patch series was posted on January 8 by Jeff Layton, who explained the motivation:

"For historical reasons, when ->setlease() file_operation is set to NULL, the default is to use the kernel-internal lease implementation. This means that if you want to disable them, you need to explicitly set the ->setlease() file_operation to simple_nosetlease() or the equivalent."

The series was applied to the vfs-7.0.leases branch on January 12 by Christian Brauner, following reviews and acknowledgments from Al Viro, Christoph Hellwig, Jan Kara, and numerous filesystem maintainers. A significant side discussion emerged about whether NFS export itself should become an explicit opt-in feature for filesystems — a topic identified as a potential LSF/MM item but left unresolved at the time.

This Week: Final Application Confirmation

On February 17, the patchwork bot notified that the series was applied to jaegeuk/f2fs.git (dev):

"This series was applied to jaegeuk/f2fs.git (dev) by Christian Brauner"

The notification listed all 24 patches with their commit hashes in the f2fs tree, covering:

  • Patches 01–22: Adding generic_setlease() to 22+ local filesystems (affs, btrfs, erofs, ext2, ext4, exfat, f2fs, fat, gfs2, jffs2, jfs, nilfs2, ntfs3, ocfs2, orangefs, overlayfs, squashfs, tmpfs, udf, ufs, xfs, and read-only filesystems)
  • Patch 23: Changing kernel_setlease() to return -EINVAL when ->setlease is NULL — the core behavioral change making lease support opt-in
  • Patch 24: Removing simple_nosetlease() as no longer needed

Impact on NFS Client Development

Although no new technical discussion occurred this week, the implications of this change for NFS client development remain significant:

  1. Lease correctness for NFS-exported filesystems: By requiring explicit opt-in, the VFS prevents future regressions where new filesystems inadvertently support leases without proper implementation — a critical concern for NFS delegation correctness and data consistency.

  2. NFS client lease behavior: The NFS client itself already implements custom ->setlease() handlers (via nfs4_setlease()), so this change does not directly affect the NFS client's own lease handling. However, it affects what underlying filesystems the NFS server can safely export.

  3. New filesystem integration: Any new filesystem intended to be NFS-exportable must now explicitly set ->setlease to generic_setlease() (or a custom implementation) to support NFS leases and delegations.

  4. NFS export opt-in discussion: The broader conversation about making NFS export itself an explicit opt-in feature remains open, with participants agreeing that the current model of equating export_operations with NFS exportability is problematic for filesystems like cgroupfs, pidfs, and nsfs that use file handles for open_by_handle_at() but should not be NFS-exportable.

Final Conclusions

The 24-patch lease opt-in series has been fully applied across the relevant trees (vfs-7.0.leases and jaegeuk/f2fs.git (dev)). The immediate goal — making VFS lease support explicit opt-in — is complete. This change will flow through linux-next into the v7.0 merge window, representing a welcome improvement for NFS server correctness and delegation safety.

The broader discussion about NFS export controls remains unresolved but has established clear consensus that the current implicit model is problematic. Further work on this front was deferred to LSF/MM.
