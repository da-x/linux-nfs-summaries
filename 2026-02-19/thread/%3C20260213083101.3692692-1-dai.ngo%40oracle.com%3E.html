NFSD: Layout Recall Timeout and Lease Manager Fencing Integration (v11)

Summary

NFSD: Layout Recall Timeout and Lease Manager Fencing Integration (v11)

This week, Dai Ngo submitted version 11 of a patch series titled "[PATCH v11 1/1] NFSD: Enforce timeout on layout recall and integrate lease manager fencing" Dai Ngo. The patch addresses a critical reliability issue in the NFS server (NFSD) regarding Parallel NFS (pNFS) layout recalls, specifically for block and SCSI layouts.

Technical Context and Problem Statement

The primary goal of this patch is to prevent excessive nfsd threads from being blocked indefinitely during layout recall conflicts. As Dai Ngo explained:

"When a layout conflict triggers a recall, enforcing a timeout is necessary to prevent excessive nfsd threads from being blocked in __break_lease ensuring the server continues servicing incoming requests efficiently."

The patch introduces a new callback, lm_breaker_timedout, within the lease_manager_operations structure. This allows the lease manager to handle timeouts by initiating a fencing operation if the client has not already been fenced, thereby preventing unauthorized access to block devices while ensuring the conflicting lease is properly disposed of.

Key Technical Arguments and Review Feedback

Chuck Lever provided significant review feedback on the same day, identifying two critical bugs in the implementation:

1. Jiffies Calculation Error

Chuck Lever pointed out a subtle but severe bug in fs/locks.c regarding how break_time is calculated:

"break_time is set to an absolute jiffies value... Now, further down in __break_lease(), break_time is passed to wait_event_interruptible_timeout(), whose third argument expects a relative timeout in jiffies. Passing an absolute value produces a wait on the order of billions of jiffies rather than lease_break_time seconds."

This error would have caused the server to hang for an extremely long period (effectively forever) when waiting for a lease break, defeating the entire purpose of the timeout mechanism.

2. Reference Counting Race Condition

Chuck Lever also identified a potential use-after-free vulnerability in fs/nfsd/nfs4layouts.c:

"Wondering if ^^^^ should be refcount_inc_not_zero()? refcount_inc() on a zero refcount triggers a WARN and still increments, then mod_delayed_work() re-queues the fence worker. Once the destructor completes and frees the layout stateid via kmem_cache_free(), the re-queued fence worker operates on freed memory."

He suggested using refcount_inc_not_zero() to safely handle the race condition where the layout stateid might be destroyed while the fence worker is being scheduled.

3. Unused Variable

Additionally, Chuck Lever noted a minor nit:

"Nit: 'dispose' is unused."

Evolution of the Discussion and Resolution

Dai Ngo acknowledged all three issues raised by Chuck Lever and confirmed they would be addressed in version 12 of the patch:

"This should be: break_time = lease_break_time * HZ; Fix in v12."

"Ah, I missed this. Fix in v12."

"I think the ls_layouts list can not be not empty and the layout stateid is 0 at the same time. But I will make this change anyway just to be on the safe side."

Conclusion

This discussion highlights a significant bug fix effort in NFSD development, focusing on improving server stability during pNFS layout conflicts. The integration of lease manager fencing with timeout enforcement is crucial for preventing server-side resource exhaustion and ensuring data integrity in distributed storage environments. The rapid identification and acknowledgment of the jiffies calculation error and reference counting race condition demonstrate the rigorous review process within the Linux NFS community. The patch is expected to be updated as v12 with these fixes incorporated.
