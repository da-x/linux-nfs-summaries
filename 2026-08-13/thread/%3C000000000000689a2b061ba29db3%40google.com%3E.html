syzbot finds reproducer for nfsd_nl_threads_get_doit hung task

Summary

Summary

This week’s only traffic on a two-year-old syzbot report is a new C reproducer for a hung-task stall in the NFS server Generic Netlink control path. There is still no human reply, no patch, and no #syz fix / #syz dup acknowledgement. The report is a bug, not a protocol change or a client feature: several tasks block uninterruptibly in nfsd_nl_threads_get_doit() on nfsd_mutex while a sibling netlink doit already holds that mutex in nfsd_nl_listener_set_doit().

Prior history (brief)

syzbot opened the bug on 24 June 2024 against upstream cea2a26553ac (6.10-rc3-era), with no reproducer:

"Unfortunately, I don't have any reproducer for this issue yet."

The original hung-task watchdog fired after more than 143 seconds:

"INFO: task syz-executor.2:20070 blocked for more than 143 seconds."

The 2024 stack already pointed at nfsd_nl_threads_get_doit waiting on nfsd_mutex (fs/nfsd/nfsctl.c:1757), while syz-executor.0 held the same mutex in nfsd_nl_listener_set_doit (fs/nfsd/nfsctl.c:1966). Both also held Generic Netlink cb_lock. The bot tagged the report [nfs?] and asked maintainers to add Reported-by: syzbot+c0831b61d6ade1e2d098@syzkaller.appspotmail.com on any fix. That thread then went silent until this week.

This week: a C reproducer on current upstream

On 7 August 2026, syzbot reported that it now has a reproducer on current upstream (364465ab19de, merge of v7.2-rc6-smb3-server-fixes). Assets include a C reproducer, console log, kernel config, and the dashboard entry. The bot restated the usual fix tag:

"IMPORTANT: if you fix the issue, please add the following tag to the commit: Reported-by: syzbot+c0831b61d6ade1e2d098@syzkaller.appspotmail.com"

The new hung-task dump is shorter (15–17 seconds rather than 143) but otherwise the same shape, and it is noisier: five executor threads hang together rather than one. The first dump is typical:

"INFO: task syz-executor549:5964 blocked for more than 15 seconds."

Tasks 5964–5968 are all in D state in __mutex_lock from nfsd_nl_threads_get_doit+0x1c0/0x790 at fs/nfsd/nfsctl.c:1754, reached via Generic Netlink (genl_family_rcv_msg_doit → netlink_sendmsg → sendto). That is the nfsd control-plane NFSD_CMD_THREADS_GET handler, not an NFS client RPC path. A sixth task, pid 6028, is blocked in the same mutex from nfsd_nl_listener_set_doit+0x135/0x1750 at fs/nfsd/nfsctl.c:1964.

Lock dump: nfsd_mutex vs. listener set

The smoking gun is the system-wide lock list, not any single hung stack. Every blocked executor thread holds Generic Netlink cb_lock and then serializes on the process-wide nfsd_mutex:

  • syz-executor549 pids 5964–5968 hold / wait on nfsd_mutex in nfsd_nl_threads_get_doit (fs/nfsd/nfsctl.c:1754).
  • pids 5969 and 6028 hold nfsd_mutex in nfsd_nl_listener_set_doit (fs/nfsd/nfsctl.c:1964).

In other words, a netlink set of NFS server listeners is sitting on the global nfsd mutex long enough that concurrent gets of the nfsd thread count trip the hung-task watchdog. Both operations also take cb_lock in genl_rcv(), so the stall is a control-plane serialization problem: genetlink plus the process-wide nfsd_mutex that still guards nfsd start/stop, version, thread, and listener ioctls/netlink commands.

The NMI backtrace captured khungtaskd on CPU 1 and an idle swapper/0 on CPU 0. That second CPU sample is fuzzing noise rather than the nfsd stall; the lockdep dump is the evidence that matters.

syzbot closed the mail with the usual test invitation:

"If you want syzbot to run the reproducer, reply with: #syz test: git://repo/address.git branch-or-commit-hash"

Nobody on linux-nfs has taken that offer this week.

Not an NFS client bug

Despite the [nfs?] syzbot tag and this summary series’ usual client focus, the code under test is nfsd, the in-kernel NFS server. nfsd_nl_threads_get_doit() lives in fs/nfsd/nfsctl.c and is the Generic Netlink replacement for the old nfsd control-channel thread-count query. There is no NFS client (fs/nfs/) frame on the hung stack, no sunrpc client slot, and no mount/idmapping involvement. Client developers can treat this as adjacent server-control fallout, not a client regression.

The same day, a sibling syzbot thread ([syzbot] [nfs?] INFO: task hung in nfsd_nl_version_get_doit) posted a matching reproducer in which a task waits in nfsd_nl_version_get_doit while another holds nfsd_mutex in nfsd_nl_listener_set_doit. That parallel report reinforces the diagnosis: nfsd_nl_listener_set_doit() can occupy nfsd_mutex long enough for any other nfsd netlink getter to look wedged. Historical cousins on the list include hung-task reports against nfsd_nl_threads_set_doit and nfsd_nl_listener_get_doit.

Status

Kind of change: bug (hung task / unbounded nfsd_mutex hold in nfsd Generic Netlink).

Evolution this week: the 2024 unreproducible report became a current-upstream C repro. The call sites have barely moved (nfsctl.c:1757 → :1754 for threads get; listener set still around :1964). The new dump is more severe in one respect: five getter tasks pile up behind the listener-set holder, which makes the global-mutex bottleneck even more obvious than the original single-waiter report.

Conclusion: none from maintainers. The thread is still waiting on an nfsd-side fix — likely shrinking the nfsd_mutex critical section in nfsd_nl_listener_set_doit, making the getters sleep killably, or otherwise preventing a netlink listener update from stalling thread/version queries. Until someone replies with a patch and #syz test / #syz fix, the reproducer stands as an open server-control deadlock/livelock under fuzzing, not a client issue.
