syzbot finds reproducer for nfsd_nl_version_get_doit hung task

Summary

This week’s only traffic on a two-year-old syzbot report is a new C reproducer for a hung-task stall in the NFS server netlink control path. There is still no human reply, no patch, and no #syz fix / #syz dup acknowledgement. The report is a bug, not a protocol change or a client feature: nfsd_nl_version_get_doit() blocks uninterruptibly on nfsd_mutex while a sibling netlink doit already holds that mutex.

Prior history (brief)

syzbot opened the bug on 24 June 2024 against upstream 2ccbdf43d5e7 (6.10-rc3-era), with no reproducer. The original hung-task watchdog fired after more than 144 seconds in:

"INFO: task syz-executor.2:26515 blocked for more than 144 seconds."

The 2024 stack already pointed at nfsd_nl_version_get_doit waiting on nfsd_mutex (fs/nfsd/nfsctl.c:1892), while another executor held the same mutex in nfsd_nl_listener_set_doit. The bot tagged the report [nfs?] and asked maintainers to add Reported-by: syzbot+41bc60511c2884783c27@syzkaller.appspotmail.com on any fix. That thread then went silent until this week.

This week: a C reproducer on current upstream

On 7 August 2026, syzbot reported that it now has a reproducer on current upstream (fcaeecb8b0cd, merge of probes-fixes-v7.2-rc6). Assets include a C reproducer, console log, kernel config, and the dashboard entry. The bot restated the usual fix tag:

"IMPORTANT: if you fix the issue, please add the following tag to the commit: Reported-by: syzbot+41bc60511c2884783c27@syzkaller.appspotmail.com"

The new hung-task dump is shorter (10 seconds rather than 144) but otherwise the same shape:

"INFO: task syz-executor371:5953 blocked for more than 10 seconds."

The blocked task is in D state in __mutex_lock from nfsd_nl_version_get_doit+0x18c/0x810 at fs/nfsd/nfsctl.c:1889, reached via Generic Netlink (genl_family_rcv_msg_doit → netlink_sendmsg → sendto). That is the nfsd control-plane NFSD_CMD_VERSION_GET handler, not an NFS client RPC path.

Lock dump: nfsd_mutex vs. listener set

The interesting evidence is the system-wide lock list, not the hung stack itself. Two threads of the same executor both hold Generic Netlink cb_lock and then serialize on nfsd_mutex:

  • syz-executor371/5952 holds nfsd_mutex in nfsd_nl_listener_set_doit (fs/nfsd/nfsctl.c:1964).
  • syz-executor371/5953 (the hung task) is waiting for the same nfsd_mutex in nfsd_nl_version_get_doit (fs/nfsd/nfsctl.c:1889).

In other words, a netlink set of NFS server listeners is sitting on the global nfsd mutex long enough that a concurrent get of the enabled NFS versions trips the hung-task watchdog. Both operations also take cb_lock in genl_rcv(), so the stall is a control-plane serialization problem: genetlink plus the process-wide nfsd_mutex that still guards nfsd start/stop, version, thread, and listener ioctls/netlink commands.

The NMI backtrace captured khungtaskd on CPU 1 and a concurrent modprobe in maple-tree mmap validation on CPU 0. That second CPU sample looks like fuzzing noise rather than the nfsd stall; the lockdep dump is the smoking gun.

syzbot closed the mail with the usual test invitation:

"If you want syzbot to run the reproducer, reply with: #syz test: git://repo/address.git branch-or-commit-hash"

Nobody on linux-nfs has taken that offer this week.

Not an NFS client bug

Despite the [nfs?] syzbot tag and this summary series’ usual client focus, the code under test is nfsd, the in-kernel NFS server. nfsd_nl_version_get_doit() lives in fs/nfsd/nfsctl.c and is the Generic Netlink replacement for the old nfsd control-channel version query. There is no NFS client (fs/nfs/) frame on the hung stack, no sunrpc client slot, and no mount/idmapping involvement. Client developers can treat this as adjacent server-control fallout, not a client regression.

The same day, a sibling syzbot thread ([syzbot] [nfs?] INFO: task hung in nfsd_nl_threads_get_doit) posted a matching reproducer in which several tasks wait in nfsd_nl_threads_get_doit while others hold nfsd_mutex in nfsd_nl_listener_set_doit. That parallel report reinforces the diagnosis: nfsd_nl_listener_set_doit() can occupy nfsd_mutex long enough for any other nfsd netlink getter to look wedged. Historical cousins on the list include hung-task reports against nfsd_nl_version_set_doit and nfsd_nl_listener_get_doit.

Status

Kind of change: bug (hung task / unbounded nfsd_mutex hold in nfsd Generic Netlink).

Evolution this week: the 2024 unreproducible report became a current-upstream C repro. The call sites have barely moved (nfsctl.c:1892 → :1889 for version get; listener set still around :1964).

Conclusion: none from maintainers. The thread is still waiting on an nfsd-side fix — likely shrinking the nfsd_mutex critical section in nfsd_nl_listener_set_doit, making the getters sleep killably, or otherwise preventing a netlink listener update from stalling version/thread queries. Until someone replies with a patch and #syz test / #syz fix, the reproducer stands as an open server-control deadlock/livelock under fuzzing, not a client issue.
