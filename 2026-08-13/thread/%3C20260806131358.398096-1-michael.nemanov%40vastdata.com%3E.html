NFS client: Trond tightens ENXIO-on-symlink type check toward v3

Overview

This is a bug fix, not a new feature or protocol change: review of Michael Nemanov's v2 for the NFSv3 client's nfs_atomic_open_v23() path in fs/nfs/dir.c. The patch stops open(2) with O_CREAT from returning ENXIO when a cold-dcache NFSv3 lookup lands on an existing symlink. Last week Nemanov posted v2 after Trond Myklebust flagged a dentry-refcount underflow in v1. This week the Linux NFS client maintainer reviewed that type check, then immediately tightened his own suggestion, and Nemanov agreed to spin a v3.

No Ack, Nack, or merge landed in this window. The thread is waiting on that v3.

Brief bridge from last week

v2 already applied Trond's one-line v1 correction: after a successful CREATE UNCHECKED, if the instantiated inode is not a regular file, return finish_no_open(file, NULL) so the VFS follows the symlink instead of calling no_open() (-ENXIO). Passing NULL avoids a second dput() on a dentry the caller still owns. The type test in v2 was !S_ISREG(d_inode(dentry)->i_mode), chosen over S_ISLNK() so any non-regular CREATE result would take the same path. That is where this week's review starts.

Trond: do not dereference a missing inode

Trond's first reply accepts the finish_no_open(file, NULL) shape but objects to assuming d_inode(dentry) is non-NULL:

"Hmm... I'm changing the above to if (!d_inode(dentry) || !S_ISREG(....)) so that we don't inadvertently try to open a negative dentry. That can happen with NFSv2 if we hit an existing directory that has been renamed on the server."

The remark is more than a NULL-safety nit. nfs_atomic_open_v23() is shared with NFSv2, and a CREATE that races a server-side rename can leave a negative dentry. v2's d_inode(dentry)->i_mode would then dereference NULL. Guarding the inode first keeps the "do not finish this open" exit for both a non-regular positive dentry (the original symlink/ENXIO case) and a negative dentry (the NFSv2 rename race).

Twenty minutes later: prefer d_is_reg()

Trond followed himself almost immediately:

"Actually, if (!d_is_reg(dentry)) is even better."

d_is_reg() is the VFS helper that is false for negative dentries and for any non-regular positive inode. It collapses the two-clause test into one call that already encodes the contract the client wants: only call finish_open() when the dentry is a regular file. Everything else — symlink, directory, device, or a hole left by an NFSv2 rename — falls through to finish_no_open(file, NULL) and the VFS open path.

That is a typical client-maintainer tightening: same control flow, less open-coded inode poking, and the negative-dentry case is no longer a special comment.

Nemanov agrees, offers v3

Nemanov replied on August 10 with a short confirmation:

"Agreed. Would you like a v3 with this fix?"

He did not push back on either the NFSv2 negative-dentry scenario or the switch from S_ISREG() to d_is_reg(). The type check that v2 had justified as "cover any other non-regular types a server might return" is now also the right check for a missing inode. A v3 would be a one-line substitution in the same seven-line hunk.

Why this matters for NFS client development

The review shows how thin the NFSv3 atomic_open path still is. The original 7c6c5249f061 work added atomic_open so O_TRUNC would ride CREATE UNCHECKED; the ENXIO-on-symlink bug is one sibling of that CREATE-result / VFS-file-type mismatch, and the NFSv2 negative dentry after a server-side directory rename is another. All three share the same exit: do not call finish_open() unless the dentry is a regular file.

It also shows the client's preferred idiom evolving in public. v1 used the wrong finish_no_open() argument and under-counted the dentry. v2 fixed the refcount and used !S_ISREG(d_inode()->i_mode). This week Trond first added an explicit NULL inode guard, then replaced both tests with d_is_reg(). Each step is a few characters; each one closes a real failure mode on the shared v2/v3 atomic-open path.
