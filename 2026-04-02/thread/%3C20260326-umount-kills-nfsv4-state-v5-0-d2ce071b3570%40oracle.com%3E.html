NFSD: Review of v5 Automatic NFSv4 State Revocation Series

Summary

Summary

This week, the Linux NFS mailing list focused on the review of Chuck Lever's [PATCH v5 0/7] series, "Automatic NFSv4 state revocation on filesystem unmount", which was submitted last week. The series introduces three new generic netlink commands (NFSD_CMD_UNLOCK_IP, NFSD_CMD_UNLOCK_FILESYSTEM, NFSD_CMD_UNLOCK_EXPORT) to allow userspace tools to revoke NFSv4 client state (opens, locks, delegations) when underlying filesystems or exports are unmounted, resolving the common EBUSY failure during unmount operations.

Jeff Layton provided a thorough review of the series, offering Reviewed-by tags for the cover letter and the first patch, while engaging in technical discussions regarding locking correctness, tracepoint efficiency, and userspace integration plans.

Key Technical Arguments

Patch 1/7: Locking Correctness in revoke_one_stid()

Jeff Layton identified a regression introduced during the final rebase of Patch 1/7, which extracts the revoke_one_stid() utility function. He noted that the kernel test robot had flagged an incorrect lock usage:

"Oh hah, just noticed the kernel test robot pointed out the above. Should be nn->deleg_lock now, no?" Jeff Layton

Chuck Lever acknowledged the error, attributing it to a last-minute rebase:

"Ja, I rebased just before sending these yesterday. Duh." Chuck Lever

Despite this bug, Layton recognized the value of the refactoring itself:

"Nice little cleanup on its own. This could be merged ahead of the rest of the series." Jeff Layton

Patch 2/7: Tracepoint Argument Efficiency

A minor but technical debate arose regarding the implementation of the NFSD_CMD_UNLOCK_IP netlink command. Layton questioned why the address length (svc_addr_len(sap)) was calculated before the tracepoint call, suggesting it could be moved inside to avoid calculation when tracing is disabled:

"All of the tracepoints get passed svc_addr_len(sap) for the length. Any reason not to just determine the length inside the tracepoint, so you don't need to calc the length unless it's enabled?" Jeff Layton

Lever initially argued that the static branch already skips argument evaluation. However, Layton persisted that reducing tracepoint arguments is preferable:

"It's a minor thing, but fewer arguments to a tracepoint is nicer, IMO." Jeff Layton

Lever ultimately explained that the current approach was dictated by the tracepoint macro requirements:

"The TP_STRUCT__entry( ) macro needs the length value up front to size the ring buffer entry. This is the cleanest way to do it." Chuck Lever

Userspace Integration Plans

Layton inquired about the userspace components required to drive these new netlink commands, specifically whether Lever planned to extend nfsdctl or create a new binary:

"Can you comment a bit about your intentions with userland here? Do you plan to extend nfsdctl to add this support or add a new binary to nfs-utils?" Jeff Layton

Lever clarified that he had already developed an exportfs patch that utilizes the netlink UNLOCK command during unexport operations, but withheld it from this submission due to ongoing debates about policy logic (e.g., skipping revocation during shutdown to allow state recovery):

"I have a version of exportfs that performs the netlink UNLOCK command as part of unexporting... I'm sure there are some details about that logic/policy that will need more debate." Chuck Lever

He emphasized that the kernel infrastructure is designed to stand alone:

"These new UNLOCK commands stand alone as a feature, even though they are not the full solution for addressing the unmounting failure after an export, so I didn't post the exportfs patch this time." Chuck Lever

Evolution of the Discussion

The discussion began with Layton's positive assessment of the series, granting Reviewed-by for the overall approach and the first patch. The conversation then shifted to specific technical details:

  1. Bug Identification: The discovery of the incorrect lock in Patch 1/7 highlighted the risks of last-minute rebases, though Lever quickly acknowledged the fix.
  2. Tracepoint Optimization: A brief back-and-forth on tracepoint argument passing demonstrated the developers' attention to performance and code cleanliness, ultimately settling on the macro-imposed structure.
  3. Userspace Scope: The dialogue clarified that while the kernel patches are complete and reviewed, the full operational solution depends on future userspace updates to exportfs, which are still being refined.

Final Conclusions

The v5 series for automatic NFSv4 state revocation has received strong initial support from Jeff Layton, with explicit Reviewed-by tags indicating readiness for merge pending minor fixes. The identified locking bug in Patch 1/7 is acknowledged and trivial to correct. The technical debate regarding tracepoints was resolved in favor of the current implementation due to macro constraints.

The series represents a significant step forward in NFS server administration, providing a modern netlink interface to resolve EBUSY unmount errors. While the kernel infrastructure is deemed solid, the complete solution awaits the integration of these commands into userspace tools like exportfs, which Lever plans to address in subsequent submissions once policy details are finalized.

"This all looks good to me. A couple of minor nits, but nothing that looks wrong." Jeff Layton
