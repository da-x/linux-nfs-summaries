NFSD: v7 Automatic NFSv4 State Revocation Series Submitted

Summary

This week, Chuck Lever submitted version 7 of his series "Automatic NFSv4 state revocation on filesystem unmount" PATCH v7 0/7. This is a new feature / protocol extension for the NFS server (nfsd), introducing three new generic netlink commands that enable userspace tools to revoke NFSv4 client state (opens, locks, delegations) when underlying filesystems or exports are unmounted. This resolves the long-standing operational problem where umount fails with EBUSY due to active NFSv4 state references.

Context from Prior Weeks

In the previous week, Jeff Layton reviewed version 5 of this series, providing Reviewed-by tags and identifying a locking regression in Patch 1/7 where state_lock should have been nn->deleg_lock. Layton also engaged in a technical discussion regarding tracepoint argument efficiency. Lever acknowledged the fixes and explained that tracepoint macro constraints dictated the argument structure.

Last week, Chuck also submitted v6 of the series PATCH v6 0/5, which was a 5-patch version. However, as noted in the v7 cover letter:

"Changes since v6: Send the complete series (v5 was missing patches 6 and 7)" Chuck Lever

This indicates that v6 was incomplete, lacking the critical UNLOCK_EXPORT command and the file cache cleanup logic. The v7 submission this week provides the full 7-patch series.

Key Technical Arguments

Three Netlink Commands for Granular State Revocation

The series introduces three distinct netlink commands, each serving a specific administrative intent:

  1. NFSD_CMD_UNLOCK_IP: Releases NLM locks held by a specific client IP address, providing a netlink equivalent of /proc/fs/nfsd/unlock_ip.

  2. NFSD_CMD_UNLOCK_FILESYSTEM: Revokes all NFS state on a superblock, serving as the netlink equivalent of /proc/fs/nfsd/unlock_fs. This is used when unmounting an entire filesystem.

  3. NFSD_CMD_UNLOCK_EXPORT: Revokes NFSv4 state acquired through exports of a specific path, regardless of client. This enables finer-grained control for administrators unexporting a single path on a shared filesystem.

Lever clarified the distinction between the last two commands:

"UNLOCK_FILESYSTEM and UNLOCK_EXPORT serve different intents. UNLOCK_FILESYSTEM means 'unmounting /data, release everything on this superblock.' UNLOCK_EXPORT means 'no clients remain for /data/projectA, release only the state acquired through exports of that path.'" Chuck Lever

Path-Only Design for UNLOCK_EXPORT

A significant architectural decision in this series is that UNLOCK_EXPORT takes only a path attribute, not a client identifier. This simplifies the interface by avoiding the complexity of auth_domain naming (e.g., use_ipaddr vs hostname-based domains):

"The path-only design for UNLOCK_EXPORT avoids the auth_domain naming complexity (use_ipaddr vs hostname-based domains) by not requiring the caller to identify a specific client. Since this mechanism is to be used to enable umount, this seemed like a reasonable compromise." Chuck Lever

Userspace tools like exportfs -u will send UNLOCK_EXPORT after removing the last client for a given path, enabling the underlying filesystem to be unmounted. When multiple clients share an export path, individual unexports do not trigger state revocation; only the final one does.

Patch Breakdown

  • PATCH 1/7: Extracts revoke_one_stid() utility function. This refactoring isolates per-stateid revocation logic, preparing the codebase for export-scoped state revocation. Jeff Layton previously noted, "Nice little cleanup on its own."

  • PATCH 2/7: Adds NFSD_CMD_UNLOCK_IP. It accepts a binary sockaddr_in or sockaddr_in6 and releases matching NLM locks. The tracepoint was updated to use %pISpc for structured output.

  • PATCH 3/7: Adds NFSD_CMD_UNLOCK_FILESYSTEM. It resolves a filesystem path to its superblock and revokes all associated NFSv4 state, including async copies and NLM locks.

  • PATCH 4/7: Replaces idr_for_each_entry_ul with a while loop over idr_get_next_ul in find_one_sb_stid() for consistency with the new find_one_export_stid().

  • PATCH 5/7: Tracks svc_export in nfs4_stid. Each stateid now records the export under which it was acquired, allowing state revocation to be scoped to a specific export without walking inode dentry aliases.

  • PATCH 6/7: Adds NFSD_CMD_UNLOCK_EXPORT. This new command revokes NFSv4 state acquired through exports of a specific path. Matching is performed by path identity (dentry + vfsmount) via the sc_export field on each nfs4_stid, correctly handling multiple svc_export objects for the same path across different auth_domains.

  • PATCH 7/7: Closes cached file handles when revoking export state. This patch adds nfsd_file_close_export(), which walks the nfsd_file hash table and closes GC-eligible entries whose underlying file resides on the same filesystem and is a descendant of the export path. This prevents cached file handles from holding the filesystem busy after state revocation.

Evolution of the Discussion

The series has evolved significantly through seven versions:

  • v1-v2: Initial design using fs_pin and SRCU umount notifier chains in VFS.
  • v3: Replaced all VFS changes with new netlink "unlock" operations.
  • v4: Split the single NFSD_CMD_UNLOCK into three separate commands; UNLOCK_EXPORT takes path only to avoid auth_domain complexity.
  • v5: Reviewed by Jeff Layton, who identified a locking bug (state_lock vs nn->deleg_lock) and provided Reviewed-by tags.
  • v6: Fixed the locking issue but was incomplete, missing patches 6 and 7.
  • v7: Complete 7-patch series with all functionality implemented.

Final Conclusions

The v7 series represents a mature and complete implementation of automatic NFSv4 state revocation on unmount. By providing three granular netlink commands—UNLOCK_IP, UNLOCK_FILESYSTEM, and UNLOCK_EXPORT—the series gives userspace administrators precise control over state cleanup. The path-only design for UNLOCK_EXPORT simplifies integration with tools like exportfs.

All patches in the series carry Reviewed-by: Jeff Layton <jlayton@kernel.org>, indicating strong technical endorsement from the NFS subsystem maintainer. With the locking issues from v5 resolved and the missing functionality from v6 now included, the series is ready for integration into the mainline kernel.

The subsequent step will be the integration of these netlink commands into nfs-utils (specifically exportfs) to complete the user experience. As Lever noted in prior discussions:

"I have a version of exportfs that performs the netlink UNLOCK command as part of unexporting... I'm sure there are some details about that logic/policy that will need more debate." Chuck Lever
