RFC: Enabling PCI Peer-to-Peer DMA (P2PDMA) in NFS Client Direct I/O

Summary

Overview

Pranjal Shrivastava submitted an RFC patch series to introduce PCI Peer-to-Peer DMA (P2PDMA) support for the NFS client, specifically targeting the Direct I/O path. This feature aims to enable high-performance storage environments to move data directly between PCIe endpoints—such as NVMe controllers and Network Interface Cards—bypassing system memory.

"As high-performance storage environments increasingly rely on direct data movement between PCIe endpoints... support for Peer-to-Peer DMA (P2PDMA) in the network filesystem layer becomes essential." — Pranjal Shrivastava

Currently, NFS O_DIRECT operations fail with -EREMOTEIO when user buffers reside in PCIe BAR memory due to legacy API limitations and a request lifecycle unaware of P2P pinning requirements.

Key Technical Changes

The four-patch series introduces several infrastructure changes:

  1. Transport-Level Detection: A new supports_p2pdma operation is added to rpc_xprt_ops. For RDMA, this queries the underlying InfiniBand device via ib_dma_pci_p2p_dma_supported() 1.
  2. 64-Bit Capability Expansion: The nfs_server->caps bitmask is expanded from 32-bit to 64-bit to accommodate the new NFS_CAP_P2PDMA flag, preventing truncation bugs in bitwise operations 2.
  3. Pin-Aware Request Lifecycle: A PG_PINNED flag is added to struct nfs_page. This ensures that pages extracted via iov_iter_extract_pages() are correctly unpinned using unpin_user_page() only after I/O completion, rather than using standard put_page() 3.
  4. API Migration: The Direct I/O path migrates from the legacy iov_iter_get_pages_alloc2() to the modern iov_iter_extract_pages(), allowing the use of the ITER_ALLOW_P2PDMA flag 4.

Reviewer Feedback and Discussion Evolution

The series received significant architectural feedback from Christoph Hellwig and Chuck Lever, highlighting necessary refinements before the feature can be merged.

Separation of Concerns and API Modernization

Christoph Hellwig emphasized that the migration to iov_iter_extract_pages() is a critical bug fix in its own right, independent of P2PDMA support. He noted that this change "fixes potential data corruption in XFS" and urged Pranjal to split it into a separate preparation series.

"Please split the conversion to iov_iter_extract_pages into a separate preparation patch, and even series. That is a long overdue change that fixes potential data corruption in XFS." — Christoph Hellwig

Hellwig also suggested that the NFS I/O code should move beyond pages to iov_iter_extract_bvecs for better efficiency with large I/O, as buffered I/O already uses folios.

Missing pNFS Support

Hellwig pointed out a major gap in the current design: the series ignores Parallel NFS (pNFS). He argued that P2PDMA support must be validated through the layout driver for the specific file range, noting that block-style layouts can also benefit from P2P DMA.

"Besides the point of splitting out the iov_iter_extract* conversion this seems to ignore pNFS. You also need to check the layout driver for the current file range and propagate P2P support or lack of through that." — Christoph Hellwig

Transport Reconnection and Stale Capabilities

Chuck Lever identified a critical flaw in the mount-time capability detection for RDMA transports. He questioned whether the transport is fully connected when nfs_server_set_init_caps() runs, noting that if an RDMA connection drops and reconnects to a different device, the NFS_CAP_P2PDMA flag would become stale.

"Note that, even if this logic /is/ correct, if the transport connection is lost the transport will reconnect automatically... The NFS client layer will be none-the-wiser and the NFS_CAP_P2PDMA flag setting will be stale at that point..." — Chuck Lever

Lever proposed that P2PDMA detection must occur during xprtrdma's connection flow, setting a flag in the rpc_xprt structure. The Direct I/O code would then check this flag dynamically for each I/O operation, ensuring correctness across reconnections.

Conclusions

This RFC series marks the beginning of P2PDMA support in the NFS client, addressing a key performance bottleneck for PCIe-attached storage and networking hardware. However, the discussion has evolved to highlight several prerequisites:

  1. API Migration First: The transition to iov_iter_extract_pages() should be separated as a standalone bug fix.
  2. Dynamic Capability Checking: P2PDMA support must be verified per-I/O or per-connection rather than at mount time to handle RDMA reconnections safely.
  3. pNFS Integration: Future iterations must integrate with pNFS layout drivers to ensure P2P DMA is only used when the underlying storage layout supports it.

The thread remains open for further refinement of these architectural concerns.
