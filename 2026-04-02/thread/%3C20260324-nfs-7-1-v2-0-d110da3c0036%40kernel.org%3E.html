NFS: Delegated Timestamp Semantics and removexattr ctime Fix

Summary

This week's discussion centered on [PATCH v2 2/2] nfs: update inode ctime after removexattr operation by Jeff Layton. The patch addresses a bug where the NFS client fails to update the inode change time (ctime) after a removexattr operation when delegated timestamps are active, causing xfstest generic/728 to fail.

The thread evolved from a specific code fix into a broader debate on NFS protocol semantics regarding delegated attributes, server authority, and specification clarity. Key participants included Jeff Layton (Red Hat), Olga Kornievskaia (UMich/Hammerspace), Thomas Haynes (Hammerspace), and Rick Macklem.

The Bug and Proposed Fix

Jeff Layton identified that when a client holds a WRITE_ATTRS_DELEG, a removexattr operation updates the server's ctime, but the client relies on its cached value because the subsequent stat() does not trigger a GETATTR.

"The client does a removexattr and then a stat to test the ctime, which doesn't change. The stat() doesn't trigger a GETATTR because of the delegated timestamps, so it relies on the cached ctime, which is wrong." Jeff Layton

Layton's solution mirrors the setxattr implementation: append a trailing GETATTR to the REMOVEXATTR compound operation to fetch the fresh ctime from the server.

Debate on Server Behavior and Authority

Olga Kornievskaia questioned whether this approach relied on assumptions about server behavior, noting that the Linux NFS server (nfsd) does not update change_attribute for operations like WRITE, CLONE, or COPY when a delegation is held. She proposed an alternative fix but acknowledged uncertainty about other server implementations.

"This approach relies on the fact that the server the serves delegated attributes would update change_attr on operations which might now necessarily happen (ie, linux server does not update change_attribute on writes or clone)." Olga Kornievskaia

Thomas Haynes (Hammerspace) shifted the discussion to protocol semantics, arguing that authority should follow the delegation model similar to delegated size in RFC 8881. He explained that Hammerspace issues a CB_GETATTR callback to the delegating client before responding to any GETATTR request to ensure consistency with the client's authoritative state.

"The authority follows the delegation, not the specific operation... So the spec question, as I see it, is not whether REMOVEXATTR (or any particular op) should update ctime/mtime, but whether delegated timestamps are meant to follow the same attribute-authority model as delegated size in RFC8881." Thomas Haynes

Olga observed that neither nfsd nor her tests against Hammerspace consistently adhered to this model for all operations, such as CLONE. Rick Macklem added historical context, noting that CB_GETATTR was traditionally intended for queries from different clients than the one holding the delegation.

"I thought the requirement to do a CB_GETATTR was if the GETATTR is from a different client than the one holding the delegation... Only after a DELEGRETURN does the server have the definitive values for these attributes." Rick Macklem

Client-Side Rationale and Consensus

Jeff Layton provided a definitive client-side rationale for why REMOVEXATTR (and SETXATTR) cannot be cached or deferred like WRITE operations:

  1. Synchronous Error Reporting: Unlike writes, which can be buffered and confirmed via fsync(), extended attribute operations must complete synchronously because they can fail and have no mechanism for deferred error reporting to user space.
  2. Limited Delegated Update Mechanism: The delegated timestamp mechanism lacks a way to update only ctime.

"I don't see how you could reasonably buffer a SETXATTR or REMOVEXATTR operation to be sent later... They must be done synchronously because: 1/ there's no way to update only the ctime in a delegated timestamp update ...and... 2/ these syscalls can fail, so we can't return from them until we know the outcome." Jeff Layton

Consequently, Layton concluded that both client and server must ignore the timestamp delegation for these operations. The server should update ctime, and the client must fetch it via a trailing GETATTR.

"Based on that, I think the client and server both need to ignore the timestamp delegation on a SETXATTR or REMOVEXATTR... Exactly what this patch does, fwiw..." Jeff Layton

Future Specification Clarification

The thread concluded with a productive discussion on improving the NFS specification to avoid similar ambiguities. Thomas Haynes warned against defining behavior by enumerating specific operations, advocating instead for a semantic classification based on completion models:

"One concern I have with the 'ops that can report delayed error' formulation is that... the ability to convey delay is not a distinguishing property of a particular operation... It seems better to define the behavior in terms of operation properties - e.g., whether the operation is synchronously visible, can be deferred/cached at the client..." Thomas Haynes

Haynes proposed that the spec should distinguish between operations where the client may acknowledge completion before authoritative server execution (allowing delegated timestamp authority) and those requiring synchronous authoritative execution. Layton agreed with this direction.

"Ack. Sounds good to me." Jeff Layton

Conclusion

  • Bug Fix: The immediate fix for xfstest generic/728 is to add a trailing GETATTR to the REMOVEXATTR compound operation in the NFS client. This ensures the ctime is refreshed from the server, justified by the synchronous nature of extended attribute operations and the limitations of delegated timestamp updates.
  • Protocol Semantics: The discussion highlighted ambiguities in the NFS specification regarding which operations invalidate or bypass delegated timestamp authority. While WRITE and COPY are clearly handled, metadata operations like SETXATTR, REMOVEXATTR, and CLONE have been implemented based on assumptions rather than explicit rules.
  • Future Spec Work: There is consensus that the NFS specification needs clarification to define delegated timestamp behavior based on operation semantics (synchronous vs. deferred completion) rather than enumerating specific opcodes. This will ensure consistent behavior across different server implementations and future protocol extensions.
