lockd TEST fix: Stable backporting complications due to nfsd-testing divergence

Summary

lockd TEST Fix: Stable Backporting Complications Due to nfsd-testing Divergence

Classification: Bug Fix (NFS Server / lockd Permission Checks) — Maintenance Discussion

Bridge from Prior Weeks

This thread continues the resolution of a regression in the NFS server's lockd subsystem. In prior weeks, Neil Brown submitted Patch v2 to fix a bug where F_GETLK (lock testing/querying) incorrectly required write access even for read-only file descriptors. The issue was exposed by commit 4cc9b9f2bf4d ("nfsd: refine and rename NFSD_MAY_LOCK"), which fixed a separate masking bug in nfsd_permission(). Patch v2, submitted on March 26, introduced O_RDWR as a mode for nlm_do_fopen() to allow lock tests to succeed with either read or write access. The patch received a Reviewed-by from Jeff Layton and was accepted in principle by Chuck Lever. A pragmatic backporting strategy was agreed upon: using Fixes: 4cc9b9f2bf4d in the metadata to ensure stable kernel automation tools correctly identify affected kernels, despite that commit only exposing rather than introducing the bug.

This Week's Activity: Stable Backporting Complications

This week saw a single message from Chuck Lever on March 27, raising a new logistical concern regarding the backporting of Neil Brown's fix to Long-Term Support (LTS) kernels.

The nfsd-testing Branch Divergence Problem

Chuck Lever highlighted that the patch, as written for upstream, will not apply cleanly to the nfsd-testing branch due to a significant code rewrite:

"We have a new problem now (or maybe just I do)."

"I think the stable folks will insist on this fix going into upstream first. However, this version of the fix does not apply to nfsd-testing because that branch has the NLMv4 xdrgen rewrite."

The nfsd-testing branch contains an NLMv4 (Network Lock Manager version 4) XDR generation rewrite, which alters the code structure in fs/lockd/svc4proc.c and related files. This means the upstream patch cannot be mechanically backported to kernels that track this branch.

Backporting Strategy for LTS Kernels

Lever further clarified that the NLMv4 xdrgen rewrite is unlikely to be backported to LTS kernels, creating a two-track maintenance situation:

"That rewrite is not likely to be backported to LTS. So this version will have to be directed to stable once upstream has been fixed. We cannot rely on automation to get upstream's version of the fix backported to v6.19 and earlier."

This implies that:

  1. The patch must first be merged into the mainline kernel (upstream).
  2. A separate, manually prepared version of the fix will need to be submitted directly to the stable tree for kernels v6.19 and earlier.
  3. Automated backporting tools cannot handle this process due to the code divergence between upstream and nfsd-testing.

Key Technical Arguments

  1. Code Divergence Between Upstream and Testing Branches: The nfsd-testing branch's NLMv4 xdrgen rewrite creates a structural mismatch that prevents clean patch application. This is a recurring challenge in NFS server development, where experimental features in testing branches can complicate stable backporting.

  2. Manual Stable Submission Required: Unlike typical fixes that flow automatically from upstream to stable kernels via automation, this fix requires manual intervention. Chuck Lever explicitly notes: "We cannot rely on automation to get upstream's version of the fix backported to v6.19 and earlier."

  3. Stable Kernel Policy: The stable maintainers' expectation is that fixes go into upstream first, after which they can be cherry-picked or adapted for LTS kernels. This process is now complicated by the need to create a separate patch variant for pre-nfsd-testing kernels.

Final Conclusions

  • Patch v2 remains accepted: The technical fix itself is sound and has been reviewed positively. No changes to the patch content are indicated at this time.
  • Backporting requires manual effort: Chuck Lever has identified that the stable tree backport for kernels v6.19 and earlier cannot rely on automation. A separate submission or manual cherry-pick will be needed after upstream merge.
  • NLMv4 xdrgen rewrite creates a maintenance boundary: The divergence between nfsd-testing and mainline/LTS code paths means that future patches touching NLM-related code may face similar backporting complications.
