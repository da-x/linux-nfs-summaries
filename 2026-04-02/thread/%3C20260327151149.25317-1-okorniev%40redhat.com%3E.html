NFSv4.2: Fix CLONE Attribute Updates with Delegated Attributes

Summary

NFSv4.2 CLONE Attribute Fix for Delegated Attributes

Classification: Bug Fix

This thread concerns a bug fix in the NFSv4.2 client related to incorrect attribute handling after a CLONE operation when delegated attributes are present.

Summary

Olga Kornievskaia from Red Hat submitted a single-patch series addressing a regression in the NFS client's handling of file attributes following an NFSv4.2 CLONE operation. The issue was detected by xfstest generic/407, which revealed two distinct failures when delegated attributes were active on the client side As described in the patch submission.

Key Technical Arguments

The core problem stems from the interaction between the CLONE operation and delegated attribute caching. Olga explains:

"xfstest generic/407 is failing in 2 ways. It detects that after doing a clone the client does not update it's mtime and it's ctime."

The technical root cause involves two issues:

  1. mtime/ctime not updated: The CLONE operation always sends a GETATTR request to the server and subsequently calls nfs_post_op_update_inode() with the returned attributes. However, when delegated attributes are present on the client, the client ignores the server-provided mtime values, relying instead on its cached delegation.

  2. Stale change_attr values: When delegated attributes are active, the server replies with the same change_attr values that the client had previously cached. This causes xfstest generic/407 to flag the inconsistency, as the file's metadata appears unchanged despite the clone operation having occurred.

Olga's fix ensures that the block attributes are invalidated after a CLONE operation, forcing the client to refresh its attribute cache rather than relying on stale delegated values. The patch targets fs/nfs/nfs42proc.c, adding 9 lines and removing 1.

The regression was introduced by commit e12912d94137, titled "NFSv4: Add support for delegated atime and mtime attributes," which added delegation-aware attribute caching but inadvertently broke the CLONE post-operation update path.

Significance for NFS Client Development

This fix is important for NFSv4.2 clients using space-efficient clone operations (a feature critical for storage virtualization and deduplication workloads). Without this patch, clients with delegated attributes would maintain stale metadata after clones, potentially leading to:

  • Incorrect file timestamp reporting to applications
  • Test failures in xfstest suites used for regression validation
  • Potential data consistency issues in production environments relying on clone semantics

The fix demonstrates the ongoing challenges in balancing performance optimizations (delegated attribute caching) with correctness guarantees in complex distributed filesystem operations.
