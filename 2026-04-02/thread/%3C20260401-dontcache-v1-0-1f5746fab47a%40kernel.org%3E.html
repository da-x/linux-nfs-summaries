mm: Improve RWF_DONTCACHE Write Performance and Reduce Lock Contention

Summary

Overview

This week, Jeff Layton proposed a patch series aimed at significantly improving write performance for the RWF_DONTCACHE IO mode, which is increasingly relevant for NFS server (nfsd) configurations that allow users to select IO modes via debugfs controls. The series addresses severe throughput collapses and tail latency spikes observed when using RWF_DONTCACHE under heavy write loads, both on local filesystems (XFS with io_uring) and over NFS.

The discussion centers on two core patches modifying the memory management subsystem to rate-limit writeback triggered by IOCB_DONTCACHE, alongside two benchmarking suites included for transparency.

Key Technical Arguments

The Problem: Aggressive Flushing and Serialization

Layton identified that IOCB_DONTCACHE currently calls filemap_flush_range() with nr_to_write=LONG_MAX on every write, flushing all dirty pages in the written range.

"Under concurrent writers this creates severe serialization on the writeback submission path, causing throughput to collapse to ~47% of buffered I/O with multi-second tail latency." As stated by Jeff Layton

Even single-client sequential writes suffered, limited to 575 MB/s versus 1442 MB/s with rate-limited writeback due to dirty throttling.

Proposed Solution: Rate-Limited Writeback

Layton proposed replacing the flush call with a new filemap_dontcache_writeback_range() function featuring two mechanisms as described in Patch 1/4:

  1. Skip-if-busy: Checks mapping_tagged(PAGECACHE_TAG_WRITEBACK) before flushing. If writeback is already in progress, the flush is skipped to eliminate contention.
  2. Proportional cap: Caps nr_to_write to the number of pages just written, preventing a single write from starving concurrent readers.

To address "thundering herd" issues when the writeback tag clears, Layton added an atomic flag AS_DONTCACHE_FLUSHING in Patch 2/4 to ensure only one writer flushes at a time. He also included a "dirty pressure escape hatch" that bypasses the skip-if-busy check if dirty pages exceed 75% of the dirty_ratio threshold.

Critique and Review

Christoph Hellwig and Ritesh Harjani provided critical feedback on April 2nd:

  • API Mismatch: Both reviewers noted that filemap_writeback in the patch had six arguments, whereas it only accepts five in mainline trees. Layton acknowledged this as a merge error: "Mea culpa... I'll post a v2 in the near future." Jeff Layton
  • Design Concerns: Hellwig questioned the fundamental approach, suggesting that in-caller writeback might be a "bad reimplementation of the single writeback thread." He asked:

    "Have you considered stopping to do in-caller writeback for IOCB_DONTCACHE vs just leaving it to the writeback daemon?" Christoph Hellwig

  • Lock Contention Theory: Harjani suggested that the performance penalty in single-writer cases might stem from xa_lock contention between submission and completion, noting that DONTCACHE completions remove folios from the page cache within the same lock. He recommended using perf to confirm this theory.
  • Coverage Gaps: Harjani pointed out that if writers skip flushes due to the busy check, background writeback must handle the data. However, subsequent writers might not overlap the skipped ranges, potentially leaving dirty pages unflushed until global pressure triggers them.

Evolution and Conclusion

Layton defended the strategy of having writers perform some writeback work to stay ahead of dirty limits, stating:

"I think having each writer do some writeback submission work makes a lot of sense. It helps keep the dirty pages below the dirty thresholds and doesn't seem to tax each writing task too much." Jeff Layton

However, he agreed to revisit the atomic guard mechanism and further profile lock contention. The discussion concluded with Layton committing to a v2 patch series that addresses the API errors and potentially refines the flush guard logic based on Hellwig's suggestions regarding writeback scalability.

Impact on NFS Client/Server Development

While these patches target the generic memory management layer, they are directly motivated by nfsd IO mode controls. Improving RWF_DONTCACHE performance allows NFS servers to offer a viable alternative to buffered I/O and direct I/O, providing better isolation for noisy-neighbor workloads without the overhead of full direct I/O. The benchmarking suites included in the series (nfsd-io-bench and dontcache-bench) provide valuable tools for evaluating these IO modes in future NFS server optimizations.
