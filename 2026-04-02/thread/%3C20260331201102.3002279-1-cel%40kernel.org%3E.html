exportfs: Release NFSv4 state when last client is unexported

Summary

exportfs: Release NFSv4 State When Last Client Is Unexported

Classification

This is a bug fix / userspace enhancement to nfs-utils, specifically targeting the exportfs utility. The patch addresses a persistent operational pain point for NFS server administrators: the inability to unmount filesystems after removing exports due to lingering NFSv4 state (opens, locks, delegations).

Overview

This week, Chuck Lever submitted a standalone patch to nfs-utils that enables exportfs -u to automatically revoke NFSv4 client state when the last export entry for a given path is removed. This submission represents the long-awaited userspace integration of the kernel-side netlink UNLOCK commands (NFSD_CMD_UNLOCK_IP, NFSD_CMD_UNLOCK_FILESYSTEM, NFSD_CMD_UNLOCK_EXPORT) that were reviewed and accepted in prior weeks.

As noted in the review of Lever's v5 kernel series, Lever had previously hinted at this userspace work:

"I have a version of exportfs that performs the netlink UNLOCK command as part of unexporting... I'm sure there are some details about that logic/policy that will need more debate." — Chuck Lever

This patch is the realization of that promise.

Key Technical Arguments

The Problem: EBUSY on Unmount After Export Removal

The core issue is well-documented in the NFS community. When an administrator removes an export using exportfs -u, the kernel's NFSv4 state (opens, locks, delegations) acquired by clients through that export remains active. These open file handles keep the underlying filesystem busy, causing subsequent umount attempts to fail with EBUSY.

Lever describes this in the patch commit message:

"When exportfs -u removes the last client for a given export path, NFSv4 state (opens, locks, delegations) acquired through that export may still hold the underlying filesystem busy, preventing unmount." — Chuck Lever

The Solution: Netlink-Driven State Revocation

The patch introduces logic into exportfs that, after removing an export entry, checks whether any active exports remain for the same path across all client types. If none remain, it sends the NFSD_CMD_UNLOCK_EXPORT command to the kernel via generic netlink, which revokes the associated NFSv4 state and closes cached file handles.

"After removing an export entry, check whether any active exports remain for the same path across all client types. If none remain, send NFSD_CMD_UNLOCK_EXPORT to the kernel via generic netlink, which revokes the associated NFSv4 state and closes cached file handles." — Chuck Lever

Shared Netlink Helper Infrastructure

A notable architectural decision is the introduction of a new shared helper function, nfsd_nl_cmd_str(), in support/nfs/nfsdnl.c. This helper abstracts the netlink socket setup, message construction, and ACK handling for simple nfsd commands carrying a single string attribute. The helper is conditionally compiled when libnl3 is available, gated by the existing nfsdctl configure option.

This shared infrastructure approach suggests that future userspace tools beyond exportfs may leverage these netlink capabilities without duplicating socket management code.

Updated Netlink Header Definitions

The patch also updates the local nfsd_netlink.h copy in utils/nfsdctl/ with the definitions for NFSD_CMD_UNLOCK_IP, NFSD_CMD_UNLOCK_FILESYSTEM, and NFSD_CMD_UNLOCK_EXPORT, ensuring userspace has the necessary protocol definitions to communicate with the kernel's new netlink interface.

Evolution of the Discussion

This thread consists of a single patch submission with no replies within this week's window. However, its context is deeply rooted in prior discussions:

  1. Kernel Infrastructure (Prior Week): The v5 series introducing the three UNLOCK netlink commands to the kernel was reviewed by Jeff Layton, who granted Reviewed-by tags and engaged in technical debates about locking correctness and tracepoint efficiency. Lever stated that these commands "stand alone as a feature" even without userspace integration.

  2. Companion Netlink Upcall Series (Prior Week): Jeff Layton's 13-patch series adding netlink upcall support for mountd/exportd was applied to the nfsd-testing tree by Chuck Lever, establishing the broader netlink communication framework that this exportfs patch builds upon.

  3. Policy Considerations: Lever had previously noted that "details about that logic/policy will need more debate," particularly regarding edge cases such as whether revocation should be skipped during system shutdown to allow for state recovery. This patch appears to implement a straightforward policy: revoke state only when the last export for a path is removed.

Final Conclusions

This patch represents a critical piece of the puzzle in resolving the EBUSY unmount problem that has long plagued NFS server administrators. By integrating the kernel's new netlink UNLOCK commands into exportfs, users can now cleanly remove exports and subsequently unmount filesystems without manual intervention to flush stale NFSv4 state.

The patch touches six files across the nfs-utils codebase, adding 115 lines of code while removing only 3. The introduction of the shared nfsd_nl_cmd_str() helper suggests a forward-looking design that will benefit future userspace tools requiring netlink communication with nfsd.

As this is a standalone submission with no replies in this week's window, its ultimate fate depends on review from the nfs-utils maintainers and broader community feedback. Given the strong prior support for the underlying kernel infrastructure, this patch is well-positioned for acceptance.
