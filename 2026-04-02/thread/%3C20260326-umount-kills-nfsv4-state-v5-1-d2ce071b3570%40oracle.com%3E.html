NFSD: CI Build Failures for revoke_one_stid() Locking Bug

NFSD: Build Failures Reported for revoke_one_stid() Extraction Patch

Summary

This week's activity on the "Automatic NFSv4 state revocation" thread was dominated by automated build failure reports from the kernel test robot. The reports targeted [PATCH v5 1/7] "NFSD: Extract revoke_one_stid() utility function", which is part of Chuck Lever's series to allow userspace tools to revoke NFSv4 client state when underlying filesystems are unmounted.

As noted in last week's summary, Jeff Layton had already identified a locking regression in this patch, attributing it to a last-minute rebase by Lever. This week, the 0-DAY CI Kernel Test Service confirmed the issue across multiple architectures and compilers, generating four separate error reports on March 27.

Key Technical Arguments

The Bug: Undeclared state_lock

The core issue is a compilation error in fs/nfsd/nfs4state.c within the newly extracted revoke_one_stid() function. The patch attempts to acquire a spinlock named state_lock, which is undeclared in this context.

The kernel test robot reported the error consistently across different configurations:

"error: 'state_lock' undeclared (first use in this function); did you mean 'task_lock'?" kernel test robot

The problematic code snippet is:

spin_lock(&state_lock);
if (!unhash_delegation_locked(dp, SC_STATUS_ADMIN_REVOKED))
    dp = NULL;
spin_unlock(&state_lock);

Last week's summary revealed that Jeff Layton had already pointed out the correct fix:

"Oh hah, just noticed the kernel test robot pointed out the above. Should be nn->deleg_lock now, no?" Jeff Layton

Chuck Lever acknowledged the mistake:

"Ja, I rebased just before sending these yesterday. Duh." Chuck Lever

Cross-Architecture and Compiler Coverage

The build failures were reported across a diverse set of configurations, demonstrating the breadth of the 0-DAY CI testing:

  1. x86_64 with GCC-14: Reported on x86_64-rhel-9.4-ltp config kernel test robot.
  2. x86_64 with Clang 20.1.8: Reported on x86_64-kexec config kernel test robot.
  3. s390 with Clang 23.0.0git: Reported on s390-defconfig, additionally flagging incompatible pointer types when the compiler attempted to resolve state_lock as task_lock kernel test robot.
  4. loongarch with Clang 19.1.7: Reported on loongarch-defconfig kernel test robot.

The s390 report was particularly verbose, noting:

"error: incompatible pointer types passing 'void (*)(struct task_struct *)' to parameter of type 'spinlock_t *' (aka 'struct spinlock *')" kernel test robot

This occurred because the compiler's suggestion to use task_lock instead of state_lock was itself invalid, as task_lock is a function for locking task structures, not a spinlock.

Evolution of the Discussion

The discussion this week was entirely automated, with no human responses recorded in the window. The kernel test robot issued four reports throughout March 27, each documenting the same fundamental bug but across different build environments. This pattern is typical of the 0-DAY CI service, which aims to provide comprehensive coverage of potential build issues.

The human conversation regarding this bug had already taken place last week, where:

  1. Jeff Layton identified the incorrect lock usage.
  2. Chuck Lever acknowledged the error as a rebase mistake.
  3. Layton provided a Reviewed-by tag for the patch despite the bug, noting it was a trivial fix and that the refactoring itself was valuable: "Nice little cleanup on its own. This could be merged ahead of the rest of the series."

Final Conclusions

The build failures reported this week are not new issues but rather automated confirmations of a bug already identified and acknowledged by the developers. The fix is straightforward—replacing state_lock with nn->deleg_lock as suggested by Layton.

This incident highlights the importance of the 0-DAY CI service in catching build errors across diverse configurations, even when human reviewers have already spotted the issue. It also underscores the risks of last-minute rebases, as acknowledged by Lever.

The patch series itself remains on track for merge, with the locking bug being a minor obstacle that has been identified and has a clear resolution path. The broader goal of the series—providing netlink commands to revoke NFSv4 state during unmount operations—remains supported by the community, pending the integration of these commands into userspace tools like exportfs.

"This all looks good to me. A couple of minor nits, but nothing that looks wrong." Jeff Layton
