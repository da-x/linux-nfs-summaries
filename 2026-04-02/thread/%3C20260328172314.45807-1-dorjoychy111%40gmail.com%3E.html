OPENAT2_REGULAR flag support for openat2 (v6)

Summary

This thread discusses Patch v6 of a series introducing the OPENAT2_REGULAR flag for the openat2() system call. This is a new UAPI feature designed to enhance security by allowing applications to explicitly request opening only regular files, thereby avoiding accidental operations on device nodes or other special file types.

Feature Overview and NFS Relevance

The patch series implements support for OPENAT2_REGULAR across the VFS layer and several filesystems, including NFS, Ceph, GFS2, and SMB. The flag ensures that if a non-regular file is encountered, the open operation fails with -EFTYPE.

In the cover letter for Patch v6 0/4, author Dorjoy Chowdhury highlighted that the implementation was tested on multiple filesystems, specifically noting:

"The following filesystems have been tested... NFS (loopback)... I have tested with OPENAT2_REGULAR that regular files can be successfully opened and non-regular files (directory, fifo etc) return -EFTYPE."

Key changes in v6 included stripping OPENAT2_REGULAR from file->f_flags in do_dentry_open to prevent leakage via fcntl(fd, F_GETFL) and updating BUILD_BUG_ON checks to use VALID_OPENAT2_FLAGS.

Review and Technical Discussion

Jeff Layton reviewed the core implementation patch PATCH v6 1/4, raising two technical concerns:

  1. Ceph Symlink Handling: Layton questioned whether the Ceph filesystem's atomic open path correctly handled symlinks when OPENAT2_REGULAR was set, noting that the code might not trigger a retry via finish_no_open in all cases.
  2. GFS2 Flag Masking: He asked if OPENAT2_REGULAR was being masked off from file->f_flags before it was checked in gfs2_atomic_open, potentially leading to incorrect behavior.

Dorjoy Chowdhury responded on March 30, clarifying that:

"The d_is_symlink() case seems to be calling finish_no_open so shouldn't this be okay?"

Regarding the GFS2 flag check, Dorjoy explained:

"Yes, I thought the masking off was happening after this codepath got executed... Maybe it's better anyway to pass another flags param to this function..."

Conclusion

Jeff Layton reviewed the clarifications and acknowledged the correctness of the implementation. On April 1, he stated:

"My mistake -- you're correct. I keep forgetting that finish_no_open() will handle this case regardless of what else happens."

And regarding the flag masking:

"Also my mistake. That happens in do_dentry_open() which happens in finish_open(), so you should be OK here."

Layton subsequently provided a Reviewed-by tag for the patch on April 1. The NFS client implementation, which includes checks in fs/nfs/dir.c, was part of the accepted patch set, benefiting from the general VFS-level validation and filesystem-specific atomic open updates.
