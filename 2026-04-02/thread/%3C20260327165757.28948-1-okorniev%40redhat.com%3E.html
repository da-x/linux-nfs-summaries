NFSv4.2 COPY timestamp fix and GETATTR compound discussion

Summary

NFSv4.2 COPY Operation Fails to Update Client-Side Timestamps with Delegations

Overview

This thread is a bug fix targeting the Linux NFS client's handling of attribute updates after an NFSv4.2 COPY operation when delegated timestamps are in play. Olga Kornievskaia submitted a patch on March 27 that addresses a subtle but impactful issue: after performing a cp via the NFSv4.2 server-side COPY mechanism, the client's cached change time (ctime) and modification time (mtime) remain stale — identical to their pre-copy values.

"A similar to generic/407 test can be done with a COPY operation instead of CLONE (reflink). And it leads to same problem that ctime and mtime saved before doing a 'cp' operation are the same as after." — Olga Kornievskaia

Technical Background

The issue mirrors a previously fixed problem with the CLONE (reflink) operation, which was addressed in relation to xfstest generic/407. The NFSv4.2 COPY operation — used by userspace tools like cp when server-side copy is available — similarly fails to refresh the client's attribute cache for the destination file. This means that any application or subsequent filesystem operation relying on up-to-date timestamps may behave incorrectly, as the client believes the file has not changed.

The patch modifies fs/nfs/nfs42proc.c, adding 6 lines to ensure proper attribute invalidation/update after a COPY completes.

Discussion and Alternative Approaches

In a follow-up message sent just ten minutes later, Kornievskaia herself raised an important architectural question about the preferred fix strategy:

"Currently the COPY compound does not add a GETATTR after the COPY. Jeff's solution to REMOVEXATTR not updating ctime was to add GETATTR to the compound and then call update attributes. This could be the alternative solution here instead. I'm not sure such an approach would be preferred. But then there is a question of whether or not the server does update its attributes on COPY." — Olga Kornievskaia

This highlights two key technical considerations:

  1. Compound structure: The current NFSv4.2 COPY compound request does not include a trailing GETATTR operation to fetch fresh attributes from the server. A more robust fix might involve appending GETATTR to the compound, following the pattern established by Jeff Layton's earlier fix for REMOVEXATTR.

  2. Server behavior: It remains an open question whether NFS servers reliably update their own attribute timestamps on a COPY operation, which would affect whether a client-side workaround or a protocol-level change is more appropriate.

Classification and Significance

This is a bug fix in the NFSv4.2 client code path. While small in scope (6 lines added), it addresses correctness of filesystem semantics — specifically timestamp consistency — which has downstream implications for backup tools, build systems, and any application relying on ctime/mtime accuracy.

The thread is still open as of this week's cutoff, with no external review or acknowledgment received yet. Kornievskaia's self-review raises valid questions about the optimal implementation strategy that may warrant further discussion from maintainers such as Trond Myklebust or Jeff Layton.

Conclusion

This patch continues a pattern of NFS client improvements led by Olga Kornievskaia, addressing edge cases where delegated state interferes with proper attribute cache coherence. The fix ensures that server-side COPY operations correctly invalidate the client's timestamp cache, maintaining filesystem semantic correctness. The open question about whether to use a compound GETATTR approach — as was done for REMOVEXATTR — suggests this discussion may evolve in coming weeks.
