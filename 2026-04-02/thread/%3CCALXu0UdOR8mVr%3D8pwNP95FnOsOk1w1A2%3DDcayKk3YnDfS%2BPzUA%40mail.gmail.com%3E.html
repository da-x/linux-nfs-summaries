Call for Linux NFS Client Patch to Enable 4MB max_block_size Support

Summary

Follow-Up: Call for Linux NFS Client Patch to Support 4MB max_block_size

Type: Protocol/Configuration Change Discussion
Status: Data Collection / Patch Solicitation Phase

Overview

This week's activity in the thread on increasing the default NFSv4 server max_block_size to 4MB consisted of a single message from Mike Snitzer, who formally requested that Anna Schumaker post her Linux NFS client patch enabling support for block sizes greater than 1MB. This follows last week's productive exchange where multiple NFS client maintainers confirmed compatibility with larger block sizes.

Bridge to Prior Week

Last week (ending 2026-03-19), Cedric Blancher proposed increasing the default max_block_size from 1MB to 4MB. Chuck Lever called for a data-driven approach, prompting responses from several client maintainers:

  • Roland Mainz confirmed ms-nfs41-client (Windows) works with 4MB blocks and observed improved git clone throughput (8.1MB/s → 8.8MB/s).
  • Rick Macklem noted FreeBSD technically supports >1MB mounts but acknowledged limited production testing.
  • Anna Schumaker revealed the Linux NFS client required a code change for >1MB support and stated:

"The NFS client would need a code change to support >1MB sizes. I spent some time playing around with 4MB yesterday and it passed all my tests." Anna Schumaker

This Week's Activity

Mike Snitzer followed up on Anna Schumaker's testing announcement, directly requesting she share her patch publicly:

"Is this something you'd be open to posting to the list?" Mike Snitzer

Snitzer also expressed interest in concrete performance benchmarking, specifically referencing a workload that Roland Mainz had previously tested:

"Would be interested to see how 'git clone' improves with it." Mike Snitzer

Significance for NFS Client Development

This message represents a critical inflection point in the discussion. Anna Schumaker's patch — which removes the Linux NFS client's historical 1MB block size limitation — is the missing piece needed to enable widespread adoption of larger max_block_size defaults on the server side. Without client-side support, increasing the server default would have limited practical benefit for the most common deployment scenario (Linux-to-Linux NFS).

Snitzer's request underscores the community's appetite for empirical performance data. The specific mention of git clone as a benchmark workload is notable, as it represents a real-world operation involving many small reads that could potentially benefit from larger transfer sizes when reading packed objects or bundles.

Conclusions and Next Steps

  • No patch has been posted yet. Anna Schumaker's Linux NFS client changes remain unpublished at the time of this summary.
  • The path forward is clear: Once Anna posts her patch, the community can conduct broader testing and gather the performance data Chuck Lever originally requested.
  • Cross-platform compatibility appears viable: With positive reports from Linux, Windows (ms-nfs41-client), and FreeBSD clients, interoperability concerns have been largely addressed.

The ball is now in Anna Schumaker's court to share her patch, after which comprehensive benchmarking and review can proceed toward a potential default configuration change in the NFSD subsystem.
