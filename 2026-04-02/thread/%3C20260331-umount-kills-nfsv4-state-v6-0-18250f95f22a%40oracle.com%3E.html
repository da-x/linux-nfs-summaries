NFSD: Submission of v6 Automatic NFSv4 State Revocation Series

Summary

This week, Chuck Lever submitted version 6 of his series "Automatic NFSv4 state revocation on filesystem unmount" PATCH v6 0/5. This series addresses a long-standing operational pain point: when an NFS server exports a filesystem and clients hold NFSv4 state (opens, locks, delegations), unmounting the underlying filesystem fails with EBUSY.

The series introduces three new generic netlink commands to allow userspace tools (such as exportfs) to explicitly revoke NFSv4 client state before unmounting. This is a feature addition and protocol extension for NFSD administration, rather than a bug fix in existing behavior, though it resolves the operational "bug" of stuck mounts.

Key Technical Arguments and Evolution

Context from Prior Weeks

In the previous week, Jeff Layton reviewed version 5 of this series. He provided Reviewed-by tags but identified a locking regression in Patch 1/7 where state_lock should have been nn->deleg_lock due to a last-minute rebase. Layton also engaged in a technical discussion regarding tracepoint argument efficiency for the NFSD_CMD_UNLOCK_IP command. Lever acknowledged the locking fix and explained that tracepoint macro constraints dictated the argument structure.

Changes in v6

The submission of v6 this week reflects several significant changes from v5, as detailed in the cover letter PATCH v6 0/5:

  1. Locking Fix: The series now correctly uses nn->deleg_lock, addressing the regression noted by Layton and the kernel test robot in v5.

    "Changes since v5: Rename state_lock => nn->deleg_lock" Chuck Lever

  2. Refined Command Structure: The single NFSD_CMD_UNLOCK command from earlier versions has been split into three distinct commands with specific scopes:

    • NFSD_CMD_UNLOCK_IP: Releases NLM locks held by a specific client IP address (netlink equivalent of /proc/fs/nfsd/unlock_ip).
    • NFSD_CMD_UNLOCK_FILESYSTEM: Revokes all NFS state on a superblock (netlink equivalent of /proc/fs/nfsd/unlock_fs).
    • NFSD_CMD_UNLOCK_EXPORT: Revokes NFSv4 state acquired through exports of a specific path, regardless of client.

  3. Simplified UNLOCK_EXPORT Design: A key architectural decision in v6 is that UNLOCK_EXPORT takes only a path, not a client identifier. This avoids the complexity of auth_domain naming (e.g., use_ipaddr vs hostname-based domains).

    "The path-only design for UNLOCK_EXPORT avoids the auth_domain naming complexity... by not requiring the caller to identify a specific client." Chuck Lever

Patch Breakdown

  • PATCH 1/5: Extracts revoke_one_stid() utility function. This refactoring prepares the codebase for export-scoped state revocation by isolating per-stateid revocation logic. Jeff Layton previously noted, "Nice little cleanup on its own."
  • PATCH 2/5: Adds NFSD_CMD_UNLOCK_IP. It accepts a binary sockaddr_in or sockaddr_in6 and releases matching NLM locks. The tracepoint was updated to use %pISpc for structured output.
  • PATCH 3/5: Adds NFSD_CMD_UNLOCK_FILESYSTEM. It resolves a filesystem path to its superblock and revokes all associated NFSv4 state, including async copies and NLM locks.
  • PATCH 4/5: Replaces idr_for_each_entry_ul with a while loop over idr_get_next_ul in find_one_sb_stid() for consistency.
  • PATCH 5/5: Tracks svc_export in nfs4_stid. This allows state revocation to be scoped to a specific export, avoiding the need to walk inode dentry aliases at revocation time.

Final Conclusions

The v6 series represents a mature implementation of automatic NFSv4 state revocation on unmount. By splitting the unlock functionality into IP, filesystem, and export scopes, Lever provides granular control for userspace administrators. The removal of client-specific identification from UNLOCK_EXPORT simplifies the interface for tools like exportfs, which can now trigger state cleanup based solely on the exported path.

As noted in the cover letter:

"UNLOCK_FILESYSTEM and UNLOCK_EXPORT serve different intents. UNLOCK_FILESYSTEM means 'unmounting /data, release everything on this superblock.' UNLOCK_EXPORT means 'no clients remain for /data/projectA, release only the state acquired through exports of that path.'" Chuck Lever

With the locking issues from v5 resolved and the design simplified, the series appears ready for integration into the mainline kernel, pending final review. The subsequent step will be the integration of these netlink commands into nfs-utils (specifically exportfs) to complete the user experience.
