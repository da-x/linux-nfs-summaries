NFSD TCP Lock Contention RFC: v2 Update — Receive Path Reworked, Client Adaptation Added

Summary

NFSD TCP Lock Contention RFC: v2 Update — Receive Path Reworked, Client Adaptation Added

Classification

Performance optimization / architectural redesign (RFC patch series under active revision). This thread concerns a seven-patch RFC series originally submitted by Chuck Lever on February 5, aimed at reducing lock contention in the NFSD TCP transport layer. This week marks the first substantive follow-up after a six-week silence, with Mike Snitzer prompting an update and Chuck Lever outlining significant architectural pivots for v2.

Bridge from Prior Weeks

The thread originated on February 5, 2026, when Chuck Lever submitted a seven-patch RFC series titled "sunrpc: Reduce lock contention for NFSD TCP sockets." The series was a direct response to an investigation into knfsd's read IOPS ceiling (approximately 300–400K IOPS regardless of hardware). Key proposals included dedicated TCP receiver threads per connection, flat combining for socket sends, page recycling, and explicit TCP buffer sizing.

On February 6, Chuck reported that Tejun Heo had rejected Patch 1/7 (the workqueue affinity scope fallback), but he had developed an alternative kthread-based solution for svcrdma to avoid workqueue pool spin lock contention. See prior summary for details.

No further activity occurred until this week.

This Week's Activity

On March 30, Mike Snitzer reached out to Chuck, breaking the six-week silence:

"Curious to know your thinking on this patchset? Can you post v2 given your note about having adapted based on Tejun's feedback here?"

Chuck Lever responded shortly after with a significant update on the direction of v2, revealing several important architectural changes:

1. Workqueue Patch Repurposed for NFS Client

Chuck clarified that the workqueue-related patch (originally Patch 1/7) is no longer relevant to the server side:

"The workqueue-related patch is not important for the server, it turns out, but I've adapted it for use on the client."

This is a notable shift — what began as a server-side scalability optimization has spawned an NFS client adaptation. The original patch targeted workqueue pool spin lock contention on single-LLC systems; its repurposing for the client suggests similar lock contention patterns exist in the NFS client's RPC transport layer under high-throughput workloads.

2. Receive Path Reworked: Away from Per-Connection Kthreads

The most significant architectural change concerns the receive path. The original RFC proposed a dedicated kthread per TCP connection to handle all sock_recvmsg() calls, eliminating socket lock contention among nfsd worker threads. However, this approach faced resistance:

"One reviewer balked at the idea of starting a kthread per connection on the server."

Chuck has since reworked the receive path to use ->read_sock instead of ->recvmsg:

"I've reworked the receive side to use ->read_sock instead of ->recvmsg."

The ->read_sock interface is a lighter-weight socket read mechanism used in other parts of the kernel (e.g., TCP splice, RDMA). This change likely eliminates or reduces the need for per-connection kthreads while still achieving the goal of decoupling socket reads from worker thread contention — a more palatable design for reviewers concerned about thread proliferation under heavy connection loads.

3. Send Path: Flat Combining Retained, xpt_mutex Replaced

The transmit-side flat combining optimization remains intact and has been further refined:

"The flat combining changes on the send side are still good."

Chuck added a key improvement to the send path:

"One further optimization was to replace xpt_mutex with an llist queuing mechanism."

This is a significant advancement. The original RFC used flat combining with xpt_mutex — one thread acquires the mutex and processes all pending sends on behalf of waiters. The v2 approach goes further by eliminating xpt_mutex entirely in favor of a lock-free llist (lock-less linked list) queuing mechanism. This removes the mutex as a contention point altogether, representing a more aggressive concurrency optimization than the original RFC proposed.

4. Additional Improvements Pipeline

Chuck indicated that the v2 series is part of a broader effort:

"A number of other improvements are in the pipeline ahead of or behind these two."

This suggests additional patches (not yet disclosed) will accompany the revised TCP lock contention series, either as prerequisites or follow-on optimizations.

Technical Significance

This week's exchange reveals three important developments for NFS development:

  1. NFS Client Impact: The repurposing of the workqueue patch for the client side indicates that similar lock contention problems exist in the NFS client stack, expanding the scope of this effort beyond NFSD alone.

  2. Receive Path Simplification: Moving from per-connection kthreads to ->read_sock represents a more conservative and likely more maintainable design. It addresses reviewer concerns about thread proliferation while still targeting the core contention problem.

  3. Send Path Aggression: Replacing xpt_mutex with an llist queuing mechanism is a more radical change than the original flat combining approach, potentially offering greater scalability gains by eliminating the mutex entirely from the critical path.

Conclusion

This week marked the first meaningful follow-up to Chuck Lever's NFSD TCP lock contention RFC after a six-week period of silence. Mike Snitzer's prompt elicited a detailed status update revealing that v2 will feature a substantially reworked receive path (using ->read_sock instead of per-connection kthreads), an enhanced send path (replacing xpt_mutex with llist queuing), and a new client-side adaptation of the workqueue optimization. A formal v2 posting has not yet appeared, but Chuck's remarks suggest it is in preparation.
