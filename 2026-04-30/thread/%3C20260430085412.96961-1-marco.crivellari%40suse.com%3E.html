xprtrdma: Move long delayed work to system_dfl_long_wq for better scheduler placement

Summary

This week, Marco Crivellari (SUSE) proposed an RFC patch for the NFS/RDMA transport layer (xprtrdma) to improve how long-running delayed work items are scheduled. The change swaps the use of system_long_wq for the newer system_dfl_long_wq, aiming to leverage scheduler task placement optimizations rather than relying on per-CPU workqueues with random timer firing locations.

Technical Context and Proposal

The patch addresses a subtle inefficiency in how xprtrdma enqueues long delayed work. Currently, the code uses queue_delayed_work() with system_long_wq. As Marco Crivellari explained in his initial post here, this mechanism results in the work being queued on whichever CPU happens to fire the global timer:

"The consequence of all of this is that the work can run anywhere, depending on where the timer fired."

Crivellari noted that a new unbound workqueue, system_dfl_long_wq, was recently added specifically for long-running works to benefit from better scheduler decisions. His patch simply swaps the workqueue identifier in net/sunrpc/xprtrdma/transport.c.

Discussion Evolution: Clarifying Motivation

Chuck Lever (Oracle), a key maintainer of the NFS client stack, initially found the commit message confusing. He pointed out that "running anywhere" could be interpreted as a feature rather than a bug, and asked for clearer motivation regarding housekeeping CPUs or isolated systems here:

"Without a sentence saying 'and that anywhere includes isolated CPUs, which we don't want,' the reader is left to fill in the gap."

Frederic Weisbecker (SUSE Labs), who has deep expertise in workqueues and timers, clarified that the issue wasn't about isolated CPUs per se, but about scheduler efficiency. He explained that global timers do not fire on isolated CPUs, so the current code already respects isolation masks. However, the placement of the work item is suboptimal because it's bound to a random CPU rather than being allowed to migrate for performance and power benefits here:

"The consequence of all of this is that the work can run on any housekeeping CPU, irrespective of the scheduler that knows better about the best task placement, which would apply if the work were to be queued on an unbound workqueue."

Chuck Lever pressed for clarity on whether this was a bug fix or an optimization here:

"Does the patch address a bug (work isn't getting rescheduled at all) or is it merely a minor optimization for certain platforms? What's the user-visible issue that will be improved with this change?"

Final Conclusions

Frederic Weisbecker confirmed that this is not a bug fix, but rather an optimization for power and performance, aligning with broader kernel efforts to remove system_long_wq in favor of unbound workqueues where locality isn't required here:

"It's not a bug, it's an optimization power-wise and performance-wise... Long works have no reason to stick to a single CPU. If they are converted to be unbound, the scheduler can move them to relevant targets to optimize performances and power consumption."

He also highlighted a logical inconsistency in the current approach:

"Using queue_delayed_work() with a bound workqueue doesn't make any sense since the target is completely random."

Chuck Lever acknowledged this explanation, stating he had no technical objections to the code change but emphasized that the commit message should clearly reflect this rationale here:

"The light dawns (for me). That's what I'd like to see in the commit message."

Summary for NFS Client Development

This discussion highlights a shift in kernel workqueue best practices, impacting NFS client subsystems like xprtrdma. Developers should be aware that:

  1. system_long_wq is being phased out for cases where CPU locality is not critical.
  2. system_dfl_long_wq is the preferred workqueue for long-running tasks to allow the scheduler to optimize placement for power and performance.
  3. Commit messages must clearly distinguish between bug fixes (functional correctness) and optimizations (performance/power), especially when the behavioral change is subtle.

The patch itself is a minor one-line change in transport.c, but it represents an important alignment with modern kernel scheduling infrastructure.
