sunrpc pool_mode: Staged deprecation strategy and hardware edge cases

Summary

This week's discussion continued the RFC debate over simplifying the SunRPC server-side thread pool configuration by hardcoding pool_mode to pernode and removing legacy modes (auto, global, percpu). The conversation shifted from the initial patch proposal (last week) to a concrete agreement on a staged deprecation strategy, while also surfacing important hardware-specific edge cases for ARM64 and CXL platforms.

Discussion Overview

The thread, initiated by Jeff Layton's RFC last week, aimed to eliminate 202 lines of legacy pool mode selection code. This week, Jeff and Chuck Lever refined the transition plan, addressing backward compatibility concerns and identifying a potential bug in the pernode path on specialized hardware.

Key Technical Arguments

Agreement on Staged Deprecation

Jeff Layton responded to Chuck Lever's previous feedback by proposing a more gradual approach:

"If we want to 'go slow' on this, then what I'd probably suggest is that we just change the default to 'pernode' initially."

Layton argued that this would be safe because:

"Single node boxes that have this set to global today should see no real change (functionally identical). Boxes with multiple NUMA nodes that don't set it now, will start using pernode mode, but that's probably a good thing in most cases."

He also clarified the relationship between auto and pernode:

"'pernode' is functionally identical to 'global' when there is only a single NUMA node"

"'percpu' mode is basically useless"

Deprecation Warnings vs. Module Load Failures

A key point of contention was how to handle legacy configurations during the deprecation period. Layton suggested:

"We probably do still want to warn in that case. Once we remove the option, the module load can fail, so we probably want to discourage people from keeping the setting."

However, Chuck Lever pushed back on the idea of making module loading fail for deprecated settings:

"I'm saying that setting a deprecated pool mode should not cause module loading to fail at all. Failing to load will be more painful than loading and having different thread affinity behavior."

This distinction is critical for production systems where NFS server availability is paramount. Lever's position aligns with the kernel's historical approach to obsoleted tuning knobs: accept-and-ignore with warnings, rather than hard-fail.

Hardware-Specific Bug: Memoryless/CPU-less NUMA Nodes

Chuck Lever raised an important technical concern regarding the pernode implementation on specialized hardware:

"The existing pernode path assumes every online node has both CPUs and some memory. nr_online_nodes on some platforms (e.g., certain ARM64, CXL) counts memoryless or CPU-less nodes; for_each_node_with_cpus() vs. for_each_online_node() matters here."

This identifies a potential bug in the current svc_pool_map_init_pernode() function, which may incorrectly allocate pools for NUMA nodes that lack CPUs or memory. Layton acknowledged this:

"Good point. We should probably change that too."

Tracking Long-Term Deprecation

Layton expressed concern about ensuring the deprecation process is completed:

"I'm terrible about following up with the later phases of long term deprecation though. Suggestions on how to make sure we don't drop the ball on finishing the change?"

This highlights a common challenge in kernel development: multi-cycle deprecations risk being abandoned if not properly tracked.

Evolution of the Discussion

The discussion evolved from last week's radical single-step removal proposal to this week's consensus on a multi-phase approach:

  1. Phase 1 (immediate): Change the default pool_mode to pernode while accepting legacy values with deprecation warnings.
  2. Phase 2 (future cycles): Remove support for global and percpu modes entirely.
  3. Parallel fix: Correct the pernode path to use for_each_node_with_cpus() instead of for_each_online_node() on platforms with memoryless or CPU-less NUMA nodes.

Final Conclusions

This week's discussion resulted in several concrete agreements:

  • Staged deprecation: The community agreed to change the default to pernode initially, rather than immediately removing other modes.
  • No module load failures: Deprecated pool modes should be accepted (with warnings) rather than causing module load failures.
  • Hardware fix needed: The pernode path requires correction for ARM64/CXL platforms with memoryless or CPU-less NUMA nodes.
  • Direction confirmed: Both developers agree that pernode is the correct long-term default, as it provides proper NUMA-local thread affinity on multi-node systems while degenerating gracefully to a single pool on single-node systems.

Classification

This discussion concerns NFS server infrastructure cleanup with elements of bug fix identification. The primary goal is technical debt reduction in the sunrpc subsystem, but the conversation also surfaced a hardware-specific bug in the pernode implementation that needs addressing. While this affects NFS server (nfsd) performance and scalability on modern multi-NUMA systems, it does not directly impact NFS client development. However, the stability of the NFS server infrastructure is critical for overall NFS ecosystem reliability.
