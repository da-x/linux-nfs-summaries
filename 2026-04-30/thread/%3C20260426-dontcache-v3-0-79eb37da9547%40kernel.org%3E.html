mm: Improve RWF_DONTCACHE write performance via background flusher kick

Summary

mm: Improve RWF_DONTCACHE Write Performance with Background Flushers

This week, Jeff Layton posted v3 of a patch series titled "[PATCH v3 0/4] mm: improve write performance with RWF_DONTCACHE" cover letter. The series aims to address high latency and poor throughput associated with RWF_DONTCACHE writes, particularly in NFS server (NFSD) workloads.

Technical Context: New Feature / Performance Optimization

The discussion centers on optimizing the IOCB_DONTCACHE writeback path. Previously, generic_write_sync() called filemap_flush_range() inline for every DONTCACHE write, submitting I/O in the writer's context. This caused significant latency spikes (p99.9 latency inflated from 23ms to 93ms) due to the work of walking page trees and submitting I/O blocking the writer.

The v3 series implements a scheme suggested by Jan Kara and Christoph Hellwig: instead of inline writeback, the writer kicks the background flusher thread to perform writeback proportional to the amount written.

Key Patches

  1. PATCH 1/4: Adds NR_DONTCACHE_DIRTY, a per-node page counter tracking dirty pages with the dropbehind flag (dirtied via RWF_DONTCACHE). This allows the VM to track DONTCACHE-specific dirty pressure.
  2. PATCH 2/4: Replaces inline filemap_flush_range() with a flusher kick (WB_start_dontcache). The flusher drains dirty pages in the background, targeting an amount proportional to the DONTCACHE writes. This moves writeback submission off the hot path.
  3. PATCH 3/4 & 4/4: Adds two benchmark suites (nfsd-io-bench and dontcache-bench) to demonstrate performance improvements. Layton noted these were largely AI-generated ("AI slop") and may not be suitable for long-term inclusion in the tree.

Performance Results

Layton provided extensive benchmarks showing significant improvements, especially for NFS:

  • Local XFS (NVMe): Multi-writer DONTCACHE throughput improved by +27.2%, matching buffered I/O performance. p99.9 latency dropped by ~73%.
  • NFSv3 (NFSD): Improvements were even more dramatic. Multi-writer DONTCACHE throughput improved by +398.3% (nearly 5x), effectively matching buffered I/O levels. Single-client sequential p99.9 latency dropped by 76.9%.

"The NFS results show even larger improvements than the local benchmarks. Multi-writer dontcache throughput improves nearly 5x, matching buffered I/O." — Jeff Layton

Discussion and Review

Andrew Morton's Concerns

Andrew Morton questioned whether deferring writeback could lead to a buildup of dirty, unreclaimable pagecache. Layton clarified that while pagecache remains dirty until the flusher acts, traditional VM limits (balance_dirty_pages()) will eventually throttle writers if the flusher cannot keep up. He noted:

"In the test runs I did, the peak pagecache with DONTCACHE writes was higher than with the unpatched version but still considerably less than with normal buffered I/O." — Jeff Layton

Morton also raised concerns about the maintainability of the AI-generated benchmark scripts, comparing it to "shipping the .s file without giving us the .c file." Layton agreed the benchmarks might be excluded from the final merge, serving only as demonstration tools.

Matthew Wilcox and Ritesh Harjani: Noisy Neighbor Tests

Matthew Wilcox pointed out that the "noisy neighbor" benchmark (DONTCACHE writer + buffered readers) showed a 45.9% drop in reader throughput. He suggested this wasn't a true "noisy neighbor" test, which should involve competing writers.

"hm. This wasn't what I thought of when I thought of 'noisy neighbour'. I'd have process A doing DONTCACHE writes to file A and process B doing normal buffered writes to file B." — Matthew Wilcox

Ritesh Harjani echoed this, asking for tests involving parallel buffered and DONTCACHE writers to ensure the new mechanism doesn't regress performance in mixed-workload scenarios. He also questioned why DONTCACHE didn't show significant benefits over buffered I/O in single-client local tests, suggesting it shines more when page cache pressure is high (file size > RAM).

Layton acknowledged these points, agreeing to recreate benchmarks that mirror Jens Axboe's original DONTCACHE use cases and test mixed writer scenarios.

Jan Kara: Per-BDI vs. Per-Node Counters

Jan Kara raised a technical concern regarding the NR_DONTCACHE_DIRTY counter being per-node rather than per-BDI (backing device info). He argued that splitting node-level stats among cgroups could underestimate writeback needs if DONTCACHE and normal writes come from different cgroups.

"So I think the stat should be a per bdi_writeback one (instead of a per node one) which would avoid the need to split the value to wb here." — Jan Kara

Syzbot Report

Syzbot reported a WARNING in __mod_memcg_lruvec_state ("missing stat item 21") when testing the series. This indicates a potential issue with how the new NR_DONTCACHE_DIRTY counter interacts with memory cgroup LRU statistics, requiring further investigation by Layton.

Conclusion

The v3 series demonstrates significant performance gains for RWF_DONTCACHE, particularly in NFS multi-writer scenarios, by moving writeback submission to background flushers. However, reviewers have identified several areas needing attention:

  1. Counter Granularity: Jan Kara suggests moving the DONTCACHE dirty counter from per-node to per-BDI.
  2. Mixed Workloads: Ritesh Harjani and Matthew Wilcox request more rigorous testing of mixed buffered/DONTCACHE writer scenarios.
  3. Syzbot Warning: A memory cgroup stat warning needs resolution.
  4. Benchmark Maintenance: The AI-generated benchmarks are likely to be dropped from the tree.

Layton agreed to address these points, including recreating specific benchmarks and refining the counter implementation before LSF/MM.
