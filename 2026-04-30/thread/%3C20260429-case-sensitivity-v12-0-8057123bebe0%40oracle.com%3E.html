Exposing case folding behavior: v12 submission with NFS client re-probe fixes

Overview

Chuck Lever submitted version 12 of his 15-patch series "Exposing case folding behavior" on April 29, 2026. This is a continuation of a long-running effort (now in its twelfth iteration) to enable file services such as NFSD and ksmbd to report the actual case-folding semantics of local filesystems to clients. The series addresses interoperability gaps with Windows and macOS NFS clients, which expect case-insensitive behavior that differs from traditional POSIX semantics.

As Chuck Lever explained in the cover letter [20260429-case-sensitivity-v12-0-8057123bebe0@oracle.com]:

"The Linux NFS community has a growing interest in supporting NFS clients on Windows and MacOS platforms, where file name behavior does not align with traditional POSIX semantics."

He emphasized that one Windows-based NFS client "explicitly requires servers to report FATTR4_WORD0_CASE_INSENSITIVE = TRUE for proper operation, a hard requirement for Windows client interoperability because Windows applications expect case-insensitive behavior."

Classification

This thread is about a new feature (VFS infrastructure to expose filesystem case-folding attributes) with significant implications for NFS client and server development. It also includes important bug fixes related to stale capability retention in the NFS client during re-probe and transparent state migration.

Evolution from v11

Last week's summary covered version 11, which saw discussions around ext4/f2fs flag propagation, ISO9660 per-file vs. per-directory attribute reporting, and XFS chattr round-trip inconsistencies. Version 12 addresses those concerns and incorporates additional refinements. Key changes since v11 include:

  • isofs: Wires .fileattr_get only on directory inodes, since NFSD and ksmbd query casefolding on directories (per Jan Kara's feedback).
  • xfs, hfsplus: Drops the FS_CASEFOLD_FL fileattr_get mask; instead admits the bit through fileattr_set's allowlist to fix the chattr round-trip issue raised by Darrick J. Wong.
  • cifs: Wires .fileattr_get on cifs_namespace_inode_operations so DFS referral/automount directories report case handling.
  • nfs: Clears NFS_CAP_CASE_INSENSITIVE and NFS_CAP_CASE_NONPRESERVING before re-OR'ing in the v3 and v4 probe paths, ensuring that re-probe or transparent state migration (TSM) does not retain stale capabilities.
  • nfsd: Switches nfsd_get_case_info() to errno return so v3 PATHCONF and v4 GETATTR can apply version-appropriate policy on failure; uses dget_parent() in v4 case-attr probe to keep the parent dentry referenced across the query.

NFS Client Development Highlights

The NFS client patch [20260429-case-sensitivity-v12-10-8057123bebe0@oracle.com] is particularly significant for re-export scenarios. When an NFS mount point is served by NFSD, the server needs to report the case sensitivity behavior of the underlying filesystem to its clients. The patch implements fileattr_get in the NFS client to surface what it learned from its own server during mount via PATHCONF (NFSv3) or FATTR4_CASE_INSENSITIVE/FATTR4_CASE_PRESERVING attributes (NFSv4).

A critical bug fix in this iteration addresses stale capability retention. As Chuck Lever described:

"Both capability bits are cleared at the start of each successful probe so a remount or NFSv4 transparent state migration to a server with different case semantics does not retain stale capabilities from the prior probe."

This ensures that if an NFS client migrates to a new server (via TSM) or is remounted, it correctly reflects the new server's case-handling semantics rather than carrying over outdated flags. Additionally, PATHCONF is now invoked unconditionally for NFSv2 and NFSv3 mounts, even when the user pins server->namelen with the namlen= mount option, ensuring case-sensitivity capabilities are always established.

Discussion: exFAT Case Sensitivity Nuances

The only reply this week came from David Timber [3d3d6e22-b8a7-4f32-8046-697e45ec6c04@dev.snart.me], who challenged the assertion in the exFAT patch that exFAT is "always" case-insensitive. He noted:

"Not necessarily 'always'. The specs (SD spec part 2 and MS spec) leave it up to the formatter implementation on how the volume should behave."

Timber pointed out that exFAT uses an up-case table for comparison, and major implementations including Linux and Windows honor whatever table is present. He suggested:

"At the end of the day, it wouldn't matter much because no sane formatter would produce a volume with some weird version up-case table. But if that attribute plays an important role in some system that has some level of impact, I suggest considering another attribute, say 'unknown' or 'it depends'."

He also noted that NTFS has a similar up-case table feature, though it is usually unused.

Conclusion

Version 12 of this series refines the VFS infrastructure for exposing case-folding behavior across numerous filesystems (FAT, exFAT, NTFS3, HFS, HFS+, XFS, CIFS, vboxsf, ISO9660) and network file services (NFSD, ksmbd). For NFS client development, the most notable advancement is the implementation of fileattr_get to support re-export scenarios, coupled with a critical fix that prevents stale case-sensitivity capabilities from persisting across remounts or transparent state migrations. The series continues its march toward enabling seamless interoperability between Linux NFS servers and non-POSIX clients on Windows and macOS platforms.
