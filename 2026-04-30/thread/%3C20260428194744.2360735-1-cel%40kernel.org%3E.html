lockd: Fix TEST Lock Handling for Read-Only File Descriptors

Summary

This week, Chuck Lever submitted v3 of a bug-fix patch on behalf of Neil Brown to correct a long-standing but recently exposed defect in the NFS lock daemon (lockd) concerning how TEST lock requests are handled when only read-only access is available to a file. The fix addresses a regression triggered by a recent change in NFSD permission checking, and resolves practical problems for users running virtual machines via QEMU with read-only filesystem images over NFS.

Classification

This is a bug fix targeting the NFS server-side lock daemon (lockd), with direct implications for NFS client workloads that perform lock queries on read-only file descriptors.

Background: The Exposed Regression

The patch's cover letter explains that lockd has historically treated F_GETLK (lock test/query) requests similarly to F_SETLK (lock set) requests — requiring write access to query an F_WRLCK lock and read access to query an F_RDLCK lock. However, POSIX semantics allow F_GETLK to operate with either read or write access:

"The F_GETLK fcntl can work with either read access or write access or both. It can query F_RDLCK and F_WRLCK locks in either case." Neil Brown

This incorrect behavior had been hidden for years because the NFS server (nfsd) previously ignored the access mode requested by lockd and required only READ access for all locking operations. The bug was exposed by a recent commit:

"The commit mentioned in Fixes: below changed nfsd_permission() to NOT override the access request for LOCK requests and this exposed the bug that we are now fixing." Neil Brown

The offending commit, 4cc9b9f2bf4d ("nfsd: refine and rename NFSD_MAY_LOCK"), was part of the broader NFSD infrastructure cleanup discussed in related threads this week.

Practical Impact

The real-world consequence is that applications like QEMU, which access read-only filesystem images (e.g., ISO files) over NFS and query lock status, would fail when attempting to test for write locks:

"This is wrong and can cause problems - e.g. when qemu accesses a read-only (e.g. iso) filesystem image over NFS (though why it queries if it can get a write lock - I don't know. But it does, and this works with local filesystems)." Neil Brown

The issue was reported via Debian bug #1128861 by user Tj.

Technical Approach

The patch modifies five files in fs/lockd/ to decouple the access mode used for TEST requests from the lock type being queried:

  1. nlm_do_fopen() now accepts O_RDWR as a mode, succeeding if either O_RDONLY or O_WRONLY can be opened.
  2. nlm_lookup_file() accepts an explicit mode argument from callers instead of deducing it based on lock type.
  3. nlm4svc_retrieve_args() and nlmsvc_retrieve_args() detect TEST requests and pass O_RDWR to nlm_lookup_file(), while preserving the previous behavior for non-TEST requests (e.g., GRANT, UNLOCK).
  4. nlmsvc_testlock() uses the file descriptor already stored in lock->fl.c.flc_file rather than recalculating the mode.

Brown notes that this incorrect behavior has existed "at least since git history began," underscoring how deeply embedded the bug was in the codebase.

Known Limitation

The patch deliberately does not address a related issue with flock(LOCK_EX) on read-only file descriptors:

"The flock(.., LOCK_EX) call is permitted on a read-only file descriptor. Linux NFS maps this to NLM locking as whole-file byte-range locks. nfsd will see this as though it were fcntl( F_SETLK (F_WRLCK)) and will now require write access, which it might not be able to get. It is not clear if this is a problem in practice, or what the best solution might be. So no attempt is made to address it." Neil Brown

This caveat leaves open the possibility of follow-up work if flock(LOCK_EX) on read-only NFS files becomes a reported issue.

Evolution and Status

This is v3 of the patch, with changes since v2 including:

  • Rebase on nfsd-testing (v7.1-rc1+)
  • Proper handling of "drop reply" scenarios

The patch carries a Reviewed-by tag from Jeff Layton, indicating peer validation. As of this week's window close, no further discussion or merge confirmation was posted to the list. The single message in this thread is Chuck Lever's submission on April 28.

Significance for NFS Client Development

For NFS client developers, this fix ensures that lock query operations (F_GETLK) behave consistently with local filesystem semantics when accessing read-only files over NFS. This is particularly relevant for:

  • Virtualization workloads: QEMU and similar hypervisors accessing disk images over NFS will no longer encounter spurious lock test failures on read-only exports.
  • Application compatibility: Any client application that queries write locks on read-only file descriptors — a pattern that works on local filesystems — will now function correctly over NFS as well.

The fix restores parity between NFS and local filesystem behavior for lock testing, closing a gap introduced by the NFSD permission refinement work.
