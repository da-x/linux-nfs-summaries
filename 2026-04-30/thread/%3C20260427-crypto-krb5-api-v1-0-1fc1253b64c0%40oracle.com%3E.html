Migrate rpcsec_gss_krb5 to the crypto/krb5 library

Summary

Migrate rpcsec_gss_krb5 to the crypto/krb5 library

Type: Major refactoring / Security improvement (Bug prevention)

Chuck Lever submitted an 18-patch series this week to migrate the NFS client's rpcsec_gss_krb5 module from its private Kerberos 5 cryptographic implementation to the common kernel crypto/krb5 library. This is a significant cleanup effort aimed at reducing the audit surface for security-critical code in the SUNRPC subsystem.

Key Technical Arguments

The primary motivation, as outlined by Chuck Lever, is that maintaining duplicate cryptographic implementations within an RPC module limits review expertise:

"Keeping cryptographic code inside an RPC module means it receives review only from the SUNRPC maintainers, who lack deep crypto expertise. Vulnerabilities and algorithmic errors can persist unnoticed."

By consolidating to a single implementation in crypto/krb5, the series achieves several goals:

  1. Reduced Audit Surface: Eliminates duplicated code for key derivation, CBC-CTS encryption, HMAC checksumming, and encrypt-then-MAC constructions (RFC 8009).
  2. Automatic Feature Propagation: New encryption types and hardware offload capabilities added to crypto/krb5 will automatically become available to SUNRPC Kerberos consumers.
  3. Code Simplification: The crypto/krb5 library handles enctype differences internally, allowing a single encrypt/decrypt function to serve all enctypes, thereby eliminating the per-enctype dispatch table previously required in struct gss_krb5_enctype.

Evolution of the Discussion

The series was posted on April 27th PATCH 00/18. The patchset is extensive, removing over 4,000 lines of code while adding roughly 570 lines, resulting in a net reduction of approximately 3,450 lines.

Key technical changes include:

  • Scatterlist Conversion: New helpers xdr_buf_to_sg() and xdr_buf_to_sg_alloc() were introduced to bridge the gap between the GSS-API layer's struct xdr_buf and the crypto/krb5 library's scatterlist interface. This avoids heap allocation for common small RPCs by using an inline stack-allocated array.
  • AEAD Migration: Wrap token encryption and decryption were switched to use AEAD (Authenticated Encryption with Associated Data) operations via crypto_krb5_encrypt() and crypto_krb5_decrypt(). This handles both MtE (RFC 3962) and EtM (RFC 8009) constructions transparently.
  • MIC Handling: MIC token generation and verification were updated to use crypto_krb5_get_mic() and crypto_krb5_verify_mic(). A specific implementation detail was noted regarding RFC 4121 Section 4.2.4, which requires MIC checksums to cover the message body followed by the GSS token header. Because crypto/krb5 hashes metadata before data, the GSS header is appended to the scatterlist rather than passed as a metadata parameter.
  • Cleanup: The series removes legacy skcipher/ahash handles, dead code from gss_krb5_keys.c, and the internal KUnit test suite for these now-removed functions (coverage is provided by crypto/krb5 selftests).

Final Conclusions

The series received positive feedback from NFS maintainer Jeff Layton, who acknowledged the scale of the cleanup:

"Love that diffstat. Nice work!"

Layton provided a Reviewed-by tag for the series Re: PATCH 00/18.

Chuck Lever confirmed that the patches were applied to his nfsd-testing tree, noting:

"Thanks, applied to nfsd-testing. An Acked-by: from one of the NFS client maintainers would be great too."

The migration represents a substantial step forward in hardening the NFS client's security infrastructure by leveraging the kernel's centralized cryptographic subsystem.
