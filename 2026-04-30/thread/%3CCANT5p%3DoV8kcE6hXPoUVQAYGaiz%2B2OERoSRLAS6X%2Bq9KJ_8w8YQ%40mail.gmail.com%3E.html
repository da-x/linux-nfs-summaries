SMB VFS Lookup Intent: MS-FSA Semantics Clarified

Overview

This thread continues a cross-filesystem discussion initiated last week regarding the "intent" of VFS lookups and how the SMB client handles open calls. The focus this week was on clarifying whether the SMB2+ protocol mandates that an open call specify whether the target is a directory or a regular file, and what happens when neither flag is set.

Type: Protocol behavior investigation (SMB-specific; no NFS impact).

Bridge to Prior Week

Last week, Shyam Prasad N raised concerns that the SMB client must retry open calls with different type flags during VFS lookup callbacks, adding overhead. Ralph Boehme suggested that omitting both FILE_DIRECTORY_FILE and FILE_NON_DIRECTORY_FILE might allow the server to open objects regardless of type. This week's discussion confirmed and clarified that behavior.

This Week's Discussion

Shyam's Initial Follow-Up

On April 24, Shyam responded to Ralph's suggestion:

"That's interesting. The spec does not seem to define this. Perhaps purposely? Will try and prototype a change to verify."

Shyam noted that the SMB2/3 protocol specification did not appear to explicitly define this behavior, prompting him to investigate further.

Tom Talpey's Clarification: MS-FSA Defines the Behavior

Tom Talpey provided the critical clarification on April 24, pointing out that this behavior is defined in MS-FSA (Microsoft File System Architecture), not in the core SMB2/3 protocol:

"This would be filesystem behavior and therefore it would be in MS-FSA, not in the SMB2/3 protocol."

Tom cited section 2.1.5.1 of MS-FSA (page 60), which specifies conditions under which an open must succeed on a directory even when neither FILE_DIRECTORY_FILE nor FILE_NON_DIRECTORY_FILE is set:

"If CreateOptions.FILE_DIRECTORY_FILE is TRUE then StreamTypeToOpen = DirectoryStream... Else if CreateOptions.FILE_NON_DIRECTORY_FILE is FALSE, StreamNameToOpen is empty, StreamTypeNameToOpen is empty, Open.File is not NULL, and Open.File.FileType is DirectoryFile then StreamTypeToOpen = DirectoryStream"

Tom also noted:

"There are a bunch of other cases involving trailing separators, etc. MS-FSA is, of course, not the only filesystem type which can be exported by SMB."

Shyam's Acknowledgment

On April 28, Shyam acknowledged Tom's input and indicated he would proceed with experiments:

"Thanks Tom. Will try some experiments with this."

Key Technical Arguments

  1. Protocol vs. Filesystem Semantics: The distinction between SMB2/3 protocol specifications and MS-FSA filesystem behavior was clarified. The open-call type-flag semantics reside in MS-FSA, not the transport-level SMB protocol.

  2. Potential Optimization for SMB Client: If omitting both type flags allows the server to open objects regardless of type (per MS-FSA), the SMB client could potentially avoid the two-step retry process during VFS lookup callbacks, reducing round-trip overhead.

  3. SMB-Specific Issue: This discussion is entirely specific to the SMB protocol and its interaction with the Linux VFS layer. NFS does not face this constraint because NFS lookups and opens follow different semantics.

Final Conclusions

  • The behavior in question is defined by MS-FSA, not the SMB2/3 protocol specification.
  • Omitting both FILE_DIRECTORY_FILE and FILE_NON_DIRECTORY_FILE may allow opens to succeed regardless of object type under certain conditions, per MS-FSA section 2.1.5.1.
  • Shyam plans to prototype a change based on these findings, which could reduce round-trips in the SMB client during path traversal operations.
  • No impact on NFS client development: This is an SMB-specific investigation with no implications for NFS semantics or implementation.

Relevance to NFS

This thread has no direct impact on NFS client development. It was discussed on the linux-nfs list as part of a broader exploration of cross-filesystem VFS behavior. The conclusion — that this issue is SMB-specific — means NFS developers can disregard this discussion for their own work. No bug fixes, protocol changes, or new features for NFS are involved.
