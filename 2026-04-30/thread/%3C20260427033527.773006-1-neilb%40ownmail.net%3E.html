Prepare to Lift Lookup Out of Exclusive Lock: VFS/NFS Concurrency Series v2 with syzbot Bugs

Summary

NFS/VFS: Preparing to Lift Lookup Out of Exclusive Lock for Directory Operations

Overview

This week, Neil Brown submitted a 19-patch series ([PATCH v2 00/19]](https://lore.kernel.org/linux-nfs/20260427033527.773006-1-neilb@ownmail.net/)) aimed at improving concurrency of directory operations in the VFS, with significant implications for NFS client development. The series represents a condensed version of a larger 53-patch set posted in March, which received limited feedback. Brown noted:

"It is a selection of patches from the 53-patch set I posted in March which got relatively little response. Maybe a shorter set will be more approachable."

The overarching goal is to move d_alloc_parallel() and related lookup operations outside the directory's i_rwsem lock, enabling broader concurrency for directory operations. This is classified as a protocol/locking change rather than a traditional bug fix, though it addresses latent race conditions and prepares NFS for safer concurrent access patterns.

Key Technical Arguments

The Locking Problem

Brown identified two critical requirements before lookup can be moved outside the exclusive lock:

  1. d_drop() must not be used before an operation completes: The presence of a dentry in the dcache becomes part of the locking protocol. This requires d_splice_alias() to work with hashed negative dentries.

  2. d_alloc_parallel() must not be called while i_rwsem is held: Doing so would result in a lock inversion. New non-blocking allocation functions are introduced to handle these cases.

Brown explained:

"There are two particular requirements before lookup can move outside the lock: 1/ d_drop() mustn't be used before an operation completes... 2/ d_alloc_parallel() mustn't be called while i_rw_sem is held, as this would result in a lock inversion."

New VFS Infrastructure

The series introduces several new VFS mechanisms:

  • d_alloc_noblock(): A non-blocking variant of d_alloc_parallel() that returns -EWOULDBLOCK instead of waiting. This is critical for readdir-based dcache priming in NFS, SMB, FUSE, and CephFS.
  • d_duplicate(): Creates an in-lookup dentry with the same name as an existing hashed dentry, preventing race conditions during operations like silly-rename where two sub-operations occur on the same name.
  • Enhanced d_splice_alias(): Now handles hashed, unhashed, and in-lookup dentries uniformly, eliminating the need for filesystems to call d_drop() before splicing.
  • LOOKUP_SHARED flag: A temporary indicator telling ->lookup handlers whether the parent directory is locked shared or exclusively. Brown acknowledged this is "rather ugly" but noted it "will be gone soon after we move d_alloc_parallel() out of the directory lock."

NFS-Specific Changes (Patches 13–19)

The NFS client receives substantial attention in patches 13 through 19:

  • Patch 13: Removes d_drop()/d_alloc_parallel() from nfs_atomic_open(), replacing the exclusion mechanism with ->d_revalidate invalidation for negative dentries during LOOKUP_OPEN. Brown stated this is "consistent with the 'close to open' caching semantics of NFS which requires the server to be queried whenever opening a file."

  • Patch 14: Uses d_splice_alias() in nfs_link(), eliminating the need for d_drop() before instantiation.

  • Patches 15–16: Remove d_drop() calls before d_splice_alias() in nfs_add_or_obtain() and atomic_create, relying on the enhanced splice functionality.

  • Patch 17: Switches nfs_prime_dcache() to use d_alloc_noblock(), avoiding blocking during readdir when a concurrent lookup is in progress. Brown noted: "Blocking in that case is pointless as the lookup will add info to the dcache."

  • Patch 18: Uses d_alloc_noblock() in silly-rename operations, open-coding parts of lookup_slow() to verify name availability on the server.

  • Patch 19: Adopts d_duplicate() for silly-rename dentry duplication, preparing for lock-free parallel allocation.

syzbot CI Findings

The automated syzbot CI testing flagged four critical issues in the patch series:

  1. KASAN: slab-out-of-bounds Read in __d_alloc_parallel — Triggered via overlayfs readdir paths (ovl_cache_update).
  2. KASAN: slab-out-of-bounds Read in __dentry_kill — Also triggered through overlayfs readdir.
  3. KASAN: slab-use-after-free Read in __d_alloc_parallel — Use-after-free in dcache allocation during overlayfs operations.
  4. WARNING in __d_instantiate — A d_in_lookup(dentry) assertion failure in shmem whiteout handling (shmem_rename2).

These bugs were reported by syzbot at [id://69ef214a.170a0220.11de9.0018.GAE@google.com] and suggest that the new dcache manipulation patterns, particularly in overlayfs integration (patches 9–10) and shmem whiteout handling (patch 12), require further debugging. The call traces show issues originating in ovl_cache_update and shmem_mknod, indicating races between dentry allocation, lookup, and deletion paths.

Final Conclusions

As of the end of this week:

  • No final merge or resolution: The patch series remains under review with Al Viro's detailed feedback pending.
  • Critical bugs identified: syzbot's findings indicate memory safety issues in the overlayfs and shmem portions of the series, which must be addressed before the patches can proceed.
  • NFS client impact is significant but preparatory: The NFS-specific changes (patches 13–19) are designed to eliminate d_drop() usage patterns that will become unsafe once lookup moves outside the directory lock. These changes improve correctness and reduce unnecessary blocking in readdir-based dcache priming.

Brown's series represents a major architectural shift toward finer-grained locking in the VFS dcache layer. The NFS client, being one of the most complex filesystems for lookup operations due to its server-side state management and "close-to-open" caching semantics, serves as a primary beneficiary and testbed for these changes. However, the syzbot findings underscore the complexity of coordinating dentry lifecycle management across multiple filesystems (NFS, overlayfs, shmem) under the new locking model.
