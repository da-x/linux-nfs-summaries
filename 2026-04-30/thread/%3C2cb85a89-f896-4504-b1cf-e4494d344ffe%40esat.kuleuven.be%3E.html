Diagnosis of NFS4ERR_SEQ_MISORDERED errors on RHEL10 servers

Summary

NFS4ERR_SEQ_MISORDERED Errors and NFS Client Very Slow

Overview

This thread addresses a critical performance regression reported by Rik Theys, where a Rocky 8 Linux client (kernel 7.0.2) experienced extremely slow NFS operations when connecting to a RHEL10 server. The root cause was identified as a bug in the RHEL10 NFS server's handling of SEQUENCE replay, leading to NFS4ERR_SEQ_MISORDERED errors.

Key Technical Arguments and Evolution

Initial Report

Rik Theys reported that cloning git repositories was "extremely slow" despite no saturation on the server side. Network captures revealed frequent NFS4ERR_SEQ_MISORDERED (10063) responses from the server. He asked:

"What could be the cause of these mismatches? Is this always a client issue, or can this be caused by the server?"

Expert Analysis

Benjamin Coddington initially suggested the error might indicate a client-side bug or network issues such as packet duplication:

"This is something you shouldn't normally see and probably indicates a bug or serious problem... I'd also check to make sure your underlying network isn't doing something totally nuts like duplicating packets."

Rick Macklem provided a detailed explanation of the NFSv4.1/4.2 SEQUENCE operation protocol, clarifying that NFS4ERR_SEQ_MISORDERED is returned by the server when the sequence ID in a request does not match the expected value (same or +1) for a given session and slot. He noted:

"If this happens, the server is behaving correctly, afaik. Then, is this a client bug or a client feature? That is more difficult to answer... I'd say it's probably a bug if neither 'intr' nor 'soft' options are on the mount."

Root Cause Identification

Rik Theys analyzed his packet capture and observed that while slot 0 sequenced correctly, other slots repeatedly used sequence ID 0x00000001, often appearing exactly three times with the same slot ID. This pattern suggested the client was resetting its view of the slot table state.

Olga Kornievskaia identified the specific server-side bug responsible. She pointed to a patch by NeilBrown (commit 1cff14b7fc7f31363c39d0269563ce75c714f7ae) titled "nfsd: ensure SEQUENCE replay sends a valid reply."

The bug occurred because the server's replay cache logic encoded the SEQUENCE reply before filling in the correct reply fields. This resulted in an incorrect maxslots value being sent to the client, causing it to believe the slot table had shrunk and discard its knowledge of current sequence numbers for higher slots. When the client later used those slots, the server rejected them with NFS4ERR_SEQ_MISORDERED.

"The incorrect maxslots value, in particular, can cause the client to think the slot table has been reduced in size so it can discard its knowledge of current sequence number of the later slots, though the server has not discarded those slots."

Conclusion and Fix

Olga confirmed that this bug affects all slots except slot 0:

"If I recall correctly, slotid=0 was not affected but all other slots were... Then at some point when client starts using slots other then slot 0 it ends in this SEQ_MISORDERED state."

The fix is included in the RHEL10.2 release and CentOS kernels 6.12.0-201 and later. Rik Theys was advised to upgrade the server kernel or wait for the RHEL10.2 update to resolve the performance issues.

Summary of Impact

  • Issue: Server-side bug in NFSv4.1/4.2 SEQUENCE replay logic.
  • Symptom: NFS4ERR_SEQ_MISORDERED errors, severe client performance degradation.
  • Fix: Kernel patch correcting the order of SEQUENCE reply encoding during replay.
  • Status: Fixed in upstream Linux and RHEL10.2/CentOS 6.12.0-201+.
