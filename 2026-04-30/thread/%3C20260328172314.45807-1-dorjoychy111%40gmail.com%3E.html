OPENAT2_REGULAR: EFTYPE Error Code Choice Debated Post-Merge

Summary

This week's activity on the OPENAT2_REGULAR flag thread was brief but pointed, focusing on a post-merge debate over the appropriateness of using -EFTYPE as the error code returned when openat2() with OPENAT2_REGULAR encounters a non-regular file. The patches were already applied to the VFS tree last week; this discussion represents a retrospective concern raised by Florian Weimer regarding POSIX compliance and historical precedent for the EFTYPE error number.

Bridge from Prior Weeks

Over the preceding weeks, the Patch v6 series introducing the OPENAT2_REGULAR flag underwent thorough review by Jeff Layton (who provided a Reviewed-by tag), Aleksa Sarai, Jori Koolstra, and others. The series was applied to the vfs-7.2.openat.regular branch by Christian Brauner on April 16. The feature allows applications to explicitly request opening only regular files via openat2(), returning -EFTYPE if a non-regular file (directory, device node, FIFO, etc.) is encountered. The NFS client implementation in fs/nfs/dir.c was part of this accepted patch set, enabling robust support for strict regular-file opens within the nfs_atomic_open codepath.

This Week's Activity (April 27)

Florian Weimer Raises POSIX Concerns

On April 27, Red Hat's Florian Weimer questioned the choice of EFTYPE as the error code in his message, citing the POSIX Rationale for System Interfaces:

"[EFTYPE] This error code was proposed in earlier proposals as 'Inappropriate operation for file type', meaning that the operation requested is not appropriate for the file specified in the function call. This code was proposed, although the same idea was covered by [ENOTTY], because the connotations of the name would be misleading. It was pointed out that the fcntl() function uses the error code [EINVAL] for this notion, and hence all instances of [EFTYPE] were changed to this code."

Weimer concluded:

"So I'm not sure if reusing this name is a good idea."

This raises an interesting historical point: POSIX originally considered EFTYPE but ultimately deprecated it in favor of EINVAL or ENOTTY, noting that the name's connotations were misleading. The concern is whether Linux should revive this largely unused error code for a new UAPI feature.

Chowdhury Defends EFTYPE with BSD Precedent

Dorjoy Chowdhury responded on April 27, explaining the evolution of the error code choice:

"I had started out the patch series with ENOTREGULAR and it was discussed that EFTYPE was a better and more generic error code which is also used in BSD systems like FreeBSD[1] and MacOS[2]. I also agree that EFTYPE makes sense. We can of course change to something else if everyone agrees."

Chowdhury noted that the original v1 submission used ENOTREGULAR, but during review, it was decided that EFTYPE was preferable because it is a more generic error code and aligns with BSD-derived systems (FreeBSD and macOS), which actively use EFTYPE. He left the door open for change if consensus formed around an alternative.

Brauner Questions the Alternative

Christian Brauner, VFS maintainer and the person who originally suggested EFTYPE, pushed back against switching to ENOTTY in his reply:

"Given that both the bsds and macos already use that is there a good reason to return ENOTTY for this other than a standard we ignore most of the time anyway? I'm honestly asking."

Brauner's position reflects a pragmatic view: Linux does not strictly follow POSIX in many areas, and aligning with BSD/macOS usage of EFTYPE provides better cross-platform consistency for applications that already handle this error code on those systems.

Classification

New Feature (UAPI addition). No bug fixes were discussed this week. The debate centers on the semantic appropriateness of the -EFTYPE error code chosen for the already-merged OPENAT2_REGULAR feature.

Implications for NFS Client Development

For NFS client development, the choice of error code has practical implications. When an application uses openat2() with OPENAT2_REGULAR on an NFS mount, the kernel will return -EFTYPE if the target is a directory, device node, or other non-regular file type. This provides a consistent and predictable error for applications to handle across filesystems (NFS, Ceph, GFS2, SMB). If the error code were changed to ENOTTY, NFS client code would need updating, and userspace applications relying on -EFTYPE would break. The current consensus among maintainers appears to favor retaining EFTYPE.

Conclusion

The discussion remains open-ended with no definitive resolution this week. Brauner's rhetorical question suggests resistance to changing the error code post-merge, while Weimer's POSIX-based concern highlights a legitimate design consideration. For NFS client development, the practical impact is minimal regardless of the outcome: the feature provides robust validation for strict regular-file opens, and the specific error code can be handled by userspace abstraction layers.
