NFSD Block Layout Exports: Repost Request and Merge-Window Process Discussion

Summary

This week, the procedural discussion around Christoph Hellwig's "cleanup block-style layouts exports v2" series continued with a focus on finalizing integration logistics. Following last week's agreement to use a vfs.nfsd subtree as the integration point for NFSD-related VFS infrastructure changes, Christian Brauner requested that Jeff Layton repost his CB_NOTIFY patchset to incorporate an error-handling fix. Brauner also raised a broader process question about establishing a quiet period for new work during the merge window.

Background (Prior Week)

Last week, the long-running dispute over which kernel tree should accept exportfs infrastructure changes touching PNFS block layouts was resolved. Chuck Lever and Christian Brauner agreed on a hybrid model: Brauner would maintain a vfs.nfsd subtree within the VFS tree, serving as the integration point for both Hellwig's block-layout export cleanup and Layton's CB_NOTIFY API modifications see prior summary.

On April 23, Layton noted an error-handling discrepancy in his CB_NOTIFY series:

"Note that there is a small difference (error-handling fix) between the most-recently posted CB_NOTIFY patchset and what's currently in my tree. You can either pick or pull the series from my tree, or I can re-post." Jeff Layton

This Week's Activity

Repost Request for CB_NOTIFY Series

On April 27, Brauner responded to Layton's offer, requesting a formal repost rather than pulling directly from the tree:

"Just repost, if you would be so kind." Christian Brauner

This ensures that the posted version matches what will be integrated into vfs.nfsd, maintaining transparency and allowing for proper review of the error-handling fix. The CB_NOTIFY operation is critical for NFSv4 clients, enabling efficient delegation recall notifications from server to client. Proper error handling in this path prevents silent failures that could leave clients with stale delegations or missed state changes.

Merge-Window Quiet Period Proposal

Brauner also raised a broader process question about managing new work during the merge window (mw):

"(I wonder whether we should start having a quiet period for new work during the mw like net has.)" Christian Brauner

This suggests aligning NFS/VFS integration practices with the networking subsystem's approach, which restricts new submissions during the merge window to reduce integration complexity and last-minute changes.

Technical Classification and Impact

This week's activity falls under infrastructure integration logistics with implications for NFS client development:

  1. Process Improvement: The repost request ensures clean integration of Layton's CB_NOTIFY error-handling fix into the vfs.nfsd subtree, maintaining review quality.
  2. Potential Process Change: Brauner's quiet period proposal could significantly impact how NFS developers time their submissions, reducing merge-window chaos and improving stability for client-facing features.

Impact on NFS Client Development:

  • The CB_NOTIFY error-handling fix ensures robust callback notification behavior, which is essential for NFSv4 clients to receive timely delegation recalls and state change notifications.
  • A potential quiet period during the merge window would provide more predictable integration timelines for client-critical infrastructure changes like PNFS block layouts and callback notifications.

Final Conclusions

The thread remains focused on procedural logistics rather than technical debate. Brauner's request for a repost of Layton's CB_NOTIFY series ensures proper review of the error-handling fix before integration into vfs.nfsd. His suggestion for a merge-window quiet period introduces a new process discussion that could benefit NFS client development by providing more stable integration timelines. The underlying technical work—Hellwig's block-layout export cleanup and Layton's CB_NOTIFY support—continues to advance through the agreed-upon vfs.nfsd workflow.
