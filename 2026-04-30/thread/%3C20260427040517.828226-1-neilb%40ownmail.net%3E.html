NFS/VFS: Preparing to Lift Lookup Out of Exclusive Directory Lock

Summary

Prepare to Lift Lookup Out of Exclusive Lock for Directory Ops

Neil Brown submitted a 19-patch series (PATCH v3 00/19) aimed at improving concurrency for directory operations in the VFS and specifically for NFS and OverlayFS (ovl). The overarching goal is to move ->lookup calls outside the exclusive inode lock (i_rwsem) on directories, allowing broader concurrency.

Key Technical Arguments and Evolution

1. VFS Infrastructure Changes

The series introduces several new VFS primitives to support the locking changes:

  • d_splice_alias() enhancements: Extended to handle hashed, unhashed, or in-lookup dentries (PATCH 02/19).
  • d_alloc_noblock(): A non-blocking variant of d_alloc_parallel() that returns -EWOULDBLOCK if a concurrent lookup is in progress (PATCH 05/19).
  • d_duplicate(): Creates an in-lookup dentry with the same name as an existing hashed dentry, preventing races during operations like silly-rename (PATCH 06/19).
  • LOOKUP_SHARED flag: Indicates to ->lookup handlers whether the parent directory is held with a shared or exclusive lock (PATCH 07/19).
  • wait_var_event in d_alloc_parallel(): Replaces the explicit waitqueue head parameter with wait_var_event_spinlock() using dentry->d_lock for synchronization (PATCH 04/19).

2. Discussion on LOOKUP_SHARED and Locking Semantics

Amir Goldstein expressed skepticism about Neil's claim that ->lookup would always be called with a shared lock in the future:

"Forgive me for being skeptical about the always part... I think it is more realistic to state that LOOKUP_SHARED is here to stay" [id://CAOQ4uxi8rqkbhK4=8N1ncfU1m6bjdHLbinSf=j3k0oVEaSa-wA@mail.gmail.com]

Neil countered that all filesystems already support ->lookup with a shared lock because simple lookups already provide only a shared lock:

"All filesystems must support ->lookup with a shared lock because it is already the case that with a simple lookup only a shared lock is provided... So I'm certain that it is safe from the filesystem's perspective to always call with only a shared lock" [id://177727962988.1474915.2841674553452335690@noble.neil.brown.name]

Amir remained cautious, noting edge cases with FUSE servers that may rely on kernel-side serialization:

"I will remain skeptical... think fuse servers (not under your control) which have grown to rely on the kernel to serialize atomic_open() on the directory" [id://CAOQ4uxiMUKHuGwpSkD=M4Z_QLxHn7Os9vaaWqAWd36HdfDRYuQ@mail.gmail.com]

3. API Design: d_add_ci() and Lock Dropping

Amir criticized the API choice in PATCH 08/19, which passed a boolean indicating shared/exclusive lock state to d_add_ci():

"I do not understand the choice of API. Seems better to pass the lookup flags and avoid exposing this very internal logic in the call sites..." [id://CAOQ4uxjj6iJNnwUqV+cRtqo4qRD4v-f-ct92=ofCZWPDATXM7g@mail.gmail.com]

Neil agreed: "That is an excellent suggestion... I will definitely do that" [id://177727971181.1474915.16652480895948480305@noble.neil.brown.name].

4. Critical Bug in OverlayFS Patch

Amir Goldstein, assisted by AI review, identified a critical bug in PATCH 09/19:

"The patch has a critical condition inversion (!d_unhashed vs d_unhashed) that would break impure readdir entirely and cause use-after-free corruption in the dcache. It also has a missing NULL check for d_alloc_name() failure" [id://CAOQ4uxidCcGpABkCtkn94i3U_u3OWK16zeAVDG2xuhh5e+ws9g@mail.gmail.com]

This bug was corroborated by a syzbot crash report, which Neil attributed to the inverted test:

"The inverted test on d_unhashed() in [PATCH v3 09/19]... could easily cause that to happen. So I believe this is now fixed" [id://177741819272.1474915.16232905294067712018@noble.neil.brown.name]

5. d_alloc_parallel() Waitqueue Refactoring

The most extensive technical debate centered on PATCH 04/19, which replaced the explicit waitqueue in d_alloc_parallel() with wait_var_event. Al Viro provided detailed feedback on optimizing the implementation, suggesting that DCACHE_LOOKUP_WAITERS should not be cleared and proposing a cleaner separation of wakeup logic:

"In __d_lookup_unhash(): just don't return anything and lose the parts related to ->d_wait... That yields the same semantics for flags as your variant does... and fs/dcache.c part is more straightforward that way" [id://20260429052626.GY3518998@ZenIV]

Al Viro subsequently posted a complete alternative patch implementing his suggestions. Linus Torvalds reviewed it:

"This looks like a clear improvement to me... But just looking at the patch I went 'Make it so'" [id://CAHk-=wgs8yAfaQYmeKWab7KES0jU46TvdBfQ3Q9+6+=E=vrx=w@mail.gmail.com]

Neil acknowledged a bug in Al's proposed __d_move() handling, noting that the wrong dentry was being woken:

"That code is wrong. It only makes sense to __d_wake_in_lookup_waiters() a dentry that we know was in-lookup, and in d_move, that is target... So we need __d_wake_in_lookup_waiters(target); in d_move" [id://177759308866.1474915.9708613530229799376@noble.neil.brown.name]

6. NFS Client-Specific Changes

The series includes seven patches targeting the NFS client (PATCH 13-19/19):

  • Removal of d_drop()/d_alloc_parallel() from nfs_atomic_open() in favor of relying on ->d_revalidate for exclusion.
  • Use of d_splice_alias() in nfs_link() and atomic create paths, eliminating unsafe d_drop() calls before splice operations.
  • Adoption of d_alloc_noblock() in nfs_prime_dcache() and silly-rename paths.
  • Use of d_duplicate() for dentry duplication.

Neil reported a testing issue at the end of the week:

"Also my testing has hit a problem with some sort of deadlock in the nfs server (so accessing an XFS filesystem). They are trying to unlink a file and are waiting in d_alloc_parallel() under reconnect_path. This is running generic/467. So better hold off this patchset until I have that understood" [id://177759308866.1474915.9708613530229799376@noble.neil.brown.name]

7. Linus Torvalds on Incremental Merging

Linus encouraged breaking the series into smaller, independently mergable pieces:

"when it comes to something as core and subtle as the dcache and filesystem integration, I'd personally be very happy to see this merged in small clear pieces... please take any cleanups in this series asap" [id://CAHk-=whXZz=-XnJdMGzM8BCwDkoqU0yDNKWyrpZSwXzchxsPUQ@mail.gmail.com]

Final Conclusions

  • The series is a protocol/locking change aimed at improving directory operation concurrency, not a bug fix or new feature in the traditional sense.
  • Several API refinements were agreed upon (passing lookup flags instead of booleans, cleaner waitqueue handling).
  • A critical bug in the OverlayFS patch was identified and fixed.
  • Al Viro's refactored d_alloc_parallel() implementation received positive feedback from Linus but requires further testing.
  • The series is on hold pending resolution of a deadlock observed during NFS client testing against an XFS server.
