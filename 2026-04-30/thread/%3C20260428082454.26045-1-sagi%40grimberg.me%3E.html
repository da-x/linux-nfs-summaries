NFSv4: Keep delegation post REMOVE when server supports preserved-unliked

Summary

NFSv4 Delegation Optimization for Preserved-Unlinked Files

Type: Proposed optimization / feature enhancement (RFC patch)

This week, Sagi Grimberg posted an RFC patch proposing an optimization to the NFSv4 client's delegation handling when a file is removed (unlink operation). The thread consists of a single message with no replies yet.

The Proposal

In his patch submission, Sagi Grimberg proposed modifying the NFSv4 client to retain delegations after a REMOVE (unlink) operation when the server advertises support for NFS4_OPEN_RESULT_PRESERVE_UNLINKED. The key insight is:

"If the server returns NFS4_OPEN_RESULT_PRESERVE_UNLINKED, it means that the file handle is kept alive for as long as the file is opened (or its delegation is held). Hence, we can skip re-opening the file and returning the delegation in this case."

Technical Context

The PRESERVE_UNLINKED flag is part of the NFSv4.2 protocol extension that allows a server to indicate it will preserve an unlinked file's data and metadata as long as it remains open or its delegation is held. This capability enables more efficient client behavior: when a file is unlinked but still has an open handle or delegation, the client does not need to re-open the file or return its delegation, since the server guarantees the file handle remains valid.

The patch modifies fs/nfs/nfs4proc.c with 10 insertions and 3 deletions, adjusting the client's REMOVE handling logic to check for this server capability and skip unnecessary operations.

Status

As an RFC (Request for Comments) submission, this patch is seeking feedback from the NFS development community. No replies or reviews were posted during this week's window. The discussion remains open for input on whether this optimization is appropriate and correctly implemented.
