Report of NFS client processes stuck in D state under memory pressure

Summary

Processes in D State / Blocked Tasks: Open Bug Report

Overview

This thread consists of a single message this week, an initial bug report from Rik Theys at KU Leuven describing a serious issue where NFS client processes become stuck in uninterruptible sleep (D state), effectively hanging the NFS client. No replies have been received as of the end of the reporting window.

Issue Classification

This is a bug report / troubleshooting request, not a proposed patch or feature. The discussion centers on diagnosing whether the hangs are caused by a kernel bug, a server-side issue, or resource exhaustion under memory pressure.

Key Technical Details

Rik Theys reported that "some of our numbercrunchers are periodically logging blocked tasks and the NFS client seems to (at least partially) hang" f32822c8-9910-43a1-8d7f-72df6b79a1e8@esat.kuleuven.be. The environment involves:

  • Clients: Rocky 9 (kernel 6.18.20) and Rocky 8 (kernel 4.18.0-553.117.1.el8_10.x86_64)
  • Server: RHEL 10 running kernel 6.12.0-124.45.1.el10_1.x86_64

The issue appears correlated with increased server utilization:

"Most likely the reason we are seeing this come up now is that more users are starting to use the shared server and it frequently comes under high memory pressure."

Observed Symptoms

Multiple kernel hung_task warnings were logged, with processes blocked for over 120 seconds. The call traces reveal three distinct blocking patterns:

  1. Writeback waits — Tasks blocked in folio_wait_writeback → nfs_write_begin → nfs_file_write, indicating pages stuck in writeback that never complete.
  2. Inode lookup waits — Tasks blocked in __wait_on_freeing_inode during nfs_fhget / _nfs4_open_and_get_state, suggesting an inode is being freed but not yet released.
  3. RPC execution hangs — Processes waiting in rpc_wait_bit_killable within the SUNRPC layer, particularly during nfs4_proc_access permission checks.

Additional stacks showed page faults stuck in filemap_fault and autofs mounts waiting in autofs_mount_wait.

Rik noted:

"When I look at the output of ps -e -o state,pid,user,cmd,wchan | grep ^D, it seems most of these blocked processes are waiting in rpc_wait_bit_killable, some in folio_wait_bit_common and a few in autofs_wait."

Rocky 8 Observations

On the older Rocky 8 system, git processes were blocked during file flush/close operations:

wait_on_page_writeback → __filemap_fdatawait_range → nfs_wb_all → nfs4_file_flush → filp_close

This suggests that writeback completion is stalled, preventing file close operations from returning.

Server Status

The server itself shows no obvious issues:

"The server seems to be fine: there's no high load, no indications of a network issue and the disks are not saturated."

Context with Prior Reports

This report comes from the same reporter who recently experienced NFS4ERR_SEQ_MISORDERED errors on the same RHEL 10 server infrastructure (summarized in a separate thread). That issue was traced to a server-side bug in SEQUENCE replay handling, fixed in RHEL 10.2 kernels. It is unclear whether this new D-state hang is related or a distinct problem.

Open Questions

Rik Theys asked:

"What could cause these processes to end up in this state? Is there some deadlock due to memory pressure? Which information could be more useful to further debug this and/or make the system recover?"

As of the end of this reporting week, no replies have been posted. The thread remains open for community diagnosis.
