NFSv4.1/pNFS: Fix LAYOUTCOMMIT Retry Loop on OLD_STATEID

Summary

This thread documents a bug fix for the NFS client's Parallel NFS (pNFS) implementation, specifically addressing an unbounded retry loop in LAYOUTCOMMIT operations when encountering stale state IDs. The discussion also clarifies submission procedures for the linux-nfs mailing list.

Technical Issue: Unbounded LAYOUTCOMMIT Retries

Lei Yin submitted a patch to resolve a critical issue where the NFS client could enter an infinite retry loop during pNFS layout commit operations.

"Without refreshing data->args.stateid, LAYOUTCOMMIT can keep retrying with the same stale stateid after OLD_STATEID, resulting in an unbounded retry loop." Lei Yin

The bug manifests when the server returns -NFS4ERR_OLD_STATEID, indicating that the state ID used in the request is no longer valid. The existing code path did not handle this error appropriately in nfs4_layoutcommit_done(), leading to repeated attempts with the same invalid state ID. This could cause affected files to become unresponsive, effectively hanging I/O operations on those files.

Reproduction and Impact

Lei Yin provided detailed reproduction steps, noting that the issue was observed on NFSv4.2:

"The most reliable way I found to reproduce it is: 1. Run a workload with relatively high concurrent I/O on the client. 2. Kill the client-side I/O process with kill -9 while those I/Os are still in flight." Lei Yin

The developer explained that using kill -9 significantly increases the likelihood of hitting the stale state ID window, though the issue can occasionally occur under heavy concurrency and stress testing even without forced process termination. The core problem is that:

"because LAYOUTCOMMIT does not recover from OLD_STATEID here, the RPC can loop indefinitely with the stale stateid; once this happens, operations on the corresponding file may stop making progress." Lei Yin

Proposed Fix

The patch introduces proper error handling by:

  1. Calling nfs4_layout_refresh_old_stateid() to refresh the layout state ID when -NFS4ERR_OLD_STATEID is received.
  2. Updating the layout state ID in the inode layout header after a successful refresh.
  3. Restarting the RPC operation only after the state ID has been successfully refreshed.

This ensures that subsequent LAYOUTCOMMIT attempts use a valid state ID, breaking the infinite retry cycle.

Submission Clarification

Lei Yin initially expressed confusion about the patch being marked as "Not Applicable" in Patchwork:

"Could you please let me know whether the Not Applicable status means: 1. an equivalent fix is already present in the target tree, 2. the patch was sent against the wrong tree or branch, or 3. there is some issue with the problem analysis or the proposed fix?" Lei Yin

Chuck Lever clarified that this was a procedural matter rather than a technical rejection:

"The linux-nfs patchworks is for NFSD only. 'Not Applicable' means the patch is not an NFSD patch." Chuck Lever

This distinction highlights that the linux-nfs Patchwork instance tracks server-side (NFSD) patches, while client-side fixes like this one follow a different submission and review workflow.

Conclusion

This thread presents an important bug fix for NFS client development, addressing a potential denial-of-service condition in pNFS implementations where stale state IDs could cause indefinite retry loops. The fix ensures proper state ID refresh mechanisms are employed when the server indicates that a state ID is obsolete, thereby maintaining I/O progress and system stability under concurrent load conditions.
