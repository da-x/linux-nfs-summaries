NFSv4: Fix -EEXIST on mkdir after NFS4ERR_DELAY retry

Summary

Bug Fix: Spurious -EEXIST from mkdir(2) After Successful Retry

This week, Igor Raits submitted a targeted bug fix for the NFSv4 client addressing a subtle but impactful regression in exception-state management during mkdir(2) retries. The patch was reviewed by NeilBrown and marked for stable backport.

The Problem

When an NFSv4 server returns NFS4ERR_DELAY for a CREATE operation (issued by mkdir(2)), the Linux NFS client correctly waits and retries. However, after the retry succeeds—creating the directory on the server—userspace can still receive -EEXIST, even though the directory was just created successfully. This manifests as intermittent failures under high-concurrency workloads.

Raits provided a concrete reproducer targeting an in-kernel Linux nfsd, which works under both NFSv4.0 and NFSv4.2:

N=2000000; base=/var/gdc/export
for ((i=1; i<=N; i++)); do
    d=$base/$(openssl rand -hex 8)
    mkdir "$d" 2>/dev/null || echo "$(date +%T) failed loop=$i $d"
    rmdir "$d" 2>/dev/null
done

Failures cluster at the cadence of server-side auth/export cache refresh, which triggers NFS4ERR_DELAY from nfsd.

Root Cause Analysis

Raits traced the issue to a wire-level sequence where three CREATE RPCs originate from a single mkdir(2) call:

"client -> server CREATE name=... -> NFS4ERR_DELAY
~100 ms later
client -> server CREATE name=... -> NFS4_OK (dir created)
~80 us later
client -> server CREATE name=... -> NFS4ERR_EXIST (correct)"

The third CREATE should never have been issued. The root cause was identified in commit dd862da61e91 ("nfs: fix incorrect handling of large-number NFS errors in nfs4_do_mkdir()"), which introduced a conditional gate around nfs4_handle_exception(). Raits explained:

"Since commit dd862da61e91, nfs4_handle_exception() is called only when _nfs4_proc_mkdir() returned an error. That gate breaks retry-state hygiene: nfs4_do_handle_exception() resets exception.{delay,recovering,retry} to 0 on entry, so calling it on success is what previously cleared the retry flag set by the preceding NFS4ERR_DELAY iteration."

With the conditional in place, exception.retry remains at 1 after a successful retry. The do-while loop in nfs4_proc_mkdir() executes one additional iteration, sending another CREATE for an already-created name, which correctly returns NFS4ERR_EXIST — but this is then surfaced as -EEXIST to userspace.

The Fix

The patch drops the conditional and calls nfs4_handle_exception() unconditionally after each iteration of the do-while loop, matching the pattern used by every other similar operation in fs/nfs/nfs4proc.c (e.g., nfs4_proc_symlink(), nfs4_proc_link()). As Raits noted:

"Drop the conditional and call nfs4_handle_exception() unconditionally, matching every other do-while in fs/nfs/nfs4proc.c. The dentry/status separation introduced by that commit is preserved."

The fix changes only 5 lines in fs/nfs/nfs4proc.c (2 insertions, 3 deletions), making it a minimal and surgical correction.

Conclusion

This is a classic example of how well-intentioned error-handling refactors can inadvertently break retry-state hygiene in complex protocol clients. The NFSv4 client's do-while retry loops depend on consistent exception-state cleanup after every iteration — success or failure. Restoring the unconditional call to nfs4_handle_exception() aligns nfs4_proc_mkdir() with the established pattern across the rest of the NFSv4 procedure implementations. Given its stable-tagging and minimal scope, this fix is expected to be merged promptly and backported to affected stable kernels.
