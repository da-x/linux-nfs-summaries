Exposing case folding behavior: VFS infrastructure and NFS client/server support (v11)

Summary

Overview

Chuck Lever submitted version 11 of a 15-patch series titled "Exposing case folding behavior" to the Linux NFS mailing list. This is a long-running effort (now in its eleventh iteration) aimed at enabling file services such as NFSD and ksmbd to report the actual case-folding semantics of local filesystems to clients.

The series addresses a critical interoperability gap: Windows and macOS NFS clients expect case-insensitive behavior, which differs from traditional POSIX semantics. As Chuck Lever explained in the cover letter [20260424-case-sensitivity-v11-0-de5619beddaf@oracle.com]:

"The Linux NFS community has a growing interest in supporting NFS clients on Windows and MacOS platforms, where file name behavior does not align with traditional POSIX semantics."

He noted that one Windows-based NFS client implementation "explicitly requires servers to report FATTR4_WORD0_CASE_INSENSITIVE = TRUE for proper operation, a hard requirement for Windows client interoperability because Windows applications expect case-insensitive behavior."

Technical Scope

The patch series introduces two new read-only extended flags, FS_XFLAG_CASEFOLD and FS_XFLAG_CASENONPRESERVING, into the VFS file_kattr structure. These flags allow filesystems to report their case-sensitivity and case-preservation characteristics via the file_getattr() syscall and FS_IOC_FSGETXATTR ioctl.

Key components of the series include:

  1. VFS Infrastructure: Moving file_kattr initialization to callers and adding case sensitivity flags to the structure [20260424-case-sensitivity-v11-1-de5619beddaf@oracle.com], [20260424-case-sensitivity-v11-2-de5619beddaf@oracle.com].

  2. Local Filesystem Implementations: Adding fileattr_get callbacks for FAT, exFAT, NTFS3, HFS, HFS+, XFS, CIFS, vboxsf, and ISO9660 to report their native case-handling behavior.

  3. NFS Client Support: The NFS client patch [20260424-case-sensitivity-v11-10-de5619beddaf@oracle.com] implements fileattr_get to surface case sensitivity information learned from the server during mount via PATHCONF (NFSv3) or FATTR4_CASE_INSENSITIVE/FATTR4_CASE_PRESERVING attributes (NFSv4). This enables re-export scenarios where an NFS mount point is served by NFSD.

  4. NFSD Enhancements: Reporting export case-folding via NFSv3 PATHCONF [20260424-case-sensitivity-v11-13-de5619beddaf@oracle.com] and implementing FATTR4_CASE_INSENSITIVE and FATTR4_CASE_PRESERVING for NFSv4 [20260424-case-sensitivity-v11-14-de5619beddaf@oracle.com].

  5. ksmbd Support: Reporting filesystem case sensitivity via SMB's FS_ATTRIBUTE_INFORMATION [20260424-case-sensitivity-v11-15-de5619beddaf@oracle.com].

Key Technical Discussions

ext4/f2fs Case Flag Propagation

Jan Kara questioned how ext4 and f2fs would report case folding, noting he could not find code transforming the S_CASEFOLDED inode flag into FS_CASEFOLD_FL on the fileattr_get path [yc7ygk6w6zvf46arzzvmxnuoqjrni2dtlhmywaivzmvfxnilf3@xv7tthtrowns]:

"Err, how is this supposed to work? I wasn't able to find any code transforming S_CASEFOLDED inode flag into FS_CASEFOLD_FL on fileattr_get path. Sure, fileattr_fill_flags() takes care of setting FS_XFLAG_CASEFOLD once FS_CASEFOLD_FL is set. What am I missing?"

Chuck Lever clarified that the path does not go through S_CASEFOLD. Instead, both filesystems report FS_CASEFOLD_FL directly from their on-disk flag words, which fileattr_fill_flags() then translates into FS_XFLAG_CASEFOLD [af3f7518-7501-4c25-9bbc-a8fc8cdb4e29@app.fastmail.com]:

"The path does not go through S_CASEFOLD. Both filesystems report FS_CASEFOLD_FL straight from their on-disk flag word."

Jan Kara acknowledged the explanation: "Oh, right. I've missed how EXT4_CASEFOLD_FL propagates into FS_CASEFOLD_FL. Thanks for clearing that out" [jq4wmu34kstqgvjspfalgedpsv3xciwkc5uaj7ewdc73a3yt6f@ddoia6tddojv].

ISO9660: Per-File vs. Per-Directory Attributes

Jan Kara questioned the decision to register fileattr_get on regular files and symlinks in the isofs patch, noting that casefolding is typically a directory attribute [isfgwmd5hxjfn7dj7p54yzlhumx2hrkt3zw7fscs2ywm57g3hu@co27drpx24lq]:

"Hum, I thought casefolding is a directory attribute. At least I don't see a big point in reporting it for regular files or symlinks (and then why not report it for device nodes or named pipes?). So why did you decide for this change?"

Lionel Cons referenced the Rock Ridge specification to challenge the premise [CAPJSo4WmRu_64TxBsaimWOqz3VAU0TZ1H-_hw36HSqzQULm39w@mail.gmail.com], but Jan Kara clarified he was referring to general VFS tracking rather than the Rock Ridge standard specifically [lxbpvsj3b6jvl2tmcxgto4aqsi6necmmha3ldby3k4bnmyxltm@mii3s6vjmanq].

XFS: Inconsistent Flag Reporting and chattr Round-Trips

Darrick J. Wong raised a significant concern about the XFS patch, which masked FS_CASEFOLD_FL from the legacy flags view to avoid issues with chattr round-trips [20260427155636.GC7751@frogsfrogsfrogs]:

"I don't understand this at all. Yes, FS_XFLAG_CASEFOLD is readonly, but how does clearing FS_CASEFOLD_FL from the fileattr_get output (without clearing XFLAG_CASEFOLD!) solve anything? This makes the reported output inconsistent between fsgetxattr and getflags -- one reports case folding, the other reports no casefolding."

He suggested that the fix should be in the fileattr_set path instead:

"If you want to avoid fileattr_set returning EINVAL when setting attributes due to the casefold flag, then don't you want to check the flag state vs. xfs_has_asciici() in the fileattr_set path?"

Chuck Lever agreed that masking was the wrong approach and outlined his plan for v12 [3fd6dcbf-ece6-459e-b114-1d8b95035acf@app.fastmail.com]:

"For v12 I'll drop the fa->flags mask and add FS_CASEFOLD_FL to the allowlist in xfs_fileattr_set(), gated on xfs_has_asciici(mp)."

He noted that the same pattern existed in the hfsplus patch and would be fixed similarly.

Conclusion

This thread represents version 11 of a mature patch series focused on exposing filesystem case-folding behavior through VFS infrastructure, with significant implications for NFS client and server interoperability. The discussion this week centered on:

  1. Clarifying how ext4/f2fs propagate case flags through the VFS layer.
  2. Debating whether case sensitivity should be reported per-file or per-directory (particularly for ISO9660).
  3. Identifying and planning fixes for inconsistent flag reporting in XFS that could cause chattr round-trip failures.

The series is classified as a new feature enabling proper case-sensitivity reporting across multiple filesystems and network file services, rather than a bug fix or protocol change. The NFS client benefits by being able to report accurate case-handling semantics when acting as a backend for NFSD in re-export scenarios, while the NFS server gains the ability to inform Windows and macOS clients of the underlying filesystem's case behavior.
