NFSv4 Client Regression Fix: mkdir EEXIST after NFS4ERR_DELAY

Summary

NFSv4 Client Regression: mkdir Returns EEXIST After DELAY-Then-Success

Overview

This thread addresses a critical regression in the Linux NFSv4 client where mkdir(2) syscalls occasionally return -EEXIST to userspace even though the directory was successfully created on the server. The issue affects both NFSv4.0 and NFSv4.2 mounts against an in-kernel Linux nfsd, reproducing reliably under load or after mount idleness.

Bug Classification

Type: Bug Fix (Regression)
Component: NFS Client (fs/nfs/nfs4proc.c)
Root Cause Commit: dd862da61e91 ("nfs: fix incorrect handling of large-number NFS errors in nfs4_do_mkdir()")

Technical Analysis

Symptom and Reproduction

Igor Raits reported that an occasional mkdir(2) returns -EEXIST, yet the directory exists on disk. The issue is reproducible with a simple loop creating random-named directories:

"Symptom: an occasional mkdir(2) on an NFSv4 mount returns -EEXIST, but the directory it was supposed to create is actually present afterwards."
— Igor Raits

Packet captures revealed a three-RPC sequence for a single mkdir syscall:

  1. Client sends CREATE → Server returns NFS4ERR_DELAY
  2. Client retries CREATE → Server returns NFS4_OK (directory created)
  3. Client sends another CREATE → Server returns NFS4ERR_EXIST

The client then incorrectly surfaces the final EXIST error to userspace, despite having already received a successful response in step 2.

Root Cause

The regression was introduced by commit dd862da61e91, which refactored nfs4_proc_mkdir() to return the error code separately from the dentry pointer. The change added an if (err) guard around the call to nfs4_handle_exception():

do {
    alias = _nfs4_proc_mkdir(dir, dentry, sattr, label, &err);
    trace_nfs4_mkdir(dir, &dentry->d_name, err);
    if (err)
        alias = ERR_PTR(nfs4_handle_exception(NFS_SERVER(dir),
                                              err, &exception));
} while (exception.retry);

Igor Raits identified the flaw:

"If I'm reading this right, on a successful retry (err == 0) nfs4_handle_exception() is skipped, so exception.retry stays at the value it had after the previous DELAY iteration (which is 1). The loop then runs once more, sends another CREATE for the same name, and that one legitimately gets NFS4ERR_EXIST."
— Igor Raits

Other similar loops in the same file (e.g., nfs4_proc_symlink) call nfs4_handle_exception() unconditionally, which correctly resets exception.retry to 0 on success and exits the loop.

Resolution

Igor Raits proposed a patch that removes the if (err) guard, ensuring nfs4_handle_exception() is always called:

"FTR I have applied following patch and it seems to fix our issue."
— Igor Raits

NeilBrown, the maintainer who authored the original problematic commit, confirmed the diagnosis:

"Oh dear, that was careless of me. We always need to call nfs4_handle_exception()."
— NeilBrown

He offered to either accept a properly formatted patch from Igor or prepare it himself, providing a Reviewed-by tag:

"That is exactly the patch I was thinking of when I saw your first email. If you would like to create a properly formatted patch for submission, please add Reviewed-by: NeilBrown neil@brown.name. If you don't want to, I can do it for you."
— NeilBrown

Conclusion

This thread demonstrates a rapid and effective resolution of an NFS client regression. The bug was identified through careful packet capture analysis and code review, with the reporter providing both a detailed reproducer and a working fix. The maintainer acknowledged the error in the original commit and endorsed the proposed solution. The fix ensures that nfs4_handle_exception() is called unconditionally in the mkdir retry loop, preventing spurious -EEXIST errors after successful retries following NFS4ERR_DELAY.
