Summary

NFS Client: Application of RCU Lock Cleanup Patch Series

Classification

Bug Fix / Code Cleanup: Removal of redundant rcu_read_lock()/rcu_read_unlock() calls in contexts where they are already implicitly held by spin_lock().

Summary

This week concluded with the application of a 14-patch series originally submitted in September 2025, which removes redundant RCU read-side critical sections. The patches address code redundancy across several subsystems, including NFS-related infrastructure, following an analysis of kernel locking semantics.

Jeff Johnson applied the final patch in the series on April 30, noting:

"Applied, thanks!"

Technical Context and Evolution

The discussion originated from a technical observation by Peng Donglin regarding changes introduced by commit a8bb74acd8efe ("rcu: Consolidate RCU-sched update-side function definitions").

Peng explained the core argument for the cleanup:

"Since commit a8bb74acd8efe... there is no difference between rcu_read_lock(), rcu_read_lock_bh() and rcu_read_lock_sched() in terms of RCU read section and the relevant grace period. That means that spin_lock(), which implies rcu_read_lock_sched(), also implies rcu_read_lock()."

"There is no need no explicitly start a RCU read section if one has already been started implicitly by spin_lock()."

This semantic change in the kernel's RCU implementation meant that explicit rcu_read_lock() calls taken while holding a spinlock were redundant. The patch series systematically removed these unnecessary lock/unlock pairs to simplify code and reduce overhead.

Conclusion

The 14-patch series was successfully applied, with the final commit (c4f518736472c8cfbf1d304e01c631babd2bbf34) addressing the ath9k wifi driver. The cleanup reflects ongoing maintenance efforts to keep kernel code aligned with evolving locking semantics, benefiting NFS client development by ensuring that RCU usage patterns remain correct and efficient across the subsystem's shared infrastructure.
