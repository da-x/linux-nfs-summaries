NFSD Per-Net Callback Ops: Review Feedback on v5 and Netlink Statistics Path

Overview

This thread covers the review phase of PATCH v5 to move accumulated NFSv4 callback operations from global statics into struct nfsd_net, providing per-network-namespace isolation for NFSD. The patch is a bug fix / container-isolation improvement for the NFS server subsystem. After the initial v5 submission on February 26 (summarized in the prior week), maintainers Chuck Lever and Jeff Layton provided detailed review feedback during this reporting period (Feb 27–28).

The discussion evolved from code-level nitpicks to a broader architectural conversation about how NFSD statistics should be exposed to userspace — specifically, whether to extend /proc/net/rpc/nfsd or adopt the newer netlink-based interface.

This Week's Activity

Chuck Lever's Detailed Review (Feb 27)

Chuck Lever opened the review with several technical observations on the v5 patch:

1. Missing Consumer Documentation:

"Where are the consumers of this information? 'Subsequent patch' is an OK answer, but that should be indicated here in your patch description."

Chuck emphasized that the patch moves statistics data structures without explaining what will consume them, making it difficult for future maintainers to understand the purpose.

2. Magic Number Concern:

"I know this is copy-paste of existing code, but can you find a proper symbolic constant to use here instead of '2'?"

This refers to const struct rpc_version *nfsd_cb_versions[2], where the array size 2 should be replaced with a named constant.

3. Statistics Accounting Change Should Be Separated:

"Previously all compound-based callbacks mapped to statidx 1 (NFSPROC4_CB_COMPOUND); now each operation gets its own counter slot (values 0–7). This changes what stats are reported, IIUC. So bundling it here means a bisect on a stats regression cannot isolate when accounting changed, and reverting either change forces reverting both. IMO this should be a pre-requisite commit with its own rationale."

This is a significant architectural concern: the patch conflates two changes — moving data to per-namespace storage and changing how callback statistics are counted. Chuck argues these should be separate commits for clean bisectability.

4. Code Style Nits:

"Nit: Reverse Christmas tree ordering -- this new declaration belongs close to the top."

And regarding the version array assignment:

"Could you add a comment explaining that slot 0 is intentionally NULL and slot 1 corresponds to the CB protocol version number? The original designated-initializer syntax made this self-evident; the replacement imperative assignment here does not."

5. Build Configuration Question:

"Does this build if CONFIG_NFSD_V4 is not enabled?"

Chuck also flagged that new non-static functions require kernel-doc comments per kernel coding standards.

Dai Ngo's Response and Clarification (Feb 27)

Dai Ngo responded by seeking guidance on the statistics consumption question:

"Should I first expand the output of /proc/net/rpc/nfsd and then follow up with a netlink-based implementation? Or are we trying to avoid adding anything new under /proc at this point?"

This question opened a broader discussion about userspace interfaces for NFSD statistics.

Chuck Lever's Policy Guidance (Feb 27)

Chuck clarified the kernel-wide policy:

"The current kernel-wide policy, as I understand it, is that subsystems are to avoid adding new items under /proc unless absolutely needed."

He directed Dai toward the netlink path:

"I believe nfsdctl and the NFSD netlink protocol does not yet have an operation to retrieve statistics. Jeff can help you put that together."

Jeff Layton's Netlink Roadmap (Feb 27)

Jeff Layton joined the discussion with a clear endorsement of netlink and a concrete implementation path:

"+1. Dealing with file-based interfaces for this sort of thing is a giant PITA for userland. Netlink is a much cleaner interface to deal with. No partial reads of the file, etc..."

He outlined the steps for Dai:

"There is a rpc-status-get command, but that's a bit different from what this is adding. You'll probably want to add a new netlink command to get these stats and a new set of attributes for them."

Jeff provided specific guidance on the implementation approach:

"For this, it might be best to first replicate the stats that /proc/net/rpc/nfsd already provides to be accessible via netlink. Then you could add support for the new stats you want to add. Then in userland, you could extend nfsstat to attempt to use netlink first and only fall back to /proc scraping if the command doesn't exist."

He also pointed Dai to the relevant documentation:

"Have a look at Documentation/netlink/specs/nfsd.yaml. You'll want to extend that and regenerate the headers and code, and then implement the new commands."

Dai Ngo's Final Response (Feb 28)

Dai clarified a misunderstanding:

"This patch does not add any new object under /proc. It moves existing statistic from global to per-net-namespace."

He acknowledged the netlink direction while noting the value of /proc for developers:

"Yes, netlink is a much cleaner interface but it requires userland utility written to retrieve and display the data in a user-friendly format for end users or administrators. I think the output of at /proc/net/rpc/nfsd' is still useful for developers who want a quick look of what's going in the back channel."

Dai confirmed he would investigate the netlink path:

"I will look into this."

Evolution of the Discussion

The discussion evolved through three distinct phases this week:

  1. Code Review Phase: Chuck Lever's detailed technical review identified several issues including magic numbers, missing documentation, code style concerns, and a significant architectural concern about conflating statistics accounting changes with namespace isolation.

  2. Architectural Policy Phase: Dai's question about /proc vs. netlink triggered a broader conversation about kernel policy on userspace interfaces. Chuck clarified that new /proc entries should be avoided, pointing toward netlink as the preferred path.

  3. Implementation Roadmap Phase: Jeff Layton provided a concrete multi-step plan for implementing netlink-based NFSD statistics, including extending the existing YAML specification and updating userland tools like nfsstat.

Key Technical Arguments

  • Separation of Concerns: Chuck Lever argued that changing how callback statistics are counted (from compound-based to per-operation) should be a separate commit from moving data structures to per-namespace storage, to preserve clean bisectability.

  • Userspace Interface Policy: The kernel-wide policy discourages new /proc entries; netlink is the preferred interface for NFSD statistics retrieval.

  • Backward Compatibility: Jeff Layton suggested a migration path where userland tools attempt netlink first and fall back to /proc scraping, ensuring compatibility across kernel versions.

Final Conclusions

As of the end of this reporting period:

  • The v5 patch has received detailed review feedback but no formal ack or nack.
  • Chuck Lever identified several issues requiring attention in a v6 submission, most notably the conflation of statistics accounting changes with namespace isolation.
  • A clear path forward has emerged: Dai should prepare a v6 that addresses the code review nits and potentially splits the patch to separate the statistics accounting change.
  • The broader work of exposing NFSD callback statistics via netlink is identified as a future follow-up, with Jeff Layton offering guidance on the implementation approach.
