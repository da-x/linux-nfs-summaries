SUNRPC auth_gss Memory Leak Fix Backport Failure for 6.6-stable

Summary

SUNRPC auth_gss Memory Leak Fix Fails to Apply to 6.6-stable

This thread consists of a single automated notification from stable tree maintainer Sasha Levin regarding a patch that failed to apply cleanly to the Linux 6.6 long-term support (LTS) tree. The underlying patch is a bug fix for memory leaks in the NFS/RPC security layer, specifically within the Generic Security Services API (GSS-API) implementation.

Background: The Bug Fix

The original commit, authored by Chuck Lever, addresses critical memory leaks in the XDR (External Data Representation) decoding error paths for auth_gss. As detailed in the patch description:

"The gssx_dec_ctx(), gssx_dec_status(), and gssx_dec_name() functions allocate memory via gssx_dec_buffer(), which calls kmemdup(). When a subsequent decode operation fails, these functions return immediately without freeing previously allocated buffers, causing memory leaks."

The issue was particularly severe in gssx_dec_ctx() because the caller initializes buffer length fields to non-zero values before decoding. If one part of the decoding succeeds (e.g., src_name) but a later part fails (e.g., targ_name), the previously allocated memory becomes unreferenced and cannot be reclaimed.

The fix introduces goto-based cleanup logic to ensure all allocated buffers are freed before returning an error code. The patch was reported by Xingjing Deng and reviewed by Jeff Layton, with a Cc: stable@vger.kernel.org tag indicating its importance for older kernel versions.

This Week's Activity

On March 1, Sasha Levin posted an automated failure notice regarding the 6.6-stable tree:

"The patch below does not apply to the 6.6-stable tree. If someone wants it applied there, or to any other stable or longterm tree, then please email the backport, including the original git commit id to stable@vger.kernel.org."

This notification indicates that the code changes in the upstream mainline kernel have diverged significantly enough from the 6.6 LTS branch that the patch cannot be applied automatically. No further discussion or response occurred within this week's window.

Conclusion and Next Steps

The discussion is effectively paused, awaiting manual intervention. For the memory leak fix to reach users on the 6.6 LTS kernel (a widely deployed long-term support version), a developer—likely Chuck Lever or another NFS/SUNRPC maintainer—must:

  1. Manually backport the patch to the 6.6 codebase.
  2. Resolve any context conflicts arising from differences between mainline and 6.6.
  3. Submit the rebased patch to the stable mailing list with the original commit ID (3e6397b056335cc56ef0e9da36c95946a19f5118).

Until such a backport is submitted and accepted, systems running 6.6 LTS remain vulnerable to these memory leaks in the RPC-GSS authentication path.
