SUNRPC auth_gss memory leak fix fails 5.15-stable application

Summary

SUNRPC auth_gss Memory Leak Fix Fails to Apply to 5.15-stable

This week, the stable tree maintenance process highlighted a significant bug fix in the NFS client's RPC security layer that requires manual backporting effort. The discussion is centered on a bug fix for memory leaks in XDR decoding error paths within SUNRPC: auth_gss.

Key Technical Arguments and Context

The original commit, authored by Chuck Lever, addresses critical memory leaks in the GSS-API authentication mechanism used by NFS clients over secure channels. The issue affects three specific functions: gssx_dec_ctx(), gssx_dec_status(), and gssx_dec_name().

As detailed in the patch description provided by Sasha Levin:

"The gssx_dec_ctx(), gssx_dec_status(), and gssx_dec_name() functions allocate memory via gssx_dec_buffer(), which calls kmemdup(). When a subsequent decode operation fails, these functions return immediately without freeing previously allocated buffers, causing memory leaks."

The leak in gssx_dec_ctx() is particularly severe because the caller initializes buffer length fields to non-zero values, triggering allocations before the full decoding process completes. For instance:

"If, for example, gssx_dec_name() succeeds for src_name but fails for targ_name, the memory allocated for exported_context_token, mech, and src_name.display_name remains unreferenced and cannot be reclaimed."

The fix introduces goto-based cleanup logic to ensure all previously allocated buffers are freed before returning an error code. This change was reported by Xingjing Deng and reviewed by Jeff Layton.

Evolution of the Discussion

This thread consists of a single notification from Sasha Levin, the stable tree maintainer. The message serves as an automated alert that the patch failed to apply cleanly to the 5.15-stable tree due to context conflicts or API changes in the older kernel version.

"The patch below does not apply to the 5.15-stable tree. If someone wants it applied there, or to any other stable or longterm tree, then please email the backport, including the original git commit id to stable@vger.kernel.org."

No further discussion occurred within this specific thread during the reporting window. The responsibility now falls on developers (likely Chuck Lever or Jeff Layton) to prepare a manually adjusted backport for the 5.15 long-term support tree and submit it to the stable maintainers.

Final Conclusions

  • Issue Type: Bug fix (memory leak in NFS client security code).
  • Status: The patch has been merged into Linus's mainline tree but failed to auto-apply to the 5.15-stable tree.
  • Action Required: A manual backport is needed for 5.15 and potentially other long-term kernels. Developers must rebase the fix against the older codebase and submit it to stable@vger.kernel.org.

This highlights an ongoing challenge in NFS client development: ensuring critical security and stability fixes reach long-term support branches, even when automated tools fail due to historical divergence in the codebase.
