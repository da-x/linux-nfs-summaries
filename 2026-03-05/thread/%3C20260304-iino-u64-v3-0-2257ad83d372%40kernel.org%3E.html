vfs: Widen inode->i_ino to u64 — v3 Posted, Scaffolding Dropped, NFS Client Cleanup Imminent

Summary

Jeff Layton posted PATCH v3 00/12, a dramatically condensed 12-patch series to widen inode->i_ino from unsigned long (32-bit on 32-bit architectures) to u64. This is an architecture-level VFS change, not a traditional bug fix, though it effectively resolves the longstanding 32-bit inode truncation problem that has plagued NFS and other network filesystems for years.

Evolution from v1 and v2

The series has undergone significant structural evolution:

  • v1 (Feb 26): A 61-patch series that faced criticism for bisection hazards due to split format-string changes vfs: i_ino u64 series — v2 planning, bisection strategy, and tracepoint ABI debates.

  • v2 (Mar 2): A massive 110-patch series introducing temporary kino_t typedef and PRIino format macro scaffolding to ensure bisectability vfs: Widen inode->i_ino to u64 — v2 posted, scaffolding debates, and NFS client implications. Christoph Hellwig strongly objected:

    "Just drop the bloody macro and the pointless micro-splitting of the change. After this the inode is always 64-bit and we can just use normal ll specifiers without messing things up."

  • v3 (Mar 4): Layton abandoned the scaffolding approach entirely, squashing format-string changes and the type change into a single large patch at the end of the series. He explained:

    "This version squashes all of the format-string changes and the i_ino type change into the same patch. This results in a giant 600+ line patch at the end of the series, but it does remain bisectable."

Key Technical Arguments This Week

The Scaffolding Debate Resolved

The core organizational debate from v2 — whether to use temporary typedefs/macros for bisectability — was resolved by Layton's decision to consolidate changes. He acknowledged that some Review-by and Acked-by tags were dropped due to the reorganization:

"Because the patchset was reorganized (again) some of the R-b's and A-b's have been dropped."

Christoph Hellwig, who had been the primary critic of the scaffolding approach in v2, provided a Reviewed-by for both the VFS hash/lookup changes and the final treewide patch:

"Looks good: Reviewed-by: Christoph Hellwig hch@lst.de" Re: PATCH 12/12

He did request one cleanup in the VFS layer:

"Can you please drop all these pointless externs while you're at it?" Re: PATCH 01/12

Tracepoint Field Reordering for 32-bit Packing

The v3 series incorporates tracepoint field reordering for better packing on 32-bit systems, addressing concerns raised by Steven Rostedt in v1. Damien Le Moal acknowledged the zonefs tracepoint changes:

"Acked-by: Damien Le Moal dlemoal@kernel.org" Re: PATCH 08/12

Audit Subsystem Widening

Patch 02/12 widens audit subsystem inode fields to u64, preventing truncation on 32-bit platforms that would cause incorrect audit log entries and broken watch/mark comparisons. This addresses a security-relevant bug where inode numbers exceeding 32 bits were silently truncated.

NFS Client Development Impact

This series has profound implications for NFS client development. In the cover letter, Layton highlighted a key cleanup opportunity:

"With this change, we may be able to shrink some inode structures. For instance, struct nfs_inode has a fileid field that holds the 64-bit inode number. With this set of changes, that field could be eliminated. I'd rather leave that sort of cleanups for later just to keep this simple." PATCH 00/12

The NFS client patches in v3 touch seven files across the client and pNFS layers:

  • fs/nfs/dir.c
  • fs/nfs/file.c
  • fs/nfs/inode.c
  • fs/nfs/nfs4proc.c
  • fs/nfs/pnfs.c
  • fs/nfs/filelayout/filelayout.c
  • fs/nfs/flexfilelayout/flexfilelayout.c

Chuck Lever provided his Reviewed-by for the NFSD hunks:

"For the NFSD hunks: Reviewed-by: Chuck Lever chuck.lever@oracle.com" Re: PATCH 12/12

Once merged, this change enables the elimination of:

  • The nfs_inode.fileid field (redundant with inode->i_ino)
  • The enable_ino64 module parameter
  • XOR-folding helpers like nfs_compat_user_ino64()
  • Various 32-bit inode hashing workarounds

These cleanups will significantly simplify the NFS codebase in a follow-on series.

Subsystem Reviews and Acknowledgments

This week saw substantial review activity across subsystems:

  • Jan Kara provided extensive Reviewed-by tags for VFS, ext2, ext4, jbd2, proc, ocfs2, udf, isofs, minix, and fsnotify patches:

    "I've reviewed the VFS, ext2, ext4, ocfs2, udf, isofs, jdb2, minix, fsnotify, and proc bits and they look good to me. Feel free to add: Reviewed-by: Jan Kara jack@suse.cz" Re: PATCH 12/12

  • Damien Le Moal acknowledged zonefs changes:

    "For the zonefs bits: Acked-by: Damien Le Moal dlemoal@kernel.org" Re: PATCH 12/12

  • Christoph Hellwig reviewed the VFS hash/lookup and treewide patches:

    "Otherwise looks good: Reviewed-by: Christoph Hellwig hch@lst.de" Re: PATCH 01/12

Conclusions and Next Steps

  1. The v3 series is posted with only 12 patches, abandoning the kino_t/PRIino scaffolding that Hellwig criticized in v2.
  2. Christoph Hellwig has endorsed v3, providing Reviewed-by tags for both the VFS and treewide patches.
  3. NFS client simplification remains a major downstream benefit: removal of nfs_inode.fileid, the enable_ino64 module parameter, and XOR-folding helpers will significantly clean up the NFS codebase in a follow-on series.
  4. The series is ready for merge pending final integration by VFS maintainer Christian Brauner, who previously encouraged Layton to "just do it" as noted in v1.
  5. Widening get_next_ino() to 64 bits remains deferred to a future follow-on series, as noted in v1.
