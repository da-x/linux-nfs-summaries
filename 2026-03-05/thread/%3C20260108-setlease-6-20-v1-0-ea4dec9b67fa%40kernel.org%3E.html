NFS Reexport lstat -EINVAL Regression Investigation

Overview

This week, Jeff Layton's 24-patch VFS lease opt-in series — which had been fully applied in January and entered a quiet period through February — saw renewed activity when Mike Snitzer reported a potential regression. The discussion shifted from the architectural patch series to an investigation of a bug where lstat() returns -EINVAL on NFS reexported mounts, possibly triggered by the lease opt-in changes.

Classification

This week's activity represents a bug investigation rather than continuation of the original VFS protocol/architectural change discussion. The underlying concern is whether the newly applied lease opt-in mechanism (which makes ->setlease() returning -EINVAL when NULL) has inadvertently broken NFS reexport scenarios.

Prior Weeks Bridge

The 24-patch series by Jeff Layton was originally posted on January 8, requiring filesystems to explicitly opt-in to lease support via ->setlease(). The core change (patch 23/24) made kernel_setlease() return -EINVAL when ->setlease is NULL, replacing the previous default behavior of using an internal lease implementation. The series was applied to vfs-7.0.leases on January 12 and confirmed landed in jaegeuk/f2fs.git (dev) on February 17.

This Week: Bug Report Emerges

Mike Snitzer's Reproducer (February 25, referenced March 4)

Although Mike Snitzer's February 25 message appeared empty in metadata, Jeff Layton's response this week reveals it contained a reproducer demonstrating lstat() returning -EINVAL on an NFS reexported mount.

Jeff Layton's Analysis (March 4)

Jeff Layton responded on March 4, expressing surprise at the behavior:

"That's a very simple reproducer! That's very strange behavior, especially since NFS4 does provide a setlease operation:"

He noted that the NFSv4 client explicitly implements nfs4_setlease:

const struct file_operations nfs4_file_operations = {
    [...]
    .setlease       = nfs4_setlease,
    [...]
};

"I'm not sure why this would cause lstat() to return -EINVAL. What's happening on the wire when this occurs?"

Layton committed to investigating:

"I'll plan to take a look here soon either way."

Mike Snitzer's Follow-up (March 4)

Mike Snitzer replied, acknowledging the unexpected nature of the issue given nfs4_setlease exists:

"Huh, not sure how I missed nfs4_setlease..."

He also expressed uncertainty about the root cause:

"Likewise, especially given nfs4_setlease"

Snitzer noted he would revisit the issue but had been occupied with other work:

"I'll have to revisit myself, been a bit. Will let you know."

Jeff Layton's Testing (March 5)

Jeff Layton reported that he tested the reproducer on his own setup:

"Thanks. I just tested your reproducer. I have a nfsv4.2 mount on one host that is reexported, and mounted the reexport on a different host with '-o vers=4.1'."

The test succeeded for him:

$ touch /mnt/scratch/test ; ./lstat /mnt/scratch/test
Information for: /mnt/scratch/test
---------------------------
File Size:              0 bytes
Number of Links:        1
File inode:             272
File Type:              Regular File

He cautioned that his setup might differ from Snitzer's:

"It seems to work for me. It's possible I don't have something set up the same way though:"

Key Technical Arguments

  1. The -EINVAL return path: The lease opt-in series introduced a change where kernel_setlease() returns -EINVAL when ->setlease is NULL. If this error propagates unexpectedly to user-space operations like lstat(), it would indicate an issue in how the VFS handles lease-related errors during file operations.

  2. NFSv4 already has nfs4_setlease: The NFS client explicitly provides a ->setlease callback, so the NULL-checking change should not directly affect NFS mounts. The question is whether the reexport path (where an NFS mount is served as an NFS export) introduces a scenario where ->setlease could be NULL at some layer.

  3. Reexport complexity: NFS reexports involve multiple layers — the underlying NFS client mount and the NFS server export. The interaction between lease handling across these layers may expose edge cases not present in direct filesystem exports.

Final Conclusions

  • No definitive root cause identified this week. Jeff Layton could not reproduce the issue on his nfsv4.2-to-vers=4.1 reexport setup, suggesting environment-specific factors may be at play.
  • Investigation is ongoing. Both Layton and Snitzer acknowledged they need to dig deeper — Layton into wire-level behavior and Snitzer into reproducing with more context.
  • The lease opt-in series itself remains applied. This potential regression does not yet indicate a flaw in the architectural change, but rather an edge case that needs characterization.
  • NFS client development impact: If confirmed as a bug related to the lease changes, this would represent an important fix for NFS reexport scenarios. The NFS client's nfs4_setlease implementation should protect direct mounts, but reexports may traverse code paths where lease handling interacts with the new -EINVAL default in unexpected ways.
