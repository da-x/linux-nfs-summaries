OPENAT2_REGULAR: Error Code Consistency and NFS/SMB Testing Requirements

OPENAT2_REGULAR: Error Code Consistency and NFS/SMB Testing Requirements

Overview

This week, the discussion around Dorjoy Chowdhury's OPENAT2_REGULAR flag for openat2() (v4) moved from a state of silence to active technical review. Jeff Layton, a prominent kernel developer with deep expertise in VFS and network filesystems (NFS, CIFS), provided detailed feedback on the patch series. The discussion focused heavily on error code consistency, cross-filesystem testing (specifically NFS and SMB), and documentation requirements.

This is a new feature request aimed at improving security by allowing programs to explicitly require that opened paths are regular files. As noted in last week's summary, the patch touches multiple filesystems, including NFS, via updates to atomic_open codepaths.

Key Technical Arguments

Error Code Consistency: -EFTYPE vs. Specific Errors

A central theme of Layton's review was the inconsistency in error codes returned when OPENAT2_REGULAR is used on a non-regular file. The current patch returns -EFTYPE in some cases but falls back to -EISDIR or -ENOTDIR in others.

Layton argued for strict consistency:

"There are some places where it doesn't seem like -EFTYPE will be returned. It looks like it can send back -EISDIR and -ENOTDIR in some cases as well. With a new API like this, I think we ought to strive for consistency."

He highlighted specific code paths where the logic was flawed, such as during a create operation that races with a directory creation:

"If you do a create and race with a directory create, then it looks like you'll send back -EISDIR here instead of -EFTYPE?"

Chowdhury initially defended the mixed approach, citing a previous comment suggesting that indicating the specific file type (e.g., a pipe) might be useful. However, after Layton's pushback, Chowdhury agreed to standardize on -EFTYPE:

"Good point. I agree. I will fix this and return -EFTYPE for everything in the next posting."

Layton further justified this by noting that distinguishing between file types is less helpful if the caller explicitly expected a regular file:

"Sure, EISDIR tells you a bit more about the target, but that info is probably not that helpful if you were expecting it to be a regular file."

NFS and SMB Testing Requirements

Layton emphasized the need for broader testing beyond local filesystems like Btrfs. He specifically called out network filesystems:

"Your cover letter mentions that you only tested this on btrfs. At the very least, you should test NFS and SMB. It should be fairly easy to set up mounts over loopback for those cases."

Chowdhury expressed uncertainty about how to test these within his current virtme-ng setup:

"Is there a similar way I can test NFS/SMB by adding kselftests? Or would I need to setup NFS/SMB inside a full VM distro with a modified kernel to test this?"

Layton suggested using kdevops for such testing but acknowledged the complexity. This highlights a significant gap in the current patch series: lack of verified behavior on network filesystems, which is critical given that NFS and SMB have complex atomic_open implementations.

Documentation and Manpages

Layton pointed out that new APIs require thorough documentation in the manpages, which are maintained in a separate repository:

"Bear in mind that you'll need to document this in the manpages too."

He advised Chowdhury to CC the linux-api mailing list for future versions and provided the correct URL for the man-pages project. Chowdhury confirmed he would follow this guidance:

"I did not know about this. I will cc linux-api mailing list from the next posting."

Fstests Integration

Layton also recommended adding tests to xfstests (formerly known as fstests) to ensure robust coverage across different filesystems:

"You should add some tests to fstests for O_REGULAR if you haven't already."

Chowdhury noted he had only added a kselftest and asked for clarification on the submission process. Layton clarified that patches to manpages and xfstests can be submitted in parallel with the kernel patches, though they may not be merged until the kernel changes are accepted:

"No, you can submit them in parallel, but they probably won't get merged until the kernel patches go in."

Evolution of the Discussion

The discussion evolved from a simple ping for review to a detailed technical critique. Key milestones include:

  1. Initial Ping: Chowdhury requested review on the v4 series in his opening message.
  2. Layton's Review: Layton provided comprehensive feedback on error codes, testing, and documentation in his response.
  3. Clarification and Agreement: Chowdhury agreed to standardize on -EFTYPE and commit to testing NFS/SMB in his reply.
  4. Process Guidance: Layton provided guidance on manpages, xfstests, and mailing list etiquette in subsequent messages.

Final Conclusions

As of this week, the OPENAT2_REGULAR patch series has received its first substantive review. The key takeaways are:

  1. Error Code Standardization: The patch will be updated to return -EFTYPE consistently for all non-regular file cases, simplifying the API and ensuring predictable behavior across filesystems.
  2. NFS/SMB Testing Gap: Chowdhury has committed to testing the patch on NFS and SMB, which is critical for validating the atomic_open changes in these network filesystems. This addresses a significant risk area for NFS client development.
  3. Documentation and Testing: The developer will submit parallel patches for manpages and xfstests, ensuring proper documentation and broader test coverage.

The discussion underscores the importance of rigorous testing and consistent error handling when introducing new system call flags, particularly those that impact network filesystems like NFS.
