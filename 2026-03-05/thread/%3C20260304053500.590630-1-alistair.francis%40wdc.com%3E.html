NVMe-TCP TLS KeyUpdate Support and Handshake Infrastructure Enhancements

Summary

This week, Alistair Francis submitted version 7 of a five-patch series introducing support for receiving TLS 1.3 KeyUpdate requests in NVMe-TCP [PATCH v7 0/5]. While primarily targeting NVMe-oF, the series also enhances the underlying kernel TLS handshake infrastructure, which is shared with NFS over TLS implementations via SunRPC.

Feature Overview and Motivation

The TLS 1.3 specification (RFC 8446) permits clients or servers to initiate a KeyUpdate, typically when sequence numbers approach overflow or after significant data encryption. As Western Digital's upcoming NVMe-TCP hardware controllers implement this behavior, the Linux kernel must handle these events gracefully to prevent connection aborts. The series builds upon existing EKEYEXPIRED detection mechanisms, allowing the kernel to forward KeyUpdate requests to userspace (e.g., ktls-utils). Userspace can then restore session state from the keyring and update keys without dropping the connection.

Technical Implementation and NFS-Relevant Infrastructure

The patch series introduces several structural changes to the net/handshake subsystem:

  • Key Serial Persistence: Patch 1/5 allows userspace to include a key serial number during handshake completion. This serial is stored and returned to userspace during KeyUpdate events, enabling session correlation. Notably, this infrastructure update modifies net/sunrpc/svcsock.c and net/sunrpc/xprtsock.c, ensuring that NFS/RDMA/TLS stacks benefit from the same robust key management capabilities [PATCH v7 1/5].
  • Reusing Handshake Context: A new function, handshake_req_keyupdate, reuses the existing handshake request from the initial connection setup rather than creating a new one, optimizing resource usage [PATCH v7 2/5].
  • NVMe-TCP Integration: Patches 4/5 and 5/5 integrate this logic into the NVMe host and target drivers, respectively, handling EKEYEXPIRED returns by triggering the handshake callback rather than failing I/O [PATCH v7 4/5].

Review Discussion and Conclusions

The discussion focused on the robustness of TLS record handling in the NVMe host driver (Patch 4/5). Hannes Reinecke reviewed the implementation and suggested simplifying the control flow for unhandled TLS records.

"I think a simple 'if' condition would be sufficient here, or do you have handling of other TLS record types queued somewhere? And we should log unhandled TLS records." Hannes Reinecke

Alistair Francis agreed with the simplification, noting it would facilitate future extensibility:

"I like this approach as it makes it really easy to handle more types in the future. I don't have any more record types queued anywhere so I can change it to an if statement." Alistair Francis

However, Hannes raised a critical security concern in a follow-up message. Since the KeyUpdate handling is now decoupled from the main state machine as a simple callback, unhandled TLS records (such as TLS Alerts) might be ignored rather than causing a connection reset.

"This is now a simple callback, and doesn't influence the main state machine. In particular, we do not reset the connection... if we received an unhandled TLS record. I guess we should be doing that nevertheless, as unhandled TLS records also will include things like TLS Alert which really require us to reset the connection." Hannes Reinecke

Final Status

The thread concludes with an agreement to simplify the record type checking and add logging for unhandled records. The open item for the next revision is to ensure that critical unhandled TLS records, such as Alerts, properly trigger a connection reset to maintain security integrity. This feature represents a significant step toward production-ready NVMe-TCP over TLS support in the Linux kernel.
