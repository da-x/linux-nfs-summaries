svcrdma v2: 18-Patch Performance Scalability Series Submitted

Summary

Chuck Lever submitted version 2 of his "svcrdma performance scalability enhancements" series this week, expanding from the 15-patch RFC submitted two weeks ago to an 18-patch formal submission PATCH v2 00/18. The series targets the NFS server-side RDMA transport (svcrdma) and aims to lower per-connection resource utilization, reduce lock contention, and decrease interrupt/doorbell rates as connection counts scale.

This is a performance optimization series (not a new feature or protocol change), rebased onto v7.0-rc1. No replies were received within this week's window.

Changes Since RFC

Lever outlined several key improvements over the RFC version:

"Changes since RFC: Rebase on v7.0-rc1; Address thundering herd in SQ fairness implementation; Release Send contexts during xpo_release_ctxt; Skip xpt_reserved accounting for RDMA; Close several races." Chuck Lever

The series grew from 15 to 18 patches, with three new patches added in the sunrpc layer to eliminate spurious transport enqueue attempts and unnecessary atomic accounting overhead.

Key Technical Arguments

Profiling-Driven Bottleneck Identification

Lever's motivation stems from profiling an 8KB NFSv3 read/write workload over RDMA, which revealed where overhead accumulates as connection count grows:

"Roughly 4% of total CPU time goes to contention on the svcrdma_wq unbound workqueue pool lock, driven by cascading work item re-queues through the Send completion path. Receive completion processing acquires a per-transport spinlock on every inbound message. Doorbell and completion event counts scale with Write chunk usage." Chuck Lever

Additionally, svc_alloc_arg() scans approximately 259 rq_pages slots per receive even when only a few pages need replacement.

Three Recurring Strategies

1. Lock-Free Lists Replace Spinlock-Protected Queues

Patches 07/18 and 08/18 convert the receive completion queue (sc_rq_dto_q) and Read completion queue (sc_read_complete_q) to use llist (lock-free lists). This eliminates producer-side locking entirely on the hottest paths:

"The lock remains for sc_read_complete_q, but the primary hot path (receive completion and consumption) no longer requires it. This eliminates producer-side contention entirely." Chuck Lever

With both queues converted, the sc_rq_dto_lock spinlock is removed entirely from the receive and Read completion paths.

2. Send Context Release Deferred to nfsd Thread

Patch 10/18 replaces the global svcrdma_wq workqueue with a per-transport lock-free list. The Send completion handler appends send contexts to sc_send_release_list without further teardown. The nfsd thread drains this list in xpo_release_ctxt between RPCs, performing DMA unmapping and resource release in batch:

"This eliminates both the workqueue pool lock and the DMA unmap cost from the Send completion path. DMA unmapping can be expensive when an IOMMU is present in strict mode, as each unmap triggers a synchronous hardware IOTLB invalidation." Chuck Lever

Patch 09/18 further removes the intermediate re-queue for write chunk resource release, freeing these resources inline during send context teardown.

3. Work Request Chaining and Doorbell Reduction

Patch 04/18 links Write chunk RDMA Write WRs onto the RPC Reply's Send WR chain, so a single ib_post_send() covers both operations with one completion event:

"A single completion event signals that all operations have finished. This reduces both doorbell rate and completion rate, as well as eliminating the latency of a round-trip between the Write chunk completion and the subsequent Send WR posting." Chuck Lever

Patch 11/18 switches Receive Queue posting from small fixed batches to watermark-triggered bulk replenishment, provisioned at twice the negotiated credit limit. For a typical configuration with 128 credits, this means ~128 Receives per posting rather than frequent small batches.

4. Fair Queuing for Send Queue Access (Thundering Herd Fix)

Patch 01/18 introduces a ticket-based fair queuing system for Send Queue slot allocation. A notable improvement since RFC addresses the thundering herd problem:

"This separation ensures that send completions (the high-frequency wake source) wake only the current ticket holder rather than all queued waiters." Chuck Lever

The implementation uses two atomic counters (sc_sq_ticket_head and sc_sq_ticket_tail) and a dedicated wait queue for ticket ordering, separate from the SQ capacity wait queue.

5. Eliminating Spurious Transport Enqueue Attempts

Three new patches (13/18, 15/18, and 16/18) address a significant source of wasted CPU cycles. Trace data from a 256KB NFSv3 WRITE workload revealed:

"approximately 14 enqueue attempts per RPC, with 62% returning immediately due to no pending work." Chuck Lever

Patch 14/18 adds a retry mechanism when receive queues drain transiently, noting:

"Trace data from a 256KB NFSv3 workload over RDMA shows 267,848 of 464,355 transport dequeues (57.7%) are these empty bounces. Each bounce costs roughly 37 us. During the READ phase, empty bounces consume 8.6% of thread capacity and inflate inter-RPC gaps by an average of 87 us." Chuck Lever

Patch 18/18 skips xpt_reserved accounting for non-UDP transports (TCP and RDMA), eliminating measurable dead overhead:

"At 257K ops/sec over NFS/RDMA, this is measurable dead overhead." Chuck Lever

6. Cache Line Separation and Per-Object Caching

Patch 06/18 uses ____cacheline_aligned_in_smp annotations to separate frequently modified fields in struct svcxprt_rdma into distinct cache lines, reducing false sharing between the Send context cache, R/W context cache, and SQ availability counter.

Patch 12/18 adds a per-recv_ctxt single-entry cache for svc_rdma_chunk structures:

"Over 99% of RPC Calls that specify RPC/RDMA chunks provide only a single chunk, so a single cached chunk handles the common case." Chuck Lever

Evolution and Conclusions

This v2 submission builds directly on the RFC from two weeks prior, incorporating fixes for identified issues (thundering herd in SQ fairness, race conditions) and expanding the scope to include sunrpc-layer optimizations that eliminate spurious dispatches. The series touches 11 files with 582 insertions and 267 deletions.

The code is available in Lever's svcrdma-next branch at: https://git.kernel.org/pub/scm/linux/kernel/git/cel/linux.git/log/?h=svcrdma-next

No discussion or review comments were received within this week's window. The series represents a comprehensive, profiling-driven optimization effort for the NFS server-side RDMA transport, with particular focus on reducing lock contention, doorbell rates, and CPU cache invalidation traffic under high-scale workloads.
