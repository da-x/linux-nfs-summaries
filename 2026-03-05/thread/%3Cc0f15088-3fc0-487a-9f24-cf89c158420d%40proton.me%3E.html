NFSD Regression: ENOLCK on Read-Only Files and NLM Lock Semantics

Summary

NFSD Regression: -ENOLCK on Read-Only Files via NLM

This week’s discussion centered on a regression introduced by commit 4cc9b9f2bf4d ("nfsd: refine and rename NFSD_MAY_LOCK"), which causes NFS clients to receive -ENOLCK (No locks available) when attempting to acquire exclusive locks on read-only files (e.g., ISO images) using the Network Lock Manager (NLM).

Verification of Persistence

The thread confirmed that the issue persists across multiple kernel versions. Thorsten Leemhuis noted that the stable backport 18744bc56b0ec corresponds to the upstream commit and asked if mainline kernels were affected. Salvatore Bonaccorso confirmed the regression is reproducible in kernel 6.19.5:

"Not tested 7.0-rc2, but the issue is reproducible still in 6.19.5."

Technical Root Cause

Olga Kornievskaia explained that the failure occurs when a user lacks write permissions on a file while the server uses auth_nlm. She referenced prior discussions indicating that flock should fail under these conditions unless specific export policies are used:

"I suspect that this occurs when the user running flock does not have write access to the file it's trying to get an exclusive lock on... Change export policy to no_auth_nlm if it's desired that flock gets an exclusive lock on a file without write permissions."

Sasha Levin, via an AI-generated analysis, detailed the root cause: commit 4cc9b9f2bf4d removed a permission downgrade in nfsd_permission() that previously changed lock request checks from MAY_WRITE to MAY_READ. This removal caused inode_permission(MAY_WRITE) to fail for read-only files. The analysis proposed restoring the downgrade:

"The fix is to restore the permission downgrade for NFSD_MAY_NLM in nfsd_permission()... This restores the 'else' branch behavior that was lost in 4cc9b9f2bf4d."

Debate on Correctness vs. Regression

NeilBrown, the author of the original commit, argued that the current behavior is technically correct due to the mapping of flock to fcntl locks over NLM. He explained:

"exclusive flock locks only require read access to the file... exclusive fcntl locks require write access to the file... So if you open a file on NFS read-only and attempt an exclusive flock, that will be sent to the server as a full-range fcntl lock which should require write access."

He suggested workarounds such as using local_lock=flock or ensuring clients request shared locks for read-only files:

"It would seems to make sense to tell qemu that the device is read-only. Then it will hopefully only request a shared lock... I think that the current behaviour is correct, however I do understand that it is a regression and maybe that justifies incorrect behaviour."

Conclusion

The discussion highlighted a tension between backward compatibility and semantic correctness in NFS locking. While the regression breaks existing workflows for read-only files, NeilBrown contends that the new behavior aligns with POSIX fcntl semantics. No definitive patch was agreed upon this week, but users were advised to adjust export policies or mount options to mitigate the issue.
