netfs: RFC to replace folio_queue with segmented bio_vec chains (bvecq)

Summary

David Howells Proposes bvecq to Replace folio_queue in netfslib

This week, David Howells submitted a significant RFC patch series aimed at refactoring the buffer management subsystem within netfslib. The 17-patch series introduces a new construct, bvecq (a segmented chain of bio_vec[] arrays), to replace the existing folio_queue, rolling_buffer, and ITER_FOLIOQ mechanisms.

Key Technical Arguments

Howells outlined three primary motivations for this architectural shift:

  1. Kernel I/O Consolidation: The kernel file I/O subsystem is trending toward bio_vec[] arrays; moving netfslib to this model aligns it with broader kernel developments.
  2. Unified Buffering Scheme: netfslib already uses bio_vec[] for unbuffered/Direct I/O (DIO). This change reduces the number of distinct buffering schemes from multiple to one.
  3. TCP Efficiency: The new design enables sending entire filesystem RPC request messages via a single kernel_sendmsg() call, avoiding corking and improving performance by keeping the transmission loop within a single tcp_sendmsg().

The proposed struct bvecq includes features such as:

  • Linked segments (next, prev) allowing arbitrary gluing of buffer bits.
  • File position tracking (fpos) and discontiguity flags to manage non-contiguous file spaces.
  • Reference counting for safe sharing of buffer slices among subrequests.
  • An associated iterator type, ITER_BVECQ, intended to replace ITER_FOLIOQ.

"These patches get rid of folio_queue, rolling_buffer and ITER_FOLIOQ, replacing the folio queue construct used to manage buffers in netfslib with one based around a segmented chain of bio_vec arrays instead." — David Howells

Important Bug Fix: Strict Sequencing for DIO Writes

Embedded within the refactoring is a critical bug fix in Patch 01/17. Howells addressed an issue where unbuffered/DIO writes could dispatch subrequests out of order, potentially leaving data holes if an error (e.g., ENOSPC) occurred mid-operation.

"Fix netfslib such that when it's making an unbuffered or DIO write, to make sure that it sends each subrequest strictly sequentially, waiting till the previous one is 'committed' before sending the next so that we don't have pieces landing out of order and potentially leaving a hole if an error occurs (ENOSPC for example)." — David Howells

The fix ensures that each subrequest waits for the previous one to complete before proceeding, simplifying retry logic and preventing data corruption.

Controversy: Use of FIEMAP in the Data Path

A significant point of contention arose regarding Patch 02/17, which implemented a kernel-internal FIEMAP callback. Howells proposed using FIEMAP to allow cachefiles (and potentially knfsd/ksmbd) to determine data extents remotely, replacing SEEK_DATA/SEEK_HOLE.

Christoph Hellwig strongly objected to this approach:

"Hell no. FIEMAP is purely a debugging tool and must not get anywhere near a data path. NAK to all of this." — Christoph Hellwig

Hellwig expanded on his concerns in response to Patch 17/17, which detailed how the cache would query occupied regions using FIEMAP. He highlighted a fundamental correctness issue:

"Independent of fiemap or not, how is this supposed to work? File systems can create speculative preallocations any time they want, so simply querying for holes vs data will corrupt your cache trivially." — Christoph Hellwig

Conclusion

The RFC series represents a major overhaul of netfslib's internal buffer management, promising greater efficiency and code consolidation. However, the reliance on FIEMAP for cache extent discovery has been met with strong resistance from Christoph Hellwig, who cites both architectural principles (FIEMAP as a debug tool) and correctness concerns (speculative preallocations).

As of this week's window, no resolution to the FIEMAP controversy has been reached. The series remains in RFC status, with Howells noting that future work should transition to a "block-fs metadata-independent way of tracking" cache extents. NFS client developers should monitor this thread closely, as the bvecq infrastructure will impact how NFS interacts with netfslib for both buffered and direct I/O operations once the FIEMAP dependency is resolved or removed.
