NFS Unmount Notification: Kernel Callbacks vs. exportfs -F

Summary

This week's discussion concluded the exploration of kernel-side mechanisms to notify NFSD when an underlying filesystem is unmounted, a feature intended to resolve NFSv4 unmount hangs caused by outstanding delegations and locks. After last week's pivot from VFS notifier chains to a userspace exportfs -F solution, Jan Kara and Jeff Layton weighed in on alternative kernel callbacks. Their exchange confirmed that existing superblock operations are insufficient for this use case, reinforcing the consensus that a userspace-driven approach via exportfs is the most pragmatic path forward.

Key Technical Arguments

The Limitation of ->umount_begin

Jan Kara suggested that if the proposed exportfs -F option proved unworkable, the existing ->umount_begin superblock callback could potentially be adapted to provide the necessary notification:

"If this option flies, then I guess it is the most sensible variant. If it doesn't work for some reason, then something like ->umount_begin sb callback could be twisted (may possibly need some extension) to provide the needed notification? At least in my naive understanding it was created for usecases like this..." Jan Kara

Jeff Layton quickly clarified why ->umount_begin is unsuitable for this problem. The callback only fires when MNT_FORCE (force unmount) is specified, whereas the desired behavior should apply to normal administrative unmounts after an unexport. More importantly, he noted that the notification needs to target NFSD, not the filesystem being unmounted:

"umount_begin is a superblock op that only occurs when MNT_FORCE is set. In this case though, we really want something that calls back into nfsd, rather than to the fs being unmounted." Jeff Layton

A Preferred Callback Architecture

Jeff proposed a more elegant kernel-side alternative: a callback mechanism that NFSD could register to run just before umount_begin, which would allow proper state teardown during force unmounts as well. He argued this would be superior from a user interface perspective compared to introducing new exportfs options:

"Maybe you could add some sort of callback that nfsd could register that runs just before umount_begin does? That would be preferable from a UI standpoint than dealing with a new exportfs option, IMO. MNT_FORCE could then (in theory) properly allow for state teardown in nfsd that way, which seems rather natural." Jeff Layton

Evolution of the Discussion

The broader thread, as summarized in prior weeks, began with Chuck Lever's patch series proposing a VFS umount notifier chain to allow NFSD to revoke NFSv4 state (opens, locks, delegations) when a filesystem is unmounted. The discussion revealed fundamental timing flaws: both SRCU notifiers and fsnotify FS_UNMOUNT events fire only after all file references are closed, but NFSD holds files open while state is outstanding, creating a circular dependency that causes unmount to hang with EBUSY.

Last week, the consensus shifted toward a userspace solution: adding a -F flag to exportfs -u that explicitly instructs NFSD to release all locks and close all state on the filesystem before completing the unexport. Chuck Lever agreed this would meet his needs and could leverage the existing "unlock filesystem" API as noted last week.

This week's contributions from Jan Kara and Jeff Layton represent final kernel-side considerations. While Jeff's proposed NFSD-registered callback is architecturally appealing, it would still require kernel changes to the VFS unmount path. Given that the exportfs -F approach can be implemented by teaching exportfs to invoke the existing "unlock filesystem" API after unexporting—leaving the kernel largely untouched—the userspace solution remains the most expedient path forward.

Final Conclusions

Discussion Type: This is primarily a bug fix / feature enhancement discussion aimed at resolving NFSv4 unmount hangs when clients hold outstanding state (delegations, locks). It involves both protocol semantics (NFSv4 state management) and VFS infrastructure considerations.

Status: The kernel-side patch series adding umount notifiers appears stalled due to timing constraints. The preferred path forward is:

  1. Short-term: Implement exportfs -F (or similar) to explicitly flush NFSD state after unexport, leveraging the existing "unlock filesystem" API. This requires no kernel changes beyond potentially exposing or refining that API.

  2. Long-term (optional): Jeff Layton's suggestion of an NFSD-registered callback running before umount_begin could enable proper state teardown during MNT_FORCE unmounts, but this is not immediately necessary for the core use case.

The remaining open question from last week—whether state revocation should be the default behavior of exportfs -u or require an explicit flag—has not been resolved and requires input from the linux-nfs@ review committee. NeilBrown argued that automatic revocation could break users relying on undocumented NFSv4 state persistence after unexport, while Chuck Lever noted that some administrators expect "unexport followed by unmount" to work seamlessly as it did in NFSv3.
