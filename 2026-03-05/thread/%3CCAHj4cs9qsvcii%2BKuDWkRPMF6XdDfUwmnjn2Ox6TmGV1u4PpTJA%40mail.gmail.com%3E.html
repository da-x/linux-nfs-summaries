blktests udev Timeout Traced to nfsrahead Latency Regression in nfs-utils

Summary

blktests Failures Traced to nfsrahead udev Rule Latency Regression

Classification: Bug Fix / nfs-utils User-Space Issue

This week, Red Hat's Yi Zhang provided a root-cause analysis for a widespread test infrastructure failure affecting the Linux NFS community. The thread addresses a bug report titled "[bug report] Most blktests block/ failed with 'Timed out while waiting for udev queue to empty.'" — a system-wide timeout error that was disrupting block-layer testing environments.

Background

The blktests suite, used extensively for validating block layer functionality in the Linux kernel, began failing en masse with udev queue exhaustion errors. The symptom was a system-wide "Timed out while waiting for udev queue to empty" message, indicating that the systemd-udevd daemon's worker threads were saturated and unable to process device events within the expected timeframe.

Root Cause Analysis

In his analysis posted on March 5 Yi Zhang, Yi Zhang traced the problem to a regression in nfs-utils, specifically in the behavior of the nfsrahead binary invoked by udev rules.

"After analyzing the systemd-udevd logs I found that the udev rule /usr/lib/udev/rules.d/99-nfs.rules triggers /usr/libexec/nfsrahead for every new block device."

The core issue is a dramatic increase in latency for non-NFS devices:

"In the current version, this binary takes exactly 10 seconds to return an exit code 2 for non-NFS devices. This latency, multiplied by thousands of test-generated events, exhausts udev worker threads and blocks the event queue, leading to the system-wide 'Timed out while waiting for udev queue to empty' error."

By contrast, the previous version of nfsrahead returned much more quickly:

"In the previous version, the binary /usr/libexec/nfsraheadprevious returns exit code 2 in 1 second."

Version Comparison

Yi Zhang provided detailed udev logs comparing two versions of nfs-utils:

PackageBehavior
nfs-common-utils-2.8.4-4.rc3.fc44 (nfs-utils 2.8.5-rc3)Returns exit code 2 in ~1 second
nfs-common-utils-2.8.5-0.rc3.fc44 (nfs-utils 2.8.6-rc3)Returns exit code 2 in ~10 seconds

The logs clearly show the 10-second delay: the command is started at Mar 04 06:07:14 but does not fail until Mar 04 06:07:24, a full 10 seconds later. During this time, udev worker threads are blocked, and subsequent device events (such as nullb0 removal and re-addition) queue up behind the stalled nfsrahead invocation.

Identified Regression Source

Yi Zhang identified the specific commit responsible for the regression in the nfs-utils repository:

"After checking the changelog for the latest nfs-utils, seems it was introduced from commit 2b62ac4c273a647df07400dc1126fceb76ad96c0."

This commit, authored by Steve Dickson (steved), is in the upstream nfs-utils tree and introduced a behavioral change that increased the timeout for non-NFS device detection from 1 second to 10 seconds.

Impact on NFS Client Development

While this is technically an nfs-utils user-space issue rather than a kernel NFS client bug, it has significant implications for NFS client development and testing:

  1. Test Infrastructure Reliability: The blktests suite is critical for validating block layer changes that may interact with NFS over block devices (e.g., NFS over RDMA, pNFS block layouts). Widespread test failures obscure real bugs and slow down development cycles.

  2. udev Integration: The 99-nfs.rules udev rule is designed to automatically configure read-ahead settings for NFS-backed block devices via the nfsrahead helper. The regression demonstrates how user-space tooling changes can have cascading effects on system stability, particularly in high-throughput testing scenarios where thousands of virtual block devices are created and destroyed rapidly.

  3. Performance Sensitivity: The 10x increase in latency (from 1s to 10s) for non-NFS devices is particularly problematic because the vast majority of block devices on a system are not NFS-backed. This means the regression affects nearly all device events, not just NFS-related ones.

Current Status

As of this week's activity, Yi Zhang has completed the root-cause analysis and identified the offending commit. No patch or resolution was posted in this window. The next steps would likely involve:

  • Upstream nfs-utils maintainers (notably Steve Dickson) reviewing the regression
  • A potential fix to reduce the timeout for non-NFS devices back to 1 second, or implementing a faster detection mechanism
  • Distribution packagers (e.g., Fedora, given the .fc44 package references) applying backports

Key Takeaway

"This latency, multiplied by thousands of test-generated events, exhausts udev worker threads and blocks the event queue."

This quote from Yi Zhang encapsulates the fundamental problem: a seemingly minor change in user-space tooling (a 9-second increase in timeout) can have disproportionate system-wide effects when invoked at scale through udev rules. For NFS client developers, this underscores the importance of ensuring that nfs-utils components remain performant and non-disruptive, even when operating on non-NFS devices.
