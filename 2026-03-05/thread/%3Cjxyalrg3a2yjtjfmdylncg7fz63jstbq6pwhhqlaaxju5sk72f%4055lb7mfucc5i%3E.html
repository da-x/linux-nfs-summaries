NFS Unmount Notification: Kernel Callback Complexity Reinforces Userspace Path

Summary

This week's discussion on the umount notifier chain for NFSD state revocation deepened the technical analysis of why a VFS-level notification mechanism is problematic. After prior weeks' exploration revealed that both SRCU notifiers and fsnotify events fire too late to resolve NFSv4 unmount hangs, Jan Kara, Jeff Layton, NeilBrown, and Christian Brauner examined the remaining kernel-side options. Their exchange confirmed that determining when to drop NFSD state in a race-free manner is exceptionally complex, reinforcing the consensus that a userspace-driven solution via exportfs is the most pragmatic path forward.

Key Technical Arguments

The Race Condition Problem with "Last Unmount" Detection

Jan Kara identified a fundamental difficulty with any VFS-based notification approach: determining whether an unmount represents the last reference to a superblock is impossible to do in a race-free manner before acquiring namespace_lock():

"Thinking about this more - Chuck was also writing about the problem of needing to shutdown the state only when this is the last unmount of a superblock but until we grab namespace_lock(), that's impossible to tell in a race-free manner? And how about lazy unmounts? There it would seem to be extra hard to determine when NFS needs to drop it's delegations since you need to figure out whether all file references are NFS internal only? It all seems like a notification from VFS isn't the right place to solve this issue..." Jan Kara

This observation highlights two distinct challenges:

  1. Race-free detection: The kernel cannot determine if an unmount is the final one until after locking, at which point it may be too late to revoke state before EBUSY is returned.
  2. Lazy unmounts (MNT_DETACH): With lazy unmounts, the vfsmount is detached immediately but cleanup occurs later, making it even harder to determine when NFSD should release its delegations.

Jeff Layton's Defense of the Unmount Trigger

Jeff Layton articulated why unmount remains the most natural trigger for state revocation from an administrator's perspective:

"The issue is that traditionally, 'exportfs -u' is what unexports the filesystem and at that point you can (usually) unmount it. We'd ideally like to have a solution that doesn't create extra steps or change this, since there is already a lot of automation and muscle memory around these commands." Jeff Layton

He contrasted NFSv3, which has no long-term state (aside from lockd), with NFSv4, where NFSD holds files open for extended periods:

"With v4 that changed and nfsd holds files open for much longer. We can't drop all the state when fs is unexported, as it's not uncommon for it to be reexported soon afterward, and we can't force a grace period at that point to allow reclaim." Jeff Layton

Jeff acknowledged that if no VFS hook could be added, he would understand — but emphasized the desirability of a kernel-side solution for this use case:

"If we can't add some sort of hook to the umount path, then I'll understand, but it would be a nice to have for this use-case." Jeff Layton

NeilBrown's Argument Against Kernel-Side Guessing

NeilBrown offered a nuanced critique, arguing that targeting the "last unmount" of a superblock is the wrong abstraction. Instead, he suggested NFSD should consider dropping state when a specific vfsmount is being considered for unmount:

"I think it could be appropriate to drop nfsd state when the vfsmount is being considered for unmount - including lazy unmount - whether the superblock has other mounts or not." NeilBrown

However, he concluded that implementing this dependency correctly would be "messy" and advocated for explicit userspace control:

"I think it would be messy to get this dependency correct. i.e. I think that guessing, in the kernel, what the user wants is problematic. I think giving the user the tools to say exactly what they want is best." NeilBrown

Christian Brauner's Agreement

Christian Brauner concurred with NeilBrown's assessment, endorsing the principle of explicit userspace control over implicit kernel-side behavior:

"Very much agree." Christian Brauner

Evolution of the Discussion

This thread, originally initiated by Chuck Lever's patch series proposing a VFS umount notifier chain, has evolved through several stages:

  1. Prior weeks: Discovery that SRCU notifiers and fsnotify FS_UNMOUNT events fire too late (after all files are closed), creating a circular dependency with NFSD-held file references.
  2. Last week: Pivot toward a userspace solution via exportfs -F, with debate over whether state revocation should be default or opt-in.
  3. This week: Deep technical analysis confirming that kernel-side notification mechanisms face insurmountable complexity due to race conditions, lazy unmount semantics, and the difficulty of determining "last unmount" status in a lock-free manner.

Final Conclusions

Discussion Type: This is primarily a bug fix / feature enhancement discussion aimed at resolving NFSv4 unmount hangs caused by outstanding client state (delegations, locks, opens). It touches on protocol semantics (NFSv4 state management), VFS infrastructure, and userspace tooling.

Status: The kernel-side patch series adding umount notifiers remains stalled. This week's exchange solidified the consensus that:

  1. VFS-level notifications are fundamentally flawed for this use case due to race conditions in determining "last unmount" status and complications with lazy unmounts.
  2. A userspace solution via exportfs -F (or similar) remains the most pragmatic path forward, leveraging the existing "unlock filesystem" API without requiring kernel VFS changes.
  3. Explicit user control is preferred over implicit kernel-side guessing, as endorsed by both NeilBrown and Christian Brauner.

The remaining open question — whether state revocation should be the default behavior of exportfs -u or require an explicit flag — has not been resolved and requires input from the linux-nfs@ review committee.
