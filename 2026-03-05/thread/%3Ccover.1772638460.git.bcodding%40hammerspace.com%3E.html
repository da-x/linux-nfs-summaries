nfs-utils: Signed Filehandle Userspace Support (v7)

Summary

This week, Benjamin Coddington posted version 7 of the nfs-utils patch series to provide userspace support for the kernel-side signed filehandle feature. This is a new feature — a security enhancement that prevents filehandle guessing attacks by appending an 8-byte SipHash Message Authentication Code (MAC) to NFS filehandles on selected exports.

The kernel-side counterpart was applied to nfsd-testing last week (v7 kNFSD patches), and this userspace series completes the end-to-end story, enabling administrators to configure and activate signed filehandles through standard NFS administration tools.

Background (Prior Weeks)

The signed filehandle feature has evolved over many iterations since January 2026. The core motivation, as Coddington explained, is that NFS filehandles are often "well-formed" and easy to guess:

"Filehandles are easy to guess because they are well-formed... You can simply insert inode numbers and iterate on the generation number. Eventually you'll be able to access the file using open_by_handle_at(2)."

The kernel-side patches (v7) were applied by Chuck Lever to nfsd-testing in the prior week, implementing SipHash-2-4 signing of filehandles and a new sign_fh export option within the kernel. The userspace patches had progressed through v1–v6 over several weeks, with feedback from NeilBrown (who contributed the missing fh_key_file.c implementation in v1), Jeff Layton (who suggested adding the -k/--fh-key-file argument to nfsdctl threads and failing gracefully if unsupported by the kernel), and others.

This Week's Activity

On 2026-03-04, Coddington posted the v7 two-patch series for nfs-utils:

Patch 1/2: exportfs — Add support for export option sign_fh

This patch adds the sign_fh export option to exportfs, allowing administrators to flag individual exports for filehandle signing:

"If configured with 'sign_fh', exports will be flagged to signal that filehandles should be signed with a Message Authentication Code (MAC)."

The patch touches 4 files (support/include/nfs/export.h, support/nfs/exports.c, utils/exportfs/exportfs.c, and utils/exportfs/exports.man), adding the option parsing and documentation.

Patch 2/2: nfsdctl/rpc.nfsd — Add support for passing encrypted filehandle key

This patch implements the key management infrastructure:

"If fh-key-file=<path> is set in the nfsd section of nfs.conf, the 'nfsdctl autostart' command will hash the contents of the file with libuuid's uuid_generate_sha1 and send the first 16 bytes into the kernel on NFSD_A_SERVER_FH_KEY. A compatible kernel can use this key to sign filehandles."

Key aspects:

  • Creates a new support/nfs/fh_key_file.c module (63 lines) for hashing the key file contents
  • Adds -k, --fh-key-file=<path> option to the nfsdctl threads command
  • The secret key is derived as "the first 128 bits of a sha1 hash of the contents of a file configured via the nfs.conf server section 'fh_key_file'"

Version Changes

Coddington documented the incremental improvements leading to v7:

  • v5: Added -k,--fh-key_file= argument to nfsdctl threads and failure handling for unsupported kernels (per Jeff Layton's feedback)
  • v6: Fixed a premature exit from the fh-key-file hashing routine
  • v7: "fix another corner-case for hashing fh-key-file, simplify"

The series touches 13 files with 145 insertions and 10 deletions.

Conclusion

No replies were received within this week's window. The patches represent the final userspace component needed to operationalize signed filehandles in production NFS deployments. In a subsequent reply (outside this week's window), Steve Dickson confirmed the patches were committed to nfs-utils:

"Committed... (tag: nfs-utils-2-9-1-rc2)"

This completes the development cycle for the signed filehandle feature, providing administrators with an opt-in mechanism to harden NFS exports against filehandle guessing attacks while maintaining backward compatibility with existing clients.
