NFSv4 Unmount Hangs: From VFS Notifiers to exportfs -F

Summary

This week's discussion continued the exploration of mechanisms to automatically revoke NFSv4 state (opens, locks, delegations) when an underlying filesystem is unmounted. Last week, consensus emerged to use fsnotify with FS_UNMOUNT events instead of a custom SRCU notifier chain as summarized last week. However, this week Chuck Lever revealed a fundamental timing flaw in that approach, prompting a pivot toward userspace solutions involving exportfs.

Key Technical Arguments

The "Fatal Flaw" of Late-Firing Notifiers

Chuck Lever reported that both the original SRCU notifier and the proposed FS_UNMOUNT fsnotify events suffer from the same critical timing issue: they fire only after all files on the mount are closed. Because NFSD holds file references open while NFSv4 state (e.g., delegations) is outstanding, the unmount operation fails with EBUSY before the notifier can ever trigger to release that state.

"Turns out FS_UNMOUNT doesn't do what I need... The problem is that NFSD holds files open when there is outstanding NFSv4 state. So the SRCU notifier will never fire, on umount, to release that state." Chuck Lever

He explained that FS_UNMOUNT events are dispatched from fsnotify_sb_delete() inside generic_shutdown_super(), which runs only when s_active drops to zero — a condition that requires all mounts (and thus all NFSD-held files) to already be freed. This creates a circular dependency.

Proposed VFS Hook and Its Complications

Chuck proposed inserting a new notification hook directly in do_umount(), before propagate_mount_busy() checks for busy mounts:

"For any notification approach to actually do what is needed, it needs to fire during do_umount(), before propagate_mount_busy()." Chuck Lever

However, he acknowledged that such a hook would fire for every mount namespace teardown (not just admin-initiated unmounts), requiring NFSD to carefully filter notifications to avoid unintended state revocation.

Amir Goldstein suggested alternative VFS approaches, including subscribing to FS_MNT_DETACH events on the superblock or having NFSD use a private cloned mount (similar to overlayfs) to isolate its file references:

"One option is that nfsd will use a private mount clone for accessing files as overlayfs does and wait until all the other mounts are gone, but FWIW that has some user visible implications." Amir Goldstein

Amir also questioned whether svc_export_put() (called during unexport) could serve as the trigger for releasing NFSD resources, rather than waiting for unmount.

The User Story: Deterministic Unexport + Unmount

Chuck clarified the core user requirement:

"As a system administrator, I'd like to be able to unexport an NFSD share that is being accessed by NFSv4 clients, and then unmount it, reliably (for example, via automation). Currently the umount step hangs if there are still outstanding delegations granted to the NFSv4 clients." Chuck Lever

He noted that making "unexport" automatically revoke NFSv4 state had been previously proposed to linux-nfs@ but faced pushback, as some users rely on NFSv4 state persisting after unexport.

Pivot to Userspace: exportfs -F

NeilBrown suggested a simpler path: adding a -F flag to exportfs -u that explicitly instructs NFSD to release all locks and close all state on the filesystem before completing the unexport:

"Could we add a "-F" or similar flag to "exportfs -u" which implements the desired semantic? i.e. asking nfsd to release all locks and close all state on the filesystem." NeilBrown

Chuck agreed this would meet his needs and could leverage the existing "unlock filesystem" API, but noted it requires linux-nfs@ review:

"That meets my needs, but should be passed by the linux-nfs@ review committee." Chuck Lever

Debate: Default Behavior vs. Explicit Flag

The discussion then centered on whether state revocation should be the default behavior of exportfs -u or require an explicit flag:

  • Chuck's concern: Some users view the current NFSv4 behavior as a regression compared to NFSv3, where "unexport followed by unmount" worked seamlessly. Others might rely on undocumented behavior where NFSv4 state persists after unexport. He was uncertain which change would be least disruptive.

  • NeilBrown's position: Making cache purge the default is complex due to multiple exports, subtrees, and implicit crossmnt exports. He argued for an explicit action:

"So I think an explicit 'flush cache' exportfs action is simplest and best. Possibly: exportfs -F /some/path would unexport all exports which reference the same mountpoint, then would tell the kernel to drop all cached data for that mount." NeilBrown

Chuck reported that the original bug reporter preferred a fix that does not require changes in user behavior (i.e., automatic revocation). Neil countered:

"I think their preference, while understandable, is naive. They are doing something that is not documented as supported, is not actually supported, and has always had the possibility of failure." NeilBrown

Evolution and Conclusion

The discussion evolved from a VFS-level mechanism debate (last week's pivot to fsnotify) to the discovery that existing notification hooks fire too late to be useful for NFSD. After exploring a new do_umount() hook and private mount clones, the conversation shifted toward userspace solutions.

Final Status: No consensus was reached this week on whether state revocation should be automatic or opt-in via exportfs -F. The kernel-side patch series (adding umount notifiers) appears stalled due to the timing flaw. The expedient path forward identified by Chuck Lever is:

"It appears that the expedient path forward would be teaching exportfs to do an 'unlock filesystem' after it finishes unexporting, and leaving the kernel untouched." Chuck Lever

The remaining question is whether this behavior should be default or require an explicit flag, a decision that requires input from the linux-nfs@ review committee and consideration of backward compatibility for both NFSv3 and NFSv4 users.
