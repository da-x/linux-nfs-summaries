xprtrdma: Race Fixes and Refactoring for nconnect Scalability

Overview

This week, Chuck Lever submitted [PATCH v2 0/8] "Fix various races in xprtrdma" to the Linux NFS mailing list, an eight-patch series targeting the RDMA transport layer (xprtrdma) of the SUNRPC subsystem. The series addresses a combination of critical race conditions, performance bottlenecks, and code cleanup — all motivated by Lever's testing of the nconnect mount option with NFS/RDMA.

"Since commit b326df4a8ec6 ('NFS: enable nconnect for RDMA'), the nconnect mount option has been enabled on proto=rdma NFS mount points. Utilizing this option increases the IOPS throughput that an NFS mount point is capable of." — Chuck Lever

Lever explained that enabling nconnect "surfaces some subtle race conditions that are well-buried when there is only a single QP." The series therefore blends bug fixes (four patches addressing races and hangs) with performance enhancements and structural refactoring (four patches optimizing memory registration and receive buffer management).

Key Bug Fixes

1. Receive Counter Hang on Early Exit (Patch 1/8)

Contributed by Eric Badger of Pure Storage, this patch fixes a hang in rpcrdma_xprt_drain() that occurs under high memory pressure. When rpcrdma_post_recvs() fails to create a work request or exits early, the re_receiving counter was not decremented, causing the drain completion to never trigger:

"In the event that rpcrdma_post_recvs() fails to create a work request (due to memory allocation failure, say) or otherwise exits early, we should decrement ep->re_receiving before returning. Otherwise we will hang in rpcrdma_xprt_drain() as re_receiving will never reach zero and the completion will never be triggered." — Eric Badger

The patch fixes a regression introduced by commit 15788d1d1077 ("xprtrdma: Do not refresh Receive Queue while it is draining"). Lever appended a lighthearted note to this patch:

"Whoops, didn't mean to include this one because you should already have it. But, it shows that I am testing it." — Chuck Lever

2. Send Context Race Blocking Transport (Patch 2/8)

This patch closes a race between rpcrdma_sendctx_get_locked() and rpcrdma_sendctx_put_locked() that can permanently set the XPRT_WRITE_SPACE flag, blocking all further sends on a transport:

"After the sender releases XPRT_LOCKED, the release path refuses to wake the next task because XPRT_WRITE_SPACE is set. The sender retries, finds XPRT_WRITE_SPACE still set, and sleeps on xprt_sending. No further Send completions arrive to clear the flag because no new Sends can be posted." — Chuck Lever

With nconnect, this is particularly dangerous: "the stalled transport's share of congestion credits are never returned, starving the remaining transports as well."

3. Lost-Wakeup Race in Slot Allocation (Patch 4/8)

A race existed between xprt_rdma_alloc_slot() and xprt_rdma_free_slot() where a buffer freed after the pool was found empty but before a task joined the backlog would be returned to the pool with no waiter to wake. The fix re-checks the pool after joining the backlog and uses xprt_add_backlog_noncongested() to ensure every allocation reaches the proper re-check path.

4. Unnecessary 250 ms Delay on Backlog Wakeup (Patch 3/8)

A prior commit set tk_status to -ENOMEM in xprt_rdma_alloc_slot(), causing tasks woken from the backlog to sleep for HZ/4 (~250 ms) before retrying — even though a slot was already available. Lever noted:

"a task woken from the backlog has a slot waiting for it, so the 250 ms rpc_delay adds latency without benefit." — Chuck Lever

Performance and Structural Enhancements

Decoupling Write-Pad Registration (Patch 5/8)

The write-pad MR registration (frwr_wp_create) was decoupled from the general frwr_map function by inlining the registration logic. This simplifies error handling and prepares for the removal of the rpcrdma_mr_seg intermediate structure.

Replacing rpcrdma_mr_seg with xdr_buf Cursor (Patch 6/8)

This is the most substantial refactoring patch. It eliminates the rpcrdma_mr_seg[] intermediate representation — described as "a relic of when multiple registration strategies existed (FMR, physical, FRWR)" — and replaces it with a lightweight 16-byte rpcrdma_xdr_cursor on the stack. This removes a 6240-byte rl_segments[260] array from each rpcrdma_req.

The patch also fixes a pre-existing bug in write-pad statistics accounting:

"Fix a pre-existing bug in rpcrdma_encode_write_list where the write-pad statistics accumulator added mr->mr_length from the last data MR rather than the write-pad MR." — Chuck Lever

Scaling Receive Batch Size (Patch 7/8)

The fixed RPCRDMA_MAX_RECV_BATCH of 7 was replaced with a per-endpoint value scaled to 25% of the negotiated credit window. For a typical 128-credit connection, this raises the batch from 7 to 32:

"reducing doorbell frequency by roughly 4x and amortizing the per-batch atomic and MMIO costs over a larger group of receive WRs." — Chuck Lever

Post Receive Buffers After RPC Completion (Patch 8/8)

The rpcrdma_post_recvs() call was moved from CQ poll context to after the RPC has been decoded and completed, reducing latency on the critical reply path:

"Every cycle spent refilling the Receive Queue delays delivery of the reply to the NFS layer." — Chuck Lever

Discussion and Issues Discovered

Anna Schumaker reported regressions after applying Patch 6/8 during cthon testing with both soft iWARP and soft RoCE:

"After this patch I start to see a bunch of errors running cthon tests with both soft iwarp and soft roce. With NFSv3 I see IO errors... I can't even get that far with NFSv4.2, the mounts just fail." — Anna Schumaker

She observed Input/output error on NFSv3 operations and mount failures on NFSv4.2. Lever acknowledged the report:

"D'oh! I'll try to track it down." — Chuck Lever

This exchange occurred just outside the weekly window (March 6), indicating that further debugging and likely a v3 of the series will follow.

Conclusion

This eight-patch series represents a significant investment in NFS/RDMA client reliability and performance, particularly for nconnect deployments. The race condition fixes address real-world deadlock and hang scenarios, while the structural refactoring modernizes the memory registration path. However, Anna Schumaker's regression report on Patch 6/8 suggests that the cursor-based MR registration changes require further attention before merging.
