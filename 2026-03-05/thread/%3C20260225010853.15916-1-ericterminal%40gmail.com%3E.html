sunrpc sysctl: Testing and strictness debate for kstrto* migration

Summary

sunrpc sysctl: Testing and Strictness Debate for kstrto* Migration

Classification: Bug Fix / Code Hardening (NFS Client Subsystem — sunrpc)

This week saw the first substantive review feedback on Yufan Chen's four-patch series to replace deprecated simple_strto* parsers with modern kstrto* equivalents. While only Patch 4/4 touches NFS-relevant code (net/sunrpc/sysctl.c), the entire series was reviewed holistically by network maintainer Simon Horman, who raised concerns about testing rigor and the classification of the changes as clean-ups versus bug fixes.

Evolution of the Discussion

Prior Context (Week of Feb 26)

The patch series was originally submitted on February 25 PATCH v2 0/4. Patch 4/4 targets proc_dodebug() in the sunrpc subsystem, replacing simple_strtol() with kstrtouint() to enforce strict parsing of sysctl debug parameters used by NFS client RPC operations. The previous week's summary noted that no responses had been received during that reporting window.

Simon Horman's Review (March 1)

Network maintainer Simon Horman provided the first review feedback, expressing skepticism about accepting the changes without demonstrated testing:

"I would like to understand what testing has been performed on these patches." Re: PATCH v2 0/4

Horman distinguished between patches that could be motivated as bug fixes and those that are mere clean-ups, noting a policy preference against accepting the latter in isolation:

"With the possible exception of patch 3/4, I feel that unless they are motivated as bug fixes, these changes are too complex to accept without testing." Re: PATCH v2 0/4

"And as for 3/4, I lean towards falling into the policy regarding clean-ups not being generally accepted unless it is part of other work." Re: PATCH v2 0/4

Author's Response on Testing and Strictness (March 4)

Yufan Chen responded with detailed testing methodology, addressing Horman's concerns point by point. The author described using virtme-ng for kernel-level verification and a userspace mock harness for the 9p tokenizing logic:

"I've verified the series using virtme-ng and a userspace mock harness (for the 9p tokenizing logic)." Re: PATCH v2 0/4

Chen characterized Patch 1 as a stability fix, describing testing of error paths on non-Xen systems:

"I've tested the error paths by forcing init failures on a non-Xen system; dmesg confirms the new sentinel-based cleanup (NULL-ing intf/data and checking INVALID_GRANT_REF) correctly prevents double-frees and Oops during teardown." Re: PATCH v2 0/4

Regarding the parsing strictness introduced in Patches 2–4 (including the NFS-relevant Patch 4), Chen emphasized that the migration to kstrto* was chosen specifically for its ability to reject malformed input — a behavior the older simple_strto* functions lacked:

"The strsep + kstrtouint approach was chosen for strictness. I've verified it handles cases like '1,,2' (empty tokens) and '1abc' (malformed input) correctly. The latter is now rejected with -EINVAL, whereas simple_strto* would have silently accepted partial values." Re: PATCH v2 0/4

"The same applies to Patches 3 and 4. The migration to kstrto* ensures that sysfs/procfs interfaces now properly validate the entire input string." Re: PATCH v2 0/4

Significance for NFS Client Development

The NFS-relevant portion of this series (Patch 4/4) hardens the sunrpc debug interface by replacing simple_strtol() with kstrtouint() in proc_dodebug(). This change:

  1. Prevents silent misconfiguration: Malformed input such as "1abc" is now rejected with -EINVAL rather than being silently parsed as "1", which could lead to unexpected debug behavior.
  2. Aligns with kernel best practices: The migration from deprecated simple_strto* helpers to modern kstrto* functions brings the NFS client's underlying RPC layer in line with current kernel coding standards.

The key technical argument this week centered on whether these changes should be classified as bug fixes (which justify acceptance) or mere clean-ups (which require additional motivation). The author's emphasis on strictness and error-path testing positions the series as a hardening improvement rather than a cosmetic refactoring.

Final Status

As of the end of this reporting window, the discussion remains open. Simon Horman has requested more clarity on testing, and Yufan Chen has provided detailed responses. No further maintainer feedback was received within this week's period. The series awaits continued review, with potential next steps including splitting the multi-subsystem patches to facilitate targeted review by individual subsystem maintainers — a suggestion previously raised by 9p maintainer Dominique Martinet in out-of-window discussion.
