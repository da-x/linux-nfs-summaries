vfs: i_ino u64 series — v2 planning, bisection strategy, and tracepoint ABI debates

Summary

vfs: Widen inode->i_ino to u64 — v2 Planning and Bisection Strategy

Overview

Following the initial 61-patch series posted on February 26, discussion continued through February 27 with reviewers focusing on patch organization, bisection safety, and tracepoint ABI implications. This is an architecture-level change (not a bug fix), though it effectively resolves the long-standing 32-bit inode truncation problem for NFS and other network filesystems. The NFS client benefits significantly from this series through removal of XOR-folding hacks and the enable_ino64 module parameter, as detailed in last week's summary.

Key Technical Arguments This Week

Bisection Hazards and Patch Structure

Matthew Wilcox raised a critical concern about the original v1 organization:

"Why are the format strings all done as separate patches? Don't we get bisection hazards by splitting it apart this way?"

Layton acknowledged the issue and revealed he was already working on a v2 series of ~107 patches that addresses this with typedef and macro scaffolding:

"I have a v2 series (~107 patches) that I'm testing now that does this more bisectably with the typedef and macro scaffolding that Mathieu suggested. I'll probably send it early next week."

He posed the question of whether to continue breaking changes up by subsystem or consolidate format string changes into fewer patches:

"Should I continue with this series as a set of patches broken up this way, or is it preferable to combine the pile of format changes into fewer patches?"

Mathieu Desnoyers' Recommended Approach

Mathieu Desnoyers proposed a structured approach to maximize signal over noise in follow-up discussions:

"Now that your series is bisectable, you could post a [RFC PATCH v2] series with the following: [...] The first few patches introduce the new type (kino_t) and macro to do the format string transition. Initially kino_t would typedef to unsigned long (no changes). [...] The final patch would change kino_t and the format string macro to 64-bit integers."

Layton confirmed his v2 already follows this pattern, pointing to his git branch:

"That's pretty much the approach the set I have takes. [...] My question was more about whether I should batch some of the changes together. My inclination is that doing it in small, incremental patches is a good thing, but I figured I'd ask before I spam everyone with a 100+ patch series."

LLM-Assisted Development and Coccinelle

The discussion touched on the role of AI tools in kernel development. Christian Brauner offered a pragmatic view:

"Frankly, as long as you understand what you're doing in general well and I know that you are a trusted and thorough developer/maintainer I could not care less if you tell me whether or not you did this all on your own or with the help of some tool."

Layton also explored whether Coccinelle might be a better tool for such semantic changes, noting his limited experience:

"I've use coccinelle before for this sort of change, but my skills with it are pretty primitive. The problem I saw with using it here is that the main set of changes involved format strings, and that didn't look straightforward to do with coccinelle. The LLM seems to have sorted it out with no trouble though."

He posed an intriguing question to the community:

"On a related note, has anyone has taught an LLM how to use Coccinelle. I wonder if it might give it a better tool for its toolbox, since Claude at least seems to mostly use bash, perl or python to make changes across the tree."

Tracepoint ABI and 32-bit Packing (Patch 03)

Steven Rostedt's earlier concerns about trace event binary format changes on 32-bit systems continued. Layton clarified that ino_t must remain unsigned long as part of the ABI, but inode->i_ino is becoming u64:

"No, ino_t isn't. That's part of the ABI and has to remain unsigned long. The point of this series is to make inode->i_ino a u64. Any event holding an ino_t today is going to need a 64-bit field to fully describe it."

He emphasized the long-term benefit for 32-bit systems:

"And to be clear, this should make things better for 32-bit boxes in the long run. Once this change is done, i_ino should be a reliable source of info regardless of machine's word size."

For tracepoints, Layton decided against using the temporary kino_t typedef:

"For the tracepoints, I think it's best to just extend them to 64-bit fields outright rather than using the new (temporary) kino_t typedef that I'm adding."

He also acknowledged Rostedt's advice on field reordering for better packing:

"Thanks for the review! I'll definitely look at reordering the tracepoint fields for better packing since that has material consequences."

DMA-buf and get_next_ino()

Christian König asked whether get_next_ino() should also be widened to 64 bits, noting current workarounds in DMA-buf:

"Currently it is always only 32bit and we have workarounds for that in DMA-buf for example."

Layton deferred this to a follow-on cleanup:

"I'm not opposed to doing that, but I'd probably leave that for a follow-on cleanup. Just doing the i_ino conversion is already making for a huge patchset."

Subsystem Reviews

Several subsystem maintainers provided reviews this week:

  • UBIFS: Zhihao Cheng gave his Reviewed-by for PATCH 47/61.
  • Zonefs: Johannes Thumshirn confirmed the changes look good for PATCH 50/61.
  • Security/Audit: Ryan Lee verified buffer sizes for AppArmor and provided his Reviewed-by for PATCH 51/61.

Conclusions and Next Steps

  1. A v2 series (~107 patches) is expected early next week, incorporating the kino_t typedef scaffolding for bisectability.
  2. The core architectural change remains unchanged: inode->i_ino will become u64, eliminating 32-bit truncation issues across all filesystems including NFS.
  3. NFS client simplification stands as a major win: removal of nfs_compat_user_ino64(), the enable_ino64 module parameter, and XOR-folding helpers will significantly clean up the NFS codebase.
  4. Tracepoint field reordering for 32-bit packing is acknowledged as necessary work for v2.
  5. The get_next_ino() widening to 64 bits is deferred to a future follow-on series.
