nvme-tcp: KeyUpdate Support Blocked by Missing read_sock_cmsg Dependency

Summary

nvme-tcp: Support KeyUpdate — Build Failures Reported on v7 Patch Series

This week's activity in this thread consisted exclusively of automated build error reports from the kernel test robot against Alistair Francis's [PATCH v7 4/5] nvme-tcp: Support KeyUpdate. The patch series ([PATCH v7 0/5]) was submitted on March 4 and aims to enable the Linux NVMe-TCP host driver to handle TLS 1.3 KeyUpdate requests initiated by an NVMe target, as described in RFC 8446 Section 4.6.3.

Context: What Is This Patch About?

This is a new feature (not a bug fix) for the NVMe-TCP client/host stack. The TLS 1.3 specification allows either party to send a KeyUpdate message — typically when the encryption sequence number is about to overflow or after a certain volume of data has been encrypted. Alistair Francis explained:

"The TLS spec doesn't mandate the conditions though, so a KeyUpdate can be sent by the TLS client or server at any time. This includes when running NVMe-OF over a TLS 1.3 connection."

Upcoming Western Digital NVMe-TCP hardware controllers implement TLS support and send KeyUpdate requests, motivating this kernel-side support. The series builds on existing TLS EKEYEXPIRED detection work, passing KeyUpdate information up to the NVMe layer and then to userspace (ktls-utils/tlshd) for key rotation.

A notable change in v7 was switching from recvmsg() to a new read_sock_cmsg() API:

"Don't use recvmsg() (see [1]) instead use read_sock_cmsg()" — Alistair Francis, cover letter

The Build Failure: Missing read_sock_cmsg Member

Three automated reports arrived this week, all flagging the same compilation error in drivers/nvme/host/tcp.c:

Error: 'const struct proto_ops' has no member named 'read_sock_cmsg'

The kernel test robot reported this across multiple configurations and compilers:

  1. x86_64-rhel-9.4-kunit with gcc-14 — March 4
  2. x86_64-buildonly-randconfig with clang-20.1.8 — March 5
  3. sh-allmodconfig with sh4-linux-gcc-15.2.0 — March 5

All three reports pinpoint the same line in nvme_tcp_try_recv():

consumed = sock->ops->read_sock_cmsg(sk, &rd_desc, nvme_tcp_recv_skb, nvme_tcp_recv_cmsg);

The robot noted that the patch was applied against trondmy-nfs/linux-next and also failed on net/main, net-next/main, linus/master, v7.0-rc2, and next-20260303/04. The patch could not be applied to linux-nvme/for-next, suggesting a dependency ordering issue.

Root Cause Analysis

The error indicates that the read_sock_cmsg() function — which is part of a prerequisite patch series submitted by Eric Biggers (referenced in the cover letter as 20260217222033.1929211-1-cel@kernel.org) — has not yet been merged into the trees against which the robot tested. The v7 series explicitly depends on this networking infrastructure patch:

"This series depends on the read_sock_cmsg() kernel patch"

Without that dependency in place, struct proto_ops lacks the read_sock_cmsg member, causing compilation to fail.

Status and Outlook

No human responses or resolutions were posted this week. The build failures are expected given the missing prerequisite. For the series to progress:

  1. The read_sock_cmsg() networking patch must be merged first (likely into net-next).
  2. Alistair Francis's v7 series would then need to be rebased or tested against a tree containing that dependency.

This is a recurring pattern in kernel development where interdependent subsystem patches must land in the correct order. The NVMe-TCP KeyUpdate feature remains blocked on its networking-layer prerequisite.
