Summary

nfsrahead: Revert of event-driven mountinfo monitoring patch

Classification: Bug Fix / Regression Revert

This week, NFS maintainer Steve Dickson submitted a revert for the recently merged nfsrahead improvement that replaced brittle polling with event-driven /proc/self/mountinfo monitoring using libmount. The original patch, authored by Aaron Tomlin and committed to nfs-utils-2.8.6-rc2 in late February, was rolled back after concerns were raised on the linux-block mailing list regarding the use of the libmount monitoring API.

Background (from prior weeks)

In February 2026, Aaron Tomlin submitted a patch addressing a race condition in nfsrahead, which correlates device numbers with NFS mount points by parsing /proc/self/mountinfo. The original implementation used a naive polling loop — five retries at 50ms intervals (250ms total) — which proved unreliable on systems with slow boot sequences or high load. Tomlin's patch replaced this with an event-driven approach using the libmount mnt_new_monitor() API, increasing the maximum wait time to 10 seconds while returning immediately once the mount entry appeared. The patch was accepted and committed by Steve Dickson for nfs-utils-2.8.6-rc2.

This Week: Revert Submission and Review

On March 5, Steve Dickson submitted a one-patch revert of commit 2b62ac4c273a647df07400dc1126fceb76ad96c0:

Revert "nfsrahead: enable event-driven mountinfo monitoring"

The patch removes 34 lines and restores the original single-line implementation in tools/nfsrahead/main.c. The commit message contained no explanation beyond the automatic revert text.

Significance for NFS Client Development

This revert highlights the cross-cutting nature of userspace tooling changes that depend on shared libraries like libmount. The nfsrahead utility is critical for tuning readahead behavior on NFS mounts; failures to configure it can lead to suboptimal I/O performance. The original patch aimed to improve reliability on systems with slow or variable boot sequences — such as embedded devices, virtual machines, or heavily loaded servers. However, the decision to revert suggests that the libmount monitoring API may have introduced compatibility issues, behavioral regressions, or concerns about its appropriateness for this use case, as discussed on linux-block.

The revert restores the original polling-based approach, which while less elegant and potentially more fragile under heavy load, avoids the dependencies and potential pitfalls of the event-driven mechanism. A future replacement may need to address the underlying concerns raised in the linux-block discussion before a similar improvement can be reintroduced.
