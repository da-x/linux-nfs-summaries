NFS Client: Fixes for Delegated Attribute ctime Updates

Summary

NFS Client: Delegated Attribute Fixes for v7.1

This week, Jeff Layton submitted a two-patch series addressing critical bugs in the Linux NFS client's handling of delegated timestamps. The patches resolve failures in xfstests when delegated attributes are enabled, ensuring that inode change times (ctime) are correctly updated during specific metadata operations.

Context and Problem Statement

The discussion centers on issues arising from the implementation of delegated timestamps, a feature designed to reduce RPC overhead by allowing clients to cache attribute updates locally. However, as reported by Olga Kornievskaia, certain operations failed to properly update the ctime when relying on cached attributes, leading to test failures in xfstests.

Layton introduced the series with the note:

"This patchset fixes a couple of test failures in xfstests when delegated timestamps are enabled. Please consider for v7.1!" PATCH 0/2

Technical Arguments and Fixes

Patch 1: Fix utimensat() for atime with delegated timestamps

The first patch addresses a failure in xfstest generic/221. When a client holds a WRITE_ATTRS_DELEG delegation and a userland process performs a utimensat() call updating only the access time (atime), the change time (ctime) was not being updated correctly.

Layton explained the root cause:

"The problem is that the client tries to cache the atime update, but there is no mtime update, so the delegated attribute update never updates the ctime." PATCH 1/2

He further noted a protocol limitation:

"Delegated timestamps don't have a mechanism to update the ctime in accordance with atime-only changes due to utimensat() and the like." PATCH 1/2

Solution: The patch modifies the client to issue an RPC in this specific case, ensuring the server updates the ctime alongside the atime, rather than relying on the insufficient local caching mechanism.

Patch 2: Update inode ctime after removexattr operation

The second patch resolves a failure in xfstest generic/728. After a removexattr operation, the client's cached ctime remained stale because the subsequent stat() call did not trigger a GETATTR due to the active delegation.

Layton described the issue:

"The client does a removexattr and then a stat to test the ctime, which doesn't change. The stat() doesn't trigger a GETATTR because of the delegated timestamps, so it relies on the cached ctime, which is wrong." PATCH 2/2

Solution: Following the strategy used by setxattr, which includes a trailing GETATTR to ensure fresh attributes, this patch adds a similar mechanism to the removexattr compound operation. This ensures the client retrieves and caches the updated ctime immediately after removing an extended attribute.

Conclusion

This series represents important bug fixes for NFS client development, specifically targeting the robustness of delegated timestamp implementations. By forcing RPC updates in edge cases where local caching leads to stale metadata, the patches ensure compliance with expected POSIX semantics regarding ctime updates. The series is targeted for inclusion in Linux kernel v7.1.
