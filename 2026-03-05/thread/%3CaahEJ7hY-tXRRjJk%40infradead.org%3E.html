Cache Occupancy Querying: SEEK_DATA/SEEK_HOLE Cannot Handle Preallocations

Summary

Cache Occupancy Querying: SEEK_DATA/SEEK_HOLE Cannot Handle Preallocations

Classification

This discussion is about a bug/correctness concern in the proposed netfs caching infrastructure — specifically, how cachefiles determines which regions of a file contain actual data versus holes when querying cache occupancy. The thread highlights a fundamental limitation of using SEEK_DATA/SEEK_HOLE for this purpose due to speculative preallocations by filesystems.

Summary

This week's activity on the RFC PATCH 17/17 thread continued the broader debate surrounding David Howells' 17-patch RFC series to refactor netfslib buffer management. The two messages this week focused on a specific correctness concern raised by Christoph Hellwig regarding how the proposed cachefiles_query_occupancy() function would determine which regions of a cached file contain data versus holes.

Key Technical Arguments

Hellwig's Correctness Concern: Speculative Preallocations

In his initial review of Patch 17/17 (summarized in the parent thread), Christoph Hellwig raised a fundamental objection to using hole-vs-data queries for cache occupancy tracking:

"Independent of fiemap or not, how is this supposed to work? File systems can create speculative preallocations any time they want, so simply querying for holes vs data will corrupt your cache trivially."

The concern is that filesystems may allocate disk blocks speculatively (preallocation) before actual data is written. A query based on SEEK_DATA/SEEK_HOLE or FIEMAP would see these preallocated regions as containing "data," even though they are empty — leading to incorrect cache state and potential corruption.

Howells' Question: Do SEEK_DATA/SEEK_HOLE Avoid Preallocations?

David Howells responded this week with a clarifying question, probing whether the SEEK_DATA/SEEK_HOLE interface might inherently avoid reporting preallocated-but-empty regions:

"SEEK_DATA and SEEK_HOLE avoid preallocations, I presume?"

This question suggests Howells was exploring whether the semantics of SEEK_DATA/SEEK_HOLE might naturally filter out speculative preallocations, unlike FIEMAP (which Hellwig had already rejected in a parallel thread on Patch 02/17).

Hellwig's Definitive Answer: No, They Cannot

Hellwig responded decisively:

"No, they can't. The file system doesn't even know what range is a persistent preallocation or not. You need to track your cached ranges yourself."

This response closes the door on using either FIEMAP or SEEK_DATA/SEEK_HOLE for reliable cache occupancy queries in cachefiles. The filesystem layer has no semantic distinction between "real data" and "speculative preallocation," making any query-based approach inherently unreliable.

Evolution of the Discussion

The conversation evolved through three clear stages:

  1. Hellwig's initial objection (prior week, summarized in the parent thread): Querying holes vs. data via FIEMAP or similar mechanisms would corrupt the cache due to speculative preallocations.
  2. Howells' probing question this week: Whether SEEK_DATA/SEEK_HOLE might offer better semantics than FIEMAP for this use case.
  3. Hellwig's definitive rejection this week: Neither approach works; the filesystem cannot distinguish preallocations from real data, so cache range tracking must be done explicitly by cachefiles itself.

Relevance to NFS Client Development

This thread has significant implications for NFS client-side caching via fscache/cachefiles:

  • Cache correctness: The inability to reliably query file occupancy means that any NFS client using cachefiles must implement its own tracking of cached ranges, independent of filesystem-level extent queries. This adds complexity to the caching layer but is necessary for correctness.
  • No easy shortcut: Howells' RFC series aimed to simplify buffer management in netfslib, which benefits NFS clients directly. However, this exchange reveals that cache occupancy tracking cannot be offloaded to generic VFS mechanisms — it must be handled at the cachefiles level with explicit bookkeeping.
  • Connection to prior FIEMAP rejection: This thread complements the parallel discussion on Patch 02/17 (where Hellwig rejected FIEMAP as a "debugging tool" unfit for data paths). Together, both threads establish that neither FIEMAP nor SEEK_DATA/SEEK_HOLE can serve as a reliable foundation for cache extent discovery.

Final Conclusions

  1. Neither FIEMAP nor SEEK_DATA/SEEK_HOLE can reliably determine cache occupancy due to speculative preallocations by filesystems.
  2. Explicit cache range tracking is required: As Hellwig stated, "You need to track your cached ranges yourself." This means cachefiles must maintain its own metadata about which file regions are actually cached, rather than querying the underlying filesystem.
  3. The RFC series remains in flux: While the bvecq buffer management refactoring has merit, the cache occupancy query mechanism needs a redesign that does not rely on filesystem extent queries.
