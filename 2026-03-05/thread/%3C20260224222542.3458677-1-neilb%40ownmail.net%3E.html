VFS Directory Locking v3: Reviews Received, Awaiting Maintainer Action

Summary

VFS Directory Locking Centralization (v3): Reviews Land, Series Awaiting Maintainer Review

Overview

This week saw the first substantive review activity on Neil Brown's 15-patch series "Further centralising of directory locking for name ops" (v3), submitted last week. Jeff Layton provided Reviewed-by tags on two patches in the series, and Neil Brown followed up with Christian Brauner to inquire about a timeline for review and application.

Classification: VFS refactoring — not a new feature, protocol change, or bug fix. This is preparatory infrastructure work aimed at transitioning from whole-directory locking to per-name locking, a prerequisite for improved VFS scalability.

Bridge from Prior Week

Last week (ending 2026-02-26), Neil Brown submitted the v3 iteration of his directory locking centralization series prior summary. The v3 addressed bugs found during Chris Mason's tool-based review, including a NULL-check error in patch 06/15 and messed-up error handling in patch 09/15. No reviews were posted that week.

This Week's Activity

Jeff Layton Reviews Patches 01/15 and 04/15

On March 2, Jeff Layton reviewed two of the early patches in the series:

[PATCH 01/15 — VFS documentation cleanup]: Layton noted a minor documentation discrepancy caught by AI-assisted review:

"lookup_one_positive_killable() documentation says 'A dentry, possibly negative' but the function explicitly converts negative dentries to ERR_PTR(-ENOENT). It should say 'A positive dentry' like the companion functions lookup_one_positive_unlocked() and lookup_noperm_positive_unlocked()." Review

He concluded:

"Aside from that nit, this looks fine to me." Review

and provided Reviewed-by: Jeff Layton <jlayton@kernel.org>.

[PATCH 04/15 — libfs cleanup]: Layton also reviewed the patch that changes simple_done_creating() to use end_creating(), providing another Reviewed-by Review.

Neil Brown's Response

Neil Brown acknowledged Layton's feedback on the documentation nit, noting:

"The top patch in my next batch contains a bunch of similar documentation cleanups. I'll add this to that patch." Response

He also appreciated the confirmation from Layton's AI-assisted review:

"Good to know!" Response

Follow-Up with Christian Brauner

On March 5, Neil Brown reached out to Christian Brauner (VFS maintainer) regarding the series:

"Hi Christian, do you have thoughts about this series? Any idea when you might have time to review and (hopefully) apply them?" Follow-up

This indicates the series is awaiting maintainer attention and has not yet been applied to any tree.

NFS Client Relevance

This series does not directly modify NFS client code. Its impact on NFS client development is indirect:

  • The locking centralization is a prerequisite for the subsequent per-name locking implementation, which will eventually affect how filesystems (including NFS) interact with VFS name operations.
  • As noted in prior summaries, parallel discussions around d_splice_alias() and hashed dentries — directly relevant to NFS client atomic_open handling — remain open and may intersect with this work.
  • The NFS server component (nfsd) is touched by patch 07/15, which converts purge_old() in the NFSv4 recovery code to use the new start_removing_noperm() / end_removing() wrappers. This was already reviewed by Jeff Layton in prior rounds.

Final Conclusions

  • Two reviews obtained: Jeff Layton's Reviewed-by tags on patches 01/15 and 04/15 represent positive progress, though the bulk of the series (particularly the overlayfs changes in patches 09–14) still awaits review.
  • Documentation nit identified and deferred: The minor documentation error in lookup_one_positive_killable() will be addressed in Neil Brown's next patch batch rather than requiring a v4 of this series.
  • Series status: pending maintainer review. Christian Brauner has not yet responded to the follow-up request within this week's window.
  • No new bugs or regressions reported: The tool-based review from Chris Mason (addressed in v3) and Layton's AI-assisted check both found only minor issues, suggesting the series is in good shape technically.
