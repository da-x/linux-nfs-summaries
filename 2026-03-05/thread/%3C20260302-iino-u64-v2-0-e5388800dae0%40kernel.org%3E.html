vfs: Widen inode->i_ino to u64 — v2 Posted, Scaffolding Debates, and NFS Client Implications

Overview

Jeff Layton posted PATCH v2 000/110, a massive 110-patch series to widen inode->i_ino from unsigned long (32-bit on 32-bit architectures) to u64. This is an architecture-level VFS change, not a traditional bug fix, though it effectively resolves the longstanding 32-bit inode truncation problem that has plagued NFS and other network filesystems for years.

Following last week's discussion of v1 vfs: i_ino u64 series — v2 planning, bisection strategy, and tracepoint ABI debates, v2 addresses the primary concern raised by Matthew Wilcox: bisection safety. The series now uses temporary typedef (kino_t) and format macro (PRIino) scaffolding to ensure each patch compiles cleanly on both 32-bit and 64-bit architectures throughout the transition.

Key Technical Arguments This Week

The Bisection Scaffolding Controversy

The core organizational debate centered on whether the temporary kino_t typedef and PRIino format macro — introduced early in the series and removed at the end — were justified. Layton defended the approach:

"Bisectability. The first version I did of this would have broken the ability to bisect properly across these changes. I don't love the 'churn' here either, but this should be cleanly bisectable."

Christoph Hellwig pushed back strongly against the scaffolding pattern:

"Just drop the bloody macro and the pointless micro-splitting of the change. After this the inode is always 64-bit and we can just use normal ll specifiers without messing things up."

Layton outlined three options for handling the transition:

"There are really only three options here: 1/ Do (almost) all of the changes in one giant patch 2/ Accept that the build may break during the interim stages 3/ This series: using a typedef and macro to work around the breakage until the type can be changed, at the expense of some extra churn in the codebase 3 seems like the lesser evil."

He noted that a single giant patch would touch approximately 182 files with ~910 insertions/deletions, creating severe merge conflicts for subsystem maintainers backporting patches.

Format String Macro Design

Theodore Tso and Darrick J. Wong both expressed discomfort with the PRIino macro design, which provides only a length modifier (e.g., "l" or "ll") rather than a complete format specifier like userspace PRIu64:

"For the record, I really hate the inttypes.h format specifiers, but I agree that we should forward the example of the C99 spec, for better or for worse." — Theodore Tso Re: PATCH 001/110

"Yeah, I don't like 'ino=%" PRIino "u, lolz\n' either. I'd rather have the whole format in the PRIino definition." — Darrick J. Wong Re: PATCH 001/110

Layton explained that the length-modifier-only design allows flexible usage (%" PRIino "u" for decimal, %" PRIino "x" for hex), matching patterns already present in the codebase. He also noted he corrected several instances where inode numbers were printed as signed values:

"There are also some places that print it as a signed value (PRIino 'd'). I suspect most of those are bugs, or just holdovers from a simpler time when we didn't worry so much about the signedness of inode numbers." Re: PATCH 001/110

Should kino_t Persist After the Change?

David Howells questioned whether the typedef should be removed at the end of the series:

"Why remove the typedef? It might be better to keep it." Re: PATCH 000/110

NeilBrown supported retaining it for documentation purposes, drawing a parallel to ktime_t:

"Implicit documentation? ktime_t is (now) always s64, but we still keep the typedef" Re: PATCH 000/110

Layton remained unconvinced:

"Why? After this change, internal kernel inodes will be u64's -- full stop. I don't see what the macro or typedef will buy us at that point." Re: PATCH 000/110

NFS Client Development Impact

This series has profound implications for NFS client development. In the cover letter, Layton highlighted a key cleanup opportunity:

"With this change, we may be able to shrink some inode structures. For instance, struct nfs_inode has a fileid field that holds the 64-bit inode number. With this set of changes, that field could be eliminated. I'd rather leave that sort of cleanups for later just to keep this simple." PATCH 000/110

The NFS client patches touch seven files across the client and pNFS layers:

  • PATCH 011/110: nfs: use PRIino format for i_ino (format string conversion)
  • PATCH 065/110: nfs: replace PRIino with %llu/%llx format strings (final cleanup)

Files modified in the NFS client include fs/nfs/dir.c, fs/nfs/file.c, fs/nfs/inode.c, fs/nfs/nfs4proc.c, fs/nfs/pnfs.c, and pNFS layout drivers (filelayout.c, flexfilelayout.c).

Once merged, this change enables the elimination of:

  • The nfs_inode.fileid field (redundant with inode->i_ino)
  • The enable_ino64 module parameter
  • XOR-folding helpers like nfs_compat_user_ino64()
  • Various 32-bit inode hashing workarounds

No NFS maintainer (Anna Schumaker, Chuck Lever, or Trond Myklebust) weighed in during this week's window, though Layton noted he would seek Christian Brauner's opinion before respinning given the VFS maintainership.

Conclusions and Next Steps

  1. The v2 series is posted with 110 patches, incorporating the kino_t/PRIino scaffolding for bisectability as suggested by Mathieu Desnoyers last week.
  2. Christoph Hellwig remains unconvinced by the scaffolding approach, preferring a single large patch or accepting interim build breakage on 32-bit. Layton is awaiting Christian Brauner's (VFS maintainer) opinion before respinning.
  3. NFS client simplification remains a major downstream benefit: removal of nfs_inode.fileid, the enable_ino64 module parameter, and XOR-folding helpers will significantly clean up the NFS codebase in a follow-on series.
  4. The typedef persistence question is unresolved: David Howells and NeilBrown advocate keeping kino_t for documentation; Layton prefers removing it once i_ino is permanently u64.
  5. Tracepoint field reordering for better 32-bit packing (noted in v1) was incorporated into v2 via PATCH 006/110.
  6. Widening get_next_ino() to 64 bits remains deferred to a future follow-on series, as noted last week.
