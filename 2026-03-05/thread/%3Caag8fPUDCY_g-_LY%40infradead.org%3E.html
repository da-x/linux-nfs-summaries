FIEMAP kernel callback rejected; SEEK_DATA/SEEK_HOLE affirmed as superior API

Summary

FIEMAP Kernel Callback Rejected; SEEK_DATA/SEEK_HOLE Affirmed as Superior API

Classification

This discussion is about a proposed new VFS feature — specifically, an RFC patch to implement a callback in the internal kernel FIEMAP API so that kernel-space consumers (such as cachefiles, knfsd, and ksmbd) can query extent maps without relying on userspace-oriented interfaces. The proposal was unequivocally rejected.

Summary

David Howells proposed adding a callback mechanism to the internal kernel FIEMAP API, enabling kernel subsystems to capture and parse FIEMAP data directly. The stated motivation was to allow cachefiles, knfsd (the NFS server), and ksmbd (the SMB server) to implement remote equivalents of FIEMAP rather than using the SEEK_DATA/SEEK_HOLE interface.

Christoph Hellwig immediately and forcefully rejected the proposal, arguing that FIEMAP is fundamentally unsuited for production data paths. The exchange concluded with Howells accepting the rejection and confirming he would continue using SEEK_DATA/SEEK_HOLE.

Key Technical Arguments

Hellwig's Rejection of FIEMAP in Data Paths

Christoph Hellwig responded to the RFC with a blunt refusal:

"Hell no. FIEMAP is purely a debugging tool and must not get anywhere near a data path. NAK to all of this."

This position reflects a longstanding kernel community consensus that FIEMAP has inherent racy semantics and was designed as a diagnostic interface, not a production-grade API for extent mapping in active I/O paths.

Howells' Use Case: cachefiles, knfsd, and ksmbd

Howells explained his motivation in his follow-up:

"So I have to stick with SEEK_DATA/SEEK_HOLE for this? (Before you ask, yes, I do want to keep track of this myself, but working out the best way to do that without reinventing the filesystem is the issue - well, that and finding time to do it)."

The cachefiles daemon relies on understanding file layout (data vs. hole regions) to manage its cache efficiently. Similarly, NFS and SMB servers need to report sparse file information to clients. Howells' proposal sought a more efficient kernel-internal path than the existing SEEK_DATA/SEEK_HOLE mechanism.

Hellwig's Defense of SEEK_DATA/SEEK_HOLE

Hellwig reinforced his position by endorsing the alternative:

"Yes. Why do you even want to move away from that? It's the far better API. Of course like all other reporting APIs it still is racy, but has far less problems than fiemap."

This characterization of SEEK_DATA/SEEK_HOLE as having "far less problems" than FIEMAP is significant. While both interfaces suffer from inherent race conditions (file contents can change between query and use), SEEK_DATA/SEEK_HOLE provides a simpler, more robust semantic model for kernel consumers.

Evolution of the Discussion

The thread was brief but decisive:

  1. Hellwig's initial NAK [id://aag8fPUDCY_g-_LY@infradead.org]: Immediate rejection on principle — FIEMAP must not enter data paths.
  2. Howells' acceptance [id://114166.1772634114@warthog.procyon.org.uk]: Acknowledged the need to use SEEK_DATA/SEEK_HOLE and noted ongoing challenges in managing file tracking without "reinventing the filesystem."
  3. Hellwig's final word [id://aahA7rQVf5liFYMv@infradead.org]: Confirmed that SEEK_DATA/SEEK_HOLE is the correct approach and superior to FIEMAP.

Relevance to NFS Client Development

While this thread concerns server-side infrastructure (knfsd) more directly than the NFS client, it has indirect implications for NFS development:

  • NFS server (knfsd): The rejection means knfsd will continue relying on SEEK_DATA/SEEK_HOLE rather than FIEMAP to report sparse file information to NFS clients via SEEK_DATA/SEEK_HOLE operations. This maintains consistency with the existing protocol semantics for sparse file handling.
  • cachefiles and NFS client caching: The cachefiles subsystem, which is often used in conjunction with NFS client-side caching (e.g., fscache), will continue using SEEK_DATA/SEEK_HOLE. Howells' comment about the difficulty of "working out the best way to do that without reinventing the filesystem" suggests ongoing complexity in this area.

Final Conclusions

  1. The FIEMAP kernel callback RFC is rejected. No further development on this approach is expected.
  2. SEEK_DATA/SEEK_HOLE is affirmed as the preferred API for kernel-internal sparse file queries, despite its own limitations.
  3. cachefiles, knfsd, and ksmbd will continue using SEEK_DATA/SEEK_HOLE, accepting its racy semantics as the lesser evil compared to FIEMAP's problems.
