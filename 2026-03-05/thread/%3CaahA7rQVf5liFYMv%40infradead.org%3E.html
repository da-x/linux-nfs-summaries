vfs: FIEMAP Callback Debate — SEEK_DATA/SEEK_HOLE vs. FIEMAP Performance

Overview

This thread concerns an ongoing RFC patch series proposing to implement a FIEMAP callback in the VFS layer (RFC PATCH 02/17). This is a protocol/API-level discussion, not a bug fix. The debate centers on whether filesystems should use the newer SEEK_DATA/SEEK_HOLE interface or the older FIEMAP ioctl for extent mapping — with direct implications for NFS client development and caching strategies.

Key Technical Arguments This Week

Only one message was posted within this week's window, but it crystallizes a fundamental performance trade-off in VFS extent-mapping APIs.

Christoph Hellwig's Position (Prior Week)

Christoph Hellwig firmly advocated for SEEK_DATA/SEEK_HOLE over FIEMAP, stating:

"Yes. Why do you even want to move away from that? It's the far better API. Of course like all other reporting APIs it still is racy, but has far less problems than fiemap."

Hellwig's argument rests on the premise that SEEK_DATA/SEEK_HOLE is semantically cleaner and avoids the known pitfalls of FIEMAP (such as inconsistent behavior across filesystems and race conditions with concurrent modifications).

David Howells' Counter-Argument (This Week)

David Howells pushed back on performance grounds in his reply:

"To find the next two extents of data, say, I have to make four calls into the backing filesystem rather than one - with all the context set up and locking those might incur."

Howells' concern is practical: SEEK_DATA/SEEK_HOLE operates on a per-extent basis, requiring alternating calls to discover data regions and holes. In contrast, FIEMAP can return multiple extents in a single ioctl call, reducing the number of round-trips into the backing filesystem — each of which may involve context setup and locking overhead.

He acknowledged, however, that this is largely an edge case:

"Granted, the vast majority of files aren't sparse, so one pair of SEEK_DATA/SEEK_HOLE should be able to establish that."

NFS Client Development Implications

This discussion has direct relevance to NFS client caching and pNFS layout operations:

  1. Cache coherence: Both FIEMAP and SEEK_DATA/SEEK_HOLE are inherently racy, as both participants acknowledged. For NFS clients relying on extent maps for read-ahead or cache management, this means either API requires additional validation mechanisms.

  2. Performance trade-offs: Howells' concern about multiple filesystem calls is particularly relevant for NFS, where each call may translate to a network round-trip in certain caching scenarios. FIEMAP's ability to batch extent queries could reduce latency for sparse files or files with complex allocation patterns.

  3. API standardization: The push toward SEEK_DATA/SEEK_HOLE as the "better API" suggests a long-term direction where NFS clients and other network filesystems may need to adapt their extent-mapping strategies away from FIEMAP-based approaches.

Conclusion

The discussion remains unresolved this week. Hellwig maintains that SEEK_DATA/SEEK_HOLE is the superior API despite its verbosity, while Howells highlights legitimate performance concerns for workloads involving sparse files or multi-extent queries. The outcome of this debate will influence how NFS and other network filesystems implement extent mapping in future kernel versions.
