NFS Unmount Notification: VFS Complexity Rejected, exportfs -F Confirmed as Path Forward

Summary

This week's activity on the NFS unmount notification thread brought closure to a multi-week debate over how to resolve NFSv4 unmount hangs caused by outstanding delegations and locks. VFS maintainer Christian Brauner firmly rejected adding custom kernel notification mechanisms to the unmount path, endorsing a userspace solution instead. Chuck Lever confirmed he will pursue changes to exportfs rather than further kernel-side patches.

Discussion Type

This is a bug fix / infrastructure enhancement discussion aimed at resolving NFSv4 unmount hangs when clients hold outstanding state (delegations, locks, opens). The core problem: when an administrator unexports an NFS share and then attempts to unmount the underlying filesystem, the unmount blocks with EBUSY because NFSD holds file references open while NFSv4 state remains outstanding.

Prior Context (Brief)

Over the preceding weeks, Chuck Lever's patch series proposing a VFS umount notifier chain evolved through several iterations:

  • SRCU notifiers were found to fire too late — only after all files are closed, but NFSD holds files open, creating a circular dependency.
  • fsnotify with FS_UNMOUNT suffered the same timing flaw as summarized previously.
  • A new hook in do_umount() was proposed but raised concerns about firing during mount namespace teardowns.
  • NeilBrown suggested adding a -F flag to exportfs -u to explicitly flush NFSD state, which Chuck Lever agreed could leverage the existing "unlock filesystem" API.
  • Jan Kara and Jeff Layton explored adapting ->umount_begin or adding an NFSD-registered callback as summarized previously.

Key Technical Arguments This Week

Christian Brauner: VFS Unmount Path Is Not the Place for More Complexity

Christian Brauner, VFS maintainer and original reviewer of Chuck's patch series, delivered a definitive position against adding custom notification mechanisms to the kernel unmount codepath. He acknowledged that while fsnotify was his suggested alternative to SRCU notifiers, he remains opposed to any new custom infrastructure:

"The locking and the guarantees that we have traditionally given to userspace make it a very convoluted codepath and I'm very hesitant to add more complexity in this part of the code." Christian Brauner

He drew a clear line: fsnotify is acceptable only if it can reasonably provide the notification NFSD needs, but no new custom VFS notifier chains will be tolerated:

"What I absolutely don't want is to have another custom notification mechanism in the VFS layer." Christian Brauner

Critically, Brauner endorsed the userspace approach as the preferred solution:

"But if we can solve this in userspace then it is absolutely the preferred variant and what we should do." Christian Brauner

Chuck Lever: Commitment to the exportfs Path

Chuck Lever accepted Brauner's reasoning without reservation and confirmed he will abandon further kernel-side notifier work in favor of modifying exportfs:

"No problem with that line of reasoning. Right now it looks like we can do this with changes to exportfs, so I will pursue that." Chuck Lever

Evolution of the Discussion

The thread's trajectory this week represents a decisive pivot:

  1. Weeks prior: Exploration of kernel-side solutions (SRCU notifiers, fsnotify, new do_umount() hooks, ->umount_begin callbacks).
  2. Late last week: Discovery that all kernel notification mechanisms fire too late due to the circular dependency between NFSD-held file references and unmount completion. Shift toward exportfs -F.
  3. This week (Mar 4): VFS maintainer Christian Brauner formally rejects custom VFS notifier infrastructure, endorsing userspace solutions. Chuck Lever confirms he will implement the fix via exportfs changes.

Final Conclusions

Status: The kernel-side patch series adding umount notifiers is effectively concluded. The consensus path forward is:

  1. Userspace solution via exportfs: Chuck Lever will modify exportfs to invoke the existing "unlock filesystem" API after unexporting, thereby releasing all NFSD-held state (locks, delegations, opens) before the administrator attempts to unmount the underlying filesystem. This requires minimal or no kernel changes beyond potentially exposing or refining the unlock API.

  2. No custom VFS notifiers: Christian Brauner has made clear that adding another custom notification mechanism to the VFS layer is unacceptable due to the complexity and locking constraints of the unmount codepath.

  3. Open question remains: Whether state revocation should be the default behavior of exportfs -u or require an explicit flag (e.g., -F). NeilBrown argued for an explicit action, noting that automatic revocation could break users relying on undocumented NFSv4 state persistence after unexport:

    "I think their preference, while understandable, is naive. They are doing something that is not documented as supported, is not actually supported, and has always had the possibility of failure." NeilBrown

This decision remains pending input from the linux-nfs@ review committee.

NFS Client Development Impact

While this thread primarily concerns NFSD (server-side), the resolution has indirect implications for NFS client development:

  • Reliable unmount behavior on the server side prevents scenarios where clients experience unexpected state recovery delays or delegation recall storms when a share is administratively removed.
  • The exportfs -F approach provides administrators with a deterministic way to clean up NFSv4 state, improving automation and scripting reliability for server management.
