lockd: Three fixes for memory leaks and uninitialized hash bytes

Summary

Lockd Fixes: Memory Leaks and Uninitialized Hash Bytes

This week, Chuck Lever submitted a series of three patches addressing critical bug fixes in the NFS lock manager (lockd) subsystem. The series was triggered by a report from Jeff Layton regarding an issue with NLMv4 file handle hashing, which led to the discovery of two additional pre-existing memory management bugs during review.

"Jeff reported an issue earlier today, and while crafting the fix, LLM review found two more pre-existing nearby problems." Chuck Lever

The discussion is focused entirely on bug fixes for the NFS client/server lock daemon, specifically targeting memory leaks and state corruption issues introduced in recent commits.

Key Technical Arguments and Fixes

1. Plug nlm_file leak when nlm_do_fopen() fails

The first patch addresses a memory leak where nlm_file structures are not freed when nlm_do_fopen() fails for a newly allocated file entry. A malicious or misbehaving client could repeatedly trigger this path by presenting invalid file handles, leading to unbounded memory consumption.

"A client can repeatedly drive nlm_do_fopen() failures by presenting file handles that the underlying export rejects... each failure leaks one nlm_file." Chuck Lever

The fix ensures that the failure path routes through out_free, allowing kfree() to execute before the function returns. This fixes a regression introduced by commit 7f024fcd5c97.

2. Plug nlm_file refcount leak on cached nlm_do_fopen() failure

The second patch addresses a reference count leak for cached nlm_file entries. When nlm_do_fopen() fails for an existing hashed entry, the code incorrectly increments the file's reference count (f_count) before returning an error. Because the caller does not receive the file pointer, it cannot release the reference, preventing the garbage collector from reaping the stale entry.

"The f_count increment is never released, and nlm_traverse_files() can no longer reap the file because its refcount never returns to zero between requests." Chuck Lever

The fix short-circuits the cached path to avoid touching *result or f_count when nlm_do_fopen() fails. This also fixes a regression from commit 7f024fcd5c97.

3. Avoid hashing uninitialized bytes in nlm4svc_lookup_file()

The third patch, which originated the series, addresses an issue where NLMv4 file handles shorter than LOCKD_FH_HASH_SIZE (32 bytes) contain uninitialized data in their tail bytes. This causes the same wire handle to hash to different buckets across calls, leading to failed lock-state lookups.

"When an NLMv4 client presents a file handle shorter than LOCKD_FH_HASH_SIZE, bytes fh.len..31 retain whatever the argument buffer held from an earlier request. The same wire handle then hashes to different buckets across calls; nlm_lookup_file() misses the existing nlm_file entry, and lock-state lookups fail." Chuck Lever

The fix zeros out only the tail bytes that file_hash() would consume, ensuring consistent hashing. This fixes a regression introduced by commit 3de744ee4e45, which moved file-handle population into nlm4svc_lookup_file().

Evolution of the Discussion

The thread was concise, consisting primarily of Chuck Lever's patch series submission. One additional message was sent by Chuck Lever regarding a separate TLS patch included in the same email batch:

"Ignore this email. It looks like something left over from a previous posting." Chuck Lever

This indicates that the TLS patch ([PATCH net] tls: Preserve sk_err across recvmsg() when data has been copied) was inadvertently included in the lockd fix series and should be disregarded in the context of this thread.

Final Conclusions

The three lockd fixes are critical for stability and correctness:

  1. Prevents memory leaks triggered by invalid file handles.
  2. Prevents reference count leaks that prevent garbage collection of stale lock entries.
  3. Ensures consistent hashing of NLMv4 file handles, preventing lock-state lookup failures.

All three patches are marked with Fixes: tags and are ready for integration into the kernel tree. The series demonstrates the value of thorough code review, including automated tools ("LLM review"), in uncovering latent bugs adjacent to the originally reported issue.
