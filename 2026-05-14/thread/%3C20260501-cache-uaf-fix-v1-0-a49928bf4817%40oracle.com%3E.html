SUNRPC: Refining cache_check_rcu() UAF fixes and dropping unnecessary netns guard

Summary

This thread discusses the refinement of a patch series addressing Use-After-Free (UAF) vulnerabilities in the SUNRPC cache content files, specifically focusing on cache_check_rcu() races. The discussion centers on validating the root cause of reported crashes and ensuring patches address actual bugs rather than perceived ones.

Key Technical Arguments

1. Misidentification of the Root Cause for SUNRPC Caches Initially, developer Yang Erkun questioned whether the UAF reported by Misbah was related to network namespace teardown, similar to a recent NFSd fix (e7fcf179b82d). He noted he could not reproduce the issue and suspected the dentry teardown path.

Chuck Lever clarified that while e7fcf179b82d fixed a specific oops in /proc/fs/nfs/exports, the SUNRPC cache files (/proc/net/rpc/<cache>/content) have different synchronization properties. He initially suggested Patch 5/6 of his series, which adds get_net() guards to SUNRPC cache opens, addressed a similar hole.

2. The Role of proc_entry_rundown Erkun provided a detailed analysis arguing that Patch 5/6 might be unnecessary. He explained that SUNRPC cache files are accessed via proc_reg_read, which calls use_pde. During cache unregistration, cache_unregister_net() triggers proc_remove(), which invokes proc_entry_rundown().

"The proc_entry_rundown function waits until unuse_pde is called in proc_reg_read. Therefore, I'm not sure if forgetting to call get_net when opening /proc/net/rpc/<cache>/content is the root cause of the null pointer in c_show."

Erkun correctly identified that proc_entry_rundown blocks until all active readers have finished, ensuring that cache_destroy_net() (which frees cd->hash_table) only runs after no reader can dereference the cache detail structure.

3. Identification of the Actual Bug: Patch 3/6 Chuck Lever conceded that Erkun's analysis was correct. He acknowledged that the changelog for Patch 5/6 overstated the window for SUNRPC cache files.

"Walked the synchronization. You're right... The sunrpc cache files reach c_show through proc_reg_read(), which goes through use_pde()/unuse_pde() and is covered by rundown. 5/6 doesn't close the hazard its changelog describes."

Chuck identified that Patch 3/6 is the actual fix for Misbah's reproducer. The bug lies in ip_map_put(), which synchronously drops an auth_domain reference:

"A reader walking auth.unix.ip/content under rcu_read_lock() can dereference im->m_client after the auth_domain has been freed. Same shape as 48db892356d6's svc_export fix, applied to ip_map."

Patch 3/6 moves this release into a deferred callback via queue_rcu_work(), ensuring the sub-object survives the RCU grace period.

Final Conclusions and Action Items

The discussion concluded with Chuck Lever outlining specific changes for v2 of the patch series:

  1. Drop or Reframe Patch 5/6: Since proc_entry_rundown already protects SUNRPC cache files from the namespace teardown race, Patch 5/6 is not a bug fix for the described UAF.

    "For v2: re-test Misbah's reproducer with patches 1-4 and 6 only and see whether 3/6 alone closes the crash. If it does, drop 5/6; if it doesn't, reframe 5/6 as a consistency change without the UAF claim..."

  2. Focus on Patch 3/6: The critical fix is deferring auth_domain_put() in ip_map release to prevent UAF during RCU traversal.
  3. Rewrite Cover Letter: The cover letter must be rewritten to accurately reflect that Patch 5/6 does not fix a UAF in SUNRPC cache files, avoiding misleading claims about network namespace lifetime extension for these specific debugfs/procfs entries.

This thread highlights the importance of rigorous synchronization analysis in kernel development, where seemingly analogous bugs (NFSd vs. SUNRPC) may have different root causes due to subtle differences in procfs entry handling.
