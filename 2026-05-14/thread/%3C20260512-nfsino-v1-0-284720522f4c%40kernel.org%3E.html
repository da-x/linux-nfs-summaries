NFS Client: Removing the Redundant fileid Field from struct nfs_inode

Summary

NFS Client Cleanup: Eliminating the Separate fileid Field

In a significant refactor aimed at simplifying the NFS client codebase and reducing memory overhead, Jeff Layton submitted a four-patch series to remove the dedicated fileid field from struct nfs_inode. This change leverages recent VFS updates in Linux v7.1-rc1, which expanded inode->i_ino to a 64-bit unsigned integer (u64).

Context and Motivation

Historically, the NFS client maintained a separate 64-bit fileid within struct nfs_inode because the generic VFS inode number (inode->i_ino) was limited to an unsigned long (32 bits on many architectures). To preserve the full NFS file identifier for internal operations while presenting a compatible inode number to user-space, the client employed XOR-folding hashing and various compatibility helpers.

With the VFS now supporting 64-bit inode numbers natively, this indirection is obsolete. Layton noted in the cover letter PATCH 0/4:

"v7.1-rc1 contains patches to make inode->i_ino to be a u64. With this change, there is no need to keep a separate 'fileid' field in struct nfs_inode."

The primary benefits cited are code simplification and memory savings:

"This patchset eliminiates that field, and the inode number hashing machinery that is no longer needed. This shaves 8 bytes off of each nfs_inode."

Layton requested that Trond Myklebust and Anna Schumaker consider the series for inclusion in v7.2.

Patch Breakdown

The series proceeds logically through four steps:

  1. PATCH 1/4: Store the full NFS fileid in inode->i_ino.
    This patch transitions internal operations to use inode->i_ino directly for storing and retrieving the 64-bit NFS file identifier. It updates functions like iget5_locked() and ilookup5() to pass the full fileid as the hash parameter, eliminating the need for folded hashes. Direct accesses in nfs_check_inode_attributes(), nfs_update_inode(), and nfs_same_file() are converted accordingly.

  2. PATCH 2/4: Remove nfs_compat_user_ino64() and deprecate enable_ino64.
    With inode->i_ino holding the full 64-bit value, the compatibility function nfs_compat_user_ino64() becomes redundant. The patch removes this function along with helper functions nfs_fileid_to_ino_t() and nfs_fattr_to_ino_t(). To maintain backward compatibility for systems using the nfs.enable_ino64 kernel parameter, the module parameter is retained as a deprecated stub that logs a notice but ignores the value.

  3. PATCH 3/4: Replace NFS_FILEID() and nfsi->fileid with inode->i_ino.
    This patch performs a widespread replacement of NFS_FILEID() macros, set_nfs_fileid() calls, and direct nfsi->fileid accesses across the NFS client codebase, including export handling, file layouts (filelayout and flexfilelayout), page lists, PNFS, and write operations.
    Notably, this patch also addresses two pre-existing bugs in tracing infrastructure:

    "Also fix two pre-existing truncation bugs in nfs4trace.h where fileid trace fields were declared as u32 instead of u64."

  4. PATCH 4/4: Remove fileid field from struct nfs_inode.
    With all references migrated, the final patch removes the fileid member from struct nfs_inode, achieving the stated goal of saving 8 bytes per inode.

Technical Significance

This series represents a clean-up and modernization effort rather than a new feature or critical bug fix. However, it does incidentally resolve minor tracing bugs related to data type truncation. The removal of legacy compatibility code reduces maintenance burden and aligns the NFS client with modern VFS capabilities.

No discussion or feedback from other developers was recorded in this window; the patches were submitted without immediate replies in the provided timeframe. The series appears to be a straightforward cleanup enabled by upstream VFS changes, targeting inclusion in the v7.2 kernel cycle.

Conclusion

Jeff Layton's patch series successfully streamlines the NFS client's inode handling by eliminating redundant storage and legacy compatibility layers. By leveraging the 64-bit inode->i_ino, the code becomes simpler, more consistent, and slightly more memory-efficient. The deprecation of enable_ino64 ensures existing configurations remain functional while guiding users toward the new default behavior.
