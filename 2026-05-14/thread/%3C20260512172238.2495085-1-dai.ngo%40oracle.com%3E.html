XFS pNFS: Fix overlapping extents in LAYOUTGET replies

Summary

This thread addresses a critical bug fix in the XFS filesystem's pNFS block layout implementation, specifically concerning how extent mappings are returned during LAYOUTGET operations. The discussion centers on preventing overlapping extents from being sent to NFS clients, which can lead to data corruption or protocol violations.

Problem Identification

Dai Ngo submitted a patch fixing overlapping extents returned for pNFS LAYOUTGET. The root cause was identified in xfs_fs_map_blocks(), which passed the XFS_BMAPI_ENTIRE flag to xfs_bmapi_read(). This caused the block mapping code to return the entire extent rather than trimming it to the requested range.

"A single LAYOUTGET request from the client can cause the server to issue multiple calls to xfs_fs_map_blocks() for different offsets within the same extent. Because of the use of XFS_BMAPI_ENTIRE flag, these calls can produce overlapping mappings."

This behavior resulted in ambiguous extent selection on the client side, potentially leading to incorrect device selection and inconsistent datastate handling. The issue was discovered using the xfstest generic/075 test with an NFSv4.2 mount and SCSI layout.

Technical Discussion and Review

Darrick J. Wong provided detailed feedback, clarifying the mechanism of the overlap:

"Nitpicking: _ENTIRE causes bmapi_read to return the whole extent instead of trimming it down to the requested range."

He illustrated a scenario where concurrent file allocation changes could result in overlapping mappings being sent to the client, such as: {.offset = 0, .length = 4096, ...} followed by {.offset = 0, .length = 8192, ...}.

Darrick also suggested simplifying the patch by hardcoding 0 instead of introducing a new variable for flags:

"Why not just replace the argument to xfs_bmapi_read with a constant zero?"

Christoph Hellwig raised an important point about client-side robustness:

"Please also add a check to the client that catches this and doesn't use the layout that has extents outside the requested range. And maybe warn about it as well."

However, Dai Ngo clarified that while the extents overlapped, they covered exactly the range requested in the LAYOUTGET operation. He provided an on-the-wire capture showing two SCSI extents starting at the same offset but with different lengths (53248 and 77824 bytes), both within the requested range.

Client-Side Handling

The discussion touched upon whether the NFS client's ext_tree_insert() function could handle overlapping extents gracefully. Dai Ngo noted:

"After reviewing ext_tree_insert(), with assist from Codex, I think this function handles overlapping extents properly... IMHO, I think we still should fix xfs_fs_map_blocks() to avoid any overhead and complication in ext_tree_insert having to handle overlapping extents."

Darrick Wong acknowledged the approach, stating:

"Not passing XFS_BMAPI_ENTIRE into bmapi_read sounds fine to me."

Conclusion

The consensus was that fixing the server-side behavior in xfs_fs_map_blocks() by removing the XFS_BMAPI_ENTIRE flag is the correct approach. This ensures that only the requested range is mapped, eliminating the possibility of overlapping extents in LAYOUTGET replies. The patch also included a minor cleanup to drop an unnecessary error check.

This fix is marked for stable backport to v6.19 and addresses a regression introduced by commit cc6c40e09d7b1 ("NFSD/blocklayout: Support multiple extents per LAYOUTGET").
