FreeBSD NFSv4 nfsd Buffer Size Increase to 4MB: Implementation Details and Performance Caveats

Summary

FreeBSD NFSv4 nfsd Buffer Size Increase to 4MB: Implementation Details and Performance Caveats

Type: Configuration/Feature Enhancement (FreeBSD NFS Server)
Status: Implemented in FreeBSD "main"; MFC to stable/15 pending

Bridge to Prior Weeks

This thread originated in March 2026 with Cedric Blancher's proposal to increase the default NFSv4 server max_block_size from 1MB to 4MB. After Chuck Lever called for a data-driven approach, client maintainers across Linux (Anna Schumaker), FreeBSD (Rick Macklem), and Windows/ms-nfs41-client (Roland Mainz) confirmed compatibility with larger block sizes. In April, Mike Snitzer requested that Anna Schumaker post her Linux NFS client patch enabling >1MB support. The focus of this week's activity shifted from the Linux NFSD default change to practical implementation details on the FreeBSD server side, as Cedric Blancher sought guidance on configuring FreeBSD's NFSv4 nfsd to utilize larger buffers.

This Week's Activity

Initial Inquiry and Configuration Guidance

Cedric Blancher opened this week's discussion by asking how to verify that FreeBSD NFSv4 nfsd utilizes 2MB buffers, referencing Rick Macklem's earlier comments from March:

"How can I verify that the FreeBSD NFSv4 nfsd now uses 2M for NFS buffers?" Cedric Blancher

Rick Macklem responded with detailed configuration instructions, noting that the default max_block_size remains 128KB but can be increased significantly:

"The default is 128K. (You can see what it is via 'sysctl vfs.nfsd.srvmaxio'.)" Rick Macklem

He outlined the two-step process required: setting nfs_server_maxio=N in /etc/rc.conf and increasing kern.ipc.maxsockbuf in /etc/sysctl.conf. He specified that FreeBSD "main" supports values up to 4MB (4194304 bytes), while FreeBSD 15 is limited to 1MB (1048576 bytes).

Commit Status and Verification Methods

Cedric followed up with questions about which FreeBSD version corresponds to "main," whether the feature is supported in 15.0, and how to verify the settings programmatically:

"Which FreeBSD version is 'main' exactly, i.e. which 16.0 snapshot date? Is this supported for 15.0?" Cedric Blancher

Rick clarified that the 4MB support had not yet been committed at the time of his first response, citing upstream dependencies:

"Oops, my bad. It isn't committed yet. I forgot that I have to convince the FreeBSD collective to increase UIO_MAXIOV or convince the ZFS folk to not check for that limit in ZFS." Rick Macklem

He provided verification methods, including:

  • Inspecting maxread and maxwrite values in GETATTR replies via Wireshark packet traces.
  • Using the vfs.nfsd.srvmaxio sysctl programmatically via the sysctl(3) library call, which returns EINVAL if the value is too large.

Commit Landing and Configuration Details

On May 14, Rick announced that the commit had landed in FreeBSD "main":

"The commit just hit 'main' as b92b9da33006. So any snapshot after to-day should have it. (It will be MFC'd to stable/15 in 2 weeks and will be in 15.2.)" Rick Macklem

He provided the exact configuration lines required to enable 4MB buffers:

/etc/rc.conf: nfs_server_maxio=4194304
/etc/sysctl.conf: kern.ipc.maxsockbuf=18892800 (or larger)

Automation Suggestion and Performance Caveats

vermaden suggested an improvement to the configuration process, proposing that setting nfs_server_maxio should automatically adjust kern.ipc.maxsockbuf:

"An idea ... if 'nfs_server_maxio' already sets the 'vfs.nfsd.srvmaxio' maybe it should automatically also set 'kern.ipc.maxsockbuf' to 4*nfs_server_maxio first?" vermaden

This would simplify administration by requiring only a single configuration entry in /etc/rc.conf rather than coordinated changes across two files.

Rick concluded the week with an important performance caveat, cautioning against blindly increasing buffer sizes:

"Oh, and I should also point out that, for the low end hardware I have, I have never seen a performance improvement for a maxio setting above 256Kbytes. The story may be different for faster hardware, but I wouldn't just assume that bumping it up will get you better performance." Rick Macklem

He also highlighted the trade-off between single-client throughput and fair resource distribution across multiple clients.

Key Technical Arguments

  1. Implementation Dependencies: The FreeBSD 4MB support required upstream changes to UIO_MAXIOV or ZFS limits, demonstrating that NFS server enhancements often depend on broader kernel subsystem modifications.

  2. Configuration Complexity: Enabling larger buffers requires coordinated changes across /etc/rc.conf and /etc/sysctl.conf, with the socket buffer size needing to be at least 4× nfs_server_maxio to accommodate concurrent reads or writes.

  3. Verification Methods: Multiple approaches exist for verifying configuration: sysctl inspection, Wireshark packet analysis of GETATTR replies, and programmatic probing via sysctl(3).

  4. Performance Nuance: Larger buffer sizes do not universally improve performance. Rick's observation that settings above 256KB showed no benefit on his low-end hardware underscores the importance of workload-specific benchmarking.

Significance for NFS Client Development

While this week's discussion focused primarily on FreeBSD server-side configuration, it has direct implications for NFS client development:

  • Cross-platform interoperability: With FreeBSD now supporting up to 4MB max_block_size, clients that have already been updated (Linux per Anna Schumaker's patch, ms-nfs41-client per Roland Mainz) can negotiate larger transfer sizes with FreeBSD servers.
  • Default configuration evolution: The progression from theoretical compatibility discussions to concrete implementation details suggests that the NFS ecosystem is moving toward wider adoption of larger block sizes.

Conclusions

This week marked a significant milestone for FreeBSD NFSv4 server capabilities:

  • Commit b92b9da33006 landed in FreeBSD "main," enabling nfs_server_maxio values up to 4MB.
  • The feature will be merged to stable/15 within two weeks and included in FreeBSD 15.2.
  • Configuration requires manual coordination between /etc/rc.conf and /etc/sysctl.conf, with vermaden suggesting automation as a future improvement.
  • Performance benefits are hardware- and workload-dependent, with Rick cautioning that larger buffers do not guarantee improved throughput on all systems.

The discussion reflects the maturation of the broader max_block_size initiative, transitioning from cross-platform compatibility verification to practical deployment guidance.
