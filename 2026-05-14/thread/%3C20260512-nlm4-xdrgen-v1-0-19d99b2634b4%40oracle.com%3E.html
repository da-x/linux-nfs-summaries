lockd: Convert NLMv3 server-side procedures to xdrgen

Summary

Overview

Chuck Lever submitted a 38-patch series to complete the migration of the NFS lock manager (lockd) server-side stack from hand-written XDR functions to code generated by xdrgen. This effort follows the earlier completion of the NLMv4 conversion. The primary goals are improved memory safety, reduced maintenance burden, and exact adherence to the Open Group XNFS specification.

"The goals of replacing hand-written XDR functions with ones that are tool-generated are to improve memory safety and make XDR encoding and decoding less brittle to maintain." Chuck Lever

Key Technical Arguments and Changes

Bug Fixes in NLMv4 (Patches 01–05)

The series begins with five fixes for issues identified in the previous NLMv4 xdrgen conversion:

  1. Spurious Warnings: Patch 01 stops a spurious pr_warn_once warning when nlm__int__drop_reply (status 30000) is encountered in non-V4 builds, distinguishing it from other internal sentinels like deadlock or stale file handle errors.
  2. Documentation Correction: Patch 02 corrects kernel-doc comments for NLMv4 GRANTED callbacks, clarifying that NLM4_DENIED_GRACE_PERIOD refers to the client's grace period after reboot, not the server's.
  3. Deadlock Translation: Patch 04 fixes a regression where the internal sentinel nlm__int__deadlock was placed directly on the NLMv4 wire instead of being translated to nlm4_deadlock, causing clients to reject the reply.
  4. Unnecessary Initialization: Patch 03 removes a redundant locks_init_lock() call in the NLMv4 GRANTED path, as subsequent code overwrites the relevant fields.
  5. Host Lookup Semantics: Patch 05 restores legacy behavior by using an unmonitored host lookup for LOCK_MSG callbacks, preventing RPC-level errors when NSM upcalls fail and ensuring clients receive proper NLM denials instead of silent failures.

Structural Refactoring (Patches 06–12)

To avoid naming collisions between machine-generated types (which follow the protocol specification) and internal lockd types, Chuck renamed several internal structures:

  • struct nlm_cookie → lockd_cookie
  • struct nlm_lock → lockd_lock
  • struct nlm_args → lockd_args
  • struct nlm_res → lockd_res
  • struct nlm_reboot → lockd_reboot
  • struct nlm_share → lockd_share

Patch 06 introduces the new RPC language description file Documentation/sunrpc/xdr/nlm3.x, derived from the Open Group XNFS specification, which serves as the source for all generated code.

NLMv3 Procedure Conversion (Patches 13–35)

The bulk of the series converts each NLMv3 server-side procedure (NULL, TEST, LOCK, CANCEL, UNLOCK, GRANTED, and their MSG/RES variants, plus SHARE, UNSHARE, NM_LOCK, FREE_ALL, and SM_NOTIFY) to use xdrgen functions.

Key implementation details include:

  • Wrapper Structures: Generated argument types are bridged with legacy lockd internals via wrapper structs. Handlers access generated fields through argp->xdrgen while populating legacy members explicitly.
  • Memory Initialization: .pc_argzero is cleared for converted procedures because xdrgen decoders initialize their own substructures. This requires handlers to explicitly initialize any wrapper fields they read.
  • Range Clamping: The 32-bit range limit for NLMv3 TEST conflict-holder byte ranges is clamped at the procedure function level rather than inside the encoder, separating data conversion concerns from local byte-range constraints.
  • Cookie Handling: A legacy HP-UX workaround that rewrote zero-length cookies into four-byte zeros was removed. Chuck noted that "HP-UX has reached end of support, and NLM_TEST reply matching relies on the RPC XID rather than the NLM cookie."

Cleanup (Patches 36–38)

The series concludes by removing unused C macros, dead code from fs/lockd/xdr.c, and unifying the cast_status helper.

Review and Conclusions

Jeff Layton reviewed the series and noted a potential regression identified by an AI-assisted review process:

"I got a sketchy review from Gemini that I had Claude validate that looks valid. You may want to add the memset() it recommends." Jeff Layton

The concern was that nlm4svc_lookup_file() copies only fh.len bytes of the file handle without zeroing the remainder, while .pc_argzero = 0 removes the defensive memset of the argument buffer. This could lead to non-deterministic hashing for handles shorter than 32 bytes.

Chuck clarified that this regression was introduced by the previous NLMv4 series and does not affect the current NLMv3 conversion:

"This appears to be a regression introduced by the (previous) NLMv4 series, and does not affect the current NLMv3 xdrgen conversion. I can post a fix for this later today." Chuck Lever

Jeff acknowledged the distinction and provided his Reviewed-by tag:

"The series itself seems mostly mechanical. You can add: Reviewed-by: Jeff Layton jlayton@kernel.org" Jeff Layton

Conclusion

This series represents a significant step in modernizing the Linux NFS lock manager infrastructure. By converting NLMv3 server-side procedures to xdrgen-generated code, the kernel maintains exact compliance with the protocol specification while reducing manual maintenance overhead. The identified file-handle zeroing issue, while real, is scoped to the prior NLMv4 work and will be addressed separately.
