mm: RWF_DONTCACHE writeback performance improvements (v6 Review & v7 Prep)

Overview

This week's activity in this thread serves as a bridge between the submission of Patch Series v6 (last week) and the subsequent posting of Patch Series v7 (later this week, summarized separately). The discussion focuses on Andrew Morton's feedback regarding static analysis findings from the Sashiko tool and Jeff Layton's confirmation that he is addressing these issues for the next iteration.

The series remains a critical performance improvement and bug fix effort for the RWF_DONTCACHE writeback path, which has significant implications for NFS client development by reducing tail latencies and improving throughput parity with buffered I/O.

Key Technical Arguments & Evolution

1. Sashiko Static Analysis Feedback

Last week, Jeff Layton submitted v6 of the series, which introduced per-bdi_writeback tracking for DONTCACHE dirty pages and replaced inline writeback submission with a background flusher kick. The series had already addressed concurrency bugs found by Sashiko in previous versions and received Reviewed-by tags from Jan Kara.

This week, Andrew Morton pointed out that Sashiko had identified additional issues in the v6 posting:

"Sashiko seems to have found more stuff: https://sashiko.dev/#/patchset/20260505-dontcache-v6-0-66463805dd6a@kernel.org" Andrew Morton

Morton's comment, while brief, highlighted the ongoing importance of automated static analysis in validating complex VM writeback changes.

2. Preparation for v7

In response, Jeff Layton confirmed that he was already aware of the new Sashiko findings and had begun addressing them. He also noted that he had utilized AI-assisted code reviews to identify further issues:

"I saw those after I sent the last set and have been working on addressing them. I've also found a couple more via dueling Gemini and Claude reviews." Jeff Layton

Layton announced that a v7 posting would arrive early the following week. This v7 series (summarized in a separate thread this week) expanded to three patches, adding a fix for preserving PG_dropbehind during folio splits, and received broad approval from Jan Kara, David Hildenbrand, Christian Brauner, and Ritesh Harjani.

Significance for NFS Client Development

The RWF_DONTCACHE flag is increasingly important for NFS clients that need to ensure data is written to stable storage without polluting the page cache with data that will not be reused. The previous inline writeback implementation caused severe tail latency issues (p99.9 latency inflated from 23ms to 93ms).

The v6/v7 series resolves this by:

  1. Targeted Dirty Tracking: Using WB_DONTCACHE_DIRTY counters to track DONTCACHE pages separately.
  2. Background Writeback: Kicking the writeback flusher instead of submitting I/O inline, which reduces tail latency by ~99.7% and improves single-stream throughput by over 200%.

These improvements ensure that NFS clients using RWF_DONTCACHE can achieve performance parity with buffered I/O while maintaining strict durability guarantees.

Final Conclusions

This week's discussion was brief but pivotal, marking the transition from v6 to v7. The key takeaway is Layton's proactive response to static analysis feedback and his commitment to a refined v7 series, which has since been posted and reviewed positively. The series is expected to be merged into the mainline kernel, delivering substantial performance benefits for DONTCACHE workloads, including NFS clients.
