Case Folding v14 Series Merged into VFS; Integration Guidance for NFSD

Summary

This week marks the culmination of a long-running effort to expose filesystem case-folding behavior across the Linux VFS and network file systems. Following the posting of v14 last week, Christian Brauner has merged Chuck Lever's 15-patch series into the vfs.git tree, completing the integration of this new feature.

Series Merged: Case Folding Exposure Lands in VFS

On May 11, Christian Brauner confirmed that the "[PATCH v14 00/15] Exposing case folding behavior" series had been applied to the vfs/vfs.git repository [id://20260511-wertverlust-vorbringen-070f016f3bd4@brauner]. The patches were initially pushed to the vfs-7.2.exportfs branch, but Brauner quickly corrected this, noting:

"Now on the correct branch and pushed out."

The series was subsequently applied to the vfs-7.2.casefold branch [id://20260511-verglast-abtropfen-f5fe2ccc79ba@brauner], which is marked as shared and will not be touched again, ensuring stability for downstream integrators.

Key NFS Client and Server Changes

This series represents a new feature with critical bug-fix implications for NFS client caching correctness. The NFS-specific patches (10/15 for the client, 13/15 and 14/15 for NFSD) address interoperability issues with non-POSIX clients, particularly Windows-based NFS clients that require explicit advertisement of case-insensitive behavior.

For the NFS client (patch 10/15), key improvements include:

  • Clearing NFS_CAP_CASE_INSENSITIVE and NFS_CAP_CASE_NONPRESERVING before each probe to prevent stale capabilities from persisting across remounts or transparent state migrations.
  • Unconditional invocation of PATHCONF for NFSv2/v3 mounts, ensuring case-handling flags are set even when namlen= is pinned by the user.

For NFSD (patches 13/15 and 14/15):

  • Probes now use kernel credentials to avoid spurious access errors from MAC policies.
  • NFSv3 PATHCONF returns NFS3ERR_STALE if an LSM hook denies the case-folding query, prompting clients to purge stale filehandles rather than silently accepting incorrect semantics.

Integration Strategy Discussion

Chuck Lever raised a question regarding branch naming and integration strategy:

"Not vfs-7.2-casefold ?"

"Fwiw, I was intending to rebase nfsd-next on the vfs integration branch, which should have both vfs-7.2-casefold and vfs-7.2.exportfs merged in, along with Jeff's series that implements the infrastructure to support directory delegation properly. LMK if that's crazy talk." [id://705e1769-6a5e-440d-bf50-5e5feec2b88d@oracle.com]

Brauner provided clear guidance on the merge strategy:

"I think you should just merge: vfs-7.2.exportfs, vfs-7.2.casefold as the order doesn't matter and they don't depend on each other... If you merge in vfs.all you're subject to problems from rebases. So I'd not recommend that." [id://20260511-kaffee-therapieren-1335259c65ee@brauner]

This advice ensures that NFSD maintainers can integrate the case-folding infrastructure cleanly without being exposed to unrelated VFS churn.

Conclusion

The v14 series is now locked in and available via linux-next. The 15-patch set spans multiple filesystems (fat, exfat, ntfs3, hfs, hfsplus, xfs, cifs, nfs, vboxsf, isofs) as well as network servers (NFSD for NFSv3/v4, ksmbd for SMB). For NFS developers, the most significant impact lies in the client's ability to correctly handle case-insensitive exports—avoiding negative dentry caching errors and ensuring proper directory invalidation—and NFSD's ability to accurately report these semantics to remote clients.

As Brauner noted upon initial application:

"Please report any outstanding bugs that were missed during review in a new review to the original patch series allowing us to drop it." [id://20260511-wertverlust-vorbringen-070f016f3bd4@brauner]

The stage is now set for NFSD maintainers to rebase their trees on these VFS changes and proceed with further NFSv4 delegation work.
