NFSv4 Flexfiles: Reject zero filehandle version count to prevent kernel panic

Summary

NFSv4 Flexfiles: Rejecting Malformed Layouts with Zero Filehandle Versions

Overview

This week, a targeted bug fix was proposed to harden the Linux NFS client's Flexfiles layout driver against malformed server responses. The patch addresses a potential kernel panic triggered by a zero-count filehandle version array in flexfile layouts.

Technical Context: A KASAN-Revealed Bug

The discussion centers on a single-patch submission by Michael Bommarito, who identified a vulnerability in ff_layout_alloc_lseg(), the function responsible for decoding the filehandle-version array count from the flexfiles layout body As described in the patch.

The core issue is that the current code only rejects NULL returns from kzalloc_objs(). However, when a server sends a layout with a filehandle version count of zero, the allocation returns ZERO_SIZE_PTR. This pointer is then stored in dss_info->fh_versions, but subsequent flexfiles code paths "assume that at least one filehandle version exists," leading to undefined behavior.

The Crash Scenario

Bommarito documented a concrete failure case observed during a QEMU/KASAN run with a malformed flexfiles layout:

KASAN: null-ptr-deref in range [0x0000000000000010-0x0000000000000017] RIP: 0010:ff_layout_encode_ff_layoutupdate.isra.0+0x15f/0x750

The crash propagated through the layout return encoding path, ultimately resulting in:

Kernel panic - not syncing: Fatal exception

The Fix

The proposed solution is straightforward and defensive: reject fh_count == 0 before the allocation occurs. This approach aligns with existing validation logic already present in the flexfiles GETDEVICEINFO parser, which performs similar zero-version_count checks.

Bommarito confirmed the fix's effectiveness:

The patched kernel rejects the malformed layout without KASAN/oops/panic, and a valid fh_count=1 regression still opens, reads, and unmounts cleanly.

Classification and Impact

  • Type: Bug fix / hardening
  • Stability: Marked for Cc: stable@vger.kernel.org, indicating backport interest to stable kernels.
  • Fixes Tag: References commit d67ae825a59d ("pnfs/flexfiles: Add the FlexFile Layout Driver"), tracing the vulnerability to the initial introduction of the Flexfiles layout driver.

Conclusion

This patch represents a typical defensive programming improvement in NFS client development: closing a gap where malformed server data could trigger a kernel panic. By validating input counts before allocation, the fix ensures that invalid flexfile layouts are rejected gracefully rather than causing fatal exceptions. The patch is self-contained, well-tested against both malicious and valid inputs, and follows existing validation patterns within the flexfiles subsystem.
