Discussion on iov_iter_extract_pages() API Cleanup and NFS Client Conversion

Summary

iov_iter_extract_pages() API Design and Deprecation of iov_iter_get_pages_alloc2

This week's activity in this thread centers on a code review discussion about the iov_iter_extract_pages() library function, with significant implications for NFS client development. The original patch (from Dmitry Mantipov) addressed freeing a pagelist on error in iov_iter_extract_pages(), but the substantive discussion this week arose from a question by Caleb Sander Mateos about whether certain code paths were dead code.

The Core Question: Is There Dead Code?

Caleb Sander Mateos observed that iov_iter_extract_pages() only allocates a pages array if the initial struct page ** passed is NULL (via want_pages_array()). He noted:

"iov_iter_extract_pages() will only allocate a pages array if the initial struct page ** passed is NULL (see want_pages_array()). So the condition pages != stack_pages will never be true. Indeed, it looks like all callers of iov_iter_extract_pages() pass a non-NULL struct page **. Would it make sense for iov_iter_extract_pages() to require a pre-allocated pages array and remove support for allocating one?"

Christoph Hellwig's Response: Urgency of Page Pinning Migration

Christoph Hellwig responded on May 11, clarifying that the NULL pages argument support was intentionally designed to facilitate a broader migration away from the deprecated iov_iter_get_pages_alloc2() function. He explained:

"I think the idea was to support this to replace existing users of iov_iter_get_pages_alloc2. Which is urgently neede as those missing the proper page pinning support."

Hellwig acknowledged the tension between keeping potentially unused code paths and avoiding dead code:

"OTOH we should not keep dead code around just in case."

Implications for NFS Client Development

For NFS specifically, Hellwig noted that active work is underway to convert the NFS client away from iov_iter_get_pages_alloc2:

"For NFS, Pranjal has an initial series to convert away from iov_iter_get_pages_alloc2, which makes use of the NULL pages argument to iov_iter_extract_pages."

This indicates that the NULL pages argument support in iov_iter_extract_pages() is being actively utilized by NFS client developers as part of a critical migration to proper page pinning support — an important bug fix area given that iov_iter_get_pages_alloc2 lacks proper page pinning.

Status of Other Subsystems

Hellwig also provided context on other subsystems affected by this API evolution:

  • 9p filesystem: "Dominique had an untested patch in December that drops iov_iter_get_pages_alloc2 in favor of a much better high level approach that doesn't even involve iov_iter_extract_pages, which seems to not have made it anywhere. It would be great to get this going again."

  • Ceph (net/ceph): "net/ceph/ needs to also do work. Not an expert on the code, but given how it is based off the encryption flag it looks kinda fishy and iov_iter_extract_pages might not be the best direct replacement."

Conclusion

This discussion highlights an ongoing kernel-wide effort to deprecate iov_iter_get_pages_alloc2() in favor of iov_iter_extract_pages(), driven by the need for proper page pinning support. For NFS client development, this represents an important bug fix migration path, with Pranjal's series actively leveraging the NULL pages argument feature. The conversation underscores the balance between API cleanliness (removing dead code) and practical migration needs (keeping transitional code paths alive during subsystem conversions).
