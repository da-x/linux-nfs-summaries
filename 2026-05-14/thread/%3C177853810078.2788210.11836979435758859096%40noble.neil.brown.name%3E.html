NFSv4 Client: Directory Delegation, Leases, and atomic_open() Handling

Summary

This week’s discussion between Neil Brown and Jeff Layton focused on the interaction between NFSv4 directory delegations, local application leases, and the VFS atomic_open() mechanism. The thread is primarily a technical design discussion regarding potential bug fixes and architectural improvements in the NFS client, rather than an immediate patch submission.

Key Technical Arguments

The conversation began with Neil Brown questioning whether atomic_open() should call try_break_deleg() on a directory when a create operation is pending. He noted that the VFS layer lacks the context to determine if a create will actually occur, making generic handling "iffy."

Jeff Layton agreed, stating:

"Agreed, so I'm thinking no to doing that in generic code... I think we sort of need to leave it to the underlying fs in those cases since the kernel doesn't have enough info to do it."

Brown identified that only GFS2 (nolocks) and NFSv4 currently support leases on directories while using ->atomic_open. He suggested that GFS2's use of ->atomic_open might be unnecessary for single-client nolocks setups. For NFSv4, he highlighted the complexity:

"NFSv4 uses delegations to provide leases. So the ->atomic_open handler does have work to do to cancel any lease while keeping the delegation."

Brown proposed several solutions, including allowing ->atomic_open to return a deleg_inode, dropping the parent lock to wait safely, or ignoring the issue until his pending changes to push locking down into the filesystem are landed. He also suggested a workaround: checking for a lease and performing a separate lookup before calling ->atomic_open if a lease is present.

Evolution of the Discussion

Layton expanded the scope by noting that SMB/CIFS might also be relevant, though Ceph's kernel client lacks support for clustered leases. He questioned the necessity of GFS2's ->atomic_open implementation for single-client scenarios.

The discussion then shifted to a specific scenario: an NFS client holding a directory delegation while an application holds a local lease on that directory, followed by an open(..., O_CREAT) for a new file. Layton pointed out a critical detail about the current NFSv4 client implementation:

"FWIW, the current NFSv4 client code won't hand out leases on a directory, as struct nfs_dir_operations doesn't set the ->setlease operation, so this situation shouldn't arise."

However, he acknowledged that if such support were added in the future, the NFSv4 client would need to revoke the local application's lease itself, as servers typically do not revoke delegations from the client initiating the change.

Final Conclusions and Open Questions

The thread concluded with Layton raising a potential bug in the existing NFSv4 client-side lease implementation. He questioned whether lease breaks are correctly triggered when one application holds a read lease and another opens the same file for write on the same client:

"Now though I'm wondering if the NFSv4 client-side lease implementation is actually broken... I don't think a lease break will happen today since the activity comes from the same client."

He noted that testing is required to verify if the v4 client's local lease handling works as expected in this intra-client conflict scenario. The immediate conclusion for the atomic_open() debate was that generic VFS code should not handle delegation breaking; instead, filesystem-specific implementations (like NFSv4) must manage these complexities, potentially requiring future architectural changes to how locking and waiting are handled within the filesystem layer.
