NFSd I/O Latency on BTRFS: Root-Cause Analysis Requested

Summary

This brief thread, initiated by Lionel Cons on May 12, represents a performance troubleshooting inquiry rather than a discussion of new features or bug fixes. The focus is on optimizing the Linux NFS server (nfsd) when serving files over BTRFS, specifically in the context of virtualization workloads.

Discussion Overview

Lionel Cons opened the thread seeking advice to "drastically reduce Linux nfsd I/O latency on BTRFS," asking if placing nfsd into a realtime process class would help As asked by Lionel Cons.

Chuck Lever, a key NFS maintainer, responded by emphasizing the necessity of root-cause analysis before applying optimizations. He suggested using structured questioning—potentially aided by an LLM—to isolate the bottleneck As advised by Chuck Lever:

"For us mere humans, the first step is you need to root-cause your issue."

Lever outlined several critical diagnostic questions, including:

  • Which specific NFS operations are slow?
  • Filesystem fullness and backing storage details.
  • Transport type (TCP vs. RDMA).
  • Server CPU availability during slowdowns.
  • Potential conflicts from other clients using OPENs and LOCKs in NFSv4.

Technical Context and Findings

In his follow-up, Lionel Cons provided detailed metrics regarding his setup:

  • Workload: Read and Write operations serving single-file disk images for bhyve and qemu virtual machines.
  • Storage: A 2 PiB BTRFS filesystem, only 9% full, backed by a large hardware RAID0 with battery-backed RAM cache, presented as a single SCSI disk.
  • Transport: TCP6.
  • Hardware: 64 CPU cores and 512GB of RAM.
  • Comparison: He noted that the same setup performs better over iSCSI, indicating the latency is specific to the NFS stack or its interaction with BTRFS rather than general hardware limitations As detailed by Lionel Cons.

Conclusion

The thread concluded with the provision of system metrics but without a definitive technical solution or patch. The discussion highlights the complexity of NFS performance tuning on copy-on-write filesystems like BTRFS, particularly for virtualization workloads where low-latency random I/O is critical. No bug fixes or protocol changes were proposed; instead, the exchange underscored the importance of precise root-cause analysis in high-performance NFS deployments.
