pNFS/filelayout: Fix striped layout detection using stripe_count

Summary

pNFS/filelayout: Fix striped layout detection logic

Overview

This week, Sagi Grimberg submitted a targeted bug fix for the parallel NFS (pNFS) filelayout client code, addressing an incorrect check used to determine whether a layout is "striped." The patch was sent as a resend on May 13, indicating it had been previously circulated.

Technical Context: What is the Bug?

The issue lies in how the NFS client determines if a pNFS filelayout segment is striped across multiple Data Servers (DSs). A striped layout distributes file data across multiple storage targets for performance and redundancy. The previous logic incorrectly relied on num_fh > 1 (number of file handles) as the sole indicator of striping.

As Sagi Grimberg explained in the commit message:

"A layout can still be striped with num_fh = 1 as it is perfectly possible that both MDS and DSs can handle the same filehandle."

This means that even when a single file handle is used (potentially because the Metadata Server and Data Servers share the same handle), the data can still be striped across multiple physical storage targets. The correct indicator of striping is stripe_count > 1, which directly reflects how many stripes (data segments) exist in the layout.

The Fix

The patch modifies fs/nfs/filelayout/filelayout.c to:

  1. Primary check: Use stripe_count > 1 as the definitive test for whether a layout is striped, which is described as "the correct check to begin with."

  2. Defensive fallback: If flseg->dsaddr is unexpectedly NULL (which should not happen in normal operation), the code returns a best-guess result based on flseg->num_fh > 1. This defensive programming approach ensures robustness even in edge cases.

The patch cites a previous fix as its origin:

Fixes: a6b9d2fa0024 ("pNFS/filelayout: Fix coalescing test for single DS")

This indicates the bug was introduced or related to an earlier attempt to correct coalescing logic for single-Data Server scenarios.

Significance for NFS Client Development

This fix is important for pNFS clients operating in environments where:

  • Metadata Servers and Data Servers may share file handles
  • Layout striping decisions affect I/O path selection and performance
  • Incorrect striped/non-striped classification could lead to suboptimal data placement or coalescing behavior

The change ensures that the NFS client correctly identifies striped layouts regardless of file handle configuration, leading to more accurate layout processing and potentially improved I/O performance in pNFS deployments.

Conclusion

This is a straightforward but important bug fix in the pNFS filelayout subsystem. By correcting the striped layout detection logic from num_fh > 1 to stripe_count > 1, the patch ensures proper handling of layouts where MDS and DSs share file handles. The addition of a defensive NULL check for dsaddr further hardens the code against unexpected conditions.
