lockd: use-after-free fix for nlm_traverse_files() gets Sashiko-flagged regression, v2 promised

Summary

lockd: pin next file across nlm_inspect_file lock-drop

Type: Bug fix (NFS server / lockd) — slab use-after-free in nlm_traverse_files(), with a stable backport requested.

The bug and the proposed fix

Michael Bommarito opened the thread on Saturday, May 23 with a single-patch submission targeting fs/lockd/svcsubs.c (42 insertions, 19 deletions). The patch carries Cc: stable@vger.kernel.org and a Fixes: tag pointing at the original deadlock fix (01df9c5e918a, "LOCKD: Fix a deadlock in nlm_traverse_files()") — i.e., this is presented as repairing a hole that the earlier lock-drop fix left behind.

The core race, in Bommarito's words:

"The f_count bump pins the current file across the lock-drop, but nothing pins next. Any nlmsvc thread that holds the last reference on the file at next will, during that window, call nlm_release_file() -> nlm_delete_file() under nlm_file_mutex, hlist_del() it from the bucket, and kfree() it. When nlm_traverse_files() reacquires the mutex and the macro reads the next entry's f_list.next on the following iteration, the read lands in the freed slab."

The chosen remedy is to walk each hash bucket with two locally-pinned cursors (file and next), so the neighbour one step ahead stays alive across the unlock window:

"Pin the neighbour explicitly instead. Walk the bucket with two locally-pinned cursors at a time: file (current, pinned by the prior iteration's next bump) and next (one ahead). Drop file's pin at the end of each iteration, then advance to next, which is still alive because we hold its f_count above zero across the unlock. This bounds the walk at O(N) per bucket and never observes a freed neighbour."

He also explains why the obvious alternative was rejected:

"A naive restart-on-action variant would deadlock-spin against an nlm_release_file holder: nlm_inspect_file() does not always drain the file (it can return 1 with an RPC still holding f_count above the cleanup threshold), and the outer predicate is_failover_file() matches static attributes of the file, so a restart can keep re-finding the same un-cleanable file until the external RPC ref drops."

The patch additionally factors the f_count/list/share/lock cleanup into a helper so that the no-match path also drops stale empty files rather than leaving them in the table.

Reproduction evidence

Bommarito reports a concrete KASAN reproduction, which is notable for an NFS lockd fix:

"Reproduced under UML + KASAN with a loopback NFSv3 mount, 768 concurrent POSIX fcntl(F_SETLKW) holders, and parallel writes to /proc/fs/nfsd/unlock_filesystem forcing nlmsvc_unlock_all_by_sb() to walk the table while clients churn locks."

"BUG: KASAN: slab-use-after-free in nlm_traverse_files+0x71d/0x9d0 — Read of size 8 at addr 0000000070314800 by task nlm-init-..."

And the patched UML kernel "ran the same harness silently." The patch also carries an Assisted-by: Claude:claude-opus-4-7 trailer, making it one of the more prominently AI-assisted lockd submissions this week.

Sashiko flags a regression; v2 promised

NFS maintainer Jeff Layton replied within ten hours pointing to the Sashiko static-analysis report:

"Sashiko seems to think there is a regression here."

Bommarito confirmed the finding and split it into two items:

"Yeah, the predicate check is a real regression. I'll fix that and send a v2."

"The other one is a separate issue (nlmsvc_create_block). I never saw that path fire in my harness, but will send a separate patch if I can get that to light up."

Status / outlook

  • v1 not accepted. The predicate-check regression blocks merge of the v1 as posted; Bommarito has committed to a v2.
  • A second, independent issue was surfaced in nlmsvc_create_block — out of scope for this patch and dependent on Bommarito being able to reproduce it.
  • Stable backport pending. The original UAF is clearly stable-worthy (it's a classic list-walk use-after-free in the lockd server path), so expect the v2 to carry the same Cc: stable / Fixes: tags and to be picked up for the current -stable tree once it lands.
  • Client-side relevance: although this is a server/lockd fix, it directly affects NFSv3 clients that hold many concurrent POSIX locks (fcntl(F_SETLKW)) against a Linux NFS server during unlock-all / failover sweeps — exactly the workload the KASAN harness exercises.

No further activity in this thread within the week; watch for the v2 and any follow-up nlmsvc_create_block patch next week.
