nfsd: reset write verifier when async COPY writeback fails

The patch

This week Chuck Lever posted the long-promised companion fix to Jeff Layton's earlier "reset write verifier on deferred writeback errors" series, closing the last hole in the same class of silent data-loss bug. The two-line change lands in fs/nfsd/nfs4proc.c and is targeted at stable:

"[PATCH] nfsd: reset write verifier when async COPY writeback fails ... Fixes: eac0b17a77fb ("NFSD add vfs_fsync after async copy is done") Cc: stable@vger.kernel.org" Chuck Lever's patch

Lever walks through the failure mode in detail, explaining that async COPY captures nn->writeverf at request time and reports it to the client via CB_OFFLOAD after the worker kthread completes:

"When the post-copy vfs_fsync_range() or filemap_check_wb_err() in _nfsd_copy_file_range() reports an error, the worker correctly leaves NFSD4_COPY_F_COMMITTED clear so that CB_OFFLOAD encodes wr_stable_how as NFS_UNSTABLE, but the server's write verifier is not rotated."

The client-visible consequence is severe: a client that receives NFS_UNSTABLE in CB_OFFLOAD follows up with COMMIT to make the copied data durable. With the verifier unchanged, COMMIT returns the same value the client just received via CB_OFFLOAD, and the client concludes the copy is durable — "silently dropping the data whose writeback in fact failed." Lever notes this violates the UNSTABLE+COMMIT durability contract (RFC 7862 §15.1, RFC 8881 §18.32) and matches the bug just fixed in nfsd_vfs_write() and nfsd_commit().

The fix itself is mechanical: rotate nn->writeverf at the writeback-failure site. Because the async COPY worker has no svc_rqst, Lever explains that commit_reset_write_verifier() is not available here, so the patch calls nfsd_reset_write_verifier() directly — "mirrors the trace-less reset already used by nfsd_file_check_write_error() for the same purpose."

Review: one open question

Jeff Layton replied within ten minutes with a single, pointed review question that remains open as of this week's window:

"commit_reset_write_verifier() filters out EAGAIN and ENOSPC. Do we need the same filter here?" Layton's reply

That is a meaningful distinction: in the synchronous nfsd_vfs_write() / nfsd_commit() paths, Layton's earlier fix leaned on the helper's built-in filtering so that transient errors (EAGAIN) or full-disk conditions (ENOSPC) would not unnecessarily rotate the verifier. In the async COPY worker context — where the call site is reached after a real writeback failure reported by vfs_fsync_range() or filemap_check_wb_err() — it is not yet clear whether the same filtering semantics are appropriate, since the error has already been observed and acted upon by the time the verifier would be rotated.

Context: part of a two-patch durability fix series

This thread is the second half of a pair that landed within hours of each other on 2026-05-22. Layton's first patch — "[PATCH] nfsd: reset write verifier on deferred writeback errors" — fixed the same missing-verifier-rotation bug in nfsd_vfs_write() and nfsd_commit(), was applied to nfsd-testing the same day (commit f8cf3c1c418ef04947bc16e4a2ef8074452de593), and explicitly deferred the async COPY case to a follow-up:

"No, I don't. I didn't spot that one before. Handling it separately is probably good. That case isn't being called from nfsd context, so it'll need different handling." — Layton, in the companion thread

Lever's patch this week is that promised follow-up. Together, the two patches close every known path where a deferred writeback failure could leave the verifier unrotated and cause a client to silently lose data under the UNSTABLE+COMMIT contract.

Classification

  • Type: Bug fix (silent data loss / protocol-contract violation), not a new feature or protocol change.
  • Subtree: NFS server (nfsd) in fs/nfsd/nfs4proc.c, but the affected contract is one that NFS clients depend on for UNSTABLE write + COMMIT semantics — so client-visible behavior changes from "silently lose data" to "receive a new verifier and learn the commit failed."
  • Severity: High. The failure mode was silent data loss in the async COPY (server-side copy-on-write) path, which is among the worst classes of storage bug because there is no error signal to alert applications or operators.
  • Status as of 2026-05-28: Patch posted; one review question from Layton (re: EAGAIN/ENOSPC filtering) remains open. No "Applied" confirmation in this thread yet within the window.
