nfsd: fix silent data loss in async COPY by sampling writeback error cursor up front

Summary

nfsd: sample writeback error cursor before async COPY loop

Type: Bug fix (race condition leading to silent data loss on the NFSv4 server)

Overview

This week's thread is short but consequential. Chuck Lever posted a one-line patch to fs/nfsd/nfs4proc.c that closes a race in the asynchronous NFSD4_COPY_F_COMMITTED path, and Jeff Layton reviewed it within four minutes of posting. The fix was reported by an automated bot (sashiko-bot) and carries a Fixes: tag pointing back to the commit that introduced errseq_t-based writeback error tracking in nfsd.

The Bug

The core issue is a classic "who observed the cursor first" race, described with unusual precision in Chuck's patch message:

_nfsd_copy_file_range() samples dst->f_wb_err into "since" after the copy loop, then uses it to detect writeback errors via filemap_check_wb_err() once vfs_fsync_range() returns. Because the nfsd_file cache reuses a single struct file across requests targeting the same inode, a concurrent COMMIT or stable WRITE on dst advances dst->f_wb_err to the current mapping->wb_err via file_check_and_advance_wb_err() during its own vfs_fsync_range().

In other words, if another thread (handling a COMMIT or a synchronous WRITE) observes and advances the per-file writeback error cursor between the moment a real writeback failure lands in mapping->wb_err and the moment the COPY worker samples "since", the COPY worker captures an already-advanced cursor. The subsequent errseq_check() then sees cur == since, returns zero, and the code sets NFSD4_COPY_F_COMMITTED as if everything succeeded:

If that advancement lands between the writeback error appearing in mapping->wb_err and the COPY worker sampling "since", the worker captures the already-advanced cursor, errseq_check() sees cur == since and returns zero, and NFSD4_COPY_F_COMMITTED is set even though writeback failed. CB_OFFLOAD then encodes wr_stable_how = FILE_SYNC4, the client treats the copied data as durable, and the failure becomes silent data loss.

The consequence on the wire is severe: the server's CB_OFFLOAD callback tells the NFSv4 client that the offloaded copy completed with full durability (FILE_SYNC4), so the client has no way to detect the underlying writeback failure. Data written by the COPY is lost without any error surfacing to userspace.

The Fix

The patch moves the sampling of since from after the copy loop to the very start of _nfsd_copy_file_range():

Sample since once at the start of the function. The cursor then reflects state in effect before this COPY issues any writes, and filemap_check_wb_err() detects any error that occurs during the copy regardless of which thread first observes it. This matches the pattern used by nfsd_vfs_write() and nfsd4_clone_file_range().

By capturing the cursor before any I/O is issued, the COPY worker guarantees that any writeback error occurring during its own operation will be a new event relative to "since", no matter how many concurrent threads also advance the shared cursor. The change is a single line (1 insertion, 1 deletion) and aligns nfsd_copy_file_range() with the already-correct pattern in nfsd_vfs_write() and nfsd4_clone_file_range().

Significance for NFS Client Development

Although this is a server-side fix, its impact on the client is direct and important. The CB_OFFLOAD callback is the mechanism by which an NFSv4 client learns that a server-initiated offloaded copy (e.g., via COPY or PUTFH-based file range copy) has completed. A false FILE_SYNC4 status means the client will:

  1. Report successful completion to userspace with no retry opportunity.
  2. Consider the destination file's data fully durable, potentially skipping its own COMMIT.
  3. Have no error path to trigger recovery or re-copy.

This makes the fix a critical correctness patch for any deployment relying on NFSv4 offloaded copy (a feature increasingly used in cloud and storage-orchestration workloads). The race window is narrow but real: it requires concurrent I/O on the same destination inode, which is common in multi-client or multi-threaded server configurations.
