xprtrdma v3: Decouple request recycling from RPC completion (use-after-free fix)

Summary

xprtrdma v3: Decoupling request recycling from RPC completion

Type: Bug fix (use-after-free / DMA race in the NFS/RDMA client), with architectural cleanup.

On Tuesday, 2026-05-26, Chuck Lever posted the third revision of his "xprtrdma: Decouple req recycling from RPC completion" series — a five-patch set aimed at the kernel's NFS-over-RDMA (xprtrdma) client. The thread in this window consists solely of the patchset itself (cover letter plus patches 1–5); no reviewer discussion landed within the week. A trivial two-patch follow-up posted on June 1 confirms the series was accepted into the tree, so this v3 is effectively the final form.

The bug being fixed

The core problem is a lifetime conflation in rl_kref, the reference count that gates both when a Reply may wake its RPC task and when an rpcrdma_req may return to its free pool. As Lever frames it in the cover letter:

"rl_kref currently conflates two lifetimes through one refcount: it gates when a Reply can wake its RPC task, and it gates when an rpcrdma_req can return to its free pool."

The danger case is a Send carrying only pre-registered buffers. Because the marshal path takes the Send-side reference only when sc_unmap_count > 0, such a Send acquires no Send-side ref. If the Reply then arrives before the Send completes, the reply handler drops rl_kref from 1 to 0 and frees the request while the HCA is still DMA-reading from its send buffer:

"When the Reply for such an RPC arrives before its Send completes, the Reply handler drops rl_kref from 1 to 0 and frees the req while the HCA may still be DMA-reading from its send buffer. A retransmission can put different bytes on the wire."

That last clause is the real-world symptom: a freed-and-reused buffer means a retransmitted RPC could silently carry corrupted data. The fix carries a Fixes: tag pointing at commit 0ab115237025 ("xprtrdma: Wake RPCs directly in rpcrdma_wc_send path"), the change that introduced the direct-wake behavior.

The design

The series narrows rl_kref to a single job by splitting ownership into two distinct references:

"The RPC layer takes one reference at slot allocation; rpcrdma_prepare_send_sges() takes a Send-side reference unconditionally after WR prep succeeds. A req returns to its free pool only after both owners release."

Replies now complete the RPC directly, with no atomic activity on rl_kref. The central patch (2/5) lays out three invariants that follow from this scheme:

"Any rpcrdma_req held by an rpc_rqst has rl_kref >= 1."

Lever is explicit about why the first invariant matters — without it, an RPC task that aborts between slot allocation and marshal (a GSS refresh failure or a signal during call_connect) would drive a kref_put against a zero refcount:

"Without this invariant, an RPC task that aborts between slot allocation and marshal ... would drive xprt_release() -> xprt_rdma_free_slot() -> kref_put against a refcount of zero, saturating refcount_t and stranding the slot."

The other two invariants cover the marshal-failure path (rpcrdma_sendctx_cancel() unmaps SGEs and clears sc_req without touching rl_kref, so "a burst of -EIO marshal failures cannot hold reqs off rb_send_bufs") and the re-arming of rl_kref in the release callback before a request returns to the pool.

Supporting patches

  • 1/5 is a prep change that converts the Send-signaling test from an indirect rl_kref check to sc_unmap_count directly, "remov[ing] one dependency on the old rl_kref semantics before the request lifetime rules are changed."

  • 3/5 adds bounded headroom to the request pool. Because recycling is now gated on Send completion, a completed RPC's request can stay pinned by the sendctx ring until the next signaled Send completion. Lever bounds the worst case at max_reqs / 8 (since re_send_batch = re_max_requests >> 3, one in eight Sends is signaled) and allocates max_reqs + DIV_ROUND_UP(max_reqs, 8) objects so "the recycle delay does not stall a slot allocation that the RPC/RDMA credit window would admit." He stresses this does not raise the in-flight ceiling — the sendctx ring and hardware Send Queue are unchanged.

  • 4/5 is an ownership-hygiene pass that clears stale receive-side pointers (rr_rqst, rl_reply, rl_sendctx) on release so each pointer can be reasoned about locally rather than "tracing the whole reply path."

  • 5/5 documents and asserts the reply-handler invariants with WARN_ON_ONCE probes. Notably, Lever frames this as a defense against automated review noise:

    "The xprtrdma reply path has been the subject of recurring LLM-driven review claims that 'an RPC can complete while receive buffers are still DMA-mapped' or that 'the req can be freed while the HCA still owns the send buffer.' No runtime reproducer has surfaced, but the absence of a written-down invariant set lets each pass of automated review reach the same hypothetical conclusion."

    He states invariants I1–I5 in a comment above rpcrdma_reply_handler() and backs four of them with assertions; I5 (the request lifecycle) is documented but not probed, since making it assertible would require restructuring the kref_init placement — "That restructuring is deferred -- the invariant is unchanged either way."

Evolution across revisions

This is a mature series that has been through two prior cycles. v1 was a single patch; v2 (posted 2026-05-23) split it into three and addressed kernel-test-robot build breaks on configs without CONFIG_SUNRPC_BACKCHANNEL, plus the teardown-ordering fixes (rpcrdma_sendctxs_destroy() ordered ahead of rpcrdma_reqs_reset(), and a second xprt_rdma_bc_destroy() call to reclaim backchannel prealloc requests). The v3 changes are summarized in the cover letter:

"While addressing sashiko review comments, substantially reworked to simplify and better align the series with the current architecture of xprtrdma."

Concretely, v3 grew from three patches to five by splitting out the pointer-cleanup patch (4/5) and adding the invariant-documentation/assertion patch (5/5).

Conclusion

As of the end of this week the v3 series sat posted with no on-list discussion. The June 1 follow-up ("Fix I3 invariant comment" and "Remove tautological I2 assertion") — both trivial cleanups to the just-merged code — indicates the series was accepted, closing out a careful, multi-cycle fix for a latent use-after-free in the NFS/RDMA client's request-recycling path.
