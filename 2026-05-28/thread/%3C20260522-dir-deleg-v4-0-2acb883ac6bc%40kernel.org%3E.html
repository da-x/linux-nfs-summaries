CB_NOTIFY Directory Delegation: NFSD Patches Land as v4 on Merged VFS Base

Overview

This week marked a significant milestone in the long-running effort to add CB_NOTIFY callback support to NFSv4 directory delegations. Jeff Layton posted version 4 of the 21-patch NFSD series on May 22, a clean rebase onto Chuck Lever's nfsd-testing branch — which itself now sits atop Christian Brauner's already-merged vfs-7.2.directory.delegations branch. This is the server-side counterpart to the VFS patches that merged into vfs.git last week.

The series is fundamentally a new protocol feature: it implements RFC8881bis's CB_NOTIFY callback, allowing NFSv4 clients to register interest in directory changes (creates, unlinks, renames) and receive asynchronous notifications with updated attributes — without losing their delegation lease. The cover letter explains the goal clearly:

"With this support, the client can register interest in a directory and get notifications about changes within it without losing its lease."

Key Technical Content of the Series

The 21-patch series (2,184 insertions across 16 files) covers several distinct areas:

Protocol and XDR plumbing:

  • Patch 02 adds the CB_NOTIFY protocol definitions to the XDR grammar (nfs4_1.x) and regenerates the C code. Notably, this also removes duplicate NFS4_VERIFIER_SIZE and NFS4_FHSIZE constants from UAPI headers — Layton notes these are "defined by the RFC, and are not part of the kernel API."
  • Patch 03 adds new NOTIFY4_* flags proposed in RFC8881bis.

Lease and fsnotify integration:

  • Patches 04–05 wire up directory leases with ignore masks and maintain the fsnotify mark as delegations are added/removed.
  • Patch 08 is a notable bug fix / race condition hardening: it converts fi_deleg_file to RCU protection because "Concurrent accesses from workqueue callbacks -- such as CB_NOTIFY -- can dereference a NULL pointer if they race with this teardown." This prepares the callback path for safe lockless reference acquisition.

Callback encoding/decoding and event handling:

  • Patches 07, 09–10 add the data structures (nfsd_notify_event, nfsd4_cb_notify), fsnotify event handlers, and the logic to create CB_NOTIFY requests from directory change events.
  • Patch 12 applies the notify mask at delegation time, with an important protocol detail: "If the client doesn't set NOTIFY4_GFLAG_EXTEND, then don't offer any notifications, as nfsd won't provide directory offset information."

Attribute marshaling in callbacks:

  • Patches 13–20 are largely refactoring to allow fattr4 encoding without a svc_export/svc_fh context (unavailable in the callback path), plus tracking of which attributes the client actually requested.
  • Patch 21 completes the feature by sending directory attribute changes alongside add/remove/rename events, with the caveat that "the server will still recall the delegation on a SETATTR, so these are only sent for changes to child dirents."

Discussion and Review Activity

The review activity this week was light but pointed:

Chuck Lever's nit on patch 20/21: Chuck Lever offered a minor clarification about the split between patches 20 and 21:

"Nit: The encode-time use of dl_notify_mask for NOTIFY4_CHANGE_DIR_ATTRS is wired up in 21/21. This patch adds only the tracking; the per-event encoder change lives in the subsequent patch."

This is a documentation/clarity suggestion rather than a functional objection — Lever is noting that a reader might expect the encode path to be active in patch 20, when it actually isn't until the next patch.

Steven Rostedt's tracepoint question: Steven Rostedt (who had already provided a Reviewed-by on patch 11) flagged that the new tracepoint references a show_fsnotify_mask() helper he couldn't find in any repo:

"Hmm, I don't have the show_fsnotify_mask() function in my repos and don't see it defined in the patch series (I scanned lore). Have a link to the patch or repo that creates it?"

Jeff Layton responded within minutes, pointing him to the right place:

"The series is in the dir-deleg branch of my kernel.org repo."

This was a straightforward resolution — the helper lives in the VFS-side patches that were merged last week into vfs-7.2.directory.delegations, which Rostedt hadn't pulled yet.

Evolution from Prior Weeks

As documented last week, the VFS-side patches (01–07 of the original 28-patch v3 series) were merged by Christian Brauner into vfs-7.2.directory.delegations on May 15, and Chuck Lever confirmed the NFSD merge prerequisites would be met "end of this week? Early next?" This v4 posting fulfills that expectation: the NFSD patches are now rebased onto the merged VFS base and ready for Chuck's nfsd tree.

The v4 changes from v3 are minimal — just the rebase and "minor contextual fixups" — indicating the series has stabilized after the substantive fixes in v2 (cross-directory rename handling, fsnotify mask recalculation ordering, not notifying the making client) and v3 (error handling crash fix in alloc_init_dir_deleg()).

Significance for NFS Client Development

While this is server-side work, the CB_NOTIFY infrastructure is a prerequisite for a meaningful client-side improvement. Once the Linux NFS client implements the corresponding callback handler, clients will be able to:

  • Maintain directory delegations across creates/unlinks/renames (currently these trigger delegation recalls)
  • Receive push notifications with up-to-date attributes and filehandles
  • Reduce round-trips for workloads that monitor directory contents

Layton's caveat remains relevant: "I don't think we'll want to merge these until we have a complete client-side implementation to test against." The server code is now in good shape, but full integration will await the client counterpart.
