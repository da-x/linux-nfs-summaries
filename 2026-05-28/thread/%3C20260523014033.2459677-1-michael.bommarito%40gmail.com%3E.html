pNFS client: kernel panic from malformed GETDEVICEINFO — NULL-deref + unbounded multipath loop fix

Summary

pNFS client: kernel panic from a 56-byte malformed GETDEVICEINFO

Type: Bug fix (NFSv4 / pNFS client) — a remotely-triggerable kernel NULL-pointer dereference in the pNFS flexfile and legacy file layout drivers, plus a latent unbounded-decode loop. Stable backport requested for all three Fixes: targets.

The bug: a malicious metadata server can panic any pNFS-flexfile client

Michael Bommarito opened the thread on Saturday, May 23 with a two-patch series describing a clean, deterministic client crash reachable purely over the wire:

"A malicious or compromised NFSv4.1+ pNFS metadata server can panic any pNFS-flexfile client by returning a GETDEVICEINFO body with a multipath-DS count of >= 3 and exactly one valid (netid, uaddr) pair."

The mechanics are an XDR-decode slip in nfs4_decode_mp_ds_addr(). The decoder pulls the r_netid/r_addr opaques out of a netaddr4 via xdr_stream_decode_string_dup() and then immediately calls strrchr(buf, '.') to find the port separator. But when the on-wire opaque has length zero, that helper sets *str = NULL and returns 0 — and the caller only checks < 0:

"The caller in nfs4_decode_mp_ds_addr() only checks '< 0' and immediately calls strrchr(NULL, '.')."

Because the inner multipath loop is unbounded, a server that lies about mp_count keeps iterating past the one valid pair and consumes the trailing version_count/version/minor words of the body as bogus netid+uaddr pairs — both decoding to zero-length strings, hence the NULL deref. Bommarito nails down how cheap and reliable the trigger is:

"The shortest crashing GETDEVICEINFO body is 56 bytes, the panic is 5/5 deterministic at multipath_count = 10, and it fires before any user-level read can complete on the first pNFS file the client touches."

He backs this with a concrete KASAN oops (Linux 7.0-rc7 + KASAN under QEMU/KVM), showing the crash landing in strrchr via nfs4_decode_mp_ds_addr → nfs4_ff_alloc_deviceid_node → nfs4_find_get_deviceid, with a full read-path call trace down to do_sendfile:

"Oops: general protection fault [#1] SMP KASAN NOPTI … RIP: 0010:strrchr+0x24/0x80 … Kernel panic - not syncing: Fatal exception"

He also notes the crash threshold is sharp: with multipath_count <= 2 "the loop ends before consuming the malformed trailing bytes," so it does not fire.

The two-patch fix

The series splits into a direct NULL-deref close and a defense-in-depth bound, with Bommarito stressing that either one alone stops the panic but only together do they retire the whole class:

"Either patch alone closes the panic; both together close the latent unbounded-decode class."

Patch 1/2 is a two-line change in fs/nfs/pnfs_nfs.c: flip the two return-value checks on xdr_stream_decode_string_dup() from < 0 to <= 0, so a zero-length decode fails with -EBADMSG (treated as a malformed GETDEVICEINFO body) instead of dereferencing NULL. It carries Fixes: 6b7f3cf96364 ("nfs41: pull decode_ds_addr from file layout to generic pnfs") — the commit that unified the netaddr decode and introduced the NULL-deref site.

Patch 2/2 is the structural fix. It promotes NFS4_PNFS_MAX_MULTI_CNT (== 256) from a filelayout-private header up into include/linux/nfs4.h so both drivers share it, caps the inner mp_count loop in both the flexfile and legacy file layout drivers against that constant, and bails on the first NULL return from nfs4_decode_mp_ds_addr(). The unbounded-loop exposure is old:

"The unbound on mp_count predates the flexfile driver: the same loop exists in the legacy file layout since 35124a0994fc … and was carried into flexfile by d67ae825a59d."

Hence two Fixes: tags (the 2011 LAYOUTGET/GETDEVICEINFO XDR cleanup and the 2014 FlexFile driver introduction). Without the bound, Bommarito warns, a hostile server can "drive the inner loop indefinitely (up to 2^32 - 1 iterations) against a fixed-size 56-byte body, with each iteration triggering an allocation / kmemdup_nul cycle."

Both patches carry Cc: stable@vger.kernel.org and an Assisted-by: Claude:claude-opus-4-7 trailer — part of a busy week for Bommarito on the list (see the sibling lockd UAF series this same week).

Review: Anna Schumaker's minor nits

NFS client maintainer Anna Schumaker replied on Tuesday, May 26 to Patch 2/2 with two small editorial asks rather than any objection to the approach:

"I don't think we need the comment saying that the value has moved." (re: a leftover note in filelayout.h about NFS4_PNFS_MAX_MULTI_CNT relocating)

"In the original location, this had a comment saying where the 256 came from. Can you carry that over to here too, please?"

Status / outlook

  • Not yet merged. The series is in review; Schumaker's two nits are cosmetic (drop a redundant comment, restore the provenance comment on the 256 constant), so a v2 is expected and unblocking should be quick.
  • Stable backport pending for all three Fixes: commits (6b7f3cf96364, 35124a0994fc, d67ae825a59d) — appropriate given this is a trivially-triggered remote client panic.
  • Client-side relevance: this is squarely an NFS client bug — any pNFS-flexfile (or legacy file-layout) client mounted against a malicious or compromised metadata server can be crashed before its first read completes. The fix hardens the XDR decode path in fs/nfs/pnfs_nfs.c and both layout drivers, closing the NULL-deref and the unbounded-decode class in one go.
