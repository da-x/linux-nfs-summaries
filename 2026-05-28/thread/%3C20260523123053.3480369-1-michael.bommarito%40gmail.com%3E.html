lockd: v2 of nlm_traverse_files() UAF fix lands, but Codex/Sashiko both flag a new leak in the skip path

Summary

lockd: v2 of nlm_traverse_files() use-after-free fix posts; reviewers flag a fresh reference-count leak

Type: Bug fix (NFS server / lockd) — slab use-after-free in nlm_traverse_files(), with a stable backport requested. This is the v2 follow-up to Michael Bommarito's v1 submission earlier in the week, which was held up after Sashiko flagged a predicate-check regression (see last week's summary for the v1 backstory).

The bug and the v2 fix

Bommarito posted the v2 patch on Saturday, May 23, again targeting fs/lockd/svcsubs.c (44 insertions, 20 deletions) and carrying the same Cc: stable@vger.kernel.org and Fixes: 01df9c5e918a ("LOCKD: Fix a deadlock in nlm_traverse_files()") tags as v1. The underlying race is unchanged from v1:

"nlm_traverse_files() pins the current file with f_count++ across a mutex_unlock for nlm_inspect_file(), but nothing pins the saved next pointer. A concurrent nlm_release_file() can kfree the next file during the unlock window, and the iterator dereferences freed memory on the next loop step."

The fix walks each hash bucket with two locally-pinned cursors:

"Pin both current and next before the lock-drop. Advance by swapping the pinned cursors at the end of each iteration so next is always held alive across the unlock."

What changed since v1

The v2 cover letter explicitly addresses the regression Sashiko had flagged on v1, which Bommarito had acknowledged and promised to fix in the prior thread:

"Fixed premature kfree of non-matching files: nlm_file_release() is now called only for files that matched the predicate and were inspected. Non-matching files just get f_count-- to undo the iteration pin."

The rationale is spelled out in the commit message:

"Only call nlm_file_release() for files that matched the predicate and were inspected. Skipped files just get f_count-- to undo the iteration pin; their f_locks is stale and must not drive cleanup."

Bommarito credits Sashiko's automated review for catching this one ("Spotted by sashiko.dev automated review"), and the patch again carries an Assisted-by: Claude:claude-opus-4-7 trailer. The KASAN reproduction harness from v1 is unchanged — UML + KASAN with 768 concurrent POSIX holders and parallel /proc/fs/nfsd/unlock_filesystem writes — and the patched v2 kernel reportedly "ran the same harness silently."

Chuck Lever's review: a new leak in the skip path

NFS maintainer Chuck Lever replied within three hours, this time relaying a finding from an AI code review (Codex / gpt-5.5 xhigh) rather than a human reviewer:

"When nlmsvc_unlock_all_by_sb() skips a file from another superblock, this branch can be handling an entry that was already pinned as the previous file's saved next. If that entry's last real nlm_release_file() ran while the traversal pin was held, it saw f_count > 0 and skipped nlm_file_inuse()/deletion; this decrement then takes f_count to zero without any cleanup, leaving the nlm_file and its open f_file references hashed indefinitely."

In other words, the very f_count---only path that v2 introduced for non-matching files can strand an nlm_file entry in the hash table forever: the real release was suppressed by the traversal pin, and then the iteration's decrement drives the count to zero without ever calling the cleanup helpers. Lever notes this is not a novel observation — Sashiko had flagged the same issue on the v2 patchset itself (linked at sashiko.dev).

Status / outlook

  • v2 not yet accepted. The Codex/Sashiko finding on the cross-superblock skip path blocks merge as posted; expect a v3 that handles the case where a skipped entry's last real release was already deferred by the traversal pin.
  • Stable backport still pending. The original UAF remains clearly stable-worthy, so the eventual clean version should land in -stable alongside mainline.
  • Client-side relevance: although this is server/lockd code, it directly affects NFSv3 clients holding many concurrent POSIX locks (fcntl(F_SETLKW)) against a Linux NFS server during nlmsvc_unlock_all_by_sb() / failover sweeps — the exact workload the KASAN harness exercises.
  • Notable pattern: both v1 and v2 of this patch were caught by automated reviewers (Sashiko, and now Codex) before human sign-off — an increasingly common workflow on linux-nfs this week.
