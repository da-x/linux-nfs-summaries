nfsd: Fix NULL pointer deref after FOREIGN PUTFH in inter-SSC COPY flow

Summary

nfsd: Block non-SAVEFH ops after FOREIGN PUTFH to prevent NULL deref

Type: Bug fix (security-relevant — remote-triggerable NULL pointer dereference in the NFSv4 server)

Overview

On Wednesday, May 27, Jeff Layton posted a single-patch fix for a NULL pointer dereference in the Linux NFSv4 server (nfsd) that is remotely exploitable when the CONFIG_NFSD_V4_2_INTER_SSC option is enabled. The patch was picked up within hours by nfsd maintainer Chuck Lever, who applied it to the nfsd-testing tree the same afternoon.

The Bug

The vulnerability sits in the NFSv4 COMPOUND dispatch loop. When a server-to-server (inter-SSC) COPY is in progress, the source filehandle may legitimately be "foreign" — i.e., not resolvable on the local server. To support this, an earlier commit (3ad685d73ed8, "NFSD: allow inter server COPY to have a STALE source server fh") introduced logic that lets nfsd4_putfh() return success even when fh_verify() fails with nfserr_stale, provided the PUTFH was flagged with no_verify (set by check_if_stalefh_allowed() during an inter-SSC COPY).

The problem: while the NFSD4_FH_FOREIGN flag was set, the dispatch loop only used it to skip the generic "no filehandle" error check. It did not prevent subsequent operations in the COMPOUND from executing with both fh_dentry and fh_export left NULL.

As Layton described in the patch submission:

"A remote client can exploit this by crafting a COMPOUND that includes an inter-SSC COPY (which causes check_if_stalefh_allowed() to set no_verify=true on the saved PUTFH) with an additional op inserted between the source PUTFH and SAVEFH. For example, SETATTR calls fh_want_write() which dereferences fh_export->ex_path.mnt without calling fh_verify() first, causing a NULL pointer dereference in the nfsd kthread."

In other words, a malicious client could interleave an arbitrary operation (such as SETATTR) between the foreign PUTFH and the SAVEFH that the inter-SSC COPY flow expects, triggering a crash in the server kernel thread.

The Fix

The patch (16 insertions, 3 deletions in fs/nfsd/nfs4proc.c) adds a gate in the compound dispatch loop: when NFSD4_FH_FOREIGN is set and fh_dentry is NULL, only two categories of operations are allowed to proceed:

  1. OP_SAVEFH — required by the inter-SSC COPY flow to restore the saved filehandle state.
  2. Ops flagged with ALLOWED_WITHOUT_FH — operations that do not require a resolved filehandle at all.

Every other operation receives NFS4ERR_STALE, which Layton justified by citing the protocol:

"All other ops receive nfserr_stale, per RFC 7862 Section 15.2.3 which specifies that foreign filehandle validation is deferred to the consuming operation and NFS4ERR_STALE returned at that point."

The patch carries a Fixes: tag pointing to the original inter-SSC COPY commit and an Assisted-by: Claude:claude-opus-4-6 trailer, indicating AI-assisted development.

Resolution

Chuck Lever confirmed in his reply just under three hours later:

"Applied to nfsd-testing, thanks!"

The commit landed as d8db9ced22a876091c432c4adb35e5d05be196aa in the nfsd-testing tree. No further discussion or review comments were posted before application, suggesting the fix was straightforward and well-understood by the maintainer.

Significance

This is a notable security fix for NFS server deployments that enable inter-server synchronous sequential copy (inter-SSC), an NFSv4.2 feature. The bug allowed a remote, unauthenticated client to crash the nfsd kernel thread via a carefully crafted COMPOUND request — a denial-of-service vector. The quick turnaround from submission to application highlights the responsiveness of the nfsd maintenance process for security-relevant fixes.
