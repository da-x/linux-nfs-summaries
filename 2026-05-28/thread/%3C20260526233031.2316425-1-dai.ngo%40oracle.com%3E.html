pNFS client: defer return_range callbacks to fix "scheduling while atomic" on unmount

Classification

This is a bug fix in the NFSv4 pNFS client, not a new feature or protocol change. It corrects a locking-ordering defect in the layout-return path that can fire a BUG: scheduling while atomic warning when an NFS filesystem with pNFS SCSI (block) layouts is unmounted.

This week's activity

The thread consists of a single message this week: Dai Ngo's patch submission on 2026-05-26, [PATCH 1/1] NFSv4/pnfs: defer return_range callbacks until after inode unlock](https://lore.kernel.org/linux-nfs/20260526233031.2316425-1-dai.ngo@oracle.com/). No replies, reviews, or follow-ups had landed by the end of the reporting window (2026-05-29), so the discussion is still in its opening phase.

The bug

Dai Ngo opened with a concrete failure scenario:

"Sometimes unmounting an NFS filesystem mounted with pNFS SCSI layouts triggers the following warning: BUG: scheduling while atomic: umount.nfs4/..."

The attached stack trace walks through the entire problem path in one breath: umount → nfs_kill_super → evict_inodes → nfs4_evict_inode → _pnfs_return_layout → ext_tree_remove (blocklayoutdriver) → nfs4_put_deviceid_node → bl_free_deviceid_node → bl_free_device → bl_unregister_dev → bl_unregister_scsi → sd_pr_out_command → scsi_execute_cmd → blk_execute_rq → io_schedule_timeout → schedule.

The root cause, as Dai Ngo explains:

"The warning occurs because the block layout driver unregisters the SCSI device while the inode lock is still held. Device unregistration issues a SCSI PR command, which may sleep, resulting in a 'scheduling while atomic' warning."

More specifically:

"During layout return, ext_tree_remove() invokes the layout driver's return_range callback while holding the inode lock. For block layouts, this callback eventually calls bl_unregister_scsi(), which may block in scsi_execute_cmd() while issuing PR commands to the device."

This is a classic sleeping-in-atomic-context bug: the pNFS extent-tree removal code calls back into the layout driver while still under the inode's truncation lock (a non-sleepable context), but the block layout driver's return_range implementation needs to issue SCSI Persistent Reservation commands that can block.

The fix

The patch defers the return_range callbacks until after the inode lock has been released:

"Fix this by deferring the return_range callbacks until after the inode lock has been released. The layout header reference count is incremented before invoking return_range(), ensuring that the layout header remains valid while the layout driver removes extents from the extent tree."

The diffstat is minimal — fs/nfs/callback_proc.c (9 lines changed) and fs/nfs/pnfs.c (4 lines changed), 7 insertions, 6 deletions total. The key design decision is bumping the layout header's reference count before dropping the lock, so the layout structure cannot be freed out from under the deferred callback while it is still manipulating the extent tree.

The Fixes: tag points at commit c88953d87f5c8 ("pnfs: add return_range method"), identifying the original introduction of the return_range callback as the point where this locking-ordering hazard was introduced.

Why this matters for NFS client development

This bug affects any Linux NFSv4.2 client using pNFS with SCSI block layouts — a configuration common in high-performance storage deployments (e.g., Oracle ZFS Storage, NetApp ONTAP with block layout, or custom RDMA-based backends). The "scheduling while atomic" warning is not merely cosmetic:

  • It indicates the kernel attempted to sleep while holding a spinlock or in an RCU/atomic section, which can corrupt lock state on some architectures.
  • In production systems with panic_on_warn enabled (common in cloud and HPC environments), this would trigger a full kernel panic during unmount.
  • The bug is intermittent ("Sometimes unmounting..."), making it particularly insidious — it depends on whether the SCSI PR command actually needs to wait for I/O completion.

The fix is squarely in client-side code (fs/nfs/pnfs.c and fs/nfs/callback_proc.c), addressing a core pNFS layout lifecycle issue that any block-layout user would encounter during filesystem teardown.
