NFSD: fh_compose Wrong-Dentry Fix Applied to nfsd-testing

Overview

This thread tracks the final disposition of Patch 1/2 in NeilBrown's two-patch bug-fix series addressing edge-case problems in the NFS server's use of atomic_open() within dentry_create(). The only in-window message this week is Chuck Lever's confirmation that both patches have been applied to nfsd-testing.

This is a bug fix series targeting the NFS server's file-creation path, closing residual edge cases introduced by commit 64a989dbd144 ("VFS/knfsd: Teach dentry_create() to use atomic_open()").

The Bug (from NeilBrown's original patch description)

The core issue is a potential use-after-free in nfsd4_create_file():

"dentry_create() can hypothetically provide a different dentry than the one passed in. This could happen, for example, if the exported filesystem is NFS, and the server return to OPEN a filehandle which matched a directory that was already in the dcache."

If this occurred, the original child dentry stored in resfhp could be freed and later dereferenced when fh_compose() was called. The fix moves the fh_compose() call to two explicit sites — one for the already-exists path, one after dentry_create() succeeds — so the filehandle is always composed from the final dentry:

"We shouldn't call fh_compose() until we are certain that we have the final dentry."

Resolution This Week

Chuck Lever (May 27) confirmed both patches are now in nfsd-testing:

"Applied to nfsd-testing, thanks!"

He recorded the commit for Patch 1/2:

  • [1/2] nfsd: fix possible fh_compose of wrong dentry in nfsd4_create_file() — commit 2dfca2b82c375e2a534447331ecd7056cb139dce

Patch 2/2 ("nfsd: ensure nfsd_file_to_acquire() does not use a non-opened file") was also applied but Chuck noted "(no commit info)" at the time of his reply, suggesting it was applied by hand without a formal git am record.

Context from Earlier This Week

The broader discussion (tracked in the companion thread on the cover letter) included:

  • Swift review: Both patches received Reviewed-by tags from Jeff Layton and Benjamin Coddington within hours of posting on May 26.
  • Base-tree friction: Chuck initially reported the patches didn't apply cleanly to nfsd-testing. NeilBrown clarified he'd based them on nfsd-next, and that patch 1 applied perfectly while patch 2 had a minor offset.
  • Process guidance: Chuck escalated this into community-wide guidance, noting: "The second patch doesn't apply to nfsd-testing without conflicts. It's not just a 'Hunk succeeded' issue for me. That's a red flag." He recommended contributors base patches on current nfsd-testing and use the b4 am → git apply/stg import flow for reliable patch retrieval.

Significance

While these are server-side fixes (not client), they matter to the broader NFS ecosystem:

  • They close theoretical use-after-free and unopened-file-dereference vectors in a network-facing service, which is critical for server robustness.
  • The scenario NeilBrown described — an NFS export where the backing filesystem is itself NFS — is precisely the kind of configuration that stresses the client-server interaction boundary, making these fixes relevant to anyone running stacked NFS configurations.
  • Chuck's process guidance about basing patches on nfsd-testing reflects the subsystem's continued maturation in contribution workflows, particularly as large feature series (like CB_NOTIFY directory delegation) push through in rapid succession.

Status

  • Both patches: Reviewed and applied to nfsd-testing.
  • No further action needed on this thread.
