sunrpc: Pin svc_xprt across async TLS handshake callback (slab-corruption bug fix)

Summary

sunrpc: Pin svc_xprt Across the Asynchronous TLS Handshake Callback

Type: Bug fix — a slab-corruption race in the kernel NFS server (net/sunrpc/svcsock.c) that is reachable on any TLS-enabled NFS server. Though it lands in the shared SUNRPC transport layer, it matters to client developers because it governs the TLS handshake path clients exercise when connecting to a tls-flavored mount.

The patch (Thursday, 2026-05-22)

Chuck Lever posted the fix, authored by Chris Mason (Meta) with an Assisted-by: kres (claude-opus-4-7) tag and a [cel: rewrote commit message to describe the actual change] note — a small 6-line addition to net/sunrpc/svcsock.c, but one that closes a genuinely nasty use-after-free.

The core problem, as Lever's commit message lays out it:

"svc_tcp_handshake() stores the raw svc_xprt pointer in tls_handshake_args.ta_data and submits the request through tls_server_hello_x509(). The handshake core takes only sock_hold(req->hr_sk); nothing references the embedding struct svc_sock that svc_tcp_handshake_done() reaches via container_of()."

Two distinct close races were identified, both leaving an in-flight callback writing through a freed svc_sock:

  1. The svc_sock_free() race. The free path calls tls_handshake_cancel() and discards its return value. A false return means handshake_complete() already set HANDSHAKE_F_REQ_COMPLETED but hp_done() may not have finished — yet the code proceeds straight to kfree(svsk).
  2. The cancel-loser fall-through inside svc_tcp_handshake() itself. When wait_for_completion_interruptible_timeout() returns ≤ 0 (timeout or signal) and tls_handshake_cancel() also returns false, the function does not drain; it returns, svc_handle_xprt() calls svc_xprt_received(), which clears XPT_BUSY and can drop the last reference. A concurrent close then runs svc_sock_free() while svc_tcp_handshake_done() is still touching xpt_flags and walking svsk->sk_handshake_done.

Lever was emphatic about how severe the resulting corruption is:

"The corruption surfaces as set_bit/clear_bit RMW into the freed xpt_flags slab slot and as complete_all() walking and writing the freed wait_queue_head_t list embedded in sk_handshake_done -- a slab-corruption primitive, not a benign read."

He also stressed how easy the trigger is:

"The path is reachable on any TLS-enabled NFS server whenever a connection close overlaps the tlshd downcall delivery window; the interruptible wait means signal delivery suffices, not just SVC_HANDSHAKE_TO expiry."

The fix

The remedy is a classic lifetime pin. Take svc_xprt_get(xprt) immediately before tls_server_hello_x509() so the in-flight callback owns its own reference, and release it at exactly the two edges where the callback is guaranteed not to fire — submission failure from tls_server_hello_x509() and a successful tls_handshake_cancel() — plus at the tail of svc_tcp_handshake_done() after complete_all(). The patch carries:

"Fixes: b3cbf98e2fdf ("SUNRPC: Support TLS handshake in the server-side TCP socket code")"

Review and outcome

The discussion was short and decisive. About eight hours later, Jeff Layton replied with an unqualified:

"Reviewed-by: Jeff Layton jlayton@kernel.org"

No objections, no alternative designs proposed, and no follow-up messages in the thread this week. The patch is effectively ready for merge — a clean, well-scoped 6-line fix that removes a slab-corruption primitive from the TLS handshake path of every Linux NFS server.

Context for client developers

While the bug lives on the server side of SUNRPC, it directly affects any deployment where clients mount over TLS: a misbehaving or simply closing client connection could previously corrupt kernel memory on the server mid-handshake. The fix tightens reference-counting around the asynchronous tlshd downcall window, so the in-flight handshake callback can no longer outlive its transport.
