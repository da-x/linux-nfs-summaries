NFSD Directory Delegation Follow-On Fixes: Four Small Patches Applied to nfsd-testing

Overview

Following the rapid application of the 21-patch CB_NOTIFY directory delegation series (v5) to nfsd-testing on May 23, Jeff Layton posted a small four-patch follow-on series on May 23 to address additional issues flagged during Sashiko's review. The patches are all bug fixes — small, targeted corrections to the newly landed code that Layton described as "None [are] super-critical but it'd be good to have them fixed before the feature ships."

Chuck Lever applied all four patches to nfsd-testing within an hour of posting, confirming:

"Applied to nfsd-testing, thanks!"

A minor post-apply correction was needed for patch 4/4 (a tracepoint format specifier), which Chuck fixed in place and pushed the update.

Bridge from Prior Activity

As documented in this week's earlier summaries, the main 21-patch CB_NOTIFY series (v5) was posted on May 22 and applied to nfsd-testing on May 23. This follow-on thread is a direct continuation of that work — addressing residual issues that Sashiko identified during review of the larger series but which were not folded into v5 itself.

The Four Patches in Detail

Patch 1/4: Check for FILEID_INVALID in setup_notify_fhandle

Jeff Layton identified a potential out-of-bounds read in the callback encoding path:

"exportfs_encode_inode_fh() can return FILEID_INVALID (255) when the buffer is too small. Since this is a positive value, the existing check (fileid_type < 0) won't catch it. If this happens, maxsize will have been updated to the required (larger) size, and fhp->fh_size could overflow the fh_raw buffer, leading to an out-of-bounds read when the filehandle is later encoded onto the wire."

This is a security-relevant bug fix — the existing error check only caught negative return values, but FILEID_INVALID (255) is positive. The fix adds an explicit check for this sentinel value alongside the existing negative-return check.

Patch 2/4: Use empty string for directory name in NOTIFY4_CHANGE_DIR_ATTRS

This patch corrects a protocol compliance issue:

"RFC 8881 Section 10.4.3 specifies that for NOTIFY4_CHANGE_DIR_ATTRS events, the ne_file component name must be a zero-length string. The code was incorrectly using the directory's own dentry name, which could leak the local namespace to the client and cause cache confusion."

This is both a protocol compliance fix and a potential information-leak correction — sending the server's local dentry name in the callback would violate the RFC and could confuse client-side caching. The fix passes an empty string and zero length instead, and removes the now-unnecessary name_snapshot.

Patch 3/4: Check delegation status in nfsd4_cb_notify_done

This patch addresses a potential infinite loop / resource leak:

"If a delegation has been closed or revoked (sc_status is set), the NFS4ERR_DELAY retry loop in nfsd4_cb_notify_done will spin indefinitely. This holds the sc_count reference and prevents the delegation from being freed."

The fix adds a check for sc_status at the top of the function, matching the pattern already used in nfsd4_cb_recall_done, to terminate the callback promptly when the delegation is no longer valid. Without this, a revoked delegation could pin its memory indefinitely while the callback kept retrying.

Patch 4/4: Fix ino_t format specifier in nfsd_handle_dir_event tracepoint

The final patch is a straightforward type correction:

"inode->i_ino is now a u64. Use the same size for the tracepoint."

The tracepoint was using __field(ino_t, u64) — which Layton realized after posting was incorrect syntax. He followed up the next day:

"My apologies. This should read: __field(u64, i_ino). I had the fix in my tree and forgot to commit it before sending."

Chuck Lever resolved this without requiring a resend:

"I fixed this in place and pushed out the update to nfsd-testing."

Significance for NFS Client Development

These fixes are important groundwork for the client-side implementation of CB_NOTIFY directory delegations. Specifically:

  • Patch 1 prevents a potential out-of-bounds read on the server when encoding filehandles into callbacks — a crash vector that could affect any client receiving CB_NOTIFY responses.
  • Patch 2 ensures protocol compliance, so that clients implementing RFC 8881's callback handling will receive well-formed ne_file fields (zero-length for directory attribute changes) rather than server-local names that would break client cache semantics.
  • Patch 3 prevents a server-side resource leak that could manifest as a denial-of-service if a client's delegation is revoked while a CB_NOTIFY callback is in flight — directly relevant to robust client-server interaction under failure conditions.

The overall picture: the server-side CB_NOTIFY infrastructure is now solid in nfsd-testing, with all known review issues addressed. The path forward remains clear — the Linux NFS client needs its corresponding CB_NOTIFY handler implementation before the feature can be merged into mainline, as Layton noted in the v5 cover letter: "I don't think we'll want to merge these until we have a complete client-side implementation to test against."
