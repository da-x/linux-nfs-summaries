sunrpc: fix slab corruption in server-side TLS handshake close race (v2)

Summary

sunrpc: Fix Slab Corruption in Server-Side TLS Handshake Close Race

Type: Bug fix (two-patch series, v2) Affected subsystem: net/sunrpc/svcsock.c — NFS server-side TCP transport with TLS Fixes: b3cbf98e2fdf ("SUNRPC: Support TLS handshake in the server-side TCP socket code")

Overview

On Friday 2026-05-22, Chuck Lever posted a two-patch v2 series addressing a slab-corruption bug in the NFS server's asynchronous TLS handshake path. The patches were authored by Chris Mason (Meta) and Chuck Lever himself, with review from Jeff Layton. Both patches received Reviewed-by tags within minutes of posting.

This is a server-side fix; it complements an earlier client-side TLS pinning series ([PATCH 0/2] Fix a few memory bugs in RPC-with-TLS, posted May 4) that addressed analogous lifetime issues on the rpc_clnt side.

The Bug: Two Close Races Freeing svc_sock Under the Callback

The core problem is a reference-counting gap in svc_tcp_handshake(). When the server initiates a TLS handshake via tls_server_hello_x509(), the handshake core takes only a sock_hold() on the socket — nothing pins the embedding struct svc_sock that the completion callback svc_tcp_handshake_done() reaches through container_of().

Chuck's commit message for patch 1/2 lays out two distinct race windows:

"Two close races leave the in-flight callback writing through a freed svc_sock."

Race 1 — svc_sock_free() discards the cancel return value: When a connection is closed, svc_sock_free() calls tls_handshake_cancel(). If that returns false (meaning handshake_complete() already set HANDSHAKE_F_REQ_COMPLETED but the callback hasn't finished yet), the code proceeds straight to kfree(svsk) while the callback is still in flight.

Race 2 — cancel-loser fall-through inside svc_tcp_handshake(): When wait_for_completion_interruptible_timeout() returns ≤ 0 (timeout or signal) and tls_handshake_cancel() also returns false, the function returns without draining. The caller svc_handle_xprt() then calls svc_xprt_received(), which clears XPT_BUSY and can drop the last reference — freeing the transport while the callback is still running.

The Corruption Primitive

The commit message is emphatic about severity:

"The corruption surfaces as set_bit/clear_bit RMW into the freed xpt_flags slab slot and as complete_all() walking and writing the freed wait_queue_head_t list embedded in sk_handshake_done -- a slab-corruption primitive, not a benign read."

This is a write-after-free on kernel slab memory, not merely a use-after-read. The path is reachable on any TLS-enabled NFS server whenever a connection close overlaps the tlshd downcall delivery window. Notably, because the wait is interruptible, signal delivery alone is sufficient to trigger it — no need for the full SVC_HANDSHAKE_TO timeout to expire.

Patch 1: Pin svc_xprt Across the Callback

The first patch (by Chris Mason, with Chuck rewriting the commit message) adds a svc_xprt_get(xprt) immediately before tls_server_hello_x509() so the in-flight callback owns its own reference. The reference is released on exactly three edges:

  1. Submission failure from tls_server_hello_x509()
  2. A successful tls_handshake_cancel()
  3. At the tail of svc_tcp_handshake_done() after complete_all()

The change is minimal: 6 lines added to net/sunrpc/svcsock.c.

Patch 2: Wait for In-Flight Callback When Cancel Loses the Race

The second patch (by Chuck Lever) addresses a subtler race in the cancel-loser path. After tls_handshake_cancel() returns false, the current code immediately reads xpt_flags to decide whether the session succeeded. Two sub-races result:

"If the callback has executed set_bit(XPT_TLS_SESSION) but not yet clear_bit(XPT_HANDSHAKE), svc_tcp_handshake() sees a session, enqueues the transport, and returns." — leading to a second xpo_handshake invocation that calls init_completion() on svsk->sk_handshake_done while the original callback concurrently calls complete_all() on it, corrupting the embedded wait queue.

"If the callback has set HANDSHAKE_F_REQ_COMPLETED but not yet entered svc_tcp_handshake_done(), svc_tcp_handshake() reads XPT_TLS_SESSION as clear and tears the connection down even though the handshake is about to succeed."

The fix: wait for the callback's completion before inspecting xpt_flags. The commit message notes this is safe because "the completion is guaranteed to fire because handshake_complete() invokes svc_tcp_handshake_done() unconditionally once it has set HANDSHAKE_F_REQ_COMPLETED." This adds 4 lines.

Evolution: v1 → v2

The v2 was posted just ~12 hours after the v1 single-patch version (posted 01:48 UTC). Jeff Layton reviewed the v1 by 10:02 UTC, granting a Reviewed-by. The v2 split the work into two logically distinct patches and added patch 2 to handle the cancel-loser fall-through race that the v1's single pinning fix did not fully cover. The Closes: tag in patch 2 references the v1 patchset URL on sashiko.dev, formally superseding it.

Review and Status

Jeff Layton responded to patch 2/2 within six minutes of posting:

"Reviewed-by: Jeff Layton jlayton@kernel.org"

Both patches carry Reviewed-by tags. No objections or further discussion followed in this window. The series appears ready for merge into the NFS tree.

Broader Context

This fix is part of a broader campaign to harden RPC-with-TLS lifetime management. A related client-side series (posted May 4, still under discussion as of June) addresses analogous pinning issues in the rpc_clnt TLS connect path. Together, these patches close a class of write-after-free bugs that were latent since TLS support was first added to the server-side TCP socket code.
