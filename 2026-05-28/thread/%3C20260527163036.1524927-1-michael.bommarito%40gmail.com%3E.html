pNFS client GETDEVICEINFO panic fix: v2 posted with Schumaker's provenance comment carried over

Summary

pNFS client: kernel-panic fix for malformed GETDEVICEINFO — v2 addresses Anna Schumaker's review nits

Type: Bug fix (NFSv4 / pNFS client) — a remotely-triggerable kernel NULL-pointer dereference in the pNFS flexfile and legacy file layout drivers, plus a latent unbounded-decode loop. Stable backport requested for all three Fixes: targets. This is the v2 of Michael Bommarito's two-patch series; v1 was posted earlier this week (see last week's summary for the full bug narrative and Schumaker's review) and was held up only by two cosmetic asks from the NFS client maintainer.

Where we are this week

Bommarito posted the v2 series on Wednesday, May 27 — roughly a day after Schumaker's review of Patch 2/2 — and the only functional delta from v1 is exactly what she asked for. The cover letter is explicit:

"Changes in v2:

  • Carry the stripe_index provenance comment from filelayout.h to the new NFS4_PNFS_MAX_MULTI_CNT location in include/linux/nfs4.h, as Anna requested."

That single line answers Schumaker's Tuesday review on Patch 2/2:

"In the original location, this had a comment saying where the 256 came from. Can you carry that over to here too, please?"

The other nit she raised — "I don't think we need the comment saying that the value has moved" — is also implicitly addressed by the v2 diffstat, which removes the now-redundant relocation note from filelayout.h while adding the provenance comment at the new home in include/linux/nfs4.h. The net effect is a five-file change (5 files changed, 21 insertions(+), 7 deletions(-)) with no functional delta versus v1: same NULL-deref close in nfs4_decode_mp_ds_addr(), same cap on the inner mp_count loop in both layout drivers, same bail-on-NULL behavior.

The bug (unchanged from v1)

The underlying vulnerability is a clean, deterministic client crash reachable purely over the wire — no special configuration, no privileged mount options, just a malicious or compromised pNFS metadata server:

"A malicious or compromised NFSv4.1+ pNFS metadata server can panic any pNFS-flexfile client by returning a GETDEVICEINFO body with a multipath-DS count of >= 3 and exactly one valid (netid, uaddr) pair."

The mechanics are an XDR-decode slip in nfs4_decode_mp_ds_addr(). The decoder pulls the r_netid/r_addr opaques out of a netaddr4 via xdr_stream_decode_string_dup() and then immediately calls strrchr(buf, '.') to find the port separator. But when the on-wire opaque has length zero, that helper sets *str = NULL and returns 0 — and the caller only checks < 0:

"The unbounded inner loop in nfs4_ff_alloc_deviceid_node() (and the parallel site in nfs4_fl_alloc_deviceid_node() for the legacy file layout) keeps iterating after the first netaddr is decoded, consuming the trailing version_count / version / minor words of the body as opaque netid + uaddr pairs. Both come out as zero-length strings; xdr_stream_decode_string_dup() sets *str = NULL and returns 0; the caller in nfs4_decode_mp_ds_addr() only checks '< 0' and immediately calls strrchr(NULL, '.')."

Bommarito nails down how cheap and reliable the trigger is:

"The shortest crashing GETDEVICEINFO body is 56 bytes, the panic is 5/5 deterministic at multipath_count = 10, and it fires before any user-level read can complete on the first pNFS file the client touches."

He backs this with a concrete KASAN oops (Linux 7.0-rc7 + KASAN under QEMU/KVM), showing the crash landing in strrchr via nfs4_decode_mp_ds_addr → nfs4_ff_alloc_deviceid_node → nfs4_find_get_deviceid, with a full read-path call trace down to do_sendfile:

"Oops: general protection fault [#1] SMP KASAN NOPTI KASAN: null-ptr-deref in range [0x0000000000000000-0x0000000000000007] RIP: 0010:strrchr+0x24/0x80 Call Trace: nfs4_decode_mp_ds_addr+0xca/0x570 nfs4_ff_alloc_deviceid_node+0x357/0x1370 nfs4_find_get_deviceid+0x6b6/0xa90 ... Kernel panic - not syncing: Fatal exception"

The crash threshold is sharp: with multipath_count <= 2 "the loop ends before consuming the malformed trailing bytes," so it does not fire. The patched kernel rejects the same crafted body and a baseline multipath_count = 1 mount + read completes normally.

The two-patch fix (unchanged in substance)

The series splits into a direct NULL-deref close and a defense-in-depth bound, with Bommarito stressing that either one alone stops the panic but only together do they retire the whole class:

"Either patch alone closes the panic; both together close the latent unbounded-decode class."

Patch 1/2 is a two-line change in fs/nfs/pnfs_nfs.c: flip the two return-value checks on xdr_stream_decode_string_dup() from < 0 to <= 0, so a zero-length decode fails with -EBADMSG (treated as a malformed GETDEVICEINFO body) instead of dereferencing NULL. It carries Fixes: 6b7f3cf96364 ("nfs41: pull decode_ds_addr from file layout to generic pnfs") — the commit that unified the netaddr decode and introduced the NULL-deref site. The patch description is precise about the failure mode:

"When the on-wire opaque has length zero, xdr_stream_decode_opaque_inline() returns 0 and xdr_stream_decode_string_dup() falls through to its '*str = NULL; return ret' tail, leaving buf NULL with a return value of 0. The '< 0' check does not catch this, and the next line is strrchr(NULL, '.'), a kernel NULL pointer dereference reachable from any pNFS-flexfile client mounted against a malicious or compromised metadata server."

Patch 2/2 is the structural fix. It promotes NFS4_PNFS_MAX_MULTI_CNT (== 256) from a filelayout-private header up into include/linux/nfs4.h so both drivers share it, caps the inner mp_count loop in both the flexfile and legacy file layout drivers against that constant, and bails on the first NULL return from nfs4_decode_mp_ds_addr(). The unbounded-loop exposure is old:

"The unbound on mp_count predates the flexfile driver: the same loop exists in the legacy file layout since 35124a0994fc ('Cleanup XDR parsing for LAYOUTGET, GETDEVICEINFO', 2011) and was carried into flexfile by d67ae825a59d ('pnfs/flexfiles: Add the FlexFile Layout Driver', 2014)."

Hence two Fixes: tags (the 2011 LAYOUTGET/GETDEVICEINFO XDR cleanup and the 2014 FlexFile driver introduction). Without the bound, Bommarito warns, a hostile server can "drive the inner loop indefinitely (up to 2^32 - 1 iterations) against a fixed-size 56-byte body, with each iteration triggering an allocation / kmemdup_nul cycle inside the decoder."

The v2 patch description adds one clarifying sentence about the relationship between the two patches:

"This is defense-in-depth on top of the companion patch which closes the NULL-deref in nfs4_decode_mp_ds_addr(); either patch alone closes the kernel-panic shape, both together close the latent unbounded-decode class."

Status / outlook

  • v2 posted, no new review yet. As of the end of this week's window (May 29), no maintainer has replied to the v2 series. Given that Schumaker's only asks on v1 were cosmetic and both are addressed verbatim in v2, a quick Reviewed-by / "Applied" is the expected next step.
  • Stable backport pending for all three Fixes: commits (6b7f3cf96364, 35124a0994fc, d67ae825a59d) — appropriate given this is a trivially-triggered remote client panic.
  • Client-side relevance: this is squarely an NFS client bug — any pNFS-flexfile (or legacy file-layout) client mounted against a malicious or compromised metadata server can be crashed before its first read completes. The fix hardens the XDR decode path in fs/nfs/pnfs_nfs.c and both layout drivers, closing the NULL-deref and the unbounded-decode class in one go.
  • Notable pattern: this is Bommarito's fourth distinct patch thread on linux-nfs this week (alongside the lockd UAF series that landed in v3, the NFSD ssc_expire_umount UAF fix that landed in v2, and a third same-day submission). The pNFS GETDEVICEINFO series has been the cleanest of his client-side submissions — only one round of review with cosmetic nits, no automated-reviewer detour (unlike the lockd series, which needed three rounds through Sashiko/Codex before Chuck Lever could apply it). The Assisted-by: Claude:claude-opus-4-7 trailer is present on both patches, continuing the week's pattern of prominently AI-assisted submissions clearing review.
