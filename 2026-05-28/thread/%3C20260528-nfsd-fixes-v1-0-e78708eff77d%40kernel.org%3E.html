nfsd: a pile of fixes for random bugs — 10-patch grab bag lands with early scrutiny on ACL cap and layout BUG_ON

Summary

Jeff Layton drops a ten-patch "grab bag" of nfsd bug fixes

On May 28, Jeff Layton posted a 10-patch series titled "nfsd: a pile of fixes for random bugs", describing the collection as covering "remotely-triggerable panics, UAFs, DoS's, etc., but they aren't reliable. There are also a few protocol fixes in here too, etc. It's a grab bag." The set spans 12 files with 142 insertions and 43 deletions, and credits three authors: Chris Mason (6 patches), Chuck Lever (2), and Layton himself (2).

Notably, one of the patches — PATCH 06/10 "NFSD: Enable return of an updated stable_how to NFS clients" — was originally submitted by Chuck Lever "a couple of years ago" but is being resubmitted now because, as Layton put it, "Claude believes that this fixes a real bug and isn't optional." The series passed basic pynfs smoke testing.

Key technical arguments per patch

PATCH 01: BUG_ON on racing delegation revoke (Layton)

The first patch fixes a client-reachable race in nfsd4_alloc_layout_stateid(). When the parent stateid is a delegation, the code reads fp->fi_deleg_file without holding fi_lock. A concurrent laundromat revoke can clear that pointer, causing nfsd_file_get() to return NULL and triggering a BUG_ON. The fix takes fi_lock around the read and replaces the BUG_ON with a graceful error return.

NeilBrown quickly pushed back on the locking approach in his reply:

"Replacing the BUG_ON with a graceful error is certainly sensible and probably all that is needed to fix the problem."

"I cannot see how the spinlock achieves anything. If ->fi_deleg_file could become NULL at this point, it can become NULL just before we take the spinlock."

NeilBrown also flagged the rcu_dereference_protected(fp->fi_deleg_file, 1) call as "a warning sign" and questioned what the '1' argument means, suggesting a comment is called for. He speculated that "fi_delegees > 0 guarantees stability" and asked why a spinlock would be needed in addition. His verdict: "Confused."

PATCH 02: Drain callbacks and clear cl_cb_session (Mason)

This patch addresses a use-after-free in the session teardown path. After DESTROY_SESSION, the per-session teardown can free a session while rpciod still holds an inflight callback rpc_task that dereferences clp->cl_cb_session. The fix mirrors the two-stage drain already used by nfsd4_shutdown_callback(): calling nfsd41_cb_inflight_wait_complete() after flush_workqueue() so rpciod-side decrements are observed before the caller releases the final session reference. A second window in nfsd4_process_cb_update() is closed by unconditionally clearing clp->cl_cb_session on error return.

PATCH 03: Serialize nfsd4_end_grace() (Mason)

This patch replaces a plain bool read/write pair guarding the grace-end drain path with try_cmpxchg(). Without it, two concurrent callers (laundromat kworker and RECLAIM_COMPLETE compound handler) can both observe grace_ended == false, both proceed into nfsd4_record_grace_done(), and double-free every nfs4_client_reclaim entry while corrupting the reclaim hash table.

PATCH 04: Dedup nfs4_client_to_reclaim inserts (Mason)

This patch fixes a bookkeeping bug where nfs4_client_to_reclaim() unconditionally allocates and prepends a new entry without checking for an existing one. After a reboot with a populated recovery directory, the counter inflates to 2N, making the fast end-of-grace path dead — "the grace period always runs out the full 90-second laundromat timer." The fix looks up the name first and folds in the principal hash if needed, using smp_store_release()/smp_load_acquire() to prevent torn reads of the (data, len) pair.

PATCH 05: Gate nfs3 setacl by argp->mask (Mason)

This patch fixes a protocol correctness bug: nfsd3_proc_setacl() called set_posix_acl() unconditionally for both ACL types, but the decoder only populates those pointers when the corresponding mask bit is set. A NULL pointer meaning "client did not send this arm" was indistinguishable from "client asked to remove this ACL." As Mason noted in the commit message: "A SETACL with mask=NFS_ACL silently drops the directory's default ACL; mask=0 drops both."

PATCH 06: Return updated stable_how (Lever)

This patch is a refactoring that allows nfsd_vfs_write() to return a possibly modified stable_how value, paving the way for promoting an UNSTABLE WRITE to FILE_SYNC and saving the client a COMMIT round trip. Layton highlighted this as a patch originally submitted by Chuck "a couple of years ago" that is now being resubmitted because it "fixes a real bug and isn't optional."

PATCH 07: Check truncate permission under inode lock (Lever)

This patch closes a TOCTOU window for append-only files. The original code checked whether a size update needed NFSD_MAY_TRUNC using an unlocked file-size sample, but the actual ATTR_SIZE update was applied later under inode_lock(). A concurrent append could extend the file in between, causing notify_change() to apply a real truncation without the append-only check. The fix rechecks the size after acquiring the lock.

PATCH 08: Fix partial-write detection in nfsd_direct_write (Mason)

This patch fixes a subtle off-by-half bug. After vfs_iocb_iter_write(), the iterator's count field is already decremented by the bytes written, so the partial-write check host_err < segments[i].iter.count was actually comparing against the residual, not the original length. The condition only fired when less than half the segment was written; short writes between 50% and 99% slipped through, causing the next segment to be written at the wrong offset.

PATCH 09: Cap decoded POSIX ACL count (Mason) — sparks discussion

This patch rejects a wire-supplied ACL entry count greater than NFS_ACL_MAX_ENTRIES before allocation, bounding the O(n²) bubble sort cost. The encoder side already had this check; the decoder introduced in 2014 did not.

This patch drew the most discussion. Rick Macklem raised a historical objection:

"My recollection is that Chuck didn't like this limit. He argued that it was specific to the NFSv3 ACL protocol and that the limit on the size of a NFSv4 RPC message was sufficient. I, personally, think that 1024 is a reasonable limit for # of ACEs."

Rick also offered a mitigating observation: "The good news w.r.t. the sort is that they are normally already sorted, so the bubble sort is normally just a single pass, I think?"

Chuck Lever confirmed and refined his earlier position:

"The NFSACL protocol limits the number of ACEs in an ACL to NFS_ACL_MAX_ENTRIES (1024). It's a limit that is defined in the protocol itself. The NFSv4 protocol sets no similar limit."

"Using NFS_ACL_MAX_ENTRIES to cap the number of ACEs in NFSv4 ACLs is a convenience, but it adds technical debt (slight though it may be)."

Chuck proposed a compromise: define an NFSD implementation-specific constant (e.g., NFSD4_MAX_...) rather than reusing the NFSv3 protocol constant, and check whether the Linux POSIX ACL implementation already defines a similar limit. He closed with characteristic humor: "Then prepare for an onslaught of complaints that 1024 is just too small :-)"

PATCH 10: Validate symlink target length in NFSv4 CREATE (Layton)

The final patch rejects cr_datalen == 0 or cr_datalen >= PATH_MAX early with nfserr_nametoolong, bounding a per-COMPOUND kmalloc that could otherwise reach the RPC-max size (~1 MiB). The VFS would eventually reject oversized targets with ENAMETOOLONG, but "the allocation has already occurred."

Discussion evolution and status

The thread is in its earliest stage — all 14 messages landed on May 28 within roughly two hours of each other. Three substantive replies have appeared so far:

  • NeilBrown questioned the locking strategy in PATCH 01, suggesting the spinlock may be unnecessary and that RCU (with a clarifying comment) is the more appropriate synchronization primitive.
  • Rick Macklem and Chuck Lever debated the correctness of using NFS_ACL_MAX_ENTRIES as an NFSv4 implementation cap in PATCH 09, with Chuck proposing a rename to make the implementation-vs-protocol distinction explicit.

No merge decision or final ack has been posted yet within this week's window. The series is primarily a bug fix collection (with one protocol-correctness fix in PATCH 05 and one performance-enabling refactor in PATCH 06), targeting remotely-triggerable panics, use-after-frees, data corruption, and DoS vectors in the NFS server.

Significance for NFS client development

While this series targets the server side, several fixes have direct implications for client behavior:

  • The stable_how return (PATCH 06) will allow clients to skip COMMIT round trips once the follow-up patch lands.
  • The partial-write detection fix (PATCH 08) prevents silent data corruption at wrong offsets on direct I/O writes.
  • The delegation revoke race (PATCH 01) is explicitly "client-reachable" — two NFS clients can trigger it by having one hold a delegation while another opens the same file.
  • The append-only TOCTOU fix (PATCH 07) ensures server-side enforcement of append-only semantics that clients may rely on for data integrity guarantees.
