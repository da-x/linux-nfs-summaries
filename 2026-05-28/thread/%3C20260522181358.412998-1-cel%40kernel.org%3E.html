svcrdma: wake sq waiters when the transport closes

Summary

svcrdma: wake sq waiters when the transport closes

Type: Bug fix (NFS server / RDMA transport) Status this week: Patch posted; no replies yet in-thread. A closely related follow-on series from the same author landed later in the window and was acked by Jeff Layton, giving context for where this fix sits in a broader svcrdma cleanup effort.

The patch

Chuck Lever posted a single-patch fix on Friday 2026-05-22 addressing an uninterruptible hang in the NFS server's RDMA transport. The bug: worker threads parked in svc_rdma_sq_wait() on either sc_sq_ticket_wait or sc_send_wait can sleep forever in TASK_UNINTERRUPTIBLE across transport teardown, pinning svc_xprt references and blocking svc_rdma_free().

Lever's cover letter lays out the root cause with unusual precision:

"The close path sets XPT_CLOSE before invoking xpo_detach and both wait_event predicates include an XPT_CLOSE term, but the predicates are re-evaluated only on wakeup. sc_sq_ticket_wait has no completion-driven wake path; it is advanced solely by the chained ticket handoff inside svc_rdma_sq_wait() itself."

The deadlock is aggravated by a second close entry point:

"A remote disconnect arrives at svc_rdma_cma_handler(), which calls svc_xprt_deferred_close(): that sets XPT_CLOSE and enqueues the transport but does not access either RDMA waitqueue, so a worker already parked in svc_rdma_sq_wait() never re-evaluates its predicate. With every worker parked on this transport, no thread is available to run the local teardown either, and the wake site there is unreachable."

The fix

The patch introduces svc_rdma_xprt_deferred_close(), a thin svcrdma wrapper that calls svc_xprt_deferred_close() and then explicitly wakes both sc_sq_ticket_wait and sc_send_wait. All seven svcrdma producers that previously called svc_xprt_deferred_close() directly are converted to use the new helper:

  • svc_rdma_cma_handler()
  • qp_event_handler()
  • svc_rdma_post_send_err()
  • svc_rdma_wc_send()
  • the sendto drop path
  • the rw completion error paths
  • the recvfrom flush and read-list error paths

Both waitqueues are also woken from svc_rdma_detach(), covering the synchronous svc_xprt_close() path (backchannel ENOTCONN, device removal via svc_rdma_xprt_done) that bypasses the deferred-close helper.

The patch touches five files (+37/−10) and carries a Fixes: tag pointing at commit ccc89b9d1ed2 ("svcrdma: Add fair queuing for Send Queue access"), identifying the introduction of the ticket-based fair-queuing mechanism as the origin of the bug.

Authorship and AI-assistance disclosure

Notably, the patch is authored by Chris Mason (Meta) with Chuck Lever taking over to complete it:

"[ cel: add svc_rdma_xprt_deferred_close() to complete the fix ]"

The commit also includes an explicit Assisted-by: kres (claude-opus-4-7) trailer — a disclosure that Claude AI assisted in drafting the initial version. This is part of a growing pattern of AI-assisted kernel contributions being transparently labeled on linux-nfs.

Context: broader svcrdma cleanup wave

This patch arrived five days before Lever posted a five-patch follow-on series titled "Fix resource lifecycle bugs in svcrdma transport setup and teardown," which also includes a Chris Mason contribution ("svcrdma: Fix unmatched rn_unregister on failed accept"). The two efforts together represent a systematic audit of svcrdma's error paths, teardown ordering, and reference-counting.

Jeff Layton acked the follow-on series on 2026-05-27 with a characteristically candid note:

"I don't feel confident in my own abilities to review svcrdma patches, so. Acked-by: Jeff Layton jlayton@kernel.org"

No reply has yet appeared in this thread as of the end of the window (2026-05-29). Given the Fixes: tag and the severity of the hang (uninterruptible sleep + memory leak), this patch is a strong candidate for stable backport.
