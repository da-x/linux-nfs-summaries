XFS pNFS layout-mapping fixes earn second round of Reviewed-bys

Summary

XFS pNFS layout-mapping fixes: Carlos Maiolino adds Reviewed-bys to Dai Ngo's two-patch series

This week in brief

The week ending 2026-05-28 brought a quiet but consequential coda to Dai Ngo's two-patch XFS pNFS bug-fix series. After Christoph Hellwig had already signed off on both patches the day they were posted last week, Red Hat's Carlos Maiolino — a long-time NFS maintainer and reviewer — added his own Reviewed-by tags to each patch on Tuesday 2026-05-26, closing out the review window with no outstanding objections.

This is a bug-fix thread, not a feature or protocol change: both patches correct server-side behavior in fs/xfs/xfs_pnfs.c that was producing malformed LAYOUTGET replies to NFS clients.

Bridge from last week

Last week's summary covered the original posting of the series and Hellwig's same-day approvals:

  • Dai Ngo posted [PATCH 0/2] xfs: correct pNFS layout mappings](https://lore.kernel.org/linux-nfs/20260520003503.2399326-1-dai.ngo@oracle.com/) on 2026-05-20, fixing two regressions in the XFS pNFS export path:
    • Patch 1 — a use of an uninitialized imap record in the error path of xfs_fs_map_blocks() (regression from 527851124d10f, "xfs: implement pNFS export operations").
    • Patch 2 — overlapping extents returned to clients during LAYOUTGET because XFS_BMAPI_ENTIRE was passed to xfs_bmapi_read() (regression from cc6c40e09d7b1, "NFSD/blocklayout: Support multiple extents per LAYOUTGET").
  • Christoph Hellwig approved both patches the same day, writing:

"Looks good: Reviewed-by: Christoph Hellwig hch@lst.de"

The prior week's summary also noted that a separate nfsd race condition (layouts inserted after ->proc_layoutget) was identified but deliberately left out of scope for this series.

This week's activity

Two short review messages from Carlos Maiolino arrived on 2026-05-26, six days after the original posting:

  1. Re: [PATCH 1/2] xfs: fix use of uninitialized imap in xfs_fs_map_blocks error path (09:59 UTC) — Maiolino quoted Dai Ngo's explanation that xfs_fs_map_blocks() "acquires the data map lock and then calls xfs_bmapi_read(). If xfs_bmapi_read() fails, the function currently [falls through to xfs_bmbt_to_iomap()]", and added a bare:

    "Reviewed-by: Carlos Maiolino cmaiolino@redhat.com"

  2. Re: [PATCH 2/2] xfs: fix overlapping extents returned for pNFS LAYOUTGET (10:05 UTC) — Maiolino quoted the patch's core rationale that xfs_fs_map_blocks() "currently passes XFS_BMAPI_ENTIRE to xfs_bmapi_read(), which causes the bmap code to expand the mapping to cover the entire [extent]", and offered a slightly more personal sign-off:

    "I'm not an expert on NFS, but the explanation and the patch looks good and make sense, so:"

    "Reviewed-by: Carlos Maiolino cmaiolino@redhat.com"

The diffstat for Patch 2 (fs/xfs/xfs_pnfs.c | 4 ++--) confirms the change is a minimal flag removal rather than a structural rewrite.

Why this matters for NFS clients

Although both fixes live in XFS server code, their blast radius is squarely on the client side:

  • Patch 1 prevents xfs_fs_map_blocks() from returning garbage mapping data when xfs_bmapi_read() fails. Without it, an NFSv4.2 block-layout export could hand a client an uninitialized iomap, which would surface as bogus device/offset pairs in the LAYOUTGET reply.
  • Patch 2 removes the source of overlapping extents in LAYOUTGET replies. As Dai Ngo explained last week, a single client LAYOUTGET can trigger multiple server-side xfs_fs_map_blocks() calls for different offsets within the same extent; with XFS_BMAPI_ENTIRE, those calls could each return the full extent, producing overlaps that "can lead to incorrect device selection, inconsistent handling of datastate, and ultimately data corruption or protocol violations on the client side."

For pNFS block-layout clients (the Linux NFSv4.2 client in particular), these two fixes eliminate server-side sources of malformed layouts that would otherwise be very hard to debug from the client side — a class of bug that tends to look like client misbehavior when it is actually bad data from the server.

Evolution and final state

The discussion has effectively converged:

  • No new technical arguments were raised this week; Maiolino's messages are pure approvals, not pushback.
  • The "I'm not an expert on NFS" caveat in his Patch 2 reply is notable only as flavor — it signals that the patch was reviewed for plausibility and consistency with the surrounding XFS code rather than deep pNFS protocol semantics, but it does not weaken the Reviewed-by.
  • With two independent Reviewed-by tags (Hellwig + Maiolino) on each patch and no objections, the series is in clean shape for merge into the next XFS/NFS development window.
  • The open nfsd race condition flagged last week remains unaddressed by this series and should be tracked as a separate follow-up.
