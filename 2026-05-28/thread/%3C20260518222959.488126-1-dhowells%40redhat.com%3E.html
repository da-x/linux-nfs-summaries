Hellwig reviews netfs bvecq helpers: rename kmap helper, kill iov_iter_get_pages*()

Summary

netfs bvecq series: block-maintainer review of the page-kmap and iov_iter helpers

This week brought the first substantive review from the block side to David Howells' 21-patch netfs "bvecq" series, which migrates netfslib (the shared I/O layer under the NFS, AFS and CIFS clients) from its private folio_queue/rolling_buffer buffering onto segmented bio_vec[] chains. Two of the series' foundational helper patches — both touching generic block/VFS infrastructure that the NFS client depends on — drew pointed feedback from block maintainer Christoph Hellwig on 2026-05-25.

Context (prior week, briefly)

Last week Howells posted the v2 series and received only light stylistic nitpicks: David Laight questioned the use of bitfields in struct bvecq, and Stefan Metzmacher acked the CIFS/SMBDirect pieces while asking for commit-message wording fixes. The NFS-relevant stakes are that this is a protocol-agnostic infrastructure refactor (not a bug fix) whose payoff for the client is unified buffered/DIO buffering, single-kernel_sendmsg() RPC transmission, and faster cachefiles lookups. This week's messages target two of the building blocks that make that possible.

Patch 05/21 — kmap_local_bvec(): naming, style, and a design question

Howells' patch 05/21 adds an inline helper to kmap a single page out of a multipage bio_vec by byte offset:

+static inline void *kmap_local_bvec(struct bio_vec *bvec, size_t offset) + offset += bvec->bv_offset; + return kmap_local_page(bvec->bv_page + offset / PAGE_SIZE) + offset % PAGE_SIZE;

Hellwig's reply raises three concerns, the first being naming:

"The name is rather confusing for something that does not map the entire bvec, and is an anagram of the existing bvec_kmap_local. So please rename it to bvec_kmap_partial or something."

He then flags the implementation as both too long and suboptimal:

"Overly long line. Also this can use shits [sic] and byte masking to be a tad more efficient and matching the rest of the bvec code."

Most importantly, he challenges the underlying design choice, asking why a bespoke page-offset kmap is needed at all when the established block idiom already exists:

"Users of this would be interesting and why you're not simply using a bvec_iter at page granularity, which is what other block kmap code does."

That last question is the crux: if the netfs I/O path can iterate with bvec_iter at page granularity (the convention used elsewhere in block), the new helper may be unnecessary API surface. Howells has not yet responded as of this week's window.

Patch 06/21 — iov_iter_get_pages*(): a call to delete, not wrap

The second patch, 06/21, is a net 145-line deletion that makes iov_iter_get_pages*() simply wrap iov_iter_extract_pages() for the kernel iterator types (ITER_BVEC, ITER_FOLIOQ, ITER_XARRAY), bumping refcounts on non-slab pages and leaving ITER_KVEC to return -EFAULT. Rather than accept this consolidation, Hellwig pushes for outright removal:

"Just kill off iov_iter_get_pages*, please. Or at least stop using it where these types matter."

This is a notable escalation from the prior week's minor nits — Hellwig is asking Howells to drop an existing VFS/block API entirely (or at least retire its use for the iterator types the netfs path relies on) instead of layering a thin wrapper over iov_iter_extract_pages(). Resolving this will determine how much of the series lands in the VFS tree versus requiring a follow-on cleanup.

Classification and status

  • Type: Protocol-agnostic infrastructure refactor / API consolidation (not a bug fix, not an on-the-wire protocol change). The NFS client is affected indirectly through netfslib's buffering and send path.
  • Evolution this week: Review shifted from cosmetic nitpicks (Laight, Metzmacher) to substantive block-maintainer pushback on two core helpers — a rename + design question for the kmap helper, and a delete-the-API demand for iov_iter_get_pages*().
  • Open items / next steps: Howells needs to (1) rename kmap_local_bvec() (e.g. to bvec_kmap_partial), shorten/rework its body with shift-and-mask arithmetic, and justify or replace it with a page-granularity bvec_iter; and (2) decide whether to remove iov_iter_get_pages*() rather than wrap it. No conclusion has been reached yet; the ball is in Howells' court.
