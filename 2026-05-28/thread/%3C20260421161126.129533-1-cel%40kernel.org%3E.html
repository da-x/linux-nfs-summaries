sunrpc OOB read fix gets Oracle field-tested validation

Summary

sunrpc: Out-of-Bounds Read Fix Gets Field Validation from Oracle

Type: Bug Fix (Memory Safety) — closing the loop on a syzkaller-reported issue Component: NFS/SunRPC Cache Subsystem (net/sunrpc/cache.c) Status this week: Final Tested-by tags received; patch effectively ready for merge

This Week's Activity

The thread, which had been quiet since late April, saw its final piece of validation land on May 26. Calum Mackay (Oracle) replied to Chuck Lever's original patch, confirming that the fix resolves a real-world production problem:

"This looks good to me, Chuck. Fixes the frequent sosreport crashes in cache_check_rcu we've been seeing, even with Erkun's revert applied."

Mackay attached Tested-by tags for both himself and Harshit Mogalapalli (also of Oracle), signaling that the fix has been validated not just by syzbot/KASAN but by field testing on systems where the crashes were actually occurring.

Background (from prior weeks)

As summarized last month, this bug was introduced by commit 7b546bd89975 ("sunrpc/cache: improve RCU safety in cache_list walking."), which removed a bounds guard at the tail of __cache_seq_start(). When the sequence iterator exhausted all hash buckets, it would store *pos = ((long long)hash << 32) + 1 with hash == cd->hash_size, producing an index one past the end of the allocated hash table. A subsequent pread(2) at that offset would skip traverse() and feed the invalid index back into __cache_seq_start(), causing an eight-byte slab-out-of-bounds read.

Chuck Lever's fix adds a symmetric bounds check at the top of __cache_seq_start():

"cache_seq_next() already bounds-checks its own loop; the start routine needs to be symmetric."

The patch was quickly endorsed in April by Benjamin Coddington ("We were hunting for this one") and NeilBrown, who noted:

"I prefer the approach you took as it is more robust."

Significance for NFS Client Development

While the bug lives in shared SunRPC infrastructure used by both client and server, the cache_check_rcu crash path that Oracle experienced is particularly relevant to NFS client deployments where export/peer caches are actively walked. The fact that the crashes persisted "even with Erkun's revert applied" (a prior workaround for a related RCU-safety issue) underscores that this was a distinct, independent defect in the sequence-file iteration logic — one that only the explicit bounds check resolves.

Conclusion

With the Tested-by tags now in hand from both the original reporter's organization and a second Oracle engineer, this small three-line patch has cleared all review hurdles. It is a clean, targeted memory-safety fix that closes out a syzkaller report and addresses a production crash affecting NFS deployments at scale.
