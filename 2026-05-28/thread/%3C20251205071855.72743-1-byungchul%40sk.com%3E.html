DEPT as AI Review Prompt: Proposal to Automate Deadlock Detection via LLM Triage

Summary

DEPT as AI Review Prompt: Proposal to Automate Deadlock Detection via LLM Triage

Classification

This thread concerns a new feature / tooling proposal for the kernel's deadlock-detection infrastructure — specifically, repurposing DEPT (DEPendency Tracker) as an AI code-review prompt. It is not an NFS-specific change or bug fix, but has indirect relevance to NFS client development given DEPT's ability to detect wait/event deadlocks invisible to Lockdep in complex paths like NFS RPC completions and page-lock waits.

Prior Context (Bridged Briefly)

DEPT was introduced by Byungchul Park as a 42-patch v18 series in December 2025, designed to track wait/event dependencies beyond what Lockdep covers. Over the following months, the series underwent detailed review (type-safety refinements for module event-site marking, Rust helper conventions) and received strong endorsement from fuzzer developer Yunseong Kim, who cited real bugs involving PG_locked and writeback dependencies that DEPT uniquely detected. In March 2026, Park raised the question of where DEPT should be maintained in the kernel tree. No resolution on placement was reached as of the last prior summary (week ending 2026-03-19).

This Week's Activity (May 22–28)

All four messages landed on May 23, forming a tight, rapid exchange between Harry Yoo and Yunseong Kim. The discussion pivots the DEPT conversation from patch review toward a novel operational model: using AI to perform deadlock detection and false-positive triage directly from source code.

Harry Yoo's Proposal: DEPT as an AI Review Prompt

Harry Yoo (signing as "Harry / Hyeonggon") opened the thread with a concrete proposal:

"Can we start DEPT as an AI review prompt, by documenting DEPT's dependency tracking model and false positive elimination rules as a carefully crafted prompt?" Harry Yoo

He acknowledged the core practical limitation of DEPT today:

"While DEPT can identify deadlock issues beyond lockdep's capabilities, it is hard to enable in automated testing; without fine-grained annotations it can produce a high rate of false positives, and verifying them requires significant human effort." Harry Yoo

Yoo pointed to an existing precedent — the open-source AI Review Prompt project's locking.md file, which teaches an LLM how to review locks and detect misuse — as a template for what a DEPT-specific prompt could look like. His vision was that the AI would handle both deadlock detection and false-positive elimination, reducing the human effort required to validate DEPT reports.

Yunseong Kim's Enthusiastic Endorsement and Practical Experience

Yunseong Kim responded within 90 minutes, calling it "an excellent idea" and drawing on his hands-on experience running DEPT in fuzzing pipelines:

"I've previously experimented with running DEPT alongside syzkaller fuzzing, and many hung tasks missed by lockdep are caught by DEPT, but the resulting high volume of reports makes it easy for issues to get lost in the massive log output. Sorting through that output manually is a huge bottleneck, so leveraging a well-crafted AI prompt to triage the warnings and filter out the false positives would be incredibly valuable." Yunseong Kim

Kim volunteered to help translate DEPT's tracking model into concrete AI-review rules:

"I'd be happy to help translate DEPT's tracking model into specific rules for reducing false positives and establishing solid filtering patterns." Yunseong Kim

Harry Yoo Clarifies Scope: Detection, Not Just Triage

In his follow-up, Yoo sharpened the proposal's scope, making clear that a prompt limited to post-hoc false-positive filtering would not be practical:

"I mean both 1) detection of deadlock issues AND 2) false positive elimination with AI." Harry Yoo

He argued that a triage-only approach would create an unwieldy pipeline:

"If the review prompt is only used to eliminate DEPT's false positives, I think that would be quite hard to get broad use. Someone would have to build out-of-tree DEPT, collect the reports, and then feed those back into the AI. I don't think building that kind of pipeline would actually work well in practice." Harry Yoo

The key insight: the AI prompt should detect deadlock patterns directly from source code (static analysis via LLM), not merely filter runtime DEPT reports. This eliminates the need for a custom build-and-collect pipeline.

Yunseong Kim's Agreement and Feedback Loop

Kim agreed fully and added an important nuance about bidirectional value:

"I completely agree. Implanting DEPT's model into an AI review prompt is a great idea. As you suggested, the patterns we develop for the AI could provide valuable feedback to enhance DEPT's itself." Yunseong Kim

He also underscored the practical pain that motivates this work:

"I also have a huge dept report of DEPT reports, and manually reviewing all of them is makes me sigh. The constant kernel rebuilds required for lockup testing every time are also quite expensive." Yunseong Kim

Key Technical Arguments

  1. DEPT's blind spot is operational, not algorithmic. The dependency-tracking model is sound and catches real bugs Lockdep misses (including PG_locked/writeback deadlocks relevant to NFS), but the false-positive rate without fine-grained annotations makes it impractical for continuous integration.

  2. AI as a static-analysis front-end, not a post-hoc filter. Yoo's critical distinction is that the prompt should perform deadlock detection directly on source code (like locking.md does for lock misuse), rather than requiring someone to first build DEPT, run it, collect reports, and then feed them to an AI. The latter pipeline is too heavyweight for broad adoption.

  3. Bidirectional improvement. Kim's point that the patterns developed for the AI prompt could feed back into improving DEPT itself suggests a virtuous cycle: formalizing DEPT's heuristics into natural-language rules forces clarity that benefits both the AI and the runtime tool.

  4. Precedent exists. The open-source AI Review Prompt project (specifically locking.md by Mason Clow) demonstrates that kernel locking semantics can be effectively encoded as LLM instructions, providing a concrete template for a DEPT-specific prompt.

Evolution of the Discussion

The thread evolved in three tight steps within a single day:

  • Proposal (Yoo): Can we document DEPT's model as an AI prompt?
  • Endorsement + practical validation (Kim): Yes, and here's why it matters from a fuzzer's perspective.
  • Scope clarification (Yoo → Kim): The prompt must do detection, not just triage; otherwise the pipeline is impractical. Kim agreed and added the feedback-loop insight.

The discussion concluded with mutual agreement on the approach but no concrete next steps (e.g., who writes the prompt, where it lives, how it integrates into existing review workflows).

Significance for NFS Client Development

While this thread does not produce any NFS code changes or bug fixes, its implications for NFS client development are notable:

  • NFS deadlock detection: The NFS client's RPC completion paths, page-lock waits (PG_locked), writeback dependencies, and delegation recall handling involve complex wait/event patterns that are precisely the class of deadlocks DEPT targets. An AI prompt encoding these patterns could flag potential NFS deadlocks at patch-review time without requiring a full kernel build and fuzzing run.
  • Reduced barrier to deadlock testing: Kim's complaint about "constant kernel rebuilds required for lockup testing" is especially relevant for NFS, where reproducing subtle RPC/page-lock interactions often requires specific server configurations. Static AI-based detection could catch issues earlier in the development cycle.
  • No direct bug fixes this week: The activity was purely a tooling/methodology discussion.

Conclusion

This week marked a significant pivot in the DEPT conversation from patch-by-patch review toward an ambitious operational proposal: encoding DEPT's dependency-tracking model as an AI code-review prompt that performs both deadlock detection and false-positive elimination directly on source code. Harry Yoo proposed the idea, Yunseong Kim validated it with concrete fuzzer experience and volunteered to help formalize the rules, and the two reached consensus on scope (detection + triage, not triage alone). The discussion ended in agreement but without a concrete action plan — no prompt has been written, no repository designated, and no timeline established. The thread remains open for further development.
