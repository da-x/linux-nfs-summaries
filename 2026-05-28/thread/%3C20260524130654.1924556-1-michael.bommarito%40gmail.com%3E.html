NFSD: ssc_expire_umount() UAF fix v2 lands in nfsd-testing after comment rewording

Summary

NFSD: restart ssc_expire_umount walk after dropping nfsd_ssc_lock — v2 applied

Type: Bug fix (NFS server / NFSv4.2 inter-server copy) — slab use-after-free in nfsd4_ssc_expire_umount(), with a stable backport requested. This is the v2 and final iteration of Michael Bommarito's patch that opened yesterday's thread; v1 already earned a Reviewed-by from Jeff Layton, and the only outstanding item was the in-code comment wording that both maintainers had flagged.

The bug (unchanged from v1)

The underlying race is the same one Bommarito laid out on May 23: nfsd4_ssc_expire_umount() walks nn->nfsd_ssc_mount_list with list_for_each_entry_safe(ni, tmp, ...), and for each expired entry it sets nsui_busy = true, drops nfsd_ssc_lock to run mntput() on the source vfsmount, then reacquires the lock to list_del + kfree the entry and continue via the macro's saved tmp pointer. As Bommarito's v2 cover letter restates:

"The nsui_busy flag protects the current ni from concurrent nfsd4_ssc_setup_dul() finders during the lock-drop window, but it does not pin tmp. Another nfsd RPC thread that fails its source-server mount and reaches nfsd4_ssc_cancel_dul() will, during that same window, take nfsd_ssc_lock, list_del + kfree its own ssc_umount item, and release the lock. If that item is the saved tmp of the expire walk, the next iteration dereferences a freed nfsd4_ssc_umount_item."

The fix strategy — restart the walk from the head after each mntput() unlock window so no saved next pointer survives the lock-drop — is carried over verbatim:

"Restart the walk from the head after the mntput() unlock window so no saved next pointer survives the lock-drop. The list is bounded by the number of active inter-server source mounts (typically small) and the expire delayed-work runs periodically rather than per-IO, so the restart is cheap."

The patch again carries Cc: stable@vger.kernel.org, Fixes: f4e44b393389 ("NFSD: delay unmount source's export after inter-server copy completed."), and the same Assisted-by: Claude:claude-opus-4-7 trailer as v1.

What changed since v1

The only substantive change in v2 is exactly what Chuck Lever requested at the close of the v1 thread — rewording the in-code comment so it describes the current code rather than the removed list_for_each_entry_safe() iterator. The cover letter is explicit about the scope:

"Changes since v1:

  • Rewrote the in-code comment above goto-restart to describe the current code (concurrent cancel_dul can free any list item while the lock is dropped) rather than referencing the removed list_for_each_entry_safe() iterator. (Chuck Lever.)"

The diffstat moves from v1's 26 insertions / 19 deletions to 25 insertions / 19 deletions in fs/nfsd/nfs4state.c — a pure comment change, no functional delta. This is the cleanest possible v2: it closes the only outstanding review item without touching the fix itself.

Chuck Lever's response: applied

NFS maintainer Chuck Lever replied within roughly two and a half hours on Sunday, May 24, after quoting the cover letter back:

"Applied to nfsd-testing, thanks!"

"[1/1] NFSD: restart ssc_expire_umount walk after dropping nfsd_ssc_lock — commit: e6dc1fc7e8483f9b36dcfdbcd33665298b018ba9"

That is the second of Bommarito's same-day submissions to land in nfsd-testing this week, following the v3 lockd nlm_traverse_files() UAF fix that Lever applied earlier the same day (commit 925b64e5fb12ad6517ff7c6729bf2fba7485f42c).

Status / outlook

  • v2 accepted. Landed in nfsd-testing as commit e6dc1fc7e8483f9b36dcfdbcd33665298b018ba9; expect it to ride the normal merge window into mainline and a -stable backport given the Cc: stable and Fixes: tags.
  • Client-side relevance: this is server-side code, but it directly affects NFSv4.2 clients that issue OP_COPY with cna_src.nl4_type = NL4_SERVER against a Linux nfsd configured for inter-server copy offload (CONFIG_NFSD_V4_2_INTER_SSC=y, inter_copy_offload_enable=Y). As Bommarito scoped it in v1, "Default Linux nfsd ships with inter_copy_offload_enable=N, so the bug is reachable only on servers where the administrator has explicitly opted into inter-SSC offload." Until this fix lands in -stable, such opt-in servers remain exposed to a KASAN-confirmed slab UAF in laundromat_main() that an authenticated client can drive by pointing the destination at a source-server netaddr that fails vfs_kern_mount().
  • Notable pattern: this v2 is the cleanest two-round resolution of Bommarito's three same-day submissions — v1 earned Layton's Reviewed-by within hours, and v2 was applied to nfsd-testing within ~2.5 h of posting, with no automated-reviewer detour (in contrast to the lockd series, which needed three rounds through Sashiko/Codex before Lever could apply it). The simpler "restart after lock-drop" pattern — already familiar to kernel maintainers per Layton's v1 note that "the 'restart the loop after dropping the lock' pattern is pretty common across the kernel" — proved far less likely to trip automated reviewers than the more intricate dual-cursor pinning in the lockd fix.
