Steve Dickson lands a small nfs-utils fix silencing a -Wstringop-overread in nfs_sockaddr2universal()

Summary

A quiet, one-line-class cleanup in the nfs-utils userspace stack

The week's only activity on this thread was a single patch from NFS maintainer Steve Dickson, posted late on Thursday and committed within days — a textbook example of the small, hygiene-level work that keeps the nfs-utils build clean as compiler warnings tighten.

The problem: a GCC overread warning in the portmapper/socket code

In his initial post, Dickson flagged a -Wstringop-overread diagnostic that surfaces when building nfs-utils with recent GCC:

in function 'nfs_sockaddr2universal', inlined from 'nsm_xmit_getaddr.constprop' at ../../support/nsm/rpc.c:251:17: ../../support/nfs/getport.c:459:24: warning: 'strndup' specified bound 108 exceeds source size 26 [-Wstringop-overread] 459 | return strndup(sun->sun_path, sizeof(sun->sun_path));

The complaint is that the code passes sizeof(sun->sun_path) (108 bytes on Linux) as the bound to strndup(), even though the actual Unix-domain socket path buffer in memory is only 26 bytes wide — a textbook "bound exceeds source size" pattern that GCC's string analysis now catches. It is not necessarily a runtime bug, but it is the kind of noise that drowns out real problems in a CI build.

The fix: a small, AI-assisted patch (with full disclosure)

The patch touches support/nfs/getport.c with three insertions and two deletions — a minimal change to make the bound passed to strndup() match the actual source buffer size rather than the type's maximum. Dickson was notably transparent about how it was produced:

This is a chatgpt solution to remove the warning... untested (yet)

That candor — disclosing that an LLM drafted the fix and that it had not yet been exercised — is itself a small but interesting data point for the kernel/userspace community's evolving relationship with AI-assisted development. The patch still carries a proper Signed-off-by line, so Dickson stands behind it in the usual maintainer sense.

Outcome: committed into nfs-utils 2.9.2-rc4

The thread closed quickly. In his follow-up reply, Dickson confirmed the patch was merged:

Committed... (tag: nfs-utils-2-9-2-rc4)

So this week's net result is a clean build for anyone tracking nfs-utils master past the 2.9.2-rc4 tag, with no protocol change and no behavior change — purely a warning-suppression bug fix in the userspace portmapper/socket helpers used by rpcinfo/NSM tooling around nsm_xmit_getaddr().

Broader context for the week

This thread sits alongside a busy stretch of NFS client work elsewhere on the list this week (directory delegation series, several Michael Bommarito patches, and related fixes), but in its own right it is best read as routine maintenance: keeping the userspace side of the stack warning-free so that genuine regressions can stand out. No discussion or pushback occurred within the reporting window; the only reply — the commit confirmation — landed on 2026-05-30, just outside this week's half-open window, and is noted here only as the immediate resolution of the patch.
