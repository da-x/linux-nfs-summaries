Bridge to prior week (2026-05-21)

For context, the original patch was posted on 2026-05-21 and is a bug fix (not a new feature or protocol change) in the NFS client's fs/nfs/dir.c. It corrects two corner cases in nfs_access_calc_mask():

  1. The special-file branch (FIFOs, block/char devices) was inconsistent with the permissions actually requested by nfs_do_access().
  2. The MAY_WRITE check used a bare bitwise AND rather than the full equality pattern ((access_result & NFS_MAY_WRITE) == NFS_MAY_WRITE) used elsewhere.

The user-visible symptom: on classic local filesystems, access(path, X_OK) on a special file depends on its UNIX permission bits, but on NFS it "would always fail" regardless of permissions — a POSIX-compliance gap introduced as a regression by ecbb903c5674 ("NFS: Be more careful about mapping file permissions"), which the patch cites in its Fixes: tag. The change is small (1 file, +5/−7) and unifies regular-file and special-file handling since both already request identical access bits.

Significance for NFS client development

  • Correctness / POSIX alignment: closes a behavioral divergence between NFS and local filesystems for access(2) on special files — the kind of edge case that surfaces during broader filesystem compatibility testing.
  • Regression tracking: the Fixes: tag to ecbb903c5674 illustrates how earlier permission-mapping hardening can leave subtle side effects on non-regular file types.
  • Process observation: this week's message shifts the story from technical review to patch-management hygiene — a contributor noticing his fix was silently dropped in Patchwork with no explanatory reply, and publicly asking for clarification. As of 2026-05-29, that question remains unanswered on the list.
