[PATCH 0/6] Harden server-side RPCSEC GSS decode and backchannel teardown

Summary

[PATCH 0/6] Harden server-side RPCSEC GSS decode and backchannel teardown

Classification: Bug fixes (hardening audit) — five memory-safety / stale-state defects in the NFS server-side RPCSEC GSS accept path, plus one race/use-after-free in callback-service teardown. Not a new feature or protocol change.

Overview

On Thursday 2026-05-28, Chuck Lever posted a six-patch series titled "[PATCH 0/6] Harden server-side RPCSEC GSS decode and backchannel teardown" introducing the work. The series is the product of an audit, as Lever framed it in the cover letter:

"Address findings from an audit of how the server-side RPCSEC GSS accept path handles partially decoded and stale credential state. The common defect class: gss_svc_data and the rpc_gss_wire_cred it embeds (svcdata->clcred) are allocated with non-zeroing kmalloc and reused across requests, so an early decode failure leaves this request's partial writes mixed with the previous request's residue for a later consumer to trust."

Four of the six patches are authored by Chris Mason (Meta), two by Lever himself. The series touches fs/nfs/callback.c, include/linux/sunrpc/bc_xprt.h, and several files under net/sunrpc/auth_gss/ and net/sunrpc/backchannel_rqst.c, with a net change of 58 insertions and 11 deletions across six files.

Although the defects are server-side, they matter to NFS client development because they govern how the kernel's own NFSv4.1+ callback (backchannel) machinery tears down — the very path the client uses for delegation recall and other server-initiated callbacks. The backchannel fix in particular is a genuine use-after-free that affects clients running an active callback service.

Patch-by-patch technical arguments

Patch 1/6 — Reject krb5 v2 wrap tokens with oversized ec field Lever A narrow two-line fix in gss_krb5_unwrap_v2(). The 16-bit "extra count" (ec) field is authenticated, but a peer holding a valid GSS context can still legitimately encrypt a token whose ec exceeds the plaintext length — structurally malformed per RFC 4121. Lever notes that although xdr_buf_trim() now clamps to avoid unsigned underflow, "the buffer is still left in a semantically invalid state (zero length, inconsistent iov lengths) when ec is oversized." The fix rejects such tokens before trimming, returning a well-defined GSS_S_DEFECTIVE_TOKEN. A subtle point: the comparison must be against the remaining wrapped segment (buf->len - offset), not the whole buffer, because "comparing against buf->len alone leaves an offset-wide window in which an oversized ec passes the test and xdr_buf_trim() cuts into the bytes ahead of the blob."

Patch 2/6 — fix gssx_dec_option_array error path bugs Mason The most intricate patch, fixing "four coupled defects" that make the error paths unsafe: a NULL deref in the caller, a refcount leak on the decoded group_info, and a latent use-after-free. The key chain of reasoning:

  • oa->count = 1 is set before allocating oa->data; on allocation failure the caller then does res.options.data[0].value — a NULL deref.
  • free_creds: releases the partially decoded svc_cred with a bare kfree(creds), dropping the refcounted, kvmalloc-backed cr_group_info wrapper and leaking it.
  • The natural leak fix (calling free_svc_cred()) would itself expose a use-after-free because the existing out_free_groups: path called groups_free() without clearing the pointer, so a later put_group_info() "would touch freed memory."

Mason fixes all four together: move the count assignment below the allocation, reset oa->count to 0 at free_oa:, wire free_svc_cred() into the free path, and switch out_free_groups: to the refcount-aware put_group_info() while clearing the pointer. Notably, this patch carries an "Assisted-by: kres (claude-opus-4-7)" tag — a sign of AI-assisted kernel development appearing in upstream-style submission metadata.

Patch 3/6 — reject duplicate CREDS_VALUE options Mason A reply carrying two CREDS_VALUE entries overwrites cr_group_info on the second iteration, orphaning (leaking) the first allocation. The fix tracks whether a CREDS_VALUE was already decoded and returns -EINVAL on any subsequent match. Lever's cover letter stresses a hard ordering dependency here: "Only once that refcount-aware free path exists does rejecting a duplicate CREDS_VALUE option actually release the single installed group_info instead of leaking it. Reviewed out of order, the duplicate-rejection patch looks incomplete."

Patch 4/6 — Guard svcauth_gss_release() dispatch on rq_auth_stat Mason svcauth_gss_release() reads gc_proc and switches on gc_svc before consulting rq_auth_stat. On the SVC_DENIED path after a failed accept, those fields "may hold stale values from a prior request or uninitialized slab residue." The fix mirrors the existing rq_auth_stat gate one frame up so the dispatch is skipped entirely when authentication has not succeeded. This patch carries the oldest Fixes: tag in the series — 1da177e4c3f4 ("Linux-2.6.12-rc2") — i.e., a defect present since the 2.6 era, though currently masked by a downstream early-return.

Patch 5/6 — Zero rpc_gss_wire_cred at svcauth_gss_decode_credbody() entry Mason The sharpest stale-state case: the trailing body_len tightness check leaves gc_ctx.data pointing into the current request's XDR pages while gc_ctx.len retains its prior value, so "once the request pages are released the pooled clcred carries a dangling pointer paired with a stale length." Zeroing the cred at function entry ensures every early-return path leaves a deterministic all-zero cred, which "neuters length-driven consumers such as gss_svc_searchbyctx() that would otherwise walk the dangling data pointer."

Patch 6/6 — close backchannel before destroying callback service Mason The standalone race/UAF fix, which Lever's cover letter describes as "a genuine race and use-after-free in callback-service teardown." The mechanism: a backchannel receive can complete a request while the NFS callback service is being torn down. If teardown has already cleared xprt->bc_serv, the committed request (and its xprt_get()) is leaked; if the producer wins the race, it can enqueue onto sv_cb_list after nfs_callback_down() stopped the threads, "leaving the request linked to a svc_serv that is about to be freed." The fix adds xprt_svc_shutdown_bc() to clear xprt->bc_serv under bc_pa_lock before stopping the service threads, releases losing requests through the normal backchannel free path, and drains any remaining sv_cb_list requests before svc_destroy(). This is the patch most directly relevant to NFS client robustness.

Discussion and outcome

The thread was short-lived but decisive. Within roughly two and a half hours of the posting, Jeff Layton replied with a review to the cover letter and granted:

"Reviewed-by: Jeff Layton jlayton@kernel.org"

No objections, no requests for changes, and no further back-and-forth appeared in the thread this week. The series is therefore in a clean, reviewed state as of the close of the window (2026-05-28), with a single Reviewed-by from an established NFS maintainer — a strong signal it is on track for merge.

Takeaways

  • This is a hardening / bug-fix series, not a feature or protocol change: five memory-safety fixes (NULL deref, refcount leaks ×2, use-after-free ×2, stale-state/dangling pointer) plus one teardown race/UAF.
  • The recurring theme — non-zeroing kmalloc buffers reused across requests — is a classic source of subtle NFS server-side credential bugs, and the series systematically closes it by zeroing state at entry and making every error path refcount-aware.
  • Patches 2/6 and 3/6 have an explicit ordering dependency that reviewers must respect.
  • The backchannel teardown fix (6/6) is the most consequential for NFS client behavior, since it protects the live callback service clients rely on for delegation recall.
  • Two patches carry Assisted-by tags referencing an AI model, a noteworthy data point in how kernel hardening work is being produced today.
