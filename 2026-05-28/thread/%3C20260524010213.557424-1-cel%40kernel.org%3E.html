sunrpc: close length validation gaps in krb5p unwrap

Summary

sunrpc: closing length-validation gaps in the krb5p unwrap path

Type: Bug fix / security hardening (not a new feature or protocol change) Status this week: Patch series posted, reviewed, and approved.

The story

On Saturday 2026-05-24, Chuck Lever posted a four-patch series on the linux-nfs list titled sunrpc: close length validation gaps in krb5p unwrap. The patches are authored by Chris Mason (Meta) and signed off by Lever, and they target a cluster of integer-handling defects in the kernel's RPCSEC_GSS / krb5p privacy ("krb5p") unwrap path — code that runs on both NFS clients and servers when processing Kerberos-encrypted RPC traffic.

The cover letter lays out the threat model with characteristic precision:

"An authenticated krb5p peer -- NFS client or server -- can send a token shorter than the 16-byte RFC 4121 header and reach gss_krb5_unwrap_v2() with a length that drives pre-decrypt out-of-bounds reads, a divide-by-zero in _rotate_left(), and a post-decrypt unsigned underflow in the movelen computation that feeds a multi-gigabyte memmove."

In other words, an authenticated peer — not an untrusted outsider — could still trigger memory-safety bugs by crafting a malformed token. Lever emphasizes the layered design of the fix:

"The fixes are layered so that neither the caller boundary nor the unwrap core depends on the other for safety. The caller-side floor checks (patches 1, 2) are sufficient to close the attack, but gss_krb5_unwrap_v2() must also be self-defending because it is reachable through gss_unwrap() from any future caller that might not enforce the same floor."

The four patches

Patch 1 — server-side minimum-length check. SUNRPC: svcauth_gss: enforce krb5 token minimum length adds a floor to svcauth_gss_unwrap_priv(), which previously only validated an upper bound on the wire-supplied opaque length. The patch explains that "a len in [0, 16] passes this check and is handed to gss_unwrap()", letting sub-header tokens reach gss_krb5_unwrap_v2() where header reads at ptr+4 and ptr+6 run past the token, and _rotate_left()'s shift %= buf->len can divide by zero. The fix is a two-line guard:

"if (len <= GSS_KRB5_TOK_HDR_LEN) goto unwrap_failed;"

It carries a Fixes: tag pointing at the original 2006-era server-side krb5p privacy implementation.

Patch 2 — client-side hardening. SUNRPC: harden gss_unwrap_resp_priv length checks is the most important patch for NFS client development, since it protects the client from a malicious or buggy krb5p server's reply. The original check offset + opaque_len > rcv_buf->len has two flaws: both operands are u32, so "a reply with opaque_len near 0xffffffff makes offset + opaque_len wrap to a small value that is below rcv_buf->len, so the bound check passes and gss_unwrap() is called with end < begin." It also lacks any lower bound. The patch replaces the single combined test with three u32-safe guards (offset bound, length bound via safe subtraction, and an RFC 4121 minimum-length floor). Lever's cover letter flags this client-only overflow:

"The client side (patch 2) has an additional u32 integer-overflow bypass that the server side does not: the original offset + opaque_len > rcv_buf->len wraps when opaque_len is near UINT_MAX, accepting a huge token length that re-enters the same underflow chain."

Patch 3 — generic xdr_buf_trim clamp. SUNRPC: xdr_buf_trim: clamp buf->len to avoid underflow fixes a defect that is independent of krb5 itself. In xdr_buf_trim(), the final accounting buf->len -= (len - trim) can underflow when buf->len is smaller than the sum of the iovec lengths, wrapping to near UINT_MAX and then "propagat[ing] as the authoritative stream bound into every downstream XDR decoder." The fix clamps the decrement with min_t(). Lever notes this is a generic invariant violation that gss_krb5_unwrap_v2() merely happens to be "the only current trigger for, but that any caller could hit if buf->len and the component iov_lens get out of sync."

Patch 4 — self-defense in the unwrap core. SUNRPC: harden gss_krb5_unwrap_v2 against short tokens adds four defense-in-depth guards inside gss_krb5_unwrap_v2() so it is safe regardless of what its callers validate: reject sub-16-byte tokens before touching ptr+4/ptr+6; bail from rotate_left() when buf->len <= base; return early from _rotate_left() when buf->len is zero (preventing the modulo fault); and replace a dead BUG_ON with a live check that returns GSS_S_DEFECTIVE_TOKEN. The patch calls out a subtle bug in the existing sanity check:

"The BUG_ON re-adds the value just subtracted, so it reduces to min(A, B) > A and is permanently false; it cannot catch the unsigned underflow of movelen, which then drives a ~UINT_MAX-byte memmove()."

Across the four files the series is small — 17 insertions, 4 deletions — but each change closes a distinct failure mode in the same attack chain.

The discussion and conclusion

The thread was short and decisive. Jeff Layton replied about ten hours later with a review:

"Looks good. The unsigned offset math in this parsing code is just so nasty. I wonder if we'd be better off using signed math here for some of this. Oh well..."

Reviewed-by: Jeff Layton jlayton@kernel.org

Layton's aside about the fragility of "unsigned offset math" captures the recurring theme of this kind of XDR/RPC parsing code — and suggests a possible future cleanup direction, though no such follow-up was posted this week.

Bottom line

This is a textbook layered-defense bug-fix series: caller-side floor checks on both the server and client entry points, a generic xdr_buf_trim() invariant fix, and self-contained guards in the krb5 unwrap core. It hardens NFS clients against crafted RPCSEC_GSS replies from a peer server (patch 2's u32 overflow bypass being the most client-relevant), while also covering the symmetric server-side exposure. With Layton's Reviewed-by, the series is in good shape for merge; no objections or open questions remained as of the end of the window.
