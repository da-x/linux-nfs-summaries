Summary

nfsd: One-Line Fix for Pre-Allocated Openowner Leak on Unconfirmed Retry Race

A compact but technically interesting bug-fix thread landed this week, addressing a memory leak in the NFSv4 server's open-state management code. The discussion was brief—just two messages—and concluded with immediate acceptance.

The Bug

Jeff Layton submitted a patch on Friday, May 22, identifying a subtle leak in find_or_alloc_open_stateowner() in fs/nfsd/nfs4state.c. The race condition unfolds as follows:

"When find_or_alloc_open_stateowner() encounters an unconfirmed owner, it calls release_openowner() and sets oo = NULL. Control then falls through past the if (oo) guard — which would have freed any pre-allocated new — and unconditionally executes new = alloc_stateowner(...). If new was already allocated on a prior iteration, the pointer is silently overwritten and the previous allocation (slab object + owner name buffer) is leaked."

The trigger requires two concurrent NFSv4.0 OPEN operations using the same owner string, with a third thread inserting an unconfirmed owner into the hash table between retry iterations. Layton noted the window was narrow but "repeatable under adversarial conditions."

The Fix

The fix is a single line: adding goto retry after oo = NULL, so that on the next iteration the already-allocated new pointer is reused rather than being clobbered by a fresh allocation. This preserves the existing allocation and avoids the leak.

Layton traced the regression to commit 23df17788c62 ("nfsd: perform all find_openstateowner_str calls in the one place.") and credited Chris Mason (Meta) with reporting the issue. The patch also carries an Assisted-by: kres:claude-opus-4-6 tag, indicating AI-assisted development.

Immediate Acceptance

NFS maintainer Chuck Lever picked up the patch within twenty minutes, quoting Layton's description and confirming:

"Applied to nfsd-testing, thanks!"

The commit landed as f36ecdd78c62 in the nfsd-testing tree. No further discussion or review comments were needed—the fix was straightforward enough that it went from submission to merge in under half an hour.
