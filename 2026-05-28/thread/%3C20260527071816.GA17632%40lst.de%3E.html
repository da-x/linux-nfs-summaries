Revisiting alloc_pages_bulk() semantics: early-fail, folio API, and sunrpc's zeroed-array quirk

Summary

Revisiting alloc_pages_bulk() semantics

Classification: Core MM allocator API redesign (not a bug fix), with direct consequences for the NFS/sunrpc server-side page-cache path. The thread is an open design discussion — no patches were posted this week, but it landed squarely in the middle of active NFS client/server memory-management work.

The opening salvo

Christoph Hellwig kicked off the thread on Wednesday with a four-point critique of alloc_pages_bulk(), which he had been trying to adopt "in a few places lately" and found wanting:

  1. Early-fail semantics — the bulk allocator does partial allocations, forcing callers into awkward fallback loops or single-page allocation. Hellwig demanded the kernel's usual "try as hard as you can" behavior, with GFP_NORETRY-style flags to relax it.
  2. Pre-zeroed page array — only one user in the tree (svc_fill_pages in sunrpc) relies on the zeroed-array behavior; for everyone else it is "extra burden and ... very error prone (speaking from experience)."
  3. Page instead of folio — "We're allocating folios, so we should have a folio API."
  4. Order > 0 support — the bulk allocator is limited to order 0, which Hellwig called a serious limitation for pagecache and bounce-buffering use cases.

The MM pushback: is "try hard" even useful?

Zi Yan (NVIDIA) pushed back on point 1, questioning whether a "try as hard" bulk allocation would actually buy anything:

"My gut feeling is that if one 'usual try' fails, the following 'usual try' might not work. So making alloc_pages_bulks() do heavy allocation might not buy you much."

He also raised the latency concern for order > 0 bulk allocations under memory pressure, noting that THP allocations have been observed to take ">30s allocation latency when under memory pressure," and asked whether "waiting minutes for bulk > order 0 allocation making sense in your use cases."

Hellwig fired back that the current behavior is "really odd, as other page/folio allocators make that an opt-in through GFP flags," and that callers currently suffer from "lots of divering cargo culting." He clarified his order > 0 needs:

"The allocations I have in mind would only require try hard allocations for typical file system blocks sizes (64k at most), while eveything larger is fair game for falling back."

Zi Yan responded with a code-level explanation: the GFP flags are respected inside __alloc_pages_noprof(); the fast rmqueue_pcplist() loop is just a quick free-page grab. He suggested that "a wrapper of __alloc_pages_bulk() that doing allocation in a loop until all requested pages are filled might be good enough," and offered a trick — asking compaction/reclaim to aim for more free pages than the requested order so subsequent allocations succeed without repeated heavy passes.

Hellwig conceded the point partially but noted that "a whole bunch of callers have the wrong assumption" about GFP flag behavior, and — in a side remark with broader MM implications — cited the LSF/MM large-folio and fragmentation sessions as grounds to raise PAGE_ALLOC_COSTLY_ORDER from 3 to 4 on 4k-page platforms, "as this seems to be a proble for 64k folio allocations."

Vlastimil Babka: partial success and the folio question

Vlastimil Babka (SUSE) weighed in with two important design questions:

  • On early-fail semantics, he argued against discarding partial progress: "Seems wasteful to suceed N-1 and then throw all away, if the caller can use a fallback only for the last one." He asked whether a flag should distinguish all-or-nothing from partial-success callers.
  • On the folio API, he noted that folios have drifted beyond "base or compound page" — they are now also rmappable via page_rmappable_folio() — and proposed keeping both alloc_pages_bulk() and folio_alloc_bulk().

Hellwig answered that "a lot of callers (but not all) need all or nothing semantics," but freeing already-allocated pages is cheap — the caller just needs a release_pages call. On sunrpc, he flagged that Chuck Lever had "objected to previous attempts to change it" and proposed a two-tier API: a lower-level helper that works as-is, plus a wrapper that zeroes the array.

The NFS angle: why sunrpc insists on zeroed pages

This is where the thread becomes genuinely about NFS development. Matthew Wilcox offered a sharp observation:

"I think the problem is that sunrpc uses the pages as a queue instead of a stack. If it consumed pages from the end instead of the beginning, it could just refill the entire tail of the array."

Chuck Lever (Oracle), pulled into the discussion, explained the real constraint:

"What the svc/nfsd thread is trying to avoid is sleeping uninterruptibly waiting for memory resources. That stalls server shutdown, among other things. Guaranteeing forward progress is the bottom line."

He argued that if sunrpc is truly the only user of the zeroed-array behavior, it would be sensible to "hoist the 'zero fill' capability into sunrpc.ko," and cited his own in-flight optimization (commit d7f3efd9ff47, targeting 7.1) that limits the rq_respages fill in svc_alloc_arg() to the [rq_respages, rq_next_page) range rather than scanning the full ~259-slot array for 1MB messages — a measurable win on the server-side RPC path.

Hellwig pressed further, asking whether svc_rqst_release_pages() NULLs the entire range (in which case no NULL check is needed at all — just point the bulk allocation at that range) and probing Wilcox's queue-vs-stack idea.

Lever closed the week with a detailed architectural explanation. The key insight: struct xdr_buf's pages field points directly into the rq_pages array, and "many places in sunrpc point to rq_pages and use it as an array" — so it cannot be treated as a simple FIFO. He described the two-phase lifecycle:

"Phase A prepares the thread (svc_rqst) for the next RPC ... alloc_bulk_pages refills the NULL entries. Phase B is done while the client is waiting for the server to send an RPC reply, so it has to be low latency."

He ended on a forward-looking note that opens the door to exactly the restructuring Hellwig wants:

"Note that as struct xdr_buf is transitioned from 'struct page **' to a bvec array, we indeed have good low-risk opportunities to restructure this code and how it uses rq_pages."

Where things stand

The thread ended without a consensus or patch set, but the discussion converged on several practical next steps:

  • Early-fail / "try hard" semantics remain contested; Zi Yan's wrapper-loop proposal is the leading lightweight option, with the PAGE_ALLOC_COSTLY_ORDER bump (3→4) as a related MM-side fix for 64k folio allocation.
  • The zeroed-array quirk is now understood as a sunrpc-specific forward-progress guarantee tied to xdr_buf's array-based page consumption, not a general allocator need. The in-tree plan is a two-tier API (raw helper + zeroing wrapper), with the longer-term hope that the xdr_buf → bvec conversion lets sunrpc drop the special case entirely.
  • Folio API and order > 0 support have broad agreement in principle, with Babka's dual-API suggestion (alloc_pages_bulk() / folio_alloc_bulk()) as the likely shape.

For NFS developers, the practical takeaway is that the server-side rq_respages allocation path — already optimized by Lever's 7.1 patch — is about to be touched again as part of a broader MM allocator cleanup, and the xdr_buf bvec migration is the natural vehicle for eliminating sunrpc's last holdout on legacy bulk-allocation semantics.
