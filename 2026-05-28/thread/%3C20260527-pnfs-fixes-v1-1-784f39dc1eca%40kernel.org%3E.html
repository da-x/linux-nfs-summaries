nfsd: XDR padding fix in flexfile GETDEVICEINFO encoder

Summary

nfsd: Fix XDR Padding Calculation in ff_encode_getdeviceinfo

Type: Bug fix (NFS server / NFSv4.1+ flexfiles layout)

The Problem

Jeff Layton opened the thread on May 27 with a patch addressing a subtle but persistent encoding bug in the NFSv4.1 flexfiles server-side XDR code. The function nfsd4_ff_encode_getdeviceinfo() was computing its da_addr_body length field incorrectly:

"nfsd4_ff_encode_getdeviceinfo() computes the da_addr_body reservation as 16 + netid_len + addr_len, but the subsequent xdr_encode_opaque() calls emit 8 + round_up(netid_len, 4) + round_up(addr_len, 4) bytes."

The practical consequence was twofold:

"The mismatch means the declared da_addr_body length exceeds the actual encoded data by 2-8 bytes on every flexfile GETDEVICEINFO reply, leaking stale reply-page content to the client and mis-aligning the subsequent version list decode."

In other words, every single flexfiles GETDEVICEINFO reply was over-declaring its address body by a few bytes. Clients would read garbage (stale page contents) in those trailing bytes, and the misalignment would cascade into the version-list decoding that follows. The fix is straightforward: use xdr_align_size() for each string length to match what xdr_encode_opaque() actually writes.

The patch carries a Fixes: tag pointing at commit efcae97fa425 ("NFSD: da_addr_body field missing in some GETDEVICEINFO replies"), and an "Assisted-by: kres:claude-opus-4-6" line, indicating LLM-assisted code review contributed to the analysis.

Review Discussion

Chuck Lever responded within an hour with two points of interest:

  1. Fixes tag uncertainty: He suggested the correct Fixes: target might instead be commit 9b9960a0ca47, noting that "LLM reviews vary on this." This highlights the ongoing challenge of attributing fixes to the right upstream commit, particularly when LLM-assisted review is in the loop.

  2. A related bug in the same file: Lever spotted an analogous unaligned-length pattern elsewhere:

    "nfsd4_ff_encode_layoutget at fs/nfsd/flexfilelayoutxdr.c:40-41 has the same unaligned pattern for UID/GID strings: 8 + uid.len + 8 + gid.len. Do you intend to address that calculation as well?"

He also floated a longer-term architectural preference:

"My preference here is to convert to xdrgen instead, but that's a much bigger and less back-portable change."

Layton confirmed he would handle the second bug separately:

"Yep, I just saw the Sashiko review for it. I'll fix that one up in a separate patch."

This reference to "Sashiko" (another automated/LLM review tool) underscores how LLM-assisted code review is becoming a routine part of the NFS development workflow — both for finding bugs and for generating patches.

Resolution

The following day (May 28), Chuck Lever applied the patch to his nfsd-testing tree:

"Applied to nfsd-testing, thanks!" commit: d53136757d4192934ad67d4c5c58eb9bc99daf4b

Significance for NFS Client Development

While this is a server-side fix, the impact is directly felt by NFS clients. Flexfiles (NFSv4.1+) is an advanced layout type used in high-performance storage deployments. A mis-encoded GETDEVICEINFO reply would cause any conforming client to:

  • Interpret 2–8 bytes of stale memory as valid data in the address body, and
  • Mis-decode the device version list that follows, potentially selecting wrong or invalid devices for I/O.

The fix ensures byte-exact XDR encoding per the RFC, restoring correct client behavior for all flexfiles GETDEVICEINFO exchanges. The companion fix for the UID/GID padding in ff_encode_layoutget (promised as a follow-up) will close out the last known instances of this class of bug in the flexfiles XDR encoder.
