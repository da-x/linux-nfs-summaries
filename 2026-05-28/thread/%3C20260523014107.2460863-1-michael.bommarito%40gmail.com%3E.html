NFSD: ssc_expire_umount() use-after-free fix gets Reviewed-by, v2 requested on comment wording

Summary

NFSD: restart ssc_expire_umount walk after dropping nfsd_ssc_lock

Type: Bug fix (NFS server / NFSv4.2 inter-server copy) — slab use-after-free in nfsd4_ssc_expire_umount(), with a stable backport requested. This is the second of several same-day submissions from Michael Bommarito this week, sitting alongside his lockd UAF series (v1→v3) and a third patch thread on the same day; it is the first of the set to receive a clean Reviewed-by from Jeff Layton within hours.

The bug and the proposed fix

Bommarito opened the thread on Saturday, May 23 with a single-patch submission targeting fs/nfsd/nfs4state.c (26 insertions, 19 deletions). The patch carries Cc: stable@vger.kernel.org, a Fixes: tag pointing at the original delayed-unmount commit (f4e44b393389, "NFSD: delay unmount source's export after inter-server copy completed."), and an Assisted-by: Claude:claude-opus-4-7 trailer — making it one of several prominently AI-assisted submissions this week.

The race, in Bommarito's words:

"nfsd4_ssc_expire_umount() walks nn->nfsd_ssc_mount_list with list_for_each_entry_safe(ni, tmp, ...). For each expired entry it sets nsui_busy = true, drops nfsd_ssc_lock to run mntput() on the source vfsmount, then reacquires the lock to list_del + kfree the entry and continue iterating via the macro's saved tmp pointer."

"The nsui_busy flag protects the current ni from concurrent nfsd4_ssc_setup_dul() finders during the lock-drop window, but it does not pin tmp. Another nfsd RPC thread that fails its source-server mount and reaches nfsd4_ssc_cancel_dul() will, during that same window, take nfsd_ssc_lock, list_del + kfree its own ssc_umount item, and release the lock. If that item is the saved tmp of the expire walk, the next iteration dereferences a freed nfsd4_ssc_umount_item."

The chosen remedy is to restart the walk from the head after each mntput() unlock window so no saved next pointer survives the lock-drop:

"Restart the walk from the head after the mntput() unlock window so no saved next pointer survives the lock-drop. The list is bounded by the number of active inter-server source mounts (typically small) and the expire delayed-work runs periodically rather than per-IO, so the restart is cheap."

Reachability — opt-in only

Bommarito is careful to scope the bug's blast radius: it requires an authenticated NFSv4.2 client issuing OP_COPY with cna_src.nl4_type = NL4_SERVER against a destination nfsd built with CONFIG_NFSD_V4_2_INTER_SSC=y and started with inter_copy_offload_enable=Y. The client chooses the source-server netaddr and can pick one that fails vfs_kern_mount() (unreachable, RST after EXCHANGE_ID, etc.) to drive nfsd4_ssc_cancel_dul() into the laundromat's lock-drop window:

"Default Linux nfsd ships with inter_copy_offload_enable=N, so the bug is reachable only on servers where the administrator has explicitly opted into inter-SSC offload."

He also notes the patch closes a sibling of an earlier fix — "The same primitive class was previously addressed by the OPEN-error path fix in __nfs42_ssc_open(); this patch closes the corresponding hole in the laundromat-driven delayed-unmount path."

Reproduction evidence

Bommarito reports a concrete KASAN reproduction, which is notable for an inter-SSC code path that is off by default:

"Reproduced under QEMU/KVM with KASAN, three nfsd network namespaces on a single host so the kernel client treats them as distinct servers, and Linux fault injection forcing vfs_kern_mount allocations inside the destination nfsd to fail. This drives nfsd4_ssc_cancel_dul into a tight loop concurrent with the laundromat workqueue."

"BUG: KASAN: slab-use-after-free in laundromat_main+0x1756/0x1be0 — Read of size 8 at addr ffff88800ce9b200 by task kworker/u16:3 / Workqueue: nfsd4 laundromat_main"

The allocation/free stacks point cleanly at nfsd4_interssc_connect() (the inlined nfsd4_ssc_setup_dul/nfsd4_ssc_cancel_dul helpers) called from nfsd4_copy(). The patched kernel "ran the equivalent workload to completion with the inter-SSC code path exercised 21–22 times per run and no KASAN report." He emphasizes that "the fault-injection knobs are standard Linux testing infrastructure … exercising the existing failure path in nfsd; no kernel source was modified."

Review: Reviewed-by from Layton, comment nit from both maintainers

Jeff Layton replied within roughly nine hours and signed off:

"The bug and patch look correct to me though. Reviewed-by: Jeff Layton jlayton@kernel.org"

His only objection was a documentation nit: the new in-code comment references list_for_each_entry_safe(), but the patched code uses plain list_for_each_entry() — so a reader looking at the post-patch source sees no _safe iterator anywhere and has to reconstruct the bug history to make sense of the comment.

Bommarito acknowledged it was a leftover from an earlier patch attempt and proposed a cleaner wording:

"Concurrent nfsd4_ssc_cancel_dul() can free an item while spinlock is dropped for mntput() above, so restart the walk from the head so no stale pointer is followed."

Layton approved the rewording and added a useful framing note:

"Sure, looks good. FWIW, the 'restart the loop after dropping the lock' pattern is pretty common across the kernel, but it is good to lay out the rationale in a comment."

Chuck Lever then weighed in later that afternoon, reinforcing the same point from a reader's-eye perspective:

"Same observation as Jeff's: The comment references list_for_each_entry_safe(), but the patched code uses plain list_for_each_entry(). A reader looking only at the post-patch source sees no _safe iterator anywhere in the function and has to reconstruct the bug history to make sense of the comment."

"The past-tense framing ('was not pinned') reinforces this: it describes a removed code state rather than the current one. Please send a v2 with this comment corrected."

Status / outlook

  • v1 functionally accepted, v2 requested on comment wording only. Layton's Reviewed-by is already in place; both maintainers agree the bug analysis and the restart-from-head fix are correct. The only outstanding item is the comment rewording Bommarito has already proposed — a v2 that drops the stale _safe reference should clear review quickly.
  • Stable backport pending. The UAF is clearly stable-worthy (a classic list-walk use-after-free in the nfsd laundromat path), so the eventual clean version should land in -stable alongside mainline given the Cc: stable and Fixes: tags.
  • Client-side relevance: this is server-side code, but it directly affects NFSv4.2 clients that issue OP_COPY with NL4_SERVER against a Linux nfsd configured for inter-server copy offload — exactly the workload where a misbehaving source-server netaddr can drive the destination into the race window. Until the fix lands, such servers are exposed to a KASAN-confirmed slab UAF in laundromat_main() triggered by an authenticated client; default configurations (inter_copy_offload_enable=N) are unaffected.
  • Notable pattern: this is the first of Bommarito's same-day submissions to land a clean Reviewed-by within hours, in contrast to his lockd series which needed three rounds (Sashiko on v1, Codex/Sashiko on v2) before Chuck Lever applied v3 to nfsd-testing. The contrast highlights how the simpler "restart after lock-drop" pattern — already familiar to kernel maintainers per Layton's note — is far less likely to trip automated reviewers than the more intricate dual-cursor pinning in the lockd fix.
