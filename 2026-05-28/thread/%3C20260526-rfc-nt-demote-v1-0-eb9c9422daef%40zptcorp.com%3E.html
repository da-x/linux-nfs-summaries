RFC: use non-temporal stores for memory demotion to lower tiers

Summary

New feature (RFC): non-temporal stores for memory demotion

A three-patch RFC series landed on the list this week from Yiannis Nikolakopoulos (co-developed with Alirad Malek, both of ZPT Corp), aimed squarely at memory tiering / demotion rather than NFS per se. The series is titled "Demote to lower tier using non-temporal stores" and was posted on 2026-05-26.

The motivation

The cover letter lays out the core argument: demoted pages are expected to be cold and already evicted from the last-level cache, so copying them with a plain memcpy pollutes the local node's cache and burns bandwidth on the target node. Non-temporal (streaming) stores avoid that pollution. The CXL angle is the headline:

"for certain types of CXL devices that support in-line memory compression, the last-level cache eviction patterns can negatively affect the bandwidth of the device. Non-temporal stores can mitigate this."

The author backs this with experimental data from a CXL system with one memory expander, where a microbenchmark allocating 64 GB locally and triggering demotion via memory.reclaim showed:

"a practically complete elimination of read traffic on the device, i.e. write traffic is N GB with and without the patch, while read traffic drops from N to almost 0 with the patch."

The three patches

  • Patch 1/3 — "mm, x86: support copying a folio using non-temporal stores." On x86 it routes through memcpy_flushcache (which emits non-temporal store instructions), building a chain of _nt-suffixed helpers from folio_mc_copy down to copy_mc_to_kernel. Touches 5 files (+80).
  • Patch 2/3 — "mm: new migrate_mode flag for async using non-temporal stores." Adds a MIGRATE_ASYNC_NON_TEMPORAL_STORES mode that is still async but uses NT stores, plus a helper to check both async modes and replaces plain MIGRATE_ASYNC checks. This patch carries the only NFS touchpoint in the series: a one-line change in fs/nfs/write.c (part of replacing raw MIGRATE_ASYNC comparisons with the new helper).
  • Patch 3/3 — "mm: use non-temporal stores for demotion." Wires the new flag into the demotion path in mm/migrate.c, guarded by a Kconfig option.

Open questions raised by the author

The cover letter is unusually candid about its rough edges, listing three explicit "Opens": (1) code duplication in the x86 tree and mm, where copy_mc_to_kernel_nt duplicates machine-check functionality — "Can we completely skip the machine checked for this path?"; (2) whether hiding the feature behind a Kconfig option is the right call; and (3) how to structure it for easy adoption on other architectures such as aarch64, which is "currently out of our scope."

First reply: question the Kconfig flag

Gregory Price replied later the same day to patch 3/3, pushing back on the opt-in design:

"Do we actually need this config flag or should we just default to this (if the arch supports NT stores)?"

That is the only in-window discussion. The thread then went quiet for two months before Nikolakopoulos responded on 2026-07-30, confirming the flag was dropped:

"As discussed in the sync call, I was just being defensive :). In fact the non-temporal instructions should be in all x86_64 afaict. So I've removed this in the next version (landing soon)."

Bottom line

This is a new feature for the memory-management demotion path — not a protocol change and not a bug fix. Its relevance to NFS is indirect but real: patch 2/3 touches fs/nfs/write.c as part of refactoring the async-migration checks, so any regression in that helper would surface on the NFS writeback path. As of this week's window, the series was still an early RFC with one open design question (the Kconfig flag), which the author later resolved by removing the flag entirely since NT stores are effectively universal on x86_64.
