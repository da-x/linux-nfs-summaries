NFSD Callback Channel Fixes: Two Small Patches Prevent Permanent CALLBACK_RUNNING Latch

Overview

On May 26, Jeff Layton posted a two-patch series targeting the NFSv4 server's callback channel machinery. Both patches are bug fixes — small, surgical corrections (5 insertions, 3 deletions total in fs/nfsd/nfs4state.c) that address scenarios where the NFSD4_CALLBACK_RUNNING bit gets stuck set, permanently disabling delegation recall for an affected client.

Layton noted the discovery method with a nod to modern tooling:

"Some fixes for the callback channel machinery. These problems were mostly found via agentic scans."

The patches were applied to nfsd-testing by Chuck Lever within two hours of posting, confirming:

"Applied to nfsd-testing, thanks!"

The Two Bugs in Detail

Patch 1/2: Defer setting NFSD4_CALLBACK_RUNNING in deleg_reaper

This patch fixes a logic ordering issue in deleg_reaper(). The function was setting the NFSD4_CALLBACK_RUNNING bit before checking two early-exit gates: a 5-second rate limit and a cl_cb_state check. When either gate fired, the loop would continue without queuing callback work — but the bit had already been set. Since the only code path that clears the bit is nfsd41_destroy_cb() (which runs from the workqueue after a callback completes), the bit remained latched forever.

"When either gate fires the loop continues without queuing callback work, so the bit's only clear site in nfsd41_destroy_cb() is never reached and RECALL_ANY dispatch is permanently disabled for the affected client."

The fix moves the test_and_set_bit() call below both non-queueing gates so the bit is only taken when nfsd4_run_cb() will actually be invoked. The Fixes: tag points to commit 424dd3df1f99 ("nfsd: eliminate cl_ra_cblist and NFSD4_CLIENT_CB_RECALL_ANY").

Patch 2/2: Clear CALLBACK_RUNNING on failed delegation recall queue

This patch addresses a related but distinct failure mode in nfsd_break_one_deleg(). This function sets NFSD4_CALLBACK_RUNNING via test_and_set_bit at entry to serialize recall work, then calls nfsd4_run_cb() to queue the callback. If the queue attempt fails (e.g., the client's callback channel is unavailable), the refcount bump is undone but the RUNNING bit is left set.

"The bit becomes a permanent latch on dp->dl_recall.cb_flags: every subsequent break_lease() on the same delegation hits the early-return guard in nfsd_break_one_deleg() and silently skips the recall, so the delegation is never broken and the conflicting open or lock stalls."

This is particularly dangerous from a client perspective: a stuck delegation means any subsequent OPEN or LOCK operation targeting the same file will hang indefinitely on the server side. The fix clears NFSD4_CALLBACK_RUNNING on the !queued error path alongside the existing refcount_dec. The Fixes: tag points to commit 1054e8ffc5c4 ("nfsd: prevent callback tasks running concurrently").

Significance for NFS Client Development

While these are server-side fixes, they have direct implications for client behavior:

  • Patch 1 prevents a scenario where a client's delegation recall mechanism is silently disabled after a rate-limit or state gate fires. Without this fix, a client could hold a stale delegation indefinitely because the server would never send a CB_RECALL — leading to data consistency issues on the client side that are very difficult to diagnose.

  • Patch 2 prevents a scenario where a conflicting OPEN or LOCK request from a different client stalls forever because the server cannot break the existing delegation. This is a denial-of-service vector: any workload pattern that triggers callback queue failures (e.g., transient network issues on the callback channel) could wedge an entire file for all clients.

Both bugs are in the "silent failure" category — no error is logged, no RPC failure is returned to the client. The server simply stops functioning correctly for the affected delegation or client. This makes them particularly insidious in production environments.

Context: Broader NFSD Callback Work This Week

This thread sits alongside other significant NFSD callback-related activity this week. The CB_NOTIFY directory delegation series (v4) was posted May 22 and applied to nfsd-testing on May 23, followed by a four-patch follow-on fix series also applied quickly. The callback channel fixes in this thread are complementary — they harden the existing CB_RECALL machinery that predates the new CB_NOTIFY feature, ensuring the foundational recall path is robust before the more complex notification infrastructure builds on top of it.
