NFSD: Two Small atomic_open() Edge-Case Fixes in dentry_create()

Overview

On May 26, NeilBrown posted a two-patch series addressing edge-case problems in the NFS server's use of atomic_open() within dentry_create(), as flagged by automated review (Sashiko). Both patches carry Fixes: 64a989dbd144 ("VFS/knfsd: Teach dentry_create() to use atomic_open()"), making this a bug fix series targeting the NFS server's file-creation path. The fixes are small (12 lines and 1 line changed respectively) but close theoretical use-after-free and unopened-file-dereference windows that could be triggered under unusual export configurations.

Both patches received Reviewed-by tags from Jeff Layton and Benjamin Coddington within hours of posting. Chuck Lever, the NFS server maintainer, applied them by hand after a brief back-and-forth about base-tree compatibility — and used the opportunity to issue process guidance to the community about basing patches on nfsd-testing.

The Two Patches in Detail

Patch 1/2: Fix possible fh_compose of wrong dentry in nfsd4_create_file()

NeilBrown's first patch addresses a subtle use-after-free scenario:

"dentry_create() can hypothetically provide a different dentry than the one passed in. This could happen, for example, if the exported filesystem is NFS, and the server return to OPEN a filehandle which matched a directory that was already in the dcache."

The danger: if dentry_create() returns a different dentry than the one pre-stored in resfhp, the original child dentry could be freed and later dereferenced when fh_compose() is called. The fix moves the fh_compose() call to two explicit sites — one for the already-exists path, one after dentry_create() succeeds — so the filehandle is always composed from the final dentry.

"We shouldn't call fh_compose() until we are certain that we have the final dentry."

This is an 8-insertion / 4-deletion change in fs/nfsd/nfs4proc.c.

Patch 2/2: Ensure nfsd_file_to_acquire() does not use a non-opened file

The second patch is a one-line change in fs/nfsd/filecache.c. It adds an FMODE_OPENED check before using the file returned by dentry_create():

"->atomic_open is permitted to return success without actually opening the file. It indicates this by calling finish_no_open(). This mean dentry_create() can return a file which hasn't been opened."

NeilBrown acknowledges the scenario is extremely unlikely:

"This is extremely unlikely as ->atomic_open handlers typically use finish_no_open() only for already existing files, and dentry_create() isn't called in that case, and the parent being locked should prevent races. However out of an abundance of caution it seems wise to teach nfsd to only use the file returned by dentry_create() if FMODE_OPENED is set."

Review and Discussion Evolution

The review was swift and positive:

  1. Jeff Layton (May 26, ~6h after posting): "For both: Reviewed-by: Jeff Layton"

  2. Benjamin Coddington (May 26): "Except for the subject in 2/2 ( _do_acquire), these look correct to me. Thanks Neil." — followed by Reviewed-by for both patches.

  3. Chuck Lever (May 26) raised a practical concern: "These do not apply to nfsd-testing. Where should I apply them?"

  4. NeilBrown responded (May 26): "I created them against nfsd-next, but I just tried applying them to nfsd-testing with 'patch -p1'. The first works perfectly. The second works with Hunk #1 succeeded at 1181 (offset -46 lines). Is that what you mean by 'does not apply' ??"

  5. Chuck clarified (May 27): "The first patch applied, the second didn't. Since you didn't specify a base commit, it's always best to ask."

  6. Chuck's final message (May 27) escalated the point into community-wide process guidance:

"This comment is directed both to you and to the room: The second patch doesn't apply to nfsd-testing without conflicts. It's not just a 'Hunk succeeded' issue for me. That's a red flag."

He also noted an infrastructure detail: "any tool that tries to retrieve these patches directly from lore (like 'curl') is blocked by Anubis. So the 'b4 am' then 'git apply' or 'stg import' flow is the only one that is reliable. Also 'b4 am' does DKIM checking of the email sender."

And issued his forward-looking preference:

"Going forward, I prefer that you base your patches on current nfsd-testing so that I can leverage the careful checking that all the scripts do. I believe that is how contribution is documented in nfsd-maintainer-entry-profile.rst."

Despite the friction, Chuck confirmed he would apply both patches by hand: "I will apply these two by hand, but that really isn't scalable for me."

Significance for NFS Development

While these are server-side fixes (not client), they matter to the broader NFS ecosystem in several ways:

  • Correctness of the atomic_open() integration: Commit 64a989dbd144 was a significant VFS/knfsd refactoring that taught dentry_create() to use atomic_open(). These two patches close residual edge cases from that refactor, ensuring the server's CREATE path is robust even in exotic configurations (e.g., NFS-on-NFS exports).
  • Defense-in-depth: Both fixes are "extremely unlikely" scenarios per NeilBrown's own assessment, but they eliminate theoretical UAF and unopened-file-dereference vectors. In a network-facing service like NFSD, eliminating any path to memory corruption is valuable.
  • Process maturation: Chuck Lever's explicit guidance about basing patches on nfsd-testing (rather than nfsd-next) and using b4 am for reliable patch retrieval reflects the NFS server subsystem's continued effort to streamline contribution workflows — particularly relevant as the CB_NOTIFY directory delegation feature (see this week's related thread) pushes through multiple large patch series in rapid succession.

Status

  • Both patches: Reviewed (Layton, Coddington) and applied by hand to nfsd-testing by Chuck Lever.
  • No resend required despite the base-tree mismatch; Chuck handled it manually.
  • Process note: Future NFSD contributors are expected to base patches on current nfsd-testing and specify the base commit in the cover letter.
