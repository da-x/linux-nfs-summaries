svcrdma: Harden Parsed Chunk List Against Malformed Wire Values

Overview

This thread is a bug-fix series (not a new feature or protocol change) targeting the NFS/RPC server-side RDMA transport (svcrdma). Chuck Lever posted a 6-patch series on 2026-05-26, with three patches authored by Chris Mason (Meta) and three by Lever himself (Oracle). The work addresses a family of input-validation defects in the "parsed chunk list" (PCL) data structure, where wire-supplied values from an NFS client are stored verbatim and later consumed by unsigned arithmetic that can underflow.

The series was acknowledged within 24 hours by Jeff Layton, who replied on 2026-05-27 with:

"Acked-by: Jeff Layton jlayton@kernel.org"

No objections or technical pushback were raised in the thread. The discussion is short and decisive — a clean ack from the NFS maintainer within a day of posting.

The Core Problem

As Lever described in the cover letter PATCH 0/6:

"The RPC/RDMA transport stores wire-supplied chunk positions, lengths, and segment counts verbatim in the parsed chunk list. Consumer functions compute gap lengths and sub-range offsets from these values using unsigned subtraction. A malicious or buggy peer can supply values that cause these subtractions to underflow, exposing slab memory to the Reply channel or driving oversized allocations."

The fix proceeds in two layers: consumer-side bounds checks (immediately backportable) and decoder-side validation at the wire boundary (defense in depth).

Patch-by-Patch Breakdown

PATCH 1/6 — Validate Read chunk positions before reconstruction

Lever's first patch addresses the most direct information-disclosure path. The ch_position field in a Read chunk is client-supplied, and xdr_count_read_segments() only checked 4-byte alignment — it never compared the position against the actual inline body length received on the wire.

"In the single-chunk path, svc_rdma_read_complete_one() splits the head and tail kvecs at ch_position. A position past the inline body underflows the tail length, exposing adjacent slab memory to the upper XDR decoder."

In the multi-chunk path, overlapping Read chunks cause unsigned subtractions of gap lengths to underflow, and svc_rdma_copy_inline_range() then copies past the receive buffer into request pages that are returned to the client through the Reply channel. The fix bounds inline-range copies against rc_saved_arg and rejects positions beyond the body or overlapping chunk lists.

Fixes: d96962e6d0e2 ("svcrdma: Use the new parsed chunk list when pulling Read chunks")

PATCH 2/6 — Fix offset arithmetic in read_chunk_range (Chris Mason)

This patch, authored by Chris Mason at Meta and assisted by an AI tool ("Assisted-by: kres (claude-opus-4-7)"), fixes two subtle arithmetic defects in svc_rdma_read_chunk_range():

  1. The skip predicate used > instead of >=, so a fully-consumed segment was not skipped, causing a u32 underflow to near-UINT_MAX.
  2. The length formula subtracted offset from the min_t() result rather than from segment->rs_length before the cap, "silently dropping offset bytes from the rebuilt chunk."

"Combined with the boundary case above it also enables the u32 underflow path, which propagates a huge nr_bvec into svc_rdma_build_read_segment() and a multi-MiB kmalloc_array_node() in svc_rdma_get_rw_ctxt()."

The patch also handles the edge case where length == 0 (last Read chunk ends exactly at the end of the Call chunk), returning success immediately rather than -EINVAL.

Fixes: d7cc73972661 ("svcrdma: support multiple Read chunks per RPC")

PATCH 3/6 — Reject oversized Read segments at decode time

Lever's second patch caps segment lengths against the receive context's page budget during Read list decoding, consistent with how xdr_check_write_chunk() already bounds Write segment counts. It also fixes a resource leak: the existing post-allocation page-overrun guard in svc_rdma_build_read_segment() fired but did not return the freshly acquired rw context.

"An oversized rs_length reaches svc_rdma_build_read_segment(), which derives nr_bvec from it and can drive a large dynamic bvec allocation before verifying that enough rq_pages remain."

Fixes: 5ee62b4a9113 ("svcrdma: use bvec-based RDMA read/write API")

PATCH 4/6 — Fix pcl_for_each_segment for empty chunks (Chris Mason)

This is arguably the most dramatic bug in the series. When ch_segcount is zero, the macro's inclusive upper bound computes &chunk->ch_segments[0u - 1u], which wraps to index 0xFFFFFFFF:

"The loop body then walks unrelated memory at sizeof(struct svc_rdma_segment) stride until it faults."

A zero-segcount chunk is reachable from the wire because xdr_check_write_chunk() only rejects segcount values greater than rc_maxpages, and pcl_alloc_write() links a freshly allocated chunk onto the list before its segment-fill loop runs. When Send-With-Invalidate is negotiated, svc_rdma_get_inv_rkey() iterates all four PCLs and dereferences segment->rs_handle on each iteration, turning the underflow into an out-of-bounds read and a general protection fault.

The fix switches the macro to a half-open upper bound using ch_segcount directly — for zero segments, loop start equals loop end and the body is skipped. All six existing call sites remain correct with no changes needed.

Fixes: 78147ca8b4a9 ("svcrdma: Add a 'parsed chunk list' data structure")

PATCH 5/6 — Reject Write/Reply chunks with segcount 0 (Chris Mason)

Building on the macro fix, this patch adds decoder-side rejection of zero-segment Write and Reply chunks as defense in depth. As Mason explained:

"RFC 8166 has no meaning for a Write/Reply chunk that describes no remote buffer, so no legitimate client is affected."

The patch also reorders pcl_alloc_write() so that list_add_tail() follows the segment fill loop, ensuring only fully-populated chunks appear on the list — protecting against future regressions where an incomplete chunk might be visible to consumers during the fill loop.

Fixes: 78147ca8b4a9 ("svcrdma: Add a 'parsed chunk list' data structure")

PATCH 6/6 — Validate Read chunk positions at decode time (consolidation)

The final patch is a consolidation pass. Lever noted that position and length validation was "scattered across three consumer functions" with each independently guarding against the same class of underflow. The new pcl_check_read_chunk_positions() function performs a single post-decode pass verifying:

  • Each Read chunk's inline-body offset falls within the inline body (or Call chunk) length
  • Adjacent Read chunk positions do not overlap
  • Each chunk length does not exceed the receive context's page budget

"Malformed frames are rejected before reaching any consumer. The existing consumer-side guards remain as defense in depth."

This ensures future PCL consumers inherit the guarantee without replicating per-site checks.

Discussion and Outcome

The thread was brief by mailing-list standards. After Lever posted the series on Tuesday afternoon (UTC), Jeff Layton — the long-time NFS maintainer — replied the following day with a clean ack, quoting the cover letter in full before his sign-off. No other participants weighed in during this week's window.

The series is notable for several reasons:

  • Security relevance: The bugs are exploitable by a malicious or buggy NFS client, with impacts ranging from slab memory disclosure to kernel crashes (GPF) and multi-MiB allocation DoS.
  • Collaborative authorship: Three patches came from Chris Mason at Meta, three from Chuck Lever at Oracle — a cross-industry collaboration on server-side hardening.
  • AI-assisted development: Two of Mason's patches carry an "Assisted-by: kres (claude-opus-4-7)" tag, reflecting the growing use of AI tools in kernel development.
  • Backportability: Lever explicitly designed the consumer-side fixes to be independently backportable, and noted that the macro fix "remains as defense in depth and is safe to backport to trees without the decoder change."

The series modifies four files with 113 insertions and 20 deletions, based on commit 887d478bb2115cec0be8caae58bad4d4b3109b1a.
