SUNRPC: drain cache_cleaner before destroying a cache_detail (UAF fix)

Summary

SUNRPC: always drain cache_cleaner before destroying a cache_detail

Type: Bug fix — use-after-free in the SUNRPC client-side cache infrastructure.

This week's thread is short but consequential: a one-patch, same-day-merged fix for a latent memory-safety bug in the kernel's NFS/SUNRPC caching layer. The discussion spans only two messages on 2026-05-26, both within this week's window, so no prior-week bridging is needed.

The Bug

Jeff Layton opened the thread with a patch targeting a use-after-free in sunrpc_destroy_cache_detail(). As Layton laid out:

"sunrpc_destroy_cache_detail() only cancels the global cache_cleaner delayed_work when cache_list is empty. During per-netns teardown cache_list is never empty because init_net's caches remain registered, so the cancel never fires."

The consequence, in his words:

"After unlink, the caller proceeds to cache_destroy_net() which kfrees the cache_detail while cache_clean() may still hold a dangling pointer to it. The result is a use-after-free: cache_dequeue() takes cd->queue_lock on freed memory, and cache_put() dereferences cd->cache_put as a function pointer from freed slab."

In other words, the global cache_cleaner delayed work could be mid-flight when a per-netns teardown freed the cache_detail structure it was operating on — leading to a lock acquisition on freed memory and a function-pointer call through freed slab. This is squarely in NFS client territory: the SUNRPC cache layer underpins the auth/rdma caches used by every NFSv3/v4 client, so a UAF here can corrupt unrelated kernel state well beyond the network namespace being torn down.

The Fix

The patch is minimal — three insertions, four deletions in net/sunrpc/cache.c. Layton's summary of the approach:

"Drop the list_empty guard so that cancel_delayed_work_sync() always runs, ensuring any in-flight cache_clean() completes before the cache_detail is freed. Re-arm the cleaner afterwards if other caches are still registered."

The patch carries a Fixes: tag pointing at commit 820f9442e711 ("SUNRPC: split cache creation and PipeFS registration"), identifying when the list-empty guard was introduced, and an Assisted-by: Claude:claude-opus-4-6 line — one of the more visible AI-assisted contributions to the NFS tree this week.

Resolution

NFS maintainer Chuck Lever picked it up within 45 minutes of posting. His reply was terse and decisive:

"Applied to nfsd-testing, thanks!"

The patch landed as commit a6a67f4010de2424ae856d5e857079fe89f1178d in the nfsd-testing tree. No objections, no redesign debate — a textbook surgical fix for a well-understood race.

Context within the Week

This landed alongside a flurry of Michael Bommarito's NFSv4 delegation work (directory delegations v4/v5 series and several follow-up fixes) summarized elsewhere this week. The cache_cleaner UAF is unrelated to that stream but reinforces a broader theme in this week's client-side activity: tightening teardown paths and synchronization around shared kernel structures that the NFS client depends on.
