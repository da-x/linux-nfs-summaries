lockd: v3 of nlm_traverse_files() UAF fix lands in nfsd-testing after live-walk cleanup addresses skip-path leak

Summary

lockd: v3 of nlm_traverse_files() use-after-free fix lands in nfsd-testing

Type: Bug fix (NFS server / lockd) — slab use-after-free in nlm_traverse_files(), with a stable backport requested. This is the v3 and final iteration of Michael Bommarito's patch series that began earlier in the week; v1 was held up by Sashiko's predicate-check finding and v2 by a Codex/Sashiko flag on a reference-count leak in the skip path (see last week's summary for the v1/v2 backstory).

The bug, unchanged from v1 and v2

The underlying race is the same as in the prior two rounds: nlm_traverse_files() pins the current file with f_count++ across a mutex_unlock taken for nlm_inspect_file(), but leaves the saved next pointer unpinned. As Bommarito's v3 cover letter restates:

"nlm_traverse_files() pins the current file with f_count++ across a mutex_unlock for nlm_inspect_file(), but nothing pins the saved next pointer. A concurrent nlm_release_file() can kfree the next file during the unlock window, and the iterator dereferences freed memory on the next loop step."

The fix strategy — pin both cursors before the lock-drop and swap them at the end of each iteration — is carried over from v2:

"Pin both current and next before the lock-drop. Advance by swapping the pinned cursors at the end of each iteration so next is always held alive across the unlock."

What changed since v2

The substantive change in v3 directly answers the leak Chuck Lever's Codex review had flagged on v2, where the f_count---only path for non-matching files could strand an nlm_file entry forever if its last real release had been suppressed by the traversal pin. Bommarito's resolution is to always run cleanup after dropping the iteration pin, and to base that decision on a live walk of the inode lock list rather than the cached f_locks field:

"Always call nlm_file_release() after dropping the iteration pin, regardless of whether the file matched the predicate. Use nlm_file_inuse(), which does a live walk of the inode lock list, rather than the cached f_locks field, so skipped files that never ran nlm_inspect_file() are evaluated correctly."

The cover letter spells out why this is correct on both paths:

"nlm_file_inuse() is correct on both paths because it walks the actual POSIX lock list rather than relying on nlm_inspect_file() having refreshed the cache. (Chuck Lever.)"

Note the explicit attribution to Chuck Lever — the v3 design directly incorporates his review feedback from the v2 round, replacing the cached-field heuristic with a live walk that is correct whether or not nlm_inspect_file() ever ran on the entry.

The patch again carries Cc: stable@vger.kernel.org and Fixes: 01df9c5e918a ("LOCKD: Fix a deadlock in nlm_traverse_files()"), plus the same Assisted-by: Claude:claude-opus-4-7 trailer as v1 and v2. The KASAN reproduction harness is unchanged — UML + KASAN with 768 concurrent POSIX holders and parallel /proc/fs/nfsd/unlock_filesystem writes — and the cover letter reports:

"Stock kernel trips KASAN slab-use-after-free in nlm_traverse_files. Patched v3 silent."

Chuck Lever's response: applied

NFS maintainer Chuck Lever replied within roughly four hours on Sunday, May 24, and merged the patch:

"Applied to nfsd-testing, thanks!"

"[1/1] lockd: pin next file across nlm_inspect_file lock-drop — commit: 925b64e5fb12ad6517ff7c6729bf2fba7485f42c"

That is the first time this three-round series has cleared review; v1 and v2 had each been bounced by an automated reviewer (Sashiko, then Codex) before human sign-off.

Status / outlook

  • v3 accepted. Landed in nfsd-testing as commit 925b64e5fb12ad6517ff7c6729bf2fba7485f42c; expect it to ride the normal merge window into mainline and a -stable backport given the Cc: stable and Fixes: tags.
  • Client-side relevance: although this is server/lockd code, it directly affects NFSv3 clients holding many concurrent POSIX locks (fcntl(F_SETLKW)) against a Linux NFS server during nlmsvc_unlock_all_by_sb() / failover sweeps — the exact workload the KASAN harness exercises. The UAF would corrupt the lockd file hash table and could crash or wedge the server's lock service under heavy concurrent locking, which clients observe as stalled SETLKW calls or spurious NLMERR_LKTYPE responses during an unlock sweep.
  • Notable pattern: all three rounds of this patch were caught by automated reviewers (Sashiko on v1, Codex/Sashiko on v2) before human sign-off; the v3 fix that finally unblocked merge was itself a direct response to Lever's review feedback — a clean example of the AI-assisted + maintainer-review loop converging on a stable backport.
