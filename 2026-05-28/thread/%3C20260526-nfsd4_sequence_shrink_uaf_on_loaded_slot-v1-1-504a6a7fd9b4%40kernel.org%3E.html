nfsd: Fix remotely triggerable use-after-free in session slot shrinker

Summary

nfsd: Fix remotely triggerable use-after-free in session slot shrinker

Type: Bug fix (security-relevant, NFSv4.1+ server-side) Status this week: Patch posted; reviewer raised a follow-up concern about concurrent in-use slots; no resolution yet within the window.

The vulnerability

On Tuesday, May 26, Red Hat's Jeff Layton published a one-line fix for what he describes as a serious latent bug in the NFSv4 server's session-slot management: [PATCH] nfsd: don't free session slots that are still in use.

Layton walks through the failure mode with characteristic precision. When the kernel's memory shrinker kicks in and reduces se_target_maxslots below se_fchannel.maxreqs, the SEQUENCE handler checks three conditions before calling free_session_slots():

"1. se_target_maxslots < maxreqs (shrink was advertised) 2. slot->sl_generation == se_slot_gen (slot is up-to-date) 3. seq->maxslots <= se_target_maxslots (client acknowledges)"

The missing fourth condition, he notes, is the bug: "However, seq->slotid is never checked against se_target_maxslots." A client using a slot in the range [se_target_maxslots, maxreqs) can satisfy all three checks — its slot carries the current generation from a prior SEQUENCE, and it simply reports sa_highest_slotid <= se_target_maxslots to acknowledge the reduction.

The consequences are severe. Layton explains: "free_session_slots() then kfrees every slot at index >= se_target_maxslots, including the caller's own slot. The function continues to write sl_seqid, sl_flags, sl_generation, and stores the dangling pointer in cstate->slot." Worse still, the freed memory is later reused for the reply cache: "Later, nfsd4_store_cache_entry() copies up to maxresp_cached bytes of the compound reply into the freed sl_data[] array, corrupting whatever slab object now occupies that address."

He classifies the bug bluntly: "This is a remotely triggerable heap use-after-free from any authenticated NFSv4.1+ client with an established session, requiring only that the kernel memory shrinker has run against nfsd session slots (a normal occurrence under memory pressure)."

The fix itself is minimal — a 2-insertion/1-deletion change in fs/nfsd/nfs4state.c adding a check that the current request's slotid is below the shrink boundary before allowing the reduction to proceed. It carries a Fixes: tag pointing at commit 8fb77d12c76e ("nfsd: add support for freeing unused session-DRC slots"), the original commit that introduced the shrink path.

Reviewer pushback

Just over half an hour later, Trond Myklebust's long-time colleague Chuck Lever replied with a pointed observation that the patch may not close the hole entirely:

"The patch guards only against the caller freeing its own slot. It doesn't guard against freeing a different slot that is concurrently in use by another thread."

Lever then floated two possible directions for a more complete fix: "Perhaps free_session_slots() should skip any slot with NFSD4_SLOT_INUSE set. Or the shrink could be deferred until no high-numbered slots are in use?"

Where things stand

As of the end of this reporting window, Layton has not replied to Lever's concern, and no v2 of the patch has appeared on the list. The thread is therefore still open: the immediate self-freeing UAF is addressed by the posted patch, but the broader question of whether free_session_slots() can race with concurrent in-flight requests on other slots remains unresolved. Given that this is a remotely triggerable heap corruption reachable from any authenticated NFSv4.1+ client under ordinary memory pressure, expect this thread to see further activity — either a v2 that incorporates Lever's suggestion or a detailed explanation of why the existing locking already covers the concurrent case.

Context

This week on linux-nfs has been dominated by Michael Bommarito's directory-delegation series and its follow-up fix patches (see the related threads summarized this week). The Layton patch is a standalone, security-motivated bug fix with no dependency on that work, but it lands in the same fs/nfsd/nfs4state.c territory and underscores how subtle the session-slot lifecycle can be under memory pressure.
