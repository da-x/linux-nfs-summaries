xprtrdma: v2 decouples request recycling from RPC completion to fix DMA race

Summary

xprtrdma: Decouple req recycling from RPC completion (v2)

What happened this week

On 2026-05-23, Chuck Lever posted a three-patch v2 series, [PATCH v2 0/3] xprtrdma: Decouple req recycling from RPC completion](https://lore.kernel.org/linux-nfs/20260523000252.465074-1-cel@kernel.org/), to the linux-nfs list. This is a bug fix for the NFS/RDMA client (xprtrdma): it corrects a use-after-free in which an rpcrdma_req could be recycled back to its free pool while the HCA was still DMA-reading from its send buffer, risking corrupted retransmissions.

The thread contains only Lever's four postings (cover letter + three patches) this week — no reviewer replies landed within the window. It is the second revision of work first sent as a single patch on 2026-05-20.

The bug being fixed

The core defect, described in the cover letter, is that rl_kref was conflating two distinct lifetimes through one refcount:

"rl_kref currently conflates two lifetimes through one refcount: it gates when a Reply can wake its RPC task, and it gates when an rpcrdma_req can return to its free pool."

The marshal path only took the Send-side reference when sc_unmap_count > 0. A Send carrying only pre-registered buffers therefore took no Send-side reference. Lever explains the consequence:

"When the Reply for such an RPC arrives before its Send completes, the Reply handler drops rl_kref from 1 to 0 and frees the req while the HCA may still be DMA-reading from its send buffer. A retransmission can put different bytes on the wire."

The fix narrows rl_kref's job so a request returns to the free pool only after both owners release it — the RPC layer (slot allocation) and the Send side (DMA unmap). The patch carries Fixes: 0ab115237025 ("xprtrdma: Wake RPCs directly in rpcrdma_wc_send path").

Evolution from v1 to v2

This is a revision, not a fresh submission. The v1 single-patch series was posted on 2026-05-20 and immediately drew two kernel test robot build-failure reports (nios2 and riscv randconfigs), both flagging the same problem: struct rpc_xprt has no member named bc_pa_lock / bc_pa_list, and struct rpc_rqst has no rq_bc_pa_list. Those backchannel-prealloc symbols only exist under CONFIG_SUNRPC_BACKCHANNEL.

Lever acknowledged the trouble in a short reply on 2026-05-21:

"Bots and LLM review have found issues with this patch, so expect a v2."

The cover letter's "Changes since v1" section maps those findings onto concrete revisions:

  • Split into three patches — a prep patch converts the Send-signaling test from a kref_read to sc_unmap_count, and a separate patch names the request-pool slack at its allocation site.
  • Wrap the bc_prealloc release branch in CONFIG_SUNRPC_BACKCHANNEL — this directly addresses the kernel test robot build break on configs without the backchannel.
  • Order rpcrdma_sendctxs_destroy() ahead of rpcrdma_reqs_reset() in rpcrdma_xprt_disconnect() so the drain runs against pre-reset reqs.
  • Run xprt_rdma_bc_destroy() a second time from xprt_rdma_destroy() to reclaim bc_prealloc reqs returned by the disconnect's drain.
  • Add rpcrdma_sendctx_cancel() for the marshal-failure path; sendctx ring walkers skip entries with sc_req == NULL.

The three patches

[1/3] Use sendctx DMA state for Send signaling](https://lore.kernel.org/linux-nfs/20260523000252.465074-2-cel@kernel.org/) is the preparatory patch. It splits the SGE DMA-unmap loop into its own helper and uses sc_unmap_count directly for the signaling decision, removing one dependency on the old rl_kref semantics before the lifetime rules change:

"This keeps the current behavior but removes one dependency on the old rl_kref semantics before the request lifetime rules are changed."

[2/3] Decouple req recycling from RPC completion](https://lore.kernel.org/linux-nfs/20260523000252.465074-3-cel@kernel.org/) is the heart of the series. It moves kref_init out of the marshal path and into the slot-allocation paths (xprt_rdma_alloc_slot, rpcrdma_bc_rqst_get), with the release callback re-arming rl_kref before a req returns to a free pool. Lever lays out three invariants, including:

"Any rpcrdma_req held by an rpc_rqst has rl_kref >= 1."

Without that invariant, he warns, "an RPC task that aborts between slot allocation and marshal (gss_refresh failure or signal during call_connect, for example) would drive xprt_release() -> xprt_rdma_free_slot() -> kref_put against a refcount of zero, saturating refcount_t and stranding the slot."

Replies now complete the RPC directly — rpcrdma_reply_handler() calls rpcrdma_complete_rqst() instead of performing a kref_put. Because Send-side references can outlive RPC completion, connection teardown must drain sendctx entries whose unsignaled Sends never had a later signaled completion to walk the ring. The patch also fixes a backchannel teardown-ordering hazard: releasing a bc_prealloc req re-adds it to bc_pa_list, which xprt_destroy_backchannel() has already emptied, so xprt_rdma_destroy() runs xprt_rdma_bc_destroy(xprt, 0) a second time to reclaim them.

[3/3] Add request-pool slack for delayed recycling](https://lore.kernel.org/linux-nfs/20260523000252.465074-4-cel@kernel.org/) addresses the side effect of gating recycling on Send completion: a completed RPC's req can stay pinned by the sendctx ring until the next signaled Send completes. Lever bounds the headroom and explains why the pool must be enlarged:

"The req pool, however, must exceed max_reqs by enough that this recycle delay does not stall a slot allocation that the credit window would admit."

Since re_send_batch is set to re_max_requests >> 3 (one in eight Sends is signaled), at most max_reqs / 8 reqs can be held. The patch allocates max_reqs + DIV_ROUND_UP(max_reqs, 8) request objects and names the slack calculation at the allocation site "so the 1/8 bound stays tied to the Send-signaling batch size."

Conclusions and significance

This is a correctness fix for the NFS/RDMA client that preserves xprtrdma's performance model — most Sends remain unsignaled, relying on strong ordering of Send completions to limit interrupt rate. As Lever framed it in v1, unconditionally gating RPC completion on Send completion "deadlocks NFS callers waiting on an RPC whose Send completion never fires," so the design instead lets replies complete the RPC immediately while rl_kref alone governs when a request may be recycled. The net effect: the send buffer stays stable until the HCA is done with it, and the reply path no longer performs a cache-cold atomic kref_put on every reply.

The series touches six files (124 insertions, 49 deletions). No reviewer feedback had arrived within this week's window; a v3 of the work was subsequently posted later in the cycle, so this v2 remains an intermediate revision rather than a landed conclusion.
