VFS/NFSd: dentry_create() error-pointer fix for nfsd4_create_file() unlock failure applied

Summary

VFS/NFSd: dentry_create() error-pointer bug fixed and applied

This week a focused, well-received bug-fix thread landed on linux-nfs. NeilBrown posted a small patch to fs/namei.c that corrects an unfortunate interaction between the VFS dentry-creation helpers and the NFSv4 server's file-creation path — one that could leave a parent inode permanently locked. The patch drew quick Reviewed-bys from the NFS maintainers, sparked a brief performance discussion, and was applied to the vfs.fixes branch by Christian Brauner within three days.

The bug: an error pointer where a dentry is required

NeilBrown opened the thread with the patch and a careful root-cause analysis. The chain of events he traced:

"atomic_create() in fs/namei.c drops the reference to the dentry when it returns an error."

That behavior was carried into dentry_create(), so on an error from atomic_create() it would leave path->dentry as an error pointer rather than a counted dentry. The caller, nfsd4_create_file(), distinguishes the two cases by inspecting path->dentry. But NeilBrown pointed out the trap:

"The change to use start_creating()/end_creating() ... means that nfsd4_create_file() needs a valid dentry so that it can unlock the parent."

So when an exported filesystem uses ->atomic_create and that call fails, nfsd4_create_file() hands the error pointer to end_creating():

"the net result is that if NFSD exports a filesystem which uses ->atomic_create, and if a call to ->atomic_create returns an error, then nfsd4_create_file() will pass an error pointer to end_creating() and the parent will not be unlocked."

The fix keeps path->dentry always a valid dentry (the real error is already returned through a separate channel), adding a dget(orig_dentry) to compensate for atomic_open()'s dput on error. NeilBrown noted an edge case: if ->atomic_create() ever returns a different dentry, it is guaranteed (via d_spliace_alias()) to share the same d_parent, so passing it to end_creating() has identical effect. The patch carries Fixes: 64a989dbd144 ("VFS/knfsd: Teach dentry_create() to use atomic_open()").

Fast, positive review from the NFS maintainers

The NFS side moved quickly. Jeff Layton confirmed "the patch itself looks correct" and granted a Reviewed-by, while flagging that an automated review (Sashiko) had spotted two additional problems in nearby code worth examining. Benjamin Coddington added a second Reviewed-by the same day.

NeilBrown took the Sashiko findings seriously but assessed them as low-risk, explaining that one would "require a remote server that is seriously misbehaving" (returning a directory filehandle for an OPEN), and the other "appears to be impossible with in-kernel filesystems." He promised follow-up patches for those nfsd-side issues, while making clear his near-term intent:

"I'm working on a rewrite of nfsd4_create_file and lookup_open() so that nfsd can use a better interface which will improve the code and fix some minor edge-case behavioural issues. So I'm just focusing on simple fixes at this stage, not necessarily best fixes."

A performance objection — and why it didn't stick

Mateusz Guzik raised a performance concern with the added dget():

"atomic_open() is a static func with only 2 callers. perhaps it would be better to change its semantics instead? I'm asking because the vfs layer is very slow single-threaded and this here just adds even more slowdown due to avoidable 2 rmw atomics."

NeilBrown's reply settled it: optimizing the helper was pointless because

"My plan is to get rid of dentry_create() completely so I don't think there is any point trying to optimise it."

He said he had patches ready to give lookup_open() a cleaner interface and route nfsd through it, and offered to include Guzik on the cc list.

A parallel discovery from Jori Koolstra

Jori Koolstra revealed he had independently hit the same bug:

"I found this same bug and submitted a patch on the same day."

He agreed that atomic_open() dput-ing the dentry on failure is awkward (noting vfs_create() doesn't do so), but accepted NeilBrown's approach for now. He added his Reviewed-by, offered to review the upcoming lookup_open() rework, and noted his own in-flight O_CREAT|O_DIRECTORY proposal touches that same code. NeilBrown responded that he would "rather no big changes to atomic_open just now" and would welcome Koolstra's review of the rearrangement patches.

Applied

Christian Brauner applied the patch to the vfs.fixes branch of vfs/vfs.git, noting it should appear in linux-next soon. In a separate note he acknowledged the nature of the bug:

"Ugh, that's an unfortunate interaction."

Takeaways for NFS client/server development

  • Classification: Bug fix (not a new feature or protocol change), targeting the NFSv4 server (nfsd) file-creation path and the shared VFS dentry_create() helper.
  • Impact: Prevents a parent-inode lock leak when an ->atomic_create-based filesystem returns an error during an NFSv4 create — a correctness fix that protects against hung/stuck exports.
  • Follow-on work in flight: NeilBrown is preparing a rewrite of nfsd4_create_file() and lookup_open() to give nfsd a cleaner interface, plus simple fixes for the two Sashiko-flagged edge cases; Jori Koolstra's O_CREAT|O_DIRECTORY work will need rework against those changes.

This thread is a tidy example of a low-level VFS/NFSd interaction bug being caught, reviewed by both NFS maintainers within hours, and merged into the fixes branch in under a week.
