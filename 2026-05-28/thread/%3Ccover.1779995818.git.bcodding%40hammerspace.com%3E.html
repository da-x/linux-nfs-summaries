Ben Coddington posts client patch to preemptively return write delegation on access-dropping SETATTR

Summary

Client patch: optimize away CB_RECALL for write delegations

Overview

This week, Benjamin Coddington (Hammerspace) opened a new thread with a single-patch series aimed at the NFSv4 client. The goal is to eliminate an unnecessary CB_RECALL round trip that occurs when a client holding a write delegation issues a SETATTR that would strip its own write access. Rather than waiting for the server to recall the delegation, the patch has the client detect the situation locally and return the delegation first — a targeted bug fix / performance optimization in the delegation state machine.

The series landed on May 28 with no in-window replies yet; follow-up discussion from Trond Myklebust and Rick Macklem began the following day (May 29), outside this week's window, so it is noted only as a forward pointer.

The Problem

Coddington frames the issue in the cover letter:

"A client holding a write delegation that performs a SETATTR that would remove the client's write access can expect the server to recall that delegation. The following patch addresses the simplest case to detect this and then preemptively return the delegation rather than have server recall it."

The deeper mechanics are spelled out in the patch description. A client holding an OPEN_DELEGATE_WRITE delegation can satisfy a later open(O_WRONLY) from the cached delegation via can_open_delegated() without contacting the server. But that cached "open for write" assertion is only valid while the holder still has write access:

"A SETATTR that changes mode, owner, or group can revoke that access -- after which an open served from the delegation would bypass an access check the server would now fail."

So there are two failure modes the patch addresses:

  1. Correctness risk — serving a cached open for write after access was revoked would bypass a server-side access check.
  2. Latency cost — against a server that recalls on such a change, the SETATTR triggers an expensive CB_RECALL/NFS4ERR_DELAY/DELEGRETURN/retry round trip.

The Fix

The patch (62 insertions, 4 deletions in fs/nfs/nfs4proc.c) adds a pre-SETATTR check: before issuing the attribute change, the client evaluates whether the proposed mode/owner/group would remove write access for the delegation's owning credential, judged by the resulting POSIX mode bits. If so, it returns the delegation first — synchronously, which also flushes modified data — so the SETATTR then proceeds on an open or special stateid and the next open revalidates with the server:

"If so, return the delegation first: the return is synchronous and flushes modified data, so the SETATTR proceeds on an open or special stateid and the next open revalidates access with the server. Permission changes that keep the holder's write access leave the delegation in place."

Deliberate Conservatism

Coddington is explicit about the limits of a client-side heuristic. The check consults only mode bits and the holder's fsuid/fsgid; it cannot evaluate NFSv4 ACLs, privileged callers may retain access the bits deny, and supplementary group membership is not checked:

"the test is necessarily approximate -- but an inexact answer costs at most an unnecessary delegation return or a fall back to the server's recall, never incorrect access."

This framing — that a false positive degrades gracefully to existing behavior while a false negative is impossible — is the key safety argument for the approach.

Relationship to Prior Work

The patch description carefully situates this change relative to an earlier optimization. Commit c01d36457dcc ("NFSv4: Don't return the delegation when not needed by NFSv4.x (x>0)") had stopped returning write delegations on SETATTR for NFSv4.1+, since modern servers can identify the holder from the SEQUENCE clientid and need not recall. Coddington's patch carves out a narrow exception to that rule:

"That holds for changes that do not affect the holder's access; restore a return only for the narrow case where the holder's own write access is removed."

The change is also grounded in protocol permission — RFC 8881 Section 10.4.4 allows a client to voluntarily return a delegation, performing the same pre-return state updates (data flush, pending truncation, CLOSE/OPEN/LOCK) it would on a recall.

Status and Outlook

  • In-window activity: Initial posting only (cover letter + patch), May 28. No in-window review comments.
  • Forward pointer: Trond Myklebust replied on May 29 (just outside this window), followed by an exchange with Rick Macklem — suggesting the patch is now under active review. That discussion will be covered in next week's summary.

This is a focused, well-reasoned client-side improvement that trades a small amount of local state computation for the elimination of a multi-step recall round trip, while preserving correctness through a deliberately conservative access test.
