nfsd: fix use-after-free when shrinking session slots still in use

Summary

nfsd: don't free session slots that are still in use

This week brought a focused, single-patch bug-fix thread on the NFS server side (nfsd) addressing a serious memory-safety flaw in how NFSv4.1+ session slots are reclaimed. The discussion was short but dense: one well-documented patch from Jeff Layton and an immediate application by nfsd maintainer Chuck Lever.

The bug: use-after-free in the session slot shrink path

The thread is squarely about a bug fix (not a new feature or protocol change), targeting a flaw introduced by commit 8fb77d12c76e ("nfsd: add support for freeing unused session-DRC slots"). Layton's v2 patch opens with the core observation:

"nfsd4_sequence() can free the very slot it is currently processing."

Layton walks through the shrink logic in detail. When the session shrinker has lowered se_target_maxslots below se_fchannel.maxreqs, the code checks three conditions before calling free_session_slots():

"1. se_target_maxslots < maxreqs (shrink was advertised) 2. slot->sl_generation == se_slot_gen (slot is up-to-date) 3. seq->maxslots <= se_target_maxslots (client acknowledges)"

The missing fourth check is the crux of the bug:

"However, seq->slotid is never checked against se_target_maxslots."

A client using a slot in the range [se_target_maxslots, maxreqs) can satisfy all three existing conditions — its slot carries the current generation from a prior SEQUENCE, and it acknowledges the reduction by sending sa_highest_slotid <= se_target_maxslots. The result is that free_session_slots() "kfrees every slot at index >= se_target_maxslots, including the caller's own slot."

Layton then describes the concrete corruption path:

"The function continues to write sl_seqid, sl_flags, sl_generation, and stores the dangling pointer in cstate->slot. Later, nfsd4_store_cache_entry() copies up to maxresp_cached bytes of the compound reply into the freed sl_data[] array, corrupting whatever slab object now occupies that address."

A second, concurrency-related hole is also documented: a parallel thread processing SEQUENCE on another high-numbered slot can have its slot yanked out from under it. Layton notes that "NFSD4_SLOT_INUSE is set under nn->client_lock before the lock is released, so any concurrent thread past SEQUENCE will have its slot marked. However, free_session_slots() does not check NFSD4_SLOT_INUSE before freeing."

The fix

The patch addresses both problems with a small change (16 insertions, 1 deletion in fs/nfsd/nfs4state.c):

"Fix both problems by:

  1. Checking that the current request's slotid is below the shrink boundary.
  2. Scanning slots in the to-be-freed range for NFSD4_SLOT_INUSE and deferring the shrink if any are active."

The v2 revision specifically added the second safeguard — "Skip doing the shrink if any potential victims have NFSD4_SLOT_INUSE set" — building on a v1 posted earlier the same day. The patch carries a Fixes: tag pointing at 8fb77d12c76e, and notably an "Assisted-by: Claude:claude-opus-4-6" trailer, marking it as AI-assisted work.

Resolution

The thread closed quickly with no objections or further back-and-forth. nfsd maintainer Chuck Lever applied the patch to nfsd-testing just over two hours after it landed on the list:

"Applied to nfsd-testing, thanks! [1/1] nfsd: don't free session slots that are still in use commit: 6085718398d83e16ccdc864c209493671f3c5998"

Takeaway

This is a classic, high-severity server-side memory-safety fix: a use-after-free in the NFSv4.1+ session slot shrink path that could corrupt slab objects and potentially be triggered by an ordinary client acknowledging a slot reduction. The fix tightens the preconditions for freeing slots (verify the caller's own slotid is below the boundary) and adds a concurrency guard (defer the shrink if any victim slot is marked in-use). With Chuck Lever's prompt application to nfsd-testing, the patch is now queued for the next merge window.
