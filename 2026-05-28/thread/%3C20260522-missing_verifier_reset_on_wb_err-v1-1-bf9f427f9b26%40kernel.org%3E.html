nfsd: reset write verifier on deferred writeback errors

Summary

nfsd: reset write verifier on deferred writeback errors

A compact but consequential NFS server bug fix landed this week. Jeff Layton posted a one-patch series, nfsd: reset write verifier on deferred writeback errors, that plugs a silent data-loss hole in the kernel's NFS server (nfsd) — not the client, but one whose consequences are felt most acutely by clients relying on the UNSTABLE+COMMIT durability contract.

The bug

The patch description lays out the mechanics of the failure clearly:

"nfsd_vfs_write() and nfsd_commit() both call filemap_check_wb_err() to detect deferred writeback errors, but neither rotates the server's write verifier (nn->writeverf) when this check fails. Every other durable-storage-failure path in these functions calls commit_reset_write_verifier() before returning an error."

In other words, two of nfsd's error paths were forgetting to do something every sibling error path already did: rotate the write verifier. The practical impact, as Layton spelled out, is severe:

"The missing rotation means clients holding UNSTABLE write data under the current verifier will COMMIT, receive the unchanged verifier back, and conclude their data is durable — silently dropping data that failed writeback. This violates the UNSTABLE+COMMIT durability contract (RFC 1813 §3.3.7, RFC 8881 §18.32)."

That phrasing — "silently dropping data" — is what makes this a high-severity fix: clients have no protocol-level way to detect that the server has actually lost their bytes. The bug was reported by Chris Mason (clm@meta.com) and credited in the patch's Reported-by: trailer.

The fix

The change itself is small — 5 insertions, 1 deletion in fs/nfsd/vfs.c — adding commit_reset_write_verifier() calls at both filemap_check_wb_err() error sites to match the pattern already used by adjacent error paths. Layton notes a nice safety property of the existing helper:

"The helper already filters -EAGAIN and -ESTALE internally, so the calls are unconditionally safe."

Discussion and scope

Chuck Lever picked up the thread quickly and asked whether the same bug existed in another code path:

"Do you have an additional fix pending that addresses the same bug in the async COPY path? If not, I can post one."

Layton confirmed he did not, and agreed it should be handled separately — noting a subtle context difference:

"No, I don't. I didn't spot that one before. Handling it separately is probably good. That case isn't being called from nfsd context, so it'll need different handling."

So the async COPY path is acknowledged as carrying the same class of bug but is deferred to a follow-up patch; this week's thread only covers the synchronous nfsd_vfs_write() / nfsd_commit() paths.

Outcome

The fix was applied the same day it was posted. Chuck Lever confirmed:

"Applied to nfsd-testing, thanks!" "[1/1] nfsd: reset write verifier on deferred writeback errors — commit: f8cf3c1c418ef04947bc16e4a2ef8074452de593"

Classification and significance

  • Type: Bug fix (data-loss / protocol-contract violation), not a new feature or protocol change.
  • Subtree: NFS server (nfsd) in fs/nfsd/vfs.c, but the affected contract is one that NFS clients depend on for UNSTABLE write + COMMIT semantics — so client-visible behavior changes from "silently lose data" to "receive a new verifier and learn the commit failed."
  • Severity: High. The failure mode was silent data loss, which is among the worst classes of storage bug because there is no error signal to alert applications or operators.
  • Open follow-up: A companion fix for the async COPY path is expected from Chuck Lever; that thread has not yet appeared in this week's window.

The exchange is a good example of how small, mechanical fixes — adding one call to an existing helper at two missed sites — can close serious durability gaps, and how a careful reviewer (Lever) can immediately spot the same pattern elsewhere in the codebase.
