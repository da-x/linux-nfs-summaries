svcrdma: Five-patch series fixes resource lifecycle bugs in transport setup/teardown

Summary

svcrdma: Fixing Resource Lifecycle Bugs in Transport Setup and Teardown

Overview

On Wednesday, May 27, Oracle's Chuck Lever posted a five-patch series titled [PATCH 0/5] Fix resource lifecycle bugs in svcrdma transport setup and teardown](https://lore.kernel.org/linux-nfs/20260527-rdma-follow-on-v1-0-1b09bd87b6cd@oracle.com/) to the linux-nfs mailing list. The series addresses a cluster of memory leaks, use-after-free hazards, and reference-counting errors lurking in the NFS server's RDMA transport (svcrdma) — specifically in its creation, acceptance, and teardown paths. This is squarely a bug-fix effort, not a new feature or protocol change, though it touches on subtle resource-management design that affects how future partially-constructed transports are handled.

The series modifies two files: net/sunrpc/xprtrdma/ib_client.c and net/sunrpc/xprtrdma/svc_rdma_transport.c, with 74 insertions and 19 deletions across the five patches. Notably, the first patch is authored by Chris Mason (Meta) with Lever's sign-off, while the remaining four are Lever's own work.

Key Design Choices Spanning the Series

In the cover letter, Lever articulated two unifying design decisions:

"The first is the rn_done sentinel. rpcrdma_rn_register() assigns rn->rn_done only after xa_alloc() and kref_get() have both succeeded, making rn_done == NULL a natural 'never registered' marker."

This turns rpcrdma_rn_unregister() into an idempotent operation — callers no longer need to track whether registration completed before calling unregister. The accept error path, the reordered free path, and any future partially-constructed transport that reaches svc_rdma_free() all rely on this single mechanism rather than separate boolean flags.

"The second is routing error-path teardown through svc_xprt_put() instead of inline cleanup."

Previously, the accept error path did manual ib_destroy_qp / rdma_destroy_id / rpcrdma_rn_unregister sequences and then leaked the svcxprt_rdma; the listener create path called kfree() directly, bypassing svc_xprt_free()'s net namespace release. Both now drop the kref_init() birth reference via svc_xprt_put(), which dispatches svc_rdma_free() where existing NULL/IS_ERR guards (plus the new rn_done sentinel) handle partially-constructed state.

Patch-by-Patch Breakdown

Patch 1: Fix Unmatched rn_unregister on Failed Accept (Chris Mason)

This patch, authored by Chris Mason from Meta, fixes the most severe bug in the series. When svc_rdma_accept() takes the errout path before rpcrdma_rn_register() has succeeded:

"the existing cleanup block calls rpcrdma_rn_unregister(dev, &newxprt->sc_rn) unconditionally. svcxprt_rdma is kzalloc'd, so on that path sc_rn.rn_index is 0 and sc_rn.rn_done is NULL; the unregister therefore xa_erase()s another caller's slot 0 and performs an unmatched kref_put() on the rpcrdma_device's rd_kref."

This was a cross-transport corruption bug — one failed accept could destroy another transport's registration. The same errout path also leaked the svcxprt_rdma (and the net/ns_tracker it pinned) because the kref went 1 → 2 → 1 and never reached zero.

The fix introduces the rn_done sentinel guard in rpcrdma_rn_unregister() and routes cleanup through svc_xprt_put(). The patch carries a Fixes: tag pointing to commit 8ac6fcae5dc0 ("svcrdma: Unregister the device if svc_rdma_accept() fails") and an "Assisted-by: kres (claude-opus-4-7)" tag, indicating AI-assisted development.

Patch 2: Reorder rpcrdma_rn_unregister before rdma_destroy_id

This patch addresses a use-after-free race in svc_rdma_free():

"svc_rdma_free() caches rdma->sc_cm_id->device before teardown, then calls rdma_destroy_id(sc_cm_id) which frees the cm_id. rpcrdma_rn_unregister() follows, but between those two calls the transport's sc_rn entry is still installed in the device's rd_xa. A concurrent ib_unregister_device walk can dispatch svc_rdma_xprt_done() against the now-freed sc_cm_id."

The fix moves rpcrdma_rn_unregister() before rdma_destroy_id() so the notification entry is removed from the xarray before the cm_id it references is destroyed. It also adds a NULL guard for sc_cm_id dereference, anticipating paths introduced by later patches. Fixes tag: c4de97f7c454.

Patch 3: Use svc_xprt_put to Free Listener on Create Failure

This patch fixes a net namespace reference leak:

"svc_rdma_create() calls kfree(cma_xprt) when svc_rdma_create_listen_id() fails. svc_xprt_init() has already acquired a net namespace reference via get_net_track(); kfree bypasses svc_xprt_free() which releases it."

The fix replaces kfree() with svc_xprt_put() and adds a compensating __module_get() to balance the module reference that both svc_xprt_free() and the caller _svc_xprt_create() would otherwise double-put. Fixes tag: 4fb8518bdac8 ("sunrpc: Tag svc_xprt with net").

Patch 4: Reject Connection When Transport Allocation Fails

This patch addresses a remotely amplifiable resource leak:

"handle_connect_req() returns without action when svc_rdma_create_xprt() fails to allocate the new transport. The CM core returns 0 for CONNECT_REQUEST events, so it does not destroy the new rdma_cm_id. Each allocation failure under memory pressure leaks one rdma_cm_id, and a remote peer driving connection attempts can amplify this."

The fix rejects the connection by returning a non-zero status from the CM event handler, telling the CM core to destroy the orphaned cm_id. This is notable as a security-adjacent fix — it prevents a remote peer from amplifying resource exhaustion. Fixes tag: 377f9b2f4529 ("rdma: SVCRDMA Core Transport Services"), one of the oldest commits in svcrdma's history.

Patch 5: Clear sc_cm_id When ADDR_CHANGE Replacement Fails

This patch fixes a use-after-free in the address-change handling path:

"When svc_rdma_listen_handler() handles RDMA_CM_EVENT_ADDR_CHANGE, it creates a replacement listener cm_id and returns 1, telling the CM core to destroy the old one. If the replacement allocation fails, sc_cm_id still points at the old cm_id that the CM core is about to destroy. Any subsequent dereference of sc_cm_id -- such as svc_rdma_detach()'s rdma_disconnect() call -- is a use-after-free."

The fix NULLs sc_cm_id on the failure path and guards svc_rdma_detach()'s rdma_disconnect() call against NULL. Fixes tag: d1b586e75ec6 ("svcrdma: Handle ADDR_CHANGE CM event properly").

Review and Acknowledgment

Within roughly 20 minutes of posting, Red Hat's Jeff Layton replied with an acknowledgment, though he was candid about his comfort level:

"I don't feel confident in my own abilities to review svcrdma patches, so."

"Acked-by: Jeff Layton jlayton@kernel.org"

This is a common pattern on the NFS list — Layton, as a long-time sunrpc maintainer, provides an Acked-by to signal that the patch is acceptable for merge even when the specific subsystem (svcrdma) falls outside his deep expertise. The quick turnaround suggests no concerns were raised about the approach.

Significance and Context

This series is significant for several reasons:

  1. Breadth of impact: The bugs span the entire transport lifecycle — creation, acceptance, address change, and teardown — suggesting a systemic weakness in how svcrdma handles error paths for partially-constructed state.

  2. Security relevance: Patch 4 specifically addresses a remotely triggerable resource leak, making it relevant to NFS server hardening.

  3. Design improvement: The rn_done sentinel and the routing of all error paths through svc_xprt_put() establish a cleaner invariant that will simplify future maintenance. As Lever noted in the cover letter: "callers no longer need to track whether registration completed before calling unregister."

  4. AI-assisted development: Patch 1's "Assisted-by: kres (claude-opus-4-7)" tag marks one of the more prominent examples of AI-assisted kernel development on the NFS list, with the fix credited to Chris Mason at Meta.

The series appears ready for merge pending standard review cycles, with Layton's early Acked-by clearing the path.
