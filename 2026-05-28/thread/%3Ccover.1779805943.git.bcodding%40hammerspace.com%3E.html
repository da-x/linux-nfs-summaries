Summary

nfs-utils: New nfs-fh-verify Tool for Validating kNFSD Signed Filehandle MACs

Overview

Type: New user-space utility (nfs-utils) — a standalone diagnostic tool to offline-verify that the Linux NFS server (knfsd) is correctly applying its 8-byte SipHash-2-4 filehandle signature to exports configured with sign_fh. Not a kernel patch, not a protocol change, and not a bug fix per se; rather an operational/verification aid for administrators who have enabled signed filehandles but lack confidence the feature is actually working.

The thread was short and productive — four messages on May 26, 2026, from Benjamin Coddington (Hammerspace) and Chuck Lever (kernel.org). No maintainer objections were raised; the discussion centered on whether Wireshark could subsume the tool's function.

The Problem

Coddington opened with a cover letter that captures the motivation succinctly:

"We've had a lot of folks configure signed filehandles, and then wonder 'Is this thing actually working?'. Given the various filehandle lengths and types, it can be pretty difficult to know if the kernel is actually correctly signing its filehandles."

The sign_fh export option (introduced in kernel commit 2a83ffc55750) causes knfsd to append an 8-byte SipHash-2-4 MAC to every filehandle it returns. The key is derived from a key file via the existing hash_fh_key_file() helper and pushed into the kernel through the NFSD_A_SERVER_FH_KEY netlink attribute by nfsdctl. But once configured, there was no simple offline way to confirm the MACs were being computed correctly — especially across heterogeneous deployments with different filehandle lengths and types.

The Tool: nfs-fh-verify

The single patch adds a 337-line C utility under tools/nfs-fh-verify/ in the nfs-utils tree, along with a man page and build system integration (529 insertions across 5 files). Key design points from the patch description:

  • Input: reads filehandles in ASCII hex from stdin (one per line), tolerant of 0x prefixes, : or whitespace separators, # comments, and mixed case.
  • Key derivation: uses the same hash_fh_key_file() helper that nfsdctl uses, so the 128-bit SipHash key matches what the running server was configured with.
  • Verification: recomputes the trailing 8-byte MAC over fh[0..n-8] and reports OK, BAD, or MALFORMED per filehandle.
  • Exit codes: 0 if all verified, 1 on any BAD/MALFORMED, 2 on setup error — making it scriptable for monitoring in distributed installations.
  • Self-checking SipHash: embeds a small reference port of the kernel's lib/siphash.c, validated at startup against two published Aumasson/Bernstein test vectors so that "an incorrect build refuses to emit verdicts rather than silently mis-reporting."
  • Build integration: wired behind --disable-nfs-fh-verify (default on), mirroring the existing nfsrahead pattern.

Coddington also noted a secondary use case beyond one-off verification:

"Beyond that, this tool shows a way to monitor the configured state of signed filehandles in a distributed installation."

The patch carries a Co-Authored-By: Claude Opus 4.7 <noreply@anthropic.com> trailer, continuing the week's pattern of prominently AI-assisted submissions (also seen in Michael Bommarito's pNFS GETDEVICEINFO and lockd series).

Discussion: Wireshark as an Alternative?

Chuck Lever responded within an hour with a practical question:

"Do you know if wireshark might be able to handle this verification instead? It might be quite useful to see a 'FH Verified' on every RPC in a network capture."

This is a reasonable suggestion — Wireshark already has NFS dissector support, and per-packet MAC verification in a capture would provide continuous, in-context validation rather than a batch offline check.

Coddington's reply acknowledged the idea but raised two practical objections:

"If we ever change the way we hash the fh-key-file in nfs-utils, we'd have a wireshark drift problem. But, its unlikely we'd change it in nfs-utils and trash everyone's existing filehandles."

"We'd have to build an interface to point it at the fh-key-file of course - would that constant reconfiguration in wireshark make it less useful than this utility?"

And he made his near-term preference explicit:

"I have a slight preference for this tool in the near-term because it immediately solves my problem rather than having to wait for distros to downstream wireshark work."

The exchange was collegial and non-blocking. Lever's Wireshark suggestion was noted as a possible future complement, but no one argued against merging the standalone tool into nfs-utils.

Significance for NFS Client Development

While this is a server-side diagnostic (it validates what knfsd sends), it has indirect client relevance:

  • Signed filehandles affect every NFSv4 client that mounts an export with sign_fh. If the MAC is wrong or missing, clients may reject filehandles or fail to recognize previously cached ones. A quick offline verification tool helps administrators rule out server-side misconfiguration before debugging client behavior.
  • The tool's key-derivation path (hash_fh_key_file() → NFSD_A_SERVER_FH_KEY) documents the exact contract between nfs-utils userspace and the kernel, which is useful reference for anyone implementing or auditing filehandle signing on the client side.
  • In distributed environments (the primary Hammerspace use case), being able to batch-verify a list of filehandles against a known key provides a fast triage step when clients report intermittent access failures that could be filehandle-related.

Status

  • Patch posted, no objections. As of the end of this week's window (May 29), no maintainer has applied or objected to the patch. Given the absence of review comments beyond Lever's Wireshark musing, and given it is a self-contained userspace addition with no kernel impact, acceptance appears likely in the near term.
