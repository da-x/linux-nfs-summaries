SUNRPC: Reject short RFC 4121 MIC tokens in gss_krb5_verify_mic_v2

A short but security-relevant thread landed this week, opened by Chuck Lever with a small bug-fix patch to the Linux NFS client's Kerberos GSS implementation and closed out the next morning with a quick review from Jeff Layton. The discussion is squarely about a bug fix — specifically an out-of-bounds read in the RFC 4121 MIC verification path that could be triggered by a malicious NFS server.

The bug: missing length check in gss_krb5_verify_mic_v2()

Chuck Lever's patch (submitted 2026-05-23, reported by Chris Mason of Meta) describes a missing bounds check in the client-side Kerberos MIC verifier:

"gss_krb5_verify_mic_v2() reads the token ID at ptr[0..1], the flags byte at ptr[2], and padding at ptr[3..7], then passes ptr + GSS_KRB5_TOK_HDR_LEN and cksum_len to gss_krb5_mic_build_sg(). None of these accesses check read_token->len first."

Lever walks through all four callers that funnel wire-supplied token lengths into this function, demonstrating that none of them enforce a lower bound large enough to be safe:

  • gss_unwrap_resp_integ() — the client-side path most relevant to NFSv3/v4 RPCSEC_GSS integrity protection. It only enforces an upper bound (offset + len <= rcv_buf->len) before doing mic.data = kmalloc(len). Lever is explicit about the attack surface:

    "A malicious NFS server can therefore supply a short checksum opaque, producing a small slab allocation that the Kerberos MIC verifier reads past."

  • gss_validate() — only checks len <= RPC_MAX_AUTH_SIZE (400) before passing the wire-supplied length into gss_validate_seqno_mic().
  • svcauth_gss_verify_header() — server-side, but the same class of bug: it only requires checksum.len >= XDR_UNIT (4 bytes).
  • svcauth_gss_unwrap_integ() — checks only that the checksum fits in gsd->gsd_scratch.

The minimum safe token size is GSS_KRB5_TOK_HDR_LEN (16 bytes) plus ctx->krb5e->cksum_len (12–24 bytes depending on enctype), so any token shorter than ~28 bytes is invalid.

The fix: a 3-line length guard

The patch adds a single early-return at the top of gss_krb5_verify_mic_v2(), before any ptr[] access or scatterlist construction, returning GSS_S_DEFECTIVE_TOKEN when the token is too short. Lever justifies why this is safe for legitimate traffic:

"Well-formed MIC tokens from gss_krb5_get_mic_v2() already have exactly GSS_KRB5_TOK_HDR_LEN + cksum_len bytes, so valid traffic is unaffected."

The change touches only net/sunrpc/auth_gss/gss_krb5_unseal.c (3 insertions) and carries a Fixes: tag pointing at de9c17eb4a91 ("gss_krb5: add support for new token formats in rfc4121"), indicating the bug has been present since RFC 4121 token-format support was originally merged.

Review and disposition

The thread closed quickly. Jeff Layton replied the following morning (2026-05-24) with a single line after quoting the patch:

"Reviewed-by: Jeff Layton jlayton@kernel.org"

No objections, no design debate — the fix is minimal, localized, and clearly correct. With an upstream reporter (Chris Mason / Meta), a Fixes: tag, and a Reviewed-by from the NFS/GSS maintainer, this patch is in good shape for the next merge window.

Significance for NFS client development

While small, this is a meaningful hardening fix for the NFS client's RPCSEC_GSS integrity path: it closes an out-of-bounds slab read that a hostile server could trigger against any Linux NFS client using Kerberos v2 (RFC 4121) MIC tokens. The same class of bug exists on the server side (svcauth_gss_*), which Lever documents but does not fix in this patch — worth watching for a follow-up.
