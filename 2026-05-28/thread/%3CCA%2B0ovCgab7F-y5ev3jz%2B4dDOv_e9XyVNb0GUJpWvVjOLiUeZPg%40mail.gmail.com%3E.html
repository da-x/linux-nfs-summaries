Independent rediscovery of fixed sunrpc cache_seq_start_rcu() slab-out-of-bounds bug

Summary

Independent Rediscovery of Fixed cache_seq_start_rcu() Slab-Out-of-Bounds Bug

Type: Bug fix (already merged) — this week's thread is a short exchange confirming that an independently reported vulnerability has already been addressed.

The Report

On May 28, Farhad Alemi (UC Berkeley) posted a bug report to linux-nfs titled [BUG] sunrpc: cache_seq_start_rcu() slab-out-of-bounds (unpriv-userns reachable). The report described a slab-out-of-bounds read in the sunrpc cache sequence-file code, reachable from an unprivileged user namespace. Alemi noted that he had performed a novelty check against the syzbot dashboard but did not find a matching report before submitting his own.

Chuck Lever's Response: Already Fixed

Within 45 minutes, NFS maintainer Chuck Lever replied confirming the bug was already known and fixed:

"Your report appears to be an independent rediscovery of a bug syzbot already reported and which we've already fixed. The fix was pushed this week to Linus for merge into v7.1-rc5."

Lever pointed Alemi to the original syzbot instance (ID 60cfa08822470bbebe44) that had first triggered the KASAN report on April 21:

"Your novelty check noted that you searched the syzbot dashboard but did not find a match. See syzbot instance ID 60cfa08822470bbebe44."

Technical Background (from prior weeks)

The underlying bug was introduced by commit 7b546bd89975 ("sunrpc/cache: improve RCU safety in cache_list walking."), which changed the tail of __cache_seq_start() to unconditionally store *pos = ((long long)hash << 32) + 1 before returning, dropping a prior hash >= cd->hash_size guard. When the while loop exits because every remaining bucket is empty, hash equals cd->hash_size, so the stored position points one past the last valid bucket. A subsequent pread(2) at that file offset skips traverse() and hands the stale index back to __cache_seq_start(), which decodes hash = cd->hash_size and dereferences cd->hash_table[cd->hash_size] — one hlist_head past the end of the kzalloc'd table.

KASAN reported an eight-byte slab-out-of-bounds read at the tail of the 2048-byte hash_table allocation for the NFSD export cache (EXPORT_HASHMAX * sizeof(struct hlist_head) == 256 * 8). The trigger path involves unshare(CLONE_NEWNET) creating a new network namespace, which initializes the NFSD export cache, followed by a pread(2) on the corresponding /proc seq_file.

The Fix

Chuck Lever posted the fix on April 21, adding a bounds check to reject an out-of-range input hash before touching the hash table:

"Reject an input hash that is out of range before touching the hash table. cache_seq_next() already bounds-checks its own loop; the start routine needs to be symmetric."

The patch (3 lines in net/sunrpc/cache.c) received quick reviews from Benjamin Coddington ("We were hunting for this one. You'll probably get a Tested-by shortly.") and NeilBrown ("I prefer the approach you took as it is more robust.").

A separate, independent patch from Alessandro Zanni addressing the same syzbot report was posted on April 28, but Lever noted it was already superseded by the fix in his nfsd-testing tree.

Real-World Impact Confirmed This Week

In a related thread also active this week, Calum Mackay (Oracle) confirmed the fix resolves production crashes:

"This looks good to me, Chuck. Fixes the frequent sosreport crashes in cache_check_rcu we've been seeing, even with Erkun's revert applied."

The fix was pushed to Linus for merge into v7.1-rc5 during this week.

Conclusion

This thread is a brief two-message exchange: an external researcher independently rediscovered and reported a sunrpc cache slab-out-of-bounds vulnerability that was already known via syzbot, and the NFS maintainer confirmed the fix had just been merged for v7.1-rc5. No new code or discussion resulted — the bug is closed.
