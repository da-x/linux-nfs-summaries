Summary

tmpfs "security.foo" xattr series: boot-time NULL deref reported, diagnosed, and fixed

What this thread is about

This week's activity in this thread is a bug fix cycle for Miklos Szeredi's three-patch VFS/tmpfs cleanup series titled "tmpfs: simplify constructing 'security.foo' xattr names" (root message 177945382308.2991556.1256192774754909984.b4-ty@b4, posted 2026-05-19). Although the series lives in linux-fsdevel/VFS, it landed on the linux-nfs list because the breakage was discovered while exercising NFS server (nfsd) test trees that pull in VFS changes. The week's arc: a reproducible kernel panic is reported → the root cause is identified in one line of reasoning → a follow-up fix patch is posted and verified by the reporter.

Monday: Calum Mackay reports a reliable boot crash

Oracle's Calum Mackay opened this week's segment by bisecting the breakage to Miklos' three patches:

"I have been doing some testing of Chuck's nfsd-testing tree, which includes some vfs changes. The test systems are reliably crashing, in what looks like it might possibly be something related to these three patches."

"I reverted the three patches, and the crashes stopped."

He attached a full oops from a QEMU/i440FX guest running 7.1.0-rc4.master.20260524.el10.rc1.x86_64, with the faulting instruction at simple_xattr_set+0x27/0x8b0 (NULL pointer dereference, address 00000000000000e0) during PID 1 (systemd). The call trace is the key evidence:

kernfs_new_node → __kernfs_new_node → security_kernfs_init_security
  → selinux_kernfs_init_security → kernfs_xattr_set → simple_xattr_set (NULL deref)

The crash fires when SELinux tries to initialize a security.* xattr on a freshly created cgroup directory — i.e. any boot with cgroups + SELinux hits it, which is why the reporter's test VMs die within seconds. The NFS angle is indirect but real: Calum was exercising nfsd via Chuck Lever's testing tree, and the VFS changes in that tree are what exposed the latent ordering bug in kernfs_new_node().

Tuesday: Miklos pinpoints the root cause

Miklos Szeredi replied the next morning with a one-line diagnosis and Cc'd Greg KH (the cgroup/kernfs maintainer):

"Since __parent is assigned after security_kernfs_init_security() gets called, kernfs_root() will return NULL."

"Greg, any idea about dealing with this?"

In other words, the simplification series reordered the node-initialisation path so that the LSM hook now runs before the parent pointer is wired up; selinux_kernfs_init_security() then walks back to the root via a NULL __parent and dereferences it. Miklos framed the question as an ordering problem for Greg — "Don't call this so early?" — rather than asking for a full revert.

Tuesday: Christian Brauner ships the fix patch

Christian Brauner (VFS maintainer, co-author of the series) responded within ~15 minutes with a follow-up patch. The body was trimmed at ingest, but Calum's reply quotes the operative line:

"The appended patch should fix it."

Wednesday: verification and Greg's non-answer

Calum Mackay confirmed the fix on his test systems and signed off:

"Looks good to me, thanks Christian; no more crashes with that patch."

Tested-by: Calum Mackay <calum.mackay@oracle.com>

Meanwhile Greg Kroah-Hartman answered Miklos' direct question with characteristic brevity:

"Don't call this so early? :)"

"I really don't know, sorry. — greg k-h"

Where things stand

  • Status: The three-patch series is effectively held pending Christian's follow-up fix patch, which has a Tested-by from the original reporter and no objections on record this week.
  • Nature of the change: Bug fix (NULL pointer dereference at boot) introduced by a VFS/tmpfs code simplification; not an NFS protocol or feature change. The NFS client/server is only affected insofar as nfsd test trees pull in the broken VFS tree.
  • Key technical argument: LSM init_security hooks must run after the kernfs parent pointer is established, because SELinux's hook walks to the root via that pointer; reordering the assignment broke an implicit invariant.
  • Open item: The fix patch itself has not yet been formally queued/acknowledged in-thread within this week's window; watch for it landing in vfs/vfs (the series referenced git.kernel.org/vfs/vfs/c/12e9e3cd03b5).
