nfsd: XDR length-calculation fix in flexfile LAYOUTGET encoder

Summary

nfsd: Fix XDR Length Calculation in nfsd4_ff_encode_layoutget

Type: Bug fix (NFS server / NFSv4.1+ flexfiles layout) — direct impact on NFS client correctness

The Problem

On May 28, Jeff Layton posted a patch fixing a cluster of buffer-size miscalculations in nfsd4_ff_encode_layoutget(), the function that encodes the LAYOUTGET reply for the flexfiles layout type. As he laid out:

"The XDR buffer size calculation in nfsd4_ff_encode_layoutget() has multiple errors that can result in either an out-of-bounds write or leaking uninitialized kernel memory to the client."

Layton itemized three distinct defects:

  1. fh_len did not account for XDR padding on the file-handle data;
  2. The uid/gid lengths used 8 + len, but xdr_encode_opaque() actually writes 4 + xdr_align_size(len) bytes;
  3. ds_len omitted the flags and stats_collect_hint fields (8 bytes), while the header constant overestimated by 8 — "these partially cancel but leave a net mismatch."

The failure modes were asymmetric, which is what made this one especially nasty:

"The worst case occurs with short strings (e.g. uid=0, gid=0 with an odd-sized file handle), where the function writes up to 5 bytes past the reserved XDR buffer. Conversely, when string lengths happen to be 4-byte aligned, the reservation is too large and stale buffer content is sent to the client."

So depending on input shape, the server either smashed memory (a real security/stability bug) or shipped garbage bytes to the client — both violating the XDR contract that NFS clients rely on for byte-exact decoding.

The patch breaks every encoded field out explicitly in ds_len, uses xdr_align_size() for all variable-length opaque fields, and corrects the header constants. It touches only fs/nfsd/flexfilelayoutxdr.c (11 insertions, 6 deletions) and carries a Fixes: tag pointing at 9b9960a0ca47 ("nfsd: Add a super simple flex file server") — i.e., the bug has been present since the flexfiles layout code was first introduced. The patch also bears an Assisted-by: kres:claude-opus-4-7 line, continuing the pattern of LLM-assisted review in this codebase.

Bridge to Prior Week

This thread is the direct follow-up that Chuck Lever requested in yesterday's flexfiles GETDEVICEINFO thread. There, while reviewing Layton's ff_encode_getdeviceinfo padding fix, Lever had flagged:

"nfsd4_ff_encode_layoutget at fs/nfsd/flexfilelayoutxdr.c:40-41 has the same unaligned pattern for UID/GID strings: 8 + uid.len + 8 + gid.len. Do you intend to address that calculation as well?"

Layton had replied, "Yep, I just saw the Sashiko review for it. I'll fix that one up in a separate patch." This thread is that promised follow-up — and notably, the final analysis went further than Lever's initial pointer, also catching the fh_len padding miss and the ds_len flags/stats_collect_hint imbalance.

No substantive review objections — the fix landed in nfsd-testing within ~36 minutes of posting, closing out the last known instance of this class of XDR padding bug in the flexfiles encoder.

Significance for NFS Client Development

Although this is a server-side fix, the impact lands squarely on NFS clients:

  • Memory-safety exposure: A 5-byte OOB write in a network-facing kernel path is a genuine stability and security concern for any host running nfsd with flexfiles exports.
  • Client-visible corruption: When the reservation was oversized (the 4-byte-aligned case), stale reply-page bytes were transmitted to clients as part of the LAYOUTGET reply. A conforming client would decode those bytes as part of the deviceinfo list — potentially mis-parsing flags, stats_collect_hint, or subsequent layout segments, leading to wrong-device I/O selection or outright decode failures.
  • Closing the flexfiles XDR bug class: Together with yesterday's ff_encode_getdeviceinfo fix (commit d53136757d41), this patch clears out the remaining known padding/length miscalculations in flexfilelayoutxdr.c. Lever had earlier noted his longer-term preference would be "to convert to xdrgen instead, but that's a much bigger and less back-portable change" — so for now, hand-audited XDR arithmetic is what keeps flexfiles clients happy.
