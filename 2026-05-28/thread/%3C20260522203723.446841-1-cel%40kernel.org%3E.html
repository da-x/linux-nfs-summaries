nfsd: reset write verifier when async COPY writeback fails (v2)

Summary

nfsd: rotate the write verifier on async-COPY writeback failure

This short thread is a bug fix in the Linux NFS server (nfsd), and it lands as a quiet but important follow-on to a data-durability bug that was being fixed in the same week. Chuck Lever posted PATCH v2 on Friday, May 22, and Jeff Layton returned a Reviewed-by within twenty minutes — the whole exchange fits inside one afternoon.

The bug in plain terms

NFSv4's async COPY (server-side offload) hands back a write verifier to the client via CB_OFFLOAD. If post-copy writeback fails, the server is supposed to tell the client "your data is UNSTABLE" so the client issues COMMIT and re-checks durability. Lever walks through the failure mode in the cover letter:

"A client that receives NFS_UNSTABLE in CB_OFFLOAD follows up with COMMIT to make the copied data durable. With the verifier unchanged, COMMIT returns the same value the client just received via CB_OFFLOAD, and the client concludes the copy is durable -- silently dropping the data whose writeback in fact failed."

That violates the UNSTABLE+COMMIT durability contract (RFC 7862 §15.1, RFC 8881 §18.32). Lever notes this is the same class of bug that was "just fixed in nfsd_vfs_write() and nfsd_commit()" — a reference to Layton's companion patch posted earlier that day, which closes the same verifier-rotation gap on the deferred-writeback error paths in vfs.c.

Why v2?

The v1 of this patch (posted ~50 minutes earlier at 19:44 UTC) drew a quick review question from Layton:

"commit_reset_write_verifier() filters out EAGAIN and ENOSPC. Do we need the same filter here?"

Lever's v2, posted about an hour later, answers that directly in the commit message:

"Filter out -EAGAIN and -ESTALE, matching commit_reset_write_verifier(), since neither indicates a durable-storage failure."

(He also explains why commit_reset_write_verifier() itself can't be reused here — the async COPY worker has no svc_rqst — so the fix calls nfsd_reset_write_verifier() directly, mirroring what nfsd_file_check_write_error() already does for the same purpose.)

The fix

The patch is a two-line change to fs/nfsd/nfs4proc.c, rotating nn->writeverf at the writeback-failure site in _nfsd_copy_file_range(). It carries:

  • Fixes: eac0b17a77fb ("NFSD add vfs_fsync after async copy is done")
  • Cc: stable@vger.kernel.org — i.e., a candidate for backport to stable trees.
  • An unusual Assisted-by: kres:claude-opus-4-7 trailer, which (like the matching kres:claude-opus-4-6 on Layton's companion patch) marks these as AI-assisted kernel submissions — a notable data point in this week's NFS activity.

Outcome

Layton's reply at 20:56 UTC is a clean sign-off:

"Reviewed-by: Jeff Layton jlayton@kernel.org"

No further discussion in this week's window. The thread closes with the patch ready for merge, and it pairs with Layton's nfsd_vfs_write()/nfsd_commit() verifier-rotation fix to close out a family of silent data-loss bugs in nfsd's UNSTABLE+COMMIT handling.
