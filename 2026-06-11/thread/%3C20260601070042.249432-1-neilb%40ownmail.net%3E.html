Chuck Lever finds NFS4ERR_EXIST logic bug in NeilBrown's vfs_lookup_open() series; cleanup of stray fh_drop_write() acknowledged

Summary

Chuck Lever Reviews Patches 16 & 17 of NeilBrown's vfs_lookup_open() Series: Logic Bug and Cleanup

Context (bridging prior week)

Last week, NeilBrown posted an 18-patch RFC series titled "VFS/nfsd: replace dentry_create()", a major VFS and nfsd refactoring that introduces vfs_lookup_open() to consolidate lookup, create, and open into a single call path. The series was motivated by a deadlock NeilBrown discovered in his earlier 53-patch directory-locking RFC when re-exporting NFS filesystems. Jori Koolstra reviewed patches 01–05 (granting three Reviewed-by tags and raising questions on 04 and 05), but the nfsd-specific patches 06–18 had not yet received review.

This week, NFS maintainer Chuck Lever turned his attention to two of those nfsd patches — PATCH 16/18 and PATCH 17/18 — producing a pair of findings that range from a cosmetic cleanup to a genuine protocol-breaking logic bug.

Classification

This is a VFS API refactoring with correctness implications for the NFSv4 server. The patches under review are not new features or protocol changes in themselves; they restructure nfsd's internal open/create path to use the new vfs_lookup_open() interface. However, the logic bug Chuck Lever found would have broken NFSv4 OPEN semantics for a common client operation (CLAIM_NULL opens of existing files), making this effectively a bug-fix review as much as a refactoring review.

This Week's Discussion

1. Stray fh_drop_write() in PATCH 16/18 (cosmetic)

On Friday, June 5, Chuck Lever reviewed PATCH 16/18, which switches nfsd4_create_file() to use vfs_lookup_open(). He spotted an asymmetry in the write-access accounting:

"This fh_want_write() is removed, but ... the 'matching' fh_drop_write remains. Harmless since nothing has set fhp->fh_want_write, but should be cleaned up."

The patch removes the fh_want_write(fhp) call (because vfs_lookup_open() now handles write-access internally) but leaves the corresponding fh_drop_write(fhp) in place. Chuck correctly notes this is harmless — dropping a write access that was never taken is a no-op — but it's dead code that should be removed for cleanliness.

NeilBrown acknowledged the finding on Monday, June 9 with a brief:

"Thanks for catching that!"

This is a straightforward cleanup, not a functional bug.

2. NFS4ERR_EXIST logic bug in PATCH 17/18 (functional)

The more significant finding came in Chuck Lever's review of PATCH 17/18, which extends vfs_lookup_open() usage to non-creating open requests (i.e., plain OPEN operations where the file already exists). Chuck identified a logic error in the refactored do_open_lookup():

"Logic bug: Pre-series, the non-create case takes do_open_lookup()'s else branch and succeeds; post-series, do_open_lookup() calls nfsd4_open_file() unconditionally. Every CLAIM_NULL open of an existing file fails with NFS4ERR_EXIST."

This is a serious protocol-level regression. In NFSv4, NFS4_OPEN_NOCREATE (the "non-creating" open mode) is the standard way clients open files they already know exist — it's the default for most OPEN operations. If every such open returns NFS4ERR_EXIST, effectively all non-creating opens would fail, rendering the server unusable for normal file access. The bug stems from the refactoring making nfsd4_open_file() (which contains create-specific logic including an existence check) run unconditionally, even when no creation was requested.

NeilBrown confirmed the bug on June 9 and proposed a concrete fix:

"yes - that is bad. I think

	if (!open->op_created &&
-	    createmode == NFS4_CREATE_UNCHECKED) {
+	    (open->op_create == NFS4_OPEN_NOCREATE ||
+	     createmode == NFS4_CREATE_UNCHECKED)) {
		/* NFSv4 protocol requires change attributes
		 * even though no change happened.
		 */

is what I wanted to do."

The fix adds open->op_create == NFS4_OPEN_NOCREATE as an additional condition for the non-creating path, so that plain opens of existing files correctly skip the create-specific error handling. NeilBrown also noted a related cleanup:

"I've also move the clearing of ATTR_SIZE down to where we know we did created the file, so no trunc is needed."

This moves the ATTR_SIZE clearing (which effectively performs a truncate-to-zero) from a position where it would run on all opens to one where it only runs when a file was actually created — another correctness improvement that prevents unintended truncation of existing files.

NeilBrown closed with: "Thanks a lot for the review."

Key Technical Arguments

  1. Unconditional call path is dangerous: The core lesson from the PATCH 17/18 bug is that refactoring do_open_lookup() to route all opens through nfsd4_open_file() (which was designed with create semantics in mind) requires careful gating on the open mode. The pre-refactor code had an explicit else branch for non-creating opens; collapsing that into a single path without adjusting the internal conditions silently broke the most common client operation.

  2. Write-access accounting must stay balanced: The PATCH 16/18 finding, while cosmetic, reinforces a general principle in nfsd: fh_want_write() / fh_drop_write() pairs must be kept in lockstep. Removing one side without the other is safe only because the drop is a no-op when nothing was taken — but it's confusing dead code that could mask a future real imbalance.

  3. ATTR_SIZE clearing scope: NeilBrown's additional fix to move ATTR_SIZE clearing down into the create-only path addresses a subtle correctness issue: clearing the size attribute on a non-creating open would truncate an existing file to zero, which is clearly wrong. This was likely another latent consequence of the same "unconditional path" refactoring.

Impact on NFS Clients

While this is server-side code, the implications for NFS clients are direct and severe:

  • CLAIM_NULL opens: The logic bug in PATCH 17/18 would have broken the most common NFSv4 OPEN operation. Any client performing a standard open of an existing file (the default NFS4_OPEN_NOCREATE mode) would have received NFS4ERR_EXIST. This is not an edge case — it is the primary path for file access on NFSv4 servers.
  • File truncation risk: The ATTR_SIZE clearing issue, had it shipped, could have silently truncated files opened without create intent — a data-loss scenario for any client.
  • Re-export correctness: The broader series (from last week) targets deadlock fixes for NFS re-export scenarios. Getting the non-create open path right is essential for the refactoring to be safe in those environments.

Status and Outlook

As of the end of this week's window:

  1. PATCH 16/18: One cosmetic cleanup identified (stray fh_drop_write()), acknowledged by NeilBrown. No functional issues found.
  2. PATCH 17/18: One significant logic bug (NFS4ERR_EXIST on all non-creating opens) identified and confirmed, with a concrete fix proposed by NeilBrown. An additional ATTR_SIZE scoping fix was also noted.
  3. The series remains in RFC stage. Patches 06–15 and 18 have not yet received review from Chuck Lever or other nfsd maintainers.
  4. A revised version of the series is expected, incorporating both fixes.
