nfs: disputed one-line refcount fix in nfs_direct_read_schedule_iovec()

A short, pointed exchange this week on the Linux NFS client list pitted a fresh bug-fix submission against immediate skepticism from the client maintainer. The thread is squarely about NFS client development and specifically a claimed bug fix (reference-counting leak) in the direct-I/O read path — not a new feature or protocol change.

The patch: an alleged io_count refcount leak

WenTao Liang posted a one-line patch titled "nfs: fix refcount leak in nfs_direct_read_schedule_iovec()". His account of the defect is precise about the failure path:

"When nfs_direct_read_schedule_iovec() encounters an error after get_dreq(dreq) increments the io_count but fails to start any I/O (requested_bytes == 0), it falls through to the error path. That path calls nfs_direct_req_release() to drop the I/O path's kref, but it never calls put_dreq() to balance the io_count."

He frames the consequence as a genuine correctness problem rather than a theoretical one:

"This leaves the request's io_count permanently elevated, a reference counting violation that corrupts the teardown logic once the object is freed via the remaining kref."

The proposed remedy is minimal and surgical — insert put_dreq(dreq) before nfs_direct_req_release() in the zero-bytes error path so the counter is "properly balanced" (1 file changed, 1 insertion). The submission carries a Cc: stable@vger.kernel.org tag and a Fixes: pointer back to commit 65caafd0d214, itself a revert of an earlier NFSv4 CLOSE/direct-IO completion fix — signaling that the author sees this as a regression in already-stable behavior.

The maintainer's pushback: "I'm not seeing" the corruption

Trond Myklebust, the Linux NFS client maintainer, replied within roughly two hours with a direct challenge to the core of the argument. Rather than objecting to the patch's mechanics, he questioned whether the claimed harm actually materializes:

"Exactly how is this corruption supposed to happen? I'm not seeing anything that cares about the value of io_count either in nfs_file_direct_read or in nfs_direct_req_free."

This is a substantive technical objection: if neither the direct-read entry point nor the request-free path consults io_count, then an unbalanced counter may be a bookkeeping blemish rather than the "corruption" the cover letter describes. The maintainer effectively asks for a concrete trace of how the elevated count leads to observable misbehavior before the fix can be justified on its stated grounds.

State of play and outlook

The discussion is in its earliest stage — two messages, both dated 2026-06-11, with no resolution yet. The key open question is whether Liang can demonstrate a real teardown failure caused by the unbalanced io_count, or whether the fix should be recharacterized (or dropped) as a defensive balancing change without a demonstrated bug. Given the Cc: stable and Fixes: tags, the stakes are that this could land in stable trees; Trond's skepticism is the kind of gate that typically forces the author to either produce a reproducer/impact analysis or rework the rationale. Watch for a follow-up from Liang defending the corruption claim, or a softened v2.
