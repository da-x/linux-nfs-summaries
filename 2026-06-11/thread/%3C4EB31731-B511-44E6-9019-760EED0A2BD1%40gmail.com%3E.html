[BUG] KASAN slab-use-after-free in xprt_put (new report, no reply yet)

Summary

[BUG] KASAN: slab-use-after-free in xprt_put — new client-side race report

Status this week: A single, unreplied bug report opened the thread. No maintainer or developer has responded within the 2026-06-05 → 2026-06-12 window, so there is no discussion evolution to track yet — just the initial report and its KASAN trace.

What was reported

Shuangpeng Bai opened the thread on 2026-06-07 with a KASAN slab-use-after-free hit in the SunRPC transport layer while testing current upstream:

"I hit the following KASAN report while testing current upstream kernel: KASAN: slab-use-after-free in xprt_put on commit: e8c2f9fdadee7cbc75134dc463c1e0d856d6e5c7 (May 25 2026)"

This is squarely an NFS client bug fix matter — the fault lives in net/sunrpc/xprt.c and net/sunrpc/clnt.c, the shared SunRPC client machinery that underpins NFS. It is not a protocol change or new feature; it is a lifetime/reference-counting defect on the transport object.

The technical core of the trace

The crash is a write of size 4 to an already-freed 2048-byte kmalloc-2k slab object, attributed to the rpc_free_client_work workqueue:

"BUG: KASAN: slab-use-after-free in xprt_put … Write of size 4 at addr ffff8881092e1000 by task kworker/1:0/24" "Workqueue: events rpc_free_client_work"

The call path is short and telling:

xprt_put (net/sunrpc/xprt.c:2195)
rpc_free_client_work (net/sunrpc/clnt.c:991)
process_scheduled_works / worker_thread / kthread

xprt_put() drops the transport's kref, and that final put lands on a transport whose slab object had already been reclaimed. The free side is an RCU-deferred slab release, which is the key to reading this as a race between RCU-delayed freeing and a late reference drop:

"Freed by task 0 on cpu 1 at 165.626544s: … __rcu_free_sheaf_prepare → rcu_free_sheaf → rcu_core" "The buggy address is located 0 bytes inside of freed 2048-byte region [ffff8881092e1000, ffff8881092e1800)"

In other words, the transport object was released through the RCU grace-period path (~5 seconds before the fault), and a subsequent xprt_put() from the client-teardown work item then wrote into that freed memory. The likely shape of the bug is a missing/early reference or an ordering problem between RCU-deferred transport destruction and the rpc_free_client_work teardown sequence — i.e., a use-after-free in the NFS/SunRPC client transport lifecycle.

Reproduction & cooperation offered

The reporter made it easy to act on, providing a minimal diagnostic patch (delays + prints only) to make the race reproducible, plus a reproducer and .config:

"To help trigger the bug more reliably, we applied a minimal diagnostic patch that only adds delays and print statements. The reproducer and .config files are here." "I'm happy to test debug patches or provide additional information."

Reproducer/config: https://gist.github.com/shuangpengbai/98a27c1e3c0dc5489f117efa7c254593 — reported on QEMU (Ubuntu 24.04 guest, i440FX), so it is a plain software race rather than hardware-specific.

Where things stand / what to watch for

  • No fix or analysis posted yet in this window; the thread is awaiting maintainer triage from the SunRPC/NFS client maintainers.
  • The interesting follow-up will be whether the root cause is (a) an RCU-grace-period vs. workqueue ordering gap, or (b) a missing reference keeping the transport alive across rpc_free_client_work.
  • Worth cross-referencing with prior KASAN UAF reports in the same area (e.g., earlier nfs_local_call_* slab-use-after-free reports and svcrdma lifecycle fixes), which suggest this corner of RPC object teardown has been a recurring trouble spot.

Bottom line: A fresh, well-documented NFS/SunRPC client-side use-after-free in the transport reference-counting path (xprt_put via rpc_free_client_work), with a reliable reproducer offered — but no technical discussion or patch had landed by the end of this week.
