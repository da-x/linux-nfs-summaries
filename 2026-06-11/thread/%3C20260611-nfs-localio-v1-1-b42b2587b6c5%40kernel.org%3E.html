Jeff Layton sends the client-side localio ref-leak fix separately to the NFS client tree

Summary

Jeff Layton spins off the client-side localio ref-leak fix as a standalone patch

Context: this is the split-out of PATCH 01/19 from Layton's "nfsd: more bugfixes" series

This thread consists of a single message posted on Thursday, June 11: Jeff Layton's standalone patch titled "nfs/localio: fix nfsd_file ref leak on nfs_local_doio() init failure." It is the direct follow-through from a routing decision made two days earlier in Layton's 19-patch "nfsd: more bugfixes" v1 series, where this same fix arrived as PATCH 01/19.

In that earlier thread, NFS maintainer Chuck Lever flagged the patch's client-side provenance:

"This updates only a client-side source file. Should it go through Anna/Trond's trees? Or were you thinking that, since the leak impacts only NFS server behavior, I should take it?"

Layton agreed to route it through the client tree, and on June 11 he did exactly that — both sending this standalone patch here and resending his series as a 21-patch v2 with the localio fix dropped, explaining: "I also dropped the localio patch from the series since that should probably go through the NFS client tree. I'll send it separately."

What the bug is

This is a bug fix — specifically a reference-count leak in the client-side LOCALIO path (fs/nfs/localio.c), not a new feature or protocol change. Layton's commit message identifies two early-return paths in nfs_local_doio() that fail to release the nfsd_file (localio) reference passed in by the caller:

"Two early return paths in nfs_local_doio() fail to release the localio (nfsd_file) reference passed in by the caller"

The two leaking paths are:

  1. Zero-count fast path — when hdr->args.count is zero, the function returns 0 without calling nfs_local_file_put().
  2. nfs_local_iocb_init() failure — on errors like -ENOMEM from allocation or -EOPNOTSUPP if the file lacks read_iter/write_iter, the function returns the error "without releasing localio or completing the hdr lifecycle."

The consequences are significant for both namespace and mount teardown:

"A leaked nfsd_file pins the associated net namespace reference, blocking network namespace teardown, and holds a reference on the exported filesystem, preventing unmount."

The fix

The patch is small — 13 insertions and 3 deletions in fs/nfs/localio.c. Per Layton's description:

"Fix the zero-count path by adding the missing nfs_local_file_put() call. Fix the iocb init failure path by jumping to a new cleanup label that releases localio, sets hdr->task.tk_status, and calls nfs_local_hdr_release() -- matching the existing error handling pattern for the post-iocb error path."

The Fixes: tag points at e77c464c31b3 ("nfs/nfsd: add 'local io' support"), though in the v1 thread Chuck Lever noted that he didn't have that commit in his tree and suggested 70ba381e1a43 ("nfs: add LOCALIO support") instead. Layton confirmed: "Yeah, that introduced the first of the leaks, I think." The standalone patch as posted here still carries the original Fixes: e77c464c31b3 tag.

Provenance and status

Like the rest of Layton's recent bugfix work, this patch carries an Assisted-by: Claude:claude-opus-4-8 tag — part of a broader pattern of LLM-assisted kernel auditing producing real fixes on linux-nfs. The cover note is candid about its origin:

"I had originally sent this as part of a pile of nfsd patches, but Chuck pointed out that this was client side."

As of the end of this week's window (2026-06-11), the patch has just been posted and no replies from Anna Schumaker or Trond Myklebust have yet landed. It is awaiting review in the NFS client tree for v7.3.
