svcrdma GFP_NOWAIT Fix for Read Sink Buffers: Tested and Found Insufficient

Summary

svcrdma GFP_NOWAIT Fix for Read Sink Buffers: Tested and Found Insufficient

Classification: Bug fix / performance regression (server-side svcrdma over NFS-over-RDMA)

Overview

This thread is a short, focused exchange — three messages in under an hour on June 5 — representing Chuck Lever's first targeted fix attempt for the svcrdma contiguous-page allocation regression reported by Mike Snitzer and Hammerspace. The patch was posted, tested rapidly by Jonathan Flynn at Hammerspace, and found insufficient, narrowing the debugging focus to the buddy allocator's higher-order path itself.

Background (Bridge from Prior Weeks)

The root cause traces back to commit 18755b8c2f24 ("svcrdma: Use contiguous pages for RDMA Read sink buffers"), merged in 7.1, which reduced DMA mappings from 16 to 1 for 64 KB READ payloads by allocating physically contiguous page sets. In early June, Mike Snitzer reported a ~60% WRITE throughput regression (24.2 GB/s vs 60.6 GB/s) on high-end RDMA hardware, with spinlock contention in the buddy allocator dominating flamegraphs. Jonathan Flynn from Hammerspace then provided detailed profiling data confirming that svc_rdma_build_read_segment_contig() → alloc_pages_noprof() → rmqueue_buddy() was the dominant cost path.

This Week's Activity (June 5)

Chuck Lever Posts the Fix

Within minutes of Flynn's profiling data, Chuck Lever posted a targeted patch svcrdma: Avoid direct reclaim when allocating Read sink buffers. The technical argument was precise:

"svc_rdma_alloc_read_pages() passes __GFP_NORETRY, which limits the allocator to a single round of direct reclaim and asynchronous compaction per attempt. Under memory pressure or fragmentation that round can take a long time, and the fallback loop repeats it at each order, multiplying the stall while the RPC waits for its Read sink buffer."

The fix replaced __GFP_NORETRY with GFP_NOWAIT, on the reasoning that:

"The contiguous allocation is opportunistic: when it fails, Read sink buffers come from the pages already in rq_pages[]. Direct reclaim effort buys little here. Allocate with GFP_NOWAIT instead, which omits __GFP_DIRECT_RECLAIM so the allocator takes pages only from the free lists and returns NULL immediately when none are available."

Lever noted that GFP_NOWAIT retains __GFP_KSWAPD_RECLAIM, so a failed attempt still wakes kswapd to replenish higher-order pages in the background. He drew a parallel to existing kernel code: "skb_page_frag_refill() takes the same approach for its opportunistic high-order allocation."

He was notably candid about his uncertainty:

"Given the perf symbol resolution inaccuracies I can't swear this will fix the issue, but here's a stab at it."

The patch carried a Fixes: tag pointing to the original commit and a Reported-by: for Jonathan Flynn.

Flynn Acknowledges and Commits to Testing

Flynn replied within eight minutes:

"Thanks Chuck, give me a few to test it out!"

Flynn's Negative Result (42 Minutes Later)

Flynn's follow-up, delivered just 42 minutes after the patch was posted, was a clear negative:

"Unfortunately, the GFP_NOWAIT change did not materially affect either throughput or the perf profile. The allocator-heavy stack rooted at svc_rdma_build_read_segment_contig() remains dominant, with alloc_pages_noprof() and rmqueue_buddy() continuing to account for a significant portion of the samples, similar to the original regressed build."

Flynn shared updated fio results, perf reports, and a flamegraph in a gfp-nowait directory on his OneDrive link, and also added a flamegraph for the original regressed configuration at rpcrdma-regression/regressed/phase2/server.

Key Technical Takeaways

  1. Direct reclaim is not the bottleneck. The GFP_NOWAIT experiment definitively ruled out direct reclaim as the primary source of the stall. The problem lies deeper in the buddy allocator's higher-order allocation path — specifically rmqueue_buddy() spinlock contention inherent to requesting large contiguous pages under high concurrency.

  2. The fix will need a structural change. Since adjusting GFP flags does not help, the eventual solution likely requires one of: per-CPU pre-allocated contiguous buffer pools, a slab-style allocator for fixed-size RDMA sink buffers, reducing the allocation order, or a fundamentally different approach to providing contiguous memory for RDMA READ operations.

  3. Rapid test-and-iterate cycle. The entire patch → test → negative-result cycle completed in under an hour (22:31 UTC to 23:13 UTC), reflecting the tight collaboration between Hammerspace's production-grade test infrastructure and Oracle's NFS development team.

Current Status

The thread is effectively closed with a negative result. The debugging has narrowed considerably, and the next iteration of the fix will need to address the fundamental allocation strategy rather than GFP flag tuning. The Fixes: tag confirms this is being tracked as a regression for stable backporting if not resolved before the next RC.
