NFS direct-write refcount leak patch questioned by maintainer

Summary

NFS: fix refcount leak in nfs_direct_write_schedule_iovec() — disputed one-liner

Type: Bug fix (claimed) — a single-line change to fs/nfs/direct.c on the NFS client side, flagged for stable. The thread is short (two messages, both on 2026-06-11) and ends with the maintainer pushing back rather than applying it.

The patch

WenTao Liang posted a one-line fix to nfs_direct_write_schedule_iovec(), arguing that the early-exit path leaks a reference on the direct-write request:

"When nfs_direct_write_schedule_iovec() fails to start any write operations (requested_bytes == 0), it bails out after calling inode_dio_end() but before releasing the dreq->io_count reference that was unconditionally acquired by get_dreq(). The normal success path balances that via put_dreq(), which decrements the io_count and eventually calls nfs_direct_write_complete(). The leaked reference prevents proper cleanup of the direct write request."

The fix adds a missing put_dreq() in the early-exit path before calling nfs_direct_req_release(). It carries a Fixes: tag pointing at 65caafd0d214 ("SUNRPC reverting d03727b248d0 ('NFSv4 fix CLOSE not waiting for direct IO compeletion')") and is Cc'd to stable, so Liang is positioning this as a real regression in the client's O_DIRECT write path.

The maintainer's pushback

Trond Myklebust, the Linux NFS client maintainer, replied within ~2.5 hours and did not accept the rationale:

"Again, I'd like you to explain this claim that somehow io_count is preventing cleanup of the request. Neither nfs_file_direct_write nor nfs_direct_req_release care about its value."

The word "Again" signals this isn't Liang's first patch in this vein — Myklebust has apparently asked for a concrete explanation of the user-visible symptom (leak, hang, CLOSE not waiting) before, and is asking again here. The maintainer's point is technical and specific: if neither nfs_file_direct_write nor nfs_direct_req_release actually inspects io_count, then an unbalanced reference on that counter may be a bookkeeping asymmetry rather than a functional bug — i.e., the patch might be cosmetically balancing a refcount without fixing any observable defect.

State of play

  • No resolution this week. The thread is at two messages and waiting on Liang to either (a) demonstrate a concrete failure mode tied to the leaked io_count (e.g., a CLOSE that doesn't wait for direct IO, a memory leak, or a use-after-free) or (b) drop the patch.
  • Not applied. No Reviewed-by, no Applied, and no v2 as of the window close on 2026-06-12.
  • Context: This lands in a week otherwise dominated by server-side work (nfsd testing, localio, directory delegation series), so client-side direct-write plumbing is getting comparatively little attention — but Myklebust's prompt reply shows he is actively policing the direct-IO refcounting code, which has been a churny area since the 65caafd0d214 revert.

Takeaway for readers

A one-line "obvious" refcount fix on a stable-tagged path is not enough to clear the bar in this subsystem: the maintainer wants the symptom tied to the counter, not just an unbalanced get_/put_ pair. Watch for a v2 from Liang with a reproducer or KASAN/syzkaller trace, or a quiet death of the patch.
