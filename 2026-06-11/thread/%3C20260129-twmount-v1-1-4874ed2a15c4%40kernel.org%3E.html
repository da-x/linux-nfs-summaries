FS_USERNS_DELEGATABLE: NFS Container Mount Fix Still Missing from Mainline — Jeff Layton Pings VFS Maintainer

FS_USERNS_DELEGATABLE: NFS Container Mount Fix Still Missing from Mainline

Classification

Type: Bug fix (regression in containerized NFS mounting) — patch applied to a VFS tree branch but never merged into a stable release.

Summary

This week's activity on this long-running thread is brief but significant: Jeff Layton sent two pings (June 8 and June 9) drawing attention to the fact that his FS_USERNS_DELEGATABLE patch — which was confirmed as "applied" back in February — apparently never made it into linux-next or any released kernel. The NFS client fix for containerized mount daemons remains unshipped more than four months after initial submission.

Background (Bridged from Prior Weeks)

The thread began on January 29 when Jeff Layton submitted a patch introducing the FS_USERNS_DELEGATABLE VFS flag to fix a regression caused by commit e1c5ae59c0f2 ("fs: don't allow non-init s_user_ns for filesystems without FS_USERNS_MOUNT"). That VFS security hardening broke NFS mounts in containerized environments that use privileged mount daemons — where a process inside a container calls fsopen() and passes the filesystem context to a vetted daemon in the init namespace via Unix socket.

"This broke NFS mounts in our containerized environment. We have a daemon somewhat like systemd-mountfsd running in the init_ns. A process does a fsopen() inside the container and passes it to the daemon via unix socket." Jeff Layton

On February 3, VFS maintainer Christian Brauner confirmed the patch was applied to the vfs-7.0.misc branch, and Anna Schumaker provided an Acked-by. A follow-up proposal to apply the same mechanism to BPFFS was also discussed.

This Week's Activity (June 8–9)

First Ping: General Nudge Toward v7.3

On June 8, Jeff Layton replied directly to his own original patch submission, opening with a simple:

"Ping?"

He then flagged the core problem and raised a new technical complication:

"I just realized that this patch never made it into -next or a release. Any chance we can get this into the coming v7.3 merge window? (although it looks like we'll need to renumber the bit since FS_USERNS_MOUNT_RESTRICTED has gone in since then."

This message reveals two important points:

  1. The patch was lost in transit — despite being marked "applied" to a VFS tree branch in February, it never propagated to linux-next or any stable release. This is an unusual and concerning gap in the kernel development pipeline.
  2. A renumbering conflict has emerged — the FS_USERNS_MOUNT_RESTRICTED flag was added to the VFS since the original patch, meaning the bit position for FS_USERNS_DELEGATABLE must be adjusted before it can be merged. This is a straightforward but necessary technical fix.

Second Ping: Targeted Follow-Up to Brauner

The very next day (June 9), Jeff sent a more targeted message replying directly to Christian Brauner's February 3 "applied" confirmation:

"I sent something yesterday, but I'm not sure you saw it. This patch never made it into v7.0 for some reason. Any chance we could get it in for v7.2?"

This follow-up is notable for a few reasons:

  • Jeff explicitly references his prior-day ping, showing he was worried the first message might have been missed.
  • The target version shifted from v7.3 (in the June 8 message) to v7.2 (in the June 9 message), suggesting either a correction or that Jeff was responding to the specific context of Brauner's February 3 message, which referenced the vfs-7.0.misc branch and linux-next timing.
  • The phrase "for some reason" carries a tone of mild frustration — the patch was confirmed applied four months ago, yet it simply vanished from the pipeline.

Key Technical Arguments

  1. Pipeline failure, not technical disagreement: Unlike many kernel threads where patches stall due to design disputes, this thread's delay appears to be an administrative/merge-window issue. The patch was reviewed, acked by the NFS maintainer, and confirmed applied — yet never reached a release.

  2. Bit renumbering required: The introduction of FS_USERNS_MOUNT_RESTRICTED into the VFS flag space since January means the original bit assignment for FS_USERNS_DELEGATABLE is now occupied or shifted. Jeff correctly identified this: "it looks like we'll need to renumber the bit." This is a minor but necessary code change before the patch can be cleanly merged.

  3. Security model remains sound: The core design — using FS_USERNS_DELEGATABLE as a middle ground between full unprivileged mounting (FS_USERNS_MOUNT) and no user-namespace mounting at all — was never challenged. The flag allows mounts from non-init user namespaces only when a privileged daemon is acting on behalf of the container, preserving the security boundary.

Final Conclusions (as of this week)

  • No response from Christian Brauner or any other VFS maintainer has been posted in this week's window. Both pings remain unanswered as of the summary cutoff.
  • The patch is still needed for the v7.2 or v7.3 merge window (Jeff's two messages reference different targets).
  • A bit renumbering fix will be required before resubmission.
  • The underlying NFS client bug — containerized mount daemons being unable to perform NFS mounts after the e1c5ae59c0f2 VFS change — remains unfixed in all released kernels.

Significance for NFS Client Development

This thread highlights a critical gap in the kernel merge pipeline: a well-reviewed, maintainer-acked bug fix for a real-world containerized NFS deployment pattern has been stuck for over four months. Organizations running containerized workloads with delegated NFS mount daemons are still affected by the regression. The fix is technically simple (a new VFS flag plus a small change to NFS's filesystem context code), and the only remaining work is administrative — getting it through the merge window with the necessary bit renumbering.
