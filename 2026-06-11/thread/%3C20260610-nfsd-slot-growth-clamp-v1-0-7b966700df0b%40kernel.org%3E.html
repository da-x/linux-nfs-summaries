NFSv4.1 slot-growth clamp RFC: capping DRC slot growth at the thread ceiling

Summary

NFSv4.1 slot-growth clamp: a 5-patch RFC to stop rewarding busy clients

What landed this week

On June 11, Chuck Lever posted a five-patch RFC titled "Stop NFSv4.1 slot-growth heuristic from rewarding busy clients." The series is a direct spin-off of Ben Coddington's per-client fair-queue dispatch RFC and the discussion it triggered with Neil Brown over the prior week — but it deliberately carves out a piece that "holds no matter which design wins."

The core problem, as Lever frames it in the cover letter:

"a single busy NFSv4.1 client, opening many connections against a large slot table, can keep enough requests in flight to monopolize the nfsd thread pool and starve its peers"

And the specific defect this series targets:

"nfsd4_sequence() grows a session's slot table by 20% every time the client reaches its highest slot, so it hands the client already keeping the most threads busy a still larger table; one session can climb toward 2048 slots on a server with far fewer threads to run them."

This is a bug fix / heuristic correction rather than a new feature or protocol change. Lever is explicit that it "removes a perverse incentive" and is "not slot admission control." The dynamic-slot machinery stays intact; the series only caps on-demand growth at the point where added slots stop buying concurrency.

The five patches

The series splits into three categories — plumbing, accounting cleanup, and the actual fix:

1. SUNRPC: Add svc_serv_maxthreads() — a new lock-free accessor that sums sp_nrthrmax across every pool, exposing the service's stable thread ceiling (as opposed to the running count, which "reflects recent demand, not the service's capacity"). Lever converts the existing hand-rolled sum in nfsd_nrthreads() to use it, giving the export an in-tree consumer and removing a duplicate dependency on svc_serv internals.

2. NFSD: Count slot 0 in nfsd_total_target_slots — an accounting cleanup. The counter previously summed target_slots - 1 across sessions, with the "minus slot 0" correction open-coded at every alloc/free site. Lever relocates that correction to the single consumer (the shrinker's count callback), giving nfsd_total_target_slots "the full-target meaning its name implies."

3. NFSD: Clean up documenting comment for reduce_session_slots() — typo fixes and dropping kdoc-style on a static function.

4. NFSD: Document and rename the NFSv4.1 session slot shrinker callbacks — renames the shrinker callback functions to prevent reuse by generic code and adds kdoc documenting their API contracts.

5. NFSD: Bound on-demand DRC slot growth by the thread ceiling — the actual fix, capping nfsd4_sequence()'s 20% growth at svc_serv_maxthreads().

Key technical arguments

Lever's cover letter makes two design points "worth checking against the diffs," and patch 5/5 elaborates both:

Per-session cap, not per-namespace. A shared budget across a namespace's sessions "breaks at the floor": every active session permanently holds slot 0 (never reclaimable), so once the session count alone reaches the thread ceiling, those floors exhaust a shared budget and end up "pinning the one busy client small while the pool sits idle." Since "a session cannot use another's slots," capping each independently is "the natural choice."

The ceiling is sunrpc-owned, and it's the configured max, not the live count. Maximum sustainable concurrency is a property of svc_serv/svc_pool, so the accessor lives in sunrpc. Crucially, Lever compares against the configured maximum rather than the running thread count:

"nfsd sizes its pool dynamically, and gating on the live count would deny a client resuming from idle the slots it needs before the pool scales back up."

The RTT rationale. The cap is justified by the observation that a slot "ties up an nfsd thread only during the processing," not for the whole round trip. On a short round trip, "one slot per thread keeps the pool busy and further slots add only backlog." Lever concedes that across a high-RTT link extra slots do raise throughput by masking latency — but argues that is "the client's call to make by sizing its session at CREATE_SESSION, not a reason for the server to grow every busy session toward 2048."

The review: fast and favorable

The discussion this week was brisk and consensus-driven, with two reviewers weighing in within hours of the posting.

Neil Brown reviewed patches 2/5 and 4/5. On patch 2/5 he caught a leftover inconsistency — Lever had described the old from ?: 1 ternary as "an unexplained fudge," yet left an unexplained one in the new code:

"You reasonably describe 'from ?: 1' as an unexplained fudge ... yet here it still is with no explanation :-)"

He nonetheless approved it: "But that is a minor detail and I do like the patch. Reviewed-by: NeilBrown." On patch 4/5 he suggested adding a note that slot zero is not reclaimable so the nfsd_total_sessions subtraction reads clearly, then extended his sign-off across the board:

"and you can add that to all patches in series. A definite improvement!"

Jeff Layton reviewed the whole series and endorsed it, picking up Neil Brown's nit about the ternary assignment:

"This makes a lot of sense. It'd be nice to clean up or comment the nit Neil pointed out with the ternary assignment, but otherwise you can add: Reviewed-by: Jeff Layton"

Chuck Lever closed the loop, committing to address both reviewers' specific comments before merging:

"Thanks for the look. I'll address your specific comments before applying these to nfsd-testing."

Nature and significance

This is a bug fix / heuristic correction in the NFSv4.1 server (nfsd) slot-accounting path, not a protocol change or new feature. It corrects an incentive that runs backwards: the client already saturating the thread pool was being rewarded with a larger slot table. The fix caps on-demand DRC slot growth at the sunrpc-reported thread ceiling, per session.

For NFS client developers, the practical takeaway is about fairness and predictable behavior rather than any client-side change:

  • No protocol or client-side negotiation changes — clients still size their sessions directly at CREATE_SESSION (bounded by NFSD_MAX_SLOTS_PER_SESSION), so existing client behavior is unaffected.
  • A greedy NFSv4.1 client can no longer inflate its session table toward 2048 slots on a server with far fewer threads, reducing the chance that one busy client monopolizes the pool and starves peers — the exact starvation scenario Coddington's fair-queueing RFC targets at the dispatch layer.
  • Lever is careful to scope this: "Enforcing per-client fairness against thread starvation belongs in the dispatch layer, not in slot accounting." This series removes the server-side amplifier; the larger fair-queueing discussion continues separately.

Final conclusions

By end of day June 11 the RFC had collected Reviewed-by tags from both Neil Brown and Jeff Layton, with only minor comment-level nits outstanding (the unexplained from ?: 1 ternary, and a suggested kdoc note about slot-zero non-reclaimability). Lever committed to address those before applying the series to nfsd-testing. The design — per-session cap against the configured sunrpc thread ceiling, leaving dynamic slots otherwise intact — was accepted without substantive objection.
