nfs: fix refcount leak in nfs_swap_activate()

Summary

NFS client: refcount leak fix in swap activation path

Overview

A single-patch bug-fix submission landed on the linux-nfs list this week from WenTao Liang (Institute of Computing Technology, Chinese Academy of Sciences), targeting a reference-counting leak in the NFS/SUNRPC swap-activation code path. The thread is still at its opening message with no replies as of the end of the reporting window.

The Bug

The issue sits in rpc_clnt_swap_activate() in net/sunrpc/clnt.c. As Liang describes in the patch cover letter:

"nfs_swap_activate() calls rpc_clnt_swap_activate(), which unconditionally increments the cl_swapper refcount via atomic_inc_return(). If the subsequent call to rpc_clnt_iterate_for_each_xprt() fails (e.g. the callback xprt_enable_swap() returns an error), rpc_clnt_swap_activate() returns the error without decrementing the refcount."

The consequence is that a failed swap activation permanently leaks one reference on the RPC client's cl_swapper counter, preventing the client from ever being cleanly destroyed. The leak was introduced by commit 15001e5a7e1e ("SUNRPC: Make NFS swap work with multipath"), which added the per-transport iteration logic.

The Fix

The patch is minimal—6 insertions, 2 deletions in a single file—and adds an atomic_dec() on the error path of rpc_clnt_swap_activate() before the error code is propagated back to nfs_swap_activate(). Liang's summary of the remedy:

"Fix this by adding an atomic_dec() in the error path of rpc_clnt_swap_activate() before returning the error code, so that a failed activation properly cleans up the refcount."

The patch carries a Cc: stable@vger.kernel.org tag and a Fixes: pointer, signalling the author's intent for backporting to stable trees.

Significance for NFS Client Development

Swap-over-NFS is a critical production feature (e.g., for database workloads that must not lose swap pages to a network timeout), so correctness in the activation/deactivation path matters for reliability. A leaked refcount here would manifest as a hung or un-destroyable RPC client after a transient transport failure during swap setup—a subtle, hard-to-diagnose resource leak. The fix is low-risk and surgical, touching only the error-handling branch without altering the success path.

Status

As of the close of this reporting week (2026-06-11), the patch has been posted but no maintainer review or ACK has appeared in the thread. Given its small scope and clear Fixes: tag, it is a strong candidate for quick acceptance in the next merge window or stable update cycle.
