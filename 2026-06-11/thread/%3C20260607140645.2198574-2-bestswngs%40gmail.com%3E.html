SUNRPC: NULL-check fix for rpc_sockaddr2uaddr() in rpcb_register_inet4/6

Summary

SUNRPC: check rpc_sockaddr2uaddr() return value in rpcb_register_inet4/6

This week brought a small but significant bug fix to the Linux NFS/SUNRPC client stack, addressing an unchecked NULL pointer that could crash the kernel when an in-kernel RPC service registers with the local rpcbind under memory pressure.

The Bug

Weiming Shi submitted a patch on June 7 fixing a NULL pointer dereference in the RPC client's registration path. The issue: rpcb_register_inet4() and rpcb_register_inet6() store the result of rpc_sockaddr2uaddr() into map->r_addr without checking whether it returned NULL.

"rpc_sockaddr2uaddr() returns NULL when its final kstrdup() fails, and the unchecked NULL is then carried into the synchronous RPCBPROC_SET encode path: rpcb_register_call() -> rpc_call_sync() -> rpcb_enc_getaddr() -> encode_rpcb_string(), whose first statement is strlen(string), dereferencing NULL and oopsing the kernel."

The crash was reproduced under failslab on v6.12, with KASAN confirming a general protection fault at address zero in strlen() (via encode_rpcb_string). The full call trace shows the path from nfsctl_transaction_write through svc_addsock, svc_register, and into the RPC encode machinery — meaning any in-kernel service (nfsd, lockd, nfs-callback) registering with local rpcbind is vulnerable.

The Fix

The fix mirrors existing error handling already present in the asynchronous getport path:

"The asynchronous getport path already handles this exact failure mode by returning -ENOMEM; only the two register helpers omit the check."

The patch adds a NULL check after rpc_sockaddr2uaddr() in both rpcb_register_inet4() and rpcb_register_inet6(), bailing out with -ENOMEM before the address is fed into the encoder. It's a minimal 4-line addition to net/sunrpc/rpcb_clnt.c.

The patch carries:

  • Reported-by: Xiang Mei xmei5@asu.edu
  • Assisted-by: Claude:claude-opus-4-8

Review and Conclusion

NFS maintainer Jeff Layton reviewed the patch on June 8, quoting the key portion of the diff and issuing a straightforward:

"Reviewed-by: Jeff Layton jlayton@kernel.org"

The thread is effectively concluded with this review. The fix is clean, minimal, and follows the established error-handling pattern in the same file — a textbook example of a small but important robustness improvement to the NFS client's RPC registration infrastructure.
