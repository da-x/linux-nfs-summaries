TLS session tags for NFSD: v1 posted, review on netlink shape and tagset data structure

Summary

TLS session tags delivered to NFSD — v1 series under review

What was posted this week

On Friday, Chuck Lever posted PATCH 0/9 "Deliver TLS session tags to upper-layer consumers (NFSD)", a nine-patch series that lets the userspace handshake agent (tlshd) evaluate TLS client certificates against admin-defined policy and hand back opaque string tags, which NFSD then uses for per-export access control. The series spans net/handshake/, lib/ (a new generic container), SUNRPC, and fs/nfsd/, touching 29 files with roughly 1,205 insertions.

This is primarily a new feature (certificate-based, tag-driven export authorization for NFSD over mTLS), but it also carries a bug fix at the head of the series: patch 1 closes a pre-existing privilege-check gap in the handshake DONE netlink command, with a Fixes: tag pointing at the original NETLINK service commit.

Chuck's cover letter frames four architectural choices, two of which are worth quoting for context:

"The tagging vocabulary is opaque to the kernel. tlshd decides what each tag means; the handshake layer and its consumers only test membership. This keeps x.509 out of the kernel and lets policy evolve at userspace speed."

"DONE gains a privilege check (patch 1) as a prerequisite, not as cleanup. Without it, an unprivileged process guessing a sockfd could submit a forged DONE and effectively grant or deny tag membership for a real handshake."

The bug fix: DONE missing GENL_ADMIN_PERM

PATCH 1/9 notes that ACCEPT already requires GENL_ADMIN_PERM but DONE has no privilege check at all — the fd lookup only confirms a pending request exists, it does not authenticate the sender. Chuck describes the exposure precisely:

"An unprivileged process that guesses or observes a valid sockfd can therefore submit a DONE with HANDSHAKE_A_DONE_STATUS == 0, leaving the kernel consumer to proceed as if the handshake succeeded."

The fix is two lines (adding the admin-perm check) plus a yaml spec update. Jeff Layton reviewed it quickly on Saturday:

"Seems like this ought to go in ahead of the rest of the set? tlshd generally runs as root anyway so I don't forsee a problem just doing this: Reviewed-by: Jeff Layton" Layton's reply.

Hannes Reinecke followed up on Monday with a matching Reviewed-by. So patch 1 is effectively ready to land independently of the rest.

The feature: plumbing tags from tlshd to NFSD exports

The series' design, in brief:

  • PATCH 2/9 adds the HANDSHAKE_A_DONE_TAG netlink attribute so tlshd can return a tag list on a successful handshake. Chuck's motivating example: restrict an export to clients whose certificate Issuer contains "O=Oracle" — tlshd parses the cert, assigns an "oraclegroup" tag, and NFSD simply tests membership. "NFSD needs no knowledge of x.509 certificates."
  • PATCH 3/9 introduces a generic tagset library (sorted array of string pointers) with O(N+M) merge-based intersection, split out so NFSD can reuse it without churn in net/handshake/.
  • PATCH 4/9 collects tags from the DONE downcall and publishes them to the consumer's completion callback. Because the genl family runs DONE with parallel_ops, Chuck splits handshake_complete() into a try/finish pair so exactly one concurrent DONE wins the gate; duplicates get -EBUSY. Over-cap tag lists are truncated with a single pr_warn_once rather than failing the handshake — "tearing down a handshake the operator almost certainly wants to keep is a worse outcome than dropping a few tags."
  • PATCH 5/9 adds a kunit test for that completion-gate idempotency.
  • PATCH 6/9 advertises HANDSHAKE_MAX_SESSIONTAGS as HANDSHAKE_A_ACCEPT_MAX_TAGS on every ACCEPT reply so tlshd can size its tag list against the kernel's runtime limit.
  • PATCH 7/9 is the SUNRPC piece: save the tags in svc_xprt, and harden against a second handshake on the same transport clobbering tags other workers are reading — svcauth_tls_accept() now refuses AUTH_TLS on a transport that already carries a TLS session, and svc_tcp_handshake() rechecks the session flag under XPT_BUSY.
  • PATCH 8/9 implements NFSD export tagging: exports with an allow_tags list grant access only when the mTLS session carries at least one matching tag; untagged exports keep existing behavior. The combination is validated — "svc_export_parse() rejects an allow_tags list paired with any other xprtsec mode, making the administrator state the combination explicitly rather than allowing a default xprtsec setting to silently expose the export."
  • PATCH 9/9 adds allow_tags to the netlink svc-export interface, closing a gap where "nfsd_nl_parse_one_export() always left ex_allow_tags empty, and check_xprtsec_policy() then granted any authenticated peer."

Review discussion: netlink shape and the tagset container

Jeff Layton raised a process issue on Saturday — he could not get the series to apply cleanly and asked what tree it was based on in his cover-letter reply. Chuck answered that the base commit was from a long-lived testing branch, with the candid admission:

"That's some old shit. I will rebase it before posting it again." Lever's reply

So a v2 is expected; nothing in this week's thread has been queued for merge beyond the standalone patch 1.

The substantive technical debate came from Hannes Reinecke on Monday, focused on two patches:

On the netlink protocol (patch 2): Hannes questioned why tags are individual string attributes rather than a nested attribute list — "we can have nested tags... Wouldn't it be better to make 'tags' a nested tag (ie a list of tags) such that we can avoid parsing in the caller/consumer?" Reinecke's comment. Chuck replied after digesting the point, explaining that the attribute is already declared "multi-attr: true" — tlshd emits one HANDSHAKE_A_DONE_TAG per tag and "the parsing you are worried about does not happen." He argued nesting only earns its keep for structured records with sub-fields, while a tag is a single string. Hannes was satisfied: "Ah. So one can have several 'tag' attributes in one 'done' downcall? That's perfect. So you can add my: Reviewed-by" Reinecke's follow-up.

On the tagset data structure (patch 3): Hannes pushed back harder, calling the sorted-array design overcomplicated — "Isn't this overcomplicating matters? In the end, this a list of strings. Wouldn't a simple rbtree holding the strings be sufficient?" He also objected to the name: "don't name it tagset. That will be confusing the hell of out of any storage folks, where a tagset is something completely different." Reinecke's comment.

Chuck defended the design on performance grounds, arguing that intersection — not lookup — is the primary operation: "Keeping a set of tags in a list or in an r-b tree would require MxN look up operations to compute that intersection." On naming he conceded ground, suggesting "Stringset?" Lever's reply.

Hannes accepted the rename ("Better.") and said runtime was of no concern given the 64-tag cap, offering to prototype an rbtree version Reinecke's reply. Chuck pushed back with concrete numbers on a busy NFS server: with 5 session tags × 5 export allow-tags, an rbtree intersection means "25 lookups, each O(log(5))" versus O(10) for the merge; at the 64-tag maximum it's "4000+ lookups, each O(log(64))" versus O(128). He added that "r-b trees are notoriously non-optimal in terms of memory access efficiency," and noted a forward-looking wrinkle: "TLS session tags have no support for PSK -- there are no data items inside the shared keys on which to match a tag. We might find something else to match on, though, who knows?" Lever's final reply.

Where things stand

  • Patch 1 (DONE privilege fix): Reviewed-by from both Layton and Reinecke; ready to land ahead of the rest.
  • Patches 2/9: Reviewed-by from Reinecke after the multi-attr clarification.
  • Patches 3/9: Open discussion — rename to "stringset" agreed in principle; sorted-array vs rbtree debate unresolved, with Chuck holding the line on intersection performance and Hannes willing to prototype an alternative.
  • Overall series: Needs a rebase (v1 was based on a stale testing branch per Chuck's own admission) before a v2 posting. No netlink maintainer decision yet on protocol shape; Chuck deferred that call to Jakub Kicinski.

For NFS client/server developers, the takeaway is that NFSD is moving from boolean TLS peer identity toward fine-grained, certificate-policy-driven export authorization — with all x.509 parsing deliberately kept in userspace and only opaque tag membership tested in-kernel.
