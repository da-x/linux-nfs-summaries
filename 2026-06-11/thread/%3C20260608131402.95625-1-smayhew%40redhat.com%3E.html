NFSD: fix up error returned by write_threads() — regression fix applied to nfsd-testing

Summary

NFSD: Fixing a Regression in write_threads() Error Handling

This week brought a short but consequential bug-fix thread on the Linux NFS list, focused squarely on the NFSD server side (rather than the client) and on restoring expected behavior for administrators and scripts that manage the kernel NFS server via /proc.

The Bug: A Regression in write_threads()

On June 8, Red Hat's Scott Mayhew posted a one-patch series titled [PATCH] NFSD: fix up error returned by write_threads()](https://lore.kernel.org/linux-nfs/20260608131402.95625-1-smayhew@redhat.com/), describing a behavioral regression introduced by an earlier change to nfsd_svc():

"Previously, writing 0 to /proc/fs/nfsd/threads would return 0 if the NFS server wasn't running. After commit 14282cc3cfa2, -EIO is returned. Existing scripts don't expect this behavior."

The offending upstream commit was 14282cc3cfa2 ("NFSD: don't start nfsd if sv_permsocks is empty"), which had tightened the start-up path so that an attempt to bring up NFSD with no persistent sockets would fail with -EIO. That hardening, while sensible in its own right, inadvertently changed the return value of a stop operation — writing 0 to /proc/fs/nfsd/threads while the server was already down now surfaced -EIO instead of silently succeeding.

Mayhew's fix is minimal and surgical: add an early check in write_threads() (in fs/nfsd/nfsctl.c) that bypasses the call to nfsd_svc() entirely when newthreads is 0 and the NFS server is already stopped, restoring the historical "no-op success" semantics. The patch touches a single file with five insertions and one deletion, and carries an explicit Fixes: tag pointing at 14282cc3cfa2.

Review and Acceptance

The thread moved quickly, as clean regression fixes tend to:

  • Jeff Layton replied the same day with a brief but authoritative endorsement, quoting the relevant hunk ending in return rv; and signing off:

    "Reviewed-by: Jeff Layton jlayton@kernel.org"

  • Chuck Lever, the NFSD maintainer, picked the patch up the next morning and confirmed it had landed in the nfsd-testing tree:

    "Applied to nfsd-testing, thanks! [1/1] NFSD: fix up error returned by write_threads() commit: 36f28c2e37a6a508f5a7be62ebe9c8887ed9bd20"

Classification and Significance

  • Type: Bug fix (regression repair), not a new feature or protocol change.
  • Subsystem: fs/nfsd/nfsctl.c — the procfs control interface for the kernel NFS server, i.e., the administrative surface that init scripts, systemd units, and cluster tooling use to start/stop NFSD and tune its thread count.
  • Why it matters: While this is server-side rather than client development, the /proc/fs/nfsd/threads knob is part of the operational contract between the kernel NFS stack and every distribution's nfs-server package. A silent change in error semantics from 0 to -EIO on an already-stopped server can break stop paths, monitoring scripts, and cluster orchestration that treat a non-zero return as a failure. Mayhew's fix preserves the long-standing "writing 0 when stopped is a no-op" contract while keeping the legitimate -EIO protection for the start path introduced by 14282cc3cfa2.

Final State

The discussion is closed: reviewed, applied to nfsd-testing as commit 36f28c2e37a6, and expected to ride the normal merge window into mainline. No further follow-up was posted in this week's window.
