Summary

lockd: Use "%*phN" to dprintk() a cookie — cleanup applied to nfsd-testing

This week's activity on this thread was brief and decisive: a small, self-contained code-cleanup patch from David Laight was posted Monday night (UTC) and merged into the nfsd-testing tree by NFS maintainer Chuck Lever just over three hours later. The discussion is squarely about bug-fix-adjacent cleanup in the Linux NFS client-side lock daemon (lockd/NLM server code), not a new feature or protocol change.

The patch

David Laight posted [PATCH 1/1] sunrpc: Use "%*phN" to dprintk() a cookie, which targets fs/lockd/svclock.c (the NLM server-side lock daemon code that the NFS client relies on for remote file locking). The change replaces a hand-rolled helper with the kernel's existing %*phN print format specifier:

"Simplifies the code and removes a 'not obviously bounded' strcpy(). Delete the local function nlmdbg_cookie2a() that did the equivalent."

The patch is net-negative — 5 insertions, 37 deletions — and deletes the now-redundant nlmdbg_cookie2a() helper that previously copied an NLM cookie into a printable buffer before passing it to dprintk(). Laight also notes a subtle safety point about the existing bounds checks:

"There is no need to worry about cookie->len being more than NLM_MAXCOOKIELEN (32), the buffer holding it is only that long. The existing length checks must pre-date this code being added in 2.4.26."

In other words, the legacy length guards are dead weight inherited from before the current debug-printing path was introduced in kernel 2.4.26 — a nice historical aside for anyone reading the lockd code.

Motivation: a stricter local build

The trigger for the patch was tooling rather than a field bug:

"Found by a local build that errors strcpy() unless a constant string is being written into an array."

So this is one of those patches where a developer's hardened compiler configuration (treating unbounded strcpy() as an error) surfaced a latent code smell in the kernel tree. The fix — using %*phN, which prints a bounded hex/ASCII representation of a byte buffer directly from dprintk — eliminates the manual copy entirely, removing both the strcpy() and the helper function in one stroke.

Resolution

Chuck Lever picked the patch up quickly on June 9 and confirmed:

"Applied to nfsd-testing, thanks!"

The commit landed as 926ef0ef7994232faab29e6b13270d5c88b058f3, with the subject retitled slightly for accuracy — from sunrpc: to lockd: — since the change actually touches fs/lockd/svclock.c rather than net/sunrpc/. The fast turnaround (post → merge in under four hours) reflects how low-risk and mechanical this kind of cleanup is, and it fits neatly alongside the other NFS client-side hygiene work that has been flowing through nfsd-testing this week.

Takeaways for NFS client developers

  • %*phN is the idiomatic way to dump a bounded byte buffer (like an NLM cookie) in debug prints; avoid hand-rolled copy-then-print helpers.
  • The lockd/NLM server code path — which underpins NFSv2/v3 file locking from the client's perspective — continues to receive low-hanging cleanup patches, keeping the tree free of patterns that trip up stricter compiler checks.
  • No behavioral or protocol change: this is purely a debug-printing refactor with no functional impact on lock acquisition, release, or cookie semantics.
