svcrdma Contiguous Pages Regression: Hammerspace Provides Profiling Data; GFP_NOWAIT Fix Proven Insufficient

Summary

svcrdma Contiguous Pages Regression: Detailed Profiling and Failed First Fix Attempt

Classification: Bug fix / performance regression (server-side svcrdma over NFS-over-RDMA)

This Week's Activity

The thread continued its active debugging phase on June 5, with Jonathan Flynn from Hammerspace providing detailed profiling data in response to Mike Snitzer's June 4 regression report. Flynn's message RE: [PATCH v4] svcrdma: Use contiguous pages for RDMA Read sink buffers supplied the underlying performance evidence that Snitzer had referenced, including fio results, perf reports, and flamegraphs hosted on a shared OneDrive link.

The Profiling Evidence

Flynn's data confirmed and refined Snitzer's initial diagnosis. The flamegraph showed that the allocator-heavy call stack rooted at svc_rdma_build_read_segment_contig() remained dominant in the regressed configuration, with alloc_pages_noprof() and rmqueue_buddy() accounting for a significant portion of CPU samples. This pointed to the higher-order page allocation path — specifically the buddy allocator's queue operations — as the source of the contention that Snitzer had initially attributed broadly to "spinlock" overhead.

Chuck Lever's First Fix Attempt (Same Day)

Within minutes of Flynn's data, Chuck Lever posted a targeted fix in a separate but directly related thread:

"svc_rdma_alloc_read_pages() passes __GFP_NORETRY, which limits the allocator to a single round of direct reclaim and asynchronous compaction per attempt. Under memory pressure or fragmentation that round can take a long time, and the fallback loop repeats it at each order, multiplying the stall while the RPC waits for its Read sink buffer."

Lever's proposed fix replaced __GFP_NORETRY with GFP_NOWAIT, reasoning that:

"The contiguous allocation is opportunistic: when it fails, Read sink buffers come from the pages already in rq_pages[]. Direct reclaim effort buys little here. Allocate with GFP_NOWAIT instead, which omits __GFP_DIRECT_RECLAIM so the allocator takes pages only from the free lists and returns NULL immediately when none are available."

He was candid about his uncertainty:

"Given the perf symbol resolution inaccuracies I can't swear this will fix the issue, but here's a stab at it."

Flynn's Rapid Test Result: Fix Proven Insufficient

Flynn turned around a test within 42 minutes of Lever posting the patch. His reply delivered the verdict:

"Unfortunately, the GFP_NOWAIT change did not materially affect either throughput or the perf profile. The allocator-heavy stack rooted at svc_rdma_build_read_segment_contig() remains dominant, with alloc_pages_noprof() and rmqueue_buddy() continuing to account for a significant portion of the samples, similar to the original regressed build."

This was a critical negative result: it ruled out direct reclaim as the primary bottleneck. The problem lies deeper in the buddy allocator's higher-order allocation path itself — the rmqueue_buddy() spinlock contention that Snitzer had flagged is inherent to requesting large contiguous pages under high concurrency, not an artifact of the GFP flags triggering reclaim.

Evolution of the Discussion (Bridge from Prior Weeks)

  • March 19: Chuck Lever posted PATCH v4, a performance optimization to reduce DMA mappings from 16 to 1 for 64 KB READ payloads by using physically contiguous page allocations.
  • March 17: Christoph Hellwig raised concerns about the size limit scaling with page size; Lever addressed these in v4.
  • June 4: Mike Snitzer reported the patch (merged as commit 18755b8c2f241 in 7.1) causes a ~60% WRITE throughput regression (24.2 GB/s vs 60.6 GB/s) on high-end RDMA, with spinlock contention dominating the flamegraph.
  • June 5: Flynn provided detailed profiling data; Lever's first fix attempt (GFP_NOWAIT) was tested and found insufficient within the hour.

Current Status and Significance

The debugging has narrowed considerably: the bottleneck is confirmed to be in the buddy allocator's higher-order page allocation path (alloc_pages_noprof() → rmqueue_buddy()), not in direct reclaim. This means the fix will likely need to address the fundamental approach — possibly per-CPU pre-allocated contiguous buffers, a different memory pool strategy, or reducing the allocation order — rather than simply adjusting GFP flags.

The rapid turnaround (regression report at ~00:00 UTC June 4, profiling data and failed fix by 23:13 UTC June 5) reflects the tight collaboration between Hammerspace's test infrastructure and Oracle's NFS development team. The Fixes: tag in Lever's patch (Fixes: 18755b8c2f24) confirms this is being tracked as a regression fix for the 7.1 merge window commit, with implications for stable backporting if not resolved before the next RC.
