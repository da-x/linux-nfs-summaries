Summary

pnfs: proposed LAYOUTSTATS refcount fix NACKed by Trond Myklebust over use-after-free risk

A short but pointed exchange this week on the Linux NFS client side. WenTao Liang (vulab@iscas.ac.cn) posted a one-patch bug fix targeting the pNFS LAYOUTSTATS reporting path in fs/nfs/nfs42proc.c, and Trond Myklebust — the Linux NFS client maintainer — NACKed it within roughly two hours, arguing that the proposed change would introduce a "massive use-after-free."

Classification

This is a bug fix discussion (not a new feature or protocol change). The patch targets an alleged reference-count leak in pnfs_report_layoutstat(), with a Fixes: tag pointing at commit be3a5d233922 ("NFSv.2/pnfs Add a LAYOUTSTATS rpc function") and a Cc: stable@vger.kernel.org line, indicating the author considered it a regression fix suitable for stable backports.

The proposed fix

In the original patch, Liang described the failure mode in detail:

"When pnfs_report_layoutstat() calls pnfs_get_layout_hdr() and passes the reference through the inode field of the layoutstats data to nfs42_proc_layoutstats_generic(), if rpc_run_task() in that function fails (IS_ERR), nfs42_proc_layoutstats_generic() returns immediately without releasing the reference. This leaks the layout header reference, leaks the allocated data, and leaves the NFS_INO_LAYOUTSTATS flag stuck on the inode, preventing further layoutstat reporting."

His proposed remedy was to call nfs42_layoutstat_release(data) before returning on the rpc_run_task() error path, mirroring the existing cleanup that already runs when the inode is missing. The diff touched only fs/nfs/nfs42proc.c (3 insertions, 1 deletion).

The maintainer's rebuttal

Trond Myklebust replied in a terse NACK, quoting the relevant snippet of the patch around return PTR_ERR(task); and stating:

"NACK! If you'd bothered to read the code, you would have found that rpc_run_task() already cleans up on failure. This patch just introduces a massive use-after-free."

The core technical disagreement is about who owns the cleanup responsibility when rpc_run_task() fails. Liang's premise was that nfs42_proc_layoutstats_generic() bails out early without releasing the layout-header reference and the allocated layoutstats data, leaving the NFS_INO_LAYOUTSTATS inode flag set so no further LAYOUTSTATS reports can be issued. Myklebust's counter is that the RPC layer (rpc_run_task()) already performs the necessary teardown on failure, so adding an explicit nfs42_layoutstat_release(data) at that site would release the structure a second time — i.e., a double-free / use-after-free rather than a leak fix.

Evolution and status

  • 06-11 15:47 UTC — Liang posts v1 of the patch, framed as a stable-worthy refcount/data leak fix for pnfs_report_layoutstat().
  • 06-11 17:36 UTC — Myklebust NACKs, citing that rpc_run_task() already cleans up on failure and that the proposed extra release would cause a use-after-free.

No further messages landed in this thread before the end of the window, so the patch is not accepted as posted. The underlying question — whether there is still a real leak when rpc_run_task() fails (e.g., around the NFS_INO_LAYOUTSTATS flag or the allocated layoutstats data) versus whether the RPC layer's cleanup fully covers it — remains open and would need to be resolved in a follow-up revision if Liang wishes to pursue the fix. For readers of the NFS client tree, the practical takeaway is that the LAYOUTSTATS error path in fs/nfs/nfs42proc.c should not be patched along the lines of v1 without first reconciling with the RPC task cleanup semantics that Myklebust pointed to.
