nfsrahead SIGBUS crash on aarch64 for non-NFS block devices

Summary

nfsrahead SIGBUS crash on aarch64 for non-NFS block devices

Overview

This week's activity in this thread consists of a single bug report filed by Ubahakwe Emeka, who documented a hard fault in the nfsrahead userspace helper when it is invoked by udev against block devices that are not NFS-backed. The report arrived late in the window (2026-06-09) and no replies or patches had landed by the end of the week, so this is a fresh issue awaiting maintainer attention rather than an ongoing discussion.

Classification

This is a bug fix request, not a new feature or protocol change. It concerns two distinct defects in the nfsrahead tooling:

  1. A missing device-type filter in the udev rule that triggers the helper for every block device on the system, and
  2. An architecture-sensitive memory-alignment bug in the cleanup/exit path that turns a benign early-exit into a SIGBUS fault on aarch64.

Key Technical Arguments

Emeka's report is concise but points to a clear root-cause chain. The udev rule 99-nfsrahead.rules "fires for all block devices with no filter for NFS-backed devices," so the helper is launched even for virtio disks and loop devices where it has nothing to do. Rather than bailing out cleanly, the program crashes:

"nfsrahead is supposed to exit gracefully for non-NFS devices but instead crashes in __libc_free() due to a misaligned pointer — a hard fault on aarch64, silent on x86_64."

The reported stack trace shows the abort happening inside libc's free path:

#0  __libc_free (libc.so.6)
#1  nfsrahead + 0x2074
#2  __libc_start_main (libc.so.6)
#3  nfsrahead + 0x22f0

The reporter observed the crash being triggered for 254:0 (a virtio disk) and 7:1, 7:2 (loop devices), confirming that this is not an NFS-specific failure but a consequence of the udev rule's lack of filtering combined with an alignment-sensitive cleanup path.

The architecture asymmetry is the most striking detail: the same misaligned-pointer bug is "silent on x86_64" but produces a hard SIGBUS fault on aarch64, which makes the defect invisible to developers and CI that only exercise x86_64 hosts.

Evolution of the Discussion

There was no back-and-forth this week — the thread contains exactly one message, the original bug report from Emeka. No maintainer (e.g., Trond Myklebust or Anna Schumaker) had responded by the end of the window, and no patch was posted. The discussion is therefore in its earliest stage: a problem statement awaiting triage.

Final Conclusions / Asks

Emeka closed with an explicit two-part fix list:

"Fix needed:

  1. nfsrahead should detect non-NFS devices and exit 0 gracefully
  2. Fix the misaligned pointer in the cleanup/exit path on aarch64"

The first item is a udev-rule / device-detection change (filter by major/minor or by backing-fs type so that nfsrahead only runs against NFS-backed block devices). The second is a genuine code defect in the helper's exit path — likely an unaligned struct member or pointer arithmetic that x86_64 tolerates but aarch64 does not.

Status at Week's End

  • Open, no replies. The bug report is fresh (filed 2026-06-09) and was the last activity in this thread for the week.
  • No patch, no maintainer acknowledgement, no related follow-up threads observed within the window.
  • Worth watching next week for a response from the NFS client maintainers or a proposed patch to nfs-utils (where nfsrahead and its udev rule typically live).

Relevance to NFS Client Development

Although nfsrahead is a userspace helper rather than kernel code, it sits squarely in the NFS client tooling stack: it is the mechanism that primes readahead on newly-appeared NFS block devices. A SIGBUS fault on aarch64 — an increasingly common platform for both servers and embedded clients — is a real reliability concern because udev will keep re-invoking the helper on every non-NFS device event, producing repeated hard faults in the boot path. The fix Emeka proposes (graceful early-exit plus alignment correction) is small but important for making NFS client tooling portable across architectures.
