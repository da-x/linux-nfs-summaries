CB_NOTIFY Directory Delegation: Review Kicks In, Series Punted to v7.3

Overview

This week's activity in the long-running CB_NOTIFY directory delegation thread was quiet but consequential: for the first time since Jeff Layton posted the v4 NFSD series on May 22, nfsd maintainer Chuck Lever actually started reviewing it — and immediately set expectations that the work will not land in v7.2.

The two messages this week both focus on patch 03/21, which adds the new NOTIFY4_* flags proposed in RFC8881bis. The discussion is about a new protocol feature (RFC8881bis CB_NOTIFY callback support for directory delegations), not a bug fix — though the review surfaced some hygiene items and an open question about spec stability.

Key Technical Points

Review begins; v7.3 punt

Chuck Lever opened the review with a candid admission and a roadmap:

"Unfortunately, reviewing this series slipped off my radar. I'm just now getting to it. I'm going to do this in order and some of the earlier reviews are cosmetic. But there are some significant changes needed later on, so I expect we'll need to redrive this series and punt it to v7.3."

He also asked Layton to scrub stale tags before reposting:

"One thing you might update before you repost is to remove the 'Acked-by: Chuck Lever' throughout the series."

Layton responded that this was reasonable, attributing the delay to other work:

"That's reasonable. We had some unrelated new bugs crop up near the end of the cycle that made it hard to get this in and tested properly."

He also confirmed the Acked-by tags were an artifact of his tooling: "Ok. I think b4 added that."

Subject prefix nit — and a shared-header wrinkle

Lever flagged that the patch subject should read nfsd: rather than nfs_common:. Layton pushed back with a substantive technical point: the XDR header touched by this patch is shared between client and server, so the nfs_common prefix is arguably more accurate:

"include/linux/sunrpc/xdrgen/nfs4_1.h is a shared header. Anna will presumably need this patch as well."

This is an important detail for NFS client development: the new NOTIFY4_* flag definitions in nfs4_1.h are the very constants the client-side callback handler (still to be written) will consume when decoding CB_NOTIFY requests. Anna Schumaker's client tree will need this patch as a prerequisite.

Spec stability — an open question

Lever raised a question he'd received privately, and asked that it be addressed in the commit message rather than left implicit:

"One recent private comment to me was a question about whether we can trust the stability of the specification, which is still a WG document and has been for years. This patch's commit message should address that."

Layton acknowledged the tension honestly:

"That's definitely an open question. We are definitely adopting these changes before the ink is dry. We might have to modify things later, especially once there is more client-side experience. I'm open to verbiage suggestions here."

This is a notable admission for a protocol patch — the kernel is implementing RFC8881bis while it is still a working-group draft, betting that the GET_DIR_DELEGATION flag bits will not change before the spec stabilizes. The "more client-side experience" caveat underscores that the Linux client implementation (the missing half of this feature) is what will actually validate the design.

XDR comment clarification

Lever also made a small but verifiable improvement to the XDR grammar file, clarifying a comment as /* Proposed in RFC8881bis */, and confirmed the generated C source was unaffected:

"I rebuilt the generated source to confirm that it hasn't been altered by recent changes to xdrgen or this comment change. The only thing that changed in the output was the header's timestamp."

Layton simply agreed: "Sounds good."

Evolution of the Discussion

The thread has now moved through a clear arc across three weeks:

  1. Week of May 15 — VFS-side patches (01–07) merged into vfs-7.2.directory.delegations by Christian Brauner; Chuck Lever confirmed NFSD merge prerequisites would be met shortly.
  2. Week of May 28 — Layton posted the v4 NFSD series (21 patches, ~2,184 lines), cleanly rebased onto the merged VFS base. Light review activity: a nit on patch 20/21 from Lever and a tracepoint question from Steven Rostedt (resolved by pointing to Layton's dir-deleg branch).
  3. This week (June 5–11) — Chuck Lever began the substantive, in-order review of the series. The first patch he reviewed (03/21) generated only cosmetic nits, but he made clear that "significant changes" are coming on later patches and the series is being punted to v7.3.

The trajectory suggests the remaining 19 patches will get more detailed scrutiny in the coming weeks, with a v5 repost expected before the v7.3 merge window.

Implications for NFS Client Development

While this thread is server-side work, its significance for the Linux NFS client cannot be overstated:

  • Patch 03/21 is a client prerequisite. The NOTIFY4_* flags in the shared XDR header are what the client's CB_NOTIFY decoder will use. Anna Schumaker's client tree needs this patch before any client-side callback handler can be written.
  • The "client-side experience" caveat matters. Layton's acknowledgment that the spec may need modification "once there is more client-side experience" means the client implementation will not just consume a finished protocol — it will help validate and potentially reshape it.
  • Layton's earlier stance holds: the server code should not be merged until there is a complete client-side implementation to test against. The v7.3 punt gives both sides time to mature in tandem.

Status

  • VFS patches: Merged (last week of May).
  • NFSD patches (v4): Posted May 22; review now underway by Chuck Lever; punted to v7.3 pending "significant changes" on later patches and a v5 repost.
  • Client-side implementation: Still pending; Layton explicitly wants it before final merge, and the shared XDR header in patch 03/21 is its first dependency.
