xprtsock: annotate shared socket callbacks with READ_ONCE/WRITE_ONCE

Summary

xprtsock callback visibility fix lands as a single-patch net submission

The week's activity in this thread consists of a single, self-contained bug-fix patch from Runyu Xiao (Soochow University), posted on 2026-06-11 and addressed to the net tree rather than mainline feature development. The patch closes a long-standing memory-visibility gap in the SUNRPC client transport layer that has been present since the original client-side transport switch was merged.

What kind of change this is

This is squarely a bug fix, not a new feature or protocol change. It does not alter any NFS wire behavior; it only adds READ_ONCE()/WRITE_ONCE() annotations to shared socket callback pointers in net/sunrpc/xprtsock.c. The patch carries a Fixes: tag pointing at the ancient commit that introduced the pattern:

"Fixes: a246b0105bbd ("[PATCH] RPC: introduce client-side transport switch")" Runyu Xiao's patch

The [PATCH net] prefix signals the author's intent to get this into a stable backport cycle rather than waiting for the next merge window.

The technical argument

The core of Xiao's write-up describes how xprtsock takes over a live socket and later hands it back, using plain stores on callback pointers that other CPUs may still be reading:

"xprtsock replaces and restores sk->sk_data_ready and sk->sk_write_space on live sockets with plain stores, and xs_udp_do_set_buffer_size() invokes sk->sk_write_space via a plain load." patch body

He frames the fix as bringing xprtsock into line with an established kernel-wide contract for shared callback pointers, explicitly invoking prior art:

"These callback pointers are shared with generic socket and protocol paths that may read or invoke them concurrently, so xprtsock needs the same READ_ONCE()/WRITE_ONCE() callback visibility contract that the validated 4022 family applied elsewhere." patch body

The concrete failure mode he describes is a stale-snapshot race during teardown:

"When SUNRPC takes over an AF_LOCAL, UDP, or TCP socket and later restores the lower-socket callbacks during teardown, another CPU may still hold an earlier callback snapshot. The plain replace/restore pattern leaves the same visibility hole as the validated 4022 family, so a stale snapshot can still invoke xs_data_ready() or xs_udp_write_space() after the live callback fields have already been restored to the lower-socket handlers." patch body

The actual change

The fix is deliberately narrow and surgical — 11 insertions and 9 deletions in a single file:

"Use WRITE_ONCE() for the shared sk_data_ready and sk_write_space stores in xs_local_finish_connecting(), xs_udp_finish_connecting(), xs_tcp_finish_connecting(), and xs_restore_old_callbacks(). Use READ_ONCE() for the direct sk_write_space invocation in xs_udp_do_set_buffer_size(). This matches the required callback visibility contract while leaving adjacent sk_state_change and sk_error_report handling unchanged." patch body

The explicit note that sk_state_change and sk_error_report are left alone is worth flagging: the author is signaling to reviewers that he has scoped the change tightly to the two callbacks xprtsock actually swaps in and out, and is not doing a blanket annotation sweep of every socket field. That restraint typically makes a net-tree patch easier to accept.

Why it matters for NFS client development

Although small, this kind of fix matters because xprtsock sits at the boundary between the RPC layer and the kernel's generic socket code. The xs_data_ready() and xs_udp_write_space() callbacks are invoked from network softirq context on whatever CPU happens to be processing the packet, while xs_restore_old_callbacks() runs in process context during transport teardown. Without the once-accessors, a compiler or aggressive CPU reordering could let a softirq on another core observe a torn or stale pointer — invoking an RPC callback after the transport has already been handed back to the lower protocol, which is precisely the kind of use-after-free-adjacent bug that is hardest to reproduce and diagnose in production NFS clients.

The patch is signed off by the author only at this point and awaits review; given its small diff and clear Fixes: tag, it is a strong candidate for quick acceptance into the next -net pull.
