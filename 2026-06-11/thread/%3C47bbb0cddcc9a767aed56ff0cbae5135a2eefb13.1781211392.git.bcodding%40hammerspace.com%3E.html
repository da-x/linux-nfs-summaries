NFSv4: include MAY_WRITE in open permission mask for O_TRUNC

Summary

NFSv4 client: O_TRUNC must demand write permission even on read-only opens

This week (ending 2026-06-11) the thread consists of a single message: a one-shot patch from Benjamin Coddington fixing a POSIX compliance bug in the NFSv4 client's local open-authorization path. No replies have landed yet, so there is no discussion to summarize beyond the patch itself — but the technical content is meaty and worth reporting.

Classification: bug fix (POSIX/authorization), not a protocol change

This is squarely a bug fix in NFSv4 client development, not a new feature or protocol change. It corrects how the client authorizes open() calls it satisfies locally from a cached write delegation, and it carries a Cc: stable@vger.kernel.org tag — a signal that maintainers expect this to be backported to stable trees.

The bug, in Coddington's words

The patch targets nfs_open_permission_mask(), which builds the access mask handed to nfs_may_open() — "the local authorization gate for OPENs the client serves itself from a cached write delegation via the can_open_delegated() path in nfs4_try_open_cached()." The flaw:

"The mask is derived from O_ACCMODE alone, so an open(O_RDONLY | O_TRUNC) against a file the caller cannot write requests only MAY_READ and passes the local check."

That is, when a process opens a file read-only with O_TRUNC, the client's local permission check only asks for MAY_READ and lets the open through — even though the caller has no write permission on the file.

Why it matters: the delegation loophole

The dangerous part is what happens next. Because the OPEN is satisfied locally from a cached write delegation, the truncation is then issued to the server as SETATTR(size=0) over the delegation stateid — and the server happily accepts it under standard write-delegation semantics. In other words, the client's local gate lets through an operation the server would have rejected had it been forced to check permissions itself:

"The OPEN is then satisfied locally and the truncation is issued to the server as a SETATTR(size=0) over the delegation stateid, which the server accepts under standard write-delegation semantics. POSIX requires that this open fail with EACCES."

So a caller without write permission can effectively zero out a file it cannot write, purely because the client's local shortcut under-reports the access being requested. This is a real privilege/authorization hole in the delegation fast path — exactly the kind of subtle divergence between "what the client checks locally" and "what the server would enforce" that delegation code is notorious for introducing.

The fix

The remedy is minimal and surgical (2 lines added to fs/nfs/dir.c): always fold MAY_WRITE into the mask whenever O_TRUNC is set, so the local check matches what the server would have enforced:

"Include MAY_WRITE in the mask whenever O_TRUNC is set so the local check matches the access the server would have enforced."

POSIX grounds the change: "POSIX requires write permission to truncate a file, so an open() that specifies O_TRUNC must be authorized for write access regardless of the O_ACCMODE access mode."

Attribution and status

The fix was suggested by Trond Myklebust (Suggested-by: trondmy@kernel.org), underscoring that this is a known class of delegation-authorization subtlety. Signed off by Coddington and cc'd to stable, the patch is in its first posting with no review or maintainer response yet as of the end of the window.

Bottom line

A tight, well-motivated client-side authorization fix: the NFSv4 client was under-checking permissions on O_RDONLY | O_TRUNC opens served from cached write delegations, allowing a non-writer to truncate a file it cannot write. The two-line change closes the gap between local and server-side enforcement. Watch for review/merge in the coming days.
