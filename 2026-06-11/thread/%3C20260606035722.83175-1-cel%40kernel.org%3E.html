svcrdma: Contiguous Read sink buffer regression — fix fails, revert lands in nfsd-next

Summary

svcrdma: Cap Read sink allocations at PAGE_ALLOC_COSTLY_ORDER — regression confirmed, revert queued

Type: Bug fix (regression from a performance optimization) — ultimately resolved by reverting the offending commit.

Background

This thread picks up a nasty NFS/RDMA server-side throughput regression introduced by commit 18755b8c2f24 ("svcrdma: Use contiguous pages for RDMA Read sink buffers"). On a 128-core single-NUMA-node server driving dual 400 Gb/s links with 640 nfsd threads, WRITE throughput collapsed from 73.9 GiB/s to 30.3 GiB/s, while server CPU utilization jumped from 8.5% to 76% and 73% of all CPU cycles landed in native_queued_spin_lock_slowpath.

The proposed fix (and why it failed)

On June 6, Chuck Lever posted a patch capping the contiguous sink allocation order at PAGE_ALLOC_COSTLY_ORDER, reasoning that:

"The page allocator serves allocations only up to PAGE_ALLOC_COSTLY_ORDER (3) from its per-CPU page lists; SVC_RDMA_CONTIG_MAX_ORDER is 4, so every contiguous sink buffer allocation falls through to rmqueue_buddy() and acquires the zone lock."

The idea was that order-3 chunks would stay on the fast per-CPU path while still collapsing eight per-page bvecs into one.

Jonathan Flynn tested it the same day and reported the fix made things worse, not better:

"Unfortunately, it did not improve the regression. Throughput was slightly worse than the previous GFP_NOWAIT test, measuring 25.4 GiB/s."

His flamegraph data told the real story: while alloc_pages_noprof() time dropped from 58% to 40%, a new hotspot appeared — svc_rdma_read_complete() and folios_put_refs() each jumped from ~7% to ~16%. The allocation-side lock contention was merely being displaced onto the release side.

Root cause identified, revert decided

Chuck Lever responded on June 7 with a clear diagnosis:

"The two failed fixes demonstrate that the current folio allocator is not up to the task -- the problem appears to be on the release side, where the individual pages have to be merged back into an order-4 compound page. I don't yet see a straightforward way to make it work."

Given proximity to v7.1-rc7, he added a revert of 18755b8c2f24 to nfsd-next:

"Since we're right up against v7.1-rc7, I've added a patch to nfsd-next to revert 18755b8c2f24 -- it will get pulled back into 7.1.y as soon as the v7.2 merge window closes in three weeks."

Jonathan Flynn agreed and thanked Chuck, offering to help test future iterations:

"If you continue exploring this area in the future and still see promise in the contiguous allocation approach, I'd be happy to help test additional changes as time permits."

Key takeaways for NFS/RDMA developers

  • The contiguous-page optimization is shelved. The revert lands in nfsd-next now and will backport to 7.1.y after the v7.2 merge window closes (~mid-July).
  • The bottleneck is deeper than allocation. Both the GFP_NOWAIT workaround and the order-cap fix failed because the real cost is on the release path — merging individual pages back into compound folios in svc_rdma_read_complete() / folios_put_refs(). Any future attempt at this optimization will need to address that side.
  • Performance regression testing at scale matters. Jonathan Flynn's shared test bundle (with flamegraphs) was instrumental in proving the fix ineffective and pinpointing the release-side hotspot.
