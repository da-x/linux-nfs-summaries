mTLS identity RFC: netns binding defended, unified-keyring idea rejected

Summary

mTLS client-identity RFC: namespace debate deepens, keyring-unification idea shot down

Type: New feature / design RFC (with an embedded security fix). This week the thread moved from Chuck Lever's original posting into a second round of architectural back-and-forth, with Sagi Grimberg and Hannes Reinecke both weighing in. The discussion is squarely about NFS client development: how xprtsec=mtls mounts will name and isolate their x.509 credentials going forward.

Bridge to last week (brief)

Last week Lever posted the RFC proposing a named, per-mount client-identity front end (tls_identity= + an nfstlskey CLI) backed by a per-network-namespace .nfs keyring held in struct nfs_net. That design also fixes a real hole: today's module-global .nfs keyring is dead and never referenced, so nfs_tls_key_verify()'s global key_lookup() means "any tlshd that learns a serial can read the key." Reinecke objected to the netns binding last week, arguing keys should be tagged per user/mount namespace, and Lever rebutted that tlshd is a network-layer service. This week picks up exactly where that left off.

The netns question gets settled (Sagi Grimberg, 2026-06-05)

Grimberg entered the debate by taking a side on the namespace-binding fight that Lever and Reinecke had been going back and forth on. After quoting Lever's defense of the network-namespace model, he asked the pointed question:

"Can tlshd run in multiple network namesapces today?"

and then conceded the point outright:

"I agree with network namespace isolation."

That was a meaningful shift — an independent voice (not the RFC author) endorsing the netns binding that Reinecke had challenged. Lever immediately confirmed the practical reality behind Grimberg's question, explaining why per-netns is not just convenient but mandatory:

"AIUI the netlink upcall in the kernel wants to use a netlink socket in the current network namespace. So there has to be at least one tlshd instance in each network namespace that wants to use in-kernel TLS consumers."

So the "which namespace?" question from last week is now leaning decisively toward network namespace, with the rationale that tlshd must already exist per-netns anyway because of the netlink upcall.

A new idea: unify .nfs and .nvme (Grimberg, 2026-06-05)

In a second message aimed at Lever's original RFC, Grimberg floated consolidating the credential keyrings across subsystems:

"Should we consider unifying .nfs and .nvme to a single one? that is handled the same way? maybe .tlshd? That is where the keys stored are directed to..."

He also probed the isolation model — questioning whether a tlshd in one namespace should be able to read a key provisioned for another ("tlshd on ns-A should be able to read it though right?") — and offered an opinion on Lever's open retrieval-primitive question:

"Perhaps option (b) is aligned to how nfs/sunrpc lookup creds ?"

On the userspace front end he was positive:

"I think this is a solid user interface."

Reinecke rejects unification (2026-06-06)

Reinecke answered the .nfs/.nvme consolidation idea directly and firmly, on two grounds. First, it would not actually buy anything because NVMe's keys are already being moved into the kernel keyring independently of tlshd:

"Not sure if that buys us anything. I already have a patchset pending to move the NVMe DH-HMAC-CHAP keys into the kernel keyring, and that will also use the .nvme keyring without having any relationship with tlshd."

Second — and more fundamentally — the two subsystems use different kinds of credentials:

"Also NVMe and NFS are using fundamentally different keys (PSK for NVMe, X.509 certificates for NFS), so I don't think we get much benefit from there."

He added that a unified design would only make sense if NVMe migrated to X.509, which is not on the horizon:

"If NVMe would be moving to X.509 things might be different, but there is no interest in that and the TPAR for that got shelved."

On Grimberg's isolation question ("should tlshd on ns-A read it?"), Reinecke pushed back hard, arguing that cross-namespace read access defeats the entire purpose of the fix:

"Why? Reading is all tlshd will ever do, so granting read access to all keys irrespective of the namespace just brings us back to the current situation."

That last line is the thread's sharpest statement of the security goal: the whole point of the per-netns keyring is that a tlshd in one namespace cannot read another namespace's credentials, so opening up cross-namespace reads would undo the isolation the RFC is trying to establish.

State of play and conclusions

This week produced two clear movements:

  1. The netns-binding question is effectively resolved in favor of network namespaces. Grimberg's "I agree with network namespace isolation" plus Lever's explanation that tlshd must run per-netns anyway (netlink upcall) closes the loop on Reinecke's user/mount-ns objection from last week. The design keeps a single .nfs keyring whose keys are visible only in the namespace where they were created, with tlshd linking the netns keyring serial per handshake and possessor-only (no KEY_USR_READ) credential keys enforcing isolation "rather than advisory."

  2. The keyring-unification idea is dead. Reinecke's two-part rebuttal — NVMe already gets its own kernel-keyring path via a pending patchset, and PSK vs. X.509 are fundamentally different key types — forecloses merging .nfs and .nvme.

Still open: Lever's retrieval primitive question (how userspace names the kernel-held netns keyring). Grimberg tentatively leaned toward option (b), an NFS-specific request_key type, on the grounds that it mirrors how nfs/sunrpc already looks up credentials — but neither the keys-subsystem maintainers nor Lever has confirmed a choice yet. The NFSROOT/TPM path (kernel obtaining the client cert itself for initial-netns root mounts) also remains unaddressed.

For NFS client developers, the takeaway is that the long-undocumented xprtsec=mtls serial options are converging on a documented, namespaced, per-mount interface with real credential isolation — and that the namespace model (network namespace) has now survived its first serious challenge.
