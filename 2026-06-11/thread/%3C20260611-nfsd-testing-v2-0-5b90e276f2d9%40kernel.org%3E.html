Jeff Layton resends 21-patch "nfsd: more bugfixes" series as v2, dropping the localio patch and adding three new fixes

Summary

Jeff Layton's nfsd bugfix series returns as a 21-patch v2

On Thursday, June 11, Jeff Layton posted a 21-patch v2 of his "nfsd: more bugfixes" series to linux-nfs, the follow-up to the 19-patch v1 he sent on June 9. The series remains a pure bugfix collection — no new features, no protocol changes — and is again explicitly aimed at the v7.3 merge window:

"AFAICT, these are garden-variety bugs. Chuck, please consider these for v7.3."

What changed between v1 and v2

The cover letter lays out the deltas succinctly:

"This version is addresses review comments from Sashiko. There wasn't much in the way of regressions in v1, but it did notice a number of nearby problems that should also be fixed. This adds 3 patches to fix those. I also dropped the localio patch from the series since that should probably go through the NFS client tree. I'll send it separately."

The three changes are:

  1. Three new patches addressing "nearby bugs sashiko noticed while reviewing v1" — specifically PATCH 19/21 (restore rq_status_counter to even on all nfsd_dispatch() exit paths), PATCH 20/21 (reset thread skip index when advancing pools in rpc_status dumpit), and PATCH 21/21 (drop the stateid, not the stateowner, on seqid_op replay retry).
  2. The localio patch was dropped — in v1, PATCH 01/19 fixed an nfsd_file reference leak in the client-side fs/nfs/localio.c. Chuck Lever had asked on June 10 whether it should go through Anna/Trond's client trees, and Layton agreed. It is now being sent separately to the NFS client tree.
  3. Cleaned-up unwind logic for server startup failure paths (visible in PATCH 17/21, which reorders debugfs and slab initialization to follow LIFO teardown).

The v2 series touches 18 files with 200 insertions and 53 deletions, spanning nfsd, lockd, sunrpc, and the netlink spec. Every patch still carries an Assisted-by: Claude:claude-opus-4-8 tag — this is one of the more prominent examples yet of LLM-assisted kernel auditing producing a substantial, maintainer-targeted fix series.

The bugfixes in detail

The 21 patches cover a wide range of correctness issues. Grouping them by theme:

RPC status / netlink dumpit hardening (patches 01–04, 19–20)

Five of the 21 patches target the rpc_status netlink interface added in commit bd9d6a3efa97 and ac18892ea3f7 — a relatively new feature whose lockless reader has proven to be a bug magnet:

  • PATCH 01/21 — nfsd4_release_compoundargs() leaves opcnt stale after freeing the dynamic ops buffer. The dumpit reader then reads min(opcnt, 16) entries from an 8-element inline array, "leak[ing] it to userspace via netlink." Fix: zero opcnt unconditionally on release.
  • PATCH 02/21 — The hand-rolled seqcount-like protocol in the dumpit handler is missing an smp_rmb() before its second counter check. On weakly-ordered architectures (ARM, POWER), "the CPU may reorder field reads past the second counter check, making the retry logic ineffective."
  • PATCH 03/21 — nfsd_genl_rpc_status_compose_msg() returns -ENOBUFS on nla_put failure without calling genlmsg_cancel(), leaving a partial message in the skb and aborting the entire dump. The fix follows standard netlink dump conventions: cancel, paginate if possible, only return fatal errno when nothing fit.
  • PATCH 19/21 (new in v2) — Only the fully successful path in nfsd_dispatch() restored rq_status_counter to even. Cache-hit, drop, and encode-error paths left it stuck odd, so "the dumpit reader treats the rqstp fields as stable and its retry check compares against the same unchanging odd value, so it never detects concurrent mutation." This is the root-cause fix that makes PATCH 01's defensive opcnt zeroing less critical.
  • PATCH 20/21 (new in v2) — When a netlink dump fills the reply buffer and resumes, "the thread skip count was applied to every pool, not just the pool the dump was suspended in," silently omitting rpc_status entries from subsequent pools.

Use-after-free / RCU fixes (patches 04, 16)

  • PATCH 04/21 — svc_rqst_free() frees rq_argp and rq_resp synchronously via kfree(), but the svc_rqst struct itself is freed via kfree_rcu(). "After svc_exit_thread() calls list_del_rcu() and svc_rqst_free(), there is a window where RCU readers that started before list_del_rcu() can still traverse the thread list and find the rqstp. These readers (e.g. nfsd_nl_rpc_status_get_dumpit()) dereference rqstp->rq_argp, which has already been freed — a use-after-free." The fix moves those two kfree() calls into an explicit call_rcu() callback.
  • PATCH 16/21 — nlmsvc_ops is published by nfsd_lockd_init() and cleared by nfsd_lockd_shutdown() with plain stores, while lockd dereferences it unguarded. "A stale load after rmmod nfsd results in either a NULL deref or a module-text use-after-free." The fix RCU-protects the pointer and adds a struct module *owner field to pin the module across indirect calls.

Grace period / state management (patches 08, 12–14, 21)

  • PATCH 08/21 — nfsd4_open() sets NFS4_OO_CONFIRMED before calling do_open_fhandle(), which can fail. "If it fails, the openowner stays permanently confirmed despite the OPEN failing."
  • PATCH 12/21 — The most severe bug in the series: clients_still_reclaiming() computes a deadline from nn->boot_time (CLOCK_REALTIME, ~1.7 billion) but compares it against ktime_get_boottime_seconds() (CLOCK_BOOTTIME). "The comparison is always false — it would take ~54 years of uptime for BOOTTIME to exceed the REALTIME-derived deadline." As Layton puts it: "any client can hold the server in grace indefinitely by sending CLAIM_PREVIOUS OPEN requests, blocking all non-reclaim operations for all other clients."
  • PATCH 13/21 — clients_still_reclaiming() uses separate test_bit() and clear_bit() calls on NFSD_NET_SOMEBODY_RECLAIMED. "A concurrent set_bit() from the OPEN or LOCK reclaim path arriving between the test and clear is silently lost, causing the next laundromat tick to end grace prematurely."
  • PATCH 14/21 — nfsd4_lock() only checks the namespace-wide grace flag, not the per-client NFSD4_CLIENT_RECLAIM_COMPLETE bit. A client that already sent RECLAIM_COMPLETE can still submit reclaim LOCKs, violating "RFC 8881 section 8.4.2.1."
  • PATCH 21/21 (new in v2) — In nfs4_preprocess_seqid_op(), the error path on -EAGAIN replay retry called nfs4_put_stateowner() without ever having taken a stateowner reference, "risking a stateowner refcount underflow and use-after-free," while leaking the sc_count reference on the stid. The fix drops the stid reference instead.

NFSv4 protocol correctness (patches 05–07, 10)

  • PATCH 05/21 — nfsd4_create() stores the return value of nfsd4_acl_to_attr() in status, but the subsequent switch(create->cr_type) block "unconditionally overwrites it in every branch. ACL translation errors are silently discarded, and the CREATE proceeds without the requested ACL."
  • PATCH 06/21 — nfsd4_delegreturn() is "the only stateful NFSv4 operation that does not call nfs4_check_fh() to verify the delegation's file matches cstate->current_fh." A client can DELEGRETURN with a mismatched filehandle, "destroying the correct delegation but waking the wrong inode's waiters."
  • PATCH 07/21 — The xdrgen-based TIME_DELEG decode paths store a raw uint32_t nseconds into tv_nsec without enforcing nseconds < NSEC_PER_SEC. "A malformed timespec can propagate through notify_change() to disk."
  • PATCH 10/21 — The FL_SLEEP guard uses lk_type & (NFS4_READW_LT | NFS4_WRITEW_LT) which "computes lk_type & 7, non-zero for all valid lock types including non-blocking ones." This was introduced by a refactoring commit and means non-blocking locks incorrectly get the sleep flag.

Input validation / initialization ordering (patches 09, 11, 15, 17–18)

  • PATCH 09/21 — The version-range loops in nfsd_acl_init_request() test nfsd_support_acl_version(rqstp->rq_vers) instead of nfsd_support_acl_version(i), so "every iteration fails and the function returns rpc_prog_unavail instead of rpc_prog_mismatch."
  • PATCH 11/21 — The BOTH_TIME_SET branch in nfsd_proc_setattr() calls fh_verify() early, causing nfsd_setattr() to skip fh_want_write(), so "notify_change() runs without a mount write reference."
  • PATCH 15/21 — NFSD_A_SOCK_ADDR is declared as bare NLA_BINARY with no minimum length. "A CAP_NET_ADMIN caller can send a 16-byte NFSD_A_SOCK_ADDR with sa_family=AF_INET6, causing a 12-byte OOB read across three consumers."
  • PATCH 17/21 — nfsd_debugfs_init() runs before nfsd4_init_slabs(). If slab allocation fails, "the bare 'return retval' bypasses nfsd_debugfs_exit(), leaving orphan debugfs files with stale fops pointers into the freed module text."
  • PATCH 18/21 — shrinker_register() precedes the DRC hash table bucket initialization. "On weakly-ordered architectures (arm64, ppc), a shrinker scan can observe drc_hashsize before the bucket list heads are initialized, causing a NULL deref in the DRC shrinker callback."

Discussion and status

The v2 posting is entirely self-contained — all 22 messages in this thread within the week window are from Layton himself (the cover letter plus 21 patches). No maintainer or reviewer has yet replied to v2. The only cross-thread context is Chuck Lever's earlier review of the now-dropped localio patch from v1, which prompted the routing change.

This is a bugfix series — no new features, no protocol changes. The fixes range from memory-safety issues (use-after-free, OOB reads, refcount underflow) to logic errors (clock domain mismatch, missing validation, stale state) to initialization ordering problems. Several are particularly noteworthy for their real-world impact: the grace-period DoS (PATCH 12), the netlink information leak (PATCH 01), and the module-text use-after-free on rmmod (PATCH 16).

As of the end of this week's window, the series is awaiting maintainer review. Layton has explicitly requested Chuck Lever's consideration for v7.3.
