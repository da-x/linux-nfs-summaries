nfsd: rejecting out-of-range NFSv3 nseconds — debate over GARBAGE_ARGS vs NFS3ERR_INVAL

A short but pointed thread landed this week around a small bug-fix patch from Synology's Robbie Ko that closes a silent metadata-corruption hole in the NFSv3 server. The whole exchange happened on 2026-06-11, and it ended with Chuck Lever asking for the fix to be reworked rather than applied as posted.

The bug (a real data-corruption path)

The original patch targets svcxdr_decode_nfstime3(), the NFSv3 decoder for the nfstime3 struct. As Ko describes it:

"The NFSv3 nfstime3 decoder svcxdr_decode_nfstime3() accepts the 32-bit nseconds field from the wire without validating its range. RFC 1813 does not constrain the value, but a tv_nsec >= NSEC_PER_SEC is not a valid timespec64."

Ko traces the damage concretely: a malicious or buggy client can send a SETATTR carrying an out-of-range nseconds (up to 4294967295), and because timestamp_truncate() does not clamp tv_nsec when the filesystem has nanosecond granularity, the inode atime/mtime setters store it verbatim. The result is silent on-disk corruption:

"ext4's ext4_encode_extra_time() shifts tv_nsec left by EXT4_EPOCH_BITS, which overflows the 32-bit extra field and clobbers the seconds-epoch bits, so the stored seconds (year) are wrong on read-back. XFS with bigtime mis-stores the timestamp for the same reason. This is silent, with no WARN_ON anywhere in the path to catch it."

This is framed as a bug fix — specifically a server-side validation gap that lets an un-normalized nanosecond value corrupt stored timestamps. The NFSv4 side already guards against this (nfsd4_decode_nfstime4() rejects such values with NFS4ERR_INVAL); NFSv3 had no equivalent check.

First reaction: conceptually fine, but tidy up the constant

Jeff Layton's reply was brief and supportive of the direction:

"Conceptually this looks fine, but it should use the named constant (NSEC_PER_SEC). Also, does v2 have a similar issue?"

Layton's two asks are minor: use NSEC_PER_SEC rather than a magic number, and check whether NFSv2 has an analogous hole.

Chuck Lever's reservation: the error path is wrong

The substantive pushback came from Chuck Lever, who agreed with the diagnosis but objected to how the patch rejects the request. His argument is that failing the XDR decode produces the wrong on-wire error:

"Returning false from svcxdr_decode_nfstime3() turns into SVC_GARBAGE, so the client gets an RPC-level GARBAGE_ARGS. But an nseconds of 4294967295 is perfectly well-formed XDR: it decodes cleanly into a valid uint32. Nothing about the request failed to parse."

Lever argues the RFC-aligned response is NFS3ERR_INVAL, returned from the SETATTR proc, not GARBAGE_ARGS from the XDR layer:

"The IMPLEMENTATION notes describe NFS3ERR_INVAL as the error for a value the server 'can not store ... in its own representation' -- an out-of-range nanoseconds is exactly that class of problem."

He also corrects the commit message's framing, noting the v3 patch maps to EIO while the v4 path maps to EINVAL:

"So the two paths produce different errors on the wire, and the commit message's claim that this 'mirrors the NFSv4 behavior' is not accurate."

The wrinkle: sattrguard3.obj_ctime

Lever adds a second, more subtle problem with rejecting at decode time. svcxdr_decode_nfstime3() is also used to decode sattrguard3.obj_ctime, which is a comparison value, not a stored one:

"The guard is a comparison value, not a value to be stored; RFC 1813 says a guard that does not match the object's ctime yields NFS3ERR_NOT_SYNC. An out-of-range guard ctime simply never matches, so the protocol-correct outcome there is NOT_SYNC. Rejecting it at decode converts a legitimate stale-guard case into 'your RPC is garbage.'"

Where things stand

The thread closed with Lever asking for a rework rather than approval:

"So let's rework this fix to handle the range check in the proc functions and return appropriate NFSv3 protocol status codes rather than rejecting the RPC Call outright."

Bottom line: the underlying bug — an unvalidated nseconds silently corrupting ext4/XFS on-disk timestamps via the SETATTR path — is real and agreed to need fixing. But the as-posted patch is not accepted: it rejects a well-formed XDR request with GARBAGE_ARGS (→ EIO) instead of the protocol-correct NFS3ERR_INVAL, misrepresents parity with NFSv4, and would mishandle the sattrguard3.obj_ctime guard case. The expected next step is a v2 that moves the range check into the proc functions and returns proper NFSv3 status codes, plus an answer to Layton's question about whether NFSv2 has a similar gap.
