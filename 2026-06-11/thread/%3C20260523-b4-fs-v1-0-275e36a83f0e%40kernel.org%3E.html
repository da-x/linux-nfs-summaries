jbd2/kmalloc follow-up: the kvalloc() detour, Wilcox's "please don't try to help," and Rapoport on the road to retiring __get_free_pages()

Summary

jbd2 __get_free_pages() → kmalloc(): post-merge follow-up — the kvalloc() detour, Wilcox's "please don't try to help," and Rapoport on the road to retiring __get_free_pages()

Type: API modernization / cleanup (with a side-conversation about memory-allocator design). Not a new feature or protocol change. Status: The underlying 17-patch series was already merged into vfs-7.2.misc on May 27; this week's activity is the tail end of the technical follow-up on [PATCH 10/17] (jbd2) plus a clarifying exchange about the long-term goal of the broader effort.

Bridge to prior weeks

The 17-patch "[PATCH 00/17] fs: replace __get_free_pages() call with kmalloc()" series was posted by Mike Rapoport on May 23 and applied by Christian Brauner to vfs-7.2.misc on May 27 (week ending 2026-05-28). Two patches touched the NFS client — [PATCH 05/17] swapping a temporary page for kmalloc() in nfs_show_devname(), and [PATCH 06/17] removing genuinely dead page/page2 buffers in the NFSv4 transport-replacement path (nfs4_replace_transport()). The following week (ending 2026-06-04) saw Theodore Ts'o reopen the jbd2 patch to probe allocator semantics, with Rapoport confirming there is no memory overhead at order == 1 and that kmalloc() ≥ PAGE_SIZE always returns contiguous, page-aligned memory. Wilcox pushed back on Ts'o's idea of a kmalloc→vmalloc fallback, arguing allocator deficiencies should be fixed at the source. This week picks up from there.

This week's discussion (June 5–11)

The "kvalloc()" detour — and its correction

The jbd2 design question Ts'o had raised last week — whether a filesystem could ask for physically contiguous pages with a fallback to vmalloc-style allocation — resurfaced when David Laight chimed in, quoting Ts'o's suggestion of using kmalloc() with flags to prevent forced reclaim/compaction and falling back to vmalloc():

"There is already kvalloc(). I'm not sure how hard that tries to get kmalloc() to succeed."

This was a misremembering of the API name. Uladzislau Rezki quickly corrected him:

"I assume you mean kvmalloc()? kvalloc() is something unknown to me."

The correction was well-taken — kvmalloc() is the real kernel API that attempts kmalloc() first and falls back to vmalloc() on failure, which is exactly the pattern Ts'o had been groping toward.

Wilcox shuts down the fallback idea (again)

Matthew Wilcox responded to Laight's suggestion with characteristic bluntness:

"Please don't try to help."

This was a pointed reference to the fact that kvmalloc() — while it exists — is precisely the kind of fallback mechanism Wilcox had argued against in his previous week's message. His position, restated last week, was that callers should not build their own kmalloc→vmalloc fallbacks; instead, allocator deficiencies should be fixed at the source via higher-level allocation APIs. The "Please don't try to help" remark effectively closed this sub-thread: the jbd2 conversion as merged is fine, and no further changes are needed.

Zi Yan asks about the end goal

Separately from the jbd2-specific debate, Zi Yan (NVIDIA) asked Rapoport a broader question about the 17-patch series:

"Is the goal to get rid of __get_free_page(s)()?"

This was a fair question given that the cover letter described the series as "a (small) part of larger work." Rapoport answered definitively on June 11:

"Yes, eventually."

He then provided useful context on how the effort evolved:

"My initial intention a few month ago was to remove the ugly casts, but then willy pointed out that Linus objected to something like this and it looks like more than a decade old technical debt."

Rapoport laid out the practical scope of the remaining work:

"Since there are more than 600 or those it will take a while to convert suitable gfp calls to kmalloc. Afterwards we can re-evaluate what APIs we want to provide for allocations that must have actual pages."

This is significant because it signals that the kernel community is committed to a multi-release effort to retire direct page allocator calls, with the end state being a cleaner API boundary between "I need a slab object" and "I genuinely need raw pages." The reference to Linus's objection (linked in Rapoport's message) underscores that this is not merely cosmetic — it addresses a longstanding design wart in the kernel's memory allocation layer.

Key takeaways

  • The jbd2 sub-thread is effectively closed. The kvmalloc()/kvalloc() naming mix-up was corrected, and Wilcox's "Please don't try to help" put a firm stop to any further discussion of fallback paths for the jbd2 patch. The conversion as merged stands.
  • The broader goal is confirmed: Rapoport explicitly stated that the end goal is to eliminate __get_free_page(s)() from the kernel, with 600+ call sites still to convert. This is a multi-release effort, not a one-shot cleanup.
  • Design direction clarified: After the bulk conversion is done, the community will "re-evaluate what APIs we want to provide for allocations that must have actual pages." This suggests future work on higher-level allocation APIs (in the direction Wilcox sketched last week) rather than ad-hoc fallbacks in individual callers.

Relevance to NFS client development

The direct NFS impact was last week's merge, but this week reinforces its safety and places it in a larger context:

  • The kmalloc()-based allocations now in nfs_show_devname() (PATCH 05/17) and the cleaned-up nfs4_replace_transport() (PATCH 06/17) rest on the same allocator guarantees Rapoport confirmed last week — no memory overhead at order == 1, contiguous page-aligned memory for sizes ≥ PAGE_SIZE.
  • The confirmed long-term goal of retiring __get_free_pages() means NFS client code that still uses direct page allocator calls (there are several in the I/O and transport paths) will eventually need to be converted as well. The 600+ call sites Rapoport cited include filesystem and network stack code, so NFS developers should expect follow-up conversion patches in future merge windows.
  • Wilcox's guiding principle — prefer fixing the allocator over sprinkling fallback paths through caller code — is a useful heuristic for any future NFS client memory-allocation changes. If an allocation pattern in the NFS client feels like it needs a kmalloc→vmalloc fallback, the right response is likely to fix the allocator or use a higher-level API, not to build the fallback inline.
