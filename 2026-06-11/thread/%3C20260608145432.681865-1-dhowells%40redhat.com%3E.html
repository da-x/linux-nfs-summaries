netfs bvecq v3: 22-patch series rebased to -rc7, addressing prior review feedback

Summary

netfs bvecq Series (v3): Rebased and Resubmitted for VFS Tree

Overview

On June 8, David Howells submitted version 3 of his 22-patch series to replace folio_queue, rolling_buffer, and ITER_FOLIOQ with a new segmented chain of bio_vec[] arrays (bvecq) in netfslib. This is the third iteration of work that began as an RFC in late March, was formally submitted as a 26-patch series on March 26, and received reviews from Paulo Alcantara and integration conflict reports from Stefan Metzmacher in early April.

"Could you add these patches to the VFS tree for next?" — David Howells

The series is classified as a major feature/refactoring with embedded bug fixes. It touches netfslib, cachefiles, AFS, CIFS, 9P, Ceph, NFS fscache integration, the mm readahead subsystem, and core iov_iter infrastructure. While the NFS client itself is not directly modified beyond fscache integration updates in fs/nfs/fscache.c, the underlying netfslib changes will affect all network filesystems leveraging this infrastructure for buffered and direct I/O operations.

Changes from v2 to v3

The cover letter documents four specific changes since the previous version:

"ver #3)

  • Rebased to -rc7 as the patches wouldn't apply for Christian.
  • Prepended a fix for a warning from generic/464 (the problem also exists upstream, just not the warning).
  • Renamed kmap_local_bvec() to bvec_kmap_partial() as requested by Christoph.
  • Adjusted smbdirect patch descriptions as requested by Stefan Metzmacher."

This represents a direct response to prior review feedback: the rebase addresses Christian Brauner's (VFS maintainer) inability to apply the patches, the rename responds to Christoph Hellwig's naming preference, and the smbdirect description adjustments address Stefan Metzmacher's earlier integration concerns. The series has also been trimmed from 26 patches to 22, with several bug fixes that were previously embedded in the series now posted separately (referenced as having been "split out" in v2).

Key Bug Fix: Write-Streaming and fscache Interaction

The first patch in the series addresses a correctness bug reported by Marc Dionne that triggers a warning from the generic/464 xfstest:

"Unfortunately, the test netfs_perform_write() uses isn't correct because it doesn't take into account the fact that the object lookup is asynchronous and farmed off to a work queue, so there's a short window in which the cache is doing a lookup but the test fails because the answer is undefined." — David Howells

The fix changes the condition for suppressing write-streaming from checking whether the fscache cookie is "enabled" to checking whether FSCACHE_COOKIE_IS_CACHING is set:

"Fix this by changing the condition to whether FSCACHE_COOKIE_IS_CACHING is set on a cookie rather than whether the cookie is marked enabled. Note that this is really just a hint as to whether we allow write streaming or not and no other aspects of the cookie or cache object are accessed." — David Howells

This is significant for NFS clients using fscache (e.g., with the cachefiles daemon), as it prevents a race condition where partial folio writes could be issued to the cache without proper DIO alignment during the async object lookup window.

Architectural Changes: The bvecq Model

The core of the series introduces struct bvecq, a segmented chain of bio_vec[] arrays that replaces the monolithic folio_queue. Howells explains the design rationale:

"The kernel file I/O subsystem seems to be moving towards consolidating on the use of bio_vec arrays, so embrace this by moving netfslib to keep track of its buffers for buffered I/O in bio_vec[] form." — David Howells

"Netfslib already uses a bio_vec[] to handle unbuffered/DIO, so the number of different buffering schemes used can be reduced to just a single one." — David Howells

"Always send an entire filesystem RPC request message to a TCP socket with single kernel_sendmsg() call as this is faster, more efficient and doesn't require the use of corking as it puts the entire transmission loop inside of a single tcp_sendmsg()." — David Howells

The bvecq structure supports:

  • Linked segments (next/prev) in a NULL-terminated linear list, enabling arbitrary gluing of protocol headers/trailers
  • File position tracking (fpos, discontig) for sparse I/O patterns (relevant to Ceph)
  • Reference counting for safe buffer slice sharing between subrequests
  • Memory type flags (BVECQ_MEM_EXTERNAL, BVECQ_MEM_PAGECACHE, BVECQ_MEM_GUP, BVECQ_MEM_ALLOCED) controlling disposal semantics

A new iterator type ITER_BVECQ is added to walk these chains, intended to replace ITER_FOLIOQ (and eventually ITER_XARRAY).

"This allows an indefinite quantity of elements to be handled and allows things like network filesystems and crypto drivers to glue bits on the ends without having to reallocate the array." — David Howells

Buffer Management: Three-Cursor Model

The series introduces a three-cursor model for buffer tracking in netfs_io_request:

"Buffer tracking is managed with three cursors: The load_cursor, at which new folios are added as we go; the dispatch_cursor, at which new subrequests' buffers start when they're created; and the collect_cursor, the point at which folios are unlocked." — David Howells

The final patch (22/22) merges the ->prepare_read()/->issue_read() (and write variants) into a single callback, fundamentally changing how filesystems interact with netfslib:

"netfs now accumulates buffers and attaches them to each stream when they become valid for that stream, then flushes the stream when a limit or a boundary is hit. The issuing code in netfs then loops around creating and issuing subrequests without calling a separate prepare stage." — David Howells

"The filesystem (or cache) then gets to take a slice of the master bvec chain as its I/O buffer for each subrequest, including discontiguities if it can support a sparse/vectored RPC (as Ceph can)." — David Howells

Cachefiles Improvements

Patch 02/22 reworks cachefiles to avoid relying on the backing filesystem's storage map (SEEK_DATA/HOLE) for the most common case of contiguous, progressively-written files:

"The most common write case, in which the application does { open(O_TRUNC); write(); write(); ... write(); close(); } where each write follows directly on from the previous and leaves no gaps in the file is reasonably easy to detect and can be noted in the primary xattr as CACHEFILES_CONTENT_ALL." — David Howells

"In this specific case, given that it is known that there are no holes in the file, there's no need to call SEEK_DATA/HOLE or use any other mechanism to track the contents. That speeds things up enormously." — David Howells

This is a significant performance improvement for NFS clients using fscache, as it eliminates two seek operations per cache read subrequest in the common case.

CIFS and AFS Integration

The series updates both CIFS and AFS to use bvecq:

  • AFS: Directory content is now held in a bvecq rather than a folio_queue Patch 11/22
  • CIFS: Encryption buffering switches to bvecq Patch 12/22
  • SMB Direct RDMA: Gains ITER_BVECQ support and loses ITER_FOLIOQ support Patches 13/22, 15/22

Notably, the smbdirect patches now carry Acked-by: Stefan Metzmacher, indicating that the integration conflicts raised in April have been resolved.

Performance and Correctness Improvements

Several patches address performance and correctness:

  • Bulk readahead loading Patch 05/22: All VM-provided folios are loaded into the queue up front in a single RCU read lock section, rather than piecemeal. "This simplifies the buffer handling later and isn't noticeably slower as the xarray doesn't need to be modified and the folios are all already pre-locked."

  • Progress reporting threshold Patch 21/22: Sets a minimum trigger of 256KiB for waking the collector thread, preventing excessive wakeups with small folios. Also fixes the base point calculation: "fix the base to be the stream collection point, not the point at which the collector has cleaned up to (which is currently 0 until something has been collected)."

  • Over-read detection Patch 20/22: Adds a check in read subrequest termination to detect more data being read than was requested, with a new tracepoint for debugging.

Future Work Announced

Howells outlines two additional work items not included in this branch:

"(1) Make it so that a filesystem can be given a copy of a subchain which it can then tack header and trailer protocol elements upon to form a single message (I have this working for cifs) and even join copies together with intervening protocol elements to form compounds."

"(2) Make it so that a filesystem can 'splice' out the contents of the TCP receive queue into a bvecq chain. This allows the socket lock to be dropped much more quickly and the copying of data read to the destination buffers to happen without the lock. I have this working for cifs too."

Resolution Status

As of this week's window, no replies or reviews have been posted in response to v3. The series is addressed to Christian Brauner (VFS maintainer) with a direct request for inclusion "for next." The prior round of reviews from Paulo Alcantara (Reviewed-by tags on core patches) and the resolution of Stefan Metzmacher's integration concerns (evidenced by his Acked-by tags on the smbdirect patches in this v3) suggest the series is well-positioned for merge.

Conclusion

This v3 submission represents a mature, review-incorporated iteration of one of the most significant netfslib refactors in recent years. The reduction from 26 to 22 patches (with fixes split out separately), the rebase to -rc7, and the incorporation of naming and description feedback all signal readiness for VFS tree inclusion. For NFS client developers, the key impacts are: improved fscache performance via CACHEFILES_CONTENT_ALL, a fixed race condition in write-streaming with fscache, and a unified buffer management model that will simplify future protocol-level optimizations (single-sendmsg RPC transmission, socket-lock-free receive splicing).
