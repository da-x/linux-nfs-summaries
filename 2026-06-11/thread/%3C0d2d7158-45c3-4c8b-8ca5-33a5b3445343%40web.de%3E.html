Coccinelle-driven cleanup: common error handling in nfs_alloc_server()

Summary

NFS client cleanup: shared error-handling label in nfs_alloc_server()

This week's activity on this thread consisted of a single, self-contained patch posted to linux-nfs by long-time cleanup contributor Markus Elfring. It is squarely in the NFS client domain (fs/nfs/client.c) and is best characterized as a code-cleanup / robustness refactor rather than a new feature, protocol change, or functional bug fix — though it touches the error path of server allocation, which is the kind of code where subtle leaks can hide.

The patch

Elfring's patch was posted on 2026-06-10 and targets nfs_alloc_server() in fs/nfs/client.c, with a modest footprint:

"Use an additional label so that a bit of exception handling can be better reused at the end of this function implementation."

"This issue was detected by using the Coccinelle software."

The change is 8 insertions and 8 deletions across one file — a classic mechanical refactor in which a duplicated goto/cleanup sequence is consolidated behind an extra label so that multiple failure branches funnel into a single tail of exception handling. The motivation, as Elfring notes, was the Coccinelle static-analysis toolchain, which flags patterns where error paths could be unified.

Context and significance

This is not a one-off: Elfring posted sibling patches in the same window with the identical "Use common error handling code" framing — e.g., for nfs_sysfs_init() and (on the server side) svc_export_alloc() in nfsd. That makes this part of a broader, Coccinelle-driven campaign to tidy up duplicated cleanup labels across the NFS client and server trees.

From an NFS-client-development standpoint, the value is incremental but real: nfs_alloc_server() sits on the mount path where a struct nfs_server is created, so its error handling must reliably unwind partial allocations. Consolidating the tail of that function reduces the chance that a future change adds a new failure branch and forgets one of the duplicated cleanup steps — a recurring source of subtle resource leaks in this file.

Status

As of the end of the reporting window (2026-06-11), the patch had been posted but no maintainer review, ack, or commit is visible in-thread yet. The discussion has not evolved beyond the initial submission; there are no objections, no design debate, and no follow-up revisions this week. It remains an open, low-risk cleanup awaiting triage by the NFS client maintainers.

Bottom line

A small, tool-driven robustness patch to the NFS client's server-allocation error path — part of a wider Coccinelle sweep of duplicated exception-handling code across nfs and nfsd. No functional behavior change is claimed; the benefit is cleaner, more maintainable cleanup logic on a critical mount-path function.
