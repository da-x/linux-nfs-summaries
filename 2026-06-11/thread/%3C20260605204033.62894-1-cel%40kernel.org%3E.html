xprtrdma: Convert Send Buffer Free List to llist for Reduced Lock Contention

Summary

xprtrdma: Convert Send Buffer Free List to llist — Reducing Spinlock Contention on the NFS/RDMA Client

Classification: Performance improvement / lock contention fix (client-side xprtrdma over NFS-over-RDMA)

Overview

This thread consists of a single patch posted by Chuck Lever on June 5, with no replies in this week's window. The patch targets a well-understood scalability bottleneck in the NFS/RDMA client: spinlock contention on rb_lock between the request submission path and the transport completion path when managing the send buffer free list. It is a focused, self-contained change that modernizes an internal data structure to eliminate lock acquisition on the hot return path.

The Patch

In xprtrdma: Convert send buffer free list to llist, Lever identified the problem precisely:

"rpcrdma_buffer_get() and rpcrdma_buffer_put() both take rb_lock to pop/push from the rb_send_bufs free list. Under high I/O concurrency (e.g., nconnect=N with small random writes), this spinlock is contended between the request submission path and the transport completion path."

The fix replaces the traditional list_head with an llist_head (the kernel's lockless singly-linked list):

"Replace the list_head with an llist_head. The put side uses lockless llist_add(), which is safe for concurrent producers. The get side retains the spinlock to satisfy the llist single-consumer contract portably; submitters continue to serialize there. Completion handlers returning buffers no longer contend on rb_lock, eliminating contention on the return path."

This is a classic producer-consumer pattern: multiple completion handlers (producers) can concurrently push freed send buffers onto the list without any lock, while a single consumer (the submission path) pops them under the existing spinlock. The net effect is that the most frequent operation — returning a buffer after an RDMA send completes — becomes completely lock-free.

Design Rationale and Precedent

Lever was careful to justify why rb_lock is retained on the get side rather than going fully lockless, and drew on existing code in the same structure:

"rb_lock remains for the MR free list and the tracking lists used during setup and teardown. rb_free_reps already uses llist_head, so the llist idiom is established in this structure."

He then made an important distinction about the locking model versus the data structure:

"The precedent is the data structure, not the locking: rb_free_reps serializes its single consumer through the re_receiving gate in rpcrdma_post_recvs, whereas rb_send_bufs serializes its consumer with rb_lock. Both satisfy the llist single-consumer contract."

This shows that the conversion is a natural evolution of an already-established pattern within rpc_rdma_priv, not an ad-hoc choice. The rb_free_reps list (for receive buffers) had previously been converted to llist_head using a different consumer-serialization mechanism; this patch extends the same data structure idiom to the send buffer pool with a simpler, more conventional spinlock-based consumer gate.

Context: NFS/RDMA Client Scalability Work

This patch is part of a broader effort by Lever and the Oracle NFS team to improve scalability of the xprtrdma client under high-concurrency workloads. The mention of "nconnect=N with small random writes" points directly to the multi-connection (NFSv4.1+ session trunking) feature that allows a single NFS client to open multiple RDMA connections to a server, dramatically increasing I/O parallelism. With more concurrent operations in flight, every per-transport lock becomes a scaling bottleneck.

The change is small — 18 insertions and 22 deletions across verbs.c and xprt_rdma.h — but targets a code path that executes on every single RDMA send completion, making it one of the hottest spots in the client under sustained I/O.

Current Status

As of the end of this week's window (June 12), the patch has been posted but has not yet received review comments or an ack from Trond Myklebust or other maintainers. No follow-up revisions have appeared. Given the small scope and clear rationale, it is likely to be picked up in the next merge window if no objections are raised.
