CB_NOTIFY Directory Delegation: v6 NFSD Series Posted, Review Continues

Overview

This week the long-running CB_NOTIFY directory-delegation thread reached its next milestone: Jeff Layton posted the v6 NFSD series on June 11 — a 20-patch set (down from 21 in v5, with the earlier fix patches folded into their respective commits) that adds RFC8881bis CB_NOTIFY callback support to Linux nfsd for directory delegations. The series is explicitly targeted at v7.3, continuing the punt Chuck Lever established when he began reviewing v4 last week.

This is a new protocol feature — not a bug fix — but the v6 repost itself carries several important bug fixes that were discovered during Lever's in-order review of v5 last week, and Lever immediately resumed his line-by-line scrutiny with a new finding on patch 02/20.

Bridge from Prior Weeks

As summarized last week, Lever had completed a deep-dive review of v5 patches 04–10, surfacing three concrete bugs (a rename TOCTOU race, an RCU use-after-free on fi_deleg_file, and a missing lease-type check) plus an architectural XDR debate that was resolved in Layton's favor via private discussion. The v6 repost is the direct product of that review: all of those findings are now folded into their respective patches.

Key Technical Arguments

The v6 repost — what changed

Layton opened with a terse but telling summary: "This version of the patchset fixes up yet more problems that Sashiko and Chuck flagged during review. Progress!" He reiterated his gating condition for upstream merge:

"They seem to work fine with those tests, but I don't think we'll want to merge these until we have a complete client-side implementation to test against."

The v6 changelog confirms the folded-in fixes from last week's review:

  • Tightened RCU handling on fi_deleg_file (the UAF Lever flagged) — now with a detailed commit message explaining the race: "Concurrent accesses from workqueue callbacks -- such as CB_NOTIFY -- can dereference a NULL pointer if they race with this teardown." The patch also fixes an error-path lease leak that would have caused "a use-after-free once the leaked lease is later broken."
  • Rename name snapshot (the TOCTOU bug) — now "take snapshot of new dentry name when creating event" rather than at callback-prepare time.
  • nfsd_fsnotify_recalc_mask() moved to filecache.c per Lever's argument that it "is accessing and modifying the internals of an nfsd_file."
  • Encoding failure now triggers delegation recall — a new safety behavior: if CB_NOTIFY encoding fails, the server recalls the affected delegation rather than dropping the event silently.
  • New nfm_recalc_mutex on the fsnotify mark to serialize concurrent recalculation from parallel delegation add/remove operations.

Patch 02/20 — Lever's new XDR finding

Lever resumed review within hours of the v6 posting, flagging a wire-safety issue in the regenerated XDR files:

"This value can be leaked onto the wire. The basic enum encoder checks that these values are part of the .x before sticking them on the wire."

The specific problem: NFS4ERR_FIRST_FREE (used to determine the numeric value for NFSERR_EOF) is a hand-rolled constant not present in the .x grammar file, so the xdrgen enum encoder's validation would reject it. Lever suggested an interim fix modeled on lockd's internal error codes:

"A better interim approach might be to select an impossible value for NFSERR_EOF, as is done for the internal NLM error status codes."

He also made a structural request about pragma public directives:

"Let's add the 'pragma public' directives in the patches where they are first needed, instead of here. As subsequent patches are modified, the need for these directives might vanish."

This is a forward-looking maintainability point — keeping the XDR grammar file minimal until a specific patch actually requires a symbol to be exposed.

Patch 03/20 — spec stability caveat retained

The RFC8881bis flag definitions carry an honest risk acknowledgment that Layton preserved from earlier versions:

"There is some risk here -- RFC8881bis is still a working group document, and has been for years. The changes to directory delegations have been stable for the last year or so however, so the hope is that those parts won't change (much)."

Patch 20/20 — signed filehandle fix in CB_NOTIFY

The final patch contains a subtle but important correctness fix for exports with NFSEXP_SIGN_FH:

"The child filehandle returned in these notifications is composed by setup_notify_fhandle() without going through fh_compose(), so it does not get a MAC appended. On exports configured with NFSEXP_SIGN_FH the client would then get back an unsigned filehandle that fh_verify() rejects as stale."

The fix passes the delegation's export down to setup_notify_fhandle() and appends the MAC via fh_append_mac(), dropping the filehandle attribute entirely if signing fails — "rather than handing out an unusable one." This is directly client-visible: without it, any client holding a directory delegation on a signed-fh export would see spurious stale-filehandle errors.

Evolution of the Discussion

The thread's multi-week arc is now clearly converging:

  1. Week of May 15 — VFS-side patches merged into vfs-7.2.directory.delegations.
  2. Week of May 28 — v4/v5 NFSD series posted; Lever begins review, punts to v7.3.
  3. Week of June 5–11 (prior summary) — Lever's deep-dive review of v5 patches 04–10: rename TOCTOU bug, RCU UAF, lease-type check, XDR architecture debate.
  4. This week (June 11) — v6 repost incorporating all reviewed fixes; Lever immediately resumes with a new XDR enum-leak finding on patch 02/20.

The review is progressing in order and the series is shrinking (21→20 patches) as fixes get folded in rather than appended. The remaining unreviewed territory is patches 11–20, which cover the attribute-encoding infrastructure and the final CB_NOTIFY payload assembly.

Implications for NFS Client Development

  • The signed-filehandle fix (patch 20/20) is client-critical. Any future Linux client implementation of CB_NOTIFY would hit spurious stale-FH errors on NFSEXP_SIGN_FH exports without this server-side fix. This is the kind of bug that only manifests in production configurations and would be extremely difficult to debug from the client side.
  • The encoding-failure-recalls-delegation behavior (new in v6) gives clients a simpler correctness model: if the server can't encode a notification, it will recall the delegation rather than silently dropping events. Client code need not handle "missing notifications" as a normal case.
  • The NOTIFY4_* flags and XDR structures remain the client's first dependency. Anna Schumaker's client tree still needs patch 03/20 (and the regenerated nfs4_1.h) before any client-side CB_NOTIFY decoder can be written. The v7.3 timeline gives both sides roughly a full merge cycle to mature in tandem.
  • Layton's testing caveat is significant: "I don't think we'll want to merge these until we have a complete client-side implementation to test against." This means the server and client will land together, and the client work is on the critical path for this feature reaching production.
