RDMA ib_device_attr int→u32 (v7): Shevchenko's code-style review, Metzmacher's smbdirect ack

Summary

RDMA: ib_device_attr capability fields int→u32 — v7 posted, detailed style review and first Ack

Overview

This week saw the seventh revision of Erni Sri Satya Vennela's (Microsoft) patch series to widen the signed-int capability counter fields in struct ib_device_attr to u32. The v7 posting on June 6 directly addressed the prior week's review feedback from Bart Van Assche, Andy Shevchenko, and David Laight — primarily by dropping min_t() in favor of plain min()/min3() wherever both operands are naturally unsigned. The series is a bug fix / type-correctness cleanup, not a new feature or protocol change.

The week's activity was brisk: Vennela posted v7 on Saturday, Shevchenko delivered a thorough line-by-line code-style review on Tuesday, and Samba's Stefan Metzmacher provided the first formal Ack (for the smbdirect hunks) on Wednesday.

The core defect (unchanged from prior versions)

As Vennela restates in the v7 cover letter:

"The capability counter fields in struct ib_device_attr are declared as signed int, but these values are inherently non-negative. Drivers maintain their cached caps as u32 and assign them directly into these int fields; if a cap exceeds INT_MAX the implicit narrowing yields a negative value visible to the IB core."

The v7 series touches 22 files (107 insertions, 97 deletions) spanning the IB core, ULPs (iSER/iSERt, SRP/SRPT, RTRS, iPOIB), NVMe-oF host/target, RDS, SMBdirect, and the NFS/RDMA stack (net/sunrpc/xprtrdma/verbs.c, frwr_ops.c, svc_rdma_transport.c, plus include/linux/sunrpc/svc_rdma.h).

Key v7 changes over v6

The changelog highlights three categories of fixes:

  1. min_t() elimination: "Drop min_t() in all sites where a plain min() (or min3()) works cleanly" — directly responding to Van Assche's and Laight's prior-week objections.
  2. NVMe host guard: "Guard nvme/host/rdma.c num_inline_segments computation against a device reporting max_send_sge == 0, so the u32 subtract cannot wrap to UINT_MAX."
  3. Format string fixes: "Use %u when printing the newly-u32 capability fields in diagnostic messages."

This week's discussion

Andy Shevchenko: detailed code-style review (June 9)

Shevchenko's reply is the most substantive message of the week — a line-by-line review spanning multiple subsystems. His comments fall into several categories:

1. rounddown_pow_of_two() reinvention (Rxe driver):

"FWIW, this one and below looks like reinvention of rounddown_pow_of_two()."

He flagged the rxe_qp.c pattern 1 << (fls(qattr->max_qp_req_rd_atomic_resc) - 1) as a hand-rolled version of an existing kernel helper. This is a maintainability concern — using the standard helper makes intent clearer and avoids subtle off-by-one bugs.

2. Variable declaration ordering ("xmas tree" convention):

"It seems the order is reversed xmas tree, why not preserving it?"

He called this out twice — in ipoib_cm.c (where u32 max_srq_sge was placed after int i) and in frwr_ops.c (where u32 max_qp_wr preceded int depth, delta). The Linux kernel convention orders declarations from most specific to most general type; Shevchenko is asking for consistency with that.

3. Line-length / formatting:

"Now perfectly a single line" "I believe we can go a few characters over and leave them to be single lines."

Several min() calls that were split across multiple lines in v6 now fit on one line after dropping the min_t() type argument, and Shevchenko suggests keeping them as single lines for readability.

4. Type migration over macro changes (RTRS, NVMe target):

"Can we rather update the type of one of them and use min() instead?" "Same question, can we change type type of variables instead?"

Rather than introducing min3() or nested min() calls to handle mixed-type comparisons, Shevchenko suggests changing the local variable types to match the now-u32 capability fields. This is a cleaner approach: if both operands are u32, plain min() works without any type-cast machinery.

5. ABI concern (SRPT module parameter):

"Theoretically this might break ABI (if somebody uses negative values for anything. I don't think it's the case, but just be informed."

He flagged the change from module_param(srpt_srq_size, int, 0444) to module_param(srpt_srq_size, uint, 0444), noting that a user passing a negative value via sysfs would now get an unexpected large unsigned number. His verdict is reassuring ("I don't think it's the case"), but he wants the author to be aware.

6. Signed arithmetic audit warning (ib_verbs.h):

"Nice, but please check that none of these (and beyond) were not used in signed multiplication or (which is more disasterous) division. Otherwise it might be subtle issues that will be hard to debug."

This is perhaps the most important technical caution in the review. Changing a field from int to u32 changes the semantics of any arithmetic expression involving it: signed overflow is undefined behavior, while unsigned wraps modulo 2³². A division like max_qp_wr / 2 behaves identically for values below INT_MAX, but if any code path performs (int)attr->max_qp * some_factor and the product exceeds INT_MAX, the result silently changes from UB to a wrapped value. Shevchenko is asking Vennela to audit all consumers before merge.

7. Conditional vs ternary (NVMe target):

"Simple conditional might be better"

if (inline_sge_count)
    inline_sge_count--;

He preferred an explicit if over the ternary inline_sge_count ? inline_sge_count - 1 : 0 for clarity.

8. Remaining min_t() in RDS:

"What about this one?"

He pointed out that conn_param->retry_count = min_t(unsigned int, rds_ib_retry_count, 7); still uses min_t() — an oversight since both operands are already unsigned.

Stefan Metzmacher: smbdirect Ack (June 10)

Metzmacher's reply was brief but significant — the first formal acknowledgment on this series:

"Acked-by: Stefan Metzmacher metze@samba.org for the smbdirect changes."

This covers the three fs/smb/smbdirect/ files (accept.c, connect.c, connection.c) where u32 capability fields are consumed when setting up RDMA transport parameters for SMB Direct. The ack confirms that the Samba team has reviewed and approved the type migration on their side of the stack.

Significance for NFS client development

While this series targets the RDMA subsystem broadly, its NFS/RDMA surface is directly relevant to NFS over RDMA clients and servers:

  • xprtrdma/frwr_ops.c: The u32 underflow guard (reordering the bounds check before subtraction in frwr_query_device()) is a genuine correctness fix for the NFS/RDMA client's forward registration work request path. Without it, a device reporting zero max_sge_rd or max_recv_sge could trigger an unsigned underflow, producing an SGE count of UINT_MAX - 1 and causing RDMA transport negotiation to fail. This is the most immediately actionable NFS/RDMA fix in the series.

  • xprtrdma/verbs.c: The min_t(u32, ...) → min(...) change ensures the client's SGE count calculations use consistent unsigned types when negotiating RDMA transport parameters with the server.

  • svc_rdma_transport.c / svc_rdma.h: The server-side NFS/RDMA transport also consumes these capability fields; sc_max_send_sges is now unsigned int, ensuring both sides of the wire handle SGE limits consistently.

  • Shevchenko's signed-arithmetic audit warning applies to all NFS/RDMA code that reads ib_device_attr fields: any existing expression like (int)attrs->max_qp_wr / 2 or attrs->max_srq_wr * some_factor must be verified to behave correctly with unsigned operands. This is a non-trivial audit given the number of consumers.
