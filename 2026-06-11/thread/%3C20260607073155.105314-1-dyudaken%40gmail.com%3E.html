nfs: support FMODE_NOWAIT on O_DIRECT reads (v2)

This week's thread is a new feature patch series from Dylan Yudaken adding FMODE_NOWAIT support to NFS O_DIRECT reads, so that io_uring can issue them inline rather than punting to a background worker. It is the second version of the series; no replies or review comments appeared in the window — the thread consists solely of the three patch messages posted on 2026-06-07.

The problem: io_uring punts NFS O_DIRECT reads

In the cover letter, Yudaken describes the motivation as a performance gap in how io_uring handles NFS direct reads:

"I had noticed that io_uring always punts O_DIRECT NFS reads to a background thread since the file does not advertise FMODE_NOWAIT."

He points out that this is a known pain point with an existing upstream report, noting:

"I do suspect that there are people that would want this fix ([1]). Applying a similar patch on that GitHub issue did give performance gains."

(Reference [1] is liburing issue #1499.)

The proposed change

Yudaken argues the fix is small and self-contained. His read of the NFS codebase:

"looking around suggests a simple change to nfs_start_io_direct is all that is required to properly support this functionality. On the request issue side, it seems everything in NFS is actually run in the background (post this lock change), and the completion codepaths all look to have no similar locking semantics."

The series is split into two patches:

  1. nfs: add nowait version of nfs_start_io_direct — The existing nfs_start_io_direct may block on in-flight operations against the same inode. This patch adds a non-blocking variant that "just returns -EAGAIN if locks could not be taken," touching fs/nfs/internal.h and fs/nfs/io.c.

  2. nfs: expose FMODE_NOWAIT for read-only files — Wires up the new nowait path and advertises FMODE_NOWAIT on the file, but deliberately scoped down:

"I have restricted this to read-only files initially, as the code paths are simpler."

Verification approach

Yudaken is candid about testing limits — he could not measure real performance gains because his local network was the bottleneck. Instead he validated correctness by tracing io_uring events:

"Using a test app ([2]) to issue O_DIRECT io_uring reads calls io_uring_queue_async_work without this patch, while with it the call is skipped and the completion is queued into io_uring directly from nfs_direct_read_completion."

v2 changes

The cover letter notes two fixes carried over from review feedback:

"v2: Suggestions from Sashiko:

  • Handle file flags changing
  • Do not use mapping_empty anymore as it was apparently racy"

This indicates the series had prior review activity (presumably in an earlier week outside this window) and that v2 addresses concerns about dynamic file-flag changes and a racy mapping_empty check.

Status

As of the end of the window, the patch set has no on-list replies — it sits awaiting review. The change is small (67 insertions across four files: fs/nfs/direct.c, fs/nfs/file.c, fs/nfs/internal.h, fs/nfs/io.c) and targets a clear performance win for io_uring workloads doing O_DIRECT reads over NFS, with the conservative read-only scope reducing risk on first submission.
