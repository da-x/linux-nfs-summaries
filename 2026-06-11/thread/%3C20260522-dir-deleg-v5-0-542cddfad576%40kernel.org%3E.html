CB_NOTIFY Directory Delegation: Lever's Deep-Dive Review of v5 Patches 04–10

Overview

This week the CB_NOTIFY directory-delegation thread moved from "series applied" to "serious line-by-line review." Continuing the in-order scrutiny he announced last week (where he punted the series to v7.3), nfsd maintainer Chuck Lever worked through patches 04, 05, 07, 08, 09, and 10 of Jeff Layton's v5 NFSD series, posting seven review messages on June 8 and receiving six responses from Layton on June 10.

The discussion is about a new protocol feature — RFC8881bis CB_NOTIFY callback support for NFSv4 directory delegations — but the review surfaced several genuine bug fixes (a rename time-of-check-to-time-of-use race, an RCU use-after-free, and a missing lease-type check) alongside architectural debates about XDR encoding. Lever is clearly using LLM reviewers ("Sashiko," "gpt-5.5," and "Claude") as a first pass, then validating and extending their findings by hand.

Bridge from Prior Weeks

As summarized last week, Layton posted the 21-patch v5 NFSD series on May 22 (a clean rebase onto Christian Brauner's already-merged VFS directory-delegation patches, with six Sashiko-flagged fixes over v4), and Lever applied it to nfsd-testing on May 23. The review of patch 03/21 began the prior week. This week picks up at patch 04 and runs through patch 10.

Key Technical Arguments, Patch by Patch

Patch 04 — dir lease with an ignore mask

Lever's first message cleared a false positive: both Sashiko and his own gpt-5.5 review flagged that nfsd_get_dir_deleg() reads a response field (gddr_notification[0]) rather than a request field, but he judged it correct — though the commit message must explain why:

"Both Sashiko and my own gpt-5.5 review noted the use of a response field here rather than a request field, but that is a false positive finding. The commit message needs to explain why the use of gddr_notification[0] is correct."

He also flagged an unrelated whitespace cleanup (kernel_setlease(...) reformat) as out of scope: "This last edit appears to be a clean-up that is unrelated to the purpose of the patch."

Patch 05 — fsnotify mark recalculation

Lever asked for rationale over restatement: "This commit message repeats what the diff below says. Can it instead explain why this change is necessary?" He questioned whether nfsd_fsnotify_recalc_mask() should live in fs/nfsd/filecache.c, and supplied an edit removing a now-obsolete kerneldoc note ("does not set up any sort of async notifications").

Layton responded with the actual rationale — "as new delegations are added or removed, the mask of events that nfsd requires from the VFS layer can change, since clients can request notifications of different events" — and folded in the kerneldoc edit. On placement he argued for keeping it static in nfs4state.c ("The only caller is in this file"), but Lever pushed back that the function "is accessing and modifying the internals of an nfsd_file — it contains local knowledge about how the filecache manages fs notifications," so filecache.c is the better home.

Patch 07 — CB_NOTIFY encode/decode linkages (the XDR debate)

This became the week's most substantive architectural exchange. Lever objected to placing a client-side argument encoder in server-side code:

"What is problematic in the longer-term is that this is a client-side encoder (since this is the server's NFSv4 callback client). xdrgen_encode_CB_NOTIFY4args() is an argument encoder, which is client-side functionality, but it resides in fs/nfsd/nfs4xdr_gen.c, which is server-side. Let's not mix these purposes."

He proposed open-coding the top level (stateid, fh, count) and delegating only the per-event complexity to xdrgen_encode_notify4, with a pragma public notify4; in nfs4_1.x. Layton resisted: "I'd really rather not go back to open-coding the encoders and decoders, particularly since CB_NOTIFY has one of the most complex argument structures in the protocol."

Lever clarified the calling-convention distinction — "encode argument" is client-side, "decode argument" server-side, etc., because "the client-side and server-side XDR implementation for the top level arguments and results ... have different calling conventions -- eg, server side wants to see a struct svc_rqst *" — and pointed Layton at his own follow-up patch: "Go look at how I implemented this in the subsequent patch. You can use the xdrgen notify4 encoder, that's where all the complexity is."

Patch 08 — RCU protection of fi_deleg_file (bug fix)

Lever flagged a use-after-free in the error path, suggesting rcu_dereference_protected() "to avoid the Sashiko-reported UAF finding," plus a nit to use RCU_INIT_POINTER(fp->fi_deleg_file, NULL) for consistency. This is a real concurrency bug: fi_deleg_file can be NULLed by put_deleg_file() during delegation teardown while an in-flight CB_NOTIFY workqueue callback still dereferences it.

Patch 09 — data structures (style debate)

Lever nitpicked C++-style comments. Layton pushed back on the checkpatch rule itself, noting "the code is littered with this comment style anyway, including a bunch of the new // SPDX- header comments," and that the cited coding-style document "says nothing about C99 comments. I move that we ignore checkpatch here."

Patch 10 — notification handlers (rename TOCTOU bug + several fixes)

The richest set of findings. Lever posted a long review that included:

  • A serialization fix for the in-flight callback drain — the nfsd4_run_cb_notify(ncn) check must be paired with a spinlock read of ncn->ncn_evt_cnt to avoid missing events queued while the callback was running.
  • A cross-directory rename guard he inserted himself: "FS_RENAME fires on the source directory even for a cross-dir rename ... NOTIFY4_RENAME_ENTRY describes an in-place rename, so reporting it here would advertise a name absent from this directory."
  • A missing lease-type check: without if (fl->fl_lmops != &nfsd_lease_mng_ops) continue;, "the loop treats every lease on the inode as an nfsd delegation unconditionally."
  • KDoc and pr_warn wording cleanups.

Then, in a second message, Lever escalated to what he called the week's most important finding — a time-of-use (TOCTOU) bug in rename name capture, which all three LLM reviewers independently identified:

"nrn_old_entry uses nne->ne_name, which alloc_nfsd_notify_event() copied when fsnotify delivered the rename. nrn_new_entry instead reads the live dentry via take_dentry_name_snapshot() at callback-prepare time, which can run long after the event was queued. ... d_move() reuses the same dentry and rewrites d_name in place, so a second rename of the entry before the queued callback encodes leaves the dget'd ne_dentry carrying the later name. An A->B event then encodes as A->C, and a client holding the directory delegation applies the wrong old->new mapping to its cache."

He explicitly stopped his minor edits here — "This is why I stopped the minor editing here and decided it was time for you to consider restructuring (or not)" — and noted he had not yet reviewed patches 11–21.

Layton's responses were constructive: he confirmed the XDR decision ("Chuck and I had a private discussion and I think we're going to keep this calling xdrgen_encode_CB_NOTIFY4args() for now. I am dropping the WARN_ON_ONCE though"), accepted the rename guard and kdoc fixes, but pushed back on the lease-type check as redundant — "should_notify_deleg() calls nfsd_breaker_owns_lease(), which already checks this before doing anything else" — and was still evaluating the callback-drain serialization ("I'll run it by Claude").

On the TOCTOU bug, Layton agreed and committed to a fix: "That sounds legit. We probably need to snapshot the name sooner, when we create the event. I'll spin something up." He also resolved Lever's open concern about memory exhaustion during restructuring: "if that happens we'll just recall the delegation. That's always the remedy when there are problems here."

Evolution of the Discussion

The thread has now completed a clear three-week arc:

  1. Week of May 15 — VFS-side patches merged into vfs-7.2.directory.delegations.
  2. Week of May 28 — v5 NFSD series posted and applied to nfsd-testing.
  3. This week (June 5–11) — Lever's substantive in-order review of patches 04–10, surfacing one architectural XDR debate (resolved in Layton's favor via a private discussion), three concrete bug fixes (rename TOCTOU, RCU UAF, missing lease-type check), and a batch of commit-message/style cleanups. A v5.x repost incorporating these changes is now clearly the next step before the v7.3 merge window.

Implications for NFS Client Development

Although this is server-side work, it directly shapes the Linux client:

  • The rename TOCTOU bug is a client-visible correctness issue. If left unfixed, a client holding a directory delegation would apply a wrong old→new name mapping to its cache after a rapid double-rename — exactly the kind of silent data-staleness bug that makes CB_NOTIFY dangerous. Fixing it server-side (snapshotting both names at event-creation time) protects every future client implementation.
  • The XDR header is shared. The notify4 encoding path and the NOTIFY4_* flags in nfs4_1.h are the same structures Anna Schumaker's client tree will decode; the decision to keep xdrgen_encode_CB_NOTIFY4args() while using xdrgen_encode_notify4 for the per-event payload affects what the client can expect on the wire.
  • Layton's gating condition still holds: the server code should not merge until a complete client-side implementation exists to test against, and the v7.3 punt gives both sides time to mature in tandem.

Status

  • Open items for next repost: rename-name snapshot fix, RCU UAF fix in the error path, callback-drain serialization (Layton still evaluating), commit-message rationale updates, and the filecache.c placement question.
