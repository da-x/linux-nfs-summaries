RDMA ib_device_attr int→u32 (v6): Author acknowledges all review feedback, v7 promised

Summary

RDMA ib_device_attr int→u32 (v6) — Vennela acknowledges reviewer feedback; v7 in the works

Bridge from prior week

This is a continuation of Erni Sri Satya Vennela's (Microsoft) six-revision patch series to widen the signed-int capability counter fields in struct ib_device_attr to u32. The v6 posting landed on June 1, and during the prior week's window (June 1–2) three reviewers — Bart Van Assche, Andy Shevchenko, and David Laight — each raised distinct but related objections to the series' use of min_t() macros. The prior summary detailed those arguments in depth; this week's activity is entirely the author's response.

This week's discussion (June 6)

All four messages this week come from Vennela, posted within a ~13-minute span on June 6 (06:48–07:01 UTC). Each reply addresses one specific reviewer thread, and together they constitute a comprehensive acknowledgment of every point raised in the prior week. No new technical arguments were introduced; the discussion is at the "author accepts feedback" stage.

Reply to Bart Van Assche (SRP min_t() → unsigned min())

In his reply, Vennela directly addresses Van Assche's June 1 suggestion that the SRP driver hunk should use plain min() with unsigned operands rather than min_t(u32, ...):

"Thankyou for your suggestion, Bart. I'll update this in the next version."

This is a clean acceptance of the specific change: replacing min_t(u32, MAX_SRPT_RQ_SIZE, sdev->device->attrs.max_qp_wr) with min(MAX_SRPT_RQ_SIZE, sdev->device->attrs.max_qp_wr), since both operands are naturally unsigned after the type migration.

Reply to Andy Shevchenko (clamp() and persistent min_t() objection)

In his reply, Vennela acknowledges Shevchenko's reminder that the same min_t() concern was raised against v5:

"Yes. I'll be incorporating those changes in the next version."

Shevchenko had noted: "Ah, I just answered in similar way against v5. I also mentioned clamp() there." Vennela's response confirms he will address both the min_t() cleanup and the clamp() suggestion across the series for v7.

Reply to David Laight (first message: min() argument ordering)

In his reply, Vennela accepts Laight's convention for argument ordering in min() calls:

"Thankyou for your suggestions, David. I'll use min() in the way you suggested in the next version."

This refers to Laight's preference for min(value, bound) over min(bound, value), mirroring the natural reading order of an if (value > bound) check.

Reply to David Laight (second message: min_3(), pointless casts, rtrs-srv hunk)

In his reply, Vennela addresses Laight's more detailed second review, which covered the rtrs-srv hunk and the NVMe target's nested min_t(u32, U8_MAX, ...) pattern. Vennela accepts both points:

"Okay, I'll update this in the next version."

(Regarding the rtrs-srv hunk where Laight noted "The constant is known to be non-negative," meaning plain min() suffices.)

"Okay. I'll use min3 as suggested in the next version and remove unneccesary casts."

This confirms adoption of min_3(a, b, c) over nested min(min(a, b), c) for three-way bounds (as Laight proposed for the NVMe target's param.initiator_depth calculation), plus removal of the gratuitous (u32)U8_MAX casts that Laight flagged as "pointless."

Key technical arguments (carried forward from prior week)

No new technical arguments were introduced this week. The discussion is in its resolution phase, with the author confirming acceptance of all prior-week feedback:

  1. min_t() → plain min(): When both operands are naturally unsigned after the type migration, min_t(u32, a, b) should be replaced with min(a, b). Accepted by Vennela for v7.
  2. min_3() over nested min(): Three-way bounds should use min_3(a, b, c) to avoid preprocessor bloat from nested ternary expansion. Accepted for v7.
  3. Argument ordering: min(value, bound) preferred over min(bound, value). Accepted for v7.
  4. Pointless casts removed: (u32)U8_MAX and similar casts that add no semantic value will be stripped. Accepted for v7.
  5. clamp() consideration: Shevchenko's suggestion to consider clamp() in appropriate places is acknowledged, though the specific application points remain to be determined in v7.

Classification

This remains a bug fix / type-correctness cleanup series, not a new feature or protocol change. The core defect — signed-int capability fields that can silently narrow u32 driver values into negative numbers when exceeding INT_MAX — is unchanged. The NFS/RDMA surface (xprtrdma/verbs.c, frwr_ops.c, svc_rdma_transport.c) contains the most consequential fixes for NFS clients:

  • frwr_ops.c u32 underflow guard: Reordering the bounds check before subtraction prevents an unsigned underflow in the forward registration path. This is a genuine correctness fix for NFS/RDMA clients on devices with unusual (zero) SGE limits.
  • verbs.c type fixes: Ensures SGE count calculations use correct unsigned types during RDMA transport negotiation.

These NFS/RDMA hunks are unlikely to change materially in v7 — the remaining feedback targets SRP, RTRS, and NVMe target code.

Evolution of the discussion

The thread has now completed its sixth revision cycle:

  • v1–v4: Initial type migration, mana driver clamp placement, commit message reframing.
  • v5 (June 1): Mis-targeted to net-next; Shevchenko's "redo this and similar pieces" objection.
  • v6 (June 1): Re-targeted to rdma-next; U8_MAX clamps added; min_t() pattern retained but refined. Three reviewers raised macro hygiene concerns on June 1–2.
  • This week (June 6): Author acknowledges all feedback and commits to a v7 incorporating: unsigned min(), min_3(), argument ordering fixes, cast removal, and clamp() consideration.

Final conclusions

As of the end of this week's window:

  1. All reviewer feedback has been acknowledged. Vennela has explicitly accepted every point raised by Van Assche, Shevchenko, and Laight, with no pushback or disagreement.
  2. A v7 is expected incorporating the mechanical cleanups (unsigned min(), min_3(), argument ordering, cast removal). No v7 has been posted yet as of June 12.
  3. No merge decision has been issued. The series awaits v7 before RDMA maintainers can evaluate it for inclusion.
  4. The NFS/RDMA portions are stable. The frwr_ops.c underflow guard, verbs.c type fixes, and svc_rdma_transport.c corrections are unlikely to change in v7 — the remaining feedback targets non-NFS code paths (SRP, RTRS, NVMe target).
  5. The discussion is converging. With all objections acknowledged and no new technical disputes raised, the path to merge appears clear once v7 addresses the macro hygiene items.
