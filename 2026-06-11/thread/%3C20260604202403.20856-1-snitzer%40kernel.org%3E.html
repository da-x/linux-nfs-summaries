First external reply: DESY's Tigran Mkrtchyan responds to flexfiles NO_IO_THRU_MDS fix

This week's activity (2026-06-05 → 2026-06-11)

This week brought the first reply in this thread since Mike Snitzer posted his two-patch series on 2026-06-04. On June 9, Tigran Mkrtchyan of DESY (Deutsches Elektronen-Synchrotron, a major European HPC facility) replied directly to PATCH 1/2, the patch that teaches ff_layout_{read,write}_pagelist() to honor FF_FLAGS_NO_IO_THRU_MDS when a data-server connect error is fatal:

Tigran Mkrtchyan's reply — "Re: [PATCH 1/2] NFSv4/flexfiles: honor FF_FLAGS_NO_IO_THRU_MDS on fatal DS connect errors"

The reply is addressed specifically to the fatal-DS-connect-error path (patch 1/2) rather than the write-fallback path (patch 2/2), suggesting Mkrtchyan's interest or concern centers on the read/write I/O fallback behavior when a data server becomes unreachable.

Context from prior week

As summarized last week, Snitzer's series is a bug fix for the NFSv4 flexfiles client. The core problem: when FF_FLAGS_NO_IO_THRU_MDS is set on a layout segment (common in single-mirror appliance deployments such as Hammerspace), the kernel was silently routing I/O to the Metadata Server after a fatal DS connect error, violating the flag's contract. Snitzer noted:

"If FF_FLAGS_NO_IO_THRU_MDS flag is set then NFSv4 flexfiles should never fallback to trying to issue IO directly to the MDS."

The fix marks the layout for return and requests PNFS_TRY_AGAIN instead of falling through to MDS I/O, so that "the failure now surfaces cleanly via pnfs_update_layout(), rather than via silent MDS I/O that contradicts the flag."

Significance

Tigran Mkrtchyan is a well-known contributor to NFS testing infrastructure (pynfs) and an active participant in linux-nfs discussions. His reply from DESY — a facility that relies heavily on NFS/flexfiles for HPC workloads — signals that this fix has attracted attention from the user community beyond the original Red Hat/Hammerspace motivation. The fact that he targeted patch 1/2 specifically (the fatal DS connect error path) may reflect operational experience at DESY where transient DS unavailability is a realistic concern in large-scale storage deployments.

Status

As of the end of this reporting window, no further replies have appeared. Snitzer has not yet acknowledged the reply, and there is no sign of a v2 or merge decision. The thread remains open with one external comment pending response.
