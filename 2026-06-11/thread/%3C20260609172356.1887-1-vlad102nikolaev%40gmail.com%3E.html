nfsd stable backport: check svc_proc_register() return (CVE-2025-22026)

Summary

nfsd stable backport: don't ignore the return code of svc_proc_register()

Type: Bug fix (security-related, CVE-2025-22026) — a stable-tree backport to 5.10 and 5.15, not a client-side change but an important nfsd robustness fix.

What happened this week

This short two-message thread is the classic fast-track for a security backport: a patch lands on the list Monday, and the stable maintainer queues it by Wednesday morning.

On June 9, Vladislav Nikolaev posted a backport of Jeff Layton's upstream fix (commit 930b64ca0c51), targeting the 5.10 and 5.15 stable trees. The commit message lays out the bug plainly:

"Currently, nfsd_proc_stat_init() ignores the return value of svc_proc_register(). If the procfile creation fails, then the kernel will WARN when it tries to remove the entry later."

The fix changes nfsd_proc_stat_init() to propagate the same pointer type that svc_proc_register() returns, and updates nfsd_net_init() to check it and abort nfsd_net construction on failure. Nikolaev notes the two realistic failure modes:

"svc_proc_register() can fail if the dentry can't be allocated, or if an identical dentry already exists. The second case is pretty unlikely in the nfsd_net construction codepath, so if this happens, return -ENOMEM."

The patch touches fs/nfsd/nfsctl.c, fs/nfsd/stats.c, and fs/nfsd/stats.h (11 insertions, 4 deletions) and carries Cc: stable@vger.kernel.org # v6.9, with a Reported-by from syzbot — the fuzzer had triggered the WARN path upstream.

Two days later, on June 11, stable maintainer Sasha Levin confirmed acceptance in his reply:

"Queued for 5.15 and 5.10, thanks."

Why it matters

This is a server-side (nfsd) hardening fix rather than a client development item, but it's worth flagging: the ignored return value meant that any failure to create the /proc/fs/nfsd/... stat entry would later produce a kernel WARN on teardown — exactly the kind of latent bug syzbot is built to surface. The CVE assignment (CVE-2025-22026) and the explicit backport to two long-term stable kernels indicate this was treated as a security-relevant fix rather than a cosmetic cleanup.

Conclusion

No discussion or pushback — the patch was queued for both 5.10 and 5.15 within ~36 hours of posting. The thread is effectively closed pending the next stable release.
