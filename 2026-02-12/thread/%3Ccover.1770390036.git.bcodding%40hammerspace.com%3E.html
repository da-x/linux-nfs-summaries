kNFSD Signed Filehandles: Security Hardening Against Guessing Attacks

Summary

This week, Benjamin Coddington posted version 4 of his patch series [PATCH v4 0/3] kNFSD Signed Filehandles cover.1770390036.git.bcodding@hammerspace.com, aiming to harden the Linux NFS server against filehandle guessing attacks.

The Security Problem

Coddington explains that NFS filehandles are "well-formed" (typically consisting of an inode number and generation number) and can be guessed by remote clients. Since holding a valid filehandle allows access to a file regardless of directory permissions, this bypasses standard access controls. He notes:

"Simple testing confirms that the correct generation number can be found within ~1200 minutes using open_by_handle_at() over NFS on a local system..."

The Solution: Signed Filehandles

The proposed solution appends an 8-byte Message Authentication Code (MAC), generated via SIPHASH, to filehandles. This requires:

  1. A secret 128-bit key persisted across reboots.
  2. A new sign_fh export option.

Jeff Layton provided a Reviewed-by for the series, stating: "Nice work, Ben. This looks good to me!" 6789380caa630c8efefce6862c77bf6780af45da.camel@kernel.org.

Critical Bug Fixes Identified During Review

Despite the positive initial reception, Chuck Lever and Coddington identified several significant bugs in the implementation during the review process:

1. Netlink Key Handling (Patch 1/3) Coddington initially used put_unaligned_le64 to copy the key from netlink attributes into the kernel structure. Chuck Lever pointed out this was backwards:

"These two lines write the contents of fh_key->key[0] into the nlattr buffer rather than reading userspace data into the key... The correct form... would be something like: fh_key->key[0] = get_unaligned_le64(nla_data(attr));" 88c1ea24-2223-4a80-afb0-89c7272dd440@app.fastmail.com.

Additionally, both key halves were being read from index [0]. Coddington acknowledged the error: "Yes- thanks Chuck, I really messed this one up.. somehow sending out the wrong version." 35697253-D872-40B1-85F3-3FD707F0E8C6@hammerspace.com. Neil Brown also noted the indexing issue 177068807252.16766.7681820155678057342@noble.neil.brown.name.

A side discussion ensued regarding void pointer arithmetic (nla_data(attr) + 8). Coddington questioned its safety, but Lever confirmed it is a sanctioned GNU extension in the kernel: "Void pointer arithmetic is explicitly sanctioned in the kernel code base." 49ee1e31-6cfa-43f7-ae1a-82dc92073569@app.fastmail.com.

2. Filehandle Decoding Length (Patch 3/3) Lever identified that when verifying a signed filehandle, the data_left variable passed to exportfs_decode_fh_raw() included the 8-byte MAC length. This could confuse filesystem decoders expecting only the raw file ID:

"Does data_left need to be reduced by sizeof(u64) / 4 after MAC verification so that exportfs_decode_fh_raw() receives the correct file ID length?" 3865f8f2-186f-4750-8b6f-1a589723fdf7@app.fastmail.com. Coddington agreed: "Yes, it sure does -- great catch." 80816E5C-3537-4ED8-B261-186C085B517F@hammerspace.com.

3. Error Code Selection Lever questioned whether MAC verification failures should return NFSERR_BADHANDLE or NFSERR_STALE, suggesting the latter might be more semantically appropriate for a handle that is no longer valid due to signing mismatch. Coddington's code currently uses _BADHANDLE.

Conclusion

The series introduces a valuable security feature but requires immediate fixes for the netlink key ingestion logic and filehandle length calculations before it can be merged. The discussion highlights the rigorous review process in NFS development, where even well-intentioned security patches must undergo strict scrutiny for correctness.
