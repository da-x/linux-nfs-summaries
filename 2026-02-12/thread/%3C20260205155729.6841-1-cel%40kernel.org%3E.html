NFSD TCP Scalability RFC: Workqueue Patch Rejected, Kthread Alternative Developed

Summary

NFSD TCP Lock Contention RFC: Workqueue Patch Rejected, Alternative Path Pursued

Classification

Performance optimization / architectural redesign (RFC patch series under review). This thread concerns a seven-patch RFC series aimed at reducing lock contention in the NFSD TCP transport layer. This week's activity centers on feedback regarding the first patch in that series.

Bridge from Prior Week

Last week, Chuck Lever submitted a seven-patch RFC series titled "sunrpc: Reduce lock contention for NFSD TCP sockets," responding to an investigation into knfsd's read IOPS ceiling (approximately 300–400K IOPS regardless of hardware). The series proposed major architectural changes including dedicated TCP receiver threads, flat combining for socket sends, and a workqueue affinity scope fallback mechanism. Patch 1/7 specifically targeted workqueue scalability on single-LLC systems, where all CPUs share a single Last-Level Cache, causing severe contention on the workqueue pool spin lock.

This Week's Activity

On February 6, Chuck Lever provided an update on the fate of Patch 1/7 — the foundational workqueue affinity scope fallback patch:

"Tejun has rejected this one."

This refers to Tejun Heo, the Linux kernel workqueue subsystem maintainer. The rejection means that the generic workqueue infrastructure change proposed in Patch 1/7 will not be merged upstream as-is.

However, Chuck Lever indicated he has developed an alternative approach that addresses the same underlying problem for NFSD specifically:

"I've worked up a patch that replaces svcrdma_wq with a kthread that does not have an issue with the workqueue pool spin lock, and that solves the same issue this one does (for NFSD)."

This alternative strategy abandons the generic workqueue subsystem modification in favor of a more targeted solution: replacing svcrdma_wq (the svcrdma workqueue) with a dedicated kernel thread (kthread). By using a kthread directly, the NFSD/RDMA code path avoids the workqueue pool spin lock contention entirely, sidestepping the need for changes to the core workqueue infrastructure.

Technical Significance

The rejection of Patch 1/7 and Chuck's pivot to a kthread-based solution represent an important evolution in the approach to NFSD scalability:

  1. Generic vs. targeted: The original patch sought to improve workqueue behavior system-wide for all subsystems affected by single-LLC topologies. The alternative focuses specifically on the NFSD/svcrdma code path, trading generality for a more acceptable upstream solution.

  2. Avoiding lock contention at the source: By replacing the workqueue with a kthread, the svcrdma component eliminates its dependency on the contested workqueue pool spin lock — a direct fix rather than a workaround in the workqueue layer.

  3. Remaining patches unaffected: The rejection of Patch 1/7 does not necessarily impact the other six patches in the RFC series (dedicated TCP receiver threads, flat combining, page recycling, etc.), which address different aspects of the NFSD lock contention problem. Those patches remain under community review.

Conclusion

This week marked a pivot point in the NFSD TCP scalability effort. While the generic workqueue affinity scope fallback was rejected by subsystem maintainer Tejun Heo, Chuck Lever has already developed an alternative kthread-based solution for svcrdma that achieves the same goal — eliminating workqueue pool spin lock contention for NFS over RDMA workloads. The broader RFC series addressing TCP receive and transmit path lock contention remains under review, with the community's feedback on those remaining patches yet to be determined.
