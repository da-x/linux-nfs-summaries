NFSD Layout Recall Timeout v9: Final Fixes Incorporated, Awaiting Review

Summary

NFSD: Enforce Layout Recall Timeout — PATCH v9 Posted (Feb 10)

Overview

Discussion type: Bug fix / reliability enhancement for NFS server (NFSD) pNFS layout recall handling.

This week, Dai Ngo posted version 9 of his patch series, [PATCH v9 1/1] NFSD: Enforce timeout on layout recall and integrate lease manager fencing, on February 10. This submission addresses all review feedback from Chuck Lever on the previous version (v8), bringing the patch closer to merge-readiness. No replies were received within this week's window as of the reporting deadline.

Bridge from Prior Weeks

This patch has evolved through nine iterations since early January, addressing a critical server-side reliability issue in pNFS block layout handling. Key milestones from prior weeks include:

  • v5–v6 (Feb 5–6): Fixed reference counting, increased fence retry counts to 20, and incorporated Jeff Layton's suggestion to unlock leases immediately after fencing completes via kernel_setlease() with F_UNLCK.
  • v7 (Feb 7): Changed the default fencing retry policy to "retry forever" in response to Jeff Layton's data corruption concerns, and added a module parameter for admin override. Jeff Layton granted Reviewed-by.
  • v8 (Feb 9): Removed the admin tunable per Chuck Lever's request, implemented exponential back-off for retries, and fixed several code quality issues. However, Chuck Lever identified additional bugs requiring fixes in v9.

Key Technical Changes in v9

Dai Ngo's v9 submission incorporates four specific fixes requested by Chuck Lever during his review of v8:

1. Capped Maximum Fence Retry Delay at 3 Minutes

Chuck Lever had questioned whether an hour-long delay between retries was excessive:

"Assuming you meant 3600 seconds and not 3600 jiffies, is an hour between retries too long? Maybe the maximum should be capped at 3 minutes or something?"

v9 now limits the fence worker's maximum delay to 3 minutes, ensuring that even with exponential back-off, the server does not wait unreasonably long between fencing attempts.

2. Fixed Delay Argument from Seconds to Jiffies

Lever identified a unit conversion bug:

"Since mod_delayed_work() takes jiffies as its third argument, you need a '* HZ' here."

v9 corrects the delay argument to use jiffies rather than seconds when calling mod_delayed_work().

3. Moved INIT_DELAYED_WORK to Allocation Time

For safety and convention, Lever recommended:

"Can this INIT_DELAYED_WORK be moved to nfsd4_alloc_layout_stateid()? INIT at allocation time is more conventional and safer."

v9 moves the delayed work initialization to nfsd4_alloc_layout_stateid(), ensuring the work structure is properly initialized before any use.

4. Replaced Boolean Flag with delayed_work_pending()

Lever noted redundant state tracking:

"Seems like there are two sources of truth about whether a fence is in progress here. Would it make sense to replace ls_fence_inprogress with a call to delayed_work_pending()?"

v9 removes the ls_fence_inprogress boolean and uses delayed_work_pending() instead, eliminating the dual-source-of-truth problem.

Technical Context: The Problem Being Solved

The patch addresses a fundamental reliability issue in NFSD's pNFS block layout support. When a layout conflict triggers a recall, the server must wait for the client to release exclusive access. Without a timeout mechanism, unresponsive or malicious clients can cause excessive nfsd threads to block indefinitely in __break_lease, leading to server starvation.

Dai Ngo summarized the core motivation:

"When a layout conflict triggers a recall, enforcing a timeout is necessary to prevent excessive nfsd threads from being blocked in __break_lease ensuring the server continues servicing incoming requests efficiently."

The solution introduces a new lm_breaker_timedout callback in the VFS lease_manager_operations structure. For NFSD's lease manager, this callback handles layout recall timeouts by triggering SCSI PR (Persistent Reservation) fencing to prevent the unresponsive client from accessing the underlying block device. The conflicting file lease remains on the flc_list until fencing completes, guaranteeing that no other clients can access the file prematurely.

Design Philosophy: Clean Module Boundaries

A recurring theme throughout the patch's evolution has been maintaining clean boundaries between the VFS lease code and NFSD-specific logic. Dai Ngo explained a key design decision:

"I experimented with having the fence worker handle lease disposal after fencing the client. However, this requires the lease code to export the lease_dispose_list function... This approach adds unnecessary complexity and reduces code clarity, as it exposes internal lease code details to the nfsd worker, which should not be the case."

"Instead, the lm_breaker_timedout operation should simply notify the lease code about how to handle a lease that times out during a lease break, rather than directly manipulating the lease list."

Significance for NFS Development

This patch represents an important bug fix and robustness improvement for NFSD's pNFS block layout support:

  • Data safety: The fencing mechanism prevents data corruption when layout recalls time out and the original client still holds exclusive block device access — a critical concern for pNFS block layouts where clients access storage devices directly.
  • Server responsiveness: Enforcing timeouts prevents nfsd thread starvation during layout conflicts, ensuring the server continues servicing incoming requests from all clients.
  • Improved concurrency: The lease-unlocking-after-fencing fix (from v6) reduces blocking time for other clients waiting on conflicting layouts.
  • Operational safety: The default "retry forever" policy (from v7) eliminates the risk of giving up on fencing and exposing the system to data corruption, while the 3-minute delay cap (v9) ensures reasonable retry intervals.
