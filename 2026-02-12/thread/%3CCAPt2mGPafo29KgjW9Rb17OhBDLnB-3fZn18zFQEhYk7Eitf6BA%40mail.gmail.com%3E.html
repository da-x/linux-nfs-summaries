NFS Server refcount_t Underflow: Candidate Patch Partially Mitigates Re-export Crash

Summary

NFS Server refcount_t Underflow: Candidate Patch Does Not Fully Resolve Re-export Crash

Classification: Bug fix (ongoing investigation)

Background (Brief Bridge)

This thread, initiated on December 23, 2025, tracks an ongoing investigation into a kernel crash affecting NFS server (NFSD) re-export deployments running Linux v6.18. The bug manifests as a refcount_t underflow in the NFSv4.1+ session sequence completion path (nfsd4_sequence_done). Daire Byrne reported intermittent crashes after upgrading from v6.4 to v6.18.0 on high-throughput (50 Gbps) re-export servers where NetApp NFSv3 mounts are re-exported as NFSv4 to Linux clients.

In prior weeks, Chuck Lever provided extensive debugging guidance — including ftrace buffer sizing, tracepoint filtering, kprobe instrumentation, and panic timeout extensions — after initial trace data proved either too voluminous or empty. A candidate fix commit (cbfd91d22776, "nfsd: never defer requests during idmap lookup") from Chuck Lever's nfsd-testing branch was identified as potentially relevant to the refcount underflow issue.

This Week's Activity (February 9, 2026)

Candidate Patch Testing Results

On February 9, Daire Byrne provided an update after applying the candidate fix patch across two servers:

"So, our busiest server is now seemingly refusing to crash..." Daire Byrne

However, the results were mixed. While the busiest server appeared stable after applying the patch, a second (lower-load) server still experienced crashes:

"I added the suggested patch ('nfsd: never defer requests during idmap lookup') to a second server (with a lower load) and did record a crash that looked the same as before." Daire Byrne

Debug Tracing Oversight

Unfortunately, Daire Byrne noted that debug tracing was not enabled on the second server at the time of its crash:

"Unfortunately I had forgotten to enable the debug tracing in this case (now corrected)." Daire Byrne

This means no new trace data was captured from the post-patch crash, limiting the diagnostic value of the observation.

Implications for the Fix

The mixed results suggest that the candidate patch may not fully address the root cause:

"But it does suggest that the patch did not address the specific stack trace I am getting sporadically." Daire Byrne

The fact that the busiest server stopped crashing while a lower-load server continued to crash is intriguing — it could indicate that the patch mitigates one code path but not another, or that the bug's manifestation depends on load characteristics in ways not yet understood.

Next Steps

Daire Byrne indicated he is continuing to collect debug information:

"I continue to wait to net some more debug information that I can share." Daire Byrne

With debug tracing now corrected on the second server, future crashes should yield actionable trace data.

Technical Significance

This week's update is notable for several reasons:

  1. Partial mitigation observed: The candidate patch appears to have stabilized the busiest server, suggesting it addresses at least one trigger path for the refcount underflow. This is encouraging but incomplete.

  2. Patch not a silver bullet: The continued crashes on the second server indicate that either (a) the root cause involves multiple code paths, or (b) the patch interacts with load-dependent behavior in unexpected ways.

  3. Debugging challenges persist: The oversight of enabling debug tracing underscores the difficulty of capturing reliable crash data in production environments — even experienced operators can miss configuration steps during incident response.

  4. Investigation remains open: No root cause has been definitively identified, and no fix has been merged into the mainline kernel. The session slot rework from the v6.13/v6.14 timeframe (identified by Chuck Lever as the likely regression window) remains the primary suspect area.

Status

Open — under investigation. The candidate fix (cbfd91d22776) shows partial promise but does not fully resolve the issue. Daire Byrne is awaiting new crash data with debug tracing properly enabled on the second server. No fix has been merged into mainline.
