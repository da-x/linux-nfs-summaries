Proposal for Common xattr Caching Infrastructure

Overview

This week saw the initiation of a discussion on creating a common extended attribute (xattr) caching infrastructure in the Linux kernel, proposed by Miklos Szeredi. The thread focuses on whether a unified layer could benefit network filesystems like NFS and userspace filesystems like FUSE, while addressing skepticism regarding its utility for local filesystems.

Classification: New Feature / Infrastructure Proposal

Key Technical Arguments

The Proposal

Miklos Szeredi opened the discussion by noting the lack of common infrastructure for xattr caching across different filesystems. He outlined existing implementations:

  • mb_cache: Used by ext2/4 for deduplication but deemed unsuitable for FUSE due to its specific design.
  • simple_xattr: Used by tmpfs/kernfs but lacks a shrinker.
  • nfs4_xattr_cache: Used by NFS, which Miklos criticized for using "separate cache tables for each inode," calling this choice "wasteful for the common case of just a couple of xattrs per inode" As mentioned by Miklos Szeredi.

He proposed combining these features into a common utility that handles large multi-page xattrs similarly to file data and stores small values inline, with deduplication of keys, values, and lists.

Skepticism Regarding Local Filesystems

Jan Kara expressed doubt about the practical gains for local filesystems:

"As you write below, accessing xattrs is relatively rare. Also frequently accessed information stored in xattrs (such as ACLs) are generally cached in the layer handling them. Finally, e.g. ext4 ends up caching xattrs in the buffer cache / page cache as any other metadata. So I guess the practical gains from such layer won't be generally big?" As mentioned by Jan Kara

He suggested defining specific workloads to measure potential benefits before proceeding.

Clarification: Network and Userspace Filesystems

Miklos clarified that his primary motivation was not local filesystems but network and userspace filesystems:

"For network fs and userspace fs caching would be a clear win." As mentioned by Miklos Szeredi

He noted that NFS already has an xattr cache, FUSE would benefit significantly, and tmpfs "lives in the cache," providing at least three potential users for a unified layer.

Jan Kara conceded this point:

"OK, I was under the impression you wanted to convert local filesystems as well and there I'm not sure about the benefit. Unifying NFS, fuse and tmpfs would definitely make sense to me." As mentioned by Jan Kara

Real-World Workload Evidence

Amir Goldstein provided concrete evidence of a production workload that would benefit from such caching. He described Samba servers fetching user.DOSATTRIB for every file during readdir operations:

"We have production workloads of Samba server which gets user.DOSATTRIB for every file during readdir (for the Archive/Hidden bits and Creation time). The numbers are quite bad." As mentioned by Amir Goldstein

He further explained that while XFS's buffer cache helps, it is "quite costly to keep a 4K page just for a 32 bytes xattr blob," leading to poor cache retention on file servers with many files. However, he suggested that caching user or trusted xattrs on local filesystems might require application opt-in mechanisms, such as a new flag like AT_GETXATTR_CACHE.

Evolution of the Discussion

  1. Proposal: Miklos Szeredi identified fragmented xattr caching implementations and proposed a unified infrastructure.
  2. Skepticism: Jan Kara questioned the benefit for local filesystems, citing existing buffer/page cache mechanisms.
  3. Clarification: Miklos narrowed the scope to network (NFS) and userspace (FUSE) filesystems, where caching overhead is more significant.
  4. Consensus on Scope: Jan Kara agreed that unifying NFS, FUSE, and tmpfs would make sense.
  5. Workload Validation: Amir Goldstein provided real-world examples (Samba/ksmbd) demonstrating performance issues with current xattr handling, supporting the need for a generic cache layer.

Final Conclusions

  • There is emerging consensus that a common xattr caching infrastructure would benefit NFS, FUSE, and potentially tmpfs.
  • The benefit for local filesystems remains debated, with suggestions that application-specific opt-in mechanisms might be necessary if extended to user/trusted xattrs on local storage.
  • Real-world workloads involving frequent small xattr reads (e.g., Samba) suffer from inefficiencies in current buffer cache usage, validating the need for a specialized cache layer.
  • No immediate patch was proposed; the discussion serves as an LSF/MM/BPF topic to gauge interest and define requirements for future development.

Relevance to NFS Client Development

While this thread is primarily about general kernel infrastructure, it directly impacts NFS client development:

  • The current nfs4_xattr_cache implementation was criticized for its per-inode table design, suggesting potential optimization opportunities in the NFS client's xattr handling.
  • A unified cache layer could simplify NFS client code by leveraging common infrastructure rather than maintaining a bespoke solution.
  • Amir Goldstein's comments on file server workloads highlight performance bottlenecks that NFS clients may encounter when interacting with servers storing extensive user xattrs.
