kNFSD Signed Filehandles: Security Feature and Review Feedback

Summary

kNFSD Signed Filehandles: Security Feature and Review Feedback

This week, Benjamin Coddington posted version 6 of a patch series introducing signed filehandles for the Linux NFS server (kNFSD). This feature aims to harden the server against filehandle guessing attacks. While primarily a server-side development, it significantly impacts the security posture of NFS environments by preventing clients from accessing files via guessed handles.

Technical Context and Motivation

The series addresses a vulnerability where NFS clients can bypass directory permission restrictions by guessing valid filehandles. As Coddington explains in the cover letter:

"Filehandles are easy to guess because they are well-formed... You can simply insert inode numbers and iterate on the generation number. Eventually you'll be able to access the file using open_by_handle_at(2)... Simple testing confirms that the correct generation number can be found within ~1200 minutes using open_by_handle_at() over NFS on a local system."

Unlike local systems where open_by_handle_at requires elevated capabilities, the NFS server must permissively allow remote clients to open by filehandle without verifying the caller's access path. To mitigate this, the proposed solution appends an 8-byte Message Authentication Code (MAC) using SipHash-2-4 to filehandles for exports configured with the sign_fh option.

Patch Series Overview

The v6 series consists of three patches posted on Feb 11:

  1. NFSD: Add a key for signing filehandles Patch 1/3: Introduces netlink interface support for setting a persistent 128-bit signing key.
  2. NFSD/export: Add sign_fh export option Patch 2/3: Adds the sign_fh export flag to signal that filehandles should be signed.
  3. NFSD: Sign filehandles Patch 3/3: Implements the signing and verification logic using SipHash-2-4.

Review and Identified Bugs

Chuck Lever reviewed the series and identified several critical issues in patch 3/3, noting that it appeared identical to v5 despite claims of fixes.

Key Criticisms

Lever highlighted three main problems:

  1. Missing Documentation: A comment was needed to explain why FILEID_ROOT is exempt from signing checks.
  2. Unaddressed Bugs: Previous feedback regarding a data_left bug and the use of magic numbers (sizeof(u64)/4) instead of symbolic constants remained unaddressed.
  3. Potential NULL Pointer Dereference: Lever identified a serious logic error in the error handling path:

"The goto out path when MAC verification fails has an error value problem in the !NOSUBTREECHECK case... nfsd_set_fh_dentry() returns 0 without setting fhp->fh_dentry or fhp->fh_export. The caller __fh_verify() then proceeds with... check_pseudo_root() dereferences exp on its first line... Can this NULL dereference occur for signed exports that also have subtree checking enabled?"

Author Response and Resolution

Benjamin Coddington acknowledged the errors, attributing them to a tooling issue where the wrong patch file was attached.

"I'm really sorry Chuck, I sent the wrong patch here. I am going to resend v6 with the correct 3/3 patch." Response

Chuck Lever responded positively, noting that patches 1/3 and 2/3 were ready for application pending the corrected third patch:

"No worries, it looked to me like a tooling issue because the v6 3/3 diff was exactly the same as v5's. The other two v6 patches in the series are ready to apply IMO, so I'll have a look at the RESEND." Conclusion

Conclusion

This discussion centers on a new security feature for kNFSD rather than a client-side bug fix. The v6 series introduces signed filehandles to prevent guessing attacks, but the final patch contained significant bugs, including a potential kernel crash scenario. The author has committed to resending the corrected patch, with the first two patches of the series already approved for integration.
