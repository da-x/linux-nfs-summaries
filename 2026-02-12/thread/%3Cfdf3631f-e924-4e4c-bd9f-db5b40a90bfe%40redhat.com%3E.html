nfs-utils 2.8.5 Release Tag Inquiry

Summary

This thread, originally initiated by Steve Dickson's nfs-utils 2.8.5 release announcement last week, saw a single reply this week from Debian maintainer Salvatore Bonaccorso. The discussion is purely administrative, concerning the availability of release artifacts in the nfs-utils git repository.

Bridge from Prior Week

Last week (ending 2026-02-05), Steve Dickson announced the release of nfs-utils 2.8.5, a maintenance and feature release headlined by the min-threads parameter for nfsdctl, systemd updates for rpc-statd-notify, and various bug fixes. The prior summary detailed the development cycle leading to this release, including the dynamic threading support and backward compatibility work.

This Week's Activity

On February 9th, Debian maintainer Salvatore Bonaccorso raised a practical concern regarding the release artifacts:

"While 2.8.5 was released, I do not see yet a release commit and tag in the git repository, is this correct?"

This inquiry highlights a common pain point for downstream packagers who rely on git tags to verify and incorporate upstream releases into their distributions. The absence of a visible release tag could cause confusion or delay in packaging workflows.

Classification

This is an administrative discussion regarding release process artifacts — not a new feature, protocol change, or bug fix. It touches on the intersection of upstream development practices and downstream distribution packaging needs.

Significance for NFS Development

While brief, this exchange underscores the importance of proper release hygiene in open-source projects. For distributions like Debian that package nfs-utils, having clear, tagged release commits is essential for reproducible builds and version tracking. The question remains unanswered within this week's window; Steve Dickson's response arrived after the current week's cutoff (on February 14th).
