kNFSD Signed Filehandles: Security Review and Bug Fixes

Summary

kNFSD Signed Filehandles: Hardening Against Guessing Attacks

This week saw the submission of v5 of Benjamin Coddington's patch series to enable signed filehandles in the Linux NFS server (kNFSD) cover letter. The series addresses a security vulnerability where malicious clients can bypass directory permissions by guessing well-formed filehandles (e.g., inode + generation number pairs). By appending an 8-byte Message Authentication Code (MAC) to filehandles, the server ensures that only valid, signed handles are accepted.

Technical Context and Evolution

The series represents a significant evolution from previous "encrypt_fh" postings. Key changes in v5 include switching from encryption to signing (per Eric Biggers' suggestion), fixing NFSEXP_ macros, and refining the userspace key-setting interface via netlink cover letter.

The series consists of three patches:

  1. Adding a 128-bit key for signing filehandles via netlink Patch 1/3.
  2. Adding the sign_fh export option Patch 2/3.
  3. Implementing the siphash-based signing and verification logic Patch 3/3.

Key Technical Arguments and Bug Fixes

Cryptographic Choice: SipHash as a MAC

Chuck Lever raised concerns about terminology, noting that siphash is typically a PRF for hash tables, not a standard MAC Review. Eric Biggers clarified the cryptographic standing:

"PRFs are also MACs, though. So SipHash is also a MAC." Eric Biggers

However, Biggers cautioned that the 64-bit tag size limits forgery resistance to $1$ in $2^{64}$. He suggested that for higher security, HMAC-SHA256 or BLAKE2s with 128-bit tags could be used. Chuck Lever noted the trade-off between performance and longevity:

"We're looking for good performance because file handle verification will be done frequently... I am relying on others to do the math regarding how much forgery protection is needed." Chuck Lever

Benjamin Coddington agreed to update the documentation to reflect Eric's guidance.

Critical Logic Bug in Filehandle Verification

Chuck Lever identified a severe bug in Patch 3/3 where the data_left calculation incorrectly subtracted the MAC size even when signing was disabled:

"When NFSEXP_SIGN_FH is not set, the condition short-circuits to false and the else branch executes, subtracting 2 from data_left even though no MAC was appended... Does the data_left calculation break all non-root filehandle lookups on exports without sign_fh?" Chuck Lever

Benjamin Coddington confirmed the error:

"Oh yeah, I messed this one up bigtime, obvious dumb error - and then of course only tested with 'sign_fh' on the version bump. Good catch." Benjamin Coddington

Security Concern: Tracepoints Logging Keys

Chuck Lever flagged a security risk in Patch 1/3, where the tracepoint logs the actual cryptographic key:

"We need to discuss the security implications of writing sensitive material like the server FH key to the trace log. AFAICT, no other NFSD tracepoint logs cryptographic material." Chuck Lever

Benjamin argued that root-only access and development visibility justified it. Chuck countered that trace files often have default permissions of 644, exposing the key to non-root users:

"Development generally has different needs than deployment and/or support engineering. Security, I'm thinking, is probably the most critical need here." Chuck Lever

The resolution was to hash or redact the key in the tracepoint output. Benjamin concluded:

"I'll probably submit to just do the same crc_hash on it that we do to filehandles, and if we still want to rip out the tracepoint later that's what we can do." Benjamin Coddington

Other Code Quality Issues

  • Error Codes: Chuck Lever suggested using _STALE instead of _BADHANDLE for MAC verification failures to align with documentation Review.
  • Return Value Consistency: fh_verify_mac() and fh_append_mac() used inconsistent return conventions (positive-on-error vs negative-on-error). Chuck Lever requested alignment with surrounding code Review.
  • Comments: A comment was requested to explain why FILEID_ROOT filehandles are exempt from MAC verification Review.

Final Conclusions

The discussion concluded with Benjamin Coddington agreeing to address all raised points:

  1. Fix the data_left logic bug for non-signed exports.
  2. Update documentation to justify SipHash as a MAC per Eric Biggers' citation.
  3. Hash/redact the key in tracepoints to prevent accidental exposure.
  4. Align error codes and return value conventions with existing NFSD code.

This patch series represents a significant security enhancement for NFS server deployments, mitigating filehandle guessing attacks through cryptographic signing. The rigorous review process highlighted the importance of balancing performance (SipHash) with security (tracepoint hygiene, correct logic paths).
