nfs-utils: Signed Filehandle Support (v4)

Summary

nfs-utils: Signed Filehandle Support (v4)

This week, Benjamin Coddington submitted v4 of a two-patch series to nfs-utils introducing support for signed NFS filehandles. This userspace work complements corresponding kernel changes (also v4) that allow the NFS server (kNFSD) to append an 8-byte SipHash Message Authentication Code (MAC) to filehandles, enhancing security against filehandle forgery or manipulation.

Key Technical Arguments and Evolution

The series introduces two main capabilities:

  1. exportfs: Adds a new export option sign_fh, which flags exports to signal that filehandles should be signed with a MAC.
  2. nfsdctl/rpc.nfsd: Adds support for passing an encrypted filehandle key from userspace to the kernel. The key is derived by hashing the contents of a file specified in nfs.conf via fh-key-file=<path> using SHA1, sending the first 16 bytes to the kernel via the NFSD_A_SERVER_FH_KEY netlink attribute.

Jeff Layton reviewed Patch 2/2 and raised concerns about error handling when the kernel does not support signed filehandles (e.g., in a "downgraded kernel" scenario). He suggested:

"I think you should add a --fh-key-file= option to the 'threads' command too."

And regarding the autostart behavior:

"Wouldn't it be better to fail to start if the kernel doesn't support setting a key? The clients are going to end up with stale filehandles in that case, no? I'd hate to mistakenly boot into an old kernel and end up with all of my clients falling over."

Benjamin Coddington clarified the design intent, distinguishing between "upgraded nfs-utils" on an old kernel versus "downgraded kernel" scenarios:

"No.. if the kernel doesn't support setting a key its not giving out any signed filehandles. I guess you're thinking about the 'downgraded kernel' case - while I'm thinking about the 'upgraded nfs-utils' case."

He further explained that the kernel protects against misconfiguration:

"the kernel makes sure not to give out filehandles for exports that have 'sign_fh' but no key, and an export with 'sign_fh' on a downgraded kernel won't export because the option returns an error."

Jeff Layton acknowledged this reasoning:

"You can disregard that. I started typing a comment there and then moved it higher. Yes, I'm OK with autostart succeeding as long as you have a coherent story for the behavior in the case of a kernel downgrade."

Final Conclusions

The discussion concluded with agreement on the following points:

  • The threads command should fail with a hard error if --fh-key-file is specified but the kernel cannot accept it, ensuring interactive users are aware of incompatibilities.
  • For autostart, it is acceptable to succeed even if the kernel does not support signed filehandles, provided that exports configured with sign_fh are rejected by the kernel in such cases, preventing stale or invalid filehandles from being issued to clients.

This series represents a new feature addition to nfs-utils, enabling secure filehandle signing in coordination with kernel-side changes. No bug fixes were discussed in this thread; the focus was entirely on implementing and refining the new functionality.
