nfs-utils: Signed Filehandle Support (v5)

Summary

This week, Benjamin Coddington submitted v5 of a two-patch series to nfs-utils introducing userspace support for signed NFS filehandles cover letter. This work complements the parallel kernel-side v5 series (kNFSD Signed Filehandles) that enables the Linux NFS server to append an 8-byte SipHash Message Authentication Code (MAC) to filehandles, mitigating filehandle guessing attacks.

The v5 userspace series received no replies during this week's window; all three messages were submitted on February 9 with no follow-up discussion yet. However, the changes from v4 to v5 reflect feedback from Jeff Layton's review of the previous version.

Background (Prior Weeks)

In the preceding week (v4), Jeff Layton raised concerns about error handling when the kernel does not support signed filehandles, particularly in "downgraded kernel" scenarios. He requested:

"I think you should add a --fh-key-file= option to the 'threads' command too."

And regarding autostart behavior on older kernels:

"Wouldn't it be better to fail to start if the kernel doesn't support setting a key? The clients are going to end up with stale filehandles in that case, no?"

Benjamin Coddington clarified that the kernel protects against misconfiguration — exports with sign_fh on an unsupported kernel would be rejected. Jeff acknowledged this reasoning, and agreement was reached that the threads command should fail hard if --fh-key-file is specified but the kernel cannot accept it.

Key Technical Changes in v5

The v5 series consists of two patches:

Patch 1/2: exportfs — Add support for export option sign_fh

This patch adds the sign_fh export option to exportfs, allowing administrators to flag specific exports so that filehandles are signed with a MAC Patch 1/2. The implementation touches support/nfs/exports.c, utils/exportfs/exportfs.c, and the man page utils/exportfs/exports.man.

Patch 2/2: nfsdctl/rpc.nfsd — Add support for passing encrypted filehandle key

This patch enables userspace to pass a secret signing key to the kernel. The key is derived by hashing the contents of a file (configured via fh-key-file=<path> in the nfsd section of nfs.conf) using SHA1, and sending the first 16 bytes to the kernel via the NFSD_A_SERVER_FH_KEY netlink attribute Patch 2/2.

Key changes from v4 to v5, as noted in the cover letter:

"Changes on v5:

  • add -k,--fh-key_file= argument to 'nfsdctl threads' command (Jeff Layton)
  • fail if 'nfsdctl threads -k' unsupported by kernel (Jeff Layton)"

The patch also creates a new file support/nfs/fh_key_file.c (79 lines) to handle key file processing, and updates utils/nfsdctl/nfsdctl.c with 57 lines of changes.

Classification

This is a new feature addition to nfs-utils, enabling secure filehandle signing in coordination with kernel-side changes. No bug fixes were discussed within this specific thread; the focus was on implementing and refining the new functionality based on prior review feedback.

Current Status

As of the end of this week's window, the v5 userspace series has been posted but has not yet received replies or further review comments. The parallel kernel-side v5 series underwent substantial review this week, including identification of a critical logic bug in filehandle verification and security concerns about tracepoint logging of cryptographic keys — issues that will likely influence subsequent iterations of both the kernel and userspace patches.
