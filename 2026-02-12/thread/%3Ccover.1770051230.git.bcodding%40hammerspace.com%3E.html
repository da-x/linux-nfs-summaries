nfs-utils Signed Filehandle Support: Error Handling Strategy for Missing Kernel Support

Summary

Discussion type: New feature (NFS server security enhancement) — userspace tooling patch review continuation

This week, the discussion around Benjamin Coddington's nfs-utils signed filehandle support v3 series continued with a single but substantive follow-up from Coddington addressing Jeff Layton's concern about error handling when the kernel lacks support for setting a filehandle signing key.

Bridge from Prior Week

Last week (2026-02-05 summary), Coddington posted the nfs-utils v3 series consisting of two patches: (1) adding the sign_fh export option to exportfs, and (2) adding nfsdctl/rpc.nfsd support for passing the signing key to the kernel via netlink. Chuck Lever flagged an NFSv2 documentation inaccuracy, while Jeff Layton raised two concerns: netlink enumeration ordering conflicts with his own min-threads series, and a backward-compatibility issue where userspace might silently proceed if the kernel doesn't support setting an fh_key. Coddington agreed to address both items.

Key Technical Argument This Week

Soft vs. Hard Error When Kernel Lacks fh_key Support

In his February 6th follow-up, Coddington directly addressed Layton's concern about whether nfsdctl should emit a hard error when the kernel cannot accept the signing key:

"I've kept this as a soft error because the server will refuse to give out filehandles if the key is not set for a 'sign_fh' export. It emits:

[ 76.000602] NFSD: unable to sign filehandles, fh_key not set.

This is a pretty good signal and safer than gating the problem in userspace."

Coddington's rationale is that the kernel itself provides a clear diagnostic when an export is configured with sign_fh but no key has been set. Rather than adding additional error-checking complexity in userspace, he prefers to let the kernel reject the misconfiguration at export time, where it can provide context-specific logging.

This represents a design philosophy choice: fail late with clear diagnostics (in the kernel) versus fail early (in userspace). Layton had originally argued for a hard error in userspace because "being unable to set the key could be a security issue (or cause stale filehandles)." Coddington's counterargument is that the kernel's refusal to serve filehandles for affected exports is itself a sufficiently strong safety mechanism.

Implications for NFS Client Development

While this thread focuses on server-side userspace tooling, the error-handling strategy has direct consequences for NFS clients:

  • Client visibility into failures: If an export cannot issue signed filehandles due to a missing key, the kernel logs the error but the export may still appear active. Clients attempting to access such exports would encounter _BADHANDLE errors or mount failures, which existing client retry and re-mount logic is designed to handle.
  • No client code changes required: As established in prior review rounds, NFS clients treat filehandles as opaque data. The 8-byte siphash MAC appended to signed filehandles is transparent to the client stack.
  • Key persistence remains an administrative concern: If a server restarts without the same signing key, all previously-issued signed filehandles become invalid, causing clients to see stale handle errors — a scenario that requires careful operational planning regardless of whether the error is caught in userspace or the kernel.

Evolution and Status

The thread has not yet reached formal acceptance. Pending items for v4 include:

  1. NFSv2 man page wording correction (acknowledged last week)
  2. Netlink enumeration ordering to accommodate Layton's MIN_THREADS attribute
  3. Error handling strategy: Coddington has defended the soft-error approach, though it remains to be seen whether Layton or other reviewers will accept this resolution
