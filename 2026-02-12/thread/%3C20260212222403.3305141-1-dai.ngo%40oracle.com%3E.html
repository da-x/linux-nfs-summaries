NFSD Layout Recall Timeout v11: Final Fixes for Fencing Integration and Lease Spin-Lock Bug

Summary

NFSD Layout Recall Timeout and Fencing Integration — PATCH v11 Posted (Feb 12)

Overview

Discussion type: Bug fix / reliability enhancement for NFS server (NFSD) pNFS layout recall handling.

This week culminated with the posting of version 11 of Dai Ngo's patch series, [PATCH v11 1/1] NFSD: Enforce timeout on layout recall and integrate lease manager fencing [id://20260212222403.3305141-1-dai.ngo@oracle.com], on February 12. This submission represents the latest iteration in an extensive, multi-week review process involving Jeff Layton and Chuck Lever, addressing a critical server-side reliability issue where nfsd threads can be blocked indefinitely during pNFS block layout recalls.

Bridge from Prior Weeks

This patch has evolved through eleven iterations since early January. Key milestones include:

  • v5–v6 (Feb 5–6): Fixed reference counting, and incorporated Jeff Layton's suggestion to unlock leases immediately after fencing completes via kernel_setlease() with F_UNLCK [id://3cb09bd01df3d43293f2f443ebb6b4a10ea50dee.camel@kernel.org].
  • v7 (Feb 7): Changed the default fencing retry policy to "retry forever" in response to Jeff Layton's data corruption concerns [id://c3000ddc3cd66f43898c7f7dd9926804d2280878.camel@kernel.org]. Layton granted Reviewed-by.
  • v8 (Feb 9): Removed the admin tunable per Chuck Lever's request, implemented exponential back-off for retries, and fixed a bug in the lease disposal loop where the remove variable was not reinitialized inside the loop [id://e957053b-53d2-4291-afaa-d5dc08f8c44b@app.fastmail.com].
  • v9 (Feb 10): Capped maximum fence retry delay at 3 minutes, fixed a jiffies-vs-seconds unit conversion bug in mod_delayed_work(), moved INIT_DELAYED_WORK to allocation time, and replaced a redundant boolean flag with delayed_work_pending() [id://e817b590-3b41-4403-b17f-3114e04c0e96@oracle.com].
  • v10 (Feb 10): Fixed the initial fence worker delay from 1 jiffy to 1 second. Chuck Lever identified a critical latent bug in __break_lease: when lm_breaker_timedout returns false, the expired fl_break_time causes an unsigned wrap-around, leading to a tight spin loop that can hang uniprocessor systems [id://a06f4c17-8227-4c04-b270-5c064b7de79c@app.fastmail.com].
  • v11 (Feb 12): Addresses all v10 feedback, including the critical spin-loop bug fix and administrative improvements.

Key Technical Arguments in v11

The Core Problem: Server Thread Starvation

Dai Ngo articulated the fundamental motivation for this patch:

"When a layout conflict triggers a recall, enforcing a timeout is necessary to prevent excessive nfsd threads from being blocked in __break_lease ensuring the server continues servicing incoming requests efficiently." [id://20260212222403.3305141-1-dai.ngo@oracle.com]

Without a timeout mechanism, unresponsive or malicious pNFS clients holding block layouts can cause nfsd threads to block indefinitely in __break_lease, leading to server starvation and degrading service for all other NFS clients.

The Solution: Timeout with SCSI PR Fencing

The patch introduces a new callback lm_breaker_timedout in the VFS lease_manager_operations structure. When a layout recall times out:

  1. If the layout type supports fencing and the client has not been fenced, a SCSI Persistent Reservation (PR) PREEMPT operation is triggered asynchronously via a system workqueue.
  2. The conflicting file lease remains on the flc_list until fencing completes, guaranteeing that no other clients can access the file prematurely.
  3. Once fencing succeeds, the lease is unlocked immediately (via kernel_setlease() with F_UNLCK), allowing waiting tasks to proceed.

Critical Bug Fix: __break_lease Timestamp Wrap-Around

Chuck Lever identified a severe bug in v10 [id://a06f4c17-8227-4c04-b270-5c064b7de79c@app.fastmail.com]:

"schedule_timeout() treats negative values as a bug: it prints a KERN_ERR message with dump_stack() and returns immediately without sleeping... On a uniprocessor system the fence worker workqueue thread never gets scheduled because the spinning task never calls schedule(), so the system hangs."

Dai Ngo proposed a generalized fix within __break_lease itself, rather than patching it specifically for layouts:

"I think this issue should be addressed by __break_lease since we can have the same problem with timed out delegation... if (break_time < jiffies) break_time = jiffies + lease_break_time * HZ;" [id://1677f1ed-27db-4525-ae3e-5e4d12a9f5a9@oracle.com]

This fix protects against similar issues with timed-out delegations as well, making the kernel's lease management code more robust overall.

Administrative Improvements in v11

Jeff Layton raised concerns about log verbosity during the v10 review [id://eb1757d7f2409ffb792d800166daff8a8c63b09e.camel@kernel.org]:

"It'd be better to do it just once. This may mean tracking a per-client flag of some sort."

v11 addresses this by:

  • Limiting fence failure logging to once (per-client).
  • Including unique client identifiers in fence log messages for easier administration.
  • Adding logging of successful fencing operations.
  • Adding recovery procedures in pnfs-block-server.rst and pnfs-scsi-server.rst.

Design Philosophy: Clean Module Boundaries

A recurring theme throughout the patch's evolution has been maintaining clean boundaries between the VFS lease code and NFSD-specific logic. Dai Ngo explained a key design decision:

"I experimented with having the fence worker handle lease disposal after fencing the client. However, this requires the lease code to export the lease_dispose_list function... This approach adds unnecessary complexity and reduces code clarity, as it exposes internal lease code details to the nfsd worker, which should not be the case." [id://20260212222403.3305141-1-dai.ngo@oracle.com]

"Instead, the lm_breaker_timedout operation should simply notify the lease code about how to handle a lease that times out during a lease break, rather than directly manipulating the lease list." [id://20260212222403.3305141-1-dai.ngo@oracle.com]

Final Conclusions

  • v11 has been posted on February 12, incorporating all feedback from the v9 and v10 review cycles.
  • The patch now addresses a critical latent bug in __break_lease that could cause system hangs on uniprocessor systems when fencing is in progress.
  • Administrative improvements include per-client logging flags, client identifiers in log messages, and updated documentation with recovery procedures.
  • Code cleanups include removing an unused dispose list, simplifying the fence delay computation, and adding a description for MAX_FENCE_DELAY.
  • The patch touches 10 files across the VFS lease subsystem (fs/locks.c, include/linux/filelock.h), NFSD layout code (fs/nfsd/nfs4layouts.c, fs/nfsd/blocklayout.c), and documentation, with a net change of +264/-16 lines.

Significance for NFS Development

This patch represents an important bug fix and robustness improvement for NFSD's pNFS block layout support:

  • Data safety: The fencing mechanism prevents data corruption when layout recalls time out and the original client still holds exclusive block device access — a critical concern for pNFS block layouts where clients access storage devices directly.
  • Server responsiveness: Enforcing timeouts prevents nfsd thread starvation during layout conflicts, ensuring the server continues servicing incoming requests from all clients.
  • Improved concurrency: The lease-unlocking-after-fencing fix reduces blocking time for other clients waiting on conflicting layouts.
  • Operational safety: The default "retry forever" policy eliminates the risk of giving up on fencing and exposing the system to data corruption, while the 3-minute delay cap ensures reasonable retry intervals.
  • Kernel-wide robustness: The __break_lease timestamp wrap-around fix protects against similar issues with timed-out delegations, benefiting all NFS clients using delegation-based caching.
