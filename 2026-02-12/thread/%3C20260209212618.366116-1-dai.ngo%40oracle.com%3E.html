NFSD: Enforce Layout Recall Timeout with Lease Manager Fencing Integration

Summary

NFSD: Enforcing Layout Recall Timeouts and Integrating Lease Manager Fencing (v8)

This week, Dai Ngo submitted version 8 of a significant patch series aimed at hardening the NFS server's handling of pNFS layout recalls. The work addresses a critical reliability issue where excessive nfsd threads could become blocked during layout conflicts, potentially degrading server performance. The solution introduces a timeout mechanism for layout recalls and integrates with the kernel's lease manager to trigger client fencing when timeouts occur.

Technical Context and Problem Statement

The discussion centers on NFS client development from the server-side perspective—specifically, how the NFSD handles block layout conflicts in pNFS (parallel NFS). When a layout conflict triggers a recall, the server must wait for the client to release its exclusive access. Without a timeout, this wait can block nfsd threads indefinitely if the client is unresponsive or malicious.

Dai Ngo explained the necessity of the change:

"When a layout conflict triggers a recall, enforcing a timeout is necessary to prevent excessive nfsd threads from being blocked in __break_lease ensuring the server continues servicing incoming requests efficiently."

The patch introduces a new callback lm_breaker_timedout in the lease_manager_operations structure. This allows the lease manager (NFSD) to decide whether a timed-out lease should be disposed of or kept while fencing operations proceed. For block layouts, if the client has not been fenced, the server initiates a fence operation to prevent further access to the underlying block device.

Evolution of the Patch (v8)

This is the eighth iteration of the patch, reflecting extensive refinement:

  • v2–v4: Addressed locking requirements, added retry counts for fencing, and corrected reference counting on layout stateids.
  • v5–v6: Improved error handling, ensured leases are unlocked promptly after fencing, and moved initialization to allocation time.
  • v7: Changed default behavior to retry fencing indefinitely, with an optional admin-controlled maximum retry limit.
  • v8: Removed the configurable retry knob, implemented exponential backoff for retries, and fixed minor issues ("nits").

Dai Ngo noted a design decision regarding lease disposal:

"I experimented with having the fence worker handle lease disposal after fencing the client. However, this requires the lease code to export the lease_dispose_list function... This approach adds unnecessary complexity and reduces code clarity... Instead, the lm_breaker_timedout operation should simply notify the lease code about how to handle a lease that times out during a lease break, rather than directly manipulating the lease list."

Review Feedback from Chuck Lever

Chuck Lever provided detailed review comments on v8, focusing on correctness and convention:

  1. Timeout Values: He questioned whether an hour (3600 seconds) between retries was too long and suggested capping the maximum at 3 minutes. He also requested a constant to document the maximum timeout.

    "Assuming you meant 3600 seconds and not 3600 jiffies, is an hour between retries too long? Maybe the maximum should be capped at 3 minutes or something?"

  2. Jiffies Conversion: Lever pointed out that mod_delayed_work() expects jiffies, not seconds:

    "Since mod_delayed_work() takes jiffies as its third argument, you need a '* HZ' here."

  3. Initialization Safety: He recommended moving INIT_DELAYED_WORK to the allocation function for safety:

    "Can this INIT_DELAYED_WORK be moved to nfsd4_alloc_layout_stateid()? INIT at allocation time is more conventional and safer."

  4. State Tracking: Lever suggested using delayed_work_pending() instead of a separate boolean flag to track whether fencing is in progress:

    "Seems like there are two sources of truth about whether a fence is in progress here. Would it make sense to replace ls_fence_in_progress with a call to delayed_work_pending()?"

Conclusion and Next Steps

Dai Ngo acknowledged all of Chuck Lever's feedback and confirmed that fixes would be included in v9:

"Fix in v9."
"Yes, let just use delayed_work_pending(). Fix in v9."

The patch remains under active development, with the next version expected to address timeout capping, jiffies conversion, initialization safety, and state tracking simplification. This work represents an important bug fix and robustness improvement for NFSD's pNFS block layout support, ensuring that the server can recover from unresponsive clients without resource exhaustion.
