NFSD TCP Lock Contention Reduction: v2 Patch Series with Dedicated Receiver Threads and Flat Combining

Summary

NFSD TCP Scalability: v2 Patch Series Reduces Lock Contention via Dedicated Receiver Threads and Flat Combining

Classification

Performance optimization / architectural redesign. This eight-patch v2 series targets significant scalability bottlenecks in the NFS server (NFSD) TCP transport layer, specifically addressing lock contention on receive and transmit paths.

Bridge from Prior Week

Last week, Chuck Lever submitted a seven-patch RFC series titled "sunrpc: Reduce lock contention for NFSD TCP sockets." That RFC proposed dedicated TCP receiver threads, flat combining for socket sends, and a workqueue affinity scope fallback mechanism. However, the foundational workqueue patch (Patch 1/7) was rejected by workqueue maintainer Tejun Heo. Chuck Lever subsequently pivoted to a kthread-based alternative for svcrdma, avoiding the contested workqueue pool spin lock entirely.

This week, Chuck Lever submitted the v2 iteration of the series, now expanded to eight patches and refined based on RFC feedback. The rejected workqueue patch has been dropped, and the remaining patches have been reworked for clarity and correctness.

This Week's Activity

On February 10, Chuck Lever posted the complete v2 patch series. The cover letter summarizes the core problem:

"High-throughput NFSD workloads exhibit significant lock contention on TCP connections. Worker threads compete for the socket lock during receives and serialize on xpt_mutex during sends, limiting scalability."

The series addresses both paths with two major architectural changes:

Receive Path: Dedicated Kernel Thread per TCP Connection

As described in Patch 5/8, the receive-side socket lock contention is eliminated by dedicating one kernel thread per TCP socket to handle all sock_recvmsg() calls:

"In the current architecture, multiple nfsd threads compete for the same socket, serializing on the socket lock inside sock_recvmsg(). A single receiver kthread per TCP connection issues all sock_recvmsg() calls and enqueues complete RPC messages for nfsd threads to process."

The design uses a lock-free llist queue to pass complete RPC messages from the receiver to nfsd worker threads, with flow control limiting queue depth to 64 messages per socket. The receiver kthread is placed on the NUMA node associated with the service pool handling the accept, mirroring svcrdma's NUMA-aware resource allocation strategy.

Transmit Path: Flat Combining for Socket Sends

As detailed in Patch 6/8, the transmit path employs a flat combining pattern to reduce mutex contention:

"High contention on xpt_mutex during TCP reply transmission limits nfsd scalability. When multiple threads send replies on the same connection, mutex handoff triggers optimistic spinning that consumes substantial CPU time. Profiling on high-throughput workloads shows approximately 15% of cycles spent in the spin-wait path."

Rather than each thread acquiring xpt_mutex independently, threads enqueue their send requests to a lock-free llist. The first thread to acquire the mutex becomes the "combiner" and processes all pending sends in a batch, amortizing the lock acquisition cost across multiple operations. TCP auto-corking naturally coalesces segments once the first send places data in flight.

Supporting Changes

The series includes several supporting improvements:

  1. Usercopy bypass for kernel iterators (Patch 2/8): Profiling revealed that hardened usercopy checks consume roughly 1.3% of CPU in the TCP receive path when both source and destination reside in kernel address space. The patch bypasses these checks for kernel-only iterators (ITER_BVEC/KVEC), benefiting NFSD and NVMe-TCP.

  2. Per-transport page recycling pool (Patch 4/8): A lock-free svc_page_pool mechanism enables efficient page reuse between receive operations, reducing overhead in the page allocator hot path under high load.

  3. Unified fore and backchannel send paths (Patch 7/8): The backchannel implementation previously acquired xpt_mutex directly while the fore channel used flat combining, leading to starvation of callback operations under heavy load. Routing backchannel sends through the same flat combining infrastructure eliminates this issue:

"High latency in callback processing for NFSv4.1+ sessions can occur when the fore channel sustains heavy request traffic... Delegation recalls and other callback operations carry time constraints that make this starvation problematic."

  1. Explicit TCP socket buffer sizes (Patch 8/8): NFSD TCP sockets now use explicit buffer sizes (approximately 16MB with default NFS payload sizes) rather than relying on system defaults, improving throughput on high-speed networks without requiring system-wide sysctl adjustments.

Changes Since RFC

The cover letter notes several refinements from the RFC iteration:

  • Drop the affinity scope patch (rejected by workqueue maintainer)
  • Skip user memory hardening for kernel-to-kernel copies
  • Avoid invoking wake_up when the receive is already running
  • Refactor svc_tcp_receiver_thread() for legibility
  • Do not set MSG_MORE during batched sends

Conclusion

This v2 series represents a significant architectural evolution in NFSD's TCP transport layer, moving away from shared-lock contention toward dedicated receiver threads and lock-free batching for transmits. The changes mirror the svcrdma architecture's approach to NUMA-aware resource allocation and message queuing. With no replies recorded within this week's window, the series awaits community review and testing. If accepted, these changes could substantially improve NFSD scalability on high-throughput workloads, particularly on systems with large bandwidth-delay products where TCP buffer sizing and lock contention have been limiting factors.
