NFSD Layout Recall Timeout v7: Fencing Retry Policy Resolved, Code Review Nits Addressed

Overview

Discussion type: Bug fix / reliability enhancement for NFS server (NFSD) pNFS layout recall handling.

This week saw the posting of version 7 of Dai Ngo's patch series, [PATCH v7 1/1] NFSD: Enforce timeout on layout recall and integrate lease manager fencing, followed by a thorough review from Jeff Layton and Chuck Lever. The patch addresses a critical server-side reliability issue where excessive nfsd threads can be blocked indefinitely during pNFS block layout recalls, potentially causing server starvation. It introduces a new lm_breaker_timedout callback in the VFS lease manager infrastructure to enforce timeouts and integrate SCSI PR (Persistent Reservation) fencing.

Bridge from Prior Weeks

As summarized in prior reports, v5 had incorporated significant fixes including reference counting corrections, increased fence retry counts (from 5 to 20), proper worker cancellation on cleanup, and restored error-handling comments. A key improvement agreed upon was unlocking the lease immediately after fencing completes (via kernel_setlease() with F_UNLCK) to allow waiting tasks to proceed sooner. v6 incorporated this fix and prompted a debate from Jeff Layton about whether giving up on fencing after a fixed number of retries risks data corruption. Layton argued:

"It seems like the answer to this ought to be 'yes' by default. If you give up on fencing, then it seems like you're opening the door to data corruption."

v7, posted this week, directly responds to that concern by changing the default behavior to retry fencing indefinitely.

Key Technical Arguments

1. Fencing Retry Policy: Default Changed to "Retry Forever"

In response to Jeff Layton's concerns about data corruption risk from fixed retry limits, Dai Ngo changed v7 to retry fencing on error forever by default:

"Change to retry fencing on error forever by default."

A module parameter nfsd4_fence_max_retries was added to allow administrators to override this behavior if needed. The patch documentation notes:

"The admin can control this behavior by setting nfsd4_fence_max_retries"

Jeff Layton gave the patch a positive review with only minor nits:

"Thanks, Dai. I think this one looks good." Reviewed-by: Jeff Layton <jlayton@kernel.org>

2. Chuck Lever's Detailed Code Review

Chuck Lever provided an extensive review covering several issues:

Bug in Lease Disposal Logic

Lever identified a subtle bug in the time_out_leases loop where the remove variable is initialized before the loop but never reset to true at the start of each iteration. This could cause leases with no lm_breaker_timedout callback to inherit a stale false value, preventing their disposal:

"The 'remove' variable is initialized before the loop but is never reset to true at the start of each iteration. If a lease's lm_breaker_timedout callback returns false, 'remove' stays false for all subsequent leases in the list."

Dai Ngo confirmed this was correct and agreed to fix it:

"Yes, it should be initialized inside the loop. Fix in v8."

Concerns About Locking and Module Boundaries

Lever expressed reservations about holding flc_lock while calling into another module's callback:

"I'm still not enthusiastic about holding flc_lock while calling another module. Especially since holding that lock does not appear to be documented in an API contract..."

Dai Ngo pointed out that the locking requirement is documented in Documentation/filesystems/locking.rst.

Questioning the Need for the Admin Tunable

Lever challenged the rationale for the nfsd4_fence_max_retries module parameter, noting that limiting retries introduces a data corruption risk and asking for a concrete use case:

"I haven't seen a clear use case stated for an admin needing to set this value." "The documenting comment does not underscore that limiting the number of retries -- setting this value -- is a data corruption risk." "I'd rather not add this setting unless there is an actual real world purpose in front of us."

Dai Ngo agreed to remove the knob:

"Ok, I'll remove this knob in v8."

Potential Deadlock Concerns

Lever raised a question about potential deadlock between nfsd4_close_layout() acquiring fi_lock and calling kernel_setlease(), which could interact with locks held by the fence worker. Dai Ngo clarified:

"nfsd4_close_layout() releases the fi_lock before calling kernel_setlease()."

Testing Confirmation for Client Expiry

Lever asked whether expiring a client actually breaks the fence retry loop. Dai Ngo confirmed manual testing:

"nfsd4_revoke_states calls nfsd4_close_layout to remove all file leases. I manually tested it."

To which Lever responded:

"Excellent!"

Additional Code Nits Fixed in v8

Several smaller issues were identified and accepted for fixing:

  • Format specifier bug: The %pISpc format was receiving the wrong pointer type. Lever suggested:

    "Should this be (struct sockaddr *)&ls->ls_stid.sc_client->cl_addr?"

    Dai Ngo agreed: "Yes, fix in v8."

  • Exponential back-off for retry delays: Lever questioned the use of a literal 1 (jiffy) delay between fence retries:

    ""1" -- is that 1 jiffy? Could this use an exponential back-off instead?"

    Dai Ngo agreed to fix.

  • Typos and formatting: A typo ("orker" instead of "worker") and a blank comment line were noted and accepted for correction.

Evolution of the Discussion

The discussion followed a clear progression:

  1. Dai Ngo posted v7 on February 7, incorporating the "retry forever" default in response to prior concerns about data corruption risk from fixed retry limits.
  2. Jeff Layton reviewed and provided a Reviewed-by with only minor nits (explicit zero initialization of a global variable).
  3. Chuck Lever conducted a thorough code review identifying a genuine bug in the lease disposal logic, questioning the need for the admin tunable, raising deadlock concerns, and flagging several code quality issues.
  4. Dai Ngo responded on February 9, agreeing to all of Lever's suggestions and confirming fixes for v8.

Final Conclusions

  • v7 has been posted with the critical change of defaulting to infinite fencing retries, directly addressing Jeff Layton's data corruption concerns from prior weeks.
  • Jeff Layton granted Reviewed-by, signaling strong approval of the patch direction.
  • Chuck Lever identified a genuine bug in the lease disposal loop logic that must be fixed before the patch can be merged.
  • The admin tunable (nfsd4_fence_max_retries) will be removed per Chuck Lever's request, as no concrete use case was presented to justify exposing a data-corruption-risk parameter.
  • v8 is expected to address all identified issues: the remove variable initialization bug, the format specifier fix, exponential back-off for retry delays, typo corrections, and removal of the admin knob.

Significance for NFS Client Development

While this is primarily a server-side change, it has important implications for pNFS clients:

  • Data safety: The fencing mechanism prevents data corruption when layout recalls time out and the original client still holds exclusive block device access. This is critical for pNFS block layouts where clients access storage devices directly.
  • Server responsiveness: Enforcing timeouts prevents nfsd thread starvation during layout conflicts, ensuring the server continues servicing incoming requests from all clients.
  • Improved concurrency: The lease-unlocking-after-fencing fix reduces blocking time for other clients waiting on conflicting layouts.
  • Operational clarity: Removing the admin tunable simplifies the operational model — the default behavior (retry forever) is the safest, and administrators can intervene via client state revocation if fencing fails persistently.
