NFSD Signed Filehandles: Sparse Build Warning on Endianness Handling

Summary

Summary: NFSD Signed Filehandles Build Warning

This week's activity on the "NFSD: Sign filehandles" thread was limited to automated feedback from the kernel test robot regarding Benjamin Coddington's patch series (v4). The discussion concerns a new feature for the NFS server (NFSD) that introduces cryptographic signing of filehandles using SipHash, aimed at preventing filehandle forgery and improving security.

Key Technical Arguments and Issues

The sole message this week came from the kernel test robot on 2026-02-07, which flagged sparse warnings during a W=1 build with clang version 20.1.8 on an x86_64-randconfig configuration.

The robot reported incorrect type assignments in fs/nfsd/nfsfh.c:

"sparse: incorrect type in assignment (different base types) @@ expected unsigned long long [usertype] hash @@ got restricted __le64 [usertype] @@"

Specifically, the warnings pointed to lines 168 and 191 in nfsfh.c, where a u64 variable (hash) is assigned the result of cpu_to_le64(siphash(...)). The cpu_to_le64 function returns a __le64 (little-endian 64-bit) type, which sparse flags as incompatible with the plain unsigned long long (u64) type when strict endianness checking is enabled.

The problematic code snippet in question is:

hash = cpu_to_le64(siphash(&fh->fh_raw, fh->fh_size, fh_key));
memcpy(&fh->fh_raw[fh->fh_size], &hash, sizeof(hash));
fh->fh_size += sizeof(hash);

Evolution and Conclusion

This warning highlights a common endianness handling issue in kernel development. The siphash function returns a native-endian u64, which is then converted to little-endian via cpu_to_le64. However, storing this directly into a u64 variable triggers sparse's type checker because __le64 is a distinct restricted type intended to track byte order explicitly.

The kernel test robot noted:

"If you fix the issue in a separate patch/commit (i.e. not just a new version of the same patch/commit), kindly add following tags | Reported-by: kernel test robot <lkp@intel.com> | Closes: https://lore.kernel.org/oe-kbuild-all/202602071819.UF8h2gl7-lkp@intel.com/"

No human responses were recorded in this window. The issue is a build warning rather than a functional bug, but it should be addressed before the patch series can be merged cleanly. A likely fix would involve either casting appropriately or adjusting the variable type to __le64 where endianness conversion is involved.
