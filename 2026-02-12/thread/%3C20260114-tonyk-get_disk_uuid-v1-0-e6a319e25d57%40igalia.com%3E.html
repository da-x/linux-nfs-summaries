overlayfs: uuid=off Cannot Solve btrfs Clone File Handle Problem; Patch Queued for 7.0

Summary

overlayfs: uuid=off Limitations with btrfs Clones Clarified, Patch Queued for 7.0 PR

Summary

This week's single message in this long-running thread delivered a substantive technical clarification from Amir Goldstein regarding the fundamental limitations of overlayfs's uuid=off mount option when used with btrfs cloned images — the core use case driving this discussion for SteamOS A/B partitioning. While Goldstein confirmed that his patch has been pushed to the overlayfs-next branch and could be submitted during the 7.0 merge window, he also drew a hard line on what uuid=off can and cannot solve.

Background (Brief)

This thread originated from André Almeida's rejected 3-patch series proposing to repurpose export_operations::get_uuid() for overlayfs origin file handles, targeting btrfs cloned images used in SteamOS A/B partitioning. After Christoph Hellwig firmly opposed that approach, the discussion pivoted to extending overlayfs's existing uuid=off mount option. Over the prior five weeks, Goldstein developed a patch lifting uuid=off's same-filesystem restriction, clarified its semantics (it must be enabled from the first mount), and tested it internally. Last week, Almeida reported initial success but encountered a reboot-related failure, recommending deferral to kernel 7.1 [id://05c37282-715e-4334-82e6-aea3241f15eb@igalia.com].

Key Technical Arguments This Week

Amir Goldstein: uuid=off Must Be Consistent Across All Mounts

Responding to Almeida's report that he believed he "forgot to add uuid=off somewhere in the mount scripts," Goldstein emphasized a critical operational requirement [id://CAOQ4uxgzK7qYDFWYT62jH_zq8JkLGussD5ro4cKDqSNQqBiVUA@mail.gmail.com]:

"Not only on the first mount - on all the mounts. Unless you use 'uuid=off' consistently, overlayfs will deny the mount."

This clarification underscores that uuid=off is not a one-time declaration but a persistent policy: every subsequent mount of the same overlayfs must also specify the option, or the mount will be rejected outright.

The Fundamental btrfs Clone Problem: File Handles, Not Just UUIDs

The most significant technical contribution this week was Goldstein's explanation of why uuid=off alone cannot solve the SteamOS cloned-image problem. Almeida reported that rebooting to the "other partition" still triggered a "failed to verify upper root origin" error. Goldstein questioned whether the issue was truly about UUIDs at all, pointing out that btrfs clones produce different file handles for the same logical file:

"Overlayfs verifies the origin by file handle + UUID. We allow relaxing UUID check with uuid=off but isn't it the case for btrfs that the same file in different clones will have a different file handle, because of different root_objectid?"

He cited the relevant btrfs code showing how file handles encode root_objectid:

fid->objectid = btrfs_ino(BTRFS_I(inode));
fid->root_objectid = btrfs_root_id(BTRFS_I(inode)->root);
fid->gen = inode->i_generation;

This led to a crucial distinction:

"That means that you can use 'uuid=off' to overcome the ephemeral nature of the btrfs clone UUID, but you cannot use it to mount an overlayfs that was created in one btrfs clone from another clone."

In other words, uuid=off addresses UUID instability (the filesystem UUID changes between clones), but it does not address file handle instability (the same file has a different root_objectid in each clone). These are two separate problems, and uuid=off only solves the first.

No "fileid=off" Option Will Be Added

When confronted with this limitation, Goldstein was unequivocal:

"Sorry, no 'fileid=off' option, this is out of the question."

He explained that the alternative is to disable the overlayfs index entirely:

"You are free to use 'index=off' to avoid those requirements, but the essence of 'index=on' is that the lower file can be uniquely identified and therefore, changing the lower file's unique id is game over."

This draws a clear boundary: if users want index=on (which provides performance and correctness benefits), they must accept that the lower layer's file identity — both UUID and file handle — must remain stable across mounts. For btrfs clones where both change, uuid=off is insufficient, and index=off becomes the only option.

Patch Status: Queued for 7.0 Merge Window

Despite the limitations, Goldstein confirmed that his patch has been integrated into his development tree:

"I pushed this patch to overlayfs-next branch. It is an internal logic change in overlayfs that does not conflict with other code, so there should not be a problem to send a PR on the second half of the 7.0 merge window if this is useful."

However, he reiterated his conditional stance on submission:

"I think that the change itself makes sense because there was never a justification for the strict rule of both upper/lower on the same fs for uuid=off, but I am still not going to send it without knowing that someone finds this useful for their workload."

Evolution of the Discussion

The thread's trajectory over its full six-week lifespan:

  • Weeks 1–2 (Jan 14–22): Almeida's original approach rejected; discussion pivoted to uuid=off as an existing mechanism.
  • Week 3 (Jan 23–29): Almeida misused uuid=off; Goldstein clarified it must be enabled from the first mount and provided documentation improvements.
  • Week 4 (Feb 5): Almeida reported initial success but a remaining reboot issue; recommended deferral to 7.1.
  • Week 5 (Feb 6, this week): Goldstein clarified that uuid=off cannot solve the btrfs clone file handle problem, ruled out any "fileid=off" option, and confirmed the patch is queued for potential 7.0 submission.

Final Conclusions

  1. uuid=off has a hard limitation with btrfs clones. It can address UUID instability but not file handle instability caused by differing root_objectid values across clones [id://CAOQ4uxgzK7qYDFWYT62jH_zq8JkLGussD5ro4cKDqSNQqBiVUA@mail.gmail.com]. This is a fundamental architectural constraint, not a bug.

  2. No "fileid=off" option will be added. Goldstein firmly rejected the idea of relaxing file handle verification, stating it is "out of the question" [id://CAOQ4uxgzK7qYDFWYT62jH_zq8JkLGussD5ro4cKDqSNQqBiVUA@mail.gmail.com]. The only alternative for users needing this flexibility is index=off.

  3. The patch is queued but submission is conditional. Goldstein has pushed the change to overlayfs-next and could submit a pull request during the 7.0 merge window, but only if someone confirms it serves their workload [id://CAOQ4uxgzK7qYDFWYT62jH_zq8JkLGussD5ro4cKDqSNQqBiVUA@mail.gmail.com].

  4. uuid=off must be used consistently on all mounts. Not just the first mount, but every subsequent mount of the same overlayfs [id://CAOQ4uxgzK7qYDFWYT62jH_zq8JkLGussD5ro4cKDqSNQqBiVUA@mail.gmail.com].

Classification

Type: Feature extension (overlayfs uuid=off support for cross-filesystem setups)

NFS Client Relevance: Indirect. This is fundamentally an overlayfs discussion, though it touches on file handle encoding semantics that are foundational to NFS exports and the exportfs subsystem. The original get_uuid() infrastructure served pNFS block layout, and Hellwig previously noted that "encoding the uuid into the file handle in the kernel is the right thing for NFS as well."
