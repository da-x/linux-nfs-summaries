svcrdma Performance Scalability Enhancements: Lock-Free Lists, WR Chaining, and Per-Transport Kthreads

Summary

Chuck Lever submitted a 15-patch RFC series titled "svcrdma performance scalability enhancements" RFC PATCH 00/15, targeting the NFS server-side RDMA transport (svcrdma). The series aims to lower per-connection resource utilization, reduce lock contention, and decrease interrupt/doorbell rates to improve scalability as connection counts grow.

Key Technical Arguments and Strategies

Lever identifies that while RPC/RDMA CPU cost is insignificant for single connections, incremental costs like memory-per-connection and interrupt rates accumulate at scale. Profiling an 8KB NFSv3 read/write workload revealed several bottlenecks:

  • ~4% of total CPU time was spent on contention for the svcrdma_wq unbound workqueue pool lock.
  • Receive completion processing acquired a per-transport spinlock on every inbound message.
  • Doorbell and completion event counts scaled linearly with Write chunk usage.

The series employs three recurring strategies to address these issues:

1. Lock-Free Lists for Completion Queues

Patches 07/15 and 08/15 replace spinlock-protected queues (sc_rq_dto_q and sc_read_complete_q) with lock-free lists (llist). This eliminates producer-side locking entirely on the hottest paths. Lever notes:

"The lock remains for sc_read_complete_q, but the primary hot path (receive completion and consumption) no longer requires it. This eliminates producer-side contention entirely."

2. Per-Transport Kthreads to Replace Global Workqueue

Patch 10/15 replaces the global svcrdma_wq workqueue with per-transport kthreads. The CQ handler appends completed send contexts to a lock-free list, and the kthread drains them in batches. This removes contention on the unbound pool lock, which was identified as "the single largest contention source."

3. Work Request Chaining for Write Chunks

Patch 04/15 links Write chunk RDMA Write WRs onto the RPC Reply's Send WR chain. This allows a single ib_post_send() call to post both operations, reducing doorbell and completion rates. Lever explains:

"A single completion event signals that all operations have finished. This reduces both doorbell rate and completion rate, as well as eliminating the latency of a round-trip between the Write chunk completion and the subsequent Send WR posting."

4. Fair Queuing for Send Queue Access

Patch 01/15 introduces a ticket-based fair queuing system for Send Queue (SQ) slot allocation to prevent starvation when the SQ fills under concurrent use:

"The previous implementation had no ordering guarantee, allowing starvation when one thread repeatedly acquires slots while others wait indefinitely."

5. Watermark-Based Receive Queue Replenishment

Patch 11/15 changes Receive Queue posting from small fixed batches to watermark-triggered bulk replenishment, provisioned at twice the negotiated credit limit. This reduces the frequency of ib_post_recv() calls and associated doorbell overhead.

6. Cache Line Separation and Per-Object Caching

Patch 06/15 uses ____cacheline_aligned_in_smp annotations to separate frequently modified fields in struct svcxprt_rdma into distinct cache lines, reducing false sharing. Patch 12/15 adds a per-recv_ctxt single-entry cache for svc_rdma_chunk structures, covering the >99% common case of single-chunk RPCs without dynamic allocation.

7. Correcting XPT_DATA Flag Handling

Patches 13/15, 14/15, and 15/15 address spurious thread dispatches caused by stale XPT_DATA flags. Trace data showed that 62% of enqueue attempts found no pending work. Lever states:

"Clearing the flag on consumption eliminates the majority of these spurious dispatches."

Evolution and Conclusions

This is an RFC submission with no replies in the current window. The series represents a comprehensive optimization effort for svcrdma, focusing on reducing overhead in high-scale scenarios. The changes are extensive, touching 8 files with 488 insertions and 241 deletions. The base commit is v6.19, and the code is available in Lever's svcrdma-next branch.

The series does not introduce new NFS features or protocol changes but rather optimizes the existing RPC/RDMA transport implementation for better scalability and lower latency under load.
