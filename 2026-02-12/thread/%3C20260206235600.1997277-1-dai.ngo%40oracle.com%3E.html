NFSD Layout Recall Timeout v6: Fencing Retry Policy Debate

Summary

NFSD Layout Recall Timeout: v6 Posted, Fencing Retry Policy Debated (Feb 6–7)

Overview

Discussion type: Bug fix / reliability enhancement for NFS server (NFSD) pNFS layout recall handling.

This week saw the posting of version 6 of Dai Ngo's patch series, [PATCH v6 1/1] NFSD: Enforce timeout on layout recall and integrate lease manager fencing, followed by a focused review from Jeff Layton on the critical question of fencing retry behavior. The patch addresses a server-side reliability issue where excessive nfsd threads can be blocked indefinitely during pNFS block layout recalls, potentially causing server starvation. It introduces a new lm_breaker_timedout callback in the VFS lease manager infrastructure to enforce timeouts and integrate SCSI PR (Persistent Reservation) fencing.

Bridge from Prior Week

As summarized last week, v5 had incorporated significant fixes including reference counting corrections, increased fence retry counts (from 5 to 20), proper worker cancellation on cleanup, and restored error-handling comments. A key improvement agreed upon was unlocking the lease immediately after fencing completes (via kernel_setlease() with F_UNLCK) to allow waiting tasks to proceed sooner. Dai Ngo confirmed this fix would be in v6, which was posted on February 6.

Key Technical Arguments

1. Patch v6: Immediate Lease Unlocking After Fencing

Dai Ngo's v6 submission incorporated the agreed-upon improvement from last week's discussion with Jeff Layton:

"unlock the lease as soon as the fencing is done, so that tasks waiting on it can proceed."

This change ensures that once SCSI PR fencing completes successfully, conflicting leases are released immediately rather than waiting for the next lm_breaker_timedout callback invocation. This enhances server responsiveness by reducing blocking time for other clients waiting on conflicting layouts.

2. Fencing Failure: Retry Forever or Give Up?

Jeff Layton raised a fundamental concern about the patch's retry logic, specifically the LO_MAX_FENCE_RETRY limit (set to 20 in v5):

"It seems like the answer to this ought to be 'yes' by default. If you give up on fencing, then it seems like you're opening the door to data corruption."

Layton argued that failing to fence a client holding exclusive block device access creates a risk of data corruption if another client is granted layout access. He suggested:

"I think in most cases, we'd want the administrator to intervene if fencing fails."

He also proposed making the retry behavior tunable, allowing administrators to set a policy about whether to time out the lease eventually or retry indefinitely:

"I can see a case for making this tunable though, and allowing the admin to set a policy about what should happen in this case (time out the lease eventually, or retry indefinitely)."

Layton also noted that proper documentation is needed for administrators on how to respond to fencing failures:

"We also need to document what the admin should do if that does occur. Presumably they could hit the power switch on the client and revoke all of its state via the administrative interfaces?"

Additionally, he suggested that fencing failures should generate immediate warnings rather than silent retries:

"A failure to fence a client should probably should earn an immediate warning. I wouldn't expect this to fail under normal circumstances so we probably ought to start complaining immediately if it does."

Evolution of the Discussion

The discussion this week was concise but impactful:

  1. Dai Ngo posted v6 on February 6, incorporating the lease-unlocking improvement from last week's review.
  2. Jeff Layton reviewed v6 on February 7 and focused his critique on the fencing retry policy, arguing that giving up on fencing after a fixed number of retries risks data corruption.

Final Conclusions

  • v6 has been posted with the agreed-upon improvement to unlock leases immediately after fencing completes.
  • The fencing retry policy remains unresolved. Jeff Layton's concern that a fixed retry limit (20) could lead to data corruption if fencing fails is significant and likely requires further discussion before the patch can be accepted. The question of whether to retry indefinitely, make the behavior tunable, or require administrative intervention needs to be addressed in v7 or later.
  • Documentation gaps identified. Layton highlighted the need for administrator-facing documentation on how to respond to fencing failures, including potential use of administrative interfaces to revoke client state.

Significance for NFS Development

While this is primarily a server-side change, it has important implications for pNFS clients:

  • Data safety: The fencing mechanism prevents data corruption when layout recalls time out and the original client still holds exclusive block device access. This is critical for pNFS block layouts where clients access storage devices directly.
  • Server responsiveness: Enforcing timeouts prevents nfsd thread starvation during layout conflicts, ensuring the server continues servicing incoming client requests from all clients, not just those involved in layout conflicts.
  • Improved concurrency: The v6 fix to unlock leases immediately post-fencing reduces blocking for other clients waiting on conflicting layouts, improving overall system throughput.
  • Administrative oversight: The debate over retry policy highlights the need for clear operational procedures when fencing fails, ensuring administrators can intervene promptly to prevent data corruption.
