VFS Directory Locking Centralization: Final Review Round and Bug Fixes

Summary

The final review round for Neil Brown's 13-patch series "Further centralising of directory locking for name ops" concluded this week with targeted bug fixes, stylistic clarifications, and a minor API design refinement. The series — a VFS refactoring effort aimed at transitioning from whole-directory locks to per-name locking — received substantial review coverage last week; this week's activity focused on resolving remaining objections and correcting errors in the patches.

AppArmor Return-Value Bug Fix

A significant intermediate bug was identified in patch 04/13 (AppArmor). Jeff Layton pointed out that a return value had been incorrectly set to 0 rather than returning the dentry pointer:

"As KTR points out, this should be 'return NULL;'"

Neil Brown corrected this further, noting that the original code returned the dentry itself, and callers would silently treat NULL as failure:

"Actually it should be 'return dentry;' which is what the original code did. I've no idea how it became 0... Callers of aafs_create() will silently treat NULL as failure." As mentioned by Neil Brown

This fix ensures that the AppArmor filesystem's create operation correctly propagates success to its callers, preventing silent failures in security module hooks.

Overlayfs Documentation and Style Clarifications

For patch 08/13 (ovl_lookup_real_one() simplification), Amir Goldstein raised concerns about kernel-doc placement within code comments and the clarity of new wording. Neil Brown agreed to rephrase and adjust formatting:

"Ok, I'll rephrase." As mentioned by Neil Brown

Brown also noted his preference for some syntax highlighting with parameter names like "connected" and "real," acknowledging the stylistic tension:

"I find that with parameter names like 'connected' and 'real', some sort of syntax helps." As mentioned by Neil Brown

Overlayfs Lock Reacquisition: Resolving the Design Debate

The most substantive technical discussion centered on patch 10/13, which changes ovl_create_real() to drop and re-acquire locks after file creation. Amir Goldstein had previously expressed confusion about whether dentries could be unhashed while still in the "creating" scope:

"It is hard for me to wrap my head around this." As mentioned by Amir Goldstein

This week, Neil Brown provided a detailed explanation of the locking semantics, clarifying that the name must remain locked and hashed until the operation succeeds or fails, but POSIX does not require the object to retain any particular name afterward:

"It will be important for the name the remain locked (and hashed) until the operation (create, remove, rename) either succeeds or fails. So leaving a dentry unhashed will be OK providing a subsequent lookup will also succeed or fail in the same way." As mentioned by Neil Brown

He also addressed Amir's concern about casefold filesystems, noting that special filesystems like tracefs always unhash on create:

"There is no reason that a casefolding filesystem would not support parallel ops. And it isn't just casefolding that acts like this. At least one of the special filesystems (tracefs maybe) always unhashes on create." As mentioned by Neil Brown

Brown proposed a refinement to the API: having callers of ovl_start_creating_temp() pass a char name[OVL_TEMPNAME_SIZE] buffer, which would simplify the three callers (ovl_lookup_or_create(), ovl_create_upper(), and ovl_create_temp()). Amir Goldstein agreed this approach would improve code clarity:

"Yes, considering that two of the callers are from the same function (ovl_whiteout()) I think that would end up looking nicer." As mentioned by Amir Goldstein

Dead Code Removal and Historical Context

For patch 12/13 (removal of ovl_lock_rename_workdir()), Neil Brown clarified the historical context of why this function became unused, noting that commit 833d2b3a072f had already removed its last use in a different branch:

"Commit 833d2b3a072f ('Add start_renaming_two_dentries()') removed the last use of ovl_lock_rename_workdir() earlier, but in a different branch." As mentioned by Neil Brown

Amir Goldstein provided a Reviewed-by tag for this patch, acknowledging the cleanup.

libfs Inline Function Discussion

For patch 03/13, Jeff Layton suggested converting simple_done_creating() into a static inline function. Neil Brown was hesitant to change the existing structure without strong justification:

"True ... but then it could have been a static inline anyway. I'd rather not change it without good reason, or knowing what it was written that way." As mentioned by Neil Brown

Brown deferred to Linus Torvalds for a final opinion on this stylistic matter.

Conclusion

This week's activity represents the final polishing phase of Neil Brown's VFS directory locking centralization series. The key outcomes include:

  1. Bug fix: Corrected return value in AppArmor's aafs_create() to prevent silent failures.
  2. Design refinement: Agreement on passing name buffers explicitly to ovl_start_creating_temp() callers for cleaner overlayfs code.
  3. Clarifications: Resolved conceptual concerns about dentry hashing semantics during the "creating" scope.
  4. Cleanups: Removed dead code and addressed documentation style issues.

The series remains a VFS refactoring effort with implications for NFS server (nfsd's purge_old() migration) and overlayfs, though no new features or protocol changes are introduced. With the remaining objections addressed or deferred, the series appears poised for integration pending final review.
