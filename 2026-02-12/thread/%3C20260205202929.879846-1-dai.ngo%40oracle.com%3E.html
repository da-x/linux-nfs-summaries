NFSD Layout Recall Timeout: Lease Removal Timing and Patch Structure Review

Summary

NFSD Layout Recall Timeout and Lease Manager Fencing — PATCH v5 Review (Feb 6)

Overview

Discussion type: Bug fix / reliability enhancement for NFS server (NFSD) pNFS layout recall handling.

This week's activity centered on the review of version 5 of Dai Ngo's patch series, [PATCH v5 1/1] NFSD: Enforce timeout on layout recall and integrate lease manager fencing, which was posted on February 5. The patch addresses a critical reliability issue where excessive nfsd threads can be blocked indefinitely during pNFS layout recalls, potentially causing server starvation. It introduces a new lm_breaker_timedout callback in the VFS lease manager infrastructure to enforce timeouts and integrate SCSI PR fencing via the kernel lease manager.

Six messages were exchanged on February 6, involving Christoph Hellwig, Jeff Layton, and Dai Ngo. The discussion focused on two main topics: (1) patch structure (single combined patch vs. split VFS/nfsd patches), and (2) the precise timing of lease removal after fencing completes.

Bridge from Prior Week

As summarized in the previous week's report, v5 incorporated significant fixes from the rigorous v4 review by Chuck Lever and Jeff Layton, including reference counting corrections, increased fence retry counts (from 5 to 20), proper worker cancellation on cleanup, and restored error-handling comments. The patch had evolved through five versions addressing fundamental data-safety concerns around timeout-based fencing schemes.

Key Technical Arguments

1. Patch Structure: Combined vs. Split Approach

Christoph Hellwig raised a structural concern about the patch mixing VFS core infrastructure with NFSD-specific code:

"Most of this is over my head (but I'll still try to come up with good comments if I can find some time to learn/relearn the lease code), but one thing I noticed is that this mixes up VFS and nfsd code. You probably want to split this into a core infrastructure and a nfsd patch."

Dai Ngo clarified that earlier versions had separated the patch, but reviewers suggested combining them:

"I did separate the patch into a core infrastructure patch (lease code) and nfsd patch in earlier version. But I think Jeff or Chuck suggested to combine them into one patch since nfsd is the only consumer of the newly introduce lm_breaker_timedout operation."

He then asked for guidance from Jeff Layton and Chuck Lever on whether to maintain the combined approach or revert to splitting.

2. Lease Removal Timing After Fencing

Jeff Layton identified a subtle timing issue in the lease lifecycle: when remove is false and lease_modify() does not execute immediately (the common case where a workqueue job is queued), the question arises of when the lease is actually removed. He questioned whether the code assumed the layout stateid's reference count would naturally drop to zero after fencing:

"When remove is false, and lease_modify() doesn't happen (i.e., the common case where we queue the wq job), when do you actually remove the lease?"

"Are you just assuming that after the client is fenced, that the layout stateid's refcount will go to zero? I'm curious what drives that process, if so."

Dai Ngo explained the two-step mechanism: first, the fence worker sets ls_fenced to true upon completion; second, when __break_lease/time_out_leases calls lm_breaker_timedout again, nfsd4_layout_lm_breaker_timedout returns true because ls_fenced is set. Regarding reference counting:

"No, after completing the fence operation, the fenced worker drops the reference count on the layout stateid by calling nfs4_put_stid(). If the reference drops to 0 then the layout stateid is freed at this point, otherwise it will be freed when the CB_RECALL callback times out."

Jeff Layton then proposed an improvement: unlocking the lease immediately after fencing completes, rather than waiting for the next lm_breaker_timedout invocation, to allow waiting tasks to proceed sooner:

"In principle the stateid could stick around for a while after the fence has occurred. It would be better to unlock the lease as soon as the fencing is done, so that tasks waiting on it can proceed (a'la kernel_setlease() with F_UNLCK)."

Dai Ngo accepted this suggestion:

"Good suggestion, fix in v6."

Evolution of the Discussion

The discussion followed a clear progression:

  1. Christoph Hellwig opened with a structural critique about mixing VFS and NFSD code, prompting Dai to seek guidance on patch organization.
  2. Jeff Layton dove into the technical details of lease lifecycle management, questioning when leases are actually removed in the common case.
  3. Dai Ngo provided detailed explanations of the fencing workflow and reference counting mechanics.
  4. Jeff Layton refined his critique, suggesting immediate lease unlocking post-fencing for better concurrency.
  5. Dai Ngo agreed to implement the improvement in v6.

Final Conclusions

  • The patch structure question (combined vs. split) remained open at week's end, pending further input from Jeff Layton and Chuck Lever.
  • A concrete improvement was agreed upon: unlocking the lease immediately after fencing completes (via kernel_setlease() with F_UNLCK), to be implemented in v6. This enhances server responsiveness by allowing waiting tasks to proceed sooner rather than waiting for the next timeout callback invocation.
  • Dai Ngo confirmed that v6 would incorporate this fix, indicating active iteration toward a final submission.

Significance for NFS Client Development

While this is primarily a server-side change, it has important implications for pNFS clients:

  • Data safety: The fencing mechanism prevents data corruption when layout recalls time out and the original client still holds exclusive block device access.
  • Server responsiveness: Enforcing timeouts prevents nfsd thread starvation during layout conflicts, ensuring the server continues servicing incoming client requests.
  • Improved concurrency: The agreed-upon v6 fix to unlock leases immediately post-fencing will further reduce blocking for other clients waiting on conflicting layouts.
