NFS Client: Fix nlink drop ordering with delegation returns during REMOVE

Summary

NFS Client: Fixing nlink Drop and Delegation Return Ordering in REMOVE

This week’s thread addresses a critical bug fix in the NFS client related to inode link count (nlink) management during file removal, specifically when delegations are involved. The discussion centers on correcting a regression introduced by a previous race-condition fix, ensuring that the VFS receives proper FS_DELETE_SELF notifications via inotify.

Context and Problem Statement

The issue stems from commit bd4928ec799b ("NFS: Avoid changing nlink when file removes and attribute updates race"), which was designed to prevent races between attribute cache updates and inflight RPCs during REMOVE operations. However, as Roberto Bergantinos Corpas explained in his initial patch submission:

"However it does not take into account that REMOVE may trigger a delegation return which also advances gencount (via the attribute refresh during delegation return), and in that case the gencount mismatch is not due to an inflight RPC that already reflected the removal."

The consequence of this oversight was a failure in the LTP inotify04 test, where the VFS failed to deliver the expected deletion notification because the generation count (gencount) logic did not account for the side effects of delegation returns.

Evolution of the Discussion

Initial Proposal: Force Drop

In his first submission, Roberto proposed a targeted fix that would force the drop of nlink if a delegation was held prior to the remove operation. He argued:

"If nlink is 1 and we have a delegation before REMOVE, we should force the drop to ensure the VFS delivers the expected FS_DELETE_SELF notification."

This approach was reviewed by Olga Kornievskaia but received feedback from NFS client maintainer Trond Myklebust, who suggested a more architectural solution rather than a conditional force flag.

Maintainer Feedback: Protocol-Specific Ordering

Trond Myklebust advised moving the logic deeper into the stack to ensure correct ordering with respect to delegation returns:

"The right way to go about this is to push the setting of gencount from nfs_safe_remove() down into the version-specific layer so that you can order it correctly with the delegation return and call to _nfs4_proc_remove()."

This feedback highlighted the need to handle NFSv3 and NFSv4 differently, as NFSv4 involves delegation returns that must be sequenced correctly before finalizing the link count drop.

Revised Solution: Version-Specific Handlers

Roberto promptly submitted v2 of the patch, incorporating Trond’s suggestion. The revised approach moves the gencount capture and nfs_drop_nlink call into the version-specific remove handlers (nfs3_proc_remove, nfs4_proc_remove, etc.). This ensures that for NFSv4, the delegation return is processed before the link count is dropped, maintaining consistency with the attribute cache.

"Push the setting of gencount under each version-specific layer, reordering correctly for nfsv4 case after the delegation returns."

Technical Significance

This fix is a bug fix rather than a new feature or protocol change. It is critical for:

  1. Correct VFS Notifications: Ensuring that inotify and other filesystem watchers receive accurate FS_DELETE_SELF events.
  2. Delegation Integrity: Properly handling the interaction between delegation returns and attribute cache updates during removal operations.
  3. Test Compliance: Resolving the LTP inotify04 failure, which is a standard compliance test for Linux filesystems.

The patch touches multiple files in the NFS client stack (fs/nfs/dir.c, fs/nfs/internal.h, fs/nfs/nfs3proc.c, fs/nfs/nfs4proc.c, fs/nfs/proc.c), reflecting the need to coordinate changes across both protocol versions.

Conclusion

The thread demonstrates a collaborative and efficient development process, with a clear problem identification, constructive maintainer feedback, and a rapid iteration to a robust solution. The final patch ensures that the NFS client correctly manages inode link counts in the presence of delegations, preserving the integrity of filesystem notifications and attribute caching.
