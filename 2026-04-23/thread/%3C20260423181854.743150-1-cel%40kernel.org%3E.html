NFSD Block Layout Export Cleanup v3: Infrastructure Refactoring for VFS Integration

Summary

This week, Chuck Lever posted v3 of Christoph Hellwig's four-patch series to clean up the NFS server's (NFSD) block-style layout export infrastructure. The series represents a significant architectural refactoring aimed at separating layout-based block device access operations from general exportfs machinery, and preparing the codebase for future multi-device export support.

This posting follows a procedural resolution reached earlier in the week: after weeks of debate between NFS maintainer Chuck Lever and VFS maintainer Christian Brauner over which kernel tree should accept these infrastructure changes, the parties agreed that Brauner would take the series through a dedicated vfs.nfsd subtree within the VFS tree. As Lever explained in the cover letter:

"Christian prefers to see them taken through the VFS tree. Once the patches are applied there, I will rebase nfsd-next and nfsd-testing on that tree and drop these."

The series was authored by Christoph Hellwig, reviewed by Jeff Layton, and submitted by Chuck Lever. No replies appeared within this week's window; subsequent discussion occurred after the window closed.

Classification

This is an infrastructure refactoring with a minor protocol-compliance correction component. It is not a new feature or a bug fix in the traditional sense, but rather a structural cleanup that improves code organization and prepares for future functionality (multi-device block layout exports).

Technical Arguments and Patch Breakdown

Patch 1/4: Always Ignore loca_time_modify

This patch corrects NFSD's handling of the loca_time_modify attribute in block layout commit operations. Hellwig justified the change by citing the NFSv4.2 specification:

"RFC 8881 Section 18.42 makes it clear that the client provided timestamp is a 'may' condition, and clients that want to force a specific timestamp should send a separate SETATTR in the compound."

The patch further notes that XFS—the only filesystem currently supporting block layout exports—uses multi-grain timestamps and already ignores ia_mtime values at the VFS layer since commit b82f92d5dd1a. The change makes this behavior explicit in NFSD rather than relying on implicit VFS-level filtering.

Significance for NFS clients: This ensures that client-provided timestamps during layout commits are not silently applied in a way that could conflict with the server's multi-grain timestamp semantics, avoiding potential data integrity issues or unexpected attribute changes.

Patch 2/4: Split Out Operations for Layout-Based Block Device Access

This patch introduces architectural separation by creating a new header file, include/linux/exportfs_block.h, and moving block layout-specific operations into their own structure. Hellwig explained the rationale:

"The support to grant layouts for direct block device access works at a very different layer than the rest of exports. Split the methods for it into a separate struct, and move that into a separate header to better split things out."

The pointer to the new operation vector is kept in export_operations to avoid bloating the super_block structure. This change affects files across NFSD (fs/nfsd/blocklayout.c, fs/nfsd/nfs4layouts.c), XFS (fs/xfs/xfs_export.c, fs/xfs/xfs_pnfs.c), and the core exportfs infrastructure (include/linux/exportfs.h).

Patch 3/4: Don't Pass struct iattr to ->commit_blocks

This patch simplifies the ->commit_blocks callback interface by removing the unnecessary struct iattr argument. Hellwig noted:

"The only thing ->commit_blocks really needs is the new size, with a magic -1 placeholder 0 for 'do not change the size' because it only ever extends the size."

This reduces coupling between the NFSD layer and filesystem-specific implementations, passing only the essential data (the new file size) rather than the full attribute structure.

Patch 4/4: Rework Checking for Layout-Based Block Device Access Support

The final patch lifts hard-coded checks for block layout support from NFSD into filesystem-level helpers and provides a generic exportfs-level helper function. Hellwig stated:

"Currently NFSD hard codes checking support for block-style layouts. Lift the checks into a file system-helper and provide a exportfs-level helper to implement the typical checks."

This change is explicitly preparatory:

"This prepares for supporting block layout export of multiple devices per file system."

Evolution of the Discussion

The v3 series builds directly on the procedural resolution documented in the prior week's summary of the related thread. Key milestones:

  1. April 1: Hellwig originally submitted v2 of the cleanup series, which was merged into nfsd-testing.
  2. April 9–21: Brauner objected to the submission path, preferring VFS-tree integration. Lever proposed a vfs.nfsd compromise tree.
  3. April 21: Brauner accepted the arrangement: "Sounds perfect."
  4. April 23 (this week): Lever posted v3 of the series with the understanding that it would flow through Brauner's VFS tree rather than being merged directly into nfsd-next.

The technical content remained largely unchanged from v2; the primary difference was the procedural context and submission path.

Final Conclusions

The v3 cleanup series represents a well-scoped infrastructure refactoring with clear benefits:

  1. Protocol compliance: Explicitly ignoring loca_time_modify aligns NFSD behavior with RFC 8881 and XFS's multi-grain timestamp semantics.
  2. Code organization: Separating block layout operations into exportfs_block.h reduces coupling and prevents superblock bloat.
  3. Interface simplification: Removing the struct iattr argument from ->commit_blocks passes only necessary data.
  4. Future readiness: Reworking support checks prepares for multi-device block layout exports per filesystem.

The series is expected to be merged through the VFS tree via the vfs.nfsd subtree, after which Lever will rebase the NFS trees accordingly. For NFS client developers, this refactoring ensures that PNFS block layout support remains correctly gated on filesystem capabilities, preventing clients from receiving incorrect layout support information that could lead to failed layout get operations or data integrity issues with timestamp handling.
