SMB Direct code relocation to net/smbdirect/ for future protocol support

Summary

SMB Direct Code Relocation: Path Debate and Future Protocol Direction

This thread, though hosted on the linux-nfs list due to cross-tree filesystem discussions, concerns the SMB (Server Message Block) subsystem, specifically the placement of SMB Direct (RDMA-based transport) code within the kernel source tree. The discussion is categorized as a code organization/structural change with implications for future protocol development.

Key Technical Arguments

The core issue revolves around where to place the smbdirect code in the kernel filesystem hierarchy. Christoph Hellwig had previously questioned why the code was not located in net/smbdirect/ or drivers/infiniband/ulp/smdirect, suggesting these would be more semantically appropriate locations for network protocol and InfiniBand ULP (Upper Layer Protocol) code respectively.

Stefan Metzmacher, the SMB subsystem maintainer, responded this week with his rationale:

"Yes, I also thought about net/smbdirect."

He indicated that net/smbdirect/ is indeed the preferred destination, motivated by upcoming protocol work:

"As IPPROTO_SMBDIRECT or PF_SMBDIRECT will be the next step... (I'll follow with that discussion soon)"

This reveals that the relocation is not merely cosmetic but preparatory for introducing SMB Direct as a proper network protocol family in the kernel networking stack.

Evolution of the Discussion

Metzmacher expressed hesitation about the administrative consequences of moving code to net/smbdirect/:

"I was just unsure about the consequences, e.g. would the maintainer/pull request flow have to change in that case? Or would Steve be able to take the changes via his trees?"

He also noted a desire to avoid interpersonal friction:

"Any I also didn't want to offend anybody, so I just took what Linus proposed."

This suggests that the initial placement was influenced by Linus Torvalds' suggestion during review, and Metzmacher prioritized avoiding maintainer conflicts over ideal directory structure.

Christoph Hellwig provided guidance on how to navigate such structural decisions:

"You might want to ask the sunrpc or ceph maintainers as they have a similar split."

This points to existing precedents in the kernel where filesystem-related network protocols (like NFS/sunrpc and Ceph) have code split between fs/ and net/, offering Metzmacher a model for resolving the maintainer flow concerns.

Final Conclusions

The discussion concludes with Hellwig's endorsement:

"Seems like it is the right fit then."

The consensus leans toward moving SMB Direct code to net/smbdirect/ in preparation for introducing IPPROTO_SMBDIRECT or PF_SMBDIRECT. The remaining work involves coordinating with network subsystem maintainers, potentially following the precedent set by sunrpc and Ceph, to ensure smooth maintainer workflows.

Relevance to NFS Client Development

While this thread does not directly involve NFS client code, it is tangentially relevant as:

  1. It establishes precedents for how filesystem-related network protocols are organized in the kernel.
  2. The sunrpc subsystem (used by NFS) was explicitly cited as a model for handling similar code splits, suggesting that lessons from SMB Direct's reorganization may inform future NFS/sunrpc structural decisions.
  3. The discussion highlights ongoing efforts to properly integrate RDMA-based transports into the kernel networking stack, which could eventually benefit NFS over RDMA (NFS/RDMA) deployments.
