NFSD: Fix security leak in filehandle key tracepoint

Summary

NFSD: Secure Filehandle Key Update Reporting

Classification

Bug Fix / Security Hardening (NFSD server-side)

Summary

This week, Chuck Lever submitted a patch to address a security concern in the NFS server's (NFSD) filehandle signing key management tracepoints. The issue was identified by security researcher Jaeyeong Kim (fin@spl.team), who reported that the existing tracing mechanism leaked information that could potentially allow an attacker with access to the trace ring buffer to recover the secret filehandle signing key.

The Problem

The nfsd_ctl_fh_key_set tracepoint was originally designed to log operator activity when the filehandle signing key is updated via netlink commands. An earlier revision logged the key bytes directly, which was subsequently fixed by hashing the 16-byte key through crc32_le. However, as Chuck Lever explained in his patch submission:

"CRC32 is a linear projection of its input rather than a one-way function, and truncating any hash of fixed-size secret material leaves the key recoverable under offline brute force when the threat model includes an attacker with access to the trace ring."

This meant that while the key was not logged in plaintext, the CRC32 fingerprint was insufficient protection against an attacker who could perform offline brute-force attacks on the 16-byte key space.

The Solution

Rather than switching to a cryptographically secure hash (which might be overkill for the operational purpose of the tracepoint), Lever's patch changes the approach entirely. Instead of logging what the key is (even in hashed form), the tracepoint now answers the specific operational question it was meant to address: did the key actually change?

The patch modifies nfsd_nl_fh_key_set() to compare the incoming key bytes against the currently stored nn->fh_key. The tracepoint now outputs a simple boolean indicator:

  • "updated": when the stored key changed.
  • "unmodified": when the new key matches the existing one, or if the first set fails due to allocation errors.

As Lever stated in the commit message:

"The operational question the fingerprint was meant to answer is whether a NFSD_CMD_THREADS_SET call that carries an NFSD_A_SERVER_FH_KEY attribute actually replaced the active key or re-installed the value already in place. Answer that question directly..."

Community Response

The patch received swift and unanimous approval from the NFS subsystem maintainers:

  • Benjamin Coddington provided a Reviewed-by tag, endorsing the fix.
  • Jeff Layton also provided a Reviewed-by tag, confirming the approach was sound.

Significance for NFS Development

This fix is significant for several reasons:

  1. Security: It eliminates a potential side-channel leakage of the filehandle signing key, which is critical for NFSv4 security as it ensures filehandle integrity and authenticity.
  2. Minimalism: The solution demonstrates a principle of least privilege in logging—only exposing information necessary for operational debugging rather than cryptographic material or its derivatives.
  3. Responsiveness: The rapid review and approval highlight the maintainers' attentiveness to security reports, particularly those from external researchers.

The patch is marked as fixing commit 62346217fd72 ("NFSD: Add a key for signing filehandles") and is expected to be merged into the mainline kernel tree shortly.
