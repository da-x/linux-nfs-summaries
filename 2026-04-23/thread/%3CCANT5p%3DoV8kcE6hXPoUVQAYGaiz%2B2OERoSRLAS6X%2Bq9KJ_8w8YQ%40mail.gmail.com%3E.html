SMB Client VFS Lookup "Intent" and Open Call Optimization

SMB Client VFS Lookup "Intent" and Open Call Optimization

Overview

This thread, initiated by Shyam Prasad N on April 23, explores whether the SMB client's challenge with VFS lookup callbacks is unique to SMB or affects other network filesystems. The discussion centers on optimizing SMB2+ open calls by understanding the "intent" of a VFS lookup — i.e., whether the current dentry is intended to be opened as a leaf (regular file) or traversed as a directory.

Type: Protocol behavior investigation / potential client optimization (not a bug fix or new feature per se, but an exploration of protocol semantics that could inform future SMB client improvements).

The Problem

Shyam opened the thread by describing a constraint imposed by the SMB2+ protocol:

"SMB2+ protocol mandate that open call specifies if the file being opened is a directory or not (regular file)."

This means the SMB client, during the VFS lookup callback, must first attempt an open with one type flag, check the return status, and potentially retry with the other type. This two-step process adds overhead. Shyam asked whether the VFS could provide intent information to avoid this:

"From SMB client POV, it would have been good to know from VFS lookup callback if the current dentry is intended to be a leaf or not. This would enable the SMB client to decide which type of open to make first."

He also sought broader context:

"Wanted to understand if this is a problem for other filesystems or if it is specific to SMB protocol?"

Ralph Boehme's Response

Ralph Boehme replied on April 23, suggesting that the SMB client may not actually need to specify either FILE_DIRECTORY_FILE or FILE_NON_DIRECTORY_FILE:

"if you neither specify FILE_DIRECTORY_FILE nor FILE_NON_DIRECTORY_FILE the server is supposed to open the object regardless of the type."

This was relayed in Shyam's follow-up message outside this week's window, where Ralph's full quoted response appeared.

Evolution and Follow-Up (Outside Window)

Shyam responded on April 24 noting that the SMB2/3 protocol specification does not explicitly define this behavior:

"That's interesting. The spec does not seem to define this. Perhaps purposely? Will try and prototype a change to verify."

Tom Talpey then clarified on April 24 that this behavior is defined in MS-FSA (the SMB File System Architecture specification), not in the core SMB2/3 protocol:

"This would be filesystem behavior and therefore it would be in MS-FSA, not in the SMB2/3 protocol."

Tom cited section 2.1.5.1 of MS-FSA (page 60), which specifies conditions under which an open must succeed on a directory even when neither FILE_DIRECTORY_FILE nor FILE_NON_DIRECTORY_FILE is set:

"If CreateOptions.FILE_DIRECTORY_FILE is TRUE then StreamTypeToOpen = DirectoryStream... Else if CreateOptions.FILE_NON_DIRECTORY_FILE is FALSE, StreamNameToOpen is empty, StreamTypeNameToOpen is empty, Open.File is not NULL, and Open.File.FileType is DirectoryFile then StreamTypeToOpen = DirectoryStream"

Shyam acknowledged this on April 28:

"Thanks Tom. Will try some experiments with this."

Key Takeaways

  • The SMB client's VFS lookup callback optimization question may have a simpler solution than originally assumed: omitting both type flags may allow the server to open objects regardless of type, per MS-FSA semantics.
  • This is specific to the SMB protocol and its interaction with the Linux VFS layer; NFS does not face this same constraint because NFS lookups and opens follow different semantics.
  • No changes to the NFS client or VFS are implied by this discussion — it is an SMB-specific investigation.
  • Shyam plans to prototype a change based on these findings, which could reduce round-trips in the SMB client during path traversal operations.

Relevance to NFS

This thread has no direct impact on NFS client development. It was posted to the linux-nfs list likely because Shyam is exploring cross-filesystem VFS behavior and wanted to understand whether other network filesystems face similar challenges. The conclusion — that this is SMB-specific — means NFS developers can disregard this issue for their own work.
