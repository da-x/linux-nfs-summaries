RFC: Hardcoding sunrpc pool_mode to pernode and removing legacy modes

Summary

Discussion Overview

This week saw an RFC patch proposal from Jeff Layton aimed at simplifying the SunRPC server-side thread pool configuration by hardcoding pool_mode to pernode and removing all other legacy modes (auto, global, percpu). The discussion centers on NFS server (nfsd) infrastructure, specifically how RPC service threads are mapped to NUMA nodes.

Key Technical Arguments

The Proposal: Simplify by Hardcoding pernode

Jeff Layton proposed a significant cleanup of the svc_pool machinery in his RFC patch. The core argument is that the complexity of multiple pool modes is no longer justified:

"The SVC_POOL_AUTO/GLOBAL/PERCPU/PERNODE pool mode selection machinery was added when NUMA was new and the right default was unclear. Today, pernode is the right choice everywhere"

Layton outlined two key technical justifications:

  1. On multi-NUMA hosts: pernode provides one pool per node with proper thread affinity and NUMA-local memory allocation.
  2. On single-node hosts: pernode degenerates to exactly one pool, identical to the old "global" mode, with no performance penalty since svc_pool_for_cpu() short-circuits when sv_nrpools <= 1.

He also noted that the percpu mode was problematic:

"The percpu mode (one pool per CPU) created excessive pools relative to the number of threads most deployments run, and was only auto-selected in a narrow case (single node, >2 CPUs)."

The patch removes 202 lines of code while adding 29, effectively stripping out the SVC_POOL_* enum, mode selection heuristics, and associated switch statements.

Chuck Lever's Feedback: Backward Compatibility Concerns

Chuck Lever responded with a nuanced critique, agreeing with the end goal but raising significant concerns about the transition path:

"Generally, I think the end goal of making 'per-node' the default and only setting is correct. My comments below are about how we get there."

The Backward Compatibility Issue

Lever's primary concern was that the patch claims backward compatibility while actually breaking existing configurations. He pointed out that the module parameter interface would reject legacy values with -EINVAL:

"The concern is that the accepted input set has narrowed from four strings to one and the setters reject the legacy three with -EINVAL. For the module parameter that path runs at module load, so existing modprobe.d configs written any time in the last ~19 years will cause load-time parameter errors. Some might categorize that as a regression."

He clarified the distinction between interface shape preservation and behavioral compatibility:

"Or, put another way, the proposed patch implements something slightly different than true backwards compatibility. Userspace that previously set pool_mode=global/percpu/auto now gets -EINVAL, which technically speaking is a behavioral narrowing, not 'backward compatibility.'"

Proposed Alternative Approach

Lever suggested a more gradual deprecation strategy for kernel v7.2:

"I might go even further and suggest that perhaps for v7.2:

  • Change the behavior of 'auto' to be per-node
  • Add a deprecation warning that is emitted when setting other modes, but don't warn when the value is specifically the only accepted one. Then wait a few more cycles before removal of percpu and global."

This approach would accept-and-ignore old values (with warnings) rather than hard-failing, which Lever described as "the historically correct approach for this kind of obsoleted tuning knob."

Hardware-Specific Concerns

Lever also raised an important technical note regarding hardware platforms:

"The existing pernode path assumes every online node has both CPUs and some memory. nr_online_nodes on some platforms (e.g., certain ARM64, CXL) counts memoryless or CPU-less nodes; for_each_node_with_cpus() vs. for_each_online_node() matters here."

This highlights a potential bug in the current pernode implementation on specialized hardware architectures where NUMA nodes may lack CPUs or memory.

Evolution of the Discussion

The thread is brief, consisting of only two messages, but represents a classic kernel development pattern:

  1. RFC Proposal: Layton presents a radical simplification patch, acknowledging it might be "too radical as a single step."
  2. Constructive Feedback: Lever validates the direction but insists on a more careful backward-compatibility strategy and points out hardware edge cases.

Final Conclusions

No final decision was reached this week, as the thread is still in RFC stage. However, the key takeaways are:

  • Agreement on direction: Both developers agree that pernode should become the default and eventually the only mode.
  • Disagreement on pace: Layton's single-step removal approach was challenged by Lever's preference for a multi-cycle deprecation with accept-and-ignore semantics.
  • Technical debt identified: The percpu mode is acknowledged as creating excessive pools, and the hardware-specific behavior of nr_online_nodes on ARM64/CXL platforms needs attention.

This discussion falls under NFS server infrastructure cleanup rather than a bug fix or new feature. It addresses technical debt accumulated over ~19 years of sunrpc development since NUMA-aware pool modes were first introduced. The outcome will likely influence how nfsd scales on modern multi-NUMA servers and specialized hardware platforms.
