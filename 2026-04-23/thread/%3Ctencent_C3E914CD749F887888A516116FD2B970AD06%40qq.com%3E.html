NFSv4.1/pNFS: fix LAYOUTCOMMIT retry loop on OLD_STATEID

Summary

NFSv4.1/pNFS: Fix LAYOUTCOMMIT Retry Loop on OLD_STATEID

Type: Bug fix (NFS client / pNFS layout operations)

Overview

This week, Lei Yin submitted a patch addressing a critical bug in the NFSv4.1 parallel NFS (pNFS) client code — specifically, an unbounded retry loop that could occur during LAYOUTCOMMIT operations when the server returns NFS4ERR_OLD_STATEID. The patch was sent on April 22 as a single-message thread with no replies yet in this window.

The Problem

The bug resides in nfs4_layoutcommit_done(), the completion handler for LAYOUTCOMMIT RPCs. As described by Lei Yin:

"Without refreshing data->args.stateid, LAYOUTCOMMIT can keep retrying with the same stale stateid after OLD_STATEID, resulting in an unbounded retry loop."

When a server responds with NFS4ERR_OLD_STATEID, it signals that the client's layout state identifier has become stale — typically because the layout was recalled or revoked by the server. The existing code did not handle this error case in the LAYOUTCOMMIT completion path, meaning the client would blindly retry the same RPC with the now-invalid stateid indefinitely.

The Fix

The patch introduces proper NFS4ERR_OLD_STATEID handling in nfs4_layoutcommit_done() by:

  1. Calling nfs4_layout_refresh_old_stateid() to refresh the layout's stateid from the server.
  2. Restarting the LAYOUTCOMMIT RPC only after a successful stateid refresh, ensuring the retry uses a valid state identifier.

As Lei Yin notes:

"Refresh the layout stateid with nfs4_layout_refresh_old_stateid() and restart the RPC only after a successful refresh."

The patch also improves consistency across the pNFS codebase:

"This also keeps the OLD_STATEID recovery path consistent with other pNFS layout operations."

Technical Details

The change modifies fs/nfs/nfs4proc.c, adding 15 lines of code to handle the OLD_STATEID error case in the LAYOUTCOMMIT completion callback. The fix leverages the existing nfs4_layout_refresh_old_stateid() helper, which is already used by other pNFS layout operations (such as GET_LAYOUT and RETURN_LAYOUT) for stateid recovery — making this a natural extension of established patterns rather than an ad hoc solution.

Status

The patch was submitted as version 1 on April 22. No replies or reviews were recorded within this week's window. Given that a version 2 of this patch has appeared in related threads (see [PATCH v2] NFSv4.1/pNFS: fix LAYOUTCOMMIT retry loop on OLD_STATEID), it is likely that review feedback was received and incorporated shortly after this submission.

Significance

This is an important stability fix for NFS clients using pNFS layouts. An unbounded retry loop in a kernel path can lead to resource exhaustion, hung tasks, or degraded I/O performance — particularly in high-throughput storage environments where LAYOUTCOMMIT operations are frequent. By aligning the LAYOUTCOMMIT error handling with other pNFS layout operations, this patch also improves the overall robustness and maintainability of the NFS client's stateid recovery logic.
