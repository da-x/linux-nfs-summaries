NFSv4: Fix state recovery deadlock when server misses grace period

Summary

NFSv4 State Recovery Deadlock: Fix Attempted, Review Ongoing

Type: Bug fix (NFS client state recovery)

The Problem

Zhihao Cheng submitted a patch addressing a critical NFSv4 client deadlock that occurs when an NFS server restarts and the client enters state recovery. In the initial patch, Cheng described how "NFS server restart causes client to enter an infinite loop during state recovery." The state manager becomes stuck in NFS4CLNT_RECLAIM_NOGRACE processing, with the server repeatedly returning NFS4ERR_GRACE for each file iteration.

Cheng provided a detailed five-step trigger sequence:

  1. Client opens files; after server reboot, it enters nfs4_do_reclaim(RECLAIM_REBOOT). The server misses its grace period and returns NFS4ERR_NO_GRACE, causing the client to set NFS4CLNT_RECLAIM_NOGRACE.
  2. During nograce recovery of the first file, the server reboots again; an open request returns NFS4ERR_BADSESSION, setting NFS4CLNT_SESSION_RESET.
  3. Session reset fails with ETIMEDOUT due to network issues; nfs4_handle_reclaim_lease_error sets NFS4CLNT_LEASE_EXPIRED but does not set NFS4CLNT_RECLAIM_REBOOT.
  4. When nfs4_reclaim_lease runs, because NFS4CLNT_RECLAIM_NOGRACE is already set, it skips setting NFS4CLNT_RECLAIM_REBOOT — the bug introduced by commit b42353ff8d346 ("NFSv4.1: Clean up nfs4_reclaim_lease").
  5. The server never receives RECLAIM_COMPLETE, so subsequent file recovery attempts always receive nfserr_grace, causing an infinite retry loop.

The bug was reported by Li Lingfeng and a reproducer is available via Kernel Bugzilla 221399.

Proposed Fix and Review Feedback

Cheng's original fix attempted to set NFS4CLNT_RECLAIM_REBOOT in nfs4_reclaim_lease if NFS4CLNT_SERVER_SCOPE_MISMATCH is not set, ensuring the client sends RECLAIM_COMPLETE to the server first before proceeding with nograce recovery.

NFS client maintainer Trond Myklebust pushed back on this approach. In his review, he stated:

"This will cause the client to try to do reboot recovery in a situation where it isn't allowed to do so by the spec. We should never be setting NFS4CLNT_RECLAIM_REBOOT if NFS4CLNT_RECLAIM_NOGRACE is already set."

Myklebust proposed an alternative:

"One solution would be to just immediately call nfs4_state_end_reclaim_reboot() if NFS4CLNT_RECLAIM_NOGRACE is set."

Status: Unresolved

In his follow-up on April 23, Cheng questioned the spec interpretation, noting that "the client can only do reclaim reboot during the grace period (after server reboot)" and citing RFC 5661 Section 8.4.2.1 to argue that "any reclaim type messages should be rejected by server for NOGRACE state."

However, he also reported that Myklebust's suggested fix did not resolve the issue:

"I tried with your suggestion, and the problem still happens"

The thread ended without a resolution this week. The core tension is between the NFSv4 specification's restrictions on reclaim operations during the NOGRACE state and the practical need to ensure RECLAIM_COMPLETE is sent so the server can properly process subsequent nograce recovery requests. A revised approach will be needed in future iterations of this patch.
