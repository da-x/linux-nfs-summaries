pNFS Blocklayout: Harden GETDEVICEINFO Volume Parser Against Server-Side Attacks

Summary

This week, Werner Kasselman submitted a two-patch series to harden the pNFS blocklayout client's GETDEVICEINFO volume parser against potential security vulnerabilities exploitable by malicious NFS servers. The patches address out-of-bounds memory accesses, kernel stack overflows, and resource exhaustion issues in the recursive-descent parser located in fs/nfs/blocklayout/dev.c.

Technical Context and Bug Fix Classification

The discussion centers on critical bug fixes for memory safety and resource management in the NFS client. The existing parser trusted server-supplied data without sufficient validation:

  1. Out-of-Bounds (OOB) Heap Read: Server-supplied volume indices were used directly as array indexes without bounds checking, allowing a malicious server to trigger an OOB read at volumes[idx].type.
  2. Kernel Stack Overflow: The mutual recursion between bl_parse_deviceid and type-specific parsers lacked a depth limit. A cyclic or deeply chained topology could overflow the kernel stack.
  3. Integer Underflow: When nr_volumes was 0, the entry point computed nr_volumes - 1 as the starting index, underflowing to -1.
  4. Resource Exhaustion: The parser materialized a separate device tree node for every volume reference. In DAG-shaped topologies where shared child references caused exponential tree materialization, CPU and memory consumption were unbounded.

Evolution of the Discussion

Werner Kasselman introduced the fixes in PATCH 0/2, noting that the issues were found via static analysis (sqry). He provided a standalone test exercising all three bug classes and the fixes at tools/testing/pnfs-blocklayout/test-volume-parser.c.

Christoph Hellwig reviewed the patches on April 23, providing specific technical feedback:

On Patch 1/2: Hellwig suggested reducing the maximum recursion depth. While Werner proposed PNFS_BLOCK_MAX_DEPTH of 16, Hellwig argued:

"I think we can and should reduce the nesting depth. The only really useful nesting is mirroring + striping or concatenation. Giving a little extra slack is fine, but I think 4 (or 8 if you insist) should be enough."

He also recommended changing nr_volumes to an unsigned value since it is transmitted over the wire, and noted that the depth parameter should be unsigned:

"nr_volumes should be siwtched to an unsigned value, as it is over the wire."

On Patch 2/2: Hellwig commented on the naming convention for the parse operation cap. He suggested aligning with NFS specification terminology:

"The OPS naming is a bit odd, these are called 'volumes' in the specs. Which isn't a great name, but it generally helps to stick to the spec terms. So maybe rename the constant, and also add a comment explaining the limit to the code?"

He also proposed grouping the depth and ops counters into a struct to avoid adding more parameters to the function signature:

"Also use unsigned here as well. And maybe we should group the depth and ops into a struct instead of adding more and more parameters?"

On Patch 0/2: Hellwig briefly commented on the standalone test, noting it wasn't included in the patch series but suggesting Werner might want to send it out separately:

"Not really, but maybe you wanted to send it out? :)"

Final Conclusions

The thread concludes with positive feedback from Christoph Hellwig, who stated regarding Patch 1/2:

"Otherwise looks good, thanks a lot!"

And for Patch 2/2:

"Otherwise this looks good."

The key takeaways are:

  1. The patches address critical security vulnerabilities in the pNFS blocklayout client.
  2. Christoph Hellwig approved the general approach but requested minor adjustments: reducing the max depth constant, using unsigned types for wire-format values and counters, renaming constants to match spec terminology, and potentially refactoring parameters into a struct.
  3. A standalone test suite was mentioned but not included in the patch series.

This work represents an important hardening effort for the NFS client, ensuring robustness against malicious or malformed server responses.
