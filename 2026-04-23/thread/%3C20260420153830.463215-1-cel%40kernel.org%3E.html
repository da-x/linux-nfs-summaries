NFSD: Default max_block_size Increased to 4MB

Summary

NFSD: Default max_block_size Raised to 4MB for High-RAM Systems

This week, the NFS server (NFSD) subsystem saw a targeted performance enhancement aimed at reducing per-RPC overhead on modern high-bandwidth networks. The discussion centered on a patch by Chuck Lever that increases the default max_block_size from 1MB to 4MB, contingent on system memory availability.

Technical Context and Proposal

The change addresses a longstanding placeholder value introduced in commit 8a81f16de64f, which set NFSSVC_DEFBLKSIZE at 1MB. Chuck Lever explained that this was "well below the 4MB NFSSVC_MAXBLKSIZE ceiling, with the stated intent that a later change would raise the default."

The primary technical argument for the increase is performance optimization:

"Raising the default reduces per-RPC overhead on fast networks by amortizing header processing and scheduling costs across larger payloads." As proposed by Chuck Lever

To ensure stability on resource-constrained systems, the patch retains a safety mechanism: the nfsd_get_default_max_blksize() function uses a halving loop that constrains the returned value to 1/4096 of available RAM. Consequently, the new 4MB default only applies to systems with at least 16GB of RAM. Smaller machines continue to receive dynamically computed values as before.

Operational Implications

Lever highlighted a significant operational consideration for administrators managing large thread pools. Because svc_sock_setbufsize() calculates socket buffer sizes as nreqs * max_mesg * 2, quadrupling the message size has direct memory implications:

"Quadrupling max_mesg therefore quadruples the per-socket buffer reservation at a fixed thread count, which operators tuning large thread pools should account for." As noted by Chuck Lever

Additionally, the patch includes a critical caveat regarding client compatibility:

"Note well: Your NFS client implementation must support large read and write size settings to benefit from this change." As warned by Chuck Lever

Community Feedback and Conclusion

The patch received swift positive feedback from key maintainers:

  • Jeff Layton endorsed the change, noting its synergy with modern kernel features: "Makes sense, particularly with dynamic threading." He provided a Reviewed-by tag. As stated by Jeff Layton
  • Roland Mainz confirmed compatibility with the Microsoft NFS client implementation, stating: "Works with ms-nfs41-client," and also provided a Reviewed-by tag. As confirmed by Roland Mainz

Classification

  • Type: Performance Enhancement / Default Configuration Change.
  • Impact: NFSD (Server-side).
  • Client Relevance: High for NFS client developers; clients must support large read/write sizes to leverage the server's new default, though the server remains backward compatible with smaller block sizes if negotiated.

The discussion concluded with consensus on the patch's merit, balancing performance gains for high-end systems with safety guards for embedded or low-memory environments.
