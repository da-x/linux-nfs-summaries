syzbot Reports Slab-Out-of-Bounds Read in NFS/sunrpc Cache Sequence Iterator

Summary

syzbot Reports Slab-Out-of-Bounds Read in cache_seq_start_rcu

On April 21, syzbot reported a KASAN-detected slab-out-of-bounds read in the SUNRPC cache subsystem, triggered during NFS daemon (NFSD) export cache operations. The bug was discovered on an upstream kernel tree and is reachable via unprivileged user namespaces.

The Bug Report

syzbot filed the report with a detailed KASAN trace showing:

BUG: KASAN: slab-out-of-bounds in __cache_seq_start net/sunrpc/cache.c:1351 [inline] BUG: KASAN: slab-out-of-bounds in cache_seq_start_rcu+0x3fe/0x420 net/sunrpc/cache.c:1399

The out-of-bounds read occurs at address ffff88802ae92800, which is exactly 0 bytes to the right of a 2048-byte kmalloc-2k allocation — the NFSD export cache's hash table (EXPORT_HASHMAX * sizeof(struct hlist_head) == 256 * 8 = 2048 bytes). The read was triggered by a pread64() syscall on a procfs interface, walking through seq_read_iter() → cache_seq_start_rcu() → __cache_seq_start().

The allocation trace shows the hash table was created during network namespace initialization via cache_create_net() → nfsd_export_init() → nfsd_net_init(), triggered by an unshare() syscall.

Classification: Bug Fix

This is a bug fix for a memory safety issue in the SUNRPC cache subsystem, which underpins NFS client and server caching infrastructure. The bug involves reading one hlist_head past the end of the allocated hash table when iterating over cache entries via RCU-protected sequence files.

Root Cause Analysis

While no developer replies appeared within this week's window, related patches submitted shortly after reveal the root cause: a prior commit (7b546bd89975, "sunrpc/cache: improve RCU safety in cache_list walking") removed a bounds-checking guard (hash >= cd->hash_size) from __cache_seq_start(). When the iteration loop exhausts all empty buckets, hash equals cd->hash_size, and the stored position pointer encodes an index one past the last valid bucket. A subsequent pread() at the same file offset reuses this out-of-bounds index, leading to the slab-out-of-bounds read.

Context: Independent Fixes Submitted

Two independent patches addressing this issue were submitted in the days following the report (outside this week's window):

  1. Chuck Lever (cel@kernel.org) proposed a fix that rejects an input hash value out of range before touching the hash table, noting:

    "cache_seq_next() already bounds-checks its own loop; the start routine needs to be symmetric."

  2. Alessandro Zanni (alessandro.zanni87@gmail.com) submitted a similar fix that verifies the hash index is within hash_size before dereferencing the hash table.

Both patches cite the same syzbot report and target the same function (__cache_seq_start() in net/sunrpc/cache.c).

Significance for NFS Client Development

While this bug manifests primarily in the NFSD (server-side) export cache, the affected code resides in net/sunrpc/cache.c — shared infrastructure used by both NFS client and server components. The SUNRPC cache subsystem is critical for managing various RPC-level caches including authentication, address resolution, and directory delegation state. A memory safety bug in this core infrastructure affects the reliability of all NFS operations that depend on cached data.

Conclusion

This week's activity consists solely of the initial syzbot bug report. No developer discussion or resolution occurred within the reporting window. The bug represents a genuine memory safety vulnerability reachable via unprivileged user namespaces, and two independent fixes were submitted in the following days to address the out-of-bounds read in the RCU-protected cache sequence iterator.
