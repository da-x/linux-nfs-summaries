Linux NFS Client Does Not Set EXCHGID4_FLAG_SUPP_FENCE_OPS: Maintainer Explains Why

Summary

Discussion: Why Linux NFS Does Not Set EXCHGID4_FLAG_SUPP_FENCE_OPS in NFSv4.2 Mode

Background (Prior Week Context)

This thread originated on January 7, 2025, when Takeshi Nishimura asked why the Linux NFS client does not set EXCHGID4_FLAG_SUPP_FENCE_OPS during EXCHANGE_ID operations in NFSv4.2 mode. Citing RFC 7862 Section 14.1.4, Nishimura noted that the specification states:

"A client SHOULD request the EXCHGID4_FLAG_SUPP_FENCE_OPS capability when it sends an EXCHANGE_ID operation."

The thread remained dormant for over a year with no response from maintainers.

This Week's Activity (April 23, 2026)

Nishimura re-bumped the thread on April 23, quoting his original question and simply adding a "?" to prompt a response.

Linux NFS client maintainer Trond Myklebust provided a concise two-point explanation the same day:

  1. Minor versions are not allowed to introduce a feature and make it mandatory
  2. Why bother, since the server is going to set the flag whether or not the client requested it?

Key Technical Arguments

Nature of the Discussion: This is a protocol compliance / bug fix discussion, centering on whether the Linux NFS client should adhere to an RFC "SHOULD" recommendation for setting the EXCHGID4_FLAG_SUPP_FENCE_OPS flag during EXCHANGE_ID operations.

Trond Myklebust's Rationale:

  1. NFS Minor Version Semantics: The first argument references a core NFS protocol design principle: minor versions (such as NFSv4.2, which is a minor version of NFSv4) are not permitted to introduce features and simultaneously make them mandatory. This preserves backward compatibility — a server implementing only NFSv4.1 must still interoperate with clients advertising NFSv4.2 capabilities. Making fence operations mandatory via the client flag could violate this principle.

  2. Server-Side Determination: The second argument points out that per RFC 7862, "It is the server's return that determines whether this capability is in effect." Since the server will set EXCHGID4_FLAG_SUPP_FENCE_OPS in its reply regardless of whether the client requested it, there is no practical benefit to the client advertising support for it. The client gains nothing from setting the flag because the server's response is the authoritative source of truth for whether fence operations are supported.

Conclusion

The discussion concluded with Trond Myklebust's explanation that there is no need to change the Linux NFS client behavior. The rationale is twofold: (a) protocol design principles prohibit minor versions from making features mandatory, and (b) the server-side flag in the EXCHANGE_ID reply already determines fence operation support regardless of client input. No code changes or patches were proposed or accepted as a result of this thread.

The EXCHGID4_FLAG_SUPP_FENCE_OPS flag relates to NFSv4.2 session fencing, which allows servers to detect and handle stale client sessions — an important reliability mechanism. However, the Linux client's current behavior (not advertising support for it) does not impair functionality, as the server controls whether fence operations are enabled.
