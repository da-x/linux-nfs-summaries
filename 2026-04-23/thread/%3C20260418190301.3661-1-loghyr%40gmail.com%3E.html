NFS client: Fix directory mtime staleness under delegation after local mutations

Summary

Context and Problem Statement

This thread addresses a bug fix in the Linux NFSv4.2 client regarding stale metadata returned for directories holding a delegation after local mutations (such as rename, create, or unlink).

Tom Haynes reported that a cross-parent rename(2) operation leaves the client's cached modification time (mtime) on both parent directories stale, even though the server correctly updates its in-memory inode timestamps. The issue was identified as entirely client-side, stemming from an interaction between directory delegations and attribute invalidation logic.

As Haynes explained in the cover letter PATCH 0/1:

"The local rename path calls nfs4_update_changeattr_locked() and marks NFS_INO_INVALID_NLINK | NFS_INO_INVALID_DATA on each parent. The next stat(2) enters __nfs_revalidate_inode() which early-exits on a held directory delegation, returning the cached (stale) mtime without sending a GETATTR RPC."

He noted that this bug reproduces against "every NFSv4 server we tested (multiple Linux knfsd versions, reffs, FreeBSD NFS)," confirming it is a client-only defect. A known workaround was disabling directory delegations via echo N > /sys/module/nfsv4/parameters/directory_delegations.

Proposed Fix

In PATCH 1/1, Haynes proposed a minimal change to fs/nfs/inode.c. The patch modifies __nfs_revalidate_inode() to bypass the early-exit optimization (which trusts cached attributes when a delegation is held) if the cache validity flags for CHANGE, MTIME, or CTIME are already marked invalid.

"Keep the early-exit for the fast path, but take the RPC when CHANGE, MTIME, or CTIME are already marked invalid. The delegation alone is not a guarantee of cached-attr freshness once the code itself has flagged the cache as stale."

Haynes also considered an alternative approach—calling nfs_update_delegated_mtime_locked() from the rename completion path—but deemed the revalidation fix "defense-in-depth for any code path that marks an attr stale without taking the delegation back."

Review and Evolution

Anna Schumaker reviewed the patch on April 23rd, questioning whether the fix should be more generic. She asked:

"Is this a problem only for the attributes you've flagged, or do you think it would be a problem for size, nlink, or mode attributes as well? I'm asking because we have NFS_INO_INVALID_ATTR which includes all of these attributes which might make this a little more generic rather than carving out an exception an attribute at a time."

Haynes agreed in his response Re: PATCH 1/1:

"Agreed on at least size (and probably atime), which means a little more generic would be a good thing."

Conclusion

The discussion concluded with consensus that the fix should likely be broadened to use NFS_INO_INVALID_ATTR rather than checking specific timestamp flags individually. This ensures that any attribute marked stale by local mutation triggers a revalidation RPC, even when a directory delegation is held. The thread ended with Haynes acknowledging the need for this more generic approach, implying a v2 patch may follow incorporating Anna's suggestion.

This fix is critical for NFS client development as it restores correctness for timestamp semantics under directory delegations, ensuring userspace applications relying on stat() receive up-to-date metadata after local directory modifications.
