NFSD: Automatic NFSv4 State Revocation on Unmount via Netlink

Summary

Overview

This week, Chuck Lever submitted version 9 of a nine-patch series titled "Automatic NFSv4 state revocation on filesystem unmount" PATCH v9 0/9. The series introduces new netlink commands to allow administrators and userspace tools (like exportfs) to cleanly revoke NFSv4 state when unmounting filesystems or removing exports. This addresses a persistent operational challenge: unmounting an underlying filesystem fails with EBUSY if clients hold opens, locks, delegations, or layouts.

The series combines critical bug fixes for pre-existing layout revocation issues with new infrastructure to support fine-grained state cleanup via netlink, replacing the older procfs-based interfaces (/proc/fs/nfsd/unlock_ip and /proc/fs/nfsd/unlock_fs).

Critical Bug Fixes in Layout State Revocation

Before adding new features, the series patches two significant bugs in the existing admin-revoked layout state handling, originally introduced by commit 1e33e1414bec.

Infinite Loop in Layout Revocation

Patch 1/9 Fixes an infinite loop in nfsd4_revoke_states(). The function find_one_sb_stid() skips state IDs (stids) whose sc_status is non-zero. However, the SC_TYPE_LAYOUT case failed to set sc_status before calling nfsd4_close_layout(). As a result, the retry loop would repeatedly find the same layout stid, hanging the revoker indefinitely.

"The retry loop therefore finds the same layout stid on every iteration, hanging the revoker indefinitely."

Memory Leak in Layout Stid Cleanup

Patch 2/9 Handles layout stids in nfsd4_drop_revoked_stid(). Previously, when a client sent FREE_STATEID for an admin-revoked layout stid, the default branch released the lock and returned without unhashing or releasing the stid. The stid remained in the IDR and on the per-client list until the client was destroyed. The fix ensures the layout stid is properly removed from the per-client list and its reference count is dropped, triggering correct cleanup via nfsd4_free_layout_stateid().

Infrastructure Refactoring

To support the new netlink commands, Lever refactored the state revocation logic:

  • Patch 3/9 Extracts a utility function revoke_one_stid() to handle per-stateid revocation. This dispatches by state type and prepares the codebase for export-scoped revocation.
  • Patch 6/9 standardizes iteration over state IDs by replacing idr_for_each_entry_ul with a while loop using idr_get_next_ul().
  • Patch 7/9 Tracks svc_export in each nfs4_stid. This allows the server to identify which export a state ID was acquired through, enabling fine-grained revocation without walking inode dentry aliases.

New Netlink Commands for State Revocation

The core of the series introduces three new netlink commands, providing structured alternatives to the legacy procfs interfaces:

  1. NFSD_CMD_UNLOCK_IP Patch 4/9: Releases NLM file locks held by a specific client IP address. This is the netlink equivalent of writing to /proc/fs/nfsd/unlock_ip.

  2. NFSD_CMD_UNLOCK_FILESYSTEM Patch 5/9: Revokes all NFS state on a superblock. This mirrors /proc/fs/nfsd/unlock_fs and is intended for scenarios where an entire filesystem is being unmounted.

  3. NFSD_CMD_UNLOCK_EXPORT Patch 8/9: This is the most significant addition. It revokes NFSv4 state acquired through exports of a specific path, regardless of the client. Lever explains the design rationale:

"UNLOCK_FILESYSTEM means 'unmounting /data, release everything on this superblock.' UNLOCK_EXPORT means 'no clients remain for /data/projectA, release only the state acquired through exports of that path.'"

This command allows exportfs -u to clean up state when the last client for a given path disconnects, enabling the underlying filesystem to be unmounted even if other exports on the same device remain active. The design avoids auth_domain naming complexities by matching on path identity (dentry + vfsmount) rather than requiring the caller to identify specific clients.

Closing Cached File Handles

Patch 9/9 Closes cached file handles when revoking export state. Even after NFSv4 state is revoked, GC-managed nfsd_file entries in the file cache can keep the underlying filesystem busy. The new function nfsd_file_close_export() walks the hash table and closes eligible entries under the target export path, ensuring the filesystem can be unmounted cleanly.

Community Feedback

Christian Brauner responded to the cover letter, expressing approval of the architectural direction:

"Thanks for moving this into nfsd itself. That's great to see."

This refers to the series' evolution from earlier versions that proposed VFS-level changes (e.g., SRCU unmount notifier chains) to a solution implemented entirely within NFSD via netlink, which Brauner views as a positive consolidation of responsibility.

Conclusion

This mature v9 series, reviewed by Jeff Layton, resolves long-standing operational friction in NFS server administration. By fixing critical bugs in layout revocation and introducing fine-grained netlink commands for state cleanup, it enables safer and more flexible filesystem unmounting procedures. The NFSD_CMD_UNLOCK_EXPORT command is particularly notable for allowing administrators to remove individual exports without disrupting other active exports on the same filesystem.
