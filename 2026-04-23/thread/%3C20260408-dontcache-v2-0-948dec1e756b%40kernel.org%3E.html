DONTCACHE: Hybrid Flusher Proposal for Batching-Aware Writeback

Summary

DONTCACHE: Proposed Hybrid Flusher Approach Balances Batching and Selectivity

Overview

This week saw a single but significant contribution to the ongoing RWF_DONTCACHE writeback optimization thread. Ritesh Harjani (IBM) proposed a hybrid approach that attempts to reconcile two competing concerns raised in prior weeks: Jeff Layton's finding that per-inode writeback loses critical I/O batching benefits, and Christoph Hellwig's and Jan Kara's concern that whole-BDI flusher wakeup is too coarse-grained.

Classification: This is a performance optimization / bug fix discussion for existing RWF_DONTCACHE functionality in the mm/writeback subsystem, with implications for NFS server (NFSD) I/O modes. No new patches were submitted this week; the thread remains in architectural debate.

Prior Context (Brief)

Over the previous two weeks, Jeff Layton submitted v2 of a three-patch series replacing inline filemap_flush_range() calls with wakeup_flusher_threads_bdi() to offload DONTCACHE writeback from the writer's hot path. Two major concerns emerged:

  1. Coarse-grained writeback: Hellwig and Kara warned that kicking the entire BDI flusher could trigger excessive writeback of unrelated dirty pages, causing regressions in mixed workloads.
  2. Batching loss: Layton's extensive benchmarking demonstrated that per-inode writeback alternatives regressed by up to -32% in multi-writer throughput and -21% in random write performance due to lost I/O batching opportunities via writeback_sb_inodes().

Last week concluded with semantic agreement that DONTCACHE means "eventually write back, don't retain in cache" rather than guaranteeing immediate writeback, and rejection of per-inode writeback approaches.

This Week's Discussion

A Hybrid Proposal: Targeted Page Counts via Whole-BDI Flusher

On April 17, Ritesh Harjani responded to Layton's benchmark analysis with a synthesis of Hellwig's earlier suggestion and the batching requirements identified by Layton:

"So, if I understood it correctly, Christoph might be talking about a different approach here. Instead of kicking flusher thread to writeback pages for a single inode, if we can track the number of dontcache pages (get_nr_dontcache_pages()), then we can kick the flusher for those many target pages." Ritesh Harjani

The key insight is that this approach would:

  • Preserve I/O batching: By still using the whole-BDI flusher thread (rather than per-inode write_inode_now() calls), the blk_plug'd pass through all dirty inodes via writeback_sb_inodes() remains intact.
  • Limit writeback scope: Instead of triggering unbounded writeback based on total dirty pages (get_nr_dirty_pages), the flusher would be instructed to write back only a number of pages proportional to pending DONTCACHE folios (get_nr_dontcache_pages()).

Harjani acknowledged a trade-off:

"I think this way we are still reducing the dirty page cache pressure - the problem which RWF_DONTCACHE is supposed to solve. But I guess, that doesn't necessarily always mean that only dontcache marked folios will get written." Ritesh Harjani

This aligns with Hellwig's earlier refinement from last week: "I'd only expedite writing by the number of pending dontcache folios. It would still write the least recently dirtied inodes." The distinction is that LRU ordering is preserved (maintaining batching efficiency), but the volume of writeback is capped proportionally to DONTCACHE pressure rather than total dirty pressure.

Harjani concluded with optimism about this approach:

"If we implement that then, this should still help with the batching problem you mentioned and hopefully should not cause a major regression for the workload which Jan mentioned." Ritesh Harjani

NFS Client/Server Relevance

While this thread targets core mm/writeback infrastructure, it directly impacts NFS server (NFSD) performance. The RWF_DONTCACHE mode is one of three I/O modes configurable via NFSD debugfs controls. Improving dontcache write performance benefits NFS workloads relying on this mode for low-latency, cache-bypassing writes. Layton's benchmark suite explicitly includes tests against an NFS server using fio's libnfs backend.

For NFS client development, the implications are indirect but noteworthy: improved NFSD dontcache performance reduces server-side writeback latency, which can improve overall NFS round-trip times for clients performing synchronous or metadata-heavy operations against servers using this I/O mode.

Final Status

The thread remains open with no v3 patches submitted. Harjani's hybrid proposal represents a potential path forward that:

  1. Retains the whole-BDI flusher mechanism (preserving I/O batching)
  2. Introduces DONTCACHE-aware page counting (get_nr_dontcache_pages()) to limit writeback volume
  3. Accepts that non-DONTCACHE pages may be written incidentally, but caps total pressure

Key open items remain:

  • Implementation details for the new WB_start_dontcache bit and node counter infrastructure Hellwig originally proposed
  • Whether Jens Axboe (block layer maintainer) will weigh in on the approach
  • Validation that this hybrid mechanism avoids both the batching regressions identified by Layton and the noisy-neighbor regressions described by Kara
