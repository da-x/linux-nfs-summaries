NFS: Fix EOF updates after NFSv4.2 fallocate/zero-range with delegation

Summary

NFS Client Fix: Correcting EOF Updates After NFSv4.2 fallocate/zero-range

Overview

This week saw a targeted bug fix submission addressing a regression in the NFS client related to file size (EOF) handling when using NFSv4.2 fallocate and zero-range operations while holding a write delegation. The patch was submitted by Dai Ngo of Oracle on April 23, 2026.

Technical Context: A Delegation-Induced Regression

The issue centers on a subtle but critical inconsistency between the server-side state and the client's cached inode metadata. As Dai Ngo explained in the patch description:

"Generic/075 reliably exposes a regression when the client holds an NFSv4 write delegation: ZERO_RANGE/ALLOCATE extends the file on the server, but the local inode keeps the old i_size."

The problem manifests as follows:

  1. The NFS client holds a write delegation, which typically allows it to cache writes locally without constant server round-trips.
  2. An fallocate or zero-range operation (NFSv4.2 features) is issued, which extends the file on the server.
  3. However, the local inode's i_size remains stale because the post-operation attribute refresh intentionally avoids updating i_size while a delegation is outstanding — under the assumption that the client itself is authoritative for size changes during a delegation.
  4. Crucially, the cached EOF was never marked as stale, leading to inconsistent state.

The result is a test failure in xfstests generic/075, which reports a "Size error" due to this mismatch.

The Fix

Dai Ngo's patch modifies _nfs42_proc_fallocate() in fs/nfs/nfs42proc.c to explicitly handle the EOF update on success. The key changes are:

  1. Bump i_size locally when the operation extends the file, ensuring the client's inode reflects the new size immediately.
  2. Mark NFS_INO_INVALID_BLOCKS, acknowledging that the block count may also have changed as a result of the allocation or zeroing operation.

As stated in the patch:

"Update _nfs42_proc_fallocate() so that on success it: bumps i_size when the operation extends the file, and marks NFS_INO_INVALID_BLOCKS since the block count can also change."

The fix was validated against xfstests generic/075 over NFSv4.2, confirming that the regression is resolved.

Classification

This discussion represents a bug fix rather than a new feature or protocol change. It addresses a correctness issue in the NFS client's handling of NFSv4.2 space management operations under delegation scenarios — an important area for data integrity and consistency in enterprise NFS deployments.

Conclusion

With only one message in this thread during the current week, there was no extended debate or review cycle captured in this window. The patch stands as a standalone fix submitted late in the week. Given its focused scope and clear test validation, it represents a straightforward correction to a known regression path in NFSv4.2 client behavior.
