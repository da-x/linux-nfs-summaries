nfsd: Fix file change detection in CB_GETATTR per RFC 8881

Summary

This thread addresses a bug fix in the NFS server (nfsd) regarding how it detects file modifications during delegation callbacks, specifically aligning implementation with RFC 8881.

Issue and Technical Argument

Scott Mayhew submitted a patch to correct the logic used by nfsd when processing CB_GETATTR replies from clients holding write delegations. The core issue was that the server was comparing a cached file size (stored in the delegation record) against the size reported by the client.

Mayhew argued that this approach violates RFC 8881, Section 10.4.3:

"RFC 8881, section 10.3 doesn't say anything about caching the file size in the delegation record, nor does it say anything about comparing a cached file size with the size reported by the client in the CB_GETATTR reply for the purpose of determining if the client holds modified data for the file."

He clarified that the RFC mandates comparing the current file size (retrieved from the filesystem) against the client's report:

"What section 10.4.3 of RFC 8881 does say is that the server should compare the current file size with size reported by the client holding the delegation in the CB_GETATTR reply, and if they differ to treat it as a modification regardless of the change attribute retrieved via the CB_GETATTR."

The bug caused the server to incorrectly believe a client held modified data even after the client had flushed changes, leading to unnecessary updates to mtime, ctime, and the change attribute on subsequent callbacks.

Resolution and Review

The patch modifies nfsd4_deleg_getattr_conflict() to use vfs_getattr() to obtain the current file size for comparison, while retaining the cached field only for encoding attributes back to the client.

Jeff Layton provided a quick review:

"Reviewed-by: Jeff Layton jlayton@kernel.org"

Chuck Lever accepted the patch for inclusion in an early 7.1-rc pull request but noted several minor code quality concerns:

  1. Kernel-doc: The comment for nfsd4_deleg_getattr_conflict needs updating due to parameter name changes.
  2. Stack Usage: He expressed concern about allocating a second struct kstat on the stack alongside one already allocated by the caller, suggesting verification with scripts/checkstack.pl.
  3. Optimization: He suggested skipping the new vfs_getattr() call if ncf_file_modified is already true, as the result wouldn't change the outcome.

Lever also noted a pre-existing inefficiency:

"Also, after a successful delegation recall, proceeding with CB_GETATTR comparison logic is probably unnecessary. But that particular control flow predates your patch."

Conclusion

The discussion concluded with the patch being accepted for the upcoming kernel release. The fix ensures strict compliance with RFC 8881, preventing false positives in file modification detection and reducing unnecessary metadata updates on the server side.
