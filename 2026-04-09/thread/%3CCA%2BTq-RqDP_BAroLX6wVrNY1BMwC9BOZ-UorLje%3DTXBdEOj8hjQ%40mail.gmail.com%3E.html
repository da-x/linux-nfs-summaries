NFSD: COMPOUND reply tag padding not zeroed?

Summary

Issue Identification: Uninitialized XDR Padding in NFSD COMPOUND Replies

Hiroyuki Sato, while implementing an NFSv4 client in Rust, identified a potential bug in the Linux NFS server (NFSD) regarding how it handles XDR padding for the COMPOUND reply tag. He reported that when sending a COMPOUND request with a tag such as "create_session" (14 bytes), the reply should include XDR padding to align to a 4-byte boundary (\x00\x00). However, on AlmaLinux 9 (kernel 5.14) and confirmed on Linux 7.0-rc7, he observed that these padding bytes were sometimes non-zero (e.g., \xff\xff or 0x69) approximately once every five attempts As reported by Hiroyuki Sato.

Technical Analysis

Sato traced the issue to two functions in the NFSD codebase:

  1. nfsd4_proc_compound(): Reserves space for taglen, tag, and opcnt using xdr_reserve_space().
  2. nfs4svc_encode_compoundres(): Copies the tag payload via memcpy() but then advances the pointer by XDR_QUADLEN(resp->taglen) without explicitly zeroing the padding bytes.

"The pointer is then advanced using: p += XDR_QUADLEN(resp->taglen); but the padding bytes do not appear to be explicitly zeroed. As a result, it seems possible that uninitialized data remains in the padding region..." Analysis by Hiroyuki Sato

Sato provided a preliminary patch that explicitly zero-fills the XDR padding, which resolved the issue in his testing Proposed fix by Hiroyuki Sato.

Protocol Clarification and Conclusion

Chuck Lever, a key NFSD maintainer, clarified the NFSv4/XDR protocol requirements regarding padding:

"I think the rules are:

  1. The sender SHOULD clear the bytes in an XDR pad but doesn't have to
  2. The receiver MUST ignore the bytes in an XDR pad" Clarification by Chuck Lever

While the issue is technically a violation of the "SHOULD" recommendation rather than a strict protocol error (since receivers must ignore padding), Lever encouraged Sato to submit a proper fix. He advised:

"Feel free to clean up your fix and send it as a contribution with a full patch description (Signed-off-by, Fixes tags, etc etc)." Encouragement by Chuck Lever

Sato confirmed he would prepare and submit a formal patch Acknowledgement by Hiroyuki Sato.

Summary

This thread highlights a minor NFSD bug where uninitialized memory could leak into XDR padding bytes in COMPOUND replies. Although not a critical security or stability issue due to the receiver's obligation to ignore padding, the discussion resulted in an agreement to clean up the code to comply with XDR best practices. A formal patch is expected from Hiroyuki Sato.
