nfsd: Fix mtime/ctime Updates for CLONE/COPY with Delegated Attributes

Summary

This thread covers a bug fix series submitted by Olga Kornievskaia to address incorrect metadata handling in the NFS server (nfsd) when CLONE and COPY operations are performed on files with active write attribute delegations. The discussion involves detailed code review from Chuck Lever, uncovering both logging concerns and a potential reference-counting bug in asynchronous copy handling.

Background: Delegated Attributes and NOCMTIME

When an NFS client obtains a write delegation with delegated attributes, the server opens the file with the NOCMTIME flag. This prevents modifying operations from updating the server's view of mtime (modification time) and ctime (change time), ensuring consistency with the client's delegated metadata cache. However, this optimization inadvertently suppressed timestamp updates for CLONE and COPY operations, causing xfstest generic/407 to fail.

Olga explained the regression:

"When delegated attributes are given on open, the file is opened with NOCMTIME and modifying operations do not update mtime/ctime as to not get out-of-sync with the client's delegated view. However, for CLONE operation, the server should update its view of mtime/ctime and reflect that in any GETATTR queries." Olga Kornievskaia

The series fixes the original commit e5e9b24ab8fa ("nfsd: freeze c/mtime updates with outstanding WRITE_ATTRS delegation") by explicitly updating timestamps after these operations complete successfully.

The Patch Series (v2)

Olga submitted a three-patch series [id://20260408190008.85082-1-okorniev@redhat.com]:

  1. Patch 1/3: Updates mtime/ctime on the destination file after a synchronous CLONE operation completes successfully, adding ATTR_DELEG handling.
  2. Patch 2/3: Updates timestamps for synchronous COPY operations when a positive number of bytes are copied.
  3. Patch 3/3: Handles asynchronous COPY, updating timestamps upon completion of the copy work (not during the initial compound processing). This patch is noted as "the trickiest" because the async copy thread lacks a direct dentry reference, requiring Olga to maintain a reference on the destination dentry while the copy runs.

Review and Technical Arguments

Chuck Lever provided two key pieces of feedback:

1. Logging Failures in CLONE (Patch 1/3) Lever noted that nfsd4_finalize_deleg_timestamps() already logs failures from notify_change(), which can fail via security hooks or filesystem-specific ->setattr methods. He questioned whether the new code path should also log errors:

"nfsd4_finalize_deleg_timestamps() invokes the same call and logs failures. notify_change() can fail through security_inode_setattr() or the filesystem's ->setattr method. Is it worth logging the failure (or adding a trace point)? (I don't really know, just asking here)." Chuck Lever

2. Potential Dentry Reference Underflow in Async COPY (Patch 3/3) Lever identified a subtle bug in the async copy error handling. If the copy fails before writing any bytes (wr_bytes_written == 0), the dput() is skipped, but the dget() taken earlier in nfsd4_copy() is never released:

"If the async copy fails before writing any bytes (wr_bytes_written == 0), the dput is skipped but the dget taken in nfsd4_copy() is never released elsewhere. This might happen when _nfsd_copy_file_range() fails on the first iteration, when nfs42_ssc_open() fails for inter-SSC copies, or when kthread_should_stop() fires before any bytes are copied." Chuck Lever

He proposed a cleaner logic structure:

"Rearranging the logic a little might avoid the issue: if (copy->d_dst) { if (copy->cp_res.wr_bytes_written > 0) nfsd_update_cmtime_attr(copy->d_dst); dput(copy->d_dst); }" Chuck Lever

Evolution and Conclusion

Olga responded to Lever's feedback, proposing a refactoring that would extract the notify_change() call into a shared function. She also reconsidered her approach to dentry management in the async copy case:

"Well, I'm now thinking of stripping out that piece that calls notify_change() in nfsd4_finalize_deleg_timestamps() into its own function and call it from both places?" Olga Kornievskaia

She further questioned whether she needed to maintain a separate dentry reference at all:

"Now that I see that nfsd4_finalize_deleg_timestamps() gets a dentry from file->fh_path.dentry, I'm thinking I don't need to save a dentry in the copy case and get it from copy->nf_dst->nf_file->fh_path.dentry? I'm assuming then I no longer need to dget/dput then?" Olga Kornievskaia

The thread concludes with Olga planning a v3 of the series that addresses both the logging consistency and the dentry reference management, potentially simplifying the async copy path by leveraging existing file structure references rather than maintaining explicit dentry pins.

Context within Broader NFS Development

This fix is part of a broader push this week to correct metadata handling in the presence of delegations:

  • Scott Mayhew's series fixing CB_GETATTR file change detection per RFC 8881 (summarized separately) addressed similar timestamp staleness issues during delegation callbacks.
  • Olga's earlier fix for GET_DIR_DELEGATION error handling when VFS leases are disabled was applied to nfsd-testing.
  • Jeff Layton's large CB_NOTIFY series for directory delegations is under active review, highlighting the ongoing maturation of delegation support in the Linux NFS server.
