nfsd: GET_DIR_DELEGATION Error Handling Fix When VFS Leases Disabled

Summary

nfsd Bug Fix: GET_DIR_DELEGATION Error Handling When VFS Leases Are Disabled

Summary

This thread concerns a bug fix in the Linux NFS server (nfsd) addressing incorrect error handling for the GET_DIR_DELEGATION compound operation when VFS leases are disabled on the server. The patch was submitted, reviewed, and applied within a single day (April 3, 2026).

Background and Context

This fix is part of an ongoing series of improvements to directory delegation support in the NFS server. Earlier this week, Olga Kornievskaia also submitted a related client-side fix for RENAME attribute staleness with directory delegations see prior summary. Additionally, Jeff Layton's larger 24-patch series adding CB_NOTIFY callback support for directory delegations was under active review this week see prior summary, highlighting the broader development momentum around directory delegation functionality.

The Problem

Olga Kornievskaia reported that running xfstest generic/309 on a server with leases disabled caused GET_DIR_DELEGATION to return EINVAL, which is an inappropriate error code for this scenario:

"When leases are disabled on the server, running xfstest generic/309 leads to an error because GET_DIR_DELEGATION returns EINVAL." — Olga Kornievskaia

The root cause was that nfsd_get_dir_deleg() could fail in multiple ways—memory allocation failures, leases being disabled, or the delegation already being held—but only the "already held" condition was translated to the NFSv4 protocol error NFS4ERR_GDD4_UNAVAIL (directory-delegation-is-unavailable). Other failure conditions, including -EINVAL from disabled leases, were passed through as generic errors.

The Fix and Technical Discussion

Olga's patch removes special-case error handling, allowing all failure conditions from kernel_setlease() to be translated to GDD4_UNAVAIL. She noted her uncertainty about whether all kernel errors should be treated this way:

"I'm unsure if kernel_setlease() can return some other error that shouldn't be converted to GDD4_UNAVAIL. Alternatively, I propose to recognize ENOMEM, EINVAL and EAGAIN as errors to translate to GDD4_UNAVAIL." — Olga Kornievskaia

Chuck Lever provided a nuanced review, clarifying that -EINVAL from disabled leases is actually a permanent condition rather than a temporary one:

"This is a bit misleading. -EINVAL from disabled leases is a permanent condition, not temporary, in the sense that retrying the request is going to get the same error until the server administrator modifies the server configuration to enable leases again." — Chuck Lever

However, Lever agreed with the overall approach because directory delegations are advisory in nature:

"However, since directory delegations are advisory, IMO GDD4_UNAVAIL is an appropriate response for both temporary and permanent inability to grant a directory delegation." — Chuck Lever

Jeff Layton offered an alternative perspective, suggesting that -EINVAL might warrant a different error code to signal to clients that the feature is fundamentally unsupported:

"ISTM that returning a hard error in that case is probably the correct thing to do. Maybe we should translate -EINVAL to something like NFS4ERR_NOTSUPP, so the client doesn't keep trying to get dir delegations that will never be granted?" — Jeff Layton

Conclusion

Despite the discussion about whether NFS4ERR_NOTSUPP might be more semantically appropriate for the permanently-disabled-leases case, Chuck Lever applied the patch as-is to the nfsd-testing tree:

"Applied to nfsd-testing, thanks!" — Chuck Lever

The fix (commit 374af81f6188) is a minimal four-line deletion from fs/nfsd/nfs4proc.c, removing the special-case handling that only translated the "already held" condition. This ensures that all failure modes of nfsd_get_dir_deleg() consistently return NFS4ERR_GDD4_UNAVAIL, allowing clients to handle the unavailability of directory delegations gracefully regardless of the underlying cause.
