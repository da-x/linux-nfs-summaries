NFSv4.2 COPY Timestamp Fix: Server-Side vs Client Workaround Debate

NFSv4.2 COPY Timestamp Bug: Server-Side Fix vs. Client Workaround Debate

Overview

This thread is a bug fix discussion concerning the Linux NFS client's handling of attribute updates after an NFSv4.2 COPY operation when delegated timestamps are present. Last week, Olga Kornievskaia submitted a patch to address stale ctime and mtime values on the client side after a server-side copy. This week, Jeff Layton weighed in with a compelling argument for fixing the problem at its source — the NFS server — rather than applying a client-side workaround, shifting the focus of the discussion toward server-side semantics and compound operation design.

Background (Bridged from Prior Week)

Last week, Kornievskaia submitted a patch addressing a bug where the client's cached timestamps remain unchanged after an NFSv4.2 COPY operation:

"A similar to generic/407 test can be done with a COPY operation instead of CLONE (reflink). And it leads to same problem that ctime and mtime saved before doing a 'cp' operation are the same as after." — Olga Kornievskaia

She also raised an architectural question about whether appending a GETATTR to the COPY compound (as was done for REMOVEXATTR) might be a preferred alternative, noting uncertainty about whether servers reliably update their own attributes on COPY.

This Week's Discussion

Jeff Layton Advocates for Server-Side Correctness

On April 3, Jeff Layton responded with a strong argument that the server — not the client — should be responsible for updating timestamps during a COPY operation:

"I think that'd ultimately be more efficient, and I think the server should be updating the c/mtime on COPY, even if there is an outstanding timestamp delegation. The server is doing the COPY. The client isn't really involved so why should it be trying to stamp the file?" — Jeff Layton

Layton further argued that adding a GETATTR to the COPY compound is both cheap and efficient, since the server-side inode is likely already in cache:

"A GETATTR is cheap and in this case, the inode will even likely be in cache on the server. We might as well update the attributes without forcing another round trip in this case, since we pretty much know that they will have changed." — Jeff Layton

He also identified a potential root cause on the server side: the FMODE_NOCMTIME flag may be set on the destination file's open file description, preventing timestamp updates. His proposed fix would involve temporarily disabling this flag during the copy operation:

"If the server isn't updating its attrs on COPY in this case, then it's probably because we're using the open file description in the destination stateid and it has FMODE_NOCMTIME set. We can probably fix this by just turning that flag off while the copy is running, and then reenabling it before returning." — Jeff Layton

Kornievskaia Signals Readiness for a GETATTR-Based Approach

On April 8, Kornievskaia responded, acknowledging Layton's point and indicating that her original patch may be unnecessary if the server properly updates timestamps:

"This patch isn't needed if the server updates mtime/ctime after doing a COPY." — Olga Kornievskaia

She also revealed that she had already prepared a patch to add GETATTR to the COPY compound, offering to post it for review:

"In the process of all the work, I have also created a patch that adds a GETATTR to the COPY compound. I'm not sure if it's needed or not but I can post it." — Olga Kornievskaia

Evolution of the Discussion

The conversation has evolved from a straightforward client-side bug fix toward a more nuanced debate about where responsibility for timestamp correctness should lie:

  1. Initial patch (last week): Kornievskaia proposed a 6-line client-side fix to invalidate timestamps after COPY.
  2. Self-review (last week): She questioned whether a GETATTR-in-compound approach would be superior, echoing Layton's earlier pattern for REMOVEXATTR.
  3. Layton's intervention (this week): He argued that the server should update timestamps natively during COPY, and that a GETATTR in the compound is both efficient and semantically correct. He also identified FMODE_NOCMTIME as a likely culprit on the server side.
  4. Kornievskaia's response (this week): She conceded that her patch may be unnecessary if the server behavior is corrected, and offered to post her GETATTR compound patch for consideration.

Key Technical Arguments

  • Server-side responsibility: Layton argues that since the server performs the COPY, it should update ctime/mtime regardless of outstanding timestamp delegations.
  • Efficiency of GETATTR in compound: Both participants agree that appending GETATTR to the COPY compound avoids an extra round trip, as the inode is likely cached on the server.
  • FMODE_NOCMTIME as root cause: Layton identifies a specific kernel flag (FMODE_NOCMTIME) on the destination file description as the probable reason timestamps are not being updated by the server.
  • Client-side workaround vs. proper fix: The original patch is a client-side bandage; the preferred path forward appears to be either fixing the server's timestamp update behavior or ensuring the compound includes GETATTR to fetch fresh attributes.

Conclusion and Outlook

The discussion has shifted away from the original 6-line client-side patch toward two potential resolution paths:

  1. Server fix: Temporarily disable FMODE_NOCMTIME on the destination file during COPY operations so the server properly updates timestamps.
  2. Client compound enhancement: Add GETATTR to the COPY compound request, ensuring the client receives fresh attributes without an extra round trip.

Kornievskaia's offer to post her GETATTR patch suggests this approach may move forward in the near term. The thread remains open, with no final resolution or merged patch as of this week's cutoff. This bug fix is significant for NFS client development because it ensures filesystem semantic correctness — accurate timestamps are critical for backup systems, build tools, and any application relying on ctime/mtime accuracy after server-side copy operations.
