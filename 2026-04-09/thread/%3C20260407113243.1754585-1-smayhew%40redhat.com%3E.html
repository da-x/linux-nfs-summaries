nfsd: Fix file change detection in CB_GETATTR

Summary

This thread addresses a bug fix in the NFS server (nfsd) regarding how it detects file modifications when handling CB_GETATTR callbacks for delegated files. The discussion centers on Scott Mayhew's patch v3, which corrects the logic used to determine if a client holding a write delegation has modified data.

Technical Context and Bug Description

The core issue lies in the implementation of RFC 8881, section 10.4.3. According to the RFC, the server should compare the current file size on disk with the size reported by the client in the CB_GETATTR reply. If they differ, it indicates a modification, regardless of the change attribute.

Scott Mayhew explained that the previous implementation incorrectly compared a cached file size (stored in the delegation record) against the client's report. This led to two significant problems:

  1. The server would falsely believe the client held modified data even if the client had already flushed changes to the server prior to the CB_GETATTR.
  2. Subsequent CB_GETATTR callbacks would cause unnecessary updates to mtime, ctime, and the change attribute, even if the client made no further updates.

"Doing otherwise would cause the server to believe the client holding the delegation has a modified version of the file, even if the client flushed the modifications to the server prior to the CB_GETATTR." Scott Mayhew

The Fix

The patch modifies nfsd4_deleg_getattr_conflict() to obtain the current file size via i_size_read() rather than relying on the cached value in the delegation record. While the ncf_cur_fsize field is retained for returning the file size to nfsd4_encode_fattr4(), it is no longer used for change detection logic. Additionally, if a delegation is recalled due to a lack of client response, the patch skips the logic that checks nfs4_cb_fattr fields.

"Modify nfsd4_deleg_getattr_conflict() to obtain the current file size via i_size_read(). Retain the ncf_cur_fsize field, since it's a convenient way to return the file size back to nfsd4_encode_fattr4(), but don't use it for the purpose of detecting file changes." Scott Mayhew

Review and Cleanup

Chuck Lever reviewed the patch, approving the technical fix but noting a minor grammatical correction in the commit message ("with size reported" should be "with the size reported"). He also suggested an additional cleanup opportunity.

"The grant-time write of ncf_cur_fsize has been dead with respect to the consumer (nfs4xdr.c:3930) since the original commit c5967721e106. Your patch removes the last other reader of that value -- the now-incorrect size comparison -- making the dead write obvious." Chuck Lever

Conclusion

The discussion concludes with the patch addressing a protocol compliance issue in NFSv4.2+ delegation handling. The fix ensures that file change detection relies on real-time disk state rather than stale cached values, preventing false positives for modified files and unnecessary metadata updates. Chuck Lever's feedback highlights an opportunity to further clean up dead code related to ncf_cur_fsize in a subsequent patch or version.
