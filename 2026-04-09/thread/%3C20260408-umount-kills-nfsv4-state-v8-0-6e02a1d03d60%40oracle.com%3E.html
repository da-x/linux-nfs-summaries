NFSD: Netlink-based NFSv4 state revocation and layout bug fixes (v8)

Summary

Overview

Chuck Lever posted version 8 of a nine-patch series introducing new NFSD netlink commands for fine-grained NFSv4 state revocation, alongside two important bug fixes in layout state handling. The series addresses the longstanding problem that client-held NFSv4 state (opens, locks, delegations, layouts) prevents unmounting exported filesystems.

"When an NFS server exports a filesystem and clients hold NFSv4 state (opens, locks, delegations), unmounting the underlying filesystem fails with EBUSY."

Bug Fixes: Layout State Revocation Hangs

Before introducing the new netlink infrastructure, the series patches two pre-existing bugs in layout state revocation reported by Dai Ngo:

Patch 1/9 fixes an infinite loop in nfsd4_revoke_states(). The function find_one_sb_stid() skips stateids whose sc_status is non-zero, but the layout case never set sc_status before calling nfsd4_close_layout(), causing the revoker to spin indefinitely on the same layout stateid.

"The retry loop therefore finds the same layout stid on every iteration, hanging the revoker indefinitely."

Jeff Layton acknowledged this as a "Nice catch."

Patch 2/9 fixes a related issue where nfsd4_drop_revoked_stid() had no handler for layout stateids. When a client sent FREE_STATEID for an admin-revoked layout, the stateid remained in the IDR and on the per-client list until the client was destroyed. The patch adds proper cleanup by removing the layout stid from the per-client list and calling nfs4_put_stid().

New Feature: Three Netlink Unlock Commands

The core of the series replaces the legacy procfs interfaces (/proc/fs/nfsd/unlock_ip and /proc/fs/nfsd/unlock_fs) with structured netlink equivalents, plus a new export-scoped command:

  1. NFSD_CMD_UNLOCK_IP (Patch 4/9): Releases NLM locks held by a specific client IP address. This is the netlink equivalent of write_unlock_ip. The patch also updates the tracepoint to use __sockaddr for structured logging.

  2. NFSD_CMD_UNLOCK_FILESYSTEM (Patch 5/9): Revokes all NFS state on a superblock, equivalent to write_unlock_fs. It cancels async copies, releases NLM locks, and revokes NFSv4 state for the given filesystem path.

  3. NFSD_CMD_UNLOCK_EXPORT (Patch 8/9): A new capability that revokes NFSv4 state acquired through exports of a specific path, regardless of client. This enables administrators to unexport a single path on a shared filesystem without disturbing other exports on the same device.

"UNLOCK_FILESYSTEM and UNLOCK_EXPORT serve different intents. UNLOCK_FILESYSTEM means 'unmounting /data, release everything on this superblock.' UNLOCK_EXPORT means 'no clients remain for /data/projectA, release only the state acquired through exports of that path.'"

To support export-scoped revocation, Patch 7/9 adds an sc_export field to struct nfs4_stid, recording which export each stateid was acquired under. This avoids the need to walk inode dentry aliases at revocation time and sidesteps auth_domain naming complexity.

"The path-only design for UNLOCK_EXPORT avoids the auth_domain naming complexity (use_ipaddr vs hostname-based domains) by not requiring the caller to identify a specific client."

Patch 9/9 ensures that cached nfsd_file entries under the target export path are closed when revoking export state, preventing stale file handles from keeping the filesystem busy.

Supporting Refactoring

  • Patch 3/9 extracts revoke_one_stid() and revoke_ol_stid() utility functions from the deeply nested switch in nfsd4_revoke_states(), preparing for reuse by the export-scoped revocation logic.
  • Patch 6/9 replaces idr_for_each_entry_ul() with a while loop over idr_get_next_ul() for consistency with the new find_one_export_stid().

Discussion and Evolution

Jeff Layton provided positive reviews on all patches but noted a discrepancy between the series subject and its current focus:

"nit: subject is a little misleading. You're not doing this on unmount anymore, but rather when unexporting."

Chuck Lever acknowledged this shift in scope:

"The Subject: matches what I used on the v1 posting. But you're correct, the mission of this patch series has changed."

Conclusion

This v8 submission represents a significant evolution from earlier versions. The series now provides three distinct netlink commands for state revocation at IP, filesystem, and export granularity, enabling more surgical administration of NFS server state. Two pre-existing layout revocation bugs are fixed as prerequisites. With Jeff Layton's reviews attached to all patches, the series appears well-positioned for integration.
