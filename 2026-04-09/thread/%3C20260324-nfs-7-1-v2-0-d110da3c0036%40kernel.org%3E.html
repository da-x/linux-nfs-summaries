NFS: Delegated Timestamps and CLONE/COPY Interactions

Summary

This week's activity in the thread surrounding [PATCH v2 1/2] nfs: fix utimensat() for atime with delegated timestamps was limited to two messages from Olga Kornievskaia. The discussion, which originated last week as a targeted bug fix for xfstest generic/221, briefly expanded this week into the broader and more complex territory of NFSv4.2 CLONE/COPY operations interacting with delegated timestamps.

Prior Context

Last week, Jeff Layton submitted a v2 patch series addressing two bugs in how the NFS client handles inode change time (ctime) updates when using delegated timestamps. The first patch (the focus of this thread) fixes utimensat() for atime-only updates by forcing an RPC to update the server's ctime, as the delegated timestamp mechanism lacks a way to update ctime locally. The second patch fixed removexattr ctime updates by appending a trailing GETATTR. These patches sparked a wider debate on NFS protocol semantics regarding which operations should bypass or invalidate delegated timestamp authority, with consensus forming that synchronous metadata operations (like extended attribute changes) must always fetch fresh attributes from the server.

This Week: CLONE/COPY and "Backwards" Timestamps

This week, Olga Kornievskaia raised a new concern while testing Layton's patch against servers (Hammerspace and a patched Linux NFS server) that update c/mtime during CLONE/COPY operations. She observed what appeared to be timestamps going "backwards" on network traces:

"With this patch and running against a server that would update the c/mtime of a GETATTR in a compound with CLONE(COPY), the timestamps is (might be) going 'backwards'? I see that SETATTR+DELEGRETURN (after the CLONE) is setting a timestamp which is earlier than what's returned by the server in the GETATTR." Olga Kornievskaia

Kornievskaia highlighted a fundamental architectural tension: whether the current patch (which forces RPCs for atime updates) inadvertently breaks other test cases (like xfstest generic/407), or if the issue points to a deeper problem with including GETATTR in compound operations while holding an attribute delegation. She questioned the appropriate server-side behavior:

"I haven't figured out if this patch needs to modify such that it fixes 221 but doesn't break 407 or we are fundamentally dealing with a problem of including a GETATTR in a compound while holding an attribute delegation that needs to be solved differently." Olga Kornievskaia

She further pondered whether the server should issue a CB_GETATTR callback before responding to such embedded GETATTRs, or if the client should avoid sending GETATTR in CLONE compounds when holding an attribute delegation.

Resolution: Client-Side Observation Error

Later the same day, Kornievskaia retracted her concern, identifying a mistake in her own analysis of the network traces. She discovered she was observing two distinct SETATTR operations (one for the source file, one for the destination) and had conflated the time_access and time_modify values:

"Apologies. Please excuse the noise about the mtime going backwards. There are 2 SETATTRs going on and I was looking at the src file SETATTR. I believe I was also confused by the difference between time_access value from time_modify in the SETATTR (for the dest file)." Olga Kornievskaia

While she noted it remained "unclear why the access time wasn't modified... but the mtime was modified based on what's received in the CLONE's GETATTR," she concluded that the apparent regression was an artifact of her trace analysis rather than a flaw in Layton's patch.

Conclusion

  • Bug Fix Status: The immediate bug fix for utimensat() with delegated timestamps remains unchanged and unchallenged this week. The apparent issue raised regarding CLONE/COPY timestamp interactions was resolved as a client-side observation error by Olga Kornievskaia.
  • Ongoing Complexity: Despite the retraction, Kornievskaia's initial questions highlight the intricate interplay between delegated timestamps, compound operations (like CLONE), and server-side attribute updates. The debate over whether servers should perform CB_GETATTR callbacks or whether clients should omit GETATTR in certain compounds when delegations are held remains an open area of complexity in NFSv4.2 client development.
  • Next Steps: With the immediate concern resolved, the patch series is poised for integration, pending any further review from the community on the broader semantic questions raised last week regarding specification clarity for delegated timestamp authority.
