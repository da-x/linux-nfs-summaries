NFS close() Semantics Debate: Blocking Behavior During Server Unavailability

Summary

NFS close does not block when server is unavailable

Overview

This thread, initiated by Jon Curley of Pure Storage on April 6, 2026, addresses a subtle but significant bug in the Linux NFS client's close() semantics. The discussion centers on whether close() should guarantee that pending writes are flushed to the server before returning — particularly when the server is unavailable or returning errors. This is classified as a bug fix / semantic correctness discussion rather than a new feature or protocol change.

Key Technical Arguments

The Problem: close() Returns Success While Writes Are Still Failing

Jon Curley opened the thread by describing test failures in their automation linked to server unavailability As reported by Jon Curley:

"We've recently been investigating test failures in our automation linked to server failures. What we've noticed is that failures during WRITE do not block close(). Close simply returns success even though the writes are in a failure loop."

Curley demonstrated that this is easily reproducible with pNFS flexfiles, where a data server returning EACCES (a fencing mechanism per the flexfiles RFC) causes writes to enter a RESET_TO_PNFS loop. Commands like dd return success while writes are stuck in this retry loop, and close() does not block or report the failure.

Curley traced the root cause to commit aded8d7b54f2 ("NFS: Don't inadvertently clear writeback errors"), which replaced vfs_fsync with nfs_wb_all in nfs_file_flush. He noted that nfs_file_fsync employs a much more rigorous flushing algorithm, including a redirtied_pages interlock to handle RESET_TO_PNFS events, while nfs_file_flush (called by close()) does not.

"I'm not trying to get into an O_PONIES argument here but I always thought NFS close-to-open semantics meant that NFS close makes a strict effort to flush writes to the server before finishing."

Trond Myklebust's Response: POSIX vs. Hard Mount Semantics

NFS client maintainer Trond Myklebust responded by clarifying the distinction between fsync() and close() semantics As explained by Trond Myklebust:

"Now the difference between how fsync() and close() work is really down to whether or not we need to give a hard guarantee that the data is really on disk or not when the syscall completes."

Myklebust explained that:

  • fsync() must guarantee data is on storage. It uses the redirtied_pages counter to monitor resends, though this does not completely avoid live locks.
  • close() does not need such a guarantee under POSIX, as it is "just a convenience that ensures close-to-open semantics can be made to work." It calls nfs_wb_all(), which does not wait for resends to finish and thus avoids live locks.

He also addressed the pNFS flexfiles nuance: errors from data servers should not be treated as fatal; instead, the client should report them to the metadata server and potentially fail over or request a new layout. The metadata server's LAYOUTGET may then return the fatal error if no resolution is possible.

"Now we can definitely discuss whether or not that close() behaviour is correct: it does not lose data (so there are no hard mount violations), but it also doesn't offer the same guarantees that fsync() does w.r.t. whether the data is on disk on exit."

Curley's Counter-Argument: Operation Reordering Causes Application Failures

Curley pushed back, agreeing that POSIX doesn't require persistence after close() but raising a more critical concern: incorrect application behavior due to operation reordering As argued by Jon Curley:

"My concern is incorrect application behavior & compatibility."

He described a concrete test failure scenario:

  1. Write to a file, extending it to size N (dd)
  2. Assert the file size equals N (stat)
  3. Truncate the file to size M, where M < N (ftruncate)
  4. Assert the file size equals M (stat)

Step 4 occasionally failed because "the close flush did not finish the writes in step 1, the client reordered writeback after the setattr in step 3." This reordering caused the truncate (setattr) to complete before the pending writes, resulting in the file retaining size N instead of M.

"Reordering operations to storage caused incorrect behavior. I suspect this violates POSIX semantics?"

Curley concluded with a broader concern about NFS's perceived POSIX compatibility:

"I already hear plenty of complaints that NFS with default mount settings isn't POSIX compatible because writes aren't visible to other clients after the write syscall completes. Would we start telling people that the rule is really fsync-close-to-open?"

Evolution of the Discussion

The thread evolved from a specific bug report about close() not blocking during server failures to a deeper philosophical and practical debate about NFS semantics:

  1. Initial observation: Curley identified that close() returns success while writes are in a failure loop, contrary to expected "close-to-open" semantics.
  2. Historical analysis: Curley traced the behavior change to a specific commit that replaced vfs_fsync with nfs_wb_all.
  3. Maintainer clarification: Myklebust distinguished between fsync() (hard guarantee) and close() (POSIX convenience), framing the current behavior as intentional to avoid live locks.
  4. Practical counter-example: Curley demonstrated that the current behavior causes real application failures due to operation reordering, not just data persistence issues.

Final Conclusions

The thread ended without a definitive resolution or patch proposal. Key takeaways:

  • The current NFS client implementation allows close() to return before pending writes complete, which can cause operation reordering bugs in applications that rely on close-to-open semantics.
  • Trond Myklebust acknowledged that the behavior is debatable: "we can definitely discuss whether or not that close() behaviour is correct."
  • Jon Curley raised a compelling argument that the NFS client may require stricter close() semantics to achieve correct application behavior, particularly in distributed environments where operation ordering matters.
  • The discussion highlights a tension between avoiding live locks (the current design goal) and providing reliable close-to-open semantics (an application expectation).

This thread underscores an ongoing challenge in NFS client development: balancing performance and reliability against POSIX compatibility expectations. No patch was proposed during this week's activity, but the issue remains open for further discussion and potential remediation.
