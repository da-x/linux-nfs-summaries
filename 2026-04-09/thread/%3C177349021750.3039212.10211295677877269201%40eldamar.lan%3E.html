NFSv4.1: Session Size Limits Applied to Clone Path (Bug Fix)

Summary

NFSv4.1 Client Fix: Session Size Limits Applied to Clone Path

Classification

Bug fix. This thread delivers a concrete patch addressing a regression in the Linux NFS client's automount clone path, where session size limits were not being enforced for submounts.

Background (Prior Week)

Last week, this thread began when Salvatore Bonaccorso reported a regression caused by commit 2b092175f5e3 ("NFS: Fix inheritance of the block sizes when automounting"). Users experienced EIO errors on Dell EMC Isilon/OneFS servers when using large rsize/wsize values (1 MB). The discussion revealed a semantic mismatch: the Linux client trusted maxread/maxwrite without cross-checking against max_request_size, while OneFS treated those limits as total packet size rather than payload-only.

Maintainer Trond Myklebust stated:

"The point is, we expect the value of maxwrite to be set to a reasonable value w.r.t. max_request_size so that the client doesn't have to sanity check everybody and their dog's server."

Jeff Layton countered that the client should be more defensive:

"ISTM the client should clamp the length down to something shorter that allows the request to fit."

No patch landed last week; the thread remained in analysis mode.

This Week's Activity

Tushar Sariya submitted a v2 patch series this week, proposing a targeted fix for the NFSv4.1 automount clone path. The patch addresses a specific gap: while top-level mounts apply session size clamping via nfs4_server_common_setup(), the clone path (nfs4_clone_server()) skips these limits entirely.

The Problem

Sariya explained:

"nfs4_clone_server() builds a child nfs_server for same-server automounted submounts but never calls nfs4_session_limit_rwsize() or nfs4_session_limit_xasize() after nfs_clone_server(). This means the child mount can end up with rsize/wsize values that exceed the negotiated session channel limits, causing NFS4ERR_REQ_TOO_BIG and EIO on servers that enforce tight max_request_size budgets."

The issue was exposed by commit 2b092175f5e3, which changed submounts to no longer unconditionally inherit the parent's already-clamped rsize/wsize. On servers with tight max_request_size budgets (such as Dell EMC Isilon/OneFS), child mounts ended up with raw, unclamped values that exceeded session channel limits.

The Fix

The patch applies the same session-limit clamping used by top-level mounts to the clone path:

"Top-level mounts go through nfs4_server_common_setup() which calls these limiters after nfs_probe_server(). Apply the same clamping on the clone path for consistency."

The changes touch three files (fs/nfs/internal.h, fs/nfs/nfs4client.c, fs/nfs/nfs4proc.c) with a minimal 7-line addition and 2-line removal. The patch is marked with Fixes: 2b092175f5e3 and Cc: stable@vger.kernel.org.

Sariya noted testing limitations:

"I was unable to reproduce the exact failure locally as it appears to require a server that enforces tight max_request_size budgets. The fix is based on code analysis — the clone path is missing the same session-limit clamping that top-level mounts apply in nfs4_server_common_setup(). Tested that the kernel builds and boots successfully."

Evolution of the Discussion

The thread evolved from a broad debate about client-vs-server responsibility for size limit enforcement (last week) to a concrete, surgical fix targeting a specific code path gap (this week). Sariya's patch does not attempt to solve the broader interoperability mismatch with OneFS's interpretation of max_request_size; rather, it ensures that the NFS client's clone path respects its own session limits consistently, preventing child mounts from exceeding negotiated budgets.

Final Conclusions

  • A targeted fix has been proposed: The v2 patch applies session size clamping to the NFSv4.1 automount clone path, ensuring consistency with top-level mount behavior.
  • The patch is minimal and well-scoped: It addresses a specific code path omission rather than attempting to overhaul the client's size negotiation logic.
  • No maintainer review yet this week: As of the end of this window, the patch has been submitted but not yet reviewed or acknowledged by Trond Myklebust or other maintainers.
  • Broader interoperability question remains open: This fix mitigates one symptom (unclamped values on clone paths) but does not resolve the deeper semantic mismatch between Linux client and OneFS server interpretations of size limits, which was debated last week.
