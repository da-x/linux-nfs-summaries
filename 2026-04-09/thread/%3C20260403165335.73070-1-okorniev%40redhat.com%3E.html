nfsd: Fix mtime/ctime updates on CLONE/COPY with delegated attributes

Summary

nfsd: Correcting mtime/ctime Updates on CLONE/COPY with Delegated Attributes

Overview

This thread concerns a bug fix in the NFS server (nfsd) related to timestamp updates during CLONE and COPY operations when delegated attributes are present. The issue stems from a previous commit (e5e9b24ab8fa) that froze c/mtime updates when a WRITE_ATTRS delegation was outstanding, causing the server to open files with FMODE_NOCMTIME. While this prevents out-of-sync states with client-delegated views for standard writes, it inadvertently suppressed timestamp updates for server-side copy operations.

Key Technical Arguments

The Problem

Olga Kornievskaia introduced the patch on April 3, explaining:

"When delegated attributes are given on open the file is opened with NOCMTIME and modifying operations do not update mtime/ctime as to not get out-of-sync with the client's delegated view. However, for operations CLONE/COPY server should update its view of mtime/ctime and reflect that in any GETATTR queries."

Her initial approach temporarily cleared FMODE_NOCMTIME during the copy operation and restored it afterward.

Race Conditions Identified

Jeff Layton immediately flagged a concurrency concern in his response:

"This seems simple enough, but there is some raciness involved if other calls are running concurrently with the COPY/CLONE. You might end up reenabling FMODE_NOCMTIME before a second COPY/CLONE finishes."

He proposed an alternative:

"A simpler idea might be to just do a notify_change() for ATTR_MTIME after each COPY or CLONE operation done on a file with FMODE_NOCMTIME set. That should set the timestamp to something pretty close to whatever the last write() would have set it to, but without having to monkey with the fmode."

Chuck Lever identified a separate but related flaw specific to async copies on April 4:

"For async copies, does this restore FMODE_NOCMTIME before the kthread performs the actual data transfer? The async path creates a kthread then falls through to the out: label. The restore runs here, before the kthread calls nfsd4_do_copy(). By the time the kthread runs... FMODE_NOCMTIME has already been restored, and the timestamp update that this patch intends to enable will not take effect for async copies."

"This is probably a variant of the race that Jeff already called out."

Resolution Direction

Olga Kornievskaia acknowledged both concerns on April 6 and adopted Jeff's notify_change() approach:

"Thanks Jeff and Chuck. I've changed the code to use the notify_change() but before I send out I have a question regarding where you think this notify_change () should take place in case of a copy (specifically thinking about async copy vs sync copy)."

She asked whether the timestamp update should occur at the completion of the COPY compound request or upon actual data transfer completion for async copies.

Jeff Layton provided the final guidance on April 6:

"I think you want to do it when the copy completes. If that's sync copy then you'd stamp it before you send the COPY reply. For async copy, I think you'd want to do it before sending a CB_OFFLOAD."

Evolution and Conclusion

The discussion evolved from Olga's initial patch—manipulating FMODE_NOCMTIME directly—to a consensus on using notify_change() for timestamp updates, avoiding fmode manipulation entirely. This approach eliminates the race conditions identified by both Jeff Layton and Chuck Lever.

Final conclusions:

  1. The original approach of toggling FMODE_NOCMTIME was rejected due to concurrency races.
  2. The notify_change() mechanism is preferred for updating mtime/ctime on COPY/CLONE operations.
  3. For synchronous copies, the timestamp should be updated before sending the COPY reply.
  4. For asynchronous copies, the timestamp should be updated before sending the CB_OFFLOAD callback to the client.

Olga Kornievskaia indicated she would send an updated patch incorporating these changes, but no v2 was posted within this week's window. The thread remains open pending the revised submission.
