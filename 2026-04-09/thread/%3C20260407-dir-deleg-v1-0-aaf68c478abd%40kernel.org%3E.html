CB_NOTIFY Support for Directory Delegations: Server-Side Implementation and Review

Summary

Overview

Jeff Layton submitted a 24-patch series adding server-side support for CB_NOTIFY callbacks in directory delegations. This is a new feature implementing NFSv4.1 protocol extensions (per RFC8881bis) that allow NFS clients to receive asynchronous notifications about directory changes (creates, unlinks, renames) without losing their directory delegation. The series touches VFS file locking, fsnotify, and nfsd callback infrastructure.

"This patchset builds on the directory delegation work we did a few months ago, to add support for CB_NOTIFY callbacks for some events. In particular, creates, unlinks and renames." — Jeff Layton

Key Technical Arguments and Evolution

VFS File Locking Changes (Patches 01-03)

The series introduces LEASE_BREAK_DIR_* flags to allow the VFS lease-break mechanism to ignore certain directory change events when a delegation has opted into notifications. Jan Kara reviewed these patches positively:

"Looks good. Feel free to add: Reviewed-by: Jan Kara jack@suse.cz" — Jan Kara

Kara noted a minor cosmetic issue with bit numbering (bit 5 was skipped):

"Just curious why you've left out bit 5 here... :)" — Jan Kara

Layton acknowledged this was an artifact of old code:

"No reason. I've had this series for a couple of years now, and I think bit 5 got removed at some point after I originally did this patch... I'll plan to renumber this for neatness sake." — Jeff Layton

Bug: Spurious Blocking in __break_lease() (Patch 01)

Chuck Lever identified a logic error in the lease-break loop. When ignored leases remain after non-ignored ones are broken, any_leases_conflict() returns true, causing the caller to block unnecessarily:

"After breaking visible leases, the restart: label calls any_leases_conflict() which does not filter ignored dir-delegation leases... The loop spins at 1-jiffy intervals until the ignored delegation is released." — Chuck Lever

Layton agreed with the diagnosis:

"Yep. The right fix is to switch the any_leases_conflict() call to visible_leases_remaining(). I'll code that up and test it." — Jeff Layton

Bug: Stale fsnotify Mask on Delegation Removal (Patch 08)

Lever pointed out that nfs4_unlock_deleg_lease() recalculates the fsnotify mask before removing the delegation via kernel_setlease(F_UNLCK), meaning the removed delegation's ignore flags are still counted:

"The result is that stale FS_CREATE/FS_DELETE/FS_RENAME bits remain in the fsnotify mark. It might be harmless in practice since the handler finds no leases and returns early, but it creates unnecessary work." — Chuck Lever

"Good catch. Will fix." — Jeff Layton

Bug: Cross-Directory Rename Notifications (Patch 13)

Lever discovered that for cross-directory renames, the VFS delivers FS_RENAME_FROM to the old directory, but the notification handler only checks for FS_RENAME. A client subscribed to NOTIFY4_REMOVE_ENTRY would receive neither a lease break nor a CB_NOTIFY:

"IIUC, a client subscribed to NOTIFY4_REMOVE_ENTRY for old_dir sees neither a lease break nor a CB_NOTIFY when a child is renamed out of the directory." — Chuck Lever

Layton confirmed and committed to a fix:

"Actually, it delivers FS_RENAME_FROM to the old directory and FS_RENAME_TO to the new one in this case... Basically, we need to watch for those in addition to FS_CREATE/DELETE and treat them the same way. I'm looking at a fix now." — Jeff Layton

Issue: Event Loss During RPC Retries (Patch 12)

Lever raised a concern about events arriving while a CB_NOTIFY RPC is being retried after NFS4ERR_DELAY. He worried that the callback's prepare() would be called again, draining an already-empty event counter and destroying the callback prematurely.

Layton clarified that the RPC framework does not re-call cb_ops->prepare on retry—the same XDR buffer is re-sent:

"When ->done() returns 0, rpc_restart_call_prepare retries the RPC through the RPC-level prepare... It does not call cb_ops->prepare again — the same encoded XDR is re-sent in that case." — Jeff Layton

However, he acknowledged a related issue: events queuing up while the callback is running won't be sent until the next event triggers a new callback. He plans to fix the ->release handler to requeue if pending events remain:

"There is a problem, however. Events that arrive while the job is running queue up, but won't get sent until the next event arrives. We need to make the ->release handler check for new events and requeue the callback if there are any." — Jeff Layton

Final Conclusions

  • The series received positive reviews from Jan Kara for the VFS/filelock portions and Steven Rostedt for the tracepoint patch.
  • Chuck Lever's review uncovered four distinct issues that Layton acknowledged and plans to address in a follow-up version:
    1. Spurious blocking in __break_lease() due to unfiltered ignored leases.
    2. Stale fsnotify mask bits on delegation removal.
    3. Missing handling of FS_RENAME_FROM/FS_RENAME_TO for cross-directory renames.
    4. Queued events not being flushed after a callback completes.
  • Layton indicated he would send another version, likely after the upcoming testing event:

"I'll plan to send another version soon (but probably not until after next week's testing event)." — Jeff Layton

  • The server-side implementation is not expected to merge until a complete client-side implementation exists for testing, as Layton noted in the cover letter:

"I don't think we'll want to merge these until we have a complete client-side implementation to test against." — Jeff Layton
