NFSv4.2: CLONE Attribute Fix with Delegated Attributes — Follow-up Discussion

Summary

NFSv4.2: Fix CLONE Attribute Updates with Delegated Attributes

Classification: Bug Fix

This thread concerns a bug fix in the NFSv4.2 client related to incorrect attribute handling after a CLONE operation when delegated attributes are present.

Background (from prior week)

Last week, Olga Kornievskaia from Red Hat submitted a single-patch series addressing a regression detected by xfstest generic/407. The test revealed that after a CLONE operation, the client failed to update mtime and ctime, and also reported stale change_attr values when delegated attributes were active Initial patch submission.

Olga explained the root cause:

"xfstest generic/407 is failing in 2 ways. It detects that after doing a clone the client does not update it's mtime and it's ctime."

The regression was traced to commit e12912d94137, which introduced delegated atime/mtime attribute caching but inadvertently broke the CLONE post-operation update path. The proposed fix invalidated block attributes after a CLONE, forcing the client to refresh its cache rather than relying on stale delegated values.

This Week's Activity

This week saw only one message in the thread, a follow-up from Olga herself:

"This patch isn't needed if the server updates mtime/ctime after doing a CLONE." Olga's remark

This comment raises an important architectural question: should the fix reside in the client (invalidating cached attributes) or should servers be responsible for updating timestamps after a CLONE operation? Olga's remark suggests that if compliant servers properly update mtime/ctime post-clone, the client-side workaround may be unnecessary.

Evolution and Open Questions

The discussion remains open-ended this week. No reviews from the NFS maintainer Trond Myklebust arrived within this window (his response came on April 13, outside this week's scope). In that later message, Trond questioned the approach:

"Why not call nfs_post_op_update_inode() instead of setting NFS_INO_INVALID_BLOCKS? It should be safe to do so."

This suggests a potential refinement to Olga's patch, though that exchange falls outside this week's coverage.

Significance for NFS Client Development

This fix targets a correctness issue in NFSv4.2 clone operations — a feature critical for storage virtualization and deduplication workloads. The interplay between delegated attribute caching and post-operation metadata updates remains a subtle area where performance optimizations can compromise consistency guarantees. Olga's observation about server-side timestamp updates also highlights an ongoing tension between client-side defensive coding and relying on proper server behavior per the NFSv4.2 specification.
