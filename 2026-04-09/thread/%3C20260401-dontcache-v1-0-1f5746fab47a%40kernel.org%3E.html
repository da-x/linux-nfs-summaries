mm: Shift RWF_DONTCACHE Writeback from In-Caller to Daemon-Based Approach

Summary

mm: Evolving RWF_DONTCACHE Writeback Strategy from In-Caller to Daemon-Based

Overview

This week, the discussion on Jeff Layton's patch series to improve RWF_DONTCACHE write performance introduced last week took a significant architectural turn. Last week, the focus was on rate-limiting in-caller writeback to reduce lock contention and prevent throughput collapse for NFS server (nfsd) workloads using RWF_DONTCACHE. This week, Christoph Hellwig challenged the fundamental premise of having user-space callers perform writeback directly, advocating instead for offloading this responsibility entirely to the kernel's background writeback daemon.

This is a bug fix and architectural improvement discussion targeting the generic memory management layer, with direct implications for NFS server performance and scalability.

Key Technical Arguments

Critique of nr_to_write Usage

Hellwig clarified a technical misunderstanding regarding Patch 1/4, which used filemap_flush_range() with nr_to_write=LONG_MAX. He argued that when .range_start and .range_end are set in a writeback_iter() loop, the iterator will process every page in the range regardless of nr_to_write, unless nr_to_write is smaller than the range size.

"But nr_to_write should not change anything. If .range_start and .range_end are set in a writeback_iter() loop, writeback_iter will try to get and writeback every page in the range." Christoph Hellwig

He further suggested that setting both a range and nr_to_write is logically inconsistent:

"In fact we should probably have a debug check to never set both a range and nr_to_write as that combination doesn't make sense." Christoph Hellwig

The Core Debate: In-Caller Writeback vs. Writeback Daemon

The most significant evolution in the thread was Hellwig's critique of Patch 2/4, which introduced an atomic flush guard (AS_DONTCACHE_FLUSHING) to serialize in-caller writeback. Hellwig argued that having multiple user processes contend for shared writeback resources (such as the XFS AIL) is inherently problematic and that the kernel has historically moved away from this pattern.

"Well, an any time you hit a shared resources from multiple threads you create that lock contention. Which is why in file system and writeback land we've moved away from random user processes hitting both data and metadata (e.g. XFS AIL) writeback as it leads to these scalability issues." Christoph Hellwig

Hellwig proposed that the ideal solution is not to optimize in-caller writeback, but to leverage the existing writeback thread infrastructure:

"And that is called the writeback thread. So what we should do there is to make sure we queue up writeback on it for each dontcache write." Christoph Hellwig

He suggested initially queuing a wb_writeback_work for each range, though he acknowledged that simply increasing a threshold might be a more efficient long-term approach.

Jeff Layton's Response and Pivot

Layton accepted Hellwig's suggestion to shift toward daemon-based writeback for IOCB_DONTCACHE:

"Ok, I like that idea. I'll give that a shot and see how it does." Jeff Layton

However, he noted a current limitation in the API:

"I'll note that there is no way to specify an inode or range (yet) in wb_writeback_work()." Jeff Layton

Layton asked whether simply waking the flusher threads via wakeup_flusher_threads_bdi() after every RWF_DONTCACHE write would suffice, or if extending wb_writeback_work to support range-specific operations on a single inode was necessary.

Hellwig's Final Guidance

Hellwig responded that precise data targeting is unnecessary for DONTCACHE operations, as they are not integrity-critical:

"I don't think we care about what exact data is written back as this is not an integrity operation. So just waking the flusher thread sounds like the right thing..." Christoph Hellwig

However, he added a caveat that the mechanism might also need to communicate a higher writeback target to ensure timely processing:

"...but we might also need a way to communicate the higher writeback target." Christoph Hellwig

Broader Impact on Buffered Write Performance

The discussion also touched on the broader issue of writeback timeouts. Both developers agreed that the current 30-second writeback timeout is detrimental to performance, particularly on SSDs:

"Yes, we've had lots of observation that the current 30s timeout is actively harmful. Especially on SSDs, but even on HDD just keeping the active might make sense." Christoph Hellwig

Final Conclusions

The discussion concluded with a clear architectural direction: abandon in-caller writeback for IOCB_DONTCACHE and instead leverage the kernel's background writeback daemon. Layton committed to implementing this approach, likely by calling wakeup_flusher_threads_bdi() after each RWF_DONTCACHE write. The precise mechanism for communicating writeback urgency remains an open question for future iterations.

Impact on NFS Client/Server Development

While these patches target the generic memory management subsystem, they are directly motivated by nfsd performance requirements. A robust RWF_DONTCACHE implementation enables NFS servers to provide a high-performance IO mode that avoids the overhead of direct I/O while preventing noisy-neighbor interference through cache bypass. The shift to daemon-based writeback promises better scalability under concurrent workloads, which is critical for production NFS server deployments. Additionally, the acknowledgment that the 30-second writeback timeout is "actively harmful" may lead to broader improvements in buffered write performance across all filesystems, indirectly benefiting NFS client operations as well.
