mm: Improve RWF_DONTCACHE Write Performance via Flusher Thread Offload

Summary

Overview

This week, Jeff Layton submitted v2 of a three-patch series aimed at improving write performance for RWF_DONTCACHE I/O in the Linux kernel's memory management subsystem. The discussion centers on a critical performance regression observed when NFS server (NFSD) or local filesystems use the "dontcache" I/O mode, and explores architectural changes to offload writeback from the writer's hot path.

Classification: This is a performance optimization / bug fix for existing functionality (RWF_DONTCACHE), not a new feature or protocol change. The patches modify core VFS/writeback behavior with implications for NFS client/server I/O patterns.

Background: The DONTCACHE Problem

The RWF_DONTCACHE flag (exposed via IOCB_DONTCACHE) allows applications and subsystems like NFSD to perform writes that should be flushed from the page cache immediately, without lingering in memory. Recently, NFSD gained debugfs controls to select between buffered, dontcache, and direct I/O modes.

Jeff Layton benchmarked these modes and discovered that RWF_DONTCACHE performed poorly under write-heavy workloads:

"one thing that really stood out was how badly RWF_DONTCACHE performed with write-heavy workloads. This turned out to be the case on a local xfs with io_uring as well as with nfsd." As noted in the cover letter

The root cause was identified: generic_write_sync() called filemap_flush_range() inline on every write, blocking the writer for milliseconds while walking the page tree and submitting I/O. This inflated p99.9 latency from 23ms (buffered) to 93ms (dontcache).

Patch v2: Kick the Flusher Thread Instead of Inline Flush

The key technical change in Patch 1/3 replaces the inline filemap_flush_range() call with a wakeup_flusher_threads_bdi() invocation. This kicks the BDI's background flusher thread to drain dirty pages asynchronously, moving writeback submission entirely off the writer's hot path:

"This moves writeback submission completely off the writer's hot path. The flusher thread handles writeback asynchronously, naturally coalescing and rate-limiting I/O without any explicit skip-if-busy or dirty pressure checks." Jeff Layton

Patches 2/3 and 3/3 add benchmark suites (nfsd-io-bench and dontcache-bench) to document the testing methodology, though Layton noted these are not intended for merge.

Evolution of the Discussion

Abandoning Per-Inode Writeback

In v1, an alternative approach using writeback_single_inode() was considered to isolate DONTCACHE writeback to specific inodes. However, Layton reported significant regressions with that approach:

"The per-inode approach is neutral-to-slightly-better for the production scenario (Scenario D), but regresses on multi-writer and random write workloads. The core issue is loss of I/O batching — writeback_sb_inodes() processes all dirty inodes in one blk_plug'd pass, while per-inode write_inode_now() calls are processed one at a time." Jeff Layton

Specific regressions included:

  • Random write throughput: -21% (363 → 286 MB/s)
  • Multi-writer aggregate throughput: -32% (1478 → 999 MB/s)
  • Multi-writer p99.9 latency: worsened by 67% (46ms → 77ms)

Layton concluded: "I think v2 is probably the best approach, on balance."

Christoph Hellwig's Concerns: Scope of Writeback

Christoph Hellwig raised a fundamental architectural concern: kicking the entire BDI flusher for every DONTCACHE write could trigger excessive writeback of unrelated dirty pages. He explained the mechanism:

"wakeup_flusher_threads_bdi ends up calling wb_start_writeback eventually, which sets WB_start_all... The flusher thread then through wb_check_start_all does a WB_SYNC_NONE writeback based on get_nr_dirty_pages. Which seems wrong - we don't want to do a huge writeback every time some DONTCACHE write finished." Christoph Hellwig

Hellwig proposed a more targeted approach:

"So I think you'll want a new WB_start_dontcache bit, a new get_nr_dontcache_pages() helper on a new node counter, etc." Christoph Hellwig

Jan Kara's Workload Regression Scenario

Jan Kara validated Hellwig's concern with a concrete regression scenario:

"I can certainly construct a workload where this behavior will lead to big regressions in performance - for example one process creating say 1G temporary file and deleting it shortly after creation + one process doing small DONTCACHE writes. Before this change only DONTCACHE writes will make it to the disk and temporary file will only be in the page cache, after this change you pay for allocating, writing back, and deleting the temporary file." Jan Kara

Kara suggested marking inodes with "dropbehind" folios and having the flusher prioritize only those:

"Maybe we could mark inodes which have folios with dropbehind set and make flush worker only write such inodes?" Jan Kara

Hellwig refined this idea:

"I'd only expedite writing by the number of pending dontcache folios. It would still write the least recently dirtied inodes." Christoph Hellwig

API Naming Concerns

Ritesh Harjani noted that the new filemap_dontcache_kick_writeback() function name is misleading, as it triggers whole-BDI writeback rather than inode-specific writeback:

"This api gives a wrong sense that we are kicking writeback to write dirty pages which belongs to only this inode's address space mapping. But instead we are starting wb for everything on the respective bdi." Ritesh Harjani

Hellwig agreed but preferred not to expose wakeup_flusher_threads_bdi() directly:

"I'd rather not expose that to wide with the extra reason arguments that's not otherwise exposed outside the core writeback code." Christoph Hellwig

Benchmark Data Quality

Hellwig also questioned the benchmark methodology, noting unexpected results:

"How does O_DIRECT manage to create almost the same peak dirty as buffered? Similarly even this patched dontcache should be lower, which feels odd." Christoph Hellwig

He requested that benchmark results be included directly in patches rather than external links, which "tend to get stale very easily."

NFS Client/Server Relevance

While this thread targets the core mm/writeback subsystem, it has direct implications for NFS server (NFSD) performance. The RWF_DONTCACHE mode is one of three I/O modes now configurable via NFSD debugfs controls. Improving dontcache write performance directly benefits NFS workloads that rely on this mode for low-latency, cache-bypassing writes. Layton's benchmark suite includes tests against an NFS server on localhost using fio's libnfs backend, demonstrating the NFS-relevant testing context.

Final Status and Next Steps

The discussion concluded without a resolved v3 direction. Key open items:

  1. Architecture: Hellwig and Kara agree that whole-BDI flusher wakeup is too coarse-grained. A more targeted approach tracking DONTCACHE-specific folios/inodes is needed, but the exact mechanism remains undecided.
  2. Review: Jens Axboe (block layer maintainer) has not yet weighed in, and Hellwig noted: "We also haven't heard from Jens at all, whom I'd really like to look over this." Christoph Hellwig
  3. Timeline: Layton suggested targeting v7.2, and Hellwig confirmed there is no rush if that is the goal.

The thread ends with significant technical consensus on the problem (inline flusher contention hurts DONTCACHE writes) but unresolved debate on the solution (whole-BDI wakeup vs. targeted inode/folio tracking).
