NFSv4.1: Session Size Limits on Clone Path (Superseded v1)

Summary

NFSv4.1: Session Size Limits Applied to Clone Path (Superseded v1 Submission)

Classification

Bug fix. This thread captures the initial (now superseded) v1 patch submission by Tushar Sariya addressing a regression in the Linux NFS client's automount clone path, where session size limits were not being enforced for submounts.

Context from Prior Activity

This issue traces back to a regression reported by Salvatore Bonaccorso, caused by commit 2b092175f5e3 ("NFS: Fix inheritance of the block sizes when automounting"). Users experienced EIO errors on Dell EMC Isilon/OneFS servers when using large rsize/wsize values. The broader discussion last week debated client-versus-server responsibility for size limit enforcement, with maintainers Trond Myklebust and Jeff Layton exchanging views on whether the client should defensively clamp request sizes.

A related prior summary covers the v2 patch submission that superseded this v1 series.

This Week's Activity

Tushar Sariya submitted a v1 patch series on April 4, proposing a fix for the NFSv4.1 automount clone path. The patch addresses a specific gap: while top-level mounts apply session size clamping via nfs4_server_common_setup(), the clone path (nfs4_clone_server()) skips these limits entirely.

The Problem

In the cover letter, Sariya explained:

"The NFS automount clone path (nfs4_clone_server) is missing the session-size clamping that top-level mounts get in nfs4_server_common_setup(). This was exposed by 2b092175f5e3 which changed submounts to no longer unconditionally inherit the parent's already-clamped rsize/wsize. On servers that enforce tight max_request_size budgets (reported on Dell EMC Isilon/OneFS), the child mount ends up with raw unclamped values that exceed the session channel limits, resulting in NFS4ERR_REQ_TOO_BIG and user-visible EIO."

The technical detail was elaborated in the patch commit message:

"nfs4_clone_server() builds a child nfs_server for same-server automounted submounts but never calls nfs4_session_limit_rwsize() or nfs4_session_limit_xasize() after nfs_clone_server(). This means the child mount can end up with rsize/wsize values that exceed the negotiated session channel limits, causing NFS4ERR_REQ_TOO_BIG and EIO on servers that enforce tight max_request_size budgets."

The Fix

The proposed solution was straightforward: apply the same clamping logic used by top-level mounts to the clone path. Sariya noted:

"Top-level mounts go through nfs4_server_common_setup() which calls these limiters after nfs_probe_server(). Apply the same clamping on the clone path for consistency."

The patch touches three files (fs/nfs/internal.h, fs/nfs/nfs4client.c, fs/nfs/nfs4proc.c) with a minimal 7-line addition and 2-line removal. It carries Fixes: 2b092175f5e3 and Cc: stable@vger.kernel.org.

Sariya acknowledged testing limitations:

"I was unable to reproduce the exact failure locally as it appears to require a server that enforces tight max_request_size budgets. The fix is based on code analysis — the clone path is missing the same session-limit clamping that top-level mounts apply in nfs4_server_common_setup(). Tested that the kernel builds and boots successfully."

Supersession

Later the same day, Sariya announced that this v1 series was superseded:

"Superseded. Reposting as a reply to the original regression report."

The v2 series was reposted as a reply to the original bug report from Salvatore Bonaccorso, ensuring better threading and context for reviewers. That v2 submission is covered in the related thread summary.

Final Conclusions

  • The v1 submission was quickly superseded: Sariya reposted the patch as v2 later the same day, threading it properly to the original regression report for better visibility and context.
  • The fix is targeted and minimal: It addresses a specific code path omission in nfs4_clone_server() rather than attempting a broader overhaul of size negotiation logic.
  • No maintainer review occurred this week: As of the end of this window, neither the v1 nor the v2 submission had received explicit acknowledgment from maintainers Trond Myklebust or Jeff Layton.
  • The broader interoperability question remains: This fix mitigates one symptom (unclamped values on clone paths) but does not resolve the deeper semantic mismatch between Linux client and OneFS server interpretations of max_request_size, which was debated in prior weeks.
