nfsd: Fix mtime/ctime updates for CLONE/COPY with delegated attributes

Summary

nfsd: Fix mtime/ctime updates for CLONE/COPY with delegated attributes

Type: Bug fix

Status: Under review; v2 planned to address reviewer feedback.

Overview

Olga Kornievskaia submitted a three-patch series addressing a regression where the generic/407 xfstest fails when delegated attributes are present on NFS files. The root cause is that when a file is opened with a delegation, it uses the NOCMTIME flag, which suppresses mtime/ctime updates to avoid getting out of sync with the client's delegated view. However, server-side operations like CLONE and COPY modify the destination file and should update its timestamps so that subsequent GETATTR queries return correct values.

The series splits the fix into three patches:

  1. CLONE: Update mtime/ctime on the destination when performing a CLONE operation Patch 1/3.
  2. Synchronous COPY: Update mtime/ctime upon completion of synchronous COPY Patch 2/3.
  3. Asynchronous COPY: The most complex case — update timestamps when the background copy thread completes, not during compound processing Patch 3/3.

Key Technical Arguments

Timestamp Semantics for CLONE/COPY

Olga raised an open question about whether CLONE/COPY should also update atime on the source or destination:

"An outstanding question I have is whether or not a CLONE/COPY operation is supposed to also update the atime on the source file? But also atime for the dest file as well?" Cover letter

Jeff Layton provided guidance based on Linux's internal implementation:

"CLONE/COPY aren't defined by POSIX so I'm not sure we have clear guidance about the atime on the source or destination. Within Linux, COPY is implemented using reads and writes though, so I'd expect that the source file has its atime updated, and the destination gets a new c/time." Review

Jeff gave an overall positive assessment:

"This all looks good to me. Thanks for fixing this up, Olga!" Reviewed-by

Delegation Recall Concerns (Patch 1/3 — CLONE)

Chuck Lever raised a concern about whether calling notify_change() without the ATTR_DELEG flag would trigger an unwanted delegation recall:

"I think there is an active delegation here. Without ATTR_DELEG, notify_change() calls try_break_deleg(), which will return -EWOULDBLOCK, causing the setattr to be silently skipped. Wouldn't it also initiate a CB_RECALL as well?" Review

Olga responded that the destination file is opened for write and holds its own delegation, so no conflict occurs in practice. However, she agreed to set ATTR_DELEG explicitly to avoid evaluating the recall path:

"However, looking at the code I now see that it does make sense to set ATTR_DELEG so that the code under 'if (!(ia_valid & ATTR_DELEG))' is not evaluated." Response

Chuck also noted that timestamps should only be updated on success:

"Should this check whether nfsd4_clone_file_range() succeeded before updating timestamps? If the clone fails, the file content is not modified, so a timestamp update would be incorrect." Review

Olga acknowledged this and confirmed a v2 would restrict the update to successful operations:

"Sounds like a v2 is needed when it's only done for success." Response

Ordering and Error Handling in Asynchronous COPY (Patch 3/3)

Chuck Lever identified several issues in the async COPY patch:

  1. Timestamp update ordering: The mtime/ctime update should precede the CB_OFFLOAD callback so that a client issuing GETATTR in response sees the updated values:

"Jeff earlier suggested that the timestamp update should happen before sending CB_OFFLOAD, so that a client issuing GETATTR in response to the callback sees the updated timestamps." Review

Olga agreed: "I'll move it up." Response

  1. Dentry reference counting bug: Chuck identified a critical refcount underflow in the error path of nfsd4_copy(). Three early error exits jump to out_dec_async_copy_err before the dget() is performed, yet the cleanup code checks FMODE_NOCMTIME to decide whether to call dput():

"If FMODE_NOCMTIME happens to be set when one of the early gotos fires, this calls dput without a matching dget, resulting in a dentry refcount underflow." Review

He proposed checking async_copy->d_dst instead, which is NULL before the dget and non-NULL after:

"Would it be simpler to check async_copy->d_dst here instead of re-reading FMODE_NOCMTIME? That field is NULL before the dget and non-NULL after, which handles both cases correctly." Review

Olga confirmed she would fix the error handling in v2: "I will attempt to correct my error handling dput() in v2!" Response

Centralizing Timestamp Updates (Patch 2/3 — Sync COPY)

Chuck suggested a refactoring approach that would benefit both sync and async paths:

"Thinking aloud: If you updated the time stamps in _nfsd_copy_file_range() wouldn't that take care of both the sync and async cases, and you could determine precisely whether a data change had been made to the destination file?" Suggestion

Olga also raised uncertainty about whether partial failures (e.g., ENOSPC after some data was written) should still trigger timestamp updates, noting: "nfsd4_do_copy can return say ENOSPC but it would have modified the file as well. So I'm not clear if we need to special case return values?" Response

Conclusions and Next Steps

The patch series addresses a real bug where delegated attributes prevent proper mtime/ctime updates on CLONE/COPY operations, causing generic/407 test failures. Jeff Layton provided a Reviewed-by tag for the overall approach. Chuck Lever's detailed review uncovered:

  • A need to guard timestamp updates behind success checks
  • A delegation recall avoidance fix via ATTR_DELEG
  • Correct ordering of timestamp updates relative to CB_OFFLOAD callbacks
  • A dentry refcount underflow in the async COPY error path
  • A potential architectural improvement by centralizing timestamp logic in _nfsd_copy_file_range()

Olga Kornievskaia confirmed all points would be addressed in v2. The discussion remains focused on NFS server-side correctness and proper interaction with delegated attributes — an important area for maintaining data consistency in modern NFS deployments.
