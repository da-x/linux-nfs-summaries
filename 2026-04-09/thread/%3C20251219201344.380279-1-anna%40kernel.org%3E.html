Al Viro Reviews NFS Directory Delegation Verifier Race Conditions and Dentry Subtleties

Al Viro Reviews NFS Directory Delegation Verifier Race Conditions and Dentry Subtleties

Summary

Type: Bug fix review — potential use-after-free and locking correctness issues in the NFS client's directory delegation verifier code.

Background (Prior Weeks)

This thread originated from Anna Schumaker's December 19 patch Fix directory delegation verifier checks, which aimed to optimize directory delegation verifier handling. Christoph Hellwig reported that the patch caused kernel Oops crashes during delegation benchmarking and generic/633 xfstests runs. Over the following weeks (summarized in January 2026), Trond Myklebust iterated through multiple fixes addressing state recovery crashes for directory delegations, with Christoph testing each iteration. The final fix from January blocked state recovery for non-regular file delegations at two crash sites, resolving generic/633 — though Anna noted the issue may persist under NFS v4.2.

This Week's Discussion (April 4–5, 2026)

VFS maintainer Al Viro re-engaged with the thread, reviewing Trond Myklebust's December 31 patch (nfs_clear_verifier_directory) and raising three distinct concerns about locking correctness and code semantics.

Concern 1: Potential Use-After-Free on Inode Iteration

In his first message [id://20260404183247.GA2798238@ZenIV], Viro questioned the safety of iterating over dentries in nfs_clear_verifier_directory():

"What's to stop the inode from being freed right under you? You are not guaranteed to be holding rcu_read_lock(), unless I'm missing something in the call chain, so... what's going on here?"

Viro added fsdevel to the CC list, signaling that this review had broader VFS implications beyond just NFS. The concern centers on whether the inode being iterated could be freed concurrently while the verifier-clearing code walks its dentry list — a classic use-after-free scenario if RCU read-side protection is absent.

Concern 2: Purpose of Directory Cursors

In a follow-up [id://20260404190735.GS3836593@ZenIV], Viro raised an additional question about the presence of cursors on NFS directories:

"While we are at it, what are cursors doing on NFS directories? AFAICS, you are not using simple_dir_operations there or anything that would call dcache_dir_open(), for that matter. Confused..."

This suggests Viro was puzzled by why the verifier-clearing code manipulates directory cursor state, given that NFS does not use simple_dir_operations or the standard dcache_dir_open() infrastructure that typically manages such cursors.

Concern 3: Dentry Lifetime Guarantees in nfs_clear_verifier_file()

In his third and most detailed message [id://20260405023953.GU3836593@ZenIV], Viro provided a technical analysis of the dentry lifetime guarantees in nfs_clear_verifier_file(), noting that it does not need to check for a NULL parent directory:

"Incidentally, nfs_clear_verifier_file() doesn't need to bother with checking for NULL dir - alias is found in ->i_dentry of inode with ->i_lock held, which means it can't have progressed through __dentry_kill() to dropping the reference to parent. So holding alias->d_lock (which stabilizes ->d_parent) is enough - ->d_parent is still pinned by alias and it can't have become negative."

Viro emphasized the critical distinction between this case and nfs_set_verifier_locked():

""Can't have progressed through __dentry_kill()" is critical here - that's the difference from nfs_set_verifier_locked() case."

He closed with a broader admonition to the NFS development community:

"Folks, this stuff can get seriously subtle; please ask around on fsdevel if you are doing something non-trivial with it."

Key Technical Arguments and Conclusions

  1. Use-After-Free Risk: Viro identified a potential race condition in nfs_clear_verifier_directory() where an inode could be freed during dentry iteration without RCU protection. This remains unresolved at week's end — no response from Trond or other NFS developers was observed within the window.

  2. Cursor Semantics Question: The purpose of directory cursor manipulation in NFS verifier code is unclear, given that NFS does not use the standard VFS directory operations that would exercise cursors. This may indicate dead code or a misunderstanding of the dcache infrastructure.

  3. Dentry Lifetime Analysis: Viro clarified that nfs_clear_verifier_file() has stronger lifetime guarantees than previously assumed due to the ->i_lock preventing progression through __dentry_kill(). This is a correctness insight that could simplify the code.

  4. Broader VFS Engagement: By adding fsdevel to the CC list and urging NFS developers to consult the broader filesystem community, Viro signaled that directory delegation verifier code involves subtle VFS internals that warrant wider review.

Open Questions

  • Whether nfs_clear_verifier_directory() requires additional RCU or reference-counting protection against inode freeing.
  • Whether directory cursor manipulation in NFS verifier code serves any functional purpose.
  • How the dentry lifetime analysis applies to other verifier-related code paths.

No responses from Trond Myklebust, Anna Schumaker, or Christoph Hellwig were observed within this week's window. The thread remains open pending further discussion.
