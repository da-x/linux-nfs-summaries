NFS Server: Fixing False Positives in Delegation File Change Detection

Summary

Overview

This week, Scott Mayhew submitted [PATCH v2] nfsd: fix file change detection in CB_GETATTR [id://20260404005405.1565136-1-smayhew@redhat.com], addressing a bug in the NFS server's handling of write delegations. The discussion, involving maintainers Chuck Lever and Jeff Layton, focused on correcting non-compliant behavior regarding file change detection, optimizing stack usage, and debating the reliability of current attributes for detecting unflushed client data.

The Bug: Cached vs. Current File Size

The core issue lies in how nfsd determines if a client holding a delegation has modified a file. When the server issues a CB_GETATTR callback to a delegating client, it expects the client to report its current view of the file attributes.

Scott Mayhew highlighted that the existing implementation compared the file size reported by the client against a cached value stored in the delegation record (ncf_cur_fsize). This violated RFC 8881, Section 10.4.3. As Scott explained:

"RFC 8881, section 10.4.3 doesn't say anything about caching the file size in the delegation record... What section 10.4.3 of RFC 8881 does say is that the server should compare the current file size with size reported by the client holding the delegation in the CB_GETATTR reply."

The consequence of this bug was significant: if a client flushed its modifications to the server and then received a CB_GETATTR, the server would incorrectly believe the client still held modified data (because the cached size differed from the current size). This triggered unnecessary updates to metadata timestamps (mtime, ctime) even when no further changes were made.

Technical Evolution of the Patch

Stack Depth Concerns

Scott's v2 patch introduced a call to vfs_getattr() within nfsd4_deleg_getattr_conflict() to retrieve the current file size accurately. Chuck Lever raised concerns about the API design and stack depth, noting:

"Passing the kstat struct in saves some stack just as I suggested, but it is an ugly API... did you happen to measure how deep it gets after this patch is applied?"

Scott provided detailed stack tracing data using bpftrace, showing a maximum stack depth of approximately 1792 bytes when traversing through SELinux hooks (avc_lookup) during the vfs_getattr call [id://adLellU5iadfbYdX@smayhew-thinkpadp1gen4i.remote.csb].

Optimization: i_size_read vs. vfs_getattr

In response to the stack depth and complexity, Chuck Lever proposed a lighter-weight alternative. Since the client holds an exclusive write delegation, the file size should be stable and visible in the inode's memory representation without a full VFS getattr call.

"Since the new code only needs the file's size, perhaps you can get away with if (i_size_read(inode) != ncf->ncf_cb_fsize)... Then there's no longer a need for a struct kstat at all." [id://fb00b2d1-e7be-4567-a077-9ec26a938a5c@app.fastmail.com]

Scott agreed to this optimization, confirming he would send a v3 patch using i_size_read [id://adPrbw7adrsXGWVq@aion].

Debate on Change Detection Reliability

Jeff Layton raised broader concerns about the reliability of using file size and change attributes to detect unflushed data. He noted that size is not a reliable indicator for fixed-size files (e.g., VM images) and suggested checking mtime or extending the protocol.

"I hate relying on the size for this, since it's not a reliable indicator of change... In fact, I wonder if this ought to be looking at the mtime too." [id://e812ca8b2caaf2cafaf94b7b5be487346fe07285.camel@kernel.org]

Scott defended the current approach, emphasizing that the patch's primary goal was strict RFC compliance regarding the source of the comparison (current vs. cached), not necessarily inventing new detection heuristics. He argued that checking mtime might encroach on "delegated timestamps" territory and that the existing change attribute mechanism already handles unflushed writes:

"If an application calls write() but not fsync(), close(), etc... the dirty pages/folios will be tracked on the nfs_inode and the client will send the elevated change attribute in the CB_GETATTR reply. What am I missing?" [id://adQwSTW7ABXvrovQ@aion]

Jeff acknowledged the point about mtime crossing into delegated timestamps but remained skeptical that the change attribute alone is a "reliable indicator that there is still buffered write data on the client" [id://67a54e834a2625d0c31b19e22088d135f89c50b7.camel@kernel.org]. He floated the idea of a spec extension:

"Should we be looking at extending the spec? Maybe we should add a 'I have outstanding buffered data' attribute that the client could send to the server in a CB_GETATTR?" [id://ca6076eba9248c39f8b95bed66cec5d907aa0ab7.camel@kernel.org]

Conclusion

The thread concluded with consensus on the immediate bug fix: v3 of the patch will use i_size_read() to compare the current inode size against the client-reported size, adhering to RFC 8881 while avoiding stack depth issues. The broader discussion about the sufficiency of the change attribute for detecting unflushed data and potential future spec extensions remains an open topic for further consideration.
