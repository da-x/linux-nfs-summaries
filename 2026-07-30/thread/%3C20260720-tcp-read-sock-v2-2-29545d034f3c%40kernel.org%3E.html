kTLS maintainer doubts TCP-style API can hide TLS records

Summary

Late on 30 July, kTLS maintainer Sabrina Dubroca closed the week's debate on Chuck Lever's read_sock_rectype proto_ops hook with a verdict that is worse for NFS than a simple NACK. She agreed with networking maintainer Jakub Kicinski's stream-socket philosophy — and then said the mismatch that NFSD and a future NFS client xprtsock conversion are trying to paper over may be unfixable:

"I agree. But TCP is a magical world where users don't have to worry about message types, and TLS isn't. It seems the users of the existing (TCP-oriented) API are unhappy with the mismatch, but I'm not convinced we can (and maybe "should") make that work."

This is a new kernel networking API, not a protocol change and not, in this patch, a bug fix. The on-the-wire TLS/RPC framing is untouched. What is at stake for NFS is how in-kernel TCP consumers (NFSD first, the NFS client next) see KeyUpdate and fatal Alerts once kTLS is active, without falling back to sock_recvmsg() and CMSG, and without leaking control bytes into page-cache receive pages.

Brief recap: how the week arrived here

Patch 2 is the API core of Lever's six-patch net-next series. It adds read_sock_rectype to struct proto_ops and a sk_read_rectype_actor_t callback that carries a protocol-layer record type (for example TLS_RECORD_TYPE_ALERT). Existing read_sock consumers keep their old behavior. Lever named four affected subsystems: NFSD (svcsock), the NFS client (xprtsock), NVMe target, and NVMe host. Each either falls back to sock_recvmsg() or lacks TLS alert handling entirely.

Earlier this week, already summarized on the cover-letter thread, Kicinski rejected the hook as a TLS-only one-off that does not belong in proto_ops. Lever conceded Dubroca's "ugly in struct proto_ops" point. A setsockopt sketch that would pre-seed the expected content type collapsed into behavior kTLS already has: recvmsg without CMSG and read_sock already error out when the next record is control. Dubroca then translated Lever's page-cache complaint: a recvmsg with CMSG and pages dumps Alert or KeyUpdate bytes into those pages. To avoid that, a consumer must drain DATA with read_sock or recvmsg without CMSG, then — once nothing else is reading the socket — do one recvmsg+CMSG into a separate buffer. read_sock_rectype was meant to skip that dance.

That is the NFS-relevant bug the series is trying to fix. For in-kernel consumers the I/O buffers are page-cache pages. Mixing control payload into rq_pages (NFSD) or the equivalent client receive pages (xprtsock) is why svcsock still runs a MSG_CTRUNC recovery path, and why a kTLS-enabled NFS client still has no first-class control-record path at all.

This week's only new note: stream vs. typed records

Minutes before Dubroca's reply, Kicinski had restated the design philosophy that had already killed the setsockopt sketch:

"I guess the difference in perspective stems from a fact that I'd look at a socket as a stream one reads and dispatches work based on the input. Not an abstraction layer that by itself dispatches different handlers for different message types."

Dubroca agreed — and then drew the line that matters for anyone planning the NFS client conversion. TCP users never have to think about message types. TLS users do. The existing read_sock API is TCP-oriented. SUNRPC is unhappy with that mismatch. Making the kernel socket layer dispatch TLS record types on behalf of the consumer — which is exactly what read_sock_rectype does — may not be something netdev can, or should, provide.

That is a sharper conclusion than "try a generic extra argument on read_sock." Earlier in the week Dubroca had left that door open: growing read_sock by an argument would be acceptable if the extra argument were not TLS-specific, because there are only two existing proto_ops.read_sock consumers (strp/sockmap and NVMe) plus a handful of direct tcp_read_sock() callers that could pass NULL. A cmsg-like generic side channel, she had already warned, would erase most of the benefit and put callers back on "try read_sock, then fall back to recvmsg." Friday night's note goes further: even a well-shaped generic hook may be the wrong fight, because the TCP-shaped API cannot honestly hide TLS record types.

No alternative was proposed in this message. No v3 was posted. Lever did not reply in-window.

What this means for NFS client development

Nothing in this week's single in-thread mail touches xprtsock directly. The client conversion was always a follow-up, with NFSD svcsock as the template. Dubroca's closing line still lands on the client path:

  • The infrastructure that would let a kTLS-enabled NFS client see KeyUpdate and fatal Alerts on read_sock without a CMSG fallback, and without leaking control bytes into page-cache receive pages, is not merely waiting on a redesign. The kTLS maintainer is now questioning whether the kernel should try to make that TCP-shaped path work at all.
  • If netdev holds that line, the NFS client will keep the two-step receive: drain DATA with read_sock / recvmsg without CMSG, then a carefully serialized recvmsg+CMSG into a non-page-cache buffer when the next record is control. That is exactly the dance read_sock_rectype was invented to avoid, and it is the dance that already leaks into rq_pages when done carelessly on the server.
  • The homework Dubroca set earlier this week still stands if Lever tries again: measure current svcsock (sock_recvmsg only), read_sock plus a recvmsg+CMSG fallback, and whatever replaces read_sock_rectype. A rare Alert is not, by itself, enough to justify a new proto_ops method. After this note, even a measured win may not be enough if the API still tries to hide TLS record types from a TCP-oriented caller.
  • The one piece still moving is independent of this patch: the no-data bound for empty TLS 1.3 data records, already split to a net prerequisite, which protects NFSD service threads from a lock-pinning DoS. A future client read_sock loop will want the same escape hatch, whether or not control-record delivery is ever first-class.

Status at week close

The patch is rejected in spirit, not just in shape. Consensus after Dubroca's 23:40 UTC note:

  • read_sock_rectype as a TLS-specific proto_ops method will not land.
  • Kicinski wants sockets treated as streams that the caller demultiplexes. Dubroca agrees, and doubts the kernel should paper over TLS record types to keep TCP-oriented consumers happy.
  • No agreed replacement. The page-cache leak that motivates a first-class control-record path for SUNRPC is understood by the kTLS maintainer; she is no longer convinced it is a problem the socket API should solve.
  • NFSD svcsock conversion (patches 5–6) and the planned NFS client xprtsock conversion cannot land until — and unless — an API both sides will accept is invented.
  • Any resend should be tagged RFC, with human-written cover text, measurements, and a design that does not assume TLS can be made to look like TCP.

The practical takeaway for NFS client development this week: the lock-pinning fix is in flight, but the client still cannot handle TLS control records on read_sock, and the kTLS maintainer has now said the TCP-shaped API that was going to change that may be the wrong model.
