statd leak on SM_MON re-monitor

Summary

This week’s linux-nfs traffic included a small but pointed bug-fix patch for the userspace rpc.statd daemon, not a protocol change and not a kernel NFS client patch. xuchenchen of KylinSoft posted a two-line change to utils/statd/monitor.c titled “[PATCH] statd: fix memory leak in sm_mon_1_svc() when existing host re-monitors.” There were no replies in the window, so the discussion has not yet evolved into review, Acked-by, or merge commentary.

What broke

The leak lives in the SM_MON RPC handler that lockd/statd uses to register hosts for NSM (Network Status Monitor) notifications. When an NFS client (or another NSM peer) already has a notify_list entry and then sends a new SM_MON with a different priv cookie, sm_mon_1_svc() sets existing=1 and reuses that entry instead of allocating a fresh host record. The newly allocated DNS name string is then written over clnt->dns_name without releasing the previous pointer.

xuchenchen’s commit message states the failure mode plainly:

"When an already-monitored host sends a new SM_MON request with a different priv cookie, the code sets existing=1 and reuses the existing notify_list entry. However, clnt->dns_name is overwritten with the newly allocated dnsname without freeing the old value, causing a memory leak."

Because rpc.statd is a long-lived helper sitting under NFS lock recovery, that is not a one-shot leak:

"Since statd is a long-running daemon, repeated SM_MON requests with changing cookies will accumulate leaked strings."

That path is client-adjacent even though the code is in nfs-utils: Linux NFS clients rely on lockd + statd to monitor the server (and vice versa) so that NLM locks can be reclaimed after a reboot. A host that remounts, restarts lockd, or re-registers with a new cookie will keep pumping SM_MON at an already-tracked peer; each of those re-monitors would drop another dns_name allocation on the floor.

The fix

The patch does the obvious, local thing: free the old dns_name before overwriting it when the existing-host reuse path is taken. It is a two-insertion change (+2 lines in utils/statd/monitor.c), signed off by xuchenchen <xuchenchen@kylinos.cn>. No new NSM wire behavior is proposed; the SM_MON request is still accepted, the existing notify-list node is still reused, and only the string ownership is corrected.

Status this week

As of the 2026-07-30 window the thread is a single unreviewed patch. There is no maintainer ACK, no request for a reproducer or kmemleak/valgrind trace, and no debate over whether dnsname should be assigned at all on the existing-host path versus only when the name actually changes. Until that review lands, the practical takeaway for NFS client operators is that a long-running statd that sees repeated re-monitor SM_MON traffic with rotating priv cookies can leak hostname strings; the proposed fix is a one-site free() before the overwrite.
