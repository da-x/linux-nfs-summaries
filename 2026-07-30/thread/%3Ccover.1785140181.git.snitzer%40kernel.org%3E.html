NFSv4.2 client uncacheable-file and uncacheable-dirent support (v4)

Summary

This week Mike Snitzer posted PATCH v4 of a six-patch NFSv4.2 client series that implements two companion OPTIONAL attributes from IETF drafts: UNCACHEABLE_FILE_DATA (FATTR4 87) and UNCACHEABLE_DIRENT_METADATA (FATTR4 88). The posting is a feature series with two important client bug fixes versus v3; no reviews arrived in-window.

The attributes let a server tell the client to stop caching state that changes faster than a typical NFS cache lifetime. Snitzer's cover letter frames the target deployments as mixed-protocol namespaces:

"The motivating deployments expose a single namespace concurrently through NFSv4.2, NFSv3, and SMB, plus server-side policy engines, so file data and directory contents can change faster than a typical client cache lifetime -- producing stale reads and read-modify-write "write holes" for file data, and stale size/timestamp listings for directories."

Both attributes are independent, type-disjoint, read-write booleans. The Linux client only honors a server-set value; it does not SETATTR either bit. A server MUST reject a query of attr 87 on a non-regular object, or attr 88 on a non-directory, with NFS4ERR_INVAL. That type-gating rule is the source of both v4 regressions.

Prior versions (brief)

v1 (late June) covered only attr 87 and tried to introduce it via xdrgen (Documentation/sunrpc/xdr/nfs4_2.x). Anna Schumaker objected that xdrgen is a server-side tool, and Chuck Lever confirmed the client does not consume those generated headers. Schumaker also asked for a bool inode flag and cleanup of stray whitespace. v2 dropped xdrgen, open-coded the FATTR4 constants in <linux/nfs4.h>, stored the flags as bool : 1 bitfields, and added the three attr-88 patches. v3 (1 July) was a one-line build fix: FATTR4_WORD2_UNCACHEABLE_FILE_DATA became the first, unconditional nfs4_fattr_bitmap word2 entry so the initializer no longer started with a stray | when CONFIG_NFS_V4_SECURITY_LABEL was off.

v4: two NFS4ERR_INVAL holes

v4's headline is two client-side request-bitmap bugs that would fail opens and directory-delegation returns against any server advertising the new attributes.

Hole 1 — regular-file OPEN vs. attr 88. v3 put UNCACHEABLE_DIRENT_METADATA into the shared request bitmaps (nfs4_fattr_bitmap, nfs4_pnfs_open_bitmap). Those arrays are used verbatim as OPEN's open_bitmap: a GETATTR that is masked only by the server's supported set and is not type-gated. Every regular-file OPEN therefore queried a directory-only attribute. Snitzer:

"v3 placed attr 88 in the shared request bitmaps ... so every regular-file OPEN queried a directory-only attribute and the server answered NFS4ERR_INVAL, failing opens broadly."

Patch 4 no longer adds attr 88 to those bitmaps. Patch 5 instead has nfs4_bitmap_copy_adjust() add it only for directory targets, gated on server->attr_bitmask. Attr 87 continues to ride the shared bitmaps because it is legal — and wanted — on a regular-file OPEN (it drives the O_DIRECT decision).

Hole 2 — directory DELEGRETURN vs. attr 87. The opposite direction: nfs4_update_changeattr_locked() only ever runs on directory inodes, but v3 had it set the file-only NFS_INO_INVALID_UNCACHEABLE_FILE_DATA bit. nfs4_bitmask_set() then translated that bit into a request for attr 87 with no object-type check. With directory delegation support, DELEGRETURN of a directory delegation would query attr 87 on a directory and fail NFS4ERR_INVAL. Patch 2 drops the bit from the directory-only aggregation and type-gates nfs4_bitmask_set() so attr 87 is requested only for S_ISREG inodes.

Net of the two gates: a regular file requests file_data and never dirent_metadata; a directory requests dirent_metadata and never file_data; an unknown/other object (LOOKUP/LOOKUPP/CREATE with a NULL inode) requests neither.

How the client honors the attributes

UNCACHEABLE_FILE_DATA (patches 1–3). Patch 1 (Tom Haynes, adapted by Snitzer) decodes attr 87, tracks per-exported-filesystem support, and records NFS_I(inode)->uncacheable_file_data. Patch 3 then opens a marked regular file with O_DIRECT via a new NFS_CONTEXT_O_DIRECT open-context flag, set in nfs4_atomic_open() (unless the open is O_APPEND) and applied by nfs_atomic_open() / nfs4_file_open(). The I/O mode is chosen at open and is not flipped on an already-open file; a later attribute change takes effect on the next open, which the draft permits.

The implementation deliberately does not take the draft's optional Section 4.3 relaxation that would keep read caching under a delegation:

"This implementation deliberately does not take it: an uncacheable file is opened O_DIRECT regardless of any delegation held, which is compliant (read caching is simply suppressed more aggressively than the Section 4.3 minimum) and avoids decoupling read vs write caching behind a single open flag. Relaxing reads under a delegation is left as a possible future optimization."

Misaligned O_DIRECT over SunRPC is already legal for the remote NFS path; the only DIO-alignment fallback is NFS LOCALIO, which is unaffected.

UNCACHEABLE_DIRENT_METADATA (patches 4–6). Patch 4 decodes attr 88 and records NFS_I(inode)->uncacheable_dirent_metadata. Unlike attr 87, this directory attribute is not tied to cache_validity / file-delegation machinery and has no NFS_INO_INVALID_* bit of its own. It is requested unconditionally for directories via the type gate, so it is refetched on every directory GETATTR and cannot go stale. A comment at the inode-recording site documents the asymmetry: a directory cannot hold an NFSv4 read/write delegation, and the draft requires a server to recall or withhold a directory delegation while the attribute is set, so there is never an authoritative cached state to optimize against. An invalidation bit would only be useful alongside a lazy re-request path such as nfs4_bitmask_set(), which is not type-gated and would request a directory-only attribute on regular files.

Patch 6 is the readdir-path change. When a directory is marked uncacheable, nfs_readdir() bypasses the readdir page cache by forcing the -EBADCOOKIE path into uncached_readdir() (including dir_cookie == 0, so the first listing of an uncacheable directory also hits the server). A new tracepoint records the bypass. Because the attribute governs per-entry size and timestamps — carried only by READDIRPLUS — the patch also forces READDIRPLUS for an uncacheable directory when the server is capable. Without that, nfs_use_readdirplus() would enable plus-mode only at directory start or after a cache-usage threshold that the cache-bypassing path never accrues, leaving continuation READDIRs of a large directory refreshing names but serving stale per-entry attributes from inode caches. Forcing READDIRPLUS makes each READDIR refresh those caches via nfs_prime_dcache() → nfs_refresh_inode(), so a subsequent stat() sees current values. Directory change-attribute semantics are unchanged; only serving READDIR responses from the local cache is suppressed.

Status

The series touches fs/nfs/{dir,inode,nfs4file,nfs4proc,nfs4xdr}.c plus the usual headers and tracepoints (~235 insertions). Authorship is Tom Haynes for patch 1 and Snitzer for the rest; several commits carry an Assisted-by: Claude:claude-opus-4-8 tag. No Acked-by/Reviewed-by tags and no on-list replies this week. The two v4 bitmap fixes are the concrete client correctness work: without them, advertising either new attribute on a server would break ordinary OPEN of regular files or DELEGRETURN of directory delegations with NFS4ERR_INVAL.
