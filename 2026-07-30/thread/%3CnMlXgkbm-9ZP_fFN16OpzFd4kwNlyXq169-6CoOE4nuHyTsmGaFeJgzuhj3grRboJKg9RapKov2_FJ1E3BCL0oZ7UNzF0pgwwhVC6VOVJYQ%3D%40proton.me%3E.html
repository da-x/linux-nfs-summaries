NFSv4.2 futimens() still silent on SETATTR

Summary

Summary

This remains a client-side bug report, not a protocol change or new feature. Last week Michael Yang showed that GNU touch on NFSv4.2 can return success from the fd-based futimens() / utimensat(fd, NULL, ...) path while never sending SETATTR, so the server inode is unchanged and the client's cached timestamps later snap back. Holger Hoffstätte independently confirmed the failure on 7.1.x and pointed at 7.0-era NFS/VFS timestamp work as a first-pass suspect.

This week's only in-window follow-up is Yang's reply of 25 July, which tightens the version and protocol picture without yet producing a maintainer diagnosis or patch.

This week's finding: not just 7.0, and not NFSv4.1

Yang thanked Hoffstätte for the confirmation, then added two facts that matter for anyone hunting the NFS client setattr path.

First, the same silent-success behaviour is already documented outside linux-nfs. He pointed at Proxmox bug 7621, where the problem showed up on 6.17.x and 7.0.x and is absent on the 6.12.88 LTS kernel:

"I've found this report (https://bugzilla.proxmox.com/show_bug.cgi?id=7621) where the problem manifested as early as 6.17.x and 7.0.x (but is not present on the 6.12.88 LTS kernel), and is isolated to NFSv4.2."

That is a meaningful shift from last week's working hypothesis. Hoffstätte had noted that 7.0.0 already reproduced and flagged b8b3002fbfef (nfs: split nfs_update_timestamps) plus 761475268fa8 (fs: refactor ->update_time handling) as plausible 7.0 merge-window suspects. A 6.17 onset means those 7.0 commits cannot be the original introduction, even if they still sit on the failing path. The practical bisection window for NFS client developers is now 6.12.88 (good) through 6.17 (bad), not 7.0.

Second, Yang isolated the failure to NFSv4.2 on the wire. Mounting the same share with vers=4.1 makes the timestamps land on the server:

"I can confirm with client mount option vers=4.1, the timestamps update successfully on the server."

Combined with last week's fd-versus-pathname split, the client picture is now quite sharp:

  • Broken: NFSv4.2, fd-based futimens() / utimensat(fd, NULL, ...) (GNU touch -d). Syscall returns 0, local cache is updated, no SETATTR is sent, server inode unchanged, later revalidation reverts the timestamps.
  • Works: the same fd-based call on NFSv4.1 (vers=4.1).
  • Works: pathname-based utimensat(AT_FDCWD, path, ...) on NFSv4.2, which does increment the client SETATTR counter and updates the server inode.
  • Works: 6.12.88 LTS, even on NFSv4.2.

That combination is characteristic of an NFS client setattr/timestamp bug in the v4.2 open-file path, not a server or autofs misconfiguration. Userspace is told the update succeeded; the local inode is dirtied; nothing is flushed to the wire.

Where things stand

No maintainer reply, bisection to a commit, or patch landed inside this week. The report is now independently reproduced, version-bounded against LTS, and protocol-bounded to v4.2. The remaining work for NFS client developers is to find which 6.13–6.17 change made the fd-based ->update_time / setattr path skip SETATTR only when speaking NFSv4.2 — last week's 7.0 timestamp-split and VFS ->update_time refactor remain relevant as later code on that path, but they are no longer the first place the regression can have landed.

No protocol change is proposed. The user-visible impact is unchanged and still nasty: tools that rely on futimens() (notably GNU touch -d) look successful, then the timestamps evaporate on the next revalidation.
