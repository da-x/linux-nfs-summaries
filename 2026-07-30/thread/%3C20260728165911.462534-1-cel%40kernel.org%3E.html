LOCALIO v2 drops client headers and version-specific FH behavior

Summary

Chuck Lever posted a five-patch v2 cleanup that finishes peeling NFS client headers out of server-side LOCALIO. The series is a refactoring / xdrgen prerequisite, not a protocol change. The cover letter still says "[n]o change in behavior is expected," though Mike Snitzer later noted that patch 5 is a small, favorable efficiency win on the LOCALIO open path.

This thread is the successor to the v1 three-patch series posted the day before. v1 already moved the LOCALIO RPC program numbers, stopped nfslocalio.h from pulling uapi/linux/nfs.h into every consumer, and replaced the client-only decode_opaque_fixed() wrapper with the shared SUNRPC primitive. Neil Brown asked v1 not to reintroduce <linux/nfs4.h> just for NFS4_FHSIZE. v2's changelog records that directly:

"Including <linux/nfs4.h> is also no longer needed (Neil Brown)"

and grows two extra NFSD patches that name, then use, a version-neutral filehandle size so LOCALIO no longer pretends to be NFSv4.

Both Brown and Snitzer Reviewed-by the whole series in-window. No further revisions were requested.

Why this matters for the NFS client

LOCALIO sits on the client/server boundary. include/linux/nfslocalio.h is compiled into the NFS client as well as NFSD, so every extra client include that leaks through that header is compile-time coupling the client cannot later break. Lever's stated goal is that fs/nfsd/localio.c "is a server-side component, so it should avoid dependency on client-specific headers and XDR utilities," as a prerequisite to converting NFSD to xdrgen more broadly.

The client-visible half of that work is the shared-header cleanup (patches 1–2). The server-visible half (patches 3–5) stops LOCALIO from compiling against nfs_fs.h / nfs_xdr.h and from taking the NFSv4 arm of nfsd_set_fh_dentry() just because the copy buffer happened to be NFS4_FHSIZE.

Shared-header cleanup (patches 1–2)

Patch 1 moves the LOCALIO RPC program definitions out of include/linux/nfs.h into include/linux/nfslocalio.h. Those numbers are not needed by most files that include linux/nfs.h; the move follows the convention used by most other in-kernel RPC programs.

Patch 2 then replaces #include <linux/nfs.h> in linux/nfslocalio.h with #include <linux/nfs_fh.h>. The only reason the shared LOCALIO header pulled in linux/nfs.h was struct nfs_fh, which now lives in linux/nfs_fh.h. The practical effect for NFS client build hygiene is that nfslocalio.h no longer carries uapi/linux/nfs.h into its consumers.

Together the two patches shrink include/linux/nfs.h and make nfslocalio.h a LOCALIO-specific header rather than a back-door into the client UAPI.

Dropping the client XDR wrapper (patch 3)

Patch 3 is the technical core carried forward from v1. fs/nfsd/localio.c pulled in three client headers it did not need:

  • <linux/nfs_fs.h> — the client inode header (struct nfs_inode, NFS_I(), writeback helpers). Server code never uses those symbols.
  • <linux/nfs_xdr.h> — referenced only for decode_opaque_fixed(), a static inline that remaps the XDR error return to -EIO for client call sites.
  • <linux/nfs.h> — the catch-all that also dragged UAPI NFS definitions into every consumer.

The UUID decoder now calls xdr_stream_decode_opaque_fixed() directly. That helper is shared by client and server, performs the identical bounds check, and is already reachable through <linux/sunrpc/clnt.h>. With the wrapper gone, localio references no symbol from <linux/nfs_xdr.h>, and with that header gone, none of the NFSv3 definitions its structs embed are needed either.

v2 still mentions NFS4_FHSIZE from <linux/nfs4.h> in the patch 3 commit message (the leftover from v1), but patches 4–5 immediately retire that constant on the LOCALIO path. struct nfs_fh is included directly from <linux/nfs_fh.h> rather than through nfslocalio.h's conditional re-export. enum nfs_stat and nfs_stat_to_errno continue to come from the already-included <linux/nfs_common.h>.

Version-neutral filehandles (patches 4–5)

This is the new work in v2, and it is the closest thing in the series to a bug fix — a correctness/efficiency fix on a version-confused code path, not a protocol change.

nfsd_set_fh_dentry() selects NFS-version-specific behavior by matching fh_maxsize against NFS_FHSIZE, NFS3_FHSIZE, or NFS4_FHSIZE. A filehandle that reaches NFSD outside an NFS request has no such version. Patch 4 names that case. nlm_fopen() already opted out of the switch by passing a bare 0, "which matches no arm, and the literal says nothing about why, so an adjacent comment has to carry it." Lever introduces NFSD_FHSIZE_UNSPEC in nfsfh.h and uses it from lockd, so the "no NFS version" intent is in the identifier rather than a comment.

Patch 5 applies the same opt-out to LOCALIO, with a Suggested-by: NeilBrown. LOCALIO serves NFS clients of every version through one entry point, so no protocol version is associated with such a request. The old code passed NFS4_FHSIZE because that was the size of the buffer nfsd_open_local_fh() copied into, so LOCALIO landed in the NFSv4 arm. fh_getattr() keys off fh_maxsize too and does run on a LOCALIO open, adding STATX_BTIME and STATX_CHANGE_COOKIE to the mask it requests: "work on filesystems that compute them for a caller that never reads them."

nfsd_open_local_fh() only verifies a handle it received, so it has no maximum size to state. v2 passes NFSD_FHSIZE_UNSPEC (as nlm_fopen() already does) and states the bound on the copy out of struct nfs_fh as NFS_MAXFHSIZE — exactly the substitution Brown asked for on v1, but applied at the call site that actually needed a size, not as a drive-by include swap.

That is the client-relevant point as well as the server one. LOCALIO filehandles are not NFSv4 filehandles; they are opaque handles whose maximum size is the generic NFS_MAXFHSIZE already defined next to struct nfs_fh. Baking NFS4_FHSIZE into a shared local-I/O path would have left a version-specific constant on a path the NFS client also compiles against.

Reviews and conclusion

Neil Brown replied to patch 5 the same evening and signed off the whole series:

"Thanks for putting in the extra research to get a fully baked solution instead of just using my half baked idea. I like what you did a lot."

"For the whole series: Reviewed-by: NeilBrown"

Mike Snitzer, LOCALIO's original author, reviewed the cover letter the next day:

"Nicely done (but patch 5 makes fh_getattr more efficient for LOCALIO right? So favorable change in behavior)."

"For the series: Reviewed-by: Mike Snitzer"

Snitzer's parenthetical is the only qualification of Lever's "no change in behavior" claim, and it is a compliment: LOCALIO opens no longer force filesystems to compute birth-time and change-cookie attributes that the caller never reads.

Status at week close: v2 has two Reviewed-by tags and no outstanding comments. The series is a cleanup / xdrgen prerequisite with one small, favorable LOCALIO efficiency fix. Consensus is that the shared LOCALIO header is now a true common layer rather than "server code that happens to include client headers," and that LOCALIO requests are version-neutral at the nfsd_set_fh_dentry() switch.

For NFS client development this week: nfslocalio.h no longer smuggles uapi/linux/nfs.h or client-only XDR wrappers into client builds, and the LOCALIO open path no longer impersonates NFSv4 just because its copy buffer was NFS4_FHSIZE. The functional LOCALIO data path is otherwise unchanged.
