Netdev rejects read_sock_rectype; kTLS API redesign demanded

Summary

Nine days after Chuck Lever posted v2 of the six-patch net-next series that would let kernel read_sock consumers see TLS Alerts and Handshake records, networking maintainer Jakub Kicinski opened a hard review of both the cover letter and the new read_sock_rectype proto_ops hook. By the end of the week the series is not a merge candidate: the no-data bound has already been split out to a net prerequisite, and the remaining API — the piece NFSD and a later NFS client xprtsock conversion both depend on — is treated as a TLS-specific one-off that must be redesigned.

This is a new kernel networking API plus a related kTLS bug fix, not a protocol change. The on-the-wire TLS/RPC framing is untouched. What is at stake for NFS is how in-kernel TCP consumers (NFSD first, the NFS client next) see KeyUpdate and fatal Alerts once kTLS is active, without falling back to sock_recvmsg() and CMSG.

Brief recap of last week

v2 added read_sock_rectype to struct proto_ops, implemented it on the kTLS software path, converted NFSD svcsock, and bounded consecutive no-data records in tls_sw_read_sock(). Hannes Reinecke Reviewed-by'd patches 1–3. Sabrina Dubroca asked Lever to peel the no-data cap out to net as a standalone fix for empty TLS 1.3 data records, and keep patches 2–6 on net-next. That split is now done; this week's fight is about whether the new API should exist at all.

Cover letter and the AI detour

Kicinski's first note was not about the code. Quoting the cover-letter paragraph that explained why the no-data cap is a prerequisite, he asked:

"Is it just me or this is incomprehensible slop? Run on sentences full of terms no kernel developer would use?"

Lever said the paragraph made sense to him and noted that patch 1 is moving to a prerequisite series, so the text can be dropped. When Kicinski pressed — "Did you write this? If not what model did you use?" — Lever answered plainly:

"I did not write this text. It was written with Opus 5 and reviewed by gpt-5.6, sashiko (gemini), and myself, repeatedly."

He added that he is "not aware of a requirement to add an AI-related tag to a series cover letter" and that the letter "needlessly duplicates content from the patch commit messages" but is "bland," not "nonsensical." Kicinski said he was just curious:

"I find gpt-5.6 output largely incomprehensible."

The exchange soured the rest of the review. When Lever later asked for direction rather than a terse NACK, Kicinski wrote:

"True. We should remove maintainers and just commit obvious LLM slop."

Lever's reply is the more useful line for anyone following the series: he uses models "to go from blank page to RFC/v1. Where we go next is up to human taste, as always." Dubroca's later remark that this posting should have been tagged "RFC v2" rather than "PATCH v2" is the procedural takeaway. The February RFC never went to netdev; posting a fully numbered v2 on net-next made the design look finished when Lever still wanted steering.

The API NACK: no TLS-only proto_ops hook

The technical core is patch 2. Kicinski's first review of it is the week's decisive sentence:

"To me this is an ugly one-off workaround that doesn't fit into the proto_ops (only TLS will use it). And you seem to net out to the same LOC on SUNRPC side with and without this?"

He added the policy line that has blocked several in-kernel networking APIs:

"There needs to be a very strong reason for us to add APIs for in kernel consumers."

Lever pushed back hard. Line count is the wrong metric:

"It's not about LOC. It's about not cluttering the normal I/O path with a lot of exception processing to handle TLS Alert records. The CMSG API is very difficult to use and leaks the alert messages into I/O buffers (which for in-kernel consumers are page cache pages). It's piss-poor API design."

On the "strong reason" demand he wrote:

"This is not a helpful position. Your objection is the same every time, treating the in-kernel users as second-class citizens. You haven't provided a single alternative to address our concerns, and you have not explained why an additional API is a problem."

Kicinski rejected the second-class framing. Kernel consumers, he said, "have a tendency to break all abstractions and insert hacks all over the place just because they are not forced to go via uAPI boundary." His instruction was to rework existing callbacks, not add a TLS-only proto_ops method:

"You just need to try a little harder to produce a better solution. Rework or augment existing callbacks to let your achieve the behavior you want."

Lever asked for that steering rather than a cold stop:

"No-one is asking you to roll over. Review means you get to steer us in the right direction, and I promise to do the leg work. Terse rejection doesn't move the discussion forward. It stops it cold."

He also explained the original shape of the series: a new read_sock variant, rather than growing read_sock itself, because he "suspected you wouldn't want read_sock itself to grow another argument."

Dubroca's design critique, and Lever's concession

kTLS maintainer Sabrina Dubroca supplied the detailed review Kicinski had not. Three points matter for anyone planning the NFS client conversion.

First, process: if Lever wanted direction, the series should have been RFC v2. "PATCH v2" reads as a finished idea.

Second, the performance case for a new callback is unproven. Non-DATA records are uncommon. She is "not that convinced 'oh well let's try again' once in a while causes a measurable degradation." She asked for numbers comparing three designs, not just old read_sock versus new read_sock:

  • current svcsock (sock_recvmsg only)
  • read_sock with a recvmsg+CMSG fallback on non-DATA
  • read_sock_rectype

The comparison that would justify an API change is "read_sock vs read_sock++".

Third, growing read_sock by an argument would be acceptable — there are only two existing proto_ops.read_sock consumers (strp/sockmap and NVMe), plus a handful of direct tcp_read_sock() callers that could pass NULL. The real problem is that the extra argument is TLS-specific:

"dropping something TLS-specific in a generic API (struct proto_ops) is quite ugly. If we want to make this generic, we're back to cmsg (or something cmsg-like). And then the benefit for users of read_sock gets down to avoiding the 'try read_sock, then fall back to recvmsg' logic."

Lever accepted that with a two-word reply: "Fair enough." That is the first explicit concession that read_sock_rectype as posted is not the shape that will land.

Alternatives: setsockopt vs. the page-cache leak

Pressed for an alternative, Kicinski sketched a setsockopt that pre-seeds the expected content type so a read returns an errno when the queued record is something else. Configure the socket for DATA; on EWHATEVER, hand the socket to a TLS control path. "This is literally the first thing that comes to mind, IDK how ugly it will look in reality so no promises."

Dubroca immediately pointed out that this is the same control-flow as today's fallback:

"But then you're back to 'read_sock stopped, caller has to take some special action to handle the next bit of payload'. It's not better than 'read_sock, and do a recvmsg when read_sock says it's not DATA'."

Kicinski then looked at the existing kTLS code and walked the sketch back:

"My bad, I replied without looking at the code. We already constrain control records in the way I proposed. rcvmsg (w/o cmsg) and read_sock will error out if the next record is control."

That left him puzzled by Lever's page-cache claim:

"I guess I don't understand what Chuck meant when he said that he has control data leaking into page cache ;/"

Dubroca translated the NFS/SUNRPC problem. If you recvmsg with a CMSG and pages, control records land in those pages. To avoid that you must:

  1. drain DATA with recvmsg without CMSG, or with read_sock;
  2. once you know the next record is control (and nothing else is reading the socket), do one recvmsg+CMSG into a separate buffer.

"The weird read_sock_rectype magic here avoids all that."

That is the NFS-relevant bug the series is trying to fix. For in-kernel consumers the I/O buffers are page-cache pages. A CMSG receive that also copies Alert or KeyUpdate bytes into rq_pages (NFSD) or the equivalent client receive pages (xprtsock) mixes control payload into RPC message memory. The current svcsock MSG_CTRUNC recovery dance exists because of this. The NFS client still has no first-class path at all.

Kicinski's closing note of the week is a statement of philosophy, not a resolution:

"I guess the difference in perspective stems from a fact that I'd look at a socket as a stream one reads and dispatches work based on the input. Not an abstraction layer that by itself dispatches different handlers for different message types."

No new API was agreed. No v3 was posted. The discussion was still open when the window closed.

The no-data bound: bug fix, now a net prerequisite

On patch 1, Kicinski asked whether Lever's cond_resched() rationale was "alluding to PREEMPT_NONE (which for practical purposes is no longer a thing AFAIU)." Lever said no: that wording was a bad way to make the point. The bound protects the calling NFSD thread:

"A client can open multiple connections that all send a continuous stream of empty TLS records, as a denial of service attack. The mechanism added here is an escape hatch for consumers."

That is the important bug fix in this thread, and it is no longer part of the net-next series. Lever confirmed it has already moved to a prerequisite series aimed at net, at Dubroca's request: https://lore.kernel.org/r/20260726-tls-follow-on-v1-0-99bf4cc1c729@kernel.org. Empty TLS 1.3 data records can already pin tls_sw_read_sock(); the cap is an escape hatch for that DoS, independent of read_sock_rectype.

What this means for NFS client development

Nothing in this week's mail touches xprtsock directly. The client conversion was always a follow-up, with NFSD svcsock as the template. The week's result still lands on the client path:

  • The infrastructure that would let a kTLS-enabled NFS client see KeyUpdate and fatal Alerts on read_sock without a CMSG fallback, and without leaking control bytes into page-cache receive pages, is on hold pending a redesign that netdev will accept.
  • Dubroca's three-way comparison is the homework before any NFS client series: measure current sock_recvmsg, read_sock plus fallback, and whatever replaces read_sock_rectype. A rare Alert is not, by itself, enough to justify a new proto_ops method.
  • Growing read_sock with a generic extra argument is on the table; a TLS-only read_sock_rectype is not. A cmsg-like generic side channel would erase most of the benefit.
  • The DoS bound for empty records is the one piece that is moving forward, on net, and it protects NFSD service threads today. A future client read_sock loop will want the same escape hatch.

Status at week close

The series is under hostile redesign, not merged. Consensus in-window:

  • Patch 1 is a standalone kTLS bug fix for empty TLS 1.3 data records / NFSD-thread DoS, already split to net.
  • Patch 2's new proto_ops method is rejected as a TLS-specific one-off. Lever has conceded Dubroca's "ugly in struct proto_ops" point.
  • No agreed replacement. Kicinski's setsockopt sketch collapsed into behavior kTLS already has. The page-cache leak that motivates a first-class control-record path for SUNRPC is now understood by the kTLS maintainer, but not yet by a design both sides will take.
  • NFSD svcsock conversion (patches 5–6) and the planned NFS client xprtsock conversion cannot land until the API is redesigned.
  • Any resend should be tagged RFC, with human-written cover text and measurements.

The practical takeaway for NFS client development this week: the lock-pinning fix is in flight, but the client still cannot handle TLS control records on read_sock, and the API that was going to change that has to be invented again.
