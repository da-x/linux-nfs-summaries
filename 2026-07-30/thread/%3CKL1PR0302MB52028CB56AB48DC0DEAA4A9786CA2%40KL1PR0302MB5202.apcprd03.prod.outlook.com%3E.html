pNFS client size stale across layoutcommit

Summary

NFSv4.2/pNFS: applications can still see a stale file size across layoutcommit

Lenovo's Quan Wang posted a one-hunk NFS client bug fix this week aimed at a pNFS attribute-consistency hole: after a parallel write has already recorded a new last-write-byte, a racing dentry revalidation can still hand userspace the metadata server's old i_size. The posting is a bug fix, not a protocol change and not a new feature. It arrived without review, without a Fixes: tag, and with a commit log short enough that maintainers will almost certainly ask for a rewrite before it can land.

What landed on the list this week

On 29 July, Wang posted [PATCH] NFSv4.2/pNFS: fix applacation get old size of file (the subject line keeps the "applacation" typo). The change is three lines in fs/nfs/inode.c (two insertions, one deletion). The entire technical argument is a single sentence:

"it happened when call nfs_lookup_revalidate_dentry between pnfs_set_layoutcommit and nfs4_layoutcommit_release"

A same-subject message from Wang appeared a day earlier, on 28 July, as a separate thread root, but that earlier note carried no usable patch body. This week's in-window discussion is therefore the 29 July resend plus silence: no Acked-by, no review comments, no maintainer follow-up.

The client race, in NFS terms

The window Wang names is the classic pNFS "MDS does not know the new size yet" interval.

  • pnfs_set_layoutcommit() is the client-side bookkeeping that runs after a pNFS data-server write. It records the new last-write-byte on the layout header and sets NFS_INO_LAYOUTCOMMIT so a later LAYOUTCOMMIT can push that size (and the modified layout) to the metadata server.
  • nfs4_layoutcommit_release() is the completion path for that LAYOUTCOMMIT RPC. Only then does the client normally fold the MDS's post-commit attributes back into the inode.
  • Between those two points the MDS GETATTR size is still the pre-write value. If nfs_lookup_revalidate_dentry() runs in that gap — a path the VFS takes on pretty much any lookup/stat of a dentry whose cache validity has expired — the revalidation can refresh inode attributes from the MDS and install that stale size.

From an application point of view the file has already been written (and the client already knows the new size via the layoutcommit state), but stat(), fstat(), or a subsequent open/lookup reports the old length. That is exactly the class of pNFS client bug that shows up as truncated reads, short copy_file_range/clone decisions, or build tools that decide a just-written artifact is empty.

The fact that the hunk lives in fs/nfs/inode.c rather than fs/nfs/pnfs.c or nfs4proc.c is the important client-design signal. Wang is not changing when LAYOUTCOMMIT is sent, nor the NFSv4.2 wire format. He is teaching the generic NFS inode attribute-update / revalidation path to respect a pending layoutcommit so that a lookup-time GETATTR cannot clobber a size the layout code has already claimed.

That is the same family of defense the client already uses for outstanding writebacks and delegations: do not let a server attribute refresh shrink or replace i_size while the client still holds a more recent locally generated size. Extending that rule across NFS_INO_LAYOUTCOMMIT is the obvious three-line shape of this patch, even though the list posting omitted a readable diff in the ingested copy.

Why this matters for NFSv4.2 / pNFS client work

On a non-pNFS NFSv4 mount, writes go through the MDS, so a GETATTR after a successful WRITE already sees the new size (or the client has unstable-write / close-to-open state that keeps i_size coherent). pNFS breaks that assumption: the data path and the metadata path are different servers. File size becomes a client-reconstructed value until LAYOUTCOMMIT. Any hole in that reconstruction is user-visible.

nfs_lookup_revalidate_dentry() is a particularly nasty trigger because it is not under the writer's lock. A second process doing stat on the same path, a directory listing that revalidates children, or even the writer's own path-based follow-up can land in the window. The bug is therefore not "writer sees the wrong size in its own fd" so much as "the dcache/inode cache forgets the pNFS-extended size the moment someone looks the name up again."

That is also why a fix in inode.c is more interesting than a layout-driver workaround. A block/SCSI-layout-only change would miss files, objects, and Flexfiles. Putting the guard on the common inode update path is the right layer — if the condition is tight enough not to paper over genuine MDS size changes (truncate from another client, setattr, etc.).

What the posting does not yet give reviewers

The patch is not review-ready by linux-nfs norms, and that is the other story this week.

  • The commit message does not name the function being changed, the flag or helper being tested, or the precise attribute field that is being preserved.
  • There is no reproducer (even a "write via pNFS, immediately stat from another task" sketch), no Fixes:, no Cc: stable, and no indication of which layout driver or NFSv4.2 feature (copy, seek, fallocate, ordinary writes) first exposed it.
  • The subject and log are riddled with typos ("applacation", "when call"), the list subject is missing a stable [PATCH] prefix, and the Signed-off-by line is slightly malformed. A day-earlier attempt at the same subject suggests the 29 July mail is already a resend.

None of that makes the race description implausible. It does mean the thread currently ends where it started: a plausible client bug with a three-line inode.c proposed fix, and no one yet on the record agreeing that the chosen condition is sufficient — or that it does not reintroduce the opposite bug of ignoring a real MDS-side shrink.

Status

Bug fix, NFS client, pNFS/NFSv4.2 attribute cache. Discussion has not evolved past the initial post. Until a reviewer walks through nfs_lookup_revalidate_dentry() versus pnfs_set_layoutcommit() / nfs4_layoutcommit_release() and confirms the inode.c guard, this should be treated as an unreviewed report of a real-looking size-coherence race rather than a merged fix.

The next useful step from Wang — or from anyone picking the report up — is a v2 that quotes the exact inode helper being changed, explains how a pending layoutcommit size wins over a GETATTR without masking truncate, and adds a Fixes: line so -stable can follow.
