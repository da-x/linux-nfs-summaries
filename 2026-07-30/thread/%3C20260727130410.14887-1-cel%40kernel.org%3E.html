LOCALIO drops NFS client headers ahead of xdrgen

Summary

Chuck Lever posted a three-patch cleanup series that strips NFS client headers out of server-side LOCALIO. The work is a refactoring, not a protocol change and not a functional bug fix: fs/nfsd/localio.c is a server component, so it should not depend on client-specific headers or XDR helpers. Lever's cover letter is explicit that "[n]o change in behavior is expected."

The series is a prerequisite for converting NFSD to xdrgen more broadly. LOCALIO sits on the client/server boundary (include/linux/nfslocalio.h is shared), so the header graph here is as much a client-development issue as a server one: every extra client include that leaks through nfslocalio.h is compile-time coupling the NFS client cannot later break.

Neil Brown reviewed patch 3 the next day, asked for one include change, and otherwise signed off. Lever absorbed that comment into a v2 series posted later on 28 July (a separate thread). This v1 thread itself ends with Brown's review.

Why the client headers were there

Patch 3 is the technical core. fs/nfsd/localio.c pulled in three client headers it did not need:

  • <linux/nfs_fs.h> — the client inode header (struct nfs_inode, NFS_I(), writeback helpers). Server code never uses those symbols.
  • <linux/nfs_xdr.h> — referenced only for decode_opaque_fixed(), a static inline that remaps the XDR error return to -EIO for client call sites.
  • <linux/nfs.h> — the catch-all that also dragged UAPI NFS definitions into every consumer.

Lever's diagnosis is that the UUID decoder in localio was going through the client wrapper rather than the shared SUNRPC primitive. The fix is to call xdr_stream_decode_opaque_fixed() directly. That helper is shared by client and server, does the same bounds check, and is already reachable through <linux/sunrpc/clnt.h>. Once the wrapper is gone, localio references no symbol from <linux/nfs_xdr.h>, and once that header is gone, none of the NFSv3 definitions its structs embed are needed either.

The remaining types are then included directly: struct nfs_fh from <linux/nfs_fh.h> (not via nfslocalio.h's conditional re-export), NFS4_FHSIZE from <linux/nfs4.h>, and enum nfs_stat / nfs_stat_to_errno from the already-included <linux/nfs_common.h>.

The shared-header cleanup

The first two patches rearrange the LOCALIO program definitions so the shared header no longer smuggles client UAPI into every consumer.

Patch 1 moves the LOCALIO RPC program numbers out of include/linux/nfs.h into include/linux/nfslocalio.h. Lever's rationale is the same convention used by most other in-kernel RPC programs: those definitions are not needed by most files that include linux/nfs.h.

Patch 2 then replaces #include <linux/nfs.h> in linux/nfslocalio.h with #include <linux/nfs_fh.h>. The only reason the shared LOCALIO header pulled in linux/nfs.h was struct nfs_fh, which now lives in linux/nfs_fh.h. The practical effect for NFS client build hygiene is that nfslocalio.h "no longer carries uapi/linux/nfs.h into its consumers."

Together the two patches shrink include/linux/nfs.h and make nfslocalio.h a LOCALIO-specific header rather than a back-door into the client UAPI.

Neil Brown's review

Neil Brown replied only to patch 3. He agreed with the direction:

"Otherwise this all looks good and sensible."

His one objection is that pulling in <linux/nfs4.h> just for NFS4_FHSIZE reintroduces a version-specific header into a path that is supposed to be version-neutral:

"I think it would be better to not include nfs4.h because it doesn't seem particularly relevant to localio. Instead, replace NFS4_FHSIZE in localio.c with NFS_MAXFHSIZE which is defined in nfs_fh.h. I think that macro is a better fit for what is actually wanted."

That is a client-relevant point as well as a server one. LOCALIO filehandles are not NFSv4 filehandles; they are opaque handles whose maximum size is the generic NFS_MAXFHSIZE already defined next to struct nfs_fh. Using NFS4_FHSIZE would bake an NFSv4 constant into a shared local-I/O path that the NFS client also compiles against.

Status at week close

This v1 thread is superseded, not merged. Consensus in-window:

  • The series is a cleanup / xdrgen prerequisite, not a protocol change. Behavior is intended to be identical.
  • Brown's review is a soft ACK of patches 1–3 with one requested include change on patch 3.
  • Lever did not reply on this thread. The next day he posted v2 ([PATCH v2 0/5] Remove NFS client header dependencies from LOCALIO) whose changelog credits Brown: "Including <linux/nfs4.h> is also no longer needed (Neil Brown)." v2 also grows two extra NFSD patches around version-neutral filehandle sizing; those belong to the v2 thread.

For NFS client development this week: the shared LOCALIO header is being peeled off the client UAPI and off client-only XDR wrappers. That is the compile-time half of making LOCALIO a true common layer rather than "server code that happens to include client headers." The functional LOCALIO path is unchanged; the follow-up v2 series is where the remaining version-specific filehandle constants get named and dropped.
