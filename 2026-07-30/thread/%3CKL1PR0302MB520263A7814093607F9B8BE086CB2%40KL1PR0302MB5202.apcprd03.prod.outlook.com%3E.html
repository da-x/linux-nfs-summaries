Incomplete pNFS client posting on stale file size

Summary

NFSv4.2/pNFS client: applications seeing a stale file size

This is a client-side bug-fix attempt, not a protocol change and not a new feature. Quan Wang (Lenovo) opened the week with a one-off linux-nfs post titled “NFSv4.2/pNFS: fix applacation get old size of file” — a typo-ridden subject that still makes the complaint plain: an application on an NFSv4.2 pNFS mount can observe an old file size.

There were no replies in this thread. The list copy of the July 28 message is effectively an empty posting: no commit log, no reproducer, and no remaining patch text after ingest. As a piece of NFS client engineering it therefore landed as a placeholder rather than a reviewable fix.

What the author was trying to fix

The intended bug is in the Linux NFS client, specifically the pNFS layoutcommit path that publishes a new file size back to the metadata server. The next calendar day Wang re-sent the same subject as a standalone [PATCH] against fs/nfs/inode.c (follow-up posting), and that resend is the only place the technical claim is written down:

"it happened when call nfs_lookup_revalidate_dentry between pnfs_set_layoutcommit and nfs4_layoutcommit_release"

In other words, the race is:

  1. a pNFS write has already called pnfs_set_layoutcommit(), so the client knows the file grew (or otherwise changed size) but has not yet finished LAYOUTCOMMIT;
  2. a concurrent lookup/stat path runs nfs_lookup_revalidate_dentry() before nfs4_layoutcommit_release() installs the committed attributes;
  3. the revalidation path trusts the still-old size from GETATTR / the inode cache, and userspace therefore sees the pre-write length.

That is a classic NFS client attribute-cache hazard: layoutcommit is the pNFS mechanism that makes a data-server write visible in the MDS size, and a revalidate that wins the window in the middle will hand an application a stale st_size. The proposed change is tiny — three lines in fs/nfs/inode.c (2 insertions, 1 deletion) — which strongly suggests the author wants the inode size/invalidation logic to treat an outstanding layoutcommit as “size is not yet trustworthy,” rather than a protocol or layout-driver redesign.

Evolution and conclusion this week

Inside this thread there was no evolution: no Acked-by, no NACK, no alternative patch, and no maintainer comment on whether inode revalidation or the layoutcommit completion path is the right place to close the race. The July 28 mail did not even give reviewers a diff to argue about.

The practical conclusion for the week is therefore:

  • the report is a real-looking NFSv4.2/pNFS client size-consistency bug (applications reading an old size across the pnfs_set_layoutcommit → nfs4_layoutcommit_release window);
  • the July 28 thread itself is incomplete and unresolved;
  • the actionable artifact is the next-day [PATCH] to fs/nfs/inode.c, which still awaited review at the time of this summary.

Until that inode-cache change is reviewed, pNFS client users who stat() or re-open a file immediately after a parallel write remain exposed to the stale-size window Wang described.
