NFS client rejects oversized NFSv4 callback bitmaps

Summary

This week’s only traffic on the thread is a two-line NFS client bug fix from Jiancheng Huang, posted as [PATCH v2] NFS: reject oversized callback bitmap lengths. There is no prior in-archive history for this series in the current window, and as of the week ending 2026-07-30 nobody has reviewed, acked, or nacked the change. The discussion is a client-side bug fix / XDR hardening patch, not a protocol change or a new feature.

The bug: decode_bitmap() trusts a wrap-prone length

Huang targets decode_bitmap() in fs/nfs/callback_xdr.c, the NFSv4 callback decoder that walks attribute bitmaps on the client’s callback path. The function only keeps three bitmap words locally, but it currently shifts the server-supplied word count into a byte length before it checks that count. A huge attrlen can therefore wrap the value handed to xdr_inline_decode(), after which the decoder still performs its fixed-word reads against memory that is no longer inside the XDR carrier.

Huang’s cover letter states the failure mode directly:

"decode_bitmap() stores at most three bitmap words, but shifts the server-supplied word count before validating it. A large attrlen can wrap the byte count passed to xdr_inline_decode() and leave the fixed-word reads outside the XDR carrier."

That is a classic integer-wrap-then-decode pattern: the client treats an attacker-controlled (or merely malformed) callback bitmap length as a trusted size, converts it with a left shift, and only then tries to pull words out of the XDR stream. Once the shifted length wraps, the “inline” decode no longer bounds the subsequent 32-bit reads, which KASAN reports as a stack out-of-bounds access.

The Fixes: tag is 1da177e4c3f4 ("Linux-2.6.12-rc2"), i.e. the original Linux git epoch rather than a recent regression. In practical terms this is a long-standing callback XDR hygiene hole on the NFS client, not a newly introduced 6.x/7.x regression.

The proposed fix

The patch is deliberately small: two insertions in fs/nfs/callback_xdr.c. Huang’s stated policy is to fail closed on anything larger than the local three-word bitmap:

"Reject lengths larger than the local three-word representation before the shift and return NFS4ERR_INVAL for malformed callbacks."

That ordering is the whole point of the change. The length check must happen before the shift so a huge attrlen cannot wrap into a seemingly plausible byte count. Returning NFS4ERR_INVAL is the NFSv4 way of saying the callback is malformed rather than attempting to skip, truncate, or partially decode an oversized bitmap. Because the client only ever materializes three words, any larger advertised length is already useless even if it were well-formed on the wire.

v2 does not change the source. Huang notes:

"Changes in v2: Add the relevant public mailing lists to Cc; no source changes."

The v2 resend is therefore a distribution fix so linux-nfs and related lists actually see the patch, not a technical revision of the decoder logic.

The patch carries Assisted-by: Codex:gpt-5.6-luna, so reviewers will be looking at an AI-assisted two-liner against a very old decode path. That does not change the substance of the overflow, but it does mean the usual extra scrutiny around whether the check is in the right place, whether three words is still the right cap, and whether NFS4ERR_INVAL is the status the rest of the callback state machine expects.

Evidence: KUnit plus KASAN on v7.2-rc4

Huang attached a KUnit/KASAN oracle log from a bounded QEMU run on v7.2-rc4, sourced as confirmed/nfs_callback_bitmap_overflow_raw_excerpt.log. The subtest is nfs-callback-bitmap-overflow in the nfsv4 module. The first case, nfs_callback_bitmap_overflow_test, is marked ok; immediately afterward KASAN fires:

"BUG: KASAN: stack-out-of-bounds in decode_bitmap+0x1e6/0x240"

"Read of size 4 at addr ffff888002f47ab0 by task kunit_try_catch/69"

The call trace is the kunit catcher → kasan_report → decode_bitmap. That is consistent with the wrap story: after xdr_inline_decode() is given a wrapped length, the decoder still does a 4-byte (one bitmap word) read that lands off the end of the stack buffer KASAN is watching. The log is presented as reproduction of the unpatched decoder, not as a post-fix regression test in the excerpt itself.

For NFS client development this is the interesting part. Callback XDR is on the hot path for delegations, layouts, and other server-initiated NFSv4 operations; a stack OOB in decode_bitmap() is a client crash (or worse) triggered by a malformed callback, which can come from a buggy or malicious NFS server. Bounding the bitmap word count before any shift is the same class of defensive decode the list has been pushing on other XDR parsers: never let a wire length be used in arithmetic until it is known to fit the local representation.

Status this week

No maintainer or reviewer mail landed in-window. The thread therefore ends where it began: a v2 client patch that:

  • identifies a wrap in NFSv4 callback bitmap decoding;
  • rejects oversized lengths before the shift;
  • returns NFS4ERR_INVAL;
  • is backed by a KASAN stack-OOB report in decode_bitmap();
  • still awaits review, testing on real callback traffic, and a decision on whether the three-word cap and Fixes: tag are the right long-term story.

Until someone on linux-nfs comments, the technical conclusion is Huang’s: the client must not shift a server-supplied bitmap length that already exceeds the three words decode_bitmap() can store.
