VFS foreign-UID hooks v3, AFS sticky-dir fix, IMA follow-up

Summary

Summary

David Howells returned this week with PATCH v3 0/2, a bug-fix series plus a new VFS inode-op API aimed at Al Viro and Christian Brauner. The VFS still assumes it can compare inode->i_uid to another inode’s i_uid or to current_fsuid(). Network filesystems violate that in four ways at once: the IDs may live in a different number space, current_fsuid() may not be the subject of the RPC, the IDs may not be 32-bit, and some filesystems (CIFS without POSIX extensions) do not even have a UNIX integer UID.

The immediate casualty is the write-to-sticky check. open(O_CREAT) of an existing AFS file in a world-writable sticky directory fails when it should succeed — a failure that bash has papered over since 1992. That workaround is no longer hypothetical: Howells now writes that it “has now been removed as of bash-5.3,” so the kernel has to stop lying about ownership before userspace stops covering for it.

This is not an NFS protocol change. NFS is in the blast radius only as a VFS consumer: the sticky-dir, lease, chown and inode-owner helpers that every network filesystem walks through are being rerouted through filesystem-overridable comparisons. kAFS is still the only implementer; CIFS remains the named next candidate. Marc Dionne acked the AFS patch. Mimi Zohar answered Howells’ open IMA question. There is still no Ack or Review-by from VFS maintainers in-window.

Brief bridge from last week

v2 landed on 23 July (outside this window): same two patches, rebased on v7.2-rc4, plus the IOP_OWNERSHIP_OVERRIDE fast-path flag. Chet Ramey sent a signed MIME wrapper with no readable review. Howells’ only functional delta in v3 is:

"Fixed afs patch to provide ops for afs symlinks too."

The bash wording also hardened. Last week the workaround was “slated to be removed”; this week it is gone in bash-5.3. The series still lives on afs-sticky-2 in Howells’ linux-fs.git.

The VFS problem, restated for v3

In the cover letter Howells defines “foreign” IDs as ones that “do not belong in the same number space as the system's user IDs.” AFS is the running example: a public cell can be mounted by a client whose local UIDs collide with, or cannot even represent, the server’s 64-bit AuriStor YFS IDs. Worse, kAFS authenticates with a token in a key, so ownership of a file is a property of that token, not of current_fsuid():

"Further, kAFS uses a key containing an authentication token to specify the subject doing an RPC operation to the server - and, as such, this needs to be used instead of current_fsuid() in determining whether the current user has ownership rights over a file."

CIFS is called out for identifiers that are not integers at all. USB drives and cdroms get a mention as local filesystems that can also ship foreign IDs.

The user-visible bug is may_create_in_sticky(). Commit 30aba6656f61 (“namei: allow restricted O_CREAT of FIFOs and regular files”) refuses O_CREAT on an existing FIFO or regular file in a world-writable sticky directory unless the caller owns the file or the file’s owner matches the directory’s. Those comparisons are i_uid vs current_fsuid() / i_uid vs i_uid. On AFS they are meaningless, so a perfectly legal echo foo >>file in a sticky AFS directory fails with EACCES.

Bash has been hiding that since version 1.11 (January 1992). redir_open() retries open() without O_CREAT if the first attempt returned EACCES and bash was built with AFS workarounds. That fallback was written against an IBM AFS 3.1 cache-manager/server bug that preferred EACCES to EEXIST; every IBM-derived AFS server still does. As an unintended side effect it also punches a hole in the Linux sticky-dir protection. With bash-5.3 shipping without the fallback, the kernel path is now the only remaining fix.

Howells also flags that chown is still incomplete for any netfs whose IDs do not fit uid_t:

"Note that chown may also need modifying in some way - but that can't necessarily supply the information required (for instance, an AuriStor YFS ID is 64 bits, but chown can only handle a 32-bit integer; CIFS might use a GUID)."

Patch 1: inode ops so the filesystem owns the comparison

vfs: Allow filesystems with foreign owner IDs to override UID checks adds three helpers and two optional inode operations, gated by IOP_OWNERSHIP_OVERRIDE on i_opflags. Defaults preserve today’s i_uid comparisons, so local filesystems and NFS (which maps into the system ID space) keep current behaviour unless they opt in.

The three helpers:

  1. vfs_inode_is_owned_by_me() — default i_uid vs current_fsuid() with idmapping. Override:

    int (*is_owned_by_me)(struct mnt_idmap *idmap, struct inode *inode);

    Return 0 if owned, 1 if not, or an error on lookup failure. The filesystem may identify the subject by something other than fsuid (an AFS token, a CIFS SID, …).

  2. vfs_inodes_have_same_owner() — default i_uid vs i_uid. Override:

    int (*have_same_owner)(struct mnt_idmap *idmap, struct inode *inode1, struct inode *inode2);

  3. vfs_inode_and_dir_have_same_owner() — same as (2), but the second inode is the parent directory taken from a nameidata.

Call sites converted this round:

  • chown_ok() / chgrp_ok() — Howells flags that these may still need to defer all interpretation of the new UID/GID to the netfs. ->setattr() still gets a chance to reject.
  • coredump_file() — “the check that's there might be sufficient.”
  • inode_owner_or_capable() — namespace mapping “probably could be used.”
  • vfs_setlease() — “Actually, it should query if leasing is permitted.” AFS has a lock-permission ACL bit, but the server already checks it on the RPC, so Howells leaves a filesystem permission hook for later.
  • may_follow_link(), may_create_in_sticky(), __check_sticky(), may_dedupe_file().

Left alone, with rationale:

  • acl_permission_check() / posix_acl_permission() — only used by generic_permission(), which a filesystem with ->permission() already overrides. AFS evaluates its own ACLs in ->permission() and on the server.
  • IMA policy ops — still unchanged; Howells is “not sure what the best way to deal with this is.”

__check_sticky() remains the AFS-shaped special case. Calling vfs_inode_is_owned_by_me() on a directory does not work for kAFS (the ADMINISTER bit is not a directory-ownership signal), so the helper falls back to vfs_inodes_have_same_owner() against the parent, matching may_create_in_sticky(). Howells still asks, unanswered, whether may_create_in_sticky() should return OK immediately if the open that is in flight created the file being checked.

He is candid that wrapping the comparisons is not free: idmapping may run an extra time, “though this is only done in three places, all to do with world-writable sticky dir checks.” Documentation is updated in Documentation/filesystems/vfs.rst.

Patch 2: kAFS implements the hooks, including symlinks

afs, bash: Fix open(O_CREAT) on an extant AFS file in a sticky dir is the actual bug fix, tagged Fixes: 30aba6656f61. kAFS grows both inode ops in fs/afs/security.c (46 lines) and wires them from dir, file, inode — and, new in v3, from fs/afs/symlink.c. That last wiring is the only functional change versus last week’s v2: AFS symlink inodes now carry the same ownership ops as files and directories, so may_follow_link() can take the override path instead of comparing i_uid.

  • ->is_owned_by_me() does not compare i_uid to current_fsuid(). It looks at the access rights from FS.FetchStatus (and friends) and treats the file as owned if the server set the ADMINISTER bit for the current key. That check “doesn't work for directories, but none of the ops should require that.” Anonymous accesses never see ADMINISTER, so they are never treated as owning an anonymously-owned file.
  • ->have_same_owner() compares the 64-bit AFS owner IDs from FS.FetchStatus — IDs that will not fit in a kuid_t on AuriStor YFS. Anonymously-owned files match anonymously-owned parents, but an anonymously-owned directory cannot have the sticky bit set, so the sticky-dir path cannot be spoofed that way.

The test Howells wants: create a sticky AFS directory (token required), create a file in it, strace bash doing echo foo >>file. Success is a single open(O_CREAT) that returns 0; failure (today, without the bash fallback) is EACCES followed by a retry without O_CREAT.

Reported-by is Etienne Champetier; CCs include Marc Dionne and Jeffrey Altman (AuriStor), Cheyenne Wills, Steve French, Chet Ramey, Mimi Zohar, and the AFS/CIFS/fsdevel/integrity lists.

Reviews this week

Marc Dionne acked the AFS patch with no further commentary:

"Acked-by: Marc Dionne marc.dionne@auristor.com"

That is the first in-thread Ack of the series across v2 and v3, and it comes from AuriStor’s kAFS co-maintainer — useful for the filesystem-specific half, silent on the VFS API.

Mimi Zohar answered the IMA question that Howells left open in patch 1. IMA policy rules can be written against uid, euid and fowner. If those need to honour foreign owner IDs, the change belongs in ima_match_rules(), not in the VFS helpers Howells converted this round:

"IMA policy rules may be written in terms of the uid, euid and fowner. Any changes, if necessary, would need to be made to ima_match_rules()."

That is a pointer, not a request to block the series. Howells left IMA “unchanged for now”; Zohar confirmed the hook point if someone later decides IMA should see AFS/CIFS ownership rather than the mapped i_uid.

Al Viro, Christian Brauner and Steve French remain silent. The inode-op API is still waiting on VFS maintainer review.

What this means for the NFS client

NFS is not converted. The default helpers still do i_uid vs current_fsuid() with mount idmapping, which is the model NFSv3/v4 already use: the client maps server IDs into the local (or idmapped) namespace before they land in inode->i_uid. So the sticky-dir, lease and chown paths keep their current NFS behaviour unless someone later implements the ops.

That is also the limit of the claim. Howells’ four violated assumptions are AFS/CIFS-shaped. NFS does treat current_fsuid() as the subject (RPC credentials are derived from it, plus krb5/machine creds), and NFS IDs are 32-bit once mapped. The series still matters to NFS client developers for three reasons:

  1. Every open(O_CREAT) in a sticky directory, every inode_owner_or_capable(), every vfs_setlease() now goes through the new helpers. A regression in the default path is an NFS regression.
  2. CIFS is the named follow-on, and CIFS and NFS share VFS sticky/lease code. If CIFS later implements is_owned_by_me with a SID/GUID, the helper contract (0 = owned, 1 = not, negative = lookup error) becomes ABI for two network filesystems.
  3. chown remains unfixed for any netfs whose IDs do not fit uid_t. NFS idmapping already collapses that to 32 bits, so NFS is not blocked; AFS and CIFS still are.

The v3 symlink wiring does not change the NFS picture. NFS already has i_uid on symlink inodes; the new ops are opt-in.

Status this week

Bug-fix series posted to linux-nfs / linux-fsdevel / linux-cifs / linux-afs / linux-integrity. kAFS is the only filesystem implementing the new ops, now including symlinks. Marc Dionne acked the AFS half. Mimi Zohar mapped the IMA follow-up to ima_match_rules() without asking for a change in this series.
