NFSv4.2 listxattr size-query oops and lockup after LSM interface change

Summary

NFSv4.2 Client listxattr Regression: NULL Deref, Orphaned Spinlock, Soft Lockup

This week the long-quiet security_inode_listsecurity() interface cleanup returned as a critical NFS client bug fix. Chuck Lever reported that Stephen Smalley's LSM hook update, merged into lsm/dev in early May, wedges an NFSv4.2 client during fstests: a size-query listxattr(2) underflows an unsigned remaining-size accumulator, copies into a NULL buffer while the xattr listcache spinlock is held, and leaves the machine spinning in the shrinker until the watchdog fires.

Classification

This is a bug fix for a regression in the NFSv4.2 client's listxattr path, not a new feature or protocol change. The underlying interface cleanup (security_inode_listsecurity() / xattr_list_one()) shipped earlier; this week's traffic is about the severity of the fallout on a filesystem that caches xattrs behind a lock.

Prior context (brief)

In late April / early May, Paul Moore forward-ported Stephen Smalley's v2 patch so LSM hooks could use xattr_list_one(), adapting fs/nfs/nfs4proc.c along with the security and VFS sides. Moore merged it into lsm/dev after SELinux testsuite runs (local and NFS) came back clean. That work was treated as a routine interface cleanup. The client-side accounting that consumed the new hook was not hardened for the size-query case (listxattr(2) with a NULL buffer and length zero).

The report: fstests hang, then the machine is gone

On 25 July, Chuck Lever wrote that the commit "wedges an NFSv4.2 client running fstests." A kdevops run against nfsd-next hangs at generic/086; the client never recovers:

"watchdog: BUG: soft lockup - CPU#3 stuck for 250s! [086:60396]"

The lockup stack is in the NFSv4 xattr listcache shrinker:

__pv_queued_spin_lock_slowpath → _raw_spin_lock → nfs4_xattr_set_listcache → nfs4_xattr_discard_cache → nfs4_xattr_cache_scan → do_shrink_slab → drop_caches_sysctl_handler

The D taint, Lever noted, means something already died. By the time the watchdog fires the client has taken "two dozen NULL pointer dereferences, all of them in the same place":

RIP: _copy_from_pages+0x44/0xd0 [sunrpc] nfs4_xattr_cache_list [nfsv4] → nfs4_listxattr [nfsv4] → vfs_listxattr → __x64_sys_listxattr

Technical argument: unsigned wrap plus a lock held across the fault

Lever connected the two stages. nfs4_listxattr() keeps its remaining-size accumulator as an unsigned size_t. On a size query, xattr_list_one() still decrements that accumulator for the SELinux label even though the buffer is NULL, so the value wraps to a huge length. nfs4_xattr_cache_list() then sees a NULL buffer paired with a length that passes its own bounds check and copies into it.

The fault happens while the xattr listcache spinlock is held. Task exit does not drop spinlocks, so the lock is orphaned; the next shrinker pass (triggered here by drop_caches from generic/086) spins until the watchdog fires.

The reproducer does not need fstests machinery:

"The reproducer is a plain getfattr on a file on an NFSv4.2 mount with SELinux enforcing, which is what fstests generic/086 arrives at by way of a drop_caches write."

Lever reverted the LSM interface commit on nfsd-next and reran the full nfs_v42 fstests section on the same guests: 745 tests, no soft lockup, no oops, generic/086 passes. The two remaining failures (generic/033, generic/258) are unrelated to xattrs.

He was explicit that a revert is not the proposed fix. Achilles Gaikwad had already posted a targeted accounting patch (v2, 7 July) that declares left as ssize_t, measures security-hook consumption with a scratch copy, and only decrements remaining size when a buffer is present. Lever left the design choice to LSM and NFS maintainers:

"Whether the right answer is that patch, a change to xattr_list_one() so it leaves the remaining size alone when the buffer is NULL, or hardening nfs4_xattr_cache_list() against a NULL buffer, is for the three of you to settle."

The severity argument was the point of the mail:

"I am reporting the severity, because the accounting bug is not confined to a short size query: on a filesystem that caches xattrs behind a lock, it takes the whole machine down."

He offered to retest whatever they settle on against the same kdevops setup.

LSM response: take Gaikwad's NFS-only fix, but get an NFS ACK

Paul Moore replied the next day that he had already reviewed Gaikwad's patch in early July and it "looked okay" (he had tagged it Reviewed-by on 7 July). Because the fix only touches NFS code, he had assumed the NFS tree would pick it up:

"I had figured that the NFS folks would have wanted to pull that via the NFS tree since it only touches NFS code. If they would prefer I send it up to Linus via the LSM tree I can do that, but I would appreciate an ACK and Tested-by from someone on the NFS side."

He started a test kernel with Gaikwad's patch through the usual selinux-testsuite.

Later the same day, Moore reported that the suite was unsurprisingly uninteresting as a reproducer, but still clean:

"Not that I was expecting this to be a good test, but FWIW, the selinux-testsuite (and audit-testsuite for that matter) ran clean with Achilles's patch."

Conclusions this week

  • The May LSM interface cleanup is a confirmed NFSv4.2 client regression: size-query listxattr underflows, _copy_from_pages faults on a NULL buffer, and an orphaned listcache spinlock turns that into a machine-wide soft lockup under shrinker pressure.
  • Revert of the LSM commit restores fstests (generic/086 included) but is not the intended fix.
  • Consensus on the LSM side is to land Gaikwad's nfs4_listxattr accounting patch rather than change xattr_list_one() or only harden nfs4_xattr_cache_list().
  • Merge path is still open: NFS tree vs LSM tree. Moore is willing to send it via LSM if the NFS maintainers ACK and Tested-by it. Lever offered the kdevops fstests setup as the real validation; that Tested-by had not landed by the end of this week.

No client-side ACK, no merge, and no alternative (xattr_list_one() NULL-buffer change vs listcache hardening) was settled in-window. The outstanding ask from LSM is an NFS-side ACK plus a Tested-by on the same NFSv4.2 + SELinux + fstests configuration that exposed the lockup.
