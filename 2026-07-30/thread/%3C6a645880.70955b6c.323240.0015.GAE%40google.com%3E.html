syzbot: hung task in nfsd_nl_svc_export_set_reqs_doit — export-cache downcall waits on listener_set

Summary

syzbot: hung task in nfsd_nl_svc_export_set_reqs_doit — the export-cache downcall waits on listener_set

Classification

This is a bug report — a hung-task / control-plane DoS, not a protocol change and not a new feature. Google's syzbot filed a single unreproduced report against the NFS server generic-netlink family. The hung function, nfsd_nl_svc_export_set_reqs_doit in fs/nfsd/export.c, is the downcall that userspace (exportd/mountd) uses to populate the nfsd.export cache. That is the table NFSv2/v3 (and some v4) clients depend on for a path to become a published export.

No human has replied in this thread. The lock dump is nonetheless decisive, and it is the same class of failure Jeff Layton and Neil Brown diagnosed last week on the sibling nfsd_nl_cache_flush_doit hang — now landing on the original svc_export netlink path that the newer expkey (nfsd.fh) upcall was modeled after.

Brief bridge from last week

Last week syzbot hung cache flush, then expkey-set-reqs and expkey-get-reqs, all on the global nfsd_mutex. Layton's diagnosis was that synchronous rpcbind registration (including a ~60s rpc_ping) runs under that mutex, and netlink listener_set can batch many sockets in one call. Neil Brown asked why a local service is given a full minute, and sketched dropping the mutex across the listener batch. No patches were posted. This week's report is that same prediction coming true on the export-table downcall itself.

What landed this week

On Saturday, 25 July, syzbot reported a hung task on upstream HEAD 248951ddc14d (Merge tag 'hwmon-for-v7.2-rc5'):

"INFO: task syz.1.1268:11597 blocked for more than 143 seconds."

"Unfortunately, I don't have any reproducer for this issue yet."

The kernel is a PREEMPT(full) syzkaller build, tainted L (SOFTLOCKUP). The hung task is blocked in __mutex_lock → nfsd_nl_svc_export_set_reqs_doit+0x8a/0x2f0 at fs/nfsd/export.c:1057, having entered via genl_family_rcv_msg_doit / sendmsg. It already holds the generic-netlink cb_lock and is waiting for the global nfsd_mutex.

syzbot asked that any fix carry:

"Reported-by: syzbot+4fb3e2ffc13bcbb4e273@syzkaller.appspotmail.com"

The lock dump: listener_set holds the mutex the export downcall is waiting on

The interesting evidence is not the hung stack itself — it is the "Showing all locks held in the system" listing, which names the holder:

TaskHandlerRole
syz.4.1009nfsd_nl_listener_set_doit (nfsctl.c:1964)holds nfsd_mutex (plus cb_lock)
syz.1.1268 (the hung task)nfsd_nl_svc_export_set_reqs_doit (export.c:1057)waiting on nfsd_mutex (already holds cb_lock)

This is not a classic AB-BA deadlock. cb_lock is an rwsem, so both tasks can hold it as readers. The hung task is in D-state on the same coarse nfsd_mutex that listener_set is not releasing for more than 143 seconds. Every other nfsd netlink command — export-table updates, fh-cache upcalls, thread-count changes, cache flushes — queues behind that hold.

That pairing is the cleanest confirmation yet that last week's diagnosis applies to the original export netlink path, not only to the new expkey handlers. Last Wednesday's expkey-set-reqs dump already showed nfsd_nl_svc_export_set_reqs_doit as a holder of nfsd_mutex. This week's dump flips the roles: the export downcall is now the waiter, and listener_set is the long-hold site — the same holder Layton named on the cache-flush hang and that the expkey-get-reqs dump already confirmed.

The NMI backtrace is a red herring for the NFS path. CPU 0 was in pv_native_safe_halt (swapper/0); the SOFTLOCKUP taint and the USB hub workqueues in the lock list are incidental syzkaller noise. The nfsd story is entirely the listener_set / svc_export_set_reqs pile-up on nfsd_mutex.

A sibling report, filed two hours later the same morning, hangs in nfsd_nl_unlock_export_doit with the same holder (listener_set at nfsctl.c:1964). Together they say: both the export-table install path and the export unlock/revoke path are now documented victims of one slow listener_set.

Same root cause already diagnosed last week

Layton's diagnosis from the cache-flush thread applies here almost verbatim:

"The hard problem here is that rpcbind registration is done synchronously under the nfsd_mutex. To talk to rpcbind, the kernel has to create a RPC client, which does a RPC ping first. If rpcbind is down then it can take up to a minute for the RPC ping to time out."

And:

"If we couple those delays with a long list of listeners, then it's easy to see how to reproduce the hang."

This dump names nfsd_nl_listener_set_doit as the holder, so the mechanism does not need to be inferred. The new netlink listener_set handler can install many sockets in one call; each one may try to register with rpcbind while still holding nfsd_mutex. A down or unresponsive local rpcbind turns each registration into a ~60-second stall. Two such stalls is 143 seconds of hung-task watchdog — exactly what syzbot observed.

Brown's question from that thread is the design fork still open when this report arrived:

"Why are we waiting a whole minute for a local service to respond? If it hasn't responded in 1 second, is it ever really likely to?"

Layton's answer — a shorter timeout is necessary but not sufficient, because "even at 1s, you could easily cause a lockup warning with just a few hundred listeners" — is the reason this new report will not be fixed by touching nfsd_nl_svc_export_set_reqs_doit itself. The export handler is an innocent waiter. The bug is that any nfsd netlink op, including the long-standing export-table downcall, takes the same global mutex that listener setup holds across synchronous rpcbind I/O.

The open design options remain last week's three:

  1. shorten rpc_ping (Brown's first preference; Layton says necessary but insufficient);
  2. drop/reacquire nfsd_mutex around registration / the listener batch (Brown's sketch);
  3. async registration off a serialized queue or callback chain (Layton's preference), with care not to scramble rpcbind's table.

None of those patches have been posted to the list as of this window.

NFS client impact

This is a server-side hang, but it sits on a path NFS clients actually use:

  • Export-table downcalls. When an administrator publishes or revokes an export, userspace replies via svc_export-set-reqs. If that handler is stuck behind nfsd_mutex for minutes, newly published exports never become visible and revoked exports stay live. A client mount of a just-exported path simply does not complete; a client still holding a revoked export continues to see it.
  • File-handle cache is already a known victim. Last week's expkey-set-reqs / expkey-get-reqs reports hung both directions of the nfsd.fh upcall. A working mount needs the export table and the fh cache; either one being serialized behind listener_set is enough to stall. That is the same failure mode Paul Moore already hit as mount.nfs: Connection refused on a localhost mount after the expkey netlink conversion.
  • Listener / thread control. nfsd_nl_listener_set_doit is the holder. If bringing nfsd up or adding sockets stalls on rpcbind while holding the mutex, every other control-plane op — including the ones clients indirectly depend on for mount — stalls with it. New clients cannot connect until the lock is released.
  • NFSv2/v3 discovery. The underlying rpcbind-under-mutex problem is specifically a v2/v3 client-visibility issue: nfsd will serve without a successful registration, but clients that find the server via portmap see a missing or stale table. The 143-second export-downcall hang is the control-plane counterpart of that same rpcbind stall.

For NFSv4.2 clients the damage is more about control-plane latency than wire protocol: inter-server copy, state reclaim, and admin-driven export changes all assume the netlink family stays responsive. An export downcall that sits in D-state for more than two minutes is not responsive.

There is no NFS client code change in this thread and no client-side bug to fix. The client-visible symptom is a server that stops answering export-cache downcalls and, in the worst case, stops appearing in portmap while listener_set holds the lock.

Status

  • Type: hung-task / DoS bug in the nfsd netlink control plane, exposing the original svc_export downcall as another victim of nfsd_mutex.
  • Reproducer: none. syzbot is fuzzing concurrent netlink commands; the lock dump — listener_set holding, svc_export_set_reqs waiting — is the reproducer.
  • Human reply: none in this thread as of 30 July. The related cache-flush thread already has a design discussion but no patches posted and nothing applied.
  • Fix tag requested: Reported-by: syzbot+4fb3e2ffc13bcbb4e273@syzkaller.appspotmail.com.

Until the mutex is no longer held across rpcbind I/O — or until rpcbind I/O fails in well under a second — every nfsd netlink command, old or new, is another hung-task report waiting to happen. This week's svc_export_set_reqs report is that prediction coming true on the export table itself, three days after the diagnosis that already named listener_set as the long-hold site.
