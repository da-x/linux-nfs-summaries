syzbot: hung task in nfsd_nl_unlock_export_doit — admin export-revoke waits on listener_set

Classification

This is a bug report — a hung-task / control-plane DoS, not a protocol change and not a new feature. Google's syzbot filed a single unreproduced report against the NFS server generic-netlink family. The hung function, nfsd_nl_unlock_export_doit in fs/nfsd/nfsctl.c, is NFSD_CMD_UNLOCK_EXPORT: the administrator-driven path that walks the NFSv4 client hash tables to revoke open state and cancel in-flight async COPY for one export. That is the same family of unlock/revoke entry points Chuck Lever hardened in June against a startup NULL-deref; this week's report is a hang on the same command, not a crash.

No human has replied in this thread. The lock dump is nonetheless decisive, and it is the same class of failure Jeff Layton and Neil Brown diagnosed last week on the sibling nfsd_nl_cache_flush_doit hang. A report filed two hours earlier the same morning already hung the export-install downcall (nfsd_nl_svc_export_set_reqs_doit) behind listener_set. This dump documents the matching revoke path — and it is a pile-up, not a single waiter.

Brief bridge from last week

Last week syzbot hung cache flush, then expkey-set-reqs and expkey-get-reqs, all on the global nfsd_mutex. Layton's diagnosis was that synchronous rpcbind registration (including a ~60s rpc_ping) runs under that mutex, and netlink listener_set can batch many sockets in one call. Neil Brown asked why a local service is given a full minute, and sketched dropping the mutex across the listener batch. No patches were posted. This week's report is that same prediction coming true on the admin export-revoke command itself.

What landed this week

On Saturday, 25 July, two hours after the sibling export-install hang, syzbot reported a hung task on upstream HEAD c6859eed755d (Merge tag 's390-7.2-5'):

"INFO: task syz.4.992:9483 blocked for more than 143 seconds."

"Unfortunately, I don't have any reproducer for this issue yet."

The kernel is a PREEMPT(full) syzkaller build, tainted L (SOFTLOCKUP). The hung task is blocked in __mutex_lock → nfsd_nl_unlock_export_doit+0x376/0x570 at fs/nfsd/nfsctl.c:2392, having entered via genl_family_rcv_msg_doit / sendmsg. It already holds the generic-netlink cb_lock and is waiting for the global nfsd_mutex.

syzbot asked that any fix carry:

"Reported-by: syzbot+406e5b77ff9375770297@syzkaller.appspotmail.com"

The lock dump: a pile-up, not a single waiter

The interesting evidence is not the hung stack itself — it is the "Showing all locks held in the system" listing, which names four tasks on nfsd_mutex at once:

TaskHandlerRole
syz.2.979nfsd_nl_listener_set_doit (nfsctl.c:1964)holds nfsd_mutex (plus cb_lock)
syz.4.992 (the hung task)nfsd_nl_unlock_export_doit (nfsctl.c:2392)waiting on nfsd_mutex (already holds cb_lock)
syz.0.1263nfsd_shutdown_threads (nfssvc.c:576)waiting on nfsd_mutex while already holding s_umount from deactivate_super
syz.6.1570nfsd_nl_rpc_status_get_dumpit (nfsctl.c:1510)waiting on nfsd_mutex (holds cb_lock and nlk_cb_mutex-GENERIC)

This is not a classic AB-BA deadlock. cb_lock is an rwsem, so the netlink tasks can hold it as readers. The hung task is in D-state on the same coarse nfsd_mutex that listener_set is not releasing for more than 143 seconds. Every other nfsd netlink command — export-table updates, fh-cache upcalls, thread-count changes, cache flushes, and admin unlock/revoke — queues behind that hold.

What is new relative to the sibling export-install hang two hours earlier is the breadth of the pile-up. That dump showed one waiter (svc_export_set_reqs) behind listener_set. This dump shows three:

  1. Admin export-revoke (nfsd_nl_unlock_export_doit) — the command that tears down NFSv4 opens, locks, delegations, and async COPY for one export.
  2. Server teardown from umount (nfsd_shutdown_threads via deactivate_super) — a filesystem going away is itself stuck on the same mutex, and it already holds exclusive s_umount.
  3. RPC-status dump (nfsd_nl_rpc_status_get_dumpit) — even a read-only netlink dumpit cannot proceed.

The umount waiter is the extra wrinkle. syz.0.1263 holds &type->s_umount_key taken in deactivate_super and then blocks in nfsd_shutdown_threads on nfsd_mutex. That is not proven as an AB-BA deadlock in this dump — listener_set is not shown taking s_umount — but it is a lock-order hazard waiting to happen: any nfsd path that holds nfsd_mutex and then needs a superblock lock will deadlock against a umount that already took s_umount and is now waiting for nfsd_mutex. Even without that deadlock, a filesystem umount that sits in D-state for more than two minutes is a client-visible outage of its own.

The NMI backtrace is a red herring for the NFS path. CPU 1 was in KFENCE's toggle_allocation_gate workqueue; the SOFTLOCKUP taint and the Bluetooth hci_dev_do_close / RCU expedited-mutex entries in the lock list are incidental syzkaller noise. The nfsd story is entirely the listener_set pile-up on nfsd_mutex.

Together with the sibling report the same morning, the two dumps say: both the export-table install path and the export unlock/revoke path are now documented victims of one slow listener_set — and the revoke hang also stalls umount and status dumps.

Same root cause already diagnosed last week

Layton's diagnosis from the cache-flush thread applies here almost verbatim:

"The hard problem here is that rpcbind registration is done synchronously under the nfsd_mutex. To talk to rpcbind, the kernel has to create a RPC client, which does a RPC ping first. If rpcbind is down then it can take up to a minute for the RPC ping to time out."

And:

"If we couple those delays with a long list of listeners, then it's easy to see how to reproduce the hang."

This dump names nfsd_nl_listener_set_doit as the holder, so the mechanism does not need to be inferred. The new netlink listener_set handler can install many sockets in one call; each one may try to register with rpcbind while still holding nfsd_mutex. A down or unresponsive local rpcbind turns each registration into a ~60-second stall. Two such stalls is 143 seconds of hung-task watchdog — exactly what syzbot observed.

Brown's question from that thread is the design fork still open when this report arrived:

"Why are we waiting a whole minute for a local service to respond? If it hasn't responded in 1 second, is it ever really likely to?"

Layton's answer — a shorter timeout is necessary but not sufficient, because "even at 1s, you could easily cause a lockup warning with just a few hundred listeners" — is the reason this new report will not be fixed by touching nfsd_nl_unlock_export_doit itself. The unlock handler is an innocent waiter. The bug is that any nfsd netlink op, including the admin-revocation command that NFSv4 clients depend on for timely state teardown, takes the same global mutex that listener setup holds across synchronous rpcbind I/O.

The open design options remain last week's three:

  1. shorten rpc_ping (Brown's first preference; Layton says necessary but insufficient);
  2. drop/reacquire nfsd_mutex around registration / the listener batch (Brown's sketch);
  3. async registration off a serialized queue or callback chain (Layton's preference), with care not to scramble rpcbind's table.

None of those patches have been posted to the list as of this window.

Same function, different bug: June's NULL-deref vs. this hang

nfsd_nl_unlock_export_doit was already in the news in June, for a different failure. Chuck Lever's NFSD_NET_UP guard closed a startup-window NULL-deref: the three unlock entry points (write_unlock_fs, nfsd_nl_unlock_filesystem_doit, nfsd_nl_unlock_export_doit) used to walk the NFSv4 client hash tables as soon as nn->nfsd_serv was non-NULL, which listener_set can make true before nfs4_state_start_net() allocates nn->conf_id_hashtbl. Lever's description of that earlier bug is worth repeating, because it is the same command under a different failure mode:

"Writing to /proc/fs/nfsd/unlock_filesystem, or sending the NFSD_CMD_UNLOCK_FILESYSTEM or NFSD_CMD_UNLOCK_EXPORT netlink command, walks the NFSv4 client hash tables to revoke open state and cancel async COPY operations."

June's patch stopped that walk from running before the tables exist. This week's hang is the walk (or the mutex acquire that precedes it) never running at all, because listener_set will not drop nfsd_mutex. A CAP_SYS_ADMIN local crash has been replaced, under syzkaller load, by a CAP_SYS_ADMIN local stall of every nfsd control-plane op — including the umount path that is supposed to take the server down cleanly.

NFS client impact

There is no NFS client code change in this thread and no client-side bug to fix. The client-visible damage is on the server paths that NFSv4 clients actually depend on for state teardown and for the server staying reachable:

  • Admin export-revoke. NFSD_CMD_UNLOCK_EXPORT is how an administrator tears down one export's NFSv4 opens, locks, delegations, and layouts without taking the whole server down. If that handler sits in D-state for minutes behind nfsd_mutex, revoked state stays live: a client continues to hold opens it should have lost, a delegated write is not recalled, and an in-flight inter-server COPY is not cancelled. That is the exact client-facing contract of the "umount kills NFSv4 state" work that landed earlier this year.
  • Filesystem umount itself is a waiter. This dump shows deactivate_super → nfsd_shutdown_threads blocked on the same mutex while already holding s_umount. A server-side umount that cannot finish is a client-visible outage: the export is neither fully up nor fully gone, nfsd threads cannot be stopped, and any subsequent listener_set / thread-count change queues behind it.
  • Export-table install is already a known victim. The sibling report two hours earlier hung nfsd_nl_svc_export_set_reqs_doit. A working mount needs the export table and a responsive unlock/revoke path; either one being serialized behind listener_set is enough to stall. A client mount of a just-exported path does not complete; a client still holding a revoked export continues to see it.
  • File-handle cache is already a known victim. Last week's expkey-set-reqs / expkey-get-reqs reports hung both directions of the nfsd.fh upcall. Combined with this week's unlock hang, the entire export lifecycle — install, lookup, revoke — is now documented as blocked by one slow listener_set.
  • NFSv2/v3 discovery. The underlying rpcbind-under-mutex problem is specifically a v2/v3 client-visibility issue: nfsd will serve without a successful registration, but clients that find the server via portmap see a missing or stale table. Brown put it cleanly last week: "nfsd doesn't need the registration, only clients do."
  • Observability. Even nfsd_nl_rpc_status_get_dumpit is in the waiter list. An operator who tries to dump RPC status to diagnose the hang cannot, because the dump takes the same mutex.

For NFSv4.2 clients the damage is about control-plane latency and stale state, not a wire-protocol change: inter-server copy, state reclaim, delegations, and admin-driven export changes all assume the netlink family stays responsive. An unlock-export that sits in D-state for more than two minutes is not responsive, and an umount stuck in nfsd_shutdown_threads is worse.

Status

  • Type: hung-task / DoS bug in the nfsd netlink control plane, exposing NFSD_CMD_UNLOCK_EXPORT (and, in the same dump, nfsd_shutdown_threads and rpc_status_get_dumpit) as further victims of nfsd_mutex.
  • Reproducer: none. syzbot is fuzzing concurrent netlink commands; the lock dump — listener_set holding, unlock-export / shutdown-threads / rpc-status-dump waiting — is the reproducer.
  • Human reply: none in this thread as of 30 July. The related cache-flush thread already has a design discussion but no patches posted and nothing applied.
  • Related earlier fix, different bug: June's NFSD_NET_UP guard closed a NULL-deref on this same unlock path; it does not address the hang.
  • Fix tag requested: Reported-by: syzbot+406e5b77ff9375770297@syzkaller.appspotmail.com.

Until the mutex is no longer held across rpcbind I/O — or until rpcbind I/O fails in well under a second — every nfsd netlink command, old or new, is another hung-task report waiting to happen. This week's unlock_export report is that prediction coming true on the admin-revocation path NFSv4 clients use for timely state teardown, three days after the diagnosis that already named listener_set as the long-hold site, and two hours after the same holder stalled the export-table downcall.
