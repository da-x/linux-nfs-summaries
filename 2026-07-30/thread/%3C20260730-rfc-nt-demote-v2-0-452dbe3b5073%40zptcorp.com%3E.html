RFC v2 NT demotion: reviewers want reason, not a new async mode

Summary

Summary

This is a new feature RFC for the memory-management demotion path — not an NFS protocol change and not a client bug fix. Two months after the May RFC, Yiannis Nikolakopoulos (with Alirad Malek, ZPT Corp) posted v2 of "[PATCH RFC v2 0/3] Demote to lower tier using non-temporal stores." The pitch is unchanged: demoted pages are already cold, so a plain memcpy pollutes the local last-level cache and can hurt CXL expanders that do in-line compression.

"Using non-temporal stores instead of a standard memcpy path can reduce the cache pollution in the local node and the bandwidth overhead to the target node."

A CXL microbenchmark that allocates 64 GB locally and then triggers memory.reclaim still claims the headline result: write traffic stays at N GB, while device read traffic drops from N to almost zero.

Brief recap of v1

v1 gated the new MIGRATE_ASYNC_NON_TEMPORAL_STORES path behind a Kconfig option. Gregory Price asked whether that opt-in was necessary. Earlier this week, on the v1 thread, Nikolakopoulos conceded the flag was just caution and promised to drop it. That is the only design change that actually landed in v2.

What v2 actually ships

  • Patch 1/3 adds _nt helpers from folio_mc_copy down to copy_mc_to_kernel, using x86 memcpy_flushcache (non-temporal stores).
  • Patch 2/3 introduces MIGRATE_ASYNC_NON_TEMPORAL_STORES and a helper that treats both async modes as async, replacing raw MIGRATE_ASYNC checks — including the one-line swap in fs/nfs/write.c.
  • Patch 3/3 uses the new mode on the demotion path only. The Kconfig is gone; NT stores are always used for demotion on x86_64.

The cover letter still lists two opens: duplication of machine-check handling in copy_mc_to_kernel_nt (Huan Nguyen is said to have ideas for v3), and no aarch64 story because ARM memcpy_flushcache does not use NT stores.

Reviewers reject the extra migrate mode

Hours after the series landed, Gregory Price asked the question that now dominates the thread: why is NT an explicit option at all?

"I'm still a bit confused why using NT Stores needs to be an explicit option - rather than the default behavior if NT Store is available."

"Lets assume we did this for all ASYNC requests, is there a negative effect? A positive effect? Why the new ASYNC type? Is there a correctness issue?"

Frank van der Linden said the separate mode was probably just "don't break anything else," then argued for always using NT on ASYNC. He noted that arm64 already uses NT-hinted stores by default, and that NT can be a slight hit only when the destination is used immediately. He suggested folding mode and reason so the copy path can decide:

"Maybe the mode and reason should be folded in to one variable, so that, further down the stack, a decision can be made as to what type of copy to use?"

He also floated skipping NT when folio_test_waiters(folio) is true, then immediately called that "overthinking it."

Johannes Weiner supplied the concrete counter-example against "NT for all ASYNC":

"do_numa_page() -> migrate_misplaced_folio() is such a case. It happens literally in the access path to that data. MIGRATE_ASYNC just means don't block, fail fast, because waiting for an IO-bound lock to avoid a remote NUMA access would be a bad idea."

Compaction, by contrast, uses MIGRATE_SYNC* and walks PFNs out of execution order — a better NT candidate. Weiner's conclusion:

"Agree. reason seems like a much stronger signal."

Price closed the loop:

"I think this ends up cleaner as well, it would be a nice improvement."

No one in-window reviewed the _nt helpers or the machine-check duplication. The authors have not yet replied to the mode-versus-reason critique.

NFS client angle

NFS is still only an incidental consumer. Patch 2/3 rewrites the MIGRATE_ASYNC test in fs/nfs/write.c to the new "either async mode" helper so NFS writeback keeps treating NT-async migrations as non-blocking. There is no NFS-specific bug fix, no writeback behavior change, and no protocol work. If v3 follows the reviewers and keys NT off MR_DEMOTION (or similar) instead of a new migrate mode, that one-line NFS helper change may shrink or disappear.

Bottom line

v2 delivered the promised Kconfig removal and still funnels NT stores through a new async migrate mode used only for demotion. Reviewers from Price, van der Linden, and Weiner have already moved the design target: pick the copy strategy from migrate reason (and whether the folio is about to be used), not from a second ASYNC flag. Machine-check vs. NT priority and aarch64 remain open. Until a v3 lands, the only NFS client footprint is that mechanical helper swap in fs/nfs/write.c.
