NT demotion RFC drops Kconfig opt-in after two-month pause

Summary

Summary

Two months after the RFC series landed, the thread woke up with a single follow-up that closes the only design question raised on-list. This remains a new feature for the memory-management demotion path — not a protocol change and not a bug fix. NFS is still only an incidental consumer: the series refactors async-migration checks, including a one-line helper swap in fs/nfs/write.c.

Brief recap of May

Yiannis Nikolakopoulos (with Alirad Malek, ZPT Corp) posted a three-patch RFC, "[PATCH RFC 0/3] Demote to lower tier using non-temporal stores](https://lore.kernel.org/linux-nfs/20260526-rfc-nt-demote-v1-0-eb9c9422daef@zptcorp.com/)", arguing that demoted pages are already cold, so a plain memcpy pollutes the local last-level cache and can hurt CXL expanders that do in-line compression. Patch 3/3 gated the new MIGRATE_ASYNC_NON_TEMPORAL_STORES path behind a Kconfig option. Gregory Price immediately asked whether that opt-in was necessary at all:

"Do we actually need this config flag or should we just default to this (if the arch supports NT stores)?"

That was the last word until this week.

This week's reply: the flag is gone

On 30 July, Nikolakopoulos answered Price on the patch-3/3 thread. The Kconfig was, he said, just caution, not a hardware requirement:

"As discussed in the sync call, I was just being defensive :). In fact the non-temporal instructions should be in all x86_64 afaict. So I've removed this in the next version (landing soon)."

The "sync call" is not on the list, so the public record now is: NT stores are treated as universal on x86_64, demotion will use them by default when the architecture supports them, and a v2 is promised imminently. No other reviewer weighed in this week, and none of the other RFC "Opens" (machine-check duplication in the _nt copy helpers, aarch64 enablement) were revisited.

NFS client angle

Nothing in this week's mail touches NFS code or writeback behavior. The client still only sees the series through the migrate-mode helper introduced in RFC 2/3: raw MIGRATE_ASYNC checks, including the one in fs/nfs/write.c, become a helper that also matches the new NT-async mode. If v2 keeps that refactor, NFS writeback will ride the same async-migration path as everyone else; there is no NFS-specific bug fix or protocol change on the table.

Bottom line

The discussion is still an early new feature RFC for CXL/tiered-memory demotion. This week's only movement is a design concession: drop the Kconfig opt-in and default to non-temporal stores on x86_64. The next version has been announced but has not yet appeared on the list. Until it does, the NFS-relevant helper change and the remaining machine-check / multi-arch questions remain open.
