NFS Weekly Summaries

  1. Summaries

NFSv4.2 client lockup, silent futimens, and pNFS stale size dominate a week of hardening

Week ending 2026-07-30

The Linux NFS list spent the week of 24–30 July on client correctness, not on new wire protocol. The loudest item is a confirmed NFSv4.2 listxattr oops that takes the machine down. Around it sit an unfixed futimens() SETATTR skip, an unreviewed pNFS size-coherence race, a callback XDR overflow, and v4 of Mike Snitzer’s uncacheable-attribute series — which is itself two client bitmap bug fixes wrapped in a feature. Netdev, meanwhile, rejected the kTLS read_sock API the NFS client was going to grow onto.

Server-side traffic was real (an nfsd procfs GPF landed in nfsd-testing; syzbot hung two more netlink commands behind listener_set) but secondary to the client picture.

Critical: NFSv4.2 listxattr size-query oops and lockup

Chuck Lever reported that Stephen Smalley’s merged security_inode_listsecurity() cleanup wedges an NFSv4.2 client in fstests. A size-query listxattr(2) (NULL buffer, length zero) underflows an unsigned remaining-size accumulator in nfs4_listxattr(). nfs4_xattr_cache_list() then copies into that NULL buffer while the xattr listcache spinlock is held. Task exit does not drop spinlocks, so the next shrinker pass — generic/086 writing drop_caches is enough — spins until the watchdog fires.

The stack is unambiguous: two dozen _copy_from_pages NULL derefs, then nfs4_xattr_cache_scan stuck on the orphaned lock. The reproducer is a plain getfattr on an NFSv4.2 mount with SELinux enforcing. Lever reverted the LSM commit on nfsd-next and reran nfs_v42: 745 tests, no lockup, generic/086 passes.

A revert is not the proposed fix. Achilles Gaikwad already posted a targeted accounting patch (left as ssize_t, only decrement when a buffer is present). Paul Moore has Reviewed-by on that patch and will send it via the LSM tree if NFS maintainers ACK and Tested-by it. That ACK had not landed by week close. Until it does, any NFSv4.2 + SELinux client built against lsm/dev can panic on a size-query listxattr.

Client bugs still open

futimens() still lies on NFSv4.2. Michael Yang tightened last week’s report: GNU touch -d on an open fd returns success, dirties the local inode, and never sends SETATTR. The server inode is unchanged; the next revalidation snaps the timestamps back. New this week: the failure is already in 6.17.x (Proxmox bug 7621), absent on 6.12.88 LTS, and absent on vers=4.1. Pathname-based utimensat on v4.2 still works. The 7.0 timestamp-split commits are no longer the first-pass suspects; the bisection window is 6.13–6.17 on the v4.2 open-file setattr path. No maintainer reply, no patch.

pNFS applications can still see a stale size. Lenovo’s Quan Wang first posted an empty same-subject note, then a three-line fs/nfs/inode.c patch. The race is classic pNFS: after pnfs_set_layoutcommit() the client already knows the new last-write-byte, but nfs_lookup_revalidate_dentry() can still refresh i_size from the MDS before nfs4_layoutcommit_release(). A concurrent stat() therefore reports the pre-write length. The hunk belongs in the generic inode path, not a layout driver — the right layer, if the guard does not paper over a real MDS truncate. The posting has no Fixes:, no reproducer, and no review.

Callback bitmap wrap. Jiancheng Huang’s v2 is two lines in decode_bitmap() (fs/nfs/callback_xdr.c): reject a server-supplied word count larger than the local three-word bitmap before shifting it into a byte length, and return NFS4ERR_INVAL. A huge attrlen currently wraps the value handed to xdr_inline_decode(), after which the fixed-word reads walk off the XDR carrier. KASAN on v7.2-rc4 reports a stack OOB in decode_bitmap. Fixes: is the git epoch; this is long-standing callback hygiene, not a 7.x regression. No review in-window.

Client features: uncacheable attributes, still no reviews

Mike Snitzer posted v4 of NFSv4.2 client support for UNCACHEABLE_FILE_DATA (FATTR4 87) and UNCACHEABLE_DIRENT_METADATA (FATTR4 88). The motivating deployments mix NFSv4.2, NFSv3, and SMB on one namespace, so data and dirents change faster than a typical cache lifetime.

v4’s real news is two request-bitmap holes that would have broken ordinary traffic against any server advertising the new attributes:

  • v3 put directory-only attr 88 on the shared OPEN bitmaps, so every regular-file OPEN got NFS4ERR_INVAL.
  • v3 had directory DELEGRETURN request file-only attr 87 the same way.

v4 type-gates both: regular files request 87 only, directories request 88 only. Honoring the bits is then straightforward — marked files open O_DIRECT (no Section 4.3 read-cache relaxation under a delegation), marked directories bypass the readdir page cache and force READDIRPLUS so per-entry size/mtime stay fresh. No Acked-by landed.

On the shared LOCALIO boundary, Chuck Lever’s v1 then v2 peel NFS client headers out of server-side LOCALIO ahead of xdrgen. nfslocalio.h no longer smuggles uapi/linux/nfs.h or the client-only decode_opaque_fixed() wrapper into client builds, and LOCALIO opens stop impersonating NFSv4 just because the copy buffer was NFS4_FHSIZE. Neil Brown and Mike Snitzer Reviewed-by the whole v2 series. Behavior is intended identical, with one favorable efficiency win: LOCALIO no longer forces filesystems to compute birth-time and change-cookie attributes nobody reads.

Debate: kTLS control records will not look like TCP

The series that was going to give NFSD — and later the NFS client xprtsock path — first-class kTLS Alert/KeyUpdate delivery on read_sock is not a merge candidate. Jakub Kicinski rejected Chuck Lever’s read_sock_rectype proto_ops hook as a TLS-only one-off that does not belong in struct proto_ops. An AI-written cover paragraph soured the review; Sabrina Dubroca’s procedural note is the useful one: this should have been RFC v2, with numbers comparing current sock_recvmsg, read_sock plus CMSG fallback, and whatever replaces the new hook.

The NFS-relevant bug the series is trying to fix is still real. A recvmsg with CMSG and pages dumps Alert/KeyUpdate bytes into those pages — and for in-kernel consumers the I/O buffers are page-cache pages. Mixing control payload into rq_pages (NFSD) or client receive pages (xprtsock) is why svcsock still runs a MSG_CTRUNC recovery dance, and why a kTLS-enabled NFS client still has no first-class control-record path.

By Friday night Dubroca had gone further than a shape NACK. On the patch-2 thread she agreed with Kicinski’s stream-socket philosophy and doubted the kernel should paper over TLS record types to keep TCP-oriented consumers happy. No replacement API was agreed. The one piece still moving is independent: the no-data bound for empty TLS 1.3 records, already split to a net prerequisite, which stops a client from pinning tls_sw_read_sock() with a stream of empty records.

Until that redesign exists, the planned client xprtsock conversion cannot land.

Userspace and the rest of the list

Steve Dickson announced nfs-utils 2.9.2 — memory-leak fixes, netlink and exportfs work, a new nfs-iostat option — and restored the missing git tag after Mike Owen noticed. xuchenchen posted an unreviewed rpc.statd leak: on SM_MON re-monitor with a new priv cookie, sm_mon_1_svc() overwrites clnt->dns_name without freeing the old string. Ian Bridges pinged his still-unreviewed strlcat() → snprintf() cleanup in rpc_sockaddr2uaddr().

On the server, Ameer Hamza’s procfs GPF — client_info_show() walking cl_sessions under cl_lock while free_client() tears the list down unlocked — was applied to nfsd-testing two days later. syzbot then hung both nfsd_nl_svc_export_set_reqs_doit and nfsd_nl_unlock_export_doit behind nfsd_nl_listener_set_doit holding nfsd_mutex across synchronous rpcbind registration. That is last week’s diagnosis coming true on the export-install and export-revoke paths clients actually depend on; still no patch.

David Howells posted VFS foreign-UID hooks v3 so kAFS can fix sticky-dir open(O_CREAT) now that bash-5.3 dropped its 1992 workaround. NFS is not converted: the default helpers still compare i_uid, which is the model the NFS client already uses. A regression in those defaults would still be an NFS regression. Marc Dionne acked the AFS half; VFS maintainers have not.

Incidental mm/include traffic touched NFS only mechanically: Brendan Jackman dropped the controversial mempolicy-internal header (sunrpc keeps the public folio_alloc_node() rename); an NT-store demotion RFC v2 still carries a one-line fs/nfs/write.c helper swap that reviewers may delete if NT is keyed off migrate reason instead of a new ASYNC mode; Thomas Gleixner acked the jiffies sysctl include in Petr Pavlu’s kmod.h cleanup (the NFS hunk is last week’s cache_lib.c umh.h swap).

What to watch

  1. Land Gaikwad’s nfs4_listxattr accounting patch — or an equivalent — with an NFS Tested-by on the same SELinux + fstests setup Lever used. This is the week’s only confirmed machine-down client regression.
  2. Bisect futimens() on NFSv4.2 between 6.12.88 and 6.17. The failure mode is now sharp enough to find.
  3. Rewrite the pNFS size patch with a named helper, a truncate-safe condition, and a Fixes: line.
  4. Review Huang’s callback-bitmap check before a malformed CB_GETATTR/CB_RECALL walks off the stack.
  5. Snitzer v4 type-gating needs eyes; advertising attrs 87/88 without it breaks OPEN and directory DELEGRETURN.
  6. kTLS control records need an RFC, measurements, and a design netdev will accept. The client xprtsock conversion is blocked until then.

The client tree this week is a pile of real bugs and one well-reviewed LOCALIO cleanup. The feature work is waiting on review; the crashers should not.
