Build Error: lockd xdr.h Move Breaks nfs_lock_check_bounds() on ARM

Summary

Build Error Reported Against lockd Header Refactoring (Patch 11/14)

Overview

This thread captures a build error report from the kernel test robot against PATCH v4 11/14, part of Chuck Lever's ongoing lockd API boundary cleanup series. The report is classified as a bug fix / build regression, not a new feature or protocol change.

Context from Prior Weeks

This patch series (v4, 14 patches) aims to clarify the lockd module's API boundaries by moving internal headers from include/linux/lockd/ to fs/lockd/, reducing the public API surface to just bind.h. As Chuck Lever explained in the cover letter:

"The lockd subsystem currently exposes internal implementation headers through include/linux/lockd/, creating implicit API contracts that complicate maintenance."

Prior iterations (v1, v2, and v3) revealed several build issues across architectures including alpha, hexagon, parisc, and s390. Version 4 was intended to address those by adding forward declarations for struct nfs_fh and struct file_lock to bind.h, and ensuring fs/nfs/nfs3proc.c explicitly includes filelock.h.

This Week's Activity

The kernel test robot reported a new build failure on the ARM architecture using the arm-randconfig-r112-20260129 configuration:

"kernel test robot noticed the following build errors" — kernel test robot

The error manifests in fs/nfs/proc.c within the function nfs_lock_check_bounds(), where access to members of const struct file_lock fails because the full type definition is no longer available:

>> fs/nfs/proc.c:677:26: error: invalid use of undefined type 'const struct file_lock'
     677 |         start = (__s32)fl->fl_start;
   fs/nfs/proc.c:678:32: error: invalid use of undefined type 'const struct file_lock'
     678 |         if ((loff_t)start != fl->fl_start)
   fs/nfs/proc.c:681:15: error: invalid use of undefined type 'const struct file_lock'
     681 |         if (fl->fl_end != OFFSET_MAX) {

The root cause is that moving xdr.h from include/linux/lockd/ to fs/lockd/ breaks a transitive include chain. The function nfs_lock_check_bounds() in fs/nfs/proc.c directly accesses fl->fl_start, fl->fl_end, and compares against OFFSET_MAX — all of which require the full definition of struct file_lock. While v4 added forward declarations to bind.h, a forward declaration is insufficient when code dereferences structure members; the full type definition from filelock.h must be included.

Significance for NFS Client Development

This build error highlights a layering issue in the NFS client that was not caught during earlier review cycles:

  • The function nfs_lock_check_bounds() performs bounds checking on lock requests, ensuring offsets fit within 32-bit NLM protocol limits (NFS_LOCK32_OFFSET_MAX).
  • The refactoring inadvertently exposed a hidden dependency: fs/nfs/proc.c relied on transitive inclusion of filelock.h through the now-relocated xdr.h.
  • This is distinct from the fix in PATCH v4 11/14 for fs/nfs/nfs3proc.c, which needed filelock.h only for the FL_CLOSE constant (a forward declaration sufficed there). In contrast, fs/nfs/proc.c needs the full struct definition.

Status and Next Steps

As of this week's window close, no response from Chuck Lever has been posted to address this new build error. The kernel test robot noted:

"If you fix the issue in a separate patch/commit (i.e. not just a new version of the same patch/commit), kindly add following tags"

A v5 iteration or an out-of-band fix will likely be needed, adding an explicit #include <linux/filelock.h> to fs/nfs/proc.c to resolve the undefined type errors. This underscores the iterative nature of header refactoring work in the NFS subsystem — each move exposes previously hidden dependencies that must be made explicit.
