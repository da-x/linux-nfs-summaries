bio_vec RDMA API v5: Final Version Accepted — All Five Patches Applied to RDMA Tree

bio_vec RDMA API v5: Final Version Accepted and Applied to RDMA Tree

Summary

Type: New feature / API addition with an important bug fix (Send Queue sizing)

Overview

Chuck Lever submitted version 5 of his five-patch series introducing a bio_vec-based RDMA read/write API to the Linux kernel's RDMA core subsystem, and — in a remarkably swift review cycle — received clean Reviewed-by tags from Christoph Hellwig on all patches within hours, followed by immediate acceptance into the RDMA tree by maintainer Leon Romanovsky.

As Chuck explained in the cover letter [id://20260128005400.25147-1-cel@kernel.org]:

"This series introduces a bio_vec based API for RDMA read and write operations in the RDMA core, eliminating unnecessary scatterlist conversions for callers that already work with bvecs."

The single change from v4 to v5 resolved the last outstanding architectural concern:

"Changes since v4: Move the synthetic SGL into struct rdma_rw_reg_ctx" Chuck Lever

Context from Prior Weeks

This series has evolved through five iterations over several weeks:

  • v1–v2: Initial submission with basic bvec API support, IOVA coalescing, and synthetic scatterlist for MR mapping.
  • v3 (prior summary): Received thorough review from Christoph Hellwig, Zhu Yanjun, and Jason Gunthorpe. Key feedback included iterator consumption conventions, MR code duplication concerns, and a clean Reviewed-by for the SQ sizing bug fix.
  • v4 (prior summary): Addressed iterator conventions and refactored common per-MR handling into a helper. Hellwig granted Reviewed-by on patches 1/5, 2/5, and 4/5 but reiterated his concern about the placement of the synthetic scatter table (sgt) outside struct rdma_rw_reg_ctx:

"I still don't understand why the sgt is not in struct rdma_rw_reg_ctx. Right now that is allocate a little bit later than the sgt initialization and freed a tiny bit to early, but that seems to be easy to fix." Christoph Hellwig

"Doing so would reduce the memory usage for the common non-registration path, and significantly reduce the churn in the patch." Christoph Hellwig

Key Technical Arguments

Patch 1/5: bio_vec RDMA API — Clean Reviewed-by Retained

PATCH v5 1/5 introduces rdma_rw_ctx_init_bvec() and rdma_rw_ctx_destroy_bvec(), accepting bio_vec arrays directly without intermediate scatterlist conversion. The patch carries Christoph Hellwig's Reviewed-by tag from the v3 cycle, with no new objections raised.

Patch 2/5: IOVA-based DMA Mapping — Reviewed-by Retained

PATCH v5 2/5 implements the two-step IOVA API (dma_iova_try_alloc / dma_iova_link / dma_iova_sync) to reduce IOTLB synchronization from O(n) per-page flushes to a single O(1) sync after all mappings complete. This also requires only a single output dma_addr_t compared to extra per-element storage in struct scatterlist.

Christoph Hellwig confirmed:

"Looks good: Reviewed-by: Christoph Hellwig hch@lst.de" [id://20260128033624.GA30926@lst.de]

Patch 3/5: MR Support — Final Blocker Resolved

PATCH v5 3/5 adds rdma_rw_init_mr_wrs_bvec() for Memory Registration support on bvec arrays, enabling iWARP devices and the force_mr debug parameter to use the bvec path. The key v5 change moved the synthetic scatter table into struct rdma_rw_reg_ctx, directly addressing Hellwig's persistent concern about memory overhead for the common non-MR path.

Hellwig's response was immediate and unqualified:

"Looks good: Reviewed-by: Christoph Hellwig hch@lst.de" [id://20260128033624.GA30926@lst.de]

Patch 4/5: SQ Sizing Bug Fix — Critical Correctness Fix

PATCH v5 4/5 introduces rdma_rw_max_sge() to correctly compute Send Queue entry requirements when memory registration is active. This fixes a critical bug where the Send CQ and credit pool were undersized relative to the QP's actual capacity:

"when the device uses memory registration for RDMA operations, rdma_rw_init_qp() inflates the QP's max_send_wr by a factor of three per context to account for REG and INV work requests. The Send CQ and credit pool remain sized for only one work request per context, causing Send Queue exhaustion under heavy NFS WRITE workloads." Chuck Lever

This patch carries Hellwig's Reviewed-by tag and includes a Fixes: tag pointing to commit 00bd1439f464.

Patch 5/5: svcrdma Conversion — Clean Reviewed-by

PATCH v5 5/5 converts the NFS server-side RDMA transport (svcrdma) to use the new bvec API, eliminating scatterlist conversion overhead and simplifying svc_rdma_rw_ctxt by removing chained SG table management:

"The bvec-based RDMA API eliminates the intermediate scatterlist conversion step, allowing direct DMA mapping from bio_vec arrays. This simplifies the svc_rdma_rw_ctxt structure by removing the chained SG table management." Chuck Lever

Hellwig confirmed:

"Looks good: Reviewed-by: Christoph Hellwig hch@lst.de" [id://20260128033646.GB30926@lst.de]

Acceptance into the RDMA Tree

Leon Romanovsky, the RDMA subsystem maintainer, applied all five patches to the rdma/rdma tree on January 28:

"Applied, thanks!" Leon Romanovsky

All five patches were assigned commit hashes in the rdma/rdma repository, confirming successful integration.

Broader Architectural Vision

Jason Gunthorpe endorsed the kernel-wide scatterlist elimination goal during the v3 review cycle:

"I haven't imagined tree wide, but I am envisioning a world where a modern server runs all its primary IO paths without using scatterlist." Jason Gunthorpe

This series represents a concrete step toward that vision, establishing bio_vec as the preferred data structure for RDMA I/O in the kernel.

Significance for NFS Client Development

While this series primarily targets the NFS server side (svcrdma), it has important implications for NFS client development:

  1. Send Queue sizing bug fix (patch 4/5): Prevents Send Queue exhaustion on NFS servers under heavy WRITE workloads with memory registration enabled — a correctness issue that directly affects client-side reliability when using iWARP or force_mr. Clients connecting to affected servers would experience stalled writes or connection resets.

  2. Scalability improvements: Eliminating scatterlist conversions reduces CPU overhead and IOTLB synchronization costs on the server side, benefiting large compound NFS operations from the client's perspective through improved tail latency. As Lever noted during v3 review:

"The changes are designed to improve scalability (eg lower CPU utilization for the same workload and less interaction between host and RNIC) more than improve raw throughput." Chuck Lever

  1. API direction: The kernel-wide push toward bio_vec over scatterlists may eventually influence NFS client RDMA code paths (pnfs/blocklayout) as those subsystems evolve to use the new API.

Final Status

All five patches have been applied to the rdma/rdma tree by Leon Romanovsky, with commit hashes confirmed. The series carries Christoph Hellwig's Reviewed-by on all patches and is expected to flow into the mainline kernel through the standard RDMA subsystem merge path.
