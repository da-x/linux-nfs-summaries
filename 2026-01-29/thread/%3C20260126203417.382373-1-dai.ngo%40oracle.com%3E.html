NFSD Layout Recall Timeout and Lease Manager Fencing: v3/v4 Reviewed, Critical Data-Safety Concerns Raised

Summary

NFSD Layout Recall Timeout and Lease Manager Fencing (v3/v4)

Summary

Type: New feature / bug fix — enforcement of timeout on NFSv4 pNFS layout recall, with integration of SCSI Persistent Reservation (PR) fencing into the lease manager framework.

This week saw the submission of version 3 (PATCH v3 1/1) and version 4 (PATCH v4 1/1) of Dai Ngo's patch to enforce timeouts on layout recall operations in the NFSD (NFS server) subsystem, and to integrate lease manager fencing for block layout clients. The patch touches both the core VFS locking layer (fs/locks.c) and NFSD-specific code (fs/nfsd/nfs4layouts.c, fs/nfsd/blocklayout.c).

Problem Statement

When a layout conflict triggers a recall, nfsd threads can become blocked indefinitely in __break_lease(), preventing the server from servicing incoming requests. The patch introduces a timeout mechanism and integrates SCSI PR fencing to ensure that when a layout holder fails to return its layout, the server can fence the client from accessing the underlying block device.

Key Technical Changes

The patch introduces a new callback in lease_manager_operations:

"lm_breaker_timedout: Invoked when a lease recall times out and is about to be disposed of. This function enables the lease manager to inform the caller whether the file_lease should remain on the flc_list or be disposed of." Dai Ngo

For NFSD, this callback triggers SCSI PR fencing when a layout recall times out and the layout type supports fencing. The fencing is performed asynchronously via a system workqueue to avoid blocking under spinlocks.

Version Evolution (v2 → v3 → v4)

v2 changes included updating the subject line, allowing conflicting leases to remain on flc_list until fencing completes, using a system worker for asynchronous fencing, and using nfs4_stid.sc_count reference counting to ensure layout stateid validity during fencing.

v3 changes (the thread root):

  • Corrected locking requirements in locking.rst documentation
  • Added maximum retry count to the fencing operation (LO_MAX_FENCE_RETRY = 5)
  • Fixed a missing nfs4_put_stid call in nfsd4_layout_fence_worker
  • Removed special-casing of FL_LAYOUT in lease_modify
  • Removed lease_want_dispose
  • Moved the lm_breaker_timedout call to time_out_leases

v4 changes:

"only increment ls_fence_retry_cnt after successfully schedule new work in nfsd4_layout_lm_breaker_timedout." Dai Ngo

Discussion: Critical Review from Chuck Lever and Jeff Layton

Error Handling and Retry Semantics

Chuck Lever raised a significant concern about error classification in nfsd4_scsi_fence_client():

"The removed code distinguishes retryable errors (such as path failures) from permanent errors (PR_STS_IOERR, PR_STS_RESERVATION_CONFLICT), but the new code clears the fence on any error, potentially causing infinite retry loops as warned in the removed comment." Chuck Lever

Dai Ngo explained that he had previously preserved this distinction but was asked to remove it in earlier review:

"In v2 and v3 patch, I left the comment and the code distinguishes retryable errors intact. And you commented this: 'In nfsd4_scsi_fence_client(), when a device error occurs (e.g., PR_STS_IOERR), ls->ls_fenced is set even though the client may still have storage access.' So I'm not sure how to treat permanent errors now." Dai Ngo

Chuck clarified:

"The comment is important and explains some of the subtleties. I think that needs to be preserved even if we decide to set ls_fenced in every error case." Chuck Lever

The Fundamental Timeout Dilemma

The most profound discussion centered on the inherent risk of timeout-based fencing. Chuck Lever articulated the core concern:

"If I'm reading this correctly, when the fence fails after all 5 retries, the client retains block device access but server believes recall succeeded?" Chuck Lever

Dai confirmed:

"You're right, the server and client can be left in opposite states if we still can not fence the client after so many retries." Dai Ngo

Chuck drew a parallel to NFS mount options:

"This is the bane of every timeout-based scheme I know about, and why we have the 'hard' mount option." Chuck Lever

Dai proposed a conservative approach:

"I propose pr_warn the admin and retry forever for now until we can find a better option. I expect this to be a very rare condition so it should not effect most environments." Dai Ngo

Chuck acknowledged the difficulty:

"A warning doesn't seem like it would prevent data corruption. (I'm not against a warning, in and of itself... it just does not seem to me to be sufficient). I would really like this mechanism to be more data-safe." Chuck Lever

Reference Counting and Locking Concerns

Chuck identified a race in the retry counter increment:

"Incrementing after the mod_delayed_work() call is racy. Instead: refcount_inc(&ls->ls_stid.sc_count); ret = mod_delayed_work(system_dfl_wq, &ls->ls_fence_work, 0); if (ret) { refcount_dec(&ls->ls_stid.sc_count); ... }" Chuck Lever

Dai explained the constraint:

"Yes, it's racy, I thought about this. But we can not just do a refcount_dec here, we need to do nfs4_put_stid. But we can not do nfs4_put_stid here since nfsd4_layout_lm_breaker_timedout runs under the spin_lock flc_lock and nfs4_put_stid might causes the flc_lock to be acquired again from generic_delete_lease if this is the last reference count on stid." Dai Ngo

Jeff Layton questioned the safety of Chuck's proposed fix:

"Is that safe? That's done in nfsd_break_one_deleg() for similar reasons, but there is a comment over that function explaining why it's OK. We'll need to validate that the lease is always released before the sc_count goes to 0 here too." Jeff Layton

Dai conceded:

"No, it's not safe. I have to think of other ways to make sure the layout statid is valid when the fence worker runs." Dai Ngo

Architectural Simplification from Jeff Layton

Jeff proposed a simpler design for the fencing flow:

"I don't understand what this new mutex is protecting, and this all seems overly complex. It feels kind of like you want nfsd to be driving the fencing retries, but I don't think we really do." Jeff Layton

He suggested making ->fence_client return a bool/int indicating success, and having the workqueue job handle retries:

"I'd just make ->fence_client a bool or int return, and have it indicate whether the client was successfully fenced or not. If it wasn't successfully fenced, have the caller (the workqueue job) requeue itself if you want to retry." Jeff Layton

Dai agreed to this approach:

"Ok, I will try this approach: have the fence worker doing the retry instead of nfsd so that the fence worker is only scheduled once to do the fencing." Dai Ngo

Jeff also clarified the lm_breaker_timedout API design:

"Make it void return and have it call lease_modify itself before returning in the cases where you have it returning true. If the operation isn't defined then just do the lease_modify here like we always have." Jeff Layton

He further explained that lm_breaker_timedout (or the workqueue job it spawns) should be responsible for calling lease_modify() at the appropriate time:

"In most cases you're going to need to queue a workqueue job to fence, and you don't want to clear out the lease until after it's done." Jeff Layton

Administrative Warnings

Both reviewers emphasized that fencing failures must be visible to administrators:

"The cases where the fencing didn't work after too many retries, or the job couldn't be queued should probably get a pr_warn or something. The admin needs to know that data corruption is possible and that they might need to nuke the client manually." Jeff Layton

Final Conclusions and Open Issues

As of the end of this week, no consensus has been reached on several critical design questions:

  1. Retry strategy: Whether to use a bounded retry count (with risk of data corruption if fencing fails) or unbounded retries (with risk of blocking other clients indefinitely). Dai leaned toward "retry forever with pr_warn" as the safest option.

  2. Reference counting under spinlock: The interaction between flc_lock and nfs4_put_stid() remains unresolved. Dai acknowledged the need to find a different approach to ensure layout stateid validity during fencing.

  3. Error classification: Whether to distinguish between retryable and permanent SCSI PR errors, and how to handle cases where the server and client disagree on reservation state.

  4. Architecture simplification: Jeff's suggestion to move retry logic into the fence worker (rather than having NFSD drive retries) was accepted in principle but not yet implemented.

Chuck Lever closed with a candid note:

"Just remember, I'm thinking about this and learning as I go along, just like you are. I know I'm possibly contradicting myself here." Chuck Lever

Dai responded:

"I'm greatly appreciated your and Jeff's comments. We're working on the same goal to build a reliable NFS server." Dai Ngo

The patch series will continue to evolve in subsequent versions, with v5 expected to address the architectural simplifications and locking concerns raised this week.
