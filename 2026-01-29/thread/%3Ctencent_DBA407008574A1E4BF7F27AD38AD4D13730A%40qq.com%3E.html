sunrpc/xs_read_stream: Dead-loop fix for xs_read_discard NACKed by Trond Myklebust

Summary

sunrpc/xs_read_stream: Fix Dead Loop When xs_read_discard — NACKed

Classification: Bug Fix (Rejected)

This week saw a bug-fix patch submission targeting the SunRPC transport layer in the NFS client, specifically addressing a potential infinite loop in xs_read_stream() when the discard path (xs_read_discard) is taken. The patch was promptly rejected by NFS maintainer Trond Myklebust with a clear technical explanation of why the proposed fix would introduce worse problems.

The Proposed Fix

jack.zhou submitted a patch titled "[PATCH] sunrpc/xs_read_stream: fix dead loop when xs_read_discard" on January 26, describing a scenario where the NFS client using TCP mode could enter an infinite loop during RPC reply processing.

The author outlined the normal operation flow:

  1. xs_read_stream() runs within a for-loop in xs_stream_data_receive(), exiting only when its return value is < 0.
  2. When transport->recv.len == 0, xs_read_stream_header() is called, which determines whether to execute RPC_CALL or RPC_REPLY and sets transport->recv.len.
  3. In the RPC_REPLY path, the return value comes from tcp_recvmsg(), indicating copied skb data size (> 0).
  4. On normal completion, transport->recv.offset and transport->recv.len are reset to 0, and the positive read value is returned — allowing the loop to continue (not exit).

The abnormal scenario described by the author:

  1. Due to a corrupted skb, transport->recv.calldir parses an incorrect value, triggering MSG_TRUNC and setting transport->recv.len.
  2. The condition if (transport->recv.offset < transport->recv.len) is entered.
  3. xs_read_discard() returns > 0, so the upstream for-loop does not exit.
  4. On re-entry to xs_read_stream(), since transport->recv.len != 0, xs_read_stream_header() is not called — meaning transport->recv.calldir can never be correctly reset.
  5. All subsequent RPC replies are forced into the xs_read_discard path indefinitely, creating an infinite loop because transport->recv.len is never reset to 0.

The proposed fix was to reset transport->recv.len to 0 after reaching xs_read_discard, mirroring the normal return path. The author noted: "The modification has been tested and passed in version 5.10.160."

Maintainer Rejection

Trond Myklebust responded on the same day with a firm NACK, explaining why the fix was fundamentally flawed:

"If we're in the xs_read_discard() case, then that's because we're out of receive buffer space, and so we've given up reading the remainder of the message into that receive buffer. However we still have to read to the end of that message before we get to the next message in the TCP stream."

Myklebust emphasized that the discard path is intentionally designed to drain the remainder of a malformed or oversized message from the TCP stream — even if it cannot be fully buffered. Resetting transport->recv.len prematurely would break this protocol discipline:

"With this change, then as soon as there is no more buffered data to read from the socket and it returns EAGAIN, you will reset the message parameters. The result is that the next call to xs_read_stream() will just leave us reading random data from the middle of the message as if it were a new message header."

In other words, the proposed fix would cause the NFS client to misinterpret partial TCP stream data as new RPC message headers, leading to complete protocol desynchronization — arguably a far more severe bug than the original infinite loop.

Myklebust also noted that the existing code already handles connection breakage gracefully: "The only thing that can prevent that is if someone breaks the connection, and in that case the client already takes care of resetting the message state as part of reconnecting."

Final Status

Rejected. The patch was NACKed by Trond Myklebust. No further discussion occurred this week. The underlying concern about infinite loops in xs_read_discard remains unaddressed, but the maintainer's analysis suggests that any fix must preserve the invariant that the full message is consumed from the TCP stream before state is reset — a constraint the original patch violated.
