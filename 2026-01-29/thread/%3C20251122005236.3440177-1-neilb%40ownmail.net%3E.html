NFSD Foreign File Handle Handling in COPY: Series Stalled, Chuck Offers to Take Over

Summary

NFSD Foreign File Handle Handling in COPY: Patch Series Stalled, Chuck Offers to Take Over

Classification

Type: NFS server (NFSD) cleanup / protocol compliance improvement — specifically an enhancement to how the NFSv4.2 inter-server COPY operation handles foreign file handles during PUTFH. Not a regression fix, security patch, or new feature, but rather a correctness and robustness improvement for cross-implementation NFS interoperability.

Overview

This thread concerns NeilBrown's 14-patch series (PATCH v7 00/14) titled "nfsd: assorted cleanups involving v4 special stateids," originally posted in November 2025. The discussion this week focuses specifically on patch 04/14 — "allow unrecognisable filehandle for foreign servers in COPY" — which addresses how NFSD handles file handles from foreign NFS servers during inter-server COPY operations (an NFSv4.2 feature).

After a technical debate spanning November 2025, Chuck Lever followed up on January 23, 2026, to inquire about the status of the series and offered to complete it himself.

Background: The Foreign File Handle Problem in COPY

The NFSv4.2 inter-server COPY operation allows a client to request that data be copied directly between two NFS servers without traversing the client. When the source file handle belongs to a foreign server (i.e., one not running the same NFSD implementation), the receiving server may not be able to verify or interpret that file handle using its own internal mechanisms.

RFC 7862 (NFSv4.2) acknowledges this scenario in section 15.2.3, noting that a foreign file handle might result in NFS4ERR_STALE when presented via PUTFH, and provides guidance on ignoring this error when the PUTFH precedes a COPY operation. However, as NeilBrown observed, the RFC does not explicitly address NFS4ERR_BADHANDLE, which can also occur when the foreign server uses a different NFS implementation with incompatible file handle formats.

NeilBrown's patch extends NFSD's existing logic — which already delays STALE errors in this context — to also delay BADHANDLE errors when PUTFH precedes a COPY operation. This allows the server to forward the foreign file handle to the destination server rather than rejecting the COMPOUND prematurely.

Evolution of the Discussion

Initial Review (November 22, 2025)

Chuck Lever provided early feedback on patch 04/14 in his first review, noting:

"These are plausible claims. But IMO, they need firmer rationale."

He suggested consulting the IETF NFS Working Group and potentially filing an RFC errata or documenting the observation in an implementation experience document he was co-authoring with Olga Kornievskaia. He also raised the possibility of NFS4ERR_MOVED as another error that might warrant similar treatment.

Deeper Analysis (November 23, 2025)

In a follow-up message, Chuck clarified his position:

"I agree that PUTFH handling NFS4ERR_BADHANDLE is a concern when there is a subsequent COPY operation in the COMPOUND."

He articulated the spirit of RFC 7862 more precisely:

"The spirit of RFC 7862 is that PUTFH mustn't fail if a client presents a foreign file handle via a PUTFH that precedes a COPY operation. The lack of BCP14 language specific to other status codes shouldn't stop NFSD from handling other status codes as it needs to."

Chuck raised several important architectural questions:

  • Should PUTFH check for specific status codes from fh_verify() before looking ahead in the COMPOUND, or should it look ahead on any failure?
  • Is this patch a fix requiring backport to LTS kernels?
  • He noted that NFSD's PUTFH implementation unconditionally invokes fh_verify, which is an artifact causing this complexity.

He also mused:

"It seems like NFSv4.2 could have added a PUT_FOREIGN_FH operation to avoid all this nonsense."

And highlighted a performance benefit:

"Now that our MAX_OPS_PER_COMPOUND has increased and might increase again, moving the COPY look ahead checking out of nfsd4_proc_compound is a huge bonus for handling large COMPOUNDs."

NeilBrown's Response (November 27, 2025)

NeilBrown replied with RFC 8881 analysis, noting that the error code description for NFS4ERR_BADHANDLE states:

"Illegal NFS filehandle for the current server. The current filehandle failed internal consistency checks. Once accepted as valid (by PUTFH), no subsequent status change can cause the filehandle to generate this error."

He concluded:

"So I think we are in agreement that the RFC isn't crystal clear but doesn't put any barriers in the way of us making this change."

On the question of which errors should trigger look-ahead, NeilBrown noted that fh_verify() can also generate nfserr_nofilehandle, nfserr_jukebox, and nfserr_perm, with nfserr_perm potentially warranting similar treatment to nfserr_stale.

Regarding backporting:

"It doesn't fix a regression, a security hole, and data corruption, a kernel panic. So I don't think it needs to be backported."

He explained the failure mode:

"I think the failure mode is that the client would fallback to handling the copy like it would for v4.1."

Status Check (January 23, 2026 — This Week)

After a two-month gap in the discussion, Chuck Lever followed up:

"I continue to be interested in improving NFSD's handling of foreign file handles (and it might be complicated by the addition of file handle signing). Do you have plans to revise this series, or would you like me to take it across the finish line?"

This message is the sole activity in this thread during the current week.

Key Technical Arguments

  1. RFC Compliance vs. Implementation Reality: While RFC 7862 explicitly addresses NFS4ERR_STALE for foreign file handles in COPY, it omits NFS4ERR_BADHANDLE. Both NeilBrown and Chuck Lever agreed that the RFC's spirit supports handling both errors similarly, even if the letter of the RFC is incomplete.

  2. PUTFH Architecture: The root cause of the complexity lies in NFSD's PUTFH implementation unconditionally invoking fh_verify(). The debate centered on whether PUTFH should look ahead for COPY on specific error codes or on any fh_verify() failure.

  3. Backport Considerations: NeilBrown determined this is not a critical fix requiring LTS backport, as the failure mode results in graceful fallback to client-mediated copy (NFSv4.1 behavior).

  4. Future Complications: Chuck Lever noted that upcoming file handle signing features may further complicate foreign file handle handling, adding urgency to resolving these issues.

Final Conclusions

  • No resolution reached this week. The thread ended with Chuck Lever's offer to take over the series if NeilBrown does not plan to revise it.
  • The patch remains unmerged. As of this week, NeilBrown has not responded to Chuck's follow-up.
  • Technical consensus exists on the approach, but questions remain about scope (which error codes to handle) and whether additional RFC errata or WG consultation is warranted.

Relevance to NFS Client Development

While this thread primarily concerns NFSD (server-side) implementation, it has implications for NFS client developers:

  1. Interoperability: Improved handling of foreign file handles in COPY means NFS clients can rely on inter-server copy working more reliably across heterogeneous server implementations.
  2. Fallback behavior: Without this fix, clients fall back to NFSv4.1-style client-mediated copy when encountering BADHANDLE errors — a functional but less efficient path.
  3. File handle signing: Chuck Lever's mention of upcoming file handle signing suggests future protocol changes that may affect both client and server implementations.
