Case Folding v6: Merge Window Targeting — v7.1 Confirmed, Follow-up Revision Planned

Summary

Case Folding v6: Merge Window Targeting and Follow-up Plans

Type: New feature / protocol enhancement (continued from prior weeks)

Prior Week Recap

Chuck Lever's 16-patch series "Exposing case folding behavior" was posted as version 6 on January 20th, completing the conversion to FS_XFLAG-based case sensitivity flags and adding error handling for NFSv4 GETATTR. Two open items were identified: a UAPI flag collision with Andrey's fsverity xflag patch (noted by Darrick J. Wong) and an initialization bug in ioctl_getflags() flagged by Jan Kara, where relocated struct zeroing could clear the flags_valid hint before the filesystem callback reads it. See last week's summary for full details on the v6 series, including NFS client fileattr_get support for re-export scenarios and NFSD enhancements for dynamic case sensitivity reporting via NFSv3 PATHCONF and NFSv4 FATTR4 attributes.

This Week's Activity: Merge Window Coordination

This week's discussion (January 23–25) focused exclusively on merge window targeting and process coordination between the series author Chuck Lever and VFS maintainer Christian Brauner, with input from Cedric Blancher representing downstream distribution interests.

Key Technical Arguments

1. Merge Window Timing Decision

Christian Brauner opened the discussion on January 23rd by addressing the series' base kernel (v6.19-rc5) and expressing concern about timing:

"We're starting to cut it close even with the announced -rc8. So my current preference would be to wait for the 7.1 merge window." Christian Brauner

This response establishes that the VFS maintainer prefers to defer the series to the next kernel cycle (v7.1) rather than attempt a late inclusion in v6.19, which is already deep into its release candidate phase with an announced -rc8 milestone.

2. Downstream Distribution Pressure

Cedric Blancher from Institut Pasteur pushed back against the deferral, citing real-world distribution needs:

"My preference would be to move forward with 6.19 as a target, as there are requests to have this in some distros using 6.x LTS kernels (Bosch for example)." Cedric Blancher

This highlights the tension between kernel development process discipline and downstream distribution requirements. Bosch's interest in having case folding support available in 6.x LTS kernels underscores the practical importance of this feature for enterprise deployments where long-term stability is paramount.

3. Merge Window Etiquette

Chuck Lever raised a procedural question about whether to continue posting revisions during the merge window, noting that some subsystems prefer quiet periods:

"Do you have a preference about continuing to post this series during the merge window? I ask because netdev generally likes a quiet period during the merge window." Chuck Lever

This reflects awareness of different subsystem cultures within the kernel community regarding merge window activity.

4. Resolution: Series Already Queued in VFS Tree

Christian Brauner provided a pragmatic resolution, revealing that he had already incorporated the series into his development tree:

"It's usually most helpful if people resend after -rc1 is out because then I can just pull it without having to worry about merge conflicts. But fwiw, I have you series in vfs-7.1.casefolding already. Let me push it out so you can see it." Christian Brauner

This is significant: the series is already staged in Brauner's vfs-7.1.casefolding branch, confirming the v7.1 target and providing a stable reference for further development.

5. Planned Follow-up Revision

Chuck Lever concluded the thread by outlining his plans for version 7:

"There will be at least one more revision of this series (and it can happen in a few weeks) to split 1/16 as Darrick requested, and address the nit that Jan noted." Chuck Lever

Two concrete items are identified for v7:

  • Split patch 1/16 as requested by Darrick J. Wong (likely to separate the UAPI flag definition from the core VFS changes, easing the linux-api review process and addressing the fsverity collision concern).
  • Address Jan Kara's initialization bug in ioctl_getflags(), where the relocated struct zeroing could inadvertently clear the flags_valid hint before the filesystem's ->fileattr_get() callback reads it.

NFS Client Development Significance

While this week's discussion was primarily about process coordination rather than technical content, the implications for NFS client development remain substantial:

  1. Target kernel clarified: The case folding feature will land in v7.1, giving NFS client developers a clear timeline for integration planning. The fileattr_get implementation in the NFS client (patch 10/16 from last week) enables re-export scenarios where an NFS server accurately reports the case sensitivity of underlying NFS mounts to its clients.

  2. No code changes this week: No patches were posted or reviewed during this period; all activity was meta-discussion about merge timing and follow-up plans.

  3. Downstream relevance confirmed: Cedric Blancher's mention of Bosch's interest in 6.x LTS kernels underscores the real-world demand for case folding support, particularly for environments where Windows/macOS NFS clients require accurate FATTR4_CASE_INSENSITIVE reporting from Linux servers.

Final Conclusions

The discussion reached a clear consensus:

  • Target kernel: v7.1 merge window (not v6.19)
  • Series status: Already queued in Christian Brauner's vfs-7.1.casefolding branch
  • Next revision: v7 will be posted "in a few weeks" after -rc1, addressing Darrick J. Wong's request to split patch 1/16 and Jan Kara's initialization bug report
  • Process outcome: No further action needed during the current merge window; Lever will resend the revised series after v7.0-rc1 is released

The case folding series remains on a strong trajectory toward eventual merge, with broad support from filesystem maintainers established across six prior versions and two remaining review items clearly identified for resolution.
