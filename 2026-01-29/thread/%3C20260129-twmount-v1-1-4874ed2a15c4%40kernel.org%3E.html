FS_USERNS_DELEGATABLE: Fixing Containerized NFS Mount Regression

Summary

NFS Container Mount Regression Fix: Introducing FS_USERNS_DELEGATABLE

Summary

Type: Bug fix (regression in containerized NFS mounting)

This thread contains a single patch submission from Jeff Layton addressing a regression that broke NFS mounts inside Linux containers. The patch introduces a new VFS filesystem flag, FS_USERNS_DELEGATABLE, enabling a secure delegation model for privileged mount daemons — an important fix for users relying on containerized NFS clients with delegated mount services.

Background and Problem Statement

The issue stems from commit e1c5ae59c0f2 ("fs: don't allow non-init s_user_ns for filesystems without FS_USERNS_MOUNT"), which tightened VFS security by preventing filesystems lacking the FS_USERNS_MOUNT flag from being mounted inside user namespaces (containers). While well-intentioned, this change inadvertently broke a legitimate deployment pattern used by some organizations.

Jeff Layton described the affected use case in his patch submission:

"This broke NFS mounts in our containerized environment. We have a daemon somewhat like systemd-mountfsd running in the init_ns. A process does a fsopen() inside the container and passes it to the daemon via unix socket." Jeff Layton

The architecture works as follows:

  1. A process inside a container calls fsopen() for NFS, which creates a filesystem context with the container's user namespace (fc->user_ns).
  2. This context is passed via Unix socket to a privileged mount daemon running in the initial (init) user namespace.
  3. The daemon validates the request — checking that it targets an allowed NFS server — and performs the actual mount.

This delegation model provides security: containers cannot directly mount arbitrary NFS servers, but can request mounts from a vetted daemon. However, the VFS change blocked this because NFS does not set FS_USERNS_MOUNT, and the filesystem context carries the container's user namespace rather than init's.

As Jeff explained the security dilemma:

"We don't want to add FS_USERNS_MOUNT to NFS since that would allow the container to mount any NFS server (even malicious ones)." Jeff Layton

Adding FS_USERNS_MOUNT directly to NFS would defeat the security purpose of the original VFS change, as it would permit unprivileged containers to mount arbitrary NFS servers without any vetting.

The Fix: FS_USERNS_DELEGATABLE

The patch introduces a new filesystem flag, FS_USERNS_DELEGATABLE, which occupies a middle ground between FS_USERNS_MOUNT (fully unprivileged mounting) and no flag at all (only init namespace mounts). The semantics are:

  • Filesystems with FS_USERNS_DELEGATABLE can be mounted from non-init user namespaces when the mount is performed via a delegated mechanism (i.e., the filesystem context's user namespace differs from the mounter's, indicating a privileged daemon is acting on behalf of the container).
  • This preserves the security boundary: containers still cannot directly mount NFS; they must go through the vetted daemon.

The patch modifies three files:

  • include/linux/fs.h: Adds the FS_USERNS_DELEGATABLE flag definition.
  • fs/super.c: Updates the VFS mount validation logic to recognize and permit delegatable filesystems.
  • fs/nfs/fs_context.c: Sets the FS_USERNS_DELEGATABLE flag on the NFS filesystem type.

The patch carries a Fixes: tag pointing to commit e1c5ae59c0f2, marking it as a regression fix.

Significance for NFS Client Development

This is an important fix for organizations using containerized NFS clients with delegated mount architectures:

  1. Restores functionality: Container-based workloads that rely on privileged mount daemons to perform NFS mounts can function again without reverting the VFS security hardening.

  2. Maintains security posture: Unlike simply adding FS_USERNS_MOUNT, this approach preserves the principle that containers cannot independently mount arbitrary NFS servers — they must still go through a trusted daemon that validates server identity.

  3. VFS-level change: The new flag is generic and could benefit other network filesystems with similar delegation requirements (e.g., CIFS, 9P) in the future.
