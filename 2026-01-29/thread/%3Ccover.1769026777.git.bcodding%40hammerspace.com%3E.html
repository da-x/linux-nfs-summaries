kNFSD Signed Filehandles: Dual-Signal Security Design Debate

Summary

kNFSD Signed Filehandles v2: Security Architecture Debate — Dual Signals and Untrusted Input

Overview

Discussion type: New feature (NFS server security enhancement) — patch review continuation

This week's activity on Benjamin Coddington's signed filehandle patch series focused on a fundamental architectural question: why does the design use two seemingly redundant signals — the sign_fh export option and the new FH_AT_MAC auth type flag — to control filehandle signature verification? The exchange between Chuck Lever, NeilBrown, and Coddington also touched on professional conduct norms in kernel review.

Bridge from Prior Week

Last week (2026-01-22 summary), the v2 series was reviewed extensively, with major debates around procfs vs. netlink API design (resolved: procfs removed), endianness bugs (Eric Biggers' catch), key rotation policy, and export option transition behavior. Coddington committed to several action items for v3. This week's discussion picks up on a deeper architectural question about the signing mechanism itself.

Key Technical Arguments This Week

The Dual-Signal Design: sign_fh Export Option vs. FH_AT_MAC Auth Type

The central technical debate this week revolved around an apparent redundancy in the design. Coddington's patch introduces both:

  • A sign_fh export option that administrators set per-export to enable signing
  • A new FH_AT_MAC auth type flag (#define FH_AT_MAC 1) embedded in the filehandle itself

Chuck Lever opened the discussion by questioning this dual approach in his review of patch 3/3:

"Why do you need both a sign_fh export option and a new FH auth type? Shouldn't the server just look for and validate FH signatures whenever the sign_fh export option is present?"

He noted:

"It seems a little subtle, so perhaps a code comment somewhere could explain the need for both."

NeilBrown initially provided a clarifying explanation in response:

"What does the server do to 'look for' an FH signature so that it can 'validate' it? Answer: it inspects the fh_auth_type to see if it is FT_AT_MAC."

He suggested a code comment:

"FT_AT_MAC allows the server to detect if a signature is expected in the last 8 bytes of the file handle."

Lever's Security Concern: Untrusted Network Input

Chuck Lever pushed back, raising a critical security principle. He argued that the sign_fh export option — a server-side policy decision — should be the authoritative signal, not information embedded in the filehandle received from a potentially malicious client in his response:

"No, NFSD checks the sign_fh export option. At first glance the two seem redundant, and I might hesitate to inspect or not inspect depending on information content received from a remote system. The security policy is defined precisely by the 'sign_fh' export option I would think?"

He further questioned whether NFSv2 filehandles (which have different sizes) would be affected:

"I believe NFSv2 is not supported."

NeilBrown acknowledged an alternative approach — always stripping and verifying the last 8 bytes when sign_fh is enabled — but offered a practical justification for the dual-signal design in his follow-up:

"Another reason is that it helps people who are looking at network packet captures to try to work out what is going wrong. Seeing a flag to say 'there is a signature' could help."

The Core Security Tension Remains Unresolved

Chuck Lever's final message this week underscored the unresolved tension between usability and security best practices:

"I'm wondering why there is both — the purpose of having these two seemingly redundant signals is worth documenting."

He raised a specific concern about root filehandles:

"There was some discussion a few days ago about whether the root FH could be signed or not. I thought for a moment or two that maybe when sign_fh is enabled, there will be one or more file handles on that export that won't have a signature, and FT_AT_NONE would set those apart from the signed FHs."

Most critically, he invoked a fundamental security principle:

"In addition, I've always been told that what comes off the network is completely untrusted. So, I want some assurance that using the incoming FH's auth type as part of the decision to check the signature conforms with known best practices."

He acknowledged the debugging benefit but drew a clear line:

"Sure. But unconditionally trusting that flag is another question."

Minor Code Review Items on Patch 1/3

NeilBrown also provided minor code review comments on patch 1/3:

  • Suggested renaming NFSD_A_SERVER_FH_KEY to NFSD_A_SERVER_MAX for the .maxattr field
  • Noted that magic numbers 35 and 38 in a size check need explanation, suggesting if (size == 36 || size == 37) would be clearer

Professional Conduct Note

NeilBrown chimed in on the interpersonal tensions from last week's heated exchange between Coddington and Chuck Lever:

"For the record I agree with Ben. It was reasonable question for Ben to ask, and an unhelpful and unprofessional response from Chuck."

Evolution of the Discussion

The thread progressed through a clear arc:

  1. Lever's initial question (Jan 23): Why two signals?
  2. NeilBrown's explanation (Jan 23): The auth type is how the server detects signatures; also aids debugging via packet captures
  3. Lever's security pushback (Jan 23): Server-side policy should be authoritative; network input is untrusted
  4. NeilBrown's concession on alternatives (Jan 23): Acknowledged that unconditional verification when sign_fh is set could work, but the flag aids debugging
  5. Lever's final position (Jan 24): The dual-signal design needs documentation; trusting the incoming auth type flag requires justification against security best practices

Final Conclusions and Open Questions

No definitive resolution was reached this week. The discussion left several action items for Coddington's v3:

  1. Document the rationale for the dual-signal design (sign_fh export option + FH_AT_MAC auth type)
  2. Address the security concern: Provide assurance that using the incoming filehandle's auth type flag in verification decisions conforms to best practices, given that network input is untrusted
  3. Clarify root filehandle behavior: Explain whether and when root filehandles are signed vs. unsigned under sign_fh
  4. Add clarifying code comments explaining why both signals exist

The broader architectural question remains: should the server unconditionally verify signatures based solely on the sign_fh export option, ignoring the auth type in the incoming filehandle? Or is the dual-signal design justified for debugging and operational clarity, with appropriate safeguards?

Significance for NFS Client Development

While this thread focuses on NFSD (server-side) changes, the signed filehandle feature has direct implications for NFS clients. Clients will need to handle larger filehandles (with appended 8-byte MAC signatures) and correctly interpret -ESTALE responses when export options change between signed and unsigned modes. The design also affects how clients cache and replay filehandles across server restarts or configuration changes.
