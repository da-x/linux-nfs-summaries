NFSD Layout Recall Timeout and Lease Manager Fencing v2: Refcount Leak, Race Condition, and Architectural Concerns Raised

Summary

NFSD Layout Recall Timeout and Lease Manager Fencing Integration v2: Review Highlights Refcount Leak, Race Condition, and Architectural Concerns

Summary

Type: Bug fix / robustness improvement for NFS server (NFSD) pNFS block layout recall handling.

Dai Ngo of Oracle submitted version 2 of a patch to enforce timeouts on layout recalls in the NFSD lease manager and integrate client fencing operations when a layout recall times out. The patch addresses a critical scalability concern: without a timeout, excessive nfsd threads can become blocked indefinitely in __break_lease() during layout conflict resolution, degrading server responsiveness.

This week's review from Chuck Lever and Jeff Layton surfaced several significant issues — including a reference count leak, a potential race condition in fencing logic, a use-after-free concern, and architectural objections to special-casing inside the low-level lease handling primitives. Dai Ngo acknowledged all concerns and committed to addressing them in v3.

Context from Prior Weeks

This patch is part of an ongoing effort to improve NFSD's pNFS block layout recall handling. The broader NFS server development cycle this week saw significant activity on RDMA API modernization, lockd boundary cleanup, and delegation timeout improvements (see related summaries). The fencing mechanism ties into the SCSI Persistent Reservation (PR) infrastructure used by block layouts to prevent clients from accessing storage after their layout has been revoked.

This Week's Activity: v2 Submission and Intensive Review

Patch Overview

Dai Ngo posted PATCH v2 1/1 on January 25, introducing the following key changes:

"When a layout conflict triggers a recall, enforcing a timeout is necessary to prevent excessive nfsd threads from being blocked in __break_lease ensuring the server continues servicing incoming requests efficiently."

The patch introduces a new callback lm_breaker_timedout in lease_manager_operations, invoked when a lease recall times out. For NFSD's lease manager, this callback triggers an asynchronous fencing operation via a system worker to prevent the client from accessing the underlying block device. The layout stateid is reference-counted during the fencing operation, and the conflicting file lease remains on the flc_list until fencing completes.

Chuck Lever's Review: Multiple Issues Identified

Chuck Lever provided a thorough code review on January 26 [id://f18c50fa-6f51-47fe-96de-ef2f0245a892@app.fastmail.com], identifying five distinct issues:

1. Documentation Inconsistency

"This might not be consistent with other comments that state lm_breaker_timedout runs with no locks held and may block. But looks like the flc_lock spinlock IS held. Documentation should say flc_lock = yes, may block = no."

The documentation table for lease_manager_operations incorrectly stated that lm_breaker_timedout runs without locks held.

2. Reference Count Leak on Early Return

"The refcount was incremented when scheduling the work but is never released for this early return."

Lever pointed out a missing nfs4_put_stid() call in an error path:

"Do you need: if (!nf) { nfs4_put_stid(&ls->ls_stid); return; } here?"

3. Race Condition in Fencing Flag Check

"Between this check and mod_delayed_work(), another thread could complete fencing. This can cause duplicate worker scheduling and reference count leaks."

Lever recommended holding cl_fence_mutex while checking the ls_fenced flag to prevent concurrent threads from both deciding fencing is needed.

4. Use-After-Free in Layout Stateid Cleanup

"nfsd4_free_layout_stateid() needs to cancel ls_fence_work explicitly before freeing stateid memory. Otherwise if the fence worker runs after the stateid is freed, it will access the freed stateid memory."

This is a critical correctness concern: without explicit cancellation of the delayed work item during cleanup, a stale worker could dereference freed memory.

5. Unbounded Fencing Retry and Error Handling

"In nfsd4_scsi_fence_client(), when a device error occurs (e.g., PR_STS_IOERR), ls->ls_fenced is set even though the client may still have storage access."

Lever also raised a broader architectural concern:

"Also, if fencing consistently fails with retryable errors, fencing is continually retried with no maximum retry limit. Is this new lease breaker timeout designed to take care of that cleanly, or is it something that needs some explicit logic? I don't immediately spot a mechanism to force lease disposal if fencing never completes."

Dai Ngo's Responses

Dai responded promptly [id://79e3e32f-05c1-4f43-9ced-3f6ba58adf95@oracle.com], acknowledging most concerns:

  • Documentation fix: "Yes, I forgot to update this doc. Fix in v3."
  • Refcount leak: "yes, we do. Fix in v3."
  • Race condition: Dai argued that holding cl_fence_mutex is not feasible since the code runs under the spinlock flc_lock:

"We can't hold the cl_fence_mutex here since this function runs under the spin_lock flc_lock."

He also contended that duplicate worker scheduling would not cause refcount leaks:

"Each worker increment and decrement the reference count separately so I don't see how it can leak?"

  • Use-after-free: Dai argued the reference count prevents premature freeing:

"The layout stateid cannot be freed by nfs4_put_stid once the fence worker has been scheduled, because the layout stateid's reference count is incremented at that point."

  • Error handling fix: "I will revert this check back to (status != 0) as error condition instead of checking for selected error codes as it does now. Fix in v3."
  • Retry limit: Dai proposed adding a maximum retry count:

"Currently there is no mechanism that prevents the fencing operation from retrying on errors forever. Would it sufficient to add a max count for retries, like 5 times?"

Jeff Layton's Architectural Objection

Jeff Layton raised a significant architectural concern [id://4cd265054051f11047276c225c70516bdcc4d8d2.camel@kernel.org]:

"Barf. I really don't care for this special-casing inside of lease_modify(). That's a fairly low-level lease handling primitive. This needs to be handled at a higher level."

Layton questioned the control flow:

"I also don't quite get what you're doing here. If you skip unlocking the lease here, when does it get unlocked?"

He suggested that lm_breaker_timedout should be called from a different location in the call chain and proposed a more general approach:

"ISTM that this function is the right place to call lm_breaker_timedout. Also, it might be best to define a lm_breaker_timedout() for all lease types, and just have the common case call lease_modify() as above."

Dai responded [id://075db2a1-5cbf-4484-9ecc-57e2fef3c45c@oracle.com]:

"I will remove this special-casing in v3." "I will move lm_breaker_timedout to here in v3." "ok, let me send out v3 and see if we still need to do this."

Key Technical Arguments

The Core Problem: Unbounded Blocking

The fundamental motivation for this patch is server-side scalability. Without a timeout on layout recalls, nfsd threads can accumulate in __break_lease(), blocking the server's ability to service new requests. This is particularly problematic in pNFS block layout deployments where layout conflicts are common during concurrent access patterns.

Fencing as a Safety Mechanism

The fencing operation ensures that when a layout recall times out (i.e., the client does not respond), the server proactively revokes the client's storage access via SCSI Persistent Reservations. This prevents data corruption scenarios where a client with an expired layout continues writing to the underlying block device.

Asynchronous Design Rationale

Fencing is performed asynchronously via a system worker because:

  1. The lease recall timeout handler runs under spinlock context and cannot block
  2. Fencing operations involve I/O (SCSI PR commands) that may take significant time
  3. The conflicting lease must remain on the flc_list during fencing to prevent other clients from gaining access

Architectural Tension: Kernel Lease API vs. NFSD-Specific Logic

Jeff Layton's objection highlights a recurring tension in kernel development: NFSD-specific behavior being embedded in generic VFS lease management code. The concern is that special-casing inside lease_modify() — a core kernel primitive used by all filesystems — reduces code clarity and maintainability.

Evolution of the Discussion

  2. Jan 26 (afternoon): Chuck Lever provides detailed code review identifying five issues
  3. Jan 26 (evening): Jeff Layton raises architectural concerns about special-casing in lease_modify()
  4. Jan 26 (night): Dai Ngo responds to all reviewers, committing to v3 fixes

Significance for NFS Client Development

While this patch targets the NFSD server side, it has important implications for NFS client developers working with pNFS block layouts:

  1. Improved server responsiveness: The timeout mechanism prevents server-side thread exhaustion during layout conflicts, indirectly improving client experience under contention.
  2. Fencing reliability: Proper fencing ensures that clients with expired layouts are blocked from storage access, preventing data corruption that would affect all clients accessing the same file.
  3. Retry limit question: The unresolved question about maximum fencing retries affects how quickly a stuck client's layout is fully revoked — impacting how fast other clients can obtain new layouts for the same file.

Final Status

As of this week's window close, no v3 has been posted. Dai Ngo committed to addressing all identified issues in v3, including:

  • Documentation corrections
  • Reference count leak fix on early return
  • Removal of special-casing from lease_modify() per Layton's suggestion
  • Relocation of lm_breaker_timedout call site
  • Reversion of error code checking to simple non-zero status check
  • Addition of a maximum fencing retry count (proposed: 5 retries)

The remaining open questions include whether the race condition in fencing flag checking requires additional synchronization and whether explicit delayed work cancellation is needed in nfsd4_free_layout_stateid().
