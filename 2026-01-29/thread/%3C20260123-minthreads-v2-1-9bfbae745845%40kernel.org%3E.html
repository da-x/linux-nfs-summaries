nfsdctl: Add min-threads support for dynamic NFS server threading

Summary

nfsdctl Gains Support for Dynamic Threading via min-threads

This week, Jeff Layton submitted a revised patch series to nfs-utils that introduces support for managing NFS server (nfsd) dynamic threading through the nfsdctl utility. This is a user-space tooling update designed to complement kernel-side changes that allow nfsd thread counts to fluctuate based on workload demand.

Feature Overview: Dynamic Threading in nfsd

The patch adds support for a new min-threads parameter, which works in tandem with the existing threads (maximum) parameter. As explained by Jeff Layton in the cover letter PATCH v2:

"If the user sets min-threads, and has a new enough kernel, the traditional threads parameters will represent the max number of threads. The min-threads value represents the minimum number of threads to run in each pool. The kernel will start the minimum number of threads at startup time, and the thread count will dynamically fluctuate between the min and max based on load."

If min-threads is not set (defaults to 0), dynamic threading is disabled, preserving backward compatibility.

Key Technical Changes

The patch modifies several components within nfs-utils:

  • configure.ac: Conditionally compiles the new feature based on the presence of NFSD_A_SERVER_MIN_THREADS in kernel headers.
  • nfsdctl.c: Updates the "autostart" subcommand to read min-threads from nfs.conf and pass it via netlink. The "threads" subcommand gains a new command-line option for setting minimum threads dynamically.
  • Documentation: Man pages (nfsdctl.8, nfs.conf.man) are updated to document the new parameter.

Changes in v2 addressed minor issues from v1, including proper getopt handling and conditional compilation of help text.

Discussion on Load Heuristics

Mike Owen raised an important question regarding the definition of "load" used by the kernel to decide when to scale threads up or down Re: PATCH:

"Can 'load' be described further in the manpage for users? I ask, because I'm interested to understand the heuristics it takes into account when nfsd makes a decision to increase or decrease the thread count. For example, is memory pressure + io pressure stall info + io requests all taken into account?"

Jeff Layton clarified that the current implementation uses a simple heuristic based on incoming RPC requests Re: PATCH:

"In this case 'load' is simply incoming RPC requests: If the server gets an RPC request and goes to wake a thread for it, and finds that none are idle, then it will start a new thread (providing it's not already at the max). The threads are eligible to exit if they've been idle for 5s."

He acknowledged room for improvement:

"It would be nice to make this a bit more sophisticated. In particular, we probably don't want to start new threads when memory pressure is high (and maybe shut some down in that case too). We'd welcome some advice here (or even better, patches)."

Layton also disagreed with the conclusions of a commonly cited article on NFS thread sizing, noting:

"On a typical server, at busy times you probably want more threads than CPUs, simply because a lot of them end up blocked doing I/O."

Conclusion

This patch is classified as a new feature for nfs-utils, enabling administrators to configure and manage dynamic threading in the NFS server. The discussion highlighted that while the current load heuristic is simple (RPC request-driven), there is interest in future enhancements—particularly around memory pressure awareness. The thread concluded with an invitation for community contributions to refine the scaling algorithm.
