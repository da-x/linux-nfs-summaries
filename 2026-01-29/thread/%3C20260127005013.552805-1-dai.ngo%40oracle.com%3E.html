NFSD Layout Recall Timeout: Fencing Integration, Data Safety Debate, and Architectural Rework

Summary

NFSD Layout Recall Timeout and Lease Manager Fencing Integration

Summary

Type: Bug fix / Protocol safety enhancement (NFSD server-side pNFS block layout recall handling)

Overview

Dai Ngo submitted version 4 of a patch to enforce timeouts on NFSv4.1/pNFS layout recalls and integrate fencing through the kernel lease manager framework (PATCH v4 1/1). The patch addresses a critical server-side reliability issue: when a layout conflict triggers a recall, the absence of a timeout can cause excessive nfsd threads to block indefinitely in __break_lease, degrading or halting the server's ability to service incoming requests.

As Dai explained in the cover letter:

"When a layout conflict triggers a recall, enforcing a timeout is necessary to prevent excessive nfsd threads from being blocked in __break_lease ensuring the server continues servicing incoming requests efficiently."

The patch introduces a new lm_breaker_timedout callback in the lease manager operations structure, enabling NFSD to trigger SCSI Persistent Reservation (PR) fencing when a layout recall times out — preventing the original client from continuing to access the underlying block device while another client is being granted exclusive access.

Key Technical Arguments

1. Timeout Enforcement and Fencing Integration

The patch adds lm_breaker_timedout to lease_manager_operations, invoked when a lease recall times out. For NFSD's lease manager, this callback schedules an asynchronous worker to fence the client via SCSI PR operations if the layout type supports fencing. The conflicting file_lease remains on the flc_list until fencing completes, ensuring no other clients can access the file prematurely.

2. Chuck Lever's Review: Error Handling and Race Conditions

Chuck Lever raised several significant concerns in his review on Jan 27:

Error distinction removal: The removed code distinguished between retryable errors (e.g., path failures) and permanent errors (PR_STS_IOERR, PR_STS_RESERVATION_CONFLICT), but the new code clears the fence on any error:

"The removed code distinguishes retryable errors (such as path failures) from permanent errors (PR_STS_IOERR, PR_STS_RESERVATION_CONFLICT), but the new code clears the fence on any error, potentially causing infinite retry loops as warned in the removed comment."

Race condition on fenced state: Chuck identified a potential TOCTOU race with ls_fenced:

"Fair enough for ls_fence_retry_cnt, but are you sure there isn't a TOCTOU issue here for ls_fenced? Isn't there a race possible with the server receiving the client's callback while lm_breaker_timeout is running?"

Reference counting race: The increment of ls_fence_retry_cnt after mod_delayed_work() was flagged as racy:

"Incrementing after the mod_delayed_work() call is racy."

Chuck also noted a missing cancel_delayed_work_sync() when freeing the layout stateid.

3. Jeff Layton's Review: Simplifying the Architecture

Jeff Layton on Jan 27 proposed a simpler architectural approach:

"I don't understand what this new mutex is protecting, and this all seems overly complex. It feels kind of like you want nfsd to be driving the fencing retries, but I don't think we really do."

He suggested making ->fence_client return a bool/int indicating success or failure, with the workqueue job responsible for requeuing itself if retry is needed:

"I'd just make ->fence_client a bool or int return, and have it indicate whether the client was successfully fenced or not. If it was successfully fenced, then have the caller call lease_modify() to remove the lease. If it wasn't successfully fenced, have the caller (the workqueue job) requeue itself if you want to retry."

Jeff also emphasized the need for admin visibility when fencing fails:

"The cases where the fencing didn't work after too many retries, or the job couldn't be queued should probably get a pr_warn or something. The admin needs to know that data corruption is possible and that they might need to nuke the client manually."

4. Reference Counting Safety Concerns

Jeff Layton follow-up on Jan 27 raised concerns about the safety of using refcount_inc/dec for protecting layout stateid lifetime during fencing:

"Is that safe? That's done in nfsd_break_one_deleg() for similar reasons, but there is a comment over that function explaining why it's OK. We'll need to validate that the lease is always released before the sc_count goes to 0 here too."

Dai acknowledged this was unsafe:

"No, it's not safe. I have to think of other ways to make sure the layout stateid is valid when the fence worker runs." Dai Ngo

5. The Fundamental Data Safety Challenge

Chuck Lever articulated the core challenge with any timeout-based fencing scheme on Jan 27:

"Fine, but with the new retry escape clause, as mentioned below, the server and client can be left in opposite states, it looks like: One believes the fence succeeded, and one believes it still has full device access. Am I incorrect about that? This is the bane of every timeout-based scheme I know about, and why we have the 'hard' mount option."

He further noted:

"A warning doesn't seem like it would prevent data corruption. (I'm not against a warning, in and of itself... it just does not seem to me to be sufficient). I would really like this mechanism to be more data-safe. It needs to deal properly with network partitions and other problems."

6. Dai's Proposed Resolution: Infinite Retry with Warning

In response, Dai proposed abandoning the fixed retry limit in favor of infinite retries with admin warnings on Jan 28:

"You're right, the server and client can be left in opposite states if we still can not fence the client after so many retries. If we want to be safe then pr_warn the admin then retry forever which effectively prevents all other clients to access the conflict file until it's manually resolved by the admin."

He elaborated:

"I propose pr_warn the admin and retry forever for now until we can find a better option. I expect this to be a very rare condition so it should not effect most environments."

Dai also restored the distinction between permanent errors (PR_STS_IOERR, PR_STS_RESERVATION_CONFLICT) treated as non-error cases, and other errors (including ENOMEM) treated as retryable.

7. Architectural Refinement: Lease Modify Responsibility

Jeff Layton clarified the expected flow for lm_breaker_timedout on Jan 28:

"The lm_breaker_timedout() function (or the workqueue job it spawns) is then responsible for calling lease_modify() at the appropriate time. In most cases you're going to need to queue a workqueue job to fence, and you don't want to clear out the lease until after it's done."

Dai acknowledged this design direction on Jan 28:

"Oh I see, thank you!"

Evolution of the Discussion

The discussion progressed through several distinct phases over two days:

  1. Initial submission (Jan 27): Dai posted v4 with a fixed retry limit of 5 and NFSD-driven fencing retries.

  2. Review concerns (Jan 27 afternoon): Chuck Lever and Jeff Layton independently identified architectural issues — Chuck focused on error handling semantics, race conditions, and the fundamental data safety problem; Jeff proposed simplifying by having the workqueue job drive retries rather than NFSD.

  3. Dai's responses (Jan 27 evening): Dai acknowledged multiple concerns — the unsafe reference counting, the need to restore error distinction logic, and agreed to rework the architecture per Jeff's suggestion.

  4. Deep dive on data safety (Jan 27-28): Chuck Lever articulated why any fixed retry limit risks leaving server and client in inconsistent states. Dai proposed infinite retries with pr_warn as a pragmatic solution for this rare edge case.

  5. Architectural alignment (Jan 28): Jeff Layton clarified the expected callback contract — lm_breaker_timedout should either call lease_modify() itself or delegate that responsibility to the spawned workqueue job. Dai confirmed understanding and agreed to rework accordingly.

Final Conclusions

As of the end of this week's window, no consensus has been reached and no v5 patch has been posted. The key unresolved items are:

  • Retry strategy: Shift from fixed retry count (5) toward infinite retries with pr_warn logging to prevent data corruption when server and client disagree on reservation state.
  • Architectural simplification: Move fencing retry logic into the workqueue job rather than having NFSD drive retries, per Jeff Layton's suggestion.
  • Reference counting safety: A new approach is needed to ensure layout stateid lifetime during asynchronous fencing operations, as the current refcount_inc/nfs4_put_stid pattern was deemed unsafe.
  • Error handling semantics: Restore distinction between permanent errors (PR_STS_IOERR, PR_STS_RESERVATION_CONFLICT) and retryable errors, with appropriate comments explaining the rationale.
  • Callback contract: lm_breaker_timedout() should be responsible for calling lease_modify() at the appropriate time (either directly or via the spawned workqueue job).

Significance for NFS Development

This patch addresses a critical reliability gap in NFSD's pNFS block layout implementation. Without timeout enforcement on layout recalls, a slow or unresponsive client can block all nfsd threads attempting to resolve layout conflicts, effectively DoS-ing the NFS server. The integration with the kernel lease manager framework also represents an important architectural advancement, enabling NFSD to leverage generic lease infrastructure for pNFS recall semantics.

The fundamental challenge identified by Chuck Lever — that timeout-based fencing inherently risks inconsistent state between server and client — echoes the classic "hard vs. soft" mount dilemma in NFS. This discussion highlights the ongoing tension between server-side liveness guarantees and data safety in distributed storage systems.
