NFSD Signed Filehandles: FH_AT_MAC Debate, ESTALE Rate Limiting RFC, and -ESTALE Handling

Summary

This week's activity on this thread focused on two distinct but related topics within the broader NFSD security hardening effort: (1) continued debate over the FH_AT_MAC auth type field in Benjamin Coddington's signed filehandles patch series (PATCH v2 3/3), and (2) a new RFC from NeilBrown proposing rate limiting of requests that result in -ESTALE errors from the filesystem.

Discussion type: New feature design refinement (signed filehandles) and RFC/proposal (ESTALE rate limiting).

Prior Weeks Recap

Last week, Coddington submitted v2 of his 3-patch signed filehandles series (prior summary). The series adds HMAC signing to NFS filehandles using siphash to prevent filehandle guessing attacks. Key v2 developments included: removal of the procfs fh_key interface (keeping only netlink), fixing an endianness bug in key handling identified by Eric Biggers, and settling on a "key locked while server running" rotation model. The discussion was active with debate over API design between Coddington and Chuck Lever.

This Week's Activity

1. The FH_AT_MAC Auth Type Debate (Jan 24–28)

The central question this week: should the filehandle include an explicit auth type field (FH_AT_MAC) indicating it carries a MAC signature, or should the server determine whether to validate based solely on export policy (sign_fh)?

Chuck Lever raised concerns about relying on network input for security decisions. He questioned why both sign_fh (an export option) and FH_AT_MAC (a filehandle field) were needed:

"Why do you need both a sign_fh export option and a new FH auth type? Shouldn't the server just look for and validate FH signatures whenever the sign_fh export option is present?" Chuck Lever

NeilBrown suggested documenting the distinction clearly:

"sign_fh is needs to configure server policy. FT_AT_MAC, while technically redundant with sign_fh, is valuable when interpreting NFS packet captures." NeilBrown

Coddington explained the field was vestigial from an earlier encrypted filehandle design but could serve useful purposes:

"It would be essential if future patches wanted to 'drain' and 'fill' clients with signed/plain filehandles using more permissive policies." Benjamin Coddington

He also noted the self-describing nature of filehandles:

"Not a great argument, I know, but I think its nice to keep the standard that filehandles are independently self-describing." Benjamin Coddington

Chuck Lever pushed back on the security implications of trusting network-provided auth type:

"If it makes no difference to the security level, then let's not bother to check it at all." Chuck Lever

He framed two key questions for the group:

"1. If I were a security reviewer, I would say that NFSD shouldn't rely on network input like this to decide whether or not to validate the MAC. Either the server expects a MAC and uses it to validate, or it doesn't." "2. Is setting FH_AT_MAC still useful for other reasons?" Chuck Lever

Trond Myklebust weighed in with a measured assessment:

"I fully agree with the argument that policy decisions about whether to check for a MAC need to be driven by the /etc/exports configuration, and not by the filehandle itself." "So personally, I'm neutral about the need for that flag. I don't think it is harmful (provided it isn't being used by knfsd to determine MAC policy enforcement) however I don't see a strong argument for it being needed either." Trond Myklebust

Chuck Lever then asked about Wireshark support for parsing signed filehandles:

"I can't recall if Wireshark is smart enough to introspect Linux NFSD file handles (I thought it could). It would be sensible to have some Wireshark update code in hand before making the final decision about keeping the new auth_type." Chuck Lever

Coddington investigated and found Wireshark already has extensive filehandle dissection code, but admitted he lacked a concrete use case:

"I've gone digging and wireshark has a surprising amount of filehandle dissection code... I certainly can add patches to parse FH_AT_MAC for the linux(s) decoders, but I admit I don't have any use case." "I'm completely neutral on keeping FH_AT_MAC at this point." Benjamin Coddington

Chuck Lever applied the principle of minimalism:

"If we can't find a use case or need for something, the usual practice is to remove it from your patches until we have one." Chuck Lever

Coddington's final counterargument was about testing infrastructure:

"Well the other use-case might just be for those pynfs tests you were asking for. Without FH_AT_MAC, its tricky for pynfs to know if its getting signed filehandles or not." Benjamin Coddington

2. ESTALE Rate Limiting RFC (Jan 24–25)

NeilBrown posted a separate RFC proposing rate limiting for requests that result in -ESTALE errors from the underlying filesystem. This is related to the broader filehandle security discussion, as ESTALE-generating attacks are one vector for DoS against NFSD.

Jeff Layton raised concerns about the approach:

"serialize and delay ESTALE errors for the same inode." Jeff Layton

NeilBrown responded that such optimization could be deferred:

"We could do that if we changed ->fh_to_dentry so that in case of a gen-number mismatch it could return the dentry but flag the error. Then we could lock the inode while waiting 15ms. I don't think that is justified up front, but if we took this approach and it proved to be problematic, we could explore this as a later improvement." NeilBrown

The discussion also touched on per-client filehandles as an alternative security mechanism. Jeff Layton suggested:

"Thinking about this some more, I think the better way to do this would probably be to tie it to TLS, so that you factor in the client's certificate. That would work on either v3 or v4." Jeff Layton

NeilBrown expressed openness to the idea:

"I do like the idea of per-client filehandles if it can be made to work." NeilBrown

Key Technical Arguments and Evolution

Security Policy Must Be Server-Side, Not Network-Derived

A strong consensus emerged that MAC validation policy must be driven by server configuration (/etc/exports with sign_fh), not by data in the filehandle itself. Trond Myklebust's statement captured this clearly:

"Policy decisions about whether to check for a MAC need to be driven by the /etc/exports configuration, and not by the filehandle itself." Trond Myklebust

The FH_AT_MAC Field: No Clear Use Case Identified

After thorough examination, no compelling use case was identified for retaining the FH_AT_MAC auth type field. Wireshark dissection support was explored but found to lack practical demand. The pynfs testing argument was noted but not deemed sufficient on its own. Chuck Lever's conclusion stands: remove it unless a concrete need emerges.

ESTALE Rate Limiting as Complementary Defense

NeilBrown's RFC for rate limiting -ESTALE responses represents a complementary defense strategy to signed filehandles — targeting the DoS vector rather than the access-control bypass vector. The discussion about per-client filehandles tied to TLS certificates suggests an interesting convergence point between these two approaches.

Significance for NFS Client Development

While this thread is primarily NFSD-focused, there are implications for NFS client developers:

  1. Filehandle format changes: Signed filehandles will be larger (8-byte MAC appended). NFS clients must handle both signed and unsigned filehandles during transition periods, especially when sign_fh export options change on the server side.

  2. -ESTALE behavior: When a server transitions from sign_fh enabled to disabled, clients presenting previously-signed filehandles will receive -ESTALE. This is documented as expected behavior but may require client-side handling strategies.

  3. Per-client filehandle exploration: The discussion about tying filehandles to TLS certificates or client identities could eventually affect NFS client protocol interactions, particularly for inter-server COPY operations where client identity propagation becomes relevant.

Status and Outlook

  • Signed filehandles v2: The FH_AT_MAC field remains in the current patch but is likely to be removed in v3 unless a concrete use case emerges. The core signing mechanism (siphash MAC) and sign_fh export option remain solid.
  • ESTALE rate limiting: Still at RFC stage; no patches submitted yet. NeilBrown indicated he wanted buy-in before investing more time.
  • Testing: Chuck Lever's request for pynfs tests covering sign_fh transitions remains an open action item.
