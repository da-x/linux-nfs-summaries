Rate-Limiting ESTALE in nfsd: An Alternative to File Handle Signing

Summary

Rate-Limiting ESTALE Responses in nfsd: An Alternative to File Handle Signing

Overview

This week, Neil Brown proposed a novel approach to mitigating NFS file handle brute-force attacks — one that avoids the overhead and configuration burden of Ben's recently discussed file handle signing mechanism. The RFC-style patch introduces rate limiting on requests that result in -ESTALE errors from the underlying filesystem, effectively raising the cost of guessing valid file handles from hours to approximately one year.

Background: The File Handle Brute-Force Problem

NFS file handles typically embed a 32-bit generation number randomly assigned by the filesystem at inode allocation time. As Neil Brown explained in his initial post on January 23:

"The only known attack methodology is to guess the inode number of a file of interest, then iterate over all possible generation numbers. This would be expected to achieve success (if the inode number is valid) in, on average, 2^31 guesses. At one per microsecond this is less than one hour. At one per 10 microseconds this is less than one day."

The proposed patch serializes ESTALE responses via a global mutex and inserts a 15ms delay for each stale file handle lookup, increasing the expected attack time to roughly one year. Neil positioned this as an alternative to Ben's signed file handle approach:

"Ben's approach requires some configuration, though not much. This approach requires zero configuration which is always better." "Ben's approach adds a siphash calculation or two to (almost) every NFS request. This may not be a great cost but it is still some time and some power. Less is more."

Key Technical Arguments

Jeff Layton's Concerns: DoS Potential and Complementary Approaches

Jeff Layton raised an important concern about the global mutex on January 24:

"Hmm...maybe a mutex_trylock and if it fails do an immediate -EAGAIN return (which hopefully becomes NFSERR3_JUKEBOX or NFS4ERR_DELAY)? This could be a way to DoS the server, otherwise."

Neil countered that returning NFS4ERR_DELAY immediately would leak nearly identical information to the attacker:

"Returning NFS4ERR_DELAY immediately instead of NFS4ERR_STALE gives the attacking client nearly identical information. It would not resend the request that reported NFS4ERR_DELAY."

Neil also argued that inducing a denial-of-service is intentional and desirable:

"Triggering a DoS is part of the point - it both defeats the attack and makes the attack obvious. If an attack is going to be obvious it will likely be caught so the potential attacker is unlikely to try."

Jeff suggested this approach might complement rather than replace file handle signing, and later proposed per-inode rate limiting to narrow the blast radius:

"It does occur to me that we're not concerned so much with ESTALE errors globally, as seeing a lot of them that refer to the same inode. It would be nice if we could track this on a per-inode basis, and only serialize and delay ESTALE errors for the same inode."

Jeff also floated an intriguing idea about client-specific file handles:

"Once we tack on the signature, there is (seemingly) no reason that every client must get the same filehandle. If we were to factor in (e.g.) the long-form clientid when generating the hash, then we'd have a v4 fh that could only be used by a single client."

Chuck Lever's Critical Review: Filesystem Gaps and Timing Attack Surface

Chuck Lever delivered the most thorough critique on January 25, identifying several significant weaknesses:

1. Non-random generation numbers in common filesystems: Chuck demonstrated that the "32 bits of randomness" claim does not hold universally:

"btrfs sets i_generation = trans->transid (a sequential counter starting from 1, incremented per transaction)" "ext2 uses sbi->s_next_generation++ (sequential counter seeded randomly at mount)" "ocfs2 uses osb->s_next_generation++ (sequential counter)"

He questioned whether the security estimate holds for btrfs exports:

"For btrfs in particular, the generation number contains zero bits of randomness. An attacker who can estimate the filesystem age or transaction count can predict valid generation numbers with high probability. Does the '1 year' security estimate hold for btrfs exports, or is that filesystem effectively unprotected by this mitigation?"

2. NFS re-export vulnerabilities: Chuck noted that NFS re-exports (fs/nfs/export.c) embed the backing server's filehandle verbatim without generating a local generation number, leaving protection entirely dependent on the upstream server.

3. Global mutex latency impact: He highlighted the operational risk of serializing all ESTALE errors:

"With N concurrent ESTALE errors, the total delay becomes N * 15ms as each thread waits for the mutex. With 100 concurrent stale handle accesses, this adds 1.5 seconds of accumulated latency."

4. Timing attack surface: Chuck drew parallels to prior efforts to eliminate synchronous delays in nfsd threads:

"We've spilled a large number of electrons trying to remove needless delays of nfsd threads (eg, waiting synchronously for NFS clients to respond to NFSv4 callbacks) because a malicious client can use this delay as a timing attack to determine the (maximum) number of available nfsd threads and simply keep them all busy, preventing the server from doing useful work."

Chuck concluded:

"I think given the gaps in covering exports of first-tier file systems such as btrfs, the unknowns in protecting re-exported NFS mounts, and the increase in the surface of timing attacks, this approach needs significant refinement before I would feel comfortable with it."

Evolution and Final Conclusions

Neil Brown responded on January 28 with a thoughtful acknowledgment of the critiques:

  • He admitted that his analysis had only covered ext4 and XFS: "Thanks for exploring this. I had only checked ext4 and xfs and thought I saw a pattern. btrfs is certainly a weakness here - though it could be 'fixed' I expect."
  • On re-exports, he deferred responsibility to the backing server: "I think we would have to expect the backing server to provide any protection that it needs."
  • On per-inode vs. per-client rate limiting, he noted trade-offs: "Per svc_export or per client-IP would be OK... per-inode requires help from each fs - not impossible but awkward."
  • He acknowledged that attackers with legitimate access could already cause some harm, but maintained the goal was protecting sensitive data rather than preventing all harm.

Neil concluded with an open stance on future work:

"In terms of defence-in-depth I think this is still a good approach. Maybe I'll resubmit with some fine tuning and better explanations. I see how time works out."

Classification

This discussion centers on a security hardening feature for the NFS server (nfsd), specifically addressing file handle enumeration attacks. It is not a protocol change but rather a server-side mitigation strategy. The approach remains an RFC/proposal at this stage, with significant refinement needed before it would be considered ready for integration.

Key Takeaways for NFS Client Development

While primarily an nfsd (server-side) discussion, the implications for NFS client development include:

  • Clients may experience increased latency on stale file handle errors if this approach is adopted.
  • The ongoing debate between server-side rate limiting and cryptographic file handle signing affects how clients should handle NFSERR_STALE and NFS4ERR_DELAY responses.
  • Client-specific file handles (if pursued) would require coordination between client identity and file handle generation, potentially impacting client caching strategies.
