RFC: Eliminating NFS Dummy Root Dentries — Viro Proposes Cleanup of 13-Year-Old Workaround

Summary

Eliminating NFS Dummy Root Dentries: An RFC Proposal by Al Viro

Type: Cleanup / Bug fix (removal of a historical workaround in the NFS client's superblock root dentry handling)

Overview

On January 24, VFS maintainer Al Viro posted an RFC patch proposing to eliminate a long-standing workaround in the NFS client related to "dummy root dentries." This is a cleanup and simplification effort targeting internal VFS/NFS client code — not a protocol change or new feature.

The patch addresses what Viro calls "weirdness around NFS dummy root dentries" — a historical hack where the NFS client manually created an alias for the root directory and removed it from the inode's alias list, violating standard dcache assumptions.

Key Technical Arguments

The Historical Problem

For over a decade (since 2013), the NFS client maintained a special "dummy" root dentry that was manually detached from its inode's alias list. This was originally necessary because dcache_shrink_for_umount() would be confused if the filesystem's ->s_root dentry were spliced onto a secondary tree during cross-mount scenarios.

Viro explains:

"These days (starting from 2013, actually) dcache_shrink_for_umount() is not bothered by having ->s_root spliced onto one of the secondary trees, so the reason for having a weird alias for root directory (manually removed from the alias list of directory inode, which violates all kinds of assumptions) no longer applies."

The Proposed Fix

The patch proposes two simplifications:

  1. Use the real dentry as ->s_root: Instead of creating a special dummy dentry, simply use the dentry that is about to be returned as the superblock's root, if it hasn't been set already.

  2. Remove manual security instantiation: The patch also eliminates redundant calls to security_d_instantiate(), since d_obtain_root() already handles this:

"And don't bother with manual security_d_instantiate(), while we are at it - d_obtain_root() has already done that."

Trade-off Noted

Viro transparently documents a behavioral change in the patch description. If the root of an earlier mount gets spliced onto a larger subtree from a subsequent mount, the chain of ancestor dentries will remain pinned in dcache for as long as any of the mounts exist. He illustrates with a concrete example:

"if root of the first mount does get spliced onto the bigger subtree of subsequent mount, it will keep the resulting chain of ancestors pinned in dcache for as long as any of mounts exist. That won't affect the 'is the filesystem busy' logics, though; just that after

mount foo:/bar/baz/barf /path1
mount foo:/bar/ /path2
ls /path2/baz/barf
umount /path1

we'll get the dentries of /path2/baz and /path2/baz/barf stay in dcache (unhashed if invalidated, etc.) until /path2 is also unmounted, rather than having only the dummy root pinned."

Viro concludes his rationale with:

"AFAICS, it works and unless there are other reasons why need it, it would be nice to get rid of that wart."

Discussion Status

As of the end of this week's window (January 30), no replies have been posted to this RFC. The thread contains only Viro's initial proposal. Given the RFC designation, the community is expected to review and provide feedback in the coming days.

Significance for NFS Client Development

This patch targets a foundational aspect of how the NFS client manages its superblock root dentry — a core data structure in the VFS layer. Key implications:

  1. Code simplification: Removing the dummy root dentry hack eliminates code that "violates all kinds of assumptions" about dcache behavior, making the NFS client's dentry handling more consistent with standard VFS patterns.

  2. No functional regression expected: The trade-off in dcache pinning behavior is described as cosmetic — it does not affect filesystem busy-checking logic or unmount semantics.

  3. Historical cleanup: This workaround has been unnecessary since 2013, making its removal a long-overdue simplification.

  4. Interaction with concurrent work: This week also saw significant NFS client development activity in the lockd API boundary clarification series, which fixed a race condition in the sysfs shutdown path and refactored lockd's public API. Viro's dentry cleanup is complementary to these efforts, further reducing NFS client code complexity.

Final Conclusions

  • Status: RFC posted; awaiting community review and feedback.
  • Nature: Cleanup of a 13-year-old workaround in NFS client dentry management.
  • Risk: Low — the behavioral change (slightly more dcache pinning) is explicitly documented and does not affect core mount/unmount semantics.
  • Next steps: Community review during the v7.0 merge window period, with potential integration into the mainline kernel if no objections are raised.
