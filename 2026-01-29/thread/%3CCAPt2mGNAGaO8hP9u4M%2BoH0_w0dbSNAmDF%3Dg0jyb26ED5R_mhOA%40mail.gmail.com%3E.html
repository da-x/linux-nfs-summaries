knfsd Read IOPS Limits: Lock Contention Investigation Begins

Summary

Type: Performance investigation / Bug diagnosis (not yet a confirmed bug fix)

Overview

Daire Byrne from DNEG initiated an investigation into the aggregate read IOPS ceiling of the Linux NFS server (knfsd) under a random 4K read workload. The discussion reveals that knfsd appears to hit a hard performance plateau at approximately 300–400K IOPS, regardless of how many clients are added, and across a wide range of hardware configurations and kernel versions. Chuck Lever and Dai Ngo joined the investigation, with Chuck identifying specific lock contention hotspots through lockstat analysis.

The Problem: A Hard IOPS Ceiling

Daire Byrne reported that his random 4K read workload saturates the NFS server with around 100 client hosts, after which aggregate IOPS "pretty much flatlines no matter how many more clients you add (I tried up to 500 clients)." He noted:

"And this 300-400k iops limit is probably the maximum that anyone can get, because I tested a wide range of hardware and kernel vintages. The results are all very similar." Daire Byrne

He clarified that his interest was in aggregate server performance rather than per-client throughput:

"I guess I am less interested in improving the per client performance, more the aggregate performance of the server." Daire Byrne

Initial Suggestions

Client-Side Slot Table Tuning

Dai Ngo from Oracle suggested increasing the NFS client's session slot table, which defaults to 64 entries:

"Have you tried to increase the slot table on the NFS client side? By default it has 64 entries... Try to double it to see if that makes any different." Dai Ngo

He noted the server supports up to 2048 slots per session on newer kernels. Daire confirmed this had no effect on aggregate server performance.

Lock Contention Hypothesis

Chuck Lever hypothesized that the workload was hitting contended spin locks:

"At risk of being glib, the performance data suggests your workload is tickling one or more contended spin locks." Chuck Lever

He directed Daire to use the kernel's lockstat tool, documented in Documentation/locking/lockstat.rst.

Lockstat Analysis: xpt_mutex Identified as Problematic

Daire Byrne shared lockstat data with Chuck. After reviewing it, Chuck identified a significant issue with the xpt_mutex:

"There's kind of no denying it, the xpt_mutex numbers are shitty. The maximum hold time on that mutex is 293379.40 usecs, with a mean hold time of nearly 16 usec, giving it the worst mean wait time by an order of magnitude. And it's not even a contended lock." Chuck Lever

This mutex, part of the SunRPC thread pool dispatch path, was exhibiting extremely high hold times despite not being highly contended — suggesting a structural problem rather than simple contention.

Cross-Kernel Consistency

Daire noted that this performance plateau appears consistent across multiple kernel generations:

"We have a few generations of hardware and OS versions like RHEL8 (4.18), RHEL9 (5.14) and mainline (v6.18) in production, but I see similar performance plateaus for this workload in all cases (~300k iops/s)." Daire Byrne

He also recalled seeing different lock contention patterns on older kernels:

"I distinctly remember seeing high nfsd_file_lru_remove & nfsd_file_put (perf lock record) contention on the RHEL9 (5.14) kernel which I don't see now on mainline." Daire Byrne

This suggests that while the overall IOPS ceiling has remained consistent, the underlying bottleneck may have shifted across kernel versions — from file cache contention in older kernels to xpt_mutex issues on mainline.

Next Steps: TCP Send Path Investigation

Chuck Lever committed to investigating the issue further:

"True, having a 'good' starting point is a pre-requisite for obtaining quality bisection results. I'm going to try some simple experiments here to see if I can spot any structural problems with the TCP send path." Chuck Lever

Daire Byrne offered to collect lockstat data across multiple kernel versions for comparative analysis.

Significance for NFS Server Development

This thread highlights a potential structural performance limitation in the knfsd server under high-concurrency random read workloads. Key takeaways:

  1. The xpt_mutex in the SunRPC thread pool dispatch path is exhibiting problematic hold times (up to 293ms maximum, ~16μs mean), which could be a throughput bottleneck for small I/O patterns.
  2. File cache contention has been addressed in newer kernels (the nfsd_file_lru_remove and nfsd_file_put hotspots seen on RHEL9/5.14 are gone), but the overall IOPS ceiling persists.
  3. The bottleneck appears to be structural rather than hardware-dependent, as similar ceilings appear across diverse configurations.

This investigation is ongoing, with Chuck Lever planning experiments on the TCP send path and potentially posting patches to address identified contention points. The thread continues into the following week (see subsequent messages in February 2026), where further analysis of lwq spinlock contention and nfsd_setuser group sort performance is discussed.
