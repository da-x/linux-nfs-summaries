Signed Filehandles: Testing Framework Debate — pynfs Deemed Unsuitable for Linux-Specific Features

Summary

Type: New feature (NFS server security enhancement) — patch review continuation

This week's activity on Benjamin Coddington's signed filehandle patch series focused on a practical question: how should the Linux-specific signed filehandle feature be tested? The discussion centered on whether pynfs — the NFS protocol compliance testing framework — is an appropriate home for testing this feature, or whether an alternative testing approach is needed.

Bridge from Prior Weeks

The signed filehandle series has been under active review since January 21 (v2 submission). Key prior developments include:

  • Jan 21–22: Intense debate over procfs vs. netlink API design (resolved: procfs removed), endianness bug fix (Eric Biggers' catch), key rotation policy, and export option transition behavior.
  • Jan 23–24: Architectural debate about the dual-signal design (sign_fh export option + FH_AT_MAC auth type flag), with Chuck Lever raising security concerns about trusting network input for verification decisions.

Chuck Lever had previously suggested comprehensive testing:

"IMHO we also want to craft some pynfs tests to ensure that these cases work as we expect, and to ensure that we capture all of the cases that need to be checked (including the cases involving transitioning from sign_fh to not sign_fh and vice versa)." Chuck Lever

This Week's Activity

The pynfs Testing Question

Benjamin Coddington raised a practical concern about using pynfs for testing signed filehandles. He noted that Wireshark already has extensive filehandle dissection code (listing numerous dissectors including dissect_fhandle_data_LINUX_NFSD_LE and others), and offered to add patches to parse FH_AT_MAC:

"I certainly can add patches to parse FH_AT_MAC for the linux(s) decoders, but I admit I don't have any use case." Benjamin Coddington

Chuck Lever responded that Wireshark support would be valuable before making a final decision on keeping the FH_AT_MAC auth type:

"I can't recall if Wireshark is smart enough to introspect Linux NFSD file handles (I thought it could). It would be sensible to have some Wireshark update code in hand before making the final decision about keeping the new auth_type." Chuck Lever

Trond Myklebust weighed in on the dual-signal design, expressing neutrality:

"I fully agree with the argument that policy decisions about whether to check for a MAC need to be driven by the /etc/exports configuration, and not by the filehandle itself." Trond Myklebust

He noted a speculative use case for metadata servers using knfsd as a flex files data server:

"I did speculate a little in some internal conversations whether or not a metadata server that is using knfsd as a flex files data server might be able to re-sign a filehandle after the secret key were changed, rather than having to look up the file again using its path. However that too is very much a corner case that we have no plans to optimise for at this time." Trond Myklebust

The Key Conclusion: pynfs Is Not the Right Tool

The most significant exchange this week came between Chuck Lever and Benjamin Coddington regarding testing. Coddington pointed out that pynfs tests would become "awfully linux specific":

"The other thing about those pynfs tests is that they get awfully linux specific - requiring new tooling to setup and change the export option." Benjamin Coddington

Chuck Lever concurred, delivering a definitive conclusion about the scope of pynfs:

"pynfs is for unit testing protocol compliance. Since signed file handles are a feature of the Linux implementation and not part of the NFS protocol standard, pynfs won't be an appropriate home for unit testing the signed FH framework in Linux. Sigh. We'll have to look for another framework that can host such testing." Chuck Lever

Evolution of the Discussion

The thread progressed through a clear arc this week:

  1. Jan 24: Coddington responded to NeilBrown's review, explaining the vestigial nature of FH_AT_MAC from the earlier encrypted_fh design and asking whether it should be kept
  2. Jan 24: Chuck Lever deferred the decision pending input from Trond Myklebust on use cases for third-party systems that pass around NFSD-generated filehandles
  3. Jan 24: Trond Myklebust expressed neutrality, noting no strong argument either way but confirming policy should be driven by /etc/exports
  4. Jan 26: Coddington reported on Wireshark's existing filehandle dissection capabilities and offered to add FH_AT_MAC parsing support
  5. Jan 28: Chuck Lever asked whether anyone was working on Wireshark patches for signed Linux filehandles
  6. Jan 28–29: Coddington raised the pynfs testing concern; Chuck Lever concluded pynfs is inappropriate for Linux-specific features

Final Conclusions and Open Questions

This week's discussion produced one clear conclusion:

  1. pynfs is ruled out as a testing framework for signed filehandles, because it targets protocol compliance rather than Linux-specific implementation features. An alternative testing framework must be identified.

Several open questions remain for v3 of the series:

  • Testing framework: What alternative to pynfs should host tests for sign_fh transitions and key change scenarios?
  • FH_AT_MAC retention: The auth type flag remains in the design pending Wireshark patches and clearer justification for its value beyond debugging packet captures
  • Security architecture: Whether NFSD should rely on the sign_fh export option alone (server-side policy) rather than also inspecting the incoming filehandle's auth type flag

Significance for NFS Client Development

While this thread focuses on server-side changes, signed filehandles have direct implications for NFS client developers:

  • Clients will need to handle larger filehandles (with appended 8-byte MAC signatures), potentially approaching or exceeding NFSv3's 64-byte maximum
  • The -ESTALE response behavior when export options change between signed and unsigned modes affects client-side caching and retry logic
  • The lack of a standardized testing framework means client interoperability with signed filehandle servers may need to be validated through ad-hoc testing rather than automated regression suites
