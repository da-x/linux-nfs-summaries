NFS Container Mounts and FS_USERNS_DELEGATABLE: Resolving User Namespace Restrictions

Summary

NFS Mounting in Containers Blocked by User Namespace Restrictions — FS_USERNS_DELEGATABLE Proposed as Solution

Classification

Type: Kernel filesystem subsystem policy change with direct impact on NFS client behavior in containers (bug fix / security hardening discussion).

Overview

A long-standing thread dating back to July 2024, originally initiated by Seth Forshee (DigitalOcean) regarding a patch titled "[PATCH] fs: don't allow non-init s_user_ns for filesystems without FS_USERNS_MOUNT," saw renewed activity this week. The core issue is a security hardening proposal that would restrict which filesystems can be mounted with a non-initial user namespace (s_user_ns). For NFS, this has significant implications for container-based deployments where privileged daemons in the init namespace assist unprivileged containers in performing mounts.

This week's discussion, occurring on January 29, 2026, centers on how to reconcile the security goal of restricting arbitrary filesystem mounts in user namespaces with the practical needs of NFS container workflows that rely on a trusted daemon model.

Background (Brief)

The original patch by Seth Forshee addressed an observation by Christian Brauner: it was possible for a privileged user to mount most filesystems with a non-initial user namespace in sb->s_user_ns, even for filesystems that do not set the FS_USERNS_MOUNT flag. The proposed fix would prevent this, tightening the security boundary around which filesystems can be mounted inside unprivileged user namespaces.

This Week's Discussion

Jeff Layton: NFS Container Mount Workflow Broken by Proposed Restriction

Jeff Layton raised a critical concern that the proposed restriction would break NFS mounting in containers for his organization:

"this patch breaks NFS mounting in containers for us, as the prohibited activity is exactly the process we use to do them."

He described their container NFS mount architecture in detail:

"We basically have a task in the container do an fsopen() and then pass the fd to a daemon in the init namespace via unix socket. The daemon vets the NFS mount parameters (ensuring that the mount options are sane, and that we trust the server), and then does the mount inside the container."

This is a well-known pattern — sometimes called the "mountfsd model" — where an unprivileged process initiates a mount operation via fsopen(), but the actual mount completion is performed by a trusted privileged daemon. This allows fine-grained policy enforcement: the daemon can validate server identity, mount options, and other security-sensitive parameters before allowing the mount to proceed.

Layton then articulated the core tension for NFS specifically:

"We don't want to set FS_USERNS_MOUNT on NFS, because that would give the container carte blanche to mount anything it likes, even a malicious server."

The concern is clear: setting FS_USERNS_MOUNT on NFS would allow any unprivileged user in a container to mount arbitrary NFS shares without any oversight. This could expose containers to malicious NFS servers or misconfigured mounts. However, the proposed patch would block the daemon-assisted workflow entirely, since it prohibits non-init s_user_ns for filesystems lacking FS_USERNS_MOUNT.

Layton proposed splitting the flag into two distinct concepts:

"Do we need to split that flag into two? Maybe FS_USERNS_SAFE and FS_USERNS_MOUNT?"

This would distinguish between filesystems that are safe to mount in user namespaces (from a kernel security perspective) and those that can be freely mounted by unprivileged users without daemon assistance.

Christian Brauner: FS_USERNS_DELEGATABLE as the Solution

Christian Brauner responded directly to Layton's concern, identifying the workflow and offering a concrete solution:

"The mountfsd model - kinda."

He then proposed using an existing mechanism rather than introducing new flags:

"I think you can simply add FS_USERNS_DELEGATABLE and raise it for nfs."

The FS_USERNS_DELEGATABLE flag is part of the modern open/fsmount API infrastructure. It indicates that a filesystem supports delegation — i.e., a file descriptor from fsopen() can be passed across namespace boundaries (e.g., via Unix socket) to a privileged process that then completes the mount on behalf of the unprivileged caller. This precisely matches the workflow Layton described.

Key Technical Arguments

  1. Security vs. Practicality: The original patch aims to close a security gap where filesystems without FS_USERNS_MOUNT can still be mounted with non-init user namespaces. However, this breaks legitimate use cases for NFS in containers that rely on the daemon-assisted mount model.

  2. NFS Cannot Use FS_USERNS_MOUNT: Unlike some other filesystems, NFS cannot simply set FS_USERNS_MOUNT because doing so would allow unprivileged users to mount arbitrary remote servers without any policy enforcement — a significant security risk.

  3. FS_USERNS_DELEGATABLE as the Middle Ground: Brauner's suggestion of using FS_USERNS_DELEGATABLE provides a mechanism for NFS to support container mounts via the delegation model (trusted daemon completes the mount) while still preventing unprivileged users from independently mounting arbitrary NFS shares.

Evolution of the Discussion

The thread has been ongoing since July 2024, with this week's exchange representing a pivotal moment where:

  • The practical impact on NFS container deployments was clearly articulated by Layton.
  • A concrete resolution path was proposed by Brauner using existing kernel infrastructure (FS_USERNS_DELEGATABLE).

Final Conclusions

The discussion concluded with Brauner's recommendation to use FS_USERNS_DELEGATABLE for NFS, which would:

  1. Allow the daemon-assisted mount workflow (fsopen + Unix socket delegation) to continue functioning in containers.
  2. Prevent unprivileged users from independently mounting arbitrary NFS shares.
  3. Maintain the security hardening goals of the original patch without breaking legitimate container use cases.

No further messages were posted this week, but this exchange sets up a clear path forward for NFS client development: adding FS_USERNS_DELEGATABLE to the NFS filesystem type would enable continued support for secure, policy-enforced NFS mounts in containers while respecting the kernel's user namespace security boundaries.

Significance for NFS Client Development

This discussion is directly relevant to NFS client developers working on container support:

  1. Container mount workflows: Organizations using the daemon-assisted fsopen() pattern for NFS mounts in containers need to ensure their setup is compatible with the evolving user namespace restrictions. The FS_USERNS_DELEGATABLE flag will be the mechanism that enables this workflow going forward.

  2. Flag semantics: Understanding the distinction between FS_USERNS_MOUNT (unrestricted unprivileged mounting) and FS_USERNS_DELEGATABLE (delegation via trusted daemon) is essential for designing secure NFS container architectures.

  3. Upstream changes: NFS client maintainers should track whether and when FS_USERNS_DELEGATABLE is added to the NFS filesystem type, as this will be required for container mount support under the tightened security model.
