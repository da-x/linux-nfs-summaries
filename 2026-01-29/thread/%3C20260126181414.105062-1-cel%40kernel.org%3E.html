bio_vec RDMA API v4: MR Structure Placement Debate Continues After Iterator and Refactoring Fixes

Summary

bio_vec RDMA API v4: Christoph Hellwig's MR Placement Concern Persists

Summary

Type: New feature / API addition with an important bug fix (Send Queue sizing)

This thread covers version 4 of Chuck Lever's five-patch series introducing a bio_vec-based RDMA read/write API to the Linux kernel's RDMA core subsystem. The v4 iteration addresses review feedback from Christoph Hellwig on iterator conventions and memory registration (MR) code refactoring, though one substantive concern about MR structure layout remains unresolved.

Context from Prior Weeks

This series has evolved through multiple iterations:

  • v1: Initial submission with basic bvec API support
  • v2: Added bvec iterators, synthetic SGL for MR mapping, and IOVA coalescing improvements
  • v3 (prior summary): Received thorough review from Hellwig, Zhu Yanjun, and Jason Gunthorpe. Key feedback included iterator consumption conventions, MR code duplication concerns, and a clean Reviewed-by for the SQ sizing bug fix.

Chuck Lever committed to posting v4 incorporating this feedback:

"I added a helper that refactors out the common logic. But I did that a few days ago and all of the context has dribbled out of my brain. I'll post a v4 soon, and we can continue from there." [id://38f7282c-31a6-4edf-8d5c-0d08b401f1f5@app.fastmail.com]

This Week's Activity: v4 Submission and Continued Review

Chuck Lever posted the v4 series on January 26, documenting two key changes:

"Changes since v3:

  • Remove the local iter from rdma_rw_init_iova_wrs_bvec()
  • Refactor common per-MR handling into a helper" [id://20260126181414.105062-1-cel@kernel.org]

Patch 1/5: bio_vec RDMA API — Clean Reviewed-by Retained

PATCH v4 1/5 introduces rdma_rw_ctx_init_bvec() and rdma_rw_ctx_destroy_bvec(), accepting bio_vec arrays directly without intermediate scatterlist conversion. This patch carries Christoph Hellwig's Reviewed-by tag from the v3 cycle, with no new objections raised.

Patch 2/5: IOVA-based DMA Mapping — Reviewed-by Granted

PATCH v4 2/5 implements the two-step IOVA API (dma_iova_try_alloc / dma_iova_link / dma_iova_sync) to reduce IOTLB synchronization from O(n) per-page flushes to a single O(1) sync. This addresses Hellwig's earlier concern about iterator conventions — Lever removed the local link_iter copy and now consumes the iterator directly, following block layer patterns.

Hellwig responded promptly:

"Looks good: Reviewed-by: Christoph Hellwig hch@lst.de" [id://20260127053843.GA24998@lst.de]

Patch 3/5: MR Support — Substantive Concern Persists

PATCH v4 3/5 adds rdma_rw_init_mr_wrs_bvec() for Memory Registration support on bvec arrays, enabling iWARP devices and the force_mr debug parameter to use the bvec path. Lever refactored common per-MR handling into a shared helper as Hellwig requested.

However, Hellwig's structural concern about the placement of the synthetic scatter table (sgt) remains unresolved:

"I still don't understand why the sgt is not in struct rdma_rw_reg_ctx. Right now that is allocate a little bit later than the sgt initialization and freed a tiny bit to early, but that seems to be easy to fix." [id://20260127054235.GB24998@lst.de]

"Doing so would reduce the memory usage for the common non-registration path, and significantly reduce the churn in the patch." [id://20260127054235.GB24998@lst.de]

This is the same concern Hellwig raised during v3 review. The issue is architectural: currently, the sgt field lives outside struct rdma_rw_reg_ctx, meaning it's allocated even when MR registration isn't needed. Moving it inside the reg structure would reduce memory overhead for the common non-MR path but requires careful timing of allocation and cleanup.

Patch 4/5: SQ Sizing Bug Fix — Reviewed-by Retained

PATCH v4 4/5 introduces rdma_rw_max_sge() to correctly compute Send Queue entry requirements when memory registration is active. This fixes a critical bug where the Send CQ and credit pool were undersized relative to the QP's actual capacity:

"when the device uses memory registration for RDMA operations, rdma_rw_init_qp() inflates the QP's max_send_wr by a factor of three per context to account for REG and INV work requests. The Send CQ and credit pool remain sized for only one work request per context, causing Send Queue exhaustion under heavy NFS WRITE workloads." [id://20260126181414.105062-5-cel@kernel.org]

This patch carries Hellwig's Reviewed-by tag and includes a Fixes: tag pointing to commit 00bd1439f464.

Patch 5/5: svcrdma Conversion — No New Review This Week

PATCH v4 5/5 converts the NFS server-side RDMA transport (svcrdma) to use the new bvec API, eliminating scatterlist conversion overhead and simplifying svc_rdma_rw_ctxt by removing chained SG table management.

Key Technical Arguments

Performance Rationale

The series is motivated by both performance and architectural cleanliness. As Lever explained during v3 review:

"Performance tests are difficult to evaluate because I don't have a multi-client set-up here to drive a heavy workload, plus filesystems bottleneck long before the network transport does. The changes are designed to improve scalability (eg lower CPU utilization for the same workload and less interaction between host and RNIC) more than improve raw throughput." [id://d67a30a0-5ff1-4e97-b916-6bd59ffe769a@linux.dev]

Broader Architectural Vision

Jason Gunthorpe endorsed the kernel-wide scatterlist elimination goal:

"I haven't imagined tree wide, but I am envisioning a world where a modern server runs all its primary IO paths without using scatterlist." [id://20260126171319.GO1134360@nvidia.com]

Evolution of the Discussion

The discussion this week was concise compared to last week's extensive review:

  1. Jan 26: Lever posts v4 with two targeted changes (iterator fix, MR refactoring)
  2. Jan 27: Hellwig grants Reviewed-by on patches 2/5 and 3/5, but reiterates his concern about sgt placement in the MR structure

The remaining blocker is architectural rather than functional: Hellwig wants the synthetic scatter table moved inside struct rdma_rw_reg_ctx to reduce memory overhead for the common non-MR path. Lever will need to address this timing-sensitive allocation issue in v5.

Significance for NFS Client Development

While this series primarily targets the NFS server side (svcrdma), it has important implications:

  1. Send Queue sizing bug fix (patch 4/5): Prevents Send Queue exhaustion on NFS servers under heavy WRITE workloads with memory registration enabled — a correctness issue that affects client-side reliability when using iWARP or force_mr.

  2. Scalability improvements: Eliminating scatterlist conversions reduces CPU overhead and IOTLB synchronization costs, benefiting large compound NFS operations from the server side.

  3. API direction: The kernel-wide push toward bio_vec over scatterlists may eventually influence NFS client RDMA code paths (pnfs/blocklayout) as those subsystems evolve.

Final Status

As of this week's window close, patches 1/5, 2/5, and 4/5 carry clean Reviewed-by tags from Christoph Hellwig. Patch 3/5 requires further iteration to address the sgt placement concern. A v5 is expected once Lever addresses this remaining architectural feedback.
