pNFS Ghost Write Scenario: Open Question on Handling Duplicate Writes

Summary

pNFS Ghost Write Scenario: An Open Question from VastData

This week, Roi Azarzar of VastData opened a discussion on handling a tricky edge case in parallel NFS (pNFS) — the "ghost writes" scenario. As of this writing, the thread has received no replies.

The Problem

Azarzar described a race condition that can arise during pNFS write operations when a client interacts with both a Data Server (DS) and a Metadata Server (MDS). The scenario unfolds as follows:

  1. Client writes to the DS and receives a Transfer Error (TO).
  2. Client resends the write to the MDS.
  3. After some delay, the server eventually executes the first (original) write.

"We can handle it with some barrier and such but we are wondering if there is any pNFS semantic that we are missing to handle such a scenario (without session trunking support)." Roi Azarzar

Classification

This discussion centers on a protocol semantic question rather than a straightforward bug fix. Azarzar's team is implementing pNFS support and is probing whether the existing NFS protocol specification provides guidance for handling this edge case, or whether server-side implementation workarounds (such as barriers) are necessary.

Key Technical Points

  • The scenario involves pNFS layout-based writes where data is written directly to a Data Server (DS), bypassing the Metadata Server (MDS).
  • When a Transfer Error occurs on the DS write, the client falls back to resending via the MDS — but the original DS write may still be pending execution.
  • The concern is about duplicate or out-of-order writes reaching the server, potentially causing data corruption or inconsistency.
  • Azarzar specifically notes this is being considered without session trunking support, which could otherwise help mitigate such issues by providing stronger ordering guarantees across connections.

Status and Outlook

With only one message in the thread so far, no consensus or resolution has emerged. The question remains open: does the pNFS protocol already define semantics sufficient to handle ghost writes, or do server implementers need to rely on custom barrier mechanisms?

This is an important consideration for any NFS server implementing pNFS data servers, as it touches on correctness guarantees in failure scenarios. Watch this thread for responses from core NFS developers such as Trond Myklebust or Christoph Hellwig, who have deep expertise in pNFS semantics.
