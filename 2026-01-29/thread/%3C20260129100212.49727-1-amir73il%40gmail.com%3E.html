nfsd: Prevent Exporting Special Kernel Filesystems (pidfs, nsfs) — v4 Applied

Overview

Amir Goldstein submitted version 4 of a two-patch bug-fix series (PATCH v4 0/2) to prevent the NFS server (nfsd) from exporting special kernel filesystems — specifically pidfs and nsfs — which recently gained file handle support for local use via name_to_handle_at(2)/open_by_handle_at(2) but are fundamentally unsuitable for NFS export.

This series is classified as a bug fix, addressing a compatibility gap between the VFS export operations subsystem and nfsd's expectations. The patches were reviewed by Jeff Layton and Chuck Lever, and applied to the vfs-7.0.misc branch by Christian Brauner within the same day of submission.

Background: The Broader Problem

This thread is part of an ongoing effort to prevent special kernel filesystems from being inadvertently exported via NFS. As documented in prior weeks (prior summary on stable-handle exports), Jeff Layton proposed a comprehensive 29-patch series introducing EXPORT_OP_STABLE_HANDLES to require filesystems to explicitly opt in to NFS export. That broader approach sparked extensive debate about terminology ("stable" vs. "persistent") and filesystem-specific edge cases (FUSE, overlayfs).

Amir Goldstein's v4 series takes a more targeted approach: rather than requiring all filesystems to opt in, it blocks specific filesystems that are known to be incompatible with nfsd due to their custom ->open() and ->permission() export operations. As Amir explained in the cover letter:

"pidfs and nsfs recently gained support for encode/decode of file handles via name_to_handle_at(2)/open_by_handle_at(2). These special kernel filesystems have custom ->open() and ->permission() export methods, which nfsd does not respect and it was never meant to be used for exporting those filesystems by nfsd."

Patch 1/2: Documentation Clarification

PATCH v4 1/2 updates the kernel-doc comments in include/linux/exportfs.h to clarify that the ->open() and ->permission() methods of struct export_operations are intended for the open_by_handle_at(2) system call only, and are not compatible with nfsd. This documentation patch is applicable to the vfs-7.0.misc tree's doc updates.

The patch carries Jeff Layton's Reviewed-by tag from prior review cycles.

Patch 2/2: The Core Fix — Block Export of Special Filesystems

PATCH v4 2/2 implements the actual guard in fs/nfsd/export.c. The fix prevents nfsd from exporting any filesystem that has custom ->open() or ->permission() export methods, as these are indicators of special kernel filesystems with non-standard file handle semantics.

The patch includes two Fixes: tags:

  • Fixes: b3caba8f7a34a ("pidfs: implement file handle support")
  • Fixes: 5222470b2fbb3 ("nsfs: support file handles")

This approach is intentionally narrow and surgical — it blocks only filesystems that exhibit the specific incompatibility pattern (custom export operations), rather than requiring all filesystems to explicitly declare their NFS export readiness. As Amir noted in the cover letter:

"The 2nd fix patch is independent of the doc changes in vfs-7.0.misc, so it should be easier to backport."

Significance for NFS Client Development

While this fix is primarily an nfsd (server-side) concern, it has important implications for NFS clients:

  1. Prevention of stale file handle errors: Without this guard, a user could inadvertently export pidfs or nsfs via NFS, leading to unpredictable behavior and stale file handle errors for NFS clients attempting to access these exports. The special kernel filesystems' file handles are not stable across reboots and use custom semantics incompatible with NFS protocol expectations.

  2. Security hardening: Preventing the export of kernel-internal filesystems reduces the attack surface. As noted in prior discussions, exporting /sys or similar kernel filesystems through a network service like NFS is inherently risky:

    "Could you end up exporting /sys if it's bind mounted into a container somewhere? Bear in mind that exportfs does allow mountpoint crossing, etc. nfsd is a network service, so I think the kernel needs to be quite conservative about what filehandles it can access."

  3. Complementary approach: This targeted fix complements Jeff Layton's broader EXPORT_OP_STABLE_HANDLES opt-in series (still under discussion). Amir's approach provides an immediate safety net for known-bad filesystems, while the opt-in mechanism would provide a more comprehensive long-term solution.
