NFS: Make NFS v4.0 KConfig-urable (v2)

Summary

Anna Schumaker submitted version 2 of her 14-patch series to make NFS v4.0 support optional via Kconfig, a significant architectural reorganization of the NFS client codebase aimed at eventual deprecation of the oldest NFSv4 minor version. The v2 series addresses feedback from the v1 submission last week by additionally KConfig-gating NFS v4.0-only XDR operations and fixing a kernel test robot build warning.

Background and Motivation

The desire to deprecate NFS v4.0 originated from discussions at the October Bake-a-thon the previous year. In her cover letter, Anna wrote:

"A desire to deprecate NFS v4.0 came up as a discussion topic during the October Bake-a-thon last year. This patchset takes the first step by moving NFS v4.0 only code into new files prefixed with 'nfs40' and introducing a KConfig option to compile without NFS v4.0 support."

She further explained the rationale for promoting v4.1:

"At the same time, I promote NFS v4.1 to be the default NFSv4 minorversion included in the kernel to prevent the situation where we have NFS v4 enabled without any minor versions."

Classification

This is a code refactoring and new feature effort — not a bug fix or protocol change. The series restructures the NFS client codebase to enable compile-time exclusion of NFS v4.0 support, while promoting NFS v4.1 as the baseline NFSv4 implementation.

Changes in v2

Compared to last week's v1 submission, Anna noted two improvements:

"Changes in v2:

  • KConfig-out NFS v4.0-only operations from nfs4xdr.c
  • Fix a kernel test robot build warning"

These changes extend the conditional compilation coverage into the XDR layer (nfs4xdr.c), ensuring that v4.0-specific encoding/decoding functions are also excluded when v4.0 support is disabled, and address an automated build warning flagged by the kernel test robot.

Patch Series Overview (v2)

The 14-patch series touches 30 files with 902 insertions and 1,122 deletions, creating two new source files (nfs40client.c and nfs40proc.c) and a new header (nfs40.h). The patches fall into three broad categories:

1. Code Extraction (Patches 01–10)

The first ten patches systematically extract NFS v4.0-specific code from shared files (nfs4client.c, nfs4proc.c, nfs4state.c) into the new nfs40* files:

  • Patch 01 Move nfs40_call_sync_ops into nfs40proc.c: Creates nfs40.h and nfs40proc.c, moving the sync operations entry point. Anna described this as "the first step in extracting NFS v4.0 into its own set of files that can be disabled through Kconfig."
  • Patch 02 Split out nfs40_reboot_recovery_ops into nfs40client.c: Creates nfs40client.c and moves reboot recovery operations (188 lines added to the new file).
  • Patch 03 Split out nfs40_nograce_recovery_ops into nfs40proc.c: Moves nograce recovery operations.
  • Patch 04 Split out nfs40_state_renewal_ops into nfs40proc.c: Moves state renewal operations (100 lines to nfs40proc.c).
  • Patch 05 Split out nfs40_mig_recovery_ops to nfs40proc.c: Moves migration recovery operations (101 lines).
  • Patch 06 Move NFS v4.0 minor version ops into nfs40proc.c: Relocates the v4.0 minor version operations structure (106 lines to nfs40proc.c, 115 lines removed from nfs4proc.c).
  • Patch 07 Make NFS v4.0 operations static again: After extraction, the v4.0 functions can be made static since they're no longer referenced outside their new files.
  • Patch 08 Move nfs40_shutdown_client into nfs40client.c: Moves client shutdown logic.
  • Patch 09 Move nfs40_init_client into nfs40client.c: Moves client initialization.
  • Patch 10 Move NFS v4.0 pathdown recovery into nfs40client.c: Moves path-down recovery operations.

2. Architectural Refactoring (Patches 11–12)

These patches introduce structural changes to support the v4.0/v4.1+ separation:

  • Patch 11 Pass a struct nfs_client to nfs4_init_sequence(): Anna noted this has "No functional change" — it simply prepares for the next patch by passing struct nfs_client to nfs4_init_sequence(), enabling sequence slot operations to be differentiated per minor version.
  • Patch 12 Move sequence slot operations into minorversion operations: Moves sequence slot management (setup, teardown, free) into the minor version operations structure, allowing v4.0 and v4.1+ to have different implementations. This is a key architectural change enabling clean separation of compound/session semantics from basic v4.0 behavior.

3. Kconfig Integration (Patches 13–14)

The final two patches implement the compile-time configuration:

  • Patch 13 Add a way to disable NFS v4.0 via KConfig: Introduces NFS4_MIN_MINOR_VERSION as a parallel to NFS4_MAX_MINOR_VERSION, allowing the kernel to check whether NFS v4.0 has been compiled in and return an appropriate error if not. This patch also adds KConfig gating for v4.0-only XDR operations in nfs4xdr.c (a v2 improvement).
  • Patch 14 Merge CONFIG_NFS_V4_1 with CONFIG_NFS_V4: The capstone patch. Anna explained:

"Compiling the NFSv4 module without any minorversion support doesn't make much sense, so this patch sets NFS v4.1 as the default, always enabled NFS version allowing us to replace all the CONFIG_NFS_V4_1s scattered throughout the code with CONFIG_NFS_V4."

This patch removes 371 lines and adds 35, eliminating CONFIG_NFS_V4_1 entirely in favor of making v4.1 the baseline when CONFIG_NFS_V4 is enabled.

Key Technical Arguments

The core architectural insight is that NFS v4.0 lacks several features present in v4.1+ (sessions, slots, compound operations with sequence frames). By extracting v4.0-specific recovery paths (reboot, nograce, migration, state renewal), client lifecycle management (init, shutdown, pathdown), and sequence slot operations into dedicated files, the codebase can cleanly conditionally compile v4.0 support.

The introduction of NFS4_MIN_MINOR_VERSION provides a symmetric counterpart to NFS4_MAX_MINOR_VERSION, enabling range-based checks for supported minor versions at runtime. The v2 addition of KConfig-gating in nfs4xdr.c ensures that XDR encoding/decoding functions are also properly excluded, completing the isolation of v4.0 code paths.

Discussion Status

This is a v2 submission with no replies as of this week's cutoff. The series was submitted on January 26 and has not yet received review feedback from other NFS developers. Given that v1 was submitted last week (January 16) with similar lack of immediate replies, this appears to be an ongoing iteration process. Anna explicitly invited community feedback in her cover letter:

"Thoughts? Anna"

Conclusion

This v2 series represents a significant architectural reorganization of the NFS client, laying groundwork for eventual NFS v4.0 deprecation. The v2 improvements — extending KConfig gating into the XDR layer and fixing an automated build warning — demonstrate responsiveness to tooling feedback and a more thorough approach to conditional compilation. By making v4.1 the default and enabling compile-time exclusion of v4.0, distributions and embedded systems can reduce code footprint while modernizing their NFS client support. The methodical approach — extracting code first, then adding configuration controls — minimizes risk of introducing regressions during this substantial refactoring effort.
