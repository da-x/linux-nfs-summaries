Build Failures Expose Hidden Header Dependencies in NFS Client During lockd API Cleanup

Summary

Build Failures Reported for lockd Header Relocation Patch

Type: Bug fix (build breakage caused by API refactoring)

Overview

This thread consists of two automated build failure reports from the kernel test robot (lkp@intel.com) against PATCH v2 10/42 of Chuck Lever's 42-patch series to clarify lockd module API boundaries. The patch in question moves xdr.h from include/linux/lockd/ to fs/lockd/, effectively removing it from the public header surface. This relocation inadvertently exposed a pre-existing dependency in the NFS client code that relied on definitions previously accessible through this now-internalized header.

Context from Prior Summary

As detailed in the prior week's summary of the cover letter thread, Chuck Lever's series aims to separate lockd's public API from internal implementation details (patches 01–13) and modernize NLMv4 XDR handling using xdrgen (patches 14–42). Patch 10/42 is part of the header relocation effort, moving xdr.h — an internal lockd XDR header — out of the public include path.

Key Technical Arguments

Build Errors on Alpha and Hexagon Architectures

The kernel test robot reported two distinct build failures on different architectures and compilers:

Alpha (GCC 15.2.0):

"fs/nfs/nfs3proc.c:1009:15: error: invalid use of undefined type 'struct file_lock'" kernel test robot

"fs/nfs/nfs3proc.c:1009:31: error: 'FL_CLOSE' undeclared (first use in this function); did you mean 'OP_CLOSE'?" kernel test robot

Hexagon (Clang 22.0.0git):

"fs/nfs/nfs3proc.c:1009:8: error: incomplete definition of type 'struct file_lock'" kernel test robot

"fs/nfs/nfs3proc.c:1009:24: error: use of undeclared identifier 'FL_CLOSE'; did you mean 'OP_CLOSE'?" kernel test robot

Both reports point to the same problematic line in fs/nfs/nfs3proc.c at line 1009, within the nfs3_proc_lock() function:

if (fl->c.flc_flags & FL_CLOSE) {

This code dereferences struct file_lock internals and references the FL_CLOSE flag — both of which were previously accessible through headers transitively included via include/linux/lockd/xdr.h. With that header moved to fs/lockd/, these definitions are no longer available to the NFS client source file.

Significance for NFS Client Development

This build failure highlights a layering violation in the NFS client: code in nfs3proc.c was depending on internal lockd headers to access struct file_lock and related locking constants. This is precisely the kind of implicit API contract that Chuck Lever's series seeks to eliminate. The error reveals that the NFS client needs its own proper includes for file locking definitions rather than relying on transitive inclusion through lockd's public headers.

Evolution of the Discussion

This thread contains only automated reports from the kernel test robot, with no human responses during this week's window. The two messages are near-identical in content, differing only in architecture (alpha vs. hexagon) and compiler (GCC vs. Clang). Both serve as actionable bug reports that Chuck Lever will need to address before the series can be merged.

Final Conclusions

The build failures reported here indicate that:

  1. Patch 10/42 requires a companion fix for the NFS client side. The fs/nfs/nfs3proc.c file needs to include the appropriate headers directly (likely include/linux/fs.h or another header that fully defines struct file_lock and FL_CLOSE) rather than relying on transitive inclusion through lockd's now-internalized xdr.h.

  2. This is a pre-existing dependency, not a new bug introduced by the patch. The code in nfs3proc.c was already depending on these definitions; the patch merely removed the implicit include path that was masking the missing explicit includes.

  3. The fix should be straightforward: adding the correct #include directives to fs/nfs/nfs3proc.c (and potentially other NFS client files with similar dependencies) before or alongside patch 10/42.

These automated reports underscore the value of cross-architecture CI testing in uncovering hidden header dependencies that may not manifest on more commonly tested configurations.
