overlayfs: uuid=off Cross-Filesystem Support for SteamOS Cloned Images

Summary

This week's activity on the overlayfs origin file handle discussion centered on testing and refining Amir Goldstein's patch to extend the uuid=off mount option to support cross-filesystem setups. The thread, which originated from André Almeida's rejected 3-patch series targeting btrfs cloned images for SteamOS A/B partitioning, has now converged on a pragmatic overlayfs-level solution rather than modifying exportfs infrastructure or btrfs UUID semantics.

Background (Brief)

Over the prior two weeks, Almeida's approach of repurposing export_operations::get_uuid() was rejected by Christoph Hellwig, who argued that the mechanism serves pNFS block layout exclusively and should not be spread further [id://20260114131130.GA6967@lst.de]. The discussion pivoted toward overlayfs's existing uuid=off mount option — originally created for Virtuozzo container disk copying — as a more suitable mechanism. However, uuid=off required all lower/upper/work directories to reside on the same filesystem, which did not match the SteamOS setup. By last week's end, Amir Goldstein had tested a patch lifting this restriction and offered to queue it for kernel 7.0 [id://CAOQ4uxg6dKr4XB3yAkfGd_ehZkBMcoNHiF5CeB9=3aca44yHRg@mail.gmail.com].

Key Technical Arguments This Week

André Almeida: Initial Testing and a Bug Report

Almeida began testing the patch on Jan 23, initially reporting that it was not working in his setup. After debugging, he identified a mismatch in UUID handling within ovl_verify_fh():

"So, your patch wasn't initially working in my setup here, and after some debugging it turns out that on ovl_verify_fh() *fh would have a NULL UUID, but *ofh would have a valid UUID, so the compare would then fail." [id://8ab387b1-c4aa-40a5-946f-f4510d8afd02@igalia.com]

He proposed a fix in ovl_get_fh() to explicitly set the file handle UUID to null when uuid=off is active:

+       if (!ovl_origin_uuid(ofs))
+               fh->fb.uuid = uuid_null;

Amir Goldstein: Clarifying the Purpose of uuid=off

Goldstein responded firmly on Jan 24, rejecting Almeida's proposed fix and clarifying a fundamental misunderstanding about how uuid=off is intended to work:

"It does not make sense to me. I think you may be using the uuid=off feature in the wrong way. What you did was to change the stored UUID, but this NOT the purpose of uuid=off." [id://CAOQ4uxiRpwuyfj_Wy3Zj+HAi+jgQOq8nPQK8wmn6Hgsz-9i1fw@mail.gmail.com]

Goldstein emphasized that uuid=off is not designed to migrate existing overlayfs mounts from one UUID scheme to another:

"The purpose of uuid=off is NOT to allow mounting an overlayfs that was previously using a different lower UUID. The purpose is to mount overlayfs the from the FIRST time with uuid=off so that ovl_verify_origin_fh() gets null uuid from the first call that sets the ORIGIN xattr." [id://CAOQ4uxiRpwuyfj_Wy3Zj+HAi+jgQOq8nPQK8wmn6Hgsz-9i1fw@mail.gmail.com]

In other words, if a user expects the underlying lower layer UUID to change (as with btrfs cloned images), they must declare this intent from the very first mount. Otherwise, overlayfs assumes an unintentional misconfiguration:

"IOW, if user want to be able to change underlying later UUID user needs to declare from the first overlayfs mount that this is expected to happen, otherwise, overlayfs will assume that an unintentional wrong configuration was used." [id://CAOQ4uxiRpwuyfj_Wy3Zj+HAi+jgQOq8nPQK8wmn6Hgsz-9i1fw@mail.gmail.com]

Goldstein also provided a documentation patch to clarify this behavior in the overlayfs mount options.

Amir Goldstein: Follow-Up and Stable Kernel Considerations

On Jan 28, Goldstein followed up with Almeida, requesting feedback so he could proceed with queuing the change for kernel 7.0:

"Sorry to nag you, but if you'd like me to queue the suggested change to 7.0, I would need your feedback soon." [id://CAOQ4uxhHFvYNAgES9wpM_C-7GvfwXC2xet1ensfeQOyPJRAuNQ@mail.gmail.com]

He also noted his stance on stable kernel backporting:

"FWIW, I think that this change of restrictions for uuid=null could be backported to stable kernels, but I am not going to mark it for auto select, because I'd rather see if anyone shouts with upstream kernel first when (if) we make this change and manually backport later per demand." [id://CAOQ4uxhHFvYNAgES9wpM_C-7GvfwXC2xet1ensfeQOyPJRAuNQ@mail.gmail.com]

Evolution of the Discussion

The week unfolded in three stages:

  1. Jan 23 (morning): Almeida reported he was still testing the patch and would provide feedback [id://ee38734b-c4c3-4b96-8ff2-b4ce5730b57c@igalia.com].

  2. Jan 23 (evening): After further debugging, Almeida reported that the patch did not work in his setup due to a UUID comparison mismatch and proposed an additional fix [id://8ab387b1-c4aa-40a5-946f-f4510d8afd02@igalia.com].

  3. Jan 24: Goldstein clarified that Almeida was misusing uuid=off — the option must be enabled from the first mount, not retroactively applied — and provided documentation improvements [id://CAOQ4uxiRpwuyfj_Wy3Zj+HAi+jgQOq8nPQK8wmn6Hgsz-9i1fw@mail.gmail.com].

  4. Jan 28: Goldstein followed up, seeking confirmation to queue the patch for kernel 7.0 and outlining his backporting philosophy [id://CAOQ4uxhHFvYNAgES9wpM_C-7GvfwXC2xet1ensfeQOyPJRAuNQ@mail.gmail.com].

Final Conclusions

This week's activity refined the understanding of how uuid=off should be used in the SteamOS cloned-image scenario:

  1. uuid=off must be declared from the first mount. The option is not designed to migrate existing overlayfs mounts between different UUID schemes. Users expecting underlying filesystem UUID changes must enable uuid=off from the initial mount [id://CAOQ4uxiRpwuyfj_Wy3Zj+HAi+jgQOq8nPQK8wmn6Hgsz-9i1fw@mail.gmail.com].

  2. The cross-filesystem restriction lift is pending user confirmation. Goldstein's patch to allow uuid=off with upper and lower layers on different filesystems has been tested internally but awaits Almeida's final validation for the SteamOS use case [id://CAOQ4uxhHFvYNAgES9wpM_C-7GvfwXC2xet1ensfeQOyPJRAuNQ@mail.gmail.com].

  3. The patch is earmarked for kernel 7.0, with potential stable backports. Goldstein indicated the change could be backported to stable kernels but prefers manual backporting based on demand rather than automatic selection [id://CAOQ4uxhHFvYNAgES9wpM_C-7GvfwXC2xet1ensfeQOyPJRAuNQ@mail.gmail.com].

  4. Documentation has been improved. Goldstein provided a patch clarifying the semantics of uuid=off in the overlayfs mount options documentation [id://CAOQ4uxiRpwuyfj_Wy3Zj+HAi+jgQOq8nPQK8wmn6Hgsz-9i1fw@mail.gmail.com].

Classification

NFS Client Relevance: Indirect — while not an NFS client change, the discussion touches on file handle encoding semantics foundational to NFS exports and the exportfs subsystem. The original get_uuid() infrastructure served pNFS block layout, and Hellwig previously noted that "encoding the uuid into the file handle in the kernel is the right thing for NFS as well" [id://20260115063630.GA9671@lst.de].
