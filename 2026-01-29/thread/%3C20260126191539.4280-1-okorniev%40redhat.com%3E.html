pNFS: Fix Missing Wake-Up on NFS_LAYOUT_DRAIN Race Condition

Summary

pNFS: Fix a Missing Wake-Up While Waiting on NFS_LAYOUT_DRAIN

Overview

This week, Olga Kornievskaia (Red Hat) submitted a bug fix for a subtle race condition in the parallel NFS (pNFS) client code that could cause tasks to hang indefinitely. The patch addresses a missing wake-up scenario when waiting on the NFS_LAYOUT_DRAIN bit flag in layout state management.

Classification

  • Type: Bug fix
  • Component: NFS client — pNFS layout handling (fs/nfs/pnfs.c)
  • Fixes commit: 880265c77ac4 ("pNFS: Avoid a live lock condition in pnfs_update_layout()")

The Problem

Kornievskaia describes a race window across multiple CPUs that can lead to tasks sleeping forever:

"It is possible to have a task get stuck on waiting on the NFS_LAYOUT_DRAIN in the following scenario"

The sequence unfolds as follows:

  1. CPU A: A waiter tests NFS_LAYOUT_DRAIN (set) and plh_outstanding (non-zero).
  2. CPU B: atomic_dec_and_test() clears the bit and issues a wake-up.
  3. CPU C: Sets NFS_LAYOUT_DRAIN again.
  4. CPU A: Calls wait_on_bit() and sleeps forever, since it missed the wake-up from step 2 and will not receive one for the re-set in step 3.

Kornievskaia provides a concrete scenario to illustrate this: two outstanding pNFS write I/O operations receive an ESTALE error, both calling pnfs_destroy_layout() and setting the NFS_LAYOUT_DRAIN bit. However, the first one has not yet called pnfs_put_layout_hdr(), which would prevent the second ESTALE write from attempting to call pnfs_destroy_layout(). A new write arriving in this window finds NFS_LAYOUT_DRAIN set and phl_outstanding > 0, so it enters wait_on_bit(). When a LAYOUTGET completes (clearing the bit and waking waiters), the second ESTALE write then sets NFS_LAYOUT_DRAIN again. The waiting write wakes up, re-checks the condition, finds the bit set once more, and goes back to sleep — this time with no future wake-up coming.

The Fix

The root cause is that when NFS_LAYOUT_INVALID_STID was already set, the code should skip the work of pnfs_mark_layout_stateid_invalid(), thereby ensuring NFS_LAYOUT_DRAIN is not set more than once for an invalid layout. As Kornievskaia explains:

"The problem revolves around the fact that if NFS_LAYOUT_INVALID_STID was already set, it should not do the work of pnfs_mark_layout_stateid_invalid(), thus NFS_LAYOUT_DRAIN will not be set more than once for an invalid layout."

The fix is a minimal one-line change in fs/nfs/pnfs.c (2 insertions, 1 deletion), adding a guard to prevent redundant re-setting of the NFS_LAYOUT_DRAIN flag. The patch was suggested by Trond Myklebust.

Significance for NFS Client Development

This fix addresses a critical reliability issue in the pNFS client: tasks can hang indefinitely under specific concurrent I/O failure conditions. While the race window is narrow, it involves realistic scenarios (ESTALE errors on parallel writes) that could occur in production environments using pNFS storage backends. The fix ensures proper synchronization semantics when draining layouts with invalid state IDs, preventing permanent task stalls.
