Clarifying lockd Module API Boundaries: 42-Patch Series Reviewed, NFS Client Race Condition Identified

Summary

Clarifying lockd Module API Boundaries (v2, 42 patches)

Type: Refactoring / API boundary cleanup (not a bug fix or new feature per se, but enables future modernization work)

Overview

Chuck Lever submitted a substantial 42-patch series (PATCH v2 00/42 through PATCH v2 42/42) aimed at clarifying the architectural boundaries of the lockd (NFS Lock Manager Daemon) subsystem in the Linux kernel. The series targets two primary goals:

  1. Separate lockd's public API from internal implementation details (patches 01–13), reducing implicit contracts exposed through include/linux/lockd/ headers.
  2. Modernize NLMv4 XDR handling using xdrgen (patches 14–42), presented for context to demonstrate the intended purpose of the API cleanup.

As Chuck explained in the cover letter:

"The lockd subsystem currently exposes internal implementation headers through include/linux/lockd/, creating implicit API contracts that complicate maintenance. External consumers such as NFSD and the NFS client have developed dependencies on internal structures like struct nlm_host, and wire protocol constants leak into high-level module interfaces."

Key Technical Arguments

API Boundary Enforcement (Patches 01–13)

The first thirteen patches refactor lockd to establish clean architectural boundaries:

  • Patch 01/42 simplifies cast_status() in svcproc.c by removing dead code for NLMv4 (which is handled separately in svc4proc.c).

  • Patch 02/42 introduces nlm__int__deadlock, an internal status value that replaces the direct use of wire protocol constants in generic lockd code. This establishes a translation boundary where version-specific handlers map internal statuses to appropriate wire protocol values.

  • Patch 03/42 changes nlm_fopen() to return standard errno values instead of on-the-wire NLM status codes, removing NFSD's dependency on NLM wire protocol definitions and eliminating a CONFIG_LOCKD_V4 check from NFSD source.

  • Patch 05/42 is particularly significant for NFS client development: it corrects a layering violation where the NFS client directly dereferenced struct nlm_host (an internal lockd structure). The patch introduces use of the nlmclnt_rpc_clnt() helper function from lockd/bind.h, maintaining clean separation between the NFS client and lockd internals. Chuck also added a NULL check to prevent a potential null pointer dereference in the sysfs shutdown path, noting that "the nlm_host's h_rpcclnt field can be NULL during initialization or after cleanup."

  • Patches 06–13 relocate internal headers (xdr4.h, share.h, lockd.h, debug.h, xdr.h, nlm.h) from include/linux/lockd/ to fs/lockd/, reducing the public API surface to just bind.h and a minimized nlm.h.

NLMv4 XDR Modernization (Patches 14–42)

The remaining patches convert all NLMv4 server-side procedures from hand-rolled XDR code to xdrgen-generated functions. This includes NULL, TEST, LOCK, CANCEL, UNLOCK, GRANTED, SM_NOTIFY, SHARE, UNSHARE, NM_LOCK, and FREE_ALL procedures, along with their corresponding MSG and RES types. The series also adds the RPC language description of NLM version 4 to Documentation/sunrpc/xdr/nlm4.x.

Discussion: NFS Client Race Condition Discovery

The most substantive discussion in this thread centered on Patch 05/42, where Jeff Layton identified a potential race condition in the NFS client's sysfs shutdown path:

"I don't see any locking here. Soon after this thing goes NULL, the nlm_clnt can be freed. ISTM that this ought to take a reference to nlm_clnt and put it afterward." Jeff Layton

Chuck initially asked for clarification:

"So there is no locking here before the patch is applied. The patch does not change that. Do you mean that the patch should add the additional reference count bump (and document that fix in the commit message)?" Chuck Lever

Jeff clarified that this was a pre-existing bug, not something introduced by the patch:

"Sorry, I didn't make it clear. This is (possibly) an existing bug and not something that is changed by your patches. If that value can go NULL and be freed (and it looks like it can in nlm_shutdown_hosts_net()) then I think that could race with someone writing to the 'shutdown' file." Jeff Layton

Jeff proposed a solution:

"The safest thing might be to take and hold the (global) nlm_host_mutex around the NLM parts of shutdown_store(). Maybe we could add a helper to the nlm public interface that does that so we don't need to expose that mutex outside of NLM?" Jeff Layton

Chuck confirmed the issue with AI-assisted analysis and agreed to address it:

"I asked Claude specifically to look for races, and he agrees there is a pre-existing synchronization issue in here. Certainly could be addressed via a pre-requisite patch to 05/42." Chuck Lever

Final Conclusions

Jeff Layton reviewed the full series and provided a Reviewed-by tag:

"I went through the series and it looks good overall. I definitely like moving away from hand-rolled XDR handling." Jeff Layton

He also recommended extended testing:

"It's a big change so it'd be good to have a nice long test cycle with it." Jeff Layton

Chuck responded with his integration plan:

"I was thinking of applying at least 1 - 13 to nfsd-testing soon so it will show up in nfsd-next as soon as the 7.0 merge window closes." Chuck Lever

Regarding the race condition, Chuck confirmed he was folding Jeff's proposed fix into a replacement for patch 05/42:

"So I've folded all that together into a replacement for 05/42." Chuck Lever

A minor naming nit was also raised on patch 02/42:

"nit: the double underscores look weird next to nlm_drop_reply. Maybe you could also rename it to nlm__int__drop_reply?" Jeff Layton

Chuck indicated a broader direction for this area:

"What I'd really like to do is replace nlm_drop_reply with setting the RQ_DROPME flag." Chuck Lever

Summary for NFS Client Development

The most directly relevant changes for NFS client developers are:

  1. Layering fix in sysfs shutdown (Patch 05/42: The NFS client must use nlmclnt_rpc_clnt() instead of directly dereferencing struct nlm_host, enforcing proper module boundaries.

  2. Pre-existing race condition identified: A potential use-after-free in the sysfs "shutdown" file write path when h_rpcclnt is NULL during lockd teardown. This will be addressed in a prerequisite patch with proper mutex protection via a new lockd API helper.

  3. API surface reduction: Internal lockd headers are being moved out of include/linux/lockd/, meaning NFS client code should only depend on bind.h for lockd interactions going forward.
