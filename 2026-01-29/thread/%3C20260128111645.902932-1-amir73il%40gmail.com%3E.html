nfsd: Prevent Exporting Special Kernel Filesystems (pidfs, nsfs)

Summary

nfsd: Prevent Exporting Special Kernel Filesystems (pidfs, nsfs)

Overview

Amir Goldstein submitted version 3 of a two-patch series addressing a bug in NFS server (nfsd) that could allow the export of special kernel filesystems — specifically pidfs and nsfs — which were never intended to be exported via NFS. This is a bug fix with an accompanying documentation clarification, targeting backporting to stable kernels.

Background

The special kernel filesystems pidfs and nsfs recently gained support for encoding and decoding file handles via the name_to_handle_at(2)/open_by_handle_at(2) system calls. These filesystems implement custom ->open() and ->permission() export operations, but nfsd does not properly respect these custom methods. As Amir Goldstein explained:

"These special kernel filesystems have custom ->open() and ->permission() export methods, which nfsd does not respect and it was never meant to be used for exporting those filesystems by nfsd."

The patches carry Fixes tags pointing to the commits that introduced file handle support in pidfs and nsfs:

  • b3caba8f7a34a ("pidfs: implement file handle support")
  • 5222470b2fbb3 ("nsfs: support file handles")

Patch Breakdown

Patch 1/2: exportfs Documentation Clarification

This patch updates kernel-doc comments in include/linux/exportfs.h to clarify that the ->open() and ->permission() methods are intended for the open_by_handle(2) system call only and are not compatible with nfsd. As Amir noted, this patch clarifies "the WHAT (to use them for) if not the HOW (to use them)."

Patch 2/2: nfsd Export Prevention

The core fix adds a check in fs/nfsd/export.c that blocks exporting any filesystem that has custom ->open() or ->permission() methods defined. The new inline function exportfs_can_decode_fh() returns false if either method is set, preventing nfsd from exporting such filesystems.

Review Feedback

Jeff Layton

Jeff Layton provided a review on the cover letter, stating:

"Updated version seems reasonable"

and granted his Reviewed-by tag.

Chuck Lever

Chuck Lever reviewed both patches and raised several points:

  1. Typos: Pointed out a typo in the subject line ("expotrfs" → "exportfs") and in the commit message ("opan_by_handle_at" → "open_by_handle_at").

  2. Documentation structure: Advised against removing the brief description for the export_operations struct in the Doxygen output:

    "Let's not remove the brief description for the export_operations struct in the Doxygen output."

  3. Comment accuracy: On patch 2/2, Chuck noted a discrepancy between the code comment and the actual logic:

    "The comment says 'with custom ->open() and ->permission() ops' but the code blocks export if either one is set. The commit message correctly says 'or' - should the comment be updated to match?"

Amir Goldstein acknowledged all feedback and confirmed he would fix these issues for v4:

"OK. will fix for v4."

Context from Prior Discussion

Amir referenced Christoph Hellwig's feedback from the v2 discussion, where Christoph expressed difficulty understanding the export methods even after reviewing their documentation and the commits that introduced them. Amir argued:

"IMO, further clarifications of the new methods is very much welcome, but should not be blocking the merge of this patch set, which at least clarifies the WHAT (to use them for) if not the HOW (to use them)."

Changes Since v2

  • Rebased over vfs-7.0.misc to avoid conflicts with kernel-doc refactoring
  • Split into separate documentation and fix patches (enabling backporting of just the fix)
  • Removed prior Reviewed-by tags due to wording changes

Conclusion

This patch series addresses a genuine bug where nfsd could attempt to export special kernel filesystems (pidfs, nsfs) that are incompatible with NFS exporting. The fix is conservative — it blocks any filesystem with custom ->open() or ->permission() export methods from being exported via nfsd. The discussion this week was focused on polishing documentation and comments, with both reviewers (Jeff Layton and Chuck Lever) providing constructive feedback that Amir agreed to address in v4. No fundamental disagreements arose over the approach.
