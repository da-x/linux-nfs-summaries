systemd: drop Wants=network-online.target for rpc-statd-notify

Summary

systemd: drop Wants=network-online.target for rpc-statd-notify

Type: Bug fix / systemd service dependency correction

Participants: Dusty Mabe, Steve Dickson

Overview

Dusty Mabe submitted a patch to remove the Wants=network-online.target dependency from the rpc-statd-notify.service unit in nfs-utils. The change was quickly accepted and committed by maintainer Steve Dickson.

Technical Argument

The core issue is that the NFS statd notification service (rpc-statd-notify) was pulling in network-online.target, which can significantly delay system boot — particularly in environments where no NFS mounts are configured or where the network is not yet available (such as install environments).

Mabe highlighted that systemd documentation explicitly discourages liberal use of this target:

"It is strongly recommended not to make use of this target too liberally: for example network server software should generally not pull this in (since server software generally is happy to accept local connections even before any routable network interface is up). Its primary purpose is network client software that cannot operate without network."

The practical impact was most visible on Fedora, where nfs-client.target is enabled by default via presets. This means that even systems with no NFS mounts configured would pull in rpc-statd-notify.service, which in turn pulled in network-online.target, causing unnecessary boot delays.

Justification for the Change

Mabe argued that sm-notify (the binary behind rpc-statd-notify) is already resilient to transient network failures. He pointed to the existing man page documentation:

"Notifications are retried if sending fails, the remote does not respond, the remote's NSM service is not registered, or if there is a DNS failure which prevents the remote's mon_name from being resolved to an address."

This retry logic means the service can safely start before the network is fully online — it will simply retry notifications once connectivity becomes available.

Mabe also noted the broader benefit:

"Making this change means if you are in an offline scenario (one example is an install environment) then you won't have to wait for network-online.target to timeout before the system comes up fully."

The issue had been previously discussed on Fedora's CoreOS config repository and Red Hat Bugzilla, as referenced in the patch.

Resolution

NFS maintainer Steve Dickson accepted the patch without objection, committing it to nfs-utils with tag nfs-utils-2-8-5-rc3:

"Committed... (tag: nfs-utils-2-8-5-rc3)" — Steve Dickson

Conclusion

This is a straightforward but impactful fix for NFS client boot performance. By removing an overly conservative systemd dependency, systems that enable nfs-client.target (particularly Fedora by default) will no longer experience unnecessary boot delays when no network is available or when no NFS mounts are configured. The change leverages the existing retry semantics of sm-notify to ensure correctness is maintained while improving startup responsiveness.
