NFS EOF Page Pollution Fix: Design Rationale and MM Subsystem Abstraction Discussion

Summary

NFS Client "EOF Page Pollution" Protection: Design Rationale Discussed

Classification

This thread concerns a bug fix in the NFS client — specifically, a discussion about the design rationale behind Trond Myklebust's patch series to protect against "eof page pollution," originally submitted in September 2025. The conversation this week represents a retrospective review by MM developer Lorenzo Stoakes seeking to understand why the NFS implementation diverges from the generic pagecache_isize_extend() helper.

Background (Prior Weeks)

The original eof page pollution fix (commit b1817b18ff20, titled "NFS: Protect against 'eof page pollution'") was designed to address xfstest generic/363 and prevent data corruption when users mmap() beyond the end of a file and write into the folio straddling the EOF boundary. In January 2026, NVIDIA engineers reported that this fix caused intermittent ext4 checksum errors during boot of nested VMs using qcow2 disk images on NFSv4.2 shares. A multi-week investigation revealed a separate race condition in NFSv4.2 fallocate and copy offload operations where file size was read before locking the inode. That regression was resolved by a targeted patch, and the original eof page pollution safeguard remains intact.

This Week's Discussion

On January 24, MM developer Lorenzo Stoakes from Oracle dug up the old patch series to understand its design choices, particularly why the NFS-specific nfs_truncate_last_folio() function diverges from the generic pagecache_isize_extend() helper:

"So this seems to be a slightly adjusted version of pagecache_isize_extend(), what was it about that that didn't work for you?"

Stoakes identified three key differences between the NFS implementation and the generic helper:

  1. Block size alignment (which he believed was still needed)
  2. Using folio_test_uptodate() instead of folio_test_dirty()
  3. The addition of a trace line

His primary concern centered on the uptodate-vs-dirty distinction:

"Really I'm confused as to why you are using folio_test_uptodate() here rather than folio_test_dirty() as in pagecache_isize_extend()? Wouldn't writeback have already handled this if the folio is up to date, or if the folio was never dirty in the first place? Shouldn't we only need to do this if the folio is dirty?"

Trond Myklebust's Response: Five Key Points

NFS client maintainer Trond Myklebust responded on January 24 with a detailed five-point explanation clarifying why the NFS-specific approach was necessary:

  1. NFS is not a block protocol:

"NFS is not a block protocol. Reads and writes are byte aligned."

  1. Block size alignment is irrelevant for NFS:

"The test for bsize >= PAGE_SIZE is nonsense for a byte aligned filesystem."

  1. Race protection via folio_mkclean():

"NFS does care about using folio_mkclean() to fix races between an application that is writing to the folio, and any zeroing of the data that may result from the file truncation."

  1. Dirty state is not the concern:

"The existing folio dirty state isn't of interest here, since NFS won't extend existing writes to cover the part of the folio that lies after the old eof."

  1. Uptodate state is what matters for reads:

"The folio uptodate state is of interest, since any future pagecache read needs to see zeroed bytes starting at the old eof and extending either to the offset at the end of the folio, or to the new eof (whichever of the two is smaller)."

Lorenzo Stoakes' Follow-Up: Toward Better Abstraction

On January 26, Lorenzo acknowledged the explanation and outlined his motivation for asking — he was working on abstracting away folio_mkclean() as an implementation detail that shouldn't be exported from the MM subsystem. He noted that NFS and ext4 are the only current users of this pattern:

"Motivation is that generally it seems to me folio_mkclean() itself is an implementation detail we shouldn't be exporting, but I'm considering how we might abstract this while retaining functionality in existing file systems (nfs and ext4 are the only current users)."

He proposed two potential paths forward:

  • An abstraction providing an alternative to pagecache_isize_extend() that accounts for NFS's use case, possibly by breaking it into parts
  • A simpler abstraction around the folio_mkclean() / folio_mark_dirty() dance

"The latter I was trying to avoid as it doesn't do all that much to un-export the implementation detail but of course ensuring in-tree filesystems work as they do now is a requirement for any such change."

He concluded with a commitment to keep the NFS maintainer informed:

"Obviously I will cc- you on anything that touches NFS in this regard!"

Conclusions

This thread represents a productive cross-subsystem discussion between MM and NFS client development. The key takeaways are:

  • The NFS eof page pollution fix is correct as designed: Trond's five-point explanation clarifies that the divergence from pagecache_isize_extend() is intentional and necessary due to NFS being a byte-aligned protocol rather than block-aligned, and because the concern is about read correctness (uptodate state) rather than writeback (dirty state).
  • Future MM subsystem cleanup may affect NFS: Lorenzo Stoakes is exploring ways to abstract folio_mkclean() away from filesystem code. The NFS implementation's specific needs will need to be accommodated in any such refactoring, and Trond has been added to the CC list for related work.
  • The original bug fix remains intact: Following last week's resolution of the ext4 checksum regression (which was a separate race condition), the eof page pollution protection continues to serve its purpose of preventing data corruption when applications mmap beyond EOF.
