bio_vec RDMA API v3 Review: Iterator Conventions, MR Refactoring Debate, and v4 Committed

Summary

bio_vec RDMA API v3: Review Week — Code Style, MR Refactoring, and a v4 in Progress

Type: New feature / API addition with an important bug fix (continued from prior week)

Prior Week Recap

Last week, Chuck Lever posted version 3 of his five-patch series to add a bio_vec-based RDMA read/write API to drivers/infiniband/core/rw.c, converting the NFS server-side RDMA transport (svcrdma) away from scatterlists. The v3 series incorporated Christoph Hellwig's feedback on iterator design, IOVA coalescing, and MR support, and notably introduced a new patch fixing a Send Queue sizing bug that caused exhaustion under heavy NFS WRITE workloads with memory registration enabled. See last week's summary for full details.

This Week's Activity: Detailed Review and Path to v4

This week, the v3 series received thorough review from Christoph Hellwig, Zhu Yanjun, and Jason Gunthorpe. The discussion focused on code style nitpicks, API design conventions around bvec_iter, structural concerns about memory registration (MR) code duplication, and broader architectural vision for scatterlist elimination in the kernel.

Performance Testing Inquiry

Zhu Yanjun opened the review by asking for performance data:

"Do you happen to have any performance or functional test results you could share for this series, in particular: Hardware RDMA devices (e.g., latency, bandwidth, or CPU utilization changes), and/or Software RDMA devices such as rxe or siw?" [id://c02ab348-5243-4e97-b916-6bd59ffe769a@linux.dev]

Lever responded that functional tests on CX-5 InfiniBand showed no regression, but quantitative performance data was limited:

"Performance tests are difficult to evaluate because I don't have a multi-client set-up here to drive a heavy workload, plus filesystems bottleneck long before the network transport does. The changes are designed to improve scalability (eg lower CPU utilization for the same workload and less interaction between host and RNIC) more than improve raw throughput." [id://d67a30a0-5ff1-4e31-a168-81f8b7bee97f@kernel.org]

He noted "perhaps a bit of improvement for tail latencies" and emphasized the broader architectural goal:

"The main purpose of the series, however, is part of an effort to enable kernel-wide replacement of the use of scatter-gather lists, which are technical debt. Socket APIs already support struct bio_vec." [id://d67a30a0-5ff1-4e31-a168-81f8b7bee97f@kernel.org]

Zhu Yanjun acknowledged the response:

"Thanks a lot. Based on the code changes, this patch series should improve performance. Unfortunately, due to various limitations, we are unable to provide performance test results." [id://6e3b0ade-6b45-4597-b065-9148c2c5e0ef@linux.dev]

Patch 1/5: Code Style Nits (Reviewed-by Retained)

Christoph Hellwig reviewed patch 1/5 with several code style observations but did not withdraw his prior Reviewed-by tag. He flagged overly long lines and questioned the open-coding of mp_bvec_iter_bvec:

"Why is this open coding mp_bvec_iter_bvec?" [id://20260123062643.GA25786@lst.de]

He also suggested using bvec_virt() instead of manual pointer arithmetic:

"Overly long line here, which could be fixed by just using bvec_virt()." [id://20260123062643.GA25786@lst.de]

These are cosmetic issues expected to be addressed in v4.

Patch 2/5: bvec_iter Conventions Debate

Hellwig questioned why the code used a local copy of the iterator (link_iter) rather than consuming the original:

"Why is this using a local link_iter? We're not using iter later." [id://20260123062844.GB25786@lst.de]

Lever explained his defensive programming rationale:

"I think we don't want to leak a partially-updated iter if the API call returns an error." [id://d70b5896-2de8-4417-a149-0fd1c55f4d2d@app.fastmail.com]

Hellwig pushed back, citing established block layer conventions:

"That's how all the block layer bvec_iter-based API work. The functions consume the iter. If a caller needs to save it for some reason, it stashes away a copy." [id://20260126061433.GA1638@lst.de]

This exchange highlights an ongoing effort to align the new RDMA API with established kernel bvec_iter conventions — a detail that matters for API consistency and future maintainability.

Patch 3/5: MR Code Duplication — The Substantive Debate

The most substantive technical discussion centered on patch 3/5, which adds Memory Registration (MR) support for bvec-based RDMA operations. Hellwig raised three concerns:

  1. Confusing naming between rdma_rw_io_requires_mr (protocol-driven, iWARP) and rdma_rw_io_needs_mr (threshold-driven):

    "I find the naming really confusing here. I guess requires is that the protocol (iWarp) doesn't work with it, needs means we need it for the number of entries." [id://20260123063622.GA26025@lst.de]

  2. Structural design of the reg field in the context structure:

    "Jumping ahead here - why can't the sgtable be stored in ->reg without renaming? Is there case where need it, but the rest of reg?" [id://20260123063622.GA26025@lst.de]

  3. Code duplication with the existing rdma_rw_init_mr_wrs:

    "I guess you looked into that, but never replied, but this still looks like it duplicates most of rdma_rw_init_mr_wrs. Is there something that prevents reusing that directly or with minor refactoring?" [id://20260123063622.GA26025@lst.de]

Lever responded that both fields are needed simultaneously in the bvec path and preferred reverting to a non-union structure:

"I think the answer is yes, with bvec, both fields are needed at the same time. My preference is to go back to the early form of the structure without a union, since there are API consumers who access the reg field directly." [id://9a8a0671-29a2-4220-8d38-361a6718b7ea@app.fastmail.com]

Hellwig clarified his position:

"What I don't understand is why it can't be added to struct rdma_rw_reg_ctx. Are there any uses of the new fields that don't have that allocated? If yes, just adding the new fields outside the union seems to cause the least churn for now, although I'd still want to clean it up later eventually." [id://20260126061631.GB1638@lst.de]

On the code duplication concern, Hellwig was firm:

"I was hoping we could just reuse the code instead of duplicating it. [...] not reusing the existing scatterlist code to then work on it feels wrong." [id://20260126061752.GC1638@lst.de]

Lever committed to addressing this in v4:

"I added a helper that refactors out the common logic. But I did that a few days ago and all of the context has dribbled out of my brain. I'll post a v4 soon, and we can continue from there." [id://38f7282c-31a6-4edf-8d5c-0d08b401f1f5@app.fastmail.com]

Patch 4/5: SQ Sizing Bug Fix — Clean Reviewed-by

The Send Queue sizing bug fix patch received an unqualified Reviewed-by from Hellwig:

"Looks good: Reviewed-by: Christoph Hellwig hch@lst.de" [id://20260123063652.GB26025@lst.de]

This is the most straightforward acceptance in the thread, reflecting consensus on the importance of this fix for NFS server stability under heavy WRITE workloads with memory registration.

Broader Vision: Scatterlist Elimination

Jason Gunthorpe weighed in on the overarching architectural motivation:

"I haven't imagined tree wide, but I am envisioning a world where a modern server runs all its primary IO paths without using scatterlist." [id://20260126171319.GO1134360@nvidia.com]

This endorsement from the RDMA subsystem maintainer reinforces that this series is not merely an optimization for svcrdma but part of a kernel-wide initiative to eliminate scatterlist technical debt.

Evolution and Conclusions

The discussion evolved from initial questions about performance data (Jan 23) through detailed code review (Jan 23–24) to structural debates about MR code organization (Jan 26), culminating in Lever's commitment to a v4 release. Key outcomes:

  1. Patch 1/5: Cosmetic fixes needed (line length, use of bvec_virt() and mp_bvec_iter_bvec). Reviewed-by retained.
  2. Patch 2/5: Iterator consumption convention should follow block layer patterns — consume the iter directly rather than using a local copy.
  3. Patch 3/5: Requires refactoring to eliminate code duplication with rdma_rw_init_mr_wrs and resolve structural concerns about the reg field. This is the primary blocker for v4.
  4. Patch 4/5: Clean Reviewed-by — ready to land pending series acceptance.
  5. Patch 5/5 (svcrdma conversion): No specific review this week; implicitly depends on patches 1–4 being finalized.

Significance for NFS Client and Server Development

While this series primarily targets the NFS server side (svcrdma), it has implications for NFS client development as well:

  • Correctness fix: The SQ sizing bug fix (patch 4/5) prevents Send Queue exhaustion on NFS servers under heavy WRITE workloads with memory registration — a scenario increasingly relevant as iWARP adoption grows.
  • Scalability improvements: By eliminating scatterlist conversions, the server-side RDMA path reduces CPU overhead and IOTLB synchronization costs, benefiting large compound NFS operations.
  • API direction: The kernel-wide push toward bio_vec over scatterlists may eventually influence NFS client RDMA code paths (pnfs/blocklayout) as those subsystems evolve.

Status

Chuck Lever has committed to posting v4 soon, incorporating Hellwig's feedback on iterator conventions and MR code refactoring. The series is expected to proceed through the RDMA subsystem tree once review concerns are resolved.
