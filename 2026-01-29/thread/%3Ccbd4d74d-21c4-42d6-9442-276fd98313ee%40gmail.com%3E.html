NFS Client Mount Option Regression Re-appears After Fix Merge

Summary

Bug Fix: Mount Option Handling Regression Resurfaces

This thread captures a bug report from Li Lingfeng (Huawei) indicating that a previously fixed NFS client mount option regression has reappeared after Trond Myklebust's 6-patch series to "Fix up NFS client mount option regressions" was merged. The discussion is classified as a bug fix, not a new feature or protocol change.

Background (Prior Weeks)

The thread originated in late November 2025 when Alkis Georgopoulos reported an NFS EACCES regression since kernel 6.15.4, where read-only NFS mounts incorrectly returned EACCES (Permission denied) instead of EROFS (Read-only file system). This broke tools like losetup during netboot scenarios.

In response, Trond Myklebust submitted a 6-patch series on 2025-11-29 to address the issue:

"The recent changes to suppress the 'ro' and 'rw' mount options when mounting the same NFS filesystem with different settings are causing confusion with users, and are an unnecessary restriction. They represent a functionality regression."

The series reverted three problematic commits and introduced targeted fixes for automount option inheritance. The patches were subsequently merged into the mainline kernel.

This Week's Activity

Bug Report: Regression Re-appears (Jan 29)

On January 29, Li Lingfeng reported that the issue he had originally identified in November 2024 has re-emerged after Trond's fix series was merged:

"After this series of patches was merged, I found that the issue described in link [1] has appeared again." — Li Lingfeng

He demonstrated the problem with a reproducible test case on kernel 6.19.0-rc7:

mount -t nfs -o ro,vers=4 127.0.0.1:/ /mnt/sdaa
mount -t nfs -o rw,vers=4 127.0.0.1:/ /mnt/sdaa
mount -t nfs -o ro,vers=4 127.0.0.1:/ /mnt/sdaa
mount -t nfs -o rw,vers=4 127.0.0.1:/ /mnt/sdaa

The output of mount | grep nfs4 showed four separate mount entries stacked on the same mount point (/mnt/sdaa), alternating between ro and rw:

127.0.0.1:/ on /mnt/sdaa type nfs4 (ro,relatime,vers=4.2,...)
127.0.0.1:/ on /mnt/sdaa type nfs4 (rw,relatime,vers=4.2,...)
127.0.0.1:/ on /mnt/sdaa type nfs4 (ro,relatime,vers=4.2,...)
127.0.0.1:/ on /mnt/sdaa type nfs4 (rw,relatime,vers=4.2,...)

This indicates that the NFS client is no longer correctly reusing or replacing existing superblocks when remounting with different ro/rw options — instead, it creates new stacked mounts each time. This is the core regression: the fix intended to allow flexible mount option handling inadvertently broke the deduplication logic for NFS superblocks.

Maintainer Response: Diagnostic Request (Jan 29)

Trond Myklebust responded promptly with a diagnostic request:

"What does the output of 'cat /proc/fs/nfsfs/volumes' show? Does it show more than 2 devices associated with that fsid?" — Trond Myklebust

This question targets the NFS client's volume tracking infrastructure. If multiple devices are associated with a single fsid, it would confirm that superblock reuse is failing and new volumes are being created on each remount — consistent with Li Lingfeng's observation of stacked mounts.

Significance for NFS Client Development

This regression touches a fundamental aspect of NFS client mount semantics:

  1. Superblock reuse: The NFS client should reuse existing superblocks when mounting the same server/export combination, adjusting options as needed rather than creating new stacked mounts.

  2. Mount option handling: The ro/rw toggle is one of the most common remount operations. Incorrect handling leads to mount table bloat and potentially inconsistent access semantics.

  3. User-facing impact: As originally reported by Alkis Georgopoulos, incorrect error codes (EACCES vs EROFS) can break user-space tools that rely on precise error reporting for netbooting and other infrastructure tasks.

Status

As of the end of this week's window, the discussion remains open with Trond seeking diagnostic information from Li Lingfeng to narrow down the root cause. The next step will be analyzing /proc/fs/nfsfs/volumes output to determine whether the issue lies in superblock matching logic, mount option propagation, or volume tracking.
