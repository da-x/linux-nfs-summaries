Build Warnings on parisc and s390 Expose Missing struct file_lock Forward Declaration in lockd Public API

Summary

Type: Bug fix (build warning caused by API refactoring exposing a missing forward declaration)

This thread captures two automated build warning reports from the kernel test robot against PATCH v3 11/14 of Chuck Lever's series to clarify lockd module API boundaries. The patch moves xdr.h from the public include path (include/linux/lockd/) to an internal location (fs/lockd/), which inadvertently exposed a missing forward declaration for struct file_lock in the public lockd API header bind.h.

Context from Prior Weeks

Chuck Lever's v3 series (14 patches) was submitted this week as a refined version of his earlier 42-patch v2 submission. The series aims to separate lockd's public API from internal implementation details, reducing the public API surface to just include/linux/lockd/bind.h. As detailed in the cover letter summary, Chuck noted:

"The patches in this series refactor the lockd code base to clearly separate its public API from internal implementation and NLM protocol details."

Patch 11/14 specifically moves xdr.h internally, adding a forward declaration for struct nfs_fh (previously pulled in transitively through xdr.h) and an explicit #include of filelock.h in fs/nfs/nfs3proc.c. A similar issue was reported during v2 review on alpha and hexagon architectures (prior summary), where the same header relocation caused build errors in nfs3proc.c. The v3 patch addressed that specific case, but as these new reports show, additional hidden dependencies remain.

Key Technical Arguments

Build Warnings on parisc and s390 Architectures

The kernel test robot reported warnings on two distinct architectures and compilers:

parisc (GCC 15.2.0):

"include/linux/lockd/bind.h:76:69: warning: 'struct file_lock' declared inside parameter list will not be visible outside of this definition or declaration" kernel test robot

s390 (Clang 22.0.0git):

"include/linux/lockd/bind.h:76:64: warning: declaration of 'struct file_lock' will not be visible outside of this function [-Wvisibility]" kernel test robot

Both warnings point to the same declaration in include/linux/lockd/bind.h at line 76:

extern int nlmclnt_proc(struct nlm_host *host, int cmd, struct file_lock *fl, void *data);

Root Cause Analysis

The warning arises because bind.h — the sole remaining public lockd API header — declares nlmclnt_proc() with a parameter of type struct file_lock *, but does not include any header that provides a forward declaration or full definition of struct file_lock. Previously, this was masked by transitive inclusion through include/linux/lockd/xdr.h, which pulled in the necessary definitions. With xdr.h moved to fs/lockd/, those implicit includes are no longer available.

This is a different issue from the v2 build errors on alpha/hexagon (which affected nfs3proc.c). The v3 patch fixed nfs3proc.c by adding an explicit #include "filelock.h". However, the warning here originates in fs/nfsd/lockd.c, which includes bind.h but does not itself include filelock.h — and now that xdr.h is no longer in the public path, the forward declaration for struct file_lock is missing from the transitive include chain.

Significance for NFS Client and Server Development

This warning highlights another layering issue exposed by the API cleanup:

  1. The NFSD side (fs/nfsd/lockd.c) depends on bind.h but was implicitly getting struct file_lock through transitive includes from xdr.h. Now it needs either a forward declaration added to bind.h or an explicit include in the consuming code.

  2. The public API contract of bind.h should be self-contained. If nlmclnt_proc() is declared as a public function accepting struct file_lock *, then bind.h must either provide a forward declaration of struct file_lock or include the appropriate header. This is the same principle that motivated adding the struct nfs_fh forward declaration in this patch.

Evolution of the Discussion

This thread contains only automated reports from the kernel test robot, with no human responses during this week's window. The two messages are near-identical in content, differing only in architecture (parisc vs. s390) and compiler (GCC vs. Clang). Both serve as actionable bug reports that Chuck Lever will need to address before the series can be merged.

Final Conclusions

The build warnings reported here indicate that:

  1. Patch 11/14 needs a small fix to add a forward declaration of struct file_lock in include/linux/lockd/bind.h, similar to how struct nfs_fh was already handled. This would make the public API header self-contained and eliminate the warning on all architectures.

  2. This is consistent with the series' goals: The warnings are precisely the kind of hidden dependency that Chuck Lever's refactoring aims to surface and resolve. By making implicit includes explicit, the codebase becomes more maintainable and less fragile to header reorganization.

  3. The fix should be straightforward: Adding struct file_lock; as a forward declaration in bind.h (or including linux/fs.h or linux/filelock.h) would resolve the issue across all architectures.

These automated reports demonstrate the effectiveness of cross-architecture CI testing in uncovering hidden header dependencies that may not manifest on more commonly tested configurations like x86_64.
