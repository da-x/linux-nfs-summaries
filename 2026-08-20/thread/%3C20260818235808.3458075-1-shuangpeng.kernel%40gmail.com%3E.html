lockd KASAN UAF in nlm_async_call during nfsd unmount

Summary

This week brought a fresh bug report, not a feature or protocol change: a KASAN slab use-after-free in lockd’s nlm_async_call path, filed against current upstream and still awaiting maintainer reply.

The report

Shuangpeng Bai wrote that the crash appeared while testing current mainline:

"I hit the following report while testing current upstream kernel: KASAN: slab-use-after-free in nlm_async_call"

The kernel under test was commit 3aa1dcaa4f6f5ae08936491e08bd456f331f2d40 (2026-08-13). To make the race easier to hit, Bai applied a diagnostic patch that “only adds delays and print statements,” and posted a reproducer plus .config on GitHub Gist, offering to test debug patches.

KASAN recorded an 8-byte read of a freed slab at nlm_async_call+0xd6/0x230 by the lockd kthread:

"BUG: KASAN: slab-use-after-free in nlm_async_call+0xd6/0x230" "Read of size 8 at addr ffff88811b04c808 by task lockd/8377"

Allocation, free, and use

The three KASAN stacks sketch a classic lockd lifetime race between NLM server lock processing, nfsd unmount, and the lockd retry loop.

Allocated by the same lockd thread while handling an NLMv4 LOCK:

  • __kmalloc_cache_noprof → nlm_alloc_call → nlmsvc_lock → nlm4svc_do_lock → nlmsvc_dispatch → svc_process → lockd

That is the server-side NLM path: a blocked lock allocates an nlm_rqst (via nlm_alloc_call) so lockd can later callback the client.

Freed about ten seconds later by another task during nfsd teardown:

  • kfree → nlmsvc_release_block → nlmsvc_traverse_blocks → nlm_traverse_files → nlmsvc_free_host_resources → nlm_shutdown_hosts_net → lockd_down → nfsd_destroy_serv → nfsd_shutdown_threads → nfsd_umount → deactivate_locked_super / cleanup_mnt

Unmounting nfsd therefore walks remaining NLM hosts and files, drops blocked-lock objects, and tears lockd down.

Used after free on the lockd kthread:

  • nlm_async_call ← nlmsvc_retry_blocked ← lockd ← kthread

So nlmsvc_retry_blocked still holds a pointer into a block/nlm_rqst that nlmsvc_release_block already freed while nfsd was going away.

Why this matters for NFS client lockd

Although the allocation and dispatch stacks are NLMv4 server (nlmsvc_* / nlm4svc_do_lock), lockd is the shared NLM engine used by the NFS client as well. nlm_async_call is the async RPC helper both sides use to send NLM messages; nlmsvc_retry_blocked is the lockd thread’s retry of GRANTED callbacks for locks that were blocked on the server. A UAF there is a memory-safety hole in the lock manager that NFS clients depend on for flock/fcntl over NFSv3 (and for NLM callbacks in mixed deployments).

The race, as the stacks present it, is shutdown vs. retry:

  1. lockd accepts a LOCK, allocates an nlm_rqst, and parks a blocked lock.
  2. nfsd is unmounted; lockd_down / nlm_shutdown_hosts_net walks hosts and calls nlmsvc_release_block, freeing that request.
  3. The lockd kthread continues nlmsvc_retry_blocked and calls nlm_async_call on the freed object.

That is consistent with historical lockd UAFs around host shutdown (NLM host teardown vs. in-flight RPC), but this week’s report pins the use site specifically on nlm_async_call and the free site on nlmsvc_release_block during nfsd_umount.

Status this week

The thread is a single message. There is no maintainer ack, no patch, and no disagreement on the traces. Bai’s ask remains:

"I'm happy to test debug patches or provide additional information."

Until someone posts a lockd fix—likely synchronizing nlmsvc_retry_blocked / nlm_async_call with nlmsvc_release_block and nlm_shutdown_hosts_net so blocked-lock RPC objects cannot outlive host teardown—this stands as an open KASAN-confirmed use-after-free in lockd on current upstream.
