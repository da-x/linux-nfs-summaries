pNFS EBUSY check in layout return path

Summary

A one-line client bug fix for pNFS layoutreturn scheduling drew an immediate maintainer veto this week, then a corrected follow-up that keeps the recall path alive on soft mounts.

What broke

Tim Menninger posted a [PATCH] against fs/nfs/pnfs.c targeting pnfs_layout_need_return(). The regression is pinned to commit 41d0a8ead9720 ("NFSv4/pnfs: Add support for the PNFS_LAYOUT_FILE_BULK_RETURN flag"), which replaced pnfs_layout_segments_returnable() with a direct call to pnfs_mark_layout_stateid_return() and then compared that helper’s return value against EBUSY rather than -EBUSY.

Because the helper returns negative errno values, the intended busy case is never seen. Menninger’s commit message is blunt about the sign error:

"Since pnfs_mark_layout_stateid_return() returns negative errno values, the -EBUSY case is never detected."

That is a client-side bug fix, not a protocol change: the pNFS layoutreturn decision on the Linux NFS client was silently ignoring the “segments still in use, defer the return” path after the bulk-return flag work landed.

The v1 mistake: treating “need return” as “must return 0”

v1 did not simply flip the sign. Menninger argued that pnfs_mark_layout_stateid_return() bottoms out in pnfs_mark_matching_lsegs_return(), which returns 0 when a layoutreturn should be scheduled, and therefore changed the comparison from EBUSY to 0. In other words, pnfs_layout_need_return() would only proceed when the mark-for-return walk reported success, not when it reported -ENOENT (no matching segments) or -EBUSY (busy segments).

That is a semantic change, not a sign fix. It collapses several historically distinct return codes into a single “only zero means return” test.

Maintainer pushback: recalls on soft mounts

Trond Myklebust rejected that approach the next day. The Linux NFS client maintainer’s objection is about recall compliance, not about the original EBUSY typo:

"This breaks the ability of the client to respond to layout recalls even when it does not think it holds a layout. That's a situation that can occur when using soft or softerr mounts."

The important client invariant is that a layout recall can still arrive after the client has already dropped or timed out its local view of the layout—especially with soft/softerr, where I/O and state recovery can fail without a hard hang. The client must still be able to send a layoutreturn (or otherwise acknowledge the recall) even when the segment walk finds nothing to mark. Requiring a 0 return from pnfs_mark_layout_stateid_return() would skip that empty-layout recall response.

That is a classic pNFS client correctness constraint: layout state on the wire and layout state in pnfs_layout_hdr are not always in lockstep, and the return path has to remain usable when they diverge.

v2: keep -ENOENT, defer only on -EBUSY

Menninger followed up on 19 August with PATCH v2 (posted in reply to Myklebust’s NAK). v2 drops the “check for 0” theory and does the minimal sign correction: compare against -EBUSY. The changelog is explicit about absorbing the review:

"Preserve the -ENOENT path so the client can respond to recalls when it no longer holds matching layout segments, as pointed out by Trond."

"Defer only on -EBUSY instead of requiring a zero return value."

v2 also adds Cc: stable@vger.kernel.org, treating the EBUSY vs -EBUSY mix-up as a stable-worthy client regression from the bulk-return flag work rather than a behavioral redesign of layoutreturn.

Status

This remains a client bug-fix thread, not a feature or NFSv4.1/pNFS protocol discussion. The technical conclusion after two days is:

  • The EBUSY comparison in pnfs_layout_need_return() is indeed wrong and never matches the negative errno from pnfs_mark_layout_stateid_return().
  • The correct fix is -EBUSY, not == 0.
  • A zero-only check would break layout-recall replies when the client no longer believes it holds matching segments, a case Myklebust called out for soft/softerr mounts.

No further review of v2 landed on this thread before the week closed. The outstanding question is whether the signed -EBUSY check plus the preserved -ENOENT recall path is accepted as the stable fix for commit 41d0a8ead9720.
