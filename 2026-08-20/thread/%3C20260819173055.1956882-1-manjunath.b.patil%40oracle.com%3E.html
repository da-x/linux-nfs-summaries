SUNRPC timeout logs gain client and transport IDs

Summary

Overview

This week’s thread is a client-side observability improvement, not a protocol change and not a functional bug fix. Manjunath Patil posted a one-file SUNRPC patch that enriches the ratelimited RPC timeout messages in rpc_check_timeout() (net/sunrpc/clnt.c) so NFS operators can tell a server stall from a transport that is disconnected, reconnecting, or on a different connection.

The discussion stayed entirely in-window (19–20 August 2026). There is no prior-week history. By Thursday evening the patch had a Reviewed-by from Petr Vorel, a resolved style nit, and no maintainer merge decision yet.

The diagnostic gap

Patil’s cover letter is blunt about the current logs:

"The existing RPC timeout messages identify only the RPC program and server name. That makes it difficult to distinguish a server-side response stall from a transport that is disconnected, reconnecting, or using a different connection."

The patch therefore adds four compact fields to those messages:

  • RPC client id (clid)
  • transport id (xprt)
  • current transport connection cookie (cc)
  • RPC task owner

Those values are meant to line up with rpcctl and other transport state. The example NFS line is:

nfs: server 192.168.50.1 clid=4 xprt=1 cc=1 owner=6245
not responding, timed out

The diff is small (20 lines in clnt.c: 13 insertions, 7 deletions). The new locals req and xprt are declared in rpc_check_timeout(), then used only on the expired-timeout path so the printk can print clnt->cl_clid, xprt->id / cookie, and the task owner. The patch carries Assisted-by: Codex:gpt-5.

For NFS client debugging this is the useful part: a soft-mount timeout that used to say only “server X not responding” can now be correlated with a specific RPC client, a specific xprt, and whether the connection cookie has rolled — i.e., whether the transport was replaced underneath the task.

Review: praise, then a pointer-ordering nit

Petr Vorel replied the next morning with an immediate thumbs-up:

"Nice improvement, thanks!"

and closed with Reviewed-by: Petr Vorel <pvorel@suse.cz> plus “The rest LGTM.”

His only question was readability versus safety: should req and xprt be assigned at the top of the function, before the RPC_SIGNALLED(task) check?

"nit: Would it work to assign req and task earlier (just readability?) Or is it not safe before checking RPC_SIGNALLED(task)?"

He sketched the more compact form:

struct rpc_clnt *clnt = task->tk_client;
struct rpc_rqst *req = task->tk_rqstp;
struct rpc_xprt *xprt = req->rq_xprt;

That is the only technical push-back in the thread.

Why the assignments stay late

Patil thanked Vorel for the tag and declined to hoist the pointers. The ordering is intentional, not leftover style:

"I kept the assignments after RPC_SIGNALLED(task) intentionally, preserving the existing behavior where a signalled task returns before we dereference task->tk_rqstp. xprt is also needed only after xprt_adjust_timeout(req) reports an expired timeout."

In other words: a signalled RPC task must still bail out without touching tk_rqstp, and the transport pointer is only required on the path that actually emits the timeout diagnostic. He would rather keep that existing control flow, while leaving the door open if maintainers prefer the earlier assignments:

"I would prefer to retain the current ordering for those reasons. Also I am open if maintainers chose to alter it."

Closure this week

Vorel accepted the rationale without asking for a v2:

"Understand, fair enough."

and on the “keep current ordering unless maintainers say otherwise” stance, simply:

"+1"

That is where the week ends. The patch is reviewed, the only nit is resolved in favor of the safer late dereference, and no NFS maintainer (Trond, Anna, Jeff, etc.) has Acked or queued it yet.

Takeaway for NFS client work

This is a diagnostics / observability change on the SUNRPC client timeout path that NFS hangs off. It does not alter timeout policy, reconnect, or rebind; it makes the existing ratelimited “not responding, timed out” line usable when a host has multiple RPC clients or multiplexed transports. The client-id / xprt-id / connection-cookie / owner tuple is the practical hook for matching dmesg against rpcctl. Until a maintainer picks it up, the code stays as posted: extra fields in the printk, pointers still assigned after the RPC_SIGNALLED guard.
