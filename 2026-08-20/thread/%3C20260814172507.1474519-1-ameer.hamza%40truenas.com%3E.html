Empty auth.unix.gid upcalls cached as positive group lists

Summary

Overview

This is a bug-fix thread, not a protocol change or a new feature. TrueNAS engineer Ameer Hamza posted a one-liner for net/sunrpc/svcauth_unix.c that stops knfsd from treating a failed mountd group lookup as a successful empty supplementary-group list. The fallout is on the NFS server, not the NFS client: a transient NSS/winbind/sssd hiccup can strip a uid of every supplementary group on every export for the full auth.unix.gid TTL (30 minutes by default), including for RPCSEC_GSS clients that otherwise carry a complete group vector.

The v1 patch itself was not NAK'd. Chuck Lever asked only that the same defect on the newer mountd netlink path be split into a second patch with its own Fixes: tag. Hamza agreed the same day and promised a v2 series.

The failure mode

With rpc.mountd --manage-gids, the kernel asks userspace for the supplementary groups of each AUTH_UNIX (and, via svcauth_gss_set_client(), RPCSEC_GSS) uid. When getpwuid() or getgrouplist() fails — Hamza's example is winbind or sssd being briefly unreachable — mountd answers the auth.unix.gid channel with zero groups. unix_gid_parse() currently installs that reply as a positive cache entry. svcauth_unix_set_client() then replaces the RPC credential's group list with that empty list on every subsequent request.

Hamza's commit message is blunt about the blast radius:

"One failed lookup strips that uid of all supplementary groups on every export for up to mountd's configured TTL (30 minutes by default), long after the NSS backend has recovered."

The semantic argument for treating a zero-group reply as a lookup failure rather than a valid empty membership is that a successful getgrouplist(3) cannot return an empty list:

"mountd cannot send an empty list for a successful lookup, since getgrouplist(3) always includes at least the user's primary group, so a zero-group reply can only mean the lookup failed."

The intended recovery path already exists. Recording the reply as a negative cache entry makes unix_gid_find() return -ENOENT, so svcauth_unix_set_client() keeps the groups the RPC credential already carries. Hamza presents that as the fallback promised by commit 3fc605a2aa38 ("knfsd: allow the server to provide a gid list when using AUTH_UNIX authentication") and as the same state try_to_negate_entry() already creates when no listener holds the channel open. The patch is tagged Fixes: 3fc605a2aa38.

The change is seven added lines in unix_gid_parse(). Hamza notes it applies unmodified (fuzz 0) to every maintained stable tree from 5.10.y through 7.1.y, and was tested on a live 6.12-based server over NFSv3 and NFSv4.0–v4.2 with both sec=sys and sec=krb5.

Reproducer

The commit message includes a tight in-kernel reproducer for any server running rpc.mountd --manage-gids. User alice is a supplementary member of group proj; /srv/proj is root:proj mode 0750:

runuser -u alice -- cat /mnt/proj/data          # ok
# the reply mountd sends when getpwuid()/getgrouplist() fail:
echo "$(id -u alice) $(( $(date +%s) + 600 )) 0" \
    > /proc/net/rpc/auth.unix.gid/channel
runuser -u alice -- cat /mnt/proj/data          # EACCES until
                                                # refresh/flush/expiry

That is the client-visible symptom: a previously authorized NFS client (or local runuser over a mount) suddenly gets EACCES until the poisoned positive entry expires or is flushed, even after NSS has recovered.

Review: split the netlink twin

Chuck Lever did not dispute the diagnosis or the channel-path fix. His only request was process and completeness:

"Looks like the same bug exists for the new mountd netlink mechanism. Since that instance of the bug arrived in a different commit, that fix needs to be a separate patch with its own Fixes: tag."

"Can you make this a two-patch series?"

That is a stable-tree hygiene point: the classic /proc/net/rpc/auth.unix.gid/channel parser and the newer netlink unix_gid path landed in different commits, so they cannot share a single Fixes: tag even if the user-visible failure is the same.

Hamza accepted immediately:

"Sure, will send v2 with the netlink fix as a separate patch. Thanks for taking a look."

Conclusion this week

v1 is a narrowly scoped knfsd/sunrpc bug fix: empty auth.unix.gid replies must be negative cache entries so a failed mountd lookup does not wipe supplementary groups for AUTH_UNIX and RPCSEC_GSS clients. There was no disagreement on the semantics. The thread closed the same day with an agreement to respin as a two-patch series covering both the classic channel parser and the netlink path. Follow-on review of that v2 series ([PATCH v2 0/2] sunrpc: don't strip a uid's groups when the mountd group lookup fails) is a separate thread.

NFS client code is not modified here; the client-visible impact is the spurious EACCES on group-restricted exports after a transient server-side NSS failure.
