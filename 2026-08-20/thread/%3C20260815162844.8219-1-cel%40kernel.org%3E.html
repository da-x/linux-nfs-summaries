SUNRPC rejects already-claimed sockets on NFSD portlist

Summary

This week Chuck Lever posted a tightly scoped bug fix for the NFSD/SUNRPC server socket path, closing a syzbot-triggered kernel stack overflow that could be provoked by handing the same file descriptor to /proc/fs/nfsd/portlist twice. The discussion stayed on the server side of SUNRPC (net/sunrpc/svcsock.c and fs/nfsd/nfsctl.c); there is no NFS client change in this thread. Jeff Layton reviewed the patch and flagged a changelog inaccuracy about which TCP callback actually recurses.

The failure: double-attach of svc_sock

Lever’s v1 patch explains that writing the same socket descriptor into portlist twice attaches a second svc_sock to one underlying socket. svc_setup_socket() first saves the socket’s existing callbacks, then installs SUNRPC’s own. On the second attach those “old” callbacks are already SUNRPC’s, so the new svc_sock records svc_write_space() as the previous write_space handler.

For UDP that immediately detonates: svc_udp_init() calls svc_sock_setbufsize(), which invokes the saved write-space callback, and svc_write_space() then calls itself until the stack guard page is hit:

"Writing the same socket descriptor to /proc/fs/nfsd/portlist twice attaches a second svc_sock to one socket. svc_setup_socket() saves the socket's callbacks before installing its own, so the second attach records svc_write_space() as the old write_space callback. svc_udp_init() invokes that callback by way of svc_sock_setbufsize(), and svc_write_space() then calls itself until the kernel stack is exhausted"

The posted splat is a classic unbounded recursion:

BUG: TASK stack guard page was hit at ffffc900037d7ff8
 svc_write_space+0x90/0x2b0 net/sunrpc/svcsock.c:429
 svc_write_space+0xe6/0x2b0 net/sunrpc/svcsock.c:430
 ... 700 more ...
 svc_sock_setbufsize+0x18d/0x220 net/sunrpc/svcsock.c:386
 svc_udp_init / svc_setup_socket / svc_addsock
 __write_ports_addfd / write_ports / nfsctl_transaction_write

Lever notes the same chaining exists on TCP via saved data_ready / state_change callbacks, so a TCP descriptor added twice recurses on the next incoming segment rather than during setup. Reaching the path requires a writer on portlist; the nfsd filesystem does not set FS_USERNS_MOUNT, so the reproducer needs CAP_SYS_ADMIN in the initial user namespace. The report is credited to syzbot (syzbot+54cdc566f64abf51b7f1@syzkaller.appspotmail.com), with a Fixes: tag on b41b66d63c73 (“knfsd: allow sockets to be passed to nfsd via 'portlist'”).

The fix: refuse sockets that already have sk_user_data

The code change is three lines in net/sunrpc/svcsock.c: reject a socket that already carries sk_user_data before svc_setup_socket() claims it. Lever’s rationale is broader than the recursion itself. Because svc_setup_socket() overwrites that field unconditionally, NFSD would corrupt any socket another consumer had already claimed, even if the callbacks did not recurse:

"Reject a socket that already carries sk_user_data. svc_setup_socket() overwrites that field unconditionally, so a socket some other consumer has claimed is one NFSD would corrupt whether or not the callbacks recurse."

That is a defensive ownership check on the shared SUNRPC server socket layer used by NFSD when administrators inject listening (or datagram) sockets through portlist, rather than a protocol change or a new feature.

Review: ack on the code, pedantry on the TCP changelog

Jeff Layton replied two days later with a Reviewed-by and an enthusiastic:

"Nice catch!"

He then relayed a changelog nit (attributed to Claude) about which TCP callbacks actually recurse. Lever’s cover letter named svc_data_ready() and svc_tcp_state_change(). Layton walks through svc_tcp_init() and points out that write_ports requires listen(3) for SOCK_STREAM, and for a listening socket svc_tcp_init() only replaces sk_data_ready with svc_tcp_listen_data_ready. sk_state_change and sk_write_space are left alone on a listener, so the second svc_setup_socket() saves svc_tcp_listen_data_ready() into sk_odata, and that is the function that chains into the saved callback:

"sk_state_change and sk_write_space are left alone on a listener, so the second svc_setup_socket() saves svc_tcp_listen_data_ready() into sk_odata and the recursion runs there instead"

The non-listen branch does install svc_data_ready() and svc_tcp_state_change(), but svc_addsock() only reaches it for a descriptor that is not listening, and svc_tcp_init() then immediately deferred-closes that transport unless the socket is already TCP_SYN_RECV or TCP_ESTABLISHED. Layton’s closing question:

"Should the paragraph name svc_tcp_listen_data_ready() instead?"

Status this week

The thread is a server-side bug fix, not an NFS client change and not a protocol update. The technical argument for the code (refuse sockets that already have sk_user_data) was uncontested; the only follow-up is a request to name svc_tcp_listen_data_ready() in the changelog for the listening-TCP recursion path. No v2 appeared in this window, and there is no maintainer merge ack yet beyond Layton’s Reviewed-by.

For NFS client readers the takeaway is indirect: the defect lives entirely in NFSD’s portlist socket-injection path and the shared SUNRPC svc_sock setup, so client RPC/transport code is unaffected. The interesting server lesson is that callback-save/restore in svc_setup_socket() is not idempotent, and sk_user_data is the right ownership bit to fail closed on before NFSD overwrites another consumer’s socket.
