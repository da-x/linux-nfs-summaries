getport stddef.h fix lands in nfs-utils-2.9.3-rc1

Summary

This week closes a small but real userspace build-fix thread: nfs-utils maintainer Steve Dickson applied Jaipaul Cheernam’s one-line getport.c include patch and tagged it for nfs-utils-2.9.3-rc1. It is a bug fix, not a protocol change and not an in-kernel NFS client patch. The kernel fs/nfs path is untouched; the operational impact is on client-side userspace that still has to talk to rpcbind before a mount can proceed.

Last week Cheernam posted [PATCH] getport: fix missing stddef.h inclusion after musl refused to compile support/nfs/getport.c because offsetof() was used without <stddef.h>. Glibc hid the defect via a transitive include. There were no technical objections then, and none appeared this week either — Dickson’s reply is the entire discussion.

This week’s conclusion

On 15 August, Dickson replied to the original patch with a terse merge notice:

"Committed... (tag: nfs-utils-2-9-3-rc1)"

That is the final word. No Acked-by, no requested v2, no debate over an alternative header. The patch as posted — a single #include <stddef.h> in support/nfs/getport.c — is what went in.

What was broken (brief recap)

Cheernam’s original diagnosis still stands as the technical argument:

"getport.c uses offsetof() but does not include <stddef.h>. On glibc this works because offsetof is pulled in transitively, but on musl it is not available without the explicit include"

The compiler error was:

getport.c:459:41: error: implicit declaration of function 'offsetof'

offsetof is specified in <stddef.h>. Musl does not re-export it from the RPC/NFS headers the file already pulled in, so a musl-based client image could not build the helper that resolves NFS/NLM ports. Implicit-declaration treatment of what should be a compile-time constant is also a warning-as-error landmine on modern toolchains. Adding the canonical header is libc-neutral and is the correct fix; nobody proposed anything else.

NFS client angle

This is not kernel NFS client development. There is no fs/nfs change, no wire-protocol tweak, and no mount-option semantics change. What is client-relevant is the userspace that the Linux NFS client still depends on for:

  • port discovery before MOUNT / NFS RPC
  • fallback when rpcbind is present but NFSv4-only assumptions do not apply
  • any tool that links the same support/nfs library and walks the getport structures that use offsetof

Until this commit, a musl rootfs could not produce a working mount.nfs / portmapper path because the build died at getport.c:459. With the include in 2.9.3-rc1, that path compiles on both glibc and musl.

Status

  • Type: bug fix (missing include; musl portability)
  • Scope: nfs-utils support/nfs/getport.c, not the kernel NFS client
  • This week: maintainer commit; tagged nfs-utils-2-9-3-rc1
  • Conclusion: accepted as-is; thread closed
