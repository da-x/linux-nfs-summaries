SUNRPC reply-page recycling hits splice-path pushback

Summary

Ameer Hamza posted a two-patch NFSD/SUNRPC performance series aimed at a long-standing page-allocator collision on the NFS server, not the client. Review this week concentrated almost entirely on patch 1/2 (how NFSD chooses a READ path). The actual recycling machinery in patch 2/2 was explicitly deferred. The series is a performance optimization, not a protocol change; it also surfaced two pre-existing NFSD iterator-READ accounting bugs, which Hamza immediately split out as a backportable fix series.

The problem: ACK-time frees versus alloc_pages_bulk()

Hamza's cover letter describes a contention pattern that only appears when an NFS READ Reply is built in pages the nfsd thread itself allocated, rather than spliced from the page cache. Those pages are freed from softirq when the peer's ACK arrives. Since commit 574907741599 ("mm/page_alloc: leave IRQs enabled for per-cpu page allocations"), that free collides with alloc_pages_bulk()'s IRQs-on per-cpu window and falls back to free_one_page() under zone->lock. On a single memory node every nfsd thread contends for the same lock:

"On a single memory node this settles into a steady state with most CPU cycles in the queued-spinlock slowpath."

Replies spliced from page-cache folios are immune, because the page cache still holds a reference. Everything else is not: gfs2, kernfs, cifs direct I/O and DAX files all go through copy_splice_read(), which allocates a fresh page for every page of payload; nfsd also allocates its own pages when splice is disabled (nfsd_disable_splice_read) and for sec=krb5i / sec=krb5p. Hamza notes ZFS is in the same boat (->splice_read is copy_splice_read()), though the posted measurements used ext4 DAX and tmpfs so they reproduce on a stock tree with a pmem device.

On a 64-thread, single-node server serving 1 MiB sequential cached NFSv4.0 reads to eight local-namespace clients, the numbers are stark:

The "knob" rows isolate patch 2. Hamza is careful about scope: "How much this is worth depends on contention: on the server below the ACK-time frees reach 43% of cycles, while on an uncontended machine the same change removes the allocations and leaves total CPU where it was." An ext4 export without DAX has no such free to collide, and is unchanged. The posted code was only run in a 20-CPU VM; the table is from a backport to 6.18.38. A build with the folio_ref_count() reuse gate deliberately removed still checksums cleanly on a fast link, but "Under a 40 ms ACK delay that build corrupts data and the series stays byte-identical."

Patch 1: stop double-allocating on copy-splice filesystems

Patch 1/2 is the smaller, more controversial half. For filesystems whose ->splice_read cannot avoid a copy, copy_splice_read() allocates a page, nfsd_splice_actor() then installs it in rq_respages (displacing pages the thread already owns), and both sets are freed. Routing those READs through nfsd_iter_read() does the same single copy into pages nfsd already holds. Hamza is explicit that this is not a throughput patch on its own:

"On its own this is not expected to raise throughput; it changes which pages a Reply is built from so that the next patch can recycle them."

The helper nfsd_splice_read_is_zero_copy() tests f_op->splice_read against known copy implementations. 9p and ceph, which fall back to copy_splice_read() inside their own methods, stay on the splice path. One visible side effect is already called out: an fsnotify watcher sees two access events per READ instead of one, the extra one from vfs_iocb_iter_read().

Patch 2: park sent Reply pages and reuse them

Patch 2/2 is the actual recycling work, and it received no review this week. After send, svc_rqst_release_pages() currently drops the thread's reference; the transport's MSG_SPLICE_PAGES hold is the last one, released from softirq at ACK time (~257 pages per 1 MiB READ on 4 KiB pages). The patch keeps the thread's reference, parks the page in a small per-thread array, and refills a free Call or Reply slot once folio_ref_count() reads 1 — "the gate the network stack has applied to its own ACK-timed references since 2012, today in skb_page_frag_refill()." Hamza points at 2021 discussions of releasing result pages as prior art.

Reuse is opt-in per transport class; only svc_udp_class and svc_tcp_class set XCL_FL_REPLY_PAGE_REUSE. A page is reused only if it is order-0, unpoisoned, not pfmemalloc, node-local and not page-cache-backed; spliced-in folios are excluded. A thread holds at most four maximum-size Replies and never more than 4 MiB (512 MiB on a 128-thread server). The scan is unordered with a persistent cursor, so a page still held by one slow connection cannot block reuse of pages parked after it. svc_reuse_scan() costs 2.5% of cycles when it is busy, falling to 0.7% when late ACKs leave little to reuse.

Chuck Lever set this patch aside on purpose: "I'm going to focus on patch 1/2 and set 2/2 aside for the moment. I promise we will come back to it."

Chuck Lever: fix the iterator-READ accounting first

Chuck Lever thanked Hamza for posting the full series so the problem statement was visible, and acknowledged the underlying pain:

"Contention in the page allocator is vexing, and is a problem we've been chasing for years."

He then argued that expanding nfsd_iter_read() to more filesystems would expose two pre-existing bugs that already affect sec=krb5i/sec=krb5p, nfsd_disable_splice_read, and NFSD_IO_DIRECT:

  1. fsnotify double-counting. vfs_iocb_iter_read() emits an access event, and nfsd_finish_read() emits a second. Splice emits none in the VFS helper, so nfsd_finish_read() is the only event on that path — correct for splice, one too many for iter.
  2. atime not updated. nfsd_splice_read() picks up file_accessed() from splice_direct_to_actor(). nfsd_iter_read() leaves atime to ->read_iter. That works for gfs2, cifs DIO, ext4 DAX and XFS DAX, but fuse_dax_read_iter() has an explicit /* TODO file_accessed(iocb->f_filp) */ and never advances atime.

Lever's ask was a backportable fix before the series, not a rewrite of 1/2 for stable:

"So what I'd like you to do is provide a backportable fix that applies before your series to address the fsnotify and atime accounting issues. I'm not convinced that stable will want the bulk of the 1/2 changes as you have them here."

Hamza agreed both issues were real and posted a separate two-patch series the same day:

  • NFSD: Fix duplicate fsnotify access events for iterator READs — move fsnotify_access() out of nfsd_finish_read() and into nfsd_splice_read(), the one path whose VFS helper does not emit it. Fixes: 507df40ebf316, Cc: stable.
  • NFSD: Update the atime for iterator READs — call file_accessed() after each successful vfs_iocb_iter_read(), because "nfsd serves whatever filesystem is exported, so it cannot rely on every ->read_iter keeping the convention." Same Fixes: tag, also Cc: stable.

Those patches are a separate thread; they are the week's actual bug-fix fallout from this series.

Neil Brown: don't poke f_op->splice_read by function pointer

NeilBrown disliked the detection method, not necessarily the goal:

"I really don't like the approach of explicitly testing whether f_op->splice_read is a particular value."

His alternative: add FMODE_DONT_COPY_FOR_SPLICE so copy_splice_read() returns -ENOTSUP (or similar). nfsd would still try splice_read, and fall back to iter_read on that error. That would also catch 9p and ceph, which Hamza's helper cannot see. Hamza accepted this for v2:

"Thanks, this indeed works better. I believe it also covers 9p and ceph falling back to copy_splice_read() internally, which the helper could not see. I will work it out this way for v2."

Christoph Hellwig: NACK on the premise

Christoph Hellwig rejected patch 1 on more fundamental grounds:

"No. None of the above are sensible use cases for NFSD exports. There is no good reason to add a barely maintained special code path thae pokes into internals for this."

Hamza conceded the internals point and said he would rework v2 around Neil's FMODE flag "unless you have something else in mind." Hellwig's follow-up made the "if" itself the issue, and was blunt about the DAX/tmpfs reproduction:

"That's a big IFF. The splice fallback is a generate case. And no, we should not add flags and big blobs of NFSD code to work around it, there's simply no point in optimizing for some LLM generated ext4 on fake DAX bullshit."

(Both of Hamza's patches, and the follow-up bug fixes, carry Assisted-by: Claude:claude-fable-5.)

Where things stand

This week did not produce a conclusion on merging either half of the series. Lever wants the fsnotify/atime bugs fixed first and is not convinced the splice-vs-iter reroute belongs in stable; Brown wants a generic FMODE handshake rather than function-pointer tests if the reroute happens at all; Hellwig does not want the reroute, or new flags to enable it, because he does not consider copy-splice filesystems (DAX, gfs2, kernfs, cifs DIO) first-class NFSD export targets. Patch 2 — the recycling design that actually removes the 43% free_one_page() tax, including for nfsd_disable_splice_read and krb5i/krb5p, which already use nfsd_iter_read() without patch 1 — has not been reviewed. Hamza is preparing a v2 around Brown's FMODE idea; whether that survives Hellwig's "big IFF" is the open question going into next week.

There is no NFS client code in this series. The client-visible effects, if any, would be server-side: fewer allocator stalls under DAX/copy-splice/krb5 integrity READ load, plus (from the split-out fixes) correct atime and a single fsnotify access event on iterator READs that already take that path today.
