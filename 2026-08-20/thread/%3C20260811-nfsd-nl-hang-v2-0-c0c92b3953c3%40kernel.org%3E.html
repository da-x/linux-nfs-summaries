NFSD netlink listeners: rpcbind registration to become non-fatal

Summary

This week's discussion on Jeff Layton's v2 hardening series for the NFSD netlink listener path closed the argument over partial rpcbind unwind and settled a mergeable policy: rpcbind registration failures will be treated as non-fatal for NFSv2/v3, patch 4/8 will be dropped, and the remaining patches will be re-rolled around that change.

This is a bug-fix / hardening series, not a protocol change. It targets nfsd_nl_listener_set_doit() stalls under nfsd_mutex that syzbot keeps hitting, plus leftover rpcbind mappings and a netns leak in the new selftests. The durable fix Layton still wants — asynchronous rpcbind RPCs so they no longer run under nfsd_mutex — remains a later patchset.

Prior week, briefly

On 11 August Layton posted PATCH v2 0/8 ("nfsd/sunrpc: harden the netlink listener interfaces"). The series validates transport names before taking nfsd_mutex, caps listener_set at 1024 entries, keeps the first svc_register() error, unwinds partial rpcbind registrations, bounds the local rpcbind client to a 1s attempt, reports listener failures via extack, and adds nfsd selftests with a per-netns rpcbind stub.

Patch 4/8 was the new piece versus v1: if svc_register() fails after some [program, version] entries have already been set, unwind them, because the caller then tears the listener down while those mappings still point at a closed port. XPT_RPCB_UNREG is only set later in svc_udp_init()/svc_tcp_init(), so svc_delete_xprt() never runs on this path.

Chuck Lever immediately objected. For an IPv4 listener the port-zero callback falls through __svc_rpcb_register4() to rpcb_register(), and PMAPPROC_UNSET ignores its protocol argument, so unwinding a partial TCP registration could also wipe mappings for existing listeners on other transports. "It might be that the best the kernel can do here is tear everything down if one registration fails," he wrote in his 11 August review.

Layton then floated making rpcbind errors non-fatal — pr_warn() and leave cleanup to the admin — rather than blocking even longer to unregister. Lever replied that he had been thinking of a declarative administrative UI: if the kernel cannot apply the requested configuration, it should fail back to the previous one. He also suggested moving rpcbind registration into userspace after the kernel listener is up. That exchange closed last week without a decision.

Separately, Lever flagged a netns leak in patch 8/8: the kselftest fixture leaves a live listener pinning the namespace. He suggested dropping any leftover serv from FIXTURE_TEARDOWN() via listener_set(NULL, 0) / threads_set(0).

This week: policy, not more unwind code

On 14 August Layton rejected both of Lever's alternatives as too large for this series. A true fail-back-to-previous-config model is "possible, but difficult":

"The original /proc interfaces were never this clean, so making the underlying bits behave this way for the netlink interfaces, but not the legacy /proc ones will be hard."

The kernel also does not currently preserve the old listener table, which that model would require.

Pushing rpcbind into userspace is likewise possible — a new boolean on the listener call meaning "don't do any rpcbind registration," then userspace registers if the kernel understands the flag — but:

"That's a major undertaking though and I don't like fundamentally changing the interface here, particularly when we'll still have to cope with doing this from the kernel for legacy cases."

He restated the non-fatal policy as the least-worst option:

"I still think the best solution of all would be to just say 'henceforth, rpcbind registration is non-fatal'. That just leaves the kernel succeeding the listener set today when it would have failed before, but will still printk() an appropriate warning in that case, so the admin should be aware that rpcbind registration failed, even though the server is up."

He asked Lever, plainly, what would make the series mergeable.

Conclusion: re-roll instructions

Lever accepted the policy the same day:

"Fair enough, let's go with that."

He then gave a concrete v3 punch list:

  • Keep patches 1, 2, 3 and 5 unchanged (transport-name validation, 1024-entry cap, first-error preservation in svc_register(), 1s local rpcbind timeout).
  • Drop patch 4/8 (the partial-registration unwind that collides with PMAPPROC_UNSET).
  • Make registration failure non-fatal for NFSv2 and NFSv3, as Layton proposed. That is the behavioural heart of the re-roll: today nfsd_version3 does not set vs_rpcb_optnl, so a v3-enabled server with no reachable rpcbind fails to bring up any listener; after the change the listener stays up and the admin is warned. NFSv4 is already optional via vs_rpcb_optnl.
  • Extend the extack in patch 6/8 so netlink can report a listener that came up without registering. write_ports() only has dmesg; Lever asked whether the netlink path can do better.
  • Fix the netns leak in patch 8/8.
  • Move any test that asserts unwind or abort onto the new non-fatal failure policy (in particular sem_register_refused, which currently requires -EACCES and no leftover listener when the stub answers RPCBPROC_SET with FALSE).

No v3 was posted in this window. The series remains aimed at v7.4. Client-side NFS is not touched; the user-visible change for administrators is that a v2/v3 nfsd listener will now come up even when local rpcbind is down or refuses SET, with a printk (and, on the netlink path, an extack) instead of aborting startup.

Status: design agreement, awaiting v3. Key remaining work is the non-fatal svc_register() policy, richer extack, the selftest netns teardown, and retargeting tests that currently require abort-on-rpcbind-failure.
