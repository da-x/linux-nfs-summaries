NFSv4 client OOB read in pNFS layout-type decode

Summary

This week’s linux-nfs traffic includes a standalone NFS client bug-fix from Alibaba’s Chuyf26: an integer-wrap out-of-bounds read in the NFSv4 XDR decoder for pNFS layout types. There were no replies in-window; the patch landed as a single-message thread and has not yet been acked, nacked, or revised.

What broke

Chuyf26 reports that decode_pnfs_layout_types() in fs/nfs/nfs4xdr.c feeds a server-supplied count into a bulk xdr_inline_decode():

"decode_pnfs_layout_types() passes nlayouttypes * 4 to a single xdr_inline_decode() call. nlayouttypes comes from the server and the multiplication can wrap around to a small value, so the bounds check only covers a few bytes while the following loop reads up to NFS_MAX_LAYOUT_TYPES words from the resulting pointer."

The attacker-controlled path is ordinary client FSINFO decoding — mount or statfs — via nfs4_xdr_dec_fsinfo() → decode_fsinfo() → decode_pnfs_layout_types(). After wrap, the pointer from xdr_inline_decode() sits at the end of the receive buffer, and the subsequent loop walks up to NFS_MAX_LAYOUT_TYPES words past it.

The failure mode is quieter than a typical KASAN splat, which is why the reporter flags it as easy to miss in testing:

"The XDR receive buffer is built from pages, not slab objects, so KASAN does not instrument these reads and the following memory is normally still mapped: the access silently produces garbage layout type values instead of failing the decode."

A malicious NFS server can therefore inject bogus layout-type values into the client’s fsinfo state at mount time rather than forcing a clean decode error.

The regression is attributed to 3132e49ecef9 ("pnfs: track multiple layout types in fsinfo structure") — the change that taught the client to keep more than one pNFS layout type. The report credits Abaci (abaci@linux.alibaba.com) and notes assistance from abaci:qwen3.8-max.

The proposed client fix

The patch is a 17-line change to fs/nfs/nfs4xdr.c (10 insertions, 7 deletions). The strategy is defensive decoding rather than a protocol change:

"Cap the number of layout types before reading them and decode each layout type word individually so every read is bounds checked."

That is the classic NFS client XDR hygiene: never multiply a server u32 into a bulk inline decode, clamp against the client’s NFS_MAX_LAYOUT_TYPES limit first, then pull one XDR word at a time so xdr_inline_decode() can reject each access independently. The result should be a failed FSINFO decode instead of a silent walk off the end of the receive pages.

Status this week

This is not a new feature and not a wire-protocol change; it is a client-side bounds-check fix against a malicious or buggy pNFS server. No maintainer review, test reports, or v2 appeared before the week closed on 2026-08-20. Until someone on the list comments, the practical takeaway for NFS client development is that decode_pnfs_layout_types() still trusts a wrapped nlayouttypes * 4 length, and this patch is the first proposed close of that hole.

A same-day sibling from the same author (GETDEVICEINFO notification bitmap OOB) uses the identical wrap-then-loop pattern in another nfs4xdr.c decoder, which suggests Abaci is sweeping bulk xdr_inline_decode(4 * server_count) sites rather than chasing an isolated layout-type bug. That GETDEVICEINFO thread is tracked separately.
