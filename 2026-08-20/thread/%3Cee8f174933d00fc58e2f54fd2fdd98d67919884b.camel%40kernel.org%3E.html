pNFS layoutreturn EBUSY sign fix, v2

Summary

A one-line Linux NFS client bug fix for pNFS layoutreturn scheduling landed this week as PATCH v2, after the first attempt was NAK'd for breaking recall replies on empty layouts.

This is a bug fix, not a new feature and not a protocol change. The regression is pinned to commit 41d0a8ead9720 ("NFSv4/pnfs: Add support for the PNFS_LAYOUT_FILE_BULK_RETURN flag"), which swapped pnfs_layout_segments_returnable() in pnfs_layout_need_return() for a direct call to pnfs_mark_layout_stateid_return() and then compared the result against EBUSY rather than -EBUSY.

Prior turn: v1 over-corrected, then got vetoed

Earlier this week, Tim Menninger posted v1 against fs/nfs/pnfs.c. The commit message already named the sign error:

"Since pnfs_mark_layout_stateid_return() returns negative errno values, the -EBUSY case is never detected."

v1 did not stop at flipping the sign. Menninger argued that pnfs_mark_layout_stateid_return() bottoms out in pnfs_mark_matching_lsegs_return(), which returns 0 when a layoutreturn should be scheduled, and therefore changed the comparison from EBUSY to 0. That would have deferred layoutreturn for every non-zero result, including -ENOENT (no matching segments).

Trond Myklebust rejected that the next day. The Linux NFS client maintainer's objection is about recall compliance on soft mounts, not about the original typo:

"This breaks the ability of the client to respond to layout recalls even when it does not think it holds a layout. That's a situation that can occur when using soft or softerr mounts."

The client invariant is that a layout recall can still arrive after the local pnfs_layout_hdr view has already been dropped or timed out. The return path has to remain usable when wire state and in-memory segments are out of lockstep.

This week's message: v2 restores the sign check only

On 19 August, Menninger replied to that NAK with PATCH v2. The one-line change in pnfs_layout_need_return() is now the minimal correction: compare against -EBUSY. The changelog is explicit about absorbing the review:

"Preserve the -ENOENT path so the client can respond to recalls when it no longer holds matching layout segments, as pointed out by Trond."

"Defer only on -EBUSY instead of requiring a zero return value."

v2 also adds Cc: stable@vger.kernel.org, treating the EBUSY vs -EBUSY mix-up as a stable-worthy client regression from the bulk-return flag work rather than a redesign of layoutreturn policy.

Client impact

pnfs_layout_need_return() is the gate that decides whether the NFS client should actually send a LAYOUTRETURN. After 41d0a8ead9720, busy segments never matched the unsigned EBUSY test, so the "segments still in use, defer the return" path was dead. v1 would have over-corrected in the other direction: only a successful mark (0) would proceed, skipping recalls when the client no longer holds matching lsegs. v2 restores the historical contract:

  • -EBUSY: defer; segments are still busy.
  • -ENOENT (and other non-busy results): still allow the client to answer a recall, including the empty-layout case Myklebust called out for soft/softerr.

Status

No further review of v2 landed on this thread before the week closed. The technical conclusion after the v1/v2 exchange is:

  • The EBUSY comparison in pnfs_layout_need_return() is wrong and never matches the negative errno from pnfs_mark_layout_stateid_return().
  • The correct fix is -EBUSY, not == 0.
  • A zero-only check would break layout-recall replies when the client no longer believes it holds matching segments.

Whether the signed -EBUSY check plus the preserved -ENOENT recall path is accepted as the stable fix for 41d0a8ead9720 remains outstanding.
