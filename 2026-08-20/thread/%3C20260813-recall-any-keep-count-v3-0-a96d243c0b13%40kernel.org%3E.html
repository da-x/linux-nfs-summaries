Jeff Layton reviews NFSD CB_RECALL_ANY keep-count series

Summary

Chuck Lever's v3 series to stop NFSD from blasting CB_RECALL_ANY with a keep count of zero picked up its remaining review tags this week, with Jeff Layton signing off on the shrinker-accounting half of the work.

Context from just before the window

On 13 August, Chuck Lever posted v3 of "NFSD: CB_RECALL_ANY fixes and a meaningful keep count" — a mix of protocol-usage bug fixes and a server-side shrinker redesign. The cover letter is blunt about the current behavior:

"NFSD currently sends every CB_RECALL_ANY with craa_objects_to_keep set to zero, as RFC 8881 Section 20.6.3 does not mandate any particular way for a client to choose which delegations to return, if any."

That zero is not a no-op. RFC 8881 defines craa_objects_to_keep as the number of recallable objects the client may retain; zero therefore asks the client to return every delegation it holds, including ones backing files that are still open. Lever's rationale is performance, not pedantry:

"a zero value can result in non-Linux clients giving back more delegations than is necessary to relieve temporary memory pressure on the server, which needlessly punctures the clients' delegation working set."

The Linux NFS client has been masking the bug. Lever notes that "only the Linux NFS client has been deeply tested against" NFSD's CB_RECALL_ANY, and that implementation "ignores the craa_objects_to_keep value and returns only one unused delegation of the named types." The fixed zero therefore never showed up in Linux-on-Linux testing. Non-Linux clients that honor the field would dump their working set on the first hint of server memory pressure.

v3 grew from a four-patch v1/v2 into eight patches after Lever split the state shrinker so the keep count can be apportioned. The first four patches already carried Layton's Reviewed-by from earlier rounds; this week's mail is the review of the new accounting work.

What the series actually changes

The eight patches, all in fs/nfsd/, fall into two buckets: client-visible protocol bugs, then the shrinker machinery needed to send a keep count that is not a lie.

Client-visible bug fixes (patches 1–4). Patch 1 stops deleg_reaper() from sending CB_RECALL_ANY to NFSv4.0 clients. That operation is NFSv4.1-only; a v4.0 callback service accepts only CB_GETATTR and CB_RECALL, so it replies OP_ILLEGAL. The decoder maps the unexpected opnum to -EIO, nfsd4_cb_done() marks the callback channel down, and nothing brings it back — nfsd4_run_cb_work() only sets NFSD4_CB_UP for minor version > 0, and the only nfsd4_probe_callback() a v4.0 client reaches is nfsd4_setclientid_confirm(). One visit from the reaper therefore leaves RENEW returning NFS4ERR_CB_PATH_DOWN for as long as the client holds delegations, and nfsd4_cb_channel_good() refuses to grant any more. Lever tags this Fixes: 44df6f439a17 ("NFSD: add delegation reaper to react to low memory condition").

Patch 2 adds cl_deleg_count on struct nfs4_client, maintained under nn->deleg_lock at the two sites that mutate cl_delegations. The reaper walks nn->client_lru under nn->client_lock and cannot take nn->deleg_lock to count the list; readers that hold only client_lock must treat the counter as a data_race(). No functional change on its own, but it is the input to the keep count.

Patch 3 adds RCA4_TYPE_MASK_DIR_DLG to craa_type_mask. RFC 8881 §20.6.3 distinguishes servers that share one pool among all recallable-object classes from those that keep per-class pools; NFSD is the former. Directory delegations already go through __alloc_init_deleg(), count against max_delegations, and are reclaimed by the shrinker, but the type mask never named them. Clients that implement directory delegations would otherwise skip them when choosing what to return.

Patch 4 is the keep-count change itself, also tagged against 44df6f439a17. Instead of zero, deleg_reaper() derives craa_objects_to_keep from cl_deleg_count so each callback asks the client to give up one delegation. Both the shrinker and the laundromat re-arm while the condition lasts, so a client with more to spare is asked again on the next pass. Lever is explicit that this is a no-op for Linux:

"The Linux client ignores craa_objects_to_keep and returns unused delegations selected from the type mask alone, so the count changes nothing for it."

The audience is every other NFSv4.1 client that actually reads the field.

Shrinker accounting (patches 5–8). These are the patches Layton reviewed this week. Patch 5 counts delegations per network namespace. The state shrinker is allocated per netns, but nfsd4_state_shrinker_count() was reporting host-wide num_delegations, so reclaim saw the population multiplied by the number of namespaces and a namespace holding nothing still queued its reaper. num_delegations remains the host-wide admission/ceiling check against max_delegations.

Patch 6 splits nfsd_client_shrinker into two. Courtesy-client reclaim is synchronous and deadlock-free; the shrinker can report a precise count of objects released. Delegation reclaim only sends CB_RECALL_ANY — clients are not obligated to return anything — so the callback cannot report progress. Worse, the combined shrinker fell back to delegation reaping only when no courtesy clients remained, so a single courtesy client kept a namespace's delegations out of the count.

Patch 7 records scan requests instead of discarding them with SHRINK_STOP. Courtesy scans accumulate in nfsd_shrink_backlog and are subtracted from the count until courtesy_client_reaper() runs. Delegations use a time bound: they are reported only once NFSD_RECALL_ANY_COOLDOWN_SECS have passed since the last sweep, matching deleg_reaper()'s skip of any client recalled inside that window.

Patch 8 is the client-facing payoff of that accounting. deleg_reaper() had been asking every eligible client for one delegation whenever it ran, "whether or not anything needs the memory." A delegation returned before it is needed costs the client an OPEN on the next touch. The scan callback now records nr_to_scan in nfsd_deleg_backlog and scales that total by each client's share of nn->nfsd_delegations. Nothing is recalled until a scan arrives, except nfs4_laundromat(), which has no scan request and instead computes what must go for num_delegations to fall below max_delegations, then passes only this namespace's share.

v3's changelog relative to v2 is exactly this accounting layer: per-namespace counts, separate shrinkers, scan-request discounting, and per-client scaling of the keep count.

This week's review

Layton's 14 August reply is short and conclusive. Patches 1–4 already carried his tag from the earlier rounds; for the new shrinker work he wrote:

"You can add this to 5-8:"

"Reviewed-by: Jeff Layton jlayton@kernel.org"

No technical objections, no requested respin, no discussion of the Linux client's decision to ignore craa_objects_to_keep. The client-side implication left on the table is that Linux will continue to return a single unused delegation per callback regardless of the newly meaningful keep count, while non-Linux clients should now see a proportional request instead of a demand to empty the working set.

Classification and status

This is a bug-fix series with a protocol-usage correction, not a protocol change and not a new feature. Two Fixes: tags point at the original delegation reaper (44df6f439a17): sending CB_RECALL_ANY to NFSv4.0 clients (callback channel permanently down, no further delegations) and advertising a keep count of zero (non-Linux clients over-returning). The rest is supporting machinery so the keep count can be a real fraction of each client's holdings under memory pressure.

With Layton's tags on all eight patches, v3 is fully reviewed. Subsequent v4/v5 postings (tracked as separate threads) pick the series up from here; this thread itself ends on that Reviewed-by.
