NFSv4.1 client rejects zero back-channel ca_maxrequests

Summary

This week’s linux-nfs traffic includes a tightly scoped NFSv4.1 client bug fix from Paula that closes a server-controlled slab out-of-bounds write in the back-channel slot table. The thread is a single patch posting dated 19 August; there were no review replies inside the week window.

What broke

The defect lives in session setup, not in a protocol change. After CREATE_SESSION, nfs4_verify_back_channel_attrs() is supposed to vet the attributes the server returns before those numbers size the callback slot table. Paula’s diagnosis is that the back-channel path never mirrored the fore-channel guard:

"Unlike its fore channel sibling nfs4_verify_fore_channel_attrs(), it never rejects a back channel ca_maxrequests (rcvd->max_reqs) of zero."

A zero max_reqs then reaches nfs4_realloc_slot_table() / nfs4_reset_slot_table(), which compute server_highest_slotid and max_slotid as max_reqs - 1. Because the arithmetic is unsigned:

"The subtraction is unsigned, so zero underflows to 0xffffffff and is stored as the table's slot-id ceiling."

With both ceilings poisoned, the later checks in nfs4_lookup_slot() (slotid <= max_slotid) and validate_seqid() (csa_slotid > server_highest_slotid) no longer constrain the slot id on a CB_SEQUENCE. nfs4_lock_slot() then does __set_bit(slotid, tbl->used_slots) against a fixed used_slots[] of SLOT_TABLE_SZ (16 unsigned longs, 1024 bits). Paula’s concrete example is a csa_slotid of 3584, which sets a bit 448 bytes past the array — a deterministic write into the neighbouring slab object.

KASAN reports the hit as a size-8 read in nfs4_lock_slot because __set_bit() is a read-modify-write and the sanitizer flags the load; Paula is explicit that the store is the real defect:

"KASAN labels the access below "Read of size 8" because __set_bit() is a read-modify-write and the sanitizer flags the load; the store is the actual defect, hence "out-of-bounds write"."

The reported call chain is the NFSv4 callback kthread: nfs4_callback_sequence → nfs4_try_to_lock_slot → nfs4_lock_slot, with the slot table allocated during nfs4_alloc_session / nfs41_init_client on the mount path.

Attack surface (client)

This is a malicious-server issue, not a local mount-option footgun. The back-channel attributes come from the server’s CREATE_SESSION reply:

"The attributes are chosen by the server in its CREATE_SESSION response: a malicious or compromised NFSv4.1 server, on the wire, with no authentication under sec=sys, and before the mount completes."

And:

"The slot id is server-controlled, so the write offset is attacker-chosen and deterministic."

Paula marks it reachable on any CONFIG_NFS_V4_1 client that mounts an NFSv4.1 export from a server the attacker controls or can spoof. That is a classic pre-mount, sec=sys callback-path write — important for anyone shipping an NFSv4.1 client against untrusted or MITM-able servers.

The proposed fix

The patch itself is two added lines in fs/nfs/nfs4proc.c: reject a zero back-channel ca_maxrequests in nfs4_verify_back_channel_attrs(), matching the existing fore-channel check. The -EINVAL then bubbles through nfs4_verify_channel_attrs() and aborts nfs4_proc_create_session() before nfs4_update_session() can install the underflowed ceiling.

"Reject a zero back channel ca_maxrequests in nfs4_verify_back_channel_attrs(), as nfs4_verify_fore_channel_attrs() already does, so the underflow never sizes the slot table."

It is tagged Fixes: 5405fc44c337 ("NFSv4.x: Add kernel parameter to control the callback server") and Cc: stable@vger.kernel.org, so the intent is a stable backport, not a new feature. The posting also carries Assisted-by: Bynario AI.

Status this week

No maintainer or reviewer comments landed on the thread before the 21 August cutoff. The technical argument on the list is therefore still Paula’s uncontested write-up: treat a zero back-channel ca_maxrequests as illegal at verification time, rather than trying to harden nfs4_lock_slot() after the slot-id ceiling has already wrapped. Until review, the client still accepts that zero and can size the callback slot table to 0xffffffff.

This sits in a small cluster of contemporaneous client-side bounds-check patches from the same author (decoder OOBs on pNFS layout types / GETDEVICEINFO, plus a SUNRPC xdr_inline_pages() write), but those are separate threads; this one is specifically the NFSv4.1 back-channel slot-table underflow.
