xprtrdma hang: serialize FRWR unmap_sync against disconnect

Summary

This week’s linux-nfs traffic includes a client-side RDMA hang fix from Tim Menninger (Pure Storage), targeting a long-standing race in the xprtrdma FRWR path that can stall rpciod during rapid disconnect/reconnect. The thread is a bug fix, not a protocol change: frwr_unmap_sync() can post LOCAL_INV work after rpcrdma_xprt_disconnect() has already drained the QP, then sleep forever waiting for a CQE that will never arrive.

The hang

Menninger’s v1 describes a four-step race:

  1. frwr_unmap_sync() snapshots r_xprt->rx_ep
  2. rpcrdma_xprt_disconnect() drains the QP
  3. frwr_unmap_sync() posts LOCAL_INV WRs after the drain
  4. No CQE arrives, so wait_for_completion() blocks indefinitely

The hung task sits on the rpciod workqueue:

"Workqueue: rpciod rpc_async_schedule [sunrpc]
wait_for_completion()
frwr_unmap_sync()
xprt_rdma_free()
xprt_release()"

The reproduction is pNFS-flavored: v7.2-rc6 under load with repeated data-server restarts to force QP disconnect/reconnect cycling. Without the fix, Menninger hit the hang twice in six attempts; with it, 300 cycles stayed clean. The same stall has been seen on v6.8 and v6.18.34. v1 tagged Fixes: c9918ff56dfb ("xprtrdma: Add ro_unmap_sync method for FRWR") and CCed stable.

The proposed serialization was an rx_unmap_rwsem plus an rx_unmap_active inflight counter. frwr_unmap_sync() takes the read side through ib_post_send(), then drops it before waiting so disconnect can take the write side and drain. Disconnect then waits for the counter to hit zero before tearing down endpoint and MR state.

Chuck Lever: real bug, too much new machinery

Chuck Lever agreed on the diagnosis and on the rwsem closing the post-after-drain window, but pushed back hard on the shape of the fix:

"I agree there is a bug. The proposed fix introduces technical debt that I would rather not see in-tree. Importantly, there are areas where you can reuse existing code instead of open-coding, the Fixes: tag might be wrong, and a few code comments need updating as part of the fix."

On the history, Lever walked the FRWR timeline: c9918ff56dfb landed in v4.5 when rx_ep was still an embedded struct, frwr_op_unmap_sync() posted to ia->ri_id->qp, and disconnect flushed CQs without draining the QP. ib_drain_qp() arrived in v4.7; the sync unmap moved to xprt_rdma_free() in v5.3. The race as described needs a freeable rx_ep and the r_xprt->rx_ep = NULL store, both from v5.7:

"Should the tag be:
Fixes: e28ce90083f0 ("xprtrdma: kmalloc rpcrdma_ep separate from rpcrdma_xprt")"

That also undercuts v1’s claim that the race has existed “since synchronous FRWR invalidation was introduced.”

Lever also asked why only the sync path is special. xprt_rdma_free() runs from xprt_release() after ->release_xprt has dropped the transport send lock, so it is the one LOCAL_INV poster disconnect is not already serialized against. frwr_unmap_async() runs inline from rpcrdma_wc_receive() → rpcrdma_reply_handler(), which ib_drain_rq() orders ahead of ib_drain_sq().

The rest of the review is about not inventing new lifetime tracking:

  • The kernel-doc for frwr_unmap_sync() still says it always sleeps until mapped memory is safe; an early return when rx_ep is NULL is only correct because rpcrdma_reqs_reset() has already released that request’s MRs.
  • The comment claiming “the RPC reply handler won’t call us unless re_id->qp is a valid pointer” is leftover from the async path and does not describe xprt_rdma_free().
  • rx_unmap_active could go away. The waiter sleeps on mr->mr_linv_done, which rpcrdma_mrs_destroy() can free; moving the completion onto struct rpcrdma_req (still alive for the duration of xprt_rdma_free()) would decouple that. Endpoint lifetime after up_read() could be an rpcrdma_ep_get() / rpcrdma_ep_put() pair instead of a counter. Together that would drop the atomic, the wait_var_event() in disconnect, and the atomic_set() in setup, “and leave the rwsem with one job.”
  • Putting the lock on struct rpcrdma_ep was considered, but Lever noted rpcrdma_xprt_drain() already fences the receive side with ep->re_receiving / ep->re_done, and an rwsem on the transport outlives every endpoint it guards.

v2: reuse existing lifetime objects

Menninger’s v2 takes Lever’s review almost point-for-point.

The Fixes: tag moves to e28ce90083f0. The changelog now spells out the async-versus-sync ordering:

"frwr_unmap_async() runs inline from Receive completion processing. rpcrdma_xprt_drain() drains the Receive Queue before the Send Queue, so asynchronous LOCAL_INV Work Requests are submitted before Send Queue drain. frwr_unmap_sync(), however, runs from xprt_rdma_free() after the transport send lock has been released, so it is not ordered against disconnect."

Mechanically, v2:

  • Keeps rx_unmap_rwsem on struct rpcrdma_xprt (an endpoint-resident lock cannot protect the initial rx_ep lookup).
  • Holds the read side while sampling rx_ep, building the LOCAL_INV chain, and posting; disconnect holds the write side across QP drain and teardown; the read side is dropped before waiting so drain can complete the posted WRs.
  • Rechecks rl_registered after acquiring the rwsem, in case disconnect reset the request while the reader was blocked, and returns without posting.
  • Moves the synchronous invalidation completion from the final MR onto struct rpcrdma_req.
  • Takes an endpoint reference across the wait and the error path.
  • Removes rx_unmap_active and the disconnect-side wait.
  • Updates the transport-recovery comments, LOCAL_INV wake kernel-doc, frwr_unmap_sync() kernel-doc, and the QP-posting locking comment.

Retest on the same pNFS restart loop: hang twice in six attempts without the fix; none across 200 cycles with v2.

As of the week’s close, v2 is on the list and awaiting further review. The discussion has already narrowed from “add a new inflight counter” to “serialize the one unmap path that QP drain does not already order, using the request and endpoint objects that already outlive the wait.”
