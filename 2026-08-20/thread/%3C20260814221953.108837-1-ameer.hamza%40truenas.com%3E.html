sunrpc: keep groups when mountd GID lookup fails

Summary

This week closed a long-standing NFS server authorization bug in the sunrpc auth.unix.gid cache: a transient name-service failure under rpc.mountd --manage-gids was being cached as a successful empty group list, stripping a UID of every supplementary group for the rest of mountd's TTL. The two-patch v2 series from Ameer Hamza (TrueNAS) was reviewed, Acked in spirit by Jeff Layton, and applied to nfsd-testing by Chuck Lever the same day.

The work is a bug fix, not a protocol change and not a client-side feature. The client still sends the groups it thinks it has; the server was throwing them away. That matters for any NFSv3/v4 sec=sys or sec=krb5 mount whose access depends on supplementary groups (project directories, shared homes, AD/winbind setups).

From v1: same bug, two transports

Hours earlier Hamza posted a single-patch v1 that only fixed the classic /proc/net/rpc/auth.unix.gid/channel parser. Chuck Lever asked for a split:

"Looks like the same bug exists for the new mountd netlink mechanism. Since that instance of the bug arrived in a different commit, that fix needs to be a separate patch with its own Fixes: tag."

Hamza agreed and sent v2 the same evening.

The failure mode

On a server running rpc.mountd --manage-gids, a brief getpwuid() / getgrouplist() failure (winbind or sssd unreachable) makes mountd answer the auth.unix.gid upcall with zero groups. The kernel treated that as a valid positive cache entry. svcauth_unix_set_client() then replaced the RPC credential's group list with the empty one on every subsequent request — including RPCSEC_GSS via svcauth_gss_set_client(). Hamza's cover letter put the blast radius plainly:

"One failed lookup strips that uid of all supplementary groups on every export for up to mountd's configured TTL (30 minutes by default), long after the NSS backend has recovered."

The semantic argument is that mountd cannot send an empty list for a successful lookup: getgrouplist(3) always includes at least the user's primary group, so a zero-group reply can only mean the lookup failed. Recording it as a negative entry makes unix_gid_find() return -ENOENT, and svcauth_unix_set_client() keeps the groups the RPC credential already carries — the fallback promised by commit 3fc605a2aa38 ("knfsd: allow the server to provide a gid list when using AUTH_UNIX authentication") and the same state try_to_negate_entry() already creates when no listener holds the channel open.

The reproducer is a one-liner against the classic channel: after a successful cat of a 0750 root:proj file as a user whose supplementary group is proj, injecting

echo "$(id -u alice) $(( $(date +%s) + 600 )) 0" > /proc/net/rpc/auth.unix.gid/channel

turns the next access into EACCES until refresh, flush, or expiry.

Patch 1: classic /proc channel

Patch 1 (sunrpc: treat empty auth.unix.gid replies as negative entries) teaches unix_gid_parse() to install a CACHE_NEGATIVE entry when the reply carries zero groups. Seven lines in net/sunrpc/svcauth_unix.c. Hamza reported it tested on a live 6.12 server over NFSv3 and NFSv4.0–v4.2 with both sec=sys and sec=krb5, and said it applies unmodified (fuzz 0) to every maintained stable tree from 5.10.y through 7.1.y. Fixes tag: 3fc605a2aa38.

Patch 2: netlink NEGATIVE flag

Patch 2 (sunrpc: honor the netlink unix_gid NEGATIVE flag) is the same defect on the newer netlink upcall. The protocol already has SUNRPC_A_UNIX_GID_NEGATIVE for failed lookups, and mountd sends it, but sunrpc_nl_parse_one_unix_gid() only allocated an empty group list without propagating the flag — so a flagged reply still became a positive empty entry. The two-line fix sets CACHE_NEGATIVE for flagged replies, matching the netlink ip_map path. An empty GIDS list without the flag remains a positive entry. Fixes tag: 0850e8603cd7 ("sunrpc: add netlink upcall for the auth.unix.gid cache"). Build- and static-checked (sparse, W=1) but not runtime-tested.

A leftover netlink-generation hole

While reviewing the netlink path, Hamza documented a related but separate issue: in steady-state netlink-only operation, mountd currently receives no unix_gid upcalls at all. unix_gid_upcall() still gates request generation on cache_listeners_exist(), which counts only classic-channel writers, and netlink-mode mountd opens no /proc channels. A flagged reply reaches the parser today only via the 30-second post-close grace window, a concurrent classic-channel writer, or a direct SUNRPC_CMD_UNIX_GID_SET_REQS. Patch 2 therefore fixes parser semantics ahead of that; making upcall generation netlink-aware needs a per-cache listener signal (mountd subscribes to the notification group even without --manage-gids) and was left for a separate, runtime-tested series.

Client-facing takeaway

No NFS client code changes. The client impact is that group-based access on --manage-gids servers no longer collapses for half an hour after a brief NSS glitch: the server keeps the groups already on the RPC credential instead of replacing them with an empty list. Operators of AD/winbind/sssd NFS servers, and anyone exporting 0750 project trees keyed off supplementary groups, are the audience. The netlink upcall-generation gap remains open; until that follow-up lands, netlink-only mountd still may not ask for GID maps in the first place.
