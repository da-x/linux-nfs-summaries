pNFS layout-return validity check NACKed

Summary

This week’s linux-nfs traffic on Tim Menninger’s pNFS client patch is a short, decisive maintainer rejection rather than a design iteration. The original change, posted 13 August from Pure Storage, is a proposed bug fix in the Linux NFS client’s pNFS error path: stop a stale layout segment from marking a replacement layout for return. Linux NFS client maintainer Trond Myklebust answered on 18 August with a hard NACK, arguing that the proposed NFS_LSEG_VALID gate would violate the client’s obligation to report I/O errors on layoutreturn.

Prior week, in brief

Menninger’s patch targets pnfs_error_mark_layout_for_return(). That helper already receives the lseg tied to the failed I/O, but previously used only the segment’s I/O mode and then operated on the inode’s current layout header, without asking whether the lseg itself was still valid.

The failure mode is a classic pNFS state-id race on the client:

  • A layout stateid can be invalidated while RPCs still hold references to its layout segments.
  • pnfs_mark_layout_stateid_invalid() clears NFS_LSEG_VALID on those segments via pnfs_clear_lseg_state().
  • A later LAYOUTGET can install a replacement stateid on the same pnfs_layout_hdr.
  • If an RPC that still holds an old lseg then reports an error, the existing code can mark the new layout for return.

Menninger’s conclusion was that once NFS_LSEG_VALID is gone, the segment “is no longer eligible for selection for new I/O and must not initiate another error-driven return of the inode’s current layout.” The patch folded pnfs_mark_layout_for_return() into pnfs_error_mark_layout_for_return() and added a pnfs_is_valid_lseg() check alongside pnfs_layout_is_valid() before setting return info. It was also tagged Cc: stable@vger.kernel.org.

The reproduction is operationally severe. Restarting a FlexFiles data server under a high-throughput read workload caused stale lsegs to repeatedly mark the replacement layout for return, which in turn cancelled I/O, forced RPC/RDMA reconnects, and produced sustained inode->i_lock contention. Menninger reported that the client did not recover on its own and burned about 94 CPU cores on a 96-CPU system; with the patch, I/O recovered in about 20 seconds and recovery load peaked around 15 cores.

This week: maintainer NACK on protocol grounds

Myklebust did not contest the FlexFiles storm as an observed client failure. He rejected the premise of the fix: that NFS_LSEG_VALID is an appropriate gate for layout returns.

"I strongly disagree with the above premise that NFS_LSEG_VALID should be used to gate layout returns. If the client tries to do I/O and fails, then it is required to report the error, the type of I/O, and the byte range to which it applies."

That is a protocol-and-client-architecture argument, not a style nits. In the pNFS client, a failed I/O is supposed to feed a layoutreturn that describes what failed. The client then redrives that layoutreturn as outstanding I/O requests fail. Myklebust pointed at the existing EBUSY serialization as the intended collector, not a validity bit on the old segment:

"We attempt to redrive that layoutreturn as the outstanding I/O requests fail. The EBUSY is there to ensure that we don't fire off the layoutreturn until all the errors have been collected."

From that reading, Menninger’s extra pnfs_is_valid_lseg() check would drop error-driven returns for I/O that still belongs to an invalidated segment—exactly the I/O the server still needs to hear about—rather than waiting until every in-flight failure has been folded into one layoutreturn. The verdict was unambiguous:

"So NACK to this patch."

No alternative patch, no request for a v2 with a different predicate, and no follow-up from Menninger appeared in this window. The discussion therefore ends this week as an open client bug with a rejected approach: the FlexFiles recovery storm is still on the table, but gating layoutreturn on NFS_LSEG_VALID is not an accepted way to stop it.

What this means for NFS client development

This is not a protocol change and not a new feature. It is a proposed client bug fix in the pNFS layout-return error path, and it collides with a long-standing client invariant: layoutreturn is how the client reports failed I/O ranges, even after the layout stateid that originated those I/Os has been invalidated and replaced.

The important client-side takeaway is the split between two recovery mechanisms that the patch tried to collapse:

  1. Segment validity (NFS_LSEG_VALID) — used to stop new I/O from selecting a dead lseg after pnfs_mark_layout_stateid_invalid().
  2. Error-driven layoutreturn — used to report I/O that already ran (or tried to run) against that segment, with EBUSY holding the return until the error set is complete.

Menninger treated (1) as a reason to suppress (2) against the inode’s current layout, on the theory that a stale lseg must not poison a replacement stateid. Myklebust treated (2) as mandatory regardless of (1), because the replacement layout and the failed byte range still have to be reconciled with the server. Until someone proposes a fix that preserves error collection—perhaps by tying the return to the failed layout’s identity rather than silencing the return entirely—the high-CPU FlexFiles restart path remains unfixed in-tree.

Status this week: patch NACKed; no merge, no v2, no alternative posted.
