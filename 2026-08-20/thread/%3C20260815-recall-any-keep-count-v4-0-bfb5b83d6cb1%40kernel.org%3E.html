NFSD v4 keep-count series draws a 5.10 backport request

Summary

Chuck Lever posted v4 of "NFSD: CB_RECALL_ANY fixes and a meaningful keep count" on 15 August, carrying Jeff Layton's Reviewed-by on all eight patches and a one-line v4 delta: avoid a divide-by-zero when max_delegations is zero. The series is a bug-fix plus protocol-usage correction, not a protocol change. Two Fixes: tags still point at 44df6f439a17 ("NFSD: add delegation reaper to react to low memory condition"). The only new debate this week is whether the keep-count fix belongs on stable kernels back to 5.10, and whether clients that dump every delegation on a zero keep count are conforming or defective.

Why the keep count matters to clients

The cover letter restates the problem that Linux-on-Linux testing has been hiding. NFSD currently sends every CB_RECALL_ANY with craa_objects_to_keep set to zero. RFC 8881 §20.6.3 defines that field as the number of recallable objects the client may retain, so zero is a request to return every delegation, including ones backing still-open files.

"NFSD currently sends every CB_RECALL_ANY with craa_objects_to_keep set to zero, as RFC 8881 Section 20.6.3 does not mandate any particular way for a client to choose which delegations to return, if any."

The Linux NFS client has been masking the bug. Lever notes that "only the Linux NFS client has been deeply tested against" NFSD's CB_RECALL_ANY, and that implementation "ignores the craa_objects_to_keep value and returns only one unused delegation of the named types." A zero keep count therefore never produced visible misbehavior in Linux-on-Linux testing. Non-Linux clients that honor the field would dump their working set on the first hint of server memory pressure:

"a zero value can result in non-Linux clients giving back more delegations than is necessary to relieve temporary memory pressure on the server, which needlessly punctures the clients' delegation working set."

The series therefore changes NFSD so each CB_RECALL_ANY asks a client to give up a sensible number of delegations instead of all of them at once. The shrinker split in patches 5–8 exists so that keep count can be a real fraction of each client's holdings rather than a constant.

Client-visible bug fixes (patches 1–4)

Patch 1 stops deleg_reaper() from sending CB_RECALL_ANY to NFSv4.0 clients. That operation is NFSv4.1-only; a v4.0 callback service accepts only CB_GETATTR and CB_RECALL, so it replies OP_ILLEGAL. The decoder maps the unexpected opnum to -EIO, nfsd4_cb_done() marks the callback channel down, and nothing brings it back — nfsd4_run_cb_work() only sets NFSD4_CB_UP for minor version > 0, and the only nfsd4_probe_callback() a v4.0 client reaches is nfsd4_setclientid_confirm(). One visit from the reaper therefore leaves RENEW returning NFS4ERR_CB_PATH_DOWN for as long as the client holds delegations, and nfsd4_cb_channel_good() refuses to grant any more. Skip clients at minor version zero.

Patch 2 adds cl_deleg_count on struct nfs4_client, maintained under nn->deleg_lock at the two sites that mutate cl_delegations. The reaper walks nn->client_lru under nn->client_lock and cannot take nn->deleg_lock to count the list; readers that hold only client_lock must treat the counter as a data_race(). No functional change on its own, but it is the input to the keep count.

Patch 3 adds RCA4_TYPE_MASK_DIR_DLG to craa_type_mask. RFC 8881 §20.6.3 distinguishes servers that share one pool among all recallable-object classes from those that keep per-class pools; NFSD is the former. Directory delegations already go through __alloc_init_deleg(), count against max_delegations, and are reclaimed by the shrinker, but the type mask never named them. Clients that implement directory delegations would otherwise skip them when choosing what to return.

Patch 4 is the keep-count change itself, also tagged against 44df6f439a17. Instead of zero, deleg_reaper() derives craa_objects_to_keep from cl_deleg_count so each callback asks the client to give up one delegation. Both the shrinker and the laundromat re-arm while the condition lasts, so a client with more to spare is asked again on the next pass. Lever is explicit that this is a no-op for Linux:

"The Linux client ignores craa_objects_to_keep and returns unused delegations selected from the type mask alone, so the count changes nothing for it."

The audience is every other NFSv4.1 client that actually reads the field.

Shrinker accounting so the keep count is not a lie (patches 5–8)

Patch 5 counts delegations per network namespace. The state shrinker is allocated per netns, but nfsd4_state_shrinker_count() was reporting host-wide num_delegations, so reclaim saw the population multiplied by the number of namespaces and a namespace holding nothing still queued its reaper. num_delegations remains the host-wide admission/ceiling check against max_delegations.

Patch 6 splits nfsd_client_shrinker into two. Courtesy-client reclaim is synchronous and deadlock-free; the shrinker can report a precise count of objects released. Delegation reclaim only sends CB_RECALL_ANY — clients are not obligated to return anything — so the callback cannot report progress. Worse, the combined shrinker fell back to delegation reaping only when no courtesy clients remained, so a single courtesy client kept a namespace's delegations out of the count.

Patch 7 records scan requests instead of discarding them with SHRINK_STOP. Courtesy scans accumulate in nfsd_shrink_backlog and are subtracted from the count until courtesy_client_reaper() runs. Delegations use a time bound: they are reported only once NFSD_RECALL_ANY_COOLDOWN_SECS have passed since the last sweep, matching deleg_reaper()'s skip of any client recalled inside that window.

Patch 8 is the client-facing payoff of that accounting. deleg_reaper() had been asking every eligible client for one delegation whenever it ran, "whether or not anything needs the memory." A delegation returned before it is needed costs the client an OPEN on the next touch. The scan callback now records nr_to_scan in nfsd_deleg_backlog and scales that total by each client's share of nn->nfsd_delegations. Nothing is recalled until a scan arrives, except nfs4_laundromat(), which has no scan request and instead computes what must go for num_delegations to fall below max_delegations, then passes only this namespace's share. The v4 changelog's divide-by-zero guard is for the case where max_delegations is zero in that apportionment.

Backport request, and a client-bug diagnosis

Cedric Blancher added a Reviewed-by on patch 4 and asked for a deep stable backport:

"Could you please backport this to the stable branches up to Linux 5.10, because conforming NFSv4.1 clients get robbed of all their delegations if craa_objects_to_keep=0."

Lever declined on two independent grounds. First, the series simply does not apply that far:

"v6.18 is as far back as this series can apply with reasonable effort."

Second, he rejected the premise that a zero keep count "robs" a conforming client. RFC 8881 §20.6.3 leaves the choice of which and how many delegations to return with the client:

"What you are describing is a client bug. RFC 8881 Section 20.6.3 says clients get to choose which and how many delegations to return in response to a CB_RECALL_ANY request."

And, more sharply:

"clients that respond to CB_RECALL_ANY by returning all delegations unconditionally are not conformant, but are defective and should be fixed."

That is the week's client-development takeaway. Linux already ignores craa_objects_to_keep and returns a single unused delegation of the named types, so the keep-count change is a no-op for it; the NFSv4.0 skip in patch 1 is the Linux-client-visible bug fix (callback channel no longer permanently marked down). Non-Linux clients that treat a zero keep count as "return everything" are, in Lever's reading, the ones that need to change. The series still stops advertising zero so those clients are not provoked, but the server will not paper over that behavior on kernels older than 6.18.

v4 itself is already superseded: Lever posted v5 two days later (tracked separately) with further shrinker-accounting tweaks — exclude skipped clients from the apportionment divisor, skip clients whose CB_RECALL_ANY is still running, and discount the delegation shrinker's count by pending requests. This v4 thread ends on the stable-backport exchange.
