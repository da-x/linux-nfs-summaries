fsnotify patch 03: dnotify recalc must not walk d_children under mark->lock

Summary

This week the fsnotify maintainers finally catch up with patch 03/12 of NeilBrown’s negative-dentry RFC — the change that tried to drop mark->lock before fsnotify_recalc_mask() so a later cond_resched() can run while walking d_children. The discussion is a locking bug-fix, not a protocol change and not a new NFS feature. No NFS client code is touched in these six mails, but the patch is a prerequisite for the series’ NFS-facing iterator work: until fsnotify can drop its spinlocks, d_for_each_positive_child() cannot schedule, and the NFS client’s nfs_clear_verifier_directory() walk of a huge sibling list remains a soft-lockup hazard.

The week ends with Jan Kara rejecting the original “just move the recalc outside the spinlock” approach, Amir Goldstein supplying a narrower mark.c patch, and Jan offering to take that patch immediately. Neil has not yet said whether he will fold it into v2.

Brief bridge from prior weeks

Brown posted the 12-patch RFC on 3 August. Patch 03 stops dnotify_recalc_inode_mask() from calling fsnotify_recalc_mask() under a spinlock, returning a “please recalc” flag instead, so callers can drop the lock first. Last week (outside this window) Miklos Szeredi asked the obvious question of the new dnotify_handle_event() call site:

"Is the fsnotify_group_lock() held in this case? I don't see it."

Neil’s 11 August reply admitted it is not held and sketched extra SRCU-side safety. This week he comes back with a firmer conclusion — and then the fsnotify maintainers tell him the lifetime rules are subtler than that.

Neil concludes SRCU is enough

On 15 August NeilBrown reports that he dug into Miklos’s question and no longer wants the extra code:

"I dug into this some more, and we do rely on srcu, but don't need the extra code below. inode_mark->lock doesn't protect inode_mark->connector, so moving the dereference out of the lock has no effect. srcu_read_lock is taken before we get the ref to the mark, so the mark and the connector cannot disappear underneath us. A race could result in inode_mark->connector reading as NULL, but fsnotify_recalc_mask() checks for NULL, so there is no risk for harm."

That is the high-water mark of confidence in patch 03 as posted. Two days later Jan Kara, back from vacation, takes it apart.

Jan Kara: the comment is the contract

Jan opens with the comment sitting above fsnotify_recalc_mask():

"Calculate mask of events for a list of marks. The caller must make sure connector and connector->obj cannot disappear under us. Callers achieve this by holding a mark->lock or mark->group->mark_mutex for a mark on this list."

and the verdict:

"and you very obviously start violating these rules with your changes."

He then reconstructs why those rules exist. A connector lives as long as any mark remains on its list. Marks and connectors are SRCU-protected. FSNOTIFY_MARK_FLAG_ATTACHED is set if and only if connector->obj still points at a live inode/mount, and that flag changes only under mark_mutex — which is why most callers of fsnotify_recalc_mask() hold the mutex. dnotify is the odd one out: it has to tweak a mark mask from event handling, where mark_mutex is forbidden by lock ordering. The fallback is mark->lock, because that same lock is required to clear FSNOTIFY_MARK_FLAG_ATTACHED.

Even the existing dnotify call is “somewhat racy”, because dnotify_handle_event() can run after ATTACHED has already been cleared. Moving the recalc outside mark->lock makes the race with fcntl_dirnotify() dropping the mark easier to hit. There is no direct UAF — the inode is pinned on the notification path and SRCU covers the rest — but:

"fsnotify_recalc_mask() simply isn't prepared for the connector changing under it due to object getting detached and so we could end up doing weird things like NULL ptr derefs or similar stuff."

"So this call to fsnotify_recalc_mask() from dnotify needs a more careful handling. Which is sad because I doubt anybody still uses dnotify..."

That last line becomes the week’s escape hatch.

Amir’s way out: skip the optimization

Amir Goldstein treats dnotify’s obscurity as a feature:

"dnotify_recalc_inode_mask() can only remove bits from i_fsnotify_mask, so it is an optimization."

"If we just remove fsnotify_recalc_mask() call from dnotify_recalc_inode_mask(), then i_fsnotify_mask will be updated when dnotify_mask gets removed eventually."

"If nobody uses dnotify, noone is likely to notice the loss of the optimization."

In other words: the event path never adds watch bits, so it does not need to walk children to set DCACHE_FSNOTIFY_* flags. Dropping the recalc entirely is safe; the mask catches up when the mark finally goes away.

Neil wants a smaller cut

Neil had been thinking along the same lines, but does not want to delete the whole recalc:

"I don't think we need to drop all of fsnotify_recalc_mask(), only the fsnotify_conn_set_children_dentry_flags() part that walks the d_children list. And that only happens when we add to the mask, not when bits are cleared. So maybe the fsnotify_conn_set_children_dentry_flags() simply never happens in this context so it doesn't need fixing."

He prefers to make that invariant visible in the code (a dnotify.c patch, omitted from ingest) and, importantly, still withholds agreement on Jan’s locking story:

"Note that I'm not (yet) convinced by the locking argument, but maybe we don't need to pursue it."

That is the NFS-relevant technical point: the only reason patch 03 exists is to get the d_children walk off a spinlock. If that walk never runs from dnotify’s event path, patch 03 as written is solving the wrong problem — and the later sleepable iterator can proceed without moving the recalc outside mark->lock.

Amir’s mark.c patch, and Jan’s ACK

Amir’s 19 August follow-up (body truncated at ingest; reconstructed from Jan’s quotes) posts a fs/notify/mark.c patch (73bbfcd1b21a0fc723999aee36af662f36ba4dd2) that drops the update_children local and, from Jan’s reply, arranges that the child-dentry-flag walk is not the thing dnotify does under mark->lock. Amir also appears to have questioned whether the children-flag update is even needed from fcntl_dirnotify().

Jan agrees with the “walk never happens from this path” half of Neil’s argument, and interprets “doesn’t need fixing” as “leave the dnotify fsnotify_recalc_mask() call site alone”:

"I agree with the "fsnotify_conn_set_children_dentry_flags() never happens from this path" part. I'm not sure I follow the "it doesn't need fixing" part - do you mean you will just not touch where dnotify calls fsnotify_recalc_mask()? In that case I agree."

He wants Neil’s clarifying patch (“Definitely”), is still puzzled by Neil’s scepticism of the locking argument (“Not sure what you mean here…”), and corrects Amir on the add path:

"Yes, it is not. Dnotify places mark on directory and sets FS_EVENT_ON_CHILD so it depends on dentry flags to be updated from fcntl_dirnotify()."

That is the invariant the series actually needs: child dentry flags are installed when a watch is added (fcntl_dirnotify()), under locks that can sleep; the event path only clears bits and must not walk d_children. Amir’s mark.c change gets a clean ACK:

"Looks good to me, Neil will you pick this into your series or should I pick the patch into my tree rightaway?"

Jan also flags the documentation debt once Brown’s later patches let the iterator sleep:

"As a side note once Neil allows the dentry iteration to sleep, we should document in the comment above that mark->lock can be used only for !update_children case and perhaps assert it in the function as well."

No reply from Neil lands in-window. The merge question — fold Amir’s patch into v2 of the negative-dentry series, or let Jan take it now — is still open at the week’s close.

Why this matters for NFS client development

This sub-thread never mentions fs/nfs/. The NFS client still cares, for two reasons.

First, patch 02 of the same series converts nfs_clear_verifier_directory() onto d_for_each_positive_child() and already drops the parent d_lock between nfs_unset_verifier_delegated() on the parent and the same call on every child. That iterator is annotated might_sleep() only after patches 03–11 have stripped every spinlock from the walk. If patch 03 is wrong, the NFS verifier walk cannot schedule, and a directory with a pathological number of negative children remains a client-side soft lockup.

Second, the resolution this week is exactly the kind of lock-constraint discovery Brown asked NFS and VFS reviewers for. The original patch 03 treated “don’t hold a spinlock across recalc” as sufficient. Jan’s reconstruction shows the real constraint is which recalc is allowed under mark->lock: mask-only, never the children-flag walk. That is the bug fix the series now has to absorb before the NFS client change is safe to merge.

Final conclusions (as of 20 August)

  • Classification: VFS/fsnotify locking bug-fix inside a larger negative-dentry hardening RFC. Not a protocol change, not an NFS feature, but a merge blocker for the NFS client iterator conversion.
  • Patch 03 as posted is not acceptable. Moving fsnotify_recalc_mask() off mark->lock violates the documented connector/connector->obj lifetime rules and widens a pre-existing dnotify vs fcntl_dirnotify() race into possible NULL derefs, even though SRCU prevents a straight UAF.
  • The d_children walk is the only part that needed to move, and it does not run on the dnotify event path because that path only clears bits. Child dentry flags are the fcntl_dirnotify() add path’s job (FS_EVENT_ON_CHILD).
  • Disposition: Amir’s mark.c patch to stop treating children-flag update as part of the mark->lock recalc is ACKed by Jan, who is willing to take it immediately. Neil’s clarifying dnotify patch is also wanted. Neil has not yet answered, and has not conceded Jan’s locking argument.
  • NFS client impact this week: none in code. The practical effect is that v2 of the series will have to replace patch 03 with the narrower “don’t walk children under mark->lock” approach before the sleepable d_for_each_positive_child() used by nfs_clear_verifier_directory() can land.
