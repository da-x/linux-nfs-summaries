NFSD: Fail truncated pool_threads reads

Summary

NFSD: Fail a pool_threads read whose reply does not fit

This week Chuck Lever posted a one-patch NFSD bug fix for a silent truncation in the pool_threads nfsctl reply. There were no replies on this thread in the week ending 2026-08-20. The change is server-side (fs/nfsd/nfsctl.c); it is not an NFS client or protocol change.

The bug

write_pool_threads() (the nfsctl handler that both writes and then reports per-pool thread counts) formats that list into a buffer capped at SIMPLE_TRANSACTION_LIMIT bytes. The existing code used snprintf() and then strlen() to size the reply. Lever described the failure mode:

"snprintf() truncates its last write and strlen() measures only what fit, so a reply too long for that buffer ends mid-number with no terminating newline. A pool running 4096 threads is reported as 40. Nothing marks the reply as incomplete, so an administrator reads a plausible but wrong count."

That is the operational hazard: a truncated integer still looks like a valid thread count. An admin reading /proc/fs/nfsd/pool_threads (or the equivalent nfsctl transaction) can act on a number that is simply the leading digits of the real value.

The patch tags Fixes: eed2965af1ba ("[PATCH] knfsd: allow admin to set nthreads per node"), the 2006 change that first allowed per-node/per-pool thread counts. Suggested-by credit goes to David Laight, with a link to his earlier overflow analysis.

The fix

Rather than trusting strlen() on the truncated buffer, Lever takes snprintf()'s return value, which reports how many bytes would have been written. If that exceeds remaining space, the read fails with -ENAMETOOLONG. He notes that this is already the errno svc_one_xprt_name() returns for the same "reply does not fit" condition, so the nfsctl interface stays consistent with other NFSD name/list formatters.

The diff is small: 8 insertions, 4 deletions in fs/nfsd/nfsctl.c. Behavior on the success path is unchanged; only an oversized per-pool list becomes an explicit error instead of a quietly chopped number.

How this relates to the overflow thread

The week before, Laight posted [PATCH net-next] fs: nfsd: Fix buffer overflow in write_pool_threads(), arguing that a failed overflow check could let the formatter write past the end of the almost-page-sized buffer. After reviewing that, Lever concluded the real user-visible defect was truncation, not a write past the buffer, and posted this v1 as the corrective patch. In the related thread he wrote that he had "convinced himself that the actual problem is the truncation" and that "the buffer overflow cannot occur."

This thread itself did not pick up that debate. No Acked-by, Reviewed-by, or follow-up v2 appeared here before the week closed.

Classification and client impact

  • Type: bug fix (silent truncation of an admin-visible NFSD control reply), not a new feature and not a protocol change.
  • Subsystem: NFSD nfsctl (pool_threads), server-side only.
  • NFS client: none. Client mount, I/O, and recovery paths are untouched. The only user-facing effect is that operators (and any tooling that reads pool_threads) will get -ENAMETOOLONG instead of a plausible but wrong thread count when the formatted list no longer fits in SIMPLE_TRANSACTION_LIMIT.

Until reviewers comment, the open question is simply whether failing the read is the preferred policy versus enlarging or chunking the reply. Lever's rationale is that an incomplete number with no truncation marker is worse than an error, and that NFSD already uses -ENAMETOOLONG for the analogous case.
