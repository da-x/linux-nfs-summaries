AMD pushes back on NT copy-path performance claim

Summary

This remains a new-feature RFC for the memory-management demotion path — not an NFS protocol change and not a client bug fix. The only NFS client footprint is still the mechanical MIGRATE_ASYNC helper swap in fs/nfs/write.c from patch 2/3. This week adds a single reply, and it does not touch NFS.

Brief recap

Yiannis Nikolakopoulos (with Alirad Malek) posted RFC v2 of "Demote to lower tier using non-temporal stores." Reviewers immediately rejected the extra MIGRATE_ASYNC_NON_TEMPORAL_STORES mode in favor of migrate reason (for example MR_DEMOTION). Last week, Huan Nguyen then attacked the copy implementation itself: copy_mc_to_kernel_nt() claims both machine-check safety and non-temporal stores but delivers neither, memcpy_flushcache() lacks an sfence, and copy_mc_highpage() is the wrong primitive for page migration. He asked for a dedicated copy_mc_page_nt(). Huang, Ying separately suggested turning migrate_mode into flags. The authors have still not answered any of that.

This week: AMD disputes the "unoptimized" copy-path claim

Seventeen days after Nguyen's review, Shivank Garg (AMD) replies only to the performance half of that critique. He does not buy the idea that copy_mc_highpage() is a poor fit for migration copies:

"I don't think copy_mc_highpage() is unoptimized for page migration copies."

His argument is microarchitectural, not API-level. On ERMS systems, copy_mc_to_kernel() already uses copy_mc_enhanced_fast_string(), which is rep movsb. Ordinary copy_page() uses rep movsq on REP_GOOD systems. The fragile MCE path is, in his view, a special case:

"The copy_mc_fragile_enabled path looks like a special case and enable_copy_mc_fragile() is reachable either when mce=recovery or through one of 4 intel CPUs in x86/kernel/quirks.c"

He then reports numbers from an AMD EPYC 9655 (ZEN 5): folio_mc_copy() and folio_copy() showed similar performance. He points at his own April series (lore) and adds that the real leftover win is elsewhere:

"And there is actually scope of upto ~2X speedup for folio_copy/folio_mc_copy for large pages if we batch 4KiB copies."

That is a useful vendor data point against rewriting the migration copy around a dedicated 4 KiB copy_page()-style helper for speed. It is not a rebuttal of Nguyen's correctness complaints. Garg does not mention movnti, the missing sfence, MCE-safety of memcpy_flushcache(), or the proposed copy_mc_page_nt(). He also does not engage the still-open mode-versus-reason debate, Huang's migrate_flags idea, or the authors' unanswered v2 design questions.

No one else posted in-window. Nikolakopoulos and Malek remain silent.

NFS client angle

Nothing this week touches NFS client code, writeback behavior, or the protocol. The only client-relevant line is still the helper that treats both async modes as non-blocking in fs/nfs/write.c. Garg's copy-path performance note lives entirely in mm/x86; if v3 follows last week's "use reason" consensus or Huang's flags idea, that one-line NFS change is still the piece most likely to shrink or vanish.

Bottom line

The series is still an MM demotion feature RFC under review, not a bug-fix landing. This week's only comment is a partial, AMD-side pushback on Nguyen's claim that copy_mc_highpage() is unoptimized: on ZEN 5, folio_mc_copy() already matches folio_copy(), and Garg would rather batch 4 KiB copies for large folios than invent a new page-copy primitive for speed. The MCE-versus-NT correctness hole, the missing fence, the extra migrate mode, and the authors' reply are all still outstanding. Until a v3 appears, there is no NFS client development and no NFS bug fix in this thread.
