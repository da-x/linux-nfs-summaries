lockd client fixes for lockowner allocation failure

Summary

This week’s linux-nfs traffic closed out a client-side lockd (NLM) bug-fix series from Ran Hongyun, targeting two residual holes on the nlmclnt_find_lockowner() allocation-failure path in nlmclnt_proc(). The discussion is neither a new feature nor a protocol change: it is a correctness rewrite of the NLM client’s file-lock private-state setup, plus a related reference leak, both triggered when lockowner allocation fails.

Brief bridge from earlier this week

Two days earlier, Ran posted a one-line v1 that cleared fl->fl_ops after nlmclnt_locks_init_private() left it set with a NULL owner. Jeff Layton accepted the diagnosis but rejected the structure:

"The fix looks correct, but I don't like the way that the initialization and cleanup is spread across multiple functions. I think it would be better to just get rid of nlmclnt_locks_init_private() altogether and open code what it does in the single caller (nlmclnt_proc())."

He also flagged a second preexisting leak of the references taken by nlmclnt_alloc_call(), and asked Ran to spin a v2 that fixed both. That rewrite arrived on Wednesday as a two-patch series.

The v2 series: two bugs, one failure path

Ran’s cover letter framed both patches as sharing a single trigger: nlmclnt_find_lockowner() returning NULL from allocation failure inside nlmclnt_proc(). The series touches only fs/lockd/clntproc.c (19 lines changed) and is squarely NFS client lockd work.

Patch 1: NULL deref in nlmclnt_locks_release_private

Patch 1 restates the crash path that v1 already diagnosed. nlmclnt_locks_init_private() unconditionally installs fl->fl_ops even when the lockowner lookup fails. nlmclnt_proc() then notices the missing owner and returns -ENOMEM, but the VFS later tears the lock down through locks_release_private(). A non-NULL fl_ops is treated as a signal to call fl_release_private, which lands in nlmclnt_locks_release_private() and dereferences the NULL fl->fl_u.nfs_fl.owner.

Ran’s call-chain sketch is unchanged from v1:

"nlmclnt_locks_init_private() unconditionally sets fl->fl_ops even when nlmclnt_find_lockowner() returns NULL due to allocation failure. When locks_release_private() later sees a non-NULL fl_ops, it calls fl_release_private, which dereferences fl->fl_u.nfs_fl.owner."

What changed is the shape of the fix. Instead of clearing fl_ops after the fact, Ran inlined the helper into its only caller so that ops are installed only after a successful nlmclnt_find_lockowner():

"Fix it by inlining nlmclnt_locks_init_private() into its single caller nlmclnt_proc(), so that fl_ops is only set after nlmclnt_find_lockowner() succeeds"

That is exactly the structure Jeff asked for. The patch is tagged Fixes: bf8848918d75 ("lockd: handle lockowner allocation failure in nlmclnt_proc()") — the same residual hole as v1. The earlier commit already tried to handle lockowner allocation failure, but it only checked the owner pointer and returned -ENOMEM; it did not prevent the helper from installing ops first.

Patch 2: reference leak on the same error path

Patch 2 addresses the second bug Jeff called out. If nlmclnt_find_lockowner() fails, nlmclnt_release_call() is invoked before call->a_callback_data is assigned. The release helper therefore passes NULL into nlmclnt_ops->nlmclnt_release_call(), which skips cleanup, and the references taken by nlmclnt_alloc_call() leak.

The fix is a one-line reorder: assign a_callback_data before the lockowner check so the error path can actually free those references. Ran tagged it Fixes: b1ece737f44f ("lockd: Introduce nlmclnt_operations"), tying the leak to the introduction of the NLM client operations hook rather than to the later lockowner-failure handling. That is an important client-side distinction: the NULL deref is a leftover from bf8848918d75, while the leak is older and lives in the nlmclnt_operations callback plumbing.

Together the two patches make the -ENOMEM path in nlmclnt_proc() actually unwind: no NLM lock ops on a lock that never got an owner, and a proper drop of the nlm_rqst (and associated host/client state) that nlmclnt_alloc_call() already took.

Review: v2 accepted, with a process nit and a merge ping

Jeff Layton reviewed the series the same day. He first noted a process nit — the cover was not marked as a respin:

"nit: usually when you send a new version of a patchset you should declare it as "v2". So "PATCH v2 0/2", etc... Using the b4 command makes this easy to track."

On substance he was satisfied, and he also pointed at an earlier, less complete attempt at the same NULL deref from July:

"New version looks good. Note it looks like Shuangpeng Bai sent a less complete patch for this problem back in July that I just noticed. Your version seems more correct though."

That July patch (Shuangpeng Bai, 2026-07-17) cleared fl_ops before init and installed NLM ops only after a successful lockowner allocation, but it did not inline the helper and did not touch the nlmclnt_alloc_call() leak. Jeff’s comparison is the client-side takeaway: Ran’s v2 is the more complete unwind of the failure path. He added:

"Reviewed-by: Jeff Layton jlayton@kernel.org"

The next day Jeff followed up to route the patches, making the tree ownership explicit:

"To be clear, these are client-side patches. Anna/Trond, can you pick these up?"

That ping is the week’s practical conclusion. Lockd straddles client and server, and these changes live entirely in fs/lockd/clntproc.c on the NLM client path (nlmclnt_proc, nlmclnt_locks_init_private, nlmclnt_release_call). They belong in the NFS client tree, not nfsd.

Where the week left it

By Thursday the technical argument was settled:

  • The NULL dereference in nlmclnt_locks_release_private() is real; the preferred fix is to delete nlmclnt_locks_init_private() and install fl_ops only after a valid lockowner exists.
  • The same error path leaked nlmclnt_alloc_call() references because a_callback_data was assigned too late for nlmclnt_release_call() to run the nlmclnt_operations cleanup hook.
  • Jeff’s Reviewed-by is on the series, and he has asked Anna Schumaker / Trond Myklebust to take the patches into the NFS client tree.

No Acked-by from the client maintainers and no merge confirmation appeared in-thread before the window closed. The remaining action is pickup, not redesign. For NFS client development the lesson is local but sharp: lockowner allocation failure in nlmclnt_proc() was only half-handled by bf8848918d75, and the NLM client operations callback introduced by b1ece737f44f made the error path even more brittle by requiring a_callback_data to be valid before any early nlmclnt_release_call(). Ran’s inlined, reordered unwind is the intended close of both holes.
