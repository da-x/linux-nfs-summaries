NFS client: size LAYOUTGET buffers for wide flexfiles layouts

Summary

This week the NFS client thread on wide flexfiles LAYOUTGET replies moved from a six-patch Hammerspace series posted just before the window to a clean review from Jeff Layton.

The work is a client bug fix plus a follow-on feature, not a protocol change. Benjamin Coddington’s cover letter states the problem in blunt terms: the flexfiles layout driver “caps its LAYOUTGET reply buffer at a single page, which limits a striped layout segment to roughly 28 ff_data_server4 entries — far below the 4096-stripe decode limit the client otherwise advertises.” A server striping wider than that returns NFS4ERR_TOOSMALL, the client falls back to MDS I/O, “and pNFS never engages for those files.”

The standalone TOOSMALL fail-over bug

Patch 1 is tagged Fixes: / Cc: stable and is the only patch that is a pure correctness fix. RFC 8881 §18.43.3 says the MDS must return NFS4ERR_TOOSMALL when the layout for the requested range is larger than loga_maxcount. Today nfs4_stat_to_errno() maps that to -ETOOSMALL, nothing in the layoutget path recognizes it, and nfs_error_is_fatal() does not treat it as fatal. The result, Coddington wrote, is that pnfs_update_layout() “clears the layout fail bit and returns no segment”:

"The I/O falls back to the MDS, but because no fail bit was set, every subsequent pageio attempt sends another LAYOUTGET that is doomed to the same NFS4ERR_TOOSMALL. Files whose layouts do not fit the reply buffer never use pNFS and pay an extra round trip on every pageio."

The fix maps -ETOOSMALL to -EMSGSIZE in the layoutget exception handler and has pnfs_update_layout() treat it like NFS4ERR_LAYOUTUNAVAILABLE: mark the layout mode failed and stay on the MDS.

That is the patch Jeff Layton reviewed this week. His only objection was editorial, aimed at an LLM-assisted comment:

"nit: LLMs sure love to generate some overly-wordy comments. I think the last sentence here is not particularly helpful, and subject to bitrot as the code changes over time. I'd just drop it."

He did not challenge the error mapping or the fail-bit policy.

Growing the LAYOUTGET reply buffer

Patches 2–5 are the feature work that makes wide layouts actually fetchable.

  • Patch 2 stops advertising a fixed PNFS_LAYOUT_MAXSIZE (4096) in loga_maxcount regardless of the allocated reply buffer. Block and SCSI layouts already allocate a session-sized buffer but still tell the server “4KB or TOOSMALL,” so a large extent list can fail even when the client has room. loga_maxcount is now derived from the page array actually allocated.

  • Patch 3 retries LAYOUTGET once with the reply buffer raised to the session’s maximum response size — “the same bound GETDEVICEINFO already uses.” There is no size hint in the TOOSMALL error and the page array is freed when the RPC completes, so Coddington prefers a single jump to the ceiling over incremental growth. The common path is unchanged: the first LAYOUTGET still uses the driver’s default buffer; larger buffers are allocated only against servers that actually hand out wide layouts.

  • Patch 4 is a related client bug fix for non-conformant servers. decode_layoutget() already detects a layout body larger than the provided buffer (“server cheating in layoutget reply”) but maps it to -EINVAL, which pnfs_update_layout() treats as transient — the same doomed-retry loop as unhandled TOOSMALL. The patch returns -EMSGSIZE from that check so the oversized-reply path shares the retry-then-fail-over recovery.

  • Patch 5 remembers the escalated size on nfs_server and uses it as the floor for later LAYOUTGET reply buffers. That is also what lets the LAYOUTGET attached to OPEN succeed: “the lgopen path is best-effort with no retry of its own,” so without a learned size it would fail with TOOSMALL at every open against a wide-striping server. The field is a racy hint that only ever grows toward the session maximum; a stale-low read “merely costs one escalation round trip.”

Patch 6 then moves the decoded per-mirror stripe array to kvzalloc_objs(). Each stripe is roughly 300 bytes; a 2048-stripe mirror is a ~600KB contiguous allocation that can fail under fragmentation once the reply buffer is no longer page-capped. The vmalloc fallback is unavailable under memalloc_noio (swap over pNFS); that case “simply behaves as before.”

Coddington explicitly left two gaps for follow-up: the decoded per-stripe footprint (nfs4_ff_layout_ds_stripe embeds localio and layoutstats state most stripes never use), and the client still “decodes only the first logr_layout entry of a LAYOUTGET reply and silently discards the rest.” A related series on flexfiles device notifications and caching is independent and applies in either order. The series was wire-validated against reffs at stripe widths 2 and 64, covering both the conformant TOOSMALL path and the buffer-overrun path.

This week’s conclusion

About an hour after the comment nit, Layton reviewed the whole series:

"Aside from my minor comment nit, this looks good."

He added Reviewed-by: Jeff Layton <jlayton@kernel.org>. There was no other in-window traffic: no NAK, no request to split the stable fix from the buffer-growth work, and no push-back on treating both RFC-conformant TOOSMALL and “server cheating” overruns as -EMSGSIZE. The series is therefore sitting with a single, minor comment-wording request and a full review tag, awaiting a v2 comment trim or maintainer pickup.
