syzbot hung-task in write_versions: nfsd_mutex pile-up

Summary

This week’s traffic is a single, unreplied bug report: a syzbot hung-task splat tagged [nfs?] against the in-kernel NFS server control plane, not the NFS client. On 16 August, syzbot reported INFO: task hung in write_versions on upstream HEAD 3d6d817622b0 (Merge tag 'scsi-fixes'), with no reproducer and no human follow-up before week close.

This is not a protocol change and not an NFS client patch. The stack never leaves fs/nfsd/nfsctl.c. The [nfs?] tag is syzbot’s uncertain subsystem guess; the traces implicate NFSD’s global nfsd_mutex, the same choke point that has produced a string of sibling hung-task reports on write_ports, write_threads, netlink listeners, and nfsd_umount.

What hung

A syzkaller worker (syz.2.2321, PID 12662) sat in uninterruptible sleep (state:D) for more than 144 seconds while taking nfsd_mutex from the /proc/fs/nfsd/versions write path:

"INFO: task syz.2.2321:12662 blocked for more than 144 seconds."

The stack is:

__mutex_lock
  write_versions+0x95/0xe30 fs/nfsd/nfsctl.c:701
    nfsctl_transaction_write+0x10f/0x160 fs/nfsd/nfsctl.c:112
      vfs_write / ksys_write

write_versions() is the nfsd control-file handler that enables or disables NFS protocol versions (v2/v3/v4). Like every other nfsctl_transaction_write() path, it serializes on the global nfsd_mutex before touching per-netns service state. The hung worker already held sb_writers#27 from vfs_write() and a f_pos_lock, then blocked on that mutex.

syzbot is explicit about the missing reproducer:

"Unfortunately, I don't have any reproducer for this issue yet."

A later fix is asked to carry:

"Reported-by: syzbot+1c807916bc4bb0c1c340@syzkaller.appspotmail.com"

Dashboard: https://syzkaller.appspot.com/bug?extid=1c807916bc4bb0c1c340. Disk image, vmlinux, and bzImage are attached.

The lock dump: three-way contention, not a classic deadlock

The interesting part of the report is the lock inventory, not the hung stack itself. Three tasks of two syzkaller processes are piled up on the same nfsd_mutex:

  • Holder (same process, sibling thread): syz.2.2321/12657 holds nfsd_mutex in write_ports+0xb5/0xd10 fs/nfsd/nfsctl.c:860 — the /proc/fs/nfsd/portlist writer that adds or removes nfsd listeners. It also holds sb_writers#27 and a f_pos_lock.
  • Hung waiter: syz.2.2321/12662 is the reported task, waiting on the same mutex in write_versions.
  • Second waiter (different process): syz.3.2488/13375 holds generic-netlink cb_lock and is waiting on nfsd_mutex in nfsd_nl_unlock_filesystem_doit+0x2af/0x400 fs/nfsd/nfsctl.c:2345.

That is the classic nfsdctl pattern: every write through nfsctl_transaction_write() takes nfsd_mutex, so a slow or stuck write_ports (socket bind, listener start, rpcbind registration, or teardown) makes every other nfsd control write — versions, threads, exports — sit in D state until the hung-task watchdog fires. The netlink unlock_filesystem path joins the same queue, which is why a procfs versions write can stall a genetlink admin command and vice versa.

This is not a proven circular deadlock. Lockdep lists no AB-BA cycle; write_ports is simply still holding nfsd_mutex after 144 seconds. The kernel is tainted G L (SOFTLOCKUP). The NMI all-CPU backtraces that follow are unhelpful: khungtaskd dumping stacks, and swapper/0 sitting in pv_native_safe_halt. There is no smoking-gun stack of a CPU spinning inside nfsd, and the dump does not capture the holder’s wait chain — only that write_ports still owns the mutex.

Whether write_ports is itself blocked behind rpcbind, RTNL, or transport teardown while holding nfsd_mutex is not proven by this splat. That missing owner stack is the same gap Jeff Layton called out on the older nfsd_umount hang.

Continuity with earlier hung-task reports

This is not a new class of bug. It is the versions-file instance of a family of NFSD control-plane hangs that have been landing all summer:

  • On 1 August, syzbot filed [syzbot] [nfs?] INFO: task hung in write_ports against 7.2-rc5, with a C reproducer. That dump showed nfsd_mutex held by nfsd_shutdown_threads on the deactivate_super path while a crowd of writers waited in write_ports.
  • Thirty-four minutes later, [syzbot] [nfs?] INFO: task hung in write_threads showed the inverse: write_ports holding the mutex, write_threads waiting. No reproducer.
  • The same day as this write_versions report (16 August), syzbot posted a follow-up on the long-running nfsd_umount hang, now with a C reproducer; that dump again has write_ports waiters stacked behind nfsd_shutdown_threads.
  • Earlier in July, the netlink listener_set / cache_flush hang was diagnosed as synchronous rpcbind registration under nfsd_mutex: a down or unresponsive local rpcbind can stall each RPC ping for ~60 seconds, and listener_set can batch many sockets. Jeff Layton’s v2 hardening series (transport-name validation, 1024-entry cap, 1s local rpcbind timeout, non-fatal v2/v3 registration) is the in-flight mitigation; the durable fix — asynchronous rpcbind so it no longer runs under the mutex — remains later work.

This week’s write_versions splat fits the same picture: a procfs versions write blocked behind a concurrent write_ports that still holds nfsd_mutex, with a netlink unlock_filesystem waiter in the same queue. Nobody has #syz dup’d these reports together on-list.

NFS client angle

There is none in this thread. No client maintainer replied, and the stack never leaves fs/nfsd/nfsctl.c. Nothing touches fs/nfs/, xprtsock.c, or any NFS client I/O path.

The client-visible fallout is still real, even though the defect is server-side:

  • /proc/fs/nfsd/versions is how rpc.nfsd enables NFSv3/v4. A hung write_versions means the server cannot change the advertised protocol set; clients that need a version that is still disabled cannot mount.
  • The mutex owner is write_ports. If that path never finishes, listeners cannot be added or dropped, so clients cannot connect or reconnect while the control fs is wedged.
  • The waiters also pin sb_writers on the nfsd control superblock, so further writes (threads, exports, unlock_filesystem) serialize behind the same bottleneck.

For client developers, there is nothing to change in fs/nfs/ this week. The actionable work is on the nfsd side: nfsd_mutex remaining a global serialization point for unmount, listener configuration, version/thread writes, and genetlink admin commands.

Status

Open. One message, no maintainer comment, no #syz fix / #syz dup / #syz test. Until someone captures the write_ports holder’s wait chain — or lands the in-flight listener/rpcbind hardening so portlist updates cannot hold nfsd_mutex for a hung-task timeout — syzkaller will keep finding this as a hung task on whichever nfsctl file happens to be the waiter.

syzbot’s usual closing boilerplate still applies: reply with #syz fix: exact-commit-title if a fix lands, or #syz dup: if this is folded into the write_ports or nfsd_umount bugs.
