lockd v2: pin blocked grants and mark B_DEAD

Summary

Chuck Lever posted [PATCH v2] lockd: fix use-after-free in nlmsvc_retry_blocked, a second-round bug fix for a KASAN slab use-after-free on lockd’s blocked-grant retry path. It is not a protocol change and not a new feature. The patch is tagged Fixes: 0e4ac9d93515 (lockd: handle fl_grant callbacks) and touches fs/lockd/lockd.h and fs/lockd/svclock.c (+26/−6).

This week’s thread is a single posting: no Acked-by, Reviewed-by, or nack landed in-window. v2 is the current candidate; it supersedes the two-line v1 from 19 August after automated review showed that pinning the block was necessary but not sufficient.

How we got here (same week)

On 19 August Shuangpeng Bai reported a KASAN hit in nlm_async_call on current upstream (3aa1dcaa4f6f, 13 August) while unmounting nfsd with a lock still blocked. The same day Lever posted a two-line v1 that took a reference on the head of nlm_blocked before dropping nlm_blocked_lock. No human review arrived on v1. sashiko-bot then flagged a second teardown hole that the extra reference itself exposes; Lever’s v2, posted 20 August as a new thread, is the response.

"Add B_DEAD so a retry cannot requeue a retired block (sashiko-bot)."

The original UAF

Lever restates the lifetime hole that v1 already targeted:

"nlmsvc_retry_blocked() examines the block at the head of nlm_blocked under nlm_blocked_lock, then releases the lock before calling nlmsvc_grant_blocked() or retry_deferred_block(). The nlm_blocked list reference is all that keeps the block alive across that window."

nlmsvc_grant_blocked() does take a reference of its own, but too late:

"nlmsvc_grant_blocked() does take one of its own, but not until after the lock has been dropped."

Unmount of the nfsd filesystem while a lock request is still blocked reaches nlmsvc_traverse_blocks(), which drops that list reference and frees the block together with the nlm_rqst hanging off it. The lockd kthread then reads the freed request in nlm_async_call():

BUG: KASAN: slab-use-after-free in nlm_async_call+0xd6/0x230
Read of size 8 at addr ffff88811b04c808 by task lockd/8377
  nlm_async_call+0xd6/0x230
  nlmsvc_retry_blocked+0x61c/0x800
  lockd+0x144/0x1c0
Freed by task 8392:
  nlmsvc_release_block+0x231/0x290
  nlmsvc_traverse_blocks+0x139/0x1b0
  nlm_traverse_files+0x1aa/0xa00
  nlmsvc_free_host_resources+0x12/0x60
  nlm_shutdown_hosts_net+0x127/0x280
  lockd_down+0xd5/0x1c0

That is the classic lockd shutdown-vs-retry race: a blocked NLMv4 LOCK allocates an nlm_rqst (nlm_alloc_call ← nlmsvc_lock ← nlm4svc_do_lock), parks it on nlm_blocked, and later the lockd thread retries the GRANT. Concurrent nfsd unmount (nfsd_umount → lockd_down → nlm_shutdown_hosts_net) walks hosts and files and drops the same block.

The blamed commit, 0e4ac9d93515 (lockd: handle fl_grant callbacks), is the conversion that taught lockd to retry blocked grants via fl_grant. That is when nlmsvc_retry_blocked() started dropping nlm_blocked_lock and calling nlmsvc_grant_blocked() without pinning the block across the window.

v1’s repair is retained: take a reference before releasing nlm_blocked_lock, and drop it once the retry has run. Both the grant arm and the deferred-retry arm are covered, because retry_deferred_block() borrows its caller’s reference.

The second bug v1 exposed

Holding that extra reference is what sashiko-bot found, and it is the reason v2 exists. Lever:

"Holding that reference exposes a second problem. Both arms of the retry end in nlmsvc_insert_block(), which queues any block it finds unlisted, while nlmsvc_traverse_blocks() skips blocks that are already unlisted. A block unlinked during the window therefore returns to nlm_blocked after the teardown scan has passed it by."

The lifetime interaction is subtle:

  1. Teardown’s nlmsvc_traverse_blocks() unlinks a block (so it is no longer on nlm_blocked) and drops the list reference.
  2. The retry path still holds the v1 pin, so the block is not freed.
  3. Both retry arms finish in nlmsvc_insert_block(), which requeues any block it finds unlisted.
  4. The teardown scan has already walked past that block (it skips unlisted entries), so the resurrected block is never seen again.

The surviving block pins its file and its host. Consequences Lever names explicitly:

"The surviving block pins its file and its host, so the host is never reaped. lockd warns that it could not shut down the host module, and the host outlives the network namespace that host->net points at."

That is a second class of bug: not a KASAN UAF, but a lockd host leak across netns teardown. A host that outlives host->net is a use-after-free waiting to happen on the next NLM operation that looks at the namespace. v1 closed the slab UAF and opened this leak; it must not be merged as-is.

The v2 repair: B_DEAD

v2 keeps the get/put from v1 and adds a retirement flag.

"Mark a block with B_DEAD before unlinking it wherever it is retired for good, and have nlmsvc_insert_block_locked() ignore a block that carries the flag."

The distinction between “unlink for grant retry” and “unlink because this block is dead” is the interesting part of the design:

"nlmsvc_grant_blocked() unlinks and requeues as a normal part of a grant attempt, so it keeps calling nlmsvc_unlink_block() directly."

So:

  • Permanent retirement (teardown / nlmsvc_traverse_blocks and other “this block is gone for good” sites) sets B_DEAD before unlinking. A later nlmsvc_insert_block_locked() sees the flag and refuses to put the block back on nlm_blocked.
  • A live grant attempt still unlinks and requeues through nlmsvc_unlink_block() without B_DEAD, which is the historical grant-retry dance and must keep working.

Net effect: the retry path may still hold a reference across the unlocked window (no UAF in nlm_async_call), but it cannot resurrect a block that teardown has already retired (no host/file pin, no “could not shut down the host module,” no host->net outliving the namespace).

Why this matters for NFS clients

The code is server-side lockd (nlmsvc_* in fs/lockd/svclock.c), not the NFS client’s fs/nfs/ NLM caller. The user-visible effect is still on the client. NLM blocking locks (LOCK with block=true, BSD flock, POSIX F_SETLKW) wait on this retry loop for a GRANT callback. nlm_async_call is the async RPC helper both sides use.

If nfsd is unmounted — container stop, nfsd thread shutdown, network-namespace teardown — while a client still has a blocked lock:

  • Without the pin: lockd UAFs in nlm_async_call and can take the lockd kthread with it. Remaining NLM clients then lose GRANT callbacks and further blocking-lock service.
  • With only v1’s pin: the kthread survives, but a retired block can reappear on nlm_blocked, pin its host, and leave that host pointing at a destroyed netns. Subsequent client lock traffic against that host is then a second UAF.

The allocation side of Bai’s KASAN report is exactly a client-facing blocked lock: nlm_alloc_call ← nlmsvc_lock ← nlm4svc_do_lock ← nlmsvc_dispatch. A blocked NFSv3/NLM lock from a client is the object being freed (or resurrected) out from under the retry.

Status this week

  • Classification: lockd/NLM server memory-safety bug fix on the blocked-grant retry path, plus a follow-on host-lifetime fix. Regression from 0e4ac9d93515. Not a protocol change.
  • v2 claim: pin the head block across the unlocked retry, and mark permanently retired blocks B_DEAD so nlmsvc_insert_block_locked() cannot requeue them after nlmsvc_traverse_blocks() has skipped them.
  • Disposition: posted 20 August, no human review in-window. v1 is superseded; do not queue the two-line patch. v2 is the patch to review.
  • Open question: reviewers still need to confirm every permanent-unlink site now sets B_DEAD before dropping the list reference, and that grant-retry’s unlink-and-requeue path remains B_DEAD-free.
