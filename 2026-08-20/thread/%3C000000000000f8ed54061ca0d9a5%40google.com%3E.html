syzbot finds a reproducer for hung nfsd_umount

Summary

This week’s only traffic on the long-running hung-task report is a syzbot follow-up: the bot now has a C reproducer for INFO: task hung in nfsd_umount, still reproducing on current upstream. The issue is an NFSD (server) bug, not an NFS client problem — a mutex stall around nfsd_umount / nfsd_mutex that can freeze nfsd control-plane writes and concurrent unmounts.

This week: a reproducer, same hang, slightly different lock picture

On 16 August 2026, syzbot reported that it had finally produced a syz and C reproducer against upstream 3eb40771c00a (Merge tag 'soc-fixes-7.2-3'). The bot asked maintainers to tag any fix with:

"Reported-by: syzbot+b568ba42c85a332a88ee@syzkaller.appspotmail.com"

and offered the usual #syz test: workflow. Nobody from linux-nfs replied in-window.

The new traces still show tasks blocked more than 143 seconds in D state. One syz-executor thread is stuck in nfsd_umount → nfsd_shutdown_threads waiting on nfsd_mutex:

nfsd_shutdown_threads+0x5b/0xf0 fs/nfsd/nfssvc.c:576
nfsd_umount+0x3b/0x60 fs/nfsd/nfsctl.c:1365
deactivate_locked_super+...
cleanup_mnt+...

Three sibling executor threads are stuck on the same mutex from the nfsctl write path:

write_ports+0xa5/0xcc0 fs/nfsd/nfsctl.c:860
nfsctl_transaction_write+0x106/0x1a0 fs/nfsd/nfsctl.c:112

The lock dump makes the contention explicit. Two unmounts hold distinct s_umount locks and then take nfsd_mutex in nfsd_shutdown_threads; three write_ports callers hold sb_writers and then wait on that same global nfsd_mutex. In other words, a slow (or stuck) nfsd thread-shutdown serializes every concurrent port-file write and every other nfsd superblock teardown.

That is a sharper picture than the 2024 original. The first report had nfsd_nl_listener_set_doit as the other nfsd_mutex holder; this week’s reproducer instead hammers the classic /proc/fs/nfsd/portlist (write_ports) path against concurrent nfsd_umount. The NMI all-CPU backtrace that Neil Brown asked for in 2024 did fire, but the sibling CPU was in a batman-adv multicast workqueue (batadv_mcast_mla_update), not in nfsd — so the dump still does not show why the mutex owner is sitting in nfsd_shutdown_threads.

No patch, no #syz fix:, and no human analysis landed this week. The bug remains open, now with a downloadable C reproducer, disk image, and vmlinux.

Brief bridge from 2024

syzbot first filed the hang on 7 July 2024 against 6.10-rc6, without a reproducer. The stuck stack was already nfsd_umount → nfsd_shutdown_threads taking nfsd_mutex, with a second task holding that mutex in nfsd_nl_listener_set_doit.

Jeff Layton immediately flagged the missing stack on the mutex owner:

"Above there are two tasks that are holding/blocked on the nfsd_mutex. The first is the stuck thread. The second is a task that took it in nfsd_nl_listener_set_doit. I don't see a way to exit that function without releasing that mutex, so it seems likely that thread is stuck too for some reason. Unfortunately, we don't have a stack trace from that task, so I can't tell what it's doing."

Neil Brown argued the owner was not blocked on another lock (or lockdep would have listed it) and guessed a sleep/spin inside transport teardown:

"I wonder if it could be looping in svc_xprt_destroy_all(), and sitting in the msleep() when the hang is detected so there are no locks to report."

He asked for /proc/sys/kernel/hung_task_all_cpu_backtrace. Harald Dunkel enabled that sysctl on a production NFS server and reported a possibly related hang of nfsd inside a legacy-cgroup container that also surfaced as an OOM on login. A later MIME follow-up from Harald did not add a usable backtrace to the list.

Status

This is a bug, not a feature or protocol change: a hung-task / possible deadlock in NFSD’s global nfsd_mutex during nfsd_umount, now shown to interact with write_ports as well as netlink listener setup. Two years on, the hang still reproduces on upstream, but maintainers finally have a C reproducer. Until someone posts a patch (or a #syz test: experiment) against nfsd_shutdown_threads / svc_xprt_destroy_all, the report stays open.

NFS client code is not implicated here; the stacks and locks are entirely on the server (fs/nfsd/nfssvc.c, fs/nfsd/nfsctl.c).
