NFSD v5 CB_RECALL_ANY series tightens keep-count accounting

Summary

Chuck Lever posted v5 of "NFSD: CB_RECALL_ANY fixes and a meaningful keep count" on 18 August. The eight-patch series is a bug-fix plus protocol-usage correction, not a protocol change and not a new feature. Two Fixes: tags still point at 44df6f439a17 ("NFSD: add delegation reaper to react to low memory condition"). There were no replies in this thread during the week: v5 is a respin of the already-reviewed v3/v4 work, with three shrinker-accounting tweaks so the keep count is computed only over clients the sweep can actually reach.

The client-development stakes are unchanged from earlier rounds. Linux-on-Linux testing has been hiding a server bug because the Linux NFS client ignores craa_objects_to_keep. Non-Linux clients that honor a zero keep count dump their delegation working set on the first hint of server memory pressure. v5 still does not change Linux client behavior; it stops NFSD from advertising a keep count of zero, and it stops sending CB_RECALL_ANY to NFSv4.0 clients whose callback channel cannot survive that operation.

Brief bridge from earlier this week

v3 (13 August) grew the original four-patch series into eight after Lever split the state shrinker so a keep count can be apportioned. Jeff Layton signed off on patches 5–8. v4 (15 August) added a divide-by-zero guard when max_delegations is zero, collected those Reviewed-by tags, and drew a 5.10 backport request from Cedric Blancher. Lever declined: the series applies with reasonable effort only as far as v6.18, and he called clients that return every delegation on a zero keep count defective rather than conforming. v5, posted two days later, is the accounting follow-up to that v4 posting.

Why a zero keep count is a client-visible bug

The cover letter restates the problem RFC 8881 §20.6.3 leaves open, and that NFSD has been filling with the worst possible value:

"NFSD currently sends every CB_RECALL_ANY with craa_objects_to_keep set to zero, as RFC 8881 Section 20.6.3 does not mandate any particular way for a client to choose which delegations to return, if any."

Zero is not a no-op. The field is the number of recallable objects the client may retain, so a keep count of zero is a request to return every delegation, including ones backing files that are still open. NFSD only intended the callback as a hint to return unused delegations. Linux has been masking the over-ask:

"To date, only the Linux NFS client has been deeply tested against it. That implementation ignores the craa_objects_to_keep value and returns only one unused delegation of the named types. Therefore the fixed zero craa_objects_to_keep value never produced visible misbehavior during our testing."

The audience for the keep-count change is everyone else:

"a zero value can result in non-Linux clients giving back more delegations than is necessary to relieve temporary memory pressure on the server, which needlessly punctures the clients' delegation working set."

The series therefore changes NFSD so each CB_RECALL_ANY asks a client to give up a sensible number of delegations instead of all of them at once. The shrinker split exists so that number can be a real fraction of each client's holdings rather than a constant.

Client-visible bug fixes (patches 1–4)

Patch 1 is the Linux-client-visible bug fix. deleg_reaper() currently sends CB_RECALL_ANY to every ACTIVE client holding delegations, including NFSv4.0 clients. That operation is NFSv4.1-only. A v4.0 callback service accepts only CB_GETATTR and CB_RECALL, so it replies OP_ILLEGAL. The decoder maps the unexpected opnum to -EIO, nfsd4_cb_done() marks the callback channel down, and nothing brings it back: nfsd4_run_cb_work() only sets NFSD4_CB_UP for a minor version above zero, and the only nfsd4_probe_callback() a v4.0 client reaches is nfsd4_setclientid_confirm(). One visit from the reaper therefore leaves RENEW returning NFS4ERR_CB_PATH_DOWN for as long as the client holds delegations, and nfsd4_cb_channel_good() refuses to grant any more. Skip clients at minor version zero.

Patch 2 adds cl_deleg_count on struct nfs4_client, maintained under nn->deleg_lock at the two sites that mutate cl_delegations. The reaper walks nn->client_lru under nn->client_lock and cannot take nn->deleg_lock to count the list; an O(n) walk per client is also the wrong cost model on a pass that already visits every client. Readers that hold only client_lock must treat the counter as a data_race() and may not depend on it for correctness. No functional change on its own, but it is the input to the keep count.

Patch 3 adds RCA4_TYPE_MASK_DIR_DLG to craa_type_mask. RFC 8881 §20.6.3 distinguishes servers that share one pool among all recallable-object classes from those that keep per-class pools; NFSD is the former. Directory delegations already go through __alloc_init_deleg(), count against max_delegations, and are reclaimed by the shrinker, but the type mask never named them. Clients that implement directory delegations would otherwise skip them when choosing what to return.

Patch 4 is the keep-count change itself, also tagged against 44df6f439a17. Instead of zero, deleg_reaper() derives craa_objects_to_keep from cl_deleg_count so each callback asks the client to give up one delegation. Both the shrinker and the laundromat re-arm while the condition lasts, so a client with more to spare is asked again on the next pass. Lever is explicit that this is a no-op for Linux:

"The Linux client ignores craa_objects_to_keep and returns unused delegations selected from the type mask alone, so the count changes nothing for it."

The audience is every other NFSv4.1 client that actually reads the field. Combined with patch 8, later sweeps no longer ask every eligible client for a single delegation "whether or not anything needs the memory"; the keep count becomes a share of the reclaim request.

Shrinker accounting so the keep count is not a lie (patches 5–8)

Patch 5 counts delegations per network namespace. The state shrinker is allocated per netns, but nfsd4_state_shrinker_count() was reporting host-wide num_delegations, so reclaim saw the population multiplied by the number of namespaces and a namespace holding nothing still queued its reaper. num_delegations remains the host-wide admission/ceiling check against max_delegations, which is sized from host memory.

Patch 6 splits nfsd_client_shrinker into two. Courtesy-client reclaim is synchronous and deadlock-free; the shrinker can report a precise count of objects released. Delegation reclaim only sends CB_RECALL_ANY — clients are not obligated to return anything — so the callback cannot report progress:

"Shrinking that population requires sending a CB_RECALL_ANY; clients are not obligated to return any delegation. The shrinker callback is structurally unable to report progress."

Worse, the combined shrinker fell back to delegation reaping only when no courtesy clients remained, so a single courtesy client kept a namespace's delegations out of the count. Each population now has its own namespace-specific shrinker.

Patch 7 records scan requests instead of discarding them with SHRINK_STOP. That size is "the only real measure NFSD gets of reclaim pressure." Courtesy scans accumulate in nfsd_shrink_backlog and are subtracted from the count until courtesy_client_reaper() runs. Delegations use a time bound: they are reported only once NFSD_RECALL_ANY_COOLDOWN_SECS have passed since the last sweep, matching deleg_reaper()'s skip of any client recalled inside that window. deleg_reaper() only sends CB_RECALL_ANY and does not track how many delegations the targeted client actually returned, so a time bound is the only honest progress signal.

Patch 8 is the client-facing payoff of that accounting. deleg_reaper() had been asking every eligible client for one delegation whenever it ran:

"A delegation returned before it is needed costs the client an OPEN when it next touches the file."

The scan callback now records nr_to_scan in nfsd_deleg_backlog and scales that total by each client's share of the delegations this sweep can reach. Handing the total to every client would ask for it once per client. The count callback reports what is left after outstanding requests, so concurrent reclaimers do not each ask for the same delegations. cl_ra_time keeps the next sweep from returning to the clients this one reached. Nothing is recalled until a scan arrives, except nfs4_laundromat(), which has no scan request and instead computes what must go for num_delegations to fall below max_delegations, then passes only this namespace's share.

What actually changed in v5

The v5 changelog is three accounting fixes on top of v4, all aimed at not over-asking clients the sweep cannot currently recall from:

"Exclude clients the sweep skips from the apportionment's divisor."

"Skip clients whose CB_RECALL_ANY callback is still running."

"Discount the delegation shrinker's count by its pending requests."

The first two land in patch 8's apportionment: a client that is on cooldown, whose callback is still in flight, or that the sweep otherwise skips must not inflate the divisor, or every remaining client is asked for too little while the skipped clients are asked for nothing. Skipping an in-flight CB_RECALL_ANY also avoids stacking a second recall on a client that has not yet answered the first. The third is the matching count-side discount: pending requests are subtracted from what the delegation shrinker reports, so reclaim does not re-issue work that is already queued.

Jeff Layton's Reviewed-by remains on all eight patches, collected from the v3 posting of 5–8 and earlier rounds of 1–4. No new review comments landed on v5 this week.

Classification, client takeaway, and status

This is a bug-fix series with a protocol-usage correction. It does not change the NFSv4.1 protocol. Two Fixes: tags address the original delegation reaper: sending CB_RECALL_ANY to NFSv4.0 clients (callback channel permanently down, no further delegations) and advertising a keep count of zero (non-Linux clients over-returning). The rest is supporting machinery so the keep count can be a real fraction of each client's holdings under memory pressure.

For NFS client development the picture is:

  • The Linux client continues to ignore craa_objects_to_keep and return a single unused delegation of the named types, so patches 4 and 8 are a no-op for it.
  • The NFSv4.0 skip in patch 1 is the Linux-client-visible server bug fix: a v4.0 client will no longer have its callback channel permanently marked down by the reaper.
  • Clients that implement directory delegations now see RCA4_TYPE_MASK_DIR_DLG in the type mask and can consider those objects when choosing what to return.
  • Non-Linux clients that treat a zero keep count as "return everything" will now see a proportional request instead. Lever's v4 reading still stands: such clients are defective, not conforming; the server is stopping the provocation rather than papering over that behavior on older stables.

v5 is posted, fully tagged from prior rounds, and awaiting merge. No further discussion landed in this thread before the week closed.
