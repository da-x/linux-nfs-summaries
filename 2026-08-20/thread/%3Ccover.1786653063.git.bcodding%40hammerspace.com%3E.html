Flexfiles device notifications: v1 paused for sashiko issues

Summary

This week’s only traffic on Benjamin Coddington’s 21-patch NFS client series is a pause, not a review. The v1 cover letter landed on 13 August, just outside the window; on 14 August Coddington told reviewers to hold off:

"Note to reviewers - this one had numerous problems identified by sashiko: https://sashiko.dev/#/patchset/cover.1786653063.git.bcodding%40hammerspace.com

I'm working on a v2.."

No human review comments arrived this week. The series remains a client-side mix of stable-bound striped-layout bug fixes, RFC 8881 CB_NOTIFY_DEVICEID implementation, and cache scaling for wide flexfiles mounts. A related LAYOUTGET-buffer series is independent and not part of this thread.

Why the client needs this

Coddington’s cover letter frames the problem as a wide-stripe flexfiles mount that “puts hundreds to ~1000 distinct deviceIDs in play for a single mount.” The client’s CB_NOTIFY_DEVICEID path does not actually refresh mappings under live layouts, deviceID-deletion race recovery from RFC 8881 is missing, and the device caches were sized for far fewer servers. He tested the series end-to-end against reffs (a notification-capable reference server) at 256 and 1000 devices, including KASAN and lockdep under concurrent notification storms.

Stable-bound striped-layout bugs (patches 1–4)

The first four patches are standalone client bug fixes, all Cc: stable.

Patch 1 repairs the CB_NOTIFY_DEVICEID XDR decoder. decode_devicenotify_args() gated consumption of the trailing ndc_immediate boolean on cbd_layout_type instead of cbd_notify_type. Layout type is never equal to NOTIFY_DEVICEID4_CHANGE (2), so the flag was “silently lost for a single CHANGE, and a multi-item cnda_changes<> array misaligned after the first item and failed with NFS4ERR_INVAL/BADXDR.”

Patch 2 widens flexfiles read data-server selection from u32 to u64. Truncating the file offset before nfs4_ff_layout_calc_dss_id() meant striped reads at offsets ≥ 4 GiB probed availability and sized coalescing against the wrong stripe’s DS. Coddington notes the actual read recomputes dss_id from the full offset, “so data is not corrupted”; the write path already used the full offset.

Patches 3 and 4 fix page coalescing that could straddle a stripe boundary and send bytes to the wrong data server. Flexfiles has no pattern_offset and partitions on absolute file offset (RFC 8435 §6), but ff_layout_pg_test() inherited files-layout segment-relative bounds. The files layout itself had the complementary bug: coalescing used pls_range.offset while DS selection used pattern_offset. Aligned / whole-file layouts are unchanged.

Making CHANGE work under live layouts (patches 5–13)

This is the core client feature work. RFC 8881 §12.2.10 lets a server re-point a deviceID without recalling layouts, but today the client only unhashes the cached device. References pinned inside layout segments keep sending I/O to the old mapping until the layouts are freed.

The flexfiles driver is first given its own device-node references: across DS setup, carried on each in-flight I/O as ds_dev on nfs_pgio_header / nfs_commit_data, and held through layoutstats encoding so a later CHANGE cannot UAF the XDR path. Patch 8 then marks the pinned mirror_ds pointer __rcu, with try-ref / cmpxchg install patterned after get_huge_zero_folio().

A new reresolve_deviceid layout-driver hook walks live layouts under i_lock and must not drop device-node references itself, because the final put can sleep. Flexfiles implements in-place re-resolve by exchanging the matching stripe’s pinned node for NULL; in-flight I/O finishes on the old node, and the next I/O re-resolves via GETDEVICEINFO. CHANGE is then dispatched to that walker instead of being treated identically to DELETE.

Patch 12 honors ndc_immediate: the old node is marked unavailable so paths still holding a reference stop selecting it, except when the walk races a freshly installed mapping (distinguished by hashed-ness). Without the flag, pending I/O drains on the old mapping. Patch 13 adds a change epoch so a GETDEVICEINFO reply that raced a CHANGE is discarded rather than re-caching the pre-change mapping (RFC 8881 §18.40.4).

DELETE race recovery (patches 14–17)

RFC 8881 §18.40.4 requires the client to handle a DELETE for a deviceID that live layouts still reference — something “a conformant server never sends.” The series adds a layout_references_deviceid hook and walkers, then a state-manager step (NFS4CLNT_DEVICEID_DELETE) because the callback thread cannot issue fore-channel RPCs. Suspects are TEST_STATEID’d; revoked layouts are recovered with FREE_STATEID. If a referring layout is still valid, the delete is confirmed with a raw GETDEVICEINFO (the usual helper swallows RPC status and cannot distinguish NFS4ERR_NOENT). Device gone plus a still-valid layout means a faulty server and lease recovery; an erroneous DELETE leaves the cache and layout intact. A DELETE with no live references keeps today’s cheap unhash path.

Scaling the device caches (patches 18–21)

The global deviceid hash grows from 32 to 256 buckets (load factor ~4 at 1000 devices). The per-net data-server cache moves from a single list to hash buckets, then is keyed by address set. That also fixes a latent aliasing bug: the old comparator matched on subset rather than equality and “merged two data servers whenever one’s address set contained the other’s.”

Finally, flexfiles gains a dataserver_nconnect module parameter. DS clients otherwise inherit MDS nconnect; at ~1000 DSes and nconnect=16 that is “~16k sockets and their slot tables for little gain on a workload striping across the DSes anyway.” Default 0 preserves inherit-from-MDS behavior.

Status this week

v1 is not under active review. Coddington has already flagged automated sashiko findings and is preparing v2; a later v2 cover ([PATCH v2 00/23]) exists as a separate thread and is out of this week’s scope. Until that lands, the client still does not implement live-layout CHANGE, still has the four stable-bound striped-layout bugs, and still cannot scale device caches to a thousand-DS flexfiles mount.
