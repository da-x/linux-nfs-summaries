NFSD recall-any trace format eval maps land with dual reviews

Chuck Lever posted a one-file tracing bug fix this week so that trace-cmd and perf can actually decode the type mask on NFSD's nfsd_cb_recall_any event. Christoph Hellwig and Jeff Layton both reviewed it the next day. The patch is not a protocol change and not a new feature: it repairs observability of an existing CB_RECALL_ANY tracepoint, which matters for anyone watching how the server asks clients to return delegations.

The bug: enumerator names left in the format file

The nfsd_cb_recall_any event uses show_rca_mask() to pretty-print the bmval0 field as named bits (RDATA_DLG and friends). Those names come from RCA4_TYPE_MASK_* enum constants. Lever's commit message explains why that never made it into a usable format string:

"RCA4_TYPE_MASK_* are enum constants, so the preprocessor cannot fold them into the print format that show_rca_mask() builds for the nfsd_cb_recall_any event. Nothing declares an eval map for them either, so trace_event_eval_update() has no substitution to apply at module load, and the event's format file ships the enumerator names verbatim. trace-cmd and perf cannot decode the bmval0 field."

In other words, the kernel's tracing machinery never got a numeric mapping for those bits. Userspace tools that parse /sys/kernel/tracing/events/.../format (or the equivalent from a recorded session) therefore saw the C enumerator identifiers instead of integer shift counts, and could not decode which recallable-object types the server had asked the client to give back.

The fix is ten lines in fs/nfsd/trace.h: declare TRACE eval maps for the nine mask bits show_rca_mask() already decodes. After that, the event format carries the shift counts as integers, matching the shape SUNRPC already emits from its BIT() flag decoders. Lever tags it Fixes: 638593be55c0 ("NFSD: add CB_RECALL_ANY tracepoints").

Why it matters for NFS client work

This is an NFSD-side change, but the field it repairs is exactly the mask a client sees on CB_RECALL_ANY. That callback is the server's way of asking a client to return some recallable state (delegations, layouts, and related objects) under memory pressure. Linux NFS client developers and operators using perf or trace-cmd against a live NFSD could not decode bmval0, so they could not tell from traces which object types the server had named.

That gap is more than cosmetic this week. Lever's parallel CB_RECALL_ANY keep-count series is still landing: it stops NFSD from sending the operation to NFSv4.0 clients (which permanently takes the callback channel down) and stops advertising craa_objects_to_keep == 0 (which non-Linux clients treat as "return everything"). The Linux NFS client has historically ignored the keep-count and returned only one unused delegation of the named types, which is why Linux-on-Linux testing never exposed the zero-keep-count bug. Being able to decode the type mask in traces is the other half of watching that path: without it, a client-side investigation of "which types did the server actually recall?" stops at an undecodable bitmap.

Reviews, no debate

Christoph Hellwig replied the next morning with a one-line ack:

"Looks good:"

and a Reviewed-by: Christoph Hellwig <hch@lst.de>.

Jeff Layton followed a few hours later with Reviewed-by: Jeff Layton <jlayton@kernel.org> after quoting the patch, including the show_rca_mask() table that maps BIT(RCA4_TYPE_MASK_RDATA_DLG) to "RDATA_DLG". There was no technical pushback, no request for a v2, and no discussion of stable backporting on this thread.

Conclusion

This is a bug fix for NFSD tracing, not a protocol change. The original CB_RECALL_ANY tracepoints shipped enumerator names that userspace cannot resolve; declaring the nine eval maps makes bmval0 decode the same way SUNRPC flag bits already do. With Hellwig and Layton's reviews in hand, the patch is ready to merge. For NFS client developers, the practical outcome is that traces of nfsd_cb_recall_any will finally name the object types the server asked the client to return — the missing decoder for a callback the keep-count series is simultaneously making less hazardous.
