statd SM_MON leak committed to nfs-utils

Summary

This week closed a small bug-fix thread for userspace rpc.statd, not a protocol change and not a kernel NFS client patch. After sitting unreviewed since late July, xuchenchen’s two-line leak fix in utils/statd/monitor.c was taken by nfs-utils maintainer Steve Dickson on 15 August.

Dickson’s reply is the entire in-window discussion. Quoting the original patch, he recorded the merge with a one-line verdict:

"Committed... (tag: nfs-utils-2-9-3-rc1)"

There was no further technical debate, no Acked-by from other reviewers, and no request for a valgrind or kmemleak trace. The conclusion of the thread is therefore a straight merge into the nfs-utils 2.9.3-rc1 tag.

Prior week, briefly

On 28 July, xuchenchen of KylinSoft posted “[PATCH] statd: fix memory leak in sm_mon_1_svc() when existing host re-monitors.” The SM_MON RPC handler that lockd/statd uses to register hosts for NSM notifications reuses an existing notify_list entry when an already-monitored host comes back with a different priv cookie. On that reuse path the newly allocated DNS name was written over clnt->dns_name without freeing the previous pointer.

The original commit message stated the failure mode plainly:

"When an already-monitored host sends a new SM_MON request with a different priv cookie, the code sets existing=1 and reuses the existing notify_list entry. However, clnt->dns_name is overwritten with the newly allocated dnsname without freeing the old value, causing a memory leak."

And because rpc.statd is a long-lived helper under NFS lock recovery:

"Since statd is a long-running daemon, repeated SM_MON requests with changing cookies will accumulate leaked strings."

The proposed fix was the obvious local change: free the old dns_name before overwriting it (+2 lines in utils/statd/monitor.c). No NSM wire behavior changed; the existing notify-list node is still reused.

Why this matters for NFS clients

Even though the code lives in nfs-utils rather than the kernel client, Linux NFS clients depend on lockd + statd to monitor the server (and vice versa) so NLM locks can be reclaimed after a reboot. A client that remounts, restarts lockd, or re-registers with a new cookie will keep pumping SM_MON at an already-tracked peer. Each of those re-monitors dropped another hostname string on the floor in a daemon that typically runs for the life of the host.

Status this week

The leak is fixed in nfs-utils 2.9.3-rc1. Operators waiting on a packaged nfs-utils refresh can treat the SM_MON re-monitor leak as closed; there is nothing left open on the list for this thread.
