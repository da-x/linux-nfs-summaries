NFSv4 client: 4-line u32 wrap check for two xdr_inline_decode() sites

Summary

NFSv4 client: a 4-line size check against 32-bit wrap in two pNFS decoders

Overview

This week’s linux-nfs traffic includes a standalone NFS client bug-fix from Griffin Kroah-Hartman: a four-line addition to fs/nfs/nfs4xdr.c that inserts a size check before two xdr_inline_decode() calls whose length argument is a server-supplied count multiplied by four. There were no replies in the week ending 2026-08-20. The patch has not been acked, nacked, or revised, and it carries neither a Fixes: tag nor a Cc: stable@vger.kernel.org trailer.

This is not a new feature and not a wire-protocol change. It is a client-side robustness fix against 32-bit integer wrap in the NFSv4 pNFS XDR decoder, aimed at the same two functions that have already been the subject of two earlier hardening campaigns on this list.

The patch (August 19)

Kroah-Hartman’s submission is deliberately small — fs/nfs/nfs4xdr.c | 4 ++++ — and names both sites in one change:

"Add a size check before xdr_inline_decode() is called in decode_pnfs_layout_types() and decode_getdeviceinfo() where the length parameter is multiplied by 4."

The stated goal is to keep the scaled length from wrapping a 32-bit variable before it is handed to the XDR helper:

"This check ensures that the parameter passed will not overwrap when using 32 bit variables, avoiding incorrect size input to xdr_inline_decode()."

The sign-off block credits an AI assistant (Assisted-by: gkh_clanker_t1000) and is signed Griffin Kroah-Hartman <griffin@kroah.com>. The ingest dropped the unified diff, so the exact predicate is not in the archived body; from the commit message the intent is a pre-multiply overflow guard at both call sites, not a rewrite of the subsequent decode loops.

That shape matters. A four-line “don’t wrap the * 4” check is the most minimal of the three independent proposals now sitting on linux-nfs for this class of bug. It does not:

  • clamp the count against NFS_MAX_LAYOUT_TYPES (or the GETDEVICEINFO notification-bitmap word limit) before the reservation;
  • switch the bulk xdr_inline_decode(count * 4) into a word-at-a-time walk;
  • call the existing xdr_stream_decode_uint32_array() helper.

Those omissions are the whole story of this thread’s significance for NFS client development.

Why the two sites wrap

Both functions follow the same pattern: read a server-controlled u32 count, multiply it by four in 32-bit arithmetic, and pass the product to a single xdr_inline_decode(). For any count ≥ 0x40000000 the multiply wraps to a small value, so the XDR bounds check only covers a few bytes while the following loop walks the original (huge) count from the resulting pointer.

  • decode_pnfs_layout_types() is on the ordinary FSINFO path (nfs4_xdr_dec_fsinfo() → decode_fsinfo() → decode_pnfs_layout_types()), so a hostile NFSv4.1+ server can hit it at mount or statfs time via a crafted FATTR4_FS_LAYOUT_TYPES attribute.
  • decode_getdeviceinfo() is on the pNFS layout-discovery path (nfs4_xdr_dec_getdeviceinfo() → decode_getdeviceinfo()). A huge notification-bitmap word count in a GETDEVICEINFO reply drives the same wrap, then a loop that can walk up to nearly a gigabyte of words past the receive buffer.

The XDR receive buffer is assembled from pages, not slab objects, so KASAN typically does not instrument the over-read. Depending on what follows in memory, the client either consumes garbage layout-type / notification bits or faults on unmapped pages. That is a decoder-robustness hole against a malicious or compromised pNFS server (or a MITM on an unprotected mount), not a protocol defect.

Same-week siblings: Alibaba already proposed a stronger shape

Two days earlier, on 2026-08-18, Alibaba’s Chuyf26 posted two independent patches against the exact same functions, still unreplied as of this week’s close:

  • [PATCH] NFSv4: fix out-of-bounds read when decoding many pNFS layout types — cap nlayouttypes first, then decode each layout-type word individually so every xdr_inline_decode() is independently bounds-checked.
  • [PATCH] NFSv4.1: fix out-of-bounds read decoding GETDEVICEINFO notification bitmap — stop the 4 * len bulk reservation entirely and walk the notification bitmap one word at a time.

Those submissions diagnose the same wrap, but they treat the bulk xdr_inline_decode(count * 4) itself as the bug, not merely the overflow of the multiply. Kroah-Hartman’s four-liner, posted the next day, does not reference either Alibaba patch and does not adopt their word-at-a-time strategy. Until a maintainer comments, linux-nfs now has three overlapping, unreviewed proposals for the same two call sites in a 48-hour window, with no discussion tying them together.

Bridge from June: Trond already rejected a hand-rolled guard

This is not a newly discovered hole. In June 2026 Michael Bommarito posted a KASAN-reproduced, Cc: stable campaign against the same XDR-wrap class:

  • 2026-06-14: bound the GETDEVICEINFO notification-bitmap length before scaling (series).
  • 2026-06-22: companion bound on decode_pnfs_layout_types() (patch).

On the layout-types patch, Linux NFS client maintainer Trond Myklebust replied within about ninety minutes:

"This is just open coding xdr_stream_decode_uint32_array(), and doing so incorrectly."

Bommarito’s June analysis also flagged a subtlety that a bare pre-multiply size check does not obviously cover. The existing NFS_MAX_LAYOUT cap is applied after the reservation, so it cannot save a short xdr_inline_decode(). And array_size() is not a safe substitute, because xdr_inline_decode() runs its nbytes argument through XDR_QUADLEN (((l) + 3) >> 2), which wraps SIZE_MAX to a zero-word reservation instead of failing. A four-line “don’t let count * 4 wrap a u32” guard addresses the multiply, but it does not automatically address the XDR_QUADLEN rounding edge, the post-reservation cap, or Myklebust’s instruction to use the helper.

Kroah-Hartman’s patch does not mention that review, does not call xdr_stream_decode_uint32_array(), and does not explain why a hand-rolled size check is now the right shape. Given Myklebust’s June one-liner, the likely maintainer response — if and when it arrives — is to point all three current proposals at the existing uint32-array helper rather than to pick a favourite hand-rolled bound.

Significance for NFS client development

  • The hole is still open. Three independent authors (Bommarito in June, Chuyf26 on August 18, Kroah-Hartman on August 19) have now found the same u32 * 4 → xdr_inline_decode() wrap in decode_pnfs_layout_types() and decode_getdeviceinfo(). None of the proposals has an in-window ACK. The pNFS client still trusts a wrapped bulk reservation on FSINFO and GETDEVICEINFO.
  • Minimal vs. canonical. Kroah-Hartman’s four insertions are the smallest possible close of the wrap itself. Alibaba’s same-week pair is the classic XDR hygiene (never multiply a server u32 into one bulk inline decode; pull one word at a time). Myklebust’s June review says the canonical close is xdr_stream_decode_uint32_array(). For future decoder work, that helper-first lesson is the one that will actually merge.
  • Testing gap. Because the receive buffer is page-backed, KASAN will not catch this in ordinary client fuzzing. Bommarito’s June KUnit/KASAN reproductions (UML for layout types, QEMU for GETDEVICEINFO) remain the only concrete oracles on the list; this week’s two new patch sets do not include tests.
  • Stable and provenance. Unlike Bommarito’s June series, this patch has no Fixes: tag and no stable Cc. If a maintainer takes a version of this, the historical Fixes: targets already identified on the list are 3132e49ecef9 (“pnfs: track multiple layout types in fsinfo structure”) for layout types and 4e59080397fa (“NFSv4.1: Allow getdeviceinfo to return notification info back to caller”) for the notification bitmap — plus Bommarito’s earlier ca440c383a58 / b1f69b754ee3 tags for the original infrastructure. Someone will need to pick the right one before a backport.

Status and outlook

  • Thread status: Open. One message, no review, no v2.
  • Likely next step: maintainer comparison of this 4-line wrap check against (a) Chuyf26’s word-at-a-time patches from August 18 and (b) Myklebust’s June direction to use xdr_stream_decode_uint32_array(). A v2 that calls the helper, covers both sites, and carries a proper Fixes: / stable trailer is the merge-shaped outcome; accepting the four-liner as-is would leave the “open coding … incorrectly” objection on the table.
  • Open items: (1) which of the three overlapping proposals (if any) becomes the vehicle; (2) whether GETDEVICEINFO’s notification bitmap should be bounded to the RFC 8881 two-bit / one-word limit rather than merely overflow-checked; (3) whether KUnit coverage from the June series should ride along.
