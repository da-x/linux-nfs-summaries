NFS DIO modernization: v6 after Sashiko unpin bugs

Summary

This week’s traffic on Pranjal Shrivastava’s NFS client Direct I/O modernization series is a short status note, not a design debate: the Google engineer announced v6 after static analysis turned up double-unpin bugs in the v5 pin-aware nfs_page path.

The work remains a client feature / preparatory refactor, not a protocol change. It replaces the legacy iov_iter_get_pages_alloc2() O_DIRECT extraction path with iov_iter_extract_pages() so NFS can later pass ITER_ALLOW_P2PDMA. That API shift is also a lifecycle bug-fix: pins must be held until I/O completes, and nfs_page has to distinguish a GUP pin from a normal page reference.

Prior context (posted 10 Aug, just before this window)

v5 kept the five-patch split agreed after the April P2PDMA RFC and the v2/v3 reviews (folio conversion and actual P2PDMA enablement stay in later series):

  1. Make nfs_page pin-aware (PG_PINNED; unpin_user_page() / unpin_user_folio() in nfs_clear_request() and nfs_direct_release_pages()).
  2. Track wb_nr_pinned so only the primary request unpins.
  3. Centralize list teardown in nfs_release_request_list().
  4. Switch Direct I/O to iov_iter_extract_pages().
  5. Factor nfs_direct_extract_pages() for read and write scheduling.

Shrivastava’s cover letter stated the motivation bluntly:

"Currently, NFS O_DIRECT relies on the legacy iov_iter_get_pages_alloc2() API which does not support the pinning requirements for P2P memory."

The v5 changelog already carried two client-side correctness fixes: an iov_iter_revert oops in nfs_direct_extract_pages(), and a swap-over-NFS refcount underflow because nfs_direct_release_pages() called put_page() on unpinned memory. Patch 4 also documents an older DIO-loop bug:

"The migration fixes a bug in the Direct I/O loop where pages were being unpinned immediately after request creation. With the new extraction model, pins are held until the I/O is complete."

Hours after posting, Shrivastava flagged process mistakes: the cover subject still said “v4”, and Christoph Hellwig’s Reviewed-by tags on patches 1–3 had been dropped in the rebase. He asked whether to resend.

This week: Sashiko unpin bugs drive v6

On 14 Aug, Shrivastava answered his own etiquette question by resending. The in-thread note is the only linux-nfs message in this window:

"Quick update: I've posted a v6 [1] with fixes for unpin bugs reported by Sashiko [2] and with R-bs from Christoph that were dropped mistakenly in v5."

The v6 cover (separate thread root, posted minutes earlier) repeats the same design and xfstests matrix (quick group on RDMA/TCP × NFSv3/4.0/4.1/4.2, no regressions vs. pre-series) and adds:

"Fixed double unpin bugs pointed out by Sashiko"

Those fixes land in the pin-tracking core, not in the VFS extraction helper. v6 patch 1 (nfs: make nfs_page pin-aware) grows from 40 to 44 lines in pagelist.c and restores Hellwig’s Reviewed-by. v6 patch 2 (wb_nr_pinned) grows from 9 to 13 lines in the same file. The Direct I/O extraction patches also pick up a few extra lines (patch 4: 34 → 37 in direct.c; patch 5: 127 → 130), consistent with tighter failed-page cleanup so a request is not unpinned twice—once in the scheduling loop and again when the nfs_page is cleared.

Hellwig’s reviews are restored across the pin-aware and helper patches; Shivaji Kant’s tags remain on patches 3–5. Folio aggregation and ITER_ALLOW_P2PDMA / transport P2P negotiation are still explicitly out of scope.

Conclusion

No maintainer ack or merge decision appeared on this thread this week. The series is still in flight: v5’s pin model is the right direction, but Sashiko’s double-unpin findings were serious enough that Shrivastava did not wait for list review of v5. Follow-up coverage belongs on the v6 series.
