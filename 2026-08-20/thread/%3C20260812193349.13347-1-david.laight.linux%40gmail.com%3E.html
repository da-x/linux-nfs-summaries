nfsd write_pool_threads overflow vs truncation

Summary

This week the write_pool_threads() debate shifted from “can nfsd walk off the end of its reply buffer?” to “does the real bug silently truncate a pool-thread count?” It is a server-side bug fix in fs/nfsd/nfsctl.c, not a protocol change and not NFS client work. The practical impact is on the pool_threads control-file reply that administrators (and tooling) use to inspect per-pool nfsd thread counts.

Prior week, in brief

On 12 August, David Laight posted [PATCH net-next] fs: nfsd: Fix buffer overflow in write_pool_threads(), targeting eed2965af1ba (“knfsd: allow admin to set nthreads per node”). The write path dumps each pool’s thread count into a caller-supplied “almost PAGE_SIZE” buffer; Laight argued that if there are enough pools, the existing overflow check fails and the loop keeps writing past the end. He already framed it as hard to hit:

"I'm pretty sure this is 'root only' code. So you'd have to try very hard to actually get the overflow."

Chuck Lever immediately spotted a compile-breaking typo (msg[-1] vs mesg[-1]). Laight conceded it (“Yes - and I thought I'd compiled it ...”) and waved off a missing trailing newline when the output “just fits,” noting you would need “over 1300 pools with 10 threads to get to 4k” and “I'd bet something else dies first.”

This week: overflow recast as truncation

On 16 August, Lever closed the original diagnosis and pointed at a different failure mode:

"I've convinced myself that the actual problem is the truncation. The buffer overflow cannot occur. I've posted a patch to address that."

That companion patch is NFSD: Fail a pool_threads read whose reply does not fit, posted minutes earlier and marked Suggested-by: David Laight. Lever’s changelog is the clearest statement of the user-visible bug: snprintf() truncates its last write and strlen() only measures what fit, so an over-long reply ends mid-number with no newline. “A pool running 4096 threads is reported as 40.” Nothing marks the reply incomplete, so an administrator can read a plausible but wrong count. The proposed fix takes snprintf()’s return value (which reports truncation strlen() cannot see) and fails the read with -ENAMETOOLONG, matching svc_one_xprt_name().

Laight’s unsigned-size analysis

Laight did not withdraw the overflow theory so much as explain why it looked real and why it may still be latent. His analysis:

"size is size_t so unsigned. So after snprintf() truncates the 'size -= len' is going to generate a big number, so the 'size > 0' check doesn't terminate the loop. Which would mean that the next iteration would write beyond the buffer."

He then qualified that snprintf() may refuse “silly” lengths, which “may stop the overwrite,” but that does not stop the length returned to the caller being longer than the buffer. At the call site the buffer is copied back to user space; if the user supplied a long enough destination, that copy “might read beyond the end of the page.” He still treated the whole scenario as practically unreachable:

"Of course this is all likely impossible for other reasons. (and root only)."

Where it stands

The discussion is a bug-fix thread, not a feature or protocol change. Two related defects were on the table:

  1. Loop / length accounting around snprintf() and an unsigned size_t remaining-space counter — Laight’s original overflow claim, still theoretically interesting if truncation wraps size and the caller trusts the returned length.
  2. Silent truncation of a pool-thread count — Lever’s conclusion, and the defect his -ENAMETOOLONG patch actually addresses.

This week’s consensus, as stated by Lever, is that a true buffer overflow “cannot occur,” while a truncated, unterminated pool_threads reply can and should fail the read instead of returning a plausible wrong number. Laight’s reply leaves a residual concern: even if snprintf() itself will not smash the page, a too-large returned length could still over-read when copying back to userspace. No client-side NFS code is involved; the only operational exposure is the nfsd pool_threads control interface.

The thread ends without an ack of Lever’s v1 on this list and without a respin of Laight’s original overflow patch. The live proposed fix is Lever’s fail-the-read change, with Laight’s unsigned-wrap analysis still on the record as the reason the old loop looked broken.
