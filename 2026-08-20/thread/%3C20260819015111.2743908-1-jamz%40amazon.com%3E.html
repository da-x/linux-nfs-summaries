NFS client: restore d_drop on failed nfs_mkdir()

Summary

Amazon’s Jimmy Zuber posted a two-line NFS client bug-fix that restores d_drop() on a failed nfs_mkdir(). The regression dates to 6.15, when NeilBrown’s “mkdir returns a dentry” conversion stopped unhashing the original negative dentry after an RPC error. No one has replied in-window; the patch is unreviewed and not queued.

This is a client dcache correctness fix, not a protocol change and not a new feature. It is tagged Fixes: 8376583b84a1 and Cc: stable@vger.kernel.org # v6.15+.

The regression

Since commit 8376583b84a1 (nfs: change mkdir inode_operation to return alternate dentry if needed), nfs_mkdir() no longer drops the dentry on RPC failure. Zuber writes:

"A negative cache value can then result in spurious ENOENT results for further operations within that directory, such as open or stat."

The user-visible failure is the classic “mkdir raced, then the loser cannot use the directory it just saw exist” pattern:

"We observed this breaking some applications where an EEXIST on mkdir caused the application to assume the directory to exist, only to fail operations within that directory due to the retained negative cache entry."

The sibling create paths were not converted the same way:

"The other create paths, nfs_create() and nfs_mknod(), still drop the dentry on failure. This patch restores the previous behavior."

The change itself is two insertions in fs/nfs/dir.c — restoring the drop that nfs_mkdir() used to do before the 6.15 inode-operation conversion. That conversion was patch 5/6 of NeilBrown’s February 2025 series that taught ->mkdir() and vfs_mkdir() to return an alternate dentry so NFS (and fuse/ceph) could hand the VFS the hashed directory dentry when lookup-plus-create found an existing inode. The mkdir RPC op was switched to return a dentry (NULL meaning “use the original”), and nfs4_do_mkdir() was split out of nfs4_do_create(). In that rewrite the failure-path d_drop() disappeared, leaving a negative dentry hashed after EEXIST (and other RPC errors).

Reproduction

Zuber reproduced it against a local knfsd export over NFSv4.1. The export is mounted six times with nosharecache so each mount is an independent client with its own dcache, plus acdirmin=30,acdirmax=60 so the seeded negatives stick around:

mount -t nfs4 -o vers=4.1,nosharecache,acdirmin=30,acdirmax=60 \
    127.0.0.1:/ /mnt/nfs$i

For each of 40 new cache/<id> directories, every mount stats the name to seed a negative entry, then all mounts race mkdir. The winner writes a file and renames it; the losers that got EEXIST then read that file back. On vanilla v6.17:

"unpatched: read OK 0 / ENOENT 200" "patched: read OK 200 / ENOENT 0"

That is a complete miss: every loser still treats the directory as absent, even though the server created it and the application correctly treated EEXIST as success.

The nosharecache setup is the right hammer for this class of bug. Shared nfs_client / nfs_server structures would otherwise collapse the six mounts onto one dcache and hide the “other client created it, this client still has a negative” race that production multi-client workloads hit.

Why it matters for NFS client development

Negative dentries are load-bearing on NFS: a hashed negative is how the client remembers “this name does not exist” across acdirmin/acdirmax. That is only correct while the name really is absent. After a failed mkdir that lost a create race (EEXIST), the name does exist on the server. Leaving the original dentry hashed means:

  1. subsequent lookup / open / stat of the directory itself return ENOENT from cache, and
  2. operations inside that directory, using a path that still walks the negative dentry, also fail with ENOENT.

Applications that do mkdir + open (or mkdir + stat of a child) and treat EEXIST as “the directory is there” are then broken until the negative times out. Zuber’s numbers say the timeout is not a practical mitigation: with acdirmin=30 every one of 200 loser reads failed.

Restoring d_drop() on the mkdir failure path matches nfs_create() and nfs_mknod() and is the historical NFS answer: unhash the negative so the next lookup goes to the server. It does not try to instantiate the existing directory from the EEXIST reply; it only stops lying about absence. That is the conservative fix, and the one that belongs on stable (v6.15+).

A more ambitious client could, on EEXIST, revalidate or splice in the hashed directory dentry that the 6.15 mkdir-returns-dentry work already knows how to return on the success path. Zuber does not propose that. Given that nfs_create()/nfs_mknod() still just drop, keeping mkdir in line with them is the right incremental repair.

Same-week context: negative dentries, different bug

The same week NeilBrown posted RFC/RFT v2 of “Fix easy bits of the negative dentry problem”, a VFS series about parent d_lockref overflow and soft lockups walking huge ->d_children lists of negatives. That work touches nfs_clear_verifier_directory() only so the NFS client can use a common, later-sleepable child iterator. It does not shrink the negative population and does not address stale negatives after a failed create.

Zuber’s patch is the complementary client bug: not “too many negatives,” but “the wrong negative is still hashed.” The two threads should not be conflated. One is a VFS scalability RFC; this one is a two-line NFS mkdir correctness fix with a hard reproducer and a stable Cc.

Final conclusions (as of 20 August)

  • Classification: NFS client bug fix (stale negative dentry after failed nfs_mkdir()). Regression from the 6.15 ->mkdir dentry-return conversion. Not a protocol change.
  • Technical claim: after 8376583b84a1, RPC failure (notably EEXIST) leaves the original negative hashed; later open/stat of that name or of children return spurious ENOENT. nfs_create() and nfs_mknod() still drop; mkdir should too.
  • Evidence: 200/200 loser reads fail unpatched on v6.17 knfsd/NFSv4.1 with nosharecache; 200/200 succeed patched.
  • Disposition: posted 19 August, no review, no ack, not merged in-window. The Fixes: / stable tag is appropriate; the patch is small enough to land independently of NeilBrown’s negative-dentry RFC.
  • Open question for reviewers: whether mkdir-on-EEXIST should go further and instantiate/return the existing directory dentry (the machinery the 6.15 series added for the success path) rather than only dropping. Zuber does not ask for that, and matching create/mknod is the safer stable fix.
