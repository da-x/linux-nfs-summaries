Wilcox series to drop aops->launder_folio, converting NFS to filemap_invalidate_pages()

Summary

Matthew Wilcox posted a seven-patch VFS/MM cleanup that would delete aops->launder_folio entirely, converting the remaining users—including the Linux NFS client—onto filemap_invalidate_pages(). The series is a page-cache invalidation refactor and efficiency fix, not an NFS protocol change. It landed on linux-nfs on 20 August with no NFS-maintainer review yet; the only in-week reply is a FUSE range-semantics objection from Bernd Schubert.

Why launder_folio is on the chopping block

Wilcox’s cover letter is blunt about the address-space method:

"There's really no reason to implement ->launder_folio. Most filesystems don't. The only problem is that some filesystems rely on dirty folios being written back this way, so we need to make sure that folios are written back before invalidating them. filemap_invalidate_pages() works well for that, once we remove the 'nowait' parameter."

The series is 87 insertions / 174 deletions across 24 files. The plan is:

  1. Export a cleaned-up filemap_invalidate_pages() to modules.
  2. Convert FUSE, btrfs, NFS, and OrangeFS off invalidate_inode_pages2[_range]() so they no longer depend on ->launder_folio for writeback-during-invalidate.
  3. Delete folio_launder() from the VFS and drop the method from the locking and VFS docs.

The VFS API change (and a small existing bug)

Patch 1 is the foundation the NFS conversion needs. Wilcox calls filemap_invalidate_pages() a better filesystem API than invalidate_inode_pages2() / invalidate_inode_pages2_range(), then strips the nowait argument as both unused by those callers and incorrectly implemented:

"It's also wrongly implemented as it will call invalidate_inode_pages2_range() even after filemap_range_has_page() returns false."

The filemap_range_has_page() check moves into the two existing in-tree callers (block/ioctl.c), kernel-doc is added, and the function is exported so NFS (and the other filesystems) can call it from modules.

NFS client: stop per-folio launder on invalidate

The NFS-facing change is patch 4/7. Today the client depends on invalidate_inode_pages2() / invalidate_inode_pages2_range() to write dirty cache via nfs_launder_folio(). Wilcox’s diagnosis is that this is correct but slow:

"nfs relies on invalidate_inode_pages2() / invalidate_inode_pages2_range() doing writeback by calling nfs_launder_folio(). While this works, it is inefficient as each folio is written back and waited for individually. Far better to call filemap_invalidate_pages() which will do a bulk write first, then remove the page cache."

"With this done, nfs_launder_folio() no longer needs to exist so delete it."

The patch touches six NFS files (fs/nfs/dir.c, direct.c, file.c, inode.c, nfs42proc.c, nfstrace.h): 10 insertions, 35 deletions. The 24-line deletion in fs/nfs/file.c is nfs_launder_folio() itself; the trace header loses the corresponding event. Call sites that previously punched holes in the page cache through the old invalidate helpers—directory invalidation, direct I/O, inode-level cache drop, and NFSv4.2 procedures—switch to the bulk writeback-then-remove path.

That is the important NFS client bug-fix/optimization in this thread: invalidation no longer serializes writeback and wait per folio. Dirty NFS pages in an invalidate range should be flushed as a batch, then dropped, which is the same contract the client already wanted from nfs_launder_folio() without the per-folio round trip.

No NFS maintainer (Trond Myklebust, Anna Schumaker, Jeff Layton, Neil Brown, or others) has replied in-window. The conversion therefore remains unacked on the NFS side.

Same conversion for FUSE, btrfs, OrangeFS

The NFS change is one of a matching set:

  • FUSE (fs/fuse/{dax,dir,file,inode}.c): drop fuse_launder_folio(), switch invalidate paths to filemap_invalidate_pages(). Wilcox repeats the same inefficiency argument—each page written back and waited for individually.
  • btrfs: same pattern, deleting btrfs_launder_folio() and updating direct-io, disk-io, free-space-cache, inode, and volumes.
  • OrangeFS: a pair of calls that already open-coded the bulk helper is collapsed to filemap_invalidate_pages().
  • OrangeFS follow-up: unlink ->launder_folio from the OrangeFS address-space ops. Wilcox leaves orangefs_launder_folio() in place because it is still used internally and “removing it entirely would be tricky.”

Closing the DIO vs. mmap redirty window

Patch 7 is the VFS endgame and matters for NFS direct I/O as much as for the other converted filesystems. Direct I/O first writes back overlapping dirty folios, then locks each folio and unmaps it from CPU page tables:

"This leaves a wide window for userspace to re-dirty the folio by storing to a shared writable mmap."

"Many filesystems respond to this situation by failing the call to release_folio(), but some try to writeback the dirty folio again, formerly in their release_folio() method and now in their launder_folio() method."

Wilcox’s conclusion is to stop that filesystem-by-filesystem inconsistency:

"Remove this inconsistency between filesystems by checking whether the folio is dirty in the VFS and failing the call to folio_unmap_invalidate(). Since we hold the folio locked and unmapped at this time, there is no way to dirty the folio after this point."

folio_launder() goes away from mm/truncate.c, include/linux/fs.h, and the VFS/locking documentation. After this, a redirtied folio during DIO invalidate fails in the VFS rather than being re-laundered by NFS (or anyone else).

Only review so far: FUSE range semantics, not NFS

Bernd Schubert replied to the FUSE conversion, not the NFS patch. He flags a possible behavior change in the invalidate-length handling:

"Please correct me if I'm wrong, but doesn't that changes behavior for len <= 0? The logic to invalidate till the file end is lost, at least if offset is != -1? And incostent behavior for len < 1? Note that the existing behavior is used by libfuse and heavily by some fuse daemons."

Wilcox has not answered in this window. The objection is FUSE-userspace ABI, not NFS, but it is the only sign the series is under review and it may stall the common helper before the NFS conversion can land.

Status

This is a VFS cleanup plus NFS client invalidation efficiency fix. It is not a protocol change. As of 20 August the series is posted, the NFS client would lose nfs_launder_folio() and call filemap_invalidate_pages() from dir, DIO, inode, and NFSv4.2 paths, and the VFS would fail DIO invalidate on a redirtied folio instead of asking the filesystem to launder again. Nothing is merged or acked on linux-nfs this week; the open question is Schubert’s FUSE len <= 0 concern, with NFS review still outstanding.
