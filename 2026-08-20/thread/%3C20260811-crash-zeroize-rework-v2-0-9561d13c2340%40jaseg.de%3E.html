Crash-region registry proposed as alternative to panic-path secret wipe

Summary

This week’s traffic on Jan Sebastian Götte’s v2 CRASH_WIPE_SECRETS series is a design debate, not an NFS client bug-fix thread. The four in-window messages all reply to patch 01/13 and converge on replacing panic-path wipe notifiers with a pre-populated crash-memory region table. No new patches landed; Götte committed to posting a registry prototype this or next week.

What this series is

This is a new opt-in kexec/kdump feature, not a protocol change and not an NFS client bug fix. Posted last week as PATCH v2 00/13, it adds CONFIG_CRASH_WIPE_SECRETS so subsystems holding keys can erase them before __crash_kexec() jumps into the dump kernel. Götte’s use case is an HSM-like ARM64 embedded target: kdump is used as a tamper-response path that then memzeros DRAM, but a full linear wipe is “rather slow,” so he wants the “obviously sensitive stuff like keys gone as fast as possible.”

The NFS client footprint in v2 is tiny. The series CCs linux-nfs because fs/nfs/nfs4idmap.c gains a two-line wipe hook on the NFSv4 idmap key type, and because patch 10/13 adds an rxrpc key wipe (session keys/tickets plus rxkad/rxgk server-key ops). Neither NFS nor rxrpc was discussed this week. There is no NFS client functional change, no pNFS/layout work, and no bug fix under review here.

Brief bridge from last week

v2’s core hook, patch 01/13, registers an atomic notifier chain invoked late in __crash_kexec() after machine_crash_shutdown() has stopped other CPUs. Callbacks must not wait on locks. Götte called it “a best-effort, defence-in-depth measure, not a guarantee.”

That approach drew immediate pushback. Eric Biggers argued the kernel already struggles to zeroize keys at normal end-of-life, so a second, panic-only, lock-free wipe path for every subsystem is unmaintainable: “If we can barely even do that, we aren't going to be able to correctly and completely implement and maintain separate zeroization code.” He asked Götte to “narrow the scope to one or two things,” noting even dm-crypt does not need a global crypto-tfm wipe list because “dm-crypt has its own copy of the key.” Götte offered to keep at least secretmem and dm-crypt.

kexec maintainer Baoquan He separately objected to stuffing more work into the crash path, analogizing it to someone wanting Oracle to “do some transactions before juming into kdump kernel because the actions will save billions of dollar,” and asked whether this belonged in a vendor tree. Götte replied that a full DRAM wipe in the kdump kernel takes “several hundred milliseconds” against a 10 ms budget, and floated the alternative that now dominates this week: a registry of (addr, len) descriptors in crashkernel memory so the kdump kernel, not the dying kernel, does the memzero.

Milan Broz also rejected the dm-crypt patch as a second wipe implementation beside crypt_wipe_key(), writing “Please no. It looks to me like you are trying to fix this on the wrong layer.” Götte agreed to drop per-driver crash_wipe_memzero helpers and flush caches in kexec instead.

This week: alternatives to panic-path handlers

On 16 August, Lukas Wunner replied to Götte’s registry sketch and offered a second model: isolate secrets in one allocator rather than tracking them after the fact.

"Or create a dedicated mempool from which all sensitive data is allocated, then call mempool_free_bulk() on kexec to poison everything in that pool?"

That idea was not taken up. The rest of the week stayed on the registry.

Baoquan He first asked the CC’d security people a threat-model question that still has no reply:

"Since there are a lot of security expert in CC, I am wondering what's the risk if we wipe secrets during dumping. System is located in user's place, and vmcore is dumped and collected in user's place. If we filter out secrets memory when we dumping, what could be leaked out?"

He then followed up with a concrete API that generalizes Götte’s secrets-only table into a small crash-memory region table with a per-entry action (message):

enum crash_region_action {
    CRASH_REG_WIPE,   /* memzero, then dump normally (leave zeros) */
    CRASH_REG_SKIP,   /* do not include in the vmcore at all */
};

struct crash_region {
    phys_addr_t addr;
    size_t      len;
    enum crash_region_action action;
};

void crash_reg_add(phys_addr_t addr, size_t len,
                   enum crash_region_action action);
void crash_reg_del(phys_addr_t addr, size_t len);

He split the two actions on purpose. WIPE is Götte’s secret-erasure case (zero the buffer, then still dump the zeros). SKIP is a vmcore-size play: omit regions entirely. He has been looking at shrinking dumps on large systems where “the vmcore size usually is several or tens of GB,” and suggested drivers could later register unused memory as SKIP. His sequencing advice was explicit: start the registry with wiping secrets, “we can add SKIP later and plus some driver used memory,” and “you can give it a shot to show what it looks like.”

That is the week’s technical conclusion. The panic-path notifier in patch 01/13 is no longer the preferred direction if the work stays in mainline. Moving the memzero into the kdump kernel via a table populated ahead of time removes code from __crash_kexec(), avoids lock-free walking of live keyrings/tfms during panic, and gives kdump a hook that can later shrink dumps as well as sanitize them.

Götte accepted without caveats:

"I think that's a good idea. I'll post a patch adding that registry this or next week."

Status and NFS client takeaway

The discussion is still design-only. Open questions: whether security reviewers will answer Baoquan’s “what leaks if we filter at dump time?” question; whether Wunner’s dedicated-mempool idea is worth a prototype; how crash_reg_add/del stay consistent if buffers move; and whether SKIP lands with wipe or later. No one this week revisited the NFS idmap or rxrpc wipe ops, and those hooks would likely be re-cast as region registrations if the registry replaces per-subsystem panic notifiers.

For NFS client development this week: no client bug fix, no protocol change, and no functional NFS discussion. The only NFS-adjacent content remains last week’s two-line nfs4idmap wipe hook riding along on a kexec series whose architecture is now being rewritten.
