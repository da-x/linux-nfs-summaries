SUNRPC OOB write in xdr_inline_pages()

Summary

A late-week bug-fix patch from Paula Moutafian targets a long-standing SUNRPC receive-path hole that can turn a legal NFSv3 AUTH_SYS reply into a peer-controlled slab write on the Linux NFS client.

The defect sits in xdr_inline_pages(), which re-carves an existing receive buffer into head, page list and tail at a caller-supplied offset and computes the tail length as buflen - offset. Because iov_len is unsigned, an offset past the end wraps instead of failing:

"It does not check that the offset lies within the buffer being carved, and iov_len is unsigned, so an offset past the end wraps the tail length instead of failing."

That offset is not an internal constant. Moutafian traces it to wire data: rpc_prepare_reply_pages() derives it from the authentication flavour’s au_ralign, which is reread on every encode, while the receive buffer size is fixed once in call_allocate() from au_rslack. unx_validate() then raises au_verfsize, au_rslack and au_ralign from the reply verifier’s length before rpc_decode_header() inspects accept_stat. A GARBAGE_ARGS reply can therefore poison the alignment and only afterwards send the task back through call_encode(). call_allocate() short-circuits on the existing buffer, so rq_rcvsize is not recomputed and the retry carves a new offset against the old size. Compounding the geometry, auth_unix keeps those fields in a file-scope static rpc_auth shared by every AUTH_SYS client.

For NFSv3 READ the design slack is a single XDR word, so the underflow needs only au_ralign at encode to exceed au_rslack at allocation by two — a five-byte verifier body. The observed case used eight: rq_rcvsize 132 with a 128-byte head and 4-byte tail, au_ralign raised from 2 to 4, and a retry carve at (26 + 4 + 4) << 2 = 136 against the unchanged 132-byte buffer. The in-tree sunrpc:rpc_xdr_reply_pages tracepoint captured the wrap on one task:

"rpc_xdr_reply_pages: head=[..a18,128] tail=[..a98,4] rpc_xdr_reply_pages: head=[..a18,136] tail=[..aa0,4294967292]"

xs_read_xdr_buf() then fills the tail against that wrapped length. TCP record length is not capped against rq_rcvsize, so the reply to the retried call writes peer-controlled bytes past the rpc_buffers object. KASAN on an unmodified v7.2-rc7 arm64 kernel reported:

"BUG: KASAN: slab-out-of-bounds in _copy_to_iter+0x7c8/0x1538 Write of size 1664 at addr ffff0000c7640aa0 by task kworker/u8:0/12"

The write landed 160 bytes past the object, with both length and payload chosen by the peer. Moutafian is careful about what KASAN actually proves: the interposed __asan_memcpy() returns without calling __memcpy once the range check fails, so the report establishes that the write is reachable and out of bounds, not that the copy executed. The enlarged head stays inside the same slab object and is not itself a violation.

The trigger is an ordinary read(2) on an already mounted NFSv3 AUTH_SYS share over TCP and needs no client privilege; every byte the attacker supplies is a legal server reply. The blast radius is narrower than a generic SUNRPC issue: under RPCSEC_GSS the verifier is authenticated and cannot be forged; UDP is bounded by datagram length in xs_udp_data_read_skb(); NFSv4 does not take the retry path because RPC_TASK_NO_RETRANS_TIMEOUT suppresses the re-encode.

Commit 53bc19f17f21 ("SUNRPC: receive buffer size estimation values almost never change") gated the equivalent slack update behind RPCAUTH_AUTH_UPDATE_SLACK in gss_update_rslack(), but auth_unix was never converted and still assigns unconditionally. Gating it the same way would only narrow the window:

"the first update can still land between the allocation and the re-encode of an in-flight request, and it would leave the other caller of xdr_inline_pages() unguarded."

The chosen fix is therefore at the carve itself: clamp the offset to the length of the buffer so the tail length cannot underflow. There is no Fixes: tag; the unbounded carve is original to xdr_inline_pages() (unchanged since the initial git import), and unx_validate() has written the shared rpc_auth slack from the reply verifier since at least v2.6.32.

Reproduction is 2/2 on unmodified v7.2-rc7 with CONFIG_NFS_V3=y; the patched kernel has not been built or booted. A reproducer exists and can be shared privately. The posting is credited Assisted-by: Bynario AI. No in-week review replies landed before the window closed.
