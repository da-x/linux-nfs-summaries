Flexfiles DS setup errors get a real opnum, not OP_ILLEGAL

Summary

This week’s linux-nfs traffic on this thread is a single, pointed client review of Benjamin Coddington’s NFSv4 flexfiles diagnostic fix, posted the previous day as patch 1 of 3 in the “pNFS/flexfiles: mirror instance error handling” series.

The discussion is a bug-fix / error-reporting improvement on the NFS client’s pNFS flexfiles layout driver, not a protocol change. It sits in a larger client-side effort to stop the flexfiles driver from lying to the metadata server (and to operators) when a data-server (DS) path dies.

Prior week, in brief

On 13 August, Coddington sent a three-patch series whose cover letter described a real recovery hazard: when a flexfiles DS fails, the client marks the layout for return and cancels in-flight I/O for the whole layout segment. ff_layout_cancel_io() currently kills RPCs on every mirror, including healthy ones. Requests already on the wire cannot be un-sent, so writes can complete on a DS after LAYOUTRETURN, and the MDS then sees writes against a file that no longer has an outstanding write layout.

Patch 1 is the diagnostic half of that story. When nfs4_ff_layout_prepare_ds() cannot even connect to a DS, the client records a device error with opnum OP_ILLEGAL because nothing ever went on the wire. Coddington argued that this is the wrong signal:

"But servers can use the ff_ioerr4 opnum to distinguish failed read-class operations from write-class operations when deciding how to recover the affected mirror -- a mirror that may have missed writes needs to be brought back in sync, while one that merely failed to serve a read does not. OP_ILLEGAL gives the server nothing to act on."

Every caller already knows which operation it was preparing (READ vs WRITE/COMMIT), and the existing fail_return boolean already splits along that same boundary (false for READ, true for WRITE and COMMIT). The patch replaces that boolean with the intended NFS opnum, derives the layout-return decision from it, and reports the real opnum in the tracked device error instead of OP_ILLEGAL. The change is confined to flexfilelayout.c, flexfilelayout.h, and flexfilelayoutdev.c.

Patches 2 and 3 (not reviewed in this thread this week) then thread a device-ID argument through ->cancel_io() so a failed mirror can be cancelled in isolation while I/O to remaining mirrors drains before LAYOUTRETURN, matching RFC 8881 §20.3.4’s advice to wait for in-flight READ/WRITE/COMMIT.

This week: Tigran Mkrtchyan’s review

On 14 August, Tigran Mkrtchyan of DESY replied only to patch 1, with the tone of someone who has been staring at the current logs in production:

"Our logs are full of those OP_ILLEGAL errors. Thanks for making them more useful."

"The change makes sense and looks valid."

He added Reviewed-by: Tigran Mkrtchyan <tigran.mkrtchyan@desy.de>. There was no request for a respin, no debate over the fail_return → opnum mapping, and no comment in this thread on patches 2/3.

That is the entire in-window conversation: an Ack on the client’s flexfiles DS-setup error path, motivated by real operational noise. The review does not close the series — cancellation of I/O to a single failed mirror remains unreviewed here — but it does lock in the first, independently useful piece: when a flexfiles client cannot even reach a DS, the MDS (and the logs) will now see the operation that was about to be sent, rather than a synthetic OP_ILLEGAL.

Conclusions

  • Type: NFS client bug-fix / error-reporting improvement in the pNFS flexfiles layout driver.
  • This week’s outcome: Patch 1 has a Reviewed-by from Mkrtchyan; no technical objections were raised.
  • Client impact: DS connection-setup failures will report the intended READ/WRITE/COMMIT opnum in ff_ioerr4, giving servers a usable recovery hint and operators a log line that is not a wall of OP_ILLEGAL.
  • Still open in the parent series: per-device cancel_io and “only cancel the failed mirror” have not been discussed on this thread this week.
