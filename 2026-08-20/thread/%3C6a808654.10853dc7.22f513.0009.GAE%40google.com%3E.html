syzbot: stack overflow in nfsctl_transaction_write via recursive svc_write_space

Summary

This week’s linux-nfs traffic includes a fresh syzbot crash against upstream, tagged [net?] [nfs?]. The report is a bug, not a protocol change or a new feature: a TASK stack guard-page hit while writing NFSD control-plane ports through nfsctl_transaction_write. No maintainer, reviewer, or patch has answered yet, so the thread remains an untriaged crash dump with a C reproducer.

What syzbot reported

On 15 August, syzbot filed:

"syzbot found the following issue on: HEAD commit: d58772d8520c Merge tag 'regmap-fix-v7.2-rc7' of git://git... git tree: upstream"

The bot asked that any fix carry:

"Reported-by: syzbot+54cdc566f64abf51b7f1@syzkaller.appspotmail.com"

The kernel is an upstream tree at d58772d8520c (around v7.2-rc7), built with gcc 14.2.0, KASAN, and PREEMPT(full). Userspace is i386 (userspace arch: i386), and the faulting task entered via a 32-bit compat write:

do_fast_syscall_32
ksys_write
vfs_write
nfsctl_transaction_write

The oops itself is unambiguous:

"BUG: TASK stack guard page was hit at ffffc900037d7ff8 (stack is ffffc900037d8000..ffffc900037e0000) Oops: stack guard page: 0000 [#1] SMP KASAN NOPTI"

RIP is in kasan_check_range() (mm/kasan/generic.c:199), with CR2 pointing at the guard page. That is stack exhaustion, not a typical KASAN heap-use-after-free.

Dashboard, console log, kernel config, syz repro, and C reproducer are all attached. Syzbot’s usual control commands (#syz fix, #syz test, #syz dup) are present; none have been used this week.

Call chain: NFSD control write into SUNRPC sockets

The outer path is NFSD’s nfsctl transaction interface, not an NFS client READ/WRITE. The truncated-but-complete tail of the trace is:

  • nfsctl_transaction_write (fs/nfsd/nfsctl.c:112)
  • write_ports / __write_ports / __write_ports_addfd (fs/nfsd/nfsctl.c:861 / 805 / 742)
  • svc_addsock (net/sunrpc/svcsock.c:1547)
  • svc_setup_socket (net/sunrpc/svcsock.c:1498)
  • svc_udp_init (net/sunrpc/svcsock.c:854)
  • svc_sock_setbufsize (net/sunrpc/svcsock.c:386)
  • then unbounded recursion through svc_write_space (net/sunrpc/svcsock.c:429–430)

In other words, a write to the NFSD ports file that adds a file descriptor (__write_ports_addfd) is enough to set up a UDP svc socket, resize its buffers, and then overflow the kernel stack.

That matters for client-facing NFS as well as the server: svc_write_space lives in shared SUNRPC socket code (net/sunrpc/svcsock.c). A recursive sk_write_space callback on an svc socket can take down any kernel thread that happens to be in that path, not only nfsd workers. Here the victim is the syzkaller process itself (Comm: syz.0.18), PID 5932, running a compat write(2) against nfsctl.

The smoking gun: recursive svc_write_space

The body of the oops is almost entirely one function calling itself. After the first frame:

svc_write_space+0x90/0x2b0 net/sunrpc/svcsock.c:429

the dump repeats, hundreds of times:

svc_write_space+0xe6/0x2b0 net/sunrpc/svcsock.c:430

The first frame is the tracepoint trace_svcsock_write_space (via cpu_online / cpumask_test_cpu / KASAN’s _test_bit). Every subsequent frame is the same function at offset 0xe6, i.e. the recursive call site at svcsock.c:430.

That pattern is the classic unbounded sk->sk_write_space recursion: svc_write_space is installed as the socket’s write-space callback; something in that callback (or in svc_sock_setbufsize, which the outer frames show calling into it) notifies write-space again on the same or a chained socket, and there is no recursion brake. Each call consumes stack; KASAN instrumentation on cpu_online inside the tracepoint makes the frames even fatter, so the 8K/16K kernel stack hits the guard page quickly.

The disassembly note in the report matches that story:

"* 2a: 55 push %rbp <-- trapping instruction"

kasan_check_range is trying to push a frame onto an already-exhausted stack.

NFS client angle, and why the subject is tagged [nfs?]

Despite the [nfs?] tag, this is not an NFS client I/O bug. The trigger is NFSD’s user-facing control file (nfsctl_transaction_write → write_ports). Client developers still care, for two reasons:

  1. Shared SUNRPC socket layer. svc_write_space, svc_sock_setbufsize, and svc_setup_socket are the same helpers used whenever a kernel RPC service binds a socket. A write-space recursion bug is a SUNRPC transport bug; it can in principle bite local RPC services that the NFS client stack also uses (lockd, rpc.statd-adjacent kernel bits, nfsdcld is userspace, but the svc socket code is common).
  2. Compat / 32-bit entry. The repro runs as i386 userspace on a 64-bit kernel (entry_SYSENTER_compat_after_hwframe, do_fast_syscall_32). NFS client test matrices that exercise 32-on-64 nfsctl or mount helpers are exactly the kind of environment that would trip this if a similar fd-add path is used.

There is no indication of a client-side nfs_file_write / sunrpc client transport issue in this dump. The [net?] tag is the more accurate of the two: the unbounded recursion is in net/sunrpc/svcsock.c.

Reproduction and environment

Syzbot shipped both a syz repro and a C reproducer, plus a non-bootable disk image, vmlinux, and bzImage for d58772d8520c. Hardware is QEMU Q35. The task is untainted (Not tainted syzkaller #0). No modules are loaded.

The control-plane write is tiny: write(fd=6, buf, 1) in the compat registers (RDX: 0000000000000001), which is consistent with writing a single-byte / short ports record that still takes the addfd branch.

Status this week

This is a one-message thread. ListThreadMessages shows only the 15 August syzbot mail; there is no prior weekly summary file for this Message-ID, and no human reply in-window. Related-subject search did not turn up an existing linux-nfs discussion of this exact nfsctl_transaction_write stack-guard hit.

Until someone replies, the technical conclusion from the dump alone is:

  • Class: kernel stack overflow / unbounded recursion (DoS, Oops).
  • Site: svc_write_space() in SUNRPC server sockets, entered from svc_sock_setbufsize() while adding a UDP svc socket via nfsctl write_ports.
  • Trigger surface: privileged write to NFSD’s ports transaction file (__write_ports_addfd), exercised here from 32-bit compat userspace.
  • Fix direction (not yet proposed): break the sk_write_space re-entry in svc_write_space / svc_sock_setbufsize (guard against calling the same callback on the socket whose write-space is already running; or defer buffer-size notification so it cannot recurse during init). Any such commit should include the syzbot Reported-by tag quoted above.

No patch, no #syz fix, and no subsystem re-tag landed this week. The crash is still open on the syzbot dashboard.
