NFSD iterator-READ fsnotify/atime fixes meet VFS pushback

Summary

Summary

Ameer Hamza posted a two-patch bug-fix series for NFSD's iterator READ path, split out of his larger SUNRPC reply-page recycling work at Chuck Lever's request. Both patches target fs/nfsd/vfs.c, carry Fixes: 507df40ebf316 ("NFSD: Hoist rq_vec preparation into nfsd_read()") and Cc: stable@vger.kernel.org, and are tagged Assisted-by: Claude:claude-fable-5. This is not a protocol change and it does not touch the NFS client; the client-visible effect, if any, is on the server: inotify watchers of exported files currently see iterator READs twice, and some exported filesystems never advance atime on that path.

By week's end, patch 2/2 (the atime update) is withdrawn. Patch 1/2 (the duplicate fsnotify event) is acknowledged as a real bug but is not yet accepted as an NFSD workaround; Lever has asked VFS/fsnotify maintainers whether the splice helpers should emit the event instead.

The bugs, as they stand today

Iterator READs already run without Hamza's recycling series. They are the path for sec=krb5i / sec=krb5p, nfsd_disable_splice_read, and the NFSD_IO_DONTCACHE / NFSD_IO_DIRECT modes. Spliced READs are a different helper stack, and that mismatch is the whole story.

Patch 1/2 documents the fsnotify double-count:

"A READ served without splice emits two fsnotify access events; a local read of the same file emits one. vfs_iocb_iter_read() emits an access event when the read succeeds, and nfsd_finish_read() emits a second one for the same READ."

Spliced READs are not affected, because splice_direct_to_actor() emits nothing and nfsd_finish_read() supplies their only event. Hamza's proposed fix is to move fsnotify_access() out of the common nfsd_finish_read() and into nfsd_splice_read(), "the one path whose VFS helper does not emit it." Measured with an inotify watch: iterator drops from two events per READ to one; splice stays at one.

Patch 2/2 is the atime counterpart. nfsd_iter_read() and nfsd_direct_read() leave atime to the filesystem's ->read_iter. Hamza argues that is not a contract NFSD can rely on:

"fuse_dax_read_iter() carries a TODO for it, and kernfs_fop_read_iter() does not touch the atime at all. On a fuse DAX export, READs never advance the atime, no matter how often clients read the file. ... nfsd serves whatever filesystem is exported, so it cannot rely on every ->read_iter keeping the convention."

The proposed fix is file_accessed() after each successful vfs_iocb_iter_read(). Spliced READs already pick this up from splice_direct_to_actor().

Hellwig: do not paper over VFS gaps in NFSD

Christoph Hellwig rejected both patches on architectural grounds, not on whether the symptoms exist.

On patch 2/2 he drew a hard line at file_accessed():

"Code outside of file systems and library code has absolutely no business ever calling file_accessed."

He also objected to the LLM-assisted style of the series, and to the broader pattern of treating filesystem corner cases as something core code should paper over:

"And please stop this LLM garbage. Your patches seem to have a pattern of finding some unusual corner case that is broken in a file system and than work around it in core code. That's not how it works."

On patch 1/2 he located the bug in splice, not in nfsd:

"Well, that is the underlying bug here. ->splice_read should not skip fsnotify events and nfsd should not work around this as fsnotify is not the business of the users of VFS APIs."

That is the same theme as his NACK on the parent recycling series: NFSD should not grow special cases to compensate for VFS helper inconsistencies.

Lever: drop the atime patch; ask fsnotify about the event site

Chuck Lever, who had asked Hamza to split these out as a backportable fix, walked both conclusions back after Hellwig's review.

On the fsnotify patch he still wants the duplicate event fixed, but no longer claims NFSD is the right layer:

"I asked for the duplicate event to be split out of Ameer's larger series as a backportable fix because there is clearly a bug here. But NFSD might not be the correct place to address it."

He then mapped the current call sites. Today the fsnotify access event comes from the system call implementations, not from the splice helpers: do_sendfile() calls fsnotify_access() after do_splice_direct() returns, and do_splice() does the same for splice(2), while vfs_splice_read() and splice_direct_to_actor() emit nothing. vfs_iocb_iter_read() is the outlier, emitting from inside the helper. NFSD calls splice_direct_to_actor() directly, so on that path it behaves like do_sendfile() and emits the event itself — which is why the two NFSD READ paths disagree. Moving the call site down into ->splice_read would double sendfile events unless the syscall implementations stop emitting it at the same time. Lever pinged Jan Kara and Amir Goldstein for a VFS-level ruling.

On the atime patch he conceded Hellwig's point outright. Every existing file_accessed() call site in the kernel is a filesystem; NFSD would have been the first outsider. More importantly, he had misread FUSE:

"I see now that FUSE does not maintain atime in the kernel. file_accessed() from NFSD would have stamped a kernel-side atime on an inode whose atime the user space filesystem manages."

He had assumed FamFS would hit the same hole, then doubted that. The TODO in fuse_dax_read_iter() remains confusing — "Implementing that should be a one-liner, or it should be replaced with a comment that explains why that callback is missing an explicit atime update" — but it is a FUSE problem, not an NFSD one.

"So we can drop 2/2. Sorry for the noise."

Where things stand

This week's conclusion is split:

  • Patch 2/2 is dead. NFSD will not call file_accessed(). If fuse DAX (or kernfs) fails to update atime on ->read_iter, that belongs in those filesystems.
  • Patch 1/2 is a real bug with no agreed home. Iterator READs still emit two fsnotify access events; splice READs emit one. Hellwig wants splice to emit the event. Lever showed why a naive move into ->splice_read would break sendfile(2) / splice(2) unless those syscalls are changed in lockstep. The question is now with the fsnotify maintainers; Amir Goldstein's reply arrived after this week's window.

There is still no NFS client code in this thread. The server-side fallout that does matter to clients is limited to inotify/fanotify watches on exported files (double access counts for krb5i/krb5p, nfsd_disable_splice_read, and direct/dontcache READs) and, until patch 2 was dropped, a mistaken kernel atime stamp on FUSE exports. The parent recycling series remains blocked on a separate splice-vs-iter debate; these two patches were meant to clear the accounting issues before that series expanded the iterator path further. After this week, only the fsnotify half is still live, and only as a VFS placement question.
