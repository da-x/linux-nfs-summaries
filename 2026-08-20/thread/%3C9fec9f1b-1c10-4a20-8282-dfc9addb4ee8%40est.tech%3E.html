nfs-utils exportfs --disable-nfsdctl link fix lands in 2.9.3-rc1

Summary

This week the Jaipaul Cheernam nfs-utils 2.9.2 build regression is closed. nfs-utils maintainer Steve Dickson selected Cheernam’s Option B, applied it with Cheernam as author, and committed it as nfs-utils-2-9-3-rc1. This is a userspace bug fix (configure/Makefile feature-gating), not a protocol change and not an in-kernel NFS client patch.

The thread still lives on the server-side tools. The operational impact for NFS clients is indirect: distributions and embedded builds that pass --disable-nfsdctl can again produce exportfs, the utility that publishes and withdraws the exports a client later mounts.

Last week, in brief

On 5 August Cheernam reported that 2.9.2 no longer links exportfs under a configuration 2.9.1 accepted:

"Building nfs-utils 2.9.2 with --disable-nfsdctl fails to link exportfs. This is a regression from 2.9.1."

The linker error was undefined reference to 'nfsd_nl_cmd_str' from unexportfs_parsed in exportfs.c. New-in-2.9.2 nfsdnl.c is compiled into libnfs only under CONFIG_NFSDCTL, while configure.ac defined HAVE_NFSD_NETLINK unconditionally, so exportfs always compiled the netlink path. Default (enable_nfsdctl=yes) builds hid the bug.

Cheernam offered two tested fixes and preferred Option B: gate HAVE_NFSD_NETLINK on --enable-nfsdctl so exportfs skips the netlink path and uses the existing nfsdnl.h -ENOSYS stub. Option A would have always compiled nfsdnl.c into libnfs. No maintainer reply landed in that week.

This week: Option B is chosen and committed

On 15 August Dickson first confirmed that Cheernam’s preferred approach works and that he would apply it himself rather than wait for a formal patch:

"Option B does work... I can just added and make you the author..."

About two and a half hours later he followed up that the change was already in the tree:

"I just went ahead an took Option B adding you as the author and I did the Signed-off-by: since it did fix the bug."

"Committed (tag: nfs-utils-2-9-3-rc1)"

That is the policy decision the original report asked for. --disable-nfsdctl now means “do not talk to nfsd over generic netlink at all,” not merely “do not build the nfsdctl binary.” HAVE_NFSD_NETLINK is defined only inside the existing if test "$enable_nfsdctl" = yes block, next to the readline check, matching the CONFIG_NFSDCTL guard in support/nfs/Makefile.am. When nfsdctl is off, exportfs no longer compiles the netlink unlock-export path and the missing nfsd_nl_cmd_str symbol is no longer required at link time.

Dickson did not debate Option A on-list. The counter-argument Cheernam had flagged — that exportfs might still want to release export state via netlink even when the nfsdctl utility is not built — was not taken. The maintainer’s test was pragmatic: Option B “did fix the bug,” so it shipped.

Conclusions

  • Bug class: 2.9.2 feature-gate split between configure.ac (HAVE_NFSD_NETLINK always on) and support/nfs/Makefile.am (nfsdnl.c only with CONFIG_NFSDCTL).
  • Fix: Option B, authored by Cheernam, Signed-off-by Dickson, committed as nfs-utils-2-9-3-rc1.
  • Design intent preserved: --disable-nfsdctl disables all netlink interaction with nfsd, including exportfs unlock-export.
  • NFS client: no on-the-wire or kernel-client change. Slim nfs-utils builds that disable nfsdctl (and often GSS) can produce exportfs again; default --enable-nfsdctl configurations were never broken.

The thread ends with the commit notice. No further review or follow-up patch was requested.
