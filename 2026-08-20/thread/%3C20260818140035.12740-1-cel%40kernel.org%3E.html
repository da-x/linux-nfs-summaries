NFSD header include hygiene for nfsd.h and xdr.h

Summary

This week Chuck Lever posted a three-patch NFSD header-cleanup series that trims transitive includes out of the server’s widely pulled-in headers. It is neither a protocol change nor a client-side bug fix: the work is strictly server-side include hygiene, aimed at making fs/nfsd/nfsd.h stop acting as a dump for NFS protocol types that the header itself never uses.

Jeff Layton reviewed all three patches the next day with no technical objections. There was no further debate, and the series stands as reviewed.

Why nfsd.h was carrying NFSv3 definitions

Patch 1 is the core of the series. Lever’s diagnosis is blunt:

"fs/nfsd/nfsd.h is included throughout the server, yet it uses no NFSv3 protocol definition of its own. The <linux/nfs3.h> include there served only to make those definitions reach the few source files that need them, by way of nfsd.h itself or the xdr.h chain that pulls it in."

The practical effect of that hidden include was that any .c file which needed NFS3_* constants could compile without declaring the dependency. Lever moves the include to the actual consumers — nfsfh.c, nfsctl.c, nfs3xdr.c, nfs3proc.c, and nfs2acl.c — and drops it from nfsd.h:

"Give each consumer its own include and drop the one in nfsd.h, so the header no longer carries a dependency unrelated to its contents."

That is a classic include-what-you-use cleanup. It does not change NFSv3 encoding, ACCESS bits, or filehandle layout; it only stops the common server header from smuggling protocol constants into every translation unit. Layton reviewed it without comment beyond Reviewed-by.

Direct struct nfs_fh includes, paving a later nfs.h drop

Patch 2 applies the same rule to filehandle types. struct nfsd4_copy embeds a struct nfs_fh, and nlm_fopen() in lockd reads that object’s size and data fields. Neither fs/nfsd/xdr4.h nor fs/nfsd/lockd.c included the header that defines the type; both reached it through nfsd.h → <linux/nfs.h>.

Lever adds #include <linux/nfs_fh.h> in both places, and states the follow-on goal explicitly:

"Add the direct include to both files, so nfsd.h can later drop the <linux/nfs.h> it carries for no use of its own."

This patch is therefore a prerequisite, not the final drop of <linux/nfs.h> from nfsd.h. The series does not yet remove that include; it only makes the remaining consumers self-contained so a later patch can. Layton reviewed this one as well.

For NFS client readers, the interesting angle is the direction of travel rather than any client code change. Lever has been peeling NFS client headers out of other subsystems (notably LOCALIO earlier this cycle). Here the same discipline is applied on the server: protocol and filehandle types should be included where they are used, not re-exported from a catch-all nfsd.h. That reduces the chance that a client-header tweak silently rebuilds, or worse, silently type-checks, large parts of nfsd.

Header-guard provenance in xdr.h

Patch 3 is a six-line mechanical cleanup of include guards in fs/nfsd/xdr.h. Lever’s one-line rationale:

"Make the header guards less ambiguous about their provenance."

The new guard is _LINUX_NFSD_XDR_H. Layton’s review again carries no extra commentary.

Outcome

By 19 August the entire series had Reviewed-by: Jeff Layton on every patch. No v2 was requested, no compile or runtime concern was raised, and no client-visible behavior is intended to change. The unfinished item Lever himself flagged is the subsequent removal of <linux/nfs.h> from nfsd.h, which this series only enables.

Classification: NFSD include-hygiene / refactor, not a bug fix and not a protocol change. Client impact is none in this week’s patches; the value for client development is the continued uncoupling of shared NFS headers from nfsd’s common include graph.
