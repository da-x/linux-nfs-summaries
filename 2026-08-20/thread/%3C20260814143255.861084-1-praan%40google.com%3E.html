NFS client DIO v6: pin-aware extract_pages path

NFS client Direct I/O modernization v6: pin-aware nfs_page and double-unpin fixes

Summary

This week Pranjal Shrivastava (Google) posted v6 of the NFS client Direct I/O modernization series — five patches, no replies yet. The work is a preparatory client feature with several lifecycle bug fixes baked in. It is not a protocol change: the RPC and NFS wire formats are untouched. The goal is to get O_DIRECT off the legacy VFS helper that cannot pin P2P memory, so a later series can pass ITER_ALLOW_P2PDMA.

Shrivastava’s cover letter states the constraint plainly:

"Currently, NFS O_DIRECT relies on the legacy iov_iter_get_pages_alloc2() API which does not support the pinning requirements for P2P memory."

The implementation therefore moves the client Direct I/O path to iov_iter_extract_pages(). Folio aggregation and actual P2PDMA enablement remain explicitly out of scope, as agreed after the April RFC and the v2 review.

v6 exists because v5 was not safe to land. The changelog’s first bullet is the client-side reason for the resend:

"Fixed double unpin bugs pointed out by Sashiko"

Hellwig’s Reviewed-by tags, dropped by accident in the v5 rebase, are restored on all five patches. Shivaji Kant’s reviews remain on patches 3–5. There is no maintainer ack and no merge decision in this window.

Why the client DIO path had to change

Standard NFS page I/O still uses get_page() / put_page(). Memory taken from iov_iter_extract_pages() is different: it is GUP-pinned, and the pin is the reference. Mixing the two models is how the earlier revisions produced oopses, refcount underflows, and double-unpins.

The design in the cover letter is therefore pin-awareness inside struct nfs_page, not a one-off in direct.c:

  1. PG_PINNED records whether a request owns a pin or a normal page ref.
  2. wb_nr_pinned counts how many pins the primary request owns, so subrequests cannot unpin on the parent’s behalf.
  3. Unpin happens only when I/O is complete (unpin_user_page() / unpin_user_folio()), not immediately after request creation.

That last point is itself a bug fix in the existing DIO loop, independent of P2PDMA.

The five patches (client DIO core)

1/5 nfs: make nfs_page pin-aware — nfs_page_create_from_page() and nfs_page_create_from_folio() take a pinned bool and set PG_PINNED. If the page is pinned, the extra get_page() / folio_get() is skipped:

"If the page is pinned, we skip the existing reference increment (get_page/folio_get) as the pin itself acts as a reference."

nfs_clear_request() and nfs_direct_release_pages() then call unpin_user_page() / unpin_user_folio() instead of put_page() when the flag is set. Subrequests inherit the parent’s pinning status. This is the patch that grew to absorb the Sashiko double-unpin findings (see below). Reviewed-by: Christoph Hellwig.

2/5 nfs: track number of pinned pages in nfs_page — adds wb_nr_pinned and uses nfs_page_array_len() so only the primary request performs the final unpin:

"ensuring that only primary requests perform the final unpinning operation, preventing subrequests from incorrectly performing unpinning on behalf of their parent requests."

Without this, a split DIO request would drop pins while the parent I/O was still in flight. Reviewed-by: Christoph Hellwig.

3/5 nfs: introduce nfs_release_request_list helper — centralizes bulk nfs_page teardown, then converts nfs_read_sync_pgio_error() to it. The helper is framed as infrastructure for two follow-ups: consistent pin-aware cleanup, and later folio-sized unlock-in-bulk “similar to the pattern in bio_release_pages.” Reviewed-by: Shivaji Kant, Christoph Hellwig.

4/5 nfs: migrate direct I/O to iov_iter_extract_pages — the actual API switch, and the oldest DIO-loop bug fix still in the series:

"The migration fixes a bug in the Direct I/O loop where pages were being unpinned immediately after request creation. With the new extraction model, pins are held until the I/O is complete. Manual release in the loop is correspondingly updated to only clean up failed pages."

That “failed pages only” cleanup is also the natural place for a double-unpin: a page that became an nfs_page must not be unpinned again in the scheduling loop. Reviewed-by: Shivaji Kant, Christoph Hellwig.

5/5 nfs: introduce nfs_direct_extract_pages helper — folds extraction + request creation out of nfs_direct_read_schedule_iovec() and nfs_direct_write_schedule_iovec() so both paths share one helper. That helper is also the intended hook for a later folio-aggregation series (export an iov_iter.c helper, then pack hugepage-backed pages into one large request to cut RPC overhead). Reviewed-by: Shivaji Kant, Christoph Hellwig.

Net diff: 134 insertions, 83 deletions across fs/nfs/direct.c, pagelist.c, read.c, write.c, and include/linux/nfs_page.h.

Evolution: from P2PDMA RFC to a pin-correct v6

Bridge, briefly. The April RFC tried to enable PCI P2PDMA in one go; reviewers asked for the modernization to be split. v1/v2 still bundled folio conversion; Matthew Wilcox objected to treating every struct page as a folio (slab pages in particular), and Christoph Hellwig advised dropping the later parts to get the pin/extract work merged first. v3 became this five-patch shape. v4 collected Hellwig and Kant reviews and style cleanups.

The client bug-fix trail is what actually forced v5 and then v6:

  • v2: data corruption in nfs_direct_extract_pages() from wrong intra-page offsets; requested_bytes was incremented before the RPC was successfully scheduled.
  • v5: an iov_iter_revert oops in nfs_direct_extract_pages(), and a swap-over-NFS refcount underflow because nfs_direct_release_pages() called put_page() on unpinned memory.
  • v6 (this week): static analysis on Sashiko flagged double unpins in the pin-aware path. The v6 cover points at the v5 patchset on sashiko.dev; the code delta is concentrated in pagelist.c (patches 1–2) plus a few lines of failed-page cleanup in direct.c (patches 4–5).

The sibling v5 thread’s only in-week note is Shrivastava pointing here: v6 restores Hellwig’s tags and fixes those unpin bugs. This thread is the series itself.

Testing

xfstests -g quick was run before and after, on RDMA and TCP, NFSv3 / 4.0 / 4.1 / 4.2:

"The tests were run before & after applying the series. No regressions were observed."

The cover letter’s table is aimed at the v1 regressions: generic/091, 130, 139, 143, 154, 155, 198, 214, 240, 263, 450, 451, 586, 647, 708, 729, 760 all pass on every transport/version combo. Several tests (183, 188, 190, 196, 203, 287, 290, 292, 330) only run (and pass) on 4.2; generic/444 remains skipped everywhere. That is still the “quick” group, not a full xfstests run — a coverage question Hellwig raised on an earlier revision.

Roadmap (still out of this series)

Shrivastava is explicit:

"This series lays the necessary groundwork for the upcoming work."

  1. Folio migration for Direct I/O — export an iov_iter.c helper so nfs_direct_extract_pages() can aggregate pages into one large folio-based request.
  2. P2PDMA enablement — ITER_ALLOW_P2PDMA on the DIO path, plus transport-level discovery of P2P-capable RDMA/NVMe devices, built on PG_PINNED.

Conclusion

v6 is the pin-correct version of a client DIO refactor that reviewers have already walked through several times. The interesting NFS-client content this week is not a new design argument; it is that unpin lifetime is now treated as a first-class nfs_page property, after Sashiko showed v5 could still drop a pin twice. Hellwig’s reviews are back on the series. Until someone replies, the series is posted, tested on the quick matrix, and waiting.
