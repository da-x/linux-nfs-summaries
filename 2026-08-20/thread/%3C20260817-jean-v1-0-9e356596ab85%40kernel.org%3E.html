nfsd: slab overwrite in the NFSv4.1 session reply cache

Summary

This week Chuck Lever posted a two-patch nfsd series that closes a KASAN-confirmed slab overwrite in the NFSv4.1 session reply cache. The report is a server-side memory-safety bug, triggerable by a client that can establish a session; there is no Linux NFS client code change in the series, and as of 18 August it has drawn no review replies.

What landed on the list

On 18 August, Chuck Lever posted [PATCH 0/2] nfsd: fix a slab overwrite in the NFSv4.1 session reply cache. The cover letter credits Jérémy Jean with a private report and a KUnit fixture that reproduces the write under KASAN. The fixture is not included.

The trigger is a legal CREATE_SESSION negotiation followed by a cachethis SEQUENCE:

"A client that can establish a session can negotiate ca_maxresponsesize_cached down to NFSD_MIN_HDR_SEQ_SZ, which leaves every slot's sl_data[] zero bytes long, and then send a cachethis SEQUENCE whose COMPOUND tag fills the narrowed reply buffer. The SEQUENCE result is never encoded, cstate.data_offset stays zero, and the whole reply is copied past the end of the slot."

That is a protocol-legal client, not a parser smash. Once the cached-reply ceiling is at NFSD_MIN_HDR_SEQ_SZ, nfsd4_alloc_slot() hands every slot a zero-length sl_data[]. A long COMPOUND tag then fills the already-narrowed reply buffer so it holds the SEQUENCE opcode but not the status word that follows.

Why the copy is not clamped

Lever walks through why a one-line clamp in nfsd4_store_cache_entry() is the wrong fix. That helper derives the copy length from cstate.data_offset and never compares it with the slot allocation. Clamping would stop the write, but:

"the slot would then hold a truncated reply that a retry replays as a complete one, and the slot seqid has already been consumed by that point. RFC 8881 Section 2.10.6.1.2 requires an error returned from SEQUENCE to leave the slot untouched, so the size has to be settled before the slot is accepted."

The copy itself is therefore left alone. The new check runs ahead of xdr_restrict_buflen(), which only fails once headers and tag overrun the negotiated limit. Adding the fixed-size SEQUENCE result on top also rejects a request that leaves no room for the reply the client asked to have cached — a request that cannot produce a complete reply today either.

Patch 1: preflight SEQUENCE before accepting the slot

Patch 1, authored by Jean and signed off by Lever, is the actual fix. It sits in nfsd4_sequence() in fs/nfsd/nfs4state.c.

The failure chain is:

  1. nfsd4_sequence() narrows the reply buffer to the session's cached-reply limit before it accepts the slot seqid.
  2. A COMPOUND tag can fill that buffer until it holds the SEQUENCE opcode but not the following status word.
  3. nfsd4_encode_operation() returns without running nfsd4_encode_sequence(), so cstate.data_offset stays zero.
  4. op->status is left at nfs_ok, so the COMPOUND is treated as success.
  5. nfsd4_store_cache_entry() declines to cache a lone SEQUENCE that returned an error, but that test reads the (still-ok) status, so it proceeds.
  6. The copy starts at offset zero and dumps the whole reply — RPC and COMPOUND headers included — into the zero-length sl_data[].

The KASAN splat Jean's fixture produced:

BUG: KASAN: slab-out-of-bounds in read_bytes_from_xdr_buf+0x1bc/0x390
Write of size 80 at addr ffff888003a549cd by task kunit_try_catch/24
 __asan_memcpy+0x38/0x60
 read_bytes_from_xdr_buf+0x1bc/0x390
 nfsd4_sequence_done+0x5b0/0x810
 nfs4svc_encode_compoundres+0x1bf/0x240

The COMPOUND tag is among the bytes written past the slot, so a client that later retries can pick up most of the overflow.

The patch checks that the fixed-size SEQUENCE result, plus room for a following operation's error status, fits the negotiated limit before narrowing the buffer and consuming the slot seqid. The slot and its reply cache stay unchanged, matching RFC 8881 §2.10.6.1.2.

It carries Fixes: 47ee52986472 ("nfsd4: adjust buflen to session channel limit") — the commit that first taught nfsd to shrink the reply buffer to the session channel limit. An Assisted-by: Codex:gpt-5 tag is also present.

Patch 2: encode-header failure must set op->status

Patch 2 is Lever's follow-on guard in nfsd4_encode_operation() (fs/nfsd/nfs4xdr.c). When the reply buffer has no room for an operation's opcode and status word, the encoder currently leaves op->status untouched. nfsd4_proc_compound() then reads the leftover nfs_ok as success and continues, so the reply counts an operation whose result was never encoded.

The patch reports the failure through nfsd4_check_resp_size(), which the rest of the function already uses. That returns NFS4ERR_REP_TOO_BIG, or NFS4ERR_REP_TOO_BIG_TO_CACHE on a session, and the COMPOUND ends at that operation.

Lever is explicit that this is not the overwrite fix:

"Two paths narrow the reply buffer: nfsd4_sequence(), which rejects a SEQUENCE result that does not fit, and nfsd4_encode_splice_read(), which can leave a single XDR word in the head page. Whether a COMPOUND reaches that boundary is unproven, so this is a guard rather than a fix."

Together the two patches are 29 insertions across nfs4state.c and nfs4xdr.c. Base commit is 76427d869120552a1a82e1f1488d9f8311827d84.

Client angle and status

Nothing here changes the Linux NFS client. The interesting client-facing point is that the overwrite is reachable from a session-capable peer that merely negotiates a tiny ca_maxresponsesize_cached and then sends a cachethis SEQUENCE with a fat COMPOUND tag. A well-behaved Linux client will not do that in ordinary use; a malicious or fuzzer client will. The series therefore belongs with nfsd's session-slot and DRC hardening, not with client reconnect or I/O path work.

No Acked-by, Reviewed-by, or follow-up questions appeared in the window. The KUnit fixture remains private, so reviewers will have to reconstruct the reproducer from the KASAN trace and the SEQUENCE preflight logic.

Bottom line: this is a bug fix, not a feature or protocol change. Jean found a slab overwrite in the NFSv4.1 reply cache; Lever's series refuses the SEQUENCE before the slot is accepted rather than truncating a cached reply after the fact, and adds a related encode-status guard. Review is still open.
