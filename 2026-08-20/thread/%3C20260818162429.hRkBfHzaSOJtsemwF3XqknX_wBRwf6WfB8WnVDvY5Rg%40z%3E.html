NFSv4.1 GETDEVICEINFO notification bitmap OOB read

Summary

This week's linux-nfs traffic includes a security-minded bug fix for the NFSv4.1 pNFS client XDR decoder: an integer wrap in decode_getdeviceinfo() that lets a malicious server trigger a large out-of-bounds read while the client is decoding a GETDEVICEINFO notification bitmap.

The discussion is a one-message patch with no replies yet in the week ending 2026-08-20. There is no protocol change and no new feature; the submitter is tightening an existing decoder path that has been in the client since the original GETDEVICEINFO notification-info work.

The report

Chuyf26 (Alibaba) posted [PATCH] NFSv4.1: fix out-of-bounds read decoding GETDEVICEINFO notification bitmap against fs/nfs/nfs4xdr.c. The function currently feeds 4 * len into a single xdr_inline_decode() call, where len is the server-supplied word count of the notification bitmap. That multiplication can wrap:

"The multiplication can wrap around to a small value, so the bounds check only covers a few bytes while the following loop reads len words from the resulting pointer. A malicious NFS server can trigger a large out-of-bounds read in the client by replying to GETDEVICEINFO with a huge bitmap word count."

The attack surface is the pNFS layout-discovery path, not a rare ioctl. A client issues GETDEVICEINFO while discovering a layout; the reply is decoded by nfs4_xdr_dec_getdeviceinfo() → decode_getdeviceinfo(). After wrap, xdr_inline_decode() returns a pointer at the very end of the receive buffer, and the subsequent loop walks len words past it:

"With a wrapped 4 * len the pointer returned by xdr_inline_decode() sits at the very end of the receive buffer, and the loop then reads up to nearly a gigabyte of words past it."

The XDR receive buffer is assembled from pages rather than slab objects, so KASAN does not instrument the walk. Depending on what follows in memory, the decoder either consumes garbage notification bits or faults on unmapped pages:

"The XDR receive buffer is built from pages, not slab objects, so KASAN does not instrument these reads; depending on what follows in memory the loop either consumes garbage notification bits or walks into unmapped memory."

That combination — silent garbage on mapped pages, or a crash on unmapped ones — is exactly the kind of decoder bug that is easy to miss in ordinary testing and ugly when a hostile server is in the path.

The patch tags Fixes: 4e59080397fa ("NFSv4.1: Allow getdeviceinfo to return notification info back to caller"), so the hole dates to the original client support for returning GETDEVICEINFO notification info to the caller, not to a recent regression. It is Reported-by: Abaci <abaci@linux.alibaba.com> with Assisted-by: abaci:qwen3.8-max.

The proposed client fix

The change is small (14 lines in fs/nfs/nfs4xdr.c, 7 insertions / 7 deletions) and is a classic XDR-hardening pattern: stop multiplying a server-controlled length into one bulk xdr_inline_decode(), and decode the bitmap one word at a time so every read is independently bounds-checked.

"Decode the bitmap one word at a time so every read is bounds checked."

That is the right shape for this class of bug. A single xdr_inline_decode(4 * len) trusts that len cannot overflow a 32-bit byte count; walking word-by-word makes the XDR layer reject a truncated or oversized bitmap before the loop ever dereferences past the receive buffer. For NFS client development this is the preferred fix over merely saturating 4 * len: even a capped bulk decode still trusts the decoder loop to stay in sync with what was actually pulled from the stream.

No maintainer Acked-by, Reviewed-by, or merge comment landed in-window. The patch remains an unreviewed client-side XDR hardening candidate.

Why it matters for the NFS client

GETDEVICEINFO is on the pNFS hot path: layout drivers need device information before they can place I/O. A hostile or buggy NFSv4.1 server that answers GETDEVICEINFO with a huge notification-bitmap word count can:

  • force the client to read far past the XDR receive buffer (up to nearly a gigabyte of words, per the report);
  • inject garbage notification bits if the following pages happen to be mapped;
  • crash the client if they are not.

Because the receive buffer is page-backed, KASAN will not catch this in typical syzbot / KASAN client fuzzing. That is an important testing note for NFS client work: XDR OOB reads of this form need either targeted decoder fuzzing or explicit integer-overflow review of every xdr_inline_decode(n * 4) site that takes a server-controlled n.

The notification bitmap itself is how the server tells the client which device-notification events it will generate. Reading garbage bits here can mis-program pNFS notification state even if the walk never faults — a correctness bug as well as a crash bug.

That path has the same pattern: nlayouttypes * 4 into one xdr_inline_decode(), wrap, then a loop that reads past the buffer during FSINFO (mount / statfs). Status

Bug fix, NFS client, unreviewed. One message, no follow-up in the week of 2026-08-14 through 2026-08-20. The technical claim is clear and the proposed remedy (word-at-a-time xdr_inline_decode() of the notification bitmap) matches established NFS XDR practice. What is still missing is maintainer review, a decision on stable backport (the Fixes: tag points at a long-lived commit), and confirmation that no other 4 * len bulk-decode sites in nfs4xdr.c share the same wrap.
