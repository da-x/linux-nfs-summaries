lockd: UAF in nlmsvc_retry_blocked during nfsd unmount

Summary

Chuck Lever posted a two-line lockd bug-fix for a KASAN slab use-after-free in nlmsvc_retry_blocked(). The race is between the lockd kthread retrying a blocked NLM grant and nfsd teardown walking the same block list. No one replied on this v1 thread in-window; Lever followed up the next day with a separate v2 after automated review found that the extra reference itself requeues a retired block.

This is a lockd server (nlmsvc) memory-safety bug fix, not a protocol change and not a new feature. It is tagged Fixes: 0e4ac9d93515 (lockd: handle fl_grant callbacks). The NLM service is the server half of NFS file locking: an NFS client’s flock/fcntl request lands here, so a UAF on the grant-retry path is a hard lockd crash under ordinary client lock traffic plus nfsd unmount.

The race

Lever states the lifetime hole directly:

"nlmsvc_retry_blocked() examines the block at the head of nlm_blocked under nlm_blocked_lock, then releases the lock before calling nlmsvc_grant_blocked() or retry_deferred_block(). It holds no reference of its own across that window, so the nlm_blocked list reference is all that keeps the block alive."

Unmount of the nfsd filesystem while a lock request is still blocked reaches nlmsvc_traverse_blocks(), which drops that list reference. The grant path does take a reference, but too late:

"nlmsvc_grant_blocked() does take a reference, but only after nlm_blocked_lock has been dropped, so the block and the nlm_rqst hanging off it can be freed before it runs."

The KASAN report that Shuangpeng Bai filed the day before matches that story exactly. The lockd kthread reads a freed nlm_rqst in nlm_async_call():

BUG: KASAN: slab-use-after-free in nlm_async_call+0xd6/0x230
Read of size 8 at addr ffff88811b04c808 by task lockd/8377
  nlm_async_call+0xd6/0x230
  nlmsvc_retry_blocked+0x61c/0x800
  lockd+0x144/0x1c0
Freed by task 8392:
  nlmsvc_release_block+0x231/0x290
  nlmsvc_traverse_blocks+0x139/0x1b0
  nlm_traverse_files+0x1aa/0xa00
  nlmsvc_free_host_resources+0x12/0x60
  nlm_shutdown_hosts_net+0x127/0x280
  lockd_down+0xd5/0x1c0

Bai hit it on 3aa1dcaa4f6f (13 August) while testing current upstream, with a gist of reproducer and .config. The free path is nfsd unmount (nfsd_umount → lockd_down → nlm_shutdown_hosts_net), so the trigger is “NFS client lock still blocked, then the server filesystem is torn down.”

The blamed commit, 0e4ac9d93515 (lockd: handle fl_grant callbacks), is the conversion that taught lockd to retry blocked grants via fl_grant. That is when nlmsvc_retry_blocked() started dropping nlm_blocked_lock and calling nlmsvc_grant_blocked() without pinning the block across the window.

The v1 fix

Two insertions in fs/lockd/svclock.c: take a reference on the head block before releasing nlm_blocked_lock, and drop it once the retry has run.

"Take a reference before releasing nlm_blocked_lock and drop it once the retry has run. retry_deferred_block() borrows its caller's reference as well, so this covers both arms of the loop."

That is the classic lockd lifetime pattern (nlmsvc_get_block / nlmsvc_release_block) applied to a path that had been living on the list’s implied ref. Both the grant arm and the deferred-retry arm are covered because the deferred helper does not take its own reference.

No review, ack, or nack landed on this v1 posting. The patch is otherwise a textbook UAF close: pin the object for the unlocked call, then put it.

Why it matters for NFS clients

This is server-side lockd (nlmsvc_* in fs/lockd/svclock.c), not the NFS client’s fs/nfs/ NLM caller. The user-visible effect is still on the client: NLM blocking locks (LOCK with block=true, BSD flock, POSIX F_SETLKW) wait on this retry loop. If nfsd is unmounted — container stop, nfsd thread shutdown, network-namespace teardown — while a client still has a blocked lock, lockd can UAF in nlm_async_call and take the lockd kthread with it. Remaining NLM clients then lose GRANT callbacks and blocking-lock service.

The allocation side of Bai’s KASAN report is the client-facing lock path: nlm_alloc_call ← nlmsvc_lock ← nlm4svc_do_lock ← nlmsvc_dispatch. A blocked NFSv3/NLM lock from a client is exactly the object being freed out from under the retry.

Same-week follow-up (v2, separate thread)

The next day Lever posted PATCH v2 as a new thread, citing sashiko-bot on this v1. Holding the extra reference exposes a second teardown bug:

"Holding that reference exposes a second problem. Both arms of the retry end in nlmsvc_insert_block(), which queues any block it finds unlisted, while nlmsvc_traverse_blocks() skips blocks that are already unlisted. A block unlinked during the window therefore returns to nlm_blocked after the teardown scan has passed it by."

The resurrected block pins its file and host, so the host is never reaped, lockd warns that it could not shut down the host module, and the host outlives the network namespace that host->net points at. v2 keeps the get/put from v1 and adds a B_DEAD flag: mark a block dead before unlinking it on permanent retirement, and have nlmsvc_insert_block_locked() ignore a dead block. nlmsvc_grant_blocked() still calls nlmsvc_unlink_block() directly because unlink-and-requeue is a normal part of a grant attempt.

That second issue is why v1 should not be merged as-is. Reviewers of this thread should look at v2.

Final conclusions (as of 20 August)

  • Classification: lockd/NLM server use-after-free fix on the blocked-grant retry path. Regression from 0e4ac9d93515 (lockd: handle fl_grant callbacks). Not a protocol change.
  • Technical claim: nlmsvc_retry_blocked() drops nlm_blocked_lock with only the list reference holding the block; nfsd unmount’s nlmsvc_traverse_blocks() can free the block and its nlm_rqst before nlmsvc_grant_blocked() / retry_deferred_block() run. KASAN hits in nlm_async_call.
  • v1 repair: get the block before dropping the lock, put it after the retry. Two lines in svclock.c.
  • Disposition: posted 19 August, no human review on v1. Superseded in-week by v2 (20 August), which keeps the pin and adds B_DEAD so a retry cannot requeue a block that teardown already retired. Do not queue v1.
  • Client impact: blocking NLM locks from NFS clients plus nfsd unmount / netns teardown. The crash is in the lockd kthread, so GRANT callbacks and further blocking-lock service die with it.
