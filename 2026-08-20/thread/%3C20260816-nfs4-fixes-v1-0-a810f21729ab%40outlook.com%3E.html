Three independent pNFS client bug fixes: LAYOUTSTATS overflow, DS cache aliasing, lseg leak

Summary

This week Junrui Luo posted a three-patch NFSv4/pNFS client series targeting three independent bugs in paths that consume server-chosen data. There were no replies in the window; the series landed as a v1 drop on 16 August and still awaits review.

Series overview

Luo's cover letter frames the work as three standalone client fixes rather than a protocol change or a new feature:

"Three independent pNFS client fixes, all in paths that consume data the server gets to choose. They touch different files and can be applied in any order."

The three problems are LAYOUTSTATS send-buffer exhaustion (flexfiles), data-server cache aliasing across NFS versions, and a layout-segment leak on the pnfs_layout_process() forget path. All three patches carry Fixes: tags, Cc: stable@vger.kernel.org, a Reported-by: Yuhao Jiang, and an Assisted-by: Claude:claude-opus-5 credit. Base commit is f5bbbfec59b4.

Patch 1: LAYOUTSTATS send buffer exhaustion

Patch 1 is a one-line NFSv4.2 client bug fix in include/linux/nfs_xdr.h: raise PNFS_LAYOUTSTATS_MAXSIZE from 256 to 384.

Luo's analysis is that encode_layoutstats_maxsz budgets XDR_QUADLEN(PNFS_LAYOUTSTATS_MAXSIZE) — 256 bytes — for the layoutupdate4 body written by the layout driver, but a flexfiles record can exceed that. ff_layout_encode_ff_layoutupdate() emits, per data server, a netaddr4, an nfs_fh4, two ff_io_latency4, an nfstime4 and a bool. A data-server filehandle of NFS_MAXFHSIZE already accounts for 132 of those bytes; the two latency records (64 bytes each), the timestamp and the bool add another 144, so the body passes 256 bytes before the netaddr4 is encoded. encode_layoutstats() additionally writes the deviceid4 and the layoutupdate4 lou_type word, neither of which the macro accounts for.

The practical failure mode is worse than a truncated RPC. Both the filehandle and the address are server-chosen via LAYOUTGET and GETDEVICEINFO, so a server can drive the encoder past the end of the send buffer. Once that happens xdr_reserve_space() returns NULL, and the two ff_layout_encode_io_latency() calls run with dss_info->mirror->lock held:

"a NULL return there leaves the lock permanently held."

The proposed fix is simply to enlarge the reservation so the record fits. The patch fixes 27c430644369 ("pnfs/flexfiles: encode LAYOUTSTATS flexfiles specific data").

Patch 2: data-server cache keyed only on address

Patch 2 is the more invasive of the three client changes. It keys the per-net pNFS data-server cache on NFS version as well as the multipath address set, touching nfs4_pnfs_ds_add(), struct nfs4_pnfs_ds / pnfs.h, and both the files and flexfiles layout device helpers.

Today nfs4_pnfs_ds_add() matches on the multipath address set alone, and struct nfs4_pnfs_ds records no version. That is enough for the files layout driver, which always connects with version 4. Flexfiles, however, takes its version tuple from GETDEVICEINFO per device, and one address can legitimately serve both NFSv3 and NFSv4. Two deviceids on one address with different ds_versions[0].version therefore share a single nfs4_pnfs_ds, and whichever mirror connects first pins ds_clp to its own version. The other mirror is then handed that client anyway, so it selects rpc_call_ops for a version the connection does not speak:

"the mismatched sequence-slot handling dereferences NULL."

Luo's fix adds the version to the cache key so the two cannot alias, giving each version its own nfs4_pnfs_ds and connection while both mirrors stay usable. Only the major version is compared, because that is what selects rpc_call_ops and rpc_ops; v4.0 and v4.1 keep sharing a client. The files layout driver passes the 4 it already hardcodes at connect time.

The patch fixes d67ae825a59d ("pnfs/flexfiles: Add the FlexFile Layout Driver") — a long-standing flexfiles client defect rather than a recent regression.

Patch 3: layout segment leak on the forget path

Patch 3 restores a one-line drain that was lost in a later simplification of pnfs_layout_process().

When the server returns a new layout stateid while a valid one is still held, pnfs_layout_process() calls pnfs_mark_matching_lsegs_return() on the on-stack free_me list and jumps to out_forget. Segments whose reference count drops to zero are unlinked from lo->plh_segs and moved to free_me by mark_lseg_invalid(); for an idle cached segment the layout header holds the only reference, so this happens on the first decrement. The success path calls pnfs_free_lseg_list(), but out_forget never drains free_me.

Luo reconstructs the regression as a three-commit sequence: 814b84971388 added the drain; 08bd8dbe8882 removed it while switching the destination to lo->plh_return_segs (which is drained elsewhere); fb700ef02676 ("NFSv4.1: Simplify layout return in pnfs_layout_process()") switched the destination back to free_me without restoring the drain. The patch restores the pnfs_free_lseg_list() call and is tagged Fixes: fb700ef02676.

Status this week

This is a bug-fix series, not a protocol change. All three patches are NFS client / pNFS (flexfiles and files layout) work; two of them (LAYOUTSTATS overflow and DS cache aliasing) are specifically about flexfiles consuming server-chosen device and filehandle data, and the third is a layout-header lifetime leak on NFSv4.1 layout-stateid replacement.

No reviewer, maintainer, or tester replied in the week ending 20 August. The series remains unacked, with stable CCs already in place and no follow-up revisions. The outstanding questions for review are whether 384 bytes is a durable LAYOUTSTATS budget (versus computing the reservation from the actual record), whether major-version-only DS cache keys are sufficient for mixed v4.0/v4.1 flexfiles devices, and whether restoring pnfs_free_lseg_list() on out_forget is complete relative to the plh_return_segs path that replaced it in 08bd8dbe8882.
