nfsd drops patch 18/18 after DELEG8 hang: OPEN no longer returns NFS4ERR_DELAY

Summary

nfsd drops patch 18/18 after DELEG8 hang: OPEN no longer returns NFS4ERR_DELAY

Type: Regression / important bug fix in a previously merged nfsd refactor (not a protocol change, not an NFS client code change). The visible failure is on the server, but it directly breaks the NFSv4 client OPEN/delegation retry path.

This week's headline

Two mails on 17 August close the open question hanging over NeilBrown's v5 nfs4_create_file() series: patch 18/18 must come out of nfsd-testing, the rest of the series can stay, and the real fix is not a one-liner.

nfsd maintainer Chuck Lever pressed for a decision after five days of silence on Jeff Layton's pynfs DELEG8 failure:

"Neil, I need a response from you. How soon do you intend to address this issue? Can this patch be dropped safely from the series, or do I need to drop the whole series?"

NeilBrown answered the same evening. He owns the bug, isolates it to that last patch, and tells Chuck the rest of the series is clean:

"I can see the problem. To fix it we need to somehow get logic similar to nfsd_open_break_lease() into the vfs_lookup_open() path. I think that'll be possible though not trivial."

"It is safe to drop just that patch for now. I don't need it for the locking work that I am doing. I think it is still good to have and I will try to rehabilitate it, but not in a hurry."

"I'm confident the rest of the series is not implicated in this problem so there is no need to drop the whole series."

That is the week's conclusion: drop 18/18, keep 01–17, defer the vfs_lookup_open() unification until lease-break can be taught to that path.

Bridging prior weeks (briefly)

On 17 July NeilBrown posted v5 of the 18-patch series that untangles nfs4_create_file() toward a shared vfs_lookup_open() VFS API. Jeff Layton Reviewed-by'd it the same day; Chuck applied all 18 commits to nfsd-testing (patch 18 as 71349ee933ed). The series also carried two real correctness fixes (exclusive v4.1 create attributes, mounted-on-file CREATE handles). See the week-ending 23 July summary.

The last patch — v5 18/18, "nfsd: use do_lookup_open() for non-creating open requests too" — is the one that now has to come out. It reroutes non-creating NFSv4 OPENs through the new do_lookup_open() helper so they share code with the create path and, eventually, with syscall open(). That is exactly where lease-break fell off.

On 12 August (just outside this window) Jeff Layton reported the regression against that patch:

"This patch is making the pynfs DELEG8 test fail. It seems like this patch breaks the behavior where the server sends back NFS4ERR_DELAY on an OPEN while waiting for a DELEGRETURN. The server just doesn't send a reply until the delegation times out with it."

This week's two messages are Chuck's follow-up and Neil's answer to that report.

The technical argument

DELEG8 is the pynfs case that checks NFSv4 OPEN-versus-delegation interaction: a client holds a delegation; another OPEN arrives; the server must recall the delegation and, while it waits for DELEGRETURN, reply NFS4ERR_DELAY so the opener retries rather than blocking the nfsd thread (and the client RPC) until the recall times out.

Historically that "don't sleep on the lease, return DELAY" behaviour lives in nfsd_open_break_lease(), which the old non-creating OPEN path invoked. Patch 18/18 stopped using nfsd_lookup() for the non-create path and opened via do_lookup_open() instead. That helper is modelled on the VFS open path — which does want to break leases by waiting — so the nfsd-specific DELAY policy never runs. The server thread sits on the lease until the delegation expires; pynfs sees a hang, not NFS4ERR_DELAY.

Neil's diagnosis this week is precise about where the missing logic has to go. The series' stated endgame is a VFS vfs_lookup_open() that nfsd and syscall open() would share; stuffing nfsd's DELAY policy into that shared helper is "possible though not trivial." Until that exists, the safe move is to revert only the non-creating-OPEN unification.

He also separates this from the locking work that motivated the series:

"I don't need it for the locking work that I am doing."

Patches 01–17 (the nfs4_create_file() refactor, the exclusive-create attribute fix, the mounted-on-file CREATE fix, and the do_lookup_open() extract for creating opens) are not implicated. Chuck's "drop the whole series?" option is declined.

Why this matters for NFS client development

No NFS client patches landed in this thread, but the regression is a client-visible OPEN/delegation bug:

  • A Linux NFS client that opens a delegated file expects NFS4ERR_DELAY and retries; instead the OPEN RPC sits unanswered until the recall timeout. That looks like a stuck mount, a hung open(2), or a lease-timeout storm rather than a clean retry.
  • pynfs DELEG8 is the interoperability canary for that contract. A server that fails it will misbehave against any NFSv4 client (Linux, or otherwise) that relies on DELAY during recall.
  • The intended vfs_lookup_open() sharing would put nfsd on the same open path the client already uses locally. Until nfsd_open_break_lease()-equivalent policy is expressed in that VFS path, unifying the two is unsafe for NFSv4 delegations.

So the client-side takeaway is: do not assume nfsd-testing still has non-creating OPENs going through do_lookup_open(); the DELAY-on-recall contract is restored by dropping 18/18, and the shared-VFS-open work is parked.

Final conclusions (as of 20 August)

  • Classification: important nfsd bug fix / regression revert, not a new feature and not a protocol change.
  • What broke: non-creating NFSv4 OPEN no longer returns NFS4ERR_DELAY while a delegation recall is in flight; the server (and therefore the client OPEN) waits until the delegation times out. Caught by pynfs DELEG8.
  • Root cause: patch 18/18 moved non-creating OPEN onto do_lookup_open() / the future vfs_lookup_open() path, which does not contain nfsd_open_break_lease().
  • Disposition: drop 18/18 only; patches 01–17 stay; Neil will try to put lease-break into the VFS lookup-open path later, without blocking his locking work.
  • NFS client impact: no client code change this week, but the server-side DELAY contract that Linux NFS clients depend on for OPEN-during-recall is the thing being restored.
