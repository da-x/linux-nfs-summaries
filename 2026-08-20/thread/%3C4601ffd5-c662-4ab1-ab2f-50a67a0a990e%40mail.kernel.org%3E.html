syzbot AI patch for nfsd_nl_listener_set_doit hang — maintainers already have a better diagnosis

Summary

On Thursday, 20 August, syzbot posted an AI-generated patch from Slawomir Stepien titled [PATCH] nfsd: prevent hung task in nfsd_nl_listener_set_doit(). Hours later Jeff Layton declined the diagnosis, pointed at his already-posted hardening series, and restated the real stall: synchronous rpcbind registration under nfsd_mutex, not request_module().

This is a bug-fix / hardening discussion, not a protocol change and not a new feature. The hang lives in the NFS server generic-netlink control plane (nfsd_nl_listener_set_doit() in fs/nfsd/nfsctl.c), but it is the same lock that serializes every nfsd admin op — including the ones that bring listeners up for clients. The thread is new this week; it is the syzbot-AI follow-up to the July hung-task reports and to Layton’s in-flight nfsd-nl-hang v2 series.

The proposed patch

syzbot’s cover letter (signed off by Stepien, Assisted-by: Gemini:gemini-3.6-flash Gemini:gemini-3.1-pro-preview syzbot) describes an unbounded loop over NFSD_A_SERVER_SOCK_ADDR attributes in nfsd_nl_listener_set_doit(). For each attribute the kernel calls svc_xprt_create_from_sa(), which “may synchronously invoke request_module() to load the corresponding transport module.” A large batch of invalid transport names, the letter argues, turns that into a long sequential module-load storm while holding the global nfsd_mutex, so a concurrent nfsd_nl_version_get_doit trips the hung-task watchdog:

"If a user provides a large number of invalid transport names, request_module() is called sequentially for each, taking a massive amount of time. Since this entire process occurs while holding the global nfsd_mutex, it blocks other tasks attempting to acquire the mutex and triggers a hung task timeout."

The dump matches the July reports: the waiter is another nfsd netlink doit (nfsd_nl_version_get_doit at nfsctl.c:1889); the holder is nfsd_nl_listener_set_doit at nfsctl.c:1964, with cb_lock and nfsd_mutex taken. The letter also notes two extra defects: the loop does not break when svc_xprt_create_from_sa() fails, and svc_find_listener() walks serv->sv_permsocks per attribute, giving O(N²) cost.

The proposed fix is small and defensive:

  • A hard cap of 128 NFSD_A_SERVER_SOCK_ADDR attributes per netlink message, enforced before taking nfsd_mutex.
  • Break the loop on the first listener-creation failure, so invalid configs do not keep calling request_module().

Fixes: 16a471177496 ("NFSD: add listener-{set,get} netlink command"). The patch is tagged as an AI-generated syzbot submission; the signer is expected to take review comments.

Layton: the LLM got the wrong slow path

Layton replied the same morning. He had already run an LLM over the same dump and it produced the same request_module() story — and he says that story is wrong:

"My LLM latched onto the same explanation, but the request module upcalls are actually quite quick and have some other gates on them that make this problem hard to hit in practice."

The stall that actually trips the watchdog is rpcbind registration, which can sit in a local rpc_ping for tens of seconds per listener when rpcbind is down or slow. That is the diagnosis he and Neil Brown reached in July on the nfsd_nl_cache_flush_doit hang, and it is what his v2 series is already hardening around (transport-name validation before the mutex, a 1024-entry cap, a 1s local rpcbind timeout, first-error preservation, extack). The durable fix is still larger:

"The real problem is rpcbind registration, which can be quite slow. The fix for that is to make the registration asynchronous, and to not trigger errors on rpcbind registration failure. That's a bigger project, but let us know if you're interested!"

He then pointed Stepien/syzbot at the series that already contains “a similar fix to this one, along with some others”:

"In any case, I've sent a series that includes a similar fix to this one, along with some others: https://lore.kernel.org/linux-nfs/20260811-nfsd-nl-hang-v2-0-c0c92b3953c3@kernel.org/"

"I'll try to get the follow-on series out later today or tomorrow."

The message trails off mid-sentence (“I have a patch series in progress for this already, which also”) — likely a leftover from an earlier draft — but the intent is clear: do not take the 128-cap / break-on-error AI patch as the merge candidate. A cap is useful (Layton’s own series uses 1024, not 128), and breaking on first create failure is reasonable hygiene, but they do not address the slow path that actually holds nfsd_mutex.

How this sits next to the in-flight hang series

Earlier this week, on the overlapping nfsd-nl-hang v2 thread, Chuck Lever accepted Layton’s policy that rpcbind registration failure becomes non-fatal for NFSv2/v3, patch 4/8 (partial rpcbind unwind) is dropped, and v3 will re-roll around that plus a netns leak fix in the new selftests. That series is the real vehicle for the cap, the pre-mutex transport-name check, the 1s rpcbind timeout, and richer netlink extack. The durable work Layton flags here — asynchronous rpcbind so it no longer runs under nfsd_mutex — remains a follow-on, which he now says he hopes to post within a day.

syzbot’s 128-entry cap is therefore both redundant with and stricter than patch 2 of that series (1024). The “break on first svc_xprt_create_from_sa() failure” change is not the same as the series’ “keep the first svc_register() error” work: one stops creating more sockets after a bind/module failure; the other is about rpcbind SET failing after some programs have already registered. Layton’s “similar fix” remark almost certainly refers to the cap / pre-mutex validation, not to the AI patch’s request_module() theory.

NFS client relevance

No NFS client code is patched here, but the hang is client-visible in two ways:

  1. Control-plane stall. While listener_set holds nfsd_mutex, every other nfsd netlink and /proc/fs/nfsd write blocks — versions, threads, exports, cache flush. New clients cannot get a listener, and admin ops that clients depend on for mount (export refresh, thread count) sit in D state until the hung-task watchdog fires.
  2. rpcbind is how NFSv2/v3 clients find the server. The slow path Layton names is the kernel registering [program, version, proto, port] with local rpcbind on behalf of those clients. Making that registration asynchronous and non-fatal (the follow-on he is promising) means a v2/v3 listener can come up even when rpcbind is down; clients then fail at mount/getport until the admin notices the printk/extack, rather than the whole nfsd control plane hanging.

NFSv4 clients, which do not use rpcbind, still suffer the first failure mode: a wedged nfsd_mutex delays listener bring-up and any netlink-driven export or thread change.

Status

  • Type: server-side hung-task / DoS hardening around nfsd_nl_listener_set_doit().
  • This week’s outcome: the AI patch is not accepted as-is. Layton rejects the request_module() root cause, confirms a cap is already in his v2 series, and points the authors at that series plus a follow-on for async, non-fatal rpcbind.
  • No Fixes: applied, no Acked-by, no v2 of the syzbot patch. The merge path remains Layton’s nfsd-nl-hang series (v3 pending from the parallel thread) and the async-rpcbind follow-on he said he would try to post later the same day or the next.
