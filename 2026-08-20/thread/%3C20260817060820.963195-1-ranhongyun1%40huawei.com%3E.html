lockd client NULL deref on lockowner allocation failure

Summary

This week’s linux-nfs traffic included a focused NFS client / lockd (NLM) bug-fix from Ran Hongyun, targeting a NULL pointer crash on the NLM client lock-release path after a lockowner allocation failure. The discussion is not a protocol change and does not introduce a new feature; it is a follow-up correctness fix for the NLM client’s file-lock private-state setup, plus a review that immediately widened the scope to a related reference leak.

The crash: fl_ops set, owner still NULL

Ran Hongyun posted a one-line patch against fs/lockd/clntproc.c titled [PATCH] lockd: fix NULL pointer dereference in nlmclnt_locks_release_private. The failure mode is specific to the NFS client NLM path: nlmclnt_locks_init_private() always installs fl->fl_ops even when nlmclnt_find_lockowner() returns NULL (allocation failure). nlmclnt_proc() then notices the missing owner and returns an error, but it leaves fl_ops populated. The VFS later tears the lock down through locks_release_private(), which treats a non-NULL fl_ops as a signal to call fl_release_private. That lands in nlmclnt_locks_release_private(), which dereferences fl->fl_u.nfs_fl.owner and crashes.

Ran spelled the call chain out explicitly:

"nlmclnt_locks_init_private() unconditionally sets fl->fl_ops even when nlmclnt_find_lockowner() returns NULL due to allocation failure. When locks_release_private() later sees a non-NULL fl_ops, it calls fl_release_private, which dereferences fl->fl_u.nfs_fl.owner."

The proposed fix is deliberately small: in nlmclnt_proc(), if the owner is still NULL after nlmclnt_locks_init_private(), clear fl->fl_ops so locks_release_private() skips the NLM private-release callback. The patch is tagged:

"Fixes: bf8848918d75 ("lockd: handle lockowner allocation failure in nlmclnt_proc()")"

That Fixes tag is important for client maintainers. The earlier commit already tried to handle lockowner allocation failure in nlmclnt_proc(), but it only checked the owner pointer and returned -ENOMEM; it did not unwind the fl_ops assignment that nlmclnt_locks_init_private() had already made. Ran’s patch is therefore a residual hole in that error path rather than a brand-new class of bug.

Review: the one-liner is right, the structure is not

Jeff Layton replied the same day. He accepted the diagnosis and the functional effect of the one-line fl_ops clear, but he objected to leaving the init/cleanup split as-is:

"The fix looks correct, but I don't like the way that the initialization and cleanup is spread across multiple functions. I think it would be better to just get rid of nlmclnt_locks_init_private() altogether and open code what it does in the single caller (nlmclnt_proc()). Then you could just not initialize fl_ops if nlmclnt_find_lockowner() fails."

That is a client-side maintainability argument as much as a correctness one. nlmclnt_locks_init_private() has a single caller. Setting fl_ops inside the helper and then trying to undo it in nlmclnt_proc() is exactly how the original hole appeared: the helper always “succeeds” at installing ops, and the caller only half-handles the allocation failure. Inlining the helper would make the success path (owner allocated → install ops) and the failure path (no owner → leave fl_ops alone) live in one place.

Jeff also flagged a second, preexisting client bug on the same failure path:

"There's also another preexisting bug here. If the lockowner allocation fails, this function also leaks the references taken in nlmclnt_alloc_call()."

In other words, by the time nlmclnt_find_lockowner() fails, nlmclnt_proc() has already allocated an NLM RPC call structure and taken the associated references. Returning -ENOMEM without dropping those refs leaks the nlm_rqst (and whatever host/client state it holds). That leak is independent of the NULL deref: even a process that somehow survived the fl_ops crash would still leak on the allocation-failure path.

He closed by asking Ran to expand the work rather than land the one-liner as-is:

"Want to spin up a v2 that fixes all of this?"

Where the week left it

This thread itself contains only the original patch and Jeff’s review. There is no Acked-by, no merge decision, and no v2 posted as a reply here. The week’s conclusion is therefore a review-driven rewrite request, not a merged fix:

  • The NULL dereference in nlmclnt_locks_release_private() is agreed to be real and the proposed fl_ops clear is agreed to be functionally correct.
  • The preferred client-side fix is to delete nlmclnt_locks_init_private() and open-code it in nlmclnt_proc(), installing NLM lock ops only after a successful nlmclnt_find_lockowner().
  • The same error path must also drop the references taken by nlmclnt_alloc_call(), which the v1 patch does not address.

A separate two-patch series addressing both issues was posted later in the week; that follow-up lives in its own thread and is outside the scope of this exchange. For this thread, the client-side takeaway is that lockowner allocation failure in nlmclnt_proc() is still incompletely unwound: ops are installed too early, the VFS release path assumes a valid nfs_fl.owner, and the NLM call allocation is not released on the -ENOMEM path. Jeff’s requested v2 is the intended vehicle for closing both holes together.
