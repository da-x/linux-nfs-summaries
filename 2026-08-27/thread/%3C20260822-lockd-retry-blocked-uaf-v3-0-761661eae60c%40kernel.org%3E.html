Chuck Lever splits lockd retry-loop UAF and host-leak races after B_DEAD backfires

Summary

This is a bug-fix series, not a protocol change and not NFS client work. The defects live in lockd’s NLM server retry loop (nlmsvc_retry_blocked() in fs/lockd/svclock.c): unmounting nfsd while a lock is still blocked can either free a block the retry is still using, or let a retry re-queue a block the teardown scan already skipped, pinning an NLM host past namespace destruction. Chuck Lever posted v3 this week after two earlier attempts (v1 on 19 Aug, v2 on 20 Aug) and Jeff Layton reviewed the cover letter the next day.

The client-visible fallout is still real even though the code is nlmsvc_*: a KASAN UAF in nlm_async_call() on the lockd kthread, plus a host that outlives its netns so lockd cannot unload. There is no NLM wire-protocol change.

Brief recap from last week

Shuangpeng Bai reported a KASAN slab-use-after-free in nlm_async_call() on 19 Aug, with a delayed reproducer. The lockd kthread was still walking a block that nlmsvc_traverse_blocks() had already released during lockd_down() / nfsd unmount. Lever’s v1 took an extra block reference across the lock-drop window. sashiko-bot then flagged a second race: holding that reference lets a retry re-insert a block the teardown scan skipped because it was off nlm_blocked. v2 tried to paper over that with a B_DEAD flag so nlmsvc_insert_block() would refuse a retired block. That is the state this week’s v3 walks back.

Why v3 exists: B_DEAD frees a live lock

Lever’s cover letter is unusually blunt about the v2 misfire. Both races live in the same unlocked window:

"nlmsvc_retry_blocked() is the only path that operates on a block with nlm_blocked_lock dropped. Both defects live in that window. Shuangpeng Bai's KASAN report catches one of them, a block freed while the retry is still using it. sashiko-bot flagged the other while reviewing v1. The retry re-queues a block that the teardown scan has already retired, so the host that block pins is never reaped."

v2’s B_DEAD looked like a clean “do not requeue a dead block” gate. It is not:

"v2 added a B_DEAD flag that makes nlmsvc_insert_block() refuse to queue a retired block. That appeared to repair the second race, but it doesn't work. Every caller relies on that insert to take the list reference, so a refused insert lets nlmsvc_grant_blocked() drop the last reference to a block whose file_lock the VFS still has queued on a blocker."

That is the important lockd invariant: nlmsvc_insert_block() is not just a list splice. It is how a grant attempt takes the list reference that keeps the nlm_block (and the VFS file_lock still sitting on a blocker) alive. Refusing the insert under B_DEAD turns a host leak into a use-after-free of a live lock. v3 therefore drops B_DEAD entirely.

The series is also split on purpose. Patch 1 is the extra block reference alone and “applies without patch 2, so it can be backported on its own.” Patch 2 “is meant for mainline only. The race it closes leaks a host, and closing it widens the f_mutex hold across the retry loop.”

Patch 1: keep the block alive across the lock-drop window

Patch 1 is a two-line change in nlmsvc_retry_blocked(). The function peeks at the head of nlm_blocked under nlm_blocked_lock, then drops that lock before calling nlmsvc_grant_blocked() or retry_deferred_block(). Until this patch, the list membership was the only reference keeping the block (and the nlm_rqst hanging off it) alive. nlmsvc_grant_blocked() does take its own reference, but only after the lock is gone. Concurrent nfsd unmount walks nlmsvc_traverse_blocks() → nlmsvc_release_block() and frees the object under the retry’s feet.

The KASAN trace Lever quotes is Bai’s original report:

"BUG: KASAN: slab-use-after-free in nlm_async_call+0xd6/0x230 Read of size 8 at addr ffff88811b04c808 by task lockd/8377 nlm_async_call+0xd6/0x230 nlmsvc_retry_blocked+0x61c/0x800 lockd+0x144/0x1c0 Freed by task 8392: nlmsvc_release_block+0x231/0x290 nlmsvc_traverse_blocks+0x139/0x1b0 ... lockd_down+0xd5/0x1c0"

The fix is the obvious one: nlmsvc_get_block() before dropping nlm_blocked_lock, nlmsvc_release_block() after the retry returns. Fixes: 0e4ac9d93515 ("lockd: handle fl_grant callbacks") — the fl_grant work that first made this retry loop drop the list lock. Reported-by Bai, Closes his KASAN thread.

Patch 2: serialize retry against traverse with f_mutex

Patch 2 attacks the host leak that B_DEAD failed to close. nlmsvc_grant_blocked() unlinks the block from nlm_blocked for the duration of a lock retry, then re-inserts it. nlmsvc_traverse_blocks() skips anything not currently on that list. Interleave those two and the scan walks past a block that the retry then puts back. The resurrected block pins its host; lockd warns that it could not shut down the host module, and the host outlives host->net.

v3’s answer is mutex ordering, not a new flag:

"Hold the file's f_mutex across the retry, and extend the scan's hold across its unlink, so a scan and a retry of the same file can no longer interleave. Drop the mutex before releasing a block reference, since the last put takes f_mutex. A retry that waited out a scan re-checks under nlm_blocked_lock that its block is still queued and due."

Two details matter for anyone backporting or reviewing lockd locking:

  • The last nlmsvc_release_block() already takes f_mutex. Holding f_mutex across that put would deadlock, so the retry drops the mutex first.
  • After waiting out a scan, the retry cannot assume the block is still the one it picked. It re-checks under nlm_blocked_lock that the block is still queued and due before calling the grant/deferred helpers.

Reported-by sashiko-bot, Closes the v1 sashiko review. This is the mainline-only half: a leak, not a UAF, and it lengthens the f_mutex critical section around the retry.

Layton’s review, and where the series sits

Jeff Layton replied the next day with a cover-letter-level:

"Reviewed-by: Jeff Layton jlayton@kernel.org"

No nits on the split, the dropped B_DEAD flag, or the f_mutex widening. There is no Acked-by from other lockd regulars in this window, and no merge notice yet.

Why this still matters to NFS

  • Kind of change: two lockd server teardown races. Not an NFS protocol change. Not NFS client (nlmclnt_* / fs/nfs) code, despite lockd sitting under the NFS umbrella.
  • The UAF is the backportable piece. Patch 1 is two lines, applies alone, and matches Bai’s KASAN stack (nlm_async_call from the lockd kthread vs. nlmsvc_release_block from lockd_down). That is the important crash fix.
  • The host leak is mainline-only by design. Patch 2 serializes retry against nlmsvc_traverse_blocks() with f_mutex because a refused insert (v2’s B_DEAD) can free a block whose file_lock the VFS still owns.
  • Status this week: v3 posted 23 Aug, Layton Reviewed-by 24 Aug. No further comments, no v4, no indication it is in nfs-next yet.

Until patch 1 lands in stable and patch 2 in mainline, nfsd unmount while NLM locks are blocked remains a KASAN UAF on the lockd thread and a host that can outlive its network namespace.
