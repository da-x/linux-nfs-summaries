Chuck Lever rewrites svcsock TCP receive around ->read_sock after netdev rejects read_sock_rectype

Summary

This is a bug-fix plus receive-path rewrite, not an NFS protocol change. Chuck Lever posted a five-patch SUNRPC series that stops using recvmsg() to ingest NFSD TCP records and instead parses the RPC stream with the existing ->read_sock actor. The work is confined to net/sunrpc/svcsock.c (555 lines, +295/−260). There were no replies this week.

The series is the svcsock-only fallback after netdev rejected the generic read_sock_rectype proto op from Lever’s July net-next v2. That earlier series tried to make TLS control-record delivery unrepresentable as a mixed data/cmsg receive for every in-kernel consumer. This week Lever scopes the same idea to NFSD alone and leaves the NFS client (xprtsock), nvmet-tcp, and nvme-tcp for later.

Why the rewrite exists

kTLS splits a TLS control record across two destinations: the record type arrives in a control-message buffer, while an alert’s level and description land in the caller’s application-data buffer. Every in-kernel consumer therefore builds the same recvmsg() dance: install a cmsg buffer, discover a control record mid-call, take the body from the data buffer, re-issue the receive with a kvec, and rewind the iterator the first copy advanced. Lever’s cover letter is unsparing:

"No consumer has gotten that sequence quite right."

He lists the fallout: tls_alert_recv() read a kvec holding no valid data on the server (bee47cb026e7) and, independently, on the client (cc5d59081fa2); xprtsock processed only the first cmsg and dropped every record type behind it (9559d2fffd4f); nvmet-tcp and nvme-tcp were built on the same split and never took the corresponding repair. The server-side repair itself left two more defects that stood for a year (dbabcbc9cf46, b6c603a2415f).

netdev would not take the proto op that would have made that class of bug unrepresentable. Lever therefore:

"Instead, this series fixes the svcsock instance alone. Data records and control records now arrive through separate calls with separate buffers, and no buffer carries both application data and record metadata. The MSG_CTRUNC recovery that bee47cb026e7 installed is removed with the old path. xprtsock, nvmet-tcp, and nvme-tcp are left for future work."

That last sentence is the client-development takeaway for this week: the NFS client still lives on the broken mixed-buffer path. The svcsock conversion is the template, not the client fix.

Two receive outcomes that used to keep a connection running now close it:

  • A handshake record during an established TLS session was drained and the receive retried; svcsock has no handler for a post-handshake handshake record.
  • ->read_sock stops at an urgent octet and consumes none of it. recvmsg() walked past that octet and cleared the condition, so an RPC stream that carries urgent data can no longer advance once ingested via read_sock.

Patch 1: classify without acting

Patch 1 splits svc_tcp_sock_recv_cmsg() into a receive helper and a policy helper. The old function both received the record at the head of the kTLS queue and decided what its content type meant for the transport, so a later caller could not learn a record’s type without also acting on it. The conversion needs a MSG_PEEK classify-before-consume step.

svc_tcp_recv_cmsg() now takes recvmsg() flags and reports octet count, record type, and message flags. Alert policy stays in svc_tcp_sock_recv_cmsg(). A zeroed control buffer replaces the msg_controllen check: an unfilled buffer reports record type zero, so a positive octet count with no record type now returns -EBADMSG instead of a count. The alert parse runs on a second msghdr over the alert buffer, so the copy and the parse share no iterator state. The hand-written rewind from bee47cb026e7 ("sunrpc: fix handling of server side tls alerts") is no longer needed.

Patch 2: unhandled TLS record types close the transport

Patch 2 is the first behavioral bug fix. The old helper drained a TLS record that was neither an alert nor application data, then returned -EAGAIN so the receive loop retried. That path only runs on an established TLS session. A handshake record there is a post-handshake message, and the server has no handler for one. Draining a KeyUpdate only delays the close: kTLS sets key_update_pending when it decrypts that record, and a later receive returns -EKEYEXPIRED. kTLS flags only a KeyUpdate, so any other post-handshake message disappeared and the connection kept running.

The new policy returns -EPROTO for an unhandled record type. Any error but -EAGAIN closes the transport. Application data still returns -EAGAIN. Lever notes, with a client-side implication:

"No NFS client is known to send a handshake record on an established connection."

That is a statement of observed client behavior, not a client code change. A future xprtsock conversion will have to decide the same close-vs-drain policy for post-handshake records.

Patch 3: flush pages once per complete record

Patch 3 is a small correctness/performance cleanup that the read_sock conversion needs. svc_tcp_read_msg() flushed destination pages after every receive, so a record that arrived in several pieces was flushed once per piece, and a page spanning two pieces was flushed twice. Nothing reads the message body before the record is complete, so no reader needed the intermediate flushes.

The flush now happens once from svc_tcp_recvfrom(), after the last fragment has arrived. svc_flush_bvec() and its ARCH_IMPLEMENTS_FLUSH_DCACHE_PAGE guard go away; a plain walk of rq_pages compiles away where flush_dcache_page() is an empty inline.

Patch 4: RPC records via ->read_sock

Patch 4 is the heart of the series. svc_tcp_recvfrom() used to read an RPC record with two recvmsg() calls — four-octet fragment marker, then body. Neither supplied a control-message buffer, so kTLS reported a TLS control record on either one by raising MSG_CTRUNC and delivering nothing. Both receives had to recognize that outcome and hand off to the recovery path bee47cb026e7 built. That recovery stays on both receives for as long as one recvmsg() serves data and control alike.

The new path parses the record stream in a ->read_sock actor. The data path carries no control-message buffer at all. A control record at the head stops ->read_sock short, so svc_tcp_recv_ctrl_record() classifies the head of the receive queue with MSG_PEEK before consuming anything.

Copying is rewritten to avoid walking a large GRO or kTLS skb once per page:

"skb_copy_bits() walks an skb from its head to reach the copy offset, so an actor that copies a page at a time rewalks a large GRO or kTLS skb once per page. Copy each callback's share of the record into rq_bvec with one skb_copy_datagram_iter() instead."

Fragment accounting is tightened. A non-final fragment carries four octets of marker and may carry no payload. sk_datalen advances only by the payload, so neither a run of empty fragments nor a run of one-octet fragments trips the sv_max_mesg check before desc->count runs out. Only desc->count bounded such a run, four or five octets at a time. The patch caps the fragments per socket-lock hold.

Urgent data becomes a hard close. recvmsg() skipped an urgent octet and cleared the condition, so the old path advanced past it. ->read_sock consumes what precedes the urgent octet and then stops there for good. With no recvmsg() left on the data path, the record stream cannot advance again. Lever’s conclusion:

"An RPC stream carries no urgent data, so close the connection. The read that first reaches the mark returns a positive count, so a zero-length read does not mark the stop. Key the close on an incomplete record."

That is a server-side transport close, not a client bug, but it is the kind of stream-framing edge the xprtsock conversion will have to re-decide when the client moves off recvmsg().

Patch 5: one receive path, no partial LSM coverage

Patch 5 is a small but sharp security-observation fix. After patch 4, svc_tcp_recvfrom() parses the RPC record stream with ->read_sock, which calls neither security_socket_recvmsg() nor the sock:sock_recv_length tracepoint. svc_tcp_recv_cmsg() still went through sock_recvmsg(), so an LSM mediated only the TLS control records on a server socket, and sock:sock_recv_length reported only those. Lever’s verdict:

"Partial coverage is worse than none. It makes the RPC stream look mediated and observed when it is not."

Until the record stream moved to ->read_sock, an LSM saw every octet NFSD read from a TCP socket. An SELinux policy that denies SOCKET__READ to NFSD blocked the receive. After this change no call on the server’s TCP receive path consults an LSM, so that denial has no effect. The patch dispatches ->recvmsg directly (sock_recvmsg_nosec() / INDIRECT_CALL_INET()) so the whole receive path behaves one way. Control records are rare on an established connection, so the extra indirect call on a retpoline build is accepted.

This is an NFSD-side LSM coverage change, not an NFS client change. A later xprtsock conversion that also switches to ->read_sock will hit the same LSM/tracepoint question on the client socket.

NFS client implications

No NFS client code moves this week. The cover letter is explicit that xprtsock is unfinished work, and the historical client bugs Lever cites (cc5d59081fa2 for tls_alert_recv(), 9559d2fffd4f for dropped extra cmsgs) remain the reason that conversion still matters. Until xprtsock gets the same split — data records through ->read_sock, control records through a separate buffer, no mixed iterator — a kTLS NFS client still has to get the recvmsg() / cmsg sequence right, and Lever’s position is that no consumer has.

What this series does give client developers is a working svcsock template after the generic netdev API was rejected:

  • Classify a TLS record with MSG_PEEK before consuming it.
  • Never put application data and record metadata in the same buffer.
  • Close on unhandled post-handshake record types rather than draining them.
  • Treat urgent data as a stream that cannot advance under ->read_sock.
  • Do not leave an LSM or a tracepoint covering only the control-record side path.

Status

Posted 2026-08-21, no review, Acked-by, or merge this window. The discussion has not evolved past Lever’s own commit messages. The series is the first concrete SUNRPC follow-through after netdev rejected read_sock_rectype; whether reviewers accept closing on handshake records and urgent octets, and whether the LSM bypass in patch 5 needs a wider audit, are open questions for next week. The NFS client conversion is named, not started.
