NFS verifier walk sleeps under i_lock; tmpfs readdir fix is incomplete

Summary

This week Chuck Lever’s xfstests run against NeilBrown’s v2 negative-dentry RFC turns the NFS client conversion of nfs_clear_verifier_directory() from preparatory lock-splitting into a real sleep-in-atomic bug, and Neil’s reply to last week’s 13/18 review knocks down the claim that the same-parent __d_move change is a standalone tmpfs readdir fix. The series remains a VFS/dcache bug-fix RFC with a small NFS client delta — not a protocol change and not a new NFS feature. Neil promises another RFC; Chuck offers a follow-on d_sib ordering patch. Nothing is queued.

Brief bridge from last week

v2 (posted 15 August) tries to fix parent d_lockref overflow and soft lockups walking ->d_children without shrinking the negative-dentry population. The NFS-facing work is 04/18 (split the locked regions in nfs_clear_verifier_directory()) and 05/18 (put that walk on d_for_each_positive_child). The iterator is only allowed to cond_resched() after later patches have stripped every other spinlock from the walk.

Last week Chuck Lever R-by’d 13/18 and reclassified it as a tmpfs offset_readdir duplicate-entry bug after rename("a","b"), not mere preparation for the sleepable iterator. Neil had not replied in-window. Al Viro’s d_walk/rename_lock objection from 15 August is unchanged.

Classification

Two in-window sub-threads, both bug fixes inside the RFC:

  1. An NFS client locking bug exposed by applying the series: d_for_each_positive_child() (which might_sleep() after 14/18) is reached from nfs_clear_verifier_delegated() while i_lock is held.
  2. A VFS/libfs correctness debate: whether 13/18 actually restores d_children vs offset-cookie order for tmpfs same-directory rename.

No protocol change. No new NFS feature.

The NFS client sleep-in-atomic bug

On 24 August Chuck reports a non-deterministic hit while running xfstests against tmpfs with the series applied. The trigger was incidental — “an unrelated process chmod'ed a file on an NFSv4 mount while xfstests was running” — but the path is not exotic:

"the path looks reachable by any SETATTR that returns a delegation on a directory"

The splat is a classic atomic-context sleep:

"BUG: sleeping function called from invalid context at fs/nfs/dir.c:1497"

in_atomic() is 1, preempt_count is 1. The stack is the NFSv4 setattr / delegation-return path:

chmod_common → notify_change → nfs_setattr → nfs4_proc_setattr → nfs4_inode_make_writeable → nfs4_inode_return_delegation → nfs_start_delegation_return → nfs_clear_verifier_delegated.

Chuck pins line 1497 as the d_for_each_positive_child() call that 05/18 introduced and that 14/18 annotated might_sleep().

That is exactly the hazard 04/18 was written to prepare for, not to create. Neil’s original 04/18 only dropped and retake the directory lock between nfs_unset_verifier_delegated() on the parent and the child walk, because:

"Subsequent patches will use a helper for walking the d_children list and that helper may drop the lock temporarily."

It did not look at the caller. The sleepable iterator is now reachable from a path that still holds i_lock.

Neil thanks Chuck for the testing and diagnoses the missing lock drop (he writes nfs_clear_verifier_deleted(), but the stack is nfs_clear_verifier_delegated):

"nfs_clear_verifier_deleted() holds the inode i_lock across nfs_clear_verifier_directory() which walks the the d_children list. I'll need to use d_find_alias() to get the dentry like I did in the notify code. Hopefully I'll send another RFC tomorrow."

That is the same pattern as v2’s 07/18 for fsnotify_set_children_dentry_flags(): d_find_alias() + dget(), drop i_lock, walk, dput(). Until that lands, applying the series makes a directory SETATTR that returns a delegation a client-side sleeping-from-atomic BUG, not merely a theoretical soft lockup on huge d_sib lists.

13/18 does not actually fix tmpfs readdir

Neil finally answers Chuck’s 20 August review of 13/18.

He accepts the commit-message nit. Chuck had asked that “both dentries” be qualified because, on an ordinary move, only dentry->d_sib is relocated; target->d_sib moves only on the exchange path. Neil:

"Thanks, I'll adjust that."

He does not accept the larger claim — that 13/18 is independently a tmpfs offset_readdir correctness fix. Chuck’s rename("a","b") example (create a, b, c; after the rename, a kept offset 4 and was rotated to the head, so a restarted readdir could report a twice) is a case the patch happens to help. A different same-directory rename does not:

"Thanks for the review, but I think the above is a false hope. In that particular case my patch helps, but in a different case it doesn't. Suppose instead of rename("a", "b"), I did rename("a", "c")."

Before the rename, d_children holds (name,offset) pairs ("c", 5), ("b", 4), ("a", 3). After 13/18, dentries are not rotated, but the name and offset of "c" are still copied onto "a" and the original "c" is unhashed:

["c", -], ("b",4), ("c", 5)

"which has the wrong ordering."

So the invariant Chuck needs — offset order is the reverse of d_children order, which is what lets offset_readdir() recover a stale cookie with mas_find_rev() and then walk siblings — is still broken for overwrite-rename of a later sibling. 13/18 remains what Neil said it was: stop __d_move() rotating a still-present child in front of a dropped-lock cursor, so the sleepable NFS/fsnotify/libfs walk cannot skip a dentry that never left the directory.

Chuck does not withdraw the Reviewed-by. He says he already has a follow-on:

"I have a fix for that, I believe, that applies on top of this one. I can post it if interested."

He does not post it in-window. Whether 13/18 can still land on its own as “don’t rotate same-parent d_sib” (Neil’s original justification, which the NFS iterator still needs) is unaddressed; the tmpfs-readdir-fix story is now explicitly incomplete.

Why this matters for NFS client development

This is the first in-series NFS client regression found by testing, and it is on the hot setattr/delegation-return path.

nfs_clear_verifier_directory() / nfs_clear_verifier_delegated() is the NFS analogue of the fsnotify children walk: unsetting change-attribute verifiers on a directory and its positive children. v2 put that walk on a common iterator that is allowed to drop d_lock and cond_resched(). Chuck’s splat shows a lock the series did not drop: the inode i_lock held by the delegated-verifier caller. That is the same class of bug 07/18 already fixed for fsnotify, and Neil’s proposed remedy is the same d_find_alias() pattern.

Until the next RFC:

  • applying v2 makes chmod/SETATTR on a delegated directory a might_sleep()-under-i_lock BUG, independent of negative-dentry count;
  • the original soft-lockup hazard (a huge d_sib list of negative children) is still not fixed in a mergeable form, because the iterator cannot be allowed to sleep while any spinlock remains;
  • the parallel v1 fsnotify argument (Neil still wants callers to own an update_children flag so no d_children walk runs under mark->lock) is unchanged this week in this thread.

Patch 13’s NFS relevance is unchanged by the tmpfs counter-example. The NFS verifier walk still needs same-parent __d_move not to rotate a live child in front of a cursor. Chuck’s promised follow-on would be a libfs/tmpfs cookie-order fix on top, not an NFS client change.

Final conclusions (as of 27 August)

  • Classification: VFS/dcache bug-fix RFC; this week’s NFS-visible result is a client locking bug (sleep in atomic context on the NFSv4 setattr/delegation-return path) plus a partial VFS rename/d_sib change whose tmpfs-readdir benefit Neil rejects as “a false hope.”
  • NFS client: Chuck reproduced sleeping function called from invalid context at the d_for_each_positive_child() in nfs_clear_verifier_delegated(). Neil will drop i_lock first via d_find_alias(), matching the fsnotify patch, and aims to post another RFC “tomorrow.”
  • 13/18: Neil will fix the “both dentries” wording. He will not sell the patch as a complete tmpfs offset_readdir fix; rename("a","c") still leaves d_children mis-ordered relative to offsets. Chuck says he has a stacked fix and offers to post it; it is not on the list this week. His earlier Reviewed-by is not withdrawn.
  • Disposition: still RFC/RFT, now with a known NFS client BUG on the series as posted. No maintainer queue. The next revision has to treat i_lock on the delegated-verifier path the same way 07/18 treated it for fsnotify, or the sleepable child iterator cannot ship.
