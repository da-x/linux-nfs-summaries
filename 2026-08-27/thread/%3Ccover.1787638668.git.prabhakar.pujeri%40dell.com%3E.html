nfsd Netlink client-state dump and grace reporting

Summary

Dell’s Prabhakar Pujeri opened a new nfsd observability series this week, proposing to expose NFSv4 client state over the existing Generic Netlink family rather than forcing monitoring tools to walk /proc/fs/nfsd/clients. The work is a new userspace ABI / admin feature, not a wire-protocol change and not a bug fix. Jeff Layton immediately challenged the grace-period semantics in patch 1/3; Pujeri accepted the critique and sketched a v2 that reports the union of NLM and NFSv4 grace via locks_in_grace(). Chuck Lever then asked that any new API leave room for future per-export grace. Patches 2/3 and 3/3 (the client dump and stateid counters) had not yet drawn review by week’s end.

Why Netlink, and what the series actually adds

Pujeri’s cover letter frames the problem as operational, not functional: administrators can already inspect NFSv4 clients through the nfsd filesystem, “but collecting a server-wide view requires walking a directory and opening multiple files for every client. That is useful for detailed inspection, but awkward for monitoring and automation.” The series therefore adds a compact query interface to the existing nfsd Generic Netlink family, in three deliberately split steps:

  1. Extend threads-get with an explicit NFSv4 recovery-grace value.
  2. Add a privileged client-get dump with basic identity, lease, confirmation, reclaim, and callback information.
  3. Extend each client reply with session and stateid record counts.

The split is ABI-conscious. Pujeri wrote that it “keeps the grace query independent, establishes the minimum useful client ABI before adding the more expensive state traversal, and permits older user space to ignore the count extension.” The existing nfsd filesystem files and their output are left unchanged; a companion nfs-utils series (not posted on linux-nfs this week) would add nfsdctl clients and surface the grace value from nfsdctl threads.

Two implementation details in the cover letter matter for anyone consuming the dump:

  • Best-effort snapshot. client-get emits one bounded message per client. The dump pins each client, uses the existing client and state locks for mutable fields, and serializes against server shutdown. “Client churn can still make a multi-message dump a best-effort snapshot; the interface documentation states this explicitly.”
  • Client ID encoding. The Netlink client ID places cl_boot in the upper 32 bits and cl_id in the lower 32 bits — “an architecture-independent representation matching NFSD’s logical and tracepoint representation, rather than the legacy procfs rendering of the in-memory bytes.”

Validation listed in the cover includes checkpatch, YNL regeneration, Sphinx -W docs, W=1 builds with CONFIG_NFSD_V4 both on and off, a two-vCPU QEMU loopback NFSv4.2 mount, grace yes/no transitions through both raw Netlink and nfsdctl, and a live client carrying one session plus open, lock, and delegation stateids (zero layouts). The series is based on nfsd-testing at 46ff234c7129c7c10ed493413d4f60d0cf4dd1f1.

Patch 1/3: grace on threads-get

Patch 1/3 adds an in-grace value to the threads-get reply. The stated goal is to let operational tooling “distinguish a server that is accepting normal NFSv4 state operations from one that is still accepting only recovery requests.” Recovery state is currently available only through the nfsd filesystem. The attribute is returned in every reply so userspace can tell a server that is not in grace from an older kernel that simply does not provide the attribute.

Patch 2/3: privileged NFSv4 client dump

Patch 2/3 is the core of the series: a privileged client-get dump that emits one bounded message per confirmed or unconfirmed client, carrying server-generated client ID, peer address, minor version, client and callback states, signed lease time remaining, and RECLAIM_COMPLETE status.

Concurrency is conservative rather than lock-free. Each client is pinned while a snapshot is taken; mutable lease and confirmation fields are protected with the per-net client lock; server shutdown is serialized with nfsd_mutex. Netlink dump cursors track table, bucket, and position. Pujeri is explicit that client churn can still produce a best-effort snapshot, and that the nfsd filesystem interface is left as the detailed-inspection path.

Patch 3/3: per-client state usage counters

Patch 3/3 extends those replies with compact totals, because “a client can retain substantial server-side state even when its lease and callback channel look healthy.” Counts are separate for sessions and for open, lock, delegation, and layout stateid records. The lock count is intentionally not a byte-range or LOCK-operation count: “A lock stateid represents a lock-owner/file pair and can cover multiple byte-range locks.”

The walk is done under cl_lock for both the session list and the stateid IDR. Pujeri notes that free_client() already detaches its session list under that lock, “so a client pinned by the dump cannot race this traversal with session teardown.”

Review: Jeff Layton on what “in grace” actually means

The only technical review this week landed on patch 1/3. Jeff Layton asked the design question first:

"What's your interest in reporting this info?"

and then pointed out that the v1 attribute answers the wrong operational question:

"Just because the v4 recovery is done does not mean that you will be able to access files. The overall system grace period is a union of both the NLM and v4 grace periods."

"This patch is reporting just the v4 one. If the goal is for the admin to reliably tell when the grace period has been lifted, then this won't tell us that."

Layton offered two ways forward: return locks_in_grace() from nfsd, or add similar reporting to lockd and let userspace compute the union.

Pujeri’s reply: restart/failover harness, and a v2 semantic switch

Two days later Pujeri answered with the use case behind the series. He is building “a validation harness for NFS server restart and failover behaviour: bounce the server, drive reclaim from a set of clients, and check that state comes back the way it should.” That harness has to know when grace has actually lifted before it can advance. Polling /proc/fs/nfsd/v4_end_grace works, “but it is a text interface, it only answers for nfsd’s v4 lock manager, and new nfsd control and observability interfaces are going to the netlink family instead.” He would “rather frame this as parity than as new information.”

He then conceded Layton’s semantic point in full:

"Agreed, and "has the grace period lifted" is the question I actually care about. I mirrored the semantics of /proc/fs/nfsd/v4_end_grace without stopping to ask whether those were the useful semantics to expose in a new interface. They aren't."

For v2 he plans to report locks_in_grace() — “which answers ‘can this server hand out normal locks and opens yet’ rather than ‘is nfsd’s v4 lock manager done’.” He does not think lockd needs a new interface: fs/nfs_common/grace.c already exposes both halves. locks_in_grace() is the union; opens_in_grace() is true only while a manager with ->block_opens is in grace (NFSv4-and-up; NLM does not set it). A second attribute for opens_in_grace() could be added later without touching lockd, letting userspace derive the NLM-only case as (locks && !opens), but he would rather not add that speculatively.

Two implementation cleanups fall out of the switch, both improvements in his view: the #ifdef CONFIG_NFSD_V4 and the open-coded nfsd_vers() / NFSD_NET_UP / NFSD_NET_GRACE_ENDED test all go away (NFSD selects LOCKD which selects GRACE_PERIOD, so the helper is always available), and the answer “stops being a v4-specific answer that just happens to be served out of the nfsd netlink family.” He will rename the attribute and fix the YAML and RST wording so the union semantics are explicit.

He also floated a design question that is still open at week’s end: threads-get otherwise reports configuration, while grace is dynamic state, so it could live in its own operation. His inclination is to keep just this boolean on threads-get for nfsdfs parity, and grow richer recovery detail — elapsed time, expected vs completed reclaims, whether grace was extended or force-ended — as a separate operation later. He offered to start that separate op now if reviewers prefer.

Chuck Lever: do not freeze grace as a server-wide boolean

Chuck Lever’s reply did not object to reporting grace, but asked that the new API not paint nfsd into a corner:

"Although NFSD does not yet support putting individual exports in grace, that is an open possibility for handling things like the reboot of a backend NFS server for a re-exported NFS client. I'd like any new API to avoid foreclosing the ability to move exports in and out of grace individually rather than as a single unit."

That is a forward-looking constraint on the Netlink schema: a single server-wide boolean is fine as a v2 starting point only if it does not become the only shape the ABI can ever express.

Status at week’s end

The series is v1, under review, not merged. Consensus so far:

  • There is appetite for a Netlink replacement of nfsdfs client enumeration for monitoring and automation; patches 2/3 and 3/3 (the dump itself and the stateid counters) have not been technically disputed this week.
  • The v1 grace attribute, which mirrored /proc/fs/nfsd/v4_end_grace, is not the right answer. v2 is expected to report locks_in_grace() (NLM ∪ NFSv4) and to rename the attribute so those union semantics are explicit.
  • Whether grace stays on threads-get or becomes its own operation is still an open design question from the author.
  • Any ABI must not preclude future per-export grace, a concern Lever tied to NFS re-export / backend reboot.

No NFS client code is touched. The client-visible impact, if the series lands, is indirect: better server-side observability of leases, reclaim, callbacks, and per-client stateid load, which is exactly the data a restart/failover test harness — or an operator watching a busy NFSv4 server — needs before deciding that recovery is finished.
