Chuck Lever prepares NFSD nfserr names for xdrgen

Summary

This is a header-cleanup / preparatory refactor, not a protocol change and not a functional bug fix. Chuck Lever posted a two-patch series on 26 August that stops NFSD from building its internal __be32 nfserr_* constants off the version-agnostic NFSERR_* names in uapi/linux/nfs.h. The work is a staging step for an upcoming xdrgen conversion: a later patch will swap linux/nfs.h for the generated linux/sunrpc/xdrgen/nfs2.h, which only re-supplies the eighteen NFSv2 status codes. There were no replies in this window.

The series is server-heavy, but the first patch lands in a shared client/server header. Lever’s cover for PATCH 1/2 is explicit that both sides of the in-kernel NFS stack currently lean on the UAPI soup:

"enum nfs_stat in uapi/linux/nfs.h collects the on-the-wire status codes for every NFS version under version-agnostic NFSERR_* names. The in-kernel NFS client and server reference these names internally, which drags uapi/linux/nfs.h into many translation units that need nothing else from that header."

That is the client-development angle this week: linux/nfs3.h is about to grow a complete NFS3ERR_* enum so later xdrgen work can drop the version-agnostic names without leaving either the client or NFSD short of a spelling.

Why the agnostic names have to go

xdrgen is meant to emit spec-based status constants. Replacing internal NFSERR_* uses with version-specific names needs a version-specific spelling for every code NFSD actually uses. linux/nfs4.h already has the NFSv4 set. NFSv3 does not have a counterpart, and the mapping is not 1:1. Lever calls out the mismatches that would otherwise force NFSD to keep fishing in uapi/linux/nfs.h:

"not every NFSv3 code has an NFS4ERR_* spelling: NFSERR_NOT_SYNC (10002) and NFSERR_REMOTE (71) have no NFSv4 equivalent at all, and NFSERR_JUKEBOX (10008) appears in NFSv4 as NFS4ERR_DELAY."

Without a dedicated NFSv3 enum, those three codes — plus the rest of the v3 table — would vanish the moment nfserr.h stopped including the UAPI header.

PATCH 1/2: NFS3ERR_* lands in linux/nfs3.h

Import NFS3ERR definitions is a 35-line addition to include/linux/nfs3.h. It introduces the NFSv3 status codes as NFS3ERR_* so the follow-up can respell NFSD’s status macros without uapi/linux/nfs.h. Lever frames it as infrastructure, not a wire-format change:

"Introduce the NFSv3 status codes as NFS3ERR_* in linux/nfs3.h so a subsequent patch can respell NFSD's status definitions without relying on uapi/linux/nfs.h."

Because linux/nfs3.h is the in-kernel NFSv3 header used by the client as well as the server, this is the piece of the series that will show up in client translation units. It does not change client behavior; it gives client (and server) code a version-correct name for every NFSv3 status instead of the mixed NFSERR_* namespace that currently pulls the whole UAPI header into unrelated C files.

PATCH 2/2: nfserr.h stops wrapping NFSERR_*

Rework be32 nfserr definitions is the NFSD-side consumer. Today fs/nfsd/nfserr.h builds the internal __be32 nfserr_* values by wrapping those agnostic NFSERR_* codes in cpu_to_be32(), reached through linux/nfs.h. Lever explains why that include cannot simply be swapped for the generated NFSv2 header:

"A subsequent patch replaces that include with the xdrgen-generated linux/sunrpc/xdrgen/nfs2.h. The generated header re-supplies only the eighteen NFSv2 status codes; the NFSv3 and NFSv4 codes that nfserr.h also uses (NFSERR_INVAL, NFSERR_JUKEBOX, NFSERR_RESOURCE, and the rest) would be left undeclared."

The patch therefore respells those definitions in terms of NFS3ERR_* (from the new nfs3.h enum) and NFS4ERR_* (from linux/nfs4.h). The one leftover bare NFSERR_MOVED in fs/nfsd/nfs4xdr.c becomes NFS4ERR_MOVED. Diffstat is concentrated: 129 lines churned in nfserr.h, a one-line swap in nfs4xdr.c. Lever is careful that this is a rename, not a protocol tweak:

"The wire values are unchanged; NFSD no longer depends on the version-agnostic NFSv3 and NFSv4 names."

That last sentence is the operational conclusion of the series: on-the-wire status numbers stay put, so clients talking to this server will not see a new error code. What changes is the in-tree spelling NFSD uses to produce those numbers, so the forthcoming xdrgen-generated NFSv2 header can replace linux/nfs.h without undeclaring nfserr_inval, nfserr_jukebox, nfserr_resource, and the rest of the v3/v4 table.

Client vs. server, and what is not in this series

  • Kind of change: preparatory refactor for xdrgen. No NFS protocol change. No runtime bug fix. No client I/O path change.
  • Client impact this week: indirect. Patch 1 extends include/linux/nfs3.h, a header the NFS client already includes. It does not convert client call sites off NFSERR_*; it only supplies the NFSv3 spellings NFSD (and, later, client xdrgen work) need. Lever’s own rationale still names the client as a co-offender for dragging uapi/linux/nfs.h into TUs that only wanted a status constant.
  • Server impact: fs/nfsd/nfserr.h and one nfs4xdr.c token. After this lands, NFSD’s internal nfserr_* macros are sourced from version-specific enums rather than the mixed UAPI nfs_stat.
  • Not included: the “subsequent patch” that actually replaces the linux/nfs.h include with linux/sunrpc/xdrgen/nfs2.h. That conversion is announced, not posted.
  • Review status: Lever is the only participant. No Reviewed-by, Acked-by, or nits this window.

Until reviewers weigh in, the series sits as unacked infrastructure: a shared NFS3ERR_* enum for the client/server tree, and an NFSD nfserr.h that is ready for xdrgen to take over the NFSv2 names without orphaning v3 and v4 status codes.
