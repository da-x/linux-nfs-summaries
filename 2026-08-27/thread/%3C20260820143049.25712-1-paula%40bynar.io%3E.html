SUNRPC xdr_inline_pages() OOB: patch confirmed to work

Summary

This is a bug-fix thread for a Linux NFS client receive-path hole: an unsigned wrap in xdr_inline_pages() that can turn a legal NFSv3 AUTH_SYS reply into a peer-controlled slab write. Last week Paula Moutafian posted the clamp; this week the only in-window traffic is NFS maintainer Anna Schumaker pressing on whether the patch was actually built, and Moutafian walking back the original "untested" note.

The technical substance of the defect is unchanged from the 20 August posting. xdr_inline_pages() re-carves a receive buffer into head, page list and tail at a caller-supplied offset and computes the tail as buflen - offset. Because iov_len is unsigned, an offset past the end wraps instead of failing. That offset is not an internal constant: rpc_prepare_reply_pages() derives it from the flavour's au_ralign, which is reread on every encode, while the receive buffer size is fixed once in call_allocate() from au_rslack. unx_validate() then raises au_verfsize, au_rslack and au_ralign from the reply verifier before rpc_decode_header() inspects accept_stat. A GARBAGE_ARGS reply can therefore poison the alignment and send the task back through call_encode(); call_allocate() short-circuits on the existing buffer, so the retry carves a new offset against the old size. auth_unix keeps those fields in a file-scope static rpc_auth shared by every AUTH_SYS client.

The observed NFSv3 READ geometry was rq_rcvsize 132 with a 128-byte head, au_ralign raised from 2 to 4, and a retry carve at 136. The in-tree sunrpc:rpc_xdr_reply_pages tracepoint captured the wrap (tail length 4294967292). xs_read_xdr_buf() then fills that tail; TCP record length is not capped against rq_rcvsize, so the retried reply writes past the rpc_buffers object. KASAN on unmodified v7.2-rc7 arm64 reported a 1664-byte write 160 bytes past the object. RPCSEC_GSS cannot forge the verifier, UDP is bounded by datagram length, and NFSv4 does not take the retry path because RPC_TASK_NO_RETRANS_TIMEOUT suppresses the re-encode. The chosen fix is at the carve itself (clamp the offset) rather than gating auth_unix slack updates the way gss_update_rslack() already does.

That original posting carried a caution that undercut the patch:

"the defect is reproduced 2/2 on an unmodified v7.2-rc7 arm64 KASAN kernel; the patched kernel has not been built or booted. A reproducer exists and can be shared privately on request."

Schumaker opened review on 21 August by quoting that note and asking the obvious maintainer question:

"Am I understanding you correctly that you have a reproducer, but haven't tested or even compiled the code to verify that it works?"

Moutafian replied the same afternoon and reversed the claim:

"The note was a mistake, I confirm that it compiles fine and the patch works. :)"

That is the entire in-window discussion. There is still no Acked-by, Reviewed-by, or comment on the three-line clamp in net/sunrpc/xdr.c, nor any debate of the AUTH_SYS slack-update path versus the carve-site guard. The client-side OOB remains a live, unmerged fix with a now-asserted working patch and a privately shareable reproducer, awaiting actual code review.
