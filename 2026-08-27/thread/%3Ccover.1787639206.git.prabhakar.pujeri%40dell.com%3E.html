nfsdctl clients table and grace reporting

Summary

Summary

Dell’s Prabhakar Pujeri posted a three-patch nfs-utils series this week that is the userspace consumer of his companion NFSD Generic Netlink client-state ABI (kernel cover). The work is a new admin feature, not a wire-protocol change and not a bug fix: it teaches nfsdctl to report NFSv4 recovery-grace from threads-get, and adds a privileged nfsdctl clients table that dumps one row per NFSv4 client plus optional session/stateid usage counts.

No review landed on this nfs-utils thread before week’s end. That silence matters because the kernel half did draw design pushback the same week — Jeff Layton rejected the v1 grace boolean as NFSv4-only, and Chuck Lever asked that any new API not freeze grace as a server-wide flag — so this userspace consumer is already one ABI revision behind the discussion it is meant to consume.

The series is based on nfs-utils master at 67ed1bdb1af1c70a5fd3b377a997401b7676b827. It is v1, posted, not merged.

Why a userspace consumer, and how it is split

Pujeri’s cover letter presents the series as a strict mirror of the kernel ABI split:

  1. Display the explicit recovery-grace value returned by threads-get.
  2. Add a privileged nfsdctl clients table for basic client state.
  3. Extend that table with session and stateid record counts.

The operational problem is the same one the kernel series is trying to solve. Monitoring NFSv4 clients today “requires walking the nfsd filesystem and parsing a separate info file for every client.” The new command is meant to be the compact, automatable view; the nfsd filesystem remains the detailed-inspection path.

Compatibility is the other design axis. Pujeri is explicit that attribute presence is the compatibility boundary:

"An older kernel omits the grace value, and missing count attributes are displayed as dashes."

A bundled nfsd_netlink.h lets nfs-utils build before the new kernel header is installed. The configure probe is deliberately conservative: it requires the final count attribute, so a system header that only knows the base CLIENT_GET command still falls back to the complete bundled copy. The cover also records a byte-for-byte comparison of that bundled UAPI against the kernel copy.

Validation listed in the cover is end-to-end rather than compile-only: a full nfs-utils build at each applicable patch state; make check with no failures (one environment-dependent test skipped); a two-vCPU QEMU loopback NFSv4.2 mount; grace yes/no transitions displayed by nfsdctl threads; and a live client row showing one session, one open stateid, one lock stateid, one delegation stateid, and zero layout stateids, with callback, reclaim, lease, peer-address, and client-ID fields checked.

Patch 1/3: grace on nfsdctl threads

Patch 1/3 is a small display change with a large semantic dependency. nfsdctl threads already reports thread configuration; Pujeri adds the kernel’s new in-grace value so an operator can tell “whether the NFSv4 server is accepting normal state operations or only recovery requests.”

The presence check is the interesting part of the patch. Displaying the attribute only when it is present

"prevents a new nfsdctl from reporting an older kernel's lack of the attribute as "no"."

That is the right userspace posture for an optional Netlink attribute. It is also, as of this week, pointed at the wrong kernel attribute. On the companion kernel series, Jeff Layton argued that a v4-only grace flag does not answer “has the grace period lifted,” because the overall system grace period is the union of NLM and NFSv4. Pujeri later agreed on that thread that v2 should report locks_in_grace() and rename the attribute. This nfsdctl patch will have to follow that rename and the new union semantics; as posted, it still documents and prints an NFSv4-only “in-grace” value.

Chuck Lever’s same-week request that any new API leave room for future per-export grace is likewise not reflected here: nfsdctl threads would print a single server-wide yes/no.

Patch 2/3: nfsdctl clients

Patch 2/3 is the meat of the series: a new privileged clients command that consumes NFSD_CMD_CLIENT_GET and prints one row per client.

Each row reports:

  • server-generated client ID
  • peer address
  • minor version
  • client state
  • lease time remaining
  • reclaim status
  • callback state

Address formatting is not an afterthought. The command formats both IPv4 and IPv6 socket addresses, including ports and IPv6 scope IDs. Unknown enum values are rendered as "unknown" so a newer kernel with extra states remains usable with this nfsdctl rather than being treated as a parse error.

The bundled UAPI header is updated here, and configure is taught to require NFSD_CMD_CLIENT_GET before selecting a system copy of that header. Man page and asciidoc updates (nfsdctl.8, nfsdctl.adoc) land with the command.

This is the userspace half of the kernel dump that pins each client, serializes against shutdown, and still documents a multi-message dump as a best-effort snapshot under client churn. nfsdctl itself does not re-litigate those kernel concurrency choices; it is a table formatter over the dump.

Patch 3/3: per-client state usage

Patch 3/3 extends the clients table with the session and stateid record counts the kernel series exports — sessions plus open, lock, delegation, and layout stateid records. The stated purpose is triage, not replacement of nfsdfs:

"These totals help an operator identify which client is retaining server-side state before using the detailed nfsd filesystem views."

Missing count attributes print as a dash, so a new nfsdctl against a kernel that has the base client dump but not the count extension stays accurate rather than inventing zeros. The configure probe is tightened again to require the last count attribute before accepting a system UAPI header, which is how a header that only knows the base command still forces the bundled copy.

On the kernel side those lock counts are stateid records, not byte-range lock counts: a lock stateid is a lock-owner/file pair and can cover multiple byte-range locks. This nfsdctl patch does not restate that distinction in the commit message; operators reading the new columns will need the kernel documentation (or a later man-page tweak) to avoid misreading a lock column as a LOCK-operation counter.

NFS client impact, and what is still open

No NFS client kernel code is touched. The client-visible effect, if both series land, is indirect and operational: nfsdctl becomes a way to watch leases, reclaim, callbacks, and per-client stateid load from the server without scraping /proc/fs/nfsd/clients. That is exactly the data a restart/failover harness — Pujeri’s stated motive on the kernel thread — needs before it can decide that recovery is finished and that NFS clients have reclaimed state.

Status at week’s end:

  • v1 posted to linux-nfs, no nfs-utils review yet. The four messages in this thread are the cover plus the three patches; there are no replies.
  • The userspace ABI is intentionally attribute-driven and mixed-version safe (omit grace, dash out missing counts, print "unknown" for new enums, bundle the UAPI header).
  • The grace column is already known to be semantically incomplete, because the kernel attribute it consumes is expected to change in v2 from “nfsd’s v4 lock manager is in grace” to locks_in_grace() (NLM ∪ NFSv4), with a possible later split for opens_in_grace() and a constraint that the ABI must not preclude per-export grace.
  • Whether grace stays on threads-get or becomes its own Netlink operation is still an open question on the kernel series; nfsdctl currently assumes the former.

Until the kernel grace attribute is renamed and reviewed, this nfs-utils series should be read as a working prototype of the table, not as a frozen userspace contract.
