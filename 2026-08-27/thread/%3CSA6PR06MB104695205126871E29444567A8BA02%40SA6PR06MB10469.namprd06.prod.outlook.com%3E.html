NFSv3 RDMA READ payload corruption when post-op attributes are omitted

Summary

This week’s linux-nfs traffic on Rakesh Bhargava’s report is a single, densely argued bug report—not a patch, protocol change, or feature request. Bhargava of NetApp opened the thread on 24 August describing silent data corruption on the Linux NFS client when an NFSv3 READ over RPC-over-RDMA returns a legal READ3resok that omits post-operation attributes. No maintainer reply landed in-window, so the diagnosis stands as an unanswered client-side defect report.

What the client does wrong

The trigger is protocol-legal. An NFSv3 server may set attributes_follow = FALSE and omit the fattr3. On a TCP mount that is usually just a header-size learning problem; on RDMA it becomes payload corruption. Bhargava’s lead sentence is the whole story:

"A legal NFSv3 READ3resok response with attributes_follow = FALSE causes the Linux RPC-over-RDMA client to prepend 84 bytes of stale receive-buffer data to an otherwise correct RDMA-written file payload."

The environment is a RHEL 9.5-class kernel (Linux 5.14.0-503.22.1.el9_5.x86_64) with vers=3, proto=rdma, port=20049 doing 4096-byte direct reads. The server’s RDMA Write of the 4096-byte file data is correct. Corruption happens later, on the client, when xdr_read_pages() realigns an oversized XDR head and copies 84 bytes of junk onto the front of those pages. Those 84 bytes are exactly sizeof(fattr3) (21 XDR words).

On a ordinary NFSv3 mount the damage is typically a one-shot event: after the first READ the client learns read_hdrsize and subsequent replies match the reserved head. FlexFiles NFSv3 data servers do not get that learning path, so the shorter DS header keeps hitting the same mismatch:

"For a normal NFSv3 mount, only the first READ typically fails because the client subsequently learns the correct read_hdrsize. With a FlexFiles NFSv3 DS, the shorter DS header size is not learned, allowing the issue to occur repeatedly."

That is the operational sting: pNFS FlexFiles over NFSv3/RDMA can corrupt every READ, not just the first one after mount.

Why the reserved head is 84 bytes too large

The client always budgets for the maximum NFSv3 READ reply header. In fs/nfs/nfs3xdr.c, NFS3_fattr_sz is 21 XDR words, and the max READ reply size folds in status, post-op attributes, count, eof, opaque length, and page padding. Before the first READ, args->replen is zero, so nfs3_xdr_enc_read3args() reserves that maximum: 104 bytes of NFS header. rpc_prepare_reply_pages() then tacks on the RPC reply and authentication header. On the observed AUTH_SYS connection the reserved head becomes 128 bytes.

The actual inline RPC payload, when fattr3 is omitted, is only 44 bytes: RPC reply/auth header, NFS status, the attributes_follow boolean, count, eof, and opaque length. 128 − 44 = 84, “exactly the size of fattr3.”

That 44-versus-128 split is the same header-size fork the client already mishandles on TCP (the 2021 read_hdrsize EIO case). Here the numbers reappear as a data-integrity bug because RDMA has already deposited the file payload into the page list before XDR tries to shrink the head.

The RDMA receive path, then the XDR realign

Bhargava walks the receive path in order:

  1. The receive buffer is prepared as a 128-byte head, then the page list, then the tail.
  2. The data server RDMA-Writes the 4096-byte payload straight into those pages. At that instant the file data is still correct.
  3. RPC-over-RDMA receives only 44 bytes of inline RPC. rpcrdma_decode_msg() measures that inline length and calls rpcrdma_inline_fixup().

The transport then leaves the head iovec lying about its length:

"rpcrdma_inline_fixup() redirects the head iovec to point directly at the received RPC reply message to avoid an extra memory copy. Although the amount of valid data is recognized as only 44 bytes, the head iovec length remains 128 bytes. As a result, bytes 44 through 127 do not contain valid RPC data and instead reference stale data remaining in a recycled RPC-over-RDMA receive buffer."

NFS decode itself is not the villain. The client correctly sees attributes_follow = FALSE, skips fattr3, and advances only four bytes over the boolean. When decode_read3resok() later calls xdr_read_pages(), the decoder position is 44 bytes but the head iovec still claims 128, leaving an 84-byte gap.

The generic XDR layer treats that gap as live inline payload. xdr_realign_pages() / xdr_shrink_bufhead() notice that head length exceeds the current decode position and shift the extra 84 bytes into the page list—overwriting the already-correct RDMA payload with stale receive-buffer contents.

So three layers share the blame: NFSv3 XDR over-reserves the READ reply head when replen is unset; rpcrdma_inline_fixup() retargets the head iovec without shrinking iov_len to the actual inline length; and xdr_shrink_bufhead() then copies the resulting “valid” tail of the head onto pages that RDMA already filled.

Client-development implications

This is a bug fix target for the NFS client and sunrpc/xprtrdma stack, with a FlexFiles-specific severity bump. The report does not propose a patch, but the analysis points at a small set of functions:

  • nfs3_xdr_enc_read3args() / nfs3_proc_read_setup() / nfs3_read_done() — the replen / read_hdrsize learning that currently assumes a stable, full-sized READ header and does not teach a FlexFiles DS the shorter size.
  • rpcrdma_inline_fixup() — head iovec length left at the reserved 128 bytes after a 44-byte inline receive.
  • xdr_read_pages() → xdr_realign_pages() / xdr_shrink_bufhead() — the copy that turns the oversized head into payload corruption rather than an XDR overflow.

Until someone replies, the practical conclusions from the report are:

  • A spec-compliant NFSv3 READ that omits post-op attributes is enough to corrupt RDMA READ data on current Linux clients.
  • The 84-byte smear is deterministic, not a race: it is unused fattr3 reservation plus leftover bytes in a recycled RDMA receive buffer.
  • Regular NFSv3/RDMA mounts may only see it on the first READ; FlexFiles NFSv3 data servers can see it on every READ because DS read_hdrsize is never learned.

The thread is still waiting on maintainer reaction—Chuck Lever, Trond Myklebust, or another xprtrdma/NFS XDR regular—on whether the fix belongs in rpcrdma_inline_fixup() (clamp head iov_len to the decoded inline length), in the NFSv3 READ encoder (stop over-reserving, or learn DS header size for FlexFiles), or in XDR realign (refuse to treat unread head bytes as payload when XDRBUF_READ pages were already filled by RDMA). This week, the list has the diagnosis and the reproduction shape, but no agreed patch.
