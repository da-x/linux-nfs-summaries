NetFS v10: bvecq buffering, NFS fscache hooks, and read-abandonment debate

Summary

David Howells posted PATCH v10 of a 35-patch netfslib overhaul, asking Paulo Alcantara to review a conversion that replaces folio_queue, rolling_buffer and ITER_FOLIOQ with a segmented bio_vec[] chain (bvecq). The series is both a large infrastructure change and a vehicle for a pile of correctness fixes that matter to NFS clients using netfslib/fscache. Howells framed three goals: follow the kernel I/O stack’s consolidation on bio_vec arrays; collapse buffered and unbuffered/DIO buffering onto one scheme; and “always send an entire filesystem RPC request message to a TCP socket with single kernel_sendmsg() call as this is faster, more efficient and doesn't require the use of corking.”

The thread this week is the v10 posting plus one follow-up question. There is no maintainer ACK or merge decision yet.

What bvecq is, and why it exists

The replacement is a NULL-terminated, refcounted chain of struct bvecq segments, each wrapping a bio_vec[] plus disposal metadata (BVECQ_MEM_EXTERNAL, PAGECACHE, GUP, ALLOCED). Howells also added ITER_BVECQ so the same construct can be handed to sendmsg() or cachefiles DIO. Buffer tracking moves onto three cursors (load_cursor, dispatch_cursor, collect_cursor), with an extra dispatch cursor per writeback stream (server vs cache).

The core switch extracts unbuffered/DIO iterators into a bvecq up front and, for pagecache I/O, adds folios as the operation proceeds. Each bio_vec holds a portion of one folio; adjacent bvecqs in a chain may be discontiguous. That last point is deliberate: Howells wants filesystems that can do vectored/sparse RPCs (he names Ceph) to be given a chain with holes rather than being forced into contiguous slices.

The supporting machinery arrives first: readahead folio-count in readahead_control, bulk-loading those folios under RCU, kmap of one page of a multipage bio_vec, the ITER_BVECQ iterator itself, bvecq chain helpers, and extraction from any iov_iter into a bvecq. AFS directories and CIFS crypto bounce buffers are converted off folioq; smbdirect gains ITER_BVECQ mapping. Then the old world is demolished: ITER_FOLIOQ, folio_queue and rolling_buffer, plus the leftover netfs_alloc/free_folioq_buffer() and netfs_extract_user_iter() helpers.

NFS client impact

NFS is not rewritten onto bvecq in this series, but several patches change the netfslib contract the NFS client already uses.

Deprecated PG_private_2 becomes opt-in. Patch 21 gates the old PG_private_2 copy-to-cache path behind NETFS_PGPRIV2 and has NFS (and Ceph) select it. Howells CCs Trond Myklebust and Anna Schumaker. The flag stays available for NFS fscache, but it is no longer a tax on every netfs user.

nfs_netfs_issue_read() is corrected as part of collapsing prepare/issue. The cover letter records three NFS-specific fallout fixes from earlier Sashiko reports, now folded into v10: nfs_netfs_issue_read() must return an int; it must set -ENOMEM rather than 0 on allocation failure; and it must terminate the subrequest only once. Patch 34 is the API change that forces that work: ->prepare_read() / ->prepare_write(), buffer setup, and ->issue_*() are merged. Netfslib now accumulates bufferage, then loops creating subrequests; the filesystem (or cache) shortens the subrequest and calls back up to slice a bvecq rather than receiving a pre-built iov_iter. fs/nfs/fscache.c is updated for that handshake.

Write-size estimation is a new filesystem/cache method. Patch 32 adds ->estimate_max_write() on both the netfs filesystem API and the cache API so netfslib can ask how much to accumulate before dispatch. 9p, AFS, CIFS and cachefiles implement it; NFS does not, because its netfslib use is still the fscache read/write path rather than full buffered writeback.

Writethrough is gone. Patch 17 deletes netfslib writethrough because “the locking is really tricky to get right and it looks like it could deadlock with Ceph if snapshots are used.” O_SYNC now relies on the existing post-write generic_write_sync() path. NFS clients that care about fscache coherency should treat this as a behavioural change in the shared library, not an NFS-local rewrite.

Bug fixes that land in v10

Howells rebased on v7.2 and absorbed a long Sashiko-driven fix list. The ones that affect NFS/netfs clients most directly:

  • Uninitialized ret in netfs_unbuffered_write() (Karl Mehltretter). If the first subrequest fails to prepare, the function could return an unrelated error. Marked Fixes: / Cc: stable. Howells notes it is reachable through CIFS when cifs_prepare_write() cannot reopen the file or obtain credits; the same helper is on the unbuffered write path any netfs user shares.
  • Read progress reporting. Progress wakeups were based on rreq->cleaned_to, which can tear on 32-bit. The new trigger is a size_t offset from the immutable rreq->start, with a 256KiB minimum so small-folio collectors are not woken constantly. Howells: “if the folios are small, the collector thread gets constantly woken up - which has a negative performance impact on the system.”
  • cachefiles xattr UAF/KASAN. trace_cachefiles_coherency() was reading eight bytes from a variable-length, possibly empty buffer.
  • uoff_t conversion throughout netfslib, fscache and cachefiles for non-negative file positions.
  • Over-read detection. A subrequest that returns more data than requested now aborts the rest of the read with -EIO, on the theory the buffer may already be corrupted.
  • Writeback unlock list. Collection no longer walks the same folio chain the issuer is filling. Unlock regions are tracked separately; the collector walks the xarray. Howells: “this is tricky… as different streams really want different folios or different parts of folios.”
  • Preset cachefiles state xattr, posted as a 36th patch. On a tiny cache, setxattr of the state xattr can hit ENOSPC after the object has already been filled. Howells now presets the xattr on the tmpfile and scraps the file immediately if that fails: “we don't really want to successfully fill a cache file only to have to scrap it because we can't set the xattr.”

Cachefiles also sunsets on-demand/EROFS mode (Gao Xiang) and stops using SEEK_DATA/HOLE for the common contiguous-write case, recording CACHEFILES_CONTENT_ALL so occupancy queries can skip two seeks per cache read. Sparse files still use the backing filesystem map; Howells flags that as future work.

Read abandonment, and the unanswered READ_PLUS question

Patch 30 is the only patch that drew a reply this week. Today, if some subrequests fail, collection tries to salvage folios that straddle successful and failed subreqs. Howells calls that “quite complicated” and simplifies it:

"Simplify this by just abandoning the rest of a read request once a permanently failed subreq is hit. This is what read_folio, DIO/unbuffered read, gap filling, RMW and write preload all need to do; readahead is the odd one out as it doesn't have any return other than unlocking folios."

Retryable failures still retry inside the request. For readahead, leftover non-uptodate folios fall back to ->read_folio().

Aurélien Couderc asked whether that partial-abandonment work could help NFSv4.2 READ_PLUS / sparse reads:

"What about READ_PLUS, i.e. sparse file reads? If you do this kind of work of handling partial abandonment, can such a work also benefit READ_PLUS?"

There was no reply in-window. The series does talk about discontiguous bvecq chains and cache occupancy extents (FSCACHE_EXTENT_DATA vs FSCACHE_EXTENT_ZERO), which is the natural hook if NFS later wants netfslib to consume READ_PLUS hole/data segments rather than synthesizing a dense buffer. That is not implemented here.

What is still unfinished

Howells lists two follow-on pieces already working for CIFS but not in this branch: giving a filesystem a copy of a subchain so it can glue protocol headers/trailers (and compounds) onto a single sendmsg(), and splicing the TCP receive queue into a bvecq so the socket lock can be dropped before copying into destination buffers. Future ideas include batched folio unlock over a bio_vec[], iterating i_pages from bvecq file position rather than walking bv_page, and eventually replacing scatterlists with bvecq so crypto drivers can still prepend headers.

Bottom line: v10 is a feature series that also lands real netfs/NFS-adjacent bug fixes (unbuffered-write error return, progress-reporting tearing, over-read -EIO, NFS issue_read termination, cachefiles xattr UAF and ENOSPC). The NFS client still selects PG_private_2 and must follow the new combined prepare/issue fscache hooks. The only review comment this week is Couderc’s unanswered READ_PLUS question; Alcantara’s review, which Howells requested, has not yet appeared on the list.
