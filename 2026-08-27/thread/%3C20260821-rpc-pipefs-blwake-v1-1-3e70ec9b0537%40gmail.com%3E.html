RFC: lost wakeup in pNFS blocklayout device resolution

Summary

This week’s linux-nfs traffic opened a client-side bug-fix RFC, not a protocol change or new feature: FAN YE posted [PATCH RFC] pnfs/blocklayout: fix lost wakeup in bl_resolve_deviceid(), targeting a hang in the pNFS block layout driver’s userspace device-map upcall path.

The report is a classic lost-wakeup race in fs/nfs/blocklayout/rpc_pipefs.c. bl_resolve_deviceid() queues the current task on nn->bl_wq and calls rpc_queue_upcall(), but it only then sets TASK_UNINTERRUPTIBLE. If blkmapd answers on another CPU in that window, wake_up() from bl_pipe_downcall() sees a still-runnable waiter; the later set_current_state() overwrites that wakeup, and schedule() never returns. Because the waiter already holds nn->bl_mutex, the stall is not local:

"The caller holds nn->bl_mutex, so every later blocklayout device resolution blocks behind it."

Ye’s four-line RFC therefore moves the uninterruptible state assignment before the upcall and restores TASK_RUNNING on the error path. The author notes that of the four rpc_queue_upcall() callers this is the only open-coded waiter; __cld_pipe_upcall() in fs/nfsd/nfs4recover.c waits on a completion and cannot lose the wakeup this way. The change is tagged Fixes: fe0a9b740881 ("pnfsblock: add device operations").

The hang has not been observed on a production pNFS mount. Reproduction was synthetic: a VM debugfs hook into bl_resolve_deviceid(), a fake blkmapd, and an mdelay() to widen the race. In that setup the first caller sticks in D state at schedule(), and the next caller then blocks on nn->bl_mutex; both symptoms disappear with the patch.

The RFC is explicitly seeking design feedback rather than claiming the reorder is the last word. Ye asks two questions of the NFS client maintainers:

"Would you rather have bl_wq converted to a completion, like __cld_pipe_upcall() in fs/nfsd/nfs4recover.c?"

and

"rpc_queue_upcall() calls dput(). If the pipe were unlinked meanwhile, that could sleep with the task already in TASK_UNINTERRUPTIBLE. Is that acceptable here?"

The second question is the more interesting client-path hazard: putting the task to sleep before rpc_queue_upcall() means any blocking dput() on an unlinked rpc_pipefs dentry would run while !TASK_RUNNING. That is exactly the sort of atomic-sleep issue CONFIG_DEBUG_ATOMIC_SLEEP is meant to catch, and it is why the posting is labeled RFC rather than a straightforward one-liner.

No replies landed on this thread during the week. The discussion therefore ends where it started: a well-described client hang, a minimal proposed fix, and two open questions about whether the wait should be rewritten as a completion and whether sleeping inside rpc_queue_upcall() with TASK_UNINTERRUPTIBLE is acceptable. Until those are answered, the blocklayout device-resolution path remains the only rpc_queue_upcall() waiter that can lose a wakeup and then serialize every subsequent resolution behind nn->bl_mutex.
