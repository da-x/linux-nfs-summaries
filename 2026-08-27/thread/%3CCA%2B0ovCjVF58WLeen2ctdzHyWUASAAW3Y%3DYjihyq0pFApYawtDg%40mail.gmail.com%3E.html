Syzkaller hits stack-queued rpc_pipe_msg in nfsd cld upcall

Summary

This week’s linux-nfs traffic closed with a bug report, not a patch, a protocol change, or a new feature. Farhad Alemi of ASU’s SEFCOM lab mailed Chuck Lever and Jeff Layton a syzkaller crash on Linux 7.1-rc5 whose subject already states the diagnosis: [BUG] sunrpc: rpc_pipe_msg left queued on a stack frame (nfsd cld upcall). There are no replies in-window. The thread therefore ends as an unacked, unreproduced-by-maintainers KASAN finding against the NFSD client-tracking (cld) upcall and the shared SUNRPC rpc_pipefs queue.

That matters to NFS client work this week even though the crashing caller is nfsd. rpc_queue_upcall() and struct rpc_pipe_msg are the same pipefs machinery the client uses for idmap, gssd, and pNFS blocklayout device maps. Two days earlier, FAN YE’s blocklayout lost-wakeup series treated __cld_pipe_upcall() in fs/nfsd/nfs4recover.c as the safe waiter — the completion-based pattern v2 copied. Alemi’s report says that model path can still leave a stack-allocated rpc_pipe_msg on the pipe’s list after the waiter’s frame is gone.

What landed on the list

Alemi wrote that the crash came out of syzkaller, not a production nfsd workload:

"While fuzzing Linux 7.1-rc5 with syzkaller, as part of research at ASU's SEFCOM lab, we hit the crash below."

The in-list splat is a KASAN vmalloc OOB while validating a list insert, which is the signature of walking a list_head that still points into a returned kernel stack (KASAN-instrumented stacks live in vmalloc space; ffffc900… is that range):

"BUG: KASAN: vmalloc-out-of-bounds in __list_add_valid_or_report+0x6a/0x130 lib/list_debug.c:32"

"Read of size 8 at addr ffffc90007027950 by task syz.0.96/13066"

The ingested body cuts off after print_address_description(). Alemi pointed maintainers at the full reports rather than pasting the rest of the trace:

https://github.com/farhad-alemi/public_bug_reports/tree/main/118-nfsd-cld-stack-rpc_pipe_msg-left-queued/

and offered to close the loop:

"Our reproducer.c is available upon request."

"Happy to test a patch if that would help."

No one asked for the reproducer, and no patch was posted.

The bug class, as named in the subject

The subject is the technical claim. NFSD’s NFSv4 client-tracking upcall (__cld_pipe_upcall() / friends in fs/nfsd/nfs4recover.c) builds a struct rpc_pipe_msg on the stack, queues it with rpc_queue_upcall(), and waits on a completion for nfsdcld (or the legacy nfsdcltrack helper) to read the pipe and write a downcall. That is legal only if every path that returns from the upcall also unlinks the message. If the waiter is interrupted, the pipe is closed, or an error path returns while msg is still on pipe->in_upcall / pipe->pipe, the next rpc_queue_upcall() or pipe-release list walk dereferences msg->list after the stack frame is dead. __list_add_valid_or_report() is exactly where CONFIG_DEBUG_LIST / KASAN notices that.

This is a use-after-return of a stack list node, not an NFS protocol issue and not a new upcall feature. The user-visible server impact, if the race is hit outside the fuzzer, is a kernel oops or memory corruption on the nfsd cld pipe during client-id tracking (reboot recovery, nfsdcld restarts, pipe close). The client-visible impact is indirect: the same SUNRPC pipefs queue is what idmapd, rpc.gssd, and blkmapd sit on.

Same-week client context: cld was the “good” waiter

The report did not mention the blocklayout series, but the two threads now sit next to each other on the list and they share the upcall primitive.

FAN YE’s RFC argued that of the four in-tree rpc_queue_upcall() callers, bl_resolve_deviceid() was the only open-coded wait-queue waiter, and that __cld_pipe_upcall() “waits on a completion and cannot lose the wakeup this way.” v2 then replaced the blocklayout wait with a completion, explicitly “the way __cld_pipe_upcall() waits,” after v1’s set_current_state() reorder proved unsafe because rpc_queue_upcall() can sleep in dput().

Alemi’s KASAN report does not contradict that wakeup analysis. Completions still do not make a stack rpc_pipe_msg safe if the function can return with the message linked. The client takeaway from this week is therefore sharper than either thread stated alone:

  • Blocklayout’s hang was a lost wakeup plus a stale bl_mount_reply; v2’s completion rewrite is the right wait style, and it still needs the message lifetime to match the wait.
  • NFSD cld, the pattern v2 copied, is now accused of the complementary pipefs bug: the rpc_pipe_msg itself is stack-backed and can remain queued.
  • Any other rpc_queue_upcall() caller that embeds rpc_pipe_msg on the stack (idmap, gssd, blocklayout) should be checked for the same unlink-on-all-return-paths rule. A heap-allocated message, or an explicit rpc_purge_list() / list_del_init() on every abort, is the usual fix for this class.

No one on the list has yet connected those two threads.

Where things stand

  • Kind of change: bug report against SUNRPC rpc_pipefs and the NFSD cld upcall. Not a feature. Not a protocol change. No patch.
  • NFS client angle: shared rpc_queue_upcall() infrastructure; this week’s pNFS blocklayout fix treated cld as the reference waiter. Client idmap/gssd/blocklayout paths that stack-allocate rpc_pipe_msg are in the same blast radius until the lifetime rule is audited.
  • Evidence: syzkaller on 7.1-rc5, KASAN vmalloc-OOB in __list_add_valid_or_report, full traces off-list on GitHub, reproducer offered but not posted.
  • Maintainer response: none from Lever, Layton, or anyone else before the week closed. The report landed late on 2026-08-27.

Until someone asks for the reproducer or posts a pipefs unlink/rpc_pipe_msg lifetime fix, the cld upcall remains a fuzzer-crashing stack-use-after-return on the shared SUNRPC pipe queue, and the client-side blocklayout series is still modeling its wait on that same path.
