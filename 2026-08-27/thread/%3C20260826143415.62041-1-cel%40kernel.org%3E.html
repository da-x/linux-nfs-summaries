Chuck Lever v2-patches xprtrdma WRITE-chunk READ corruption on short NFSv3 headers

Summary

This is a client-side bug fix in xprtrdma, not a protocol change and not a new feature. Chuck Lever posted v2 of the RPC-over-RDMA transport patch that stops a legal NFSv3 READ3resok from returning stale receive-buffer bytes in place of file data. There were no replies in this thread during the week: no Reviewed-by, no Tested-by, no Ack. The posting is the iteration on yesterday’s RFC, which itself answered Rakesh Bhargava’s NetApp report of silent 84-byte READ corruption on vers=3,proto=rdma.

Brief recap: the RFC already named the fault

The RFC thread (summarized separately) established the client-visible bug. RFC 1813 lets a server send READ3resok with attributes_follow = FALSE, omitting the 21-word fattr3. The Linux NFS client still reserves head-iovec space for the largest possible READ reply, so that inline RDMA message lands 84 bytes short of the reservation. rpcrdma_inline_fixup() then points the head iovec at the received message but leaves iov_len at the reserved size. xdr_realign_pages() / xdr_shrink_bufhead() treat the extra bytes as payload and slide them into the page list, overwriting the first 84 bytes of an RDMA Write that had already landed correctly.

On an ordinary NFSv3 mount only the first READ is wrong, because nfs3_read_done() records the shorter header. A FlexFiles NFSv3 data server corrupts every READ, because the layout driver installs its own completion callback and that bookkeeping never runs. The regression is cb0ae1fbb2f5 (“xprtrdma: Do not update {head, tail}.iov_len in rpcrdma_inline_fixup()”), which dropped the length adjustment while repairing krb5p reply decoding.

What v2 actually changes

v2 keeps the RFC’s layering decision — shrink the head only when a Write chunk carried the READ payload — and tightens the length math. Lever’s changelog is explicit:

"Reduce the head iovec to the inline header bytes received."

"Exclude a Responder's implicit XDR roundup from that length."

The RFC reduced the head to “the number of bytes actually received.” That is too coarse: an RPC-over-RDMA responder may pad the inline message to an XDR 4-byte boundary, and those pad bytes are not NFS header. Feeding them into head.iov_len would still leave xdr_realign_pages() with extra bytes to shove into the page list. v2 therefore sets the head to the inline header bytes, not the raw receive length, and strips the responder’s implicit roundup before that assignment.

The commit message restates the corruption path in the same terms as the RFC, now with the Write-chunk scope as the actual fix:

"rpcrdma_inline_fixup() points the head iovec at the received message but leaves its length at the reserved size, so it runs past the header into stale receive buffer content. xdr_realign_pages() then shifts those bytes into the page list, and the READ returns transport data where READ payload belongs."

And the FlexFiles blast radius, which is why this is not a one-shot first-READ curiosity:

"nfs3_read_done() records the shorter header size, so on an ordinary NFSv3 mount, only the first READ is corrupted. However, the FlexFiles layout driver installs its own completion callback, so every READ from a data server is corrupt."

The krb5p invariant is unchanged from the RFC. GSS integrity/privacy transforms the payload and therefore cannot use a Write chunk; restoring the length shrink only on the Write-chunk path leaves cb0ae1fbb2f5’s krb5p repair alone:

"An auth flavor that transforms the payload cannot use a Write chunk, so scoping it to Write chunks leaves krb5[ip] alone."

The code change is still a single-file edit of net/sunrpc/xprtrdma/rpc_rdma.c (14 insertions, 2 deletions versus the RFC’s 10-line addition). Credits are the same: Fixes cb0ae1fbb2f5, Reported-by Bhargava, Closes the NetApp bug mail. The RFC’s “Compile-tested only” disclaimer is gone from v2; Lever does not claim a runtime Tested-by either.

Why the length tweak matters for the NFS client

This is the important client-transport invariant the RFC left slightly loose. After rpcrdma_inline_fixup():

  • The RDMA Write payload already sits in the page list and must not be touched.
  • The XDR decoder must see a head whose length is exactly the NFS/RPC header that arrived inline, so xdr_read_pages() does not invent an 84-byte “payload” from recycled receive-buffer junk.
  • Implicit XDR roundup on the wire is padding, not header. Counting it as header would reintroduce a (smaller) realign into the pages.
  • krb5i/krb5p replies still need the reserved {head,tail}.iov_len that cb0ae1fbb2f5 preserved, because those flavors wrap the payload and never use a Write chunk.

Bhargava’s original arithmetic still applies as the field symptom: AUTH_SYS reserved head 128 bytes, actual inline RPC 44 bytes, difference 84 bytes = sizeof(fattr3). v2 does not change that diagnosis; it changes which received-byte count is written back into head.iov_len so the generic XDR layer stops treating the gap as file data.

Where v2 sits at week’s end

  • Kind of change: NFS client transport bug fix in xprtrdma. No ONC RPC or NFSv3 protocol change.
  • Symptom (unfixed in-tree until this lands): short NFSv3 READ reply headers (attributes_follow = FALSE) prepend 84 bytes of recycled receive-buffer junk onto an otherwise correct RDMA Write payload. Ordinary mounts lose the first READ; FlexFiles NFSv3 data servers lose every READ.
  • v2 vs RFC: same Write-chunk-only shrink, but the head is now the inline header bytes received, with the responder’s implicit XDR roundup excluded. That is the only technical evolution this posting adds.
  • This thread: v2 only. No review, no Tested-by, no Ack, no further respin in-window.
  • Credits: Reported-by Bhargava, Fixes cb0ae1fbb2f5, Closes the NetApp bug mail. Link-to-v1 points at the RFC.

Until a reviewed v2 is merged, NFSv3-over-RDMA clients — and especially FlexFiles DS READs — remain exposed to silent 84-byte payload corruption whenever a server omits post-op attributes.
