syzbot: hung nfsd_nrthreads waits on write_ports

Summary

Classification

This is a bug report, not a new feature and not a protocol change. syzbot filed a hung-task on the NFS server control plane: a write to /proc/fs/nfsd/threads blocked in nfsd_nrthreads() waiting for the global nfsd_mutex, while another syzkaller task already held that mutex in write_ports(). There is no NFS client code in the thread, and no human reply yet.

The client-visible damage is still real. While nfsd_mutex is pinned, thread-count changes, listener setup, export-cache upcalls, and nfsd teardown all sit in D-state. A client mount that still needs a live nfsd listener or an export-cache fill simply does not complete.

What landed this week

Late Thursday, 27 August, syzbot reported the hang on upstream HEAD 502d45774af0 (Merge tag 'clk-for-linus' …):

"INFO: task syz.5.1942:10848 blocked for more than 143 seconds."

"Unfortunately, I don't have any reproducer for this issue yet."

The kernel is a PREEMPT(full) syzkaller build, tainted L (SOFTLOCKUP). syzbot asked that any fix carry:

"Reported-by: syzbot+86a9d43d89b86def6d59@syzkaller.appspotmail.com"

This is the first list report that names the legacy /proc/fs/nfsd/threads write path as the waiter. Earlier August and July hung-task mail hit the generic-netlink family (listener_set, svc_export get/set-reqs, expkey, cache flush, version get). Here the victim is the old nfsctl transaction file: nfsctl_transaction_write → write_threads → nfsd_nrthreads.

Two hung tasks, one file, one mutex

The report actually names two tasks from the same process, both blocked for more than 143 seconds.

Task 10848 is the one in the subject line. It is writing the nfsctl threads file and is stuck taking nfsd_mutex in nfsd_nrthreads():

"nfsd_nrthreads+0x57/0xd0 fs/nfsd/nfssvc.c:252 write_threads+0x34a/0x600 fs/nfsd/nfsctl.c:445 nfsctl_transaction_write+0x106/0x1a0 fs/nfsd/nfsctl.c:114"

It already holds &f->f_pos_lock and sb_writers from ksys_write.

Task 10849 is a sibling thread of the same process, blocked in fdget_pos() on a read of fd 3 — the same nfsctl file, the same f_pos_lock that 10848 already owns. That is not a second nfsd bug; it is the usual f_pos_lock serialization on a shared file, piled on top of the mutex stall. A concurrent reader of /proc/fs/nfsd/threads cannot even enter VFS because the writer never drops f_pos_lock while it waits for nfsd_mutex.

The lock dump: write_ports is the holder

The interesting evidence is the system-wide lock listing, not the hung stack itself:

TaskSiteRole
syz.4.1396/9282write_ports (nfsctl.c:867)holds nfsd_mutex (plus f_pos_lock and sb_writers)
syz.5.1942/10848nfsd_nrthreads (nfssvc.c:252)waiting on nfsd_mutex (already holds f_pos_lock)
syz.5.1942/10849fdget_pos / ksys_readwaiting on the same &f->f_pos_lock

This is not an AB-BA deadlock between threads and ports. write_ports() — the /proc/fs/nfsd/portlist writer that creates nfsd listeners — has held the global nfsd_mutex long enough for the hung-task watchdog. nfsd_nrthreads() is an innocent waiter: it only takes that mutex to read nn->nfsd_serv->sv_nrthreads. Every other nfsd admin path that uses the same lock (netlink listener_set, export dumps, cache flush, thread get/set, nfsd unmount) queues behind that hold.

The NMI backtrace is a red herring for the NFS path. CPU 1 was in kcov/tracing during rt_sigreturn; the SOFTLOCKUP taint is incidental syzkaller noise. The nfsd story is entirely write_ports holding nfsd_mutex across a long operation while write_threads waits.

Same root cause as this week’s other nfsd hung-task mail

Hours earlier the same day, syzbot hung nfsd_nl_svc_export_get_reqs_dumpit behind nfsd_nl_listener_set_doit. That report named the netlink listener-set handler as the mutex holder. This report names the procfs equivalent: write_ports. Both paths create listeners and, for NFSv2/v3, register them with local rpcbind while still holding nfsd_mutex.

Jeff Layton’s diagnosis from the July cache-flush thread still applies almost verbatim:

"The hard problem here is that rpcbind registration is done synchronously under the nfsd_mutex. To talk to rpcbind, the kernel has to create a RPC client, which does a RPC ping first. If rpcbind is down then it can take up to a minute for the RPC ping to time out."

And:

"If we couple those delays with a long list of listeners, then it's easy to see how to reproduce the hang."

write_ports can add sockets one at a time through the nfsctl file; listener_set can batch many in one netlink message. Either way, a down or unresponsive local rpcbind turns each registration into a tens-of-seconds stall. Two such stalls is the 143-second hung-task watchdog syzbot observed again.

Neil Brown’s question from that earlier thread is still the open design fork:

"Why are we waiting a whole minute for a local service to respond? If it hasn't responded in 1 second, is it ever really likely to?"

This week’s related listener_set discussion already closed the short-term patch path. Slawomir Stepien’s AI-generated 128-listener cap was rejected as the wrong root cause (module upcalls are fast; rpcbind is not). After talking to Chuck Lever, Layton shifted the long-term plan from “make kernel rpcbind asynchronous” to moving most rpcbind SET/UNSET into userland, which would rev the nfsd netlink protocol:

"Right now, I don't have a timeline for working on this, so we're probably just going to have to suffer with more syzbot reports until that can come to fruition."

This nfsd_nrthreads report is that prediction coming true on the procfs threads file, the same day as the export-dump hang.

NFS client impact

There is no client patch here and no client-side bug to fix. The stall still sits on paths NFS clients actually use:

  • Thread and listener control. write_threads / nfsd_nrthreads is how nfsd is started and how the thread pool is resized. While it is stuck behind write_ports, new nfsd threads do not come up. NFSv4 clients never talk to rpcbind, but they still need a live listener and a responsive control plane.
  • Export-cache and mount. The same nfsd_mutex serializes export-table dumps and downcalls. A client mount of a just-exported path that still needs an export-cache fill will not finish for the duration of the rpcbind stall.
  • NFSv2/v3 discovery. The underlying rpcbind-under-mutex problem is specifically a v2/v3 client-visibility issue: nfsd will serve without a successful registration, but clients that find the server via portmap see a missing or stale table. The 143-second nfsd_nrthreads hang is the control-plane counterpart of that same stall.
  • Admin tools that still use /proc/fs/nfsd. Not every deployment has moved to nfsd netlink. rpc.nfsd, nfs-utils, and scripts that echo N > /proc/fs/nfsd/threads are the waiters in this dump. They hang even when the operator is only trying to start or resize the server, not add ports.

Chuck Lever’s VFS splice wrapper for duplicate fsnotify ACCESS on iterator READs, also in this week’s nfsd traffic, does not touch nfsd_mutex and does not mitigate this hang. Tim Menninger’s xprtrdma unmap/disconnect series is a client RDMA hang of a different kind and is unrelated.

Status

  • Type: hung-task / DoS bug in the nfsd procfs control plane (write_threads / nfsd_nrthreads waiting on write_ports). Same nfsd_mutex × synchronous rpcbind root cause as the July/August netlink reports; still unpatched.
  • Reproducer: none. syzbot is fuzzing concurrent nfsctl writes (ports vs threads) plus a same-file reader; the lock dump — write_ports holding, nfsd_nrthreads waiting, sibling read stuck on f_pos_lock — is the reproducer.
  • Human reply: none in this thread as of 27 August. The related listener_set thread already has a design discussion (shorten rpc_ping, drop the mutex around registration, or move rpcbind to userland) but no merged fix and, as of this week, no timeline for the userland protocol rev.
  • Fix tag requested: Reported-by: syzbot+86a9d43d89b86def6d59@syzkaller.appspotmail.com.

Until listener setup no longer holds nfsd_mutex across rpcbind I/O — or until that I/O fails in well under a second — every nfsd admin path, netlink or /proc/fs/nfsd, is another hung-task report waiting to happen. This week’s nfsd_nrthreads mail is that prediction hitting the threads file.
