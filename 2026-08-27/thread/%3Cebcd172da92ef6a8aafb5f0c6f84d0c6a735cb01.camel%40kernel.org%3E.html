Linus merges NFS client 7.3 pull, rebukes shortlog-as-changelog

Summary

This week’s last linux-nfs thread is not a single patch fight: it is Trond Myklebust’s merge-window [GIT PULL] of NFS client updates for Linux 7.3, Linus Torvalds’ rebuke of the tag message, and the kernel.org bot confirming the tree is in torvalds/linux.git. The pull is a mixed bag of stable-worthy client bug fixes, other correctness work, and a handful of features — not a protocol change of its own, though several of the features implement protocol bits the client had been missing.

The pull

On 26 August Myklebust asked Linus to fetch tags/nfs-for-7.3-1 from git://git.linux-nfs.org/projects/trondmy/linux-nfs.git, based on 7.2-rc7 and running through Junrui Luo’s NFSv4.1: fix layout segment leak on the pnfs_layout_process() forget path. The delta is 34 files, 534 insertions, 146 deletions, spanning fs/nfs/, fs/lockd/, net/sunrpc/, and a small workqueue helper.

Myklebust’s tag text grouped the work the way a maintainer shortlog does — “Stable fixes”, “Other bugfixes”, “Features and cleanups” — and that grouping is what Linus later objected to. For readers of this list, the interesting part is what actually shipped for the client.

Stable-class client bugs that landed

The tag’s “Stable fixes” list is the highest-severity client work in the window:

  • SunRPC use-after-free in __rpc_clnt_handle_event / __rpc_clnt_remove_pipedir (Luxiao Xu), plus a TLS handshake completion race (Jérémy Jean: wait for an in-flight client handshake callback before tearing the transport down).
  • NFSv4 delegation hash table leak when nfs4_server_common_setup() fails (Nate Prodromou).
  • lockd NULL dereference on lockowner allocation failure (Shuangpeng Bai).
  • pNFS layoutreturn sign error (Tim Menninger): pnfs_layout_need_return() compared pnfs_mark_layout_stateid_return() against unsigned EBUSY instead of -EBUSY, so busy segments never deferred a LAYOUTRETURN. Last week’s v1 over-corrected to == 0 and was NAK’d; v2 is what is in this pull. Myklebust’s earlier objection still defines the client contract:

    "This breaks the ability of the client to respond to layout recalls even when it does not think it holds a layout. That's a situation that can occur when using soft or softerr mounts."

  • NFSv4.1 layout-segment leak on the pnfs_layout_process() forget path (Junrui Luo) — the tip commit of the tag.

Those are the items Myklebust marked for stable. They are all client-side memory-safety, lifetime, or layout-state bugs, not wire-format changes.

Other client bug fixes

The rest of the bug list is the usual merge-window catch-up, but several entries are the ones operators will feel:

  • Delegations: Chuck Lever’s “return a delegation the client fails to record”; Guangshuo Li’s delayed-return list handling; nfs_inode_set_delegation() error paths now return the delegation they could not attach.
  • State / umount: Jia Zhu pins the superblock for active state owners (“Fix another state manager race with umount”); Ruoyu Wang frees the callback IDR on nfs4_alloc_client() failure; Zhansong Gao passes the right argument to nfs4_delete_lease().
  • pNFS / flexfiles: Benjamin Coddington’s trio — report clora_changed in the layoutrecall tracepoint, honor clora_changed so an unchanged recall does not cancel in-flight I/O, and report cancelled flexfiles I/O as a layout error. ZhangGuoDong plugs device leaks on blocklayout parse failure. Jeuk Kim’s NULL deref on NFSv4.0 data servers (cl_session is NULL; cl_lease_time stayed 0 and the renew manager busy-looped).
  • NFSv3 symlinks: Michael Nemanov’s ENXIO on O_CREAT of an existing symlink, and ZhangGuoDong’s “verify symlink inode before caching target” — fallout from nfs_atomic_open_v23().
  • SunRPC plumbing: missing NULL check in the rpcbind client; READ_ONCE/WRITE_ONCE on shared socket callbacks; uninitialised referring-call lists in the NFSv4.1 callback decoder; NFSv4.2 LAYOUTSTATS send-buffer exhaustion.

Arnaud Bonnet’s clear_and_wake_up_bit() conversions in the invalid-mapping and pNFS paths are the one cleanup that is really a wakeup correctness fix rather than style.

Features that rode along

Three client features are in the same tag, which is why calling the pull “fixes” undersells it:

  1. NFSv4.2 UNCACHEABLE_FILE_DATA (Tom Haynes + Mike Snitzer). The server can mark a regular file’s data uncacheable; the client then opens it O_DIRECT. That is the HPC concurrent-writer case from the in-flight IETF draft: cached write-behind on disjoint ranges produces write holes. The client only requests the attribute for regular files.
  2. NFS/localio (Snitzer): issue I/O and commit inline when not in a memory-reclaim context, and drop dead FLUSH_SYNC handling from nfs_local_commit.
  3. Flexfiles loosely coupled data servers (Jeuk Kim) plus keying the pNFS data-server cache on NFS version (Junrui Luo). RFC 8435 allows a DS that does not advertise EXCHGID4_FLAG_USE_PNFS_DS; the client had been ignoring ffdv_tightly_coupled and treating every DS as tightly coupled, so NFSv4.1+ I/O to a loosely coupled DS failed during setup. Version-keying the DS cache is the matching cache-identity fix.

None of those are wire-protocol inventions by Linux; they are the client finally implementing attributes and DS coupling rules the RFCs already described.

What this pull is not

Same-week client threads that did not make nfs-for-7.3-1 are worth naming so the merge is not mistaken for a full queue dump. Tim Menninger’s xprtrdma frwr_unmap_sync() / disconnect hang (v4, Chuck Lever Reviewed-by) is still sitting outside this tag. FAN YE’s pNFS blocklayout lost-wakeup rewrite (waitqueue → completion, plus a stale bl_mount_reply reset) has no maintainer Ack yet. NeilBrown’s negative-dentry RFC v3 — including the NFS verifier walk that now drops i_lock before d_for_each_positive_child(), the fix for Chuck Lever’s sleep-in-atomic splat on setattr/delegation-return — remains RFC/RFT. Those are next-cycle client bugs, not 7.3 material.

Linus: merged, with a lecture on the changelog

Linus pulled the tree, then spent the reply on the merge message rather than the code. He quoted the “Stable fixes” bullets and wrote:

"Please give a real summary of what has happened, not just a lightly edited git shortlog list sorted by "is stable cc'd or not"."

The subsystem prefixes were the first example:

"just to look at that first bullet point: why have that "SunRPC:" thing at all? It adds no value. This is a NFS client merge message, and the line goes on to say "fixes for the sunrpc client code"."

He said the same of “pretty much every single bullet entry,” and drew the line between merge overview and commit text:

"The merge message shouldn't be about some minor details - that's what the individual commits messages are for."

He did the light edit himself this time, and asked not to have to:

"I did some more light editing to at least make it slightly more readable, but it's still not exactly great. Please don't make me do that. Give me that overview of what happened and what matters. And it's ok to say "And misc fixes" for things that really doesn't matter and people who care should just look at the individual commits."

That is a process note for the NFS client maintainer, not a technical NAK. The code went in.

Conclusion

pr-tracker-bot closed the loop the same evening: tags/nfs-for-7.3-1 is merged as 73e3f0710014fe6d4ed98cfc02292f6121db7558 in torvalds/linux.git.

Classification: merge-window GIT PULL of Linux NFS client work for 7.3 — predominantly bug fixes (UAF, leaks, NULL derefs, layoutreturn sign error, delegation/state races, flexfiles v4.0 DS crash, NFSv3 symlink ENXIO), plus features (UNCACHEABLE_FILE_DATA, localio inline I/O, loosely coupled flexfiles DSes). No new NFS protocol is being invented here.

Disposition: merged. Linus’s remaining request is editorial: next pull wants a user-facing overview of what changed and why it matters, with “misc fixes” for the rest, not a stable-cc-sorted shortlog with redundant SunRPC: / NFSv4: prefixes. The client bugs that were still in review this week (xprtrdma unmap hang, blocklayout lost wakeup, negative-dentry verifier walk) will have to come in a later tag.
