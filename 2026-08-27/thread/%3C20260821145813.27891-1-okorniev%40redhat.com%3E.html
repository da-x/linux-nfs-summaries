libtirpc GSS principal-name one-byte overflow

Summary

This week Olga Kornievskaia posted a one-line-class bug fix for libtirpc’s server-side RPCSEC_GSS helper, with no replies yet on the list.

What landed this week

On 21 August, Olga Kornievskaia sent [PATCH 1/1] libtirpc: fix rpc_gss_get_principal_name to allocate memory correctly. The patch is a bug fix, not a protocol change and not a new feature: it closes a one-byte heap overflow in rpc_gss_get_principal_name() in src/svc_auth_gss.c. That helper is part of the server-side rpc_gss_*() API that user-space NFS (and other RPC) servers use when they import a GSS principal for RPCSEC_GSS.

The function builds a principal string of the form user, user/node, or user/node@secdomain, then hands the buffer to gss_import_name(). Kornievskaia’s diagnosis is that the payload length is already correct, but the allocation is not:

"The calculation for namebuf.length correctly accounts for the separator characters ("/" and "@") via the +1 in nodelen and secdomlen, but does NOT include space for the C string NUL terminator. The subsequent strcpy() and strcat() calls write a NUL terminator that overflows the buffer by exactly 1 byte in all cases"

She walks through the three construction paths and shows they all miss the same byte:

  • node=NULL, secdomain=NULL: allocates strlen(user_name), writes strlen(user_name) + 1
  • node="host", secdomain=NULL: allocates strlen(user_name) + strlen(node) + 1, writes one extra NUL
  • both non-NULL: same pattern, always one byte short

The important design constraint is that namebuf.length is supposed to be the GSS payload length, without the C terminator, because that length is passed into gss_import_name(). Inflating namebuf.length would paper over the overflow while corrupting the import. Kornievskaia is explicit about that split:

"The namebuf.length value is intentionally the payload length (without NUL) for the subsequent gss_import_name() call, so the bug is specifically in the allocation size, not in the length field itself. The proposed fix correctly introduces a separate alloclen = namebuf.length + 1 for the allocation while preserving namebuf.length semantics."

The code change is five lines in src/svc_auth_gss.c: compute alloclen = namebuf.length + 1, allocate that, and keep namebuf.length as the unterminated payload length. The patch tags Fixes: dec8d9775ded ("Finish server-side rpc_gss_*() APIs"), so this is a latent overflow in the completed server-side GSS API rather than a regression in this week’s NFS client work.

Why it matters for NFS

Even though the file lives in libtirpc, the function sits on the RPCSEC_GSS path that NFS servers (and some client-side user-space RPC consumers) use to turn a user/node/domain triple into a GSS name. A one-byte overflow on every principal import is the sort of heap smash that can show up as intermittent auth failures, allocator corruption, or a crash under GSS-authenticated NFS mounts. The fix is deliberately conservative: it does not change how principals are spelled, does not change the GSS import length, and does not touch the kernel NFS client. It only makes the C-string construction match the buffer that was actually allocated.

Status

This is a single-message thread. There is no Reviewed-by, Acked-by, or follow-up on the list in the week ending 27 August, and no earlier summary file for this root. The technical argument is fully stated in the original post; what remains is review and merge into libtirpc.

Bottom line: a real, always-on one-byte overflow in libtirpc’s GSS principal import, with a small, well-scoped allocation fix that keeps gss_import_name()’s length semantics intact. Await maintainer review.
