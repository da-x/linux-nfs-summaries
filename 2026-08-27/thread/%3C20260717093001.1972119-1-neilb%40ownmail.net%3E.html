Summary

nfsd lookup-open series held for v7.4 after extra linux-next soak

Type: merge-window status of an nfsd refactoring series (with earlier bug fixes). Not a protocol change and not NFS client code this week. The client-visible contract at stake remains NFSv4 OPEN-during-delegation-recall (NFS4ERR_DELAY).

This week's headline

Three mails on 24 August close the merge-window question hanging over NeilBrown's v5 nfs4_create_file() series: it will not land in this window. The patches stay in nfsd-testing for another month or two of linux-next exposure, then become the first items in nfsd-next for v7.4.

NeilBrown opened the week by noticing the series was missing from Chuck Lever's recent pull request and, he thought, from Chuck's tree:

"I notice this series wasn't in your recent pull request and they seem to have disappeared from your tree. What do you understand the status of these patches to be? I was hoping they would land this merge window."

Chuck Lever corrected the tree location and stated the maintainer decision, reached with Jeff Layton:

"I see them in nfsd-testing, where they’ve been since August 10."

"Jeff and I discussed this, and we’d like these to get another month or two in linux-next because they modify common paths. When v7.3-rc1 opens, they will be at the first patches in nfsd-next for v7.4."

NeilBrown accepted both the location and the delay, with a self-deprecating aside about missing the testing branch:

"uhmm... yes .... none some blind as .... :-("

"Ok, thanks. I should send you another patch to switch from do_lookup_open() to vfs_lookup_open() now that is in mainline."

That is the week's conclusion: no v7.3 merge, extra soak because the series touches common VFS/open paths, first in line for v7.4, and a follow-up to call the now-upstream vfs_lookup_open() instead of nfsd's local do_lookup_open() helper.

Bridging prior weeks (briefly)

On 17 July Neil posted v5 of the 18-patch series that untangles nfs4_create_file() toward a shared VFS lookup-open API. Jeff Layton Reviewed-by'd it the same day; Chuck applied all 18 commits to nfsd-testing. The series also carries two real correctness fixes (exclusive v4.1 create attributes, mounted-on-file CREATE handles). See the week-ending 23 July summary.

Patch 18/18 — v5 18/18, "nfsd: use do_lookup_open() for non-creating open requests too" — later failed pynfs DELEG8: non-creating NFSv4 OPEN stopped returning NFS4ERR_DELAY while a delegation recall was in flight, because do_lookup_open() does not run nfsd_open_break_lease(). Last week (17 August) Neil isolated the bug to that last patch, authorised dropping 18/18 only, and deferred teaching lease-break to the VFS path. See the week-ending 20 August summary.

This week's three messages do not re-litigate DELEG8. They answer the remaining process question: with 18/18's fate already decided, do patches 01–17 (and the planned vfs_lookup_open() conversion) still make this merge window?

The technical argument this week

The argument is about risk on common paths, not a new design. Chuck and Jeff want more linux-next time precisely because the remaining series changes how nfsd opens and creates files through VFS helpers that sit on the same lookup/open machinery syscall open() uses. That is the series' stated endgame — share code with the local open path so directory locking can later be relaxed — and it is also why a late merge-window pull is unattractive.

Neil's follow-up is the next concrete step on that endgame. Patch 17/18 extracted nfsd's VFS-specific open/create work into a local do_lookup_open(). Upstream now has the real vfs_lookup_open(), so nfsd should call that instead of keeping a private copy. He flags that conversion as a patch he still owes Chuck; it is not a claim that 18/18's lease-break hole is fixed. Last week's diagnosis still stands: stuffing nfsd's NFS4ERR_DELAY policy into the shared VFS helper is "possible though not trivial," and 18/18 remains the patch that must not go in until that policy exists.

This week's mails do not explicitly reconfirm that 18/18 has already been dropped from nfsd-testing. Chuck's "them … since August 10" predates the 12/17 August DELEG8 exchange. The practical effect of the delay is the same either way: nothing from this series is going upstream for v7.3, and Neil's next delta is the do_lookup_open() → vfs_lookup_open() switch, not a rushed rehabilitation of non-creating OPEN.

Why this still matters for NFS client development

No NFS client patches appear in this thread. The client-visible contract is unchanged from last week, and the extra soak is aimed at keeping it that way:

  • Linux NFS clients that OPEN a delegated file expect NFS4ERR_DELAY and retry. Patch 18/18 made the server (and therefore the client OPEN RPC) sit until the recall timed out — a hung open(2) / stuck mount rather than a clean retry. That is why 18/18 was pulled back.
  • Holding the rest of the series in linux-next for "another month or two" is the maintainer hedge on common open/create paths that every NFSv4 client exercises against this server (exclusive create attributes, mounted-on-file CREATE handles, FMODE_CREATED create detection).
  • Once nfsd calls mainline vfs_lookup_open(), server OPEN and local open(2) share more code. Until lease-break/NFS4ERR_DELAY is expressed on that shared path, unifying non-creating OPEN remains unsafe for any NFSv4 client that relies on DELAY during recall. pynfs DELEG8 is still the interoperability canary.

Client-side takeaway: do not expect this nfsd open/create refactor in v7.3; the DELAY-on-recall contract stays with the pre-18/18 path through v7.3, and the shared-VFS-open work is queued for v7.4 after more linux-next time.

Final conclusions (as of 27 August)

  • Classification: process / merge-window hold on an nfsd refactoring-and-bugfix series, not a new feature and not a protocol change.
  • This window: the series is not in the v7.3 pull. It remains in nfsd-testing for more linux-next time because it modifies common open/create paths.
  • Next window: first patches in nfsd-next for v7.4 once v7.3-rc1 opens.
  • Next code change: Neil will send a patch to call upstream vfs_lookup_open() instead of nfsd's do_lookup_open(). That does not, by itself, restore 18/18.
  • Still unresolved from last week: non-creating OPEN via lookup-open still lacks nfsd_open_break_lease() / NFS4ERR_DELAY; 18/18 stays out until that logic can live on the VFS path.
  • NFS client impact: no client code this week; the server-side DELAY contract Linux NFS clients depend on for OPEN-during-recall is preserved by not merging 18/18, and the rest of the refactor is deliberately delayed rather than rushed into v7.3.
