pNFS blocklayout lost-wakeup fix switches to a completion

Summary

Summary

This week’s linux-nfs traffic produced a second, more careful client-side bug fix for a hang in the pNFS block layout driver’s userspace device-map upcall path. Two days after an RFC that merely reordered set_current_state(), FAN YE posted [PATCH v2] pnfs/blocklayout: fix lost wakeup in bl_resolve_deviceid(), replacing the open-coded wait entirely.

The underlying race is unchanged. bl_resolve_deviceid() queues the current task on nn->bl_wq and calls rpc_queue_upcall(), but it only then sets TASK_UNINTERRUPTIBLE. If blkmapd answers on another CPU in that window, wake_up() from bl_pipe_downcall() sees a still-runnable waiter; the later set_current_state() overwrites that wakeup, and schedule() never returns. Because the waiter already holds nn->bl_mutex, the stall is not local:

"The caller holds nn->bl_mutex, so every later blocklayout device resolution blocks behind it."

v1 tried to close that window by moving the uninterruptible state assignment before the upcall. Ye now withdraws that approach outright:

"Apologies for v1: I sent it without checking that rpc_queue_upcall() can sleep, so the fix it proposed could not have worked."

That is the same hazard the RFC had flagged as an open question: rpc_queue_upcall() can dput(), and putting the task to sleep first means any blocking dput() on an unlinked rpc_pipefs dentry would run while !TASK_RUNNING. v2 therefore does what the RFC had asked maintainers about, and what __cld_pipe_upcall() in fs/nfsd/nfs4recover.c already does:

"Replace the open-coded wait with a completion, the way __cld_pipe_upcall() waits."

The patch is small: wait_queue_head_t bl_wq in struct nfs_net becomes struct completion bl_done; bl_pipe_downcall() and the abort path in bl_pipe_destroy_msg() call complete() instead of wake_up(); bl_resolve_deviceid() does reinit_completion() and wait_for_completion(). The change is still tagged Fixes: fe0a9b740881 ("pnfsblock: add device operations").

v2 also closes a second, independent client bug that the RFC left untouched. bl_mount_reply was never reinitialised, so a wakeup from bl_pipe_destroy_msg() (daemon closing the pipe unread) left the caller reading the previous resolution’s device number. Ye now resets reply->status before the upcall:

"The reply status is reset before the upcall so that the abort path in bl_pipe_destroy_msg() cannot leave the caller looking at the reply from an earlier resolution."

That stale-reply path, Ye writes, is

"a bug of its own, independent of the lost wakeup."

Reproduction remains synthetic. The hang has

"Not seen on a real pNFS mount."

Everything reported is from a VM where a debugfs hook calls bl_resolve_deviceid() with a fake nfs_server and a fake blkmapd answers every upcall in the same loop iteration. Three kernels, same initramfs, all built with CONFIG_DEBUG_ATOMIC_SLEEP, produced a four-row matrix that is the real news of this posting:

  • 5000 upcalls with no added delay: upstream hung twice (task stuck at the schedule() after set_current_state(), still holding nn->bl_mutex); both v1 and v2 were clean.
  • rpc_queue_upcall() forced to block 50 ms: upstream hung; v1 fell through and returned the previous device number because an msleep() at the dput() cleared task state; v2 was clean.
  • Upcall aborted by the daemon closing the pipe unread: upstream and v1 both returned a stale device; v2 returned 0 plus a warning.
  • DEBUG_ATOMIC_SLEEP: upstream quiet; v1 warned on the first upcall, before any race — "do not call blocking ops when !TASK_RUNNING; state=2 set at bl_resolve_deviceid"; v2 quiet.

That table is why v2 exists. The RFC reorder papered over the lost wakeup in the no-delay case, but it introduced an atomic-sleep warning and, once rpc_queue_upcall() actually slept, it turned a hang into a silent wrong device number. The completion rewrite is the only of the three kernels that is correct on every injected path.

No replies landed on this v2 thread during the week. The discussion therefore ends with a well-tested client hang fix, a second stale-reply fix in the same patch, and no maintainer Ack or review yet. Until that lands, the blocklayout device-resolution path remains the only rpc_queue_upcall() waiter that can lose a wakeup, serialize every subsequent resolution behind nn->bl_mutex, and, on pipe abort, hand back a device id from an earlier resolution.
