Chuck Lever RFC-patches xprtrdma READ corruption on short NFSv3 reply headers

Summary

This is a client-side bug fix, not a protocol change and not a new feature. Chuck Lever posted an RFC to net/sunrpc/xprtrdma/rpc_rdma.c after Rakesh Bhargava reported that a perfectly legal NFSv3 READ over RPC-over-RDMA can return stale transport bytes in place of the first 84 bytes of file data. There were no replies in this thread during the week. Lever followed up the next day with a tightened PATCH v2 as a separate posting; that v2 is noted only as the immediate successor.

What the client actually corrupts

The trigger is RFC 1813’s permission for a server to send READ3resok with attributes_follow = FALSE, omitting the 21-word fattr3. The Linux NFS client still reserves head-iovec space for the largest possible READ reply, so the inline RDMA message lands 84 bytes short of that reservation. Lever’s diagnosis is the same path Bhargava walked on a 5.14 RHEL client doing 4 KiB direct reads, vers=3,proto=rdma:

"The client reserves room in the head iovec for the largest possible reply header, so the inline part of such a reply falls short of that reservation by the 21 words of the omitted fattr3. rpcrdma_inline_fixup() repoints the head iovec at the received message but leaves its length at the reservation, so the last 84 bytes of the iovec cover stale receive buffer content."

From there the generic XDR layer does the damage. xdr_realign_pages() sees a head longer than the decode cursor and treats the extra bytes as payload; xdr_shrink_bufhead() slides them into the page list, overwriting the first 84 bytes of an RDMA Write that had already landed correctly. Bhargava’s numbers make the arithmetic concrete: for AUTH_SYS the reserved head is 128 bytes, the actual inline RPC is 44 bytes, and 128 − 44 = 84, exactly sizeof(fattr3).

The client-visible blast radius depends on which completion callback runs:

"An ordinary NFSv3 mount corrupts only the first READ, because nfs3_read_done() records the shorter header size for subsequent calls. A FlexFiles NFSv3 data server corrupts every READ, because the layout driver installs its own completion callback and nfs3_read_done() skips that bookkeeping."

That FlexFiles path is the production sting. pNFS data-server READs never learn the shorter header, so every RDMA READ from the DS is wrong, not just the first one after mount. Bhargava put it the same way in the original report: “With a FlexFiles NFSv3 DS, the shorter DS header size is not learned, allowing the issue to occur repeatedly.”

Why xprtrdma is the right layer, and why krb5p is left alone

This is not an NFS protocol bug and not an NFSv3 decoder bug. The decoder correctly skips fattr3 when attributes_follow is false. The fault is that rpcrdma_inline_fixup() advertises a head length the receive buffer does not contain. Lever traces that to commit cb0ae1fbb2f5 (“xprtrdma: Do not update {head, tail}.iov_len in rpcrdma_inline_fixup()”), which dropped the length adjustment while repairing krb5p reply decoding.

The RFC restores the adjustment, but only when a Write chunk carried the payload:

"An authentication flavor that touches the payload cannot use a Write chunk, so restoring the adjustment only for Write chunks leaves the krb5p repair alone."

That is the important client-transport invariant: GSS integrity/privacy must still see the reserved head/tail lengths that cb0ae1fbb2f5 preserved, while RDMA Write-chunk READs (the NFSv3/FlexFiles case) must shrink the head to the bytes actually received so xdr_read_pages() does not steal from the page list.

The patch itself is a 10-line addition to rpcrdma_inline_fixup() in net/sunrpc/xprtrdma/rpc_rdma.c. Lever marked it compile-tested only:

"Note: Compile-tested only."

Where the RFC sits at week’s end

  • Kind of change: NFS client transport bug fix in xprtrdma. No ONC RPC or NFSv3 protocol change.
  • Symptom: short NFSv3 READ reply headers (attributes_follow = FALSE) prepend 84 bytes of recycled receive-buffer junk onto an otherwise correct RDMA Write payload. Ordinary mounts lose the first READ; FlexFiles NFSv3 data servers lose every READ.
  • This thread: RFC only, no review, no Tested-by, no Ack. Credits: Reported-by Bhargava, Fixes cb0ae1fbb2f5, Closes the NetApp bug mail.
  • Immediate follow-up (separate thread): Lever’s v2 the next day keeps the Write-chunk-only shrink, but reduces the head to the inline header bytes received and excludes the responder’s implicit XDR roundup from that length. That is the version that actually iterates on the RFC; this posting is the diagnosis and the first cut.

Until a reviewed v2 lands, NFSv3-over-RDMA clients — and especially FlexFiles DS READs — remain exposed to silent 84-byte payload corruption whenever a server omits post-op attributes.
