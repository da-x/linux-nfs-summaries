READ_PLUS hole reporting still missing on Linux 7.2 NFSD

Summary

This week’s traffic is a bug-fix / regression revival, not a new feature or protocol change. Aurélien Couderc reopened a year-old complaint that Linux NFSD’s NFSv4.2 READ_PLUS no longer reports sparse-file holes, and Chuck Lever answered that the current data-only replies are intentional and spec-compliant. There is no patch, no client-side code change, and no consensus that a kernel bug still exists.

Brief background (October 2025)

The thread began as Dai Ngo’s nfstest_dio patch to issue READ_PLUS whenever nfs_version >= 4.2. Trond Myklebust immediately flagged the client-test assumption:

"READ_PLUS is (like all NFSv4.2 features) optional to implement. As such, you really should expect that a server implementation is perfectly within its rights to return NFS4ERR_NOTSUPP, in which case the client should fall back to using READ."

Dai agreed to probe server support rather than hard-wire Linux NFSD. Couderc then hijacked the thread with a production regression: Linux 5.10 READ_PLUS reported holes; Linux 6.12 reported only data.

"FYI READ_PLUS is BROKEN for sparse files. It was working in Linux 5.10, but as soon as we switched to Linux 6.12 it reported only data and no holes in sparse files. We're back to Linux 5.10 and cannot upgrade because of this."

He also argued that sparse-file support needs a pathconf()-style probe of SEEK/READ_PLUS. In late October he asked where to file a server bug; Chuck pointed him at Bugzilla (File Systems / NFSD). That is where the thread sat until this week.

This week: still no holes on Linux 7.2

On 24 August, Couderc pinged the list with a one-line reminder:

"Reminder: This is still broken in Linux 7.2."

Chuck Lever refused to treat that as a bug report:

"Aurélien, "broken" is not an actionable bug report. It's a complaint."

He then restated the actual NFSD behavior and the reason it changed:

"Do you mean that NFSD returns READ_PLUS responses that contain only data segments, never holes? That is perhaps not optimal, but it is 100% spec-compliant, as far as I am aware."

"NFSD was changed to do this because there is no common race-free way to detect holes in files on Linux filesystems. If kernel VFS developers know of a way to do this, please reach out to me."

That is the key technical claim of the week: Linux NFSD still implements READ_PLUS, but it no longer emits hole segments. From the NFS client’s point of view, a READ_PLUS reply that is all data is indistinguishable from a dense file. Clients that used hole segments to skip zeros, punch local holes, or accelerate sparse copies therefore see a silent functional regression even though the on-wire operation still succeeds.

Couderc disputed the VFS framing and offered a lock-based workaround instead of a new VFS hole API:

"Why is this a job of the VFS? On the NFS server side? If someone wants a race-free hole listing he has to lock (shared lock) that file on the NFS client side, NFS server handles THAT lock. Problem solved."

No one from VFS, NFSD, or the NFS client replied after that. The thread ends with an unresolved design disagreement: Couderc wants hole-aware READ_PLUS restored (or at least a race-free hole listing under a client-held share lock); Lever treats data-only READ_PLUS as legal, safer, and blocked on a missing race-free VFS primitive.

Client-development impact

Nothing in this week’s mail changes Linux NFS client code. The practical consequences for client work are still:

  • Do not assume READ_PLUS implies hole maps. Linux NFSD 6.12 through 7.2 may advertise and complete READ_PLUS while returning only data segments. Sparse-file clients must still use SEEK_HOLE/SEEK_DATA (NFSv4.2 SEEK) or local heuristics if they need holes.
  • READ_PLUS remains optional. Trond’s 2025 fallback-to-READ rule still stands for tests and for any client that probes the operation.
  • No client bug fix landed here. The reported 5.10→6.12 behavior change is an NFSD policy change around hole detection, not a decoder bug in the Linux NFS client. Until NFSD emits holes again, or until a documented probe exists, client sparse-I/O optimizations that depended on READ_PLUS hole segments will keep seeing dense replies against Linux servers.

Conclusion

This week closed with diagnosis, not a fix. Lever confirmed the “only data, never holes” READ_PLUS replies as current, spec-compliant NFSD behavior driven by the lack of a race-free hole-detection API. Couderc still calls that a regression on Linux 7.2 and argues client-side file locks should be enough. No patch, no Bugzilla follow-up in-thread, and no NFS client change were proposed. Sparse-file READ_PLUS on Linux NFSD remains data-only.
