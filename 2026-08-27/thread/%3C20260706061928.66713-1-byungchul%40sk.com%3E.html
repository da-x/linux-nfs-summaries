DEPT v19: Lockdep Retrofit vs. Sibling Detector, Folio Handoff

Summary

DEPT v19: Lockdep Retrofit vs. Sibling Detector, Folio Handoff

Classification

This remains a new kernel feature under review: Byungchul Park's 40-patch DEPT (DEPendency Tracker) series, still at v19. Nothing this week is an NFS protocol change or an NFS client bug fix. The debate is architectural — whether DEPT should ship as a sibling of Lockdep, and how (or whether) folio PG_lock / PG_writeback waits can be modeled with existing Lockdep primitives. That question is nevertheless NFS-shaped: the client’s readahead, writeback, and RPC-completion paths are exactly the “lock in task context, unlock from interrupt or workqueue” pattern under discussion.

Bridging Prior Weeks (Briefly)

v19 landed on 6 July. Matthew Wilcox challenged per-page PG_locked tracking; Gary Guo flagged a Rust dept_key collision; Park confirmed an init_completion_dkey() plan and agreed to merge two Rust hygiene patches. The series then went quiet for five weeks. On 20 August, David Hildenbrand reopened the cover letter — asking why DEPT cannot be a CONFIG_LOCKDEP_* extension, and proposing a debug lockdep_map in struct folio — and Wilcox restated three reasons PG_lock is not a Lockdep-shaped object (page lifetime vs. lock semantics, owner-based hierarchy, task-acquire / IRQ-release with an I/O-submit hole). Park’s replies, and the subsequent Lockdep-vs-DEPT design debate, fall in this window. The only NFS-tree patch in the series remains the SUNRPC rcu_head relocation (patch 37/40, Reviewed-by Jeff Layton).

This Week's Activity (21–25 August)

Fifteen messages, clustered on 21 August and 24–25 August. The cover letter, not any individual patch, is the battlefield.

1. Park answers Hildenbrand: classification, timestamps, unofficial support

Park opened the week by agreeing that folio locking rules belong to mappings, not pages, and that DEPT already uses lock-class style classification rather than a full map in every page:

"DEPT doesn't use a full map in each page but uses a minimum space for a timestamp in each to track when each starts to wait so as to use the recorded timestamp when the event occurs e.g. folio_unlock()."

He accepted Hildenbrand’s future struct folio allocation as “good news for lockdep. (And even for DEPT :)” but held the line on independence. Lockdep, he argued, tracks acquisition order; folio lock is special because it can be released from a context other than the acquirer. Retrofitting that into Lockdep is not a small extension:

"Focusing on only the dependency checking, the most parts of lockdep are for the tricky things, so the reusable parts are not that big."

His two reasons for a separate engine were (1) similar or less effort than a retrofit, and (2) stability risk — the argument Hildenbrand had already rejected. On maintainer buy-in he offered only an unofficial LPC hallway conversation:

"One of locking maintainers who I met in an LPC told me that he agrees with the direction of DEPT and supports DEPT, not officially tho."

"What he and other people are concerning w.r.t DEPT the most is, false positives, which is the most important issue for now."

His near-term plan is operational, not architectural: share DEPT’s true reports periodically on LKML, especially around folio locks.

2. Park answers Wilcox: three folio classes, annotate I/O submit

Thirty minutes later Park told Wilcox that the three properties Wilcox listed are classification, and that DEPT currently buckets folios into three global maps:

"1. folios in mm paths 2. folios in block device buffer (meta data) 3. folios in regular file cache"

He agreed Wilcox’s finer cut — “this folio belongs to this xfs file inode” rather than merely “this inode” — would be better, and called the current split “still a good start.” On the I/O-submit hole (locked folio never submitted, so it will never unlock), he proposed treating submit as the event that will eventually release folio_lock():

"Annotate the point submitting IO as an event for the folio_lock() to be released. That way, the issue above can be detected by DEPT."

"Again, DEPT can do every thing we need w.r.t. deadlock."

That last claim is the one the rest of the week spends dismantling.

3. Hildenbrand: lifetime is well-defined; four merge options

Hildenbrand pushed back on Wilcox’s lifetime argument: until folios are dynamically allocated, PG_locked still has a well-defined life between allocator hand-out and return, and debug kernels already spend memory on page_ext. He conceded the cross-context release is hard to squeeze into Lockdep, and that “Dept might be a more natural fit for this scenario.”

His second mail the same morning, to Park, asked the questions the series has not answered in public:

  • Where does DEPT store the per-page timestamp?
  • Is Lockdep impossible to extend for release in a different context, or merely expensive?
  • Can DEPT and Lockdep run at the same time?
  • Are false positives conceptual, or missing edge-case annotations?

He then laid out four paths and picked one:

"(1) Don't merge it and carry it OOT. Shame if it delivers real value. (2) Merge it … keeping it entirely separate from lockdep. (3) Integrate it with lockdep on a high level, giving us a single locking dependency checker, but mostly letting dept have a separate implementation. (4) Retrofit and extend lockdep to really have one mechanism."

"As the saying goes, it's hard to teach old dogs new tricks, but in the end taking care of two dogs is likely harder than only a single dog? :)"

"I tend to favor (4) (or 3 with possible future work to achieve 4), but I am not a locking maintainer, so really they have to voice what to do."

"I do see value in DEPT (even if the folio lock might be handled differently)."

4. NeilBrown: Lockdep already has a hand-off API

NeilBrown — the voice on this list who actually ships NFS locking — argued that neither Lockdep nor DEPT needs per-page maps. Lockdep needs one lockdep_map per class; all folio locks could share a global one. Cross-thread hand-off is already expressible:

"If you have some code that takes a lock and then hands it off to another thread, at the hand-off point you call lock_map_release(&the_lock_map) … Somewhere else some other task takes responsibility … That code then calls lock_map_acquire_try(&the_lock_map)."

"So you definitely can send lock dependency information between tasks with lockdep. I have only tried it in extremely simple cases … There may be — and probably are — more complexities involved with locking folios and passing them around. Maybe it is so complex that you need all the support that DEPT provides. But I'd like to see a coherent explanation of how the functionality offered by DEPT is clearly better."

That request — a coherent superiority argument, not a stability argument — becomes the week’s refrain.

5. Readahead, bios, and two page flags (24 August)

Hildenbrand mapped Neil’s hand-off onto the actual I/O path: readahead submits I/O and unlocks from interrupt via folio_wake_bit(folio, PG_locked) in folio_end_read(); writeback never unlocks on the I/O path and uses a dedicated flag instead. He repeated:

"Stating that lockdep is stable and should not be destabilized is not really a good argument."

Neil then gave the most concrete Lockdep-shaped design of the week. rhashtable bucket bit-spinlocks already share a single lockdep_map — existence proof that one map per lock is unnecessary. A lockdep_map in each struct address_space would be enough for file folios. “Submit the I/O” is a queue (folio → bio → device transmit queue). The hard part is cardinality:

"A small difficulty here is that a bio has multiple folios and they are all locked. I cannot see that lockdep has a concept of holding an arbitrarily large set of related locks. We could just tell lockdep 'I have some folios locked' or maybe enhance lockdep to allow 'I have N folios in address-space A with the highest offset being O'."

That last form would let Lockdep accept a later folio lock only if it is the same address space and a higher offset — the writeback/readahead ordering rule Wilcox has been asking for since July. Neil also split the two bits:

"PG_locked and PG_writeback are two different lock-bits with two different meanings. … So these are two separate, though related, lock bits that would both need to be tracked."

And he stated the process doctrine that hanging over v19:

"Replacing one big thing with another big thing is almost always rejected. Incremental development is the preferred approach. So developing something like DEPT to explore and learn and demonstrate a cool idea is great. … But the path from there to upstream acceptance is to take the lessons learned and to apply them one by one to the existing tools."

6. Wilcox and Neil on what Lockdep should actually be told

Wilcox said Neil’s bio/offset sketch is still too simple, and floated a callback (“I hold this lock, is that lock OK to acquire”), plus the history of the writeback split: before PG_writeback, the kernel held PG_locked throughout writeback; it was split so a page could be mapped into an address space while dirty data was in flight.

Neil declined arbitrary callbacks. Lockdep does not prove locking is correct; it proves the annotations are consistent. The right abstraction is not “this folio” at all:

"We don't want to tell lockdep that we are locking a 'folio'. The particular folio is irrelevant. Rather we want to tell lockdep that we are locking something at a particular offset of some array of folios."

vfs_lock_two_folios() is the same pattern as lock_two_nondirectories(): subclasses, plus a white lie when needed. His d_walk() example — drop a subclass, try_lock the primary on the same dentry, walk down the tree — is the NFS-adjacent lesson:

"This example highlights the idea that lockdep doesn't need to know exactly what is going on, it just needs to know about the stuff we want it to check."

Hildenbrand endorsed that incremental path as “likely the direction DEPT should take … unless there is something so fundamental different that it cannot possibly be integrated into lockdep.” A side note on readahead (Hildenbrand) wondered whether a PG_locked → something-else downgrade analogous to writeback’s PG_writeback could exist; he immediately marked it as not a proposal.

7. Park’s Friday replies: simultaneous, timestamps, hunting dog

Park finally answered Hildenbrand’s configuration question: DEPT and Lockdep can run at the same time. False positives are not a conceptual hole:

"It's because of lack of annotations for proper classification. As Willy mentioned, different call paths for various usages should be annotated with different classes throughout the kernel."

On the four options he reached for a counter-metaphor:

"Or it's better to train a unmatured hunting dog than to teach a pet dog, how to hunt, for better hunting, even though the pet dog might eventually become able to."

Hildenbrand declined the analogy (“I'm not sure whether 'pet dog' is the right analogy to lockdep”), and Park walked it back:

"Ah. Okay. I will be careful in using terms. I wanted to tell DEPT has its strength, lockdep has its own, and they are different."

To Neil’s hand-off sketch, Park granted the class-map point and then restated DEPT’s core claim: classes can be global, but DEPT still needs a per-page timestamp so folio_unlock() can be matched to the wait that started on that page. Ownership tracking is not the essence:

"It's certainly useful to track who owns the lock, but the essence, when it comes to deadlock detection, lies elsewhere. DEPT is based on the essence, that is, a deadlock comes from waits that are never awakened."

"It's an interesting approach if your goal is to track the owenership, but if the goal is for tracking dependencies.. well.. I'm not sure."

The week ends there: two models of what a deadlock is (never-awakened wait vs. inconsistent annotated acquisition order), no locking-maintainer Ack, no v20.

Evolution of the Discussion

The arc is revival → concrete Lockdep design → unresolved dual-engine stance:

  1. 21 August: Park answers last week’s two mails, defends a separate wait/event engine, lists three folio classes, and offers I/O-submit-as-event. Hildenbrand enumerates four merge options and prefers a Lockdep retrofit. Neil shows lock_map_release / lock_map_acquire_try as an existing cross-context path.
  2. 24 August: The discussion leaves the cover-letter FAQ and lands on real I/O: readahead unlock-from-IRQ, bio-sized sets of folio locks, PG_locked vs PG_writeback, and Neil’s process doctrine that big-for-big replacements are rejected.
  3. 25 August: Wilcox and Neil converge on what to tell Lockdep (address-space + offset, not per-folio objects; subclasses and white lies rather than callbacks). Park confirms simultaneous operation, attributes false positives to missing annotations, and refuses the ownership-hand-off model because DEPT’s essence is waits that never wake.

No code changed. No locking maintainer spoke on-list. Hildenbrand’s option (4) is the reviewer’s preference; Park’s preference remains a mature separate engine that eventually supersedes only Lockdep’s dependency-checking logic.

Significance for NFS Client Development

No NFS client patch moved this week. The design fight is still the one that will decide whether DEPT (or a Lockdep extension) is usable on the NFS client:

  • Readahead and writeback are the motivating I/O path. NFS client reads lock folios, submit READ RPCs, and unlock from RPC completion (softirq / workqueue) — Wilcox’s task-acquire / async-release pattern, Hildenbrand’s folio_end_read() path, Neil’s bio-as-queue. A detector that cannot mark the submit point will either scream about every NFS read or miss the “locked but never submitted” hang f2c817bed58d was written to contain.
  • Owner-based, range-based classification is the NFS-shaped design. Wilcox’s “all folios of this inode share locking rules” and Neil’s “N folios in address-space A with highest offset O” both map onto nfsi->vfs_inode.i_mapping. Park’s current three global classes (mm / block-buffer / regular file cache) are coarser than that; until DEPT (or Lockdep) tracks folio waits at the address_space / filesystem-type / offset level, NFS writeback and readahead reports will mix stale-wgen false positives with same-mapping false negatives.
  • PG_locked and PG_writeback are two locks. NFS writeback already lives in the split-flag world Wilcox recounted. Any detector that treats “the folio lock” as one object will mis-model the downgrade.
  • The SUNRPC rcu_head relocation is still the only in-tree NFS change, a compile-time kfree_rcu() accommodation for CONFIG_DEPT, not a runtime client fix. Nothing this week revisits it.

Final Conclusions (as of window close)

  • The series is still v19, still experimental, still without a locking-maintainer Ack.
  • Hildenbrand’s position: four options, prefer retrofit (4) or high-level integration then merge (3→4); dual similar mechanisms will confuse people; the stability argument is not accepted. He does “see value in DEPT.”
  • NeilBrown’s position: Lockdep already has class maps, subclasses, and a cross-task hand-off API; folio locks should be described as ranges of an address space, not as per-page objects; the upstream path is incremental lessons applied to Lockdep, not a sibling detector.
  • Wilcox’s position: PG_lock hierarchy is an owner property; I/O submit must be annotated; writeback’s PG_locked→PG_writeback split is historical evidence that these are wait/event bits, not mutexes. He did not bless DEPT’s current per-page wgen.
  • Park’s position: DEPT and Lockdep can run together; false positives are missing classification annotations, not a conceptual flaw; DEPT still needs a per-page timestamp; deadlock is a wait that is never awakened, which ownership-hand-off Lockdep does not capture; he will publish true reports and work folio classification in follow-ups.
  • No merge path, no code change, no NFS client bug fix this week. The open question is sharper than in July: either DEPT’s wait/event model is taught to Lockdep in pieces (the room’s preference), or Park demonstrates — with real folio-lock reports, not cover-letter FAQs — that the two engines are different enough that a sibling is justified.
