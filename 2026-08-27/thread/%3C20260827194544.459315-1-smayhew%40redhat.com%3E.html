pNFS SCSI layout can now build without block layout

Summary

Summary

This week’s linux-nfs traffic produced a client-side build-system change, not a protocol revision and not a runtime bug fix: Scott Mayhew posted [PATCH] nfs/blocklayout: allow pNFS SCSI layout without pNFS block layout, splitting the two pNFS layout types that have lived in a single blocklayout driver since SCSI layout was added on top of RFC 5663 block volumes.

The problem is a Kconfig coupling that has been quietly forcing SCSI-layout kernels to carry block layout and device-mapper as well. Until now CONFIG_PNFS_BLOCK was an unprompted symbol that pulled in both LAYOUT_BLOCK_VOLUME (RFC 5663) and LAYOUT_SCSI (RFC 8154) whenever NFS_V4 and BLK_DEV_DM were enabled. Mayhew’s commit message states the consequence directly:

"a kernel could not offer SCSI layout without also enabling block layout and device-mapper."

The patch keeps one shared blocklayoutdriver module — the read/write path, the extent tree, and the composite SLICE/CONCAT/STRIPE volume types stay common — and compiles only the type-specific leaves in or out:

  • block.c holds SIMPLE volume parsing, which still resolves the device through the userspace rpc_pipefs daemon. That path is block-layout only.
  • scsi.c holds SCSI leaf volume parsing plus persistent-reservation register/unregister. That path is SCSI-layout only.

Type-specific call sites in the shared core are now wrapped in IS_ENABLED(), and the helpers that crossed files (bl_map_simple, bl_parse_simple, bl_parse_scsi, bl_register_scsi, bl_unregister_scsi) become global with prototypes in blocklayout.h. Mayhew also drops an unused device-mapper.h include from that header and pulls in blkdev.h for the block_device / sector_t / BLK_OPEN_* definitions the header actually uses.

The Kconfig split is the part that matters for distributors. CONFIG_PNFS_BLOCK and a new CONFIG_PNFS_SCSI_LAYOUT become prompted booleans that only select which volume types are compiled in. Module linkage is carried by a single internal tristate, CONFIG_PNFS_BLOCK_LAYOUT_DRIVER, which follows NFS_V4. Mayhew is explicit about why the two user-facing options are booleans rather than tristates:

"making the two options booleans avoids a y/m mismatch where a built-in composite would silently drop a module-only object."

Default polarity flips as well: SCSI layout now defaults on and no longer depends on BLK_DEV_DM; block layout now defaults off. That is the client-facing policy change. A distro that wants pNFS SCSI on a machine with no device-mapper stack can finally enable SCSI layout without dragging in SIMPLE-volume parsing, the blkmapd pipefs daemon path, or DM.

The work is tagged Assisted-by: Claude:claude-opus-4-8 and signed off by Mayhew. The diff is an 8-file refactor (fs/nfs/Kconfig, fs/nfs/Makefile, the blocklayout Makefile, blocklayout.c, blocklayout.h, dev.c, plus the two new files), +300/−215, with the bulk of dev.c’s type-specific parsing moved into block.c and scsi.c.

No replies landed during the week. There is no Ack, no Reviewed-by, and no follow-up from other NFS client maintainers yet. The discussion therefore ends where it started: a well-motivated Kconfig decoupling of two layout types that share a driver, posted on the last day of the window, waiting for review.

This sits next to, but does not overlap, the other blocklayout client work this week — FAN YE’s lost-wakeup / stale-reply fix in bl_resolve_deviceid(). That series still targets the SIMPLE-volume userspace upcall path that this patch now compiles only when CONFIG_PNFS_BLOCK is on. If both land, SCSI-only kernels would no longer even build the pipefs waiter that Ye is repairing.
