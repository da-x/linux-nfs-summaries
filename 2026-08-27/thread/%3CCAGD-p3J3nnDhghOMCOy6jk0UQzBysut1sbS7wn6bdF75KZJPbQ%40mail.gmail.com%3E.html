Client sunrpc receive UAF wedges NFS after leaking TCP socket lock

Summary

This week brought a bug report, not a patch and not a protocol change: Kris Globtrotter described a Linux NFS client crash in the SUNRPC TCP receive path that is fatal rather than merely noisy. An xprtiod worker oopses inside xs_read_stream_request() while copying a reply, then exits still holding the TCP socket lock. Every later RPC piles up on that lock, the client starts logging nfs: server not responding against a live server, and only a reboot restores I/O. There were no replies on the list this week, so the report is still untriaged.

What failed

The host is a Proxmox VE kernel (7.0.14-12-pve, Ubuntu-7.0.0-31.31 plus later CVE cherry-picks) mounting NFSv4.2 hard from a TrueNAS SCALE in-kernel nfsd guest on the same machine, over a virtio bridge. nconnect is currently off. The workload is a high rate of small RPCs (~1100 concurrent torrents plus media scanners). Five crashes since 8 August, with MTBF now around two days:

"I'm hitting a crash in the sunrpc receive path that leaves the machine permanently unable to do any NFS I/O. Five occurrences since Aug 8, MTBF now around two days."

The oops is a supervisor instruction fetch at address 0x8 on workqueue xprtiod / xs_stream_data_receive_workfn. The call chain is the stream receive path into the socket:

xs_stream_data_receive_workfn → xs_read_stream → xs_read_stream_request → xs_sock_recvmsg → sock_recvmsg → inet_recvmsg → tcp_recvmsg → tcp_recvmsg_locked → skb_copy_datagram_iter → simple_copy_to_iter, with RIP 0x8.

Globtrotter’s reading is a use-after-free of the rpc_rqst while the reply is copied into the request receive buffer (an indirect call through a NULL struct at offset 8). There is no reproducer beyond “it happens every couple of days under this load.” The same two functions (xs_read_stream and xs_stream_data_receive_workfn) appear in both traces captured so far. The worker also exited with IRQs disabled.

Why the crash wedges all NFS traffic

The more important client-side consequence is not the oops itself but the lock that dies with the worker. tcp_recvmsg() takes lock_sock() before tcp_recvmsg_locked(), so the dead xprtiod thread still owns the socket. Hours later another rpciod worker is stuck in:

rpc_async_schedule → __rpc_execute → call_transmit → xprt_transmit → xs_tcp_send_request → tcp_sock_set_cork → lock_sock_nested → __lock_sock

Globtrotter’s diagnosis of that hang:

"Waiting on a lock whose owner no longer exists. Every subsequent RPC queues behind it, load climbs past 65, and "nfs: server not responding" appears even though the server is idle and responsive throughout (verified independently on every occurrence). umount -f, remount and service restarts are all futile since the state is in the socket. Only a reboot recovers."

That is a classic client transport-lock leak: the NFS mount’s TCP xprt is permanently unusable because the sock lock is not released on the oops path, and userspace recovery (umount -f, remount, service restart) cannot break a kernel socket lock whose owner is gone.

What was ruled out

The reporter already tried the usual red herrings:

  • Hardware: six hours of stressapptest over 103GB with zero errors and zero corrected ECC.
  • nconnect: the first occurrence was on a single transport, with the same __lock_sock signature, before nconnect was enabled.
  • The server: idle and independently responsive on every occurrence (same-host TrueNAS SCALE VM).
  • Taint: P O from ZFS used for local storage. ZFS is not on the crash path (sunrpc + TCP receive only); there is no proprietary GPU driver. Globtrotter acknowledged that taint may still limit how seriously the report is taken and cannot easily run a vanilla kernel, but offered to test patches because the machine reproduces on its own every couple of days.

First mitigation attempted this week: NFSv4 directory delegations were disabled, with a promise to report back. Full dmesg, mountstats, and sysrq-t were offered for the next occurrence.

Where things stand

This is an NFS client / SUNRPC bug report against the TCP stream receive worker. No maintainer has yet confirmed a use-after-free of rpc_rqst, named a commit, or posted a fix. The operational takeaway for client developers is the combination of:

  1. a NULL indirect call in xs_read_stream_request() while skb_copy_datagram_iter() fills the request buffer, and
  2. an xprtiod oops that leaks lock_sock(), after which xs_tcp_send_request() cannot proceed and the whole mount is wedged until reboot.

Until someone on linux-nfs maps the RIP-at-0x8 to a specific freed object (likely rpc_rqst or its receive xdr_buf/iov_iter ops) and makes the receive worker drop the sock lock on the failure path, this remains an unreproduced-but-repeating production hang for hard NFSv4.2 clients under a high rate of small RPCs.
