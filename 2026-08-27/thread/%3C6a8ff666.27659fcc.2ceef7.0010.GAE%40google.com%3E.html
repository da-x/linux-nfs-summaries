syzbot: hung dumpit in nfsd_nl_svc_export_get_reqs — export upcall waits on listener_set

Summary

Classification

This is a bug report — a hung-task / control-plane DoS on the NFS server generic-netlink family, not a protocol change and not a new feature. There is no NFS client code in the thread. The client-visible damage is that the export-cache upcall dump (get-reqs) stops answering while nfsd_nl_listener_set_doit holds the global nfsd_mutex, so a client mount of a path that still needs an export-cache fill simply does not complete.

No human has replied. The lock dump is nonetheless decisive, and it is the same class of failure Jeff Layton and Neil Brown diagnosed in July: synchronous rpcbind registration (including a ~60s rpc_ping) runs under nfsd_mutex, and netlink listener_set can batch many sockets in one call.

What landed this week

On Thursday, 27 August, syzbot reported a hung task on upstream HEAD f9a2394a2348 (Merge tag 'mm-hotfixes-stable-2026-08-06-18-4…'):

"INFO: task syz.1.4033:18710 blocked for more than 143 seconds."

"Unfortunately, I don't have any reproducer for this issue yet."

The kernel is a PREEMPT_{RT,(full)} syzkaller build, tainted L (SOFTLOCKUP). The hung task is blocked in mutex_lock_nested → nfsd_nl_svc_export_get_reqs_dumpit+0xf7/0xc40 at fs/nfsd/export.c:674, having entered via genl_dumpit / netlink_dump / sendmsg. It already holds the generic-netlink cb_lock and the per-socket nlk_cb_mutex-GENERIC, and is waiting for the global nfsd_mutex.

syzbot asked that any fix carry:

"Reported-by: syzbot+e7cea59fd1cb261746b5@syzkaller.appspotmail.com"

This is the first list report of the dump side of the original svc_export netlink path. July’s siblings hung the matching downcall (nfsd_nl_svc_export_set_reqs_doit), the export unlock/revoke path, and both directions of the newer expkey (nfsd.fh) upcall. get-reqs is the handler userspace (exportd/mountd) uses to pull pending export-cache requests after nfsd multicasts NFSD_CMD_CACHE_NOTIFY. A dump that sits in D-state for more than two minutes means those upcalls never complete.

The lock dump: listener_set still holds the mutex; shutdown is in the pile-up too

The interesting evidence is not the hung stack itself — it is the “Showing all locks held in the system” listing:

TaskHandlerRole
syz.7.3941nfsd_nl_listener_set_doit (nfsctl.c:1964)holds nfsd_mutex (plus cb_lock)
syz.1.4033 (the hung task)nfsd_nl_svc_export_get_reqs_dumpit (export.c:674)waiting on nfsd_mutex (already holds cb_lock and nlk_cb_mutex-GENERIC)
syz-executor/18969nfsd_shutdown_threads (nfssvc.c:576)waiting on nfsd_mutex while already holding s_umount from deactivate_super

This is not a classic AB-BA deadlock. cb_lock is an rwsem, so the two netlink tasks can hold it as readers. The hung dumpit is in D-state on the same coarse nfsd_mutex that listener_set is not releasing for more than 143 seconds. Every other nfsd netlink command — export-table dumps and downcalls, fh-cache upcalls, thread-count changes, cache flushes — queues behind that hold.

The new wrinkle versus the July reports is nfsd_shutdown_threads. That task already has exclusive s_umount from deactivate_super and is then taking nfsd_mutex. With listener_set sitting on the mutex across rpcbind I/O, nfsd teardown / nfsd-filesystem unmount is stuck as well. Anything else that needs s_umount on that superblock queues behind a control-plane op that has no business blocking unmount.

The NMI backtrace is a red herring for the NFS path. CPU 0 was in pv_native_safe_halt (swapper/0); the SOFTLOCKUP taint is incidental syzkaller noise. The nfsd story is entirely the listener_set / svc_export_get_reqs / nfsd_shutdown_threads pile-up on nfsd_mutex.

Brief bridge from July: same root cause, still unpatched

A month ago syzbot hung cache flush, then expkey-set-reqs / expkey-get-reqs, then the export-table downcall and the export unlock path, all on nfsd_mutex. Layton’s diagnosis from the cache-flush thread still applies here almost verbatim:

"The hard problem here is that rpcbind registration is done synchronously under the nfsd_mutex. To talk to rpcbind, the kernel has to create a RPC client, which does a RPC ping first. If rpcbind is down then it can take up to a minute for the RPC ping to time out."

And:

"If we couple those delays with a long list of listeners, then it's easy to see how to reproduce the hang."

This dump names nfsd_nl_listener_set_doit as the holder at the same nfsctl.c:1964 site as the 25 July svc_export_set_reqs report, so the mechanism does not need to be inferred. The new netlink listener_set handler can install many sockets in one call; each one may try to register with rpcbind while still holding nfsd_mutex. A down or unresponsive local rpcbind turns each registration into a ~60-second stall. Two such stalls is 143 seconds of hung-task watchdog — exactly what syzbot observed again.

Brown’s question from that thread is the design fork that is still open a month later:

"Why are we waiting a whole minute for a local service to respond? If it hasn't responded in 1 second, is it ever really likely to?"

Layton’s answer — a shorter timeout is necessary but not sufficient, because “even at 1s, you could easily cause a lockup warning with just a few hundred listeners” — is why this new report will not be fixed by touching nfsd_nl_svc_export_get_reqs_dumpit itself. The dump handler is an innocent waiter. The bug is that any nfsd netlink op, including the long-standing export-table dump, takes the same global mutex that listener setup holds across synchronous rpcbind I/O.

The open design options remain July’s three. None of those patches have been posted to the list as of this window:

  1. shorten rpc_ping (Brown’s first preference; Layton says necessary but insufficient);
  2. drop/reacquire nfsd_mutex around registration / the listener batch (Brown’s sketch);
  3. async registration off a serialized queue or callback chain (Layton’s preference), with care not to scramble rpcbind’s table.

NFS client impact

This is a server-side hang, but it sits on a path NFS clients actually use:

  • Export-cache upcalls. When nfsd has a pending export lookup, userspace is supposed to dump the request list via svc_export-get-reqs and reply via set-reqs. If the dumpit is stuck behind nfsd_mutex for minutes, those upcalls never complete. A client mount of a just-exported (or not-yet-cached) path simply does not finish. July already documented the matching downcall hang; this week closes the loop on both directions of the original svc_export netlink path.
  • File-handle cache is already a known victim. The July expkey-set-reqs / expkey-get-reqs reports hung both directions of the nfsd.fh upcall. A working mount needs the export table and the fh cache; either one being serialized behind listener_set is enough to stall. That is the same failure mode Paul Moore already hit as mount.nfs: Connection refused on a localhost mount after the expkey netlink conversion.
  • Listener / thread control, plus shutdown. nfsd_nl_listener_set_doit is the holder. This week’s dump also shows nfsd_shutdown_threads waiting on the same mutex while holding s_umount. Bringing nfsd up, adding sockets, or tearing it down can stall every other control-plane op — and now filesystem unmount of the nfsd superblock — for the duration of rpcbind I/O.
  • NFSv2/v3 discovery. The underlying rpcbind-under-mutex problem is specifically a v2/v3 client-visibility issue: nfsd will serve without a successful registration, but clients that find the server via portmap see a missing or stale table. The 143-second export-dump hang is the control-plane counterpart of that same rpcbind stall.

For NFSv4.2 clients the damage is more about control-plane latency than wire protocol: inter-server copy, state reclaim, and admin-driven export changes all assume the netlink family stays responsive. An export dump that sits in D-state for more than two minutes is not responsive.

There is no NFS client code change in this thread and no client-side bug to fix. The client-visible symptom is a server that stops answering export-cache dumps and, in the worst case, stops appearing in portmap and stops unmounting while listener_set holds the lock.

This week’s other nfsd traffic (Chuck Lever’s VFS splice wrapper for duplicate fsnotify ACCESS on iterator READs) does not touch nfsd_mutex and does not mitigate this hang.

Status

  • Type: hung-task / DoS bug in the nfsd netlink control plane, exposing the original svc_export dump path as another victim of nfsd_mutex. Same root cause as the July set-reqs / expkey / cache-flush reports; still unpatched.
  • Reproducer: none. syzbot is fuzzing concurrent netlink commands against a PREEMPT_RT kernel; the lock dump — listener_set holding, svc_export_get_reqs waiting, nfsd_shutdown_threads waiting with s_umount — is the reproducer.
  • Human reply: none in this thread as of 27 August. The related cache-flush thread already has a design discussion but no patches posted and nothing applied.
  • Fix tag requested: Reported-by: syzbot+e7cea59fd1cb261746b5@syzkaller.appspotmail.com.

Until the mutex is no longer held across rpcbind I/O — or until rpcbind I/O fails in well under a second — every nfsd netlink command, old or new, is another hung-task report waiting to happen. This week’s svc_export_get_reqs report is that prediction coming true on the export-table dump, a month after the diagnosis that already named listener_set as the long-hold site.
