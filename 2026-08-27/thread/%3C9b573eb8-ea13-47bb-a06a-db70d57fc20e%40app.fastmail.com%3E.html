xprtrdma hang: v4 polishes unmap/disconnect kdoc

Summary

Summary

This week’s linux-nfs traffic on Tim Menninger’s xprtrdma hang fix is a single posting: PATCH v4, sent as a reply to Chuck Lever’s v3 review. The thread remains a bug fix for a client-side FRWR race in the NFS/RDMA transport, not a protocol change or a new feature. No further review of v4 landed in-window.

Earlier this week, v3 absorbed Lever’s comment and layering nits and earned a Reviewed-by. v4 is the leftover documentation polish from that review, not another redesign of the hang fix.

The race, still the same hang

Menninger’s changelog still walks the four-step window that stalls rpciod when synchronous MR invalidation races with transport teardown:

  1. frwr_unmap_sync() samples r_xprt->rx_ep
  2. rpcrdma_xprt_disconnect() drains the QP
  3. frwr_unmap_sync() posts LOCAL_INV WRs after the drain
  4. No CQE arrives, so wait_for_completion() blocks indefinitely

The hung task remains:

"Workqueue: rpciod rpc_async_schedule [sunrpc] wait_for_completion() frwr_unmap_sync() xprt_rdma_free() xprt_release()"

The same pNFS restart loop is the reproduction: v7.2-rc6 under load with repeated data-server restarts. Without the fix, the hang hit twice in six attempts; with it, 200 cycles stayed clean. The stall has also been seen on v6.8 and v6.18.34. The Fixes: tag stays on e28ce90083f0 ("xprtrdma: kmalloc rpcrdma_ep separate from rpcrdma_xprt"), which made rx_ep a separately allocated, kref-managed pointer. Cc: stable@vger.kernel.org is unchanged.

The mechanics are still the v2/v3 model: rx_unmap_rwsem serializes the post-after-drain window; the reader drops the lock before waiting so disconnect can drain submitted work and deliver CQEs; rl_registered is rechecked after acquiring the rwsem in case disconnect already reset the request; the completion lives on struct rpcrdma_req, not the MR; the sampled endpoint is held across the wait so disconnect can destroy MRs without a separate active-unmap counter. The async path still needs no extra lock:

"frwr_unmap_async() runs inline from Receive completion processing. rpcrdma_xprt_drain() drains the Receive Queue before the Send Queue, so asynchronous LOCAL_INV Work Requests are submitted before Send Queue drain. frwr_unmap_sync(), however, runs from xprt_rdma_free() after the transport send lock has been released, so it is not ordered against disconnect."

What v4 actually changes

v3 already added rpcrdma_ep_release() so CM ID destruction stays in verbs.c, exported the get/release pair instead of get/put, used ep->re_id->qp directly while the rwsem read side is held, and narrowed the lock comments. Lever then signed off:

"The new block comments are wordy, and could be tightened. But no show-stoppers here:

Reviewed-by: Chuck Lever cel@kernel.org"

He left two documentation nits and one call-site reminder. v4’s changelog addresses the first two:

"Changes in v4:

  • Add kernel-doc comments for rpcrdma_ep_get() and rpcrdma_ep_release().
  • Convert the rpcrdma_ep_put() comment to ordinary comment style."

That matches Lever’s request that the new exported helpers grow kernel-doc, and that the now-static rpcrdma_ep_put() drop kernel-doc style. The patch carries Lever’s Reviewed-by forward.

The third leftover from the v3 review is not listed in the v4 changelog. Lever had asked that disconnect stop open-coding the put-then-destroy idiom:

"Nit: rpcrdma_xprt_disconnect() retains

if (rpcrdma_ep_put(ep))
    rdma_destroy_id(id);

but should call the new rpcrdma_ep_release() helper."

Whether that call site was silently folded into v4 is not documented in the posting. The wordy-comment remark is likewise unmentioned. Those are the only open questions v4 leaves on the table; the hang itself is not being re-argued.

Status

The client-side FRWR unmap/disconnect race is closed on the design Lever asked for: one transport-wide rwsem, existing request and endpoint objects for lifetime, no inflight counter. This week’s v4 is a kdoc polish pass on that Reviewed-by, not a new lifetime model. No ACK, NACK, or merge notice for v4 appeared before the window closed; the series is waiting on whether maintainers take v4 as-is or want the disconnect helper call site called out explicitly.
