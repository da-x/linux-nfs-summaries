Olga Kornievskaia clamps snprintf offsets in mount.nfs error formatting

Summary

Summary

This is a userspace bug fix in nfs-utils mount.nfs, not a protocol change and not a kernel NFS client patch. Olga Kornievskaia posted a one-patch series that stops utils/mount/error.c from treating snprintf()’s return value as a safe buffer index. There were no replies in this window; the change sits unreviewed at week’s end.

The defect is a classic C string-formatting trap on the NFS client mount helper. snprintf() reports how many bytes would have been written if the destination were large enough, not how many were actually stored. When a formatted error string overflows PATH_MAX—Kornievskaia’s example is a long progname—that unclamped return value is then used as an index into errbuf. The next snprintf() therefore writes past the end of the stack buffer.

She states the failure mode directly:

"snprintf() returns the number of bytes that would have been written if sufficient space were available, not the number actually written. When the formatted string exceeds PATH_MAX (e.g. due to a long progname), the return value exceeds the buffer size. Using that unclamped value as an index into errbuf produces an out-of-bounds pointer, and subsequent snprintf() calls write past the buffer."

The fix is small and local. She adds errbuf_clamp() to pin the running write position to the valid range of errbuf before it is used as an index, then applies that helper in the three text-based error formatters that compose messages piecewise:

  • rpc_mount_errors()
  • sys_mount_errors()
  • rpc_strerror()

The patch is 24 lines in utils/mount/error.c (22 insertions, 2 deletions) and carries:

"Fixes: 6e54f6179cb9 ("text-based mount.nfs: Add text-based error reporting function")"

That Fixes: tag is the historical context that matters for client-side mount.nfs: the overflow is not a new protocol path, it is a latent buffer-index bug in the text-based error reporter that has been in the tree since that commit. A long program name (or any other over-long prefix) on a failed RPC or sys mount is enough to walk off the end of errbuf.

Why it matters for NFS client development

mount.nfs is the userspace half of the Linux NFS client. These three helpers are what turn RPC and kernel mount failures into the human-readable diagnostics operators see on a failed mount -t nfs. An out-of-bounds errbuf pointer is not a cosmetic log glitch: it is memory corruption on the error path, which is exactly when administrators most need a trustworthy message (and when a crash would be hardest to diagnose).

The patch does not change NFS wire protocol, mount options, or kernel client code. It also does not add new error strings. It only makes the existing piecewise snprintf() composition safe when a fragment would have overflowed PATH_MAX.

Where things stand

  • Kind of change: bug fix in nfs-utils utils/mount/error.c.
  • Scope: clamp snprintf() return values before they are used as errbuf indices in rpc_mount_errors(), sys_mount_errors(), and rpc_strerror().
  • Review: none this week. No Reviewed-by, Acked-by, or maintainer comment landed in-window.
  • Merge status: posted 2026-08-25; still open at the close of the week.

Until someone reviews and applies it, a sufficiently long progname (or similarly oversized formatted fragment) can still drive mount.nfs off the end of its error buffer on a failed mount.
