Flexfiles device notifications and cache scaling for wide striped layouts

Summary

This week Benjamin Coddington posted PATCH v2 00/23, a 23-patch NFS client series that makes flexfiles CB_NOTIFY_DEVICEID handling work under live layouts, implements the RFC 8881 deviceID-deletion race recovery, and scales the pNFS device caches for wide striped deployments. The series is a mix of stable-bound bug fixes in the striped-layout I/O paths, a protocol-correctness feature for CHANGE/DELETE notifications, and cache scaling. Review has only just begun: NFS maintainer Anna Schumaker questioned the first patch’s 32-bit stripe-unit rejection, and the rest of the stack is still awaiting comments.

Why this series exists

Coddington’s cover letter frames the work around HammerSpace-scale striping:

"Striping deployments initially anticipate device counts scaling to 1024 or more devices, all in play for a single mount. This series makes the client's CB_NOTIFY_DEVICEID handling actually work under live layouts, implements the deviceID-deletion race recovery RFC 8881 asks for, and scales the device caches to that number of devices."

The client’s current CHANGE path is a no-op for in-flight I/O. RFC 8881 Section 12.2.10 exists so a server can re-point a deviceID without recalling layouts, but today the client only unhashes the cached device. References pinned inside layout-driver segments keep sending I/O to the old mapping until those layouts are freed.

v2 is a substantial rewrite of the v1 21-patch posting. Coddington prepended two standalone striped-layout fixes, redesigned the deferred-put contract so a shared device node can be unpinned more than once without list corruption, scoped the CHANGE/GETDEVICEINFO race epoch per-nfs_client, hardened the deviceid-ref collection walker, and fixed DELETE recovery so NFS4ERR_OLD_STATEID no longer confirms a delete of a still-live layout. A companion series, “NFS: size the LAYOUTGET reply buffer for wide flexfiles layouts,” remains independent.

The series was tested against reffs on a KASAN + lockdep + PROVE_RCU kernel. Coddington reports exact wire counts: W=2 placement is record-exact; each CHANGE variant produces exactly one re-resolve; a DELETE against a held layout ran Section 18.40.4 recovery while 436 I/O operations continued; and a 120-second storm of 30 triggers racing 4872 I/O operations drove 44 re-resolves and 24 race recoveries with FREE_STATEID 0 and LAYOUTRETURN 0.

Patches 1–6: latent striped-layout bug fixes (Cc: stable)

The first six patches are standalone client bug fixes, all tagged for stable.

PATCH 01/23 is the only patch reviewed this week. ff_layout_alloc_lseg() decodes stripe_unit as the protocol’s 64-bit value, but every consumer treats it as a u32: nfs4_ff_layout_calc_dss_id() divides with do_div(), and ff_layout_pg_test() copies it into a u32 first. Coddington:

"A value that does not fit is silently truncated, so the client stripes on a unit the server did not specify -- or divides by zero, if the low 32 bits happen to be clear."

The fix rejects a non-32-bit-fitting stripe_unit with -EINVAL so the layout is discarded and I/O falls back to the MDS, matching the existing fh_count check. That also moves the existing stripe_unit == 0 case off the -EIO exit it shared, which failed the I/O instead of falling back.

On 27 August, Anna Schumaker pushed back on the artificial 32-bit limit rather than the diagnosis:

"What would it take to update the users of stripe_unit that you mention above to treat it as a u64 instead of a u32? The calls to do_div() could be replaced with div64_u64() for example. It just feels a little more robust to me than artificially limiting ourselves to a 32-bit value."

That is the week’s only review comment. Coddington has not yet replied, so the design choice — reject oversized stripe units versus promote the I/O path to full 64-bit arithmetic — remains open.

The other five stable fixes have not been discussed:

  • 02/23 bounds the CB_NOTIFY_DEVICEID array count against xdr_stream_remaining() before kmalloc_objs(), so a bogus server count cannot ask the allocator for an enormous array.
  • 03/23 is a decoder alignment bug: decode_devicenotify_args() gated consuming ndc_immediate on cbd_layout_type instead of cbd_notify_type, so the flag was silently lost and a multi-item cnda_changes<> array misaligned after the first entry.
  • 04/23 stops truncating the file offset to 32 bits on the flexfiles read DS-selection path. The write path already passed the full 64-bit offset; above 4 GiB the read path was picking the wrong stripe’s data server for availability probing and coalescing.
  • 05/23 and 06/23 fix page coalescing straddling a stripe boundary. Flexfiles partitions on the absolute file offset (RFC 8435 Section 6) but coalesced on a segment-relative offset; files layout selected the DS relative to pattern_offset but coalesced relative to pls_range.offset. An unaligned segment let a coalesced I/O send bytes past the stripe boundary to the wrong data server.

Patches 7–15: CHANGE notifications under live layouts

This is the heart of the client feature work. The current pin — a single device-node pointer on the mirror, trusted for the life of the layout segment — cannot be re-pointed while I/O is in flight. Coddington rebuilds that contract before turning on the notification path.

Reference ownership. 07/23 replaces ff_layout_init_mirror_ds() with ff_layout_get_mirror_ds(), which returns the node with its own reference held and threads it through DS setup. 08/23 then carries that reference across each I/O on nfs_pgio_header and nfs_commit_data as ds_dev, so completion-path error tracking, availability marks, and connection-error deletes act on the node the I/O was actually sent to — not on a pointer a CHANGE might have already replaced. 09/23 does the same for layoutstats/layoutreturn XDR encode, which otherwise would become a use-after-free once the pinned node can be re-pointed.

RCU-managed pin. 10/23 annotates mirror->dss[dss_id].mirror_ds as __rcu. A v1 leftover is called out explicitly: ff_layout_mirror_prepare_stats() used rcu_dereference_protected() naming i_lock, which does not exclude the resolve path’s cmpxchg that runs from I/O submission. The pointer is still only set once per mirror lifetime in this commit; the annotation makes the subsequent in-place re-resolve safe.

The new layout-driver hook. 11/23 adds reresolve_deviceid plus a generic walker, pnfs_layout_reresolve_deviceid_byclid(). The deferred-put contract is the v2 redesign: a device node is a shared, refcounted object that one re-resolve pass can unpin more than once (multiple stripes, or multiple layouts over a common data server). A single list_head embedded in the node cannot express that — a second list_add() corrupts the list. Each dropped reference is now an nfs4_deviceid_put entry the hook allocates and the walker frees, taken before the pointer is exchanged out so an allocation failure leaves the reference pinned rather than lost. The walk is deliberately not gated on pnfs_layout_is_valid(): a header with NFS_LAYOUT_INVALID_STID set can still pin the stale node through draining lsegs, the cached device is already unhashed, and a subsequent LAYOUTGET can pick the surviving mirror back up.

12/23 implements the flexfiles hook: matching uses the raw deviceid decoded from the layout, so a never-resolved stripe is left alone, and an ERR_PTR sentinel from a previous failed resolution is cleared so the stripe retries GETDEVICEINFO. 13/23 is the dispatch: CHANGE unhashes the stale cache entry, then invokes the walker. Re-resolution is best-effort:

"A lookup that hit the cache just before the unhash can still install that node after the walk has passed the stripe, and the walk skips nothing else; such a stripe keeps the old mapping until the next notification. Nothing is left inconsistent by that -- the old mapping is a valid address the server published -- so the race is tolerated rather than serialised against."

ndc_immediate and the GETDEVICEINFO race. 14/23 honors ndc_immediate by marking the old node unavailable, but only if it is no longer hashed (hlist_unhashed_lockless() — the hook does not hold nfs4_deviceid_lock). A write whose DS connection is already up keeps using the old node until that I/O errors; a read skips the node while another mirror is usable. 15/23 tracks a per-nfs_client change epoch, bumped before the stale entry is unhashed. nfs4_find_get_deviceid() snapshots the epoch, discards a raced GETDEVICEINFO reply, and refetches — bounded by NFS4_DEVICEID_FETCH_RETRIES, because an unbounded retry would let a server drive GETDEVICEINFO traffic without limit. Scoping the epoch per client (v2 vs. v1’s global counter) means a CHANGE on one server no longer forces unrelated servers’ in-flight lookups to discard and refetch.

Patches 16–19: RFC 8881 Section 18.40.4 DELETE race recovery

Coddington is careful to say this is not faulty-server handling. Section 20.12 forbids DELETE while the client holds a referring layout, but that constraint is equally satisfied once the server has revoked those layouts — and a revocation is never announced. A conformant server therefore reaches this path; the client’s view of which layouts are live is simply older than the server’s.

16/23 adds layout_references_deviceid plus two walkers: a boolean existence query and a collection walker that pins matching headers, grabs inodes, and snapshots layout stateid and cred under i_lock so the caller can issue sleeping RPCs. v2 hardens this: allocate the ref only after a layout matches; move pnfs_put_layout_hdr() out of the RCU read-side (it can send a layoutreturn and sleep); report a partial list as -ENOMEM / -EAGAIN rather than a short list the caller would read as “no references.” The header-reference argument now rests on NFS_I()->layout == lo under i_lock, not on NFS_LAYOUT_INVALID_STID — a full LAYOUTRETURN resets the stateid rather than invalidating it.

17/23 queues suspects on the nfs_client (the callback thread cannot issue fore-channel RPCs) and recovers them in a new state-manager step keyed on NFS4CLNT_DEVICEID_DELETE. TEST_STATEID answers are classified carefully: NFS4ERR_OLD_STATEID means the layout exists and was not revoked, so it counts against the delete the way NFS4_OK does. v1’s default arm treated OLD_STATEID as confirming the delete, so one revoked layout plus one OLD_STATEID answer deleted a deviceID a live layout still referenced. Invalidation is paired with nfs_commit_inode(), because pnfs_clear_lseg_state() drops only the VALID and LAYOUTCOMMIT references and an lseg still held by a commit bucket would keep the device nodes alive.

18/23 confirms a still-referenced DELETE with GETDEVICEINFO. The device really being gone while the server also considers a referring layout valid is the one server-fault case, and it re-establishes the client ID. The call is nfs4_reset_all_state(), not nfs4_schedule_lease_recovery():

"nfs4_schedule_lease_recovery() sets NFS4CLNT_CHECK_LEASE, which the state manager turns into a lease renewal; on the healthy session this recovery runs over, that renewal succeeds and the EXCHANGE_ID Section 18.40.4 prescribes was never sent."

That escalation discards all client state, so it is announced with a rate-limited warning naming the server. 19/23 turns the path on: an unreferenced DELETE keeps today’s cheap unhash; a referenced DELETE is deferred and not unhashed immediately, in case recovery concludes the DELETE was erroneous. The change epoch is bumped for DELETE as well as CHANGE so an in-flight GETDEVICEINFO cannot re-cache a device the notification has just invalidated.

Patches 20–23: cache scaling and nconnect

20/23 grows the global deviceid hash from 32 to 256 buckets — four deep at 1024 devices rather than 32 — for 2 KB of BSS in nfsv4.ko, paid by every NFSv4 client. 21/23 is the mechanical half of moving the per-net data-server cache from a single list to hash buckets (split so a bisect can tell a list-conversion bug from a hash-key bug). 22/23 keys that cache by the DS address set and tightens the comparator from a subset test to set equality. The old subset match was an aliasing bug:

"The aliasing was therefore one-directional: cache {A,B} first and an incoming {A} did not match, but cache {A} first and an incoming {A,B} did. ... The effect is lost path diversity and a truncated ds_remotestr (and the netaddr flexfiles reports in layoutstats), not I/O sent to the wrong server."

23/23 adds a flexfiles dataserver_nconnect module parameter. Data-server clients otherwise inherit the MDS nconnect, which at 1024 data servers and nconnect=16 means 16k sockets and their slot tables, for little gain on a workload already striping across them. Default 0 preserves today’s inherit-from-MDS behavior.

Coddington notes the 256-distinct-address topology that would exercise the nconnect multiplier, the 1000-device topology, and targeted tests for patches 1 and 2 were not covered by the reffs run.

Status this week

The series landed on the list on 21 August as a complete v2 respin; six days later the only review is Schumaker’s question on whether stripe_unit should be promoted to u64 rather than rejected. Nothing has been merged, no other patches have collected tags, and the CHANGE/DELETE/cache-scaling stack is still unreviewed. The open design question on patch 01 is the one to watch: if Schumaker’s 64-bit arithmetic suggestion is taken, the first stable fix — and possibly the coalescing helpers that copy stripe_unit into a u32 — will need a v3 rewrite before the rest of the series can land.
