Chuck Lever posts implied-ACK eviction for NFSD’s duplicate reply cache

Summary

This is a server-side performance feature, not an NFS client change and not a protocol revision. Chuck Lever posted a seven-patch series that lets NFSD drop completed duplicate-reply-cache (DRC) entries as soon as the next request arrives on the same TCP or RDMA connection, instead of parking them until the 120-second RC_EXPIRE timeout. No reviews, Acked-bys, or follow-ups landed in this window; the thread is the v1 posting only.

The work sits on the server lookup hot path that NFSv3 (and NFSv2) clients hit on every non-idempotent RPC. Shorter-lived DRC entries keep the per-bucket rb-trees small, which is the actual win: fewer LLC misses on rb_erase/rb_insert_color while the client is streaming writes. There is no corresponding client patch; Linux NFS client retransmission and session-slot DRC are untouched.

Why the 120-second hold is expensive

A completed DRC entry currently lives until RC_EXPIRE or until the cache exceeds max_drc_entries. Entries whose replies the client already holds still occupy a bucket and slow every later lookup that hashes there. Lever’s cover letter reports numbers from perf record -e cycles -e cpu-clock -e LLC-load-misses -e branch-misses on an NFSv3/RDMA 4KB random-write workload:

"nfsd_cache_lookup overhead dropped from 1.53% to 0.76% of CPU cycles. The rb-tree operations (rb_erase, rb_insert_color) that dominated LLC cache misses fell from a combined 13.2% to 1.1% of all LLC-load-misses, because shorter-lived entries keep the per-bucket trees small."

That is the entire motivation. The series does not change the DRC key, the checksum, or the RC_INPROG/RC_DONE state machine; it only shortens how long a RC_DONE entry is allowed to linger when the transport can prove the reply was delivered.

The implied-ACK rule

Connection-oriented transports (TCP, RDMA) deliver in order. Arrival of a later request on the same svc_xprt is treated as evidence that every prior reply on that connection has been received. Lever cites RFC 1813 §4.5 for the protocol reading: on a live connection-oriented transport, a duplicate request comes from reconnection, not from inside an established stream. Patch 5 is explicit that the signal is still only advisory:

"Even there the evidence is not conclusive, since a client with several requests outstanding sends the next before the previous reply arrives. The cache is advisory: a premature eviction costs a miss and re-execution, the same outcome memory pressure and RC_EXPIRE already produce."

UDP is excluded. A UDP svc_xprt is shared by every peer and carries retransmits on timeout, so a later datagram is not an ACK of an earlier reply. Eviction is therefore confined to transports marked XPT_ORDERED.

During bucket pruning, nfsd_prune_bucket_locked() compares each RC_DONE entry’s c_timestamp against xpt_last_recv on the transport the current request arrived on. A newer timestamp on the same transport means the reply was delivered and the entry is dropped immediately. Only that transport is consulted, because it is the one the pruning thread holds a reference to; entries recorded on other transports wait for a later lookup or a shrinker pass.

Implied ACK does not evict in age order, so the prune loop can no longer stop at the first non-evictable entry. Lever bounds the walk because a client controls its XIDs and the bucket is chosen by an XID hash:

"an unbounded scan lets it pack one bucket and turn every miss into a walk of the whole bucket under cache_lock. Bound the work per call to four times the eviction limit."

That bound is the closest thing in the series to a bug-class hardening: without it, implied-ACK eviction would turn a dense XID hash into a lock-held linear scan.

Plumbing: stable xprt IDs, last-recv, XPT_ORDERED

The eviction policy needs three pieces of SUNRPC state that the DRC did not previously have.

Patch 1 assigns each svc_xprt a per-netns identifier from a cyclic IDR. A consumer that associates state with a transport without holding a reference cannot detect ABA collisions: once a transport is freed, SLUB may hand out a new svc_xprt at the same address. The cyclic IDR delays reuse. svc_xprt_init() now returns a boolean, and its callers in svcsock.c and svc_rdma_transport.c unwind on allocation failure. The DRC is the first consumer.

Patch 2 records that xprt id in each DRC entry. No behavior change on its own.

Patch 3 adds xpt_last_recv on svc_xprt and updates it in svc_handle_xprt() after each successful xpo_recvfrom(). A revisited deferred request leaves the stamp alone, because that request arrived before the deferral and is not fresh client activity.

Patch 4 adds XPT_ORDERED, set by the TCP and RDMA init paths and left clear for UDP. The commit message flags a real semantic cost on svcrdma: handle_connect_req() zeroes the remote port in the DRC key so a cached reply survives a reconnect, and implied-ACK eviction can retire such an entry while the original connection is still up. Lever treats that as consistent with TCP, which already loses the same association whenever a client re-binds its reserved port:

"TCP gives up the same thing whenever a client re-binds its reserved port, so this follows from the eviction policy rather than from RDMA."

That is the one place the series can change client-visible replay behavior: a reconnecting RDMA (or rebound TCP) client that retransmits an in-flight non-idempotent RPC after the next request has already arrived may now miss the DRC and re-execute, the same outcome RC_EXPIRE already produces under memory pressure.

Observability

Patch 6 adds tracepoints for each eviction reason — memory pressure, expiry, implied ACK — plus one for the transport-mismatch case that keeps an otherwise eligible entry in the cache. Without those events there is no way to confirm implied-ACK eviction actually fires or to compare its rate with the other prune paths.

Patch 7 adds an entries= field to nfsd_drc_found so a trace can show whether a miss happened under pressure. The count is passed as an explicit argument rather than read from nn->num_drc_entries in TP_fast_assign, “so that per-connection lookup paths can later supply their own depth without changing the tracepoint format.” That last clause is a hint that Lever is already thinking about per-connection DRC accounting; it is not implemented here.

Client impact, and what this is not

This series does not touch the Linux NFS client. Client-side DRC, NFSv4.1 session slots, retransmission timers, and nconnect are out of scope. The client-visible effect, if any, is on the server’s ability to absorb a replay of a non-idempotent NFSv3 RPC after the next request on the same TCP/RDMA connection has already arrived: a premature eviction is a cache miss and a re-execution, which Lever argues is already an accepted outcome of shrinker pressure and RC_EXPIRE. UDP clients keep the 120-second hold.

It is also not a protocol change. RFC 1813 §4.5 is used as justification for a local eviction heuristic, not as a wire-format or interoperability update.

Where things stand

  • Kind of change: NFSD/SUNRPC performance feature (implied-ACK DRC eviction) with supporting xprt identity and tracing. Not a bug fix, not a protocol change, not NFS client code.
  • No review this window. The eight messages are the cover letter plus patches 1–7, all dated 2026-08-26, all from Lever. Nothing is merged on the strength of this thread.
  • Risk surface to watch in review: ABA-safe xprt IDs (patch 1), the RDMA reconnect / TCP rebind interaction with XPT_ORDERED (patch 4), the four-times-eviction-limit bound on the prune walk (patch 5), and whether implied ACK is too aggressive for pipelined clients with many requests outstanding.
  • Why it still matters to NFS clients: NFSv3/RDMA and NFSv3/TCP write-heavy workloads spend less server CPU in nfsd_cache_lookup and take fewer LLC misses in the DRC rb-trees. That is a server efficiency win that shows up as client throughput, not as a client code change.

Until reviewers weigh in, the 120-second RC_EXPIRE hold remains the in-tree policy, and implied-ACK eviction is a v1 proposal backed by the RDMA random-write profile above.
