syzbot: recursive svc_tcp_state_change overflows the stack during inet_stream_connect

Summary

This is a bug report, not a protocol change and not a new feature. syzbot filed a TASK stack-guard hit against upstream, tagged [net?] [nfs?]. The overflowing function is the SUNRPC server TCP state-change callback, entered from a 32-bit compat connect(2). There is no NFS client code in the dump, and no human reply this week.

The report is the TCP sibling of last week’s UDP svc_write_space overflow on /proc/fs/nfsd/portlist. Chuck Lever already posted a three-line sk_user_data ownership check for that class of bug; it has not landed, and syzbot has now reproduced the same double-attach recursion on the TCP sk_state_change path.

What syzbot reported

On 24 August, syzbot wrote:

"syzbot found the following issue on: HEAD commit: d58772d8520c Merge tag 'regmap-fix-v7.2-rc7' of git://git... git tree: upstream"

That is the same d58772d8520c tree as the 15 August nfsctl_transaction_write stack-guard report. The kernel is gcc 14.2.0, KASAN, PREEMPT(full). Userspace is i386. Dashboard, console log, kernel config, syz repro, and C reproducer are attached. Any fix is asked to carry:

"Reported-by: syzbot+c9834a0c0215e6d8697a@syzkaller.appspotmail.com"

The oops itself:

"BUG: TASK stack guard page was hit at ffffc900062a7ff8 (stack is ffffc900062a8000..ffffc900062b0000) Oops: stack guard page: 0000 [#1] SMP KASAN NOPTI"

RIP is the function prologue of svc_tcp_state_change() at net/sunrpc/svcsock.c:911. The trapping instruction is a push %r12 — the callback is trying to open a new frame on an already-exhausted kernel stack. The task is syz.0.18, PID 5926, untainted.

The smoking gun: unbounded svc_tcp_state_change recursion

The call trace is almost entirely one function calling itself. After the first frame at offset +0x8 (the prologue that hit the guard page), the dump repeats, hundreds of times:

svc_tcp_state_change+0x81/0x350 net/sunrpc/svcsock.c:917

Offset +0x81 / line 917 is the recursive call site: svc_tcp_state_change invoking the saved sk_state_change callback. That saved callback is itself svc_tcp_state_change. Each re-entry consumes stack; KASAN instrumentation makes the frames fat enough that an 8K/16K kernel stack hits the guard page quickly.

The frames under the recursion show how the callback was entered:

tcp_done
tcp_done_with_error
tcp_reset
tcp_rcv_synsent_state_process / tcp_rcv_state_process
tcp_v4_do_rcv
sk_backlog_rcv / __release_sock / release_sock
inet_wait_for_connect / __inet_stream_connect
inet_stream_connect
__sys_connect / __ia32_sys_connect
do_fast_syscall_32

In other words: a 32-bit connect(2) is waiting in inet_wait_for_connect for a SYN-SENT handshake. A TCP RST arrives, tcp_reset → tcp_done fires sk->sk_state_change, and that pointer is the SUNRPC server callback, chained to itself.

The subject names inet_stream_connect because that is the syscall that was on the stack when the guard page was hit. The defect is not in af_inet.c.

How this relates to last week’s portlist double-attach

Last week’s syzbot UDP report overflowed in svc_write_space while write_ports added a UDP descriptor. Chuck Lever’s v1 explained the mechanism: writing the same socket to /proc/fs/nfsd/portlist twice attaches a second svc_sock. svc_setup_socket() saves the existing callbacks, then installs SUNRPC’s own. On the second attach those “old” callbacks are already SUNRPC’s, so the new svc_sock records svc_write_space / svc_tcp_state_change as the previous handlers. The next invocation chains into itself until the stack dies.

Lever already named the TCP half of that story:

"the same chaining exists on TCP via saved data_ready / state_change callbacks, so a TCP descriptor added twice recurses on the next incoming segment rather than during setup."

This week’s dump is that TCP half, observed from connect() rather than from write_ports. A socket whose sk_state_change is svc_tcp_state_change, and whose saved callback is also svc_tcp_state_change, is the double-attach signature. A RST on a SYN-SENT socket is enough to detonate it.

Jeff Layton’s review of Lever’s patch is the right decoder ring for which TCP callback recurses. For a listening socket, svc_tcp_init() only replaces sk_data_ready with svc_tcp_listen_data_ready; sk_state_change is left alone. The non-listen branch does install svc_tcp_state_change(). svc_addsock() reaches that branch for a descriptor that is not listening, then deferred-closes the transport unless the socket is already TCP_SYN_RECV or TCP_ESTABLISHED. This crash is in SYN-SENT (tcp_rcv_synsent_state_process), so it is that non-listen / connecting-socket path, not the listener svc_tcp_listen_data_ready path Layton asked Lever to name in the changelog.

Lever’s proposed fix still covers it: refuse a socket that already carries sk_user_data before svc_setup_socket() overwrites the callbacks. That patch was Reviewed-by Layton on 17 August; no v2 and no merge ack appeared this window. syzbot is still fuzzing the unfixed tree.

NFS client angle — why the [nfs?] tag is a red herring

Despite the subject and the [nfs?] tag, this is not an NFS client I/O or client-transport bug.

  • The overflowing function is svc_tcp_state_change in net/sunrpc/svcsock.c. The NFS client TCP state machine is xs_tcp_state_change in net/sunrpc/xprtsock.c. They are not the same callback.
  • The trigger is a raw connect(2) on a socket that already has SUNRPC server callbacks installed. That is the NFSD portlist / svc_addsock injection surface, not nfs_file_write and not an RPC client reconnect.
  • Shared SUNRPC still matters to client developers: svc_setup_socket is the same helper lockd and other in-kernel RPC services use. A recursive sk_state_change on an svc socket can take down whatever thread happens to be in release_sock / tcp_done, which here is the connecting task itself.

Client test matrices that mix 32-on-64 compat syscalls with nfsctl socket passing are exactly the environment that would trip this. Ordinary NFSv4 client mounts do not.

Reproduction and environment

Syzbot shipped both a syz repro and a C reproducer, plus a non-bootable disk image, vmlinux, and bzImage for d58772d8520c. Hardware is QEMU Q35. The connect is a compat syscall (entry_SYSENTER_compat_after_hwframe, __ia32_sys_connect) with AF_INET address length 16 (RDX: 0x10). No modules are loaded.

Syzbot’s usual control commands (#syz fix, #syz test, #syz dup) are present; none have been used this week.

Status this week

This is a one-message thread. ListThreadMessages shows only the 24 August syzbot mail. There is no prior weekly summary for this Message-ID, and no maintainer, reviewer, or patch has answered in-window.

Until someone replies, the technical conclusion from the dump — read against last week’s Lever/Layton thread — is:

  • Class: kernel stack overflow / unbounded recursion (Oops / DoS).
  • Site: svc_tcp_state_change() in SUNRPC server sockets, entered from tcp_done while a compat connect(2) waits in SYN-SENT.
  • Root cause (inferred, not yet confirmed on-list): the same non-idempotent svc_setup_socket() callback-save that last week overflowed svc_write_space on UDP. A second attach records svc_tcp_state_change as the previous sk_state_change; the next RST/state-change chains into itself.
  • Fix already posted, not merged: Lever’s “reject a socket that already has sk_user_data” patch. It should close this TCP path as well as the UDP one. It needs a v2 changelog that names both svc_tcp_listen_data_ready (listener) and svc_tcp_state_change (non-listen / connecting), plus this report’s Reported-by tag.
  • Not an NFS client bug. Client RPC uses xs_tcp_state_change. The [net?] tag is the accurate one; [nfs?] is NFSD’s portlist socket-injection surface.

No #syz fix, no #syz dup against the 15 August UDP report, and no subsystem re-tag landed this week. The crash is still open on the syzbot dashboard.
