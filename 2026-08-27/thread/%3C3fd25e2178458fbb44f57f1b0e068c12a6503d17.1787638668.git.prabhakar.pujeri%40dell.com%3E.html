nfsd Netlink grace reporting shifts to locks_in_grace()

Summary

This week’s traffic is a design review of a new nfsd observability feature, not an NFS client bug fix and not a wire-protocol change. Prabhakar Pujeri had posted v1 of “report NFSv4 grace state through Netlink” as patch 1/3 of a series that also dumps NFSv4 clients and per-client state usage. The patch adds an in-grace boolean to the existing Generic Netlink threads-get reply so user space can tell a live server that is still in recovery from one that is handing out normal NFSv4 state, without walking nfsdfs. Jeff Layton’s 25 August review (quoted in this week’s follow-up) objected that the v1 attribute only mirrored /proc/fs/nfsd/v4_end_grace and therefore reported nfsd’s v4 lock manager, not the system-wide grace period that actually gates file access.

Why the attribute exists

Pujeri’s 27 August reply answered Layton’s “what’s your interest?” with a concrete operational story: a validation harness that bounces the server, drives reclaim from a set of clients, and must know when grace has actually lifted before the next phase. Polling v4_end_grace works, but it is a text interface, it only answers for nfsd’s v4 lock manager, and new nfsd control is moving to netlink. He framed the work as parity with a retiring interface, not as new information:

"My interest is in making nfsd's operational state observable to monitoring and validation tooling without parsing nfsdfs."

He then conceded Layton’s semantic critique in full:

"Agreed, and "has the grace period lifted" is the question I actually care about. I mirrored the semantics of /proc/fs/nfsd/v4_end_grace without stopping to ask whether those were the useful semantics to expose in a new interface. They aren't."

Layton had written that “just because the v4 recovery is done does not mean that you will be able to access files,” because overall grace is the union of NLM and NFSv4 grace periods, and had suggested either returning locks_in_grace() or adding a lockd counterpart so userland could union the two.

v2 plan: report the union, not the v4-only flag

Pujeri rejected growing lockd. fs/nfs_common/grace.c already exports both halves, and nfsd already calls both helpers:

  • locks_in_grace() is true while any lock manager in the netns is still in grace (the union Layton described).
  • opens_in_grace() is true only while a manager with ->block_opens is in grace — the NFSv4-and-up case; NLM does not set that flag.

For v2 he will report locks_in_grace(), which answers “can this server hand out normal locks and opens yet” rather than “is nfsd’s v4 lock manager done.” A second attribute for opens_in_grace() could be added later without touching lockd; userland could then derive the NLM-only case as (locks && !opens). He would rather not add that speculatively.

Two implementation cleanups fall out of the switch, both improvements over v1:

  • The #ifdef CONFIG_NFSD_V4 and the open-coded nfsd_vers() / NFSD_NET_UP / NFSD_NET_GRACE_ENDED test go away. NFSD selects LOCKD which selects GRACE_PERIOD, so the helper is always available, and a lock manager that is not running simply is not on the grace list.
  • The answer stops being a v4-specific value that merely happens to be served from the nfsd netlink family.

He will rename the attribute and fix the YAML and RST wording so the union semantics are explicit.

Where the boolean should live

Pujeri also asked whether grace belongs on threads-get at all. That operation otherwise reports configuration; grace is dynamic state. His inclination is to keep just this boolean on threads-get for nfsdfs parity, and to grow richer recovery detail — elapsed time, expected vs completed reclaims, whether grace was extended or force-ended — as a separate operation later rather than widening threads-get. He offered to start that separate op now if reviewers prefer grace not ride on threads-get.

Chuck Lever: do not freeze a server-wide-only ABI

Chuck Lever did not object to exposing grace, but set a forward-looking constraint on the new API:

"Although NFSD does not yet support putting individual exports in grace, that is an open possibility for handling things like the reboot of a backend NFS server for a re-exported NFS client. I'd like any new API to avoid foreclosing the ability to move exports in and out of grace individually rather than as a single unit."

That is the only in-week maintainer direction beyond Layton’s semantic review. A boolean on threads-get that is documented as server-wide / netns-wide is compatible with a later per-export operation; a user-visible contract that “the server is in or out of grace as a single unit” would not be.

Client angle and status

There is no NFS client code change in this thread. The client relevance is operational: the intended consumers are monitoring and a restart/failover harness that drives client reclaim and must wait until the server is actually out of grace before asserting that locks and opens succeed. The v1 attribute would have been the wrong signal for that (v4 lock manager done, NLM possibly still blocking). v2’s locks_in_grace() is the value those clients and tests actually need.

Conclusion this week: Pujeri accepted the review, will respin v2 around locks_in_grace(), will make the union semantics explicit in the spec, and left open whether the boolean stays on threads-get or becomes its own operation. Lever’s per-export grace warning is unresolved in-thread; no v2 patch landed in this window.
