NFS client CB_NOTIFY v2 draws first dcache review

Summary

Overview

This week Anna Schumaker posted v2 of her four-patch new feature series that teaches the Linux NFS client to consume CB_NOTIFY callbacks for directory delegations. The work is not a protocol change — CB_NOTIFY has been in NFSv4.1 since RFC 5661 / 8881 — and it is not a bug-fix series. It is the missing client half of directory delegations: the client already knows how to request a directory lease; these patches teach it what to do when the server later says the directory changed.

The v1 posting (4 August) sat unanswered. v2 arrived on 25 August with decoder and handler cleanups, and this time it drew a first review: Jeff Layton challenged the REMOVE path’s use of d_drop(), asking whether a remove notification should instead leave a negative dentry. Schumaker had not replied by the end of the window. Nothing from the series merged.

Bridge from v1

Three weeks ago Schumaker posted the original four patches with an explicit request for comments and no replies in that window. The design thesis has not changed. In the v2 cover letter she restates the same conservative client-engineering choice:

"These patches add support for the CB_NOTIFY callback operation from NFS servers. Editing directory order or placement in our caches isn't easy or practical the way things are structured now. Instead, I use CB_NOTIFY as an indication that the client needs to refresh its view of the directory."

That is still the heart of the series: treat CB_NOTIFY as a cache-invalidation / refresh signal rather than a full directory-journal replay. A naïve implementation would splice, reorder, or rewrite dentries in place as NOTIFY4_* events arrive. Schumaker argues the current NFS client cache layout makes that kind of surgical edit impractical.

She closed again with a one-word invitation — > "Thoughts?" — and this time Layton answered, on the REMOVE handler.

What changed in v2

The cover letter lists three explicit v2 deltas:

  • Fix signed / unsigned type mixups
  • Don't try to share lookup code between NOTIFY4_REMOVE and NOTIFY4_ADD
  • Add handling for the NOTIFY4_ADD na_have_old_entry case

Those map onto the per-patch notes. Patch 1 changes the callback result to ssize_t. Patch 2 initializes res to 0 in nfs4_callback_notify(), adds missing error handling, and removes the shared nfs4_cb_notify_lookup() helper that v1 tried to use for both add and remove. Patch 3 is the largest rewrite: handle na_have_old_entry, initialize fattr->valid to 0 before decoding, actually check decode_fattr_cb()'s return code, and reshape nfs4_cb_notify_add() so it more closely resembles nfs_prime_dcache(). Patch 4 is still the thin rename composition.

The diffstat is essentially unchanged from v1 — six files, 409 insertions, 5 deletions — all on the client callback path: fs/nfs/callback.h, fs/nfs/callback_proc.c, fs/nfs/callback_xdr.c, fs/nfs/nfs4_fs.h, fs/nfs/nfs4xdr.c, and include/linux/nfs4.h. No fs/nfs/dir.c rewrite. That still matches a decoder plus three notification handlers, not a readdir-cache journal.

The split of lookup code is the most important client-correctness fix in v2. Sharing a lookup helper between REMOVE (name is gone; dcache should forget or go negative) and ADD (name now exists; dcache should grow a positive dentry) was always a type-confusion risk. Dropping nfs4_cb_notify_lookup() and giving ADD its own nfs_prime_dcache()-shaped path is the right structural answer, even before Layton's review of the REMOVE side.

Patch 1: CB_NOTIFY skeleton

Patch 1 still only wires CB_NOTIFY into the client's callback operation table and XDR decoder:

"Support for individual notification types will be added over the next few patches."

The v2 note — change res to a ssize_t — is the signed/unsigned mixup fix from the cover. Until the later patches land, an incoming CB_NOTIFY can be recognized and parsed far enough to be dispatched rather than treated as an unknown callback. The outline is where the protocol constants (include/linux/nfs4.h), argument structs (fs/nfs/callback.h), stub procedure, and decode path live.

Patch 2: REMOVE_ENTRY, and Layton's d_drop question

Patch 2 is the first real handler, and it still follows the cover letter's "refresh, don't rewrite" rule almost verbatim:

"When the server tells us that a directory entry has been removed then we need to take that as an indication that our knowledge of the directory has changed and needs to be refreshed."

The implementation looks up the child dentry and then d_drop()s it. That is the line Layton stopped on. In his reply he asked:

"Should this instead make this a negative dentry?"

and spelled out the consequence of the current code:

"I think this will just drop the existing dentry and it'll trigger a lookup next time we end up trying to hit it."

That is the first real design fight of the series, and it is a client-dcache question, not an XDR one.

d_drop() unhashes the dentry. The next lookup() of that name misses the dcache and goes to the server. That matches a conservative "our knowledge is stale, go refresh" policy, and it is hard to get wrong: no leftover positive dentry for a name the server just deleted. But it also throws away the information the notification just delivered. With a directory delegation held, the whole point of CB_NOTIFY is that the client may keep serving the namespace from cache. A negative dentry would let the next lookup answer ENOENT locally, without a round trip, which is exactly the performance win directory delegations are supposed to buy.

The tension with the cover letter is now explicit. Schumaker said surgical dcache edits are impractical and CB_NOTIFY should mean "refresh." Layton is pointing at the one surgical edit REMOVE can do cheaply and correctly: turn the name negative. That is also the more delegation-friendly answer. Leaving the name unhashed forces a GETATTR/LOOKUP that a holder of a directory delegation should not need.

v2's other REMOVE-side fixes — initialize res to 0, add missing error handling, stop sharing lookup with ADD — are the sort of correctness nits that belong in a second posting. They do not resolve Layton's question. The thread ended there; Schumaker had not answered by week's end.

Patch 3: ADD_ENTRY still instantiates

Patch 3 is still the one place the series does reach into the dcache, and v2 leans further into that rather than backing off:

"When the server tells us that a directory entry has been created, we need to instantiate a new dentry and add it to the dcache on the client."

An add notification carries enough information for the client to create a positive dentry immediately, so a subsequent lookup can hit without a round trip. That is a stronger action than the cover letter's "refresh the view" slogan, and it is the operation most likely to interact badly with concurrent local creates, negative dentries, and the existing nfs_force_lookup_revalidate() machinery that directory delegations already shortcut.

The v2 rewrite of nfs4_cb_notify_add() to resemble nfs_prime_dcache() is the right client-side instinct. nfs_prime_dcache() is the well-worn helper that READDIR uses to stuff names into the dcache; cloning that shape for a callback-context add is much safer than inventing a third insertion path. Handling na_have_old_entry closes a protocol hole v1 ignored: the server may tell the client that the added name replaced a previous entry, which is the ADD-side twin of Layton's negative-dentry question. Zeroing fattr->valid before decode and checking decode_fattr_cb() are ordinary but necessary XDR hygiene; a stale valid mask from the stack would let a truncated attribute set look complete.

This remains the patch that will need the closest review. Instantiating dentries from callback context is a classic source of locking and lifetime bugs, and the client's earlier directory-delegation work already had a rough winter of verifier and state-recovery crashes. Layton reviewed REMOVE first; ADD is the obvious next target, especially the na_have_old_entry case (old name should go negative or be dropped, new name instantiated).

Patch 4: RENAME_ENTRY as remove-plus-add

Patch 4 is still the smallest of the four (38 insertions) because it refuses to invent a third code path:

"Renaming an entry essentially combines a remove with an add, allowing us to reuse most of the code from the previous patches to do the work for us."

That composition is faithful to the NFSv4 notify model — a rename is a remove of the old name plus an add of the new one, possibly across directories. It also means Layton's d_drop() vs. negative-dentry question inherits into rename. If REMOVE only unhashes the old name, a rename notification will force a lookup on the source name the next time anyone hits it, even though the client just learned the name is gone. If ADD instantiates the target, the destination side of the rename is cache-hot and the source side is not. Cross-directory rename notifications will exercise both, which is exactly the combination a directory-delegation holder needs when another client rearranges a tree — but only if the two halves of the policy agree.

How this fits the existing client directory-delegation work

The November 2025 client-side directory-delegation series already sent GET_DIR_DELEGATION / GDD_GETATTR, requested a directory lease on ACCESS, CREATE, UNLINK, and same-directory RENAME, short-circuited lookup revalidation while a directory delegation is held, and added a module option to turn the feature off.

What it did not do is react to server-initiated directory change notifications. Without CB_NOTIFY, a client that holds a directory delegation has only two choices when another client mutates the directory: wait for a recall, or discover the change the hard way when a verifier or getattr fails. A working CB_NOTIFY path is what lets the client keep the delegation across other clients' creates, unlinks, and renames, instead of bouncing the lease on every remote mutation.

That is why Layton's negative-dentry question is not a nit. If REMOVE d_drop()s and the next access of that name issues a LOOKUP, the client is paying a round trip for information it already has, and it is exercising the very lookup-revalidation path directory delegations were meant to skip. If the LOOKUP also causes the client to question the delegation, the feature unravels. Turning the dentry negative keeps the lease useful.

The earlier client work also left scars reviewers remember. Directory-delegation verifier checks and state-recovery paths produced kernel Oopses over the 2025–2026 holiday window; Trond Myklebust at one point warned that another incident might mean disabling directory delegations on the client until the next release. This CB_NOTIFY decoder walks some of the same inode and dcache edges. The conservative "refresh the directory" policy in the cover letter looks like a reaction to that history. Layton is now asking whether that conservatism is leaving performance on the table — and whether d_drop() is even the correct VFS primitive for "this name is gone."

Status

  • Type: new NFS client feature (directory-delegation CB_NOTIFY support). Not a protocol change, not a bug-fix series. v2 of the 4 August posting.
  • Posted: 25 August 2026, four patches, ~409 lines, client callback / XDR only.
  • v2 focus: type-safety, stop sharing ADD/REMOVE lookup, handle na_have_old_entry, reshape ADD toward nfs_prime_dcache().
  • Review: Jeff Layton on patch 2 only. Open question: d_drop() vs. a negative dentry on CB_NOTIFY4_REMOVE_ENTRY. No reply from Schumaker in-window. No comments yet on ADD, RENAME, or the XDR outline.
  • Not merged. The client still cannot usefully hold a directory delegation across remote namespace changes until some version of this decoder lands, and the REMOVE-side dcache policy is now the gate.

The obvious next step is a v3 that answers Layton — either by converting the removed name to a negative dentry (and doing the same for the source of a rename), or by defending d_drop() as the intentional "force a refresh" behavior the cover letter described. ADD's na_have_old_entry path should get the same treatment, or the two notification types will disagree about what "the old name is gone" means.
