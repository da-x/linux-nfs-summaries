Dell posts pNFS GETDEVICEINFO decoder hardening with KUnit coverage

Summary

Summary

This is a bug-fix / hardening series for the NFS client pNFS device-address decoders, not a protocol change and not a new layout feature. On 23 August, Prabhakar Pujeri of Dell posted a four-patch series that tightens how the client consumes server-supplied GETDEVICEINFO payloads: malformed universal-address port octets, and unbounded multipath address counts that can spin the decoder for billions of iterations once the XDR stream is exhausted. The series is based on linux-next commit 10f307e525a1 (next-20260821). There were no replies this week; the patches sit unreviewed on the list.

Pujeri’s cover letter states the threat model in one paragraph:

"pNFS GETDEVICEINFO replies contain server-provided universal addresses and multipath counts. The current decoders accept malformed port octets and can spend billions of iterations on a count that is not bounded by the reply length."

All three functional patches carry Fixes: tags and Cc: stable@vger.kernel.org, so the intent is a backportable client-side robustness fix rather than a new pNFS capability.

Why the client decoder is the story

pNFS file layout and flexfiles both learn data-server endpoints from GETDEVICEINFO. The shared helper nfs4_decode_mp_ds_addr() turns a server-provided netaddr4 (netid plus universal address, including two decimal port octets) into a socket address. The layout drivers then loop over a server-chosen multipath count. That count is a u32; once XDR is exhausted the decoder returns NULL without consuming input, so a malicious or truncated reply can keep the client in a kernel-context loop until the count wraps. That is a classic untrusted-XDR bug on the client path, not a server-side layout issue.

Pujeri did not have a pNFS-capable server for this posting. He exercised the decoder directly with new KUnit suites and ran ordinary NFSv3/v4.1/v4.2 data, locking, and parallel workloads plus ACL and xattr checks on a Dell PowerEdge R660:

"No pNFS-capable server was available, so the affected decoder paths were exercised directly by KUnit."

The pNFS decoder suite passed 16/16, the flexfiles suite 3/3, with an empty kmemleak scan. The series builds with GCC and Clang W=1 and Sparse C=2.

Patch 1: stop trusting sscanf() on port octets

Patch 1 rewrites the port parse in nfs4_decode_mp_ds_addr() (fs/nfs/pnfs_nfs.c). The existing code used an unchecked sscanf() on the two decimal port octets of the universal address. Pujeri’s diagnosis is that a missing or non-numeric field leaves part of a temporary array uninitialized, while values outside the octet range are silently folded into the resulting port.

The replacement splits the two port fields at their delimiters and parses each with kstrtou8(). That rejects missing fields, trailing garbage, integer overflow, and values outside 0–255 before the data-server socket address is constructed.

"Split the two port fields at their delimiters and parse each with kstrtou8(). This rejects missing fields, trailing garbage, integer overflow, and values outside 0 through 255 before constructing the data server socket address."

Fixes: 6b7f3cf96364 ("nfs41: pull decode_ds_addr from file layout to generic pnfs") — this is the generic pNFS helper, so both file layout and flexfiles inherit the stricter parse.

Patches 2 and 3: bound multipath loops by remaining XDR, not U32_MAX

The more serious client bug is the unbounded multipath loop. Patch 2 hits file layout (nfs4_fl_alloc_deviceid_node()). That function already bounds the number of data-server multipath lists, but not the number of addresses inside each list. The inner count is server-supplied and can be U32_MAX.

"Once the XDR stream is exhausted, nfs4_decode_mp_ds_addr() returns NULL without consuming input. The enclosing loop can therefore spin for billions of iterations in kernel context when decoding a malicious GETDEVICEINFO response."

The chosen bound is not an arbitrary protocol cap. A netaddr4 needs at least the two XDR length words for its netid and universal-address strings. The decoder now rejects a count that cannot fit that minimum representation in the remaining XDR stream, so the loop is proportional to reply length. The existing file-layout multipath-list limit stays, because it is tied to the u8 stripe-index representation. A small helper is added in fs/nfs/pnfs.h so flexfiles can reuse the same check.

Fixes: 14f9a6076f53 ("NFS: Parse and store all multipath DS addresses").

Patch 3 applies the same remaining-XDR bound to flexfiles (nfs4_ff_alloc_deviceid_node()), which previously did not validate the multipath address count at all. Same failure mode: nfs4_decode_mp_ds_addr() returns NULL without consuming input, so a count near U32_MAX can spin the client in kernel context.

"This makes the loop bound proportional to the reply length without imposing an arbitrary protocol limit, matching the protection in the file-layout decoder."

Fixes: d67ae825a59d ("pnfs/flexfiles: Add the FlexFile Layout Driver"). Together, patches 2 and 3 close the same class of bug on both layout drivers that share the generic decoder.

Patch 4: KUnit for the decoder, not just a live pNFS server

Patch 4 is the test investment that makes the first three patches reviewable without a pNFS MDS. It adds page-backed XDR tests for nfs4_decode_mp_ds_addr() covering valid IPv4 and IPv6 universal addresses, boundary port values, missing fields, non-numeric fields, out-of-range values, integer overflow, and trailing garbage (fs/nfs/tests/pnfs_decode_kunit.c). A separate flexfiles GETDEVICEINFO module (fs/nfs/flexfilelayout/tests/deviceid_kunit.c) exercises a valid single-address payload and verifies that zero and U32_MAX multipath counts are rejected.

The two flexfiles decoder helpers are exported only when KUnit is enabled. Both suites sit behind guideline-compliant Kconfig entries that default with KUNIT_ALL_TESTS and can be built as modules. Flexfiles fixtures and decoded devices are managed as KUnit resources so assertion failures do not leak them.

That is the notable client development piece this week: decoder hardening plus in-tree unit coverage for a path that is otherwise hard to hit without a cooperating pNFS server.

Where things stand

  • Kind of change: NFS client bug fix / XDR hardening. No protocol change. No new pNFS layout feature.
  • Scope: generic nfs4_decode_mp_ds_addr(), file-layout GETDEVICEINFO, flexfiles GETDEVICEINFO, plus two new KUnit modules.
  • Stable intent: all three functional patches are Cc: stable with Fixes: back to the original decoder, the multipath-address parser, and the flexfiles driver.
  • Review status: posted 23 August; no Acked-by, Reviewed-by, or maintainer comment this window. The series is unmerged as of week-end.
  • Testing gap Pujeri already flags: no pNFS-capable server was used; the new KUnit suites are the primary evidence that the decoder now rejects the bad cases.

Until a reviewer picks this up, a malicious or truncated GETDEVICEINFO can still feed the client an unbounded multipath count and an unchecked port parse. The series is the proposed client-side close of that hole.
