NFSD session-slot replay race lands in nfsd-testing

Summary

This week Ameer Hamza posted a server-side bug fix for a regression in NFSD’s NFSv4.1 session reply cache, and Chuck Lever applied it to nfsd-testing the next day. The discussion is not a protocol change and not NFS client code, but the crash is triggered by a perfectly legal client behavior: pipelining two copies of a cached SEQUENCE request before reading either reply. That is exactly the retry/replay path NFSv4.1 sessions were designed to support, so the server-side interlock around NFSD4_SLOT_INUSE is the piece that has to hold.

The thread is short and conclusive. Hamza’s patch diagnoses a production NULL-pointer panic on 6.12.91, traces it to commit cc028a10a48c (“NFSD: Hoist status code encoding into XDR encoder functions”), and restores the missing “did this request actually claim the slot?” distinction with a new cstate->slot_owned flag. Chuck Lever accepted it without further review comments:

"Applied to nfsd-testing, thanks!"

What broke

nfsd4_sequence() claims a session slot by setting NFSD4_SLOT_INUSE under nn->client_lock. A reply served from the slot’s DRC does not claim it. That distinction used to live only in cstate->status, which nfsd4_sequence() set to nfserr_replay_cache. Hamza’s commit message is explicit about the subsequent landmine:

"Commit cc028a10a48c ("NFSD: Hoist status code encoding into XDR encoder functions") moved nfsd4_proc_compound()'s cstate->status assignment below the out: label, and the replay path's goto out was the one path that relied on skipping it. The test in nfsd4_sequence_done() therefore no longer identifies a replay, and every replay now stores its reply and clears NFSD4_SLOT_INUSE as though it owned the slot."

NFSD4_SLOT_INUSE is the interlock. check_slot_seqid() rejects every sequence id for a slot that is in use, before replay_matches_cache() runs. A replay never sets the flag, so two replays can be in flight on the same slot at once. One thread can then read slot->sl_cred under nn->client_lock while the other’s completion frees and rebuilds that credential from the XDR encoder without the lock. Two completions can also collide and put the same group_info twice. free_svc_cred() leaves cr_uid, cr_gid, and cr_flavor intact, so the racing reader sails through every earlier test in same_creds() and then dereferences a NULL cr_group_info.

Hamza captured the resulting panic from a 6.12.91 production server:

"BUG: kernel NULL pointer dereference, address: 0000000000000004 CPU: 63 UID: 0 PID: 39015 Comm: nfsd RIP: 0010:same_creds+0x38/0xa0 [nfsd] [...] Kernel panic - not syncing: Fatal exception"

The stack is the classic nfsd compound path: same_creds ← nfsd4_sequence ← nfsd4_proc_compound ← nfsd_dispatch.

There is a second, newer failure mode. Since v6.14 a live session’s slot table can shrink. nfsd4_sequence() defers that shrink while a slot is in use, but it tests NFSD4_SLOT_INUSE, which a replay does not set. free_session_slots() can therefore kfree() the slot the replay still holds in cstate->slot. The unowned store of the cached reply then becomes a use-after-free write.

Hamza reproduced the race on an unmodified tree:

"Reproduced on an unmodified tree with a client that pipelines two copies of a cached request before reading either reply."

That is the NFS client angle that matters here. The Linux NFS client (and any other NFSv4.1 client) is allowed to have more than one copy of a SEQUENCE-tagged request in flight when it has not yet seen the reply. The server’s DRC is supposed to serve the cached reply without claiming the slot. After cc028a10a48c, that “serve but do not own” path was indistinguishable from a first-time execution, so the cache itself became racy under client retry.

The fix

The patch is small: seven insertions in fs/nfsd/nfs4state.c and one new field in fs/nfsd/xdr4.h. Hamza records the claim in cstate->slot_owned when nfsd4_sequence() accepts a request, and tests that flag in nfsd4_sequence_done(). Only the request that actually claimed the slot updates the cached reply and clears NFSD4_SLOT_INUSE. svc_generic_init_request() zeroes the compound response before each request, so the flag starts clear and does not leak across RPCs.

The patch is tagged:

  • Fixes: cc028a10a48c ("NFSD: Hoist status code encoding into XDR encoder functions")
  • Assisted-by: Claude:claude-opus-5
  • Signed-off-by: Ameer Hamza <ameer.hamza@truenas.com>

This is a bug fix, not a new feature. It restores the original slot-ownership contract that the XDR-encoder hoist accidentally dropped, rather than changing how NFSv4.1 sessions or the DRC are specified.

Outcome this week

No design debate, no v2, no NAK. Lever’s b4-ty note on 25 August is the entire follow-up: the patch is in nfsd-testing. There is no SHA in the applied-mail (“no commit info”), so the exact testing-branch commit is not recorded on-list.

For operators, the practical takeaway is that any 6.12-era (and later) nfsd that inherited the XDR-encoder hoist can panic or UAF when a client retries a cached SEQUENCE while another replay is still completing. The client does not have to be buggy; pipelined retries of a cached request are enough. The server-side slot_owned flag is the intended back-port candidate.
