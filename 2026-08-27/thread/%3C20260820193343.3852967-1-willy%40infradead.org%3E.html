FUSE and btrfs push back on dropping launder_folio; NFS conversion still unreviewed

Summary

FUSE and btrfs challenge Wilcox’s launder_folio removal; NFS client conversion still unacked

Recap

Last week Matthew Wilcox posted a seven-patch VFS cleanup to delete aops->launder_folio, converting FUSE, btrfs, NFS, and OrangeFS onto filemap_invalidate_pages(). The NFS-facing change is patch 4/7: drop nfs_launder_folio() and switch directory, DIO, inode, and NFSv4.2 invalidate paths to a bulk writeback-then-remove helper. Wilcox’s diagnosis for NFS was efficiency, not correctness:

"nfs relies on invalidate_inode_pages2() / invalidate_inode_pages2_range() doing writeback by calling nfs_launder_folio(). While this works, it is inefficient as each folio is written back and waited for individually."

This is a page-cache invalidation refactor, not an NFS protocol change. No NFS maintainer had reviewed it as of 20 August. This week the series finally drew real review — from FUSE maintainer Miklos Szeredi, btrfs developer Boris Burkov, and VFS reviewer Jan Kara — and the debate is whether the new helper is semantically equivalent to per-folio launder under page lock. That question lands directly on the NFS client: the same writeback-during-invalidate contract is what nfs_launder_folio() currently provides for mmap, DIO, and server-driven cache drop.

FUSE: is filemap_invalidate_pages() actually equivalent?

Miklos Szeredi opened on the FUSE conversion (patch 2/7) with a locking concern. The kernel-doc for filemap_invalidate_pages() suggests holding invalidate_lock to keep pages from coming back; without it, he is not sure the behavior matches invalidate_inode_pages2() plus fuse_launder_folio():

"filemap_invalidate_page() suggests to use invalidate_lock to prevent races with pages coming back. I'm not sure that without it the behavior is identical."

"Maybe add a variant that takes that lock?"

Wilcox rejected a helper-internal lock. Holding invalidate_lock only inside the function is useless, because pages can be reinstated the instant it drops:

"I don't understand what use that would be. As soon as that function drops the lock, the pages could be reinstated. If the caller needs the pages to not come back, it must need to hold the invalidate_lock across the whole operation."

He also warned filesystems off trying to close the classic O_DIRECT vs. mmap race with that lock:

"Before any filesystem people get funny ideas about closing the O_DIRECT race, you can't do that because you'll deadlock on doing I/O to the same file that you've mmaped."

Szeredi then sharpened the real objection: the old path guaranteed no dirty data remained after the call, because launder ran while the folio was locked. Bulk writeback does not:

"invalidate_inode_pages2_range() together with launder_page guaranteed that no dirty data remained in the cache after that call. Yes, the pages can be reinstated after that but those need faults and the server can then serialize those against the invalidation."

"I don't see that guarantee with the filemap_write_and_wait_range() (with or without invalidate_lock actually) since the mapping can be dirtied again without the filesystem's knowledge."

Wilcox asked him to name the serialization that exists in the old path and not the new one, laying out both call stacks. Before: fuse_open() → invalidate_inode_pages2() → lock, unmap, folio_launder(), unlock. After: filemap_invalidate_pages() → filemap_write_and_wait_range() then invalidate_inode_pages2_range() which only tests dirty under the folio lock.

Szeredi’s answer is the mmap redirty window:

"In the second case filemap_write_and_wait_range() won't write protect or unmap the page, so it may become dirty after the writeback."

"That can't happen in the first case, since the page is written and unmapped while under page lock."

He agreed that wrapping filemap_invalidate_pages() in invalidate_lock would not help (“Nothing”), and asked what would stop a writeback + unmap + writeback sequence from still racing.

Wilcox: the race was always there

Wilcox conceded a wider window, not a new race:

"But that can also happen in the first case. page_mkwrite() can be called immediately after the folio is unlocked, for example. Or the folio can be evicted and replaced with a different folio which is then dirtied."

"I've widened the race window, no doubt. But it was always there."

His prescription is the same one he gave for O_DIRECT: if a filesystem needs pages to stay clean, it must hold invalidate_lock across filemap_invalidate_pages() and the subsequent operation that depends on that cleanliness. A second writeback after unmap would not close it either:

"We could do that -- but it won't solve the problem because the pages could still be redirtied after the second writeback."

That stance matches patch 7 from last week, which moves the “folio got dirty again during DIO invalidate” failure into the VFS (folio_unmap_invalidate()) instead of asking each filesystem to launder again. For NFS, that would replace the current nfs_launder_folio() retry with a VFS-level fail of the invalidate.

Szeredi’s distributed-cache example (and why NFS should care)

Szeredi came back with a concrete — if admittedly artificial — scenario meant to prove the two paths are not equivalent. He framed it as a FUSE-based distributed filesystem that serializes writers so sub-page stores cannot revert to stale data on cached writeback, invalidating aliases on other nodes:

"Let's imagine a distributed filesystem based on fuse. It wants to serialize accesses to a file to avoid sub page writes reverting to stale data on cached writeback. Cached writeback is unavoidable in case of writable mmap, so it tries to handle this case correctly by totally excluding cached aliases existing on different nodes."

With launder_page, an INVALIDATE on node A locks the page, unmaps it, and writes it back under that lock, so a concurrent store either rides the launder or blocks on the page lock until writeback finishes and the server can serialize a new READ. Without launder, writeback and unmap are split:

"b) happens after page writeback but before unmap: - since page is still mapped, store succeeds, page becomes dirty - at this point we have differing cache contents on A and B"

He is careful not to claim a live FUSE daemon depends on this today:

"It's not realistic and very unlikely to exist, yet something more subtle might be relying on this behavior. I don't know. At this point I'm just trying to show you that the two are really not equivalent, not that this has any practical significance."

For NFS client development this is the most important remark of the week. Linux NFS is exactly a distributed cache with server-driven invalidation, writable mmap, and close-to-open / delegation recall paths that currently punch the page cache through invalidate_inode_pages2*() and nfs_launder_folio(). Szeredi’s “store after writeback, before unmap” window is the same class of mmap redirty that NFS has historically papered over with per-folio launder. If FUSE cannot accept the widened window, the NFS conversion in patch 4/7 needs the same scrutiny — and no NFS developer has yet provided it. Wilcox still has not answered this example in-window.

Bernd Schubert’s earlier FUSE len <= 0 / “invalidate to EOF” ABI objection from 20 August also remains unanswered.

btrfs: launder_folio was never writeback

Boris Burkov reviewed patch 3/7 and disputed the commit message’s premise. Unlike NFS and FUSE, btrfs is not using ->launder_folio as a writeback hook:

"I don't believe btrfs_launder_folio() is doing writeback, it is just dropping otherwise leaked qgroup reservation. So this part of the commit message feels inaccurate to me, at least."

The call he originally cared about is transaction-failure cleanup: invalidate remaining dirty pages that still have delalloc attached. He is checking whether forcing writeback in that “semi-failed” context still frees the qgroup reservation, and whether the series still passes the test that motivated adding this “creative” ->launder_folio use:

"I am trying to figure out if trying to force the writeback in this semi-failed context will also result in freeing the reservation, and also testing this patch series on the test that I originally fixed with launder_folio()."

"With all that said, thank you for working on cleaning up the mess I made by adding this "creative" usage of ->launder_folio(). Hopefully we can figure this out cleanly."

That is a filesystem-specific bug-fix question, not an NFS one, but it undercuts Wilcox’s uniform “everyone used launder for writeback” story. NFS does use nfs_launder_folio() for writeback; btrfs does not. Any v2 of the series will likely need a btrfs-specific replacement for the qgroup leak, while NFS still needs a demonstrated equivalent of “write dirty folios, then drop them” under mmap.

Jan Kara: the locked-folio guarantee may still matter

Jan Kara replied to the cover letter and likes the direction, echoing Wilcox’s “is launder_folio actually needed?” instinct — with one reservation that aligns with Szeredi:

"I like the idea (and was myself wondering from time to time whether launder_folio is actually needed) but what was putting me off was that when using folio_launder() you can clean a folio while keeping folio locked and so you can guarantee later eviction without someone messing with the folio between writeout & ->release_folio. Maybe nobody actually needs this, which would be great, but it would be great to hear more from the folks using launder_folio about their reasons..."

That is an explicit invitation to NFS. The client is one of the remaining ->launder_folio users; nfs_launder_folio() exists precisely so invalidate can write a dirty folio while it stays locked, then drop it. Kara wants those users on the record before the method dies. None have spoken on linux-nfs this week.

Status and NFS client impact

This remains a VFS cleanup plus NFS client invalidation efficiency change, not a protocol change. The important NFS bug-fix/optimization on the table is still last week’s: stop per-folio writeback-and-wait in nfs_launder_folio() and flush invalidate ranges in bulk via filemap_invalidate_pages().

What changed this week is that the conversion is no longer an unreviewed drive-by. Szeredi argues the new helper is not equivalent because writeback and unmap are no longer atomic under the folio lock, and he sketched a distributed-cache failure that looks uncomfortably like NFS mmap vs. server INVALIDATE. Wilcox says the race always existed and filesystems that care must hold invalidate_lock themselves. Kara wants launder_folio users — NFS included — to explain whether they need the locked writeout-to-release window. Burkov shows at least one “user” of the method was never doing writeback at all.

Nothing is merged or acked. The NFS client patch still has no review from Trond Myklebust, Anna Schumaker, Jeff Layton, or Neil Brown. Until someone on the NFS side answers Kara’s question — does the client rely on launder-under-folio-lock for mmap/DIO/delegation invalidation, or is a widened redirty window acceptable because it was always racy? — Wilcox’s deletion of nfs_launder_folio() should be treated as blocked on the same semantic debate that is now holding FUSE.
