Client pNFS SCSI layout rejects oversized designators to stop a GETDEVICEINFO OOB read

Summary

This week’s linux-nfs traffic includes a client security bug fix, not a protocol change and not a new feature: Jérémy Jean posted a one-patch hardening of the pNFS SCSI layout decoder so a malicious GETDEVICEINFO cannot turn a 32-bit length into a SIZE_MAX memcpy. There are no replies in the window. Maintainers have not acked, nacked, or queued it.

The hole: a signed SCSI designator length that can wrap to −1

The bug lives in the NFS client pNFS blocklayout path that implements RFC 8154 SCSI layouts (fs/nfs/blocklayout/). When the client processes a layout and needs the backing device, pnfs_layout_process() → bl_alloc_lseg() → nfs4_find_get_deviceid() → bl_alloc_deviceid_node() decodes the SCSI designator from the device-info XDR.

Jean’s diagnosis is a classic signedness bypass on that length:

"A SCSI GETDEVICEINFO reply can encode designator_len as 0xffffffff. The current signed field turns that into -1, so the size check is bypassed and the value is converted to SIZE_MAX for xdr_inline_decode() and memcpy()."

0xffffffff is a legal on-the-wire u32. Stored in a signed C field it becomes -1. The existing “is this designator too big?” test treats that as in-range, then the length is widened to size_t and becomes SIZE_MAX (18446744073709551615 on 64-bit). Both xdr_inline_decode() and the subsequent memcpy() are then asked to consume that many bytes.

KASAN on a file read against a layout that pulls in the poisoned device id reports exactly that:

"BUG: KASAN: out-of-bounds in bl_alloc_deviceid_node+0x616/0x1110"

"Read of size 18446744073709551615"

The stack in the report is the client layoutget path: __asan_memcpy ← bl_alloc_deviceid_node ← nfs4_find_get_deviceid ← bl_alloc_lseg ← pnfs_layout_process ← nfs4_proc_layoutget. This is not a server crash and not a local unprivileged ioctl; it is the mounted NFSv4.1+ client trusting device-info XDR from the MDS.

Attacker model: a mounted client, a hostile NFSv4.1+ server

Jean is explicit about who can hit this:

"The attacker model considers a controlled NFSv4.1+ server and a client already mounted to that server. An OOB read can be triggered in the client on a file read."

That is the standard pNFS “malicious MDS” model: the client has already accepted the export and is using SCSI layouts. A file read that causes layoutget/deviceid resolution is enough. There is no claim of unauthenticated remote attack, and no claim of a write primitive — KASAN shows an out-of-bounds read of essentially unbounded size. For a production client that still means kernel memory disclosure or an oops, which is why the patch is Cc: stable@vger.kernel.org.

The regression tag goes all the way back to the original SCSI layout code:

Fixes: d9186c039765 ("nfs/blocklayout: add SCSI layout support")

That is the 2016 client work that added pNFS SCSI. Every kernel with CONFIG_PNFS_BLOCK SCSI layout support is in the backport set.

The fix: u32 length, reject before xdr_inline_decode()

The patch is five lines across two files (blocklayout.h, dev.c):

  • pnfs_block_dev_scsi.designator_len (or the local length used while decoding) is stored as u32, matching the XDR type, instead of a signed integer that can go negative.
  • Oversized values are rejected rather than clamped after the fact.
  • The bounds check is moved up, so it runs before xdr_inline_decode() rather than after a decode that already used the wrapped length.

Jean’s one-sentence summary of the code change:

"The fix stores the length as u32 and reject oversized values before decoding. The check is moved up before the call to xdr_inline_decode()."

That ordering matters. Checking after xdr_inline_decode(xdr, designator_len) is too late once designator_len has become SIZE_MAX: the decoder has already tried to pull an impossible span out of the XDR buffer. Rejecting first means a hostile 0xffffffff becomes -EIO / a failed deviceid node, not a KASAN splat in memcpy.

This is the same class of client XDR hygiene as other “reject oversized length” work on linux-nfs (callback bitmap lengths and similar), applied here to the SCSI designator in GETDEVICEINFO. It is not a wire-protocol change: RFC 8154 designators were never allowed to be 4 GiB; the client is finally refusing the illegal encoding instead of wrapping.

The commit trailer also carries Assisted-by: Codex:gpt-5. That is disclosure of LLM assistance on a security fix, not a technical argument; nobody on-list commented on it this week.

Client impact, and what did not happen this week

  • Kind of change: NFS client bug fix / hardening in pNFS SCSI layout device-id decoding. No NFSD change, no new layout type, no protocol extension.
  • Who is exposed: any client that mounts an NFSv4.1+ pNFS SCSI export (pnfs=scsi / blocklayout SCSI). Trigger is a READ (or any operation that forces layoutget + GETDEVICEINFO) against a server that returns designator_len = 0xffffffff.
  • What the user would see today: KASAN OOB, or a hard crash / memory over-read in bl_alloc_deviceid_node on non-KASAN kernels. After the patch: the device id is rejected and the layout path fails closed.
  • Stable: requested. The Fixes: tag implies every SCSI-layout-capable stable tree.
  • Review status: none in this window. The Message-ID is numbered -2- (typical of a git-send-email series), but only this standalone [PATCH] landed on linux-nfs; there is no cover letter, no patch 1, and no reply from Trond, Anna, Chuck, Christoph, or the blocklayout regulars.

Until someone reviews the u32 conversion and the new max-designator constant, this remains an unacked client security patch sitting on the list. The technical claim is straightforward — do not feed a wrapped SCSI designator length to xdr_inline_decode() / memcpy() — and the KASAN trace backs it up. What is missing this week is an ack that the new limit matches the SCSI designator sizes the client actually accepts (NAA, EUI-64, T10 vendor ID) and that failing the device node is the right recovery for a hostile MDS.
