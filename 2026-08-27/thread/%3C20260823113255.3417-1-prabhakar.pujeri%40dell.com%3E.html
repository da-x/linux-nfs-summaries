NFSD POSIX ACL leak in unexecuted compounds

Summary

This week’s discussion is a server-side memory-leak bug fix in NFSD’s NFSv4 COMPOUND teardown, not a protocol change and not NFS client work. Dell’s Prabhakar Pujeri reported that a remote client can force the server to leak POSIX ACL objects by sending compounds that decode ACL-bearing operations and then abort before those operations run.

The leak

Pujeri’s patch traces the leak to nfsd4_decode_fattr4(), which allocates POSIX ACLs while decoding OP_OPEN, OP_CREATE, and OP_SETATTR. In the happy path, a processed OPEN drops them from its op_release callback, while CREATE and SETATTR hand ownership to struct nfsd_attrs and clear the pointers. If compound processing stops first, nfsd4_release_compoundargs() frees the operation array without dropping those ACL references.

"If compound processing stops before a decoded ACL-bearing operation, nfsd4_release_compoundargs() frees the operation array without dropping those ACL references. A client can repeat an aborting compound to leak server memory."

The same patch also tightens opcnt handling so the procedure-release callback never walks stale inline entries after a hard XDR decode failure: keep opcnt limited to fully initialized entries on a truncated operation number, and clear it when the dynamic operation array cannot be allocated.

Pujeri tagged it Fixes: 5fc51dfc2eb1 ("NFSD: Add support for XDR decoding POSIX draft ACLs") and backed the diagnosis with kmemleak:

"An A/B kmemleak test with 512 crafted NFSv4.2 compounds found 347--349 leaked 64-byte ACL objects without this change and none with it. On the rebased kernel, 512 runtime-abort and 512 hard-decode compounds completed without a kmemleak or KASAN report."

The proposed fix was a teardown sweep: release ACLs still attached to decoded operations when compound arguments are destroyed, and clear OPEN’s pointers in its release callback so the final sweep stays idempotent.

Maintainer review: two bugs, two patches

Chuck Lever accepted the diagnosis and the remote-triggerability, then declined to take the combined patch as-is.

"Thanks for the report. I agree with the diagnosis and its status as triggerable by a remote. After careful review, I have decided to split the work into two patches."

He treated the two opcnt assignments as a separate defect that needs a stable backport, and argued that the ACL leak’s real root cause is pointer ownership, not missing teardown:

"For the ACL half, the underlying issue is that ->set_acl() borrows the caller's reference rather than consuming it. That makes pointer ownership the true root cause, which IMHO needs a different approach than your proposed fix. And, since POSIX ACLs in NFSv4 are experimental and disabled by default, it's something that can be treated as mainline-only; no backport."

He asked for the 512-compound test and said he would post a two-patch series for review.

Reporter agrees, then publishes the reproducer

Pujeri agreed with the split and with treating the ACL half as mainline-only.

"Thanks, the split makes sense, and separating the opcnt fix so it can go to stable on its own is clearly the right call -- it stands independent of the ACL question and is the part with the wider blast radius."

On the ownership question he deferred:

"My sweep in nfsd4_release_compoundargs() cleans up the symptom at teardown; putting the fix at the ownership boundary is the more durable answer, and it makes the release path idempotent by construction rather than by careful pointer-clearing."

He offered a Tested-by against his harness and sketched the attack: decode an ACL-bearing op, then stop the compound before that op executes so the ACL is allocated during decode but never reaches ->set_acl() or op_release(). Unpatched, one ACL leaks per iteration; patched, the slab stays flat.

Minutes later he corrected the runtime-abort shape: the invalid PUTFH comes before the ACL-bearing SETATTR, not after.

"The invalid PUTFH comes before the ACL-bearing SETATTR. The server decodes both operations, allocating the POSIX ACL while decoding SETATTR, then execution stops on the earlier PUTFH before SETATTR runs. Thus the decoded ACL remains owned by compound-argument cleanup."

The exact NFSv4.2 runtime compound is:

PUTFH(invalid one-byte filehandle)
SETATTR(FATTR4_WORD2_POSIX_ACCESS_ACL)

The hard-decode case decodes SETATTR, advertises a second operation, and truncates the request before that second operation number. He posted a raw-XDR Python client (default 512 iterations of each mode; --mode runtime or --mode hard-decode) rather than a pynfs case, and offered to convert it if maintainers prefer it live with the existing NFSv4 tests.

Where it stands

No code from this thread was merged this week. Pujeri is holding his patch and waiting to review Lever’s rewrite. Lever did post that rewrite the next day as a separate series, [PATCH 0/2] NFSD: Fixes for NFSv4 COMPOUND argument teardown, which is outside this thread but is the direct follow-through:

  • He split the original report because the two defects need different LTS routing.
  • After closer review he decided Pujeri’s argp->opcnt assignments actually address an unreachable problem; the stable-worthy half is instead an unprivileged out-of-bounds read in nfsd_nl_rpc_status_get_dumpit() (NFSD_CMD_RPC_STATUS_GET has no GENL_ADMIN_PERM).
  • For the ACL leak he keeps a compound-lifetime reference by chaining decoded ACLs on the temporary allocation list with an optional release callback, and gives struct nfsd_attrs its own posix_acl_dup() so nfsd_attrs_free() still balances. That removes OPEN’s op_release method. The ACL patch is marked experimental / no autosel for stable.

Client impact is only as the attacker: a crafted NFSv4.1/4.2 COMPOUND is enough. There is no client-side code change in this thread.

Conclusion this week: remote-triggerable NFSD leak confirmed; original combined patch withdrawn in favor of a maintainer rewrite that separates a stable-bound rpc_status OOB from a mainline-only POSIX ACL ownership fix. The reporter’s Python harness is now on-list for that follow-up series.
