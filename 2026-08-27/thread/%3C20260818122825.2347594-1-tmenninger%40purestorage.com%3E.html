xprtrdma hang: Lever nits v2 unmap/disconnect serialization

Summary

This week’s linux-nfs traffic on Tim Menninger’s xprtrdma hang fix is a single review: Chuck Lever signs off on the correctness of v2 and asks for comment and layering cleanups rather than another redesign. The thread remains a bug fix for a client-side FRWR race, not a protocol change.

Last week established the hang: frwr_unmap_sync() can post LOCAL_INV work after rpcrdma_xprt_disconnect() has already drained the QP, then sleep forever on a CQE that will never arrive. v1’s extra inflight counter was dropped; v2 serializes the post-after-drain window with rx_unmap_rwsem, reuses rpcrdma_ep_get()/rpcrdma_ep_put() for endpoint lifetime across the wait, and moves the completion onto struct rpcrdma_req.

Correctness is in; comments are not

Lever’s opening line is the news of the week:

"I didn't find any correctness issues in this one."

The rest of the mail is titled as nits: stale kernel-doc and a layering change around CM ID teardown.

Kernel-doc for frwr_unmap_sync()

The rewritten function comment drops the old sleeping contract:

"Sleeps until it is safe for the host CPU to access the previously mapped memory regions."

v2 also takes and releases a transport-wide rwsem. Lever wants both facts in a Context section:

"Context: Process context. Takes and releases @r_xprt->rx_unmap_rwsem for read. May sleep."

Disconnect no longer fully tears down hardware

rpcrdma_xprt_disconnect() now holds rx_unmap_rwsem for write across the QP drain and resource teardown, but its kernel-doc still records only the caller-side rule:

"Caller serializes. Either the transport send lock is held, or we're being called to destroy the transport."

The rwsem belongs there as well. More importantly, the old “completely divested” claim is now false:

"On return, @r_xprt is completely divested of all hardware resources and prepared for the next ->connect operation."

A concurrent frwr_unmap_sync() holds an endpoint reference across its completion wait, so rpcrdma_ep_put() returns 0. The QP, both completion queues, the PD, and the CM ID then outlive disconnect’s return.

rx_unmap_rwsem overclaims what it covers

The new lock comment on struct rpcrdma_xprt claims more than the lock delivers. rx_ep is still sampled without this rwsem in frwr_mr_init(), frwr_map(), frwr_send(), frwr_unmap_async(), frwr_wp_create(), rpcrdma_xprt_drain(), rpcrdma_mrs_create(), rpcrdma_mrs_refresh(), rpcrdma_rep_create(), rpcrdma_rep_resize(), and rpcrdma_post_recvs(). Lever wants the comment narrowed to the actual ordering:

"Orders frwr_unmap_sync()'s LOCAL_INV submission ahead of the QP drain. Disconnect holds the write side across the drain and resource teardown."

Layering: don’t destroy CM IDs from frwr_ops.c

v2’s error path in frwr_unmap_sync() open-codes rdma_destroy_id() after rpcrdma_ep_put() returns 1. Lever flags this as not a defect, but a layering break:

"This is not a defect, but it makes frwr_ops.c the only file outside verbs.c that destroys a CM ID."

The other three teardowns already live in verbs.c (rpcrdma_create_id() and rpcrdma_ep_create() error paths, plus rpcrdma_xprt_disconnect()). The rule that a nonzero rpcrdma_ep_put() return leaves the CM ID for the caller to destroy is only documented above that helper. Lever wants a small verbs.c wrapper to carry the rule instead of duplicating the idiom:

void rpcrdma_ep_release(struct rpcrdma_ep *ep)
{
        struct rdma_cm_id *id = ep->re_id;

        if (rpcrdma_ep_put(ep))
                rdma_destroy_id(id);
}

That would export rpcrdma_ep_get() / rpcrdma_ep_release() rather than the get/put pair. The local id snapshot in frwr_unmap_sync() then goes away, because ib_post_send() can read ep->re_id->qp directly while the read side is still held. The new rpcrdma_ep_put() prototype in xprt_rdma.h also needs to document that a return of 1 leaves the CM ID for the caller.

Status

No v3 landed this week. The discussion has moved from “is this the right lifetime model?” to “the hang is closed; tidy the comments and keep CM ID destruction in verbs.c.” The client-side FRWR unmap/disconnect race remains the bug under fix; merge still waits on those nits.
