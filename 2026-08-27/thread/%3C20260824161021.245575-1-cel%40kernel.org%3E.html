Chuck Lever posts the VFS splice wrapper for NFSD’s duplicate fsnotify ACCESS bug

Summary

This is a bug-fix thread, not a protocol change and not NFS client work. It is the follow-through on Ameer Hamza’s earlier NFSD series: iterator READs still fire two fsnotify_access() events, splice READs fire one, and VFS maintainers had already ruled that NFSD must not paper over that mismatch itself. Chuck Lever now posts the agreed VFS helper. Amir Goldstein reviews it on the spot. Christoph Hellwig does not NACK the layering, but he wants the new public API renamed and slimmed before it lands.

The client-visible symptom is unchanged until a v2 ships: an inotify/fanotify watch on an exported file sees a READ twice when NFSD takes the iterator path (sec=krb5i/sec=krb5p, splice disabled, NFSD_IO_DONTCACHE/NFSD_IO_DIRECT) and once when it splices.

Brief recap of the placement fight

Hamza’s original 1/2 moved fsnotify_access() into nfsd_splice_read() so both NFSD READ helpers would emit from one place. Hellwig rejected that as an NFSD workaround of a VFS hole. Goldstein then proposed exporting vfs_splice_direct_to_actor(): wrap splice_direct_to_actor() with the permission hook and a single access event, keep those hooks outside freeze protection (the 2023 “Tidy up file permission hooks” rule), and let NFSD call the wrapper. Hellwig called that “the right thing to do.” Lever volunteered to write it.

Lever’s v1: one ACCESS per NFSD READ, emitted by VFS

Lever’s patch is a three-file change (fs/nfsd/vfs.c, fs/splice.c, include/linux/splice.h) that does exactly that. The commit message restates the double-count:

"nfsd_finish_read() calls fsnotify_access() on both NFSD read paths, because splice_direct_to_actor() does not emit the event itself. The iterator path reaches nfsd_finish_read() from vfs_iocb_iter_read(), which has already emitted one. A READ served without splice therefore emits two access events."

And the GSS-specific reason it shows up in the field:

"NFSD does not use splice for the GSS integrity and privacy services, so a READ on a sec=krb5i or sec=krb5p mount takes the iterator. An inotify watch on that file sees the READ twice."

The VFS side introduces vfs_splice_direct_to_actor(), which runs rw_verify_area(), calls the existing splice_direct_to_actor(), and then emits fsnotify_access() once for the whole READ. NFSD’s splice READ helper switches to that wrapper, and nfsd_finish_read() stops calling fsnotify_access() so the iterator path (already covered by vfs_iocb_iter_read()) no longer double-fires. That is the important server-side accounting fix: both NFSD READ flavors now produce one ACCESS event, and the event is generated by the VFS API rather than by nfsd special-casing.

Credits on the patch: Reported-by Hamza, Suggested-by Goldstein, Closes the Hamza 1/2 thread.

Goldstein: Reviewed-by, no further comments

Goldstein replied the same afternoon with a bare:

"Reviewed-by: Amir Goldstein amir73il@gmail.com"

That is the fsnotify maintainer signing off on the layering he sketched days earlier. He did not ask for a rename, a kerneldoc rewrite, or a change to the splice_desc argument list.

Hellwig: keep the wrapper, retire “direct”, maybe hide splice_desc

Hellwig reviewed the new helper as API, not as an nfsd workaround. First he wants the historically confusing “direct” terminology gone from the new public name:

"Can we use this to start retiring the really weird direct terminology here that is confusing? I.e. name this vfs_splice_to_actor? With that we'll only need to fix up do_splice_direct (which is an event worse name) to fix the public API."

Then the kerneldoc. The @ lines dump too much of the splice_desc contract; the Description: heading is “accepted by te parset, but redundant.” He supplied a rewritten comment that describes the helper as “call an actor on data read from a file,” notes that it “Ensures the read is allowed using rw_verify_area() and emits fsnotify access events,” and keeps the seekable (FMODE_LSEEK) requirement.

He then floated a deeper cleanup of the “weird semantics of the splice_desc”: build the descriptor inside the helper and pass pos, count, actor, and private instead of making every caller fill in sd. That would turn NFSD into a caller of something closer to:

vfs_splice_to_actor(in, pos, count, actor, private)

rather than a splice_desc assembler. He left both options on the table; the second is “maybe an even better idea,” not a hard requirement.

Hellwig did not dispute the fsnotify placement, the removal of fsnotify_access() from nfsd_finish_read(), or the fact that this is the right layer for the bug. The review is a request for a v2 of the VFS surface, not a return to Hamza’s nfsd-only patch.

Where things stand

  • Kind of change: bug fix in VFS splice plus a small NFSD call-site update. No NFS protocol change. No NFS client code.
  • The double ACCESS event is still unfixed in-tree. v1 is posted and Goldstein-acked; Hellwig wants vfs_splice_to_actor (and possibly no public splice_desc) before it is the public API.
  • NFSD remains a consumer, not the emitter. That was the point of last week’s VFS ruling, and Lever’s patch follows it.
  • No v2 this window. Lever has not yet answered Hellwig’s naming and signature nits.
  • Why it still matters to NFS: GSS integrity/privacy READs, and any other iterator-READ work (including Hamza’s SUNRPC reply-page recycling series), inherit the duplicate inotify ACCESS until this wrapper lands. Watchers of exported files are the users who see it.

Until Lever respins, the splice and iterator READ helpers remain inconsistent, and the “one ACCESS per user READ” contract Goldstein asked for is agreed in principle but not merged.
