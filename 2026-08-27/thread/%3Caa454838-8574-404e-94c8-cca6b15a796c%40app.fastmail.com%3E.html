xprtrdma hang: v3 serializes unmap_sync, Lever R-b

Summary

Summary

This week’s linux-nfs traffic on Tim Menninger’s xprtrdma hang fix is the v3 respin and Chuck Lever’s review-with-nits. The thread remains a bug fix for a client-side FRWR race, not a protocol change: frwr_unmap_sync() can post LOCAL_INV work after rpcrdma_xprt_disconnect() has already drained the QP, then sleep forever on a CQE that never arrives.

Prior weeks established the hang and the lifetime model. v1 added an inflight counter that Lever rejected as technical debt; v2 dropped that counter, moved the completion onto struct rpcrdma_req, and reused endpoint krefs. Lever then signed off on correctness but asked for comment and layering cleanups. v3 is that cleanup series. Lever still wants two small follow-ups, but the hang fix itself now has a Reviewed-by.

The race, restated

Menninger’s changelog still walks the four-step window that stalls rpciod:

  1. frwr_unmap_sync() samples r_xprt->rx_ep
  2. rpcrdma_xprt_disconnect() drains the QP
  3. frwr_unmap_sync() posts LOCAL_INV WRs after the drain
  4. No CQE arrives, so wait_for_completion() blocks indefinitely

The hung task remains:

"Workqueue: rpciod rpc_async_schedule [sunrpc] wait_for_completion() frwr_unmap_sync() xprt_rdma_free() xprt_release()"

The same pNFS restart loop is the reproduction: v7.2-rc6 under load with repeated data-server restarts. Without the fix, the hang hit twice in six attempts; with it, 200 cycles stayed clean. The stall has also been seen on v6.8 and v6.18.34. The Fixes: tag stays on e28ce90083f0 ("xprtrdma: kmalloc rpcrdma_ep separate from rpcrdma_xprt"), which made rx_ep a separately allocated, kref-managed pointer.

v3 keeps the v2 mechanics: rx_unmap_rwsem serializes the post-after-drain window; the reader drops the lock before waiting so disconnect can drain submitted work; rl_registered is rechecked after acquiring the rwsem in case disconnect already reset the request; the completion lives on the request, not the MR; the sampled endpoint is held across the wait so disconnect can destroy MRs without a separate active-unmap counter. The async path still needs no extra lock, because Receive-before-Send Queue drain already orders frwr_unmap_async().

v3: comments, encapsulation, and a verbs.c helper

The changelog lists the nits Lever asked for after v2:

"Document the sleepable rx_unmap_rwsem locking context in frwr_unmap_sync() and rpcrdma_xprt_disconnect(). Add rpcrdma_ep_release() so CM ID destruction remains encapsulated in verbs.c; export the endpoint get/release pair instead of get/put. Use ep->re_id->qp directly while frwr_unmap_sync() holds the rwsem read side. Correct rpcrdma_xprt_disconnect() documentation to account for endpoint resources that can outlive the disconnect operation. Narrow the rx_unmap_rwsem comment to describe the LOCAL_INV versus QP-drain ordering it provides."

That last point is the lock-comment overclaim from last week: rx_ep is still sampled without this rwsem in a long list of other FRWR and verbs helpers, so the comment now describes only the LOCAL_INV versus QP-drain ordering. Disconnect’s kernel-doc no longer claims the transport is “completely divested of all hardware resources” on return, because a concurrent unmap can keep the endpoint (QP, CQs, PD, CM ID) alive past disconnect. CM ID teardown is no longer open-coded from frwr_ops.c; rpcrdma_ep_release() in verbs.c carries the rule that a last rpcrdma_ep_put() leaves the ID for the caller to destroy.

Lever: Reviewed-by, two leftover nits

Chuck Lever does not reopen the race or the lifetime model. The remaining comments are documentation and one missed call site.

The new exported helpers still lack kernel-doc, and rpcrdma_ep_put() is now static:

"Nit: The new externally-visible functions need kdoc comments. rpcrdma_ep_put() is now static, so the kdoc comment there can be converted to non-kdoc-style."

Disconnect still open-codes the put-then-destroy idiom that rpcrdma_ep_release() was added to encapsulate:

"Nit: rpcrdma_xprt_disconnect() retains

if (rpcrdma_ep_put(ep))
    rdma_destroy_id(id);

but should call the new rpcrdma_ep_release() helper."

He also notes the new block comments are wordy. None of that is a merge blocker:

"The new block comments are wordy, and could be tightened. But no show-stoppers here:

Reviewed-by: Chuck Lever cel@kernel.org"

Status

The client-side FRWR unmap/disconnect race is closed on the design Lever asked for: one transport-wide rwsem, existing request and endpoint objects for lifetime, no inflight counter. v3 absorbed last week’s comment and layering nits; this week’s leftover work is kdoc on the new rpcrdma_ep_get() / rpcrdma_ep_release() pair, converting the now-static rpcrdma_ep_put() comment, and routing disconnect through that helper. With Lever’s Reviewed-by on the hang fix itself, the remaining items look like a v4 polish pass rather than another redesign.
