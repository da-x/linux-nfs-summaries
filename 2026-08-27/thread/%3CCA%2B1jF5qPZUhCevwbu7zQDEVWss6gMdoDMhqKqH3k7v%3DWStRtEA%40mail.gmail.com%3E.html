Howells: netfs read abandonment is not a READ_PLUS sparse-read hook

Summary

This week’s only in-window traffic on the READ_PLUS follow-up is David Howells’ reply to Aurélien Couderc. The parent discussion is PATCH v10 30/35 of Howells’ netfslib bvecq overhaul: a simplification of how netfs collection treats a permanently failed subrequest. Couderc had asked whether that “partial abandonment” work could also help NFSv4.2 READ_PLUS (sparse-file reads). Howells’ answer is a polite no: the two problems live in different layers, and netfslib still has no sparse-read model for the NFS client to hang READ_PLUS on.

What the abandonment patch actually changes

Patch 30 is a bug-fix / simplification of the netfs read collector, not a protocol change and not an NFS client feature. Previously, if one subrequest in a multi-subreq read failed, collection tried to salvage folios that were fully downloaded but spanned several subreqs, provided every contributing subreq succeeded. Howells called that “quite complicated,” because a subreq can contribute to multiple folios and a folio can be contributed to by multiple subreqs.

The new rule is blunt: once a permanently failed subreq is hit, abandon the rest of the request. That is what read_folio, DIO/unbuffered read, gap filling, RMW and write preload already need. Readahead is the odd one out — it has no error return other than unlocking folios — but even there leftover non-uptodate folios simply fall back to ->read_folio(). Retryable failures still retry inside the request.

That is the work Couderc was looking at when he asked:

"What about READ_PLUS, i.e. sparse file reads? If you do this kind of work of handling partial abandonment, can such a work also benefit READ_PLUS?"

Howells: READ_PLUS is NFS, and netfslib does not know about holes

Howells’ 24 August reply first pins the protocol:

"READ_PLUS is NFS, right?"

Then he separates sparse-file I/O from fatal-error abandonment:

"I'm not sure it would particularly help or hinder."

The architectural argument is the one that matters for NFS client development. The VFS/VM only ever asks netfslib to read contiguous regions. Netfslib then chops those into subrequests. It currently has no knowledge of sparse reads:

"The VFS/VM only asks to read contiguous regions and netfslib breaks that up into subrequests, but currently netfslib doesn't know anything about sparse reads."

The filesystem, not the library, is expected to know where the holes are. Howells’ working example is Ceph, not NFS:

"What I'm looking at with Ceph, for example, is that Ceph knows where the gaps are and will clear them before terminating the subrequest."

Partial abandonment, by contrast, is strictly an error-path tool:

"Partial abandonment is for when some sort of fatal error occurs and we cannot finish the request."

In other words: a hole in a sparse file is not a failed subreq, and a failed subreq is not a hole. Salvaging or abandoning the tail of a request after a permanent error does not give the NFS client a way to consume READ_PLUS data/hole segments.

NFS client implications

This is not a READ_PLUS implementation, a protocol change, or even a netfs API for sparse replies. It is a clarification that the NFS client cannot piggy-back NFSv4.2 sparse reads on the new collector behaviour.

For an NFS client that already talks to netfslib (today, mainly the fscache path), the practical picture after this exchange is:

  • Read abandonment is now a fail-fast collector policy. A permanently failed NFS/netfs subreq drops the remainder of that request; read() retries via ->read_folio(). That is a correctness/simplification fix in the shared library, not a sparse-file optimisation.
  • Sparse files remain the filesystem’s problem. Netfslib still presents contiguous subrequests. If the NFS client later wants to issue READ_PLUS and punch holes / skip zeroes, it would have to do what Howells describes for Ceph: the client knows the gaps and clears them before terminating the subrequest. The library will not invent that knowledge from abandonment.
  • No netfs sparse-read model yet. Howells is explicit that netfslib “doesn't know anything about sparse reads.” The v10 series does talk about discontiguous bvecq chains and cache occupancy extents (DATA vs ZERO) in the parent posting, which would be the natural buffer representation if NFS ever fed READ_PLUS hole/data segments into netfslib — but that is not implemented, and Howells did not offer it as a READ_PLUS plan here.

The discussion ends with Howells’ assessment. There is no follow-up from Couderc in-window, no NFS-client patch, and no commitment to teach netfslib about READ_PLUS. The conclusion for this week is Howells’ own: the abandonment work “would [not] particularly help or hinder” NFS sparse reads, because the two mechanisms solve different problems.
