Linux NFS — Week ending 2026-06-25

Top story: NFS client 7.2 pull merged into mainline

The single most consequential event of the week is the merge of Anna Schumaker's nfs-for-7.2-1 pull request into torvalds/linux.git — sent June 23, confirmed merged by pr-tracker-bot just six hours later on June 24. The diffstat is substantial: 35 files changed, +703 / -326, with the heaviest concentration in net/sunrpc/xprtrdma/ and fs/nfs/.

The pull bundles:

  • XPRTRDMA hardening (13 patches by Chuck Lever) — decoupling request recycling from RPC completion, fixing a use-after-free where an rpcrdma_req could be recycled while the HCA was still DMA-reading from its send buffer. Includes conversion of the send-buffer free list to a lockless llist and several connect/reply-path fixes by Chris Mason (ep kref imbalance on ADDR_CHANGE, re_id init, bcall rep leak).
  • FMODE_NOWAIT for read-only files — lets io_uring complete NFS I/O inline rather than punting to worker threads.
  • 16 distinct bug fixes across SUNRPC, XPRTRDMA, NFS core, NFSv4, pNFS, and flexfiles (EOF updates after fallocate/zero-range, sticky page-group read-failed flag, file-lock list UAF fix by Yang Erkun, LAYOUTCOMMIT retry loop on OLD_STATEID, return_range callback deferral, flexfiles FF_FLAGS_NO_IO_THRU_MDS honoring, zero-length r_addr/filehandle rejection, etc.).
  • Fileid field removal from struct nfs_inode — the long-promised follow-on to the 7.1 treewide inode->i_ino widening; eliminates the decade-old XOR-folding hack for 32-bit userspace.
  • Mount option redaction — cert_serial/privkey_serial now shown as <redacted> in /proc/mounts.

The follow-on fileid cleanup also landed into Anna's linux-next branch this week after a five-week dormancy, with a side-thread on an arm32 LTP ioctl10 regression (the test's sscanf() overflows when /proc/self/maps now prints full 64-bit inode numbers on 32-bit arches).

Critical client bugs and fixes in flight

KASAN slab-use-after-free in xprt_put — confirmed live on mainline

The KASAN UAF report from June 7 finally got its first maintainer triage this week. Anna Schumaker asked the reporter to retest against current mainline in light of the recently merged transport-lifecycle fixes; Shuangpeng Bai confirmed within hours that the bug still reproduces on f0e6f20cb52b with an essentially unchanged trace — a write into a freed 2048-byte slab object from rpc_free_client_work. This is now queued for genuine root-cause work in the SunRPC client transport lifetime path.

NFSv4.1/pnfs: XDR-wrap OOB read in decode_pnfs_layout_types

Michael Bommarito posted a stable-tagged fix for an integer-overflow-driven out-of-bounds read reachable from a malicious NFSv4.1+ server during FSINFO decode. A u32 count multiplied by 4 wraps for values ≥ 0x40000000, letting the verify loop read up to ~2^30 words past the inline XDR buffer. Trond Myklebust's reply was terse but consequential: "This is just open coding xdr_stream_decode_uint32_array(), and doing so incorrectly." — steering the fix toward the canonical helper. This is the companion to his earlier GETDEVICEINFO notification-bitmap fix from last week; both are part of a pNFS decoder-hardening campaign against hostile servers.

NFSv4 callback IDR leak on allocation failure

Ruoyu Wang posted a surgical fix for a publish-before-free lifetime bug in nfs4_alloc_client(): if any later initialization step fails, the error path frees the client directly with nfs_free_client() (bypassing nfs_put_client()), leaving cb_ident_idr pointing at freed memory. A later NFSv4.0 callback lookup by cb_ident would find the stale pointer and take a reference to it. Found by a local static-analysis checker, confirmed manually. No maintainer reply yet as of week's end.

NFSv4.1 FREE_STATEID refcount leak + blocklayout device leaks

ZhangGuoDong (KylinOS) posted a two-patch series: (1) a one-line fix dropping the nfs_client reference before returning -ENOMEM in nfs41_free_stateid(), and (2) three related fixes in the pNFS blocklayout device parser — child array leak on parse failure, bl_free_device() not releasing the children array when nr_children == 0, and a double-free risk in bl_parse_scsi() after fput(). No replies yet.

NFS file-lock UAF fix lands in linux-next after 16-week wait

The long-running RFC from Yang Erkun (Huawei) to protect NFS file-lock list traversal using nfsi->rwsem instead of flc_lock finally landed in Anna Schumaker's linux-next branch this week (commit 4837fb36219e). The fix has carried Jeff Layton's Reviewed-by since March; the delay was purely queue-related. Erkun's final ping and apology for checking only the MAINTAINERS-listed tree closed out a cordial sixteen-week saga.

RPC-with-TLS memory bugs finally get maintainer attention

After seven weeks unqueued, Chuck Lever's two-patch series fixing an rpc_clnt leak and a use-after-free in RPC-over-TLS got a gentle ping from Lever on June 24 and an immediate commitment from Anna Schumaker: "I'll take a look soon, and try to include them in a bugfixes pull request." The UAF was reported in the field by Michael Nemanov (Vast Data) and produces a refcount_t underflow on mTLS mounts whose client certificate the server rejects.

lockd: GRANTED_MSG regression fix

Olga Kornievskaia (Red Hat) posted a one-line-per-file swap fixing a regression introduced by the xdrgen XDR conversion of GRANTED_MSG: pure NFS clients (no nfsd running) were failing every incoming NLM callback because the client-side path was wired through server-oriented nlm4svc_lookup_host() helpers that require nlmsvc_ops registration. The fix uses the generic nlmsvc_lookup_host() instead.

lockd: TEST handling fix queued for 7.0

NeilBrown's patch (posted by Chuck Lever) fixing how lockd handles NLM TEST when not all permissions are available was confirmed queued for 7.0 by Sasha Levin. The bug — present since git history began but masked until a recent nfsd permission-handling change — caused qemu to fail when accessing read-only filesystem images over NFS.

Major new features and RFCs

pNFS/flexfiles: honor clora_changed and report cancelled I/O (v2)

Benjamin Coddington posted v2 of his three-patch series fixing a long-standing protocol-compliance gap: the Linux client has ignored the clora_changed flag in CB_LAYOUTRECALL since 2015, cancelling in-flight data-server I/O on every recall — which can leave a write incomplete at the DS with no write layout held. The v2 addresses Anna's review nits (kerneldoc, FILE_INODE → inode->i_ino) and is now based on nfs-for-7.2-1, awaiting final sign-off.

NFSv4.2 client support for UNCACHEABLE_FILE_DATA

Mike Snitzer posted a four-patch series adding Linux NFSv4.2 client support for FATTR4_UNCACHEABLE_FILE_DATA (attribute 87) from the in-flight IETF draft. The motivating use case is HPC-style concurrent writers modifying disjoint byte ranges of a shared file, where cached/delayed writes cause read-modify-write "write holes." When a server marks a file uncacheable, the client transparently opens it O_DIRECT. Review discussion focused on whether to use the server-side xdrgen infrastructure for a client-only attribute; Chuck Lever steered toward keeping the client self-contained.

NFS Direct I/O modernization (v2) — folio/bvec debate continues

Pranjal Shrivastava responded to last week's review feedback on his seven-patch series migrating NFS O_DIRECT to the modern iov_iter_extract_pages() API. He provided full xfstests quick-suite results (no regressions across RDMA and TCP), acknowledged CC-list additions, and raised a pointed counter-observation: the block layer's own bvec extraction path also calls page_folio() via get_contig_folio_len() without slab/vmalloc checks — questioning whether the correct long-term fix is an API change in lib/iov_iter.c that shields all filesystems from folio semantics.

SUNRPC: latency floor for interactive clients (RFC)

Benjamin Coddington posted a three-patch RFC adding a second per-pool ready queue for transports with no requests in flight, granting them a burst allowance of 64 high-priority dispatches. The goal: prevent interactive NFS client sessions (stats, opens, directory listings) from being starved by bulk workloads saturating the server thread pool. Benchmark data shows up to 12.8× p50 latency improvement for interactive bursts under heavy contention with no throughput regression. Chuck Lever's review identified a deferred-close routing bug and asked Coddington to validate the exact-zero re-arm trigger under contention via kprobe.

nfsd netlink stats (v6) — UAF fixed, dump design debated

Jeff Layton posted v6 of his series converting nfsstat to generic netlink, fixing both of Chuck Lever's prior-week blockers (UAF in nfsd4_run_cb() via snapshotting, CB_SEQUENCE undercount). However, Lever's review of v6 introduced two new concerns: (1) the single-message dump design is fragile against buffer-size growth as NFSv4 ops are added — he recommends the streaming pattern already used by nfsd_nl_rpc_status_get_dumpit(); and (2) the CB_SEQUENCE increment still fires for null-probe work items that never send a callback. A v7 will likely address both. See also the v5 review thread.

Ongoing debates and design discussions

NFS delegations: the "warm ls -l is slower than cold" puzzle

A 12-message thread opened by Piyush Sachdeva drew in all four core NFS client maintainers (Layton, Coddington, Schumaker, Myklebust) plus Tigran Mkrtchyan (DESY). The benchmark: on a 100K-file directory with actimeo=5s, a warm ls -l issues 100,000 GETATTRs and takes ~62 s vs ~14 s for the cold pass. Root cause: directory delegations protect dentries but not file attributes, so post-actimeo stats fall through to per-file GETATTR — far more expensive than batched READDIRPLUS.

Key proposals discussed:

  • Anna Schumaker's "statx-based readdirplus syscall" — letting userspace declare its intent up front so the client can pick READDIRPLUS deterministically. "I don't think we'll ever have a readdir plus heuristic that makes everybody happy without userspace somehow telling us their intentions."
  • NOTIFY4_CHANGE_CHILD_ATTRIBUTES — examined and effectively set aside by Trond Myklebust: "Unlike delegations, notifications are asynchronous by design... the absence of that notification is insufficient to deduce that it is safe not to revalidate those attributes."
  • Benjamin Coddington's benchmarking scars: "We made the mistake of trying to improve the benchmark which resulted in performance regressions for real-world users."

No code was committed; the thread is a design discussion, but it surfaces several concrete improvement ideas that would touch the client and possibly the protocol.

GSS fore-channel slots vs. replay window — stopgap or structural fix?

Vjaceslavs Klimovs posted a patch capping GSS session fore-channel slots at 32 to mitigate a production krb5p streaming-write stall (stall to ~0 after 6.12→6.18 upgrade, bisected to on-demand slot growth). Chuck Lever delivered a detailed rebuttal: "the GSS window bounds relative lag, not concurrency... no ratio can close that gap and prevent reordering." He outlined three structurally correct fix directions (client-side spread throttling, per-connection GSS contexts, negotiated window size) and characterized the cap as "a probability knob, not an invariant." The author himself flagged two client-side problems not addressed by the patch: the default 64-slot over-commit across nconnect links, and the v6.16 RFC2203 seqno cache turning a recoverable graze into a hard EIO.

sunrpc pool_mode: hardcode to pernode

Jeff Layton posted v2 of his patch removing all non-pernode pool modes. Chuck Lever flagged a critical edge case: when nrservs < number of NUMA nodes, trailing pools get zero threads and work routed to those pools is never serviced. Layton proposed a two-part fix (minimum one thread per CPU-bearing node + enqueue fallback to a populated pool). NeilBrown added code-level nits and design opinions. No v3 yet.

Server-side bug fixes (client-impact)

nfsd inter-server copy offload: three UAF/race fixes

Jeff Layton posted a three-patch series fixing bugs in NFSv4.2 COPY/COPY_NOTIFY/OFFLOAD_CANCEL, all identified through LLM inspection: (1) a cpntf publish race allowing an authenticated client to oops the server via OFFLOAD_CANCEL; (2) a UAF in the statelist drain loop; (3) two interlocking UAF hazards in async copy cancel/shutdown (double nfsd_file_put() and kthread lifetime race). All carry Fixes: tags pointing to code in-tree for years.

svcrdma: slab-corrupting overflow in pull-up path

Chuck Lever posted a fix for a remote-exploitable memory corruption: a malicious RPC-over-RDMA client can trigger an out-of-bounds slab write and out-of-bounds DMA read by requesting a reply without providing a Write list or Reply chunk when the SGE budget is exhausted. The fix fails the request with ERR_CHUNK per RFC 8166 §4.5.3 rather than dropping the connection. Reported by Chris Mason (Meta), AI-assisted development.

NFSD admin state-revocation: startup NULL-deref

Following XIAO WU's KASAN-confirmed report of a NULL pointer dereference in unlock_filesystem during the startup window, Chuck Lever posted the follow-on fix switching all three unlock paths from testing nn->nfsd_serv to NFSD_NET_UP. Jeff Layton provided a careful re-derivation and Reviewed-by within a day. See also the original UAF thread where the new bug was discovered.

nfsd dir-delegation CB_NOTIFY recall fix (v3 folded)

Layton's v3 patch closing the vfs_getattr() masking gap flagged by Lever's AI-assisted review of v2 was folded into the upstream commit by Lever on June 21. This completes a three-round bug-fix saga ensuring that any client implementing RFC 8881bis directory delegations can rely on the server to either deliver the notification or recall the delegation. See also the v2 review thread.

pynfs: 26-patch directory delegation test suite (v3)

Layton posted v3 of his comprehensive pynfs test series covering all CB_NOTIFY notification types (ADD, REMOVE, RENAME, CHANGE_DIR_ATTRS), recall behavior, edge cases (cross-directory renames, rename-over with nad_old_entry), and lifecycle. Calum Mackay (Oracle) acknowledged receipt on June 23: "I have a bit of a backlog, again, but will get to these asap." These tests are the verification vehicle for the server-side CB_NOTIFY support landing in v7.3.

Stale block count debate: NFS vs. XFS

Jingbo Xu (Alibaba) posted a two-line patch to invalidate i_blocks after COMMIT, fixing xfstests generic/694 on NFSv4-over-XFS. Trond Myklebust NACKed firmly: "That sounds like an XFS bug, not an NFS bug... I fail to see why we should degrade the performance of the generic NFS client in order to address a bug in one of the back end filesystems." Brian Foster (Red Hat) reframed the question — is st_blocks changing across fsync actually a POSIX violation? — and suggested the xfstest may simply need adjustment for NFS. No resolution reached; the ball is with Xu and the XFS maintainers.

Themes this week

  1. Memory safety is the dominant theme. The 7.2 pull merged a dozen UAF/refcount fixes; new KASAN reports (xprt_put, svcrdma pull-up, nfsd copy offload) continue to surface in both client and server paths. AI-assisted review (Sashiko, Claude, gpt-5.5) is now routine in both patch authorship and review, catching issues that human reviewers miss — and the loop is closing: findings drive revisions that get folded within days.

  2. The NFS client's readdir/stat path remains the hardest optimization problem. The delegation behavior analysis thread crystallizes why: the kernel cannot see userspace intent, heuristics regress other workloads, and protocol-level solutions (NOTIFY4) have semantic limitations. The "statx-based readdirplus syscall" idea may be the most promising forward-looking direction.

  3. Protocol compliance gaps in pNFS/flexfiles are being systematically closed. Coddington's clora_changed fix, Snitzer's UNCACHEABLE_FILE_DATA support, and Bommarito's decoder-hardening campaign all target RFC 8881/5661 conformance issues that have been latent for years.

  4. Server-side work has direct client impact. The netlink stats interface, CB_NOTIFY directory delegations (v7.3), the latency-floor RFC, and the GSS slot/window debate all shape what clients will need to implement or adapt to in coming cycles.
