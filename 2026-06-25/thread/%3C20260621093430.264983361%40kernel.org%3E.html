Rostedt's trace_printk.h cleanup sparks pushback; sunrpc/debug.h quietly added an include

Summary

Rostedt's trace_printk.h cleanup sparks pushback; sunrpc/debug.h quietly added an include

Overview

This week's activity in this thread is a cross-listed kernel-wide discussion that landed on linux-nfs because one of the touched files is include/linux/sunrpc/debug.h. Steven Rostedt posted a two-patch series to remove <linux/trace_printk.h> from the ubiquitous kernel.h and replace it with a new CONFIG_TRACE_PRINTK_DEBUGGING option that injects the include via CFLAGS in the Makefile. The series is not an NFS bug fix or protocol change — it is a build-system/header-hygiene cleanup — but it has a small, concrete touchpoint for NFS developers: the SUNRPC debug header now needs to add its own #include <linux/trace_printk.h> (one of 21 files in the diff), and any developer using trace_printk() inside the NFS client or server will need to either enable the new config or add the include by hand.

The discussion itself is a textbook example of how a "trivial" header change can reignite a long-running debate about kernel build ergonomics, with Thomas Gleixner, Peter Zijlstra, Yury Norov, David Laight, Christophe Leroy and Randy Dunlap all weighing in over two days. No NFS maintainer (Layton, Lever, or the nfsd list) chimed in during this window; the sunrpc touch is a one-line include addition that did not generate specific NFS-side commentary.

The Patch Series (June 21)

Rostedt's cover letter frames the motivation in familiar terms:

"There's been complaints about trace_printk() being defined in kernel.h as it can increase the compilation time. As it is only used by some developers for debugging purposes, it should not be in kernel.h causing lots of wasted CPU cycles for those that do not ever care about it."

The two patches:

  1. PATCH 1/2 moves the non-trace_printk tracing-control prototypes (e.g. ftrace_dump()) back into kernel.h, because they are used by other common headers like rcu.h. Rostedt's rationale: "Prototypes are very cheap for the compiler and should not be an issue."
  2. PATCH 2/2 adds CONFIG_TRACE_PRINTK_DEBUGGING to kernel/trace/Kconfig and, when set, appends -include trace_printk.h to the Makefile CFLAGS so developers "can add trace_printk() without the need to add the include for it." The diff touches 21 files, including include/linux/sunrpc/debug.h (one added line), plus i915, ext4, powerpc KVM, hwtracing/stm, infiniband/hfi1, usb/early/xhci-dbc, and several ftrace samples.

Within minutes of posting, Rostedt flagged a self-inflicted problem:

"Bah, I only tested with the config option enabled, and missed some dependencies with it disabled. For instance, rcu.h also uses ftrace_dump() so that too needs to go into kernel.h."

The Pushback (June 21–22)

Thomas Gleixner delivered the sharpest early objection in a short note:

"IOW, you make it worse just because. With the header being separate I add the three trace_printk()s and the include to the source file I'm investigating. The recompile will build exactly this source file. Having to enable the config knob will result in a full kernel rebuild for no value. Seriously?"

Rostedt's reply, sent from the London Tube, reframed the option as a development-environment default rather than a per-debugging-session toggle:

"Like having lockdep enabled, this would always be set in the development environment. It's not something to only enable when you need to add a trace_printk. If you don't want to rebuild everything, by all means add the include file by file."

David Laight then challenged the underlying premise: "Isn't trace_printk() just an extern? Having it defined somewhere isn't going to make any difference to build times." Rostedt corrected him on the latency-sensitive design of the macro:

"No it is not. It is a macro to cut as many nanoseconds as possible as trace_printk() was created to debug tight race conditions and any added latency can make the race go away."

Yury Norov pushed back hardest on both patches, arguing against putting the prototypes in kernel.h:

"Please don't. Instead, you can split them out to trace_control.h, and include where needed. ... It's not about cost, it's about mess. kernel.h is included everywhere. Is that API needed everywhere? No, it's needed in literally 10 files. So, no place in kernel.h."

He then warned about the developer-experience trap of the config-gated approach:

"Developers who use trace_printk() on their development machine, will be really frustrated when their debugging code will break client build just because CONFIG_TRACE_PRINTK_DEBUGGING is disabled there. They will spend a day, at best, communicating with remote managers, and end up with adding #include <linux/trace_printk.h> in the files they touch. Is that your plan?"

Rostedt conceded on the header-splitting point: "Sure, I have no problem adding another header for this."

Peter Zijlstra entered on June 22 with the strongest C-style argument against the whole approach:

"Did you forget your C 101 class? If you use a function, you gotta include the relevant header. You don't see userspace saying: 'Hey, you know what, perhaps we should add stdio.h to every other header, just in case someone wants to printf()' either."

Rostedt's reply pointed to historical precedent: "If this was the way it was back in 2009, yeah sure. But the header wasn't need for 17 years. Now it suddenly will be."

Christophe Leroy asked for evidence: "Do we have a measurement of the increased compilation time?" Rostedt deferred to Norov, who then retracted the performance argument himself:

"I re-run compilation is a more strict environment, and the difference is negligible."

Randy Dunlap closed the loop on the C-101 point by citing Documentation/process/submit-checklist.rst, and Rostedt's final reply in the window acknowledged the cleanup burden:

"Because that is what you should do. But now you also need to remember to remove the include <linux/trace_printk.h> too."

NFS Relevance

The only direct NFS touchpoint in this thread is the one-line addition of #include <linux/trace_printk.h> to include/linux/sunrpc/debug.h in PATCH 2/2. That header is used by both the NFS client (fs/nfs/) and server (fs/nfsd/) for rpc_debug()-style trace_printk instrumentation, so:

  • NFS developers who use trace_printk() in their debug sessions will need to either enable CONFIG_TRACE_PRINTK_DEBUGGING in their local .config or add the include explicitly to any file they touch — exactly the workflow friction Norov and Gleixner warned about.
  • No NFS maintainer responded in this window; the sunrpc change is mechanical and was not separately reviewed on linux-nfs.
  • The broader debate (header hygiene vs. build ergonomics) will affect how future NFS client/server patches that sprinkle trace_printk() for race-condition debugging are written — if the series lands as posted, those patches must carry explicit includes.

Status and Outlook

  • Thread status: Open and unresolved as of the end of the window. Rostedt has not posted a v2 addressing Norov's trace_control.h suggestion or the missing-dependency issues he flagged on June 21.
  • Key open items: (a) where the tracing-control prototypes should live (kernel.h vs. a new trace_control.h); (b) whether the config-gated CFLAGS approach is acceptable given the full-rebuild cost Gleixner highlighted; (c) the lack of a measured build-time delta, which Norov's "negligible" remark effectively concedes.
  • NFS-specific: Nothing to track beyond the sunrpc include line; no NFS client or server behavior changes are implied by this series.
