KASAN slab-use-after-free in xprt_put: retested on Linus tree, still reproduces

Summary

[BUG] KASAN slab-use-after-free in xprt_put — first maintainer triage; bug confirmed to persist

Status this week: After sitting silent for a couple of weeks, the NFS/SunRPC client use-after-free thread finally got its first maintainer response. Anna Schumaker asked the reporter to retest against the current upstream tree on the strength of recently merged fixes, and Shuangpeng Bai promptly confirmed the bug still reproduces — so the issue is not resolved by the recent transport-lifecycle patches and remains open for root-cause work.

Bridge from prior weeks

The thread was opened on 2026-06-07 with a well-documented KASAN slab-use-after-free in xprt_put, reached via the rpc_free_client_work workqueue — a classic NFS/SunRPC client-side transport reference-counting / lifetime defect (not a protocol change or new feature). The original report included a minimal diagnostic patch, reproducer, and .config to make the race reliable. See the prior week's summary for the full initial trace and reproduction details.

This week's exchange (2026-06-24)

The discussion this week is short but consequential: it moved the bug from "untriaged" to "confirmed live on current mainline."

1. Anna Schumaker asks for a retest against current mainline

Anna, the NFS client maintainer, opened with a request that frames the whole thread's next step — recent fixes have landed in this area, so she wants to know whether the report is stale:

"There have been a handful of fixes in this area that were just merged upstream. Any chance you can check if the problem is still there with Linus's current tree (or with -rc1 when it releases after the weekend)?"

This is the key technical pivot of the week: rather than immediately diving into a root-cause analysis, Anna first wanted to establish whether the recently merged transport-lifecycle fixes already cover this report. That is standard triage for a corner of RPC object teardown that has been a recurring trouble spot.

2. Shuangpeng confirms the bug persists on current Linus tree

The reporter responded within hours with a clean retest, pinning it to a specific mainline commit:

"I retested this on current Linus tree, f0e6f20cb52b ("Merge tag 'ntfs3_for_7.2'"), and it still reproduces."

Crucially, he reports the failure is unchanged in shape — same fault class, same call path, only the expected address/line-number drift from the newer tree:

"The stack trace is essentially unchanged from the original report, aside from expected address and line-number shifts in the newer tree:"

BUG: KASAN: slab-use-after-free in xprt_put+0x13/0x50
Write of size 4 at addr ffff8881046bd000 by task kworker/1:3/8075
Workqueue: events rpc_free_client_work

Call Trace:
  xprt_put+0x13/0x50
  rpc_free_client_work+0x152/0x250
  process_scheduled_works / worker_thread / kthread

And the free side is again an RCU-deferred slab release, which keeps the diagnosis pointing at a race between RCU-delayed transport destruction and a late reference drop:

"Freed by task 0 on cpu 1 at 249.878823s: __rcu_free_sheaf_prepare → rcu_free_sheaf → rcu_core"

Technical read

  • Classification: Bug fix (NFS/SunRPC client), specifically a slab use-after-free in the transport reference-counting path — xprt_put() writing into an already-freed 2048-byte kmalloc-2k object during rpc_free_client_work teardown.
  • What this week established: The recently merged fixes in the area do not resolve this report; the bug is live on current mainline (f0e6f20cb52b). That rules out "already fixed" and means a distinct, still-unpatched lifetime/ordering defect remains.
  • Likely shape (carried over): A missing/early reference or an ordering gap between RCU-grace-period-deferred transport freeing and the rpc_free_client_work client-teardown sequence — i.e., a late xprt_put() lands on a transport whose slab object was already reclaimed by the RCU path.

Where things stand / what to watch for

  • The bug is confirmed open and reproducible on current Linus tree; Anna's retest request has been satisfied with a negative result (still broken).
  • The next expected step is a real root-cause analysis from the SunRPC/NFS client maintainers — either an RCU-grace-period vs. workqueue ordering fix or a missing reference keeping the transport alive across rpc_free_client_work.
  • Worth cross-referencing with prior KASAN UAF reports in the same RPC teardown area, which suggest this corner of the client transport lifecycle is a recurring trouble spot.

Bottom line: First substantive triage on the xprt_put use-after-free. Anna Schumaker asked whether recent upstream fixes had already addressed it; Shuangpeng Bai retested on current mainline and confirmed "it still reproduces" with an essentially unchanged trace — so this NFS client bug remains unresolved and is now queued for a genuine fix.
