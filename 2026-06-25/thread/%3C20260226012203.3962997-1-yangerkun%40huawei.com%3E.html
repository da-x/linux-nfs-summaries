NFS file-lock UAF fix finally lands in linux-next after 16-week wait

Summary

NFS file-lock UAF fix finally lands in linux-next after a long wait

Classification

This is a bug fix on the NFS client side — not a new feature or protocol change. It resolves a use-after-free (UAF) hazard during traversal of the per-inode file-lock list in the delegation-claim and lock-reclaim paths, carrying a Fixes: tag pointing to commit c69899a17ca4 ("NFSv4: Update of VFS byte range lock must be atomic with the stateid update").

Bridge from prior weeks (brief)

This thread has been running since late February 2026, when Huawei's Yang Erkun opened it with an RFC patch to protect NFS file-lock list traversal using nfsi->rwsem instead of flc_lock. The bug — originally identified by Li Lingfeng — arises because functions like nfs_delegation_claim_locks and nfs4_reclaim_locks must release flc_lock to call blocking RPC code, opening a UAF window. In March, maintainer Jeff Layton reviewed the patch and awarded it a Reviewed-by ("Nice work!"), corroborated by an AI-assisted review that found no regressions. April and May brought nothing but polite pings from Erkun as the well-vetted fix languished unmerged.

This week's activity: the resolution

This week is the payoff of a long wait. On June 23, Erkun sent yet another nudge, noting that the patch had been reviewed but left to sit for a long time:

"Gently ping..."
"This patch has been reviewed, but leave alone here for a long time..." [id://9b27efad-f22a-45b9-b080-1552acf50016@huawei.com]

NFS maintainer Anna Schumaker responded the same day with the news everyone in the thread had been waiting for — the patch has landed in her linux-next branch:

"The patch is in my linux-next branch right here: https://git.linux-nfs.org/?p=anna/linux-nfs.git;a=commit;h=4837fb36219e6c08b666bc31a86841bad8526358" [id://261c255e-2cc5-4f27-8239-e708f1c9f95a@app.fastmail.com]

Erkun replied the next day, thanking Schumaker and explaining why he had kept pinging — he had been checking only the tree listed in MAINTAINERS and never realized the commit had already landed:

"Aha, thanks for this! MAINTAINERS only point git://git.linux-nfs.org/projects/trondmy/linux-nfs.git and I did not found this commit exists. Sorry for the noise...." [id://a12a6847-b74c-4fe8-9ad8-b1e0c607bc9d@huaweicloud.com]

Key technical arguments (recap)

The fix rests on two pillars, both settled in the earlier weeks of discussion:

  1. Per-inode protection via nfsi->rwsem. The previous guard (so_delegreturn_mutex) is per-state-owner, but a single inode can carry multiple nfs4_state objects, allowing races between state owners on the same inode. Switching to nfsi->rwsem aligns with the already-established pattern in nfs4_reclaim_locks.

  2. Relocation of locks_lock_inode_wait. The call was moved out of the asynchronous RPC callbacks (nfs4_lock_done, nfs4_locku_done) into the synchronous caller _nfs4_proc_setlk, so it can execute under nfsi->rwsem without risking deadlocks. Erkun argued this does not regress the original atomicity bug fixed by commit c69899a17ca4, because later commits (notably 0460253913e5) drain slots before reclaim, and the delegation-claim path sets the stateid only once.

Final conclusions

The discussion has reached a clean conclusion. After roughly sixteen weeks from initial RFC submission — including Jeff Layton's Reviewed-by since March and no objections ever raised — the patch is now in Anna Schumaker's linux-next branch (commit 4837fb36219e), on its way toward mainline. The exchange this week was cordial and brief: a final ping, confirmation of the merge, and an apology for the noise caused by Erkun checking only the MAINTAINERS-listed tree rather than Schumaker's linux-nfs git repository.
