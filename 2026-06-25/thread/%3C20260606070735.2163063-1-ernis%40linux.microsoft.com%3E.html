RDMA ib_device_attr int→u32 (v7): Vennela accepts all Shevchenko style fixes, v8 promised

Summary

RDMA ib_device_attr int→u32 — Author accepts full style review; v8 on the way

This week at a glance

The single message in this thread's window is Vennela's June 19 reply to Andy Shevchenko's detailed code-style review delivered the previous week. It is a point-by-point acceptance of every suggestion, closing out the review cycle and committing to a v8 that incorporates all changes. No new patches were posted this week; the thread is in a quiet "author is fixing" phase.

Bridge from prior weeks

As summarized last week, Vennela's Microsoft patch series (now at v7, targeting rdma-next) widens the signed-int capability counter fields in struct ib_device_attr to u32. The motivation is a genuine type-correctness bug:

"The capability counter fields in struct ib_device_attr are declared as signed int, but these values are inherently non-negative. Drivers maintain their cached caps as u32 and assign them directly into these int fields; if a cap exceeds INT_MAX the implicit narrowing yields a negative value visible to the IB core."

The series spans 22 files across the IB core, ULPs (iSER/iSERt, SRP/SRPT, RTRS, iPOIB), NVMe-oF, RDS, SMBdirect, and the NFS/RDMA stack. Last week saw Shevchenko's line-by-line style review (~8 categories of minor issues) and Stefan Metzmacher's first formal Acked-by for the smbdirect hunks.

This week's message: Vennela's acceptance (June 19)

The reply opens with a brief apology for the delay:

"Hi Andy, Sorry for delayed response."

Vennela then walks through each of Shevchenko's points in order, accepting every one. The key exchanges:

1. rounddown_pow_of_two() reinvention (rxe driver): Shevchenko had flagged the hand-rolled pattern 1 << (fls(qattr->max_qp_req_rd_atomic_resc) - 1) as a reinvention of an existing kernel helper. Vennela simply confirms:

"Acked."

2. Remaining min_t() usages: Shevchenko had asked, "What about this one?" pointing at a missed min_t(unsigned int, rds_ib_retry_count, 7) in the RDS code. Vennela acknowledges the oversight:

"Sorry. I missed this one, I'll update it."

And for the broader category:

"I'll remove all the min_t usages in the next version."

3. Signed-arithmetic audit (the most critical technical point): Shevchenko had warned that changing fields from int to u32 could silently alter arithmetic semantics — particularly division and multiplication that previously relied on signed overflow being undefined behavior:

"please check that none of these (and beyond) were not used in signed multiplication or (which is more disasterous) division. Otherwise it might be subtle issues that will be hard to debug."

Vennela confirms the audit was performed:

"Yes I have checked that for all the variables I updated."

This is the most important technical assurance in the thread. It means every consumer of the now-u32 fields — including the NFS/RDMA client code in xprtrdma/verbs.c and frwr_ops.c — has been verified to behave correctly under unsigned arithmetic.

4. Variable declaration ordering ("xmas tree" convention): For Shevchenko's repeated point about reversed declaration order:

"Okay. I'll update all such instances."

5. SRPT module parameter ABI concern: Shevchenko had noted the int → uint change to srpt_srq_size could theoretically break ABI for anyone passing negative values via sysfs. Vennela accepts:

"Yes. I'll be doing it in the next version."

6. NVMe target conditional style: For the suggestion to replace a ternary with an explicit if:

"Okay. I'll update all such instances."

The message closes with a blanket commitment:

"Thankyou for all your suggestions. The next version will be incorporated with all these changes."

Assessment

This is a bug fix / type-correctness cleanup series, not a new feature or protocol change. The core defect — signed narrowing of inherently non-negative RDMA capability values — is well understood and uncontroversial. What remains before merge is purely stylistic: helper-function usage, declaration ordering, line-length conventions, and one missed min_t().

The trajectory across seven revisions over six weeks shows clear convergence. The substantive correctness concerns (underflow guards in the NFS/RDMA frwr_ops.c path, NVMe host zero-division guard, format-string fixes) were resolved by v7. Shevchenko's review shifted to code style, and Vennela's full acceptance this week means v8 should be merge-ready pending rdma-next maintainer pickup.

NFS/RDMA relevance

The NFS client portions of the series (xprtrdma/verbs.c, frwr_ops.c, svc_rdma_transport.c) are unlikely to change materially in v8 — Shevchenko's feedback targeted RTRS, NVMe target, iPOIB, and RDS code. The critical NFS/RDMA fix remains the unsigned underflow guard in frwr_query_device(), which prevents a device reporting zero max_sge_rd from producing an SGE count of UINT_MAX - 1 and breaking RDMA transport negotiation for NFS over RDMA clients. Vennela's confirmation that all variables were checked for signed-arithmetic misuse provides additional assurance that the NFS/RDMA consumers are safe.
