Layton posts pynfs v3 dir-delegation testcases; Mackay acknowledges with review backlog

Summary

pynfs v3: 26-patch directory delegation test suite lands, awaiting Oracle review

Overview

This week's activity in this thread is dominated by a single event: Jeff Layton posted v3 of his 26-patch pynfs series adding directory delegation testcases to the pynfs framework, followed four days later by a brief acknowledgment from Calum Mackay at Oracle confirming he has the patches queued for review. This is squarely a test-infrastructure contribution in service of a protocol feature (RFC 8881bis directory delegations with CB_NOTIFY), not itself a bug fix — though it does include one small internal test-harness fix.

Bridge from Prior Weeks

The series has been in flight since September 2025, when Layton first posted v1 (7 patches) introducing the NOTIFY4_GFLAG_EXTEND flag and a handful of basic tests. v2 (25 patches) landed in mid-April 2026 with expanded CB_NOTIFY coverage. The long gap between v2 and v3 is explained in the cover letter:

"Long delay since v2, but the CB_NOTIFY patches only recently got merged into Chuck's nfsd-testing branch. They're currently slated to make v7.3."

That server-side series — the nfsd CB_NOTIFY support work reviewed by Chuck Lever over the past several weeks — is what these pynfs tests are ultimately validating. This week's activity in the sibling threads shows that series is actively being hardened: Layton posted v2 of the dir-attr CB_NOTIFY recall fix on June 19 (same day as this pynfs v3), which Lever's AI-assisted review flagged as incomplete, and then v3 was posted and folded the next day after closing the vfs_getattr() masking gap. The pynfs tests in this thread are the client-side verification harness that will exercise exactly those server paths once they land in v7.3.

The v3 Series (June 19)

The cover letter summarizes the changes from v2:

"This version of the series fixes some potential state leaks that Scott pointed out, and adds a patch to make the output a bit less chatty with normal settings."

The 26 patches add 1,147 lines (primarily in a new st_dir_deleg.py file) across six files. The test coverage breaks down into several categories:

Foundation patches (01–02)

  • Patch 01/26 adds the NOTIFY4_GFLAG_EXTEND flag from RFC 8881bis to pynfs's XDR definitions. Layton notes: "In practice, the Linux nfs server requires that the client support this flag if it's requesting anything other than a recall-only delegation."
  • Patch 02/26 adds a GETFH operation to the end of the create_obj() compound, needed by later tests that must verify filehandles in ADD notifications.

Recall-only tests (03–09)

These test basic directory delegation behavior that should work on current mainline kernels:

  • Basic GET_DIR_DELEGATION handout/recall/return
  • Duplicate GET_DIR_DELEGATION requests
  • pass_warn() when server doesn't support dir delegations — "This should make it safe to keep the directory delegation tests in the 'all' group."
  • Recall triggered by remove, rename, mkdir, and link from a second client.

CB_NOTIFY tests (10–25)

These require the new CB_NOTIFY server support:

  • No notifications without GFLAG_EXTEND — verifies CB_RECALL is issued instead of CB_NOTIFY.
  • Unrequested notification type triggers recall.
  • REMOVE_ENTRY notifications, ADD_ENTRY notifications, and RENAME_ENTRY notifications.
  • Child attributes in ADD notification and CHANGE_DIR_ATTRS notification.
  • mkdir triggers ADD notification and DELEGRETURN stops notifications.
  • Filehandle verification in ADD notification — this is where the GETFH addition from patch 02 pays off.
  • Cross-directory rename tests: REMOVE on source and ADD on target.
  • Link triggers ADD notification and same-client changes don't trigger notifications.
  • Two rename-over tests exercising the nad_old_entry field: cross-directory and within-directory. The cross-directory test cites the RFC: "Per RFC 8881 Section 18.26.4, when the removal is done atomically with the rename, a separate NOTIFY4_REMOVE_ENTRY notification will not be generated."

Housekeeping (26)

  • Demote chatty log messages to debug level: "Most of these are note terribly useful in the normal case."

Internal test-harness fix

Patch 24/26 also includes a small but important bug fix to the test harness itself:

"Also fix _getDirDeleg to initialize cb.changes as a list and use extend() to accumulate notifications, so tests that receive multiple CB_NOTIFY callbacks can see all notifications."

Without this fix, any test expecting more than one callback in sequence would silently lose earlier notifications.

Mackay's Acknowledgment (June 23)

Calum Mackay's reply is brief but sets expectations:

"Thanks very much Jeff, I have a bit of a backlog, again, but will get to these asap."

The "again" suggests this is a recurring pattern — Oracle's review capacity for pynfs has been a bottleneck across multiple series. No technical feedback or objections were raised in this window.

Significance for NFS Client Development

  • Testing the untested. The server-side CB_NOTIFY directory delegation support is landing in v7.3, but until now there was no automated test coverage for it in pynfs. This 26-patch series closes that gap comprehensively, covering recall behavior, all notification types (ADD, REMOVE, RENAME, CHANGE_DIR_ATTRS), edge cases (cross-directory renames, rename-over with nad_old_entry, same-client suppression), and lifecycle (DELEGRETURN stopping notifications).
  • Client-side implementation dependency. Layton has previously stated that the server patches shouldn't merge without a complete client-side implementation to test against. These pynfs tests are the verification vehicle for that requirement — they exercise the exact protocol paths a Linux NFSv4.1 client would use when implementing RFC 8881bis directory delegations.
  • Graceful degradation. The pass_warn() approach in patch 05/26 ensures the tests can run against any server without breaking CI, while still providing signal when CB_NOTIFY support is present.
  • RFC 8881bis protocol validation. The tests encode specific RFC expectations — particularly around nad_old_entry behavior in rename-over scenarios and the distinction between within-directory RENAME_ENTRY and cross-directory ADD+REMOVE notification pairs. These are exactly the kinds of subtle protocol semantics that are easy to get wrong in a client implementation.

Status and Outlook

  • Thread status: Open, awaiting Mackay's review. No technical objections or requests for changes have been raised in this window.
  • Relationship to server series: The tests target the CB_NOTIFY dir-delegation series currently in Chuck Lever's nfsd-testing branch, slated for v7.3. The sibling bug-fix threads (dir-attr recall fix) are actively being resolved in parallel.
  • Open items: Review by Mackay; potential further revisions based on his feedback; eventual merge into pynfs once both the server and client implementations are in place.
