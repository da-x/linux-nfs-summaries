RDMA ib_device_attr int→u32 (v8): Vennela posts merge-ready revision, all style fixes incorporated

Summary

RDMA ib_device_attr int→u32 — v8 posted; the long style-review cycle closes

This week at a glance

The single in-window message is Erni Sri Satya Vennela's June 19 posting of v8, the eighth revision of his Microsoft patch series that widens the signed-int capability counter fields in struct ib_device_attr to u32. This is the follow-through on the commitment he made in the companion v7 thread just hours earlier, where he told Andy Shevchenko:

"Thankyou for all your suggestions. The next version will be incorporated with all these changes."

No maintainer merge decision or further review has landed within this window — the next three replies (Vennela's July 2 self-reply, Shevchenko's July 2 follow-up, and Vennela's July 3 response) all fall outside the week ending 2026-06-25. The thread is therefore in a "posted, awaiting rdma-next maintainer pickup" state at window close.

Bridge from prior weeks

As summarized in the companion v7 thread, this is a bug fix / type-correctness cleanup, not a new feature or protocol change. The core defect has been stable since v1:

"The capability counter fields in struct ib_device_attr are declared as signed int, but these values are inherently non-negative. Drivers maintain their cached caps as u32 and assign them directly into these int fields; if a cap exceeds INT_MAX the implicit narrowing yields a negative value visible to the IB core."

Stefan Metzmacher's Acked-by for the smbdirect hunks was already in hand by v7, and Shevchenko's line-by-line style review (declaration ordering, leftover min_t(), reinvented rounddown_pow_of_two(), signed-arithmetic audit, SRPT module-parameter ABI) had been fully accepted by Vennela on June 19.

What v8 actually changes

The v8 changelog in the commit message is essentially a checklist of Shevchenko's review items, now executed:

  • Field coverage completed. The remaining non-negative counter fields — max_ee_rd_atom, max_ee_init_rd_atom, max_ee, max_rdd, max_raw_ipv6_qp, and max_srq_wr — are converted to u32. Notably, max_srq is deliberately kept as int:

    "keep max_srq as int (its consumer compares it against ib_device.num_comp_vectors, still int)." That's a thoughtful carve-out that avoids dragging the ib_device struct into scope.

  • All leftover min_t() removed. "Drop all remaining min_t() where plain min() now works." This directly answers Shevchenko's earlier "What about this one?" on the missed RDS site, and Vennela's promise to "remove all the min_t usages in the next version."

  • SRPT module parameter ABI change. srq_size is made unsigned int so its min() stays a plain min(). This was the one point with real ABI implications (negative sysfs values), and Vennela had flagged it: "Yes. I'll be doing it in the next version."

  • Style cleanups. Ternary-inside-min() replaced with if (x) x--;; send_queue_depth min() reordered to min(value, CONST); reverse-xmas-tree declaration order restored; single-line collapses where 100-column budget allows; %d → %u for the newly-unsigned fields.

The diffstat is unchanged in shape from v7: 24 files, +117/−123, spanning include/rdma/ib_verbs.h, the IB core (cq.c), rxe, qedr, iPOIB, iSER/iSERt, SRP/SRPT, RTRS, NVMe host/target, SMBdirect, RDS, and the NFS/RDMA stack (net/sunrpc/xprtrdma/{frwr_ops.c,svc_rdma_transport.c,verbs.c}, include/linux/sunrpc/svc_rdma.h).

NFS/RDMA relevance

The NFS client portions of the series are now effectively frozen — Shevchenko's review targeted RTRS, NVMe target, iPOIB, and RDS code, not the xprtrdma hunks. The substantive NFS/RDMA fixes that landed in earlier revisions remain:

  • frwr_ops.c unsigned underflow guard — reordering the check before the subtraction so a device reporting zero max_sge_rd cannot produce an SGE count of UINT_MAX − 1 and break RDMA transport negotiation for NFS-over-RDMA clients.
  • svc_rdma_transport.c min_t(int, …) → plain min() — the type-mismatch cleanup that was one of v5's headline items.
  • verbs.c / svc_rdma.h — sc_max_send_sges to unsigned int, inline_sge_count to u32, and %d → %u in diagnostic prints.

Vennela's earlier confirmation that he audited every updated variable for signed-arithmetic misuse ("Yes I have checked that for all the variables I updated") provides the assurance that these NFS/RDMA consumers are safe under unsigned semantics.

Assessment

Seven revisions over six weeks have converged cleanly. The substantive correctness concerns (underflow guards, zero-division guard in NVMe host, format strings) were resolved by v5–v7; Shevchenko's review shifted to style; Vennela accepted every point and delivered v8 the same day. With Metzmacher's ack already attached and no outstanding technical objections visible in the thread metadata, v8 is merge-ready pending rdma-next maintainer pickup. The follow-up messages after this window (July 2–3) will tell us whether that pickup happened or whether a final nit remains.
