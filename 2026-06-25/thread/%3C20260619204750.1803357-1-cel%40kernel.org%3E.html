Summary

lockd: fix TEST handling when not all permissions are available

This week's thread is a short, decisive bug-fix exchange around the Linux NFS client/lockd stack. Chuck Lever posted a patch authored by NeilBrown to correct how lockd handles NLM TEST (i.e., F_GETLK) requests when the caller does not have all the permissions lockd was demanding, and Sasha Levin confirmed it is queued for 7.0.

The bug

The patch explains the core defect in plain terms:

"The F_GETLK fcntl can work with either read access or write access or both. It can query F_RDLCK and F_WRLCK locks in either case."

"However lockd currently treats F_GETLK similar to F_SETLK in that read access is required to query an F_RDLCK lock and write access is required to query a F_WRLCK lock."

The practical symptom, per the commit message, is that qemu fails when it accesses a read-only filesystem image (e.g. an ISO) over NFS:

"This is wrong and can cause problems - e.g. when qemu accesses a read-only (e.g. iso) filesystem image over NFS (though why it queries if it can get a write lock - I don't know. But it does, and this works with local filesystems)."

The bug was reported upstream via Debian bug 1128861 by Tj, and the patch carries a Fixes: tag pointing at commit 4cc9b9f2bf4d ("nfsd: refine and rename NFSD_MAY_LOCK").

Why it surfaced now

A particularly interesting journalistic detail is why a long-standing bug only started biting recently. Chuck/Neil explain that the over-strict permission check has been in lockd "at least since git history began," but was masked by nfsd behavior:

"This behaviour of lockd - requesting O_WRONLY access to TEST for exclusive locks - has been present at least since git history began. However it was hidden until recently because knfsd ignored the access requested by lockd and required only READ access for all locking requests (unless the underlying filesystem provided an f_op->open function which checked access permissions)."

"The commit mentioned in Fixes: below changed nfsd_permission() to NOT override the access request for LOCK requests and this exposed the bug that we are now fixing."

So the regression chain is: a recent nfsd change tightened permission handling for LOCK operations, which finally surfaced an older latent lockd defect. The fix is therefore on the lockd side (the NFS client's server-side locking daemon), not in nfsd itself.

The fix

The patch touches five files (fs/lockd/svc4proc.c, fs/lockd/svclock.c, fs/lockd/svcproc.c, fs/lockd/svcsubs.c, include/linux/lockd/lockd.h) and restructures how the open mode is derived for TEST requests:

  • nlm_do_fopen() now accepts O_RDWR as a mode and succeeds if either an O_RDONLY or an O_WRONLY file can be opened.
  • nlm_lookup_file() takes a mode argument from its caller instead of deducing it from the lock type, and forwards it to nlm_do_fopen().
  • nlm4svc_retrieve_args() and nlmsvc_retrieve_args() detect TEST requests and pass O_RDWR to nlm_lookup_file, while keeping the previous mode for non-TEST requests. They also set lock->fl.c.flc_file to whichever file was actually opened, for TEST.
  • nlmsvc_testlock() stops recomputing the mode and uses whatever is stored in lock->fl.c.flc_file.

In other words, a TEST request no longer demands a specific read/write permission; it just needs some access, matching what local filesystems allow for F_GETLK.

Known limitation (explicitly out of scope)

NeilBrown flags a related but unaddressed issue in the commit message:

"Note that there is another issue that this patch does not address. The flock(.., LOCK_EX) call is permitted on a read-only file descriptor. Linux NFS maps this to NLM locking as whole-file byte-range locks. nfsd will see this as though it were fcntl( F_SETLK (F_WRLCK)) and will now require write access, which it might not be able to get."

"It is not clear if this is a problem in practice, or what the best solution might be. So no attempt is made to address it."

This flock(LOCK_EX) on read-only fds case is left as a follow-up candidate rather than being folded into this fix.

Outcome

Sasha Levin's reply was brief and conclusive:

"Queued for 7.0, thanks."

The patch carries Reviewed-by: Jeff Layton <jlayton@kernel.org> and the standard NeilBrown/Chuck Lever sign-offs. The discussion is a clean bug fix (not a new feature or protocol change) targeting NFS client-side lockd behavior, with the regression window tied to a recent nfsd permission-handling commit.
