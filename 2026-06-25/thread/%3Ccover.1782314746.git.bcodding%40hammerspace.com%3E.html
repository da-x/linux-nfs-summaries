SUNRPC: RFC for a latency floor for interactive NFS clients via sparse-flow dispatch

Summary

SUNRPC: A Latency Floor for Interactive Clients via Sparse-Flow Dispatch (RFC)

Classification

New feature / performance improvement — a three-patch RFC series targeting the NFSD/SUNRPC server-side transport dispatcher. It is not a protocol change and not a traditional bug fix; it addresses a long-standing fairness deficiency in how nfsd services ready transports, which manifests as interactive NFS client sessions stalling whenever a bulk (backlogged) client saturates the server's thread pool.

Background (Brief Bridge)

This RFC is the direct successor to two earlier discussions:

  1. The per-client fair-scheduling thread from May/June 2026, in which the list debated whether nfsd should enforce proportional fairness between clients. The consensus that emerged — as Coddington frames it — was a reframe by Chuck Lever:

    "This is starvation avoidance, not proportional fairness (per Chuck's reframe on [1])."

  2. Chuck Lever's slot-growth clamp RFC ("Stop NFSv4.1 slot-growth heuristic from rewarding busy clients"), which caps how large a busy session's slot table can grow relative to the thread ceiling. Coddington explicitly bases this series on that work:

    "This series is based on Chuck's 'Stop NFSv4.1 slot-growth heuristic from rewarding busy clients' [2], and both A and B above include it -- so the A/B delta isolates this series and the clamp does not account for the improvement."

The two are complementary: the clamp limits how many slots a busy session can hold (nfsd accounting), while this RFC changes the order in which ready transports are dispatched (sunrpc dispatch layer). Coddington notes that "a slot-capped session still fills the pool, so the dispatch-layer floor is still wanted on top of it."

The Problem

NFS server pools dispatch ready transports in strict FIFO order. A transport's position in the queue is independent of how much work it already has in flight. The practical consequence:

"A client that keeps many requests in flight -- nconnect, a deep v4.1 slot table, or simply several connections -- sits in that queue on equal terms with a client that has been idle. So the request a user is waiting on (a stat, an open, a directory listing) waits behind a backup job's backlog, even though servicing it costs a single round trip."

The user-visible symptom: an interactive session stutters whenever a bulk client is busy.

The Approach (Three Patches)

Coddington posted the full RFC on June 24 with three patches:

Patch 1/3 — Add a second per-pool ready queue

Adds sp_xprts_hi alongside the existing sp_xprts, initialized with each pool. No functional change yet; it is purely structural groundwork.

"Nothing is enqueued to it yet, so this is no functional change; a later patch routes transports with no requests in flight onto it and drains it ahead of sp_xprts."

Patch 2/3 — Dispatch idle transports ahead of backlogged ones

The core dispatch logic: when a transport is enqueued, if xpt_nr_rqsts == 0 (no prior requests in flight), it goes on the high-priority queue; otherwise it stays on the normal queue. The dequeue path drains sp_xprts_hi first.

"A flow whose last reply has completed reads zero and jumps the queue, while a flow with requests still in flight stays in the bulk queue."

Key design properties:

  • No client identity: keys only on a transport's own in-flight depth, so it covers v3, v4.0, and v4.1 uniformly.
  • No new lock: each queue is an independent lwq with its own ordering; svc_thread_should_sleep() simply tests both.
  • Always on, nothing to tune.

Patch 3/3 — Grant a burst allowance (64 dispatches)

A single idle-to-active transition only protects the leading RPC of a burst. Interactive work (a syscall, a page fault) fans out into many correlated RPCs. This patch grants a budget of SVC_XPRT_HI_BURST (fixed at 64) high-priority dispatches when a transport transitions from idle to active.

"The budget refills only on an idle-to-active transition, so a flow that stays continuously backlogged spends its budget once and then lives in the bulk queue: a client cannot hold the high-priority queue by keeping its connections busy or by opening more of them."

Aggregate throughput is within 1% A vs B at saturation (~1290 ops/s) — "the dispatcher reorders, it does not throttle."

Review Discussion (June 25)

Chuck Lever's deferred-close bug (Patch 2/3)

Lever identified a concrete flaw in the classification logic: deferred transport closes are enqueued through the same svc_xprt_enqueue() path but with xpt_nr_rqsts != 0 (the slot is still held). Because the high-priority queue is drained first, a deferred close on a backlogged connection would wait behind idle-flow traffic — precisely when the server most needs to reclaim resources.

"Control work isn't request work, and svc_xprt_ready() already treats XPT_CONN|XPT_CLOSE|XPT_HANDSHAKE as a class distinct from XPT_DATA. Routing that class to the high-priority queue regardless of the request count keeps the two consistent."

He proposed a fix: route any transport with XPT_CONN | XPT_CLOSE | XPT_HANDSHAKE set to the high-priority queue unconditionally, in addition to the zero-in-flight check.

Lever also flagged a pre-existing issue identified by sashiko (an automated patch-review tool) that "might be amplified by this patch" and should be addressed as a prerequisite:

"You should also have a look at the pre-existing issue that sashiko identified: it might be amplified by this patch, so we should consider addressing that issue as a pre-requisite to this series."

Coddington's response

Coddington accepted both points immediately:

"Excellent - if we v1, I'll add this fix." "I'll head over there (cool - sashiko looks smart) and give that issue attention for any v1."

Chuck Lever's deep-dive on the re-arm trigger (Cover letter reply)

In a longer analysis posted later on June 25, Lever probed the most critical assumption in the design: does an interactive flow actually reach xpt_nr_rqsts == 0 often enough under contention to keep its budget refilled? His concern:

"My worry was that a sustained interactive flow (a tree walk holding a couple of RPCs in flight) never reaches zero, spends its 64 once, and then rides the normal queue."

He ran a kprobe-based measurement on an uncontended v4.2 loopback walk of a 7500-file tree (~15.5k server RPCs):

depth 0 : 25.6%   <- re-arms the 64-credit budget
depth 1 : 62.3%
depth 2 : 12.2%
depth 3 : ~0

"So zero recurs about every fourth enqueue. ~3 credits spent between refills against a budget of 64 -- the credit never approaches zero and the flow stays high-priority for the whole walk."

But he immediately noted the caveat: this was uncontended loopback, where nfsd keeps up and depth collapses naturally. The real risk is under pool contention — "aggressor saturating the threads, the interactive flow's replies delayed, depth staying elevated, the zero-crossings that refill credits becoming rare." He asked Coddington to run the same probe under his aggressor + 10ms service-time hook, providing a ready-made ftrace kprobe recipe.

"The question that settles it: for the interactive xprt under load, does the depth==0 fraction hold up, or do you see depth>=1 runs longer than 64? If it holds, the trigger is fine and the uncovered tail is just the N>64 knee you already document. If it collapses, that's the argument for a low-watermark refill rather than exact-zero."

Open Questions (as of end of window)

Coddington explicitly posed two questions to the list in the cover letter:

  1. Budget shape: "is the budget (64 here) the right shape, and should it be fixed, derived from the thread count, or hinted by the v4.1 slot table?"
  2. Cooperative vs. adversarial framing: "does the cooperative framing hold, or must we resist deliberate sparse-shaping?" — i.e., can a client game the system by sending ≤64 RPCs, draining, and repeating?

Lever's follow-up added a third implicit question: whether the exact-zero re-arm trigger is robust under contention, or whether a low-watermark refill is needed.

The series also deliberately leaves out (for follow-up):

  • Inter-tier deficit round-robin to bound bulk-queue starvation under sustained high-priority load.
  • LOCALIO (out of scope; local clients bypass RPC dispatch entirely).

Status and Outlook

As of the end of this week's window, the RFC has received substantive technical review from Chuck Lever with two concrete action items for v1:

  1. Fix the deferred-close routing to the high-priority queue.
  2. Address the sashiko-identified pre-existing issue as a prerequisite.

Additionally, Coddington is expected to provide kprobe data under contention to validate (or refute) the exact-zero re-arm assumption. No further replies from Coddington or other participants fell within this week's window; the next activity in the thread (Neil Brown's replies and Coddington's responses) begins June 26–29, outside this summary's scope.

NFS Client Development Relevance

While this series is server-side (nfsd/sunrpc), its impact on the NFS client experience is direct and significant: it establishes a latency floor that prevents interactive client operations (stats, opens, directory listings, page faults) from being starved by bulk workloads. The design's protocol-agnostic nature — keying on transport in-flight depth rather than client identity — means it uniformly protects NFSv3, v4.0, and v4.1 clients without any client-side changes. For deployments where a single NFS server serves both interactive desktops and backup/CI pipelines, this is the kind of dispatch-layer fix that eliminates the "my NFS share freezes during backups" complaint without requiring per-client QoS configuration.
