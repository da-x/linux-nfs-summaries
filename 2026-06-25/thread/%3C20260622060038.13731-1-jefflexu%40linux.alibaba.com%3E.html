NFS: invalidate i_blocks after COMMIT — stale block count bug fix NACKed by maintainer

Summary

NFS: invalidate i_blocks after COMMIT to fix stale block count on NFSv4

Type: Bug fix (proposed) — Status this week: NACKed by the client maintainer, discussion ongoing.

The proposed patch

On Monday, Jingbo Xu of Alibaba posted a two-line patch to fs/nfs/write.c marking NFS_INO_INVALID_BLOCKS on successful COMMIT completion. The stated problem: the NFSv4 COMMIT compound does not include GETATTR, and nfs4_commit_done_cb never refreshes inode attributes — yet every WRITE marks NFS_INO_INVALID_BLOCKS via nfs_post_op_update_inode_force_wcc_locked. As Xu put it:

"After COMMIT, i_blocks remains stale until the next stat() triggers a full revalidation. In writeback-heavy workloads where COMMITs happen without intervening stat() calls, the cached block count can stay indefinitely wrong."

The fix would force the next nfs_getattr requesting STATX_BLOCKS to issue a GETATTR with SPACE_USED, "matching NFSv3 behavior where nfs3_commit_done already calls nfs_refresh_inode with the wcc_data post-op attributes." The patch fixes xfstests generic/694 on an NFSv4.0 loopback setup (notably, it carries an Assisted-by: Qoder:Qwen3.7-Max tag).

The maintainer's pushback

Trond Myklebust, the Linux NFS client maintainer, replied quickly and bluntly the same day:

"That sounds like an XFS bug, not an NFS bug. COMMIT isn't changing the data contents of the file: it is just ensuring that the existing data is persisted onto disk."

Xu confirmed the backend was indeed XFS and posted a detailed AI-generated root-cause analysis, cc'ing linux-xfs. The sequence: the client's last UNSTABLE WRITE piggybacks a GETATTR that caches SPACE_USED before the server-side delayed allocation has materialized metadata blocks; syncfs then triggers COMMIT, which forces local writeback and allocates a bmap/extent-tree block (+8 sectors), but per RFC 7530 §16.3.3 the COMMIT response carries only a write verifier — no attributes — so the stale cached value persists until remount. Xu noted the failure "is much likely reproducible on NFS upon XFS, while NFS upon EXT4 succeeds for 50 consecutive test runs," and that XFS itself passes the test locally.

Myklebust doubled down, conceding "this may indeed be a consequence of XFS's delayed allocation feature" but arguing that:

"that hardly changes the fact that it would be a violation of the POSIX rules for how write(), fsync() and stat() are supposed to work in this situation. My point is that I fail to see why we should degrade the performance of the generic NFS client in order to address a bug in one of the back end filesystems (in this case XFS) being exported. So strong NACK to this patch from me."

Xu, admitting "I'm not familiar with NFS," responded simply: "Understand. Just have no idea which is the proper way to fix this."

Brian Foster's reframing

Brian Foster of Red Hat stepped in on Tuesday with a more nuanced take, first questioning Myklebust's POSIX framing:

"Is the implication here that st_blocks changing across an fsync is a POSIX violation? If so, can you clarify where that is said? My understanding is that the rules/definitions here are rather vague and st_blocks is a simple count of blocks allocated to the inode (i.e., so this is ambiguous wrt delalloc, metadata blocks, etc.), but I could be missing something."

Foster then walked through the mechanics — NFS caches a post-op block count on write-out; fsync/COMMIT doesn't refresh it; XFS changes the count during fsync via metadata allocation — and offered a different diagnosis of generic/694:

"It feels a little odd to me to call this an fs bug, tbh. The intent of the test seems more to catch an incorrect block count calculation as opposed to enforce any sort of caching or accounting rules... It seems more like the issue is just that the fsync that was added for consistency at the fs level is not sufficient for NFS due to this attribute caching."

He closed by questioning whether this matters in practice: "Is this actually a problem for NFS in practice or will it eventually get the latest value from the server? If the latter, maybe the test simply needs to be fixed up or skipped for NFS..?" He also flagged that g/694 can use fallocate or fall back to buffered write, asking whether fallocate support over NFS is a factor.

Where things stand

The thread ends with the patch firmly NACKed by the maintainer on performance grounds (forcing GETATTRs after every COMMIT in the generic client), while the XFS-list cc and Foster's questions leave open three possible resolutions: fix it in XFS, adjust/skip the xfstest for NFS, or find a cheaper invalidation path. No conclusion was reached this week; the ball is back with Xu and the XFS maintainers.
