ZhangGuoDong's two-part leak-fix series: NFSv4.1 FREE_STATEID refcount and pNFS blocklayout device cleanup

Summary

Overview

A compact, self-contained bug-fix series landed on the linux-nfs list this week from ZhangGuoDong (KylinOS). The two patches, posted together on 2026-06-25, target two distinct resource-leak paths in the NFS client: one in the NFSv4.1 stateid-freeing RPC machinery and one in the pNFS blocklayout device parser. No discussion has developed yet — both messages are original submissions with no replies as of end-of-week.

This is squarely a bug-fix series (not a new feature or protocol change), addressing reference-count and memory leaks that surface on error paths.

Patch 1/2: NFSv4.1 nfs_client refcount leak in nfs41_free_stateid

Posted by ZhangGuoDong, this patch fixes a reference-count leak on the nfs_client structure in fs/nfs/nfs4proc.c.

The author's description is precise about the failure mode:

"nfs41_free_stateid() takes a reference on the nfs_client before allocating the FREE_STATEID calldata. If the calldata allocation fails, the function returns -ENOMEM without dropping that reference."

And the reason the existing cleanup path doesn't catch it:

"The normal async RPC release path drops the reference from nfs41_free_stateid_release(), but that path is not reached when calldata allocation fails."

The fix is minimal — 3 insertions, 1 deletion in fs/nfs/nfs4proc.c — dropping the nfs_client reference before returning the -ENOMEM error. This matters because a leaked nfs_client refcount prevents the client structure (and everything it pins: sockets, state, mounts) from ever being freed, which is particularly painful for short-lived NFSv4.1 sessions or clients that are repeatedly created and destroyed.

Patch 2/2: pNFS blocklayout device leaks on parse failure

The companion patch addresses a more involved set of leaks in fs/nfs/blocklayout/dev.c, the pNFS block layout driver's device parsing code. The author identifies three related problems:

1. Child array leak in concat/stripe parsers:

"bl_parse_concat() and bl_parse_stripe() allocate a child device array and then parse each child in turn. If parsing a child fails, the failed child is not counted in nr_children and the parent may be left with a children array that bl_free_device() will not release when nr_children is zero."

The fix releases both the failed child and any already-parsed siblings before propagating the error upward.

2. bl_free_device() not releasing the children array:

"Also make bl_free_device() release the child array whenever the children pointer is set, so that partially initialised concat or stripe devices are cleaned up correctly."

This is a defensive hardening: rather than relying on nr_children > 0 as the trigger for freeing the array, the cleanup now keys off the pointer itself being non-NULL. This catches any future code path that might leave children set with nr_children == 0.

3. Double-free risk in bl_parse_scsi():

"bl_parse_scsi() can also fail after assigning d->bdev_file and dropping the file reference. Clear the pointer after fput() so that an outer cleanup path does not put it again."

This is a classic use-after-fput / double-put hazard: the code drops the struct file reference but leaves the dangling pointer in the device struct, so an outer error handler would call fput() on it a second time. Clearing the pointer after the explicit fput() closes that window.

The patch is 15 insertions, 6 deletions in fs/nfs/blocklayout/dev.c.

Discussion and Status

As of the end of this reporting week (2026-06-25), no replies have been posted to either patch. The thread consists solely of the two original submissions. Given the small, well-scoped nature of both fixes — a one-line refcount drop and a targeted error-path cleanup in the blocklayout parser — these are the kind of patches that typically receive a quick "Reviewed-by" or direct pick-up by the NFS maintainer without extended discussion.

Significance for NFS Client Development

Both patches reinforce a recurring theme in kernel NFS client maintenance: error-path resource management. The NFSv4.1 stateid machinery and the pNFS blocklayout driver both involve multi-step allocation sequences where intermediate failures must unwind cleanly. Leaks on these paths are low-frequency (they require an kmalloc failure or a malformed layout response) but high-impact in long-running systems:

  • A leaked nfs_client refcount is effectively unrecoverable at runtime — the client and all its mounts are pinned forever.
  • Leaked blocklayout device structures accumulate on every failed layout parse, which can happen transiently during server-side reconfiguration or network glitches that corrupt layout responses.

The series comes from KylinOS contributors, continuing a steady stream of hardening patches from non-upstream-primary vendors into the mainline NFS client.
