NFSD: New NULL-deref bug found in the startup window of unlock_filesystem

Summary

NFSD: A second, distinct crash lurking in the unlock_filesystem paths

This week's activity on this thread was a short but sharp exchange that surfaced a new, previously unreported bug adjacent to — but separate from — the post-shutdown use-after-free fix series Chuck Lever posted last week. The discussion is squarely about an NFSD (server-side) bug fix, not a client change, protocol change, or new feature.

Bridge: where things stood last week

Last week, Chuck Lever's three-patch series fixed a local-admin-triggerable slab-use-after-free in both the procfs and netlink unlock_filesystem paths. The fix moved the async COPY cancellation (nfsd4_cancel_copy_by_sb()) inside the nfsd_mutex-held, nn->nfsd_serv-checked region. Jeff Layton endorsed it quickly:

"This all looks good. Reviewed-by: Jeff Layton jlayton@kernel.org"

The series was awaiting merge into nfsd-next when this week's messages arrived.

This week: an AI review flags a residual hole, and XIAO WU confirms it with KASAN

On June 21, XIAO WU posted a detailed report replying directly to PATCH 1/3. The trigger was an external AI code review (Sashiko) that flagged the nn->nfsd_serv check as insufficient:

"I came across a Sashiko AI code review [1] that flagged a remaining issue in write_unlock_fs() — the nn->nfsd_serv check is not sufficient to guarantee that nfsd_startup_net() has run and allocated the state tables."

XIAO WU then went beyond the AI's static finding and reproduced the crash in QEMU with KASAN on kernel 7.1.0-rc7-next-20260612. The mechanism: creating an NFSD listener via portlist sets nn->nfsd_serv, but if no threads are started, nfsd_startup_net() never runs and the state tables remain NULL. Writing to unlock_filesystem then passes the nn->nfsd_serv check and calls nfsd4_cancel_copy_by_sb(), which walks a NULL hashtable:

"Oops: general protection fault, probably for non-canonical address 0xdffffc0000000000 … KASAN: null-ptr-deref in range [0x0000000000000000-0x0000000000000007] … RIP: 0010:nfsd4_cancel_copy_by_sb+0x184/0xa70"

The minimal reproducer was three shell commands:

echo 2049 > /proc/fs/nfsd/portlist
mount -t nfsd nfsd /proc/fs/nfsd
echo /mnt > /proc/fs/nfsd/unlock_filesystem

Chuck Lever's response: confirms the crash, corrects a detail, and draws the line between two bugs

Chuck Lever replied the same afternoon, confirming the finding while making an important technical distinction. He first validated the mechanism:

"Thanks for the careful analysis and the reproducer. I agree the crash is real. nfsd_create_serv() sets nn->nfsd_serv from the portlist and netlink listener paths, none of which run nfsd_startup_net(), so nn->nfsd_serv can indeed be non-NULL while the NFSv4 state tables are still NULL."

He then offered a small but notable correction to the report — the array actually dereferenced is nn->conf_id_hashtbl, not nn->nfs4_client_hashtbl:

"One correction: the array the walk dereferences is nn->conf_id_hashtbl, not nn->nfs4_client_hashtbl. Both are allocated together in nfs4_state_create_net(), reached only via nfsd_startup_net(), so your mechanism holds either way; the name in the report is just off."

The most significant part of his reply was clarifying that this is a different bug from the one the patch series fixes, and that it predates the patches:

"However, this crasher is a different bug from the one this series addresses, and AFAICT it is not introduced by this patch. Before this change the cancel ran unconditionally, so the same NULL conf_id_hashtbl walk was reachable in the startup window (and more besides). The nn->nfsd_serv guard added here narrows the post-shutdown case but does not cover the startup window, because nn->nfsd_serv is set before the tables exist."

He drew a precise KASAN-level distinction between the two bugs:

"The two also differ at KASAN: this patch fixes a slab-use-after-free on a freed-but-not-cleared conf_id_hashtbl; what you hit is a null-ptr-deref on a never-allocated one."

The path forward

Chuck identified the correct guard for the startup window and committed to addressing it separately:

"The correct guard for the startup window is NFSD_NET_UP, which is set at the tail of nfsd_startup_net() exactly when the state tables become valid, rather than nn->nfsd_serv. nfsd4_revoke_states() walks the same tables and nfsd_nl_unlock_filesystem_doit() repeats the pattern, so a fix needs to cover both unlock paths. I'll address that in a separate follow-up and add your Reported-by."

Why this matters

This exchange highlights an important subtlety in NFSD's state-table lifecycle: nn->nfsd_serv is set at listener-creation time (via portlist or netlink), but the actual NFSv4 state tables (conf_id_hashtbl, nfs4_client_hashtbl) are only allocated later, inside nfsd_startup_net(). Any code that walks those tables must guard on NFSD_NET_UP — not nn->nfsd_serv — to be safe across the full startup-to-shutdown window. The fact that an AI review caught this, and a community member validated it with a concrete KASAN reproducer, underscores how these lifecycle windows remain a fertile source of latent bugs in NFSD's admin interfaces.

The original three-patch series remains valid and reviewed; the new NULL-deref fix is expected as a separate follow-up from Chuck Lever with a Reported-by: for XIAO WU.
