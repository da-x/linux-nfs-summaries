NFS delegations behavior analysis: warm ls -l GETATTR storm on large directories

Summary

NFS delegations behavior analysis — the "warm ls is slower than cold" puzzle

This week's thread (all 12 messages landed on Tue, 2026-06-23) opened with a fresh performance study by Piyush Sachdeva and quickly drew in the core Linux NFS client maintainers — Jeff Layton, Benjamin Coddington, Anna Schumaker, Trond Myklebust — plus Tigran Mkrtchyan (DESY) and Daire Byrne. It is squarely about NFS client caching behavior (directory delegations, actimeo, READDIRPLUS vs GETATTR), not a bug fix or a protocol change per se, but it surfaces several concrete improvement ideas that would touch the client and possibly the protocol.

The setup: a benchmark that surprises

Piyush posted a micro-benchmark of ls against a flat directory with ~100K files, comparing cold vs warm passes under actimeo=5s, rdirplus=force, ACLs off in his opening analysis:

"if the next ls -l is issued after the actimeo, a massive GETATTR storm hits the server, doing stat() calls for every file in the directory. As a result, the performance of this warm ls -l run ends up being worse than the cold pass."

His numbers: on the warm pass the client issues 100,000 GETATTRs (vs 27 READDIRPLUS calls and ~23.6 MB received on the cold pass) and takes ~62 s vs ~14 s for the cold run. The diagnosis: the directory delegation keeps the dcache valid so no READDIR is needed, but file attributes are only cached per actimeo, so every stat() falls through to a single-file GETATTR — which turns out to be far more expensive than one batched READDIRPLUS.

He proposed three fixes: (1) fall back to READDIRPLUS when the client detects attribute cache misses, (2) extend directory delegations to cover file attributes (a protocol change), or (3) a bulk GETATTR operation.

The core difficulty: the kernel can't see userspace's intent

Jeff Layton framed the fundamental problem in his first reply:

"ls is such a hard workload to get right, because we don't really get an indication in the kernel of what userland's intentions are. It's basically a readdir() call followed by a bunch of stat()'s, but at the point where we're getting the readdir() call, we don't know if userland intends to stat() those files or not."

He pushed back on Piyush's READDIRPLUS-fallback idea with a pointed question: "Why should you decide to do a READDIRPLUS at that point instead of a regular READDIR?" — i.e., the client has no signal at readdir time that stats are coming. He then asked whether existing heuristics could be tuned, noting in his follow-up that "Ben did the latest pass of trying to tune the heuristics here" and asking what workloads must not regress.

Tigran's angle: a statx-based readdirplus syscall

Tigran Mkrtchyan (DESY) weighed in in his reply, arguing for a way to "get all attributes in one go" — effectively letting userspace declare its intent up front. Anna Schumaker responded with her take:

"We do something like that already. I don't think we'll ever have a readdir plus heuristic that makes everybody happy without userspace somehow telling us their intentions. I know a statx-based readdir plus system call probably sounds crazy, but something like that would go a long way to take all the guesswork out of things on our end."

That "statx-based readdirplus syscall" idea — letting the application say "I will stat these entries" so the client can pick READDIRPLUS deterministically — became one of the thread's most discussed proposals.

Benjamin Coddington: benchmarking scars and a delegation question

Benjamin Coddington brought practical war stories from his Red Hat readdir work:

"We also found that our performance benchmarks rarely matched the most common real-world workloads. We made the mistake of trying to improve the benchmark which resulted in performance regressions for real-world users."

He also noted prior ideas about teaching readdir to respond to fadvise flags, while conceding utilities try to stay filesystem-agnostic, and offered a pragmatic fallback: "sometimes the simplest thing might be to just use more directories on NFS." He then turned to the delegation mechanics with a self-directed question — "can we simply re-hydrate the dentry cache from the directory page mappings if the delegation is still valid?" — and answered it himself minutes later:

"we don't keep the file attributes in the mappings today. And, more to the point - the directory delegation doesn't protect those file attributes either. We'd need NOTIFY4_CHANGE_CHILD_ATTRIBUTES implemented."

Daire Byrne: negative lookups as a sibling problem

Daire Byrne connected this to a long-standing pain in his reply:

"I have also long hoped for a way to cache or speed up 'negative' lookups using something akin to directory delegations... It would be nice if a client that got the directory contents could also serve negative lookups until the server told it that something had changed. But as has been explained to me multiple times before, there is no mechanism to say that a client 'has the complete cache of directory contents'."

Jeff's root-cause refinement and the NOTIFY4 detour

Jeff sharpened the diagnosis in his later message:

"the client skips checking directory attributes before trusting the dcache because of the delegation (which is good), but the inodes those dentries point to have an attrcache timeout, and we end up doing a GETATTR for each statx() call when a readdirplus would have been cheaper."

He floated watching for bursts of statx() from one pid on one directory as a trigger to switch to READDIR, while admitting "that sounds horrid to get right and keep working." On the NOTIFY4_CHANGE_CHILD_ATTRIBUTES route he sketched a Linux-server implementation path — fsnotify already supports FS_EVENT_ON_CHILD | FS_ATTRIB — but warned it "could be very chatty" and would require nfsd to send multi-page callbacks. Benjamin agreed in his reply that it "could easily end up having the opposite effect of optimizing performance by amplifying op counts for information the client might not actually use."

Trond's closing verdict: notifications don't solve this

Trond Myklebust, Linux NFS client maintainer, delivered the final word on the notification-based approach:

"Unlike delegations, notifications are asynchronous by design. Upon reception of a notification, you may deduce that you should revalidate the attributes on a file. However the absence of that notification is insufficient to deduce that it is safe not to revalidate those attributes. So when it comes to informing the client whether to use READDIR or READDIRPLUS, I'm sceptical concerning the value of throwing NOTIFY4_CHANGE_CHILD_ATTRS at the problem."

Where things stand

  • No code was committed this week; the thread is an analysis/design discussion rather than a bug fix.
  • The consensus root cause: directory delegations protect dentries but not file attributes, so post-actimeo ls -l degrades into a per-file GETATTR storm that beats READDIRPLUS on cost.
  • The most promising forward-looking idea is userspace signaling intent (Anna's "statx-based readdirplus system call", echoing Tigran's "all attributes in one go"), since kernel-side heuristics have repeatedly regressed other workloads per Benjamin's Red Hat experience.
  • The NOTIFY4_CHANGE_CHILD_ATTRIBUTES route was examined and effectively set aside by Trond on semantic grounds (asynchronous notifications can't prove absence of change).
  • Practical mitigations remain: rdirplus=force, larger actimeo, or sharding large flat directories.

This thread is a useful snapshot of why the NFS client's readdir/stat path remains one of the hardest corners of the stack to optimize without userspace cooperation.
