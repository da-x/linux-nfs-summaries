NFSv4.1/pnfs: bound layout-type count in decode_pnfs_layout_types (Trond flags open-coded helper)

Summary

NFSv4.1/pnfs: bounding the FSINFO layout-type count — a new client-side XDR-wrap fix, with a maintainer's "open coding" caveat

Overview

This week's activity in this thread is brief but pointed: Michael Bommarito posted a single-patch bug fix on 2026-06-22 that closes an integer-overflow-driven out-of-bounds read in the NFSv4.1 pNFS client's decode_pnfs_layout_types(), and Linux NFS client maintainer Trond Myklebust replied about ninety minutes later with a terse but consequential review note. This is squarely a bug fix (a security-relevant robustness fix on the NFS client), not a new feature or protocol change, and it carries Cc: stable@vger.kernel.org for backporting.

Bridge from Prior Week

This submission is the direct continuation of Bommarito's pNFS decoder-hardening campaign. As summarized last week, he had posted a two-patch series on 2026-06-14 fixing the same XDR-wrap class in decode_getdeviceinfo() — where a server-supplied notification bitmap length, scaled by four in 32-bit arithmetic, wraps to zero for lengths ≥ 0x40000000 and lets the verify loop read up to ~2^30 words past the inline XDR buffer. That prior thread had no maintainer reply within its window. This week's patch is explicitly framed as the companion:

"This is the decode_pnfs_layout_types companion to the same XDR-wrap class fixed in decode_getdeviceinfo (NFSv4.1/pnfs: bound notification bitmap length in decode_getdeviceinfo)."

The earlier series also remains awaiting review; no v2 or maintainer ACK has appeared for it within this week's window.

The Patch (June 22)

Bommarito's submission targets fs/nfs/nfs4xdr.c (9 insertions, 1 deletion) and is anchored to the original commit that introduced the layout-type list:

"Fixes: ca440c383a58 ("pnfs: add a new mechanism to select a layout driver according to an ordered list")" "Cc: stable@vger.kernel.org"

The defect is laid out with the same precision as the GETDEVICEINFO report. The decoder reads a server-controlled u32 count and then reserves 4 * count bytes:

"decode_pnfs_layout_types() reads a server-controlled u32 count and then reserves 4 * count bytes:

fsinfo->nlayouttypes = be32_to_cpup(p);
...
p = xdr_inline_decode(xdr, fsinfo->nlayouttypes * 4);

The multiplication is u32, so any count >= 0x40000000 wraps to a small value and xdr_inline_decode() reserves too few bytes."

Two secondary observations sharpen the analysis. First, the existing NFS_MAX_LAYOUT cap is applied after the reservation, so it cannot save the decode:

"The NFS_MAX_LAYOUT cap is applied only afterwards, so the subsequent reads run past the short reservation."

Second, the obvious array_size() guard is itself unsafe because of how xdr_inline_decode() rounds its argument:

"array_size() is not a safe guard here either: xdr_inline_decode() runs its nbytes argument through XDR_QUADLEN(((l) + 3) >> 2), which wraps SIZE_MAX to a zero-word reservation instead of failing."

The fix rejects counts that cannot fit in the u32 multiplication before the reservation, and switches to sizeof(__be32) for explicit size arithmetic:

"Reject counts that cannot fit in the u32 multiplication before the reservation, and use sizeof(__be32) so the size arithmetic is explicit."

The threat model is a malicious or compromised NFSv4.1+ server (or man-in-the-middle on an unprotected mount):

"A malicious NFSv4.1+ server returning a crafted FATTR4_FS_LAYOUT_TYPES attribute triggers this on the client during FSINFO decode."

Testing and KUnit coverage

As with the GETDEVICEINFO series, Bommarito reproduced the bug under KASAN — this time on a UML build:

"Reproduced on a UML KASAN build with a KUnit case that feeds decode_pnfs_layout_types() an xdr buffer whose nlayouttypes is 0x40000001: nlayouttypes * 4 wraps, xdr_inline_decode() reserves a short buffer, and the decode reads past xdr->end (KASAN slab-out-of-bounds read). With this patch the count is rejected (-EIO) before the reservation."

He deliberately decoupled the test from the fix so it can be accepted or dropped independently:

"The KUnit test can ride as a separate patch (matching the decode_getdeviceinfo series). Before/after logs available on request."

The sign-off block again credits AI assistance: "Assisted-by: Claude:claude-opus-4-8."

Trond Myklebust's Review (June 22)

Myklebust's reply is short — a single sentence after quoting the patch — but it reframes the change from "add a bounds check" to "use the existing helper":

"This is just open coding xdr_stream_decode_uint32_array(), and doing so incorrectly."

That one line carries two implications:

  1. The fix should be a refactor, not a hand-rolled guard. The kernel already provides xdr_stream_decode_uint32_array() for exactly this pattern — reading a server-supplied count followed by that many __be32 words with proper bounds handling. Bommarito's patch reimplements the loop and bounds check by hand; Myklebust is saying the correct upstream shape is to call the helper instead, which would also make the GETDEVICEINFO-series fix consistent if it touches similar patterns.
  2. "Doing so incorrectly" suggests the hand-rolled version has a residual defect beyond the wrap itself — most plausibly that the post-hoc NFS_MAX_LAYOUT cap and the new pre-reservation bound do not together cover every edge the helper would (e.g., the interaction between the u32 multiply, the XDR_QUADLEN rounding inside xdr_inline_decode(), and the final cap). Myklebust does not elaborate in this message; the expectation is that Bommarito will rework the patch to call the helper.

Evolution of the Discussion and Current State

Within this week's window the thread has exactly two messages: the patch and the maintainer reply. There is no v2, no further back-and-forth, and no ACK — the discussion is at the "review comment received, rework expected" stage. The trajectory so far:

  • June 14 (prior week): Bommarito posts the GETDEVICEINFO notification-bitmap fix + KUnit series; no maintainer reply in that window.
  • June 22 (this week): Bommarito posts the FSINFO layout-type companion fix; Myklebust replies within ~90 minutes pointing at xdr_stream_decode_uint32_array().

The pattern across both submissions is consistent: a precise, KASAN-reproduced, stable-tagged client-side bug fix from the same author, with AI-assisted sign-offs, and a maintainer who is engaging quickly but steering toward the canonical XDR helper rather than accepting hand-rolled bounds checks.

Significance for NFS Client Development

  • Decoder robustness against hostile servers. Both fixes in this campaign target the same class of bug — server-controlled u32 counts multiplied in 32-bit arithmetic before an xdr_inline_decode() reservation — and both are reachable from a malicious or compromised NFSv4.1+ server (or MITM on an unprotected mount). Closing them reduces the attack surface of the pNFS client's GETDEVICEINFO and FSINFO decode paths, which run early in mount and layout setup.
  • The helper-first lesson. Myklebust's "open coding … incorrectly" note is a useful signal for future decoder work: when xdr_stream_decode_uint32_array() (or the corresponding string/array helpers) already exists, the upstream-preferred fix is to call it rather than hand-roll bounds checks. This will likely shape how Bommarito reworks both this patch and, if applicable, the GETDEVICEINFO series.
  • Stable backport intent. Both patches carry Cc: stable@vger.kernel.org, so once accepted they are expected to flow into stable trees — relevant for any distribution shipping an affected kernel.

Status and Outlook

  • Related open thread: The GETDEVICEINFO notification-bitmap series from 2026-06-14 is still awaiting maintainer review; if Myklebust applies the same "use the helper" lens there, that series may also be reworked.
