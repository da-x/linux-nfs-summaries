pNFS/flexfiles: honor clora_changed and report cancelled I/O (PATCH 0/3)

Summary

pNFS/flexfiles: honor clora_changed and report cancelled I/O

Type: Bug fix series for the NFSv4.1+ pNFS client, addressing a long-standing protocol-compliance gap in how the Linux client handles CB_LAYOUTRECALL callbacks under RFC 8881 (the NFSv4.x flexfiles layout specification).

The problem

Benjamin Coddington opened a three-patch series on Wednesday, June 24, targeting v7.1, that exposes a subtle but serious flaw in the pNFS client's layout-recall handling. The cover letter lays out the background:

"RFC 8881 section 20.3.3 lets CB_LAYOUTRECALL carry clora_changed: when it is FALSE the client may flush modified data to the data servers before returning the layout; only when it is TRUE should it stop writing to the DS and redirect through the MDS."

The Linux client had been decoding the cbl_layoutchanged field but silently ignoring it ever since commit b739a5bd9d9f ("NFSv4/flexfiles: Cancel I/O if the layout is recalled or revoked"), which made the client cancel in-flight data-server I/O on every recall, regardless of intent. Coddington flags the consequence bluntly:

"…cancelling in-flight DS I/O unconditionally -- which can leave a write incomplete at the DS with no write layout held."

In other words, when a server sent an unchanged recall (the layout is still valid, the client just needs to return it), the client was needlessly aborting writes that may already have reached the data server — and those orphaned writes could land after the LAYOUTRETURN, which the metadata server would then see as a write with no layout.

The three patches

Patch 1/3 (report clora_changed in the cb_layoutrecall_file tracepoint) is an observability improvement: it gives nfs4_cb_layoutrecall_file its own tracepoint event definition so that the intent of a recall (changed vs. unchanged) becomes visible in ftrace output rather than being "otherwise invisible."

Patch 2/3 (honor clora_changed when recalling a layout) is the core fix. It threads the recall's clora_changed value through pnfs_mark_matching_lsegs_return() and only cancels in-flight I/O when the layout is actually changing (restriping or a failed storage device). For an unchanged recall, the existing deferred-return path now waits for in-flight writes to drain before sending LAYOUTRETURN. Coddington notes that other callers — those tearing down or returning layouts for their own reasons — "continue to cancel as before," so the behavior change is scoped precisely to the callback path.

Patch 3/3 (report cancelled I/O as a layout error) closes the reporting loop for the cases where cancellation is warranted (changed recall or revoke). The problem: cancellations completed with -EAGAIN, which ff_layout_io_track_ds_error() did not recognize — it "fell through the switch and recorded nothing, so no error was reported to the server." Coddington's fix avoids keying on -EAGAIN (which is overloaded in the RPC layer) by cancelling with -ECANCELED instead, then mapping that to NFS4ERR_NXIO — the same status already used for transport errors that leave a write incomplete. The error is then reported via LAYOUTERROR / LAYOUTRETURN so the MDS can "reconcile the affected mirror instance."

A notable subtlety in Patch 3: because the client itself aborted the I/O (rather than discovering a device failure), it deliberately skips marking the data server unreachable and forcing an additional layout return. Coddington explains:

"Unlike a genuine transport error, though, we aborted the I/O ourselves and have no evidence the device is at fault, so once the error is recorded we skip marking the device unreachable and forcing a further layout return."

He also confirms the retry path is unchanged: both NFS4ERR_NXIO and -ECANCELED are no-ops in ff_layout_async_handle_error(), which "still resets the I/O to pNFS (or the MDS), so it is re-driven as before."

Review feedback

Anna Schumaker reviewed the series within roughly 40 minutes of submission, issuing two small nits:

  1. On Patch 1, she flagged a stale API usage in the new tracepoint code:

    "Note that Jeff had some patches that went into 7.2 to store the nfs fileid directly in the inode. The NFS_FILEID() macro has been removed, and you should use inode->i_ino instead." (review reply)

  2. On Patch 2, she requested documentation for the new parameter:

    "Can you also add a description for the new 'cancel_io' parameter to the documentation right above this function?" (review reply)

Neither comment objects to the technical approach; both are housekeeping items for a v2. No further replies were posted within this week's window, so the series is pending a revised posting.

Significance

This is squarely a bug fix with protocol-compliance implications: the client was violating RFC 8881 §20.3.3 by treating every layout recall as a "layout changed" event. The practical risk — writes landing at a data server after the layout has been returned, leaving the MDS unable to reconcile mirror state — is exactly the kind of silent data-integrity hazard that pNFS deployments are most exposed to during restriping or DS failure events. The series is small (92 insertions across five files) but touches three distinct layers: tracepoint observability, the generic pNFS recall path in pnfs.c, and the flexfiles layout driver's error reporting.
