NFS fileid cleanup lands for v7.3 after arm32 LTP regression is diagnosed and fixed

Summary

NFS Client: fileid Removal Lands for v7.3 After an arm32 Test Regression

Background (bridging prior weeks)

In mid-May, Jeff Layton posted a four-patch series to remove the now-redundant fileid field from struct nfs_inode, enabled by the VFS change in v7.1-rc1 that widened inode->i_ino to a 64-bit value. The goal was code simplification and an 8-byte-per-inode memory saving, plus deprecation of the legacy enable_ino64 knob. As summarized last time, the series went up on 2026-05-12 with no immediate replies, targeting v7.2.

This week: a ping, a review, and a merge — then a regression report

The thread sat dormant for over five weeks before activity resumed this week (June 21–23). The arc of the discussion moved from "will this land?" to "it landed, but it broke an arm32 test."

The ping. On June 21, Layton nudged the maintainers, noting the series had slipped past its original target:

"i just noticed that this never made v7.2. Maybe consider for v7.3?"

The review and merge confirmation. Benjamin Coddington picked it up quickly on June 22, replying to the cover letter with a clean endorsement — Reviewed-by: Benjamin Coddington <bcodding@hammerspace.com> — after quoting the series' rationale that "v7.1-rc1 contains patches to make inode->i_ino to be a u64."

Anna Schumaker then confirmed the series was already in motion, telling Layton it wasn't merely under consideration but actively queued:

"These are actually the first four patches in my linux-next branch for the pull request I'm planning on sending (hopefully) later today."

So the cleanup is effectively merged for v7.3 — a notable resolution after five weeks of silence.

The technical meat: an arm32 regression in the LTP ioctl10 test

The most substantive exchange this week was a side-thread on PATCH 1/4 (store the full NFS fileid in inode->i_ino). Mark Brown reported a test failure triggered by that patch, with a LAVA bisect log and a pointer to his scheduler job. He isolated the symptom:

"Note that the vm_inode value is arm32's ULONG_MAX." "arm64 seems unaffected, I didn't really investigate but I'll note that unsigned long is 32 bit on arm."

Layton diagnosed the root cause by examining the LTP ioctl10 test source. The test parses /proc/self/maps with an sscanf() that reads the inode column into an unsigned long:

"Note that it's trying to stuff the inode number field into an unsigned long. Before this patch, the maps file would have printed the old (hashed) inode number on 32-bit. Now, it prints the full 64-bit inode number."

He then explained the silent-overflow behavior — a genuinely useful aside for anyone parsing /proc files — quoting his own analysis of glibc:

"In practice, glibc's scanf internally uses strtoul/strtoull, which on overflow store ULONG_MAX/ULLONG_MAX and set errno = ERANGE. However, scanf itself does not propagate ERANGE to the caller — it still returns 1 (success). So you'd silently get ULONG_MAX stored."

Layton concluded this was a test bug rather than a kernel regression:

"We could argue that this is a bug in the testcase. It assumes that the maps file will never print a value larger than ULONG_MAX in that field, and I don't see why it would make that assumption in this day and age."

He also raised a broader compatibility question worth watching:

"Are there actual programs in the field that scrape the maps file that might be affected by this change?"

The fix. On June 23, Layton proposed an LTP patch — [PATCH LTP] ioctl10: fix the sscanf() call to handle 64-bit inode on 32-bit arch — that widens the parsed field. As he put it:

"Change the testcase to allow for a full 64-bit inode number on all arches. The value it's compared to is already 64-bits so widening this field is all that is necessary."

He planned to send it to the LTP list but asked the community to verify it on arm32: "it would be nice if someone could confirm the fix on arm32." Mark Brown replied later that same day (body not captured in this window), presumably closing out the regression thread.

Conclusions

  • Classification: This is primarily a client-side cleanup/modernization (removing redundant fileid storage and legacy hashing/compat code), with one incidental real-world bug fix surfacing — not in the kernel, but in an LTP test that assumed 32-bit inode numbers in /proc/self/maps.
  • Outcome: The series is confirmed merged into Anna Schumaker's linux-next branch for v7.3, with a Reviewed-by from Benjamin Coddington.
  • Open item: The arm32 LTP ioctl10 fix needs on-target confirmation; Layton also left an open question about whether real-world /proc/maps scrapers could be affected by the now-visible 64-bit inode numbers on 32-bit architectures.
