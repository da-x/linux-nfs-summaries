Summary

pNFS/flexfiles: honor clora_changed and report cancelled I/O (v2)

Type: Bug-fix series for the NFSv4.1+ pNFS client (RFC 8881 / flexfiles layout). This week's activity is the v2 resubmission of a three-patch series that fixes a long-standing protocol-compliance gap in how the Linux client handles CB_LAYOUTRECALL callbacks.

What happened this week

The only new activity in this window is Benjamin Coddington posting the v2 series on Thursday, June 25 — a clean re-roll of the three patches that closed out Anna Schumaker's review nits from v1 (posted June 24 and summarized in the prior week). No new replies or objections appeared within this week's window, so the series is now awaiting maintainer pickup.

The cover letter explicitly calls out what changed between revisions:

"Changes on v2: Anna: fix missing kerneldoc comment, remove FILE_INODE"

Both items trace directly to Schumaker's earlier feedback — the removed FILE_INODE/NFS_FILEID() usage (replaced with inode->i_ino per Jeff Layton's 7.2 fileid work) and the requested kerneldoc for the new cancel_io parameter on pnfs_mark_matching_lsegs_return(). The series is now based on "Anna's nfs-for-7.2-1," a step up from v1's v7.1 target, reflecting its move into the 7.2 merge window.

The technical substance (unchanged from v1)

The core problem, restated in the cover letter, is that RFC 8881 §20.3.3 lets CB_LAYOUTRECALL carry a clora_changed flag:

"when it is FALSE the client may flush modified data to the data servers before returning the layout; only when it is TRUE should it stop writing to the DS and redirect through the MDS."

The Linux client decodes cbl_layoutchanged but has ignored it since commit b739a5bd9d9f, cancelling in-flight data-server I/O on every recall — "which can leave a write incomplete at the DS with no write layout held." On an unchanged recall this abandons writes whose data may already have reached the storage device; such a write can then land after the LAYOUTRETURN, which the metadata server sees as a write with no layout.

The three patches, all posted June 25:

  1. Patch 1/3 (report clora_changed in the cb_layoutrecall_file tracepoint) — observability. It gives nfs4_cb_layoutrecall_file its own tracepoint event definition so that "the intent of a recall can be observed in a trace," rather than the flag being "otherwise invisible."

  2. Patch 2/3 (honor clora_changed when recalling a layout) — the core fix. It threads the recall's clora_changed value through pnfs_mark_matching_lsegs_return() and only cancels in-flight I/O when the layout is actually changing (restriping or a failed storage device). For an unchanged recall, "the existing deferred return path waits for the in-flight writes to drain before sending the LAYOUTRETURN." Coddington notes the change is precisely scoped: "Other callers, which are tearing down or returning the layout for their own reasons, continue to cancel as before."

  3. Patch 3/3 (report cancelled I/O as a layout error) — closes the reporting loop for the cases where cancellation is warranted (changed recall or revoke). Cancellations previously completed with -EAGAIN, which ff_layout_io_track_ds_error() did not recognize — it "fell through the switch and recorded nothing, so no error was reported to the server." Because -EAGAIN is overloaded in the RPC layer, Coddington cancels with -ECANCELED instead and maps that to NFS4ERR_NXIO, the status already used for transport errors that leave a write incomplete. The error is then reported via LAYOUTERROR / LAYOUTRETURN so the MDS can reconcile the affected mirror instance.

A key subtlety in Patch 3: because the client itself aborted the I/O rather than discovering a device failure, it deliberately does not blame the data server:

"Unlike a genuine transport error, though, we aborted the I/O ourselves and have no evidence the device is at fault, so once the error is recorded we skip marking the device unreachable and forcing a further layout return."

He confirms the retry behavior is preserved: both NFS4ERR_NXIO and -ECANCELED are no-ops in ff_layout_async_handle_error(), which "still resets the I/O to pNFS (or the MDS), so it is re-driven as before."
