NFSv4.2 client support for UNCACHEABLE_FILE_DATA (PATCH 0/4)

Summary

NFSv4.2 client support for UNCACHEABLE_FILE_DATA (PATCH 0/4)

Type: New feature — Linux NFSv4.2 client support for the per-file UNCACHEABLE_FILE_DATA attribute defined by the in-flight IETF draft draft-ietf-nfsv4-uncacheable-files.

Overview

Mike Snitzer posted a four-patch series on Wednesday, June 24, adding Linux NFSv4.2 client support for FATTR4_UNCACHEABLE_FILE_DATA (attribute number 87), an OPTIONAL per-file read-write boolean that a server can set on a regular file to advise the client to suppress all client-side caching of that file's data — both write-behind and read caching.

The cover letter frames the motivation in HPC terms:

"The attribute is an OPTIONAL, per-file, read-write boolean (FATTR4 number 87) that a server may set on a regular file to advise the client to suppress client-side caching of that file's data -- both write-behind and read caching. It is conceptually similar to O_DIRECT but operates at the protocol level and requires no application changes."

"The motivating use case is HPC-style concurrent writers modifying disjoint byte ranges of a shared file, where cached/delayed writes cause read-modify-write hazards ('write holes')."

A key design point: the client only honors a server-set attribute; it never sets it itself. When a regular file is marked uncacheable, the client transparently opens it O_DIRECT, which "suppresses read and write-behind caching and satisfies the spec's durability invariant via the existing direct-I/O path."

The four patches

  1. PATCH 1/4 — introduces Documentation/sunrpc/xdr/nfs4_2.x to generate the attribute definition via xdrgen, mirroring how sibling NFSv4.2 attributes (FATTR4_OFFLINE=83, FATTR4_TIME_DELEG_*=84/85, FATTR4_OPEN_ARGUMENTS=86) are defined in nfs4_1.x. Wires the fs/nfsd "make xdrgen" target and includes the generated <linux/sunrpc/xdrgen/nfs4_2.h> from <linux/nfs4.h>. Marked "No functional change."

  2. PATCH 2/4 — the core attribute support, based on original code from Tom Haynes (Hammerspace). Decodes the attribute via GETATTR, tracks per-exported-filesystem support, and records it on the inode in NFS_I(inode)->uncacheable_file_data.

  3. PATCH 3/4 — gates the request so the attribute is only requested for regular files (NF4REG). This matters because per the draft a server MUST reject a query on any other object type with NFS4ERR_INVAL, and a strict server would fail directory GETATTRs, LOOKUPs resolving to directories, or CREATEs. The fix gates at the single choke point nfs4_bitmap_copy_adjust().

  4. PATCH 4/4 — opens uncacheable regular files with O_DIRECT via a new NFS_CONTEXT_O_DIRECT open-context flag. The patch notes the I/O mode is selected at open time and not changed for an already-open file; it also deliberately does not take the optional Section 4.3 delegation relaxation (read caching may remain under a delegation), choosing instead to suppress reads more aggressively than the spec minimum.

Review discussion

The review activity this week concentrated on patches 1 and 2, with Anna Schumaker and Chuck Lever raising concerns about the build/infrastructure approach in patch 1.

Anna's first concern (patch 1): she questioned whether client-side changes should be using the server-side xdrgen infrastructure at all:

"Aren't these client side changes? The xdrgen stuff is used on the server-side. I wouldn't expect any of these values to be available if nfsd is kconfig-ed off." (review reply)

Mike's response clarified that the client does need the NFS spec definitions, and that the kernel build is not dependent on xdrgen running at build time — the generated header is committed:

"The NFS4.x client code needs and has access to NFS spec definitions also, via <linux/nfs4.h>. Its only that the server side's xdrgen framework is needed to generate updates to the headers."

"So to be clear: the Linux kernel build (and NFS client build) isn't dependent on xdrgen running at build time."

He also floated a tangential idea of moving the xdrgen tooling to fs/nfs_common/ since it's now serving both sides. (response)

Chuck Lever then weighed in, confirming Mike's point about the Makefile but pushing back on adopting the generated approach for the client at this stage:

"Correct: The Makefile changes are for a target that is used only when the .x file changes, not for rebuilding the kernel."

"However, as far as I am aware the client does not use the xdrgen headers for anything, currently. Changing the server-side should be done in a separate patch and only if the server-side code also needs the new protocol definitions. Otherwise I think we continue with the duplicated infrastructure -- or only hand-rolled, if there are no server-side needs yet."

On Mike's fs/nfs_common/ suggestion, Chuck was candid about how immature the tooling is:

"We're not that far along with xdrgen. I haven't heard any interest in the client-side maintainers adopting the tool-generated approach." (Chuck's reply)

This is the substantive open item: whether patch 1 should hand-roll the FATTR4_UNCACHEABLE_FILE_DATA constant (and size macro) in the client rather than pulling it through the server-side xdrgen pipeline, since no server-side consumer exists yet.

Anna's nits on patch 2: she flagged an unrelated whitespace change that "accidentally snuck in," suggested the new nfs4_fattr_maxsz value could simply be a literal '1' like neighboring entries, and asked whether the boolean attribute could be stored in a bool. (review reply)

Mike's responses to patch 2: he agreed to clean up the whitespace "if v2 needed," defended using the xdrgen-generated size variable over a magic +1 ("over time the reason for each unnamed +1 gets lost"), and was open to switching the struct member to a bool/bitfield:

"Sure, we can use a bitfield with bool as well. I don't have a preference, but seeing 'bool' would express the boolean flag nature of this struct member (and any other flags that might follow)." (response)

Status / conclusion

The thread is still in early review with no final decision or merge within this week's window. The patches 3 and 4 gating/O_DIRECT logic drew no objections, but patch 1 has a genuine architectural question (xdrgen vs. hand-rolled for the client) that Chuck effectively steered toward keeping the client self-contained unless/until the server side also needs the definitions. A v2 addressing Anna's whitespace/bool nits and possibly reworking patch 1 is the likely next step; no further replies were posted after Chuck's June 25 message.

Significance

This is a new protocol feature (not a bug fix) that extends the NFSv4.2 client to honor a draft IETF attribute, with direct relevance to HPC workloads where concurrent writers on disjoint byte ranges of a shared file currently suffer read-modify-write "write holes" from delayed/cached writes. The implementation's elegance — reusing the existing O_DIRECT path rather than inventing new caching machinery — is worth noting, as is the careful spec-compliance reasoning in patch 3 (avoiding NFS4ERR_INVAL on non-regular objects) and patch 4 (deliberately not taking the optional delegation read-cache relaxation). The open discussion about whether to adopt server-side xdrgen tooling for a client-only attribute is itself a small but telling marker of where the NFS codebase's build infrastructure currently stands.
