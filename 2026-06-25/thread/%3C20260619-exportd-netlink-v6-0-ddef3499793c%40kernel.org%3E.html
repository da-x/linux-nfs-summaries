nfsd netlink stats v6: fixes UAF and CB_SEQUENCE gaps, Lever flags single-message dump buffer risk

Summary

nfsd/sunrpc netlink stats (v6): Layton ships fixes for the UAF and CB_SEQUENCE review items; Lever digs into the dump design

Context (brief bridge)

This is version 6 of Jeff Layton's series converting the NFS server-side nfsstat interface from procfs scraping to a generic netlink dump handler, with per-netns accounting for both forward-channel procedure counts and — new since v5 — NFSv4 backchannel (callback) operations. The full posting history is summarized in last week's v5 thread and the v5 review follow-up. In that prior week, Chuck Lever had raised two concrete blockers on the callback patches: a use-after-free in patch 5 and a CB_SEQUENCE undercount in patch 6. v6 is Layton's response to both.

This Week (June 19): The v6 Posting and Lever's Detailed Review

All nine in-window messages landed on June 19. Seven are Layton's v6 submission; two are Lever's review replies, arriving a few hours later.

The v6 cover letter: what changed

Layton frames the revision tersely: the cover letter states, "This version fixes a few problems that Chuck and Sashiko pointed out in review." The three bullets of the v6 delta:

  • Emit the entire server-stats object in a single netlink dump message
  • Count CB_SEQUENCE on v4.1+ callbacks, for parity with the forechannel SEQUENCE count
  • Fix a use-after-free in nfsd4_run_cb() by snapshotting the opcode, net, and minorversion

So both of Lever's prior-week blockers are addressed: the UAF is fixed by snapshotting the callback opcode, netns pointer, and minorversion before queuing (so the work item no longer dereferences cb/clp after they may be freed), and the CB_SEQUENCE gap is closed by explicitly counting it on v4.1+ callbacks to match the forechannel SEQUENCE convention. The series remains six patches; the patch list is unchanged from v5, but the contents of patches 3, 5, and 6 were revised.

Patch-by-patch (v6)

  1. Patch 1/6 — per-netns per-procedure counts in svc_stat: Adds a vs_count pointer array to struct svc_stat plus svc_stat_alloc_counts()/svc_stat_free_counts() helpers managing per-version percpu count arrays, allocated in nfsd_net_init() and freed in nfsd_net_exit(). The per-net counter is incremented alongside the global one in svc_generic_init_request().

  2. Patch 2/6 — svc_seq_show() uses per-net counts: A one-line change making /proc/net/rpc/nfsd report per-network-namespace procedure call counts. Layton's safety argument: "The only caller is nfsd, which always allocates vs_count via svc_stat_alloc_counts() in nfsd_net_init(), so the per-netns arrays are always available."

  3. Patch 3/6 — server-stats-get netlink handler: Implements nfsd_nl_server_stats_get_dumpit() in the nfsd generic netlink family. This is where v6 diverges most from v5: the commit message still describes a streaming design ("Subsequent messages: NFSv4 per-operation counts (proc4ops-ops), one entry per message, using cb->args[0] to track the current operation index across dump calls"), but — as Lever immediately points out — the code actually emits everything in a single message. Includes 105 lines of netlink YAML spec and new UAPI definitions.

  4. Patch 4/6 — remove unused svc_version vs_count: With both consumers migrated to per-netns arrays, the global vs_count percpu counters are dead. This patch deletes the field and all its DEFINE_PER_CPU_ALIGNED initializers across nfsd, lockd, and the NFS client callback service (fs/nfs/callback_xdr.c) — 39 lines of pure cleanup.

  5. Patch 5/6 — count NFSv4 callback operations per netns: Adds a per-netns array of percpu counters for backchannel operations, indexed by RFC 8881 callback opcode (OP_CB_GETATTR..OP_CB_OFFLOAD), bumped in nfsd4_run_cb(). This is where the UAF fix lives: the opcode, net, and minorversion are now snapshotted before nfsd4_queue_cb() returns, so the post-queue counter increment no longer dereferences a potentially-freed cb. The patch also contains the behavioral rework of the old wdeleg_getattr counter:

    "CB_GETATTR is sent when a GETATTR conflicts with an outstanding write delegation, which is roughly what the dedicated wdeleg_getattr counter tracked. The two are not identical: the old counter incremented on every such conflict, whereas the CB_GETATTR counter only counts callbacks that are actually queued, so concurrent conflicts that coalesce onto an already in-flight CB_GETATTR are now counted once rather than once per conflict."

  6. Patch 6/6 — export callback op stats via netlink: Adds a proc4cb-ops nested attribute to the server-stats dump, reusing the existing server-proc-entry (op/count) layout. Since the callback opcode set is small, it fits in the first dump message with no extra paging: "This lets nfsstat report NFSv4 backchannel operation counts over netlink, including CB_GETATTR which corresponds to the procfs wdeleg_getattr line."

Chuck Lever's review of patch 3/6 — the big one

Lever's reply to patch 3 is the most substantive piece of this week's discussion. He opens with a mismatch between the commit message and the code:

"The commit message says: ... Subsequent messages: NFSv4 per-operation counts (proc4ops-ops), one entry per message, using cb->args[0] to track the current operation index across dump calls. The code does not stream across subsequent messages. The proc4ops-ops nests are emitted in the first message, inside the same 'if (start == 0)' block as the scalars, and cb->args[0] only ever holds 0 or -1, never an operation index."

He then asks the pointed question: "Should the commit message be reworded to match the code, or should the code move to the streaming design the message describes?" — and immediately follows with a buffer-size argument for why the single-message form is fragile:

"Does that hold up once the assembled message no longer fits the dump buffer? A dump skb is allocated at max(cb->min_dump_alloc, NLMSG_GOODSIZE), and this handler sets neither cb->min_dump_alloc nor a .start callback, so the floor is NLMSG_GOODSIZE, which is SKB_WITH_OVERHEAD(PAGE_SIZE), roughly 3.7k on a 4k-page host."

He quantifies the worst case: "With LAST_NFS4_OP at 75, the proc4ops-ops loop alone emits 76 nests of about 28 bytes each (~2.1k); the proc2 and proc3 nests plus the scalar block bring the total to roughly 3.5k -- already within a few hundred bytes of the floor, and growing by one nest for every NFSv4 operation added later."

Lever then traces the failure mode precisely: "when an nla_put eventually fails, control reaches err_cancel, and genlmsg_cancel() trims the partial message back out, so skb->len is 0 on return. In netlink_dump(): if (nlk->dump_done_errno == -EMSGSIZE && skb->len) nlk->dump_done_errno = skb->len; the skb->len test fails, so -EMSGSIZE is delivered to userspace as a terminal error rather than being taken as 'buffer full, call again'. With everything emitted under 'if (start == 0)' and no per-attribute cursor in cb->args, a retry rebuilds the same oversized message, so the dump cannot ever complete."

His recommendation: "nfsd_nl_rpc_status_get_dumpit() already follows the streaming pattern the commit message describes: one entry per message, saving the cursor in cb->args and returning skb->len on EMSGSIZE. Would building this dump the same way be more robust than the single-message form?"

He also raises two smaller items: (a) the proc4ops loop open-codes the same nest-building logic that nfsd_nl_fill_proc_ops() already implements — "Could the helper be generalized to take the per-op counter source so this is not a second copy of the same code?"; and (b) the loop emits zero-count ops while the per-version block above skips empty versions — "Is that difference intentional? Skipping zero counts here would also trim the worst-case message size above." He also notes the dump omits wdeleg_getattr from the netlink path even though procfs prints it: "Since the goal is to expose the statistics currently available via /proc/net/rpc/nfsd, should wdeleg_getattr get an attribute here too, so nfsstat over netlink does not drop it relative to the procfs path?"

Chuck Lever's review of patch 5/6 — CB_SEQUENCE inflation

Lever's reply to patch 5 is shorter but flags a subtle counting bug. He first notes a comment inaccuracy: "The comment says the opcode is snapshotted before queuing, but the code captures the cb_ops pointer and reads ops->opcode after nfsd4_queue_cb() returns." He concedes the read is safe ("every cb_ops points at a file-scope static const nfsd4_callback_ops ... which outlives cb") but suggests the comment be corrected.

The more important point: CB_SEQUENCE is incremented even when no callback goes on the wire. Lever traces the path:

"Can this inflate the OP_CB_SEQUENCE count for callbacks that never send a CB_SEQUENCE? The increment fires whenever minorversion > 0, including the ops == NULL case. The only callback with cb_ops == NULL is the null probe ... For a 4.1+ client, nfsd4_run_cb_work() drops that work item without sending any RPC."

He identifies the affected scenarios: "callback-channel probes, backchannel changes, and client teardown each bump OP_CB_SEQUENCE for a minorversion > 0 client even though no CB_SEQUENCE (and no callback at all) goes on the wire." His suggested fix is to move the increment inside the if (ops) block:

"A real callback on a 4.1+ client always prepends CB_SEQUENCE, and the null probe carries cb_ops == NULL, so: if (queued) { if (ops) { nfsd_stats_cb_op_inc(nn, ops->opcode); if (minorversion > 0) nfsd_stats_cb_op_inc(nn, OP_CB_SEQUENCE); } }"

Classification and Significance

  • Type: This is a new feature (server-side netlink stats interface with per-netns scoping and callback-op accounting) combined with bug fixes in the statistics path:
    • The UAF in nfsd4_run_cb() (fixed in v6 by snapshotting).
    • The CB_SEQUENCE undercount from v5 (addressed in v6, but Lever identifies a new overcount for null-probe cases).
    • The wdeleg_getattr overcounting behavior (concurrent conflicts coalescing onto in-flight callbacks were previously counted multiple times; now counted once per queued callback).
  • NFS client relevance: The work is server-side (nfsd/sunrpc), but the callback backchannel is the channel the NFS client receives delegation and state-change callbacks over. Accurate CB_* counters matter for anyone diagnosing delegation recall, CB_GETATTR storms, or forechannel/backchannel sequencing on a client. Patch 4 also touches the client's callback service code (fs/nfs/callback_xdr.c) during cleanup of the global counter removal.
  • Net effect: v6 resolves both prior-week blockers (UAF fixed, CB_SEQUENCE now counted), but Lever's review introduces two new concerns: (1) the single-message dump design is fragile against buffer-size growth as NFSv4 ops are added — he recommends the streaming pattern already used by nfsd_nl_rpc_status_get_dumpit(); and (2) the CB_SEQUENCE increment still fires for null-probe work items that never send a callback, inflating the count. A v7 will likely need to address both.
