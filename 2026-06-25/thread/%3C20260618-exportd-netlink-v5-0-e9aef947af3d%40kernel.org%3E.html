Chuck Lever reviews v5 callback-stats patches: flags UAF in patch 5, CB_SEQUENCE gap in patch 6

Summary

nfsd netlink stats (v5): Chuck Lever's review of the new NFSv4 callback-op counters

Context (brief bridge)

This thread is the v5 posting of Jeff Layton's series converting the NFS server-side nfsstat interface from procfs scraping to a generic netlink dump handler, with two new patches adding per-netns accounting for NFSv4 backchannel (callback) operations — the design agreed in last week's review. The full v5 submission (all seven messages) is covered in last week's summary. This week brings the first substantive reviewer feedback on those two callback patches.

This Week: Chuck Lever's Two Review Replies

Both in-window messages are from Chuck Lever, landing at the very start of June 19, and both target the new callback-statistics work rather than the netlink plumbing itself.

Patch 5/6 — a UAF concern blocks application

In his reply to patch 5 (the per-netns callback-op counter), Lever endorses the direction but flags a memory-safety defect:

"I agree with the Sashiko review that this patch introduces a UAF possibility that needs to be addressed before the patch is applied."

So the patch — which adds a per-netns array of percpu counters for backchannel operations, indexed by RFC 8881 callback opcode and bumped in nfsd4_run_cb() — is not yet acceptable as-is. Lever is aligning with an automated (Sashiko) review that identified a use-after-free risk, most plausibly tied to the lifetime of the per-netns counter array relative to netns teardown. This is the gating issue for the series: the callback accounting cannot land until the UAF is resolved.

Patch 6/6 — CB_SEQUENCE is emitted but never counted

Lever's second reply dissects a subtle correctness gap in how patch 6 exports the counters. The netlink dump loop "emits an entry for every opcode in OP_CB_GETATTR..OP_CB_OFFLOAD," but only opcodes with a real nfsd4_callback_ops instance are ever incremented (via nfsd4_run_cb() keyed on cb->cb_ops->opcode). Lever isolates the one case that breaks this assumption:

"The exception is op 11 / CB_SEQUENCE: it's written by encode_cb_sequence4args() on every minorversion>0 callback, so it goes out on the wire but is never counted. The dump always shows op 11 with count 0, which could be misread as 'none sent' rather than 'not tracked.'"

He closes with an actionable pointer:

"Check what the forechannel counter does for SEQUENCE operations."

This is a statistics-correctness / observability bug: the netlink dump would report CB_SEQUENCE (op 11) as zero even though it is sent on every minorversion>0 callback, misleading anyone reading the stats. The fix direction Lever suggests is to mirror whatever convention the forward-channel (proc4ops) counter already uses for SEQUENCE — i.e., keep the backchannel reporting consistent with the existing forechannel behavior rather than emitting a perpetually-zero line.

Classification and Significance

  • Type: This week's activity is purely review of a new feature (server-side netlink stats + callback-op accounting) plus identification of two defects — one a memory-safety bug (UAF, patch 5) and one a statistics-reporting bug (CB_SEQUENCE undercount, patch 6). No client protocol change.
  • NFS client relevance: The work is server-side (nfsd/sunrpc), but the callback backchannel is the channel the NFS client receives callbacks over, so accurate CB_* counters matter for anyone diagnosing delegation and callback behavior on a client. Note also that patch 4 of the series touched the client's callback service code (fs/nfs/callback_xdr.c) during cleanup — but that was last week's posting, not this week's discussion.
  • Net effect: The v5 series is still in review. Two concrete blockers are now on record for the callback patches: resolve the UAF before applying patch 5, and reconcile CB_SEQUENCE reporting with the forechannel convention before exporting patch 6.
