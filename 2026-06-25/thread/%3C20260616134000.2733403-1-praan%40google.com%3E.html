NFS Direct I/O modernization (v2): author responds on test coverage, CC list, and the folio/bvec extraction question

Summary

NFS Direct I/O Modernization (v2) — Author's follow-up on testing, mailing-list hygiene, and the folio-extraction debate

Type: New feature / architectural refactor of the NFS client direct-I/O path (not a protocol change), with two embedded bug fixes. This week's activity is the author's response to the round of review feedback from last week — no new patches have landed yet, but the discussion has sharpened around patch 6/7 ("Optimize direct I/O to use folios for requests").

Bridge from prior week

Last week (week ending 2026-06-18) Pranjal Shrivastava posted [PATCH v2 0/7] "nfs: Modernize Direct I/O path"](https://lore.kernel.org/linux-nfs/20260616134000.2733403-1-praan@google.com/), a seven-patch series that migrates NFS O_DIRECT from the legacy iov_iter_get_pages_alloc2() API to the modern iov_iter_extract_pages() API, makes requests folio-based rather than page-based, and lays groundwork for PCI Peer-to-Peer DMA (P2PDMA). The series also fixes two real bugs: a data-corruption bug in nfs_direct_extract_pages() (incorrect intra-page offset) and an early-unpin / bytes-accounting defect in the direct read/write loop.

The substantive review debate that opened last week centered on whether patch 6's assumption — "every page returned by iov_iter_extract_pages() is a valid folio, so page_folio() is safe" — holds across all memory types. Trond Myklebust, Christoph Hellwig, and Matthew Wilcox pushed back: the MM subsystem's invariant that "every page is part of a folio" has important exceptions (slab, vmalloc, iomem), and filesystems should not be reasoning about the underlying memory representation at all. The reviewers' consensus guidance was to mirror or reuse the block layer's extraction logic rather than hand-rolling folio grouping in NFS.

This week: three responses from the author (all 2026-06-19)

All three messages this week are from Pranjal Shrivastava, responding one-for-one to the review feedback that arrived on June 18. No new patches were posted; no merge decision was recorded.

1. Test coverage: full xfstests quick suite shows no regressions

Christoph Hellwig had questioned last week whether the 26-test xfstests subset in the cover letter was sufficient, asking whether Pranjal had run "the full set of xfstests, which should give you much better coverage?"

Pranjal responded by clarifying that the 26 tests were highlighted because they were specifically reported as failures for the NFS direct I/O path, and then going further than asked:

"I've also run the full xfstests quick group on both the unpatched and patched kernels (7.1-rc7) across RDMA and TCP transports. I did not see any regressions between the two runs, the results were identical across the quick suite."

He offered to include the full run output in the v3 cover letter: "I could report the entire run for a patched and unpatched kernel in the v3 cover letter if you'd like?" This directly addresses Hellwig's coverage concern with a before/after comparison on the current -rc kernel, which is a stronger test signal than the subset alone.

2. CC list: adding linux-rdma and linux-pci for v3

Chuck Lever had suggested last week that, since the series is groundwork for P2PDMA, the author should CC linux-rdma@vger.kernel.org and linux-pci@vger.kernel.org. Pranjal acknowledged:

"Ack. Apologies for missing these out, I just ran get_maintainers on the current (part 1) patches and CC'd. I'll include the lists and relevant people in the next version."

This is a straightforward process fix; no technical disagreement.

3. The folio/bvec extraction question: author accepts the critique but surfaces a wrinkle

The most technically interesting exchange this week is Pranjal's reply to Matthew Wilcox's and Christoph Hellwig's pushback on patch 6. He concedes the core point:

"Thanks for the clarification. I understand the larger vision of keeping filesystems agnostic to the underlying memory represented by the iov_iter."

He acknowledges that the page_folio() documentation's claim that "Every page is part of a folio" has "important nuances regarding slab and other memory types that I was not aware of."

However, he then raises a pointed counter-observation: the block layer's own bvec extraction path (iov_iter_extract_bvecs()) also calls page_folio() via get_contig_folio_len() on pages obtained from iov_iter_extract_pages(), without additional slab/vmalloc checks. He asks:

"I am happy to refactor the NFS Direct I/O path to reuse the same helper (get_contig_folio_len()) from the bvec extractor, but I'm a little confused as the bvec extractor seems to suffer from the same risk?"

He then poses two forward-looking design questions to the MM/block maintainers:

"Is the recommendation to keep these details abstracted by the iov_iter lib and eventually hide things like iov_iter_extract_pages() and manual folio conversions from filesystems entirely?"

"If that's the case, would it help to export get_contig_folio_len() (or introduce new helpers) in the iov_iter lib for NFS and other fs to use?"

This is a meaningful escalation of the discussion: rather than simply accepting "reuse the block code" as an instruction, Pranjal is asking whether the correct long-term fix is an API change in lib/iov_iter.c that shields all filesystems from having to reason about folio semantics at all. If the bvec extractor has the same latent risk he identified, then the problem is not NFS-specific but a gap in the iov_iter abstraction layer.

Where things stand (end of week)

The thread remains open and unresolved. The uncontroversial parts of the series — pin-aware nfs_page infrastructure, the API migration to iov_iter_extract_pages(), the data-corruption fix, and the early-unpin/bytes-accounting fix — have not been challenged. The open question is patch 6's folio-grouping logic:

  • Author's position: willing to refactor NFS to reuse get_contig_folio_len() from the bvec extractor, but questioning whether that helper itself is safe across all memory types, and proposing that the iov_iter library should export (or create) a safe helper for filesystems.
  • Reviewers' position (last week): "stick to what the block code does or even better reuse as much as possible of that code" (Hellwig); "Fundamentally, it is no business of the filesystem what the iov_iter refers to" (Wilcox).

The ball is now in the court of Hellwig and Wilcox to address whether get_contig_folio_len() / the bvec path has the same slab/vmalloc exposure that Wilcox flagged, and whether an iov_iter API change is warranted. A v3 posting with updated CC lists, full xfstests results, and a refactored patch 6 (or a new helper in lib/iov_iter.c) is expected but has not yet appeared as of the end of this window.
