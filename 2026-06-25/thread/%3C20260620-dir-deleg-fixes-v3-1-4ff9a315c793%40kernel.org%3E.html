Layton's v3 dir-attr CB_NOTIFY recall fix folded into the series by Lever

Summary

nfsd: v3 of the dir-attr CB_NOTIFY recall fix accepted and folded

Overview

This week closes out a short but consequential bug-fix saga. Jeff Layton posted v3 of the patch that recalls a directory delegation when the NFS server cannot encode a requested NOTIFY4_CHANGE_DIR_ATTRS event into the CB_NOTIFY callback, and Chuck Lever replied the next day with a terse acceptance:

"Folded into 'nfsd: add support to CB_NOTIFY for dir attribute changes', thanks!"

This is squarely a bug fix — a protocol-correctness defect in the server-side CB_NOTIFY path introduced by the recently-reviewed RFC 8881bis directory-delegation series, with direct implications for any client that relies on cached directory attributes. The thread is now closed: the patch has been folded into the upstream commit rather than applied as a standalone fix.

Bridge from Prior Week

As summarized last week, Layton had posted v2 on June 19, and Lever's AI-assisted review (Sashiko + gpt-5.5 cross-check) concluded it "is not yet a complete fix" because the upstream commit that introduced the feature also masked vfs_getattr() failures as a 0-length attribute set — a second path that could still silently drop the requested notification in violation of RFC 8881 s10.9.4. This week's v3 is precisely the response to that caveat.

The v3 Patch (June 20)

Layton's v3 cover restates the core defect:

"When the client requested NOTIFY4_CHANGE_DIR_ATTRS, nfsd4_cb_notify_prepare() tried to append the dir attribute change to the CB_NOTIFY, but silently dropped it if the attrmask space reservation failed or nfsd4_encode_dir_attr_change() failed to marshal the change into the buffer. It then returned true and transmitted a CB_NOTIFY lacking the requested notification, leaving the client's cached directory attributes stale with no indication."

The RFC anchor is explicit: "RFC 8881 s10.9.4 requires the server to recall the delegation when the directory changes in a way that is not covered by the notification." The fix treats an encode failure like the per-event encode failures already handled in the loop above — set an error and fall through to out_recall.

The v3 changelog is terse but targeted:

"Changes in v3:

  • Recall delegations on vfs_getattr() failure instead of sending empty attr set"

That single bullet is exactly the gap Lever flagged last week. The patch body now walks through how nfsd4_setup_notify_entry4() previously routed three distinct conditions through its noattrs label and returned true with a zero-length attribute set:

"Only the first is benign; the latter two are genuine failures that were indistinguishable from the 'no attributes requested' case, so a requested change could still be silently dropped (the per-event entries encoded by nfsd4_encode_notify_event() were affected the same way). Return false on a vfs_getattr() or nfsd4_encode_attr_vals() failure so the error propagates to the caller and the delegation is recalled, and reserve the noattrs path for the NULL or negative dentry case."

The patch also preserves the v2 distinction between a genuine encode failure (which forces the recall) and the benign case where a client was granted NOTIFY4_CHANGE_DIR_ATTRS while requesting no specific dir attributes — those masks come from independent fields of the GET_DIR_DELEGATION request. As before, Layton credits AI assistance in the sign-off block: "Assisted-by: Claude:claude-opus-4-8." The patch touches fs/nfsd/nfs4state.c and fs/nfsd/nfs4xdr.c (62 insertions, 41 deletions) and carries Fixes: 757a16cd93d5 ("nfsd: add support to CB_NOTIFY for dir attribute changes").

Lever's Acceptance (June 21)

Lever's reply is the shortest of the three rounds:

"Folded into 'nfsd: add support to CB_NOTIFY for dir attribute changes', thanks!"

No further review commentary, no additional AI-reviewer findings — just a clean fold. The patch will land as part of the original commit rather than as a separate fixup, which keeps the git history tidy and ensures the bug never ships in the first place.

Significance for NFS Client Development

Although the fix is server-side, its blast radius is entirely on the client:

  • Stale directory caches. Without the recall, a client that has accepted NOTIFY4_CHANGE_DIR_ATTRS and is caching directory attributes (size, mtime, fileid, etc.) would continue to serve those cached values after the underlying directory changes. The client has no in-band signal that its cache is invalid — it would only notice on an explicit GETATTR or a failed operation.
  • The v3 closure matters for clients. Last week's "not yet a complete fix" caveat meant that even with v2 applied, a vfs_getattr() failure (e.g., during a concurrent unexport or filesystem error) could still produce a CB_NOTIFY lacking the requested dir-attr event without a recall. With v3 folded in, that residual path is closed — any client-side implementation of RFC 8881bis directory delegations can now rely on the server to either deliver the notification or recall the delegation, per RFC 8881 s10.9.4.
  • AI-assisted review continues to shape the process. Both Layton (Claude) and Lever (Sashiko + gpt-5.5 in v2's review) explicitly credit AI tools. The fact that the AI reviewer caught a "High" severity issue in v2 that drove the v3 revision underscores the value of cross-checking, and this round shows the loop closing cleanly once the human author addresses the finding.

Status and Outlook

  • Thread status: Closed. The v3 patch has been folded into the upstream commit by Lever; no further revisions are expected.
  • Relationship to main series: This was always intended to be folded into the CB_NOTIFY dir-delegation series (targeting v7.3) rather than applied as a standalone commit, and that is exactly what happened.
  • Open items from prior weeks: The other open items from the broader review (refcount race in nfsd_break_one_deleg(), stale ncn_encode_err flag, order-aware client mask negotiation, two-word bitmap size budgeting) remain tracked in their own threads and are unaffected by this closure.
