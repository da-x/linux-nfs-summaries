lockd: fix GRANTED_MSG handling on the client side

Summary

lockd: fix GRANTED_MSG handling (NFSv3/v4 callback path)

Type: Bug fix — a regression in the NFS client-side NLM callback path, introduced by the xdrgen XDR refactoring of the GRANTED_MSG procedure.

The week's activity

The thread opened late on Thursday with a single patch from Olga Kornievskaia (Red Hat): [PATCH 1/1] lockd: fix GRANTED_MSG handling](https://lore.kernel.org/linux-nfs/20260625211852.31972-1-okorniev@redhat.com/). No further replies landed inside the reporting window, so this week's coverage is essentially the patch itself plus its clearly stated rationale. (Two follow-up acks from NeilBrown and Chuck Lever are visible on lore but fall outside the 2026-06-19 → 2026-06-26 window.)

Key technical argument

The patch targets a subtle asymmetry between two families of host-lookup helpers in fs/lockd:

"GRANTED_MSG is a server-to-client callback, so it runs on the client, where nfsd never registers nlmsvc_ops." — Olga Kornievskaia

The nlm4svc_lookup_host() / nlm3svc_lookup_host() helpers were designed for the server-side NLM request handlers (TEST/LOCK/CANCEL/UNLOCK). Those paths reach into nlmsvc_ops->fopen, and the lookup is intentionally strict so that requests are rejected when nfsd isn't running. The xdrgen XDR conversion of GRANTED_MSG (NLMv3 and NLMv4) had mistakenly wired the client-side callback through those same server-oriented helpers, so a pure NFS client — one that never runs nfsd and therefore never registers nlmsvc_ops — would fail every incoming GRANTED_MSG.

"The nlm4svc_lookup_host()/nlm3svc_lookup_host() helpers are for the server-side request handlers (TEST/LOCK/CANCEL/UNLOCK), which reach nlmsvc_ops->fopen and must reject requests when nfsd isn't running. GRANTED_MSG only calls nlmclnt_grant(). Instead, of calling nlm4svc_lookup_host()/nlm3svc_lookup_host() (which results in a client failing a GRANTED_MSG call) call nlmsvc_lookup_host." — Olga Kornievskaia

The fix is a one-line-per-file swap in fs/lockd/svcproc.c (NLMv3) and fs/lockd/svc4proc.c (NLMv4): use the generic nlmsvc_lookup_host() instead of the versioned *svc_lookup_host() helpers, since GRANTED_MSG only needs to call nlmclnt_grant() and never touches nlmsvc_ops->fopen.

Regression provenance

The patch carries two Fixes: tags pointing at the xdrgen XDR conversions that introduced the bug:

  • 62721885e861 — "lockd: Use xdrgen XDR functions for the NLMv4 GRANTED_MSG procedure"
  • 6c534ad999b6 — "lockd: Use xdrgen XDR functions for the NLMv3 GRANTED_MSG procedure"

So this is a follow-up to the broader lockd XDR modernization effort, not a new feature or protocol change. The diff is minimal (2 files, +4/-2) and confined to fs/lockd/svcproc.c and fs/lockd/svc4proc.c.

Why it matters for NFS clients

GRANTED_MSG is the NLM callback the server uses to tell a client that an earlier blocked lock request has been granted. A pure NFS client — exactly the configuration where nfsd is not running — would previously have failed every such callback, breaking asynchronous lock-grant notifications on both NFSv3 and NFSv4 mounts. The fix restores correct client-side behavior without weakening the server-side safety check that nlmsvc_ops->fopen callers still rely on.
