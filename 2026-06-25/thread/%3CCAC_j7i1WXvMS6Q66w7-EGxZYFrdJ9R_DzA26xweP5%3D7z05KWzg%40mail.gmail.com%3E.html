nfsd: Capping GSS Fore-Channel Slots to the Replay Window — A Stopgap for krb5p Retransmit Storms

Summary

nfsd: Bounding GSS Fore-Channel Slots to the Replay Window

Classification

Bug fix / regression mitigation (server-side). The thread is about a production krb5p streaming-write stall caused by the interaction between NFSv4.1 fore-channel slot growth and the fixed 128-entry RPCSEC_GSS replay window. It is framed as a defensive server-side bound, with the author explicitly flagging that the real fix belongs on the client side.

Overview

This week opened with Vjaceslavs Klimovs posting a patch that caps a GSS-authenticated session's fore-channel slot count at one quarter of the GSS replay window, followed by Chuck Lever delivering a detailed technical rebuttal arguing the cap is "an operational hack, not a long-term solution." The exchange is short (two messages, both 2026-06-19) but dense — it lands squarely on NFS client/server slot management and GSS sequence-number handling.

Background / Bridge

The regression traces to the session-slot rework that landed in the v6.13/v6.14 window — the same cluster of commits (xarray-based slots, on-demand allocation, freeing, and a shrinker) identified as suspects in an earlier v6.18 refcount_t underflow investigation. The specific culprit here is commit 60aa6564317d ("nfsd: allocate new session-based DRC slots on demand.", v6.14), which lets the server grow the slot table far beyond the client's default 64 fore-channel slots — and past the 128-entry GSS window once nconnect reordering and retransmits are counted.

The Reported Bug

Klimovs describes a production krb5p NFSv4.2 mount that "began stalling to ~0 after a 6.12 -> 6.18 upgrade":

"A production krb5p NFSv4.2 mount (vers=4.2, rsize=wsize=1M, proto=tcp, nconnect=8, sec=krb5p, enctype aes256-cts-hmac-sha384-192) that used to sustain ~1 GB/s on a 10 GbE link began stalling to ~0 after a 6.12 -> 6.18 upgrade." Vjaceslavs Klimovs

The mechanics: a single GSS context's sequence numbers are round-robined across several TCP connections that drain at different rates, and every retransmit consumes a fresh seqno. Once the spread between the oldest in-flight and newest issued seqno exceeds the 128-entry window, the server drops the lagging request, the hard mount retransmits, and "a krb5p streaming write collapses into a retransmit storm (a stall to ~0 in the field; an EIO under the krb5-nfs-perf reproducer)." He bisected it cleanly to 60aa6564317d and validated with a two-VM QEMU harness: "unpatched 6.18.x : retransmit storm (hundreds of retransmits) -> EIO; patched : clean, retrans 0."

The Proposed Fix

The patch bounds a GSS session's fore-channel slots to a quarter of the window (32), at both the initial CREATE_SESSION grant and on-demand growth. sec=sys is unaffected (no per-context sequence window) and keeps the full table. Klimovs defended 32 with throughput measurements at 16 vCPU:

"40 starts to graze the window again; 32 was the largest value that stayed clean (retrans 0) across the sweep, so it keeps a 4x window margin without throttling streaming writes on many-core servers." Vjaceslavs Klimovs

Crucially, the author himself framed this as a server-side stopgap and pointed at two client-side problems "not addressed by this patch":

  • "the default of 64 GSS fore-channel slots already over-commits a single 128-entry context window once spread across nconnect links"; and
  • the v6.16 RFC2203 seqno cache (commit 08d6ee6d8a10, by Nikhil Jha) — "the intended mitigation for this storm -- in our testing converts a recoverable window graze into a hard EIO at the 64-slot floor rather than recovering."

Chuck Lever's Rebuttal

Lever opened with process notes (the diff was mangled and unappliable; the patch targets linux-6.18.y, not upstream or nfsd-testing, so he read it as a request for review) before getting to the substance. His core verdict:

"to be blunt, the proposed approach is an operational hack, not a long-term solution that closes the re-ordering window." Chuck Lever

He then made the key structural argument — the GSS window bounds relative lag, while the session slot count controls concurrency, and those are different quantities:

"the GSS window bounds relative lag, not concurrency, but the NFSv4.1 session slot count controls concurrency. Those are different quantities, which is why no ratio can close that gap and prevent reordering." Chuck Lever

His reasoning: the server window is a sliding bound tracking sd_max (the highest accepted seqno), rejecting anything below sd_max - GSS_SEQ_WIN. If one request stalls while the other M-1 slots keep cycling, the leading edge advances and the stalled request's lag "grows without bound for as long as it stays stalled... until it crosses 128 and is dropped. This happens for any M ≥ 2. The only genuinely safe value is M = 1 (strict serialization, lag is always 0), which is useless." He characterized the cap precisely:

"That's all the 32 does: it widens the grace window and lowers the typical spread enough that drops become rare under the reproducer's reorder pattern. It is a probability knob, not an invariant." Chuck Lever

He also noted the cap "should be relative to the GSS window size, not a fixed constant," that the server can't know how many transport connections the client will open at CREATE_SESSION time, and that other NFS versions (and krb5i) are affected but lack a session slot table entirely.

Lever's Structural Fix Directions

Speaking "generally here, not proposing a specific fix," Lever laid out three options that bound lag directly:

  1. Client-side spread throttling — the client knows the oldest unacked and newest issued seqno and can refuse to issue one more than (GSS_SEQ_WIN - margin) ahead of the oldest outstanding. "This is the structurally correct fix, and it's on the side that has the information."
  2. Per-connection (or per-slot) GSS contexts — give each transport its own seqno space, removing cross-connection reorder at the cost of more context state and a spec/implementation change.
  3. Negotiated window size — scale GSS_SEQ_WIN with the advertised slot count rather than a fixed 128, trading memory for headroom.

He closed by conceding the server-side cap has some merit: "The server slot cap is defensible as a stopgap the server might deploy unilaterally without trusting clients... but it's treating the symptom (spread) one step removed from the cause (unbounded lag, controllable only where seqnos are issued)."

Conclusions & Status

  • Open — under discussion. The patch is not headed for upstream as-is; Lever read it as a review request against linux-6.18.y. No merge decision was made this week.
  • Consensus on the diagnosis: both parties agree the root cause is unbounded seqno lag relative to the fixed 128-entry GSS window, amplified by nconnect > 1 and on-demand slot growth from 60aa6564317d.
  • Disagreement on the remedy: Klimovs offers a pragmatic server-side probability knob (cap at 32); Lever argues only client-side lag bounding (or per-connection contexts / negotiated window) is structurally correct, and that no slot ratio can make reordering impossible.
  • Client-side follow-ups flagged for separate work: the 64-slot GSS default over-committing a single context window across nconnect links, and the v6.16 RFC2203 seqno cache turning a recoverable graze into a hard EIO (Nikhil Jha cc'd).
