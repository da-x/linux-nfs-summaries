sunrpc: hardcode pool_mode to pernode — v2 posted, empty-pool edge case under debate

Summary

sunrpc: hardcode pool_mode to pernode, remove other modes (v2)

Type: Cleanup / behavior change in the NFS server (sunrpc) layer — not a client feature or protocol change. The patch removes the long-standing SVC_POOL_AUTO/GLOBAL/PERCPU/PERNODE selection machinery and makes "pernode" the only pool mode, while preserving the module parameter and netlink interfaces for backward compatibility.

This week's activity (Jun 19–26 window)

The thread got its v2 posting on Thursday, June 25, followed by a detailed review from Chuck Lever the same day. NeilBrown's follow-up landed early Friday morning (June 26), just outside the reporting window, but is worth noting since it frames the next revision.

Jeff Layton posted v2, explaining that the pool mode selection machinery "was added when NUMA was new and the right default was unclear. Today, pernode is the right choice everywhere." The patch removes 201 lines from net/sunrpc/svc.c (37 insertions vs. 201 deletions), eliminating the SVC_POOL_* enum, the mode selection heuristic, svc_pool_map_init_percpu(), and all mode-based switch statements.

The key v2 change over the April RFC (v1) is backward compatibility: rather than rejecting legacy values with -EINVAL, the kernel now accepts any previously-accepted setting silently. As Layton put it, this "should alleviate concerns about breakage." The module parameter and netlink interfaces are preserved — writing any old value succeeds, reading always returns "pernode", and a deprecation notice is emitted on write.

Another notable behavioral change: if pool map allocation fails, svc_pool_map_get() now returns 0 and service creation fails outright, rather than silently falling back to a single global pool.

Chuck Lever's review: the empty-pool problem

Chuck Lever responded with two substantive concerns:

1. Empty pools when nrservs < number of NUMA nodes. This is the most technically significant issue raised. Chuck traced through svc_set_num_threads() and showed that when the total thread count is smaller than the number of NUMA nodes, base = nrservs / serv->sv_nrpools becomes 0, leaving trailing pools with zero threads. He then followed the enqueue path:

"Work is still routed to the per-node pool selected from the running CPU… and svc_pool_wake_idle_thread() only consults that one pool's idle list, with no fallback to a sibling pool. If a connection lands on a node whose pool has no threads, does its transport sit on sp_xprts and never get serviced?"

He emphasized this couldn't happen under the old default: "The old global default kept a single pool, so this configuration could not arise without an explicit pernode/percpu selection." With global mode removed, there is no longer an escape hatch for admins.

2. Stale documentation. The Documentation/admin-guide/kernel-parameters.txt still presents all four modes as distinct and states the option "will affect which CPUs will do NFS serving." Chuck noted: "The patch should update this documentation."

He also flagged a smaller point: "The commit message should call out the change in the default setting."

NeilBrown's review (just after window)

NeilBrown weighed in on June 26 with code-level nits and a design opinion:

  • On the !strncmp pattern in the new setter: "!strncmp" is one most disliked construct.... What would you think of using match_string() or even sysfs_match_string() ??
  • On the deprecation message: "Which future release? How will we remember?"
  • On the refcount decrement: suggested m->count = 0 for clarity, and asked whether svc_pool_for_cpu() can run when m->count is zero.
  • On Chuck's empty-pool concern: "I think a minimum of one thread per node, rather than a minimum of one thread total, is the sensible approach. Of course if there exist memory-only nodes, they wouldn't need a thread."

Chuck pushed back on the memory-only node case: "What happens when transport work is scheduled on a memory-only pool? Obviously there's no execution engine there, even if we do provide one or more threads."

Jeff Layton's response: belt-and-braces solution

Jeff Layton replied with a two-part approach to the empty-pool problem:

"1/ when min-threads is set, assign at least one thread to each node that has a cpu as a minimum, but only when we are auto-distributing threads between nodes (the typical case). This allows us to preserve the wishes of userland when it sends down a more complex pool array."

"2/ add in a fallback in the queueing path so that when there are no threads in a node, we queue it to a populated one. We could even add a pr_notice_once() that fires in that case to warn that the configuration is sub-optimal."

He also noted an important constraint: userland can dictate per-pool thread counts via an array (e.g., 0 128 0 0 for four pools), so the kernel must honor explicit zero-thread assignments rather than overriding them.

In a separate reply to NeilBrown, Layton confirmed:

  • Switched to sysfs_match_string() (addressing Neil's nit)
  • Will make the deprecation message more vague: "I'm not sure what the guidance is on removal of knobs like this. A few years, I guess?"
  • Fixed the m->count = 0 issue
  • Confirmed that svc_pool_for_cpu() can indeed be called when m->count == 0, since it's "called unconditionally from svc_new_thread(), which runs for non-pooled services created via svc_create() (e.g. lockd) that never call svc_pool_map_get()."

Context: prior week / earlier history

This is the second iteration of a patch first posted as an RFC on April 23, 2026. In that original exchange, Chuck Lever raised the backward-compatibility concern that "existing modprobe.d configs written any time in the last ~19 years will cause load-time parameter errors," and suggested a staged approach: first change the default, then deprecate, then remove. Layton agreed to stage it but noted: "I'm terrible about following up with the later phases of long term deprecation though." Chuck also flagged that nr_online_nodes on some ARM64/CXL platforms counts memoryless or CPU-less nodes, making for_each_node_with_cpus() vs. for_each_online_node() a concern in svc_pool_map_init_pernode().

The v2 posting this week directly addresses the backward-compatibility concern from April by accepting all legacy values silently. The empty-pool issue and documentation updates remain open for v3.

Status

The discussion is active with no final conclusion yet. Layton has acknowledged the review points and outlined a path forward (minimum one thread per CPU-bearing node + enqueue fallback), but no v3 has been posted as of the end of this window. The thread is expected to continue into next week's reporting period.
