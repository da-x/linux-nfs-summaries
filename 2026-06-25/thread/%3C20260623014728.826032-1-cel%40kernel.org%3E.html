svcrdma: Patch plugs slab-corrupting overflow in RDMA pull-up path

Summary

svcrdma: Reject inline replies that overflow the pull-up buffer

Type: Bug fix (memory corruption / out-of-bounds write) in the NFS/RDMA server transport.

What happened this week

The thread is a single-message patch submission from Chuck Lever on 2026-06-23, with no replies yet in the window. It addresses a serious memory-safety bug in svcrdma, the kernel's RPC-over-RDMA server-side transport that underpins NFS over RDMA.

The bug

As Lever describes, a malicious or misbehaving RPC-over-RDMA client can request a reply — such as an NFS READ payload — without providing a Write list or Reply chunk to carry it:

"An RPC-over-RDMA client can request a reply, such as an NFS READ payload, without providing a Write list or a Reply chunk to carry it."

When the resulting reply needs more scatter/gather (SGE) entries than the device's Send Queue supports, the server falls back to "pull-up": svc_rdma_pull_up_reply_msg() linearizes the entire reply into sctxt->sc_xprt_buf. The problem is that this buffer is only sc_max_req_size bytes, but on this particular code path the reply size is bounded only by the client's request:

"That buffer is only sc_max_req_size bytes, while the reply on this path is bounded only by the client's request, so svc_rdma_xb_linearize() copies past the end of the buffer and corrupts adjacent slab memory."

The corruption does not stop at kernel heap. The oversized length is also posted to the hardware:

"The oversized length is then stored in sc_sges[0].length and posted, so the device also reads beyond the mapped region."

So a single bad client request could trigger both an out-of-bounds slab write on the server and an out-of-bounds DMA read by the RDMA NIC — a classic remote-exploitable memory-corruption primitive.

Why only one branch is vulnerable

Lever walks through the three pull-up entry points to show that the SGE-exhaustion branch is the only one that can exceed the buffer:

"The SGE-exhaustion branch is the only pull-up path that can exceed the buffer: the threshold branch pulls up only replies smaller than RPCRDMA_PULLUP_THRESH, and replies that fit the device's SGE budget are sent directly without linearization."

That analysis matters because it scopes the fix tightly — no need to rework the well-behaved fast paths.

The fix

The patch makes two changes in net/sunrpc/xprtrdma/svc_rdma_sendto.c (32 insertions, 15 deletions):

  1. Error reporting instead of a boolean. The helper no longer answers yes/no; it now reports one of three outcomes — pull up, don't pull up, or -E2BIG when the reply would not fit sc_max_req_size:

    "The helper no longer answers a simple yes/no question: it now reports pull-up, no pull-up, or -E2BIG for a reply too large to linearize."

  2. Protocol-correct failure. Rather than tearing down the connection (which would be disruptive and is not what the spec asks for), the server fails just that request with ERR_CHUNK, as RFC 8166 §4.5.3 prescribes:

    "fail the request with ERR_CHUNK as RFC 8166 Section 4.5.3 directs rather than dropping the connection."

  3. Rename for clarity. Because the function is no longer a predicate, it is renamed svc_rdma_pull_up_needed() → svc_rdma_check_pull_up():

    "Rename svc_rdma_pull_up_needed() to svc_rdma_check_pull_up() so its name no longer implies a boolean predicate."

Provenance and context

  • Reported-by: Chris Mason (Meta) — a real-world report rather than a static-analysis find.

Status

Bottom line

This is a textbook "remove the guard, forget the invariant" regression: dropping the connect-time max_sge check was fine on its own, but it left a pull-up path that assumed replies were bounded by the server's request size when in fact they were bounded only by the client. The fix restores the invariant at the right layer (per-request validation with -E2BIG) and uses the protocol's own error mechanism (ERR_CHUNK) instead of a connection reset — a clean, minimal, spec-compliant patch that should land quickly.
