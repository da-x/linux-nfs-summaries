RPC-with-TLS memory bug fixes finally get maintainer attention after seven-week wait

Background (from prior weeks)

Back in early May, Chuck Lever posted a two-patch series titled "[PATCH 0/2] Fix a few memory bugs in RPC-with-TLS" [id://20260504-sunrpc-tls-clnt-pin-v1-0-197f359c6072@oracle.com] to address two critical memory-management defects in the kernel's SUNRPC-over-TLS code path. The first patch fixed a resource leak of the "lower" rpc_clnt structure when the TLS handshake wait was interrupted by a signal; the second patched a use-after-free (UAF) that fired when an mTLS mount failed because the server rejected the client certificate. Michael Nemanov, the original UAF reporter from Vast Data, reviewed and tested both patches within a day of posting:

"Reviewed and tested both patches. Confirmed 3-sec delayed work was happening multiple times without UAF. Thank you."

Despite that quick review-and-test cycle, the series sat unqueued for seven weeks.

This week's activity (2026-06-19 → 2026-06-25)

This week saw only two messages in the thread, but they mark a meaningful turning point: the patches finally landed on a maintainer's radar.

Chuck Lever pings the series

On June 24, Chuck Lever sent a gentle nudge to the list, asking whether anyone could queue the two patches for an upcoming release:

"Gentle ping on this series, posted seven weeks ago. Michael Nemanov reviewed and tested both patches the following day; he is the reporter of the use-after-free that patch 2 addresses on an mTLS mount whose client certificate the server rejected."

"Could one of you queue these for an upcoming release? I am glad to repost against a current base if that is easier to apply."

The offer to rebase preemptively shows how long the series had been sitting — Lever was anticipating possible merge conflicts against a moving mainline.

Anna Schumaker picks it up

About fifty minutes later, NFS maintainer Anna Schumaker responded with an apology and a concrete commitment:

"I don't remember seeing these patches when they came in initially. Sorry about that! I'll take a look soon, and try to include them in a bugfixes pull request."

That reply is the substantive outcome of this week's activity: the series has been acknowledged by the NFS subsystem maintainer and is now slated for inclusion in an upcoming bugfixes pull request rather than waiting for the next feature merge window.

Nature of the discussion

This thread is squarely about bug fixes — specifically two memory-safety defects in the Linux NFS client's RPC-over-TLS implementation:

  1. Resource leak (xs_tcp_tls_setup_socket): the killed-wait path skipped rpc_shutdown_client(), leaking the lower rpc_clnt and its transport.
  2. Use-after-free (TLS connect_worker): the upper rpc_clnt could be freed by the mount caller before the queued worker fired, leading to a refcount underflow when the server rejected the client certificate during an mTLS handshake.

The second bug is the more serious one — it was reported in the field by Michael Nemanov and produced observable kernel memory corruption (a refcount_t underflow) on real mTLS mounts.

Final state

As of the close of this week, the series has not yet been merged but has moved from "unreviewed / unqueued" to "maintainer-acknowledged, scheduled for a bugfixes pull." No new technical arguments or design debates emerged this week — the discussion was purely about getting already-reviewed fixes into the tree. The remaining work is mechanical: Anna Schumaker will review and fold both patches into an upcoming -stable/bugfixes pull request, with Chuck Lever standing by to rebase if needed.
