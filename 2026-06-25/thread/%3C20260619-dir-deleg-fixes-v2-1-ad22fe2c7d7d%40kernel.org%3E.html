Layton revises dir-attr CB_NOTIFY recall fix; Lever flags incomplete coverage via Sashiko review

Summary

nfsd: v2 of the dir-attr CB_NOTIFY recall fix, and a reviewer's "not yet complete" caveat

Overview

This week's activity in this thread is short but consequential: Jeff Layton posted v2 of the patch that recalls a directory delegation when the server cannot encode a requested NOTIFY4_CHANGE_DIR_ATTRS event into the CB_NOTIFY callback, and Chuck Lever replied a few hours later with an AI-assisted review that — while accepting the patch's framing — concludes it "is not yet a complete fix." This is squarely a bug-fix discussion: a protocol-correctness defect in the server-side CB_NOTIFY path introduced by the recently-reviewed RFC 8881bis directory-delegation series, with direct implications for any client that relies on cached directory attributes.

Bridge from Prior Week

As summarized last week, Layton had posted a three-patch "follow-on fixes for CB_NOTIFY support" series on June 17, all of it server-side. Patch 3/3 was the original version of this very fix; patches 1/3 and 2/3 addressed the queue-overflow livelock and the sc_export UAF/NULL-deref in setup_notify_fhandle(). Chuck Lever's v6 review of the underlying NFSD series had surfaced those issues, and Layton noted that "These are just some problems that Sashiko pointed out in review that seem to be valid concerns." This week's thread is the continuation of patch 3/3 only — re-posted as a standalone v2 after addressing Lever's earlier NULL-pointer comments.

The v2 Patch (June 19)

Layton's v2 cover restates the core defect with precision:

"When the client requested NOTIFY4_CHANGE_DIR_ATTRS, nfsd4_cb_notify_prepare() tried to append the dir attribute change to the CB_NOTIFY, but silently dropped it if the attrmask space reservation failed or nfsd4_encode_dir_attr_change() failed to marshal the change into the buffer. It then returned true and transmitted a CB_NOTIFY lacking the requested notification, leaving the client's cached directory attributes stale with no indication."

The RFC anchor is explicit: "RFC 8881 s10.9.4 requires the server to recall the delegation when the directory changes in a way that is not covered by the notification." The fix treats an encode failure like the per-event encode failures already handled in the loop above — set an error and fall through to out_recall.

Two refinements distinguish v2 from v1:

  1. Distinguishing benign absence from genuine failure. Layton notes that "the granted notification mask and the requested dir attribute mask come from independent fields of the GET_DIR_DELEGATION request, so a client can be granted NOTIFY4_CHANGE_DIR_ATTRS while requesting no specific dir attributes." The new nfsd4_encode_dir_attr_change() therefore distinguishes "a genuine encode failure (which forces the recall) from that benign case (which simply omits the event)."
  2. Cleanup. "While we're in there, also remove an unneeded check for NOTIFY4_CHANGE_DIR_ATTRS from nfsd4_encode_dir_attr_change()."

The v2 changelog is terse: "Allow nfsd4_encode_dir_attr_change() to return ERR_PTR when there are errors," "Drop unneeded NOTIFY4_CHANGE_DIR_ATTRS check," and a link back to v1. The patch touches fs/nfsd/nfs4state.c and fs/nfsd/nfs4xdr.c (45 insertions, 28 deletions) and carries Fixes: 757a16cd93d5 ("nfsd: add support to CB_NOTIFY for dir attribute changes"). Layton also flags AI assistance in the sign-off block: "Assisted-by: Claude:claude-opus-4-8."

Lever's Review (June 20)

Lever's reply is notable for its methodology — he leans on an AI reviewer and a second model to cross-check:

"Sashiko reports (and gpt-5.5 agrees): Pre-existing issues:

  • [High] Genuine encode failures and vfs_getattr failures are silently masked as 0-length attributes, causing the directory attribute change event to be erroneously omitted instead of triggering a delegation recall."

Lever then reframes the severity classification himself:

"But this isn't really a pre-existing issue. It pre-exists this fix, yes, but it was introduced by 'nfsd: add support to CB_NOTIFY for dir attribute changes'. What that means is this patch is not yet a complete fix."

In other words: the v2 patch closes the path where nfsd4_encode_dir_attr_change() itself fails, but the upstream commit that introduced the feature also has an earlier failure mode — vfs_getattr returning an error gets masked as a 0-length attribute set rather than propagated as an encode error. That second path still silently drops the requested notification, which is exactly the RFC 8881 s10.9.4 violation the patch is meant to eliminate.

Significance for NFS Client Development

Although the fix is server-side, its blast radius is entirely on the client:

  • Stale directory caches. Without the recall, a client that has accepted NOTIFY4_CHANGE_DIR_ATTRS and is caching directory attributes (size, mtime, fileid, etc.) will continue to serve those cached values after the underlying directory changes. The client has no in-band signal that its cache is invalid — it would only notice on an explicit GETATTR or a failed operation.
  • The v2 gap matters for clients. Lever's "not yet a complete fix" caveat means that even with this patch applied, a vfs_getattr failure (e.g., during a concurrent unexport or filesystem error) can still produce a CB_NOTIFY that lacks the requested dir-attr event without a recall. Any client-side implementation of RFC 8881bis directory delegations — which Layton has previously identified as the gating dependency for upstream merge ("I don't think we'll want to merge these until we have a complete client-side implementation to test against") — will need to be tested against that residual path.
  • AI-assisted review is becoming routine. Both Layton (Claude) and Lever (Sashiko + gpt-5.5) explicitly credit AI tools in their sign-offs and review notes. The fact that the AI reviewer caught a "High" severity issue that the human author's v2 did not fully address underscores the value of cross-checking, but also shows that an AI flag alone does not close the loop — Lever still had to reclassify the finding and decide it blocked acceptance.

Status and Outlook

  • Thread status: Open. The v2 patch has received a substantive review comment indicating it is incomplete; no v3 has been posted in this thread's window.
  • Relationship to main series: Like the other two patches in Layton's follow-on series, this one is intended to be folded into the CB_NOTIFY dir-delegation series (targeting v7.3) rather than applied as a standalone commit.
  • Open items: The vfs_getattr masking path flagged by Sashiko/Lever needs an additional fix before this patch can be considered complete. The other open items from the prior week's review (refcount race in nfsd_break_one_deleg(), stale ncn_encode_err flag, order-aware client mask negotiation, two-word bitmap size budgeting) remain unaddressed in this thread.
