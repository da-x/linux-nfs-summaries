NFSD: Guard admin state-revocation walks with NFSD_NET_UP (startup NULL-deref fix)

Summary

NFSD: Guard admin state-revocation walks with NFSD_NET_UP

Type: Bug fix (NULL pointer dereference in the NFS server's admin state-revocation paths).

The patch and the bug it closes

Chuck Lever opened this thread on Sunday, June 21 with a single-patch submission, [PATCH] NFSD: Guard admin state-revocation walks with NFSD_NET_UP. The problem is a locally-triggerable kernel crash in nfsd. As Chuck describes in the commit message:

"Writing to /proc/fs/nfsd/unlock_filesystem, or sending the NFSD_CMD_UNLOCK_FILESYSTEM or NFSD_CMD_UNLOCK_EXPORT netlink command, walks the NFSv4 client hash tables to revoke open state and cancel async COPY operations. All three handlers gate that walk on nn->nfsd_serv, but a listener added via portlist or netlink listener_set sets nn->nfsd_serv before any nfsd thread starts."

The consequence is that nn->conf_id_hashtbl is still NULL when the walkers run, so:

"A local administrator with CAP_SYS_ADMIN can crash the kernel this way without ever starting the server."

The fix switches the three unlock entry points (write_unlock_fs, nfsd_nl_unlock_filesystem_doit, nfsd_nl_unlock_export_doit) from testing nn->nfsd_serv to testing the NFSD_NET_UP flag, which "brackets the window where the tables are live: set at the end of nfsd_startup_net() and cleared in nfsd_shutdown_net() after they are freed, both under nfsd_mutex." The patch touches fs/nfsd/nfs4proc.c, fs/nfsd/nfs4state.c and fs/nfsd/nfsctl.c (12 insertions, 15 deletions), carries a Reported-by: XIAO WU <xiaowu.417@qq.com> tag, and is marked as a follow-on to commit 1ac3629bf012 ("nfsd: prepare for supporting admin-revocation of state").

Review exchange

Jeff Layton picked up the patch the next morning (June 22) with a careful re-derivation of the race. He traced nfsd_create_serv() in nfssvc.c and confirmed the startup window:

"Can nn->nfsd_serv be non-NULL while the NFSv4 state tables are still NULL? ... nfsd_startup_net() is what calls nfs4_state_start_net() which allocates nn->conf_id_hashtbl in nfs4_state_create_net(). Until threads are started, nn->nfsd_net_up stays false and the hashtables stay NULL."

He then walked through nfsd4_cancel_copy_by_sb() to show exactly where the NULL deref lands, citing the KASAN report:

"The KASAN trace shows RIP in nfsd4_cancel_copy_by_sb at offset 0x184 with RAX 0, which matches the head pointer load."

He extended the same analysis to nfsd4_revoke_states() and the netlink path, and asked whether checking nn->nfsd_net_up would be more accurate than nn->nfsd_serv.

Chuck's reply (also June 22) confirmed the diagnosis and clarified the relationship between this patch and an earlier series:

"Yep, that's exactly the gap. The hunk you've quoted is 1/3 of the earlier 'post-shutdown use-after-free' series, which only guarded the shutdown side of the window."

He explained that the current patch is the follow-on that closes the startup side by switching all three unlock paths to test_bit(NFSD_NET_UP, &nn->flags) and updating the walkers' Context: notes accordingly. He also gently noted that Jeff's comment appeared to be aimed at the earlier series:

"I assume your comment was meant for 1/3 of that series rather than this thread... but we've reached the same conclusion, so no action needed beyond this patch, correct?"

Jeff acknowledged the mix-up and signed off:

"Ahh right. I missed that that had been fixed in the other series. This is fine then. Reviewed-by: Jeff Layton jlayton@kernel.org"

Context and significance

This is a small but important hardening fix in the NFS server (NFSD) admin-revocation machinery, which has been under active development — earlier work added automatic NFSv4 state revocation on filesystem unmount and a "post-shutdown use-after-free" guard. The current patch completes the picture by ensuring the revocation walkers cannot run before the per-netns state tables are allocated.

From an NFS client-development perspective, the relevance is indirect but real: the same admin-revocation paths that revoke open state and cancel async COPY operations on the server side determine how quickly a client's stale opens and in-flight COPY/WRITE_SAME-style operations are torn down when an administrator revokes access. A NULL-deref crash here would take down the entire NFS service (and with it, every connected client) without any client-side fault — so closing this startup-window race is a meaningful reliability improvement for deployments that use unlock_filesystem / netlink UNLOCK_FILESYSTEM / UNLOCK_EXPORT as operational tools.
