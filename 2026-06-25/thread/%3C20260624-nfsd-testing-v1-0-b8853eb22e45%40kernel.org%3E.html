nfsd: three inter-server copy offload bug fixes (cpntf race + UAFs)

Summary

nfsd: inter-server copy fixes — a 3-patch series lands on the list

This week's activity in this thread is limited to a single event: Jeff Layton posted a three-patch series titled [PATCH 0/3] nfsd: inter-server copy fixes](https://lore.kernel.org/linux-nfs/20260624-nfsd-testing-v1-0-b8853eb22e45@kernel.org/) on June 24, targeting bugs in the NFSv4.2 inter-server copy offload (COPY / COPY_NOTIFY / OFFLOAD_CANCEL) code paths. No replies have been recorded in the thread within this week's window.

Nature of the work

This is a bug-fix series — not a new feature or protocol change. The cover letter is candid about provenance:

"These patches fix bugs in inter-server copy offload code noticed by LLM inspection."

Two of the three patches are authored by Chris Mason (Meta) and one by Jeff Layton himself, with all carrying an Assisted-by: kres:claude-opus-4-x tag, making this one of the more prominent examples of AI-assisted kernel bug discovery reaching the public mailing list.

The series touches fs/nfsd/nfs4proc.c and fs/nfsd/nfs4state.c, with a net change of +164 / -41 lines across the two files.

Patch 1/3: cpntf publish race in nfs4_init_cp_state

PATCH 1/3 (Chris Mason) addresses a publish race in the COPY_NOTIFY state initialization. The core problem: nfs4_alloc_init_cpntf_state() splits IDR publication and cp_list linkage across two separate s2s_cp_lock critical sections. In the gap between them, a concurrent OFFLOAD_CANCEL can find the entry via idr_find(), pass the cs_type check, and call list_del() on a still-zeroed list_head — oopsing the server.

The race window is particularly dangerous because:

"The so_id returned to the client by COPY_NOTIFY is echoed back as cnr_stateid, so any authenticated NFSv4.2 client can drive OFFLOAD_CANCEL into manage_cpntf_state() against an entry still in the window."

The fix folds the cs_type assignment and list_add() into the same critical section as idr_alloc_cyclic(), initializes cp_list with INIT_LIST_HEAD(), and switches _free_cpntf_state_locked() to list_del_init() so stale unlinks become benign no-ops.

Patch 2/3: UAF in cpntf statelist drain

PATCH 2/3 (Chris Mason) fixes a use-after-free in nfs4_free_cpntf_statelist(). The drain loop re-decrements the same entry when a concurrent holder has bumped cs_count, eventually burning that holder's reference and freeing the slab object out from under it:

"The late put writes into the freed slab object's refcount_t, a KASAN-detectable use-after-free."

The fix rewrites the drain to unconditionally revoke each entry (unlink from list, remove from IDR) before dropping the parent's reference via a new put_cpntf_state_unlinked_locked() helper. A subtlety worth noting: gating idr_remove() on !list_empty() is essential because idr_alloc_cyclic() may have already recycled the so_id:

"an unconditional idr_remove() would silently unhash that live entry and corrupt subsequent find_cpntf_state() lookups."

Patch 3/3: UAF in async copy cancel and shutdown

PATCH 3/3 (Jeff Layton) is the most involved fix, addressing two interlocking UAF hazards in the async copy lifecycle:

  1. Double nfsd_file_put(): find_async_copy() bumps the refcount but leaves the copy on clp->async_copies, so both the cancel path and the reaper can call release_copy_files() concurrently, each observing a non-NULL nf_src pointer and double-decrementing nf_ref.

  2. kthread lifetime race: If the kthread sets NFSD4_COPY_F_STOPPED before the teardown caller's test_and_set_bit(), kthread_stop() is skipped and the copy can be freed while the kthread still runs.

The fix has several parts: unlinking the copy in find_async_copy() (mirroring nfsd4_unhash_copy()), giving the kthread its own reference, reordering wake_up_process() before list_add(), and adding an smp_load_acquire() barrier for cp_clp reads in nfsd4_send_cb_offload():

"set_bit() and clear_bit() are unordered atomics per Documentation/atomic_bitops.rst and provide no ordering fence, so a plain load of cp_clp could be reordered past the subsequent clp dereference on weakly-ordered hardware."

Context and significance

All three patches carry Fixes: tags pointing to the original COPY_NOTIFY introduction (624322f1adc5) and the async copy reaper (ac0514f4d198), indicating these are long-standing latent bugs in code that has been in-tree for years. The fact that they were identified through LLM-assisted inspection rather than field reports or KASAN fuzzing underscores a growing trend in kernel development where AI tools are surfacing subtle concurrency bugs that escape traditional review.

The series targets base commit 2bb83225da8ee0383d17783b5c903589696faf90 and was posted to the linux-nfs list with no visible discussion in this week's window. Given the severity (server oops, KASAN-detectable UAFs), these are likely candidates for stable backport once merged.

Status

As of the end of this reporting window, the series is at v1 with no recorded replies. The next development will be review feedback from Trond Myklebust, Anna Schumaker, or other nfsd maintainers.
