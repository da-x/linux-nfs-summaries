nfsd/sunrpc: v2 13-patch series for netlink-based mountd/exportd upcalls submitted

Summary

nfsd/sunrpc: Netlink Upcalls for mountd/exportd — v2 Series Submitted

Classification

This is a new feature / protocol interface change affecting the NFS server (nfsd) and SunRPC subsystem. It introduces netlink-based communication channels to replace antiquated /proc-based pipe interfaces used by mountd and exportd. While primarily an nfsd/userspace tooling concern, it has implications for containerized NFS deployments and future export option extensibility.

Overview

On March 25, Jeff Layton submitted the second version of a 13-patch series titled "nfsd/sunrpc: add support for netlink upcalls for mountd/exportd". The series adds generic netlink families and commands to replace the decades-old /proc-based cache pipe mechanism used by mountd and exportd for handling identity mapping (auth.unix.ip, auth.unix.gid) and export resolution (svc_export, nfsd.fh).

"mountd/exportd use the sunrpc cache mechanism for some of its internal caches that are populated by userland. These currently use some very antiquated interfaces in /proc to handle upcalls and downcalls. While it has worked well for decades and is relatively stable, it has some problems." — Jeff Layton

Layton identified two primary motivations:

"Most notably, it's very difficult to extend to add support for new export options. There is also the matter of requiring /proc which is not always desirable in a container." — Jeff Layton

The v2 series addressed review feedback from Chuck Lever (noted as "Chuck's review comments") and added the netdev mailing list for broader netlink expertise. No replies or reviews appeared within this week's window; substantive discussion from Chuck Lever began on March 30, outside the reporting period.

Key Technical Architecture

The series introduces a new cache_notify callback in struct cache_detail. When a cache miss occurs and an upcall is needed, the kernel sends a multicast netlink notification to userspace. Userspace then fetches pending requests via a dump operation and responds with results — all over netlink rather than through /proc pipes.

Patch Breakdown

Patches 01/13–04/13: Preparatory Renames

These patches rename existing functions to remove the "pipe" terminology in anticipation of the new netlink mechanism:

  • sunrpc_cache_pipe_upcall() → sunrpc_cache_upcall() Patch 02/13
  • sunrpc_cache_pipe_upcall_timeout() → sunrpc_cache_upcall_warn() Patch 03/13
  • cache_pipe_upcall() → cache_do_upcall() Patch 04/13

Patches 05/13–06/13: Core Infrastructure

Patch 05/13 adds the cache_notify callback to struct cache_detail. Patch 06/13 introduces sunrpc_cache_requests_count() and sunrpc_cache_requests_snapshot() helpers that safely enumerate pending cache requests without exposing internal structures.

"The snapshot function takes a cache_get() reference on each item so the caller can safely use them after the queue_lock is released." — Jeff Layton

Patch 07/13: SunRPC Generic Netlink Family

A new "sunrpc" generic netlink family is created with an "exportd" multicast group, since the auth.unix.ip and auth.unix.gid caches reside in the sunrpc module and cannot use the nfsd netlink family. A YAML spec (sunrpc_cache.yaml) defines the cache-type enum and notification events.

Patches 08/13–09/13: Auth Cache Netlink Upcalls

Patch 08/13 implements netlink upcall support for the auth.unix.ip (ip_map) cache, including dumpit handlers that snapshot pending requests and doit handlers that parse userland responses. Patch 09/13 does the same for the auth.unix.gid (unix_gid) cache, supporting multi-attribute GID lists.

Patches 10/13–11/13: NFSd Export Cache Netlink Upcalls

Patch 10/13 adds netlink support for the svc_export (nfsd.export) cache — the most significant patch in the series at 835 lines added. It handles export resolution with attributes for client name, path, expiry, flags, anon uid/gid, fslocations, UUID, secinfo, xprtsec, and fsid.

"Note that the export-flags and xprtsec-mode enums are organized to match their counterparts in include/uapi/linux/nfsd/export.h. The intent is that future export options will only be added to the netlink headers, which should eliminate the need to keep so much in sync." — Jeff Layton

Patch 11/13 adds the same pattern for the nfsd.fh (expkey) cache, used for filehandle-to-path resolution.

Patches 12/13–13/13: Cache Flush Commands

The final two patches add SUNRPC_CMD_CACHE_FLUSH Patch 12/13 and NFSD_CMD_CACHE_FLUSH Patch 13/13 commands, allowing userspace to flush auth and export caches via netlink instead of writing to /proc/net/rpc/*/flush. An optional mask attribute selects specific caches; omitting it flushes all.

v2 Changes from v1

Layton listed the following improvements over v1:

  • Reworded comment above cache_do_upcall()
  • Delayed inclusion of genetlink.h until needed
  • Implemented proper netlink dump continuation support in all downcalls
  • Only triggers ->cache_notify if request is still PENDING
  • Added comments to svc_export netlink flag enums
  • Shrunk size passed to genlmsg_new for notify requests to sizeof(u32)
  • Moved nfsd_cache_notify() out of autogenerated file

Significance for NFS Development

While this series targets the NFS server side (nfsd/sunrpc) rather than the NFS client, it is highly relevant to NFS infrastructure:

  1. Container Support: Eliminating the /proc dependency enables NFS server daemons to run in containers where /proc access may be restricted or undesirable.
  2. Extensibility: The netlink-based interface makes it straightforward to add new export options without modifying pipe protocols — a long-standing pain point for nfsd developers.
  3. Companion Userspace Work: Layton noted that a companion patchset for nfs-utils adds support in mountd, exportd, and exportfs, with /proc fallback for older kernels.

Conclusion

This 13-patch series represents a modernization of the NFS server's userspace communication infrastructure, replacing decades-old /proc pipe interfaces with generic netlink. The v2 submission addressed prior review concerns and expanded the reviewer base to include netdev experts. With no discussion within this week's window, the series awaits further review — Chuck Lever's responses began arriving on March 30.
