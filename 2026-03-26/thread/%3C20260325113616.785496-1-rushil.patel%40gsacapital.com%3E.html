Making NFS Writeback Waits Killable to Prevent Unkillable D-State Processes

Summary

Making NFS Writeback Waits Killable: A Critical Fix for Unkillable D-State Processes

Type: Bug fix / Kernel infrastructure change (generic writeback path with NFS-specific implications)

Overview

This week saw an important RFC discussion on a long-standing problem in the Linux NFS client: processes with dirty NFS pages becoming stuck in uninterruptible sleep (D-state) when their jobs are cancelled, effectively requiring a node reboot to recover. Rushil Patel of GSA Capital proposed a fix that touches the generic mm/filemap writeback path, and received detailed feedback from Matthew Wilcox, the maintainer of the page cache subsystem.

The Problem

Rushil Patel described a production issue encountered on Slurm compute nodes using NFSv4.1 mounts to NetApp filers:

"When a job is cancelled, processes with dirty NFS pages get stuck in D-state inside folio_wait_bit_common() because __filemap_fdatawait_range() uses folio_wait_writeback(), which is TASK_UNINTERRUPTIBLE. If the filer is slow to respond these processes are unkillable - we've found the only recovery in practice is rebooting the node."

The root cause is that __filemap_fdatawait_range() waits for writeback completion using folio_wait_writeback(), which operates with TASK_UNINTERRUPTIBLE sleep state. This means SIGKILL cannot interrupt the wait, leaving processes permanently stuck if the NFS server is slow or unresponsive.

The Proposed Fix

Patel's RFC patch proposes two key changes:

  1. Switch to killable waits: Replace folio_wait_writeback() with folio_wait_writeback_killable() in __filemap_fdatawait_range(), allowing SIGKILL to interrupt the wait. Writeback continues on the server side; the client simply stops waiting for the acknowledgement.

  2. Handle re-entry during process exit: A critical subtlety arises when a killed process re-enters the writeback path during do_exit(). Patel identified a five-step failure scenario:

    "1. SIGKILL wakes the killable wait, signal is consumed by get_signal()"
    "2. do_exit() -> exit_signals() sets PF_EXITING"
    "3. do_exit() -> exit_files() -> nfs4_file_flush() -> nfs_wb_all() re-enters __filemap_fdatawait_range()"
    "4. wants_signal() checks PF_EXITING before the SIGKILL special case (kernel/signal.c:951 vs 954), so it returns false"
    "5. No signal can wake the second wait -> stuck in D-state again"

To address this, Patel added a PF_EXITING check to avoid re-entering the wait entirely, citing precedent in mm/oom_kill.c, mm/memcontrol.c, block/blk-ioc.c, and io_uring/.

Matthew Wilcox's Feedback

Matthew Wilcox expressed strong sympathy for the problem, noting it was similar to one he encountered when introducing the TASK_KILLABLE infrastructure in 2007:

"It was something similar which led to me introducing the TASK_KILLABLE infrastructure back in 2007. My problem was read-only though, and while I had an initial attempt to also handle write workloads, it didn't work and I didn't have a personal need for it, so I abandoned it. Now you have a real need, so let's make it work."

However, Wilcox raised concerns about the placement of the PF_EXITING check:

"I'm not entirely comfortable with the location of the check. I feel that __filemap_fdatawait_range() is a bit too low level for a check of PF_EXITING. I could see there being other places which really do want to wait, even in the presence of an exiting task."

Wilcox suggested an alternative approach: suppressing the call from nfs_wb_all() itself by using filemap_fdatawrite() (which initiates writeback without waiting) instead of filemap_write_and_wait() when the process is exiting:

-	ret = filemap_write_and_wait(inode->i_mapping);
+	if (current->flags & PF_EXITING)
+		ret = filemap_fdatawrite(inode->i_mapping);
+	else
+		ret = filemap_write_and_wait(inode->i_mapping);

Wilcox also noted a concern about the subsequent nfs_commit_inode(inode, FLUSH_SYNC) call in nfs_wb_all(), which he inferred would also wait for the server. However, he acknowledged that Patel's testing showed the approach works:

"but if your testing shows that it works, I must be mistaken about that."

Key Technical Considerations

  • Error reporting: Patel argued that all six callers of __filemap_fdatawait_range() detect errors independently via errseq_t / filemap_check_errors(), so the early return doesn't suppress error reporting. Wilcox was cautious: "I'm not entirely sure it doesn't suppress error reporting. But I think I see what you're trying to say, and I think the change of behaviour is one that was never guaranteed anyway."

  • NFS consistency model: Wilcox noted that NFS has a close-to-open consistency model and other filesystems don't perform this flush-on-close behavior. He concluded:

"I believe we can break this guarantee in this case as it's not an orderly close but an involuntary termination of the process."

Current Status

The discussion remains at the RFC stage. Wilcox added NFS maintainers to the thread for their opinions, and Patel demonstrated flexibility on the approach, having considered alternatives but seeking guidance on whether modifying mm/filemap.c was the right place for the fix or if a different approach would be preferred. The patch was tested with iptables DROP on port 2049 to simulate server unresponsiveness, confirming that the killable-only revision still gets stuck on re-entry while the PF_EXITING + killable combination allows clean termination.

Significance for NFS Client Development

This fix addresses a critical operational issue where NFS client nodes become effectively bricked when jobs are cancelled during active writeback to an unresponsive server. The ability to cleanly kill such processes without rebooting has significant implications for HPC environments using Slurm and similar job schedulers with NFS-backed storage.
