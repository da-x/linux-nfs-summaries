NFS: v2 patch to fix writeback loops on ENOSPC errors

Summary

NFS: Fix Writeback Loops on ENOSPC Errors — v2 Patch Submitted

Classification

This is a bug fix targeting the NFS client's page cache writeback subsystem. It addresses a scenario where writeback I/O can become stuck in an infinite retry loop when the server returns ENOSPC (out of space) errors during unstable writes.

Overview

On March 25, Red Hat's Olga Kornievskaia submitted v2 of her patch titled "NFS: fix writeback in presence of errors" 20260325180050.55186-1-okorniev@redhat.com. This follows an RFC posted on March 12 that first identified the problem while running xfstest generic/751.

The v2 submission represents a significant architectural refinement over the RFC: rather than marking synchronous writeback intent in the transient nfs_page structure, Kornievskaia now stores the flag in the more persistent nfs_open_context. Additionally, the fix has been extended to cover the LocalIO code path.

The Bug: Two Failure Patterns

As originally described in the RFC and reiterated in v2, Kornievskaia identified two distinct patterns that cause writeback to loop indefinitely:

Pattern #1: Writeback I/O experiences ENOSPC on an offset smaller than the file size:

"write offset=0 len=4096 how=unstable OK write offset=8192 len=4096 how=unstable OK write offset=12288 len=4096 how=unstable ENOSPC write offset=4096 len=4096 how=unstable ENOSPC"

The client sends a commit and receives a verifier different from the last successful write. It marks pages dirty and retries writeback — but again sends writes as unstable, hitting the same ENOSPC error in a loop.

Pattern #2: An unstable write followed by a short write and then ENOSPC:

"write offset=0 len=4096 how=unstable OK write offset=4096 len=4096 how=unstable returns OK but count=100 write offset=4197 len=3996 how=stable returns ENOSPC"

The same looping behavior ensues.

The Fix: Synchronous Writeback via nfs_open_context

Kornievskaia's core proposal remains the same — detect these error conditions and force synchronous writeback instead of allowing the asynchronous path to retry indefinitely. However, the v2 implementation differs materially from the RFC:

"Instead, this patch proposes to identify those conditions and mark requests to be done synchronously instead. Previous solution tried to mark it in the nfs_page, however that's not persistent thus instead mark it in the nfs_open_context."

The key insight driving the v2 change is that nfs_page structures are transient — they can be freed and recreated during writeback retries, losing any state stored therein. The nfs_open_context, by contrast, persists across multiple page allocations for a given file open, making it a reliable location for tracking the "do sync" flag.

Files Modified

The patch touches four files with 23 lines added:

  • fs/nfs/localio.c (+10 lines): Extends the fix to the LocalIO code path, recognizing that the same looping problem occurs there as well.
  • fs/nfs/pagelist.c (+3 lines): Adds logic to check the synchronous flag in page list handling.
  • fs/nfs/write.c (+9 lines): Implements the core detection and flagging logic for error conditions.
  • include/linux/nfs_fs.h (+1 line): Adds the new field to nfs_open_context.

The decision to move the flag from nfs_page to nfs_open_context is a notable architectural improvement, ensuring that the synchronous writeback intent survives page reallocation during retry cycles.

Significance for NFS Client Development

This fix addresses a data integrity and reliability concern in the NFS client:

  1. Infinite Loop Prevention: Without this fix, writeback can hang indefinitely under server-side ENOSPC conditions, potentially causing application stalls or system-level I/O deadlocks.
  2. LocalIO Support: The extension to LocalIO ensures that systems using the newer LocalIO optimization path are equally protected.
  3. Test-Driven Discovery: The bug was uncovered by xfstest generic/751, demonstrating the value of filesystem test suites in surfacing edge-case client behavior.

Given that the RFC also received no responses in its initial posting week, this may indicate either a quiet review period or that the change is being tracked internally by the maintainers.
