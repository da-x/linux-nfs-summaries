Summary

netfs: Replace folio_queue with Segmented bio_vec[] Chains (bvecq)

Overview

This week, David Howells submitted a formal 26-patch series to the VFS tree, superseding last week's 17-patch RFC. The series constitutes a major architectural refactoring of netfslib's buffer management subsystem, replacing the legacy folio_queue, rolling_buffer, and ITER_FOLIOQ constructs with a new segmented chain of bio_vec[] arrays dubbed bvecq.

"The patches get rid of folio_queue, rolling_buffer and ITER_FOLIOQ, replacing the folio queue construct used to manage buffers in netfslib with one based around a segmented chain of bio_vec arrays instead." — David Howells

The series is classified as a feature/refactoring with embedded bug fixes. It touches netfslib, cachefiles, AFS, CIFS, 9P, Ceph, NFS fscache integration, the mm readahead subsystem, and core iov_iter infrastructure.

Key Technical Arguments

Howells articulated three primary motivations for the shift:

  1. Kernel I/O Consolidation: The kernel file I/O subsystem is converging on bio_vec[] arrays; migrating netfslib aligns it with this direction.
  2. Unified Buffering Scheme: netfslib already uses bio_vec[] for unbuffered/Direct I/O (DIO). Consolidating to a single buffering scheme reduces complexity.
  3. TCP Efficiency: The new design enables sending entire filesystem RPC request messages via a single kernel_sendmsg() call, eliminating the need for corking and keeping the transmission loop within a single tcp_sendmsg().

The core data structure is struct bvecq, which supports linked segments (next/prev), file position tracking (fpos), discontiguity flags, reference counting for safe buffer slice sharing, and an associated iterator type ITER_BVECQ intended to replace ITER_FOLIOQ.

Resolution of the FIEMAP Controversy

Last week's RFC drew strong objections from Christoph Hellwig regarding the use of FIEMAP in the data path for cache extent discovery. Hellwig stated:

"Hell no. FIEMAP is purely a debugging tool and must not get anywhere near a data path. NAK to all of this."

In this formal submission, Howells addressed that concern by removing the FIEMAP dependency entirely. Instead, Patch 08/26 introduces a new cachefiles content-tracking mechanism using CACHEFILES_CONTENT_ALL for contiguous files and a refined ->query_occupancy() cache method that leverages SEEK_DATA/SEEK_HOLE only when necessary. The backing file's i_size is now used to track the highest written position, while xattr.object_size stores the network filesystem object size, enabling efficient detection of whether holes exist without relying on FIEMAP.

Important Bug Fixes Embedded in the Series

The series incorporates several critical bug fixes contributed by other developers:

NULL Pointer Dereference in Unbuffered Write Retry

Deepanshu Kartikey fixed a NULL pointer dereference in netfs_unbuffered_write() on retry. When a write subrequest is marked NETFS_SREQ_NEED_RETRY, the retry path unconditionally called stream->prepare_write() without checking for NULL. Filesystems like 9P do not set this operation, causing a crash when get_user_pages() fails with -EFAULT. The fix mirrors the pattern in write_retry.c: if stream->prepare_write is NULL, it skips renegotiation and directly reissues via netfs_reissue_write().

"Filesystems such as 9P do not set the prepare_write operation, so stream->prepare_write remains NULL. When get_user_pages() fails with -EFAULT and the subrequest is flagged for retry, this results in a NULL pointer dereference." — Deepanshu Kartikey

Kernel BUG in netfs_limit_iter() for ITER_KVEC

Also from Deepanshu Kartikey, this patch resolves a kernel BUG triggered when a process crashes and the kernel writes a core dump to a 9P filesystem, creating an ITER_KVEC iterator that netfs_limit_iter() did not handle. The fix adds netfs_limit_kvec() following the same pattern as netfs_limit_bvec().

VM_BUG_ON_FOLIO in netfs_write_begin()

Viacheslav Dubeyko fixed a race condition reproducible via generic/013 xfstests that triggered VM_BUG_ON_FOLIO(!folio_test_locked(folio)) in folio_unlock(). The issue arose because netfs_unlock_abandoned_read_pages() did not check the NETFS_RREQ_NO_UNLOCK_FOLIO flag and executed folio_unlock() unconditionally, even when another path had already unlocked the folio.

"The key reason of the issue that netfs_unlock_abandoned_read_pages() doesn't check the flag NETFS_RREQ_NO_UNLOCK_FOLIO and executes folio_unlock() unconditionally." — Viacheslav Dubeyko

Error Handling in netfs_extract_user_iter()

Paulo Alcantara corrected error handling in netfs_extract_user_iter(), ensuring that short DIO reads and writes can be issued even when iov_iter_extract_pages() fails to extract all user pages (bailing out only on -ENOMEM). This fix resolved failures in the LTP mmapstress02 test against CIFS.

Read Abandonment During Retry

Howells fixed a bug where all remaining subrequests from a read request could be abandoned during retry due to an uninitialized or stale subreq pointer in the abandonment loop.

Excess dput() in Cachefiles

Howells fixed a reference counting bug in cachefiles_bury_object() that caused an excess dput() after end_removing(), leading to occasional dcache warnings and potential use-after-free on directory entries.

Architectural Changes

The series introduces significant structural changes to netfslib:

  • Buffer tracking is managed with three cursors: load_cursor (where new folios are added), dispatch_cursor (where subrequest buffers start), and collect_cursor (where folios are unlocked).
  • Prepare and issue operations are merged: ->prepare_read(), buffer setup, and ->issue_read() are collapsed into a single callback model. The filesystem receives a bvecq holding the buffer rather than an iov_iter, enabling it to duplicate and attach headers/trailers for protocol elements or link multiple bvecqs for compound operations.
  • CIFS and AFS integration: CIFS switches to bvecq for encryption buffering and RDMA extraction; AFS directories use bvecq instead of folio_queue.
  • Cleanup: All folio_queue, rolling_buffer, and ITER_FOLIOQ code is removed.

"The filesystem (or cache) then gets to take a slice of the master bvec chain as its I/O buffer for each subrequest, including discontiguities if it can support a sparse/vectored RPC (as Ceph can)." — David Howells

Discussion and Reception

Discussion within this week's window was minimal. The only reply was from ChenXiaoSong, who noted a typo in the subject of Patch 25/26:

"There are two 'the's in the subject."

Substantive reviews from Paulo Alcantara and Stefan Metzmacher arrived after the window closed (March 28–29), providing Reviewed-by tags on several patches.

Conclusion

This 26-patch series represents a landmark refactoring of netfslib's buffer management, consolidating multiple buffering schemes into a unified bio_vec[]-based model. The embedded bug fixes address real-world crashes and correctness issues affecting 9P, CIFS, Ceph, and NFS clients using fscache. By resolving the FIEMAP controversy through an alternative cachefiles extent-tracking mechanism, the series is now positioned for inclusion in the VFS tree. NFS client developers should note that while the NFS client itself is not directly modified beyond fscache integration updates, the underlying netfslib changes will affect all network filesystems leveraging this infrastructure for buffered and direct I/O operations.
