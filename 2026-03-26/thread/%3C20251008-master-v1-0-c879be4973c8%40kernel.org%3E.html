Summary

NFS: NFSv4.0 Server Deprecation Lands in nfs-utils 2.9.1-rc1

Overview

This thread tracks the finalization and integration of Jeff Layton's patch series to disable NFSv4.0 server support by default in nfsd and nfsdctl. This is a protocol deprecation change, not a bug fix or new feature, aimed at nudging administrators toward newer NFSv4 minor versions (v4.1+) while preserving backward compatibility for those who explicitly opt-in.

Background (Prior Weeks)

Originally submitted in October 2025 following discussions at the NFS Bakeathon, the two-patch series modifies both the kernel nfsd module and the userspace nfsdctl utility to reject NFSv4.0 connections unless explicitly enabled via configuration. As noted in the January 2026 summary, Steve Dickson had acknowledged review ("Working on it...") but integration was delayed due to other priorities, including CVE remediation and additional release cycles.

Activity This Week

Patch Integration Confirmed

On March 22, Steve Dickson announced that the patches have been committed and are included in the nfs-utils-2.9.1-rc1 release [id://a04afd6b-e295-4100-a785-2b6feb6b3cf7@redhat.com]:

"Committed... (tag: nfs-utils-2-9-1-rc1)"

He apologized for the delay, citing competing priorities:

"My apologies for taking so long... The CVE took longer than expected and there was some issues with recent patches, which caused another release."

Dickson emphasized the significance of this change:

"Turning off a protocol version (v4.0) on the server by default which this rc release does, is not a small thing although with the 7.X kernels the v4.0 client is already off."

He also outlined the path forward for the nfs-utils release cycle:

"So the next rc releases will contain the current outstanding patches (a rc release for each patch set) then creating another release (2.9.1)... Definitely in time for the upcoming Bakeathon!"

Configuration Consistency Follow-Up

Salvatore Bonaccorso raised a consistency concern regarding the nfs.conf documentation/comments [id://acBfpHr2e6LMmiGQ@eldamar.lan]. He noted that the default configuration file still shows # vers4.0=y as a commented example, which contradicts the new default behavior:

"Should the 'default off' change as well be reflected in the commented entry for vers4.0 and read vers4.0=n for consistency?"

Jeff Layton acknowledged this as a valid observation [id://643b2d6bb1bdda8c2602535da9c679e6dfbe68a7.camel@kernel.org]:

"Yes, good catch. Would you mind spinning up a patch? If not, I'll do one in the near future."

Salvatore agreed to prepare and submit the follow-up patch [id://acDlnPo3z5Uk2vcH@eldamar.lan]:

"Thanks for confirming, yes happy to provide a patch for that, will send it later the day."

Key Technical Arguments

  1. Deprecation Rationale: NFSv4.0 lacks features present in later minor versions (stateless operations, improved security, pNFS support). Disabling it by default reduces server complexity and encourages adoption of modern protocol versions.
  2. Client-Server Alignment: With kernel 7.X already disabling the v4.0 client by default, this change aligns server behavior with client-side defaults, reducing confusion in homogeneous deployments.
  3. Backward Compatibility: The change is opt-out rather than removal; administrators can still enable v4.0 via nfs.conf or command-line options if legacy clients require it.
  4. Documentation Consistency: The follow-up discussion highlights the importance of keeping configuration file comments aligned with actual default behavior to avoid misleading administrators.

Final Conclusions

  • The NFSv4.0 server deprecation patches have been merged into nfs-utils and are available in version 2.9.1-rc1.
  • A follow-up patch is being prepared by Salvatore Bonaccorso to update the nfs.conf commented defaults from # vers4.0=y to # vers4.0=n for consistency.
  • The change represents a significant step in the broader NFS ecosystem modernization effort, with full release targeted for the upcoming NFS Bakeathon.
