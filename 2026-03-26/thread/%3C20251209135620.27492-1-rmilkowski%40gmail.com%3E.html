pNFS/filelayout: Data server op_status error handling patch acknowledged

Summary

pNFS/filelayout: Handle Data Server op_status Errors

Classification: Bug Fix (pNFS Client)

This thread concerns a bug fix for the NFS client's pNFS file layout driver, addressing how data server (DS) NFS-level status errors are handled during I/O operations.

Background (December 2025)

The discussion began on December 9, 2025, when Robert Milkowski submitted a patch titled "[PATCH] pnfs/filelayout: handle data server op_status errors" introducing the issue. The patch identified that the file layout driver only examined RPC transport errors when communicating with data servers, ignoring NFS-level status codes returned in op_status. This meant session errors, layout-invalidating statuses, and retry hints from the DS could be silently ignored — potentially leading to missed session recovery, stale layouts, or failed retries.

Milkowski's patch proposed passing the DS op_status into the async error handler and handling the same set of NFS status codes as the flexfiles driver (referencing commit 38074de35b01, "NFSv4/flexfiles: Fix handling of NFS level errors in I/O").

Maintainer Feedback

NFS client maintainer Trond Myklebust responded on the same day with a nuanced review. He clarified an important architectural detail:

"The task->tk_status can carry NFS level status if there was no RPC error. That's why we distinguish between task->tk_status and task->tk_rpc_status (the latter being guaranteed to only carry RPC errors)."

Myklebust then questioned the premise of the patch:

"IOW: is there any evidence of what you call out above?"

He indicated willingness to accept a cleanup-style patch, provided it replaced existing NFSv4.1 error handling using task->tk_status rather than simply adding new cases. However, he emphasized the need for thorough testing:

"However I'd want to see evidence that the resulting patch has been thoroughly tested before submission, because I currently have no way to test it myself."

This Week's Activity (March 23, 2026)

After a gap of over three months, Robert Milkowski sent a reply this week. The message body is empty — no text, no revised patch, no additional commentary. This appears to be an acknowledgment or a placeholder reply, possibly indicating that Milkowski has received and noted Myklebust's feedback and intends to address the concerns (providing evidence of the issue and/or submitting a properly tested revision).

Current Status

The thread remains open with no revised patch submitted as of this week. The key outstanding items are:

  1. Evidence of the bug: Trond Myklebust requested concrete evidence that the file layout driver is indeed missing NFS-level error handling in practice.
  2. Thorough testing: Any revised patch must be accompanied by testing evidence, given that the maintainer cannot test pNFS file layout scenarios himself.
  3. Proper integration: The fix should replace (not duplicate) existing task->tk_status-based error handling for NFSv4.1 errors.

Significance for NFS Client Development

This patch touches a critical area of the NFS client: proper error handling in pNFS environments where data servers can return NFS-level status codes independently of RPC transport errors. If left unaddressed, clients using the file layout driver could experience silent failures — stale layouts persisting after invalidation, missed session recovery opportunities, and incorrect retry behavior. The flexfiles driver already handles this correctly (via commit 38074de35b01), making this a parity fix for the older file layout driver.
