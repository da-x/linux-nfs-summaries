NFSv4.1 Client Hang in OPEN Reclaim Path on Kernel 5.15

Overview

This week, a new bug report thread was opened by Wei Guo from UCloud regarding an NFSv4.1 client hang observed on Linux kernel 5.15 (Ubuntu 22.04). The discussion is classified as a bug fix investigation — specifically targeting a deadlock-like condition in the NFS client's state recovery path. No replies from maintainers or other developers were received during this window; the thread consists solely of two messages from the reporter.

The Problem: Stuck State Manager During OPEN Reclaim

The issue manifests when the NFS server returns NFS4ERR_EXPIRED, triggering the client to enter state recovery. However, the reclaim process fails to complete, leaving the state manager thread permanently stuck. The observed kernel stack trace is:

rpc_wait_bit_killable
__rpc_wait_for_completion_task
nfs4_run_open_task
nfs4_open_recover_helper
nfs4_open_recover
nfs4_do_open_expired
nfs40_open_expired
__nfs4_reclaim_open_state
nfs4_reclaim_open_state
nfs4_do_reclaim
nfs4_state_manager

As described by the reporter:

"The issue starts when the server returns NFS4ERR_EXPIRED. The client appears to enter recovery, but the reclaim process does not complete."

Key observations from the initial report include:

  • ~30 million RPC calls have been issued, yet retransmissions are extremely low (only 94), suggesting the problem is not caused by network loss or server unresponsiveness.
  • The server continues to return NFS4ERR_EXPIRED throughout.
  • IO operations continue but repeatedly fail.
  • Network connectivity appears stable and the NFS server shows no signs of restart or failover.

Lease Renewal Anomaly in NFSv4.1

A particularly notable aspect of this bug is that the client continues to send RENEW/SEQUENCE traffic — which in NFSv4.1 should implicitly renew the lease — yet the client still encounters NFS4ERR_EXPIRED. This raises the question of whether lease renewal is effectively occurring despite the apparent activity.

The reporter posed three critical questions:

  1. Under what conditions might a client still hit NFS4ERR_EXPIRED despite ongoing SEQUENCE activity and a seemingly healthy server/network?
  2. Could there be scenarios where RPC completion, session slot handling, or sequence handling prevents the lease from being properly renewed?
  3. Is this behavior something that has been observed before in the NFSv4.1 recovery or session handling paths, particularly in 5.15?

Updated Finding: Stale StateIDs and Sequence IDs

In a follow-up message posted shortly after, the reporter provided additional server-side diagnostics:

"Server-side logs indicate that the client is sending stale stateids / sequence IDs, and the server responds with NFS4ERR_OLD_STATEID."

"This suggests that the client state may not be properly updated after previous operations."

This finding significantly narrows the root cause hypothesis: the client's internal state tracking (stateids and/or sequence counters) appears to have diverged from the server's view, causing the server to reject reclaim attempts with NFS4ERR_OLD_STATEID. This would explain why the OPEN reclaim loop never completes — each attempt is rejected due to stale state references, and the client remains stuck in rpc_wait_bit_killable waiting for RPC completion that can never succeed.

Current Status

As of the end of this reporting window, no responses from NFS maintainers or other developers have been received. The thread remains open with no proposed patches or workarounds. The reporter also asked:

"If there are any known fixes or relevant patches in newer kernels (e.g., 5.19 or 6.x), we would also be very interested to learn about them."

This question has not yet been addressed.

Significance for NFS Client Development

This bug report highlights a subtle but serious class of issues in the NFSv4.1 client's state recovery machinery:

  1. State divergence between client and server: When the client's cached stateids or sequence IDs become stale, the reclaim path can enter an infinite loop where every OPEN attempt is rejected by the server.
  2. Lease renewal vs. state consistency: Even when SEQUENCE operations appear to be flowing normally, underlying state inconsistencies can still cause NFS4ERR_EXPIRED and subsequent recovery failures.
  3. Kernel version impact: The issue was reported on kernel 5.15 (an LTS release widely used in production), raising concerns about whether similar bugs exist in other supported kernels or have been addressed in newer versions.

Further investigation by the NFS maintainer team will be needed to determine whether this is a regression, a latent bug in the reclaim logic, or an interaction with specific server implementations.
