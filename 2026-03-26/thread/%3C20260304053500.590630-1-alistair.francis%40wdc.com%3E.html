NVMe-TCP KeyUpdate: Code Structure Review by Christoph Hellwig

Summary

NVMe-TCP TLS KeyUpdate: Code Structure Review Continues

Overview

This week, the discussion around Alistair Francis's five-patch series [PATCH v7] nvme-tcp: Support receiving KeyUpdate requests continued with Christoph Hellwig providing detailed code-structure and style feedback on patches 4/5 (NVMe host) and 5/5 (NVMe target). This series introduces support for TLS 1.3 KeyUpdate messages in NVMe-TCP, enabling connections to survive key rotation events without dropping I/O. The underlying net/handshake infrastructure touched by this series is also shared with NFS over TLS via SunRPC, making these changes relevant to the broader NFS/TLS ecosystem.

Prior Context (Brief)

In the previous week's activity summarized on 2026-03-05, Hannes Reinecke reviewed Patch 4/5 and suggested simplifying TLS record type handling from a switch to an if statement, while also raising a security concern that unhandled TLS records (such as Alerts) must trigger connection resets. Alistair agreed with the simplification approach.

This Week's Discussion: Code Structure and Style

Christoph Hellwig weighed in on March 20 with two messages offering structural improvements to both the NVMe host and target sides of the KeyUpdate implementation.

Patch 4/5 (NVMe Host): Factoring Out Switch Statements

Building on the prior exchange between Hannes Reinecke and Alistair Francis about simplifying TLS record type handling, Christoph Hellwig pushed further for better code organization:

"Agreed. OTOH having more than a handful of lines in switches like this is a always a bad idea, so factoring this out into a type-specific helper would be much preferred." Christoph Hellwig

This recommendation goes beyond merely replacing a switch with an if; it advocates extracting the TLS record type dispatch logic into dedicated helper functions, improving maintainability and readability for future TLS record type additions.

Patch 5/5 (NVMe Target): Conditional Compilation and Code Style

Christoph's review of the target-side patch focused on several code hygiene issues:

  1. Avoiding #ifdef in function declarations: Christoph suggested relying on compiler dead-code elimination instead of sprinkling preprocessor conditionals throughout the header:

    "Can we find a way to just avoid the ifdefered here and just rely on compiler dead code elimination?" Christoph Hellwig

  2. Using IS_ENABLED() for runtime checks: For conditional blocks guarded by CONFIG_NVME_TARGET_TCP_TLS, Christoph recommended the standard kernel pattern:

    "This is a pretty clear candidate for IS_ENABLED()." Christoph Hellwig

  3. Switch on queue state: Rather than using if conditions to check the queue's TLS handshake state, Christoph suggested a more explicit switch statement for better clarity and extensibility:

    "switch on the queue state?" Christoph Hellwig

  4. Formatting nitpicks: Christoph flagged an overly long single line and extra indentation in error-handling code, emphasizing kernel coding style compliance.

Technical Classification

This discussion is about a new feature — TLS 1.3 KeyUpdate support for NVMe-TCP — rather than a protocol change or bug fix. The feature enables seamless key rotation during active NVMe-TCP connections, preventing I/O disruption when sequence numbers approach overflow or after significant encrypted data transfer. The shared net/handshake infrastructure also benefits NFS over TLS deployments via SunRPC.

Conclusions and Open Items

The thread this week concluded with Christoph Hellwig's structural review comments. Key open items for the next revision include:

  • Factoring TLS record type handling into a dedicated helper function in the NVMe host driver (Patch 4/5).
  • Replacing #ifdef guards with IS_ENABLED() and relying on compiler dead-code elimination in the NVMe target driver (Patch 5/5).
  • Using a switch statement for queue state evaluation instead of if chains.
  • Addressing Hannes Reinecke's prior security concern that unhandled TLS records (e.g., Alerts) must properly trigger connection resets.

The series remains under active review, with the NVMe and TLS subsystem maintainers providing detailed feedback to harden both functionality and code quality before merge consideration.
