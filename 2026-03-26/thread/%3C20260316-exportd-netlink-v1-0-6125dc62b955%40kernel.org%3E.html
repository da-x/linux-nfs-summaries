Netlink upcall review: dump continuation bug, YAML policy masks, and dead code cleanup

Summary

Netlink Upcalls for mountd/exportd — Review Continues on Dump Bugs and Protocol Design

Classification

This discussion is part of an ongoing new feature / protocol interface change effort to replace /proc-based cache upcalls with generic netlink interfaces in the NFS server (nfsd) and SunRPC subsystem. The three messages this week focus on detailed code review of patches 09/14 and 10/14 from Jeff Layton's v1 series, identifying a potential infinite-loop bug and several protocol design concerns.

Context

Last week (ending 2026-03-19), Chuck Lever initiated a thorough review of the 14-patch v1 series, raising concerns about TOCTOU races in cache snapshotting and spurious notifications. On March 25, Jeff Layton submitted v2 of the series, addressing those concerns including proper netlink dump continuation support. However, Chuck Lever's review messages this week were still referencing the v1 patches against his nfsd-testing branch, and Jeff Layton's responses on March 23 confirmed he was working on incorporating the feedback.

Key Technical Arguments This Week

1. Infinite Retry Bug in GID Cache Dump Handler

On March 20, Chuck Lever identified a critical bug in Patch 09/14 (the auth.unix.gid cache netlink upcall):

"sunrpc_nl_unix_gid_get_reqs_dumpit() packs its reply entries into a single netlink message. The default SKB size is ~8 KiB, and each entry encodes to ~24 bytes, so the buffer fills at roughly 340 entries. When nla_put fails, the function returns -ENOBUFS but never sets cb->args[0] = 1; causing the netlink subsystem to retry indefinitely. A big NFS server can easily exceed 340 pending GID cache entries." — Chuck Lever

He proposed implementing proper netlink dump continuation:

"Should we implement proper netlink dump continuation: snapshot once then emit entries across multiple dumpit calls using a cursor in cb->args?" — Chuck Lever

This is a significant reliability concern for production NFS servers with large GID caches. The v2 series (submitted March 25) addressed this by implementing proper dump continuation support in all downcalls, as noted in the v2 cover letter.

2. Dead Code and Deferred Attribute Sets

In his review of Patch 10/14 (the svc_export netlink spec), Chuck Lever noted that he was able to apply only through this patch cleanly to nfsd-testing:

"This is the last patch in this series that applied cleanly to the current nfsd-testing branch, so I'm stopping with this one." — Chuck Lever

He flagged two pieces of dead code introduced in this patch:

"The svc-export-req attribute set isn't used in this patch; perhaps its introduction should be deferred to a patch where it is used. NFSD_CMD_CACHE_NOTIFY looks like the same: dead code for now." — Chuck Lever

Jeff Layton agreed on March 23:

"Ok. I'll see about moving those bits." — Jeff Layton

3. Raw Hex Masks in NLA Policy Definitions

Chuck Lever raised a maintainability concern about the netlink attribute policy masks:

"0x3ffff and 0x7 in the NLA policy masks correspond to NFSEXP_ALLFLAGS and NFSEXP_XPRTSEC_ALL from include/uapi/linux/nfsd/export.h, but the policy uses raw hex. Adding a new export flag requires updating three independent locations with no compile-time check. Using the named constants directly in the policy would make the link more explicit." — Chuck Lever

Jeff Layton explained that these values are auto-generated by the ynl (Yet Another Netlink) code generation tool from the YAML specification:

"These are generated by ynl from the provided flags in the spec. I'm not sure there is much we can do here. ynl just has no idea that those constants exist. All it cares about is filtering out flags that it doesn't understand." — Jeff Layton

He acknowledged the concern remains valid:

"Ease of adding new flags is a valid concern though. That's one of the main reasons for doing this. I'll think about this some more." — Jeff Layton

This tension between code generation automation and maintainability is a recurring theme in netlink protocol development.

4. Request for Netlink Protocol Expert Review

Chuck Lever recommended expanding the reviewer base:

"Recommend you add Jakub to the cc: for the series for closer human inspection of the YAML / netlink protocol aspects." — Chuck Lever

Jeff Layton confirmed he would do so in the next posting:

"I'll do that on the next posting." — Jeff Layton

Evolution and Conclusions

This week's discussion represents the middle phase of a multi-week review process. The key outcomes are:

  1. Bug identified and fixed: The infinite retry bug in the GID cache dump handler was identified by Chuck Lever and subsequently addressed in the v2 series through proper netlink dump continuation support.

  2. Dead code cleanup agreed upon: Both parties agreed that unused attribute sets and commands should be deferred to patches where they are actually used, improving patch clarity.

  3. Policy mask maintainability remains open: The tension between auto-generated code and explicit constant references has no immediate resolution; Jeff Layton indicated he would continue thinking about the problem.

  4. Reviewer expansion planned: Jakub Kicinski (netlink subsystem maintainer) will be added to the CC list for future postings to ensure proper protocol-level scrutiny.

Jeff Layton concluded:

"Thanks for all the review so far! I'm working on addressing your other comments too." — Jeff Layton

The v2 series, submitted March 25, incorporated several of these fixes including proper dump continuation and reduced genlmsg_new sizes for notify requests. The discussion is ongoing as the series awaits broader review from netlink protocol experts.
