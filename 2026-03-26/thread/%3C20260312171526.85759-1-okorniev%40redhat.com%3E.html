NFS: Writeback error-loop fix — partial success, continued investigation

Summary

NFS Writeback Error-Loop Fix: Partial Success, Continued Investigation

Overview

This thread concerns an ongoing bug-fix effort in the NFS client to resolve infinite writeback retry loops triggered by ENOSPC (out-of-space) errors on the server side. Originally introduced last week as an RFC patch by Red Hat's Olga Kornievskaia as reported previously, the discussion this week consists of a self-correction and status update from the author herself.

Background (Brief)

Last week, Kornievskaia identified two distinct failure patterns discovered while running xfstest generic/751, both of which caused the NFS client to enter an infinite loop during writeback when encountering server-side errors. Her proposed fix involved marking requests for synchronous writeback rather than allowing the asynchronous path to retry indefinitely.

This Week's Development: A Partial Retraction

On March 24, Kornievskaia returned to the thread with an important clarification regarding the efficacy of her patch in her follow-up message.

Pattern #1: Not Fixed

The first failure pattern — where writeback I/O experiences ENOSPC on an offset smaller than the file size, leading to repeated unstable writes and commit cycles — is not resolved by the current patch. Kornievskaia admitted:

"The patch doesn't actually fix this pattern. I mistakenly thought it was."

She explained the fundamental obstacle with her approach:

"I continue working on trying to find the solution but it looks like the same approach does not work (ie marking the request in some way so that the next time writeback happens it does so sync doesn't work as each time writeback creates a new request and thus the requests that was marked is not useful)."

The core issue is architectural: because the NFS writeback subsystem creates new requests on each pass, any marking applied to a previous request is lost, rendering the synchronous-writeback strategy ineffective for this pattern.

Pattern #2: Fixed

The second failure pattern — involving an unstable write followed by a short write and then ENOSPC — is successfully addressed by the patch:

"This pattern the patch does fix though."

Technical Significance

This discussion highlights a subtle but critical area of NFS client development: ensuring data integrity and preventing livelock conditions when servers report resource exhaustion. The fact that one of two identified patterns remains unresolved underscores the complexity of the NFS writeback path and its interaction with server-side error reporting.

Kornievskaia's candid self-correction demonstrates rigorous testing practices, and her continued work on the problem suggests a more comprehensive solution is in development. The architectural challenge she identified — request lifecycle management during retry scenarios — may require a deeper redesign of how writeback state is tracked across retries.

Conclusion

As of this week, the RFC patch partially addresses the reported bug, fixing one of two failure patterns while leaving the other unresolved. No other participants have weighed in on the thread. Kornievskaia continues her investigation into a complete solution for Pattern #1, acknowledging that the current approach of marking individual requests is insufficient due to the ephemeral nature of writeback request objects.
