lockd: Fix TEST handling for read-only files; Patch v2 submitted

Summary

lockd: Fix TEST Handling for Read-Only Files; Patch v2 Submitted

Classification: Bug Fix (NFS Server / lockd Permission Checks)

Bridge from Prior Weeks

This thread continues the resolution of a regression introduced by commit 4cc9b9f2bf4d ("nfsd: refine and rename NFSD_MAY_LOCK"), which caused NFS clients to receive -ENOLCK ("No locks available") when querying lock status on read-only files (e.g., ISO images served via NFSv3). The issue was originally reported by Tj in the context of Debian openQA infrastructure, where QEMU failed to acquire "consistent read" locks on NFS-mounted disk images.

In prior weeks, Neil Brown identified that the root cause was not a broad semantic error regarding exclusive locks, but a specific bug: lockd was treating F_GETLK (a lock query) identically to F_SETLK (lock acquisition), incorrectly requiring write access for read-only lock queries. Jeff Layton endorsed this analysis, noting, "We definitely allow F_GETLK requests on local files when the task doesn't have write access to the file... Your fix seems sensible to me."

This Week's Activity: Patch Submission and Review

This week saw the formal submission of Neil Brown's fix, followed by review from Jeff Layton and Chuck Lever, and a discussion regarding stable kernel backporting strategy. The week concluded with the submission of Patch v2, incorporating feedback on the Fixes: tag and commit message clarity.

Patch Submission and Initial Review

Neil Brown submitted the initial patch on March 24, modifying fs/lockd/ to distinguish between lock testing and lock acquisition:

"The F_GETLK fcntl can work with either read access or write access or both. It can query F_RDLCK and F_WRLCK locks in either case. However lockd currently treats F_GETLK similar to F_SETLK in that read access is required to query an F_RDLCK lock and write access is required to query a F_WRLCK lock."

The patch introduces O_RDWR as a mode for nlm_do_fopen(), allowing it to succeed if either a read-only or write-only file descriptor can be opened. This mode is used specifically for TEST requests, while other requests retain their previous behavior.

Jeff Layton reviewed the patch positively:

"Patch looks good though."

Reviewed-by: Jeff Layton jlayton@kernel.org

Layton did note a minor comment regarding the documentation of the O_RDWR mode:

"Meaning either... ?"

Backporting Strategy Discussion

Chuck Lever asked about backporting scope:

"Hi Neil, which kernels should this fix apply to?"

Neil Brown clarified that the bug has been present since early git history, but was hidden by a previous bug in nfsd_permission() that ignored access requests for lock operations. The commit 4cc9b9f2bf4d fixed that masking bug, thereby exposing the original lockd defect:

"The Fixes: tag is actually wrong. This bug has been present forever. However a different bug that Commit: 4cc9b9f2bf4d ("nfsd: refine and rename NFSD_MAY_LOCK") fixed was hiding the bug."

Chuck Lever suggested using the Fixes: tag to point to the commit that introduced the issue (i.e., "since forever") and using a stable Cc comment to control backport depth:

"IIUC, we want Fixes: to point to the commit that introduced the issue (Fixes: since forever) and then use a "# v6.13+" comment on the Cc: stable to control how far back to backport it."

Neil Brown countered that pointing to 4cc9b9f2bf4d in the Fixes: tag, despite it not introducing the bug but only exposing it, would better serve automation tools:

"What you suggest is correct in a pure sense (and I like that) but as Ben points out, it will miss older kernels that have backported 4cc9b9f2bf4d. We know which kernel.org kernels that includes, but not what other organisations might maintain for their own purposes. So I think we meet the needs of automation best by saying: Fixes: 4cc9b9f2bf4d even though that didn't introduce the bug but only expose the bug."

(Ben Hutchings participated in this discussion, though his specific remarks were not included in the provided context.)

Patch v2 Submission

Neil Brown submitted Patch v2 on March 26, incorporating the agreed-upon Fixes: tag and expanding the commit message to clarify the historical context:

"This behaviour of lockd - requesting O_WRONLY access to TEST for exclusive locks - has been present at least since git history began. However it was hidden until recently because knfsd ignored the access requested by lockd and required only READ access for all locking requests... The commit mentioned in Fixes: below changed nfsd_permission() to NOT override the access request for LOCK requests and this exposed the bug that we are now fixing."

The patch also includes a note about an unrelated issue:

"Note that there is another issue that this patch does not address. The flock(.., LOCK_EX) call is permitted on a read-only file descriptor... nfsd will see this as though it were fcntl( F_SETLK (F_WRLCK)) and will now require write access, which it might not be able to get. It is not clear if this is a problem in practice, or what the best solution might be. So no attempt is made to address it."

Key Technical Arguments

  1. POSIX Compliance for F_GETLK: The core argument is that F_GETLK (lock testing) should not require write access, as POSIX permits querying lock status with read-only file descriptors. Local filesystems already behave this way, and NFS should match.

  2. Historical Bug Exposure: The bug in lockd existed since early git history but was masked by a separate bug in nfsd_permission() that downgraded all lock access requests to read-only. Commit 4cc9b9f2bf4d fixed the masking bug, inadvertently exposing the original lockd defect.

  3. Backporting Strategy: The discussion concluded that using Fixes: 4cc9b9f2bf4d in the patch metadata, despite it not introducing the bug, is the pragmatic choice to ensure stable kernel automation tools correctly identify affected kernels.

Final Conclusions

  • Bug confirmed and fixed: The regression is a specific bug in lockd's handling of F_GETLK requests, which incorrectly required write access for lock queries on read-only files.
  • Patch v2 submitted: Neil Brown's fix has been reviewed positively by Jeff Layton and accepted in principle by Chuck Lever. The patch distinguishes between lock testing (which accepts either read or write access) and lock acquisition (which retains its previous permission requirements).
  • Backporting plan: The patch will be backported to kernels v6.13 and later, with the Fixes: tag pointing to 4cc9b9f2bf4d to ensure stable automation tools correctly identify affected kernels.
  • Outstanding issue: A separate issue regarding flock(LOCK_EX) on read-only file descriptors was noted but not addressed in this patch, as its practical impact and optimal solution remain unclear.
