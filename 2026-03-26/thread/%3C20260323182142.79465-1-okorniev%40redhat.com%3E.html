nfsdctl: Better error handling when starting threads without listeners

Summary

NFS Server Administration: Improving nfsdctl Error Handling for Thread Management

This week, a focused discussion took place around a user-space bug fix in the NFS server administration tooling. Olga Kornievskaia submitted a patch to improve the error messaging and robustness of nfsdctl, the control utility for the kernel NFS daemon (nfsd). While this is not an NFS client change, it directly impacts server administrators who configure the NFS service that clients depend upon.

The Problem: Cryptic Errors When Starting Threads Without Listeners

The patch addresses a usability issue in nfsdctl. Previously, if an administrator attempted to start NFS server threads via the thread command before any network listeners had been added, the tool would fail with a generic and unhelpful EIO error. Olga noted:

"When a thread command is executed and yet no listeners have been added prior to it, instead of failing with EIO error print an informative error."

Additionally, the patch ensures that the thread 0 command (used to stop threads) does not error out regardless of whether listeners are present.

Technical Review: Implementation Details

Jeff Layton reviewed the patch and provided a quick "Ack on the basic idea," but suggested a code structure improvement. Olga's initial implementation added an output parameter to the existing print_listeners() function to allow it to either print or count listeners. Jeff proposed a cleaner separation of concerns:

"Maybe instead of adding the 'output' parameter, you could just add a count_listeners() function?"

Olga responded that she had opted for reusing the function because she assumed all the validation checks performed by print_listener() would also be necessary when counting listeners. She asked for clarification:

"If you think it's sufficient to just check if sock->name is non-empty and active and do no further checking, I can."

Jeff clarified the semantics of the listener tracking in nfsdctl, explaining that the "active" flag is primarily used on the set side (when adding/removing listeners). For read operations, any fetched listener is considered active. He provided a simplified approach:

"If you fetch_current_listeners() first, then I think you can just check that nfsd_socket_count is non-zero."

Conclusion

This thread represents a straightforward bug fix and usability improvement for NFS server administration tools. The discussion was brief and constructive, with Jeff Layton providing guidance on simplifying the implementation by leveraging existing internal state (nfsd_socket_count) rather than duplicating validation logic. The patch aims to provide administrators with clearer feedback when misconfiguring the NFS server startup sequence, preventing confusion caused by generic EIO errors.
