Support for Multiple Block Devices in pNFS Block-Style Layouts

Summary

Overview

This week, Christoph Hellwig submitted a seven-patch series titled "support multiple block devices per file system for block-style layouts" to extend the NFS server's (nfsd) ability to export multiple block devices via pNFS block-style layouts. The primary motivation is to enable support for the XFS Real-Time (RT) device, allowing clients to access RT extents directly through pNFS.

The series refactors the exportfs interface to split layout-based block device operations into a separate structure (exportfs_block_ops) and updates nfsd to handle multiple device IDs and indices. The final patch implements this support in XFS, enabling layout grants on the RT device.

Key Technical Arguments and Bug Fixes

The series faced rigorous review from Chuck Lever, who identified three significant issues: a potential NULL pointer dereference, a critical fencing logic error, and a timestamp regression.

1. NULL Pointer Dereference in Layout Setup

Chuck Lever pointed out that the refactoring in PATCH 1/7 introduced a potential crash for non-XFS filesystems. He noted:

"block_ops itself is NULL for any filesystem that does not provide block layout support (everything other than XFS today). When an admin exports such a filesystem with pNFS enabled... svc_export_parse() calls nfsd4_setup_layout_type(), and bops->get_uuid dereferences a NULL pointer."

He suggested adding a null check: if (bops && bops->get_uuid && ...). Christoph Hellwig acknowledged the issue in his response on March 26, stating:

"Yes, I'll fix it up." Response

2. Critical Fencing Logic Error

The most significant technical debate centered on PATCH 5/7, which adds support for GETDEVICEINFO for multiple devices. Chuck Lever identified a severe flaw in the fence client path (nfsd4_scsi_fence_client).

He explained that when a layout is granted on the RT device (device index 1), Persistent Reservation (PR) registration occurs on the RT block device. However, the fencing code incorrectly targets the data device:

"This always gets the data device. For an RT inode whose layout was granted with dev_idx=1, PR registration happened on the RT bdev... but the preempt here fires against the data bdev."

Chuck detailed a concrete path to a kernel oops or security vulnerability:

  1. An XFS filesystem has a SATA data device (no pr_ops) and an NVMe RT device (with pr_ops).
  2. The server enables LAYOUT_SCSI because the RT device supports it.
  3. A client accesses an RT inode, registering PR on the RT device.
  4. Upon recall failure, nfsd4_scsi_fence_client attempts to fence the data device.
  5. Since the data device lacks pr_ops, this results in a NULL pointer dereference (kernel oops).

Even if both devices support PR, Chuck noted that fencing the wrong device leaves the RT device unfenced, compromising data integrity. He argued that fixing this requires threading the device index through to the fence path:

"The difficulty is that fence_client receives a nfs4_layout_stateid and nfsd_file, neither of which carries the dev_idx that was encoded in the device ID at layout grant time... So the fix isn't just a one-liner — it requires threading the device index (or the bdev) through to the fence path."

Christoph Hellwig disagreed with the scope of the fix, arguing that fencing should be broader:

"This is bollocks. A fence happens when the client fails to respond, so we need to fence access to all devices for it. Which means we just need to track which devices it got access to. I'll look into it." Response

This indicates a planned redesign of the fencing mechanism to track all accessed devices per client rather than just fixing the index for the current layout.

3. Mtime Regression in LAYOUTCOMMIT

In PATCH 2/7, Christoph removed struct iattr from the ->commit_blocks callback, passing only the new size. Chuck Lever identified that this broke the handling of loca_time_modify in LAYOUTCOMMIT:

"After this change is applied, nfsd4_block_commit_blocks continues to compute lcp->lc_mtime (honoring UTIME_NOW etc.) but never passes it to the underlying filesystem... This change introduces a regression against RFC 8881 Section 18.42 (LAYOUTCOMMIT's loca_time_modify is ignored)."

Christoph clarified that this behavior was not new to the patch but highlighted the need for a separate fix:

"That's not new in this patch. For the is_mgtime() case, which applies to XFS, setattr_copy always sets mtime to the current time when ATTR_MTIME is passed. We'd need to move ATTR_MTIME_SET to set a specific time." Response

Conclusion

The discussion highlights the complexity of extending pNFS block layouts to multi-device filesystems like XFS with RT devices. While the series provides a clean architectural foundation for multiple device exports, it exposed critical edge cases in error handling (fencing) and interface cleanup (mtimes). Christoph Hellwig has agreed to address the NULL pointer dereference immediately and is investigating a broader solution for the fencing logic that tracks all accessed devices per client. The mtime issue remains a known regression requiring a follow-up fix using ATTR_MTIME_SET.
