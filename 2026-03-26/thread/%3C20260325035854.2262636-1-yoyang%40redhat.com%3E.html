generic/551: Debate over OOM mitigation strategy for NFS on swapless VMs

Summary

Overview

This thread concerns a proposed patch to the LTP fstests suite — specifically test generic/551 — aimed at preventing out-of-memory (OOM) kills when running NFS workloads on virtual machines without swap memory. The discussion centers on whether the fix should live in the test infrastructure or in the NFS client itself.

The Proposed Change

Scott Mayhew (Red Hat), via Yongcheng Yang, submitted a patch addressing a recurring issue: the OOM-killer frequently terminates aio-dio-write-verify when generic/551 runs on NFS filesystems on AWS virtual machines. Since AWS VMs typically lack swap partitions, the patch proposes detecting this condition and limiting the test to use only 90% of available memory when generating write operations.

Christoph Hellwig's Objection

Christoph Hellwig pushed back against the approach, arguing that adjusting the test is a band-aid rather than a root-cause fix:

"I don't think this is a good idea. The proper fix is reduce whatever crazy large memory allocations this workloads causes in NFS."

He suspected the underlying issue lay in how the NFS client handles large memory allocations — possibly page lists or similar structures — and suggested that breaking these into smaller chunks or using potentially-failing allocation flags to allow dynamic adjustment would be a more appropriate solution. This positions the discussion as fundamentally about NFS client memory management rather than test harness tuning.

Darrick J. Wong's Perspective

Darrick J. Wong offered a counterpoint from his experience running fstests on XFS:

"I run fstests on XFS every night on a fleets of VMs with no swap and never hit OOM."

His comment implies that the OOM behavior may be specific to NFS client memory allocation patterns rather than an inherent problem with the test or the absence of swap. He also noted a separate operational concern — CrowdStrike endpoint security software had recently been mandated by IT, casting uncertainty on the validity of current test results.

Classification and Status

  • Type: Bug fix / infrastructure improvement (fstests)
  • NFS relevance: High — the discussion highlights potential inefficiencies in NFS client memory allocation during large asynchronous I/O workloads
  • Status: The patch has not been accepted. Christoph Hellwig's critique suggests the maintainers prefer an upstream NFS client-side fix rather than a test-level workaround. No resolution was reached this week.

Key Takeaway for NFS Client Development

The thread underscores that the NFS client may be performing excessively large contiguous memory allocations during aio-dio-write operations, which become problematic on memory-constrained systems without swap. Hellwig's suggestion to use smaller chunks and potentially-failing allocations points toward a desirable direction for future NFS client hardening — making the client more resilient to memory pressure rather than relying on test infrastructure to compensate.
