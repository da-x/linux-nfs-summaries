Benchmarking nfsd IOModes: DONTCACHE_LAZY Proposal and Testing Critique

This week, Jeff Layton published a detailed benchmarking analysis of the new NFS server (nfsd) input/output modes (iomodes), highlighting significant performance issues with the existing RWF_DONTCACHE implementation for streaming write workloads. In response, he proposed an experimental optimization called DONTCACHE_LAZY. The discussion attracted commentary from Chuck Lever and Mike Snitzer, who questioned both the AI-assisted analysis and the validity of the benchmarking methodology relative to high-performance server environments.

Key Technical Arguments

Performance Collapse with RWF_DONTCACHE

Jeff Layton reported that RWF_DONTCACHE performs "absolutely terrible" for streaming write workloads. The core issue identified is severe serialization under concurrent writers:

"IOCB_DONTCACHE flushes all dirty pages on every write via filemap_flush_range() with nr_to_write=LONG_MAX. Under concurrent writers, this creates severe serialization: every writer contends on the writeback submission path, leading to catastrophic throughput collapse (~1 GB/s vs ~10 GB/s for buffered) and multi-second tail latency." Jeff Layton

Proposal: DONTCACHE_LAZY

To address this, Layton introduced an experimental patch adding IOCB_DONTCACHE_LAZY (and the user-visible RWF_DONTCACHE_LAZY). This mode employs two mechanisms to mitigate contention while maintaining dropbehind semantics:

  1. Skip-if-busy: Checks if writeback is already in progress (mapping_tagged(PAGECACHE_TAG_WRITEBACK)). If so, the flush is skipped entirely.
  2. Proportional cap: Caps nr_to_write to the number of pages just written, preventing full-file flushes that starve concurrent readers.

Layton noted that while this experimental mode outperforms others in his tests, the long-term goal is likely to merge these optimizations into the standard DONTCACHE mode rather than maintaining a separate iomode indefinitely:

"I doubt we'll want a new iomode long-term. What we'll probably want to do is modify DONTCACHE to work like DONTCACHE_LAZY." Jeff Layton

Critique of AI Analysis and Splice Reads

Chuck Lever questioned an assertion in the accompanying AI-generated analysis (by "Claude") that suggested disabling splice reads was beneficial. Lever stated:

"My own benchmarking in that area has shown that splice read is always a win over not using splice." Chuck Lever

Layton quickly corrected this, admitting it was an error in the AI's writeup:

"Good catch. That turns out to be a mistake in Claude's writeup... I (and it) have no idea why it would recommend disabling them, when the testing all left them enabled for buffered reads." Jeff Layton

Mike Snitzer clarified that the confusion likely stemmed from the mutual exclusion between splice_read and both NFSD_IO_DONTCACHE and NFSD_IO_DIRECT, meaning splice reads are implicitly disabled when testing these modes.

Critique of Benchmarking Methodology

Mike Snitzer raised significant concerns about whether Layton's tests were sufficient to expose the Memory Management (MM) bottlenecks that differentiate buffered IO from O_DIRECT in high-performance scenarios. He contrasted Layton's results with Jon Flynn's earlier testing, which achieved 72 GB/s using RDMA and multiple NVMe drives:

"Your bandwidth for 1MB sequential IO of 793 MB/s for O_DIRECT and 4,952 MB/s for buffered and dontcache is considerably less than the 72 GB/s offered in Jon's testbed. Your testing isn't exposing the bottlenecks (contention) of the MM subsystem for buffered IO... not yet put my finger on why that is." Mike Snitzer

Snitzer argued that because the tests did not saturate the backend storage or trigger severe MM contention, the comparison with O_DIRECT was not fully representative of high-end server capabilities. However, he conceded on the core issue:

"Putting that aside, yes DONTCACHE as-is really isn't helpful.. your lazy variant seems much more useful." Mike Snitzer

Evolution and Conclusions

The discussion evolved from a performance report into a critique of both the benchmarking scale and the reliability of AI-assisted analysis in kernel development.

  1. Bug Fix/Optimization Focus: The thread confirms that RWF_DONTCACHE has serious scalability issues for concurrent streaming writes due to aggressive flushing behavior.
  2. Proposed Solution: The DONTCACHE_LAZY approach, which rate-limits writeback and skips flushes when writeback is already active, is viewed as a promising direction. Layton intends to eventually merge these behaviors into the standard DONTCACHE implementation.
  3. Testing Standards: Snitzer's comments highlight the need for benchmarking that can drive enough load to expose MM subsystem bottlenecks, particularly when comparing buffered IO variants against O_DIRECT in high-throughput NFS server environments.

The consensus is that while the current DONTCACHE implementation requires improvement, the lazy variant represents a meaningful step forward for NFS client and server performance in streaming write scenarios.
