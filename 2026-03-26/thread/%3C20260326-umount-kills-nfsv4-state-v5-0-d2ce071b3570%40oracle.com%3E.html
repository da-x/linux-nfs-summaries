NFSD: v5 series for automatic NFSv4 state revocation on unmount via netlink commands

Summary

NFSD: Automatic NFSv4 State Revocation on Unmount — v5 7-Patch Series Submitted

Classification

This is a new feature / infrastructure enhancement targeting the NFS server (nfsd) subsystem. It introduces three new generic netlink commands to enable automatic revocation of NFSv4 client state (opens, locks, delegations, layouts) when filesystems or exports are unmounted or removed. While primarily an nfsd/userspace tooling concern, it has significant implications for NFS server administrators managing shared filesystems and containerized NFS deployments.

Overview

On March 26, Chuck Lever submitted the fifth version of a 7-patch series titled "Automatic NFSv4 state revocation on filesystem unmount". The series addresses a long-standing operational problem: when an NFS server exports a filesystem and clients hold NFSv4 state (opens, locks, delegations), unmounting the underlying filesystem fails with EBUSY.

"When an NFS server exports a filesystem and clients hold NFSv4 state (opens, locks, delegations), unmounting the underlying filesystem fails with EBUSY. The /proc/fs/nfsd/unlock_ip and /proc/fs/nfsd/unlock_fs procfs interfaces handle this, but have no netlink equivalents, and unlock_fs operates at whole-superblock granularity." — Chuck Lever

The series adds three new NFSD netlink commands, each with its own attribute set:

  • NFSD_CMD_UNLOCK_IP: Releases NLM locks held by a client IP address — the netlink equivalent of write_unlock_ip.
  • NFSD_CMD_UNLOCK_FILESYSTEM: Revokes all NFS state on a superblock — the netlink equivalent of write_unlock_fs.
  • NFSD_CMD_UNLOCK_EXPORT: Revokes NFSv4 state acquired through exports of a specific path, regardless of client.

Lever clarified the distinction between the two unlock scopes:

"UNLOCK_FILESYSTEM and UNLOCK_EXPORT serve different intents. UNLOCK_FILESYSTEM means 'unmounting /data, release everything on this superblock.' UNLOCK_EXPORT means 'no clients remain for /data/projectA, release only the state acquired through exports of that path.' Userspace (exportfs -u) sends UNLOCK_EXPORT after removing the last client for a given path, enabling the underlying filesystem to be unmounted." — Chuck Lever

Evolution Across Versions

The cover letter documents significant architectural changes across five versions:

Changes since v4:

"Split single NFSD_CMD_UNLOCK into three separate commands. UNLOCK_EXPORT takes path only, no client attribute to avoid auth_domain naming complexity with use_ipaddr." — Chuck Lever

Changes since v3:

"All VFS changes replaced with new netlink 'unlock' operation." — Chuck Lever

This represents a major pivot: earlier versions attempted to solve the problem through VFS-level mount notification hooks (fs_pin, SRCU unmount notifier chains). The v3 redesign moved all logic into nfsd's netlink interface, decoupling it from VFS internals.

Changes since v2:

"Replace fs_pin with an SRCU umount notifier chain in VFS. Merge the pending COPY cancellation patch. Replace xa_cmpxchg() with xa_insert(). Use cancel_work_sync() instead of flush_workqueue(). Remove rcu_barrier(). Correct misleading claims in kdoc comments and commit messages." — Chuck Lever

Changes since v1:

"Explain why drop_client() is being renamed. Finish implementing revocation on umount. Rename pin_insert_group. Clarified log output and code comments. Hold nfsd_mutex while closing nfsd_files." — Chuck Lever

Key Technical Design Decisions

Path-Only UNLOCK_EXPORT Design

A notable design choice is that UNLOCK_EXPORT takes a path only, without requiring the caller to identify a specific client. Lever explained:

"The path-only design for UNLOCK_EXPORT avoids the auth_domain naming complexity (use_ipaddr vs hostname-based domains) by not requiring the caller to identify a specific client. Since this mechanism is to be used to enable umount, this seemed like a reasonable compromise." — Chuck Lever

This simplifies the userspace interface for exportfs -u, which triggers state revocation after removing the last client for a given path. When multiple clients share an export path, individual unexports do not trigger state revocation; only the final one does.

Tracking svc_export in nfs4_stid

Patch 5/7 adds an sc_export field to struct nfs4_stid, so each stateid records the export under which it was acquired. This enables fine-grained revocation by export path without walking inode dentry aliases at revocation time. Open stateids record the export from current_fh->fh_export; lock stateids and delegations inherit from their parent open stateid; layout stateids inherit from their parent stateid.

Closing Cached File Handles

Patch 7/7 addresses a subtle but critical issue: GC-managed nfsd_file entries for files under an export path may remain in the file cache even after NFSv4 state is revoked, still holding the underlying filesystem busy. The patch adds nfsd_file_close_export(), which walks the nfsd_file hash table and closes GC-eligible entries whose underlying file resides on the same filesystem and is a descendant of the export path.

"False positives -- closing a cached handle that did not originate from the target export -- are harmless; the handle is simply reopened on the next access." — Chuck Lever

Code Refactoring: revoke_one_stid()

Patch 1/7 extracts the per-stateid revocation logic from nfsd4_revoke_states() into two helpers: revoke_ol_stid() for open/lock stateids and revoke_one_stid() as a dispatcher by sc_type. This is preparatory work enabling export-scoped state revocation to reuse the same revocation machinery.

Relationship to Jeff Layton's Netlink Upcall Series

This series complements Jeff Layton's parallel netlink upcall series for mountd/exportd (submitted March 25). Both efforts modernize nfsd's userspace communication by replacing /proc-based interfaces with generic netlink. Layton's series handles identity mapping and export resolution upcalls; Lever's series adds administrative commands for state revocation. Together, they enable a fully netlink-based nfsd management interface suitable for containerized deployments where /proc access may be restricted.

Conclusion

This v5 series represents a mature, well-refined solution to the NFS server unmount-blocking problem. By providing three granularity levels of state revocation (IP, filesystem, export) through a modern netlink interface, it enables administrators and tools like exportfs to cleanly release client-held state before unmounting underlying filesystems. The path-only design for UNLOCK_EXPORT elegantly sidesteps auth_domain naming complexities while serving its intended purpose. With no discussion within this week's window (replies from Jeff Layton began arriving on March 27, outside the reporting period), the series awaits further review.
