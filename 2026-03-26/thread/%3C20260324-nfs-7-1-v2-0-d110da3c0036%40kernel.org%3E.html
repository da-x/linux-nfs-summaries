NFS: Fixes for delegated attribute handling in utimensat and removexattr

Summary

NFS Client Bug Fixes: Delegated Attribute Timestamps

Jeff Layton submitted a v2 patch series this week addressing two distinct bugs related to how the NFS client handles inode change time (ctime) updates when using delegated timestamps. The issues were reported by Olga Kornievskaia and manifest as failures in specific xfstest cases.

Context: Delegated Timestamps

Delegated timestamps allow the NFS client to cache attribute updates (like access and modification times) locally without issuing an RPC for every change, provided it holds a WRITE_ATTRS_DELEG delegation. However, this optimization has edge cases where the server-side ctime must be updated, but the client's local caching logic fails to trigger the necessary synchronization or RPCs.

Patch 1: Fix utimensat() with atime-only updates

The first patch addresses a failure in xfstest generic/221.

"When the client holds a WRITE_ATTRS_DELEG delegation, and a userland process does a utimensat() for only the atime, the ctime is not properly updated. The problem is that the client tries to cache the atime update, but there is no mtime update, so the delegated attribute update never updates the ctime." Jeff Layton

Layton noted that the existing mechanism for delegated timestamps lacks a way to update ctime in response to atime-only changes. The fix forces the client to issue an RPC in this specific scenario, ensuring the server updates both atime and ctime.

In a follow-up message, Layton suggested adding a clarifying comment to the code:

"An atime-only update via an explicit setattr (e.g.: utimensat() and the like) requires updating the ctime as well. Delegated timestamps don't have a mechanism for updating the ctime with a delegated atime-only update, so an RPC must be issued." Jeff Layton

Patch 2: Update ctime after removexattr

The second patch fixes xfstest generic/728, which fails because the inode ctime is not updated after removing an extended attribute.

"The client does a removexattr and then a stat to test the ctime, which doesn't change. The stat() doesn't trigger a GETATTR because of the delegated timestamps, so it relies on the cached ctime, which is wrong." Jeff Layton

The solution mirrors the strategy used for setxattr: adding a trailing GETATTR to the removexattr compound operation. This ensures the client retrieves the fresh ctime from the server immediately after the attribute removal, keeping the local cache consistent.

Conclusion

Both patches are bug fixes targeting regressions introduced by previous optimizations in delegated timestamp handling. The v2 series added proper Fixes: tags to identify the originating commits:

  1. 40f45ab3814f ("NFS: Further fixes to attribute delegation a/mtime changes")
  2. 3e1f02123fba ("NFSv4.2: add client side XDR handling for extended attributes")

The discussion was brief, with Layton primarily refining the code comments for clarity rather than debating technical approaches. These fixes ensure that NFS clients correctly maintain metadata consistency when using delegated timestamps, particularly in scenarios involving explicit atime updates or extended attribute removals.
