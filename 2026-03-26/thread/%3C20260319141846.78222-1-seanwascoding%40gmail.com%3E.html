NFS/SunRPC Debug Cleanup: v4 to Revert Redundant __maybe_unused Workaround

Summary

NFS/SunRPC: Cleanup Redundant Debug Checks and Refactor Macros — v4 Preparations

Overview

This thread continues the discussion around Sean Chang's three-patch series to clean up redundant IS_ENABLED(CONFIG_SUNRPC_DEBUG) guards across SunRPC, nfsd, lockd, and svcrdma, and to refactor NFS error-reporting macros. The series is classified as a code cleanup / maintainability improvement rather than a new feature or runtime bug fix.

Last week (ending 2026-03-19), the v3 series was submitted and received initial review from Andy Shevchenko, who provided Reviewed-by and Tested-by tags after discussing macro refactoring approaches for nfs_errorf versus nfs_invalf. This week's activity (March 20) focused on two additional cleanup opportunities identified by Shevchenko that will be incorporated into the upcoming v4 submission.

Key Developments This Week

1. Reverting a Workaround for __maybe_unused Attributes

Early in the week, Andy Shevchenko raised an important point about a previously merged commit that is now rendered obsolete by Chang's refactoring:

"Shall we also revert the commit ebae102897e7 ("nfsd: Mark variable __maybe_unused to avoid W=1 build break") as it seems related to dprintk() issues?" Andy Shevchenko asked.

Commit ebae102897e7 had introduced __maybe_unused annotations on variables in nfsd to suppress W=1 build warnings when debug code was compiled out. However, Chang's series removes the redundant IS_ENABLED(CONFIG_SUNRPC_DEBUG) guards because the underlying dprintk() macros already handle this internally — meaning those variables are no longer conditionally dead and the workaround is unnecessary.

Sean Chang confirmed the observation:

"That's a great catch. I've verified that with the new dprintk() refactoring, those __maybe_unused attributes are indeed redundant. I will include a new patch in v4 to remove them and properly credit the cleanup." Sean Chang replied.

This represents a meaningful improvement: not only does v4 clean up the current codebase, but it also enables the reversion of a prior workaround, resulting in cleaner nfsd source code.

2. Addressing Unrelated Sparse Warnings and Trace Header Errors

In his earlier review (last week), Shevchenko had flagged several unrelated issues in nfs/super.c and trace headers (nfstrace.h, nfs4trace.h). This week, Chang acknowledged these items:

"Regarding the Sparse warnings in super.c and the trace header errors, I've noted them down. I'll look into them separately and may submit a follow-up patch to address them later." Sean Chang stated.

These issues are outside the scope of the current series but will be tracked for future cleanup patches.

Final Conclusions

  • The series is accepted with Reviewed-by and Tested-by from Andy Shevchenko.
  • v4 will expand the scope: In addition to the original three patches, Chang will add a fourth patch to revert commit ebae102897e7, removing now-redundant __maybe_unused attributes from nfsd.

Significance for NFS Client Development

While this series does not address runtime bugs or protocol changes, it improves the robustness and maintainability of the NFS debugging infrastructure. By eliminating redundant debug guards and consolidating macro patterns, the codebase becomes easier to audit and less prone to subtle build-time issues — particularly under W=1 configurations. The reversion of ebae102897e7 further demonstrates how targeted refactoring can clean up legacy workarounds, resulting in a more elegant NFS client/server codebase.
