NFSv4 Server Recovery: Resolving Session Reset via server_scope Configuration

Overview

This thread documents a user's journey to achieve high-availability (HA) for NFSv4, specifically focusing on the migration of client locks and sessions between cluster nodes. The discussion highlights a critical configuration requirement for successful state recovery that is not immediately obvious from standard documentation.

Classification: Bug Fix / Configuration Guidance (NFS Server/Client Interaction)

Discussion Evolution

1. Initial Problem: Missing Upcall Pipe

Matthew Schumacher initiated the thread on March 6, describing an HA setup where locks were lost during failover from nodeA to nodeB. Despite using nfsdcld and sharing /var/lib/nfs, the kernel reported:

"NFS: 10.255.255.3: lost 1 locks"

Schumacher observed that nfsdcld failed to open the upcall pipe /var/lib/nfs/rpc_pipefs/nfsd/cld, resulting in a fallback to usermodehelper operations rather than the preferred direct kernel communication.

Jeff Layton responded, noting:

"The kernel failed to recognize the cld upcall for some reason, so it fell back to running the usermodehelper upcall."

2. Intermediate Fix: Kernel Configuration

Schumacher replied that he identified the root cause of the missing pipe:

"I figured out why /var/lib/nfs/rpc_pipefs/nfsd/cld was missing, I had CONFIG_NFSD_LEGACY_CLIENT_TRACKING enabled in the kernel."

After disabling this legacy option, nfsdcld successfully communicated with the kernel, and the grace period ended correctly. However, locks were still lost during failover.

3. The Core Issue: Session Reset and Scope Mismatch

In a follow-up on March 9, Schumacher provided detailed logs showing that while client tracking was working, sessions were being reset upon failover. The client kernel logged:

"nfs41_sequence_process ERROR: -10052 Reset session" "_nfs4_proc_exchange_id: server_scope mismatch detected"

The server-side logs confirmed the session was not found in the hash table:

"__find_in_sessionid_hashtbl: 1773078573:732586373:19:0 session not found"

Schumacher questioned whether sessions and locks should persist across node migrations when using shared storage for nfsdcld state.

4. Resolution: Unified Server Scope

In the final message, Schumacher identified the solution. The server_scope parameter, which defaults to the node's hostname, must be identical across all nodes in the HA cluster. Because each node had a different hostname, the NFSv4 protocol treated them as distinct servers, causing clients to reset their sessions and lose locks.

"It appears my assumption is correct because now I see my locks and sessions maintained when moving from nodeA to nodeB... the issue was this: _nfs4_proc_exchange_id: server_scope mismatch detected. The scope must be the same on all nodes in a cluster and defaults to the node hostname."

Key Technical Takeaways

  1. Kernel Configuration: Ensure CONFIG_NFSD_LEGACY_CLIENT_TRACKING is disabled to allow nfsdcld to use the modern upcall pipe mechanism for efficient client tracking.
  2. Server Scope Consistency: For NFSv4 HA clusters using shared state storage, all nodes must be configured with the same server_scope. This ensures that clients recognize the failover target as the same logical server, preserving sessions and locks without requiring a full session reset.
  3. Debugging Aid: The error _nfs4_proc_exchange_id: server_scope mismatch detected is a definitive indicator of this configuration issue.

Conclusion

The thread concludes with a successful resolution, emphasizing that while nfsdcld handles lock persistence, the NFSv4 protocol's identity verification (via server_scope) must also be aligned across cluster nodes to prevent session resets. This serves as an important reminder for administrators building HA NFSv4 clusters.
