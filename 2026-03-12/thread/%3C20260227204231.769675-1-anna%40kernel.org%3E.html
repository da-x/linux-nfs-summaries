NFS KConfig Typo Fix: Confirmation of Regression and User Impact

Summary

This week, the discussion around Anna Schumaker's patch **[PATCH] NFS: Fix NFS KConfig typos](https://lore.kernel.org/linux-nfs/20260227204231.769675-1-anna@kernel.org/) received a significant user confirmation and Tested-by tag from Dan Williams. This is classified as a bug fix, addressing configuration defaults that regressed NFS boot configurations for users following standard kernel update practices.

Prior Context (Bridged Briefly)

Last week, Anna Schumaker submitted the patch to correct two issues introduced by recent NFS v4.0 Kconfig changes: misleading help text for CONFIG_NFS_V4 and an incorrect default value for CONFIG_NFS_V4_0, which was set to "off" instead of "on". The fix targeted commit 7537db24806f ("NFS: Merge CONFIG_NFS_V4_1 with CONFIG_NFS_V4").

This Week's Activity

Dan Williams provided real-world validation of the regression and the fix. His response highlights the practical impact on users who perform routine kernel builds:

"Can confirm that this commit, 7537db24806f, regressed my long standing NFS boot configuration."

Williams further emphasized the value of the fix in avoiding debugging overhead:

"Can also confirm that had this proposed fix been in the tree before I did my first post v7.0-rc1 build it would have saved me a bisect."

He provided his Tested-by tag, confirming the patch resolves the issue:

"for this patch: Tested-by: Dan Williams dan.j.williams@intel.com"

Key Technical Issue: Stale Configuration State

Williams identified an important caveat for affected users. Those who ran make olddefconfig after v7.0-rc1 with the broken defaults would have their .config files permanently locked into the incorrect state:

"Unfortunately, anyone like me that did a post v7.0-rc1 build with 'make olddefconfig' will not enjoy any relief until they clean out the errant: # CONFIG_NFS_V4_0 is not set ...so that the default can be applied."

This underscores a broader challenge in kernel configuration management: once an incorrect default is baked into a user's .config, simply merging a fix does not automatically restore correct behavior. Users must manually remove the stale entry to allow the new default to take effect.

Conclusion

The patch received strong validation from a real-world user, confirming both the regression and the effectiveness of the fix. The Tested-by tag strengthens the case for merging. However, the discussion also reveals a lingering issue for users who already configured their kernels with the broken defaults—manual intervention is required to restore proper NFS v4.0 support.

"Not sure of any good way to address that problem"

Williams noted the lack of an automated solution for this stale configuration state, leaving it as a known limitation for affected users.
