nfsrahead: Fix udev worker exhaustion and subsequent crash on non-NFS devices

Summary

This thread addresses a critical stability issue in the nfsrahead utility, part of the NFS client ecosystem. The discussion focuses on fixing a race condition during mount detection that led to udev worker exhaustion, followed by the discovery and resolution of a memory corruption bug introduced by the initial fix.

Initial Problem: Race Condition and Udev Exhaustion

Aaron Tomlin submitted a patch to replace the naive polling mechanism in nfsrahead with an event-driven monitor using libmount. The previous implementation relied on fixed 50ms delays, which proved brittle under heavy load or slow boot sequences.

The new approach introduced a "fast-path rejection" for non-NFS devices (those with non-zero major numbers) to prevent udev worker thread exhaustion. As Tomlin explained:

"By instantly exiting with -ENODEV for any device string not beginning with '0:', we safely bypass the monitor for physical drives, preventing the exhaustion of udev worker threads."

Steve Dickson committed this patch quickly, tagging it for nfs-utils-2-8-6-rc4:

"Committed... (tag: nfs-utils-2-8-6-rc4)"

Regression: Crash on Non-NFS Devices

Yi Zhang reported that the fix introduced a new critical bug. During blktests, nfsrahead crashed with an ABRT signal when processing non-NFS block devices (e.g., 8:16). The journal logs revealed a heap corruption error:

"malloc_printerr (libc.so.6 + 0x7fd2c)"

The stack trace indicated the crash occurred in free_device_info() within the cleanup path of main().

Root Cause and Resolution

Aaron Tomlin analyzed the crash and identified the root cause: the fast-path optimization caused an early exit from the function, bypassing the initialization of the device_info struct. Consequently, the cleanup code attempted to free uninitialized stack memory pointers.

Tomlin noted:

"The log points directly to an unintended side effect of the recent fast-path optimisation... this early exit completely bypasses the initialisation of the device_info struct in main()."

He proposed a straightforward fix: explicitly zero-initializing the struct at declaration (struct device_info device = { 0 };). This ensures all internal pointers are NULL, allowing the cleanup path to safely handle early exits without triggering glibc aborts. Tomlin promised to send a follow-up patch for Yi Zhang to test against his blktests environment.

Conclusion

This thread highlights the iterative nature of robust NFS client development. While the initial fix addressed performance and stability concerns regarding udev workers, it inadvertently introduced a memory safety issue. The final conclusion is that a simple initialization fix will resolve the crash, ensuring nfsrahead handles both NFS and non-NFS devices safely.
