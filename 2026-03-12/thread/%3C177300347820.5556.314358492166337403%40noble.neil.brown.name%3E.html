Cachefiles Fixup Patch Applied: VFS Directory Locking Refactoring Continues

Summary

This thread concludes with the application of a fixup patch to Neil Brown's ongoing VFS directory locking refactoring series. The fixup addresses a behavioral regression in the cachefiles subsystem identified by VFS maintainer Christian Brauner during his review of v3 of the 15-patch "Further centralising of directory locking for name ops" series.

Classification: Bug fix (fixup) within a broader VFS refactoring effort — not a new feature or protocol change. The work centralizes directory locking into unified interfaces (start_creating(), start_removing(), start_renaming_dentry(), etc.), laying groundwork for future per-name locking.

Bridge from Prior Activity

Earlier this week (March 6–8), Christian Brauner posted two detailed reviews of the v3 series. In his review of [PATCH 10/15 — cachefiles: change cachefiles_bury_object to use start_renaming_dentry()], Brauner identified that the new code introduced subtle behavioral changes in error handling that could cause permanent cache disabling on transient failures prior summary. Specifically:

"If rep->d_parent != dir after lock_rename this returned 0 in the old code. With your changes the same condition in __start_renaming_dentry returns -EINVAL which means cachefiles_io_error() sets CACHEFILES_DEAD and permanently disables the cache." Review

Brauner also flagged that -ENOMEM from lookup_one() was now routed through cachefiles_io_error(), again triggering permanent cache death:

"In the old code a -ENOMEM return from lookup_one() let the cache stay alive and returned directly. The new code gets sent via cachefiles_io_error() causing again CACHEFILES_DEAD to be set and permanently disabling the cache." Review

Neil Brown submitted a [PATCH] FIXUP on March 8 addressing these concerns, preserving the original error-return behavior and ensuring cachefiles_io_error() is called in exactly the same circumstances as before Fixup.

This Week's Activity: Fixup Applied

On March 9, Christian Brauner confirmed the fixup has been applied to the vfs-7.1.directory branch of the vfs/vfs.git tree:

"Applied to the vfs-7.1.directory branch of the vfs/vfs.git tree. Patches in the vfs-7.1.directory branch should appear in linux-next soon." Application

Brauner also noted that patches in this branch will appear in linux-next shortly, and encouraged contributors to provide Acked-by and Reviewed-by tags even post-application:

"It's encouraged to provide Acked-bys and Reviewed-bys even though the patch has now been applied. If possible patch trailers will be updated." Application

Key Technical Arguments and Evolution

  1. Behavioral regression caught pre-merge: Brauner's review identified that the cachefiles conversion to start_renaming_dentry() altered error handling semantics, turning transient failures (parent mismatch, ENOMEM) into fatal cache-disabling events via cachefiles_io_error().
  2. Rapid fixup cycle: Neil Brown acknowledged the issue within hours and submitted a targeted fixup patch on March 8. Brauner applied it to his tree by March 9 — a swift review-and-fix workflow demonstrating effective maintainer collaboration.
  3. Preservation of original semantics: The fixup ensures that cachefiles_io_error() is called in "exactly the same circumstances as the original" code, maintaining cache reliability for transient errors while still adopting the new VFS locking API.

NFS Client Relevance

This thread does not directly modify NFS client code. However, the cachefiles subsystem can interact with NFS in certain configurations (e.g., FUSE-based caching solutions). The fixup patch is significant because it:

  • Prevents unnecessary permanent cache disabling on transient errors — a reliability improvement for any caching layer that may sit alongside NFS workloads.
  • Demonstrates the importance of careful error-handling semantics when refactoring VFS infrastructure that underpins filesystem interactions.

The broader VFS directory locking centralization is a prerequisite for per-name locking, which will eventually affect how all filesystems — including NFS — interact with VFS name operations.

Final Conclusions

  • Fixup applied: The cachefiles fixup patch has been merged into vfs/vfs.git branch vfs-7.1.directory and will appear in linux-next.
  • Bug fixed pre-merge: Brauner's thorough review caught a behavioral regression before it reached mainline, preserving cache reliability for transient errors.
  • Review process effective: The rapid identification of issues and submission of fixups demonstrates an efficient maintainer-developer workflow.
  • Series continues: The broader 15-patch VFS directory locking series remains under review, with remaining patches (particularly overlayfs changes) still awaiting Brauner's feedback.
