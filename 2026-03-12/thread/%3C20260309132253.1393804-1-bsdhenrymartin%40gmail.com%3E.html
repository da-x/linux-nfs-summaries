NFS: Fix kernel BUG() when mounting NFSv3 with xprtsec=tls

Summary

This week, Henry Martin submitted a targeted bug fix addressing a kernel BUG() crash that occurs when mounting an NFSv3 filesystem with the xprtsec=tls mount option. The issue stems from the NFS client's failure to handle the XPRT_TRANSPORT_TCP_TLS protocol type during mountd transport setup, causing an invalid protocol value to propagate into timeout initialization code.

The Bug: Unhandled TCP_TLS Protocol in Mount Transport Setup

When a user mounts an NFSv3 share with xprtsec=tls, the NFS client upgrades nfs_server.protocol to XPRT_TRANSPORT_TCP_TLS. However, the function nfs_set_mount_transport_protocol() — responsible for configuring the transport protocol used by the mount daemon (mountd) client — does not recognize this new protocol type. As a result, mount_server.protocol can remain in an invalid state.

Martin explained:

"xprtsec=tls upgrades nfs_server.protocol to XPRT_TRANSPORT_TCP_TLS. For NFSv3, nfs_set_mount_transport_protocol() does not handle XPRT_TRANSPORT_TCP_TLS, and mount_server.protocol can remain invalid."

This invalid protocol value is then passed into nfs_init_timeout_values(), which contains a BUG() assertion for unrecognized protocol types — triggering an immediate kernel panic.

The crash trace included in the patch submission shows the failure path clearly:

"kernel BUG at fs/nfs/client.c:512! Oops: invalid opcode: 0000 [#9] SMP KASAN NOPTI"

The call trace confirms the crash originates from nfs_init_timeout_values+0x235/0x27a, invoked through nfs_mount → nfs_request_mount → nfs_try_get_tree → nfs_get_tree.

The Fix: Map TCP_TLS to TCP for mountd Transport

The proposed fix is minimal — a single-line addition in fs/nfs/fs_context.c that treats XPRT_TRANSPORT_TCP_TLS the same as plain TCP or RDMA when configuring the mountd transport. Martin noted:

"Handle XPRT_TRANSPORT_TCP_TLS like TCP/RDMA and map it to TCP for mountd transport setup."

This is a reasonable approach because the mount protocol itself (portmap/mountd) does not support TLS; TLS encryption applies only to the NFS data channel. Therefore, mapping TCP_TLS down to plain TCP for the mountd connection is semantically correct.

The patch includes:

  • Fixes tag: c8407f2e560c ("NFS: Add an "xprtsec=" NFS mount option") — identifying the commit that introduced the regression.
  • Cc: stable@vger.kernel.org — indicating this should be backported to stable kernels.

Context: Part of a Broader TLS Hardening Effort

This patch is closely related to another fix submitted by Henry Martin earlier in the same week (sunrpc: fix TLS connect_worker rpc_clnt lifetime UAF), which addressed a use-after-free bug in the SUNRPC TLS transport layer. Together, these patches represent ongoing hardening of the NFS client's TLS support, which was introduced relatively recently and has been exposed to real-world testing by developers and vendors such as Hammerspace.
