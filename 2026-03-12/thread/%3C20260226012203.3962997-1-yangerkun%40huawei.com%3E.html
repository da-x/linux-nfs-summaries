Reviewed-by: NFS file-lock list UAF fix using nfsi->rwsem

Summary

NFS client: use-after-free in file-lock list traversal gets review and approval

This week at a glance

After sitting as an unreviewed RFC since late February, Yang Erkun's patch to protect NFS file-lock list traversal with nfsi->rwsem finally attracted attention from maintainer Jeff Layton this week. The result is a Reviewed-by for what amounts to a surgical bug fix addressing a long-standing use-after-free (UAF) hazard in the NFS client's delegation and lock-reclaim paths.

Classification

This is a bug fix on the NFS client side, not a new feature or protocol change. It targets locking discipline during per-inode file-lock list walks, carrying a Fixes: tag pointing to commit c69899a17ca4 ("NFSv4: Update of VFS byte range lock must be atomic with the stateid update").

Background (brief bridge from prior week)

As summarized last month, Li Lingfeng identified a UAF bug: traversing the file-lock list requires holding flc_lock, but functions like nfs_delegation_claim_locks and nfs4_reclaim_locks must release it to call blocking RPC code. The reclaim path already switched to nfsi->rwsem; Erkun's patch extends that discipline to the delegation-claim path and relocates locks_lock_inode_wait out of asynchronous RPC callbacks (nfs4_lock_done, nfs4_locku_done) into the synchronous caller _nfs4_proc_setlk.

Erkun followed up with a gentle nudge early this week:

"ping again" [id://ed0b2bc6-5e43-4b20-8883-74c0c0d3362a@huawei.com]

This week's evolution

Jeff Layton weighed in on March 9 with a straightforward endorsement:

"Nice work!"
"Reviewed-by: Jeff Layton jlayton@kernel.org" [id://dcf0b02002857a6be502e372ebb3e175412d7184.camel@kernel.org]

Layton then added an interesting methodological aside, noting he had also run the commit log through Claude for a sanity check:

"FWIW, I did point Claude at this too and it found no regressions." [id://c5c31ffa3557e0aab5c1a75d6ff69cb7c7806dc1.camel@kernel.org]

Claude's summary, as relayed by Layton, distilled the fix neatly:

"This patch fixes a use-after-free bug in NFS file lock list traversal. The core problem was that nfs_delegation_claim_locks released flctx->flc_lock during iteration (to call nfs4_lock_delegation_recall, which can block on RPCs) and relied on so_delegreturn_mutex for protection — but that mutex is per-state-owner, not per-inode, so multiple state owners on the same inode could race."
"The fix uses nfsi->rwsem (per-inode) for proper protection, matching the existing pattern in nfs4_reclaim_locks. It also moves locks_lock_inode_wait out of RPC callbacks (nfs4_lock_done, nfs4_locku_done) into the synchronous caller (_nfs4_proc_setlk) so it can be called under nfsi->rwsem."

Erkun acknowledged the review on March 10:

"Hi Jeff, thanks a lot for your review!" [id://3d7e7fa3-242f-4350-8c7f-0ea81199e16c@huawei.com]

Key technical arguments

The patch's correctness rests on two pillars:

  1. Per-inode protection. The old guard (so_delegreturn_mutex) is per-state-owner, but an inode can have multiple nfs4_state objects. Switching to nfsi->rwsem aligns with the already-established pattern in nfs4_reclaim_locks.

  2. No regression of the original c69899a17ca4 fix. Erkun argued that moving locks_lock_inode_wait out of the async callbacks does not reintroduce the atomicity bug, because later commits (notably 0460253913e5) drain slots before reclaim, and the delegation-claim path sets the stateid only once via nfs4_lock_delegation_recall.

Final conclusions

With Jeff Layton's Reviewed-by in hand, this patch is now well-positioned for inclusion. The discussion was brief but decisive — no objections were raised, and an independent AI-assisted review corroborated the absence of regressions. This represents a clean resolution to a bug that has been on the list's radar since at least April 2025.
