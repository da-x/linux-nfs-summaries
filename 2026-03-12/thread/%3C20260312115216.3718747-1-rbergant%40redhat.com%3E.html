NFSv3 client: fix oops on concurrent dir/file creation race

Summary

This week saw a focused bug fix submission from Red Hat developer Roberto Bergantinos Corpas addressing a kernel oops in the NFS client when handling concurrent directory and file creation scenarios. The patch, marked as a RESEND, targets a race condition in nfs3_proc_create that can lead to a negative dentry being passed to do_dentry_open, resulting in a crash.

Technical Argument and Bug Description

The issue arises in the NFSv3 client's atomic open path. When nfs3_do_create calls into nfs_add_or_obtain and subsequently d_splice_alias, it may encounter an existing alias that is a directory dentry. As Roberto explains:

"If we found an alias through nfs3_do_create/nfs_add_or_obtain /d_splice_alias which happens to be a dir dentry, we don't return any error, and simply forget about this alias, but the original dentry we were adding and passed as parameter remains negative."

This leaves the original dentry in a negative state. The problem manifests later when nfs_atomic_open_v23 calls finish_open, which attempts to use this negative dentry with do_dentry_open:

"This later causes an oops on nfs_atomic_open_v23/finish_open since we supply a negative dentry to do_dentry_open."

Reproduction Context

The bug was discovered during stress testing with lustre-racer, a tool that simulates concurrent filesystem operations:

"This has been observed running lustre-racer, where dirs and files are created/removed concurrently with the same name and O_EXCL is not used to open files (frequent file redirection)."

This highlights a real-world scenario where rapid creation and deletion of directories and files with identical names—without using O_EXCL—can trigger the race condition.

The Fix

The patch adds an explicit check for directory dentries after d_splice_alias returns, ensuring that the NFS client does not attempt file operations on a directory inode:

"While d_splice_alias typically returns a directory alias or NULL, we explicitly check d_is_dir() to ensure that we don't attempt to perform file operations (like finish_open) on a directory inode, which triggers the observed oops."

The fix returns EISDIR when such a condition is detected, providing a proper error code rather than allowing the kernel to crash. The patch traces its origin to commit 7c6c5249f061, which introduced atomic open support for NFSv3 to handle O_TRUNC correctly.

Review and Acceptance

The patch received two review acknowledgments from Red Hat colleagues:

  • Reviewed-by: Olga Kornievskaia okorniev@redhat.com
  • Reviewed-by: Scott Mayhew smayhew@redhat.com

This indicates strong internal consensus on the correctness of the fix within the NFS development team at Red Hat.

Conclusion

This is a bug fix addressing a kernel oops in the NFSv3 client's atomic open path. The patch is minimal (6 insertions, 1 deletion) and targets a specific race condition that occurs under high-concurrency workloads involving mixed directory and file operations. With reviews from key NFS maintainers at Red Hat, this fix appears ready for integration into the mainline kernel.
