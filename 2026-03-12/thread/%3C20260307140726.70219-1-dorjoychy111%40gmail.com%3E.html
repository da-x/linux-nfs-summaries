OPENAT2_REGULAR flag support: Semantics of "Regular File" Debated

Summary

Thread Subject: [PATCH v5 0/4] OPENAT2_REGULAR flag support for openat2 Date Range: 2026-03-07 to 2026-03-12

This week, Dorjoy Chowdhury submitted a v5 patch series introducing the OPENAT2_REGULAR flag for the openat2() system call. This new feature aims to enhance security by allowing programs to open only regular files (S_IFREG), returning -EFTYPE if the target is a device node, FIFO, or other non-regular file type. The patch series includes updates to multiple filesystems, including NFS, Ceph, GFS2, and SMB, as well as kselftests and architecture-specific header conversions for SPARC and MIPS.

Key Technical Arguments

The discussion quickly evolved from implementation details to a deep semantic debate about what constitutes a "regular file" in the Linux kernel, particularly concerning virtual filesystems like procfs and sysfs.

  • Security Motivation: Dorjoy Chowdhury explained that the flag is intended to help secure programs avoid being "tricked into opening device nodes with special semantics while thinking they operate on regular files."
  • Defining "Regular": Andy Lutomirski challenged the definition, asking: "What about procfs? What about sysfs? What about /proc/self/fd/17 where that fd is a memfd?" He questioned whether the flag should protect against blocking opens, strange side effects, or privilege escalation.
  • VFS Consistency: Jeff Layton argued for consistency with existing VFS behavior, noting: "Since we allow programs to open a directory under /proc or /sys using O_DIRECTORY, I don't think we should do anything different here. To the VFS, all of the examples you gave above are S_IFREG 'regular files', even if they are backed by something quite irregular."
  • Procfs/Sysfs Concerns: Andy Lutomirski pressed on whether magical /proc and /sys files should be openable. Florian Weimer highlighted specific risks, stating: "It seems reading from /proc/kmsg is destructive... It's more like a character device." He suggested this might be sufficient reason for blocking access via the new flag.
  • Semantic Skepticism: Christian Brauner expressed doubt about the utility of a strict "regular file" API in Linux, arguing: "In general, Linux has been so loosey-goosey with 'regular file' for such a long-time that making OPENAT2_REGULAR come up with some strict definition... is just doomed to fail." He further opined that APIs with immediate irreversible side-effects on open are bugs and suggested LSM/BPF hooks as a better alternative for scoping opens.

NFS Client Impact

The patch series includes modifications to fs/nfs/dir.c to integrate the OPENAT2_REGULAR check into the NFS client's open path. Dorjoy Chowdhury confirmed testing with NFS (loopback), ensuring that regular files are opened successfully while non-regular files return -EFTYPE. While no specific NFS bugs were fixed, the change adds a new layer of validation for NFS opens when this flag is used.

Evolution and Conclusion

The discussion did not reach a final conclusion within this week's window. The thread ended with Andy Lutomirski asking Aleksa Sarai for clarification on "checks" mentioned in a previous message (whose body was not fully retrievable).

"Can you give a brief decription or a link to what these checks are and what problem they solve?" Andy Lutomirski

The core tension remains between the security benefit of preventing accidental opens of special files and the practical reality of Linux's loose VFS definitions. The patch series remains under active review with significant debate about its semantics and utility.
