Removal of kthread_exit() Alias and Debate on Task Exit Exports

Summary

Summary: Cleanup of Kernel Thread Exit Paths

This week, a significant discussion unfolded regarding the cleanup of kernel thread exit paths, specifically the removal of the kthread_exit() function. This change directly impacts the NFS infrastructure, as the patch modifies include/linux/sunrpc/svc.h, ensuring that RPC tasks (used by both NFS client and server) utilize a consistent and safe exit mechanism.

The Patch: Removing a Dangerous Alias

Christian Brauner initiated the thread with a patch to completely remove kthread_exit(). This function had previously been folded into do_exit() to fix a "nasty UAF bug" (use-after-free), but was left as an alias for compatibility. Brauner argued that maintaining this alias served no purpose and risked confusion.

"We left kthread_exit() around as an alias to do_exit(). Remove it completely." — Christian Brauner

The patch updates various subsystems, including sunrpc, to call do_exit() directly. David Gow provided an Ack for the KUnit portions of the change, noting that while the name do_exit() is not ideal, the cleanup is correct.

"The KUnit bits of this look fine... (That being said, I agree that do_exit() isn't as nice a name.)" — David Gow

The Debate: Safety of Exporting do_exit()

Christoph Hellwig raised a strong objection, not to the removal of the alias per se, but to the implication that modules (like those in the NFS stack) should be calling do_exit(). He argued that exporting do_exit, which can operate on any task, was a "really bad idea" and suggested re-adding a wrapper that strictly checks for PF_KTHREAD flags.

"I think exporting do_exit which can work on any task is a really bad idea. I'd much rather re-add a kthread_exit wrapper that checks PF_KTHREAD first..." — Christoph Hellwig

Linus Torvalds vigorously rebutted this position, arguing that do_exit() is inherently safe because it only exits the current task. He contended that artificially limiting exit functions to kthreads provided no technical benefit and had historically caused bugs.

"do_exit() cannot mess up random tasks. It can only exit the current task... Exiting a task is about the least effed up you can do to a task when you are in kernel mode." — Linus Torvalds

Torvalds further highlighted that the previous separation of kthread_exit() from do_exit() was precisely what led to the memory corruption bugs Brauner's patch addressed. He noted that kthread_exit() had started doing "extra things" beyond standard exit, creating a divergence that caused subtle cleanup failures.

"And that 'kthread_exit() does extra things' was the actual bug that needed fixing and caused nasty memory corruption due to subtle lack of cleanup when it was bypassed." — Linus Torvalds

Conclusion and Future Direction

The discussion concluded with a consensus that maintaining kthread_exit() as a separate, limited entity was counterproductive. Brauner agreed with Torvalds' assessment, stating that the line between kthreads and other worker types (like vhost) is "very very blurry," making special-cased exit functions problematic.

"And no, we should definitely not keep kthread_exit() as a separate thing around. That just seems weird and clearly that has led to bugs before." — Christian Brauner

Brauner indicated he would follow up with a series to rename the unified exit function (suggesting task_exit() or similar) to address the naming concerns raised by Torvalds and Hch, ensuring that NFS and other subsystems have a clear, safe, and correctly named interface for task termination.

"I have that as a follow-up series... But I didn't want to muddle the two patches as this one was meant as a clean-up for the kthread_exit() leftover." — Christian Brauner

While Hch remained unconvinced about modules exiting tasks, Torvalds' historical analysis and technical arguments regarding the benign nature of do_exit() for the current task appear to have steered the direction toward unification rather than restriction.
