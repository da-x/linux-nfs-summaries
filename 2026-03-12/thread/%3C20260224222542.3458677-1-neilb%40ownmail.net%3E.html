VFS Directory Locking v3: Brauner Reviews, AppArmor Refcount Bug Found, Cachefiles Fixup Patch Submitted

Summary

VFS Directory Locking v3: Brauner Reviews, AppArmor Refcount Bug Found, Cachefiles Fixup Patch Submitted

Overview

This week marked the first substantive maintainer-level review of Neil Brown's 15-patch series "Further centralising of directory locking for name ops" (v3). VFS maintainer Christian Brauner posted two detailed reviews on March 6, identifying a reference count leak fix in the AppArmor conversion and a subtle behavioral regression in the cachefiles patch. Neil Brown responded promptly, acknowledging both findings and submitting a fixup patch for the cachefiles issue on March 8.

Classification: VFS refactoring with incidental bug fixes — not a new feature or protocol change. The series centralizes directory locking for name operations into unified interfaces (start_creating(), start_removing(), start_renaming_dentry(), etc.), a prerequisite for transitioning from whole-directory to per-name locking.

Bridge from Prior Weeks

Last week (ending 2026-03-05), Jeff Layton provided Reviewed-by tags on patches 01/15 and 04/15, and Neil Brown followed up with Christian Brauner requesting a review timeline prior summary. The v3 series itself was submitted on February 24, addressing bugs found during Chris Mason's tool-based review of v2.

This Week's Activity

Brauner Identifies AppArmor Refcount Leak Fix

In his review of [PATCH 05/15 — AppArmor: Use simple_start_creating() / simple_done_creating()], Christian Brauner identified that the patch inadvertently fixes a pre-existing reference count leak in the AppArmor aafs_create function:

"Fwiw, I think this fixes a reference count leak: The old aafs_create returned dentries with refcount=2 (one from lookup_noperm, one from dget in __aafs_setup_d_inode). The cleanup path aafs_remove puts one reference leaving one reference that didn't get cleaned up. After your changes this is now correct as simple_done_creating() puts the lookup reference." Review

Neil Brown confirmed Brauner's analysis on March 6:

"Yes, I think you are correct. I remember reviewing how ->dents was used to confirm that the new refcounting was correct. I didn't notice at the time that the old was wrong." Response

This represents an incidental bug fix: the VFS refactoring corrected a latent dentry reference leak in AppArmor's filesystem code.

Brauner Flags Cachefiles Behavioral Regression

Brauner's review of [PATCH 10/15 — cachefiles: change cachefiles_bury_object to use start_renaming_dentry()] raised two concerns about subtle behavioral changes that could cause unnecessary cache disabling:

Issue 1 — Parent mismatch error handling: Brauner noted that if rep->d_parent != dir after lock_rename, the old code returned 0 (success), but the new __start_renaming_dentry() returns -EINVAL. This triggers cachefiles_io_error(), which sets CACHEFILES_DEAD and permanently disables the cache:

"I think this is a subtle change in behavior? If rep->d_parent != dir after lock_rename this returned 0 in the old code. With your changes the same condition in __start_renaming_dentry returns -EINVAL which means cachefiles_io_error() sets CACHEFILES_DEAD and permanently disables the cache." Review

Issue 2 — ENOMEM handling: Similarly, a -ENOMEM return from lookup_one() in the old code allowed the cache to stay alive and returned directly. The new code routes this through cachefiles_io_error(), again setting CACHEFILES_DEAD:

"In the old code a -ENOMEM return from lookup_one() let the cache stay alive and returned directly. The new code gets sent via cachefiles_io_error() causing again CACHEFILES_DEAD to be set and permanently disabling the cache." Review

Brauner offered to fold a fixup into his tree:

"Maybe both changes are intentional. If so we should probably note this in the commit message or this should be fixed? If you give me a fixup! on top of vfs-7.1.directory I can fold it." Review

Neil Brown Submits Cachefiles Fixup Patch

On March 8, Neil Brown submitted a [PATCH] FIXUP addressing Brauner's concerns Fixup. The fixup preserves the original error-return behavior and log messages, and importantly ensures cachefiles_io_error() is called in exactly the same circumstances as the original code:

"[[This fixup for f242581e611e in vfs/vfs-7.1.directory provides a new commit description has preserves the error returns and log message, and importantly calls cachefiles_io_error() in exactly the same circumstances as the original - thanks]]" Fixup

The patch adds 20 lines to fs/cachefiles/namei.c, re-checking error conditions after start_renaming_dentry() returns an error to ensure correct handling. Neil Brown also notes that the check verifying ->graveyard is still d_can_lookup() is dropped, as this was already verified when ->graveyard was assigned and cannot change.

NFS Client Relevance

This series does not directly modify NFS client code. Its impact on NFS client development remains indirect:

  • Cachefiles: The cachefiles subsystem is used by FUSE-based caching solutions and can interact with NFS in certain configurations. The fixup patch ensures that transient errors (parent mismatch, ENOMEM) no longer cause permanent cache disabling — a reliability improvement for any caching layer that may sit alongside NFS.
  • VFS locking infrastructure: The centralization of directory locking is a prerequisite for per-name locking, which will eventually affect how all filesystems — including NFS — interact with VFS name operations. Parallel discussions around d_splice_alias() and hashed dentries (directly relevant to NFS client atomic_open handling) remain open and may intersect with this work.
  • NFS server: Patch 07/15 converts nfsd's purge_old() in the NFSv4 recovery code to use the new API, but this has no behavioral impact on NFS client operations.

Key Technical Arguments and Evolution

  1. Incidental bug discovery: Brauner's review revealed that the AppArmor conversion patch fixes a pre-existing dentry reference count leak — an unintended but beneficial side effect of the VFS refactoring.
  2. Behavioral regression caught early: The cachefiles patch introduced subtle changes in error handling that could cause permanent cache disabling on transient failures. Brauner's thorough review caught this before the patch was merged.
  3. Rapid fixup cycle: Neil Brown submitted a targeted fixup within two days of receiving feedback, demonstrating an effective review-and-fix workflow.

Final Conclusions

  • Two issues identified and one resolved: The AppArmor refcount leak is acknowledged as a beneficial side effect (no separate fix needed). The cachefiles behavioral regression has been addressed via a fixup patch ready for Brauner to fold into vfs-7.1.directory.
  • Maintainer review in progress: Christian Brauner has engaged with the series and provided actionable feedback. The remaining patches (particularly the overlayfs changes in patches 09–14) still await his review.
  • Series quality improving: Both automated review (Chris Mason's tool-based analysis in v3) and human review (Brauner's detailed examination) have proven effective at catching issues before merge.
  • NFS client impact: minimal direct, but important indirect. The cachefiles fixup preserves cache reliability for any caching infrastructure that may interact with NFS workloads.
