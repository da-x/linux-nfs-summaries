RFC 53-Patch Series: Lifting VFS Lookup Out of Exclusive Directory Lock for NFS Client Concurrency

Summary

RFC 53-Patch Series: Lifting VFS Lookup Out of Exclusive Directory Lock

Overview

On March 12, Neil Brown submitted a massive **[PATCH RFC 00/53] series](https://lore.kernel.org/linux-nfs/20260312214330.3885211-1-neilb@ownmail.net/) titled "lift lookup out of exclive lock for dir ops", representing a major step in his long-running effort to improve concurrency of directory operations across the Linux VFS and filesystems — with significant implications for NFS client development.

Classification: VFS locking refactoring with broad protocol-level implications for dcache management. This is not a simple bug fix but a foundational architectural change enabling concurrent directory updates by removing the dependency on exclusive parent-directory locks during lookup operations.

Bridge from Prior Weeks

Last week, Neil Brown's earlier 15-patch series "Further centralising of directory locking for name ops" (v3) received substantive review from VFS maintainer Christian Brauner. Brauner identified an incidental AppArmor dentry reference count leak fix and a behavioral regression in the cachefiles subsystem prior summary. A fixup patch was submitted and applied to vfs-7.1.directory on March 9 prior summary. The current 53-patch RFC series represents the next phase of this work, building on that foundation.

This Week's Activity

The Core Problem: Exclusive Locking as a Concurrency Bottleneck

Neil Brown's cover letter outlines the fundamental issue: the VFS currently requires a shared parent lock to exclude directory-modifying operations during d_alloc_parallel(). This serializes directory operations unnecessarily. The series aims to:

"remove this dependency so that d_alloc_parallel() can be called without locking and all directory modifying operations receive either a hashed dentry or an in-lookup dentry" Cover Letter

The long-term goal is to push parent-directory locking down into individual filesystems (which can discard it if unnecessary) and use exclusive dentry locking in the VFS for all directory operations except readdir:

"My longer term goal involves pushing the parent-directory locking down into filesystems (which can then discard it if it isn't needed) and using exclusive dentry locking in the VFS for all directory operations other than readdir" Cover Letter

Two Key Technical Challenges

Neil Brown identified two critical obstacles:

1. Lock Ordering and Deadlock Potential: Since d_alloc_parallel() effects a blocking lock, calling it while holding the directory lock creates deadlock risk when the locking order is inverted:

"If we are to take the directory lock after calling d_alloc_parallel() (and still holding an in-lookup dentry... then we must never call d_alloc_parallel() while holding the directory lock, even a shared lock." Cover Letter

This particularly affects readdir operations where filesystems prime the dcache using d_alloc_parallel() in ->iterate_shared. The solution is a new API, d_alloc_noblock(), which fails rather than blocking.

2. Unsafe d_drop() Patterns: With d_alloc_parallel() running without the directory lock, holding that lock exclusively is insufficient to protect dcache manipulations:

"several filesystems d_drop() a dentry and (possibly) re-hash it. This will no longer be safe as d_alloc_parallel() could run while the dentry was dropped, would find that name doesn't exist in the dcache, and would create a new dentry leading to two uncoordinated dentries with the same name." Cover Letter

The fix involves enhancing d_splice_alias() to handle hashed, unhashed, and in-lookup dentries uniformly, eliminating the need for early d_drop() calls.

New APIs Introduced

  • d_alloc_noblock() — Non-blocking variant of d_alloc_parallel() that returns -EWOULDBLOCK instead of sleeping
  • d_duplicate() — Creates an in-lookup dentry with the same name as an existing hashed dentry, preventing race conditions during rename operations

APIs Removed (at series end)

  • d_alloc(), d_rehash(), d_add(), lookup_one(), lookup_noperm()

NFS Client-Specific Changes

The series contains seven patches directly modifying NFS client code (patches 09–15), each addressing specific locking and dcache management issues:

PATCH 09/53: Remove d_drop()/d_alloc_parallel() from nfs_atomic_open()

This patch eliminates the current workaround in nfs_atomic_open() where a negative dentry is discarded and recreated via d_alloc_parallel() to prevent races between concurrent non-create opens. Neil Brown explains:

"We can achieve the same effect by causing ->d_revalidate to invalidate a negative dentry when LOOKUP_OPEN is set. Doing this is consistent with the 'close to open' caching semantics of NFS which requires the server to be queried whenever opening a file — cached information must not be trusted." Patch 09/53

This change removes 23 lines of code while maintaining correctness through the nfs_neg_need_reval mechanism.

PATCH 10/53: Use d_splice_alias() in nfs_link()

Previously, nfs_link() called d_drop() followed by d_add() because no single API could handle both hashed and unhashed dentries. With the enhanced d_splice_alias():

"Recent changes to d_splice_alias() mean that it can work with either hashed or unhashed dentries. Future changes to locking mean that it will be unsafe to d_drop() a dentry while an operation (in this case 'link()') is still ongoing." Patch 10/53

PATCH 11/53: Don't d_drop() before d_splice_alias() in nfs_add_or_obtain()

The nfs_add_or_obtain() function (used via nfs_instantiate()) previously dropped the dentry before splicing. This is no longer necessary:

"As d_splice_alias() now works with hashed dentries, the d_drop() is no longer needed." Patch 11/53

PATCH 12/53: Don't d_drop() before d_splice_alias() in atomic_create

When atomic_create fails with -ENOENT, the old code dropped and re-added the dentry with a NULL inode. This pattern is incompatible with the new locking model:

"As d_splice_alias() now supports hashed dentries, we don't need the d_drop() until it is determined that some other error has occurred." Patch 12/53

PATCH 13/53: Use d_alloc_noblock() in nfs_prime_dcache()

NFS primes the dcache with readdir results. Blocking during this operation is both pointless and dangerous under the new locking order:

"Blocking in that case is pointless as the lookup will add info to the dcache and there is no value in the readdir waiting to see if it should add the info too." Patch 13/53

The patch switches to d_alloc_noblock() and uses try_lookup_noperm() instead of full_name_hash and d_lookup.

PATCH 14/53: Use d_alloc_noblock() in silly-rename

The NFS silly-rename mechanism (used to preserve deleted-but-open files on the server) is reworked to avoid normal lookups:

"Rather than performing a normal lookup (which will be awkward with future locking changes) use d_alloc_noblock() to find a dentry for an unused name, and then open-code the rest of lookup_slow() to see if it is free on the server." Patch 14/53

This patch adds 36 lines while removing 20, reflecting the complexity of the silly-rename path.

PATCH 15/53: Use d_duplicate() in NFS

Prepares for d_alloc_parallel() running without directory locks by using the new d_duplicate() API for silly rename operations:

"As preparation for d_alloc_parallel() being allowed without the directory locked, use d_duplicate() to duplicate a dentry for silly rename." Patch 15/53

Key Technical Arguments and Evolution

  1. Foundational locking change: The series represents a paradigm shift from whole-directory exclusive locking to per-dentry exclusive locking via DCACHE_PAR_LOOKUP, enabling true concurrent directory updates.
  2. NFS client simplification: Seven NFS-specific patches collectively remove complex d_drop()/d_alloc_parallel() workarounds, replacing them with cleaner patterns using enhanced d_splice_alias(), d_alloc_noblock(), and d_duplicate().
  3. Deadlock prevention: The introduction of d_alloc_noblock() eliminates blocking in dcache-priming paths (readdir) that would otherwise create lock-order inversions.
  4. Race condition elimination: The d_duplicate() API prevents windowed races during rename operations where two uncoordinated dentries with the same name could be created.

Final Conclusions

  • Series status: RFC stage, awaiting Al Viro's ACK as explicitly required by Linus Torvalds. A git branch has been requested to facilitate review and automated testing.
  • NFS client impact: Significant — seven patches directly modify NFS client code, simplifying nfs_atomic_open(), nfs_link(), nfs_add_or_obtain(), dcache priming, and silly-rename paths. The changes remove 23+ lines of workaround code in nfs_atomic_open() alone while maintaining correctness through NFS's "close to open" caching semantics.
  • Risk assessment: Neil Brown acknowledged the conceptual magnitude: "It is a big conceptual change and there could easily be surprising implications." He noted testing was limited to NFS at submission time.
  • Next steps: The series requires Al Viro's review and ACK, availability of a git branch for reviewers and test robots, and broader filesystem maintainer engagement (the series touches xfs, ovl, coda, shmem, afs, smb/client, exfat, configfs, ext4, tracefs, cephfs, ecryptfs, gfs2, libfs, fuse, hostfs, efivarfs).
