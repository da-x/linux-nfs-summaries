Summary

sunrpc: Refactor TLS Transport to Remove rpc_clnt Dependency

This week's discussion focused on an architectural refactoring of the SUNRPC subsystem's TLS transport layer, proposed by Benjamin Coddington (Hammerspace). This effort follows last week's urgent fix for a use-after-free (UAF) bug in TLS connection workers summarized previously, which was caused by improper lifetime management of the rpc_clnt structure.

The Proposal: Decoupling Transport from Client

Coddington introduced an RFC PATCH titled "sunrpc: refactor TLS transport to remove rpc_clnt dependency." The core argument is that the TLS connection worker (xs_tcp_tls_setup_socket) currently requires a reference to the upper-layer rpc_clnt to populate arguments for rpc_create() when setting up the lower-layer transport. This dependency created the lifetime issues and UAF risks addressed in the previous week's patch.

"It is architecturally cleaner to decouple the transport connection logic from the RPC client entirely."

The proposed refactoring involves:

  • Removing the clnt member from struct sock_xprt.
  • Saving the RPC program number and version from the task during xs_connect() into the sock_xprt structure.
  • Using these saved parameters for lower-layer client creation via dummy program definitions.
  • Updating TLS-related tracepoints to remove the rpc_clnt dependency.

Coddington admitted the patch was a work in progress:

"I'm not sure I like what came out here. It adds a lot of boilerplate, and it reduces the tracepoint data... This is lightly tested by hand.."

Review and Technical Critique

Chuck Lever provided a thorough review on March 12, acknowledging the direction but highlighting several technical concerns:

  1. Architectural Rationale: Lever questioned why simply bumping the reference count on rpc_clnt wasn't sufficient, noting that while the refactor removes "abuse" in the current code, the rationale for avoiding refcounting needed expansion.
  2. Safety of NULL Credentials: He asked for a rationale in the patch description regarding why using a NULL credential is safe in this context.
  3. Layering Violations and Boilerplate: Lever pointed out that creating dummy rpc_program definitions for every NFS version (2, 3, and 4) was a "layering violation" and added unnecessary complexity. He suggested a simpler design:

    "Use a single dummy version at index 0 with args->version = 0 always, relying solely on args->prognumber for the wire program number. The TLS probe never consults cl_vers -- it uses a fixed proc via msg.rpc_proc."

  4. Tracepoint Data Loss: Lever noted that dropping the program number and version from tracepoints was problematic because this information is critical for administrators debugging AUTH_TLS failures:

    "The program number and version that /are/ dropped are what actually go on the wire in the AUTH_TLS NULL call, so if the probe fails, the administrator wants to know which program/version pair was rejected..."

  5. Timeout Behavior Change: He identified an unintentional change in timeout behavior, where the source shifted from the upper-layer client's configured timeout to the transport's default timeout, potentially altering retry behavior for mounts with custom settings.
  6. Coding Style: Minor nitpicks regarding indentation (spaces vs. tabs) in the new static structures.

Despite these critiques, Lever concluded positively:

"The proposed refactoring seems like a sensible direction. The UAF potential is eliminated structurally, and some of the transport-to-client coupling (and layering violation) is removed."

Next Steps

Benjamin Coddington responded later on March 12, acknowledging the rough spots and Lever's feedback. He explained that his initial idea of a simpler dummy program was complicated by sanity-checking code in rpc_new_client() that verifies version consistency.

"I kinda wish I could define a completely static rpc_clnt, make a mutable copy, set prognum and version and somehow get that plumbed through the rpc_create() machinery.. then throw it away.."

Coddington committed to iterating on Lever's review points for a v2 patch:

"Ok - thanks for looking at this and showing interest. As you've noted there are quite a few rough spots here due to me just tacking this together quickly. Sorry for the messiness. I'll plan on iterating on your review points for a v2..."

Conclusion

This thread marks a transition from an emergency bug fix to a more robust architectural solution for NFS-over-TLS. While the immediate UAF was patched last week, this RFC discussion highlights the community's commitment to cleaning up technical debt in the SUNRPC layer. The key takeaway is the consensus that decoupling the transport layer from the rpc_clnt is the correct long-term strategy, even if the implementation details require further refinement to address coding style, tracepoint visibility, and timeout behavior.
