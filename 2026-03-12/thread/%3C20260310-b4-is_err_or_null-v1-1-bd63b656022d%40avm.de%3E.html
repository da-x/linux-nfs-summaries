Coccinelle: Prefer IS_ERR_OR_NULL over manual NULL check

Overview

This thread concerns a code cleanup / static analysis tooling improvement rather than an NFS-specific feature or bug fix. Markus Elfring submitted a 61-patch series, with the first patch introducing a new Coccinelle semantic patch (scripts/coccinelle/api/is_err_or_null.cocci) designed to automatically convert manual IS_ERR() plus NULL checks into the more concise IS_ERR_OR_NULL() macro throughout the kernel source tree.

Discussion Summary

The thread contains two messages from Markus Elfring this week, both responding to his own initial patch submission. The discussion is notable for its focus on the design and correctness of the Coccinelle (SmPL) rules themselves, rather than on NFS client or server code changes directly.

Message 1: Questions about SmPL Rule Design

In his first message on March 10, Elfring raises several questions about the structure and robustness of the semantic patch rules:

"Can this information trigger any more consequences on corresponding summary phrases?"

He probes whether the rule definitions adequately cover all case distinctions and asks:

"Did you eventually check probabilities for the occurrence of mentioned case distinctions?"

Elfring also suggests reconsidering potential side effects in the splitting of SmPL rules:

"I suggest to reconsider 'side effects' according to the splitting of these SmPL rules once more."

Regarding the report and org operation modes, he expresses skepticism about certain syntax choices:

"I doubt that the usage of SmPL asterisks fits to these two operation modes."

He further questions whether certain code patterns should be reorganized within the rule listing and whether additional operation modes might benefit from the search patterns.

Message 2: Follow-up on Confidence and Failure Predicates

In his second message on March 11, Elfring notes that the patch carries a // Confidence: High annotation but acknowledges prior scrutiny:

"Some contributors presented discerning comments for this change approach."

He then focuses on a specific transformation rule that converts expressions like E != NULL && !IS_ERR(E) into !IS_ERR_OR_NULL(E), noting that many of these detected expressions refer to function return values. He raises two forward-looking questions:

"Do any development challenges hinder still the determination of corresponding failure predicates?"

"How will interests evolve to improve data processing any further for such use cases?"

Key Technical Points

  • Nature of the work: This is a tooling/cleanup effort using Coccinelle (SmPL) to standardize error-checking patterns across the kernel, including NFS-related code.
  • No direct NFS bug fix: While the patches may touch NFS client or server files as part of the broader cleanup, the thread itself does not address any NFS-specific protocol issues, bugs, or features.
  • Self-review pattern: The discussion consists entirely of Elfring questioning and refining his own patch approach, with no responses from other maintainers or contributors this week.

Conclusion

The thread reflects ongoing meta-discussion about the correctness and completeness of automated code transformation rules. No conclusions were reached this week, as no other participants engaged in the conversation. The broader series aims to improve code consistency by replacing verbose error-checking patterns with the IS_ERR_OR_NULL() macro, but the immediate focus remains on refining the Coccinelle rules themselves rather than on NFS client development or bug fixes.
