vfs: inode->i_ino widened to u64 — Series Merged, EVM ABI Concerns Surface for 32-bit

Summary

The [PATCH v3 00/12] vfs: change inode->i_ino from unsigned long to u64 series by Jeff Layton was merged this week into the vfs-7.1.kino branch of vfs/vfs.git, marking a major milestone in the long-running effort to provide a universal 64-bit inode identifier across all architectures. However, post-merge review uncovered an oversight in the Extended Verification Module (EVM) subsystem, sparking a debate about ABI implications for 32-bit embedded/IoT devices.

This is primarily a VFS architecture-level change with significant downstream benefits for NFS client development, though it also functions as a bug fix for 32-bit systems where inode numbers exceeding 32 bits were previously truncated.

Series Merged

Christian Brauner applied the full 12-patch series to vfs-7.1.kino, expressing satisfaction with the outcome:

"This series makes me happy. We've been talking about this conversion for a while and I'm thankful that you did this work. Without the automation available this probably wouldn't have happened as quickly as it did now." Re: PATCH 00/12

Paul Moore provided an Acked-by for the audit subsystem changes in patch 02/12, which widen audit inode fields to u64 to prevent truncation in security-relevant logging:

"Acked-by: Paul Moore paul@paul-moore.com" Re: PATCH 02/12

Christoph Hellwig had previously requested cleanup of unnecessary extern declarations in the VFS hash/lookup functions. Jeff Layton acknowledged the request but noted the series was already merged:

"I was planning to do that, but then Christian merged it! I'll do a patch on top of this that does this in the range of fs.h that the patch touches." Re: PATCH 01/12

Brauner confirmed this minor cleanup could be handled post-merge:

"I can easily drop those so no need to resend for stuff like this as per the usual protocol." Re: PATCH 01/12

EVM Oversight and ABI Concerns on 32-bit

After the merge, Mimi Zohar identified that the Extended Verification Module (EVM) subsystem was missed by the series. In hmac_add_misc(), EVM copies i_ino to calculate HMAC or file metadata hashes used for signing:

"Jeff, missing from this patch set is EVM. In hmac_add_misc() EVM copies the i_ino and calculates either an HMAC or file meta-data hash, which is then signed." Re: PATCH 00/12

Layton proposed a straightforward fix — changing the EVM ino field to u64 alongside everything else. However, Zohar raised concerns about the ABI implications:

"What we do know: changing the size of the i_ino field would affect EVM file metadata verification and would require relabeling the filesystem. Even packages containing EVM portable signatures, which don't include or verify the i_ino number, would be affected." Re: PATCH 00/12

This triggered a deeper discussion about 32-bit systems. Layton considered an alternative — keeping the EVM field as unsigned long to preserve compatibility:

"Ouch. Technically, I guess this is ABI... While converting to u64 seems like the ideal thing to do, the other option might be to just keep this as an unsigned long for now. No effect on 64-bit, but that could keep things working 32-bit when the i_ino casts properly to a u32." Re: PATCH 00/12

Zohar agreed with the cautious approach but expressed concern for embedded/IoT deployments:

"My concern would be embedded/IoT devices, but I don't have any insight into who might be using it on 32 bit." Re: PATCH 00/12

Layton concluded that preserving unsigned long in EVM for now was the best path forward, noting the declining but still significant presence of 32-bit devices:

"For now, I think that's the best approach. I'll spin up a patch to add the comment." Re: PATCH 00/12

He referenced an LWN article on Arnd Bergmann's talk about the state of 32-bit support, observing:

"The upshot is that it's hard to buy 32-bit CPUs these days, and will only get harder. But, there are still a fair number of 32-bit devices out in the field and will be for some time." Re: PATCH 00/12

NFS Client Development Impact

As highlighted in last week's summary, this series enables significant NFS client simplification. With inode->i_ino now universally 64-bit, the NFS client can eventually eliminate:

  • The redundant nfs_inode.fileid field
  • The enable_ino64 module parameter
  • XOR-folding helpers like nfs_compat_user_ino64()
  • Various 32-bit inode hashing workarounds

Layton noted in the cover letter that these cleanups would be deferred to a follow-on series:

"With this change, we may be able to shrink some inode structures. For instance, struct nfs_inode has a fileid field that holds the 64-bit inode number. With this set of changes, that field could be eliminated. I'd rather leave that sort of cleanups for later just to keep this simple."

Chuck Lever had previously provided Reviewed-by for the NFSD hunks in patch 12/12 last week. The merge of this series paves the way for those downstream NFS simplifications.

Conclusions

  1. The v3 series has been merged into vfs-7.1.kino, with patches expected to appear in linux-next shortly.
  2. An EVM oversight was identified post-merge, raising ABI concerns for 32-bit systems using EVM-signed filesystems. The consensus leans toward keeping the EVM field as unsigned long temporarily to avoid breaking existing 32-bit deployments, with a comment explaining the rationale.
  3. NFS client simplification is now imminent: the groundwork has been laid for removing legacy 32-bit inode workarounds in a follow-on series.
  4. Minor VFS cleanup (removing unnecessary extern declarations) will be handled post-merge without requiring a resend of the full series.
