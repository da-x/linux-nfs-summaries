RDMA/rw: Fix MR pool exhaustion in bvec RDMA READ path

Summary

This week, Chuck Lever submitted a two-patch series (PATCH v2 0/2) addressing a critical Memory Region (MR) pool exhaustion bug in the RDMA core and proposing an optimization for the NFS server's RDMA implementation (svcrdma). The discussion is focused entirely on bug fixes and performance optimizations related to NFS over RDMA.

Key Technical Arguments and Bug Fix

The primary issue, detailed in Patch 1/2, affects systems where IOVA-based DMA mapping is unavailable (e.g., IOMMU passthrough mode). In this scenario, rdma_rw_ctx_init_bvec() incorrectly falls back to checking rdma_rw_io_needs_mr() using the raw bvec count.

Lever explains that unlike the scatterlist path, which uses a post-DMA-mapping entry count reflecting coalesced physically contiguous pages, the bvec path uses a pre-mapping page count. This discrepancy leads to significant issues:

"This overstates the number of DMA entries, causing every multi-bvec RDMA READ to consume an MR from the QP's pool."

Under NFS WRITE workloads, where the server performs RDMA READs to pull data from the client, this inflated demand rapidly exhausts the MR pool. The consequences are severe for system stability:

"The pool is rapidly exhausted, ib_mr_pool_get() returns NULL, and rdma_rw_init_one_mr() returns -EAGAIN. svcrdma treats this as a DMA mapping failure, closes the connection, and the client reconnects -- producing a cycle of 71% RPC retransmissions and ~100 reconnections per test run."

Lever notes that RDMA WRITEs (NFS READ direction) are unaffected because DMA_TO_DEVICE never triggers the max_sgl_rd check. The fix removes the rdma_rw_io_needs_mr() gate from the bvec path entirely, ensuring bvec RDMA operations always use the map_wrs path (direct WR posting without MR allocation). Lever argues that the raw page count cannot serve as a reliable input for rdma_rw_io_needs_mr() because physical contiguity is only discovered during DMA mapping.

Evolution of the Discussion and Optimization Proposal

This is version 2 of the patch series. In the cover letter, Lever notes:

"This series now carries the original fix with review comments addressed, and a proposal for using contiguous pages for RDMA Read sink buffers in svcrdma."

He recommends that the fix patch be merged into the 7.0-rc cycle, while the behavioral change can wait for the next merge window:

"IMO the fix patch should go into 7.0-rc, and the RDMA Read behavior change can wait for the next merge window."

Patch 2/2 proposes an optimization for svc_rdma_build_read_segment(). Currently, it constructs RDMA Read sink buffers by consuming pages one-at-a-time, resulting in multiple bvecs and DMA mappings for a single payload (e.g., 16 bvecs for a 64KB NFS READ).

Lever proposes using a single higher-order allocation followed by split_page() to yield physically contiguous memory. This allows the use of a single bvec spanning the contiguous range, triggering the rdma_rw_init_single_wr_bvec() fast path:

"A single bvec spanning the contiguous range causes rdma_rw_ctx_init_bvec() to take the rdma_rw_init_single_wr_bvec() fast path: one DMA mapping, one SGE, one WR."

The implementation includes robust fallback mechanisms. It uses __GFP_NORETRY | __GFP_NOWARN and falls back through decreasing orders if higher-order allocations fail. Lever emphasizes that this optimization does not increase per-request page consumption and prevents accumulation under memory pressure.

Final Conclusions

The thread concludes with the submission of these two patches. The first patch is a critical bug fix for MR pool exhaustion in specific hardware configurations, while the second is a performance optimization to reduce DMA mapping overhead. Lever suggests that Christoph Hellwig influenced the contiguous page allocation approach ("Suggested-by: Christoph Hellwig"). No further discussion occurred within this week's window, leaving the patches pending review and integration into the kernel tree.
