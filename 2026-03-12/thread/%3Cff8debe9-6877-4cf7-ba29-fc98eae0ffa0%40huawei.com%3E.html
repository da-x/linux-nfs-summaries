NFS Client Hangs with NFS_CS_NO_RETRANS_TIMEOUT: Protocol Semantics Debate

Summary

Background (Prior Weeks)

This thread originated in August 2025 when Zhangjian from Huawei reported a severe issue on NFS client kernel 5.10: over 400,000 delegations accumulated in the NFS_DELEGATION_REVOKED state, causing massive TEST_STATEID request storms after any non-privileged operation. The root cause was identified as NFSPROC4_CLNT_DELEGRETURN procedures timing out (ETIMEOUT), which marked delegations as revoked on the client but left them permanently in the server's clp->cl_revoked list. Jeff Layton noted that "v5.10 is pretty old, and there have been a number of fixes in this area in both the client and server over the last several years" and suggested upgrading or backporting. Trond Myklebust offered four remedies, including garbage-collecting revoked stateids on the server side. Zhangjian pushed back, arguing that server-side timeout during delegation return was not the only path to permanent revocation accumulation and that "garbaging collecting revoked stateid after a while (4) is more reasonable way to avoid this problem."

This Week's Activity

The thread re-emerged this week with a related but distinct question about NFS client retransmission semantics. On March 6, Zhangjian reported a new hang scenario:

"1.Nfs wait for sunrpc 2.Sunrpc send OPEN message and hang the rpc task onto sunrpc pending queue. 3.Server never reply, and since NFS_CS_NO_RETRANS_TIMEOUT is forced and connection is ESTABLISHED, task will never be retransmitted. This cause procedures waiting on this file hang forever."

Zhangjian acknowledged that umount -f could kill the stuck RPC tasks and noted "the key to the problem most likely lies in the network layer," but asked whether NFS should retransmit after a long wait regardless of the connection state.

Trond Myklebust's Response: Protocol Compliance

NFS client maintainer Trond Myklebust responded firmly on March 6, grounding his answer in the NFSv4 specification:

"Please read the NFSv4 spec. It very clearly states that the client should never retransmit unless the connection breaks."

He concluded bluntly:

"IOW: the problem here is your broken server, not the client."

This position reflects a core design principle of the Linux NFS client: under hard mount semantics (the default), the client must wait indefinitely for a response on an established connection to preserve POSIX consistency guarantees. The NFS_CS_NO_RETRANS_TIMEOUT flag enforces this by suppressing retransmission timeouts when the TCP connection is still alive.

Zhangjian's Follow-Up: Should NFS Timeout Instead?

On March 12, Zhangjian returned with a refined question, changing the subject to "should nfs timeout even with NFS_CS_NO_RETRANS_TIMEOUT?" He argued:

"NFSv4 spec said client should never retransmit, but not said client need to wait forever. Maybe sunrpc should tell nfs -ETIMEOUT and nfs return ERROR rather than retransmit."

This is a nuanced point: the spec prohibits retransmission, but Zhangjian suggested that returning an error (rather than hanging indefinitely) might be acceptable behavior.

Trond Myklebust's Final Response: The Slot Exhaustion Problem

Trond responded on March 12 with a detailed explanation of why unconditional timeout-and-error semantics are not viable for NFSv4 clients under hard mount options:

"You are 100% free to use the existing 'soft' or 'softerr' mount options if you have applications that can parse those (non-POSIX) errors."

He then highlighted a critical protocol constraint from RFC 8881:

"Note however that there is no way to tell the server that you are 'cancelling' an RPC call, so it will hold onto that slot until it is done executing the call (see RFC8881, Section 2.10.6.1.). So you are eventually going to run out of usable slots, and the system will gum up anyway."

Trond's key conclusion was:

"The default mount option is 'hard', because those are the only semantics that are compatible with POSIX and NFSv4.x."

Key Technical Arguments

  1. NFSv4 retransmission rules: The NFSv4 specification explicitly forbids client retransmission on an established connection. This is by design — unlike NFSv3, NFSv4 uses a slot-based compound RPC mechanism where duplicate requests could cause undefined server behavior.

  2. NFS_CS_NO_RETRANS_TIMEOUT semantics: This flag prevents the SUNRPC layer from timing out and retransmitting when the TCP connection is ESTABLISHED. The rationale is that if the connection is alive, the server may simply be slow or busy processing a long-running operation (e.g., a delegation recall).

  3. The slot exhaustion problem: Even if the client were to unilaterally timeout and return an error, NFSv4 provides no mechanism to cancel an in-flight RPC on the server side. The server retains the allocated slot until it completes the operation. Repeated timeouts would exhaust all available slots, causing the entire mount to stall — effectively producing the same hang Zhangjian is trying to avoid.

  4. soft vs hard mount semantics: Trond emphasized that soft mounts (which do timeout and return errors) are non-POSIX and should only be used by applications capable of handling those error conditions gracefully. The default hard mount is the only POSIX-compliant option for NFSv4.

Classification

This discussion is about protocol semantics and client behavior, not a new feature or bug fix per se. It centers on whether the Linux NFS client's adherence to NFSv4 retransmission rules (no retransmit on established connections) should be relaxed to allow timeout-and-error behavior. The maintainer's position is that the current behavior is correct by specification, and workarounds exist (soft mount options, umount -f) for environments with unreliable servers.

Conclusion

No code changes resulted from this week's exchange. Trond Myklebust maintained that the Linux NFS client's behavior is spec-compliant and that the root cause lies with unresponsive servers rather than client logic. Zhangjian's concerns about indefinite hangs are acknowledged but deemed an inherent trade-off of POSIX-compatible hard mount semantics in NFSv4. The recommended paths forward remain: use soft/softerr mount options for applications that can tolerate non-POSIX errors, or address server-side reliability issues directly.
