xprtrdma: Regression Report on MR Cursor Refactoring Patch

Overview

This week's activity in the xprtrdma race-fix and refactoring series was limited to a critical regression report filed by Anna Schumaker against PATCH v2 6/8, which replaces the rpcrdma_mr_seg intermediate structure with an xdr_buf cursor in the RDMA transport layer. The broader eight-patch series, introduced last week by Chuck Lever, targets race conditions surfaced by the nconnect mount option and includes structural refactoring for memory registration performance.

Context from Prior Week

Last week, Chuck Lever submitted [PATCH v2 0/8] "Fix various races in xprtrdma," an eight-patch series blending bug fixes (race conditions, hangs, lost wakeups) with performance enhancements (scaled receive batch size, deferred post-recvs) and structural cleanup. Patch 6/8 — the focus of this week's discussion — eliminates the rpcrdma_mr_seg[] array (a 6240-byte per-request structure described as "a relic of when multiple registration strategies existed") in favor of a lightweight 16-byte stack-based rpcrdma_xdr_cursor.

This Week: Regression Discovered

On March 6, Anna Schumaker reported that applying Patch 6/8 broke NFS/RDMA functionality across both iWARP and RoCE transports during cthon testing:

"After this patch I start to see a bunch of errors running cthon tests with both soft iwarp and soft roce." — Anna Schumaker

NFSv3: I/O Errors

With NFSv3 over RDMA, basic operations failed with Input/output error:

mkdir: cannot create directory '/mnt/test/server/nfs3/client.test': Input/output error
basic tests failed

The mount itself succeeded, but subsequent file system operations (such as mkdir) returned I/O errors, indicating a breakdown in the RDMA read/write data path.

NFSv4.2: Mount Failures

With NFSv4.2 over RDMA, the situation was more severe — mounts failed entirely:

mount.nfs: mount system call failed for /mnt/test/server/nfs4.2
Can't mount server:/srv/test/xfs/anna/nfs4.2 on /mnt/test/server/nfs4.2

This suggests the regression affects fundamental RDMA exchange mechanisms, possibly during the initial COMPOUND exchange or memory registration setup.

Schumaker asked for guidance on debugging:

"Is there anything specific I should look at to try to figure out what's going on?" — Anna Schumaker

Developer Response

Chuck Lever acknowledged the regression promptly:

"D'oh! I'll try to track it down." — Chuck Lever

No further debugging details or a revised patch were submitted within this week's window.

Technical Significance

This regression is notable because:

  1. It affects both NFSv3 and NFSv4.2, suggesting the bug lies in the shared RDMA transport layer rather than protocol-specific code.
  2. It manifests on both iWARP and RoCE, indicating the issue is not hardware-driver-specific but rather in the common xprtrdma memory registration or encoding logic.
  3. The patch eliminates a major data structure (rpcrdma_mr_seg[260]) and replaces it with cursor-based iteration over xdr_buf. The regression likely stems from an incorrect translation between the old segment-based accounting and the new cursor approach — possibly in write-list encoding, read-list decoding, or scatter-gather list construction.

Conclusion

The discussion this week is centered on a bug fix scenario: Patch 6/8 introduced a regression that broke NFS/RDMA client functionality. The series remains in flux, with a v3 expected once Lever identifies and resolves the root cause. The broader goal of the series — hardening xprtrdma for nconnect scalability while modernizing memory registration — remains important for NFS client performance, but the regression underscores the risk inherent in refactoring core transport-layer data structures.
