NFSv4 ACL Passthrough: Hellwig NAKs, Lever Conditionally Accepts Clean Implementation

Overview

This week's activity on Mike Snitzer's RFC PATCH v2 series for NFSv4 ACL passthrough in re-export scenarios [id://20260224192438.25351-1-snitzer@kernel.org] saw a significant escalation with the entry of kernel maintainer Christoph Hellwig, who issued a strong NAK on the entire approach. The discussion then evolved into a tripartite debate between Hellwig (opposing any kernel-level ACL passthrough), Trond Myklebust (defending the necessity of the feature for Hammerspace's re-export use case), and Chuck Lever (conditionally willing to accept an upstream merge if implemented cleanly).

This is a discussion about a bug fix / protocol compliance issue in NFSD: the lossy mapping of NFSv4 ACLs to POSIX ACLs breaks NFSv4 re-export scenarios. The proposed solution is a new feature (ACL passthrough) to address this deficiency.

Prior Context

Last week, Chuck Lever issued a detailed architectural critique of Snitzer's prototype, NACKing the addition of .setacl/.getacl operations to export_operations and calling for proper native DACL/SACL support in NFSD as a prerequisite. The series remained in RFC status with no consensus.

Key Technical Arguments This Week

Christoph Hellwig's Strong Opposition

Christoph Hellwig entered the thread with an unequivocal rejection of the entire approach:

"NAK on this whole thing. Linux does not support NFSv4 ACLs for pretty good reasons. If you want to add it you'd have to do it properly (even if that is a bad idea in my opinion). But adding a weird special case for passthrough is a no-go." [id://abAb8NYJECfXkRLg@infradead.org]

Hellwig argued that the kernel should not be burdened with this protocol-level passthrough functionality, suggesting instead:

"If you want to pass in the protocol do it in userspace without burdening the kernel with it." [id://abAb8NYJECfXkRLg@infradead.org]

Trond Myklebust's Defense of Necessity

Linux NFS client maintainer Trond Myklebust countered by explaining that Linux knfsd already "pretends" to support NFSv4 ACLs through a lossy mapping to POSIX-style ACLs, which creates real problems in re-export scenarios:

"Like it or not, Linux knfsd does pretend to support NFSv4 ACLs. It does so by using a (lossy!) mapping to try to convert the NFSv4 ACL into a POSIX style ACL. This is a problem when you're re-exporting NFSv4, as we need to do, because at best it mangles your ACL. At worst, it throws random error codes back at the client." [id://1c630798e0c931310f86f636abe84a72b86f7aae.camel@kernel.org]

Myklebust stated that Hammerspace requires this passthrough capability for re-exports to function correctly, and offered an ultimatum:

"If the upstream community is unwilling to take patches to address the issue, then we're quite happy to maintain the code separately. It will still be available to those who need it through our github site." [id://1c630798e0c931310f86f636abe84a72b86f7aae.camel@kernel.org]

Hellwig responded favorably to the out-of-tree option:

"For something so special purpose I think that is the better way. Having it publically available in this case would be very helpful in the case someone ever needs it, so thanks for that." [id://abAxp5ulzweVS7sb@infradead.org]

Chuck Lever's Conditional Acceptance and Broader Concerns

Chuck Lever intervened to push back against the notion that this is merely a niche Hammerspace concern. He acknowledged the technical validity of the problem:

"I recognize the need to avoid ACE mapping when re-exporting NFSv4. This is an issue specifically for NFSD (which remaps NFSv4 ACLs to POSIX ACLS) and NFSv4 re-export." [id://caf43aae-e08a-423c-bc32-04acac9d20a4@oracle.com]

Lever reaffirmed his willingness to merge a properly implemented solution:

"I will accept a clean implementation of that for merge, and I've already pointed out where the prototype implementation can be improved." [id://caf43aae-e08a-423c-bc32-04acac9d20a4@oracle.com]

However, Lever raised significant concerns about the long-term maintainability of Hammerspace's contribution patterns. He argued that NFSv4 re-export is not exclusive to Hammerspace and that keeping this fix out-of-tree would harm the broader community:

"My experience is that Hammerspace is not the only consumer of NFSv4 re-export, so I regard the issue as a shortcoming of the current NFSD NFSv4 ACL implementation that will have broader impact than one storage vendor. Thus I feel that having Hammerspace maintain this feature separately will in the end not be good for the community -- it should be merged upstream if it can be." [id://124af63a-b7a2-4c37-adc1-f3a07c10acec@app.fastmail.com]

Lever also reiterated his preference for implementing FATTR4_DACL and FATTR4_SACL as full-fledged NFSD features rather than solely for re-export, which would enable proper CI testing via pynfs without requiring a re-export setup:

"Where I have trouble generally with Hammerspace's contributions is that they do tend towards the niche, and frequently they are presented here without consideration for how the community will test, support, and maintain them in the long run. The proposed features are often complex and they will have real ongoing costs for us." [id://124af63a-b7a2-4c37-adc1-f3a07c10acec@app.fastmail.com]

Evolution of the Discussion

The thread progressed through three distinct phases this week:

  1. Hellwig's NAK: A principled objection to adding any NFSv4 ACL passthrough mechanism to the kernel, advocating for userspace handling instead.
  2. Myklebust's counter and out-of-tree offer: A defense of the technical necessity of the feature, coupled with a willingness to maintain it externally if upstream acceptance proves impossible.
  3. Lever's intervention: A pushback against the out-of-tree solution on community grounds, reaffirming conditional upstream acceptance while raising broader concerns about contribution patterns and testability.

Final Conclusions

The discussion ended without a definitive resolution but with clarified positions:

  • Christoph Hellwig remains firmly opposed to any kernel-level NFSv4 ACL passthrough mechanism.
  • Trond Myklebust has offered to maintain the code out-of-tree if upstream acceptance is not forthcoming, while emphasizing that the problem (lossy ACL mapping breaking re-export) is real and impactful.
  • Chuck Lever stands ready to accept a clean implementation upstream, arguing that the issue affects more than just Hammerspace and that an out-of-tree solution would ultimately harm the community. He continues to advocate for implementing DACL/SACL as proper NFSD features with full testability, rather than as a narrow re-export bypass.

The patch series remains in RFC status. The path forward appears to require either (a) Snitzer addressing Lever's architectural concerns from last week to produce a "clean implementation" acceptable for merge, or (b) Hammerspace maintaining the feature out-of-tree despite Lever's objections to that approach.
