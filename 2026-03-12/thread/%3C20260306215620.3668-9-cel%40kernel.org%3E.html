xprtrdma: v3 Series Fixes Races and Refactors Memory Registration for nconnect Scalability

Overview

This week, Chuck Lever submitted [PATCH v3 0/7] "Fix various races in xprtrdma," a seven-patch series addressing subtle race conditions and performance bottlenecks in the NFS/RDMA client transport layer (xprtrdma). The work is driven by testing with the nconnect mount option, which enables multiple RDMA queue pairs (QPs) per NFS mount point to increase IOPS throughput. As Lever explained:

"Utilizing this option increases the IOPS throughput that an NFS mount point is capable of."
— Chuck Lever

However, enabling nconnect also exposed latent concurrency bugs:

"I've found that, as well as enabling much better utilization of fast network fabrics, it surfaces some subtle race conditions that are well-buried when there is only a single QP."
— Chuck Lever

This v3 series replaces the previously rejected v2, which suffered a regression reported by Anna Schumaker last week that broke NFS/RDMA functionality across both iWARP and RoCE transports. The v3 series incorporates fixes for those issues and drops one patch (Eric's) that was already applied.

Classification

This discussion is primarily about bug fixes (race conditions, transport deadlocks, lost wakeups) combined with performance scalability enhancements and a significant structural refactoring of the memory registration path. No new protocol features are introduced.

Key Technical Arguments and Evolution

1. Closing the sendctx get/put Race (Patch 1/7)

The first patch addresses a race between rpcrdma_sendctx_get_locked() and rpcrdma_sendctx_put_locked() that can permanently set XPRT_WRITE_SPACE, blocking all further sends on a transport:

"rpcrdma_sendctx_get_locked() and rpcrdma_sendctx_put_locked() can race in a way that leaves XPRT_WRITE_SPACE set permanently, blocking all further sends on the transport."
— Chuck Lever

The scenario unfolds as follows: a sender reads rb_sc_tail, finds the ring full, and returns -EAGAIN. Meanwhile, a send completion advances rb_sc_tail but observes that WRITE_SPACE is not set, so it does not wake waiters. The sender then sets WRITE_SPACE and returns. When the completion path later tries to wake the next task, it sees WRITE_SPACE already set and skips the wakeup. No new sends can be posted, and no completions arrive to clear the flag — a deadlock.

With nconnect, this is particularly damaging:

"With nconnect, the stalled transport's share of congestion credits are never returned, starving the remaining transports as well."
— Chuck Lever

The fix ensures proper serialization and wakeup behavior in verbs.c.

2. Eliminating a 250 ms Delay on Backlog Wakeup (Patch 2/7)

A prior commit (a721035477fb) changed xprt_rdma_alloc_slot() to set tk_status to -ENOMEM, causing tasks woken from the backlog to sleep for HZ/4 (~250 ms) before retrying. Lever argues this rationale applies only to dynamic allocation under memory pressure, not to the RDMA backlog path where a slot is already waiting:

"a task woken from the backlog has a slot waiting for it, so the 250 ms rpc_delay adds latency without benefit."
— Chuck Lever

The patch reverts to returning -EAGAIN, aligning with existing kernel-doc and reducing unnecessary latency.

3. Closing the Lost-Wakeup Race in Slot Allocation (Patch 3/7)

A second race condition exists between xprt_rdma_alloc_slot() and xprt_rdma_free_slot(): a buffer may be freed after a task finds the pool empty but before it joins the backlog, leaving the task stuck indefinitely:

"A buffer freed after rpcrdma_buffer_get() finds the pool empty but before rpc_sleep_on() places the task on the backlog is returned to the pool with no waiter to wake, leaving the task stuck on the backlog indefinitely."
— Chuck Lever

The fix introduces a post-sleep re-check of the buffer pool and uses xprt_wake_up_backlog() to serialize wakeups properly. It also employs a new helper xprt_add_backlog_noncongested() to avoid ineffective congestion double-checks.

4. Decoupling frwr_wp_create from frwr_map (Patch 4/7)

This patch inlines the write-pad memory registration logic directly into frwr_wp_create, eliminating its dependency on frwr_map. This decoupling simplifies the subsequent removal of rpcrdma_mr_seg from the data-path interface:

"Inlining the registration logic directly ... eliminates the coupling that would otherwise complicate the removal of rpcrdma_mr_seg from frwr_map's interface."
— Chuck Lever

The inlined version also adds a proper error-unwind ladder, improving robustness over the previous approach that relied on teardown-time cleanup.

5. Replacing rpcrdma_mr_seg with xdr_buf Cursor (Patch 5/7)

This is the most significant structural change and the patch that caused the regression in v2. The FRWR registration path previously converted data through three representations: xdr_buf → rpcrdma_mr_seg[] → scatterlist[] → ib_map_mr_sg(). Lever describes the intermediate structure as obsolete:

"The rpcrdma_mr_seg intermediate is a relic of when multiple registration strategies existed (FMR, physical, FRWR). Only FRWR remains, so this indirection and the 6240-byte rl_segments[260] array embedded in each rpcrdma_req serve no purpose."
— Chuck Lever

The patch introduces struct rpcrdma_xdr_cursor to track position within an xdr_buf during iterative MR registration, populating scatterlist entries directly from the xdr_buf regions. This eliminates a large per-request data structure and simplifies boundary logic for non-SG_GAPS devices.

Notably, this patch also fixes a pre-existing bug:

"Fix a pre-existing bug in rpcrdma_encode_write_list where the write-pad statistics accumulator added mr->mr_length from the last data MR rather than the write-pad MR."
— Chuck Lever

The v2 version of this patch broke NFS/RDMA entirely, as reported by Anna Schumaker last week. The v3 version incorporates fixes for that regression (including a corrected tail boundary check in frwr_map, noted in the cover letter).

6. Scaling Receive Batch Size with Credit Window (Patch 6/7)

The fixed RPCRDMA_MAX_RECV_BATCH of 7 caused frequent small ib_post_recv batches during high-rate workloads. Lever replaces this with a per-endpoint value scaled to 25% of the negotiated credit window:

"For a typical 128-credit connection this raises the batch from 7 to 32, reducing doorbell frequency by roughly 4x and amortizing the per-batch atomic and MMIO costs over a larger group of receive WRs."
— Chuck Lever

7. Posting Receive Buffers After RPC Completion (Patch 7/7)

The final patch moves the rpcrdma_post_recvs() call from the CQ poll context to after the RPC has been decoded and completed:

"Every cycle spent refilling the Receive Queue delays delivery of the reply to the NFS layer."
— Chuck Lever

The larger batch size from Patch 6 provides sufficient receive queue headroom to absorb the brief delay before buffers are replenished, making this deferral safe.

Final Conclusions

This v3 series represents a comprehensive hardening of the xprtrdma transport layer for nconnect scalability. The key outcomes are:

  1. Three critical race conditions fixed: The sendctx get/put race, the lost-wakeup race in slot allocation, and the unnecessary 250 ms backlog delay are all addressed, preventing transport deadlocks and starvation under multi-QP configurations.

  2. Memory registration refactored: The elimination of rpcrdma_mr_seg in favor of an xdr_buf cursor reduces per-request memory overhead by approximately 6 KB and simplifies the code path. This patch survived a v2 regression and has been corrected for v3.

  3. Performance enhancements: Receive batch sizing is now adaptive to the credit window, and receive buffer posting is deferred to reduce latency on the reply path. Together, these changes reduce doorbell frequency by roughly 4x and improve cycle efficiency on the critical completion path.

The series touches eight files with a net addition of 305 lines and removal of 174 lines, reflecting both bug fixes and structural simplification. No objections or further discussion were recorded within this week's window; the patches appear to be in good standing for inclusion pending maintainer review.
