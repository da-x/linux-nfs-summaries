NFSD Lock Regression: F_GETLK Misdiagnosis and Revised Fix Direction

Summary

NFSD Lock Regression: F_GETLK Misdiagnosis and Revised Fix Direction

Classification: Bug Fix (NFS Server / lockd Permission Checks)

Bridge from Prior Weeks

This thread, first reported by Tj on February 24, tracks a regression introduced by commit 4cc9b9f2bf4d ("nfsd: refine and rename NFSD_MAY_LOCK"), which caused NFS clients to receive -ENOLCK ("No locks available") when attempting file locking operations on read-only files (e.g., ISO images served via NFSv3). The issue was discovered in production on the Debian openQA infrastructure, where QEMU failed to acquire "consistent read" locks on NFS-mounted disk images.

In prior weeks, Neil Brown argued that the new behavior was technically correct — exclusive fcntl-style locks over NLM require write access by POSIX semantics — and suggested workarounds such as using no_auth_nlm export options or marking devices as read-only. Sasha Levin proposed a patch to restore the permission downgrade in nfsd_permission(), but Neil Brown resisted, contending it would break legitimate lock-denial cases. The discussion appeared stalled until this week's activity.

This Week's Activity: A Critical Misdiagnosis Corrected

Thorsten Leemhuis Presses for Resolution

Thorsten Leemhuis reopened the thread on March 12, asking Jeff Layton for his opinion and emphasizing that this is a confirmed regression requiring resolution:

"But as Neil mentioned, it's a regression, so it must be handled some way. And it looks like this stalled."

He posed two key questions: whether other users would encounter this issue (in which case Linus would expect a fix), or whether the Debian openQA infrastructure could work around it by upgrading QEMU:

"If yes, I'd say Linus expects us to fix this."

Jeff Layton Rejects the Naive Fix and Questions QEMU's Behavior

Jeff Layton responded firmly with a NAK on Sasha Levin's proposed patch:

"Yes. NAK on the patch below. It would break legitimate cases where the lock should be denied. Neil is right not to encourage its use."

He acknowledged the protocol constraint — NLM lacks flock()-style semantics, so exclusive locks require write access — but questioned whether the old behavior was ever correct:

"It may technically be a regression since it worked before, but I'm wondering whether it ever should have."

Layton suggested the no_auth_nlm export option as a workaround and separately wondered if QEMU itself had a bug:

"Why is it opening a file read-only and then taking out an exclusive lock on it? What's the point of denying access to other readers?"

Neil Brown Corrects His Own Diagnosis: It's F_GETLK, Not flock

The pivotal moment came when Neil Brown reversed his earlier analysis. He admitted he had misdiagnosed what QEMU was actually doing:

"It turns out that I mis-diagnosed the problem. i.e. I guess wrong as to what weird thing qemu is doing."

QEMU is not using flock() at all. Instead, it uses fcntl() locking with the F_GETLK or F_OFD_GETLK operation — which tests whether a lock already exists rather than acquiring one:

"qemu isn't using flock(). It is using fcntl() locking but at this point isn't trying to GET a lock, it is testing if a lock already exists. i.e. F_GETLK or F_OFD_GETLK."

Critically, POSIX semantics dictate that F_GETLK does not require write access, even when querying an exclusive lock:

"F_GETLK doesn't require WRITE access, even when getting an exclusive lock. But NFSD does :-)"

This distinction changes the entire framing of the problem. The regression is not about whether exclusive locks should require write access (they do for F_SETLK/F_SETLKW), but rather that NFSD incorrectly demands write permission for a query operation (F_GETLK) that POSIX does not require it to enforce.

Neil Brown concluded:

"So maybe this is the fix that we want."

He included a patch (diff omitted at ingest) targeting the lockd subsystem to correct the permission check for F_GETLK operations.

Key Technical Arguments and Evolution

  1. Initial framing: The regression was understood as a question of whether exclusive locks on read-only files should be permitted over NLM. Neil Brown argued "no" based on POSIX fcntl semantics, while Sasha Levin proposed restoring the old permission downgrade.

  2. Jeff Layton's position: He agreed with Neil Brown that blindly restoring the old behavior would break legitimate lock-denial cases, but acknowledged the regression needed addressing.

  3. The pivot: Neil Brown's self-correction revealed the true root cause — NFSD was requiring write access for F_GETLK (a lock query), not just for F_SETLK (lock acquisition). This is a narrower and more clearly correctable bug than the broader semantic debate about exclusive locks on read-only files.

  4. Fix direction: The proposed fix targets the lockd subsystem to distinguish between lock acquisition (F_SETLK) and lock testing (F_GETLK), ensuring that only the former requires write permission. This aligns with POSIX semantics without undermining legitimate lock-denial cases.

Final Conclusions

  • Bug confirmed and reclassified: The regression is not about whether exclusive locks should require write access (they do for acquisition), but rather that NFSD incorrectly enforces write permission for F_GETLK queries, which POSIX does not require.
  • Fix direction identified: Neil Brown proposed a targeted patch to lockd to correct the permission check for F_GETLK/F_OFD_GETLK operations. This represents a significant shift from the earlier debate about broadly restoring the old behavior.
  • Resolution pending: As of this week's window, the fix has not yet been reviewed or applied. The thread continued beyond March 12 with further discussion and patch iterations (including a [PATCH] lockd: fix TEST handling when not all permissions are available on March 24).
  • Workaround available: Users experiencing this issue can use the no_auth_nlm export option on the NFS server as an interim measure, as suggested by Jeff Layton.
