NFSv4 Client: Directory Leases, atomic_open(), and Lease-Breaking Resolution

Overview

This week the long-running design discussion between Neil Brown and Jeff Layton on the interaction between try_break_deleg(), VFS atomic_open(), and local application leases reached a natural conclusion. The thread is a technical design / potential bug-fix investigation in the NFSv4 client — not a protocol change or a new feature landing this week. No patches were posted; the exchange closed out the open questions raised last week.

Bridge from Prior Week (ending 2026-05-14)

Last week, Brown opened the thread questioning whether atomic_open() should call try_break_deleg() on a directory when a create is pending, and Layton agreed generic VFS code lacked sufficient context to make that decision. The key open threads were: (a) which filesystems actually combine directory leases with ->atomic_open, (b) how the NFSv4 client's local lease handling interacts with delegations, and (c) whether a manpage update documenting the requirement existed. This week resolved all three.

Key Technical Arguments This Week

1. Narrowing the Scope: Which Filesystems Are Actually Affected?

Brown confirmed that neither NFSv4 nor CIFS currently hands out directory leases, correcting his own earlier assumption:

"Oh.... I had thought that I saw that it did. Clearly I was wrong. So at present the only filesystem which supports directory leases and ->atomic_open is gfs2 when 'nolocks' is active and we both agree that is an odd configuration."

Layton then contextualized GFS2's nolocks mode:

"AIUI, 'nolocks' is mostly used with GFS2 in a single-node configuration, so I think it should basically work in that case."

This effectively de-scoped the problem: no production NFSv4 or CIFS deployment is currently exposed to the race where ->atomic_open creates a file without first breaking a directory lease. Brown noted the GFS2/nolocks combination "likely doesn't work as expected and maybe we should discuss fixing it with the gfs2 devs," flagging it as a separate, lower-priority follow-up.

2. Two Proposed Approaches for Future Directory-Lease + atomic_open Support

Brown laid out two architectural options for when (if) directory leases are ever combined with ->atomic_open:

"One approach is to decide that ->atomic_open needs to handle any lease breaking that might be needed. In that case we should document this requirement for atomic_open."

"The other approach is to have the VFS proactively break the lease if a create is expected."

Layton's position, carried over from last week, was that the NFS (or CIFS) client itself would need to revoke the local application's lease, since most servers will not recall a delegation from the very client making the change. Both approaches leave the decision open for future implementers.

3. Manpage Update Location

Brown asked where the promised manpage update was:

"Where can I see the manpage update? It isn't in https://git.kernel.org/pub/scm/docs/man-pages/man-pages/"

Layton pointed to the new F_SETDELEG/F_GETDELEG constants:

"These got new F_SETDELEG/F_GETDELEG constants, so they're in: ./man2const/F_GETDELEG.2const"

This confirms that documentation for delegation-based leases is in progress but has not yet been merged into the main man-pages tree or shipped to distros.

4. NFSv4 Client-Side Lease Handling: Likely Correct, Testing Advised

The most technically significant exchange concerned whether the existing NFSv4 client-side lease implementation is actually broken for intra-client conflicts (one app holds a read lease, another opens the same file for write on the same client). Brown argued it should work correctly:

"I think the local lease handling is enough to break the lease. As long as the NFS client only gives out leases when it holds a delegation, and break them when it loses the delegation (and this is what the code appears to do) then it should all work properly. Testing wouldn't hurt of course."

Layton concurred: "Agreed." This closes the bug-investigation thread without a confirmed defect, but with an implicit recommendation that someone run the test scenario to be certain.

Final Conclusions

Brown provided the thread's definitive wrap-up:

"So the short answer to my original question is that something should break leases when ->atomic_create is called, but it doesn't actually matter for any filesystem at present so we can delay having a firm opinion until someone wants to implement directory leases combined with atomic_open."

The consensus is:

  • No immediate bug fix needed in the NFSv4 client for the atomic_open() + directory lease interaction, because no current filesystem exposes that combination.
  • GFS2/nolocks is a theoretical edge case that may warrant a separate discussion with GFS2 developers but is not urgent.
  • The NFSv4 client's local lease logic appears correct for intra-client conflicts; empirical testing is recommended but not blocking.
  • Documentation (manpage) for F_SETDELEG/F_GETDELEG is in progress and will clarify the expected behavior when directory leases are eventually supported alongside ->atomic_open.

Classification

This is a design discussion with potential bug-fix implications in the NFSv4 client. No patches, protocol changes, or new features were submitted this week. The thread effectively closes, deferring concrete action until a future implementer combines directory leases with ->atomic_open.
