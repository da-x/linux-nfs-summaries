pNFS: Fix use-after-free in pnfs_update_layout() tracepoint ordering

Summary

pNFS: Fix use-after-free in pnfs_update_layout()

Type: Bug fix (memory safety / use-after-free)
Week: 2026-05-15 → 2026-05-21
Status this week: Patch posted; no in-window review or merge activity.

Overview

On Tuesday, 18 May, Wentao Liang (ISCAS) posted a one-line fix to the pNFS client's layout-update path, correcting a use-after-free that occurs when a tracepoint dereferences a layout header that has already been freed. The patch targets fs/nfs/pnfs.c and is marked for stable backports.

The Bug

The problem sits in pnfs_update_layout(). When the code takes the NFS_LAYOUT_RETURN branch, it calls pnfs_prepare_to_retry_layoutget(lo). On success, the original code sequence was:

  1. pnfs_put_layout_hdr(lo) — drops the last reference and may free the layout header.
  2. trace_pnfs_update_layout(...) — still reads fields from lo.

As Liang described in the patch cover letter:

"This results in a use-after-free when the tracepoint accesses lo's fields."

The root cause was introduced by commit 2c8d5fc37fe2 ("pNFS: Stricter ordering of layoutget and layoutreturn"), which re-ordered the put/trace calls in a way that left the tracepoint after the reference drop.

The Fix

The fix is minimal — a single-line reordering that moves trace_pnfs_update_layout() before pnfs_put_layout_hdr(lo), ensuring the tracepoint only reads from a live object:

"Fix this by moving the tracepoint call before pnfs_put_layout_hdr(lo)."

The diff touches exactly one line in fs/nfs/pnfs.c (1 insertion, 1 deletion). The patch carries Cc: stable@vger.kernel.org, indicating the author considers it appropriate for backporting to maintained stable trees.

Discussion So Far

No replies landed within this week's window. A follow-up from Markus Elfring arrived on 23 May (just outside the reporting period), so further review activity may appear in next week's digest.

Significance

While a one-line change, use-after-free bugs in kernel memory management paths are high-severity: they can be exploited for information leaks or privilege escalation under the right conditions. The pNFS layout-update path is exercised on every layout recall/retry cycle, making this bug reachable in real-world multi-client NFS deployments. The fix is low-risk (pure reordering of two adjacent calls) and well-suited for stable backport.
