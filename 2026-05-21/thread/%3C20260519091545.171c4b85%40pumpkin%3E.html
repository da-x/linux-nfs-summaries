netfs: Follow-up discussion on bvecq chain design details

Summary

This thread represents a brief but technically dense follow-up to David Howells' 21-patch series transitioning the network filesystem library (netfslib) from folio_queue to segmented bio_vec[] chains (bvecq). The prior week's summary covered the initial submission and broad feedback. This week, only one message was posted: a detailed reply from David Howells addressing structural concerns raised by reviewer David Laight regarding the struct bvecq design.

This is an infrastructure feature/refactoring discussion with implications for NFS, AFS, and CIFS clients, rather than a specific bug fix. However, the changes aim to reduce complexity and potential bugs in buffered I/O paths shared by all network filesystems.

Key Technical Arguments

David Laight had previously questioned several aspects of the bvecq structure, including the use of bitfields, the necessity of a backward (prev) pointer, and the type used for file position tracking. In his reply on May 19, Howells addressed each point:

Memory Layout and Bitfields

Laight noted that "There is a massive hole here anyway" in the structure's memory layout. Howells clarified the actual footprint:

"On a 64-bit machine, the whole thing fits into 48 bytes - 6 words (or 3 bio_vec slots). next, prev, fpos, bv and ref+priv take up 5 of those words; nr_segs and max_segs take up half of the 6th, leaving a 4 byte hole."

He conceded that Laight was right about the bitfields:

"You're right, though, I could make them all non-bitfields as the enum is marked mode(byte)."

Backward Traversal (prev pointer)

Laight asked whether backward traversal of the segment list was ever necessary. Howells acknowledged the desire to eliminate it:

"iov_iter_revert() exists, unfortunately, but yes, I would like to avoid having a prev pointer."

He indicated that ideas exist to remove the prev pointer or at least store the start in struct iov_iter and always work forwards, though he had not yet implemented them.

File Position Tracking (fpos)

Laight suggested using off_t or u64 for the file position field rather than long long. Howells corrected the type usage:

"It's not 'long long' and off_t is actually 'long' in asm-generic. Actually, I should probably switch to using uoff_t. Note that this file position should never be seen as negative; I think loff_t should only really be used in llseek."

Rationale for File Position in the Chain

Laight admitted, "At this point you lose me :-)" regarding the discontiguity and file position semantics. Howells apologized and provided a more coherent explanation of why file position tracking is embedded directly in the bvecq chain rather than derived from folios:

  1. Unified buffered and DIO writeback: "I can treat buffered writeback and DIO write more similarly if there's no requirement to access the folios in the list to get file position information."
  2. Efficient cleanup: "When cleaning up lists of folios in buffered writeback, the file position is needed to access the i_pages xarray in order to clean up the marks on it. This means I don't need to go from my list to access each folio, but can look them up through the xarray instead."
  3. Sparse writes for network filesystems: "Some network filesystems, e.g. ceph, allow discontiguous (sparse) writes to be made to the server in a single RPC operation. This gives a means to convey that information to them, but then allows the data to be conveyed in a single blob to the socket (the mapping between blob offsets and file regions is tabulated separately within the RPC call)."

He also clarified that network filesystems typically do not require block-size alignment:

"Network filesystems don't typically require any block alignment, doing RMW locally on the server. I should really have separated that from the discontiguity bit."

Impact on NFS Client Development

While this thread does not introduce new patches, it clarifies design decisions in the bvecq infrastructure that will directly affect the NFS client:

  • Cachefiles integration: The file position tracking enables more efficient cache cleanup and lookup via the xarray, benefiting NFS clients using fscache/cachefiles for page caching.
  • TCP send efficiency: The broader series aims to enable single-call kernel_sendmsg() for entire RPC messages, improving NFS over TCP performance by eliminating socket corking overhead.
  • Sparse write support: Although Howells cited Ceph as the primary beneficiary of discontiguous write support, the infrastructure is shared across netfslib and could benefit NFS clients in scenarios where servers support sparse or non-contiguous writes.

Final Conclusions

This week's activity was limited to a single design clarification message from David Howells. No new patches were submitted, and no critical bugs were fixed. The discussion refined the understanding of bvecq internals, particularly around memory layout, traversal semantics, and file position tracking. Howells acknowledged several points for improvement in future iterations (removing bitfields, potentially eliminating the prev pointer, switching to uoff_t).

The broader 21-patch series remains under review, with minor stylistic feedback from Stefan Metzmacher regarding CIFS commit messages also pending resolution. The infrastructure changes represent a significant step toward unifying I/O buffer management across network filesystems, with NFS clients expected to benefit from improved performance and reduced code complexity.
