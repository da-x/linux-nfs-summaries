SUNRPC: Fix xdr_buf_to_bvec() bio_vec array overflow (2-patch hardening)

Summary

SUNRPC: Fix xdr_buf_to_bvec() bio_vec array overflow

Type: Bug fix / hardening (NFS server-side, SUNRPC layer) Week ending: 2026-05-21 Status this week: Patches posted and both received Reviewed-by from Jeff Layton; no further discussion in the window.

Overview

On Tuesday 2026-05-19, Oracle's Chuck Lever posted a two-patch series titled [PATCH 0/2] SUNRPC: Fix xdr_buf_to_bvec() bio_vec array overflow](https://lore.kernel.org/linux-nfs/20260519-xdr-buf-to-bvec-fix-v1-0-1c9decbd4466@oracle.com/) targeting a latent out-of-bounds write in the kernel's XDR-to-bio_vec conversion helper, xdr_buf_to_bvec(). The function sits on the NFS server's WRITE-decode and TCP/UDP send hot paths, so even though the bug is not currently reachable from a remote client, it represents a serious hardening gap.

The technical problem

In the cover letter, Lever frames the issue precisely:

"xdr_buf_to_bvec() lives on the NFS server's WRITE-decode and TCP/UDP send hot paths, and the array it writes into is sized exactly to the budget the caller passes -- no slack."

He identifies two halves of the same overflow hazard:

  1. Store-before-check: The head, page-loop, and tail branches write a bio_vec slot before testing whether that slot is in range. When the budget is exactly consumed, the next store lands one element past the end of the array.
  2. Silent short return on overflow: The overflow label returns a foreshortened slot count rather than failing. Callers feed that count into iov_iter_bvec() with the original byte length, and because iterate_bvec() walks by byte count, "the bvec pointer steps past nr_segs into adjacent slab and dereferences it as bv_page/bv_offset/bv_len, handing the result to sock_sendmsg() or the file's iter_write path."

The second patch's description makes the client-visible consequence explicit:

"For an NFS WRITE the server reports the truncated transfer to the client as full success."

Why this is hardening, not a confirmed regression fix

Lever is careful to note that the current in-tree callers all size their bvec arrays via svc_serv_maxpages(), whose formula "reserves slack above the maximum decoded-WRITE footprint." So:

"a WRITE payload extracted from rq_arg by xdr_stream_subsegment() therefore fits within the budget that nfsd_vfs_write() passes, and the overflow path is not reachable from a remote NFS WRITE today."

However, because xdr_buf_to_bvec() has been EXPORT_SYMBOL_GPL since commit 62bf165c04bf, the bound also covers any future caller that does not replicate the same accounting. The issue was reported by Chris Mason (Meta) and carries a Fixes: tag pointing at 2eb2b9358181 ("SUNRPC: Convert svc_tcp_sendmsg to use bio_vecs directly").

Patch-by-patch breakdown

PATCH 1/2 — Bound-check before writing

Bound-check xdr_buf_to_bvec() stores before writing reorders the in-range check ahead of the store in all three branches (head, page-loop, tail). With the check at the top, count is incremented only after a successful store, so the overflow label can return count directly. This patch is deliberately self-contained with no API change, making it safe for stable-tree backport.

PATCH 2/2 — Return -ESERVERFAULT on overflow

Return an error from xdr_buf_to_bvec() on overflow changes the function signature to return a signed int, with the overflow label now returning -ESERVERFAULT. The three callers are updated:

  • nfsd_vfs_write() folds the error into host_err, which nfserrno() translates to nfserr_serverfault for the WRITE reply.
  • svc_udp_sendto() and svc_tcp_sendmsg() propagate the error out of the send path.

Lever explains the rationale: "The overflow represents an internal invariant violation: a higher layer reserved a bvec budget too small for the xdr_buf it then asked the encoder to convert. That is a server-side fault, not a media I/O failure and not a malformed client argument." He also notes the signature change "is not appropriate for stable trees," which is why it was split from the first patch.

Adjacent hazard deliberately left alone

Lever flags one related concern he chose not to fix: svc_tcp_sendmsg() passes rqstp->rq_maxpages as the budget for a write into svsk->sk_bvec, which is sized at socket creation. Static analysis flagged the two snapshots as a potential divergence if sv_max_mesg changes mid-flight. However, "in current code sv_max_mesg has exactly one writer (__svc_create()) and is never mutated thereafter, so the values cannot diverge." After this series, any future breakage of that invariant would surface loudly via -ESERVERFAULT.

Review and outcome

Jeff Layton (Red Hat) reviewed both patches within hours of posting:

  • Reviewed-by on PATCH 1/2 at 13:54 UTC (~20 minutes after posting)
  • Reviewed-by on PATCH 2/2 at 16:38 UTC

No objections, design debates, or alternative approaches were raised. The thread closed cleanly with both patches carrying a Reviewed-by tag, positioning them for merge into the mainline and (for patch 1) backport to stable trees.

Significance for NFS development

This is a textbook example of proactive hardening in the NFS server stack: a latent OOB write identified through static analysis (reported by Chris Mason at Meta), carefully split into a backportable bounds-check fix and a forward-looking API change, with clear documentation of why the bug is not currently exploitable from the network. The two-patch structure ensures stable trees get the critical memory-safety fix without the signature churn, while mainline gains the louder error path that will catch any future budget-accounting mistakes.
