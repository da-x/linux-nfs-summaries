xprtrdma: Decouple RPC completion from Send completion — bug fix lands with build errors, v2 expected

Summary

xprtrdma: Decoupling RPC Completion from Send Completion

Overview

This week's thread centers on a bug fix (with significant performance implications) for the xprtrdma transport in the Linux NFS client. Chuck Lever posted a patch on May 20 that restructures how request lifetimes are managed in the RDMA-based RPC transport, and by end of day May 21 the kernel test robot had flagged build errors, prompting Chuck to announce a v2 is forthcoming.

The Bug

The core issue is a use-after-free / data-corruption hazard in xprtrdma. As Lever described in the patch cover letter:

"rl_kref currently coordinates RPC completion with both the Send carrying an RPC Call and the Receive carrying its reply. The kref_get in the marshal path is conditional on sc_unmap_count, so a Send carrying only pre-registered buffers takes no Send-side reference. When the Reply then arrives before the Send completes, rpcrdma_reply_handler() drops the kref from 1 to 0, freeing the req for reuse while the HCA may still be DMA-reading from its send buffer. A retransmission can put different data on the wire."

In other words: if a reply arrives before the RDMA Send completion fires (a race that is entirely possible with unsignaled Sends), the request structure could be recycled and overwritten while the hardware was still reading from it. This is a classic DMA lifetime bug with real-world consequences — silently corrupted RPC data on the wire.

The patch carries a Fixes: tag pointing to commit 0ab115237025 ("xprtrdma: Wake RPCs directly in rpcrdma_wc_send path"), indicating this regression was introduced when the wake-up logic was moved into the Send completion path.

The Fix — Architectural Rework

The fix is not a one-liner; it's a rethinking of the reference-counting model:

  1. Decouple the two lifetimes. The Receive path now completes the RPC immediately without touching rl_kref. The refcount gates request recycling (return to rb_send_bufs), not RPC completion.

  2. Two explicit owners. An rpc_rqst holds one reference; rpcrdma_prepare_send_sges() takes a second for the prepared Send. Both must release before the req is recycled.

  3. Preserve unsignaled batching. Lever explicitly rejected the naïve fix:

    "Forcing a kref_get on every Send is not viable: xprtrdma leaves most Sends unsignaled, relying on the strong ordering of Send completions to limit interrupt rate."

    Unconditionally gating RPC completion on Send completion would deadlock NFS callers waiting on an RPC whose Send completion never fires.

  4. Teardown drain. Because Send-side references can now outlive RPC completion, rpcrdma_sendctxs_destroy() walks the active ring range and calls rpcrdma_sendctx_unmap() on each entry to release held krefs before freeing the ring.

  5. Buffer headroom. To avoid regressing effective concurrency: "Allocate one-eighth more reqs than max_reqs so the transport does not regress the effective concurrency advertised by the SUNRPC slot table."

  6. Performance win. The patch removes a cache-cold atomic kref_put from the hot reply path and eliminates the now-obsolete reply_waits_for_send counter. Lever notes this "brings xprtrdma into alignment with the two other in-kernel RDMA ULPs that batch Sends into groups where only one is signaled."

The patch touches six files under net/sunrpc/xprtrdma/ with 93 insertions and 36 deletions.

Build Failures and v2

Within hours of posting, the kernel test robot reported build errors on nios2-randconfig (GCC 8.5.0) and a second report on riscv with clang 23. Both flagged the same issue: in rpcrdma_req_release(), the code references xprt->bc_pa_lock, rqst->rq_bc_pa_list, and xprt->bc_pa_list — members that do not exist in struct rpc_xprt / struct rpc_rqst on the tested trees. This appears to be a stale reference to backchannel preallocation infrastructure that has since been removed or renamed upstream.

Chuck acknowledged the situation succinctly in his reply:

"Bots and LLM review have found issues with this patch, so expect a v2."

Significance for NFS Client Development

This is an important fix for NFS-over-RDMA deployments. The bug could silently corrupt RPC data in production environments using RDMA transports (common in high-performance storage clusters). The architectural change also improves the hot path by removing an atomic operation from every reply, and aligns xprtrdma with the design patterns used by other in-kernel RDMA ULPs. The v2 is expected to address the build errors around the removed backchannel preallocation fields while preserving the core decoupling logic.
