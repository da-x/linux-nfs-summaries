NFSD fixes for v7.1-rc merged into mainline

Summary

This thread is short and procedural: a single GIT PULL request from NFS server maintainer Chuck Lever, followed hours later by an automated confirmation from the kernel's pr-tracker-bot that the pull was merged into torvalds/linux.git. There is no technical debate in this thread — it is the formal record of a batch of bug fixes landing in the v7.1-rc cycle for the NFSD (NFS server) and its underlying sunrpc infrastructure.

The pull request itself is worth dissecting, because the commit list reveals where the NFS server team's attention has been focused during the rc period: delegated attribute correctness, layout state revocation, the new sunrpc cache netlink protocol, and CB_GETATTR change detection.

The Pull Request

In the pull message, Chuck Lever framed the batch in two buckets:

"Issues reported with v7.1-rc:

  • Correctness fix for the new sunrpc cache netlink protocol"

"Issues that need expedient stable backports:

  • Correctness fixes for delegated attributes
  • Prevent an infinite loop when revoking layouts"

The tag nfsd-7.1-1 is based on commit d644a698de12e996778657f65a4608299368e138 ("NFSD: Docs: clean up pnfs server timeout docs", 2026-04-03) and brings in six commits up to 4f8ef58c10bfe5f86a643c7c8331b37e69e3dae1 ("NFSD: Fix infinite loop in layout state revocation", 2026-05-10). The diffstat is modest but touches the heart of NFSv4 state management:

The Six Commits, by Author

Chuck Lever (1) — NFSD: Fix infinite loop in layout state revocation The head commit and the most severe bug in the batch. An infinite loop during layout state revocation is a classic NFSv4.1 pNFS hazard: if the server cannot make forward progress while reclaiming or revoking layouts, it can hang indefinitely, blocking other clients' operations on the same export. Lever flagged this as needing an "expedient stable backport," underscoring its production impact.

Jeff Layton (1) — sunrpc: start cache request seqno at 1 to fix netlink GET_REQS A one-line correctness fix in net/sunrpc/cache.c (the 2 +- line in the diffstat). The new sunrpc cache netlink protocol introduced in this cycle had a subtle off-by-one: starting the sequence number at 0 instead of 1 broke the GET_REQS netlink operation. Layton's fix is small but important for any userspace tooling that relies on the new netlink interface to inspect the sunrpc cache.

Olga Kornievskaia (3) — delegated attribute correctness Three fixes, all in the delegation machinery:

  • nfsd: fix GET_DIR_DELEGATION when VFS leases are disabled — directory delegations were not being handled correctly when the underlying filesystem did not support VFS leases.
  • nfsd: update mtime/ctime on CLONE in presence of delegated attributes — the new NFSv4.2 CLONE operation was not updating timestamps when the source file had delegated attributes, leading to stale metadata.
  • nfsd: update mtime/ctime on COPY in presence of delegated attributes — the same class of bug for the COPY operation.

These three together paint a picture of the delegation subsystem needing attention as new NFSv4.2 operations (CLONE, COPY) interact with pre-existing delegation semantics. The +64/-... churn in fs/nfsd/nfs4state.c is largely attributable to these fixes.

Scott Mayhew (1) — nfsd: fix file change detection in CB_GETATTR A fix for the server's ability to detect that a file has changed when responding to a client's CB_GETATTR callback. Incorrect change detection can cause clients to operate on stale cached data, violating NFSv4 consistency guarantees.

Relevance to NFS Client Development

While this is formally an NFSD (server-side) pull, the fixes have direct implications for NFS clients:

  • Delegated attribute fixes (Kornievskaia): Clients that hold delegations on files being CLONE'd or COPY'd by other clients would previously observe stale mtime/ctime values. The server-side fix ensures that when a delegation is broken and attributes are re-evaluated, the timestamps reflect the new operation. This is critical for client-side caching correctness.
  • CB_GETATTR change detection (Mayhew): Clients rely on accurate change attribute reporting to decide whether their cached data is still valid. A server that fails to detect changes will send incorrect CB_GETATTR responses, causing clients to serve stale data.
  • Layout revocation infinite loop (Lever): pNFS clients depend on the server completing layout state transitions in a timely manner. An infinite loop here would effectively hang all pNFS I/O on the affected export, a severe availability issue for client workloads.
  • sunrpc cache netlink (Layton): While primarily a server/infrastructure fix, the sunrpc layer is shared between NFS clients and servers. The netlink protocol fix ensures that diagnostic tooling works correctly on any system running the kernel's RPC subsystem.

Final Conclusions

  • This thread documents a bug-fix pull request, not a new feature or protocol change.
  • All six commits were merged into mainline within hours of the pull request, with no objections or discussion.
  • The fixes span delegation correctness, pNFS layout state management, the new sunrpc cache netlink interface, and callback-based change detection — collectively addressing the most pressing issues reported during the v7.1-rc period.
  • Three of the six commits are flagged for expedient stable backports, indicating they address bugs that affect production NFS deployments.
  • For NFS client developers, the delegation and CB_GETATTR fixes are particularly relevant, as they directly affect the correctness of client-side caching and data consistency guarantees.
