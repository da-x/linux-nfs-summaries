rpcbind: Three Memory Leak Fixes Identified by Valgrind

Overview

On May 21, Red Hat's Scott Mayhew posted a compact three-patch series to the linux-nfs list addressing memory leaks in the rpcbind daemon — the user-space service that maps RPC program numbers to network addresses and is a critical dependency for NFS clients and servers. The patches are straightforward bug fixes (not new features or protocol changes), each accompanied by valgrind output demonstrating the leak.

"Fix a handful of leaks reported by valgrind." — Scott Mayhew, cover letter

The series touches three files (src/rpcbind.c, src/util.c, src/warmstart.c) with a combined addition of just 10 lines — a testament to how surgical these fixes are.

Patch-by-Patch Breakdown

Patch 1/3: Memory leak in init_transport()

"Once a service registration has been added to list_rbl via rbllist_add(), we no longer need the value stored in taddr.addr.buf. Free it before we leave init_transport()." — Scott Mayhew

The valgrind trace shows a 19-byte definite loss in init_transport.isra.0 at rpcbind.c:726. The fix adds a free() call for the transport address buffer after it has been consumed by the registration list, preventing a small but persistent leak each time a service is registered.

Patch 2/3: Memory leaks in network_init()

This patch addresses two distinct leaks in the network initialization path:

  1. getaddrinfo() result not freed before reuse:

    "Before reusing res in another getaddrinfo() call, we need to free the previous value stored there." — Scott Mayhew

    Valgrind reported 128 bytes (64 direct, 64 indirect) definitely lost in generate_addrinfo → gaih_inet → getaddrinfo, called from network_init at util.c:316.

  2. getifaddrs() not paired with freeifaddrs():

    "getifaddrs() needs to be paired with freeifaddrs()." — Scott Mayhew

    This one leaked 1,296 bytes via calloc in getifaddrs_internal, called from network_init at util.c:347.

Both are classic resource-management oversights that accumulate over the daemon's lifetime, particularly relevant for long-running rpcbind instances on NFS servers.

Patch 3/3: Memory leak in read_warmstart()

"struct rpcblist contains a struct rpcb, which has pointers to 3 strings. We need to free those before freeing the struct rpcblist or we leak memory." — Scott Mayhew

The valgrind trace shows 56 bytes in 12 blocks lost through the XDR decoding path (xdr_string → xdr_rpcb → xdr_reference → xdr_rpcblist_ptr), called from read_struct at warmstart.c:122. This leak occurs when rpcbind reads its warmstart file at startup to restore previously registered services.

Discussion and Outcome

Within the current week's window, no replies or review comments were posted — the thread consisted solely of Mayhew's four messages (cover letter + three patches). However, looking just beyond the window, NFS maintainer Steve Dickson confirmed on May 27 that the series was accepted:

"Committed...(tag: rpcbind-1_2_9-rc1)" — Steve Dickson

The patches landed in the rpcbind 1.2.9-rc1 release cycle, indicating they were considered low-risk and appropriate for a stable release candidate.

Significance for NFS Ecosystem

While rpcbind is user-space rather than kernel code, it sits squarely on the critical path for every NFS mount operation. Memory leaks in a long-running daemon like rpcbind can degrade system performance over time, especially on heavily utilized NFS servers where services are frequently registered and unregistered. These fixes, though small, improve the robustness of the entire NFS stack by ensuring that the portmapper does not silently consume memory across its lifetime.
