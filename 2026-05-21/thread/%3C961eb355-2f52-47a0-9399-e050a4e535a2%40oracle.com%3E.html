XFS pNFS LAYOUTGET: Extent merge mechanics and v2 patch finalization

Summary

XFS pNFS LAYOUTGET: Extent Merge Mechanics and Locking Scrutiny in v2 Patch Planning

Classification

This thread concerns a bug fix for overlapping extents returned by XFS during pNFS LAYOUTGET operations. The issue causes ambiguity for NFS clients when selecting device layouts and managing data states. This week's messages (May 19) represent the final exchanges in this thread, where Dai Ngo provided a detailed mechanical explanation of how extent merging produces overlaps, and Darrick J. Wong raised three targeted review questions that shaped the v2 patch plan.

Bridging Prior Weeks

As summarized in prior weeks, Dai Ngo's original patch proposed replacing the XFS_BMAPI_ENTIRE flag with 0 in xfs_fs_map_blocks() to prevent overlapping extents when multiple calls are made within a single LAYOUTGET request. Christoph Hellwig identified both the core overlap bug and a separate race condition in the NFS server code where layouts are inserted only after calling into ->proc_layoutget. Over May 15–20, Darrick J. Wong raised three specific review questions on locking adequacy, multi-map API design, and reflink/realtime inode check placement; Christoph Hellwig responded affirmatively to each concern; and Dai Ngo outlined a pragmatic path forward for v2.

This Week's Activity (May 19)

Darrick J. Wong's Three-Point Review

Darrick J. Wong, acknowledging his limited familiarity with NFS layouts ("/me has no idea about nfs layouts but has thoughts anyway :)"), posed three incisive questions in his May 19 message:

  1. Locking adequacy: xfs_fs_map_blocks() only takes i_rwsem and XFS_ILOCK, not the mmap invalidation lock. Could page faults interfere with layout construction? He hypothesized:

    "I think the race that Christoph is referring to here is that any other thread can wander in and change the mapping after a ->map_blocks call returns, because nfs isn't holding any kind of lock on the inode"

  2. Multi-map API: With NFS now capable of serving multiple mappings at once, should ->map_blocks accept an array element count to return multiple iomaps in a single lock cycle?

  3. Reflink/realtime checks: Do reflink and realtime inode checks need re-assessment after acquiring the inode lock, since these properties can change concurrently?

Dai Ngo's Mechanical Explanation of the Overlap Bug

Dai Ngo responded on May 19 with a detailed step-by-step walkthrough of how the overlap bug manifests, confirming Darrick's race hypothesis:

"I think this is what happened."

He illustrated the scenario using a file with three segments:

  • 0000-4095: IOMAP_UNWRITTEN (preallocated)
  • 4096-8191: IOMAP_HOLE (no block allocated)
  • 8192-12287: IOMAP_UNWRITTEN (preallocated)

With XFS_BMAPI_ENTIRE set and nimaps limited to 1, three successive calls from nfsd produced the following sequence:

  1. First call (offset 0, length 12288): Returns the first unwritten extent at offset 0, length 4096.
  2. Second call (offset 4096, length 8192): Allocates a new unwritten extent to fill the hole at 4096. This allocation causes the three segments to merge into a single contiguous extent (br_startoff = 0, br_blockcount = 3).
  3. Third call (offset 8192, length 4096): Looks up the range starting at 8192 and finds the merged single extent. Because XFS_BMAPI_ENTIRE is set, xfs_bmapi_trim_map() bypasses trimming and returns the full extent:

    "Because XFS_BMAPI_ENTIRE is set, xfs_bmapi_trim_map() bypasses trimming and returns the full extent to xfs_bmbt_to_iomap()."

The result: the third call returns an extent spanning offset 0–12287, which overlaps with the extents returned by the first two calls. This explains why removing XFS_BMAPI_ENTIRE (replacing it with 0) resolves the issue — without the flag, trimming occurs and only the requested subrange is returned.

Final Conclusions

This week's exchange solidified the technical understanding of the bug and reinforced the v2 patch plan agreed upon in prior days:

  1. Core fix: Replace XFS_BMAPI_ENTIRE with 0 in xfs_fs_map_blocks() to prevent overlapping extents — now fully explained by Dai Ngo's mechanical walkthrough.
  2. Locking improvements: Move reflink and realtime inode checks inside the inode lock, as these properties can change concurrently.
  3. Deferred work: Multi-map API enhancements (returning multiple iomaps in a single call) are acknowledged as desirable but deferred to future coordinated changes between nfsd and XFS.

Implications for NFS Client Development

The fix has direct relevance for NFS client robustness. As Christoph Hellwig noted in prior weeks:

"And the client should probably also validate that extents of the same kind do not overlap (read vs write extents are allowed to overlap)."

With the server-side fix progressing toward v2, clients will encounter fewer malformed LAYOUTGET responses. However, defensive validation on the client side remains advisable as a belt-and-suspenders approach against future regressions or edge cases. Dai Ngo's detailed explanation of how extent merging produces overlaps provides valuable context for client developers who may need to handle similar scenarios in their layout processing code.
