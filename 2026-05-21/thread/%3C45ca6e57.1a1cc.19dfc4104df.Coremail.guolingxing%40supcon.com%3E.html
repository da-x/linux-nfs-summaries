Rick Macklem flags "soft" mount as likely culprit in nfs4_drain_slot_tbl hang

Summary

NFSv4.1 Client Hang in nfs4_drain_slot_tbl — Soft Mount Warning

This Week's Activity (2026-05-15 → 2026-05-21)

The thread saw a single but significant contribution this week: a reply from Rick Macklem on May 16, offering a key diagnostic insight into the reported hang.

The Key Technical Observation

Rick Macklem, long-time maintainer of the Linux NFS client, identified the reporter's use of the soft mount option as a probable root cause of the nfs4_drain_slot_tbl hang:

"Just fyi, 'soft' mounts are often going to be troublesome for NFSv4.1. (Whenever an RPC times out and doesn't wait for a reply from the server, it will leave a session slot messed up.)"

This is a critical observation because it connects two otherwise separate subsystems:

  1. RPC timeout handling with soft mounts: When an RPC call times out on a soft mount, the client does not block indefinitely waiting for a server reply. Instead, it returns an error to the caller and moves on.
  2. NFSv4.1 session slot table management: NFSv4.1 uses a slot table to track in-flight requests within a session. Each request occupies a slot until the server's reply is received and the slot is released. If an RPC times out and the client gives up without receiving the reply, the corresponding session slot remains occupied (or in an inconsistent state).

The combination means that under concurrent workload against a Windows NFS server (which may have different timing or response characteristics than a Linux server), timed-out soft-mount requests can leave slots stuck. When nfs4_drain_slot_tbl is later invoked—typically during session recovery, reconnection, or teardown—it attempts to drain (wait for) all in-flight slots. If some slots are permanently stuck due to the soft-mount timeout behavior, the drain operation hangs indefinitely.

Significance for NFS Client Development

This is a bug fix / interoperability discussion. While no patch has been proposed yet, Rick's comment points toward a well-known tension in the Linux NFS client between:

  • The soft mount semantics (inherited from NFSv2/v3) which prioritize returning errors over blocking, and
  • The NFSv4.1 session/slot table design which assumes that every sent request will eventually receive a reply so that slots can be properly released.

This tension is particularly acute when talking to non-Linux servers (here, Windows), whose RPC timing behavior may differ. The practical implication for the reporter is to try hard mount options (the default) and see if the hang disappears, which would confirm the diagnosis. For the client codebase, this highlights a potential robustness gap in how nfs4_drain_slot_tbl handles slots that were orphaned by soft-mount timeouts—a scenario that could be hardened with slot timeout/reclamation logic.
