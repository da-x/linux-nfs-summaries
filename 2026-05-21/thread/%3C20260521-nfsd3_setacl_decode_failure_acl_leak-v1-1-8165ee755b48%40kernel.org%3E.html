nfsd: posix_acl leak fix on SETACL decode failure

Summary

nfsd: posix_acl leak fix on SETACL decode failure

Type: Bug fix (memory leak in NFSv2/NFSv3 server-side ACL handling)

Overview

On Thursday, May 21, Jeff Layton posted a one-patch series fixing a long-standing memory leak in the Linux NFS server (nfsd) that could cause posix_acl objects to be orphaned for the lifetime of the server whenever a SETACL request failed during argument decoding. The patch was accepted within roughly two hours by nfsd maintainer Chuck Lever.

The Bug

Layton's patch submission describes the problem in precise terms. Both nfsaclsvc_decode_setaclargs() (NFSv2 ACL extension) and nfs3svc_decode_setaclargs() (NFSv3 ACLs) call nfs_stream_decode_acl() twice — first for the access ACL (NFS_ACL) and then for the default ACL (NFS_DFACL). Each successful decode allocates a fresh posix_acl and transfers ownership into argp->acl_access or argp->acl_default. The critical failure mode:

"If the first call succeeds but the second fails, the decoder returns false and argp->acl_access is left dangling."

The existing cleanup path was unreachable in this scenario. Layton traced the exact flow through svc_process_common():

svc_process_common()
  pc_decode()                  /* decode_setaclargs: false */
  /* pc_func skipped */
  pc_release()                 /* fh_put only — ACLs leaked */

The pc_release handlers were wired to generic functions (nfssvc_release_attrstat and nfs3svc_release_fhandle) that only called fh_put() with no awareness of the ACL fields. The posix_acl_release() calls lived at out: labels inside the proc functions themselves, but svc_process() skips pc_func entirely when pc_decode returns false — making that cleanup dead code on the decode-failure path.

"The orphaned posix_acl is leaked for the lifetime of the server."

The Fix

Layton's solution introduces two new release functions — nfsaclsvc_release_setacl() and nfs3svc_release_setacl() — which release both argp->acl_access and argp->acl_default in addition to calling fh_put(). These are wired as the pc_release handlers for their respective SETACL procedures. Because pc_release runs on every path svc_process() takes after decode (including decode failure), the redundant posix_acl_release() pairs are removed from the proc functions' out: labels, consolidating ownership in a single place.

"This matches the existing release_getacl() pattern used by the sibling GETACL procedures."

The patch touches two files (fs/nfsd/nfs2acl.c and fs/nfsd/nfs3acl.c) with 24 insertions and 10 deletions. It carries a Fixes: tag pointing to commit a257cdd0e217 ("[PATCH] NFSD: Add server support for NFSv3 ACLs."), indicating the bug has been present since NFSv3 ACL server support was first added.

Acceptance

Chuck Lever responded just over an hour and a half later, applying the patch to the nfsd-testing tree:

"Applied to nfsd-testing, thanks!"

commit: c5d94697918a13dd9cd5a288f5b3b8dbecd4a783

Significance for NFS Server Development

This is a classic resource-management bug in the kernel's RPC service dispatch layer. The leak is triggered by malformed or truncated SETACL requests — exactly the kind of input an untrusted client (or network corruption) could produce, making it relevant to server robustness and DoS resistance. The fix aligns the SETACL cleanup pattern with the already-correct GETACL pattern, reducing future maintenance risk in this area. While not a protocol or feature change, it is a meaningful correctness fix for long-running NFS servers that handle ACL operations.
