XFS pNFS: Correcting layout mappings and uninitialized imap handling

Summary

This week, Dai Ngo submitted a two-patch series to address critical bugs in the XFS pNFS export implementation. The patches fix issues exposed by running xfstests generic/075 against an NFSv4.2 block layout export. Christoph Hellwig reviewed and approved both patches on the same day they were posted.

This submission represents the formalization of fixes discussed at length in prior weeks, where concerns about overlapping extents in LAYOUTGET replies and potential race conditions in the NFS server code were debated. As noted in last week's summary, Dai Ngo had committed to resubmitting a combined series addressing both the XFS_BMAPI_ENTIRE flag issue and an uninitialized mapping record bug.

Bug Fix Classification

This thread is squarely focused on bug fixes for the XFS pNFS server-side implementation, with direct implications for NFS client stability. The two patches address:

  1. A use of uninitialized memory in the error path of xfs_fs_map_blocks().
  2. Overlapping extents returned to clients during LAYOUTGET operations, which can cause data corruption or protocol violations on the client side.

Key Technical Arguments

Patch 1: Uninitialized imap in Error Path

The first patch addresses a subtle but dangerous bug where xfs_fs_map_blocks() would fall through to xfs_bmbt_to_iomap() even after xfs_bmapi_read() failed, consuming an uninitialized imap record. Dai Ngo explained:

"If xfs_bmapi_read() fails, the function currently still falls through to xfs_bmbt_to_iomap(), which consumes an uninitialized imap record and may return invalid data to the caller."

The fix releases the data map lock and returns immediately upon error, preventing the propagation of garbage data to the NFS server layer. This patch fixes a regression introduced by commit 527851124d10f ("xfs: implement pNFS export operations").

Patch 2: Overlapping Extents in LAYOUTGET

The second patch removes the XFS_BMAPI_ENTIRE flag from the call to xfs_bmapi_read() within xfs_fs_map_blocks(). As Dai Ngo detailed:

"A single LAYOUTGET request from the client can cause the server to issue multiple calls to xfs_fs_map_blocks() for different offsets within the same extent. Because the use of XFS_BMAPI_ENTIRE flag, these calls can produce overlapping mappings."

The consequences for NFS clients are severe:

"This creates ambiguity in extent selection for a given file range, which can lead to incorrect device selection, inconsistent handling of datastate, and ultimately data corruption or protocol violations on the client side."

By replacing XFS_BMAPI_ENTIRE with 0, each request returns only the mapping for the explicitly requested range, eliminating overlaps. This patch fixes a regression from commit cc6c40e09d7b1 ("NFSD/blocklayout: Support multiple extents per LAYOUTGET").

Evolution of the Discussion

The path to this two-patch series was paved by extensive debate in prior weeks (see previous summary). Key developments included:

  • Christoph Hellwig's skepticism about why overlaps occurred at all, suggesting a hidden bug in nfsd code rather than solely an XFS issue.
  • Dave Chinner's proposal to conditionally use XFS_BMAPI_ENTIRE — keeping it for the first mapping call but dropping it for subsequent calls. However, Dai Ngo countered that the current map_blocks() API does not distinguish between first and subsequent calls, making this optimization impractical without API changes.
  • Discovery of a potential race condition in nfsd where layout insertion happens after ->proc_layoutget, creating a window for races against unwritten extent conversions or concurrent writers. Christoph Hellwig noted:

"We only insert layouts (and search for conflicts) after calling ->proc_layoutget. So this might be racy against unwritten extent conversion, or other writers, which is a bit of an issue."

This race condition remains an open item for future work and is not addressed by the current patch series.

Final Conclusions

Christoph Hellwig provided swift review approvals for both patches:

"Looks good: Reviewed-by: Christoph Hellwig hch@lst.de"

The two-patch series is now ready for integration, addressing two distinct but related bugs in the XFS pNFS implementation. For NFS client developers, these fixes are significant because they eliminate server-side sources of malformed layout responses that could trigger client-side data corruption or protocol violations. The broader nfsd race condition identified during this discussion remains unresolved and warrants separate attention in future development cycles.
