Summary

netfs: Transition from folio_queue to segmented bio_vec[] chains (bvecq)

David Howells submitted a significant 21-patch series (PATCH v2 00/21) aimed at modernizing the network filesystem library (netfslib) by replacing its internal buffer management structures. This is a protocol-agnostic infrastructure change with implications for NFS, AFS, and CIFS clients, focusing on performance optimization and code consolidation rather than fixing a specific bug.

Key Technical Arguments

The primary motivation for this series is to align netfslib with the kernel's broader trend toward using bio_vec arrays for I/O operations. Howells outlined three main goals:

  1. Consolidation: Move netfslib from its custom folio_queue and rolling_buffer constructs to a segmented chain of bio_vec arrays (bvecq). This reduces the number of buffering schemes in the kernel, as unbuffered/Direct I/O (DIO) already uses bio_vec.
  2. Performance: Enable sending entire filesystem RPC request messages via a single kernel_sendmsg() call. Howells noted this is "faster, more efficient and doesn't require the use of corking as it puts the entire transmission loop inside of a single tcp_sendmsg()."
  3. Simplification: Merge the ->prepare_read()/->issue_read() operations (and their write counterparts) to simplify subrequest setup.

The new struct bvecq introduces a linked list of segments, each containing an array of bio_vec entries. Key features include:

  • File position tracking (fpos) per segment to allow folio lookup by file offset.
  • A reference count (ref) to facilitate sharing slices of the chain.
  • Memory type indicators (mem_type) to handle different memory sources (pagecache, GUP-pinned, allocated).

Howells also introduced a new iterator type, ITER_BVECQ, allowing these chains to be passed directly to sendmsg() or block-based DIO operations.

Evolution of the Discussion

The series was met with minor stylistic and structural feedback from reviewers:

  • David Laight questioned the use of bitfields in the bvecq structure, noting that "There doesn't seem to be any point using bitfields" given the existing padding. He also suggested using off_t or u64 for fpos instead of long long and asked if backward traversal of the list was ever necessary, proposing a tail queue alternative if not.

  • Stefan Metzmacher provided an Acked-by for the CIFS/SMBDirect patches but requested minor commit message updates. Specifically, he asked that references to cifs: and smb_extract_iter_to_rdma be changed to smbdirect: and smbdirect_map_sges_from_iter respectively, to better reflect the code's location and function. He repeated this request for the removal of ITER_FOLIOQ support.

Impact on NFS Client Development

While the series affects multiple network filesystems, its impact on the NFS client is primarily through the netfs library abstraction. The NFS client relies on netfslib for buffered I/O and caching (via fscache/cachefiles). By switching to bvecq:

  1. Cachefiles Optimization: The series includes significant changes to cachefiles, reducing reliance on SEEK_DATA/SEEK_HOLE calls for contiguous files. Howells introduced a CACHEFILES_CONTENT_ALL type for files written progressively without holes, which "speeds things up enormously" by avoiding per-read seek operations.
  2. Unified Buffering: NFS clients will benefit from the unified buffering scheme, where both buffered and unbuffered I/O use the same underlying bvecq structure. This simplifies the codebase and reduces potential for bugs related to divergent buffer management paths.
  3. Improved TCP Efficiency: The ability to send entire RPC messages in a single kernel_sendmsg() call should improve network throughput and reduce CPU overhead for NFS over TCP, as it eliminates the need for socket corking.

Final Conclusions

The series represents a major refactoring of the netfs library's I/O path. While no critical bugs were fixed, the changes are designed to improve performance and maintainability. The feedback received was minor, focusing on code style and commit message accuracy. Howells indicated that further work is planned to allow filesystems to "splice" TCP receive queues into bvecq chains, which would further reduce lock contention during data copying.

The series is targeted for inclusion in the VFS tree, pending the requested minor adjustments to commit messages.
