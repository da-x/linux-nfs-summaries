rxrpc/RxGK: v4 pre-decrypt/pre-verify length check fix for Kerberos crypto

Summary

rxrpc/RxGK: v4 Pre-Decrypt/Pre-Verify Length Check Fix

Type: Bug fix (security hardening) — fourth revision of a patch series already in flight.

This Week's Activity

David Howells posted version 4 of the patch on 2026-05-15, the latest in a series targeting the net tree that has now been iterated four times since early May. The patch description is unchanged from prior revisions:

"Change the krb5 crypto library to provide facilities to precheck the length of the message about to be decrypted or verified."

"Fix AF_RXRPC to make use of this to validate DATA packets secured with RxGK."

The Fixes: tag points at commit 9d1d2b59341f ("rxrpc: rxgk: Implement the yfs-rxgk security class (GSSAPI)"), and the patch closes an external bug tracker entry on sashiko.dev. It is marked for stable backporting (cc: stable@vger.kernel.org) and CC'd to linux-nfs@, linux-afs@, netdev@, and linux-crypto@ — with Chuck Lever, Marc Dionne, Jeffrey Altman, Herbert Xu, and the net maintainers (davem, edumazet, kuba, pabeni, horms) on the cc list.

Technical Scope

The v4 patch touches five files:

FileChanges
Documentation/crypto/krb5.rst+17/-3 (API documentation)
crypto/krb5/krb5_api.c+54/-4 (core length-checking logic)
include/crypto/krb5.h+9/-2 (API header updates)
include/trace/events/rxrpc.h+1 (tracing enhancement)
net/rxrpc/rxgk.c+15/-2 (rxrpc integration)

The fix adds a new pre-check facility to the krb5 crypto library so that callers can validate the length of an incoming message before handing it to the decrypt/verify path, and then wires AF_RXRPC's RxGK security class to use it for DATA packets. A new trace event is added so the validation outcome is observable.

Evolution of the Discussion (Bridge from Prior Weeks)

This thread has been a steady drumbeat of revisions over the past three weeks:

  • v2 was posted on 2026-05-13 as part of a four-patch series, with Jeffrey Altman sending a brief acknowledgment. See prior week's summary for details.

  • Still on 2026-05-13, Howells posted a self-correction identifying a subtle sizeof() bug in his own v2:

    "This should be sizeof(hdr) here in patch 2 and sizeof(*hdr) in patch 3."

    This precision fix matters because the pre-decrypt length check is only as good as the header size it's handed — using the wrong sizeof expression could either reject valid packets or fail to catch malformed ones.

  • v3 followed on 2026-05-14, with a slightly larger delta in net/rxrpc/rxgk.c (+15/-2 vs. +11/-2 in v2), consistent with the sizeof correction and additional hardening.

  • v4 (this week) lands on 2026-05-15 with the same five-file footprint as v3, suggesting the series has largely stabilized after the self-correction.

Relevance to NFS Client Development

While the patch's primary target is AF_RXRPC and the kernel's Kerberos crypto library — infrastructure shared between AFS and NFS clients that use GSSAPI/Kerberos security — it lands squarely in the cross-subsystem security path that NFS clients depend on. The cc line to linux-nfs@vger.kernel.org and Chuck Lever signals that the NFS maintainers consider this fix relevant to their tree, particularly for any client configuration that routes Kerberos-secured traffic through rxrpc-based transports or shares the underlying krb5/crypto API.

The practical effect is defensive: by validating message length before decryption or verification, the kernel avoids feeding malformed (or malicious) packet payloads into the crypto pipeline, which is a classic vector for buffer overruns and denial-of-service on network-facing code. For NFS clients using Kerberos security, this hardening reduces the attack surface of any path that ultimately calls into crypto_krb5_* primitives.

Final Conclusions

  • This is a bug fix / security hardening patch, not a new feature or protocol change.
  • The v4 posting on 2026-05-15 represents the latest iteration of a series that has been refined over three weeks; no substantive technical debate has emerged in any window, suggesting the approach is well-received.
  • The cc: stable@vger.kernel.org tag and the explicit Fixes:/Closes: tags indicate Howells expects this to be backported to stable kernels once merged into net.
  • For NFS client developers, the key takeaway is that the shared Kerberos crypto API now exposes a pre-decrypt length-check primitive, which any future consumer (including NFS-side code paths) can leverage for similar hardening.
