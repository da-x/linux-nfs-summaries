NFS client: Don't always trust server inode size while holding a write delegation

Summary

On the final day of the week, Oracle's Dai Ngo posted v2 of a small but important NFS client bug fix that hardens how the Linux NFS client reconciles cached inode metadata with server-reported attributes when the client is operating under a write delegation. The thread consists of a single message this week — the v2 patch submission itself — with no replies yet in the window.

Classification

This is a bug fix for the NFSv4 client, not a new feature or protocol change. It corrects an incorrect assumption in nfs_wcc_update_inode() that the server's GETATTR size is always authoritative, which breaks under write delegations where the client legitimately buffers writes and metadata updates locally before propagating them to the server.

Key Technical Argument

Dai Ngo's cover message lays out the core problem clearly:

"With a write delegation, the server permits the client to buffer writes and associated metadata updates (including file size changes) locally and defer propagating them to the server. As a result, the server-reported GETATTR size may legitimately lag behind the client's cached size for the duration of the delegation, so it must not be treated as authoritative."

The proposed fix is narrowly scoped: modify nfs_wcc_update_inode() in fs/nfs/inode.c (7 lines changed, +5/-2) so that the cached inode size is updated from server data only when either:

  1. The client does not hold a write delegation, or
  2. The nfs_inode's cache_validity has the NFS_INO_INVALID_SIZE bit set (i.e., the local size is already known to be stale).

This preserves the existing WCC-based cache validation behavior for the common non-delegated case while preventing the client from clobbering a fresher locally-known size with an older server-reported value during the delegation window.

Significance for NFS Client Development

For NFS client developers and downstream users, this fix matters because write delegations are a primary performance mechanism in NFSv4: they let the client skip round-trips for metadata updates while it is the sole writer. If the client blindly accepts a stale server size during that window, applications can observe inconsistent st_size values, file-size regressions after writes, or spurious cache invalidation — all of which undermine the very reason delegations exist. By gating the WCC size update on delegation state and the NFS_INO_INVALID_SIZE flag, the patch aligns the client's metadata handling with the protocol's intent that delegated clients own the truth about file size until they return the delegation.
