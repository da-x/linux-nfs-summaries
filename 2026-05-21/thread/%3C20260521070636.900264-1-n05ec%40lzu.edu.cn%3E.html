sunrpc: rq_procinfo lifecycle hardening (double-free fix) applied to nfsd-testing

What happened this week

A compact but consequential bug-fix thread landed on the linux-nfs list on Thursday, 2026-05-21. Luxiao Xu's patch — posted by Ren Wei as v2 — closes a double-free / use-after-free hole in the SUNRPC server-side request path, and it was picked up by nfsd maintainer Chuck Lever within hours of posting.

The bug (v2 submission)

Ren Wei posted the v2 patch, authored by Luxiao Xu, which describes the underlying defect in terms that matter for NFS server maintainers:

"The svc_release_rqst() function executes the callback inside rqstp->rq_procinfo->pc_release. However, if a worker thread begins processing a new request and encounters an early error path (e.g., unsupported protocol, short frame, or bad auth) before a valid rq_procinfo is installed, a stale release hook can be re-triggered against reused state from the previous RPC, resulting in a double-free or use-after-free vulnerability."

The proposed fix hardens the lifecycle of rq_procinfo in three places:

  1. svc_release_rqst() now always clears rq_procinfo after the optional pc_release() call, regardless of whether the hook exists.
  2. svc_process() explicitly clears rq_procinfo at request entry, before any early decode or drop path can run.
  3. svc_process_bc() does the same at backchannel entry.

The patch carries a Fixes: tag pointing at d9adbb6e10bf ("sunrpc: delay pc_release callback until after the reply is sent") and a Cc: stable@kernel.org line, plus four Reported-by: tags (Yuan Tan, Yifan Wu, Juefei Pu, Xin Liu) and a Suggested-by: Chuck Lever <cel@kernel.org> — an indication that this is the second iteration of a fix that has already been through at least one review cycle. The v2 changelog notes the two refinements made since v1:

"Extended the fix to clear rq_procinfo at request entries (both in svc_process and svc_process_bc) before early decode/drop paths." "Moved the pointer clearing in svc_release_rqst outside the conditional block to ensure it always clears, as suggested by Chuck."

The diff itself is small — four insertions in net/sunrpc/svc.c — but it touches a code path that every NFS server request traverses, which is why the stable Cc matters.

Review and acceptance

Chuck Lever responded within roughly six hours, quoting the patch's own description of the stale-hook hazard and then confirming acceptance:

"Applied to nfsd-testing, thanks! [1/1] sunrpc: harden rq_procinfo lifecycle to prevent double-free commit: 2739a03352101a0f6b3b185bc6c9e983129cbd49"

Jeff Layton followed minutes later with a formal Reviewed-by: Jeff Layton <jlayton@kernel.org>, after quoting the relevant hunks (including the backchannel-side change that sets rqstp->rq_bc_net = req->rq_xprt->xprt_net).

Significance for NFS server development

  • Classification: This is a bug fix — specifically a memory-safety hardening of the SUNRPC server request lifecycle. It is not a protocol change and not a new feature; it does not alter wire format or client-visible behavior, but it does close a class of exploitable double-free/UAF on the server side reachable via malformed or early-failing RPCs (bad auth, short frames, unsupported protocols).
  • Why it matters for NFS: The rq_procinfo/pc_release machinery is shared by every NFSD program (NFSv2/v3/v4.x, NLM, mountd, etc.), so a stale hook here can corrupt kernel state across requests. Clearing the pointer at both entry points (svc_process and svc_process_bc) plus on release makes the lifecycle robust against any future early-exit path being added to svc.c.
  • Process note: The patch went from v2 posting to nfsd-testing merge in under a day, with an independent Reviewed-by from Layton — a clean example of how small, well-scoped SUNRPC fixes flow through the NFS server tree.

Bottom line

A four-line lifecycle hardening in net/sunrpc/svc.c, fixing a stale-rq_procinfo double-free/UAF introduced by the delayed pc_release callback work, was submitted as v2 on 2026-05-21, reviewed by Jeff Layton, and applied to nfsd-testing by Chuck Lever the same day (commit 2739a0335210). Stable backport is requested.
