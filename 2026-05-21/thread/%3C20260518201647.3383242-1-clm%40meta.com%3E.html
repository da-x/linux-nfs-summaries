nfsd: fix dangling layout stid on setlease failure

Summary

nfsd: release layout stid on setlease failure — quick turnaround fixes a use-after-free in pNFS layout stateids

Type: Bug fix (use-after-free / dangling IDR pointer) in the NFS server (nfsd) pNFS layout code.

The bug

On Monday, May 18, Chris Mason posted a single-patch fix to the linux-nfs list describing a subtle but dangerous teardown path in the NFSv4 server's pNFS layout stateid handling. As Mason laid out:

"nfs4_alloc_stid() publishes the new stid into cl->cl_stateids via idr_alloc_cyclic() under cl_lock before returning to nfsd4_alloc_layout_stateid(). When nfsd4_layout_setlease() then fails, the error path frees the layout stateid directly with kmem_cache_free() without ever calling idr_remove(), leaving the IDR slot pointing at freed slab memory. Any subsequent IDR walker (states_show, client teardown) dereferences the dangling pointer."

In other words, a failed SETATTR/lease setup on a pNFS layout would leave a stale IDR entry that any later walk of the client's stateid table — for example via /proc/fs/nfsd/clients/*/states or during client disconnect — could follow into freed slab memory. The patch carries a Fixes: tag pointing at c5c707f96fc9 ("nfsd: implement pNFS layout recalls"), so the latent bug has been present since layout recalls were first implemented.

The fix and its wrinkle

The correct teardown for an IDR-published stateid is nfs4_put_stid(), which removes the IDR slot under cl_lock and dispatches the proper destructor. But Mason noted a second, blocking issue:

"nfsd4_free_layout_stateid() unconditionally inspects ls->ls_fence_work via delayed_work_pending() under ls_lock, but INIT_DELAYED_WORK(&ls->ls_fence_work, ...) currently runs only after the setlease call. On the setlease-failure path the destructor would touch an uninitialized delayed_work."

The fix therefore does two things in fs/nfsd/nfs4layouts.c (a net +5/−7 lines): it hoists the ls_fenced / ls_fence_delay / INIT_DELAYED_WORK() initialization above the nfsd4_layout_setlease() call, and replaces the manual nfsd_file_put + put_nfs4_file + kmem_cache_free cleanup with a single nfs4_put_stid(stp). Mason also credited AI assistance in the commit metadata ("Assisted-by: kres (claude-opus-4-7)").

Review and merge — same-day

The patch drew an immediate, clean response. Chuck Lever applied it to his nfsd-testing tree within an hour of posting:

"Applied to nfsd-testing, thanks!" — Chuck Lever's reply, landing as commit 9e93f8c13374d21254f8dcd0010103da346bc1f3.

Jeff Layton followed with a brief review endorsement:

"Reviewed-by: Jeff Layton jlayton@kernel.org" — Layton's reply.

Takeaway

This is a textbook example of the kind of bug that only surfaces under rare error paths: the happy-path layout allocation was fine, but the setlease-failure branch skipped IDR removal and would have crashed (or corrupted state) on any subsequent stateid walk. The fix is small, surgical, and already in the nfsd-testing tree for the upcoming merge window. For NFS server maintainers running pNFS with layout recalls enabled, this one will be worth picking up as soon as it lands upstream.
