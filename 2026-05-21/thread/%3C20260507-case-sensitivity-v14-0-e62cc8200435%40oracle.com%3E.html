Case Folding v14: Linux 7.2 Merge Confirmed; LTP statx04 Regression on vfat Traced to fileattr_get

Bridge from Prior Weeks

The v14 series "[PATCH v14 00/15] Exposing case folding behavior" was posted by Chuck Lever on May 7 and merged into the VFS tree by Christian Brauner on May 11 (see prior week's summary). The series spans fat, exfat, ntfs3, hfs, hfsplus, xfs, cifs, nfs, vboxsf, isofs filesystems plus NFSD and ksmbd server-side changes. This week's activity covers two distinct threads of follow-up: a community question about merge timing, and a substantive debugging session around an LTP regression triggered by the FAT fileattr_get patch.

Community Question: Will Case-Insensitive Filesystem Support Land in Linux 7.2?

On May 16, Cedric Blancher from the Institut Pasteur asked Chuck Lever to confirm the timeline for case-insensitive filesystem support [id://CALXu0UdsurG-ayuYViqs0HXOfgyDw8gpNC+f=5y59cuuSPUbBA@mail.gmail.com]:

"Does that mean the support for case-insensitive filesystems will work with Linux 7.2?"

Lever responded cautiously, acknowledging the early stage of the feature:

"I don't want to make claims with 100% certainty, but we expect this series to get merged into 7.2. It's early days, so there are likely to be bugs -- there is so much subtle behavior under the covers." [id://bd45e387-cc11-4d19-8bd6-58a0251d7714@kernel.org]

This exchange is notable as it represents one of the first external (non-maintainer) inquiries about the feature's availability, signaling growing community interest in the case-folding infrastructure.

LTP statx04 Regression: vfat fileattr_get Breaks Test Assumptions

The bulk of this week's activity (May 20) is a focused debugging conversation between Mark Brown and Chuck Lever on patch 03/15 ("fat: Implement fileattr_get for case sensitivity"). This is fundamentally a bug fix discussion — the new fileattr_get implementation inadvertently changes observable kernel behavior that an existing LTP test depends upon.

The Bug Report

Mark Brown opened the thread by reporting bisect results pointing to patch 03/15 as the cause of LTP statx04 failures [id://dc69224d-9926-4414-8c6e-4c15ae98705b@sirena.org.uk]. The specific failure was:

"statx04.c:121: TFAIL: STATX_ATTR_NODUMP not supported"

Initial Skepticism and Narrowing

Chuck Lever's first reaction was skepticism about the bisect result [id://04302551-3628-4036-9a3f-596cb782f5b7@app.fastmail.com]:

"At first blush, that does not seem like a plausible bisect result. This commit shouldn't affect the behavior of tmpfs in any way."

Brown confirmed the failure was indeed on vfat (not tmpfs), and provided additional test output showing the test running across multiple filesystems [id://a366645c-364d-4588-8a15-4cd446f64366@sirena.org.uk]. Lever then asked a clarifying question to scope the regression:

"OK. Is vfat the only failure in LTP statx04?" [id://8b750b3f-4d73-41f3-84fb-6e387fd24168@app.fastmail.com]

Brown confirmed that vfat was the only filesystem showing failures, with four corresponding TFAILs [id://3a347b64-f91b-450f-b27d-26ea6810b960@sirena.org.uk].

Root Cause Analysis

Lever delivered a detailed root cause explanation in his most substantive message of the week [id://858d7233-1d9c-48f4-aa4f-c5a9f6e1f5dc@app.fastmail.com]:

"03/15 adds .fileattr_get = fat_fileattr_get for both fat_file_inode_operations and vfat_dir_inode_operations. LTP opens a directory (SAFE_OPEN(TESTDIR, O_RDONLY|O_DIRECTORY)), so FS_IOC_GETFLAGS on the dir now succeeds, and statx04 proceeds where it was previously skipped."

The key insight: before patch 03/15, FS_IOC_GETFLAGS on a vfat directory returned ENOTTY, causing LTP statx04 to skip its attribute tests entirely. Now that fileattr_get is wired up, the ioctl succeeds, and the test proceeds to check all four STATX_ATTR_* bits (IMMUTABLE, APPEND, COMPRESSED, NODUMP) — of which FAT only genuinely supports two:

"AFAICS, 03/15 did not change pre-existing kernel behavior of stx_attributes_mask on vfat. It merely converted a 'skipped' LTP outcome into an 'executed but failed' outcome."

Proposed Fix Options

Lever laid out three remediation paths:

  1. Narrowest kernel fix: Have fat_getattr() call generic_fill_statx_attr(inode, stat), which advertises KSTAT_ATTR_VFS_FLAGS (IMMUTABLE + APPEND). "That clears 2 of 4 TFAILs but not COMPRESSED/NODUMP, which FAT genuinely does not back."

  2. Broader mask: Set stat->attributes_mask |= KSTAT_ATTR_FS_IOC_FLAGS in fat_getattr(). Lever was candid about the trade-off: "This would silence the test failures, but advertises capabilities (COMPRESSED, NODUMP) FAT doesn't track."

  3. Fix the test: "Admit the LTP statx04 test needs to be updated. FS_IOC_GETFLAGS succeeding does not logically imply all four FS_IOC_FLAGS-mapped STATX_ATTR_* bits are supported. The test's gate is too coarse for filesystems that gained a narrowly-scoped fileattr_get (just casefold/immutable)."

Lever recommended option 1: "The first option is the narrowest kernel-side change, and matches what other minimal-fileattr filesystems do."

Resolution and Next Steps

Mark Brown endorsed the approach [id://cdeaab82-06bf-47c1-8f6c-4e40dbec2344@sirena.org.uk]:

"That sounds like a good idea regardless of what we do with the test?"

Lever agreed but flagged the need for broader sign-off before implementation [id://d2425b45-a37a-4cc9-8984-bed55ee54a32@app.fastmail.com]:

"Yes, I have no objection to this approach, but it would be great to hear from the vfat maintainers/contributors on this one before I dig in."

Significance for NFS Client Development

While this particular regression is in the FAT filesystem code (not directly in the NFS client), it has direct implications for NFS:

  • Re-export correctness: When an NFS server exports a FAT/vfat filesystem, the case-folding patches (10/15 for the client, 13/15 and 14/15 for NFSD) rely on fileattr_get to report correct semantics. A bug in the underlying filesystem's fileattr_get would propagate into NFS attribute reporting.
  • LTP as a regression gate: The statx04 test is part of the standard kernel test suite. Its interaction with newly-wired fileattr_get handlers across multiple filesystems (fat, exfat, ntfs3, hfs, etc.) means similar regressions could surface in other filesystems as well — each one a potential source of incorrect case-sensitivity reporting to NFS clients.
  • The "skipped → failed" pattern: Lever's observation that the patch "merely converted a 'skipped' LTP outcome into an 'executed but failed' outcome" is a general warning for any filesystem gaining a new fileattr_get implementation: previously invisible test coverage becomes active, and incomplete implementations will now be flagged.

Conclusion

This week marked the transition from merge celebration to post-merge bug triage for the case-folding series. The Linux 7.2 target was confirmed (with appropriate caveats), and a concrete LTP regression in vfat was identified, root-caused, and a fix direction agreed upon — pending vfat maintainer sign-off. The discussion underscores the subtlety Lever warned about: "there is so much subtle behavior under the covers."
