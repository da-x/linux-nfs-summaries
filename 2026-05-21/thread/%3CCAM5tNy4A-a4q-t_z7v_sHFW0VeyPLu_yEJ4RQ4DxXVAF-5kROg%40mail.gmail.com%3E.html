Summary

NFSv4.1 Client Hang in nfs4_drain_slot_tbl — Reporter Provides Environment Details and Lease Evidence

This Week's Activity (2026-05-15 → 2026-05-21)

This week the thread advanced with a single but substantive reply from reporter 郭玲兴 on May 18, directly answering the diagnostic questions posed by Lionel Cons last week and engaging with Rick Macklem's soft-mount hypothesis. The message is posted here.

Environment Details Supplied

The reporter closed the information gap left open by Lionel Cons's earlier request for server and client specifics:

  • Server: Windows Server 2022, version 10.0.20348.587
  • User mapping: None — no AD, LDAP, or passwd-based mapping; unmapped users fall through to the default "Everyone" account
  • Authentication: sec=sys (AUTH_SYS), as reported by nfsstat -m
  • Architecture: x86_64 on both the Linux clients and the Windows server
  • Memory: 16 GB RAM per Linux client VM

This is significant because it confirms the hang reproduces against a stock, recent Windows NFS server with the simplest possible authentication path — ruling out GSS/Kerberos complications and pinning the issue squarely in the NFSv4.1 session/slot-table interaction layer.

New Diagnostic Evidence: Lease Expiry on Two Clients

The most important new technical data this week is the reporter's observation of lease state on two independent clients at hang time:

"Client A: age: 498061, lease_time: 120, lease_expired: 497941" "Client B: age: 69598, lease_time: 120, lease_expired: 69478"

The reporter notes that in both cases lease_expired ≈ age - lease_time, which means the lease expired almost immediately after mount and was never renewed. This is a strong signal that the client's state management machinery stopped functioning long before the hang — consistent with a slot-table or session-state corruption rather than a transient network event.

Hang-Time Observations

The reporter also documented what both clients looked like at the moment of the hang:

"both clients are blocked in nfs4_drain_slot_tbl" "no NFS RPC traffic is observed, only TCP ACKs" "nfsstat reports retrans=0" "on the Windows server side, the session state is reported as 'Initialized'"

The combination of retrans=0 with a live TCP connection (ACKs flowing) and a server-side session still in "Initialized" state suggests that from the client's perspective the RPC layer believes everything is quiescent, while the slot table still contains entries that nfs4_drain_slot_tbl is waiting on. This is precisely the "orphaned slot" condition Rick Macklem warned about last week.

Engaging with the Soft-Mount Hypothesis

The reporter acknowledges Rick Macklem's soft-mount warning from May 16 and commits to a follow-up test:

"Regarding the 'soft' mount option: understood. We will retest with a hard mount as well."

More importantly, the reporter pushes back constructively by asking whether the observed behavior is even expected under soft mounts — framing the question in terms of client robustness:

"Even if a soft mount contributes to the problem, is it expected that a single RPC timeout can leave the client in a state with no forward progress, blocked in nfs4_drain_slot_tbl, and with lease renewal no longer occurring? Or would that more likely indicate a client-side recovery bug?"

This reframing is important for the NFS client development conversation: it shifts the discussion from "the user misconfigured their mount" to "does the client's recovery path have a robustness gap when slots are orphaned by soft-mount timeouts?" The reporter is explicitly inviting a client-side fix discussion, not just a workaround.

Classification and Significance

This remains a bug fix / interoperability thread targeting the Linux NFSv4.1 client. No patch has been proposed yet, but the diagnostic picture has sharpened considerably this week:

  1. The hang is reproducible on two independent clients against a stock Windows Server 2022 with AUTH_SYS.
  2. Lease renewal stops early, suggesting session state corruption well before the visible hang.
  3. The slot table contains entries that never complete, and nfs4_drain_slot_tbl blocks indefinitely on them.
  4. The reporter is now testing whether removing soft from the mount options eliminates the hang, which would confirm Rick Macklem's hypothesis about soft-mount RPC timeouts orphaning session slots.

The open question — raised explicitly by the reporter — is whether the client should be hardened so that a single timed-out RPC on a soft mount cannot leave the slot table in a permanently stuck state. That question will likely drive the next phase of this thread, potentially toward a concrete patch for nfs4_drain_slot_tbl or the surrounding session recovery logic.
