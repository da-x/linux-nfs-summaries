sunrpc: kref_get_unless_zero patch for auth_domain_lookup dropped after review

Summary

sunrpc: kref_get_unless_zero in auth_domain_lookup — Patch Proposed, Reviewed, and Dropped

Type: Bug fix (proposed, ultimately withdrawn) Subsystem: NFS server / SUNRPC authentication (net/sunrpc/svcauth.c)

Background

On Wednesday, May 20, Jeff Layton posted a small patch to the linux-nfs list as part of his nfsd-fixes series. The change targeted auth_domain_lookup() in the SUNRPC server-side authentication code, proposing a switch from plain kref_get() to kref_get_unless_zero() when acquiring a reference on an auth_domain hash entry.

Layton's cover description painted a vivid race-condition scenario:

"auth_domain_put() uses kref_put_lock(), which atomically decrements the refcount before acquiring auth_domain_lock. This creates a window where an auth_domain entry is still linked on the hash list with refcount == 0."

He argued that if auth_domain_lookup() encountered such a transient zero-refcount entry, the plain kref_get() would trigger a WARN (saturating refcount_t semantics) yet still return the pointer, leaving the caller with a dangling reference that could be freed by the concurrent auth_domain_put(). The fix was to mirror what the sibling function auth_domain_find() already does: treat a zero-refcount entry as absent and continue searching.

The patch carried a Reported-by: tag for Chris Mason (Meta) and an unusual Assisted-by: kres:claude-opus-4-6 line, indicating AI-assisted development.

Review and Rebuttal

Chuck Lever responded within about an hour with a brief note supplying the appropriate Fixes: tag:

"Fixes: 608a0ab2f54a ("SUNRPC: Add lockless lookup of the server's auth domain")"

A second reply from Lever, roughly half an hour later, forwarded results from sashiko (an automated code-review tool) that raised two high-severity objections:

"[Severity: High] Is this description of kref_put_lock() accurate? Looking at kref_put_lock(), it uses refcount_dec_and_lock() which acquires the spinlock before the 1->0 transition is completed. Since auth_domain_lookup() holds the same auth_domain_lock, is it actually possible for it to encounter a 0-refcount entry under normal conditions?"

The second concern was equally pointed:

"[Severity: High] If a 0-refcount entry is encountered here, wouldn't it indicate a severe underlying refcount imbalance or use-after-free rather than a normal race? By using kref_get_unless_zero() and continuing the search, might this silently mask the root cause of the WARN instead of resolving it?"

Sashiko also flagged a potential functional regression: if the loop skipped a zero-refcount entry and fell through to the end of the function, it could insert a duplicate auth_domain with the same name into the hash list.

Resolution

Layton conceded quickly, agreeing with the automated reviewer's analysis:

"Sashiko is correct. This codepath can't see a 0 refcount here. The patch won't break anything, but it's not fixing anything either. Let's just drop this one."

The key technical insight was that kref_put_lock() internally uses refcount_dec_and_lock(), which acquires the spinlock before completing the 1→0 transition. Since auth_domain_lookup() already holds that same lock while walking the hash, it can never observe an entry in a zero-refcount state — the race window Layton described does not actually exist.

Significance for NFS Client/Server Development

Although this particular patch was withdrawn, the thread is instructive on several fronts:

  1. AI-assisted kernel development: The Assisted-by: kres:claude-opus-4-6 tag marks one of the more visible instances of AI tooling contributing to mainline kernel patches. The automated sashiko review effectively caught a subtle misunderstanding of lock ordering in kref_put_lock(), preventing a no-op (or worse, masking) patch from entering the tree.
  2. SUNRPC auth_domain locking: The discussion clarified the precise semantics of the lockless lookup path introduced by commit 608a0ab2f54a, reinforcing that the existing kref_get() in auth_domain_lookup() is safe under the current locking scheme.
  3. nfsd-fixes series context: This patch was message 1 of a larger nfsd-fixes v1 series from Layton; its withdrawal does not affect the remaining fixes in the set.

The thread concluded within roughly two hours of the initial posting, with no further activity.
