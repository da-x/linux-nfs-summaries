OPENAT2_REGULAR: Brauner Massages Series, Moves Flag to Upper 32-bit UAPI Space

Summary

This week brought a quiet but consequential update to the long-running OPENAT2_REGULAR patch series. VFS maintainer Christian Brauner announced that he had reworked the already-applied patches—moving the OPENAT2_REGULAR flag from the legacy 32-bit O_* flag space into the upper 64-bit UAPI region, and porting the selftests to the modern TEST* framework. Author Dorjoy Chowdhury acknowledged the changes with a brief thank-you. The exchange was short but signals a post-merge refinement that will affect how NFS (and other filesystems) consume this new open-time flag.

Bridge from Prior Weeks

The OPENAT2_REGULAR series (v6) has been under review since late March 2026. Over the preceding weeks:

  • Review & merge (April 16): After thorough review by Jeff Layton (who provided a Reviewed-by tag), Aleksa Sarai, and Jori Koolstra, Brauner applied the series to the vfs-7.2.openat.regular branch. The feature allows applications to request opening only regular files via openat2(), returning -EFTYPE if a non-regular file is encountered. The NFS client implementation in fs/nfs/dir.c was part of this accepted patch set, enabling strict regular-file validation within the nfs_atomic_open codepath.
  • UAPI design debate (April 16): Jori Koolstra questioned why OPENAT2_REGULAR occupied a bit in the legacy 32-bit O_* flag range when it is exclusively an openat2() feature. Brauner initially concurred that the placement was "harmless" since legacy open() would silently ignore unknown bits.
  • Post-merge EFTYPE debate (April 27): Florian Weimer raised POSIX compliance concerns about reviving the largely unused EFTYPE error code. Chowdhury defended the choice citing BSD/macOS precedent, and Brauner pushed back against switching to ENOTTY.

This Week's Activity (May 21)

Brauner Announces Post-Merge Rework

On May 21, Christian Brauner posted a message quoting his earlier April 16 application note and explaining the changes he had made:

"So I've massaged this series a bit in that I moved OPENAT2_REGULAR into the upper 64-bit and internally use a __O_REGULAR bit. After having thought about it makes a lot more sense to move the openat2() only features into the upper 32-bit for the uapi space."

This is a notable design evolution: rather than leaving OPENAT2_REGULAR in the legacy 32-bit O_* range (as originally applied), Brauner has relocated it to the upper 64-bit portion of the UAPI flag space, reserving the lower bits for backward compatibility with traditional open() flags. Internally, the kernel uses a new __O_REGULAR bit to represent the flag in the internal open_flags representation.

Brauner also noted:

"I also ported the selftests to the TEST* framework to fit with Aleksa's recent rework."

This modernization of the kselftests aligns the OPENAT2_REGULAR test coverage with the broader kselftest infrastructure improvements that Aleksa Sarai has been driving.

Chowdhury Acknowledges

Dorjoy Chowdhury replied shortly after:

"Thanks for fixing up!"

The brief exchange confirms the author's acceptance of the maintainer's rework and closes out this phase of the discussion.

Classification

New Feature (UAPI addition) — post-merge refinement. No bug fixes were discussed this week. The change is a design improvement to an already-merged feature, clarifying the UAPI flag space allocation for openat2()-exclusive flags.

Implications for NFS Client Development

The move of OPENAT2_REGULAR into the upper 64-bit UAPI space has practical implications for the NFS client:

  1. Cleaner flag separation: By isolating openat2()-only features from the legacy O_* bits, the kernel avoids any risk of flag leakage into f_flags or confusion with traditional open flags. The NFS client's nfs_atomic_open codepath in fs/nfs/dir.c will now check against the new __O_REGULAR internal bit rather than a shared O_* constant.

  2. Forward compatibility: Reserving the upper 32-bit space for future openat2()-exclusive flags provides room for additional open-time-only features without consuming scarce legacy O_* bits. This is relevant for NFS client development as new atomic-open semantics (e.g., stricter type checking, extended attribute validation) may be added in the future.

  3. No behavioral change for NFS: The functional behavior of the feature remains identical—applications using openat2() with OPENAT2_REGULAR on an NFS mount will still receive -EFTYPE when targeting a non-regular file. The change is purely at the UAPI encoding level.

Conclusion

This week's activity was minimal but architecturally significant. Brauner's decision to relocate OPENAT2_REGULAR into the upper 64-bit UAPI space resolves the earlier design concern raised by Jori Koolstra about wasting a legacy O_* bit for an openat2()-only feature. The series is now in its final, polished form within the VFS tree, with NFS client support fully integrated and selftests modernized. No further discussion was anticipated at the time of this summary.
