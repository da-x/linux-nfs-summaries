XFS pNFS: Deepening investigation into overlapping extents and race conditions in LAYOUTGET

Summary

This week's discussion continued the review of Dai Ngo's patch to fix overlapping extents returned by XFS during pNFS LAYOUTGET operations. While the previous week established consensus on removing the XFS_BMAPI_ENTIRE flag from xfs_fs_map_blocks(), this week's exchange revealed deeper concerns about the root cause of the overlaps and potential race conditions in the NFS server code.

Bug Fix Context

The patch addresses a regression where multiple calls to xfs_fs_map_blocks() within a single LAYOUTGET operation could return overlapping extents due to the use of the XFS_BMAPI_ENTIRE flag. This caused ambiguity for NFS clients when selecting device layouts and handling data states.

Key Technical Arguments

Christoph Hellwig's Skepticism About Overlaps

Christoph Hellwig questioned why overlapping extents appeared at all, suggesting a hidden bug in the nfsd code:

"Now that is really weird. How do we end up not using the remainder of the previous extent from a previous nfsd4_block_map_extent call in nfsd4_block_proc_layoutget? Looks like there is another bug hiding in the nfsd code somewhere."

He also reiterated the need for client-side validation:

"And the client should probably also validate that extents of the same kind do not overlap (read vs write extents are allowed to overlap)."

Dave Chinner's Proposed Optimization

Dave Chinner proposed a more nuanced solution that would preserve performance benefits while avoiding overlaps:

"The problem is not the use of XFS_BMAPI_ENTIRE on the first mapping call, it's the use of it on the -second- after the first call didn't return a range that mapped the -entire- request range."

He suggested keeping XFS_BMAPI_ENTIRE for the initial call to minimize pNFS client mapping calls, but dropping the flag and trimming ranges for subsequent calls:

"That was we get large extents reported most of the time, and in the corner cases where we have a race like this one or an extent boundary lies in the middle of the requested range, we will get correct, non-overlapping behaviour. Best of both worlds, yes?"

Dai Ngo's API Limitation Argument

Dai Ngo countered that the current map_blocks() API between NFS server and XFS does not distinguish between first and subsequent calls:

"Currently the map_blocks() API between the NFS server and XFS does not provide a way to specify whether XFS should use XFS_BMAPI_ENTIRE or '0'. xfs_fs_map_blocks() just uses XFS_BMAPI_ENTIRE."

He argued that since the first call always requests the entire file range from the client, using XFS_BMAPI_ENTIRE makes no practical difference if it cannot return the full range:

"So if xfs_fs_map_blocks() can not return the requested mapping range with '0' on the first mapping call then I think using XFS_BMAPI_ENTIRE in the first mapping call makes any different."

Christoph Hellwig agreed with this assessment:

"And that is a good thing."

Discovery of Potential Race Condition

Dai Ngo provided debug output showing that file extent mappings changed during the LAYOUTGET operation, with two entries merging into one:

"As shown, the file map changes. Entry# 7 and 8 before the NFSD calls merged into entry#7 after the calls. So there must be some activities that cause the map to change."

This led Christoph Hellwig to identify a potential race condition in the NFS server code:

"Hmm. We only insert layouts (and search for conflicts) after calling ->proc_layoutget. So this might be racy against unwritten extent conversion, or other writers, which is a bit of an issue. I guess we need to fix nfsd4_layoutget to insert an in-progress layout before calling into ->layouget."

Dai Ngo requested clarification on the race condition but acknowledged the need for the fix:

"I can't quite see the race condition regarding layoutget here. Could you please explain?"

Final Conclusions

The discussion concluded with agreement on two fronts:

  1. Immediate Fix: Dai Ngo will resubmit the patch series combining the removal of XFS_BMAPI_ENTIRE (replaced with 0) and a fix for uninitialized imap handling in the error path:

"I'll resubmit the patch series with both fixes combined: the uninitialized imap handling in the error path and the replacement of XFS_BMAPI_ENTIRE with 0."

  1. Deeper nfsd Fix: Christoph Hellwig identified a separate issue requiring nfsd4_layoutget to insert an "in-progress" layout before calling into the filesystem's layoutget handler, to prevent races against unwritten extent conversions or concurrent writers. This remains an open item for future work.

Classification

This discussion centers on a bug fix for pNFS LAYOUTGET operations in XFS, with implications for NFS client development regarding robustness against malformed server responses. The exchange also uncovered a potential race condition in the NFS server code that warrants separate attention.
