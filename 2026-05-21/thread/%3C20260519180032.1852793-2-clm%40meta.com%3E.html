nfsd: drain backchannel callbacks before freeing a session (UAF fix)

Summary

nfsd: drain backchannel callbacks before freeing a session

Type: Bug fix — a use-after-free in the NFSv4 server (nfsd) backchannel callback path, triggered by DESTROY_SESSION racing with an in-flight CB RPC on rpciod.

This is a two-patch series posted by Chris Mason (Meta) on May 19, drawing quick review from both J. Bruce Fields and Jeff Layton within a few hours. The discussion is squarely about NFS server-side callback teardown safety, not the client — though the backchannel is the mechanism by which the server pings NFS clients for delegation recalls and layout-return notifications, so the fix protects the integrity of that client-facing RPC path.

The bug

Mason's cover letter frames the problem concisely:

"DESTROY_SESSION can free an nfsd4_session while a backchannel callback for the same client is still live on rpciod, leaving clp->cl_cb_session as a dangling pointer."

The detailed PATCH 2/2 lays out the race with an ASCII two-CPU diagram: nfsd4_probe_callback_sync() only flushes cl_callback_wq, which drains the work_struct that submits CB RPCs but returns before the rpciod-side completion tail (rpc_call_done -> rpc_release -> nfsd41_destroy_cb) has run. A CB RPC submitted just before teardown can therefore still be executing on rpciod, with clp->cl_cb_session pointing at the session about to be freed.

Mason pinpoints why the existing reference-count gate doesn't help:

"The se_ref gate in nfsd4_put_session_locked() does not close this window: the backchannel dispatch path does not take a se_ref via nfsd4_get_session_locked(), so se_ref can already be zero while a CB RPC is still in flight against the session."

The fix is to wait on cl_cb_inflight — a counter introduced years earlier by commit 2bbfed98a4d8 ("nfsd: Fix races between nfsd4_cb_release() and nfsd4_shutdown_callback()") — after the workqueue flush, so every queued CB RPC has reached its rpc_release before the caller proceeds to free the session. Mason notes that nfsd4_shutdown_callback() already does this for exactly this reason; nfsd4_probe_callback_sync() was simply never updated when cl_cb_inflight was introduced. The patch carries a Fixes: tag pointing at that original commit, and — notably — an Assisted-by: kres (claude-opus-4-7) line indicating AI-assisted development.

The second half: clearing the stale pointer

PATCH 1/2 addresses a secondary hazard that survives even after the drain: clp->cl_cb_session still caches the freed pointer, because no destroy, expire, or shutdown path clears it — the stale value lingers until the next CREATE_SESSION overwrites it. Mason identifies three helpers that dereference the cached session and could hit a use-after-free in that window:

"A backchannel dispatch that races in during that window dereferences the freed session through one of three helpers: nfsd41_cb_get_slot(), nfsd41_cb_release_slot(), nfsd4_cb_sequence_done()."

The fix clears the cached pointer under clp->cl_lock (using a WRITE_ONCE store) and pairs it with READ_ONCE loads plus NULL checks in the three helpers so each takes its early-return/requeue path. The encode/decode helpers are argued to be safe because they only read cl_cb_session from in-flight RPCs that nfsd4_probe_callback_sync() has already quiesced.

Review: Bruce Fields questions whether the drain is even needed

The first reply came from J. Bruce Fields, who pushed back on the premise of patch 2/2 — suggesting the existing rpc_shutdown_client() path may already guarantee completion:

"nfsd4_probe_callback_sync()->nfsd4_probe_callback() sets NFSD4_CLIENT_CB_UPDATE and calls nfsd4_run_cb(), which should ensure work is queued that will run nfsd4_run_cb_work and call nfsd4_process_cb_update()->setup_callback_client(), which calls rpc_shutdown_client()--and I think that isn't supposed to return until any rpc callbacks have run? And since that's called from the workqueue, the flush should do it."

He was candid about his uncertainty: "I may not have thought about this in 4 years, but you did cc me, so if I'm raving, well, you get what you deserve...." This is an open question rather than a rejection — Fields is asking whether the explicit cl_cb_inflight wait is redundant with the workqueue flush already exercising rpc_shutdown_client().

Review: Jeff Layton validates both problems and spots a spin-loop

Jeff Layton's reply to patch 1/2 is the most substantive technical contribution. He opens with a wry observation about the AI-assisted review process:

"Dueling agent review. Looks like both problems are valid:"

Layton flags two issues:

  1. Series ordering / commit message. The cover letter and patch 1/2 say "The parent commit drains in-flight backchannel callbacks," but the drain is actually added by patch 2/2, which applies after patch 1/2. He asks: "Should 'The parent commit drains' be rephrased, or should the series order be swapped so the drain lands first?"

  2. A busy-spin in nfsd41_cb_get_slot(). When ses is NULL (the new early-return path), the function returns false without calling rpc_sleep_on(). Layton traces through the RPC state machine to show this creates a livelock: because nfsd41_cb_get_slot is the rpc_call_prepare callback, and it returns without either starting the call or sleeping the task, __rpc_execute() loops back and calls prepare again indefinitely. He walks through the exact loop:

"When prepare returns without calling rpc_call_start() and without sleeping the task, __rpc_execute() loops back and calls prepare again because tk_action is unchanged and the task is not queued."

He confirms the path is reachable — after nfsd4_destroy_session() clears cl_cb_session but before cl_cb_client is torn down, another client's delegation recall can queue a new CB RPC that enters this spin. His suggested fix sets an error status to break the loop:

"Would something like the following avoid the spin? if (!ses) { task->tk_rpc_status = -EIO; return false; } That would route the task through rpc_exit_task -> nfsd4_cb_sequence_done (which already handles NULL session via goto requeue) and on to nfsd4_cb_release, breaking the loop."

Final status: Reviewed-by granted with caveats

Layton's reply to the cover letter closes the thread with a conditional approval:

"Assuming you want to reverse the order, you can add this: Reviewed-by: Jeff Layton jlayton@kernel.org"

"The other review comment from Claude sounds reasonable too, but harder to hit in practice."

So the series has a Reviewed-by from one of the core nfsd maintainers, contingent on reordering (drain first, then NULL-clear) or at minimum fixing the commit-message wording. The spin-loop fix for nfsd41_cb_get_slot() is acknowledged as valid but "harder to hit in practice." Bruce Fields' question about whether rpc_shutdown_client() already covers the drain remains open and would need Mason's response before the series is fully settled.

Key takeaways

  • Bug class: Use-after-free on session teardown, a classic NFSv4 backchannel race that has been partially addressed before (commit 2bbfed98a4d8) but with a gap in nfsd4_probe_callback_sync().
  • Fix strategy: Two-layer defense — wait on cl_cb_inflight to drain the rpciod completion tail, and NULL out the cached cl_cb_session pointer so any future regression is caught by early-return guards rather than silently dereferencing freed memory.
  • Open items for v2: (a) reorder or reword the series; (b) add -EIO status to the NULL-session path in nfsd41_cb_get_slot() to avoid a prepare-loop spin; (c) resolve Bruce Fields' question about whether the explicit drain is redundant with rpc_shutdown_client().
  • Notable process detail: Both patches carry Assisted-by: kres (claude-opus-4-7) tags, and Layton's "Dueling agent review" remark highlights the growing role of AI in kernel patch preparation and review.
