sunrpc: clear rq_procinfo in svc_release_rqst to prevent double-free

Summary

sunrpc: Clearing rq_procinfo in svc_release_rqst() to Prevent Double-Free

A compact but security-relevant bug-fix thread landed on the linux-nfs list this week, with all three messages posted on 2026-05-20. The discussion centers on a stale-pointer hazard in the kernel's NFS server-side RPC layer (sunrpc) that can be triggered by a reused svc_rqst and ultimately lead to a double-free or use-after-free.

Nature of the change: bug fix (security hardening)

This is squarely a bug fix, not a new feature or protocol change. The patch is marked with a Fixes: tag pointing at commit d9adbb6e10bf ("sunrpc: delay pc_release callback until after the reply is sent") and carries Cc: stable@kernel.org, signaling that it is intended for backporting to stable trees.

The vulnerability, as described by the author

Ren Wei posted the patch on behalf of Luxiao Xu, explaining the root cause:

"The svc_release_rqst() function unconditionally calls rqstp->rq_procinfo->pc_release. However, svc_process_common() does not clear rq_procinfo when a worker thread starts processing a new request."

The failure scenario, in the author's words:

"If a previous RPC selected a procedure with a non-idempotent release hook, and the subsequent RPC takes an early error path before a new rq_procinfo is installed (e.g., due to an oversized RPC fragment, bad auth, or unknown program), the stale release hook will run against reused state from the earlier RPC. This leads to a double-free or use-after-free vulnerability."

The minimal fix proposed is to set rqstp->rq_procinfo to NULL immediately after running the release hook inside svc_release_rqst(). The patch touches only net/sunrpc/svc.c (3 insertions, 1 deletion). Four reporters are credited in the commit message: Yuan Tan, Yifan Wu, Juefei Pu, and Xin Liu.

Review response

Jeff Layton responded a couple of hours later with a brief:

"Reviewed-by: Jeff Layton jlayton@kernel.org"

Chuck Lever asks for a hardened respin

The most substantive technical input came from Chuck Lever, who endorsed the direction but asked that the fix be broadened to make the lifecycle of rq_procinfo explicit across all entry points:

"We should harden this fix a bit by extending it so that:

  • svc_release_rqst() /always/ clears rq_procinfo after the optional pc_release() call, not only when pc_release exists.
  • svc_process() clears rq_procinfo at request entry before early decode/drop paths.
  • svc_process_bc() does the same before its early backchannel decode return."

Lever framed the rationale in terms of making the invariant obvious to future readers:

"That makes the lifecycle explicit: each request starts with no selected proc, pg_init_request() installs one, svc_release_rqst() consumes it. It guarantees that the error flows in svc_process() won't encounter a non-NULL rq_procinfo pointer when there is nothing to release."

He closed by asking the author to respin: "Can you respin your patch with those changes?"

Status and outlook

The thread ends here for this week — no v2 has been posted yet. The consensus is clear: the underlying bug (a stale rq_procinfo triggering a non-idempotent pc_release on early-error paths of svc_process() / svc_process_bc()) is real, the minimal fix is correct but narrow, and the maintainers want a slightly broader patch that nulls the pointer at every request entry point so the lifecycle invariant holds by construction. Expect a v2 from Luxiao Xu / Ren Wei in the coming days, after which the change should be straightforward to merge and backport to stable.

Relevance to NFS client development

While this fix lives on the server-side sunrpc path (net/sunrpc/svc.c), it is worth flagging for client developers because the same sunrpc subsystem underpins both directions of an NFS mount, and the early-error paths called out (oversized fragment, bad auth, unknown program) are exactly the conditions a misbehaving or hostile peer can induce against an in-kernel NFS server. Hardening the release-hook lifecycle here reduces the attack surface for any host that runs nfsd alongside its client stack.
