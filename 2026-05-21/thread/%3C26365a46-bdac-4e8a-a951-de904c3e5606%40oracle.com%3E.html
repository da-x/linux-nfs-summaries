XFS pNFS LAYOUTGET: Finalizing v2 — locking, page faults, and reflink checks

Summary

XFS pNFS LAYOUTGET: Finalizing v2 Patch Plans — Locking, Page Faults, and Reflink Checks

Classification

This thread concerns a bug fix for overlapping extents returned by XFS during pNFS LAYOUTGET operations. The issue causes ambiguity for NFS clients when selecting device layouts and managing data states. This week's messages represent the closing exchanges on the patch revision plan for version 2 of Dai Ngo's fix series.

Bridging Prior Weeks

As detailed in prior summaries, Dai Ngo's original patch proposed replacing the XFS_BMAPI_ENTIRE flag with 0 in xfs_fs_map_blocks() to prevent overlapping extents when multiple calls are made within a single LAYOUTGET request. Over the preceding weeks, Christoph Hellwig identified both the core overlap bug and a separate race condition in the NFS server code where layouts are inserted only after calling into ->proc_layoutget. Darrick J. Wong raised three specific review questions on locking adequacy, multi-map API design, and reflink/realtime inode check placement. Christoph Hellwig responded to each, and Dai Ngo outlined a pragmatic path forward.

This Week's Activity (May 20)

The final two messages of this week's window consist of Darrick J. Wong and Dai Ngo reaching consensus on the remaining open items for v2.

Page Fault Race Clarification

Dai Ngo had previously questioned whether page faults were relevant during server-side LAYOUTGET construction, arguing that "the server is not servicing actual data accesses through page faults when constructing a LAYOUTGET response." Darrick J. Wong clarified the scenario in his May 20 message:

"Some other process on the nfs server mmaps the file and generates faults."

Dai Ngo acknowledged this point, noting the practical consequence:

"This would cause a layout conflict and this process would be delayed until the nfs server finishes recalling the layout from the first client."

While this exchange did not resolve whether additional locking (such as the mmap invalidation lock) is strictly necessary in xfs_fs_map_blocks(), it established that concurrent page faults on the NFS server are indeed a realistic concern — even if they manifest as layout conflicts rather than direct data corruption.

Multi-Map API: Deferred to Future Work

On the question of whether ->map_blocks should be enhanced to return multiple iomaps in a single call (thereby eliminating the need for repeated calls that can produce overlaps), Darrick J. Wong endorsed Dai Ngo's earlier position to defer this work:

"Agreed."

Both participants concurred that multi-map support requires coordinated changes across nfsd and XFS, and should be addressed in follow-up patches rather than complicating the immediate bug fix.

Reflink and Realtime Inode Checks

The most concrete action item emerged around Darrick's third question: whether reflink and realtime inode checks need to be re-assessed after acquiring the inode lock, since these properties can change concurrently. Christoph Hellwig had already confirmed "Yes," and Dai Ngo committed to the fix:

"I can move the check for reflink and realtime inode inside the ilock in v2 of this patch series."

Darrick J. Wong affirmed:

"Yeah, that probably needs to be made too. :)"

Dai Ngo confirmed the plan in his final message:

"Thanks! I'll include this change in v2."

Final Conclusions

The discussion concluded with a clear, agreed-upon action plan for Dai Ngo's v2 patch series:

  1. Replace XFS_BMAPI_ENTIRE with 0 in xfs_fs_map_blocks() — the core fix preventing overlapping extents.
  2. Move reflink and realtime inode checks inside the inode lock acquisition, as these properties can change concurrently and must be re-validated under proper locking.
  3. Defer multi-map API enhancements to future coordinated work between nfsd and XFS.

The broader question of whether xfs_fs_map_blocks() requires additional locking (e.g., the mmap invalidation lock) remains an open concern, though the participants acknowledged that concurrent page faults would manifest as layout conflicts rather than immediate data corruption.

Implications for NFS Client Development

This fix has direct relevance for NFS client robustness. As Christoph Hellwig noted in prior weeks:

"And the client should probably also validate that extents of the same kind do not overlap (read vs write extents are allowed to overlap)."

With the server-side fix progressing toward v2, clients will encounter fewer malformed LAYOUTGET responses. However, defensive validation on the client side remains advisable as a belt-and-suspenders approach against any future regressions or edge cases.
