Summary

nfsd: Fix Inverted cp_ttl Check in Async Copy Reaper

Overview

This week's thread is a compact, same-day bug-fix cycle on the NFS server side (nfsd), touching the NFSv4.2 asynchronous copy (COPY / OFFLOAD_STATUS) machinery. It is squarely a bug fix, not a new feature or protocol change: a one-line predicate inversion in nfsd4_async_copy_reaper() was causing completed async-copy state to be freed far too early, breaking the client's ability to query results via OFFLOAD_STATUS.

The thread ran from patch posting through review and merge into nfsd-testing within roughly two and a half hours on Thursday, 2026-05-21 — a textbook quick turnaround for a small, well-understood fix.

The Bug

Jeff Layton opened the thread with the original patch, explaining the intended behavior of the reaper:

"nfsd4_async_copy_reaper() is supposed to keep completed async copy state around for NFSD_COPY_INITIAL_TTL (10) laundromat ticks so that OFFLOAD_STATUS can report the result, then reap the state once the countdown expires."

The problem was a classic inverted test. As Layton described:

"The TTL predicate is inverted: if (--copy->cp_ttl) is true while ticks remain and false when the counter reaches zero. This causes the copy to be reaped on the very first tick (cp_ttl goes from 10 to 9, which is non-zero) instead of after all 10 ticks elapse."

The practical consequence for NFS clients was direct:

"Once reaped, OFFLOAD_STATUS returns NFS4ERR_BAD_STATEID because the copy state has already been freed."

Layton also flagged a latent secondary hazard that the current initial value of 10 happens to mask:

"A secondary consequence: if cp_ttl ever reached zero (not possible with the current initial value of 10 since the copy is reaped at 9), the copy would never be added to the reaplist and would leak indefinitely on clp->async_copies."

The fix itself is a one-character negation in fs/nfsd/nfs4proc.c (1 insertion, 1 deletion). The bug was reported by Chris Mason at Meta.

Self-Corrections During Review

In a follow-up minutes after posting, Layton walked back two details:

"Mea culpa. This doesn't need to go to stable so we can drop that tag. It's a bug, but not one that results in a crash or data corruption or anything."

He also noted the patch should have carried an Assisted-by: tag crediting an AI assistant (kres:claude-opus-4-6), an increasingly common convention on the list for AI-assisted patches.

Paulo Alcantara then caught a subtle metadata error in the Fixes: tag:

"Wouldn't aa0ebd21df9c be the correct commit id?"

Layton confirmed:

"Thanks, yes it would. The other commit id is correct for a copy in my tree, but aa0ebd21df9c is the correct upstream one."

This is a small but important detail for stable-tree tooling: the Fixes: hash must reference the upstream commit, not a local variant.

Merge

NFS server maintainer Chuck Lever applied the patch to nfsd-testing the same day:

"Applied to nfsd-testing, thanks!"

The merged commit is 14ba3b4b7cb4d05a070c77226d10dfc332898421.

Significance for NFS Clients

Although the fix lives in nfsd, its impact is felt on the client side of the wire: any NFSv4.2 client issuing an asynchronous COPY and then polling OFFLOAD_STATUS would have been receiving spurious NFS4ERR_BAD_STATEID responses because the server was discarding the copy state on the first laundromat tick rather than after the full 10-tick TTL window. The fix restores the intended contract of the async-copy API and removes a latent memory-leak path should the initial TTL ever be changed to zero in the future.

Conclusions

  • Type: Bug fix (one-line predicate negation), not a feature or protocol change.
  • Root cause: Inverted if (--copy->cp_ttl) test reaped async-copy state on tick 1 instead of after all 10 TTL ticks.
  • User-visible symptom: OFFLOAD_STATUS returning NFS4ERR_BAD_STATEID for still-valid async copies.
  • Latent risk: Memory leak on clp->async_copies if cp_ttl were ever initialized to zero.
  • Outcome: Patch corrected (drop stable tag, fix Fixes: hash to upstream aa0ebd21df9c, add Assisted-by:), and merged into nfsd-testing as 14ba3b4b7cb4 within hours of posting.
