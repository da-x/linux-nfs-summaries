XFS pNFS LAYOUTGET: Locking Concerns, Multi-Map API Debate, and v2 Patch Plans

Summary

This week's activity on the XFS pNFS LAYOUTGET overlapping extents bug fix thread advanced from high-level design debates to concrete patch revision planning. The discussion, sparked by Darrick J. Wong's review questions (raised May 19, just outside this week's window), focused on three technical concerns: locking adequacy in xfs_fs_map_blocks(), the feasibility of returning multiple extent mappings in a single call, and proper placement of reflink/realtime inode checks. Christoph Hellwig and Dai Ngo reached consensus on a pragmatic path forward for version 2 of the patch series.

Classification

This is a bug fix discussion addressing overlapping extents returned by XFS during pNFS LAYOUTGET operations — a regression that causes ambiguity for NFS clients when selecting device layouts and handling data states. The exchange also touches on potential API enhancements for future multi-map support.

Bridging Prior Weeks

As summarized in prior weeks, Dai Ngo's original patch proposed replacing the XFS_BMAPI_ENTIRE flag with 0 in xfs_fs_map_blocks() to prevent overlapping extents when multiple calls are made within a single LAYOUTGET request. Christoph Hellwig had also identified a separate race condition in the NFS server code where layouts are inserted only after calling into ->proc_layoutget, potentially racing against unwritten extent conversions or concurrent writers.

Key Technical Arguments This Week

Christoph Hellwig's Responses to Locking and API Questions

In response to Darrick J. Wong's three-point review, Christoph Hellwig addressed each concern in his May 20 message:

On the question of whether page faults could interfere with layout construction due to insufficient locking:

"Looks like it."

On whether ->map_blocks should accept an array element count to enable multiple iomaps in a single lock cycle:

"I guess we need to do that, or revert the code to provide multiple maps for now."

And on whether reflink and realtime inode checks must be re-evaluated after acquiring the inode lock:

"Yes."

Christoph also added Sergey (the author of the multi-mapping code) to the discussion thread for further input.

Dai Ngo's Pragmatic Response

Dai Ngo responded later on May 20 with a measured, stepwise approach to addressing the concerns:

On the page fault concern, Dai pushed back on its relevance to pNFS layouts:

"I also don't see how page faults are relevant in the context of pNFS layouts. The server is not servicing actual data accesses through page faults when constructing a LAYOUTGET response"

He noted that he had already described scenarios where file mappings change between successive xfs_fs_map_blocks() calls triggered by a single LAYOUTGET request — suggesting the underlying issue is broader than just page fault races.

On the multi-map API question, Dai advocated for separating the immediate bug fix from longer-term architectural improvements:

"I think we should address the immediate problem first by replacing XFS_BMAPI_ENTIRE with 0, and handle support for returning multiple map entries from a single call to xfs_fs_map_blocks() in follow-up patches. That work is more involved, as it requires coordinated changes in both the nfsd and XFS code."

On the reflink/realtime inode check placement, Dai committed to a straightforward fix:

"I can move the check for reflink and realtime inode inside the ilock in v2 of this patch series."

Evolution of the Discussion

The conversation evolved from identifying potential locking deficiencies (Darrick's questions) through Christoph's acknowledgment of those concerns, to Dai's pragmatic resolution plan. Rather than attempting a comprehensive redesign of the map_blocks() API in this patch cycle, the participants agreed on a two-track approach:

  1. Immediate fix (v2): Replace XFS_BMAPI_ENTIRE with 0 and move reflink/realtime checks inside the inode lock.
  2. Future work: Develop coordinated changes across nfsd and XFS to support returning multiple map entries from a single xfs_fs_map_blocks() call, potentially eliminating the need for repeated calls altogether.

Final Conclusions

The discussion concluded with clear action items for Dai Ngo's v2 patch series:

  • Replace XFS_BMAPI_ENTIRE with 0 in xfs_fs_map_blocks() to prevent overlapping extents — the core bug fix.
  • Move reflink and realtime inode checks inside the inode lock acquisition, as confirmed necessary by both Christoph Hellwig and Dai Ngo.
  • Defer multi-map API enhancements to follow-up patches requiring coordinated nfsd/XFS changes.

The broader question of whether xfs_fs_map_blocks()'s locking (taking only i_rwsem and XFS_ILOCK, but not the mmap invalidation lock) is sufficient remains an open concern, though Dai argued that page faults are not relevant during server-side LAYOUTGET construction.

Implications for NFS Client Development

While this thread primarily addresses server-side XFS behavior, the fix has direct implications for NFS clients. Overlapping extents in LAYOUTGET responses create ambiguity when clients select device layouts and manage data state. A robust client should validate that extents of the same kind do not overlap — a point Christoph Hellwig raised in prior weeks:

"And the client should probably also validate that extents of the same kind do not overlap (read vs write extents are allowed to overlap)."

This week's patch progression brings the server-side fix closer to resolution, reducing the likelihood that clients will encounter malformed layout responses.
