NFS writeback UAF fix: dereference loop-local req in nfs_write_completion

Summary

NFS writeback use-after-free: a one-line fix for a multi-page-group race

This week's activity on this thread is a single, self-contained patch from Dave Jones that plugs a slab-use-after-free in the NFS client's write-completion path. It is squarely a bug fix — no new feature, no protocol change — and it lands as a one-line correction to fs/nfs/write.c.

The bug

The regression was introduced by commit 5d3869a41f36 ("NFS: fix writeback in presence of errors"), which added a dereference of hdr->req->wb_lock_context inside the per-request loop of nfs_write_completion(). As Jones explains in the patch submission:

"hdr->req is set once at nfs_pgheader_init() time and is not refcount-protected for the lifetime of the loop; when hdr aggregates requests from multiple page groups (common under heavy NFSv3 writeback), a parallel COMMIT on hdr->req's group can drop the last reference and free it while the outer loop is still iterating requests from other groups."

In other words, hdr->req is a stale pointer that outlives its own refcount. The race window opens whenever a single pgio header spans multiple page groups — which, per Jones, is "common under heavy NFSv3 writeback" — and a concurrent COMMIT releases the first group's pages while the completion loop is still walking later groups.

KASAN caught it as an 8-byte read at offset +24 of a freed nfs_page slab object (the wb_lock_context field):

"BUG: KASAN: slab-use-after-free in nfs_write_completion+0x8f8/0xa50 [nfs]"

The full report, reproduced in the patch, shows the allocation coming from an rsync write path (nfs_update_folio → nfs_page_create) and the free coming from a parallel COMMIT (nfs_commit_release_pages → nfs_unlock_and_release_request → nfs_page_group_destroy). The reproducer was running on 7.1.0-rc4+ with KASAN enabled.

The fix

The correction exploits an invariant Jones calls out:

"All requests in a given pgio share the same open_context, so reading the loop-local req's wb_lock_context yields the same value and is safe -- req is still on hdr->pages and holds its writeback kref through the commit branch."

So the patch simply swaps hdr->req for the loop-local req, which is guaranteed to be alive for the duration of that iteration because it is still linked into hdr->pages and pinned by its writeback kref. The diff is one insertion, one deletion in fs/nfs/write.c.

Review and status

The patch carries a Reviewed-by from Jeff Layton (jlayton@kernel.org) and a Fixes: tag pointing at 5d3869a41f36. It is Cc'd to the NFS maintainers — Olga Kornievskaia, Trond Myklebust, Anna Schumaker — and to linux-nfs@vger.kernel.org. Jones also credits AI assistance:

"Assisted-by: Claude:claude-opus-4-7"

No replies or further discussion have appeared in the thread as of this week's window; the submission stands on its own with a reviewer already on board, making it a strong candidate for merge into the current development cycle.

Why it matters

This is a textbook example of why refcount discipline in the NFS writeback path is so delicate: the pgio header deliberately aggregates work across page groups to amortize COMMIT overhead, but that aggregation means any per-header pointer must be either refcount-protected for the whole loop or replaced by a per-iteration reference. The original "fix writeback in presence of errors" commit took the latter route incorrectly; Jones's patch restores it with minimal churn. For NFSv3 users running heavy writeback (the KASAN trace shows an rsync workload), this eliminates a real use-after-free that could corrupt slab memory or, in principle, be exploited.
