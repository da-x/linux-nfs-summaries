PATCH: Fix nfs_access_calc_mask() corner cases for special files

Summary

NFS client: Fix nfs_access_calc_mask() corner cases for special files

Overview

This week, Red Hat's Ondrej Mosnacek submitted a bug-fix patch targeting the NFS client's access-permission calculation logic. The patch addresses two inconsistencies in nfs_access_calc_mask() in fs/nfs/dir.c that caused incorrect behavior when calling access(2) with X_OK on special files (FIFOs, block devices, character devices).

Key Technical Arguments

The patch identifies two distinct bugs in the existing code:

  1. Inconsistent special-file handling: The special case for files that are neither regular files nor directories was inconsistent with the permissions actually requested by nfs_do_access(). Mosnacek notes:

    "The special case for special files (neither regular file nor directory) is inconsistent with the perms requested in nfs_do_access()"

  2. Incorrect MAY_WRITE condition: The check used a bare bitwise AND rather than the full equality comparison pattern used elsewhere:

    "the MAY_WRITE condition seems incorrect (checks just access_result & NFS_MAY_WRITE instead of (access_result & NFS_MAY_WRITE) == NFS_MAY_WRITE as is the pattern for the other cases)"

The fix unifies the treatment of regular and special files, since nfs_access_calc_mask() already requests the same access bits for both:

"Since nfs_access_calc_mask() requests the same access bits for regular and special files, we end up with nfs_access_calc_mask() that treats both the same as well."

User-Visible Impact

The most significant consequence is a behavioral inconsistency between NFS and classic local filesystems. On local filesystems, access("...", X_OK) on a FIFO, block device, or character device depends on the file's UNIX permission bits. On NFS, it would always fail regardless of permissions:

"On classic filesystems the result of that call depends on the UNIX permissions of the file, while on NFS it would always fail."

Mosnacek included a comprehensive test script in the commit message demonstrating the difference by creating a FIFO, a character device (c 1 3), and a block device (b 7 0), then comparing os.access(..., os.X_OK) results between the local export directory and the NFS mount—both before and after applying chmod u+x.

He also noted a practical caveat for Fedora/RHEL users:

"on some Fedora/RHEL systems you may need to also do setenforce 0 before running the script, because the SELinux policy could block the execute permission for the special files on the server side - this bug will be fixed independently in the policy."

Significance for NFS Client Development

This patch is a small but important correctness fix that aligns NFS client semantics with POSIX expectations for access(2). The fact that it was triggered by testing special-file execute permissions—likely as part of broader filesystem compatibility testing—underscores the ongoing effort to close behavioral gaps between NFS and local filesystems. The regression trace back to ecbb903c5674 also highlights how permission-mapping changes in the NFS client can have subtle side effects on edge-case file types.
