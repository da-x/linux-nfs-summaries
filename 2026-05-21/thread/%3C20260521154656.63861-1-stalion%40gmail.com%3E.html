nfsd: Fix unchecked get_user() of princhashlen in v2 upcall path

Summary

nfsd: check get_user() return when reading princhashlen

A compact, one-day bug-fix exchange landed this week on the linux-nfs list, closing out a small but real correctness hole in the NFSv4 server's state-recovery upcall path. The discussion was entirely about a bug fix — no protocol change, no new feature — and it moved from patch to review to merge within roughly four hours.

The bug

Dominik Woźniak opened the thread with a one-line-class patch targeting __cld_pipe_inprogress_downcall() in fs/nfsd/nfs4recover.c. His diagnosis was precise:

"In __cld_pipe_inprogress_downcall(), the get_user() that reads princhashlen from the userspace cld_msg_v2 buffer does not check its return value. A failing copy leaves princhashlen with uninitialised stack contents, which are then used to drive memdup_user() and stored as princhash.len on the resulting reclaim record."

In other words, if the copy from the userspace cld_msg_v2 buffer failed, the kernel would proceed with a garbage length value, feed it into memdup_user(), and bake that bogus length into the princhash.len field of the recovery record. Woźniak noted the inconsistency was conspicuous — every other get_user() in the same function checks its return; only this one slipped through. He attributed it to a likely copy-paste oversight:

"which is most likely a copy-paste oversight from when v2 upcalls were introduced."

The fix mirrors the existing pattern used a few lines above for namelen, and he pointed out that cleanup was already handled because namecopy is declared with __free(kfree), so the early return path frees the already-allocated buffer automatically. The patch carried a Fixes: tag pointing at commit 6ee95d1c8991 ("nfsd: add support for upcall version 2"), and touched just three lines (2 insertions, 1 deletion).

Review and merge

Jeff Layton responded within six minutes of the posting, granting a review with a brief but unambiguous endorsement:

"Nice catch."

"Reviewed-by: Jeff Layton jlayton@kernel.org"

Chuck Lever then applied the patch to the nfsd-testing tree later that same day:

"Applied to nfsd-testing, thanks!"

The fix landed as commit aff199f9ef2d1870edbc27253798bd97ee9c65be.

Takeaways

This is a textbook example of the kind of low-risk, high-value hardening work that keeps the NFS server robust: a missing return-value check on a get_user() call in the v2 upcall path could have led to an out-of-bounds or over-sized allocation driven by uninitialised stack data. Because the flaw was introduced with the v2 upcall feature and went unnoticed, it underscores how easy it is for a single unchecked copy to slip past review when surrounded by correctly-written siblings. The thread itself was efficient — patch, quick Reviewed-by from a core nfsd maintainer, and same-day merge into nfsd-testing — and there were no objections or follow-up questions raised.
