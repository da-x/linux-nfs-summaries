fhandle: UAF fix for unlocked mnt_ns read in may_decode_fh() — rapid review and merge

Summary

fhandle: UAF fix for unlocked ->mnt_ns read in may_decode_fh()

Type: Bug fix (use-after-free in VFS file-handle layer, affecting NFS client via open_by_handle_at())

Overview

Google's Jann Horn submitted a two-day sprint to fix a use-after-free (UAF) in the kernel's file-handle decoding path — code that NFS clients exercise through open_by_handle_at() when resolving an opaque file handle back to a filesystem path. The bug, introduced by a 2024 commit that relaxed permission checks on open_by_handle_at(), allowed a concurrent unmount to free the mount namespace while may_decode_fh() was still reading mount::mnt_ns without any lock held.

The v1 patch landed Wednesday evening (June 3), drew immediate and detailed review from Al Viro within an hour, and the revised v2 was applied to the vfs.fixes branch by Christian Brauner the following morning (June 4) — a remarkably fast turnaround for a concurrency fix touching core VFS semantics.

The Bug

Jann Horn's v1 submission laid out the race in a clear three-column diagram:

"may_decode_fh() accesses mount::mnt_ns without holding any locks; that means the mount can concurrently be unmounted, and the mnt_namespace can concurrently be freed after an RCU grace period."

The trigger requires a mount created via open_tree(..., OPEN_TREE_CLONE): one thread calls close() on the file descriptor, which dissolves the mount tree and frees the namespace; another thread simultaneously enters open_by_handle_at(), reaches may_decode_fh() → is_mounted(), and dereferences the now-freed mnt_namespace.

Horn noted the practical reachability constraints:

"This bug is unreachable unless one of the following is set: CONFIG_PREEMPTION, CONFIG_RCU_STRICT_GRACE_PERIOD — because it requires an RCU grace period to happen during a syscall without an explicit preemption."

He also assessed the security impact as limited:

"This doesn't seem to have interesting security impact; worst-case, it could leak the result of an integer comparison to userspace (from the level check in cap_capable()), cause an endless loop, or crash the kernel by dereferencing an invalid address."

The fix was straightforward — wrap the mnt_ns access in rcu_read_lock() (mirroring what __prepend_path() already does) — but the subtlety lay in why RCU is sufficient here.

The Review: Documenting mnt_namespace Lifecycle

Al Viro responded within 37 minutes, not objecting to the fix but pressing for a proper explanation of why RCU access is valid:

"Umm... It's somewhat subtle - at the very least you need to explain why there will be an RCU delay between umount_tree() clearing that and having the sucker freed."

This kicked off a focused discussion about the mnt_namespace lifecycle. Viro explained the invariant in a follow-up:

"Basically, the store that cleared ->mnt_ns has been done in namespace_sem scope and that scope is either no later than the scope in put_mnt_ns() that has dropped the active refcount of ns to zero. At the beginning of that scope in put_mnt_ns() we are guaranteed to have the passive refcount positive. Dropping the passive reference happens after an rcu delay started in later in the same namespace_sem scope and namespace is not freed until the passive refcount reaches zero."

He then confirmed:

"TL;DR: your fix is correct, but needs a better explanation of correctness. If nothing else, I'd like to have the above findable on lore - I've way too many pieces of half-baked docs sitting around in local notes as it is ;-/"

Horn proposed comment wording, and Viro refined the terminology — the namespace is "active or deactivating," not simply "active," because mounts within a namespace do not pin it:

"Mounts within a namespace do not pin it - it's the other way round; they are guaranteed to stay live until they leave the sucker. Anything that hasn't left by the time the active refcount of namespace drops to zero will get pushed out."

Viro also flagged a documentation gap in general:

"The lifecycle for mnt_namespace really needs to be documented; right now we have a maze of twisty little functions around that area and it takes quite a non-trivial amount of searching to recall the names - and I am familiar with the area ;-/"

v2 and Merge

Horn posted v2 about 2 hours later, incorporating Viro's feedback:

"Changes in v2: improve comment on mnt_ns semantics based on discussion with viro@"

The patch touches three files (fs/fhandle.c, fs/mount.h, fs/namespace.c), adding the rcu_read_lock() guard, documenting mnt_ns semantics in the header, and converting racing writers to use WRITE_ONCE(). It carries a Fixes: tag pointing at commit 620c266f3949 ("fhandle: relax open_by_handle_at() permission checks") and is Cc'd to stable.

Horn also offered additional tooling:

"I used custom tooling to force this race condition to occur and check that it leads to a KASAN splat - let me know if you want me to create a kernel patch to force the race condition and a reproducer you can run."

And acknowledged his own earlier oversight in reviewing the original commit:

"I remember Christian asking me for feedback on the patch that introduced the bug, and I missed the bug because I didn't realize what the semantics of mount::mnt_ns are..."

Christian Brauner applied the patch to vfs.fixes on June 4 at 07:40 UTC:

"Applied to the vfs.fixes branch of the vfs/vfs.git tree. Patches in the vfs.fixes branch should appear in linux-next soon."

In a separate reply on the v1 thread, Brauner provided a useful taxonomy of namespace reference counts that complements Viro's explanation:

"(1) generic reference count of namespaces in general: __ns_ref — for mntns: keeps the mount namespace and the mounts attached to it alive; (2) active reference count... only regulates userspace visibility of the namespace and has no lifetime implications per se; (3) passive reference count of struct mnt_namespace — keeps the mount namespace alive but not the mounts attached to it."

NFS Relevance

While this is a VFS-layer fix, it directly affects NFS client code paths: any user-space program (including NFS-aware tools like nfsdcltrack or container runtimes) that calls open_by_handle_at() on a file handle obtained from an NFS export will traverse may_decode_fh(). The fix ensures the mount-namespace pointer is safely read even under concurrent unmount, preventing a kernel crash or information leak in that path. The stable Cc indicates it will be backported to all supported kernels.
