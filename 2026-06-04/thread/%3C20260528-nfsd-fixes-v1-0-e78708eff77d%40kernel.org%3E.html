nfsd fixes grab bag: v2 signals emerge — stable_how NAK'd, callback UAF reworked, ACL cap and error codes refined

Context from prior week

This thread began on May 28 when Jeff Layton posted a 10-patch "grab bag" of nfsd bug fixes covering remotely-triggerable panics, use-after-frees, DoS vectors, and a few protocol-correctness issues. Initial review from NeilBrown (on PATCH 01's locking), Rick Macklem, and Chuck Lever (on PATCH 09's ACL cap) had already begun. This week saw the full breadth of that review unfold across all ten patches, with Layton committing to a v2 series and one patch being formally self-NAK'd.

Key developments this week

PATCH 06: stable_how return — self-NAK'd

The most consequential decision of the week came from Layton himself on PATCH 06 "NFSD: Enable return of an updated stable_how to NFS clients":

"After looking at this more closely and talking it over with Chuck, self-NAK on this patch. It's not clear to me that it's safe to downgrade a SYNC write to an UNSTABLE one."

Layton acknowledged the spec technically requires it — RFC 1813 §3.3.7 says the server MUST set committed to UNSTABLE if it didn't commit to stable storage — but flagged the practical risk: "it's not clear to me that the clients would be prepared to issue a COMMIT in those cases." Since this only affects users of the "async" export option, he concluded they could "safely just drop this one."

Cedric Blancher followed up on May 30 with a client-side question: could the NFS client simply record write positions and lengths and only issue COMMIT on an explicit flush? Layton confirmed the drop and clarified the client's expected behavior: "the client is more or less expected to keep track of what UNSTABLE writes are still outstanding and eventually issue one or more COMMIT calls to sync them out to disk."

PATCH 01: Delegation revoke BUG_ON — RCU approach adopted

Following NeilBrown's prior-week critique that the spinlock was insufficient, Layton agreed on May 29:

"Good point. I think the right thing to do here is to use RCU to access this pointer. Don't think it's protected by anything now. I'll do some more analysis and put together a v2."

This confirms the fix will move from a spinlock-protected read to proper RCU semantics for fp->fi_deleg_file.

PATCH 02: Callback drain — DoS vector identified, rework planned

Chuck Lever raised a significant concern about PATCH 02's callback drain approach:

"Several NFSD callback done handlers retry indefinitely on NFS4ERR_DELAY via rpc_delay(), so a client that keeps replying DELAY leaves this per-client counter nonzero and blocks the foreground CREATE/BIND/DESTROY_SESSION request even though the callback no longer references the session being torn down."

"this patch potentially introduces a client-controlled DoS vector."

Layton responded with a rework plan: "I'm currently looking at reworking this so that each stage of the callback state machine can tolerate a NULL cl_cb_session pointer. If I can make that work, then we can fix the UAF without blocking." He confirmed "I'll definitely be sending a v2 of the series."

PATCH 03: Grace-end serialization — atomic bit op agreed

A brief but pointed exchange on PATCH 03 saw Chuck Lever question whether try_cmpxchg on a boolean is portable: "Perhaps try_cmpxchg on a boolean variable is not going to behave as you expect on every hardware platform."

Layton initially pushed back — "We just need a single flag here though. try_cmpxchg() had better work the same way on every platform or a lot of stuff is FUBAR. Where wouldn't it?" — but Chuck cited that "Codex suggests on Hexagon, cmpxchg grabs more than just that boolean." Layton was convinced: "Ok, I'm convinced. What I think I'll do is add a new flags unsigned long to struct nfsd_net and we can convert most of the bools in that struct to use it instead."

PATCH 04: Reclaim dedup — commit message recast requested

Chuck Lever noted that the motivating example in the commit message was built on the legacy recovery-directory path, but the actual bug is nfsdcld-only. He asked Layton to "recast the example around the path the patch actually repairs — a boot-time cld enumeration record followed by an in-grace RECLAIM_COMPLETE downcall for the same cl_name." The code change itself was confirmed correct.

PATCH 08: Partial-write detection — data corruption risk debated

This patch drew the most back-and-forth. Chuck Lever questioned its necessity: "How many filesystems can return a short write in this case? My impression was that only the NFS client can do that."

Layton pushed back firmly: "I'm fairly sure Ceph and CIFS can and they're exportable. For local filesystems, I'm not even sure how to audit that. Given that the potential effect is data corruption, omitting this patch based on guesswork about what filesystems are being exported seems unwise."

Chuck conceded partially but noted: "In any event, I think this one needs testing to confirm that the logic change doesn't introduce a regression in known working use cases." The patch appears likely to survive into v2 with added test coverage.

PATCH 09: ACL count cap — error code and rationale refined

The most-discussed patch from last week continued to evolve. Several threads of discussion converged:

Rationale for the cap: Chuck Lever refined his position: "A different take on this might be that we want to ensure that ACLs set via the NFSv4 POSIX ACL extension can always be retrieved via NFSACL. In that case, capping the ACE count at the same number makes sense." Layton confirmed the encoder already enforces this and added a comment to the patch making the rationale explicit.

Error code debate: Chuck Lever argued against nfserr_resource: "nfserr_resource is consistent with other fattr4 decoders, but does not make sense here, IMO. A better choice is nfserr_inval." Layton initially defended the choice: "An ACL that long doesn't violate the spec... the implementation just can't handle it. I do agree that nfserr_resource is not the ideal error code, but it's the closest error I can see that says 'you hit an internal limitation of the server'."

Chuck pressed further: "Among other reasons, NFS4ERR_RESOURCE does not exist outside of NFSv4.0. The server is not out of resources in this case. For NFSv4.1+ NFSD's compound encoder converts it to either nfserr_rep_too_big or nfserr_rep_too_big_to_cache, neither of which are close to appropriate."

Rick Macklem weighed in as the author of the NFSv4 POSIX ACL spec: "Looking at Table 12 in RFC8881, NFS4ERR_INVAL seems the best fit for SETATTR, although I didn't specify that in my draft. (It's a bit unfortunate that there is no other error values, since NFS4ERR_INVAL gets used for everything else, but??) Maybe I should add that to the draft?"

Bubble sort question: Cedric Blancher asked pointedly: "What about (finally) getting rid of the bubble sort?" Layton responded: "It's certainly not clear to me that it's necessary (is it?). I'm not opposed to removing it, but I'd rather not make a behavioral change like this in the context of this patchset. Maybe you could propose a patch to remove it?"

PATCH 10: Symlink target length — named constant nit

Chuck Lever offered a clean-up suggestion: use the protocol-defined NFS4_MAXPATHLEN instead of raw PATH_MAX, and change the boundary from >= PATH_MAX to > NFS4_MAXPATHLEN to match v3's idiom (which accepts a target of exactly PATH_MAX bytes).

Status and conclusions

The thread is clearly heading toward a v2 series. Layton has committed to reworking at least three patches:

  • PATCH 01: switch to RCU for fi_deleg_file access
  • PATCH 02: eliminate the blocking drain in favor of NULL-tolerant callback state machine
  • PATCH 03: convert to atomic bit ops via a new flags field in struct nfsd_net

PATCH 06 is formally dropped (self-NAK). The remaining patches appear close to final, with minor comment/commit-message adjustments pending. No merge decision has been posted yet within this window.

Significance for NFS client development

While this series targets the server, several fixes have direct client-side implications:

  • The delegation revoke race (PATCH 01) is explicitly client-reachable — two clients can trigger a kernel panic by racing on layout stateids.
  • The partial-write detection fix (PATCH 08) prevents silent data corruption when the underlying filesystem returns short writes during direct I/O, which matters for NFS re-export scenarios and Ceph/CIFS-backed exports.
  • The callback UAF fix (PATCH 02) addresses a scenario where a malicious or buggy client can keep replying NFS4ERR_DELAY to trigger a DoS on session teardown — relevant to any NFSv4.1+ client implementation.
  • The stable_how NAK means clients will not see servers downgrade SYNC writes to UNSTABLE via this path, preserving existing COMMIT behavior for "async" export users.
