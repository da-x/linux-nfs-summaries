nfsd filecache shutdown-race fix merged as v4: final patch of Layton's nine-patch bugfix series

Summary

This thread records the v4 (and final) resend of the last remaining patch from Jeff Layton's "locally-triggerable bugs" series — a single-file fix for a per-net shutdown race in the NFS server filecache. The patch was posted on June 4 and merged into nfsd-testing by Chuck Lever within two hours, completing the nine-patch series that hardened nfsd's filecache lifetime management against an entire class of shutdown races.

Context from prior weeks (brief bridge)

This is the culmination of a week-long saga around PATCH 8/9 of Layton's series:

  • v1 (June 1) took get_net() at allocation time; Al Viro objected on scalability grounds (atomic counter on a shared cacheline).
  • v2 (June 2) reworked the patch to take the net ref only at disposal time. Chuck Lever identified two defects: a put-ordering race in nfsd_file_put_local() and a placement flaw where get_net() sat "at the consuming end of the window it is meant to close." Layton conceded on June 3 — "> Ok, I'm convinced, and the fix looks fairly straightforward. If you're ok with merging the rest of the set, I'll plan to resend this one separately." — and Lever merged the other eight patches that same day.
  • v3 (June 4, ~13:57 UTC) was posted as a standalone resend abandoning net references entirely in favor of widening nfsd_gc_lock.

This thread's v4 is a minor contextual-diff fix over v3, posted just ~30 minutes later.

The patch (June 4)

Jeff Layton posted the v4 on June 4 at 14:31 UTC. The cover note is terse and purely mechanical:

"This is the remaining patch from the 9 patch series I posted earlier this week. I'm only sending v4 to fix up a minor contextual diff vs. a patch in Chuck's nfsd-testing branch. This one should merge cleanly."

The bug being fixed is a memory leak (not a UAF) triggered by a race between filecache disposal and per-net namespace teardown. As Layton describes it:

"The shrinker, GC worker, and fsnotify/lease callbacks can unhash an nfsd_file from the rhashtable and then call nfsd_file_dispose_list_delayed() to move it to the per-net dispose list. If nfsd_file_cache_shutdown_net() runs concurrently, its rhashtable walk misses the already-unhashed file, and its drain of the per-net dispose list can run before the file has been queued. The file then sits on the per-net list with no thread to drain it, leaking both the file and its associated state."

The root cause is a synchronization gap: the GC worker and shrinker already hold nfsd_gc_lock while walking the LRU, but they release it before calling nfsd_file_dispose_list_delayed(), and the fsnotify/lease path (nfsd_file_close_inode) has no synchronisation at all.

The three-part fix

  1. Widen nfsd_gc_lock in both nfsd_file_gc() and nfsd_file_lru_scan() to cover the nfsd_file_dispose_list_delayed() call.
  2. Wrap nfsd_file_close_inode() in nfsd_gc_lock so that all three callers of nfsd_file_dispose_list_delayed() hold the lock.
  3. Add a spin_lock/unlock(nfsd_gc_lock) barrier in nfsd_file_cache_shutdown_net() after the purge, "so that any in-progress disposal has fully completed before the per-net list is drained."

Layton justifies the spinlock choice: "All operations inside the lock are non-sleeping (rhashtable lookups, atomic bit/refcount ops, list moves, svc_wake_up), so the spinlock is appropriate."

The change touches a single file (fs/nfsd/filecache.c) with 26 insertions and 9 deletions. It carries Fixes: 43fd953fa7e2 ("nfsd: simplify the delayed disposal list code") and an Assisted-by: Claude:claude-opus-4-8 tag, continuing the series' pattern of AI-assisted analysis with human architectural judgment.

Nature of the discussion

This is a bug fix — specifically a memory leak (file + associated state: struct file, dentry, inode) triggered by a race between filecache disposal and per-net namespace teardown. It is not a new feature or protocol change. The thread itself contains no substantive review discussion; all design debate occurred in the prior v2/v3 threads.

Significance for NFS client development

While the fix is entirely server-side, its implications for client-facing deployments are concrete:

  • Namespace teardown reliability: Any deployment using network namespaces with active NFS exports (containers, k8s pods, multi-tenant servers) could previously leak file cache entries when a namespace was destroyed while files were in-flight through the GC/shrinker path. For clients, this manifests as server-side resource exhaustion over time — each leaked nfsd_file pins an underlying struct file, dentry, and inode.
  • Shrinker interaction: The memory shrinker is a global mechanism that fires under memory pressure. On heavily-loaded NFS servers serving many clients, the shrinker path was one of the three race participants. Clients generating sustained I/O load increase the probability of hitting this window during namespace teardown.
  • Lease/fsnotify path: The fsnotify/lease callback (nfsd_file_close_inode) was the most exposed path since it had no prior synchronization. Clients that trigger file closes (via CLOSE, delegation recall, or lease expiry) while a namespace is being torn down were the primary trigger vector.

Final conclusions

  1. The patch is merged into nfsd-testing as commit 2f8b2f5b13f9. The full nine-patch "locally-triggerable bugs" series is now complete — all patches are in the tree.
  2. The net-reference approach is definitively abandoned in favor of lock widening. This resolves both Al Viro's scalability concern (no atomic counter on a shared cacheline) and Chuck Lever's correctness objection (no new refcount to order).
  3. The series represents a comprehensive hardening of nfsd's filecache lifetime management, eliminating an entire class of shutdown races by consolidating synchronization under nfsd_gc_lock and inlining dispose state into struct nfsd_net.
