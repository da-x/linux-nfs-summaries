sunrpc: fix uninitialized xprt_create_args structure (v1→v2)

Summary

sunrpc: Fix Uninitialized xprt_create_args Structure

Type: Bug fix (NFS client / sunrpc transport layer), with a Cc: stable tag.

The Problem

This week, Hongling Zeng of KylinOS submitted a patch addressing an uninitialized-stack-variable bug in the sunrpc sysfs code path used to add new RPC transports at runtime. As Zeng explained:

"The xprt_create_args structure is allocated on the stack without initialization in rpc_sysfs_xprt_switch_add_xprt_store(). While some fields are manually populated, critical fields like srcaddr, bc_xps, and flags contain uninitialized stack garbage."

Zeng laid out three concrete consequences of leaving those fields as stack garbage:

"This can lead to:

  1. Kernel panic when xs_setup_xprt() dereferences garbage srcaddr
  2. Information leak if srcaddr points to sensitive stack data
  3. Unpredictable behavior if flags has random bits set"

The original fix was a one-line change in net/sunrpc/sysfs.c that zero-initialized the structure after allocation, and it was marked for stable backporting.

The Review

The patch drew quick attention from both of the sunrpc maintainers on the same day.

Jeff Layton endorsed the fix but suggested a stylistic improvement:

"Good catch. You could also just use an initializer here at declaration. A'la: struct xprt_create xprt_create_args = {}; ...but this works too, of course."

He then added a formal Reviewed-by.

Anna Schumaker took a deeper look and raised a substantive design question in her reply:

"I took a look through the transport setup function to see what they do when these fields are set to NULL, and it looks like thy do their best to choose a default value which might be different than the values set to the original transport that we are trying to clone. Can we instead set the missing fields in the xprt_create_args based on how the main xprt is configured?"

In other words, Anna was concerned that zero-initializing would silently fall back to defaults rather than faithfully cloning the source transport's configuration — a behavioral difference for users who add a transport via sysfs.

The Resolution

Zeng responded with a field-by-field analysis explaining why Anna's preferred approach isn't possible under the current design:

"Based on my analysis, these missing fields are not stored in struct rpc_xprt:

  • srcaddr: only passed during creation, not stored in xprt
  • bc_xps: not present in rpc_xprt (only bc_xprt is stored)
  • flags: not stored in xprt after creation Since these values are not available in the main xprt, we cannot copy them. Zero-initializing is the correct approach with the current design."

He then confirmed he had folded in Jeff's stylistic suggestion:

"Updated to v2 with designated initializer as suggested by Jeff."

Outcome

The thread concluded within two days. The consensus was that zero-initialization (now written as a C99-style designated/empty initializer at declaration) is the correct fix given that the relevant fields are transient creation-time arguments and are not persisted on struct rpc_xprt. Anna's concern about cloning fidelity was acknowledged but determined to be unaddressable without a larger design change to store these values on the transport. The patch carries Jeff Layton's Reviewed-by and a stable Cc, positioning it for backporting to stable kernels.

Significance for NFS Client Development

This is a small but important hardening fix in the NFS client's sunrpc transport management path — specifically the sysfs interface that lets administrators hot-add RPC transports (e.g., new TCP/UDP endpoints) without remounting. The bug was latent: it only manifested when exercising the xprt_switch_add_xprt_store sysfs write, but its failure modes (kernel oops on a bad pointer dereference, or stack-data information leak through a crafted srcaddr) are serious enough to warrant stable backporting. It's a textbook example of defensive initialization in kernel code and underscores the value of maintainers like Anna pushing for the right fix rather than just a fix.
