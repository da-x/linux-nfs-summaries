Sachdeva Reports Dirty-Bit Bug: Pages Not Re-dirtied After Failed fsync on ENOSPC/EDQUOT

Summary

Sachdeva Reports Dirty-Bit Bug: Pages Not Re-dirtied After Failed fsync on ENOSPC/EDQUOT

Overview

This week, the long-running discussion on preventing ENOSPC/EDQUOT writeback errors on network filesystems received its most concrete technical contribution to date. Piyush Sachdeva returned with experimental findings that pinpoint a specific behavioral discrepancy in how the kernel handles failed flushes — one that could mask data-loss conditions from applications that correctly check fsync() return values.

Context: Prior Weeks

The thread began on 2026-05-05 when Sachdeva raised the fundamental problem of silent data loss via buffered writes on network filesystems, noting that "A user or application can keep issuing writes to an fd well beyond the available space, since buffered writes return success as soon as data is copied to the page cache." Jeff Layton responded by framing this as an inherent limitation of delayed writeback and recommending that applications proactively call fallocate() to reserve space. In a follow-up the following week, Sachdeva noted that even NFSv4.2's ALLOCATE operation "ends up checking for space during write-back as well," meaning the data-loss window persists, and promised to run experiments.

This Week's Finding: A Dirty-Bit Handling Discrepancy

Sachdeva's message of June 4 reports a specific behavioral bug discovered during those experiments. The key observation concerns what happens when fsync(2) fails with ENOSPC or EDQUOT:

"the NetFS layer, used by the SMB client to do the writeback, doesn't re-set the dirty bit on the pages/folios on which fsync fails. At this point the pages with critical user-data are sitting in the pagecache, but no longer marked dirty/referenced by the inode of the file."

He notes that this behavior is specific to EDQUOT/ENOSPC errors, as opposed to EIO:

"This behavior is seen for EDQUOT/ENOSPC errors, contrary to EIO errors where data is re-dirtied. It seems that EDQUOT/ENOSPC are treated as non-retriable errors, as a reason the dirty bit is not re-set."

Crucially, Sachdeva confirmed this is not limited to SMB:

"I noticed that NFS also has a similar behavior where the pages are not dirty after the failed fsync."

The Practical Consequence

The most alarming implication is that an application which correctly calls fsync() before close() — the recommended pattern for detecting writeback errors — will see the error on fsync(), but if it then retries or inspects state, the data is already effectively orphaned from the inode's dirty list. Moreover:

"Naturally, now that the fsync is tried before calling close, and with the data not-dirty anymore, no errors are seen on close."

This means a second fsync() or close() after the first failure will silently succeed, giving the application false confidence that the problem has been resolved (e.g., after increasing server capacity).

Sachdeva's Proposed Direction

Despite acknowledging that the close(2) manpage states close should not be retried upon failure, Sachdeva argues for a specific kernel behavior change:

"I do believe that the data should still remain dirty. An application (should) calling fsync before close would monitor for errors, and should be able to retry the fsync after increasing the capacity on the server."

This positions the issue as a bug fix candidate: treating ENOSPC/EDQUOT as non-retriable in the writeback error path (by clearing the dirty bit) is inconsistent with how EIO is handled, and it defeats the purpose of the fsync()-before-close() error-detection pattern.

Classification

This week's contribution shifts the thread from an architectural discussion toward a concrete bug fix in NFS client (and NetFS/SMB) writeback error handling. The specific defect is: on ENOSPC/EDQUOT during writeback triggered by fsync(), the kernel fails to re-dirty the affected pages/folios, unlike its behavior for EIO. This makes retry-after-capacity-increase impossible and can lead to silent data loss under memory pressure (clean pages are reclaimable).

Status

No maintainer has yet responded to this week's finding. The thread awaits reaction from the NFS and NetFS maintainers on whether the dirty-bit clearing for ENOSPC/EDQUOT is intentional or an oversight, and whether a patch to re-dirty pages on these errors (matching EIO behavior) would be appropriate.
