libnfsidmap: malloc(0) fix committed to nfs-utils 2.9.2-rc4

Steve's commit confirmation arrived on 2026-05-30, roughly four days after the original patch submission. The terse "Committed..." reply is typical of Dickson's workflow — no lengthy review discussion was needed for a two-line fix.

Bridge from Prior Week

The patch itself was submitted by xuchenchen (KylinOS) on 2026-05-26 in the prior week's window. The bug: when Local-Realms in /etc/idmapd.conf contains only empty fields (e.g., ", ,"), conf_get_list() returns an empty list, the logging path computes a zero-length buffer size, and the code writes a NUL terminator into the result of malloc(0) — undefined behavior per the C standard.

The fix was surgical: reserve space for the terminating NUL byte so the computed size is never zero, and switch from malloc() to calloc() to guarantee a valid, zero-initialized allocation even in the degenerate case. The diff touched only five lines in support/nfsidmap/libnfsidmap.c (two insertions, three deletions).

Significance for NFS Client Development

While libnfsidmap is user-space rather than kernel code, it sits on the critical path for NFSv4 ID-mapping — the mechanism that translates local UIDs/GIDs to global identities across NFSv4 mounts. A crash in this library during configuration parsing could take down the idmapper service entirely, breaking all NFSv4 file access on the affected host. The fix eliminates a class of crashes triggered by misconfigured realm files (stray commas) without altering broader parsing logic, making it low-risk for backporting to stable branches.

The patch is now part of the nfs-utils-2.9.2-rc4 release cycle and will ship in the next stable nfs-utils point release.

Conclusion

This was a straightforward, well-scoped bug fix with no controversy or design debate. The discussion lifecycle — submission → commit confirmation — completed in under a week, and the thread is now closed.
