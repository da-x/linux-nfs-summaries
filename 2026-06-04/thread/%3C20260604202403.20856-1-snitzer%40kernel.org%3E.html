Snitzer patches flexfiles client to honor FF_FLAGS_NO_IO_THRU_MDS on fatal DS errors and write fallback

Summary

NFSv4/flexfiles: fix unwanted in-band IO fallback from DS to MDS

This week's activity in this thread is a single, tightly-scoped bug-fix submission from Mike Snitzer (Red Hat), posted on 2026-06-04. The series targets the NFSv4 flexfiles client and addresses two distinct code paths where the FF_FLAGS_NO_IO_THRU_MDS layout flag — which explicitly forbids I/O through the Metadata Server — is silently ignored, causing unwanted in-band (MDS) I/O.

What kind of change this is

This is a bug fix for the NFSv4 flexfiles client, not a new feature or protocol change. It corrects two regressions/oversights where the kernel's pNFS fallback logic routes I/O to the MDS even when the layout segment carries FF_FLAGS_NO_IO_THRU_MDS (typically set on single-mirror appliance layouts).

Context and motivation

In the cover letter, Snitzer frames the problem clearly:

"If FF_FLAGS_NO_IO_THRU_MDS flag is set then NFSv4 flexfiles should never fallback to trying to issue IO directly to the MDS."

He notes that a Hammerspace test exposed the bug by widening the window between LAYOUTRETURN and the next LAYOUTGET, during which unwanted in-band I/O could be issued:

"A Hammerspace test that caused the time between layout return and get to be much longer widened exposure for unwanted in-band IO to be issued by flexfiles. The test allowed for these fixes to be developed and the test now passes."

Patch 1/2 — fatal DS connect errors

PATCH 1/2 targets a regression introduced by commit f06bedfa62d5 ("pNFS/flexfiles: don't attempt pnfs on fatal DS errors"). That earlier commit taught ff_layout_{read,write}_pagelist() to return PNFS_NOT_ATTEMPTED when nfs4_ff_layout_prepare_ds() fails with a fatal errno (e.g., -ETIMEDOUT from a SOFTCONN connect deadline). The intent was to avoid spinning on unreachable data servers.

However, as Snitzer explains, the fallback path that follows is unconditional:

"That fallback is unconditional and silently violates FF_FLAGS_NO_IO_THRU_MDS: when the layout segment carries the flag (typically single-mirror appliance layouts where MDS I/O is explicitly forbidden), the out_failed: path's && !ds_fatal_error clause overrides the flag's short-circuit through ff_layout_avoid_mds_available_ds() and routes the I/O to the MDS file handle anyway."

The practical trigger is a data-server restart: SOFTCONN exhaustion produces -ETIMEDOUT, which is fatal per nfs_error_is_fatal(), which triggers PNFS_NOT_ATTEMPTED, which "silently goes to MDS."

The fix preserves the upstream intent of not spinning on fatal errors for layouts that permit MDS fallback, but for layouts with FF_FLAGS_NO_IO_THRU_MDS set, it marks the layout for return and requests PNFS_TRY_AGAIN instead:

"For layouts with FF_FLAGS_NO_IO_THRU_MDS set, mark the layout for return and request PNFS_TRY_AGAIN instead; if the server cannot supply a usable layout the failure now surfaces cleanly via pnfs_update_layout(), rather than via silent MDS I/O that contradicts the flag."

Patch 2/2 — pg_get_mirror_count_write

PATCH 2/2 addresses a second, related gap. The FF_FLAGS_NO_IO_THRU_MDS flag lives on each layout segment (lseg), so when there is no current lseg — for example between LAYOUTRETURN and the next LAYOUTGET — the per-lseg check cannot run.

Snitzer introduces a sticky header-level flag (NFS4_FF_HDR_NO_IO_THRU_MDS bit in struct nfs4_flexfile_layout::flags) that is set whenever ff_layout_alloc_lseg() parses an lseg with the no-fallback flag:

"The bit is never cleared for the lifetime of the layout hdr; the server is assumed to be consistent in its no-fallback policy per file."

This new header-level bit gates ff_layout_pg_get_mirror_count_write(). Previously, when pnfs_update_layout() returned NULL (due to NFS_LAYOUT_BULK_RECALL, a failed layout I/O test, or blocked layoutgets), the code unconditionally called nfs_pageio_reset_write_mds() — "a source of unwanted WRITE to MDS." The fix checks the new bit and, if set, surfaces -EAGAIN instead:

"Fix it by checking NFS4_FF_HDR_NO_IO_THRU_MDS bit, and if set surface -EAGAIN instead; the writepage-side caller (nfs_do_writepage() for buffered, nfs_direct_write_reschedule() for O_DIRECT) then redirties the request so writeback retries via pNFS."

Discussion status

As of the end of this reporting window (2026-06-04), no replies or review comments have appeared in-thread. The series is 45 lines of insertions across two files (fs/nfs/flexfilelayout/flexfilelayout.c and .h) and carries Fixes: tags pointing to the two upstream commits that introduced the gaps. Snitzer closes with "All review appreciated."

Significance for NFS client development

This is a meaningful correctness fix for flexfiles-based appliance deployments (e.g., Hammerspace) where MDS I/O is architecturally forbidden. The bug could have caused data to be written to or read from the wrong server during transient DS unavailability, potentially violating consistency guarantees that the storage vendor relies on. The introduction of a sticky header-level flag is a small but notable architectural addition to the flexfiles layout code, acknowledging that fallback decisions can occur in lseg-less windows and need a persistent policy signal.
