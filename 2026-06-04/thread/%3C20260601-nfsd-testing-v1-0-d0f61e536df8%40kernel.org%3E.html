nfsd locally-triggerable bugfixes: eight patches address UAFs, refcount leaks, and an unprivileged IPv6 info leak

Summary

nfsd locally-triggerable bugfixes: eight patches address UAFs, refcount leaks, and an unprivileged IPv6 info leak

Context from prior weeks

This thread is part of a concentrated burst of NFS server-side hardening work in late May/early June 2026. Just days earlier, Jeff Layton posted and merged the v2 "grab bag" series of nine remotely-triggerable fixes (panics, UAFs, data corruption, DoS vectors), and the following day posted a six-patch "medium-severity" series covering remote-triggerable memory leaks and refcounting bugs. The series summarized here — posted June 1 — is the third wave, targeting a different threat class: locally-triggerable defects that require either admin access or (in one case) merely unprivileged user-level access within the network namespace.

Series overview (June 1)

Jeff Layton posted the eight-patch series on June 1, describing the threat model:

"These are bugs that Claude classified as locally-triggerable. A couple can be triggered by an unprivileged user, but the rest require admin access."

He also noted a design decision for the last three patches:

"The last 3 patches fix one bug. I originally had a more targeted fix that kres generated, but I think it's better to simplify the filecache disposal mechanism to get rid of the bug rather than add more complexity."

The series is co-authored by Chris Mason (3 patches) and Jeff Layton (5 patches), touching 8 files with 80 insertions and 94 deletions. Base commit is d7203affbe85baad683cef946f661c5541966d97.

Patch-by-patch highlights

PATCH 1/8: Defer vfree of compound ops to fix rpc_status UAF — A use-after-free on vmalloc memory in the rpc_status netlink dumpit. The dumpit walks in-flight svc_rqst entries under rcu_read_lock and reads opnums from args->ops[], but that buffer was being freed synchronously via vfree() at compound completion. As Layton explains:

"A concurrent compound completion can therefore free the buffer while the dumpit is reading it — a use-after-free on vmalloc memory."

The fix replaces vfree(args->ops) with kvfree_rcu_mightsleep(), deferring reclamation across one RCU grace period. The tradeoff is modest: "completed compound ops buffers (up to 200 * sizeof(struct nfsd4_op)) persist in memory slightly longer, across one grace period, before being reclaimed."

PATCH 2/8: Hold rcu across localio cmpxchg retry — Chris Mason's fix for a UAF in nfsd_open_local_fh(). The again: retry block loads a pointer with cmpxchg and calls refcount_inc_not_zero() without holding rcu_read_lock, while the slab backing freed nfsd_file objects is not SLAB_TYPESAFE_BY_RCU. The commit message includes a detailed two-CPU race diagram showing how a recycled slab page can contain a non-zero word at the nf_ref offset, making the refcount bump "appear to succeed" before the caller dereferences freed memory. The fix takes rcu_read_lock() immediately before the cmpxchg.

PATCH 3/8: Fix ref leak on nfs_uuid_add_file failure — Another Chris Mason fix. When nfs_uuid_add_file() races with nfs_uuid_put() tearing down the net, it returns -ENXIO without publishing the RCU pointer, and the error path in nfs_open_local_fh() leaks both a caller-owned nfsd_file reference and an entry-time nfsd_net reference. The leak "pins one nfsd_file (and the underlying struct file, dentry, inode) and one nfsd_net_ref per occurrence, which blocks nfsd_net and netns teardown."

PATCH 4/8: Guard nfsd_serv deref in nfsd_file_net_dispose — Chris Mason's fix for a NULL pointer dereference during per-net teardown. The service thread loop calls nfsd_file_net_dispose() which unconditionally calls svc_wake_up(nn->nfsd_serv), but nn->nfsd_serv is cleared before the filecache laundrette shuts down. As Mason notes, "The sibling helper nfsd_file_dispose_list_delayed() already documents this ordering and caches nn->nfsd_serv into a local before testing it for NULL. nfsd_file_net_dispose() was introduced with the same raw svc_wake_up(nn->nfsd_serv) call and never picked up the guard."

PATCH 5/8: Widen nfsd_genl_rqstp address fields to sockaddr_storage — The most security-sensitive patch in the series. struct nfsd_genl_rqstp declared rq_daddr and rq_saddr as plain struct sockaddr (16 bytes), but for IPv6 clients the code casts them to struct sockaddr_in6 * (28 bytes) and reads past the end into adjacent memory. As Layton describes:

"The 16-byte nla_put_in6_addr then ships 8 bytes of truncated IPv6 address followed by 8 bytes of rq_flags to userspace via the NFSD_A_RPC_STATUS_SADDR6/DADDR6 netlink attributes."

This is particularly notable because it's reachable by any unprivileged process: "This is reachable by any unprivileged process in the network namespace because NFSD_CMD_RPC_STATUS_GET uses GENL_CMD_CAP_DUMP without GENL_ADMIN_PERM." The fix widens the fields to struct sockaddr_storage and zero-initializes the stack variable.

PATCH 6/8: Fix refcount leak in nfsd_file_lru_add on insertion failure — A latent bug where nfsd_file_lru_add() unconditionally increments nf_ref before attempting LRU insertion, and never releases it on failure. While "currently unreachable" because the sole caller operates on freshly-allocated objects, it "represents a latent bug that would become exploitable if a future change adds another call site or alters the PENDING protocol." The fix adds a compensating refcount_dec() and changes WARN_ON(1) to WARN_ON_ONCE(1).

PATCH 7/8: Fix fcache_disposal UAF by inlining dispose state into nfsd_net — The first of three patches that together fix a single UAF. The per-net struct nfsd_fcache_disposal (containing the spinlock and freeme list) was separately allocated and freed during net teardown, but "The global shrinker, laundrette, and fsnotify callbacks can still be inside nfsd_file_dispose_list_delayed() dereferencing that pointer, causing a use-after-free." The fix inlines the spinlock and list directly into struct nfsd_net, giving them the same lifetime as the net namespace itself. This eliminates 69 lines of alloc/free boilerplate.

PATCH 8/8: Hold net namespace reference in nfsd_file — The third patch in the UAF trilogy. Without a net reference held by nfsd_file, "nf_net can dangle for in-flight files whose net namespace is torn down concurrently, causing a use-after-free when nfsd_file_dispose_list_delayed() calls net_generic(nf->nf_net, ...)." The fix takes get_net() in nfsd_file_alloc() and releases it in nfsd_file_free(), with a consequential change to nfsd_file_put_local() which now returns void since the net reference is managed internally.

Review discussion: Al Viro's scalability concern (June 1)

The only review comment on this series came from Al Viro, who raised a performance concern about PATCH 8/8:

"That means that each nfsd_file_alloc()/nfsd_file_free() is now touching the same cacheline on kernels with netns enabled. Scalability implications might be interesting..."

This is a pointed observation: get_net()/put_net() increment/decrement an atomic counter in the struct net object, which becomes a shared cacheline hotspot when many NFS server threads are concurrently allocating and freeing file cache entries — particularly on multi-socket systems with network namespaces enabled.

Jeff Layton acknowledged the concern immediately:

"That's a very good point. There are some alternatives. Let me play around with them and see if I can find something better."

About 15 minutes later, he followed up with his findings:

"That's definitely a valid concern. I looked at a couple of alternatives but they turned out to be pretty nasty. One thing we can do is only take a net reference for GC'ed files, since we don't need a reference for the others. That would cut down some of the get/put_net activity, but it's still likely to be substantial. I'll plan to implement that for v2. I'll keep thinking about other ways to do this, but I think we're stuck taking net references for at least some of these for now."

This indicates a v2 of the series is expected, with PATCH 8/8 reworked to limit the scope of get_net()/put_net() calls to only those files that have been isolated by the garbage collector or shrinker — the subset where nf_net can actually dangle.

Nature of the discussion

This is a bug fix series — not a new feature or protocol change. All eight patches address locally-triggerable defects: two use-after-free vulnerabilities (rpc_status netlink dumpit, localio cmpxchg retry), one NULL pointer dereference on net teardown, three patches jointly fixing a filecache disposal UAF, two refcount leaks (localio error path, LRU insertion failure), and one unprivileged information disclosure (truncated IPv6 address + adjacent memory leaked via netlink).

The series is notable for its use of AI-assisted code analysis: multiple patches carry Assisted-by: tags referencing Claude models (claude-opus-4-6, kres:claude-opus-4-7), and the cover letter explicitly credits "Claude" for classifying the bugs as locally-triggerable. This represents a new pattern in kernel development where AI tools are used for systematic vulnerability classification and initial fix generation, with human developers (Layton, Mason) providing architectural judgment — as evidenced by Layton's decision to replace a "more targeted fix that kres generated" with a broader simplification of the filecache disposal mechanism.

Significance for NFS client development

While all fixes are server-side, several have direct implications for NFS clients and testing:

  • The rpc_status UAF (PATCH 1) is relevant to any deployment using the nfsd netlink interface for monitoring in-flight requests — a common practice in production NFS servers. Clients generating high compound request rates increase the race window.
  • The localio cmpxchg UAF (PATCH 2) affects NFS re-export configurations where the local I/O path is used. A client hammering file opens on an exported filesystem could trigger the race, potentially corrupting server memory.
  • The unprivileged IPv6 info leak (PATCH 5) is the most immediately actionable for security teams: any unprivileged user in a network namespace with an active NFSv4-over-IPv6 connection can read 8 bytes of kernel stack/adjacent struct memory via netlink. Clients connecting over IPv6 to affected servers are the trigger, though the vulnerability is entirely server-side.
  • The filecache disposal UAF (PATCHES 7–8) is relevant to any deployment using network namespaces with NFS exports: tearing down a namespace while files are still in-flight through the GC/shrinker path could corrupt kernel memory, potentially affecting all clients on that server.
  • The refcount leaks (PATCHES 3, 6) are slow-burn DoS vectors: each occurrence pins a file/inode/dentry or inflates a refcount permanently, eventually blocking namespace teardown or preventing LRU eviction.

Final conclusions and open items

As of the end of this week's window:

  1. The series has been posted but not yet merged. No merge confirmation from Chuck Lever appears in this thread within the window.
  2. PATCH 8/8 will receive a v2 incorporating Al Viro's scalability feedback — limiting get_net()/put_net() to GC'ed files only, per Layton's stated plan.
  3. The broader filecache disposal simplification (inlining the dispose state into nfsd_net) is a net reduction in complexity (-69 lines) that eliminates an entire class of lifetime bugs.
  4. The series continues the pattern established over the prior week: systematic, AI-assisted vulnerability classification followed by targeted fixes, with human reviewers providing architectural direction and performance guidance.
