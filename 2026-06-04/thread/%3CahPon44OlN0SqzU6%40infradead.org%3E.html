Howells defends keeping iov_iter_get_pages*(): a socket-buffering overhaul is the real blocker

Summary

This week's single message in this thread closes out (for now) the exchange that opened last week, when block maintainer Christoph Hellwig objected to David Howells' plan to consolidate the kernel-side page-extraction helpers. The upshot: Howells has declined Hellwig's call to delete iov_iter_get_pages*() outright, arguing that doing so would require reworking the network socket buffering stack — a project too large to fold into this netfslib refactor.

What the patch does (brief bridge)

The discussion is about patch 06/21 of Howells' 21-patch netfs "bvecq" series, which migrates netfslib — the shared I/O layer under NFS, AFS and CIFS — from its private folio_queue/rolling_buffer buffering onto segmented bio_vec[] chains. The patch in question is a net ~145-line deletion that makes iov_iter_get_pages*() simply wrap iov_iter_extract_pages() for the kernel iterator types:

"Make iov_iter_get_pages*() wrap iov_iter_extract_pages() for kernel iterator types (e.g. ITER_BVEC, ITER_FOLIOQ, ITER_XARRAY). The pages obtained have their refcounts incremented afterwards if they're not slab pages. ITER_KVEC is left returning -EFAULT."

Last week, Hellwig pushed back hard:

"Just kill off iov_iter_get_pages*, please. Or at least stop using it where these types matter."

This week's reply

On 2026-06-04, Howells responded, quoting Hellwig's demand and then drawing a firm line:

"Much as I would like to, this isn't the place to do it. It will require an overhaul of the network socket buffering."

That is the entire in-window contribution — a short but decisive deflection. Howells is effectively conceding that iov_iter_get_pages*() is redundant API surface (his own patch already reduces it to a thin wrapper) while arguing that the callers of that API live in the TCP/socket send path, and retiring the function would force a coordinated rewrite of how kernel sockets buffer outgoing data. That rewrite is out of scope for a VFS-tree netfslib series.

Technical significance for NFS

  • Type: Protocol-agnostic infrastructure refactor / API consolidation — not a bug fix and not an on-the-wire protocol change. The NFS client is affected indirectly through netfslib's buffering and kernel_sendmsg() send path.
  • Why it matters to the client: The broader series aims to (1) unify buffered and DIO buffering in netfslib, (2) let a full RPC message be sent in a single kernel_sendmsg() call (avoiding corking), and (3) drop the now-redundant ITER_FOLIOQ iterator type. Patch 06/21 is one of the foundational VFS-side pieces that makes those goals possible, so its fate affects how cleanly the rest of the series lands.
  • Where things stand: The wrap-based consolidation in patch 06/21 appears to be the landing position for this cycle; Hellwig's deletion request is parked pending a separate socket-buffering project. The kmap-helper question from last week (patch 05/21) remains open as well.

Evolution of the discussion

  1. 2026-05-18 — Howells posts v2 of the bvecq series, including patch 06/21 consolidating iov_iter_get_pages*() onto iov_iter_extract_pages().
  2. 2026-05-25 — Hellwig reviews and demands outright deletion of the get_pages family rather than a wrapper.
  3. 2026-06-04 (this week) — Howells declines, citing the network socket buffering overhaul as a prerequisite. No further back-and-forth in this thread within the window; the ball is now with Hellwig to either accept the wrapper or open a separate socket-buffering effort.
