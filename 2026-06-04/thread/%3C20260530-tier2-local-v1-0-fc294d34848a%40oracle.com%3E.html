SUNRPC server-side init race fixes: gssp_lock and percpu counter allocation

Overview

On May 30, Chuck Lever posted a small two-patch series titled Fix two latent server-side initialization bugs targeting the SUNRPC server subsystem. Both patches address the same structural bug shape — an object becoming reachable by a consumer while a field it depends on is still invalid — but in different code paths. The series attracted quick review from Jeff Layton, who issued Reviewed-by tags on both patches within roughly 90 minutes of posting, with one design-level objection to Patch 2 that was resolved by mutual agreement before the end of the day.

This thread sits alongside the nfsd fixes grab bag v2 posted the same day, making May 30 a particularly productive day for NFS server-side bug fixing.

Nature of the discussion

This is a bug fix series — specifically, two latent initialization-ordering bugs in the SUNRPC server that are only exposed under narrow trigger conditions (preemption-timed writes or percpu allocation failure). Neither patch introduces new functionality or changes any protocol behavior.

Patch 1: sunrpc: init gssp_lock before publishing proc entry

Chris Mason's patch (signed off by Chuck Lever) fixes a race in create_use_gss_proxy_proc_entry(). The function calls proc_create_data() to publish /proc/net/rpc/use-gss-proxy before calling init_gssp_clnt() which runs mutex_init() on sn->gssp_lock. Once the dentry is linked, it is immediately reachable from userspace.

The commit message lays out the race precisely:

"A writer that wins the race locks a zero-filled struct mutex. On CONFIG_DEBUG_MUTEXES the missing magic value trips a 'lock used without init' splat; on a production kernel the fast path acquires the lock via CMPXCHG(owner, 0, current). In the latter case a second writer that arrives before init_gssp_clnt() re-zeroes owner can enter set_gssp_clnt() concurrently, shut down the first writer's clnt while it is still in use, and leak the loser's clnt."

The fix moves mutex_init(&sn->gssp_lock) into sunrpc_init_net() so its lifetime matches the sunrpc_net structure. The safety argument rests on module load order: sunrpc.ko is a build-time dependency of auth_rpcgss.ko, guaranteeing that sunrpc_init_net() has already run on every net namespace before any auth_gss pernet init can publish the proc entry. This also eliminates the now-unnecessary lazy init_gssp_clnt() helper and its prototype.

Patch 2: SUNRPC: Check svc pool percpu counter allocation

Chuck Lever's own patch addresses a more insidious bug in __svc_create(). The function initializes three per-pool percpu_counter stats and ignores every return value. On allocation failure, the counter is left with fbc->counters == NULL and its embedded spinlock, list_head, and count never initialized.

The consequences are severe but hard to trigger:

"Once that service is live, the hot-path increments in svc_xprt_enqueue(), svc_handle_xprt(), and svc_pool_wake_idle_thread() reach a counter whose backing pointer is NULL. The pointer is a per-cpu offset, so the access does not fault: it resolves to offset zero of the current CPU's per-cpu area and silently corrupts whatever variable lives there."

The trigger requires a percpu allocation failure during RPC server startup — reachable only by a local administrator under memory pressure or fault injection. A remote peer cannot induce the bad state.

Review discussion on Patch 2

Jeff Layton reviewed the patch and initially approved it, but raised a structural concern about the use of percpu_counter_init_many():

"Switching to this looks like a good thing, but it means that the svc_pool struct fields now have some strict ordering requirements. The percpu_counters all need to be snuggled up together. That deserves a comment to that effect in the struct svc_pool, so that we don't inadvertently break it later."

He still issued his Reviewed-by: "Patch itself looks fine though."

Chuck Lever responded briefly:

"A comment or a static_assert"

Then Layton revised his position, citing an external observation:

"Actually, sashiko points out that struct randomization could break here too. Given that service creation isn't a hot codepath, I'd keep these as discrete percpu_counter_init/destroy() calls and avoid the hassle."

Chuck Lever agreed immediately:

"Yeah. It's too clever by half."

The final resolution: the patch will be revised to use three discrete percpu_counter_init() / percpu_counter_destroy() calls instead of the _many variants, eliminating both the struct-layout fragility and the risk from CONFIG_RANDSTRUCT field randomization. The Reviewed-by stands for the logic (checking return values and unwinding on failure), but the implementation detail changes.

Key technical arguments

  1. Init-before-publish invariant: Both patches enforce that no consumer can observe an object mid-initialization. Patch 1 relies on module dependency ordering (sunrpc.ko before auth_rpcgss.ko); Patch 2 relies on local error handling within __svc_create().

  2. Silent corruption vs. crash: The percpu counter bug is particularly dangerous because it does not produce a page fault — the NULL per-cpu pointer resolves to offset zero of the current CPU's per-cpu area, silently corrupting an unrelated variable. This makes it far harder to diagnose in the field than a straightforward oops.

  3. Simplicity over micro-optimization: The final design decision on Patch 2 reflects a common kernel review principle — service creation is not a hot path, so three separate percpu_counter_init() calls are preferable to one _many call that imposes fragile struct layout constraints vulnerable to future refactoring or compiler-level randomization.

Significance for NFS client development

While both fixes target the server side, they have indirect relevance to client developers:

  • The gssp_lock race affects any NFS client (or server) using RPCSEC_GSS authentication via gssproxy. A corrupted lock state could manifest as intermittent authentication failures or leaked RPC clients visible on the client side during re-authentication storms.
  • The percpu counter corruption could cause pool_stats to report garbage values, potentially confusing monitoring tools that track NFS server load from the client's perspective (e.g., via /proc/fs/nfsd/pool_stats on a local export). More critically, silent per-cpu memory corruption in the server's hot path could lead to unpredictable RPC handling delays or dropped requests that clients would see as timeouts.

Final state

As of the end of the week window (June 4), the thread shows both patches reviewed with one pending revision (discrete percpu init/destroy calls for Patch 2). No merge confirmation has appeared in this thread yet, but given the quick turnaround and clean review, a v2 posting or direct application to nfsd-testing is expected imminently.
