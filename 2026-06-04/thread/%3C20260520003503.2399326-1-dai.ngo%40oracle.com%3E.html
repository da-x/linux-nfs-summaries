XFS pNFS layout-mapping fixes merged into for-next

Summary

XFS pNFS layout-mapping fixes: Dai Ngo's two-patch series lands in for-next

This week in brief

The thread that began with Dai Ngo posting a two-patch bug-fix series on 2026-05-20 reached its natural conclusion this week. On Saturday 2026-05-30, NFS/XFS maintainer Carlos Maiolino confirmed that both patches have been applied to the for-next tree, closing out a ten-day review-and-merge cycle with no objections or revisions.

"Applied to for-next, thanks!" — Carlos Maiolino

Maiolino's message also records the final commit hashes for both patches:

  • [1/2] xfs: fix use of uninitialized imap in xfs_fs_map_blocks error path — commit 97bdbf2613eb89428b739ce09d1a6e1c8435a286
  • [2/2] xfs: fix overlapping extents returned for pNFS LAYOUTGET — commit 36ca6f11424a5b6d92b88df37c40bf2fe825d5a0

Classification

This is a bug-fix thread, not a new feature or protocol change. Both patches correct server-side behavior in the XFS pNFS export path (fs/xfs/xfs_pnfs.c) that was producing malformed LAYOUTGET replies to NFSv4.2 block-layout clients. The fixes were exposed by running xfstests generic/075 against a block layout export.

Bridge from prior weeks

The discussion spanned three weeks:

  • Week of 2026-05-21: Dai Ngo posted the original PATCH 0/2 series. Christoph Hellwig reviewed and approved both patches the same day, writing:

    "Looks good: Reviewed-by: Christoph Hellwig hch@lst.de"

    The prior summary also noted that a separate nfsd race condition (layouts inserted after ->proc_layoutget) was identified during the discussion but deliberately left out of scope.

  • Week of 2026-05-28: Carlos Maiolino added his own Reviewed-by tags to both patches on 2026-05-26, adding a second independent reviewer sign-off. For Patch 2 he offered the candid caveat:

    "I'm not an expert on NFS, but the explanation and the patch looks good and make sense"

    No new technical arguments were raised; the review window closed cleanly.

Key technical arguments (recap)

The two bugs fixed are both server-side in origin but have direct client-side consequences:

  1. Uninitialized imap in error path (Patch 1): As Dai Ngo explained at posting time, xfs_fs_map_blocks() "acquires the data map lock and then calls xfs_bmapi_read(). If xfs_bmapi_read() fails, the function currently still falls through to xfs_bmbt_to_iomap(), which consumes an uninitialized imap record and may return invalid data to the caller." The fix releases the data map lock and returns immediately on error. This was a regression from commit 527851124d10f ("xfs: implement pNFS export operations").

  2. Overlapping extents in LAYOUTGET (Patch 2): The second patch removes the XFS_BMAPI_ENTIRE flag so that "each request only returns the range the client asked for, eliminating overlapping [extents] in LAYOUTGET replies." Without this fix, a single client LAYOUTGET could trigger multiple server-side xfs_fs_map_blocks() calls for different offsets within the same extent, each returning the full extent. As Dai Ngo warned:

    "This creates ambiguity in extent selection for a given file range, which can lead to incorrect device selection, inconsistent handling of datastate, and ultimately data corruption or protocol violations on the client side."

    This was a regression from commit cc6c40e09d7b1 ("NFSD/blocklayout: Support multiple extents per LAYOUTGET").

Why this matters for NFS clients

Although both fixes live in XFS server code, their blast radius is squarely on the client side. For pNFS block-layout clients — the Linux NFSv4.2 client in particular — these two fixes eliminate server-side sources of malformed layout data that would otherwise surface as:

  • Bogus device/offset pairs in LAYOUTGET replies (from Patch 1), which could cause a client to issue I/O to the wrong block device or at the wrong offset.
  • Overlapping extent mappings (from Patch 2), which create ambiguity in extent selection and can lead to data corruption or protocol violations that are extremely difficult to debug from the client side, since they look like client misbehavior when the root cause is bad server data.

Evolution and final state

The discussion followed a clean, linear path:

  1. Posting + same-day review (May 20) — Dai Ngo posted; Hellwig approved both patches immediately.
  2. Second reviewer sign-off (May 26) — Maiolino added Reviewed-by tags to both patches.
  3. Merge confirmation (May 30, this week) — Maiolino confirmed application to for-next with final commit hashes.

No revisions, no pushback, no additional technical debate were needed after the initial posting. The series is now merged and will be carried in the next kernel development cycle.

The open nfsd race condition (layouts inserted after ->proc_layoutget, creating a window for races against unwritten extent conversions or concurrent writers) remains unaddressed by this series and should be tracked as a separate follow-up item.
