nfsd cleanup: Andy Shevchenko suggests simpler hex format for clidname patch

Summary

nfsd: Replace open-coded conversion of bytes to hex — late formatting nitpick

Type: Code cleanup / refactoring (no functional change) in the NFS server (nfsd), specifically in fs/nfsd/nfs4recover.c.

Brief bridge from prior weeks

This thread originated back in August 2025 when Eric Biggers posted a two-patch series titled "nfsd: Clean up nfs4_make_rec_clidname()" cover letter. The patches:

  1. Replaced the hand-written md5_to_hex() helper with the kernel's built-in "%*phN" sprintf format specifier, and added an explicit array bound to the dname parameter of nfs4_make_rec_clidname().
  2. Eliminated a dynamic allocation by storing the fixed-size MD5 digest in a stack buffer instead.

Both patches received a Reviewed-by: Jeff Layton <jlayton@kernel.org> tag, and Chuck Lever promptly applied them to nfsd-testing on 2025-08-05:

"Applied v2 to nfsd-testing, thanks!" — Chuck Lever

The series has been merged and sat quietly in the tree for nearly ten months.

This week's activity (2026-05-29 → 2026-06-05)

A single message landed on 2026-06-03 from Intel's Andy Shevchenko, who revisited the already-merged patch and offered a minor stylistic improvement:

"FWIW, since the length is static no need to use stack for that: sprintf(dname, "%16phN", cksum.data); will be better." — Andy Shevchenko

The point is straightforward: Eric's original patch used the variable-width form "%*phN" with an explicit 16 argument, which causes the format specifier to pop a width from the stack at runtime. Since the MD5 digest is always exactly 16 bytes, the literal form "%16phN" bakes the width directly into the format string, avoiding one extra stack operand and making the intent slightly clearer.

This is a cosmetic / micro-optimization suggestion, not a bug fix or protocol change. The patch has already been merged (commit 9093f8308442fc5096e973a46107f8623e2b336b), so any follow-up would require a new cleanup commit. As of the end of this reporting window, no reply from Eric Biggers or Chuck Lever has appeared in the thread.

Significance for NFS client development

This thread touches the server-side recovery-state code (nfs4recover.c) that generates the clientid name used in NFSv4 state-recovery files. While it does not alter any wire protocol behavior, the cleanup reduces code complexity in a security-sensitive area (MD5-based client identifier generation) and removes an unnecessary heap allocation from the recovery path — both of which are positive for long-term maintainability of the NFS subsystem.
