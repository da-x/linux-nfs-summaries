sunrpc: fix uninitialized xprt_create_args structure (v2)

Summary

sunrpc: Fix Uninitialized xprt_create_args in sysfs Transport Switch Path

Overview

A single-message thread landed this week on linux-nfs, carrying a bug-fix patch to the SUNRPC client's sysfs transport-switch code. The patch is version 2 of a fix from Hongling Zeng (KylinOS) that addresses an uninitialized stack structure in rpc_sysfs_xprt_switch_add_xprt_store(), with review and suggestion credits to NFS maintainer Jeff Layton.

The thread contains only the v2 submission itself — posted by Hongling Zeng on 2026-06-03 — with no further replies in the mailing-list archive within the current window. The v1 discussion and Layton's review apparently happened outside the indexed history (no earlier messages from this thread appear in the corpus), so the v2 changelog is the primary record of how the patch evolved.

The Bug

The fix targets a classic C footgun in the NFS client's sysfs interface: a stack-allocated xprt_create_args structure that was never zeroed before being passed to the transport-setup path. As Zeng explains in the cover letter:

"The xprt_create_args structure is allocated on the stack without initialization in rpc_sysfs_xprt_switch_add_xprt_store(). While some fields are manually populated, critical fields like srcaddr, bc_xps, and flags contain uninitialized stack garbage."

Zeng enumerates three concrete failure modes this can cause:

  1. Kernel panic when xs_setup_xprt() dereferences garbage srcaddr
  2. Information leak if srcaddr points to sensitive stack data
  3. Unpredictable behavior if flags has random bits set

This is squarely an NFS client bug fix — the affected code path (net/sunrpc/sysfs.c) is exercised when userspace writes a new transport into an existing xprt-switch via sysfs, which is the mechanism NFS clients use to hot-add transports (e.g., for multipath or RDMA/TCP failover setups). A garbage srcaddr pointer being dereferenced by xs_setup_xprt() is a real kernel-panic risk on any system that uses this interface.

The Fix and Its Evolution

The fix itself is minimal — a one-line change in net/sunrpc/sysfs.c (1 insertion, 1 deletion) to zero-initialize the structure so that all unused fields are NULL/0:

"The fix is to zero-initialize the structure to ensure all unused fields are NULL/0, preventing the transport setup code from acting on garbage data."

What makes this v2 interesting is the evolution noted in the changelog. Layton — who both suggested and reviewed the fix — pushed back on the initial approach:

"Changes in V2:

  • Use designated initializer instead of memset, as suggested by Jeff Layton
  • Add Reviewed-by tag"

So the v1 patch evidently used memset() to zero the structure, and Layton's review steered it toward a C99 designated initializer — a more idiomatic kernel style that lets the compiler verify field names at compile time rather than relying on a runtime memory wipe. The patch now carries both Suggested-by: Jeff Layton and Reviewed-by: Jeff Layton, signaling maintainer-level buy-in before submission.

Significance for NFS Client Development

While small in diff size, this fix touches a security- and stability-relevant path in the NFS client:

  • Stability: Eliminates a potential kernel panic in the transport hot-add path.
  • Security: Closes an information-leak vector where uninitialized stack data could be exposed through a garbage srcaddr pointer.
  • Maintainability: The designated-initializer approach (per Layton's suggestion) makes the code more robust against future struct field additions — new fields will be zeroed by default rather than silently inheriting stack garbage.

The patch is marked Cc: stable@vger.kernel.org, indicating Zeng considers this suitable for backport to stable kernel trees — a reasonable call given that the bug class (uninitialized stack data in a user-triggerable sysfs path) can affect any running system, not just new deployments.

Status

As of the end of this reporting week, the v2 patch has been submitted with full review from the NFS maintainer but no visible merge confirmation or additional discussion in the thread. Given the Reviewed-by tag and the trivial nature of the change, it is a strong candidate for inclusion in the next merge window or stable update.
