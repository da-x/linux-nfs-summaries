nfsd OPEN ACL leak fix v2: replay path patched, NeilBrown suggests single call-site cleanup for v3

Summary

nfsd OPEN ACL leak fix v2: replay path patched, NeilBrown suggests single call-site cleanup for v3

Context from prior weeks

This thread is the direct continuation of PATCH 5/6 from Jeff Layton's six-patch "medium-severity bugfixes" series posted on May 31. In that series, Chris Mason's fix addressed a posix_acl refcount leak on the NFSv4 OPEN short-circuit path: when nfsd4_decode_open_claim4() returns a non-seqid-mutating error, the compound dispatcher skips op_func entirely, but the decoded ACLs in open->op_pacl and open->op_dpacl still needed releasing. The v1 fix added nfsd4_open_release() as .op_release for OP_OPEN.

However, Chuck Lever caught a gap before merging:

"The double-free fix is right, but op_release is not called unconditionally after every op, and that gap leaks the ACLs on the v4.0 replay path."

He explained that op_release runs only inside nfsd4_encode_operation(), and the compound loop skips that encoder for replayed operations: "So every ACL-bearing v4.0 OPEN retransmit leaks two posix_acl refs." Lever applied the other five patches to nfsd-testing and asked Layton to resend just this one.

This week's activity (May 31 – June 1)

v2 posted (May 31)

Jeff Layton posted the v2 patch on May 31, incorporating Chuck Lever's fix. The v2 changelog is concise:

"Changes in v2:

  • Ensure that op_release is called in the v4.0 replay case as well"

The patch (authored by Chris Mason, reviewed by Chuck Lever) makes two changes to fs/nfsd/nfs4proc.c:

  1. Adds op_release call to the replay branch. The compound loop has two encoding branches — nfsd4_encode_operation() for normal ops and nfsd4_encode_replay() for v4.0 replayed ops. Previously, op_release was only called from the former. The v2 patch adds the release call to the replay path as well, ensuring cleanup on every code path.

  2. Wires nfsd4_open_release() as .op_release for OP_OPEN and removes the now-redundant posix_acl_release() pair from nfsd4_open()'s out_err: label to avoid double-release. As Layton notes in the commit message, "posix_acl_release() is NULL-safe, so the single release site covers both the normal path and the nfsd4_open_omfg short-circuit."

The patch carries a Fixes: tag pointing to commit 5fc51dfc2eb1 ("NFSD: Add support for XDR decoding POSIX draft ACLs"), confirming this is a regression fix for a bug introduced when POSIX draft ACL support was added.

NeilBrown's review and cleanup suggestion (June 1)

NeilBrown reviewed the patch early on June 1 and approved it, but offered a structural improvement:

"I think this patch is good, but I think it would be even better if the ->op_release() call were moved out of nfsd4_encode_operation() and places after this if-else. Then there would be only one call-site in a fairly obviously-correct place."

His reasoning is straightforward: rather than having op_release called in two separate branches (the normal encode path and the replay path), it should be hoisted to a single point after both branches converge, making the invariant "every op gets released" structurally obvious. He granted a review-by on the current version nonetheless:

"Reviewed-by: NeilBrown neil@brown.name"

Layton's response and v3 decision (June 1)

Layton agreed with the suggestion later that day:

"I like that idea. I'll be testing a pile of other patches today anyway, so I'll make this change and test it alongside the rest."

He then offered Chuck Lever two options: "you can either take this one and I'll do a cleanup patch along the lines of what Neil suggests, or I can send a v3."

Chuck Lever's decision (June 1)

Chuck Lever opted for the cleaner path:

"v3 sounds fine."

This means the patch will not be merged in its current v2 form. Layton will send a v3 that incorporates NeilBrown's single-call-site restructuring, and Chuck Lever will merge that version into nfsd-testing.

Nature of the discussion

This is a bug fix — specifically, a posix_acl refcount leak on two NFSv4 OPEN error paths:

  1. The nfsd4_open_omfg short-circuit (when claim decoding fails with a non-seqid-mutating error), and
  2. The v4.0 replay path (when an ACL-bearing OPEN is retransmitted).

Both leaks are remotely triggerable: any client sending a malformed OPEN compound with valid POSIX ACL createhow4 attributes, or retransmitting such an OPEN over v4.0, would cause two posix_acl reference leaks per request. Over time, this constitutes a memory exhaustion DoS vector against the server.

The discussion is not about a new feature or protocol change. It is a targeted fix for a regression introduced by commit 5fc51dfc2eb1, with the v2→v3 evolution driven by a code-quality improvement (single call-site vs. duplicated calls in two branches).

Significance for NFS client development

While this is a server-side fix, it has direct implications for NFS clients:

  • NFSv4.0 clients are most directly affected: any v4.0 client retransmitting an OPEN with POSIX ACL attributes (even non-conformantly, since as Layton noted in the parent thread, "knfsd doesn't gate attributes by minorversion") would trigger the leak on every retransmit. This is a potential DoS vector against servers that accept such requests.
  • NFSv4.2+ clients using the POSIX draft ACL extension (RFC 8881) are affected on the short-circuit path: any OPEN with ACL createhow4 attributes that fails claim validation leaks two posix_acl refs per attempt.
  • The fix ensures that the server's compound dispatcher properly releases all decoded resources regardless of which error path is taken, restoring the invariant that clients can rely on for reliable operation under error conditions (retries, malformed requests, etc.).

Final conclusions and open items

As of the end of this week's window:

  1. v2 is reviewed and approved by NeilBrown (with a structural suggestion) and was already reviewed by Chuck Lever.
  2. A v3 is expected incorporating NeilBrown's single-call-site cleanup, per Chuck Lever's "v3 sounds fine."
  3. The patch will be merged into nfsd-testing after the v3 is posted and tested (Layton indicated he'd test it alongside other patches).
  4. The broader question of whether knfsd should gate attribute acceptance by minorversion (raised in the parent thread) remains open and deferred to a separate changeset.
