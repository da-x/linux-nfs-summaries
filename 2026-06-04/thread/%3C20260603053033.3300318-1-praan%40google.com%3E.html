NFS Direct I/O modernization: pin-aware pages and folio migration hits xfstests wall

Summary

NFS Direct I/O Modernization: Pin-Aware Pages and a Folio Migration That Breaks xfstests

Type: New feature / architectural refactor (with an incidental bug fix), in direct support of future PCI Peer-to-Peer DMA (P2PDMA).

This week, Google's Pranjal Shrivastava posted a seven-patch series titled nfs: Modernize Direct I/O path, aimed at overhauling how the NFS client handles O_DIRECT I/O. The work landed squarely in the review window, with NFS maintainer Anna Schumaker pushing back on two fronts within 24 hours — and one of her objections surfaced a serious functional regression.

The pitch: laying groundwork for P2PDMA

The cover letter frames the series as explicitly preparatory. Shrivastava explains that NFS O_DIRECT "relies on the legacy iov_iter_get_pages_alloc2() API which does not support the pinning requirements for P2P memory," and that the work moves NFS to "the modern iov_iter_extract_pages() API" while migrating direct I/O "from pages to use folios."

He notes the split from an earlier RFC was deliberate: "Following feedback on the initial RFC [1], the modernization and architectural changes are split into this standalone series." (He later had to post a follow-up admitting he'd forgotten the link: "My bad, I missed appending the link for the RFC.")

The cover letter lays out three design pillars — pin-awareness via a new PG_PINNED flag and wb_nr_pinned counter, API migration, and a folio-based extraction helper — and emphasizes bisectability across the seven patches. Notably, he flags that "zone_device_pages_have_same_pgmap() checks are intentionally omitted in the extraction helper since P2PDMA enablement will be introduced in a follow-up series."

The bug fix hidden inside the refactor

Worth highlighting for readers tracking client fixes: patch 4 (nfs: migrate direct I/O to iov_iter_extract_pages) is not purely mechanical. Its commit message states it "fixes a bug in the Direct I/O loop where pages were being unpinned immediately after request creation," with pins now correctly held until I/O completion. That's a genuine lifetime-correctness fix folded into the modernization.

The remaining patches build the scaffolding: making nfs_page pin-aware, tracking pinned-page counts to ensure only primary requests perform final unpinning, centralizing list release in a new nfs_release_request_list helper, introducing an nfs_direct_extract_pages() helper, and finally grouping contiguous pages from the same folio into single nfs_page structures.

Review: doc nits and a wall of test failures

Shrivastava's self-testing was modest — "lightly tested using fio (bs=1M, size=1G) on a small (non-server) machine running Linux 7.1-rc6," reporting a healthy ~5.1 GB/s read run. That turned out to be the crux of the problem.

Anna Schumaker's first reply was a minor one on patch 1: she flagged two kernel-doc warnings about the new pinned parameter not being described in nfs_page_create_from_page and nfs_page_create_from_folio. Shrivastava conceded both: "Ack. I'll add a description in v2."

The substantive blow came from Schumaker's review of patch 6, the folio-grouping optimization. She reported: "I am seeing a LOT of failing xfstests after applying this patch (testing against various NFS versions over TCP with AUTH_SYS)," accompanied by a table showing widespread failures across generic/091, generic/130, generic/240, generic/450, generic/647, and many more — on every NFS version from v3 through v4.2. She asked directly whether he'd run xfstests, "and if you see the same failures?"

The response: a likely grouping bug and a question about scope

In his reply the next morning, Shrivastava was candid that the test gap was his own: "I've just run fio and haven't run xfstests (sorry wasn't aware of them)." He correctly diagnosed the probable culprit, noting that "generic/091 (fsx) is failing across the board," and suspecting "an error in the contiguous grouping logic in Patch 6, likely the offset calculation or handles partial page boundaries." He committed to running xfstests to confirm.

He then raised a structural question worth watching: "Would you suggest breaking out the move to folio in a separate series if patches 1-5 work fine?" That proposal — carving the risky folio migration out of the safer pin-awareness/API-migration groundwork — is likely the shape v2 will take, though it remained an open question at the end of this window.

Where things stand

The thread closed its in-week activity with the regression unresolved and a v2 promised to address both the doc comments and the folio-grouping failures. (A later follow-up landed on 2026-06-16, outside this week's scope.) The key takeaway for NFS client watchers: the P2PDMA groundwork is progressing, but the folio-based direct I/O path needs to clear xfstests before it can be trusted.
