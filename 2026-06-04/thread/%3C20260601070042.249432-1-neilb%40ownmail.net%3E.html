NeilBrown's 18-patch RFC: replacing dentry_create() with vfs_lookup_open() to fix NFS re-export deadlocks

Summary

NeilBrown's 18-Patch RFC: Replacing dentry_create() with vfs_lookup_open()

Overview

On June 1, NeilBrown posted an 18-patch RFC series titled "VFS/nfsd: replace dentry_create()", a significant VFS and NFS server refactoring that introduces a new vfs_lookup_open() interface to consolidate lookup, create, and open operations into a single call path for nfsd. The series is classified as a VFS API refactoring with bug-fix motivation — it eliminates the dentry_create() function entirely while fixing a deadlock class that would have been introduced by NeilBrown's earlier 53-patch directory-locking RFC.

Motivation: A Deadlock in the Prior Series

The cover letter makes the motivation explicit. NeilBrown's March 2026 53-patch series proposed inverting the lock order between inode_lock() on a parent directory and d_alloc_parallel(). As he explains:

"My recent proposal for inverting the order between inode_lock() on a parent dir and d_alloc_parallel() missed that fact that atomic_open() has two callers, and would have resulted in easy deadlocks from nfsd when re-exporting and NFS filesystem."

The solution: rather than trying to make dentry_create() work under the new locking model, provide nfsd with a richer interface that includes all the locking and inode_operations calls internally, allowing nfsd to share more code with the system-call path.

"I think the best way to fix this is to provide a richer interface for nfsd to use, which includes all the locking as well as inode_operations calls. This allows the nfsd behaviour to share more code with the system-call behaviour."

Series Structure

The 18 patches fall into three logical groups:

VFS Refactoring (Patches 01–05)

  • Patch 01: Moves mnt_want_write() and parent inode locking from open_last_lookups() into lookup_open(), since they're only needed there.
  • Patch 02: Moves the delegated_inode retry loop into lookup_open(), eliminating a pointer that was passed around unnecessarily.
  • Patch 03: Replaces struct nameidata and struct open_flag pointer arguments to lookup_open() with individual fields, making it exportable.
  • Patch 04: Adds the new exported vfs_lookup_open() function — "a limited version of lookup_open() which is exported for nfsd to use - to replace dentry_create()."
  • Patch 05: Ensures FMODE_CREATE (actually FMODE_CREATED) is always set when a file is created via the vfs_create() branch, not just atomic_open().

NFSD Refactoring (Patches 06–17)

These patches progressively restructure nfsd4_create_file():

  • Replace fh_fill_both_attrs() with a cleaner pre/post attribute model
  • Move NFS-specific code into a preamble before VFS interaction
  • Remove "subtlety" from the EXCLUSIVE/EXCLUSIVE4_1 switch cases
  • Let the VFS report whether a file was actually created (fixing an assumption that breaks with atomic_open)
  • Reduce the range of directory locks and write-access holds
  • Open-code nfsd4_vfs_create() into nfsd4_create_file()
  • Patch 16: The key switch — "switch nfsd4_create_file() to use vfs_lookup_open()"
  • Patch 17: Extend vfs_lookup_open() usage to non-creating opens as well, so that "when exporting NFS, the lookup and open can be combined using ->atomic_open"

VFS Cleanup (Patch 18)

  • Remove dentry_create() entirely: "dentry_create() is no longer used and can be removed. vfs_lookup_open() is a better interface."

Key Technical Arguments

The atomic_open Optimization

A central technical point in PATCH 16/18 is that the old code performed a separate lookup via start_creating() before calling dentry_create(), which then used atomic_open(). NeilBrown notes:

"Part of the point of supporting atomic_open is to avoid needing a separate lookup. ->atomic_open can do lookup, create, open all in one operation. So doing a lookup before dentry_create() is not optimal."

The new vfs_lookup_open() eliminates this redundancy by combining all three operations.

O_EXCL Semantics for NFSv4

In PATCH 16/18, NeilBrown clarifies a subtle protocol point:

"We only set O_EXCL in the NFS4_CREATE_GUARDED case. This is an NFS protocol option which requests the server to take full responsibility for atomic-create. For NFS4_CREATE_EXCLUSIVE and NFS4_CREATE_EXCLUSIVE4_1 the NFS protocol takes responsibility for exclusive create by providing a verifier to store with the file, and using O_EXCL would interfere with this."

Locking Range Reduction

PATCH 12/18 reduces the directory lock scope:

"We only need to hold the lock taken by start_creating() until the create has been attempted. Holding for longer can serve no purpose... Holding the lock prevents the name from being removed or renamed, but it doesn't prevent a GETATTR or a racing SETATTR or an OPEN."

Similarly, PATCH 15/18 narrows the write-access hold, adding a second want_write only for the unusual case of a read-only creating open that still needs setattr.

Review Discussion: Jori Koolstra's Feedback

Jori Koolstra reviewed patches 01 through 05 on June 1, providing rapid and substantive feedback:

PATCH 01 — Reviewed-by with lockdep question

In his review of PATCH 01, Koolstra raised a lockdep concern:

"This is not about a change in your patch, but I do wonder whether we should also set the lockdep subclass here. We aren't taking any other locks, but that is also true in the create path of mknod, which ultimately calls start_dirop and there we do inode_lock_nested(dir, I_MUTEX_PARENT);"

He concluded positively: "I will say we are doing a lot in lookup_open(), but since open_last_lookups() is its only caller, and there is no particular reason that I see for doing this work there, this is fine by me if it helps your nfsd refactor." — granting Reviewed-by.

PATCH 02 — Reviewed-by

On PATCH 02, Koolstra noted the cognitive-load benefit: "It does make sense to me that we deal with the retry-loop in the function where we call try_break_deleg(). That part is then dealt with on return to open_last_lookups(). So I think, at least from a cognitive load perspective, this change makes sense." — Reviewed-by.

PATCH 03 — Reviewed-by with caveat

On PATCH 03, Koolstra acknowledged the churn: "I think the churn and pushing nd state through many arguments would normally be too much to justify the improvement of scope reduction, but for the goal of getting rid of dentry_create() this is fine." — Reviewed-by.

PATCH 04 — Questions raised (no Reviewed-by)

On PATCH 04, Koolstra identified two issues:

  1. O_EXCL enforcement: "Is O_EXCL enforced anywhere in this call path? I don't really know nfsd, but for the standard O_CREAT call chain, this happens in do_open(), and EEXIST is returned."
  2. Nonsensical flags: "Also, maybe warn when nonsensical bits here, like __O_TMPFILE, are set in open_flag?"

He also noted a positive side effect: "Ah, good, this fixes the bug in dentry_create() where on failing the open part of atomic_open() no other attempt was done by the vfs to do the open."

PATCH 05 — Question raised (no Reviewed-by)

On PATCH 05, Koolstra asked: "What if vfs_create() succeeded but vfs_open() failed? Then we don't set FMODE_CREATED, why?" — an open question about the semantics of FMODE_CREATED when the file exists but the open fails.

Context from Prior Weeks

This series is the direct successor to two related efforts:

  • The 53-patch "lift lookup out of exclusive lock" RFC from March, which established the new locking model but exposed the nfsd deadlock issue.
  • A two-patch fix series from May 26 that patched edge cases in dentry_create()'s use of atomic_open() — fixes that are now subsumed by the complete replacement of dentry_create().

The series is based on a merge of nfsd-testing, vfs-next/work.dcache, and vfs/vfs.fixes. NeilBrown notes: "I probably will need to resubmit after a bunch of that has hit mainline - though a few of the patches could easily be cherry-picked now."

He also flags a dependency conflict: "This will conflict with the O_CREAT|O_DIRECTORY work so obviously we'll need to work out how to order them once we both have enough positive review."

Significance for NFS Client Development

While primarily a server-side refactoring, this series has important implications for NFS client behavior:

  • NFS re-export correctness: The deadlock fix directly affects servers that re-export NFS filesystems (a common pattern in storage virtualization). Clients connecting to such servers would have experienced deadlocks under the prior proposed locking changes.
  • atomic_open path unification: By routing nfsd's CREATE/OPEN through vfs_lookup_open() which can use ->atomic_open, the server's file creation path becomes more consistent with local filesystem behavior. This matters for NFS clients that rely on atomic create semantics (e.g., NFS4_CREATE_GUARDED).
  • Locking range reduction: Narrower lock holds in nfsd mean less contention for concurrent client operations, potentially improving throughput under parallel CREATE/OPEN workloads.
  • Bug fix in open fallback: Koolstra's observation that the new code "fixes the bug in dentry_create() where on failing the open part of atomic_open() no other attempt was done by the vfs to do the open" is a genuine correctness improvement for NFS clients whose atomic_open implementations use finish_no_open().
