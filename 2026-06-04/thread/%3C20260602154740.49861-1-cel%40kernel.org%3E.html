RFC: Named mTLS client identities + per-netns .nfs keyring (early design debate)

Summary

RFC: Named mTLS Client Identities and a Per-Namespace .nfs Keyring

Type: New feature / design RFC — with an embedded bug/security fix. Chuck Lever posted a request-for-comments on 2026-06-02 proposing a named, per-mount client-identity interface for NFS mutual-TLS (xprtsec=mtls) mounts, backed by a new provisioning CLI and a kernel-held .nfs keyring scoped to the network namespace. It is also a fix: it replaces a dead, module-global keyring whose global key_lookup() lets any tlshd that learns a serial read the key.

Why this matters now (brief bridge)

This RFC is the direct payoff of an open question from early May. When Sagi Grimberg tried to document the raw cert_serial=/privkey_serial= mount options in nfs(5) on 2026-05-05, Chuck Lever NAK'd it, calling them "part of an internal kernel-user space API... not intended to be user administrative controls," and admitted he had "no idea this capability was a priority" and would think it through after LSF. Lever's June 2 RFC is that answer: keep the raw serial options as a documented escape hatch, but put a clean named front end on top. It also lands amid a busy stretch of mTLS client bug-fixing — a use-after-free in the mTLS connect path (reported by Michael Nemanov), Chuck's two-patch "Fix a few memory bugs in RPC-with-TLS" series, and Scott Mayhew's tlshd keyring cert-retrieval offset fix — so the design discussion arrives on a foundation that is being actively hardened.

The proposal (Chuck Lever, 2026-06-02)

Lever frames the current state as both awkward and insecure. Today exactly one x.509 cert/key pair serves all NFS mounts, configured in /etc/tlshd/config, and the only per-mount override is two undocumented integer options:

"The administrator must load the cert and key into the keyring out of band, discover the integer serials, and paste them onto the command line. Serials are opaque, non-reproducible across boots, and easy to transpose."

He then flags the security hole at the heart of the fix:

"There is also no isolation: nfs_tls_key_verify() does a global key_lookup() on the serial, and the .nfs keyring created in fs/nfs/inode.c is module-global and never referenced again -- any tlshd that learns a serial can read the key."

The design has three pillars:

  1. A per-network-namespace .nfs keyring, held in struct nfs_net (fs/nfs/netns.h) and allocated at nfs_net_init(), replacing the dead module-global one. Lever points to the DNS resolver's per-netns key scoping (net->key_domain, request_key_net()) as precedent that netns-scoped key handling is acceptable.
  2. Handshake-time attachment, not launch-time. Because the keyring may be empty when tlshd starts, NFS sets ta_keyring to the netns .nfs keyring serial in xs_tls_handshake_sync(), sends it as HANDSHAKE_A_ACCEPT_KEYRING, and tlshd links that serial into its session keyring per handshake — a path tlshd already implements. Credential keys are created possessor-readable only (no KEY_USR_READ), so isolation is "enforceable rather than advisory."
  3. A userspace front end following the nvme-cli / cifscreds pattern: a new nfs-utils tool, working name nfstlskey, with add/list/remove subcommands that convert PEM to DER and create two "user" keys (nfs:x509:<identity>:cert / ...:privkey). The mount command names the identity via a new tls_identity= option; mount.nfs resolves it to the existing serial options. The kernel handshake ABI (integer serials over genetlink) is explicitly unchanged.

Lever was candid about how the draft came together — "I asked Claude to write a rough draft of a design document" — and pointed at where he most wanted input: the retrieval primitive by which userspace names the kernel-held netns keyring. He offered three candidates modeled on KEYCTL_GET_PERSISTENT: (a) a new keyctl command that links the caller's netns .nfs keyring into a destination and returns its serial; (b) an NFS-specific request_key key type; or (c) a per-netns serial exported via procfs/netlink. He also asked the keys folks to confirm the quota/ownership interaction is sane when the user_namespace and net_namespace boundaries do not coincide.

He closed with a forward-looking note on mTLS-protected NFSROOT: because root mounts run in the initial netns before any userspace exists, "the kernel must obtain the client cert and key itself -- the leading candidate is extracting key material from a TPM," making the kernel-owned per-netns keyring a prerequisite.

The debate: which namespace? (Hannes Reinecke, 2026-06-03)

The first substantive reply came from SUSE's Hannes Reinecke, who supported the direction but challenged the binding. He is "all for making keyrings namespace-aware" but argued the netns choice is not a natural fit:

"Logically I think they should be tagged per user-namespace, as this really is about the filesystem (and as such would warrant to be tagged per mount ns). Tagging it per net-namespace is not a great fit... as also block devices might require keys to present the bdev (eg nvme authentication)."

Reinecke's deeper concern was forward-compatibility — that binding to netns "restrict[s] ourselves too much" if non-network consumers of these keys appear later. He framed the real design question crisply:

"As really, the question is: what is the driving the namespace selection? Is it the requesting layer, ie the layer issuing the mount() call? Or is it the providing layer... If it's the former, then we need to tag is as net-namespace. If it's the latter, then we need to tag it as a user-namespace / mount-ns."

He suggested "We should probably ask Christian" (Kozlowski, the keys maintainer).

Chuck's rebuttal (2026-06-03)

Lever pushed back on two points. First, he clarified that his model is not one keyring per namespace in the way Reinecke feared — it is a single .nfs keyring whose keys are visible only in the namespace where they were created:

"My understanding of the proposal is that there is one keyring on the system for .nfs and the keys in it are visible only in the namespace where they were created. Therefore the consumer (say, NFS, or NFSD) is running in a particular network namespace... only the tlshd in that same network namespace will have access to those keys."

Second, he rejected the user/mount-ns binding on functional grounds:

"tlshd is a network layer service, so it doesn't make sense to bind it to a user or mount namespace, IMHO."

State of play

The thread is still in its opening exchange — an RFC posted, one architectural objection raised (netns vs. user/mount-ns binding), and a rebuttal defending the netns choice on the grounds that tlshd is inherently a network-layer service. No final conclusion has been reached. The two live open questions are (1) whether the per-netns keyring binding holds up against Reinecke's "requesting vs. providing layer" framing, and (2) which retrieval primitive userspace should use to name the kernel-held keyring — the point Lever flagged as where he most wants input. Notably, neither the keys subsystem maintainers nor the NFSROOT/TPM path has weighed in yet this week.

For NFS client developers, the headline is that the long-undocumented xprtsec=mtls serial options are finally getting a documented, namespaced, per-mount user interface — and that the security isolation of those credentials is being fixed at the same time. Expect follow-up from the keys folks (Christian Kozlowski) on the quota/ownership nuance and the retrieval primitive.
