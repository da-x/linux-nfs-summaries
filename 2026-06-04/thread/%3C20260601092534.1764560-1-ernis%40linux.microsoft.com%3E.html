Summary

RDMA: ib_device_attr capability fields int→u32 (v6) — min_t() cleanup debate

Context from prior week

This is the sixth revision of Erni Sri Satya Vennela's (Microsoft) patch series to widen the signed-int capability counter fields in struct ib_device_attr to u32. The v5 posting landed on June 1 but was mis-targeted to net-next instead of rdma-next, and drew a pointed objection from Andy Shevchenko:

"Just no. min_t() usage has to be very well justified. It's a beast which may stub one in the back. As Linus said in most of the cases one wants clamp() rather than min(). Please, redo this and similar pieces."

The v6 series summarized here is the direct response: re-targeted to rdma-next, with the min_t() pattern largely retained (but refined) rather than fully replaced by clamp().

The patch — a type-boundary bug fix with NFS/RDMA fallout

The core defect, as Vennela frames it in the cover letter:

"The capability counter fields in struct ib_device_attr are declared as signed int, but these values are inherently non-negative. Drivers maintain their cached caps as u32 and assign them directly into these int fields; if a cap exceeds INT_MAX the implicit narrowing yields a negative value visible to the IB core."

This is a bug fix / type-correctness cleanup, not a new feature or protocol change. The series touches 21 files with 90 insertions and 84 deletions, spanning the IB core, ULPs (iSER/iSERt, SRP/SRPT, RTRS, iPOIB), NVMe-oF host/target, RDS, SMBdirect, and the NFS/RDMA stack (net/sunrpc/xprtrdma/verbs.c, frwr_ops.c, svc_rdma_transport.c, plus include/linux/sunrpc/svc_rdma.h).

The v6 changelog documents the key changes over v5:

  • Fixed subject prefix: net-next → rdma-next.
  • Added U8_MAX clamps in iser_verbs, nvme/host, nvme/target, isert, rds/ib_cm, smbdirect/connect and smbdirect/accept where u32 capability fields were directly narrowed into u8 rdma_conn_param fields without clamping.
  • Guarded the inline_sge_count calculation in nvmet_rdma_find_get_device() to prevent u32 underflow when both max_sge_rd and max_recv_sge are zero.
  • Expanded type migration to 9 additional fields (max_mw, max_raw_ethy_qp, max_mcast_grp, max_mcast_qp_attach, max_total_mcast_qp_attach, max_ah, max_srq, max_srq_wr, max_srq_sge).
  • Fixed min_t(int,...) in svc_rdma_transport; min_t(u32,...) in ipoib, srpt, nvme/target, rds/ib, rtrs-clt, rtrs-srv, xprtrdma/verbs.
  • Fixed frwr_ops.c u32 underflow guard (reorder check before subtraction).
  • Changed sc_max_send_sges to unsigned int, inline_sge_count to u32.
  • Fixed %d → %u in rxe_qp, rxe_srq, ipoib_cm, ib_isert, svc_rdma_transport.

This week's discussion (June 1–2)

Bart Van Assche: min_t() vs unsigned min()

The first review comment came from Bart Van Assche on June 1, who zeroed in on the SRP driver hunk:

"min_t() shouldn't be used if there is an alternative available. For the SRP drivers, please make sure that both arguments of min() are unsigned instead of using min_t()."

This is a narrower objection than Shevchenko's prior-week "redo this and similar pieces" — Van Assche isn't asking for clamp() wholesale, but rather for the author to ensure both operands of min() are naturally unsigned so that min_t() becomes unnecessary. The distinction matters: min_t(type, a, b) exists precisely when the two arguments have different types; if both are already u32, plain min(a, b) is cleaner and avoids the type-cast machinery.

Andy Shevchenko: echoing his v5 objection

Andy Shevchenko followed up on June 2, confirming continuity with his prior-week review:

"Ah, I just answered in similar way against v5. I also mentioned clamp() there."

This reinforces that the min_t() pattern is a persistent concern across multiple reviewers, though neither Shevchenko nor Van Assche has formally blocked the patch — they are requesting changes for v7.

David Laight: macro hygiene and min_3() suggestions

The most technically detailed review came from David Laight on June 2, who raised several distinct points:

On argument ordering in min():

"IMHO it is also best to do min(value, 255) not min(255, value). Like an 'if' put the value you are comparing against second."

This is a style/convention point — Laight argues for putting the variable first and the constant bound second, mirroring how one would write an if statement. It's a minor but consistent preference that affects readability across the series.

On the removed min_t(u8, ...) calls:

"The min_t(u8, x, y) you've removed are usually broken."

Laight is pointing out that the old code was already buggy — using min_t(u8, ...) on values that could legitimately exceed 255 would silently truncate. The v6 U8_MAX clamps (added in v5) address this, but Laight's comment underscores why the original code was problematic.

On clamp() and mixed signedness:

"Maybe I should change clamp() to allow clamp(int_var, 0, unsigned_var). That will need the order of the compares swapping (to do the low bound first). I think they used to be that way around, got changed by a commit that said it didn't change it! Correct code shouldn't care."

This is an interesting aside: Laight is suggesting that clamp() itself could be improved to handle mixed signed/unsigned bounds without requiring the caller to cast. He notes that the comparison order in clamp() was apparently changed at some point with a commit message claiming no behavioral change — but "correct code shouldn't care" about the ordering, implying the original change may have been a regression for edge cases.

On min_3() and preprocessor bloat (second message):

In his second reply, Laight examined specific hunks more closely:

"That should compile as min(). (The constant is known to be non-negative.)"

(Referring to the rtrs-srv hunk where a min_t() was used with a known-non-negative constant — plain min() would suffice since both operands are naturally unsigned after the type migration.)

On the NVMe target's nested min_t(u32, U8_MAX, ...) pattern:

"I think you've change one of those to min_3(). Nesting min() is a good way to bloat the pre-processor output. You don't need any of the casts."

He then proposed a concrete alternative:

"param.initiator_depth = min_3(p->initiator_depth, queue->dev->device->attrs.max_qp_init_rd_atom, U8_MAX); should be fine - if a bit long."

And flagged gratuitous casts:

"There are also (u32)U8_MAX casts lurking - pointless."

Key technical arguments

  1. min_t() is a code smell when avoidable. Both Van Assche and Laight independently argue that min_t(type, a, b) should be replaced by plain min(a, b) when both operands are already the same unsigned type after the migration. The min_t() macro exists to handle mixed-type comparisons; using it when both sides are u32 adds unnecessary preprocessor complexity and obscures intent.

  2. min_3() over nested min(). Laight's suggestion to use min_3(a, b, c) instead of min(min(a, b), c) is a practical improvement — nested min() calls expand into deeply nested ternary expressions in the preprocessor output, while min_3() produces a single flat expression.

  3. Argument ordering convention. Laight's preference for min(value, bound) over min(bound, value) mirrors the natural reading order of an if (value > bound) check. This is a minor style point but one that affects consistency across the series.

  4. The frwr_ops.c underflow guard remains the most concrete NFS/RDMA correctness fix. The reordering of the bounds check before the subtraction in xprtrdma/frwr_ops.c prevents a u32 underflow that would now be possible with unsigned operands. This is a genuine bug fix for NFS over RDMA clients, not just a type migration.

  5. U8_MAX clamps are necessary. The v5/v6 additions of explicit U8_MAX clamps where u32 capability fields are narrowed into u8 rdma_conn_param fields address a real truncation risk that the old signed-int code masked (negative values from overflow would have been caught by sign checks; large positive values now need explicit clamping).

Evolution of the discussion

The thread has now gone through six revisions, with the review focus shifting across versions:

  • v1–v4: Initial type migration, mana driver clamp placement, commit message reframing.
  • v5 (June 1): Mis-targeted to net-next; Shevchenko's "redo this and similar pieces" objection to min_t().
  • v6 (June 1): Re-targeted to rdma-next; U8_MAX clamps added; min_t() pattern retained but refined. Van Assche, Shevchenko, and Laight all request further min_t() cleanup for v7.

The discussion is converging: the core type migration is uncontroversial, the U8_MAX clamps and underflow guards are accepted, and the remaining work is mechanical — replacing min_t(u32, a, b) with min(a, b) where both operands are unsigned, using min_3() for three-way bounds, removing pointless casts, and fixing argument ordering.

Significance for NFS client development

While this series targets the RDMA subsystem, its NFS/RDMA surface is directly relevant to NFS over RDMA clients:

  • xprtrdma/verbs.c: The min_t(u32, ...) fix ensures that the NFS/RDMA client's SGE count calculations use the correct unsigned type, preventing potential underflow or truncation when negotiating RDMA transport parameters.
  • xprtrdma/frwr_ops.c: The u32 underflow guard (reordering the bounds check before subtraction) is a genuine correctness fix for the NFS/RDMA client's forward registration path. Without it, a device reporting zero max_sge_rd or max_recv_sge could trigger an unsigned underflow, leading to incorrect SGE counts and potential RDMA transport failures.
  • xprtrdma/svc_rdma_transport.c: The server-side NFS/RDMA transport also consumes these capability fields; the type migration ensures consistent handling on both sides of the wire.
  • svc_rdma.h: The header change (sc_max_send_sges to unsigned int) affects both client and server code that includes this header.

The frwr_ops.c fix is the most immediately actionable for NFS/RDMA deployments: it prevents a potential transport negotiation failure on devices with unusual (zero) SGE limits, which could manifest as connection setup failures or I/O errors for NFS clients using RDMA transport.

Final conclusions and open items

As of the end of this week's window:

  1. v6 is posted to rdma-next with all prior-week feedback incorporated (correct tree, U8_MAX clamps, underflow guards).
  2. Three reviewers have requested further min_t() cleanup for v7: Van Assche (use unsigned min() instead of min_t() in SRP), Shevchenko (echoing his v5 objection, suggesting clamp()), and Laight (use min_3() over nested min(), remove pointless casts, fix argument ordering).
  3. No merge decision has been posted. The series is expected to receive a v7 addressing the macro hygiene feedback before being picked up by the RDMA maintainers.
  4. The NFS/RDMA portions (frwr_ops.c underflow guard, verbs.c type fixes, svc_rdma_transport.c min_t fix) are unlikely to change materially in v7 — the remaining feedback targets SRP, RTRS, and NVMe target code that doesn't affect the NFS stack.
