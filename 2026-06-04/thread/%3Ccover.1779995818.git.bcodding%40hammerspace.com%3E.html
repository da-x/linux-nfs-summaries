Delegation-recall debate: Coddington defends pre-emptive return; Trond and Macklem push back on v4.1 recall necessity

Summary

Delegation-recall debate: is the client's pre-emptive write-delegation return actually needed?

Overview

This week the thread that opened last week with Benjamin Coddington's single-patch series — a Linux NFSv4 client change to preemptively return a write delegation when a SETATTR drops the holder's own write access — moved from initial posting into active, substantive review. All six in-window messages landed on Friday, 2026-05-29, and the discussion was driven by two of the client's principal maintainers: Trond Myklebust (Hammerspace / Linux NFS client maintainer) and Rick Macklem (FreeBSD knfsd author).

This is a client-side bug fix / performance optimization in the delegation state machine. The patch (in fs/nfs/nfs4proc.c) makes the client detect, before issuing a SETATTR that would strip its own write access, and synchronously return the delegation first — flushing dirty data — so the attribute change then proceeds on an open/special stateid rather than triggering a server-initiated CB_RECALL. The week's debate was not about whether the patch is correct, but about whether the recall it avoids is even required for NFSv4.1+, and where the real latency win should live.

Trond's opening pushback: v4.1 need not recall at all

Trond opened the review by challenging the premise of the whole optimization. He argued that while recalling a delegation in this situation is mandatory under NFSv4.0, "that is certainly not true for NFSv4.1":

"if the holder of a write delegation is just changing the mode, then that should never result in a delegation recall for a well written NFSv4.1 server. The reason is this does not impact the client's ability to cache data, metadata or lock state. It only impacts its ability to rely on previously cached access data when handling new opens."

He extended the same skepticism to uid/gid changes ("the right behaviour is to err on the side of not recalling"), with one carve-out for attribute delegations where the holder's credential might lose the ability to update atime/mtime on return. His bottom line split the problem cleanly:

"So yes to pre-emptive invalidation of the access cache, but I'm very sceptical to actually pre-emptively returning the delegation or even the layouts."

In short, Trond was arguing that the correct client-side response is to invalidate the cached access result, not to tear down the delegation — and that a well-behaved v4.1 server should not be recalling in the first place.

Coddington's core defense: the recall is about truncate semantics, not cache coherence

Coddington responded by reframing why servers actually do recall here. He conceded Trond's point on mode changes and confirmed the stale-access exposure is already handled — the SETATTR reply path sets NFS_INO_INVALID_ACCESS in nfs_update_inode(), and a fresh open over the delegation still revalidates through nfs_may_open() -> nfs_do_access() rather than trusting the cache. But he argued the recall is not about data/metadata/lock coherence; it is about the truncate path:

"When the change removes the holder's write, a later SETATTR(size) under the delegation carries the delegation stateid, not an open stateid (nfs4_copy_delegation_stateid()), and the client can reopen O_WRONLY from the delegation with no OPEN on the wire — so the server can't tell whether the holder still has the file open for write, nor apply the usual 'open-for-write overrides current mode' check for the truncate."

The recall forces a DELEGRETURN + CLAIM_DELEGATE_CUR reclaim that re-establishes a real (or absent) open stateid, "letting the server decide the truncate correctly." He then redirected the optimization's value:

"For write-retaining SETATTRs none of that applies and the server shouldn't recall — which is where the latency I was chasing actually came from, and the better place to remove it."

This was a notable concession: Coddington acknowledged the latency he was targeting actually lives in the write-retaining case (where servers are over-recalling), not necessarily the access-dropping case the patch addresses.

Rick Macklem enters: delayed writes and server-side authorization

Macklem, speaking from the FreeBSD server side, pushed back on Trond's "no impact on cached data" framing by raising delayed writes:

"The case I would be concerned about is delayed writes sitting in the client."

He questioned whether an NFSv4.1/4.2 server should always allow writes from a delegation holder, noting he wasn't sure RFC 8881 spelled it out ("I'm never sure, given that monstrous document") and admitting "the FreeBSD server does not do that" — though the FreeBSD server does allow the file's owner to write. He asked what knfsd currently does, and floated leaving the recall decision up to the server:

"I might argue that whether or not clearing mode bits requires a delegation recall should be left up to the server."

In a follow-up he flagged a "quirky corner": if the server provided a non-empty ACE for the delegation's permissions field, then these SETATTRs either require a recall or the client must invalidate use of that ACE — and he suggested the latter, again leaving recall to the server. He also asked, unprompted by anyone, "Lost me. What's an attribute delegation?"

Coddington's technical rebuttal: knfsd already authorizes via stateid

Coddington gave a detailed, code-level answer that effectively closed Macklem's data-safety concern for Linux. On delayed writes:

"Those stay safe on Linux. The client flushes cached writes on the delegation (or open) stateid, and knfsd authorizes a WRITE from the stateid's granted access, not from a re-check of the current mode — nfsd4_write() just rides the already-open, write-capable nfsd_file resolved from the stateid, so a later mode change doesn't block the holder's writes."

He drew the sharp conclusion: "The only way to lose data is a server that neither honors the holder's stateid writes nor recalls." On what knfsd does, he confirmed it already allows delegation-holder writes and framed it as FreeBSD's target behavior in disguise:

"So knfsd effectively already does the override you're considering for FreeBSD, just implicitly — write authorization comes from the open/deleg stateid, the same principle as the truncate-via-stateid case."

On the ACE corner, he confirmed the Linux client never uses the server-supplied permissions ACE at all:

"decode_rw_delegation() parses the delegation's permissions ACE and discards it (decode_ace() is passed a NULL sink), and the client always does its own ACCESS. So there's nothing to invalidate on our side, and agreed: the recall decision belongs to the server."

He also clarified Trond's attribute-delegation aside for Macklem: the *_ATTRS_DELEG variants "additionally delegate attribute authority — notably the timestamps — so the client can hold and modify them and write them back at DELEGRETURN," which is what Trond meant by the holder's credential needing to retain access.

Macklem's closing synthesis: a server-side path forward

Macklem closed the thread with a constructive, cross-cutting observation that reframed the whole exchange around a server fix rather than the client patch. Noting Coddington's server already authorizes WRITE via the delegation stateid:

"it could allow SETATTR(size) based on a delegation stateid as well. (SETATTR(size) is just a weird variant of WRITE. is it not.)"

He then raised the strategic cost of the client-side pre-emptive return — that it may preemptively remove the incentive for servers to solve this properly:

"I suppose the disadvantage of doing the DELEGRETURN pre-emptively will never allow server implementations to figure out how to allow it without a CB_RECALL, etc."

He committed to a concrete FreeBSD change and acknowledged the interim reality:

"I do plan on patching the FreeBSD server to allow READ, WRITE and SETATTR(size) based on a write delegation stateid (and READ based on a read delegation stateid). ... The FreeBSD server will be doing the CB_RECALL in the meantime."

He signed off warmly: "Useful discussion. Thanks, rick."

Conclusions

  • The patch's correctness is uncontested. Coddington's conservative design — false positives degrade to existing behavior, false negatives are impossible — held up under review.
  • The real disagreement was about necessity, not safety. Trond argued a well-written NFSv4.1 server should not recall on mode/uid/gid changes and that the client should only invalidate the access cache; Coddington countered that servers do recall here, and for a sound reason tied to truncate-via-stateid semantics, with the latency win actually belonging in the write-retaining case.
  • A key technical finding emerged: knfsd already authorizes WRITE (and could authorize SETATTR(size)) purely from the delegation/open stateid rather than re-checking current mode — meaning the data-safety concern that might justify a recall is already handled by Linux's server.
  • The discussion pivoted toward a server-side fix. Macklem's plan to patch the FreeBSD server to honor READ/WRITE/SETATTR(size) via delegation stateids points to the more durable solution, while noting the client's pre-emptive return could inadvertently remove the pressure that drives such server improvements.

The thread ended amicably with no final verdict on whether the patch should land as-is; it stands as a well-reasoned optimization whose long-term value depends on how servers evolve their delegation-recall behavior.
