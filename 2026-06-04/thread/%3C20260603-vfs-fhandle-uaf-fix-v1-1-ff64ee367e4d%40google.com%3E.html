Jann Horn fixes UAF in may_decode_fh() via RCU-protected mnt_ns read; VFS maintainers clarify namespace lifetime semantics

Summary

fhandle: Fix UAF due to unlocked ->mnt_ns read in may_decode_fh()

Overview

This week brought a focused, fast-moving bug-fix discussion on the linux-nfs list (cross-posted to VFS) centered on a use-after-free vulnerability in the open_by_handle_at() syscall path. Google security researcher Jann Horn submitted a patch fixing an unlocked read of mount::mnt_ns in may_decode_fh(), and VFS maintainers Al Viro and Christian Brauner engaged in a detailed back-and-forth to nail down the precise lifetime semantics of mount namespaces that make the RCU-based fix correct.

The Bug

This is a bug fix (not a new feature or protocol change). Jann Horn's initial patch describes the race:

"may_decode_fh() accesses mount::mnt_ns without holding any locks; that means the mount can concurrently be unmounted, and the mnt_namespace can concurrently be freed after an RCU grace period."

The race requires a mount point created via open_tree(..., OPEN_TREE_CLONE), where one thread calls __do_sys_open_by_handle_at (which traverses into may_decode_fh → is_mounted → reads mount::mnt_ns) while another thread closes the last file descriptor, triggering umount_tree → free_mnt_ns → call_rcu(mnt_ns_release_rcu) → eventual kfree. The UAF manifests when the RCU callback frees the namespace while the first thread is still dereferencing it.

Horn noted the bug is only reachable with CONFIG_PREEMPTION or CONFIG_RCU_STRICT_GRACE_PERIOD, since an RCU grace period must elapse during a single syscall without explicit preemption. He assessed the security impact as limited:

"This doesn't seem to have interesting security impact; worst-case, it could leak the result of an integer comparison to userspace (from the level check in cap_capable()), cause an endless loop, or crash the kernel by dereferencing an invalid address."

The fix takes rcu_read_lock() around the mnt_ns access (mirroring what __prepend_path() already does), adds WRITE_ONCE() on racing writers, and documents the pointer's semantics. The patch carries a Fixes: tag for commit 620c266f3949 ("fhandle: relax open_by_handle_at() permission checks") and is Cc'd to stable.

Horn also offered additional tooling: "I used custom tooling to force this race condition to occur and check that it leads to a KASAN splat - let me know if you want me to create a kernel patch to force the race condition and a reproducer you can run." He acknowledged his own role in the original bug: "I remember Christian asking me for feedback on the patch that introduced the bug, and I missed the bug because I didn't realize what the semantics of mount::mnt_ns are..."

The Discussion: Why Is RCU Sufficient?

The core technical question raised by Al Viro was whether the RCU delay between zeroing ->mnt_ns and freeing the namespace is actually guaranteed. In his first reply, Viro wrote:

"Umm... It's somewhat subtle - at the very least you need to explain why there will be an RCU delay between umount_tree() clearing that and having the sucker freed."

Horn proposed documentation language in his next reply:

"This is like an __rcu pointer which is protected by RCU and namespace_sem; however, because most accesses happen under namespace_sem, it is not marked as __rcu, and RCU access is done with READ_ONCE()."

Viro then provided the detailed correctness argument:

"Basically, the store that cleared ->mnt_ns has been done in namespace_sem scope and that scope is either no later than the scope in put_mnt_ns() that has dropped the active refcount of ns to zero. At the beginning of that scope in put_mnt_ns() we are guaranteed to have the passive refcount positive. Dropping the passive reference happens after an rcu delay started in later in the same namespace_sem scope and namespace is not freed until the passive refcount reaches zero."

He immediately corrected himself on a wording error ("s/either//") and summarized his position:

"TL;DR: your fix is correct, but needs a better explanation of correctness. If nothing else, I'd like to have the above findable on lore - I've way too many pieces of half-baked docs sitting around in local notes as it is ;-/"

Refining the Documentation Language

The rest of the thread became an exercise in precise kernel documentation. Viro pushed back on Horn's initial phrasing of "active" for the namespace state, noting in this message:

"Umm... That's actually 'active or has just dropped the last active reference and didn't get around to scheduling decrement of passive refcount yet', unfortunately. Hell knows - 'active or deactivating', perhaps?"

He added a clarification about the distinction between "active" as a state and "active reference" as a refcount concept:

"Note that 'active' in such context is easy to mistake for 'active reference', which it definitely isn't - it does not contribute to active refcount. Mounts within a namespace do not pin it - it's the other way round; they are guaranteed to stay live until they leave the sucker."

Horn agreed and proposed "Containing namespace (active or deactivating, non-refcounted)." Viro endorsed this phrasing:

"That would probably do for now... The lifecycle for mnt_namespace really needs to be documented; right now we have a maze of twisty little functions around that area and it takes quite a non-trivial amount of searching to recall the names - and I am familiar with the area ;-/"

Christian Brauner's Reference-Count Taxonomy

The thread concluded with Christian Brauner's detailed explanation (the maintainer who originally requested feedback on the buggy patch) of the three distinct reference counts in play:

"(1) generic reference count of namespaces in general: __ns_ref - for mntns: keeps the mount namespace and the mounts attached to it alive (2) active reference count of namespaces in general: __ns_ref_active. - always a subset of (1) - only regulates userspace visibility of the namespace and has no lifetime implications per se. 'active' just means 'reachable from userspace'. It's nothing that the mount layer itself should care about at all. (3) passive reference count of struct mnt_namespace - keeps the mount namespace alive but not the mounts attached to it"

He emphasized the practical significance: "With (3) you can grab a reference to the mount namespaces without pinning the mounts in it... At no point does the caller need to artificially prolong the lifetime of a mount namespaces by grabbing a __ns_ref reference count. This is especially useful if the caller needs to do a bunch of sleeping operations before they can actually do the meat of the work they need."

NFS Client Relevance

While this fix lives in fs/fhandle.c (VFS layer), it directly affects NFS client userspace: any process calling open_by_handle_at() on an NFS mount handle is subject to this race. The may_decode_fh() function is the VFS gatekeeper that validates file handles before dispatching to filesystem-specific decode routines (including NFS's nfs_decode_filehandle). A UAF here could corrupt kernel state before the NFS client code ever runs, making this a critical correctness fix for NFS handle-based operations.

Status

The fix is confirmed correct by both Viro and Brauner. The remaining work is documentation polish—Horn will update the commit message and in-tree comments with the agreed-upon "active or deactivating" language and the RCU-delay justification. No v2 has been posted yet as of this week's window close, but consensus on correctness is clear.
