nfs: support FMODE_NOWAIT on O_DIRECT reads (PATCH 0/2)

Summary

nfs: support FMODE_NOWAIT on O_DIRECT reads — initial patch series

Type: New feature / performance improvement for the NFS client (enables non-blocking O_DIRECT reads so io_uring can avoid punting to a background worker).

What happened this week

On 2026-05-30, Dylan Yudaken posted a two-patch series titled "[PATCH 0/2] nfs: support FMODE_NOWAIT on O_DIRECT reads"](20260530221947.49518-1-dyudaken@gmail.com). The thread is self-contained for this week — all three messages (cover letter + two patches) landed in a single burst and, as of the end of the window, had no replies or review feedback from the maintainers. No prior-week history exists for this thread; it opens fresh here.

The problem

Yudaken's cover letter frames the issue around io_uring's behavior with NFS:

"I had noticed that io_uring always punts O_DIRECT NFS reads to a background thread since the file does not advertise FMODE_NOWAIT."

In other words, because NFS O_DIRECT read files do not set the FMODE_NOWAIT flag, io_uring cannot complete these requests inline and must offload them to a task work / async worker path — an avoidable latency cost for users who want fast, non-blocking direct reads.

The proposed fix

Yudaken is candid about his familiarity with the codebase but argues the change is small:

"I am not very familiar with the NFS codebase, but looking around suggests a simple change to nfs_start_io_direct is all that is required to properly support this functionality."

His reasoning for why it is safe:

"On the request issue side, it seems everything in NFS is actually run in the background (post this lock change), and the completion codepaths all look to have no similar locking semantics."

The series is split into two patches:

  1. [PATCH 1/2] nfs: add nowait version of nfs_start_io_direct](20260530221947.49518-2-dyudaken@gmail.com) — introduces nfs_start_io_direct_nowait, a non-blocking variant that "just returns -EAGAIN if locks could not be taken" rather than blocking on existing operations to the same inode. This patch alone adds an unused helper (touching fs/nfs/internal.h and fs/nfs/io.c).

  2. [PATCH 2/2] nfs: expose FMODE_NOWAIT for O_DIRECT read files](20260530221947.49518-3-dyudaken@gmail.com) — wires the helper into the direct-read path and flips on FMODE_NOWAIT. The rationale: "O_DIRECT reads already (mostly) handle async requests, with the exception of locking the inode for direct."

The overall footprint is modest — 4 files changed, 53 insertions, 4 deletions (fs/nfs/direct.c, fs/nfs/file.c, fs/nfs/internal.h, fs/nfs/io.c).

Testing and motivation

Yudaken is upfront that he could not measure the performance win directly:

"I unfortunately do not have the means to test the performance improvement, since even without this change my local network is the bottleneck here."

He nonetheless points to a real-world demand signal — a liburing GitHub issue (axboe/liburing#1499) — noting that "Applying a similar patch on that GitHub issue did give performance gains." He validated correctness functionally by tracing io_uring events:

"Using a test app ... to issue O_DIRECT io_uring reads calls io_uring_queue_async_work without this patch, while with it the call is skipped and the completion is queued into io_uring directly from nfs_direct_read_completion."

Status / where things stand

As of 2026-06-04 the series has been posted but is unreviewed in this window — no maintainer (e.g. Trond Myklebust or Anna Schumaker) has weighed in on the locking-safety argument, which is the crux of the change. A follow-up "[PATCH v2 0/2]" with the same title was posted later by Yudaken on 2026-06-07 (outside this week's scope), indicating the series is actively being iterated toward a reviewable form.

Key takeaways for NFS client readers

  • This is a client-side change enabling FMODE_NOWAIT for O_DIRECT reads, directly benefiting io_uring users by avoiding the async-worker punt path.
  • The central technical question for reviewers is whether returning -EAGAIN from a new non-blocking nfs_start_io_direct variant (instead of blocking on the inode lock) preserves correctness — Yudaken argues the rest of the direct-read request and completion paths are already background/lock-free, but that claim awaits maintainer sign-off.
