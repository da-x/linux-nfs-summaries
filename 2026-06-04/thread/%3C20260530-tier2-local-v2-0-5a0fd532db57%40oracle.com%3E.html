SUNRPC init bug fixes v2 posted — percpu counter check and gssp_lock ordering land clean

Context from prior week

This thread is the direct successor to the v1 series posted by Chuck Lever on May 30. Last week's review cycle saw Jeff Layton issue Reviewed-by tags on both patches within roughly 90 minutes, but raise a design-level objection to Patch 2: the use of percpu_counter_init_many() imposed fragile struct-layout ordering constraints vulnerable to CONFIG_RANDSTRUCT field randomization. The resolution was immediate — Chuck Lever agreed it was "too clever by half" and the v1 review concluded with an agreement to revert to discrete per-pool init/destroy calls.

Key developments this week

v2 series posted (May 31)

Chuck Lever posted the revised two-patch v2 series on May 31, incorporating the sole change requested during v1 review. The cover letter describes the bug shape both patches address:

"Both patches fix the same bug shape in the SUNRPC server: an object becomes reachable by a consumer while a field it depends on is still invalid."

The v2 changelog is minimal and focused:

"Reverted the percpu_counter_init_many() consolidation back to discrete percpu_counter_init()/percpu_counter_destroy() calls."

This single change eliminates both the struct-layout fragility and the CONFIG_RANDSTRUCT risk that Layton identified. The cover letter also emphasizes the two distinct safety arguments: for the proc entry, "the guarantee comes from module load order: sunrpc.ko is a build-time dependency of auth_rpcgss.ko"; for the svc_serv, "the percpu allocation failure is caught and unwound inside __svc_create(), so a half-constructed service never reaches nfsd, lockd, or the NFS callback service."

Patch 1: sunrpc: init gssp_lock before publishing proc entry

Chris Mason's patch (signed off by Chuck Lever) is unchanged from v1. It fixes a race in create_use_gss_proxy_proc_entry() where the /proc/net/rpc/use-gss-proxy dentry is published via proc_create_data() before mutex_init() runs on sn->gssp_lock. The commit message details the consequences:

"A writer that wins the race locks a zero-filled struct mutex. On CONFIG_DEBUG_MUTEXES the missing magic value trips a 'lock used without init' splat; on a production kernel the fast path acquires the lock via CMPXCHG(owner, 0, current). In the latter case a second writer that arrives before init_gssp_clnt() re-zeroes owner can enter set_gssp_clnt() concurrently, shut down the first writer's clnt while it is still in use, and leak the loser's clnt."

The fix moves mutex_init(&sn->gssp_lock) into sunrpc_init_net() so its lifetime matches the sunrpc_net structure, and eliminates the now-unnecessary lazy init_gssp_clnt() helper. The patch carries a "Reviewed-by: Jeff Layton" tag from the v1 cycle.

Patch 2: SUNRPC: Check svc pool percpu counter allocation

Chuck Lever's own patch now uses three discrete percpu_counter_init() calls in __svc_create(), each with its return value checked. On failure, the function unwinds the counters already set up in the current pool and every prior pool before returning an error. The commit message describes the danger of the unpatched code:

"Once that service is live, the hot-path increments in svc_xprt_enqueue(), svc_handle_xprt(), and svc_pool_wake_idle_thread() reach a counter whose backing pointer is NULL. The pointer is a per-cpu offset, so the access does not fault: it resolves to offset zero of the current CPU's per-cpu area and silently corrupts whatever variable lives there."

The trigger is narrow — "a percpu allocation failure during RPC server startup" reachable only by "a local administrator under memory pressure or fault injection; a remote peer cannot induce the bad state on its own." The fix carries Fixes: ccf08bed6e7a ("SUNRPC: Replace pool stats with per-CPU variables").

Review (May 31)

Jeff Layton replied within 28 minutes with a clean Reviewed-by on the revised Patch 2:

"Reviewed-by: Jeff Layton jlayton@kernel.org"

No further discussion followed. The thread closed with both patches carrying full review approval and no outstanding objections.

Nature of the discussion

This is a bug fix series — specifically, two latent initialization-ordering bugs in the SUNRPC server that are only exposed under narrow trigger conditions (a preemption-timed write to a proc entry, or a percpu allocation failure under memory pressure). Neither patch introduces new functionality or changes any protocol behavior. The v2 posting is purely a mechanical revision addressing the one design concern raised during v1 review.

Key technical arguments

  1. Init-before-publish invariant: Both patches enforce that no consumer can observe an object mid-initialization, but through different mechanisms. Patch 1 relies on module dependency ordering (sunrpc.ko before auth_rpcgss.ko guarantees sunrpc_init_net() has run); Patch 2 relies on local error handling within __svc_create() so a half-constructed service never escapes to nfsd, lockd, or the NFS callback service.

  2. Silent corruption is worse than a crash: The percpu counter bug is particularly dangerous because it does not produce a page fault — the NULL per-cpu pointer resolves to offset zero of the current CPU's per-cpu area, silently corrupting an unrelated variable. This makes it far harder to diagnose in the field than a straightforward oops or lockdep splat.

  3. Simplicity over micro-optimization: The v2 change from percpu_counter_init_many() back to discrete calls reflects a common kernel review principle — service creation is not a hot path, so three separate init calls are preferable to one consolidated call that imposes fragile struct layout constraints vulnerable to future refactoring or compiler-level randomization.

Significance for NFS client development

While both fixes target the server side, they have indirect relevance to client developers:

  • The gssp_lock race affects any system using RPCSEC_GSS authentication via gssproxy. A corrupted lock state could manifest as intermittent authentication failures or leaked RPC clients visible on the client side during re-authentication storms.
  • The percpu counter corruption could cause /proc/fs/nfsd/pool_stats to report garbage values, potentially confusing monitoring tools that track NFS server load. More critically, silent per-cpu memory corruption in the server's hot path could lead to unpredictable RPC handling delays or dropped requests that clients would see as timeouts.

Final state

As of the end of the week window (June 4), both patches carry full Reviewed-by tags with no outstanding objections. The v2 series is ready for merge into nfsd-testing. Given the clean review and the fact that Chuck Lever is both the submitter and the nfsd-testing maintainer, application is expected imminently — consistent with the sub-12-hour turnaround seen on the nfsd fixes grab bag v2 posted the same day.
