jbd2/kmalloc follow-up: Ted Ts'o probes allocator semantics; Wilcox favors fixing the allocator over fallback paths

Summary

jbd2 __get_free_pages() → kmalloc(): post-merge design discussion

Type: API modernization / cleanup (with a side-conversation about memory-allocator design). Not a new feature or protocol change. Status: The underlying 17-patch series was already merged into vfs-7.2.misc last week; this week's activity is a technical follow-up on the jbd2 patch specifically.

Bridge to prior weeks

Last week (week ending 2026-05-28) Mike Rapoport posted the full "[PATCH 00/17] fs: replace __get_free_pages() call with kmalloc()" series, which Christian Brauner applied to vfs-7.2.misc on May 27. That series touched two NFS client paths — [PATCH 05/17] swapping a temporary page for kmalloc() in nfs_show_devname(), and [PATCH 06/17] removing genuinely dead page/page2 buffers in the NFSv4 transport-replacement path (nfs4_replace_transport()). This week's thread is a continuation of the review of [PATCH 10/17] (jbd2), which had already drawn a brief question from David Laight about whether __get_free_pages() returns physically contiguous memory.

This week's discussion (June 3–4)

The conversation restarted when ext4 maintainer Theodore Ts'o reopened the jbd2 patch, motivated by a historical concern:

"So historically __get_free_pages() was more efficient than kmalloc since previously the kmalloc overhead meant that a single 4k allocation would take two pages instead of one. I'm guessing that has since changed?"

Ts'o asked Rapoport to explain, for someone not tracking allocator changes over time: how kmalloc compares to __get_free_page at order == 1 (memory and CPU overhead), what kmalloc() does when handed a size larger than PAGE_SIZE (contiguous? error? BUG?), and the overhead at 2× and 8× PAGE_SIZE.

Mike Rapoport answered point by point, confirming that the historical inefficiency is gone:

"Today there's no memory overhead for kmalloc(PAGE_SIZE). Cache refill takes more pages of course, but they will be handed over to the next kmalloc(PAGE_SIZE)."

"There's no memory overhead when order == 1. As for the CPU overhead, the difference for the fast path allocations is not measurable and for the slow path it is anyway determined by the amount of reclaim involved rather than by what allocator is used."

"For size >= PAGE_SIZE kmalloc() always returns contiguous page aligned memory. Larger allocations (> PAGE_SIZE * 2) go straight to the page allocator."

Ts'o thanked Rapoport and pivoted to a broader design question: whether a filesystem could ask for "physically contiguous pages if possible, but ... fall back to a vmalloc-style approach" when contiguity is too hard to obtain. He floated using kmalloc() with flags that suppress forced reclaim/compaction and falling back to vmalloc() on failure, asking whether there's a better way.

Matthew Wilcox responded — noting first that he'd rather see his own "Remove special jbd2 slabs" patch taken instead of this one — and pushed back firmly on the fallback idea:

"I think we'd like to avoid doing that. A lot of code has various workarounds for deficiencies in the memory allocator (some of which have been fixed and thus the workarounds only complicate matters). If the memory allocator(s) aren't providing what you need ... it's best to get that fixed rather than having fallback paths."

Wilcox also clarified the contiguity guarantee ("What users are guaranteed is that kmalloc returns physically contiguous memory. And that if it's a power-of-two that it's naturally aligned"), defended requiring folios to stay contiguous, and sketched the direction he'd prefer:

"We've been trying to move in the direction of exposing more high-level APIs so people can say 'I want to allocate 10MB of memory but it doesn't need to be contiguous' and have the allocator either fail the whole thing up front or make efforts to ensure that you get the whole 10MB. It's a lot more efficient than calling get_free_page() 2500 times and possibly having reclaim run a dozen different times."

Key takeaways

  • No regression from the swap: Rapoport confirmed there is no memory overhead at order == 1, negligible fast-path CPU difference, and guaranteed contiguous, page-aligned memory for kmalloc() sizes ≥ PAGE_SIZE. This validates the jbd2 conversion (and by extension the NFS client conversions in patches 05/06).
  • Design consensus: Wilcox's position is that callers should not build their own kmalloc→vmalloc fallbacks; instead, allocator deficiencies should be fixed at the source, ideally via higher-level allocation APIs.
  • Open threads (just outside this window): David Laight and others continued the jbd2 discussion on June 5 (after the week closed), so the design question is not yet fully settled.

Relevance to NFS client development

The direct NFS impact was last week's merge, but this week reinforces its safety: the kmalloc()-based allocations now in nfs_show_devname() and the cleaned-up nfs4_replace_transport() rest on the same allocator guarantees Rapoport confirmed here. Wilcox's broader argument — prefer fixing the allocator over sprinkling fallback paths through filesystem code — is a useful guiding principle for future NFS client memory-allocation work, since the client relies heavily on page-based buffers in its I/O and transport paths.
