svcrdma Contiguous Pages Patch Causes Major WRITE Regression on Fast RDMA

Summary

svcrdma: Contiguous Pages for RDMA Read Sink Buffers — Severe WRITE Regression Reported

Classification: Bug fix / performance regression (server-side svcrdma over NFS-over-RDMA).

This Week's Activity

The thread, dormant since Chuck Lever's v4 submission in March, was re-opened on June 4 by Mike Snitzer with a serious performance regression report against the now-merged commit.

The Regression

Snitzer reports that the patch, which landed during the 7.1 merge window as commit 18755b8c2f241 ("svcrdma: Use contiguous pages for RDMA Read sink buffers"), causes a dramatic performance drop on very fast RDMA networking on x86_64:

"This patch, which landed during the 7.1 merge window as commit 18755b8c2f241 ("svcrdma: Use contiguous pages for RDMA Read sink buffers"), severely hurts RDMA performance when testing on very fast RDMA networking on x86_64."

The numbers are stark:

"With this commit WRITE performance is 'only' 24.2GB/s. Without this commit WRITE performance is 60.6GB/s."

That is a ~60% throughput loss — roughly 36 GB/s of lost bandwidth on what appears to be a high-end RDMA fabric.

Root Cause Hypothesis: Spinlock Contention

Snitzer points to the profiling data as the key diagnostic clue:

"The cpu burn due to spinlock dominates the flamegraph that was collected."

This suggests the contiguous-page allocation path introduces significant lock contention — likely around the higher-order page allocator or a shared data structure in svcrdma's sink buffer construction — that becomes a bottleneck at high IOPS on fast fabrics. The original patch was designed to reduce per-page DMA mapping overhead (16 bvecs → 1 bvec for a 64 KB READ), but the spinlock cost apparently outweighs that benefit under sustained heavy WRITE load.

Current Status and Next Steps

Snitzer indicates an immediate workaround has been identified:

"We may have a window now on the current Hammerspace testbed to try an incremental fix, but as of now simply reverting commit 18755b8c2f241 is as far as we got."

The testing was performed by Jon Flynn at Hammerspace, and Snitzer offered to share the flamegraph off-list with Chuck Lever and any interested parties. The message is addressed directly to Lever, who authored the original patch series.

Context from Prior Weeks (Brief)

The original v4 patch posted March 19 was a performance optimization for NFS server-side RDMA READ operations. It replaced per-page scatter-gather construction with a single higher-order contiguous page allocation, reducing DMA mappings and Work Requests from 16 to 1 for a typical 64 KB payload. The patch went through three prior review iterations (v2 on March 12, v3 on March 13) with feedback from Christoph Hellwig, who raised concerns about the size limit scaling with page size and suggested min() for clamping. Two companion MR pool exhaustion fixes were accepted into the RDMA subsystem tree by Leon Romanovsky. The contiguous-page optimization itself was queued for the NFS server tree (nfsd-testing) and subsequently merged in 7.1.

Significance

This is a textbook case of a well-intentioned micro-optimization (reducing per-page DMA mapping overhead) that backfires at scale on modern high-bandwidth RDMA fabrics. The spinlock contention in the allocation path — invisible on slower hardware or lower IOPS workloads — becomes dominant when the fabric can sustain 60+ GB/s. The regression affects WRITE performance specifically, which is notable since the patch was designed for the READ sink buffer path; this suggests the contiguous allocation mechanism may be shared or that WRITE operations also traverse the affected code path in svcrdma.

The thread now awaits Chuck Lever's response with either an incremental fix (e.g., reducing lock scope, using per-CPU buffers, or a different allocation strategy) or confirmation of a revert for the next stable/RC cycle.
