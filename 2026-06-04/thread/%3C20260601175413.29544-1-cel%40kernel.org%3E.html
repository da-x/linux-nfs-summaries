xprtrdma: Trivial follow-up fixes to "Decouple req recycling" series

Type: Bug fix / code cleanup (comment correction + dead-assertion removal) on the NFS/RDMA client side.

Overview

On Monday, June 1, Chuck Lever posted a small two-patch follow-up to his recent "xprtrdma: Decouple req recycling from RPC completion" series, addressing minor issues that slipped through in the original work. The patches touch only comments and one dead assertion — no functional behavior changes — but they tidy up the invariant documentation around RDMA memory registration/unregistration on the client.

Patch 1/2 — Fix I3 invariant comment in rpcrdma_complete_rqst

Lever clarified that the WARN_ON_ONCE in rpcrdma_complete_rqst() does not verify that hardware unmapping has completed; it verifies that the list-drain step has occurred:

"frwr_unmap_sync() and frwr_unmap_async() drain rl_registered via rpcrdma_mr_pop() before posting invalidation Work Requests to hardware. The WARN_ON_ONCE verifies that the list-drain step has occurred, not that hardware unmapping has completed."

The comment was reworded to match what the assertion actually checks. This is a documentation fix in net/sunrpc/xprtrdma/rpc_rdma.c (2 lines changed).

Patch 2/2 — Remove tautological I2 assertion in rpcrdma_reply_put

The second patch removes a dead WARN_ON_ONCE(req->rl_reply) check in rpcrdma_reply_put() (net/sunrpc/xprtrdma/verbs.c, 4 lines removed). Lever explained why it can never fire:

"rpcrdma_reply_put() sets req->rl_reply to NULL when it is non-NULL, and skips the block when it is already NULL. The WARN_ON_ONCE(req->rl_reply) that follows can never fire because both paths leave rl_reply NULL."

Discussion and outcome

The thread was very short — just Chuck's cover letter, two patches, and one reply. Anna Schumaker (NFS maintainer) acknowledged the fixes within about two hours:

"Thanks for the extra fixes! I've added them to my testing branch which should be pushed out by the end of the day."

No objections or further discussion followed. The patches are queued in Anna's testing branch for eventual merge, completing the follow-up cleanup to the req-recycling decoupling work on the xprtrdma client.
