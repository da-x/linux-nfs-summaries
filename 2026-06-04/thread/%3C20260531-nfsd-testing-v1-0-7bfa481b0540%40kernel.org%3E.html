nfsd medium-severity bugfixes: six remote-triggerable fixes land, with a replay-path ACL leak and a cross-mount cleanup to follow

Summary

nfsd medium-severity bugfixes: six remote-triggerable fixes land, with a replay-path ACL leak and a cross-mount cleanup to follow

Context from prior weeks

This thread is part of the same week's flurry of NFS server-side hardening work. Just one day earlier, Jeff Layton posted and merged the v2 "grab bag" series of nine patches covering panics, UAFs, data corruption, and DoS vectors. The "medium-severity" series summarized here was posted the following day as a separate, more tightly scoped set of fixes — all classified as remote-triggerable memory leaks, refcounting bugs, and one tracepoint buffer overrun.

Series overview (May 31)

Jeff Layton posted the six-patch series on May 31, describing it as:

"These are classified as medium-severity, remote-triggerable. Some memory leaks and refcounting bugs, and a potential buffer overrun in a tracepoint."

The series is co-authored by Chris Mason (3 patches) and Jeff Layton (3 patches), touching six files with 39 insertions and 25 deletions. Base commit is d9f35aa8be6e on the nfsd-testing tree.

Patch-by-patch highlights

PATCH 1/6: Size fh_verify server sockaddr slot by xpt_locallen — Chris Mason's fix for a tracepoint buffer overrun. The nfsd_fh_verify and nfsd_fh_verify_err tracepoints declared the server sockaddr slot sized by xpt_remotelen but filled it from xpt_local using xpt_locallen. As Mason explains:

"When xpt_locallen exceeds xpt_remotelen, __assign_sockaddr's memcpy writes past the reserved ring-buffer slot."

The bug is particularly nasty on NFS/UDP, where svc_xprt_set_remote() is never called (only TCP and RDMA invoke it), so xpt_remotelen stays 0 for the transport's lifetime. Every fh_verify trace for an NFSv2/v3-over-UDP request then copies 16 or 28 bytes into a zero-byte slot. The fix aligns with all other NFSD tracepoints that already size the server slot by xpt_locallen.

PATCH 2/6: Release path refs on follow_down() error — Another Chris Mason fix. In nfsd_cross_mnt(), a local struct path is initialized with mntget() and dget() before calling follow_down(). On error, the code jumped to out without releasing those references:

"Every other early-exit arm in nfsd_cross_mnt() (other-namespace return, IS_ERR(exp2), and the success tail after the swap) already calls path_put(&path); the err < 0 arm is the lone omission."

The leak inflates mnt_count and d_count on each failed cross-mount, "blocking umount and pinning dentries against the shrinker," and is reachable by any authenticated NFS client through nfsd_lookup_dentry or the NFSv4 READDIR encode path.

PATCH 3/6: Fix nfsd_file leak on inter-server COPY setup failure — Layton's fix for a straightforward error-path leak. When nfsd4_setup_inter_ssc() fails, nfsd4_copy() returned nfserr_offload_denied directly, bypassing the out: label where release_copy_files() would drop the nf_dst reference. Each failed inter-server COPY leaked one nfsd_file, "pinning file/inode/dentry/vfsmount."

PATCH 4/6: Fix dentry ref leak on V4ROOT export filehandle lookup — Layton's fix for a craftable-filehandle leak. nfsd_set_fh_dentry() leaked the dentry reference from exportfs_decode_fh_raw() when the NFS3_FHSIZE or NFS_FHSIZE switch cases detected NFSEXP_V4ROOT and jumped to out. The out: label called exp_put() but never dput(dentry), and fhp->fh_dentry was never assigned so fh_put() couldn't compensate. As Layton notes, "A crafted NFSv3 filehandle targeting a V4ROOT export's fsid triggers the leak on every request."

PATCH 5/6: Release OPEN-decoded posix ACLs via op_release — Chris Mason's fix for a posix_acl refcount leak on the NFSv4 OPEN short-circuit path. When nfsd4_decode_open_claim4() returns a non-seqid-mutating error, the dispatcher short-circuits before op_func runs, but op_release must still release op_pacl and op_dpacl. Before this change, OP_OPEN had no .op_release in nfsd4_ops[], so both posix_acl refs leaked on every malformed OPEN compound carrying valid POSIX ACL createhow4 attributes. The fix adds nfsd4_open_release() as .op_release for OP_OPEN and removes the now-redundant release pair from nfsd4_open()'s out_err: label to avoid double-release.

PATCH 6/6: Fix layout fence worker double-reference race — Layton's fix for a pNFS layout stateid leak. The workqueue core clears WORK_STRUCT_PENDING before the callback is invoked, so delayed_work_pending() in lm_breaker_timedout() can return false while the fence worker is already running:

"This lets the breaker take a duplicate sc_count reference and schedule a new worker that coalesces with the in-progress one. The extra reference is never put, leaking the layout stateid."

The fix replaces the racy delayed_work_pending() check with an ls_fence_inflight boolean set atomically with refcount_inc_not_zero() under ls_lock, and removes the self-rearm mod_delayed_work() at the top of the worker.

Review discussion and evolution

Chuck Lever's replay-path catch (May 31)

The series was merged quickly, but not without a significant review catch. Chuck Lever applied five of the six patches to nfsd-testing on May 31, but held back PATCH 5/6 after identifying a gap in the fix:

"The double-free fix is right, but op_release is not called unconditionally after every op, and that gap leaks the ACLs on the v4.0 replay path."

Lever pointed out that op_release runs only at the release: label inside nfsd4_encode_operation(), and the compound loop skips that encoder on a replay:

"So every ACL-bearing v4.0 OPEN retransmit leaks two posix_acl refs."

He provided a concrete fix — calling op->opdesc->op_release(&op->u) in the nfserr_replay_me branch — and noted: "I've applied the other 5 in this series, so you can just resend this one."

Jeff Layton acknowledged the catch: "Good catch, will fix." He also raised an interesting protocol question:

"I initially had hoped that we could rely on the fact that a v4.0 client couldn't issue an OPEN with a POSIX ACL attribute in it, but it turns out that knfsd doesn't gate attributes by minorversion. Maybe it should? That's a separate changeset though if so."

This highlights a broader protocol-hygiene gap: the kernel NFS server accepts and processes v4.2+ attributes (like POSIX draft ACLs) even from v4.0 clients, which is technically non-conformant but has practical security implications for error paths like this one.

Al Viro's cross-mount cleanup (June 1)

Al Viro weighed in on PATCH 2/6 the following day, suggesting a broader cleanup of nfsd_cross_mnt():

"Might be better to unify all those path_put()... Something like this, perhaps?"

He proposed moving all path_put() calls past the point where the codepaths join, eliminating the separate path_put() on each failure exit. Jeff Layton responded favorably: "Looks reasonable. Chuck has already taken this patch into his tree, but we could do a cleanup on top. Want to send us an 'official' patch?"

Al Viro sent the formal patch with the caveat: "Not a problem, but it's completely untested. It compiles, but..." The commit message explains the rationale:

"Instead of having a separate path_put() on each failure exit, as well as on the normal path, let's move all of those past the point where these codepaths join. We want to keep the ordering between path_put() and exp_put(), so move that one as well."

Layton confirmed he'd test it: "Thanks Al. I'll toss it onto the pile that I'm testing." Chuck Lever noted that the cleanup could be applied directly: "We can replace any of the patches already in nfsd-testing, it's a topic branch."

Nature of the discussion

This is a bug fix series — not a new feature or protocol change. All six patches address remotely-triggerable defects: a tracepoint buffer overrun (PATCH 1), three memory/refcount leaks on error paths (PATCHES 2–4), a posix_acl refcount leak on the OPEN short-circuit path (PATCH 5), and a layout stateid double-reference race in pNFS fencing (PATCH 6). The discussion evolved from a clean merge of five patches into two follow-up items: a replay-path ACL leak fix for PATCH 5/6, and an untested cleanup patch for nfsd_cross_mnt() from Al Viro.

Significance for NFS client development

While all fixes are server-side, several have direct implications for client behavior and testing:

  • The fh_verify tracepoint overrun (PATCH 1) is particularly relevant for any deployment using ftrace/perf on NFS/UDP servers — the zero-byte slot means every single fh_verify event was corrupting ring buffer memory. Clients using NFSv2/v3 over UDP are the trigger, though the corruption is entirely server-side.
  • The layout fence worker double-reference race (PATCH 6) directly affects pNFS clients: a leaked layout stateid means the server can't properly reclaim or re-fence layouts, potentially causing client-visible stalls during lease manager fencing operations. Clients relying on timely layout recalls after server restarts are most affected.
  • The V4ROOT dentry leak (PATCH 4) is a DoS vector: "A crafted NFSv3 filehandle targeting a V4ROOT export's fsid triggers the leak on every request." Any client that can send arbitrary filehandles (including misconfigured or malicious ones) can pin dentries indefinitely.
  • The inter-server COPY leak (PATCH 3) affects deployments using NFSv4.1+ inter-server copy operations; each failed setup leaks a file reference that pins the underlying inode, potentially preventing filesystem unmounts.
  • The replay-path ACL leak identified by Chuck Lever is notable for NFSv4.0 clients specifically: any v4.0 client retransmitting an OPEN with POSIX ACL attributes (even if non-conformant) would trigger the leak on every retransmit, making it a potential DoS vector against servers accepting such requests.

Final conclusions and open items

As of the end of this week's window:

  1. Five of six patches are merged into nfsd-testing with commit hashes confirmed by Chuck Lever.
  2. PATCH 5/6 needs a v2 to add op_release on the v4.0 replay path, as directed by Chuck Lever. Layton has acknowledged and committed to resending.
  3. Al Viro's cleanup patch for nfsd_cross_mnt() is in Jeff Layton's testing queue but untested; it will presumably be applied on top of or as a replacement for the already-merged PATCH 2/6.
  4. The question of whether knfsd should gate attribute acceptance by minorversion (raised by Layton) remains open and was explicitly deferred to a separate changeset.
