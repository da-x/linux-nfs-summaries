nfsd filecache shutdown-race fix lands as v3: net-ref approach abandoned in favor of widened nfsd_gc_lock

Summary

nfsd filecache shutdown-race fix lands as v3: net-ref approach abandoned in favor of widened nfsd_gc_lock

Context from prior weeks

This thread is the v3 resend of a single patch that was PATCH 8/9 in Jeff Layton's "locally-triggerable bugs" series. That series went through two full review cycles this week: the original eight-patch v1 posted June 1 drew a scalability objection from Al Viro about taking get_net()/put_net() on every file allocation, and the nine-patch v2 posted June 2 reworked the patch to take the net ref only at disposal time. Even that rework was rejected: Chuck Lever identified a put-ordering race in nfsd_file_put_local() and a placement flaw where get_net() sat "at the consuming end of the window it is meant to close." Layton conceded on June 3 — "> Ok, I'm convinced, and the fix looks fairly straightforward. If you're ok with merging the rest of the set, I'll plan to resend this one separately." — and Lever merged the other eight patches into nfsd-testing that same day.

This week's single message is that promised resend, posted June 4.

The patch (June 4)

Jeff Layton posted the standalone v3 on June 4 at 13:57 UTC, with a cover note that frames it as the last piece of the series:

"This is the remaining patch from the 9 patch series I posted earlier this week. This version doesn't touch the net refcount and instead relies on increasing the scope of the nfsd_gc_lock."

The bug being fixed is a per-net shutdown race in the filecache. As Layton describes it, the shrinker, GC worker, and fsnotify/lease callbacks can unhash an nfsd_file from the rhashtable and then call nfsd_file_dispose_list_delayed() to move it to the per-net dispose list. If nfsd_file_cache_shutdown_net() runs concurrently, its rhashtable walk misses the already-unhashed file, and its drain of the per-net dispose list can run before the file has been queued:

"The file then sits on the per-net list with no thread to drain it, leaking both the file and its associated state."

The root cause is a synchronization gap: the GC worker and shrinker already hold nfsd_gc_lock while walking the LRU, but they release it before calling nfsd_file_dispose_list_delayed(), and the fsnotify/lease path (nfsd_file_close_inode) has no synchronisation at all.

The three-part fix

Rather than taking net references (the approach rejected in v1/v2), v3 widens the existing spinlock:

  1. Widen nfsd_gc_lock in both nfsd_file_gc() and nfsd_file_lru_scan() to cover the nfsd_file_dispose_list_delayed() call.
  2. Wrap nfsd_file_close_inode() in nfsd_gc_lock so that all three callers of nfsd_file_dispose_list_delayed() hold the lock.
  3. Add a spin_lock/unlock(nfsd_gc_lock) barrier in nfsd_file_cache_shutdown_net() after the purge, "so that any in-progress disposal has fully completed before the per-net list is drained."

Layton justifies the spinlock choice: "All operations inside the lock are non-sleeping (rhashtable lookups, atomic bit/refcount ops, list moves, svc_wake_up), so the spinlock is appropriate."

The change touches a single file (fs/nfsd/filecache.c) with 26 insertions and 9 deletions. It carries Fixes: 43fd953fa7e2 ("nfsd: simplify the delayed disposal list code") and an Assisted-by: Claude:claude-opus-4-8 tag, continuing the series' pattern of AI-assisted analysis with human architectural judgment.

Evolution across versions

The patch's journey through three versions illustrates a notable design pivot in kernel locking strategy:

VersionApproachOutcome
v1 (June 1)get_net() at allocation, put_net() at freeRejected by Al Viro for cacheline scalability
v2 (June 2)get_net() only at disposal time + NFSD_FILE_NET_HELD flagRejected by Chuck Lever for put-ordering race and get_net() placement
v3 (June 4)Widen nfsd_gc_lock to cover dispose calls; no net refPosted, pending merge

The v3 approach is arguably the cleanest of the three: it avoids adding any new reference-counting machinery, leverages a lock that already exists for this code path, and the critical section remains short (all non-sleeping operations). The tradeoff is slightly longer spinlock hold times during GC/shrinker operation, but since those paths are already serialized on nfsd_gc_lock for the LRU walk, the additional time is bounded by a single list move and atomic refcount decrement.

Nature of the discussion

This is a bug fix — specifically a memory leak (file + associated state) triggered by a race between filecache disposal and per-net namespace teardown. It is not a new feature or protocol change. The thread contains no review replies within this week's window; it is a standalone resend awaiting Chuck Lever's merge decision.

Significance for NFS client development

While the fix is entirely server-side, its implications for client-facing deployments are concrete:

  • Namespace teardown reliability: Any deployment using network namespaces with active NFS exports (containers, k8s pods, multi-tenant servers) could previously leak file cache entries when a namespace was destroyed while files were in-flight through the GC/shrinker path. For clients, this manifests as server-side resource exhaustion over time — each leaked nfsd_file pins an underlying struct file, dentry, and inode.
  • Shrinker interaction: The memory shrinker is a global mechanism that fires under memory pressure. On heavily-loaded NFS servers serving many clients, the shrinker path was one of the three race participants. Clients generating sustained I/O load increase the probability of hitting this window during namespace teardown.
  • Lease/fsnotify path: The fsnotify/lease callback (nfsd_file_close_inode) was the most exposed path since it had no prior synchronization. Clients that trigger file closes (via CLOSE, delegation recall, or lease expiry) while a namespace is being torn down were the primary trigger vector.

Final conclusions and open items

  1. The v3 patch has been posted but no merge confirmation from Chuck Lever appears within this week's window. Given that Layton explicitly framed it as "the remaining patch" and Lever had already merged the other eight, a quick merge is expected.
  2. The net-reference approach is definitively abandoned in favor of lock widening. This resolves both Al Viro's scalability concern (no atomic counter on a shared cacheline) and Chuck Lever's correctness objection (no new refcount to order).
  3. The full nine-patch "locally-triggerable bugs" series is now complete — eight patches merged June 3, and the ninth (this patch) posted June 4. The series represents a comprehensive hardening of nfsd's filecache lifetime management, eliminating an entire class of shutdown races by consolidating synchronization under nfsd_gc_lock.
