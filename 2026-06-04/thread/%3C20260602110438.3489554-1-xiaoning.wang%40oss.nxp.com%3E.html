NFS client: fix stale PG_UPTODATE warning in nfs_free_request() after read errors

Overview

This week, NXP engineer Clark Wang posted a one-patch series to the linux-nfs list addressing a long-dormant bug in the NFS client read path. The thread is currently just the cover letter and the patch itself, both posted on 2026-06-02, with no maintainer or community replies yet in this window. It is squarely a bug fix for the NFS client (not a protocol change or new feature), and it lands in the same nfs_free_request() territory that has produced other stale-flag WARNING reports earlier this year.

The reported bug

Wang found the problem "occasionally occurring in the recent daily test based on 6.18" on an NXP i.MX952 EVK board, producing a kernel WARNING at fs/nfs/pagelist.c:587 inside nfs_free_request(), reached via the read-completion path (nfs_read_completion → nfs_release_request → nfs_page_group_destroy → nfs_free_request).

He notes the issue is deterministic to reproduce:

"This WARN dump can be reliably reproduced on my side by using rsize=1024 during NFS mount and disconnecting the connection while reading data from NFS."

Root-cause analysis

The heart of the report is Wang's diagnosis of how PG_UPTODATE accumulates across subrequests:

"I found when a folio is split into multiple subrequests, the PG_UPTODATE flag is set each time a subrequest data read succeeds. As earlier subrequests succeed, this bit accumulates progressively; however, if a later subrequest fails, all previously accumulated bits must be invalidated."

The failure mode: when a folio's read is split into several subrequests, early completions that fall within hdr->good_bytes advance the page group's uptodate state. If a later subrequest in the same group then completes with NFS_IOHDR_ERROR, the error path of nfs_read_completion() does not clear the previously accumulated bits:

"The problem arises because the error path of nfs_read_completion() does not properly clear these stale bits, leading to a WARN when the page group is destroyed."

Wang traces the offending logic back to a very old commit and candidly flags his uncertainty about whether it was intentional:

"The logic causing this issue appears to have existed since '67d0338edd71 (nfs: page group syncing in read path)', which is a very old patch. No one seemed to have reported this issue before. I'm not sure if this was intentionally designed that way? (Sorry, I don't know much about NFS; Just study some code to try fixing this issue.)"

The proposed fix

The single patch, "nfs: keep PG_UPTODATE clear after read errors in page groups", touches fs/nfs/read.c (+24/-1) and include/linux/nfs_page.h (+1). Rather than merely clearing the flag once on error, it introduces a sticky page-group read-failed flag:

"Add a sticky page-group read-failed flag. Once any subrequest in the group is known to be bad, mark the group failed, clear any accumulated PG_UPTODATE state, and refuse further PG_UPTODATE synchronization for the rest of the completion walk."

This matters because a naive one-shot clear would not be enough — as Wang explains, "a subsequent successful subrequest can re-enter nfs_page_group_set_uptodate(), restore the page-group sync state, and leave stale PG_UPTODATE behind for nfs_page_group_destroy() to trip over in nfs_free_request()." The sticky flag prevents that rebuild for the remainder of the completion walk.

The patch carries a Fixes: 67d0338edd71 ("nfs: page group syncing in read path") tag and is signed off by Clark Wang. (The actual diff was omitted at ingest, so the precise implementation details are not reproduced here.)

Context and significance

This joins a recurring pattern of stale-page-flag WARNINGs surfacing in nfs_free_request() on the NFS client. Earlier this year there were separate reports about a stale PG_WB_END flag during read completion with FS-Cache enabled (Mike Owen, March 9 and April 1, 2026). Wang's report is distinct — it concerns PG_UPTODATE and the subrequest-splitting / partial-read error path rather than FS-Cache writeback — but the shared symptom (a stale page-group flag tripping a WARN at teardown) underscores how delicate the page-group state machine is when reads are fragmented across multiple RPCs.

Status / open questions

  • No replies yet in this window; the patch is awaiting maintainer review.
  • Wang explicitly invites discussion and acknowledges his limited NFS background, so expect scrutiny on whether the sticky-flag approach is the cleanest fix versus an alternative (e.g., clearing state more centrally in nfs_read_completion()).
  • The key open question he poses — whether the original behavior was "intentionally designed that way" — will likely drive the maintainer response.
