nfsd OPEN ACL leak fix v3 merged: single op_release call-site closes the last gap

Summary

This thread is the final, two-message coda to a three-week saga about a posix_acl refcount leak in the Linux NFSv4 server (nfsd). After PATCH v2 was reviewed and approved last week — with NeilBrown suggesting a structural cleanup and Chuck Lever agreeing that "v3 sounds fine" — Jeff Layton posted the v3 patch on June 1, and Chuck Lever applied it to nfsd-testing the next morning. The fix is now merged, closing out a remotely triggerable memory-exhaustion vector against NFSv4 servers.

Context from prior weeks (brief bridge)

The bug was introduced by commit 5fc51dfc2eb1 ("NFSD: Add support for XDR decoding POSIX draft ACLs"), which made nfsd4_decode_createhow4() allocate refcounted struct posix_acl objects and stash them in open->op_pacl and open->op_dpacl. Those refs had to be released when the OPEN compound finished — but two code paths leaked them:

  1. The nfsd4_open_omfg short-circuit: when nfsd4_decode_open_claim4() returns a non-seqid-mutating error, the dispatcher skips op_func (i.e., nfsd4_open() never runs), so the release pair that lived at nfsd4_open()'s out_err: label was never reached.
  2. The v4.0 replay path: op_release was only invoked from nfsd4_encode_operation(), and the compound loop skips that encoder for replayed operations — so every ACL-bearing v4.0 OPEN retransmit leaked two refs.

v1 (May 31) fixed the short-circuit by adding nfsd4_open_release() as .op_release for OP_OPEN. Chuck Lever caught the replay gap before merging: "So every ACL-bearing v4.0 OPEN retransmit leaks two posix_acl refs." v2 (May 31) patched the replay branch, and NeilBrown approved it while suggesting a cleaner structure: "I think it would be even better if the ->op_release() call were moved out of nfsd4_encode_operation() and places after this if-else. Then there would be only one call-site in a fairly obviously-correct place."

This week's activity (June 1 – June 2)

v3 posted (June 1)

Jeff Layton posted the v3 patch on June 1, authored by Chris Mason and carrying review-by tags from both Chuck Lever and NeilBrown. The v3 changelog is terse:

"Changes in v3:

  • Move op_release to a single callsite that accomodates all cases"

The patch makes the structural change NeilBrown proposed. Rather than calling op_release() separately in the normal-encode branch and the replay branch, it hoists the call out of both branches and places it once, after the if-else in nfsd4_proc_compound():

"Move the op_release() call out of nfsd4_encode_operation() and the replay branch, placing it after the if-else in nfsd4_proc_compound(). This gives a single call site in a fairly obviously-correct place, covering both the normal encoding and replay paths."

The OP_OPEN wiring from v2 is retained: nfsd4_open_release() is registered as .op_release for OP_OPEN, and the now-redundant posix_acl_release() pair is removed from nfsd4_open()'s out_err: label to avoid a double-release. As Layton's commit message notes, "posix_acl_release() is NULL-safe, so the single release site covers both the normal path and the nfsd4_open_omfg short-circuit." The diff touches fs/nfsd/nfs4proc.c (+11/-2) and fs/nfsd/nfs4xdr.c (-3).

Merged (June 2)

Chuck Lever applied the patch to nfsd-testing on June 2, quoting the commit message and confirming:

"Applied to nfsd-testing, thanks!" "[1/1] nfsd: release OPEN-decoded posix ACLs via op_release — commit: 844f63869b2038377b82cdb90f8872acbdc8fde3"

The merge landed roughly eighteen hours after the v3 posting, with no further review comments in between.

Nature of the discussion

This is a bug fix — not a new feature or protocol change. Specifically, it repairs a posix_acl refcount leak on two NFSv4 OPEN error paths (the nfsd4_open_omfg short-circuit and the v4.0 replay path), tagged with Fixes: 5fc51dfc2eb1. The v3 iteration was driven purely by a code-quality improvement (single call-site vs. duplicated calls in two branches) rather than any new defect.

Significance for NFS client development

Though this is a server-side fix, the implications for clients are concrete:

  • NFSv4.0 clients were most directly exposed: any v4.0 client retransmitting an OPEN carrying POSIX ACL attributes (even non-conformantly, since knfsd does not gate attribute acceptance by minorversion) triggered two posix_acl ref leaks per retransmit — a memory-exhaustion DoS vector against the server.
  • NFSv4.2+ clients using the POSIX draft ACL extension (RFC 8881) were exposed on the short-circuit path: any OPEN with ACL createhow4 attributes that failed claim validation leaked two refs per attempt.
  • The fix restores the server-side invariant that all decoded resources are released regardless of which error or replay path is taken — a guarantee clients can rely on for reliable operation under retries and malformed-request conditions.

Final conclusions

  1. The patch is merged into nfsd-testing as commit 844f63869b2038377b82cdb90f8872acbdc8fde3, resolving the leak on both the short-circuit and replay paths.
  2. NeilBrown's single-call-site restructuring was adopted in v3, making the "every op gets released" invariant structurally obvious.
  3. The thread is closed; no open items remain for this fix. (The separate question of whether knfsd should gate attribute acceptance by minorversion, raised in the parent series, remains deferred to a different changeset.)
