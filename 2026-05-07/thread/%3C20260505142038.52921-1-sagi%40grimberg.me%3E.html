Discussion on Documenting mTLS Mount Parameters in nfs(5)

Summary

Discussion on Documenting mTLS Mount Parameters in nfs(5)

This week, a brief but significant discussion occurred regarding the documentation of mutual TLS (mTLS) authentication parameters for NFS mounts. The exchange highlights an ongoing tension between exposing kernel capabilities to userspace and maintaining clean administrative interfaces.

The Proposal

Sagi Grimberg submitted a patch to document two new mount parameters, cert_serial and privkey_serial, which are used for x.509 certificate and private key pair authentication in mTLS scenarios As proposed by Sagi Grimberg. He noted:

"Two new mount params for x.509 certificate and private key pair used for mTLS authentication. These have been added a while ago, document them officially."

The patch aimed to add these parameters to the nfs(5) man page, making them part of the official user-facing documentation.

The Rejection

Chuck Lever immediately rejected the patch, providing a clear rationale rooted in API design principles:

"NAK. There is a very good reason they have not been added to nfs(5) already. As I stated before, these are part of an internal kernel-user space API. They are not intended to be user administrative controls."

Lever's position is that these parameters represent an internal mechanism rather than a stable, user-administrated interface. This distinction is crucial for NFS client development, as it affects how administrators configure secure mounts and what interfaces they can rely upon long-term.

The Open Question

Sagi Grimberg responded by seeking clarification on the intended user interface:

"Ah ok, I guess I misunderstood the thread. So what do you think the user interface for this if not key serials?"

This question reveals a gap in the current mTLS implementation roadmap. Chuck Lever acknowledged this uncertainty:

"I don't have an answer for that question. Again, I had no idea this capability was a priority so I haven't thought it through yet. When LSF is done I will give it some thought."

Conclusions and Implications

This discussion highlights several key points for NFS client development:

  1. API Stability Concerns: The rejection of documenting cert_serial and privkey_serial indicates that the current mTLS implementation may undergo significant changes before being exposed as a stable user interface.

  2. Priority Assessment: Chuck Lever's admission that he was unaware of the priority level of mTLS capabilities suggests this feature may not have been broadly considered in NFS development planning until now.

  3. Future Direction: The conversation points toward future discussions at LSF (Linux Storage Forum) where the proper user interface for mTLS authentication will be designed. This implies that current implementations using key serials may be temporary or internal-only solutions.

  4. Documentation Philosophy: The exchange reinforces the principle that not all kernel capabilities should be documented in user-facing manuals, particularly when they represent internal APIs rather than stable administrative interfaces.

The thread concludes without resolution, leaving the question of how mTLS authentication will be properly exposed to userspace administrators open for future discussion. This is an important area to watch for NFS client developers implementing secure mount capabilities.
