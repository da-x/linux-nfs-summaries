mm: Improve RWF_DONTCACHE write performance with targeted dirty tracking (v6)

Summary

mm: Improve RWF_DONTCACHE write performance with targeted dirty tracking (v6)

Status: Patch series v6 posted, Reviewed-by obtained from Jan Kara. Type: Performance Improvement / Bug Fix (concurrency fixes in v6). Key Participants: Jeff Layton, Jan Kara.

Overview

Jeff Layton submitted version 6 of a two-patch series aimed at significantly improving write performance for RWF_DONTCACHE operations. This iteration addresses concurrency bugs discovered via the Sasiko static analysis tool after the v5 submission. The patches introduce per-bdi_writeback tracking for DONTCACHE dirty pages and replace inline writeback submission with a background flusher kick, drastically reducing tail latency and improving throughput parity with buffered I/O.

Key Technical Arguments & Evolution

1. Tracking DONTCACHE Dirty Pages (Patch 1/2)

The first patch introduces a WB_DONTCACHE_DIRTY counter per bdi_writeback. This allows the writeback subsystem to distinguish between standard dirty pages and those marked with the dropbehind flag (dirtied via RWF_DONTCACHE).

  • Concurrency Fixes: Layton noted that Sasiko identified bugs in previous versions. Key fixes in v6 include:
    • Using atomic folio_test_clear_dropbehind() in __filemap_get_folio_mpol() to prevent double-decrementing the counter by concurrent readers.
    • Adding a mapping_can_writeback() guard before decrementing the counter to match the increment path logic.
  • Review: Jan Kara approved this approach, stating:

    "Yeah, good catch with the folio_test_clear_dropbehind(). Feel free to add: Reviewed-by: Jan Kara jack@suse.cz" Reviewed-by added.

2. Kicking Writeback Flusher Instead of Inline Submission (Patch 2/2)

The second patch replaces the inline filemap_flush_range() call in generic_write_sync() with a mechanism that kicks the writeback flusher thread. This moves writeback submission off the writer's hot path.

  • Problem: Perf profiling showed that the performance bottleneck was not lock contention but the work of walking the page tree and submitting I/O inline, which inflated p99.9 latency from 23ms (buffered) to 93ms (dontcache).
  • Solution: A new WB_start_dontcache bit triggers the flusher to write back a proportional number of pages based on the WB_DONTCACHE_DIRTY counter. This preserves I/O batching while limiting the scope of expedited writeback to avoid flushing unrelated buffered data.
  • Concurrency Fixes:
    • Using test_and_clear_bit for WB_start_dontcache to prevent lost wakeups from concurrent writers.
    • Moving wb_wakeup() outside the unlocked_inode_to_wb_begin/end section to avoid re-enabling interrupts while the i_pages xa_lock is held during cgroup writeback switches.
  • Review: Jan Kara approved this patch as well:

    "Looks good. Feel free to add: Reviewed-by: Jan Kara jack@suse.cz" Reviewed-by added.

Performance Impact

Layton provided extensive benchmark results demonstrating significant improvements:

  • Single-stream throughput: Sequential write/dontcache improved by +201% (298 MB/s to 897 MB/s).
  • Tail Latency: p99.9 latency for sequential writes dropped from ~8.9 seconds to ~28ms (-99.7%).
  • Multi-writer Parity: In competing writer scenarios (dontcache vs. buffered), the previous version starved the dontcache writer 2:1. With per-bdi_writeback tracking, both writers now receive equal bandwidth.

    "Previously the buffered writer starved the dontcache writer 2:1. With per-bdi_writeback tracking, both writers now receive equal bandwidth." Layton

  • Dirty Page Reduction: Peak dirty pages in a 32-file write test dropped from 1.8 GB to 213 MB (-88%).

Conclusion

The v6 series is now ready for inclusion, having addressed critical concurrency issues and received review from Jan Kara. The changes promise substantial performance gains for RWF_DONTCACHE workloads, particularly in reducing tail latency and ensuring fair bandwidth sharing with buffered I/O. Layton requested Christian Brauner to consider these patches for v7.2.
