mm: Improve RWF_DONTCACHE Write Performance (v5)

Summary

This week, Jeff Layton posted version 5 of a patch series aimed at significantly improving write performance for RWF_DONTCACHE (Dropbehind) I/O. This is a continuation of the v4 series posted earlier in the week, incorporating feedback from Jan Kara and Jens Axboe. The series represents a performance optimization rather than a bug fix or new feature, though it addresses severe tail latency issues that effectively acted as performance bugs for workloads using RWF_DONTCACHE.

Evolution from v4 to v5

The v4 series (previously summarized) received positive reviews but included two benchmarking patches that were deemed unsuitable for mainline inclusion. In v5, Jeff Layton streamlined the series:

"I've also dropped the two patches that add the benchmarks that I was using for testing. I don't think they're appropriate for inclusion here, though we could consider cleaning them up and adding them to xfstests or something if there is interest." As stated by Jeff Layton

The primary technical change in v5 was an updated comment on filemap_dontcache_kick_writeback(), addressing Jan Kara's concern from the previous round:

"This comment is a bit confusing as in fact we write arbitrary dirty pages. It is only the amount of pages that is influenced by WB_DONTCACHE_DIRTY..." As stated by Jan Kara in the v4 discussion

Jeff Layton confirmed this adjustment:

"The main difference in this version is an updated comment over filemap_dontcache_kick_writeback(), using the verbiage suggested by Jan." As stated by Jeff Layton

Technical Arguments and Solution

The core problem addressed by this series is that the IOCB_DONTCACHE writeback path previously called filemap_flush_range() inline for every write, submitting writeback directly in the writer's context. This caused severe tail latency:

"Perf lock contention profiling shows the performance problem is not lock contention but the writeback submission work itself — walking the page tree and submitting I/O blocks the writer for milliseconds, inflating p99.9 latency from 23ms (buffered) to 93ms (dontcache)." As stated by Jeff Layton

The solution involves two key patches:

  1. Patch 1/2: Introduces a per-bdi_writeback counter (WB_DONTCACHE_DIRTY) to track dirty pages with the dropbehind flag set. This allows the writeback system to know how many DONTCACHE pages are pending without flushing all dirty pages on the BDI.

  2. Patch 2/2: Replaces the inline filemap_flush_range() call with a flusher kick that drains dirty pages in the background:

"Replace the inline filemap_flush_range() call with a flusher kick that drains dirty pages in the background. This moves writeback submission completely off the writer's hot path." As stated by Jeff Layton

The flusher uses a new WB_start_dontcache bit and writes back a number of pages proportional to the DONTCACHE dirty count, preserving I/O batching while limiting the scope of expedited writeback.

Performance Improvements

The benchmarks included in Patch 2/2 demonstrate dramatic improvements:

  • Single-stream sequential write throughput: +201% (298 MB/s → 897 MB/s)
  • Tail latency (p99): -82% (135,266 μs → 23,986 μs)
  • Tail latency (p99.9): -99.7% (8,925,479 μs → 28,443 μs)
  • Multi-writer throughput: Matches buffered I/O (4,532 MB/s vs 4,616 MB/s)
  • Peak dirty pages: -88% in 32-file concurrent writes (1.8 GB → 213 MB)

Notably, the series also resolves fairness issues between buffered and DONTCACHE writers:

"Previously the buffered writer starved the dontcache writer 2:1. With per-bdi_writeback tracking, both writers now receive equal bandwidth." As stated by Jeff Layton

NFS Client Relevance

While the core changes are in the memory management and generic filesystem layers, this optimization is highly relevant to NFS clients utilizing RWF_DONTCACHE for improved performance characteristics. The NFS client can leverage RWF_DONTCACHE writes to achieve lower latency and higher throughput when appropriate, particularly for workloads that do not require immediate data persistence in the page cache.

The series received Reviewed-by tags from both Jan Kara and Jens Axboe, indicating strong support from key maintainers. Jeff Layton requested consideration for inclusion in kernel v7.2:

"Christian, please consider these for v7.2." As stated by Jeff Layton

Conclusion

The v5 series represents a mature, well-reviewed performance enhancement for RWF_DONTCACHE writes. By moving writeback submission off the writer's hot path and introducing targeted dirty page tracking, the series eliminates severe tail latency issues and brings DONTCACHE throughput to parity with buffered I/O. With approvals from Jens Axboe and Jan Kara, the series is poised for integration into the mainline kernel.
