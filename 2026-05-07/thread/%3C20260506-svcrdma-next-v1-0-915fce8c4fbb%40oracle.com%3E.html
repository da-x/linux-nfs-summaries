svcrdma: Reduce Send completion path contention and fix OOM issues

Summary

This week, Chuck Lever submitted a two-patch series aimed at optimizing the svcrdma subsystem by reducing contention on the svcrdma_wq workqueue during the Send completion path. The discussion highlights significant performance improvements for NFS over RDMA and resolves critical Out-Of-Memory (OOM) issues observed in large-scale deployments.

Technical Arguments and Evolution

The thread begins with Chuck Lever identifying a bottleneck through profiling an 8KB NFSv3 read/write workload. He noted that approximately 4% of total CPU cycles were spent on the svcrdma_wq unbound workqueue pool spinlock. The contention arose because each Send completion queued work to release the send_ctxt, which in turn queued additional items for every write_info chunk, causing cascading lock acquisitions As detailed by Chuck Lever.

Patch 1: Inline Resource Release The first patch addresses the inner re-queueing mechanism. Lever argued that since svc_rdma_write_info_free already runs on svcrdma_wq, the extra work item adds spinlock contention without gaining parallelism. By inlining the chunk release, the patch recovers roughly 1% of CPU cycles As explained by Chuck Lever.

Patch 2: Deferring Context Release The second, more ambitious patch retires the svcrdma_wq for send completions entirely. Instead, Send completion handlers append the send_ctxt to a per-transport lock-free list (llist). The nfsd thread then drains this list in xpo_release_ctxt between RPCs. This move shifts DMA unmapping and page release out of the completion context. Lever emphasized that this is crucial when an IOMMU runs in strict mode, as each unmap synchronously invalidates the IOTLB; moving this to the nfsd thread allows batching and absorbs latency where it is harmless As described by Chuck Lever.

Key Conclusions and Validation

Mike Snitzer provided critical validation for the first patch, confirming its effectiveness in resolving OOM issues. He reported:

"You were correct: this patch alone eliminates the OOM (we tested with both 16K and then 4K read IO from 121 clients to 8 NFS servers, no measurable memory growth while testing)."

Snitzer added his Reviewed-by tag and included a Tested-by tag for Jonathan Flynn As confirmed by Mike Snitzer.

Regarding the second patch, Snitzer noted that while he could not test it at the customer site due to kernel version constraints (the baseline was 6.12-stable, while the patch builds on 7.1 changes), he expressed confidence in its design:

"I think your 2nd patch is ideal though, and will be able to pull it in to test in future..."

Summary of Impact

This series represents a significant optimization for NFS server-side RDMA performance. The first patch provides an immediate bug fix for OOM conditions under heavy load and reduces CPU overhead by eliminating unnecessary workqueue re-queuing. The second patch offers a deeper architectural improvement by removing workqueue contention entirely from the Send completion path, deferring expensive DMA unmapping operations to the nfsd thread context. Both patches are accepted with positive feedback from key stakeholders in the NFS community.
