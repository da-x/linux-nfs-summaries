ktls-utils Keyring Fix and Release Strategy

Overview

This thread continues the investigation into a regression in ktls-utils where keyring-based NFS client certificate management was broken by the introduction of dual-certificate support. This week, the discussion evolved from identifying the bug to fixing it, debating whether the feature is "production-ready," and ultimately agreeing on a maintenance release strategy for older users.

The issue is classified as a bug fix with significant implications for NFS client development regarding TLS keyring integration.

Key Technical Arguments

The Fix and Dual Certificate Support

Scott Mayhew confirmed he could reproduce the bug reported last week by Sagi Grimberg. He explained that his recent addition of dual certificate support did not intend to touch keyring code, but the interaction caused failures. He outlined the current manual process for using the .nfs keyring:

"you need to load nfs.ko first so that the .nfs keyring gets created via nfs_init_keyring()... you need to convert the cert and key to DER format... then you mount w/ '-o xprtsec=mtls,cert_serial=...,privkey_serial=...'" Scott Mayhew

Mayhew submitted a patch that fixes the immediate regression but raised questions about future-proofing dual certificate support via keyrings. He asked whether the solution should involve adding Post-Quantum (PQ) parameters to the upcall or teaching tlshd to parse multiple cert/key pairs from existing keys.

Is Keyring Support "Finished"?

A central debate emerged regarding the maturity of NFS keyring support. Chuck Lever characterized the capability as "aspirational/experimental," noting that the cert_serial and privkey_serial mount options are undocumented in nfs(5) and intended for internal use by mount.nfs, not direct administration:

"The 'cert_serial' and 'privkey_serial' mount options are not documented at all in nfs(5). They are intended to be a way for the mount.nfs command to pass key serial numbers to the kernel NFS client, not as an administrative interface. Because, yuck." Chuck Lever

Lever argued that the infrastructure needs to support network namespace-specific certificates and TPM storage before it can be considered fully robust. He initially resisted issuing a dot-release for ktls-utils, stating:

"You are the first user I know of for this capability... Yes, technically it's a regression, but it's not really a feature that is supposed to be ready for users at this stage." Chuck Lever

User Expectations and NVMe Comparisons

Sagi Grimberg pushed back, arguing that users expect existing functionality to remain stable. He compared the NFS situation to NVMe/TLS, where keyring support for PSK (Pre-Shared Keys) is considered first-class:

"What makes NVMe PSK more 'supported' than x.509? Both rely on userspace to create keys using a keyring... These are not different IMO." Sagi Grimberg

Grimberg emphasized that the breakage affected users on Ubuntu 24.04 with ktls-utils version 1.3.0, making it a real-world regression rather than just an edge case for developers building from source. He advocated for releasing the fix immediately rather than waiting for a polished mount.nfs interface:

"IMO we shouldn't hold out a fix for this until we are happy with a nicer mount.nfs interface." Sagi Grimberg

Hannes Reinecke chimed in regarding the NVMe comparison, noting that x.509 support for NVMe/TCP is currently shelved due to lack of resources:

"Sadly, this has been shelved for now. There are no takers to move things forward. So we're stuck with PSK for the time being." Hannes Reinecke

Evolution of the Discussion

  1. Triage and Fix: Scott Mayhew reproduced the issue and submitted a patch, while also raising architectural questions about dual-certificate keyring support Scott Mayhew.
  2. Debate on Maturity: Chuck Lever pushed the fix to a "fixes" branch but hesitated on releasing it in a dot-release, arguing the feature was experimental and undocumented Chuck Lever.
  3. User Advocacy: Sagi Grimberg argued that the lack of documentation shouldn't prevent fixing a regression for existing users, highlighting the impact on distribution packages like Ubuntu 24.04 Sagi Grimberg.
  4. Resolution: After further discussion, Chuck Lever audited the commit history and agreed to create a maintenance branch for an older version of ktls-utils:

"After auditing the commit history between ktls-utils-1.3.0 and 1.4.0, there are enough fixes to bundle together and release a 1.3.1 that includes the fix for the keyring-based NFS mount failure." Chuck Lever

Final Conclusions

The thread concluded with a practical resolution for the immediate bug while leaving broader architectural questions open for future work:

  1. Immediate Fix: A patch fixing the keyring regression in tlshd was accepted and pushed to a fixes branch.
  2. Maintenance Release: Chuck Lever created a ktls-utils-1.3-fixes branch to support a 1.3.1 release, addressing concerns for users on older distribution packages.
  3. Future Work: The discussion highlighted the need for better documentation of keyring-related mount options in nfs(5) and a more robust automation interface (potentially via mount.nfs) to handle certificate loading, namespace isolation, and TPM integration. Dual-certificate support via keyrings remains an area requiring further design work.

This resolution ensures that NFS clients relying on the .nfs keyring for TLS authentication can continue to function, while acknowledging that the interface is still evolving toward a more polished, production-ready state.
