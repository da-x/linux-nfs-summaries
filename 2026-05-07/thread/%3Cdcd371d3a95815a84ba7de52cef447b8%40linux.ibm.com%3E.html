NFS Server UAF in cache_check_rcu(): Multi-Architecture Confirmation and Remediation Update

Summary

NFS Server Use-After-Free in cache_check_rcu(): Multi-Architecture Confirmation and Remediation Update

Classification: Critical Bug Fix (NFS Server / SUNRPC)

This week's activity on this long-running thread focused on clarifying the scope of a persistent use-after-free (UAF) bug in the NFS server's SUNRPC cache layer and confirming that a comprehensive fix is imminent. The discussion, originally sparked by a ppc64le-specific crash report from IBM in February, expanded to reveal that the issue affects multiple architectures and comprises several distinct but related instances within the same UAF class.

Background (Brief)

The thread originated on 2026-02-19 when Misbah Anjum N reported a 100% reproducible kernel panic in cache_check_rcu() triggered by the sosreport diagnostic tool on ppc64le systems. A partial fix was applied in February, addressing one instance of this UAF class, but additional instances remained. On 2026-04-30, Misbah confirmed the bug had propagated into mainline (kernel v7.0) and shared git bisect results that landed on an unlikely x86 platform driver merge commit.

This Week's Activity

Jeff Layton: Bisect Results and Diagnostic Recommendations

On 2026-05-01, Jeff Layton responded to Misbah's follow-up, contextualizing the bisect result and suggesting further diagnostics d6701b40b8b7c143f87ecec0afb08af8a2867358.camel@kernel.org:

"The commit you landed on is a merge commit and is not likely to be the cause, particularly since that merge was for x86 drivers and you're seeing this on PPC."

Layton recommended enabling KASAN (Kernel Address Sanitizer) to gain deeper visibility into the memory corruption:

"What might be best is to run this test with KASAN enabled. That might give us a clearer picture of what object is being freed and when."

Chuck Lever: Scope Clarification and Fix Status

Chuck Lever provided the most significant update, clarifying the relationship between the February fix and the current reports 8e8847fb-0eff-46b0-97dc-fe683c706db3@app.fastmail.com:

"You didn't miss it. We responded to that report in February with a fix that you and Neil both reviewed and it is in v7.0 now."

He emphasized that the February patch was only a partial solution:

"That fix addressed one instance of this problem; there are actually several more, all in the same UAF class. I have a patch series nearly complete to address these issues."

Lever also distinguished the current crash from the earlier one:

"The issue Misbah reports here is not the same as the February issue, though it is very similar."

Crucially, Lever confirmed the bug was not architecture-specific, noting an internal report of identical stack traces on ARM64:

"We have an internal bug reporting the same stack trace on ARM64. Now that we have both a reproducer and a platform that is easily accessible it will be straightforward to confirm these issues are fully addressed before we merge the new fixes."

Key Technical Arguments and Evolution

  1. Multi-Instance UAF Class: The discussion revealed that this is not a single bug but a class of use-after-free vulnerabilities in the SUNRPC cache layer's cache_check_rcu() function. The February fix addressed one instance, but several others remain — all sharing similar root causes related to RCU lifecycle management of cache entries during /proc file reads.

  2. Cross-Architecture Impact: Initially reported on ppc64le, the bug is now confirmed to affect ARM64 as well. This broadens the operational impact and underscores that the issue is not tied to PowerPC-specific memory ordering or alignment behaviors.

  3. Remediation Readiness: Chuck Lever's statement that a patch series is "nearly complete" signals that the community is close to resolving this persistent regression. The availability of a reliable reproducer (modprobe nfsd followed by sosreport) on multiple platforms will facilitate thorough validation before merge.

  4. Bisect Limitations: Jeff Layton's observation about the bisect result highlights a common challenge in kernel debugging: when git bisect lands on a large merge commit unrelated to the subsystem under investigation, it may indicate timing coincidences rather than causal relationships. KASAN testing was recommended as a more precise diagnostic tool.

Conclusions

This week's exchange marked an important milestone in resolving this long-standing NFS server bug:

  • The bug is confirmed multi-architectural, affecting both ppc64le and ARM64, with identical stack traces observed on both platforms.
  • A comprehensive fix is imminent: Chuck Lever has a patch series "nearly complete" to address all remaining instances of this UAF class in cache_check_rcu().
  • The February fix was partial: It resolved one instance of the problem but left others unfixed, explaining why the bug persisted into mainline (kernel v7.0).
  • Testing infrastructure is in place: With reliable reproducers on multiple platforms, the new fixes can be validated thoroughly before merge.

This thread exemplifies the collaborative nature of kernel debugging: a bug reported by an IBM tester on ppc64le, partially fixed by NFS maintainers, confirmed persistent through community testing, and now approaching full resolution with cross-architecture validation. The focus remains squarely on NFS server stability and the integrity of the SUNRPC cache layer's RCU-based lifetime management.
