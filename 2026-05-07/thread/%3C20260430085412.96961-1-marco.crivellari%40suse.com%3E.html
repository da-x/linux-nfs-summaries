xprtrdma: Workqueue optimization patch accepted pending improved commit message

Summary

Thread Summary: xprtrdma Workqueue Optimization Patch Moves to v2

This thread, which began last week as an RFC, concerns a minor optimization in the NFS/RDMA transport layer (xprtrdma). The patch swaps the use of system_long_wq for the newer, unbound system_dfl_long_wq when queuing long delayed work items. This allows the kernel scheduler to make better placement decisions for power and performance, rather than binding the work to a random CPU where the timer happened to fire.

Evolution of the Discussion

Last week's discussion focused heavily on clarifying the motivation behind the change. Maintainer Chuck Lever initially found the commit message ambiguous, questioning whether the patch addressed a functional bug or merely an optimization. Workqueue expert Frederic Weisbecker clarified that the change was strictly an optimization:

"It's not a bug, it's an optimization power-wise and performance-wise... Long works have no reason to stick to a single CPU. If they are converted to be unbound, the scheduler can move them to relevant targets to optimize performances and power consumption."

Chuck Lever acknowledged this explanation last week, stating:

"The light dawns (for me). That's what I'd like to see in the commit message. I don't have any technical objections to the code change."

Final Conclusions

This week, Marco Crivellari confirmed that he would incorporate Chuck Lever's feedback into the commit message and submit version 2 of the patch here:

"Thanks for all your feedback. I will improve the commit log with your suggestion and then send v2."

Key Takeaways for NFS Client Development

  1. Classification: This is an optimization, not a bug fix. It aligns xprtrdma with modern kernel workqueue best practices that favor unbound workqueues (system_dfl_long_wq) for long-running tasks where CPU locality is irrelevant.
  2. Status: The technical objections have been resolved. The patch is approved in principle, pending an improved commit message in v2 to clearly articulate the power and performance rationale.
  3. Broader Context: This change reflects a kernel-wide trend of phasing out system_long_wq for use cases where scheduler-driven task placement can yield better efficiency.
