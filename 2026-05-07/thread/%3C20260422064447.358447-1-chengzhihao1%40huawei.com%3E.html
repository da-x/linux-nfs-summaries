NFSv4 State Recovery Deadlock: Ping Without Resolution

Type: Bug fix (NFS client state recovery)

This Week's Activity

This week saw minimal activity on this long-running thread. The sole message was a friendly ping from Zhihao Cheng on May 6, aimed at drawing attention back to the unresolved deadlock issue. The message quoted his earlier finding that maintainer Trond Myklebust's suggested fix had not resolved the problem:

"I tried with your suggestion, and the problem still happens"

No new technical proposals or responses from Myklebust were posted this week.

Background (from prior weeks)

As summarized in the April 23 summary, Zhihao Cheng submitted a patch addressing a critical NFSv4 client deadlock that occurs when an NFS server restarts and the client enters state recovery. The bug, reported via Kernel Bugzilla 221399, causes the client to enter an infinite loop during NFS4CLNT_RECLAIM_NOGRACE processing when the server repeatedly returns NFS4ERR_GRACE.

Cheng's original fix attempted to set NFS4CLNT_RECLAIM_REBOOT in nfs4_reclaim_lease, but Myklebust pushed back, arguing:

"This will cause the client to try to do reboot recovery in a situation where it isn't allowed to do so by the spec. We should never be setting NFS4CLNT_RECLAIM_REBOOT if NFS4CLNT_RECLAIM_NOGRACE is already set."

Myklebust proposed instead calling nfs4_state_end_reclaim_reboot() immediately when NFS4CLNT_RECLAIM_NOGRACE is set — but Cheng confirmed this did not resolve the deadlock either.

Status: Unresolved

The core tension remains between NFSv4 specification restrictions on reclaim operations during the NOGRACE state and the practical need to ensure RECLAIM_COMPLETE is sent so the server can properly process subsequent nograce recovery requests. No new patch iteration or resolution has emerged this week. The issue awaits a revised approach from the developers.
