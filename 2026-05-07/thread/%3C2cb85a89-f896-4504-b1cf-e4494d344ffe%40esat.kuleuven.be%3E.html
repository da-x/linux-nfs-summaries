Confirmation of NFS4ERR_SEQ_MISORDERED fix deployment

Summary

Resolution of NFS4ERR_SEQ_MISORDERED Performance Regression

Background

Last week, this thread saw extensive analysis of a critical performance regression affecting Rocky 8 clients connecting to RHEL10 servers. The issue manifested as severe slowdowns during operations such as git cloning, accompanied by frequent NFS4ERR_SEQ_MISORDERED errors in packet captures. Olga Kornievskaia identified the root cause as a bug in the server's replay cache logic (introduced by commit 1cff14b7fc7f31363c39d0269563ce75c714f7ae), where SEQUENCE replies were encoded before reply fields were correctly populated, leading to incorrect maxslots values. This caused clients to erroneously believe their slot tables had shrunk, discarding sequence state for higher slots and triggering misorder errors when those slots were reused.

This Week's Activity

The only message this week is a brief update from Rik Theys confirming the deployment of the fix:

"We're now running 7.0.3 on the server. We will monitor if the performance issue returns." Rik Theys

He also extended his gratitude to the community:

"Thanks everybody for your time and effort." Rik Theys

Conclusion

This thread represents a successful example of collaborative bug diagnosis on the Linux NFS mailing list. The issue was:

  • Type: Bug fix (server-side SEQUENCE replay logic error).
  • Root Cause: Incorrect maxslots value in SEQUENCE replay responses, causing client slot table state corruption.
  • Resolution: Fixed in upstream Linux and RHEL10.2/CentOS kernels 6.12.0-201+. The reporter has upgraded to kernel 7.0.3 and is monitoring for recurrence.

The thread is now effectively closed, pending confirmation from the reporter that no further issues arise.
