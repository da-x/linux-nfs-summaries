Discussion on Preventing ENOSPC/EDQUOT Writeback Errors in NFS

Summary

Preventing Silent Data Loss from ENOSPC/EDQUOT on Network Filesystems

This week, a significant discussion emerged regarding the handling of writeback errors—specifically ENOSPC (No Space Left on Device) and EDQUOT (Disk Quota Exceeded)—on network filesystems like NFS. The thread highlights the inherent risks of buffered I/O in distributed storage environments and explores potential mitigation strategies.

The Problem: Silent Data Loss via Buffered Writes

Piyush Sachdeva initiated the discussion by outlining a critical vulnerability in how network filesystems handle buffered writes As described by Piyush.

The core issue is that when an application performs a write() syscall, data is copied into the page cache and success is returned immediately. The actual upload to the server occurs later during writeback. If the server runs out of space at that point:

  1. The write fails with ENOSPC.
  2. The folio's writeback flag is cleared, marking the page as "clean."
  3. Under memory pressure, the VM can reclaim these clean pages, permanently losing data that the application believes was successfully written.
  4. Meanwhile, i_size has already been updated, so stat() shows a file size inclusive of data that was never persisted.

"A user or application can keep issuing writes to an fd well beyond the available space, since buffered writes return success as soon as data is copied to the page cache. A significant amount of data, exceeding the available quota can accumulate before fsync() is called, at which point critical data loss is nearly certain."

Sachdeva noted that while errors are technically observable via fsync() or close(), many applications do not check these return values, leading to silent data corruption.

Proposed Solutions

Sachdeva proposed a multi-pronged approach to prevent this issue:

  1. Pre-allocation: Use fallocate()-style pre-allocation on the write path to guarantee server-side space before accepting data into the page cache.
  2. Cached statfs() gating: To avoid the performance penalty of per-write round-trips, use cached statfs() output to trigger pre-allocation only when free space drops below a threshold (e.g., 20%).
  3. Cache synchronization: Handle refresh and synchronization of cached statfs() data separately to avoid staleness issues.

NFS Community Response: Jeff Layton's Perspective

Jeff Layton, a key NFS maintainer, responded with a pragmatic assessment of the situation As explained by Jeff.

Layton emphasized that this is a fundamental issue with buffered writes and delayed writeback:

"Either you flush the data to stable storage now, or you have to do it later. If you do it later, then it can still fail for all sort of reasons."

He pointed out that while NFSv4.2 includes an ALLOCATE operation (defined in RFC 7862), using it proactively doesn't solve the problem because:

"By the time we're issuing RPCs to the server, the client application has already finished its writes and moved on."

Conclusion: The Role of Applications

The discussion concluded that there is no perfect kernel-side solution that eliminates this risk without significant performance overhead. The recommended approach for applications seeking to avoid ENOSPC/EDQUOT errors is:

"For applications that want to avoid ENOSPC/EDQUOT, the best thing they could do is call fallocate() themselves to ensure that the space exists. With a sufficiently recent NFS client and server, that should DTRT."

This reinforces the POSIX model where applications responsible for data integrity must explicitly synchronize their state with stable storage. While the kernel can provide tools like fallocate(), the burden of using them correctly remains with the application developer.

Key Takeaways for NFS Client Development

  • Bug Fix Context: This is not a bug fix but a discussion on architectural limitations of buffered I/O in network filesystems.
  • No Immediate Kernel Changes: No new patches were proposed; instead, the focus was on educating developers about existing mechanisms.
  • Application Responsibility: The consensus is that applications must proactively manage space allocation if they cannot tolerate silent data loss.
  • Future Considerations: While pre-allocation via fallocate() is viable, automating this in the kernel would require careful design to balance performance and reliability.
