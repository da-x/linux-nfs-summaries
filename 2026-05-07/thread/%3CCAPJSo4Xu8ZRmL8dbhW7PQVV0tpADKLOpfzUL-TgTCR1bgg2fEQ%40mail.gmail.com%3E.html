NFSv4.1 Client Hang in nfs4_drain_slot_tbl — Environment Details Provided for Windows Server Reproduction

Summary

NFSv4.1 Client Hang in nfs4_drain_slot_tbl Against Windows NFS Server

Summary

Bug Report Follow-Up: Environment Details Provided

This thread concerns a bug fix investigation into an NFSv4.1 client-side hang occurring in nfs4_drain_slot_tbl under concurrent workload when the Linux NFS client is connected to a Windows NFS server. The discussion is currently in the diagnostic and information-gathering phase; no code patches have been proposed yet.

Prior Context (Bridge from Earlier Activity)

Earlier this week, 郭玲兴 reported a bug in which the Linux NFSv4.1 client hangs in nfs4_drain_slot_tbl — a function responsible for draining the slot table during session recovery or teardown — when operating against a Windows NFS server under concurrent workload. The mount options in use were:

"Mount options: vers=4.1,soft,proto=tcp,timeo=60,retrans=10"

Lionel Cons responded the same day, requesting additional diagnostic details to aid in reproducing and analyzing the issue:

"Which version of WindowsServer do you use, e.g what does the 'ver' command in cmd.exe output? How did you set up the user accounts, and which authentication (AUTH_SYS, GSS, ...) do you use?"

He also asked about client-side hardware configuration:

"Which CPU architecture do you use? How much memory do you have on the Linux NFS client?"

This Week's Activity

On May 7, 郭玲兴 provided a detailed response with the requested environment specifics:

  1. Windows Server version: Microsoft Windows Server 2022, Version 10.0.20348.587
  2. User accounts: No mapping mechanism is configured — no AD, LDAP, or passwd mapping. Unmapped users are handled by the default "Everyone" account.
  3. Authentication: sec=sys (AUTH_SYS), as reported by nfsstat -m
  4. CPU architecture: Both Linux clients and Windows server are x86_64
  5. Memory: Each Linux client VM has 16GB RAM

These details narrow the reproduction environment significantly: a standard x86_64 setup with basic AUTH_SYS authentication and no user mapping, running against a recent Windows Server 2022 NFS implementation. The use of soft mount semantics combined with concurrent workload may interact with slot table draining in ways that expose edge cases in session management — particularly when the server's behavior diverges from what the Linux client expects per the NFSv4.1 protocol.

Status and Outlook

As of the end of this week, the discussion remains in the information-gathering phase. No patches or proposed fixes have been submitted. The next logical step would be for Lionel Cons or other developers to attempt reproduction using the provided configuration details and investigate whether the hang stems from a client-side race condition in nfs4_drain_slot_tbl, a server-side protocol deviation by the Windows NFS implementation, or an interaction between the two.

This bug is notable for highlighting interoperability challenges between Linux NFSv4.1 clients and non-Linux (Windows) servers — a recurring theme in NFS development where edge cases in session management and slot table handling can surface under specific workload patterns.
