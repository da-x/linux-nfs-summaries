mm: Improve RWF_DONTCACHE Write Performance via Flush Kicking

Summary

This week, Jeff Layton posted version 4 of a patch series aimed at significantly improving write performance for RWF_DONTCACHE (Dropbehind) I/O. The series addresses critical latency issues in the DONTCACHE write path and introduces new benchmarking tools relevant to NFS development.

Problem Statement

The previous implementation of IOCB_DONTCACHE called filemap_flush_range() inline for every write, submitting writeback directly in the writer's context. As Jeff Layton explained, profiling revealed that the bottleneck was not lock contention but the overhead of the writeback submission itself:

"Perf lock contention profiling shows the performance problem is not lock contention but the writeback submission work itself — walking the page tree and submitting I/O blocks the writer for milliseconds, inflating p99.9 latency from 23ms (buffered) to 93ms (dontcache)." As stated by Jeff Layton

Proposed Solution

The v4 series implements a scheme suggested by Jan Kara and Christoph Hellwig. Instead of inline writeback, the writer now kicks the flusher thread to handle writeback in the background. To avoid flushing all dirty pages on the BDI (which would be inefficient), the series introduces a per-bdi_writeback counter (WB_DONTCACHE_DIRTY) to track DONTCACHE dirty pages.

"Replace the inline filemap_flush_range() call with a flusher kick that drains dirty pages in the background. This moves writeback submission completely off the writer's hot path." As stated by Jeff Layton

The flusher is triggered to write back an amount of data proportional to the DONTCACHE writes, though it does not target specific inodes or pages. This approach preserves I/O batching while keeping dirty page counts manageable.

Performance Improvements

The benchmarks included in the patch description demonstrate substantial gains:

  • Single-stream sequential write throughput increased by 201% (298 MB/s to 897 MB/s).
  • Tail latency (p99.9) collapsed by 99.7% (from ~8.9 seconds to ~28 milliseconds).
  • Multi-writer throughput now matches buffered I/O performance.
  • Peak dirty pages were reduced significantly, dropping from 1.8 GB to 213 MB in a 32-file concurrent write test.

NFS Client Relevance

While the core changes are in the memory management and generic filesystem layers, this optimization is highly relevant to NFS clients utilizing RWF_DONTCACHE for improved performance characteristics. Additionally, Patch 3 introduces an NFS server benchmark suite (nfsd-io-bench) to test NFSD I/O mode performance using fio with the libnfs backend. This tool allows developers to evaluate buffered, dontcache, and direct I/O modes via NFSD debugfs controls, providing valuable infrastructure for future NFS client/server tuning.

Review and Feedback

The series received positive feedback from key maintainers:

  • Jens Axboe approved the approach: "I like this, this is the better way to kick off the writeback." As stated by Jens Axboe
  • Jan Kara also provided a Reviewed-by tag but noted a minor clarification needed in the code comments:

"This comment is a bit confusing as in fact we write arbitrary dirty pages. It is only the amount of pages that is influenced by WB_DONTCACHE_DIRTY... I'd rephrase the last sentence like: We queue writeback for the inode's wb for as many pages as there are dontcache pages but we don't restrict writeback to dontcache pages only." As stated by Jan Kara

Jeff Layton acknowledged the suggestion and agreed to update the comments. As confirmed by Jeff Layton

Conclusion

The v4 series represents a significant performance enhancement for RWF_DONTCACHE writes, resolving severe tail latency issues and improving throughput to parity with buffered I/O. With approvals from Jens Axboe and Jan Kara, the series is poised for integration into the mainline kernel, pending minor comment adjustments. The inclusion of new benchmarking tools further supports ongoing NFS client and server development efforts.
