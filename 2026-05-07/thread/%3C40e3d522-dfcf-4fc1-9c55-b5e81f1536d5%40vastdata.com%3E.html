RFC: Use-After-Free Bug in NFS mTLS Connect Path

Overview

This week, Michael Nemanov of Vast Data submitted an RFC PATCH reporting a critical use-after-free (UAF) bug in the NFS client's mTLS (mutual TLS) connection establishment path. The discussion is classified as a bug fix investigation, with no replies received during this week's window.

This report builds on prior activity: in February 2026, Debian maintainer Salvatore Bonaccorso reported a kernel panic when repeatedly attempting to mount an NFSv4 share with mismatched mTLS certificates, resulting in a NULL pointer dereference in rcu_do_batch (thread). Nemanov's submission provides deeper diagnostic insight into the underlying mechanism causing such crashes.

Key Technical Arguments

The Bug Mechanism

Nemanov identified a race condition where a raw, unrefcounted pointer to an rpc_clnt structure is stored during xs_connect() and subsequently accessed by a delayed workqueue item after the client has been freed. The issue manifests specifically when:

  1. An NFS mount uses incorrect credentials (a valid client certificate that does not match the server's requirements) during TLS setup.
  2. The TLS handshake fails, triggering client teardown via rpc_shutdown_client → rpc_free_client.
  3. Meanwhile, a delayed work item scheduled by xs_connect() still holds a pointer to the now-freed client structure.

"The NFS-over-TLS implementation seems to have a use-after-free bug where a raw unrefcounted pointer to an rpc_clnt is stored in xs_connect() and accessed by a delayed workqueue item after the client has been freed." Michael Nemanov

Diagnostic Evidence

Nemanov provided extensive kernel log traces from vmcore-dmesg showing the lifecycle of the RPC client from creation to use-after-free. The critical sequence is:

[   39.065470] @ rpc_shutdown_client: 00000000f636d223
[   39.065580] @ rpc_free_client: put_cred 00000000f636d223    << Client being destroyed
...
[   42.033267] @ xs_tcp_tls_setup_socket: Using clnt 00000000f636d223  << Client used AFTER free
...
[   42.164197] ------------[ cut here ]------------
[   42.165779] refcount_t: underflow; use-after-free.

The three-second gap between the client being freed and the delayed work accessing it is attributed to an msleep(100) added for reproduction purposes, though Nemanov notes this timing is not guaranteed.

Reproduction Methodology

A detailed reproduction script was provided, involving repeated mount attempts with mTLS:

for i in {1..1000}; do
    sudo mount -o vers=4.2,proto=tcp,xprtsec=mtls remote_addr:/opt/export /mnt/export
    sleep 5
done

Dynamic debug traces were enabled for net/sunrpc/clnt.c and net/sunrpc/xprtsock.c to capture the lifecycle events.

Open Questions

Nemanov explicitly acknowledged uncertainty about the root cause:

"I don't understand if the use-after-free is the root cause and must be fixed or a symptom of a problem elsewhere." Michael Nemanov

He also noted puzzling behavior regarding the timing:

"I am also not sure what causes the bug to manifest. It might be related to the timing of server's FIN (sk_state=8 in the log) and the flags it changes." Michael Nemanov

Evolution of the Discussion

This thread consists of a single message this week — the initial RFC submission. No replies were received from NFS maintainers or other developers during the reporting window. The submission is marked as "RFC" (Request for Comments), indicating that Nemanov is seeking guidance on whether the observed use-after-free represents the fundamental problem or merely a symptom of a deeper architectural issue in the mTLS connection handling code.

Final Conclusions

As of this week, the discussion remains in its initial investigative phase:

  1. Bug Identified: A use-after-free condition exists in the NFS client's mTLS connect path when TLS handshakes fail due to credential mismatches.
  2. Impact: The bug can cause kernel crashes (refcount_t: underflow; use-after-free) and has been linked to prior reports of NULL pointer dereferences in RCU cleanup paths during repeated failed mTLS mounts.
  3. Status: No fix has been proposed yet. Nemanov's submission includes diagnostic patches with debug traces but no corrective code, seeking community input on the proper remediation strategy.

This bug is particularly significant for NFS client development as it affects the relatively new NFS-over-TLS transport security feature (xprtsec=mtls), which is gaining adoption in enterprise environments requiring encrypted and authenticated NFS connections. The interaction between delayed workqueue scheduling and RPC client lifecycle management represents a subtle but dangerous race condition that could affect production deployments using mTLS.
