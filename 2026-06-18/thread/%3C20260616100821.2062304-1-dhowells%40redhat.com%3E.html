netfs bvecq v4: 30-Patch Series Rebased to v7.1, but Hellwig balks at Merge-Window Timing

Week ending 2026-06-18

Overview

On June 16, David Howells posted version 4 of his long-running series to replace folio_queue, rolling_buffer, and ITER_FOLIOQ with a segmented chain of bio_vec[] arrays (bvecq) in netfslib — the shared I/O infrastructure under NFS, AFS, CIFS, 9P, and Ceph. The 30-patch series touches 69 files with ~4,937 insertions and ~3,640 deletions, and is addressed to Christian Brauner (VFS maintainer) with a direct request:

"Could you add these patches to the VFS tree for next?" — David Howells

This is the fourth iteration of work that began as a 17-patch RFC in late March, was formally submitted as a 26-patch series on March 26 (with reviews from Paulo Alcantara and integration conflict reports from Stefan Metzmacher in early April), trimmed to 21 patches in v2 (May 18), expanded to 22 patches in v3 (June 8, rebased to -rc7), and now arrives as a 30-patch series rebased onto v7.1.

The series is classified as a major feature/refactoring with embedded bug fixes. While the NFS client itself is not directly modified beyond fscache integration updates in fs/nfs/fscache.c, the underlying netfslib changes will affect all network filesystems leveraging this infrastructure for buffered and direct I/O operations.

Changes from v3 to v4

The cover letter documents an extensive list of bug fixes, primarily reported by the Sashiko static analysis tool:

"ver #4)

  • Fixed a number of bugs reported by Sashiko[3].
    • Added a patch to fix an underflow in iov_iter_extract_xarray_pages().
    • Added a patch to fix alloc failure in iov_iter_extract_bvec_pages().
    • Added a patch to remove an unused var in kunit code.
    • Added a patch to fix the folio offset in extract_xarray_to_sg().
    • Added a patch to fix the exclusion over writeback to make it cover collection too.
    • Fixed double fput() in cachefiles.
    • ... [~40 additional fixes]
  • Rebased on v7.1." — David Howells

Key new patches in v4 include:

  1. Write-streaming/fscache race fix (Patch 01/30): A correctness bug reported by Marc Dionne that triggers a warning from the generic/464 xfstest. The fix changes the condition for suppressing write-streaming from checking whether the fscache cookie is "enabled" to checking whether FSCACHE_COOKIE_IS_CACHING is set:

    "Unfortunately, the test netfs_perform_write() uses isn't correct because it doesn't take into account the fact that the object lookup is asynchronous and farmed off to a work queue, so there's a short window in which the cache is doing a lookup but the test fails because the answer is undefined." — David Howells

    "Fix this by changing the condition to whether FSCACHE_COOKIE_IS_CACHING is set on a cookie rather than whether the cookie is marked enabled." — David Howells

    This is significant for NFS clients using fscache (e.g., with the cachefiles daemon), as it prevents a race condition where partial folio writes could be issued to the cache without proper DIO alignment during the async object lookup window.

  2. Cachefiles double fput fix (Patch 02/30): A one-line fix for a double fput() in error handling in cachefiles_create_tmpfile().

  3. iov_iter underflow fix (Patch 03/30): Fixes a potential underflow in iov_iter_extract_xarray_pages() when no pages are extracted due to a hole in the xarray:

    "In iov_iter_extract_xarray_pages(), if no pages are extracted because there's a hole (or something otherwise unextractable) in the xarray, then the calculation of maxsize at the end can go wrong if the starting offset is not zero." — David Howells

  4. iov_iter alloc failure check (Patch 04/30): Fixes a missing allocation failure check in iov_iter_extract_bvec_pages().

  5. Scatterlist offset fix (Patch 06/30): Fixes the calculation of the offset in the folio being extracted in extract_xarray_to_sg().

  6. Writeback lock asynchronicity (Patch 07/30): Replaces the wb_lock mutex with a bit flag and a list of lock waiters so that the lock can be dropped in the collector thread after collection is complete:

    "The netfs_inode::wb_lock mutex is used to prevent multiple simultaneous writebacks from fighting each other (a writeback thread will write multiple discontiguous regions within the same request). The mutex, however, only serialises the issuing of subrequests; it doesn't serialise the collection of results, and, in particular, the updating of file size information and fscache populatedness data." — David Howells

  7. Cachefiles content tracking (Patch 09/30): A significant performance improvement for NFS clients using fscache. The patch introduces CACHEFILES_CONTENT_ALL to avoid relying on the backing filesystem's storage map (SEEK_DATA/HOLE) for the most common case of contiguous, progressively-written files:

    "The most common write case, in which the application does { open(O_TRUNC); write(); write(); ... write(); close(); } where each write follows directly on from the previous and leaves no gaps in the file is reasonably easy to detect and can be noted in the primary xattr as CACHEFILES_CONTENT_ALL." — David Howells

    "In this specific case, given that it is known that there are no holes in the file, there's no need to call SEEK_DATA/HOLE or use any other mechanism to track the contents. That speeds things up enormously." — David Howells

    This eliminates two seek operations per cache read subrequest in the common case, a substantial performance win for NFS clients using fscache.

Architectural Changes: The bvecq Model

The core of the series introduces struct bvecq, a segmented chain of bio_vec[] arrays that replaces the monolithic folio_queue. Howells explains the design rationale:

"The kernel file I/O subsystem seems to be moving towards consolidating on the use of bio_vec arrays, so embrace this by moving netfslib to keep track of its buffers for buffered I/O in bio_vec[] form." — David Howells

"Netfslib already uses a bio_vec[] to handle unbuffered/DIO, so the number of different buffering schemes used can be reduced to just a single one." — David Howells

"Always send an entire filesystem RPC request message to a TCP socket with single kernel_sendmsg() call as this is faster, more efficient and doesn't require the use of corking as it puts the entire transmission loop inside of a single tcp_sendmsg()." — David Howells

The bvecq structure supports:

  • Linked segments (next/prev) in a NULL-terminated linear list, enabling arbitrary gluing of protocol headers/trailers
  • File position tracking (fpos, discontig) for sparse I/O patterns (relevant to Ceph)
  • Reference counting for safe buffer slice sharing between subrequests
  • Memory type flags (BVECQ_MEM_EXTERNAL, BVECQ_MEM_PAGECACHE, BVECQ_MEM_GUP, BVECQ_MEM_ALLOCED) controlling disposal semantics

A new iterator type ITER_BVECQ is added to walk these chains, intended to replace ITER_FOLIOQ (and eventually ITER_XARRAY).

"This allows an indefinite quantity of elements to be handled and allows things like network filesystems and crypto drivers to glue bits on the ends without having to reallocate the array." — David Howells

Buffer Management: Three-Cursor Model

The series introduces a three-cursor model for buffer tracking in netfs_io_request:

"Buffer tracking is managed with three cursors: The load_cursor, at which new folios are added as we go; the dispatch_cursor, at which new subrequests' buffers start when they're created; and the collect_cursor, the point at which folios are unlocked." — David Howells

The final patch (29/30) merges the ->prepare_read()/->issue_read() (and write variants) into a single callback, fundamentally changing how filesystems interact with netfslib:

"netfs now accumulates buffers and attaches them to each stream when they become valid for that stream, then flushes the stream when a limit or a boundary is hit. The issuing code in netfs then loops around creating and issuing subrequests without calling a separate prepare stage." — David Howells

"The filesystem (or cache) then gets to take a slice of the master bvec chain as its I/O buffer for each subrequest, including discontiguities if it can support a sparse/vectored RPC (as Ceph can)." — David Howells

CIFS and AFS Integration

The series updates both CIFS and AFS to use bvecq:

  • AFS: Directory content is now held in a bvecq rather than a folio_queue Patch 18/30
  • CIFS: Encryption buffering switches to bvecq Patch 19/30
  • SMB Direct RDMA: Gains ITER_BVECQ support and loses ITER_FOLIOQ support Patches 20/30, 22/30

Notably, the smbdirect patches now carry Acked-by: Stefan Metzmacher, indicating that the integration conflicts raised in April have been resolved.

Performance and Correctness Improvements

Several patches address performance and correctness:

  • Bulk readahead loading Patch 12/30: All VM-provided folios are loaded into the queue up front in a single RCU read lock section, rather than piecemeal. "This simplifies the buffer handling later and isn't noticeably slower as the xarray doesn't need to be modified and the folios are all already pre-locked."

  • Progress reporting threshold Patch 28/30: Sets a minimum trigger of 256KiB for waking the collector thread, preventing excessive wakeups with small folios. Also fixes the base point calculation: "fix the base to be the stream collection point, not the point at which the collector has cleaned up to (which is currently 0 until something has been collected)."

  • Over-read detection Patch 27/30: Adds a check in read subrequest termination to detect more data being read than was requested, with a new tracepoint for debugging.

Future Work Announced

Howells outlines two additional work items not included in this branch:

"(1) Make it so that a filesystem can be given a copy of a subchain which it can then tack header and trailer protocol elements upon to form a single message (I have this working for cifs) and even join copies together with intervening protocol elements to form compounds."

"(2) Make it so that a filesystem can 'splice' out the contents of the TCP receive queue into a bvecq chain. This allows the socket lock to be dropped much more quickly and the copying of data read to the destination buffers to happen without the lock. I have this working for cifs too."

Discussion and Reception

Christoph Hellwig's Objection

The only substantive reply in this week's window came from Christoph Hellwig, who raised concerns about both the timing and the review status of the series:

"Really? Not only are we in the merge window, but this is gigantic unreviewable series, which consequently has none of the relevant reviews." — Christoph Hellwig

Hellwig went on to suggest a different approach:

"Please try to work like everyone else and split out useful parts. E.g. if your new iter type is useful there must be smaller standalone candidates for it that can explain the use. Having to wade through all of netfs to try to understand it is not really going to fly." — Christoph Hellwig

This is a significant obstacle for Howells, as Hellwig is the block maintainer and has previously been involved in reviewing aspects of this series (e.g., the FIEMAP controversy in March, the kmap_local_bvec() naming in v3). The objection to the merge-window timing is particularly pointed, as the series was posted on June 16, which falls within the typical Linux kernel merge window period.

ChenXiaoSong's Observation

A minor observation came from ChenXiaoSong, who noted that Patch 30/30 ("CHANGES") appears to be missing its subject and commit message:

"Is this patch missing the subject and commit message?" — ChenXiaoSong

This is a trivial issue, but it highlights the fact that the series has not yet undergone thorough review by the community.

Resolution Status

As of this week's window, the series faces a significant hurdle: Hellwig's objection to the merge-window timing and the lack of relevant reviews. The prior round of reviews from Paulo Alcantara (Reviewed-by tags on core patches in v2/v3) and the resolution of Stefan Metzmacher's integration concerns (evidenced by his Acked-by tags on the smbdirect patches in this v4) suggest the series is technically ready, but the process objection may delay its inclusion.

For NFS client developers, the key impacts are: improved fscache performance via CACHEFILES_CONTENT_ALL, a fixed race condition in write-streaming with fscache, and a unified buffer management model that will simplify future protocol-level optimizations (single-sendmsg RPC transmission, socket-lock-free receive splicing). However, the series' fate now hinges on whether Howells can address Hellwig's concerns about review and timing.
