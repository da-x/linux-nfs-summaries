Summary

Shelton probes whether CPU context switches explain NFSv4.2's higher I/O latency vs iSCSI and P9FS

Bridge from prior week

Last week (ending 2026-06-11), Dan Shelton opened this thread on linux-nfs by cross-posting a FreeBSD-hackers discussion in which Bakul Shah had attributed 9P's lower latency to its lack of caching:

"p9fs doesn't cache but nfs does, so anything cached is served much faster."

Shelton then asked the Linux community to put numbers on the comparison:

"How is the situation on Linux? How is read/write latency NFSv4.2 compared to iSCSI and P9FS?"

No kernel developers had replied as of that week's close.

This week's activity (2026-06-12 → 2026-06-18)

The only in-window message is a self-reply from Shelton on 2026-06-12, in which he introduces a new technical hypothesis for the latency gap:

"Colleague of mine said Linux NFS is much worse, because of multiple CPU context switch for each NFS write to disk, NFS read from disk. Is that accurate?"

This shifts the question's framing from a purely architectural comparison (caching vs. no-caching) toward a more concrete kernel-internal mechanism: the number of thread wakeups and scheduler transitions involved in servicing a single NFS I/O request. In the Linux NFS client, a write path can involve the calling process, the NFS page-flush workqueue, the RPC tasklet/softirq context, and (for RDMA or TCP) the network stack's softirq — each potentially landing on a different CPU and incurring a context switch. By contrast, an iSCSI block I/O may complete entirely within a single softirq or kworker context, and 9P (especially in its simpler configurations) can round-trip with fewer intermediate kernel threads. Shelton is asking whether this multi-context overhead is the dominant contributor to the observed latency delta.

Nature of the discussion

This remains a performance/behavior question, not a bug report, patch submission, or protocol change. No code changes, no client-side fixes, and no new features are under discussion. The thread is an open call for maintainers (Trond Myklebust, Anna Schumaker, or others on the NFS client side) to either confirm or refute the context-switch hypothesis with measurement data or architectural explanation.

Status

  • In-window messages: 1 (Shelton's follow-up question).
  • Developer responses: None within this reporting window.
  • The thread remains open and unanswered from the kernel-devel side as of 2026-06-18.

Key technical points raised

  1. Caching asymmetry (prior week): NFS maintains a client-side page cache with delegation/lock state management; 9P in its default configuration does not, so "cold" reads on 9P are comparable to NFS misses but "warm" reads on NFS should be faster — yet Shelton's measurements show the opposite.
  2. Context-switch overhead (this week): The hypothesis that each NFS I/O traverses multiple kernel threads (process → workqueue → softirq), incurring scheduler latency that block-level protocols avoid. If accurate, this would point to a structural cost in the Linux NFS client's I/O path rather than a tunable parameter.

Bottom line

The thread is still in its question-asking phase. Shelton has now articulated two competing explanations for why NFSv4.2 read/write latency appears higher than iSCSI and P9FS on Linux — the caching architecture (from FreeBSD) and multi-CPU context-switch overhead (from a colleague). Neither has been addressed by a kernel developer within this reporting window. The discussion will likely resolve once a maintainer engages with the specific measurement methodology and confirms which architectural factors dominate the observed latency numbers.
