lockd: fix swapped arguments in nlmsvc_match_ip()

Summary

lockd: Fix Swapped Arguments in nlmsvc_match_ip() — A Long-Silent Bug in Unlock-by-IP

Type: Bug fix (NFS server / lockd)

A one-line bug fix from Synology's Oscar Ou landed quickly this week, correcting a subtle argument-swap defect in the NFS lock daemon that had rendered the /proc/fs/nfsd/unlock_ip interface effectively non-functional since its introduction.

The Bug

Oscar Ou submitted the patch on Wednesday, June 17, explaining the root cause in detail:

"nlmsvc_match_ip() has had these two arguments reversed ever since the unlock-by-IP feature was introduced in commit 4373ea84c84d ('lockd: unlock lockd locks associated with a given server ip')"

The issue is one of callback-convention confusion. When an administrator triggers a bulk unlock by IP via /proc/fs/nfsd/unlock_ip, the code path flows through nlmsvc_unlock_all_by_ip() → nlm_traverse_files(server_addr, nlmsvc_match_ip, NULL). The traversal machinery then invokes the match callback with the convention that arg1 is the real nlm_host (the lock owner) and arg2 is the caller-supplied reference value (here, the server sockaddr). Every other match callback in the file — nlmsvc_mark_host(), nlmsvc_same_host(), nlmsvc_is_client() — follows this convention.

But nlmsvc_match_ip() had it backwards:

"Here @host is actually the server sockaddr, so nlm_srcaddr(host) dereferences a struct sockaddr as a struct nlm_host and reads garbage at the offset of h_srcaddr; meanwhile @datap is actually the lock owner's nlm_host but is compared as a sockaddr. As a result the comparison practically never matches and locks are not released for the requested IP."

In other words, the function was dereferencing a struct sockaddr as if it were a struct nlm_host, reading out-of-bounds garbage, and comparing it against the actual lock owner's host structure cast to a sockaddr. The comparison essentially never succeeded, meaning locks were silently never released for the requested IP — a functional failure rather than a crash, which likely explains why it went unnoticed.

The Fix

The fix is a single-line swap of the two arguments in rpc_cmp_addr():

- return rpc_cmp_addr(nlm_srcaddr(host), datap);
+ return rpc_cmp_addr(nlm_srcaddr(datap), (struct sockaddr *)host);

This correctly compares the lock owner's source address (datap, which is actually the nlm_host) against the requested server address (host, which is the sockaddr passed down as opaque data).

Resolution

NFS maintainer Chuck Lever picked up the patch later the same day:

"Applied to nfsd-testing, thanks!"

The fix was committed as 80e05cc8a30aec76f4457a9c163b222e9ff5a671 in the nfsd-testing tree. The same-day turnaround reflects how straightforward and well-scoped the fix is — a classic case of a bug that's easy to spot once you understand the callback convention, but easy to miss in code review because the types involved (struct sockaddr * vs struct nlm_host *) are both opaque pointers at the call site.

Context

This is a server-side lockd fix rather than a client change, but it matters for NFS administrators who rely on /proc/fs/nfsd/unlock_ip as an operational tool to release stale locks after a client or server IP changes. The Fixes: tag points back to the original feature commit, confirming this has been broken since the unlock-by-IP mechanism was first added.
