Summary

nfsd: reject out-of-range nseconds in setattr atime/mtime

A two-patch series from Robbie Ko (Synology), posted Friday 2026-06-12, addresses a long-standing data-integrity bug in the NFS server's handling of client-supplied file timestamps. The work is squarely about NFS server-side correctness and an important bug fix, with implications for any client that can issue SETATTR (or, on NFSv3, file creation) with a malformed time.

The bug

The core problem is that a client can send a SETATTR carrying an atime or mtime whose nseconds field is out of range — well-formed on the wire and decodable into a valid uint32, but not a valid timespec64:

"A client can send a SETATTR (and, for NFSv3, a file creation) carrying an atime or mtime whose nseconds field is out of range. The value is well-formed on the wire and decodes cleanly into a valid uint32, but it is not a valid timespec64: tv_nsec must be less than NSEC_PER_SEC."

Robbie Ko traced why nothing in the existing path catches it in the patch 1/2 cover:

"Nothing in the path clamps it. notify_change() runs the time through timestamp_truncate(), which does not reduce tv_nsec below NSEC_PER_SEC when the filesystem supports nanosecond granularity (s_time_gran == 1), and the inode atime/mtime setters store it verbatim (only ctime is normalized, via inode_set_ctime_to_ts())."

The consequence is concrete on-disk corruption rather than a benign no-op:

"The un-normalized value then corrupts on-disk metadata. ext4's ext4_encode_extra_time() shifts tv_nsec left by EXT4_EPOCH_BITS; an out-of-range value overflows the 32-bit extra field and clobbers the seconds-epoch bits, so the stored seconds (and thus the year) are wrong on read-back. XFS with bigtime mis-stores the timestamp for the same reason. There is no WARN_ON anywhere in the path to catch it."

The fix

The patch validates client-supplied atime/mtime in nfsd_setattr(), chosen as "the common choke point for SETATTR and for the create paths (via nfsd_create_setattr()), and covers both NFSv2 and NFSv3." The check is performed up front, before any resources are acquired, so no cleanup path is involved. On failure it returns NFS3ERR_INVAL (NFSERR_INVAL for NFSv2), which the client maps to EINVAL.

Ko carefully scoped what is and is not checked, citing RFC 1813:

"Only client-supplied times are checked: SET_TO_SERVER_TIME requests carry no client value and are filled in by the server. The NFSv2 Sun 'set both to now' convention clears ATTR_[AM]TIME_SET in the SETATTR proc before nfsd_setattr() runs, so it is unaffected."

He also explained a deliberate non-change for the ctime guard:

"The sattrguard3 ctime is deliberately left alone: an out-of-range guard simply never matches the object's ctime and yields NFS3ERR_NOT_SYNC via the existing guardtime comparison, which is the protocol-correct outcome rather than rejecting the request."

Notably, NFSv4 was already protected — nfsd4_decode_nfstime4() rejects such values, so they "do not reach this check on that path." Because the missing validation predates the git history of the code, no Fixes: tag is provided, but Ko flagged it as a candidate for LTS backport:

"The lack of validation is long-standing and predates the git history of this code, so no Fixes: tag is provided. This is a data-integrity fix and is a candidate for LTS backport."

Companion cleanup

Patch 2/2 is a readability-only change to the NFSv4 decoder, replacing an open-coded literal with the named constant:

"nfsd4_decode_nfstime4() open-codes the nanoseconds upper bound as the literal (u32)1000000000. Use the named constant NSEC_PER_SEC instead, matching the out-of-range check added for the NFSv2/NFSv3 setattr path and improving readability. No functional change."

Review status

As of the end of this week's window, the series is in early review. Jeff Layton replied to patch 1/2 on 2026-06-12 to point the author toward automated review feedback:

"Sashiko had some review comments on this series that you should take a look at."

No substantive technical objections or merge decisions have landed in-thread yet, so the discussion is still in its first round.

Bottom line

This is a bug fix (data integrity), not a new feature or protocol change. It closes a gap where malformed NFSv2/NFSv3 timestamps could silently corrupt on-disk metadata on ext4 and bigtime XFS, by adding an early validation check at the nfsd_setattr() choke point and returning EINVAL to the client. A trivial companion patch cleans up the existing NFSv4 constant usage. The series is a candidate for LTS backport and awaits further review following Layton's pointer to Sashiko's automated comments.
