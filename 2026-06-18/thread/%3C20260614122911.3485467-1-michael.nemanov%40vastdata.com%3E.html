NFS client: fix ENXIO on O_CREAT open of existing symlink over NFSv3

Summary

NFS Client Bug Fix: ENXIO on O_CREAT Open of Existing Symlink over NFSv3

Overview

On June 14, Michael Nemanov (Vast Data) posted a targeted bug-fix patch to the linux-nfs mailing list addressing a long-standing edge case in the NFSv3 client's atomic_open path. The issue: calling open(2) with O_CREAT on a path that already exists as a symbolic link, over an NFSv3 mount with a cold dentry cache, causes the kernel to return ENXIO (errno 6) instead of transparently following the symlink to its target.

This is a bug fix in the NFS client (fs/nfs/dir.c), not a new feature or protocol change.

The Bug and Its Root Cause

Nemanov provided a concise reproducer script demonstrating the failure on kernel 7.1-rc6:

"When open(2) is called with O_CREAT on a path that already exists as a symlink, over an NFSv3 mount with a cold dcache, the kernel returns ENXIO instead of following the symlink to its target."

The root cause involves a confluence of three factors:

  1. NFSv3 CREATE UNCHECKED semantics: Per RFC 1813 §3.3.8, when the server receives a CREATE for a name that already exists as a non-regular file (like a symlink), it returns NFS3_OK with the existing object's file handle — not NFS3ERR_EXIST. Nemanov noted:

    "when the name already exists as a non-regular file the server returns NFS3_OK with the existing object's file handle rather than NFS3ERR_EXIST"

  2. Unconditional finish_open() call: After nfs_do_create() succeeds (returning 0), the client code unconditionally calls finish_open(), which dispatches through inode->i_fop->open().

  3. Symlink inodes have no real file operations: The VFS initializes symlink inodes with &no_open_fops because POSIX mandates that open(2) must follow symlinks, never open them directly. Thus no_open() returns -ENXIO.

The bug is masked when the dcache is warm (e.g., after a prior stat(2)), because lookup_open() then finds a positive dentry and skips atomic_open entirely, leaving symlink resolution to the normal VFS path. Nemanov highlighted this subtlety:

"The bug does not trigger when the dcache is warm (e.g. after a prior stat(2)), because lookup_open() then finds a positive dentry and skips atomic_open entirely, leaving symlink resolution to the VFS."

The Fix

The patch adds 7 lines to fs/nfs/dir.c. After nfs_do_create() succeeds, the code now verifies that the returned inode is a regular file before calling finish_open(). If the object is not regular, it returns finish_no_open() so the VFS can follow the symlink through the normal open path.

Nemanov explained the design choice for the type check:

"!S_ISREG() is used rather than S_ISLNK() to cover any other non-regular types a server might return."

This defensive approach ensures correctness even if a non-conformant NFSv3 server were to return a handle for, say, a directory or device node.

The patch carries a Fixes: tag pointing to commit 7c6c5249f061 ("NFS: add atomic_open for NFSv3 to handle O_TRUNC correctly."), identifying the original code that introduced the regression.

Status and Context

As of this week's window, the thread contains only the initial patch submission — no replies from maintainers (Trond Myklebust or others) have yet appeared within the June 12–18 timeframe. The patch is a small, well-scoped fix with a clear Fixes: tag and self-test, making it a strong candidate for inclusion in a stable/fixes tree once reviewed.

This type of bug — where NFSv3's lenient CREATE semantics interact poorly with the VFS's assumptions about file types at open time — is a recurring theme in NFS client development, underscoring the fragility of the atomic_open path when the server returns an unexpected file type.
