nfs-utils: EIO-on-zero-threads fix committed by Steve Dickson

Summary

nfsd thread-count fix lands in nfs-utils

Type: Bug fix (nfs-utils userspace, server-side) — resolution week

The verdict this week

The story on this thread reached its conclusion this week with a single, characteristically terse message from the nfs-utils maintainer. On June 16, Steve Dickson confirmed the patch was accepted, replying directly to Scott Mayhew's original submission:

"Committed... steved."

That two-word-plus-signature reply is Dickson's signature review style on the list — a clean, uncontroversial fix that warranted no further debate. With this commit, the discussion effectively closed.

Bridging the prior week

For context, the patch itself was posted by Scott Mayhew on June 8, in the previous reporting window. The technical problem it addressed was a kernel behavioral change:

"Newer kernels return -EIO if you try to write to /proc/fs/nfsd/threads and there are no active listeners."

The fix, confined to utils/nfsd/nfsd.c (10 insertions, 6 deletions), stops the userspace tool from blindly assuming the service is running before attempting to set the thread count to zero. Instead of surfacing an unhandled I/O error during shutdown or thread-count management, the init script now gracefully handles the no-active-listeners case.

Significance for the NFS ecosystem

While this is a server-side userspace change rather than a client fix, it matters to administrators running nfsd on modern kernels (6.x+). Without the patch, stopping or restarting the service on systems with no active exports could emit confusing errors in logs or disrupt systemd unit transitions. The change tightens the contract between the init script and the kernel's procfs interface — a recurring friction point as kernel behavior evolves.
