knfsd fair scheduling: Brown probes a stateless-v4 escape hatch; Coddington holds the line on one shared pool

Summary

knfsd per-client fair scheduling: the "is there a workaround?" week

Classification: This remains an RFC-stage feature proposal / protocol-adjacent scheduling change for the NFS server (knfsd/sunrpc), not a traditional client bug fix. The three in-window messages this week are short but pointed: Neil Brown floats two possible workarounds that would let the design sidestep covering v3, and Benjamin Coddington shoots both down to defend the core architectural premise — one shared, version-agnostic fairness pool. No patch is posted; the thread stays at the design stage, but the week's exchange narrows what a complete fix must look like.

Bridge from prior weeks

The thread was opened by Benjamin Coddington arguing that a client opening many TCP connections plus a large v4.1 slot table can saturate the whole nfsd thread pool and starve other clients, because "the xprt is the unit of fairness." Chuck Lever welcomed it as "a well-known shortcoming of NFSD" but proposed scheduling per-session for NFSv4.1+ and managing each session's load by raising and lowering its slot table. Last week Coddington delivered the promised benchmark data (a one-connection "interactive" client drops to ~1/(K+1) of the pool when another drives K connections, for both v3 and v4.1), Neil Brown proposed reusing the existing memory-pressure slot-reduction code as the mechanism, and — just past that window on June 5 — Coddington closed the "why v3?" gap: Flexfiles uses v3 in its data plane, and Lever reframed the whole effort as a security posture. This week's three messages are Brown and Coddington working through what follows from those two conclusions.

This week: two escape hatches, both rejected

The week opens with Neil Brown replying to Coddington's June 5 message — the one that justified v3 via Flexfiles and stressed that knfsd has no per-version resource pools. Brown's instinct is to ask whether the v3 requirement can be dissolved rather than satisfied. He points out that NFSv4 already ships a feature that looks like exactly what Coddington wants for a stateless data plane:

"v4 already has the anonymous stateid which seems perfect for a data plane. You can read/write with it just like v3 (i.e. access check on every IO etc), but there is no state to recover."

He notes you still get client-state and session-state "when [they] can be used for flow control, but these don't need to be recovered so they don't impose the same costs as open state," then floats a concrete client-side change:

"I wonder if flex-files can be updated to allow v4 with anonymous stateid. We would have to enhance the Linux NFS client to have a 'stateless' mount option, or similar."

That is the week's only genuinely client-development thread: Brown is proposing that the Linux NFS client grow a "stateless" mount option (and that Flexfiles be updated to permit v4 with an anonymous stateid) so that the v3 data-plane workload could migrate to v4 and inherit the session/slot-table fairness machinery — eliminating the need for a separate v3 identity mechanism entirely.

On the shared-pool point, Brown also offers a second escape hatch: per-version pools could be built if there were "a coherent model of how that would work." He sketches two ways to get there, both leaning on infrastructure that already parses RPC metadata before queueing for a thread:

"We could parse out the RPC program and version before queuing for a thread, much like we already parse out the TCP message size. We could even do that today: create a separate net-namespace for the separate pool, and add some iptables rules to redirect select traffic to that namespace."

He concedes the limitation of the off-the-shelf trick — "iptables cannot switch on RPC version, but it could switch on source-IP if we knew which clients used v3 and which didn't."

Brown's second message takes a different tack: it pushes back on Lever's "DoS surface" framing from last week, arguing that the security lens is overkill for what is really a coordination problem:

"I can't see that DoS is a useful way to look at this. For that we would need a threat model which I don't think we have."

He recasts the affected parties as cooperating actors rather than adversaries:

"The problem situations that have been mentioned involve actors that would like to co-operate but have no obvious mechanism to enable that co-operation. For v4, I think session flow control should be the 'obvious' mechanism. For v3, nothing is obvious so we have to look at heuristics, classifying by recent behaviour or some sort of identity."

And he sets a deliberately modest bar for success: "We don't need a system that is always perfect, just a system that clients are able to co-operate with."

The week closes with Coddington's reply to Brown's per-version-pool sketch. He accepts it is technically possible but rejects it on principle, because splitting the pool by version defeats the entire point of the RFC:

"Doable, but I'd rather not split the pool by version: the point for us is that one shared pool stays fair regardless of which version a client speaks. Per-version pools just relocate the unfairness from 'client with N connections' to 'version with N connections.'"

Why this matters for the design

  • The "avoid v3" route is now explicitly on the table and explicitly rejected. Brown's anonymous-stateid / "stateless mount option" idea is the first concrete proposal in the thread that would let Flexfiles move its data plane to v4 and thereby inherit the slot-table fairness mechanism — sidestepping the v3 identity problem. It also names a real, scoped Linux NFS client change (a new stateless mount option plus a Flexfiles update). Coddington does not directly answer it this week, but his insistence on one shared pool signals he is not willing to let the design's correctness depend on migrating workloads off v3.
  • The shared-pool invariant is now load-bearing. Coddington's "relocate the unfairness" line crystallizes the central constraint: whatever mechanism is chosen must keep a single pool fair across all exported versions. That forecloses the per-version net-namespace/iptables hack Brown sketched and reinforces that v3 needs its own identity (source-address fallback or behavior-based classification) inside the same queue — not a separate pool.
  • The DoS framing is contested, but it doesn't change the requirement. Brown's "I can't see that DoS is a useful way to look at this" is a genuine disagreement with Lever over motivation (adversarial threat model vs. cooperating-but-starved clients). Yet both sides converge on the same engineering conclusion: cover all versions in one pool. The dispute is about how hard the guarantee must be, not whether v3 must be included.

Conclusions and open threads

  • Resolved this week: Coddington reasserts that per-version pools are off the table — fairness must hold across a single shared pool regardless of version ("Per-version pools just relocate the unfairness"). Brown's DoS framing is formally challenged as lacking a threat model, reframing the goal as enabling cooperation rather than defeating attackers.
  • Newly raised, still open: whether Flexfiles can be updated to use v4 with an anonymous stateid, and whether the Linux NFS client should gain a "stateless" mount option — a potential path that would let the v3 data-plane workload adopt the v4 session/slot-table mechanism (Brown's idea; no response from Coddington yet).
  • Still open from prior weeks: the concrete v3 identity mechanism (source-address fallback vs. behavior-based heuristics), tracking an effective thread maximum under dynamic pool growth and allocation failures, whether to add a shrinker to stop nfsd threads under memory pressure, and how LOCALIO workloads fit into the fairness model.
  • No patch has been posted — the discussion remains at the design/measurement stage, but this week's exchange tightens the spec: one shared pool, all versions covered, with a possible (unanswered) client-side "stateless mount" workaround that could shrink the v3 problem.
