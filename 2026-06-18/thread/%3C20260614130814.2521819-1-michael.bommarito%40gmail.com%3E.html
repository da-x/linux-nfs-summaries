NFSv4.1/pnfs: bound GETDEVICEINFO notification bitmap length (new fix, awaiting review)

Summary

NFSv4.1/pnfs: bounding the GETDEVICEINFO notification bitmap — a new client-side bug fix

This week's activity in this thread is limited to a single event: Michael Bommarito submitted a two-patch series on 2026-06-14 that fixes an out-of-bounds read in the NFSv4.1 pNFS client's GETDEVICEINFO decoder. There were no replies, reviews, or discussion within this week's window — the thread stands at the point of submission, awaiting maintainer and reviewer response.

What kind of change this is

This is a bug fix (a security-relevant robustness fix on the NFS client), not a new feature or protocol change. It targets the Linux NFSv4.1 pNFS client — specifically decode_getdeviceinfo() in fs/nfs/nfs4xdr.c — and is marked for stable backporting:

"Fixes: b1f69b754ee3 ("NFSv4.1: pnfs: add LAYOUTGET and GETDEVICEINFO infrastructure")" "Cc: stable@vger.kernel.org"

The technical argument

The core of the report is an integer-overflow-driven out-of-bounds read in how the client handles a server-supplied notification bitmap length. As Bommarito lays it out in the cover letter PATCH 0/2:

"decode_getdeviceinfo() scales a server-supplied notification bitmap length by four for xdr_inline_decode(). The 32-bit multiply wraps to 0 for len >= 0x40000000, so the bounds check passes on an empty request and the verify loop reads up to ~2^30 words past the inline XDR buffer."

The mechanism is precise: a u32 length is multiplied by four in 32-bit arithmetic. For lengths of 0x40000000 or greater, that multiply wraps to zero, which defeats the subsequent !p bounds check on an otherwise empty request and lets the verification loop read far past the inline XDR buffer.

Bommarito carefully scopes the impact in both directions. On the threat side:

"A malicious or compromised pNFS server, or a man in the middle on an unprotected mount, can drive this out-of-bounds read while the client decodes a GETDEVICEINFO reply."

On the severity side, he is explicit that this is not an information leak:

"It is a read, not a leak: the loop only checks each word for nonzero and returns -EIO on the first, so over-read contents are never returned."

The fix

The remedy rests on a protocol observation: RFC 8881 defines only two deviceid notification bits (CHANGE and DELETE), both in word 0, so a conformant reply needs just one word. The fix bounds the length before scaling it, eliminating the wrap entirely:

"Bound len to NFS4_GETDEVICEINFO_NOTIFY_MAXWORDS before scaling, which cannot wrap and still tolerates trailing zero words the decoder keeps verifying."

Patch 1 PATCH 1/2 is the minimal fix — six lines across fs/nfs/nfs4xdr.c and a new constant in include/linux/nfs4.h.

Testing and KUnit coverage

A notable feature of this submission is its testing rigor. Bommarito reproduced the bug under KASAN on QEMU, citing:

"BUG: KASAN: slab-out-of-bounds in decode_getdeviceinfo"

Because integer overflow has no dedicated sanitizer, the test oracle is the downstream KASAN fault itself. Patch 2 PATCH 2/2 adds a KUnit suite that drives the real file-local decode_getdeviceinfo() over a crafted reply. To reach the static decoder without exporting it, the test is compiled into nfs4xdr.c behind a new config gate:

"It is included into nfs4xdr.c (gated by CONFIG_NFS_GETDEVICEINFO_KUNIT_TEST) to reach the static decoder without exporting it."

The suite contains one trigger case (the wrapping length, placed at a page edge) and two benign in-bounds controls. The reported results:

"on QEMU x86_64 with KASAN the trigger faults on stock and passes after patch 1, while both controls pass on stock and fixed trees."

Bommarito deliberately decoupled the test from the fix so it can be accepted or dropped independently:

"Patch 2 adds KUnit coverage and is offered separately so it can be taken or dropped on its own."

He also notes a gap in existing coverage that motivated the new suite:

"fs/nfs has no existing kselftest for this decoder."

Broader context (brief bridge)

This submission continues a pattern of pNFS GETDEVICEINFO hardening by the same author. In late May 2026, Bommarito posted related work titled "fix client kernel panic from malformed GETDEVICEINFO," which addressed a zero-length r_addr in nfs4_decode_mp_ds_addr and bounded the multipath DS count in GETDEVICEINFO. The current series extends that effort to the notification-bitmap length path — the same decoder family, a different overflow vector — reinforcing an ongoing campaign to make the pNFS client robust against malformed or malicious GETDEVICEINFO replies.
