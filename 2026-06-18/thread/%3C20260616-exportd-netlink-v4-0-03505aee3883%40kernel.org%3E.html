nfsd/sunrpc: Convert nfsstat server-side interfaces to netlink (v4) — review and design debate

Summary

nfsd/sunrpc: Convert nfsstat server-side interfaces to netlink (v4)

Type: New feature / interface conversion (with a minor bug fix in v4)

Overview

On June 16, Jeff Layton posted version 4 of his patch series to convert the NFS server-side statistics interface from procfs to netlink. The series replaces the fragile, global /proc/net/rpc/nfsd scraping used by nfsstat with a proper generic netlink dump handler in the nfsd family, adding network-namespace-awareness and extensibility.

The v4 changes were minimal:

"This version just fixes an error handling bug that Sashiko noticed."

Specifically, the series now ensures errors are returned when nla_put_*() calls fail in the netlink dump path. The four patches:

  1. Patch 1 – Adds per-netns per-procedure percpu call count arrays to struct svc_stat, allocated with the nfsd_net lifecycle.
  2. Patch 2 – Switches svc_seq_show() to read from the per-netns counters, making /proc/net/rpc/nfsd namespace-aware (a deliberate behavior change Layton called "desirable").
  3. Patch 3 – Implements the server-stats-get netlink dump handler, streaming reply-cache, filehandle, IO, network, and RPC statistics plus per-version and per-operation procedure counts across multiple netlink messages.
  4. Patch 4 – Removes the now-unused global svc_version vs_count percpu arrays from nfsd, lockd, and the NFS client callback service (39 lines deleted).

Layton also noted: "I'll also be sending an nfs-utils patch to convert nfsstat to use the new interfaces."

Review Round 1: Build Breakage (Patch 1)

Chuck Lever identified a build break in Patch 1 the same evening:

"This patch appears to break the build for an NFSv3-only server configured with CONFIG_PROC_FS=n."

The issue: svc_stat_alloc_counts() and svc_stat_free_counts() live in net/sunrpc/stats.c, which is only compiled when CONFIG_PROC_FS=y. However, nfsd_net_init()/nfsd_net_exit() call both helpers unconditionally, and the declarations sit outside the #ifdef CONFIG_PROC_FS guard. Since CONFIG_NFSD does not depend on PROC_FS (only NFSD_V4 does), a valid Kconfig combination of NFSD=y with V2/V3 only and PROC_FS=n results in an undefined reference at link time.

Lever suggested moving the functions to net/sunrpc/svc.c, which is always built. Layton agreed:

"Thanks. Looks pretty simple to fix. I'll plan to send a v5."

Review Round 2: Missing wdeleg_getattr Counter (Patch 3)

The more substantive design discussion centered on Patch 3. Lever pointed out that the netlink dump handler drops a counter present in the procfs output:

"The procfs output in nfsd_show() emits one more counter that this dump handler drops: wdeleg_getattr (NFSD_STATS_WDELEG_GETATTR), printed at the end of the CONFIG_NFSD_V4 block in fs/nfsd/stats.c, right after proc4ops."

Lever provided a concrete fix recipe: add a wdeleg-getattr (u64) attribute to the YAML schema, add the corresponding UAPI enum value, and emit it as a scalar in the first dump message wrapped in CONFIG_NFSD_V4.

Layton pushed back, arguing the omission was intentional:

"This omission was intentional. The stated purpose of this patchset was to convert nfsstat to use netlink. nfsstat does not access or display this field today. Without something that consumes this stat, I don't see the point of adding it here."

Lever rebutted on API-compatibility grounds:

"If we were adding a greenfield kernel-userspace API, I would agree. However, this API is meant to be compatible with the existing procfs API, so it should match to prevent a regression."

He added a useful process note: "since a missing feature cannot be expressed in a patch's diff body, your intention to exclude this field could be mentioned in the commit message." Lever also noted that nfsstat should display the field: "It has simply been forgotten."

Layton conceded:

"Ok. I'll plan to add it to the interface and send it in v5."

Design Evolution: Callback Call Counts

In a follow-up message, Layton proposed a broader design change. He noted that wdeleg_getattr is "weird in that it's not a statistic about server-side protocol operations" and suggested instead keeping and exposing server-side callback call counts as a new section in nfsstat output:

"What would you (and Dai) think about instead keeping and exposing server-side callback call counts? Then we could just add a new section to nfsstat server-side output with all of the callback operation counts in it. wdeleg_getattr would just be the count for CB_GETATTRs."

Lever endorsed the idea:

"That sounds ideal."

Conclusions and Next Steps

The thread ended with clear agreement on the v5 changes:

  1. Fix the CONFIG_PROC_FS=n build break by relocating the count allocation/free helpers to net/sunrpc/svc.c.
  2. Add wdeleg_getattr to the netlink interface for procfs compatibility, or better yet, expose the full set of server-side callback operation counts as a new section in both the netlink dump and nfsstat output.
  3. Layton will send v5 with these fixes; an nfs-utils follow-on patch to update nfsstat is also planned.

The discussion was entirely about NFS server-side infrastructure (nfsd/sunrpc), though it touches the NFS client callback service (fs/nfs/callback_xdr.c) in Patch 4's cleanup of the removed vs_count field. No NFS client protocol or client bug fixes were involved.
