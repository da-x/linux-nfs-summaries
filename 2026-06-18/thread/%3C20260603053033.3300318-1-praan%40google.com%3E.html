NFS Direct I/O folio patch: xfstests failures resolved, v2 posted with clean test matrix

Summary

NFS Direct I/O Folio Patch: xfstests Failures Resolved, v2 Posted with Clean Test Matrix

Type: New feature / architectural refactor of the NFS client direct-I/O path (groundwork for PCI Peer-to-Peer DMA), with an incidental bug fix. This week's activity is a bug-fix follow-up to the v1 review.

Context from prior weeks

In the week ending 2026-06-04, Pranjal Shrivastava (Google) posted a seven-patch series to modernize the NFS client's O_DIRECT path — migrating from the legacy iov_iter_get_pages_alloc2() API to the modern iov_iter_extract_pages(), and moving requests from pages to folios. NFS maintainer Anna Schumaker flagged widespread xfstests failures on patch 6 (the folio-grouping optimization), and Shrivastava acknowledged the gap:

"I've just run fio and haven't run xfstests (sorry wasn't aware of them)."

He suspected "an error in the contiguous grouping logic in Patch 6, likely the offset calculation or handles partial page boundaries" and promised to run the full suite.

This week: the fix lands

On June 16, Shrivastava replied to close out that thread, confirming he had diagnosed and fixed the issues:

"I was able to run xfstests [1] and identify the issues. I've fixed those issues and posted a v2 [2]. I don't see any failure."

The v2 series (posted separately) carries two specific bug fixes called out in its changelog:

  • Data corruption fix: "Fix data corruption in nfs_direct_extract_pages() by correctly calculating intra-page offsets using offset_in_page()." This is the offset-calculation error Shrivastava had suspected back on June 4.
  • Accounting fix: "Fix requested_bytes accounting in direct read/write paths to only increment after successful RPC scheduling."

Additionally, patch 4's API migration corrects a latent lifetime bug: "pages were being unpinned immediately after request creation" — pins are now held until I/O completion.

Test evidence

Shrivastava included an exhaustive xfstests matrix in his reply, running 26 generic/ tests across eight configurations (RDMA and TCP transports at NFSv3, v4.0, v4.1, and v4.2). The result: "Passed all 27 tests" in every section (the count of 27 reflects one test that was skipped on some sections but passed on others, yielding 27 executed per run). A formatted summary table shows uniform "pass" across all configurations, with a handful of tests (generic/183, generic/188, generic/190, generic/196, generic/203, generic/287, generic/290, generic/292, generic/330) skipped on v3/v4.0/v4.1 but passing on v4.2, and generic/444 skipped everywhere.

He also noted a small process detail: "I couldn't figure out the tool used to generate that table, so I wrote a small script [3] that picked up logs from each run in results/* dir," linking his display.py utility on GitHub.

Where things stand

The v1 xfstests regression is resolved. The v2 series (summarized separately this week) now faces a different, more fundamental review challenge — Trond Myklebust's question about whether page_folio() is safe for all user-space memory regions, and pushback from Christoph Hellwig and Matthew Wilcox that the "every page is a folio" invariant is fragile (particularly for slab pages). The discussion has shifted from "does it work?" to "is the underlying assumption sound?", with maintainers steering toward reusing block-layer extraction code. No merge decision has been recorded yet.
