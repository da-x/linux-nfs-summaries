CB_NOTIFY dir-delegation v7: Layton folds in Lever's review fixes; Lever applies all 20 patches to nfsd-testing

Summary

CB_NOTIFY Directory Delegation v7 — Review Fixes Folded In, Series Accepted into nfsd-testing

Overview

This week marked the resolution of a multi-month review cycle on Linux NFS server (nfsd) support for RFC8881bis CB_NOTIFY callbacks in directory delegations. On June 16, Jeff Layton posted v7 of the 20-patch series, incorporating fixes for "yet more problems that Sashiko and Chuck flagged during review." A day later, on June 17, Chuck Lever applied the entire series to his nfsd-testing branch, closing out the review loop and moving the feature toward the v7.3 merge window.

This is primarily new-feature development — server-side CB_NOTIFY support for directory delegations (creates, unlinks, renames, and directory attribute changes) — but the series also contains a notable bug fix: patch 17/20 corrects a reply-size estimation error in GET_DIR_DELEGATION that could leave clients without a granted stateid.

Bridge from Prior Week

As summarized last week, Lever completed his review of all 20 v6 patches on June 12, surfacing eight distinct findings across concurrency (a refcount inc-from-zero race in the delegation recall path), protocol correctness (an order-aware client spec violation in notify-mask negotiation), size budgeting (a one-word vs. two-word bitmap underestimation), and a use-after-free on svc_export during in-flight CB_NOTIFY callbacks. Layton's stated gating condition for upstream merge remained:

"I don't think we'll want to merge these until we have a complete client-side implementation to test against."

v7 is the direct response to that review burst, and Lever's acceptance confirms the fixes were satisfactory.

Key Technical Arguments and Patch Highlights

The Cover Letter — Framing v7

Layton's cover letter is concise but informative:

"This version of the patchset fixes up yet more problems that Sashiko and Chuck flagged during review. Progress!"

He restates the feature's purpose:

"With this support, the client can register interest in a directory and get notifications about changes within it without losing its lease."

The v7 changelog highlights three categories of fixes over v6:

  • "Fixes for several bugs that Chuck pointed out in review"
  • "Dropped fi_connectable flag (no longer needed with stid->sc_export)" — addressing Lever's patch 16/20 finding about shared nfs4_file connectability
  • "Ensure FH signing is done properly on returned filehandles"

Patch 02/20 — Protocol Support and UAPI Cleanup

This patch adds CB_NOTIFY to the XDR specification and regenerates wire encoders/decoders. A notable side effect: regenerating the XDR files exposed duplicate definitions of NFS4_VERIFIER_SIZE and NFS4_FHSIZE in include/uapi/linux/nfs4.h. Layton removed them, noting:

"These constants are defined by the RFC, and are not part of the kernel API. Userspace consumers who require those constants should plan to get them from more authoritative sources."

The patch also addresses Lever's earlier XDR enum leak finding by basing nfsd's internal error codes at an impossible nfsstat4 value rather than carrying NFS4ERR_FIRST_FREE into the generated encoder.

Patch 03/20 — RFC8881bis Flags and a Protocol Risk Note

This patch adds new NOTIFY4_* flags from the still-in-progress RFC8881bis working group document. Layton is candid about the risk:

"There is some risk here -- RFC8881bis is still a working group document, and has been for years. The changes to directory delegations have been stable for the last year or so however, so the hope is that those parts won't change (much)."

The new flags allow Linux nfsd to omit cookie and ordering information it cannot easily provide, which is directly relevant to the order-aware client issue Lever flagged in v6.

Patch 05/20 — Serializing fsnotify Mask Recalculation

This patch adds an nfm_recalc_mutex to serialize concurrent calls to nfsd_fsnotify_recalc_mask(). The problem: the fsnotify mark is shared by every nfsd_file open on an inode, and "a recalc working from a stale snapshot of the lease list could clobber a concurrent update and leave the mark missing required events." This carries a Reviewed-by: Jan Kara <jack@suse.cz>, indicating VFS-side sign-off.

Patch 08/20 — RCU Protection for fi_deleg_file

This patch addresses the RCU use-after-free that Lever identified in earlier review rounds. The commit message describes the race precisely:

"fi_deleg_file can be NULLed by put_deleg_file() when fi_delegees drops to zero during delegation teardown (e.g. DELEGRETURN). Concurrent accesses from workqueue callbacks -- such as CB_NOTIFY -- can dereference a NULL pointer if they race with this teardown."

The fix converts all accessors to proper RCU primitives and prepares for the CB_NOTIFY callback path to safely acquire references without holding fi_lock. Notably, the patch also documents a subtle lease-teardown bug: "the lease's flc_file is set to fi_deleg_file in nfs4_alloc_init_lease(), which differs from nf when an earlier client already holds a delegation on the same directory, and generic_delete_lease() matches on flc_file -- unlocking the wrong file would leak the lease on the inode."

Patch 10/20 — Notification Handlers (Addressing the Refcount Race)

This patch adds the fsnotify callback handling that creates CB_NOTIFY requests. The commit message states the error-handling policy: "If anything fails along the way, recall any affected delegations." This is where Lever's v6 finding about the unlocked refcount_inc in nfsd_break_one_deleg() was addressed — the v7 version presumably uses refcount_inc_not_zero() as Layton confirmed in his v6 review response:

"I think we need to do a refcount_inc_not_zero() in nfsd_break_one_deleg() and just return without queuing the callback if it's already at 0."

Patch 11/20 — Order-Aware Client Mask Negotiation Fix

This patch directly addresses Lever's v6 finding about the order-aware client spec violation. The commit message now explicitly handles both cases:

"If the client doesn't set NOTIFY4_GFLAG_EXTEND, then don't offer any notifications, as nfsd won't provide directory offset information, and 'classic' notifications require them."

"Similarly, if the client sets GFLAG_EXTEND | CFLAG_ORDER, then zero out the notification mask. The Linux server can't provide the necessary ordering info to those clients."

This ensures order-aware clients get a clean delegation without notification promises they cannot fulfill, rather than receiving unusable notifications while retaining their lease.

Patch 15/20 — Filehandle Encoding Without svc_fh (Addressing FSID NULL Deref)

This patch generalizes filehandle encoding to work without a svc_fh, which is unavailable in the CB_NOTIFY callback context. It also addresses Lever's v6 finding about the FSID encoder's NULL dereference risk by adding fsid_source_fh() that operates on a bare knfsd_fh and its svc_export:

"The FSID attribute shares the same attrmask gate as the filehandle, so do the same for it: add fsid_source_fh() which takes a bare knfsd_fh and its svc_export."

Patch 17/20 — The Reply Size Estimation Bug Fix

This patch is the series' most client-visible bug fix. It corrects nfsd4_get_dir_delegation_rsize(), which was returning its estimate in XDR words instead of bytes:

"The ~4x too-small estimate lets a compound near the session/reply limit pass the check, grant a directory delegation, and then fail to encode the reply with NFS4ERR_RESOURCE/REP_TOO_BIG, leaving the client without the returned stateid."

The fix is a one-line multiplication by sizeof(__be32), matching all other _rsize helpers. It carries a Fixes: tag pointing to the original GET_DIR_DELEGATION commit, indicating this bug predates the CB_NOTIFY work.

Patches 18–19/20 — Size Budgeting for Two-Word Bitmaps

Patch 18 and patch 19 track the union of requested and supported child/directory attributes in the delegation. Both note that word-1 attributes can cause nfsd4_encode_bitmap4() to emit a two-word bitmap, and both bump the corresponding budget in nfsd4_get_dir_delegation_rsize():

"Bump the child-attribute bitmap budget in nfsd4_get_dir_delegation_rsize() from one word to two accordingly, so the reply-size check before this non-idempotent op accounts for the larger encoding."

This directly addresses Lever's v6 finding that the size underestimation could leave clients in an inconsistent state after a failed encode.

Patch 20/20 — Directory Attribute Change Notifications

The final patch completes the feature by sending directory attribute changes alongside add/remove/rename events. An important caveat:

"Note that the server will still recall the delegation on a SETATTR, so these are only sent for changes to child dirents."

This means the CB_NOTIFY path is complementary to (not a replacement for) the existing delegation recall mechanism.

Lever's Acceptance

Lever's reply is characteristically terse:

"Applied to nfsd-testing, thanks!"

He lists all 20 commit hashes, confirming clean application. This brings the multi-month review cycle (spanning v1 through v7, with reviews from both Lever and Sashiko) to a close for the server-side component.

Evolution of the Discussion

The thread's full arc:

  1. April 7 — v1 posted.
  2. April 16 – May 22 — v2–v5 iterations addressing early review feedback (error handling, GFP flags, tracepoint safety).
  3. June 11 — v6 posted with folded fixes; Lever begins systematic review.
  4. June 12 — Lever completes review of all 20 patches in one day, surfacing 8 findings.
  5. June 16 (this week) — v7 posted incorporating all fixes.
  6. June 17 (this week) — Lever applies to nfsd-testing.

The convergence from 7 versions to acceptance took roughly three months, with the final review-to-acceptance cycle taking just one day.

Implications for NFS Client Development

  • The server-side foundation is now in place. With all 20 patches in nfsd-testing, the Linux client team has a stable target to develop against. The CB_NOTIFY callback infrastructure (encoding, decoding, event queuing, delegation state tracking) is complete on the server side.

  • The order-aware client path is now safe. The v7 fix ensures that clients setting GFLAG_EXTEND | CFLAG_ORDER will not receive notifications they cannot use. This removes a protocol-correctness blocker for future client implementations.

  • The reply-size bug fix (patch 17) eliminates a class of client-visible failure. Clients near session/reply limits will no longer encounter the inconsistent state of a granted delegation followed by NFS4ERR_RESOURCE with no stateid.

  • The remaining gating dependency is unchanged: Layton's caveat about needing "a complete client-side implementation to test against" still applies. The v7.3 merge window (targeted for late 2026) gives the client team roughly one more merge cycle to deliver their half.

  • RFC8881bis dependency risk remains. The new NOTIFY4_* flags are from a working-group document that has been in flux for years. If the directory delegation portions change before final publication, both server and client would need updates. Layton's assessment that "those parts won't change (much)" is optimistic but reasonable given a year of stability.

Status

  • Server-side (nfsd): Complete. All 20 patches applied to nfsd-testing by Lever on June 17. Targeting v7.3.
  • Client-side: Not yet posted. Remains the gating dependency for final upstream merge.
  • Testing: Layton reports pynfs-based tests pass, with new testcases "that I'll be posting soon."
  • Open items: None from the review cycle. The feature is functionally complete on the server side pending client implementation and end-to-end testing.
