nfsd: out-of-range timestamp validation (v3) — per-version checks applied to nfsd-testing

Summary

nfsd: reject out-of-range timestamps in NFSv2/NFSv3 setattr & create (v3)

The series lands — v3 splits the check per protocol version and is merged

This week's activity is the resolution of a multi-week data-integrity bug fix that began on 2026-06-12 (v1), was re-posted as v2 on 2026-06-15, and closed out on Tuesday 2026-06-16 with v3 posted, reviewed, and applied to nfsd-testing in a single day. The work is squarely an NFS server-side bug fix (not a feature, not a protocol change), though its practical impact lands on the client side: any NFSv2 or NFSv3 client that issues SETATTR, CREATE, MKDIR, SYMLINK, or MKNOD with a malformed timestamp no longer silently corrupts on-disk metadata.

The v3 series is Robbie Ko's (Synology) direct response to Chuck Lever's review of v2, in which Lever had objected to the single choke-point check in nfsd_setattr() and laid out a per-version redesign. Ko restructured the series exactly along those lines, expanding it from two patches to three:

Patch 1/3 — NFSv2 decode-time guard on raw useconds

The first patch addresses the specific 32-bit hazard Lever had flagged: in svcxdr_decode_sattr(), the wire useconds is converted to nanoseconds via iap->ia_atime.tv_nsec = tmp2 * NSEC_PER_USEC; where tmp2 is a u32. On ILP32 that product is computed in a 32-bit unsigned long, so an out-of-range value wraps:

"tmp2 is a u32 and NSEC_PER_USEC is 1000, so the product is computed in unsigned long. On ILP32 that is 32 bits, and an out-of-range useconds value such as 4294968 wraps to tv_nsec == 704. The corruption therefore happens during decode, before any proc function can inspect the value, and a later range check on tv_nsec would see an in-range result and accept it."

The fix guards the raw useconds before the multiplication, rejecting values greater than 1000000. Ko carefully preserves the Sun "set to current server time" convention:

"useconds == 1000000 is kept: it is the Sun convention for 'set to the current server time', and the in-tree Linux NFSv2 client emits it in both the atime and the mtime field for a plain touch / utimes(file, NULL) ... Rejecting 1000000 would turn that common operation into a hard decode failure for both SETATTR and CREATE."

Ko also fixed an asymmetry Lever's review implicitly exposed: the decoder had only applied the Sun convention in the mtime block. The patch extends it to the atime block as well, clearing ATTR_ATIME_SET so the server uses its current time rather than storing a bogus value.

Patch 2/3 — NFSv3 proc-handler check, placed before object creation

The second patch moves the NFSv3 validation out of nfsd_setattr() and into the per-operation proc handlers, which is precisely Lever's concern about orphaned objects on the create path:

"Checking in the proc handlers, rather than in nfsd_setattr(), keeps the rejection in front of object creation. The create operations create the object before nfsd_create_setattr() runs, so a late failure would leave the new object behind and turn a non-idempotent request into a namespace change that reports failure."

Ko explains the cast-width choice (matching timespec64_valid() rather than truncating to u32):

"tv_nsec is a long, so the comparison casts it to unsigned long (the same width) rather than to u32, matching timespec64_valid(). A u32 cast would truncate on 64-bit; the unsigned long cast also rejects a value that became negative when an out-of-range u32 wire nseconds was assigned to a 32-bit long."

The patch returns NFS3ERR_INVAL, which Ko justifies against RFC 1813: "the error for a value the server 'can not store ... in its own representation'; the client maps it to EINVAL." The sattrguard3 ctime is deliberately left unvalidated, since an out-of-range guard simply never matches and yields NFS3ERR_NOT_SYNC — "the protocol-correct outcome rather than rejecting the request."

Patch 3/3 — NFSv4 readability cleanup

The third patch is a one-line change to nfsd4_decode_nfstime4(), replacing the open-coded (u32)1000000000 literal with NSEC_PER_SEC. It carries no functional change but preserves the 32-bit signed-compare protection by casting tv_nsec to unsigned long:

"The original code cast the literal to u32 to force an unsigned comparison, which matters on 32-bit where tv_nsec is a 32-bit signed long ... Keep that protection by casting tv_nsec to unsigned long, the same width as tv_nsec, matching timespec64_valid(). No functional change."

Review: Layton's minor style note, then immediate Reviewed-by

Jeff Layton reviewed all three patches within hours of posting. On patch 1/3 he approved the logic but suggested a cosmetic improvement — replacing the repeated magic-number comments with a named constant:

"The logic looks fine, but rather than having these verbose comments above each use of 1000000, it'd be better to declare a constant and document its use once above that. Something like this (and consolidate the comments above that): #define SUN_V2_SET_TO_NOW 1000000"

On patches 2/3 and 3/3 he issued Reviewed-by tags without further comment.

Applied — Chuck Lever merges all three to nfsd-testing

Lever applied the full series to nfsd-testing later that same evening:

"Applied to nfsd-testing, thanks!"

with commit hashes 5a6e45730d33afefe6ac1208173365840314dfd9, ccf2a0a8a51b8fa23bd4e4413e01b57a81451c7f, and 324975079e798c30a15d23396c51216937389baf.

When Layton's style suggestion about the named constant came up, Lever confirmed it was already handled in the applied version and closed the loop:

"The applied version of this patch defines such a symbolic constant. Robbie, no need to resend."

Bottom line

This is a data-integrity bug fix that closes a long-standing gap where malformed NFSv2/NFSv3 timestamps could silently corrupt on-disk metadata (wrong year on read-back for ext4 and bigtime XFS). The v3 series — which restructured the validation from a single nfsd_setattr() choke point into per-protocol-version checks at the decode/proc layer — was posted, reviewed, and merged to nfsd-testing in under 24 hours on 2026-06-16. The fix is flagged as an LTS backport candidate. No further changes are expected; the thread is closed.
