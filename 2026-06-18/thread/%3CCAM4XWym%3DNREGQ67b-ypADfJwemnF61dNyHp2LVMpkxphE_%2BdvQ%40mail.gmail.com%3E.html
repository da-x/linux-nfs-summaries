nfsd: fix null dereference in nfsd4_setattr for deleg timestamp attrs

Summary

[SECURITY] nfsd: fix null dereference in nfsd4_setattr for deleg timestamp attrs

Type: Bug fix (security) — a remotely triggerable null pointer dereference in the NFSv4 server (nfsd) SETATTR path.

The report

The thread opened on Friday, June 12 with Nikol Kuklev's bug report, flagged with the [SECURITY] tag. As quoted in Chuck Lever's reply, Kuklev wrote:

"I would like to report a remotely triggerable null pointer dereference in nfsd4_setattr(), introduced by commit 7e13f4f8d27d ("nfsd: handle delegated timestamps in SETATTR")."

The follow-up message (Saturday, June 13) elaborated on the trigger condition:

"When a SETATTR request includes FATTR4_WORD2_TIME_DELEG_ACCESS or FATTR4_WORD2_TIME_DELEG_MODIFY in the attribute bitmap, nfsd4_setattr() ..."

So the bug is server-side: a malicious (or buggy) NFSv4 client can send a SETATTR carrying the delegated-timestamp attribute bits and crash the kernel via a NULL dereference. The fix Kuklev proposed was, per the maintainer, "only a one-line change."

The process friction

The substantive technical discussion was short; most of the thread's energy went into patch-submission hygiene. Chuck Lever's first reply (within 40 minutes) thanked Kuklev for the report but rejected the submission format:

"Thank you for the bug report. Unfortunately the attachment does not apply using git apply. Please resend the patch inline."

Lever pointed to Documentation/process/email-clients.rst, noting that patches are submitted "preferably as inline text in the body of the email" and that attachments are "generally frowned upon because it makes quoting portions of the patch more difficult in the patch review process." He also linked the companion docs submitting-patches.rst and applying-patches.rst.

Kuklev resent the patch, but Lever's second reply (June 13) found it still broken:

"The above snippet still does not apply. In particular, note the whitespace damage in the diff body -- all the tabs are gone."

Lever then offered what he framed as onboarding advice for a first-time contributor:

"This appears to be your very first submission to the Linux kernel. I don't see your email in the commit history nor does a lore search find it. So I'm going to provide some friendly feedback."

"Maintainers are few and contributions are many. We rely on scripts and automation to make the individual chores easy and not overwhelming. When you submit a patch that does not follow the guidelines above, we have to take time to massage your submission. For many maintainers, that means they won't bother to apply it at all, even if your patch is valid."

Resolution

Rather than bounce the patch back a third time, Lever took ownership of the cleanup:

"Since this is your first submission and it is only a one-line change, I hand-rolled it and applied it to the nfsd-testing branch. Next time, please carefully observe our posting guidelines so this process goes smoothly for you and for us."

So the fix landed in nfsd-testing (Chuck Lever's staging tree) within 24 hours of the report — a fast turnaround for a remotely triggerable server crash — with the maintainer doing the whitespace repair by hand.

Takeaways

  • Security relevance: A NULL deref reachable from an unprivileged NFSv4 client is a remote DoS vector for any Linux box exporting NFS; the fix closes a regression introduced by commit 7e13f4f8d27d ("nfsd: handle delegated timestamps in SETATTR").
  • Client angle: While the bug lives in nfsd, it is triggered entirely by client behavior — specifically clients that set FATTR4_WORD2_TIME_DELEG_ACCESS / TIME_DELEG_MODIFY in a SETATTR bitmap without the server having an active delegation to back them. Well-behaved Linux NFS clients only send those bits when they hold a matching delegation, so the exposure is mostly to third-party or malicious clients talking to a Linux NFS server.
  • Process note: The thread is a useful reminder that even valid one-line security fixes get stuck at the git apply gate if whitespace is mangled; the kernel's email-client documentation exists precisely for this case.
