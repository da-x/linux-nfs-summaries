NFS client bug fix: return a delegation the client fails to record

Overview

This week's activity on this thread is a single, self-contained patch submission from Chuck Lever (Oracle), posted Wednesday, June 17. The change is squarely about NFS client development and constitutes an important bug fix in fs/nfs/delegation.c — not a new feature or protocol change. It closes a long-standing hole where the NFSv4 client could silently drop a delegation granted by the server, leaving both sides out of sync on state.

As of the end of this week's window (2026-06-18), the thread contains only the initial patch — no maintainer review or commit has landed yet. The two follow-up messages in the thread (from Chuck Lever and Anna Schumaker) are dated July 2, outside this reporting window, and will be covered next week.

The bug: three error flows that drop a delegation

Lever's patch targets nfs_inode_set_delegation(), the function the client calls when an NFS server grants a delegation in an OPEN reply. The core problem, as Lever frames it:

"When an NFS server grants a delegation in an OPEN reply, nfs_inode_set_delegation() records it on the client. However, three of its error flows return without sending DELEGRETURN."

The protocol consequence is severe. Lever grounds the argument in RFC 8881 (NFSv4.2):

"A delegation can be relinquished only by DELEGRETURN (RFC 8881 Section 20.2.4), so dropping one silently leaves the server believing the client still holds it."

He then traces the cascade of failures that follows when the server later tries to recall that phantom delegation:

"If the server happens to recall that delegation, the client answers CB_RECALL with NFS4ERR_BADHANDLE because it has no record of the stateid. The server revokes the delegation and moves it onto its cl_revoked list, because the client never sends the FREE_STATEID that would drain it."

The end state is a livelock in the client's state manager:

"Every subsequent SEQUENCE reply then carries SEQ4_STATUS_RECALLABLE_STATE_REVOKED, and the client's state manager loops issuing TEST_STATEID across its delegations without ever clearing the condition."

Why the window is easy to reach now

Lever flags that this is not a theoretical corner case. The race is now routinely reachable because of how modern servers grant write delegations:

"The window is easy to reach now that a server offers a write delegation on any write OPEN: a delegation recalled for one opener races a re-open that the server answers with a fresh write delegation."

This makes the bug particularly relevant for NFS client workloads where multiple openers contend on the same file — exactly the pattern that stresses delegation recall/re-grant cycles.

The fix

The patch is small and surgical: 14 insertions, 4 deletions in fs/nfs/delegation.c. Rather than letting the three error paths silently return (and thereby drop the delegation), they now hand the delegation back to the server via DELEGRETURN:

"Instead of dropping it, hand the delegation back during these error flows."

The patch carries a Fixes: tag pointing at commit ade04647dd56 ("NFSv4: Ensure we honour NFS_DELEGATION_RETURNING in nfs_inode_set_delegation()"), identifying the original code that introduced the regression. No Cc: stable tag is visible in the cover message, but given the Fixes: tag and the severity of the resulting state-manager livelock, this is a strong candidate for stable backport.

Context within this week's NFS client activity

This patch sits alongside several other NFS client fixes posted this week, reinforcing a theme of delegation-state correctness:

  • CB_NOTIFY dir-delegation v6 review (Layton/Lever): Lever's sweep of patches 10–20 surfaced an unlocked refcount inc-from-zero in the delegation recall path and an order-aware-client spec violation — both server-side but with direct client-visible consequences.
  • NFSv3 ENXIO on O_CREAT symlink open (Nemanov, Vast Data): a separate NFS client bug fix in fs/nfs/dir.c addressing a different edge case in the atomic_open path.
  • Missing ida_free() in nfs_alloc_server() (Elfring/Jaillet): a resource-leak fix on the NFS mount path, elevated from a Coccinelle cleanup to a genuine bug fix during review.

The delegation-return fix is the most protocol-sensitive of this week's client patches: it touches the exact state-machine boundary (OPEN → DELEGRETURN → CB_RECALL → FREE_STATEID) where client and server must agree on who holds what, and where a single dropped RPC can leave both sides in an unrecoverable loop.
