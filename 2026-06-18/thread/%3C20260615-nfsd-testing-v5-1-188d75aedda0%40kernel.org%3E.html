nfsd sockaddr validation fix (v5) lands in nfsd-testing same day

Summary

nfsd: validate sockaddr length per family in listener_set — v5 applied to nfsd-testing

Classification

This is a bug fix for an out-of-bounds read vulnerability in the NFS server's netlink listener-management path. It is not a new feature or protocol change. The patch carries a Fixes: tag pointing to the original commit that introduced the listener-set/listener-get netlink commands.

Bridge from Prior Week

This patch is the long-awaited replacement for PATCH 15/21 from Jeff Layton's 21-patch "nfsd: more bugfixes" v2 series, which Chuck Lever dropped during the June 13 merge with the note "Dropped 15/21 - will be replaced." Layton had flagged on June 12 that Sashiko's review had surfaced a problem:

The v5 repost arrived three days later as a standalone patch (no longer part of the larger series), after two intermediate revisions (v3 and v4) that reworked the validation approach.

This Week's Activity (June 15)

The entire thread — posting through application — completed in under 24 hours on June 15, 2026.

The Patch (v5)

Jeff Layton posted the v5 patch at 18:31 UTC. The vulnerability is straightforward but serious:

"nfsd_sock_nl_policy declares NFSD_A_SOCK_ADDR as a bare NLA_BINARY attribute with no minimum length. A CAP_NET_ADMIN caller can send a 16-byte NFSD_A_SOCK_ADDR with sa_family=AF_INET6, causing a 12-byte OOB read across three consumers (rpc_cmp_addr_port, svc_find_listener, kernel_bind)."

The fix introduces an nfsd_nl_validate_listeners() helper that performs a single pre-validation pass over the entire listener list before any mutation occurs. Each entry must:

  • Parse successfully as a nested netlink attribute
  • Carry both an address and a transport name
  • Be long enough for its declared address family (sizeof(struct sockaddr_in) for AF_INET, sizeof(struct sockaddr_in6) for AF_INET6, -EAFNOSUPPORT otherwise)

Layton emphasized the design principle behind the restructuring:

"Call it before taking nfsd_mutex or creating the serv, so a malformed request fails cleanly with no side effects."

The v5 changelog highlights the key evolution from earlier versions:

  • v4 → v5: "Vet the entire listener list before making any changes"
  • v3 → v4: "Drop policy floor and do full inline validation"

The prior code had parsed and validated entries in two separate loops interleaved with mutations to the running listener configuration, using an open-coded nla_len < sizeof(struct sockaddr) check that was too short for AF_INET6 (28 bytes vs. the 16-byte minimum of struct sockaddr). The new approach drops all redundant per-entry checks from both loops since validity is guaranteed by the upfront pass.

The patch touches a single file (fs/nfsd/nfsctl.c) with 65 insertions and 12 deletions, and carries an Assisted-by: Claude:claude-opus-4-8 tag.

Key Technical Arguments

  1. Pre-validation vs. inline validation: The core design decision in v5 is to separate validation from mutation entirely. Earlier versions (v3, v4) attempted inline per-entry checks within the existing loops, which led to duplicated logic and inconsistent error handling depending on which loop first noticed a malformed entry. The v5 approach — walk once, validate all, then mutate — eliminates that class of bug.

  2. Per-family minimum length: The fix correctly uses sizeof(struct sockaddr_in) (16 bytes) for AF_INET and sizeof(struct sockaddr_in6) (28 bytes) for AF_INET6, rather than the generic sizeof(struct sockaddr) (2 bytes) which was the original insufficient check. This closes the 12-byte OOB read window that existed when a 16-byte buffer declared AF_INET6 was passed to consumers expecting 28 bytes.

  3. Three affected consumers: The OOB read spanned rpc_cmp_addr_port, svc_find_listener, and kernel_bind — all of which dereference the sockaddr beyond its actual length when the family field indicates a larger structure than what was actually provided.

Implications for NFS Client Development

This is primarily a server-side hardening fix with limited direct client impact, but it is relevant to client developers in two ways:

  • Netlink-based listener management: Any userspace tool or daemon that configures nfsd listeners via the NFSD_A_SOCK_ADDR netlink attribute (e.g., container runtimes, cloud-init scripts) now gets a clean -EINVAL/-EAFNOSUPPORT error on malformed input rather than triggering an OOB read in kernel space. This is a security-relevant fix for any CAP_NET_ADMIN caller.

  • No client-visible behavior change: The fix does not alter the NFSv3/v4 wire protocol, delegation semantics, or any client-facing RPC behavior. Clients that were previously working with correctly-formed listener configurations are unaffected.

Status
