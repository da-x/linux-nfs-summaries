sunrpc: Re-attempted fix for shift-out-of-bounds in xprt_calc_majortimeo (UDP timeout)

Summary

sunrpc: Fix shift-out-of-bounds for majortimeo (UDP transport)

Overview

This week brought a new patch to the linux-nfs list addressing a long-standing shift-out-of-bounds bug in the SUNRPC transport layer's major timeout calculation. The thread is currently a single-message submission with no replies yet, but it revives an issue that has been known since at least December 2020.

The Patch

zhangjian (CG) from Huawei submitted a fix on June 12 targeting net/sunrpc/xprt.c (9 insertions, 3 deletions):

"For UDP proto, to->to_exponential is true. Too large to_retries may cause shift-out-of-bounds error for 'majortime <<= to_retries'. Add sanity checks to fix it."

The bug affects the NFS/SUNRPC client's transport timeout logic. When using the UDP protocol, the to_exponential flag is set, causing the major timeout to be computed via a left-shift by to_retries. If to_retries grows large enough (≥ BITS_PER_LONG), the shift exponent overflows, triggering a UBSAN shift-out-of-bounds warning and potentially producing an incorrect (zeroed or wrapped) timeout value.

Classification: Bug Fix

This is a bug fix for a correctness issue in the NFS client's RPC transport layer — not a new feature or protocol change. The affected code path (xprt_calc_majortimeo) determines how long the client waits before declaring a major timeout and retrying an RPC, which directly impacts NFS client reliability over UDP transports.

Historical Context

This is notably not the first attempt to fix this bug:

  • December 2020: syzbot reported the issue with a full UBSAN trace showing shift exponent 536871232 is too large for 64-bit type 'long unsigned int' at net/sunrpc/xprt.c:658. The call trace showed the path from nfs_get_tree → rpc_create → xprt_reserve → xprt_calc_majortimeo.

  • December 2020: Randy Dunlap submitted a patch that capped the retry count:

    "If to_exponential is true and to_retries is >= BITS_PER_LONG, this will cause an invalid shift value when calculating the new majortimeo value. In this case, when to_retries >= BITS_PER_LONG, cap (new local) retry at BITS_PER_LONG - 1 and continue."

  • April 2021: Kurt Manucredo also submitted a patch with the same UBSAN report reference, fixing the same line in xprt_calc_majortimeo().

The fact that this 2026 patch from Huawei revisits the same fix suggests either the earlier patches were never merged or the code was restructured in a way that reintroduced the vulnerability. The new patch's diff (12 lines changed, same file) is consistent with the approach Randy Dunlap outlined — adding a bounds check before the shift operation.

Current Status

As of the end of this reporting week, the thread has no replies from maintainers (Trond Myklebust, Anna Schumaker, or Chuck Lever). The patch awaits review and potential merge into the SUNRPC/NFS client subsystem. Given the bug's age (5+ years) and its origin in a syzbot report, it would be notable if this fix finally lands in mainline.

Significance for NFS Client Development

The xprt_calc_majortimeo function is on the critical path for every RPC request timeout calculation in the SUNRPC layer. A shift-out-of-bounds here could:

  • Produce a zero or wrapped timeout value, causing either immediate spurious retries or effectively infinite waits
  • Trigger UBSAN warnings in hardened kernels, potentially panicking in configurations with UBSAN_TRAP=y
  • Affect NFS-over-UDP mounts specifically (TCP uses the linear to_increment path)

This fix is a small but important robustness improvement for the NFS client's transport layer.
