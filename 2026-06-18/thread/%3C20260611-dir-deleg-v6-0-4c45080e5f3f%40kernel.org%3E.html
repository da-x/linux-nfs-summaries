Summary

CB_NOTIFY Directory Delegation v6 — Review Sweeps Patches 10–20

Overview

This week the CB_NOTIFY directory-delegation thread moved from posting to deep review. After Jeff Layton posted the v6 NFSD series on June 11 — a 20-patch set adding RFC8881bis CB_NOTIFY callback support to Linux nfsd for directory delegations, targeted at v7.3 — Chuck Lever resumed his in-order review within hours with a wire-safety finding on patch 02/20 (an XDR enum leak via NFS4ERR_FIRST_FREE).

On June 12, Lever swept through the remaining unreviewed patches in one concentrated burst, posting eight review messages covering patches 10, 11, 15, 16, 17, 18, 19, and 20 of the series. The findings range from a genuine concurrency bug (an unlocked refcount inc-from-zero in the delegation recall path) to protocol-correctness issues that would break future order-aware clients, to several nits and latent hazards. Layton responded within about an hour on the most serious item, agreeing with the fix direction.

This is primarily new-feature development (the CB_NOTIFY dir-delegation callback), but this week's review surfaced a cluster of bug fixes that will need to be folded into v7: the refcount race, the stale ncn_encode_err flag, an order-aware-client spec violation in the notify-mask negotiation, and a size-budgeting bug that can leave clients without a granted stateid.

Bridge from Prior Week

As summarized last week, the v6 repost already folded in Lever's earlier findings (the rename TOCTOU race, the RCU UAF on fi_deleg_file, and a lease-type check). Layton's gating condition for upstream merge was restated:

"I don't think we'll want to merge these until we have a complete client-side implementation to test against."

That caveat remains in force and is the reason this feature is still landing server-first with the client on the critical path.

Key Technical Arguments

Patch 10/20 — The refcount race (the week's headline finding)

Lever's review of patch 10/20 is the most technically significant message of the week. He identified three distinct problems in the new notification-handler code:

  1. A stale ncn_encode_err flag. The flag "is zeroed only once, at allocation time in alloc_init_dir_deleg(). It is never cleared in nfsd4_cb_notify_prepare()." Because the callback can be requeued while in flight, a clean encode followed by a stale error observation would cause the server to "discard a good notification and recall the delegation unnecessarily."

  2. An unlocked refcount inc-from-zero. This is the core bug:

    "nfsd_break_one_deleg() does an unconditional refcount_inc(&dp->dl_stid.sc_count), and its comment justifies this with 'the lease code is serialized by the flc_lock.' That invariant holds when called from nfsd_break_deleg_cb() under flc_lock, but nfsd4_cb_notify_prepare() runs on a workqueue WITHOUT flc_lock."

    Lever noted that "the delegation can be concurrently destroyed with sc_count already at zero, making this an inc-from-zero," and pointed out that the dispatch path nfsd4_run_cb_notify "already does this correctly with refcount_inc_not_zero" — the out_recall: path just needs the same guard.

  3. The overflow branch becomes a live path. Lever observed that the final patch in the series rewrites the queue-size guard from if (count > NOTIFY4_EVENT_QUEUE_SIZE) to if (count > limit) with limit = NOTIFY4_EVENT_QUEUE_SIZE - 1, which "turns the previously-dead overflow branch into a live, routine path to out_recall, which adds another normal-operation route into this unlocked recall."

Layton responded within ~45 minutes, accepting all three points. On the refcount race he confirmed the fix direction:

"I think we need to do a refcount_inc_not_zero() in nfsd_break_one_deleg() and just return without queuing the callback if it's already at 0. That means that the recall is racing with the lease teardown, so I think the right thing to do is to not send the recall in that case."

On the stale flag he simply agreed: "Ok, so we need to reset this in ->prepare."

Patch 11/20 — Order-aware client spec violation

Lever's review of patch 11/20 flagged a protocol-correctness issue in the notify-mask negotiation. When a client requests NOTIFY4_GFLAG_EXTEND | NOTIFY4_CFLAG_ORDER plus ADD/REMOVE/RENAME, the patch "still grants the content notification bits because it only requires GFLAG_EXTEND." The problem:

"The rest of NFSD's CB_NOTIFY encoder does not store that order-aware request and emits zero/absent cookie and previous-entry information, which is only safe for order-unaware clients. An order-aware client can then keep an ordered directory cache from unusable notifications instead of having the delegation recalled."

Lever cited the bis draft directly (sections 27.4.5, 16.2.13, and 16.2.11.3) to show that "GFLAG_EXTEND set PLUS CFLAG_ORDER set is also order-aware," and concluded: "This finding is latent when this patch is first applied, but the NFSD's negotiation is incorrect for any future order-aware client." He noted he did not see the issue addressed by a subsequent patch in the series.

Patch 15/20 — Latent NULL deref on FSID encoding

Lever's review of patch 15/20 was a smaller finding: after making filehandle encoding svc_fh-free, the FSID encoder still calls fsid_source(args->fhp) without a NULL check, and both share the same attrmask gate. "No current caller trips it: the CB_NOTIFY path does not request FSID. But a future CB_NOTIFY attrset that adds FSID would dereference a NULL fhp."

Patch 16/20 — Shared nfs4_file connectability hazard

Lever's review of patch 16/20 flagged that when two clients use exports of the same directory root differing only in subtree_check/no_subtree_check, "the root filehandle is the same and nfsd4_file_hash_insert() can reuse the same nfs4_file." This makes fi_connectable depend on whichever export first initialized the shared object. Lever's recommendation: "the delegation's sc_export is the per-export state to derive connectability from, and the export is already available via dp->dl_stid.sc_export."

Patch 17/20 — Signed filehandle MAC (confirming a prior fix)

Lever's review of patch 17/20 confirmed that the signed-filehandle fix from last week's review was correctly carried into v6. He noted: "Codex flagged setup_notify_fhandle() for constructing a child FILEHANDLE attribute without calling fh_append_mac()." The fix — signing the constructed handle or suppressing the attribute when the export requires signed filehandles — is client-visible: "A client that does not receive the FH falls back to a LOOKUP, so suppression degrades gracefully."

Patch 18/20 — Size-budgeting bug (client-impacting)

Lever's review of patch 18/20 identified a reply-size bug: when a client requests any supported child attribute in word 1, "nfsd4_encode_bitmap4() emits a two-word bitmap. nfsd4_get_dir_delegation_rsize() still budgets only the old one-word child-attribute bitmap before executing this non-idempotent op." The consequence is directly client-visible:

"a compound near the reply/slot limit can grant a directory delegation and then fail encoding with NFS4ERR_RESOURCE/REP_TOO_BIG, leaving the client without the returned stateid."

Patch 19/20 — Bisectability / premature feature advertisement

Lever's review of patch 19/20 raised a bisectability concern: after this patch, "a client that requests NOTIFY4_CHANGE_DIR_ATTRS now gets that bit echoed in gddr_notification, but the callback path still only maps/encodes add, remove, and rename notifications." His conclusion: "That lets the server grant a directory delegation while promising dir-attribute CB_NOTIFYs it cannot send until the follow-up support lands, so this bit should not be advertised in this patch." He also added a minor type nit: "Maybe these should be u32. uint32_t is a user space type."

Patch 20/20 — Queue overflow livelock and export UAF

Lever's review of patch 20/20 was the longest and most detailed. He identified:

  • A queue overflow livelock: "the CB_NOTIFY event queue can fill to NOTIFY4_EVENT_QUEUE_SIZE (3) events while the consumer only accepts 2 (it reserves a slot for the dir-attr-change entry). The resulting overflow path in nfsd4_cb_notify_prepare() recalls the delegation without draining the queue, and nfsd4_cb_notify_release() then requeues the same callback indefinitely."

  • An export use-after-free: "The function dereferences the new exp parameter unconditionally... An in-flight CB_NOTIFY callback holds a sc_count reference but NOT an export reference. drop_stid_export() can run concurrently (admin revoke / unexport), NULL sc_export, and drop what may be the last export reference, freeing the svc_export while the callback dereferences it."

  • A minor XDR rollback nit: when nfsd4_encode_dir_attr_change() returns NULL after a successful xdr_reserve_space(), "the 4-byte reservation is never rolled back and *maskp is never written, yet the function still takes the success path." Lever noted this is "probably benign only because nfs4_xdr_enc_cb_notify re-encodes from the ncn_nf[] array."

  1. Week of May 15 — VFS-side patches merged.
  2. Week of May 28 — v4/v5 NFSD series posted; Lever begins review, punts to v7.3.
  3. Week of June 5–11 — Lever's deep-dive review of v5 patches 04–10 (TOCTOU, RCU UAF, lease-type check).
  4. Week of June 11 (prior summary) — v6 repost incorporating all reviewed fixes; Lever flags XDR enum leak on patch 02/20.
  5. This week (June 12) — Lever completes review of patches 10–20 in a single day, surfacing 8 distinct findings across concurrency, protocol correctness, size budgeting, and UAF categories. Layton responds to the most critical item (the refcount race) within an hour, confirming the fix.

The review is now essentially complete for v6 — all 20 patches have received Lever's scrutiny. The remaining work is for Layton to produce a v7 incorporating this week's fixes.

Implications for NFS Client Development

  • The order-aware client spec violation (patch 11/20) is the most forward-looking finding. Any future Linux client implementing NOTIFY4_CFLAG_ORDER would receive notifications it cannot use to maintain its ordered directory cache, and — worse — would not get a delegation recall as the spec requires. This must be fixed server-side before any order-aware client ships.

  • The size-budgeting bug (patch 18/20) is directly client-visible. A client near the reply/slot limit could grant a directory delegation and then receive NFS4ERR_RESOURCE with no stateid, leaving it in an inconsistent state. Client code would need to handle this as a transient error, but the fix should eliminate the case entirely.

  • The export UAF (patch 20/20) is a server-side crash risk that could manifest as a client-visible connection reset or stale-handle storm during admin operations (unexport/revoke) while CB_NOTIFY callbacks are in flight.

  • Layton's testing caveat remains the gating dependency: "I don't think we'll want to merge these until we have a complete client-side implementation to test against." The v7.3 timeline gives both sides roughly a full merge cycle, but the client work is on the critical path.
