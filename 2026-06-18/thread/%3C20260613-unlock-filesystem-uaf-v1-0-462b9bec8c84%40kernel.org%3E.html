NFSD: Fix post-shutdown use-after-free in the unlock_filesystem paths

Summary

NFSD: Fix post-shutdown use-after-free in the unlock_filesystem paths

This week's activity on this thread was short but consequential: a three-patch bug-fix series from Chuck Lever addressing a local-admin-triggerable use-after-free in the NFS server (NFSD), followed by a quick review from Jeff Layton. The series landed without any technical pushback, and the discussion is now effectively closed pending merge.

Nature of the change: a security-adjacent bug fix

This is squarely a bug fix, not a feature or protocol change. As Chuck Lever framed it in the cover letter:

"Musaab Khan reported that a local administrator holding CAP_SYS_ADMIN can trigger a use-after-free in nfsd by writing a filesystem path to /proc/fs/nfsd/unlock_filesystem after the server has been stopped."

The root cause is an ordering bug. Both the procfs unlock_filesystem handler and the NFSD_CMD_UNLOCK_FILESYSTEM netlink command called nfsd4_cancel_copy_by_sb() before taking nfsd_mutex and before confirming that nn->nfsd_serv was still set. Once the server had shut down, nfs4_state_destroy_net() had already freed nn->conf_id_hashtbl but left the pointer intact, so:

"the cancel helper walks freed slab memory as an array of struct list_head and then dereferences a bogus nfs4_client when it takes clp->async_lock. KASAN reports a slab-use-after-free read in nfsd4_cancel_copy_by_sb()."

The fix is conceptually simple: the async COPY cancellation was added ahead of the existing protected section (which nfsd4_revoke_states() already uses), so it "escaped the guard." Moving the cancel inside the nfsd_mutex-held, nn->nfsd_serv-confirmed region closes the hole. Chuck notes that this is safe because "Async copies exist only while the server runs, so gating the cancel on nn->nfsd_serv loses nothing."

The three patches

  1. PATCH 1/3 — fixes the procfs unlock_filesystem path in fs/nfsd/nfsctl.c. Carries a Reported-by: for Musaab Khan and a Fixes: tag pointing at commit 3daab3112f03 ("nfsd: cancel async COPY operations when admin revokes filesystem state"), which introduced the buggy ordering.

  2. PATCH 2/3 — applies the same reordering to the NFSD_CMD_UNLOCK_FILESYSTEM netlink path. Chuck notes this one is forward-looking:

    "The netlink command that patch 2 corrects, 327c5168eff2 ("NFSD: Add NFSD_CMD_UNLOCK_FILESYSTEM netlink command"), has not yet reached mainline; it sits in nfsd-next, destined for v7.2. Patch 2 therefore applies to nfsd-next, not to a released kernel, and needs no stable backport."

  3. PATCH 3/3 — hardening: adds lockdep_assert_held(&nfsd_mutex) to the state-table walkers and documents the precondition in a Context: kdoc section. The stated goal is to "so a future caller added to this path cannot silently reintroduce the same use-after-free."

The series touches three files (fs/nfsd/nfs4proc.c, fs/nfsd/nfs4state.c, fs/nfsd/nfsctl.c) for a net +29/-7 lines.

Review and outcome

Three days later, Jeff Layton posted a brief but decisive endorsement:

"This all looks good. Reviewed-by: Jeff Layton jlayton@kernel.org"

No other in-window messages were exchanged, so the thread is at the point of awaiting merge into nfsd-next. (Two follow-up messages from XIAO WU and Chuck Lever appear on 2026-06-21, outside this week's window, and will be covered in next week's summary.)

Why it matters for NFS developers

While the bug lives on the server side rather than the client, it is a reminder of how NFSD's state-table walkers — shared infrastructure that both unlock_filesystem and the new netlink admin interface depend on — require strict locking discipline. The addition of lockdep assertions in patch 3 is a useful long-term guardrail for anyone extending these paths, and the fact that the same latent bug existed on two independent entry points (procfs and netlink) underscores how easy it is to slip past an existing mutex-protected region when adding new callers.
