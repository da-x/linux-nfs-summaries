Summary

nfsd: Three Follow-On Bug Fixes for CB_NOTIFY Directory Delegation Support

Overview

On June 17, Jeff Layton posted a three-patch series titled "nfsd: follow-on fixes for CB_NOTIFY support," addressing defects in the recently reviewed RFC 8881bis CB_NOTIFY directory-delegation callback code. The series is squarely a bug-fix effort — three distinct concurrency and correctness issues in the server-side callback path that were surfaced during review of the v6 NFSD series earlier this week.

"These are just some problems that Sashiko pointed out in review that seem to be valid concerns." — Jeff Layton, cover letter

The patches target fs/nfsd/nfs4state.c and fs/nfsd/nfs4xdr.c, with 64 insertions and 28 deletions across the two files. Layton noted that the Fixes: tags reference commits from his own tree, so maintainers will need to fold them into the appropriate upstream patches rather than apply them as standalone fixes.

Bridge from Prior Week

As summarized in the CB_NOTIFY dir-delegation v6 thread, Chuck Lever completed his review of all 20 patches in the v6 NFSD series on June 12, surfacing eight distinct findings. Two of those findings — the queue-overflow livelock and the export use-after-free — were specifically called out in Lever's review of patch 20/20. This week's three-patch series addresses those two plus a third protocol-correctness issue (silently dropping requested dir-attr notifications), all in the nfsd4_cb_notify_prepare() / setup_notify_fhandle() code path.

Patch-by-Patch Analysis

PATCH 1/3 — Fix CB_NOTIFY workqueue loop when queue overflows

Jeff Layton's first patch fixes a livelock in the callback workqueue. The root cause is an off-by-one between the producer and consumer of the CB_NOTIFY event queue:

"When NOTIFY4_CHANGE_DIR_ATTRS is requested, nfsd4_cb_notify_prepare() lowers its limit to NOTIFY4_EVENT_QUEUE_SIZE - 1 to reserve a slot for the dir attribute update. The producer in nfsd_handle_dir_event() caps ncn_evt_cnt at NOTIFY4_EVENT_QUEUE_SIZE, so the queue can fill to one more than that limit."

The consequence is severe: when the overflow branch fires, prepare() jumps to out_recall without draining the queue, leaving ncn_evt_cnt nonzero. The release op then requeues the callback, which hits the same overflow check again — spinning a workqueue thread forever while pinning an stid reference so the delegation is never freed:

"Returning false from prepare causes nfsd41_destroy_cb() to run the release op, and nfsd4_cb_notify_release() requeues the callback whenever ncn_evt_cnt > 0. The requeued callback hits the same overflow check and recalls again, spinning a workqueue thread forever."

The fix drains queued events (dropping their references) and resets ncn_evt_cnt before recalling, and additionally guards the release-side requeue against a revoked delegation:

"Also guard the release-side requeue against a revoked delegation: there is no point notifying a client that no longer holds the delegation, and skipping the requeue avoids pinning the stid and spinning the workqueue."

This was first identified by Lever in his patch 20/20 review, who described it as a "queue overflow livelock."

PATCH 2/3 — Fix NULL deref / UAF of sc_export in setup_notify_fhandle

The second patch addresses a use-after-free and NULL pointer dereference in setup_notify_fhandle(). The function read dp->dl_stid.sc_export locklessly and dereferenced it unconditionally in the subtree-check branch, even though the code later acknowledged with an if (exp && ...) guard that the pointer could be NULL.

The race window is narrow but real: CB_NOTIFY callbacks run asynchronously holding only an sc_count reference. While nfs4_put_stid() keeps the export alive until sc_count reaches zero, the admin-revocation path (drop_stid_export() via revoke_one_stid()) clears sc_export and drops its reference independently of sc_count, under cl_lock:

"A concurrent revocation can therefore make the lockless read return NULL (NULL deref in the subtree-check branch) or a pointer that exp_put() frees mid-encode (use-after-free)."

The fix grabs a reference to the export under cl_lock — mirroring the locking discipline already used in drop_stid_export() — and guards every use of exp with a NULL check. This was also flagged by Lever in his patch 20/20 review.

PATCH 3/3 — Recall delegation if a requested dir attr change can't be encoded

The third patch fixes a protocol-correctness bug: when the client requested NOTIFY4_CHANGE_DIR_ATTRS, the server could silently fail to encode the directory attribute change (due to attrmask space reservation failure, buffer exhaustion, or an encode error) and still transmit a CB_NOTIFY lacking the requested notification. The result was that "the client's cached directory attributes [would be] stale with no indication."

Layton cites the RFC directly:

"RFC 8881 s10.4 requires the server to recall the delegation when it cannot deliver a requested notification."

The fix treats a failure to encode the dir attribute change identically to the per-event encode failures already handled in the loop above — setting an error and falling through to out_recall. This ensures the client is properly notified that its cached directory attributes are no longer valid.

Significance for NFS Client Development

All three fixes are server-side, but their impact on clients is direct:

  • The livelock (patch 1/3) would manifest as a hung server with an unresponsive delegation — the client would see no recalls and no notifications indefinitely, while the server burns CPU. This is the kind of bug that can only be caught under sustained directory-event load.
  • The UAF (patch 2/3) is a crash risk during admin operations (unexport, revoke) while CB_NOTIFY callbacks are in flight. A client would see connection resets or stale-handle storms.
  • The silent notification drop (patch 3/3) is the most insidious: without the fix, a client maintaining a cached directory view could operate on stale attributes with no way to detect the staleness until it performs an explicit GETATTR.

These fixes are prerequisites for the client-side implementation that Layton has identified as the gating dependency for upstream merge:

"I don't think we'll want to merge these until we have a complete client-side implementation to test against." — Layton, prior week
