nfsstat: new patch to display NFSv4 callback operation statistics

Summary

nfsstat: New Patch to Display NFSv4 Callback Operation Statistics

Type: New feature (userspace tooling) — v1 posted, no replies yet this week
Week ending: 2026-06-18
Status: Posted; awaiting maintainer review.

This Week's Activity

On Thursday, June 18, Red Hat's Jeff Layton posted a follow-up nfs-utils patch that extends the nfsstat tool to display NFSv4 backchannel (callback) operation statistics: [PATCH nfs-utils] nfsstat: display NFSv4 callback operation statistics. The thread is brand new — this single message is the only in-window activity, and no replies have landed yet.

The patch adds a new "Server nfs v4 callback operations" section to nfsstat output that reports per-operation call counts for the callbacks the server sends to clients (from OP_CB_GETATTR through OP_CB_OFFLOAD). It touches two files: support/include/nfsd_netlink.h (+1) and utils/nfsstat/nfsstat.c (+46/−3).

Key Technical Arguments

The patch description lays out three design points worth highlighting:

  1. Netlink-only data source. The callback counters exist only in the new netlink dump, not in procfs:

    "The data is only available over netlink -- the /proc interface exposes nothing equivalent (only the single wdeleg_getattr line, which corresponds to CB_GETATTR) -- so the section is displayed solely when the stats were fetched via netlink."

    The code detects this by checking srvproc4cbinfo[0] being non-zero — a value the netlink handler sets from the entry count and that the /proc parsers never touch.

  2. Opcode-indexed counters. Because the kernel indexes its counters directly by RFC 8881 callback opcode, the userspace name array must keep alignment:

    "The counters are indexed directly by RFC 8881 callback opcode, so the name array carries placeholders for the unassigned opcodes 0-2 to keep the array index aligned with the opcode value, mirroring the kernel's cb_counter layout."

  3. Tied to a new kernel feature. Layton explicitly frames this as the userspace counterpart to freshly-reviewed kernel work:

    "After the most recent review, we decided to add server side callback counts as a new feature for nfsstat."

Bridge from Prior Weeks (brief)

This patch is the second leg of a closely coupled two-part effort that has been in flight since late May:

  • Week ending 2026-05-28: Layton posted v1 of the netlink fetch support for nfsstat alongside the companion kernel series converting nfsd/sunrpc server-side interfaces to netlink.
  • Week ending 2026-06-04: Steve Dickson committed that first userspace patch into nfs-utils (tag nfs-utils-2-9-2-rc4), noting it "went in cleanly on its first posting" thanks to the graceful procfs fallback.
  • This week: The companion kernel series reached v5 on June 18, with the stated main difference being "the addition of server callback operation counts." Layton's cover letter explicitly flags that he would be "sending another nfs-utils patch to add support for displaying those in nfsstat" — this thread is that promised follow-up, posted just ~25 minutes after the kernel v5.

Related Kernel-Side Context (same day)

Worth flagging for readers: the kernel v5 series that motivates this userspace patch received substantive review feedback from Chuck Lever on June 19 (just outside this window):

  • On PATCH v5 5/6 (counting callback ops per netns), Lever wrote:

    "I agree with the Sashiko review that this patch introduces a UAF possibility that needs to be addressed before the patch is applied."

    This means the kernel-side counter infrastructure on which the userspace display depends is not yet in a mergeable state.

  • On PATCH v5 6/6 (exporting callback op stats via netlink), Lever raised a semantic concern:

    "Opcodes nfsd never sends correctly report 0. The exception is op 11 / CB_SEQUENCE: it's written by encode_cb_sequence4args() on every minorversion>0 callback, so it goes out on the wire but is never counted... which could be misread as 'none sent' rather than 'not tracked.' Check what the forechannel counter does for SEQUENCE operations."

These kernel-side issues do not block the userspace patch per se (it simply displays whatever the netlink dump provides), but they mean the new nfsstat section will only become meaningful once v6 of the kernel series resolves the UAF and the CB_SEQUENCE accounting question.

Significance for NFS Client Development

Although this is server-side tooling, it has direct relevance to NFS client developers working on delegation-related code paths:

  • The new counters expose per-opcode volumes for CB_GETATTR, CB_RECALL, CB_SEQUENCE, CB_CONFIRM, and (eventually) CB_OFFLOAD — exactly the backchannel traffic that a client's delegation handling must respond to.
  • In particular, the kernel patch replaces the old wdeleg_getattr procfs counter with a more accurate CB_GETATTR count: as Layton explains in the kernel commit message, "the old counter incremented on every such conflict, whereas the CB_GETATTR counter only counts callbacks that are actually queued, so concurrent conflicts that coalesce onto an already in-flight CB_GETATTR are now counted once rather than once per conflict." Client-side developers tuning delegation-conflict behavior will want this refined metric.
  • Combined with the namespace-aware netlink path (already merged into nfs-utils), this gives containerized NFS deployments a way to observe per-netns callback traffic — useful when debugging client-visible delegation recall storms or backchannel congestion in multi-tenant environments.

Conclusion

A single, clean v1 posting from Layton extending nfsstat with a new callback-operations section. No review comments yet this week; the patch is small (+46/−3) and rides on infrastructure already merged into nfs-utils. The real gating factor is the companion kernel series (v5), which Chuck Lever has flagged for a UAF fix and a CB_SEQUENCE accounting question — expect v6 of that series to be the next milestone before this userspace feature becomes useful in production.
