NFS Direct I/O modernization (v2): pin-aware, folio-based path for P2PDMA

Summary

NFS Direct I/O Modernization (v2) — pin-aware, folio-based path as groundwork for P2PDMA

Type: New feature / architectural refactor of the NFS client direct-I/O path (not a protocol change). It is explicitly preparatory work to enable PCI Peer-to-Peer DMA (P2PDMA), and it incidentally fixes two real bugs in the existing direct-I/O code.

The submission

On Tuesday, Pranjal Shrivastava (Google) posted [PATCH v2 0/7] "nfs: Modernize Direct I/O path"](https://lore.kernel.org/linux-nfs/20260616134000.2733403-1-praan@google.com/), a seven-patch series that reworks how the NFS client handles O_DIRECT. The stated goal is to move off the legacy page-extraction API onto the modern one, and to make requests folio-based rather than page-based:

"Currently, NFS O_DIRECT relies on the legacy iov_iter_get_pages_alloc2() API which does not support the pinning requirements for P2P memory. The implementation moves NFS to the modern iov_iter_extract_pages() API and migrates NFS direct I/O away from pages to use folios."

The series is structured for bisectability: patches 1–2 add pin-aware infrastructure (PG_PINNED flag + wb_nr_pinned count on struct nfs_page), patch 3 adds a centralized nfs_release_request_list() helper, patch 4 performs the actual API migration, patches 5–6 introduce the extraction helper and folio grouping, and patch 7 deletes the now-orphaned page-based helper.

Bug fixes carried in v2

This is the second revision (v1 was posted June 3). The cover letter's changelog calls out two genuine correctness fixes from the first round:

"Fix data corruption in nfs_direct_extract_pages() by correctly calculating intra-page offsets using offset_in_page(). Fix requested_bytes accounting in direct read/write paths to only increment after successful RPC scheduling."

The second fix is also reflected in patch 4, which notes that the old loop had a latent defect: "The migration fixes a bug in the Direct I/O loop where pages were being unpinned immediately after request creation. With the new extraction model, pins are held until the I/O is complete." So alongside the modernization, the series corrects an early-unpin bug and a bytes-accounting race.

Pranjal included an extensive xfstests matrix (26 generic tests) across RDMA and TCP transports at NFSv3/v4.0/v4.1/v4.2 — all passing or appropriately skipped. He also posted a small follow-up adding the missing link to his test-display script (display.py).

The central technical dispute: is page_folio() safe here?

The substantive review debate focused on patch 6/7, "Optimize direct I/O to use folios for requests", which groups contiguous pages from the same folio into a single nfs_page. Trond Myklebust (NFS client maintainer) pushed back hard on the core assumption:

"I'm clearly missing something. The memory pointed to by these pages can be any arbitrary user space (or kernel space) memory region. It could be mapped device memory, for instance. So why can you assume that page_folio() will resolve to a valid folio here?"

Pranjal responded at length, arguing the MM subsystem guarantees it:

"AFAIU, the MM subsystem explicitly ensures that every valid struct page is part of a folio... Since iov_iter_extract_pages() only returns pages that are successfully pinned and tracked by the kernel, we are guaranteed that pagevec[i] points to a valid struct page and thus a valid folio."

He added that ZONE_DEVICE pages now support folios, that page_folio() degrades gracefully to a size-1 folio for non-compound pages, and that GUP pinning prevents the folio from being split or freed under NFS. He also noted that device memory without a backing struct page (dmabuf / PFN mappings) is already unsupported for NFS direct I/O today — "The underlying page pinning (GUP) would fail with -EFAULT in check_vma_flags() even before reaching this point."

Reviewers push back: it's a minefield

Christoph Hellwig and Matthew Wilcox — both MM/block veterans who have wrestled with the same problem elsewhere — pushed back on that confidence. Hellwig wrote:

"It is definitively not what the vision for the folio is, although if I'm not mistaken it actually is still true right now. This whole area is a minefield unfortunately, and we also ran into it with iov_iter_extract_bvecs and the earlier block code it was extracted from... for now your best bet is to stick to what the block code does or even better reuse as much as possible of that code."

Wilcox sharpened the point in reply:

"It's not true, eg, for slab. While there's still a struct page there for slab, there's no refcount and flags like PG_locked have different meanings. You'll get into a lot of trouble trying to treat slabs as folios (and that will include assertions tripping)."

"Fundamentally, it is no business of the filesystem what the iov_iter refers to. We can do direct io to slab memory, vmalloc memory, memory that doesn't have a struct page (eg iomem), or whatever we choose."

The reviewers' consensus guidance: rather than relying on the (fragile) "every page is a folio" invariant, NFS should mirror — and ideally reuse — the block layer's extraction logic, which already handles this correctly.

Two secondary review notes

  • Process / CC list: Chuck Lever suggested that, because the series is groundwork for P2PDMA, Pranjal should add linux-rdma@vger.kernel.org and linux-pci@vger.kernel.org (the latter per MAINTAINERS) when reposting.
  • Test coverage: Hellwig questioned whether the 26-test xfstests subset was enough: "Did you only run these tests that previously failed for Anna or all of xfstests, which should give you much better coverage?"

Where things stand (end of week)

The thread is open and unresolved as of Friday. The pin-aware infrastructure, the API migration, and the two bug fixes are uncontroversial; the open question is whether patch 6's folio-grouping logic is safe across all iov_iter sources, with the maintainers steering toward reusing block-layer extraction code rather than relying on the page-is-a-folio invariant. No ACK or merge decision has been recorded this week. (For context, this series later evolved into v3 and v4 postings in July/August 2026.)
