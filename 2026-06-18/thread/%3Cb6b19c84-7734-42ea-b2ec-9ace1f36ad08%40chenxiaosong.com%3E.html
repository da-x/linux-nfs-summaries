CHANGES patch in netfs bvecq v4: Howells admits forgotten fold-down

CHANGES patch in netfs bvecq v4: Howells admits the final patch was never folded down

Week ending 2026-06-18 — a single-message thread, but it lands at a tense moment in the larger netfs/bvecq saga.

The exchange in one breath

This thread is a two-line Q&A that grew out of David Howells' 30-patch v4 series to replace folio_queue, rolling_buffer and ITER_FOLIOQ with a segmented chain of bio_vec[] arrays (bvecq) in netfslib. The series is the fourth iteration of work that began as a 17-patch RFC in late March, was formally submitted on March 26, trimmed to 21 patches in v2 (May 18), expanded to 22 patches in v3 (June 8), and now arrives rebased onto v7.1 with ~40 new bug fixes — most of them reported by the Sashiko static-analysis tool.

The thread itself is anchored on patch 30/30 "CHANGES", which — as its subject suggests — was supposed to be the series' change-log, but shipped with only a git diff --stat and no commit message body:

"Is this patch missing the subject and commit message?" — ChenXiaoSong

Howells replied within three hours, candidly:

"No. I got distracted and forgot to finish folding its contents down into earlier patches." — David Howells

That's the whole thread. No code, no protocol change, no new feature — just a process slip in an otherwise enormous submission.

Why this tiny exchange matters for NFS client readers

The "CHANGES" patch is the kind of artifact that exists to give reviewers a single place to read what changed between versions. Its accidental emptiness is small, but it lands at exactly the moment when the series is already under fire from Christoph Hellwig, who objected on the same day to the merge-window timing and review status:

"Really? Not only are we in the merge window, but this is gigantic unreviewable series, which consequently has none of the relevant reviews." — Christoph Hellwig

Hellwig went on to ask Howells to split out smaller, independently reviewable pieces:

"Please try to work like everyone else and split out useful parts. E.g. if your new iter type is useful there must be smaller standalone candidates for it that can explain the use. Having to wade through all of netfs to try to understand it is not really going to fly." — Christoph Hellwig

In that context, a missing change-log on the final patch is a small but telling data point: the series is so large that even its own bookkeeping has slipped.

What the v4 series actually contains (NFS-client-relevant highlights)

For readers tracking NFS client development, the v4 series — despite being filed under netfs rather than nfs — touches the NFS client directly through fs/nfs/fscache.c and through every buffered/DIO path that goes through netfslib. The most important items for NFS client developers:

  1. Write-streaming / fscache race fix (patch 01/30). A correctness bug reported by Marc Dionne, surfacing as a warning from the generic/464 xfstest. Howells explains the root cause:

    "Unfortunately, the test netfs_perform_write() uses isn't correct because it doesn't take into account the fact that the object lookup is asynchronous and farmed off to a work queue, so there's a short window in which the cache is doing a lookup but the test fails because the answer is undefined." — David Howells

    The fix changes the condition from "is the fscache cookie enabled?" to "is FSCACHE_COOKIE_IS_CACHING set?", closing a window in which partial folio writes could be issued to the cache without proper DIO alignment. This is a real bug fix for any NFS client using fscache (e.g., with the cachefiles daemon).

  2. Cachefiles double fput() (patch 02/30) — a one-line error-path fix in cachefiles_create_tmpfile().

  3. iov_iter underflow and missing alloc-fail checks (patches 03/30, 04/30) — fixes in iov_iter_extract_xarray_pages() and iov_iter_extract_bvec_pages(), both of which sit on the hot path for NFS reads/writes that go through the new bvecq machinery.

  4. Cachefiles content tracking (patch 09/30). A significant performance win for NFS clients using fscache: a new CACHEFILES_CONTENT_ALL xattr value lets the cache skip SEEK_DATA/SEEK_HOLE on the most common case of contiguous, progressively-written files.

    "In this specific case, given that it is known that there are no holes in the file, there's no need to call SEEK_DATA/HOLE or use any other mechanism to track the contents. That speeds things up enormously." — David Howells

  5. Writeback lock asynchronicity (patch 07/30). Replaces the wb_lock mutex with a bit flag and a waiter list so the collector thread can drop the lock after collection completes, improving writeback throughput for NFS clients.

  6. The core bvecq model (patches 15/30–26/30). The architectural heart of the series: a segmented chain of bio_vec[] arrays with file-position tracking, reference counting, and memory-type flags, plus a new ITER_BVECQ iterator type. Howells' stated goals are consolidation on bio_vec[], unifying buffered and DIO buffering into one scheme, and sending each RPC message in a single kernel_sendmsg() call:

    "Always send an entire filesystem RPC request message to a TCP socket with single kernel_sendmsg() call as this is faster, more efficient and doesn't require the use of corking as it puts the entire transmission loop inside of a single tcp_sendmsg()." — David Howells

    The final patch in the series (29/30) merges ->prepare_read()/->issue_read() (and write variants) into a single callback, fundamentally changing how filesystems interact with netfslib.

Classification

This thread is not about a new feature, a protocol change, or a bug fix in its own right. It is a process/cleanup observation on the tail end of a large refactoring series that does contain both a major feature (the bvecq model) and numerous embedded bug fixes. The thread's only substantive content is Howells' admission that the change-log patch was never finished — a minor blemish on an otherwise substantial submission.

Status as of week end

  • The v4 series has been posted; Hellwig has objected to timing and review coverage; ChenXiaoSong's question about the CHANGES patch has been answered (the contents were meant to be folded into earlier patches but weren't).
  • No Reviewed-by or Acked-by tags have landed on the core netfslib/bvecq patches in this window, though Stefan Metzmacher's Acked-by on the smbdirect patches (carried over from v3) suggests the CIFS integration concerns have been resolved.
  • For NFS client developers, the practical takeaway is unchanged from the main thread: the series, if it lands, will reshape how the NFS client does buffered and direct I/O, with concrete wins in fscache performance and a fixed write-streaming race. Its fate now hinges on whether Howells can address Hellwig's call to split the series into smaller, independently reviewable pieces — and, presumably, to actually finish folding down the CHANGES patch.
