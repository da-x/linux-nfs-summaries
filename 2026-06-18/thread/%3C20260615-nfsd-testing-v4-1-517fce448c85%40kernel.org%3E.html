nfsd: validate sockaddr length per family in listener_set (v4)

Summary

nfsd: validate sockaddr length per family in listener_set — v4 posted

This week's activity on this thread is a single message: Jeff Layton's PATCH v4, posted 2026-06-15. No replies or reviews landed in the window, so the discussion is still at the "patch out for review" stage.

What kind of change this is

This is a bug fix — specifically a security-relevant input-validation fix in the NFS server (nfsd), not a new feature or protocol change. It targets the netlink listener-management path that was introduced by commit 16a471177496 ("NFSD: add listener-{set,get} netlink command"), as noted in the Fixes: tag.

The vulnerability described

Layton's cover letter lays out a concrete out-of-bounds read:

"nfsd_sock_nl_policy declares NFSD_A_SOCK_ADDR as a bare NLA_BINARY attribute with no minimum length. A CAP_NET_ADMIN caller can send a 16-byte NFSD_A_SOCK_ADDR with sa_family=AF_INET6, causing a 12-byte OOB read across three consumers (rpc_cmp_addr_port, svc_find_listener, kernel_bind)."

The root cause is that the existing open-coded check only verified nla_len < sizeof(struct sockaddr) — which is too short to cover an IPv6 address. As Layton puts it:

"This replaces the open-coded 'nla_len < sizeof(struct sockaddr)' check, which was too short for AF_INET6."

The fix in v4

The patch (43 insertions, 6 deletions in fs/nfsd/nfsctl.c) does two things:

  1. Per-family length validation — In both nlmsg_for_each_attr_type loops inside nfsd_nl_listener_set_doit(), the code now first checks that the attribute is large enough to read sa_family, then requires the full family-specific size (sizeof(struct sockaddr_in) for AF_INET, sizeof(struct sockaddr_in6) for AF_INET6), and rejects any other family.

  2. Error reporting instead of silent success — In the listener-creation loop, a malformed or unsupported address was previously skipped, and if it was the only one supplied the call returned 0. The fix sets -EINVAL for too-short addresses and -EAFNOSUPPORT for unsupported families so userspace actually sees the failure:

"In the listener-creation loop, report the error rather than silently succeeding. Previously a malformed or unsupported address was skipped, and if it was the only one supplied the call returned 0."

Evolution across versions

The v4 changelog is terse but informative about how the approach evolved:

"Changes in v4:

  • Drop policy floor and do full inline validation"

This tells us that an earlier revision (v3, linked here) had attempted to enforce a minimum length via the netlink policy ("policy floor"), but v4 abandons that in favor of explicit inline validation in the doit handler. That's a meaningful design shift — moving from declarative policy constraints to imperative per-attribute checks — likely because the policy mechanism couldn't express the family-dependent length requirement cleanly.

Status and outlook

As of the end of this window, the patch has no visible reviewer feedback on the list. The Assisted-by: Claude:claude-opus-4-8 tag indicates AI-assisted development, which is worth noting for context but does not change the technical content. Given that this fixes a CAP_NET_ADMIN-triggerable OOB read in a privileged server path, expect it to be picked up by the security-focused reviewers (Trond Myklebust / Chuck Lever) in the coming days. The fix is small, well-scoped, and has a clear Fixes: tag, so it's a reasonable candidate for stable backport once merged.

NFS client relevance

While this is strictly an nfsd (server-side) change, it matters to client developers and administrators because the listener-set/get netlink interface is what userspace tools use to manage which addresses/ports nfsd listens on. A silent success on a malformed address (the pre-fix behavior) could lead to a server that appears configured but isn't actually listening where expected — a subtle operational trap for anyone scripting NFS server deployment.
