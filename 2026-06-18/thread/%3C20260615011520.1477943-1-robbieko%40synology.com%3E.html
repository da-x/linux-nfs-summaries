nfsd: reject out-of-range nseconds in setattr (v2) — Chuck Lever objects to choke-point placement

Summary

v2 of the nfsd timestamp-validation series; review pushes back on where the check lives

This week's activity picks up a two-patch series from Robbie Ko (Synology) that was originally posted last week as v1 and summarized in the 2026-06-18 thread file. Ko re-posted it on Monday 2026-06-15 as v2, and NFS maintainer Chuck Lever replied the same afternoon with a substantive objection to the design of patch 1/2. This is a data-integrity bug fix (not a new feature, not a protocol change), squarely in NFS server territory, though it has direct consequences for any client that can issue SETATTR or CREATE with a malformed timestamp.

The series in brief

Patch 1/2 rejects out-of-range nseconds in setattr atime/mtime by adding a validation check in nfsd_setattr(), returning NFS3ERR_INVAL (mapped to nfserr_io for NFSv2 via nfsd_map_status()). Patch 2/2 replaces the open-coded (u32)1000000000 literal in nfsd4_decode_nfstime4() with the named constant NSEC_PER_SEC, a readability-only change with "No functional change."

The bug (recap, from v1)

Ko's cover note re-states the core problem:

"A client can send a SETATTR (and, for NFSv3, a file creation) carrying an atime or mtime whose nseconds field is out of range. The value is well-formed on the wire and decodes cleanly into a valid uint32, but it is not a valid timespec64: tv_nsec must be less than NSEC_PER_SEC."

And the consequence:

"The un-normalized value then corrupts on-disk metadata. ext4's ext4_encode_extra_time() shifts tv_nsec left by EXT4_EPOCH_BITS; an out-of-range value overflows the 32-bit extra field and clobbers the seconds-epoch bits, so the stored seconds (and thus the year) are wrong on read-back. XFS with bigtime mis-stores the timestamp for the same reason. There is no WARN_ON anywhere in the path to catch it."

Ko frames the fix as a long-standing data-integrity gap and an LTS candidate:

"The lack of validation is long-standing and predates the git history of this code, so no Fixes: tag is provided. This is a data-integrity fix and is a candidate for LTS backport."

v2 refinements over v1

The v2 cover letter adds two notable clarifications that were not in v1:

  1. Cast width rationale. Ko explains why the comparison casts tv_nsec to unsigned long rather than u32:

    "tv_nsec is a long, so the comparison casts it to unsigned long (the same width) rather than to u32, matching timespec64_valid(). A u32 cast would be wrong on both ends: on 32-bit it cannot widen, and on 64-bit it would truncate the NFSv2 value (svcxdr_decode_sattr() computes tv_nsec as tmp2 * NSEC_PER_USEC, which can exceed the u32 range). The unsigned long cast also rejects a value that became negative when an out-of-range u32 wire nseconds was assigned to a 32-bit long."

  2. NFSv2 status mapping. Because RFC 1094 has no NFSERR_INVAL (no stat enum value 22), the patch maps nfserr_inval to nfserr_io in nfsd_map_status() so the NFSv2 reply stays within the RFC 1094 status set, while NFSv3/NFSv4 leave INVAL as-is.

Patch 2/2's cover letter also re-emphasizes the 32-bit signed-compare hazard it preserves:

"The original code cast the literal to u32 to force an unsigned comparison, which matters on 32-bit where tv_nsec is a 32-bit signed long: an out-of-range u32 wire nseconds (>= 0x80000000) assigned to it becomes negative and a signed compare against NSEC_PER_SEC (a signed long) would wrongly pass. Keep that protection by casting tv_nsec to unsigned long, the same width as tv_nsec, matching timespec64_valid() and the NFSv2/NFSv3 setattr check."

Chuck Lever's review: objecting to the choke-point placement

Lever's reply on 2026-06-15 is the week's most important technical contribution. He raises three distinct issues with patch 1/2:

1. Orphaned objects on the create path. Lever points out that the check in nfsd_setattr() runs after the object has been created:

"nfsd3_proc_create() and nfsd_create_locked() call vfs_create()/vfs_mkdir()/vfs_mknod() before nfsd_create_setattr() reaches this new nfserr_inval return. The server then reports failure for the invalid timestamp but leaves the new object behind, so retries can hit EXIST and clients observe a failed non-idempotent operation that actually modified the namespace."

He is careful to note this is not a brand-new class of bug:

"But this is not strictly new behavior. 'post-create setattr fails, object left behind' is a long-standing property of this path. Any failure in nfsd_create_setattr() (commit_metadata, fh_update, uid/gid) already orphans the object. However, this patch adds one new, client-triggerable way to hit it. So it's a fresh trigger of an existing wart, not a brand-new class of bug."

And he frames the trade-off plainly:

"The trade is corruption vs. orphan. Pre-patch, that same input created the object and stored a corrupt timestamp (the bug the patch targets). Post-patch it creates the object and reports failure. Neither is good; the orphan is the lesser evil but it is still avoidable."

2. A 32-bit decode-time corruption the check cannot catch. Lever identifies a case where Ko's >= NSEC_PER_SEC test in nfsd_setattr() is itself defeated on ILP32:

"Moreover, on 32-bit platforms, svcxdr_decode_sattr() computes tmp2 * NSEC_PER_USEC before this check, and that multiplication is 32-bit unsigned long on ILP32. A wire useconds value such as 4294968 wraps to tv_nsec == 704, so this >= NSEC_PER_SEC test accepts an out-of-range client value and stores a bogus timestamp instead of rejecting it."

3. Sashiko's automated review was a false positive. Lever dismisses the sashiko.dev comment that had been pointed at Ko in v1:

"The sashiko.dev review is based on a branch that does not have Jeff's fix for CB_GETATTR for this exact issue, so it's effectively a false positive."

Lever's proposed redesign

Lever lands on a clear architectural position — push the validation down into the per-version decode/proc layer rather than centralizing it in nfsd_setattr():

"In summary: I don't agree with adding the check in nfsd_setattr(). The incoming values need to be checked closer to the protocol-specific code because each NFS version has to solve a slightly different problem."

He then lays out the per-version plan:

"For NFSv2, the incoming value needs a decode-time guard on the raw microseconds, because its decode does a unit conversion that silently corrupts an out-of-range value on 32-bit before any proc function can see it.

For NFSv3, the check should happen in nfsd3_proc_setattr(), and in nfsd3_proc_create() before creation is attempted.

NFSv4 (SETATTR, CREATE, and CB_GETATTR) all seem to be covered by the current implementation and don't need the extra check in nfsd_setattr()."

Status as of end of window

As of Sunday 2026-06-15 15:07 UTC (the last message in this thread within the week's window), Ko has not yet replied to Lever's review. The series is therefore in a rework-pending state: patch 2/2 (the NSEC_PER_SEC readability cleanup) appears uncontroversial, but patch 1/2 needs to be restructured along Lever's lines — a decode-time guard for NFSv2, an early check in nfsd3_proc_setattr() and before the create call in nfsd3_proc_create(), and no change to the NFSv4 path. The data-integrity goal is unchallenged; only the placement of the validation is in dispute.

Bottom line

This week's thread is a bug fix discussion (NFS server-side timestamp validation), not a feature or protocol change. The v2 re-post tightened the cast-width and NFSv2 status-mapping rationale, but Chuck Lever's review reframed the design question: a single choke-point check in nfsd_setattr() is the wrong layer because (a) it runs too late on the create path to avoid orphaning objects, and (b) it cannot see the raw wire value on 32-bit NFSv2 where the unit-conversion multiplication has already wrapped. The expected next step is a v3 that splits the validation per protocol version.
