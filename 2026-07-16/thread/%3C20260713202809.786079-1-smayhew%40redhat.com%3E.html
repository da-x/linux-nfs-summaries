nfs-utils: ignore_hosts flag now passed through to export_create() — DNS-query bug fixed and committed

nfs-utils: ignore_hosts now honored in export_create() — a one-line DNS-query bug fix lands

What happened this week

This week's activity in the thread is brief but decisive. On Monday, 2026-07-13, Scott Mayhew posted a small one-line bug fix for nfs-utils titled "[nfs-utils PATCH] Pass ignore_hosts to export_create() in export_read()". Two days later, on Wednesday, 2026-07-15, nfs-utils maintainer Steve Dickson replied with the customary terse:

"Committed... steved."

The patch is now upstream. The thread is complete — no review debate, no follow-up fixes, just a clean fix-and-commit cycle typical of well-understood nfs-utils maintenance work.

The bug: an ignore_hosts flag that only worked halfway

This is squarely a bug fix, and it corrects an incomplete earlier change. Mayhew's cover message explains the backstory clearly:

"Commit 8f3d12ce ("nfs-server-generator: avoid using external services.") added the 'ignore_hosts' flag to export_read() so nfs-server-generator can bypass DNS queries when calling it."

The problem, as he describes it, is that the earlier commit only half-implemented its stated goal:

"If the export doesn't already exist, export_read() calls export_create() with the 'canonical' argument hard-coded to 0, triggering a DNS query in client_lookup()."

In other words, the ignore_hosts flag existed on export_read() but was silently dropped when that function delegated to export_create(). The fix is correspondingly small — one line in support/export/export.c (1 insertion, 1 deletion) — passing the flag through so client_lookup() no longer performs a DNS query in this code path.

Why it matters: systemd timeouts from an unresponsive DNS server

The practical symptom Mayhew highlights is what makes this more than a cosmetic cleanup. The nfs-server-generator unit runs during boot and produces the order-with-mounts.conf config drop-in that orders NFS mounts relative to exports. If it stalls, systemd's boot-time budget can be blown:

"An unresponsive DNS server can cause delays in nfs-server-generator and can even lead to 'systemctl daemon-reload' timing out, leading to further administrative issues."

That is a real operational failure mode on any deployment where the local resolver is flaky or unreachable at boot — and daemon-reload timeouts are notoriously disruptive for administrators trying to recover.

Mayhew also makes the design argument that justifies skipping DNS entirely in this path:

"nfs-server-generator only cares about what is exported, so it can create the order-with-mounts.conf config drop-in. It doesn't need to know who those filesystems are exported to, so it has no need to perform DNS queries."

The Fixes: tag points back at 8f3d12ce, making this a proper follow-up fix rather than a new feature.

Client-side relevance

Although the patch touches server-side tooling (nfs-server-generator, part of nfs-utils), its impact on NFS client experience is direct and worth flagging: a hung or timing-out nfs-server-generator delays the availability of the export ordering information that client mount units depend on during boot. On systems where NFS root or early-boot filesystems are involved, this can push clients into fallback paths or delayed mounts. The fix removes one class of boot-time stalls for clients in environments with unreliable DNS — a common situation in containers, VMs mid-migration, and air-gapped data centers.
