nfs-utils: fix heap-buffer-overflow in haddr (with submission process notes)

Summary

nfsd: fix memory overflow for haddr

This week's activity on this thread was brief but instructive. A one-line bug fix landed from a Huawei contributor, and the NFS maintainer took the opportunity to flag two process issues that could block future submissions.

The Bug Fix

zhangjian (CG) from Huawei reported a heap-buffer-overflow in the nfsd user-space daemon (part of nfs-utils, not the in-kernel server):

"when hcounter is not 0, haddr memory is not enough."

The overflow was caught by AddressSanitizer when running:

CFLAGS="-fsanitize=address -g" ./configure && make
./utils/nfsd/nfsd -H 192.168.1.1 -H 192.168.1.2

The fix is a one-line change in utils/nfsd/nfsd.c (1 insertion, 1 deletion) that corrects the size of the haddr buffer allocation so it can accommodate multiple host addresses when hcounter > 0. This is a straightforward bug fix for a memory safety issue in the NFS user-space tooling.

Maintainer Feedback on Submission Process

Chuck Lever, the NFS subsystem maintainer, replied the same day with two important process notes:

  1. Subject prefix / target project ambiguity: Chuck noted that the "nfsd:" subject prefix and the To: line made it look like a patch for the in-kernel NFS server, when it was actually for nfs-utils:

    "You sent this To: chuck.lever and prefixed the Subject with 'nfsd:' so I assumed it was for the Linux in-kernel NFS server. In fact, it's for nfs-utils. Steve might not recognize that he is responsible for this patch. I suggest using 'nfs-utils:' instead for such patches (including the preceding patch labeled 'gssd:')."

  2. DKIM misconfiguration: Chuck flagged a security concern with the submitter's email infrastructure:

    "your email transfer agent's DKIM is misconfigured. This security feature is tested by our patch intake tooling as a way to spot bogus submitters."

    The b4 import tool reported ✗ BADSIG: DKIM/h-partners.com, and Chuck warned:

    "This might become a blocking gate for future submissions, so you should speak with your email administrator to get this corrected."

Conclusions

  • The patch itself is a trivial, correct one-line fix for a real heap-buffer-overflow in nfs-utils' nfsd daemon.
  • No further technical discussion or objections were raised this week; the thread closed after Chuck's process-oriented reply.
  • The key takeaway for future contributors is to use the "nfs-utils:" prefix for user-space patches and to ensure DKIM signatures are valid, as the kernel's patch intake tooling (b4) may reject submissions with bad signatures.
