Chuck Lever ships five minor xdrgen fixes ahead of NFSv2/v3 server conversion

Summary

Chuck Lever ships five minor xdrgen fixes ahead of NFSv2/v3 server conversion

Type: Bug-fix / cleanup series for the xdrgen XDR code generator (tooling that underpins kernel NFS client and server XDR marshalling). No new feature or protocol change — this is maintenance work unblocking a larger effort.

Context and motivation

On Sunday, July 12, Chuck Lever posted a five-patch series titled "Minor fixes for xdrgen." The cover letter frames the motivation clearly:

"While working on server-side xdrgen conversion for NFSv2 and NFSv3, I found several unrelated minor issues with the xdrgen tool. They are collected here in this series."

So although the patches touch shared infrastructure (tools/net/sunrpc/xdrgen, include/linux/sunrpc/xdrgen), the practical driver is the ongoing conversion of the kernel NFS server (nfsd) to generated XDR code — work that will eventually make both client and server paths lean on the same generator. The series touches 22 files with a net deletion of 20 lines, regenerating NLMv3/NLMv4 lockd XDR code as well.

Patch-by-patch breakdown

1/5 — Cosmetic: blank line before enum declarations. This patch fixes a whitespace inconsistency in generated headers: the struct, pointer, and typedef declaration templates each lead with a blank line, but the enum template did not. Lever notes the omission "stayed invisible as long as every generated header happened to lead with a non-enum declaration." Tagged Fixes: 4329010ad9c3 ("xdrgen: Address some checkpatch whitespace complaints").

2/5 — Symbol collision for void RPC handlers (the most consequential patch). This patch addresses a real link-time bug that would have blocked the NFSv2+NFSv3 conversion:

"The generated server-side decoder and encoder for a void procedure argument or result are named after the RPC program... so two versions of one program built into the same module emit the identical symbol. NFSv2 and NFSv3 both declare program NFS_PROGRAM; once both are converted, fs/nfsd fails to link with multiple definitions of nfs_svc_decode_void and nfs_svc_encode_void."

The fix is elegant: since a void handler "carries no program- or version-specific behavior," Lever defines one shared pair — xdrgen_svc_decode_void() / xdrgen_svc_encode_void() — in the xdrgen builtins header and stops the generator from emitting per-program copies. lockd (NLMv3/NLMv4) is regenerated to use the shared handlers. He explicitly scopes the change: "Only the server (svc) handlers are affected. The client-side void stubs remain static and per-program, so they do not collide."

3/5 — Redundant union prototypes in definitions header. This patch removes xdrgen_decode_*/xdrgen_encode_* prototypes that the union definitions template was emitting into a header that doesn't include <linux/sunrpc/xdr.h>:

"Those prototypes name struct xdr_stream, which the definitions header neither includes nor forward-declares, so any translation unit that includes the definitions header without xdr.h already in scope draws -Wvisibility warnings."

The same prototypes are already emitted into the declarations header (which does include xdr.h), making the definitions-header copies redundant. Fixes: 4b132aacb076 ("tools: Add xdrgen").

4/5 — Missing width macros for 16-bit integers. This patch is a two-line fix: commit ae78eb497868 taught the generator to emit XDR_short and XDR_unsigned_short in computed maxsize macros but "left the two width macros themselves undefined in _defs.h." Lever defines them, each one XDR unit wide.

5/5 — Unbounded opaque/string encoders rejected all non-empty values. This patch fixes what is arguably the most impactful functional bug in the series:

"XDR represents an unbounded specifier (opaque foo<>, string foo<>) as a maxsize of 0, so for an unbounded member the check degenerates to 'len > 0' and the generated encoder refuses every non-empty value."

The decoder was already correct (it treats maxlen 0 as unbounded), and the sibling variable-length array templates already guarded their bound check with maxsize != "0" — but the struct and pointer forms of both the opaque and string encoders were missing that guard. The fix adds the same guard to all four affected Jinja2 templates. Lever also notes an edge case: "An explicit zero-length bound (foo<0>) parses to the same maxsize of 0 and so also skips the check; xdrgen does not distinguish it from the unbounded form, matching the decoder and the array encoders."

Assessment

This is a classic "sweep before the main event" series: Lever hit these issues while preparing the NFSv2/NFSv3 server-side conversion and collected them into a self-contained, bisectable set. Four of five patches carry Fixes: tags pointing back to the original xdrgen introduction (4b132aacb076) or follow-up commits, signaling that these are genuine defects rather than style preferences. The void-handler symbol collision (patch 2/5) is the one that would have been a hard blocker for the nfsd conversion; the unbounded-encoder bug (patch 5/5) could have produced silent data-loss-class failures in any generated encoder dealing with unbounded strings or opaque blobs — a latent risk for both client and server paths.
