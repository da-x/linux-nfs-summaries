RFC: Restrict TASK_FREEZABLE_UNSAFE freezing to system sleep (NFS)

Summary

RFC: Restrict unsafe freezable tasks to system sleep (NFS client)

This week brought a new single-message RFC from Stanislav Kinsburskii touching on a long-standing NFS client behavior around the kernel task freezer. It is an RFC patch proposal — not yet merged, and no replies landed within this week's window — but it targets a real usability bug in how network filesystem sleeps interact with administrative freezing.

What the patch proposes

The thread root was posted on 2026-07-14 as [RFC PATCH] freezer: Restrict unsafe freezable tasks to system sleep. Kinsburskii's cover message frames the problem clearly:

"TASK_FREEZABLE_UNSAFE is used by network filesystems for sleeps that may happen while a task holds locks or transport resources needed by other tasks. Allowing the freezer to park such tasks for administrative freezer requests can therefore block unrelated users of the same mount until the task is thawed."

The proposed fix preserves the original intent of these "unsafe freezable" sleeps — which exist so that suspend/hibernation isn't blocked indefinitely by RPC or filesystem waits — while preventing non-PM (i.e., administrative) freezer requests from freezing such tasks:

"Preserve that behavior for suspend and hibernation, but do not freeze TASK_FREEZABLE_UNSAFE tasks for non-PM freezer requests."

Technical details of the change

The patch is small (3 files, +14/-1) and touches three areas:

  1. kernel/freezer.c — adds logic so the freezer checks whether a TASK_FREEZABLE_UNSAFE task should actually be frozen, restricting it to PM (suspend/hibernation) requests only.

  2. include/linux/sched.h — makes the __TASK_FREEZABLE_UNSAFE bit independent of CONFIG_LOCKDEP, so the freezer can test the unsafe state in all builds (not just lockdebug ones). As Kinsburskii explains:

    "Make __TASK_FREEZABLE_UNSAFE independent of CONFIG_LOCKDEP so the freezer can test the unsafe state in all builds. The lockdep check still uses the same bit to suppress the locks-held warning for these known unsafe waits."

  3. Documentation/power/freezing-of-tasks.rst — documents the new PM-only freezer semantics for TASK_FREEZABLE_UNSAFE.

Context and history

The TASK_FREEZABLE_UNSAFE mechanism was introduced around 2019–2020 by Brian Callaghan (Red Hat) specifically to let NFS use freezable sleeps without triggering lockdep warnings, since NFS tasks routinely hold locks or transport resources during RPC waits. This RFC is a follow-up refinement: the original helper solved the "don't block suspend" problem but inadvertently made those same tasks vulnerable to being frozen by any freezer invocation (e.g., systemd admin operations), which could stall unrelated users of the mount.

Discussion status

As of this week's window, the thread contains only the initial RFC posting. A follow-up reply from Kinsburskii is dated 2026-08-05 (outside this week's scope). No NFS maintainers or other reviewers have yet weighed in within the current reporting period, so the patch remains at the earliest stage of review. Given that it touches core freezer semantics shared by multiple filesystems, expect discussion to involve Trond Myklebust, Anna Schumaker, and possibly the freezer/power management maintainers.

Bottom line

This is a bug-fix-oriented RFC for the NFS client's interaction with the kernel freezer: it narrows when "unsafe" freezable sleeps can actually be frozen, preventing administrative freeze operations from wedging shared NFS mounts, while keeping the suspend/hibernation guarantee intact.
