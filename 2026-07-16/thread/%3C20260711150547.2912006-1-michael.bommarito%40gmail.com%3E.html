pNFS blocklayout zero-value hardening patch NACKed by Trond Myklebust

Summary

pNFS blocklayout: zero chunk_size/volumes_count rejection patch rejected by client maintainer

This week's activity in this thread is a short but pointed exchange over a proposed bug fix / defensive hardening patch to the Linux NFS client's pNFS blocklayout driver. The discussion ended with an outright NACK from the NFS client maintainer, Trond Myklebust, and no resolution in favor of merging the change.

The patch (July 11)

Michael Bommarito opened the thread on July 11 with a patch titled "pnfs/blocklayout: reject zero chunk_size and volumes_count in GETDEVICEINFO." The change targets nfs4_block_decode_volume() in fs/nfs/blocklayout/dev.c, which decodes stripe parameters from the GETDEVICEINFO XDR response without validating for zero values.

The technical argument is straightforward and specific:

  • A server returning chunk_size=0 triggers a division-by-zero panic in bl_map_stripe() via div_u64(offset, dev->chunk_size).
  • Separately, volumes_count=0 passes the existing upper-bound check and causes a second division-by-zero via div_u64_rem(chunk, dev->nr_children=0).

Bommarito framed the impact: "a malicious or compromised pNFS blocklayout server can panic an affected Linux NFS client after the client mounts/uses the server and maps I/O through the poisoned blocklayout." He noted that an in-kernel parser/mapper KUnit reproducer was available privately. The fix is minimal — four insertions, one deletion — rejecting both zero values at decode time with -EIO.

The patch carries a Fixes: tag pointing to commit 5c83746a0cf2 ("pnfs/blocklayout: in-kernel GETDEVICEINFO XDR parsing") and is marked for stable. Notably, it includes an "Assisted-by: Claude:claude-opus-4-7" tag, indicating AI-assisted authorship.

The NACK (July 14)

Three days later, Trond Myklebust responded with a blunt rejection:

"NACK to this, and all further patches with the words 'malicious server' as their justification. It's time to stop this incessant flood of worthless AI slop..."

Myklebust's core technical argument rests on the threat model for storage systems:

"This is storage, not grandma's email server. If you have a 'malicious server' then it's game over. Your attempts to detect 0 length fields is going to be pointless security theatre because a real malicious actor will just corrupt the data."

He drew a distinction between a buggy server and a hostile one: "If a server is sending this kind of thing due to a bug, then you shouldn't trust it with your data. Just find a server that follows the spec." He concluded: "So no, we're not going to waste more time on this kind of junk."

Bommarito's rebuttal (July 14)

Bommarito replied the same day, partially conceding but pushing back on the threat model:

"Sure, I hear you. I'll make a note to skip your subsystem going forward."

He then offered a practical counterpoint about network-level attacks:

"FWIW though, these are often exactly the networks where ARP spoofing still works and malicious server can be read to mean 'anyone who can pretend to be a server/peer' for the relevant packet/session."

Myklebust's final word (July 14)

Myklebust closed the exchange by redirecting to transport-layer security:

"Then seeing this is a great opportunity to discover that you have an insecure network, and that you should have been using either krb5i, krb5p, TLS or secure VLAN technology to protect your on-the-wire message protocols against precisely this kind of man-in-the-middle attack."

He added a final point about attacker incentives:

"Again, though, a savvy man-in-the-middle won't be trying to cause clients to crash when they have a golden opportunity to manipulate the stored data instead."

Assessment

This thread sits at the intersection of several ongoing tensions in kernel development:

  1. Defensive parsing vs. trust model: The patch addresses a genuine class of bug (missing input validation in XDR decode paths) that could cause a kernel panic. However, Myklebust's position is that for NFS, the server is inherently trusted — a compromised or buggy server already has full access to your data, so crashing the client is not a meaningful security boundary.

  2. AI-assisted patch submissions: The "Assisted-by: Claude" tag and Myklebust's reference to "worthless AI slop" suggest this rejection is part of a broader frustration with a volume of AI-generated patches that may not align with subsystem-specific threat models or design philosophy.

  3. Threat model disagreement: Bommarito's ARP-spoofing / man-in-the-middle argument has some validity for flat networks, but Myklebust's counter — that the correct mitigation is transport security (krb5i/p, TLS) rather than client-side input validation — reflects the established NFS design philosophy where server trust is a precondition.

The patch was not merged this week, and the thread appears closed with the maintainer's final position standing.
