Paul Moore bisects his NFS regression to the nfsd.fh netlink upcall commit

Summary

NFSv4.2 listxattr thread: the side-quest bisect lands on an NFS server (nfsd) netlink commit

Context from last week (brief bridge)

This thread began as a client-side bug fix for nfs4_listxattr size accounting in fs/nfs/nfs4proc.c. Achilles Gaikwad's v2 patch — which fixes both a NULL-pointer oops on the zero-length size query and a silent size undercount caused by the security_inode_listsecurity() interface change (f71ece9712b7) — was reviewed, given a Reviewed-by from Paul Moore, and routed through the NFS tree by Anna Schumaker. While testing that fix, Paul Moore hit an unrelated NFS regression that appeared between vanilla v7.1 and v7.2-rc1 and promised to bisect it. That open thread is exactly what this week's four messages resolve.

What happened this week

All four in-window messages are from Paul Moore, who finally completed the git bisect he'd been running and reported the culprit — with a brief, self-correcting sequence of posts on Friday night.

  1. The bisect result (Jul 10, ~21:55 UTC). Paul announced that the offending commit was 01c2305795a3b6b164df48e72b12022a68fd60c1, authored by Jeff Layton and signed off by Chuck Lever:

    "I haven't had a chance to look into this yet, but the git bisect just produced the commit below as the offending commit" — Paul Moore's bisect result

    The commit in question is "nfsd: add netlink upcall for the nfsd.fh cache", which adds netlink-based cache-upcall support for the expkey (nfsd.fh) file-handle cache, following the existing svc_export netlink pattern. It introduces an expkey attribute set (client, fsidtype, fsid, negative, expiry, path), the expkey-get-reqs / expkey-set-reqs operations in the nfsd YAML spec, nfsd_nl_expkey_get_reqs_dumpit() and nfsd_nl_expkey_set_reqs_doit(), and wires up expkey_notify() so cache misses trigger NFSD_CMD_CACHE_NOTIFY multicast events.

  2. A 47-second retraction (Jul 10, ~21:55 UTC). Almost immediately after posting the bisect result, Paul walked it back:

    "Ooops, nevermind, scratch that - I still have one more kernel to test." — Paul Moore's retraction

  3. Reconfirmation (Jul 10, ~22:20 UTC). Twenty-five minutes later he confirmed the original finding after all:

    "... and scratch that, the offending commit was that one." — Paul Moore's reconfirmation

    So the bisect conclusion stands: 01c2305795a3b6b164df48e72b12022a68fd60c1 ("nfsd: add netlink upcall for the nfsd.fh cache") is the regression.

  4. A minimal repro and a call for help (Jul 14). Four days later Paul reported that he could reproduce the failure with a trivial command on a current Fedora Rawhide system, and asked the NFS developers to take a look:

    "I can reproduce the problem with a simple command line: % mount -t nfs localhost:/mnt/test /mnt/nfs_test → mount.nfs: Connection refused for localhost:/mnt/test on /mnt/nfs_test" — Paul Moore's repro

    He ruled out several confounders: an explicit vers={4,4.1,4.2} had no effect (v2/v3 aren't built into his kernels), there was "nothing obvious in dmesg," and the failure occurred with SELinux both permissive and disabled — so "This doesn't appear to be related to SELinux, it may simply be that we are the first ones to hit this." He listed his userspace stack (nfs-utils-2.9.1-4.rc4.fc45 and friends) in case of a userspace interaction, said his next step was "try disabling portions of the NFS file handle cache upcall," and offered: "I'm happy to test things out or answer any questions about my test system."

Key technical takeaways

  • This is a bug-fix / regression hunt, not a feature or protocol change. The original listxattr fix (the thread's namesake) was already agreed and routed last week; this week's activity is entirely about the separate NFS regression Paul hit while testing it.
  • The bisect points at an NFS server (nfsd) commit, not a client change. The culprit 01c2305795a3 is Jeff Layton's netlink upcall for the nfsd.fh/expkey file-handle cache — a server-side feature that talks to userspace over netlink. That makes the "Connection refused" on mount plausibly a server-side failure in the new file-handle-cache upcall path (or its interaction with the Rawhide nfs-utils userspace), rather than anything in the NFS client's xattr code.
  • The regression is now trivially reproducible (mount -t nfs localhost:/mnt/test /mnt/nfs_test → "Connection refused"), independent of SELinux and NFS version, on Fedora Rawhide with nfs-utils-2.9.1-4.rc4.fc45.

Status / open questions

  • The bisect conclusion is confirmed (after the brief retraction): commit 01c2305795a3b6b164df48e72b12022a68fd60c1 is the offending change.
  • No fix has landed and no NFS developer had responded within this window. Paul explicitly asked "it would be nice if the NFS devs could take a look at this too," so the thread is left open pending maintainer attention to the nfsd.fh netlink upcall regression.
