Summary

nfsd: copy offload fixes — v3 applied to nfsd-testing

What happened this week

On Friday, July 10, Jeff Layton posted the third revision of his "nfsd: copy offload fixes" patchset PATCH v3 00/10, and by that evening Chuck Lever had the entire ten-patch series applied to the nfsd-testing tree. The turnaround was swift — a same-day review and merge, with no objections raised on the list.

This is squarely a bug-fix series, though it also includes structural refactoring aimed at preventing future lifetime bugs in NFSv4.2 inter-server copy offload (COPY / COPY_NOTIFY / OFFLOAD_CANCEL). The discussion itself was minimal: one posting of the series and one "Applied" reply. All the technical substance lives in the patch descriptions.

Background and discovery process

The cover letter is notable for its candid account of how these bugs were found:

"These patches fix bugs in inter-server copy offload code noticed by LLM inspection. The first 3 were found via kres, and the next 4 fix problems that were flagged in agentic review of those patches (and some via testing)."

Layton also noted that he had Claude generate a set of pynfs tests for COPY, which he planned to post separately. The v3 changes over v2 were: writing a new stateid to cp_res to prevent a potential bad CB_OFFLOAD call, fixing an interim regression that could cause an IDR leak, and making comments more terse.

Key technical fixes (patches 01–07)

The first seven patches address concrete, exploitable bugs in the copy offload code:

Patch 01 — cpntf publish race (PATCH v3 01/10, authored by Chris Mason): nfs4_alloc_init_cpntf_state() published a new cpntf entry into the IDR in one lock section, then took the lock again to add it to the parent's list. In that gap, a racing OFFLOAD_CANCEL could reach list_del() on a zeroed list_head, crashing the server. The fix folds the cs_type assignment and list_add() into the same critical section as idr_alloc_cyclic().

Patch 02 — UAF in async copy cancel/shutdown (PATCH v3 02/10): This was the most involved fix, addressing four distinct use-after-free and double-put scenarios where teardown callers (OFFLOAD_CANCEL, nfsd4_shutdown_copy, nfsd4_cancel_copy_by_sb) raced the copy kthread. The fix reworks the entire teardown lifetime: unlinking copies under async_lock before freeing, giving the kthread its own reference, pinning the task_struct, and taking a copy reference in nfsd4_send_cb_offload().

Patch 03 — stale IDR entry for async COPY (PATCH v3 03/10): nfsd4_copy() called nfs4_init_copy_state() before dup_copy_fields(), so the IDR pointed at per-request COMPOUND buffer memory that was reused by the next request. Any IDR walker (laundromat, manage_cpntf_state()) would dereference garbage. Fix: duplicate fields first, then register the stateid on the stable async copy object.

Patch 04 — initialize cpntf stateid before publishing (PATCH v3 04/10): nfsd4_copy_notify() finished initializing the cpntf state after it was already linked into the IDR. A racing OFFLOAD_CANCEL with a crafted clientid and guessable so_id could free the entry, turning subsequent reads into use-after-free.

Patch 05 — check client ownership on cancel (PATCH v3 05/10): The OFFLOAD_CANCEL path freed the target cpntf state without checking ownership. Since so_id is allocated cyclically (guessable) and the embedded clientid is a fixed per-net value, any authenticated NFSv4.2 client could cancel and free another client's copy-notify stateid. This is effectively a security fix.

Patch 06 — revoke cpntf stateids before dropping reference (PATCH v3 06/10): All three revoke paths (parent-stid drain, OFFLOAD_CANCEL, laundromat expiry) could drop the membership reference without unlinking if a concurrent holder had elevated cs_count, leaving the entry discoverable with its reference already consumed — a KASAN-detectable UAF. The fix adds revoke_cpntf_state_locked() which unhashes from the IDR and list first.

Patch 07 — NFS4ERR_NOTSUPP for unsupported netloc4 types (PATCH v3 07/10): A smaller correctness fix — nfsd4_decode_nl4_server() returned nfserr_bad_xdr for NL4_NAME and NL4_URL, which are well-formed XDR. The correct response is NFS4ERR_NOTSUPP.

Structural refactoring (patches 08–10)

The last three patches are the "make it less problematic in the future" portion:

Patch 08 — split nfsd4_copy into transient and durable objects (PATCH v3 08/10): struct nfsd4_copy served two roles — a transient per-COMPOUND argument and a durable heap object with a kthread, reaper linkage, and IDR stateid. That dual identity was "the root of the recent lifetime bugs." The fix introduces struct nfsd4_async_copy for the durable object, embedding a nfsd4_copy for operation parameters.

Patch 09 — make copy offload stateid a first-class nfs4_stid (PATCH v3 09/10): The async COPY offload stateid was previously a copy_stateid_t in the per-net s2s_cp_stateids IDR, sharing that table with COPY_NOTIFY stateids. This patch promotes it to a first-class nfs4_stid (SC_TYPE_COPY) allocated from the client's cl_stateids, making it "per-client by construction rather than relying on a guessable cyclic id in a global table."

Patch 10 — drop dead COPY-vs-COPYNOTIFY type handling (PATCH v3 10/10): Cleanup removing the now-unnecessary type-distinguishing machinery from the s2s stateid IDR. No functional change.

Resolution

Chuck Lever's reply was brief and decisive:

"Applied to nfsd-testing, thanks!"

All ten commits landed in nfsd-testing on the same day. The series is now a candidate for upstream merge in the next kernel development cycle.

Significance for NFS client/server development

While this series targets the server (nfsd), the bugs it fixes have direct implications for NFSv4.2 clients: the UAFs and race conditions could cause server crashes or data corruption during inter-server copy operations, which is a feature increasingly used in cloud and storage virtualization environments. The ownership-check fix (patch 05) closes what was effectively a denial-of-service vector where any authenticated client could disrupt another client's copy-notify state.

The series also highlights an emerging pattern in kernel development: LLM-assisted code review (via "kres" and agentic review) catching subtle concurrency bugs that had survived traditional review for years. Layton's transparent attribution of the discovery process — including "Assisted-by: Claude" tags on individual patches — marks a notable moment in how kernel bug-finding is evolving.
