RFC: Introducing CONFIG_IPV4 to decouple the IPv4 stack (with NFS Kconfig impact)

Summary

RFC: Introducing CONFIG_IPV4 to Decouple the IPv4 Stack

This week, SUSE's Fernando Fernandez Mancera kicked off a 13-patch RFC series targeting net-next with the goal of introducing a dedicated CONFIG_IPV4 Kconfig symbol — a long-overdue build-system change that would finally allow kernels to be compiled without the IPv4 stack. The series touches 53 files and has direct implications for NFS client and server configuration, making it worth tracking on this list.

The Patch: Laying Build-System Foundations

The first patch in the series introduces CONFIG_IPV4 as a def_bool y symbol, meaning it defaults to enabled and does not yet permit fully disabling IPv4:

"This patch introduces the CONFIG_IPV4 Kconfig symbol, which is set to 'def_bool y' for now. This does not allow to completely disable the IPv4 stack yet but it lays the necessary build-system work for that goal."

The motivation is architectural: because shared infrastructure like the TCP/UDP engine, routing tables, and INET hashtables all live inside net/ipv4/, it has historically been impossible to compile a kernel with only IPv6 support. The patch adjusts Kconfig dependencies across a wide swath of subsystems — tunnels, NIC drivers, filesystems, and notably fs/nfs/Kconfig, fs/nfsd/Kconfig, and net/sunrpc/Kconfig — to make them depend on CONFIG_IPV4.

This is classified as a build-system / protocol decoupling change, not a bug fix or new feature per se, but it is a prerequisite for future IPv6-only NFS deployments.

Arnd Bergmann's Review: Build Regression Concerns and Kconfig Logic

Arnd Bergmann responded the same day with two substantive points:

  1. Build regression risk: He warned that the next step — actually allowing IPV4=n — would likely trigger "additional (trivial) build regression" when randconfig builds hit obscure corner cases like INET=y IPV4=n IPV6=y. He offered to run the patch early on his randconfig tree to surface these issues quickly and asked whether he should simply add more depends on IPV4 directives or if Fernando had other plans.

  2. Kconfig guard logic: Arnd proposed a specific Kconfig snippet to ensure at least one of IPv4 or IPv6 is enabled:

    "Should we have some logic to ensure that at least one of IPV4 or IPV6 is enabled? I think this would work: config IPV4 / bool "The IPv4 protocol" if IPV6 / default INET — which only allows turning IPV4 off if IPV6 has enabled."

Fernando's Response: Pragmatic Approach and the "Pure L2" Question

Fernando replied the following day confirming he already had a randconfig job running to verify nothing breaks, and laid out his two-phase strategy:

"If something breaks and it isn't core networking stack I would just make the Kconfig symbol depend on IPv4. Then later we will have more time to write a dedicate patch so it does not depend on IPv4."

On Arnd's proposal to require at least one IP protocol, Fernando pushed back tentatively:

"I do wonder, should we? I mean, I didn't try it off but I don't see why we should not allow a pure L2 system.."

Resolution: Consensus on the Kconfig Guard

Arnd followed up clarifying his thinking:

"I expected a pure L2 system to be CONFIG_ETHERNET=y CONFIG_INET=n. Which user-visible parts of CONFIG_INET would you want keep working when both v4 and v6 are disabled?"

This framing — that a true "pure L2" system would disable INET entirely, not just one IP version — resolved the question. Fernando agreed:

"Yes, you are right. So I think introducing something as you proposed makes sense. Right now I cannot think about something needed from INET for pure L2."

NFS-Relevant Takeaways

  • NFS client (fs/nfs/Kconfig) and NFS server (fs/nfsd/Kconfig) both gain a depends on IPV4 in this patch, as does the underlying SUNRPC transport layer (net/sunrpc/Kconfig). This is a dependency cleanup, not a functional change — but it signals that future IPv6-only NFS configurations will require follow-up work to remove these dependencies.
  • The series is explicitly marked RFC, and Fernando's own words acknowledge that "follow-up work is required to convert the Kconfig symbol to bool and remove the dependency on IPv4 where it makes sense." For NFS developers, this means the current NFS-over-TCP/UDP path will remain coupled to IPv4 until those follow-ups land.
  • The agreed-upon Kconfig guard (IPv4 can only be disabled if IPv6 is enabled) provides a safety net: no one can accidentally build a kernel with no IP stack at all while INET is still in use, which would have broken NFS and virtually every other network filesystem.

Status

The discussion concluded with alignment between the two participants on both the randconfig testing approach and the Kconfig guard logic. The remaining 12 patches in the series are expected to follow, and the thread will likely continue as Arnd's randconfig results come in.
