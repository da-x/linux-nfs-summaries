gssd: fix memory leak in gssd_free_client

Type: Bug fix (userspace NFS client tooling — gssd) Week ending: 2026-07-16

Overview

A quiet but important bug-fix thread opened this week on the linux-nfs list, focused on a memory leak in the user-space GSS daemon (gssd), one of the core pieces of the Linux NFS client stack responsible for handling Kerberos/GSS-API credentials via upcalls from the kernel. The patch was submitted by zhangjian (CG) of Huawei and touched utils/gssd/gssd.c, with 14 insertions and 10 deletions.

The Bug

The one-line diagnosis in the cover message from zhangjian is blunt:

"clp->servername is always not null, so upcall_* is never free."

In other words, the cleanup path in gssd_free_client() was gated on a condition that could never be true — because clp->servername is always set — so the associated upcall_* resources were leaked every time a client context was torn down. For a long-running daemon like gssd, which cycles through upcall contexts as NFS clients come and go, this is exactly the kind of slow leak that accumulates over days or weeks of uptime.

The patch restructures the freeing logic in gssd_free_client() so that the upcall_* allocations are released unconditionally (the diff spans 24 lines in utils/gssd/gssd.c, with the commit carrying a single Signed-off-by from zhangjian).

Discussion This Week

The thread was short this week — only the initial patch landed inside the reporting window, on 2026-07-14. No review replies, no objections, and no follow-up discussion appeared before the end of the week. The next message in the thread (a reply from Steve Dickson at Red Hat) is dated 2026-07-23, which falls outside this week's window, so it is not summarized here; it will be picked up when that week's digest runs.

Significance for NFS Client Development

While small in scope, the fix matters to anyone running Kerberized NFS clients:

  • Userspace daemon hygiene: gssd is a long-lived helper process; leaks there are invisible in kernel-side accounting but show up as slow RSS growth on hosts that mount many or churning GSS-secured filesystems.
  • Cleanup-path correctness: The bug was a classic "dead branch" — code written to handle a null servername that the rest of the codebase made impossible. The fix removes the dead conditional rather than trying to make the invariant hold, which is the cleaner direction.
  • No protocol or feature change: This is purely a maintenance/correctness patch; nothing about the upcall protocol, GSS context handling, or kernel-client interface changes.

Bottom Line

A tidy, surgical leak fix in gssd submitted by Huawei's zhangjian on 2026-07-14. No in-window discussion yet; watch for Steve Dickson's follow-up next week to see whether it lands as-is or with review tweaks.
