DEPT v19: Rust dept_key Fix Confirmed and Patch Hygiene Tightened

Summary

DEPT v19: Rust dept_key Fix Committed, Patch Hygiene Tightened

Classification

This is a new kernel feature (DEPT – DEPendency Tracker) in active review. This week's activity consists of two small but consequential design clarifications on the 40-patch series posted last week: one resolving a real bug in the Rust integration path, and one addressing patch-hygiene feedback from the Rust for Linux maintainer.

Bridging Prior Week (Briefly)

Last week (ending 2026-07-09), Byungchul Park posted the full v19 series — 40 patches implementing DEPT, a wait/event deadlock detector that fills Lockdep's structural blind spot for completion-based deadlocks. Two patches drew immediate review: patch 22/40 (PG_locked tracking) sparked a substantive design debate with Matthew Wilcox over per-page vs. per-owner classification, and patch 31/40 (unique dept_key per wait_for_completion() caller) was flagged by Gary Guo as having a Rust-side bug — all Rust callers would share one key, defeating the false-positive avoidance the patch exists to provide. Park had not yet responded to Guo at the end of that window.

This Week's Activity (July 10–16)

Three messages landed this week, resolving both open threads from last week:

1. Park Confirms the Rust dept_key Fix Plan (July 10)

Byungchul Park responded to Gary Guo's July 7 concern about patch 31/40, confirming the diagnosis and committing to a concrete fix:

"Yes, dept_key is similar to lock_class_key. IIUC, the way you tried for lock_class_key can be applied to DEPT too."

Park then laid out a three-step plan for the next revision:

  1. add 'key' parameter to sdt_might_sleep_start_timeout()
  2. introduce init_completion_dkey() to allow custom keys
  3. remove init_completion_dmap() and adjust the existing users

He added an important operational caveat about key lifecycle management:

"Just in case, it's worth noting that the custom keys must be well-managed using e.g. dept_key_destroy() when the key gets freed."

This resolves the open bug from last week: the Rust wait_for_completion() helper can remain a plain function (rather than being turned into a macro) while still getting per-caller unique keys, following the same pattern Guo used for lock_class_key bindings.

2. Miguel Ojeda Questions Patch Splitting (July 11)

Miguel Ojeda, the Rust for Linux maintainer, raised a patch-hygiene question about patch 39/40 (rust: completion: Add __rust_helper to rust_helper_wait_for_completion()):

"Apart from what Gary said -- why did you need to do this in a separate patch in the same series?"

The concern is that patch 38/40 (percpu sizing) and patch 39/40 (Rust helper annotation) are tightly coupled — the Rust helper change exists solely to enable DEPT instrumentation of wait_for_completion() from Rust code, so splitting them adds review friction without independent value.

3. Park Agrees to Merge (July 13)

Byungchul Park concurred immediately:

"Not necessary. I will make them into one patch. Thanks."

Evolution of the Discussion

The arc this week is resolution and tightening:

  1. July 10: Park closes the loop on Guo's Rust dept_key bug report with a concrete fix plan, confirming the lock_class_key analogy and committing to API changes (init_completion_dkey() replacing init_completion_dmap()).
  2. July 11: Ojeda raises a minor but valid structural point about patch splitting in the Rust portion of the series.
  3. July 13: Park agrees to merge, signaling willingness to streamline the series for easier review.

Both open items from last week are now resolved at the design level. The PG_locked/Wilcox discussion (patch 22/40) remains open but saw no new activity this week; Park had already committed to follow-up classification patches.

Significance for NFS Client Development

  • The Rust dept_key fix is important for any future Rust-based NFS client components. If NFS client code in Rust uses wait_for_completion() (e.g., for RPC task synchronization), the v19-as-posted version would have produced false-positive deadlock reports. The planned init_completion_dkey() API will allow per-caller key assignment, making DEPT usable from Rust without false positives.
  • No new NFS protocol changes or NFS client bug fixes were introduced this week. The SUNRPC rcu_head relocation (patch 37/40, with Jeff Layton's Reviewed-by) remains the only directly-NFS-tree patch in the series.
  • The overall DEPT series is still in early review; no maintainer has issued a merge verdict.

Final Conclusions

  • Both open technical questions from last week (Rust dept_key bug, patch splitting) are resolved at the design level for v20.
  • Park's stated plan: add key parameter to sdt_might_sleep_start_timeout(), introduce init_completion_dkey(), remove init_completion_dmap(), and merge patches 38/40 + 39/40.
  • The series remains in active review with no overall maintainer verdict yet. The PG_locked classification work (Wilcox's feedback) is the next major open item.
