Chuck Lever hardens xdrgen diagnostics: RFC 4506/5531 semantic checks and caret alignment

Summary

Chuck Lever hardens xdrgen with RFC-mandated semantic checks and better error carets

Type: Bug-fix / tooling-hardening series for xdrgen, the Python XDR code generator that underpins both the kernel NFS client and server marshalling paths. This is not a new feature or a protocol change — it closes gaps in the front end so malformed .x specifications are rejected at generation time rather than surfacing later as confusing C compiler errors (or, worse, silent runtime dispatch collisions).

Context and motivation

On Sunday, July 12, Chuck Lever posted a five-patch series titled "Improve diagnostic reporting." The cover letter is terse but sets the scope precisely:

"Add missing detection and reporting for semantic errors specified in RFCs 4506 and 5531."

The series touches 12 files with a net addition of 428 lines, most of it new semantic-check logic in xdr_ast.py plus six new negative test cases. It lands the same day as Lever's companion five-patch "Minor fixes for xdrgen" series, which fixed generated-code defects (void-handler symbol collisions, unbounded opaque/string encoders, missing 16-bit width macros). Together the two series are part of the ongoing effort to convert both the NFS client and nfsd server to generated XDR code — work that makes the generator's correctness a first-order concern for the whole sunrpc stack.

The recurring theme across all five patches is where an error is caught: Lever repeatedly argues that the xdrgen front end is "the only place that can reject" certain malformed inputs, because they compile cleanly as C but are invalid on the wire.

Patch-by-patch breakdown

1/5 — Align the error caret under tab-indented source. This patch fixes a cosmetic-but-frustrating bug in how xdrgen prints diagnostics. When reporting a parse or transform error, the tool echoes the offending source line and drops a caret under the bad column — but the two were computed from different tab origins:

"The source line is emitted with its tab characters intact, but the caret offset is computed from a tab-expanded copy of the text ahead of the column. A terminal expands the line's leading tabs relative to the four-space output indent, while the caret math expands the same tabs from column zero, so the two disagree whenever the line is indented with tabs and the caret lands past the token it should mark."

The fix renders the displayed line with its tabs already expanded so "the line and the caret share one tab origin," and folds the now-identical formatting out of both error handlers into a single helper. It's a small change (18 insertions, 8 deletions in xdr_parse.py) but it sets up the rest of the series: every new semantic check needs its caret to point at exactly the right token.

2/5 — Record the source position of each declared identifier. This patch is the enabling infrastructure for the semantic checks that follow. The transformer previously kept an identifier's spelling but threw away its position, retaining only the enclosing definition's location:

"A caret built from that position falls on the definition keyword rather than on the identifier, because the definition production begins at the keyword."

The fix stores each identifier's own line and column on every named construct — constants, enumerated types and their enumerators, structs, unions, pointers, typedefs, and RPC program/version/procedure names. The fields live on the AST base node as keyword-only arguments so lark's positional construction is unaffected; unrecorded positions simply stay zero. This is 83 insertions against 33 deletions in xdr_ast.py.

3/5 — Reject specifications that define a name twice. This patch enforces the RFC 4506 name-space rule:

"RFC 4506 Section 6.4 places constant and type identifiers in a single name space that must be unique within a specification."

Previously, a duplicate type or constant name sailed through xdrgen and only surfaced later as a C compiler error about a redefined struct or function — one that "points at generated code instead of the actual offending line in the .x source." Now the duplication is caught at the front end with a caret on the second definition.

4/5 — Enforce RFC 5531 name and number scoping for RPC programs. This patch extends the duplicate check from XDR identifiers to the RPC program model, which RFC 4506 alone does not cover:

"RFC 5531 Section 12.3 completes the model: a program identifier shares the specification-wide name space with constant and type identifiers, a version name and number are unique within their program, and a procedure name and number are unique within their version."

Lever flags one rule as particularly dangerous because it is silent:

"A duplicate procedure number is more dangerous because it is silent: the two procedures emit enumerators of equal value -- valid C that compiles cleanly -- leaving a dispatch collision to surface only at run time."

This is the kind of bug that would be nearly impossible to debug in a running NFS client or server, which makes front-end rejection especially valuable.

5/5 — Reject out-of-range program, version, and procedure numbers. The final patch closes the last gap: numeric range validation. RFC 5531 encodes each number as an unsigned 32-bit integer, so a valid value must fall in [0, 2**32 - 1], but the grammar accepts signed decimals with no ceiling:

"a negative procedure number emerges as an enumerator such as 'FOO = -5', valid C that compiles cleanly even though the wire field is an unsigned 32-bit integer. Thus the xdrgen front end is the only place that can reject the malformed value."

This patch adds six new negative test files (negative and too-large program, version, and procedure numbers) to lock in the behavior.

Assessment

This is a textbook "make the tool honest" series: no runtime behavior of any already-correct specification changes, but every malformed one now fails fast with a precise, well-aligned diagnostic instead of a misleading downstream C error or — in the case of duplicate procedure numbers and out-of-range values — a silent wire-format bug. The progression is carefully sequenced: fix the caret (1/5), record identifier positions (2/5), then layer on the RFC 4506 check (3/5), the RFC 5531 scoping check (4/5), and the numeric-range check (5/5), each building on the position-tracking infrastructure from patch 2.

For NFS client development specifically, the value is in preventing defects: as both the client and nfsd move to generated XDR code, a specification that slips past xdrgen today becomes a latent dispatch or wire-encoding bug in production tomorrow. Lever's framing — that the front end "is the only place that can reject" these values — underscores that this is defensive work ahead of the larger NFSv2/NFSv3 conversion.
