Brendan Jackman's page_alloc cleanups: hiding mm-internal APIs, with a sunrpc touchpoint and an "ulterior motive" for alloc_flags

Summary

Type: API cleanup / header-hygiene series in the memory-management subsystem — not a new feature and not a protocol change. It is maintenance work that touches one line of RPC/NFS-adjacent code (net/sunrpc/svc.c) as a side effect, and it is explicitly groundwork for a later functional change to the page allocator.

On Thursday, July 16, Brendan Jackman (Google) posted a three-patch series titled "mm: yet more cleanups for page_alloc APIs," based on mm-new. The cover letter is unusually candid about the series' dual nature — genuine cleanup and a setup for something bigger:

"Align some APIs with recent cleanups [0][1], and hide more mm-internal APIs from public headers."

"And just like with my other recent patches, this has the ulterior motive of enabling later incoming patches to add alloc_flags arguments to these internal functions. (But, I do think these are justified as cleanups in their own right)."

The series spans 13 files (+65/−38). The NFS/RPC connection is thin but real: patch 2/3 migrates net/sunrpc/svc.c off the removed __folio_alloc_node() API. There was no prior-week activity on this thread; all nine in-window messages landed within a single afternoon (14:30–17:00 UTC) on July 16, and the substantive back-and-forth is contained entirely in that window.

Patch-by-patch breakdown

1/3 — Move internal mempolicy APIs to a new mm/mempolicy.h. This patch pulls declarations such as folio_alloc_mpol_noprof() out of the public include/linux/gfp.h into a new internal header, on the grounds that "there are no external users for this surface." Jackman pre-empts an obvious design question — why not just drop it into mm/internal.h?

"Note it might seem like this could just go in internal.h, since it's pretty small, but actually it will eventually need to import page_alloc.h, we don't want to import that from internal.h so best to proactively created this header now."

This patch drew the most discussion (see below).

2/3 — Replace __folio_alloc_node() with folio_alloc_node(), treewide. This patch mirrors an earlier removal of __alloc_pages_node(), arguing the double-underscore variant "just complicates the API (requiring users to handle NUMA_NO_NODE, or risking hotplug bugs) for no real benefit." It is a mechanical rename across iommu, LoongArch irqchip, filemap, migrate, and — the NFS-relevant line — net/sunrpc/svc.c. Jackman credits Vlastimil Babka with the idea (Suggested-by) and notes it is done as one patch because "the users are fewer." He flags "No functional change intended."

3/3 — Move __folio_alloc() into mm/page_alloc.h. This patch is the smallest: "This is no longer used outside of mm so reduce the scope," again with the stated "ulterior motive" that a later patch will add an alloc_flags argument.

The discussion: where should the internal mempolicy API live?

The technical heart of the thread is a short but pointed design debate over patch 1/3, pitting header-organization purity against API-surface philosophy.

Vlastimil Babka (SUSE) opened the exchange by questioning the need for a brand-new header at all:

"Hmm, maybe it could just go to page_alloc.h then? After all this is just bunch of internal page allocation functions, which just take the mempolicy pointer?" reply

Jackman conceded the option was viable but defended the new header on organizational grounds:

"That would work AFAICS, but I think it's quite tidy that, currently, all functions declared in page_alloc.h are defined in page_alloc.c. This would break that." reply

Matthew Wilcox then raised the more substantive objection — that hiding mempolicy-aware allocation from public headers sends a misleading message about who is allowed to use it:

"Hm. So what we're saying is that allocations which respect mempolicy are only for core mm and not for, eg, device drivers to do. Is that really what we want to say? I don't think so, because that's inconsistent with having just widened __filemap_get_folio_mpol to allow guest_memfd to specify a mempolicy." reply

Jackman's response is the key clarification of the whole thread. He agreed that mempolicy itself is a "public concept," but argued the specific function has no external users and therefore need not be public — while fully disclosing the real driver:

"Yeah I agree, mempolicy definitely seems like a 'public concept'. All I'm saying here is this specific function doesn't have any external users so it doesn't need to be an external header."

"... With the ulterior motive that I want to add a new parameter to it that actually is mm-internal. Namely, alloc_flags, so I can add ALLOC_UNMAPPED to implement AS_NO_DIRECT_MAP, i.e. the next iteration of [0]. So basically this is about trying to extend the allocator without creating a GFP flag." reply

He closed with a concrete migration plan that directly answers Wilcox's concern — if an external user ever appears, the API can be re-exposed cleanly:

"So I'm envisaging if an external user arises for it later, we'd slap two underscores on the beginning of the internal one, (with the alloc_flags arg), and then bring back the public one as a wrapper."

A self-correction on patch 2/3

In a final in-window note, Jackman caught his own mistake in the patch 2/3 commit message:

"Oh, I just remembered this commit hash is unstable. In fact it's already wrong." reply

He was referring to the Commit 5b584d2d22dca reference (the original removal of __alloc_pages_node()), flagging that the cited hash is unstable/incorrect — a small but honest correction to his own changelog.

Assessment and where things stand

This is textbook "clean up now, extend later" kernel work: three low-risk, mostly mechanical patches that shrink the public surface of the page allocator by moving genuinely internal symbols into mm/, while deliberately keeping the door open for a follow-on series that threads an alloc_flags argument (specifically to support ALLOC_UNMAPPED / AS_NO_DIRECT_MAP) through the allocator without adding yet another GFP flag. The NFS/RPC footprint is incidental — a single call-site migration in net/sunrpc/svc.c with no functional change.

The one genuine open question at the close of this week's window was Wilcox's API-philosophy challenge, which Jackman addressed but did not fully resolve: the maintainer-side decision on whether the mempolicy-aware allocation helper should remain a public (if currently unused) API or be tucked into an internal header. No final verdict appeared within the July 10–17 window; subsequent replies in the thread (July 20 and later, outside this week's scope) continued that sub-thread. As of end-of-week, the series was posted and under active discussion with no merge decision recorded.
