Anna Schumaker patches FREE_STATEID use-after-free; Jia Zhu flags related superblock pinning race

Summary

NFS client: Pin nfs_server during FREE_STATEID to fix use-after-free

This week's activity on this thread is a two-patch bug-fix series from Anna Schumaker addressing a real-world use-after-free in the NFSv4.1 client, plus a reply from Jia Zhu (ByteDance) surfacing a related but distinct race he hit in production.

The bug and the fix

Anna's first patch, "[PATCH 1/2] NFS: Pin the 'struct nfs_server' during a FREE_STATEID call," fixes a use-after-free reported by Dan Aloni of Vast Data:

"Dan Aloni reports that he was able to hit a use-after-free bug if a FREE_STATEID operation gets delayed for whatever reason. Fix this by bumping the refcount of the 'struct nfs_server' object for the duration of the FREE_STATEID so it doesn't get cleaned up from underneath us while operations are still in flight."

The patch adds five lines to fs/nfs/nfs4proc.c and carries a Fixes: tag pointing at commit 7c1d5fae4a87 ("NFSv4: Convert nfs41_free_stateid to use an asynchronous RPC call"), which is what introduced the async path that could outlive the server object. Dan Aloni is credited with both reporting and testing the fix.

The second patch, "[PATCH 2/2] NFS: Decrement refcounts if allocating nfs_free_stateid_data fails," closes a follow-on leak Anna spotted while working on the first one:

"I noticed that we were immediately exiting this function if the allocation fails, leaving the client and server object refcounts bumped. Fix this by creating a common exit point to clean up dangling references."

This one fixes commit 576acc259146 ("nfs4: take a reference on the nfs_client when running FREE_STATEID") and restructures the error path in nfs4proc.c (13 insertions, 7 deletions) so both the client and server references are released on allocation failure.

A related race from production

Jia Zhu replied three days later, noting the patch reminded him of a different nfs_server use-after-free his team hit in production at ByteDance:

"This patch reminded me of a similar nfs_server use-after-free that we recently encountered in production. However, it appears to involve a different race and root cause"

He pointed Anna to his own series, "NFSv4: pin the superblock for active state owners," and asked:

"Would you mind taking a look at it and letting me know if the approach looks reasonable?"

Status

As of the end of this window, Anna's two-patch series has been posted but not yet reviewed or acknowledged on-list; Jia Zhu's request for feedback on his separate superblock-pinning series is still pending. Both threads concern the same general area — keeping NFSv4 state-owner structures alive while FREE_STATEID RPCs are in flight — but address distinct races, so they should be evaluated independently.
