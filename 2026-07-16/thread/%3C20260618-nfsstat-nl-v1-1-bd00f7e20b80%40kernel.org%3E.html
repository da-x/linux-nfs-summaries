nfsstat callback-ops patch committed to nfs-utils (rc5)

nfsstat: NFSv4 callback operation statistics patch committed

The one in-window message is a short but consequential note from Red Hat's Steve Dickson, the nfs-utils maintainer, replying directly to Jeff Layton's June 18 v1 posting: Re: [PATCH nfs-utils] nfsstat: display NFSv4 callback operation statistics. Dickson's reply is essentially a commit announcement, quoting the original patch and adding:

"Committed... (tag: nfs-utils-2-9-2-rc5)"

No review objections, no v2, no rework: the patch went in as originally posted. That is a notably fast turnaround for an nfs-utils feature — roughly three weeks from posting to merge, with no intermediate revisions.

Bridge from Prior Weeks (brief)

For readers new to this thread, the context was established in the week ending 2026-06-18:

  • Layton's v1 posting (June 18) added a new "Server nfs v4 callback operations" section to nfsstat output, reporting per-operation call counts for the callbacks the server sends to clients (OP_CB_GETATTR through OP_CB_OFFLOAD).
  • The data source is netlink-only — as Layton explained, "the /proc interface exposes nothing equivalent (only the single wdeleg_getattr line, which corresponds to CB_GETATTR) -- so the section is displayed solely when the stats were fetched via netlink." The code detects this by checking srvproc4cbinfo[0] being non-zero.
  • The counters are opcode-indexed per RFC 8881, so "the name array carries placeholders for the unassigned opcodes 0-2 to keep the array index aligned with the opcode value, mirroring the kernel's cb_counter layout."
  • This patch is the userspace counterpart to Layton's companion kernel series (exportd/netlink v5), which at the time had received review feedback from Chuck Lever flagging a UAF possibility in the per-netns counter patch and a CB_SEQUENCE accounting question.

Key Technical Points

  1. Clean, unmodified merge. The fact that Dickson committed the patch verbatim — no v2, no fixups — signals that the design (netlink-gated display section, opcode-aligned name array) was accepted without objection from the nfs-utils community. This is worth noting: unlike the kernel-side series, which required revisions to address a UAF and a semantic accounting issue, the userspace side was considered correct as posted.

  2. Netlink gating preserves backward compatibility. The new section only appears when stats are fetched via netlink, so existing nfsstat consumers on older kernels or procfs-only configurations see no change in output. This is the same graceful-fallback pattern that allowed the earlier netlink fetch support patch to "go in cleanly on its first posting" (per Dickson's June 4 commit note).

  3. Dependency on kernel-side fixes. The feature is now merged into nfs-utils, but it will only produce meaningful data once the companion kernel series (v5 → v6) resolves Chuck Lever's concerns:

    • A UAF in the per-netns callback counter infrastructure.
    • CB_SEQUENCE accounting: "Opcodes nfsd never sends correctly report 0. The exception is op 11 / CB_SEQUENCE: it's written by encode_cb_sequence4args() on every minorversion>0 callback, so it goes out on the wire but is never counted... which could be misread as 'none sent' rather than 'not tracked.'"

    Until those kernel patches land, the new nfsstat section will either not appear (on kernels without the netlink counters) or report all zeros.

Significance for NFS Client Development

Although this is server-side tooling, it has direct relevance to NFS client developers working on delegation-related code paths:

  • The new counters expose per-opcode volumes for CB_GETATTR, CB_RECALL, CB_SEQUENCE, CB_CONFIRM, and (eventually) CB_OFFLOAD — exactly the backchannel traffic that a client's delegation handling must respond to.
  • The kernel patch replaces the old wdeleg_getattr procfs counter with a more accurate CB_GETATTR count: "the old counter incremented on every such conflict, whereas the CB_GETATTR counter only counts callbacks that are actually queued, so concurrent conflicts that coalesce onto an already in-flight CB_GETATTR are now counted once rather than once per conflict." Client-side developers tuning delegation-conflict behavior will want this refined metric.
  • Combined with the namespace-aware netlink path (already merged into nfs-utils), this gives containerized NFS deployments a way to observe per-netns callback traffic — useful when debugging client-visible delegation recall storms or backchannel congestion in multi-tenant environments.

Conclusion

This week's single message marks the completion of the userspace leg of the NFSv4 callback statistics effort. Steve Dickson committed Jeff Layton's v1 patch unmodified into nfs-utils (tag nfs-utils-2-9-2-rc5), closing out a thread that had been awaiting maintainer action since June 18. The remaining gating factor is now entirely on the kernel side: the companion netlink series must resolve the UAF and CB_SEQUENCE accounting issues before the new nfsstat section becomes useful in production. For client developers, the tooling is ready — the data will follow once the kernel patches land.
