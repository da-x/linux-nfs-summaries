NFSv4.2 listxattr thread: SELinux netlink upcall red herring resolved

Summary

NFSv4.2 listxattr size accounting: a SELinux detour resolves to "server wasn't running"

Context (prior weeks, brief)

This week's activity sits on top of an earlier exchange in the [PATCH v2] NFSv4.2: fix nfs4_listxattr size accounting thread, in which Paul Moore had reported a mount failure ("connection refused") that he initially attributed to the kernel's NFS client / mountd netlink upcall path. His bisection work had pointed at recent mountd changes, and he offered to answer questions about his test system. No prior-week summary file for this thread was found in the outputs tree, so the bridge is based solely on the quoted material visible in this week's messages.

This week's activity (2026-07-14 → 2026-07-15)

Scott Mayhew: "Pardon the dumb question" — was the server even up?

On Tuesday, Scott Mayhew pushed back on the premise of the bug report with a characteristically blunt first-principles check:

"Pardon the dumb question, but are you positive your NFS server is running? No errors from 'systemctl status nfs-server.service' or 'systemctl status nfs-mountd.service'? A connection refused error typically indicates the server isn't running."

He offered a concrete workaround — adding no-netlink=1 to the mountd stanza in /etc/nfs.conf and restarting nfs-server.service — and then flagged what he believed was the real underlying issue, even if it wasn't the one Paul had hit:

"FWIW the netlink upcall requires CAP_NET_ADMIN, which is blocked by the current selinux-policy on rawhide (and I think it's a dontaudit rule)... but you said you've disabled SELinux and reproduced your problem, so I'm scratching my head. Plus the symptom I ran into was the mount command hanging, not a 'connection refused' error."

Scott also noted two upstream items he'd been tracking:

  • A Fedora selinux-policy PR to allow the capability: https://github.com/fedora-selinux/selinux-policy/pull/3278 ("no movement on that yet").
  • A recent mountd patch improving the fallback to the old proc interface, which "I don't think it's been added to Fedora yet either."

This is a notable point for NFS client tooling: the netlink upcall path in mountd/nfs-utils has a real SELinux permission gap on rawhide, and the fallback-to-proc behavior is still being hardened upstream.

Paul Moore: "your question wasn't as dumb as one might have thought"

The next day, Paul Moore conceded the point with good humor:

"I'm slightly embarrassed to admit that your question wasn't as dumb as one might have thought :)"

He explained the mechanics of the false positive:

"While my bisection testing used the selinux-testsuite which ensures the NFS server starts, when I tried to create a simple reproducer to share with the non-SELinux crowd I neglected to verify that the NFS server was running, the directory, was exported, etc. My apologies for the confusion. However, the problem was real, even if my reproducer and error message were junk."

So the kernel bug itself (the SELinux block on the netlink upcall) stood; only the "connection refused" symptom Paul had shared with the list was an artifact of a misconfigured test box.

Paul then validated Scott's diagnosis directly by patching his local policy:

"As a quick test I added a quick hack to my policy (allow rule below) and everything appears to be working again. Thanks for the pointer!"

allow nfsd_t nfsd_t:capability { net_admin };

Key technical takeaways

  • Classification: This is a bug fix discussion, not a new feature or protocol change. The underlying defect is in the interaction between mountd's netlink upcall path and Fedora's SELinux policy (missing CAP_NET_ADMIN for nfsd_t), with a secondary concern about mountd's fallback to the legacy proc interface.
  • NFS client angle: The thread touches NFS client-side tooling (mountd / nfs-utils netlink upcall) rather than in-kernel nfs4_listxattr() code; the original patch subject refers to size accounting in the kernel client, but this week's traffic was entirely about the userspace mount path and test methodology.
  • Process lesson: A "connection refused" on an NFS mount is a strong signal that the server side (or its export) is down, not that the client's upcall mechanism is broken — worth keeping in mind when triaging similar reports.

Final state

The thread closed this week with the false alarm retracted and the real SELinux policy gap confirmed and locally worked around via an explicit allow nfsd_t nfsd_t:capability { net_admin }; rule. Upstream fixes remain pending: the Fedora selinux-policy PR (#3278) is unmerged, and the improved mountd proc-fallback patch has not yet landed in Fedora. No kernel-side conclusion or merge decision was recorded this week.
