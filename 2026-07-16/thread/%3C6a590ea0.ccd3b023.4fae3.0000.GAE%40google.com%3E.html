syzbot: task hung in nfsd_nl_cache_flush_doit (nfsd netlink lock contention)

Summary

syzbot: task hung in nfsd_nl_cache_flush_doit — a new netlink hang in the NFS server

What happened this week

On Thursday, July 16, Google's syzbot fuzzer filed a fresh report against upstream kernel 44696aa3a489 (post-merge of the input-for-v7.2-rc2 tag):

"INFO: task syz.3.4381:22405 blocked for more than 143 seconds."

The hung task was stuck in nfsd_nl_cache_flush_doit at fs/nfsd/nfsctl.c:2236, waiting on a mutex. This is the only message in this thread within the current window — no human replies, no reproducer, and no fix have landed yet as of the end of the week.

Classification

This is a bug report (not a new feature or protocol change), and it is squarely about the NFS server's netlink control interface — the same nfsd generic-netlink family that has been the focus of heavy development this cycle. The hung function, nfsd_nl_cache_flush_doit, is the netlink handler for flushing the nfsd cache (the modern replacement for the old /proc/fs/nfsd/... cache-flush sysctls).

Technical analysis of the hang

The call trace and lock dump tell a clear story:

  1. The hung task (syz.3.4381, PID 22405) is blocked in __mutex_lock on nfsd_mutex:

    nfsd_nl_cache_flush_doit+0xb5/0x1b0 fs/nfsd/nfsctl.c:2236

    It holds two locks itself: the generic-netlink cb_lock and (per the "locks held" section) it is waiting for nfsd_mutex.

  2. A second syzbot task (syz.1.3757, PID 20367) is holding nfsd_mutex while inside nfsd_nl_listener_set_doit at fs/nfsd/nfsctl.c:1964:

    #1: ffffffff8ee8e5e0 (nfsd_mutex){+.+.}-{4:4}, at: nfsd_nl_listener_set_doit+0x135/0x1750 fs/nfsd/nfsctl.c:1964

So the picture is a lock-contention / long-hold on nfsd_mutex: one netlink callback (listener_set, which adds/removes RPC listener sockets) holds the global nfsd_mutex for an extended period, and a concurrent cache_flush netlink request blocks behind it for over 143 seconds — long enough to trip the hung-task watchdog. The kernel was also tainted with [L]=SOFTLOCKUP, suggesting the mutex holder itself may have been spinning or stuck in a slow path (e.g., socket teardown, or waiting on network state) while holding the lock.

This is not a classic deadlock (no circular wait is visible — listener_set holds only cb_lock + nfsd_mutex, and cache_flush wants nfsd_mutex); it is a livelock/long-hold problem where a single coarse-grained mutex serializes all nfsd netlink operations, and one of them (listener_set) can block for an unbounded time.

Why this matters — and the connection to this week's other activity

This report lands in the middle of an unusually active week for the nfsd netlink interface:

  • The exportd/mountd netlink upcall series (Layton's v6, "nfsd/sunrpc: add support for netlink upcalls") has been under active review all cycle, with Chuck Lever and Jeff Layton re-litigating design details this week.
  • nfs-utils mountd netlink fixes were committed to nfs-utils-2.9.2-rc5 on July 11 — notably including a fix for "mount requests could hang indefinitely" when falling back from netlink to /proc under SELinux, showing that netlink-path hangs in this area are a known pain point.
  • The nfsd copy-offload bugfix series (Layton's v3, applied to nfsd-testing on July 10) shows the maintainers are actively hardening nfsd's concurrency and lifetime handling.

The nfsd_mutex is a long-standing global lock in fs/nfsd/nfsctl.c that serializes all netlink control operations (listener add/remove, cache flush, thread count changes, etc.). As the netlink interface has grown from a few handlers to a full-featured control plane (listeners, exports, stats, cache management), the coarse granularity of this single mutex is becoming a scalability and reliability liability. The syzbot report is the first concrete evidence that the problem is real: under concurrent netlink traffic, one slow handler can wedge the entire control plane.

NFS client relevance

While this is a server-side bug, its impact on NFS clients is direct:

  • A hung nfsd control plane means that administrative operations (adding/removing listeners, flushing caches after export changes) can stall indefinitely. On a production server, this could delay the activation of new exports or the removal of stale state — both of which affect client mount and access behavior.
  • The listener_set handler is what adds/removes the TCP/UDP sockets nfsd listens on. If it hangs while holding nfsd_mutex, new clients cannot connect and existing connections may not be serviced correctly until the lock is released.
  • For NFSv4.2 clients using inter-server copy offload (the feature Layton's bugfix series targets this week), a wedged control plane could interfere with state management operations that depend on netlink callbacks.

Status and outlook

As of the end of this window:

  • No reproducer — syzbot explicitly states: "Unfortunately, I don't have any reproducer for this issue yet."
  • No human replies — no maintainer (Lever, Layton, or others) has acknowledged the report on the list within this week.
  • No fix posted.

The likely next steps are: (1) a maintainer triages the report and confirms it is a real issue rather than a syzbot artifact; (2) someone investigates whether nfsd_nl_listener_set_doit can be made to release nfsd_mutex during its slow paths (socket teardown, network namespace operations); (3) potentially a broader refactoring to split nfsd_mutex into finer-grained locks or to use RCU for read-mostly netlink state.

Given the pace of nfsd netlink development this cycle, it would not be surprising to see this addressed in the next patch round — but as of now, it remains an open, unacknowledged bug report.
