NFS client: fix delegation_hash_table slab leak on failed NFSv4 mount setup

NFS client: fix delegation_hash_table slab leak on failed NFSv4 mount setup

What happened this week

A compact but consequential bug-fix thread landed in the window ending 2026-07-16. Nate Prodromou posted a single-patch fix for a kernel memory leak in the NFSv4 client, and Christoph Hellwig (hch) reviewed it within roughly ten hours. The thread is entirely about an NFS client bug fix — no new feature or protocol change is involved.

The bug

In his patch submission, Prodromou describes a lifetime mismatch in nfs4_server_common_setup():

"nfs4_server_common_setup() allocates server->delegation_hash_table first, but server->destroy - the only path that frees the table via nfs4_destroy_server() - is not assigned until the very end of the function."

If any intermediate step fails — is_ds_only_client(), nfs4_init_session(), nfs4_get_rootfh(), or nfs_probe_server() — the function returns with server->destroy still NULL, so the caller's nfs_free_server() skips the destroy callback and the hash table is leaked.

Why it matters: production impact

The report stands out for its unusually concrete field evidence. Prodromou notes the leak is "trivially reachable from userspace": every failed NFSv4 mount leaks one allocation, so a persistent retry loop leaks kernel memory without bound. He documented real-world damage:

"Observed in production where a Longhorn backup poller retried mount.nfs4 against an NFSv3-only server roughly 10 times per second, leaking ~3.4 GiB of unreclaimable slab (kmalloc-rnd-13-4k) per day; the node accumulated 12 GiB of leaked slab before the source was identified via the kmem:kmalloc tracepoint (call_site=nfs4_delegation_hash_alloc)."

He also supplied a one-liner reproducer — loop mount -t nfs4 <server>:/missing /mnt against an NFSv3-only export and watch SUnreclaim in /proc/meminfo grow 4 KiB per iteration.

The fix

The patch frees the delegation hash table on the error paths between its allocation and the assignment of server->destroy. It carries:

  • Fixes: f5b3108e6a14 ("NFS: use a hash table for delegation lookup")
  • Cc: stable@vger.kernel.org — i.e., it is flagged as a backport candidate for stable trees, appropriate given the unbounded-slab-leak severity.

Review and conclusion

Christoph Hellwig replied the next morning with an unqualified endorsement:

"Looks good: Reviewed-by: Christoph Hellwig hch@lst.de"

No objections or design debate followed in this window. The thread closes with a clean Reviewed-by on a straightforward, well-motivated client-side leak fix — a textbook example of a production-diagnosed NFS client bug (the delegation_hash_table slab allocation) being corrected at its root cause rather than papered over by the retrying caller.
