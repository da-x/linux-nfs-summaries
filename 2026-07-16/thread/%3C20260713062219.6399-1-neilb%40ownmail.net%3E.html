nfsd: NeilBrown's 17-patch refactor of nfs4_create_file() — v3 posted, two bugfixes, active review

Summary

nfsd: NeilBrown's 17-patch refactor of nfs4_create_file() — v3 posted, two bugfixes, active review

Type: Refactoring series with embedded bug fixes (NFS server / nfsd)

Overview

On Monday, July 13, NeilBrown posted the third revision of his ambitious 17-patch series to refactor nfs4_create_file() in the Linux NFS server. The cover letter explains that v3 "incorporates fixes for issues Chuck reported from 'Codex review'" and highlights patch 02/17 as "an interesting new bugfix." The series targets nfs-testing (commit 5f5dc3d855cf).

The overarching goal is to separate NFS-protocol-specific logic from VFS-interaction code in the create/open path, with an eye toward eventually replacing nfsd's hand-rolled lookup-and-open sequence with a new vfs_lookup_open() interface that would share more code with the syscall open path.

Key Bug Fixes

1. Honour client-provided attributes for NFS4_CREATE_EXCLUSIVE4_1 (patch 01/17)

This patch fixes a longstanding bug where the server silently discarded client-requested attributes on an exclusive v4.1 create:

"When the mtime/atime are set to hold the verifier, the other ia_valid flags are cleared, so no attributes requested by the client are used."

NeilBrown notes the code was "originally written for NFSv3 where NFS3_CREATE_EXCLUSIVE never includes attributes" and that "when it was updated for v4.1, the fact that an exclusive create CAN include attributes was not handled properly." It carries a Fixes: tag pointing to commit ac6721a13e5b and a Reviewed-by from Jeff Layton.

2. Correctly handle CREATE of mounted-on files (patch 02/17)

This patch addresses a correctness issue where an NFSv3/v4 unchecked CREATE on a file that has another filesystem mounted on it would return the underlying file's filehandle instead of the mountpoint's:

"if CREATE is used on an existing mounted-on file, the filehandle for the underlying file is returns. The client will then continue to use that filehandle."

The practical symptom: after a dcache flush (drop_caches), appending to /mnt/file would show the mounted-on (underlying) file rather than the mounted filesystem's file. NeilBrown states this "has never worked correctly" and is "not a regression and is not exploitable."

The Refactoring Arc (patches 03–17)

The bulk of the series performs incremental, reviewable steps:

  • Patches 03–06: Replace fh_fill_both_attrs() with fh_fill_post_noop(), move fh_want_write() and NFS-specific preamble code earlier in the function, and remove a "subtle" goto difference between EXCLUSIVE and EXCLUSIVE4_1 replay handling.
  • Patches 07–11: Let VFS report via FMODE_CREATED whether a file was actually created (important with atomic_open), move the NFSD_MAY_CREATE check earlier, defer fh_want_write() failure until creation is confirmed needed, and open the file even when it already exists.
  • Patches 12–15: Open-code nfsd4_vfs_create(), reduce the directory lock range (releasing start_creating() before setattr), reduce the want-write range to cover only what's needed, and move protocol-version checking out of nfsd_check_obj_isreg().
  • Patches 16–17: Extract all VFS-specific code into a new do_lookup_open() function, then use it for non-creating OPEN requests as well — the final step preparing for the future vfs_lookup_open() VFS API.

Review Activity

Chuck Lever's review of patch 02/17 (July 13):

Chuck found the other patches clean but identified several correctness issues in the mounted-on-file fix:

"This one doesn't build here with CONFIG_NFSD_V2=y, and the NFSv2 and NFSv3 create paths have some refcount and behavior problems. The NFSv4 path looks good."

Specifically he flagged:

  • A missing exp_get() before calling nfsd_cross_mnt() in the v2 path (refcount underflow)
  • Using the wrong export in fh_compose() after a mount crossing
  • Inconsistent attribute handling across v2/v3/v4 for mounted-on files ("The v4 behavior is the one I prefer, so bring v2 and v3 into line with it")
  • The v2 path not truncating on size-zero unchecked create

He also asked about LTS backporting. NeilBrown responded that he'd "develop some fixes in a day or 3" and advised against backporting:

"I wouldn't bother back poring. This is not a regression and is not exploitable."

Jeff Layton's review (July 16):

Jeff gave a Reviewed-by on patch 14/17 (reduce want-write range) but mused:

"It sucks that file creation is so fraught with peril and places that things can go wrong and leave stuff sitting out on the fs. I wonder if we ought to be using O_TMPFILE where possible to do all of this setup and only later link it into the namespace."

He also reviewed patch 15/17 with a clean Reviewed-by.

However, in his series-level review, Jeff reported findings from an LLM-assisted review pass that identified several regressions:

  • [High] Patch 10/17 (always open file): Opening a FIFO with default O_RDONLY while holding the parent directory's i_rwsem would block an nfsd thread indefinitely. Device nodes would invoke driver ->open.
  • [Medium] Patch 14/17 (reduce want-write range): For write-mode creates, setattr now runs without sb_start_write() freeze protection, creating a window where a concurrent freeze_super() could complete before notify_change().
  • [Medium] Patch 16/17 (separate VFS code): A __be32 status is compared against the raw host enum NFSERR_NOENT (integer 2) instead of nfserr_noent, so on little-endian the branch never fires and a create-permission error is masked by NFS4ERR_NOENT.
  • [High] Patch 17/17 (use do_lookup_open for non-creating open): An unconditional mnt_want_write() at the top of do_lookup_open() means a plain read-only OPEN now returns NFS4ERR_ROFS on read-only filesystems (squashfs, iso9660, erofs, ro-mounted ext4/xfs). Additionally, start_creating() takes the parent i_rwsem exclusively for every non-creating OPEN, serialising concurrent opens that previously used a shared or no lock via lookup_one_unlocked().

Jeff offered to provide "more detailed inline reviews" if NeilBrown wanted them.

Status and Outlook

As of the end of this week's window (July 16), the thread is in active review. Two patches have received Reviewed-by tags, but at least four regressions remain to be addressed — two rated high severity (FIFO open stall; read-only OPEN regression). The mounted-on-file fix (patch 02/17) needs a v4 addressing Chuck's refcount and build issues. NeilBrown indicated fixes would come "in a day or 3."

The series is significant for NFS server development: it paves the way for a unified vfs_lookup_open() that would let nfsd share more code with the VFS open path, potentially improving both correctness and performance (especially around concurrent directory operations).
