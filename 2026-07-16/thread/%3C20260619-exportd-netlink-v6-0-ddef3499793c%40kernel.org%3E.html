nfsd netlink stats v6: Layton and Lever re-litigate the fate of wdeleg_getattr in the new interface

Summary

nfsd netlink stats v6: the wdeleg_getattr question resurfaces

Context (brief bridge)

This thread continues last week's v6 posting of Jeff Layton's series converting the NFS server-side nfsstat interface from procfs scraping to a generic netlink dump handler, with per-netns accounting for both forechannel procedure counts and — new since v5 — NFSv4 backchannel (callback) operations. In that prior week, Chuck Lever had raised two concrete blockers on the callback patches (a use-after-free in patch 5 and a CB_SEQUENCE undercount in patch 6), plus a detailed review of patch 3/6 flagging the single-message dump buffer risk and, among other items, asking whether wdeleg_getattr should get a netlink attribute for parity with procfs.

This Week (July 16): A Focused Re-litigation of One Statistic

All six in-window messages landed on July 16 and revolve around exactly one question: should the legacy wdeleg_getattr counter be exposed via netlink, kept as a separate stat, or dropped entirely? Layton opens by noting that everything else from Lever's review has been addressed in his current series except this point.

Layton's opening position: the CB_GETATTR approximation is enough

Layton reopens the thread by recalling the earlier agreement:

"The only thing in this review that is not addressed in my current series is the above comment, and I think we had agreed in an earlier email thread that this was approximately the same value as the counter for CB_GETATTR calls and so it's good enough for this purpose. Are you still ok with this approach?"

Lever pushes back: include it now to avoid technical debt

Lever responds that he'd lost track of the earlier context, but on re-reading:

"Looking at this now, I think someone later could get an urge to add the wdeleg_getattr statistic to netlink… for symmetry, because it smells like technical debt, or it might actually be useful for something. IMHO we should include it now."

Layton: re-litigating whether the stat should exist at all

Layton pushes back on the premise, arguing the counter is a poor fit for the interface:

"IDGI: what's the point of collecting that stat separately when we have stats for CB_GETATTR already? I'd prefer to avoid perpetuating wdeleg_getattr as a stat here, since it's not directly tied to the protocol in the same way as the others are."

He then precisely articulates the semantic difference between the two counters:

"The only difference between the two is that if another client does a GETATTR for the fh while there is already a CB_GETATTR in flight, wdeleg_getattr gets bumped today, whereas CB_GETATTR counter does not (since there is only a single CB_GETATTR for that). Is that difference relevant? I think Dai added wdeleg_getattr originally, so I'd really like to hear his opinion on this."

Lever: API equivalence first, defer to the original author

Lever concedes he had misread the scope of Layton's objection:

"OK, so you are actually re-litigating whether the stat should exist at all. I confess I had forgotten that context. I'm arguing only that the netlink and procfs APIs should remain equivalent, at least initially. Deleting the stat entirely probably has no consequences right now, but let's hear from Dai when the US west coast wakes up."

He then floats a third option:

"Another option is to keep the stat but report it some other way. It is arguable whether nfsstat is the proper mechanism to report the different reasons for sending a CB_GETATTR."

Layton's closing position: no public consumer, want a use-case

Layton wraps up by reconstructing the earlier decision and putting the burden of proof on keeping the stat:

"We had decided that wdeleg_getattr was sort of an oddity that didn't really belong in this /proc file. The values in that file are mostly counting other very specific protocol operations, but wdeleg_getattr is basically counting GETATTR operations from other clients while there is an outstanding write delegation on a file. Since CB_GETATTR counts should approximate wdeleg_getattr, we decided to start counting those instead (along with all of the other callback ops). wdeleg_getattr in this series is changed to just report CB_GETATTR counts."

And:

"Sure. We could add some way to keep reporting it (or just keep using /proc for this). AFAIK though, there is no (public) consumer of this stat. nfs-utils doesn't look at it. To wit: I'd like to head a clear use-case for this stat before we decide to we need to count it like we did before."

Classification and Significance

  • Type: This week's exchange is squarely about the new netlink stats feature (patch 3/6 of the v6 series), specifically whether the legacy wdeleg_getattr procfs counter should be carried over into the new interface. There is no protocol change; the underlying counting behavior in patch 5 was already revised last week so that wdeleg_getattr reports CB_GETATTR counts rather than the old per-conflict count.
  • NFS client relevance: The discussion is server-side, but it directly concerns how clients' delegation activity is observed. wdeleg_getattr historically counted GETATTR operations from other clients that conflicted with an outstanding write delegation — a signal useful for diagnosing delegation recall storms and CB_GETATTR pressure on the backchannel. Layton's argument that "CB_GETATTR counts should approximate wdeleg_getattr" is exactly the kind of approximation that matters when a client admin is trying to understand why a particular file's write delegation was recalled: the new counter tells you how many callbacks actually went out, while the old one told you how many conflicts were observed (including those coalesced onto an in-flight callback).
  • Bug-fix angle: No new bug fix this week; the UAF and CB_SEQUENCE fixes from last week stand. The open question is a design/ABI one: drop the stat, keep it procfs-only, or expose it over netlink for API equivalence.

Where Things Stand

The thread ends with Layton asking for a concrete use-case before preserving the legacy counting behavior, and Lever deferring to Dai (the original author of wdeleg_getattr) who had not yet replied as of the end of the window. The likely outcomes are: (a) the stat is dropped from netlink but retained in procfs unchanged, (b) it's exposed over netlink for API equivalence, or (c) Dai provides a use-case that tips the balance. A v7 will need to resolve this before merge.
