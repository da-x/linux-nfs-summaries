NFS: Require Filesystems to Opt-In for nfsd Export Support via EXPORT_OP_STABLE_HANDLES

Summary

Overview

Jeff Layton submitted a 29-patch series, [PATCH 00/29] fs: require filesystems to explicitly opt-in to nfsd export support [id://20260115-exportfs-nfsd-v1-0-8e80160e3c0c@kernel.org], introducing a new mechanism to prevent unsuitable filesystems from being exported via NFS. This is a bug fix / hardening change targeting the NFS server (nfsd) subsystem, with broad implications across many kernel filesystems.

Problem Statement

Layton explained the core issue in his cover letter:

"In recent years, a number of filesystems that can't present stable filehandles have grown struct export_operations. They've mostly done this for local use-cases (enabling open_by_handle_at() and the like). Unfortunately, having export_operations is generally sufficient to make a filesystem be considered exportable via nfsd, but that requires that the server present stable filehandles."

Filesystems such as kernfs, pidfs, and nsfs have acquired struct export_operations for local utilities (e.g., open_by_handle_at()), yet their filehandles are not stable across reboots — a fundamental requirement for NFS exports. Without an explicit opt-in mechanism, nfsd would incorrectly consider these filesystems exportable.

Proposed Solution

The patch series introduces a new flag, EXPORT_OP_STABLE_HANDLES, in include/linux/exportfs.h. The approach unfolds in three stages:

  1. Patch 01/29: Adds the new EXPORT_OP_STABLE_HANDLES flag to the export operations structure [id://20260115-exportfs-nfsd-v1-1-8e80160e3c0c@kernel.org].
  2. Patches 02–28/29: Adds the flag to every filesystem that genuinely supports stable filehandles — including tmpfs, ext4, ext2, erofs, efs, xfs, ceph, btrfs, befs, ufs, udf, affs, squashfs, smb/client, ovl (overlayfs), orangefs, ocfs2, ntfs3, nilfs2, nfs, jfs, jffs2, isofs, gfs2, fuse, fat, and f2fs.
  3. Patch 29/29: Adds a check in __fh_verify() within fs/nfsd/nfsfh.c that returns nfserr_stale if the flag is not set [id://20260115-exportfs-nfsd-v1-29-8e80160e3c0c@kernel.org].

Key Technical Discussion: "Stable" vs. "Persistent" Handles

The most substantial debate in the thread centered on nomenclature. Amir Goldstein immediately questioned the choice of STABLE_HANDLES over PERSISTENT_HANDLES:

"Where does the term 'stable file handles' come from? and what does it mean? Why not 'persistent handles', which is described in NFS and SMB specs?" [id://CAOQ4uxjOJMwv_hRVTn3tJHDLMQHbeaCGsdLupiZYcwm7M2rm3g@mail.gmail.com]

Chuck Lever defended the term "stable" on two grounds. First, he argued that "persistent" implies storage on persistent media, which is not true of tmpfs:

"PERSISTENT generally implies that the file handle is saved on persistent storage. This is not true of tmpfs. The use of 'stable' means that the file handle is stable for the life of the file. This /is/ true of tmpfs." [id://d486fdb8-686c-4426-9fac-49b7dbc28765@app.fastmail.com]

Second, and more significantly, Lever raised a forward-looking concern about terminology collision with NFSv4:

"Another reason not to adopt the same terminology as NFS is that someone might come along and implement NFSv4's VOLATILE file handles in Linux, and then say 'OK, /now/ can we export cgroupfs?' And then Linux will be stuck with overloaded terminology and we'll still want to say 'NO, NFS doesn't support cgroupfs'." [id://4d9967cc-a454-46cf-909b-b8ab2d18358d@kernel.org]

Amir Goldstein pushed back initially, noting that "persistent" can also mean "continuing to exist or occur over a prolonged period," which works for tmpfs. However, he conceded after Chuck's argument about NFSv4 VOLATILE handles:

"Good argument. I'm fine with stable as well :)" [id://CAOQ4uxhtorpd6FVsaGO=NdRD72MxeDyabip84ctQYSNufobS8w@mail.gmail.com]

Dave Chinner added a pedantic but important clarification about inode lifetimes versus file lifetimes, noting that XFS physically reuses inodes across multiple files:

"Hence I think that file handle stability/persistence needs to be defined in terms of -file lifetimes-, not the lifetimes of the filesystem objects implement the file's persistent data store." [id://aWlXfBImnC_jhTw4@dread.disaster.area]

Chuck Lever acknowledged this point: "Fair enough, 'inode' is the wrong term to use here" [id://06dcc4b6-7457-4094-a1c6-586ce518020f@app.fastmail.com].

Jeff Layton noted that the name was Chuck's suggestion and expressed flexibility: "I don't much care about the flag name, so if everyone likes PERSISTENT better I'll roll with that" [id://9c99197dde2eafa55a1b55dce2f0d4d02c77340a.camel@kernel.org].

Filesystem-Specific Feedback

Several filesystem maintainers raised concerns about specific patches:

  • Overlayfs (ovl): Amir Goldstein flagged that overlayfs has a variant of export_ops used when nfs_export=off, where "encoded file handles can change after copyup+reboot" [id://CAOQ4uxhnxipJcjznEoa_D2R91NDZRgT_TTouGA4PGJO-7R9spw@mail.gmail.com]. Jeff acknowledged: "Also, on the ovl patch: will fix..." [id://9c99197dde2eafa55a1b55dce2f0d4d02c77340a.camel@kernel.org].

  • FUSE: Amir Goldstein noted that FUSE export operations are used when the server declares FUSE_NO_EXPORT_SUPPORT, meaning they should not opt in for NFS export: "The sad thing w.r.t FUSE is that in most likelihood server does not provide persistent handles also when it does not declare FUSE_NO_EXPORT_SUPPORT but we are stuck with that" [id://CAOQ4uxh4VaVL9PD7-_Op9Xs-z5Qrx8g6x2x5FccujQX-Cw9RqQ@mail.gmail.com]. Jeff responded: "Thanks, I removed that flag in the patch in my tree" [id://0d838a5cf271f98ce7158998dd6b1d0a86ea7eb7.camel@kernel.org].

  • SMB/client: Amir noted it was "Kind of odd to have this here after the comment out of NFS export" and suggested placing the flag inside the commented-out block [id://CAOQ4uxiTE+8r+F-e91cg9wZY-fjZfSHHOeLk3RWb+2JQQZvbvA@mail.gmail.com].

  • Ceph: Viacheslav Dubeyko provided a review: "Looks good. Reviewed-by: Viacheslav Dubeyko" [id://dd46aee3d0523cb88e3fe5e5c0e20df08b848a59.camel@ibm.com].

  • JFS: Dave Kleikamp acknowledged the patch: "Acked-by: Dave Kleikamp" [id://3e190d32-fa91-4d5f-a0ce-225bfff7a410@oracle.com].

Additional Technical Concern

Amir Goldstein raised a question about Patch 29/29, questioning whether the check should be in check_export() rather than __fh_verify():

"IDGI. Don't you want to deny the export of those fs in check_export()? By the same logic that check_export() checks for can_decode_fh() not for can_encode_fh()." [id://CAOQ4uxg304=s1Uoeayy3rm1e154Nf7ScOgseJHThw4uQjKwk0A@mail.gmail.com]

This point was left unresolved at the end of the week's discussion.

Conclusion

The series received broad conceptual support but generated a lively debate over terminology and several filesystem-specific corrections. The key outcomes:

  1. Naming settled: EXPORT_OP_STABLE_HANDLES retained over PERSISTENT_HANDLES, with Amir Goldstein conceding after Chuck Lever's argument about avoiding confusion with NFSv4 VOLATILE handles.
  2. FUSE corrected: Jeff Layton removed the flag from FUSE in his tree based on Amir's feedback.
  3. Overlayfs flagged: The ovl patch requires a fix for the nfs_export=off code path.
  4. Check location questioned: Amir raised an open question about whether the guard belongs in check_export() rather than __fh_verify().

The series represents an important hardening of the NFS server stack, ensuring that only filesystems with genuinely stable filehandles can be exported via nfsd — preventing subtle data corruption scenarios where unstable handles would silently produce stale-filehandle errors for NFS clients.
