Summary

NFS Client Hangs from NFS/fscache Re-export Servers

Overview

This week saw the opening of a new thread reporting intermittent NFS client hangs in a complex multi-tier NFS re-export architecture using fscache. The report, submitted by Mike Owen on January 9, describes a production issue affecting clients mounted behind NFS re-export servers. No responses or patches were posted this week; the thread remains open for community input.

Classification: Bug Report

This is a bug report describing unexpected client-side hangs in an NFS/fscache re-export deployment. The reporter seeks diagnostic guidance and potential fixes.

Environment and Setup

The reported infrastructure uses a "fan-out" or "daisy-chain" topology with fscache at multiple tiers:

  • Tier 1 server: Mounts shares from on-premises filers (Isilon and NetApp) via NFSv3 with fscache, then re-exports them. Runs Ubuntu 24.04 with kernel 6.14.0-36-generic, using 256 nfsd threads and nconnect=16.
  • Tier 2 servers (×5): Mount the Tier 1 server via NFSv4.2 with fscache, then re-export to end clients. Approximately 125+ clients per Tier 2 server.
  • Clients: Run AlmaLinux 9.6, mounting Tier 2 servers over NFSv4.2 with nconnect=1.

Symptoms Described

"We are seeing occasional NFS client hangs from NFS/fscache re-export servers."

Key observations from the report:

  1. Silent hangs: A small subset of clients hang on their mounts at unpredictable times, across different Tier 2 servers. Other clients on the same server remain unaffected.
  2. No logging: > "Nothing is logged on the client or server when this happens - i.e. no 'NFS server not responding' or similar messages etc."
  3. No network activity: > "Also, there is no network traffic between the client and server when the client gets into this state - by the time the client is flagged as being in this state, there is no NFS socket to the server."
  4. Workaround discovered: The reporter found that forcing an unmount of the first NFS-mounted share — even though it reports "device is busy" — has a side effect of reviving connectivity: > "it has the side effect of kicking things back into life again ... an NFS socket is created to the NFS server and traffic starts flowing."

Technical Significance

The symptom of no NFS socket existing on the client side, combined with the absence of error logging, suggests a potential issue in one of several areas:

  • Socket lifecycle management: The NFS client may be dropping its transport connection without proper recovery or diagnostic output.
  • fscache interaction: The use of fscache at both Tier 1 and Tier 2 introduces complexity around cache coherency, invalidation, and potential deadlock scenarios in the re-export path.
  • nconnect behavior: The mix of nconnect=16 (upstream) and nconnect=1 (downstream) may interact poorly with connection teardown or recovery logic.

The workaround involving umount -f suggests that forcing a cleanup of stale state can re-trigger socket creation, pointing toward a possible issue in the NFS client's reconnect or idle-connection management code.

Status

As of the end of this week, no replies, patches, or diagnostic suggestions have been posted to this thread. The community is awaiting input from NFS subsystem maintainers and developers regarding potential causes and debugging steps.
