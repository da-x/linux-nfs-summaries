Brauner Defends Separation of File Handles from NFS Export in Lease Opt-In Thread

Summary

VFS Lease Opt-In: Brauner Defends Separation of File Handles from NFS Export

Overview

This thread is a sub-thread within the broader VFS lease opt-in series discussion. The 24-patch series requiring filesystems to explicitly opt-in to lease support was applied to vfs-7.0.leases earlier this week by Christian Brauner. This thread specifically addresses whether kernfs-based filesystems (cgroupfs, nsfs, pidfs) should be NFS-exportable — a protocol/architectural discussion with direct implications for NFS server (nfsd) and client development.

Background (from Prior Week)

The root of this thread was Amir Goldstein's message on January 9 in response to Jeff Layton's cover letter, questioning whether kernfs-based filesystems were intended to be NFS-exportable:

"It is not accurate that kernfs filesystems are NFS exportable in general. Only cgroupfs has KERNFS_ROOT_SUPPORT_EXPORTOP."

Amir noted that nsfs and pidfs had recently gained export_operations for open_by_handle_at() support, but questioned whether this implied NFS exportability:

"I have a recollection about wanting to be explicit about not allowing those to be exportable to NFS (nsfs specifically), but I can't see where and if that restriction was done."

The broader discussion across related threads this week evolved through several stages:

  • Jeff Layton raised concerns about inadvertent export of cgroupfs via container bind mounts.
  • Christian Brauner argued for severing file handle operations from the export mechanism entirely.
  • Christoph Hellwig initially pushed back against explicit prohibition, questioning the value of blocking NFS export when administrators can use alternative tools (userspace NFS servers, Samba, FUSE).
  • Amir Goldstein reframed the issue as a correctness concern rather than security, noting that NFS file handles must behave persistently.

This Week: Brauner's Defense of Architectural Separation

On January 14, Christian Brauner responded to Christoph Hellwig's skepticism with a firm defense of separating file handle operations from export operations in his sole message this week:

"File handles can legitimately be conceptualized independently of exporting a filesystem. If we wanted to tear those concepts apart implementation wise we could."

Brauner rejected the notion that all filesystems with export_operations should be NFS-exportable:

"It is complete nonsense to expect the kernel to support exporting any arbitrary internal filesystem or to not support file handles at all."

He emphasized that the implementation details are secondary to the core argument made by Jeff Layton and Amir Goldstein — that it is sensible to allow one capability (file handles via open_by_handle_at()) without implying the other (NFS export):

"The point Jeff and Amir are making that it is sensible to allow one without the other."

Brauner dismissed concerns about userspace alternatives enabling the same behavior:

"Whether or not some userspace crap allows you to achieve the same thing is entirely irrelevant and does not at all imply we have to allow the same crap in the kernel."

Evolution of the Discussion

This thread represents the culmination of a multi-day debate that converged on several key points across related threads this week:

  1. Hellwig shifted from skepticism to agreement that the problem is about broken semantics — filesystems with non-persistent file handles violating export_operations assumptions — rather than arbitrary export permissions in a related thread:

    "If we do have file systems that break the original exportfs semantics we need to fix that, and something like a 'stable handles' flag will work well for that. But a totally arbitrary 'is exportable' flag is total nonsense."

  2. Amir Goldstein proposed concrete terminology — EXPORT_OP_PERSISTENT_HANDLES — grounded in NFS protocol specifications in a related thread:

    "Very well then. How about EXPORT_OP_PERSISTENT_HANDLES? This terminology is from the NFS protocol spec and it is also used to describe the same trait in SMB protocol."

  3. Chuck Lever clarified tmpfs semantics, noting that tmpfs file handles are persistent within their natural lifetime in a related thread:

    "tmpfs filehandles align quite well with the traditional definition of persistent filehandles. tmpfs filehandles live as long as tmpfs files do, and that is all that is required to be considered 'persistent'."

Impact on NFS Client Development

This discussion has several implications for NFS client and server development:

  1. NFS server (nfsd) correctness: The proposed EXPORT_OP_PERSISTENT_HANDLES flag would prevent nfsd from exporting filesystems with non-persistent file handles, avoiding broken export scenarios where file handles become invalid after reboot or during normal operation.

  2. NFS client stability: Clients relying on persistent file handles (e.g., for state recovery, cache coherency) would be protected from servers that inadvertently export filesystems with volatile handles — a scenario that could cause client hangs or data corruption.

  3. kernfs-based filesystems excluded: cgroupfs, nsfs, and pidfs would not be NFS-exportable by default, preventing "remote partial resource management" through the cgroup tree, as Brauner described in earlier messages:

    "I don't think we want to expose cgroupfs via NFS that's super weird. It's like remote partial resource management and it would be very strange if a remote process suddenly would be able to move things around in the cgroup tree."

  4. New filesystem integration: Any new filesystem intending to support NFS export must now consider whether its file handles are persistent and set the appropriate flag accordingly.

Final Conclusions

The lease opt-in series itself is complete (applied to vfs-7.0.leases). The NFS export discussion has converged on a "persistent handles" flag approach rather than an arbitrary "is_exportable" predicate. Brauner's message this week provides the strongest articulation of the architectural rationale: file handles and NFS export are conceptually distinct capabilities, and the kernel should reflect that distinction in its implementation.

The discussion remains open for further refinement, particularly around the interaction between the kernel-level flag and exportfs user-space options. This was identified as a potential LSF/MM topic in prior weeks' summaries.
