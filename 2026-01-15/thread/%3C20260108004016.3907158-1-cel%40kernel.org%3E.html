NFSv4 State Revocation: fs_pin Rejected, SRCU Notifier Proposed

Summary

Automatic NFSv4 State Revocation on Filesystem Unmount: Architectural Reassessment

Overview

This week's discussion centered on Chuck Lever's [PATCH v2 0/6] Automatic NFSv4 state revocation on filesystem unmount series, which was initially submitted last week. The series aims to automatically revoke NFSv4 client state (opens, locks, delegations) when an exported filesystem is unmounted — eliminating the need for administrators to manually invoke /proc/fs/nfsd/unlock_fs. This is classified as a new feature for the NFS server (NFSD).

The week's activity was dominated by VFS maintainers raising fundamental concerns about the fs_pin infrastructure that the series relies upon, ultimately signaling that the current approach may need to be abandoned in favor of an alternative mechanism.

Key Technical Arguments

The fs_pin Infrastructure Is Not a Good Foundation

The most consequential development this week was VFS maintainer Al Viro's strong objection to building new NFSD infrastructure on top of fs_pin:

"FWIW, fs_pin had never been a good API and experiments with using it for core stuff had failed - we ended up with dput_to_list() and teaching shrink lists to DTRT with mixed-fs lists instead. TBH, I'd rather not see it growing more users." Al Viro

This concern was echoed by Jeff Layton, who noted that fs_pin's sole current consumer — BSD process accounting — is slated for removal:

"One thing I want to point out here is that the only user of fs_pin is the BSD process accounting subsystem, which would be really nice to get rid of at some point." Jeff Layton

Chuck Lever acknowledged the feedback and conceded that a different approach would be needed:

"Fair enough. I will look for a different solution." Chuck Lever

Per-Mount vs. Per-Superblock Granularity

Al Viro also identified a deeper architectural issue: the series conflates per-mount and per-superblock semantics:

"more serious problem is that you are mixing per-mount and per-fs things here." Al Viro

In response, Chuck Lever clarified the distinction between pin_insert() (per-mount) and pin_insert_sb() (per-superblock):

"The 'locking context' rationale in the commit message is stale. The actual distinction between pin_insert() and pin_insert_sb() is semantic: per-mount versus per-superblock granularity." Chuck Lever

NeilBrown (from prior week, referenced this week) had raised concern that unmounting a bind mount would revoke NFSv4 state for the entire filesystem — an unintended side effect of superblock-level pins. Chuck Lever agreed:

"I agree that isn't the desired behavior." Chuck Lever

The Write Count Problem

Al Viro probed whether NFSD's open files would prevent read-only remounts even after unexport, demonstrating with a shell example that any file opened for write blocks remount,ro until the final fput():

"You don't need to be in the middle of write(2); just having a file opened for write prevents r/o remount." Al Viro

He then asked Chuck Lever to clarify the desired semantics:

"Do you want to be able to * umount without an unexport? * remount read-only without an unexport?" Al Viro

Chuck Lever clarified that unexport should remain a prerequisite for configuration changes, and the goal is to make unmount work reliably after unexport:

"I think unexport is a reasonable pre-requisite for any configuration changes to the local mount on the NFS server. So IMHO we don't want either of those." Chuck Lever

"The issue I'm trying to resolve is that even after unexport, unmount doesn't work reliably. Triggering 'unlock_filesystem' automatically on unmount should be able to mitigate or fully address that." Chuck Lever

Proposed Alternative: SRCU Notifier Chain

Jeff Layton proposed an alternative mechanism that avoids fs_pin entirely:

"An alternate idea might be to plumb an srcu notifier chain into the umount codepath, similar to the lease_notifier_chain in fs/locks.c. Then nfsd could register to be notified when there is a umount attempt and do the right thing to tear down state." Jeff Layton

Christian Brauner, another VFS maintainer, endorsed this direction:

"Doesn't sound too bad." Christian Brauner

Final Conclusions

The discussion this week resulted in a clear pivot away from the fs_pin-based approach:

  1. fs_pin is not suitable as a foundation for NFSD's unmount notification, per Al Viro's authoritative assessment that it "had never been a good API" and should not grow new users.

  2. The SRCU notifier chain proposed by Jeff Layton has received positive feedback from both Christian Brauner and appears to be the preferred path forward for v3 of this series.

  3. The problem statement remains valid: After unexport, NFSv4 client state (opens, locks, delegations) keeps files open on the server, preventing clean unmount. The goal is automatic cleanup at unmount time, with unexport remaining a prerequisite.

  4. A v3 redesign is expected that replaces fs_pin with an SRCU-based notifier mechanism in the VFS unmount path, analogous to the existing lease_notifier_chain in fs/locks.c.

This represents a significant course correction for NFS server development, with the architectural foundation of the feature being reworked before implementation details can be finalized.
