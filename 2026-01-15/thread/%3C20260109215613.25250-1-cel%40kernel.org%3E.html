NFSD: Asynchronous Write Throttling for UNSTABLE WRITEs (RFC v2 Discussion)

Summary

NFSD: Asynchronous Write Throttling for UNSTABLE WRITEs (RFC PATCH v2)

Classification: New feature / protocol-level flow control mechanism
Status: RFC discussion; no consensus reached this week.

Overview

Chuck Lever proposed an RFC patch series aimed at improving NFSD's resilience under memory pressure by introducing asynchronous write throttling specifically for UNSTABLE WRITE operations. The proposal seeks to prevent server-side memory exhaustion caused by high rates of uncommitted write payloads, a problem that has been observed in production environments including Hammerspace deployments.

Key Technical Arguments

Chuck Lever's Proposal

Chuck Lever introduced the patch on January 9th, explaining the core problem:

"When memory pressure occurs during buffered writes, the traditional approach is for balance_dirty_pages() to put the writing thread to sleep until dirty pages are flushed. For NFSD, this means server threads block waiting for I/O, reducing overall server throughput."

The proposed solution uses the BDP_ASYNC flag with balance_dirty_pages_ratelimited_flags() to check memory pressure before performing a buffered write. If the call returns -EAGAIN (indicating memory exhaustion), NFSD returns NFS4ERR_DELAY (or NFSERR_JUKEBOX for NFSv3) to the client, prompting the client to wait and retry rather than tying up server memory with cached uncommitted write payloads.

Key changes from RFC v1:

  • Removal of an experimental debugfs setting
  • Throttling enforcement restricted specifically to UNSTABLE WRITEs only

NeilBrown's Critique

NeilBrown raised several concerns about the approach on January 10th, questioning whether the mechanism would work reliably:

"I doubt that this will do what you want - at least not reliably."

His primary objection centered on how balance_dirty_pages_ratelimited_flags() operates:

"balance_dirty_pages_ratelimited_flags() assumes it will be called repeatedly by the same task and it lets that task write for a while, then blocks it, then lets it write some more. The way you have integrated it into nfsd could result in the write load bouncing around among different threads and behaving inconsistently."

NeilBrown also noted that the delay imposed (100ms to 15 seconds) may be too long compared to what would be desirable, suggesting:

"What we really want, I think, is to be able to push back on the client by limiting the number of bytes in unacknowledged writes, but I don't think NFS has any mechanism for that."

He speculated about a deeper integration with writeback code and suggested that allowing the thread pool to grow might make this a non-problem.

Chuck Lever's Rebuttal

Chuck Lever responded on January 10th, clarifying his intent:

"Set aside my threading comments for a moment. What I'm trying to prevent is UNSTABLE WRITEs tying up server /memory/. When under memory pressure, NFSD needs to delay UNSTABLE WRITEs until there is adequate memory to cache the WRITE payloads, without having to evict something more critical that could cause the server significant heartburn or livelock."

He dismissed the thread pool growth suggestion:

"I think allowing the thread pool to grow could make the memory problem worse."

Chuck Lever also proposed an alternative idea involving cgroup-based memory constraints for svc threads.

The Underlying Problem: Server Memory Exhaustion

In a follow-up exchange, NeilBrown pressed for concrete symptoms:

"What exactly is 'the memory problem'? Do you have specific symptoms you are trying to address? Have you had NFS server run out of memory and grind to a halt?"

Chuck Lever pointed to prior work by Mike on direct I/O over the past nine months:

"Review the past 9 months of Mike's work on direct I/O, published on this mailing list. Hammerspace has measured this misbehavior and experienced server melt-down. Their solution is to avoid using the page cache entirely."

He characterized the issue as an effective denial-of-service vector:

"But even so there still seems to be an effective denial-of-service vector by overloading NFSD with UNSTABLE WRITE traffic faster than it can push it to persistence."

Evolution of the Discussion

The conversation evolved toward broader architectural considerations. NeilBrown asked whether Chuck Lever was seeking an alternative to existing mechanisms like drop-behind and direct I/O:

"Are you trying to find another way to address the same problem?"

Chuck Lever confirmed this on January 12th, emphasizing the need for LTS kernel compatibility:

"Yes. I don't think we can backport direct I/O, for example, to LTS kernels. I expect it will be important to have an alternative to the new I/O caching modes for this reason alone."

He also dismissed drop-behind as insufficient:

"Drop-behind is too inefficient to be used here. This is why direct I/O is also an option. Direct I/O is measurably superior to drop-behind."

Final Conclusions

No definitive conclusion was reached this week. The discussion highlighted several key points:

  1. The problem is real: Server memory exhaustion under heavy UNSTABLE WRITE traffic has been observed in production (notably by Hammerspace), leading to server "melt-down" scenarios.

  2. The proposed solution has architectural concerns: NeilBrown raised valid questions about the interaction between NFSD's multi-threaded architecture and the per-task assumptions of balance_dirty_pages_ratelimited_flags().

  3. Testing is needed: Both participants acknowledged that empirical testing under realistic load conditions would be essential to validate or refute the approach. As Chuck Lever noted, "Perhaps we need better observability first."

  4. Broader context: This discussion sits within a larger effort to improve NFSD's I/O handling, including direct I/O support and alternative caching modes. The challenge is finding solutions that can be backported to LTS kernels where newer features like direct I/O may not be available.

The thread remains open with no clear path forward identified this week. Further exploration of cgroup-based memory constraints, improved observability, and deeper integration with the writeback subsystem were suggested as potential directions.
