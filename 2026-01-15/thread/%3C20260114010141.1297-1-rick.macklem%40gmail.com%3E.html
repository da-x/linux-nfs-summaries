NFSv4.2 POSIX ACL Client: Standalone Repost of SB_POSIXACL Patch

Classification: New feature (protocol extension implementation)

Overview

On January 14, Rick Macklem posted a standalone message re-submitting [PATCH v2 7/8] from his eight-patch series adding client-side support for the NFSv4.2 POSIX draft ACL extension:

"Check to see if both the POSIX draft default ACL and POSIX draft access ACL are supported by the server. If so, set SB_POSIXACL." Rick Macklem

This message is a repost of patch 7/8 from the v2 series originally submitted on January 3 (see prior summary). The thread contains only this single message, with no review feedback or replies during the current reporting week.

Background: The Broader POSIX ACL Client Series

The broader eight-patch v2 series (PATCH v2 0/8) implements a sideband protocol for NFSv4.2 that allows POSIX draft ACLs to be acquired and set directly — bypassing the lossy "loosey" NFSv4-to-POSIX ACL mapping algorithm. As Rick Macklem explained in the v2 cover letter:

"The Internet draft 'POSIX Draft ACL support for Network File System Version 4, Minor Version 2' describes an extension to NFSv4.2 so that POSIX draft ACLs can get acquired and set directly, without using the loosey NFSv4->POSIX draft mapping algorithm. It extends the protocol with four new attributes."

Patch 7/8 specifically sets the SB_POSIXACL superblock flag when the server advertises support for both POSIX draft default ACL and POSIX draft access ACL attributes. This is essential for enabling proper VFS-level POSIX ACL semantics on NFSv4.2 mounts, allowing tools like getfacl(1) and setfacl(1) to work transparently over the network mount.

Prior Review Context: The CONFIG_NFS_V4 Build Issue

In the prior week's activity, Anna Schumaker identified a build issue with this same patch (v2 7/8): the code accesses server->attr_bitmask in fs/nfs/super.c, but this member only exists when the kernel is configured with CONFIG_NFS_V4=y. She reported:

"Just a heads up that server->attr_bitmask only exists if the kernel is configured with CONFIG_NFS_V4=y, so the compiler will complain about this:" Anna Schumaker

Rick Macklem responded that an #ifdef guard was the appropriate fix, but noted he could not move the code to NFSv4-specific paths due to module dependency cycles:

"I think hiding it behind an #ifdef is the obvious solution." Rick Macklem

"I cannot see how the NFSv4 specific code gets called when the superblock gets set up. I know that the generic superblock code cannot call anything in the NFSv4 code. Already made that mistake and ended up with a cycle in the module dependencies." Rick Macklem

Rick also noted a timeline constraint:

"I can repost the patch in a couple of weeks. (I have limited access to the Linux system I run at home until end of March.)" Rick Macklem

The standalone repost of patch 7/8 does not appear to include any changes beyond the original v2 content, suggesting this may have been an administrative resend or a partial re-post rather than a substantive update.

Significance

This feature represents a significant enhancement for NFS client development, enabling native POSIX ACL support over NFSv4.2 and eliminating the need for lossy translation between NFSv4 ACLs and POSIX draft ACLs when both ends of the connection support the extension — an important improvement for enterprise environments relying on fine-grained access control.
