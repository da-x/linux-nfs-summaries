Brauner and Hellwig Converge on Persistent Handles Flag for NFS Export Control

Summary

VFS Lease Opt-In: Brauner and Hellwig Clash Over NFS Export Policy

Overview

This thread captures the final exchanges in a multi-day debate about whether kernfs-based filesystems (cgroupfs, nsfs, pidfs) should be NFS-exportable. The discussion was spawned by Jeff Layton's 24-patch series to require filesystems to explicitly opt-in to lease support, which was applied to vfs-7.0.leases on January 12. This week's two messages represent the closing arguments between Christian Brauner and Christoph Hellwig on the broader question of NFS export controls.

This is classified as a VFS/NFS protocol architectural discussion, not a bug fix or new feature implementation. No patches were submitted this week.

Background (Brief Bridge)

The debate originated when Layton observed that export_operations — originally designed for NFS export — are now also used by filesystems like kernfs solely for open_by_handle_at() support:

"At one time, those were only defined by filesystems that wanted to allow NFS export. Now we've grown them on filesystems that just want to provide filehandles for open_by_handle_at() and the like. nfsd doesn't care though: if the fs has export operations, it'll happily use them." — Jeff Layton

The core concern: kernfs-based filesystems have non-persistent file handles that violate NFS protocol assumptions, yet nfsd treats any filesystem with export_operations as exportable. Over the course of the week, participants converged on a proposed EXPORT_OP_PERSISTENT_HANDLES flag to distinguish filesystems suitable for NFS export from those merely supporting local file handle operations.

This Week's Messages

Brauner: File Handles and NFS Export Must Be Separated

On January 14, Christian Brauner responded to Christoph Hellwig's skepticism about the value of explicitly prohibiting NFS export of kernfs-based filesystems. Hellwig had argued that if administrators want to export such filesystems, they will find a way (userspace NFS servers, Samba, FUSE), and questioned what benefit explicit prohibition provides.

Brauner delivered a forceful rebuttal on January 14:

"File handles can legitimately be conceptualized independently of exporting a filesystem. If we wanted to tear those concepts apart implementation wise we could."

He rejected the notion that all filesystems with export_operations should be NFS-exportable:

"It is complete nonsense to expect the kernel to support exporting any arbitrary internal filesystem or to not support file handles at all."

Brauner emphasized that the implementation details are secondary to the core argument made by Layton and Amir Goldstein — that it is sensible to allow one capability (file handles via open_by_handle_at()) without implying the other (NFS export):

"The point Jeff and Amir are making that it is sensible to allow one without the other."

He dismissed concerns about userspace alternatives enabling the same behavior:

"Whether or not some userspace crap allows you to achieve the same thing is entirely irrelevant and does not at all imply we have to allow the same crap in the kernel."

In a brief follow-up on January 14, Brauner also addressed Layton's concern about file handle stability across reboots for kernfs filesystems:

"They aren't and it's not desirable."

Hellwig: Convergence on Technical Grounds

On January 15, Christoph Hellwig responded to Brauner's firm position on January 15, acknowledging that the lack of stable file handles is indeed the technical argument at hand:

"None of that is a technical argument. The lack of stable file handles would be one, and I think we came to the conclusion yesterday that this is the case."

Hellwig clarified his position on the broader question of whether all filesystems meeting technical requirements should be exportable:

"If a file systems meets all technical requirements of being nfsd exportable and the users asks for it, it is not our job to make an arbitrary policy decision to say no."

He continued, distinguishing between technical correctness and arbitrary prohibition:

"If it does not meet the technical requirements it obviously should not be exportable. And it seems like the spread of file handles beyond nfs exporting created some ambiguity here, which we need to fix."

Key Technical Arguments

  1. The core problem is broken semantics, not security: Hellwig's pivot during the week was decisive — the issue is that export_operations were overloaded with dual semantics (NFS export vs. open_by_handle_at()), and filesystems with non-persistent file handles violate the original assumptions of the export infrastructure. As he stated in a related thread:

    "If we do have file systems that break the original exportfs semantics we need to fix that, and something like a 'stable handles' flag will work well for that. But a totally arbitrary 'is exportable' flag is total nonsense."

  2. Persistent handles as the criterion: Amir Goldstein's EXPORT_OP_PERSISTENT_HANDLES proposal gained traction because it grounds the solution in NFS protocol terminology rather than an arbitrary "is_exportable" flag. This was endorsed by Hellwig, Brauner, and implicitly by Layton.

  3. kernfs filesystems must be excluded: Brauner's hard NAK on cgroupfs, nsfs, and pidfs export is based on both correctness (non-persistent handles) and semantics (these are local resource management interfaces that make no sense remotely). As he noted in a related thread:

    "cgroupfs shows local processes. So a server will see completely nonsensical PID identifiers listed in cgroup files and it can fsck around with processes in a remote system. Hard NAK."

  4. tmpfs is not a problem case: Hellwig's clarification that tmpfs handles are stable within their mount lifetime resolves a potential edge case, meaning tmpfs exports would continue to work naturally under the proposed flag:

    "tmpfs handles are stable. It's the tmpfs files that don't survive an unmount or reboot.."

Impact on NFS Client Development

While this discussion primarily concerns NFS server (nfsd) behavior, it has important implications for NFS client development:

  1. Client stability: NFS clients relying on persistent file handles for state recovery, cache coherency, and delegation management would be protected from servers that inadvertently export filesystems with volatile handles — a scenario that could cause client hangs or data corruption. As David Laight noted in a related thread:

    "You really shouldn't be allowed to nfs export a fs that doesn't have persistent file handles."

  2. Delegation correctness: The lease opt-in series (now applied) and the proposed export opt-in mechanism together ensure that NFS delegations are only granted on filesystems that properly support both leases and persistent file handles — a prerequisite for correct delegation recall and revocation semantics.

  3. New filesystem integration: Any new filesystem intended to be NFS-exportable must now explicitly implement ->setlease (per the applied series) and set an EXPORT_OP_PERSISTENT_HANDLES flag (proposed but not yet implemented). This two-gate approach prevents future regressions in NFS client/server interoperability.

Final Conclusions

The lease opt-in series is complete (applied to vfs-7.0.leases). The NFS export discussion has converged on a "persistent handles" flag approach, with key participants agreeing that:

  • The problem is broken semantics caused by overloading export_operations, not an arbitrary policy decision about what should be exportable.
  • EXPORT_OP_PERSISTENT_HANDLES is the preferred terminology, grounded in NFS protocol specifications.
  • kernfs-based filesystems (cgroupfs, nsfs, pidfs) must not be NFS-exportable due to non-persistent handles and semantic mismatch.
  • tmpfs exports remain valid because its file handles are persistent within their mount lifetime.

As Brauner concluded in a related thread:

"We are all in agreement here."

The discussion remains open for further refinement, particularly around the interaction between a kernel-level flag and exportfs user-space options. This was identified as a potential LSF/MM topic for continued discussion.
