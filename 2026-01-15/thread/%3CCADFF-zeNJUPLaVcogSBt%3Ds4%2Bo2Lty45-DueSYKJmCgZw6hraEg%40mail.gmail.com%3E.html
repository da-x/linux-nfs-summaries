fscache/NFS Re-export Server Lockup: nfs_release_folio Deadlock Fix Identified

Summary

fscache/NFS Re-export Server Lockup: Deadlock Fix Identified, Testing Pending

Classification: Bug fix (NFS client deadlock in nfs_release_folio() during NFS re-export with fscache/cachefiles).

Background (Prior Week)

This thread originated on December 19, 2025, when Mike Owen reported persistent server lockups on Ubuntu 24.04-based NFS re-export servers using fscache to cache data from Isilon and NetApp filers over NFSv3, while serving clients over NFSv4. The symptoms included complete system deadlocks with hung tasks in kcompactd, kjournald2, and nfsd threads, followed by cache corruption (terabytes of cached data lost after reboot).

This Week's Activity

Initial Follow-up and Context Expansion

On January 9, Mike Owen responded to earlier diagnostic suggestions from Daire Byrne here, confirming that the machine was dedicated solely to KNFSD caching duties and that the issue occurred even at low cache utilization (~10–20% of NVMe capacity). Owen noted:

"We did try running 6.17.0 but made no difference."

He also referenced a related thread with Chuck Lever regarding "refcount_t underflow (nfsd4_sequence_done?) with v6.18 re-export" and suggested commits to investigate, including cbfd91d22776 ("nfsd: never defer requests during idmap lookup"), speculating that "there is a cascading issue here and we are in need of some NFS patches."

Deadlock Fix Identified by Mike Snitzer

On January 10, Mike Snitzer provided the critical breakthrough here. He identified a specific commit from Trond Myklebust that should address the deadlock:

"This commit from Trond, which he'll be sending to Linus soon as part of his 6.19-rc NFS client fixes pull request, should fix the NFS re-export induced nfs_release_folio deadlock reflected in your below stack trace."

Snitzer pointed to commit cce0be6eb4971456b703aaeafd571650d314bcca, which fixes a deadlock in nfs_release_folio() — the same function visible in Owen's stack traces during memory compaction (folio_wait_private_2 → nfs_release_folio). Snitzer confirmed the fix had resolved his own LOCALIO-based re-export deadlock situation and noted:

"I'm doing my part to advocate that Red Hat (Olga cc'd) take this fix into RHEL 10.2 (and backport as needed)."

Testing Plan Confirmed

On January 12, Mike Owen acknowledged the promising lead here:

"Whilst we wait for the necessary NFS client fixes PR, I'll look to add the patch to 6.19-rc5 and report back if this fixes the issue we are seeing."

He also committed to advocating internally for Canonical/Ubuntu to absorb the fix.

Continued Investigation — Distinct Deadlock Path?

On January 15, Mike Owen posted an extensive analysis of his deadlock scenario here, detailing the environment and tracing a complex dependency chain involving fscache cookie state machine timeouts, NFS readahead, cachefiles I/O on ext4, and memory compaction.

Mike Snitzer responded later that day here, noting an important distinction between the two deadlock scenarios:

"OK, my deadlock was blocked in wait_on_commit whereas you've consistently shown folio_wait_private_2 in your stack traces (I originally missed that detail). So I'm not aware of what is different in your setup.. devil is in the details, but maybe its your use of fscache?"

Snitzer suggested that David Howells (fscache maintainer) may need to weigh in from an fscache-specific perspective, and praised Owen's detailed analysis while noting it would be most useful for informing the fscache subsystem maintainers.

Key Technical Arguments

  1. Root Cause Hypothesis: The deadlock involves nfs_release_folio() performing synchronous operations during memory reclaim/compaction in an NFS re-export scenario with fscache, creating a circular dependency where page migration cannot complete because the NFS client is blocked waiting on I/O that itself depends on memory allocation.

  2. Proposed Fix: Trond Myklebust's commit cce0be6eb497 transforms nfs_release_folio() to avoid synchronous waits, instead using asynchronous writeback/commit kicks via a new nfs_wb_folio_reclaim() helper — the same approach that resolved Wang Zhaolong's slot table draining deadlock and Snitzer's LOCALIO re-export deadlock.

  3. Open Question: Whether Owen's fscache-specific stack trace (blocked in folio_wait_private_2 rather than wait_on_commit) represents a distinct variant of the same bug or a separate fscache-related issue requiring additional investigation by David Howells.

Final Conclusions

  • The discussion has converged on a specific upstream fix (cce0be6eb497) from Trond Myklebust that addresses the nfs_release_folio() deadlock in NFS re-export scenarios.
  • Mike Owen plans to test the patch against kernel 6.19-rc5 and report results.
  • Distribution backporting efforts are underway for both RHEL (advocated by Snitzer) and Ubuntu/Canonical (advocated by Owen).
  • The interaction between fscache and the NFS client's folio release path remains an area requiring further scrutiny, with David Howells potentially needed to provide additional insight.
