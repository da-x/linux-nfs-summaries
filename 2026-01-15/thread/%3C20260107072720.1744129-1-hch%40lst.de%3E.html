NFS Delegation LRU: Server vs. Client Recall Debate and RECALL_ANY Bug Identified

Summary

NFS Client Delegation LRU: Debate on Server vs. Client Recall Responsibility

Overview

This week's discussion continued the review of Christoph Hellwig's 24-patch series to introduce an LRU-based eviction policy for NFS client delegations, which was posted last week. The focus shifted from architectural details to a broader philosophical debate about delegation recall strategy: should clients proactively return delegations based on local heuristics, or should servers drive recalls through protocol mechanisms like RECALL_ANY?

Evolution of the Discussion

Sagi Grimberg's Endorsement and RECALL_ANY Observation

The week opened with Sagi Grimberg signaling his support for Hellwig's series while raising an implementation concern about the existing RECALL_ANY handling. He acknowledged Hellwig's dismissal of more complex eviction heuristics:

"I understand. Regardless, this patchset is an obvious win IMO."

As noted by Sagi Grimberg, he then pointed out a gap in the client's RECALL_ANY implementation:

"And I see that the client does not pay attention to that keep arg, it nukes all the delegs afaict..."

This observation highlights a bug or shortcoming in the current NFS client: when the server issues a RECALL_ANY with a "keep" parameter (specifying how many delegations the client should retain), the client ignores this value and returns all delegations indiscriminately. This is significant because Hellwig had previously mentioned that proper RECALL_ANY support could complement the LRU mechanism, reclaiming from the end of the LRU list when requested by the server.

Server vs. Client Interests: A Nuanced Debate

Grimberg continued pushing back on Chuck Lever's assertion that server and client interests are purely orthogonal. In a follow-up message [5ae5ed3a-5351-4dc1-98e4-0f31653ee2b6@grimberg.me], he argued:

"They both share the interest of reducing rpc calls..."

Grimberg's position was that the client, lacking knowledge about other clients or server resource pressure, may prefer to hoard delegations defensively:

"However arguably the client may want keep delegation states around for as long as it can 'just in case' the application opens the file again (the client doesn't know the nature of the workload) assuming they fit in client memory. It doesn't know anything about other clients nor the server resources."

He contrasted this with the server's vantage point:

"The server on the other hand, has the knowledge of what delegations conflict (or may conflict) and act accordingly (not grant or recall)."

Trond Myklebust Enters: The rm -rf Counterargument

NFS client maintainer Trond Myklebust weighed in with a practical counterexample to Grimberg's server-centric view. He warned against blindly extending delegation retention times, citing the destructive workload scenario:

"You can't just assume this: it really depends heavily on the workload. Imagine an 'rm -rf' operation if you have to recall delegations from various clients on all the files in the tree because they are caching read delegations 'just in case'."

As explained by Trond Myklebust, the current behavior is grounded in a pragmatic assumption:

"The current behaviour is based on the assumption that if your application has not locally reopened the file for several minutes, then that RPC call to reopen it on the server is by comparison not particularly expensive."

He emphasized that data caching (via change attributes) remains effective even without delegation state, and that any write attempt would trigger recalls anyway. His conclusion was measured but firm:

"IOW: Before agreeing to change the delegation expiration times, I'd like to see actual data that justifies caching for longer as a general rule, rather than just relying on peoples' assumptions that this is the case."

Grimberg's Concession and an Opportunistic Idea

Grimberg responded constructively [2b1e83fc-4765-4e8c-93dd-a74698a3fe03@grimberg.me], conceding that Trond's concern was valid while reframing the issue as one of server responsibility:

"Isn't that a concern of the server though? IMO the server should be the one that can both track and account for other clients. Seems to me that giving up the delegation just because some other client may modify the file is an assumption that the nfs client takes without basing it on real data."

He then proposed an interesting optimization idea — using WANT_DELEGATION opportunistically in GETATTR compounds to acquire read delegations during stat operations, not just open operations:

"The use-case where I think this assumption does not hold is when the client does not open the file, but rather stat it. Perhaps that case can be mitigated if the client can add an opportunistic WANT_DELEG in the GETATTR compound to ask for a read delegation."

Grimberg ultimately agreed with Trond's data-driven approach:

"That makes perfect sense to me Trond."

Hellwig's Final Nudge

The week closed with Christoph Hellwig posting a lighthearted but pointed message [20260115162437.GA17257@lst.de], seeking feedback on the series itself rather than speculative enhancements:

"Any comments on this series except how to make it more complicated? :)"

This suggests that Hellwig was eager to move forward with the current design, which focuses on a simple LRU-based eviction policy without additional complexity.

Key Technical Arguments

  1. RECALL_ANY Implementation Gap: The NFS client currently ignores the "keep" argument in RECALL_ANY recalls, returning all delegations regardless of the server's request. This is a latent bug that could be addressed alongside or after the LRU series.

  2. Client vs. Server Recall Responsibility: The debate centered on whether delegation recall decisions should be client-driven (based on local usage patterns) or server-driven (based on global resource pressure and conflict awareness). Trond Myklebust argued for maintaining client-side proactivity, citing workloads like rm -rf where excessive delegation retention would cause costly recalls.

  3. Opportunistic Delegation Acquisition: Grimberg suggested that the client could request read delegations during GETATTR operations (e.g., stat calls) via WANT_DELEGATION, potentially reducing RPC overhead for workloads that frequently stat but rarely open files.

  4. Data-Driven Policy Decisions: Trond Myklebust emphasized the need for empirical evidence before changing delegation expiration policies, rather than relying on assumptions about workload behavior.

Classification

This discussion is primarily about a new feature (LRU-based delegation eviction) with secondary implications for bug fixes (the RECALL_ANY "keep" argument handling). The debate also touches on potential future protocol-level enhancements (WANT_DELEGATION in GETATTR, improved RECALL_ANY support).

Final Conclusions

  • Hellwig's LRU-based delegation eviction series received explicit endorsement from Sagi Grimberg ("an obvious win").
  • No substantive objections to the series were raised this week; the discussion focused instead on broader design philosophy.
  • A concrete bug was identified: the NFS client ignores the "keep" parameter in RECALL_ANY operations.
  • The community agreed that future delegation policy changes should be data-driven rather than assumption-based.
  • Hellwig's closing message suggests he is ready to proceed with the series as-is, pending any remaining review feedback.
