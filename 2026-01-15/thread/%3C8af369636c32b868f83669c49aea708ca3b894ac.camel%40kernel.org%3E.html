NFS Export: Converging on Persistent Handles Flag for export_operations

Summary

VFS Lease Opt-In: Refining NFS Export Semantics Around Persistent File Handles

Overview

This thread is a continuation of the broader VFS lease opt-in discussion that began earlier this week. The 24-patch series requiring filesystems to explicitly opt-in to lease support was already applied to vfs-7.0.leases by Christian Brauner on January 12. This week's four messages focus exclusively on a side discussion about NFS export controls — specifically, how to handle filesystems that have export_operations for open_by_handle_at() but should not be exported via NFS due to non-persistent file handles.

This is classified as a protocol/architectural discussion with direct implications for NFS server (nfsd) and client development. No patches were submitted this week; the conversation centers on refining the design of an export opt-in mechanism.

Background (from Prior Summaries)

The lease opt-in series was applied earlier this week, and a significant side debate emerged about whether NFS export should similarly become explicit opt-in. The concern: kernfs-based filesystems (cgroupfs, pidfs, nsfs) gained export_operations for open_by_handle_at() support, but nfsd treats any filesystem with export_operations as exportable — despite these filesystems having non-persistent file handles that would break NFS semantics.

Key prior positions:

  • Christian Brauner argued for severing file handle operations from the export mechanism entirely on January 13.
  • Christoph Hellwig questioned the value of explicit prohibition, noting administrators who want to export will find a way.
  • Amir Goldstein reframed the issue as one of correctness rather than security, highlighting that NFS file handles must behave persistently on January 14.

This Week: Converging on "Persistent Handles" Semantics

Hellwig Agrees the Core Problem Is Broken Semantics

Christoph Hellwig responded to Amir Goldstein's correctness argument, clarifying his position on January 14:

"That is not just very strange, but actually broken (discounting the obscure volatile file handles features not implemented in Linux NFS and NFSD). And the export ops always worked under the assumption that these file handles are indeed persistent. If they're not we do have a problem."

Hellwig drew a critical distinction between two categories:

"Because 'want to export' is a stupid category. OTOH 'NFS exporting doesn't actually properly work because someone overloaded export_ops with different semantics' is a valid category."

He rejected an arbitrary "is_exportable" flag but endorsed a solution grounded in the actual semantic problem:

"If we do have file systems that break the original exportfs semantics we need to fix that, and something like a 'stable handles' flag will work well for that. But a totally arbitrary 'is exportable' flag is total nonsense."

Layton Confirms cgroupfs Export Is Broken in Practice

Jeff Layton provided practical evidence that exporting kernfs-based filesystems via NFS does not function correctly on January 14:

"cgroupfs definitely doesn't behave as expected when exported via NFS. The files aren't readable, at least. I'd also be surprised if the filehandles were stable across a reboot, which is sort of necessary for proper operation."

He reiterated his preference for deliberate opt-in:

"I'd prefer that we require someone to take the deliberate step to say 'yes, allow nfsd to access this type of filesystem'."

However, Layton raised an important complication — tmpfs remains a special case:

"The problem there is that we very much do want to keep tmpfs exportable, but it doesn't have stable handles (per-se)."

Amir Goldstein Proposes EXPORT_OP_PERSISTENT_HANDLES

Building on Hellwig's endorsement of a "stable handles" flag, Amir Goldstein proposed concrete terminology on January 14:

"Very well then. How about EXPORT_OP_PERSISTENT_HANDLES? This terminology is from the NFS protocol spec and it is also used to describe the same trait in SMB protocol."

Amir also suggested an exportfs-level option for administrators:

"How about adding an exportfs option 'persistent_handles', use it as default IFF neither options fsid=, uuid= are used, so that at least when exporting tmpfs, exportfs -v will show 'no_persistent_handles' explicitly?"

Chuck Lever Clarifies tmpfs File Handle Semantics

Chuck Lever pushed back on the characterization of tmpfs file handles as non-persistent on January 14:

"I think we need to be careful. tmpfs filehandles align quite well with the traditional definition of persistent filehandles. tmpfs filehandles live as long as tmpfs files do, and that is all that is required to be considered 'persistent'."

This clarification suggests tmpfs may not need special treatment under a PERSISTENT_HANDLES flag — its handles are persistent within the lifetime of the filesystem, which satisfies NFS requirements.

Evolution of the Discussion

The conversation this week shows clear convergence:

  1. Hellwig shifted from skepticism to agreement that the problem is about broken semantics (non-persistent file handles violating export_operations assumptions), not about arbitrary export permissions.
  2. Layton provided practical evidence that cgroupfs export is already broken, reinforcing the need for a fix.
  3. Amir Goldstein proposed concrete terminology (EXPORT_OP_PERSISTENT_HANDLES) grounded in NFS protocol specifications.
  4. Chuck Lever clarified tmpfs semantics, potentially simplifying the design by showing tmpfs may naturally qualify as having persistent handles.

Impact on NFS Client and Server Development

This discussion has several implications for NFS development:

  1. NFS server (nfsd) correctness: The proposed EXPORT_OP_PERSISTENT_HANDLES flag would prevent nfsd from exporting filesystems with non-persistent file handles, avoiding broken export scenarios where file handles become invalid after reboot or during normal operation.

  2. NFS client stability: Clients relying on persistent file handles (e.g., for state recovery, cache coherency) would be protected from servers that inadvertently export filesystems with volatile handles — a scenario that could cause client hangs or data corruption.

  3. New filesystem integration: Any new filesystem intending to support NFS export must now consider whether its file handles are persistent and set the appropriate flag accordingly.

  4. tmpfs remains supported: Chuck Lever's clarification suggests tmpfs file handles meet the persistence requirement within their natural lifetime, meaning tmpfs exports would continue to work without special handling.

Final Conclusions

The lease opt-in series itself is complete (applied to vfs-7.0.leases). The NFS export discussion has converged on a "persistent handles" flag approach rather than an arbitrary "is_exportable" predicate. Key agreements:

  • Hellwig and Layton agree the problem is broken semantics, not security per se.
  • Amir Goldstein's EXPORT_OP_PERSISTENT_HANDLES proposal aligns with NFS protocol terminology.
  • Chuck Lever's clarification on tmpfs simplifies the design space.

The discussion remains open for further refinement, particularly around the interaction between the kernel-level flag and exportfs user-space options. This was identified as a potential LSF/MM topic in prior weeks' summaries.
