kNFSD Encrypted Filehandles: Threat Model Debate and Path to v2

Summary

kNFSD Encrypted Filehandles: Threat Model and Design Direction

Classification: New feature proposal (security hardening of NFS file handles).

Overview

Benjamin Coddington (Hammerspace) resumed work on his RFC series to add encrypted file handle support to the Linux NFS server (kNFSD). The week's discussion, concentrated on January 13, revolved around fundamental architectural concerns, the threat model justifying the feature, and the choice of cryptographic primitive. The conversation involved Chuck Lever (NFS maintainer) and Jeff Layton.

Architectural Concern: Per-Thread Buffers and Layering

Coddington's v1 implementation required dynamically allocated buffers per kNFSD thread for hashing file handles using the synchronous crypto API. He proposed attaching a callback to svc_rqst (the SunRPC request structure) so that NFSD could free these buffers when an RPC service thread exits:

"I need small, dynamically allocated buffers for hashing the filehandles, and it makes the most sense to have them per-thread as that's the scope of contention. I want to allocate them once when(if) they are needed, and free them when the thread exits." Ben Coddington

Chuck Lever pushed back strongly on adding NFSD-specific hooks to the SunRPC layer, calling it a "layering violation":

"I'd rather avoid hanging anything NFSD-related off of svc_rqst, which is really an RPC layer object. I know we still have some NFSD-specific fields in there, but those are really technical debt." Chuck Lever

Jeff Layton offered a compromise: adding a generic void *rq_private pointer to svc_rqst, allowing higher-level services like NFSD to attach their own per-thread structures without hardcoding NFSD-specific fields into SunRPC. He noted this could also clean up an existing layering violation by moving the NFS-specific rq_lease_breaker pointer out of svc_rqst:

"I think we need something like this in svc_rqst: void *rq_private; nfsd could hang some sort of struct nfsd_thread_info off of it, other services can just leave it as NULL." Jeff Layton

Threat Model: What Is Being Protected?

A significant portion of the thread was devoted to clarifying why file handle protection is needed. Chuck Lever pressed Coddington to articulate a concrete threat model, noting that other reviewers (Neil Brown and Eric Biggers) had also requested clarification:

"We need to understand your threat model before deciding whether completely obscuring the file handles is more secure than making a cryptographic hash part of the on-the-wire handle." Chuck Lever

"No, what I'm saying is you haven't described your threat model in enough detail to justify the proposed design of encrypting file handles." Chuck Lever

Coddington's core argument: NFS file handles allow clients to access files directly without traversing the directory tree. If file handles are predictable (as they are for some filesystems), a malicious or compromised client could guess file handles and bypass directory-level permission checks. This is particularly relevant in pNFS Flexfiles deployments where Hammerspace Data Servers (DSes) use root_squash exports, and one client may act as a broker handing out file handles to other clients:

"As you know, a client that has a filehandle can access a file without needing to walk the directory tree to the file's location. That walk might have permissions set on parent directories above the file that restrict the walk to the file from that user." Ben Coddington

Chuck Lever challenged whether this is truly unique to NFS or specific to Hammerspace's deployment model:

"And I think that means that every NFS server implementation out there has the same exposure. And wouldn't open_by_filehandle() have the same exposure?" Chuck Lever

Coddington acknowledged that open_by_handle() has similar exposure on local systems but argued that NFS is "a bit more exposed" and that solving it in kNFSD could later be generalized to all exportfs users.

Signing vs. Encryption: The Cryptographic Debate

Chuck Lever questioned whether full encryption (AES) was necessary, suggesting that a cryptographic hash/MAC would suffice to prevent fabrication of file handles:

"What you really want to do is prevent a remote client (maliciously or accidentally) from fabricating a file handle that can be used to access areas of the exported file system that have explicitly not been shared. A hash that cannot be fabricated without the server's secret key would accomplish that, ISTM." Chuck Lever

Coddington argued for encryption over signing on three grounds:

  1. A MAC appends to the file handle (adding 8 bytes), while AES-CBC may sometimes produce smaller handles depending on padding.
  2. With a MAC, having more known file handles could theoretically make it easier to guess the secret key; with full encryption, the plaintext is never exposed to the client.
  3. Non-obscured file handles can leak filesystem-internal information that the NFS server does not control and may not wish to reveal.

Chuck Lever pushed back on each point, noting that transport-level security (krb5p or TLS) should already protect in-transit data, and questioned whether per-user isolation on a shared client could truly be solved by file handle encryption alone:

"Each RPC message protected by krb5p is wrapped by a specific user's Kerberos credentials, so generally speaking another user cannot decrypt that message." Chuck Lever

Coddington countered that transport encryption does not prevent local users on the same client from using open_by_handle() to guess file handles:

"It doesn't matter, because the users on the client can just use open_by_handle() on NFS and guess filehandles." Ben Coddington

Key Rotation and Cryptographic Considerations

Chuck Lever raised important cryptographic concerns about the design:

  • File handles are public and persist for the lifetime of a file, meaning the signing/encryption key cannot be rotated.
  • Billions of file handles may be encrypted or signed by the same key.
  • The file handle plaintext is predictable.

"Filehandles are public and live as long as a file on a filesystem instance. This means (I think) that the signing/encryption key cannot be rotated." Chuck Lever

Coddington acknowledged these concerns but noted that multi-key support could theoretically be added later, allowing a "drain and fill" migration strategy between keys.

Conclusions and Path Forward

The discussion concluded with agreement to restart the review process with a revised v2 submission:

  1. Simpler cryptographic primitive for v2: Chuck Lever recommended starting with siphash rather than AES encryption:

"If you want to prototype something quickly, please use siphash for v2. We need to understand if signing is enough, if encryption is actually required, or if even that isn't sufficient." Chuck Lever

Coddington agreed: "Ok, will do - thanks for your time and engagement on this so far." Ben Coddington

  1. Broader audience: Chuck Lever requested that v2 broaden the CC list to include linux-crypto:

"Let's reset and start over with a v2, and broaden the Cc's." Chuck Lever

  1. Concrete examples required: The maintainer requested specific, concrete attack scenarios tied to particular Linux filesystem implementations:

"Can you provide some specific examples when you repost? For instance, give a particular file system implementation and explain exactly how a plaintext filehandle generated by the filesystem can be used to game the server into accessing a file?" Chuck Lever

Coddington committed to providing these examples in v2.

Significance for NFS Client Development

While this thread focuses on the NFS server (kNFSD), the implications extend to NFS clients. Encrypted or signed file handles would change the semantics of file handle caching and validation on the client side. The discussion also touches on open_by_handle() interactions, which are relevant to any NFS client implementation that supports direct file handle access. The debate over whether transport-level security (krb5p/TLS) is sufficient versus needing application-layer file handle protection has broad relevance for NFS security architecture decisions affecting both clients and servers.
