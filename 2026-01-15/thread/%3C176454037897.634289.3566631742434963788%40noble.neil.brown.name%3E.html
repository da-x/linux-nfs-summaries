FUSE: Fix deadlock in fuse_reverse_inval_entry() from incorrect start_removing() conversion

Summary

FUSE: Fix Deadlock in fuse_reverse_inval_entry() Caused by Incorrect start_removing() Conversion

Classification: Bug Fix (FUSE / VFS)

This thread addresses a regression bug introduced during the recent conversion of FUSE directory operations to use the new centralized locking APIs (start_removing() and related functions). The fix was submitted by NeilBrown and applied by Christian Brauner to the vfs.fixes branch.

Background

Earlier in November 2025, NeilBrown introduced a series of patches to centralize locking for directory operations, including new APIs such as start_creating_noperm() and start_removing_noperm(). As part of this effort, the FUSE function fuse_reverse_inval_entry() was converted to use start_removing(). However, this conversion introduced a subtle but serious issue.

The Problem

As reported by Val Packett, the original implementation of fuse_reverse_inval_entry() did not call the filesystem's ->lookup operation. The new code, however, did invoke ->lookup, which could lead to a deadlock. NeilBrown explained the root cause in his patch:

"The recent conversion of fuse_reverse_inval_entry() to use start_removing() was wrong. As Val Packett points out the original code did not call ->lookup while the new code does. This can lead to a deadlock."

NeilBrown's patch cites the original report from Val Packett and fixes commit c9ba789dad15 ("VFS: introduce start_creating_noperm() and start_removing_noperm()").

The Fix

Rather than reverting to the old approach using full_name_hash() and d_lookup(), NeilBrown proposed a cleaner solution leveraging the newer API try_lookup_noperm(), which combines name hashing and lookup without invoking ->lookup directly. The result is then passed to start_removing_dentry() to obtain the required locks for removal, followed by a double-check that the dentry name has not changed in the meantime.

Key aspects of the fix include:

  • Using try_lookup_noperm() instead of full_name_hash() + d_lookup(), avoiding the problematic ->lookup call.
  • Passing the resulting dentry to start_removing_dentry() for proper lock acquisition.
  • Delaying the dput() on the parent directory until the end of the function, with a NULL-initialized pointer to ensure safe cleanup in all code paths.

The patch modifies fs/fuse/dir.c with 16 insertions and 7 deletions.

Resolution

On January 12, 2026, Christian Brauner confirmed the patch was applied:

"Applied to the vfs.fixes branch of the vfs/vfs.git tree. Patches in the vfs.fixes branch should appear in linux-next soon."

Christian Brauner's confirmation provides the commit hash cab012375122 and directs readers to the vfs.git repository.

Brauner also encouraged further review:

"Please report any outstanding bugs that were missed during review in a new review to the original patch series allowing us to drop it. It's encouraged to provide Acked-bys and Reviewed-bys even though the patch has now been applied."

Significance for NFS Client Development

While this fix targets FUSE rather than NFS directly, it is part of the broader VFS locking refactoring effort that impacts all network filesystem clients. The centralized directory operation locking APIs (start_removing(), start_creating_noperm()) are designed to improve scalability by reducing exclusive lock contention — a concern shared by NFS client development. Bugs in these shared infrastructure components can affect multiple filesystems, making timely fixes like this one important for overall kernel stability.
