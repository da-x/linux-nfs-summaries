Summary

VFS: Lease Opt-In Series Applied; Discussion on NFS Export Controls

Overview

This week, Jeff Layton's 24-patch series to require filesystems to explicitly opt-in to lease support was applied to the vfs-7.0.leases branch by Christian Brauner. The series represents a major VFS architectural change — shifting file lease handling from an implicit opt-out model (where ->setlease() == NULL defaults to kernel-internal lease support) to an explicit opt-in model (where ->setlease() == NULL returns -EINVAL).

The discussion this week also branched into a significant side conversation about whether NFS export should similarly become an explicit opt-in feature for filesystems, sparked by concerns about kernfs-based filesystems (cgroupfs, pidfs, nsfs) being inadvertently exportable via NFS.

Classification

This is primarily a VFS protocol/architectural change with direct implications for NFS client and server development. It is not a bug fix per se, but rather a preventive measure against future regressions in lease and delegation handling.

Background (from Prior Week)

Last week, the 24-patch series was posted on January 8. The cover letter explained:

"For historical reasons, when ->setlease() file_operation is set to NULL, the default is to use the kernel-internal lease implementation. This means that if you want to disable them, you need to explicitly set the ->setlease() file_operation to simple_nosetlease() or the equivalent." — Jeff Layton

The series was targeted for v7.0, following a separate v6.19-targeted fix for directory delegation handling that had been posted the previous day (and subsequently applied to vfs.fixes this week).

The kernfs Debate

A significant discussion emerged around whether kernfs-based filesystems (sysfs, cgroupfs, pidfs, nsfs) should be included in the lease opt-in set. This was originally raised by Jan Kara last week and continued this week.

Layton's Position on kernfs

Jeff Layton proposed leaving kernfs out of the initial set, noting:

"As far as kernfs goes: AIUI, that's basically what sysfs and resctrl are built on. Do we really expect people to set leases there?" — Jeff Layton (prior week, continued this week)

He initially suggested a diagnostic wrapper:

"One idea: we could add a wrapper around generic_setlease() for filesystems like this that will do a WARN_ONCE() and then call generic_setlease(). That would keep leases working on them but we might get some reports that would tell us who's setting leases on these files and why."

Jan Kara agreed with the diagnostic approach on January 9:

"Yeah, this makes sense at least for some transition period so that we faster learn if our judgement about sane / insane lease use was wrong."

Amir Goldstein pushed back on the caution on January 9:

"IMO, you are being too cautious, but whatever. It is not accurate that kernfs filesystems are NFS exportable in general. Only cgroupfs has KERNFS_ROOT_SUPPORT_EXPORTOP."

Layton ultimately decided against the WARN_ONCE() approach on January 12:

"I think so too. For now, I think I'll not bother with the WARN_ONCE(). Let's just leave kernfs out of the set until someone presents a real use-case."

The NFS Export Opt-In Discussion

The kernfs conversation evolved into a broader debate about whether NFS export itself should become an explicit opt-in feature for filesystems. This is highly relevant to NFS server (nfsd) development.

Layton's Proposal

Layton observed that export_operations were originally designed for NFS export but are now also used by filesystems like kernfs solely for open_by_handle_at() support:

"At one time, those were only defined by filesystems that wanted to allow NFS export. Now we've grown them on filesystems that just want to provide filehandles for open_by_handle_at() and the like. nfsd doesn't care though: if the fs has export operations, it'll happily use them." — Jeff Layton

He proposed:

"Should we add a mechanism to prevent exporting these sorts of filesystems? Even better would be to make nfsd exporting explicitly opt-in. What if we were to add an EXPORT_OP_NFSD flag that explicitly allows filesystems to opt-in to NFS exporting?"

Chuck Lever's Response

Chuck Lever questioned the active harm on January 12:

"What's the active harm in exporting /sys/fs/cgroup? It has to be done explicitly via /etc/exports, so this is under the NFS server admin's control. Is it an attack surface?"

Layton clarified that the concern was about inadvertent export through container bind mounts on January 13:

"Could you end up exporting /sys if it's bind mounted into a container somewhere? Bear in mind that exportfs does allow mountpoint crossing, etc. nfsd is a network service, so I think the kernel needs to be quite conservative about what filehandles it can access."

Christian Brauner's Position

Brauner strongly agreed with making NFS export opt-in on January 13:

"I don't think we want to expose cgroupfs via NFS that's super weird. It's like remote partial resource management and it would be very strange if a remote process suddenly would be able to move things around in the cgroup tree."

He proposed separating file handle operations from export operations:

"So my preference would be to really sever file handles from the export mechanism so that we can allow stuff like pidfs and nsfs and cgroupfs to use file handles via name_to_handle_at() and open_by_handle_at() without making them exportable."

Hellwig's Skepticism

Christoph Hellwig pushed back against explicit prohibition on January 13:

"I don't understand this discussion. If someone really wants to expose say cgroupfs to the network they'll find a way, be that using a userspace nfs server, samba, 9p or a custom fuse thing. What's the benefit of explicitly prohibiting a knfsd export?"

He continued on January 14:

"Sure. But how is this worse than accidentally exporting private data or any other misconfiguration?"

Amir Goldstein's Correctness Argument

Amir reframed the issue as a correctness concern rather than security on January 14:

"My POV is that it is less about security (as your question implies), and more about correctness."

He highlighted the NFS file handle persistence problem:

"The special thing about NFS export, as opposed to, say, ksmbd, is open by file handle, IOW, the export_operations. I perceive this as a very strange and undesired situation when NFS file handles do not behave as persistent file handles."

David Laight's Historical Perspective

David Laight added historical context about non-persistent file handles on January 14:

"You really shouldn't be allowed to nfs export a fs that doesn't have persistent file handles. Even file handles containing 'random' numbers can be problematic."

He recounted past issues with hard mounts causing client kernel hangs when exported filesystems became unavailable after reboot.

Chuck Lever on Orthogonality

Chuck Lever suggested the "is_exportable" predicate should be separate from export_ops on January 13:

"Well I think my point is that 'is this file system type exportable' might be orthogonal to whether the FS offers a filehandle capability. Perhaps the 'is_exportable' predicate is better placed separately from export_ops."

Layton concurred on January 13:

"That's a fair point. An fstype flag would seem most natural then."

Layton suggested this as an LSF/MM topic:

"This would be a good LSF/MM topic, but I'm hoping we can come to a consensus before then."

Series Applied

On January 12, Christian Brauner confirmed the full 24-patch series was applied on January 12:

"Applied to the vfs-7.0.leases branch of the vfs/vfs.git tree. Patches in the vfs-7.0.leases branch should appear in linux-next soon."

All 24 patches were applied, covering:

  • Patches 01–22: Adding generic_setlease() to 22+ local filesystems (affs, btrfs, erofs, ext2, ext4, exfat, f2fs, fat, gfs2, jffs2, jfs, nilfs2, ntfs3, ocfs2, orangefs, overlayfs, squashfs, tmpfs, udf, ufs, xfs, and read-only filesystems)
  • Patch 23: Changing kernel_setlease() to return -EINVAL when ->setlease is NULL (the core behavioral change)
  • Patch 24: Removing simple_nosetlease() as no longer needed

Impact on NFS Client Development

This change has significant implications for NFS client and server development:

  1. Lease correctness for NFS-exported filesystems: By requiring explicit opt-in, the VFS prevents future regressions where new filesystems inadvertently support leases without proper implementation — a critical concern for NFS delegation correctness and data consistency.

  2. NFS client lease behavior: The NFS client itself already implements custom ->setlease() handlers (via nfs4_setlease()), so this change does not directly affect the NFS client's own lease handling. However, it affects what underlying filesystems the NFS server can safely export.

  3. New filesystem integration: Any new filesystem intended to be NFS-exportable must now explicitly set ->setlease to generic_setlease() (or a custom implementation) to support NFS leases and delegations. This is documented in the updated porting documentation added by patch 23.

  4. NFS export opt-in discussion: The broader conversation about making NFS export itself an explicit opt-in feature remains open. If implemented, this would prevent inadvertent export of kernel-internal filesystems (cgroupfs, pidfs, nsfs) that have export_operations for open_by_handle_at() but should not be exported via NFS due to non-persistent file handles and potential security concerns.

Final Conclusions

The 24-patch lease opt-in series has been fully applied to the vfs-7.0.leases branch and will flow through linux-next into the v7.0 merge window. The immediate goal — making VFS lease support explicit opt-in — is complete.

The broader discussion about NFS export controls remains unresolved but has gained significant momentum. Key participants (Brauner, Layton, Goldstein, Lever) agree that the current model of equating export_operations with NFS exportability is problematic. The proposed solutions range from an EXPORT_OP_NFSD flag to a more fundamental separation of file handle operations from export operations. This was identified as a potential LSF/MM topic for further discussion.
