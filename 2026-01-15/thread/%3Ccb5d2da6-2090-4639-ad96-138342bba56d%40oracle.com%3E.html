NFS Export: Persistent Handles Flag and kernfs Exclusion Converge

Summary

NFS Export: Final Exchanges on Persistent File Handles and kernfs Exportability

Overview

This thread is a continuation of the broader VFS lease opt-in discussion that dominated linux-nfs this week. The 24-patch series requiring filesystems to explicitly opt-in to lease support was applied to vfs-7.0.leases earlier in the week. This thread, rooted in Chuck Lever's question about the active harm of exporting cgroupfs on January 12, captures the final two messages of a multi-day debate about NFS export controls — specifically, how to handle filesystems with export_operations that should not be NFS-exportable due to non-persistent file handles.

This is classified as a VFS/NFS protocol architectural discussion, not a bug fix or new feature implementation. No patches were submitted this week; the conversation centers on refining the design of an export opt-in mechanism.

Background (Brief Bridge from Prior Weeks)

The debate originated when Jeff Layton observed that export_operations — originally designed for NFS export — are now also used by filesystems like kernfs solely for open_by_handle_at() support. nfsd treats any filesystem with export_operations as exportable, even if its file handles are non-persistent:

"At one time, those were only defined by filesystems that wanted to allow NFS export. Now we've grown them on filesystems that just want to provide filehandles for open_by_handle_at() and the like. nfsd doesn't care though: if the fs has export operations, it'll happily use them."

The discussion evolved through several stages across related threads this week:

  • Amir Goldstein reframed the issue as a correctness concern rather than security, noting NFS file handles must behave persistently on January 14.
  • Christoph Hellwig shifted from skepticism to agreement that the problem is broken semantics, endorsing a "stable handles" flag on January 14.
  • Amir Goldstein proposed EXPORT_OP_PERSISTENT_HANDLES as concrete terminology grounded in NFS protocol specifications on January 14.
  • Chuck Lever clarified tmpfs semantics, noting tmpfs file handles are persistent within their natural lifetime on January 14.

This Week's Messages (January 14–15)

Hellwig on tmpfs Handles: Stable Within Their Lifetime

In response to Amir Goldstein's proposal of EXPORT_OP_PERSISTENT_HANDLES, Christoph Hellwig addressed a complication raised by Jeff Layton — that tmpfs does not have stable handles "per-se." Hellwig clarified on January 14:

"tmpfs handles are stable. It's the tmpfs files that don't survive an unmount or reboot.."

This distinction is critical: NFS file handle persistence is defined relative to the filesystem's lifetime, not across reboots. Since tmpfs file handles remain valid for the duration of the tmpfs mount, they satisfy the NFS protocol's requirement for persistent handles within that context. This clarification potentially simplifies the design space by showing tmpfs may naturally qualify under a PERSISTENT_HANDLES flag without special handling.

Brauner: Hard NAK on Exporting kernfs Filesystems

Christian Brauner delivered the strongest concluding remarks on January 15, directly addressing Hellwig's earlier skepticism about the value of explicitly prohibiting NFS export of kernfs-based filesystems. Brauner dismissed the argument that administrators who want to export will find alternative ways:

"You're arguing for the sake of arguing imho. You're getting exactly what we're all saying as evidenced by the last paragraph in your mail: it is entirely what this whole thing is about."

He emphasized that cgroupfs, nsfs, and pidfs do not meet the criteria for NFS exportability — regardless of whether they technically implement export_operations:

"This is an entirely irrelevant point because we're talking about cgroupfs, nsfs, and pidfs. And they don't meet this criteria. cgroupfs is a local resource management filesystem why would we ever want to support exporting it over the network."

Brauner highlighted the practical absurdity of such exports:

"cgroupfs shows local processes. So a server will see completely nonsensical PID identifiers listed in cgroup files and it can fsck around with processes in a remote system. Hard NAK. Entirely irrelevant if that filesystem meets the theoretical standards."

On the broader question of whether all filesystems meeting technical requirements should be exportable, Brauner concurred with Hellwig's final position:

"If it does not meet the technical requirements it obviously should not be exportable. And it seems like the spread of file handles beyond nfs exporting created some ambiguity here, which we need to fix."

"We are all in agreement here."

Key Technical Arguments

  1. The core problem is broken semantics, not security: Hellwig's pivot was decisive — the issue is that export_operations were overloaded with dual semantics (NFS export vs. open_by_handle_at()), and filesystems with non-persistent file handles violate the original assumptions of the export infrastructure.

  2. Persistent handles as the criterion: Amir Goldstein's EXPORT_OP_PERSISTENT_HANDLES proposal gained traction because it grounds the solution in NFS protocol terminology rather than an arbitrary "is_exportable" flag.

  3. tmpfs is not a problem case: Hellwig's clarification that tmpfs handles are stable within their mount lifetime resolves a potential edge case, meaning tmpfs exports would continue to work naturally under the proposed flag.

  4. kernfs filesystems must be excluded: Brauner's hard NAK on cgroupfs, nsfs, and pidfs export is based on both correctness (non-persistent handles) and semantics (these are local resource management interfaces that make no sense remotely).

Impact on NFS Client Development

While this discussion primarily concerns NFS server (nfsd) behavior, it has important implications for NFS client development:

  1. Client stability: NFS clients relying on persistent file handles for state recovery, cache coherency, and delegation management would be protected from servers that inadvertently export filesystems with volatile handles — a scenario that could cause client hangs or data corruption. As David Laight noted in a related thread on January 14:

    "You really shouldn't be allowed to nfs export a fs that doesn't have persistent file handles. Even file handles containing 'random' numbers can be problematic."

  2. Delegation correctness: The lease opt-in series (now applied) and the proposed export opt-in mechanism together ensure that NFS delegations are only granted on filesystems that properly support both leases and persistent file handles — a prerequisite for correct delegation recall and revocation semantics.

  3. New filesystem integration: Any new filesystem intended to be NFS-exportable must now explicitly implement ->setlease (per the applied series) and set an EXPORT_OP_PERSISTENT_HANDLES flag (proposed but not yet implemented). This two-gate approach prevents future regressions in NFS client/server interoperability.

Final Conclusions

The lease opt-in series is complete (applied to vfs-7.0.leases). The NFS export discussion has converged on a "persistent handles" flag approach, with key participants agreeing that:

  • The problem is broken semantics caused by overloading export_operations, not an arbitrary policy decision about what should be exportable.
  • EXPORT_OP_PERSISTENT_HANDLES is the preferred terminology, grounded in NFS protocol specifications.
  • kernfs-based filesystems (cgroupfs, nsfs, pidfs) must not be NFS-exportable due to non-persistent handles and semantic mismatch.
  • tmpfs exports remain valid because its file handles are persistent within their mount lifetime.

The discussion remains open for further refinement, particularly around the interaction between a kernel-level flag and exportfs user-space options. This was identified as a potential LSF/MM topic for continued discussion.
