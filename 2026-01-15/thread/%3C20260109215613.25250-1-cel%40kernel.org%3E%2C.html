NFSD: Asynchronous Write Throttling for UNSTABLE WRITEs (RFC v2 — Continued Debate)

Summary

NFSD: Asynchronous Write Throttling for UNSTABLE WRITEs (RFC v2 — Continued)

Classification: New feature / server-side flow control mechanism
Status: RFC discussion; no consensus reached this week.

Overview

This thread continues the RFC discussion initiated last week by Chuck Lever on introducing asynchronous write throttling for NFSD's UNSTABLE WRITE operations. The proposal aims to prevent server memory exhaustion under heavy write loads by returning NFS4ERR_DELAY to clients when memory pressure is detected, rather than blocking server threads in balance_dirty_pages().

Last week's exchange established the core problem: Hammerspace has observed server "melt-down" scenarios under sustained UNSTABLE WRITE traffic. This week, NeilBrown pressed further for concrete evidence and questioned whether existing kernel mechanisms already provide adequate flow control.

Key Technical Arguments This Week

NeilBrown Questions the Premise

On January 10th, NeilBrown challenged Chuck Lever's characterization of how balance_dirty_pages() operates:

"That isn't correct. If the 'dirty threshold' is reached (e.g. 10% of memory dirty) then balance_dirty_pages() will delay all writes to avoid exceeding the dirty page limit."

He explained that the writeback subsystem already monitors throughput per backing device and throttles writers proportionally:

"It attempts to monitor the recent throughput of each backing device, and to divide available memory among them in the same proportion as throughput, then throttle writes to backing devices using more than their share."

NeilBrown also questioned whether cgroup-based memory constraints for NFSD threads would achieve the desired effect:

"I have no direct experience with mem-cgroups so there are doubtless subtleties that I miss, but I suspect the primary effect of including nfsd in a mem-cgroup would be to push file content out of the page-cache more quickly. I don't think it can control dirty pages separately from clean pages, but I could easily be wrong."

He then asked for concrete symptoms:

"What exactly is 'the memory problem'? Do you have specific symptoms you are trying to address? Have you had NFS server run out of memory and grind to a halt?"

Chuck Lever Clarifies the Problem

Chuck Lever responded by pointing to nine months of prior work on direct I/O published on this mailing list:

"Review the past 9 months of Mike's work on direct I/O, published on this mailing list. Hammerspace has measured this misbehavior and experienced server melt-down. Their solution is to avoid using the page cache entirely."

He emphasized that even with existing mechanisms, there remains a denial-of-service vector:

"But even so there still seems to be an effective denial-of-service vector by overloading NFSD with UNSTABLE WRITE traffic faster than it can push it to persistence."

NeilBrown's Follow-Up on January 12th

In his second message this week, NeilBrown expressed skepticism about the severity of dirty page accumulation:

"I would be surprised if that actual count of dirty pages grep Dirty /proc/meminfo grows much above the dirty page limit. There is some elasticity so the threads don't need to check global variables on every page - only every 1024 pages or something like that - so the nominal limit can be exceeded briefly."

He conceded his earlier footprint calculations were incorrect:

"My footprint calculation was extremely wrong. I didn't allow for the rq_pages allocation - so add 1MB or more per thread."

However, he maintained that existing flow control mechanisms should already handle the problem:

"The transport queue already has flow control (for TCP). And the threads allocate a large rq_pages whether they are serving WRITEs or not. So when the server is under memory duress, the threads will block in bdp, which will push back on the transport queue once all threads are blocked..."

NeilBrown concluded by asking whether this was an alternative approach to existing solutions:

"Are you trying to find another way to address the same problem?"

He also called for better observability:

"It would definitely be helpful to have numbers to categorise the problem."

Evolution of the Discussion

The conversation this week shifted from architectural concerns about balance_dirty_pages_ratelimited_flags() integration (raised last week) to a more fundamental question: whether the proposed mechanism is necessary given existing kernel flow control. NeilBrown consistently argued that the writeback subsystem and TCP transport queue already provide back-pressure mechanisms, while Chuck Lever maintained that these are insufficient under extreme UNSTABLE WRITE loads.

Key themes that emerged:

  1. Dirty page limits: NeilBrown argued that balance_dirty_pages() already enforces memory bounds via /proc/sys/vm/dirty_ratio and /proc/sys/vm/dirty_bytes.
  2. Thread footprint: Chuck Lever clarified he was concerned about WRITE payloads, not thread overhead, though NeilBrown corrected his earlier underestimation of per-thread memory usage (1MB+ for rq_pages).
  3. Flow control debate: The central disagreement is whether TCP-level flow control and writeback throttling are sufficient to prevent server memory exhaustion.

Final Conclusions

No definitive conclusion was reached this week. The discussion remains open with the following unresolved questions:

  • Whether existing kernel mechanisms (writeback throttling, TCP flow control) adequately protect against NFSD memory exhaustion under extreme UNSTABLE WRITE loads
  • What concrete metrics and observability data would validate or refute the need for additional server-side flow control
  • How to reconcile the Hammerspace-reported "melt-down" scenarios with NeilBrown's assessment that existing bounds should prevent such behavior

As Chuck Lever noted last week, "Perhaps we need better observability first" — a sentiment echoed by NeilBrown this week. The thread remains in exploratory RFC status with no clear path forward identified.
