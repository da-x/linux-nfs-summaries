NFSD v3: ACL, Security Label, and Atomicity Bug Fixes Accepted for 6.6.y Stable Tree

Summary

NFSD v3: ACL, Security Label, and Atomicity Bug Fixes Accepted for 6.6.y Stable Tree

Overview

This week concluded a multi-week backport effort to the Linux 6.6 stable tree aimed at resolving three significant bugs in the NFS server (NFSD). Chuck Lever submitted version 3 of a four-patch series on January 9th, which was accepted by Greg Kroah-Hartman on January 12th. The discussion is classified as a bug fix backport, addressing POSIX ACL omission during file creation, SELinux security label misapplication, and NFSv3 atomicity race conditions.

Evolution of the Discussion

Prior Context (Weeks Ending Jan 5 & Jan 8)

The thread originated with Chuck Lever's v1 submission on January 3rd, which encountered an automated report indicating that the primary ACL fix patch failed to apply cleanly to the 6.6-stable tree. In response, Lever posted a v2 series on January 8th, replacing one patch with its upstreamed version and passing LLM-based review and CI testing without regressions.

This Week: The Build Warning Blocker

The v2 series was promptly rejected by Greg Kroah-Hartman due to a build failure introduced in the timestamp accessor patch (1/4):

"Adds a build warning, which breaks the build:

fs/nfsd/blocklayout.c: In function 'nfsd4_block_commit_blocks': fs/nfsd/blocklayout.c:123:16: error: unused variable 'new_size' [-Werror=unused-variable] 123 | loff_t new_size = lcp->lc_last_wr + 1; | ^~~~~~~~ cc1: all warnings being treated as errors

try a 3rd version?" Greg Kroah-Hartman

Chuck Lever responded with characteristic brevity:

"Harumph. I didn't see any warnings before I posted yesterday.

/me trudges back to his drawing board." Chuck Lever

Resolution: v3 Accepted

Lever returned on January 9th with the v3 series, addressing three items:

"Changes since v2:

  • Add a Signed-off-by to 1/4
  • Address a build warning introduced in 1/4
  • Fix the In-Reply-To header" Chuck Lever

The series was accepted without further delay:

"Nice, this worked, thanks!" Greg Kroah-Hartman

Patch Series Breakdown (v3)

The four-patch series touches 10 files across fs/nfsd/, with a net result of 44 insertions and 30 deletions:

Patch 1/4: nfsd: convert to new timestamp accessors Jeff Layton

A preparatory change updating NFSD to use newer kernel inode timestamp accessor functions (upstream commit 11fec9b9fb04). This serves as a dependency for the subsequent atomicity fix. The v3 iteration specifically addressed the -Werror=unused-variable build failure in fs/nfsd/blocklayout.c.

Patch 2/4: nfsd: Fix NFSv3 atomicity bugs in nfsd_setattr() Trond Myklebust

This patch resolves critical race conditions in NFSv3 attribute-setting operations. The guarded SETATTR mechanism — designed to prevent races with concurrent WRITE and SETATTR calls — was checking the guard time against the inode ctime before acquiring the inode lock, defeating its purpose:

"The main point of the guarded SETATTR is to prevent races with other WRITE and SETATTR calls. That requires that the check of the guard time against the inode ctime be done after taking the inode lock." Trond Myklebust

The fix also accounts for NFSv3's 32-bit timestamp limitations:

"Furthermore, we need to take into account the 32-bit nature of timestamps in NFSv3, and the possibility that files may change at a faster rate than once a second." Trond Myklebust

Patch 3/4: nfsd: set security label during create operations Stephen Smalley

This patch fixes a bug where SELinux security labels passed by NFSv4 clients during file creation were received but never applied to the new inode:

"When security labeling is enabled, the client can pass a file security label as part of a create operation for the new file, similar to mode and other attributes. At present, the security label is received by nfsd and passed down to nfsd_create_setattr(), but nfsd_setattr() is never called and therefore the label is never set on the new file." Stephen Smalley

Smalley included a detailed SELinux reproducer demonstrating that files created via NFSv4 received incorrect security contexts (test_file_t instead of the expected test_filesystem_filetranscon_t). He also raised an important observation about ACLs:

"Looking at nfsd_setattr() I am uncertain as to whether the same issue presents for file ACLs and therefore requires a similar fix for those." Stephen Smalley

This concern is directly addressed by patch 4/4.

Patch 4/4: NFSD: NFSv4 file creation neglects setting ACL Chuck Lever

This is the primary bug fix driving the entire series. When an NFSv4 client creates a file with a POSIX ACL containing named principals, the ACL is silently dropped:

"An NFSv4 client that sets an ACL with a named principal during file creation retrieves the ACL afterwards, and finds that it is only a default ACL (based on the mode bits) and not the ACL that was requested during file creation. This violates RFC 8881 section 6.4.1.3: 'the ACL attribute is set as given'." Chuck Lever

The root cause lies in nfsd_create_setattr(), which calls nfsd_attrs_valid() to determine whether to invoke nfsd_setattr(). However, this validation function checked only for standard iattr changes and security labels — not POSIX ACLs:

"However, nfsd_attrs_valid() checks only for iattr changes and security labels, but not POSIX ACLs. When only an ACL is present, the function returns false, nfsd_setattr() is skipped, and the POSIX ACL is never applied to the inode." Chuck Lever

The fix is a minimal one-line change in fs/nfsd/vfs.h to include POSIX ACLs in the validity check. The bug was originally reported by Aurélien Couderc and traces back to commit c0cbe70742f4.

Significance for NFS Client Development

While this series targets the NFS server (NFSD), it has direct implications for NFS clients:

  1. ACL enforcement gap: Clients creating files with named-principal ACLs via NFSv4 experienced silent security policy violations, as requested ACLs were never applied. The server returned a default ACL derived from mode bits — a compliance violation against RFC 8881.

  2. SELinux label misapplication: Clients using NFSv4.2 with security labeling (e.g., SELinux) saw files created with incorrect security contexts, potentially breaking mandatory access control policies.

  3. NFSv3 atomicity races: The nfsd_setattr() fix prevents data consistency issues when clients perform concurrent attribute updates (e.g., via chmod or chown) over NFSv3 mounts.

  4. Stable tree importance: These fixes target the 6.6 LTS kernel, widely deployed in production environments. The backport ensures enterprise NFS deployments benefit from these security and correctness improvements without requiring a full kernel upgrade.

Conclusion

The v3 submission resolved all remaining issues from prior iterations — including a build warning that broke the -Werror-enforced stable tree compilation — and was accepted by Greg Kroah-Hartman for integration into the 6.6.y stable kernel. The series incorporates prerequisite patches from Jeff Layton, Trond Myklebust, and Stephen Smalley, and passed both LLM-based review and CI testing with no reported regressions. This marks a successful resolution to three distinct but related bugs in the Linux NFS server affecting POSIX ACLs, SELinux security labels, and NFSv3 atomicity guarantees.
