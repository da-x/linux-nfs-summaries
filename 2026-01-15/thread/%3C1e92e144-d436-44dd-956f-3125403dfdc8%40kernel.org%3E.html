kNFSD Encrypted Filehandles: MAC vs. Encryption Debate for NFS Security

Summary

kNFSD Encrypted Filehandles: Cryptographic Debate on MAC vs. Encryption for NFS Security

Type: New feature — security hardening of NFSv4 filehandle handling in kNFSD (the kernel NFS server)

Background

Benjamin Coddington (Hammerspace) has been developing a patch series to encrypt NFSv4 filehandles in kNFSD, motivated by concerns that plaintext filehandles expose filesystem internals and can be guessed or sniffed to subvert access controls. The original RFC/v1 was posted on December 27th (cover letter), and the discussion continued into this week with significant cryptographic review from Eric Biggers and architectural input from key NFS maintainers.

This Week's Discussion: Cryptographic Critique of AES-CBC

Eric Biggers' Security Analysis

On January 14th, cryptography expert Eric Biggers delivered a pointed critique of the proposed use of AES-CBC for filehandle encryption [id://20260114004205.GC2178@quark]:

"AES-CBC is an unauthenticated encryption algorithm that protects a message's confidentiality. It isn't a hash function, it isn't a MAC, and it doesn't protect a message's authenticity. AES-CBC will successfully decrypt any ciphertext, even one tampered with by an attacker, into some plaintext. You may be confusing AES-CBC with AES-CBC-MAC."

Biggers argued that the actual security goal — ensuring only filehandles issued to a given client are accepted by the server — is better served by a Message Authentication Code (MAC) rather than unauthenticated encryption:

"To me it seems like you want to ensure that for a given client, only file handles that it was sent by the server will be accepted by the server (provided that it can't snoop on handles sent to other clients). An unauthenticated encryption mode like AES-CBC doesn't solve that problem. I think a MAC is sufficient to solve that problem."

He recommended kernel-native MAC algorithms with clean APIs — HMAC-SHA256, HMAC-SHA512, BLAKE2s, or SipHash-2-4 — noting these avoid the dynamic memory allocation and scatterlist overhead of crypto subsystem calls. On FIPS 140-3 compliance:

"In the case where the kernel is certified as a FIPS 140-3 module, I don't know whether this feature would actually be considered a security function for FIPS purposes or not."

Benjamin Coddington's Response

Coddington acknowledged Biggers' critique [id://834DBCBA-1CD8-4BA9-81E8-09E621B3F176@hammerspace.com]:

"I'm not confusing them, and you're absolutely correct — if an encrypted filehandle were tampered with we'd be relying on the decoded filehandle being garbage — the routines to decode the fsid and fileid would return errors, because a filehandle's data is meaningful and well-structured."

He distinguished this from what a MAC provides:

"That's a big difference from what using a MAC would provide — immediate knowledge the filehandle had been modified."

Coddington closed with appreciation: "Thanks Eric, much appreciate your advice here."

Jeff Layton: MACs Enable Client-Bound Filehandles

Jeff Layton endorsed the MAC approach and proposed an enhancement: salting the MAC with the NFSv4 client ID to create per-client filehandles [id://a092bf21127a679a32ac9f9c476e7d070667c36b.camel@kernel.org]:

"If you append a MAC though and check it on the server, you could give out filehandles that are limited-use. For instance, with v4, you could salt the hash with the long-form clientid and ensure that that filehandle is only usable by that client. Anyone else gets back NFS4ERR_STALE."

He noted the combination with TLS would provide strong protection:

"Couple that with TLS and you'd have a pretty decent guard against sniffing and filehandle guessing attacks."

Chuck Lever: The Sniffing vs. Guessing Distinction

Chuck Lever pushed back on conflating two different attack vectors [id://c8ad96c5-1da1-4aeb-8999-2a8b63021a23@kernel.org]:

"A sniffing attack is easier than guessing a file handle or constructing one. Neither encrypting a filehandle nor signing it protects against sniffing attacks. But using full in-transit encryption does, and we have that implemented already."

He emphasized that with TLS protecting the wire, plaintext filehandles are less predictable:

"With full in-transit encryption, the plaintext is much much less predictable as well."

Trond Myklebust: Defining the Orthogonal Problem Space

Trond Myklebust clarified the distinction between sniffing and spoofing protection [id://a78cf4e4274f8b4e69a3c7bf3aa778ce7cc25f72.camel@kernel.org]:

"Protection against sniffing and protection against spoofing are two completely orthogonal problems. Please don't muddle the already murky waters in this thread by confusing the two."

When Lever argued they were not orthogonal in this context, Myklebust articulated the core security requirement driving this work [id://d982f950ef0291076801b23cfd53ae8da1b31c00.camel@kernel.org]:

"The orthogonal problem that we're looking to solve is when a trusted client is shared by multiple users who are trusted to access different data sets. If they can set up a TLS connection (or if there is no need to set up TLS because network access is trusted through other methods), then the users can currently just iterate through sets of valid filehandles in order to brute force access to data sets that they are not supposed to see."

He further explained why existing mechanisms fall short:

"We cannot use krb5 as a solution here because the flexfiles protocol does not currently support that, and because pNFS authorisation at the data server is not based on user authentication, but on proof that the user holds a valid layout. If the filehandle is unguessable in that situation, then that does suffice as proof that the user holds a layout."

Final Conclusions

The discussion converged on several important points:

  1. AES-CBC is not well-suited for this use case — it provides confidentiality without authenticity guarantees.
  2. A MAC-based approach (e.g., HMAC-SHA256) is preferred by multiple reviewers for its ability to detect tampering and its simpler kernel API.
  3. Client-bound filehandles via salting the MAC with the NFSv4 client ID could provide stronger isolation between users sharing a client connection.
  4. The core threat model is not wire sniffing (already addressed by TLS) but rather filehandle guessing/brute-forcing within a trusted network context, particularly relevant to pNFS flexfiles where layout holders need proof of authorization without krb5 support.

The thread did not reach a final resolution on the patch series itself — Coddington acknowledged Biggers' feedback and indicated he would refine the approach in a future version. The cryptographic direction has shifted from encryption toward authentication (MAC), with client-binding as a potential enhancement.
