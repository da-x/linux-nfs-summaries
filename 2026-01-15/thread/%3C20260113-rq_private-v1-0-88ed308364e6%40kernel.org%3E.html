NFSD/SunRPC Layering Cleanup: rq_private Pointer and Removal of NFSv4-Specific svc_rqst Fields

Summary

Fixing Layering Violations Between NFSD and SunRPC via rq_private

Type: Bug fix / code cleanup (architectural refactoring)

On Tuesday, January 13th, Jeff Layton posted a two-patch series titled "fix up some layering violations" targeting the NFS server (nfsd) and the SunRPC service layer. The patches address long-standing architectural issues where nfsd-specific state was embedded directly in the generic struct svc_rqst, violating the clean separation between the RPC transport layer and the NFS server implementation.

Motivation and Background

Layton explains the rationale:

"The rq_lease_breaker and rq_cachetype fields are only used by nfsd. These patches shrink struct svc_rqst slightly and makes the layering between the two a little cleaner. In the case of rq_lease_breaker, I think this also gives us a little more type safety."

The rq_lease_breaker field in particular has been described as "always a NFSv4 specific layering violation in svc_rqst" [id://20260113-rq_private-v1-1-88ed308364e6@kernel.org]. It was needed because nfsd requires thread-local storage accessible from the svc_rqst pointer during request processing.

Patch Details

Patch 1: Introducing svc_rqst->rq_private and Removing rq_lease_breaker

The first patch [id://20260113-rq_private-v1-1-88ed308364e6@kernel.org] adds a new rq_private pointer to struct svc_rqst, explicitly reserved for use by the service threads handling requests — the sunrpc core code does not touch it. In nfsd, a new struct nfsd_thread_local_info is defined and allocated on the stack; a pointer to this structure is stored in rq_private. The former rq_lease_breaker field is replaced with an ntli_lease_breaker field within this new structure.

Patch 2: Moving rq_cachetype into nfsd's Thread-Local Info

The second patch [id://20260113-rq_private-v1-2-88ed308364e6@kernel.org] extends the same cleanup to rq_cachetype, which is also exclusively used by nfsd. It is moved into struct nfsd_thread_local_info.

Review Discussion: Stack Allocation Concerns

Benjamin Coddington provided a quick review of both patches [id://D867076E-FF23-47C5-87BD-5DE805DF4ED1@hammerspace.com]:

"Both look good to me: Reviewed-by: Benjamin Coddington bcodding@hammerspace.com"

Chuck Lever, however, raised an architectural concern about the stack-based allocation of struct nfsd_thread_local_info [id://5806015a-ad18-4bc9-a320-2fdab4d86969@app.fastmail.com]:

"This assumes sizeof(structure nfsd_thread_local_info) will always be small enough that it is reasonable to keep on the stack. I can't say that would be a good bet in the long run."

He suggested dynamic allocation via kmalloc instead, noting:

"And we don't need the perfect reliability of not doing a dynamic allocation here. If kmalloc(sizeof(struct nfsd_thread_local_info)) fails, the thread exits immediately, no harm."

Lever also pointed out a practical limitation of stack-based storage for future extensions:

"Also, scatter-gather lists could not be stored directly in this object because it is on the stack. If Ben wanted to stick a 32-byte buffer in struct nfsd_thread_local_info to be used with the crypto API, it would have to be a pointer to it, not the buffer itself."

Jeff Layton acknowledged the concern but pushed back on the need for dynamic allocation at this stage [id://71ddafd443a0e13f79cea09ba2b3ac4f106163ce.camel@kernel.org]:

"Not sure how much space Ben will need (if any). We certainly could have nfsd allocate this separately. I didn't see the point for something that is only a few bytes though."

Chuck Lever proposed a compromise — adding a build-time assertion as a safety tripwire [id://6f112559-43e0-41ad-864c-03b1841920d2@app.fastmail.com]:

"If we are designing for today, another approach would be to set up a BUILD_WARN_ON or other type of static build failure if this structure grows larger than, say 256 bytes -- then add dynamic allocation at that point."

Layton remained skeptical [id://3b5faf0e9bb08c779854e3aaa8b30fb12e86b25e.camel@kernel.org]:

"I don't see us growing this to huge proportions. I think that's the sort of thing we just have to watch out for as maintainers. If you really insist on a BUILD_WARN_ON tripwire, I'll add one, but it seems like overkill to me."

Chuck Lever stood his ground with characteristic bluntness [id://d9060e6f-f1d5-4322-80fa-3794770c0153@app.fastmail.com]:

"I think a tripwire documents the assumption made here in a single line... no different than a lockdep_assert. More critically, though, maintainers tend to have a very short memory. Not a trustworthy lot, really."

He suggested static_assert(sizeof(struct nfsd_thread_local_info) < 256); as the concrete safeguard.

Final Outcome

Despite the unresolved discussion about the stack-size tripwire, Chuck Lever applied both patches to the nfsd-testing tree on January 14th [id://176841919290.418760.6153318776379161550.b4-ty@oracle.com]:

"Applied to nfsd-testing, thanks!"

The commits are:

  • Patch 1/2: 2f9a5cd51d92 — "nfsd/sunrpc: add svc_rqst->rq_private pointer and remove rq_lease_breaker"
  • Patch 2/2: a5428a9e04ff — "nfsd/sunrpc: move rq_cachetype into struct nfsd_thread_local_info"

Significance for NFS Client Development

While this series primarily targets the NFS server (nfsd) and sunRPC infrastructure, it is relevant to the broader NFS client ecosystem. The cleanup removes NFSv4-specific state from the generic RPC request structure, improving the modular boundaries that both server and client subsystems depend upon. The rq_private mechanism also provides a cleaner path for future nfsd extensions — such as crypto buffers or scatter-gather lists — without further polluting the shared svc_rqst structure.
