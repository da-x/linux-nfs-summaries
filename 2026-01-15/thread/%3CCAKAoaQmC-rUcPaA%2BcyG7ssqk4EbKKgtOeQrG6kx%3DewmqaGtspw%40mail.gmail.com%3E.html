Forwarded: ms-nfs41-client Windows Driver Binaries Announcement

Summary

Forwarded Announcement: ms-nfs41-client Windows Driver Binaries for Testing

This week's activity on this thread was limited to a single message in which Martin Wege forwarded an announcement from Roland Mainz regarding new test binaries for the ms-nfs41-client, an open-source NFSv4.2/NFSv4.1 filesystem client driver for Windows 10/11 and Windows Server 2019/2022/2025 Martin Wege, 2026-01-12.

Nature of the Discussion

This thread is not about Linux kernel NFS client development or bug fixes. Instead, it serves as a cross-post to linux-nfs requesting interoperability feedback from the Linux NFS community when using their Windows-based NFS client against Linux NFS servers. As Wege noted:

"interoperability feedback with NFSv4.1/NFSv4.2 servers based on Linux 6.6+ LTS and 6.17+ would be great."

Key Features Highlighted in the Announcement

The forwarded announcement from Roland Mainz outlined a substantial set of new features and bug fixes in the Windows NFS client driver, including:

  • Windows Alternate Data Streams (ADS) support via NFS named attributes
  • Server-side copy acceleration for Windows file copy operations (xcopy.exe, cmd.exe copy, MS Explorer) using NFSv4.2 COPY and block cloning
  • Sparse file support with hole/data range enumeration
  • Bug fixes for FreeBSD NFS server compatibility
  • Fixed issues probing sparse files when using the nfs-ganesha NFS server
  • Support for Windows Server 2025, ARM64 architectures, and various protocol enhancements

Mainz emphasized that certain features are particularly notable:

"Windows Alternate Streams (Win32 streams) support was added, xcopy.exe/cmd.exe copy/MS Explorer file copy acceleration via NFS server side copies and copy-by-block-cloning are IMO the most interesting new features"

Relevance to Linux NFS Development

While this announcement does not involve changes to the Linux kernel NFS client or server code, it is relevant to the broader NFS ecosystem. The ms-nfs41-client project's improvements in interoperability with Linux NFS servers (particularly regarding NFSv4.2 features like CLONE, SEEK, DEALLOCATE, and named attributes) may inform future compatibility testing and protocol refinement efforts within the Linux NFS subsystem.

No technical arguments or debates occurred in this thread; it was purely an informational cross-post requesting community participation in interoperability testing.
