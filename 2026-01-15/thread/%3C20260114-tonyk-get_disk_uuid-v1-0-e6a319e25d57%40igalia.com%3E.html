btrfs/overlayfs: Rejected get_disk_uuid() Approach for Cloned Image Support

Summary

btrfs/overlayfs: Support for Cloned Images via get_disk_uuid() — Rejected Approach

Summary

Overview

André Almeida submitted a 3-patch series, [PATCH 0/3] fs: Support btrfs cloned images and overlayfs [id://20260114-tonyk-get_disk_uuid-v1-0-e6a319e25d57@igalia.com], aimed at resolving a compatibility problem between btrfs cloned images and overlayfs's "index" feature. This is a new feature / bug fix targeting the interaction between btrfs, overlayfs, and the NFS export subsystem. The series was met with significant pushback from Christoph Hellwig, who fundamentally disagreed with the approach — arguing that the underlying problem should be solved in btrfs itself rather than through kernel infrastructure repurposing.

Problem Statement

The core issue stems from how btrfs handles cloned disk images. As Almeida explained in his cover letter:

"Every time the same image cloned is mounted, btrfs assigns a new random UUID for it to avoid clashing with the exist UUID. This UUID is then used by overlayfs origin check, to avoid reusing the same directory for a different filesystem. Remounting the same filesystem in the same directory is supported, but the different random UUIDs will make the check fail." [id://20260114-tonyk-get_disk_uuid-v1-0-e6a319e25d57@igalia.com]

The practical use case driving this work is SteamOS A/B partitioning on the Steam Deck. The device maintains two partitions for atomic updates: when updating from partition A, the new image is written to partition B (and vice versa). Both partitions are cloned btrfs images with identical UUIDs. During installation, overlayfs is used to mount these images multiple times, and each remount triggers a new random temporary UUID — breaking overlayfs's origin file handle validation.

Almeida clarified the exact failure scenario:

"The problem happens before switching from A to B, it happens when trying to install the same image from A on B. During the image installation process, while running in A, the B image will be mounted more than once for some setup steps, and overlayfs is used for this. Because A have the same UUID, each time B is remouted will get a new UUID and then the installation scripts fails mounting the image." [id://0241e2c4-bf11-4372-9eda-cccaba4a6d7d@igalia.com]

Proposed Solution (Rejected)

The 3-patch series attempted to solve this by repurposing the existing export_operations::get_uuid() mechanism:

  1. Patch 1/3: Rename get_uuid() to get_disk_uuid() in exportfs, expanding documentation to clarify it can serve filesystems with cloned devices [id://20260114-tonyk-get_disk_uuid-v1-1-e6a319e25d57@igalia.com].
  2. Patch 2/3: Implement get_disk_uuid() for btrfs to return the original image UUID rather than the random temporary one [id://20260114-tonyk-get_disk_uuid-v1-2-e6a319e25d57@igalia.com].
  3. Patch 3/3: Modify overlayfs to use get_disk_uuid() for origin file handle validation instead of sb->s_uuid [id://20260114-tonyk-get_disk_uuid-v1-3-e6a319e25d57@igalia.com].

Key Technical Arguments

Christoph Hellwig's Opposition to Repurposing get_uuid()

Christoph Hellwig delivered the strongest critique, fundamentally rejecting the approach on multiple grounds. First, he questioned the semantics of "disk UUID":

"I'm not sure what a 'disk uuid' is -- XFS can store two of them in the ondisk superblock: the admin-modifiable one that blkid reports, and the secret one that's stamped in all the metadata and cannot change." [id://20260114061028.GF15551@frogsfrogsfrogs]

More critically, Hellwig argued that get_uuid() serves a very specific purpose for pNFS block layout — not general filesystem identification:

"Totally independent of the rest of the discussion, the get_uuid exportfs operation is not useful for anything but the original pNFS block layout. Which is actually pretty broken and should be slowly phased out." [id://20260114062424.GA10805@lst.de]

He further warned against spreading this pattern:

"That method does not just return an uuid, but in fact a unique identifier of the file systems choice and the offset/len where to look for it on disk, as that is how pnfs/block finds the matching device. It is a dangerous concept and should not spread further." [id://20260114131130.GA6967@lst.de]

Hellwig's Preferred Fix: Solve It in btrfs

Hellwig consistently argued that the right fix lies within btrfs, not in overlayfs or exportfs infrastructure:

"... and the fix is to not assign random uuid, but to assign a new uuid to the cloned image that is persisted. That might need a new field to distinguish the stamped into the format uuid from the visible uuid like the xfs metauuid, but not hacks like this." [id://20260114062608.GB10805@lst.de]

When Almeida asked how to create a non-random persistent UUID, Hellwig pointed to XFS's precedent:

"Just allocate an entirely new uuid? That's what XFS did with the metadata uuid (persistent and stamped into all metadata headers) vs user visible uuid that can be changed." [id://20260115062944.GA9590@lst.de]

Hellwig also challenged btrfs's fundamental behavior of allowing duplicate fsids:

"And btrfs developers, I think the main problem is indeed that btrfs simply allows mounting the same fsid twice. Which is really fatal for anything using the fsid/uuid, such NFS exports, mount by fs uuid or any sb->s_uuid user." [id://20260115072311.GA10352@lst.de]

Amir Goldstein's Alternative: Delegate to encode_fh()

Amir Goldstein acknowledged the conceptual need for a "domain UUID" but suggested a different architectural approach. He proposed extending ->encode_fh() with a flags argument, delegating the encoding of globally unique file handles directly to the filesystem:

"Perhaps this is the wrong way to abstract what overlayfs needs from real fs. Maybe better to extend ->encode_fh() to take a flags argument... This essentially delegates the encoding of a 'globally unique file handle' to the filesystem without specifying this or that version of uuid." [id://CAOQ4uxjAQu9sQt3qOOVWS5cz5B51Hg0m4RAjsreBkmPhg-2cyw@mail.gmail.com]

Hellwig endorsed this direction, noting it would benefit NFS as well:

"Encoding the uuid into the file handle in the kernel is the right thing for NFS as well. Hacking in the uuids in userspace instead of the kernel was done initially because there was no good kernel uuid infrastructure. So doing this in general and have NFS use it when available would be beneficial for everyone." [id://20260115063630.GA9671@lst.de]

Qu Wenruo's btrfs Perspective: The temp_fsid Hack

Qu Wenruo, a btrfs maintainer, provided crucial context on the btrfs side. He explained that the automatic temporary fsid generation was merged despite his earlier proposal for an opt-in mechanism:

"My initial idea for this problem is to let btrfs not generate a tempfsid automatically, but put some special flag (e.g. SINGLE_DEV compat ro flag) on those fses that want duplicated fsid... Unfortunately that idea is not accepted and the current automatic new tempfsid solution is merged." [id://633bb5f3-4582-416c-b8b9-fd1f3b3452ab@suse.com]

He suggested reverting this behavior before it becomes too entrenched:

"I'm wondering will that behavior (returning the same fsid) be acceptable for overlayfs? If so, I think it's time to revert the behavior before it's too late." [id://633bb5f3-4582-416c-b8b9-fd1f3b3452ab@suse.com]

Amir Goldstein Questions the Use Case

Amir raised important questions about whether overlayfs with index is even appropriate for this SteamOS A/B scenario:

"And what do you expect to happen wrt overlayfs when switching from image A to B? What are the origin file handles recorded in overlayfs index from image A lower worth when the lower image is B? Is there any guarantee that file handles are relevant and point to the same objects?" [id://CAOQ4uxhbz7=XT=C3R8XqL0K_o7KwLKsoNwgk=qJGuw2375MTJw@mail.gmail.com]

He noted a similar precedent with squashfs and OpenWRT, which led to the uuid=off mount option:

"FWIW, the setup you are describing sounds very familiar. I am pretty sure that a similar setup with squashfs and OpenWRT was the use case to add the uuid=off overlayfs mount options." [id://CAOQ4uxhbz7=XT=C3R8XqL0K_o7KwLKsoNwgk=qJGuw2375MTJw@mail.gmail.com]

Evolution of the Discussion

The discussion unfolded in three distinct phases:

Phase 1 (Jan 14 morning): Almeida's patches were posted. Darrick J. Wong and Christoph Hellwig immediately raised concerns about the get_disk_uuid() naming and semantics. Hellwig declared the existing get_uuid() infrastructure unsuitable for repurposing.

Phase 2 (Jan 14 afternoon): Amir Goldstein entered the conversation, proposing an alternative abstraction via encode_fh() flags. Almeida sought clarification on how to implement a persistent non-random UUID in btrfs and asked whether this should be a super_block member. Hellwig reiterated that XFS's approach — requiring nouuid for duplicate mounts — was the correct model.

Phase 3 (Jan 15): Qu Wenruo joined, explaining btrfs's temp_fsid history and suggesting an opt-in flag mechanism. Hellwig pressed on the fundamental issue: btrfs allowing same-fsid mounts is "really fatal" for UUID consumers. Almeida clarified the SteamOS A/B use case, noting the failure occurs during installation (remounting the same image multiple times), not at runtime switching. Hellwig concluded firmly:

"Then you'll really need to assign them different (persistent) fsids/uuids." [id://20260115160816.GA16080@lst.de]

Final Conclusions

By the end of this week's activity, the consensus was clear: the proposed approach of repurposing get_uuid() / get_disk_uuid() was rejected. The key conclusions were:

  1. get_uuid() is not suitable for general filesystem identification. It serves a specific pNFS block layout purpose and should not be spread further. [id://20260114131130.GA6967@lst.de]

  2. The fix belongs in btrfs, not overlayfs or exportfs. btrfs should either assign persistent (non-random) UUIDs to cloned images — similar to XFS's metadata UUID approach — or require an explicit opt-in flag for same-fsid mounts. [id://20260114062608.GB10805@lst.de], [id://20260115062944.GA9590@lst.de]

  3. btrfs allowing same-fsid mounts by default is problematic. This behavior is "really fatal for anything using the fsid/uuid" and should require explicit opt-in (like XFS's nouuid mount option). [id://20260115072311.GA10352@lst.de]

  4. An alternative overlayfs approach may be viable. Amir Goldstein's suggestion to extend ->encode_fh() with flags for encoding globally unique file handles was endorsed by Hellwig as beneficial for both overlayfs and NFS. [id://CAOQ4uxjAQu9sQt3qOOVWS5cz5B51Hg0m4RAjsreBkmPhg-2cyw@mail.gmail.com], [id://20260115063630.GA9671@lst.de]

  5. The SteamOS use case may not need overlayfs index at all. Amir questioned whether origin file handles from image A would be meaningful when switching to image B, suggesting uuid=off might be the appropriate solution instead. [id://CAOQ4uxhbz7=XT=C3R8XqL0K_o7KwLKsoNwgk=qJGuw2375MTJw@mail.gmail.com]

The thread continued beyond this week (through February 2026) with further iteration, but no patches from this series were accepted in their current form. The discussion highlights the tension between specialized use cases (SteamOS A/B partitioning) and kernel infrastructure cleanliness — a recurring theme in Linux filesystem development.
