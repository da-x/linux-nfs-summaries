NFS EOF Page Pollution Fix: Proposed Race Condition Patch for Nested VM Corruption

Summary

NFS EOF Page Pollution Fix: Proposed Race Condition Patch for Nested VM Corruption

Type: Bug fix regression investigation (NFS client)

Overview

Following last week's initial report of ext4 checksum corruption in nested virtual machines traced to the NFS client's "eof page pollution" protection fix, Trond Myklebust proposed a targeted patch this week addressing a suspected race condition in NFSv4.2 fallocate and copy offload operations.

Background (Prior Week)

Last week, Mark Bloch from NVIDIA reported that commit b1817b18ff20 ("NFS: Protect against 'eof page pollution'") caused intermittent ext4 directory checksum failures during boot of nested VMs. The setup involves qcow2 disk images stored on an NFSv4.2 share serving as backing storage for VMs running ext4 filesystems. Reverting the offending commits eliminated the issue, confirming causality.

This Week's Developments

Proposed Fix: Size Read Race in fallocate and Copy Offload

After several days of analysis, Trond Myklebust identified a specific race condition as the likely culprit. As explained by Trond:

I've been staring at this for several days now, and the only candidate for a bug in the NFS client that I can see is this one. Can you please check if the following patch helps?

The proposed patch, titled "NFSv4.2: Fix size read races in fallocate and copy offload", addresses a scenario where the pre-operation file size is read before locking the inode and quiescing O_DIRECT writes. This ordering issue can cause nfs_truncate_last_folio() to overwrite valid file data — directly contradicting the intent of the original eof page pollution fix.

The patch modifies two files:

  • fs/nfs/io.c (2 lines added)
  • fs/nfs/nfs42proc.c (21 insertions, 10 deletions)

NVIDIA's Response and Testing Status

Mark Bloch responded with additional details about the test environment. He confirmed that qcow2 images use dynamic file sizing (with a fixed maximum of 35 GB), rather than pre-allocated fixed sizes:

The file size is dynamic (with a fixed maximum of 35 GB).

Regarding NFS discard/unmap behavior, Mark initially stated the discard option was set to "ignore," but Trond noted this contradicted earlier QEMU command-line output showing "discard":"unmap":

I believe in your previous email you had it set as "unmap"... However if you've already tested with "ignore" and it didn't make a difference then let's not worry about it.

Mark committed to having his team test the proposed patch:

Thanks for the patch, I'll let the team dealing with the issue know and let them test the patch. I'll update once I know anything.

Technical Significance

This investigation highlights a subtle but critical interaction in NFS client development:

  1. The original eof page pollution fix was designed to prevent data corruption when users mmap() beyond EOF and write into the folio straddling the end-of-file boundary — a legitimate concern addressed by xfstest generic/363.

  2. The regression suggests that the protection mechanism itself can corrupt valid data under certain race conditions, particularly when NFSv4.2 operations like fallocate and copy offload interact with dynamic file sizing in sparse image files (qcow2).

  3. The proposed fix ensures proper ordering of inode locking relative to size reads, preventing nfs_truncate_last_folio() from acting on stale size information.

Current Status

As of the end of this week's window, NVIDIA's team is testing Trond's proposed patch. The outcome of that testing will determine whether this race condition fix resolves the ext4 checksum corruption observed in nested VM workloads. A resolution would represent an important correction to NFS client data integrity protections without rolling back the original eof page pollution safeguard entirely.
