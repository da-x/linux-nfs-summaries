Exposing Case Folding Behavior: v3 Patch Series for NFSD, NFS Client, and Filesystem Case Sensitivity Reporting

Summary

Exposing Case Folding Behavior to NFS and SMB File Services (v3)

Type: New feature / protocol enhancement

Chuck Lever posted version 3 of his 16-patch series "Exposing case folding behavior" on Monday, January 12th. The series introduces a kernel-wide mechanism for filesystems to report their case sensitivity and case preservation characteristics via the file_kattr structure, enabling NFSD, ksmbd, and NFS clients to accurately convey filename semantics across protocol boundaries.

Motivation and Background

The Linux NFS community has a growing interest in supporting NFS clients on Windows and macOS platforms, where filename behavior diverges from traditional POSIX semantics. Lever explains:

"The Linux NFS community has a growing interest in supporting NFS clients on Windows and MacOS platforms, where file name behavior does not align with traditional POSIX semantics."

A key driver is interoperability with Windows-based NFS clients (e.g., ms-nfs41-client), which explicitly require servers to report FATTR4_WORD0_CASE_INSENSITIVE = TRUE. Lever notes:

"When an NFS client knows the server is case-insensitive, it can avoid issuing multiple LOOKUP/READDIR requests to search for case variants, and applications like Win32 programs work correctly without manual workarounds or code changes."

The Linux NFS client also benefits: Trond Myklebust merged patches four years ago that enable the client to detect case-insensitive shares and adjust negative dentry caching behavior accordingly.

Series Overview

The series adds two boolean fields — case_insensitive and case_preserving — to the kernel-internal struct file_kattr, and implements fileattr_get callbacks across twelve filesystems: FAT, exFAT, NTFS3, HFS, HFS+, ext4, XFS, CIFS, NFS client, f2fs, vboxsf, and ISO9660. The default for unsupported filesystems remains POSIX behavior (case-sensitive, case-preserving).

NFS-specific patches are the core of this series:

  • PATCH 10/16: The NFS client implements fileattr_get to expose case sensitivity information it already retrieves from servers during mount (via PATHCONF for NFSv3, or FATTR4_CASE_INSENSITIVE/FATTR4_CASE_PRESERVING for NFSv4). This enables re-export scenarios where an NFS-mounted filesystem is served via NFSD.

  • PATCH 14/16: NFSD's NFSv3 PATHCONF handler replaces its hard-coded MSDOS_SUPER_MAGIC check with a query through ->fileattr_get, allowing accurate reporting for any filesystem that implements the interface.

  • PATCH 15/16: NFSD's NFSv4 path stops returning hard-coded values and instead queries the underlying filesystem via nfsd_get_case_info(), supporting per-directory settings for filesystems like ext4 that allow mixing case-sensitive and case-insensitive directories.

Review Feedback

Christian Brauner approved the overall direction but raised a UAPI concern:

"This reads like you are exposing the new file attr bits via userspace but I can only see changes to the kernel internal headers not the uapi headers. So are you intentionally not exposing this as a new uapi extension to file attr or is this an accident?"

Lever confirmed this was unintentional and promised a fix for v4:

"The intention is to expose the new bits to user space. IIRC those got removed from uapi headers when I converted from using statx. I can fix that up and post a v4."

Christoph Hellwig suggested an alternative flag design:

"Given that not case preserving is by far the exception, maybe have a flag for that instead?"

Hellwig also questioned FAT's case-preservation claim:

"Is that actually true? It's been a while since I deal with them, but IIRC at least vfat is case preserving."

Darrick J. Wong reviewed the XFS patch and acknowledged correctness but raised a broader concern about the semantics of case folding rules:

"But the next obvious question I would have as a userspace programmer is 'case insensitive how, exactly?', which was the topic of the previous revision."

He noted the complexity of NLS-aware casefolding across different languages. Neal Gompa added context on NTFS's dual namespace (Win32k case-insensitive vs. SFU/SUA/LXSS case-sensitive) and emphasized:

"The biggie is that it has to be NLS aware. That's where it gets complicated since there are different case rules for different languages."

Status and Next Steps

The series has broad support across filesystem maintainers. Two items require attention before v4: (1) exposing the new file attribute bits in UAPI headers as originally intended, and (2) addressing Christoph Hellwig's question about FAT's case-preservation behavior. The broader discussion about encoding detailed case-folding transformation rules (Unicode version, NLS locale specifics) was deferred to a future effort.
