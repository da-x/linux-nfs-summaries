NFSv4.2 POSIX ACL Client Patch 5/7: Build Failures Across Architectures; v2 Resolves Missing Server Dependency

Summary

NFSv4.2 POSIX ACL Client — Patch 5/7 Build Failures Reappear on Additional Architectures; v2 Resolves Issue

Classification: New feature (build error feedback)

Background

This thread continues the discussion around patch 5/7 of Rick Macklem's seven-patch series introducing client-side support for the NFSv4.2 POSIX draft ACL extension. In the prior week (see summary), the kernel test robot reported build failures on x86_64 configurations (both Clang and GCC) due to undeclared identifiers FATTR4_WORD2_POSIX_DEFAULT_ACL and FATTR4_WORD2_POSIX_ACCESS_ACL. Rick Macklem explained that these definitions come from a companion server-side patch series, and the 0-DAY CI system was testing the client patches independently. He asked whether to incorporate the server dependency into the client set.

This Week's Activity

On January 9–10, the kernel test robot reported the same build failures against patch 5/7, but this time across three additional architecture/compiler combinations:

1. um-allyesconfig with GCC-14 (x86_64 user-mode Linux)

The first report (kernel test robot) tested against trondmy-nfs/linux-next and also confirmed the issue on linus/master v6.19-rc4 and next-20260109. Using gcc-14 (Debian 14.2.0), the robot reproduced:

"error: 'FATTR4_WORD2_POSIX_DEFAULT_ACL' undeclared (first use in this function)"

"error: 'FATTR4_WORD2_POSIX_ACCESS_ACL' undeclared (first use in this function); did you mean 'FATTR4_WORD1_TIME_ACCESS_SET'?"

Additionally, a control-flow warning was flagged:

"warning: control reaches end of non-void function [-Wreturn-type]"

This warning arises because the switch statement in nfs4_server_supports_acls() lacks an explicit default return path — when all cases are consumed but the compiler cannot prove exhaustiveness, it warns about missing returns. The problematic code at lines 6082–6085 of fs/nfs/nfs4proc.c:

case NFS4ACL_POSIXDEFAULT:
    return server->attr_bitmask[2] & FATTR4_WORD2_POSIX_DEFAULT_ACL;
case NFS4ACL_POSIXACCESS:
    return server->attr_bitmask[2] & FATTR4_WORD2_POSIX_ACCESS_ACL;

2. sh-allmodconfig with GCC-15 (SuperH architecture)

The second report (kernel test robot) confirmed the identical undeclared identifier errors using sh4-linux-gcc (GCC 15.2.0), demonstrating that the issue is not architecture-specific but rather a universal missing-definition problem.

3. hexagon-allmodconfig with Clang-17 (Qualcomm Hexagon)

The third report (kernel test robot) reproduced the same two undeclared identifier errors using clang version 17.0.6 on the Hexagon architecture, further confirming the cross-platform nature of the build failure.

Resolution: v2 Patch Series Addresses the Issue

Rick Macklem responded to the sh-architecture report with a concise resolution update:

"This should be fixed in the v2 patches I posted." Rick Macklem

"(It needs the same patch as patch 0001 in the server series, so I added it to the v2 series.)" Rick Macklem

As confirmed by the separate v2 series thread (see summary), Rick posted version 2 of his client series on January 3, which incorporated the server-side POSIX ACL attribute definitions as patch 1/8 — making the series self-contained and eliminating the build failures. The v2 cover letter properly credited the kernel test robot reports with Reported-by: and Closes: tags.

Technical Significance

This thread illustrates several important aspects of kernel development for NFS client features:

  1. Interdependent client/server patches: The nfs4_server_supports_acls() function in fs/nfs/nfs4proc.c checks server capability bitmask values (FATTR4_WORD2_POSIX_DEFAULT_ACL, FATTR4_WORD2_POSIX_ACCESS_ACL) that are defined only in the companion server series. Without bundling these definitions, the client code cannot compile independently.

  2. Cross-architecture CI coverage: The 0-DAY CI system caught the same issue across multiple architectures (x86_64 user-mode Linux, SuperH, Hexagon) and compilers (GCC 14, GCC 15, Clang 17), demonstrating the breadth of automated testing for the NFS subsystem.

  3. Rapid iteration: Rick Macklem resolved the dependency issue by posting v2 within a day of the initial reports, incorporating the missing definitions directly into the client series. This self-contained approach is the recommended practice for feature patches that span multiple subsystems.

Status

The build failures reported in this thread have been addressed in the v2 patch series (PATCH v2 0/8), which is now under review with a separate outstanding issue regarding CONFIG_NFS_V4 conditional compilation (raised by Anna Schumaker in the v2 thread).
