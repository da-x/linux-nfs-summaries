Exposing Case Folding Behavior: v4 Series for NFSD, NFS Client, and Filesystem Case Sensitivity Reporting

Summary

Exposing Case Folding Behavior: v4 Patch Series for NFSD, NFS Client, and Filesystem Case Sensitivity Reporting

Type: New feature / protocol enhancement

Chuck Lever posted version 4 of his 16-patch series "Exposing case folding behavior" on Wednesday, January 14th. This is a follow-up to the v3 series posted earlier this week (see prior summary for v3 discussion). The series introduces a kernel-wide mechanism for filesystems to report their case sensitivity and case preservation characteristics via the file_kattr structure, enabling NFSD, ksmbd, and NFS clients to accurately convey filename semantics across protocol boundaries.

Motivation: Cross-Platform NFS Client Interoperability

The primary driver for this work is improving interoperability between Linux NFS servers and non-POSIX clients, particularly Windows and macOS. Lever explains the motivation in the cover letter [id://20260114142900.3945054-1-cel@kernel.org]:

"The Linux NFS community has a growing interest in supporting NFS clients on Windows and MacOS platforms, where file name behavior does not align with traditional POSIX semantics."

A concrete example is the ms-nfs41-client, a Windows-based NFS client that explicitly requires servers to report FATTR4_WORD0_CASE_INSENSITIVE = TRUE. Lever notes:

"When an NFS client knows the server is case-insensitive, it can avoid issuing multiple LOOKUP/READDIR requests to search for case variants, and applications like Win32 programs work correctly without manual workarounds or code changes."

The Linux NFS client also benefits significantly. Trond Myklebust merged patches four years ago enabling the client to detect case-insensitive shares and adjust negative dentry caching behavior accordingly — a lookup for "FILE.TXT" failing should not cache a negative entry when "file.txt" exists on a case-insensitive share.

Key Changes from v3 to v4

The v4 series addresses three items raised during v3 review:

  1. Renamed case_preserving to case_nonpreserving: Following Christoph Hellwig's suggestion that non-preservation is the exception, the flag was inverted for clarity [id://20260114142900.3945054-2-cel@kernel.org].
  2. VFAT confirmed as case-preserving: Lever corrected the FAT implementation based on Hellwig's earlier question about whether VFAT preserves case.
  3. UAPI exposure restored: Christian Brauner noted in v3 that the new file attribute bits were missing from UAPI headers. Lever confirmed this was unintentional and restored the UAPI changes [id://20260114142900.3945054-2-cel@kernel.org].

NFS Client Development: Patch 10/16 — fileattr_get for Case Sensitivity

The NFS client patch [id://20260114142900.3945054-11-cel@kernel.org] is central to the series' re-export use case. The NFS client already retrieves case sensitivity information from servers during mount via PATHCONF (NFSv3) or FATTR4_CASE_INSENSITIVE/FATTR4_CASE_PRESERVING attributes (NFSv4). This patch exposes that information through fileattr_get:

"An NFS server re-exporting an NFS mount point needs to report the case sensitivity behavior of the underlying filesystem to its clients. Without this, re-export servers cannot accurately convey case handling semantics, potentially causing client applications to make incorrect assumptions about filename collisions and lookups."

For NFSv2 mounts lacking PATHCONF support, the patch defaults to standard POSIX behavior: case-sensitive and case-preserving. The implementation touches multiple NFS subsystem files (client.c, inode.c, nfs3proc.c, nfs4proc.c, etc.) to propagate the flags through the VFS layer.

NFSD Enhancements: Accurate Case Reporting for NFSv3 and NFSv4

Two patches modernize NFSD's case sensitivity reporting, replacing hard-coded assumptions with dynamic filesystem queries:

NFSv3 PATHCONF (Patch 14/16) [id://20260114142900.3945054-15-cel@kernel.org]

The previous implementation contained a hard-coded MSDOS_SUPER_MAGIC check that only recognized FAT filesystems as case-insensitive:

"The hard-coded MSDOS_SUPER_MAGIC check in nfsd3_proc_pathconf() only recognizes FAT filesystems as case-insensitive. Modern filesystems like F2FS, exFAT, and CIFS support case-insensitive directories, but NFSv3 clients cannot discover this capability."

The new implementation queries the export's actual case behavior through ->fileattr_get, allowing accurate reporting for any filesystem that implements the interface.

NFSv4 Attributes (Patch 15/16) [id://20260114142900.3945054-16-cel@kernel.org]

Similarly, NFSD's NFSv4 path previously returned hard-coded values indicating all exports were case-sensitive and case-preserving:

"NFSD currently provides NFSv4 clients with hard-coded responses indicating all exported filesystems are case-sensitive and case-preserving. This is incorrect for case-insensitive filesystems and ext4 directories with casefold enabled."

The patch queries the underlying filesystem via nfsd_get_case_info() and supports per-directory settings, which is important for filesystems like ext4 that allow mixing case-sensitive and case-insensitive directories within an export.

Review Feedback This Week

Struct Layout Discussion: Jan Kara, Darrick J. Wong, Christian Brauner

Jan Kara raised a question about the struct layout in [id://3kq2tbdcoxxw3y2gseg7vtnhnze5ee536fu4rnsn22yjrpsmb4@fpfueqqiji5q]:

"file_attr already have fa_xflags field and there is already one flag which doesn't directly correspond to on-disk representation (FS_XFLAG_HASATTR) so we could also put the two new flags in there... I have hard time imagining fa_case_behavior would grow past the two flags you've introduced so u32 seems a bit wasteful."

Darrick J. Wong concurred in [id://20260114200130.GJ15551@frogsfrogsfrogs]:

"Sounds like a better use of space in struct file_attr than adding another pair of u32."

Christian Brauner also approved this approach in [id://20260115-mitgift-crashtest-35039325f65c@brauner]:

"Fine by me as well."

Chuck Lever acknowledged the feedback and agreed to wait for additional guidance:

"No problem. I'll wait for additional guidance on this." [id://7b6aa90f-79dc-443a-8e5f-3c9b88892271@app.fastmail.com]

FAT nocase Mount Option: OGAWA Hirofumi

OGAWA Hirofumi, the FAT maintainer, raised an important edge case regarding the nocase mount option for MSDOS filesystems in [id://874ionw8ty.fsf@mail.parknet.co.jp]:

"Hm, if 'nocase' option is specified for msdos, it would be the case preserving (ignores/breaks the spec though)."

He demonstrated that with nocase, MSDOS preserves the original case of filenames rather than uppercasing them:

$ touch aAa.txT
$ ls
aAa.txT

This observation suggests the FAT implementation may need refinement to correctly handle the interaction between the nocase mount option and case preservation reporting.

Series Scope

The 16-patch series implements fileattr_get for case sensitivity across twelve filesystems: FAT, exFAT, NTFS3, HFS, HFS+, ext4, XFS, CIFS, NFS client, f2fs, vboxsf, and ISO9660. It also updates NFSD (patches 14/16 and 15/16) and ksmbd (patch 16/16 [id://20260114142900.3945054-17-cel@kernel.org]) to query actual filesystem case behavior rather than relying on hard-coded assumptions. The default for unsupported filesystems remains POSIX behavior (case-sensitive, case-preserving).

Status and Outlook

The v4 series has resolved the major UAPI and flag-naming concerns from v3 review. The remaining open item is the struct layout question raised by Jan Kara — whether to use a dedicated fa_case_behavior field or pack the flags into the existing fa_xflags field. Chuck Lever is awaiting consensus on this point before proceeding. The FAT nocase edge case flagged by OGAWA Hirofumi may also require attention in a subsequent revision.
