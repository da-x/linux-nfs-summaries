IOCB_NOWAIT v4: Maintainer Process Discussion on "Applied" Notifications

IOCB_NOWAIT Writes v4: Process Discussion on "Applied" Notification Timing

Summary

Bridge to Prior Week

Christoph Hellwig's series to re-enable IOCB_NOWAIT writes to files has been through six iterations since November 2025, addressing a performance regression where commit 66fa3cedf16a ("fs: Add async write file modification handling") effectively disabled non-blocking writes because timestamp updates always required blocking operations. Last week (ending January 8), the series reached v6 with final polish — incorporating fixes for ctime sampling order and a FAT bisectability concern — and received Reviewed-by tags from Jan Kara, Jeff Layton, and Chaitanya Kulkarni. The v4 iteration of this thread had previously surfaced confusion when Brauner sent an "applied" notification before Hellwig flagged bugs discovered by Julia Lawall's static type-checking tools; Brauner clarified the patches had never actually been pushed to any tree.

This Week's Activity (January 12, 2026)

Three messages were exchanged on January 12 as Brauner and Hellwig revisited the procedural question about "applied" notification timing that arose in the prior week.

Brauner Seeks Clarification. Christian Brauner followed up on Hellwig's earlier suggestion to improve the clarity of "applied" notifications, asking for specifics:

"What are you thinking of exactly?" Christian Brauner

Hellwig Proposes a Simple Rule. Hellwig responded with a straightforward procedural recommendation:

"Only send out the applied message when something is actually pushed to the public tree?" Christoph Hellwig

Brauner Acknowledges but Cautions. Brauner recognized the practical challenge: sending an "applied" notification only after pushing to a public tree often means patches are still waiting on testing, which can create its own ambiguity. He committed to paying more attention but tempered expectations:

"When that happens it usually means that it's still waiting on tests. I can pay more attention to this but don't expect it to be perfect in all cases." Christian Brauner

Nature of the Discussion

This thread is about maintainer process rather than a new feature, protocol change, or bug fix. The substantive technical work — Hellwig's v6 series to re-enable IOCB_NOWAIT writes — was completed and reviewed in the prior week. This week's exchange represents a brief meta-discussion about communication best practices between subsystem maintainers and patch authors.

NFS Client Relevance

While this week's messages themselves do not contain NFS-specific technical content, the broader thread remains highly relevant to NFS client development:

  • The v6 series (posted last week) includes [PATCH 03/11] nfs: split nfs_update_timestamps, which refactors the NFS client's timestamp update infrastructure to align with new VFS conventions — a prerequisite for future non-blocking timestamp support on NFS.
  • Restoring IOCB_NOWAIT functionality directly impacts io_uring-based NFS write performance, reducing unnecessary context switches for asynchronous I/O workloads.

Conclusions

  • The discussion settled on a pragmatic understanding: Brauner will endeavor to send "applied" notifications only after patches are pushed to public trees, though he acknowledged that testing delays make this imperfect in practice.
  • No new technical changes to the IOCB_NOWAIT series were proposed this week; the v6 iteration from last week remains the current state of the patch set.
  • The exchange highlights an ongoing tension in kernel development between timely communication of patch status and the reality of testing workflows.
