pNFS blkmapd Error Noise and Distribution Defaults for nfs-blkmap.service

Summary

pNFS Block Layout Daemon: Error Noise and Distribution Defaults

A discussion arose on the nfs-utils mailing list regarding the behavior of blkmapd, the pNFS block layout mapping daemon, and how various Linux distributions handle the nfs-blkmap.service systemd unit by default. The thread centers on a long-standing Debian bug report (#1009106) concerning an alarming but ultimately benign error message emitted at service startup.

The Problem: A Harmless But Irritating Error

Salvatore Bonaccorso opened the discussion by describing how Debian ships nfs-blkmap.service enabled by default via the nfs-common package, following the guidance in nfs.systemd(7). However, on systems not actively using pNFS with the block layout protocol, the daemon logs an error at startup:

"blkmapd[898]: open pipe file /run/rpc_pipefs/nfs/blocklayout failed: No such file or directory"

Bonaccorso explained that this is largely harmless. Since commit 42a065968d0f ("blkmapd: allow blocklayoutdriver module to load/unload"), the pipe file at /run/rpc_pipefs/nfs/blocklayout is dynamically created and deleted when the blocklayoutdriver kernel module is loaded or unloaded. The daemon correctly detects the pipe's creation via inotify watches once the module is loaded, as confirmed by the subsequent log line:

"blkmapd[898]: blocklayout pipe file created"

The question posed was whether this startup error should be logged at error level at all, given that it is expected behavior on systems without pNFS block layout in use. Bonaccorso advocated for keeping the service enabled by default to ensure administrators who do want pNFS with block layout can simply load the module:

"For Debian purposes at least I would like to make things bit less irritating for users, keep ideally the service enabled by default, so that administrators who want to make use of pNFS setup with the blocklayout layout protocol, they just need to make the module load."

The Response: Block Layout Is Deprecated

Christoph Hellwig responded with a more fundamental concern about the block layout protocol itself. He argued that Debian should reconsider enabling blkmapd by default, pointing out that the original block layout is deprecated due to safety concerns:

"The original blocklayout is deprecated because there is almost no way to use it safely. So I'd argue for not enabling blkmapd by default, and maybe even splitting it into a separate binary package."

Hellwig also clarified an important distinction: the newer SCSI and NVMe pNFS layouts are safe to use and do not require blkmapd at all:

"Note that none of this affects the revised scsi/nvme layouts that are safe to use, and don't require blkmapd."

Distribution Practices: Fedora and RHEL Already Disabled It

Scott Mayhew chimed in confirming that Red Hat-based distributions have already taken a different approach. On Fedora and RHEL, nfs-blkmap.service is disabled by default via systemd presets:

"Right, on both Fedora and RHEL nfs-blkmap.service is disabled by default (via /usr/lib/systemd/system-preset/99-default-disable.preset) because we support SCSI layout but not block layout."

Mayhew also noted that there had been prior internal discussions about removing blkmapd from Red Hat packages entirely, reflecting the declining relevance of the original block layout protocol.

Conclusion

This thread highlights a divergence in distribution policies around pNFS client infrastructure:

  • Debian enables nfs-blkmap.service by default but faces user complaints about an alarming (yet benign) startup error message when the block layout driver is not loaded.
  • Fedora/RHEL disable the service by default, recognizing that only the SCSI/NVMe layouts are actively supported and safe — and those do not need blkmapd.

The discussion did not conclude with a definitive resolution for Debian, but it underscored two key points: (1) the original block layout protocol is deprecated and unsafe, and (2) modern pNFS deployments using SCSI or NVMe layouts operate without blkmapd entirely. This suggests that distributions may eventually want to phase out or de-emphasize blkmapd in their default configurations.
