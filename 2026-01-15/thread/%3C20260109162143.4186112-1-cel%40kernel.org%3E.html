NFSv4.2 POSIX ACL Server Support: Patch Series v3 Submitted

Summary

Overview

This week, Chuck Lever and Rick Macklem submitted version 3 of a 13-patch series implementing server-side support for NFSv4.2 POSIX ACLs in the Linux kernel NFS daemon (knfsd). This is a new protocol feature, not a bug fix: it implements the IETF draft "POSIX Draft ACL support for Network File System Version 4, Minor Version 2" (draft-ietf-nfsv4-posix-acls).

"The Internet draft 'POSIX Draft ACL support for Network File System Version 4, Minor Version 2' defines an extension to NFSv4.2 that enables POSIX draft ACLs to be retrieved and set directly, without the lossy NFSv4->POSIX draft mapping algorithm." — Chuck Lever

The series was submitted on 2026-01-09 and, as of the end of this week's window, had not yet attracted replies from reviewers. Jeff Layton has provided Reviewed-by tags on several patches, indicating prior offline or earlier-round review.

Evolution of the Patch Series

This is the third iteration of the series. Key changes since v2 include:

  • Removal of an NFS_MAX_ACL_ENTRIES check
  • Clearing POSIX ACL fattr4 bits when CONFIG_NFSD_V4_POSIX_ACLS is disabled
  • Addition of xdrgen support for % pass-through lines in XDR specifications
  • Updating the .x file based on Rick Macklem's -01 draft revision

Since v1, the series was restructured to be bisect-safe, folded fixes into early patches, and introduced a compile-time Kconfig gate (CONFIG_NFSD_V4_POSIX_ACLS) to keep the feature experimental.

"This approach mirrors the existing NFSD_V4_DELEG_TIMESTAMPS option, which gates another experimental NFSv4 extension based on an unratified IETF draft." — Patch 02/13

Key Technical Arguments and Design Decisions

1. Avoiding Lossy ACL Translation

The core motivation for this work is the semantic imprecision of mapping between NFSv4 ACLs and POSIX draft ACLs:

"Mapping between NFSv4 ACLs and POSIX ACLs is semantically imprecise: a client that sets an NFSv4 ACL and reads it back may see a different ACL than it wrote." — Patch 04/13

The extension introduces four new protocol attributes that allow POSIX draft ACLs to be manipulated directly, analogous to the NFS_ACL sideband mechanism used with NFSv2/3. This enables tools like getfacl(1) and setfacl(1) to operate transparently over NFSv4.2.

2. Four New File Attributes

The series adds support for:

  • FATTR4_ACL_TRUEFORM — Reports whether a file stores permissions using NFSv4 ACLs or POSIX ACLs (ACL_MODEL_POSIX_DRAFT, ACL_MODEL_NFS4, or ACL_MODEL_NONE). Linux file systems never report ACL_MODEL_NFS4 since they do not store NFSv4 ACLs natively.
  • FATTR4_ACL_TRUEFORM_SCOPE — Indicates the granularity at which the ACL model varies (per file, per file system, or server-wide). Linux reports ACL_SCOPE_FILE_SYSTEM, reflecting that the SB_POSIXACL superblock flag applies uniformly to all files within a file system.
  • FATTR4_POSIX_ACCESS_ACL — Retrieves or sets the access ACL of any file or directory.
  • FATTR4_POSIX_DEFAULT_ACL — Retrieves or sets the default ACL of directories.

3. VERIFY/NVERIFY Prohibition

Per Section 9.3 of the IETF draft, POSIX ACL attributes must not be used with VERIFY or NVERIFY operations:

"Section 9.3 of draft-ietf-nfsv4-posix-acls-00 prohibits use of the POSIX ACL attributes with VERIFY and NVERIFY operations: the server MUST reply NFS4ERR_INVAL when a client attempts this." — Patch 08/13

Beyond protocol compliance, the patch notes that POSIX ACL ACE ordering is not mandated by clients, making reliable comparison impractical.

4. Refactored Error Reporting for SETATTR

Patch 09/13 introduces separate error fields (na_paclerr for access ACLs, na_dpaclerr for default ACLs) to distinguish which ACL type encountered an error during SETATTR. This enables the server to report per-ACL-type failures accurately when one succeeds and the other fails. The patch also adds validation that was previously absent:

  • Default ACL processing rejects non-directory targets with EINVAL
  • Access ACL processing rejects zero ACE count with EINVAL under ACL_SCOPE_FILE_SYSTEM semantics

5. Mutual Exclusion of ACL Models

The series enforces mutual exclusion between NFSv4 ACLs and POSIX ACLs on the same file object:

"Setting both op_acl and op_dpacl/op_pacl simultaneously returns nfserr_inval." — Patch 11/13

6. xdrgen Pass-Through Support

Patch 01/13 adds infrastructure to the xdrgen tool to support %-prefixed pass-through lines in XDR specifications, bringing it closer to feature parity with traditional rpcgen:

"This brings xdrgen closer to feature parity with traditional rpcgen while maintaining the existing document-order processing model." — Patch 01/13

7. SUPPATTR Advertisement

The final patch (13/13) adds the new POSIX ACL attributes to the SUPPATTR bitmasks, advertising support to NFSv4.2 clients:

"Now that infrastructure for NFSv4 POSIX draft ACL has been added to NFSD, it should be safe to advertise support to NFS clients." — Patch 13/13

Scope and Limitations

The current implementation does not support "per file" scope, where individual files could store either an NFSv4 ACL or a POSIX draft ACL. Instead:

"The implementation assumes POSIX draft ACLs apply to an entire file system when support for POSIX draft ACLs is indicated." — Cover letter

The feature remains gated behind CONFIG_NFSD_V4_POSIX_ACLS (disabled by default) as it is based on an unratified IETF draft.

Conclusion

This 13-patch series represents a significant step toward first-class POSIX ACL support in NFSv4.2, eliminating the lossy translation layer that has historically plagued cross-platform ACL management over NFS. The server-side implementation by Chuck Lever and Rick Macklem is now ready for review. No replies were received during this week's window; discussion is expected to continue next week.

Notably, a companion client-side series (also in v2) was submitted earlier in the week by Rick Macklem (separate thread, summarized elsewhere), suggesting coordinated progress on both ends of the NFSv4 POSIX ACL extension.
