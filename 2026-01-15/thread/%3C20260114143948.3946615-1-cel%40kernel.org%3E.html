bio_vec-Based RDMA Read/Write API for svcrdma

Summary

bio_vec-Based RDMA Read/Write API for svcrdma

Classification: New feature / API addition (with performance optimization)

Overview

Chuck Lever introduced a four-patch series on Wednesday, January 14 to add a bio_vec-based API for RDMA read and write operations in the RDMA core subsystem (drivers/infiniband/core/rw.c). The series targets the NFS server-side RDMA transport (svcrdma), eliminating unnecessary scatterlist conversions for callers that already maintain data in bio_vec format.

Patch Series Breakdown

Patch 1/4 — RDMA/core: add bio_vec based RDMA read/write API: Introduces rdma_rw_ctx_init_bvec() and rdma_rw_ctx_destroy_bvec() to accept bio_vec arrays directly, using dma_map_phys() for hardware RDMA devices and virtual addressing for software RDMA devices (rxe, siw). Memory registration support was deferred; callers requiring MR-based transfers received -EOPNOTSUPP.

Patch 2/4 — RDMA/core: use IOVA-based DMA mapping for bvec RDMA operations: Replaces per-page IOTLB synchronization with the two-step IOVA API (dma_iova_try_alloc/dma_iova_link/dma_iova_sync), reducing IOTLB flushes from O(n) to O(1).

Patch 3/4 — RDMA/core: add MR support for bvec-based RDMA operations: Adds rdma_rw_init_mr_wrs_bvec() to handle memory registration for bvec arrays by constructing a synthetic scatterlist from the bvec DMA addresses, reusing existing ib_map_mr_sg() infrastructure.

Patch 4/4 — svcrdma: use bvec-based RDMA read/write API: Converts svcrdma to the new API, replacing its scatterlist conversion code and significantly reducing the svc_rdma_rw_ctxt structure size from ~4KB (with an embedded scatterlist array of RPCSVC_MAXPAGES entries) down to approximately 100 bytes.

Review Feedback

Leon Romanovsky — Positive Initial Assessment

RDMA subsystem maintainer Leon Romanovsky provided an encouraging but preliminary review:

"Amazing, thanks a lot."

"I haven't done a deep-dive review yet, but from what I've seen so far it looks solid and well put together."

He also noted a minor issue in patch 4/4 — a stray Signed-off-by: cel@kernel.org line that appeared to be an error.

Christoph Hellwig — Substantive Technical Concerns

Christoph Hellwig raised several important points across multiple messages:

On the cover letter (pre-allocated vs. dynamic allocation):

"But isn't that comparison a little unfair when a preallocated/embedded data structure is replaced with a dynamic allocation?"

Hellwig questioned whether the structure size reduction claim was entirely fair, since the old approach used an embedded scatterlist while the new one uses dynamic allocation.

On patch 1/4 (API design and code duplication):

"Hmm, if we need to split/adjust bvecs, it might be better to pass a bvec_iter and let the iter handle the iteration?"

He suggested using bvec_iter for more robust iteration handling. He also flagged significant code duplication:

"Much of this seems to duplicate rdma_rw_init_map_wrs. I wonder if having a low-level helper that gets either a scatterlist or bvec array (or bvec_iter) and just has different inner loops for them would make more sense? If not we'll just need to migrate everyone off the scatterlist version ASAP :)"

On patch 2/4 (IOVA mapping logic):

Hellwig identified what he believed was a correctness issue with the IOVA mapping approach:

"This creates a single contiguous IOVA for all the passed in bvecs, even if they had non-contiguous host physical addresses."

"... which means that here you just need a single WR and SGE to register all of them. No need to split the IOVA space up again."

He also suggested passing the total transfer length from the caller rather than computing it in the helper.

On patch 3/4 (MR API):

"I wish we'd just have a bvec based MR API, and could use that. But I don't want to hold this work back, because of that."

Hellwig expressed a preference for a native bvec-based MR API but did not block the series on this point.

On patch 4/4 (svcrdma specifics):

Hellwig asked two clarifying questions:

"Can you explain why this switches to the dynamic allocation? To me that seems like a separate trade-off to bvec vs scatterlist."

"For both the old and new version, can you explain they have to start on a page boundary? Because that's not how scatterlists or bvecs work in general."

Chuck Lever's Responses

Chuck Lever addressed Hellwig's questions in two follow-up messages:

On dynamic allocation: He explained that the current svcrdma implementation uses a "default size" scatterlist with chaining for larger requests. With bvecs, there is no chaining concept — the exact-size array must be allocated dynamically, otherwise every context would need to carry a maximum-sized bio_vec array. He noted:

"Now, I suppose that later on we will be able to adopt the use of the rqstp->rq_bvec, when the full NFSD stack supports biovecs, and this allocation could be replaced, at least in some cases."

On page alignment: Lever clarified that the constraint stems from how xdr_buf represents pages — as an array of struct page * pointers with a single page_offset field applying only to the first entry. Subsequent entries have no per-entry offsets:

"Therefore the payload buffer starts at an offset of zero or greater in the first page in that array, but after that, the buffer continues across the boundaries of each page from offset 4095 on page N to byte 0 of page N+1, for all N."

He acknowledged the comment was misleading and noted:

"We can certainly clarify that as part of this bvec conversion series. And (much) later on, when the head, tail, and pages fields in 'struct xdr_buf' are replaced with a single bio_vec array, this issue goes away completely."

Status and Outlook

The thread concluded with substantive review feedback but no final resolution or revised patches within this week's window. Key open items include:

  1. API consolidation: Hellwig's suggestion to unify the scatterlist and bvec code paths into a single low-level helper with different inner loops.
  2. IOVA mapping correctness: Whether the contiguous IOVA approach in patch 2/4 is correct or needs adjustment.
  3. Minor fixes: The stray Signed-off-by line and comment clarifications.

This series represents an important step toward modernizing the NFS server-side RDMA transport, reducing memory footprint, and improving IOTLB synchronization efficiency — all while paving the way for eventual full bio_vec adoption across the NFSD stack.
