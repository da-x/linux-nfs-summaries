SUNRPC Sysfs Race Fix Backported to 5.15.y

Overview

This week saw a single-message thread: a backport of an important bug fix in the SUNRPC subsystem, targeting the stable 5.15.y kernel tree. The patch addresses a race condition that can cause a kernel oops when reading certain sysfs attributes of RPC transports.

Classification: Bug fix — specifically, a concurrency/locking issue in the SUNRPC transport layer that affects NFS client stability.

The Patch

Robert Garcia submitted **[PATCH 5.15.y] SUNRPC: lock against ->sock changing during sysfs read](https://lore.kernel.org/linux-nfs/20260318075551.1668418-1-rob_garcia@163.com/) on March 18, backporting upstream commit b49ea673e119f59c71645e2f65b3ccad857c90ee, originally authored by NeilBrown.

The core problem is straightforward but insidious: the ->sock field of an RPC transport can be set to NULL asynchronously unless the ->recv_mutex is held. Without proper locking, a concurrent sysfs read can dereference a now-NULL socket pointer, triggering a kernel oops.

NeilBrown's original commit message from 2022 described the issue precisely:

"->sock can be set to NULL asynchronously unless ->recv_mutex is held. So it is important to hold that mutex. Otherwise a sysfs read can trigger an oops."

He further noted that a prior attempt at fixing this problem was insufficient:

"Commit 17f09d3f619a ('SUNRPC: Check if the xprt is connected before handling sysfs reads') appears to attempt to fix this problem, but it only narrows the race window."

Technical Details

The patch modifies two files:

  • net/sunrpc/sysfs.c (5 lines changed)
  • net/sunrpc/xprtsock.c (7 lines changed)

The fix ensures that ->recv_mutex is properly held during sysfs reads of transport attributes, preventing the race where ->sock is nulled out between a null-check and a dereference. The patch carries two Fixes: tags:

  • 17f09d3f619a ("SUNRPC: Check if the xprt is connected before handling sysfs reads")
  • a8482488a7d6 ("SUNRPC query transport's source port")

Significance for NFS Client Development

This fix is directly relevant to NFS client stability. The SUNRPC layer is the foundation upon which the NFS client operates; any race condition in transport management can manifest as crashes when administrators or monitoring tools read sysfs attributes (such as the transport's source port) while connections are being established, torn down, or reset.

The fact that this fix was originally authored by NeilBrown in January 2022 and is now being backported to the 5.15.y stable tree underscores its importance for long-term support kernels still in use in production environments. The original upstream patch had already been accepted (as evidenced by the Upstream commit reference), but this backport ensures that systems running the 5.15.y LTS kernel also benefit from the correction.

Conclusion

This is a clean, uncontroversial backport of an established fix with no discussion or review activity this week. The patch addresses a genuine kernel oops scenario in the SUNRPC sysfs interface and carries proper sign-offs from NeilBrown, Anna Schumaker (NFS maintainer), and Robert Garcia (stable maintainer). For NFS client operators on 5.15.y kernels, this backport eliminates a potential crash vector when inspecting RPC transport state via sysfs.
