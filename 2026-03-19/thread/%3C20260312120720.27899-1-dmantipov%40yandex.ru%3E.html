NFS Server: Debate over Stack vs Heap Allocation in nfsd4_interssc_connect()

Summary

This week, the discussion surrounding Dmitry Antipov's patch to simplify nfsd4_interssc_connect() evolved from a straightforward code cleanup proposal into a technical debate about kernel memory allocation conventions. The thread highlights tensions between code simplification and established kernel development practices regarding stack usage and safety.

Type: Code Refactoring / Best Practice Debate (NFS Server, not Client) Key File: fs/nfsd/nfs4proc.c

Evolution of the Discussion

Last week, Dmitry Antipov submitted a patch to replace heap allocation (kzalloc/kfree) of a 64-byte buffer with stack allocation in nfsd4_interssc_connect(), arguing that the buffer was small enough for the stack and that using the return value of rpc_ntop() could eliminate a redundant strlen() call.

This week, NFS maintainer Chuck Lever responded with strong objections, effectively rejecting the patch based on safety and convention concerns.

Key Technical Arguments

Chuck Lever's Objections:

Lever identified two primary issues with the proposed simplification:

  1. Uninitialized Buffer Safety Issue: The original code used kzalloc, which zero-initializes memory. If rpc_ntop() failed (returning 0), the result would be an empty string. The new stack buffer is uninitialized, meaning a failure could cause snprintf to format garbage stack bytes into raw_data.

  2. Kernel Stack Convention: Lever emphasized that the kernel community prefers heap allocation for buffers to keep stack frames small, given the limited and shared nature of the kernel stack (8–16 KB). He noted:

"The kernel community has a general preference for heap allocation of buffers to keep stack frames small. The kernel stack is typically only 8–16 KB and shared across the entire call chain. While 64 bytes alone isn't alarming, this function already has struct sockaddr_storage (128 bytes) on the stack, and the cumulative effect matters more than any single buffer." Chuck Lever

Lever concluded that the patch traded a "well-understood heap allocation (with clear ownership and cleanup)" for marginal control flow simplification while introducing an uninitialized-buffer risk. He stated:

"The commit trades a well-understood heap allocation (with clear ownership and cleanup) for a marginally simpler control flow, while introducing the uninitialized-buffer subtlety. The kzalloc/kfree pattern it removed was idiomatic and not a maintenance burden: it's the standard way to handle buffers in kernel code." Chuck Lever

"The simplification benefit (removing one goto label and one error check) is modest compared to the cost of moving against the prevailing convention and losing the zero-initialization safety net." Chuck Lever

"The commit message does not provide a sufficient justification to warrant applying this patch." Chuck Lever

Dmitry Antipov's Response:

Antipov acknowledged the safety concern, noting it could be easily fixed with = {0} initialization. However, he pushed back on the stack size argument by questioning whether current -Wframe-larger-than warning thresholds are too permissive:

"If 64 + 128 is alarming enough for a single function, wouldn't you think that typical current values of -Wframe-larger-than are too large and better to be reduced to, say, 512 or even smaller?" Dmitry Antipov

Final Conclusions

The patch was effectively rejected by Chuck Lever due to:

  • The uninitialized buffer safety risk introduced by removing kzalloc
  • Violation of kernel conventions favoring heap allocation for buffers to preserve stack space
  • Insufficient justification in the commit message for deviating from idiomatic patterns

While Antipov suggested a trivial fix for the initialization issue, he did not resubmit the patch this week. The discussion underscores the NFS subsystem's adherence to conservative memory management practices, prioritizing safety and convention over minor code simplifications.

Note: This thread concerns NFS server (nfsd) development, not NFS client development or bug fixes. No client-side changes or critical bug resolutions were discussed in this thread.
