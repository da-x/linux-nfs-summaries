Automatic NFSv4 State Revocation via Netlink

Summary

This week, Chuck Lever submitted version 4 of a six-patch series titled [PATCH v4 0/6] Automatic NFSv4 state revocation on filesystem unmount [id://20260318-umount-kills-nfsv4-state-v4-0-56aad44ab982@oracle.com]. The series addresses a persistent operational pain point: when an NFS server exports a filesystem with active client state (opens, locks, delegations), unmounting the underlying filesystem fails with EBUSY. While the existing /proc/fs/nfsd/unlock_fs interface can force revocation, it operates at superblock granularity and lacks extensibility.

Key Technical Arguments and Evolution

1. Transition from Procfs to Netlink The series replaces previous VFS-based approaches with a new netlink command, NFSD_CMD_UNLOCK. This allows for typed, validated attributes and supports multiple scopes. The initial implementation includes:

  • IP Scope: A netlink equivalent of write_unlock_ip, releasing NLM locks for a specific client address.
  • Filesystem Scope: A netlink equivalent of write_unlock_fs, accepting a path string to revoke NFSv4 state, NLM locks, async COPY operations, and cached file handles.

2. Export-Scoped Revocation A significant enhancement in v4 is the refinement of the "filesystem" scope to operate at export granularity rather than superblock granularity. As Chuck Lever explained, when multiple exports share a filesystem, only state referencing files under the specified export root should be affected. The implementation walks all dentry aliases of each inode to ensure hard-linked files outside the export are not incorrectly matched [id://20260318-umount-kills-nfsv4-state-v4-5-56aad44ab982@oracle.com].

3. API Design Debate: Single Command vs. Multiple Commands Jeff Layton raised a structural concern regarding the netlink interface design. He questioned whether a single command with a "type" attribute was optimal, suggesting that different scopes require different attributes and would be easier to validate if implemented as distinct commands:

"I wonder if we'd be better served with different commands instead of passing a type value to a single command? Different types are going to require different attributes, and it'll be easier to validate those if they use different commands." [id://33d42b3de7a2c7cd61bdd01bae04a2e082755f95.camel@kernel.org]

Chuck Lever acknowledged this, noting that while he initially followed the philosophy of the THREADS command, the YAML/netlink infrastructure struggles with divergent argument sets:

"I don't think it would be difficult to break UNLOCK into three separate unlock netlink commands." [id://9ea5b835-5e91-458c-9929-c1df7e6df25d@kernel.org]

4. The Hardlink Across Exports Bug/Concern The most significant technical critique came from Jeff Layton regarding the export-scoped revocation logic. He highlighted a scenario where two exports (/export/foo and /export/bar) reside on the same superblock, and a file is hardlinked between them. If state is acquired via both paths, revoking state for one export might incorrectly revoke state for the other if the check relies solely on dentry aliases:

"Ouch the hardlinked thing makes this hard to reason about... Won't client foo's state end up being revoked too in that case?" [id://f582806fcf3c6d6f7416c24c55462fc502cb0ab0.camel@kernel.org]

Layton suggested tracking the specific export in the stateid structure (e.g., an st_export field) to ensure precise revocation. While he conceded that hardlinks across exports are rare, he emphasized maintainability:

"OTOH, hardlinks are rare so maybe this isn't worth fretting over." [id://c42d3896eb47aa3bb766f29776fd0aac2a1eb07d.camel@kernel.org]

Final Conclusions

Chuck Lever agreed that the current approach was difficult to reason about and committed to addressing the export-tracking issue in the next version:

"Probably rare, but the point is the current approach is difficult to reason about, thus will be hard to maintain. For v5, I'll try linking NFSv4 state to exports." [id://2ef59bf1-c4f7-4818-9f47-16d056edcb8b@kernel.org]

Jeff Layton provided Reviewed-by tags for the refactoring patches ([id://7288d90cf67a4a8b3473b0118f3ce844e3538a3b.camel@kernel.org], [id://e1c465a1010b702ff41af23caef6177ff88aa4e8.camel@kernel.org]) and noted that the userland support in nfs-utils would integrate well with this netlink interface. The discussion concluded with a clear path forward for v5: refine export-scoping to handle hardlinks correctly and potentially split the netlink commands for better API clarity.
