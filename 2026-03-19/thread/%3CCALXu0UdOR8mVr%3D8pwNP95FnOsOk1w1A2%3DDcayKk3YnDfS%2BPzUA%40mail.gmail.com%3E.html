Discussion on Increasing Default NFSv4 max_block_size to 4MB

Summary

Increase Default NFSv4 Server "max_block_size" to 4MB

Type: Protocol/Configuration Change Discussion
Status: Under Review / Data Collection Phase

Overview

This week's discussion centered on a proposal by Cedric Blancher to increase the default max_block_size for NFSv4 servers from its current value (1MB) to 4MB. The thread explored the feasibility of this change, client compatibility across different operating systems, and the need for data-driven validation before any default configuration changes are made in the Linux kernel NFSD subsystem.

Key Technical Arguments

Initial Proposal

Cedric Blancher opened the thread by referencing a prior debate on this topic:

"As debated a while ago, can the default NFSv4 server size for 'max_block_size' be increased to 4MB, please?" Cedric Blancher

Chuck Lever's Data-Driven Approach

Chuck Lever responded by emphasizing the need for empirical evidence before changing defaults. He noted that while administrative settings exist to raise this limit in recent kernel versions, he wanted concrete reports on real-world usage:

"Can you report your experience when you raise the limit? Hiccups, performance issues, etc? I would kind of like this exercise to be data-driven." Chuck Lever

Lever also raised a critical compatibility concern: without widespread client support for larger block sizes, increasing the server default would have limited practical impact. He specifically asked Rick Macklem (FreeBSD), Anna Schumaker (Linux client), and Roland Mainz (Windows/ms-nfs41-client) about their implementations' capabilities.

Client Compatibility Findings

Roland Mainz (ms-nfs41-client / Windows):
Roland reported successful testing with a 4MB max_block_size on Linux 6.17 NFS server using his ms-nfs41-client implementation:

"Mounting the filesystem with ms-nfs41-client and compiling Cygwin bash.exe and ms-nfs41-client with Visual Studio etc. works fine... ... and I verified that |FATTR4_MAXREAD| and |FATTR4_MAXWRITE| have the value |4194304| as expected." Roland Mainz

He also provided preliminary performance observations:

"I didn't make any benchmarks yet, but quick observation shows that cloning a git from a git bundle on the same NFSv4.2 filesystem is up from 8.1MB/s to 8.8MB/s." Roland Mainz

Rick Macklem (FreeBSD):
Rick confirmed that FreeBSD supports mounts larger than 1MB, though he noted limited testing:

"Although it has not seen much testing, it is possible to do a > 1Mbyte NFSv4 mount in FreeBSD. For a 2Mbyte mount, (the only size > 1Mbyte I've tried)..." Rick Macklem

He detailed the required kernel parameters (kern.maxphys, vfs.maxbcachebuf, kern.ipc.maxsockbuf) and admitted:

"I doubt anyone does this, but it works for trivial tests." Rick Macklem

Anna Schumaker (Linux NFS Client):
Anna provided the most significant update regarding Linux client support. She revealed that while a code change is required to support sizes greater than 1MB, she had already conducted testing:

"The NFS client would need a code change to support >1MB sizes. I spent some time playing around with 4MB yesterday and it passed all my tests." Anna Schumaker

Evolution of the Discussion

The thread progressed from a simple request to change defaults into a broader investigation of cross-platform client compatibility. Chuck Lever's response shifted the focus toward gathering concrete data, which prompted contributors from multiple NFS client implementations (Linux, FreeBSD, Windows/ms-nfs41-client) to report their status.

Key turning points:

  1. Chuck Lever's call for data established the need for empirical validation rather than theoretical justification.
  2. Roland Mainz's positive test results demonstrated that at least one non-Linux client (ms-nfs41-client) can handle 4MB blocks with observable performance benefits.
  3. Anna Schumaker's confirmation that Linux client support is feasible and has passed internal tests represents the most critical development, as the Linux NFS client is arguably the most widely deployed.

Conclusions and Next Steps

No definitive conclusion was reached this week regarding an immediate change to the default max_block_size. However, several important points emerged:

  • Client support is progressing: Both the Linux NFS client (Anna Schumaker) and ms-nfs41-client (Roland Mainz) have demonstrated capability with 4MB blocks.
  • FreeBSD support exists but is untested in production: Rick Macklem confirmed technical feasibility but noted limited real-world usage.
  • Data collection is ongoing: Chuck Lever's emphasis on data-driven decision-making suggests that more comprehensive benchmarking and field reports are needed before any default change is considered.

The discussion implies that the groundwork for increasing the default max_block_size is being laid, particularly with Anna Schumaker's positive test results on the Linux client side. Future patches or proposals may follow once broader testing data is available.

Relevance to NFS Client Development

This thread highlights active development in NFS client support for larger block sizes, which directly impacts I/O performance for large file operations. Anna Schumaker's work on the Linux NFS client to support >1MB transfers represents an important bug fix/enhancement area, as it removes a historical limitation that constrained throughput. The cross-platform nature of the discussion also underscores the importance of interoperability testing across different NFS implementations.
