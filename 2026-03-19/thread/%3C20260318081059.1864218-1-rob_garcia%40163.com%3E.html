SUNRPC sysfs race condition fix backported to 5.15.y

Summary

SUNRPC: Locking Fix for sysfs Read Race Condition Backported to 5.15.y

Overview

This week, a critical bug fix was backported to the stable 5.15.y kernel tree, addressing a race condition in the SUNRPC subsystem that could trigger a kernel oops during sysfs reads of transport socket information. The patch, originally authored by NeilBrown and upstreamed as commit b49ea673e119f59c71645e2f65b3ccad857c90ee, was submitted for stable inclusion by Robert Garcia.

Classification: Bug fix — race condition leading to potential kernel oops in SUNRPC sysfs interface.

Technical Details

The issue centers on the ->sock pointer within the SUNRPC transport structure (xprtsock). This pointer can be set to NULL asynchronously unless the ->recv_mutex is held. When a user-space process reads from certain sysfs attributes (such as the transport's source port), the kernel code accesses ->sock without proper synchronization, creating a race window where the socket may be freed or nulled out between the check and the dereference.

NeilBrown identified that a previous attempt to fix this problem was insufficient:

"Commit 17f09d3f619a ("SUNRPC: Check if the xprt is connected before handling sysfs reads") appears to attempt to fix this problem, but it only narrows the race window." NeilBrown

The patch addresses two specific commits:

  • Fixes: 17f09d3f619a ("SUNRPC: Check if the xprt is connected before handling sysfs reads")
  • Fixes: a8482488a7d6 ("SUNRPC query transport's source port")

The Fix

The solution involves ensuring that ->recv_mutex is held during sysfs read operations in two locations:

  1. net/sunrpc/sysfs.c: Modified to properly acquire the mutex before accessing transport socket information.
  2. net/sunrpc/xprtsock.c: Updated to ensure consistent locking when querying the transport's source port.

The patch modifies 2 files with 10 insertions and 2 deletions, a minimal but impactful change that closes the race window entirely rather than merely narrowing it.

Significance for NFS Client Development

While this fix targets the SUNRPC subsystem (the RPC transport layer shared by NFS and other RPC-based protocols), it has direct implications for NFS client stability:

  • Kernel oops prevention: Without proper locking, reading sysfs attributes related to NFS/RPC transports could crash the kernel — a serious reliability issue for production systems.
  • Stable tree backport: The fact that this fix was backported to the 5.15.y stable tree indicates its importance for long-term support kernels still in widespread use.
  • Race condition resolution: This represents a class of bugs where asynchronous socket teardown races with user-space diagnostic reads, a scenario particularly relevant during NFS connection failures or server migrations.

Conclusion

This is a straightforward but important stability fix. NeilBrown's analysis correctly identified that the prior mitigation was inadequate, and the proper solution — holding ->recv_mutex during sysfs reads — eliminates the race condition entirely. The patch carries sign-offs from NeilBrown, Anna Schumaker (NFS maintainer), and Robert Garcia (stable backporter), indicating broad consensus on its correctness and necessity.
