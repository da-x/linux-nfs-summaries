NFS writepages infinite loop on -EBADF after state recovery failure

Summary

Bug Report: NFS nfs_writepages Infinite Loop After State Recovery Failure

Type: Bug fix (infinite loop in NFS client writeback path)

Overview

Li Lingfeng of Huawei reported a critical bug in the NFS client where nfs_writepages enters an infinite loop after a server restart and state recovery failure, causing mount operations to hang indefinitely As described by Li Lingfeng.

Problem Description

The bug manifests when the NFS server is restarted and the client's state manager attempts to reclaim open files. If the server returns errors such as EROFS, EIO, or ESTALE during reclamation, the affected file's state is marked as bad via nfs4_state_mark_open_context_bad. The reporter explained:

"When the NFS server is restarted, the client's state manager attempts to reclaim open files. If the server returns errors such as EROFS, EIO, or ESTALE during reclamation, the affected file's state is marked as bad (via nfs4_state_mark_open_context_bad)."

Subsequently, when the kernel writeback worker (wb_workfn) tries to flush dirty pages for that inode, nfs_writepages enters an infinite loop. The root cause is that nfs_page_create returns -EBADF for the bad open context, but nfs_writepages does not treat -EBADF as a fatal error:

"nfs_writepages retries the loop as long as the error is not fatal according to nfs_error_is_fatal(). Since -EBADF is not considered fatal, it keeps retrying forever."

This prevents the superblock lock from being released, causing any concurrent mount operation to hang.

Call Chain Analysis

The reporter provided a detailed call chain showing how the bug propagates:

  1. State recovery path: nfs4_do_reclaim → nfs4_reclaim_open_state → __nfs4_reclaim_open_state (gets -ESTALE) → nfs4_state_mark_recovery_failed → nfs4_state_mark_open_context_bad → sets the NFS_CONTEXT_BAD bit.

  2. Writeback path: wb_workfn → wb_do_writeback → writeback_sb_inodes → __writeback_single_inode → do_writepages → nfs_writepages (loops here) → write_cache_pages → nfs_writepages_callback → nfs_do_writepage → nfs_page_async_flush → nfs_create_subreq → nfs_page_create (returns -EBADF).

Reproduction Steps

The reporter provided a reliable reproducer on Linux 7.0-rc4:

  1. Set up an NFS server with an export containing test data.
  2. On the client, mount the export and run a Python script that opens a file, writes ~1GB of dirty pages, and keeps the file descriptor open.
  3. Restart the server and wipe the underlying filesystem to force ESTALE errors during state recovery.

Temporary Workaround

The reporter proposed a patch that treats -EBADF as a fatal error in nfs_writepages, thereby breaking the infinite loop. This workaround was described as:

"We have applied the following patch to break the loop by treating -EBADF as fatal in nfs_writepages"

Current Status

As of this week (ending 2026-03-19), this thread contains only the initial bug report with no replies from maintainers or other developers. The discussion remains open, awaiting review and potential integration of the proposed fix into the mainline NFS client code.
