Soft Mount Ineffective with NFS_CS_NO_RETRANS_TIMEOUT: Maintainer Refuses Client-Side Workaround

Summary

NFS Client Hang with NFS_CS_NO_RETRANS_TIMEOUT: Soft Mount Ineffectiveness and Maintainer Pushback

Background (Prior Weeks)

This thread, originating in August 2025, concerns persistent hangs in the Linux NFS client when dealing with unresponsive servers. Zhangjian from Huawei reported that over 400,000 delegations accumulated in the NFS_DELEGATION_REVOKED state on kernel 5.10, causing massive TEST_STATEID storms. The core technical debate has centered on whether the NFS client should timeout or retransmit when the TCP connection is established but the server never replies — a scenario governed by the NFS_CS_NO_RETRANS_TIMEOUT flag.

In prior weeks (see 2026-03-12 summary), Trond Myklebust emphasized that the NFSv4 spec forbids retransmission on an established connection, and that slot exhaustion would occur if clients unilaterally timed out. He pointed users toward soft mount options as a workaround for non-POSIX-tolerant applications.

This Week's Activity (March 13)

The discussion continued with two messages on March 13, where Zhangjian challenged the effectiveness of the recommended soft mount option and Trond delivered a firm concluding response.

Zhangjian: Soft Mount Does Not Work When Connection Is Established

Zhangjian reported that even after mounting with soft,retrans,timeo options, the client still hangs indefinitely:

"I have already mounted with soft,retrans,timeo options. The connection is in established state. But since NFS_CS_NO_RETRANS_TIMEOUT is set. The OPEN rpctask will not return -ETIMEOUT. Any operation waiting for the seqid will hang. The soft don't works when connection is good."

This is a significant technical observation: the NFS_CS_NO_RETRANS_TIMEOUT flag suppresses retransmission timeouts at the NFS layer regardless of mount options, as long as the underlying TCP connection remains in the ESTABLISHED state. This means that even with soft semantics requested by the user, the client cannot timeout an OPEN RPC when the network stack reports a healthy connection — rendering the soft option ineffective for this class of server failures.

Zhangjian further argued that indefinite hanging is worse than slot exhaustion:

"Maybe client hanging for so long is more serious than running out of client slot. Even auto-reconnecting is better than this."

Trond Myklebust: No Client-Side Fixes for Broken Servers

Trond Myklebust responded with a terse but definitive conclusion, refusing to entertain client-side workarounds for server misbehavior:

"We do not ever 'fix' broken servers by hacking the client."

He advised:

"I suggest that either you fix your server, or that you replace it with one that isn't broken."

Key Technical Arguments

  1. NFS_CS_NO_RETRANS_TIMEOUT overrides soft mount semantics: Zhangjian's report reveals a gap between user expectation and implementation. The soft mount option is intended to allow timeouts, but the NFS client's internal flag NFS_CS_NO_RETRANS_TIMEOUT prevents timeout-based retransmission when the TCP connection is ESTABLISHED. This means that for certain operations (like OPEN with seqid tracking), the client will hang indefinitely even under soft mounts if the server accepts the connection but never responds.

  2. The seqid hang problem: Operations waiting on a sequence ID (seqid) cannot proceed until the pending RPC completes or times out. With NFS_CS_NO_RETRANS_TIMEOUT active, the SUNRPC layer does not generate -ETIMEOUT, and the NFS layer has no mechanism to abort the wait — causing all subsequent operations on that file to hang.

  3. Slot exhaustion vs. indefinite hang: Trond previously argued that unilateral client timeouts would exhaust server-side slots (per RFC 8881, Section 2.10.6.1), gumming up the system anyway. Zhangjian counters that an indefinite client hang is a more severe failure mode than eventual slot exhaustion, suggesting that auto-reconnection or other recovery mechanisms might be preferable.

  4. Maintainer philosophy: Trond's position remains consistent — the Linux NFS client implements POSIX-compliant hard mount semantics by default, and deviations for broken servers are not acceptable. The onus is on server administrators to ensure server reliability.

Classification

This discussion is about protocol semantics and client behavior, specifically whether the NFS client should provide escape hatches from indefinite hangs when NFS_CS_NO_RETRANS_TIMEOUT is active. No bug fix or new feature was agreed upon; rather, it represents an ongoing philosophical debate about the boundary between client robustness and protocol compliance.

Conclusion

No code changes resulted from this week's exchange. Trond Myklebust maintained his position that the Linux NFS client should not be modified to work around broken servers. Zhangjian's report that soft mount options are ineffective when the TCP connection is established highlights a real usability gap for administrators dealing with unresponsive but network-visible NFS servers, but no resolution was reached. The recommended paths forward remain: fix or replace the problematic server, use umount -f to forcibly kill stuck RPC tasks, or explore whether future kernel versions address this soft mount edge case.
