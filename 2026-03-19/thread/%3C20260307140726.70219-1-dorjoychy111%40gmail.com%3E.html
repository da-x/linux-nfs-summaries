OPENAT2_REGULAR: Flag Leakage and Build Guard Bugs Identified via AI Review

Summary

Thread Subject: Re: [PATCH v5 0/4] OPENAT2_REGULAR flag support for openat2 Date Range: 2026-03-16 (within week ending 2026-03-19) Classification: New Feature / Bug Fix in VFS and Filesystem Clients

Following a week of intense semantic debate over the definition of "regular file" for virtual filesystems like procfs and sysfs last week, this week's activity on the OPENAT2_REGULAR patch series shifted to concrete implementation bugs. NFS maintainer Jeff Layton utilized an AI tool (Claude) to review the V5 patches, uncovering two significant regressions in the core VFS layer that affect all filesystems, including NFS.

Key Technical Arguments and Evolution

The discussion this week was brief but technically dense, centering on two bugs identified in PATCH v5 1/4, which introduces the OPENAT2_REGULAR flag for the openat2() system call. This flag is designed to restrict opens to regular files (S_IFREG), returning -EFTYPE for non-regular files, thereby enhancing security for applications that wish to avoid accidentally opening device nodes or FIFOs.

1. Flag Leakage into f_flags

Jeff Layton reported that the AI review identified a critical bug where the OPENAT2_REGULAR flag leaks into the persistent file flags:

"OPENAT2_REGULAR leaks into f_flags - do_dentry_open() strips open-time-only flags (O_CREAT|O_EXCL|O_NOCTTY|O_TRUNC) but does not strip OPENAT2_REGULAR. When a regular file is successfully opened via openat2() with this flag, the bit persists in file->f_flags and will be returned by fcntl(fd, F_GETFL)."

This is a significant issue because fcntl(fd, F_GETFL) is expected to return only standard POSIX flags. Leaking an internal VFS/open-time-only flag into user-space visible state constitutes a regression in ABI cleanliness.

Dorjoy Chowdhury acknowledged the bug and proposed the fix:

"I guess for issue 1 I need to modify the line in do_dentry_open implementation to f->f_flags &= ~(O_CREAT | O_EXCL | O_NOCTTY | O_TRUNC | OPENAT2_REGULAR); right?"

2. Outdated BUILD_BUG_ON Guard

The second bug relates to a compile-time safety check. The existing BUILD_BUG_ON guard in the VFS code checks that no flags are set in the upper 32 bits of VALID_OPEN_FLAGS. However, the new patch introduces VALID_OPENAT2_FLAGS, which expands the accepted flag set but was not included in the guard:

"BUILD_BUG_ON not updated - The compile-time guard checks upper_32_bits(VALID_OPEN_FLAGS) but the code now accepts VALID_OPENAT2_FLAGS. The guard should cover the expanded flag set."

Dorjoy confirmed the necessary correction:

"And for issue 2, I should change the VALID_OPEN_FLAGS to VALID_OPENAT2_FLAGS in both build_open_flags in fs/open.c and in fcntl_init in fs/fcntl.c, correct?"

NFS Client Impact

While the bugs identified are in the core VFS layer (fs/open.c, fs/fcntl.c), they directly impact the NFS client implementation included in this patch series. The NFS client's atomic_open path was modified to respect the OPENAT2_REGULAR flag.

Notably, the AI review explicitly ruled out a potential false positive regarding NFS error handling:

"NFS -ENOTDIR to -EFTYPE conversion: in atomic_open context, parent path is VFS-resolved, server errors relate to target"

This indicates that the existing NFS logic for converting -ENOTDIR errors from the server to -EFTYPE when the OPENAT2_REGULAR flag is used is correct, as the parent path resolution is handled by the VFS before the NFS-specific open occurs. The review also confirmed that:

"All filesystem cleanup paths (ceph, gfs2, nfs, cifs) properly handle resources when returning -EFTYPE"

This provides assurance that the NFS client does not leak dentries or other resources when rejecting non-regular file opens via this new flag.

Final Conclusions

The discussion concluded with Dorjoy Chowdhury agreeing to fix both identified issues in a subsequent patch version (V6). The use of AI-assisted code review by Jeff Layton highlighted two subtle but important bugs:

  1. ABI Pollution: OPENAT2_REGULAR leaking into user-visible f_flags.
  2. Compile-Time Safety: An outdated BUILD_BUG_ON guard that fails to cover the new flag set.

These fixes are critical for ensuring that the new security feature does not introduce regressions in the VFS layer or expose internal kernel flags to user-space applications. The NFS client implementation itself was found to be robust, with proper resource cleanup and correct error conversion logic.
