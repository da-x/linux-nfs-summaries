NFS Client Regression: Large rsize/wsize (1MB) Causes EIO with Dell EMC OneFS Servers

Summary

NFS Client Regression: Large rsize/wsize (1MB) Causes EIO with Dell EMC OneFS Servers

Classification

Bug fix / regression analysis. This thread addresses a client-side regression introduced by commit 2b092175f5e3 ("NFS: Fix inheritance of the block sizes when automounting"), which exposed an interoperability issue between the Linux NFS client and Dell EMC Isilion/OneFS servers when using large read/write sizes (1 MB).

Summary

Salvatore Bonaccorso opened the discussion on behalf of Debian, reporting that users experienced I/O errors (EIO) on NFS client writes after upgrading to kernels containing commit 2b092175f5e3 and its stable backports. The regression manifested specifically when the NFS server was a Dell EMC Isilion (OneFS) system with large rsize/wsize values (1 MB).

The root cause, as identified by affected user Valentin SAMIR in correspondence with Dell support, is a semantic mismatch between how the Linux client and Dell's OneFS interpret NFSv4 size limits:

"The kernel treats the max size as the nfs payload max size whereas OneFs treat the max size as the overall compound packet max size (everything related to NFS in the call). Hence when OneFS receives a call with a payload of 1M, the overall NFS packet is slightly bigger and it returns an NFS4ERR_REQ_TOO_BIG."

In other words, the Linux client uses the maxread/maxwrite attributes returned by the server to determine how large a READ/WRITE payload to send, but does not cross-check this against the server's max_request_size. When the compound request (SEQUENCE + PUTFH + WRITE + GETATTR) exceeds max_request_size, OneFS rejects it with NFS4ERR_REQ_TOO_BIG, which manifests as EIO on the client.

Evolution of the Discussion

Trond Myklebust's Initial Position

Linux NFS client maintainer Trond Myklebust responded by explaining the current client behavior:

"The Linux NFS client uses the 'maxread' and 'maxwrite' attributes (see RFC8881 Sections 5.8.2.20. and 5.8.2.21.) to decide how big a payload to request/send to the server in a READ/WRITE COMPOUND."

He noted that the client assumes no conflict between maxread/maxwrite and max_request_size because both values originate from the server:

"It won't cross check with the max request size, because it assumes that since both values derive from the server, there will be no conflict between them."

Aurélien Couderc's Suggestion

Aurélien Couderc questioned whether the client should enforce bounds:

"So maxread and/or maxwrite MUST NOT be larger than the clients maximum RPC size?"

He proposed adding defensive logging:

"Maybe add an assert()-like warning to syslog if there is a mismatch?"

Jeff Layton's Counter-Argument

Jeff Layton pushed back against Trond's interpretation, arguing that the client is responsible for respecting max_request_size:

"Servers use the max_request_size to properly size their receive buffers, and the client is responsible for adhering to that value. I don't think you can stick a bunch of operations in a request compound and then put a huge WRITE at the end that blows out max_request_size, and expect the server to be OK with that."

Layton suggested a practical mitigation:

"ISTM the client should clamp the length down to something shorter that allows the request to fit. Maybe drop the last folio and force another request? Performance would suck but it would work."

However, he also acknowledged that the server-side behavior was flawed:

"All that said, the server in this case isn't sizing max_request_size with enough overhead for the client to actually achieve a full 1M write, which is just dumb. Dell should fix that."

Trond Myklebust's Final Position

Trond reiterated his stance, clarifying that the compound request structure is minimal (SEQUENCE, PUTFH, WRITE, GETATTR) and emphasizing server-side responsibility:

"We're not putting 'a bunch of operations' before the WRITE. There's a SEQUENCE, PUTFH, WRITE and GETATTR."

"The point is, we expect the value of maxwrite to be set to a reasonable value w.r.t. max_request_size so that the client doesn't have to sanity check everybody and their dog's server."

Key Technical Arguments

  1. Client-side assumption: The Linux NFS client trusts that maxread/maxwrite values returned by the server are already consistent with max_request_size. It does not perform a cross-check or clamp operations.

  2. Server-side obligation: Per NFSv4 semantics, servers should set max_request_size large enough to accommodate the compound overhead plus the maximum payload indicated by maxread/maxwrite. Dell's OneFS appears to treat these values as total packet size rather than payload-only, creating a conflict.

  3. Proposed client hardening: Layton and Couderc suggested the client could defensively clamp write sizes or emit warnings when a mismatch is detected, improving robustness against non-conformant servers.

  4. Maintainer position: Trond Myklebust maintains that adding client-side sanity checks for every server's configuration would be an undue burden, arguing instead that the server should provide consistent values.

Final Conclusions

The thread did not conclude with a definitive patch or resolution this week. The key takeaways are:

  • The regression is real: Commit 2b092175f5e3 exposed a pre-existing interoperability gap between the Linux NFS client and Dell EMC OneFS servers when using large I/O sizes.
  • Dual responsibility: Both sides have valid arguments — the server should advertise consistent size limits, but the client could be more defensive in clamping or warning about mismatches.
  • No immediate fix landed: The discussion remains open, with Trond Myklebust leaning toward a server-side fix from Dell, while Jeff Layton and others advocate for additional client-side robustness.

This issue is being tracked via Debian bug #1128834 and the Linux kernel regressions tracker.
