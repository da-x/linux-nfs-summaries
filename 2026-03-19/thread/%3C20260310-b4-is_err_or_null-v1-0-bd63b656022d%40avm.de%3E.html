IS_ERR_OR_NULL Refactor: Mixed Reactions, No NFS Impact This Week

Overview

This week's activity in the thread rooted at [PATCH 00/61] treewide: Use IS_ERR_OR_NULL over manual NULL check - refactor Philipp Hahn consisted of four replies from subsystem maintainers responding to individual patches in the series. No NFS-specific patches were reviewed this week; the sole NFS-relevant patch ([PATCH 30/61] net/sunrpc) was addressed last week and received Reviewed-by tags from Jeff Layton and Chuck Lever prior summary.

Classification: Code cleanup / refactoring. This is not a protocol change, new feature, or bug fix. The series mechanically replaces IS_ERR() + manual NULL checks with the IS_ERR_OR_NULL() macro across 61 subsystems using Coccinelle-generated patches.

Bridge from Prior Week

Last week, the full 61-patch series was submitted and reviewed. The NFS/sunrpc patch ([PATCH 30/61]) modifying net/sunrpc/xprtrdma/svc_rdma_transport.c was accepted with positive reviews. Broader discussion emerged around the philosophy of mechanical refactoring, with some maintainers welcoming consistency improvements while others cautioned against blind macro substitution.

This Week's Activity: Four Maintainer Responses

1. David Sterba (btrfs): Acceptance for Consistency

David Sterba reviewed [PATCH 02/61] btrfs and accepted it into his for-next branch:

"Added to for-next, we seem to be using IS_ERR_OR_NULL() already in a few other places so this is makes sense for consistency. Thanks." David Sterba

Sterba's response reflects the pragmatic view that where IS_ERR_OR_NULL() is already in use within a subsystem, extending its usage promotes internal consistency.

2. Robin Murphy (IOMMU): Strong Criticism of Mechanical Cleanup

Robin Murphy delivered the most pointed critique of the series in his review of [PATCH 50/61] iommu. He argued that the specific call sites in question did not actually need either check:

"AFAICS it doesn't look possible for the argument to be anything other than valid at both callsites, so both conditions here seem in fact to be entirely redundant." Robin Murphy

Murphy went further to question the broader approach, urging more thoughtful cleanup:

"Please use coccinelle responsibly. Mechanical changes are great for scripted API updates, but for cleanup, whilst it's ideal for finding areas of code that are worth looking at, the code then wants actually looking at, in its whole context, because meaningful cleanup often goes deeper than trivial replacement." Robin Murphy

He added a design-level observation:

"In particular, anywhere IS_ERR_OR_NULL() is genuinely relevant is usually a sign of bad interface design, so if you're looking at this then you really should be looking first and foremost to remove any checks that are already unnecessary, and for the remainder, to see if the thing being checked can be improved to not mix the two different styles." Robin Murphy

Murphy concluded that simply replacing code with IS_ERR_OR_NULL() — which he described as "this ugly macro that's arguably less readable than what it replaces" — was not constructive cleanup.

3. Alex Williamson (VFIO): Rejection on Clarity Grounds

Alex Williamson reviewed [PATCH 46/61] vfio and declined the change, echoing concerns about code clarity:

"As others have expressed in general, this doesn't seem to be cleaner and tends to mask that we consider IS_ERR() and NULL as separate cases in the goto. This code looks like it could use some refactoring, and likely that refactoring should handle the IS_ERR() and NULL cases separately, but conflating them here is not an improvement." Alex Williamson

Williamson's argument highlights a semantic concern: IS_ERR() and NULL often represent distinct failure modes that deserve separate handling paths. Conflating them via IS_ERR_OR_NULL() can obscure the intent of error handling logic.

4. Jan Kara (Quota): Preference for Original Style

Jan Kara reviewed [PATCH 12/61] quota and politely declined:

"Thanks for the patch but frankly I find the original variant clearer wrt what is going on. So I prefer to keep the code as is." Jan Kara

Kara's response reinforces the theme that explicit IS_ERR() plus NULL checks can be more readable than the combined macro, particularly in contexts where the two conditions have different semantic meanings.

Key Technical Arguments

The discussion this week crystallized around three competing perspectives on the IS_ERR_OR_NULL() refactoring:

  1. Consistency argument (Sterba): Where a subsystem already uses IS_ERR_OR_NULL(), extending its use reduces stylistic variance and is worth accepting.

  2. Design-quality argument (Murphy): The presence of IS_ERR_OR_NULL() often signals poor interface design that returns both error pointers and NULL. Better cleanup would fix the interface rather than paper over it with a macro. Additionally, some checks may be entirely redundant and should simply be removed.

  3. Clarity argument (Williamson, Kara): Explicitly separating IS_ERR() and NULL checks makes the code's intent clearer, as these often represent different failure modes requiring different handling. The macro conflates them and can reduce readability.

Evolution of the Discussion

The thread has evolved from initial broad acceptance (last week) to more nuanced pushback this week. While some maintainers like Sterba see value in consistency, others are pushing back against the mechanical nature of the changes. Murphy's critique is particularly significant because it challenges not just individual patches but the methodology: using Coccinelle to find cleanup opportunities is valuable, but blindly applying replacements without contextual review may produce inferior code.

Final Conclusions

  • NFS impact: None this week. The NFS/sunrpc patch was already accepted last week with dual Reviewed-by tags from Layton and Lever.
  • Series status: Mixed outcomes. Some patches are being accepted (btrfs), while others face rejection or requests for deeper refactoring (iommu, vfio, quota).
  • Key takeaway: The community is divided on whether IS_ERR_OR_NULL() represents an improvement over explicit checks. The consensus among critics is that mechanical replacement without contextual analysis can degrade code quality rather than improve it.
  • No bug fixes or protocol changes: This remains a pure code-style refactoring effort with no functional impact on NFS client development.
