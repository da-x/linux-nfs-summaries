NFSD Lock Regression: Jeff Layton Endorses NeilBrown's F_GETLK Fix Direction

Summary

NFSD Lock Regression: Jeff Layton Endorses NeilBrown's F_GETLK Fix Direction

Classification: Bug Fix (NFS Server / lockd Permission Checks)

Bridge from Prior Weeks

This thread, first reported by Tj on February 24, tracks a regression introduced by commit 4cc9b9f2bf4d ("nfsd: refine and rename NFSD_MAY_LOCK"), which caused NFS clients to receive -ENOLCK ("No locks available") when attempting file locking operations on read-only files (e.g., ISO images served via NFSv3). The issue was discovered in production on the Debian openQA infrastructure, where QEMU failed to acquire "consistent read" locks on NFS-mounted disk images.

In prior weeks, Neil Brown argued that the new behavior was technically correct — exclusive fcntl-style locks over NLM require write access by POSIX semantics — and resisted simply restoring the old permission downgrade. The discussion appeared stalled until last week's pivotal moment when Neil Brown corrected his own diagnosis, revealing that QEMU was not using flock() at all, but rather fcntl() with the F_GETLK operation — a lock query that POSIX does not require write access for. He proposed a targeted patch to the lockd subsystem to fix this narrower bug.

This Week's Activity: Consensus on the Fix Direction

This week saw a single but significant message from Jeff Layton, who endorsed Neil Brown's revised analysis and proposed fix:

"Oh! That makes much more sense."

Layton confirmed that the local filesystem already permits F_GETLK requests without write access, validating Neil Brown's argument:

"We definitely allow F_GETLK requests on local files when the task doesn't have write access to the file, so I don't see any issue with allowing it here. Your fix seems sensible to me."

This represents a notable shift from Layton's position last week, where he had NAKed Sasha Levin's broader patch and questioned whether the old behavior was ever correct. Neil Brown's reframing of the issue — from a broad debate about exclusive locks on read-only files to a specific bug in F_GETLK permission handling — successfully resolved Layton's concerns.

Layton also contributed additional historical context, suggesting the bug may have deeper roots than initially thought:

"Looking back, it looks like this may have been broken back in 2021 in: 7f024fcd5c97 ('Keep read and write fds with each nlm_file')?"

This observation points to commit 7f024fcd5c97 as a potential earlier source of the problem, suggesting the issue may have been latent for years before surfacing through the 2026 refactoring.

Key Technical Arguments and Evolution

  1. Initial framing (Feb–early Mar): The regression was understood as a question of whether exclusive locks on read-only files should be permitted over NLM. Neil Brown argued "no" based on POSIX fcntl semantics; Sasha Levin proposed restoring the old permission downgrade in nfsd_permission().

  2. Stalemate (mid-Mar): Jeff Layton agreed with Neil Brown that blindly restoring the old behavior would break legitimate lock-denial cases, but acknowledged the regression needed addressing. The thread appeared stalled.

  3. The pivot (March 12): Neil Brown's self-correction revealed the true root cause — NFSD was requiring write access for F_GETLK (a lock query), not just for F_SETLK (lock acquisition). This is a narrower and more clearly correctable bug.

  4. Consensus achieved (March 13): Jeff Layton endorsed Neil Brown's fix direction, confirming that local filesystem behavior already supports F_GETLK without write access. The debate over broad semantic correctness was resolved by focusing on the specific POSIX-compliant behavior for lock queries.

Final Conclusions

  • Bug confirmed and reclassified: The regression is not about whether exclusive locks should require write access (they do for acquisition via F_SETLK/F_SETLKW), but rather that NFSD incorrectly enforces write permission for F_GETLK queries, which POSIX does not require.
  • Fix direction agreed upon: Neil Brown's targeted patch to the lockd subsystem — distinguishing between lock acquisition and lock testing — has received positive feedback from Jeff Layton. The thread continued beyond this week with formal patch submissions ([PATCH] lockd: fix TEST handling when not all permissions are available) on March 24, followed by review from Chuck Lever and Ben Hutchings.
  • Historical context: Jeff Layton's observation that the issue may trace back to commit 7f024fcd5c97 from 2021 suggests this bug may have been latent for years, only surfacing when the 2026 refactoring exposed it.
  • Workaround available: Users experiencing this issue can use the no_auth_nlm export option on the NFS server as an interim measure, as suggested by Jeff Layton in prior weeks.
