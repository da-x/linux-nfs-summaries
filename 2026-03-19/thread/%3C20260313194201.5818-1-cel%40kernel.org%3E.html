RDMA/rw: Fix MR pool exhaustion and optimize svcrdma buffer allocation

Summary

This week, Chuck Lever submitted version 3 of a four-patch series addressing critical stability issues in the RDMA subsystem that directly impact NFS over RDMA (svcrdma) performance. The primary focus is resolving Memory Region (MR) pool exhaustion, which causes connection resets under heavy load, alongside an optimization to reduce DMA mapping overhead.

Root Cause and Technical Arguments

The discussion centers on a regression where write-intensive NFS workloads trigger rapid MR pool exhaustion. As Chuck Lever explained in the cover letter PATCH v3 0/4:

"Under write-intensive workloads that issue many concurrent RDMA READs, the pool is rapidly exhausted... Upper layer protocols treat this as a fatal DMA mapping failure and tear down the connection."

The exhaustion occurs because, in IOMMU passthrough mode, large transfers generate many Scatter-Gather Entries (SGEs). When the SGE count exceeds the device's max_sgl_rd threshold, the RDMA core attempts to register Memory Regions. However, the MR pool is sized roughly at one MR per concurrent context (max_rdma_ctxs). When the pool is empty, ib_mr_pool_get() returns NULL, leading to -EAGAIN errors that svcrdma interprets as fatal, causing connection teardown and high retransmission rates.

Evolution of the Discussion

1. Fixing MR Exhaustion (Patches 1 & 2) Chuck Lever proposed two fixes for the immediate stability issue:

  • Patch 1: Introduces a fallback mechanism. If MR allocation fails with -EAGAIN, the code now falls back to direct SGE posting ("map_wrs") instead of failing the operation entirely. This preserves connectivity while sacrificing some performance optimization PATCH v3 1/4.
  • Patch 2: Addresses a bug in the bvec (bio vector) path where the raw page count was used to determine MR needs, overstating the required DMA entries and forcing unnecessary MR consumption for every multi-bvec RDMA READ PATCH v3 2/4.

Leon Romanovsky quickly accepted these critical fixes:

"I applied these two to wip/leon-for-rc." Re: PATCH v3 0/4

2. Optimization and Refactoring (Patches 3 & 4) The remaining patches address code quality and performance optimization for the next merge window:

  • Patch 3: Adds a svc_rqst_page_release() helper to encapsulate folio batch release logic, cleaning up call sites in SUNRPC PATCH v3 3/4.
  • Patch 4: Proposes using contiguous higher-order page allocations for RDMA Read sink buffers. This reduces the number of bvecs, DMA mappings, and Work Requests (WRs) per operation PATCH v3 4/4.

Review and Conclusions

Christoph Hellwig provided reviews for all four patches. He granted "Reviewed-by" to the first three patches without comment. For Patch 4, he raised a technical question regarding the maximum allocation order:

"Isn't the limit really an order and thus grows with the page size, instead of based on a fixed size?" Re: PATCH v3 4/4

Chuck Lever responded by clarifying that even on platforms with larger page sizes (e.g., 16KB), a higher-order allocation (e.g., order-4 for 256KB) remains desirable for the optimization's purpose Re: PATCH v3 4/4.

Final Status:

  • Patches 1 & 2: Accepted into the RDMA tree for the current release candidate cycle (-rc) as urgent bug fixes.
  • Patches 3 & 4: Pending integration into nfsd-testing for the next merge window, pending any minor adjustments from the review feedback.

This series represents a significant improvement in NFS over RDMA stability under heavy write loads, preventing spurious connection drops while laying groundwork for more efficient buffer management.
