NFS: Fix drop_nlink during REMOVE with delegations

Summary

NFS Client Bug Fix: Forcing drop_nlink During REMOVE with Delegations

This week saw a targeted bug-fix patch for the NFS client addressing an issue with link-count handling during file removal when delegations are involved. The discussion is centered on a regression introduced by a previous commit aimed at preventing races between attribute updates and file removals.

Background and Problem Statement

The patch, submitted by Roberto Bergantinos Corpas here, addresses a flaw in commit bd4928ec799b ("NFS: Avoid changing nlink when file removes and attribute updates race"). That earlier commit was designed to prevent race conditions on the attribute cache with any inflight RPC that might modify inode attributes (and the generation count, or gencount) during a REMOVE operation.

However, as Bergantinos Corpas explains in the patch description:

"However it does not take into account that REMOVE may trigger a delegation return which also advances gencount (via the attribute refresh during delegation return), and in that case the gencount mismatch is not due to an inflight RPC that already reflected the removal."

The core issue is that when a file with nlink of 1 and an active delegation is removed, the REMOVE operation triggers a delegation return. This return process advances the gencount through an attribute refresh. The previous logic incorrectly interpreted this gencount mismatch as evidence that an inflight RPC had already reflected the removal, thereby skipping the necessary link-count drop.

Technical Argument and Fix

The fix ensures that when nlink is 1 and a delegation exists before the REMOVE operation, the client forces the link count to drop. This is critical for correct VFS behavior:

"If nlink is 1 and we have a delegation before REMOVE, we should force the drop to ensure the VFS delivers the expected FS_DELETE_SELF notification."

The patch modifies fs/nfs/dir.c to handle this edge case, ensuring that the VFS receives the proper FS_DELETE_SELF notification, which is essential for filesystem event monitoring tools like inotify.

Impact and Validation

The regression manifested as a failure in the Linux Test Project (LTP) suite. Specifically:

"This fixes LTP/inotify04 failure after bd4928ec799b."

The patch carries a Reviewed-by tag from Olga Kornievskaia, indicating peer validation of the fix within the Red Hat NFS development team.

Conclusion

This is a focused bug fix for the NFS client, correcting an interaction between delegation returns and link-count management during file removal. The fix restores correct inotify behavior (specifically FS_DELETE_SELF notifications) that was broken by a previous race-condition mitigation. With only one message in the thread this week, no further discussion or debate occurred; the patch stands as a straightforward correction with peer review already secured.
