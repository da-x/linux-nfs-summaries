Summary

VFS Directory Locking RFC: Week 2 — Filesystem Adaptations and Reviewer Feedback

Overview

This week marked the second phase of Neil Brown's [PATCH RFC 00/53] series](https://lore.kernel.org/linux-nfs/20260312214330.3885211-1-neilb@ownmail.net/) titled "lift lookup out of exclive lock for dir ops." Last week, the series was introduced along with initial reactions from Linus Torvalds and Steven Rostedt prior summary. This week, the focus shifted to filesystem-specific adaptations (patches 19–38) and substantive technical reviews from overlayfs maintainer Amir Goldstein and ext4 maintainer Jan Kara.

Classification: VFS locking refactoring with broad implications for NFS client development. The series is an architectural change enabling concurrent directory updates by removing the dependency on exclusive parent-directory locks during lookup operations.

Bridge from Prior Week

Last week, Neil Brown submitted all 53 patches of the RFC series. Linus Torvalds responded positively but conditionally:

"I only got about half the patches, but the ones I did get didn't raise my hackles." Linus Torvalds

However, he emphasized that the series "absolutely requires ACKs from Al" and requested a git branch for easier review. Neil Brown responded this week by providing the GitHub branch link: github.com/neilbrown/linux.git branch pdirops, and noted that if reviewers have time for only one patch, "52/53 is the one to look at" Neil Brown.

"They don't seem to have made it to lore.kernel.org either. Maybe I'm being rate-limited somewhere." Neil Brown

Filesystem-Specific Adaptations (Patches 19–38)

This week's message bodies include the remaining filesystem adaptation patches. These patches modify numerous filesystems to comply with the new locking model. Key themes include:

AFS Client Changes (Patches 19–24)

The AFS client received significant updates, mirroring patterns already applied to NFS in last week's patches:

  • PATCH 19/53: Switched AFS from using ->d_fsdata to ->d_time for storing parent directory version information, freeing ->d_fsdata for other uses.
  • PATCH 20/53: Eliminated the AFS pattern of unhashing/rehashing dentries during unlink/rename, replacing it with an NFS-style mechanism using ->d_fsdata to block lookups.
  • PATCH 21/53: Adopted d_splice_alias() in afs_vnode_new_inode() to handle potential double-dentry scenarios from open_by_handle_at().
  • PATCH 22/53: Replaced normal lookups in silly-rename with d_alloc_noblock() and open-coded lookup_slow().
  • PATCH 23/53: Dropped and reclaimed the directory lock around d_alloc_parallel() in lookup_atsys to prevent future lock-order inversions.
  • PATCH 24/53: Adopted the new d_duplicate() API for whiteout creation.

SMB/CIFS Client Changes (Patches 25–28)

The SMB client received parallel updates:

  • PATCH 25/53: Reverted a prior commit that moved timestamp storage from ->d_time to ->d_fsdata, freeing ->d_fsdata for generic use.
  • PATCH 26/53: Replaced the unhash/rehash pattern for blocking new opens during unlink/rename with an NFS/AFS-style mechanism using ->d_fsdata and ->d_revalidate.
  • PATCH 27/53: Adopted d_splice_alias() in atomic_open to keep dentries hashed throughout operations.
  • PATCH 28/53: Switched from d_alloc_parallel() to d_alloc_noblock() in cifs_prime_dcache(), noting that "Blocking in that case is pointless as the lookup will add info to the dcache."

Other Filesystem Changes (Patches 29–38)

  • exfat (PATCH 29/53): Simplified exfat_lookup() by removing a no-op function and using d_move() for alias handling.
  • configfs (PATCH 30/53, PATCH 31/53): Removed unnecessary d_add() calls and switched to d_splice_alias().
  • ext4 (PATCH 32/53, PATCH 33/53): Moved dcache-modifying code out of __ext4_link() and adopted on-stack dentries for fast-commit replay.
  • tracefs (PATCH 34/53): Switched from d_add() to d_splice_alias().
  • cephfs (PATCH 35/53, PATCH 36/53, PATCH 37/53): Removed d_add() usage, eliminated wasteful d_alloc() in LOOKUPNAME handling, and switched to d_alloc_noblock() in readdir prepopulation.

Reviewer Feedback: Amir Goldstein on Overlayfs

Amir Goldstein provided critical feedback on PATCH 16/53 (ovl: drop dir lock for lookups in impure readdir), which was submitted last week but reviewed this week. He identified a significant flaw:

"You missed the fact that overlayfs uses the dir inode lock to protect the readdir inode cache, so your patch introduces a risk for storing a stale readdir cache when dir modify operations invalidate the readdir cache version while lock is dropped and also introduces memory leak when cache is stomped without freeing cache created by a competing thread." Amir Goldstein

Goldstein noted that ovl_cache_update() is also called from ovl_iterate_merged() where the inode is locked, and provided an untested fixup patch. He added a caveat: "I did not look into ovl_iterate_merged() to see if it has a simple fix and I am not 100% sure that this fix for impure dir is enough."

Reviewer Feedback: Jan Kara on ext4

Jan Kara reviewed the two ext4 patches (PATCH 32/53 and PATCH 33/53) and provided mixed feedback:

For PATCH 33/53 (use on-stack dentries), he was positive:

"Looks good to me. Feel free to add: Reviewed-by: Jan Kara jack@suse.cz" Jan Kara

However, for PATCH 32/53 (move dcache modifying code out of __ext4_link()), he raised several concerns:

  1. Constification scope: "The constification of take_dentry_name_snapshot() should probably be a separate patch?"
  2. Fast-commit tracking logic: He identified what he described as an incorrect change to __ext4_fc_track_link(): "This looks wrong. If fastcommit replay is running, we must skip calling __ext4_fc_track_link(). Similarly if the filesystem is currently ineligible for fastcommit (due to some complex unsupported operations running in parallel). Why did you change ext4_fc_track_link() to __ext4_fc_track_link()?"
  3. Code consistency: He suggested using inc_nlink() instead of ext4_inc_count() for consistency with ext4_fc_replay_link_internal().

Key Technical Arguments and Evolution

  1. Cross-filesystem pattern propagation: The NFS-specific patterns introduced last week (using d_splice_alias(), d_alloc_noblock(), d_duplicate(), and the ->d_fsdata blocking mechanism) are now being propagated to AFS, SMB/CIFS, cephfs, ext4, and other filesystems. This demonstrates the breadth of the VFS-level change.

  2. Overlayfs complexity: Amir Goldstein's review highlights that some filesystems use the directory inode lock for purposes beyond just dcache consistency — in overlayfs's case, protecting the readdir cache version. Simply dropping the lock introduces subtle race conditions and memory leaks. This suggests the series may require filesystem-specific adaptations beyond the mechanical API changes.

  3. ext4 fast-commit intricacies: Jan Kara's feedback reveals that ext4's fast-commit replay path has specific requirements around tracking links that the patch inadvertently disrupted. The change from ext4_fc_track_link() to __ext4_fc_track_link() bypasses eligibility checks, potentially causing incorrect behavior during crash recovery.

Final Conclusions

  • Series status: RFC stage. Linus Torvalds' requirement for Al Viro's ACK remains unfulfilled. A git branch has been provided at github.com/neilbrown/linux.git branch pdirops.
  • NFS client impact: The NFS-specific patches (09–15) from last week remain unchanged this week, but the parallel adaptations to AFS and SMB/CIFS demonstrate that the patterns established for NFS are being generalized across network filesystems.
  • Reviewer concerns: Two significant issues have been identified:
    • Overlayfs's use of the directory lock for readdir cache protection requires additional fixes beyond the current patch Amir Goldstein.
    • ext4's fast-commit tracking logic may be broken by the refactoring of __ext4_link() Jan Kara.
  • Next steps: Neil Brown will need to address Amir Goldstein's overlayfs concerns and Jan Kara's ext4 fast-commit issues before the series can progress. Al Viro's review remains the critical path for acceptance.
