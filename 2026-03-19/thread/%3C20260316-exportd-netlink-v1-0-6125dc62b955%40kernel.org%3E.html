Netlink upcalls for mountd/exportd caches

Summary

Netlink-Based Upcalls for NFS Daemon Caches

This week, Jeff Layton introduced a 14-patch series replacing the antiquated /proc-based interfaces used by mountd and exportd for sunrpc cache upcalls with a new generic netlink interface. The series affects both the sunrpc module (for auth.unix.ip and auth.unix.gid caches) and nfsd (for svc_export and nfsd.fh caches).

Technical Overview

The core design adds a cache_notify callback to struct cache_detail. When a cache miss occurs, the kernel sends a netlink multicast notification to userspace. Userspace then fetches the outstanding cache_request entries via a dumpit handler and responds with the resolved data over netlink. The series also introduces SUNRPC_CMD_CACHE_FLUSH and NFSD_CMD_CACHE_FLUSH commands to allow userspace to flush caches without writing to /proc.

Review Discussion

Chuck Lever provided detailed review comments on March 19, focusing on concurrency semantics and code organization.

TOCTOU Race in Cache Snapshotting

Chuck identified a potential Time-Of-Check-Time-Of-Use (TOCTOU) issue in the helper functions added to count and snapshot pending requests:

"This API architecture introduces a TOCTOU, since as soon as the queue_lock is dropped, the count can immediately become stale." Chuck Lever

He noted that the dumpit handlers perform a one-shot snapshot: they count requests, allocate buffers, and then snapshot. If new requests are added between these steps, they are silently truncated. Since the handlers signal completion after a single pass, these entries would be lost.

Jeff Layton clarified that this is not a data loss issue in practice because userspace receives an independent netlink notification for each queued request:

"Userland will receive a separate notify request whenever a cache_request is queued... select() will return the notify descriptor again on the next pass and mountd will pick up the remaining entries at that point." Jeff Layton

Chuck accepted this explanation but recommended documenting the expected retry behavior in the code:

"Makes sense. But perhaps should be documented somewhere; the 'retry' loop is not obvious from the source code introduced here." Chuck Lever

Spurious Notifications

On Patch 05, Chuck pointed out that cache_notify is called even when the upcall fails with -EAGAIN, indicating another thread already cleared the CACHE_PENDING bit. This results in a notification for an entry that is no longer pending:

"Calling cache_notify in this case sends a netlink notification for an entry that is no longer pending... a possible fix might be: if (ret != -EAGAIN && detail->cache_notify)" Chuck Lever

Code Organization and Unrelated Hunks

Chuck raised minor concerns about premature includes in Patch 05 and the placement of sunrpc_cache_notify() in Patch 07. More significantly, he noticed an unrelated hunk in fs/nfsd/netlink.c within Patch 07:

"This hunk is clearly not related to adding 'a generic netlink family for cache upcalls'. Should I apply it instead to the appropriate FH-signing patch?" Chuck Lever

Jeff attributed the change to an update in the ynl code generation tool, but Chuck confirmed the tool had not changed. He traced the anomaly to a previous patch ("NFSD: Add a key for signing filehandles") and applied the fix separately to his nfsd-testing branch:

"I think 'NFSD: Add a key for signing filehandles' introduced this anomaly, so I've gone back to that patch and re-ran the tool... I applied it and pushed it to nfsd-testing." Chuck Lever

Conclusion

The series represents a significant modernization of the NFS server's user-space communication interfaces, removing dependencies on /proc and enabling easier extension for new export options. The review highlighted important concurrency considerations in the snapshotting mechanism, which were resolved through an explanation of the userspace retry protocol. Minor code organization issues and an unrelated hunk were addressed separately by the maintainer.
