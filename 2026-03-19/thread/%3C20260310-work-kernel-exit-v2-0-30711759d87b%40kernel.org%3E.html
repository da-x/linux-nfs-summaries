kthread Exit Cleanup: Rostedt Clarifies module_put Behavior in Non-Module Kernels

Summary

kthread Exit Cleanup: Resolving the module_put Mystery

Bridge from Prior Week

Last week, Christian Brauner submitted [PATCH v2 0/2] kthread, exit: clean up kernel thread exit paths Cover, a two-patch series removing the redundant kthread_exit() alias and renaming do_exit() to task_exit(). The series received positive reviews from Frederic Weisbecker, though Steven Rostedt raised a selftest compatibility concern regarding backward-compatible function name detection.

A key question emerged from David Laight, who asked how the macro module_put_and_kthread_exit() — now calling do_exit() directly — actually performs the module_put():

"I'm intrigued... How does that actually know to do the module_put()? (I know it does one - otherwise my driver wouldn't unload.)" Laight

This week's sole message resolves that question.

This Week's Activity

Rostedt Clarifies the module_put Mechanism

In his reply Rostedt, Steven Rostedt provided a concise explanation for Laight's question about how module_put_and_kthread_exit(code) performs the module reference count decrement when it simply calls do_exit(code):

"It's in the !CONFIG_MODULES section. No module_put() necessary. Only the kthread_exit (do_exit) is needed."

This clarification reveals that the macro's behavior differs depending on kernel configuration:

  • With CONFIG_MODULES enabled: The macro performs both module_put(THIS_MODULE) and do_exit(code), ensuring the module reference acquired by try_module_get() at thread creation time is properly released.
  • Without CONFIG_MODULES (!CONFIG_MODULES): No module reference counting exists, so only do_exit(code) (formerly kthread_exit()) is needed — no module_put() call is necessary or present.

This conditional compilation approach explains why Laight's driver unloads correctly in both configurations, resolving the apparent mystery of how the macro "knows" to perform module_put().

Classification and NFS Relevance

Classification: Bug fix follow-up / API cleanup — not a new feature or protocol change. This thread concludes the discussion around Brauner's v2 series that removes the kthread_exit() alias (leftover from a use-after-free fix in commit 28aaa9c39945) and renames do_exit() to task_exit().

NFS Client/Server Impact: The changes affect include/linux/sunrpc/svc.h, part of the RPC server infrastructure used by NFSv3 and NFSv4 servers. The module_put_and_kthread_exit() macro ensures RPC service threads properly release module references before exiting, preventing module unloading issues. While this week's message does not introduce new NFS-specific changes, it clarifies a design detail that impacts any loadable kernel module spawning kernel threads — including NFS server modules.

Final Conclusions

  • Laight's question resolved: Rostedt's explanation confirms the macro's behavior is configuration-dependent, with no module_put() needed when modules are disabled at compile time.
  • Series status: The v2 series remains under review. Rostedt's earlier selftest compatibility concern (requiring fallback logic for do_exit/task_exit detection in ftrace-based tests) still needs to be addressed before merge.
  • No new patches this week: This week's activity was limited to a clarifying reply, with no new patch submissions or substantive technical debates.
