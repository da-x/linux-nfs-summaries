sunrpc: Finalizing nfs_errorf() macro refactor for v3

Overview

This week, the discussion surrounding Sean Chang's [PATCH v2] to simplify SunRPC debug macros reached a concrete resolution regarding the nfs_errorf() macro definition. The thread focused on eliminating Sparse type-mismatch warnings while maintaining clean, idiomatic C code in the NFS client/server infrastructure.

Building on last week's agreement that Chuck Lever would merge the patches through his tree once review was complete, this week's exchange finalized the specific syntax for the nfs_errorf() macro, paving the way for a v3 submission.

Context from Prior Weeks

In the previous summary period ending 2026-03-12, Andy Shevchenko raised a Sparse warning regarding void vs int type mismatches in debug macros as noted in the prior summary. Sean Chang confirmed the issue and proposed using do-while(0) constructs to ensure macros always evaluate to void. Additionally, Andy Shevchenko suggested dropping redundant statement expression wrappers (({})) in nfs_error*() macros Andy's suggestion. Chuck Lever offered to take all three planned patches through his tree once the review was settled.

Key Technical Arguments This Week

Resolving the ({}) Wrapper Debate

Sean Chang responded to Andy's suggestion about removing ({}) wrappers, explaining the technical constraints:

"I understand that the ({}) wrapper might look redundant at first glance. However, even if I remove it, the return type remains an issue because no_printk() (which dprintk() expands to) already contains its own ({}) statement expression." — Sean Chang

Sean noted that refactoring errorf(), which "hasn't been touched in years," was undesirable, and proposed modifying dfprintk() instead. He acknowledged an alternative approach of forcing the return type to void:

"One alternative is to explicitly force the return type to void like this: ({ dprintk(fmt "\n", ##__VA_ARGS__); (void)0; })... it is admittedly clunky." — Sean Chang

Andy's Position on Legacy Code

Andy Shevchenko pushed back gently on the argument that legacy code should remain untouched:

"Personally I found the ({}) in nfs_error*() redundant and the point of those functions not being touched in years doesn't work for internal APIs. Do you know the reason why it wasn't touched? Perhaps there was nothing to do simply with that until dprintk() issue reveals some (legacy?) stuff to improve." — Andy Shevchenko

He reiterated his preference:

"I would not go with (void)0 approach, but I also think that dropping unneeded (if confirmed) expression wrapping is a good thing to do." — Andy Shevchenko

The Final Proposal: do{} while(0) with Conditional Logic

Sean Chang proposed a refined solution that removes both the ({}) wrapper and the ternary operator, using a traditional do{} while(0) construct to prevent dangling-else problems:

"Thanks for your comment, how about removing the ({}) and ternary operator to prevent sparse throw incompatible types. And use the do{} while(0) to prevent dangling-else problem." — Sean Chang

The proposed macro definition:

#define nfs_errorf(fc, fmt, ...) do { \
    if ((fc)->log.log) \
        errorf(fc, fmt, ## __VA_ARGS__); \
    else \
        dprintk(fmt "\n", ## __VA_ARGS__); \
} while (0)

Consensus Reached

Andy Shevchenko approved the proposal:

"LGTM." — Andy Shevchenko

Classification

This discussion concerns a bug fix (addressing Sparse type-mismatch warnings) combined with code cleanup (simplifying macro definitions in the SunRPC/NFS subsystem). The changes ensure proper type checking while maintaining zero-cost debug stubs in non-debug builds.

Conclusion

The thread concluded with consensus on the nfs_errorf() macro syntax for the upcoming v3 series. Sean Chang confirmed he would send out the v3 series once this discussion was settled Sean's note, and with Chuck Lever already offering to merge the patches, the path forward is clear. The technical achievement is a cleaner, warning-free macro implementation that leverages standard C idioms (do{} while(0)) rather than GCC-specific statement expressions where unnecessary.
