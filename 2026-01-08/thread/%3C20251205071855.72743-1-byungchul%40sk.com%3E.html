DEPT Module Support Review: Event Site Dependency Tracking for Loadable Modules

Summary

DEPT: Module Support Review for Event Site Dependency Tracking

Overview

This thread is part of Byungchul Park's 42-patch v18 series introducing DEPT (DEPendency Tracker), a new kernel subsystem designed to detect deadlock possibilities by tracking wait/event dependencies rather than lock acquisition order — complementing the existing Lockdep infrastructure. The series was originally posted on December 5, 2025 (cover letter).

This week's activity consists of a single review message from Petr Pavlu (SUSE) on patch 34/42, which adds module loader support for struct dept_event_site and dept_event_site_dep. This is classified as a new feature (kernel infrastructure), not an NFS-specific change or bug fix. The DEPT subsystem has broad kernel-wide applicability, including potential future use in NFS client/server deadlock detection, but this particular patch deals with core module loading mechanics.

Background: The DEPT Subsystem

DEPT aims to address limitations of Lockdep in handling waits and events — such as wait_for_completion()/complete() pairs — that can lead to deadlocks but are invisible to lock-order tracking. As Byungchul Park explained in the cover letter:

"Waits and their associated events that are never reachable can eventually lead to deadlocks. However, since Lockdep focuses solely on lock acquisition order, it has inherent limitations when handling waits and events." Byungchul Park

The subsystem is marked EXPERIMENTAL in Kconfig and is not yet suitable for automation, but early adopters have already found real problems in practice.

This Week's Activity: Petr Pavlu's Module Loader Review

On January 7, 2026, Petr Pavlu posted review comments on patch 34/42 from the module loader perspective. The patch introduces dept_mark_event_site_used() and related infrastructure to handle DEPT event site sections during module load/unload.

Key Technical Comments

1. Coding Style — extern Keyword

Petr flagged a minor style issue:

"Nit: The coding style recommends not using the extern keyword with function declarations." Petr Pavlu

He referenced the kernel documentation on function prototypes.

2. Type Safety Concerns

Petr raised a significant type-safety observation about the .dept.event_sites section:

"My understanding is that entries in the .dept.event_sites section are added by the dept_event_site_used() macro and they are pointers to the dept_event_site_init struct, not dept_event_site." Petr Pavlu

He suggested that dept_mark_event_site_used() should take pointers to dept_event_site_init rather than generic void* to catch type mismatches with module::dept_event_sites:

"Nit: I suggest that dept_mark_event_site_used() take pointers to dept_event_site_init, which would catch the type mismatch with module::dept_event_sites." Petr Pavlu

3. Section Lifetime and .init Prefix

Petr questioned whether the .dept.event_sites section needs to persist after module initialization:

"It seems to me that the .dept.event_sites section can be discarded after the module is initialized. In this case, the section should be prefixed by '.init' and its address can be obtained at the point of use in dept_mark_event_site_used_module(), without needing to store it inside the module struct." Petr Pavlu

This is a meaningful optimization question — if the section data is only needed during module load, marking it as .init would reduce memory footprint.

4. Indirection Question

Petr questioned the design choice of using an indirection layer:

"Additionally, what is the reason that the dept_event_site_init data is not stored in the .dept.event_sites section directly and it requires a level of indirection?" Petr Pavlu

5. Build-Time vs Runtime Checking

Finally, Petr posed a broader architectural question about whether the "used" check for dept_event_site could be performed at build time rather than runtime:

"In general, for my own understanding, I also wonder whether the check to determine that a dept_event_site is used needs to be done at runtime, or if it could be done at build time by objtool/modpost." Petr Pavlu

Significance for NFS Development

While this thread is not directly about NFS, the DEPT subsystem has implications for NFS client and server development:

  1. Deadlock detection: NFS operations involve complex wait/event patterns (e.g., RPC call completions, page lock waits, delegation recall handling) that are difficult to track with Lockdep alone. DEPT could help uncover latent deadlock conditions in NFS code paths.

  2. Module support: The reviewed patch ensures DEPT works correctly with loadable kernel modules — critical since many filesystems and network stacks are modularized.

  3. Experimental status: As noted by Byungchul Park, DEPT is tagged EXPERIMENTAL and will require ongoing annotation efforts across subsystems (similar to Lockdep's two-decade evolution). NFS developers should be aware of this tool as it matures.

Conclusion

This week saw Petr Pavlu provide detailed module-loader-focused review feedback on patch 34/42 of the DEPT series. His comments address coding style, type safety, section lifetime optimization, and architectural questions about build-time versus runtime checking. No response from Byungchul Park was recorded within this week's window. The discussion remains focused on refining the DEPT subsystem's module integration before it can serve as a reliable deadlock detection tool across the kernel, including NFS-related code paths.
