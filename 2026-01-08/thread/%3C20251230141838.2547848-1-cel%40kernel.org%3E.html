NFSD: Automatic NFSv4 State Revocation on Unmount — v1 Review and VFS Design Discussion

Summary

NFSD: Automatic NFSv4 State Revocation on Filesystem Unmount — v1 Review

Overview

This week, Jeff Layton reviewed Chuck Lever's five-patch series (v1) introducing automatic NFSv4 state revocation when a filesystem is unmounted. This is classified as a new feature for the NFS server (NFSD), with significant implications for NFS client behavior and server-side reliability. The series aims to eliminate the need for manual administrator intervention via /proc/fs/nfsd/unlock_fs before unmounting exported filesystems.

Background (Prior Week)

The patch series was originally posted on December 30, 2025. NeilBrown provided early feedback on the cover letter, questioning whether the mechanism catches actual unmounts or only remount-read-only events:

"I think you aren't catching umount, only 'mount -o remount,ro'"

As noted by NeilBrown

NeilBrown also raised concerns about the claim that clients receive no notification when state becomes invalid:

"I don't understand this claim. You code uses exactly the same internal mechanisms, which trigger ADMIN_REVOKED errors to the extent supported by the protocol (v4.1 does this better than v4.0)."

As questioned by NeilBrown

Chuck Lever acknowledged the feedback and committed to producing a v2:

"I'll digest your other comments and produce a v2. Thanks for having a look!"

As confirmed by Chuck Lever

This Week's Discussion (January 6, 2026)

Patch 1/5: Cancel Async COPY Operations on State Revocation — Approved

Jeff Layton reviewed the first patch, which ensures that ongoing async COPY operations are canceled when an administrator revokes filesystem state via unlock_fs. Each canceled copy triggers a CB_OFFLOAD callback carrying NFS4ERR_ADMIN_REVOKED to notify the client.

"Looks reasonable, and seems like the right thing to do if the state is cancelled."

As reviewed by Jeff Layton

Layton provided a formal review acknowledgment:

"Reviewed-by: Jeff Layton jlayton@kernel.org"

As stated by Jeff Layton

Patch 2/5: Export pin_insert and pin_remove for Modular Filesystems — Approved

The second patch exports the core fs_pin functions so that modular filesystems (such as NFSD, which is built as a loadable module) can use them. Layton noted this was simply an oversight:

"This seems like it was probably just a case of no having needed it until now."

As observed by Jeff Layton

He also provided a formal review acknowledgment:

"Reviewed-by: Jeff Layton jlayton@kernel.org"

As stated by Jeff Layton

Patch 3/5: Add pin_insert_group() for Superblock-Only Pins — Discussion on Design

The third patch introduces a new VFS API function, pin_insert_group(), which registers pins only on the superblock's s_pins list (triggering callbacks during remount-read-only via group_pin_kill()), rather than also on mount-specific pins (which would trigger mnt_pin_kill() during mount teardown). This distinction is critical because NFSD's state revocation path acquires locks that conflict with the mnt_pin_kill() context, creating potential AB-BA deadlocks.

Jeff Layton raised two important concerns:

1. VFS Infrastructure Appropriateness:

"Having nfsd as another user of the fs_pin infrastructure seems like a reasonable thing to do, but I wonder if the VFS maintainers might rather we use something different here (notifiers maybe?). I'd loop them and fsdevel in on the next posting."

As suggested by Jeff Layton

Layton also corrected a minor inaccuracy in the patch description:

"This is a little misleading. Filesystems don't really use fs_pin, AFAICT. It's only currently used by BSD process accounting to kill accounting when the filesystem is unmounted."

As clarified by Jeff Layton

2. Behavior with Bind Mounts:

"This is going to have some interesting behaviors around exported bind mounts. I guess with this scheme you won't get any state revocation if you unexport and unmount a bind mount?"

As questioned by Jeff Layton

Chuck Lever concurred with the suggestion to involve VFS maintainers:

"Agreed."

As confirmed by Chuck Lever

Key Technical Arguments

AspectDetail
ProblemUnmounting an exported filesystem fails with EBUSY due to pinned NFSv4 state; manual intervention via /proc/fs/nfsd/unlock_fs breaks automation
SolutionUse the kernel's fs_pin infrastructure to detect unmount events and automatically revoke all associated NFSv4 opens, locks, delegations, NLM locks, and cached file handles
Client notificationClients receive NFS4ERR_ADMIN_REVOKED via standard NFSv4 recall/callback mechanisms (better supported in v4.1 than v4.0)
Deadlock avoidanceNew pin_insert_group() API registers superblock-only pins to avoid AB-BA lock ordering conflicts with VFS unmount path
Workqueue designRevocation work runs on a dedicated nfsd_pin_wq workqueue to avoid deadlocks since VFS kill callbacks run with locks held
Design concernLayton questions whether fs_pin is the right VFS abstraction, suggesting notifiers as an alternative; recommends involving VFS maintainers and fsdevel for v2
Bind mount edge caseUnclear behavior when unexporting/unmounting bind mounts — state revocation may not trigger in this scenario

Significance for NFS Client Development

While this series targets the NFS server, it has direct implications for NFS clients:

  1. Automated infrastructure: Containerized NFS servers, orchestration systems (Kubernetes, OpenShift), and unattended maintenance scripts can now reliably unmount exported filesystems without custom workarounds. This is a critical improvement for cloud-native NFS deployments.

  2. Client error handling: Clients will receive NFS4ERR_ADMIN_REVOKED errors through standard recall/callback mechanisms when their state is invalidated due to unmount, rather than encountering silent failures or data corruption from stale state.

  3. Async COPY reliability: The cancellation of async COPY operations with proper client notification prevents orphaned server-side copy threads and ensures clients are informed of interrupted offload transfers.

  4. NFSv2/3 file cache cleanup: Closing cached NFSv2/3 file handles during unmount ensures that legacy protocol interactions do not prevent filesystem teardown.

Conclusions

  • Patches 1/5 and 2/5 received formal Reviewed-by approvals from Jeff Layton.
  • Patch 3/5 sparked a productive design discussion: Layton recommended involving VFS maintainers and the fsdevel mailing list for v2, and raised an open question about bind mount behavior.
  • Chuck Lever agreed to loop in VFS maintainers for the next posting.
  • The series remains at v1 with a v2 expected after incorporating NeilBrown's and Layton's feedback, particularly around: (a) whether fs_pin is the right abstraction vs. notifiers, (b) bind mount semantics, and (c) clarifying the scope of unmount detection per NeilBrown's earlier concern.
