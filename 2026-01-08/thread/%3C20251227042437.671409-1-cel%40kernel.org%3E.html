NFSD SCSI Fencing xarray API refinement

Summary

NFSD: SCSI Persistent Registration Fencing — xarray API Refinement

Overview

This thread concerns a bug-fix patch series (now at v5) for the NFS server's pNFS block layout support. The patch, authored by Dai Ngo and Chuck Lever, introduces per-client tracking of SCSI persistent registration fencing using an xarray data structure. The goal is to prevent redundant and failing fence operations when a client holding pNFS SCSI layouts becomes unresponsive.

This week's discussion focused on code review feedback from Christoph Hellwig regarding the choice of xarray API functions and the long-term architectural implications of the approach.

Background (Prior Weeks)

The patch series has evolved through five versions since its initial posting on December 26, 2025. The core problem: when the NFS server revokes access from an unresponsive client by preempting its SCSI persistent reservation key, subsequent fence operations for the same device fail because the key is no longer registered. The solution tracks fenced devices per client via an xarray indexed by dev_t.

Dai Ngo provided early approval on January 3rd:

"Thanks Chuck! it looks fine to me."

As confirmed by Dai Ngo

This Week's Discussion

Christoph Hellwig's Architectural Concerns (Jan 7)

Christoph Hellwig reviewed the patch and raised two key points:

  1. Unconventional xarray usage: He noted that using an xarray "only for values is creative" but acknowledged it should work functionally.

  2. Long-term design consideration: Hellwig argued that the current approach, while pragmatic, may not be the ideal long-term solution:

"Right now the nfsd code has no object for pNFS device, mostly because: a) there can only be one per file system and thus export b) there is no per-device state managed by nfsd. This patch changes b)."

As stated by Christoph Hellwig

He suggested that "having a per-device object, and then tracking fenced clients in that would seem more natural" in the long run, but conceded:

"But with all the effort already invested it probably makes sense to go with it to fix the bug."

  1. API concern: Hellwig pointed out that xa_store "actually stores the new entry/value and returns the old one," meaning "this does quite a bit of work for the non-initial GETDEVICEINFO."

Chuck Lever's Follow-Up (Jan 8)

Chuck Lever acknowledged the misleading comment and asked whether the code should use xa_insert instead of xa_store:

"The comment is misleading then, and should be clarified. But should the code use xa_insert instead of xa_store?"

As questioned by Chuck Lever

NeilBrown's Suggestion (Jan 8, referenced in Hellwig's reply)

NeilBrown suggested considering xa_cmpxchg() to replace NULL with a value as an alternative approach.

Christoph Hellwig's Final Recommendation (Jan 8)

Hellwig weighed the options and concluded:

"xa_insert seems like a lot less heavy handed."

As recommended by Christoph Hellwig

Key Technical Arguments

AspectDetail
ProblemRedundant SCSI fence operations fail when a client's persistent reservation key has already been preempted
SolutionPer-client xarray tracking fenced devices by dev_t, with a flag to skip duplicate fencing
API concernxa_store performs unnecessary work for non-initial GETDEVICEINFO calls
Proposed fixReplace xa_store with xa_insert (preferred over xa_cmpxchg)
Long-term designA dedicated per-device object may be more natural, but the current approach is acceptable as a bug fix

Classification

This discussion is about a bug fix for the NFS server's pNFS block layout SCSI persistent reservation fencing logic. The patch prevents failed fence operations and associated error conditions when handling unresponsive clients.

Conclusions

  • Dai Ngo approved the v5 changes early in the week.
  • Christoph Hellwig accepted the approach pragmatically while noting architectural concerns about long-term maintainability.
  • The immediate action item is to replace xa_store with xa_insert and clarify the misleading comment, as recommended by Hellwig.
  • The patch series appears close to being ready for merge pending this minor API adjustment.
