NFS readdir Slow-Start Regression Fix – Follow-Up

Overview

This thread concerns a bug fix for a performance regression in the NFS client's readdir path. Sagi Grimberg submitted a patch (v2) last week and followed up with a brief ping this week to solicit feedback from the NFS maintainers.

Background

The regression was introduced by commit 580f236737d1 ("NFS: Adjust the amount of readahead performed by NFS readdir"), which reduced the amount of readahead name caching done by the NFS client. While this change aimed to improve efficiency, it inadvertently caused a slow-start problem:

"The downside of this approach is READDIR now may suffer from a slow-start issue, where initially it will fetch names that fit in a single page, then in 2, 4, 8 until the maximum supported transfer size (usually 1M)."

In other words, directory reads would begin with small transfers and only gradually ramp up to optimal sizes, degrading performance for workloads that scan directories.

This Week's Activity

The only message within the reporting window was a follow-up from Sagi Grimberg on January 5:

"Anna, Trond, any feedback on this patch?" Sagi Grimberg

The patch itself is a minimal two-line change in fs/nfs/dir.c (2 insertions, 2 deletions), designed to strike what Sagi described as:

"a balanced approach between mitigating the slow-start issue still maintaining some efficiency gains."

Status

As of the end of this reporting week, no feedback or review comments have been posted from Anna Schumaker or Trond Myklebust. The patch remains pending review.

Key Technical Points

  • Type: Bug fix (with a Fixes: tag pointing to commit 580f236737d1).
  • Impact: NFS client readdir performance — specifically the initial ramp-up phase of directory reads.
  • Approach: Adjusts the readahead behavior to avoid the slow-start penalty while preserving some of the efficiency gains from the original commit.
