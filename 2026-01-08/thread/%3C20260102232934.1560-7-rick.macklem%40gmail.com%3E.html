NFSv4.2 POSIX ACL Client: Build Failures on Patch 6/7 Due to Missing Server Dependency

Summary

Classification: New feature (build error feedback)

This thread captures automated build failure reports against patch 6/7 of Rick Macklem's seven-patch series introducing client-side support for the NFSv4.2 POSIX draft ACL extension. The broader series, posted on January 2 (see prior summary), adds a sideband protocol allowing POSIX draft ACLs to be acquired and set directly over NFSv4.2, bypassing the lossy NFSv4-to-POSIX ACL mapping algorithm.

Build Error Reported by 0-DAY CI

On January 3, the kernel test robot (lkp@intel.com) reported build failures for patch 6/7 ([PATCH v1 6/7] Set SB_POSIXACL if the server supports the extension) under the x86_64-kexec configuration with clang version 20.1.8:

"error: use of undeclared identifier 'FATTR4_WORD2_POSIX_DEFAULT_ACL'" kernel test robot

"error: use of undeclared identifier 'FATTR4_WORD2_POSIX_ACCESS_ACL'" kernel test robot

The problematic code in fs/nfs/super.c (lines 1356–1358) checks the server's attribute bitmask to determine whether POSIX ACL support should be enabled on the superblock:

/* Set SB_POSIXACL if the server supports the NFSv4.2 extension. */
if ((server->attr_bitmask[2] & FATTR4_WORD2_POSIX_DEFAULT_ACL) &&
    (server->attr_bitmask[2] & FATTR4_WORD2_POSIX_ACCESS_ACL))
    s->s_flags |= SB_POSIXACL;

This patch's purpose is to set the SB_POSIXACL superblock flag when both POSIX draft default ACL and POSIX draft access ACL attributes are supported by the server, enabling proper VFS-level POSIX ACL semantics for NFSv4.2 mounts.

Root Cause: Same Missing Dependency as Patch 5/7

Rick Macklem responded promptly, noting this is the same underlying issue reported against patch 5/7 earlier in the day (see related summary):

"Next dumb question. This error is the same story. It needs 0001 from the server patch series." Rick Macklem

The identifiers FATTR4_WORD2_POSIX_DEFAULT_ACL and FATTR4_WORD2_POSIX_ACCESS_ACL are defined in the server-side patch series (authored by Chuck Lever), which introduces the new NFSv4.2 POSIX draft ACL attribute bitmask definitions. The client series was designed to be applied after that server series, but the 0-DAY CI test infrastructure attempted to build the client patches independently against the base tree, where these definitions do not yet exist.

Open Question: Multiple "Closes:" Tags

Macklem raised a practical question about how to properly attribute fixes when incorporating the server-side dependency patch into the client series:

"If I repost this series with that patch in it, this report wants a different tag for Closed by:. Do I put multiple 'Closed by:' lines on the commit or just the first one?" Rick Macklem

This question reflects a procedural concern about properly closing multiple 0-DAY CI bug reports when a single patch resolves build failures reported against several patches in the same series.

Technical Significance

This thread is a continuation of the dependency issue identified in patch 5/7's feedback (see prior summary). Both patches reference bitmask constants (FATTR4_WORD2_POSIX_DEFAULT_ACL and FATTR4_WORD2_POSIX_ACCESS_ACL) that are defined only in the companion server series. The pattern underscores a common challenge in kernel development when implementing protocol extensions spanning both client and server code:

  1. Interdependent patches: The client-side superblock flag setup (nfs_get_tree_common()) references bitmask constants defined only in the server series, creating a hard dependency between the two patch sets.
  2. Automated testing gaps: The 0-DAY CI system correctly identified the build failure but could not resolve the dependency ordering issue on its own.

Conclusion

No final resolution was reached within this reporting week. The thread ended with Rick Macklem's question about proper attribution when incorporating the server-side dependency patch into the client series. This represents an open action item for the next version of the patch set. The build failures are not indicative of a logic error in the client code, but rather a missing header definition from the companion server series — the same root cause identified in the parallel discussion on patch 5/7.
