NFSv4.2 POSIX ACL Client Support v2: Server Dependency Fixed, New CONFIG_NFS_V4 Build Issue Raised

Summary

NFSv4.2 POSIX ACL Client Support — Patch Series v2

Classification: New feature (protocol extension implementation)

Overview

Rick Macklem posted version 2 of his eight-patch series introducing client-side support for the NFSv4.2 POSIX draft ACL extension on January 3, 2026. This is a follow-up to the initial seven-patch v1 series submitted on January 2 (see prior summary), which encountered build failures from the 0-DAY CI kernel test robot due to missing server-side definitions (see related summaries, [id://20260102232934.1560-7-rick.macklem@gmail.com)).

The series implements a sideband protocol for NFSv4.2 that allows POSIX draft ACLs to be acquired and set directly — bypassing the lossy "loosey" NFSv4-to-POSIX ACL mapping algorithm. As Rick Macklem explains in the cover letter:

"The Internet draft 'POSIX Draft ACL support for Network File System Version 4, Minor Version 2' describes an extension to NFSv4.2 so that POSIX draft ACLs can get acquired and set directly, without using the loosey NFSv4->POSIX draft mapping algorithm. It extends the protocol with four new attributes."

This approach is analogous to the NFSACL sideband protocol used for NFSv3, enabling getfacl(1)/setfacl(1) to work transparently over NFSv4.2 mounts when both client and server support the extension.

Changes from v1 to v2

The key change in v2 was addressing the build failures reported by the kernel test robot against v1. As Rick Macklem notes:

"The only changes from v1 is the addition of the 0001 patch from the server series, to make the kernel test robot happy and a small change to the calculation of NFS4_ACL_MAXPAGES."

By incorporating the server-side definitions patch (originally authored by Chuck Lever) as patch 1/8 of this series, the previously missing identifiers FATTR4_WORD2_POSIX_DEFAULT_ACL and FATTR4_WORD2_POSIX_ACCESS_ACL are now self-contained within the client series. Patch 1/8 includes proper Closes: tags referencing all three kernel test robot reports from v1:

"Reported-by: kernel test robot lkp@intel.com" "Closes: https://lore.kernel.org/oe-kbuild-all/202601031506.MX594pma-lkp@intel.com/" "Closes: https://lore.kernel.org/oe-kbuild-all/202601031639.zIQYLs4h-lkp@intel.com/" "Closes: https://lore.kernel.org/oe-kbuild-all/202601031746.QiLqxADW-lkp@intel.com/"

Patch Breakdown (v2, 8 patches)

Patch 1/8: POSIX Draft ACL Attribute Definitions

Adds the server-side definitions for the four new NFSv4.2 POSIX draft ACL attributes to include/linux/nfs4.h. This is the patch incorporated from the server series to resolve the v1 build failures, adding 37 lines of attribute bitmask definitions.

Patch 2/8: Predefined Client Operations Enum

Extends the predefined Linux client operations enum in include/linux/nfs4.h with entries for getting and setting POSIX draft ACLs.

Patch 3/8: POSIX Draft ACL Structures

Introduces new structures and definitions in include/linux/nfs_xdr.h for handling POSIX draft ACLs in the NFS client, adding 57 lines.

Patch 4/8: Global Accessor Function

Makes posix_acl_from_nfsacl() global so it can be called from the NFSv4.2 client code handling POSIX draft ACL extensions.

Patch 5/8: Shared ACL Helper Functions

Refactors three functions — nfs3_prepare_get_acl(), nfs3_complete_get_acl(), and nfs3_abort_get_acl() — by moving them to a new shared file fs/nfs/nfs34acl.c and renaming them to nfs34_XXX(). This enables reuse from both NFSv3 and the new NFSv4.2 POSIX ACL code paths.

Patch 6/8: Server Capability Check

Makes nfs4_server_supports_acls() global and extends it to check for POSIX draft ACL support, allowing the capability to be verified in nfs4proc.c.

Patch 7/8: Superblock Flag

Sets SB_POSIXACL on the superblock when both POSIX draft default ACL and POSIX draft access ACL attributes are supported by the server, enabling proper VFS-level ACL semantics.

Patch 8/8: Core Implementation

The largest patch adds the full procedure implementations and XDR encoding/decoding for the four new NFSv4.2 POSIX draft ACL attributes. It touches fs/nfs/nfs42proc.c (304 lines), fs/nfs/nfs42xdr.c (642 lines), and several other files, totaling 965 insertions. As Rick Macklem notes:

"The last patch is rather large, but I would get either build failures or build warnings when I broke it up into smaller chunks."

Review Feedback: CONFIG_NFS_V4 Build Issue

On January 5, Anna Schumaker reviewed patch 7/8 and identified a new build issue: the code accesses server->attr_bitmask in fs/nfs/super.c, but this member only exists when the kernel is configured with CONFIG_NFS_V4=y. She reported:

"Just a heads up that server->attr_bitmask only exists if the kernel is configured with CONFIG_NFS_V4=y, so the compiler will complain about this:" Anna Schumaker

The compiler errors she observed were:

fs/nfs/super.c:1348:15: error: no member named 'attr_bitmask' in 'struct nfs_server'
fs/nfs/super.c:1349:15: error: no member named 'attr_bitmask' in 'struct nfs_server'

She suggested:

"You'll probably need to either move it into NFS v4 specific code or hide it behind an #ifdef." Anna Schumaker

Rick Macklem responded the same day, agreeing with the #ifdef approach but explaining why moving the code to NFSv4-specific paths was not viable:

"I think hiding it behind an #ifdef is the obvious solution." Rick Macklem

"I cannot see how the NFSv4 specific code gets called when the superblock gets set up. I know that the generic superblock code cannot call anything in the NFSv4 code. Already made that mistake and ended up with a cycle in the module dependencies." Rick Macklem

Known Limitations

Rick Macklem calls out an important caveat regarding the "per file" scope mode:

"The current implementation may not handle the 'per file' scope, where individual file objects store/use either an NFSv4 ACL or a POSIX draft ACL. The only known file system that implements this is IBM's GPFS, and only if the 'all' option is set for ACLs on it. Until a server implements this case, it will be difficult to implement correct client semantics for this case."

Status and Outlook

The series is pending a v3 to address Anna Schumaker's CONFIG_NFS_V4 build issue. Rick Macklem noted a timeline constraint:

"I can repost the patch in a couple of weeks. (I have limited access to the Linux system I run at home until end of March.)" Rick Macklem

He also offered:

"If you happen to be inspired to do so, you are welcome to fix it." Rick Macklem

This represents a significant feature addition that would enable native POSIX ACL support over NFSv4.2, eliminating the need for lossy translation between NFSv4 ACLs and POSIX draft ACLs when both ends of the connection support the extension — an important improvement for enterprise environments relying on fine-grained access control.
