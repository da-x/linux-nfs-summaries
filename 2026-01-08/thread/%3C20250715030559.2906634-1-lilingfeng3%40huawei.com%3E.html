NFS Client: Deadlock Discovered in Proposed Lock/Unlock Race Fix

Overview

This week saw a significant development in an ongoing effort to fix a use-after-free (UAF) bug in the NFS client's file locking subsystem. The discussion, initiated months earlier by Li Lingfeng of Huawei, has taken a critical turn: the proposed solution was found to introduce a deadlock, casting doubt on the viability of the approach and leaving the original UAF issue unresolved.

Background (Prior Weeks)

The thread originated in July 2025 with Li Lingfeng's PATCH v2 submission, which aimed to fix a race condition between NFS lock/unlock operations and file open operations. The original bug involved a scenario where:

  1. Thread T1 holds multiple locks on a file, with one lock operation extending an existing lock and releasing another.
  2. Thread T2 triggers the NFS state manager (e.g., after a server restart), which reclaims open state and accesses file locks.
  3. Thread T3 opens the file in write-only mode, accessing locks that have been freed by T1's operations — resulting in a use-after-free.

The proposed fix in v2 was to use nfsi->rwsem (a read-write semaphore on the NFS inode) to protect file locks from concurrent access during reclaim and open operations. A friendly ping was sent in September 2025, but the patch did not gain traction or review feedback during that period.

This Week's Development: Deadlock Identified

On January 7, Li Lingfeng returned with a critical finding: the rwsem-based solution introduces a deadlock under specific conditions.

The Deadlock Scenario

Li Lingfeng detailed a two-thread deadlock involving the NFS state manager and an unlock operation:

"Recently, we found that this solution can introduce a deadlock issue"

The deadlock unfolds as follows:

  • Thread T1 (user-space flock/unlock path):

    • nfs_flock → do_unlk → nfs4_proc_lock → nfs4_proc_unlck
    • Acquires down_read(&nfsi->rwsem) (holding the read lock)
    • Calls rpc_wait_for_completion_task, waiting for an RPC task to complete
    • The RPC callback (nfs4_locku_done) triggers error recovery, causing the RPC task to sleep on &clp->cl_rpcwaitq

  • Thread T2 (NFS state manager):

    • nfs4_state_manager → nfs4_do_reclaim → nfs4_reclaim_open_state → nfs4_reclaim_locks
    • Attempts down_write(&nfsi->rwsem) — but this blocks because T1 holds a read lock that will never be released (T1 is waiting for the RPC task, which in turn waits for T2 to wake it)

This is a classic ABBA deadlock: T1 holds rwsem and waits for the state manager; T2 (the state manager) needs rwsem to proceed.

Key Conclusion

Li Lingfeng concluded:

"It seems that using &nfsi->rwsem to protect file locks is not a good idea."

The developer then posed an open question to the community:

"Does anyone have a viable approach to address this UAF issue?"

Assessment

This discussion centers on a bug fix — specifically, a race condition leading to use-after-free in the NFS client's file locking code. The original bug was reported by Zhang Jian and the initial approach suggested by Yangerkun, both from Huawei.

The evolution of the thread reveals:

  1. July 2025: Initial patch proposal using rwsem protection.
  2. September 2025: Follow-up ping with no further activity.
  3. January 2026: Discovery that the proposed fix introduces a deadlock, effectively invalidating the approach.

As of this week's final message, no alternative solution has been proposed. The UAF bug remains unfixed, and the community is being asked to contribute ideas for a viable resolution. This underscores the complexity of concurrent locking in the NFS client, where interactions between user-space lock operations, RPC error recovery, and the state manager create subtle deadlock hazards.
