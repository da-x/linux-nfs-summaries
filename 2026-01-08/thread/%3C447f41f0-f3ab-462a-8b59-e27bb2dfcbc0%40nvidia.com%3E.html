NFS EOF Page Pollution Fix Causes ext4 Corruption in Nested VMs

Summary

NFS EOF Page Pollution Fix Causes ext4 Checksum Corruption in Nested VMs

Type: Bug fix regression investigation

Overview

NVIDIA engineers reported a filesystem corruption regression traced to Trond Myklebust's "eof page pollution" protection fix in the NFS client. The issue manifests as intermittent ext4 checksum errors during boot of nested virtual machines, where qcow2 disk images stored on an NFSv4.2 share are used as backing storage for VMs running ext4 filesystems.

Key Technical Details

The Regression

Mark Bloch from NVIDIA opened the thread reporting that their internal regression tests began exhibiting ext4 checksum errors after a specific commit: As reported by Mark:

We've recently started seeing filesystem issues in our internal regression runs, and we were able to bisect the problem down to the following commit:

commit b1817b18ff20e69f5accdccefaf78bf5454bede2 Author: Trond Myklebust trond.myklebust@hammerspace.com Date: Thu Sep 4 18:46:16 2025 -0400

NFS: Protect against 'eof page pollution'

The original commit was designed to fix xfstest generic/363, addressing a scenario where users mmap() an area beyond end-of-file and write data into the folio straddling EOF. When the file length is subsequently extended, the NFS client must discard that folio data to prevent corruption.

Symptoms

The regression manifests as intermittent ext4 directory checksum failures during boot:

EXT4-fs warning (device vda2): ext4_dirblock_csum_verify:375: inode #263414: comm updatedb: No space for directory leaf checksum. Please run e2fsck -D.
EXT4-fs error (device vda2): __ext4_find_entry:1624: inode #263414: comm updatedb: checksumming directory block 0

The issue occurs in roughly half of nested VM boots, making it non-deterministic but reproducible.

Confirmation of Causality

Trond Myklebust initially expressed skepticism about the connection between NFS and ext4 corruption: As noted by Trond:

I'm having trouble seeing how those issues can be related unless ext4 and NFS are somehow sharing the same folios. Does reverting just commit b1817b18ff20 and b2036bb65114 actually fix the ext4 problem?

Mark confirmed that reverting both commits eliminated the issue: As confirmed by Mark:

Yes, after reverting those two commits we no longer can reproduce it.

Nested VM Architecture

Mark explained the complex nested virtualization setup: As described by Mark:

Say we have host A. On host A we run VM B. Inside VM B we run VM C.

Inside VM B we have a mount (nfs one) which holds the .img files. [...] inside VM C, it's a regular ext4 mount: /dev/vda2 on / type ext4 (rw,relatime)

The setup involves:

  • Host A: Physical host running VM B
  • VM B: Runs QEMU with qcow2 images stored on an NFSv4.2 mount (discard=unmap), hosting VM C
  • VM C: Guest VM with ext4 root filesystem backed by the qcow2 image

Trond's Follow-Up Questions

Trond sought to understand whether the interaction between NFS discard/unmap operations and the EOF page pollution fix might be the culprit: As asked by Trond:

OK so if I'm understanding correctly, this is organised as ext4 partitions that are stored in qcow2 images that are again stored on a NFSv4.2 partition.

Do these qcow2 images have a file size that is fixed at creation time, or is the file size dynamic? Also, does changing the "discard" option from "unmap" to "ignore" make any difference to the outcome?

Bar Friedman joined the thread on January 6th, copying in additional NVIDIA engineers for further investigation.

Current Status

The discussion remains open-ended as of this week's window. Key questions remain:

  1. Whether qcow2 images use fixed or dynamic sizing
  2. Whether disabling NFS discard/unmap operations affects the outcome
  3. The precise mechanism by which the EOF page pollution fix corrupts data in nested VM scenarios

Significance for NFS Client Development

This regression highlights a subtle interaction between:

  • The NFS client's EOF page protection logic (designed to prevent data leakage beyond file boundaries)
  • NFSv4.2 discard/unmap operations on sparse files (qcow2 images)
  • Nested virtualization workloads where filesystem layers are stacked through block devices

The fact that reverting the fix eliminates ext4 corruption suggests the EOF page pollution protection may be incorrectly zeroing or invalidating pages that should remain intact in certain discard-heavy workloads.
