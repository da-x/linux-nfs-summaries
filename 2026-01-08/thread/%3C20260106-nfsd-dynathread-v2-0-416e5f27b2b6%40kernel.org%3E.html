NFSD/SUNRPC: Dynamically-Sized Thread Pool for nfsd (v2 Applied)

Summary

This week, Jeff Layton posted version 2 of an eight-patch series introducing dynamic thread pool sizing to the NFS server (NFSD) and the underlying SUNRPC service infrastructure. This is classified as a new feature, not a bug fix or protocol change. The series was positively reviewed by NFSD maintainer Chuck Lever and subsequently applied to the nfsd-testing tree on January 8th.

Background

Prior to this work, nfsd operated with a statically-configured number of threads per pool — set at startup via the traditional threads parameter. This meant that servers either had to over-provision threads (wasting resources during idle periods) or under-provision them (limiting throughput during peak loads). The dynamic thread pool feature allows nfsd to automatically scale its thread count up and down based on actual workload demand.

Patch Series Breakdown

The eight-patch series, posted on January 6th, is structured as follows:

Preparatory SUNRPC Refactoring (Patches 1-3)

Patch 1/8 — sunrpc: split svc_set_num_threads() into two functions Jeff Layton

The existing svc_set_num_threads() handled two divergent codepaths: setting threads for a single pool (when given a pool pointer) and distributing threads evenly across all pools (when given NULL). This patch splits these into separate helpers — the new svc_set_pool_threads() for per-pool control and a streamlined svc_set_num_threads() for global distribution.

Patch 2/8 — sunrpc: remove special handling of NULL pool from svc_start/stop_kthreads() Jeff Layton

Further cleanup removing legacy NULL-pool special-casing in thread start/stop functions, simplifying the codebase for dynamic threading.

Patch 3/8 — sunrpc: track the max number of requested threads in a pool Jeff Layton

Adds tracking of the maximum requested thread count per pool, establishing the upper bound for dynamic scaling.

Core Dynamic Threading Infrastructure (Patches 4-6)

Patch 4/8 — sunrpc: introduce the concept of a minimum number of threads per pool Jeff Layton

This patch introduces the sp_nrthrmin field to track a minimum thread count per pool. The key behavioral change: when min_threads is non-zero and less than the max, the server starts at the minimum and scales up as needed. As Layton explains in the cover letter [Jeff Layton](https://lore.kernel.org/linux-nfs/20260106-nfsd-dynathread-v2-0-416e5f27b2b6@kernel.org>:

"When the minimum is set to a non-zero value, the traditional 'threads' setting is interpreted as a maximum number of threads instead of a static count. The server will start the minimum number of threads, and then ramp up the thread count as needed. When the server is idle, it will gradually ramp down the thread count."

Patch 5/8 — sunrpc: split new thread creation into a separate function Jeff Layton

Refactors thread creation logic into its own function, enabling the dynamic scaling code to spawn new threads on demand.

Patch 6/8 — sunrpc: allow svc_recv() to return -ETIMEDOUT and -EBUSY Jeff Layton

A critical change for the feedback mechanism. svc_recv() now accepts a timeout parameter and can return:

  • -ETIMEDOUT: When a thread waits the full timeout period with no work, signaling that the service is idle and threads could be retired.
  • -EBUSY: When a thread wakes up, finds pending work but no available threads, signaling that more threads are needed.

As described in the patch:

"If it wakes up, finds that there is more work and that no threads are available, then attempt to set SP_TASK_STARTING. If wasn't already set, have the task return -EBUSY to cue to the caller that the service could use more threads."

NFSD Integration (Patches 7-8)

Patch 7/8 — nfsd: adjust number of running nfsd threads based on activity Jeff Layton

The core dynamic scaling logic in the nfsd thread function. On -ETIMEDOUT, a thread marks itself as RQ_VICTIM for exit (if above minimum). On -EBUSY, it attempts to spawn a new thread (if below maximum), serialized via the SP_TASK_STARTING flag and mutex_trylock().

Notably, NeilBrown contributed co-authorship with an important design note:

"I think we want memory pressure to be able to push a thread into returning -ETIMEDOUT. That can come later."

Patch 8/8 — nfsd: add controls to set the minimum number of threads per pool Jeff Layton

Adds user-facing controls via both nfsdfs and netlink interfaces, allowing administrators to configure min_threads per pool from userland.

Key v2 Changes

Layton highlighted several improvements over v1 in the cover letter [Jeff Layton](https://lore.kernel.org/linux-nfs/20260106-nfsd-dynathread-v2-0-416e5f27b2b6@kernel.org>:

"Changes in v2:

  • svc_recv(/) now takes a timeout parameter. This should mean that non-dynamic RPC services are unaffected by these changes.
  • if min_threads is larger than the max, then clamp it to the max
  • simplify SP_TASK_STARTING usage. Have same task set and clear it.
  • rework thread starting logic (EBUSY handling)
  • reorder arguments to svc_set_num_threads() and svc_set_pool_threads()
  • break up larger patches"

The timeout parameter for svc_recv() is particularly significant — it ensures backward compatibility with non-dynamic RPC services (like lockd and NFS callbacks) that continue to use the traditional blocking wait behavior.

Significance for NFS Development

This feature represents a meaningful step forward in NFSD resource management:

  1. Resource efficiency: Servers can now start with a minimal thread footprint and scale up only when demand warrants it, reducing CPU overhead during idle periods.

  2. Backward compatibility: The design is carefully backward-compatible. When min_threads is zero (the default), behavior is unchanged — the server runs the full static thread count as before. This allows safe deployment across mixed kernel environments.

  3. Graceful degradation: As Layton noted [Jeff Layton](https://lore.kernel.org/linux-nfs/20260106-nfsd-dynathread-v2-0-416e5f27b2b6@kernel.org>:

"This control scheme should allow us to sanely switch between kernels that do and do not support dynamic threading. In the case where dynamic threading is not supported, the user will just get the static maximum number of threads, just like they do today."

  1. Userland tooling pending: Layton indicated that complementary nfs-utils patches are forthcoming, which will enable administrators to configure the new min_threads controls from userspace.

Conclusion

The dynamic thread pool feature for NFSD has been successfully merged into the nfsd-testing tree following a clean v2 review cycle. The implementation is architecturally sound — introducing minimum/maximum thread bounds in SUNRPC, using timeout-based feedback via -ETIMEDOUT and -EBUSY return codes, and maintaining full backward compatibility with existing NFS server configurations. Future work includes benchmarking performance impact (noted as pending by Layton/) and potential integration of memory pressure signals into the scaling decision logic (suggested by NeilBrown).
