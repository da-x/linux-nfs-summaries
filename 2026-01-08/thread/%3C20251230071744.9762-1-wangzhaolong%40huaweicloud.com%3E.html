NFSv4.1: Fixing slot table draining + memory reclaim deadlock in state manager creation

Summary

NFSv4.1 Deadlock: Slot Table Draining vs. Memory Reclaim

Background (Prior Weeks)

This thread addresses a critical bug fix targeting a deadlock in the NFSv4.1 client that can render a system permanently stuck during server outages combined with memory pressure. The discussion began late last week when Wang Zhaolong reported the issue as an RFC patch on December 30, followed by a comprehensive response and proposed fix from NFS maintainer Trond Myklebust on December 31.

The Deadlock Scenario

Wang Zhaolong described a production-like scenario involving three participants in a circular wait:

  • P1 (sunrpc worker): On receiving an error like NFS4ERR_BADSESSION, the session slot table is set to draining (NFS4_SLOT_TBL_DRAINING) and recovery triggers creation of a state manager thread via kthread_run(), which waits for kthreadd.
  • P2 (kthreadd): While creating the new thread, memory allocation triggers direct reclaim. During reclaim, nfs_release_folio() is invoked, which calls nfs_commit_inode(inode, FLUSH_SYNC) — a synchronous commit that waits for RPC completion.
  • P3 (sunrpc worker 2): Non-privileged RPC tasks are blocked on the slot table wait queue because the table is in draining state.

The result: kthreadd blocks waiting for commits to complete, but commits cannot progress because the slot table is draining and non-privileged requests are blocked. The system remains stuck even after the server or network is restored.

Wang noted this issue likely became possible after commit c907e72f58ed ("NFSv4.1: freeze the session table upon receiving NFS4ERR_BADSESSION"), which sets draining before the recovery thread runs. He also referenced SUSE Bugzilla #1211527 as a potentially related prior report.

Trond's Proposed Fix Direction

Trond Myklebust proposed a fundamentally different approach rather than Wang's initial patch. His core insight was that nfs_release_folio() should not perform synchronous waits at all:

"I think we need to treat nfs_release_folio() as being different from nfs_wb_folio() altogether. There are too many different ways in which waiting on I/O can cause deadlocks, including waiting on the writeback to complete."

He suggested treating the call as a hint to kick off either writeback or an asynchronous commit — but never waiting for completion:

"My suggestion is therefore that we just make this simple, and see it as a hint that we should kick off either writeback or a commit, but not that we should be waiting for it to complete."

Trond provided a full patch titled "NFS: Fix a deadlock involving nfs_release_folio()" that introduces a new function nfs_wb_folio_reclaim(). This function asynchronously kicks off writeback or an async commit without blocking, breaking the circular dependency. The patch targets the root cause traced to commit 96780ca55e3c ("NFS: fix up nfs_release_folio() to try to release the page").

Current Week Activity (January 2–8)

Wang Zhaolong replied on January 6, expressing agreement with Trond's approach:

"I agree with the overall direction. Avoiding any synchronous waits from ->release_folio() makes a lot of sense."

Wang also identified a minor code issue in Trond's proposed patch — an uninitialized variable ret in the nfs_wb_folio_reclaim() function:

"One small thing: in nfs_wb_folio_reclaim(), the else nfs_commit_inode(inode, 0); branch seems to return an uninitialized ret (unless I missed something)."

He suggested either initializing ret = 0 or returning the value from nfs_commit_inode() for tracing purposes. Wang offered to test the fix once formally posted:

"Happy to test this with my reproducer once you post it."

Summary and Status

  • Type: Bug fix — a critical deadlock in NFSv4.1 client state recovery under memory pressure.
  • Root cause: nfs_release_folio() performing synchronous commit waits during memory reclaim, which can block kthreadd from creating the state manager thread needed to unblock slot table draining.
  • Proposed resolution: Replace synchronous waits in nfs_release_folio() with asynchronous writeback/commit kicks via a new nfs_wb_folio_reclaim() helper.
  • Status: Trond's patch has been reviewed and conceptually approved by Wang, pending a minor fix for an uninitialized return value. The patch has not yet been formally posted to the mailing list as of this week's end; Wang is prepared to test it once available.
