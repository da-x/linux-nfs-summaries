Debate on ACE Count Limits for NFSv4.2 POSIX Draft ACLs

Summary

Limit on Number of ACEs in a POSIX Draft ACL

Classification: Implementation design discussion / protocol guidance (related to new feature development)

Overview

This thread, sparked by Rick Macklem during the review of his NFSv4.2 POSIX draft ACL client support patch series, examines whether and how the Linux NFS client should enforce an upper limit on the number of Access Control Entries (ACEs) in a POSIX draft ACL. The discussion touches on memory allocation strategies, protocol design philosophy, and real-world usage patterns from enterprise environments.

Background

Rick Macklem's seven-patch series for NFSv4.2 POSIX ACL client support (posted January 2) introduced a constant NFS4_ACL_MAXPAGES calculated from the existing NFS_ACL_MAX_ENTRIES value of 1024 — a limit originally defined for the NFSv3 NFS_ACL protocol. This prompted Rick to reconsider whether this limit was appropriate for NFSv4.2 POSIX draft ACLs.

Key Technical Arguments

Rick Macklem's Initial Assessment

Rick opened the discussion on January 6, acknowledging a mistake in his earlier design:

"When I did the POSIX draft ACL patches, I mistakenly thought that NFS_MAX_ACL_ENTRIES was a generic limit that the code should follow. Chuck informed me that it is the limit for the NFS_ACL protocol."

He identified three distinct limits:

  • Server side: Whatever the underlying file system can handle (detected at set time)
  • Encoding: The maximum size of an RPC message (for NFSv4.2)
  • Client side: Most important, as it determines how many pages to allocate for a large ACL that cannot be encoded inline

Rick noted that NFS_MAX_ACL_ENTRIES is 1024, calling it "a pretty generous limit," and sought community input on whether a sanity limit was warranted. He also mentioned his dual role as Internet Draft author:

"When wearing my internet draft author hat, I lean to 'no limit in the draft', since that is what the RFCs do w.r.t. NFSv4 ACLs, but that doesn't mean implementations will handle any number of them."

Aurélien Couderc's Real-World Pushback

Aurélien Couderc strongly disagreed that 1024 is generous:

"Nope, this is not a 'pretty generous limit'. Realistically, with big organisations, you can easily have 300, 400, 500 ACL entries per file or directory."

He described real-world usage patterns in large organizations, particularly around MEMOs with need-to-know access controls where individual users get personal ACL entries rather than group-based ones. He later provided Windows comparison data:

"Biggest ACL list I could find in-house has 722 ACE entries, funny enough it is the memo for new Chef de services."

His conclusion: "a maximum of 1024 NFSv4 ACEs in a NFSv4 ACL should be enough," based on Windows limits (64KB memory budget yielding ~1024 Win32 ACE entries).

Chuck Lever's Architectural Perspective

Chuck Lever took a principled stance against reusing the NFS_ACL protocol constant for NFSv4 ACLs:

"NFS_ACL_MAX_ENTRIES is an NFS_ACL protocol constant, it's not related to any sort of implementation limit. So it is, IMHO, not appropriate to apply to either NFSv4 ACLs or NFSv4.2 POSIX draft ACLs."

He highlighted a fundamental difference between NFSv3 and NFSv4 ACL representations:

"The thing that is new about NFSv4 is that NFS_ACL ACEs are fixed in size because they encode 'who' identities as UID/GID numbers. In NFSv4, 'who' identities are variable-length strings. It's really quite impossible for receivers to guess how large these things are before they land in memory."

Chuck suggested treating ACLs similarly to directories in the NFS layers, noting that both have XDR representations with similar characteristics — variable-sized content that grows dynamically.

On the Internet Draft side, Chuck recommended including implementation guidance:

"Client implementations should be prepared to handle ACLs with many ACEs and large 'who' fields."

Client Memory Allocation Concerns

Rick pushed back on Chuck's assessment that the Linux client already handles dynamic page allocation gracefully:

"There may be a better way (and I coded this some time ago), but I needed an array for the page references, so I could free them."

He pointed to the NFS4_ACL_MAXPAGES calculation in his patch series:

#define NFS4_ACL_MAXPAGES (((2*(3*4+IDMAP_NAMESZ)*  \
       NFS_ACL_MAX_ENTRIES))+PAGE_SIZE-1)>>PAGE_SHIFT

The client code declares a fixed-size array struct page *pages[NFS4_ACL_MAXPAGES], requiring a compile-time constant for the number of ACEs. Chuck responded that this problem "should already be solved in the current code, although it's possible I'm missing your point."

In his final message, Rick acknowledged that dynamic allocation (using struct page **pages with reallocation) was possible but noted:

"I do not think there is anywhere else in the client code that does this dynamically?"

He concluded that some constant limit was needed for the fixed-size array approach, and 1024 seemed reasonable.

Evolution of the Discussion

The conversation evolved through three phases:

  1. Problem identification (Jan 6): Rick questioned whether NFS_ACL_MAX_ENTRIES should govern NFSv4.2 POSIX ACL limits.
  2. Real-world context (Jan 6-7): Aurélien provided enterprise usage data showing ACLs with hundreds of entries are common, while Chuck articulated architectural concerns about conflating protocol constants with implementation limits.
  3. Implementation details (Jan 7-8): The discussion narrowed to the practical question of how the Linux NFS client allocates memory for page arrays when decoding large ACLs, and whether dynamic allocation is feasible or necessary.

Final Conclusions

No formal consensus was reached this week, but several positions crystallized:

  • Chuck Lever maintained that NFS_ACL_MAX_ENTRIES should not be reused as a generic limit for NFSv4 ACLs, since it is protocol-specific to NFSv3's NFS_ACL sideband. He advocated for the Internet Draft to include implementation guidance about handling large ACLs rather than prescribing hard limits.
  • Aurélien Couderc confirmed that 1024 ACEs is a practical upper bound based on real-world enterprise deployments and Windows platform limits, with his largest observed ACL containing 722 entries.
  • Rick Macklem acknowledged the need for some sanity limit in the client code to bound memory allocation for page arrays, tentatively accepting 1024 as reasonable while recognizing that dynamic allocation would be a more elegant but more complex solution.

The discussion highlights a tension between protocol design purity (no artificial limits) and implementation practicality (bounded memory allocation). The outcome will influence both the Linux NFS client code and the Internet Draft specification for NFSv4.2 POSIX ACL support.
