VFS: Require Filesystems to Explicitly Opt-In to Lease Support (24-patch Series)

Summary

VFS Lease Support: Requiring Explicit Opt-In from Filesystems

Overview

On January 8, 2026, Jeff Layton posted a significant VFS-level protocol change series titled "[PATCH 00/24] vfs: require filesystems to explicitly opt-in to lease support." This 24-patch series represents a major architectural shift in how the Linux VFS handles file leases — changing the default behavior from implicit lease support (opt-out) to explicit opt-in. While this is primarily a VFS/filesystem infrastructure change, it has direct implications for NFS client and server development, as NFS and SMB are the primary consumers of kernel file leases and delegations.

Background: The Problem with Implicit Lease Support

Layton explained the historical context in his cover letter [2026-01-08]:

"For historical reasons, when ->setlease() file_operation is set to NULL, the default is to use the kernel-internal lease implementation. This means that if you want to disable them, you need to explicitly set the ->setlease() file_operation to simple_nosetlease() or the equivalent." Jeff Layton

This opt-out model has caused recurring problems:

"This has caused a number of problems over the years as some filesystems have inadvertantly allowed leases to be acquired simply by having left it set to NULL. It would be better if filesystems had to opt-in to lease support, particularly with the advent of directory delegations." Jeff Layton

Layton noted this series is intended for v7.0, following a separate v6.19-targeted fix for directory delegation handling that was posted the previous day. He focused on NFS-exportable filesystems:

"I mainly focused on filesystems that are NFS exportable, since NFS and SMB are the main users of file leases, and they tend to end up exporting the same filesystem types." Jeff Layton

Patch Series Structure

The 24-patch series follows a clear three-phase approach:

Phase 1: Opt-In Existing Filesystems (Patches 01–22)

The first 22 patches add generic_setlease() to the ->setlease file operation across a wide range of local filesystems, ensuring they continue to support leases under the new model. Filesystems covered include:

  • Read-only filesystems (BEFS, EFS, ISOFS, QNX4, QNX6, CRAMFS, FREEVXFS) via generic_ro_fops
  • Mainline local filesystems: affs, btrfs, erofs, ext2, ext4, exfat, f2fs, fat, gfs2, jffs2, jfs, nilfs2, ntfs3, ocfs2, orangefs, overlayfs, squashfs, tmpfs, udf, ufs, xfs

Each patch follows a uniform pattern: adding generic_setlease to both file and directory operations. Jan Kara provided Reviewed-by tags for ext2, ext4, ocfs2, tmpfs, udf, the read-only filesystem batch, and the core VFS changes. Other maintainers contributed acknowledgments:

  • "Acked-by: OGAWA Hirofumi" — for fat

  • "Reviewed-by: Dave Kleikamp" — for jfs

  • "Acked-by: David Sterba" — for affs and btrfs

  • "Acked-by: Namjae Jeon" — for exfat

Phase 2: Change Default Behavior (Patch 23)

Patch 23/24 is the core behavioral change: modifying kernel_setlease() to return -EINVAL when the ->setlease operation is NULL. This effectively makes lease support opt-in for all new filesystems. Jan Kara reviewed and approved this critical patch:

"Looks good. Feel free to add: Reviewed-by: Jan Kara" Jan Kara

Phase 3: Cleanup (Patch 24)

The final patch removes simple_nosetlease() entirely, since a NULL ->setlease now achieves the same effect. Jan Kara commented:

"Nice." Jan Kara

Key Discussion Points

Missing Filesystems: FUSE and kernfs

Jan Kara raised an important question about coverage, noting two exportable filesystems that lacked ->setlease:

"So, what about kernfs and fuse? They seem to be exportable and don't have .setlease set..." Jan Kara

Layton responded with a nuanced analysis:

For FUSE, he acknowledged the oversight:

"Yes, FUSE needs this too. I'll add a patch for that." Jeff Layton

For kernfs (the foundation of sysfs and resctrl), he questioned whether leases are genuinely expected:

"As far as kernfs goes: AIUI, that's basically what sysfs and resctrl are built on. Do we really expect people to set leases there?" Jeff Layton

He noted that while this would technically be a regression (leases previously worked on kernfs files), it is unlikely to cause practical issues:

"people don't usually export kernfs based filesystems via NFS or SMB, and that seems like something that could be used to make mischief." Jeff Layton

Layton also proposed a diagnostic approach for kernfs:

"One idea: we could add a wrapper around generic_setlease() for filesystems like this that will do a WARN_ONCE() and then call generic_setlease(). That would keep leases working on them but we might get some reports that would tell us who's setting leases on these files and why." Jeff Layton

Impact on Network Filesystems

The series also removes ->setlease from several network filesystems (NFS, 9p, Ceph, FUSE, vboxsf, cifs), which already implement their own lease handling and do not rely on the VFS default. This cleanup is consistent with the opt-in philosophy — these filesystems manage leases through their own protocol-specific mechanisms.

Significance for NFS Client Development

This change is highly relevant to NFS client development for several reasons:

  1. Lease correctness: NFS clients rely on file leases and directory delegations for performance optimization. The opt-in model prevents future regressions where new filesystems inadvertently support leases without proper implementation, which could lead to stale cache issues or delegation recall failures.

  2. NFS export safety: By ensuring only filesystems that explicitly opt in can support leases, NFS servers exporting local filesystems will have more predictable lease behavior. This is particularly important for directory delegations, where incorrect lease handling can cause data consistency problems.

  3. New filesystem integration: Any new filesystem intended to be NFS-exportable must now explicitly set ->setlease to generic_setlease() (or a custom implementation) to support NFS leases and delegations. This is documented in the updated porting documentation added by patch 23.

Conclusion

This series represents a well-received architectural improvement to the VFS lease subsystem. The discussion was constructive, with maintainers providing prompt reviews and acknowledgments across the filesystem tree. The key open item is the addition of FUSE support, which Layton committed to addressing. The kernfs question remains an interesting edge case, with Layton proposing a diagnostic wrapper as a potential middle ground.

The change shifts the VFS lease model from opt-out to opt-in, reducing the risk of inadvertent lease support on filesystems that should not participate — a welcome improvement for NFS and SMB server correctness.
