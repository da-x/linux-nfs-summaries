NFSD SCSI Persistent Registration Fencing: Review Clarification on xarray-Based Per-Client Tracking

Summary

NFSD: Track SCSI Persistent Registration Fencing per Client with xarray — Review Follow-up

Background (Prior Weeks)

This thread concerns a patch series by Dai Ngo targeting the NFS server (NFSD), specifically around SCSI persistent registration fencing for block layout devices. The original patch was introduced as [PATCH v4 1/1] on December 26, proposing to use an xarray associated with each nfs4_client structure to track which block devices have already been fenced per client detailed in the initial submission.

The mechanism works as follows: when the server issues a persistent registration key to a client, it creates an xarray entry indexed by the device's dev_t, with a fenced flag initialized to 0. Before performing a fence via nfsd4_scsi_fence_client, the server checks this flag — if already set, the fence is skipped; otherwise, it proceeds and sets the flag to 1.

NeilBrown reviewed the patch on December 27, raising concerns about a code comment that stated /* device already fenced */. He pointed out that in a race condition between two threads, the second thread might reach this point before any thread has actually called ->pr_preempt(), meaning the device is not yet fenced but merely committed to being fenced.

"It isn't the case that 'device [is] already fenced' but that 'we have already committed to fencing the device'."

NeilBrown further questioned:

"Does the second thread need to wait for the fence to complete, or should the comment acknowledge that might not have completed yet?"

Activity This Week (January 3)

The sole message this week is Dai Ngo's response on January 3, addressing NeilBrown's concerns.

Dai confirmed that NeilBrown's interpretation was correct — the flag indicates either that the device has been fenced or is in the process of being fenced:

"Yes, that is correct - it's either the device has been fenced or it's in the processed of being fenced."

He then provided a clear explanation of the purpose of fencing in the NFS server context:

"Fencing is a mechanism used to prevent data corruption and ensure consistency in a shared storage environment. It occurs when a server is unable to recall a layout from a client—typically due to a layout conflict arising from another client gaining access or control over the same device. In such situations, fencing disables or restricts the first client's access to the device, ensuring that only one client interacts with the device at a time. This helps maintain data integrity and prevents simultaneous conflicting operations."

Regarding whether the second thread needs to wait for the fence to complete, Dai clarified:

"No waiting is necessary, as long as the fence operation will be done then that is all it's needed."

Classification

This discussion centers on a new feature — specifically, per-client SCSI persistent registration fencing tracking in NFSD using an xarray data structure. It is not a bug fix but rather a correctness and safety enhancement for NFSv4 block layout (pNFS-block) operations, ensuring that multiple clients accessing the same underlying block device do not cause data corruption through conflicting I/O.

Key Takeaways

  • The patch introduces an xarray (cl_dev_fences) on each nfs4_client to track fencing state per device (dev_t).
  • NeilBrown's review highlighted a subtle semantic issue: the fenced flag represents a commitment to fence, not necessarily a completed fence.
  • Dai Ngo confirmed that no synchronization/waiting is required beyond setting the flag — the critical invariant is that only one fence operation proceeds per device per client.
  • The discussion underscores the importance of fencing in NFS block layout for maintaining data integrity in shared storage environments where layout conflicts may arise between clients.

Current Status

The thread appears to be in a review/clarification phase with no final resolution or merge status communicated this week. The patch has gone through four revisions (v1–v4), addressing concerns around memory allocation, locking, error handling, and code clarity.
