NFSD v1: ACL, Security Label, and Atomicity Bug Fixes Backport to 6.6.y (Dropped)

Summary

NFSD: v1 Backport Series for ACL, Atomicity, and Security Label Bug Fixes to 6.6.y Stable Tree

Overview

This week, Chuck Lever submitted the initial version (v1) of a four-patch series targeting the Linux 6.6 stable tree to address multiple bugs in the NFS server (NFSD). This is classified as a bug fix backport effort, not a new feature or protocol change. The series addresses three distinct but related issues: POSIX ACL omission during NFSv4 file creation, SELinux security label omission during create operations, and NFSv3 atomicity race conditions in attribute setting.

The v1 series was posted on January 3rd but was ultimately dropped by stable maintainer Greg Kroah-Hartman on January 8th due to an incorrect upstream commit reference in the first patch. A corrected v2 series was subsequently submitted later in the week (see related thread summary).

Patch Series Breakdown (v1)

The four-patch series, posted on January 3rd, consists of:

Patch 1/4: nfsd: convert to new timestamp accessors

A preparatory change updating the NFS server code to use newer kernel inode timestamp accessor functions. This patch serves as a dependency for the subsequent atomicity fix as noted by Chuck Lever:

"Stable-dep-of: 24d92de9186e ('nfsd: Fix NFSv3 atomicity bugs in nfsd_setattr()')" Chuck Lever

The patch was tagged with upstream commit 335a7be84b526861f3deb4fdd5d5c2a48cf1feef, which would later prove to be incorrect.

Patch 2/4: nfsd: Fix NFSv3 atomicity bugs in nfsd_setattr()

This patch addresses critical race conditions in NFSv3 attribute-setting operations, authored by Trond Myklebust. The core issue is that the guarded SETATTR mechanism — designed to prevent races with concurrent WRITE and SETATTR calls — was checking the guard time against the inode ctime before acquiring the inode lock, defeating its purpose:

"The main point of the guarded SETATTR is to prevent races with other WRITE and SETATTR calls. That requires that the check of the guard time against the inode ctime be done after taking the inode lock." Trond Myklebust

Additionally, the fix accounts for NFSv3's 32-bit timestamp limitations:

"Furthermore, we need to take into account the 32-bit nature of timestamps in NFSv3, and the possibility that files may change at a faster rate than once a second." Trond Myklebust

This patch was reviewed by Jeff Layton and NeilBrown and serves as a dependency for the security label fix:

"Stable-dep-of: 442d27ff09a2 ('nfsd: set security label during create operations')" Chuck Lever

Patch 3/4: nfsd: set security label during create operations

Authored by Stephen Smalley, this patch fixes a bug where security labels passed by NFSv4 clients during file creation were received by nfsd but never actually applied to the new inode:

"When security labeling is enabled, the client can pass a file security label as part of a create operation for the new file, similar to mode and other attributes. At present, the security label is received by nfsd and passed down to nfsd_create_setattr(), but nfsd_setattr() is never called and therefore the label is never set on the new file." Stephen Smalley

Smalley also raises an important observation about ACLs that directly motivates patch 4/4:

"Looking at nfsd_setattr() I am uncertain as to whether the same issue presents for file ACLs and therefore requires a similar fix for those." Stephen Smalley

The patch includes a detailed SELinux reproducer demonstrating the bug — files created via NFSv4 receive incorrect security contexts (test_file_t instead of the expected test_filesystem_filetranscon_t).

Patch 4/4: NFSD: NFSv4 file creation neglects setting ACL

This is the primary bug fix driving the entire series, authored by Chuck Lever. When an NFSv4 client creates a file with a POSIX ACL containing named principals, the ACL is silently dropped:

"An NFSv4 client that sets an ACL with a named principal during file creation retrieves the ACL afterwards, and finds that it is only a default ACL (based on the mode bits) and not the ACL that was requested during file creation. This violates RFC 8881 section 6.4.1.3: 'the ACL attribute is set as given'." Chuck Lever

The root cause lies in nfsd_create_setattr(), which calls nfsd_attrs_valid() to determine whether to invoke nfsd_setattr(). However, this validation function checks only for standard iattr changes and security labels — not POSIX ACLs:

"However, nfsd_attrs_valid() checks only for iattr changes and security labels, but not POSIX ACLs. When only an ACL is present, the function returns false, nfsd_setattr() is skipped, and the POSIX ACL is never applied to the inode." Chuck Lever

The bug was originally reported by Aurélien Couderc and traces back to commit c0cbe70742f4 ("NFSD: add posix ACLs to struct nfsd_attrs"). The fix is a minimal one-line change in fs/nfsd/vfs.h.

Discussion: Incorrect Upstream Commit Reference

On January 8th, stable maintainer Greg Kroah-Hartman raised concerns about the upstream commit reference in patch 1/4. He first questioned whether the cited commit existed in Linus's tree:

"I don't see this git id anywhere in Linus's tree, are you sure it is correct?" Greg Kroah-Hartman

He followed up with a second inquiry about authorship attribution:

"Is this really commit 11fec9b9fb04 ('nfsd: convert to new timestamp accessors')? if so, what happened to the original authorship and other signed-off-by lines?" Greg Kroah-Hartman

Chuck Lever acknowledged the error, explaining that he had mistakenly picked up a commit ID from an nfsd-related tag:

"I picked up 335a7be84b526861f3deb4fdd5d5c2a48cf1feef from an nfsd-related tag by mistake. Do you want to drop this series and I can rework it properly?" Chuck Lever

He correctly identified the actual upstream commit as 11fec9b9fb04fd1b3330a3b91ab9dcfa81ad5ad3, authored by Jeff Layton and committed by Christian Brauner in October 2023.

Greg Kroah-Hartman confirmed the series would be dropped:

"Now dropped, please rework, thanks!" Greg Kroah-Hartman

Significance for NFS Client and Server Development

While this series targets the NFS server (NFSD), it has direct implications for NFS clients:

  1. ACL enforcement gap: Clients creating files with named-principal ACLs via NFSv4 would experience silent security policy violations, as the requested ACLs were never applied. The server would return a default ACL derived from mode bits instead — a compliance violation against RFC 8881.

  2. SELinux label misapplication: Clients using NFSv4.2 with security labeling (e.g., SELinux) would see files created with incorrect security contexts, potentially breaking mandatory access control policies.

  3. NFSv3 atomicity races: The nfsd_setattr() fix prevents data consistency issues when clients perform concurrent attribute updates (e.g., via chmod or chown) over NFSv3 mounts.

  4. Stable tree importance: These fixes target the 6.6 LTS kernel, which is widely deployed in production environments. The backport ensures that enterprise NFS deployments benefit from these security and correctness improvements without requiring a full kernel upgrade.

Conclusion

This week's v1 submission represented the initial attempt to backport three critical NFSD bug fixes to the 6.6.y stable tree. While the technical content of the patches was sound — addressing ACL omission, security label omission, and NFSv3 atomicity races — the series was dropped due to an incorrect upstream commit reference in the first patch. Chuck Lever promptly acknowledged the error and a corrected v2 series was submitted later in the week (see related thread), which replaced patch 1/4 with the properly attributed upstream version.

This episode underscores the rigorous review process applied to stable tree backports, where commit provenance and authorship attribution are carefully verified by maintainers.
