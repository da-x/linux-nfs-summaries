NFS Client: Introducing LRU-Based Delegation Eviction

Summary

NFS Client Delegation LRU: A Major Rework for Performance and Correctness

Christoph Hellwig posted a substantial 24-patch series to introduce a Least Recently Used (LRU) list for NFS delegations, aiming to fix long-standing inefficiencies in how the NFS client manages delegation state. The series is focused on NFS client development, specifically improving delegation lifecycle management through architectural cleanup and a new eviction strategy.

The Problem: Inefficient Delegation Returns

The current NFS client implementation struggles with delegations not associated with an open file descriptor. As Hellwig explained in the cover letter [20260107072720.1744129-1-hch@lst.de]:

"currently the NFS client is rather inefficient at managing delegations not associated with an open file. If the number of delegations is above the watermark, the delegation for a free file is immediately returned, even if delegations that were unused for much longer would be available."

Additionally, the periodic freeing mechanism was overly aggressive:

"Also the periodic freeing marks delegations as not referenced for return, even if the file was open and thus force the return on close."

The Solution: LRU-Based Eviction

The series introduces a dedicated LRU list for delegations. When the delegation count exceeds a configured watermark, the client now returns the least recently used delegations rather than immediately returning the most recently freed one. This mirrors the referenced-flag-based eviction policies already used by the VFS inode and dentry caches.

Key technical changes in the series include:

  • Removal of legacy helper functions (__nfs_client_for_each_server, nfs_client_mark_return_unused_delegation_types, nfs_client_mark_return_all_delegations) [20260107072720.1744129-2-hch@lst.de] through [20260107072720.1744129-4-hch@lst.de].
  • Simplification of delegation attachment/detachment logic and removal of the NFS_DELEGATION_INODE_FREEING flag [20260107072720.1744129-5-hch@lst.de] through [20260107072720.1744129-10-hch@lst.de].
  • Introduction of a separate delegation return list and LRU-based eviction when over the watermark [20260107072720.1744129-23-hch@lst.de].
  • A less aggressive periodic cleanup that avoids marking open-but-unused delegations for forced return on close [20260107072720.1744129-24-hch@lst.de].

Performance Impact

Hellwig reported dramatic improvements for workloads involving repeated module imports (e.g., Python virtual environments):

"For a workload simulating repeated runs of a python program importing a lot of modules, this leads to a 97% reduction of on-the-wire operations, and ~40% speedup even for a fast local NFS server."

Discussion: LRU vs. LFU and Future Heuristics

Chuck Lever questioned whether alternative eviction policies such as Least Frequently Used (LFU) had been considered [0b0b21c1-0bfd-4e2e-9deb-f368a66f5e9c@app.fastmail.com]:

"I'm curious if you tried other methodologies like LFU to decide which delegation to return?"

Hellwig dismissed LFU as impractical due to its overhead:

"LFU I guess means least frequently used. That would imply tracking usage frequency, and rotating a list of other lookup structure a lot. The first is something not really provided in the delegation code, and the latter tends to be really horrible for in terms of cache dirtying."

Sagi Grimberg acknowledged the complexity but suggested that more sophisticated heuristics could be valuable future enhancements [ea31c230-1ace-4721-872e-2313b497214f@grimberg.me]:

"I think that there is merit for tracking file usage frequency and accounting it for deleg return policy, and I don't necessarily think that it would not be worth the overhead (compared to sending rpcs to the server)... but I agree that its a much heavier lift (it can always be done incrementally to this patchset)."

Grimberg also proposed several ideas:

  • Holding read delegations longer than write delegations, since shared files in Python/bash workloads are "likely to be updated very rarely, yet accessed frequently by lots of clients."
  • Using file modification time (mtime) as a heuristic — files with old mtime values could have their delegations held "with 'low risk' of a conflict."
  • Relying more on server-initiated delegation recalls rather than client-side watermark thresholds.

Hellwig pushed back on the complexity argument, noting:

"There's a reason the rest of the kernel uses fairly simple LRU (or rather modified LRU / clock like) eviction policies like this, in that the sampling is quite overboard. I'm not going to keep you from looking into this, but I don't think it's worthwhile."

Client vs. Server Interests in Delegation Recall

Grimberg suggested that servers might be better positioned to solicit preemptive delegation recalls [ea31c230-1ace-4721-872e-2313b497214f@grimberg.me]:

"And, in general, I think that the server is in a much better position to solicit preemptive delegation recalls as opposed to the client voluntarily return delegations when crossing a somewhat arbitrary delegation_watermark."

Chuck Lever countered that server and client have "orthogonal interests" [45ba87f3-2322-424b-95b1-9129a2537545@app.fastmail.com]:

"The server is concerned with resource utilization -- memory consumed, slots in tables, and so on -- that other active clients might benefit from having freed. The server doesn't really care which delegations are returned. A client wants to keep delegation state that applications are using, and it knows best which ones those are."

Hellwig agreed, pointing to RECALL_ANY as the protocol mechanism that could bridge this gap [20260108153546.GA7623@lst.de]:

"Yes. A good way to deal with that is implementing RECALL_ANY as I mentioned, which with these changes could reclaim off the end of the LRU. But as this series is a big change already, and doing fine grained recalls is another huge one I'd rather wait a bit before going there."

Conclusion

This series represents a significant architectural improvement to NFS client delegation management. By replacing the simplistic immediate-return-on-close behavior with an LRU-based eviction policy, the patchset delivers substantial performance gains for common workloads while simplifying the delegation codebase. The discussion also laid groundwork for future enhancements, including RECALL_ANY support and potentially more sophisticated delegation retention heuristics.
