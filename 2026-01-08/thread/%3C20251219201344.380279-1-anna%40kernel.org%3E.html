NFS: Fix directory delegation state recovery crashes

Summary

NFS Client Directory Delegation Bug Fix: Iterative Crash Resolution

Type: Bug fix — critical kernel crashes in the NFS client related to directory delegation state recovery.

Background (Prior Weeks)

This thread traces back to Anna Schumaker's original patch Fix directory delegation verifier checks, submitted December 19, which aimed to optimize directory delegation verifier handling for performance. Christoph Hellwig reported that applying this patch led to kernel Oops crashes when running his delegation benchmarking script and the generic/633 xfstests test. On December 31, Trond Myklebust proposed an initial fix addressing nfs_clear_verifier_delegated() for delegated directories [id://53d40f4781783f9b79196bb30975b788be8bb969.camel@hammerspace.com].

This Week's Discussion (Jan 6–8, 2026)

First Crash Report: nfs_end_delegation_return Oops

On January 6, Christoph Hellwig reported that Trond's initial fix resolved the original crash but introduced a new one in generic/633:

"It does. But now generic/633 crashes reliably" [id://aVyp3SIddHB5sMhp@infradead.org]

The crash manifested as a general protection fault at nfs_end_delegation_return+0xda/0x390, triggered during a chown operation via the call path: chown_common → notify_change → nfs_setattr → nfs4_proc_setattr → nfs_end_delegation_return. The Oops indicated access to a non-canonical address (0xcccccccccccccd0c), suggesting use-after-free or uninitialized pointer corruption in delegation return handling.

First Iteration of Fix: Blocking State Recovery for Directories

Trond Myklebust responded with frustration but determination, proposing another patch while warning that persistent issues might necessitate disabling directory delegations entirely:

"Sigh... One last patch on top of all the previous ones, but if we hit another issue I think we need to consider just disabling directory delegations on the client until all the remaining issues can be fixed in the next release." [id://1df4bb7ff3e6fd607c1811d75fcd6dcb860e320e.camel@kernel.org]

The patch, titled "NFSv4.x: Directory delegations don't require any state recovery", addressed the core insight that the state recovery code in nfs_end_delegation_return() was designed for regular files (to recover cached open and lock state) but had "no function for directory delegations, and may cause corruption." Trond also asked Anna Schumaker:

"Anna, are you able to reproduce these bugs?" [id://1df4bb7ff3e6fd607c1811d75fcd6dcb860e320e.camel@kernel.org]

Second Crash Report: nfs_inode_find_state_and_recover Oops

Christoph tested the new patch and reported it still crashed generic/633, this time at a different location:

"This still crashes generic/633" [id://aV3ttYmT2vAtPDws@infradead.org]

The new Oops occurred in nfs_inode_find_state_and_recover+0x9c/0x260, called from nfs4_delegreturn_done via the RPC async workqueue. The crash again involved a non-canonical address (0xcccccccccccccd50), indicating that the state recovery path was still being exercised for directory delegations in a code path not covered by Trond's first patch.

Second Iteration of Fix: Completing the State Recovery Block

Trond acknowledged the incompleteness of his fix and provided an incremental patch, noting:

"Thanks for doing all this testing, Christoph. I really appreciate it. The previous patch was incomplete." [id://d8ddd23a18985ae360855931f185d0e24c466310.camel@kernel.org]

The follow-up patch, "NFSv4.x: Directory delegations don't require any state recovery (part 2)", addressed the second crash site in nfs_inode_find_state_and_recover(). Trond clarified his integration plan:

"This is incremental to yesterday's patch, but I'll squash them together in the testing branch, since they're both about blocking state recovery in the non-regular file case." [id://d8ddd23a18985ae360855931f185d0e24c466310.camel@kernel.org]

Resolution and Remaining Concerns

Christoph confirmed the combined fix resolved the crash:

"This fixes generic/633. I've kicked off a full xfstests run and will report back." [id://aV58KBha24bpbLUf@infradead.org]

Anna Schumaker then weighed in with her own testing results, revealing a version-specific nuance:

"I finally hit Christoph's crasher this morning, and this patch did help when running with NFS v4.1 but I still see the problem with v4.2. I haven't dug into it enough to know if it's just harder to hit now, though." [id://0bc24199-7e23-4419-bc70-17ad4bebd690@oracle.com]

She offered to take over debugging:

"Do you want me to take back over debugging this from here?" [id://0bc24199-7e23-4419-bc70-17ad4bebd690@oracle.com]

In his final message of the week, Christoph reported positive results from the full xfstests suite but flagged a separate regression:

"xfstests survives without crashing. However since 6.19-rc a bunch of timestamp related tests keep failing." [id://aV93q3w00seoH5xC@infradead.org]

Key Technical Arguments and Conclusions

  1. Root Cause: The NFS client's state recovery infrastructure in nfs_end_delegation_return() and nfs_inode_find_state_and_recover() was designed for regular file delegations (recovering open/lock state). When applied to directory delegations, these code paths accessed invalid memory, causing kernel crashes.

  2. Fix Strategy: Two complementary patches were needed to block state recovery for non-regular file delegations at both the delegation return completion path and the inode state recovery lookup path. These will be squashed into a single commit.

  3. Open Question: Anna's observation that the crash persists with NFS v4.2 (but not v4.1) suggests there may be additional code paths or protocol differences between versions that need investigation. This remains unresolved at week's end.

  4. Contingency Plan: Trond indicated willingness to disable directory delegations on the client entirely if further issues emerged, underscoring the severity of the bugs introduced by the directory delegation feature (commit 156b09482933).
