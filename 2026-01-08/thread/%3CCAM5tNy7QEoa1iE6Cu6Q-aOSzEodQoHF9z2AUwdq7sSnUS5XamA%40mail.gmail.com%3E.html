NFSv4.2 POSIX ACL Capability Detection Design Decision

Summary

NFSv4.2 POSIX ACL Client Development: Resolving Capability Bit Exhaustion

Classification: New feature (protocol extension implementation)

This thread is a brief but important side discussion in the broader effort to bring NFSv4.2 POSIX draft ACL support to the Linux NFS client. Rick Macklem, the primary developer of this feature, raised a design question about how to signal server capability for the new POSIX ACL extension, given that all existing NFS_CAP_xxx bits were already consumed. The exchange with NFS client maintainer Trond Myklebust resulted in a clear architectural decision that shaped the subsequent patch series.

Background

Rick Macklem initiated this RFC on January 1, 2026, while cleaning up the client-side implementation of the NFSv4.2 POSIX draft ACL extension:

"I'm trying to clean up the client side of the NFSv4.2 patches that implement the POSIX draft ACL extension. I need to set a 'server->caps' bit to indicate that the NFS server supports POSIX draft ACLs." Rick Macklem

The existing NFS_CAP_ACLS bit was already in use to indicate NFSv4 ACL support, leaving no room for a new capability flag. Rick followed up with a straightforward proposal:

"Oh. I forgot to ask if the simple answer of bumping the 'caps' field of 'struct nfs_server' to 64bits is ok to do?" Rick Macklem

Key Technical Argument: Avoiding Redundant Sources of Truth

Trond Myklebust, Linux NFS client maintainer, provided a decisive architectural recommendation. Rather than expanding the capability bitmask or adding new bits, he advised checking the server's attribute bitmask directly — the mechanism already used for other NFSv4 features:

"For features that are implemented through new NFSv4 attribute types, it is better to check server->attr_bitmask[] directly rather than add new bits to server->caps. For one thing, that means we don't have to keep several different sources of truth in synch." Trond Myklebust

Trond also pointed out that NFS_CAP_ACLS is now primarily used by the NFSv3 ACL code, and directed Rick to the existing function nfs4_server_supports_acls() as the appropriate mechanism for checking ACL support.

Resolution and Evolution

Rick initially attempted to make nfs4_server_supports_acls() a global function callable from nfs_get_tree_common() to conditionally set the SB_POSIXACL superblock flag. However, this approach hit a circular dependency issue:

"Actually, the above didn't quite work, because it resulted in the nfs module depending on the nfsv4 one (and vice versa)." Rick Macklem

He resolved this by placing the capability tests directly in super.c, avoiding the inter-module dependency. This final approach was reflected in the patch series posted later that day (PATCH v1 6/7), which sets SB_POSIXACL when both POSIX draft default and access ACL attributes are supported by the server.

Final Conclusions

The discussion concluded with a clear architectural principle for NFS client development: new NFSv4 features implemented through attribute types should be checked via server->attr_bitmask[] rather than introducing new capability bits. This approach:

  1. Avoids exhausting the limited NFS_CAP_xxx bitmask space
  2. Eliminates redundant sources of truth that must be kept synchronized
  3. Leverages existing infrastructure for feature detection

This decision directly informed the structure of the NFSv4.2 POSIX ACL client patch series, which was posted on January 2, 2026, and represents a significant new feature enabling native POSIX ACL support over NFSv4.2 without lossy translation.
