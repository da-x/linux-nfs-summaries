NFSv4.2 POSIX ACL Client: Build Failures on Patch 5/7 Due to Missing Server Dependency

Summary

Build Failures in NFSv4.2 POSIX ACL Client Series — Patch 5/7

Classification: New feature (build error feedback)

This thread captures automated build failure reports against patch 5/7 of Rick Macklem's seven-patch series introducing client-side support for the NFSv4.2 POSIX draft ACL extension. The broader series, posted on January 2 (see prior summary), adds a sideband protocol allowing POSIX draft ACLs to be acquired and set directly over NFSv4.2, bypassing the lossy NFSv4-to-POSIX ACL mapping algorithm.

Build Errors Reported by 0-DAY CI

On January 3, the kernel test robot (lkp@intel.com) reported build failures for patch 5/7 ([PATCH v1 5/7] Make nfs4_server_supports_acls() global) under two different configurations and compilers:

Clang Build (x86_64-kexec config)

The first report, using clang version 20.1.8, identified two undeclared identifier errors in fs/nfs/nfs4proc.c:

"error: use of undeclared identifier 'FATTR4_WORD2_POSIX_DEFAULT_ACL'" kernel test robot

"error: use of undeclared identifier 'FATTR4_WORD2_POSIX_ACCESS_ACL'" kernel test robot

The problematic code in nfs4_server_supports_acls() attempts to check server capability bitmask for POSIX ACL support:

case NFS4ACL_POSIXDEFAULT:
    return server->attr_bitmask[2] & FATTR4_WORD2_POSIX_DEFAULT_ACL;
case NFS4ACL_POSIXACCESS:
    return server->attr_bitmask[2] & FATTR4_WORD2_POSIX_ACCESS_ACL;

A secondary warning was also noted: variable 'ptr' set but not used at line 9630.

GCC Build (x86_64-rhel-9.4 config)

The second report, using gcc-14, confirmed the same undeclared identifier errors and added a control-flow warning:

"error: 'FATTR4_WORD2_POSIX_DEFAULT_ACL' undeclared (first use in this function)" kernel test robot

"warning: control reaches end of non-void function [-Wreturn-type]" kernel test robot

The latter warning arises because the switch statement in nfs4_server_supports_acls() lacks a default return path when all cases are consumed but the compiler cannot prove exhaustiveness.

Root Cause: Missing Dependency Patch

Rick Macklem responded promptly, clarifying that the build failures stem from a missing dependency:

"The reason this happens is that this patch series requires the 0001 patch from the server series." Rick Macklem

The identifiers FATTR4_WORD2_POSIX_DEFAULT_ACL and FATTR4_WORD2_POSIX_ACCESS_ACL are defined in the server-side patch series (authored by Chuck Lever), which introduces the new NFSv4.2 POSIX draft ACL attribute bitmask definitions. The client series was designed to be applied after that server series, but the 0-DAY CI test infrastructure attempted to build the client patches independently against the base tree, where these definitions do not yet exist.

Macklem then posed a practical question about how to proceed:

"Should I repost with that patch including in this set as well?" Rick Macklem

Technical Significance

This exchange highlights a common challenge in kernel development when implementing protocol extensions that span both client and server code:

  1. Interdependent patches: The client-side capability check (nfs4_server_supports_acls()) references bitmask constants defined only in the server series, creating a hard dependency between the two patch sets.

  2. Automated testing gaps: The 0-DAY CI system correctly identified the build failure but could not resolve the dependency ordering issue on its own. This is a known limitation when patches reference symbols introduced in companion series.

  3. Impact on POSIX ACL support: Resolving this dependency is essential for the broader NFSv4.2 POSIX ACL feature, which would enable getfacl(1)/setfacl(1) to work transparently over NFSv4.2 mounts without lossy translation — a significant improvement for enterprise environments relying on fine-grained access control.

Conclusion

No final resolution was reached within this reporting week. The thread ended with Rick Macklem's question about whether to incorporate the server-side dependency patch into the client series. This represents an open action item for the next version of the patch set. The build failures themselves are not indicative of a logic error in the client code, but rather a missing header definition from the companion server series.
