NFSv4.1 Migration Bug: Stale Session Credentials Cause Kernel Panic

Summary

Bug Report: Stale Session Credentials During NFSv4.1 Transparent State Migration

Overview

This week, Wonju Ka of Kakao Corp. reported a critical bug in the Linux NFS client's handling of NFSv4.1 transparent state migration. The issue manifests as a kernel panic caused by a use-after-free condition when in-flight RPC requests are retried with stale session credentials after migration completes.

Problem Classification: Bug Fix

This is a bug report (not a new feature or protocol change). The reporter identified a race condition in the NFS client's migration path that leads to data corruption and kernel panics under heavy I/O load during server-to-server state migration.

Technical Details

The bug occurs when the NFSv4.1 client performs a transparent state migration while many WRITE operations are in-flight (all 16 session slots fully utilized). As described by Wonju Ka, the problematic sequence unfolds as follows:

"During migration, when many WRITE operations are in-flight (16 slots fully utilized), the following sequence occurs:

  1. Client detects LEASE_MOVED flag from source server
  2. Client performs migration recovery (FS_LOCATIONS, CREATE_SESSION on target)
  3. Migration completes - nfs_server now points to target server's nfs_client
  4. rpc_xprt is switched to target server connection
  5. In-flight RPCs on source connection receive NFS4ERR_BADSESSION
  6. These RPCs are retried using the NEW transport (target server) but with OLD session credentials (source server's session ID)
  7. Target server receives requests with foreign session ID -> "client not found"
  8. Eventually leads to use-after-free panic"

The core issue is that when rpc_switch_client_transport() switches the RPC transport to the target server, pending RPC tasks retain their original session credentials from the source server. When these tasks are retried after failing on the old connection, they arrive at the target server with the source server's session ID — a credential mismatch that the target cannot resolve.

Evidence and Timeline

The reporter provided detailed logs showing the exact sequence of events:

"07:28:57.069 LEASE_MOVED flag detected (source server) 07:28:58.251 CREATE_SESSION on target (new ClientID: 2:1767652138) 07:28:58.252 RECLAIM_COMPLETE 07:28:58.5xx WRITEs still processing on source (session 5:1767650393:0:1) 07:28:58.5xx New WRITEs on target (session 2:1767652138:0:1) 07:28:59.248 Target receives request with SOURCE session ID! ERROR: client not found {"clientId": "5:1767650393", "sessionId": "5:1767650393:0:1"} 07:28:59.489 PANIC: "refcount_t: addition on 0; use-after-free""

The target server logs confirm that requests arrived on the target connection port (59244) rather than the source port (56768), proving that the transport was correctly updated but session credentials were not.

Kernel Panic Trace

The bug culminates in a kernel panic with a use-after-free error:

"refcount_t: addition on 0; use-after-free. WARNING: CPU: 7 PID: 33665 at lib/refcount.c:25 refcount_warn_saturate+0x9f/0x150 Workqueue: rpciod rpc_async_schedule [sunrpc] Call Trace: nfs4_schedule_state_manager+0x... nfs4_schedule_session_recovery+0x... nfs41_sequence_process+0x... nfs4_sequence_done+0x... nfs4_write_done+0x..."

Root Cause Analysis

Wonju Ka identifies the root cause:

"In fs/nfs/nfs4state.c, nfs4_try_migration() switches the nfs_server to point to the new nfs_client and updates the RPC transport. However, RPC tasks that are already in-flight retain references to the old session."

The session ID embedded in the SEQUENCE operation comes from the rpc_task's credentials, which were established before migration began and are not refreshed when the transport is switched.

Proposed Fix Directions

The reporter suggests three potential remediation strategies:

"1. Drain all in-flight RPCs before completing migration 2. When retrying failed RPCs after migration, refresh session credentials 3. Mark pending RPCs for re-authentication after transport switch"

Related History

The reporter notes that this issue is related to a previously reported problem on the mailing list, indicating this may be a long-standing or recurring class of bugs in the NFSv4.1 migration path.

Current Status

This thread contains only the initial bug report as of this week. No responses from maintainers (Trond Myklebust, Chuck Lever, Anna Schumaker, or others) have been recorded yet. The community awaits further discussion on which fix direction is most appropriate and whether a patch will be submitted.

Significance for NFS Client Development

This bug highlights a subtle but dangerous race condition in the NFSv4.1 client's state migration implementation. It affects systems relying on transparent server failover or load balancing, where session state must be migrated between servers without disrupting clients. The use-after-free panic represents a serious reliability concern that could lead to data loss or system crashes in production environments using NFSv4.1 with pNFS or clustered server deployments.
