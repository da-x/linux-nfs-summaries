NFSD Asynchronous Write Throttling RFC Review — Focus on Patch 2/2

Summary

NFSD: Asynchronous Write Throttling for UNSTABLE WRITEs — RFC v1 Review

Overview

This thread covers Christoph Hellwig's review of Chuck Lever's two-patch RFC series (v1, originally posted December 19, 2025) proposing new write throttling mechanisms for the NFS server. The discussion is classified as a new feature aimed at preventing NFSD meltdown conditions caused by write-intensive client workloads. Mike Snitzer also joined the conversation to offer testing support.

Background (Prior Week)

Chuck Lever originally posted this RFC series on December 19, 2025, following up on an earlier observation about NFSD instability:

"Client workloads that are write-intensive can sometimes trigger an NFSD meltdown (thrashing, livelocking, or becoming unresponsive). This can happen when clients present NFSD with more UNSTABLE WRITEs than can fit in the server's physical memory, and the system simply can't get those dirty pages onto persistent storage fast enough."

As described by Chuck Lever

The two-patch series proposed:

  • Patch 1/2: A debugfs-controlled "aggressive write throttling" mode that reduces nr_dirtied_pause to force more frequent calls to balance_dirty_pages(), providing 4x more frequent throttling on systems with 4KB pages.
  • Patch 2/2: Asynchronous write throttling using the BDP_ASYNC flag, which returns NFS4ERR_DELAY (or NFSERR_JUKEBOX for NFSv3) to clients when memory is exhausted, rather than blocking server threads in sleep.

Lever characterized these as "crazy ideas" intended as conversation starters.

This Week's Discussion (January 7, 2026)

Christoph Hellwig's Initial Skepticism on Patch 1/2

Hellwig opened with fundamental questions about the need for NFSD-specific throttling:

"What makes NFSD so special here vs say a userspace process with a bunch of threads? Also what is the actual problem we're trying to solve?"

As questioned by Christoph Hellwig

He expressed concern about introducing NFSD-specific mechanisms when the underlying issue might be more general:

"I kinda hate having this stuff in NFSD when there's nothing specific about nfs serving here."

As stated by Christoph Hellwig

Chuck Lever's Response: UNSTABLE WRITE as a Denial-of-Service Vector

Lever clarified the core problem:

"The problem, as I see it, is that the system is not providing enough backpressure to slow down noisy clients, allowing them to overwhelm the server's memory with UNSTABLE WRITE traffic."

As explained by Chuck Lever

He drew a parallel to related work:

"This is the same issue, IMO, that Mike's direct I/O is attempting to address. Our implementation of UNSTABLE WRITE is a denial-of-service vector."

As characterized by Chuck Lever

Lever acknowledged the patches were not yet in mergeable shape:

"Don't worry too much about that, these patches are obviously not in any kind of merge-able shape yet. We do need to understand the metabolism of UNSTABLE WRITEs, in particular, to get a clear picture of what needs to be controlled to make the server autonomously stable."

As conceded by Chuck Lever

Hellwig's Follow-Up: Comparison to Samba and Userspace NFS Servers

Hellwig pressed further on the universality of the problem:

"But how is this different from Samba or a userspace NFS server?"

As questioned by Christoph Hellwig

Lever responded that the answer was still unknown:

"Well it might not be different. But at this point I don't think we know enough about the problem to say one way or another. I'm just trying to gather more experimental evidence about what is happening."

As stated by Chuck Lever

Hellwig's Feedback on Patch 2/2: debugfs Concerns and Request for Data

On the second patch, Hellwig reiterated his strong preference against debugfs-gated features:

"Let me reiterate that I really, really hate all this magic debugs-fs enabled features. Either they are genuinely useful (think this would be such a thing) and they should be enabled unconditionally, or they are tradeoffs and should have a proper tunable not hidden in debugfs."

As stated by Christoph Hellwig

He acknowledged the concept was useful but demanded empirical validation:

"This all seems very useful to me. But it really needs to show numbers on how it helps."

As emphasized by Christoph Hellwig

He also flagged a minor code style issue:

"Overly lone line."

As noted by Christoph Hellwig

Chuck Lever's Response on Patch 2/2: Experimental Nature and Testing Plans

Lever defended the use of debugfs as appropriate for an experimental RFC:

"The use of debugfs here is because we don't yet have a coherent design in mind -- this new facility is entirely experimental, and we need a way to enable and disable it to make good comparisons, without making immutable changes to the actual NFSD administrative interface."

As explained by Chuck Lever

He added a wry note:

"The RFC sign out front should have told ya."

As quipped by Chuck Lever

But concurred with the long-term goal:

"But I agree, in the long term I most prefer no new administrative controls -- it should just work if at all possible."

As agreed by Chuck Lever

Lever offered to focus on patch 2/2 and drop or postpone patch 1/2:

"I'm happy to run with this one and drop (or postpone) 1/2, if that is your assessment."

As proposed by Chuck Lever

He also mentioned potential testing collaboration:

"Well if I can get this into operational shape, perhaps J. Flynn would be interested in trying it out for us."

As suggested by Chuck Lever

Hellwig's Clarification: Patch 2/2 Makes Sense, Patch 1/2 Does Not

Hellwig clarified his position on the two patches:

"I don't really understand what exactly patch 1 is aiming for. Not stalling nfsd threads when congested makes total sense on the other hand."

As concluded by Christoph Hellwig

Mike Snitzer's Support and Testing Offer

Mike Snitzer, who had been working on related direct I/O improvements, offered concrete testing support:

"Probably a good start. Definitely looks useful and worth measuring to see if buffered IO improves."

As assessed by Mike Snitzer

He committed to providing a test kernel for real-world evaluation:

"I can include it in a test kernel for Jon Flynn once you're happy with the patch and would like further testing (fyi I've rebased to latest 6.18-stable but Jon hasn't done baseline testing of it yet, so we could kill 2 birds once ready)."

As offered by Mike Snitzer

Snitzer also summarized the emerging consensus:

"Also patch 1/2, but consensus seems to be 'focus on 2/2 first'"

As observed by Mike Snitzer

Significance for NFS Client Development

While this series targets the NFS server, it has direct implications for NFS clients:

  1. Client backpressure: The async throttling mechanism returns NFS4ERR_DELAY to NFSv4 clients and NFSERR_JUKEBOX to NFSv3 clients, prompting them to back off and retry — a standard protocol behavior that clients already handle. This prevents server-side thread exhaustion from cascading into complete unresponsiveness for all clients.

  2. NFSv2 limitation: Async throttling is automatically disabled for NFSv2 requests since the protocol lacks NFSERR_JUKEBOX, meaning NFSv2 clients will not benefit from this protection.

  3. Production testing opportunity: Jon Flynn's real-world workload testing (facilitated by Mike Snitzer) could provide valuable data on how these throttling mechanisms affect client-side performance and stability under heavy write loads.

Conclusions

  • Patch 1/2 received a lukewarm reception: Hellwig did not understand its purpose and questioned whether NFSD-specific aggressive throttling is warranted.
  • Patch 2/2 was viewed more favorably: Hellwig acknowledged the concept of avoiding thread stalls during congestion "makes total sense," but demanded empirical numbers demonstrating benefit.
  • Consensus emerged to focus on patch 2/2 first, with patch 1/2 to be dropped or postponed.
  • debugfs gating is a temporary measure: Both participants agreed the feature, if proven useful, should eventually either be enabled unconditionally or exposed through proper administrative interfaces — not hidden in debugfs.
  • Testing path established: Mike Snitzer committed to providing a test kernel for Jon Flynn's evaluation once Chuck Lever finalizes patch 2/2.
  • A v2 of the series (focusing on async write throttling) was subsequently posted on January 9, 2026, outside this week's window.
