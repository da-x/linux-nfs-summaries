NFS/localio: Fixing Data Corruption and Short Write Handling

Summary

NFS/localio: Fixing Data Corruption and Short Write Handling

Trond Myklebust submitted a four-patch series titled "Fix misc localio issues" to address critical bugs in the NFS LOCALIO (local I/O) subsystem. LOCALIO allows an NFS client to bypass network RPC when the server is on the same host, directly accessing the underlying filesystem. The series was motivated by two primary concerns:

"Data corruption when localio hits a transient error." "Short write handling can trigger spurious ENOSPC errors"

As outlined in the cover letter, the patches target fs/nfs/localio.c with 66 insertions and 40 deletions. Mike Snitzer, a key reviewer and contributor to LOCALIO development, provided thorough reviews and reviewed-by tags for all four patches.

Patch 1: Stop Further I/O Upon Hitting an Error

The first patch addresses a bug where the localio code would continue issuing I/O after encountering an error from the underlying filesystem. Trond explained:

"If the call into the filesystem results in an I/O error, then the next chunk of data won't be contiguous with the end of the last successful chunk. So break out of the I/O loop and report the results."

This patch fixes a regression introduced by commit 6a218b9c3183. Mike Snitzer noted that the patch needed rebasing against Linus's master due to a more recent fix for an out-of-order __put_cred regression. He provided a rebased version with his reviewed-by tag in his reply, praising the cleanup:

"Thanks, definitely cleaner to not have the awkward force_done flag, sorry for that nastiness."

Trond confirmed he had already caught the rebase issue in his testing branch in response.

Patch 2: Deal with Page Bases Larger Than PAGE_SIZE

The second patch fixes an issue where the page base could grow larger than PAGE_SIZE during request resends. Trond noted:

"When resending requests, etc, the page base can quickly grow larger than the page size."

Mike Snitzer reviewed this patch and reflected on the origin of the bug:

"This was bound to happen given the 'No functional change.' in the header for commit 091bdcfcece0 -- wasn't purely a refactor, ugh. Should the implications of not having this fix be made clearer in this patch header?"

He added his reviewed-by tag in his reply.

Patch 3: Handle Short Writes by Retrying

The third and most complex patch addresses short write handling. Previously, the localio code would truncate I/O on a short write and set an error, risking data loss since the partially written data might not be persisted. Trond explained:

"To fix this, change localio so that the upper layers can direct the behaviour to persist any unstable data by rewriting it, and then continuing writing until an ENOSPC is hit."

Mike Snitzer raised two concerns in his review here: whether a code comment should be added to nfs_local_pgio_release() explaining the subtle dependency on rpc_call_done conditionally setting task->tk_action, and whether a default case in a switch statement warranted a BUG_ON(). Trond responded in his reply:

"That's how restarts work in the RPC code: after the rpc_call_done callback is done, rpc_exit_task() will check for whether or not the task->tk_action got reset, and if so, it will prepare a new RPC call."

Regarding the BUG_ON() question, he added:

"I considered a BUG_ON(), but it shouldn't really matter. All this does now is cancel the restart."

Mike Snitzer accepted this reasoning and provided his reviewed-by tag in his final reply.

Patch 4: Cleanup nfs_local_pgio_done() Parameters

The final patch removes a redundant force parameter from nfs_local_pgio_done(), a straightforward cleanup. Mike Snitzer provided his reviewed-by tag in his reply.

Follow-Up: Additional LOCALIO Improvements

On January 7, Mike Snitzer posted a follow-up series titled "NFS/localio: various improvements" here, rebased on Trond's patchset. He revealed that his patches were developed while chasing a severe deadlock under heavy LOCALIO load on systems with limited memory (16GB). The deadlock involved khugepaged and nfsd tasks stuck in wait_on_commit, ultimately resolved by a separate nfs_release_folio() deadlock fix from Trond. Snitzer noted:

"Anyway, I think this LOCALIO series is worthwhile on its own and ready for wider review and hopeful inclusion."

Conclusion

This thread represents a focused bug-fix effort to harden the NFS LOCALIO subsystem against data corruption and spurious errors. All four of Trond's patches received reviewed-by tags from Mike Snitzer after constructive discussion around rebase requirements, code clarity, and edge-case handling. The follow-up series from Snitzer further demonstrates ongoing investment in LOCALIO stability under stress conditions.
