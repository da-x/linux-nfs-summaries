Re-enable IOCB_NOWAIT Writes to Files v5: Non-Blocking Timestamp Updates

Summary

Re-enable IOCB_NOWAIT Writes to Files (v5)

Christoph Hellwig posted version 5 of his series to re-enable IOCB_NOWAIT writes to files, addressing a performance regression introduced by commit 66fa3cedf16a ("fs: Add async write file modification handling."). The series consists of 11 patches that refactor the VFS timestamp update infrastructure and add non-blocking lazytime support, with XFS as the first filesystem implementation.

Background: The IOCB_NOWAIT Problem

The cover letter explains the core issue:

"commit 66fa3cedf16a ("fs: Add async write file modification handling.") effectively disabled IOCB_NOWAIT writes as timestamp updates currently always require blocking, and the modern timestamp resolution means we always update timestamps. This leads to a lot of context switches from applications using io_uring to submit file writes, making it often worse than using the legacy aio code that is not using IOCB_NOWAIT."

The series aims to allow non-blocking timestamp updates for lazytime when the filesystem supports it, thereby restoring the performance benefits of IOCB_NOWAIT for io_uring-based workloads.

Series Structure

The 11-patch series progresses through several stages:

  1. Patches 01–03: Preparatory VFS cleanup — removing inode_update_time, allowing error returns from generic_update_time, and splitting NFS's nfs_update_timestamps.
  2. Patch 04: FAT-specific flag cleanup for fat_truncate_time.
  3. Patches 05–07: Core refactoring of ->update_time handling, factoring out a sync_lazytime helper, and adding a new ->sync_lazytime filesystem method.
  4. Patch 08: The key feature — adding support for non-blocking timestamp updates by passing IOCB_NOWAIT to ->update_time.
  5. Patches 09–11: Further refactoring of file_update_time_flags, and XFS-specific implementations of ->sync_lazytime and non-blocking timestamp updates.

NFS Client Development: Splitting nfs_update_timestamps

The most NFS-relevant change is Patch 03/11, which splits nfs_update_timestamps into separate paths for atime updates versus ctime/mtime updates:

"The VFS paths update either the atime or ctime and mtime but never mix between atime and the others. Split nfs_update_timestamps to match this to prepare for cleaning up the VFS interfaces."

This patch was reviewed positively by both Jan Kara and Jeff Layton:

  • Jan Kara: "Looks good. Feel free to add: Reviewed-by: Jan Kara"
  • Jeff Layton: "Reviewed-by: Jeff Layton"

The NFS client's nfs_update_timestamps is also updated in Patch 05/11 to use the new enum-based update type interface instead of the legacy S_* flags, aligning it with the broader VFS refactoring.

Key Technical Discussions and Bug Fixes

Timestamp Sampling Order Bug (Patch 05/11)

Jan Kara identified a critical bug in the refactored inode_update_cmtime() function:

"This needs to be below sampling of ctime. Otherwise inode dirtying will be broken..."

The issue was that inode_set_ctime_current() must be called after sampling the current ctime value, not before. Christoph acknowledged and fixed this: "Fixed."

Jeff Layton corroborated: "I think Jan is correct though that you need to sample those in reverse order."

FAT Bisectability Concern (Patch 04/11)

OGAWA Hirofumi flagged a bisectability issue:

"This breaks fat_update_time() by calling fat_truncate_time() with old S_* flags (later patch looks like fixing though). Please add the commit comment about it, or fix it in this patch."

OGAWA later retracted his concern after noticing the new values reuse the same numeric values as S_*, granting an Acked-by. However, Christoph took additional precautions:

"Still not a good idea to not create a bisection hazard. I've added a local fat_flags variable and a translation for this patch, even if that will go away in the next patch to be 100% sane." Christoph Hellwig

Documentation Nit (Patch 05/11)

Jeff Layton noted a documentation inconsistency: "nit: these are int return in the code, but are documented as void return here. Can you fix that up while you're in here?"

Non-Blocking Timestamp Updates (Patch 08/11)

The centerpiece of the series is Patch 08/11, which enables non-blocking timestamp updates:

"Currently file_update_time_flags unconditionally returns -EAGAIN if any timestamp needs to be updated and IOCB_NOWAIT is passed. This makes non-blocking direct writes impossible on file systems with granular enough timestamps."

Both Jan Kara and Jeff Layton provided positive reviews, with Jan noting: "Much nicer now! Thanks for the refactoring."

XFS Implementation (Patches 10–11/11)

The series concludes with XFS-specific patches that implement ->sync_lazytime and enable non-blocking timestamp updates. The final patch carries a Fixes: tag pointing to the original regression:

"The lazytime path using the generic helpers can never block in XFS because there is no ->dirty_inode method that could block."

Changes Since Prior Versions

The cover letter summarizes the evolution across versions:

  • v5: Replaced S_* flags with an enum to fix a bug and reduce fragility.
  • v4: Fixed was_dirty_time handling, refactored inode_update_timestamps, allowed non-blocking updates for FAT.
  • v3: Dropped merged patches, adjusted for inode state accessors, fixed XFS blocking behavior and race conditions.

Conclusion

This is a feature-enabling series with significant bug-fix implications. It restores IOCB_NOWAIT write performance for io_uring applications by introducing non-blocking lazytime timestamp updates. The NFS client receives targeted refactoring to align its nfs_update_timestamps with the new VFS interface, though NFS itself does not yet implement non-blocking timestamp updates in this series — that remains future work. All patches received positive reviews from key filesystem maintainers (Jan Kara, Jeff Layton), and Christoph addressed identified bugs promptly.
