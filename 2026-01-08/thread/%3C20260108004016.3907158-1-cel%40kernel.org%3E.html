Summary

Automatic NFSv4 State Revocation on Filesystem Unmount (v2)

Overview

This week, Chuck Lever submitted version 2 of a six-patch series that introduces automatic NFSv4 state revocation when an underlying filesystem is unmounted. This is classified as a new feature for the NFS server (NFSD), addressing a long-standing operational pain point: when clients hold NFSv4 opens, locks, or delegations on an exported filesystem, unmounting fails with EBUSY, requiring administrators to manually invoke /proc/fs/nfsd/unlock_fs.

The series leverages the kernel's existing fs_pin infrastructure — previously used only by BSD process accounting — to detect mount teardown events and trigger cleanup. This is a significant architectural change that touches both VFS core code and NFSD internals, with implications for containerized NFS servers, orchestration systems, and unattended maintenance scripts.

As Chuck Lever explained in the cover letter:

"Manual intervention breaks automation workflows. Containerized NFS servers, orchestration systems, and unattended maintenance scripts cannot reliably unmount exported filesystems without implementing custom logic to detect the failure and invoke unlock_fs." Chuck Lever

Patch Series Breakdown (v2)

Patch 1/6: Cancel async COPY operations on admin revocation

This patch extends the existing unlock_fs mechanism to also cancel ongoing asynchronous NFSv4 COPY operations, which hold copy stateids representing NFSv4 state. Each cancelled copy triggers a CB_OFFLOAD callback carrying NFS4ERR_ADMIN_REVOKED to notify the client. The static drop_client() function is renamed to nfsd4_put_client() and exported for use by both the new cancellation path and the CB_OFFLOAD release callback.

"Async COPY operations hold copy stateids that represent NFSv4 state. Thus, when the NFS server administrator revokes all NFSv4 state for a filesystem via the unlock_fs interface, ongoing async COPY operations referencing that filesystem must also be canceled." Chuck Lever

Patch 2/6: Export pin_insert and pin_remove for modular filesystems

The existing fs_pin infrastructure provides unmount callbacks, but pin_insert() and pin_remove() lacked EXPORT_SYMBOL_GPL(), restricting the facility to built-in subsystems. This patch exports both symbols to permit modular filesystems like NFSD to register fs_pin callbacks:

"NFSD requires this to revoke NFSv4 delegations, layouts, and open state when the underlying filesystem is unmounted, preventing use-after-free conditions in the state tracking layer." Chuck Lever

Patch 3/6: Add pin_insert_sb() for superblock-only pins

A critical deadlock concern drove this addition. The standard mnt_pin_kill() callback runs during cleanup_mnt() with namespace locks held, but NFSD's state revocation path acquires these same locks for mount table lookups — creating an AB-BA deadlock risk. The new pin_insert_sb() registers pins on the superblock's s_pins list only, avoiding the problematic locking context:

"NFSD maintains NFSv4 client state associated with the superblocks of exported filesystems. Revoking this state during unmount requires lock ordering that conflicts with mnt_pin_kill() context." Chuck Lever

Patch 4/6: Invoke group_pin_kill() during mount teardown

Previously, group_pin_kill() was called only during remount read-only. This patch adds a call in cleanup_mnt() so that pins registered via pin_insert_sb() receive callbacks during mount teardown as well. An important side effect is noted:

"Because group_pin_kill() operates on the superblock's s_pins list, unmounting any mount of a filesystem—including bind mounts—triggers callbacks for all pins registered on that superblock. For NFSD, this means unmounting an exported bind mount revokes NFSv4 state for the entire filesystem, even if other mounts remain." Chuck Lever

Patch 5/6: Revoke NFSv4 state on filesystem unmount

The core patch of the series. An xarray in nfsd_net tracks per-superblock pins. When any NFS state is created, a pin is registered idempotently for that superblock. On unmount, the VFS invokes the kill callback, which queues work to:

  • Cancel ongoing async COPY operations (nfsd4_cancel_copy_by_sb)
  • Release NLM locks (nlmsvc_unlock_all_by_sb)
  • Revoke NFSv4 state (nfsd4_revoke_states)

The revocation runs on a dedicated workqueue (nfsd_pin_wq) to avoid deadlocks. Chuck Lever notes:

"If state revocation takes an unexpectedly long time (e.g., when re-exporting an NFS mount whose backend server is unresponsive), periodic warnings are emitted every 30 seconds." Chuck Lever

Patch 6/6: Close cached files on filesystem unmount

Even after NFSv4 state is revoked, the nfsd_file cache can hold open NFSv2/3 file handles that pin the filesystem. This patch extends the revocation mechanism to also close cached file handles belonging to the target superblock.

"When a filesystem is unmounted while NFS is exporting it, the unmount can fail with EBUSY even after NFSv4 state has been revoked." Chuck Lever

Key Technical Discussion

Jeff Layton's Alternative Proposal

Jeff Layton reviewed the series and raised an important architectural concern regarding the fs_pin infrastructure's long-term viability:

"One thing I want to point out here is that the only user of fs_pin is the BSD process accounting subsystem, which would be really nice to get rid of at some point." Jeff Layton

He suggested an alternative approach:

"An alternate idea might be to plumb an srcu notifier chain into the umount codepath, similar to the lease_notifier_chain in fs/locks.c. Then nfsd could register to be notified when there is a umount attempt and do the right thing to tear down state." Jeff Layton

This feedback points toward a potential v3 redesign that would decouple NFSD's unmount notification from fs_pin, which is slated for eventual removal once BSD process accounting is eliminated.

Changes Since v1

Chuck Lever noted several improvements over the initial submission:

  • Explained why drop_client() is being renamed
  • Finished implementing revocation on umount
  • Renamed pin_insert_group
  • Clarified log output and code comments
  • Hold nfsd_mutex while closing nfsd_files

Significance for NFS Development

This series represents a major quality-of-life improvement for NFS server administrators, particularly in containerized and automated environments:

  1. Elimination of manual state revocation: Administrators no longer need to manually invoke /proc/fs/nfsd/unlock_fs before unmounting exported filesystems. The server handles cleanup automatically.

  2. Client notification via standard error codes: Clients receive NFS4ERR_ADMIN_REVOKED through standard NFSv4 mechanisms, allowing applications to handle state loss gracefully rather than encountering silent failures.

  3. Comprehensive state cleanup: The series addresses all forms of state that can pin a filesystem — NFSv4 opens, locks, delegations, async COPY operations, NLM locks, and cached NFSv2/3 file handles.

  4. VFS integration: By extending fs_pin to support modular filesystems and superblock-only pins, this work lays groundwork for other subsystems that may need mount lifecycle notifications.

  5. Deadlock avoidance: The careful separation of pin_insert_sb() from mnt_pin_kill() demonstrates sophisticated understanding of VFS lock ordering constraints.

Conclusion

This v2 submission is a polished, well-reviewed feature addition to the NFS server stack. While Jeff Layton's feedback about fs_pin's eventual removal suggests potential architectural changes for future iterations, the current approach provides a functional and safe solution using existing kernel infrastructure. The series received Reviewed-by tags from both NeilBrown and Jeff Layton on the VFS patches, indicating strong maintainer support for the core mechanism.
