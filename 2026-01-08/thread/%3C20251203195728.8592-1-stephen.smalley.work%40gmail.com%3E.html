NFS Client: Unifying security_inode_listsecurity() Calls Merged

Summary

NFS Client: Unifying security_inode_listsecurity() Calls Merged

This thread concerns a bug fix and code cleanup in the NFSv4.2 client related to security extended attributes (xattrs). After over a month without objections, LSM maintainer Paul Moore announced he would merge Stephen Smalley's patch into the lsm/dev tree this week.

Background

The issue traces back to two prior commits in the NFS client:

  1. Commit 243fea134633 ("NFSv4.2: fix listxattr to return selinux security label") introduced a direct call to security_inode_listsecurity() in nfs4_listxattr().
  2. However, nfs4_listxattr() already indirectly called the same function via nfs4_listxattr_nfs4_label() when CONFIG_NFS_V4_SECURITY_LABEL was enabled and the server advertised NFS_CAP_SECURITY_LABEL.

A follow-up fix (commit 9acb237deff7, "NFSv4.2: another fix for listxattr") made the second call conditional on the server not having the security label capability. As Stephen Smalley explained:

"the combination of the two changes effectively makes one call to security_inode_listsecurity() in every case - which is the desired behavior since getxattr() always returns a security xattr even if it has to synthesize one."

Additionally, the two separate code paths produced inconsistent ordering of security.* versus user.* xattr names.

The Patch

Smalley's patch unifies the two separate calls into a single invocation and removes the now-redundant nfs4_listxattr_nfs4_label() function entirely. The change is a net reduction of 32 lines in fs/nfs/nfs4proc.c (3 insertions, 35 deletions).

Discussion Timeline

  • December 3, 2025: Stephen Smalley submitted the patch to the linux-nfs mailing list with full technical justification.
  • December 16, 2025: Paul Moore followed up, asking for feedback from NFS maintainers:

"NFS folks, any thoughts on this? We'd like to clean up the security_inode_listsecurity() interface (see the Link: metadata above), but we need to sort this out first."

  • January 6, 2026: With no objections or comments received over more than a month, Paul Moore announced the merge:

"It's been over a month without any comments, positive or negative, so I'm going to go ahead and merge this into lsm/dev; if anyone has any objections, ACKS, etc. please speak up soon."

Conclusion

The patch was merged into the lsm/dev tree without controversy. This cleanup simplifies the NFS client's handling of security xattrs by eliminating redundant code paths and ensuring consistent behavior regardless of server capabilities or compile-time configuration. The change also paves the way for broader cleanups to the security_inode_listsecurity() interface in the LSM subsystem.
