NFS Server refcount_t Underflow Debugging: nfsd4_sequence_done Crash on v6.18 Re-export

Summary

NFS Server refcount_t Underflow in nfsd4_sequence_done — Debugging Guidance for v6.18 Re-export Crash

Classification: Bug fix (ongoing investigation)

Summary

This thread, initiated on December 23, 2025, continues an ongoing investigation into a kernel crash affecting NFS server (NFSD) re-export deployments running Linux v6.18. The bug manifests as a refcount_t underflow in the NFSv4.1+ session sequence completion path (nfsd4_sequence_done), leading to a use-after-free warning and system instability. This week's activity focused on refining debugging methodology after initial trace data proved too voluminous to be practically useful.

Background (Prior Weeks)

The thread was opened by Daire Byrne, who reported intermittent kernel crashes after upgrading NFS re-export servers from v6.4 to v6.18.0:

"We recently upgraded our NFS re-export servers from a heavily patched (but stable) v6.4 kernel to pretty virgin v6.18.0. But we have started to record a fairly infrequent (once every 2 weeks) crash of the form: refcount_t: underflow; use-after-free." Daire Byrne

The crash occurs in the nfsd kernel thread, with a call trace pointing to nfsd4_sequence_done:

Call Trace:
  nfsd4_sequence_done+0x1d6/0x210 [nfsd]
  nfs4svc_encode_compoundres+0x50/0x60 [nfsd]
  nfsd_dispatch+0x111/0x210 [nfsd]

The environment is notable for its high throughput ("constant 50gbit") and re-export configuration, where NetApp NFSv3 mounts are re-exported as NFSv4 to Linux clients.

In the initial exchange (December 24), Chuck Lever advised against a full bisect given the two-week reproduction window, instead recommending kernel debug options (CONFIG_DEBUG_OBJECTS, CONFIG_KFENCE) and targeted ftrace tracepoints for session slot and client lifecycle events:

"Given the two-week reproduction window, bisecting would be painful, especially because it's difficult to tell if the problem is present and just not triggering." Chuck Lever

Daire Byrne confirmed the debugging infrastructure was deployed: "I have put this all in place so now we wait..." Daire Byrne

This Week's Activity (January 8, 2026)

Trace Data Volume Problem

On January 8, Daire Byrne reported that additional crashes had occurred but the ftrace buffer output was impractically large — approximately 8MB of text:

"So I have had a couple more of these, but I'm not entirely sure what to do with the ftrace buffer output - it's somewhat larger (8MB of text) than I anticipated." Daire Byrne

The dump revealed a critical issue: the trace buffer had lost over 4 million events, and the VM reset itself during the console dump before reaching the end of the buffer:

"[373929.683722] CPU:9 [LOST 4084645 EVENTS]"

The captured data consisted almost entirely of nfsd_slot_seqid_sequence tracepoint entries — one per NFSv4.1+ compound operation — which at 50 Gbps throughput saturates any reasonably-sized buffer.

Chuck Lever's Refined Debugging Recommendations

Chuck Lever responded with a comprehensive set of improved debugging strategies:

1. Buffer sizing and tracepoint filtering: He identified that the nfsd_slot_seqid_sequence tracepoint fires on every compound operation, making it too noisy for high-throughput environments:

"The 'LOST 4084645 EVENTS' message strongly suggests the trace data is incomplete -- the events immediately preceding the crash were likely among those lost. The nfsd_slot_seqid_sequence tracepoint fires on every NFSv4.1+ compound, which at 50 Gbps throughput will saturate any reasonably-sized buffer." Chuck Lever

He recommended:

  • Increasing the buffer size to 200MB per CPU
  • Disabling the high-volume nfsd_slot_seqid_sequence tracepoint
  • Enabling only client lifecycle events (nfsd_clid_expired, nfsd_clid_destroyed)

2. Single-CPU dump: To avoid the multi-gigabyte dump that caused the reboot timeout:

"Dump only the triggering CPU's buffer: echo orig_cpu > /proc/sys/kernel/ftrace_dump_on_oops" Chuck Lever

3. Direct refcount underflow capture via kprobe: A targeted approach to catch the exact moment of the underflow:

"Add a kprobe to catch the refcount underflow directly: echo 'p:kprobes/refcount_warn refcount_warn_saturate' > /sys/kernel/debug/tracing/kprobe_events" Chuck Lever

4. Extended panic timeout: To allow more time for trace buffer dumps:

"Extend panic timeout: echo 300 > /proc/sys/kernel/panic" Chuck Lever

Suspect Commits Identified

Chuck Lever narrowed the likely source of the regression to the session slot rework that landed in the v6.13/v6.14 timeframe, specifically highlighting four commits:

"the major changes landed in the v6.13/v6.14 timeframe: 0b6e14242630 ('nfsd: use an xarray to store v4.1 session slots'), 60aa6564317d ('nfsd: allocate new session-based DRC slots on demand'), fc8738c68d0b ('nfsd: add support for freeing unused session-DRC slots'), 35e34642b599 ('nfsd: add shrinker to reduce number of slots allocated per session')" Chuck Lever

He identified the slot freeing and shrinker commits as the most likely candidates:

"If bisection becomes necessary, I would start with the slot freeing and shrinker commits (fc8738c68d0b and 35e34642b599) as the most likely candidates given they add the most complexity to slot lifecycle management." Chuck Lever

Potential Fix Candidate

In a follow-up message, Chuck Lever pointed to an unmerged fix in his nfsd-testing branch that might be directly relevant:

"This fix: cbfd91d22776 ('nfsd: never defer requests during idmap lookup') has the possibility of being highly relevant." Chuck Lever

This commit addresses request deferral during ID mapping lookups, which could interact with the session slot lifecycle management in ways that trigger the refcount underflow.

Resolution Path Forward

Daire Byrne confirmed he had applied the refined ftrace debugging suggestions and planned to test the potential fix:

"I've applied (all) your recent ftrace debug suggestions so let's see if I can capture anything useful first and then I will try again with those patches to see if it makes any odds." Daire Byrne

Technical Significance

This bug represents a critical reliability issue for NFS server deployments, particularly those using re-export configurations at high throughput. The refcount_t underflow in nfsd4_sequence_done indicates a reference counting imbalance in the NFSv4.1+ session slot management code — likely introduced by the architectural changes to use xarray-based slot storage and on-demand allocation with shrinker support (v6.13/v6.14).

The investigation highlights several important aspects of kernel debugging at production scale:

  1. Tracepoint noise management: At 50 Gbps, even per-operation tracepoints can overwhelm buffers, losing the critical pre-crash context.
  2. Targeted kprobes: Direct instrumentation of refcount_warn_saturate provides a more surgical approach to capturing underflow events.
  3. Suspect commit narrowing: By identifying the session slot rework as the likely regression window, the bisect effort can be focused on a manageable set of commits rather than the full v6.4-to-v6.18 span.

Status

Open — under investigation. No root cause has been identified or fix merged. Daire Byrne is collecting improved trace data using Chuck Lever's refined debugging methodology and plans to test the candidate fix (cbfd91d22776) from the nfsd-testing branch. The thread remains active with follow-up messages expected in subsequent weeks.
