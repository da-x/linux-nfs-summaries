NFSD: Third Round of Fixes for Kernel 6.19 — UAF, Memory Leak, and Protocol Compliance

Summary

NFSD: Third Round of Fixes for Kernel 6.19

Overview

On January 6, 2026, NFS subsystem maintainer Chuck Lever submitted a third round of NFSD (NFS server) fixes targeting the Linux 6.19 kernel cycle. This pull request is classified as a set of bug fixes, not new features or protocol changes. The fixes address issues that emerged after the 6.19 merge window and include several items flagged for expedient stable backporting.

The pull request was promptly merged into Linus Torvalds's mainline tree, as confirmed by the PR tracker bot on January 6th pr-tracker-bot.

Fix Summary

The pull request encompasses six patches from five contributors, touching 11 files with 74 insertions and 34 deletions. Chuck Lever highlighted the following issues as requiring expedient stable backports:

"Issues that need expedient stable backports:

  • Remove an invalid NFS status code
  • Fix an fstests failure when using pNFS
  • Fix a UAF in v4_end_grace()
  • Fix the administrative interface used to revoke NFSv4 state
  • Fix a memory leak reported by syzbot" Chuck Lever

Individual Fixes

1. NFSD: Remove NFSERR_EAGAIN (Chuck Lever)

An invalid NFS status code NFSERR_EAGAIN was removed from the NFSD codebase. This cleanup eliminates a spurious error code that should not be returned to NFS clients, ensuring protocol compliance.

2. NFSD: net ref data still needs to be freed even if net hasn't startup (Edward Adam Davis)

This patch addresses a memory leak reported by syzbot. Network namespace reference data was not being properly freed in the case where the network subsystem had not yet started up, leading to leaked resources during NFSD initialization failure paths.

3. nfsd: provide locking for v4_end_grace (NeilBrown)

This patch fixes a use-after-free (UAF) bug in v4_end_grace(). The function lacked proper locking, which could lead to race conditions when NFSv4 grace period handling was invoked concurrently. This is a critical stability fix for NFSv4 server operations.

4. nfsd: use correct loop termination in nfsd4_revoke_states() (NeilBrown)

The administrative interface used to revoke NFSv4 state had an incorrect loop termination condition. This bug could prevent the proper revocation of stale or expired NFSv4 client state, impacting server-side state management and potentially leaving orphaned state entries.

5. nfsd: check that server is running in unlock_filesystem (Olga Kornievskaia)

This patch resolves an fstests failure when using pNFS. The unlock_filesystem function did not properly verify whether the NFS server was still running before attempting to release locks, leading to test failures and potential issues in production pNFS deployments.

6. NFSD: Fix permission check for read access to executable-only files (Scott Mayhew)

A permission-checking bug was fixed where the NFSD incorrectly evaluated read access on executable-only files. This ensures that clients receive accurate access control decisions from the server, maintaining proper security semantics.

Significance for NFS Client Development

While these fixes target the NFS server (NFSD), they have direct implications for NFS clients:

  1. Protocol compliance: The removal of NFSERR_EAGAIN ensures clients do not receive invalid error codes that could cause unexpected behavior or spurious retries.
  2. pNFS reliability: The fix to unlock_filesystem directly benefits pNFS clients by resolving fstests failures and improving lock management during server shutdown scenarios.
  3. State revocation correctness: Fixes to the NFSv4 state revocation interface ensure that client state is properly cleaned up, preventing stale state from interfering with new sessions.
  4. Permission semantics: The executable-only file permission fix ensures clients receive accurate access decisions, which is critical for security-sensitive workloads.
