Summary

NFSD: NFSv4 File Creation ACL Bug Fix Backported to 5.10.y Stable Tree

Overview

This week, Chuck Lever submitted a single-patch submission targeting the Linux 5.10 stable tree to address a bug in the NFS server (NFSD) where NFSv4 file creation operations neglect to set Access Control Lists (ACLs). This is classified as a bug fix, not a new feature or protocol change.

Background and Context

This submission is part of an ongoing effort to backport a critical ACL enforcement fix across multiple stable kernel branches. Earlier this week, Chuck Lever posted similar backports for the 6.6.y stable tree (see related summaries), which included a four-patch series addressing ACL omission, SELinux security label omission during create operations, and NFSv3 atomicity race conditions.

The 5.10.y backport is more straightforward, requiring only a single patch due to the simpler codebase in this older LTS branch.

The Bug Fix

On January 5th, Chuck Lever submitted the patch:

"An NFSv4 client that sets an ACL with a named principal during file creation retrieves the ACL afterwards, and finds that it is only a default ACL (based on the mode bits) and not the ACL that was requested during file creation. This violates RFC 8881 section 6.4.1.3: 'the ACL attribute is set as given'." Chuck Lever

Root Cause

The issue originates in nfsd_create_setattr(). The function checks whether nfsd_setattr() should be called, but on the 5.10.y branch (and similarly on 6.1.y), this check only accounts for standard iattr changes:

"On 6.1.y, the check to determine whether nfsd_setattr() should be called is simply 'iap->ia_valid', which only accounts for iattr changes. When only an ACL is present (and no iattr fields are set), nfsd_setattr() is skipped and the POSIX ACL is never applied to the inode." Chuck Lever

As a result, when an NFSv4 client creates a file with a POSIX ACL containing named principals, the server silently drops the ACL. When the client subsequently retrieves the ACL, the server returns a default ACL derived from the file's mode bits rather than the originally-specified ACL — a direct violation of RFC 8881.

The Fix

The patch is a minimal one-line change in fs/nfsd/vfs.c. Chuck Lever notes:

"[ cel: Adjust nfsd_create_setattr() instead of nfsd_attrs_valid() ]" Chuck Lever

The fix ensures that nfsd_setattr() is invoked even when only an ACL (and no other iattr fields) is present during file creation, thereby applying the POSIX ACL to the newly created inode.

Upstream Origin

The patch backports upstream commit 913f7cf77bf14c13cfea70e89bcb6d0b22239562 and traces its origin to the original fix for commit c0cbe70742f4 ("NFSD: add posix ACLs to struct nfsd_attrs"). The bug was originally reported by Aurelien Couderc.

Significance for NFS Client Development

While this patch targets the NFS server (NFSD), it has direct implications for NFS clients:

  1. ACL enforcement gap: Clients creating files with named-principal ACLs via NFSv4 would experience silent security policy violations, as the requested ACLs were never applied on the server side.
  2. RFC compliance: The bug constitutes a violation of RFC 8881 section 6.4.1.3, which mandates that "the ACL attribute is set as given" during file creation.
  3. Stable tree importance: The 5.10 LTS kernel remains widely deployed in production environments. This backport ensures that enterprise NFS deployments on older kernels benefit from this security and correctness improvement without requiring a full kernel upgrade.

Conclusion

This week's activity represents a targeted stable-tree backport to the 5.10.y branch, resolving an ACL enforcement gap in the Linux NFS server. The fix is minimal — a single-line change — but addresses a protocol compliance violation with significant security implications for NFSv4 clients relying on POSIX ACLs for fine-grained permission management over network-mounted filesystems.
