NFSD: SCSI Persistent Registration Fencing per Client with xarray — v6 Applied

Summary

NFSD: SCSI Persistent Registration Fencing per Client with xarray — v6 Applied

Overview

This thread marks the final resolution of a six-version patch series that addresses a correctness bug in the NFS server's pNFS block layout implementation. Authored by Dai Ngo and Chuck Lever, the patch introduces per-client tracking of SCSI persistent registration fencing using an xarray data structure. The v6 submission was posted on January 8th, received a review from Christoph Hellwig, and was promptly applied to the nfsd-testing tree — all within the same day.

This is classified as a bug fix for the NFS server's SCSI persistent reservation fencing logic in pNFS block layouts.

Background: The Problem

The core issue arises when an NFS client holding pNFS SCSI layouts becomes unresponsive. As described in the patch cover letter:

"When a client holding pNFS SCSI layouts becomes unresponsive, the server revokes access by preempting the client's SCSI persistent reservation key. A layout recall is issued for each layout the client holds; if the client fails to respond, each recall triggers a fence operation. The first preempt for a given device succeeds and removes the client's key registration. Subsequent preempts for the same device fail because the key is no longer registered." Chuck Lever

In practical terms, when a layout recall triggers fencing on an unresponsive client, the server attempts to preempt the client's SCSI persistent reservation key. The first such operation succeeds, but subsequent recalls for other layouts on the same device attempt to fence again — and fail, because the key was already removed by the first preempt. This results in unnecessary error conditions and potentially misleading log output.

Evolution of the Patch Series (Bridge from Prior Weeks)

The patch has evolved through six versions since its initial posting on December 26, 2025:

  • v1–v4 (December 26): Initial submission addressing memory allocation concerns, locking strategy (cl_fence_lock removed in favor of xa_lock), error handling for xa_store, and comment clarity. NeilBrown raised a semantic concern about the fenced flag representing a commitment to fence rather than a completed fence operation. Dai Ngo clarified:

"Yes, that is correct - it's either the device has been fenced or it's in the processed of being fenced." Dai Ngo

  • v5 (December 27): Addressed NeilBrown's feedback, improved the problem statement, handled pr_register/pr_reserve failures correctly, removed stale xa_state data usage, avoided looping on pr_preempt failure, and fixed CONFIG_SCSILAYOUT usage. Christoph Hellwig reviewed v5 and raised an API concern about using xa_store, noting it "does quite a bit of work for the non-initial GETDEVICEINFO." He recommended switching to xa_insert.

"xa_insert seems like a lot less heavy handed." Christoph Hellwig

  • v6 (January 8): Incorporated the v5 review feedback, including:
    • Use of xa_insert() instead of xa_store()
    • Added check for PR_STS_RETRY_PATH_FAILURE

This Week's Activity (January 8)

Patch Submission

Chuck Lever posted the v6 submission on January 8th. The patch modifies three files:

  • fs/nfsd/blocklayout.c (+41 lines): Core fencing logic with xarray tracking
  • fs/nfsd/nfs4state.c (+6 lines): xarray initialization and cleanup in client lifecycle
  • fs/nfsd/state.h (+3 lines): New cl_dev_fences field on nfs4_client

The mechanism works as follows: when the server issues a persistent registration key to a client, it creates an xarray entry at the device's dev_t index with a fenced flag initialized to 0. Before performing a fence via nfsd4_scsi_fence_client, the server checks this flag — if already set, the fence is skipped; otherwise, it sets the flag and proceeds with fencing. The xarray is destroyed when the client is released in __destroy_client.

Technical Significance

This fix has important implications for NFS server deployments using pNFS block layouts:

  1. Data integrity protection: SCSI persistent registration fencing is a critical mechanism for preventing data corruption when multiple clients access the same underlying block device. The fence operation ensures that only one client can interact with a device at a time during layout conflicts.

  2. Elimination of spurious errors: Without this fix, the server would generate repeated failure messages when attempting to fence an already-fenced device — noise that could obscure genuine problems in production environments.

  3. Correctness under concurrent recalls: When multiple layouts are held by an unresponsive client, each layout recall independently triggers fencing logic. The xarray-based tracking ensures idempotent fencing behavior regardless of how many times the operation is invoked for the same device-client pair.

  4. Pragmatic design choice: Christoph Hellwig noted that a dedicated per-device object might be more architecturally natural in the long term:

"Right now the nfsd code has no object for pNFS device, mostly because: a) there can only be one per file system and thus export b) there is no per-device state managed by nfsd. This patch changes b)." Christoph Hellwig

However, he acknowledged the pragmatic value of the current approach:

"But with all the effort already invested it probably makes sense to go with it to fix the bug." Christoph Hellwig

Conclusion

This thread represents the successful conclusion of a six-week patch refinement process. The v6 submission incorporated all reviewer feedback — including NeilBrown's semantic concerns about fencing state and Christoph Hellwig's API recommendations — and was accepted and applied within hours of posting. The fix strengthens the NFS server's handling of pNFS block layout fencing, ensuring robust behavior when managing unresponsive clients in shared storage environments.
