NFSD SCSI Fencing: xa_insert vs xa_cmpxchg API Decision

Summary

NFSD: SCSI Persistent Registration Fencing — xarray API Refinement (Week Ending 2026-01-08)

Classification

This discussion is about a bug fix for the NFS server's pNFS block layout SCSI persistent reservation fencing logic. The patch series (now at v5), authored by Dai Ngo and Chuck Lever, introduces per-client tracking of fenced devices using an xarray data structure to prevent redundant and failing fence operations when handling unresponsive clients.

Prior Context

Over the preceding weeks, the thread evolved through five versions of the patch. Early in this week, Dai Ngo approved v5:

"Thanks Chuck! it looks fine to me."

As confirmed by Dai Ngo

Christoph Hellwig then raised architectural and API concerns on January 7, noting that the xarray was being used "only for values" in a creative way, and that xa_store performs unnecessary work for non-initial GETDEVICEINFO calls. He suggested a per-device object might be more natural long-term but conceded:

"But with all the effort already invested it probably makes sense to go with it to fix the bug."

As stated by Christoph Hellwig

Chuck Lever followed up on January 8, asking whether the code should use xa_insert instead of xa_store:

"The comment is misleading then, and should be clarified. But should the code use xa_insert instead of xa_store?"

As questioned by Chuck Lever

This Week's Activity (Jan 8)

The sole new contribution this week came from NeilBrown, who entered the discussion to propose an alternative xarray API function:

"or xa_cmpxchg() to replace NULL with a value??"

As suggested by NeilBrown

NeilBrown's suggestion of xa_cmpxchg() offers an atomic compare-and-exchange approach, which would replace a NULL entry with the new value only if the slot is still empty — a potentially more precise semantic match for the "insert-if-absent" pattern needed here.

Christoph Hellwig weighed both options and concluded:

"xa_insert seems like a lot less heavy handed."

As recommended by Christoph Hellwig

Key Technical Arguments

AspectDetail
ProblemRedundant SCSI fence operations fail when a client's persistent reservation key has already been preempted
SolutionPer-client xarray tracking fenced devices by dev_t, with a flag to skip duplicate fencing
API debateWhether to use xa_store, xa_insert, or xa_cmpxchg() for populating the xarray
xa_storeStores unconditionally and returns the old value — does "quite a bit of work" unnecessarily
xa_insertInserts only if slot is empty — preferred by Hellwig as "less heavy handed"
xa_cmpxchgAtomic compare-and-exchange — suggested by NeilBrown but deemed more complex than needed

Conclusions

  • The patch series remains close to merge-ready pending a minor API adjustment.
  • Christoph Hellwig's recommendation to use xa_insert over both xa_store and xa_cmpxchg() represents the consensus direction.
  • The immediate action item for the authors is to replace xa_store with xa_insert and clarify the misleading comment in the code.
  • While Hellwig noted that a dedicated per-device object would be architecturally cleaner, the community accepted the current xarray-based approach as a pragmatic bug fix given the effort already invested.
