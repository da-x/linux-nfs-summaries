OPENAT2_REGULAR Flag Applied to VFS Tree

Summary

This week concluded the review cycle for Patch v6 of the OPENAT2_REGULAR flag series, which introduces a new UAPI feature allowing applications to explicitly request opening only regular files via openat2(). If a non-regular file (e.g., directory, device node) is encountered, the operation fails with -EFTYPE. This feature enhances security and correctness for filesystems implementing atomic open paths, including NFS, Ceph, GFS2, and SMB.

Bridge from Prior Weeks

In previous weeks, Jeff Layton reviewed the v6 series, initially raising concerns about Ceph symlink handling and GFS2 flag masking in the atomic open codepaths. After clarifications from author Dorjoy Chowdhury, Layton acknowledged the correctness of the implementation—including the NFS client updates—and provided a Reviewed-by tag. The discussion this week shifted to final UAPI design details and merge logistics.

Patch Application

On April 16, VFS maintainer Christian Brauner officially accepted the series:

"Applied to the vfs-7.2.openat.regular branch of the vfs/vfs.git tree. Patches in the vfs-7.2.openat.regular branch should appear in linux-next soon." Christian Brauner

The applied series includes core VFS support, kselftests, and architecture-specific header updates. Two patches converting O_* flag macros from hex to octal on SPARC and MIPS were dropped as they were deemed stylistic and unrelated to the core feature.

Key Technical Discussions

1. Flag Leakage into f_flags

Aleksa Sarai raised a concern regarding whether OPENAT2_REGULAR persists in the file description flags after a successful open, referencing a previous review comment by Jeff Layton about the flag leaking into file->f_flags and being visible via fcntl(fd, F_GETFL). Dorjoy Chowdhury confirmed that OPENAT2_REGULAR is an open-time-only flag (similar to O_CREAT) and should be stripped.

Jeff Layton elaborated on the semantics of returning this flag:

"I don't have a strong feeling either way, but it 'feels' like O_REGULAR is not particularly useful to return in F_GETFL. Once the file is open, then O_REGULAR really doesn't matter anymore. We know it's a regular file at that point or the open wouldn't have happened." Jeff Layton

2. UAPI Flag Space Allocation

Jori Koolstra questioned why OPENAT2_REGULAR was defined within the existing 32-bit O_* flag range if it is exclusively supported by openat2():

"I don't quite understand why we are adding OPENAT2_REGULAR inside the O_* flag range. Wasn't this supposed to be only supported for openat2()? If so, I don't see the need to waste an O_* flag bit." Jori Koolstra

Dorjoy Chowdhury explained that legacy open() system calls do not mask unknown bits, meaning adding new O_* flags could inadvertently break older userspace programs. In contrast, openat2() explicitly strips unknown bits, making the 32-bit space safe for new flags:

"It's not easy to add new O_* flags for the old open system calls since that could break userspace programs... So I guess it's okay to add OPENAT2_REGULAR in the 32 bits range anyway?" Dorjoy Chowdhury

Christian Brauner concurred, noting that while separating the bits might be cleaner, the current approach is harmless:

"I don't mind too much if we leave OPENAT2_REGULAR in the 32-bit flag space. It'll silently be ignored but the flag name should give it away." Christian Brauner

Implications for NFS Client Development

For NFS, this patch series enables robust support for strict regular-file opens within the nfs_atomic_open codepath. By leveraging VFS-level validation and filesystem-specific checks, the NFS client can now reliably reject attempts to open non-regular files when OPENAT2_REGULAR is specified, preventing potential security issues or application logic errors arising from unexpected file types. No new bug fixes were discussed this week; the focus remained on finalizing the UAPI design for this new feature.
