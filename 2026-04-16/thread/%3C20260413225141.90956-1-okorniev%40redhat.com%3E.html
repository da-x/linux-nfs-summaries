NFSv4.2 COPY Timestamp Fix v2: Minimal Patch Resubmitted After Maintainer Review

Summary

NFSv4.2 COPY Timestamp Fix v2: Minimal Patch Resubmitted After Maintainer Review

Classification

Bug fix — Linux NFS client handling of stale ctime/mtime attributes after an NFSv4.2 server-side COPY operation when delegated timestamps are present.

Bridge from Prior Weeks

This thread represents a v2 resubmission of a patch originally posted on March 27 under the root <20260327165757.28948-1-okorniev@redhat.com>. The original submission addressed a regression detected by xfstest generic/407: after an NFSv4.2 COPY operation, the client failed to update ctime and mtime, reporting stale values when delegated attributes were active.

The prior thread generated substantial discussion:

  • Jeff Layton argued that the server should update timestamps natively during COPY, identifying FMODE_NOCMTIME as a likely root cause on the server side:

    "I think that'd ultimately be more efficient, and I think the server should be updating the c/mtime on COPY, even if there is an outstanding timestamp delegation. The server is doing the COPY. The client isn't really involved so why should it be trying to stamp the file?"

  • Olga Kornievskaia acknowledged the architectural debate, noting:

    "This patch isn't needed if the server updates mtime/ctime after doing a COPY."

  • Trond Myklebust, the NFS client maintainer, raised a pointed technical question about the original patch's redundancy:

    "Isn't NFS_INO_INVALID_BLOCKS already set it nfs42_copy_dest_done()?"

This question suggested that the original fix — which added block attribute invalidation after COPY — might have been unnecessary if nfs42_copy_dest_done() already handled this. The original v1 patch touched 6 lines; the v2 resubmission this week is a dramatically simplified 1-line change.

This Week's Activity

On April 13, Olga Kornievskaia submitted [PATCH v2 1/1] 20260413225141.90956-1-okorniev@redhat.com, a minimal fix to fs/nfs/nfs42proc.c (1 file changed, 1 insertion). The patch description reiterates the core problem:

"A similar to generic/407 test can be done with a COPY operation instead of CLONE (reflink). And it leads to same problem that ctime and mtime saved before doing a 'cp' operation are the same as after."

No replies or further discussion occurred within this week's window. The thread remains open.

Evolution and Significance

The dramatic reduction from a 6-line v1 patch to a 1-line v2 suggests Kornievskaia refined her approach in response to Myklebust's question about NFS_INO_INVALID_BLOCKS already being set by nfs42_copy_dest_done(). Rather than duplicating invalidation logic, the v2 likely addresses a more targeted gap — perhaps ensuring that delegated timestamps are properly invalidated in a specific code path that was previously overlooked.

This fix is significant for NFS client development because:

  1. Correctness of metadata: Accurate ctime/mtime values are essential for backup systems, build tools, and filesystem semantics compliance. Stale timestamps after server-side operations like COPY can cause silent data consistency issues.
  2. Delegation edge cases: The interplay between delegated attribute caching and post-operation metadata updates is a subtle area where performance optimizations can compromise consistency guarantees — a recurring theme in NFS client development.
  3. Parallel with CLONE fix: This issue mirrors the separate CLONE (reflink) timestamp bug fixed in another thread, suggesting a systemic pattern in how the NFS client handles delegated attributes after server-side file operations.

Conclusion

This week saw a quiet resubmission of a refined v2 patch for the NFSv4.2 COPY timestamp bug. With no maintainer feedback yet this week, the thread awaits review. The minimal scope of the v2 change (1 line vs. 6 lines in v1) suggests Olga Kornievskaia has incorporated lessons from the prior discussion, particularly Myklebust's observation about existing invalidation logic. Whether this streamlined approach resolves the issue without redundancy remains to be determined by further maintainer review.
