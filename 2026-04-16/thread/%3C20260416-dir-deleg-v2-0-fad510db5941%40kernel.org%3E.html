pynfs: v2 patchset for NFSv4.1 directory delegation testcases

Summary

pynfs: Comprehensive Test Suite for NFSv4.1 Directory Delegations

This week, Jeff Layton submitted a substantial version 2 patch series to the pynfs testing framework, introducing 25 new test cases focused on NFSv4.1 directory delegations. This submission represents a significant advancement in client/server interoperability testing, specifically targeting the mechanisms defined in RFC 8881 and its proposed extension, RFC 8881bis.

Nature of the Discussion

This is a new feature/testing enhancement submission rather than a bug fix or protocol change discussion. However, it indirectly supports bug detection by providing rigorous validation for directory delegation behaviors, including recalls and notifications (CB_NOTIFY). The patches update the pynfs framework to test both "recall-only" delegations (supported by current mainline kernels) and full notification-based delegations (requiring server support for CB_NOTIFY).

Key Technical Arguments and Evolution

1. Introduction of NOTIFY4_GFLAG_EXTEND

The series begins by adding support for the proposed NOTIFY4_GFLAG_EXTEND flag, part of RFC 8881bis. As Layton notes in patch 01/25:

"In practice, the Linux nfs server requires that the client support this flag if it's requesting anything other than a recall-only delegation."

This distinction is critical: without GFLAG_EXTEND, clients can only receive recalls when changes occur. With it, they can opt into specific notification types (ADD, REMOVE, RENAME), allowing for more efficient cache coherence without full delegation revocation.

2. Recall-Only Tests (DIRDELEG1-7)

The first batch of tests validates basic delegation mechanics where the server issues a CB_RECALL upon any conflicting operation. These include:

  • Basic handout and return: Patch 03/25 tests the fundamental GET_DIR_DELEGATION flow.
  • Duplicate requests: Patch 04/25 ensures servers handle redundant delegation requests correctly.
  • Recall triggers: Separate patches verify that remove 06/25, rename 07/25, mkdir 08/25, and link 09/25 operations from a second client correctly trigger recalls on the holding client.

3. Notification-Based Tests (CB_NOTIFY)

The majority of the series focuses on testing CB_NOTIFY behaviors, which are only active if the server supports them and the client requests specific notification types via GFLAG_EXTEND. Key scenarios include:

  • Notification vs. Recall: Patch 10/25 verifies that if a client requests notifications but does not set GFLAG_EXTEND, the server falls back to issuing recalls. Conversely, Patch 11/25 confirms that unrequested notification types (e.g., requesting REMOVE but triggering an ADD) also result in recalls.

  • ADD Notifications: Multiple patches validate NOTIFY4_ADD_ENTRY:

    • Basic add via file creation 13/25.
    • Add via mkdir 17/25.
    • Add via hard link 22/25.
    • Cross-directory rename generating an ADD on the target directory 21/25.

  • REMOVE and RENAME Notifications:

    • Basic remove notification 12/25.
    • Within-directory rename generating NOTIFY4_RENAME_ENTRY 14/25.
    • Cross-directory rename generating a REMOVE on the source directory (not a RENAME) 20/25.

  • Attribute Verification: The tests go beyond simple event detection, verifying that notifications include correct child attributes 15/25 and filehandles 19/25.

4. Edge Cases and Protocol Compliance

The series includes sophisticated tests for edge cases defined in RFC 8881:

  • Rename-over semantics: When a rename overwrites an existing entry, the server should report the overwritten entry via nad_old_entry within the ADD or RENAME notification, rather than sending a separate REMOVE notification. This is tested for both cross-directory 24/25 and within-directory 25/25 scenarios.

    "Per RFC 8881 Section 18.26.4, when the removal is done atomically with the rename, a separate NOTIFY4_REMOVE_ENTRY notification will not be generated."

  • Self-inflicted changes: Patch 23/25 verifies that changes made by the delegation-holding client itself do not trigger callbacks, ensuring no unnecessary network overhead.

  • Delegation Return: Patch 18/25 confirms that issuing a DELEGRETURN immediately stops notifications, validating proper cleanup.

Final Conclusions and Impact

This patchset significantly matures the pynfs test suite's coverage of NFSv4.1 directory delegations. By distinguishing between recall-only and notification-based behaviors, it provides a robust framework for validating both current mainline kernels (which support recalls) and future servers implementing full CB_NOTIFY support.

The use of pass_warn() when the server lacks directory delegation support 05/25 ensures these tests can be safely included in general test groups without causing failures on non-supporting servers. This approach encourages wider adoption of directory delegation testing across diverse NFS implementations.

As Layton summarized in the cover letter 00/25:

"DIRDELEG1-7 should pass on current mainline kernels, with recall-only support. The rest require CB_NOTIFY support."

This submission lays the groundwork for ensuring that NFS clients and servers correctly implement the complex state management required for directory delegations, reducing the risk of cache coherence bugs in production environments.
