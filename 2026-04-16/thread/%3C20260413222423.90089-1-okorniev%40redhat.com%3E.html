NFS: v3 writeback error-loop fix submitted after maintainer ACK

Classification

This is a bug fix for the NFS client's page cache writeback subsystem, addressing infinite retry loops when the server returns ENOSPC errors during unstable writes.

Prior Context (Brief)

In March 2026, Olga Kornievskaia submitted an RFC and then v2 of her patch "NFS: fix writeback in presence of errors" targeting a bug discovered while running xfstest generic/751. The bug manifests as stuck writeback I/O under two specific failure patterns involving ENOSPC errors from the NFS server during unstable writes.

Last week, maintainer Trond Myklebust reviewed v2 and gave it an ACK with one nitpick:

"Can we please do something to avoid 2 calls to iov_iter_count() here?"

He concluded:

"Otherwise, the rest looks good to me."

This Week's Activity

On April 13, Olga Kornievskaia submitted v3 of the patch 20260413222423.90089-1-okorniev@redhat.com, addressing the maintainer's feedback. This is the only message in this thread for the current week; no further discussion occurred before the window closed.

The Bug: Two Failure Patterns

The patch description reiterates the two problematic patterns that cause writeback to loop indefinitely:

Pattern #1: Writeback I/O experiences ENOSPC at an offset smaller than the file size. For example:

  • Write at offset 0, length 4096, unstable — OK
  • Write at offset 8192, length 4096, unstable — OK
  • Write at offset 12288, length 4096, unstable — ENOSPC
  • Write at offset 4096, length 4096, unstable — ENOSPC

The client sends a commit and receives a verifier different from the last successful write. It marks pages dirty and retries writeback, but again sends unstable writes, re-entering the same ENOSPC loop.

Pattern #2: An unstable write followed by a short write and then ENOSPC:

  • Write at offset 0, length 4096, unstable — OK
  • Write at offset 4096, length 4096, unstable — returns OK but count=100 (short write)
  • Write at offset 4197, length 3996, stable — ENOSPC

The same retry loop ensues.

The Fix: Synchronous Fallback via Persistent Context Flag

The patch proposes identifying these error conditions and marking requests to be performed synchronously instead of asynchronously. Kornievskaia explains the architectural evolution:

"Previous solution tried to mark it in the nfs_page, however that's not persistent thus instead mark it in the nfs_open_context."

Storing the synchronous-writeback flag in nfs_open_context (rather than the transient nfs_page) ensures the state persists across retries. The fix also extends to the LocalIO code path:

"Furthermore, the same problem occurs during localio code path so recognize that IO needs to be done sync in that case as well."

The patch touches four files:

  • fs/nfs/localio.c — 15 lines added/modified
  • fs/nfs/pagelist.c — 3 lines added
  • fs/nfs/write.c — 9 lines added
  • include/linux/nfs_fs.h — 1 line added

Total: 27 insertions, 1 deletion.

v3 Changes

While the full diff was not included in this week's ingest, v3 follows directly from Myklebust's review of v2. The primary change expected is the elimination of the redundant iov_iter_count() calls flagged by the maintainer. No new objections or discussion arose this week, suggesting the fix is now in a merge-ready state.

Significance for NFS Client Development

  1. Reliability Improvement: This fix prevents application stalls and potential I/O deadlocks caused by infinite writeback loops under server-side ENOSPC conditions — a real-world scenario exposed by xfstest generic/751.
  2. Architectural Soundness: The shift from transient nfs_page state to persistent nfs_open_context state represents a thoughtful design choice validated by the maintainer without objection.
  3. LocalIO Coverage: By extending the fix to the LocalIO code path, the patch ensures consistent behavior across both traditional NFS and LocalIO writeback scenarios.
  4. Test-Driven Development: The bug was discovered through automated testing (xfstest), exemplifying the value of systematic regression testing in kernel development.

Conclusion

This week saw the submission of v3 of Olga Kornievskaia's writeback error-loop fix, incorporating maintainer feedback from last week's review. With Trond Myklebust's prior ACK and no new objections this week, the patch appears poised for imminent merge into the Linux NFS client tree. The fix addresses a genuine reliability bug that could cause application stalls under server-side space exhaustion conditions.
