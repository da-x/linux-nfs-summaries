NFSv4.2 COPY Timestamp Fix: Maintainer Questions Patch Redundancy

Summary

NFSv4.2 COPY Timestamp Fix: Maintainer Questions Patch Redundancy

Classification

Bug fix — Linux NFS client handling of attribute invalidation after an NFSv4.2 server-side COPY operation when delegated timestamps are present.

Background (Bridged from Prior Weeks)

This thread began on March 27 with Olga Kornievskaia submitting a 6-line patch to address stale ctime/mtime values on the client after an NFSv4.2 COPY:

"A similar to generic/407 test can be done with a COPY operation instead of CLONE (reflink). And it leads to same problem that ctime and mtime saved before doing a 'cp' operation are the same as after." — Olga Kornievskaia

She immediately followed up questioning whether appending a GETATTR to the COPY compound (as done previously for REMOVEXATTR) might be a superior approach. On April 3, Jeff Layton argued strongly that the server should update timestamps natively during COPY and identified FMODE_NOCMTIME as a likely root cause on the server side:

"I think that'd ultimately be more efficient, and I think the server should be updating the c/mtime on COPY, even if there is an outstanding timestamp delegation. The server is doing the COPY. The client isn't really involved so why should it be trying to stamp the file?" — Jeff Layton

Kornievskaia responded on April 8, conceding that her patch may be unnecessary if the server properly updates timestamps, and offering to post a separate GETATTR-in-compound patch:

"This patch isn't needed if the server updates mtime/ctime after doing a COPY." — Olga Kornievskaia

This Week's Activity

The only message this week comes from NFS client maintainer Trond Myklebust on April 13, who directly questions whether the original patch's attribute invalidation logic is even necessary:

"Isn't NFS_INO_INVALID_BLOCKS already set it nfs42_copy_dest_done()?" — Trond Myklebust

Myklebust's remark targets the core of Kornievskaia's patch, which adds a block to invalidate NFS_INO_INVALID_BLOCKS on the destination inode after COPY. His question suggests that this invalidation flag may already be set by the existing nfs42_copy_dest_done() function — meaning the original bug might already be partially or fully addressed in the current codebase, rendering the patch redundant.

Evolution of the Discussion

The thread has evolved through three distinct phases:

  1. Patch submission (March 27): Kornievskaia proposes a client-side fix for stale timestamps after COPY, while simultaneously questioning whether a GETATTR compound approach would be better.
  2. Architectural debate (April 3–8): Layton argues for server-side correctness and identifies FMODE_NOCMTIME as the probable root cause; Kornievskaia acknowledges her patch may be unnecessary if server behavior is corrected.
  3. Maintainer review (April 13, this week): Myklebust raises a pointed technical question suggesting the patch's core mechanism — setting NFS_INO_INVALID_BLOCKS — may already be handled by existing code in nfs42_copy_dest_done().

Key Technical Arguments

  • Redundancy concern: Myklebust's observation that NFS_INO_INVALID_BLOCKS might already be set by nfs42_copy_dest_done() could render the entire patch moot. This is a significant finding for NFS client development, as it suggests the bug may have been inadvertently fixed or partially addressed in prior work.
  • Server-side responsibility: Layton's argument that the server should update timestamps during COPY (and that FMODE_NOCMTIME may be blocking this) remains an open path for a more fundamental fix.
  • GETATTR compound approach: Kornievskaia's prepared patch to add GETATTR to the COPY compound has not yet been posted, leaving this alternative unresolved.

Conclusion

As of this week's cutoff, the thread remains open with no merged patch. Myklebust's question introduces a new dimension: if NFS_INO_INVALID_BLOCKS is indeed already set by nfs42_copy_dest_done(), then Kornievskaia's original patch may be entirely redundant. This would shift the discussion toward either (a) confirming that the existing code already handles the issue, or (b) investigating why timestamps still appear stale despite the invalidation flag being set. The bug fix remains significant for NFS client correctness, as accurate ctime/mtime values are essential for backup systems, build tools, and filesystem semantics compliance.
