NFS P2PDMA RFC: Capability Detection Refinement and API Modernization Roadmap

Summary

NFS Client P2PDMA RFC: Refining Capability Detection and API Modernization

Overview

This week, discussion continued on Pranjal Shrivastava's RFC series to enable PCI Peer-to-Peer DMA (P2PDMA) support in the NFS client Direct I/O path. Last week, Christoph Hellwig and Chuck Lever raised significant architectural concerns regarding API modernization, pNFS integration, and dynamic capability detection. This week, Pranjal responded to those points, and the reviewers provided further guidance on how to structure the upcoming preparation series.

The thread remains focused on feature development (P2PDMA support) intertwined with critical bug fixes and API modernizations (migration from iov_iter_get_pages_alloc2() to iov_iter_extract_pages(), folio adoption for Direct I/O, and pin-aware page lifecycle management).

Evolution of the Discussion

Transport Capability Detection: Server Caps vs. Transport Flags

Last week, Chuck Lever highlighted that P2PDMA support is a transport-level property, not an NFS server capability, and noted the risk of stale flags during RDMA reconnections. In response, Pranjal asked whether the capability should be initialized at mount time and updated on disconnect, or populated only when a transport is connected:

"Ack. I agree, so should we start with an inital cap and then update it in the event of a transport change / disconnect? Or shall we populate the cap only when a transport is connected?" — Pranjal Shrivastava

Chuck Lever pushed back further, arguing that NFS_CAP_P2PDMA does not belong in the server caps structure at all. He pointed out the complexity of multi-transport scenarios and the need for per-I/O decision-making:

"IMO this flag does not belong in the NFS server CAPS, as it is a capability associated with each RPC transport. How should NFS_CAP_P2PDMA be set if there are two RPC transports, one with P2PDMA enabled and with it disabled?" — Chuck Lever

Lever emphasized that the mechanism must be re-evaluated every time a direct I/O request (dreq) is scheduled, because the underlying RPC transport (xprt) can change between an original send and a retransmission—for example, if a COMMIT verifier changes due to a server reboot. He deferred the final architectural decision to Trond Myklebust and Anna Schumaker:

"Which mechanism to use has to be re-decided every time a dreq is scheduled because the xprt can change between an original send and a retransmission... Trond and Anna will have the final say about how this works." — Chuck Lever

API Modernization: Splitting Out Preparation Patches

Christoph Hellwig reiterated that the migration from iov_iter_get_pages_alloc2() to iov_iter_extract_pages() is a critical, long-overdue bug fix that should be separated from the P2PDMA feature. Pranjal agreed and asked whether this migration should be combined with the pin-aware page lifecycle changes and folio adoption for Direct I/O:

"Sure, I'll send out a series with the migration to iov_iter_extract_pages, should I club this with the pin-aware + folios for direct I/O or send it as a separate series?" — Pranjal Shrivastava

Hellwig advised combining the preparation changes but keeping P2PDMA separate:

"I think combining all this sounds find. I'd just do the P2P separately as it is bound to get quite a bit more complicated." — Christoph Hellwig

Hellwig also suggested that the NFS Direct I/O code should move beyond pages entirely, adopting iov_iter_extract_bvecs for better efficiency with large I/O operations, noting that buffered I/O already uses folios:

"currently the NFS I/O code is using folios for buffered I/O, but pages for direct I/O, which makes larger I/O very inefficient." — Christoph Hellwig (quoted in Pranjal's response)

Pranjal acknowledged this direction, stating he would attempt an "open coded variant" of iov_iter_extract_bvecs tailored to nfs_page structures:

"Ack. I'll attempt an open coded variant." — Pranjal Shrivastava

Code Style and checkpatch Limitations

Hellwig noted that some of the submitted code had lines exceeding standard length limits. Pranjal expressed surprise that checkpatch did not flag these issues. Hellwig responded candidly about the limitations of the tool:

"checkpatch is unfortunately completely broken :( It misses lots of important bits, but at the same time has complete incoherent and crazy warnings." — Christoph Hellwig

Key Technical Arguments

  1. P2PDMA is a transport property, not a server capability: Chuck Lever argued that NFS_CAP_P2PDMA should not reside in the NFS server caps bitmask, as P2PDMA support varies per RPC transport and can change dynamically during reconnections or retransmissions.

  2. Per-I/O capability checking is required: Because the underlying transport can change between an original send and a retransmission, the decision to use P2PDMA must be made at request scheduling time, not at mount time.

  3. API migration is a prerequisite bug fix: The transition from iov_iter_get_pages_alloc2() to iov_iter_extract_pages() fixes potential data corruption (noted as affecting XFS) and must be separated into its own preparation series.

  4. Folio adoption for Direct I/O improves efficiency: Hellwig highlighted that the NFS client uses folios for buffered I/O but pages for Direct I/O, creating inefficiency for large I/O operations. Moving to iov_iter_extract_bvecs or a custom variant is recommended.

Final Conclusions and Next Steps

The discussion this week clarified the path forward for the P2PDMA RFC series:

  • Preparation series: Pranjal will submit a separate series combining the migration to iov_iter_extract_pages(), pin-aware page lifecycle management, and folio adoption for Direct I/O. This series addresses critical bug fixes and efficiency improvements independent of P2PDMA.
  • P2PDMA series: The actual P2PDMA support will be developed separately, with further architectural decisions on capability detection pending input from Trond Myklebust and Anna Schumaker.
  • Transport-level flagging: Future iterations will likely move P2PDMA detection out of the NFS server caps and into the RPC transport layer, with per-I/O validation to handle dynamic transport changes.
