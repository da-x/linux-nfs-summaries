Summary

NFSv4.2 CLONE Attribute Fix — Maintainer Suggests Alternative Approach

Classification: Bug Fix

This thread concerns a bug fix in the NFSv4.2 client related to incorrect attribute handling after a CLONE operation when delegated attributes are present.

Bridge from Prior Weeks

The patch series was originally submitted by Olga Kornievskaia on March 27, addressing a regression detected by xfstest generic/407: after an NFSv4.2 CLONE operation, the client failed to update mtime and ctime, and reported stale change_attr values when delegated attributes were active. The root cause was traced to commit e12912d94137, which introduced delegated atime/mtime attribute caching but inadvertently broke the CLONE post-operation update path. Olga's proposed fix invalidated block attributes after a CLONE, forcing the client to refresh its cache rather than relying on stale delegated values.

In the preceding week (ending 2026-04-09), Olga added a follow-up remark:

"This patch isn't needed if the server updates mtime/ctime after doing a CLONE."

This raised an architectural question about whether the fix should reside in the client or whether servers should be held responsible for updating timestamps post-CLONE.

This Week's Activity

This week saw one message: a review comment from NFS client maintainer Trond Myklebust on April 13. Rather than addressing Olga's architectural observation, Trond focused on the implementation details of the patch itself, suggesting a cleaner alternative to the proposed fix:

"Why not call nfs_post_op_update_inode() instead of setting NFS_INO_INVALID_BLOCKS? It should be safe to do so." Trond Myklebust

This is a notable suggestion. Olga's patch used the NFS_INO_INVALID_BLOCKS flag to force attribute invalidation — a somewhat blunt mechanism that marks block attributes as stale, requiring a subsequent refresh. Trond's proposal to call nfs_post_op_update_inode() directly would apply the server-provided attributes immediately, which is more in line with standard post-operation update patterns used elsewhere in the NFS client codebase. This approach would be both more direct and potentially less disruptive than flag-based invalidation.

Evolution of the Discussion

The thread remains open-ended. Trond's comment represents a constructive code review suggestion rather than an outright approval or rejection. No response from Olga has arrived within this week's window, so it is unclear whether she will revise the patch to incorporate nfs_post_op_update_inode() or defend the current approach. The broader question raised by Olga — about server-side responsibility for timestamp updates after CLONE — also remains unaddressed.

Significance for NFS Client Development

This fix targets a correctness issue in NFSv4.2 clone operations, a feature critical for storage virtualization and deduplication workloads. The interplay between delegated attribute caching and post-operation metadata updates is a subtle area where performance optimizations can compromise consistency guarantees. Trond's suggestion to use nfs_post_op_update_inode() reflects the maintainer's preference for leveraging existing infrastructure rather than introducing ad-hoc invalidation mechanisms — a pattern that promotes code maintainability and reduces the risk of future regressions in the NFS client attribute handling subsystem.
