nfsd: Fix mtime/ctime updates for CLONE/COPY with delegated attributes

Summary

NFS Server Bug Fix: Correcting Timestamp Updates for CLONE and COPY Operations

A two-patch series submitted by Olga Kornievskaia addresses a regression in the NFS server (nfsd) where modification time (mtime) and change time (ctime) were not being updated correctly during CLONE and COPY operations when delegated attributes were present. The patches were accepted and applied to the nfsd-testing tree by maintainer Chuck Lever.

The Problem: Delegated Attributes Masking Timestamps

The issue stems from how nfsd handles files with outstanding attribute delegations. When a client holds a delegation, the file is opened with the NOCMTIME flag. This prevents modifying operations from updating mtime and ctime on the server side to avoid getting out-of-sync with the client's delegated view of the metadata.

However, this optimization created a bug for specific compound operations. As Olga Kornievskaia explained in the cover letter:

"generic/407 is failing in presence of delegated attributes and this patch series explores the solution where the CLONE compound returns updated mtime/ctime in the GETATTR op in the compound."

The core technical argument is that while general writes might defer timestamp updates to preserve delegation consistency, CLONE and COPY operations explicitly modify the destination file's content and should therefore update its timestamps. The server needs to reflect these changes in any subsequent GETATTR queries within the same compound operation.

Evolution of the Patch Series (v4)

This is the fourth version of the series, showing significant refinement from earlier iterations:

  • v3 changes: Consolidated synchronous and asynchronous COPY patches into a single patch. Additionally, notify_change() code was extracted from nfsd4_finalize_deleg_timestamps to be shared with nfsd_update_cmtime_attr, ensuring consistent error logging if the timestamp update fails.
  • v4 changes:
    • Patch 1: Moved struct iattr into nfsd_update_cmtime_attr(), which was relocated to nfs4state.c. It now accepts flags as a second argument, allowing for the addition of ATTR_ATIME when necessary.
    • Patch 2: Removed a comment about dput in nfsd4_do_async_copy() and now tests for a set nfsd4_copy->attr_update flag. This flag is set if the file had NOCMTIME set on open and timestamps are subsequently modified.

Technical Details of the Fix

Patch 1/2: CLONE Operation The first patch addresses the CLONE operation. It ensures that when a clone occurs, the server updates its internal view of mtime and ctime for the destination file, even if a delegation is present. This allows the GETATTR operation in the same compound request to return accurate timestamps.

"When delegated attributes are given on open, the file is opened with NOCMTIME and modifying operations do not update mtime/ctime as to not get out-of-sync with the client's delegated view. However, for CLONE operation, the server should update its view of mtime/ctime and reflect that in any GETATTR queries."

Patch 2/2: COPY Operation The second patch applies the same logic to the COPY operation, covering both synchronous and asynchronous copies. It introduces a tracking mechanism (attr_update) to determine if timestamp updates are required based on the presence of NOCMTIME at open time.

Conclusion and Application

Chuck Lever applied both patches to the nfsd-testing tree without further discussion:

"Applied to nfsd-testing, thanks!"

The fixes target a specific regression introduced by commit e5e9b24ab8fa ("nfsd: freeze c/mtime updates with outstanding WRITE_ATTRS delegation"), restoring correct behavior for NFSv4.1+ pNFS-like operations (CLONE/COPY) when delegations are active. This ensures that clients receive accurate metadata after these bulk data transfer operations, resolving failures in the generic/407 test suite.
