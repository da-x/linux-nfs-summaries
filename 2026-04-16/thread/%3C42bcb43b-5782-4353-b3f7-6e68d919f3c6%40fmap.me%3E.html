Help tracking down a possible race

Summary

A Potential NFS Cache Race: Stale Zero-Fill Beyond EOF

This thread consists of a single message this week, an initial report from Nikolay Amiantov raising concerns about a potential race condition in the NFS client (and potentially any network filesystem). The discussion is centered on a possible bug fix, not a new feature or protocol change.

The Reported Race Condition

Amiantov, originally investigating a bug in JuiceFS (a FUSE-based distributed filesystem), distilled the issue down to a minimal reproducible example (MRE) that also manifests with NFS. He describes a scenario involving:

  • Host A: A writer appends to a file one byte at a time.
  • Host B: Simultaneously reads the file byte-by-byte (possibly from multiple threads/processes) while hammering the same file with stat() calls.

The symptom: "you may randomly read a zero byte instead of the byte you are expecting to read."

Technical Analysis

Amiantov traces the root cause to the interaction between page caching and inode size updates in filemap_read() (mm/filemap.c). He outlines the critical sequence:

do {
    ...
    error = filemap_get_pages(iocb, ...);  // (1) get cached folios
    ...
    isize = i_size_read(inode);            // (2) get file size
    ...
    // (3) copy from folio to user, capped at isize
} while (...);

The core issue is that when a file grows remotely, the page cache before the old EOF contains zero-fill beyond the previous size. "Those zeroes are valid while new size <= old size (they are beyond EOF), but become stale once the new size is updated to reflect the remote growth: the remote host wrote real data there, but the local cache still has the old zero-fill."

If the inode size is updated between steps (1) and (2) — for instance, via a getattr call discovering remote growth — "the race happens; the old page gets capped at the new size, so the userspace reads zeroes where there should be actual data."

NFS-Specific Context

Amiantov notes that NFS already attempts to mitigate cache staleness:

"NFS does stall the cache already — it sets NFS_INO_INVALID_DATA, then before we read invalidates the cache as needed. However the window between (1) and (2) is still there."

He argues that the fundamental problem is architectural: "there is no way to 'lock' the page and the inode size simultaneously, so the race cannot be fixed just by stalling the cache in getattr."

Scope and Significance

The author emphasizes that this issue is not unique to NFS: "the race, as I understand it, is actually relevant to any network FS when updates may happen bypassing the cache layer." He provides test repositories for both NFS (nfs_stale_cache_test) and FUSE (fuse_growtest) to reproduce the behavior.

Amiantov concludes by noting the apparent lack of prior discussion: "Apart from the patches introducing NFS_INO_INVALIDATING I can't find any prior discussion of this issue for FUSE-based, NFS, CIFS or any other network FS." He invites the community to help "denying or confirming my findings, or generally pointing me in the right direction."

Status

As of the end of this week's window, no replies have been received. The thread remains open for community feedback on whether this represents a genuine bug in NFS client cache coherency or a misunderstanding of the expected behavior.
