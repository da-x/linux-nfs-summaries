sunrpc: Fix netlink GET_REQS hang by initializing cache request seqno at 1

Summary

Bug Fix: Resolving Persistent mountd Hangs via Cache Sequence Number Initialization

This week, the Linux NFS community addressed a critical bug in the Sun RPC (sunrpc) subsystem that caused persistent hangs in mountd upcalls, particularly affecting NFSv4 export key (expkey) and file handle (nfsd.fh) cache entries. The fix was proposed by Jeff Layton and applied by Chuck Lever to the nfsd-testing tree.

The Problem: Silent Skipping of Cache Requests

Jeff Layton identified a subtle initialization error in the sunrpc cache request handling logic. The issue stemmed from how sequence numbers (seqno) were assigned to new cache requests and subsequently filtered during netlink dumps.

"sunrpc_cache_requests_snapshot() filters requests with crq->seqno <= min_seqno. The min_seqno for the first netlink dump call is cb->args[0] which is 0. Since next_seqno was initialized to 0, the very first cache request got seqno=0 and was silently skipped by the snapshot (0 <= 0 is true)." Jeff Layton

This logic error had severe downstream consequences for NFS server operations:

  1. Empty Snapshots: The netlink-based GET_REQS operation would return zero pending requests, even when a request was actually queued.
  2. Blocked Resolution: Because mountd could not see the pending requests via netlink, it failed to resolve cache entries (specifically expkey and nfsd.fh).
  3. Permanent Hangs: Entries remained in an unresolved CACHE_PENDING state, which blocked all further notifications for that entry. This resulted in "permanent NFS4ERR_DELAY hangs," effectively freezing NFS operations that depended on these cache lookups.

Layton noted that he encountered this issue as a "persistent hang in mountd upcalls just after reboot," suggesting the bug manifests early in system initialization when the first cache requests are created.

The Fix

The solution was a minimal one-line change to net/sunrpc/cache.c. By initializing next_seqno to 1 instead of 0, all subsequent cache requests receive a sequence number greater than or equal to 1. This ensures they pass the snapshot filter when min_seqno is 0 (the default for the first dump).

"Start next_seqno at 1 so all requests have seqno >= 1 and pass the snapshot filter when min_seqno is 0." Jeff Layton

Layton recommended that this fix be folded into the original patch that introduced the queue split, citing:

"Fixes: facc4e3c8042 ("sunrpc: split cache_detail queue into request and reader lists")"

Conclusion

Chuck Lever accepted the patch without further discussion, applying it to the nfsd-testing tree. The commit was recorded as 2dd2484661eb.

"Applied to nfsd-testing, thanks!" Chuck Lever

This fix is significant for NFS server stability, particularly in environments where netlink-based cache management is used to coordinate between kernel-space NFS daemon components and user-space utilities like mountd. The bug had been present since the queue refactoring commit facc4e3c8042, making this an important regression fix for recent kernels.
