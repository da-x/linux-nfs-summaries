DONTCACHE: Semantic Interpretation and Per-Inode Writeback Benchmarks

Overview

This week's discussion on the RWF_DONTCACHE writeback optimization thread continued with two key developments: a semantic clarification about what DONTCACHE guarantees, and extensive benchmark data comparing whole-BDI flusher wakeup against per-inode writeback approaches. The thread remains focused on performance optimization for existing RWF_DONTCACHE functionality in the mm/writeback subsystem, with implications for NFS server (NFSD) I/O modes.

Prior Context (Brief)

Last week, Jeff Layton submitted v2 of a three-patch series replacing inline filemap_flush_range() calls with wakeup_flusher_threads_bdi() to offload DONTCACHE writeback from the writer's hot path. Christoph Hellwig and Jan Kara raised concerns that kicking the entire BDI flusher could trigger excessive writeback of unrelated dirty pages. Hellwig proposed tracking DONTCACHE-specific folios with a new WB_start_dontcache bit, while Kara suggested marking inodes with "dropbehind" folios for prioritized writeback.

This Week's Discussion

Semantic Interpretation of DONTCACHE Guarantees

Jan Kara and Jeff Layton debated the semantics of Hellwig's proposal to expedite writeback proportional to pending dontcache folios while still processing LRU inodes.

Kara raised a concern about potential delays for mixed workloads:

"So that may result in dontcache folios staying cached for quite some time if DONTCACHE and normal writes are mixed. But I agree over longer time it might just level out so maybe that's fine." Jan Kara

Layton responded with a clarifying interpretation of the DONTCACHE contract:

"I think that's probably OK. In my interpretation, DONTCACHE on write just means 'don't cache this data beyond what's needed for writeback'. It doesn't provide any guarantees about when the writeback will be done." Jeff Layton

This semantic distinction is significant: if DONTCACHE merely means "eventually write back, don't retain in cache," then LRU-based ordering with expedited volume is acceptable. If it implies more immediate writeback guarantees, a more targeted approach would be necessary.

Per-Inode Writeback Benchmarks: The Batching Problem

The most substantial contribution this week came from Layton on April 16, who published detailed fio benchmark results comparing the whole-BDI flusher approach (current v2 proposal) against a per-inode writeback alternative he had drafted.

Layton concluded that per-inode writeback should be abandoned:

"I think we're probably better off not doing this because we lose some batching opportunities by trying to force out a single inode's pages rather than allowing the thread to do its thing." Jeff Layton

Key Benchmark Findings

Single-Client Workloads:

  • Sequential write: Essentially identical between whole-BDI (1450 MB/s) and per-inode (1438 MB/s)
  • Random write: Per-inode regressed -21% (363 → 286 MB/s) with p99.9 latency worsening from 1.8ms to 16.7ms

Multi-Writer Workloads (Scenario A):

  • Aggregate throughput: Per-inode regressed -32% (1478 → 999 MB/s)
  • p99.9 latency: Worsened by 67% (46ms → 77ms)

Noisy Neighbor Scenarios:

  • Scenario D (mixed-mode writer + buffered readers): Essentially identical or slightly better for per-inode (+2% reader throughput, +19% better p99.9 latency)

Root Cause: Loss of I/O Batching

The analysis identified the core issue: writeback_sb_inodes() processes all dirty inodes in a single blk_plug'd pass, enabling efficient I/O merging. Per-inode write_inode_now() calls are processed serially, losing this batching benefit:

"With whole-BDI, the flusher did one batched pass through all dirty inodes via writeback_sb_inodes(). With per-inode, each of 4 writers queues a separate work item processed serially by write_inode_now() — losing the batch I/O merging benefit." Analysis included in

NFS Client Relevance

While this thread targets the core mm/writeback subsystem, it has direct implications for NFS server (NFSD) performance. The RWF_DONTCACHE mode is one of three I/O modes configurable via NFSD debugfs controls. Improving dontcache write performance benefits NFS workloads relying on this mode for low-latency, cache-bypassing writes. Layton's benchmark suite includes tests against an NFS server using fio's libnfs backend.

Final Conclusions

This week established two important conclusions:

  1. Semantic agreement: DONTCACHE is interpreted as "eventually write back, don't retain in cache" rather than guaranteeing immediate writeback. This relaxes the requirements for the flusher mechanism.

  2. Per-inode writeback rejected: Extensive benchmark data demonstrates that per-inode writeback approaches lose critical I/O batching benefits, causing significant regressions in random write and multi-writer scenarios. The whole-BDI flusher approach remains preferable despite concerns about triggering excessive writeback of unrelated pages.

The discussion remains open on how to address Hellwig's concern about whole-BDI wakeup being too coarse-grained. No v3 patches were submitted this week, and the thread awaits further architectural direction.
