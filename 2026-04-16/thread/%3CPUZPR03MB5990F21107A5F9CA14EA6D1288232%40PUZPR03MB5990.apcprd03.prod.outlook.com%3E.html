NFS pNFS: Grace-period caching of data server entries rejected

Summary

Overview

This week saw a brief but definitive exchange around a proposed optimization for pNFS (parallel NFS) data server cache management in the Linux NFS client. Lei Yin submitted a patch to introduce a "grace period" for data server cache entries, aiming to reduce churn in open/close-heavy workloads. The proposal was promptly rejected by NFS client maintainer Trond Myklebust on protocol-compliance grounds.

The Proposal: Deferred Destruction of Data Server Cache Entries

Lei Yin submitted a single patch titled "NFS: pnfs: cache data server entries for a short grace period." The patch addresses a performance concern in the pNFS client:

"pNFS data server cache entries are currently destroyed as soon as the last reference is dropped. Workloads that repeatedly open and close the same files can end up tearing down and rebuilding the same data server cache entries over and over, even when the reuse interval is very short."

The proposed solution was to defer destruction of data server cache entries using delayed work. If the same data server was looked up again before a timeout expired, the pending destroy would be cancelled and the existing entry reused. The patch also included a cleanup measure for network namespace teardown:

"Because destruction is now deferred, reap scheduled destroy work during netns teardown before checking that the data server cache is empty."

This is classified as a bug/performance fix targeting unnecessary cache churn in the NFS client's pNFS subsystem.

The Rejection: Protocol Non-Compliance

Trond Myklebust issued an immediate and unambiguous rejection in his reply here:

"NACK. This approach is the same as was presented a few months ago on this list."

The maintainer noted that this proposal had been raised previously and rejected for the same reason. The core objection centers on compliance with RFC 8881, Section 12.2.10, which governs device ID behavior in pNFS:

"As stated at the time, it does not agree with the description of deviceid behaviour in RFC8881 section 12.2.10."

Myklebust clarified what a compliant approach would require:

"If you want to cache entries on the client when not holding a layout, then you need to request a deviceinfo notification so that you can detect changes."

In other words, simply keeping stale data server entries alive via a timer-based grace period risks using outdated or invalid device information. The RFC mandates that clients must actively subscribe to device info notifications to safely cache such entries when no layout is held — ensuring they are alerted to any changes in the server's state.

Key Technical Arguments

  1. Performance motivation: Repeated open/close cycles cause unnecessary teardown and recreation of pNFS data server state, adding latency.
  2. Proposed mechanism: Timer-based deferred destruction with early cancellation on reuse.
  3. Maintainer's objection: The approach violates RFC 8881 §12.2.10 regarding device ID lifecycle management. Caching entries without holding a layout requires active subscription to device info notifications, not passive timer-based retention.

Final Conclusion

The patch was rejected (NACK). The maintainer's position is clear: any client-side caching of data server entries outside the scope of an active layout must be accompanied by proper deviceinfo notification subscriptions to detect changes, as mandated by the pNFS protocol specification. This closes the discussion for now, though it leaves open the possibility of a future, RFC-compliant implementation that uses deviceinfo notifications rather than simple grace-period timers.
