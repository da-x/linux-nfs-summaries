NFS Client: Inode Size Trust During Write Delegations — Reproduction Case Provided

Summary

NFS Client Fix: Don't Trust Server Inode Size During Write Delegations — Continued

Overview

This week, discussion continued on Oracle engineer Dai Ngo's bug fix patch addressing a subtle correctness issue in the NFS client's handling of inode metadata when holding write delegations. The thread, originally opened last week with the initial patch submission, saw two exchanges this week between Dai and Linux NFS client maintainer Trond Myklebust.

Classification: Bug fix — NFS client (fs/nfs/inode.c)

Background (Prior Week)

Last week, Dai Ngo submitted a patch to nfs_wcc_update_inode in fs/nfs/inode.c, arguing that the client should not unconditionally overwrite its locally cached file size with server-reported values while holding an active write delegation. As Dai explained in the original submission:

"With a write delegation, the server permits the client to buffer writes and associated metadata updates (including file size changes) locally and defer propagating them to the server. As a result, the server-reported GETATTR size may legitimately lag behind the client's cached size for the duration of the delegation, so it must not be treated as authoritative."

The patch adds a guard condition: the cached inode size is updated from server data only when the client does not hold a write delegation, or when the NFS_INO_INVALID_SIZE cache invalidation flag is set.

This Week's Discussion

Trond Myklebust Questions the Rationale

On April 13, NFS client maintainer Trond Myklebust responded to the patch, questioning whether the described issue actually manifests in practice. He pointed to an existing safeguard in the codebase:

"Under what circumstances are you seeing this making a difference? Please see the call to nfs_writeback_check_extend() in nfs_writeback_update_inode() which is supposed to prevent the issue you're talking about." Trond Myklebust

This response indicates that Trond believed the existing nfs_writeback_check_extend() function in the writeback path already handled the scenario Dai was describing, and requested a concrete reproduction case to justify the additional fix.

Dai Ngo Provides a Reproduction Case

In reply on April 16, Dai Ngo confirmed the bug manifests as actual file corruption under specific conditions:

"I see file corruption when running the git test with v4.2 and pNFS with SCSI layout:" Dai Ngo

Dai specified the reproduction involves:

  • NFSv4.2 protocol version
  • pNFS with SCSI layout (parallel NFS using block storage layouts)
  • Running Git's test suite (make -j100 under GIT_TEST_EXT_CHAIN_LINT=0)

This is a significant finding, as it demonstrates the issue is not merely theoretical but results in tangible data corruption in a real-world workload involving pNFS—a feature set used for high-performance NFS deployments with block storage backends.

Evolution and Status

The discussion evolved from Dai's initial patch submission to a maintainer-requested justification, culminating in a concrete reproduction case that validates the bug's existence. The key technical question raised by Trond—whether nfs_writeback_check_extend() already covers this scenario—remains open at week's end. Dai's reply confirms the corruption occurs despite existing safeguards, suggesting either:

  1. The existing nfs_writeback_check_extend() path does not cover all code paths where stale server sizes can overwrite client state, or
  2. There is a race condition or specific pNFS-related scenario that bypasses the existing protection.

No final resolution or patch acceptance was recorded this week; the thread remains open for further technical analysis.

Significance

This bug fix targets a correctness issue in NFS client metadata handling during write delegations—a core optimization mechanism in NFSv4. The fact that it manifests as file corruption under pNFS with SCSI layouts underscores the importance of rigorous delegation state management, particularly in high-performance storage configurations where data integrity is paramount.
