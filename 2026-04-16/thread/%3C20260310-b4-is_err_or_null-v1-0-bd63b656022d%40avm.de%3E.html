IS_ERR_OR_NULL Refactor: Krzysztof Kozlowski Identifies Bug and Condemns Coccinelle Script

Summary

This week, the long-running discussion surrounding Philipp Hahn's 61-patch series to replace manual IS_ERR() + NULL checks with IS_ERR_OR_NULL() received a sharp rebuttal from Krzysztof Kozlowski. His intervention elevated the debate from stylistic preference to concrete correctness concerns, highlighting both a latent bug introduced by one of the patches and a broader philosophical objection to the Coccinelle script driving the series.

Classification: Code cleanup / refactoring. This is not a protocol change, new feature, or bug fix in NFS itself; however, Kozlowski's comments expose how mechanical refactoring can introduce bugs.

Bridge from Prior Weeks

The series was submitted on March 10th Philipp Hahn. The sole NFS-relevant patch, [PATCH 30/61] net/sunrpc, was accepted in March with Reviewed-by tags from Jeff Layton and Chuck Lever. Subsequent weeks saw growing pushback: Robin Murphy criticized the mechanical approach March 19 summary, and Al Viro delivered a harsh condemnation of the macro's proliferation April 9 summary.

This Week's Activity: Kozlowski's Two-Pronged Critique

Krzysztof Kozlowski posted two messages on April 16th, targeting both a specific patch and the Coccinelle script itself.

1. Bug Identification in [PATCH 55/61] interconnect

Responding to [PATCH 55/61], which targeted the interconnect subsystem, Kozlowski identified a semantic bug introduced by the mechanical replacement. The original code used WARN_ON(IS_ERR(path)), warning only on error pointers but not on NULL. The patch replaced this with WARN_ON(IS_ERR_OR_NULL(path)), thereby emitting a warning for perfectly valid NULL cases.

"IS_ERR_OR_NULL is simply discouraged, but beside of code preference, you just added bug here. This is clearly not equivalent and you emit warn on perfectly valid case!" Krzysztof Kozlowski

This critique underscores a recurring theme: IS_ERR() and NULL often represent semantically distinct states. Conflating them via IS_ERR_OR_NULL() in warning contexts can produce false-positive warnings, degrading the signal-to-noise ratio of kernel diagnostics.

2. Rejection of the Coccinelle Script ([PATCH 01/61])

In his second message, Kozlowski targeted the Coccinelle semantic patch that automates the conversion. He argued that promoting IS_ERR_OR_NULL() through tooling is fundamentally misguided:

"Neither this, nor try from 2011, nor any future try should be accepted, because it creates impression IS_ERR_OR_NULL is somehow okay. No, it is not okay, it is a discouraged pattern leading to less readable and maintainable code." Krzysztof Kozlowski

He concluded with a firm stance against tool-assisted propagation of the pattern:

"We should not have therefore any tools suggesting usage of IS_ERR_OR_NULL, because people will be converting poor code into that, instead of fixing that poor code." Krzysztof Kozlowski

Key Technical Arguments

The discussion this week crystallized around two critical points:

  1. Correctness over Consistency: Kozlowski's identification of a bug in the interconnect patch demonstrates that mechanical refactoring can alter program semantics in harmful ways. When WARN_ON() is involved, the distinction between error pointers and NULL is not merely stylistic—it affects runtime behavior and debugging visibility.

  2. Tooling Philosophy: Kozlowski's rejection of the Coccinelle script adds a new dimension to the debate. While Robin Murphy (last month) argued that Coccinelle should be used responsibly as a discovery tool rather than an application tool, Kozlowski goes further: he argues that no tool should promote IS_ERR_OR_NULL() at all, because it perpetuates a coding pattern that obscures poor interface design.

Evolution of the Discussion

The thread has evolved from initial acceptance (March) to philosophical criticism (April 9, Al Viro) to concrete bug identification and tooling rejection (April 16, Kozlowski). The trajectory suggests increasing resistance at multiple levels:

  • Subsystem level: Some maintainers accept patches for consistency; others reject them for clarity.
  • Core kernel level: Al Viro's condemnation signals high-level opposition.
  • Tooling level: Kozlowski's rejection of the Coccinelle script challenges the methodology itself.

Final Conclusions

  • NFS Impact: The NFS/sunrpc patch was accepted in March and remains unchanged. No new NFS-specific activity occurred this week. However, Kozlowski's bug identification serves as a cautionary tale for any subsystem that accepted similar mechanical changes without careful review of semantic equivalence.
  • Series Status: The series faces mounting opposition. With Al Viro condemning the macro as "crap" and Kozlowski identifying concrete bugs and rejecting the automation tool, future patches in this series are likely to face heightened scrutiny or outright rejection.
  • Key Takeaway for NFS Developers: While the NFS/sunrpc patch was reviewed and accepted, the broader discussion highlights the importance of contextual code review over mechanical refactoring. As Kozlowski demonstrated, even seemingly harmless macro substitutions can introduce behavioral regressions when applied without understanding the semantic distinction between error pointers and NULL.
  • No Bug Fixes or Protocol Changes: This thread remains focused on code style and error-checking idioms. No NFS client bugs were fixed this week, nor were any protocol changes proposed.
