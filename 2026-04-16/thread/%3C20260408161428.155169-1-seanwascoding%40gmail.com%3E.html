NFS: RCU Safety and Tracing Pointer Fixes Refined

Overview

This week, the discussion around Sean Chang's two-patch series to fix RCU safety and tracing pointer issues in the NFS client evolved significantly following review by Benjamin Coddington. The patches are classified as bug fixes addressing Sparse static analysis warnings and potential concurrency hazards in fs/nfs/super.c and fs/nfs/nfstrace.h.

Last week, Sean Chang submitted the initial v1 series as described in prior summaries. This week, Benjamin Coddington provided detailed feedback on both patches, and Sean responded with plans for a revised v2 series incorporating those suggestions.

Patch 1: RCU Safety in nfs_compare_super_address

Technical Context

The first patch addresses unsafe access to the cl_xprt pointer in struct rpc_clnt, which is marked as __rcu. The original code in nfs_compare_super_address() dereferenced this pointer without RCU protection, risking use-after-free bugs during concurrent transport switches.

Review and Evolution

Benjamin Coddington raised a nuanced concern about the null-pointer check proposed in the patch:

"I'm not sure that's a great test, the rpc_xprt objects are refcounted. These might not be null but you could still race with a freeing path?" Ben Coddington

However, he also noted that the existing RCU section might already provide sufficient protection:

"I think you might just be safe inside the RCU section here because rpc_switch_client_transport() uses synchronize_rcu() before xprt_put(old). I didn't audit all the freeing paths." Ben Coddington

Additionally, Ben suggested narrowing the RCU critical section:

"Probably safe to drop the RCU protection scope after this point. No need to hold it over all the other checks.." Ben Coddington

Sean's Response

Sean acknowledged the feedback and proposed a more robust approach for v2, adding an XPRT_CONNECTED state check to ensure the transport is logically active, not just memory-safe:

"The XPRT_CONNECTED check ensures that the transport is not only memory-safe (via RCU) but also logically active. Since the RPC layer clears this bit before initiating the teardown of an rpc_xprt, this prevents accessing xprt_net on an object that is on the freeing path." Sean Chang

He also agreed to narrow the RCU scope:

"I will move rcu_read_unlock() to immediately after the net_eq check in v2 to keep the critical section as small as possible." Sean Chang

Patch 2: Tracing Pointer Safety in nfs_page_class

Technical Context

The second patch aimed to resolve a Sparse warning about dereferencing a __private-marked pointer in the nfs_page_class tracepoint by changing the field type from a pointer to unsigned long.

Review and Evolution

Benjamin Coddington pointed out a security concern with bypassing kernel pointer obfuscation:

"Probably we don't want to bypass the %p formatting because some configurations use it to obfuscate kernel pointers." Ben Coddington

He further clarified that the __private annotation was likely incorrect in this context:

"I think in this context the __private annotation is incorrect. We deref the nfs_page pointer only in TP_fast_assign() which runs at the call site, and the TP_printk only outputs the pointer value." Ben Coddington

Sean's Response

Sean concurred and outlined his plan for v2:

"I realize that using unsigned long results in printing the raw pointer address, which bypasses the intended %p formatting. You are right that the __private annotation is not appropriate here... I will rework the patch to remove __private and keep the pointer type with %p formatting." Sean Chang

Final Conclusions

The discussion this week refined both patches significantly:

  1. RCU Safety Fix: The v2 patch will add an XPRT_CONNECTED state check for robustness against freeing paths and narrow the RCU critical section to only cover the network namespace comparison, improving both safety and performance.

  2. Tracing Fix: Rather than changing the field type to unsigned long, the v2 patch will retain the pointer type with %p formatting and remove the incorrect __private annotation, preserving kernel pointer obfuscation features while satisfying Sparse.

Both patches remain bug fixes targeting correctness and static analysis compliance in the NFS client. A revised v2 series is expected shortly.
