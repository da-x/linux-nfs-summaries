exportfs: NFSv4 state release on unexport committed to nfs-utils

exportfs: Release NFSv4 state on last client unexport — Committed

Summary

This thread, which began last week with Chuck Lever's submission of a patch to nfs-utils and received a positive review from Jeff Layton, concluded this week with the patch being merged into the upstream codebase.

This Week's Activity

On April 12, Steve Dickson confirmed that the patch has been accepted and integrated:

"Committed... (tag: nfs-utils-2-9-2-rc1)" Steve Dickson

This marks the successful completion of the review and merge cycle for this enhancement to exportfs.

Background (Bridged from Prior Week)

As summarized last week, Chuck Lever submitted version 2 of a patch addressing a resource cleanup issue in NFS server administration. The problem was that when an administrator removes the last client for a given export path using exportfs -u, associated NFSv4 state (opens, locks, and delegations) could persist, keeping the underlying filesystem busy and preventing unmount operations.

The patch introduced logic to send an NFSD_CMD_UNLOCK_EXPORT command to the kernel via generic netlink when no exports remain for a path, thereby revoking the associated NFSv4 state and closing cached file handles. Jeff Layton provided a review with minor feedback on conditional compilation guards but otherwise approved the implementation:

"The rest looks good." Jeff Layton

Classification

This discussion concerns a bug fix and usability improvement for NFS server administration tooling (exportfs in nfs-utils). It is not a new feature or protocol change, but rather a correction to ensure proper cleanup of NFSv4 state during export removal operations.

Conclusion

The patch has been merged into nfs-utils under the release tag nfs-utils-2-9-2-rc1. This fix ensures that administrators can cleanly unmount filesystems after removing the last client export, resolving a practical maintenance pain point in NFS server management.
