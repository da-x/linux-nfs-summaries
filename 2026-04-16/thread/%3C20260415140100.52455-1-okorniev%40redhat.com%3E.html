NFSv4: Retry GETATTR on Directory Delegation Failure (v2)

Summary

NFSv4: Retry GETATTR on Directory Delegation Failure (v2)

Classification

This is a bug fix for the NFSv4 client, addressing an issue where opportunistic directory delegation requests cause otherwise valid GETATTR operations to fail and propagate errors to userspace.

Prior Context (Brief)

On April 10, Olga Kornievskaia submitted v1 of this patch 20260410164805.57887-1-okorniev@redhat.com, which introduced the core idea of retrying GETATTR without a directory delegation when the initial combined request fails. The v1 submission noted an alternative approach:

"Note: instead of clearing NFS_INO_REQ_DIR_DELEG perhaps turning off directory delegations for the whole server is appropriate but I wasn't sure."

This Week's Activity

On April 15, Olga Kornievskaia submitted v2 of the patch 20260415140100.52455-1-okorniev@redhat.com, refining the fix to handle a specific edge case involving BSD servers. This is the only message in this thread for the current week; no further discussion occurred before the window closed.

The Problem

The NFSv4 client opportunistically requests directory delegations by piggybacking GET_DIR_DELEGATION onto existing GETATTR calls — an optimization introduced by commit 156b09482933 ("NFS: Request a directory delegation on ACCESS, CREATE, and UNLINK"). However, when the server declines or fails to grant the delegation, the entire compound operation fails, causing the legitimate GETATTR request to error out as well.

As Olga Kornievskaia explained in the patch description:

"Currently, getting a directory delegation is opportinistic and gets added to an existing GETATTR that's trying to retrieve some needed attributes. However, GET_DIRDELEGATION can fail and that currently causes a GETATTR to fail and an error is propagated to the user."

The Fix

The patch modifies fs/nfs/nfs4proc.c (9 lines added) to implement two key behaviors:

  1. Retry without delegation: If a GETATTR combined with a directory delegation request fails, the client retries the original GETATTR operation without requesting a directory delegation.
  2. Per-inode suppression: The client clears the flag requesting a directory delegation for that specific inode, preventing repeated failures on the same file handle.

v2 Changes: BSD Server Compatibility

The primary change in v2 addresses an edge case with certain server implementations. Olga noted:

"BSD server can return NFS4ERR_NOFILEHANDLE when requesting directory delegations on "/" that isn't exported."

This refinement ensures the client gracefully handles scenarios where a BSD-based NFS server returns NFS4ERR_NOFILEHANDLE when directory delegation is requested on a root path ("/") that is not exported. Without this fix, such servers would trigger spurious errors for clients attempting to retrieve attributes from those directories.

Significance for NFS Client Development

  1. User-Visible Reliability: This fix prevents unexpected errors from reaching applications when the server simply declines an opportunistic delegation — a scenario that should be transparent to the user.
  2. Server Interoperability: The v2 update specifically improves compatibility with BSD-based NFS servers, broadening the client's robustness across diverse server implementations.
  3. Targeted Optimization Preservation: Rather than disabling directory delegation requests entirely (which Olga considered as an alternative), the fix preserves the optimization for successful cases while providing a graceful fallback path on failure.

Conclusion

This week saw the submission of v2 of Olga Kornievskaia's GETATTR retry fix, incorporating a BSD server compatibility improvement over the v1 posted earlier in the week. The patch addresses a genuine usability bug where opportunistic delegation failures incorrectly propagate to userspace. With no objections raised this week, the fix appears ready for maintainer review and merge.
