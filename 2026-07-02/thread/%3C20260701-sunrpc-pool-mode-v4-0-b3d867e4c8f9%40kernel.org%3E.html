sunrpc pool_mode v4: NeilBrown reviews all four patches, Fixes tag corrected to bfd241600a3b

Summary

sunrpc pool_mode v4: review round lands, Fixes: tag finally pinned down

Type: Server-side bug fix + cleanup in the sunrpc (NFS server) layer. This is not an NFS client feature or protocol change — it concerns how nfsd schedules RPC work across NUMA pools on the server. The week's headline is a genuine bug fix: a latent request-starvation bug that becomes reachable once the "global" pool escape hatch is removed, plus a performance micro-optimization in the enqueue hot path.

Bridging prior weeks (brief)

This thread has been running for several weeks. Layton posted v2 on June 25, and that week's discussion was dominated by Chuck Lever's warning that with nrservs < number of NUMA nodes, trailing pools end up with zero threads and the enqueue path has no fallback — a connection landing on an empty pool would hang indefinitely. NeilBrown and Layton converged on a "belt-and-braces" plan: guarantee ≥1 thread per CPU-bearing node during auto-distribution, honor explicit userland per-pool arrays as-is, and add a queueing-path fallback to a populated pool. v3 landed June 29 implementing that plan, but it also dragged in a follow-on RCU patch (5/4) to fix a preexisting use-after-free race in the lockless pool-map reader — and NeilBrown pushed back on the RCU approach as overkill. That RCU debate is where v4 picks up: Layton dropped the RCU patch entirely and instead folded the pooled-service gate directly into the main series.

This week's activity (July 1–2)

The v4 series lands (July 1, ~20:00 UTC)

Jeff Layton posted v4 as a four-patch set. The cover letter is terse about what changed:

This version drops the 5/4 follow-on patch that I had sent after the original series, and changes the second patch to not allow unpooled services to consult the map.

Patches #1 and #3 address what is a shortcoming of the existing code -- namely that the server can be configured to schedule RPCs to pools with no threads in them.

The four patches:

  1. Route to a populated pool (1/4) — the core starvation fix. svc_pool_for_cpu() now skips pools with no threads and falls back to a populated one, trading NUMA locality for guaranteed service. Carries Fixes: 0f0257eaa5d2 (which NeilBrown will dispute).
  2. Hardcode pool_mode to pernode (2/4) — removes the SVC_POOL_AUTO/GLOBAL/PERCPU/PERNODE enum, mode-selection heuristic, and all mode-based switch statements (−215/+49 lines net). The module parameter and netlink interface are preserved for backward compatibility; writing any previously-accepted value "succeeds silently," reading always returns "pernode." This is where the RCU debate was resolved: instead of protecting pool_to[] with RCU, Layton now gates the map lookup in svc_new_thread() on sv_is_pooled, so unpooled services (lockd, NFS callback) use NUMA_NO_NODE and never touch the shared array.
  3. Guarantee a thread per CPU-bearing node (3/4) — floors each CPU-bearing node's pool at one thread during auto-distribution, while leaving explicit svc_set_pool_threads() callers unchanged.
  4. Eliminate a modulus from the enqueue path (4/4) — a micro-optimization that "trades a ~20-30 cycle operation that isn't pipelined and monopolizes the divider for a ~1 cycle well-predicted branch."

NeilBrown's rapid-fire review (July 1, ~22:00–22:40 UTC)

NeilBrown replied to all four patches within roughly an hour of each other — a fast, thorough review pass.

On patch 1/4 (his reply): NeilBrown challenged the Fixes: tag immediately:

Why that commit? Did this ever work correctly? It seems more likely that Fixes: 3262c816a3d7 ("[PATCH] knfsd: split svc_serv into pools") is appropriate.

He also asked whether a WARN_ON_ONCE() would be appropriate for the "no pool has any threads" fallback path, then gave his endorsement:

I think this is a sensible defensive-programming approach. Reviewed-by: NeilBrown neil@brown.name

On patch 2/4 (his reply): NeilBrown approved but flagged a further simplification opportunity:

I think this patch is good, but there is probably room for further simplification which is probably best left to a later patch. In particular, ->sv_nrpools is now either '1' or svc_pool_map.count, and these possibilities match ->sv_is_pooled. So we only need one of those.

On patch 3/4 (his reply): NeilBrown pointed out a redundant condition — svc_pool_map_init_pernode() uses for_each_node_with_cpus(), so every allocated pool is guaranteed to have at least one CPU. He suggested a cleaner formulation:

I would probably address the problem outside the loop with if (base == 0 && nrservs != 0) /* We need at least one thread per pool for correct functionality */ remain = serv->sv_nrpools; or similar. But your version works too and this isn't performance-critical code.

On patch 4/4 (his reply): NeilBrown tied the modulus elimination back to his earlier simplification suggestion:

I would rather discard ->sv_nrpools as described in previous reply, then this modulus would disappear as it isn't needed.

Layton's responses (July 2, ~12:00–13:00 UTC)

Layton replied to each of NeilBrown's four reviews the next morning. The most substantive exchanges:

The Fixes: tag saga (patch 1/4). Layton first conceded NeilBrown's point: in his initial reply, "Indeed. Good catch." But then, in a follow-up message just 14 minutes later, he reversed course after deeper investigation:

I had the LLM run this down. We're both wrong. It briefly worked properly after 3262c816a3d7 ("split svc_serv into pools"), but then was broken in the same series in commit bfd241600a3b ("knfsd: make rpc threads pools numa aware"). So I think we want: Fixes: bfd241600a3b ("knfsd: make rpc threads pools numa aware")

This is a notable moment — both the original author and the reviewer had the wrong commit, and the correct Fixes: tag required tracing the bug's introduction through two consecutive commits in the same series. The bug was introduced by the NUMA-awareness patch, not the initial pool-splitting patch.

On NeilBrown's WARN_ON_ONCE() suggestion for the "no pool has any threads" path, Layton pushed back with a practical concern:

This is probably not feasible, as there are cases where we legitimately queue the call to a pool with no threads. At startup, we create listeners and then threads only get spun up later. If we get a RPC on the listener port during that window, the message would fire. There's a similar window on shutdown. It might not hurt to add a tracepoint there though.

He settled on a middle ground: "Maybe a pr_notice_once()? A stack trace isn't particularly helpful here, but it would be good to let someone know that this isn't optimally configured. I'll add one for v5."

The sv_nrpools vs. sv_is_pooled simplification (patch 2/4). NeilBrown had suggested removing sv_nrpools entirely since it's now derivable from sv_is_pooled. Layton pushed back with a concrete counterexample:

I took a look at that cleanup, but it's not quite the same.

  • unpooled service (lockd, NFS callback): sv_is_pooled=false, sv_nrpools=1
  • pooled service on a single-node host: sv_is_pooled=true, sv_nrpools=1 (pernode degenerates to one pool)
  • pooled service on multi-node: sv_is_pooled=true, sv_nrpools=N>1 So you can't derive sv_is_pooled from sv_nrpools because of the single-node case.

He also flagged a performance concern: "it also means that we'd have to create more accessors for the svc_pool_map. There are several places that access sv_nrpools that would have to be converted to get it from the map. That may have performance implications too since the map is accessed during receives." The conclusion: "this kind of cleanup is doable, but it's a bit messier than it sounds at first."

The thread-floor formulation (patch 3/4). Layton simply agreed with NeilBrown's cleaner approach: in his reply, "I like your version better. I'll adopt it."

Key technical arguments & evolution

  1. The starvation bug fix is now fully reviewed and approved. All four patches carry NeilBrown's Reviewed-by. The core fix — routing to a populated pool when the selected one has no threads — is settled. This is the headline bug fix of the week, and it directly implements the belt-and-braces consensus reached during v2 review.

  2. The RCU debate was resolved by elimination. Last week's open question (RCU vs. pooled-service gate for the pool_to[] race) was resolved not by choosing one approach over the other, but by dropping the RCU patch entirely and folding the sv_is_pooled gate directly into patch 2/4. Unpooled services now use NUMA_NO_NODE and never consult the shared map, sidestepping the race without any synchronization machinery.

  3. The Fixes: tag required three rounds to get right. Layton's original tag (0f0257eaa5d2) was wrong; NeilBrown's suggested correction (3262c816a3d7) was also wrong. The correct tag is bfd241600a3b ("knfsd: make rpc threads pools numa aware"), which introduced the bug in the same series that created the pool infrastructure. This matters for backporting: the fix needs to go into kernels containing bfd241600a3b, not just the earlier pool-splitting commit.

  4. The modulus elimination (patch 4/4) may become moot. NeilBrown's suggestion to remove sv_nrpools entirely would make the modulus unnecessary, but Layton demonstrated that the single-node case prevents a clean derivation. The modulus patch stands as a standalone micro-optimization for now.

  5. Startup/shutdown race window is a known limitation. Layton identified that during service startup (listeners created before threads are spun up) and shutdown, RPCs can legitimately land on threadless pools. This means the "no pool has any threads" fallback path is not purely an error condition — it's a transient normal state. A WARN_ON_ONCE() would false-positive; a pr_notice_once() or tracepoint is more appropriate (planned for v5).

Relevance to NFS client development

While this is server-side sunrpc code, the stakes for clients are concrete:

  • The starvation fix prevents indefinite connection hangs. A client connecting to an NFS server with fewer nfsd threads than NUMA nodes would previously have its transport enqueued on an empty pool and hang forever. With this fix, the work is routed to a populated pool. This is a direct reliability improvement for any client talking to a multi-NUMA NFS server.
  • The modulus elimination (patch 4/4) improves enqueue latency. The hot path that determines which pool services an incoming RPC now uses a ~1-cycle branch instead of a ~20-30 cycle division. On busy servers handling many concurrent client connections, this reduces per-RPC overhead.
  • The pernode default change (patch 2/4) alters NUMA behavior for all NFS servers. Services that previously ran with a single global pool now get one pool per NUMA node by default, giving proper thread affinity and NUMA-local memory allocation. Clients on multi-NUMA hosts will see improved latency characteristics.

Final status (as of window close)

The v4 series is fully reviewed — NeilBrown has given Reviewed-by on all four patches. The open items are minor:

  • Layton will adopt NeilBrown's cleaner thread-floor formulation for patch 3/4 in v5.
  • A pr_notice_once() or tracepoint for the "no pool has any threads" path is planned for v5.
  • The Fixes: tag for patch 1/4 needs updating to bfd241600a3b.
  • The sv_nrpools simplification is deferred to a future cleanup.

The series appears close to merge-ready, pending these small v5 tweaks and the NFS maintainer's (Chuck Lever's) final sign-off. No v5 has been posted within this window.
