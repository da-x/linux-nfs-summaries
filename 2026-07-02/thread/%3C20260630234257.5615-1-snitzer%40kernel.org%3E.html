NFSv4.2 client support for UNCACHEABLE_FILE_DATA and UNCACHEABLE_DIRENT_METADATA (v2)

Summary

NFSv4.2 "uncacheable" attributes: v2 patch series posted

Status this week: On 2026-06-30, Mike Snitzer posted a six-patch v2 series adding Linux NFSv4.2 client support for two companion, per-object "uncacheable" attributes defined in IETF drafts. The thread consists solely of the patch postings — there is no reviewer discussion yet in this window, so the entry below documents what was submitted and its technical rationale rather than a back-and-forth debate.

What kind of change it is

This is a new feature (client-side protocol support), not a bug fix or a wire-protocol change. It implements two optional, read-write boolean attributes from two companion IETF drafts:

  • UNCACHEABLE_FILE_DATA — FATTR4 87, draft-ietf-nfsv4-uncacheable-files: a per-regular-file flag telling the client to stop caching the file's data (both write-behind and read caching).
  • UNCACHEABLE_DIRENT_METADATA — FATTR4 88, draft-ietf-nfsv4-uncacheable-directories: a per-directory flag telling the client to refetch directory-entry metadata (names plus per-entry size/timestamps) from the server on each READDIR rather than serving it from the readdir cache.

The two attributes are independent and apply to disjoint object types — "a regular file may carry 87, a directory 88." The Linux client only honors a server-set attribute; it never sets either itself.

Motivation

As Snitzer explains in the cover letter, the driving use case is multi-protocol namespaces:

"The motivating deployments expose a single namespace concurrently through NFSv4.2, NFSv3, and SMB, plus server-side policy engines, so file data and directory contents can change faster than a typical client cache lifetime -- producing stale reads and read-modify-write 'write holes' for file data, and stale size/timestamp listings for directories."

The six patches

  1. Add UNCACHEABLE_FILE_DATA attribute support (patch 1/6) — originally by Tom Haynes, adapted by Snitzer. Decodes the attribute via GETATTR, tracks per-exported-filesystem support, and records it on the inode in NFS_I(inode)->uncacheable_file_data. Acting on it is deferred to a later patch.

  2. Request UNCACHEABLE_FILE_DATA only for regular files (patch 2/6) — the spec mandates that "a server MUST reject a query of it on any other object type with NFS4ERR_INVAL." The fix gates the request at the single choke point nfs4_bitmap_copy_adjust(), which clears the bit unless the target inode is a regular file (and also when the inode is NULL / unknown type). This covers GETATTR, SETATTR, LINK, LOOKUP, LOOKUPP and CREATE.

  3. Open UNCACHEABLE_FILE_DATA files with O_DIRECT (patch 3/6) — the core behavior change. A new NFS_CONTEXT_O_DIRECT open-context flag makes such regular files transparently opened with O_DIRECT, so reads and writes bypass the page cache without the application requesting it. Snitzer notes this follows the spec's model:

    "the attribute is 'similar in intent to O_DIRECT' and clients 'retain flexibility in how they satisfy the requirements'."

    Two notable design decisions stand out. First, on delegation interaction (spec Section 4.3), the implementation deliberately does not relax read caching under a held delegation:

    "an uncacheable file is opened O_DIRECT regardless of any delegation held, which is compliant ... and avoids decoupling read vs write caching behind a single open flag."

    Second, on I/O alignment: the spec's caveat about "well-formed I/O requests" does not constrain the over-the-wire path, because "the client readily issues misaligned I/O using O_DIRECT over SunRPC to the remote NFS server"; only the LOCALIO fallback path is affected by alignment.

  4. Add UNCACHEABLE_DIRENT_METADATA attribute support (patch 4/6) — mirrors patch 1 for directories, recording the flag in NFS_I(inode)->uncacheable_dirent_metadata. Notably it is not tied to the cache_validity / file-delegation machinery, because "a directory cannot hold an NFSv4 read/write (file) delegation," so there is no authoritative cached state to optimize against.

  5. Request UNCACHEABLE_DIRENT_METADATA only for directories (patch 5/6) — the directory-side analogue of patch 2, stripping the bit in nfs4_bitmap_copy_adjust() unless the target is known to be a directory. The result: "a regular file requests file_data and never dirent_metadata, a directory requests dirent_metadata and never file_data, and an unknown/other object requests neither."

  6. Honor UNCACHEABLE_DIRENT_METADATA by refetching readdir (patch 6/6) — the core behavior change for directories. For a marked directory, nfs_readdir() bypasses the page cache by forcing the -EBADCOOKIE path (including the start-of-directory case), so every readdir goes to the server. Crucially, it also forces READDIRPLUS, because plain READDIR only refreshes names while leaving per-entry attributes to the inode caches:

    "Forcing READDIRPLUS makes each READDIR refresh the entries' attribute caches (via nfs_prime_dcache() -> nfs_refresh_inode()), so a subsequent stat() observes current values."

Changes since v1

The cover letter documents the v2 refinements, the most significant being a simplification of the XDR plumbing: the v1 patch that added generated xdrgen definitions was dropped in favor of open-coding the constant alongside other hand-defined FATTR4 protocol-extension constants. The per-inode flag is now a bool ... : 1 bitfield, stray blank lines were cleaned up, and — most importantly for this week's scope — client support for the companion UNCACHEABLE_DIRENT_METADATA attribute (patches 4–6) was added, expanding the series from a file-data-only effort to both attributes.

Conclusion

This is a clean, well-scoped feature addition that gives the Linux NFSv4.2 client the ability to honor server-side "stop caching" hints for both file data and directory metadata — directly addressing stale-read and write-hole problems in multi-protocol (NFSv4.2 + NFSv3 + SMB) shared namespaces. The design leans on existing mechanisms (O_DIRECT for file data, READDIRPLUS for directory metadata) rather than inventing new I/O paths, and it carefully gates attribute requests by object type to satisfy the drafts' NFS4ERR_INVAL requirements. No maintainer or reviewer response has landed in this week's window yet, so the series is awaiting review.
