NeilBrown posts 10-patch nfsd4_create_file() refactor to prep for vfs_lookup_open(); Chuck Lever flags Sashiko findings and merge-ordering question

Summary

NeilBrown's 10-patch nfsd4_create_file() refactor lands; Chuck Lever raises two high-level concerns

What happened this week

On July 2, NeilBrown posted a 10-patch series titled "nfsd: refactor nfsd4_create_file()", targeting the nfsd-testing tree. The series is explicitly a preparatory refactoring for the larger vfs_lookup_open() effort (the 18-patch RFC that Christian Brauner green-lited earlier this same week in a sibling thread). NeilBrown frames the motivation clearly:

"nfs4_create_file() duplicates knowledge about opening a file which exists in the VFS, mostly in lookup_open(). It does use dentry_create() which shares some code, but there is more code that could be shared."

"The nfsd code doesn't get some details quite right, particularly patch 05 shows this."

"I hope to introduce a new VFS interface which encapsulates more of what nfsd needs and shares more code with lookup_open(). I particularly want this as it will simplify some changes to locking rules that I am working on."

So the series is not itself a protocol change or a user-visible feature. It is a server-side (nfsd) refactoring with bug-fix motivation, designed so that when the new VFS interface lands, nfsd can "switch over fairly easily." NeilBrown adds a candid caveat: "Hopefully the series helps clarity even before that happens."

The ten patches at a glance

The series walks nfsd4_create_file() through a sequence of increasingly structural rearrangements. Read together, they separate NFS-specific preamble from VFS interaction, tighten locking ranges, and fix a subtle correctness gap around who actually created the file:

  1. PATCH 01/10 — Replaces fh_fill_both_attrs() with a new fh_fill_post_noop(). The idea: call fh_fill_pre_attrs() once early so "errors only need to be caught in one place," then mark pre-fetched attrs valid via the new post-noop helper when no creation happens.
  2. PATCH 02/10 — Moves fh_want_write() to just before it is actually needed, letting preamble errors "be returned immediately rather than needing to 'goto out'."
  3. PATCH 03/10 — Pushes more NFS-specific prep into the preamble, ahead of any VFS interaction.
  4. PATCH 04/10 — Unifies the NFS4_CREATE_EXCLUSIVE and NFS4_CREATE_EXCLUSIVE4_1 switch cases, which were "identical except for one line which is marked 'subtle' in both cases." Guarding the setattr with is_create_with_attrs() lets both cases share a single goto, making the code "clearer and less subtle."
  5. PATCH 05/10 — The substantive bug fix of the series. NeilBrown explains: "nfsd4_create_file() currently assumes that if a lookup failed but then a create succeeds, then the 'create' operation actually created the file. With atomic_open this may not be the case - some other actor might have created the file between the lookup and the create." The fix moves nfsd4_vfs_create() earlier and sets ->op_created from its result, using "! ->op_created" to trigger nfserr_exist handling. It also requires changing dentry_create() (in fs/namei.c) to "reliably set FMODE_CREATED when the file was actually created," not only under atomic_open.
  6. PATCH 06/10 — Removes a redundant NFSD_MAY_CREATE check, since dentry_create() already performs it.
  7. PATCH 07/10 — Narrows the directory-lock range: "We only need to hold the lock taken by start_creating() until the create has been attempted." NeilBrown notes the current longer hold "serves no purpose," since it doesn't even prevent a racing GETATTR, SETATTR, or OPEN.
  8. PATCH 08/10 — Open-codes nfsd4_vfs_create() back into nfsd4_create_file(), arguing the sub-function "doesn't really add clarity" and that merging "allows for some refactoring and ultimately using a different VFS interface."
  9. PATCH 09/10 — Moves code out of the d_really_is_negative() branch, a change whose benefit "isn't immediately obvious" but will "make it easier to switch to using vfs_lookup_open()."
  10. PATCH 10/10 — Splits the want_write range: one for create/open, and a second (only if needed) for setattr on a read-only open, so write access isn't held unnecessarily across both.

Chuck Lever's reply: two high-level concerns

NFS maintainer Chuck Lever responded the same day, with a full disclosure that "I haven't looked closely at these yet." He raised two points:

  1. A Sashiko finding. Lever points to an automated-review result, noting with dry humor:

    "Sashiko found something remarkable in 9 of the 10 patches in this series ... Which I commend to you for study ;-)"

    The fact that a static-analysis tool flagged 9 of 10 patches is a signal worth watching — it suggests a systematic issue (possibly a mechanical artifact of the refactor, or a genuine recurring mistake) that NeilBrown will need to address before the series can move forward. This is the single most important open item from this week's exchange.

  2. Merge-ordering against the in-flight VFS series. Lever asks:

    "We'll need to decide how to merge these given the other related series you have in flight that targets VFS code that NFSD consumes. Are these two series truly independent?"

    This directly echoes the coordination problem flagged in the sibling vfs_lookup_open() thread, where Brauner deferred ordering against his own O_CREAT|O_DIRECTORY work. The question here is whether this 10-patch nfsd refactor can be merged independently of (or ahead of) the VFS interface it is preparing for — a scheduling decision that will shape the next several weeks.

Evolution and context

This series sits squarely in the middle of a multi-week arc:

  • Prior weeks: NeilBrown's 18-patch RFC to replace dentry_create() with vfs_lookup_open() was reviewed, with Chuck Lever catching a protocol-breaking NFS4ERR_EXIST bug and an ATTR_SIZE truncation hazard in PATCH 17/18. Christian Brauner then green-lit a resubmission earlier this same week ("Yes, please resubmit").
  • This week: Rather than immediately resubmitting the VFS series, NeilBrown posted this 10-patch nfsd-side refactor — the "get it ready for switching to the new interface" work he described in the cover letter. The two efforts are coupled: this series restructures nfsd4_create_file() so that the later swap to vfs_lookup_open() is a smaller, cleaner change.

Notably, PATCH 05/10 here addresses the same class of correctness concern (who actually created the file under atomic_open) that was central to the earlier review, reinforcing that this refactor is doing real bug-fixing work and not just cosmetic shuffling.

Relevance to NFS client development

Although this is server-side nfsd code, the stakes for clients are concrete:

  • PATCH 05/10 fixes a create-race correctness gap. If another actor created the file between lookup and create (possible under atomic_open), the old code could misreport the outcome. Correct NFS4ERR_EXIST handling matters to any client relying on atomic-create semantics such as NFS4_CREATE_GUARDED.
  • Tighter locking (PATCH 07/10, PATCH 10/10) reduces contention on directory and mount write locks during create/open — a performance and scalability win for busy NFS servers serving many clients.
  • The unification with lookup_open() means re-exporting servers will eventually use a create/open path consistent with local filesystems, improving the atomicity guarantees clients can depend on.

Status and outlook

As of the close of this week's window:

  1. The 10-patch series is freshly posted (July 2) against nfsd-testing, with no substantive per-patch review yet — only Chuck Lever's two high-level remarks.
  2. The Sashiko finding across 9/10 patches is the most urgent open item; it will likely drive the next round of discussion and a possible v2.
  3. The merge-ordering question (independent vs. coupled with the vfs_lookup_open() VFS series) remains unanswered and will need resolution between Lever, NeilBrown, and Brauner.
  4. No client-facing protocol change is introduced by this series itself; its value is preparatory refactoring plus a genuine create-race bug fix.

The near-term expectation is that NeilBrown addresses the Sashiko findings and answers Lever's independence question, after which both this series and the resubmitted vfs_lookup_open() series will need coordinated scheduling against Brauner's pending O_CREAT|O_DIRECTORY work.
