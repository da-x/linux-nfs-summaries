lockd: Regenerate NLMv4 XDR code to pick up enum value validation

Summary

lockd: Regenerate NLMv4 XDR code

A short but consequential thread landed on the list this week, in which Chuck Lever resynced the checked-in NLM (Network Lock Manager) XDR decoder output with the current in-tree xdrgen tooling. The change is a pure regeneration — no protocol or specification changes — but it closes a real gap in input validation for several NFSv4 file-locking enums on both the client and server sides of lockd/nfsd.

The patch

Chuck Lever posted the single-patch series on 2026-06-30, explaining the motivation in the commit message:

"The checked-in NLMv4 xdrgen output predates the addition of enum value validation to generated decoders. As a result the decoders for fsh4_mode, fsh4_access, and nlm4_stats still accept any 32-bit value, while the current generator rejects values outside the enumeration."

He framed it as a hygiene fix rather than a behavioral change:

"This is a plain regeneration with no specification change; it also refreshes the recorded specification modification time to show that all existing enum decoders have picked up the xdrgen tool fix."

The diffstat touches nine files, with the substantive work concentrated in fs/lockd/nlm4xdr_gen.c (47 lines changed) and a handful of one-line header timestamp updates across fs/lockd/, fs/nfsd/, and include/linux/sunrpc/xdrgen/:

Why it matters for the NFS client

This is a bug fix / hardening item rather than a new feature or protocol change. The NLMv4 XDR decoders are used by both lockd (the kernel's lock manager, which backs the NFSv3/v4 file-locking path on the client) and nfsd (the server). Before this regeneration, the generated decoders for three enums — fsh4_mode, fsh4_access, and nlm4_stats — would happily accept any 32-bit value off the wire. That is a classic XDR footgun: a peer (or an attacker on a misconfigured network) could send out-of-range enum values, and the kernel's decoder would not reject them at the boundary.

By regenerating from the unchanged nlm4.x specification with the current generator, the decoders now reject values outside the enumeration, matching what the rest of the in-tree generated XDR code already does. Chuck's emphasis on "no specification change" is the key reassurance: wire-format compatibility with existing peers is preserved; only invalid inputs are now rejected.

Discussion and outcome

The thread was brief. Jeff Layton replied three minutes later with a quick review, quoting the commit message and the regenerated #define _LINUX_XDRGEN_NLM4_DEF_H guard line before signing off:

"Reviewed-by: Jeff Layton jlayton@kernel.org"

No objections, no follow-up questions, and no additional patches in the thread. The change is a clean Reviewed-by from an NFS maintainer and is expected to merge as-is.

Bottom line

  • Type: Bug fix / input-validation hardening (regeneration of generated code).
  • Scope: NLMv4 XDR decoders for fsh4_mode, fsh4_access, and nlm4_stats in lockd/nfsd; header timestamp refreshes across the sunrpc xdrgen tree.
  • Behavioral impact: Out-of-range enum values on the wire are now rejected instead of silently accepted — a meaningful robustness improvement for both the NFS client's lock path and nfsd, with no change to the NLMv4 specification or valid wire traffic.
  • Status: Reviewed-by from Jeff Layton; ready for merge.
