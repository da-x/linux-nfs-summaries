RFC for null root/cwd in fs_struct rejected by Brauner on security grounds

Summary

RFC: Support tasks with a null root or cwd — shot down on day one

What this is

This week's activity centers on a single, short-lived thread: an RFC patch series (not a bug fix) from John Ericson proposing that kernel tasks be allowed to run with a NULL root directory and/or working directory in struct fs_struct. The motivation is explicitly about building less-privileged, more cheaply spawned processes — a prelude to nulling out namespace fields and to a new non-fork-exec process-spawning API. It landed on linux-nfs only tangentially; the real home of this discussion is the general kernel mailing list, but it crossed over here because struct fs_struct touches filesystem code that NFS developers care about (path resolution, *at(2) lookups, getcwd, /proc/PID/root).

The proposal

Ericson posted a three-patch RFC on 2026-06-29:

  • Patch 0/3 (cover letter) — frames the motivation and explicitly notes that "nothing creates such a task yet" and that this is a dead-code demonstration patch, ahead of future UAPI work.
  • Patch 1/3 — adds documentation to struct fs_struct fields.
  • Patch 2/3 — the actual implementation: teaches namei, d_path, fhandle, cachefiles, and /proc readers to cope with a NULL root or cwd instead of dereferencing it.
  • Patch 3/3 — adds a KUnit test suite gated by CONFIG_NULL_ROOT_CWD_KUNIT_TEST.

The cover letter is unusually candid about its own status:

"It may not be appropriate to submit such a 'dead-code' patch, but I wanted to demonstrate just how easy this change is (along with at least a unit test to exercise it), before getting into UAPI designs."

Ericson also acknowledged the strongest known alternative — using the new "nullfs" for root/cwd:

"So far in the linked discussion, the alternative that best addresses my motivation is using the new 'nullfs' for the root directory and cwd. Practically, that is almost as good... The downside is simply that we would like those operations also to fail."

The core technical argument of patch 2/3 is that a task with no root cannot use absolute pathnames (its .. climbs to the mount root instead), and a task with no cwd cannot use AT_FDCWD-relative lookups — but descriptor-anchored *at(2) calls keep working. The setter side (chdir, chroot, pivot_root) needs no changes because they already resolve via filename_lookup(AT_FDCWD, ...) and would simply fail.

The reaction

VFS maintainer Christian Brauner replied within ~2 hours on the same day, and his verdict was unambiguous:

"No, absolutely we're not going to have tasks with struct path's in their struct fs_struct that have NULL members in them. struct path is used insanely widely in the kernel this is just an open invitation for a slew of security bugs. Not going to happen." — Brauner, 2026-06-29

The objection is architectural rather than stylistic: struct path is one of the most widely dereferenced types in the entire kernel, and introducing a NULL-member variant into fs_struct would require auditing every single consumer — an audit that, by definition, cannot be completed safely. Ericson's patch only fixes the handful of readers he identified (namei, d_path, fhandle, cachefiles, proc); Brauner's point is that there are many more, and any missed one is a potential NULL-deref or worse.

Where this leaves NFS

For NFS client developers specifically, the practical takeaway is small but worth noting:

  1. No change to path resolution semantics. The RFC would have altered path_init() / nd_jump_root() behavior for AT_FDCWD and absolute paths — code paths that NFS's dentry/lookup machinery interacts with on every RPC round-trip. That change is now dead, so existing NFS assumptions about non-NULL root/cwd remain valid.
  2. The "nullfs" alternative survives. Ericson himself flagged nullfs as the near-equivalent approach. If a future UAPI (e.g., Li Chen's embryonic-process spawning work) wants to give sandboxed processes an empty root, nullfs is the path that VFS maintainers are more likely to accept — and that would be transparent to NFS clients since it's just another filesystem mounted at /.
  3. No bug fix here. This was a new-feature RFC that was rejected before any implementation could land. There is no regression, no workaround needed, and no follow-up patch expected in the near term.

Bottom line

The thread opened and closed in a single day. Ericson's RFC was a deliberate probe — he wanted to show how small the diff would be before investing in UAPI design — and Brauner's response drew a firm line: NULL members inside struct path fields of fs_struct are not acceptable. The discussion is effectively over for this approach; any future work on minimally-privileged process spawning will need to route around it, most likely via nullfs or by keeping root/cwd always populated and restricting access through other mechanisms (seccomp, LSMs, or the embryonic-process model itself).
