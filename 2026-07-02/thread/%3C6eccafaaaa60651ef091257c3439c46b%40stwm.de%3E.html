6.18.37 nfsd regression: null-deref Oops in remove_blocked_locks; bisect points at export-cache revert

Summary

6.18.37 nfsd regression: null-deref Oops in remove_blocked_locks, bisect pinpoints the export-cache cleanup revert

Type: Bug fix / regression investigation (NFS server side, not client). This week's activity is the first round of a debugging exchange between reporter Wolfgang Walter and NFS maintainer Chuck Lever to isolate a hard lockup that appeared in stable kernel 6.18.37 but not in 6.18.36.

Context (bridging prior weeks)

The thread root — Wolfgang's original bug report, Re: 6.18.37 has problems with nfs4 (server), 6.18.36 works — predates this reporting window and is not directly retrievable here, but its substance is fully reconstructed from Chuck's reply: a production NFSv4.2 fileserver running 6.18.37 wedged hard (requiring a power cycle) roughly a day after the upgrade, while the identical box ran fine on 6.18.36. Wolfgang had already done an A/B comparison and suspected a specific commit. No prior weekly summary exists for this thread.

The week's discussion

Chuck Lever opens the investigation (2026-07-01). He validates Wolfgang's bisect and identifies the single suspect:

"You've picked the right commit to suspect: 95f9eb19d5e6 ("Revert 'NFSD: Defer sub-object cleanup in export put callbacks'") is the only change to the NFS server between 6.18.36 and 6.18.37, so an A/B test around it is exactly the right experiment."

He then requests two things to pin down the fault:

  1. The complete kernel log — the trace Wolfgang sent began mid-register-dump and was missing the task that actually triggered the stall (the RCU stall named CPU 13 / PID 8887, nfsd, whose backtrace sat above the paste). Chuck asks for everything from the first "soft lockup" / "rcu ... stall" / "hung task" line onward, with all CPU backtraces, and offers netconsole/pstore/ramoops as a fallback if the machine wedges hard.
  2. A revert-the-revert diagnostic build — git revert --no-edit 95f9eb19d5e6 on a 6.18.37 tree, which restores the 6.18.36 behavior for this code:

"If that build stays healthy, it strongly implicates the change; if it still locks up, we've ruled it out and should look at the NFSv4 laundromat/grace-period path instead."

Chuck flags an important caveat about the diagnostic — the reverted commit had itself fixed a real problem:

"this also brings back a separate problem the revert fixed (a lingering mount reference that can make 'exportfs -r' followed by umount fail with EBUSY), so treat it as a diagnostic build, not something to run long term."

He closes by noting he could usually tell from the full backtrace whether the export-cache change was even on the hung code path, "or whether 6.18.37 just happened to expose something else."

Wolfgang Walter supplies the missing crash data and environment (2026-07-02). systemd-journald had not captured the event, but /var/log/messages did. The decisive backtrace is a null-pointer Oops in the NFSv4 client-state teardown path:

Oops: 0000 [#1] SMP NOPTI   CPU: 2  PID: 8844  Comm: nfsd  6.18.37-debian64.all+1.3
RIP: __list_del_entry_valid_or_report+0x8/0x110
Call Trace:
 remove_blocked_locks+0x91/0x1d0 [nfsd]
 __destroy_client+0x1b4/0x2a0 [nfsd]
 nfsd4_destroy_clientid+0xe6/0x1c0 [nfsd]
 nfsd4_proc_compound+0x325/0x680 [nfsd]
 nfsd_dispatch / svc_process_common / svc_process / svc_recv / nfsd  (kthread)

The faulting instruction dereferences a NULL RAX/RDI inside the list-corruption validity check, i.e. remove_blocked_locks() walked a corrupted or already-freed lock list while destroying a client ID during a COMPOUND — consistent with the export-cache cleanup-timing change under suspicion.

On environment, Wolfgang reports:

  • NFS 4.2 with sec=krb5p; clients on a mix of 6.18 and various distro kernels.
  • Roughly 50 users still connected at crash time (~16:30), some shutting down clients — so client state was actively being torn down.
  • A one-off, not reproducible: "It wasn't a reproduce, it was the first time 6.18.37 was running, I upgraded to 6.18.37 the evening before."
  • The box had to be hard-reset after ~½ hour (neither reboot nor sync made progress), and the crash "did some damage to the filesystem" requiring an fsck, which is why he downgraded back to 6.18.36 in the interim.

He accepts the revert-the-revert diagnostic, recalling a possibly related earlier symptom:

"Maybe I encountered that in 6.18.19, I wrote a report that nfsd got stuck when rebooting, but maybe it is something different as it seems to have disappeared in the last 6.18 kernels. So I will give 3.18.37 with this change reverted a try."

Technical assessment

  • Classification: A regression/bug-fix hunt, not a new feature or protocol change. The fault is on the NFS server (nfsd), specifically in the NFSv4 client-ID destruction / blocked-lock removal path — a state-management bug, not a wire-protocol issue. (The task brief's emphasis on client development does not apply here; this thread is squarely server-side.)
  • Leading hypothesis: Commit 95f9eb19d5e6 ("Revert 'NFSD: Defer sub-object cleanup in export put callbacks'"), the only NFS-server delta between 6.18.36 and 6.18.37, altered the timing of export-cache sub-object cleanup and is suspected of creating a use-after-free / list-corruption window hit when remove_blocked_locks() runs during client teardown under concurrent client disconnects.
  • Open question for next week: whether the revert-the-revert build stays healthy (confirming the commit) or still locks up (pointing instead at the NFSv4 laundromat/grace-period path). The thread continues past this window (later activity dated 2026-07-03 and a follow-up from Chuck on 2026-07-06), so the outcome of the diagnostic build is not yet recorded here.

Status

Unresolved as of end of window. The reporter has committed to running the diagnostic (revert-the-revert) build; the full backtrace has been delivered and points at remove_blocked_locks() → __destroy_client() in nfsd. Awaiting the A/B result before a fix or further bisect can be proposed.
