sunrpc pool_mode v3: starvation fix lands, RCU race surfaces a deeper design debate

Summary

sunrpc pool_mode v3: the empty-pool starvation fix ships, and an RCU race sparks a design fight

Type: Server-side bug fix + cleanup in the sunrpc (NFS server) layer. This is not an NFS client feature or protocol change — it concerns how nfsd schedules RPC work across NUMA pools on the server. The week's most important artifact is a genuine bug fix: a latent request-starvation bug that becomes reachable once the "global" pool escape hatch is removed, plus a newly-surfaced use-after-free / NULL-deref race in the lockless pool-map reader.

Bridging prior weeks (brief)

Jeff Layton posted v2 on June 25, and last week's thread was dominated by Chuck Lever's warning that with nrservs < number of NUMA nodes, trailing pools end up with zero threads and the enqueue path has no fallback — a connection landing on an empty pool would hang indefinitely. NeilBrown and Layton converged on a "belt-and-braces" plan: guarantee ≥1 thread per CPU-bearing node during auto-distribution, honor explicit userland per-pool arrays as-is, and add a queueing-path fallback to a populated pool. That plan is exactly what v3 delivers.

This week's activity (June 29 – July 1)

The v3 series lands (June 29)

Jeff Layton posted v3 as a four-patch set, explicitly building on last week's discussion:

The other three patches address what is a shortcoming of the existing code -- namely that the server can be configured to schedule RPCs to pools with no threads in them. The first patch addresses this problem: if the chosen pool has no threads, then choose another that does.

The four patches are:

  1. Route to a populated pool (1/4) — the core starvation fix, carrying Fixes: 0f0257eaa5d2. It makes svc_pool_for_cpu() skip threadless pools and fall back to a populated one. Layton is candid about the tradeoff: "This trades NUMA locality for a guarantee that the work is actually serviced."
  2. Hardcode pool_mode to pernode (2/4) — removes the SVC_POOL_AUTO/GLOBAL/PERCPU/PERNODE enum, the mode-selection heuristic, and all mode-based switch statements (−215/+49 lines). The module parameter and netlink interface are preserved for backward compatibility; writing any previously-accepted value "succeeds silently," reading always returns "pernode." Notably this patch carries an Assisted-by: Claude:claude-opus-4-8 tag.
  3. Guarantee a thread per CPU-bearing node (3/4) — floors each CPU-bearing node's pool at one thread during auto-distribution, while leaving explicit svc_set_pool_threads() callers (who may set a pool to zero) unchanged.
  4. Eliminate a modulus from the enqueue path (4/4) — a micro-optimization that "trades a ~20-30 cycle operation that isn't pipelined and monopolizes the divider for a ~1 cycle well-predicted branch."

An RCU race surfaces (June 30)

The plot thickened with PATCH 5/4, a fix Layton added on the strength of an external review:

Sashiko pointed out this (preexisting) problem during review of the other 4 in the series. I figure we might as well fix it too while we're in here.

The bug: svc_pool_map_get_node() reads the global pool map without holding svc_pool_map_mutex and dereferences m->pool_to[], but that array is published and torn down with no synchronization against this lockless reader. Two distinct hazards:

  • svc_pool_map_get() bumps m->count to one before pool_to[] is allocated, so a concurrent reader can see the map as "in use" while pool_to[] is still NULL (or half-built) and oops.
  • svc_pool_map_put() frees pool_to[] as soon as the last reference drops, so a reader mid-dereference can use-after-free it.

Because svc_new_thread() takes this lockless path for every service — including unpooled ones like lockd that hold no map reference — the race is genuinely live during another service's start/stop. Layton's fix publishes pool_to[] via rcu_assign_pointer() only after it's fully built, reads it under rcu_read_lock(), and defers teardown with kfree_rcu_mightsleep().

Chuck Lever's review: nits + a backport call (June 30)

Chuck Lever's detailed review of patch 2/4 raised several precise points:

  • A behavioral regression in the parameter parser. sysfs_match_string() compares whole strings, whereas the old code matched prefixes. "An input like 'globalx' that the old code accepted is now rejected with -EINVAL." He notes this contradicts the commit message's claim that "Writing any previously-accepted value succeeds silently," though only prefix-extended (undocumented) strings are affected.
  • A stale kdoc comment. With percpu removed, "cpus to pools" now contradicts the struct field comments the same patch corrected.
  • Dead code. In svc_pool_map_set_cpumask(), "pool_to[pidx] is dereferenced before the m->count == 0 check, so if count were ever 0 the NULL deref has already happened and the WARN/return can never fire." The sv_nrpools > 1 gate at the call site keeps it safe, making the guard dead.
  • The key structural suggestion — gate on whether the service holds a map reference: "An unpooled service (sv_nrpools == 1) could then take numa_mem_id() without reading the shared map."

And his most consequential line for the series' fate:

For the series as a whole, let's consider moving 5/4 to the front. It looks like a fix that might want to be backported.

NeilBrown pushes back on the RCU approach (July 1)

NeilBrown replied to the RCU patch with a design objection, arguing the RCU machinery is overkill:

I don't think this is the best approach. The problem only occurs when svc_create() is used as when svc_create_pooled() is used, svc_pool_map_get() is called early so a reference is held to svc_pool_map.

His alternative is simpler and mirrors Chuck's gating idea: since svc_new_thread() is the only caller of svc_pool_map_get_node(), just check pool->sv_is_pooled and only consult the map when it's true, otherwise use NUMA_NO_NODE. He sketched a patch to that effect.

Key technical arguments & evolution

  1. The starvation bug is now fixed in-tree (pending merge). The v3 series directly implements last week's belt-and-braces consensus: per-node thread floor for auto-distribution + enqueue-path fallback to a populated pool, with explicit userland arrays still honored. This is the headline bug fix of the week.
  2. A preexisting memory-safety race got exposed by the cleanup. Making pernode the default means the lockless pool_to[] reader now runs for every server (the old global mode returned numa_mem_id() and never touched the array). That turned a dormant bug into an active one — and it's the kind of fix Chuck flags as backport-worthy.
  3. Two competing fixes for the same race. Layton chose RCU (rcu_assign_pointer/rcu_read_lock/kfree_rcu_mightsleep); both NeilBrown and Chuck independently argued for a lighter-weight gate on sv_nrpools > 1 / sv_is_pooled, which would let unpooled services bypass the shared map entirely. This is where the discussion stands — unresolved as of the window's end.
  4. Subtle edge case that keeps recurring: non-pooled services (lockd, NFS callback) are created via svc_create() with npools = 1 and never call svc_pool_map_get(), so their m->count is whatever a pooled nfsd left behind — any code in the shared path must tolerate zero-count / NULL-pointer state.

Final status (as of window close)

The v3 series is posted and largely converges on last week's design; the open item is how to fix the pool_to[] race — RCU (Layton, 5/4) vs. a pooled-service gate (NeilBrown/Chuck). Chuck has also recommended reordering so the race fix leads the series for potential backporting. No v4 or resolution has landed within this window; expect Layton to reconcile the two approaches next.
