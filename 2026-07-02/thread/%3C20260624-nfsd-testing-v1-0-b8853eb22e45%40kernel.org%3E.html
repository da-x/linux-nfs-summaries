nfsd inter-server copy fixes: Neil Brown reviews the cpntf race and UAF patches

Summary

nfsd inter-server copy fixes — Neil Brown weighs in on the LLM-found bug series

The week at a glance

Last week, Jeff Layton posted a three-patch series fixing concurrency bugs in the NFSv4.2 inter-server copy offload code (COPY / COPY_NOTIFY / OFFLOAD_CANCEL) — bugs, notably, that were surfaced by LLM-assisted inspection rather than field reports. This week brought the first substantive review: Neil Brown replied to all three patches on June 26, delivering a mixed verdict — one patch essentially approved, and two flagged for rework. No v2 has landed within this window, so the series remains at v1 with open review comments.

This is a bug-fix series, not a new feature or protocol change. All three patches carry Fixes: tags pointing to long-standing code (the COPY_NOTIFY introduction 624322f1adc5 and the async copy reaper ac0514f4d198), making them strong candidates for stable backport once merged.

Patch 1/3 — cpntf publish race: "a substantially simpler solution"

Neil Brown's reply to PATCH 1/3 is the most prescriptive of the three. He objects to the verbose inline comment added by Chris Mason's fix, arguing that "This comment seems excessive. The explanation certainly should be in the commit message, and is probably there already."

More importantly, he pushes back on the shape of the fix — which passes cs_type into nfs4_init_cp_state() — and proposes a cleaner alternative:

"A substantially simpler solution would be to not pass cs_type to nfs4_init_cp_state() so the type remains initialised to zero, which is invalid. Anything which finds that stateid will ignore it because they already check the type. Then callers of nfs4_init_cp_state() set the type themselves."

His logic: if the stateid's cs_type starts at zero (an invalid value), any concurrent OFFLOAD_CANCEL lookup naturally ignores the half-published entry, so the publish race closes without the extra plumbing. This is a design-level suggestion that would reshape the patch rather than just trim it.

Patch 2/3 — UAF in cpntf statelist drain: Reviewed-by granted

Neil Brown's reply to PATCH 2/3 is the most favorable. He repeats his comment-hygiene objection ("Again, this comment doesn't belong in the final code") and notes that switching the drain loop from while() to list_for_each_entry_safe() "isn't required for this change, and isn't justified by the commit message." He prefers an explicit while ((cps = list_first_entry_or_null(...)) != NULL) form because it "makes it abundantly clear that the list will be emptied."

But he lands on a positive verdict:

"Apart from the comment, the code changes looks correct. Reviewed-by: NeilBrown neil@brown.name"

So Patch 2/3 is effectively cleared pending cosmetic cleanup — the UAF fix (unconditionally revoking each entry before dropping the parent's reference via put_cpntf_state_unlinked_locked()) has earned a reviewer's stamp of approval.

Patch 3/3 — UAF in async copy cancel and shutdown: "hard for me to follow"

The most involved patch drew the harshest review. In his reply to PATCH 3/3, Neil Brown dissects the patch as conflating two distinct changes:

"This patch seems to make two changes. One involves extra refcount on the 'copy' structure, which is probably sensible but hard for me to follow because the patch is so noisy."

The second change — memory barriers around the ->cp_clp assignment — he finds opaque:

"The other is barriers around assignment of ->cp_clp which doesn't make any sense to me at all, and the copious comments don't help with. A barrier is always between two things... The comments should make clear what the something else is. They don't (at least not to me)."

His conclusion is a request for rework rather than approval:

"I would rather two patches with less noise and more useful comments."

Assessment and outlook

The review week splits cleanly into three outcomes:

  • Patch 1/3 — design-level pushback; Neil Brown offers a simpler alternative that avoids passing cs_type at all.
  • Patch 2/3 — approved with a Reviewed-by, modulo comment cleanup and an unneeded loop-style change.
  • Patch 3/3 — asked to be split into two cleaner patches, with the barrier rationale made explicit.

A recurring theme across all three replies is Neil Brown's insistence on lean code: explanatory prose belongs in commit messages, not inline comments, and patches should do one thing clearly. The next development will be a v2 from Chris Mason / Jeff Layton addressing these points — particularly the rework of Patch 3/3 — before the series can move toward merge and stable backport.
