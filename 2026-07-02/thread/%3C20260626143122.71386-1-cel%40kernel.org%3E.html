lockd: fix TEST handling when not all permissions are available (queued for 6.18)

Summary

This week's thread is short but consequential: a long-latent lockd bug that broke read-only NFS access (notably qemu on ISO images) was fixed and queued for the 6.18 stable series within a day of posting.

The patch

Chuck Lever posted the backport on Friday, carrying NeilBrown's original fix:

"The F_GETLK fcntl can work with either read access or write access or both. It can query F_RDLCK and F_WRLCK locks in either case."

"However lockd currently treats F_GETLK similar to F_SETLK in that read access is required to query an F_RDLCK lock and write access is required to query a F_WRLCK lock."

The real-world trigger was a Debian bug report: qemu probing a read-only ISO image over NFS would ask whether it could acquire a write lock, and lockd demanded O_WRONLY access it could never grant. As NeilBrown put it in the commit message: "when qemu accesses a read-only (e.g. iso) filesystem image over NFS (though why it queries if it can get a write lock - I don't know. But it does, and this works with local filesystems)."

Why it only surfaced now

The bug is ancient — "This behaviour of lockd - requesting O_WRONLY access to TEST for exclusive locks - has been present at least since git history began." It stayed hidden because knfsd had been ignoring the access lockd requested. The commit cited in Fixes: (4cc9b9f2bf4d, "nfsd: refine and rename NFSD_MAY_LOCK") changed nfsd_permission() to honor the access request for LOCK operations, exposing the latent defect.

Technical approach

The fix restructures how TEST requests flow through lockd rather than special-casing them at the permission check:

  • nlm_do_fopen() now accepts O_RDWR and succeeds if either a read-only or write-only file can be opened
  • nlm_lookup_file() takes an explicit mode from its caller instead of deducing it from the lock type
  • nlm4svc_retrieve_args() / nlmsvc_retrieve_args() detect TEST requests and pass O_RDWR, also setting lock->fl.c.flc_file to whichever file is actually available
  • nlmsvc_testlock() stops recomputing the mode and uses whatever was stored

Five files touched (fs/lockd/svc4proc.c, svclock.c, svcproc.c, svcsubs.c, include/linux/lockd/lockd.h), 49 insertions / 20 deletions. Reviewed-by: Jeff Layton.

Known limitation (explicitly out of scope)

NeilBrown flagged a related but unaddressed issue in the commit message:

"The flock(.., LOCK_EX) call is permitted on a read-only file descriptor. Linux NFS maps this to NLM locking as whole-file byte-range locks. nfsd will see this as though it were fcntl( F_SETLK (F_WRLCK)) and will now require write access... It is not clear if this is a problem in practice, or what the best solution might be. So no attempt is made to address it."

Resolution

Sasha Levin confirmed on Saturday: "Queued for 6.18." No further discussion followed this week; the thread is closed pending merge into the stable tree.
