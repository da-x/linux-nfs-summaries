RFC: Injecting PID namespace into NFSv4 COMPOUND tag for multi-tenant debugging

Summary

RFC: Injecting PID Namespace into the NFSv4 COMPOUND Tag

Thread: [PATCH] [RFC] nfs4: inject process namespace into COMPOUND tag
Week ending: 2026-07-02 (window 2026-06-26 → 2026-07-03)
Type: New feature / debuggability improvement to the NFSv4 client — explicitly marked RFC, not a bug fix
Status: Open; maintainer review raised two concrete issues (compile/scope, buffered-write semantics). No v2 posted this week.

Bridge from prior context

This is a sibling of another Tigran Mkrtchyan RFC posted the same morning (2026-06-26) that proposed embedding the PID namespace in the auth_unix machinename field instead (see companion summary). That earlier thread drew a correctness objection from Jeff Layton about async credential staleness. The COMPOUND-tag variant in this thread is Tigran's follow-up attempt to solve the same multi-tenant debugging problem through a different, per-RPC channel — the tag41 field of the NFSv4 COMPOUND header — which avoids the auth-credential caching issue because the tag is encoded at RPC-send time. The idea is credited as Suggested-by: Chuck Lever.

Motivation

Tigran opened the RFC with the same framing he used in the machinename thread:

"On large shared machines often multiple jobs of a same user run in parallel. For debugging, it's usually impossible to identify requests coming from different processes."

He highlighted that batch schedulers such as HTCondor and SLURM launch each job inside its own PID namespace, so the namespace inode number is a natural per-job discriminator that can be surfaced on the server side for log correlation. To make the benefit concrete he included a Wireshark-style trace showing how requests from two jobs would otherwise look identical:

"192.168.122.150 → 192.168.178.69 NFS 260 V4 Call GETATTR FH: 0xd5ffb2cb …
192.168.122.150 → 192.168.178.69 NFS 284 V4 Call ns:4026532507 GETATTR FH: 0xd67b66a5"

The ns:<inum> prefix on the COMPOUND tag is what would let an operator tell which job issued which RPC.

The patch (technical detail)

The RFC patch touches three files:

  • fs/nfs/nfs4xdr.c — at COMPOUND encoding time, if the task has a non-zero tk_ns_inum, format "ns:<inum>" into a local char ns_tag[NFS4_MAXTAGLEN + 1] and assign it to hdr->tag / hdr->taglen.
  • include/linux/sunrpc/sched.h — adds a new tk_ns_inum field to the RPC task struct.
  • net/sunrpc/sched.c — populates task->tk_ns_inum = pid_ns->ns.inum; during task setup.

This is intentionally minimal: no protocol change, just reusing the existing free-form COMPOUND tag (which servers are already required to log) as a debug channel.

Review: Trond Myklebust's two objections

Linux NFS client maintainer Trond Myklebust replied on 2026-06-28 with two concrete technical objections.

1. The patch does not compile / has a scope bug. Trond flagged the local buffer:

"Hmm.... This has not been compile tested."

and then pinpointed the lifetime issue:

"ns_tag is only scoped to this block. I suggest that instead of assigning to hdr->taglen and hdr->tag, you just do the assignment to hdr->replen + call to encode_string() here, so you don't have to assign a scope limited buffer to an externally visible struct."

He added a secondary note on string handling:

"Note also that there is no need to NUL terminate ns_tag[] when hdr->taglen > NFS4_MAXTAGLEN, since encode_string() does not require a nul terminated string. In addition, snprintf() always guarantees that the string is nul terminated, even when truncated by the buffer size :-)."

The practical fix he is steering toward: encode the tag directly into the XDR stream at the point of use rather than stashing a pointer to a stack-allocated buffer on hdr.

2. Buffered writes will report the wrong namespace. Trond raised a deeper semantic issue about when the namespace is captured:

"For buffered writes, this will tell you the pid namespace of the process that is flushing the data, not that of the process that wrote the data into the page cache. Is that what you expected?"

This mirrors the async-context concern Jeff Layton raised in the companion machinename thread, but here it manifests differently: because tk_ns_inum is captured at task setup (i.e., when the flusher's RPC task is created), a buffered write issued by job A but flushed later by the kernel's writeback path will carry the writeback context's namespace — or none at all — rather than job A's. For the debugging use case Tigran describes, that defeats the purpose for one of the most common workload patterns on shared HPC nodes.

Author response

Tigran replied on 2026-06-30 acknowledging Trond's review. The reply is short and contains no new technical argument or a v2 patch; the thread was still open at the end of the week window with both issues (scope/compile fix, buffered-write semantics) unresolved.

Key takeaways for NFS client developers

  1. The COMPOUND tag is a legitimate, low-risk debug channel. It is already part of the protocol and required to be logged by servers, so embedding per-process context there avoids any wire-format change — but only if the encoding is done at send time with a properly scoped buffer.
  2. Per-task metadata capture is fragile in sunrpc. Both this thread and its machinename sibling surfaced the same underlying hazard: any "current process" attribute captured at task-creation or credential-setup time can be stale for async or writeback-originated RPCs. A robust design would need to either re-read the namespace at encode time or accept that buffered writes will carry the flusher's context and document that limitation.
  3. The discussion is still open. As of 2026-07-02 no v2 patch has been posted; the next step depends on Tigran addressing Trond's two points, particularly the buffered-write semantics question which is a design decision rather than a code fix.
