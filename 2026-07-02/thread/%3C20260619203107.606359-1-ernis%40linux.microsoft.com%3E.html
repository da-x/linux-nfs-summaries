RDMA ib_device_attr int→u32 (v8): Shevchenko confirms Sashiko's INT_MIN concern, v9 promised

Summary

RDMA ib_device_attr int→u32 — v8 follow-up: one last edge case confirmed, v9 on the way

This week at a glance

Two messages landed in this window (both July 2), closing out the quiet stretch since Vennela posted v8 on June 19. The thread moves from "posted, awaiting maintainer pickup" to "one final low-priority fix identified and acknowledged."

Erni Sri Satya Vennela's July 2 follow-up is a polite nudge back to his own patch, referencing the automated Sashiko review tool:

"Just a friendly follow-up on this patch. The Sashiko review mentioned a low-priority item, and I'd appreciate any guidance on whether the change is needed."

He links directly to the Sashiko patchset page for context.

Andy Shevchenko's reply two and a half hours later is brief but definitive:

"As I read this it needs to be fixed, the problem is that there is a potential of a weird case (not sure they are IRL) when somebody can use INT_MIN (in representation of signed number) to actually mean 0x80000000 size."

Shevchenko's framing — "not sure they are IRL" (in real life) — is characteristically pragmatic. He acknowledges the scenario is unlikely in practice but confirms the type-correctness argument: a signed int field holding a 32-bit capability value can represent INT_MIN (−2147483648), which in two's-complement bit pattern is exactly 0x80000000. A driver reporting that raw value would appear as a negative size to any consumer doing signed comparisons.

The thread then received Vennela's July 3 confirmation (just outside this window):

"Thankyou for the confirmation, Andy. I'll add this change in the next version."

So a v9 is now promised to address this final item.

Bridge from prior weeks

As summarized last week, this is a bug fix / type-correctness cleanup spanning seven prior revisions over six weeks. The core defect: capability counter fields in struct ib_device_attr declared as signed int despite being inherently non-negative, with drivers caching caps as u32 and implicitly narrowing on assignment. v8 incorporated all of Shevchenko's style-review items (declaration ordering, leftover min_t(), reinvented helpers, %d→%u format strings) and carried Stefan Metzmacher's Acked-by for the smbdirect hunks.

NFS/RDMA relevance

The NFS client portions of this series — specifically the unsigned underflow guard in frwr_ops.c (preventing a device reporting zero max_sge_rd from producing an SGE count of UINT_MAX − 1 and breaking RDMA transport negotiation for NFS-over-RDMA clients) and the min_t(int, …) → plain min() cleanup in svc_rdma_transport.c — have been stable since v5–v7. This week's INT_MIN discussion does not alter those hunks; it concerns a residual signed-int field that Sashiko flagged as low-priority. The NFS/RDMA consumers are already safe under the unsigned semantics Vennela confirmed in earlier revisions.

Assessment

The thread is converging on closure. Seven revisions became eight, and now a ninth is promised for a single remaining edge case. Shevchenko's confirmation — while noting the scenario is unlikely "IRL" — removes any ambiguity: the fix is warranted, the change is small, and v9 should be the final revision before rdma-next maintainer pickup. No new technical objections or scope expansions emerged this week.
