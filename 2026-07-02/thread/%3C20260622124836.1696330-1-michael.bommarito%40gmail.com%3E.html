NFSv4.1/pnfs: FSINFO layout-type count fix lands as v2 using xdr_stream_decode_uint32_array()

Summary

NFSv4.1/pnfs: the FSINFO layout-type overflow fix arrives as a helper-based v2

Overview

This week's activity in this thread is a single, decisive message: on 2026-06-26 Michael Bommarito posted the v2 of his pNFS client bug fix that bounds the server-controlled layout-type count in decode_pnfs_layout_types(). This is squarely a bug fix — a security-relevant robustness hardening of the NFSv4.1 pNFS client's FSINFO decode path — not a new feature or protocol change, and it again carries Cc: stable@vger.kernel.org for backporting.

The v2 exists entirely in response to maintainer feedback from last week. As summarized last week, Bommarito's v1 (posted 2026-06-22) added a hand-rolled U32_MAX guard, and Linux NFS client maintainer Trond Myklebust replied within about ninety minutes with the terse verdict:

"This is just open coding xdr_stream_decode_uint32_array(), and doing so incorrectly."

The v2 is Bommarito's direct answer to that note.

Bridge from Prior Week

Last week the thread had exactly two messages — the v1 patch and Myklebust's one-line review — and was sitting at the "review comment received, rework expected" stage. The underlying defect was already well characterized: decode_pnfs_layout_types() reads a server-controlled u32 count and reserves 4 * count bytes in 32-bit arithmetic, so any count ≥ 0x40000000 wraps to a small value and xdr_inline_decode() reserves too few bytes; the existing NFS_MAX_LAYOUT_TYPES cap is applied only afterwards, so the subsequent reads run past the short reservation. The threat model — a malicious or compromised NFSv4.1+ server (or MITM on an unprotected mount) returning a crafted FATTR4_FS_LAYOUT_TYPES attribute during FSINFO decode — was unchanged.

The v2 closes that open item: instead of defending the hand-rolled bounds check, Bommarito deleted it and called the canonical helper.

The v2 Patch (June 26)

Bommarito's v2 retargets fs/nfs/nfs4xdr.c, now at 11 insertions and 23 deletions — a net simplification relative to v1's added guard. The core of the change is stated plainly in the cover:

"This open-codes xdr_stream_decode_uint32_array(), which reads the count, rejects a length that would overflow the size calculation, decodes the array, zero-fills the remainder, and bounds the result against the destination size. Use it."

The v2 changelog makes the response to the review explicit:

"v2: use xdr_stream_decode_uint32_array() instead of an open-coded count read and manual bound, per Trond Myklebust's review of v1. v1 added a hand-rolled U32_MAX guard; the helper already does the overflow-safe count read, array decode, and destination bound."

One behavior is deliberately preserved: an over-large-but-valid server advertisement must not break the mount. The patch keeps that path non-fatal by mapping the helper's size error into the existing cap:

"A server advertising more than NFS_MAX_LAYOUT_TYPES stays non-fatal as before by treating -EMSGSIZE as a cap."

The fix is still anchored to the original commit that introduced the layout-type list, and the stable tag is retained:

"Fixes: ca440c383a58 ("pnfs: add a new mechanism to select a layout driver according to an ordered list")" "Cc: stable@vger.kernel.org"

The sign-off block again credits AI assistance: "Assisted-by: Claude:claude-opus-4-8."

Testing and KASAN coverage

Bommarito re-ran the reproduction on a UML KASAN build, this time confirming both the failure mode of the original/v1 arithmetic and the new safe behavior in one report:

"Reproduced on a UML KASAN build: a crafted FATTR4_FS_LAYOUT_TYPES with nlayouttypes=0x40000001 made the v1/original u32 multiply wrap and the decode read past xdr->end (KASAN slab-out-of-bounds read). With this patch xdr_stream_decode_uint32_array() rejects the length (-EBADMSG -> -EIO) before any over-read; a valid small count still decodes, and a count > NFS_MAX_LAYOUT_TYPES is capped as before."

Note the error-path detail worth flagging for reviewers: the helper rejects the overflowing length with -EBADMSG, which the patch surfaces to the caller as -EIO — i.e., a decode failure rather than a successful short reservation. The KUnit test, as in v1 and the companion GETDEVICEINFO series, is decoupled from the fix ("Before/after logs available on request").

Evolution of the Discussion and Current State

The thread's trajectory across the two weeks is clean and fast:

  • June 22 (prior week): Bommarito posts v1 (hand-rolled U32_MAX guard); Myklebust replies within ~90 minutes pointing at xdr_stream_decode_uint32_array() as "open coding … incorrectly."
  • June 26 (this week): Bommarito posts v2, dropping the hand-rolled guard and calling the helper, with KASAN before/after evidence.

Within this week's window there is exactly one message — the v2 itself. There is no maintainer ACK or further reply in-window; the thread has moved from "review comment received" to "rework submitted, awaiting review." The open question now is whether Myklebust accepts the helper-based form (which his own note framed as the correct upstream shape).

Significance for NFS Client Development

  • Decoder robustness against hostile servers. This closes the FSINFO half of the same XDR-wrap class Bommarito has been hardening — server-controlled u32 counts multiplied in 32-bit arithmetic before an xdr_inline_decode() reservation — reachable from a malicious or compromised NFSv4.1+ server during early mount/layout setup. It is the companion to the GETDEVICEINFO notification-bitmap fix from 2026-06-14.
  • The helper-first lesson, applied. Myklebust's "open coding … incorrectly" note steered the fix toward the canonical XDR helper, and the v2 shows the author following that guidance cleanly: the result is a smaller patch (net −12 lines) that leans on xdr_stream_decode_uint32_array() for overflow-safe count read, array decode, zero-fill, and destination bound. This is a useful template for future decoder work — when the array/string helper already exists, call it rather than hand-rolling bounds checks.
  • Stable backport intent. The retained Cc: stable@vger.kernel.org means that once accepted, this fix is expected to flow into stable trees — relevant for any distribution shipping an affected kernel.

Status and Outlook

  • Thread status: Open. v2 submitted; awaiting maintainer review/ACK from Myklebust on the helper-based form.
  • Related open thread: The GETDEVICEINFO notification-bitmap series (2026-06-14) remains in review; if Myklebust applies the same "use the helper" lens there, that series may also be reworked to xdr_stream_decode_uint32_array().
  • Open items: (a) maintainer ACK on v2; (b) whether the KUnit test rides as a separate patch, matching the GETDEVICEINFO series.
