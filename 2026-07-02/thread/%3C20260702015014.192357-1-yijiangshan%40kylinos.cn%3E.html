NFS: fix folio dereference before NULL check in nfs_inode_remove_request()

NFS: Fix Folio Dereference Before NULL Check in nfs_inode_remove_request()

Overview

This week's activity on this thread is limited to a single event: Jiangshan Yi (KylinOS) posted a one-patch bug fix on July 2 targeting the NFS client writeback path in fs/nfs/write.c. As of the close of this week's window, no maintainer or reviewer has yet replied, so the discussion is at its very first stage — a fresh submission awaiting review.

Classification: Bug Fix (Client-Side)

This is squarely a bug fix in the NFS client, not a new feature or protocol change. It corrects a latent NULL-pointer dereference in nfs_inode_remove_request(), a function on the writeback completion path that detaches an I/O request from its inode's list of pending requests.

The Technical Argument

The core of the patch is a classic "deref-before-check" ordering bug. Jiangshan Yi walks through the defect precisely, showing how the existing code reads folio->mapping (and takes mapping->i_private_lock) before it ever validates that folio is non-NULL:

"The presence of the 'if (likely(folio))' check shows the code already assumes folio can be NULL. However, folio was dereferenced before that check"

He lays out the offending sequence with inline annotations to make the ordering mistake obvious:

"folio = nfs_page_to_folio(req->wb_head); mapping = folio->mapping; /* deref / spin_lock(&mapping->i_private_lock); if (likely(folio)) { / too late */"

The root cause is that nfs_page_to_folio() "returns NULL when the PG_FOLIO flag is not set on req->wb_head." Because the dereference, the lock acquisition, and the folio_end_dropbehind(folio) call all happen before the guard, a NULL folio would crash the kernel before the safety check is ever reached — "rendering the check useless," as Yi puts it.

The fix is minimal and behavior-preserving: move the folio->mapping read, the i_private_lock section, and the folio_end_dropbehind() call inside the if (likely(folio)) block so the folio "is only dereferenced after it has been confirmed non-NULL." Yi is explicit that this is a no-op for the common case: "The behaviour is unchanged when folio is non-NULL." The diff touches just 11 lines in one file (6 insertions, 5 deletions).

Context and Evolution: A Recurring Bug, and a Dropbehind Footprint

Two threads of context are worth flagging for the record.

1. This function has been flagged before. A near-identical fix was proposed by Baolin Liu (also KylinOS) in October 2025 — "[PATCH v1] NFS: Fix possible NULL pointer dereference in nfs_inode_remove_request()"](https://lore.kernel.org/linux-nfs/20251012083957.532330-1-liubaolin12138@163.com/) — which diagnosed the same defect with strikingly similar language:

"nfs_page_to_folio(req->wb_head) may return NULL in certain conditions, but the function dereferences folio->mapping and calls folio_end_dropbehind(folio) unconditionally. This may cause a NULL pointer dereference crash."

That earlier patch carried the same 11-line footprint (6 insertions, 5 deletions). Jiangshan Yi's submission this week appears to be a fresh re-raise of the same underlying issue in fs/nfs/write.c, suggesting the bug has persisted in the tree and is being revisited by the KylinOS team.

2. The dropbehind hook ties into recent VFS work. The presence of folio_end_dropbehind() in this path links the fix to the broader RWF_DONTCACHE / drop-behind writeback effort that landed for v7.2 (the Jeff Layton series, confirmed merged into Christian Brauner's vfs-7.2.writeback branch earlier this year). That work added the dropbehind flag and its lifecycle helpers to folios; this NFS patch is a downstream consequence of ensuring those new helpers are only invoked on valid folios in the client's writeback completion path.

Final Conclusions

At present there is no conclusion from reviewers — the thread consists solely of Jiangshan Yi's initial submission posted July 2. The patch presents a clean, well-justified ordering fix for a genuine NULL-dereference hazard in the NFS client, and it is now awaiting review from the NFS maintainers (Trond Myklebust / Anna Schumaker) and the broader writeback community. Given its small scope and the prior art from Baolin Liu's October 2025 patch, the key open question for next week is whether this resubmission will be picked up quickly or folded into a more complete treatment of the same latent bug.
