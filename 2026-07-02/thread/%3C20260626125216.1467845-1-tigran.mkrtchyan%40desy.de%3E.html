RFC: Injecting PID namespace into NFS machinename for multi-tenant debugging

Summary

RFC: Injecting PID Namespace into NFS machinename Field

Thread: [PATCH 0/1] inject process namespace into machinename field
Week ending: 2026-07-02
Status: RFC / discussion-trigger — not intended for mainline merge
Type: New feature (debuggability improvement to the NFS/sunrpc client)

Overview

DES's Tigran Mkrtchyan posted a single-patch RFC on 2026-06-26 proposing that the Linux NFS client embed the caller's PID namespace identifier into the machinename field of the RPC auth-Unix credential, so that NFS servers can distinguish requests originating from different containers or batch-system jobs running as the same user. The patch touches only net/sunrpc/auth_unix.c (+25/−2).

Motivation and Problem Statement

Tigran framed the problem clearly in his cover letter:

"On large shared machines often multiple jobs of a same user run in parallel. For debugging, it's usually impossible to identify requests coming from different processes."

He noted that batch schedulers such as HTCondor and SLURM launch each job inside its own PID namespace, so the namespace inode number is a natural discriminator. He was equally explicit about the patch's status:

"This path don't intended to land into the kernel, but more trigger a discussion and collect some ideas."

The Patch (Technical Detail)

The RFC patch modifies the sunrpc auth-Unix credential construction path in net/sunrpc/auth_unix.c. The core logic:

  • At credential-setup time, check whether the current process is in a non-initial PID namespace (pid_ns != &init_pid_ns).
  • If so, format the nodename as <pid_ns_inum>@<current-hostname> using snprintf into a local buffer (ns_aware_nodename), and use that prefixed string as the machinename sent to the server.
  • If the process is in the init namespace, fall through to the existing behavior (plain hostname).

The diff is small (25 insertions, 2 deletions) and self-contained within the credential path.

Review: Jeff Layton's Concerns

NFS maintainer Jeff Layton replied within roughly an hour, flagging a correctness concern by pointing to automated review comments from Sashiko:

"FYI, Sashiko has some comments on this that seem valid: … Fetching the user namespace ID might not be correct in some async ops."

Layton quoted the key patch lines — the init_pid_ns guard and the snprintf into ns_aware_nodename — to anchor his concern. The issue he raised is a classic sunrpc threading hazard: the auth-Unix credential's machinename is computed once at RPC client setup, but the process context (and thus the "current" PID namespace) may differ from the context in which subsequent async RPCs are actually executed. If the namespace is captured at the wrong point, the machinename could be stale or wrong for operations issued from a different task/namespace.

Tigran's Response and Thread Close

Tigran replied the same day (14:21 UTC, ~17 minutes after Layton's note). His reply was brief and acknowledged the feedback; no further patch revision or extended technical debate followed within this week's window.

Key Takeaways for NFS Client Developers

  1. The machinename field in auth_unix is a de-facto extension point. It is a free-form string that servers already log and display, making it a low-risk channel for embedding extra client context (namespace ID, cgroup label, job name) without any protocol change.
  2. Async credential staleness is a real constraint. Any per-process metadata injected at RPC-client setup time must be audited against the fact that sunrpc work queues and async callbacks may execute in a different task context — exactly the concern Layton surfaced via Sashiko's review.
  3. The discussion remains open. No consensus was reached this week; Tigran acknowledged the feedback but no v2 patch or design refinement has been posted as of 2026-07-02.
