NFS Direct I/O folio debate: Hellwig clarifies slab/vmalloc exposure for direct-I/O user pinning

Summary

NFS Direct I/O Folio Debate — Hellwig's Clarification on Slab/Vmalloc Exposure

Type: New feature / architectural refactor of the NFS client direct-I/O path (not a protocol change), with two embedded bug fixes. This week's single message is Christoph Hellwig's long-overdue reply to the folio-safety question that has been the thread's central open item for over a week.

Bridge from prior weeks

The thread traces back to [PATCH v2 0/7] "nfs: Modernize Direct I/O path"](https://lore.kernel.org/linux-nfs/20260616134000.2733403-1-praan@google.com/) posted by Pranjal Shrivastava (Google) on June 16, a seven-patch series migrating NFS O_DIRECT from the legacy iov_iter_get_pages_alloc2() API to the modern iov_iter_extract_pages() API and making requests folio-based. The series is groundwork for PCI Peer-to-Peer DMA (P2PDMA) and fixes two real bugs: a data-corruption bug in nfs_direct_extract_pages() (incorrect intra-page offset) and an early-unpin / bytes-accounting defect in the direct read/write loop.

The central technical dispute, which opened on June 16–18, concerns patch 6/7 ("Optimize direct I/O to use folios for requests"): whether it is safe to assume that every page returned by iov_iter_extract_pages() belongs to a valid folio and therefore page_folio() will work. Trond Myklebust, Christoph Hellwig, and Matthew Wilcox pushed back, noting the MM invariant "every page is part of a folio" has important exceptions (slab, vmalloc, iomem). Last week (June 19), Pranjal accepted the critique but raised a pointed counter-observation: the block layer's own iov_iter_extract_bvecs() path also calls page_folio() via get_contig_folio_len() without additional slab/vmalloc checks, and he asked whether the iov_iter library should export a safe helper for all filesystems.

This week: Hellwig's reply (2026-06-26)

After noting he had been slow to respond — > "[sorry, dropped the ball a bit on this due to overload]" — Christoph Hellwig replied directly to the question Pranjal posed last week about whether the bvec extractor shares the same slab/vmalloc risk.

Hellwig's answer is nuanced. He concedes that in the general case, Wilcox's concern is valid:

"True." (referring to Wilcox's point that treating slab pages as folios would trip assertions)

But he immediately narrows the scope of the problem for NFS specifically:

"But also not relevant for direct I/O user pinning. If we stopped having valid folios for anything mapped into userspace, iov_iter_extract_bvecs would run into problems, and we had the discussion before that at least right now it would be hard to fix."

This is a significant clarification: for the specific use case of NFS direct I/O — where user-space pages are pinned via GUP — the slab/vmalloc concern does not apply. The dangerous cases (slab, vmalloc) are kernel-internal memory types that would not appear in a user-pinned iov_iter for direct I/O.

Hellwig then adds a forward-looking caveat about kvec iterators:

"Also if iov_iter_extract_bvecs was used on kvec or bvec iters we could run into the slab problem. The block usage currently makes sure bvec iters are not handed to iov_iter_extract_bvecs, but there is no such thing for kvec vectors, although no one is using them for direct I/O right now. Not that I'd want to rely on that in the long run."

This last sentence — "Not that I'd want to rely on that in the long run" — is telling. Hellwig is acknowledging a latent fragility in the broader iov_iter/block layer architecture: the safety of iov_iter_extract_bvecs() for kvec iterators currently depends on an informal convention (no one uses them for direct I/O) rather than an enforced invariant. This validates Pranjal's earlier question about whether the abstraction should be made more robust at the library level.

Assessment and where things stand

Hellwig's reply effectively de-escalates the immediate concern for patch 6: the folio-grouping logic in NFS direct I/O is safe for the user-pinning path it actually handles, because GUP-pinned user pages are always valid folios. The slab/vmalloc edge cases that Wilcox flagged are not reachable through the direct-I/O user pinning mechanism.

However, Hellwig's caveat about kvec iterators keeps the broader architectural question alive. The discussion now has two distinct threads:

  1. Patch 6 as written is likely acceptable — the folio assumption holds for user-pinned pages in direct I/O.
  2. The iov_iter/block layer abstraction has a latent gap for non-user-memory iterators (kvec), which Hellwig does not want to rely on long-term but does not propose fixing in this series.

No new patches have been posted this week, and no merge decision has been recorded. The thread remains open, with the expectation that Pranjal will post a v3 incorporating the CC-list fixes, full xfstests results, and potentially minor adjustments to patch 6's comments or structure based on this clarification.
