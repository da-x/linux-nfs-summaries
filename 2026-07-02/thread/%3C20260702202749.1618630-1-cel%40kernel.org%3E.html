nfsd stable-6.12.y: CB_GETATTR change-detection fix and layout stid leak fix queued

Summary

nfsd 6.12.y stable series: delegation change detection + layout stateid teardown

What happened this week

On Thursday, July 2, Chuck Lever posted a two-patch stable backport series targeting the 6.12.y kernel for the Linux NFS server (nfsd). Both patches are bug fixes — one correcting protocol-compliant file-change detection in delegation callbacks, and the other fixing a use-after-free in pNFS layout stateid teardown. The series was queued for 6.12.y within hours by stable maintainer Sasha Levin.

Patch 1/2: Fix file change detection in CB_GETATTR (bug fix / protocol compliance)

Submitted by Chuck Lever, authored by Scott Mayhew, this patch corrects how nfsd determines whether a client holding a write delegation has modified a file when the server issues a CB_GETATTR callback.

The core technical argument is grounded in RFC 8881 (NFSv4.2), section 10.4.3:

"What section 10.4.3 of RFC 8881 does say is that the server should compare the current file size with the size reported by the client holding the delegation in the CB_GETATTR reply, and if they differ to treat it as a modification regardless of the change attribute retrieved via the CB_GETATTR."

The previous code compared a cached file size (stored in the delegation record) against the client-reported size. As Mayhew explains, this was incorrect:

"Doing otherwise would cause the server to believe the client holding the delegation has a modified version of the file, even if the client flushed the modifications to the server prior to the CB_GETATTR."

This had a notable side effect: spurious mtime/ctime/change-attribute updates on every subsequent CB_GETATTR even when no actual writes occurred. The fix modifies nfsd4_deleg_getattr_conflict() to obtain the current file size via i_size_read() rather than relying on the stale cached value. The ncf_cur_fsize field is retained as a convenience for returning the size to nfsd4_encode_fattr4(), but is no longer used for change detection.

The patch also adds logic to skip the nfs4_cb_fattr field checks when the delegation was recalled (i.e., the client didn't respond to CB_GETATTR at all).

Chuck Lever noted a minor adaptation for the 6.12.y tree: [ cel: no deleg_ts in 6.12.y; dropped the now-dead ncf_cur_fsize init ].

Patch 2/2: Release layout stid on setlease failure (bug fix / use-after-free)

Submitted by Chuck Lever, authored by Chris Mason, this patch fixes a dangling-pointer bug in the pNFS layout stateid error path.

The technical problem is precisely described:

"nfs4_alloc_stid() publishes the new stid into cl->cl_stateids via idr_alloc_cyclic() under cl_lock before returning to nfsd4_alloc_layout_stateid(). When nfsd4_layout_setlease() then fails, the error path frees the layout stateid directly with kmem_cache_free() without ever calling idr_remove(), leaving the IDR slot pointing at freed slab memory. Any subsequent IDR walker (states_show, client teardown) dereferences the dangling pointer."

The fix replaces the manual nfsd_file_put + put_nfs4_file + kmem_cache_free cleanup with a single nfs4_put_stid(stp) call, which properly removes the IDR slot under cl_lock, dispatches sc_free to release the layout file via nfsd4_close_layout(), and drops the nfs4_file reference.

This is a straightforward three-line change (1 insertion, 3 deletions) in fs/nfsd/nfs4layouts.c. The original bug was introduced by commit c5c707f96fc9 ("nfsd: implement pNFS layout recalls").

Chuck Lever adapted the patch for 6.12.y: [ cel: no ls_fence_work in 6.12.y; dropped INIT_DELAYED_WORK hunk ].

Assessment

This thread represents routine but important stable maintenance work on the NFS server side. Both patches address real correctness issues:

  1. CB_GETATTR fix — a protocol-compliance bug that could cause unnecessary metadata churn and false modification detection, affecting any NFSv4.2 deployment using write delegations with CB_GETATTR callbacks.
  2. Layout stid fix — a memory-safety bug (use-after-free via dangling IDR pointer) in the pNFS layout recall path, triggered only when nfsd4_layout_setlease() fails after stateid allocation. While narrow in trigger conditions, the consequence is a kernel oops or worse if any code walks the stateid IDR.

Neither patch introduces new features or protocol changes; both are targeted bug fixes with clear upstream provenance and appropriate stable backport annotations. The rapid turnaround (posted 20:27 UTC, queued by 02:05 UTC the next day) reflects the well-oiled workflow between nfsd maintainers and the stable tree.
