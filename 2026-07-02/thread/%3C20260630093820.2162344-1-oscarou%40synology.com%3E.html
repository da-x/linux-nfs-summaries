lockd: refcount NLM_SHARE access/deny modes — v1/v2 reviewed, idempotency concern raised

Summary

lockd: refcount NLM_SHARE access/deny modes

Type: Bug fix (server-side NLM share tracking), with a protocol/robustness angle.

The reported bug

Oscar Ou of Synology opened the thread on 2026-06-30 with a patch describing a long-standing defect in the Linux lockd server's handling of NLM_SHARE / NLM_UNSHARE:

"When an NFSv3/NLM client issues multiple NLM_SHARE calls from a single host for the same (file, owner) tuple, the current implementation overwrites the recorded access and deny modes with the latest pair. A subsequent NLM_UNSHARE then drops the entire entry, even if other grants were implicitly subsumed by the most recent SHARE."

Oscar noted this is "particularly visible to Windows-style clients that map each open of a file to a distinct NLM_SHARE, all carrying the same NLM owner handle," and walked through a four-step scenario where an RW/deny-W reservation silently disappears after a second R/deny-N share overwrites it. The v1 fix tracked each of the four fsh_access / fsh_mode values with a small per-value refcount, recomputed s_access/s_mode as the union of positive buckets, and extended NLM_UNSHARE to carry the access/deny modes so the correct buckets could be decremented.

Chuck Lever's v1 review — three concrete nits

Chuck Lever's reply the same afternoon was a dense, code-level review that rejected v1 as written but pointed the way forward:

  1. Wrong locking claim. Oscar's commit message said the per-file f_mutex "continues to serialise share manipulation." Chuck showed this is inaccurate — nlm_lookup_file() in fs/lockd/svcsubs.c drops file->f_mutex before returning, so by the time nlmsvc_share_file() runs it is not held. The real reason no extra locking is needed:

    "What actually serialises these requests is that lockd runs a single service thread (svc_set_num_threads(serv, 0, 1) in fs/lockd/svc.c), so the conclusion that the arrays need no extra locking holds."

  2. Commit-message invariant mismatch. Because the recompute loop starts at v = 1, bucket index 0 (fsa_NONE / fsm_DN) is written but never read, so an entry can be freed while s_access_counts[0] or s_mode_counts[0] is still non-zero. Chuck flagged that the wording "the entry is freed only when every bucket has reached zero" is "slightly stronger than the code."

  3. Out-of-bounds write from a remote client. The most serious issue:

    "A remote NLMv4 client can drive access or mode out of {0..3} here and write past s_access_counts[] / s_mode_counts[]. There are one or two other spots with the same issue. Thus your patch can't be applied as written."

    Chuck announced he would post a companion patch regenerating the NLMv4 XDR decoders to prevent exactly this, and asked about a Fixes: tag — noting the bug dates back to commit 1da177e4c3f4 ("Linux-2.6.12-rc2") but "a proper fix will need both the regeneration patch and this one to be applied."

v2 — cleanups, plus a process lesson

Oscar's v2 addressed both review points: the commit message now says the entry "is freed once s_access and s_mode are both zero," and the incorrect f_mutex claim was dropped from both the message and the comment on nlm_recompute_share(). The patch is marked "Applies on top of 'lockd: Regenerate NLMv4 XDR code' by Chuck Lever" and deliberately carries no Fixes: tag, with Oscar explaining that "a Fixes: tag would mislead -stable backporters."

Chuck's reply to v2 opened with a process note — two of the more instructive bits of contributor guidance in this week's digest:

"1. New thread per revision — no In-Reply-To: back to the old version. Post v2 as its own top-level thread; don't reply-to the v1 cover or any v1 patch."

He explained that b4 and patchwork group threads by reference chain, so threading v2 under v1 makes b4 am "pick up stale patches" and lets maintainers who "apply the latest" grab the wrong blobs. Second: use [PATCH v2], not RESEND — "RESEND is only for re-sending an /unchanged/ series that got no response."

The idempotency problem — where the discussion lands

The substantive core of Chuck's v2 review was a deeper protocol concern he had not raised in v1: NLM has no duplicate reply cache, so every request handler must be idempotent. He walked through nlmsvc_dispatch() and noted that LOCK, UNLOCK, CANCEL, FREE_ALL, and SM_NOTIFY are all built around that invariant — "a replayed request lands on the same state." The refcount design breaks it in both directions:

  • Replayed SHARE over UDP (lost reply → client retransmit) increments the bucket a second time, so a single matching UNSHARE leaves s_access_counts[3] = 1 and "the entry is never freed" — potentially leaving a stale share reservation that denies later conflicting opens until the host is torn down.

  • Replayed UNSHARE decrements a still-positive bucket, so a retransmit can free the entry while the client still holds a second open with the same (access, deny) pair:

    "Here the client still holds open #2, but its reservation is gone, so a conflicting open from another owner would now be granted. Can a retransmitted UNSHARE release a grant the client still holds?"

Chuck proposed an alternative — track the set of held (access, deny) combinations with a 16-bit mask rather than per-value counts:

SHARE(a, d):   held_mask |=  BIT((a << 2) | d);
UNSHARE(a, d): held_mask &= ~BIT((a << 2) | d);

Setting or clearing a bit is idempotent, so retransmits land on the same state. He acknowledged the tradeoff — two opens with an identical (access, deny) pair collapse to one bit — but argued it stays within RFC 1813, which "does not require that repeated identical SHAREs from one owner survive an equal number of UNSHAREs," and whose duplicate-request discussion (section 4.5) treats non-idempotent requests as something a reply cache must guard, "which lockd does not run for NLM."

He closed with the verdict on the refcount approach:

"The bottom line is that after more consideration, IMO the reference count approach is not going to work, in particular because NLM still operates on unreliable network transports like UDP. Consider the above direction not as a mandate but as a possible approach that might address the issue you've reported while avoiding introducing non-idempotency."

Status at end of week

The thread ends with Chuck's idempotency critique outstanding — no v3 has been posted, and no ack or fix is in the tree. The underlying bug (SHARE/UNSHARE state corruption for multi-open NLM clients) remains unfixed upstream; the path forward appears to be a mask-based redesign plus Chuck's pending XDR-regeneration patch that closes the remote out-of-bounds write.
