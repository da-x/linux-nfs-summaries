fhandle: one-line fix rejects detached mounts in capable_wrt_mount() to stop a NULL mnt_ns panic

Summary

fhandle: reject detached mounts in capable_wrt_mount() — crash fix lands same day

A compact but consequential bug-fix thread closed out this week on the NFS list, centered on a one-line patch from Trail of Bits that plugs a kernel panic reachable through open_by_handle_at() against a file handle pointing at a mount that has been detached mid-flight. Because open_by_handle_at() is the VFS entry point that NFS (and other network filesystems) use to resolve opaque file handles, the fix matters directly to NFS client behavior even though the code lives in fs/fhandle.c.

The bug: a stale non-NULL assumption in an RCU path

David Lee of Trail of Bits posted the patch on July 1, describing a race introduced by a recent fhandle RCU fix that moved the mount-namespace capability check into capable_wrt_mount():

"The recent fhandle RCU fix moved the mount namespace capability check into capable_wrt_mount(), so a non-NULL mnt_namespace survives the ns_capable() dereference. The helper still assumes the later READ_ONCE(mount->mnt_ns) must be non-NULL because may_decode_fh() checked is_mounted() first."

Lee explained that this assumption "is not stable": a detached mount produced by open_tree(..., OPEN_TREE_CLONE) can be dissolved on fput while open_by_handle_at() sits between the two checks, and umount_tree() can clear mount->mnt_ns. If the helper then observes NULL, it dereferences mnt_ns->user_ns and panics.

The fix is deliberately conservative — return false when the RCU read sees a detached mount:

"Return false when the RCU read observes a detached mount. This keeps the relaxed permission path conservative: a mount no longer attached to a namespace cannot authorize open_by_handle_at() access."

The patch carries Fixes: 620c266f3949 ("fhandle: relax open_by_handle_at() permission checks") and is Cc'd to stable, with the cover note stating that "Trail of Bits has a minimal PoC that triggers this crash on a custom kernel build, which can be shared further if needed."

Review and merge: same-day Reviewed-by, applied to vfs.fixes

NFS maintainer Jeff Layton responded within roughly 35 minutes, after quoting the relevant portion of may_decode_fh():

"Seems sane. Reviewed-by: Jeff Layton jlayton@kernel.org"

VFS maintainer Christian Brauner then applied the patch to the vfs.fixes branch of vfs/vfs.git (commit b2f046af8c6c), noting that "Patches in the vfs.fixes branch should appear in linux-next soon" and encouraging any further review feedback on a new thread.

Takeaways for NFS client work

  • Classification: bug fix (NULL-pointer panic / race), not a feature or protocol change; one insertion, one deletion in fs/fhandle.c.
  • NFS relevance: open_by_handle_at() is the syscall path by which NFS clients and server-side handle resolution interact with the VFS. A crash here is a local kernel DoS triggered through file-handle operations, so stable backports are warranted for any host that mounts network filesystems.
  • Pattern worth watching: this is the second fhandle RCU-related fix in the same area (the Fixes tag points at commit 620c266f3949), suggesting the relaxed permission path introduced by that earlier change may deserve a broader audit of its non-NULL assumptions under concurrent mount teardown.

The thread is fully resolved: patch posted, reviewed, and merged into vfs.fixes on July 1, 2026.
