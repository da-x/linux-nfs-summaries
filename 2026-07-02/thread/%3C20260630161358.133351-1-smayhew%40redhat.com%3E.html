rpcbind: One-line fix for nconf memory leak in main()

Summary

rpcbind: Fix Leak of nconf in main()

Type: Bug fix (memory leak)
Component: nfs-utils / rpcbind (userspace NFS client-side RPC portmapper)
Status this week: Committed

The Patch

On June 30, Red Hat's Scott Mayhew posted a minimal one-line patch to the rpcbind daemon: [PATCH] rpcbind: fix leak of nconf in main(). The commit message explains the problem clearly:

"Before reusing nconf in the getnetconfig() loop, we need to free the memory that was previously allocated via getnetconfigent()."

The bug is a classic C memory-management slip: rpcbind's main() iterates over network configuration entries using getnetconfigent() from libtirpc. Each call allocates a new structure, but the code was reusing the nconf pointer on the next loop iteration without freeing the prior allocation. Valgrind confirmed the leak:

"1,136 (136 direct, 1,000 indirect) bytes in 1 blocks are definitely lost in loss record 63 of 67 … at malloc … by getnetconfigent (in /usr/lib64/libtirpc.so.3.0.0) … by main (rpcbind.c:271)"

The fix adds a single free() call before the pointer is reassigned, touching just one line in src/rpcbind.c.

Resolution

The response was swift and unambiguous. On July 1, Steve Dickson—long-time maintainer of nfs-utils—replied with a simple acknowledgement:

"Committed…"

No review discussion, no objections, no follow-up questions. The patch was accepted and merged within roughly 24 hours of posting.

Significance

While small in scope, this fix addresses a real (if minor) resource leak in rpcbind, the userspace daemon that underpins RPC service registration for NFS clients and servers on Linux. A leaking rpcbind could accumulate memory over long uptimes or repeated restarts. The valgrind-driven discovery process underscores the ongoing effort to harden nfs-utils against subtle memory bugs. For NFS client developers, a clean rpcbind is a prerequisite for reliable portmapper lookups, so eliminating even small leaks contributes to overall stack robustness.
