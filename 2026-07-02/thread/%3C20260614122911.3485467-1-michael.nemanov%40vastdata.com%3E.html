Bridge from Prior Week

The original patch was submitted on June 14 (see the 2026-06-18 summary). In brief, the bug: calling open(2) with O_CREAT on a path that already exists as a symlink, over an NFSv3 mount with a cold dentry cache, causes the kernel to return ENXIO instead of following the symlink. The root cause is a confluence of NFSv3 CREATE UNCHECKED semantics (RFC 1813 §3.3.8 returns NFS3_OK with the existing object's file handle rather than NFS3ERR_EXIST), an unconditional finish_open() call after nfs_do_create() succeeds, and the VFS's use of &no_open_fops for symlink inodes (which returns -ENXIO). The fix adds a 7-line type check — using !S_ISREG() rather than S_ISLNK() to be defensive against any non-regular file type a server might return — and dispatches through finish_no_open() so the VFS can follow the symlink normally. The patch carries a Fixes: tag pointing to commit 7c6c5249f061.

Significance for NFS Client Development

The re-post underscores a recurring theme in NFS client work: the fragility of the atomic_open path when an NFSv3 server returns an unexpected file type. The bug is masked by a warm dcache (a prior stat(2) causes lookup_open() to find a positive dentry and skip atomic_open entirely), which is precisely why it slipped through — it only manifests on cold-cache paths, the kind of edge case that's easy to miss in day-to-day testing but visible in production workloads with high churn.

The "Trying again" re-post is a common pattern on linux-nfs for small fixes that don't get immediate attention; it keeps the patch visible without requiring a new version.
