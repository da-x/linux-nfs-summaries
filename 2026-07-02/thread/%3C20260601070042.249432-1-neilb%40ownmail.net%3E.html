Christian Brauner green-lights resubmission of NeilBrown's vfs_lookup_open() series, defers O_CREAT|O_DIRECTORY ordering

Summary

Christian Brauner clears the path for a resubmission of the vfs_lookup_open() series

The one message that matters this week

This week was quiet — exactly one message landed in the window, but it is a significant one. On July 2, VFS maintainer Christian Brauner replied directly to NeilBrown's June 1 cover letter for the first time, answering the two process questions that had been left hanging ever since the 18-patch RFC "VFS/nfsd: replace dentry_create()" was posted.

Brauner's reply is short but decisive, and it resolves the first open item outright:

"Yes, please resubmit."

This is a direct answer to NeilBrown's cover-letter note that he "probably will need to resubmit after a bunch of that has hit mainline - though a few of the patches could easily be cherry-picked now." Getting an explicit "yes" from the VFS maintainer — rather than a silence or a "not yet" — is the kind of signal that moves an RFC out of limbo. The series had been waiting on exactly this go-ahead, since it touches core VFS code (lookup_open(), open_last_lookups()) well outside nfsd's usual lane.

The second question: O_CREAT|O_DIRECTORY ordering — deferred, not resolved

The cover letter also flagged a scheduling conflict that Brauner addresses with characteristic understatement:

"This will conflict with the O_CREAT|O_DIRECTORY work so obviously we'll need to work out how to order them once we both have enough positive review."

Brauner's response acknowledges the problem but does not solve it:

"I have that on my todo but somehow said todo keeps growing..."

So the ordering of this series against the in-flight O_CREAT|O_DIRECTORY work remains open. The practical takeaway is that a resubmission is welcome, but it will need to be sequenced carefully against Brauner's own pending directory-creation changes once both have accumulated enough review. This is a "we'll sort it out when we get there" rather than a firm plan — the classic maintainer deferral.

Classification

This message is process/maintenance, not a new feature, protocol change, or bug fix in itself. It is the VFS maintainer's endorsement of the resubmission path for a series that is fundamentally a VFS API refactoring with bug-fix motivation (eliminating dentry_create() and fixing an NFS re-export deadlock class). The technical substance — the locking model, the atomic_open unification, the NFSv4 OPEN semantics — was all established in prior weeks; this week's contribution is that the VFS side has now formally agreed to take a resubmission.

Bridging prior weeks (brief)

  • Week of 2026-06-04: NeilBrown posted the 18-patch RFC introducing vfs_lookup_open() to replace dentry_create(), motivated by a deadlock his earlier 53-patch directory-locking RFC would have caused when re-exporting NFS filesystems. Jori Koolstra reviewed patches 01–05, granting three Reviewed-by tags and raising questions on 04 (O_EXCL enforcement) and 05 (FMODE_CREATED semantics).
  • Week of 2026-06-11: NFS maintainer Chuck Lever reviewed the nfsd-specific tail. He found a stray fh_drop_write() in PATCH 16/18 (cosmetic, acknowledged by NeilBrown) and — more importantly — a protocol-breaking logic bug in PATCH 17/18 where "Every CLAIM_NULL open of an existing file fails with NFS4ERR_EXIST." NeilBrown confirmed the bug and proposed a concrete fix, gating the create-specific path on open->op_create == NFS4_OPEN_NOCREATE, and additionally moved the ATTR_SIZE clearing into the create-only branch to avoid truncating existing files.

The series has thus been in a "fixes identified, resubmission pending" state for three weeks — until Brauner's message this week removed the last VFS-side blocker on resubmitting.

Relevance to NFS client development

Although this is server-side (nfsd) and VFS work, the stakes for NFS clients are real and were crystallized by last week's review:

  • The NFS4ERR_EXIST bug was a client-facing landmine. It would have broken the most common NFSv4 operation — plain opens of existing files (NFS4_OPEN_NOCREATE / CLAIM_NULL). Any client doing standard file access against a server running an unpatched version of this series would have seen its opens fail. The fact that it was caught in review, and is now slated for a corrected resubmission, is the important outcome for client stability.
  • The ATTR_SIZE scoping fix prevents silent data loss. Had the size-clearing (a truncate-to-zero) run on non-creating opens, existing files could have been silently truncated. Moving it into the create-only path protects client data.
  • Re-export correctness and atomic_open unification mean servers that re-export NFS filesystems will use a create/open path consistent with local filesystems — relevant to clients relying on atomic-create semantics such as NFS4_CREATE_GUARDED.

Status and outlook

As of the close of this week's window:

  1. Resubmission is explicitly green-lit by Christian Brauner ("Yes, please resubmit").
  2. Ordering against O_CREAT|O_DIRECTORY remains unresolved — deferred to a later coordination once both efforts have enough positive review.
  3. The series still needs to absorb the two fixes from Chuck Lever's review (the stray fh_drop_write() and the NFS4ERR_EXIST/ATTR_SIZE corrections in PATCH 17/18) before it is resubmitted.
  4. Patches 06–15 and 18 still lack full nfsd-maintainer review; the VFS-side questions on patches 04 and 05 from Jori Koolstra also remain formally open, though Brauner's blanket "please resubmit" suggests the VFS side is no longer a gating concern.

The near-term expectation is a revised v2 of the series once NeilBrown folds in the review fixes and the base trees (nfsd-testing, vfs-next) settle into mainline.
