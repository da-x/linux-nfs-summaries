sunrpc pool_mode hardcoding: empty-pool debate and belt-and-braces fix outlined

Summary

sunrpc: hardcode pool_mode to pernode — empty-pool edge case drives the design

Context (bridging prior week)

Jeff Layton posted v2 of this patch on June 25, removing the long-standing SVC_POOL_AUTO/GLOBAL/PERCPU/PERNODE selection machinery from the NFS server (sunrpc) layer and making "pernode" the only pool mode. Chuck Lever's review that same day raised the central technical concern: when nrservs < number of NUMA nodes, trailing pools end up with zero threads, and there is no fallback in the enqueue path — a connection landing on an empty pool would sit unserviced. This week's activity (all four messages landed on Friday, June 26) is entirely about working through that edge case plus a handful of code-level nits.

Type: Server-side cleanup / behavior change in sunrpc — not an NFS client feature or protocol change. The relevant "bug" being addressed is a latent starvation bug (work routed to a pool with no threads and never serviced) that becomes reachable once the global-pool escape hatch is removed.

This week's activity

NeilBrown's review: code nits and a design opinion

NeilBrown opened this week's discussion with a series of targeted code-level comments on the v2 diff, then weighed in on Chuck's empty-pool concern:

"!strncmp" is one most disliked construct.... What would you think of using match_string() or even sysfs_match_string() ??

On the deprecation notice (pr_notice("sunrpc: the pool_mode parameter is deprecated and will be removed in a future release.\n")):

Which future release? How will we remember?

He also suggested making the refcount decrement explicit — m->count = 0 rather than m->count-- — "to make it crystal clear that there are now no references," and asked whether svc_pool_for_cpu() could run when m->count is zero.

On the design question, NeilBrown endorsed a per-node minimum:

I think this is a good a worthwhile change. Regarding Chucks comments, I think a minimum of one thread per node, rather than a minimum of one thread total, is the sensible approach. Of course if there exist memory-only nodes, they wouldn't need a thread.

Chuck Lever pushes back on memory-only nodes

Chuck Lever replied with a sharp follow-up that complicates NeilBrown's "skip memory-only nodes" carve-out:

What happens when transport work is scheduled on a memory-only pool? Obviously there's no execution engine there, even if we do provide one or more threads.

The point: a memory-only NUMA node has no CPUs to run a thread on, so the question isn't whether to spawn a thread there but what happens when work is routed there by the per-node pool selection (which keys off the running CPU / memory locality). This reframes the problem from "how many threads do we spawn" to "what do we do when the selected pool can't execute anything."

Jeff Layton's belt-and-braces solution

Jeff Layton responded to Chuck with a two-part approach, carefully preserving userland's ability to dictate per-pool thread counts:

The hitch here is that we have traditionally allowed userland to dictate how many threads each pool gets. You're allowed to send down an array like this with (4 pools): 0 128 0 0. That would give you exactly that layout (128 threads in pool 2 and none elsewhere). I think we can continue to honor that by saying that if you set a thread count of 0 in a pool then we should not spawn any threads there.

Because of this, I favor a belt and bracers approach: 1/ when min-threads is set, assign at least one thread to each node that has a cpu as a minimum, but only when we are auto-distributing threads between nodes (the typical case). This allows us to preserve the wishes of userland when it sends down a more complex pool array. We should not override the user's wishes in that case. 2/ add in a fallback in the queueing path so that when there are no threads in a node, we queue it to a populated one. We could even add a pr_notice_once() that fires in that case to warn that the configuration is sub-optimal. The cost is an extra check for sp_nrthreads == 0 when enqueueing, but it should almost always come back false when things are properly configured.

This is the most technically significant contribution of the week: it resolves both Chuck's starvation concern (fallback in the queueing path) and NeilBrown's per-node minimum (auto-distribution assigns ≥1 thread to each CPU-bearing node), while respecting explicit userland configuration. The pr_notice_once() is a nice touch for surfacing misconfigurations without spamming the log.

Jeff Layton addresses NeilBrown's nits

In a separate reply, Layton confirmed the code-level fixes:

  • sysfs_match_string(): "Thanks. Switched to sysfs_match_string()."
  • Deprecation message: "I'll make this more vague. I'm not sure what the guidance is on removal of knobs like this. A few years, I guess?"
  • m->count = 0: "Yep, fixed. I didn't rename the counter though. That can be future cleanup."
  • Can svc_pool_for_cpu() run with m->count == 0? This was a substantive correctness question, and Layton confirmed it can:

Yes, it can. It's called unconditionally from svc_new_thread(), which runs for non-pooled services created via svc_create() (e.g. lockd) that never call svc_pool_map_get(). In that case m->count == 0 and m->pool_to == NULL.

This is an important edge case: lockd and other non-pooled services go through svc_new_thread() without ever initializing the pool map, so any code in that path must tolerate a zero-count / NULL-pointer state. Layton also cross-referenced his earlier reply on the empty-pool fallback: "I responded to Chuck's reply on this point. I think that's part of a solution, but we probably also need to avoid queueing to pools (nodes) that have no threads in them, to help catch misconfigurations."

Key technical takeaways

  1. The starvation bug is real and now reachable. With global mode removed, a NUMA system with more nodes than nrservs will have empty pools, and the current enqueue path has no fallback. This is the primary bug fix driving the v3 changes.
  2. The solution is layered: (a) auto-distribution guarantees ≥1 thread per CPU-bearing node; (b) explicit userland arrays are honored as-is (including zeros); (c) a queueing-path fallback routes work to a populated pool when the selected one is empty, with a one-time warning.
  3. Memory-only NUMA nodes (present on some ARM64/CXL platforms) complicate the "one thread per node" rule — you can't run a thread where there's no CPU, so the fallback in the queueing path is essential, not just belt-and-braces.
  4. Non-pooled services (lockd) exercise svc_pool_for_cpu() with an uninitialized pool map (m->count == 0, m->pool_to == NULL), a subtle edge case that must be preserved in any refactor.

Status

No v3 has been posted as of the end of this window. Layton has outlined a clear path forward (per-node minimum for auto-distribution + enqueue fallback + code nits fixed) and the discussion appears to have converged on the design. The thread is expected to produce a v3 in the coming days.
