SUNRPC TLS control-record v2: length check before fatal classification

Summary

Chuck Lever posted v2 of an eight-patch bug-fix series that hardens how in-kernel SUNRPC consumes kTLS control records on both the NFSD server path (svcsock.c) and the NFS client path (xprtsock.c). This is not a protocol change and not a new feature: RFC 8446 / RFC 9289 framing is unchanged. The work remains a cleanup of the existing CMSG receive path after the read_sock_rectype proto_ops proposal was NACKed on netdev.

No replies landed in-window. The series is v2, posted 6 August, and still waiting on review — in particular an Acked-by from the NFS client maintainers for the three xprtsock.c patches. A later v3 exists as a follow-up thread outside this week’s window.

Brief recap of v1 (same week)

v1 landed the day before with the same eight fixes and the same LTS-backport posture. It was summarized separately. The defects were not reported in the field; they were found while designing a replacement for read_sock_rectype. v1 ordered the server-side “treat every TLS error alert as fatal” patch before the two-octet length check that guards it, and did the same on the client. v2 exists to reverse that order and to tone down one comment.

Why the series exists (unchanged from v1)

Lever’s v2 cover letter restates the provenance in the same candid terms:

"The read_sock_rectype proto_ops method is not going forward. Designing its replacement meant another pass over the receive path it was meant to replace, and that pass turned up the defects fixed here. None arrived as a bug report."

The control-message path has already been rewritten twice. Lever recites the history: 5e052dda121e added CMSG recognition; 39067dda1d86 moved parsing into net/handshake; bee47cb026e7 and cc5d59081fa2 reworked both sides after Scott Mayhew reported that kTLS was writing alert bodies into the RPC receive buffer (FreeBSD mutual-TLS mounts broke); 9559d2fffd4f restored the other cmsg types. The last rework moved the receive into a local buffer, but the length accounting did not follow.

The remaining defects:

  • A control record’s octets are credited to the RPC stream.
  • A consumed control record leaves the server transport unmarked, so an RPC Call queued behind an Alert or KeyUpdate waits for the peer to send more.
  • The peer still controls the alert body’s length, and nothing checks it before tls_alert_recv() reads two octets from an uninitialized stack buffer.
  • A peer that aborts with an error alert while leaving the legacy AlertLevel octet set to warning currently leaves a dead TLS session attached to a live transport.

Lever is explicit that the accounting bugs have no trigger today:

"These accounting defects do not have a trigger today. Both need a peer that sends a post-handshake control record (e.g., KeyUpdate). However, no existing RPC-with-TLS implementation does this today. Therefore these patches are posted as individual fixes that can be backported if LTS kernels should need to interoperate when KeyUpdate subsequently arrives in clients and servers."

That policy is unchanged: keep each fix independently backportable rather than bundling a larger helper refactor.

What changed in v2

The cover letter’s “Changes in v2” list is short and mechanical:

"- Series reorder: length check goes before the severity change it guards

  • Reword the XPT_DATA comment to drop an overstated guarantee
  • Link to v1"

The reorder is the technically important one. In v1, “treat every TLS error alert as fatal” ran before “reject a TLS alert record that is not two octets” on both the server and the client. That meant the severity classifier could inspect a description octet that tls_alert_recv() had just read from uninitialized stack. v2 puts the two-octet gate first so a malformed or zero-length Alert never reaches the description-based close/keep decision.

The XPT_DATA comment tweak lives in PATCH v2 4/8 (resume receiving after a TLS control record). Lever does not quote the old wording in the cover; the intent is that the comment no longer claims a stronger “transport is ready” guarantee than the drain-and-mark-ready path actually provides.

Everything else — Fixes: tags, backport shape, deferred net/handshake/alert.c helper — is the same as v1. Lever still asks:

"I'd appreciate an Acked-by from the client maintainers for the three patches that touch xprtsock.c."

Those three are now patches 6–8, with the client length check also moved ahead of the client severity change.

Server-side fixes (svcsock.c)

PATCH v2 1/8 — do not credit control-record octets to the RPC stream. (Was 2/8 in v1.)

svc_tcp_sock_recv_cmsg() receives up to two octets into a local buffer and returns that count for any record type other than TLS_RECORD_TYPE_ALERT. Nothing reached the caller’s buffer, but svc_tcp_read_marker() adds the count to sk_tcplen and svc_tcp_read_msg()’s caller adds it to sk_datalen. The RPC stream advances over octets it never received: the fragment marker is assembled from stale sk_marker octets, and the message body comes from pages nothing wrote.

A conforming client can hit this. RFC 8446 Section 4.6.3 lets either peer send KeyUpdate once it has sent Finished, and svcsock has no rekey path. kTLS leaves the partially consumed record on ctx->rx_list, so the body drains two octets per svc_tcp_recvfrom() call, each pair credited the same way. The patch returns -EAGAIN for a non-alert record — restoring the default arm of svc_tcp_sock_process_cmsg() from before the receive moved into a local buffer. Fixes bee47cb026e7.

PATCH v2 2/8 — reject a TLS alert record that is not two octets. (Was 3/8 in v1; now before the severity change.)

tls_alert_recv() reads two octets from the kvec it is handed and does not check the length. The alert[] buffer has no initializer. A one-octet alert body leaves the description read from uninitialized stack and reported through trace_tls_alert_recv(). Neither tls_rx_msg_size() nor tls_rx_one_record() enforces the two-octet Alert payload; a TLS 1.3 record carrying only the inner content-type octet decrypts to a zero-length payload. RFC 8446 Section 5.1 requires a record with an Alert type to carry exactly one message, so any other length is malformed.

The patch requires exactly two octets before parsing and returns -EBADMSG otherwise, closing the transport rather than acting on a partly uninitialized alert. The path is gated on a control message rather than a positive count so a zero-length record still reaches the check. Fixes bee47cb026e7.

PATCH v2 3/8 — treat every TLS error alert as fatal. (Was 1/8 in v1; now after the length check.)

svc_tcp_sock_process_cmsg() currently decides whether an alert ends the session by reading the AlertLevel octet. RFC 8446 Section 6 retired that field: severity is implicit in the description, and a receiver treats every alert listed in Section 6.2 as an error alert “regardless of the AlertLevel in the message.” A peer that aborts with unexpected_message but leaves the legacy octet set to warning makes the server return -EAGAIN. svc_tcp_recvfrom() then leaves a dead TLS session attached to an open transport, and NFSD keeps polling it.

The fix classifies from the alert description instead. close_notify and user_canceled are the only closure alerts (RFC 8446 Section 6.1). Every other description — including one this kernel does not recognize — ends the session. Fixes 39067dda1d86.

PATCH v2 4/8 — resume receiving after a TLS control record.

A TLS control record delivers no payload to the RPC layer. svc_tcp_recvfrom() clears XPT_DATA before the receive, and svc_tcp_sock_recv_cmsg() returns -EAGAIN for the record it consumed. Nothing marks the transport ready again. kTLS raises data_ready for arriving TCP segments, not for records it has already decrypted. An RPC Call queued behind an alert or a KeyUpdate waits until the client sends more; the client blocks until its RPC timeout expires. Worse, the receive takes only the first two octets of the record, so kTLS holds the remainder on its receive list and each later receive takes two octets more.

The patch drains a non-alert record, then marks the transport ready once a control record has been consumed. This is also where the v2 XPT_DATA comment reword lives. Fixes 5e052dda121e.

PATCH v2 5/8 — fold svc_tcp_sock_process_cmsg() into its only caller.

After patches 1–4, svc_tcp_sock_recv_cmsg() returns -EAGAIN for every record type except an alert before it calls the helper, so the case 0, TLS_RECORD_TYPE_DATA, and default arms are unreachable. The DATA arm is inert twice over: it clears MSG_EOR in a local msghdr that is discarded on return, and svc_tcp_sock_recvmsg() has already cleared the flag in the caller’s msghdr. Deriving the record type a second time also fires trace_tls_contenttype() twice for every alert. The helper is deleted; the DATA arm’s MSG_EOR account moves to svc_tcp_sock_recvmsg().

NFS client-side fixes (xprtsock.c)

The client half is the part that matters most for NFS client development this week. The three xprtsock.c patches still mirror the server-side alert-severity and length checks, then do the same helper fold. They still do not include the server’s “do not credit control-record octets” or “resume receiving after a control record” fixes — those are svcsock-specific because of how sk_tcplen / XPT_DATA work. The client path already returns -EAGAIN for non-alert control records; the remaining holes are classification, length, and dead helper code.

v2’s reorder applies here too: the length check is now 6/8 and the severity change is 7/8, so a malformed Alert cannot drive the fatal/closure decision.

PATCH v2 6/8 — reject a client-side TLS alert record that is not two octets. (Was 7/8 in v1.)

Same uninitialized-stack hazard as the server: tls_alert_recv() reads two octets with no length check, and xs_sock_recv_cmsg()’s alert[] buffer is uninitialized. A one-octet (or zero-octet) alert body reports garbage through trace_tls_alert_recv(). RFC 9289 Section 5 bars RPC-with-TLS from negotiating below TLS 1.3, so no other alert framing applies.

The client returns -EACCES rather than the server’s -EBADMSG, because xs_stream_data_receive() already treats -EACCES as a fatal alert and reports it to pending tasks. The path is gated on a control message rather than a positive count so a zero-length record still reaches the check. Fixes cc5d59081fa2.

PATCH v2 7/8 — treat every client-side TLS error alert as fatal. (Was 6/8 in v1; now after the length check.)

xs_sock_process_cmsg() has the same AlertLevel bug as the server. A peer that aborts with unexpected_message but leaves the legacy octet set to warning makes the client return -EAGAIN. xs_stream_data_receive() wakes no pending task for that error, so RPC Calls queued on a dead TLS session wait for their timeouts to expire. Same classification as the server: close_notify and user_canceled close cleanly; every other description, including an unrecognized one, ends the session. Fixes 39067dda1d86.

This is the client-visible hang. Without it, a kTLS-enabled NFS mount that receives a fatal alert with a spoofed-or-legacy warning level sits on a dead session until every in-flight RPC times out. Putting the two-octet check first means that hang is not replaced by a misclassification of garbage.

PATCH v2 8/8 — fold xs_sock_process_cmsg() into its only caller.

xs_sock_process_cmsg() switches on the TLS record type, and every arm but TLS_RECORD_TYPE_ALERT returns the -EAGAIN its caller passed in. The DATA arm clears MSG_EOR in the caller’s msghdr, but xs_sock_recvmsg() has already cleared that flag. Deriving the record type a second time also fires trace_tls_contenttype() twice. Alert handling moves into xs_sock_recv_cmsg(); the helper is deleted; the MSG_EOR account moves to xs_sock_recvmsg().

Deferred work and LTS posture

Lever notes that the two call sites this series touches are the last consumers of <net/tls_prot.h> in net/sunrpc/. Both now state the same record-type test, the same two-octet rule, and the same closure classification. A helper in net/handshake/alert.c could hold all three and return a verdict, which would let net/sunrpc/ drop the header and keep only the transport policy. That is deferred:

"That is deferred to a next step rather than included as part of this series to keep LTS backports practical."

The series is therefore still eight independently bisectable, independently backport-able commits rather than a single handshake-layer helper plus two call-site conversions. The Fixes: tags point at 39067dda1d86, bee47cb026e7, cc5d59081fa2, and 5e052dda121e — the earlier CMSG reworks — so stable maintainers have a clear trail if KeyUpdate shows up in the field before a later helper lands.

What this means for NFS client development

This is the second concrete client-side xprtsock.c posting this week, and the one that should actually be reviewed. The related read_sock_rectype discussion remains stuck on documenting ->read_sock’s errno contract; that conversion is not happening. Meanwhile Lever is hardening the CMSG path the client already uses:

  • The two-octet Alert check now runs before description-based classification. A kTLS NFS client will not parse uninitialized stack into a close/keep decision, and will not report garbage through trace_tls_alert_recv(). Malformed Alert records (wrong length, including the TLS 1.3 zero-payload case) become -EACCES and are reported to pending tasks.
  • Fatal-alert classification no longer trusts the retired AlertLevel octet. A kTLS NFS client will tear down the session on any Section 6.2 error description, even if a peer (or a buggy stack) leaves the level set to warning. Without this, in-flight RPCs sit on a dead TLS session until timeout.
  • The client still does not implement a KeyUpdate/rekey path. Non-alert control records continue to return -EAGAIN. The server-side “drain and mark ready” logic is not mirrored in xprtsock in this series; if a server starts sending KeyUpdate, the client’s existing -EAGAIN behavior is what remains.
  • Client maintainers have been asked for Acked-by on patches 6–8 and have not replied in-window.

Net of the two files: svcsock.c 108 lines changed, xprtsock.c 69 lines changed. Base commit 0b6d2c7e3abca8d17fddeecb6e4c32a8438ec2fb. Change-id 20260805-svcsock-cmsg-fixes-9165f6cbb8de is shared with v1.

Status at week close

Posted as v2, not reviewed, not merged. No Acked-by, no Reviewed-by, no nits on this thread. Consensus in-window is Lever’s alone: these are latent, backport-shaped bug fixes found while walking away from read_sock_rectype; v2 only reorders the length check ahead of the severity change it guards and softens the XPT_DATA comment. The NFS client half still needs an ack before it can land. A v3 of the same subject appears as a later thread and is out of this week’s window.
