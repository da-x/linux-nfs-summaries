nfs-utils 2.9.2: --disable-nfsdctl breaks exportfs link

Overview

This is a bug fix / build-regression report, not a new feature or protocol change. On 1 August, Gentoo developer Lars Wendler reported that nfs-utils 2.9.2 fails to link exportfs when configured with --disable-nfsdctl. The only in-window message in this thread is that report. There is no maintainer reply, Ack, or patch on this thread before the 6 August week close.

The failure is in userspace nfs-utils, not the kernel NFS client. It still matters for client-facing deployments: exportfs is the tool that publishes and withdraws NFS exports, and the 2.9.2 netlink path is how it is supposed to talk to nfsd without the older upcall machinery. Distros that ship a slim nfs-utils (no nfsdctl binary, no GSS, no LDAP) cannot even build 2.9.2 as released.

The report

Wendler was packaging 2.9.2 for Gentoo with a long, typical distro configure line: --disable-static, TIRPC, systemd units, --enable-caps, IPv6, NFSv4 server, blkmapd / nfsdcld / nfsdcltrack, and --disable-nfsdctl. GSS, svcgss, LDAP, junction, krb5, and tcp-wrappers were all off.

The link of utils/exportfs dies here:

"exportfs.c:(.text+0xfbe): undefined reference to nfsd_nl_cmd_str"

The undefined symbol is referenced from unexportfs_parsed in exportfs-exportfs.o. The rest of the link line is otherwise ordinary: libexport.a, libnfs.a, libmisc.a, libreexport.a, libuuid, pthread, and libnl-3 / libnl-genl-3. So netlink libraries are already on the link line; the missing piece is a helper that should have come from libnfs.

Wendler's workaround is blunt:

"Switching --disable-nfsdctl to --enable-nfsdctl in the above set of configure flags makes the build succeed."

That is the entire thread. No patch, no "please file a bug", no "this is expected". The 2.9.2 tarball, as released, does not build with a configure switch that nfs-utils itself documents.

What the linker is telling us

nfsd_nl_cmd_str is the string helper for nfsd generic-netlink commands. It lives in nfsdnl.c, which 2.9.2 added so exportfs / exportd / mountd can drive nfsd over netlink (unlock-export / unexport) instead of the older channels. unexportfs_parsed is the path that tears an export down; that path now wants the netlink command name even when the operator asked not to build nfsdctl.

Two configure knobs have been allowed to drift apart:

  • --enable/--disable-nfsdctl (default yes) gates CONFIG_NFSDCTL in support/nfs/Makefile.am, and that conditional is what actually compiles nfsdnl.c into libnfs.
  • HAVE_NFSD_NETLINK is the preprocessor gate in exportfs.c. configure.ac defines it unconditionally once the nfsd netlink headers are present, independent of --disable-nfsdctl.

Result: exportfs.c always compiles the netlink unexport path, but libnfs only provides nfsd_nl_cmd_str when nfsdctl is enabled. Default ./configure && make hides the bug. Any distro that turns nfsdctl off — Gentoo in Wendler's case — hits the undefined reference.

The link line already pulls in libnl, so this is not "you forgot a dependency". It is a feature-gate mismatch between the utility (nfsdctl) and the library helper that exportfs now unconditionally calls.

Same-week independent confirmation

Four days later, outside this thread, Jaipaul Cheernam filed the same 2.9.2 link failure with a minimal reproducer (./configure --disable-nfsdctl --disable-gss && make) and called it a regression from 2.9.1. That diagnosis matches Wendler's symptom exactly: exportfs.c:491: undefined reference to nfsd_nl_cmd_str. Cheernam's analysis is the technical root cause above; he also sketched two fixes (always compile nfsdnl.c into libnfs, or move HAVE_NFSD_NETLINK under --enable-nfsdctl) and asked which the maintainers prefer. No answer landed on either thread this week.

Why it matters for NFS userspace

2.9.2 is the first nfs-utils release in which exportfs is wired to nfsd generic netlink. That is the userspace half of the exportfs/exportd/mountd netlink up/downcall work from earlier in the year. The utility flag --disable-nfsdctl was left meaning "do not build the nfsdctl binary", but the new netlink helper was hung off that same conditional while exportfs was compiled as if netlink were always there.

For NFS client machines that still build nfs-utils (to get mount.nfs, nfsidmap, etc.) and for servers that do not want nfsdctl, 2.9.2 is a hard stop. Wendler's Gentoo flags are not exotic: --enable-nfsv4server plus --disable-nfsdctl is a perfectly reasonable "NFSv4 server, no extra ctl tool" build. The fact that flipping one switch makes the link succeed is the giveaway that the C sources are fine and the automake/configure split is not.

Final status (this week)

  • Type: Build-regression bug in nfs-utils 2.9.2 (exportfs / nfsdnl.c / --disable-nfsdctl)
  • This week's activity on this thread: one report from Lars Wendler; no replies
  • Symptom: undefined reference to nfsd_nl_cmd_str from unexportfs_parsed when linking exportfs
  • Workaround stated by the reporter: configure with --enable-nfsdctl
  • Outstanding at week close: no maintainer Ack, no agreed fix, no 2.9.3 / stable patch on this thread. A parallel report later in the week independently confirmed the regression and proposed two gating fixes; that discussion is also unanswered in-window.
