NFS client: Trond flags dentry refcount underflow in ENXIO-on-symlink O_CREAT fix

NFS client: Trond flags dentry refcount underflow in ENXIO-on-symlink O_CREAT fix

Overview

After nearly two months of silence, Linux NFS client maintainer Trond Myklebust finally reviewed Michael Nemanov's NFSv3 atomic_open bug-fix this week — and immediately found a refcount landmine in the proposed patch. This is a bug fix (not a new feature or protocol change) targeting fs/nfs/dir.c: open(2) with O_CREAT on an existing symlink over NFSv3, with a cold dentry cache, currently returns ENXIO instead of following the link.

The only in-window message is Trond's August 5 review, which does not nack the approach but requires a one-line correction before the patch can land.

Bridge from prior weeks

Nemanov (Vast Data) posted the original patch on June 14 and nudged it on June 30 with a terse "Trying again". The diagnosis, in brief: NFSv3 CREATE UNCHECKED (RFC 1813 §3.3.8) returns NFS3_OK plus the existing object's file handle when the name is already a non-regular file, so nfs_do_create() succeeds and the client unconditionally calls finish_open(). Symlink inodes carry &no_open_fops, whose no_open() returns -ENXIO. A warm dcache masks the bug because lookup_open() then skips atomic_open entirely. The proposed 7-line fix in nfs_atomic_open_v23() checks !S_ISREG() after create and routes non-regular objects through finish_no_open() so the VFS can follow the symlink. The patch carries Fixes: 7c6c5249f061 ("NFS: add atomic_open for NFSv3 to handle O_TRUNC correctly.").

This week's review: a refcount underflow

Trond Myklebust replied directly to the June 14 submission, quoting the new finish_no_open() call site:

+				return finish_no_open(file, dentry);

and delivering a two-sentence verdict:

"This will cause the dentry to underflow the refcount. It needs to be finish_no_open(file, NULL)."

That is the entire technical substance of this week's activity, and it is the kind of VFS-contract detail that only a client maintainer is likely to catch on first reading. In the atomic_open path, finish_no_open(file, dentry) consumes a dentry reference; here the dentry is already held by the caller after nfs_do_create() succeeded, so passing it in would drop one reference too many. Passing NULL tells the VFS "do not consume this dentry; leave symlink follow-up to the normal open path" without touching the refcount.

Trond did not dispute the diagnosis, the !S_ISREG() defensive type check, or the Fixes: tag. The review is a surgical correction to the helper arguments, not a redesign. No v2 appeared in this week's window, so the patch remains unmerged pending that one-line change.

Significance for NFS client development

This is a textbook illustration of how fragile the NFSv3 atomic_open path remains. The original regression was introduced specifically to handle O_TRUNC correctly on CREATE; the ENXIO-on-symlink case is a sibling edge condition of the same CREATE-UNCHECKED / VFS-file-type mismatch. Nemanov's approach — treat any non-regular type as "do not finish_open, let the VFS continue" — is the right shape of fix. Trond's comment shows why the exit helper matters as much as the type check: finish_open() vs finish_no_open(), and dentry vs NULL, are the difference between a correct open and a use-after-free-class dentry underflow.

The long latency (June 14 submission, June 30 ping, August 5 review) also underscores a recurring linux-nfs pattern: small, well-scoped client fixes can sit unreviewed for weeks, then get a precise, blocking comment in a handful of lines.

Final status

  • Type: Bug fix (NFSv3 client, nfs_atomic_open_v23() in fs/nfs/dir.c)
  • This week's activity: Maintainer review; one required change identified
  • Required fix: finish_no_open(file, dentry) → finish_no_open(file, NULL)
  • Outstanding: v2 from Nemanov; no merge, no Acked-by, no further discussion in-window
