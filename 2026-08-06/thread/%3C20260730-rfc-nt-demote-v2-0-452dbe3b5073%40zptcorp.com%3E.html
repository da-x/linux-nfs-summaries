RFC v2 NT demotion: copy path and migrate_mode still under fire

Summary

This is still a new-feature RFC for the memory-management demotion path — not an NFS protocol change and not a client bug fix. The only NFS client footprint remains the mechanical MIGRATE_ASYNC helper swap in fs/nfs/write.c from last week's patch 2/3.

Brief recap from last week

Yiannis Nikolakopoulos (with Alirad Malek) posted RFC v2 of "Demote to lower tier using non-temporal stores." The idea is that demoted pages are already cold, so a normal memcpy pollutes the local last-level cache. Reviewers immediately rejected the extra MIGRATE_ASYNC_NON_TEMPORAL_STORES mode: Gregory Price, Frank van der Linden, and Johannes Weiner argued that migrate reason (for example MR_DEMOTION) is a stronger signal than a second ASYNC flag. The authors had not yet answered that critique when the previous week closed.

This week: the _nt helpers fail their own contract

The first in-window reply finally inspects the copy implementation that last week's reviewers skipped. Huan Nguyen — the same reviewer the cover letter said had ideas for v3 — writes that copy_mc_to_kernel_nt() "asserts both 'mc' (machine check exception) and 'nt' (non-temporal store)" but "the implementation fails to deliver both":

"1. copy_mc_fragile() is MCE-safe, but it does not use movnti. 2. memcpy_flushcache() uses movnti, but it is not MCE-safe."

That is a correctness complaint, not a style nit. The Intel WC protocol for movnti is weakly ordered, so a fence is required. Because memcpy_flushcache() has no sfence, Nguyen warns it "can result in reading stale or corrupted data after folio_unlock()."

He also argues the page-migration path is using the wrong primitive. copy_mc_highpage() (and therefore the new copy_mc_highpage_nt()) reuses copy_mc_to_kernel(), which is built for variable-length, unaligned copies. Ordinary copy_highpage() instead uses copy_page(), which is dedicated to 4 KiB-aligned migration. His proposed direction:

"Therefore, copy_mc_highpage_nt() should call a dedicated page-copy assembly routine that provides MCE safety, movnti stores, and an sfence, rather than the generic copy_mc_to_kernel_nt(). We can name it copy_mc_page_nt(), following the naming convention of copy_page()."

No one has answered him in-window. The machine-check versus NT-store tension that the cover letter already listed as an open is now a concrete design request: a dedicated, fenced, MCE-safe page-copy routine rather than a wrapper around two existing helpers that each only do half the job.

This week: another vote against a new migrate mode

Five days later, Huang, Ying reviewed patch 2/3 — the patch that adds MIGRATE_ASYNC_NON_TEMPORAL_STORES and rewrites every MIGRATE_ASYNC check, including the one in NFS writeback. His comment is short and points in the same direction as last week's reason-versus-mode debate:

"Is it better to turn migrate_mode parameter into migrate_flags?"

That is not an endorsement of a third async enum value. It is a suggestion to stop growing enum migrate_mode and treat the NT/async knobs as flags — which would also make the "either async mode" helper in fs/nfs/write.c unnecessary if NT is no longer a distinct mode.

NFS client angle

Nothing this week touches NFS client code, writeback behavior, or the protocol. The only client-relevant line is still the helper that treats both async modes as non-blocking in fs/nfs/write.c. If v3 follows last week's "use reason" consensus or Huang's migrate_flags idea, that one-line change is likely to shrink or vanish.

Bottom line

The series remains an MM demotion feature RFC under active review, not a bug-fix landing. This week's two comments deepen last week's design objections rather than resolving them: Nguyen says the _nt copy path is neither MCE-safe nor correctly fenced and wants a dedicated copy_mc_page_nt(); Huang wants migrate_mode turned into flags instead of another async enum. The authors have not replied to either note, nor to last week's reason-versus-mode critique. Until a v3 appears, there is no NFS client development and no NFS bug fix in this thread.
