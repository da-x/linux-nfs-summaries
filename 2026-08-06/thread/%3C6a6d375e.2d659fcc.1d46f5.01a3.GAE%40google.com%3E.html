syzbot hung-task in write_ports: nfsd_mutex pile-up during nfsd unmount

Summary

syzbot hung-task in write_ports: nfsd_mutex pile-up during nfsd unmount

Type: Bug report (kernel fuzzer finding — hung task / lock contention). Not a protocol change and not an NFS client patch; the stack is entirely in the NFSD control plane (fs/nfsd/nfsctl.c).

On 1 August, syzbot filed a hung-task report against upstream Linux 7.2-rc5 (f5098b6bae76), tagged [nfs?]. Unlike several sibling NFSD hung-task reports this week, this one ships both a syz reproducer and a C reproducer. No human reply, diagnosis, or patch landed in the window.

syzbot's boilerplate is the usual:

"syzbot found the following issue on: HEAD commit: f5098b6bae76 Linux 7.2-rc5"

and, for a later fix:

"IMPORTANT: if you fix the issue, please add the following tag to the commit: Reported-by: syzbot+0f7085f07e9cfba423cd@syzkaller.appspotmail.com"

What hung

Five (and, in the lock dump, dozens more) syzkaller workers sat in uninterruptible sleep (state:D) for more than 143 seconds, all on the same path:

__mutex_lock
  write_ports+0xb5/0xd10 fs/nfsd/nfsctl.c:860
    nfsctl_transaction_write+0x10f/0x160 fs/nfsd/nfsctl.c:112
      vfs_write / ksys_write

write_ports() is the /proc/fs/nfsd/portlist transaction write: userspace (rpc.nfsd / nfsdctl) adding or removing NFS listener sockets. It takes the global nfsd_mutex before touching the per-netns service. Every hung worker already held sb_writers#12 from vfs_write() and then blocked on that mutex.

The lock holder: unmount vs. portlist

The interesting line is not the waiters. It is the holder:

2 locks held by syz-executor/5763:
 #0: (&type->s_umount_key#54) at deactivate_super
 #1: (nfsd_mutex) at nfsd_shutdown_threads+0x4e/0xd0 fs/nfsd/nfssvc.c:576

One executor is tearing down the nfsd control filesystem (nfsd_umount → nfsd_shutdown_threads) while holding the superblock's exclusive s_umount lock and nfsd_mutex. Everyone else is trying to write portlist while holding sb_writers and waiting for the same mutex.

That is a classic NFSD control-plane pile-up, not a network-protocol stall:

  • Unmount path: s_umount → nfsd_mutex
  • Portlist path: sb_writers (from file_start_write in vfs_write) → nfsd_mutex

Once shutdown owns the mutex, every concurrent write_ports (and, as a same-day sibling report shows, write_threads) queues behind it. The lock listing in this dump is extreme: more than forty syz workers each hold sb_writers#12 plus nfsd_mutex wait, all at write_ports+0xb5. khungtaskd then fires NMI backtraces; CPU 0 is idle in pv_native_safe_halt, so this is a sleeping hang, not a CPU soft lockup.

The hung-task banner itself is the usual:

"INFO: task syz.0.17:6054 blocked for more than 143 seconds. Not tainted syzkaller #0"

Client impact (even though the bug is server-side)

This is not an NFS client bug. write_ports / nfsctl_transaction_write live in the in-kernel NFS server. The client-visible fallout is still real:

  • portlist is how the server binds NFS/NLM listeners. A hung write_ports means rpc.nfsd cannot add or drop sockets, so clients cannot mount or reconnect while the control fs is wedged.
  • The mutex owner is nfsd_shutdown_threads. If that path never finishes, the server never comes back up; every connected client loses the export.
  • The waiters also pin sb_writers on the nfsd control superblock, so further writes (threads, versions, exports) serialize behind the same bottleneck.

For client developers, there is nothing to change in fs/nfs/ this week. The actionable work is on the nfsd side: nfsd_mutex remaining a global serialization point for unmount, listener configuration, and (in related reports) netlink thread/version ioctls.

Same-day sibling: write_threads

Thirty-four minutes later syzbot posted a closely related hang, [syzbot] [nfs?] INFO: task hung in write_threads (<6a6d3f57.6ce73036.24301b.0010.GAE@google.com>), against a slightly newer HEAD (3708dd948844). That dump has no reproducer, but the lock picture is the same family: one task in write_ports already holding nfsd_mutex, another blocked in write_threads waiting for it. Together they show the procfs transaction writers (portlist and threads) sharing one mutex with teardown.

Continuity with earlier hung-task reports

This is not a new class of bug. In January, syzbot reported a hang in expkey_flush with the same three-way contention on nfsd_mutex: export-cache flush (holding sb_writers), nfsd_shutdown_threads during unmount (holding s_umount), and nfsd_nl_threads_set_doit from netlink. That earlier dump already called out nfsd_umount → nfsd_shutdown_threads as Path 2. This week's write_ports report is the same teardown-versus-admin-write pattern, now hitting the listener-configuration entry point and arriving with a C reproducer.

Later in the same week, additional [nfs?] hung-task reports landed on the netlink side (nfsd_nl_threads_get_doit, nfsd_nl_version_get_doit). Those are out of this thread's window, but they reinforce that nfsd_mutex is still the single choke point for both procfs and genetlink control.
