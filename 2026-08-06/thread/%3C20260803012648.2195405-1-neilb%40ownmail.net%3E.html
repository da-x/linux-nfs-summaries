NeilBrown RFC: easy VFS fixes for negative-dentry overflow and lockups

Summary

NeilBrown posted a 12-patch RFC/RFT this week that tries to sand down the “easy bits” of the long-running negative-dentry problem, rather than redesign how the VFS stores or reclaims those dentries. The series is a bug-fix / VFS-hardening effort, not a protocol change and not a new NFS feature. It is aimed at v7.2-rc6 and lives on the vfs-neg-dentries branch of Brown’s GitHub tree (top commit 56768a600dd9).

There were no replies in the week ending 2026-08-06. The discussion this week is therefore the series itself: a carefully staged refactor that Brown wants reviewed and, more importantly, run against workloads that already trigger soft lockups.

What Brown is not trying to fix

Brown is explicit that he is treating symptoms, not the underlying cache-size problem. After reading the LWN write-up of the negative-dentry mess, he decided against shrinking the negative-dentry population or treating negatives differently from positives:

"So I didn't try to reduce the number of negative dentries or handle them differently to positive dentries. I just tried to address specific symptoms."

He also left d_walk() alone, calling the series “big enough for now.” Most of d_walk() already schedules; leftover cases can wait.

Two reported symptoms

The cover letter names the two bugs the series actually attacks.

1. Parent d_lockref overflow. A directory can accumulate an effectively unbounded number of negative children. Each child historically held a counted reference through ->d_parent, so a parent with billions of negatives can wrap ->d_lockref.count. Patch 01 is the entire fix for that:

"The number of negative child dentries that a given dentry can have is effectively unbounded, so counting the references through ->d_parent can overflow ->d_lockref.count."

The new accounting is “list nonempty,” not “one ref per child.” The parent is dget()’d when ->d_children becomes nonempty and dput()’d when it becomes empty. Inactive DCACHE_DENTRY_CURSOR children are not on that list, but they already exist only in contexts that hold a separate parent reference. __d_move() is careful around IS_ROOT() dentries that are not on any d_children list: it dget()s a parent with an empty list before shuffling children, then dput()s if the list is still empty afterwards. A new dput_dlock() helper warns instead of decrementing to zero, which “should never happen.”

Brown calls this “the easiest easy bit.”

2. Soft lockups walking ->d_children. The harder half is unbounded walks of the sibling list, especially in fsnotify_set_children_dentry_flags(). Brown does not bound the walk:

"I haven't addresses the "arbitrarily long" part, but the "soft lockups" only takes another 11 patches. With these in place I would feel more confident addressing the "arbitrarily long" part."

The strategy is a common iterator that can drop the parent lock, insert a cursor, and cond_resched(). That idea only works if three preconditions hold: nothing else is held across the walk, dentries are not needlessly reshuffled on the sibling list, and the libfs readdir helpers are refactored to share the same iterator.

The common iterator, and the NFS client change

Patch 02 is the NFS-facing change. It introduces d_for_each_positive_child() / d_for_each_positive_child_continue() in include/linux/dcache.h and converts every out-of-dcache, out-of-libfs walker to those macros. The iterators report only positive children (cursors are never positive, so they are skipped). scoped_guard() makes break/goto drop the parent lock.

Callers converted in this patch: autofs expire, Ceph MDS client, Coda cache, libfs, NFS fs/nfs/dir.c, and fsnotify.

The NFS client tweak is in nfs_clear_verifier_directory(). The parent lock is now dropped and retaken between nfs_unset_verifier_delegated() on the parent and the same call on every child. Brown flags this twice — once in the cover letter, once in the patch — and both times he thinks it is harmless:

"NFS: patch 02 drops the parent lock between calling nfs_unset_verifier_delegated() on the parent and calling it on all the children. I don't think this is significant."

and, in the patch itself:

"nfs_clear_verifier_directory() is changed slightly so the parent lock is dropped and retaken between clearing the verifier on the parent and on all the children. I think this is safe."

That is the only NFS-client functional change in the series. It matters for directory-delegated verifier invalidation: a concurrent lookup or readdir could theoretically observe a parent whose delegated verifier has already been cleared while some children still have theirs. Brown is asking NFS reviewers to confirm that window is acceptable. Ceph is described as “nothing interesting”; Coda merely loses a redundant rcu_read_lock() because the spinlock already implies RCU protection.

Making the walk sleepable

The remaining ten patches exist so that the new iterator is allowed to schedule.

fsnotify (patches 03–04). Brown is least confident here. Patch 03 stops dnotify_recalc_inode_mask() from calling fsnotify_recalc_mask() under a spinlock; the function now returns a “please recalc” flag and callers invoke fsnotify_recalc_mask() after dropping the lock. dnotify_handle_event() is also reduced to a single recalc per loop. After that, the only spinlocks still held across a d_children walk are i_lock and d_lock. Patch 04 then dget()s the dentry and drops i_lock before fsnotify_set_children_dentry_flags() walks children. That dput() can sleep, which is now legal because no lock is held across the call.

libfs readdir (patches 05–08, 12). scan_positives() is rewritten to talk in struct dentry * rather than raw hlist_node pointers (05), then switched onto d_for_each_positive_child_continue() (06), then allowed to run without a cursor (07). Patch 08 deletes find_positive_dentry() and uses scan_positives() for offset-directory lookup. That needs a new lockref_get_not_dead_nested() so a child ref can be taken opportunistically while the parent lock is held, and it must step over dead/cursor dentries under parent->d_lock because cursors are not RCU-safe. Brown claims identical behaviour for the offset-dir code, just a cleaner RCU/scan split.

autofs (patch 09). Patch 09 drops ->lookup_lock from get_next_positive_subdir() and get_next_positive_dentry(). That lock only protects sbi->expiring and sbi->active_list, neither of which these walkers touch. Holding it would block the later cond_resched().

Don’t reshuffle same-parent siblings (patch 10). Patch 10 stops __d_move() from moving both dentries to the head of ->d_children when they already share a parent. That move “achieves nothing” today, but once the iterator can drop d_lock, a same-directory rename could bounce a still-present child to the front of the list and cause the walk to miss it. After this change, the only misses are dentries moved out of the directory or inserted after the walk started — “unavoidable and should not be unexpected.”

The actual cond_resched() (patches 11–12). Patch 11 is the payload. d_for_each_positive_child*() now calls d_next_sibling_sched() and is annotated might_sleep(). The cursor is an on-stack dentry (~330 bytes), which Brown admits is unusual. He argues it is safe because commit 3df5153c5f12 (“make cursors NORCU”) already established that cursors can be released without waiting, and “nothing ever takes a reference on a cursor that it doesn't own.” A new __d_init() is split out of __d_alloc() so d_init_cursor() can initialise that stack object. d_walk() is still not converted; some of its callers abort on need-resched and some do not. Patch 12 then deletes the now-redundant cond_resched() from scan_positives().

Review asks, especially for NFS testers

Brown expects he has missed call sites and lock constraints:

"so I have probably missed some bits and would be very happy to be told what I have missed."

He particularly wants:

  • confirmation that the on-stack dcache cursor logic in patch 11 is sound (“this is not something that other code does”);
  • a second look at the fsnotify lock surgery, “non-trivial code that I'm not familiar with”;
  • and, for NFS, a verdict on the dropped parent lock around nfs_unset_verifier_delegated().

He has only run “basic testing including the ‘notify’ parts of ltp.” The real request is for anyone who can already trigger the soft lockups to try the series and report that the lockups are gone and that nothing else broke.

Status this week

This is a new VFS bug-fix RFC that happens to touch the NFS client’s directory-verifier path. It does not change the NFS protocol, does not add client features, and does not attempt the harder negative-dentry reclamation work. As of 2026-08-06 there is no review, no Tested-by, and no conclusion from the list — only Brown’s own claim that patch 01 stops the refcount overflow and that patches 02–12 make every common d_children walk able to schedule. The next step he wants is exactly that testing, plus a close reading of the NFS verifier window and the on-stack cursor.
