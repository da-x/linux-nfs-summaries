netfs v8: bvecq buffer tracking and NFS fscache issue_read rework

Summary

David Howells posted [PATCH v8 00/25] of the long-running netfslib buffer-tracking overhaul on 4 August, asking Christian Brauner to take the series into the VFS tree for the next merge window. There were no in-week replies: the thread is a 25-patch drop plus cover letter, rebased on v7.2-rc6, with earlier Sashiko-reported bugs and NFS-specific issue_read fixes folded in rather than discussed again.

This is an infrastructure rewrite, not a protocol change. It retires folio_queue, rolling_buffer and ITER_FOLIOQ in favour of a segmented bio_vec[] chain (bvecq + ITER_BVECQ) so buffered I/O, unbuffered/DIO and cache I/O share one buffer representation. Howells framed three aims in the cover letter:

"The kernel file I/O subsystem seems to be moving towards consolidating on the use of bio_vec arrays, so embrace this by moving netfslib to keep track of its buffers for buffered I/O in bio_vec[] form."

"Always send an entire filesystem RPC request message to a TCP socket with single kernel_sendmsg() call as this is faster, more efficient and doesn't require the use of corking as it puts the entire transmission loop inside of a single tcp_sendmsg()."

For NFS client developers the practical consequence is that fscache-backed reads now go through the merged prepare/issue path, with nfs_netfs_issue_read() required to return an error, slice a bvecq buffer, and terminate a subrequest exactly once.

Why bvecq, and what it looks like

Patch 05/25 introduces struct bvecq: a NULL-terminated, refcounted list of bio_vec[] segments. Each segment records file position (fpos), slot occupancy, memory-disposal type (BVECQ_MEM_PAGECACHE / GUP / ALLOCED / EXTERNAL), and a discontig flag so adjacent segments need not be contiguous. Howells is explicit that this is for sparse RPCs:

"When the file position is relevant, the model I'm working with is that all the segments pointed to by a single bvecq must represent contiguous data, but adjacent bvecqs within a chain need not be contiguous. This allows a bvecq chain to be used to provide bufferage for a sparse read or write RPC such as can be done with Ceph."

He also added ITER_BVECQ so the same construct can be handed to sendmsg() or block DIO (cachefiles). Follow-on patches supply kmap of a multipage bio_vec (03/25), wrap iov_iter_get_pages*() around iov_iter_extract_pages() (04/25), add chain helpers and a mempool (06–07/25), and extract any iov_iter into a labelled bvecq (08/25). Writeback uses the mempool because writeback_iter() cannot fail with -ENOMEM under WB_SYNC_ALL.

Patch 16/25 is the actual switch. Buffer tracking is three cursors on netfs_io_request (load_cursor, dispatch_cursor, collect_cursor) plus per-subrequest dispatch_pos/content. Buffered writeback keeps a dispatch cursor per stream (server vs cache). Unbuffered/DIO extracts the source iterator up front; buffered I/O adds folios as it goes, but only the dirty portion of a folio is queued for the server, with cache writes getting a rounded-up duplicate for DIO alignment.

AFS directories and CIFS crypto bounce buffers move off folioq in 09–10/25; smbdirect gains ITER_BVECQ mapping and drops ITER_FOLIOQ (11/25, 17/25). Cleanup then removes netfs_alloc/free_folioq_buffer(), netfs_extract_user_iter(), ITER_FOLIOQ, and the folio-queue/rolling-buffer code itself (18–21/25).

NFS client: issue_read contract and fscache

NFS is a netfslib consumer via fs/nfs/fscache.c. The client-visible API change lands in 24/25, which also touches fs/nfs/Kconfig. Prepare, buffer setup and issue are collapsed: netfs presents a maximum-extent subrequest; the filesystem (or cache) shortens it, calls back to slice the master bvecq, and dispatches. iov_iter is pushed down into the filesystem; netfs hands out a bvecq that can later grow protocol headers/trailers or be compounded.

Howells summarised the writeback motivation:

"The issue, primarily, is in writeback: the code has to create multiple streams of write requests to disparate targets with different properties (e.g. server and fscache), where not every folio needs to go to every target"

and the new dispatch loop:

"netfslib now builds up an accumulation of buffered data before issuing writes on each stream (one server, one cache). It asks each stream for an estimate of how much data to accumulate before it next generates subrequests on the stream."

For reads, the entire VM readahead folio set is loaded into a bvecq in one xarray walk (01–02/25); cache occupancy is queried two extents at a time, and each ->issue_read() is given the current extent to slice. -ENOMEM from ->issue_xxx() aborts further subrequest generation; other early errors fail the enlarged subrequest.

That is exactly the NFS path that previous versions got wrong. The v8 changelog records three NFS-specific fixes already merged into this posting (no new NFS patch this week):

  • nfs_netfs_issue_read() now returns int (v7).
  • alloc failure sets -ENOMEM, not 0 (v4).
  • the subrequest is terminated only once (v4).

Those matter because the new issue loop will spin if ->issue_read() fails without consuming buffer, and a double terminate is now a use-after-free risk on the subrequest. Anyone carrying out-of-tree NFS netfs glue needs the same contract: return an error, slice once, terminate once.

Bug fixes that affect NFS I/O and cache

Several netfs correctness patches in this series are client-visible even without NFS-local diffs.

Over-read is now fatal. 22/25 aborts the rest of a buffered read with -EIO if a subrequest transfers more than requested, on the theory the buffer may already be corrupted. Collection no longer winds subreq->transferred back. Combined with v7's "abandon the rest of a read if a subreq over-reads" change, an NFS server that overshoots a READ will fail the whole netfs request rather than retry into a smashed buffer.

Progress wakeups are rate-limited. 23/25 stops the collector being kicked for every 4K folio on a large RPC. The trigger is now max(256KiB, size of the folio at the front of the queue), and the base is the stream collection point rather than "cleaned up to 0". That is aimed at "really big read RPC ops that span multiple folios" — the NFS READ path when rsize is large.

Writethrough is gone. 12/25 deletes the netfs writethrough path:

"Remove the netfs writethrough code as it's very tricky to get the locking right and it will probably deadlock if used in conjunction with Ceph snapshots because it excludes writeback for the duration, but to flush out old snapshots, it does a synchronous flush that invokes writeback."

O_SYNC now relies on the existing generic_write_sync() after netfs_perform_write(). NFS was not the deadlock poster child, but any NFS netfs buffered write that assumed in-band writethrough no longer has that option.

v8 Sashiko fallout still in the cover letter. Howells lists a pile of loop/ENOMEM/cursor bugs fixed since v7 that sit on the shared retry/collect paths NFS uses: bvecq_alloc_buffer2() breakout when pre_slots > 0 && size == 0; netfs_extract_iter() capping max_pages for iov_iter_npages(); missing ENOMEM check in netfs_pgpriv2_begin_copy_to_cache(); netfs_retry_read_subrequests() unsetting dispatch_cursor on the abandon_after path; netfs_issue_write() clearing stream->construct on ENOMEM; netfs_collect_read_results() unpausing the app when a read is abandoned; netfs_retry_write_stream() handling superfluous subreqs the way read retry does. Cachefiles no longer waits for FSCACHE_WANT_READ in cachefiles_issue_read() because query_occupancy() already did.

Cachefiles: occupancy, ALL-type objects, ENOSPC

NFS fscache users also inherit the cachefiles rewrite.

13/25 (Gao Xiang) sunsets on-demand mode — EROFS-over-fscache is gone, so fs/cachefiles/ondemand.c and include/uapi/linux/cachefiles.h go with it.

14/25 stops using SEEK_DATA/SEEK_HOLE on the common path. Progressive open(O_TRUNC); write…; close() files are tagged CACHEFILES_CONTENT_ALL; backing i_size tracks stored data (DIO-aligned) and the netfs size lives in the xattr. Howells' complaint about the old scheme:

"this means it does two seek operations on the backing file for each individual read call it wants to prepare … Worse, the backing filesystem is at liberty to insert or remove blocks of zeros in order to optimise its layout which may cause false positives and false negatives."

Netfs now allocates an fscache_occupancy and calls ->query_occupancy() for the next two extents (FSCACHE_EXTENT_DATA or ZERO). ->prepare_read() only limits size. Completed contiguous cache writes are collated into a new ->collect_write(). Sparse files still use SEEK_DATA/HOLE; Howells flags that as "needs to be fixed, but in a separate set of patches as it's not trivial."

25/25 presets the state xattr on tmpfile create so a full cache object is not later discarded because setxattr hit ENOSPC. v8 also teaches cachefiles_collect_write() to tolerate cres->cache_priv2 being NULL when object create failed (ENOSPC). A cachefiles_no_space tracepoint logs those events. 15/25 puts the cache object debug ID on netfs read/write tracepoints so NFS cache traces can be joined to cachefiles traces.

Future work Howells is already running locally

Not in this branch, but called out as CIFS prototypes that NFS will care about if they land:

  1. Give the filesystem a copy of a subchain so it can tack RPC header/trailer and even join copies into compounds — "I have this working for cifs".
  2. Splice the TCP receive queue into a bvecq so the socket lock can drop before copy-out — again working for CIFS. "Kernel recvmsg() doesn't then block kernel sendmsg() for anywhere near as long."

Longer-term ideas: batched folio unlock over a bio_vec[], walking i_pages by fpos instead of bv_page, making iov_iter_revert() reset to a stored start (which would drop bvecq->prev), and eventually replacing scatterlists so crypto can glue headers the way it does today.

Status this week

v8 is a rebase-and-fix posting: fix patches were split to their own branches, the series sits on v7.2-rc6, and Howells asked for VFS-tree inclusion. Paulo Alcantara has Reviewed-by/Acked-by on several early iov_iter/bvecq patches; Stefan Metzmacher acked the smbdirect ITER_BVECQ work. There is no Acked-by from the NFS maintainers on this revision, and no review traffic in the 31 July–6 August window. The git branch is netfs-next in linux-fs.git.

For NFS client development the actionable items are: (1) nfs_netfs_issue_read() must match the new int-returning, single-terminate, bvecq-slicing issue op; (2) over-read from the server is now -EIO for the whole netfs request; (3) fscache occupancy and ALL-type cachefiles behaviour change how NFS cached reads are sourced and how ENOSPC during cache create is handled.
