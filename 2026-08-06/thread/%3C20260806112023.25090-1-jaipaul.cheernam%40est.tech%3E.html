getport: add missing stddef.h for musl offsetof

Summary

Summary

This week’s linux-nfs traffic includes a one-line userspace build fix for nfs-utils: Jaipaul Cheernam posted [PATCH] getport: fix missing stddef.h inclusion so support/nfs/getport.c compiles against musl. There are no replies in the window. It is a bug fix, not a protocol change and not an in-kernel NFS client patch.

The change sits in the same support/nfs/ library that the client-side mount helpers use to resolve RPC ports. A musl-based client image that cannot build getport.c cannot produce a working mount.nfs / portmapper path, so the operational impact is real even though the kernel client is untouched.

The failure

getport.c calls offsetof() but never includes <stddef.h>. That is invisible on glibc, where the macro arrives through some other header, and fatal on musl:

"getport.c uses offsetof() but does not include <stddef.h>. On glibc this works because offsetof is pulled in transitively, but on musl it is not available without the explicit include"

The compiler error is:

getport.c:459:41: error: implicit declaration of function 'offsetof'

That is a classic C89/C99 hygiene problem: offsetof is specified in <stddef.h>, and musl does not re-export it from the RPC or NFS headers the file already pulls in. Implicit-declaration treatment of a macro that should have been a compile-time constant is also a warning-as-error landmine on modern toolchains.

The patch itself is a single insertion:

support/nfs/getport.c | 1 +
 1 file changed, 1 insertion(+)

Cheernam’s commit message is the entire technical argument. No alternative approach is proposed, and none is needed: adding the canonical header is the correct fix, and it is libc-neutral.

Client-side context

getport.c is the nfs-utils helper that talks to rpcbind/portmap to locate NFS, NLM, and related services. Kernel NFS client development is not in play here — there is no fs/nfs change, no wire-protocol tweak, and no mount-option semantics change. What is in play is whether a musl-based distribution or embedded rootfs can build the userspace that the client still depends on for:

  • port discovery before MOUNT / NFS RPC
  • fallback when rpcbind is present but NFSv4-only assumptions do not apply
  • any tool that links libnfs and walks the same getport structures that use offsetof

The line number in the diagnostic (getport.c:459) is the offsetof use that musl rejects. Once <stddef.h> is present, that expression is a proper compile-time offset again.

Same-week company

This is Cheernam’s second nfs-utils build report of the week. The day before, he filed a separate exportfs link failure with --disable-nfsdctl against 2.9.2. That thread is a feature-gate mismatch (HAVE_NFSD_NETLINK vs CONFIG_NFSDCTL); this one is a missing standard header. They share an author and a theme — nfs-utils does not currently build cleanly on slim or non-glibc configurations — but they are independent defects.

No maintainer Acked-by, Reviewed-by, or merge notice appears in this thread. The patch is self-contained and should be a trivial apply for nfs-utils.

Status this week
