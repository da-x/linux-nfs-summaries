NFS client adds CB_NOTIFY for directory delegations

Summary

Overview

This week Anna Schumaker posted a four-patch new feature series that finally teaches the Linux NFS client how to consume CB_NOTIFY callbacks for directory delegations. The work is not a protocol change — CB_NOTIFY has been in NFSv4.1 since RFC 5661 / 8881 — and it is not a bug fix. It is the missing client half of the directory-delegation story: last November's client-side GET_DIR_DELEGATION series taught the client to request a directory lease and skip some lookup revalidation while it holds one; this week's patches teach it what to do when the server later says the directory changed.

There were no review replies in the window. The series landed as a design proposal with an explicit request for comments, and it sits next to the same week's nfsd CB_NOTIFY encoder debate (the sparse / host-endian XDR thread), which is keeping the server-side encoder in nfsd-next while promising a cleanup.

The design choice: refresh, don't rewrite the dcache

Schumaker's cover letter is the technical heart of the series. She does not try to keep the client's directory cookie order in lock-step with the server:

"These patches add support for the CB_NOTIFY callback operation from NFS servers. Editing directory order or placement in our caches isn't easy or practical the way things are structured now. Instead, I use CB_NOTIFY as an indication that the client needs to refresh its view of the directory."

That is a conservative client-engineering decision. A directory delegation is only useful if the client can trust its dcache and readdir cache; a naïve implementation would try to splice, reorder, or rewrite dentries in place as NOTIFY4_* events arrive. Schumaker argues that the current NFS client cache layout makes that kind of surgical edit impractical, so CB_NOTIFY is treated as a cache-invalidation / refresh signal rather than a full directory-journal replay.

She closed the cover with a one-word invitation — > "Thoughts?" — and left the series sitting for review.

The four patches touch only the client callback path and the NFSv4 XDR tables: fs/nfs/callback.h, fs/nfs/callback_proc.c, fs/nfs/callback_xdr.c, fs/nfs/nfs4_fs.h, fs/nfs/nfs4xdr.c, and include/linux/nfs4.h. The diffstat is compact — 400 insertions, 5 deletions — which matches a first-cut decoder plus three notification handlers rather than a rewrite of fs/nfs/dir.c.

Patch 1: a CB_NOTIFY skeleton

Patch 1 wires CB_NOTIFY into the client's callback operation table and XDR decoder without implementing any notification type. Schumaker's commit message is deliberately skeletal:

"Support for individual notification types will be added over the next few patches."

That outline is the right place for the protocol constants (include/linux/nfs4.h), the callback argument structs (fs/nfs/callback.h), a stub procedure in callback_proc.c, and the decode path in callback_xdr.c. Until the later patches land, an incoming CB_NOTIFY can be recognized and parsed far enough to be ignored or rejected cleanly rather than treated as an unknown callback.

Patch 2: REMOVE_ENTRY as a refresh hint

Patch 2 is the first real handler, and it follows the cover letter's "refresh, don't rewrite" rule almost verbatim:

"When the server tells us that a directory entry has been removed then we need to take that as an indication that our knowledge of the directory has changed and needs to be refreshed."

A CB_NOTIFY4_REMOVE_ENTRY is therefore not implemented as a precise d_delete() of one name. It is a signal that the client's picture of that directory is stale. That is the important client-side correctness property: after a remove notification, subsequent lookups and readdirs must not keep serving the old name. Treating the event as a directory-wide refresh is weaker than a surgical unlink, but it is also harder to get wrong — no cookie-order surgery, no risk of leaving a negative dentry that no longer matches the server.

Patch 3: ADD_ENTRY does instantiate a dentry

Patch 3 is the one place the series does reach into the dcache, and it is the patch that will need the closest review:

"When the server tells us that a directory entry has been created, we need to instantiate a new dentry and add it to the dcache on the client."

That is a stronger action than the cover letter's "refresh the view" slogan. An add notification carries enough information (name, filehandle / attributes, depending on what the decoder accepts) for the client to create a positive dentry immediately, so a subsequent lookup can hit without a round trip. It is also the operation most likely to interact badly with concurrent local creates, negative dentries, and the existing nfs_force_lookup_revalidate() machinery that directory delegations already shortcut.

This is the patch that adds the extra nfs4_fs.h helpers and the bulk of the XDR decode for notify entries (155 insertions across six files). If reviewers push back, this is where they will push: instantiating dentries from a callback context is a classic source of locking and lifetime bugs, and the client's earlier directory-delegation work already had a rough winter of verifier and state-recovery crashes.

Patch 4: RENAME_ENTRY as remove-plus-add

Patch 4 is the smallest of the four (38 insertions) because it refuses to invent a third code path:

"Renaming an entry essentially combines a remove with an add, allowing us to reuse most of the code from the previous patches to do the work for us."

That composition is faithful to the NFSv4 notify model — a rename is a remove of the old name plus an add of the new one, possibly across directories — and it keeps the client's policy consistent: the old name is treated as stale (refresh), the new name is instantiated. Cross-directory rename notifications will exercise both the remove-side refresh and the add-side dcache insert, which is exactly the combination a directory-delegation holder needs when another client (or the same client on another mount) rearranges a tree.

How this fits the existing client directory-delegation work

The November 2025 Client Side Directory Delegations series already:

  • sent GET_DIR_DELEGATION / GDD_GETATTR,
  • requested a directory lease on ACCESS, CREATE, UNLINK, and same-directory RENAME,
  • short-circuited lookup revalidation while a directory delegation is held,
  • and added a module option to turn the feature off.

What it did not do is react to server-initiated directory change notifications. Without CB_NOTIFY, a client that holds a directory delegation has only two choices when another client mutates the directory: wait for a recall, or discover the change the hard way when a verifier or getattr fails. That is why this week's series matters for client performance. A working CB_NOTIFY path is what lets the client keep the delegation across other clients' creates, unlinks, and renames, instead of bouncing the lease on every remote mutation.

The earlier client work also left scars that reviewers will remember. Directory-delegation verifier checks and state-recovery paths produced kernel Oopses over the 2025–2026 holiday window; Trond Myklebust at one point warned that another incident might mean disabling directory delegations on the client until the next release. This CB_NOTIFY decoder walks some of the same inode and dcache edges. The conservative "refresh the directory" policy in the cover letter and the REMOVE handler looks like a reaction to that history: prefer a correct cache drop over a clever in-place edit.

Relationship to this week's nfsd CB_NOTIFY work

The series is the client counterpart of the nfsd directory-delegation / CB_NOTIFY encoder that is already in nfsd-next. The same week, Jeff Layton and Chuck Lever argued over that encoder's host-endian scratch usage in the XDR stream. Lever was explicit that the on-the-wire behavior is not being reverted and that the encoder stays queued; Layton promised a follow-on cleanup, likely v7.4 material.

For this client series that pairing is the practical test plan. A Linux client running these four patches against nfsd-next is the first in-tree end-to-end GET_DIR_DELEGATION + CB_NOTIFY path. Reviewers will want to see:

  • that the client's decoder accepts the notify bitmaps and entry types nfsd actually sends (REMOVE_ENTRY, ADD_ENTRY, RENAME_ENTRY, and any attr / cookie-verifier notifications the server may still emit),
  • that a decode failure does not leave a directory delegation held with a silently stale dcache,
  • and that callback-context dentry instantiation in patch 3 does not deadlock against the local VFS create/unlink paths that already request directory delegations.

Status

  • Type: new NFS client feature (directory-delegation CB_NOTIFY support). Not a protocol change, not a bug-fix series.
  • Posted: 4 August 2026, four patches, ~400 lines, client callback / XDR only.
  • Review: none in this window. Schumaker asked for thoughts and the thread stopped there.
  • Open design question: the cover letter says "refresh the view"; patch 3 still instantiates dentries on add. That tension is the obvious review target.
  • Next step: review, and likely a v2 once someone has run the series against the nfsd-next CB_NOTIFY encoder.

No patches were merged from this thread this week. The client still cannot usefully hold a directory delegation across remote namespace changes until some version of this decoder lands.
