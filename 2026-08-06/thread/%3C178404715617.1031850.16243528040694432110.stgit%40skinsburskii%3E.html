NFS freezer RFC ping: Mesos can wedge mounts

Summary

Summary

NFS client freezer RFC still waiting on review

This week's only traffic on Stanislav Kinsburskii's mid-July RFC is a gentle ping — no maintainer replies, no v2, and no new code. The discussion remains a bug-fix-oriented RFC for how the NFS client (and other network filesystems) interact with the kernel freezer: TASK_FREEZABLE_UNSAFE sleeps must stay freezable for suspend/hibernation, but must not be parked by administrative freezer requests.

Brief recap of the July RFC

On 14 July, Kinsburskii proposed restricting TASK_FREEZABLE_UNSAFE freezing to PM (suspend/hibernation) only. Network filesystems use that state for sleeps that can occur while a task still holds locks or transport resources other tasks need. The original 2019–2020 helper (Brian Callaghan / Red Hat) solved the "don't block suspend, don't trip lockdep" problem, but it also made those same tasks fair game for any freezer invocation — including cgroup freezer / systemd admin operations. The RFC's three-file change (kernel/freezer.c, include/linux/sched.h, Documentation/power/freezing-of-tasks.rst) keeps the PM path and documents the new non-PM exemption.

This week's ping: why the stall is not theoretical

Three weeks later, with the list silent, Kinsburskii pinged the RFC and sharpened the operational case. He does not claim a suspend regression; he argues that administrative freeze of an in-flight NFS request is simply the wrong model:

"I understand that this change may not look like a pressing matter, but allowing a process to be frozen in the middle of a request, while holding a lot of locked state and without any guarantee that it will be thawed, does not look right."

The concrete failure mode he adds this week is Mesos (and similar orchestrators) using the freezer to quiesce processes, then dying and leaving those processes frozen:

"Some applications, such as Mesos, use the freezer to quiesce processes, and if they are killed, they may leave those processes frozen. If the frozen process leaves access to the NFS server locked, other applications cannot access it, which may lead to an inability to log in to the host."

That last clause is the NFS-client punchline: a single frozen requester can hold mount/server-side state that blocks unrelated users of the same NFS mount — up to and including login if the host's authentication or home directories sit on NFS. There is no thaw guarantee once the freezer user has exited, so the wedge is not a transient stall; it is a host-level outage until someone notices and thaws (or reboots).

What still has not happened

No NFS maintainer (Trond Myklebust, Anna Schumaker, or otherwise), freezer/power-management reviewer, or CIFS/other-network-fs consumer has replied in this window. The patch is still the original RFC; Kinsburskii did not attach a v2 or additional testers. The technical argument is therefore unchanged from July — only the urgency and the Mesos/login-lockout scenario are new.

Bottom line

This remains an unreviewed NFS-client bug-fix RFC. This week's contribution is not new code but a clearer statement of the production failure: administrative freezer users (Mesos and kin) can freeze a task mid-NFS request, leave locks and transport state held indefinitely, and take the rest of the mount — and potentially host login — with them. Review from both the NFS client side and the freezer maintainers is still outstanding.
