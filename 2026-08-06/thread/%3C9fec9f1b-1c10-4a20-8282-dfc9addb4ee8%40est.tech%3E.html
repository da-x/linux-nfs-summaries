nfs-utils 2.9.2 exportfs link failure with --disable-nfsdctl

Summary

This week’s linux-nfs traffic includes a cleanly diagnosed userspace build regression in nfs-utils 2.9.2: exportfs fails to link when the tree is configured with --disable-nfsdctl. The report is from Jaipaul Cheernam and, as of the week ending 2026-08-06, has no replies. It is a bug-fix discussion (a configure/Makefile feature-gating mismatch), not a protocol change and not an NFS client kernel patch.

The thread sits on the server-side userspace tools rather than the in-kernel NFS client. The practical impact is still operational: anyone building a slim nfs-utils (no nfsdctl, often also no GSS) cannot produce exportfs, which is the tool that publishes and withdraws exports the client later mounts.

The regression

Cheernam reports that 2.9.2 no longer builds under a configuration that 2.9.1 accepted:

"Building nfs-utils 2.9.2 with --disable-nfsdctl fails to link exportfs. This is a regression from 2.9.1."

His reproducer is:

./configure --disable-nfsdctl --disable-gss --disable-svcgss
make

--disable-gss is only there to drop the krb5 dependency. The failure is triggered by --disable-nfsdctl alone. The linker error is:

/usr/bin/ld: exportfs-exportfs.o: in function 'unexportfs_parsed': exportfs.c:491: undefined reference to 'nfsd_nl_cmd_str'

Default builds hide the bug because enable_nfsdctl defaults to "yes".

Root cause: two switches that no longer agree

The 2.9.2 tree added nfsdnl.c, which implements nfsd_nl_cmd_str(). That object is compiled into libnfs only under if CONFIG_NFSDCTL in support/nfs/Makefile.am. Meanwhile exportfs.c calls the same symbol under #ifdef HAVE_NFSD_NETLINK, and configure.ac defines that macro unconditionally:

AC_DEFINE([HAVE_NFSD_NETLINK], 1,
          [Define to 1 if nfsd generic netlink support is available])

The result, in Cheernam’s words:

"So exportfs always compiles the netlink code path, but the implementation isn't linked in when --disable-nfsdctl is used."

That is a classic feature-gate split: the compiler thinks generic-netlink unlock-export support is always present; the library only ships it when the nfsdctl utility is enabled.

Two proposed fixes

Cheernam verified both approaches build cleanly and asked maintainers which design they want before sending a formal patch.

Option A — always compile nfsdnl.c into libnfs (drop the CONFIG_NFSDCTL guard in support/nfs/Makefile.am). exportfs would always be able to release export state over netlink. He notes this adds no new dependency:

"libnl is already unconditionally required so this adds no new dependency"

The sketched Makefile change still pulls in LIBNL3/LIBNLGENL3 cflags and libs, but drops the -I$(top_srcdir)/utils/nfsdctl include that only made sense when nfsdctl itself was being built.

Option B — stop defining HAVE_NFSD_NETLINK unless --enable-nfsdctl is on, so exportfs skips the netlink path when nfsdctl is disabled. nfsdnl.h already has a static inline stub that returns -ENOSYS for that case. The configure.ac change moves the AC_DEFINE inside the existing if test "$enable_nfsdctl" = yes block, next to the readline check.

Cheernam prefers B:

"I lean towards Option B as it preserves the design intent that --disable-nfsdctl disables all netlink interaction with nfsd, and keeps the feature gating consistent between configure.ac and Makefile.am."

He still flags the counter-argument for A:

"Option A has merit if exportfs should always release state via netlink regardless of whether the nfsdctl utility is built."

That is the real design question the report leaves open: is --disable-nfsdctl “do not build the nfsdctl binary,” or “do not talk to nfsd over generic netlink at all”? Option A treats netlink unlock-export as a property of exportfs/libnfs. Option B treats it as part of the nfsdctl feature set.

Status this week

No maintainer has chosen A or B, and no formal patch has been posted. The report is self-contained — reproducer, exact linker error, root-cause analysis, and two tested diffs — so a follow-up should be a one-line policy decision plus a cleaned-up patch.

For NFS client readers: this does not change on-the-wire behavior or the kernel client. It does affect how distributions and embedded builds that pass --disable-nfsdctl obtain a working exportfs. Until a fix lands, those builds stop at link time on nfsd_nl_cmd_str. Default (--enable-nfsdctl) configurations are unaffected.
