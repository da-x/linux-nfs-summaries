NFS client: Nemanov posts v2 of ENXIO-on-symlink O_CREAT fix

Overview

This is a bug fix, not a new feature or protocol change: a seven-line correction to the NFSv3 client's atomic_open path in fs/nfs/dir.c. Michael Nemanov (Vast Data) posted v2 of his patch to stop open(2) with O_CREAT from returning ENXIO when the path is an existing symlink on a cold-dcache NFSv3 mount. The only in-window message is that v2 submission. It is the direct follow-through to Trond Myklebust's August 5 review of v1, which flagged a dentry refcount underflow in the original finish_no_open() call.

No maintainer Ack, Nack, or merge appears in this week's window. Later review of v2 exists after August 7 and is out of scope here.

Bridge from v1

Nemanov posted v1 on June 14, nudged it on June 30, and finally got a maintainer look on August 5. Trond's one-line verdict on v1 was:

"This will cause the dentry to underflow the refcount. It needs to be finish_no_open(file, NULL)."

v2 is that one-line correction, posted the next day. The diagnosis, the !S_ISREG() type check, and the Fixes: tag are unchanged.

The bug: ENXIO instead of following the symlink

The failure is tightly scoped. On an NFSv3 mount, with a cold dentry cache, open(2) with O_CREAT on a path that already exists as a symlink returns ENXIO ("No such device or address") instead of following the link to its target. Nemanov's reproducer is a dropped-caches os.open(..., O_WRONLY | O_CREAT | O_APPEND) against a symlink on /mnt/export.

A warm dcache hides the bug completely. After a prior stat(2), lookup_open() finds a positive dentry and skips atomic_open entirely, leaving symlink resolution to the VFS. That is why the regression survived: it only fires on the cold-cache atomic_open path.

Root cause: CREATE UNCHECKED meets no_open_fops

nfs_atomic_open_v23(), registered as inode->i_op->atomic_open for NFSv3, handles O_CREAT by sending a CREATE UNCHECKED RPC. RFC 1813 §3.3.8 (and nfsd3_create_file() in fs/nfsd/nfs3proc.c) require that when the name already exists as a non-regular file, the server return NFS3_OK plus the existing object's file handle — not NFS3ERR_EXIST. nfs_do_create() therefore returns 0 with the dentry now pointing at a symlink.

The client then unconditionally calls finish_open(), which dispatches through inode->i_fop->open(). Symlink inodes never have a real i_fop: the VFS initialises them to &no_open_fops because POSIX requires open(2) to follow symlinks, never open them directly. no_open() returns -ENXIO.

Nemanov traces the regression to commit 7c6c5249f061 ("NFS: add atomic_open for NFSv3 to handle O_TRUNC correctly.") — the same CREATE-UNCHECKED / VFS-file-type mismatch that the original atomic_open work introduced to get O_TRUNC right.

The v2 fix: type-check, then finish_no_open(file, NULL)

After nfs_do_create() succeeds, v2 verifies the returned inode is a regular file before calling finish_open(). If it is not, the path returns finish_no_open(file, NULL) so the VFS follows the symlink through the normal open path.

The NULL argument is the whole point of v2. Nemanov now documents it explicitly:

"NULL is passed because nfs_do_create() instantiates the inode on the dentry already owned by the caller; passing dentry back would cause atomic_open() to dput() it a second time."

That is Trond's underflow, written into the changelog. Passing the dentry would consume a reference the caller still holds; passing NULL tells the VFS not to drop it.

The type check is !S_ISREG() rather than S_ISLNK():

"!S_ISREG() is used rather than S_ISLNK() to cover any other non-regular types a server might return."

That is a defensive client posture: treat any non-regular CREATE-UNCHECKED result as "do not finish the open; let the VFS continue," not as a symlink-only special case.

The changelog's v2 note is a single bullet:

"Pass NULL to finish_no_open() per Trond's feedback."

The patch is still seven insertions in fs/nfs/dir.c, with Nemanov's Signed-off-by and Tested-by.

Significance for NFS client development

This is a textbook illustration of how fragile NFSv3 atomic_open remains. The original work added atomic_open specifically to handle O_TRUNC on CREATE; the ENXIO-on-symlink case is a sibling edge of the same CREATE-UNCHECKED / VFS-file-type mismatch. The warm-dcache skip means the bug is invisible in any test that stats the path first.

v2 also shows why the exit helper matters as much as the type check. finish_open() versus finish_no_open(), and dentry versus NULL, are the difference between a correct open and a dentry refcount underflow. Trond's August 5 review was two sentences; Nemanov's v2 changelog now encodes that VFS contract so the next reader does not reintroduce the underflow.

The latency — June 14 v1, June 30 ping, August 5 review, August 6 v2 — is a recurring linux-nfs pattern: small, well-scoped client fixes sit unreviewed for weeks, then get a precise, blocking comment that is turned around in a day.
