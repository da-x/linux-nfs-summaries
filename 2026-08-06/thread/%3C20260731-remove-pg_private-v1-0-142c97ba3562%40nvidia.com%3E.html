RFC: drop PG_private, with mechanical NFS folio-private cleanup

Summary

RFC to retire PG_private lands on linux-nfs with mechanical client cleanup

Zi Yan (NVIDIA) posted an RFC 14-patch series that is not an NFS protocol change and not an NFS bug fix. It is a core-MM flag-space reclaim: delete PG_private so a forthcoming PG_folio (currently reserved as __PG_folio) can mark every page that belongs to a folio. Callers would stop testing the flag and instead treat page/folio->private != NULL as the presence check.

Yan framed the motivation in the cover letter:

"This patchset removes PG_private to make space for upcoming PG_folio (reserved as __PG_folio) for identifying pages from a folio"

The intended end state is broader than NFS: page_rmappable_folio() would set PG_folio on every page of a folio so vm_insert_*() can reject folios and rmap can accept only folios, with page_folio() eventually returning NULL for non-folio pages.

Why linux-nfs was on the To/Cc list

Most filesystems already go through folio_attach/detach/change_private(), which bump and drop the folio refcount as ->private is set and cleared. Yan listed NFS as one of the exceptional users that does not fit that helper pattern, but also as one that needs no semantic rewrite:

"6. fs/nfs/write.c: folio refcount maintenance is in a bigger scope than folio->private. So folio_attach/detach/get_private() is not used. Nothing to change."

That is the client-side takeaway. NFS already keeps writeback request state on folio->private (the nfs_page / page-group path) while holding folio references over a wider lifetime than a simple attach/detach pair. The series therefore does not try to convert NFS onto the generic helpers; it only strips now-redundant flag ops and comments.

Two of the 14 patches actually touch the NFS client:

  • PATCH RFC 11/14 — treewide: remove folio_set/clear_private(). After the flag helpers become no-ops, the two remaining calls in fs/nfs/write.c are deleted (2 lines). The same patch also drops the now-empty helpers from include/linux/pagemap.h and a leftover in mm/migrate.c. Yan: "They are no-ops now. Remove them."
  • PATCH RFC 13/14 — treewide: adjust comments on PagePrivate and PG_private. fs/nfs/file.c comments that still talk about PagePrivate / PG_private are rewritten to talk about page/folio->private instead (4 lines). Ceph and UBIFS get the same comment pass.

Trond Myklebust and Anna Schumaker are on the To: line of both NFS-touching patches, and linux-nfs@vger.kernel.org is Cced. Neither NFS maintainer had replied in-window.

The cover letter also notes a related helper, folio_test_fs_private(), added so core MM can ask “does this folio have filesystem-only private data?” while excluding swapcache (which overlays swp_entry_t on ->private) and hugetlb (which stores its own flags there). Filesystem code, including NFS, is not expected to see those two cases.

Exceptional users around NFS, and the Xen question

The rest of the series is the inventory of code that used PG_private as a marker rather than as a shadow of ->private: zsmalloc first-component zpdesc pages, perf ring-buffer high-order AUX pages, Xen grant-table foreign-page encoding (pointer on 32-bit, packed {domid,gref} on 64-bit, including the valid-zero case), fscrypt bounce pages, erofs reverse-readahead lists plus in-flight I/O counters, f2fs PAGE_PRIVATE_NOT_POINTER bit packing, and hugetlb’s folio_change_private(folio, NULL) without a matching refcount.

That inventory is what produced the only in-window review. On 3 August, Jürgen Groß (SUSE, Xen) asked — the OpenPGP-signed body arrived truncated on the list, but Yan’s reply preserves the tail of the question as not set)? — whether ->private can be live without PG_private.

Yan confirmed:

"Yes, it is possible. See: #5 in the exceptional users: erofs uses ->private for reverse linked list and in-flight counters without setting PG_private. I get rid of the first one and converted the second one to use folio_attach/detach/get_private() to follow the general ->private use pattern."

He then restated the non-filesystem overlays and the new helper:

"For non file system folios, anon swapcache puts swap_entry_t in ->private and hugetlb puts its flags in ->private. I added folio_test_fs_private() to exclude them, but this helper is planned to be used by core MM, since filesystem code should not encounter these two."

That answer is the week’s only technical conclusion: the flag and the pointer were already allowed to diverge, which is exactly why NFS can keep using ->private as request state without a PG_private bit, and why the flag can be deleted.

Semantic nits that could still matter to NFS tooling

Yan flagged a minor ABI/docs shift, not an NFS functional change:

"KPF_PRIVATE has a minor semantic change. Since PG_private will be removed, KPF_PRIVATE represents pagecache folios whose ->mapping is not NULL and with ->private set. Currently KPF_PRIVATE can be set for orphaned pagecache folios with ->mapping == NULL."

He also left Documentation/mm/hugetlbfs_reserv.rst alone because it is already stale. Testing reported this week is MM/selftest plus zsmalloc, erofs, fscrypt, and f2fs; no NFS or xfstests run is claimed. The series is explicitly LLM-assisted (Claude for planning and review, Codex for a final pass).

Status at week’s end

This remains an RFC. The NFS client impact in-tree is two deleted no-op flag calls in fs/nfs/write.c and comment wording in fs/nfs/file.c; writeback still owns folio->private over a wider refcount window than the generic attach/detach helpers. No Acked-by or Reviewed-by from NFS maintainers, no follow-up patches, and no merge discussion. The only reviewer engagement is Groß’s Xen-oriented question, answered by Yan with the erofs/folio_test_fs_private() explanation. Watch for whether Trond/Anna object to dropping the explicit folio_set/clear_private() markers on the NFS writeback path, or whether a later revision tries to force NFS onto folio_attach/detach_private() after all.
