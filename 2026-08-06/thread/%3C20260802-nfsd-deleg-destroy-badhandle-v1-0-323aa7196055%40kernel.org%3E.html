NFSD stops revoking delegations the client never recorded

Summary

This week Chuck Lever posted a nine-patch NFSD series that closes the server half of a client-visible delegation livelock. The work is a bug fix (with a protocol-correctness follow-through), not a new feature: when a client answers CB_RECALL with NFS4ERR_BAD_STATEID or NFS4ERR_BADHANDLE, NFSD must destroy that delegation rather than park it on cl_revoked and keep advertising SEQ4_STATUS_RECALLABLE_STATE_REVOKED. There were no reviews in-window; the thread is the series itself.

Client-facing failure that motivated the series

Lever's cover letter traces the bug to a nightly backup on his home-directory server. NFSD had granted a write delegation during the day; the Linux client then lost that stateid to the hole that NFS: Return a delegation the client fails to record already addressed on the client. When NFSD later recalled the delegation, the client had no record of the stateid:

"When NFSD recalled that delegation, the client had no record of the stateid and answered CB_RECALL with NFS4ERR_BAD_STATEID. NFSD added the delegation to cl_revoked, where only a FREE_STATEID drains it. That FREE_STATEID never arrives, so every later SEQUENCE reply carries SEQ4_STATUS_RECALLABLE_STATE_REVOKED. The client's state manager loops issuing TEST_STATEID but never finds the missing state."

That is the same cascade documented in June: a dropped client-side DELEGRETURN leaves the server believing the client still holds the stateid; the recall is rejected; the server revokes; the client's recovery loop never terminates. The client patch (queued by Anna Schumaker for the next bugfix round as of early July) stops the silent drop. This series stops NFSD from turning a rejected recall into a permanent SEQ4_STATUS_RECALLABLE_STATE_REVOKED flag that the client's state manager cannot clear.

RFC 8881: complete the recall, do not revoke

Patch 8 is the functional core. A client that answers CB_RECALL with NFS4ERR_BADHANDLE or NFS4ERR_BAD_STATEID has no record of the delegation, so the FREE_STATEID that would drain cl_revoked never arrives. Lever now destroys that delegation on reap instead of revoking it:

"Destroy such a delegation when it is reaped rather than revoking it onto cl_revoked. RFC 8881 Section 20.2.4 completes the recall at the reply when its status is neither NFS4_OK nor NFS4ERR_DELAY, so a rejected recall leaves nothing to revoke."

Administrative revoke is left alone, because NFS4ERR_ADMIN_REVOKED still has to report it. A destroyed stateid now returns NFS4ERR_BAD_STATEID instead of NFS4ERR_DELEG_REVOKED. Lever is explicit about the remaining hazard for a misbehaving client:

"A client that rejects the recall but still holds the delegation gets no notice that its state was revoked."

The patch is tagged Fixes: 3bd64a5ba171 ("nfsd4: implement SEQ4_STATUS_RECALLABLE_STATE_REVOKED") and Cc: stable for 6.14.x — the same era in which the revoked-state flag started trapping Linux clients in the TEST_STATEID loop.

The race: CB_RECALL can outrun the grant

A naive "destroy on BAD_STATEID" rule is wrong when the recall races the OPEN that granted the delegation. The cover letter and patch 8 both insist on RFC 8881 Section 2.10.6.3 as the proof that the client has seen the grant:

"CB_RECALL can outrun the reply that granted the delegation; a rejection proves nothing until the client has seen that grant. RFC 8881 Section 2.10.6.3 makes retirement of the slot that carried the grant that proof. NFSD retries the CB_RECALL until the slot retires and revokes in the old way when the retries lapse."

Until that slot retires, a BAD_STATEID is ambiguous: the client may simply not have recorded the grant yet. Retrying, then falling back to the old revoke path if retries expire, keeps the server from destroying a live delegation that the client is about to start using.

Referring calls on CB_RECALL

Patch 9 makes CB_RECALL the second consumer of referring-call lists, so the client can distinguish "I have not processed the grant yet" from "I never held this stateid." Until the granting slot retires, each recall names that request in CB_SEQUENCE:

"Remove the ambiguity with the referring call mechanism of RFC 8881 Section 2.10.6.3: until the slot that carried the grant retires, name that request as a referring call in the CB_SEQUENCE of each recall. A client that finds it still outstanding may respond NFS4ERR_DELAY, and the recall is retried until the client has processed the grant."

Without that list, retries eventually lapse and NFSD revokes a delegation the client is by then able to return — the exact client-visible failure the series is trying to kill. A recall reuses one callback context across retries and ->prepare does not run on every send; the granting request is stable, so an inherited list is the right list. Slot retirement drops it, and nfs4_free_deleg() releases whatever remains.

For NFS client developers this is the operationally important half of the series: a Linux client that implements referring-call NFS4ERR_DELAY can now stall the recall until nfs_inode_set_delegation() has recorded the stateid, instead of answering BAD_STATEID and triggering either destroy or revoke.

XDR budget repairs (patches 1–6)

Referring-call lists cannot ride in CB_RECALL until the send-buffer budget is honest. Lever notes that NFSD's original referring-call implementation got several XDR sizes wrong, and the first six patches correct those macros in fs/nfsd/xdr4cb.h.

Patch 1 is the one that actually changes the backchannel contract. cb_sequence_enc_sz counted the session ID, four scalars, and one referring-call list, but encode_cb_sequence4args() also emits the CB_SEQUENCE opcode and the csa_referring_call_lists array count — two XDR words short. Every NFS4_enc_cb_*_sz built on that macro is short by the same two words. Because NFSD_CB_MAX_REQ_SZ derives from NFS4_enc_cb_recall_sz, check_backchannel_attrs() was accepting a ca_maxrequestsize eight bytes too small:

"The minimum a client must advertise rises by those eight bytes."

Lever is careful that this is not a send-buffer overrun: rq_callsize already adds two credential slacks on top of p_arglen. The only client that notices is one whose ca_maxrequestsize falls inside those eight bytes, so he marks it as no-backport.

Patch 2 budgets the CB_RECALL truncate field (one more XDR word, four more bytes on the advertised minimum). Patches 3 (CB_LAYOUTRECALL discriminator and recall stateid, five words), 4 (CB_OFFLOAD opcode), 5 (CB_NOTIFY_LOCK opcode), and 6 (CB_RECALL_ANY opcode) fix the same class of off-by-N-word macros. Those four size p_arglen only; credential slack has always covered the shortfall, so none of them need a backport. Taken together, they are plumbing so that a referring-call list can actually fit in the CB_RECALL send buffer.

Locking comment cleanup

Patch 7 is documentation only. The comment above the SC_STATUS_ flags claimed nn->deleg_lock protects sc_status for delegation stateids, but only hashed-delegation transitions take that lock. c88c150a467f ("nfsd: fix possible badness in FREE_STATEID") started setting SC_STATUS_CLOSED under ->cl_lock; 8dd91e8d31fe ("nfsd: fix race between laundromat and free_stateid") added two more sites. The comment is updated so the destroy/revoke path in patch 8 is not coded against a lock that is no longer exclusive.

Status

  • Classification: NFSD bug fix with protocol-correct recall completion; XDR-budget prerequisite plus referring-call support on CB_RECALL. Directly complementary to the June NFS client DELEGRETURN fix.
  • Client impact: Stops SEQ4_STATUS_RECALLABLE_STATE_REVOKED from sticking after a client rejects a recall for a stateid it never recorded; Linux clients that honor referring calls can NFS4ERR_DELAY until the grant is recorded. Backchannel ca_maxrequestsize minimum rises by twelve bytes (eight from CB_SEQUENCE, four from truncate).
  • Review: None in this week's window. Patch 8 is the stable candidate (Cc: stable 6.14.x); patches 1–6 are explicitly not.
  • Files: fs/nfsd/nfs4callback.c, fs/nfsd/nfs4state.c, fs/nfsd/state.h, fs/nfsd/xdr4cb.h (231 insertions, 48 deletions).
