NFSv4.2 futimens() still skips SETATTR; leases workaround

Summary

This remains a client-side NFS bug report, not a protocol change or new feature. Earlier weeks established that GNU touch -d on NFSv4.2 can return success from fd-based futimens() / utimensat(fd, NULL, ...) while never sending SETATTR, so the server inode stays stale and the client's cached timestamps later snap back. Michael Yang originally isolated the fd-versus-pathname split; Holger Hoffstätte confirmed it on 7.1.x and flagged b8b3002fbfef (nfs: split nfs_update_timestamps) plus 761475268fa8 (fs: refactor ->update_time handling) as 7.0-era suspects. Last week Yang further bounded the regression to 6.17+ and NFSv4.2 only (absent on 6.12.88 LTS; vers=4.1 updates the server).

This week's four in-window messages add a third independent reproduction, a practical workaround tied to NFSv4 delegations, a regressions-list nudge for a real bisection, and a negative result on 7.2-rc5. There is still no maintainer diagnosis or patch.

Third reproduction, and a leases workaround

Matt Kinni reported the same silent-success behaviour on Fedora 44 with kernel 7.0.8 and nfs-utils 2.8.7. Local extraction preserved timestamps; copying onto an NFSv4.2 mount with rsync -a only updated the client view. The server-side backing inode did not change, and the client later reverted. touch -d failed the same way.

The new operational clue is that the failure tracks NFS delegations / leases, not just the protocol minor version:

"I have not tried forcing vers=4.1 yet, but disabling NFS delegations on the server with fs.leases-enable=0 made the problem go away for me."

That is the first in-thread observation that the missing SETATTR is associated with a write/open delegation rather than a generic v4.2 setattr path. Combined with last week's vers=4.1 success, the client picture now looks like: fd-based ->update_time on a delegated NFSv4.2 open file dirties the local inode and returns 0 without flushing attributes to the wire.

Holger Hoffstätte immediately tried both workarounds and ranked them:

"Disabling leases seems like the best workaround for now if one can live with the performance hit. Forcing 4.1 makes files work, but in turn seems to break directory modification timestamps. :-/"

So vers=4.1 is not a free escape hatch: file mtimes land, but directory mtime updates appear to regress. fs.leases-enable=0 on the server restores persistence at the cost of delegation performance.

Still no bisection; 7.2-rc5 does not help

Thorsten Leemhuis, writing from the kernel regressions list, pressed for the missing developer-facing evidence:

"Did anyone bisect this (or try reverting the two commits that Holger mentioned earlier)? Seems this is needed to get the attention of the developers -- especially if it's really a VFS issue, as they won't see the report on a nfs list."

Nobody in this week's traffic answered that call. Hoffstätte's two 7.0 commits remain un-reverted in public, and last week's Proxmox data already showed the bug on 6.17.x, so those commits cannot be the original introduction even if they sit on the failing path. The practical bisection window is still 6.12.88 (good) through 6.17 (bad).

Later the same day Hoffstätte tested 7.2-rc5 with leases left enabled, hoping recent related timestamp/setattr commits in that tree would close the hole:

"Since 7.2-rc contains a few commits that fix related problems, I decided to give -rc5 a try (with fs.leases-enable=1). Unfortunately the lack of attribute persistence seems to persist."

The regression is therefore still live on current -rc, not just 7.0/7.1 stable.

Where things stand

The report is now independently reproduced on three setups (Yang, Hoffstätte, Kinni), protocol-bounded to NFSv4.2, version-bounded against 6.12 LTS, and workaround-bounded to NFS leases/delegations. The user-visible impact is unchanged and still nasty: tools that rely on futimens() (touch -d, rsync -a) look successful, then timestamps evaporate on revalidation.

What NFS client developers still lack is a commit-level bisection (or a revert of the 7.0 timestamp-split / VFS ->update_time refactor) and a look at how the v4.2 delegated open-file setattr path interacts with nfs_update_timestamps. No protocol change is proposed. No maintainer reply landed this week.
