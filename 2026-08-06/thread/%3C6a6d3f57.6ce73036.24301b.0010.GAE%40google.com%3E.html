syzbot hung-task report in nfsd write_threads

Summary

Summary

This week’s traffic is a single, unreplied bug report: a syzbot hung-task splat tagged [nfs?] against the in-kernel NFS server control plane, not the NFS client. syzbot reported INFO: task hung in write_threads on upstream HEAD 3708dd948844 (Merge tag 'pm-7.2-rc6'), with no reproducer and no human follow-up before week close.

The hung task is a syzkaller worker blocked more than 143 seconds in uninterruptible sleep while taking nfsd_mutex from the /proc/fs/nfsd/threads write path:

"INFO: task syz.8.803:9466 blocked for more than 143 seconds."

The stack is:

__mutex_lock
write_threads+0x39d/0x5a0 fs/nfsd/nfsctl.c:432
nfsctl_transaction_write+0x10f/0x160 fs/nfsd/nfsctl.c:112
vfs_write / ksys_write

This is a server-side hang, not a client I/O stall and not a protocol change. write_threads() is the nfsd control-file handler that starts or stops nfsd threads; it serializes on the global nfsd_mutex. The [nfs?] tag is syzbot’s uncertain subsystem guess. Nothing in the trace touches fs/nfs/, xprtsock.c, or any NFS client code path.

What the lock dump actually shows

The interesting part of the report is the lock inventory, not the hung stack itself. Two threads of the same syzkaller process are piled up on nfsd_mutex:

  • syz.8.803/9460 holds nfsd_mutex in write_ports+0xb5/0xd10 fs/nfsd/nfsctl.c:860 — the /proc/fs/nfsd/portlist writer that adds or removes nfsd listeners.
  • syz.8.803/9466 is the hung task, waiting on the same mutex in write_threads.

Both also hold sb_writers on the nfsd control filesystem and a f_pos_lock. That is the classic nfsdctl pattern: every write through nfsctl_transaction_write() takes nfsd_mutex, so a slow or stuck write_ports (socket bind, listener start, or teardown) makes every other nfsd control write — threads, versions, exports — sit in D state until the hung-task watchdog fires.

The rest of the lock dump is noisier. A kworker holds rtnl_mutex in addrconf_dad_work, and syz.5.1691 is in rtnl_dellink waiting on rtnl_mutex and then synchronize_rcu_expedited. The kernel is also tainted G S L (CPU_OUT_OF_SPEC and SOFTLOCKUP). The NMI backtraces that follow are unhelpful: khungtaskd dumping stacks, and swapper/0 sitting in pv_native_safe_halt. There is no smoking-gun stack of a CPU spinning inside nfsd.

Whether write_ports is itself blocked behind RTNL (listener bind/unbind while holding nfsd_mutex) is not proven by this dump. The report does not capture the holder’s full wait chain, only that it still owns nfsd_mutex after 143 seconds.

Reproducer status and related reports

syzbot is explicit:

"Unfortunately, I don't have any reproducer for this issue yet."

Assets (disk image, vmlinux, bzImage) and a dashboard entry (extid=78013a8f4497a445a448) are attached. The prescribed Reported-by tag is syzbot+78013a8f4497a445a448@syzkaller.appspotmail.com.

The same morning, syzbot filed a sibling splat, [syzbot] [nfs?] INFO: task hung in write_ports, against 7.2-rc5. That report does have a C reproducer, and its lock dump is more diagnostic: nfsd_mutex is held by nfsd_shutdown_threads on the deactivate_super path while a crowd of writers wait in write_ports. Together the two reports point at the same bottleneck — global nfsd_mutex serializing thread start, portlist updates, and nfsd teardown — rather than a client-side bug. They remain separate syzbot bugs; nobody has #syz dup’d them on-list this week.

Older hung-task reports against the netlink siblings (nfsd_nl_threads_get_doit, nfsd_nl_threads_set_doit) exist from prior cycles. They share the same mutex, not the same reproducer.

NFS client angle

There is none in this thread. No client maintainer replied, and the stack never leaves fs/nfsd/nfsctl.c. The client-relevant work this week (Chuck Lever’s kTLS CMSG fixes in xprtsock.c, TCP read_sock follow-ups) lives in other threads. A hang in write_threads can of course starve a test harness that is also mounting NFS, but that is a test-lab coupling, not a client defect.

Status at week close

Unanswered. No #syz fix, no #syz dup, no maintainer analysis, no patch. The report is a bug report of a hung nfsd control-file write, likely nfsd_mutex held too long by a concurrent write_ports (and possibly by nfsd shutdown, if the sibling write_ports splat is the same bug). Until someone captures the holder’s wait chain or runs the write_ports C reproducer against this tree, it stays an open, unreproduced server-side hung-task report.

syzbot’s usual closing boilerplate still applies: reply with #syz fix: exact-commit-title if a fix lands, or #syz dup: if this is folded into the write_ports bug.
