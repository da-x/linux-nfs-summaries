Flexfiles decode hardening for LAYOUTGET and GETDEVICEINFO

Summary

This week Junrui Luo posted a five-patch v1 series that hardens the NFSv4 flexfiles layout driver against malformed metadata-server replies. The work is a bug-fix series, not a protocol change or a new feature: every patch closes a decode-path hole in LAYOUTGET or GETDEVICEINFO that a hostile or buggy MDS can trigger on the client. There were no replies in-window; the series landed on 4 August and still awaits review.

Luo framed the set as independent, stable-bound client fixes:

"All five patches fix bugs the flexfiles layout driver hits while decoding a reply body from the metadata server."

"The five are independent of each other and can be applied in any order."

The cover letter splits the series along the two XDR decode paths: patches 1–3 sit on GETDEVICEINFO (nfs4_ff_alloc_deviceid_node() / nfs4_decode_mp_ds_addr()), patches 4–5 on LAYOUTGET (ff_layout_alloc_lseg()). Yuhao Jiang is credited as reporter on every patch; four of the five carry Cc: stable@vger.kernel.org.

GETDEVICEINFO: unbounded loops, a netid leak, and a stack-port leak

Patch 1 bounds the multipath address count taken off the wire in nfs4_ff_alloc_deviceid_node(). mp_count is used as the loop bound for nfs4_decode_mp_ds_addr() with no upper cap, even though nfs4_get_device_info() only bounds pdev->pglen. Once the XDR stream is exhausted, nfs4_decode_mp_ds_addr() returns NULL without consuming a byte, so every remaining iteration re-fails at the same offset. Luo’s diagnosis is blunt:

"A server advertising 0xffffffff addresses in a body that holds none of them spins the loop for roughly 2^32 iterations with no rescheduling point, potentially tripping the soft lockup watchdog and the RCU stall detector on non-preemptible kernels. The list_empty(&dsaddrs) check below the loop only runs once the loop has finished."

The fix rejects implausible counts up front, matching the existing mirror_array_cnt / dss_count checks in ff_layout_alloc_lseg(). The bound is introduced as a new constant in flexfilelayout.h. Fixes tag: d67ae825a59d ("pnfs/flexfiles: Add the FlexFile Layout Driver").

Patch 2 is a resource leak, not a DoS. nfs4_decode_mp_ds_addr() allocates r_netid and hands it to the returned nfs4_pnfs_ds_addr, but both drain loops in nfs4_ff_alloc_deviceid_node() free only da_remotestr and the da itself. Luo notes two call sites:

"The success-path loop runs when nfs4_pnfs_ds_add() finds an equivalent data server already cached and leaves the caller's list intact; the out_err_drain_dsaddrs loop runs on every late failure in the function."

"da_remotestr and da_netid are the only heap pointers in the structure, so free both, as nfs4_pnfs_ds_addr_free() does."

This is the only patch in the series without a stable Cc. Fixes tag: 4be78d26810b ("NFSv4/pNFS: Store the transport type in struct nfs4_pnfs_ds_addr").

Patch 3 is the most security-flavoured of the GETDEVICEINFO trio, and it lives in shared pNFS code (fs/nfs/pnfs_nfs.c) rather than the flexfiles driver. nfs4_decode_mp_ds_addr() splits r_addr with two strrchr() passes; rpc_pton() validates the address half with an explicit length and never looks at the port octets. The port is converted with sscanf(portstr, "%d-%d", &tmp[0], &tmp[1]) and the return value is discarded. tmp[] is uninitialised, so an r_addr such as "192.168.1.1.x.y" leaves both elements unwritten:

"The stale stack contents then become the destination port of the data server connection and are rendered into da_remotestr, potentially leaking client stack memory to the metadata server."

The fix requires both conversions to succeed and otherwise takes the existing out_free_da path, matching rpc_uaddr2sockaddr(). Fixes tag: 16b374ca439f ("NFSv4.1: pnfs: filelayout: add driver's LAYOUTGET and GETDEVICEINFO infrastructure") — so this is older than flexfiles itself and applies to any layout driver that uses the shared multipath decoder.

LAYOUTGET: allocator WARN and a client panic on stripe_unit

Patch 4 closes the remaining unbounded count in ff_layout_alloc_lseg(). fh_count is decoded from the flexfiles LAYOUTGET body and passed straight to kzalloc_objs() to size dss_info->fh_versions. Commit 2c6bb3c40bc2 already rejected a zero count, but unlike neighbouring mirror_array_cnt and dss_count the value had no upper bound:

"sizeof(struct nfs_fh) is 130, so an fh_count of 32264 or more pushes get_order() past MAX_PAGE_ORDER and trips the page allocator's WARN_ON_ONCE_GFP()."

Luo rejects implausible counts up front, matching both the local mirror/dss checks and filelayout_decode_layout()’s handling of the equivalent num_fh field. A new header constant carries the cap. Fixes tag again: d67ae825a59d.

Patch 5 is the most severe of the five: a client panic on first I/O. ff_layout_alloc_lseg() decodes stripe_unit as a u64 and only rejects it when dss_count > 1 && stripe_unit == 0. Every consumer then divides by only the low 32 bits. ff_layout_pg_test() narrows explicitly to u32; nfs4_ff_layout_calc_dss_id() passes the u64 to do_div(), which narrows the divisor itself. Luo’s conclusion:

"A server-supplied non-zero multiple of 2^32 such as 0x100000000 therefore passes the check and reaches both dividers as a zero divisor, so the first read or write through the layout takes a divide error and panics the client. The same narrowing silently turns any other value above U32_MAX into an unrelated stripe size."

"Values that do not fit in 32 bits are not representable by the arithmetic this driver performs on stripe_unit, so reject them at decode time rather than truncating them."

Fixes tag: 20b1d75fb840 ("NFSv4/flexfiles: Add support for striped layouts").

Status this week

The series is a clean, small (22 insertions / 3 deletions across four files) client-side hardening drop against base commit 075b74841bd0065a3bda3440873c747938e69b68. No Acked-by, Reviewed-by, or maintainer comment landed before the week closed. The practical takeaway for NFS client development is that flexfiles still trusts several on-the-wire counts and a 64-bit stripe unit that the rest of the driver cannot actually use: an MDS can stall the client in GETDEVICEINFO, leak da_netid, leak stack into da_remotestr and the DS port, trip the page allocator on LAYOUTGET, or panic the client on the first striped I/O. Four of the five patches are marked for stable; patch 2 (the netid leak) is not.

Until review arrives, the series stands as posted: five independent decode-path bug fixes for the flexfiles client, with the shared pNFS multipath decoder (patch 3) and the stripe-unit divide-by-zero (patch 5) the two that reach beyond flexfiles-only code or beyond a mere WARN.
