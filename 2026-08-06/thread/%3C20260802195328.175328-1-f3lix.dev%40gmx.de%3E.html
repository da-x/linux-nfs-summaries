NFSv4.2 client: request mode after CLONE to drop stale setid bits

Summary

This week's linux-nfs traffic includes a one-message bug-fix from Felix Hoffmann that targets a stale-mode hole in the NFSv4.2 client's CLONE path. There is no protocol change and no new feature: the patch asks the existing post-CLONE GETATTR to fetch mode so the client's inode cache cannot keep setuid/setgid bits the server has already cleared. No maintainer reply, Acked-by, or NACK landed in the week ending 2026-08-06.

Stale setid bits after CLONE

Hoffmann reports that an NFS server may strip setuid and setgid bits when CLONE writes into the destination file, but the Linux client currently omits mode from the compound's post-operation attributes. The cached mode can therefore still look privileged after the server has dropped those bits, and a local process can execute the file under that stale view:

"The NFS server can clear setuid and setgid bits when CLONE modifies the destination. The client currently omits mode from the post-operation attributes, so the cached mode can retain setid bits after the server has removed them. A local process can then execute the file using those stale privilege bits."

The proposed fix is a three-line change in fs/nfs/nfs42proc.c: request mode in the CLONE compound's GETATTR so the ordered post-operation inode update installs the server's mode before CLONE returns to the caller.

"Request mode in the CLONE compound's GETATTR. This lets the ordered post-operation update install the server's mode before CLONE returns."

Hoffmann tags the original NFSv4.2 CLONE plumbing, Fixes: e5341f3a5762 ("nfs42: add CLONE proc functions"), and CCs stable@vger.kernel.org. The commit message also carries Assisted-by: Codex:gpt-5.

Reproducer and test evidence

The patch is a client-side correctness/security fix rather than a server or XDR change. Hoffmann tested on x86-64 with an NFSv4.2 loopback mount against Linux NFSD exporting Btrfs:

  • Before the change, the client retained mode 04775 while the server stored 0775, and the privilege transition reproduced in 10/10 non-debug runs.
  • With the change, both client and server reported mode 0775, and no privilege transition occurred in 10/10 non-debug runs or 3/3 KASAN runs.

He notes that the reproducer needs write authorization on the destination: NFSD rejected the same operation against a non-writable 04755 file with EACCES. A working reproducer is offered privately on request.

Client-development context

This is the same family of post-op attribute bugs the client has hit on other NFSv4.2 data-modifying ops: after ALLOCATE/DEALLOCATE the client historically failed to refresh mode bits, and earlier this year Olga Kornievskaia fixed CLONE/COPY timestamp and block-attribute updates when delegated attributes were present. Hoffmann's patch is narrower and more security-flavored: it does not touch delegation handling, it only adds mode to the CLONE GETATTR bitmap so nfs_post_op_update_inode() cannot leave setid bits in cache.

Status this week

The thread has a single in-window message and no follow-up. Until reviewers weigh in, the client still ships the original CLONE attribute bitmap; anyone reproducing server-side setid clearing on CLONE (Linux NFSD on Btrfs in Hoffmann's setup) can still see a privileged cached mode on the destination until this, or an equivalent, lands.
