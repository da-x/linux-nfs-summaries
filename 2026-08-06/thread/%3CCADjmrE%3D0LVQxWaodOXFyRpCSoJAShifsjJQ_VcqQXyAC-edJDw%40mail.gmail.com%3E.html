NFSD: write_unlock_fs() post-shutdown UAF already queued in nfsd-next

Summary

This week's activity is a two-message bug report, not a feature or protocol change. George Chapman flagged what he believed was a leftover post-shutdown use-after-free in the procfs write_unlock_fs() path; Chuck Lever closed it the same weekend by pointing at a fix already sitting in nfsd-next.

The report

On 1 August, George Chapman wrote to linux-nfs with:

"[BUG] NFSD: write_unlock_fs() has the same pre-shutdown-check UAF that 92ea163c773c just fixed for the netlink command"

The claim is that the procfs handler for /proc/fs/nfsd/unlock_filesystem still walks NFSD state after the server has been torn down, in the same way the NFSD_CMD_UNLOCK_FILESYSTEM netlink command did before commit 92ea163c773c ("NFSD: Prevent post-shutdown use-after-free in NFSD_CMD_UNLOCK_FILESYSTEM"). That netlink fix is already in the v7.2-rc tree.

The ingest of Chapman's body is truncated (Chuck's reply quotes only the opening "Hi all," and a closing "before sending."), so the detailed reproducer and code walk are not on the record here. The subject line, however, is unambiguous: this is the procfs twin of a UAF that maintainers already treated as a local-admin (CAP_SYS_ADMIN) slab use-after-free in the unlock-filesystem admin paths.

Background (briefly)

This is not a new class of bug. In mid-June, Chuck Lever posted a three-patch series, "[PATCH 0/3] Fix NFSD post-shutdown use-after-free in the unlock_filesystem paths", after Musaab Khan showed that writing a path to /proc/fs/nfsd/unlock_filesystem after nfsd had stopped could hit freed nn->conf_id_hashtbl memory inside nfsd4_cancel_copy_by_sb(). Both the procfs handler and the then-pending netlink command called the cancel helper before taking nfsd_mutex and before confirming the server was still up. Jeff Layton reviewed that series. A follow-on patch then switched the same three unlock entry points (write_unlock_fs, nfsd_nl_unlock_filesystem_doit, nfsd_nl_unlock_export_doit) from nn->nfsd_serv to NFSD_NET_UP to close a distinct startup-window NULL deref.

Chapman's report is aimed at the first of those holes — the post-shutdown UAF on the procfs side — after noticing that only the netlink half (92ea163c773c) had a visible mainline SHA.

Maintainer response: already fixed

Less than a day later, Chuck Lever replied that the procfs half is already queued:

"Commit 208b023eef24 ("NFSD: Prevent post-shutdown use-after-free in unlock_filesystem") is already queued in the nfsd-next branch."

That commit title matches the June PATCH 1/3, the procfs write_unlock_fs() / unlock_filesystem counterpart to the netlink fix Chapman cited. Lever added a process note rather than a technical debate:

"You can search the linux-nfs@ list archive on lore.kernel.org as part of your research to determine whether an issue like this has been previously reported or fixed."

No patch was requested, no counter-analysis was offered, and no further replies landed in-window. The thread is closed as a duplicate of an already-queued NFSD bug fix.

Why it still matters for NFS client work

The code under discussion is server-side (fs/nfsd/nfsctl.c and the NFSv4 state-table walkers), not the NFS client. The operational impact on clients is nevertheless real: unlock_filesystem is the admin path that revokes NFSv4 open state, NLM locks, and in-flight async COPY operations for a superblock. A post-shutdown UAF here is a host crash, not a protocol error — every connected client loses the export. The June series already established the correct locking: cancel and revoke must run only while nfsd_mutex is held and the per-netns tables are live (NFSD_NET_UP), because nfs4_state_destroy_net() frees nn->conf_id_hashtbl on the way down and does not poison the pointer.

The split landing — netlink UAF 92ea163c773c already in v7.2-rc, procfs UAF 208b023eef24 still in nfsd-next as of this reply — is what made Chapman's report look novel. Lever's SHA is the status that matters: no new client or server patch is needed from this thread; the remaining work is for 208b023eef24 to leave nfsd-next and reach mainline/stable.

Conclusion

This week's thread is a duplicate bug report against NFSD's procfs write_unlock_fs() path. Chapman correctly identified that the netlink unlock command and the procfs handler shared a pre-shutdown-check UAF; Lever confirmed the procfs fix is already commit 208b023eef24 on nfsd-next and pointed the reporter at lore. No new patch, no protocol change, and no client-side code change came out of the exchange.
