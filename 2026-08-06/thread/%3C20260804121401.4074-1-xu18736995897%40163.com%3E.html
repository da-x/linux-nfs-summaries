nfs-utils conffile unmatched-quote section leak

Summary

This week’s linux-nfs traffic includes a small but pointed bug fix in the nfs-utils configuration parser, not a protocol change and not kernel NFS client code. xuchenchen posted [PATCH] conffile: clear invalid section on unmatched quote against support/nfs/conffile.c, then respun it as v2 four minutes later. There were no replies, acks, or nacks in-window.

The bug

conf_parse_line() mishandles a section header that opens a quote and never closes it. The parser allocates a new section name and leaves that name live after it has already diagnosed the header as invalid. Later key = value lines can therefore land in that bogus section, even though the diagnostic claims they will be ignored until the next real section.

The author put the mismatch in the commit log:

"When a section header contains an opening quote without a matching closing quote, conf_parse_line() leaves the newly allocated section name active. As a result, assignments following the malformed header can be added to that invalid section even though the diagnostic says they will be ignored until the next section."

That is a correctness issue for nfs-utils consumers of the shared conffile helper (exports, idmap, nfs.conf-style files, and similar). A malformed quoted section should fail closed: subsequent assignments must not attach to a half-parsed name.

The fix

The patch is two insertions in support/nfs/conffile.c. On the unmatched-quote error path, the newly allocated section name is freed and the current-section pointer is cleared before return:

"Free and clear the section name before returning so subsequent assignments are ignored as intended."

That restores the documented ignore-until-next-section behavior and also avoids leaking the allocated name. The change is local to userspace parsing; it does not touch the kernel NFS client, mount path, or wire protocol.

v1 to v2

v1 and v2 describe the same two-line edit (support/nfs/conffile.c | 2 ++). The respin reformats the commit message (line wrapping in the problem statement) rather than changing the approach. Both carry Signed-off-by: xuchenchen <xuchenchen@kylinos.cn>.

Status
