More NFS client bugfixes land in Linux 7.2-rc

Summary

Overview

This week NFS client maintainer Anna Schumaker sent Linus a second 7.2-rc bugfix pull, tagged nfs-for-7.2-3 and based on 7.2-rc4. The request is a bug-fix pull, not a feature or protocol change: three client-only corrections, all in fs/nfs/nfs4proc.c (27 insertions, 6 deletions). The kernel.org PR tracker confirmed the merge into torvalds/linux.git the same afternoon, at 7c350d079e79.

There was no on-list debate this week. The technical argument already happened in July, when the FREE_STATEID lifetime series and the NFSv4.2 listxattr accounting fix were reviewed. This pull is the delivery vehicle that puts those client fixes on the 7.2-rc train.

The tag covers:

  • NFS: Pin the struct nfs_server during a FREE_STATEID call (Anna Schumaker)
  • NFS: Decrement refcounts if allocating nfs_free_stateid_data fails (Anna Schumaker)
  • NFSv4.2: fix nfs4_listxattr size accounting (Achilles Gaikwad)

How this pull sits in the 7.2-rc cycle

Three weeks earlier, Schumaker's first 7.2-rc client pull (nfs-for-7.2-rc3) already landed SUNRPC rpc_clnt pinning, an O_TRUNC permission-mask fix, and unstable-write memory accounting. This week's follow-on is narrower and more surgical: it only touches NFSv4 procedure code, and it closes two independent client bugs that both showed up as real crashes rather than theoretical review nits.

Schumaker's cover note is deliberately terse:

"More NFS Client Bugfixes for Linux 7.2-rc

Bugfixes:

  • NFS: Pin the 'struct nfs_server' during a FREE_STATEID call
  • NFS: Decrement refcounts if allocating nfs_free_stateid_data fails
  • NFSv4.2: fix nfs4_listxattr size accounting"

The tip commit is Gaikwad's listxattr fix (e053b624f5d3, 31 July). The PR tracker bot's one-line confirmation is the entire public resolution:

"has been merged into torvalds/linux.git"

FREE_STATEID: keep nfs_server alive while the async RPC is in flight

The first two commits are Schumaker's July 10 series, written after Dan Aloni of Vast Data hit a use-after-free when a delayed FREE_STATEID outlived the server object it was cleaning up.

The root cause is the async conversion of nfs41_free_stateid. Once that RPC can complete after the mount / nfs_server teardown path has already dropped the last reference, the completion callback is walking freed memory. Schumaker's first patch pins the server for the life of the call:

"Dan Aloni reports that he was able to hit a use-after-free bug if a FREE_STATEID operation gets delayed for whatever reason. Fix this by bumping the refcount of the 'struct nfs_server' object for the duration of the FREE_STATEID so it doesn't get cleaned up from underneath us while operations are still in flight."

That is a classic NFS client lifetime bug. FREE_STATEID is the NFSv4.1/4.2 cleanup RPC that returns a stateid the client no longer needs (after close, delegation return, or lock release). Making it asynchronous was a latency win; it also created a window where unmount, failover, or server-object teardown can race the still-queued RPC. Pinning nfs_server is the same pattern the client already uses for nfs_client on this path (Fixes: 7c1d5fae4a87, "NFSv4: Convert nfs41_free_stateid to use an asynchronous RPC call"). Aloni both reported and tested the fix.

The second patch is the error-path twin. While adding the server pin, Schumaker noticed that a failed nfs_free_stateid_data allocation bailed out with both the client and server refcounts already incremented:

"I noticed that we were immediately exiting this function if the allocation fails, leaving the client and server object refcounts bumped. Fix this by creating a common exit point to clean up dangling references."

That leak is tagged Fixes: 576acc259146 ("nfs4: take a reference on the nfs_client when running FREE_STATEID"). Together the two commits make the async FREE_STATEID path refcount-balanced on both the success path and the allocation-failure path. Without the second patch, the first one would have turned a use-after-free into a quieter nfs_server / nfs_client leak under memory pressure — exactly the kind of "fix the crash, miss the leak" mistake that shows up weeks later as an unmount hang.

A related but distinct race is still outstanding. In mid-July Jia Zhu (ByteDance) replied to the original series that production had hit another nfs_server UAF around state owners, and pointed at his own "pin the superblock for active state owners" patches. That work is not in this pull. Schumaker shipped only the Aloni-tested FREE_STATEID pin, which is the right 7.2-rc call: merge the confirmed crash fix, leave the broader superblock-pinning redesign for later review.

NFSv4.2 listxattr: size-query accounting that oopsed and undercounted

The third commit is Achilles Gaikwad's v2 nfs4_listxattr fix, which closes a 7.2 regression introduced when LSM updated security_inode_listsecurity().

listxattr(path, NULL, 0) is the standard "how big a buffer do I need?" probe. On an NFSv4.2 mount that path went through nfs4_listxattr → security_inode_listsecurity() → nfs4_listxattr_nfs4_user() and oopsed in _copy_from_pages():

"A call to listxattr() with a buffer size of 0 returns the actual size of the buffer needed for a subsequent call. On an NFSv4.2 mount this triggers the following oops: BUG: kernel NULL pointer dereference ... RIP: _copy_from_pages ... nfs4_xattr_alloc_entry → nfs4_xattr_cache_set_list → nfs4_listxattr"

Gaikwad's analysis is the important client-side detail. After f71ece9712b7 ("security,fs,nfs,net: update security_inode_listsecurity() interface"), the LSM hook decrements the remaining size even when the buffer pointer is NULL. In the size-query case left underflowed to a huge size_t, so nfs4_listxattr_nfs4_user() treated the NULL buffer as a real destination and copied into it.

v1 only papered over the NULL deref. v2, posted after Paul Moore's suggestion, fixes the accounting itself:

"security_inode_listsecurity() does not return the number of bytes it added to the list, so the code derived it as 'size - error - left'. That is also wrong in the size-query case: the generic_listxattr() contribution is only subtracted from 'left' when a buffer is present. Thus, the query result comes up short by exactly that contribution (e.g., "system.nfs4_acl" on a mount with ACL support), and a caller that allocates the returned size gets -ERANGE on the subsequent call."

The landed change declares left as ssize_t, measures the security-hook contribution with a scratch copy, and only decrements left when a real buffer is present. That simultaneously stops the oops and makes the size-query result match what the next listxattr() will actually write — including system.nfs4_acl on ACL-enabled NFSv4.2 mounts.

Moore Reviewed-by the v2 and offered to take it via the LSM tree if NFS did not. Schumaker claimed it for the client tree:

"Yeah, we'll send it through the NFS tree."

That promise is what this week's pull fulfills. Moore could not runtime-test the patch at the time because of a separate 7.2-merge-window NFS problem (later chased into an nfsd / SELinux-policy CAP_NET_ADMIN netlink-upcall issue, not a client regression). The review still stands: the accounting math is local to nfs4_listxattr and does not depend on that server-side policy bug.

What this means for the NFS client in 7.2-rc

Two independent crash classes are now on the 7.2-rc branch:

  1. State-recovery lifetime. Async FREE_STATEID can no longer use a struct nfs_server that unmount has already freed, and a failed allocation no longer leaks the client/server pins that the first fix added. Anyone running NFSv4.1/4.2 with frequent close/delegation-return traffic — especially with delayed or retried FREE_STATEID — is the audience.
  2. NFSv4.2 xattr size queries. listxattr(..., NULL, 0) on an NFSv4.2 mount is usable again, and the returned length includes the LSM and system.nfs4_acl contributions so the follow-up call does not get -ERANGE. Backup tools, SELinux userland, and anything that probes xattr size before allocating a buffer are the audience.

No protocol change shipped. No new client feature shipped (Schumaker's separate CB_NOTIFY directory-delegation series, posted the same day, is not in this tag). The pull is exactly what a late-rc client pull should be: small, Fixes:-tagged, confined to nfs4proc.c, and already reviewed.
