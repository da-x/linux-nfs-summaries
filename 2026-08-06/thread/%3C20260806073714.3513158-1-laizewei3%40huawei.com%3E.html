nfsd reclaim-record NULL check restored, but not as a stable crash fix

Summary

This week Huawei's Lai Zewei posted a fifth-revision nfsd patch that restores a missing NULL check in the NFSv4 server's legacy client-tracking recovery path. The change is a small server-side defensive fix, not an NFS client or protocol change. Jeff Layton gave it a Reviewed-by while floating deprecation of the whole legacy tracker; Chuck Lever accepted the code as nominally correct but rejected the crash narrative, the Fixes tag, and the subject line, and asked for a rewritten v6.

The proposed fix

Lai's v5 targets __nfsd4_create_reclaim_record_grace() in fs/nfsd/nfs4recover.c. After commit 4552f4e3f2c9 ("nfsd: change nfs4_client_to_reclaim() to allocate data"), nfs4_client_to_reclaim() itself allocates the reclaim record and can return NULL if alloc_reclaim() fails. The grace-record helper then does an unconditional crp->cr_clp = clp. Lai's three-line change adds the obvious guard:

"nfs4_client_to_reclaim() may return NULL if alloc_reclaim() fails. The caller __nfsd4_create_reclaim_record_grace() then unconditionally dereferences the returned pointer via crp->cr_clp = clp, leading to a null-ptr-deref crash."

"Add a NULL check before assignment. If crp is NULL, just return."

The patch carries a Fixes tag for that allocation-move commit. No changelog from v1–v4 appeared on linux-nfs.

Layton: take the check, start talking about deprecation

Jeff Layton did not fight the NULL check. He treated it as the least-bad local repair:

"I suppose this is the best we can do here."

He then used the review as a broader product note on the code this helper lives in:

"As an aside, it's probably time to start a discussion about (finally) deprecating the legacy client tracking code. We've had it marked as "legacy" for several years now, and the intention was always to eventually get rid of it."

He added Reviewed-by: Jeff Layton <jlayton@kernel.org>. That deprecation aside did not get a follow-up in this thread.

Lever: restore the check, drop the crash story

Chuck Lever first flagged process: v1 through v4 never hit linux-nfs, and this posting has no changelog. Public first posts should be v1, or later revisions should say what changed.

On the code, he agreed the restoration is consistent with the other callers. Commit 4552f4e3f2c9 moved the allocations into nfs4_client_to_reclaim() and stripped this caller's NULL check (and the kfree() that check used to guard). Putting the test back aligns __nfsd4_create_reclaim_record_grace() with load_recdir() and __cld_pipe_inprogress_downcall(), both of which already tolerate a NULL return.

He did not accept the null-ptr-deref as a production crash, and he explicitly said UAF is not in play:

"However, IMO a UAF crash is not reachable. struct nfs4_client_reclaim is just 48 bytes, and a GFP_KERNEL allocation of that size is almost guaranteed to succeed 100% of the time on production systems."

That undercuts the Fixes tag, which would pull the patch into stable:

"The Fixes: tag then asks stable maintainers to backport a fix for it, and I wonder if there's any need to."

He asked for a v6 that (1) describes the change as restoring a check dropped by 4552f4e3f2c9, (2) drops the Fixes tag, (3) states that the NULL return is not reachable from this caller, and (4) says whether the finding came from static analysis or slab fault injection rather than a production oops. He also wanted a more accurate subject: the current one names nfsd4_create_reclaim_record_grace (the function is __nfsd4_create_reclaim_record_grace) and tacks on "in nfs4recover", which the nfsd: prefix already covers. His suggested title:

"nfsd: restore nfs4_client_to_reclaim() error check"

He closed by inviting a counter-argument:

"Do let me know if I've missed something that makes this patch more than a clean-up."

Where it stands

The discussion is a defensive nfsd bug-fix / cleanup in the legacy NFSv4 client-tracking reclaim path, not a protocol change and not NFS client work. By the end of the week the code change itself had one Reviewed-by and maintainer agreement that the NULL check belongs, but no merge: Lever wants v6 recast as restoring a dropped error check, without a stable backport tag, unless Lai can show a reachable production crash. No v6 landed in-window.
