nfsd sparse-warning fixes spark XDR host-endian storage debate

Summary

Overview

This week's thread is a bug-fix series, not a protocol change. Jeff Layton posted a two-patch nfsd cleanup to silence sparse warnings that landed with the directory-delegation / CB_NOTIFY work now sitting in nfsd-next. Patch 2 — a one-line __be32 vs. int type correction in nfsd_lookup_dentry() — was folded immediately. Patch 1, which tried to paper over a host-endian store into an XDR stream with a comment, instead opened a pointed design argument with Chuck Lever about using the XDR buffer as scratch storage. The directory-delegation series stays in nfsd-next; the XDR anti-pattern is deferred to a follow-on series, likely v7.4.

The work is server-side, but it sits on the CB_NOTIFY encoding path that a Linux NFSv4.1 client will consume once directory delegations are enabled. The sparse warning is treated as a canary for a structural encoding problem, not as the real bug.

The patches

Layton's cover letter was brief:

"The first patch should fix the sparse warning that the KTR noticed last week. I also took the opportunity to add a comment over the weird xdr stream (ab)use we're doing there. The second patch just fixes up a sparse warning that I noticed."

Patch 1 (nfsd: fix type mismatch and explain host-endian xdr buffer usage) touches fs/nfsd/nfs4xdr.c. Sparse had flagged a type mismatch in the directory-event notification encoder. The Fixes: tag points at 4b64b811f368 ("nfsd: add notification handlers for dir events"), reported by the kernel test robot. Layton also added a comment describing the non-standard XDR usage: the encoder "steals" a few 32-bit words from the stream buffer to hold host-endian bitmap fields that are later encoded for real.

Patch 2 (nfsd: fix nfserr type in nfsd_lookup_dentry()) is a one-line change in fs/nfsd/vfs.c. Both nfsd_lookup_dentry() and nfsd_cross_mnt() return __be32; the local nfserr variable had the wrong type after cf78c5a7d742 ("nfsd: move check_nfsd_access() call into nfsd_cross_mnt()").

Chuck Lever folded patch 2 into the original nfsd_cross_mnt() commit the same afternoon. That half of the series is done.

The XDR-buffer fight

Patch 1 did not land as written. Lever's first review rejected the "steal a few words" comment as an explanation of a design he still did not accept:

"I still don't understand what's going on. "Steal a few words to hold it" sounds like you're trying to avoid a kmalloc call. Is this code reserving space in the XDR stream, or isn't it? If it is, then accessing those bytes has to be done with a big-endian pointer, the same way it is done at every other xdr_reserve_space() call site. Storing host-order bytes that are not part of an opaque into an XDR stream is just... wrong."

If this was the usual reserve-and-backfill dance, he wanted it spelled the way every other encoder does it, "so us poor human readers can recognize that's what's going on."

Layton pushed back: the three 32-bit words are a private scratch area for host-endian bitmap fields that get encoded later. Nothing else touches that slice, and the buffer has room. Separate allocations would mean one bitmap per notify_entry4, with no obvious place to track and free them.

Lever then laid out three objections in a longer reply:

  1. Technical debt. "It just isn't obvious what's going on, it needs a four-line comment to explain it, and it opens the door to people copy-pasting it to other encoders."
  2. Ephemeral stream. Callers have to keep an xdr_stream pointer valid for the stream's lifetime; parking host data there is not a contract the XDR API offers.
  3. SUNRPC API assumptions. "Yes, we have a sordid history of grabbing a piece of the xdr_buf's tail iov for temporary storage. That doesn't make it wise to do," and it will hurt if the tail becomes a page instead of kmalloc'd memory, or if the encoder is converted to xdrgen.

His verdict:

"So what you've done is fine for operational prototype code, but not something we can carry forward as production code. The sparse warning is a canary, it's not the actual structural problem."

He suggested the server's existing chain of temporary allocations, freed when the COMPOUND is released, as a model the callback client could copy.

Will directory delegations be dropped?

Layton took that as a possible revert:

"I had no idea this practice was suddenly forbidden. That has certainly not been communicated to me in any of the previous review rounds over the last couple of years."

And, more pointedly:

"Does this mean you intend to drop dir delegation series again? Allocating from the xdr stream in order to hold host-endian fields is done in several places in this code. Reworking that will be a substantial effort."

Lever said no. He has been removing this anti-pattern for some time and had not seen new instances until now; it simply had not come up in earlier review rounds. On the series itself:

"No. It's deep in nfsd-next now, and this is a long-term issue, not an immediate on-the-wire behavioral problem or a vulnerability."

That is the operational conclusion of the week: CB_NOTIFY directory-delegation support stays queued. The host-endian XDR scratch is accepted as debt, not as a merge blocker.

Follow-on plan

Layton first offered an LLM-drafted rewrite, calling it "a bit invasive" and needing more testing, to be sent as a follow-on to the CB_NOTIFY patches. The next day he committed to a separate series:

"Ok, I'll send a separate series on top of this that should address your concerns. We may be able to get away with stack allocations for some of these, and for the others we can just add a separate kmalloc'ed set of buffers or something. That'll probably be v7.4 material at the soonest though."

Significance for NFS client development

Directory delegations are a client-visible NFSv4.1 feature (RFC 8881bis GET_DIR_DELEGATION / CB_NOTIFY). The Linux client cannot usefully take a directory delegation until the server's CB_NOTIFY encoder is trustworthy. This week's argument is about that encoder's internals:

  • On-the-wire behavior is unchanged. Lever was explicit that this is not a protocol bug or a vulnerability. Clients talking to nfsd-next should see the same CB_NOTIFY payloads they saw last week.
  • The sparse warning is the wrong layer. Casting around a host-endian store into an XDR buffer silences the checker without fixing the lifetime and endianness contract. A client-side decoder that assumes well-formed, big-endian XDR is only as safe as the server's encoder remaining disciplined.
  • xdrgen and buffer-layout changes. Lever's third objection is the one that matters for the client stack long-term: if nfsd later switches the callback encoder to xdrgen, or if SUNRPC stops guaranteeing a kmalloc'd tail iov, any host-endian scratch parked in that buffer becomes a landmine. Cleaning it up before v7.4 keeps the callback path from ossifying around an anti-pattern the client (and pynfs) already exercise.
  • Allocation model for notify bitmaps. Each notify_entry4 carries its own bitmap. Layton's concern about tracking multiple allocations is real; Lever pointed at nfsd's COMPOUND-scoped temp chain as the existing pattern. Whatever lands in the follow-on series will determine how CB_NOTIFY encoding scales when a client holds many directory delegations and the server has to encode bursts of ADD/REMOVE/RENAME notifications.

Status

  • Patch 2: folded into nfsd: move check_nfsd_access() call into nfsd_cross_mnt().
  • Patch 1: not accepted as a comment-only sparse fix. The underlying host-endian XDR scratch stays in nfsd-next as known technical debt.
  • Directory-delegation / CB_NOTIFY series: remains in nfsd-next; not being dropped.
  • Next step: Layton to post a follow-on series replacing XDR-buffer scratch with stack or kmalloc'd bitmaps, targeted at v7.4 at the earliest.

No client-side patches were posted in this thread. The client impact is indirect: the server CB_NOTIFY path that directory-delegation clients will depend on is staying, with a promised encoder cleanup after the current merge window.
