First DESY ping on loosely coupled flexfiles DS series, still awaiting review

Summary

NFSv4/flexfiles loosely coupled DS series draws a first (empty) reply after a month

Classification

This remains a new feature plus bug fix thread in NFS client development. Jeuk Kim's July 8 two-patch series implements RFC 8435 loosely coupled flexfiles data-server behavior the client had been ignoring, and it plugs a latent NULL-dereference / lease-renewal busy-loop on NFSv4.0 data servers. There is no wire-protocol change.

Brief bridge from July 8

Kim posted PATCH 0/2 with a compact diagnosis:

"RFC 8435 allows a flexfiles data server to be loosely coupled, i.e. an NFS server that does not advertise EXCHGID4_FLAG_USE_PNFS_DS via EXCHANGE_ID. The client currently ignores the ffdv_tightly_coupled flag and treats every DS as tightly coupled, so NFSv4.1+ I/O to a loosely coupled DS fails during DS setup."

Patch 1/2 is the crash-class client bug fix (Fixes: a7878ca14008). Two NFSv4 paths assume a DS client always has a session; a v4.0 DS does not (clp->cl_session is NULL; it uses clp->cl_slot_tbl):

"nfs4_init_ds_session() dereferences clp->cl_session->session_state while seeding the DS lease. It also only seeds cl_lease_time when NFS4_SESSION_INITING is set; without a session that never happens, so cl_lease_time stays 0 and nfs4_renew_state() busy-loops, requeuing every 5 seconds."

The same patch also stops ff_layout_async_handle_error_v4() from walking clp->cl_session->fc_slot_table on every DS I/O error, falling back to the v4.0 transport slot table.

Patch 2/2 is the RFC 8435 feature: thread ds_versions[0].tightly_coupled from the flexfiles driver down to the DS connect path, and when it is false skip both NFS_CS_PNFS (so EXCHANGE_ID is not sent with EXCHGID4_FLAG_USE_PNFS_DS) and the subsequent is_ds_client() -ENODEV check. Kim's conceptual line is the one that matters for client topology:

"A loosely coupled DS is just a normal NFS server and does not act in the pNFS DS role, so the client must not require it to advertise that role."

The file layout driver always passes true, so the behavior change is flexfiles-specific. Together the two patches cover the three documented DS topologies: tightly coupled v4.1+, loosely coupled v4.1+, and v4.0 (implicitly loosely coupled, since there is no EXCHANGE_ID).

No reviewer had spoken by the July 9 window close.

This week: first external voice, no technical content in the archive

Nearly four weeks of silence ended on August 6, when Tigran Mkrtchyan (DESY) replied to the cover letter. That is the only in-window message.

The archived mail is a Zimbra-generated reply (JavaMail.zimbra@desy.de) whose body is empty in the linux-nfs archive: no Reviewed-by, no Acked-by, no questions about the tightly_coupled plumbing, and no comment on the v4.0 Fixes: tag or a possible Cc: stable. Whatever Mkrtchyan intended to say did not survive ingest, so this week's activity cannot be read as a technical review.

The DESY address is still noteworthy for client work. Mkrtchyan is associated with dCache, a deployment style that often treats data servers as ordinary NFS servers rather than pNFS-role DSes — exactly the loosely coupled topology Patch 2 is trying to unblock. Interest from that camp is a signal that the RFC 8435 gap is not theoretical, but it is not a substitute for code review.

Status of the NFS client work

Nothing in the series has changed this week:

  • No v2, no incremental diffs, no maintainer mail from Trond Myklebust or Anna Schumaker.
  • Patch 1's NULL-deref / nfs4_renew_state() busy-loop fix is still unacked, still carrying Fixes: a7878ca14008 and still the more urgent of the two changes for anyone already running NFSv4.0 flexfiles data servers.
  • Patch 2's tightly_coupled threading through nfs4_set_ds_client() / nfs4_init_ds_session() / pnfs_nfs.c is likewise unreviewed.
  • Neither patch is applied.

Conclusion

The thread has moved from "posted, no replies" to "one external ping, still no review." The client-side work — a crash fix on the v4.0 DS session-less path plus RFC 8435 loosely coupled DS setup — is unchanged and still waiting on NFS client maintainers. Until someone actually comments on the code, the series remains an unmerged, unacked pair sitting on the list.
