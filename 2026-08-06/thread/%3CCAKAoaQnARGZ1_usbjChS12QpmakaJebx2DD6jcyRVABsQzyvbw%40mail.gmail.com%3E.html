ms-nfs41-client Aug 1 Drop: Idmapper, Linux 7.2 Casefold, Copy Offload

Summary

ms-nfs41-client 2026-08-01 Test Binaries: Idmapper, Linux 7.2 Case-Insensitivity, and Copy Offload

This week's activity on the thread was a single cross-post: Martin Wege forwarded Roland Mainz's 1 August announcement of new test binaries for the open-source ms-nfs41-client NFSv4.1/NFSv4.2 Windows filesystem driver. There were no replies on linux-nfs in the week ending 2026-08-06.

This is not a Linux kernel NFS client patch, protocol change, or in-tree bug fix. It is a recurring feature announcement and interoperability request aimed at Linux NFS server maintainers: please exercise the Windows client against current Linux nfsd.

Call for Linux nfsd interoperability

Wege asked the Linux NFS community to test the drop against current servers:

"Please test the binaries. The NFSv4.2/4.1 client is for Windows 10/11 ARM64+AMD64+x86 and Windows Server 2019+2022+2025/AMD64, but Interoperability feedback with NFSv4.1/NFSv4.2 servers based on Linux 6.6+ LTS and 6.19+/7.2 would be great."

That 7.2 target is new relative to earlier 2026 cross-posts, which asked for 6.19+/7.0 coverage. The binaries are built from kofemann/ms-nfs41-client commit #a2eb45f0ecb915260bc47dbcc783bf80771a815e.

Wege highlighted the features he considers most relevant to Linux server operators:

"New idmapper which maps any NFS user/group to any Windows user/group, support for Linux 7.2 case-insensitive NFS filesystems, Windows Alternate Streams (Win32 streams) support, xcopy.exe/cmd.exe copy/MS Explorer file copy acceleration via NFS server side copies, and copy-by-block-cloning are IMO the most interesting new features."

He also noted a deployment change for x86-64 Windows hosts: the kernel module can now be loaded without kernel testsigning mode by flipping use_secureboot=false to use_secureboot=true in /sbin/msnfs41client and running the project's opensource_driver_bootbypass.bash helper after install.

Bug reports and test results are directed to the project's SourceForge list (ms-nfs41-client-devel), not to linux-nfs itself.

Features that exercise Linux NFSv4.2 servers

Mainz's changelog is a Windows-client feature drop, but several items are concrete tests of Linux nfsd NFSv4.2 operations, attributes, and casefold reporting.

Case-insensitive Linux exports (Linux >= 7.1 / 7.2)

The release adds "more fixes for case-insensitive NFS filesystems," requiring:

  • FreeBSD nfsd >= 16.0, or
  • Linux NFS server >= 7.1, or
  • Windows Server NFS exporting a case-insensitive filesystem.

Wege separately called out "support for Linux 7.2 case-insensitive NFS filesystems." That is the Windows-client counterpart of the ongoing Linux work to expose VFS casefold/case-preserving flags so nfsd can report FATTR4_WORD0_CASE_INSENSITIVE accurately — a hard requirement for Windows applications.

Server-side copy and block cloning

The client implements Windows offload/copy ioctls on top of NFSv4.2:

  • FSCTL_OFFLOAD_READ / FSCTL_OFFLOAD_WRITE for server-side NFSv4.2 COPY, used by Windows 10 xcopy, Explorer, and similar copy paths.
  • FSCTL_DUPLICATE_EXTENTS_TO_FILE so Windows 11 CopyFile2() users (cmd.exe copy, xcopy.exe, etc.) can copy via block cloning. This requires an NFSv4.2 server with { CLONE, SEEK, DEALLOCATE } exporting a clone-capable filesystem (btrfs, xfs). Sparse files are cloned correctly.

These are the same COPY/CLONE/SEEK/DEALLOCATE paths Linux nfsd already exposes; the ask is whether they remain interoperable when the initiator is this Windows driver rather than a Linux NFS client.

Sparse files and Ganesha

Sparse-file support still requires NFSv4.2 { SEEK, ALLOCATE, DEALLOCATE } plus FATTR4_WORD1_SPACE_USED, including hole/data range enumeration and hole punching (fsutil sparse queryrange). Mainz records a bug fix for probing sparse files against nfs-ganesha, which remains the userspace Linux server of interest.

Named attributes: ADS and EAs

Win32 Alternate Data Streams and improved Extended Attributes are mapped to NFS named attributes. The listed servers that provide that (Solaris >= 11.4, Illumos, FreeBSD >= 15.0) do not include Linux nfsd. For Linux operators this is mainly a reminder that ADS/EA workloads still depend on named-attribute support that Linux nfsd does not currently advertise the same way.

Identity mapping against Linux uid/gid/owner strings

The new per-mount idmapper maps any NFS { uid, gid, fattr4_owner, fattr4_owner_group } to any Windows account, including localized builtin names. Mapping is a shell script (cygwin_idmapper.ksh) rather than compiled policy:

"Idmapping itself is done with a shell script (for maximum flexibility, as attemps to handle this with builtin code could NOT cover all compliciated site setups, including Windows localised account names, and NFS clients which have to connect to multiple different sites with completely different NFS server account setups)"

A new winfsinfo subcommand, fsctlnfs41queryidmapinfo, dumps the mapped Win32 names, Cygwin/UWIN/SFU uid/gid, and NFSv4 owner strings for a file. Unicode owner/group names (e.g. German umlauts) are supported. This is the Windows-side counterpart of Linux nfsidmap/fattr4_owner handling and is the most likely source of "it works on Linux clients, fails on Windows" identity bugs.

Other client-side changes (context for testers)

Less directly about Linux nfsd, but useful when reproducing Windows-client bugs:

  • Experimental UNC tag numbers (nfs_mount -o unctagnum=4000) for a unique UNC path and a separate NFS server connection.
  • UNC path format changed to <hostname>@<protocol>@<port> (e.g. ournfsserver@NFS@2049) to leave room for RDMA/TLS.
  • Referrals now honor non-default (non-TCP/2049) ports.
  • Windows "SRVOpen collapsing" shares one NFS file handle across opens that differ only in access/permission bits, cutting OPEN/CLOSE round trips.
  • ACL can be set at create time; ECP QUERY_ON_CREATE / QoCFileStatInformation / QoCFileLxInformation are implemented.
  • sec=none; nfs_globalmount for machine-wide mounts; nfsclientdctl for runtime daemon knobs.
  • Native Windows 11 ARM64 kernel module and userland; FreeBSD 16.0 nfsd support; ReactOS-on-NFS build fixes.
  • Compatibility claims: MariaDB, Office 2016, Visual Studio 2022, Cygwin svn, and Windows Git.

Conclusions

No technical debate occurred on linux-nfs this week; the thread is an informational cross-post. For Linux NFS client development there is nothing to merge. For Linux NFS server development the drop is a live interoperability matrix:

  1. Case-insensitive exports on Linux >= 7.1/7.2 (FATTR4_WORD0_CASE_INSENSITIVE).
  2. NFSv4.2 COPY, CLONE, SEEK, ALLOCATE, DEALLOCATE, and SPACE_USED against btrfs/xfs (and Ganesha sparse-file probing).
  3. fattr4_owner / fattr4_owner_group and uid/gid mapping from a Windows initiator with a fully custom idmapper.

Feedback is expected on ms-nfs41-client-devel, not as kernel patches on this list.
