Trond flags DIO extract helper oops and swap-over-NFS refcount hole

Summary

Three weeks after v3 of Pranjal Shrivastava's NFS Direct I/O modernization series landed, Linux NFS client maintainer Trond Myklebust finally walked patch 5/5 — the new nfs_direct_extract_pages() helper — and found two real client-side bugs that Hellwig's earlier Reviewed-by had not caught. Shrivastava acknowledged both the same afternoon and sketched the v5 fix. This remains NFS client plumbing (a refactor with an embedded pin-lifetime bug fix), not a protocol change.

Brief bridge from prior weeks

v3 (cover) dropped the stalled folio conversion and kept five patches: pin-aware nfs_page, wb_nr_pinned tracking, a bulk nfs_release_request_list helper, the iov_iter_extract_pages() migration that stops unpinning pages immediately after request creation, and the shared extract helper that unifies the read and write schedule_iovec paths. The week of 20 July brought Christoph Hellwig Reviewed-by on the two functional DIO patches and Shivaji Kant Reviewed-by on the helpers; Shrivastava promised a quick v4 for style nits. That v4 never appeared. The series then sat quiet until this week.

Maintainer review: two bugs in the extract helper

On 5 August, Trond Myklebust replied directly to patch 5/5 with two pointed comments on the error path.

The first is a classic mixed-error-code hole. The helper walks extracted pages, creates nfs_page requests, and on failure does iov_iter_revert(iter, result - bytes). If nfs_page_create_from_page() fails, bytes is assigned PTR_ERR(req) — a negative errno — so the revert arithmetic is not a byte count at all:

"Oopsable if bytes == PTR_ERR(req)" — Myklebust

The second is a swap-over-NFS refcount bug in the leftover-page cleanup. After the extract-API migration in patch 4, pages that are not GUP-pinned (the swap-over-NFS path sets pinned = false) never took a get_page() ref. The existing nfs_direct_release_pages() still put_page()s them when pinned is false:

"See what happens above with swap over NFS (which sets pinned = false)." — Myklebust

That is an important client-side finding: the same extract model that fixes premature unpinning of user DIO pages would, on the error path, drop a reference the swap path never held.

Author response: separate err, unpin-only cleanup, v5 incoming

Shrivastava acked both issues within two hours and proposed concrete code. Errors will no longer be stuffed into the bytes accumulator:

"Ack. I'll catch errors in a separate variable something like:"

req = nfs_page_create_from_page(...);
if (IS_ERR(req)) {
    err = PTR_ERR(req);
    break;
}
...
bytes += req_len;
...
return bytes ? bytes : err;

— Shrivastava

On the swap path he confirmed the diagnosis — "we never got a ref (after patch 4) but we'll call put_page() if pinned == false" — and will shrink nfs_direct_release_pages() in patch 4 so leftover pages are only unpinned, never put_page()'d:

static void nfs_direct_release_pages(struct page **pages, unsigned int npages,
                                     bool pinned)
{
        if (pinned)
                unpin_user_pages(pages, npages);
}

— Shrivastava

He closed by asking the maintainer, "Sounds good for v5?" — skipping the v4 that was promised for Hellwig's style nits and folding these two functional fixes into the next posting.

Where the series stands

This week's exchange is the first maintainer-level review of the DIO extract helper. The series is still a client-side refactor plus bug-fix stack preparing nfs_page for pin-based GUP (and, later, PCI P2PDMA); folio conversion and ITER_ALLOW_P2PDMA remain follow-ups. Hellwig's Reviewed-by on patches 4/5 and 5/5 now has to be re-earned against the oopsable revert and the swap-over-NFS put-without-get. No merge ack has been given. Watch for v5, and for whether Myklebust is satisfied that the unpin-only cleanup is correct for every non-pinned extract source, not just swap.

Bottom line: the DIO pin-lifetime rewrite is not merge-ready. Trond found an oopsable error path and a swap-over-NFS refcount hole in the new extract helper; Shrivastava has a v5 plan, but the patches are not on the list yet.
