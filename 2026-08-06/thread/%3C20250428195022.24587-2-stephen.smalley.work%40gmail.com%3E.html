NFSv4.2 listxattr regression fix queued for Linus via NFS tree

Summary

NFSv4.2 Client listxattr Fix: Anna Takes Gaikwad's Patch to Linus

This week the long-running security_inode_listsecurity() fallout on the NFSv4.2 client moved from diagnosis to a merge-path decision. The work is a bug fix for a client-side listxattr regression, not a new feature or protocol change. After LSM maintainer Paul Moore pressed for an NFS ACK before v7.2 ships, NFS client maintainer Anna Schumaker confirmed she already had Achilles Gaikwad's accounting patch in a private test branch, moved it onto her public linux-next tree, and will send it to Linus in the next few days.

Prior context (brief)

Stephen Smalley's LSM hook cleanup, forward-ported by Moore and merged into lsm/dev in early May, taught security_inode_listsecurity() to use xattr_list_one() and adapted fs/nfs/nfs4proc.c to the new signature. Last week Chuck Lever reported that the change wedges an NFSv4.2 client under fstests: a size-query listxattr(2) underflows an unsigned remaining-size accumulator, _copy_from_pages faults on a NULL buffer while the xattr listcache spinlock is held, and the orphaned lock turns a NULL deref into a machine-wide soft lockup in the shrinker. Lever pointed at Gaikwad's 7 July nfs4_listxattr accounting patch as the intended fix and left the merge path to LSM and NFS maintainers. Moore had already Reviewed-by'd that patch and was willing to send it via the LSM tree, but wanted an NFS ACK and Tested-by.

Moore's deadline: ACK it, or LSM sends it anyway

On 31 July, Paul Moore pinged the NFS maintainers by name — Chuck, Anna, Trond, Jeff — and made the calendar pressure explicit:

"Chuck, Anna, Trond, Jeff - can someone ACK Achilles's patch below or suggest what changes might be necessary? There is a known regression (see the existing mails) and we need to fix this before v7.2 ships."

He offered to carry the patch himself, but only as a last resort:

"I'm happy to send this up to Linus if you would prefer, but I would really like to see an ACK from someone on the NFS side. If I don't see any comments be early next week I'll send this up to Linus via the LSM tree."

The linked target remains Gaikwad's client-only change: declare left as ssize_t, measure security-hook consumption with a scratch copy, and only decrement remaining size when a buffer is present. That is the NFS-side hardening that stops xattr_list_one() from wrapping the unsigned accumulator on a NULL-buffer size query, which is what sent nfs4_xattr_cache_list() into _copy_from_pages with a NULL destination while the listcache spinlock was held.

Lever declines to ACK a client patch

Chuck Lever answered within the hour and drew the server/client line:

"Since Achilles' patch is client-side, I shouldn't Ack it."

He also noted the patch was not yet visible in the NFS client's public tree:

"I don't see this patch in Anna's tree either. A response from the NFS maintainers would be helpful."

That is the practical bottleneck Moore had been circling: the LSM tree can carry an NFS-only fix in a pinch, but the people who own fs/nfs/nfs4proc.c had not yet said they would take it.

Schumaker: it was already in a test branch

Anna Schumaker closed the gap twenty minutes later. The patch had not been missing so much as unpublished:

"Looks like I did have it in a branch with other commits for testing, but I never pushed it out. I've moved it over to my public linux-next and will pass it along to Linus in the next few days."

That is the NFS-side ACK Moore asked for, in the form of an actual merge commitment rather than a Reviewed-by tag. The client maintainer is taking Gaikwad's accounting fix through the NFS tree, which is the path Moore preferred all along because the patch "only touches NFS code."

Moore treated that as the end of the LSM-tree fallback:

"Perfect, thanks Anna!"

Conclusions this week

  • Classification remains a client bug fix: Gaikwad's nfs4_listxattr remaining-size accounting change, written to stop the May LSM xattr_list_one() interface cleanup from NULL-deref'ing and orphaning the NFSv4 xattr listcache spinlock on a size-query listxattr.
  • The merge-path question from last week is settled. LSM will not send the patch via lsm/dev. Anna has moved it onto her public linux-next tree and will send it to Linus in the next few days, targeting v7.2.
  • Chuck correctly declined to ACK a client-only patch; the needed signal was from the NFS client maintainer, and it arrived the same afternoon.
  • No one this week reopened Lever's earlier design alternatives (changing xattr_list_one() to leave remaining size alone on a NULL buffer, or hardening nfs4_xattr_cache_list() against a NULL buffer). The chosen fix stays NFS-local.
  • A public Tested-by on Lever's kdevops NFSv4.2 + SELinux + fstests setup still has not landed in-thread, but Schumaker's note that the patch was already in a testing branch implies client-side validation preceded the linux-next push.

The outstanding item is no longer "who merges it," but whether the linux-next copy survives to Linus before v7.2 and whether Lever's fstests guests stay clean once it is there.
