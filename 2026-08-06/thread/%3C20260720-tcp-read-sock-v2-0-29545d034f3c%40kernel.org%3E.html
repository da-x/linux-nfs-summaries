kTLS read_sock needs a documented errno contract

Summary

Two days after netdev NACKed read_sock_rectype, the thread this week is no longer arguing for that proto_ops method. Chuck Lever and kTLS maintainer Sabrina Dubroca instead spend 31 July picking apart the existing ->read_sock contract — the one NFSD svcsock and a later NFS client xprtsock conversion would have to live with if control records stay a fallback path.

This remains a new kernel networking API discussion plus a related kTLS bug-fix / API-hygiene thread, not a protocol change. The on-the-wire TLS/RPC framing is untouched. What is at stake for NFS is still how in-kernel TCP consumers see KeyUpdate and fatal Alerts once kTLS is active, without leaking control bytes into page-cache receive pages.

Brief recap of prior weeks

v2 of Lever's six-patch net-next series added read_sock_rectype to struct proto_ops, implemented it on the kTLS software path, converted NFSD svcsock, and bounded consecutive no-data records in tls_sw_read_sock(). The no-data cap was split out to a net prerequisite as a standalone DoS fix for empty TLS 1.3 data records. Last week Jakub Kicinski rejected the new proto_ops hook as a TLS-only one-off; Dubroca called a TLS-specific argument in a generic API "quite ugly"; Lever conceded. Kicinski's setsockopt sketch then collapsed into behavior kTLS already has: recvmsg without CMSG and read_sock already error out if the next record is control. That is the claim this week's two messages answer.

Lever: -EINVAL is not a contract

Replying to Kicinski's "we already constrain control records", Lever first restated the SUNRPC preference that motivated the series:

"But the “recover the control type with a separate operation” is strictly better than “pass a CMSG buffer to every I/O operation just in case” ;-)"

Then he corrected the "already constrained" claim. There is no API contract for ->read_sock. The TLS implementation happens to return -EINVAL for two unrelated reasons:

  • net/tls/tls_sw.c:2068-2072 — entry gate: sk_psock_get(sk) is non-NULL, so the socket is under sockmap/BPF. Drop the ref and refuse before acquiring the reader.
  • net/tls/tls_sw.c:2111-2115 — per-record: tlm->control != TLS_RECORD_TYPE_DATA. The record is requeued rather than consumed.

"As far as I can tell, no other socket provider that implements read_sock will return -EINVAL. But this isn’t a documented guarantee that a socket consumer can depend on, currently."

That is the NFS-relevant bug in this week's mail. A kTLS-enabled NFS client (or NFSD) that treats -EINVAL as "control record pending, fall back to recvmsg+CMSG" cannot tell that condition from "this socket is under sockmap." Mixing those two failures is exactly the kind of exception processing Lever has been trying to keep off the normal I/O path. His concrete ask:

"What would make this just a little friendlier is having distinct errnos for these two conditions, and a kdoc API contract that documents them."

Dubroca: document read_sock, kill the leftover, maybe a new errno

Dubroca agreed on the documentation, and went further: the first -EINVAL is not even a real condition anymore.

"You can ignore this one, it's just a leftover that 79511603a65b ("tls: remove dead sockmap (psock) handling from the SW path") missed. I'll get back to cleaning all this up once I'm not drowning in reviews (I'm sure being on holidays next week will help with that)."

That is a latent kTLS bug fix: dead sockmap/psock handling still sitting in tls_sw_read_sock() after the SW-path cleanup, returning a confusing -EINVAL that no consumer should have to interpret. Dubroca owns that cleanup; it is not in this series.

On the remaining control-record -EINVAL, she +1'd a kdoc contract and admitted the current read_sock semantics are opaque even to the kTLS maintainer:

"+1 on the API contract doc. I have no idea what read_actor does to desc, how that relates to the returned value, and if it modifies the skb it gets in any way. That makes it hard to figure out the correct behavior for tls_sw_read_sock()."

She floated two design options that would actually give SUNRPC something to code against:

"Maybe we should even come up with some new internal errno (like one of the >=512 in include/linux/errno.h). And maybe this -errno return should be desc->error instead. I really don't know how read_sock is supposed to behave."

She did not concede Lever's "separate operation is strictly better" line. On that she only wrote:

"That's up to every user to decide :)"

So the CMSG-on-every-I/O vs. recover-control-type-separately argument is still open. What is no longer open is whether consumers can treat today's -EINVAL as a stable signal: they cannot, until someone writes the contract.

What this means for NFS client development

Nothing this week touches xprtsock directly. The client conversion remains a follow-up that was going to copy the NFSD svcsock template. The week's result still lands on the client path:

  • Last week's NACK of read_sock_rectype stands. There is still no first-class control-record delivery for kernel read_sock consumers.
  • Lever is now arguing for a documented read_sock error contract as the minimum viable alternative: distinct errnos so "next record is not DATA" is not the same code as "socket is under sockmap," plus kdoc so NFSD and the NFS client can depend on it.
  • Dubroca agrees the contract is missing and has queued a cleanup of the leftover sockmap -EINVAL. She is also willing to invent a new internal errno (>= 512) or route the failure through desc->error instead of the read_sock return value. Either of those would be the hook a future xprtsock read_sock loop would use to stop draining DATA and issue one recvmsg+CMSG into a side buffer — the dance that avoids leaking Alert/KeyUpdate bytes into page-cache receive pages.
  • Until that contract exists, a kTLS-enabled NFS client still cannot distinguish "control record queued" from a generic -EINVAL, and still cannot handle KeyUpdate or fatal Alerts on read_sock without the CMSG fallback that mixes control payload into RPC message memory.

Status at week close

The series is still under redesign, not merged. Consensus in-window:

  • read_sock_rectype as posted remains rejected. No v3, no replacement API, no measurements of the three-way comparison Dubroca asked for last week.
  • Existing kTLS read_sock does requeue non-DATA records and return -EINVAL, but that is an implementation accident, not a documented guarantee. Lever wants distinct errnos and kdoc; Dubroca wants the same plus possibly a new internal errno or desc->error.
  • The sockmap/psock -EINVAL at tls_sw.c:2068 is dead code leftover from 79511603a65b. Dubroca will clean it up; she is on holiday the following week.
  • The empty-record DoS bound remains the only piece moving independently, on net.
  • NFSD svcsock conversion and the planned NFS client xprtsock conversion still cannot land.

The practical takeaway for NFS client development this week: the lock-pinning fix is still the only forward-moving piece. The control-record path has shifted from "new proto_ops method" to "please document read_sock so we can even write the fallback correctly," and that documentation does not exist yet.
