nfsd: Restore traditional thread count reporting in /proc and netlink interfaces

Summary

nfsd: Report Requested Maximum Threads Instead of Running Count

Summary

This week, Jeff Layton submitted a kernel-side bug fix patch to restore traditional reporting behavior for NFS server thread counts in the netlink and /proc interfaces. The change addresses a regression introduced by the recent addition of dynamic threading support, where these interfaces began reporting the current number of running threads rather than the configured maximum — a departure from historical behavior that left administrators with no reliable way to determine the actual thread configuration.

Bridge from Prior Weeks

In recent weeks, the NFS community has been actively developing and integrating dynamic threading support for nfsd:

  • The kernel-side dynamic threading feature (allowing threads to scale between a minimum and maximum based on workload) was merged into Chuck Lever's tree.
  • The user-space nfs-utils tooling received a min-threads parameter, committed to nfs-utils 2.8.5-rc3 as summarized previously.
  • A follow-up compatibility fix was submitted to handle older kernels lacking min-threads support as summarized in a related thread this week.

This thread continues that effort by fixing the reporting semantics on the kernel side.

This Week's Activity

The Patch: Restoring Traditional Reporting Behavior

On February 4, Jeff Layton submitted a single-patch fix that modifies both the netlink and /proc interfaces to report the requested maximum number of threads instead of the number currently running. In his commit message, he explained:

"The current netlink and /proc interfaces deviate from their traditional values when dynamic threading is enabled, and there is currently no way to know what the current setting is. This patch brings the reporting back in line with traditional behavior."

The patch carries a Fixes: tag referencing the commit that introduced the regression:

"Fixes: d8316b837c2c ("nfsd: add controls to set the minimum number of threads per pool")"

Layton also noted his reasoning for not adding extra netlink attributes at this time:

"We could also consider adding netlink attributes to report the number of running threads, but you can get that info from ps too."

Review: Documentation Updates Needed

Chuck Lever responded on February 4 with an AI-assisted code review, pointing out that three documentation locations need updating to reflect the new semantics:

"The documentation should be updated to reflect that these interfaces now report the configured maximum threads rather than running threads:

  1. Documentation/netlink/specs/nfsd.yaml line 168 - threads-get is documented as 'get the number of running threads' but now returns the configured maximum
  2. fs/nfsd/nfsctl.c lines 387-405 - The write_threads() docstring says it reports 'the number of running NFSD threads' but now reports the configured maximum
  3. fs/nfsd/nfsctl.c lines 1666-1673 - The nfsd_nl_threads_get_doit() docstring says 'get the number of running threads'"

Jeff Layton agreed to address this in v2:

"Ok, I'll do that for v2."

User Concern: Observability of Thread Counts

Mike Owen raised a practical concern on February 5, noting that he currently relies on /proc/net/rpc/nfsd to monitor thread counts:

"I currently rely on: '/proc/net/rpc/nfsd' to retrieve the current number of threads via 'th'. After the various patches to introduce dynamic threading, where in the future, would a user retrieve the currently set min, max and actual running thread count reliably? Would be lovely if the man page indicated this."

Jeff Layton clarified the available interfaces:

"You won't be able to get to the min-threads setting from /proc. That's only available via netlink. If you enable dynamic threading (via netlink), then the traditional 'th' count in /proc currently shows you the number of running threads. If this patch is applied, it'll show you the requested maximum instead."

He added:

"So, with this patch applied you can query both the min and max number of threads via netlink. We don't yet have an interface to query the number of threads currently running. In principle, you can get that info from 'ps', but we could add that to the netlink interface if someone can make a good use-case for it."

Chuck Lever concisely confirmed the practical workaround:

"I use pgrep -c nfsd"

Classification

This discussion centers on a bug fix in the NFS server kernel code. Specifically, it corrects a regression in the reporting semantics of the netlink and /proc interfaces introduced by the dynamic threading feature, restoring them to their traditional behavior of reporting the configured maximum thread count rather than the fluctuating number of currently running threads.

Significance for NFS Server Development

This fix is important for several reasons:

  1. Interface consistency: The change restores backward-compatible semantics for tools and scripts that rely on /proc/net/rpc/nfsd and netlink to query NFS server configuration. Previously, the reported thread count would fluctuate with workload, making it impossible to determine the actual configured maximum.

  2. Observability trade-offs: The discussion reveals an ongoing tension between what information is exposed through which interfaces. The /proc interface will report the maximum (traditional behavior), min-threads is only available via netlink, and the current running thread count has no dedicated kernel interface — administrators must use ps or pgrep -c nfsd as a workaround.

  3. Documentation debt: Chuck Lever's review highlighted that documentation across three locations (netlink spec YAML, and two C docstrings) needs updating to reflect the corrected semantics — a reminder that behavioral changes require corresponding documentation updates.

  4. Future enhancement opportunity: Layton left the door open for adding a netlink attribute to report currently running threads if a compelling use case emerges, suggesting this area may see further refinement.

Conclusion

The patch restores traditional reporting behavior for NFS server thread counts, ensuring that both /proc and netlink interfaces report the configured maximum rather than the volatile running count. Documentation updates are planned for v2. The community has identified pgrep -c nfsd as a practical workaround for monitoring actual running threads, while Layton remains open to adding dedicated kernel support for this metric if demand justifies it.
