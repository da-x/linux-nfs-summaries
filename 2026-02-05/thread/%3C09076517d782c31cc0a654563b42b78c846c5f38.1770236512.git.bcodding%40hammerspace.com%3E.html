nfsdctl: Load Modules on Netlink Family Resolution Error

Summary

Discussion type: Bug fix / usability improvement (NFS server administration tooling)

Benjamin Coddington from Hammerspace posted a single-patch submission this week to improve the robustness of nfsdctl, the primary userspace control utility for the Linux NFS server (NFSD). The patch addresses a common operational issue: when the netlink family required by nfsdctl is not yet loaded, the tool fails with a name resolution error rather than attempting to load the necessary kernel module.

Context and Bridge from Prior Weeks

This patch is part of a broader series of improvements to NFSD administration and configuration posted by Coddington this week. Related work includes the ongoing development of signed filehandles for kNFSD (v3, with an endianness bug identified) and various netlink-based configuration enhancements. The nfsdctl tool is the userspace counterpart to these kernel-side changes, serving as the primary interface for administrators to configure NFSD exports, keys, and other settings via netlink.

Key Technical Arguments

The Problem: Missing Module Loading on Resolution Failure

In the patch submission, Coddington explains the motivation by pointing to established precedents in NFS userspace tooling:

"There's a precedent of attempting to load kernel modules for userspace functionality: rpc.statd will 'modprobe lockd' and rpc.nfsd will 'mount -t nfsd' which uses the kernel's internal module loading to load the nfsd module."

The proposed fix follows this pattern: when nfsdctl encounters a name resolution failure for the netlink family, it should first attempt to resolve normally, and if that fails, try again after making a "simple effort to load the required module" via modprobe.

Jeff Layton's Review: Privilege Considerations

Jeff Layton provided a review with two important observations. First, he noted the current reliance on /proc/fs/nfsd for module loading:

"I think that right now, we're actually relying on the /proc/fs/nfsd mount to plug in the module for us. Eventually we don't want to rely on that."

This points to a broader architectural goal of transitioning NFSD configuration entirely to netlink, reducing dependency on the legacy /proc/fs/nfsd interface.

Second, Layton raised an important caveat regarding unprivileged usage:

"The catch is that you can run nfsdctl as an unprivileged user for the 'get' operations. The modprobe won't work in that case, so this would be 'best effort'."

This highlights a design constraint: nfsdctl supports read-only ("get") operations without root privileges, but module loading inherently requires elevated permissions. The patch therefore implements a "best effort" approach — attempting to load the module when resolution fails, but gracefully handling cases where the user lacks sufficient privileges.

Layton concluded with a formal review acknowledgment:

Reviewed-by: Jeff Layton jlayton@kernel.org

Evolution of the Discussion

The thread was brief and efficient, consisting of only two messages on February 4th:

  1. Patch submission (Feb 4, ~20:23 UTC): Coddington posts the patch with clear rationale and precedent
  2. Review (Feb 4, ~20:54 UTC): Layton provides context about the broader /proc/fs/nfsd dependency and the unprivileged user caveat, then grants his Reviewed-by

Final Conclusions

The patch received a Reviewed-by from Jeff Layton, indicating it is ready for integration pending maintainer acceptance. Key takeaways:

  • The change follows established NFS userspace conventions for module loading
  • It is implemented as "best effort" to accommodate unprivileged read-only usage of nfsdctl
  • It supports the broader goal of reducing reliance on /proc/fs/nfsd in favor of netlink-based configuration

Significance for NFS Client Development

While this patch targets server-side administration tooling rather than the NFS client directly, it is relevant to developers and administrators deploying NFSD:

  • Improved out-of-box experience: Administrators no longer need to manually ensure the NFSD netlink module is loaded before using nfsdctl
  • Alignment with netlink transition: This change supports the ongoing migration from /proc/fs/nfsd to netlink for NFSD configuration, which will eventually affect how clients interact with server-side features like signed filehandles
  • Unprivileged operation preserved: Read-only nfsdctl operations continue to work without root, maintaining the existing capability model
