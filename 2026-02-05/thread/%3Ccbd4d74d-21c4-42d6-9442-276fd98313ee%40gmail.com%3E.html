NFS Mount Stacking Clarified: Behavior Is Intended, Not a Regression

Summary

NFS Client Mount Option Regression: Stacking Mounts Is Intended Behavior

Summary

Bug Fix Discussion: Clarification of NFS Mount Semantics

This week's activity on this thread represents the resolution of a bug report filed last week by Li Lingfeng (Huawei), who observed that remounting an NFS filesystem with alternating ro/rw options created multiple stacked mount entries rather than replacing the existing mount. The discussion is classified as a bug fix investigation, ultimately concluding that the observed behavior was intended and correct — not a regression.

Background (Prior Week)

Last week, Li Lingfeng reported that after Trond Myklebust's 6-patch series to "Fix up NFS client mount option regressions" was merged, remounting an NFS filesystem with alternating ro/rw options produced four stacked mount entries on the same mount point (/mnt/sdaa) instead of reusing or replacing the existing superblock. This appeared to contradict the expected behavior where the NFS client should deduplicate mounts of the same remote filesystem.

Trond Myklebust responded by requesting diagnostic output from /proc/fs/nfsfs/volumes to determine whether multiple devices were being associated with a single fsid, which would indicate a genuine superblock reuse failure.

This Week's Activity (Jan 30)

Diagnostic Results: Two Devices, Not Unbounded Growth

Li Lingfeng provided the requested diagnostic data in his first message of the week. His test case involved four sequential mount operations alternating between ro and rw:

mount -t nfs -o ro,vers=4 127.0.0.1:/ /mnt/sdaa
mount -t nfs -o rw,vers=4 127.0.0.1:/ /mnt/sdaa
mount -t nfs -o ro,vers=4 127.0.0.1:/ /mnt/sdaa
mount -t nfs -o rw,vers=4 127.0.0.1:/ /mnt/sdaa

The output of cat /proc/fs/nfsfs/volumes revealed only two devices associated with the same fsid:

v4 7f000001  801 0:51        0:0                  no
v4 7f000001  801 0:52        0:0                  no

This confirmed that the NFS client correctly created exactly two superblocks — one for ro and one for rw — and reused them on subsequent mount operations. The four stacked entries in the mount table reflected mount point stacking, not unbounded superblock creation. Li Lingfeng noted:

"There are only 2 devices associated with that fsid."

Maintainer Clarification: Stacking Is Not a Bug

Trond Myklebust responded in his first message of the week, clarifying that this behavior is intentional:

"Then it is working as expected. It's not the kernel's job to stop people from stacking one mount on top of another. If it were, then the right place to do that would be in the VFS and not the NFS client."

He further explained the design principle governing NFS superblock reuse:

"The NFS client does try to ensure that mounts of the same remote filesystem with the same set of mount options gets mapped to the same super block (and hence device). The exception is if you're playing with the nosharecache option; in that case you're knowingly asking the kernel to ignore that constraint."

This establishes a clear distinction: the NFS client deduplicates superblocks based on mount options, but does not prevent mount point stacking — that responsibility belongs to the VFS layer.

Li Lingfeng's Follow-Up: Should NFS Restrict Stacking Like ext4?

In his second message this week, Li Lingfeng raised a comparison with local filesystems. He demonstrated that ext4 prevents remounting the same block device with different ro/rw options at the same mount point:

mount -o rw /dev/sdb /mnt3
mount -o ro /dev/sdb /mnt3
# Error: sdb: Can't mount, would change RO state
# mount: /mnt3: /dev/sdb already mounted on /mnt3.

He then asked:

"Do you think NFS should have a similar restriction, allowing only one mount per mount point?"

Trond's Final Response: No Reason to Break Backward Compatibility

Trond Myklebust responded definitively, explaining the architectural difference between block-based and network filesystems:

"Why would we do that? The above is a reflection of the fact that for ext4, the block device can only be associated with one filesystem. After you've mounted that block device in one place, you can't mount it read-only anywhere else."

He noted that ext4 requires bind mounts to create both read-only and read-write views of the same filesystem, but:

"NFS has no need for that restriction, so what would be the point of duplicating it? In particular why would we want to break backward compatibility for people who may already be relying on the current behaviour?"

Technical Significance

This discussion clarifies several important aspects of NFS client mount semantics:

  1. Superblock deduplication vs. mount stacking: The NFS client correctly deduplicates superblocks based on mount options (two devices for ro and rw), but allows multiple mount entries to stack on the same mount point. This is by design, not a bug.

  2. VFS vs. filesystem responsibility: Preventing mount stacking is a VFS-level concern, not an NFS client concern. The NFS client's role is limited to managing its own superblock lifecycle.

  3. Network vs. block filesystem semantics: Unlike ext4, where a block device can only have one active filesystem instance, NFS has no such constraint. Multiple views of the same remote filesystem with different options are legitimate use cases.

  4. Backward compatibility: Trond emphasized that changing this behavior would break existing users who rely on the current semantics — a key principle in kernel development.

Conclusion

The thread concludes with the consensus that no bug exists. The observed mount stacking behavior is intentional and correct. The NFS client properly deduplicates superblocks while allowing flexible mount point management, which is fundamentally different from (and more permissive than) block-based filesystems like ext4. No code changes are warranted as a result of this investigation.
