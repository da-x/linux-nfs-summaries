nfs-utils Signed Filehandle Support v3: Userspace Tooling Reviewed, NFSv2 Wording and Netlink Ordering Fixed

Overview

Discussion type: New feature (NFS server security enhancement) — userspace tooling patch review

This week, Benjamin Coddington posted version 3 of the nfs-utils companion patches that enable administrators to configure signed filehandles on Linux NFS servers. This two-patch series provides the userspace infrastructure needed to pair with the kernel-side kNFSD changes (posted as a separate thread this week). The review brought attention from Chuck Lever and Jeff Layton, who identified documentation and netlink enumeration issues requiring fixes in v4.

Bridge from Prior Weeks

The signed filehandle feature has been evolving through multiple rounds of review. The preceding kernel patch series (v3, covered separately this week) addressed earlier architectural concerns — notably removing the controversial FH_AT_MAC flag that Chuck Lever had criticized as trusting untrusted network data. The kernel v3 series itself caught several bugs during review, including an endianness issue in MAC computation (caught by Eric Biggers) and an uninitialized pointer bug (caught by the kernel test robot). This nfs-utils v3 series corresponds to those kernel changes and provides the userspace knobs administrators need to activate the feature.

Key Technical Arguments This Week

The Patch Series Structure

The nfs-utils v3 series consists of two patches:

  1. PATCH 1/2: Adds the sign_fh export option to exportfs, allowing per-export control of filehandle signing
  2. PATCH 2/2: Adds nfsdctl/rpc.nfsd support for passing the signing key to the kernel via netlink

In the cover letter, Coddington explains the design:

"The secret key passed to the server is the first 128 bits of a sha1 hash of the contents of a file configured via the nfs.conf server section 'fh_key_file'. Exports that have the option 'sign_fh' set will cause the server to use this key to append an 8-byte siphash of the filehandle onto each filehandle."

The key derivation approach — hashing a configurable file with SHA1 and using the first 128 bits — provides a convenient way for administrators to persist a signing key across reboots while avoiding storing raw cryptographic material in plaintext configuration files.

Chuck Lever: NFSv2 Wording Correction

Chuck Lever reviewed patch 1/2 and flagged an inaccuracy in the man page documentation. The patch included a warning that filehandles might exceed maximum size limits, with mention of NFSv2:

"Now I thought NFSv2 wasn't supported."

Lever pointed out that NFSv2 filehandles are fixed-size with no room for a MAC:

"NFSv2 file handles are all the same size, so there is no space to add the MAC."

Coddington acknowledged the error and committed to a fix:

"My mistake, I will update this wording. There's nothing here (or in the kernel patches) that tries to handle the NFSv2 case."

This is a straightforward documentation correction — the code itself does not attempt to support NFSv2 signing, but the man page misleadingly suggested otherwise.

Jeff Layton: Netlink Enumeration Ordering and Kernel Compatibility

The more substantive review came from Jeff Layton on patch 2/2. Layton noted that his own recently-posted min-threads patch series also adds a netlink attribute (MIN_THREADS) to the same NFSD netlink enumeration. He warned about ordering:

"We'll need to add MIN_THREADS to this before your value, or this won't line up properly."

He suggested an opportunity to clean up conditional compilation:

"I suppose if we do that too, then we can rip out the autoconf check for that constant as well, and get rid of the #ifdefs. I can send a v2 of the series I just sent that just does this."

Layton also raised an important backward-compatibility concern:

"You will also want to rebase this on top of those patches, so you can better handle the case where the kernel doesn't support setting a fh_key. I suppose you probably want to throw a hard error in that case, since being unable to set the key could be a security issue (or cause stale filehandles)?"

This is a critical point for NFS client development: if an administrator configures sign_fh on exports but the kernel cannot accept the signing key (e.g., because it's an older kernel without the corresponding infrastructure), the server would silently serve unsigned filehandles while clients expect signed ones — leading to _BADHANDLE errors and mount failures. Layton correctly identifies that this mismatch should be treated as a hard error rather than a silent degradation.

Coddington agreed:

"That all makes sense - I will do. Thanks!"

Final Conclusions

The nfs-utils v3 series has not yet received formal acceptance. Three concrete items require attention for v4:

  1. NFSv2 man page wording: The documentation incorrectly references NFSv2 in the context of filehandle size limits, despite neither the userspace nor kernel patches supporting NFSv2 signing
  2. Netlink enumeration ordering: The NFSD_A_SERVER_FH_KEY attribute must be ordered after Layton's MIN_THREADS attribute to maintain proper netlink attribute numbering alignment
  3. Kernel compatibility error handling: When the kernel does not support setting an fh_key, nfsdctl should emit a hard error rather than silently proceeding — preventing the dangerous mismatch where exports are configured for signing but no key is available

Significance for NFS Client Development

This thread focuses on userspace server tooling, but has direct implications for NFS client development:

  • No client code changes needed: As established in prior review rounds, NFS clients treat filehandles as opaque data. The 8-byte siphash MAC appended to signed filehandles is transparent to clients — they simply pass larger filehandles back and forth without interpretation
  • Error handling remains unchanged: Clients will encounter _BADHANDLE errors if there's a key mismatch or export configuration issue, which existing client retry logic already handles through re-mount or re-lookup
  • Key persistence matters: The signing key is derived from a configurable file and set once. If the server restarts without the same key, all previously-issued signed filehandles become invalid, causing clients to see stale handle errors — a scenario administrators must plan for
  • Backward-compatibility safety net: Layton's concern about hard-erroring when the kernel doesn't support fh_key is directly relevant to client stability. Without this check, clients could silently fail with _BADHANDLE errors due to an undetected server-side misconfiguration

The coordinated development between the kernel patches (kNFSD) and userspace tools (nfs-utils) demonstrates the careful integration required for security features that span the kernel-userspace boundary — and the importance of netlink protocol stability when multiple developers are extending the same interface.
