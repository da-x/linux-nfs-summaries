NFSD Layout Recall Timeout and Lease Manager Fencing — PATCH v5 Posted

Overview

Discussion type: Bug fix / reliability enhancement for NFS server (NFSD) pNFS layout recall handling.

Dai Ngo from Oracle posted version 5 of his single-patch series, [PATCH v5 1/1] NFSD: Enforce timeout on layout recall and integrate lease manager fencing [id://20260205202929.879846-1-dai.ngo@oracle.com], addressing a critical reliability issue in the NFS server's pNFS block layout subsystem. The patch enforces a timeout on layout recall operations and integrates fencing via the kernel lease manager infrastructure to prevent data corruption when clients hold exclusive block device access.

No replies were received within this week's window; all substantive review occurred during the prior week (Jan 27–28) on the v4 submission. This summary bridges that prior discussion briefly to provide context for the v5 changes.

Bridge from Prior Week

The v4 patch was posted on January 27 and received extensive, rigorous review from Chuck Lever and Jeff Layton over two days. Key concerns raised included:

  • Chuck Lever flagged a race condition in reference counting: incrementing ls_stid.sc_count after mod_delayed_work() is racy, and the function runs under flc_lock (a spinlock), making it impossible to safely call nfs4_put_stid() which may reacquire flc_lock. He also raised a fundamental data-safety concern:

    "Fine, but with the new retry escape clause, as mentioned below, the server and client can be left in opposite states, it looks like: One believes the fence succeeded, and one believes it still has full device access. Am I incorrect about that?"

    He further noted:

    "This is the bane of every timeout-based scheme I know about, and why we have the 'hard' mount option."

  • Jeff Layton proposed a simpler architectural approach — making fence_client return a bool/int to indicate success/failure, having the workqueue job handle retries itself rather than re-scheduling from lm_breaker_timedout(), and calling lease_modify() directly from within the lease manager callback:

    "I'd just make ->fence_client a bool or int return, and have it indicate whether the client was successfully fenced or not. If it was successfully fenced, then have the caller call lease_modify() to remove the lease."

  • Dai Ngo acknowledged these concerns and proposed retrying forever with pr_warn() as a safety measure, rather than giving up after a fixed retry count:

    "If we want to be safe then pr_warn the admin then retry forever which effectively prevents all other clients to access the conflict file until it's manually resolved by the admin."

Jeff Layton clarified the intended control flow for lm_breaker_timedout():

"the lm_breaker_timedout() function (or the workqueue job it spawns) is then responsible for calling lease_modify() at the appropriate time. In most cases you're going to need to queue a workqueue job to fence, and you don't want to clear out the lease until after it's done."

Key Technical Changes in v5

The v5 patch addresses several issues identified during v4 review:

  1. Reference counting fix: The layout stateid reference is now taken before starting the fence worker (not after), preventing use-after-free scenarios:

    "take reference count on layout stateid before starting fence worker."

  2. Fence retry count increased: From 5 to 20 retries, addressing Chuck Lever's concern that 5 might be too low:

    "increase fence retry from 5 to 20."

  3. Worker cancellation on cleanup: The fence worker is now properly cancelled before freeing the layout stateid, addressing Chuck Lever's note about missing cancel_delayed_work_sync():

    "cancel fence worker before freeing layout stateid."

  4. Restored error-handling comments: Comments in nfsd4_scsi_fence_client() and specific error-checking code were restored per Chuck Lever's request to preserve the rationale for distinguishing retryable vs. permanent errors:

    "restore comments in nfsd4_scsi_fence_client and the code that check for specific errors."

  5. Documentation fix: The kdoc comment for @fl parameter was moved as requested.

Design Rationale (from Patch Cover)

The patch introduces a new callback lm_breaker_timedout in lease_manager_operations, invoked when a lease recall times out. Dai Ngo explains the design decision to keep the lease manager and fence worker decoupled:

"I experimented with having the fence worker handle lease disposal after fencing the client. However, this requires the lease code to export the lease_dispose_list function, and for the fence worker to acquire the flc_lock in order to perform the disposal. This approach adds unnecessary complexity and reduces code clarity, as it exposes internal lease code details to the nfsd worker, which should not be the case."

"Instead, the lm_breaker_timedout operation should simply notify the lease code about how to handle a lease that times out during a lease break, rather than directly manipulating the lease list."

Significance for NFS Client Development

While this is a server-side change, it has important implications for pNFS clients:

  • Data safety: The fencing mechanism prevents data corruption when a layout recall times out and the original client still holds block device access. Without proper fencing, concurrent access from multiple clients could corrupt data on shared storage.
  • Server responsiveness: Enforcing timeouts prevents excessive nfsd threads from being blocked in __break_lease, ensuring the server continues servicing incoming requests — directly impacting client experience during layout conflicts.
  • Retry behavior: With 20 retries (up from 5), the server will persist longer before giving up on fencing, reducing the window where inconsistent state could occur between server and client.

Final Status

The v5 patch was posted on February 5 with no replies within this week's window. The patch has evolved significantly through five versions, incorporating substantial architectural feedback from Chuck Lever and Jeff Layton. Key open questions remain around whether a finite retry count is sufficient for data safety in the face of network partitions — a fundamental challenge that Dai Ngo acknowledged:

"I expect this to be a very rare condition so it should not effect most environments."

The patch continues active development, with subsequent versions (v6 through v12) already posted in the following weeks.
