VFS Directory Locking Centralization: nfsd and overlayfs Impact

Summary

Centralising Directory Locking for Name Operations — VFS Refactoring Series

Neil Brown submitted a 13-patch series titled "Further centralising of directory locking for name ops" on February 4, continuing his broader effort to transition VFS directory locking from whole-directory locks to per-name locking. The series is a VFS refactoring rather than a new feature or bug fix, though it has important implications for NFS server (nfsd) and overlayfs code paths.

Background and Motivation

In the cover letter, Brown explained:

"I am working towards changing the locking rules for name-operations: locking the name rather than the whole directory."

The series builds on previously introduced start_creating(), start_removing(), and start_renaming() interfaces that combine locking with lookup. This round addresses remaining callers outside fs/namei.c that still perform explicit directory locking via inode_lock(), lock_rename(), or similar primitives:

"These were missed in the first pass for an assortment of uninteresting reasons."

Brown noted he was running xfstests overlay tests and planned to run NFS tests as well.

Series Overview

The 13 patches span several subsystems:

  • Patches 01–02: Cleanup — removing unnecessary locking from procfs self/thread-self creation (called before the filesystem is live), and repositioning a kerndoc comment.
  • Patch 03: Merging simple_done_creating() into end_creating() in libfs to centralize unlocking.
  • Patches 04–05: Converting AppArmor and SELinux security module code to use simple_start_creating()/simple_done_creating().
  • Patch 06 (nfsd): Switching purge_old() in NFS server recovery code to use start_removing_noperm()/end_removing().
  • Patch 07: Making lookup_one_qstr_excl() static now that it has no external callers.
  • Patches 08–12 (overlayfs): The bulk of the changes — simplifying ovl_lookup_real_one(), modifying ovl_create_real() to re-acquire locks after creation, replacing lock_rename() with is_subdir() for sanity checks, and removing the now-unused ovl_lock_rename_workdir().
  • Patch 13: Unexporting lock_rename(), lock_rename_child(), and unlock_rename() since they are now only used within namei.c.

NFS-Relevant Changes: nfsd purge_old() Refactoring

Patch 06/13 directly affects the NFS server. The change replaces explicit locking in fs/nfsd/nfs4recover.c's purge_old() function with the centralized start_removing_noperm() and end_removing() wrappers. Brown noted:

"This was not done with other start_removing changes due to conflicting in-flight patches."

Jeff Layton reviewed this patch without comment, providing a straightforward Reviewed-by tag here.

Overlayfs Discussion: The Substantive Technical Debate

The most technically interesting discussion centered on the overlayfs patches, particularly patches 08 and 10.

Patch 08: Simplifying ovl_lookup_real_one()

This patch removes explicit locking from ovl_lookup_real_one() in favor of lookup_noperm_unlocked(), arguing that consistency tests after lookup are sufficient. Amir Goldstein raised a stylistic concern about the kernel-doc comment placement:

"I dislike kernel-doc inside code comments. I think this is actively discouraged and I haven't found a single example of this style in fs code."

He also noted the new wording reduced clarity compared to the existing header comment, though otherwise found the patch acceptable. Jeff Layton provided a Reviewed-by tag.

Patch 10: ovl_create_real() Lock Reacquisition

This was the most contentious patch. It changes ovl_create_real() to drop the directory lock after creation and re-acquire a new lock for lookup, since the proposed per-name locking model won't support holding the same lock across both operations. Amir Goldstein raised two concerns:

"According to the new locking rules, if the hashed dentry itself is the synchronization object, is it going to be allowed to filesystem to unhash the dentry while the dentry still in the 'creating' scope? It is hard for me to wrap my head around this."

He also questioned whether this was needed due to casefold filesystems not supporting parallel creations, and expressed aesthetic concern:

"OK. not saying no to this (yet) but I have to admit that it is pretty ugly that the callers of ovl_create_real() want to create a specific stable name... and yet we end up doing this weird dance here just to keep the name from newdentry."

No resolution was reached within this week's window; Amir's concerns remain open.

Patch 12: Removing ovl_lock_rename_workdir()

Amir Goldstein raised an interesting historical question about removing this unused function:

"I am confused. What was this 'fix' fixing an unused function: e9c70084a64e5 ovl: fail ovl_lock_rename_workdir() if either target is unhashed"

This highlights a broader VFS maintenance concern — patches were applied to functions that had already become dead code.

AppArmor Bug Fix

Jeff Layton identified a return-value bug in patch 04/13 (AppArmor):

"As KTR points out, this should be 'return NULL;'"

This was acknowledged as a fix needed before the Reviewed-by would apply.

Review Status

Jeff Layton provided Reviewed-by tags for nearly all patches: procfs cleanup here, kerndoc movement here, libfs consolidation (with a nit suggesting simple_done_creating() become a static inline) here, SELinux here, nfsd here, VFS static conversion here, overlayfs lookup simplification here, cachefiles here, is_subdir usage here, dead-code removal here, and the final unexport patch here. Amir Goldstein reviewed patches 08, 11, and 12 with the caveats noted above.

Conclusion

This series is a significant VFS infrastructure refactoring that centralizes directory locking for name operations, paving the way for future per-name locking semantics. The NFS server impact is limited to a straightforward API migration in purge_old(). The overlayfs changes are more substantial and generated the most discussion, particularly around lock reacquisition patterns and dentry hashing semantics. As of this week's end, Amir Goldstein's concerns about patch 10 remain unresolved, and a minor return-value bug was identified in the AppArmor patch.
