Overview

Discussion type: New feature (NFS server security enhancement) — automated documentation warning on patch 3/3

This thread covers a single message this week: an automated build warning from the kernel test robot against [PATCH v3 3/3] NFSD: Sign filehandles [id://11253ead28024160aaf8abf5c234de6605cc93b5.1770046529.git.bcodding@hammerspace.com], the final patch in Benjamin Coddington's three-patch series for signed NFS filehandles.

Bridge from Prior Weeks

The v3 series was posted on February 2nd and generated significant review activity, as detailed in the cover-letter summary and the patch 1/3 summary. Key developments from earlier this week include:

  • Coddington's self-correction on a misplaced hunk in patch 1/3
  • Eric Biggers catching an endianness bug in the MAC computation (patch 3/3) that would break filehandles across different-endian systems — Coddington confirmed: "Thanks, yes - not intended. I only corrected the userspace key copy. This would break filehandles if the server were migrated onto a different endian system. I will fix this in v4."
  • A separate uninitialized-pointer bug caught by the kernel test robot on patch 1/3

The v3 series also addressed earlier concerns from Chuck Lever about trusting network-provided security signals, having removed the controversial FH_AT_MAC flag in favor of a purely server-side sign_fh export option.

This Week's Activity: Documentation Warning on Patch 3/3

On February 3rd, the kernel test robot (lkp@intel.com) reported a documentation formatting warning under the dabff11003f9aaf293bd8f907a62f3366bd5e65f base:

Documentation/filesystems/nfs/exporting.rst:264: WARNING: Title underline too short.

The warning targets the "Configuration" section in Documentation/filesystems/nfs/exporting.rst, where the tilde-based underline is shorter than the title text itself — a common reStructuredText formatting error that triggers Sphinx build warnings. The offending lines:

Configuration
~~~~~~~~~~~~

While this is purely a cosmetic/documentation issue and does not affect runtime behavior, it represents one of several issues identified across the v3 series that must be addressed before acceptance.

Significance for NFS Client Development

This particular warning has no direct impact on client behavior — it is a documentation formatting nit. However, it adds to the growing list of items for Coddington to address in v4:

  1. Patch 1/3: Misplaced hunk (self-identified by Coddington)
  2. Patch 1/3: Uninitialized pointer in nfsd_nl_fh_key_set() (caught by kernel test robot on patch 1/3)
  3. Patch 3/3: Endianness bug in MAC computation (caught by Eric Biggers)
  4. Patch 3/3: Documentation title underline too short (this thread's finding)

For NFS client developers, the most impactful of these remains the endianness bug — which, if left unfixed, would cause filehandles signed on one architecture to become invalid when served from another, resulting in _BADHANDLE errors.

Final Conclusions

No resolution was reached within this week's window. The documentation warning is straightforward to fix (extending the underline to match the title length) and will likely be addressed alongside the other v4 fixes. The automated CI feedback continues to prove valuable in catching both subtle code bugs and documentation issues across the signed filehandle series.
