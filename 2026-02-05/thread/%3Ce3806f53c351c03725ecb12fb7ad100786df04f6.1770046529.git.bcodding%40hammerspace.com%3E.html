Overview

Discussion type: New feature (NFS server security enhancement) — automated build warning on patch infrastructure

This thread focuses on a single message this week: an automated build warning from the kernel test robot against [PATCH v3 1/3] NFSD: Add a key for signing filehandles [id://e3806f53c351c03725ecb12fb7ad100786df04f6.1770046529.git.bcodding@hammerspace.com], the first patch in Benjamin Coddington's three-patch series for signed NFS filehandles.

Bridge from Prior Weeks

The broader v3 series was posted earlier this week and received significant attention, as covered in the cover-letter summary. Key developments included:

  • Coddington's self-correction on a misplaced hunk in patch 1/3
  • Eric Biggers catching an endianness bug in the MAC computation (patch 3/3) that would break filehandles across different-endian systems

The v3 series addresses earlier concerns from Chuck Lever about trusting network-provided security signals, having removed the controversial FH_AT_MAC flag in favor of a purely server-side sign_fh export option.

This Week's Activity: Build Warning on Patch 1/3

The kernel test robot (lkp@intel.com) reported a clang build warning under the x86_64-buildonly-randconfig-003-20260203 configuration:

"variable 'fh_key' is used uninitialized whenever 'if' condition is false [-Wsometimes-uninitialized]"

The warning targets the nfsd_nl_fh_key_set() function in fs/nfsd/nfsctl.c, which copies a signing key from userspace via netlink. The problematic code path:

siphash_key_t *fh_key;

if (!nn->fh_key) {
    fh_key = kmalloc(sizeof(siphash_key_t), GFP_KERNEL);
    if (!fh_key)
        return -ENOMEM;
}

memcpy(fh_key, nla_data(attr), sizeof(siphash_key_t));  // <-- warning here
nn->fh_key = fh_key;

When nn->fh_key is already non-NULL (the key was previously set), the if block is skipped, leaving fh_key uninitialized. The subsequent memcpy() then writes to an indeterminate pointer — a clear bug that would cause undefined behavior when attempting to update an existing signing key.

The compiler helpfully suggests:

"initialize the variable 'fh_key' to silence this warning"

In practice, the fix should assign fh_key = nn->fh_key in the else branch (or unconditionally before the if) so that the memcpy() writes into the existing allocated buffer rather than a garbage pointer.

Significance for NFS Client Development

While this is a server-side patch, the implications for clients are direct:

  • Key management via netlink: The signing key is configured through the NFSD netlink interface, and this bug would prevent reliable key updates — potentially leaving servers without proper signing capability
  • Filehandle integrity: A broken key-setting path could mean filehandles are either unsigned (defeating the security purpose) or signed with inconsistent keys, leading to _BADHANDLE errors on clients
  • Interaction with prior bugs: This uninitialized-pointer bug in patch 1/3 compounds the endianness issue already identified by Eric Biggers in patch 3/3. Both issues must be resolved before the feature can be safely deployed

Final Conclusions

No resolution was reached within this week's window. The build warning remains open and requires a fix from Coddington, likely to be addressed alongside the endianness bug and the misplaced hunk issue in an upcoming v4 resubmission.

The kernel test robot's report underscores the importance of automated CI feedback in catching subtle pointer-handling errors that can slip through manual review — particularly in new infrastructure code introducing security-critical functionality.
