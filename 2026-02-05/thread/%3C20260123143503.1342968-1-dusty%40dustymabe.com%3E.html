systemd: rpc-statd-notify network-online.target patch committed (nfs-utils-2-8-5-rc3)

Summary

systemd: drop Wants=network-online.target for rpc-statd-notify (continued)

Summary

Type: Bug fix / systemd service dependency correction

Participants: Dusty Mabe, Steve Dickson

Bridge from Prior Week

Last week, Dusty Mabe submitted a patch to remove the Wants=network-online.target dependency from the rpc-statd-notify.service unit in nfs-utils. The rationale was that sm-notify already has built-in retry logic for transient network failures, making the strict network-online dependency unnecessarily conservative and a source of boot delays — especially on systems (like Fedora) where nfs-client.target is enabled by default even when no NFS mounts are configured.

Activity This Week

This week saw the final resolution of this thread. NFS maintainer Steve Dickson confirmed that the patch had been accepted and merged:

"Committed... (tag: nfs-utils-2-8-5-rc3)" — Steve Dickson

The commit was tagged as part of nfs-utils-2-8-5-rc3, indicating it will be included in the upcoming nfs-utils 2.8.5 release.

Conclusion

This straightforward but impactful fix is now merged into nfs-utils. By removing an overly conservative systemd dependency from rpc-statd-notify.service, systems that enable nfs-client.target — particularly Fedora by default — will no longer experience unnecessary boot delays when no network is available or when no NFS mounts are configured. The change relies on the existing retry semantics of sm-notify to ensure correctness while improving startup responsiveness. As Mabe noted in his original patch:

"Making this change means if you are in an offline scenario (one example is an install environment) then you won't have to wait for network-online.target to timeout before the system comes up fully."

The fix is expected to ship with nfs-utils 2.8.5, benefiting NFS client deployments across distributions that adopt the updated package.
