NFSD: Fix nfsd_file Reference Leak in Write Delegation Race Condition

NFSD: Fix nfs4_file Access Extra Count in Write Delegation Path

Summary

Discussion type: Bug fix (NFSD server-side reference counting)

Dai Ngo from Oracle submitted a targeted bug fix addressing an nfsd_file reference leak in the NFSv4 write delegation code path. The patch was quickly reviewed and accepted by both Jeff Layton and Chuck Lever, with the latter applying it to the nfsd-testing tree on the same day.

Bridge from Prior Weeks

This is a new thread with no prior discussion history. However, it relates to a previous fix — commit 8072e34e1387 ("nfsd: fix nfsd_file reference leak in nfsd4_add_rdaccess_to_wrdeleg()") — which introduced the regression this patch now corrects. This week also saw other NFSD-related activity, including Benjamin Coddington's signed filehandle series and Chuck Lever's min-threads series (see related summaries).

The Bug: Reference Count Leak in Delegation Race Condition

Dai Ngo described the issue as follows:

"In nfsd4_add_rdaccess_to_wrdeleg, when there is a race condition where fp->fi_fds[O_RDONLY] is not NULL, __nfs4_file_get_access should not be called to increment the access count nfs4_file since that was already done by the thread that adds READ access to the file."

The core problem lies in the function nfsd4_add_rdaccess_to_wrdeleg(), which handles adding read access to a write delegation. In a race condition scenario where two threads contend — one adding READ access and another attempting to add read access to an existing write delegation — the access count on the nfs4_file object can be incremented twice when it should only be incremented once.

Impact: Memory Leak and Kernel BUG

The consequences of this double-counting are severe, as Dai Ngo explained:

"The extra fi_access count in nfs4_file can prevent the corresponding nfsd_file to be freed."

This manifests as a kernel-level error during server shutdown:

"When stopping nfs-server service, these extra access counts trigger a BUG in kmem_cache_destroy() that shows nfsd_file object remaining on __kmem_cache_shutdown."

Dai Ngo noted that the issue is reproducible through existing test infrastructure:

"This problem can be reproduced by running the git test."

The Fix

The patch is a minimal two-line change in fs/nfsd/nfs4state.c. It corrects the logic so that when fp->fi_fds[O_RDONLY] is already non-NULL (indicating another thread has already established READ access and incremented the count), the function avoids calling __nfs4_file_get_access() again. Instead, it properly reuses the existing reference without incrementing the access counter a second time.

Review and Acceptance

The patch received swift review from two key NFSD maintainers:

Jeff Layton provided a Reviewed-by on February 5th, signaling his approval of the fix.

Chuck Lever applied the patch to nfsd-testing on February 4th, the same day it was submitted:

"Applied to nfsd-testing, thanks!"

The commit landed as b4ae2fc4d1344fe20f431baf00f8256fb3bbaa87 in the nfsd-testing tree.

Significance for NFS Client Development

While this is a server-side (NFSD) fix, it has direct implications for NFS client interactions:

  • Server stability: The kmem_cache_destroy() BUG triggered during nfs-server shutdown represents a denial-of-service scenario where the server cannot be cleanly restarted. Clients connected to such a server would experience abrupt disconnections.
  • Delegation handling: The fix ensures that write delegations with read access upgrades are handled correctly under concurrent load, preventing resource leaks that could eventually exhaust server-side file descriptors.
  • Test coverage: Dai Ngo's note that the issue is reproducible via "the git test" suggests this scenario exercises real-world delegation patterns that clients may trigger during concurrent read/write operations on shared files.

Final Conclusions

This was a straightforward bug fix with clear problem statement, minimal code change, and rapid acceptance. The patch corrects a regression introduced by a prior reference-counting fix, demonstrating the ongoing challenge of getting reference counting right in concurrent NFS server code paths. With the fix applied to nfsd-testing, it is expected to flow into the mainline kernel via the standard NFSD merge path.
