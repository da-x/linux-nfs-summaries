sunrpc: RFC Series to Reduce Lock Contention for NFSD TCP Sockets

Summary

sunrpc: Reduce Lock Contention for NFSD TCP Sockets — RFC Series Submitted

Classification

New feature / performance optimization (RFC patch series). This is not a bug fix per se, but rather an architectural redesign of the NFSD TCP receive and transmit paths to eliminate lock contention bottlenecks that limit server scalability under high-throughput workloads.

Bridge from Prior Weeks

Last week, Daire Byrne from DNEG initiated an investigation into knfsd's read IOPS ceiling, reporting that the NFS server hits a hard performance plateau at approximately 300–400K IOPS regardless of client count or hardware configuration. Chuck Lever identified xpt_mutex as a problematic hotspot through lockstat analysis, noting:

"There's kind of no denying it, the xpt_mutex numbers are shitty. The maximum hold time on that mutex is 293379.40 usecs, with a mean hold time of nearly 16 usec, giving it the worst mean wait time by an order of magnitude."

Chuck committed to investigating the TCP send path further:

"I'm going to try some simple experiments here to see if I can spot any structural problems with the TCP send path."

This RFC series is the direct outcome of that investigation — a comprehensive redesign targeting both receive-side and transmit-side lock contention.

This Week's Activity

On February 5, Chuck Lever submitted a seven-patch RFC series titled "sunrpc: Reduce lock contention for NFSD TCP sockets," based on kernel v6.19-rc8. The series touches 9 files with 1,044 insertions and 126 deletions — a substantial architectural change to the SunRPC server infrastructure.

No replies were received within this week's window; the thread is in its initial RFC stage awaiting community feedback.

Patch-by-Patch Breakdown

Patch 1/7: Workqueue Affinity Scope Fallback

This foundational patch addresses a workqueue scalability problem on single-LLC (Last-Level Cache) systems — common with Intel monolithic dies. Chuck explains the problem:

"On systems where all CPUs share a single LLC... this scope degenerates to a single worker pool. All queue_work() calls then contend on that pool's single lock, causing severe performance degradation under high-throughput workloads."

He cites concrete profiling data:

"For example, on a 12-core system with a single shared L3 cache running NFS over RDMA with 12 fio jobs, perf shows approximately 39% of CPU cycles spent in native_queued_spin_lock_slowpath, nearly all from __queue_work() contending on the single pool lock."

The patch introduces wq_effective_affn_scope() to automatically detect when an affinity scope collapses to a single pod and fall back to a finer-grained scope (e.g., "cache → smt"), making the behavior transparent via sysfs.

Patch 2/7: Split svc_data_ready into Protocol-Specific Callbacks

This preparatory patch separates data-ready callbacks for UDP and TCP transports. Chuck notes that "UDP sockets do not implement DTLS, so the XPT_HANDSHAKE check is unnecessary overhead for them," and this refactoring prepares the infrastructure for subsequent TCP-specific changes.

Patch 3/7: Per-Transport Page Recycling Pool

This patch introduces svc_page_pool, a lock-free page recycling mechanism to reduce allocator overhead under high load:

"RPC server transports allocate pages for receiving incoming data on every request. Under high load, this repeated allocation and freeing creates unnecessary overhead in the page allocator hot path."

The pool uses llist for lock-free producer-consumer handoff (workers return pages as producers; receivers consume them) and tracks NUMA node affinity for memory locality. Chuck notes that "svcrdma's RDMA Read path might also make use of this mechanism some day."

Patch 4/7: Dedicated TCP Receiver Thread

This is the centerpiece receive-side patch. Chuck identifies the core problem:

"Current architecture has multiple nfsd worker threads competing for the same socket, serializing on socket lock inside sock_recvmsg()."

The new design creates one dedicated kernel thread per TCP connection that owns all sock_recvmsg() calls and queues complete RPC messages to workers via a lock-free llist. The architecture shift is illustrated as:

Before: Workers compete for xprt → sock_recvmsg() → CONTENTION

After: Receiver Thread → sock_recvmsg() (no contention) → Workers process/send

Key design details:

  • Flow control limits queue depth to 64 messages per socket (SVC_TCP_MSG_QUEUE_MAX) to bound memory usage.
  • The receiver thread is NUMA-affinitized to the service pool's node, with page allocations targeting that same node via __alloc_pages_bulk().
  • This mirrors the svcrdma architecture where "RDMA completion handlers queue received messages for worker threads rather than having workers compete for hardware resources."

Patch 5/7: Flat Combining for TCP Socket Sends

This patch addresses the transmit-side bottleneck identified in last week's investigation. Chuck cites profiling data:

"Profiling on high-throughput workloads shows approximately 15% of cycles spent in the spin-wait path."

The flat combining pattern allows one thread to send on behalf of multiple waiters: threads enqueue requests to a lock-free llist, and the first thread to acquire xpt_mutex becomes the "combiner," processing all pending sends as a batch. This amortizes lock acquisition cost across multiple sends and enables TCP segment coalescing via MSG_MORE:

"Setting MSG_MORE on all but the final send in each batch hints TCP to coalesce segments, reducing protocol overhead when multiple replies transmit in quick succession."

Patch 6/7: Unify Fore and Backchannel Server TCP Send Paths

This patch extends flat combining to NFSv4.1+ backchannel (callback) operations, which previously acquired xpt_mutex directly and could starve under heavy fore-channel load:

"A thread in the combining loop processes queued sends continuously until the llist empties, which under load means backchannel threads block on xpt_mutex for extended periods waiting for a turn at the socket. Delegation recalls and other callback operations carry time constraints that make this starvation problematic."

By routing both channels through the same llist queue, "backchannel operations receive fair treatment in the send ordering" and the codebase benefits from reduced maintenance burden with a single TCP send path.

Patch 7/7: Explicit TCP Socket Buffer Sizes for NFSD

The final patch sets explicit TCP buffer sizes for NFSD data sockets, addressing throughput limitations on high bandwidth-delay product networks:

"On networks with large bandwidth-delay products, the default maximum buffer sizes (6MB receive, 4MB send) can throttle throughput."

The buffer size is set to 4 * sv_max_mesg (~16MB with default NFS payload sizes), capped at 1/1024 of physical RAM on memory-constrained systems. Auto-tuning is disabled via SOCK_SNDBUF_LOCK and SOCK_RCVBUF_LOCK for predictable memory consumption, avoiding the need for system-wide tcp_rmem/tcp_wmem sysctl adjustments.

Technical Significance

This RFC series represents a major architectural overhaul of the NFSD TCP transport layer with implications for NFS server scalability:

  1. Receive path: Eliminates socket lock contention among worker threads by dedicating one receiver thread per connection — a pattern already proven in svcrdma.
  2. Transmit path: Introduces flat combining to amortize xpt_mutex acquisition, directly addressing the bottleneck identified in last week's IOPS ceiling investigation.
  3. Backchannel fairness: Ensures NFSv4.1+ callback operations (delegation recalls, layout returns) are not starved under heavy fore-channel load.
  4. Memory efficiency: Page recycling reduces allocator pressure; explicit buffer sizing avoids system-wide TCP tuning.
  5. Hardware awareness: Workqueue affinity fallback ensures scalability on single-LLC systems common in modern server hardware.

Conclusion

Chuck Lever's RFC series is a direct response to the NFSD performance ceiling investigation from last week, proposing comprehensive architectural changes to eliminate lock contention on both receive and transmit paths. The series introduces proven concurrency patterns (dedicated receiver threads, flat combining) already used in other parts of the NFS server stack (svcrdma). As an RFC submission with no replies yet within this week's window, the community's feedback will determine whether these changes proceed to a formal patch series for merge consideration.
