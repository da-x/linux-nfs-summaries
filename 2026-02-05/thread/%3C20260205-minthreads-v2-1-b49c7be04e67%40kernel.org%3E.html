nfsd: Restore Traditional Thread Count Reporting in /proc and netlink Interfaces

Summary

This week, Jeff Layton submitted v2 of a kernel-side bug fix to correct a regression in how the NFS server reports thread counts through its /proc and netlink interfaces. The patch restores traditional behavior — reporting the configured maximum number of threads rather than the volatile count of currently running threads — a change necessitated by the recent introduction of dynamic threading support in nfsd.

Bridge from Prior Weeks

The broader story began with the development of dynamic threading for nfsd, allowing the kernel to scale server threads between a configurable minimum and maximum based on workload:

  • The kernel-side feature was merged into Chuck Lever's tree, introducing min-threads controls per thread pool.
  • User-space support landed in nfs-utils 2.8.5-rc3, with Steve Dickson confirming the merge last week.
  • A backward-compatibility fix for older kernels lacking min-threads support was also submitted as a four-patch nfs-utils series this week.

However, the dynamic threading merge introduced an unintended side effect: the /proc/net/rpc/nfsd and netlink interfaces began reporting the current number of running threads instead of the configured maximum. This broke backward compatibility for scripts and monitoring tools that relied on those values.

This Week's Activity

The v2 Patch Submission

On February 5, Jeff Layton submitted the revised patch with the following description:

"The current netlink and /proc interfaces deviate from their traditional values when dynamic threading is enabled, and there is currently no way to know what the current setting is. This patch brings the reporting back in line with traditional behavior."

The patch carries a Fixes: tag pointing to the commit that introduced the regression:

"Fixes: d8316b837c2c ("nfsd: add controls to set the minimum number of threads per pool")"

Changes from v1 to v2

The v1 patch, submitted on February 4 and discussed in detail in a prior thread this week, received review from Chuck Lever who identified documentation gaps. Layton's v2 addresses those concerns:

"Changes in v2:

  • Update docs and comments that this is a max and not the current value"

The patch modifies three files (Documentation/netlink/specs/nfsd.yaml, fs/nfsd/nfsctl.c, and fs/nfsd/nfssvc.c) to ensure documentation, code comments, and actual behavior all consistently reflect that the reported value is a maximum, not a live count.

Observability Considerations

Layton also addressed the question of how administrators can monitor currently running threads:

"We could also consider adding netlink attributes to report the number of running threads, but you can get that info from ps too."

This follows up on earlier discussion in the v1 thread where Mike Owen expressed concern about losing visibility into running thread counts, and Chuck Lever suggested the practical workaround of using pgrep -c nfsd.

Classification

This is a bug fix in the NFS server kernel code. It corrects a regression in interface semantics introduced by the dynamic threading feature, restoring backward-compatible behavior for /proc and netlink thread count reporting.

Significance for NFS Server Development

  1. Interface consistency restored: Tools and scripts that parse /proc/net/rpc/nfsd or query netlink will once again receive the configured maximum thread count — a stable value that reflects administrator intent rather than fluctuating with workload.

  2. Documentation hygiene: The v2 revision underscores the importance of updating documentation alongside code changes. Three locations (netlink spec YAML, two C docstrings) were corrected to reflect the true semantics.

  3. Observability trade-offs acknowledged: The community has identified that while /proc and netlink will report the maximum, and min-threads is queryable via netlink, there is currently no dedicated kernel interface for the running thread count. Administrators must rely on user-space tools like ps or pgrep. Layton left the door open for future enhancement: "we could add that to the netlink interface if someone can make a good use-case for it."

  4. Continued maturation of dynamic threading: This fix is part of an active development cycle around NFS server scalability. The rapid turnaround from v1 to v2 (one day) and attention to documentation suggest careful stewardship of this feature area.

Conclusion

Jeff Layton's v2 patch restores traditional thread count reporting semantics for the NFS server, ensuring that both /proc and netlink interfaces report the configured maximum rather than the volatile running count. With documentation updated across all affected locations, the patch is well-positioned for integration. The community has identified practical workarounds for monitoring running threads while remaining open to future kernel-side enhancements if demand justifies them.
