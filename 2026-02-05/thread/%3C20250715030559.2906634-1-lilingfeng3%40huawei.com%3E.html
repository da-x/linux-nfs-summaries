NFS Client: Revised Approach for Lock/Unlock vs. Open Race After Deadlock Discovery

Summary

NFS Client: New Approach Proposed for Lock/Unlock vs. Open Race After Deadlock Discovery

Overview

This week saw a new development in the long-running effort to fix a use-after-free (UAF) bug in the NFS client's file locking subsystem. Li Lingfeng of Huawei proposed an alternative approach after the previously suggested rwsem-based fix was found to introduce a deadlock in January.

Background (Prior Weeks)

The thread originated in July 2025 with Li Lingfeng's PATCH v2 submission, which aimed to fix a race condition between NFS lock/unlock operations and file open operations. The original bug involved a scenario where concurrent lock extension/release, state manager reclaim, and write-only opens could lead to freed locks being accessed — resulting in a use-after-free.

The proposed v2 fix used nfsi->rwsem (a read-write semaphore on the NFS inode) to protect file locks from concurrent access during reclaim and open operations. However, as reported in January 2026, this approach introduced a deadlock:

"Recently, we found that this solution can introduce a deadlock issue"

The deadlock occurred when Thread T1 (an unlock path) held down_read(&nfsi->rwsem) and waited for an RPC task to complete, while the RPC callback triggered error recovery causing the RPC task to sleep waiting for the state manager. Meanwhile, Thread T2 (the NFS state manager) attempted down_write(&nfsi->rwsem) and got stuck — a classic ABBA deadlock.

Li Lingfeng concluded at that time:

"It seems that using &nfsi->rwsem to protect file locks is not a good idea."

This Week's Development: A Revised Approach

On February 2, Li Lingfeng returned with a new strategy, describing an attempt to separate the local VFS lock update from the RPC completion path:

"I tried separating the local VFS lock update from the RPC completion path (performing an unlock if the VFS lock update fails), and then using nfsi->rwsem to protect the file lock to prevent UAF."

The key idea of this revised approach is to split the local VFS lock update from the RPC completion path, with a fallback mechanism that performs an unlock if the VFS lock update fails. The nfsi->rwsem would still be used, but in a more carefully scoped manner — specifically to protect file locks from UAF rather than being held across the entire RPC wait cycle.

Assessment

This discussion centers on a bug fix — addressing a use-after-free vulnerability in the NFS client's file locking code that arises from race conditions between lock/unlock operations and file open operations. The evolution of the thread reveals:

  1. July 2025: Initial patch proposal using rwsem protection.
  2. September 2025: Follow-up ping with no further activity.
  3. January 2026: Discovery that the proposed fix introduces a deadlock, effectively invalidating the approach.
  4. February 2026 (this week): A revised approach is proposed, attempting to decouple the VFS lock update from RPC completion while still using rwsem for targeted protection against UAF.

As of this week's message, no review feedback has been received on the new approach. The patch diff was included in the email but remains unreviewed by other NFS developers. The complexity of concurrent locking in the NFS client — where interactions between user-space lock operations, RPC error recovery, and the state manager create subtle deadlock hazards — continues to make this a challenging problem to resolve.
