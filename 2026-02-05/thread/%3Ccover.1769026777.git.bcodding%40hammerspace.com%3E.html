kNFSD Signed Filehandles v2: Performance Concerns and Client Compatibility Clarified

Summary

Overview

Discussion type: New feature (NFS server security enhancement) — patch review continuation

This week's activity on Benjamin Coddington's signed filehandle patch series shifted from the architectural debates of prior weeks to practical concerns about performance impact and client compatibility. The thread, which had been dominated by Chuck Lever's security design critique and NeilBrown's clarifications in the previous week (see 2026-01-29 summary), saw a new participant — Lionel Cons — raise questions about CPU overhead and client-side requirements.

Notably, Coddington also posted v3 of the series this week under a separate thread (see 2026-02-05 summary), which addressed many of the prior review concerns including removing the FH_AT_MAC flag that had been the subject of intense debate.

Bridge from Prior Weeks

The signed filehandle feature has been under development for several weeks. Last week's discussion centered on Chuck Lever's persistent question about why the design uses two signals — a sign_fh export option and an FH_AT_MAC auth type flag — to control filehandle signature verification. Lever invoked the security principle that "what comes off the network is completely untrusted," questioning whether the server should rely on a flag embedded in a client-provided filehandle for security decisions. NeilBrown defended the dual-signal design, citing debugging benefits via packet captures. No definitive resolution was reached last week; Coddington committed to documenting the rationale and addressing the security concern in v3.

Key Technical Arguments This Week

Performance Impact: The Siphash Overhead Question

Lionel Cons opened this week's discussion with two practical questions, the first of which raised a significant concern about embedded hardware:

"Linux NFSv4 servers consume LOTS of CPU time, which has become a HUGE problem for hosting them on embedded hardware (so no realistic NFSv4 server performance on an i.mx6 or RISC/V machine). And this has become much worse in the last two years. Did anyone measure the impact of this patch series?"

This question resonated with the broader community's awareness that NFSD CPU consumption is already a pain point for resource-constrained deployments. The concern was particularly relevant because the signed filehandle feature adds a siphash operation to every filehandle encode and decode path.

Benjamin Coddington responded with both qualitative and quantitative assessments:

"We're essentially adding a siphash operation for every encode and decode of a filehandle. Siphash is lauded as 'faster than sha256, slower than xxhash'. Measuring the performance impact might look like crafting huge compounds of GETATTR, but I honestly don't think (after network latency) the performance impact will be measurable."

He noted his own testing:

"I attempted to measure a time difference between runs of fstests suite -- there were no significant measurable effects in my crude total time calculations."

Coddington offered to produce more detailed profiling data but emphasized the security trade-off:

"the users of this option do not care about gating it behind strict performance optimizations because we're fixing a security problem that matters much more to those users."

Client Compatibility: No Changes Required

Lionel Cons' second question was straightforward:

"Do NFS clients require any changes for this?"

Coddington's answer was definitive and reassuring for client developers:

"No - the filehandle is opaque."

This is an important conclusion for NFS client development. Because NFS filehandles are treated as opaque byte sequences by the protocol, clients need no modification to handle signed filehandles. The 8-byte MAC appended to filehandles is transparent to the client; it simply passes larger filehandles back and forth without interpretation. This means that once the server feature is merged, existing NFS client implementations (both in-kernel and user-space) will work correctly with signed filehandles without any code changes.

Community Response: Opt-In Nature Emphasized

Chuck Lever responded to Cons' performance concern by emphasizing two points. First, he called for data-driven regression reporting:

"If this is a general concern, please take the time to collect some data and file a full regression report."

Second, he underscored that the feature is entirely optional:

"Also note that signed file handles are enabled by administrative settings that default 'off'. There will be little to no additional CPU load if you choose not to use them."

Trond Myklebust, Linux NFS client maintainer, echoed this point:

"The other thing to note is that this is an opt-in feature. If you don't want to use it for fear of CPU load, you are free not to change your /etc/exports config file."

This consensus — that the feature defaults off and administrators retain full control — was a recurring theme throughout the review process and helps address concerns about mandatory performance overhead.

Flame Graph Evidence: Quantifying the Overhead

Chuck Lever suggested that Coddington produce flame graphs to visually demonstrate the CPU impact:

"Trond or Mike can demonstrate for you how to capture flame graphs to very graphically illustrate how much CPU utilization is introduced when using this feature. It would be valuable to confirm our expectation that the additional CPU consumption will essentially be in the noise."

Coddington delivered on this request, providing a flame graph from a workload of "a client doing 10 passes at a directory with 10k files, looking them up and then doing GETATTR on each. Each pass starts with an empty cache." The profile was filtered to NFS daemon threads only, and the fh_append_mac and fh_verify_mac functions were annotated to prevent compiler optimization from hiding them in the profile.

The flame graph (hosted at bcodding.com) shows that both signing functions appear as small fractions of total CPU time within their respective call chains (nfsd4_proc_compound for encoding and nfsd4_putfh for verification). While no precise percentage was quoted in the thread, the visual evidence supports Coddington's claim that the overhead is minimal — "essentially in the noise" as Lever put it.

Final Conclusions

This week's discussion reached several clear conclusions:

  1. Performance overhead is minimal: The siphash operations for signing and verification add negligible CPU cost, confirmed both by Coddington's fstests measurements and his flame graph analysis. The community consensus is that the overhead is "in the noise" compared to network latency and other NFSD processing costs.

  2. No client changes required: NFS clients treat filehandles as opaque data, so no modifications are needed in any NFS client implementation — whether Linux kernel NFS, user-space NFS clients, or third-party implementations. This is a significant finding for NFS client development, as it means the signed filehandle feature can be deployed server-side without coordinating client updates.

  3. Feature is opt-in with sensible defaults: The sign_fh export option defaults to off, meaning administrators who are concerned about performance (particularly on embedded hardware) or who don't need the security enhancement simply never enable it. This addresses the primary concern raised by Cons about impact on resource-constrained systems.

  4. Flame graph evidence provided: Coddington's profiling data provides concrete visual confirmation that fh_append_mac and fh_verify_mac consume a tiny fraction of NFSD CPU time, even under heavy directory traversal workloads.

Significance for NFS Client Development

While this thread focuses on server-side changes, the conclusions are directly relevant to NFS client developers:

  • Zero code changes needed: Clients need not be modified to support signed filehandles since filehandles remain opaque
  • Larger filehandles handled transparently: The 8-byte MAC extension fits within existing NFSv3 (64-byte) and NFSv4 filehandle size limits
  • Error handling unchanged: Clients will see _BADHANDLE or -ESTALE responses in edge cases (e.g., export option transitions), which are already handled by standard client retry logic
  • Cross-version compatibility: Since the feature is opt-in, clients can work with both signed and unsigned filehandles from the same server depending on per-export configuration
