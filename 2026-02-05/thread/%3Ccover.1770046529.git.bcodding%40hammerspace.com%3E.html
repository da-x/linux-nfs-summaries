kNFSD Signed Filehandles v3: Endianness Bug Caught, Series Resubmitted

Summary

kNFSD Signed Filehandles v3: Endianness Bug Caught, Patch Series Resubmitted

Overview

Discussion type: New feature (NFS server security enhancement) — patch resubmission and review

Benjamin Coddington from Hammerspace posted version 3 of his signed filehandle patch series this week, aimed at hardening the Linux NFS server (kNFSD) against filehandle guessing attacks. The v3 series incorporates significant architectural changes from prior rounds, including a major security review finding: an endianness bug in the MAC computation caught by Eric Biggers.

Bridge from Prior Weeks

The signed filehandle feature has been under development through multiple iterations. Last week (2026-01-29 summary), the v2 series sparked an intense debate between Chuck Lever and NeilBrown over a dual-signal design — both a sign_fh export option and an FH_AT_MAC auth type flag embedded in filehandles. Chuck Lever raised concerns about trusting network-provided flags for security decisions, invoking the principle that "what comes off the network is completely untrusted." Coddington addressed these concerns in v3 by removing the FH_AT_MAC flag entirely, relying solely on the server-side sign_fh export option to control signing behavior.

Key Technical Arguments This Week

The Patch Series Structure

The v3 series consists of three patches:

  1. PATCH 1/3: Adds infrastructure for a 128-bit signing key, configurable via netlink and the nfsctl interface
  2. PATCH 2/3: Introduces the sign_fh export option (NFSEXP_SIGN_FH)
  3. PATCH 3/3: Implements the actual signing and verification logic using siphash as a MAC

Cover Letter: Problem Statement and Design Rationale

In the cover letter, Coddington provides a detailed explanation of the threat model:

"Filehandles are easy to guess because they are well-formed."

He illustrates with an XFS example showing a filehandle consisting of a 64-bit inode number and 32-bit generation number, noting that:

"Simple testing confirms that the correct generation number can be found within ~1200 minutes using open_by_handle_at() over NFS on a local system and it is estimated that adding network delay with genuine NFS calls may only increase this to around 24 hours."

The proposed defense appends an 8-byte siphash MAC to filehandles, making guessing "practically impossible without knowledge of the MAC's key." Coddington emphasizes key persistence:

"Because filehandles are long-lived, and there's no method for expiring them, the server's key should be set once and not changed. It also should be persisted across restarts."

He also addresses a potential overflow concern with NFSv3's 64-byte filehandle maximum:

"The server will refuse to give out filehandles at mount time and emit a pr_warn()."

Self-Correction on Patch 1/3

Shortly after posting, Coddington identified a mistake in patch 1/3:

"Oof, I messed it up right here^^ this hunk needed to be folded in.. can send another version on this one:"

He offered to resubmit the corrected version.

Eric Biggers' Endianness Bug Catch

The most significant review finding came from Eric Biggers, who identified an endianness issue in patch 3/3's MAC computation:

"Note that this is still creating endianness-specific MAC values, considering that siphash() returns a u64 which is being copied directly into a byte array. Maybe not what was intended?"

Coddington confirmed the bug and acknowledged its implications:

"Thanks, yes - not intended. I only corrected the userspace key copy. This would break filehandles if the server were migrated onto a different endian system. I will fix this in v4."

This is particularly important because it's a recurrence of an endianness issue that Biggers previously caught in v2 — suggesting the kernel-side signing code still needs careful byte-order handling even after the userspace key copy was fixed.

Evolution of the Discussion

The thread followed a concise arc on February 2nd:

  1. Patch series posting (Feb 2, ~16:19 UTC): Coddington posts all four messages of the v3 series
  2. Self-correction (Feb 2, ~16:51 UTC): Coddington identifies a hunk error in patch 1/3
  3. Eric Biggers' review (Feb 2, ~18:19 UTC): Endianness bug identified in MAC computation
  4. Coddington's acknowledgment (Feb 2, ~18:25 UTC): Confirms the bug and commits to fixing it in v4

Notably absent from this week's discussion is Chuck Lever, who was a prominent reviewer in prior rounds. His earlier concerns about the dual-signal design appear to have been addressed by Coddington's removal of FH_AT_MAC in v3.

Final Conclusions and Open Items

The v3 series has not yet received formal acceptance. Two concrete issues require attention for v4:

  1. Patch 1/3 hunk error: A code hunk was incorrectly placed and needs to be folded in properly
  2. Endianness bug in MAC computation: The siphash result (a u64) is being copied directly into a byte array without explicit endianness handling, which would break filehandle compatibility across systems of different endianness

The broader architectural debate from prior weeks — about whether the server should trust network-provided signals for security decisions — appears resolved: v3 uses only the server-side sign_fh export option, eliminating the FH_AT_MAC flag that had drawn criticism.

Significance for NFS Client Development

While this series targets NFSD (server-side), it has direct implications for NFS clients:

  • Larger filehandles: Clients must handle filehandles with an appended 8-byte MAC signature
  • Error handling: Unsigned filehandles presented to a sign_fh export will be rejected with _BADHANDLE, requiring clients to re-mount or re-lookup
  • Key persistence: The server key is set once and cannot be changed, meaning filehandle validity depends on the server maintaining the same key across restarts
  • Cross-endianness compatibility: Once fixed, the endianness handling must ensure that filehandles signed on one architecture remain valid when served from another

The endianness bug caught by Biggers is particularly relevant for client developers, as it would have caused silent filehandle corruption in heterogeneous environments.
