NFS sysfs memory leak patch rejected — no bug in nfs_sysfs_init error path

Summary

NFS sysfs Memory Leak Fix Patch Rejected — No Bug Found

Overview

This thread concerns a proposed bug fix for a memory leak in the NFS client's sysfs initialization code, specifically in nfs_sysfs_init(). The patch was submitted by Salah Triki and quickly reviewed by NFS subsystem maintainers Benjamin Coddington and Trond Myklebust. After examination of the kernel source, the patch was determined to be incorrect — no bug exists in the current code.

Classification

Bug fix (proposed) — ultimately rejected as the reported bug does not exist.

Discussion Evolution

Patch Submission

Salah Triki submitted a one-line patch on January 31st addressing an alleged memory leak in the NFS client's sysfs initialization path. The patch proposed replacing kfree() with kobject_put() in the error handling path of nfs_sysfs_init().

Triki argued that when kset_register() fails, it does not clean up the underlying kobject, and therefore calling kfree() directly is incorrect:

"When kset_register() fails, it does not clean up the underlying kobject. Calling kfree() directly is incorrect because the kobject within the kset has already been initialized, and its internal resources or reference counting must be handled properly."

The patch cited commit 943aef2dbcf75 ("NFS: Open-code the nfs_kset kset_create_and_add()") as the source of the regression.

Review and Rejection

Benjamin Coddington responded swiftly, disputing the correctness of the patch on the same day:

"I don't think this patch is correct — the kobj is not initialized yet, and on error return from kset_register() you'll likely get the WARN from lib/kobject.c:734 kobject_put() when calling kset_put()."

Coddington suggested that there might be a leak of kobj->name and recommended using kfree_const() instead. He also asked for clarification on how the issue was discovered:

"Did you test this — how did you determine this was a problem?"

Trond Myklebust, the Linux NFS client maintainer, provided the definitive answer later that day:

"If you take a look at kset_register(), you'll see that it does free the kobj.name pointer if there is an error when adding the kobject. IOW: there is no bug in the current code."

Resolution

Salah Triki acknowledged the feedback and withdrew the patch:

"Thanks for the clarification. You're right, kset_register() already frees kobj.name on failure, and the kobject is not fully initialized at that point. I double-checked the error path in kset_register(), and the current cleanup in nfs_sysfs_init() is correct. Apologies for the noise — I'll drop this patch."

Key Technical Points

  1. kset_register() error handling: When kset_register() fails, it internally frees the kobj.name pointer and does not leave resources that require kobject_put() cleanup, since the kobject is not yet fully initialized at that point.

  2. Correctness of existing code: The current use of kfree() in the error path of nfs_sysfs_init() is correct because kset_register() handles its own internal cleanup on failure.

  3. Potential for warnings: Applying Triki's proposed patch would likely trigger a warning from lib/kobject.c:734 in kobject_put() when kset_put() is called, since the kobject has not been properly initialized.

Conclusion

This thread represents a case of a well-intentioned but incorrect bug fix submission. The NFS client's sysfs initialization error handling was found to be correct as-is, with no memory leak present. The maintainers' quick review and clear explanation helped prevent an unnecessary regression from being introduced into the codebase.
