AppArmor VFS Locking Patch: Sparse Warning and Return-Value Bug

Summary

AppArmor Patch in VFS Directory Locking Series: Sparse Warning and Return-Value Bug

Overview

This thread covers activity around [PATCH 04/13] Apparmor: Use simple_start_creating() / simple_done_creating() submitted by Neil Brown on February 4, part of a broader 13-patch series titled "Further centralising of directory locking for name ops." This is a VFS refactoring effort rather than a new feature or bug fix, though it introduced a minor return-value bug that was caught by automated testing.

Context: VFS Directory Locking Centralization

Neil Brown's overarching goal is to transition VFS directory locking from whole-directory locks to per-name locking. In the cover letter he explained:

"I am working towards changing the locking rules for name-operations: locking the name rather than the whole directory."

Patch 04/13 specifically converts AppArmor's aafs_create() function in security/apparmor/apparmorfs.c to use the centralized simple_start_creating() and simple_done_creating() helpers instead of explicit parent inode locking. Brown noted:

"This removes the need to check for an existing entry (as simple_start_creating() acts like an exclusive create and can return -EEXIST), simplifies error paths, and keeps dir locking code centralised."

Bug Identified: Return Value Error

The kernel test robot reported a sparse warning on February 4 here:

"sparse: Using plain integer as NULL pointer"

The issue is at line 295 of security/apparmor/apparmorfs.c, where the function aafs_create() — which returns a struct dentry * — incorrectly returns 0 (an integer) instead of NULL on success. The problematic code path is:

error = __aafs_setup_d_inode(dir, dentry, mode, data, link, fops, iops);
simple_done_creating(dentry);
if (error)
    goto fail;
return 0;   /* BUG: should be return NULL or return dentry */

Jeff Layton confirmed this in his review on February 5:

"As KTR points out, this should be 'return NULL;'"

He granted a conditional Reviewed-by tag:

"Assuming you fix the minor problem above. Reviewed-by: Jeff Layton jlayton@kernel.org"

NFS Client Relevance

While this patch does not directly affect NFS client code, it is part of a series that includes patch 06/13, which modifies fs/nfsd/nfs4recover.c's purge_old() function to use start_removing_noperm()/end_removing(). This NFS server-side change was reviewed without comment by Jeff Layton. The broader VFS locking refactoring has implications for all filesystems, including NFS, as it paves the way for per-name locking semantics that will eventually affect how directory operations are serialized across all VFS users.

Conclusion

This sub-thread is brief: one automated warning from the kernel test robot and a conditional Reviewed-by from Jeff Layton contingent on fixing the return-value bug. The patch converts AppArmor's filesystem creation code to use centralized VFS locking helpers, reducing code complexity but introducing a trivial yet real bug — returning 0 instead of NULL from a function returning struct dentry *. No resolution was reached within this week's window; the fix awaits an updated patch version.
