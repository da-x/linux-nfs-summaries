AUTOSEL backports NFS fallocate EOF fix and xprtrdma pool slack

Summary

Sasha Levin’s AUTOSEL machinery dropped two NFS client bug-fix backports onto linux-nfs on 31 August, both already signed off upstream by NFS maintainer Anna Schumaker. There is no review traffic in-window: no Acked-by, no NACK, no “please drop this from stable.” The week’s story is therefore the content of the fixes themselves — a stale-i_size hole in the NFSv4.2 fallocate path, and a request-pool undersize that can stall RPC/RDMA slot allocation after Send-gated recycling — and the fact that AUTOSEL is now pushing them into long-lived stable trees.

The cover for the batch, Message-ID <20260831133314.4125787-1-sashal@kernel.org>, is not present as a standalone linux-nfs post. The two patches that did land on the list sit in that same AUTOSEL series: Dai Ngo’s NFSv4.2 EOF update for 6.18–6.1, and Chuck Lever’s xprtrdma pool slack for 6.18–5.10.

Type of change

Both postings are stable backports of client bug fixes. Neither is a protocol change, a new userspace API, or a feature. One is metadata-cache correctness in nfs.ko; the other is transport-pool sizing in xprtrdma.

NFS: stale EOF after NFSv4.2 fallocate / ZERO_RANGE

Levin’s AUTOSEL 6.18–6.1 posting is Dai Ngo’s fs/nfs/nfs42proc.c fix, upstream commit 35168eb947f230aaa35fd8416a30563ef89f5421. The original April posting is Ngo’s v1. The failure mode is a client-side size mismatch that xfstests generic/075 hits whenever the client holds an NFSv4 write delegation:

"Generic/075 reliably exposes a regression when the client holds an NFSv4 write delegation: ZERO_RANGE/ALLOCATE extends the file on the server, but the local inode keeps the old i_size."

The post-op WCC refresh is not a safety net here. Ngo’s diagnosis is that the client initiated the size change, then asked the attribute path to learn it from the server — and that path is designed not to overwrite i_size while a delegation is outstanding:

"The test then fails with 'Size error' because the post-op attribute refresh refuses to touch i_size while a delegation is outstanding, and the cached EOF was never marked stale."

The surgical fix is in _nfs42_proc_fallocate(), the common success path for NFSv4.2 ALLOCATE, DEALLOCATE, and ZERO_RANGE. On RPC success the client now:

  • computes newsize = offset + len and bumps i_size when the operation extends the file, under inode->i_lock;
  • always marks NFS_INO_INVALID_BLOCKS, because the on-disk block count can change even when size does not (hole punch / deallocate);
  • keeps the existing suid-stripping invalidation in that same lock region, then still calls nfs_post_op_update_inode_force_wcc().

That is the same “update locally when delegation blocks server-driven refresh” pattern the writeback path already uses. DEALLOCATE does not spuriously grow the file: the newsize > i_size_read() guard is false when punching a hole. Ngo reports:

"Tested with xfstests generic/075 over NFSv4.2."

Anna Schumaker’s Signed-off-by is on the AUTOSEL copy. There is still no Fixes: tag, which is why AUTOSEL rather than an explicit Cc: stable is doing the backport work. The range — 6.18 back through 6.1 — is the interesting client-development fact this week: _nfs42_proc_fallocate() and write delegations have been in those trees for years, so a stale EOF after fallocate(2) extend is not a 6.18-only regression. FALLOC_FL_ZERO_RANGE made the path more visible, but ALLOCATE with a write delegation was already enough to leave i_size behind.

For NFS client users this is a medium-severity metadata bug, not a crash. Applications that fallocate()-extend a delegated NFSv4.2 file and then trust stat() / lseek(SEEK_END) can see the old length, mis-size subsequent I/O, or fail tests that check size. Unprivileged writers can trigger it; it is deterministic, not a race. The AUTOSEL posting did not attract a “too risky for 6.1” objection in-window.

xprtrdma: request-pool slack after delayed recycling

Thirty seconds later Levin posted AUTOSEL 6.18–5.10 of Chuck Lever’s net/sunrpc/xprtrdma/verbs.c change, upstream 64bf6892057b746c55bcc045b9492741b72d8d27. This is patch 3 of Lever’s May series “[PATCH v3 0/5] xprtrdma: Decouple req recycling from RPC completion” (cover, patch 3).

The parent series is a real client transport correctness fix. rl_kref had been doing two jobs at once: waking the RPC task from the Reply, and returning the rpcrdma_req to the free pool. Lever’s cover stated the use-after-free / wrong-bytes-on-the-wire failure:

"rl_kref currently conflates two lifetimes through one refcount: it gates when a Reply can wake its RPC task, and it gates when an rpcrdma_req can return to its free pool."

A Send that used only pre-registered buffers took no Send-side reference. If the Reply arrived first, the handler dropped rl_kref to zero and freed the req while the HCA could still be DMA-reading the send buffer. A retransmission could then put different bytes on the wire. The series makes recycling wait for Send completion.

That wait is the reason the pool must grow. Once a completed RPC’s rpcrdma_req can sit pinned on the sendctx ring until the next signaled Send completion, a credit-window-legal new RPC can fail to allocate a req. Lever’s AUTOSEL commit message is explicit that this is slack, not a higher flight ceiling:

"After the previous patch gates req recycling on Send completion, a completed RPC's rpcrdma_req can remain pinned by the sendctx ring until the next signaled Send completion releases it."

"The req pool, however, must exceed max_reqs by enough that this recycle delay does not stall a slot allocation that the credit window would admit."

The bound is the existing Send-signaling batch: frwr_open() sets re_send_batch to re_max_requests >> 3 (one signaled Send in eight). Worst case, max_reqs / 8 reqs are pinned, with a one-slot floor when the shift rounds to zero. The sendctx ring and the hardware Send Queue stay sized for re_max_requests; xprt_request_get_cong() still gates against xprt->cwnd. Lever’s operational claim:

"The pool slack does not raise that ceiling -- it only lets allocation keep pace with the credit window during the brief interval in which earlier reqs are pinned waiting for the next signaled completion."

The code change is one allocation site in verbs.c: allocate max_reqs + DIV_ROUND_UP(max_reqs, 8) request objects, and name that slack at the call site so it stays tied to the 1/8 signaling batch. Anna Schumaker signed off. AUTOSEL’s 6.18–5.10 range is wider than the fallocate fix, which is consistent with xprtrdma living in those stables — but it only makes sense if the prerequisite “decouple recycling from RPC completion” patch is already in those trees (or travels with this one). Nobody on linux-nfs raised that dependency question this week.

Evolution of the discussion

There is no evolution on-list this week. Levin posted the two AUTOSEL patches; the list was silent. The technical arguments are therefore the ones already frozen in the upstream commit messages:

  • Ngo: local i_size / NFS_INO_INVALID_BLOCKS update on fallocate success, because delegated attribute refresh will not do it.
  • Lever: extra max_reqs/8 req objects so Send-gated recycling cannot starve a credit-window-admitted RPC.

Prior-week context is only the original postings (April for Ngo, May v3 for Lever). Neither original thread is active this week.

Client-development takeaways

These are the NFS client fixes that matter this week, even though they arrived as stable spam rather than a new patch series:

  1. nfs.ko fallocate + write delegations. Anyone running NFSv4.2 with delegations (the common enterprise case) can extend a file via fallocate() / FALLOC_FL_ZERO_RANGE and keep a stale EOF until something else invalidates the inode. The fix belongs in every stable that has _nfs42_proc_fallocate(). Watch 6.1, 6.6, 6.12, and 6.18 for the commit; generic/075 is the regression test.
  2. xprtrdma request lifetime. The slack patch is the operational half of a UAF-class transport bug: recycling must wait for Send DMA, and the pool must be large enough that waiting does not look like congestion. NFS/RDMA client deployments on 5.10–6.18 should see both the decoupling patch and this slack, not one without the other.
  3. No protocol work. Wire ALLOCATE / ZERO_RANGE / RPC-RDMA credits are unchanged. This is cache coherency and transport resource accounting.

Conclusions

  • Bug fixes, not features. AUTOSEL is backporting two already-merged NFS client corrections.
  • Fallocate EOF: on successful NFSv4.2 ALLOCATE/ZERO_RANGE, the client must itself extend i_size and invalidate block counts; post-op attributes will not, while a write delegation is held. Quote of record remains Ngo’s “Size error” / generic/075 report.
  • xprtrdma slack: after Send-gated recycling, allocate max_reqs + DIV_ROUND_UP(max_reqs, 8) reqs so pinned sendctxes cannot stall a credit-legal RPC. The SQ and sendctx ring stay at re_max_requests.
  • This week’s list conclusion: none. No reviewer objected, and no reviewer confirmed. The patches sit in AUTOSEL queues for 6.18–6.1 (fallocate) and 6.18–5.10 (xprtrdma) unless a stable maintainer drops them off-list.
