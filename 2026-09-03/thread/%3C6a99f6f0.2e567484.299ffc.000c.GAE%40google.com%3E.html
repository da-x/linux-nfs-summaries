syzbot: hung task in nfsd4_cld_tracking_init on nfsdcld upcall

Summary

This is a bug report, not a feature and not a protocol change. Late on 3 September, syzbot filed a new hung-task against NFSD’s NFSv4 client-tracking (cld) upcall. There is no human reply in this thread, no patch, and no #syz dup: against the week’s other nfsd hangs. The stack is server-side — write_threads → nfsd4_cld_tracking_init — but the waiter is the shared SUNRPC rpc_pipefs completion that NFS client idmap, gssd, and pNFS blocklayout also sit on, and that Chuck Lever spent this same week rewriting.

Classification

syzbot hung syz-executor224 for more than 143 seconds on upstream HEAD 940de590b839 (Merge tag 'hardening-v7.3-rc2'), a PREEMPT(full) syzkaller build, untainted:

"INFO: task syz-executor224:5626 blocked for more than 143 seconds. Not tainted syzkaller #0"

Unlike several sibling reports this week, this one already has both a syz reproducer and a C reproducer. syzbot asked that any fix carry:

"Reported-by: syzbot+edbebd898142ee5e24ce@syzkaller.appspotmail.com"

Nobody used the #syz test: hook before the week closed. This thread has no prior weekly history; GlobOutputs found no earlier summary under this root.

The stack: GetVersion, not rpcbind

The hung task is in D-state inside __wait_for_common / schedule_timeout, i.e. an uninterruptible completion wait, not a mutex acquire:

"__cld_pipe_upcall fs/nfsd/nfs4recover.c:673 [inline] cld_pipe_upcall fs/nfsd/nfs4recover.c:691 [inline] nfsd4_cld_get_version fs/nfsd/nfs4recover.c:1425 [inline] nfsd4_cld_tracking_init+0x4be/0x10f0 fs/nfsd/nfs4recover.c:1490 nfsd4_client_tracking_init+0xe5/0x1c0 fs/nfsd/nfs4recover.c:1941 nfs4_state_start_net.cold+0xb7/0x480 fs/nfsd/nfs4state.c:9838 nfsd_startup_net fs/nfsd/nfssvc.c:391 [inline] nfsd_svc+0x54a/0x7d0 fs/nfsd/nfssvc.c:775 write_threads+0x316/0x600 fs/nfsd/nfsctl.c:438"

That is NFSD startup, not listener rebuild. Writing /proc/fs/nfsd/threads starts the server; nfs4_state_start_net() then probes nfsdcld with a GetVersion upcall before NFSv4 client tracking is live. __cld_pipe_upcall() queues a struct rpc_pipe_msg and waits on cu_done with TASK_UNINTERRUPTIBLE. If the daemon never answers — or answers in a way that never completes the waiter — the threads writer never returns.

The lock listing makes the blast radius explicit. The hung task already holds three locks, on CPU 1:

#LockSite
0&f->f_pos_lockfdget_pos
1sb_writers#9ksys_write
2nfsd_mutexwrite_threads+0x288 (nfsctl.c:436)

This is not the week’s rpcbind-under-mutex story. The holder is the hung task: write_threads took nfsd_mutex and then blocked in the cld pipe. Every other nfsd admin path — netlink listener_set, unlock_filesystem, write_ports, write_versions, umount via nfsd_shutdown_threads — queues behind a GetVersion upcall that is not coming back. The NMI backtraces are a red herring for the NFS path (CPU 1 is khungtaskd dumping stacks; CPU 0 is serial8250_console_write).

Same waiter Lever already named; complementary failure to Alemi’s KASAN

This dump is the hang face of a bug class the list has been working all week. Farhad Alemi’s 7.1-rc5 syzkaller report was a KASAN vmalloc-OOB because __cld_pipe_upcall() returned too soon, leaving a stack rpc_pipe_msg queued. Chuck Lever’s v2 series ([PATCH v2 0/8] Fix premature completion of rpc_pipefs upcalls, 1 September) is the opposite failure, described in the cover letter before this syzbot id existed:

"Guarding the reply exposes the opposite failure. Once a daemon has read a whole upcall, rpc_pipe_read() unlinks the message from every pipe list, so nothing the pipe purges on close can reach it. A daemon that exits between the read and the write leaves its waiter sleeping uninterruptibly with no way back."

And, from v2 patch 3 / the v1 diagnosis of a faulting downcall:

"__cld_pipe_upcall() waits on cu_done uninterruptibly, so the nfsd thread that sent the upcall is stuck, and nfsd shutdown hangs behind it."

This week’s stack is exactly that waiter, entered from nfsd4_cld_get_version rather than GraceStart. Two holes in current __cld_pipe_upcall() produce a 143-second hung-task:

  1. No complete on pipe close. cld_upcall_ops has no .release_pipe. Once nfsdcld has read the GetVersion record, rpc_pipe_read() unlinks the message; if the daemon then exits (or never writes a downcall), cld_pipe_destroy_msg() does not complete cu_done. Lever’s v2 patch 7 is the intended fix: complete consumed-but-unanswered upcalls with -EPIPE on close, not the -EAGAIN that would make cld_pipe_upcall() retry.
  2. No complete on a faulting reply copy. cld_pipe_downcall() drops the xid from cn_list before copy_from_user(). A faulting write returns -EFAULT without waking the waiter, and a retry cannot find the upcall. v2 patch 3 records the fault and completes.

A third, older path is also in scope for a syzkaller environment: the cld pipe is created with RPC_PIPE_WAIT_FOR_OPEN, so an absent nfsdcld queues the GetVersion message and waits for a daemon that never appears. If cld_pipe_destroy_msg() still refuses to complete “because a downcall was expected,” the timeout/purge path does not save write_threads either.

Lever’s v2 is not in the kernel syzbot tested. The report is against linus 940de590b839; the eight-patch series was posted to the list on 1 September and had no Acked-by, no merge, and no #syz fix: before this filing. The C reproducer is therefore a test vector for that series, not a demonstration that it failed.

This is also not Jeff Layton’s listener_set / rpcbind hang, which dominated the week’s other [syzbot] [nfs?] INFO: task hung in … subjects (nfsd_nrthreads, nfsd_nl_unlock_filesystem_doit). Those waiters sit in __mutex_lock(nfsd_mutex) while write_ports or nfsd_nl_listener_set_doit talks to a silent rpcbind. Here the threads writer is the holder, and the I/O is the nfsdcld pipe. Deduplicating this extid against the rpcbind reports would be wrong.

NFS client impact

There is no client function on the stack and no client patch in this thread. The stall still sits on paths NFS clients actually use, and the waiter is the same rpc_pipefs object the client copies.

  • NFSv4 server never finishes coming up. nfsd4_client_tracking_init() is on the nfs4_state_start_net() path. Until GetVersion returns, nfsd_svc() does not complete, /proc/fs/nfsd/threads stays in D-state, and there is no NFSv4 state machine. A client mount against that server simply does not complete for the duration of the hang — 143 seconds in this dump, unbounded if the hung-task watchdog is disabled.
  • Reclaim and grace depend on this upcall. nfsdcld is how the server persists client ids across restart. A GetVersion that never completes means tracking never initializes, so even after an operator kills the stuck echo the next startup has no daemon protocol version and no reclaim database. NFSv4 clients that expected to reclaim opens, delegations, and locks after a server restart lose that contract.
  • nfsd_mutex turns a daemon stall into a control-plane DoS. While write_threads holds the global nfsd lock across __cld_pipe_upcall(), export-cache downcalls, listener changes, NFSD_CMD_UNLOCK_FILESYSTEM, and umount-time nfsd_shutdown_threads all block. That is the same mutex the week’s rpcbind reports already showed as a single point of failure; this dump proves the cld pipe is another synchronous userspace round-trip taken under it.
  • Shared waiter with the NFS client. __cld_pipe_upcall() is the completion model FAN YE’s pNFS blocklayout series treated as safe, and that Lever’s v2 patches 5 and 8 rewrite on the client. gss and idmap already keep rpc_pipe_msg in a heap object and gss already releases what a departing daemon left behind; cld and bl_resolve_deviceid() did neither. A dying blkmapd that has read a device-map upcall and then exited is the client-side twin of this hang, except the client waiter also holds nn->bl_mutex and freezes every later GETDEVICEINFO in the net namespace. Client developers watching this syzbot id are looking at the nfsd half of that audit.

Nothing in this week’s other linux-nfs traffic — Layton’s listener_set v5 landing in nfsd-testing, the svc_addsock -EBUSY duplicate — touches __cld_pipe_upcall() or nfsd4_cld_get_version. They do not mitigate this hang.

Status

  • Type: hung-task / DoS in the nfsd procfs startup path (write_threads → nfsd4_cld_tracking_init → __cld_pipe_upcall). Uninterruptible wait on the nfsdcld GetVersion upcall while holding nfsd_mutex. Complementary to Alemi’s premature-completion KASAN, not a duplicate of the rpcbind listener_set hangs.
  • Reproducer: yes. C reproducer and syz reproducer linked from the report.
  • Human reply: none in this thread as of 3 September.
  • Likely on-list fix, not yet applied here: Lever’s v2 patches 3 and 7 (complete on copy fault; complete on pipe close with -EPIPE), with patches 1–2 moving the message off the stack so a hostile or broken nfsdcld cannot also leave a list_head in a returned frame. That series is unreviewed and unmerged from its own thread; this syzbot kernel does not contain it.
  • Fix tag requested: Reported-by: syzbot+edbebd898142ee5e24ce@syzkaller.appspotmail.com.
  • Test hook unused: a #syz test: of Lever’s v2 (or a #syz fix: once it lands) is the obvious next step. Nobody sent either on this thread.

Until __cld_pipe_upcall() completes on every path that drops the pipe — close, purge, copy fault, and “daemon never opened” — starting NFSD via /proc/fs/nfsd/threads remains a way to pin nfsd_mutex for minutes and leave NFSv4 clients with a server that never finishes coming up. This week’s filing does not change Lever’s diagnosis. It gives maintainers a C reproducer whose stack is nfsd4_cld_get_version, which is enough to test the close-path patch and not enough to ship it from this thread.
