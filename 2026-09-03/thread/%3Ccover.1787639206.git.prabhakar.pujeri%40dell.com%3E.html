nfsdctl clients table held for kernel softlockup

Summary

The first review of Dell’s Prabhakar Pujeri nfs-utils series landed this week, and it was a hold, not an ACK. Jeff Layton and nfs-utils maintainer Steve Dickson parked the v1 nfsdctl clients work until a companion-kernel defect — a Sashiko-flagged softlockup in the NFSD Netlink client dump — is fixed. The series remains a new admin feature (a userspace consumer of a proposed Generic Netlink ABI), not a wire-protocol change and not an NFS client bug fix. Nothing in this thread was applied.

Brief bridge from last week

Last week Pujeri posted “[PATCH v1 0/3] nfsdctl: list NFSv4 clients” (cover) as the userspace half of his NFSD Netlink client-state ABI. The three patches taught nfsdctl threads to print an in-grace boolean, added a privileged nfsdctl clients table (client ID, peer address, minor version, state, lease remaining, reclaim, callback), and extended that table with session and stateid-record counts. Compatibility was attribute-driven: older kernels omit grace, missing counts print as dashes, unknown enums print as "unknown", and a bundled nfsd_netlink.h lets nfs-utils build before the kernel header exists.

There were no nfs-utils replies last week. The kernel companion, however, had already drawn design pushback: Layton rejected a v4-only grace flag, and Chuck Lever asked that any new API not freeze grace as a server-wide boolean. That ABI mismatch is still hanging over this userspace consumer.

This week: first review is a hard wait

On 28 August, Jeff Layton replied to the cover with a short, explicit apply-blocker. He did not nit the nfsdctl table formatting. He pointed at automated review of the kernel companion series and named a concrete runtime risk:

"Sashiko has some comments about this that probably need to be addressed before we apply these. There is potential for a softlockup in patch #3, in particular:"

The URL he cited is the kernel cover (cover.1787638668.git.prabhakar.pujeri@dell.com), not this nfs-utils thread. Patch #3 on that kernel series is the per-client session/stateid counter walk — the dump that walks client state under lock to populate the columns nfsdctl clients would print. A softlockup there is a server-side stall, not a cosmetic userspace issue: an operator (or a restart/failover harness) running nfsdctl clients against a busy NFSv4 server could livelock the nfsd dump path while it counts opens, locks, delegations, and layouts.

The implication for this thread is that nfs-utils cannot usefully land ahead of the kernel ABI it consumes. Even a clean nfsdctl table is worthless — and potentially harmful as an operational tool — if the dump it issues can softlock the server.

The next day, Steve Dickson — the person who would actually apply nfs-utils patches — accepted that sequencing:

"Okay... I'll wait to apply them until things get sorted out... but I will keep them on my todo list..."

That is the week’s conclusion on v1: not merged, explicitly deferred, still on the nfs-utils maintainer’s radar. There was no patch-level review of the grace display, the clients table, the IPv6/scope-ID formatting, or the configure UAPI probe. The only technical argument on this thread is “do not apply userspace until the kernel dump is safe.”

How this couples to the kernel ABI this week

The hold is not only about Sashiko. On the companion kernel thread the same day as Layton’s note here, Pujeri agreed with Lever to drop the grace-reporting patch from the client-visibility reroll so a server-wide boolean does not freeze the ABI before nfsd can express per-export grace. Lever’s one-line ACK was “WFM!” That means nfsdctl v1 patch 1/3 — the threads grace column — is already aimed at an attribute that will not land, even before the softlockup is fixed.

No NFS client kernel code is touched in either series. The client-visible effect, if both sides eventually land, is still operational: a compact way to watch leases, reclaim, callbacks, and per-client stateid load from the server without scraping /proc/fs/nfsd/clients. Until the kernel dump no longer risks a softlockup, and until grace reporting is redesigned with an explicit scope, that operational picture is incomplete.

Status

  • v1 nfsdctl series: posted, first-reviewed, not applied. Dickson will wait.
  • The apply-blocker is a kernel bug risk (softlockup in the client-state count walk), plus still-open ABI work on grace.
  • A grace-less nfsdctl v2 cover appeared later in the week as a new thread (<cover.1787988918.git.prabhakar.pujeri@dell.com>); that reroll is out of scope here, but it is the expected follow-through on both the Sashiko hold and the dropped grace patch.
