Lever hardens cld and blocklayout rpc_pipefs waiters after KASAN

Summary

This week’s linux-nfs traffic on Farhad Alemi’s syzkaller report produced a bug-fix / hardening series, not a protocol change and not a new feature. Two days after Jeff Layton asked Alemi to retest 7.1-rc5 on a newer tree, Chuck Lever posted [PATCH 0/5] Fix premature completion of rpc_pipefs upcalls — a five-patch diagnosis of the KASAN vmalloc-out-of-bounds in rpc_queue_upcall(), plus two related cld holes he found while reading the downcall, plus a client-side pNFS blocklayout rewrite of the same waiter class. There are no replies in this thread in-window. The series is therefore an unreviewed v1, with Lever asking Alemi to close the loop.

"Farhad, a run of your reproducer against this series would help."

That matters to NFS client work more than the subject line suggests. Four in-tree consumers sit on rpc_pipefs. Lever’s cover letter draws the line explicitly: gss and idmap already keep struct rpc_pipe_msg in an object that outlives the waiter; cld and blocklayout do not. Patch 5 is the client patch. It is also the first on-list maintainer rewrite of bl_resolve_deviceid() after FAN YE’s lost-wakeup series treated __cld_pipe_upcall() as the safe waiter.

Prior week, in brief

Alemi of ASU’s SEFCOM lab mailed a syzkaller crash on Linux 7.1-rc5 whose subject already named the class: [BUG] sunrpc: rpc_pipe_msg left queued on a stack frame (nfsd cld upcall). The splat was a KASAN vmalloc OOB in __list_add_valid_or_report() while NFSD was starting client tracking (nfsd4_cld_grace_start → cld_pipe_upcall → rpc_queue_upcall). Layton’s only in-thread reply, two days later, asked for a retest against Linus’ master or Lever’s nfsd-testing branch and did not identify a Fixes: candidate. Separately, FAN YE’s blocklayout v2 had replaced bl_resolve_deviceid()’s open-coded wait with a completion “the way __cld_pipe_upcall() waits,” and reset bl_mount_reply so a purged upcall could not return a stale device. Completions still do not make a stack rpc_pipe_msg safe if the waiter can return with the message linked. Lever’s series is the first posting that treats those two threads as the same bug class.

The diagnosis

Lever’s cover letter restates Alemi’s crash as a matching-rule failure, not a generic unlink miss:

"The cld downcall matches a reply to its upcall by xid alone. If a write arrives before nfsdcld has read the upcall, the waiter returns while its struct rpc_pipe_msg is still queued, and the pipe is left holding a list_head into a dead stack frame."

The same pattern is on the client:

"The blocklayout device upcall has the same bug, plus two of its own: the waiter can go to sleep after the reply has arrived, and a reply left over from a purged upcall is taken as a fresh one."

He frames the series as hardening, not as an emergency, because the pipes are mode 0600:

"rpc_pipefs pipes are mode 0600, so the writer is a daemon running as root. These patches guard against a broken or hostile daemon, which is unlikely. So consider the series as hardening rather than urgent."

The gss and idmap consumers are the reference implementation:

"The gss and idmap consumers keep their message in an object that lives as long as the upcall and do not have this problem. The cld and blocklayout fixes also complete only once the daemon has consumed the whole message, and keep the message somewhere that outlives the waiter."

Reading cld_pipe_downcall() for that fix turned up two unrelated problems: a faulting copy_from_user() that strands the waiter (and hangs NFSD shutdown behind it), and an unchecked principal-hash length that reads past a stack array in nfsd4_cld_check_v2(). Those become patches 3 and 4. Base commit is e3c3b1a8188b; the change-id is 20260830-alemi-d9f420956e8d. Net diff: 78 insertions, 41 deletions across fs/nfsd/nfs4recover.c, fs/nfs/blocklayout/rpc_pipefs.c, fs/nfs/blocklayout/blocklayout.h, and fs/nfs/netns.h.

Patch 1: do not complete a cld upcall the daemon has not read

Patch 1 is the direct fix for Alemi’s KASAN hit. cld_pipe_downcall() currently matches on xid alone, so a write that arrives before nfsdcld has read the upcall completes __cld_pipe_upcall() while struct rpc_pipe_msg is still queued. The waiter returns, its stack frame goes away, and the next rpc_queue_upcall() walks a list_head into dead vmalloc stack:

"BUG: KASAN: vmalloc-out-of-bounds in __list_add_valid_or_report"

The call chain in the splat is rpc_queue_upcall → cld_pipe_upcall → nfsd4_cld_grace_start → nfsd4_cld_tracking_init. Lever’s rule is: record whether the daemon has consumed the whole message, and complete only when it has. cld_pipe_destroy_msg() already runs on every path by which the pipe releases a message, so it can maintain that flag under cn_lock. The GraceStart record stream is the compatibility check:

"nfsdcld sends its -EINPROGRESS downcalls only after reading the upcall, so the new check does not break the GraceStart record stream."

Tagged Fixes: f3f8014862d8 ("nfsd: add the infrastructure to handle the cld upcall"), Reported-by: Farhad Alemi, and Closes: the original report.

Patch 2: get the cld message off the stack

Patch 2 is the lifetime half of the same bug. Completing only after the daemon has read the message is still not enough if the message itself lives in the waiter’s stack frame and the peer that drives those completion rules is userspace:

"Only the completion rules keep that frame alive for as long as the pipe refers to it, and the peer that drives those rules is an untrusted userspace daemon. The gss and idmap upcalls do not take that on: each keeps the message in the object it already allocates."

Lever puts struct rpc_pipe_msg in struct cld_upcall, beside the reply buffer it already carries. cld_pipe_destroy_msg() then reaches the upcall from the message directly rather than through msg->data. That is the same object-lifetime model the NFS client already uses for gssd and idmapd. No Fixes: tag; this is structural hardening on top of patch 1.

Patch 3: a faulting reply copy must still complete the waiter

Patch 3 is the first of the two holes Lever found while reading the downcall. cld_pipe_downcall() removes the matching upcall from cn_list before copy_from_user(). If that copy faults, the downcall returns -EFAULT without completing the upcall, and a retried write cannot find it because the xid is gone. The waiter is uninterruptible:

"__cld_pipe_upcall() waits on cu_done uninterruptibly, so the nfsd thread that sent the upcall is stuck, and nfsd shutdown hangs behind it."

The fix records the fault in the upcall’s pipe message and completes it, so the waiter returns the error to its client-tracking operation instead of hanging nfsd. Same Fixes: f3f8014862d8 as patch 1. Client-visible impact is indirect: a wedged nfsd during nfsdcld misbehavior blocks reclaim and new mounts.

Patch 4: reject an oversized principal hash from nfsdcld

Patch 4 is a bounds check, not a pipefs lifetime fix. __cld_pipe_inprogress_downcall() takes the principal hash length from the daemon’s GraceStart downcall without checking it against the cc_princhash payload, which holds at most SHA256_DIGEST_SIZE bytes. The length is stored verbatim in the reclaim record. Later, nfsd4_cld_check_v2() hands it to memcmp() against a digest array of SHA256_DIGEST_SIZE on the stack:

"A length up to U8_MAX reads past the end of that array, and the stray bytes can only make the comparison fail, denying the client its reclaim."

That is a client-reclaim denial, not a crash: a hostile or broken nfsdcld can force every v2 reclaim to fail by overstating the hash length. Lever rejects a length larger than the wire field, matching the existing check on client-name length. Tagged Fixes: 6ee95d1c8991 ("nfsd: add support for upcall version 2").

Patch 5: the NFS client fix — complete a blocklayout device upcall only on its own reply

Patch 5 is the important NFS client development in this thread. bl_pipe_downcall() currently wakes bl_resolve_deviceid() on any write of the right size, without checking that blkmapd has read the upcall being replied to. A write that arrives first returns the waiter while its stack rpc_pipe_msg is still queued — Alemi’s cld bug, on the pNFS blocklayout device-map pipe. Reaching that pipe takes root, so the trigger is a broken or hostile blkmapd.

Lever lists two further client defects that FAN YE’s v2 had already named, and then goes further than a completion swap:

"bl_resolve_deviceid() sets TASK_UNINTERRUPTIBLE only after rpc_queue_upcall() has made the message visible, so a reply that lands in between wakes a running task and the schedule() that follows sleeps forever holding bl_mutex. And nn->bl_mount_reply is never reset, so when the pipe purges an unread upcall the waiter takes the previous reply as its own."

The rewrite:

  • Moves the message into struct nfs_net, where bl_mutex already limits the pipe to one upcall per net namespace. That is the gss/idmap lifetime rule applied to blocklayout: the rpc_pipe_msg outlives the waiter.
  • Accepts a reply only while blkmapd has read the whole message and no earlier reply has been taken; any other write is -EINVAL.
  • Waits on a completion so the reply cannot slip past the sleep, and checks msg->errno before trusting it.

"Move the message into struct nfs_net, where bl_mutex already limits the pipe to one upcall per net namespace. Accept a reply only while blkmapd has read the whole message and no earlier reply has been taken, and reject any other write with -EINVAL. Wait for that reply on a completion so it cannot slip past the sleep, and check msg->errno before trusting it."

Tagged Fixes: fe0a9b740881 ("pnfsblock: add device operations") — the same origin commit FAN YE used. Relative to Ye’s v2, Lever’s patch is the superset: Ye closed the lost wakeup and the stale bl_mount_reply; Lever additionally refuses a downcall that does not belong to the current upcall, gets the message off the stack, and treats a hostile blkmapd as in-scope. Client-visible failures this closes are a kernel oops on the next rpc_queue_upcall(), a hang holding bl_mutex that serializes every later blocklayout device resolution, and a wrong device id after a purged upcall.

NFS client takeaway

The series is the first maintainer-level audit of the four rpc_queue_upcall() consumers against Alemi’s stack-queued rpc_pipe_msg class:

  • gss / idmap (client): already keep the message in a heap object that lives as long as the upcall. Lever cites them as the pattern. No change in this series.
  • cld (nfsd client tracking): xid-only matching plus a stack message. Patches 1–2 close the KASAN hole; patches 3–4 close a shutdown hang and a reclaim-denial bounds bug found on the same path.
  • pNFS blocklayout (client): same premature-completion bug, plus the lost-wakeup and stale-reply bugs Ye found. Patch 5 is the client fix, and it is a larger rewrite than Ye’s completion-only v2.

This is not a wire-protocol change. nfsdcld and blkmapd still speak the same upcall/downcall messages. The new kernel-side rule is: do not complete, and do not trust a reply, until the daemon has consumed the whole upcall, and never let rpc_pipe_msg live on a stack frame whose waiter can return while the pipe still holds it.

Where things stand

  • Kind of change: bug-fix / hardening series against SUNRPC rpc_pipefs waiters. Not a feature. Not a protocol change.
  • This week’s evolution: Alemi’s KASAN report and Layton’s retest request → Lever posts a five-patch v1 that names the matching-rule bug, moves both cld and blocklayout messages off the stack, and folds in two extra cld holes. No Reviewed-by, Acked-by, or tester reply landed on this thread before the week closed.
  • Client impact: pNFS blocklayout device resolution is the in-tree NFS client consumer being rewritten; gss and idmap are the reference; a hostile nfsdcld can still deny v2 reclaim via an oversized principal hash until patch 4 lands.
  • Open loop: Lever asked Alemi to rerun the reproducer against this series. Until that result, or a review, shows up, v1 is the on-list candidate and not yet merged from this thread.

A later v2 of the same work appears as a separate thread later in the week; this v1 thread itself ends with Lever’s five patches and silence.
