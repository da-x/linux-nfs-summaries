syzbot: hung task in nfsd_nl_unlock_filesystem_doit behind listener_set

Summary

This is a bug report — a hung-task / control-plane DoS on the NFS server generic-netlink family, not a protocol change and not a new feature. There is no NFS client code in the stack and no human reply. Google's syzbot hung nfsd_nl_unlock_filesystem_doit (NFSD_CMD_UNLOCK_FILESYSTEM) on the global nfsd_mutex while a sibling netlink listener_set already holds that mutex. The unlock handler is an innocent waiter; the stall is the same rpcbind-under-mutex long hold Jeff Layton diagnosed in July.

Classification

On Friday, 28 August, syzbot filed a single unreproduced report against upstream HEAD 45c13f3f9e3b (Merge tag 'hwlock-v7.3'):

"INFO: task syz.2.1768:11730 blocked for more than 143 seconds."

"Unfortunately, I don't have any reproducer for this issue yet."

The kernel is a PREEMPT(full) syzkaller build, tainted L (SOFTLOCKUP). The hung task entered via genl_family_rcv_msg_doit / sendmsg and blocked in __mutex_lock at nfsd_nl_unlock_filesystem_doit+0x203/0x410 (fs/nfsd/nfsctl.c:2677). syzbot asked that any fix carry:

"Reported-by: syzbot+0093d3ab8d8eb2fdde82@syzkaller.appspotmail.com"

This thread has no prior weekly history. It is a new syzbot id, not a follow-up on last week's nfsd_nrthreads or listener_set reports, but the lock dump is the same class of failure those threads already named.

The lock dump: filesystem-unlock waits on listener_set, umount waits too

The hung stack itself only says "waiting for a mutex." The "Showing all locks held in the system" listing names three tasks on nfsd_mutex at once:

TaskHandlerRole
syz.0.1424/10896nfsd_nl_listener_set_doit (nfsctl.c:2057)holds nfsd_mutex (plus generic-netlink cb_lock)
syz.2.1768/11730 (the hung task)nfsd_nl_unlock_filesystem_doit (nfsctl.c:2677)waiting on nfsd_mutex (already holds cb_lock)
syz.1.2261/12930nfsd_shutdown_threads (nfssvc.c:582)waiting on nfsd_mutex while already holding s_umount from deactivate_super

This is not an AB-BA deadlock between unlock and listener_set. cb_lock is an rwsem, so the netlink tasks can hold it as readers. Both netlink ops take nfsd_mutex in the same direction. The hang is a long hold: listener_set is not releasing the global nfsd lock for more than 143 seconds, and every other nfsd netlink command — including the admin filesystem-unlock that walks NFSv4 client state — queues behind it.

The umount waiter is the extra wrinkle, and it is the same pattern the 25 July unlock_export dump already showed. syz.1.2261 holds &type->s_umount_key#75 taken in deactivate_super and then blocks in nfsd_shutdown_threads. That is not proven as a deadlock here — listener_set is not shown taking s_umount — but it is a lock-order hazard: any nfsd path that holds nfsd_mutex and then needs a superblock lock will deadlock against a umount that already took s_umount and is now waiting for nfsd_mutex. Even without that deadlock, a filesystem umount that sits in D-state for more than two minutes is a client-visible outage of its own.

The NMI backtrace is a red herring for the NFS path. CPU 0 is khungtaskd dumping stacks; the SOFTLOCKUP taint and the incidental tty / bridge / unix-dgram locks in the listing are syzkaller noise. The nfsd story is entirely listener_set holding nfsd_mutex across a slow operation while filesystem-unlock and server teardown wait.

Line numbers have moved since the summer reports (unlock_filesystem was nfsctl.c:2345 in the 14 August write_versions dump; listener_set was nfsctl.c:1964 in July). The hang has not.

Same waiter, now the subject line

nfsd_nl_unlock_filesystem_doit is NFSD_CMD_UNLOCK_FILESYSTEM: the administrator-driven path that walks the NFSv4 client hash tables to revoke open state, NLM locks, delegations, and in-flight async COPY for a whole superblock. Chuck Lever described that contract when he hardened the same three unlock entry points (write_unlock_fs, nfsd_nl_unlock_filesystem_doit, nfsd_nl_unlock_export_doit) in June:

"Writing to /proc/fs/nfsd/unlock_filesystem, or sending the NFSD_CMD_UNLOCK_FILESYSTEM or NFSD_CMD_UNLOCK_EXPORT netlink command, walks the NFSv4 client hash tables to revoke open state and cancel async COPY operations."

Those June fixes were crash bugs, not hangs. Musaab Khan's post-shutdown UAF and XIAO WU's startup-window NULL deref both came from walking nn->conf_id_hashtbl outside the window where the tables are live. Lever's follow-up switched the three unlock paths from testing nn->nfsd_serv to NFSD_NET_UP, which "brackets the window where the tables are live: set at the end of nfsd_startup_net() and cleared in nfsd_shutdown_net() after they are freed, both under nfsd_mutex." That work made the unlock command safe to run. It did not make it timely: the handler still takes the same global mutex that listener setup holds across synchronous rpcbind I/O.

The filesystem-unlock hang is not even new as a waiter. On 14 August syzbot already listed nfsd_nl_unlock_filesystem_doit as a secondary waiter behind a stuck write_ports in the write_versions dump. The 25 July nfsd_nl_unlock_export_doit report was the per-export twin of this command, with listener_set as the named holder. This week's mail is the first time unlock_filesystem itself is the hung-task subject — the whole-superblock revoke path, not just one export.

Root cause already diagnosed; still unpatched

Layton's July diagnosis of the cache-flush / listener_set hangs applies here almost verbatim:

"The hard problem here is that rpcbind registration is done synchronously under the nfsd_mutex. To talk to rpcbind, the kernel has to create a RPC client, which does a RPC ping first. If rpcbind is down then it can take up to a minute for the RPC ping to time out."

And:

"If we couple those delays with a long list of listeners, then it's easy to see how to reproduce the hang."

This dump names nfsd_nl_listener_set_doit as the holder at nfsctl.c:2057, so the mechanism does not need to be inferred. The netlink listener_set handler can install many sockets in one call; each one may try to register with local rpcbind while still holding nfsd_mutex. A down, slow, or not-yet-started rpcbind turns each registration into a tens-of-seconds stall. Two such stalls is 143 seconds of hung-task watchdog — exactly what syzbot observed.

Neil Brown's question from that earlier thread is still the design fork:

"Why are we waiting a whole minute for a local service to respond? If it hasn't responded in 1 second, is it ever really likely to?"

Layton's answer then — a shorter timeout is necessary but not sufficient, because "even at 1s, you could easily cause a lockup warning with just a few hundred listeners" — is why this new report will not be fixed by touching nfsd_nl_unlock_filesystem_doit itself. The unlock handler is not the bug. Any nfsd netlink op, including the admin-revocation command NFSv4 clients depend on for timely state teardown, takes the same global mutex that listener setup holds across rpcbind I/O.

The short-term hardening series (Layton's nfsd-nl-hang v2: 1024-entry cap, 1s local rpcbind timeout, non-fatal v2/v3 registration, richer extack) was still awaiting v3 as of mid-August. Last week Layton, after talking to Chuck Lever, changed the long-term plan: move most rpcbind SET/UNSET into userland, which would rev the nfsd netlink protocol. He was explicit about the near term:

"Right now, I don't have a timeline for working on this, so we're probably just going to have to suffer with more syzbot reports until that can come to fruition."

This week's unlock_filesystem report is that prediction, one day into the new week. Nobody #syz dup'd it against the July unlock_export hang or the August listener_set reports. Nobody used the #syz test: hook.

NFS client impact

There is no client patch here and no client-side bug to fix. The stall sits on server paths that NFS clients actually depend on for state teardown, for the server staying reachable, and for mounts completing.

  • Admin filesystem-revoke. NFSD_CMD_UNLOCK_FILESYSTEM is how an administrator tears down all NFSv4 opens, locks, delegations, layouts, and async COPY for a superblock without taking the whole server down — the "umount kills NFSv4 state" contract that landed earlier this year. If that handler sits in D-state for minutes behind nfsd_mutex, revoked state stays live: a client continues to hold opens it should have lost, a delegated write is not recalled, and an in-flight inter-server COPY is not cancelled. That is worse than the per-export UNLOCK_EXPORT hang of 25 July, because the blast radius is the whole filesystem.
  • Filesystem umount itself is a waiter. This dump shows deactivate_super → nfsd_shutdown_threads blocked on the same mutex while already holding s_umount. A server-side umount that cannot finish is a client-visible outage: the export is neither fully up nor fully gone, nfsd threads cannot be stopped, and any subsequent listener_set / thread-count change queues behind it. Linux NFS clients see that as a server that has gone silent, not as a netlink admin stall.
  • Control plane for every client, including NFSv4. While listener_set holds nfsd_mutex, other nfsd netlink and /proc/fs/nfsd writes block — versions, threads, exports, cache flush, unlock. New listeners do not come up. A client mount against a server that is still bringing up nfsd, or that is trying to revoke state for an export being taken down, simply does not complete for the duration of the hang. NFSv4 clients never talk to rpcbind, but they still need a live listener and a responsive control plane.
  • NFSv2/v3 discovery. The underlying rpcbind-under-mutex problem is specifically a v2/v3 client-visibility issue: nfsd will serve without a successful registration, but clients that find the server via portmap see a missing or stale table. Brown put it cleanly in July: "nfsd doesn't need the registration, only clients do." Until registration moves to userland — or until it no longer runs under nfsd_mutex — those clients keep depending on a kernel path that can stall the entire nfsd admin lock.

Nothing in this week's other linux-nfs traffic — Chuck Lever's NFSv2 NFSERR_ISDIR mapping for U-Boot, the cifs-fixes merge named in a sibling syzbot HEAD — touches nfsd_mutex or nfsd_nl_unlock_filesystem_doit. They do not mitigate this hang. The sibling nfsd_nrthreads report in this same week is the procfs twin (threads writer waiting on write_ports → rpcb_create_local); this report is the netlink filesystem-unlock twin of the same long hold.

Status

  • Type: hung-task / DoS bug in the nfsd netlink control plane (NFSD_CMD_UNLOCK_FILESYSTEM waiting on nfsd_nl_listener_set_doit). Same nfsd_mutex × synchronous rpcbind root cause as the July/August netlink and procfs reports; still unpatched.
  • Reproducer: none. syzbot said so explicitly.
  • Human reply: none in this thread as of 28 August. The related listener_set discussion already has a design fork (shorten rpc_ping, drop the mutex around registration, or move rpcbind to userland) but no merged fix and no timeline for the userland protocol rev.
  • Not a crash in the unlock path. The June UAF / NULL-deref work on nfsd_nl_unlock_filesystem_doit is a different failure mode. This dump is a hang, and the unlock function is not the site that needs the patch.
  • Fix tag requested: Reported-by: syzbot+0093d3ab8d8eb2fdde82@syzkaller.appspotmail.com.
  • Test hook unused: syzbot will keep the issue open until a #syz fix: / #syz dup: reply lands.

Until listener setup no longer holds nfsd_mutex across rpcbind I/O — or until that I/O fails in well under a second — every nfsd admin path, netlink or /proc/fs/nfsd, is another hung-task report waiting to happen. This week's unlock_filesystem filing does not change the diagnosis. It documents the whole-superblock revoke command, and a concurrent umount, sitting behind the same listener_set hold that already stalled export-install, export-revoke, cache flush, versions, and threads.
