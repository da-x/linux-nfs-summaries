rpcinfo stack overflow in rpcbdump()

Summary

This week’s linux-nfs traffic includes a one-message security fix for the userspace rpcinfo helper rather than a kernel NFS client change. There is no follow-up, ACK, or NAK in-window: Krzesimir Nowak posted a single patch against src/rpcinfo.c and the thread ends there.

What kind of change this is

This is a bug fix (a stack buffer overflow in a diagnostic client), not a protocol change and not a new NFS feature. The vulnerable path is rpcinfo’s rpcbdump() helper, which talks to an RPCBIND/portmapper-style service and prints the program versions that service advertises. That tool is part of the nfs-utils client-side toolkit operators use when debugging NFS mounts, so a crash or memory corruption there still sits on the NFS client workflow even though the kernel NFS client is untouched.

The defect

Nowak’s commit message is blunt about both the mechanism and the threat model:

"rpcinfo's rpcbdump() formats a server-controlled list of versions into a fixed size buffer with sprintf(). A malicious server returning a large number of versions may overflow it."

The shape of the bug is classic C string handling: a stack buffer of fixed size is filled with sprintf() while walking a version list that comes from the remote RPCBIND server. Because the number of versions is not under local control, a hostile or buggy server can make the formatted string overrun the stack slot. That is a client-side availability (and potentially memory-safety) issue for anyone who points rpcinfo at an untrusted host.

Michalis Vasileiadis is credited as the reporter (Reported-by: Michalis Vasileiadis <vmihalis.tmd@gmail.com>). Nowak signs the patch from a Microsoft address (Signed-off-by: Krzesimir Nowak <knowak@microsoft.com>).

The proposed fix

The patch is small: 12 lines in src/rpcinfo.c (7 insertions, 5 deletions). The ingest of this week’s archive omitted the hunk itself, but the surrounding description is enough to characterize the intent: stop treating a remote-controlled version list as something that will always fit a fixed sprintf() destination. In practical terms that means bounding the write (or otherwise refusing to keep concatenating versions once the local buffer is full) so a long version vector cannot smash the stack.

There is no discussion of alternative approaches this week—no request to switch to a heap buffer, no debate about truncating the printed version list versus failing the dump, and no review of whether other rpcinfo formatters have the same sprintf() pattern.

Status at week’s end

As of 2026-08-28 the patch is posted and unsigned-off by anyone else. No maintainer comment, no v2, and no indication it has been applied. For NFS client operators the takeaway is narrow but real: rpcinfo -p/rpcbdump() against an untrusted RPCBIND endpoint is currently unsafe until this (or an equivalent) lands in nfs-utils. Kernel NFS client I/O paths are not implicated.

No prior-week summary exists for this thread; the discussion begins and, so far, ends with Nowak’s PATCH.
