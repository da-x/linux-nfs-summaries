rpciod SMT affinity hits NFS/RDMA throughput regression

Summary

Chuck Lever’s RFC 6/8 overrides rpciod to WQ_AFFN_SMT so each SMT group gets its own unbound worker pool and lock. The patch is client performance work, not a protocol change: it is meant to cut native_queued_spin_lock_slowpath contention on the RPC state-machine workqueue. This week it ran into a throughput regression on a large NFS/RDMA box, and the follow-up data turned the story from “SMT is the culprit” into “a low-throughput mode still exists after v2 dropped the async-inline hop.”

The original commit message states the intent clearly:

"Set WQ_AFFN_SMT on rpciod so each SMT group gets its own pool and lock. Most UNBOUND workqueues never contend on the pool lock and profit from a coarser scope's cache locality. rpciod's sustained completion traffic makes the lock a first-order bottleneck, so the override belongs on this workqueue rather than in the system-wide default."

That is the Tejun Heo-suggested path from the parent RFC 0/8: do not change the global unbound default; retune the NFS queues. On Lever’s 12-core single-LLC system, WQ_AFFN_CACHE lost 30–40% of cycles in the rpciod pool lock, and WQ_AFFN_CACHE_SHARD still left only two six-core pools. v2 kept the SMT override (PATCH RFC v2 6/8) after dropping the v1 patch that ran the first async RPC states in the submitter.

Prior context (brief)

v1 was posted 31 August with no replies on this patch. Two days later Lever superseded the series. The important client-development change in v2 is that async RPC startup stays on rpciod: inlining the first FSM states let completion callbacks run in the submitter and re-created the pNFS read-resend vs. layoutreturn deadlock of 54e4a0dfa25d. That matters here because Tim’s first report was against v1, whose rpciod traffic pattern is heavier.

The v1 regression: SMT vs. cache_shard, live and reversible

On 2 September, Tim Menninger reported a large, bisected regression on a 96-CPU two-socket machine (48 physical cores, SMT-2):

"I am seeing a significant throughput regression from the rpciod SMT affinity change on a high-throughput NFS/RDMA workload."

"I bisected the regression to the patch that changes rpciod to use WQ_AFFN_SMT."

Numbers:

  • default cache_shard: ~45 GB/s
  • smt: some runs fall to ~15–25 GB/s

The failure is intermittent across workload starts and easier shortly after boot. Once a run is bad, the affinity knob is causal without restarting the workload:

"throughput recovers to ~45 GB/s immediately when I change /sys/bus/workqueue/devices/rpciod/affinity_scope to cache_shard, then regresses again immediately when I restore smt."

"Nothing else about the workload, mount, RPC connections, or RDMA connections is changed between those transitions."

wq_dump.py on that box:

  • SMT: 48 affinity pods (one physical core / two sibling CPUs)
  • CACHE_SHARD: 6 affinity pods (eight physical cores / sixteen logical CPUs)

Tim refused to guess at the lock or scheduler interaction:

"I have not yet identified the exact mechanism that causes the SMT configuration to lose throughput, so I don't want to speculate about the specific lock or scheduler interaction involved."

His merge bar is unambiguous:

"Given the magnitude of the regression, I think this needs to be understood before the rpciod SMT affinity change is merged."

This is an NFS client performance bug in the proposed workqueue override: a change that helps Lever’s 12-core, transport-limited 4KB NFSv3/RDMA harness can cut a 45 GB/s pNFS/RDMA streaming workload by more than half.

Lever’s diagnostic checklist

Chuck Lever thanked Tim and declined to conclude until the setup is characterized. He asked six things, and the first is the client-scheduler distinction that v2 already made:

"Does v2 of the series behave the same way? v2 dropped the patch that ran the first RPC states in the submitter's context, so the rpciod traffic pattern differs from v1. The same smt -> cache_shard -> smt toggle on v2 would tell us whether that matters."

The rest of the list is RDMA-client plumbing, not SUNRPC theory:

  1. mlx5 completion IRQ placement (/proc/interrupts, smp_affinity_list, irqbalance vs. hand-pinning)
  2. perf record -a -g plus perf report --sort comm,cpu, focusing on which CPUs rpciod kworkers and ib-comp-wq threads run on under each scope
  3. tools/workqueue/wq_monitor.py rpciod to see whether pools are evenly loaded
  4. workload shape: threads, I/O size/direction, mounts, RDMA connections, nconnect in particular
  5. base kernel, RDMA device, and driver

"If you have a way to capture a bad run reliably shortly after boot, a 'before and after' of items 2 through 4 across a single scope toggle would be the most direct evidence."

That is the right client-development instinct: SMT affinity can put rpciod completions on the same SMT siblings as mlx5 completion vectors, or starve ib-comp-wq, without any SUNRPC lock being “wrong.”

v2 follow-up: the low-throughput mode survives, the live toggle does not

Late on 3 September, Tim reported back on v2. The headline for NFS client development is that dropping the async-inline patch changed the failure mode. The 15 GB/s cliff is still there; the deterministic smt ↔ cache_shard switch is not:

"The v2 series behaves similarly insofar as some runs see ~15 GB/s and other runs see ~45 GB/s, but the low-throughput state no longer appears to be directly controlled by the rpciod affinity scope."

With both scopes he saw all three of: stay at ~45 GB/s, stay at ~15 GB/s, and start at ~45 GB/s then drop abruptly to ~15 GB/s, with no pattern for how long a good run lasts.

"cache_shard does still seem somewhat more likely to give me a ~45 GB/s run, particularly as uptime increases, but unlike v1 I can reproduce both good and bad runs with either scope. The deterministic live smt -> cache_shard -> smt behavior I reported for v1 is no longer present in v2."

"So the low-throughput state remains with v2, but it no longer seems to be from the SMT affinity change alone."

That is an important correction to the v1 bisection. v1’s extra rpciod hop (every async RPC bounced onto the workqueue before call_start) made SMT affinity look like the cause. Once that hop is gone, affinity is at most a bias.

Workload: pNFS flexfiles, 1 MiB reads, nconnect=16

This is not Lever’s 4KB NFSv3 microbenchmark. Tim’s client is:

elbencho --iter 1 --threads 160 --files 16 --size 256G \
    --block 1m --dropcache --iodepth 64 --direct --read

Mount: NFSv4.1, rsize=wsize=524288, nconnect=16, proto=tcp in /proc/mounts, but:

"It's pNFS over RDMA with one client, one MDS, one DS."

"This is a pNFS flexfiles workload. The MDS connection is TCP, and I see 16 RDMA rpc_xprt instances for the data-server traffic during these tests."

Hardware: two ConnectX-7 (mlx5_0/mlx5_1), firmware 28.47.2682, mlx5_core 7.3.0-rc1. Base kernel 940de590b839 plus the full v2 series. irqbalance is inactive; mlx5 completion IRQs are one-per-CPU (mlx5_comp0→CPU 0 … wrapping across the two sockets). Affinity was the same in good and bad captures, so IRQ placement does not explain the 3× swing by itself.

wq_monitor.py: bad cache_shard is busier, bad SMT is idler

The four v2 windows are the most useful client-side numbers in the thread.

Two client-visible facts:

  1. Bad cache_shard still queues a lot of rpciod work (high cumulative total and CPUtime, mayday 0 vs. 16 on the good run). Throughput is down, but the RPC state machine is not idle. That argues against a simple “pool lock is too coarse / too fine” story.
  2. Bad smt is the opposite: much lower total, CPUtime, and CMW/RPR. Completions are not arriving, or not being turned into rpciod work, at the same rate.

Tim’s perf capture is not yet usable (perf itself and cpuidle_enter dominate). He will follow up. Until then, the open client questions Lever posed — which CPUs rpciod and ib-comp-wq run on, and whether SMT siblings collide with mlx5 completion vectors — remain unanswered.

Evolution and conclusions

This thread is a performance-feature regression report, not a protocol discussion. The proposed change is still “set WQ_AFFN_SMT on rpciod.” The week’s evidence says:

  1. Do not merge the SMT override on the v1 bisection alone. On a 96-CPU pNFS/RDMA flexfiles client, v1’s SMT scope cut 45 GB/s to 15–25 GB/s, live-toggled through sysfs. That is a first-order NFS client bug relative to the stated goal of the series.
  2. v2’s removal of async-inline execution changes the failure. The 15 GB/s mode remains, but it is no longer pinned to affinity_scope. The extra rpciod hop in v1 was load-bearing for the appearance of an SMT bug; it was also the hop v2 dropped to avoid a pNFS deadlock. Client developers should treat v1 SMT results as contaminated by that hop.
  3. cache_shard is not a clean default either, even though it is “somewhat more likely” to stay at 45 GB/s as uptime grows. Both scopes can start good and then fall off a cliff. That points at a scheduler / IRQ / nconnect=16 / ib-comp-wq interaction that the affinity knob only modulates.
  4. Lever has not withdrawn the patch. He asked for IRQ maps, perf, and wq_monitor.py before drawing conclusions. Those data are now partly in; perf locality of rpciod vs. ib-comp-wq is the missing piece.
  5. The series is still RFC. No Reviewed-by, no “drop SMT,” no alternative scope. The practical client-development conclusion this week is Tim’s original bar, now refined: understand the 15 GB/s mode — and why v1 made SMT look uniquely guilty — before WQ_AFFN_SMT on rpciod (and by extension nfsiod / xprtiod) goes upstream.

The discussion remains open on Tim’s next perf capture.
