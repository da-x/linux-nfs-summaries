nfs-utils junction hardening: buffer over-read and use-after-free

Summary

Scott Mayhew posted a two-patch nfs-utils hardening series on 3 September aimed at memory-safety bugs in junction handling, the userspace path that turns FedFS/XML junction attributes into NFS referral (fs_locations) data. The thread is a same-day drop with no replies yet in this window; it is a bug-fix series, not a protocol change or new feature.

Mayhew framed the work in the cover letter as two independent but related defects:

"The first patch fixes a buffer overrun in junction_parse_xml_read() and the second fixes a use-after-free when parsing multi-location junctions in locations_to_fslocdata()."

Together the patches touch only support/junction/junction.c and support/export/cache.c (+8/-1). That is the export-cache / junction plumbing used when nfs-utils materializes referrals for clients, so the practical impact is on NFS referral correctness and daemon robustness rather than on the kernel NFS client itself.

Patch 1: opaque xattr treated as a C string

PATCH 1/2 addresses a buffer over-read (the cover letter calls it an overrun; the patch subject is more precise) in junction_parse_xml_read(). junction_get_xattr() returns an opaque, length-delimited buffer, but the XML parser later hands that buffer to xlog() as if it were a NUL-terminated string. Mayhew's diagnosis is terse:

"junction_get_xattr() returns an opaque buffer, but junction_parse_xml_read() treats it as a string by passing it to xlog()."

The chosen fix is at the source rather than at the log call: allocate one extra byte in junction_get_xattr() and NUL-terminate the buffer before returning it. That makes the xattr payload safe for %s-style logging without changing the XML parse path itself. The change is three lines in support/junction/junction.c.

For NFS client-facing behavior this is a hardening fix around junction XML that can be stored as an xattr: a missing terminator could make xlog() walk off the end of the allocation when a junction is dumped, which is a classic over-read on a path that runs in the nfs-utils daemons rather than in the kernel client.

Patch 2: dangling last_path on multi-location junctions

PATCH 2/2 is the more operationally interesting bug for referral handling. In locations_to_fslocdata(), multi-location junctions are collapsed into fs_locations data by comparing each location's root_path against last_path. Mayhew describes a classic aliasing mistake:

"While parsing a multi-location junction, locations_to_fslocdata() sets last_path = root_path and then frees root_path, leaving last_path dangling. On the next iteration, strcmp(rootpath, last_path) dereferences freed memory."

The next location therefore compares against freed heap. The repair transfers ownership instead of aliasing-then-freeing:

"Fix it by transferring ownership of root_path to last_path when they should be aliased."

The six-line change lives in support/export/cache.c, which is the export-cache conversion of junction locations into fsloc data that NFS clients consume as referrals. A use-after-free here is not a kernel-client bug, but it can corrupt or crash userspace junction/export processing precisely on the multi-location case that referrals are meant to express.

Status this week

No review, Acked-by, or follow-up appeared before the window closed. The series therefore stands as an unreviewed nfs-utils bug-fix drop: one over-read from treating junction xattrs as C strings, and one use-after-free in multi-location locations_to_fslocdata(). Both are hardening/correctness fixes on the userspace junction path that feeds NFS referrals, not kernel NFS client changes and not a protocol revision.
