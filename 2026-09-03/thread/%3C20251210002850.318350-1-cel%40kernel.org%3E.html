NFSv2 NFSERR_INVAL cleanup breaks U-Boot symlink boot

Summary

This week a December 2025 NFSD status-code cleanup came back as a real-world bug fix for an NFSv2 client: U-Boot’s NFS boot path no longer recognizes Linux’s error when a READ hits a symlink. Maintainers rejected a revert to the illegal NFSERR_INVAL mapping and instead agreed to make NFSD return the historic Sun/Solaris code NFSERR_ISDIR, which U-Boot already treats as “follow the symlink.”

Prior work (brief)

In December 2025, Chuck Lever posted a two-patch series that aligned NFSD status codes with the RFCs after comparing hand-written headers with xdrgen output. Patch 2, NFS: NFSERR_INVAL is not defined by NFSv2, noted that RFC 1094 never defines NFSERR_INVAL (NFS3ERR_INVAL arrives only in RFC 1813) and that nfsd_map_status() had been mapping nfserr_symlink and nfserr_wrong_type to that illegal v2 code. Lever’s proposed replacement was NFSERR_IO.

Jeff Layton and NeilBrown both Reviewed-by the series. Brown added a caveat that later proved optimistic:

"I cannot easily find a path that would lead to NFSv2 being presented with nfserr_symlink or nfserr_wrong_type, so that change probably isn't visible."

The mapping change landed as commit 0ac903d1bfdc and sat quietly until this week.

The regression: U-Boot’s NFS client

On 28 August, Jörg Sommer reopened the thread against patch 2, reporting that NFSv2 boot via U-Boot had broken and asking how “to get it working again.” That is a firmware NFS client regression, not a Linux nfs.ko issue: U-Boot uses NFSv2 READ, and when the target is a symlink it expects a specific status so it can issue READLINK.

NeilBrown diagnosed the client from U-Boot’s NFS state machine:

} else if ((rlen == -NFSERR_ISDIR) || (rlen == -NFSERR_INVAL)) {
        /* symbolic link */
        nfs_state = STATE_READLINK_REQ;

After 0ac903d1bfdc, NFSD returns NFSERR_IO (5) for that case. U-Boot does not treat 5 as “this is a symlink,” so netboot of a symlink path fails. Brown laid out three unattractive options: have nfsdv2 return NFSERR_ISDIR for a non-directory, restore the illegal NFSERR_INVAL, or teach U-Boot to also accept NFSERR_IO. His first instinct was a revert:

"There is no "good" option. I suspect we should revert this change and document that we violate the RFC for historical compatibility with u-boot."

Protocol vs. deployed clients

Chuck Lever refused to restore NFSERR_INVAL. He split U-Boot’s two checks: NFSERR_ISDIR is the Sun-compatible path; the NFSERR_INVAL arm was “presumably added for Linux NFSD.” Going back to the pre-0ac903d1bfdc mapping was off the table:

"So the pre-0ac903d1bfdc code is not something I want to go back to. Returning NFSERR_INVAL is incompatible with the reference NFSv2 implementation, and so is NFSERR_IO."

The constructive alternative is to map nfserr_symlink to NFSERR_ISDIR for NFSv2 READ/WRITE/SETATTR. Solaris already returns NFSERR_ISDIR when READ or WRITE hits a non-regular object, “which suggests to me that is the behavior clients will expect.” He wanted nfserr_wrong_type left alone until someone files a concrete complaint.

U-Boot maintainer Tom Rini then made the client-side cost explicit. The NFS code dates to 2004, borrowed from NetBSD, with symlink handling stacked on top—“we're likely the originator of the incorrect behavior.” But every U-Boot that ever used this feature now fails, and the lag between the kernel change and the report implies field firmware that will not be updated:

"But also, this means that everything U-Boot that's ever been using this feature now fails. … So perhaps things do need to go back to the way it was."

Lever pushed back that a revert “moves NFSD backwards instead of forward,” is fine for stable trees, but would take as long to land in mainline as a correct fix. The “can’t be updated” argument also cut both ways: those boxes would not pick up a kernel revert either.

Rini clarified the firmware reality. This is decades-old NFSv2, not a new protocol feature, and it looks like an ABI break with no security rationale. He already had a U-Boot-side fix from Sommer that could make the October release, but:

"When will that actually be seen by people using U-Boot? Well, maybe newer products based on... Fedora will pick up v2027.04, some semis will base on v2027.01, but most places? Probably never."

"By deployments I mean U-Boot deployments. It's notoriously hard to update firmwares most of the time. … So most of the time, it's never updated."

The agreed server-side fix

Lever then reframed the NFSD change so it does not depend on the Linux NFS client or on shipping new U-Boot:

"I'm talking about changing NFSD to return NFSERR_ISDIR, which would be picked up by the first "if" check above, which already exists in U-Boot."

"That addresses the regression and can be backported into the LTS Linux kernels that have commit 0ac903d1bfdc [*]. It does not depend on making changes to U-Boot."

Affected trees, as he counted them: LTS v6.12 and v6.18, plus stables v7.1 and v7.2.

Rini accepted that plan immediately: “Yes, something that doesn't require changing U-Boot is good, thanks.”

NeilBrown endorsed it as matching OpenSolaris nfs_srv.c (archived lines 619–624), “the closest thing to a real standard for NFSv2.” Lever closed the week with “Exactly. Patch coming soon.”

Conclusions

  • Type of change: compatibility bug fix on top of an earlier protocol-correctness patch, not a new feature and not an RFC change. Linux’s in-kernel NFS client is not being modified; the affected client is U-Boot’s NFSv2 bootloader.
  • Do not revert 0ac903d1bfdc on mainline just to restore illegal NFSERR_INVAL. That code was never in RFC 1094 and is not what the Sun reference server did.
  • Do map nfserr_symlink → NFSERR_ISDIR for NFSv2 READ (and the related WRITE/SETATTR paths). That is what Solaris does, what U-Boot already checks, and what can be backported to the LTS/stable kernels that shipped the regression.
  • Leave nfserr_wrong_type alone until a specific field report appears.
  • A U-Boot-side check for NFSERR_IO is welcome for new firmware, but cannot be the primary fix: most deployed bootloaders will never be updated.

No patch had been posted by the end of the window; Lever’s follow-up is the next item to watch.
