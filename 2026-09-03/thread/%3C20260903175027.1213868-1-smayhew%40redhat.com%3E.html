fsidd: don't arm client events after accept4() failure

Summary

Summary

Scott Mayhew posted a one-file nfs-utils robustness patch that hardens fsidd, the userspace filesystem-ID daemon on the NFS reexport path. The change is a bug fix, not a protocol change and not a new kernel NFS client feature: the accept path in support/reexport/fsidd.c currently arms a client event even when accept4() has already failed, and it has no backoff when the kernel is out of file descriptors or other accept resources.

Mayhew’s commit message is the entire technical brief:

"Handle failures from accept4() before creating a client event, and add a short backoff on errors indicating resource exhaustion."

That is two related defects in one accept loop. First, creating a client event after a failed accept4() is inverted control flow: the event is supposed to represent a live accepted connection, not a failed syscall. If the daemon still registers an event against a negative or otherwise invalid descriptor, the event loop can fire on garbage, leak watcher state, or keep retrying a connection that never existed. Second, resource-exhaustion errors from accept4() (EMFILE, ENFILE, ENOMEM, ENOBUFS and kin) are not transient in the “try again immediately” sense. Without a short backoff, a full fd table or a depleted accept queue turns into a tight spin: the listen socket stays readable, accept4() keeps failing, and fsidd burns CPU while still failing to accept the next reexport client.

The diff is small — 28 lines in support/reexport/fsidd.c (+26/−2) — but the shape is the right one for a local-socket helper. Check accept4() first. Only then create the client event. On exhaustion, sleep briefly instead of hammering the syscall. That keeps the daemon alive under fd pressure and stops it from advertising a client that was never accepted.

This lands two minutes after Mayhew’s companion fsidd parse-hardening patch, which replaced assert() on local-socket command parsing with explicit error returns. Together they are a late-week reliability pair: do not abort on malformed commands, and do not invent client events for connections that accept4() refused. Neither patch is a kernel NFS client change, but both sit on the userspace path that maps filesystem identities for reexported mounts. A wedged or spinning fsidd is not a quiet helper failure; it can stall or confuse client-visible reexport operations until the daemon recovers.

The patch is a 3 September 2026 drop with no review replies in this window. There is no Acked-by, no requested-changes, and no discussion of which errno values count as “resource exhaustion,” how long the backoff is, or whether the event-creation reorder covers every accept path. Until that review lands, the technical conclusion is Mayhew’s: fail accept4() before creating a client event, and back off when the kernel is out of resources.

NFS client kernel code is untouched. The client-development relevance is operational. Reexport clients depend on this helper staying alive and only tracking connections that actually exist. Hardening the accept path is a small but important bug fix on that path.
