NFSD listener_set v4: drop ENAVAIL, classify rpcbind silence as EIO

Summary

Jeff Layton posted a 14-patch v4 of the NFSD netlink LISTENER_SET hardening series on 31 August, three days after v3. This is a bug-fix and hardening series against syzbot hung-task reports, not a protocol change and not a client-facing feature. The work lives in NFSD and the shared SUNRPC local rpcbind client; NFS client code is only a bystander, because the same rpcb_clnt path is what the server uses to talk to loopback/AF_LOCAL rpcbind under nfsd_mutex.

No review, ack, or nack landed on v4 this week. The series is a same-week follow-up to Chuck Lever's v3 review of patch 06, which argued that v3's new -ENAVAIL "no answer" bucket swallowed real replies (-ENOMEM, -ERESTARTSYS, -EPFNOSUPPORT, auth -EACCES) and turned them into a synthesized timeout. Layton had already conceded the point on v3: "Fair point. I've mostly been trying to classify errors as to whether there is any point is attempting further registrations." v4 is that cleanup.

The cover letter is short and pointed:

"This version just fixes up some errno handling confusion that was in v3 that Chuck pointed out. This version also drops ENAVAIL as a special error code -- we can use EIO for that instead."

"Please consider these for v7.4."

The rest of the architecture is unchanged from v3: cap the request, validate transport names before taking nfsd_mutex, bound the local rpcbind client to 1s, and stop walking listeners/programs once rpcbind goes silent. Olga Kornievskaia's "give up after the first failure" rule remains the hinge.

What changed from v3: error taxonomy, not the hang bound

The only material kernel change is patch 06. v3 introduced -ENAVAIL as a dedicated "rpcbind never answered" errno; Chuck showed that rpc_call_sync() returns a much wider set, and folding those into -ENAVAIL was an observability regression and dropped syscall-restart semantics on -ERESTARTSYS. v4 splits rpcb_register_call() failures into three buckets instead of inventing a new errno:

  • answered: a FALSE reply, or an RPC-level rejection that rpc_decode_header() derives from the reply — -EACCES (FALSE reply or AUTH_ERROR), -EPROTONOSUPPORT, -EPFNOSUPPORT, -EOPNOTSUPP.
  • never sent: -ENOMEM, -EMSGSIZE, -ERESTARTSYS.
  • no answer: everything else, i.e. transport errors.

Any no-answer error is then represented by -EIO, which is already what the RPC layer reports for a soft timeout without RPC_TASK_TIMEOUT. Layton notes that call_status() documents -EIO as "shutdown or soft timeout." The serv still keeps a sv_rpcb_failures count; later patches still watch that count and stop further SET/UNSET once it moves. The difference is that a real reply, a memory failure, or a fatal signal no longer increment that count and no longer get rewritten into a synthetic timeout.

That is the whole v4 delta on the kernel side. The other thirteen patches are the v3 design, rebased onto the new classification.

The hang this series is trying to kill

The original bug is a server-side hung-task, not a client I/O stall. nfsd_nl_listener_set_doit() holds nfsd_mutex across listener teardown and rebuild. Each new listener calls svc_register(), which talks to the local rpcbind synchronously. A rpcbind that accepts the connection and never replies used to cost one transport-default timeout per listener, per program, per version. The AF_LOCAL default is 10s; the loopback TCP fallback is 60s. Patch 04 records the watchdog trip that made this visible:

"INFO: task hung in nfsd_nl_cache_flush_doit"

The holder itself waits killably and escapes the watchdog; other NFSD netlink operations pile up behind nfsd_mutex. With the 1024-entry cap that patch 01 now enforces, patch 10 still spells out the worst case without the give-up rule:

"With the cap of 1024 entries the request can hold nfsd_mutex for about 34 minutes, which is roughly 17 times the hung-task threshold."

Patches 01, 02 and 10 still carry Fixes: 16a471177496 ("NFSD: add listener-{set,get} netlink command"). Patches 02, 04 and 10 still link the syzbot report (extid=c7eae0eb80858a2dba0f). Several patches remain Assisted-by: LLM.

Input validation and the 1s bound (unchanged from v3)

The first half of the series is still about work that today runs under nfsd_mutex or sv_lock with bottom halves disabled:

  • 01/14 rejects a listener_set with more than NFSD_NL_LISTENER_MAX (1024) entries in nfsd_nl_validate_listeners(), before taking any lock. The nested match loop is O(N×M). The patch still does not cap M (existing sockets); __write_ports_addxprt() can still push M past the cap. Both interfaces require CAP_NET_ADMIN.
  • 02/14 checks the transport name against tcp/udp/rdma before nfsd_create_serv(), so an arbitrary name no longer reaches request_module("svc%s", name) as a TASK_KILLABLE usermode helper under nfsd_mutex. Modular svcrdma autoload is deliberately left in place. The rejection names the offending attribute through extack, because -EPROTONOSUPPORT alone does not say which entry carried the bad name.
  • 03/14 makes svc_register() keep the first error instead of the last, so a later success cannot erase an earlier failure. This is also what makes CONFIG_NFS_LOCALIO=y agree with =n on "a failed registration stays fatal."
  • 04/14 bounds the local rpcbind client to a single 1s attempt. Layton is still explicit that this is a mitigation, not the end state:

"This shortens the stall. It does not remove the stall, and it is not free. Registration stays synchronous and stays fatal. … An rpcbind that is merely slow to be scheduled can therefore now fail server startup, where it succeeded before. The real fix is to make the registration asynchronous."

  • 05/14 reports listener-creation failures through netlink extack, naming both the attribute and the transport so a multi-entry request is not reduced to a bare "Address already in use." NL_SET_BAD_ATTR() is required because several entries can share a transport name.

v2's svc_register() unwind stays dropped, for the reason Chuck found earlier: rpcbind matches an UNSET on [program, version, netid], and the v2 fallback ignored protocol, so the unwind "could therefore clear entries that belong to other live listeners."

Give up once rpcbind is silent (unchanged policy, new errno)

Patches 07–10 still implement Olga's rule, now keyed off -EIO rather than -ENAVAIL:

  • 07/14 stops the program loop in svc_register() on no-answer, not just the version loop, so an nfsd serv does not pay 2s (nfsd + nfsacl) for a dead rpcbind.
  • 08/14 and 09/14 bound the unregistration side the same way: svc_unregister() gives up after the first silent call, and svc_delete_xprt() clears XPT_RPCB_UNREG on every remaining transport in the net once one UNSET gets no answer. One LISTENER_SET therefore pays one timeout in each direction rather than one per listener/program/version.
  • 10/14 is the NFSD consumer: once svc_rpcb_failure_count() moves, the rest of the request is created with SVC_SOCK_ANONYMOUS. Suggested-by Olga Kornievskaia.

A refused SET (-EACCES) is still an answer, so it stays fatal for that listener and does not trip the give-up path. That distinction is what the selftests in patches 13–14 are written to protect.

Selftests: a per-netns rpcbind stub, still the bulk of the series

The last four patches add tools/testing/selftests/nfsd/nfsd_netlink_listener.c (~1.3k lines) and put the new directory in the NFSD MAINTAINERS entry. That is the only part of the series that a client-side developer might actually reuse: a harness for talking to NFSD netlink without poisoning the host's rpcbind.

11/14 covers the pre-mutex validation: bad/absent transport name, missing address, truncated sockaddr, bad family, a malformed entry behind a well-formed one, more than 1024 entries, and LISTENER_GET on an empty netns. Each kselftest harness test runs in its own net and mount namespace with /run masked, because unix_find_bsd() has no struct net and a connect to /var/run/rpcbind.sock would otherwise hit the host rpcbind — and svc_rpcb_setup() opens with svc_unregister(), which would clear the host's nfsd registrations. The config fragment therefore includes NAMESPACES, NET_NS, SHMEM, TMPFS and UNIX; without them every test skips.

12/14 is the interesting piece: a per-netns rpcbind stub bound to the abstract name "\0/run/rpcbind.sock" (that lookup is netns-local via unix_find_abstract()). The stub never decodes arguments; NULL gets success, SET/UNSET get TRUE, and it speaks RPCBVERS_4 as well as v2 so IPv6 listeners are not left unregistered. Mode and counters live in a shared page so a test can switch the stub to silent without killing the connection the kernel holds — killing it would make the next rpcb_register_call() fail immediately with -ENOTCONN (RPC_TASK_NOCONNECT) instead of waiting out a timeout. Layton is still careful that errno alone is a weak oracle. Several tests exist "to catch a revert, not to describe the interface": val_bad_transport now also requires the stub saw no traffic; sem_register_refused re-reads the listener set because -EACCES can also come from bind; func_empty_destroys uses the connection count to distinguish a destroyed serv from a live serv with no permsocks.

13/14 is where the new error split shows up in tests. RPCB_STUB_SILENT reads a call and writes nothing back; RPCB_STUB_REFUSE cannot serve here, because "a refusal is an answer, and the count ignores it on purpose." The NULL procedure still has to be answered: rpcb_create_af_local() builds its client without RPC_CLNT_CREATE_NOPING, so silencing the ping would fail the AF_LOCAL client, send rpcb_create_local() on to the loopback fallback, and leave the stub seeing one call per request no matter how many listeners it carried. The four cases:

  • rpcb_stop_after_failure — one listener, then three; three entries must not cost three times as much.
  • rpcb_silent_set_complete — the entry that finds rpcbind silent is the one that pays the timeout; a three-entry request must still bring up all three, succeed, and warn.
  • rpcb_v4_only_bounded — v4-only, so vs_rpcb_optnl discards every error and every listener comes up; the count, not a failed listener, is what bounds the walk.
  • rpcb_retry_next_request — the stop lasts for one request; after the stub starts answering, the next request must reach rpcbind again.

14/14 covers the teardown side of the same rule: remove one listener, then three, with the stub silent. Three removals must not cost three timeouts. Both measurements also pay the svc_unregister() sweep that nfsd_destroy_serv() runs once the last listener is gone, so that cancels out of the comparison.

Where it stands

v4 is the series Layton wants in v7.4. The direction is the same as v3 — cap the request, validate before taking nfsd_mutex, bound the local rpcbind client, stop walking once rpcbind is silent — with Chuck's errno objection addressed by dropping -ENAVAIL and classifying silence as -EIO while leaving real replies, allocation failures and -ERESTARTSYS alone. No one has acked it yet this week.

The 1s timeout remains a mitigation. Both the cover letter's v3 history and patch 04 still point at asynchronous (and eventually userland) rpcbind registration as the real cure for holding nfsd_mutex across a synchronous RPC. Client developers waiting for a protocol or mount-path change will not find one here; the important bug fix is that a silent local rpcbind can no longer pin the NFSD netlink path for tens of minutes.
