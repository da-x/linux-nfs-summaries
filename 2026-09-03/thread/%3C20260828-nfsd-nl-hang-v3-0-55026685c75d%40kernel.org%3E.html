NFSD listener_set v3: bound rpcbind hangs, error-class debate

Summary

This week Jeff Layton posted a 14-patch v3 series to stop NFSD's netlink LISTENER_SET path from hanging the server under a silent local rpcbind, then took a pointed review from Chuck Lever on how "no answer" is classified. The work is a bug-fix and hardening series (syzbot hung-task reports against the listener netlink command), not a protocol change. It lives on the server and in SUNRPC; the client is only indirectly involved via the shared rpcbind client.

From v2 to v3: stop retrying a dead rpcbind

Layton's cover letter opened by stressing how far v3 had moved:

"This series is quite a bit different from v2. First, I cleaned things up along the lines of Chuck's review of v2, but then Olga suggested that we should just give up on trying to do new rpcbind registrations when one fails."

That Olga Kornievskaia suggestion is the architectural hinge. A LISTENER_SET with many entries used to call svc_register() once per listener; a local rpcbind that accepted the connection and never replied therefore paid one timeout per entry, all under nfsd_mutex. With the new 1024-entry cap that stall could run to "about 34 minutes," as patch 10 put it — "roughly 17 times the hung-task threshold." Layton said the new give-up-after-first-failure rule "now seems to fix the reproducer that syzbot provided recently" and that he had "high hopes that it will fix the other syzbot hangs that have been reported." He asked for the series in v7.4, and noted it is also "a foundation for some other work I have that will move the rpcbind registration into userland."

v3 also dropped v2's svc_register() unwind. rpcbind matches an UNSET on [program, version, netid], and the v2 fallback ignored protocol, so the unwind "could therefore clear entries that belong to other live listeners. Chuck Lever found that." A failed registration stays fatal; patch 3 makes CONFIG_NFS_LOCALIO=y agree with =n on that point.

What the 14 patches actually change

The first half is input validation and timeout bounding, all aimed at work that today runs under nfsd_mutex or sv_lock with BHs disabled:

  • 01/14 caps a listener_set request at NFSD_NL_LISTENER_MAX (1024) before taking any lock. The nested match loop is O(N×M); a huge userspace list could otherwise spin in atomic context. The patch does not cap M (existing sockets), and __write_ports_addxprt() can still push M past the cap.
  • 02/14 checks the transport name against tcp/udp/rdma before nfsd_create_serv(), so an arbitrary name no longer reaches request_module("svc%s", name) as a TASK_KILLABLE usermode helper under nfsd_mutex. The autoload for modular svcrdma is deliberately left in place. This is one of the patches tagged against the syzbot bug.
  • 03/14 makes svc_register() keep the first error instead of the last, so a later success cannot erase an earlier failure.
  • 04/14 bounds the local rpcbind client to a single 1s attempt (the defaults were 10s on AF_LOCAL and 60s on loopback TCP). Those calls are synchronous and sit under nfsd_mutex; a silent rpcbind was tripping INFO: task hung in nfsd_nl_cache_flush_doit on other NFSD netlink ops. Layton was explicit that this only shortens the stall:

"This shortens the stall. It does not remove the stall, and it is not free. … An rpcbind that is merely slow to be scheduled can therefore now fail server startup, where it succeeded before. The real fix is to make the registration asynchronous."

  • 05/14 reports listener-creation failures through netlink extack, naming both the attribute and the transport so a multi-entry request is not reduced to a bare "Address already in use."

The second half is the "give up once rpcbind goes silent" machinery:

  • 06/14 introduces -ENAVAIL for a local rpcbind call that got no answer, distinct from -EACCES (FALSE reply). svc_generic_rpcbind_set() lets -ENAVAIL past vs_rpcb_optnl; svc_register() then tallies it in serv->sv_rpcb_failures. Callers compare svc_rpcb_failure_count() as they go.
  • 07/14 stops the program loop in svc_register() on no-answer, not just the version loop, so an nfsd serv does not pay 2s (nfsd + nfsacl) for a dead rpcbind.
  • 08/14 and 09/14 bound the unregistration side the same way: svc_unregister() gives up after the first silent call, and svc_delete_xprt() clears XPT_RPCB_UNREG on every remaining transport in the net once one UNSET gets no answer. One LISTENER_SET therefore pays one timeout in each direction rather than one per listener/program/version.
  • 10/14 is the NFSD consumer of that count: once svc_rpcb_failure_count() moves, the rest of the request is created with SVC_SOCK_ANONYMOUS. The entry that paid the timeout is retried anonymous rather than left out of the set; a silent rpcbind is reported as its own ack condition instead of being glued onto whatever unrelated error the last entry had. Suggested-by Olga Kornievskaia.

Patches 01, 02 and 10 carry Fixes: 16a471177496 ("NFSD: add listener-{set,get} netlink command"). Several patches are marked Assisted-by: LLM.

Selftests: a per-netns rpcbind stub

The last four patches add tools/testing/selftests/nfsd/nfsd_netlink_listener.c (about 1.3k lines) and put the new directory in the NFSD MAINTAINERS entry.

11/14 covers the pre-mutex validation: bad/absent transport name, missing address, truncated sockaddr, bad family, a malformed entry behind a well-formed one, more than 1024 entries, and LISTENER_GET on an empty netns. Each kselftest harness test runs in its own net and mount namespace with /run masked, because unix_find_bsd() has no struct net and a connect to /var/run/rpcbind.sock would otherwise hit the host rpcbind — and svc_rpcb_setup() opens with svc_unregister(), which would clear the host's nfsd registrations.

12/14 is the interesting piece for anyone writing NFS server tests: a per-netns rpcbind stub bound to the abstract name "\0/run/rpcbind.sock" (that lookup is netns-local). The stub never decodes arguments; NULL gets success, SET/UNSET get TRUE, and it speaks RPCBVERS_4 as well as v2 so IPv6 listeners are not left unregistered. Mode and counters live in a shared page so a test can switch the stub to silent without killing the connection the kernel holds. Layton was careful that errno alone is a weak oracle — several tests exist "to catch a revert, not to describe the interface." val_bad_transport now also requires the stub saw no traffic; sem_register_refused re-reads the listener set because -EACCES can also come from bind; func_empty_destroys uses the connection count to distinguish a destroyed serv from a live serv with no permsocks.

13/14 and 14/14 then assert the new bound: a three-entry listener_set (or a three-listener removal) against a silent stub must not cost three timeouts; a v4-only server still comes up with a warning; the stop lasts for one request, so the next request after the stub starts answering reaches rpcbind again.

Chuck's review: -ENAVAIL is too coarse

The only technical review this week landed on patch 06. Chuck Lever argued the new errno taxonomy does not match the code:

"If I'm reading this correctly, rpcb_register_call() classifies every failure except -EPROTONOSUPPORT as "no answer"."

rpc_call_sync() can return -ENOMEM, -ERESTARTSYS, -EPFNOSUPPORT, -EOPNOTSUPP, -EIO, auth -EACCES, -EKEYREJECTED — "All of these show that rpcbind did answer." Those then become -ENAVAIL, get counted in sv_rpcb_failures, are silently converted to success for a vs_rpcb_optnl version, and reach userspace as a synthesized -ETIMEDOUT for mandatory versions.

He listed three consequences. First, the commit message's claim that "-EACCES continues to mean a FALSE reply" is false once the RPC layer's auth -EACCES is rewritten. Second, "rpcbind not running" (-ECONNREFUSED/-ENOENT) and every other transport error become indistinguishable ETIMEDOUT/ENAVAIL in the listener_set ack, the svc_register/svc_unregister tracepoints, and the printk — "which IMO is an observability regression." Third, -ERESTARTSYS -> -ETIMEDOUT "drops syscall-restart semantics on a fatal signal during registration." He closed with, "I'm probably missing something."

Layton's reply did not contest the reading:

"Fair point. I've mostly been trying to classify errors as to whether there is any point is attempting further registrations. For most of the errors besides -EACCES (aka rpc_auth_error), there is no point."

He said he had already cleaned up the error handling, "so v4 should be a bit more explicit about how errors are handled."

Where it stands

No acks landed on v3 this week. The series is treated as the right direction — cap the request, validate before taking nfsd_mutex, bound the local rpcbind client, and stop walking listeners/programs once rpcbind is silent — but patch 06's "no answer" bucket is too wide, and Layton has already pointed at v4 for the fix. The 1s timeout remains a mitigation, not the end state; both the cover letter and patch 04 keep pointing at asynchronous (and eventually userland) rpcbind registration as the real cure for holding nfsd_mutex across a synchronous RPC.
