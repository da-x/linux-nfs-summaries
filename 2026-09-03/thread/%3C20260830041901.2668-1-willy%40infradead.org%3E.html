Wilcox FGP_NOFS cleanup touches NFS dir folio lookup

Summary

Matthew Wilcox posted a nine-patch cleanup this week that retires the FGP_NOFS folio-get flag in favor of the scoped memalloc_nofs_save() API. The series is a cleanup / API-simplification, not a protocol change and not an NFS bug fix; the NFS client is touched only because fs/nfs/dir.c was one of the last remaining FGP_NOFS users.

Why this landed on linux-nfs

Wilcox framed the work as a small step toward the broader agreement that __GFP_FS should disappear:

"There is broad agreement that we should eliminate __GFP_FS in favour of using memalloc_nofs_save(). This is a small step in that direction by getting rid of FGP_NOFS. It's also a nice simplification in its own right."

He listed four patterns that still used the flag: (1) callers that already pass FGP_NOWAIT (so reclaim never happens), (2) callers already inside a memalloc_nofs scope, (3) callers that never needed NOFS at all, and (4) callers that should switch to memalloc_nofs_save(). The NFS change is pattern (1).

Patch 1 rewrites the memalloc_nofs_save() kerneldoc to be filesystem-centric rather than MM-centric, which Wilcox explicitly asked filesystem maintainers to review. Jan Kara liked the rewrite:

"Yeah, I think the documentation is better."

NFS client: one-line dir.c cleanup

Patch 4/9 is the only NFS-client change. In fs/nfs/dir.c Wilcox drops FGP_NOFS from a __filemap_get_folio() call whose flags already include FGP_NOWAIT:

"The flags already include FGP_NOWAIT which prohibits all reclaim, not just reclaiming from the filesystem."

That is a correctness-preserving simplification, not a behavior change. FGP_NOWAIT already forbids waiting on reclaim of any kind, so the extra __GFP_FS suppression was dead. The NFS directory-cache folio lookup still fails fast under memory pressure; it simply no longer pretends to need a narrower NOFS constraint.

No NFS maintainer (Trond Myklebust, Anna Schumaker, Jeff Layton, Chuck Lever) replied this week. The only review of the NFS hunk came from Jan Kara, who treated it as obvious:

"Obvious enough :) feel free to add: Reviewed-by: Jan Kara jack@suse.cz"

From a client-development standpoint this is housekeeping: directory readdir/lookup folio allocation stays non-blocking, and the NFS code path will keep compiling once FGP_NOFS is deleted from include/linux/pagemap.h in patch 9.

Rest of the series (context for the NFS drop)

The other filesystem patches exist so that patch 9 can actually delete the flag:

  • ext4 (2/9): two FGP_NOFS uses in fs/ext4/inline.c are dropped because they run inside a journal transaction, which already calls memalloc_nofs_save(). Reviewed by Jan Kara, Baokun Li, Zhang Yi, and acked by Ted Ts'o.
  • erofs (3/9): same FGP_NOWAIT redundancy as NFS. Reviewed by Jan Kara and Gao Xiang.
  • ntfs (5/9, 6/9): one site is argued to be unnecessary because the sibling non-resident pwrite path never used NOFS; the other is FGP_NOWAIT redundancy plus a switch to mapping_gfp_mask() so GFP_MOVABLE is preserved. Both reviewed by Namjae Jeon.
  • filemap (8/9, 9/9): drop the last in-tree FGP_NOWAIT|FGP_NOFS combination, then delete FGP_NOFS from pagemap.h and mm/filemap.c. Kara reviewed both.

Open question: squashfs (not NFS)

The only push-back this week is on patch 7/9, which replaces squashfs's FGP_NOFS with an explicit memalloc_nofs_save() around folio allocation while a folio is locked. Wilcox's rationale:

"Since we can allocate memory while holding a folio locked, we cannot allow page reclaim to call into the filesystem and attempt to compact the folio we're currently holding locked."

Jan Kara asked why the extra scope is needed at all:

"Why do you need this? The only allocation I can see is the one using FGP_NOWAIT below..."

Wilcox had not answered by the end of the week. That question does not affect the NFS hunk: NFS already uses FGP_NOWAIT, so it does not need a new memalloc_nofs_save() wrapper.

Status

This is cleanup, not a bug fix. Reviews are in for the NFS, erofs, ext4, ntfs, documentation, and filemap patches; the series is blocked only on the squashfs memalloc_nofs_save() debate. Once that is resolved, deleting FGP_NOFS will leave the NFS client directory folio path using FGP_NOWAIT alone — same non-blocking reclaim behavior, one fewer obsolete GFP flag.
