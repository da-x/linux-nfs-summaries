VFS foreign-UID checks: Howells posts v4 sticky-dir ownership hooks

Summary

This week David Howells posted v4 of a two-patch series that treats a long-standing VFS ownership-check bug as a first-class filesystem hook. The series is a bug fix (with a new VFS inode-op API), not an NFS protocol change. It landed on linux-nfs because the default i_uid comparisons it rewires sit on every network-filesystem open/create path, including the NFS client, even though only kAFS implements the new callbacks in this posting.

No reviews arrived in-window. The three messages are Howells' cover letter plus the two patches, rebased onto v7.3-rc1. Earlier rounds (v3 in late July, plus 2025 review from Christian Brauner) are bridged only where they explain why v4 looks the way it does.

The bug: VFS assumes local UNIX UIDs

Howells' diagnosis is that the VFS still treats inode->i_uid as a local UNIX credential. In the cover letter he writes that "foreign" IDs are those that "do not belong in the same number space as the system's user IDs," and that "Network filesystems are prime examples of this, but it may also impact things like USB drives or cdroms."

He lists four assumptions the VFS currently makes:

  1. comparing i_uid to another i_uid or to current_fsuid() is meaningful;
  2. current_fsuid() is the subject of the action;
  3. the number in i_uid lives in the system's ID space;
  4. IDs fit in 32-bit integers.

AFS violates all four: cell-local 64-bit owner IDs (AuriStor YFS), IDs that can collide with local UIDs, and a subject identified by a keyring token rather than current_fsuid(). CIFS is called out as the other extreme: "filesystems (CIFS being a notable example) may also have user identifiers that aren't simple integers." NFS is not named as an implementer, but it is in the same class of network filesystems whose client inodes still go through these VFS checks on every open(O_CREAT) in a sticky directory.

The user-visible failure is open(O_CREAT) of an existing AFS file in a world-writable sticky directory. may_create_in_sticky() compares the file's i_uid to current_fsuid() and to the parent directory owner; those comparisons are wrong for AFS, so the open fails with EACCES when it should succeed. Bash has papered over that since 1992 with an AFS-specific retry that drops O_CREAT. Howells notes that workaround "has now been removed as of bash-5.3," which is why the kernel path has to be fixed rather than left as a userspace quirk.

He also flags a related syscall limitation that this series does not solve:

"Note that chown may also need modifying in some way - but the system call as it stands can't necessarily supply the information required (for instance, an AuriStor YFS ID is 64 bits, but chown can only handle a 32-bit integer; CIFS might use a GUID)."

Patch 1: VFS ownership override API

Patch 1 adds three VFS helpers and two optional inode operations, gated by a new IOP_OWNERSHIP_OVERRIDE flag on i_opflags. That flag is the v2 carry-over from Brauner's earlier request to "bias this towards the common case where the filesystem will not have a custom ownership comparison callback at all" — i.e., NFS, ext4, XFS and friends keep doing cheap i_uid compares unless they opt in.

The helpers:

  • vfs_inode_is_owned_by_me() — default is i_uid vs current_fsuid() (with idmap). Filesystems may supply ->is_owned_by_me(idmap, inode), returning 0 if owned, 1 if not, or a negative error on lookup failure. The filesystem is allowed to identify the subject by something other than fsuid (AFS uses a keyring token).
  • vfs_inodes_have_same_owner() — default is pairwise i_uid compare. Override is ->have_same_owner(idmap, inode1, inode2).
  • vfs_inode_and_dir_have_same_owner() — same idea, but the second inode is the parent directory and the helper takes a nameidata.

Howells then walks the VFS call sites that currently do raw UID compares and switches them to the helpers:

SiteChange
chown_ok() / chgrp_ok()vfs_inode_is_owned_by_me(). Howells notes these "Possibly … need to defer all their checks to the network filesystem" because the new UID/GID is also foreign, but ->setattr() still gets a chance.
coredump_file()owned-by-me check on the dump file.
inode_owner_or_capable()owned-by-me; Howells is unsure "whether the namespace mapping makes sense in such a case."
vfs_setlease()owned-by-me. He adds that "setting locks could perhaps do with a permission call to the filesystem driver as AFS, for example, has a lock permission bit in the ACL," but the AFS server already enforces that on the RPC.
may_follow_link()both same-owner (link vs parent) and owned-by-me.
may_create_in_sticky()both helpers. He even asks whether the function "Should … return ok immediately if the open call we're in created the file being checked."
__check_sticky()owned-by-me on file and dir, except AFS directories cannot answer owned-by-me, so same-owner is used instead.
may_dedupe_file()owned-by-me.

Left unchanged, deliberately:

  • acl_permission_check() / posix_acl_permission() — only used from generic_permission(), which a netfs overrides via ->permission(). "AFS, for example, implements its own ACLs and evaluates them in ->permission() and on the server."
  • IMA policy ops — "Unchanged for now. I'm not sure what the best way to deal with this is." (Mimi Zohar, reviewing v3, had already pointed at ima_match_rules() if IMA uid/euid/fowner rules ever need a foreign-ID story.)

Howells is candid that wrapping the helpers "isn't necessarily the most efficient as it means we may end up doing the uid idmapping an extra time — though this is only done in three places, all to do with world-writable sticky dir checks."

Patch 2: kAFS implements the hooks

Patch 2 is the AFS-specific fix, tagged Fixes: 30aba6656f61 ("namei: allow restricted O_CREAT of FIFOs and regular files") and reported by Etienne Champetier. It wires ->is_owned_by_me and ->have_same_owner for kAFS files, directories, and (since v3) symlinks.

Ownership of a file is not i_uid == current_fsuid(). kAFS asks whether the server set the ADMINISTER bit in the access rights from FS.FetchStatus (and similar) for the caller's key. Howells is explicit about the anonymous case:

"Note that anonymous accesses to AFS will never see the ADMINISTER bit being set and so will not be perceived as owning an anonymously-owned file."

Same-owner compares the 64-bit AFS owner IDs from status, which "won't fit in a kuid_t" on AuriStor YFS. Anonymous file vs anonymous parent directory will match, but "an anonymously-owned directory cannot have the sticky bit set." Directory is_owned_by_me is acknowledged not to work; none of the VFS call sites that matter are expected to need it.

The historical bash workaround is documented in detail: since bash 1.11 (January 1992), redir_open() retried open() without O_CREAT on EACCES when built with AFS workarounds, originally to paper over IBM AFS 3.1 returning EACCES in preference to EEXIST. That retry also "undermines the Linux kernel protections against O_CREAT opening FIFOs and regular files not owned by the user in world writeable sticky directories" from commit 30aba6656f61. With bash-5.3 dropping the fallback, the kernel incompatibility is now exposed.

Test recipe: create a sticky dir with a token, create a file, then strace bash doing echo foo >>file and check whether bash issues a single successful O_CREAT open or an EACCES followed by a non-O_CREAT retry.

NFS client implications

This series does not change the NFS client, NFSD, or the NFS protocol. The linux-nfs audience is here because:

  • Every NFS client open(O_CREAT) in a sticky directory still runs may_create_in_sticky(). Until NFS grows IOP_OWNERSHIP_OVERRIDE, it keeps the default i_uid path. That is usually correct for NFSv3 and for NFSv4 with idmapping, where remote owners are already mapped into local kuid_ts.
  • The interesting NFS question — not answered this week — is whether there are remaining cases (unmapped NFSv4 owner strings, idmapped mounts whose on-disk UID is not the security subject, or a future non-integer owner model) that should implement these ops the way AFS and, potentially, CIFS will. Howells lists CIFS as the other filesystem that "may also have user identifiers that aren't simple integers."
  • Locking and leases: vfs_setlease() now goes through vfs_inode_is_owned_by_me(). Howells suggests a filesystem permission hook for leases/locks, then immediately walks it back for AFS because the server checks the ACL on the RPC. NFS already has server-side lock enforcement; a client-side override would only matter if local VFS lease checks were rejecting otherwise-valid NFSv4 delegations/leases based on a bogus i_uid compare.
  • inode_owner_or_capable() and the chown/chgrp helpers are on the setattr path that NFS clients use for chown(2). Howells leaves the new UID interpretation to ->setattr(), which is how NFS already handles idmapped setattr.

NFS client developers watching this thread therefore have a VFS API they can opt into, not a mandatory behavior change. The default remains "compare i_uid," which is the NFS-friendly common case Brauner asked to keep fast.

Evolution and status

v4's only listed change versus v3 is "Rebased on v7.3-rc1." v3 had added the AFS symlink inode ops; v2 had added IOP_OWNERSHIP_OVERRIDE after Brauner's 2025 review demanded a flag "similar to IOP_FASTPERM" to avoid pointer derefs on the common path.

From the prior-week v3 thread (not re-litigated here): Marc Dionne acked the AFS patch; Mimi Zohar noted IMA uid/euid/fowner rules live in ima_match_rules() if they ever need updating; Christian Brauner closed v3 with "Seems that some other changes are required for this. I'll take a look once a new version is out." That new version is this week's v4. There is no in-window reply from Brauner, Al Viro, Steve French, or NFS maintainers.

Conclusion this week: the series is posted, rebased, and waiting. The technical direction is a VFS opt-in for filesystems whose owner IDs are not local UNIX UIDs, with kAFS as the first consumer so that bash-5.3 can open(O_CREAT) an existing AFS file in a sticky directory without the 34-year-old userspace retry. NFS clients are spectators unless they choose to implement the same inode ops; the default path, and thus current NFS client UID/idmap behavior, is unchanged. Outstanding questions Howells himself leaves open: chown's 32-bit UID API, IMA policy, whether may_create_in_sticky() should short-circuit when the open created the file, and whether lease/lock permission should become a filesystem callback.
