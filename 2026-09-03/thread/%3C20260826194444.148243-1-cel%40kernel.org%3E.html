Jeff Layton acks NFS3ERR import and NFSD nfserr rework

Summary

This week the two-patch xdrgen staging series that Chuck Lever posted on 26 August picked up review and nothing else. Jeff Layton stamped Reviewed-by on both patches on 28 August, twelve seconds apart, with no nits, no requested v2, and no follow-up from Lever. The discussion is a header-cleanup / preparatory refactor, not a protocol change and not a functional bug fix. Wire status numbers stay put; only the in-tree spellings that produce them change.

Prior week (brief)

Last week’s posting was unacked infrastructure. enum nfs_stat in uapi/linux/nfs.h still collects every NFS version’s on-the-wire status under version-agnostic NFSERR_* names. Lever’s cover for PATCH 1/2 named both sides of the in-kernel stack as co-offenders:

"The in-kernel NFS client and server reference these names internally, which drags uapi/linux/nfs.h into many translation units that need nothing else from that header."

The forthcoming xdrgen conversion will swap that UAPI include for generated linux/sunrpc/xdrgen/nfs2.h, which only re-supplies the eighteen NFSv2 codes. NFSv3 has no dedicated enum today, and the mapping is not 1:1: NFSERR_NOT_SYNC (10002) and NFSERR_REMOTE (71) have no NFSv4 equivalent, and NFSERR_JUKEBOX (10008) is NFS4ERR_DELAY in v4. Patch 1 therefore plants a complete NFS3ERR_* enum in the shared include/linux/nfs3.h. Patch 2 respells fs/nfsd/nfserr.h (and one leftover NFSERR_MOVED in nfs4xdr.c) in terms of NFS3ERR_* and NFS4ERR_*. Lever’s operational claim:

"The wire values are unchanged; NFSD no longer depends on the version-agnostic NFSv3 and NFSv4 names."

This week: review, not debate

Layton on PATCH 1/2 quoted the new NFS3ERR_* enum through NFS_DATA_SYNC and added only:

"Reviewed-by: Jeff Layton jlayton@kernel.org"

Layton on PATCH 2/2 did the same for the nfserr.h rework, quoting through nfserr_bad_session_digest and repeating the tag. There is no technical argument this week because the reviewer did not open one. The series therefore leaves the window as acked infrastructure: the shared NFSv3 status names the client already includes, plus an NFSD nfserr.h that can survive the generated NFSv2 header.

Client development angle

The series remains server-heavy, but PATCH 1 is the client-facing piece. include/linux/nfs3.h is the in-kernel NFSv3 header used by nfs.ko as well as NFSD. Growing a complete NFS3ERR_* enum there does not convert client call sites off NFSERR_* and does not change client I/O, reconnect, or error-mapping paths. What it does is give later client-side xdrgen work a version-correct spelling for every NFSv3 status so the mixed UAPI nfs_stat soup can be dropped from client translation units the same way NFSD is dropping it now.

That is the important client-development takeaway this week, even though no client C file is touched: the header the client already includes is now the canonical home for NFSv3 status names, and a core NFS maintainer has signed off on putting them there. Until a follow-up actually rewrites client NFSERR_* uses, Linux nfs.ko still drags uapi/linux/nfs.h for those constants — Lever’s original complaint is only half-addressed.

What this is not

  • Not a bug fix. No runtime failure, no Fixes: tag, no stable candidate.
  • Not a protocol change. On-the-wire NFS3ERR / NFS4ERR numbers are identical before and after.
  • Not the xdrgen swap itself. The “subsequent patch” that replaces linux/nfs.h with linux/sunrpc/xdrgen/nfs2.h is still announced, not posted, and did not appear in this thread this week.
  • Not a client I/O-path change. Client impact is the new enum in a shared header, plus the promise that client TUs can later stop including the UAPI kitchen sink for a status constant.

Conclusions

Layton’s two Reviewed-by tags close the review gap that last week’s summary flagged. With no nits outstanding, the series is in shape to land: NFS3ERR_* in linux/nfs3.h for both client and server, and NFSD’s internal __be32 nfserr_* macros sourced from version-specific enums rather than enum nfs_stat. Watch for the still-unposted xdrgen include swap; that is the patch that will actually stop NFSD (and, later, the client) from pulling uapi/linux/nfs.h just to name a status code.
