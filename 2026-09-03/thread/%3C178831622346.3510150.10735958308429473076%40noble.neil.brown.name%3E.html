nfsd vfs_lookup_open() conversion hits DELAY and VFS-tree blockers

Summary

This week NeilBrown delivered the follow-up he promised on 24 August: switch NFSD’s NFSv4 OPEN/create path from the local do_lookup_open() helper onto mainline vfs_lookup_open(). The change is a server-side refactor of the create/open path, not a protocol change and not an NFS client patch. Jeff Layton Reviewed-by’d it the same day as “much less fiddly,” but Chuck Lever then listed process and correctness blockers — a VFS-tree merge requirement, two client-visible behavior shifts, and a directory-delegation stall that can pin every NFSD thread. Neil has not replied in-window. The patch does not land this week.

Prior weeks (brief)

Neil’s v5 nfs4_create_file() series extracted nfsd’s lookup-open work into a private do_lookup_open(). Maintainers held that series in nfsd-testing for extra linux-next soak (first in nfsd-next for v7.4) after patch 18/18 failed pynfs DELEG8: non-creating OPEN stopped returning NFS4ERR_DELAY during delegation recall. On 24 August Neil accepted the hold and said he would send the do_lookup_open() → vfs_lookup_open() conversion now that the VFS helper is upstream. This thread is that conversion. The DELEG8/NFS4ERR_DELAY contract is still the interoperability canary.

The patch

Neil’s posting is a two-file change (fs/namei.c plus fs/nfsd/nfs4proc.c, net −38 lines) against nfsd-test. He wants it in that tree for soak:

"This implementation shares more code with syscall open paths and so uses some filesystem interfaces slightly more correctly. It also takes the responsibility for locking out of nfsd so that planned changes can happen entirely in VFS code."

"This patch is against nfsd-test. I would like it to land there so it best good nfsd testing over the coming weeks."

The commit message flags two known deltas versus do_lookup_open():

  • Type errors: the old helper used nfsd_check_obj_isreg(). vfs_lookup_open() returns -ENODEV for a device-special file, which the patch maps to -EFTYPE.
  • vfs_lookup_open() rejects O_LARGEFILE, so the patch also tweaks fs/namei.c “to avoid a warning.”

The subject names nfsd4_open(). Chuck later notes the actual edit is nfsd4_create_file().

Review: lockdep dismissed, then real blockers

Jeff Layton liked the cleanup and tagged Reviewed-by, pointing at a Sashiko lockdep report:

"This looks good to me, but sashiko noted a lockdep issue you probably want to address"

"Other than that though, this looks good to me. Much less "fiddly"."

Neil dismissed the lockdep hit as a false positive from inode-mutex subclassing:

"This is of no consequence. start_creating() doesn't really need I_MUTEX_PARENT as the child will never be locked. Only start_removing() and start_renamed() need that. But it was simpler to use the same subclass for all cases."

"lookup_open() could use I_MUTEX_PARENT but doesn't need to as the opened inode will not be locked, whether it is created or not."

Chuck Lever then opened the real review. First, process: because the patch touches fs/namei.c, it cannot go through nfsd alone.

"Since it touches fs/namei.c, Christian will want to take this through the VFS tree. To get the testing you requested, I’ll have to merge the VFS tree into nfsd-next / nfsd-testing when it is ready for exposure. That might be a while."

He also asked whether the subject is wrong:

"IIUC the patch modifies nfsd4_create_file(), not nfsd4_open() ?"

Then two client-visible behavior changes he wants declared intentional or fixed:

"A client sending mode 0040755 gets an inode created with S_IFSOCK|0755 and trips this WARN_ONCE. The old code clamped the incoming mode with S_IALLUGO."

"Looks like a GUARDED4 create over a non-regular name now returns NFS4ERR_EXIST. The old code returned ISDIR or SYMLINK. Does this match NFSv3’s behavior? Should the commit message provide a rational that this is intended, or is a type check needed?"

The mode hole is a concrete bug-class issue for any NFSv4 client that puts a type bit in mode on OPEN(CREATE): the server can now create a socket (and WARN) instead of a regular file. The GUARDED4 mapping change is an interoperability question for Linux nfs.ko and every other v4 client that treats NFS4ERR_ISDIR / NFS4ERR_SYMLINK as a type probe rather than a simple “name exists.”

The DELAY contract, again

Chuck’s last point is the same class of failure that killed patch 18/18, now on the creating path and on directory delegations:

"Since NFSD threads now sleep on directory delegation recalls, if lookup_open() passes a real delegated_inode, it waits in break_deleg_wait() and retries for up to lease_break_time."

"The old path called vfs_create(..., NULL), so the client got NFS4ERR_DELAY instead. NFSD needs to continue to work this way, otherwise a client can cause all the NFSD threads to block."

That is the important client-development takeaway this week. Linux NFS clients that hit a recall (file or directory) expect NFS4ERR_DELAY and retry. The old nfsd create path passed a NULL delegated-inode into vfs_create() so the server bounced the RPC instead of sleeping. vfs_lookup_open() / lookup_open() will wait in break_deleg_wait() for up to lease_break_time. A single client that holds a directory delegation can therefore park every nfsd thread in the lease-break wait, starving the server. Until that policy is expressed on the shared VFS path — DELAY to the client, no thread stall — unifying nfsd OPEN/create with syscall open() remains unsafe for any NFSv4 client.

No Linux client code is proposed here. The risk is entirely server-side behavior that clients already depend on.

Conclusions this week

  • Classification: nfsd refactor toward shared VFS lookup-open, with a small fs/namei.c tweak. Not a protocol change. Not an NFS client patch. Not ready to merge.
  • Jeff’s review is an ack of the direction (“much less fiddly”) plus a lockdep nit Neil considers harmless.
  • Chuck’s review is blocking: VFS-tree routing, subject/function mismatch, missing S_IALLUGO clamp, GUARDED4 error-code change (EXIST vs ISDIR/SYMLINK), and the break_deleg_wait() stall versus NFS4ERR_DELAY.
  • Client impact: Linux nfs.ko is not patched, but three server behaviors it (and other v4 clients) see would change: create-mode type bits, GUARDED4 type errors, and OPEN/CREATE during directory-delegation recall. The last of those can hang the server thread pool rather than return DELAY.
  • Status: no v2, no merge to nfsd-testing this week. Neil still owes a reply, and any landing path runs through Christian Brauner’s VFS tree first.
