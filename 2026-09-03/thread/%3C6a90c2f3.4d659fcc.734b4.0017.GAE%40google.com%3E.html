syzbot: C reproducer for nfsd_nrthreads hang under rpcbind

Summary

Summary

This is a bug report, not a feature and not a protocol change. The thread remains an nfsd server control-plane hung-task: a write to /proc/fs/nfsd/threads blocks in nfsd_nrthreads() on the global nfsd_mutex while a sibling write to /proc/fs/nfsd/portlist already holds that mutex in write_ports(). There is still no NFS client code in the stack and still no human reply. What changed this week is that the hang is no longer a one-off lock dump: syzbot now has a C reproducer, and the lock listing names the missing piece of last week's diagnosis — the holder is sitting in rpcb_create_local().

Prior week (brief)

On 27 August, syzbot's original report hung two tasks of the same process for more than 143 seconds on upstream 502d45774af0. The waiter was write_threads → nfsd_nrthreads; the holder was write_ports. There was no reproducer. The lock dump already matched Jeff Layton's July diagnosis of the related netlink listener_set hangs: listener setup registers with local rpcbind while still holding nfsd_mutex, and a down or slow rpcbind turns that into a tens-of-seconds stall. Neil Brown's question from that earlier thread — why wait a whole minute for a local service — was still unanswered. Layton had already said, after talking to Chuck Lever, that the long-term plan is to move most rpcbind SET/UNSET into userland, with no timeline, so the list would "suffer with more syzbot reports." This week's mail is that prediction, now with a test case.

What landed this week

Late Wednesday, 2 September, syzbot followed up on linus HEAD 89a312991dc6 (Merge tag 'cifs-fixes-7.3-rc2'). The important sentence is the one that was missing last week:

"syzbot has found a reproducer for the following issue"

The C reproducer is at https://syzkaller.appspot.com/x/repro.c?x=143c8b49580000. The kernel is again a PREEMPT(full) syzkaller build, this time untainted. The hung-task watchdog fired at the default 10-second threshold rather than the 143-second figure from the first dump, which is consistent with a now-repeatable stall rather than a long, accidental timeout. syzbot again asked that any fix carry:

"Reported-by: syzbot+86a9d43d89b86def6d59@syzkaller.appspotmail.com"

and offered the usual #syz test: hook. Nobody on linux-nfs used it this week.

The lock dump now names rpcbind

The waiter is unchanged. Task syz-executor195/6046 is in D-state on nfsd_mutex in the legacy nfsctl threads writer:

"nfsd_nrthreads+0x57/0xd0 fs/nfsd/nfssvc.c:252 write_threads+0x34a/0x600 fs/nfsd/nfsctl.c:445 nfsctl_transaction_write+0x106/0x1a0 fs/nfsd/nfsctl.c:114"

It already holds &f->f_pos_lock and sb_writers from ksys_write.

The holder is the same sibling pattern as 27 August, but the lock listing is more specific. Task syz-executor195/6044 holds four locks, on CPU 3:

#LockSite
0&f->f_pos_lockfdget_pos
1sb_writers#13ksys_write
2nfsd_mutexwrite_ports+0xa5 (nfsctl.c:867)
3rpcb_create_local_mutexrpcb_create_local+0x100 (rpcb_clnt.c:353)

That fourth lock is the smoking gun last week's dump did not print. write_ports() — the /proc/fs/nfsd/portlist writer that creates nfsd listeners — is not merely "taking a long time." It is inside rpcb_create_local(), the SunRPC helper that builds the in-kernel rpcbind client (and does a synchronous RPC ping of local rpcbind) while still holding nfsd_mutex. nfsd_nrthreads() is an innocent waiter: it only takes that mutex to read nn->nfsd_serv->sv_nrthreads. Every other nfsd admin path that uses the same lock queues behind the rpcbind I/O.

This is not an AB-BA deadlock between threads and ports. Both tasks take nfsd_mutex in the same direction. The hang is a long hold: listener setup coupled to local rpcbind under a global mutex that also serializes thread-count changes, export-cache upcalls, and nfsd teardown.

The NMI backtraces are again a red herring for the NFS path. CPU 0 is in csd_lock_wait / smp_text_poke_batch_finish from a kfence toggle_allocation_gate work item; CPU 2 is in serial8250_console_write; CPU 3 is idle. None of that is on the nfsd stacks. The nfsd story is entirely write_ports → rpcb_create_local holding nfsd_mutex across a local rpcbind operation while write_threads waits.

Same root cause, now mechanically reproducible

The 2 September dump is the procfs twin of the netlink listener_set hangs from late August. Both paths create listeners and, for NFSv2/v3, register them with local rpcbind while still holding nfsd_mutex. write_ports adds sockets one at a time through the nfsctl file; listener_set can batch many in one netlink message. Either way, a down, slow, or not-yet-started local rpcbind turns each registration into a stall long enough for hung_task_timeout_secs.

Jeff Layton's diagnosis from the July cache-flush thread still applies almost verbatim, and this week's lock listing is the first time this particular thread has shown the rpcbind client being created on the holder:

"The hard problem here is that rpcbind registration is done synchronously under the nfsd_mutex. To talk to rpcbind, the kernel has to create a RPC client, which does a RPC ping first. If rpcbind is down then it can take up to a minute for the RPC ping to time out."

The C reproducer is concurrent nfsctl writes (ports vs threads) on a syzkaller kernel. Operators do not need syzkaller to hit the same shape: echo a listener into /proc/fs/nfsd/portlist while rpc.nfsd or a script writes /proc/fs/nfsd/threads, with rpcbind slow or absent. The 10-second hung-task report is then the control plane, not the data path.

The design fork is unchanged from last week. Short-term options on the table in the related listener_set discussion were: shorten the local rpc_ping timeout (Neil Brown: if a local service has not answered in one second, it is not going to), drop nfsd_mutex around registration, or cap the listener list (already rejected as the wrong root cause). The long-term plan Layton described after talking to Chuck Lever is to move most rpcbind SET/UNSET into userland, which would rev the nfsd netlink protocol. None of those patches appeared in this thread this week. There is still no timeline.

NFS client impact

There is no client patch here and no client-side bug to fix. The stall still sits on paths NFS clients actually use, and the new rpcb_create_local evidence makes that coupling explicit.

  • Thread and listener control. write_threads / nfsd_nrthreads is how nfsd is started and how the thread pool is resized. While it is stuck behind write_ports → rpcb_create_local, new nfsd threads do not come up. NFSv4 clients never talk to rpcbind, but they still need a live listener and a responsive control plane. A client mount against a server that is still bringing up nfsd simply does not complete for the duration of the hang.
  • Export-cache and mount. The same nfsd_mutex serializes export-table dumps and downcalls. A client mount of a just-exported path that still needs an export-cache fill waits out the rpcbind stall even if the operator never touched portlist from that client.
  • NFSv2/v3 discovery. The underlying rpcbind-under-mutex problem is specifically a v2/v3 client-visibility issue: nfsd will serve without a successful registration, but clients that find the server via portmap see a missing or stale table. The hung nfsd_nrthreads is the control-plane counterpart of that same stall. rpcb_create_local_mutex on the holder is the kernel building the rpcbind client that those v2/v3 clients depend on, on the wrong side of the mutex that also starts the server.
  • Admin tools that still use /proc/fs/nfsd. Not every deployment has moved to nfsd netlink. rpc.nfsd, nfs-utils, and scripts that echo N > /proc/fs/nfsd/threads are the waiters in this dump. They hang even when the operator is only trying to start or resize the server, not add ports. The C reproducer is that workload, automated.

Nothing in this week's other linux-nfs traffic — Chuck Lever's NFS3ERR / nfserr header rework, the cifs-fixes merge named in the syzbot HEAD — touches nfsd_mutex or rpcb_create_local. They do not mitigate this hang.

Status

  • Type: hung-task / DoS bug in the nfsd procfs control plane (write_threads / nfsd_nrthreads waiting on write_ports → rpcb_create_local). Same nfsd_mutex × synchronous rpcbind root cause as the July/August netlink reports; still unpatched.
  • Reproducer: yes, as of 2 September. C reproducer linked from the follow-up. Last week's lock dump is confirmed, not superseded.
  • New evidence this week: the holder also owns rpcb_create_local_mutex in net/sunrpc/rpcb_clnt.c. That is the first on-list confirmation in this thread that the long nfsd_mutex hold is the in-kernel rpcbind client, not some other listener-setup work.
  • Human reply: none in this thread as of 2 September. The related listener_set discussion already has a design fork (shorten rpc_ping, drop the mutex around registration, or move rpcbind to userland) but no merged fix and no timeline for the userland protocol rev.
  • Fix tag requested: Reported-by: syzbot+86a9d43d89b86def6d59@syzkaller.appspotmail.com.
  • Test hook unused: syzbot will apply a pasted patch or #syz test: git://repo/address.git branch-or-commit-hash. Nobody sent either this week.

Until listener setup no longer holds nfsd_mutex across rpcbind I/O — or until that I/O fails in well under a second — every nfsd admin path, netlink or /proc/fs/nfsd, is another hung-task report waiting to happen. This week's follow-up does not change the diagnosis. It gives maintainers a C reproducer and a lock dump that names rpcb_create_local on the holder, which is enough to test a fix and not enough to ship one.
