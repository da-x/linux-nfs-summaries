Windows NFSv4.1/4.2 Client Test Binaries Seek Linux 6.6+/7.2 Interop

Summary

This week’s linux-nfs traffic on this thread is a single cross-post, not a Linux kernel NFS client patch series. Martin Wege forwarded Roland Mainz’s 2026-09-03 test-binary announcement for the out-of-tree ms-nfs41-client Windows NFSv4.1/4.2 filesystem driver, asking the Linux NFS community for interoperability feedback against current Linux nfsd.

This is a new-feature / interoperability announcement for a third-party Windows client. There is no in-thread debate, no kernel patch review, and no conclusion beyond the request to test. The binaries target Windows 10/11 (x86, x86-64, ARM64) and Windows Server 2019/2022/2025 (x86-64, ARM64), built from git commit #448d4492cd7075bccdda94fc013f2af80c78d8d0.

Call for Linux nfsd testing

Wege’s cover note is aimed squarely at Linux server operators:

"Please test the binaries. The NFSv4.2/4.1 client is for Windows 10/11 ARM64+AMD64+x86 and Windows Server 2019+2022+2025/AMD64, but Interoperability feedback with NFSv4.1/NFSv4.2 servers based on Linux 6.6+ LTS and 6.19+/7.2 would be great."

He flags four items as the most interesting for Linux-side testers:

"New idmapper which maps any NFS user/group to any Windows user/group, support for Linux 7.2 case-insensitive NFS filesystems, Windows Alternate Streams (Win32 streams) support (requires NFSv4 named stream support), xcopy.exe/cmd.exe copy/MS Explorer file copy acceleration via NFS server side copies, and copy-by-block-cloning are IMO the most interesting new features."

A practical Windows-side note for testers: x86-64 users can now load the kernel module without testsigning mode by running opensource_driver_bootbypass.bash after /sbin/msnfs41client install.

What changed since the 1 August drop

Mainz’s changelog since the 2026-08-01 binaries is mostly stability and Windows plumbing, but several items matter for Linux nfsd interop:

  • many NFSv4.1 callback fixes — the Windows client’s backchannel path, which Linux nfsd still has to service
  • XDR cleanup “for better stability”
  • krb5/SSPI fixes (Kerberos mounts against Linux KDC/nfsd)
  • Network Provider no longer depends on debug DLLs and “now should work reliable in Win11 Explorer&co”
  • Creating virtual disks from sparse files on NFSv4.1 now works with OFSMount
  • The driver can now be built on 32-bit Windows 10 with VS2019 (runtime on 32-bit kernels already worked)

Features Linux nfsd operators should actually exercise

The longer “since 2026-06-01” list is where the Linux-relevant protocol surface lives. Testers hitting Linux 6.6 LTS, 6.19+, or 7.2 nfsd should pay attention to:

Case-insensitive exports. Mainz now claims “more fixes for case-insensitive NFS filesystems,” requiring “FreeBSD n>= 16.0 NFS server, Linux >= 7.1 NFS server or Windows Server NFS server with a case-insensitive filesystem.” That lines up with the ongoing Linux nfsd work to report FATTR4_WORD0_CASE_INSENSITIVE correctly; Wege specifically names Linux 7.2.

NFSv4.2 COPY and CLONE. The client implements FSCTL_OFFLOAD_READ/FSCTL_OFFLOAD_WRITE so Windows Explorer, xcopy.exe, and cmd.exe copy can use server-side NFSv4.2 COPY, plus FSCTL_DUPLICATE_EXTENTS_TO_FILE so CopyFile2() can clone via NFSv4.2 { CLONE, SEEK, DEALLOCATE } on btrfs/xfs (including sparse files). This is the main Linux-client-adjacent protocol exercise in the drop: Linux nfsd’s COPY/CLONE/SEEK/DEALLOCATE path, as seen from a Windows application stack.

Sparse files. Requires NFSv4.2 { SEEK, ALLOCATE, DEALLOCATE } and FATTR4_WORD1_SPACE_USED. Mainz also records a prior fix for “issues probing sparse files when using the nfs-ganesha NFS server.”

Named attributes / Win32 ADS. Alternate Data Streams and Windows EAs are mapped to NFS named attributes. Linux nfsd named-attribute coverage is the obvious interop question; the announcement’s working examples are Solaris ≥ 11.4, Illumos, and FreeBSD ≥ 15.0.

Idmapper. A per-mount shell-script idmapper (cygwin_idmapper.ksh) can map any NFS {uid,gid,fattr4_owner,fattr4_owner_group} to any Windows account, including localized builtin names. Mainz’s rationale:

"Idmapping itself is done with a shell script (for maximum flexibility, as attemps to handle this with builtin code could NOT cover all compliciated site setups, including Windows localised account names, and NFS clients which have to connect to multiple different sites with completely different NFS server account setups)"

A new winfsinfo subcommand, fsctlnfs41queryidmapinfo, dumps the mapped Win32 names, Cygwin/UWIN uid/gid, and NFSv4 owner strings for diagnostics.

Other protocol/ops notes. SRVOpen collapsing (one NFS filehandle shared across Windows opens, cutting OPEN/CLOSE round-trips); ACL-at-create; sec=none; NFS referrals on non-2049 ports; UNC paths rewritten as <hostname>@<protocol>@<port> (e.g. ournfsserver@NFS@2049) to leave room for RDMA/TLS; experimental UNC tag numbers for distinct connections; nfs_globalmount for machine-wide mounts; nfsclientdctl for runtime daemon knobs.

What this is not

This is not Linux NFS client development and not a kernel bug-fix thread. No linux-nfs replies landed in the 28 August–3 September window. The value for this list is as a test vector: a Windows NFSv4.1/4.2 client that now leans on Linux nfsd’s case-insensitive attrs, NFSv4.2 COPY/CLONE/SEEK/DEALLOCATE, sparse-file attributes, callbacks, and (where implemented) named attributes. Mainz asks that bugs and test reports go to the ms-nfs41-client-devel list, not here.

Downloads and SHA-256 sums are in Mainz’s announcement; full notes are at the 20260903 git448d449 HTML/readme URLs he posted.
