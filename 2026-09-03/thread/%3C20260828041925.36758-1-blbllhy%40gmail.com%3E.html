nfsd: lock cl_openowners walk to close EXCHANGE_ID UAF

Summary

This week's linux-nfs traffic included a compact but consequential bug-fix thread for the NFSD state machine: a KASAN-confirmed slab use-after-free in client_has_state() / client_has_openowners(), triggered on the EXCHANGE_ID path when an openowner is unhashed and freed under cl_lock while another thread walks the same list without that lock.

The discussion is entirely server-side (fs/nfsd/nfs4state.c). There is no NFS client code change here; the practical impact for client developers is that a concurrent EXCHANGE_ID with mismatched credentials could previously crash the server, which in turn would stall or reset client mounts. The patch is tagged for stable.

The race: unlocked openowner walk vs. nfs4_put_stateowner()

Cen Zhang of Microsoft Security FORGE Labs posted a one-file patch that takes clp->cl_lock for the duration of the openowner walk in client_has_state(). The commit message lays out the race with unusual clarity:

"client_has_openowners() walks clp->cl_openowners and reads so_stateids without clp->cl_lock. nfs4_put_stateowner() unhashes that openowner under cl_lock and then frees it, so a concurrent EXCHANGE_ID with mismatched creds can use-after-free the nfs4_openowner."

KASAN caught it in the EXCHANGE_ID compound:

BUG: KASAN: slab-use-after-free in client_has_state+0x10a/0x140
  fs/nfsd/nfs4state.c:3718 client_has_openowners()
  nfsd4_exchange_id
  nfsd4_proc_compound
  nfsd_dispatch
  svc_process

The regression is pinned to 4eaea1342507 ("nfsd: improve client_has_state to check for unused openowners") — the earlier improvement that started inspecting unused openowners (and their so_stateids) without also taking the lock that serializes unhash/free. Xiang Mei (Microsoft) is credited as reporter; the patch Ccs AutonomousCodeSecurity@microsoft.com and stable@vger.kernel.org.

The mechanical change is small (12 lines in fs/nfsd/nfs4state.c): acquire clp->cl_lock before walking cl_openowners, drop it afterwards. That matches the locking already used by nfs4_put_stateowner() when it unhashes an openowner, so the list walk can no longer observe a freed nfs4_openowner.

Process niggle: From: address vs. applying a UAF fix

The only technical objection this week was not about the lock at all. Greg Kroah-Hartman asked Zhang to resend from a corporate address:

"Please use your microsoft.com email address, and not a random gmail.com address. It's kind of odd that Microsoft would have to rely on Google to send kernel patches :)"

Chuck Lever, as NFSD maintainer, treated that as a process question rather than a NAK of the fix, and asked Greg whether he should wait:

"Greg, would you prefer that I hold off on applying this to nfsd-testing until Cen can post this one again?"

Greg declined to dictate:

"That's your call."

Conclusion: applied to nfsd-testing

Lever then applied the original patch without waiting for a resend. His b4-ty note records:

"Applied to nfsd-testing, thanks!"

as commit 6882aca9f9cabfaec5ea23d1512f345fbd288b65 (nfsd: hold cl_lock in client_has_state()).

No follow-up from Zhang, no alternative locking scheme, and no argument that the UAF diagnosis was wrong. The thread therefore ends this week as a stable-bound NFSD bug fix already in nfsd-testing: the openowner list walk in client_has_state() is now serialized with unhash/free, closing a KASAN-visible use-after-free on concurrent EXCHANGE_ID. Client-side work is unaffected except insofar as a previously crashable server is now expected to survive that race.

Classification: bug fix (locking / use-after-free), not a new feature or protocol change. Status: applied to nfsd-testing; From-address hygiene left as a maintainer judgment call rather than a blocker.
