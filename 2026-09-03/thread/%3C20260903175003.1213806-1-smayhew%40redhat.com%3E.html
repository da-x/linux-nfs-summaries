statd notify_list leak in nlist_free

Summary

This week Scott Mayhew posted a small but consequential nfs-utils PATCH that repairs a long-standing memory leak (and a related wrong-free) in rpc.statd's notify-list teardown. The change is a userspace bug fix, not a protocol change: it targets the NSM helper that NFS clients rely on for lock recovery after a server reboot.

There is no prior-week history for this thread. The posting arrived on 3 September with no replies yet in the window, so the discussion is still at the "proposed fix" stage.

Why it matters for the NFS client

rpc.statd is the Network Status Monitor daemon. NFS clients (and servers) register hosts with it so that, after a crash or reboot, SM_NOTIFY can drive NLM lock reclaim. The notify list is the in-memory structure that carries those cloned host records through SM_NOTIFY processing and SM_UNMON teardown. A leak there is not a data-path performance tweak; it is a slow leak on every monitor/unmonitor and notify cycle, which is exactly the traffic a lock-using NFS client generates.

Mayhew's diagnosis is blunt: nlist_free() never matched its own contract.

"nlist_free() freed an entry's string members but never the notify_list struct itself, despite its name and comment ("Destroy an entry ... and free the memory"). Every caller was expected to free the struct separately, but several did not"

The leaky callers he names are all on the NSM request paths that a client (or a client-facing statd) actually hits:

  • process_reply() and process_notify_list() in rmtcall.c, which clean up entries cloned onto the notify list during SM_NOTIFY handling
  • sm_unmon_1_svc() and sm_unmon_all_1_svc() in monitor.c, which leak the same way on SM_UNMON

That is the client-visible bug: notify and unmonitor processing drop string members and then abandon the notify_list node.

The second bug: nlist_kill() freed the wrong node

The same helper had a more dangerous mistake on the kill path. Mayhew writes:

"nlist_kill() previously called nlist_free(head, *head) followed by free(*head); since nlist_remove() (called from nlist_free) already advanced *head to the next entry, that free(*head) freed the wrong, still-live element."

In other words, the intended free of the just-destroyed entry instead released the next live list node. That is a use-after-free / double-free class defect sitting next to the leak, not merely an accounting miss.

The fix

Rather than paper over each caller, Mayhew moves ownership into nlist_free() itself so the function actually frees the struct. Call sites that already did the extra free() — sm_mon_1_svc() and load_one_host() — drop those now-redundant calls to avoid a double-free. nlist_kill() is taught to pass NULL so nlist_free() only frees the current entry, then the list pointer is advanced by hand.

The diff is tiny: two files (utils/statd/monitor.c, utils/statd/notlist.c), two insertions and four deletions. The design choice is the interesting part: fix the helper's contract instead of sprinkling free() at every SM_NOTIFY / SM_UNMON cleanup site. That is the right shape for a leak that several independent callers had already gotten wrong.

The patch carries Assisted-by: Claude Opus 4.8 and Mayhew's Signed-off-by. No reviewer Acked-by or comments landed this week.

Status

This is an unreviewed nfs-utils bug-fix posting. It does not change NSM on the wire; it corrects userspace lifetime of the notify-list nodes that the NFS client's lock-recovery helper allocates. Until it is reviewed and merged, rpc.statd still leaks notify_list structs on SM_NOTIFY cleanup and SM_UNMON, and nlist_kill() still risks freeing a live successor. Watch for review on the next list cycle.
