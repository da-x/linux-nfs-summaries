nfsd: Accept backdated timestamps from delegation holders

Summary

Summary

Jeff Layton posted a targeted bug fix for NFSD's handling of delegated timestamps: when a client holding an attribute delegation reports a backdated atime or mtime at DELEGRETURN, the server currently discards the value and then stamps c/mtime with "now," so tools that preserve timestamps (cp -p, rsync -t, tar -x) lose them. The patch treats the delegated client's SETATTR as authoritative. Chuck Lever immediately flagged a correctness hole in the ctime comparison, and Layton agreed to rework the logic in the VFS under consistent locking rather than land v1.

This is a server-side change with a direct NFS client impact: it is the missing half of the delegated-timestamp story that lets Linux clients cache utimensat() locally instead of issuing an RPC for every timestamp rewrite.

The client-visible failure

Layton's v1 describes a well-worn preservation path that currently fails against nfsd:

"A client with an attribute delegation reports the file times in a SETATTR at DELEGRETURN. nfsd ignores a time that moves backwards. It then stamps the c/mtime with the current time, so the file keeps the DELEGRETURN time. cp -p, rsync -t and tar -x lose timestamps."

The Linux NFS client is doing the right thing for a delegation holder. It applies an explicit utimensat() to its own inode and does not send a SETATTR while it still holds the delegation, so the backdated value reaches nfsd only as TIME_DELEG_MODIFY at return. The client could send an RPC for each time change, and that path already works, but it throws away the caching the delegation exists to provide.

Layton's design argument is that the delegation makes the client the authority for those times, so nfsd should treat the report as a statement of fact. The same value would already be accepted without a check if the client sent an ordinary (non-delegated) SETATTR.

The proposed rules:

  • nfsd accepts a backwards atime or mtime from a delegation holder.
  • An mtime that moves backwards sets the ctime to the current time. The ctime never moves backwards.
  • nfsd still clamps a future time.
  • The CB_GETATTR path keeps the old rule: a backwards time there is treated as a stale report, not as a SETATTR.

The patch is tagged Fixes: 3952f1cbcbc4 ("nfsd: fix SETATTR updates for delegated timestamps").

Client-side alternative, and why it was rejected

In the cover note, Layton considered fixing this purely on the client by always issuing an RPC for utimensat():

"We could fix this more correctly on the client by making it always issue an RPC for a utimensat(), but I think that would hurt untar-type workloads (which often backdate timestamps)."

That is the important client-development trade-off this week. Earlier this year the Linux NFS client already had to punch a hole in delegated-timestamp caching for atime-only utimensat() (xfstest generic/221), because there is no protocol mechanism to update ctime from a delegated atime-only change. Expanding that "always RPC" policy to ordinary timestamp-preserving workloads would serialize tar -x / rsync -t / cp -p against the server for every file. Layton is choosing to keep the client cache-friendly and make the server honor the delegated report.

One remaining semantic gap is acknowledged and left unfixed: nfsd cannot tell an explicit utimensat() from a report of a write. An mtime after the delegation grant and before "now" therefore sets ctime to that mtime instead of to the current time. RFC 9754 requires the "now" behavior; closing the gap would require the client to issue an RPC for the mtime. Layton is not taking that client hit for v1.

Protocol tension with RFC 9754

The commit message is explicit that this patch does not follow one sentence of RFC 9754 (the NFSv4.2 delegated-attribute spec), which says the server ignores a time before the original time. Layton argues that the same section also says the server MUST accept the change or MUST reject it with NFS4ERR_DELAY, and a silent discard does neither:

"A retry after NFS4ERR_DELAY carries the same backdated value, so that option cannot succeed."

In other words, the RFC's "ignore" rule is not a viable recovery path for a Linux client that is faithfully reporting a utimensat() it already applied locally. Accepting the backdated value is the option that actually interoperates.

Review: stale dl_ctime vs. multiple SETATTRs

Chuck Lever treated an LLM-assisted review finding as a blocker. The new helper nfsd4_vet_deleg_time() compared the incoming ctime against dp->dl_ctime, which is sampled once when the delegation is granted in nfs4_open_delegation() and never refreshed:

"Is dp->dl_ctime the right value to compare against here? It is sampled once, when the delegation is granted, and nothing refreshes it after that."

He then asked the client-facing question that matters for attribute delegations: is there anything that stops a client from sending more than one SETATTR with TIME_DELEG_MODIFY while it still holds the delegation?

His counter-example:

  1. First SETATTR carries mtime T5 later than grant-time dl_ctime. Vetting succeeds, ATTR_CTIME_SET stays set, inode ctime becomes T5.
  2. Second SETATTR backdates mtime to T3, where dl_ctime < T3 < T5. The comparison is still against the grant-time dl_ctime, so vetting succeeds again and T3 is carried into ia_ctime.
  3. notify_change() → setattr_copy() → inode_set_ctime_deleg() then drops that update, because T3 is older than the T5 already in the inode.

Result: mtime moves back to T3 and ctime stays at T5 — so ctime is neither carried from the mtime nor stamped with the current time. That contradicts both the comment in the patch and the commit message's claim that "An mtime that moves backwards sets the ctime to the current time."

Lever's suggested fix: compare against the inode's current ctime (the inode is already in hand for the current_time() call at the top of vet_deleg_attrs()).

Conclusion this week: v1 withdrawn in favor of a VFS rework

Layton agreed immediately:

"Yes, I think we do want to rework it to do that. Additionally, I noticed another race condition that we ought to fix while we're in here."

"I'll be sending a v2, but I think we have to push some of this handling into the VFS layer so that it's done under more consistent locking and properly uses the mgtime infrastructure."

v1 is therefore not landing. The discussion closed the same day it opened, with consensus that:

  • The bug is real and client-visible (timestamp-preserving tools against a delegated NFS mount).
  • The client should keep caching utimensat() under the attribute delegation; the server should accept the backdated report.
  • The v1 nfsd-only helper is not sufficient: ctime vetting must track the live inode, not the grant-time snapshot, and the update must run under VFS locking / mgtime so a second delegated SETATTR cannot leave ctime stranded.

A three-patch v2 ([PATCH v2 0/3] fs/nfsd: accept a backdated timestamp from a delegation holder) followed the next day as a separate thread, moving the stale-ctime stamp into inode_set_ctime_deleg() and comparing CB_GETATTR times against the inode. That series is out of scope for this v1 thread, but it is the direct continuation of the conclusion reached here.

Why this matters for NFS client development

Attribute delegations only pay off if the Linux client can apply local metadata updates — especially the backdated utimensat() storm from archive extraction — without a round trip per file. The current nfsd policy silently rewrites those times at DELEGRETURN, so a client that is correctly caching under WRITE_ATTRS_DELEG still fails userspace timestamp preservation. This week's v1 makes that failure explicit, rejects the "just RPC from the client" workaround as too expensive for untar-class workloads, and sets the requirement for the follow-on VFS change: honor the client's delegated times without breaking ctime monotonicity across multiple SETATTRs.
