nfsd v3 Netlink client dump still too clever for Layton

Summary

Dell’s Prabhakar Pujeri posted v3 of the nfsd Generic Netlink client-visibility series on 3 September, a two-patch reroll that applies Jeff Layton’s naming and defensive-programming nits from v2 and rebases onto nfsd-testing at ac579868af0c. This is a new userspace ABI / admin feature on the server — a privileged dump of connected NFSv4 clients plus O(1) per-client session and stateid counters — not a wire-protocol change, not a Linux NFS client patch, and not a runtime I/O bug fix. The existing nfsd filesystem files stay unchanged.

Layton reviewed patch 1/2 the same afternoon and rejected the dump iterator a second time. He wants the confirmed/unconfirmed walk pulled into a helper and called twice, not incremented through an enum. Patch 2/2 (the O(1) counters) is still uncommented. The series is v3, under review, not merged.

Brief bridge from v1/v2

v1 was a three-patch proposal: grace status on threads-get, a client-get dump, and per-client state counts. Layton objected that the grace attribute mirrored /proc/fs/nfsd/v4_end_grace and answered the wrong operational question (NFSv4 recovery done ≠ files accessible). Chuck Lever then asked that any new API not freeze grace as a server-wide boolean, because per-export grace is an open possibility for re-export / backend reboot. Pujeri dropped the grace patch; Lever’s “WFM!” closed that design dispute.

v2 was the promised two-patch client dump without grace. Layton called it “pretty sane” but asked for nfsd-style naming (find/marshal instead of get/put), an explicit table check instead of aliasing NFSD4_NL_CLIENT_DONE to unconfirmed, and a less clever dump iterator. This v3 is that reroll.

What v3 actually adds

Pujeri’s cover restates the operational problem: administrators can already inspect NFSv4 clients through the nfsd filesystem, “but collecting a server-wide view requires walking one directory and opening multiple files for every client.” The existing nfsdfs files stay unchanged. A companion nfs-utils v2 series (cover <cover.1787988918.git.prabhakar.pujeri@dell.com>) adds nfsdctl clients.

The two remaining steps:

  1. Dump basic NFSv4 client identity, address, lease, confirmation, reclaim, and callback state.
  2. Add O(1) snapshots of per-client session and stateid record counts.

He is explicit that grace stays out:

"This reroll intentionally drops the grace-status patch. As discussed with Chuck, that interface needs an explicitly scoped design that can represent both current server-wide grace and possible per-export grace in the future. I will address it in a separate proposal."

Changes since v2, all from Layton’s review:

  • rename the client lookup helper to nfsd_nl_find_client() ("get" connotes refcounting)
  • validate the client-table argument explicitly in nfsd_nl_find_client() instead of aliasing NFSD4_NL_CLIENT_DONE to "unconfirmed"
  • rename nfsd4_nl_client_put_address() to nfsd4_nl_client_marshal_address() ("put" connotes refcounting)
  • document the confirmed-then-unconfirmed table ordering in the dump loop comments
  • rebase onto nfsd-testing at ac579868af0c

Carried from v1→v2: split sockaddr into IPv4/IPv6 address, port, and optional IPv6 scope-ID; a nonzero client-table generation plus genl_dump_check_consistent() so churn marks the dump NLM_F_DUMP_INTR; maintained u64 counters instead of walking session lists and stateid IDRs under cl_lock; variable-width Netlink uint attributes.

Validation this round is narrower than v2’s QEMU boots: strict checkpatch on both patches and a focused NFSD W=1 build of fs/nfsd on nfsd-testing at ac579868af0c. The series is 565 insertions across 11 files, including YAML Netlink specs, nfsd-admin-interfaces.rst, and include/uapi/linux/nfsd_netlink.h.

Patch 1/2: privileged client-get dump

Patch 1/2 is the ABI core. It emits one bounded message per confirmed or unconfirmed client: server-generated client ID, peer address, minor version, client and callback states, signed lease time remaining, and RECLAIM_COMPLETE status.

Concurrency is still conservative. Each client is pinned for the snapshot; mutable lease and confirmation fields sit under the per-net client lock; server shutdown is serialized with nfsd_mutex. Client-table churn is a real dump-consistency flag:

"Track client-table changes with a nonzero generation counter and use genl_dump_check_consistent() so a dump that can skip or repeat a client is marked NLM_F_DUMP_INTR."

The peer is no longer a raw sockaddr blob: separate IPv4 or IPv6 address, port, and optional scope-ID attributes. That is what monitoring tools actually want.

The v2 nits that did land in this patch are the lookup helper rename, an explicit table switch that returns NULL for unexpected values, the marshal-address rename, and comments documenting confirmed-then-unconfirmed ordering. The dump loop itself still increments cb->args[0] through the table enum — and that is what Layton came back for.

Patch 2/2: O(1) per-client state usage

Patch 2/2 is a functional no-op versus v2 (rebase only). A client can “retain substantial server-side state even when its lease and callback channel look healthy,” so the dump grows separate counts for sessions and for open, lock, delegation, and layout stateid records. The lock count is deliberately not a byte-range or LOCK-operation count:

"A lock stateid represents a lock-owner/file pair and can cover multiple byte-range locks, so document that these are record counts rather than protocol operation or byte-range counts."

Counters live under cl_lock at the existing session and stateid publish/removal points, so the dump takes an O(1) snapshot instead of holding the spinlock across an unbounded IDR. Counters decrement only at final IDR removal, preserving record-count semantics for retained stateids. Encoding is variable-width Netlink uint (four bytes when the value fits in u32, eight otherwise).

That is the important server-side performance fix in this series: not a client I/O bug, but a dump that will not stall cl_lock on a client with a huge stateid table. Nobody has reviewed this patch in v2 or v3.

Jeff Layton: the iterator is still too clever

Layton’s review is confined to patch 1/2 and to a single remaining complaint. He did not object to the feature, the Netlink family, the generation/NLM_F_DUMP_INTR churn handling, or the naming changes that v3 already applied. He is not satisfied with comments-plus-enum-order as a substitute for rewriting the dump loop:

"Maybe I wasn't clear in my earlier email. cb->args[0] is an enum. Why are you incrementing through it like this? It's weird and it makes it unclear what this code is doing."

"It's also brittle. If someone expands that enum later, it could be problematic."

"Given that there are only two possible tables, there's no reason to make this so clever. Please rework this to be more human-readable."

His preferred shape is explicit, not clever:

"What I'd do is move all of the stuff inside the while() loop into a helper function, and then just call that twice: once with NFSD4_NL_CLIENT_CONFIRMED and once with NFSD4_NL_CLIENT_UNCONFIRMED."

That rewrite is the remaining review item. There is no ACK, no comment on patch 2/2, and no merge in this thread.

What this means for NFS client development and bug fixes

Nothing in this thread is an NFS client patch, a protocol change, or a client-visible I/O bug fix. The client-visible impact, if v3 lands after the iterator rewrite, is still indirect and operational: a privileged Netlink dump that a restart/failover harness — or an operator watching Linux NFSv4 clients against a Linux nfsd — can consume without walking /proc/fs/nfsd/clients.

The dump payload is the data that harness actually needs from each connected client: server-generated client ID, peer address (split into IPv4/IPv6, port, optional IPv6 scope-ID), minor version, client and callback states, signed lease time remaining, and RECLAIM_COMPLETE. Patch 2/2 then adds per-client session and stateid record counts so a client that still looks healthy on lease/callback can be spotted as the owner of a large state table. The grace half of that picture remains deferred to a later, scoped operation.

The only “bug-fix-shaped” pieces are dump robustness, not client correctness:

  • nfsd_nl_find_client() no longer treats NFSD4_NL_CLIENT_DONE as unconfirmed; unexpected table values return NULL.
  • Client-table churn is marked with a generation counter and genl_dump_check_consistent() / NLM_F_DUMP_INTR, so a dump that can skip or repeat a client is not silently inconsistent.
  • Unbounded session-list and stateid-IDR walks under cl_lock are replaced by maintained u64 counters, so the dump does not stall the per-client lock on a client with a huge stateid table.

Status at week’s end: v3, under review, not merged. Layton’s two-phase iterator rewrite is the open review item; patch 2/2 is unreviewed. A v4 that actually splits the dump loop is the next expected post.
