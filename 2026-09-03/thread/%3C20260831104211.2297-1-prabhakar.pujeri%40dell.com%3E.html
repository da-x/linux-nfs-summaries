gssd and idmapd name-validation bug fixes

Summary

Dell engineer Prabhakar Pujeri posted a three-patch nfs-utils series that hardens the NFS client user-space daemons against untrusted names coming from kernel upcalls and error paths. The work is a bug-fix series, not a protocol change or new feature: it stops rpc.gssd and rpc.idmapd from treating externally supplied buffers as C strings before those buffers have been shown to be NUL-terminated and to fit in their destination arrays.

In the cover letter, Pujeri framed the series as a single class of defects:

"These fixes validate externally supplied names before treating them as C strings. They correct an uninitialized read in an error path, keep idmapd inside the fixed NAMETOID field, and reject server hostnames that do not fit in gssd's destination buffer."

The series is based on current nfs-utils master. Pujeri reported a clean autotools rebuild and make check; the statd integration test is skipped when its service environment is missing. The three patches together touch only 11 insertions and 7 deletions across utils/gssd/gssd.c, utils/gssd/krb5_util.c, and utils/idmapd/idmapd.c. No reviews, acks, or nacks landed in this week's window.

Patch 1: gssd error path dumps uninitialized heap

Patch 1 is a one-line fix in gssd_get_topdir(). On inotify_add_watch() failure the code printed tdi->name, but that flexible-array member is filled only by a later strcpy(). The error path therefore logged uninitialized heap and could walk past the allocation if no NUL happened to sit nearby.

Pujeri's diagnosis is blunt:

"gssd_get_topdir() prints tdi->name in the inotify_add_watch() error path, but that flexible array member is only filled in by the strcpy() after the call. The message ends up dumping uninitialized heap memory and can even read past the allocation if no NUL byte is nearby."

The fix prints the caller-supplied name argument instead — the directory the watch was actually being added for. That is a client-side robustness fix for rpc.gssd's pipefs/inotify setup, not a change in Kerberos or NFS protocol behavior.

Patch 2: idmapd NAMETOID names must terminate inside the field

Patch 2 repairs imconv() in rpc.idmapd. The old code capped len at IDMAP_NAMESZ - 1 and then inspected im_name[len + 1]. An unterminated name therefore read one byte past the fixed field; a properly terminated name could still be rejected based on the unrelated byte after its NUL.

Pujeri replaced that with strnlen() so a terminator is required inside im_name:

"Use strnlen() to require a terminator within im_name. Mark an unterminated request as invalid before returning it to the kernel."

That is an important NFS client idmapping bug fix. Kernel NAMETOID upcalls arrive in a fixed-size IDMAP_NAMESZ slot; idmapd must not assume a C string and must not bounce a conversion based on memory outside that slot. Unterminated names are now marked invalid and returned to the kernel rather than being walked off the end of the buffer.

Patch 3: gssd rejects overlong server hostnames

Patch 3 is the most security-relevant client change. find_keytab_entry() copied a hostname from the kernel upcall into a stack NI_MAXHOST buffer with strcpy(), so an overlong name could smash the stack. The patch switches to snprintf() and checks the result:

"Use snprintf() and check its result. Reject a truncated hostname with ENAMETOOLONG instead of performing a keytab lookup with a different name. The verified string also fits in the following myhostad copy."

Truncation is treated as failure, not as a silent rename. That avoids looking up a Kerberos keytab principal for a different hostname than the kernel asked for — a correctness and security property for NFSv4/krb5 mounts — and it also keeps the subsequent myhostad copy in bounds.

Status this week

This is a new series posted on 31 August 2026. There were no replies, tags, or follow-up revisions in the week ending 3 September. The three patches stand as a compact nfs-utils client hardening set: stop logging uninitialized memory in gssd, keep idmapd inside the NAMETOID field, and refuse hostnames that do not fit gssd's keytab lookup buffer. Reviewers have not yet weighed in on whether ENAMETOOLONG is the right errno to surface to the kernel upcall, or whether similar strcpy() sites elsewhere in gssd/idmapd need the same treatment.
