Dell expands pNFS XDR hardening to leaks, version counts, and LAYOUTGET

Summary

This is an NFS client bug-fix / XDR-hardening series, not a protocol change and not a new pNFS layout feature. On 31 August, Prabhakar Pujeri of Dell posted [PATCH v2 0/7] NFS: harden pNFS XDR decoding, expanding last week's four-patch GETDEVICEINFO address-decoder work into a seven-patch series that also plugs netid leaks and bounds flexfiles version and filehandle counts. There were no replies this window; the patches remain unreviewed.

The threat model is now broader than malformed ports and unbounded multipath loops. Pujeri's cover letter states:

"pNFS device and layout replies contain several counts and strings supplied by the server. The current decoders trust some of those values before the reply has proved that the corresponding XDR objects are present. A broken or malicious server can therefore provoke oversized allocations, very long decode loops, malformed data-server ports, or leaked netid strings on temporary-address cleanup paths."

The series "makes those paths proportional to the received XDR length" and "validates both decimal port octets and uses the common data-server address destructor wherever a temporary address is discarded." All six functional patches carry Fixes: tags and Cc: stable@vger.kernel.org.

From last week's v1 to this v2

Last week Pujeri posted a four-patch series, "[PATCH 0/4] NFS: harden pNFS device address decoding," based on linux-next commit 10f307e525a1. That v1 validated port octets, bounded file-layout and flexfiles multipath loops by remaining XDR, and added KUnit coverage (16 address cases, 3 flexfiles cases). It drew no review.

v2 rebases onto v7.3-rc1 (cee9395acd8043be0644b25c34bfa86623f2b935) and adds three new functional patches plus expanded tests. The cover letter lists the delta:

"- rebase from the NFS client linux-next integration commit 10f307e525a1 to v7.3-rc1

  • free da_netid on file-layout and flexfiles temporary-address paths
  • bound flexfiles GETDEVICEINFO version_count before allocation
  • bound flexfiles LAYOUTGET fh_count before allocation
  • expand flexfiles KUnit coverage from three to six cases, including the cache-hit and malformed-version cleanup paths
  • rename the test patch to reflect the broader XDR coverage"

The test patch is now titled "add KUnit coverage for pNFS XDR decoding" rather than "address decoding," matching the wider decoder surface.

Patch 1: netid leak on temporary DS-address cleanup

Patch 1 is new in v2 and is a client memory-leak fix on the pNFS data-server address path. nfs4_decode_mp_ds_addr() transfers its r_netid allocation into da_netid. The generic destructor nfs4_pnfs_ds_addr_free() already releases that field, but the file-layout and flexfiles drivers open-coded disposal of temporary address objects and omitted it.

"Cache hits and later decode failures therefore leak one netid string per discarded address."

The fix exports nfs4_pnfs_ds_addr_free() to the layout modules (fs/nfs/pnfs.h) and uses it for every temporary address list in filelayoutdev.c and flexfilelayoutdev.c. Fixes: 4be78d26810b ("NFSv4/pNFS: Store the transport type in struct nfs4_pnfs_ds_addr"). This is the kind of leak that only shows up on cache-hit and decode-failure paths — exactly the cases the expanded KUnit suite now drives.

Patches 2 and 3: bound flexfiles version and filehandle counts before allocation

These two are the other v2 additions, both targeting oversized allocations from short replies.

Patch 2 hits the flexfiles GETDEVICEINFO decoder. It currently allocates ds_versions from a server-provided count before proving that the corresponding fixed-size XDR tuples are present.

"A large count can therefore provoke an oversized allocation from a short reply."

Each version tuple is five XDR words. The patch bounds the count by bytes remaining in the stream before allocating the array, and uses the same expression when decoding each tuple. Fixes: d67ae825a59d ("pnfs/flexfiles: Add the FlexFile Layout Driver").

Patch 3 applies the same idea to flexfiles LAYOUTGET. ff_layout_alloc_lseg() allocates a filehandle-version array from the server-provided fh_count before checking that the layout body can contain that many filehandles.

"Even an empty XDR opaque value consumes a length word. Bound fh_count by the number of length words remaining in the stream before allocating the array."

Same Fixes: as patch 2 — this is original flexfiles-driver fallout, now treated as a stable-bound client robustness bug. Together, patches 2 and 3 close the "trust the count, then allocate" pattern on both the device-info and layout-get sides of flexfiles.

Patch 4: stop trusting sscanf() on data-server port octets

Patch 4 is v1's port-octet rewrite, carried forward. nfs4_decode_mp_ds_addr() parsed the two decimal port octets of a server-provided universal address with an unchecked sscanf(). A missing or non-numeric field left part of a temporary array uninitialized; values outside the octet range were silently folded into the resulting port.

The replacement splits the two port fields at their delimiters and parses each with kstrtou8():

"This rejects missing fields, trailing garbage, integer overflow, and values outside 0 through 255 before constructing the data server socket address."

Fixes: 6b7f3cf96364 ("nfs41: pull decode_ds_addr from file layout to generic pnfs"). Because this is the generic pNFS helper, both file layout and flexfiles inherit the stricter parse.

Patches 5 and 6: bound multipath loops by remaining XDR, not U32_MAX

These are v1's most serious client bugs, restated unchanged.

Patch 5 hits file layout (nfs4_fl_alloc_deviceid_node()). That function already bounds the number of data-server multipath lists, but not the number of addresses inside each list. The inner count is server-supplied and can be U32_MAX. Once the XDR stream is exhausted, nfs4_decode_mp_ds_addr() returns NULL without consuming input.

"The enclosing loop can therefore spin for billions of iterations in kernel context when decoding a malicious GETDEVICEINFO response."

The chosen bound is not an arbitrary protocol cap. A netaddr4 needs at least the two XDR length words for its netid and universal-address strings. The decoder now rejects a count that cannot fit that minimum representation in the remaining stream, so the loop is proportional to reply length. The existing file-layout multipath-list limit stays, because it is tied to the u8 stripe-index representation. A helper is added in fs/nfs/pnfs.h so flexfiles can reuse the same check. Fixes: 14f9a6076f53 ("NFS: Parse and store all multipath DS addresses").

Patch 6 applies the same remaining-XDR bound to flexfiles (nfs4_ff_alloc_deviceid_node()), which previously did not validate the multipath address count at all.

"This makes the loop bound proportional to the reply length without imposing an arbitrary protocol limit, matching the protection in the file-layout decoder."

Fixes: d67ae825a59d ("pnfs/flexfiles: Add the FlexFile Layout Driver").

Patch 7: KUnit for address, GETDEVICEINFO, and LAYOUTGET

Patch 7 is the test investment that makes the first six patches reviewable without a pNFS MDS. It adds page-backed tests for nfs4_decode_mp_ds_addr() covering valid IPv4 and IPv6 universal addresses, boundary port values, missing fields, non-numeric fields, out-of-range values, integer overflow, and trailing garbage (fs/nfs/tests/pnfs_decode_kunit.c).

The flexfiles suite (fs/nfs/flexfilelayout/tests/deviceid_kunit.c) grows from three cases to six:

"Exercise the flexfiles GETDEVICEINFO decoder with valid device data, cache reuse, and zero or oversized multipath and version counts. Exercise the LAYOUTGET decoder with an oversized filehandle-version count. The cache-reuse and malformed-version cases also drive both temporary-address cleanup paths."

That last sentence is the client-development point: the new leak fix and the version/fh_count bounds are not just described — the tests force the temporary-address destructor and the allocation-before-decode failure paths. Flexfiles decoder helpers are exported only when KUnit is enabled. Both suites sit behind guideline-compliant Kconfig entries that default with KUNIT_ALL_TESTS.

Validation and where things stand

Pujeri reports:

  • nfs_pnfs_decode KUnit suite: 16/16 passed
  • nfs_flexfile_deviceid KUnit suite: 6/6 passed (up from 3/3 in v1)
  • GCC 16 and Clang 22 W=1 builds of fs/nfs/ with no NFS diagnostics
  • Sparse C=2 on every touched C source: clean
  • GCC 16 W=1 full kernel and modules build: passed
  • per-patch checkpatch: no errors; patch 7 reports only the generic FILE_PATH_CHANGES warning for the new test files

Unlike v1, this cover letter does not restate the "no pNFS-capable server" caveat, but the evidence is still the in-tree KUnit suites rather than a live MDS/DS topology.

Status this week: posted 31 August against v7.3-rc1; no Acked-by, Reviewed-by, or maintainer comment. Unmerged as of week-end. Until this lands, a broken or malicious pNFS server can still feed the client unbounded multipath/version/filehandle counts, an unchecked port parse, and leaked da_netid strings on cache-hit and decode-failure cleanup.

  • Kind of change: NFS client bug fix / XDR hardening. No protocol change.
  • Scope: generic nfs4_decode_mp_ds_addr() and nfs4_pnfs_ds_addr_free(), file-layout GETDEVICEINFO, flexfiles GETDEVICEINFO and LAYOUTGET, plus two KUnit modules.
  • Stable intent: all six functional patches are Cc: stable with Fixes: back to the original decoder, the multipath-address parser, the netid-in-nfs4_pnfs_ds_addr change, and the flexfiles driver.
