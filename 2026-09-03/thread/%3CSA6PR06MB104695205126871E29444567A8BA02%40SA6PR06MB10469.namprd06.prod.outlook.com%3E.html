Reporter retracts NFSv3 RDMA READ bug after spotting xprtrdma fix

Summary

This week’s traffic on Rakesh Bhargava’s NFSv3-over-RDMA corruption report is a two-message close-out, not a new diagnosis. The original 24 August bug mail remains the technical record: a legal READ3resok with attributes_follow = FALSE prepends 84 bytes of stale receive-buffer data onto an otherwise correct RDMA Write payload. On 1 September Bhargava pinged Trond Myklebust and Anna Schumaker for a status update; a day later he withdrew the ping, having found Chuck Lever’s already-posted client transport patch. This is a bug-fix thread, not a protocol change and not a new feature.

Prior week (brief)

Last week’s report, summarized separately, walked a RHEL 9.5-class client (Linux 5.14.0-503.22.1.el9_5.x86_64, vers=3, proto=rdma, port=20049) doing 4096-byte direct reads. RFC 1813 lets a server omit fattr3. The Linux NFS client still reserves a 128-byte AUTH_SYS head for the maximum READ reply; the actual inline RPC is 44 bytes. rpcrdma_inline_fixup() retargets the head iovec without shrinking iov_len, and xdr_read_pages() / xdr_shrink_bufhead() then slide the extra 84 bytes — exactly sizeof(fattr3) — onto pages that RDMA had already filled correctly. Ordinary NFSv3 mounts typically lose only the first READ because nfs3_read_done() then learns read_hdrsize. FlexFiles NFSv3 data servers never run that bookkeeping, so every DS READ is wrong.

Chuck Lever answered that report in separate postings last week: an RFC on 25 August and a tightened PATCH v2 on 26 August, both targeting rpcrdma_inline_fixup() in net/sunrpc/xprtrdma/rpc_rdma.c. The fix shrinks the head iovec to the inline header bytes actually received, but only when a Write chunk carried the payload, so the earlier krb5p repair in cb0ae1fbb2f5 is left alone. Those patches did not land as replies on this Message-ID; they are the “patch mail” Bhargava later said he missed.

This week: a ping, then a retraction

On 1 September, with no in-thread maintainer reply on the original Message-ID, Bhargava wrote:

"Hi, Any update on this..?"

The quoted original report is unchanged: same 84-byte smear, same FlexFiles repeatability, same three-layer blame (nfs3_xdr_enc_read3args() over-reserving, rpcrdma_inline_fixup() leaving iov_len at 128, XDR realign treating the gap as payload). The ping adds no new reproduction, no new numbers, and no proposed patch. It is a status request to trondmy@kernel.org and anna@kernel.org, with Scott Mayhew, Olga Kornievskaia, and Jorge Mora still on Cc.

Twenty-five hours later he took it back:

"Please ignore the mail. I missed the patch mail which fixed the issue."

That is the only new technical conclusion this thread produces this week: the reporter now treats Lever’s xprtrdma Write-chunk head-length shrink as the fix for the corruption he filed. He does not attach a Tested-by, does not name the patch Message-ID, and does not say whether he ran the v2 against the 5.14 RHEL client or a FlexFiles DS. The close-out is a retraction of the nudge, not a new analysis of the client path.

Client-development implications

The important NFS client fact is unchanged from last week, but this week the reporter and the transport maintainer are now aligned on where the fix belongs.

  • The bug is not in NFSv3 decode. decode_read3resok() correctly honors attributes_follow = FALSE and never walks an omitted fattr3. Corruption happens after a correct RDMA Write, when generic XDR realigns an oversized head.
  • The durable fix is in xprtrdma, not in nfs3_read_done()’s read_hdrsize learning. Header-size learning still explains why a regular NFSv3/RDMA mount only fails the first READ; it does not protect FlexFiles DS READs, whose layout-driver completion callback never records the shorter size. Clamping head.iov_len to the inline header on the Write-chunk path covers both.
  • The regression tag remains cb0ae1fbb2f5 (“xprtrdma: Do not update {head, tail}.iov_len in rpcrdma_inline_fixup()”). Restoring the length adjustment only for Write chunks is the client-transport invariant that keeps krb5i/krb5p reply decoding working.

Until Lever’s v2 is reviewed and merged, the in-tree client is still exposed. This thread, however, is no longer waiting on a diagnosis from NetApp. Bhargava’s 2 September note is an implicit Ack that the posted xprtrdma patch addresses the field failure, even without a formal Tested-by on this Message-ID.

Conclusions

  • Type of change: client-side bug fix (RPC-over-RDMA receive path). Not a new feature, not an ONC RPC or NFSv3 protocol change.
  • This week’s in-thread activity: a 1 September status ping, withdrawn on 2 September after the reporter found Lever’s already-posted patch.
  • Reporter’s closing line: “I missed the patch mail which fixed the issue.” That points at last week’s RFC / v2 rpcrdma_inline_fixup() shrink, not at a new patch in this thread.
  • Still open outside this thread: review and merge of the xprtrdma v2, plus a runtime Tested-by on the original 4 KiB direct-read / FlexFiles DS reproduction. No maintainer reply landed on this Message-ID this week.

The discussion on the original bug mail is effectively closed from the reporter’s side. Watch Lever’s v2 thread for the actual client merge.
