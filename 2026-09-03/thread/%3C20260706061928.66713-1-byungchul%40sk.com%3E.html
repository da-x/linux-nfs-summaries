DEPT v19: NeilBrown Challenges Wait-vs-Ownership Model

Summary

DEPT v19: NeilBrown Challenges Wait-vs-Ownership Model

Classification

This remains a new kernel feature under review: Byungchul Park's 40-patch DEPT (DEPendency Tracker) series, still at v19. Nothing this week is an NFS protocol change or an NFS client bug fix. The single in-window message continues the architectural fight over whether DEPT's wait/event engine is a sibling of Lockdep or merely a set of missing Lockdep annotations — specifically around folio PG_lock hand-off from task context to interrupt or workqueue completion, the pattern NFS client readahead and writeback live in every day.

Bridging Prior Weeks (Briefly)

v19 landed on 6 July. After a five-week lull, David Hildenbrand reopened the cover letter on 20 August, asking why DEPT cannot be a CONFIG_LOCKDEP_* extension, and Matthew Wilcox restated why PG_lock is not a Lockdep-shaped object (page lifetime vs. lock semantics, owner-based hierarchy, task-acquire / IRQ-release with an I/O-submit hole). Last week (21–25 August) the debate crystallized: Park defended a separate wait/event engine with a per-page timestamp and three global folio classes; Hildenbrand enumerated four merge options and preferred a Lockdep retrofit; NeilBrown showed that lock_map_release() / lock_map_acquire_try() already express cross-thread hand-off, and argued folio locks should be described as ranges of an address_space, not per-page objects. Park's last word of that week was that deadlock is a wait that is never awakened, and that ownership tracking is "not the essence." Neil's reply to that claim is this week's only mail. The only NFS-tree patch in the series remains the SUNRPC rcu_head relocation (patch 37/40).

This Week's Activity (28 August – 3 September)

One message, late on 30 August: NeilBrown answering Park's 25 August mail. No patches, no locking-maintainer Ack, no v20.

1. The timestamp is still unexplained

Park had said DEPT does not need a full lockdep_map in every page, only "a minimum space for a timestamp in each to track when each starts to wait so as to use the recorded timestamp when the event occurs e.g. folio_unlock()." Neil's first question is the one the cover letter and dept.rst (patch 25/40) have not answered at a reviewer's level:

"A timestamp? What does that do?"

"There is a lot of detail in your cover letter, but I think there is a lot missing too. I would like to understand how DEPT works, but I don't want to dig too hard. The document in patch 25/40 helps a bit, but it is still a bit vague."

"Where is the document which would explain at a level that would help me understand this timestamp?"

That is not a nit. Without a readable account of what the per-page wgen actually correlates — wait start versus unlock event, across reclaim and reuse of the same struct page — reviewers cannot judge whether DEPT's extra per-page state is load-bearing or an artifact of refusing Lockdep's class-map model.

2. Deadlock is ownership plus waiting, not "never awakened"

Park's essence claim — "a deadlock comes from waits that are never awakened" — is the point Neil rejects outright:

"I disagree."

"The "essence" of deadlock detection involves the interplay of ownership and waiting."

He then maps DEPT's own cover-letter vocabulary onto Lockdep's:

"In your cover letter "THE DEPT APPROACH" talks about [S] where and event context begins, and [E] where the even occurs. This S-E section is exactly ownership. During that time something "owns" the event. Maybe the terminology is different, but the concept is the same."

Park had granted that tracking who owns a lock is "certainly useful" but "if the goal is for tracking dependencies.. well.. I'm not sure." Neil's answer is equally short:

"I am sure. Dependencies are between waiters and owners."

If that identification holds, DEPT's wait/event engine is not a different theory of deadlock. It is Lockdep's ownership graph with different names, plus a per-page timestamp whose job has not been explained.

3. Annotation, not a sibling detector

Neil restates the process doctrine he put on-list last week, now aimed at Park's "comprehensive annotation" theme:

"A strong theme in your cover letter is the need to add comprehensive annotation for DEPT to work. My position is that most of what we need for LOCKDEP to be able to detect exactly the same things is appropriate annotation. We need to annotate when ownership is handed off to another thread, and when the other thread takes on ownership."

The superiority question from 21 August is asked again, sharper:

"So what does your scheme provide that is clearly better? Is the annotation easier? Is some of it automatic? Does if give better error reports?"

He grants one possible DEPT-only property after reading dept.rst: a lock released by a different thread than the acquirer. Even that, he treats as teachable:

"I had a look through dept.rst and it seems that if a lock is released by a different thread than the one which took the lock, then DEPT can detect that and do something useful. That might be interesting."

"But how does it know when it first took ownership of that lock? Or you use your terminology: how does it know when that lock first entered the context in that thread?"

His working hypothesis — and the Lockdep extension he is offering — is:

"Maybe when you see an "unlock", you assume the lock has been owned since the last time the context didn't hold hold any locks. Would that be right?"

"Surely it wouldn't the too hard to teach lockdep about that. i.e. when a lock, which is allowed to migrate across threads, is released though it wasn't held - insert this lock at the top of the current context and re-assess all the wait points."

The closer is the dual of the same question: if DEPT can add a lock to a context at unlock time, how does it drop one?

"How do you decide that a lock that was taken is no longer part of the current context?"

Park has not answered this week. The thread is waiting on him.

Evolution of the Discussion

The arc this week is one counter-punch, no reply:

  1. Last week closed with Park asserting that deadlock is a wait that never wakes, that a per-page timestamp is required, and that Lockdep-style ownership hand-off is the wrong model for dependency tracking.
  2. Neil spends 30 August identifying DEPT's [S]/[E] interval as ownership, insisting dependencies are waiter-to-owner, demanding a readable timestamp document, and sketching a concrete Lockdep change (insert a migratable lock at the top of the current context on a "released but not held" unlock, then re-assess wait points).
  3. No locking maintainer spoke. No v20. The dual-engine vs. retrofit question is unchanged, but the burden of proof has shifted: Park now owes an explanation of the timestamp and a demonstration that DEPT is not Lockdep-plus-hand-off-annotations.

Significance for NFS Client Development

No NFS client patch moved this week. The design fight is still the one that will decide whether DEPT (or a Lockdep extension) is usable on the NFS client:

  • Readahead and writeback remain the motivating I/O path. NFS client reads lock folios, submit READ RPCs, and unlock from RPC completion (softirq / workqueue). Neil's "released though it wasn't held" sketch is exactly that path: the completing context never acquired PG_locked, yet it is the owner at unlock. A detector that cannot mark the hand-off — whether DEPT's timestamp or Lockdep's proposed insert-and-reassess — will either scream about every NFS read or miss the "locked but never submitted" hang f2c817bed58d was written to contain.
  • Ownership hand-off is the NFS-shaped annotation. Neil's "annotate when ownership is handed off to another thread, and when the other thread takes on ownership" maps onto submit-bio / submit-RPC as the hand-off point, and folio_end_read() / SUNRPC completion as the take-on point. That is the same I/O-submit hole Wilcox flagged on 20 August.
  • The unanswered timestamp question is an NFS question. NFS reuses folios aggressively. If DEPT's per-page wgen cannot be explained without "dig too hard," reviewers cannot tell whether NFS writeback and readahead reports will mix stale-wgen false positives with same-mapping false negatives.
  • The SUNRPC rcu_head relocation is still the only in-tree NFS change, a compile-time kfree_rcu() accommodation for CONFIG_DEPT, not a runtime client fix. Nothing this week revisits it.

Final Conclusions (as of window close)

  • The series is still v19, still experimental, still without a locking-maintainer Ack.
  • NeilBrown's position this week: DEPT's [S]/[E] is ownership; dependencies are between waiters and owners; Lockdep needs hand-off annotations, not a sibling; the timestamp is undocumented at reviewer's level; a migratable-lock "unlock without hold" path could be taught to Lockdep by inserting the lock at the top of the current context and re-assessing wait points.
  • Park has not replied in this window. Last week's stance (separate wait/event engine, per-page timestamp, deadlock as never-awakened wait) is the position Neil is dismantling.
  • Hildenbrand's preference from last week — retrofit (option 4) or high-level integration then merge (3→4) — is consistent with Neil's incremental path and is still unanswered by a locking maintainer.
  • No merge path, no code change, no NFS client bug fix this week. The open question is now operational as well as architectural: either Park produces the missing timestamp document and a clear superiority argument (easier annotation, automatic coverage, better reports), or the room's working theory stands — DEPT's folio-lock value is a Lockdep annotation problem.
