Flexfiles v2 review: 64-bit stripe_unit and ndc_immediate nits

Summary

Review of Benjamin Coddington’s 23-patch NFS client series on flexfiles CB_NOTIFY_DEVICEID handling and wide-stripe cache scaling resumed this week with two focused exchanges between Coddington and NFS maintainer Anna Schumaker. The series remains a mix of stable-bound client bug fixes, a protocol-correctness feature for CHANGE/DELETE notifications under live layouts (RFC 8881), and cache scaling. Nothing merged. The design question that closed last week — reject a 64-bit stripe_unit that does not fit 32 bits, or promote the I/O path to full 64-bit arithmetic — is now settled in favor of the latter, and will land in v3. Schumaker’s first look at the ndc_immediate CHANGE path produced only comment nits, which Coddington accepted.

Brief bridge from last week

On 21 August Coddington posted PATCH v2 00/23, rebuilding the client’s device-node pin so a CHANGE can re-point a live layout, implementing RFC 8881 Section 18.40.4 DELETE race recovery, and growing the deviceid and data-server caches toward 1024-device striping. The first six patches are standalone client bug fixes (Cc: stable): silent 32-bit truncation of stripe_unit, an unbounded CB_NOTIFY_DEVICEID array allocation, a decoder that dropped ndc_immediate and then misaligned the rest of the array, a 32-bit file-offset truncation on the flexfiles read DS-selection path, and two page-coalescing bugs that sent bytes past a stripe boundary to the wrong data server.

Last week’s only review was Schumaker’s push-back on patch 01. Coddington had proposed rejecting a stripe_unit that does not fit 32 bits with -EINVAL so the layout is discarded and I/O falls back to the MDS, matching the existing fh_count check. Schumaker asked instead:

"What would it take to update the users of stripe_unit that you mention above to treat it as a u64 instead of a u32? The calls to do_div() could be replaced with div64_u64() for example. It just feels a little more robust to me than artificially limiting ourselves to a 32-bit value."

That question was still open when the week closed.

Patch 01: 32-bit rejection dropped in favor of u64 arithmetic

Coddington answered on 28 August, agreeing that promoting the consumers is the better client fix:

"I agree it would be better that way, storage is already u64. I don't think the division cost is a big deal. I'll make that change for v3."

That is a material rewrite of the first stable fix. ff_layout_alloc_lseg() already decodes stripe_unit as the protocol’s 64-bit value; the truncation lives in the consumers — nfs4_ff_layout_calc_dss_id() divides with do_div() (which casts the divisor) and ff_layout_pg_test() copies the unit into a u32 first. A value that does not fit is silently truncated, so the client stripes on a unit the server did not specify, or divides by zero if the low 32 bits happen to be clear. Rejecting the layout was the conservative path: MDS fallback, no new arithmetic, and the existing stripe_unit == 0 case moved off the -EIO exit that failed I/O instead of falling back.

Schumaker’s alternative keeps the server’s 64-bit stripe unit all the way through DS selection and page coalescing. Coddington’s concession that “storage is already u64” and that div64_u64() is cheap enough means v3 will replace the -EINVAL gate with 64-bit consumers rather than paper over the truncation. That also touches the coalescing helpers in patches 05/23 and (indirectly) 04/23, which already exist to stop treating file offsets as 32-bit quantities on the read path. The rest of the stack — RCU-managed pins, the reresolve_deviceid hook, DELETE recovery, hash-table growth — is unaffected, but the first Cc:stable commit will not land as posted.

Patch 14: ndc_immediate review is comment nits, not a protocol objection

Later the same day Schumaker opened the CHANGE path, starting at PATCH v2 14/23. That patch is the protocol-correctness piece that actually honors ndc_immediate on CB_NOTIFY_DEVICEID CHANGE. RFC 8881 Section 20.12 says an immediate change is enforced at once and the client might not complete pending I/O. Today the client only unhashes the cached device; references pinned inside layout-driver segments keep sending I/O to the old mapping until those layouts are freed. Patch 14, sitting on top of the new in-place re-resolve walker, marks the old node unavailable in addition to unpinning it.

The mark is deliberately leaky. Coddington’s commit message is explicit that it does not recall references already handed out:

"A write whose DS connection is already up keeps using the old node until that I/O errors: nfs4_ff_layout_prepare_ds() returns early on a live ds_clp, and the unavailable flag is only consulted when a connection is being established. What the mark does change is that a read skips the node while another mirror is usable, and that an IOMODE_RW segment still pinning it stops counting as fully available -- so I/O the server rejects falls back to the MDS rather than being retried against a mapping the server has already withdrawn."

The subtle client bug the patch is careful not to introduce is marking a node that already carries the new mapping. A re-resolve that completed between the unhash and the walk reaching the stripe — raced by this walk, or by a later CHANGE for the same deviceid — can install a fresh node that the walk then exchanges out. Ripping that node out is harmless (it is still hashed, so the next I/O re-pins it from the cache), but marking it unavailable would poison the new mapping. Stale nodes are distinguishable by hashed-ness: every superseded node was unhashed before its walk began and is never re-inserted, while a fresh node is inserted before it is installed. The test is hlist_unhashed_lockless(), because the hook runs under the layout inode’s i_lock and rcu_read_lock() but not under nfs4_deviceid_lock, which is what serializes writers of node.pprev. __hlist_del() stores a neighbour’s pprev with WRITE_ONCE(), so removing any other entry in the same bucket can write the field this test reads.

Schumaker’s review did not challenge that race analysis, the RFC reading, or the unavailable-mark semantics. She objected to the comment’s vocabulary and length. On the phrase “Only mark stale vintages”:

"I don't think I've seen "vintage" used when talking about anything other than wine before."

And on the lockless explanation:

"Nit: this comment is pretty wordy. Do we really need to define what "lockless" means here?"

Coddington’s reply treated both as accepted nits. On “vintage”:

"Not even cheese?"

And on the comment:

"I'll trim it up!"

That is the entire technical substance of the patch-14 review this week: the ndc_immediate path, the hashed-ness test, and the decision not to recall in-flight writes are unchallenged. v3 will carry a shorter comment and a less vinous noun.

Status and what is still unreviewed

Two of twenty-three patches have now drawn comments. Patch 01 will be rewritten for v3 as a 64-bit-arithmetic client bug fix rather than a layout-rejection gate. Patch 14 needs only comment cleanup. The rest of the client stack — reference ownership across DS setup, I/O, and layoutstats (07–09); the RCU pin and reresolve_deviceid hook (10–13); the per-nfs_client CHANGE/GETDEVICEINFO race epoch (15); RFC 8881 Section 18.40.4 DELETE recovery, including the v2 fix that stops treating NFS4ERR_OLD_STATEID as confirming a delete of a still-live layout (16–19); the 32-to-256 deviceid hash, the data-server cache re-home, the set-equality keying that closes a one-directional aliasing bug, and the flexfiles dataserver_nconnect cap (20–23) — has not been reviewed.

No tags, no merge, no v3 posting yet. The open item to watch is the v3 rewrite of patch 01 and whatever fallout it has on the coalescing helpers that still copy stripe_unit into a u32. Until that lands, the stable-bound striped-layout fixes and the CHANGE/DELETE feature work remain blocked together in the same series.
