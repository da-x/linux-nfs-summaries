SUNRPC deferred-call copy underflow with RPCSEC_GSS

Summary

This week Chuck Lever posted a v1 security fix for SUNRPC's deferred-request path, a server-side bug that NFS clients using RPCSEC_GSS can trigger when a Call is snapshotted for later replay.

What landed on the list

On 2 September, Chuck Lever posted [PATCH v1] SUNRPC: Copy the deferred RPC Call from the head buffer. There were no replies in-window. The change is a bug fix (with a privilege-escalation flavor), not a protocol change or a new feature. It touches net/sunrpc/svc_xprt.c only: seven insertions, fifteen deletions.

The reporter credit goes to Kimi Security Team and Yilin Zhang. Lever tags it:

"Fixes: 260c1d1298f6 ("svc: Add transport hdr size for defer/revisit")"

That 260c1d1298f6-era backup of a transport header is the historical reason svc_defer() still computes a start address as (rq_arg.len - head[0].iov_len) bytes before head[0].iov_base. Lever notes the premise has been dead since 983084b2672c ("SUNRPC: Remove svc_rqst::rq_xprt_hlen"):

"No transport has had one since commit 983084b2672c … so the two lengths are meant to be equal."

The underflow, and why GSS makes it exploitable

svc_defer() snapshots an RPC Call so the server can replay it after a pending cache upcall. The old copy start is fine when rq_arg.len == head[0].iov_len. An RPCSEC_GSS Call breaks that equality:

  • Integrity unwrap truncates rq_arg.len by the trailing checksum length.
  • Privacy unwrap leaves rq_arg.len short by an amount the client chooses, via trailing bytes after the wrap token.
  • Neither path adjusts head[0].iov_len.

Because both lengths are size_t, the subtraction underflows. The memcpy then starts past head[0].iov_base. Lever's diagnosis is blunt:

"Every deferred integrity Call replays a shifted snapshot."

The security consequence is on the server, but it is driven by what the client put on the wire. A deferred replay skips GSS verification, so the shifted snapshot is treated as an already-authenticated Call. With the privacy service the skip distance is client-chosen:

"A forged Call placed in that window, naming another user's GSS context handle, runs under that identity."

In other words: a malicious NFS client using RPCSEC_GSS privacy can arrange that a deferred replay executes under a victim context. Integrity-protected Calls are "only" shifted (still wrong, still authenticated without a fresh MIC check). Privacy-protected Calls give the attacker a controllable window.

This is not an NFS client-core patch — svc_defer() lives on the server — but it is an important interoperability and security bug for any Linux NFS client that talks RPCSEC_GSS to a Linux nfsd/svcrpc stack. Deferred cache upcalls (typical for auth/idmapping) are the trigger; the client does not have to do anything exotic beyond sending a GSS-wrapped Call that the server later defers.

The proposed fix

Lever's v1 does two things:

  1. Copy from head[0].iov_base, dropping the obsolete transport-header backup.
  2. Refuse to defer a Call whose length runs past the head buffer, so the snapshot cannot read out of bounds.

That second check is the bounds-safety counterpart of the first: once the copy origin is the head iovec, a Call that spills into pages must not be deferred with a naive linear copy.

No ACK, NAK, or v2 appeared before the window closed. The thread is therefore a posted-but-unreviewed security fix as of 3 September. Operators of GSS-authenticated NFS servers should treat the report as high priority even before review lands: the failure mode is "deferred integrity Call always shifted" plus "privacy offset is client-chosen," and replay skips GSS verification.

Client-side takeaway

NFS client developers do not need a matching client patch from this thread. They do need to know:

  • Linux servers still defer GSS Calls through svc_defer(); a shifted snapshot is accepted as authenticated.
  • A client using integrity can hit the underflow on every deferred Call (checksum length mismatch).
  • A client using privacy can choose the underflow, which is the identity-confusion path Lever describes.
  • Until this lands, the practical client-side mitigation is to avoid depending on server-side defer/revisit of GSS-wrapped Calls against unpatched Linux servers — not something a client can reliably control.

Watch for review of the head-buffer-only copy and the "refuse to defer if it does not fit in the head" policy; those are the two behavioral changes NFS client/server pairs will see once the patch is merged.
