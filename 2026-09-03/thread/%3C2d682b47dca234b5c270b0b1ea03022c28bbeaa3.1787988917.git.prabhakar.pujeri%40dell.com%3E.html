Pujeri accepts Layton nits on nfsd client-get dump

Summary

Dell’s Prabhakar Pujeri answered Jeff Layton’s review of v2 patch 1/2 this week, taking every naming and defensive-programming nit and pointing at a v3 reroll. The work remains a new nfsd Generic Netlink admin feature — a privileged dump of connected NFSv4 clients — not a wire-protocol change, not a Linux NFS client patch, and not a runtime I/O bug fix. The existing /proc/fs/nfsd/clients interface is left untouched.

Brief bridge

v2 of “[PATCH 0/2] nfsd: expose NFSv4 client state through Netlink” landed on 31 August (cover, patch 1/2). It dropped last week’s grace-status attribute after Chuck Lever asked that any new ABI not freeze grace as a server-wide boolean. What remains is a compact client-get dump (identity, address, lease remaining, confirmation, reclaim, callback state) plus O(1) per-client session/stateid counters, with client-table churn marked NLM_F_DUMP_INTR.

Layton’s 1 September review called the dump “pretty sane” but objected to nfsd-unfriendly helper names (get/put read as refcounting), a missing defensive check when the dump cursor hits NFSD4_NL_CLIENT_DONE, and a dump loop that increments cb->args[0] through an enum of confirmed then unconfirmed tables.

This week: Pujeri takes the nits, offers a two-phase loop

On 3 September, Pujeri replied point-for-point. The lookup helper is renamed as Layton asked:

"I'd call this nfsd_nl_find_client() as we usually use "get" in terms of reference counting."

"Good point, renamed in v3."

The NFSD4_NL_CLIENT_DONE aliasing bug is closed with an explicit switch rather than a fall-through that treated “done” as “unconfirmed”:

"This means that table == NFSD4_NL_CLIENT_DONE means the same an "UNCONFIRMED". The caller shouldn't call it in that case I guess, but this is a lack of defensive programming."

"Fixed: nfsd_nl_find_client() now selects the table via an explicit switch and returns NULL for any unexpected value."

The address encoder is likewise renamed so “put” no longer looks like a refcount drop:

"In nfsd, we often use "put" with reference counting, so looking at this cold, this is confusingly named. Maybe change this to be named nfsd4_nl_client_marshal_address() ?"

"Renamed as suggested."

The dump iterator is the one item he did not fully rewrite. He documented that args[0..2] track table, bucket, and offset, and that the enum declaration order (confirmed, unconfirmed, done) is the iteration order — then offered the more explicit alternative Layton later insisted on:

"Agreed; the table ordering is now documented where the loop is, and the comment states that args[0..2] track table, bucket, and offset. The enum itself keeps its declaration order (confirmed, unconfirmed, done), so the iteration order is visible at both sites."

"(Alternatively, if you would prefer an explicit two-phase loop over an array of tables rather than relying on enum order, say so and I'll restructure it that way instead.)"

He closed with “Thanks for the review!” The same morning he posted a separate v3 series that encodes those four changes on nfsd-testing at ac579868af0c.

Iterator still open at week’s end

Layton was not satisfied with comments-plus-enum-order. Reviewing v3 1/2 later the same day, he repeated the iterator complaint more sharply:

"Maybe I wasn't clear in my earlier email. cb->args[0] is an enum. Why are you incrementing through it like this? It's weird and it makes it unclear what this code is doing."

"It's also brittle. If someone expands that enum later, it could be problematic."

"Given that there are only two possible tables, there's no reason to make this so clever. Please rework this to be more human-readable."

His preferred shape is exactly the two-phase helper Pujeri had already offered: pull the while body into a function and call it once with NFSD4_NL_CLIENT_CONFIRMED and once with NFSD4_NL_CLIENT_UNCONFIRMED. That rewrite is the remaining review item; patch 2/2 (O(1) session/open/lock/delegation/layout record counts) is still uncommented in this discussion.

NFS client development and bug-fix angle

Nothing here changes the Linux NFS client, the NFSv4 wire protocol, or a client I/O path. The client-visible impact is operational and on the server side of the client/server pair: a privileged Netlink dump that a restart/failover harness — or an operator watching Linux NFSv4 clients against a Linux nfsd — can consume without walking one nfsdfs directory per client.

The dump payload is the data that harness actually needs from each connected client: server-generated client ID, peer address (split into IPv4/IPv6, port, optional IPv6 scope-ID rather than a raw sockaddr), minor version, client and callback states, signed lease time remaining, and RECLAIM_COMPLETE. Patch 2/2 then adds per-client session and stateid record counts so a client that still looks healthy on lease/callback can be spotted as the owner of a large state table.

The only bug-fix-shaped pieces this week are dump robustness, not client correctness:

  • nfsd_nl_find_client() no longer treats NFSD4_NL_CLIENT_DONE as unconfirmed; unexpected table values return NULL.
  • v2 already marked client-table churn with a generation counter and genl_dump_check_consistent() / NLM_F_DUMP_INTR, so a dump that can skip or repeat a client is not silently inconsistent.
  • v2 also replaced unbounded session-list and stateid-IDR walks under cl_lock with maintained u64 counters, so the dump does not stall the per-client lock on a client with a huge stateid table.

Status of this thread: Pujeri accepted Layton’s v2 nits and posted v3. Status of the feature: v3, under review, not merged; the dump iterator still has to become an explicit two-phase walk before Layton will stop calling it “too clever.”
