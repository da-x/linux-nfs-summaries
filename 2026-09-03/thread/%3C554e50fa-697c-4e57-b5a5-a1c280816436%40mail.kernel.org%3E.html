syzbot's svc_addsock EBUSY patch duplicates Lever's nfsd-testing fix

Summary

This is a server-side bug-fix thread, not a protocol change and not an NFS client patch. On 3 September, syzbot posted an AI-generated patch signed off by Slawomir Stepien that refuses to re-attach a socket already claimed by SUNRPC. Twenty minutes later Chuck Lever pointed at a similar three-line check already sitting in nfsd-testing. Stepien dropped the resubmission. There is no NFS client code in the dump, the patch, or the replies.

The takeaway for client readers is the same as in mid-August: the recursion lives in NFSD's /proc/fs/nfsd/portlist injection path and the shared SUNRPC svc_sock setup. Client TCP uses xs_tcp_state_change in xprtsock.c, not svc_tcp_state_change. Ordinary NFSv4 mounts do not hit this. The interesting shared-SUNRPC lesson is that svc_setup_socket() is not idempotent, and sk_user_data is the ownership bit that must fail closed before NFSD overwrites another consumer's socket.

The crash: svc_tcp_state_change calling itself from connect()

syzbot's cover letter (authored as Stepien, "Assisted-by" Gemini, posted through the syzbot-AI pipeline) restates the double-attach story that Chuck Lever diagnosed on 15 August. Writing a socket FD to /proc/fs/nfsd/portlist goes through svc_addsock() → svc_setup_socket(). That helper saves the socket's original callbacks (sk_state_change, sk_data_ready, sk_write_space) into struct svc_sock and replaces them with SUNRPC's. It also plants the new svc_sock in sk->sk_user_data.

A second add of the same descriptor runs svc_setup_socket() again. This time svsk->sk_ostate captures the already replaced svc_tcp_state_change. The next TCP state event — here a connect() that ends in tcp_reset / tcp_done_with_error — has svc_tcp_state_change() invoke svsk->sk_ostate, which is itself. The stack guard page dies:

"When a state change event subsequently occurs on the socket (for example, when connect() is called), svc_tcp_state_change() invokes svsk->sk_ostate, calling itself in an infinite recursion until the kernel stack overflows and triggers a stack guard page fault"

The posted splat is the same class as the 24 August syzbot report (syzbot+c9834a0c0215e6d8697a): RIP in svc_tcp_state_change, hundreds of recursive frames, entered from tcp_rcv_synsent_state_process while __inet_stream_connect waits. That is the non-listen / connecting TCP path, not the listener svc_tcp_listen_data_ready path Jeff Layton asked Lever to name in the August changelog.

The proposed code is three lines in svc_addsock(): if so->sk->sk_user_data is already non-NULL, return -EBUSY and skip svc_setup_socket(). Tags:

  • Fixes: fa9251afc33c ("SUNRPC: Call the default socket callbacks instead of open coding") — the commit that made saved callbacks actually get invoked, which is what turns a double-attach into unbounded recursion.
  • Reported-by: syzbot+c9834a0c0215e6d8697a — the TCP inet_stream_connect overflow, not the earlier UDP svc_write_space one.

Duplicate of the August sk_user_data check, now in nfsd-testing

Chuck Lever did not nack the approach. He simply noted it is already queued:

"A similar fix is already in nfsd-testing: https://git.kernel.org/pub/scm/linux/kernel/git/cel/linux.git/commit/net/sunrpc/svcsock.c?h=nfsd-testing&id=7e8d1b4845aac4ad3c7bcd39032754917f5b966d"

That commit is Lever's 15 August v1, "[PATCH v1] SUNRPC: Reject a socket that already has an svc_sock attached". Same three-line sk_user_data test, same -EBUSY return, same net/sunrpc/svcsock.c. Layton had already Reviewed-by'd it on 17 August. The only material differences versus this week's syzbot patch are the tags:

Both Fixes: tags are defensible. b41b66d63c73 is when NFSD grew the injection surface; fa9251afc33c is when saved callbacks started being called instead of open-coded, which is the recursion primitive. Lever's commit message also made the broader ownership argument that the syzbot letter omits: svc_setup_socket() overwrites sk_user_data unconditionally, so a socket some other consumer had already claimed would be corrupted even if the callbacks did not recurse.

Stepien closed the loop in one sentence:

"Ah ok, a different extid of syzbug that's why I've missed it. Thanks!"

The two syzbot bugs are the UDP and TCP faces of the same non-idempotent svc_setup_socket(). The AI pipeline generated a correct patch against the TCP extid without noticing Lever had already covered both callbacks from the UDP report.

NFS client angle

Despite the [nfs?] heritage of the original syzbot splat, this is not an NFS client I/O or client-transport bug.

  • Overflowing function: svc_tcp_state_change in net/sunrpc/svcsock.c (SUNRPC server sockets).
  • Client TCP state machine: xs_tcp_state_change in net/sunrpc/xprtsock.c. Different callback, different file.
  • Trigger: a raw connect(2) on a socket that already has server callbacks installed via svc_addsock / portlist. Not nfs_file_write, not an RPC client reconnect.

Shared SUNRPC still matters to client developers: lockd and other in-kernel RPC services use the same svc_setup_socket() helper. A recursive sk_state_change can take down whichever thread happens to be in release_sock / tcp_done — here, the connecting task itself. Client test matrices that mix compat connect(2) with nfsctl socket passing would trip it. Ordinary client mounts would not.

Status this week

The discussion is a duplicate bug-fix, closed the same afternoon it opened.

  • Class: kernel stack overflow / unbounded recursion (Oops / DoS) on double svc_addsock.
  • Site: svc_tcp_state_change() entered from tcp_done while connect() waits in SYN-SENT; the UDP sibling overflows in svc_write_space during setup.
  • Fix: refuse a socket that already carries sk_user_data before svc_setup_socket() claims it. Return -EBUSY.
  • Disposition: Lever's August patch is in nfsd-testing as 7e8d1b4845aa. The syzbot/Stepien resubmission is not needed. Stepien agrees.
  • Not an NFS client change. No protocol update. No merge of the AI patch was requested after Chuck's pointer.

What remains off-list, if anything, is tagging the TCP syzbot extid (c9834a0c0215e6d8697a) onto the commit already in nfsd-testing so the dashboard closes both bugs. That did not happen in this thread.
