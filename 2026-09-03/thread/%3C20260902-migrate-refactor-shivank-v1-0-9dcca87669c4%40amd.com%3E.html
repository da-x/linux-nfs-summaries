RFC splits migrate_pages paths and threads policy into migrate_control

Summary

Shivank Garg posted an 11-patch RFC that reworks the core migrate_pages() engine and, as a side effect, changes the filesystem ->migrate_folio() callback that the NFS client implements. The series is a refactor / interface extension, not an NFS protocol change and not a client bug fix: LRU and hugetlb behavior is intended to stay the same, while movable_ops pages get a dedicated pass with a few deliberate differences. The NFS-relevant payoff is that nfs_migrate_folio() would start receiving a const struct migrate_control * instead of a bare enum migrate_mode, so future copy-cache or offload policy can reach the client without another round of aops churn.

Why the core is being split

Garg’s cover letter argues that migrate_pages() currently juggles three page classes whose locking, mapping, and retry rules do not match:

"migrate_pages() handles hugetlb folios, movable_ops pages and LRU folios, although their locking, mapping and retry requirements differ. It already dispatches hugetlb folios to a dedicated engine but movable_ops pages still pass through the regular folio unmap and move machinery."

Policy is the second problem. migrate_mode (blocking discipline) and migrate_reason travel as independent positional arguments, and only the mode reaches address_space_operations->migrate_folio(). Adding another dimension — non-temporal copies, DMA offload, batch size — would mean more arguments, an overloaded mode, or hidden side state.

The proposed new dispatcher is:

migrate_pages(ctl)
  +-- migrate_hugetlbs()
  +-- migrate_movable_ops_pages()
  `-- migrate_lru_folios()
        `-- __migrate_lru_folios()
              +-- async: migrate_folios_batch()
              `-- sync: async pre-pass, then one-at-a-time retry

migrate_pages() would only classify work. Each class owns its lists and retries; the LRU engine also owns batching and the synchronous fallback. Garg credits Zi Yan and David Hildenbrand for shaping the design, and notes he used AI tools to hunt edge cases.

Patch-by-patch: class and phase boundaries

Patches 1–8 stay inside mm/migrate.c and are the mechanical split:

  • 01/11 extracts the unmap retry loop into migrate_folios_unmap(), so unmap, TLB flush, move, and undo become distinct phases.
  • 02/11 moves the move-phase retry bookkeeping into migrate_folios_move() itself, matching the unmap helper’s nr_failed reporting.
  • 03/11 factors large-folio split-on-alloc-failure into migrate_folio_split_on_alloc_fail().
  • 04/11 collects hugetlb folios onto a dedicated list so migrate_hugetlbs() no longer rescans the mixed source list on every retry.
  • 05/11 is the one intentional behavior change: a new migrate_movable_ops_pages() pass runs before LRU migration. Movable_ops pages skip unmap/TLB/copy/LRU handling and talk to the driver callback directly. Garg lists four differences versus today:
    • they are processed before LRU folios rather than in source-list order;
    • synchronous callers use the requested mode from the first attempt (no LRU async pre-pass);
    • a callback -EAGAIN drops the destination so the retry allocates a fresh one;
    • MIGRATE_SYNC_LIGHT waits for the page lock instead of giving up, “because !uptodate check is not applicable for movable_ops pages.”
  • 06/11 renames migrate_pages_batch() to migrate_folios_batch() now that movable_ops is gone from that path.
  • 07/11 and 08/11 hoist async/sync LRU dispatch and NR_MAX_BATCHED_MIGRATION batching into migrate_lru_folios() / __migrate_lru_folios(), leaving migrate_pages() as a class dispatcher.

The movable_ops split is also preparatory: those pages are expected to lose their folio representation (memdescs). Isolating them now keeps folio/folio->lru assumptions out of that path.

Policy: struct migrate_control

09/11 introduces caller-owned, stack-allocated, const struct migrate_control in include/linux/migrate_mode.h. Internal helpers take the struct instead of separate mode/reason. Async pre-passes and split-folio retries get a derived control (copy, then override mode) so extra policy fields survive. Public aops are left alone in this patch.

10/11 pushes that into the migrate_pages() prototype. Compaction, DAMON, GUP, memory-failure, hotplug, mempolicy, page_alloc, and vmscan all construct a stack migrate_control. Async derivatives still copy the caller’s control and only flip the mode.

11/11 is the NFS-facing change. migrate_folio(), the common helpers, and address_space_operations->migrate_folio take const struct migrate_control *. Documentation (locking.rst, vfs.rst) and every in-tree implementation are updated, including:

  • fs/nfs/internal.h
  • fs/nfs/write.c (nfs_migrate_folio())

Garg is explicit that no NFS behavior change is intended yet:

"Existing callbacks continue to make their decisions from ctl->mode only, none changes behavior yet."

That is the client-development story this week: a mechanical aops signature change so nfs_migrate_folio() can later inspect more than blocking mode (for example a cache hint) without another filesystem-wide API break. The cover letter frames that as one-time caller pain:

"This is one-time pain of updating callers, but doing it once avoids repeating that churn whenever a new use case or optimization need additional policy."

Follow-on sketches (not in this series) show a demotion caller setting ctl.cache_hint = MIGRATE_COPY_NT beside existing MR_DEMOTION / MIGRATE_ASYNC, and a later batch-copy/offload series stuffing copy-engine preference into the same struct.

Review this week

Jan Kara reviewed 11/11 the same morning and signed off the filesystem interface:

"The changes to FS interface look good to me. Feel free to add: Reviewed-by: Jan Kara jack@suse.cz"

That is the only external review so far. No NFS maintainer comment landed in-window.

Separately, an automated review (“Sashiko”) on 09/11 found a real uninitialized-stack bug in __migrate_lru_folios(): if ctl->mode == MIGRATE_ASYNC, an early goto out skips async_ctl initialization; a subsequent split-folio retry can then call migrate_folios_batch() with garbage policy — potentially treating an async migration as MIGRATE_SYNC and sleeping. Garg acknowledged it immediately:

"Yes, this is valid issue. I should initialize async_ctl early before it make goto jump."

He posted a five-line fix moving the async_ctl init ahead of the goto. That is the only concrete bug called out this week, and it is in the new LRU engine, not in NFS.

Status

The thread opened and closed on 2026-09-02: the RFC, Kara’s FS Reviewed-by, and Garg’s agreement on the async_ctl init bug. Nothing is merged; no v2 yet. For NFS client readers the actionable piece is 11/11’s nfs_migrate_folio() prototype change — still mode-only in behavior, but the hook that future migration policy will use — plus Kara’s blessing of that VFS/aops shape. The uninitialized async_ctl issue needs to be in the next revision before the LRU path is trustworthy under async split-folio retries.
