Client timeout patch waits on NFS maintainers

Summary

Overview

This week’s traffic is a process ping, not a new feature, protocol change, or bug fix. Eleven days after Petr Vorel’s Reviewed-by on Manjunath Patil’s SUNRPC timeout-diagnostics patch, the patch still has no NFS client maintainer Ack, and Patil came back asking what to do next. Chuck Lever answered the Patchwork confusion and pointed the review request at the client tree.

The underlying change remains the one posted on 19 August: extra fields on the ratelimited RPC timeout printk in rpc_check_timeout() so operators can tell a server stall from a disconnected or replaced transport. No v2 landed this week.

Brief prior context

Last week Patil posted a one-file client-side observability patch for net/sunrpc/clnt.c. Existing “not responding, timed out” lines named only the RPC program and server; the patch adds client id (clid), transport id (xprt), connection cookie (cc), and task owner so the line can be matched against rpcctl. Vorel called it a “Nice improvement” and tagged Reviewed-by. A nit about hoisting req/xprt earlier was declined because a signalled task must still return before task->tk_rqstp is dereferenced; Vorel accepted that. Maintainers (Trond, Anna, Jeff) had not queued it.

The ping

On 31 August Patil asked Trond Myklebust, Anna Schumaker, and Chuck Lever for a status call:

"Could you please let me know the next steps for this patch submission? Should I wait longer for review, or are there any formatting or submission issues that I need to fix?"

He also flagged Patchwork event Not Applicable for patch 14757794 and asked what that meant for the submission. There is no new diff, no changelog, and no technical argument in the mail — it is a follow-up on a reviewed-but-unmerged client patch.

Patchwork is the NFSD queue

Chuck Lever answered the Patchwork question the same evening and did not treat it as a submission defect:

"The kernel patchwork service applies only to NFSD. Your patch is for the Linux NFS client, so it’s “Not Applicable” to NFSD. The NFS client maintainers need to respond to your review request."

That is the only technical-process conclusion this week. “Not Applicable” is expected for SUNRPC/NFS client work: kernel.org Patchwork here tracks the server tree. The client maintainers (typically Trond and Anna) are the ones who need to Ack or queue the change. Lever did not Ack it himself, did not request a respin, and did not comment on the late tk_rqstp dereference that Vorel already signed off.

Where the client work stands

For NFS client debugging the patch is still the same small observability win: a soft-mount timeout that used to say only “server X not responding” would print clid / xprt / cc / owner, which is how you tell a hung server from a transport that reconnected underneath the task. Timeout policy, reconnect, and rebind are untouched.

This week did not advance that code. Vorel’s review still stands; the pointer-ordering rationale still stands; there is still no client-maintainer Ack. The actionable takeaway from Lever is purely routing: ignore the NFSD Patchwork state and wait on the Linux NFS client maintainers.

Takeaway

A diagnostics patch for the SUNRPC client timeout path remains reviewed and unmerged. The only new information is that Patchwork Not Applicable is the expected NFSD-queue result for client code, not a formatting reject. Until Trond or Anna respond, the printk still lacks transport identity on timeout.
