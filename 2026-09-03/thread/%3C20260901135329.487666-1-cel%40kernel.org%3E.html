Lever’s v2 splice helper collects VFS acks for the NFSD duplicate ACCESS bug

Summary

This week’s thread is a bug-fix respin, not a protocol change and not NFS client code. Chuck Lever posted v2 of the VFS splice wrapper that stops NFSD iterator READs from firing two fsnotify_access() events. Jan Kara and Christoph Hellwig both Reviewed-by the same day and the next. Combined with Amir Goldstein’s Reviewed-by carried from v1, the public API nits that blocked last week’s patch are gone.

The client-visible symptom is unchanged until this lands: an inotify/fanotify watch on an exported file still sees a READ twice when NFSD takes the iterator path (sec=krb5i / sec=krb5p, splice disabled, NFSD_IO_DONTCACHE / NFSD_IO_DIRECT) and once when it splices.

Brief recap from prior weeks

Ameer Hamza originally tried to fix the double ACCESS event inside NFSD by moving fsnotify_access() into nfsd_splice_read(). VFS maintainers rejected that as an nfsd workaround of a hole in the splice helpers: vfs_iocb_iter_read() already emits the event, splice_direct_to_actor() does not, and nfsd_finish_read() then emits a second one on both paths. The agreed layering was a VFS wrapper around splice_direct_to_actor() that runs rw_verify_area() and a single fsnotify_access() outside freeze protection, with NFSD as a caller rather than a special-case emitter.

Lever’s v1 last week did exactly that, as vfs_splice_direct_to_actor(). Goldstein acked it on the spot. Hellwig did not dispute the fsnotify placement, but he wanted the historically confusing “direct” terminology retired from the new public name and, preferably, the weird splice_desc contract hidden inside the helper:

"Can we use this to start retiring the really weird direct terminology here that is confusing? I.e. name this vfs_splice_to_actor?"

He also floated building the descriptor inside the helper and taking pos, count, actor, and private instead of making every caller fill in sd. That was the open item at the end of last week.

v2: Hellwig’s API, Goldstein’s layering, one ACCESS per NFSD READ

Lever’s v2 is still a three-file change (fs/nfsd/vfs.c, fs/splice.c, include/linux/splice.h) and restates the same double-count:

"nfsd_finish_read() calls fsnotify_access() on both NFSD read paths, because splice_direct_to_actor() does not emit the event itself. The iterator path reaches nfsd_finish_read() from vfs_iocb_iter_read(), which has already emitted one. A READ served without splice therefore emits two access events."

And the GSS-specific reason it shows up in the field:

"NFSD does not use splice for the GSS integrity and privacy services, so a READ on a sec=krb5i or sec=krb5p mount takes the iterator. An inotify watch on that file sees the READ twice."

The changelog is a direct answer to Hellwig:

"Changes in v2:

  • Rename the new helper to vfs_splice_to_actor()
  • Take pos, count, and actor data, not a splice_desc"

That is the deeper of the two options Hellwig offered last week, not just the rename. The new public helper is vfs_splice_to_actor(in, pos, count, actor, private): it builds the splice_desc internally, runs rw_verify_area(), calls the existing splice_direct_to_actor(), and emits fsnotify_access() once for the whole READ. NFSD’s splice READ helper switches to that wrapper, and nfsd_finish_read() stops calling fsnotify_access(), so the iterator path (already covered by vfs_iocb_iter_read()) no longer double-fires.

Credits are unchanged from v1: Reported-by Hamza, Suggested-by Goldstein, Reviewed-by Goldstein (carried forward), Closes Hamza’s original 1/2 thread.

This is the important server-side accounting fix. Both NFSD READ flavors now produce one ACCESS event, and the event is generated by the VFS API rather than by nfsd special-casing. There is still no NFS client code in the patch. The people who notice it are watchers of exported files, especially on krb5i/krb5p mounts that cannot splice.

Kara and Hellwig: Reviewed-by, no further nits

Jan Kara replied within an hour:

"Looks good. Feel free to add:

Reviewed-by: Jan Kara jack@suse.cz"

That is the fsnotify/VFS maintainer who Lever originally pinged when Hamza’s nfsd-only patch stalled. He did not ask for more API churn.

Christoph Hellwig followed the next morning with the same verdict on the surface he requested:

"Looks good:

Reviewed-by: Christoph Hellwig hch@lst.de"

He did not reopen the splice_desc debate, the “direct” naming, or the fsnotify placement. Last week’s review was a request for a v2 of the VFS surface; this week’s is an ack of that surface.

Where things stand

  • Kind of change: bug fix in VFS splice plus a small NFSD call-site update. No NFS protocol change. No NFS client code.
  • The double ACCESS event is still unfixed in-tree this week, but the patch now has Reviewed-by from Goldstein (v1, carried), Kara, and Hellwig. There were no remaining nits in-window.
  • NFSD remains a consumer, not the emitter. That was the point of the VFS ruling two weeks ago, and v2 still follows it.
  • Hamza’s original nfsd-only 1/2 stays superseded. The atime half of that series remains withdrawn; nothing this week revived file_accessed() in NFSD.
  • Why it still matters to NFS: GSS integrity/privacy READs, and any other iterator-READ work (including Hamza’s SUNRPC reply-page recycling series), inherit the duplicate inotify ACCESS until this wrapper is merged. Watchers of exported files are the users who see it.

Until it hits a tree, the splice and iterator READ helpers remain inconsistent. After it lands, the “one ACCESS per user READ” contract Goldstein asked for is the VFS contract, not an nfsd quirk.
