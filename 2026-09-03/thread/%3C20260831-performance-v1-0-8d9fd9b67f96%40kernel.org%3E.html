RFC: NFS client lock-contention cuts for RDMA

Summary

On 31 August, Chuck Lever posted an eight-patch RFC that attacks lock contention in the Linux NFS client under a 4KB NFSv3 workload on 100GbE RDMA. This is not a protocol change. It is a performance series: three independent SUNRPC hot-path lock splits plus a workqueue affinity override on rpciod, nfsiod, and xprtiod. No one replied in this thread. Two days later Lever superseded the series with RFC v2, dropping the most aggressive scheduler change after it reopened a known pNFS deadlock.

The cover letter frames the problem in CPU-profile terms, not IOPS:

"Under a 4KB NFSv3 workload on 100GbE RDMA, roughly 150 RPC worker threads drive the client, and lock contention dominates its CPU profile: up to 53% of non-idle cycles are spent in native_queued_spin_lock_slowpath."

The test harness is transport-limited, so the cycles that come back do not raise IOPS. They show up as tighter submission latency and a lower tail:

"My test harness is transport-limited, so the freed cycles appear as reduced submission latency variance and lower tail completion latency rather than higher IOPS."

Prior context (brief)

An earlier RFC tried to fix this in the workqueue core by falling back to a finer affinity scope when an unbound queue collapsed to a single pod. Tejun Heo rejected a finer global default for unbound workqueues and offered two alternatives: a sharded scope between CACHE and SMT, and a per-workqueue scope change on the NFS queues themselves. The first became WQ_AFFN_CACHE_SHARD. Lever’s cover letter explains why that is still not enough on the machines he cares about:

"The first became the WQ_AFFN_CACHE_SHARD default, whose 8-core shards still leave a 12-core single-LLC system with only two pools. This series does the second."

Patches 6–8 are tagged Suggested-by: Tejun Heo.

What kind of change this is

  • Not a protocol change. Wire formats, XID semantics, and NFS versions are untouched.
  • Not a classic correctness bug fix, except that v2 later identified a use-after-free in the queue_lock split and a pNFS deadlock in the async-inline patch.
  • Client performance work in net/sunrpc/ and fs/nfs/, plus a small kernel/workqueue.c export so sunrpc/nfs can retune unbound queues without a module reload.

The three contended locks named in the later v2 cover — reserve_lock on every XID allocation, queue_lock on every submit and completion, and the unbound worker pool lock on every rpciod/nfsiod/xprtiod enqueue and dequeue — are exactly the three axes of this v1 series.

Patch 1: take XID allocation off reserve_lock

PATCH 1/8 replaces the reserve_lock-protected XID counter with atomic_t. xprt_alloc_xid() currently grabs reserve_lock just to increment a counter. Under the same 100GbE RDMA NFSv3 load, that lock is 1.06% of system-wide CPU in xprt_request_init as ~150 RPC workers serialize on it.

Lever’s invariant is that XID allocation does not need the slot table or the backlog:

"reserve_lock protects the slot table and backlog queue, but XID allocation is an independent operation that does not require synchronization with either."

This is the cheapest win in the series: a counter that never needed the lock it was sitting behind.

Patch 2: run the first async FSM states in the caller (later withdrawn)

PATCH 2/8 is the most aggressive SUNRPC scheduler change, and the one v2 dropped. Today every async RPC is bounced onto rpciod before its first FSM state runs, even though call_start through call_allocate typically complete without blocking. That is one enqueue, one dequeue, and one context switch per RPC, and it feeds the rpciod pool lock.

The proposed fix is to have rpc_execute() call __rpc_execute() directly for async tasks too. Initial states run in the submitter; __rpc_execute() returns to the caller when the task first sleeps; later wake-ups still go through rpc_make_runnable() onto rpciod.

Lever argues this does not undo commit d6a1ed08c6ac ("SUNRPC: Reduce asynchronous RPC task stack usage"), which moved async dispatch onto rpciod to bound caller stack depth:

"Inline execution preserves that bound because __rpc_execute() still runs each state from the same stack frame."

v2’s cover letter is the post-mortem. Running the first states in the submitter also lets completion callbacks run there. A pNFS read resent from rpc_release then waits for a layout segment its submitter still holds — the deadlock commit 54e4a0dfa25d ("pNFS: Fix a deadlock between read resends and layoutreturn") already fixed. v2 therefore leaves the rpciod hop in place. That is an important client-development conclusion from this RFC even though the objection never landed as a reply on v1: do not inline async RPC startup. The workqueue hop is load-bearing for pNFS.

Patch 3: split recv_lock out of xprt->queue_lock

PATCH 3/8 is the lock that accounts for the 53% figure. xprt->queue_lock currently protects two independent structures: the recv_queue rb-tree used for reply matching, and the xmit_queue list used for transmit draining. No hot path touches both in one critical section, but every RPC submit and every completion contends on the same lock. The RDMA completion worker running rpcrdma_reply_handler serializes against ~150 kworkers enqueuing receives and transmits.

The split is surgical:

"Introduce xprt->recv_lock for the receive path -- recv_queue operations, request lookup, receive-side pinning, and completion -- leaving queue_lock to the xmit_queue and the xprt_transmit drain loop."

A second, smaller shrink: move the rq_private_buf memcpy in xprt_request_enqueue_receive above the lock. Until the rb-tree insert publishes the request, the reply handler cannot see it, so the copy is safe unlocked and the submitter’s critical section collapses to the insert alone.

This is the core NFS-client bug-adjacent fix in the series: a lock that was protecting two unrelated queues on the hottest path in the RDMA client. v2 kept the split and added a send-bvec use-after-free fix in xprt_request_dequeue_xprt() (credited to sashiko), which is why this patch should not be cherry-picked from v1 as-is.

Patches 4–5: expose NFS workqueues and export workqueue attribute helpers

PATCH 4/8 sets WQ_SYSFS on the key NFS-related workqueues so affinity scope can be tuned under /sys/devices/virtual/workqueue/ without reloading modules.

PATCH 5/8 exports the workqueue allocation, apply, and teardown helpers so modules such as sunrpc can change affinity scope at run time. v2 replaced this three-function export with a single workqueue_set_affn_scope() helper after Tejun Heo engaged on that API; v1 never received that review in-thread.

v2 also records a remaining race that v1 leaves open: the scope change is applied after alloc_workqueue() has registered the queue in sysfs, so an administrator write that lands in between is overwritten. Closing that window needs workqueue_sysfs_register() exported and WQ_SYSFS dropped from the alloc calls. This series does not close it.

Patches 6–8: WQ_AFFN_SMT on rpciod, nfsiod, and xprtiod

These three patches are the payload Tejun suggested: override affinity scope on the NFS workqueues rather than changing the unbound default.

PATCH 6/8 sets WQ_AFFN_SMT on rpciod. On a 12-core system, 30–40% of cycles are lost to native_queued_spin_lock_slowpath in the rpciod pool at WQ_AFFN_CACHE (one pool per LLC). WQ_AFFN_CACHE_SHARD barely helps: its 8-core shards split that machine into two pools of six. Lever’s justification for a per-queue override, rather than another global default fight, is explicit:

"Most UNBOUND workqueues never contend on the pool lock and profit from a coarser scope's cache locality. rpciod's sustained completion traffic makes the lock a first-order bottleneck, so the override belongs on this workqueue rather than in the system-wide default. Idle kworkers are culled, so the extra pools cost little on large systems."

PATCH 7/8 does the same for nfsiod. On a single-socket system whose LLC fits in one CACHE_SHARD, every NFS I/O completion serializes on one nfsiod pool lock. Profiling 4KB random writes over NFSv3/RDMA with nconnect=3 shows that lock at 17% of CPU: 8% dequeuing work, 9% enqueuing follow-on work from rpciod and nfsiod workers. WQ_AFFN_SMT gives each CPU its own pool, so queue_work_on() no longer takes a lock on another CPU. Enqueue contention disappears; dequeue contention drops to 1.4%. Throughput is unchanged (transport-limited), but the latency numbers are the client-visible result:

"the freed cycles cut submission latency variance by 67% (slat stdev 31.6 us to 10.5 us), IOPS stdev by 31%, and p99.9 completion latency by 11%."

PATCH 8/8 applies the same WQ_AFFN_SMT override to xprtiod, which handles socket receive processing, error recovery, and connection lifecycle and contends on the unbound pool lock the same way rpciod does.

v2 kept all three overrides, split the WQ_SYSFS change into separate SUNRPC and NFS patches, and corrected the pool-cost and SMT-group wording.

Evolution and conclusions

This v1 thread is a drive-by RFC: eight patches, zero replies, then a v2 two days later. The technical argument is entirely in Lever’s commit messages, and it is aimed squarely at NFS client development:

  1. XID allocation does not belong under reserve_lock. Make it atomic_t. Cheap, independent, 1% of CPU.
  2. queue_lock is doing two jobs. Split recv_lock for the reply rb-tree; leave queue_lock for transmit drain. This is the 53% lock. Do not take v1 as-is — v2 fixes a send-bvec use-after-free in xprt_request_dequeue_xprt().
  3. Do not inline the first async RPC states. v1 proposed it to skip a rpciod hop; v2 withdrew it because completion callbacks in the submitter re-create the pNFS read-resend vs. layoutreturn deadlock of 54e4a0dfa25d.
  4. Workqueue pool locks are a first-order NFS client bottleneck on high-IOPS RDMA, and WQ_AFFN_CACHE_SHARD is too coarse on single-LLC 12-core boxes. Override rpciod, nfsiod, and xprtiod to WQ_AFFN_SMT rather than fighting for a finer global default. That is Tejun’s suggested path, and it is the one this series takes.
  5. Expect latency, not IOPS. On a transport-limited 100GbE RDMA client the win is submission-latency variance (−67%), IOPS stdev (−31%), and p99.9 completion latency (−11%).

No Reviewed-by, no nits, and no merge conclusion in this thread. Treat v1 as the problem statement and the lock-split design; treat v2 as the series that actually has a chance to land, minus the async-inline patch and with a narrower workqueue API.
