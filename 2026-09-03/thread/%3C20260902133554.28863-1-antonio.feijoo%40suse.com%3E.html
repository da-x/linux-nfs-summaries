Flexfiles NFS root hang: softdep on nfsv3

Summary

Antonio Alvarez Feijoo posted a one-line NFS client bug-fix for the pNFS FlexFiles layout driver: nfs_layout_flexfiles now declares MODULE_SOFTDEP("pre: nfsv3") so the NFSv3 client is pulled in when the layout module is loaded, instead of being discovered on the first data-server I/O. The change targets an unbootable NFSv4 root against a Linux knfsd with FlexFiles enabled. There were no replies in-window; the patch is unreviewed as of this week.

This is not a protocol change and not a new feature. It is a client-side module-loading fix for a deadlock that became fatal once FlexFiles stopped falling back to the metadata server.

The hang

An NFS root mounted over NFSv4 against a Linux NFS server wedges during boot: either it never leaves the switch-root execve(), or a loaded machine spins until the softlockup watchdog fires. Feijoo traces it to the FlexFiles path into nfs4_pnfs_ds_connect() on the first I/O through a layout segment. For an NFSv3 data server that call does symbol_request(nfs3_set_ds_client), which becomes request_module("symbol:nfs3_set_ds_client") when nfsv3 is not already resident. request_module() execs /sbin/modprobe via the usermode helper. On an NFS root, that binary — and libkmod, and the libraries behind it — must be read from the very filesystem whose I/O is blocked waiting for the DS connection:

"the helper cannot make progress, so neither can the mount."

On a system whose init is on NFS, the first such I/O is typically the execve() of init itself, immediately after pivot_root(), at which point the initramfs — and the only reachable copy of modprobe — is gone. Feijoo includes a warning from fs/nfs/pnfs_nfs.c:792 in nfs4_pnfs_ds_connect(), with CPU#0: systemd/1 and a call chain through nfs4_ff_layout_prepare_ds → ff_layout_choose_ds_for_read → ff_layout_pg_init_read → nfs_readahead → bprm_execve. The linked-modules list has nfs_layout_flexfiles and nfsv4 but, as he notes, no nfsv3.

Why it stayed latent, and why it is fatal now

The bug has been latent since the FlexFiles driver was added (d67ae825a59d, "pnfs/flexfiles: Add the FlexFile Layout Driver"). A fatal DS connect error used to be absorbed: ff_layout_read_pagelist() returned PNFS_NOT_ATTEMPTED and pnfs_do_read() reissued the I/O through pnfs_read_through_mds(). The read completed over plain NFSv4 against the metadata server, so nobody noticed that the layout had been abandoned.

Commit 7a375cafc14e ("NFSv4/flexfiles: honor FF_FLAGS_NO_IO_THRU_MDS on fatal DS connect errors") removed that fallback for layouts carrying FF_FLAGS_NO_IO_THRU_MDS. Feijoo agrees that was the right protocol behavior:

"correctly, since silently contradicting the flag was a bug."

The catch is that knfsd sets that flag on every FlexFiles layout it hands out (fs/nfsd/flexfilelayout.c: FF_FLAGS_NO_LAYOUTCOMMIT | FF_FLAGS_NO_IO_THRU_MDS | FF_FLAGS_NO_READ_IO, unconditionally). Against a Linux server, the no-fallback path is therefore not the appliance corner case that commit described — it is every layout. With no MDS fallback left, a DS connect that cannot complete is now fatal to the boot.

FF_FLAGS_NO_READ_IO does not rescue the read either. The client only diverts reads off IOMODE_RW segments; a read-only NFS root is served IOMODE_READ segments, where that flag does not apply.

The client fix

The proposed change is a softdep, not a runtime request_module() from I/O context. The layout driver is itself loaded by request_module("nfs-layouttype4-4") from find_pnfs_driver() during mount(), which on an initramfs boot happens while the initramfs and a working /sbin/modprobe are still in place. Resolving MODULE_SOFTDEP("pre: nfsv3") at that point is when the usermode helper can actually run.

The acknowledged cost is over-pulling:

"This pulls in nfsv3 whenever the flexfiles driver is loaded, including for layouts whose data servers all speak NFSv4.1 and which would never have needed it. That seemed the better trade against an unbootable system."

The patch is a two-line edit of fs/nfs/flexfilelayout/flexfilelayout.c (one insertion, one deletion). It is tagged Fixes: d67ae825a59d (the original FlexFiles driver, not the later no-fallback commit) and Cc: stable@vger.kernel.org.

Reproduction and workaround

Reported on openSUSE Tumbleweed with kernel 7.2.2 under QEMU, and reproducible with dracut's TEST-60-NFS suite against any knfsd built with CONFIG_NFSD_FLEXFILELAYOUT=y. Booting with rd.driver.pre=nfsv3, which loads the module from the initramfs before the pivot, is a complete workaround and confirms the diagnosis.

Conclusions

  • Type of change: NFS client bug fix in the FlexFiles layout driver (nfs_layout_flexfiles). Not a protocol change, not a new pNFS feature, not an NFSD patch.
  • Root cause: first FlexFiles DS I/O does symbol_request(nfs3_set_ds_client) → request_module(), which on an NFSv4 root after pivot_root() tries to exec /sbin/modprobe from the filesystem that is blocked waiting for that same DS connect.
  • Why it is a regression now: 7a375cafc14e correctly stopped MDS fallback on FF_FLAGS_NO_IO_THRU_MDS, but knfsd sets that flag on every FlexFiles layout, so a failed DS connect is fatal to boot rather than silently falling back to NFSv4 MDS I/O.
  • Proposed fix: MODULE_SOFTDEP("pre: nfsv3") so nfsv3 is loaded when the layout driver is requested at mount time, while the initramfs still has a working modprobe.
  • Trade-off accepted by the author: nfsv3 is pulled in even for NFSv4.1-only data servers, in preference to an unbootable system.
  • Workaround: rd.driver.pre=nfsv3.
  • Status this week: single patch, no Reviewed-by / Acked-by, no maintainer comment. Watch for review of the softdep approach versus a narrower load of nfsv3 only when the DS actually speaks v3.
