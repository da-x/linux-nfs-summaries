v2 implied-ACK DRC eviction draws Layton review over NFSv3 reconnect races

Summary

Summary

This is a server-side performance feature, not an NFS client patch and not a protocol change. Two days after posting v1 with no review, Chuck Lever respun implied-ACK eviction for NFSD’s duplicate reply cache as a seven-patch v2. The only listed delta from v1 is cosmetic: print the DRC eviction tracepoints’ age field as unsigned. The technical design is unchanged from last week’s posting: on TCP and RDMA, arrival of a later request on the same svc_xprt is treated as evidence that earlier replies were delivered, so completed DRC entries can be dropped immediately instead of sitting until the 120-second RC_EXPIRE timeout.

This week the series finally got review. Jeff Layton nitted the plumbing, then challenged the central claim that “the cache is advisory.” The resulting exchange is the first real debate over whether implied-ACK eviction can drop a non-idempotent NFSv3 reply just before a reconnecting client retransmits it. No Acked-by landed, and Lever did not post a v3 in this window.

There is no Linux NFS client code in the series. Client-visible impact is entirely through the server’s DRC: shorter-lived entries on the NFSv3 lookup hot path, and a narrower window in which a reconnecting client can still hit a cached non-idempotent reply.

The v2 series, briefly

The cover letter repeats the v1 motivation and the same perf numbers from an NFSv3/RDMA 4KB random-write workload:

"nfsd_cache_lookup overhead dropped from 1.53% to 0.76% of CPU cycles. The rb-tree operations (rb_erase, rb_insert_color) that dominated LLC cache misses fell from a combined 13.2% to 1.1% of all LLC-load-misses, because shorter-lived entries keep the per-bucket trees small."

The seven patches are the same scaffolding as v1:

  • PATCH v2 1/7 — per-netns cyclic IDR identifier on each svc_xprt, so DRC entries can name a transport without holding a reference and without ABA collisions when SLUB reuses the address. svc_xprt_init() now returns a boolean; callers unwind on allocation failure.
  • PATCH v2 2/7 — record that xprt id in each DRC entry. No behavior change.
  • PATCH v2 3/7 — xpt_last_recv on svc_xprt, updated after each successful xpo_recvfrom(). Deferred requests leave the stamp alone.
  • PATCH v2 4/7 — XPT_ORDERED on TCP and RDMA, left clear for UDP, so implied-ACK eviction is confined to transports where in-order delivery holds.
  • PATCH v2 5/7 — the eviction policy itself. During nfsd_prune_bucket_locked(), compare each RC_DONE entry’s c_timestamp against xpt_last_recv on the transport the current request arrived on. Bound the walk to four times the eviction limit, because implied ACK no longer evicts in age order and an unbounded XID-hash scan would hold cache_lock over a packed bucket.
  • PATCH v2 6/7 — tracepoints for each eviction reason (pressure, expiry, implied ACK).
  • PATCH v2 7/7 — entries= on nfsd_drc_found, passed as an explicit argument so a later per-connection lookup path can supply its own depth without changing the tracepoint format.

RFC 1813 §4.5 is again the protocol reading: on a live connection-oriented transport, a duplicate request comes from reconnection, not from inside an established stream. UDP is excluded because a UDP svc_xprt is shared by every peer and carries timeout retransmits. Patch 4 still flags the svcrdma cost: handle_connect_req() zeroes the remote port in the DRC key so a cached reply survives a reconnect, and implied-ACK eviction can retire that entry while the original connection is still up. Lever treats that as consistent with TCP rebinding a reserved port.

Layton’s nits on the plumbing

Review arrived the same afternoon. On patch 4, Layton asked for the XPT_ORDERED consumer to be visible in the same commit:

"It would be helpful to see how this new flag will be used other than in the tracepoint. Maybe this patch should be folded into the following one?"

On patch 1, he questioned a local-variable hoist in the socket setup path (int err moved to the outer scope). Neither nit was answered in this window.

The real argument: is the DRC advisory?

The substantive fight is over patch 5. Lever’s commit message still says the cache is advisory and that a premature eviction “costs a miss and re-execution, the same outcome memory pressure and RC_EXPIRE already produce.” Layton rejected that framing outright:

"No, it's not. The DRC is necessary for proper function, and if we drop non-idempotent requests prematurely, then that could cause spurious errors."

He added that the basic approach and code looked OK “modulo some nits,” and asked whether BSD already takes this approach — a question Lever did not answer here.

Lever’s reply drew a hard line between the old NFSv2/v3 DRC and the NFSv4.1 session cache:

"Not talking about the NFSv4.1 session cache. The old DRC has always been best-effort. It cannot be relied upon for proper function, since the DRC is non-deterministic."

His performance argument is that actively dropping entries that are very unlikely to be hit reduces the chance that more valuable entries get pushed out by the size cap or the shrinker. That is the inverse of Layton’s concern: Lever wants a hotter, smaller cache; Layton wants the cache to still be there when a non-idempotent replay arrives.

The RENAME-then-reconnect race

Layton then spelled out the client-visible failure he is worried about, in a follow-up:

"- client does a v3 RENAME (anything non-idempotent, really)

  • reply to the RENAME goes out just before a new call comes in (WRITE or something maybe). The RENAME DRC entry's timestamp is a few jiffies earlier so we evict it.
  • connection drops before client gets the reply and client reconnects and retransmits the v3 RENAME

...hilarity ensues? Maybe this sort of bad luck never happens in practice, but I don't see what would prevent it."

That is exactly the pipelined-client case the series already admits is not conclusive evidence: a client with several requests outstanding sends the next one without waiting for the previous reply, so xpt_last_recv can move forward while the earlier reply is still in flight. Implied ACK then treats the in-flight RENAME as delivered and drops it. If the connection dies before the client sees the reply, the retransmit hits a miss and the server re-executes a non-idempotent op.

Layton also noted that the traditional prune path evicts oldest-first and is sized to outlast typical retransmission windows:

"Sure, but usually we evict the oldest stuff first, and we generally keep a big enough cache to get past the point where retransmissions occur. This patchset changes that and will evict things earlier.

Maybe that's OK in practice."

Lever’s closing note did not deny the race. He argued it is already possible under load, and that modern hardware makes DRC overrun more likely, not less:

"The same thing can happen if NFSD is handling a thousand chatty clients. With fast networks and fast storage, overrunning the DRC is more likely than it ever has been."

He said he has more patches that “moderate this behavior some,” but held them back to keep the series narrow. On the reconnect case specifically:

"The reconnect case is the only one I'm really concerned about. I'm not brushing aside your concern, but missing a non-idempotent reply during a reconnect storm is somewhat rare, and is already not 100% deterministic.

And we have NFSv4.1 now. For anyone who is deeply concerned about this race, NFSv4.1 is the only total answer."

That last sentence is the policy conclusion of the thread: implied-ACK eviction is a heuristic for the old DRC, not a correctness fix, and anyone who needs deterministic replay of non-idempotent ops should be on sessions.

Client impact, and what this is not

This series does not touch the Linux NFS client. Client-side DRC, NFSv4.1 session slots, retransmission timers, and nconnect are out of scope. The client-visible effect, if any, is on the server’s ability to absorb a replay of a non-idempotent NFSv3 RPC after the next request on the same TCP/RDMA connection has already arrived.

That is also why the thread matters to NFS client development even though no client patch is here. NFSv3/TCP and NFSv3/RDMA write-heavy clients are the workload Lever profiled; they spend less server CPU in nfsd_cache_lookup if the DRC trees stay small. The same clients are the ones exposed to Layton’s RENAME/reconnect race: a Linux NFSv3 client that pipelines a non-idempotent call with a later WRITE, then loses the connection before the first reply lands, can now miss the DRC and re-execute. UDP clients keep the 120-second hold. NFSv4.1 clients are unaffected because they do not use this DRC.

It is not a protocol change. RFC 1813 §4.5 is used as justification for a local eviction heuristic. It is not a bug fix either, though patch 5’s four-times-eviction-limit bound is hardening against a lock-held linear scan of a packed XID bucket.

Where things stand

  • Kind of change: NFSD/SUNRPC performance feature (implied-ACK DRC eviction) with supporting xprt identity and tracing. Not a bug fix, not a protocol change, not NFS client code.
  • v2 vs v1: only the unsigned age field in the eviction tracepoints. Design and numbers are unchanged from the 2026-08-26 posting.
  • Review this window: Layton nitted patches 1 and 4, accepted the overall approach on patch 5 “modulo some nits,” and then argued the DRC is not advisory. Lever defended best-effort semantics and pointed at NFSv4.1 for anyone who needs a total answer. No Acked-by, Reviewed-by, or v3.
  • Open questions left on the table: fold XPT_ORDERED into the eviction patch; the err hoist in patch 1; whether BSD already does this; the RENAME-then-reconnect race; and the unposted “moderate this behavior” follow-ups Lever mentioned.
  • Why it still matters to NFS clients: NFSv3/RDMA and NFSv3/TCP write-heavy workloads spend less server CPU in nfsd_cache_lookup if this lands. The same clients take a narrower DRC hit window on reconnect after a pipelined non-idempotent RPC. NFSv4.1 is Lever’s recommended escape hatch.

Until a v3 addresses Layton’s race, or someone Acks the current heuristic, the 120-second RC_EXPIRE hold remains the in-tree policy.
