gssd: clean up upcall threads on shutdown

Summary

gssd: clean up upcall threads on shutdown

Red Hat's Scott Mayhew posted a one-patch nfs-utils change that teaches rpc.gssd to join and free its GSS upcall worker threads when the daemon is going down. The work is a bug fix for a userspace NFS client leak, not a protocol change and not a new feature: Kerberos upcall handling is unchanged; only process-exit hygiene is.

No replies, acks, or nacks landed in the week ending 3 September 2026. The thread is a single posting.

The leak Valgrind sees

rpc.gssd is the NFS client's GSS helper. Kernel upcalls for context establishment are dispatched from the libevent loop in handle_gssd_upcall() into per-upcall pthreads created by start_upcall_thread() in gssd_proc.c. Mayhew ran the daemon under Valgrind and got a "possibly lost" report on thread-local storage allocated inside pthread_create():

"Valgrind reports leaks such as the following: 736 bytes in 2 blocks are possibly lost ... at calloc ... allocate_dtv ... _dl_allocate_tls ... pthread_create@@GLIBC_2.34 ... start_upcall_thread ... handle_gssd_upcall ... event_base_loop ... main"

He traces the blocks to two allocations that the existing watchdog is supposed to reclaim:

"This is due to the thread-local storage allocated by pthread_create() as well as the upcall_thread_info struct allocated by start_upcall_thread(). Those do eventually get freed by the watchdog thread in scan_active_thread_list(). The thread-local storage gets freed when pthread_tryjoin_np() succeeds and the upcall_thread_info gets freed via TAILQ_REMOVE() + free()."

The catch is timing. The watchdog sleeps between scans — 30 seconds by default — so a clean shutdown that does not wait for the next scan looks like a leak to Valgrind and similar tools:

"But since the watchdog thread sleeps between iterations (30 seconds by default), from the perspective of tools like valgrind there’s a leak."

That watchdog is itself NFS-client machinery Mayhew added years ago (the 2021 gssd: add timeout for upcall threads series) so hung Kerberos upcalls cannot pin rpc.gssd forever. The leak is therefore not a missing free in the steady-state path; it is a missing shutdown path that would drain the same list the watchdog walks.

The fix

The patch is 60 insertions in utils/gssd/gssd.c. Mayhew's stated goal is narrow:

"Add logic to clean up the threads on shutdown to make tools like valgrind happy."

Functionally, that means joining leftover upcall threads and releasing their upcall_thread_info nodes when rpc.gssd is exiting, instead of relying on a sleeping watchdog iteration that may never run. TLS from pthread_create() is reclaimed by a successful join (pthread_tryjoin_np() in the watchdog; an explicit join on shutdown), and the info structs go away with the same TAILQ_REMOVE() + free() sequence the scanner already uses.

This is client-side daemon hygiene. It does not change how the kernel NFS client posts gssd upcalls, how rpc_pipefs delivers them, or how GSS tokens are built. It does make it practical to run rpc.gssd under leak detectors without a 30-second wait, and it avoids leaving joinable pthreads behind when the helper is stopped.

Status this week

The patch stands alone. There is no review commentary in-window, no v2, and no indication yet whether nfs-utils maintainers want the shutdown drain to cancel still-running upcalls, wait on them, or only reap threads that have already exited — details that live in the omitted diff rather than the cover note.

It sits next to Mayhew's same-day companion gssd: fix upcall_* leak when re-reading service info, another Valgrind-driven rpc.gssd leak fix (strdup of upcall_address / upcall_port / upcall_protoname / upcall_service on a failed gssd_read_service_info()). Together they show a client-userspace leak-hunting pass on gssd this week, alongside the separate Pujeri name-validation series, but this thread itself is only the shutdown-join change.

Until someone reviews it, the conclusion is Mayhew's own: the watchdog already frees these objects, and shutdown should do the same work immediately so leak tools stop flagging rpc.gssd.
