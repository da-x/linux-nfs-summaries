nfsd v2 Netlink client dump, O(1) state counts

Summary

Dell’s Prabhakar Pujeri posted v2 of the nfsd Generic Netlink client-visibility series on 31 August, shrinking last week’s three-patch proposal to two: a privileged client-get dump of NFSv4 clients, plus O(1) per-client session and stateid counters. This is a new userspace ABI / admin feature on the server, not a wire-protocol change and not a runtime bug fix. No NFS client code is touched.

Jeff Layton reviewed patch 1/2 the next day. He called the dump “pretty sane” but asked for nfsd-style naming (find/marshal instead of get/put) and a less clever dump iterator. There was no reply, no review of patch 2/2, and no merge in this thread by week’s end.

Brief bridge from v1

Last week’s v1 cover also wanted a grace-status attribute on threads-get. Layton objected that it mirrored /proc/fs/nfsd/v4_end_grace and therefore answered the wrong operational question (NFSv4 recovery done ≠ files accessible; system grace is NLM ∪ v4). Chuck Lever then asked that any new API not freeze grace as a server-wide boolean, because per-export grace is an open possibility for re-export / backend reboot. Pujeri dropped the grace patch; Lever’s “WFM!” closed that design dispute. This v2 is the promised client-dump reroll without grace.

What v2 actually adds

Pujeri’s cover restates the operational problem: administrators can already inspect NFSv4 clients through the nfsd filesystem, “but collecting a server-wide view requires walking one directory and opening multiple files for every client.” The existing nfsdfs files stay unchanged. A companion nfs-utils v2 series (cover <cover.1787988918.git.prabhakar.pujeri@dell.com>) adds nfsdctl clients.

The two remaining steps:

  1. Dump basic NFSv4 client identity, address, lease, confirmation, reclaim, and callback state.
  2. Add O(1) snapshots of per-client session and stateid record counts.

He is explicit about the grace split:

"This reroll intentionally drops the grace-status patch. As discussed with Chuck, that interface needs an explicitly scoped design that can represent both current server-wide grace and possible per-export grace in the future. I will address it in a separate proposal."

Material changes since v1:

  • raw sockaddr attribute replaced by separate IPv4/IPv6 address, port, and optional IPv6 scope-ID attributes
  • nonzero client-table generation plus genl_dump_check_consistent(), so churn marks the dump NLM_F_DUMP_INTR
  • session-list and stateid-IDR walks under cl_lock replaced by maintained u64 counters, making every per-client snapshot O(1)
  • counts encoded as variable-width Netlink uint attributes
  • rebase onto nfsd-testing at 65b583e874b3

Validation is unusually thorough for an admin ABI: strict checkpatch, YNL regeneration (33 schema checks), Sphinx -W docs, W=1 GCC 16.1.1, Sparse over every fs/nfsd translation unit, and two independent two-vCPU QEMU boots. Each boot created one live NFSv4.2 client with one session, open stateid, lock stateid, and delegation stateid (zero layouts); raw Netlink, nfsdctl, and /proc/fs/nfsd/clients agreed. The series carries Assisted-by: LLM sparse.

Patch 1/2: privileged client-get dump

Patch 1/2 is the ABI core. It emits one bounded message per confirmed or unconfirmed client: server-generated client ID, peer address, minor version, client and callback states, signed lease time remaining, and RECLAIM_COMPLETE status.

Concurrency is still conservative. Each client is pinned for the snapshot; mutable lease and confirmation fields sit under the per-net client lock; server shutdown is serialized with nfsd_mutex. The v1 “best-effort snapshot” caveat is now a real dump-consistency flag:

"Track client-table changes with a nonzero generation counter and use genl_dump_check_consistent() so a dump that can skip or repeat a client is marked NLM_F_DUMP_INTR."

The sockaddr split is the other ABI cleanup: the peer is no longer a raw sockaddr blob, which is what monitoring tools actually want (family, address, port, optional IPv6 scope ID).

Patch 2/2: O(1) per-client state usage

Patch 2/2 is the monitoring-oriented follow-on. A client can “retain substantial server-side state even when its lease and callback channel look healthy,” so the dump grows separate counts for sessions and for open, lock, delegation, and layout stateid records. The lock count is deliberately not a byte-range or LOCK-operation count:

"A lock stateid represents a lock-owner/file pair and can cover multiple byte-range locks, so document that these are record counts rather than protocol operation or byte-range counts."

v1 walked the session list and the stateid IDR under cl_lock. v2 maintains u64 counters at the existing session and stateid publish/removal points, so the dump takes an O(1) snapshot instead of holding the spinlock across an unbounded IDR. Counters decrement only at final IDR removal, preserving the existing record-count semantics for retained stateids. Encoding is variable-width Netlink uint (four bytes when the value fits in u32, eight otherwise).

That is the important server-side performance fix in this series: not a client I/O bug, but a dump that will not stall cl_lock on a client with a huge stateid table.

Jeff Layton: naming, defensive programming, dump iterator

Layton’s review is confined to patch 1/2. He did not object to the feature, the Netlink family choice, or the generation/NLM_F_DUMP_INTR churn handling. The nits are nfsd house style and dump-state clarity.

On the lookup helper:

"I'd call this nfsd_nl_find_client() as we usually use "get" in terms of reference counting."

On walking unconfirmed clients when the table cursor has already reached NFSD4_NL_CLIENT_DONE:

"This means that table == NFSD4_NL_CLIENT_DONE means the same an "UNCONFIRMED". The caller shouldn't call it in that case I guess, but this is a lack of defensive programming."

On marshalling the peer address (v1-style put in the helper name):

"In nfsd, we often use "put" with reference counting, so looking at this cold, this is confusingly named. Maybe change this to be named nfsd4_nl_client_marshal_address() ?"

On the dump loop that increments cb->args[0] through confirmed then unconfirmed tables:

"This while loop is a bit too clever for our own good. cb->args[0] is effectively a state enum, so why are we incrementing through its values?"

"It's looking at confirmed, then unconfirmed clients, but that's not evident here."

He closed with a net-positive verdict:

"The rest looks pretty sane though."

No comments landed on the O(1) counters, the uint encoding, or the YAML/RST docs this week.

What this means for NFS client development and bug fixes

Nothing in this thread is an NFS client patch, a protocol change, or a client-visible bug fix. The client-visible impact, if v2 lands after Layton’s nits, is still indirect and operational: a privileged Netlink dump that a restart/failover harness — or an operator watching a busy NFSv4 server — can consume without walking /proc/fs/nfsd/clients. Identity, lease remaining, confirmation, reclaim, callbacks, and per-client session/open/lock/delegation/layout record counts are the data that harness needs; the grace half of that picture remains deferred to a later, scoped operation.

The only “bug-fix-shaped” change is defensive dump quality: NLM_F_DUMP_INTR on client-table churn, and O(1) counters so the dump does not walk unbounded IDRs under cl_lock. Those are server observability hardening, not client I/O fixes.

Status at week’s end: v2, under review, not merged. Layton’s naming and iterator comments are the open review items; patch 2/2 is unreviewed in this thread. A later v3 exists as a separate series and is out of scope here.
