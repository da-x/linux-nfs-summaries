nfsdctl v2 clients table, no replies yet

Summary

Dell’s Prabhakar Pujeri posted v2 of the nfs-utils nfsdctl clients series on 31 August, shrinking last week’s three-patch proposal to two and aligning it with the companion NFSD Generic Netlink client-state v2 ABI (kernel cover). This is a new admin feature — a privileged userspace consumer of a proposed Generic Netlink dump — not a wire-protocol change and not a Linux NFS client bug fix. The three messages in this thread are the cover plus the two patches; no review landed here by week’s end.

The operational problem is unchanged. Monitoring NFSv4 clients today “requires walking the nfsd filesystem and parsing a separate info file for every client.” nfsdctl clients is meant to be the compact, automatable view; the nfsd filesystem remains the detailed-inspection path.

Brief bridge from v1

v1 (cover) taught nfsdctl threads to print an in-grace boolean, added the clients table, and extended it with session/stateid counts. Earlier this week, on that v1 thread, Jeff Layton held apply because Sashiko had flagged a softlockup in the kernel companion’s per-client count walk, and Steve Dickson — the nfs-utils maintainer who would actually apply these patches — accepted the sequencing:

"Okay... I'll wait to apply them until things get sorted out... but I will keep them on my todo list..."

Separately, Chuck Lever asked that any new API not freeze grace as a server-wide boolean. Pujeri dropped the kernel grace patch; this nfsdctl v2 is the matching userspace reroll.

What v2 actually changes

Pujeri’s cover is explicit that this is the userspace half of kernel v2:

"Add the userspace consumer for the companion NFSD Netlink client-state v2 series"

The two remaining steps:

  1. A privileged nfsdctl clients table for basic client identity, address, lease, confirmation, reclaim, and callback state.
  2. Session and stateid record counts on that table.

Compatibility is still attribute-driven:

"Attribute presence remains the compatibility boundary. Missing count attributes are displayed as dashes."

A bundled nfsd_netlink.h lets nfs-utils build before the new kernel header is installed. The configure probe selects a system header only when it contains the complete count extension.

Material changes since v1, all mirroring the kernel ABI cleanup:

  • decode separate IPv4/IPv6 address, port, and scope-ID attributes instead of raw sockaddr data
  • detect NLM_F_DUMP_INTR on client records and NLMSG_DONE, and fail with a retry diagnostic rather than displaying a potentially inconsistent list
  • decode variable-width 32-bit or 64-bit uint count attributes and display counts as uint64_t values
  • drop the companion grace-status patch with the kernel-side grace patch

The series is based on nfs-utils master at 67ed1bdb1af1c70a5fd3b377a997401b7676b827. It carries Assisted-by: LLM.

Validation is end-to-end rather than compile-only: strict checkpatch with no findings; full nfs-utils make check against both the bundled UAPI and headers_install from the companion kernel (one environment-dependent test skipped in each run); byte-for-byte comparison of bundled and kernel-source NFSD UAPI headers; and two independent two-vCPU QEMU boots of the exact companion kernel. Each nfsdctl clients run showed the expected NFSv4.2 client, loopback peer, lease, callback/reclaim state, one session, one open, one lock, one delegation, and zero layouts, and “nfsdctl output agreed with raw Netlink and /proc/fs/nfsd/clients state.”

Patch 1/2: nfsdctl clients

Patch 1/2 is the meat of the series: a new privileged clients command that consumes NFSD_CMD_CLIENT_GET and prints one row per client.

Each row reports:

  • server-generated client ID
  • peer address
  • minor version
  • client state
  • lease time remaining
  • reclaim status
  • callback state

The address decoder is the ABI-facing change from v1. Instead of a raw sockaddr blob, nfsdctl now reconstructs the peer from separate IPv4 or IPv6 address, port, and scope-ID attributes — the same split the kernel v2 dump emits. Unknown enum values still print as "unknown" so a newer kernel with extra states remains usable rather than being treated as a parse error.

The other v1-to-v2 fix is dump integrity. The kernel companion now tracks client-table generation and uses genl_dump_check_consistent(), so a dump that can skip or repeat a client is marked NLM_F_DUMP_INTR. nfsdctl treats that as a hard failure:

"Detect NLM_F_DUMP_INTR on both client records and NLMSG_DONE. Report an error instead of silently presenting a client list that may have skipped or repeated a record."

That is the important userspace counterpart of the kernel consistency work: an operator (or a restart/failover harness) must not act on a silently truncated or duplicated client list. The commit message’s “Changes since v1” restates the policy as “reject interrupted dumps and ask the administrator to retry.”

The bundled UAPI header is updated here, and configure is taught to require NFSD_CMD_CLIENT_GET before selecting a system copy of that header. Man page and asciidoc updates (nfsdctl.8, nfsdctl.adoc) land with the command. The patch is +325/−1 across five files, most of it in utils/nfsdctl/nfsdctl.c.

Patch 2/2: per-client state usage

Patch 2/2 extends the clients table with the session and stateid record counts the kernel series exports — sessions plus open, lock, delegation, and layout stateid records. The stated purpose is triage, not replacement of nfsdfs:

"These totals help an operator identify which client is retaining server-side state before using the detailed nfsd filesystem views."

The decoder now accepts both four-byte and eight-byte Netlink uint encodings and stores every count as uint64_t, matching the kernel’s variable-width uint attributes. A missing or malformed count still prints as a dash, so a new nfsdctl against a kernel that has the base client dump but not the count extension stays accurate rather than inventing zeros:

"This keeps the command accurate when a new nfsdctl is used with a kernel that supports the base client dump but not the count extension."

The configure probe is tightened again to require the last count attribute before accepting a system UAPI header, which is how a header that only knows the base command still forces the bundled copy.

On the kernel side those lock counts are stateid records, not byte-range lock counts: a lock stateid is a lock-owner/file pair and can cover multiple byte-range locks. This nfsdctl patch does not restate that distinction in the commit message; operators reading the new columns will still need the kernel documentation (or a later man-page tweak) to avoid misreading a lock column as a LOCK-operation counter.

How this couples to the kernel ABI this week

This nfsdctl v2 is sequenced against kernel v2, which replaced unbounded session-list and stateid-IDR walks under cl_lock with maintained u64 counters — the fix for the Sashiko-flagged softlockup that blocked v1. The userspace series itself does not re-litigate that kernel performance work; it just consumes the O(1) snapshot and the NLM_F_DUMP_INTR flag.

The kernel companion did draw review this week, but not on this thread. Jeff Layton called the kernel dump “pretty sane” while asking for nfsd-style naming (find/marshal instead of get/put) and a less clever dump iterator. Pujeri later accepted those nits on the kernel thread and posted a kernel v3. None of that discussion migrated here: Steve Dickson did not re-ACK the nfs-utils reroll, and nobody nitted the table formatting, the retry diagnostic, or the UAPI probe.

The grace column is gone. nfsdctl v1 patch 1/3 — the threads in-grace display — targeted an attribute that will not land until a separately scoped grace operation exists. Until that lands, nfsdctl clients can show leases, reclaim, callbacks, and per-client stateid load, but not whether the server is still in recovery.

NFS client development and bug-fix angle

Nothing in this thread is an NFS client patch, a protocol change, or a client-visible I/O bug fix. No fs/nfs code is touched. The client-visible impact, if both the kernel dump and this nfsdctl consumer land, is still indirect and operational: a compact way for an operator — or a restart/failover harness watching Linux NFSv4 clients against a Linux nfsd — to see which clients hold leases, which have finished RECLAIM_COMPLETE, which have a live callback channel, and which are retaining a large session/stateid table, without scraping /proc/fs/nfsd/clients.

The only bug-fix-shaped pieces are dump robustness on the server-admin path:

  • NLM_F_DUMP_INTR is treated as a hard error with a retry diagnostic, so a churned dump is not silently presented as truth.
  • Count attributes are decoded as variable-width uint and displayed as uint64_t, so a kernel that emits eight-byte counts is not truncated.
  • Missing counts print as dashes rather than zeros, which is the mixed-version safety net for a new nfsdctl on an older kernel.

Those are observability correctness issues, not client I/O fixes. The kernel-side softlockup that blocked v1 is addressed in the companion series (O(1) counters), not here.

Status

  • v2 posted to linux-nfs, no nfs-utils review on this thread. The three messages are the cover plus two patches; there are no replies.
  • The apply-blocker from v1 (kernel dump softlockup) is the reason this reroll exists; Dickson’s “I’ll wait” on v1 has not yet been revisited here.
  • The userspace ABI is still attribute-driven and mixed-version safe (dash out missing counts, print "unknown" for new enums, bundle the UAPI header, fail interrupted dumps).
  • Grace reporting remains deferred to a later, scoped kernel operation; this series no longer pretends to print it.
  • Kernel v2 of the dump is under review (Layton nits on naming/iterator, later a kernel v3); this nfsdctl v2 still consumes the v2 ABI as posted on 31 August.

Until Dickson — or another nfs-utils reviewer — looks at the retry diagnostic, the sockaddr split, and the uint64 count decoder, this should be read as the working userspace prototype of the table, not as a frozen nfs-utils contract.
