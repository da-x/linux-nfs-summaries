rpcbind hardening: rmtcalls, stats, and spoofed replies

Summary

Scott Mayhew posted a six-patch rpcbind hardening series on 3 September, targeting userspace rpcbind rather than the kernel NFS client. The work is a collection of bug fixes and defensive hardening, not a protocol change. Most of the patches close resource-exhaustion and spoofing holes around CALLIT/BCAST/INDIRECT processing — the remote-call path that NFS stacks historically used for PMAPPROC_CALLIT-style broadcasts, and that is supposed to be off unless --enable-rmtcalls is passed at configure time.

Mayhew framed the series around a gap in that default:

"Many of these are related to CALLIT/BCAST/INDIRECT processing, which in theory should be disabled when --enable-rmtcalls was not passed to the configure script, except currently that only prevents the forwarding port from being created."

No review replies landed in-window. The six patches stand as posted.

Logging fork bomb in check_callit()

Patch 1/6 stops check_callit() from calling logit() on every rejected CALLIT/BROADCAST/INDIRECT unless rpcbind was started with -l (connection logging). logit() forks a child just to call syslog(), so a remote client can spam those procedures and burn CPU, scheduler slots, and PIDs. Failures still fail closed; they simply stop generating a child process per packet.

Unbounded rpcbind stats lists

Patch 2/6 caps the addrinfo and rmtinfo linked lists built by rpcbs_getaddr() and rpcbs_rmtcall() at 4096 entries, trimming the oldest tail node after each prepend. Unique program/version/netid combinations previously grew those lists without bound, so a client that walked program numbers could force unbounded memory growth even when the request itself was later rejected. The patch is marked Assisted-by: Claude:claude-opus-4-6.

--enable-rmtcalls was only half-disabled

The centerpiece is patch 3/6. Commit 2e9c289 ("rpcbind: Disable remote calls by default") added --enable-rmtcalls (off by default) but only skipped creating rmtcallfd for a netconfig entry. Clients could still send CALLIT/BCAST/INDIRECT; processing bailed out later in rpcbproc_callit_com() after find_rmtcallfd_by_netid() failed — but not before logit() (the fork) or rpcbs_rmtcall() (a stats bucket for a unique program/procedure) had already run.

With the option unset, those procedures now return PROC_UNAVAIL immediately. Dispatch is wired through pmap_svc.c, rpcb_svc.c, rpcb_svc_4.c, rpcb_svc_com.c, rpcb_stat.c, and security.c, with a new helper in rpcbind.h. Mayhew:

"If configure is run without the '--enable-rmtcalls' option, then fully disable remote call functionality. Attempts to call CALLIT/BCAST/INDIRECT will receive an accept state of PROC_UNAVAIL."

That is the change that actually matches the documented default for NFS deployments that never opted into remote calls.

GETSTAT no longer answers the network

Patch 4/6 restricts RPCBPROC_GETSTAT to loopback callers in security.c. Mayhew's rationale is blunt:

"There's no reason to allow remote machines to query the local machine's rpcbind statistics."

Together with the stats-list cap, this keeps rpcbind's internal counters from being both a remote reconnaissance surface and an allocation oracle.

Null netmask in addrmerge()

Patch 5/6 is a small defensive fix in util.c. getifaddrs(3) allows ifa_netmask to be NULL; addrmerge() now skips those interfaces instead of handing a null pointer to bitmaskcmp(). Mayhew called it mainly defensive — bitmaskcmp() is only used for AF_INET/AF_INET6, and he is "not sure it's possible for an interface to have an IP address but no netmask" — but a NULL deref in address merging would take down the daemon that NFS clients and servers use to find portmapper/rpcbind services.

Spoofed XIDs freeing forward slots

Patch 6/6 tightens handle_reply() so a forward slot is freed only when the reply XID matches the original request XID. If remote calls are enabled and the ephemeral forwarding ports are reachable, an attacker can spoof replies with a bogus XID, free slots out from under in-flight forwards, and disrupt replies to legitimate CALLIT requesters. The one-line policy change is the series' only explicit spoofing fix, and it matters for any NFS/rpcbind deployment that still compiles with --enable-rmtcalls.

Status

Eight files, +78/−13. The series is hardening/bug-fix work on the userspace rpcbind that the Linux NFS client (and NFSD) still depend on for portmap/rpcbind lookups and, when enabled, remote calls. Nothing in-window ACK'd, NAK'd, or iterated the patches; they remain Mayhew's v1 drop from 3 September. The practical takeaway for NFS client deployments is that default builds (no --enable-rmtcalls) would finally reject CALLIT/BCAST/INDIRECT at the procedure table instead of after allocating stats and forking loggers, while GETSTAT and spoofed forward replies are fenced even when remote calls stay on.
