gssd: fix upcall_* leak when re-reading service info

Summary

Red Hat's Scott Mayhew posted a one-patch nfs-utils change that plugs a definite strdup() leak in rpc.gssd when the daemon re-reads a client's rpc_pipefs "info" file. This is a bug fix in the NFS client userspace helper, not a protocol change and not a new feature: Kerberos upcall semantics stay the same; only lifetime of four cached strings is corrected.

No replies, acks, or nacks landed in the week ending 3 September 2026. The thread is a single posting.

It is the companion to Mayhew's same-day gssd: clean up threads on shutdown patch. Together they are a Valgrind-driven leak-hunting pass on the client GSS daemon.

The leak

rpc.gssd watches rpc_pipefs with inotify. When a client directory appears or changes, gssd_inotify_clnt() walks into gssd_scan_clnt(), which calls gssd_read_service_info() whenever clp->prog == 0. That function parses the per-client "info" file and caches four strings on the client object: upcall_address, upcall_port, upcall_protoname, and upcall_service.

The fail path is the problem. If the first read is incomplete — Mayhew's example is the "info" file not yet fully populated when inotify fires — the function still strdup()s whatever it parsed into those four fields, then leaves clp->prog == 0. The next scan therefore calls gssd_read_service_info() again. Both the success path (which NULLs the pointers) and a subsequent fail path (which strdup()s fresh copies) overwrite the previous allocations without freeing them.

Mayhew states the overwrite plainly:

"A subsequent re-scan then calls gssd_read_service_info() again and overwrites those fields without freeing them first: the success path sets them to NULL and the fail path strdup()s fresh copies, leaking the previous allocations."

Valgrind classified the result as a definite leak, not a "possibly lost" TLS leftover like the companion shutdown-join patch:

"5 bytes in 1 blocks are definitely lost in loss record 13 of 929 ... at malloc ... strdup ... gssd_read_service_info (gssd.c:373) ... gssd_scan_clnt (gssd.c:734) ... gssd_inotify_clnt (gssd.c:922) ... gssd_inotify_cb ... event_base_loop ... main"

The stack is the client inotify path: libevent delivers the watch callback, gssd_inotify_clnt() rescans the client, and gssd_read_service_info() leaks the previous strdup(). The 5-byte block is consistent with a short parsed token (address, port, protoname, or service) that was replaced on the next read.

This is a real leak in a live daemon, not a shutdown artifact. Every time inotify fires before the "info" file is complete, rpc.gssd can drop another small heap block. On a busy client that is mounting, remounting, or racing rpc_pipefs population, that can accumulate.

The fix

The patch is 15 insertions in utils/gssd/gssd.c. Mayhew's approach is the obvious one: free the four upcall_* fields at the top of gssd_read_service_info() before the function repopulates them.

"Free the upcall_* fields at the top of the function before repopulating. clp is calloc()'d so the fields are NULL on the first call, making the free() calls safe."

That is important for the first-call case. Client objects come from calloc(), so the pointers start NULL and free(NULL) is a no-op. Subsequent calls, whether they succeed or fail, now drop the previous strings before writing new ones (or NULLing them on success). The fail path can still strdup() partial results and leave clp->prog == 0 so a later scan retries; it just no longer leaks the previous copies.

The change does not alter how rpc.gssd interprets the "info" file, how it talks to the kernel NFS client, or how GSS upcalls are dispatched. It is strictly allocation hygiene around a retry that already existed.

Client-side context

rpc.gssd is the userspace half of the Linux NFS client's Kerberos/GSS stack. The kernel posts upcalls through rpc_pipefs; gssd reads per-client service metadata (program number, address, port, protocol, service name) from the "info" file and then runs the GSS context dance. gssd_scan_clnt() treating clp->prog == 0 as "not yet initialized" is why a partial inotify event retries the read. That retry is correct; the missing free() on the cached strings was not.

Mayhew marked the patch Assisted-by: Claude Opus 4.8. The commit message and Valgrind traceback are his; the assistant credit is noted but the diagnosis is specific to gssd's inotify/scan path.

Status this week

The patch stands alone. There is no review commentary in-window, no v2, and no indication yet whether nfs-utils maintainers want the fail path to avoid caching partial strings at all (which would also stop the leak, by never storing them until prog is set) versus Mayhew's free-before-repopulate approach. The posted fix is the latter: keep the existing retry-and-cache behavior, just stop leaking.

Until someone reviews it, the conclusion is Mayhew's own: gssd_read_service_info() must free upcall_address, upcall_port, upcall_protoname, and upcall_service before it overwrites them, because inotify can call it more than once while clp->prog is still zero.
