NFS client rides along on v2 PG_private removal

Summary

Zi Yan posted PATCH v2 00/14 of a treewide MM series that deletes the PG_private page flag so the bit can be reused as upcoming PG_folio (__PG_folio). Callers that used to test the flag now look at page/folio->private != NULL. This is infrastructure work, not an NFS protocol change and not an NFS bug fix; the NFS client is an exceptional user whose writeback private data already lives in folio->private with its own refcount rules.

The series is a follow-up to last month’s RFC. Yan kept the NFS diagnosis unchanged from v1:

"fs/nfs/write.c: folio refcount maintenance is in a bigger scope than folio->private. So folio_attach/detach/get_private() is not used. Nothing to change."

That is the important NFS-client point. Most filesystems can switch to folio_attach/detach/change_private() so the folio refcount rises and falls with ->private. NFS does not: nfs_page (and related writeback state) is attached for a wider lifetime than a simple attach/detach pair, so the client continues to poke folio->private directly. The v2 NFS diffs are therefore mechanical cleanup, not a rewrite of dirty-page tracking.

Two patches actually touch fs/nfs and are addressed to Trond Myklebust and Anna Schumaker:

  • PATCH v2 11/14 removes the now-noop folio_set_private() / folio_clear_private() helpers. fs/nfs/write.c loses two calls; Yan’s commit message is blunt: they “are no-ops now.” After PG_private itself is gone, those helpers no longer set a flag distinct from the pointer, so leaving them in the NFS writeback path would only obscure the real invariant (folio->private non-NULL means NFS private data is attached).
  • PATCH v2 13/14 retargets comments that still named PagePrivate / PG_private. fs/nfs/file.c is a four-line comment tweak so the mmap/writeback notes talk about page/folio->private instead of the doomed flag.

No other NFS files appear in the v2 diffstat (file.c +4/−, write.c −2). The treewide PagePrivate() → page_private() conversion does not need extra NFS call-site churn.

Yan also introduces folio_test_fs_private() to mean “filesystem private data,” excluding swapcache (which overlays swp_entry_t on ->private) and hugetlb (which stores its own flags there). v2 “converted more call sites” to that helper. NFS writeback should keep treating a non-NULL folio->private as nfs_page state; the new helper is the MM-side way to ask the same question without tripping over swap or hugetlb.

v2’s other exceptional users (zsmalloc, perf AUX ring buffers, Xen grant-table, fscrypt bounce pages, erofs readahead/I/O counters, f2fs PAGE_PRIVATE_NOT_POINTER, hugetlb) are outside the NFS client. The NFS-relevant changelog items are the no-op helper removal and the comment retargeting; the rest of v2 tightens non-NFS conversions (open-coded zsmalloc checks, erofs I/O-counter bias so folio->private never goes NULL between attach and detach, and so on).

Testing listed in the cover letter is allmodconfig, zsmalloc/erofs/fscrypt/f2fs workloads, and MM selftests. There is no NFS-specific test plan (no xfstests against an NFS mount, no writeback/unstable-page stress). That is a gap for client reviewers: NFS is called out as the filesystem that cannot use the standard attach/detach helpers, yet it is not in the test matrix.

On 3 September the f2fs patchwork bot reported that Jaegeuk Kim applied [PATCH v2 06/14] (“f2fs: stop using PG_private”) to jaegeuk/f2fs.git (dev). That is subsystem uptake of the f2fs half, not an NFS ack. Nobody from linux-nfs replied in-window.

Bottom line for NFS client development: v2 still treats NFS writeback as a special case that already owns folio->private and its refcount, and it only deletes leftover folio_set/clear_private() calls plus PagePrivate comments. The series remains a page-flag reclamation for PG_folio, not an NFS bug fix. Client maintainers have not yet reviewed the two fs/nfs patches; until they do, the risk is comment/helper drift rather than a behavioral change in how nfs_page is stored on a folio.
