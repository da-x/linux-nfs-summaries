SUNRPC rejects truncated deferrals to close GSS replay bypass

Summary

This week’s linux-nfs traffic included a standalone security fix from Yilin Zhang of Moonshot AI, targeting a SUNRPC server-side hole in request deferral rather than any NFS client path. The patch, titled “[PATCH] SUNRPC: reject deferral when rq_arg.len < head[0].iov_len”, landed on 1 September with no replies in-window.

What kind of change this is

This is a bug fix with security impact, not a protocol change and not a new feature. The code under repair is svc_defer() in net/sunrpc/svc_xprt.c — the NFS server RPC layer that snapshots an incoming request so it can be replayed later. NFS client development is untouched: there is no client-side code, no mount-option work, and no nfs.ko change in this thread.

Zhang frames the defect as a missing length-consistency check that lets a crafted RPCSEC_GSS packet poison the deferred copy of a request:

"svc_defer() misses the rq_arg.len vs head[0].iov_len check, so a crafted RPCSEC_GSS packet can make the deferred snapshot no longer be the original request."

The security consequence follows from how deferred replays are authenticated:

"Since deferred replays skip GSS verification, this may lead to an authentication bypass."

The report is credited to Kimi Security Team (bug-report@moonshot.ai).

Technical argument

SUNRPC deferral is the mechanism nfsd uses when a request cannot be completed immediately (cache waits, recall/delegation conflicts, and similar “come back later” cases). svc_defer() is supposed to freeze a faithful copy of the original RPC arguments. Later, when the server is ready, that snapshot is replayed as if it were the same request.

Zhang’s claim is that the snapshot path does not enforce the same rq_arg.len versus head[0].iov_len invariant that other receive/parse paths expect. If those two lengths disagree — specifically if the recorded argument length is smaller than the first iovec — a crafted GSS-wrapped packet can make the deferred buffer no longer represent the original request. Because the replay path skips GSS verification (the request was already “authenticated” on first receipt), a mismatched snapshot can be executed without a second integrity check.

The proposed fix is small: four added lines in net/sunrpc/svc_xprt.c that refuse deferral when rq_arg.len < head[0].iov_len. In other words, if the argument vector is internally inconsistent, do not take a deferred snapshot at all. That is a conservative server-side rejection rather than an attempt to reconstruct or clamp the buffer.

Evolution of the discussion

There is no evolution yet. Zhang’s patch is the only message in the thread this week, and ListThreadMessages shows no follow-ups, Reviewed-by tags, or maintainer ACK. Prior-week summaries on this list do not cover this Message-ID; the issue appears as a new report rather than a continuation of the nfsd netlink hang series or other in-flight SUNRPC work.

Client-development angle

Readers tracking NFS client development can treat this as adjacent infrastructure, not a client bug:

  • The vulnerable function is svc_defer(), used by nfsd / the in-kernel RPC server.
  • The attack surface is a crafted RPCSEC_GSS packet arriving at a server that defers requests.
  • Client GSS (RPCSEC_GSS on nfs/rpc.gssd) is not implicated; a well-behaved client would not generate the inconsistent rq_arg.len / head[0].iov_len pair that the patch now rejects.

The important client-adjacent takeaway is operational: any site that uses RPCSEC_GSS to nfsd, and that exercises server deferral (common under cache/delegation load), should treat this as a server authentication-bypass candidate until the four-line guard is reviewed and merged. There is no client workaround described in the thread.

Conclusions this week

No conclusion from maintainers yet. The reporter’s own conclusion is that deferral must be refused when the argument header is longer than the recorded request length, because otherwise a GSS-crafted packet can replace the deferred snapshot and skip GSS on replay. Until review lands, the thread stands as an unacked security patch against SUNRPC request deferral, not as an accepted fix and not as NFS client work.
