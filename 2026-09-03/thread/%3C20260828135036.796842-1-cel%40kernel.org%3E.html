svcrdma credit-grant clamp and extra-dispatch fixes

Summary

On 28 August, Chuck Lever posted a three-patch series of bug fixes for the in-kernel NFS/RDMA server (svcrdma) and the shared SUNRPC transport layer. The cover letter is short and unsentimental:

"Rediscovered these while cleaning out old development branches. All minor fixes."

Nothing in the series is a protocol change, and nothing adds a new feature. Two of the three patches are correctness fixes that matter to NFS/RDMA clients; the third is a small accounting skip that only UDP ever consulted. No replies, Reviewed-by tags, or follow-up versions landed in-window. The discussion this week is the posting itself.

What this is

  • Type: bug-fix series (two svcrdma correctness/perf patches, one SUNRPC accounting skip).
  • Not a new feature, not an RFC/protocol change, not a Linux nfs.ko code change.
  • Client impact is still real: patch 1 can drop an NFS/RDMA connection with an RNR error if the client honors the advertised credit grant; patch 2 cuts a wasted server-side dispatch that shows up as extra cycles on every RPC.

Patch 1: credits after the RQ clamp (client-visible disconnect)

PATCH 1/3 is the important client-facing fix. svc_rdma_accept() currently computes sc_fc_credits from sc_max_requests before the Receive Queue depth is checked against the device's max_qp_wr. When that check lowers sc_max_requests, the credit grant keeps the original value. Lever's diagnosis is blunt:

"When that check lowers sc_max_requests, the credit grant keeps the original value, so the server advertises more credits than it has Receives posted. A client that uses the full grant overruns the Receive Queue, and the connection is lost with an RNR error."

The one-line change is to set sc_fc_credits after the clamp, so the advertised grant matches the number of Receives the server actually posts. Tagged Fixes: fc2e69db82c1 ("svcrdma: Clean up comment in svc_rdma_accept()") — a comment-cleanup commit that apparently left the assignment on the wrong side of the clamp.

For NFS client development this is the headline. Linux xprtrdma (and any other NFS/RDMA client that trusts the server's credit grant) will post Sends up to that grant. If the server over-advertises, the client's next Send hits an empty Receive Queue, the QP goes RNR, and the connection dies. The bug is silent until a device with a tight max_qp_wr actually clamps sc_max_requests; on roomy hardware the two values stay equal and nobody notices. The client does not need a matching patch — it is already behaving correctly by using the grant — but operators of NFS/RDMA clients will see fewer unexplained disconnects once this lands on the server.

Patch 2: leftover XPT_DATA dispatches a second thread

PATCH 2/3 is a server-side dispatch bug that wastes a thread per RPC. svc_rdma_wc_receive() and svc_rdma_wc_read_done() set XPT_DATA after queuing a completed context. svc_rdma_recvfrom() then dequeues one context and leaves the flag set, so svc_xprt_received() re-enqueues the transport and svc_xprt_enqueue() wakes a second thread that finds both queues empty and returns zero.

The fix rechecks the receive queues after each dequeue and clears XPT_DATA when the last context is taken, rather than only when a dequeue finds nothing. Lever also relaxes svc_xprt_received()'s kernel-doc, which no longer described every transport's XPT_DATA protocol.

The measurements are on one NFSv4.2 connection over 100GbE RoCE, and they are specific enough to quote:

"A 4KB random read at queue depth 1 falls from 2.997 transport dequeues per RPC to 1.998, and from 96,629 to 82,398 server cycles per RPC. A 256KB random write falls from 3.270 dequeues to 2.004, and from 259,936 to 246,059 cycles. Each dispatch removed is worth about 10,000 cycles."

The gain shrinks as the receive queues fill — a leftover XPT_DATA then dispatches a thread that finds real work. An 8KB random write at queue depth 512 already runs at the two dequeues an RPC with a Read chunk requires, and shows no change. Throughput only moves where the server has no idle CPU to absorb the saving, so only the queue-depth-1 read gains, by 1.8%.

One dispatch per RPC remains on purpose:

"svc_rdma_send_ctxt_put() sets XPT_DATA to schedule a drain of sc_send_release_list, and svc_rdma_recvfrom() does not service that list."

Client I/O is unchanged; this is a server-cycle tax on every NFS/RDMA RPC. Low-QD, latency-sensitive clients (single-threaded 4K reads) are the ones that will notice the 1.8% throughput bump.

Patch 3: stop accounting xpt_reserved on TCP and RDMA

PATCH 3/3 is housekeeping with a small hot-path win. The xpt_reserved counter exists for UDP socket-buffer back-pressure. svc_udp_has_wspace() is the only has_wspace implementation that consults it, so on TCP and RDMA the counter is maintained and never read. svc_handle_xprt() adds to it once per RPC; svc_reserve() shrinks it again from svc_process_common(), from svc_xprt_release(), and from every proc function that calls svc_reserve_auth(). Every shrinking call also runs svc_xprt_resource_released(), which issues an smp_mb() and can enqueue the transport.

The patch adds an xcl_flags field to svc_xprt_class, sets SVC_XPRT_FLAG_WSPACE_RESERVE on the UDP class, and gates the accounting on that flag. After the change, svc_reserve() no longer calls svc_xprt_resource_released() on TCP and RDMA. Two paths still cover that enqueue: svc_xprt_release() via svc_xprt_release_slot(), and svc_xprt_received() for a transport whose XPT_DATA remains set.

This is not a client bug fix. It is a server-side skip of a counter and a memory barrier that TCP and RDMA never needed. Combined with patch 2, it trims spurious transport enqueues on the NFS/RDMA and NFS/TCP server paths.

Client-development takeaway

Linux nfs.ko / xprtrdma is not modified. The series still belongs in a client-development roundup because patch 1 is a server bug that only manifests on the client: an NFS/RDMA client that uses the full advertised credit grant overruns the server RQ and loses the connection with an RNR error. That is exactly how a well-behaved client is specified to behave. Until the clamp and the grant stay in lockstep, operators will keep seeing "the RDMA mount dropped" on devices whose max_qp_wr is tighter than sc_max_requests. Patch 2 then shaves a wasted server dispatch that shows up as extra latency on low-QD NFS/RDMA reads.

Conclusions

  • Bug-fix series, not a feature and not a protocol change. Three patches, 40 insertions, no discussion yet.
  • Patch 1 is the must-land item. Grant credits from the clamped sc_max_requests so the server never advertises more Receives than it posted. Without it, a client that honors the grant can RNR the QP and drop the mount. Tagged against fc2e69db82c1.
  • Patch 2 stops a leftover XPT_DATA from waking a second, empty recvfrom. Measured ~10k cycles per avoided dispatch; 1.8% throughput on QD1 4K reads over 100GbE RoCE. One dispatch remains because send-context release still uses the flag.
  • Patch 3 gates xpt_reserved on a new SVC_XPRT_FLAG_WSPACE_RESERVE, set only on UDP. TCP and RDMA stop paying smp_mb() + possible enqueue on every svc_reserve().
  • No review in-window. The series left the week as posted-and-unacked. Watch for Reviewed-by tags and for patch 1 to be treated as a stable candidate, given the Fixes: tag and the client-visible disconnect.
