Layton asks Alemi to retest the cld rpc_pipe_msg KASAN hit

Summary

This week’s linux-nfs traffic on Farhad Alemi’s syzkaller report is a maintainer triage reply, not a patch, a protocol change, or a new feature. Two days after Alemi’s KASAN finding against NFSD’s client-tracking (cld) upcall, Jeff Layton answered with a request to retest rather than a diagnosis or a fix. The thread still has no in-list reproducer, no Fixes: candidate, and no unlink/rpc_pipe_msg lifetime patch.

That matters to NFS client work because the crashing caller is nfsd, but the object under discussion is the shared SUNRPC rpc_pipefs queue. rpc_queue_upcall() and a stack-backed struct rpc_pipe_msg are the same machinery the client uses for idmap, gssd, and pNFS blocklayout device maps. Last week’s blocklayout lost-wakeup series treated __cld_pipe_upcall() as the safe waiter. Layton’s reply does not close that circle; it only asks whether 7.1-rc5 is already stale.

Last week, in brief

Alemi of ASU’s SEFCOM lab mailed Chuck Lever and Jeff Layton a syzkaller crash on Linux 7.1-rc5 whose subject already states the diagnosis: [BUG] sunrpc: rpc_pipe_msg left queued on a stack frame (nfsd cld upcall). The splat was a KASAN vmalloc OOB in __list_add_valid_or_report() — the signature of walking a list_head that still points into a returned kernel stack. The claim is that NFSD’s NFSv4 client-tracking upcall (__cld_pipe_upcall() in fs/nfsd/nfs4recover.c) builds rpc_pipe_msg on the stack, queues it, and can return with the message still on pipe->in_upcall / pipe->pipe. Completions do not make that safe. Alemi pointed at off-list traces, offered a reproducer.c on request, and volunteered to test a patch. No one answered before that week closed.

This week’s only in-thread message

On 29 August, Layton replied without quoting the KASAN analysis, without asking for the reproducer, and without naming a commit. The entire technical content is a version check:

"We've had a lot of bugfixes go into the last couple of releases. Can you test this against a more bleeding-edge kernel and see if it's still a problem?"

He ranked the trees he wants:

"Testing against Linus' master branch would be good, but if you can pull down Chuck's nfsd-testing branch, that would be even better."

That is a reasonable first response to a fuzzer report against 7.1-rc5. It is also not a confirmation that the stack-queued rpc_pipe_msg class is already fixed. Layton does not identify which of “the last couple of releases” would have unlinked the message on every abort path, nor does he connect the report to FAN YE’s contemporaneous pNFS blocklayout completion rewrite — the client series that copied __cld_pipe_upcall() as its wait model.

Alemi did not answer this thread in-window. As of the week ending 3 September, the original report still has no on-list confirmation that master or nfsd-testing is clean, and no on-list NAK that the 7.1-rc5 hit was a false positive.

NFS client angle: the shared pipefs waiter is still the story

The user-visible server impact, if the race is real outside the fuzzer, is a kernel oops or memory corruption on the nfsd cld pipe during client-id tracking (nfsdcld restarts, pipe close, reboot recovery). The client-visible impact is the blast radius of rpc_queue_upcall():

  • pNFS blocklayout’s bl_resolve_deviceid() still stack-allocates rpc_pipe_msg and, after v2, waits on a completion “the way __cld_pipe_upcall() waits.” A leftover queued message after the waiter returns is the complementary bug to last week’s lost wakeup.
  • Client idmap and gssd upcalls sit on the same rpc_pipefs lists. Any of those paths that embed rpc_pipe_msg on the stack needs the same unlink-on-all-return-paths rule: a heap-allocated message, or an explicit list_del_init() / rpc_purge_list() on every abort.
  • Layton’s “lot of bugfixes” remark is the closest thing this thread has to a client-development conclusion, and it is deliberately unspecific. Until Alemi retests, maintainers are treating the 7.1-rc5 KASAN hit as possibly already fixed, not as a confirmed remaining hole in the waiter that client code is copying.

This thread does not itself land a client fix. It also does not refute Alemi’s subject-line diagnosis. The discussion is still a bug report against SUNRPC pipefs lifetime, parked on a retest request.

Where things stand

  • Kind of change: bug report (use-after-return of a stack rpc_pipe_msg on the nfsd cld upcall). Not a feature. Not a protocol change. No patch in this thread.
  • This week’s evolution: silence → Layton asks for a retest on Linus’ master, preferably Chuck Lever’s nfsd-testing.
  • Evidence still on the table: syzkaller on 7.1-rc5, KASAN vmalloc-OOB in __list_add_valid_or_report, full traces off-list on GitHub, reproducer offered but never requested in-thread.
  • Open questions for client work: whether current rpc_queue_upcall() callers (blocklayout, idmap, gssd, cld) still leave a stack message queued on interrupt, pipe close, or error; whether any of “the last couple of releases” already closed that; whether the completion wait that blocklayout v2 copied from cld is sufficient without a matching message lifetime.

Until Alemi posts a master/nfsd-testing result on this thread, the cld upcall remains an unreproduced-by-maintainers fuzzer crash on the shared SUNRPC pipe queue, and the NFS client’s blocklayout/idmap waiters remain in the same blast radius.
