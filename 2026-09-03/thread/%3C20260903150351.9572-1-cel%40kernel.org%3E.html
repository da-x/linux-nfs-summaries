xdrgen gains pages and aggregate pragmas for v2/v3/ACL codecs

Summary

xdrgen gains pages and aggregate pragmas for v2/v3/ACL codecs

Chuck Lever posted a ten-patch new-feature series for the in-tree xdrgen code generator on 3 September, adding two specification-level directives that the forthcoming NFSv2, NFSv3, and NFS_ACL conversions need. This is not a protocol change and not a runtime bug fix: no in-tree .x file applies either directive yet, so generated codecs stay byte-identical. There were no replies in-window.

Why the tool had to grow

The cover letter names the two XDR shapes that still force hand-rolled codecs, and that therefore block converting the remaining NFS programs:

"The first is a payload that resides in the Linux page cache. Currently the generated codec for a variable-length opaque copies through a data pointer, but a READ result already sits in the pages of rq_res and a WRITE payload arrives in the pages of the Receive buffer. Marshaling and unmarshaling this type of payload needs to avoid copying the payload's content."

"The second is an array of non-scalar objects. Examples include the NFS_ACL aclent<> list, which is the on-the-wire form of the kernel's posix_acl, and the READDIR entry list, which is produced from a VFS iteration."

Those two cases are exactly the ones a Linux NFS client also has to get right: nfs.ko already stages READ/WRITE through the page cache and already shares fs/nfs_common/nfsacl.c with the server. The series is server-shaped in its helpers (svcxdr_*), but the generator changes are the prerequisite for converting both sides of NFSv2/v3 and the shared ACL codec off hand-rolled XDR.

The series is 23 files, +1043/−43, concentrated in tools/net/sunrpc/xdrgen/ plus a thin SUNRPC runtime layer. Lever’s operational guarantee:

"No in-tree XDR specification applies either directive yet, so the generated output remains unchanged across the whole series."

Runtime plumbing: a codec context on xdr_stream

Generated functions take only an xdr_stream. Extra state as extra arguments would make every generated signature depend on a whole-spec analysis. Patch 01/10 therefore adds xdrgen_ctx to struct xdr_stream, following seq_file->private and netlink_callback->data. Every initializer clears it, including the NFSv4 server encoder in fs/nfsd/nfs4xdr.c and the client-side paths in net/sunrpc/xdr.c, so a stack-allocated or recycled stream cannot leak a stale pointer.

Patch 02/10 then binds the server transaction into that slot from svcxdr_init_decode() / svcxdr_init_encode(), recovered through svcxdr_rqst() rather than an open-coded void * cast:

"A client stream already records its transaction in the rqst field; a server stream records nothing, so each generated codec that needs the svc_rqst would have to store it in xdrgen_ctx itself, and every such site would decide on its own what the pointer means."

The guarantee is scoped: other initializers leave xdrgen_ctx NULL, svcxdr_rqst() returns NULL there, and a codec that needs the svc_rqst has to name those two entry points in its Context: line. That is the client-relevant design choice: the shared xdr_stream grows a generic private pointer, but the server-only svc_rqst binding is not smuggled into client encode/decode.

pragma pages: encode and decode bulk payloads by reference

Patch 03/10 adds svcxdr_encode_opaque_payload(). Generated encoders currently call xdr_stream_encode_opaque(), which copies. On the server an NFS READ payload is already in rqstp->rq_res pages from the filesystem read:

"Copying that payload into the RPC Reply buffer adds a data copy on every READ and prevents a transport capable of direct data placement from conveying the payload separately from the rest of the Reply."

The helper encodes the length, splices the payload pages into the stream, and marks the byte range as a result payload. Parameters are only the stream and the length; the svc_rqst comes back through svcxdr_rqst().

Patch 04/10 is the generator prerequisite: member encoder/decoder emitters, including the self-referential _XdrPointer path in pointer.py, now receive the containing struct name so a later directive can key on the (struct, member) pair. Output is still byte-identical.

Patch 05/10 introduces pragma pages. A marked variable-length opaque or string member emits svcxdr_encode_opaque_payload() instead of the copying encoder. The front end refuses a directive that names an undeclared type or member, a member that cannot carry a payload, or a second marked member of the same type:

"svcxdr_encode_opaque_payload() consumes the whole page vector and moves the stream into the tail, so one encoder carries at most one payload."

"A directive that binds to nothing would degrade silently to the copying encoder, so the front end rejects one…"

That last rule is the anti-bug-fix: a typo in a .x file must not quietly reintroduce the copy the conversion is trying to delete.

Patch 06/10 is the decode-side counterpart, svcxdr_decode_opaque_payload(), for a WRITE-class argument that already sits in Receive-buffer pages. Patch 07/10 lets the same pragma pages drive that decoder when the containing type is reachable from an RPC procedure argument. Reachability is closed over nested aggregates and typedef aliases before directives are checked. A decoded page-resident member is a struct xdr_buf so later stages can hand the payload to the VFS without a copy. A marked union arm of an argument type is rejected because the union generator still only emits the copying decoder.

For the Linux NFS client, this is the missing piece for generated NFSv2/v3 READ/WRITE codecs: the server helpers are svcxdr_*, but the generator contract (one page-resident opaque per type, xdr_buf on decode, no silent fallback) is what a later client conversion would reuse rather than inventing a second copy-avoidance story.

pragma aggregate: hook-driven arrays and optional-data lists

Patch 08/10 attacks the other remaining hand-rolled island. A generated variable-length array currently materializes a C array and walks it. That is wasted traffic when the in-kernel object is not that array. Lever’s canonical example is shared client/server code:

"The NFS_ACLv2 secattr aclent<> list is one such case: it is a Solaris wire form of the kernel's posix_acl. The hand-rolled codec that performs that transform forces its containing types to keep external linkage (pragma public), and that linkage collides at link time with the same generated types in a sibling program."

pragma aggregate <struct> <member> makes the generated codec own only the wire framing and call hand-written begin/item/end hooks, one element at a time. Interior codec signatures do not change. The loop is modelled on xdr_encode_array2() — “whose only remaining user is fs/nfs_common/nfsacl.c” — and on seq_file’s start/show/stop. Unlike those APIs, the consumer is known at generation time, so hooks bind by name at link time the way ASN.1 compiler actions do:

"A missing hook is a link error, the emitted prototypes enforce the element type, and no indirect call is added per element."

Item hooks return only success or failure, with no early “no more elements” return, so the same contract can later frame RFC 4506 optional-data lists. A bad marker is reported against its own source position rather than silently falling back to the array-walking codec.

Patch 09/10 extends that to optional-data (type *name) list members, the NFSv2 READDIR entry list being the example. There is no count on the wire; the loop uses value-follows framing, calling the element encoder once per entry and once more with NULL for the terminator. The generated decoder is linkage-only:

"Decoding a value-follows list needs a presence-reporting element decoder, which this change does not add. NFSv2 READDIR only encodes its entry list, so the decode path is never exercised."

That encode-only READDIR path is a server fact. A client still has to decode READDIR replies, so this series does not yet give nfs.ko a generated READDIR decoder; it unblocks the NFSD conversion and leaves a presence-reporting decoder as future generator work.

Patch 10/10 then stops requiring the begin hook to know the element count up front. The v9 optional-data encoder looped cursor.count times, which would force a streaming producer to materialize the whole list:

"A producer that reads its elements while the reply is encoded -- NFSv2 READDIR streaming directory entries straight into the send buffer -- does not know that count in advance, and would have to materialize the whole list just to satisfy the loop bound."

Because an optional-data list carries no count on the wire, the encoder is now driven from the item hook: a false return ends the list and the framing writes the terminator. The counted-array form and its hook contract are unchanged.

Client development and what this is not

  • Type of change: generator feature plus a small SUNRPC runtime API (xdrgen_ctx, svcxdr_rqst(), svcxdr_{en,de}code_opaque_payload()). Not a wire-protocol change. Not a Fixes: candidate.
  • No behavioral change this week. Until an .x file uses pragma pages or pragma aggregate, every existing generated codec is identical. The README grows 136 lines documenting the new directives.
  • Linux nfs.ko is not converted here. Shared struct xdr_stream gains a cleared private pointer; client initializers already had a rqst field and are not rebound through svcxdr_rqst(). The important client-facing payoff is later: generated NFSv2/v3 READ/WRITE can avoid payload copies, and the shared nfsacl.c transform can drop pragma public (and the xdr_encode_array2() leftover) without colliding with a sibling program’s generated types.
  • READDIR decode is still a gap for the client. Optional-data aggregate encode can now stream; optional-data aggregate decode is a stub. NFSD READDIR only encodes, so that is enough for the server conversion Lever is staging. A client READDIR conversion still needs a presence-reporting element decoder that this series explicitly does not add.
  • Zero-copy / DDP. The pages helpers exist so a DDP-capable transport can keep the bulk payload out of the RPC header copy. That matters equally to a client WRITE and a server READ; only the server helpers are written so far.

Conclusions

The discussion is a v1 posting with no review yet. Lever’s design is conservative in the ways that matter for a code generator sitting under both NFS client and server:

  1. Directives that do not bind fail at parse time, never by silently emitting the old copying or array-walking codec.
  2. One page-resident payload per encoder, because the helper consumes the whole page vector.
  3. Aggregate hooks are link-time named functions, not a per-element ops vtable, so a missing NFS_ACL or READDIR hook is a build break rather than a NULL deref.
  4. Generated output is unchanged until the NFSv2/v3/NFS_ACL specs actually apply the pragmas.

Watch for review of the svcxdr_* helpers and of the optional-data decoder stub, and for the follow-up series that first uses pragma pages on READ/WRITE and pragma aggregate on aclent<> / READDIR. Those are the patches that will start deleting hand-rolled codecs on the server and, later, on the client.
