nfsd drops grace Netlink ABI pending per-export scope

Summary

Summary

Dell’s Prabhakar Pujeri and nfsd maintainer Chuck Lever closed the remaining design dispute on patch 1/3 of Pujeri’s v1 Netlink observability series this week. The work remains a new userspace ABI / admin feature on the nfsd Generic Netlink family — not a wire-protocol change and not a bug fix — and it still does not touch NFS client code. What changed is the shape of the series: the grace-reporting patch is coming out of the client-visibility reroll so that a server-wide boolean does not freeze the ABI before nfsd can express per-export grace.

Brief bridge from last week

Last week Pujeri posted “[PATCH v1 0/3] nfsd: expose NFSv4 client state through Netlink” (cover), splitting three steps: report NFSv4 recovery-grace on threads-get, add a privileged client-get dump, and attach per-client session/stateid counters. Jeff Layton objected that the v1 grace attribute mirrored /proc/fs/nfsd/v4_end_grace and therefore answered the wrong operational question — “Just because the v4 recovery is done does not mean that you will be able to access files. The overall system grace period is a union of both the NLM and v4 grace periods.” Pujeri accepted that and sketched a v2 that would report locks_in_grace().

Separately, Chuck Lever asked that any new API leave room for future per-export grace, a possibility he tied to re-export / backend-server reboot:

"I'd like any new API to avoid foreclosing the ability to move exports in and out of grace individually rather than as a single unit."

That constraint is what this week’s two messages resolve.

This week: Pujeri will not freeze a server-wide boolean

On 28 August, Pujeri replied that Lever’s point “makes sense.” A network-namespace-wide boolean would still be useful as an aggregate, but the v1 single attribute does not make its scope explicit enough for a later per-export model:

"A network-namespace-wide boolean would remain useful as an aggregate, but the current single attribute does not make its scope explicit enough for future per-export grace."

The practical consequence is a split of the series rather than a quiet semantic tweak inside threads-get. Pujeri will:

  1. Drop the grace-reporting patch from the forthcoming client-visibility v2.
  2. Post the client dump and state-count patches separately (last week’s 2/3 and 3/3), so the monitoring ABI can move without waiting on grace-schema design.
  3. Follow up with a dedicated grace-status proposal whose records carry an explicit scope, so the same operation can represent server-wide state today and individual exports later.
  4. Wait for agreement on export identity before adding that part speculatively — he does not want to invent a per-export key in the Netlink schema until reviewers have signed off on how an export is named.

He closed by asking whether that direction addresses Lever’s concern.

Lever signs off

Ten minutes later, Lever answered with a one-line maintainer ACK:

"WFM!"

That is the week’s conclusion on patch 1/3: the v1 grace attribute will not land, even in the locks_in_grace() form Pujeri had already conceded to Layton. Grace reporting is deferred to a later, scoped operation. The client-dump and state-count work is expected to proceed on its own.

What this means for NFS client development and bug fixes

Nothing in this thread is an NFS client patch, a protocol change, or a runtime bug fix. The client-visible impact, if the remaining pieces land, is still indirect and operational: a privileged Netlink dump of NFSv4 clients (identity, lease, confirmation, reclaim, callbacks, and per-client session/open/lock/delegation/layout stateid counts) that a restart/failover harness — or an operator watching a busy server — can consume without walking /proc/fs/nfsd/clients. The grace half of that picture, which is exactly the signal such a harness needs before it can declare recovery finished, is now blocked on a future ABI that can name an export.

No further review of patches 2/3 or 3/3 appeared this week. The series as a whole remains v1, under review, not merged; the next expected posts are a grace-less client-visibility v2 plus a separate, scoped grace-status RFC.
