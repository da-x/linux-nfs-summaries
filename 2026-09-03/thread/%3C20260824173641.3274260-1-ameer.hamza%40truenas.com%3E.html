Jeff Layton reviews NFSD session-slot replay fix

Summary

This week the NFSD session-slot replay race thread added a single, conclusive review: Jeff Layton tagged Ameer Hamza’s already-applied server-side bug fix with:

"Reviewed-by: Jeff Layton jlayton@kernel.org"

That is the entire in-window discussion. There is no v2, no protocol debate, and no further design commentary. The patch remains a bug fix, not a new feature or a protocol change.

Brief bridge from last week

Last week Hamza posted nfsd: don't modify a session slot when replaying its cached reply, and Chuck Lever applied it to nfsd-testing the next day. The regression is in NFSD’s NFSv4.1 session DRC, not in NFS client code. Commit cc028a10a48c (“NFSD: Hoist status code encoding into XDR encoder functions”) moved nfsd4_proc_compound()’s cstate->status assignment below the out: label, so nfsd4_sequence_done() no longer recognized a replay. Every cached-reply path then stored its reply and cleared NFSD4_SLOT_INUSE as if it owned the slot.

Hamza’s diagnosis from last week still frames the client-visible failure:

"nfsd4_sequence() claims a session slot by setting NFSD4_SLOT_INUSE under nn->client_lock. A reply served from the slot's reply cache does not claim it."

The crash is triggered by a legal NFSv4.1 client behavior: pipelining two copies of a cached SEQUENCE request before reading either reply. After the hoist, two replays could run on the same slot, race on slot->sl_cred / group_info, and panic in same_creds(), or (since v6.14 slot-table shrink) kfree() a slot a replay still held. Hamza reproduced it “with a client that pipelines two copies of a cached request before reading either reply.” The Linux NFS client does not have to be buggy; retry/replay of a SEQUENCE-tagged compound is exactly what sessions were designed to allow.

The fix records actual slot claim in a new cstate->slot_owned flag and tests that flag in nfsd4_sequence_done(), so only the owner updates the cached reply and clears NFSD4_SLOT_INUSE.

This week’s conclusion

Layton’s Reviewed-by arrives three days after Lever already queued the patch. Combined with last week’s apply, the thread is now closed from a review standpoint: Hamza’s slot_owned restoration of the original DRC ownership contract has both maintainer application and an independent review from a core NFS developer.

For operators and client testers, the practical takeaway is unchanged: any 6.12-era (and later) nfsd that inherited the XDR-encoder hoist can panic or UAF when a client retries a cached SEQUENCE while another replay is still completing. The back-port candidate is the server-side slot_owned flag, not a client change.
