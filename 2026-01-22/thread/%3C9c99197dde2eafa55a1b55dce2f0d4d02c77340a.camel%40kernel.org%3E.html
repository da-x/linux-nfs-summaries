NFS Export Opt-In: Hellwig Insists on Stable Handles Flag and Userspace Exposure

Summary

NFS Export Opt-In: Hellwig Pushes Back on cgroupfs Exports and Insists on Stable Handles Flag Exposure

Summary

Type: Protocol change / filesystem export infrastructure enhancement (continued from prior weeks)

Prior Weeks Recap

Jeff Layton's 29-patch series "require filesystems to explicitly opt-in to nfsd export support" was posted on January 15th. The series introduces a new EXPORT_OP_STABLE_HANDLES flag to prevent filesystems with unstable filehandles (such as kernfs-based pseudo-filesystems like cgroupfs) from being accidentally exported via NFS. Prior weeks saw extensive debate about the flag's naming (STABLE_HANDLES vs PERSISTENT vs NeilBrown's preferred EXPORT_OP_SUPPORTS_NFS_EXPORT), the semantics of what "stable" means, and Christian Brauner's firm stance that pseudo-filesystems like pidfs and nsfs should never be exportable regardless of filehandle characteristics. See prior summaries for related NFS server security discussions this week.

This Week's Activity: Hellwig's Two-Part Response on January 21st

This week saw two closely-spaced messages from Christoph Hellwig, both responding to Jeff Layton's January 20th message [id://a35ac736d9ebc6c92a6e7d61aeb5198234102442.camel@kernel.org], where Layton suggested adopting NeilBrown's EXPORT_OP_SUPPORTS_NFS_EXPORT naming and argued against allowing cgroupfs exports.

1. Pushback on cgroupfs Export Use Cases [id://aXCjsTBnHGuqTJdb@infradead.org]

In response to Layton's argument that there is no good use case for exporting cgroupfs via NFS, Hellwig reinforced the consensus:

"Yeah. And I'm pretty sure everyone here will push back hard on any such use case."

This brief but emphatic statement underscores the community's unified position: pseudo-filesystems like cgroupfs should not be NFS-exportable, regardless of whether their filehandles happen to meet technical stability criteria. The concern is not merely about filehandle stability per se, but about the semantic appropriateness of exporting kernel internal state via a network file protocol.

2. Insistence on Stable Handles Flag and Userspace Exposure [id://aXCj9ooYaqsL9oyP@infradead.org]

Hellwig's second message addressed Layton's suggestion to adopt NeilBrown's EXPORT_OP_SUPPORTS_NFS_EXPORT flag name, which would be "much more arbitrary" than basing the decision on filehandle stability criteria. Hellwig pushed back firmly:

"We'll still need a stable handles flag, and expose it to userspace to avoid applications being tricked into using broken non-stable file handles. We should have caught that when they were added, but didn't unfortunately."

This is a significant point in the discussion. Hellwig is arguing for two things:

  1. A stable handles flag with clear semantics: Rather than an arbitrary "supports NFS export" flag, Hellwig wants a flag that conveys what the filehandles are actually about — their stability over the lifetime of a file. As he argued in earlier exchanges (referenced by NeilBrown):

"This flag is about the fact that for a given file, as long as that file exists in the file system the handle is stable."

  1. Userspace exposure: Hellwig emphasizes that this information should be exposed to userspace applications so they can make informed decisions about whether to rely on filehandle stability. This addresses a broader concern: applications using open_by_handle_at() or similar interfaces could be "tricked" into depending on filehandles that are not actually stable across reboots or filesystem remounts.

Evolution of the Discussion

The debate has evolved through several key phases:

  • Initial proposal (Jan 15): Layton introduced EXPORT_OP_STABLE_HANDLES as a technical criterion for NFS export eligibility.
  • Naming debate (Jan 15-19): Amir Goldstein suggested PERSISTENT as an alternative name; NeilBrown advocated for EXPORT_OP_SUPPORTS_NFS_EXPORT or EXPORT_OP_NOT_NFS_COMPATIBLE, arguing the flag is fundamentally about NFS compatibility, not filehandle properties.
  • Christian Brauner's hard line (Jan 19-20): Brauner made clear he would "hard NAK" any approach that mandates filesystems be exportable simply because their filehandles meet technical criteria, emphasizing that pseudo-filesystems like pidfs and nsfs must never be exported.
  • Layton's concession (Jan 20): Layton suggested adopting NeilBrown's arbitrary naming approach to achieve the desired effect — conscious decisions by filesystem maintainers about NFS export support.
  • Hellwig's counter (Jan 21, this week): Hellwig insisted that a semantically meaningful stable handles flag is still needed and must be exposed to userspace.

Key Technical Arguments

The Naming Semantics Debate

At the heart of this discussion is whether the flag should describe:

  • A property of filehandles (stable/persistent over a file's lifetime) — Hellwig's preference
  • A capability of the filesystem (supports NFS export) — NeilBrown's preference

NeilBrown argued in [id://176877859306.16766.15009835437490907207@noble.neil.brown.name]:

"I don't like PERSISTENT. I'd rather call a spade a spade. EXPORT_OP_SUPPORTS_NFS_EXPORT or EXPORT_OP_NOT_NFS_COMPATIBLE."

Hellwig countered in [id://aW3SAKIr_QsnEE5Q@infradead.org] (referenced by NeilBrown):

"Pick a name that conveys what the flag is about, and document those semantics well. This flag is about the fact that for a given file, as long as that file exists in the file system the handle is stable."

The kernfs/cgroupfs Problem

NeilBrown raised an important technical point: kernfs filehandles are stable while files exist, but they may be reused relatively soon after destruction. He asked [in id://176880736225.16766.4203157325432990313@noble.neil.brown.name]:

"I suspect kernfs does re-use filehandles relatively soon after the file/object has been destroyed. Maybe that is the real problem here: filehandle reuse, not filehandle stability."

This suggests the issue may be more nuanced than simple stability — it involves the lifetime and uniqueness guarantees of filehandles across file creation/destruction cycles.

Two Flags May Be Needed

NeilBrown speculated in [id://176885553525.16766.291581709413217562@noble.neil.brown.name]:

"I actually think that what Christoph wants is actually quite different from what Jeff wants, and maybe two flags are needed."

This observation points toward a potential resolution: one flag for filehandle stability semantics (for userspace consumption) and another for NFS export eligibility (for NFSD internal use).

Significance for NFS Client Development

While this discussion primarily concerns the NFS server (NFSD) side, it has implications for NFS clients as well. The stable handles flag, if exposed to userspace, could inform client-side decisions about:

  1. Filehandle caching: Clients could adjust their filehandle cache invalidation strategies based on whether the underlying filesystem provides stable handles.
  2. Re-export scenarios: When an NFS server re-exports a mount point, understanding the stability guarantees of the underlying filesystem's filehandles becomes critical for correct client behavior.

Status and Outlook

The discussion remains unresolved as of this week's end. Key open questions include:

  1. Whether one or two flags are needed (stability semantics vs. NFS export eligibility)
  2. How to handle pseudo-filesystems that have technically stable filehandles but should not be exported
  3. The mechanism for exposing stability information to userspace

Hellwig's insistence on a semantically meaningful, userspace-exposed stable handles flag suggests the final solution may incorporate both approaches: a stability flag for general use and an NFS-specific opt-in mechanism for NFSD.
