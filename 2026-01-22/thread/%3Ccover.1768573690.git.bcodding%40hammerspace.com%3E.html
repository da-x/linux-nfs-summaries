kNFSD Signed Filehandles: Security Enhancement Proposal Under Review

Summary

kNFSD Signed Filehandles: A New Security Mechanism Under Scrutiny

Discussion type: New feature (NFS server security enhancement)

Overview

Benjamin Coddington introduced a 4-patch series this week proposing to add Message Authentication Code (MAC) signing to NFS filehandles in the kernel NFS server (kNFSD). The goal is to prevent filehandle guessing attacks, where an attacker fabricates valid filehandles to access files they shouldn't be able to reach through normal directory permission checks.

The series comprises:

  1. Patch 1/4: Convert export flags to use BIT() macro (cleanup)
  2. Patch 2/4: Add a key for signing filehandles via netlink and nfsctl filesystem
  3. Patch 3/4: Add sign_fh export option
  4. Patch 4/4: Implement actual signing and verification of filehandles using siphash

The Problem: Filehandle Guessing Attacks

Coddington explained the vulnerability in detail in the cover letter: filesystem filehandles are well-formed and predictable — for example, an XFS filehandle consists of a 64-bit inode number and a 32-bit generation number. While local systems protect against guessing via CAP_DAC_READ_SEARCH on open_by_handle_at(2), the NFS server must permissively accept remote filehandles without verifying the caller's local privileges.

"An NFS client holding a valid filehandle can remotely open and read the contents of the file referred to by the filehandle."

Coddington demonstrated the practicality of this attack: using a modified version of the t_open_by_handle_at.c example from the man page, he averaged 16 microseconds per open attempt on a local client-server setup and discovered his target filehandle in less than an hour. He also cited Trond Myklebust's estimate that with a 1ms round-trip and 50 parallel GETATTRs, it would take only one day to brute-force a 32-bit generation number.

NeilBrown reframed the problem elegantly in his analysis:

"You are trying to enforce path-based restriction in NFS... this effectively means you need a capability framework. So you are enhancing the filehandle to act as a capability by adding a MAC."

Key Technical Arguments

Chuck Lever's Skepticism About Threat Model

Chuck Lever provided the most thorough critique of the proposal, questioning whether filehandle fabrication is truly the premier attack vector:

"I'm unconvinced that this provides any real security. There are other ways of obtaining a filehandle besides guessing, and nothing here suggests that guessing is the premier attack methodology."

He raised several concerns:

  • Key stability: Nothing prevents userspace from providing a different key after reboot, since destroying the net namespace removes the server's ability to remember the previously set fh_key.
  • Rekeying: Changing the key would invalidate all existing filehandles, which is problematic given their long-lived nature. He noted: "An fh_key change is safe to do once all exported file systems are unexported and unmounted."
  • AUTH_SYS limitations: The fundamental issue is that NFS READ and WRITE lack authorization checks, a classic limitation of the AUTH_SYS security model.

Coddington responded patiently, clarifying that network security is assumed solved (via transport encryption) and the threat model assumes the client implementation may be compromised or buggy:

"We assume it might be able to send guessed filehandles because the client implementation is out of the server's control and scope of trust."

NeilBrown's Alternative Approach

NeilBrown proposed an alternative design that would avoid API changes to nfs-utils entirely:

"The problem can be rephrased as saying that 32 bits is too small for a generation number as it allows guessing in a modest time. A 64bit generation number would provide sufficient protection."

His proposal: filesystems could combine their existing 32-bit generation numbers with stable, non-NFS-visible superblock UUIDs (e.g., ext4's s_journal_uuid, XFS's sb_meta_uuid) to produce effectively unguessable 64-bit generation numbers embedded directly in filehandles. This would require per-filesystem changes but avoid the need for a signing key infrastructure.

Coddington acknowledged this as "good pondering" and noted the challenge of managing per-fs unique values across cloned/golden-image deployments:

"If so, it would be nice to find a way to unify setting/changing the per-fs unique value because cloning and 'golden image' approaches are often used in deployments."

Netlink Interface Design Debate

Jeff Layton suggested integrating the fh-key into the existing "threads" netlink operation as an optional attribute, rather than creating a new dedicated operation:

"Rather than a new netlink operation, I think we might be better served with just sending the fh-key down as an optional attribute in the 'threads' op."

Chuck Lever disagreed, arguing for separation of concerns:

"I'd much rather set a precedent of several small ops rather than one or two Swiss army knives."

Coddington agreed to adopt Jeff's suggestion for v2, while the broader debate about netlink interface design continued.

Layering and Code Structure

Chuck Lever flagged a layering violation in patch 4/4, where signing logic was embedded in XDR encoding code:

"This is a layering violation. XDR encoding never alters the content in the local data structures, and this will be impossible to convert to xdrgen down the line."

He recommended containing the signing logic within fh_compose() and fh_verify(). Coddington acknowledged this was feasible but noted that fh_compose() creates partial handles requiring fh_update() after file creation, making it more complex. He also accepted Chuck's suggestions to use crypto_memneq() for timing-safe comparison, pr_warn_ratelimited(), and symbolic constants.

NeilBrown on Root Filehandles

NeilBrown corrected a misleading comment in the code about why root filehandles remain unsigned:

"rpc.mountd always asks the kernel for a filehandle, so it doesn't need a key. However signing the root filehandle would be pointless as the client can 'PUT_ROOTFH' without needing to provide a signature."

Coddington agreed to drop the comment.

Broader Interest

Christian Brauner expressed enthusiasm for the concept, noting its potential applicability to pseudo-filesystems like nsfs and pidfs:

"I really like this concept... For new types of file handles for such pseudo-fses I think this would be very lovely to have."

Miklos Szeredi asked whether the signing mechanism could be generalized as a utility in fs/exportfs/, with an eye toward enabling unprivileged open_by_handle_at(2):

"The ultimate use case for me would be unprivileged open_by_handle_at(2)."

Defense-in-Depth: Attack Detection

NeilBrown proposed an additional defense-in-depth measure: monitoring the ratio of stale filehandle errors per client/export and imposing delays when suspicious patterns emerge:

"We would need to monitor the result of exportfs_decode_fh_raw() for stale vs non-stale, and if the proportion of stale filehandles (on a given export) exceeds some low threshold (1%?) over a modest time period (5 minutes?) then .... what?"

Export Flags Cleanup

Patch 1/4's attempt to convert export flags to BIT() macro was flagged by Chuck Lever as a potential UAPI breakage since BIT() is a kernel convention. Coddington agreed to drop this patch in v2:

"I'm happy leaving these as hex constants."

Status and Next Steps

The thread concluded with no formal acceptance or rejection. The discussion remains open-ended, with several directions identified for future work:

  1. Coddington will iterate on the design, addressing Chuck's review comments (layering, timing-safe comparison, mutex protection for key setting) and adopting Jeff Layton's netlink suggestion.
  2. NeilBrown's alternative approach of embedding per-filesystem UUIDs into generation numbers warrants further exploration as a potentially simpler solution avoiding nfs-utils changes.
  3. Attack detection as defense-in-depth was identified as worth pursuing regardless of the signing approach chosen.
  4. Generalization of filehandle signing to fs/exportfs/ for broader use (including unprivileged open_by_handle_at) remains an open question.

Coddington summarized:

"Good pondering, I'm hoping this discussion continues a bit and we can figure it out — I'll still iterate on this design in the meantime."
