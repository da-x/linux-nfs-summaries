kNFSD Signed Filehandles v2: API Design Debate and Technical Refinements

Summary

kNFSD Signed Filehandles: v2 Patch Series Sparks Heated Debate on API Design

Overview

Discussion type: New feature (NFS server security enhancement)

Benjamin Coddington submitted a revised 3-patch series this week, refining his proposal to add Message Authentication Code (MAC) signing to NFS filehandles in the kernel NFS server (kNFSD). The goal remains unchanged from the v1 series last week: prevent filehandle guessing attacks, where an attacker fabricates valid filehandles to access files they shouldn't reach through normal directory permission checks.

The v2 series is reduced from 4 patches to 3, incorporating several changes:

  • Dropped the export flags BIT() macro conversion (per Chuck Lever's UAPI concerns)
  • Moved MAC signing into __fh_update() rather than XDR encoding code (addressing layering concerns)
  • Made fh_key setting an optional attribute on the netlink "threads" verb (per Jeff Layton's suggestion)
  • Fixed format string and uninitialized variable warnings caught by the kernel test robot

The series comprises:

  1. Patch 1/3: Add a key for signing filehandles via netlink and nfsctl filesystem
  2. Patch 2/3: Add sign_fh export option
  3. Patch 3/3: Implement actual signing and verification using siphash

Key Technical Arguments This Week

The Enduring Debate: procfs vs. Netlink API

The most contentious discussion this week centered on whether the fh_key setting interface should exist in both procfs (/proc/fs/nfsd/fh_key) and netlink (via nfsdctl). Coddington included both interfaces, arguing that distributions use different startup mechanisms:

"Some distros use one or the other. Some try to use both! Until you guys deprecate one of the interfaces I think we're stuck expanding them both."

Chuck Lever pushed back strongly against adding new procfs APIs:

"We have said we don't want to continue adding new APIs to procfs. It's not just NFSD that prefers this, it's a long term project across the kernel. If you have a clear technical reason that a new procfs API is needed, let's hear it."

Lever emphasized that netlink provides better guarantees about startup ordering — preventing the server from starting without setting the key first:

"Sounds like it will cause spurious stale file handles, which will kill applications on NFS mounts."

Jeff Layton sided with Lever, calling the procfs interface "categorically inferior due to its piecemeal nature":

"The old /proc interface is really for the case where you have old nfs-utils and/or an old kernel. In order to use this, you need both new nfs-utils and new kernel. If you have those, then both should support the netlink interface."

Coddington countered with a practical concern about RHEL's systemd startup, which falls back to rpc.nfsd on nfsdctl failure:

"The systemd startup for the nfs-server in RHEL falls back to rpc.nfsd on nfsdctl failure. Without the additional interface you can have systems that start the nfs-server via rpc.nfsd without setting the key - exactly the situation you're so adamant should never happen."

He also noted his own product (Hammerspace) would need the procfs interface since their tooling hasn't been converted to nfsdctl yet.

The exchange escalated in tone, with Chuck Lever writing:

"Is it? There's no point in asking that question other than as the kind of jab a kid makes when trying to catch a parent in a contradiction."

Coddington responded:

"Wow, yes. It's personal, and unprofessional. It has nothing to do with the merits of the argument at hand."

Ultimately, Coddington conceded:

"I understand. I'll remove the procfs interface here on the next posting."

Key Rotation Mechanism

Chuck Lever pressed for documentation or a mechanism for rotating the signing key when compromised. The initial design allowed setting the key only once per module load, with no reset capability. Jeff Layton proposed a more flexible approach:

"Personally, I think just disallowing key changes while the nfs server is running should be sufficient. If someone wants to shut down the threads and then change the key on the next startup, then I don't see why that shouldn't be allowed."

Coddington agreed and asked Chuck for approval. Chuck concurred:

"I hadn't thought of the 'nfsd.ko is built in' case. Oops. Yes, I think it's fine to keep the fh_key value locked only while the server is running, much like most of the other NFSD settings."

Endianness Bug Caught by Eric Biggers

Eric Biggers identified a subtle but important bug in the key handling code:

"Note that siphash_key_t consists of a pair of native-endian u64's. If you copy a byte array into it, the result will differ on little endian vs. big endian CPUs. You may want to do le64_to_cpus() on each u64, like what fscrypt_derive_siphash_key() does."

Coddington acknowledged: "Great catch - thanks Eric." This is a significant correctness issue that would cause signed filehandles to behave differently across CPU architectures.

Behavior When sign_fh Export Option Changes

Jeff Layton raised an important edge case regarding export option transitions:

"Support we start with sign_fh enabled, and client gets a signed filehandle. The server then reboots and the export options change such that sign_fh is disabled. What happens when the client tries to present that fh to the server?"

Coddington explained that the current code would return -ESTALE because the unsigned path would bypass MAC verification but still fail to resolve the oversized filehandle. He considered whether to trim the MAC without verification:

"Would it be a good idea to allow the server to see that the filehandle has FH_AT_MAC set, and just trim off the MAC without verifying it?"

Jeff Layton concluded: "No, I think -ESTALE is fine in this situation. We just need to understand what happens if it does, and make sure that it's documented."

Chuck Lever agreed and added:

"The documentation for 'changing from signed to unsigned and back' goes along with what happens when the fh_key needs to change, I would think."

He also suggested comprehensive testing:

"IMHO we also want to craft some pynfs tests to ensure that these cases work as we expect, and to ensure that we capture all of the cases that need to be checked (including the cases involving transitioning from sign_fh to not sign_fh and vice versa)."

nfsdctl Usability Concerns

In a side discussion, Coddington shared frustrations with nfsdctl's error reporting:

"When it reports a failure its not easy to figure out what's going wrong... I had to turn on the function tracer in the kernel to find that the error was coming from somewhere in nfs4_state_start()."

Jeff Layton acknowledged these rough edges and suggested improvements:

"In principle, we could have the kernel pass an error string back in the netlink upcall that nfsdctl could display. The problem is that nfs startup is spread over a bunch of functions, so passing that string back from the deep call stack would take some refactoring."

NeilBrown's Request for Quantified Threat Assessment

NeilBrown requested more concrete evidence in the cover letter:

"Simple testing confirms that the correct generation number can be found within XXX minutes using open_by_handle_at() and it is estimated that adding network delay with genuine NFS calls would only increase this to YYY minutes (ZZZ hours)."

This follows up on his v1 feedback asking for quantified threat modeling rather than qualitative assertions.

Evolution of the Discussion

The thread progressed through several phases:

  1. Patch submission (Jan 21): Coddington posted v2, incorporating most v1 review feedback
  2. API design debate (Jan 21-22): Intense back-and-forth between Coddington and Chuck Lever over procfs vs. netlink, escalating in tone before de-escalating
  3. Technical corrections (Jan 22): Eric Biggers identified the endianness bug; Jeff Layton raised the export option transition question
  4. Resolution (Jan 22): Coddington agreed to remove procfs interface; key rotation approach was settled on "locked while server running" model; documentation commitments made for edge cases

Final Conclusions and Next Steps

The discussion concluded with several clear action items for v3:

  1. Remove the procfs fh_key interface, keeping only netlink (Coddington's commitment)
  2. Fix the endianness bug in key handling per Eric Biggers' suggestion
  3. Allow key changes when server is stopped (not just once per module load), with documentation of the procedure
  4. Document the behavior when sign_fh export option transitions between enabled/disabled, including -ESTALE responses for mismatched filehandles
  5. Add pynfs tests for corner cases involving sign_fh transitions and key changes (Chuck Lever's suggestion)
  6. Quantify the threat model in the cover letter with concrete timing measurements (NeilBrown's request)

The series remains under active development with no formal acceptance or rejection. The broader architectural debate about signed filehandles versus alternative approaches (such as NeilBrown's proposal for 64-bit generation numbers using per-filesystem UUIDs, discussed in v1) continues to inform the design direction but was not revisited in detail this week.
