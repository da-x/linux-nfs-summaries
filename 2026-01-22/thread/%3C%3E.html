kNFSD Export Infrastructure: Signed Filehandles Clarification, export_operations Consolidation Proposal, and Lock State Discussion

Summary

kNFSD Signed Filehandles and Export Operations: Late-Week Follow-Ups from NeilBrown

Discussion type: New feature / API design (continued from prior weeks)

Prior Weeks Recap

This thread captures three brief late-week follow-up messages from NeilBrown, each continuing a separate but related discussion about NFS export infrastructure. The broader context spans several major threads this week:

  1. kNFSD Signed Filehandles (prior summary): Benjamin Coddington's 4-patch series proposing MAC signing of NFS filehandles to prevent filehandle guessing attacks, which sparked extensive debate about threat models, alternative designs (NeilBrown's 64-bit generation number proposal), and code layering.

  2. Filesystem export opt-in ([PATCH 00/29] fs: require filesystems to explicitly opt-in to nfsd export support): A large series restructuring how filesystems declare NFS export support via export_operations.

  3. EXPORT_OP_NOLOCKS documentation ([PATCH v2 01/31]): Part of a larger series documenting export operation flags, including the EXPORT_OP_NOLOCKS flag that controls whether NFS locking is available for an export.

See the Signed Filehandles summary for full prior-week context on the security discussion.

This Week's Activity: Three Follow-Up Messages

1. Signed Filehandles: Clarifying .permission in export_operations (Jan 19)

In his reply to Jeff Layton's concerns about the .permission callback in export_operations, NeilBrown clarified an important distinction:

"I was referring to the .permission function in export_operations, not the one in inode_operations (and no, it isn't confusing at all that both structs have the ops with the same name but different function....)."

He then made a significant observation about current NFS support:

"NFS doesn't define .permission in export_operations. Only pidfs and nsfs do."

This comment highlights that the .permission callback in export_operations is currently used only by pseudo-filesystems (pidfs and nsfs) for access control on filehandle-based operations, and is not yet implemented by the NFS client filesystem. This has implications for any future work to integrate signed filehandles or path-based access controls into NFS re-export scenarios — the NFS client would need to implement this callback to properly enforce permission checks when NFSD serves files accessed via NFS mounts.

2. Export Operations: Merging into super_operations (Jan 21)

In his response to Jeff Layton's suggestion about creating a separate filehandle_operations struct for local filehandle access operations, NeilBrown offered an alternative architectural direction:

"If that sort of change were seen to be valuable, I would rather not create a filehandle_operations but merge some (or all) of export_operations into super_operations."

He elaborated on the rationale:

"Maybe then the existence of s_export_op would return to mean 'NFS export supported' even if it is empty."

This proposal suggests consolidating VFS infrastructure by merging export_operations into the existing super_operations struct, rather than proliferating separate operation vectors. The benefit would be that the mere presence of s_export_op could serve as a clear indicator that a filesystem supports NFS export — even if the operations vector itself is empty. This would simplify the opt-in model being discussed in the 29-patch series and reduce the number of per-superblock pointers needed.

3. EXPORT_OP_NOLOCKS: Lock State Generalization (Jan 21)

In his reply to Jeff Layton's discussion about the EXPORT_OP_NOLOCKS flag and NFS locking semantics, NeilBrown explored how lock state could be generalized across NFSv4 and NLM (NFSv3) locking:

"statd keeps state in /var/lib/nfs/sm, and nfsd keeps v4 state elsewhere in /var/lib/nfs. This state effectively records if any NFS client might try to recover a lock."

He noted that NFSv4 state tracking is already granular enough to identify the filesystem involved:

"I think the v4 state is granular enough to identify the filesystem. lockd could be enhanced to use the same state I suspect."

NeilBrown outlined what would be needed for a VFS-level solution:

"We would need to generalise that state and load it at mount time and block new state creation accordingly. i.e. this would have to be a vfs-level thing which nfsd makes use of."

However, he tempered enthusiasm with pragmatism:

"Possibly, but there are other things better worth our time."

This suggests that while the idea of VFS-level lock state management is architecturally interesting, it may not warrant the development effort compared to other priorities in the NFS subsystem.

Key Technical Arguments and Evolution

Architectural Consolidation vs. Proliferation

A recurring theme across all three messages is NeilBrown's preference for consolidating VFS infrastructure rather than adding new structs or operation vectors. His suggestion to merge export_operations into super_operations reflects a broader design philosophy: keep the number of per-superblock pointers minimal and use existing infrastructure where possible.

NFS Client Gap in export_operations.permission

The observation that NFS doesn't implement .permission in export_operations (while pidfs and nsfs do) highlights an asymmetry in the current codebase. For re-export scenarios — where an NFS server serves files from an NFS mount — this gap means that path-based permission checks cannot be enforced at the filehandle level by the NFS client. This has implications for both the signed filehandles proposal and any future work on capability-style access controls for NFS re-exports.

Lock State Generalization: Interesting but Low Priority

The discussion about generalizing lock state across NFSv4 and NLM locking reveals a potential architectural improvement — using VFS-level state to coordinate lock availability across protocols. However, NeilBrown's candid assessment that "there are other things better worth our time" suggests this remains a nice-to-have rather than an urgent priority.

Significance for NFS Client Development

While these messages are brief and don't introduce new patches, they touch on several areas relevant to NFS client development:

  1. Re-export permission enforcement: The absence of .permission in the NFS client's export_operations means re-export servers cannot enforce path-based access controls at the filehandle level. Future work on signed filehandles or capability frameworks would need to address this gap.

  2. Export operations consolidation: Merging export_operations into super_operations could simplify the interface for filesystems that want to support NFS export, potentially making it easier for the NFS client (and other network filesystems) to declare their export capabilities.

  3. Lock state coordination: While deprioritized, the idea of VFS-level lock state management could eventually benefit NFS clients in multi-protocol environments where both NFSv3/NLM and NFSv4 locking are active.

Status and Outlook

These three messages represent late-week clarifications rather than new developments. The broader discussions they reference remain open:

  • Signed filehandles: Coddington is iterating on the design for v2, addressing review feedback on layering, timing-safe comparison, and netlink interface design.
  • Export opt-in series: The 29-patch series continues to evolve, with NeilBrown's suggestion about merging into super_operations offering an alternative architectural direction.
  • Lock state generalization: Acknowledged as interesting but not a current priority.
