nfsd: Block export of special kernel filesystems (pidfs, nsfs)

Summary

nfsd: Prevent Exporting of Special Kernel Filesystems (pidfs, nsfs)

Overview

This thread concerns a bug fix submitted by Amir Goldstein to prevent NFS daemon (nfsd) from exporting special kernel filesystems — specifically pidfs and nsfs. These filesystems recently gained file handle encode/decode support via name_to_handle_at(2)/open_by_handle_at(2), but their custom ->open() and ->permission() export operations are not respected by nfsd, making them unsuitable for NFS export.

Key Technical Arguments

The Problem

Amir Goldstein opened the discussion with a patch that blocks nfsd from exporting filesystems implementing custom ->open() or ->permission() export methods:

"These special kernel filesystems have custom ->open() and ->permission() export methods, which nfsd does not respect and it was never meant to be used for exporting those filesystems by nfsd."

The patch carries two Fixes: tags targeting the commits that added file handle support to pidfs and nsfs, indicating this should be backported to stable kernels. Amir framed this as a resolution to an ongoing debate about "stable file handles":

"I had enough of the stable file handles discussion... This patch which I already suggested on week ago, states a justified technical reason why pidfs and nsfs should not be exported by nfsd, so let's use this technical reasoning and stop the philosophic discussions about what is a stable file handle is please."

Code Review Feedback

NeilBrown reviewed the patch and confirmed its safety, noting that a potential NULL pointer concern is handled by exportfs_can_decode_fh():

"It is not immediately obvious that this is safe when nop is NULL, but it is because exportfs_can_decode_fh() checks for that case. As that is a static inline a static analyser can easily confirm this."

NeilBrown provided his Reviewed-by tag and endorsed the approach:

"I think this is a good check to have whether or not we decide to add a flag."

Christoph Hellwig (hch) raised documentation concerns, requesting that the patch's comment explain why ->open and ->permission are disallowed, not just what the code does:

"Please spell out here why ->open and ->permission are not allowed. Listing what the code does is generally not that useful, while why it does that provides value."

He also criticized the existing API documentation in exportfs.h:

"While looking this I have to say the API documentation for these methods in exportfs.h is unfortunately completely useless as well. It doesn't mention the limitation that it's only used by the non-exportfs code, and also doesn't mention why a file system would implement or have to implement them."

Jeff Layton provided his Reviewed-by while echoing hch's request:

"Seems reasonable, though I agree with HCH that you should explain why we're excluding these in the 'requirements' above."

Evolution of the Discussion

Amir responded that he preferred not to rewrite the existing documentation comment himself, suggesting instead that maintainers handle it:

"I prefer that Check and Jeff apply a separate patch to rewrite the documentation if they feel that this is needed or to propose the phrasing that they prefer."

hch insisted that proper documentation was essential:

"I don't really care who writes the documentation, but if we reject based on the presence of the methods we really need to document the why."

He emphasized the urgency of documenting these kernel internals:

"We're already confused only 2 years after this was added, and it's only going to get worse."

In a separate note, hch also advised against naming any helper function with "nfs" in it, since exportfs is a generic layer:

"Please drop the nfs - exportfs is a generic layer, and not tried to nfs, even if that's currently the only user."

Final Conclusions

  • The patch received Reviewed-by from both NeilBrown and Jeff Layton.
  • The core fix — blocking NFS export of filesystems with custom ->open()/->permission() export ops — was broadly supported as a necessary safeguard for pidfs and nsfs.
  • A remaining action item is improving the documentation in exportfs.h to clarify why these methods are restricted, with hch offering to incorporate explanatory text into a revision if Amir does not take it on.
  • The patch is marked for stable backport via its Fixes: tags, addressing a retroactive issue introduced when file handle support was added to pidfs and nsfs.
