NFSD Signed Filehandles: Uninitialized Variable Warning on Patch 2/4

Summary

This week's activity on the "Add a key for signing filehandles" thread (patch 2/4 of Benjamin Coddington's kNFSD signed filehandle series) was limited to a single automated build warning from the kernel test robot. The broader discussion about this security enhancement unfolded extensively earlier in the week and is summarized in the cover letter thread summary.

Discussion Type

Bug fix / code quality issue — an uninitialized variable in the netlink handler for setting the filehandle signing key.

Prior Context (Brief)

Coddington's 4-patch series proposes adding Message Authentication Code (MAC) signing to NFS filehandles using siphash, preventing attackers from fabricating valid filehandles to bypass directory permission checks. Patch 2/4 specifically introduces the infrastructure for setting the signing key via netlink and the nfsctl filesystem. The series sparked extensive debate about threat models, netlink interface design, code layering, and alternative approaches (such as NeilBrown's proposal for 64-bit generation numbers). No formal acceptance or rejection occurred; Coddington committed to iterating on the design for v2.

This Week: Uninitialized Variable Warning from Kernel Test Robot

The kernel test robot reported a build warning in patch 2/4, which adds the nfsd_nl_fh_key_set_doit() netlink handler in fs/nfsd/nfsctl.c:

As reported by the kernel test robot:

"variable 'ret' is uninitialized when used here"

The warning occurs at line 2282 in nfsd_nl_fh_key_set_doit():

int ret;  /* declared at line 2260, never initialized */
...
trace_nfsd_ctl_fh_key_set((const char *)fh_key, ret);  /* uses uninitialized 'ret' */
return ret;  /* also returns uninitialized value */

The function declares int ret but never assigns it a value before using it in the trace call and as the return value. The robot noted:

"initialize the variable 'ret' to silence this warning"

This was detected during an x86_64-kexec build with clang 20.1.8 under W=1 (warnings-as-errors) mode.

Technical Significance

While this is a straightforward bug, it's notable because the function has multiple early return paths that all correctly return explicit error codes (-EINVAL, -EEXIST, -ENOMEM). The issue is that after the successful code path — where the key is allocated and stored — the function falls through to return ret without ever setting ret. The correct fix would be to either initialize ret = 0 at declaration or set ret = 0 before the trace call.

This type of automated testing feedback is typical during early patch review cycles and helps ensure code quality before merging. Notably, this thread (patch 2/4) saw a similar warning from the kernel test robot on patch 4/4 in a separate but related report — both highlighting format/initialization issues caught by clang's static analysis.

Status

The series remains under active development. Coddington will address this uninitialized variable warning along with other review comments (layering concerns, timing-safe comparison, mutex protection for key setting) in a v2 submission. The broader architectural debate about signed filehandles versus alternative approaches continues to inform the design direction.
