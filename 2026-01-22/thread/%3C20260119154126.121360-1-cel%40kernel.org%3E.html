NFSD SCSI Fencing v7: GETDEVICEINFO Fence Clearing and Refactoring, Reviewed by Hellwig

Summary

NFSD: SCSI Persistent Registration Fencing per Client with xarray — v7 Posted and Reviewed

Overview

This thread covers version 7 of the patch series "NFSD: Track SCSI Persistent Registration Fencing per Client with xarray," authored by Dai Ngo and Chuck Lever. This is a bug fix for the NFS server's pNFS block layout implementation, addressing redundant and failing fence operations when handling unresponsive clients.

Background: The Problem

The core issue arises in pNFS SCSI block layout deployments when an NFS client becomes unresponsive. As described in the patch cover letter [id://20260119154126.121360-1-cel@kernel.org]:

"When a client holding pNFS SCSI layouts becomes unresponsive, the server revokes access by preempting the client's SCSI persistent reservation key. A layout recall is issued for each layout the client holds; if the client fails to respond, each recall triggers a fence operation. The first preempt for a given device succeeds and removes the client's key registration. Subsequent preempts for the same device fail because the key is no longer registered."

In practical terms: when a layout recall triggers fencing on an unresponsive client, the server attempts to preempt the client's SCSI persistent reservation key. The first such operation succeeds, but subsequent recalls for other layouts on the same device attempt to fence again — and fail, because the key was already removed by the first preempt. This results in unnecessary error conditions and misleading log output.

This Week's Activity: v7 Posted and Reviewed

Patch Submission (January 19)

Chuck Lever posted version 7 on January 19th [id://20260119154126.121360-1-cel@kernel.org], building on the already-applied v6. The v7 changelog outlines two significant improvements:

"V7: . GETDEVICEINFO must clear existing fences . Refactor for separation of concerns"

The patch modifies three files with 81 lines of additions:

  • fs/nfsd/blocklayout.c (+72 lines): Core fencing logic with xarray tracking, including the new fence-clearing behavior in GETDEVICEINFO
  • fs/nfsd/nfs4state.c (+6 lines): xarray initialization and cleanup in client lifecycle
  • fs/nfsd/state.h (+3 lines): New cl_dev_fences field on nfs4_client

The mechanism works as follows: when the server issues a persistent registration key to a client, it creates an xarray entry at the device's dev_t index with a fenced flag initialized to 0. Before performing a fence via nfsd4_scsi_fence_client, the server checks this flag — if already set, the fence is skipped; otherwise, it sets the flag and proceeds with fencing. The xarray is destroyed when the client is released in __destroy_client.

Notable v7 enhancements:

  1. GETDEVICEINFO clears existing fences: This ensures that when a new device info request is processed, any stale fencing state from prior operations is cleared, preventing incorrect skip behavior for newly registered devices.
  2. Refactored for separation of concerns: The code has been reorganized to improve maintainability and clarity of the fencing logic.

Technical Significance for NFS Client Development

This fix has important implications for NFS server deployments using pNFS block layouts:

  1. Data integrity protection: SCSI persistent registration fencing is a critical mechanism for preventing data corruption when multiple clients access the same underlying block device. The fence operation ensures that only one client can interact with a device at a time during layout conflicts.

  2. Elimination of spurious errors: Without this fix, the server would generate repeated failure messages when attempting to fence an already-fenced device — noise that could obscure genuine problems in production environments.

  3. Correctness under concurrent recalls: When multiple layouts are held by an unresponsive client, each layout recall independently triggers fencing logic. The xarray-based tracking ensures idempotent fencing behavior regardless of how many times the operation is invoked for the same device-client pair.

  4. GETDEVICEINFO fence clearing (v7): The new requirement that GETDEVICEINFO clears existing fences ensures that when a client re-registers with the server, any stale fencing state from prior operations is properly reset — preventing incorrect skip behavior for newly registered devices.
