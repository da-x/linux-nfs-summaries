Case Folding v5: NFS Client fileattr_get and NFSD Dynamic Case Sensitivity Reporting Posted

Summary

Exposing Case Folding Behavior: v5 Series Posted — NFS Client and NFSD Enhancements for Cross-Platform Interoperability

Type: New feature / protocol enhancement (continued from prior weeks)

Prior Weeks Recap

Chuck Lever's 16-patch series "Exposing case folding behavior" has been under review since early January, progressing through v3 (January 12), v4 (January 14), and now v5. The series introduces a kernel-wide fileattr_get mechanism enabling filesystems to report their case sensitivity and case preservation characteristics, allowing NFSD, ksmbd, and NFS clients to accurately convey filename semantics across protocol boundaries. Key review feedback from prior weeks included struct layout optimization (packing flags into fa_xflags), FAT's nocase mount option edge case, and the renaming of case_preserving to case_nonpreserving. See prior summaries for full details.

This Week's Activity: v5 Series Posted

On January 16th, Chuck Lever posted version 5 of the series [id://20260116144616.2098618-1-cel@kernel.org], incorporating changes from prior review rounds and addressing open items. The cover letter outlines the motivation clearly:

"The Linux NFS community has a growing interest in supporting NFS clients on Windows and MacOS platforms, where file name behavior does not align with traditional POSIX semantics."

Lever highlighted a concrete interoperability problem: Windows-based NFS clients such as ms-nfs41-client "explicitly require servers to report FATTR4_WORD0_CASE_INSENSITIVE = TRUE for proper operation, a hard requirement for Windows client interoperability because Windows applications expect case-insensitive behavior."

He also emphasized the Linux NFS client's own benefit from this information:

"When a client detects a case-insensitive NFS share, negative dentry caching must be disabled (a lookup for 'FILE.TXT' failing shouldn't cache a negative entry when 'file.txt' exists) and directory change invalidation must clear all cached case-folded file name variants."

Changes Since v4

The v5 series addresses two specific items from prior review:

  • MSDOS nocase mount option: The FAT implementation now correctly observes the MSDOS nocase mount option.
  • New FS_XFLAGs for user API: New extended flags (FS_XFLAG_CASEFOLD and FS_XFLAG_CASENONPRESERVING) are defined for exposing case sensitivity information to userspace via the existing fa_xflags field.

Key Technical Components

1. VFS Infrastructure: file_kattr Extension (Patch 01/16)

The foundational patch [id://20260116144616.2098618-2-cel@kernel.org] adds two boolean fields — case_insensitive and case_nonpreserving — to struct file_kattr. These default to false (POSIX semantics: case-sensitive, case-preserving), allowing filesystems to set them only when behavior differs. Case sensitivity information is exported to userspace via the existing fa_xflags field using new FS_XFLAG_CASEFOLD and FS_XFLAG_CASENONPRESERVING flags.

2. Filesystem Implementations (Patches 02-13/16)

The series implements fileattr_get callbacks across twelve filesystems:

  • FAT/exFAT [id://20260116144616.2098618-3-cel@kernel.org], [id://20260116144616.2098618-4-cel@kernel.org]: Report case-insensitivity, with FAT now observing the nocase mount option.
  • NTFS3 [id://20260116144616.2098618-5-cel@kernel.org]: Reports case sensitivity based on NTFS configuration.
  • HFS/HFS+ [id://20260116144616.2098618-6-cel@kernel.org], [id://20260116144616.2098618-7-cel@kernel.org]: Report case sensitivity for Apple filesystems.
  • ext4 [id://20260116144616.2098618-8-cel@kernel.org]: Reports per-directory casefold settings.
  • XFS [id://20260116144616.2098618-9-cel@kernel.org]: Reports case sensitivity for XFS directories with case-insensitive collation.
  • CIFS [id://20260116144616.2098618-10-cel@kernel.org]: Reports case sensitivity based on the nocase mount option; always reports as case-preserving since SMB servers preserve filename case at rest.
  • NFS client [id://20260116144616.2098618-11-cel@kernel.org]: See detailed analysis below.
  • f2fs, vboxsf, ISO9660: Additional filesystem implementations.

3. NFS Client: fileattr_get for Case Sensitivity (Patch 10/16) — Critical for Re-export

The NFS client patch [id://20260116144616.2098618-11-cel@kernel.org] is particularly significant for NFS infrastructure. As Lever explains in the commit message:

"An NFS server re-exporting an NFS mount point needs to report the case sensitivity behavior of the underlying filesystem to its clients. Without this, re-export servers cannot accurately convey case handling semantics, potentially causing client applications to make incorrect assumptions about filename collisions and lookups."

The implementation exposes case sensitivity information that the NFS client already retrieves from servers during mount — via PATHCONF for NFSv3 or FATTR4_CASE_INSENSITIVE/FATTR4_CASE_PRESERVING attributes for NFSv4. NFSv2 mounts default to POSIX behavior since that protocol lacks PATHCONF support. The patch touches nine files across the NFS client codebase (client.c, inode.c, internal.h, nfs3proc.c, nfs3xdr.c, nfs4proc.c, proc.c, symlink.c, and include/linux/nfs_xdr.h), adding a new field to track case sensitivity state and registering the fileattr_get callback across directory, file, and symlink inode operations.

4. NFSD: Dynamic Case Sensitivity Reporting (Patches 14-15/16)

NFSv3 PATHCONF [id://20260116144616.2098618-15-cel@kernel.org]: The patch replaces the hard-coded MSDOS_SUPER_MAGIC check in nfsd3_proc_pathconf() with a dynamic query through ->fileattr_get. Previously, only FAT filesystems were recognized as case-insensitive; now any filesystem implementing the interface can report accurate behavior.

NFSv4 FATTR4 attributes [id://20260116144616.2098618-16-cel@kernel.org]: NFSD previously provided hard-coded responses indicating all exported filesystems are case-sensitive and case-preserving. The patch now queries the underlying filesystem's actual case sensitivity via nfsd_get_case_info() and returns accurate values, supporting per-directory settings for filesystems that allow mixing case-sensitive and case-insensitive directories within an export.

5. ksmbd Integration (Patch 16/16)

The series also updates the in-kernel SMB server [id://20260116144616.2098618-17-cel@kernel.org] to report filesystem case sensitivity via FS_ATTRIBUTE_INFORMATION, enabling consistent multi-protocol file serving environments.

Review Feedback This Week

Darrick J. Wong provided early review feedback on patch 01/16 [id://20260116162837.GX15551@frogsfrogsfrogs], raising two concerns:

"Hrm. If you're going to memset the file_kattr here, then you might as well remove the memset calls from fileattr_fill_*. It's not great that filesystems have to know that a 'fill_xflags' function assigns to more than just xflags."

He also questioned the structural design:

"Er... if you're encoding fs name handling qualities through FS_XFLAG_*, then filesystems can set them in fsx_xflags directly. No need for separate bitfields here."

These comments echo prior review discussions about struct layout optimization and whether case sensitivity flags should be packed into fa_xflags or maintained as dedicated fields.

Significance for NFS Client Development

This series is a major step forward for NFS client-server interoperability, particularly in multi-protocol environments:

  1. Windows/macOS NFS clients: Accurate case sensitivity reporting enables these clients to operate correctly without workarounds. As Lever noted, Windows-based NFS clients "explicitly require servers to report FATTR4_WORD0_CASE_INSENSITIVE = TRUE for proper operation."

  2. Linux NFS client caching correctness: When a Linux client detects a case-insensitive share, it can properly manage negative dentry caching and directory change invalidation — avoiding subtle bugs where lookups fail due to stale cache entries.

  3. Re-export scenarios: The NFS client's fileattr_get implementation enables NFSD to accurately report the case sensitivity of re-exported NFS mounts, a critical capability for file service proxies and multi-protocol gateways.

  4. Multi-protocol environments: As Lever observed, "Hammerspace servers and several other NFS server implementations operate in multi-protocol environments, where a single file service instance caters to both NFS and SMB clients. In those cases, things work more smoothly for everyone when the NFS client can see and adapt to the case folding behavior that SMB users rely on and expect."

Status and Outlook

The v5 series is now posted and under review. As confirmed in last week's discussion, the series will proceed through Christian Brauner's VFS tree rather than the NFSD subtree, with a target kernel version of v6.20 or later (v6.19 is closed to new features). Open review items include Darrick J. Wong's structural concerns about file_kattr layout and memset handling. The series has broad support across filesystem maintainers from prior rounds, suggesting it is on a strong path toward eventual merge.
