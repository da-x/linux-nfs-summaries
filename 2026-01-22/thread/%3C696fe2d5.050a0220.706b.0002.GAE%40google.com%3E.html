syzbot Reports NFS Server Task Hang in expkey_flush — nfsd_mutex Contention

Summary

syzbot Reports NFS Server Task Hang in expkey_flush — Lock Contention on nfsd_mutex

Type: Bug report (kernel fuzzer finding)

Overview

On January 20th, Google's syzkaller fuzzing bot reported a task hang in the NFS server (NFSD) subsystem syzbot. The report was filed against the upstream kernel tree at commit 983d014aafb1 and tagged with [nfs?], indicating syzbot's heuristic subsystem classification for NFS-related code. No human responses or patches were posted within this week's window.

Technical Analysis of the Hang

The report documents a severe concurrency issue involving multiple tasks blocked in uninterruptible sleep (state D) for over 143 seconds, all contending on the global nfsd_mutex. The call traces reveal three distinct code paths converging on this single lock:

Path 1: Export Key Cache Flush (expkey_flush)

One task hung while attempting to acquire nfsd_mutex inside expkey_flush():

__mutex_lock+0xc69/0x1ca0 kernel/locking/mutex.c:776
expkey_flush+0x20/0x90 fs/nfsd/export.c:250
write_flush.constprop.0+0x2af/0x3d0 net/sunrpc/cache.c:1550

This path was triggered by a write to the /proc/fs/nfsd/exports flush interface, which is used to force the NFS export cache to write out pending entries. The task held sb_writers#3 (superblock writer lock) and then attempted to acquire nfsd_mutex.

Path 2: NFS Server Thread Shutdown (nfsd_shutdown_threads)

Multiple tasks were blocked in nfsd_shutdown_threads() during filesystem unmount operations:

__mutex_lock+0xc69/0x1ca0 kernel/locking/mutex.c:776
nfsd_shutdown_threads+0x5b/0xf0 fs/nfsd/nfssvc.c:575
nfsd_umount+0x3b/0x60 fs/nfsd/nfsctl.c:1353
deactivate_locked_super+0xc1/0x1a0 fs/super.c:474

These tasks held the superblock's s_umount_key (exclusive unmount lock) and then attempted to acquire nfsd_mutex. The lock listing shows numerous syz-executor threads in this state, each holding both s_umount_key#53 and waiting on nfsd_mutex.

Path 3: Netlink Thread Configuration (nfsd_nl_threads_set_doit)

Additional tasks were blocked while attempting to configure NFS server thread counts via netlink:

__mutex_lock+0xc69/0x1ca0 kernel/locking/mutex.c:776
nfsd_nl_threads_set_doit+0x687/0xbc0 fs/nfsd/nfsctl.c:1596
genl_family_rcv_msg_doit+0x209/0x2f0 net/netlink/genetlink.c:1115

These tasks held the cb_lock (callback lock from netlink reception) and then attempted to acquire nfsd_mutex.

Path 4: Superblock Lock Contention (down_write)

One task was blocked acquiring a write-side superblock lock:

rwsem_down_write_slowpath+0x521/0x1310 kernel/locking/rwsem.c:1185
down_write+0x1d6/0x200 kernel/locking/rwsem.c:1591
super_lock+0x17d/0x3f0 fs/super.c:121
grab_super+0xab/0x420 fs/super.c:531
sget_fc+0x612/0xc20 fs/super.c:801

This task was attempting to mount a new NFS filesystem while the superblock lock was held by one of the unmount operations.

Lock Ordering and Deadlock Characteristics

The "locks held in the system" section reveals a complex web of interlocking dependencies. The critical observation is that nfsd_mutex serves as a global serialization point for multiple NFSD administrative operations — export cache flushing, thread shutdown during unmount, and netlink-based thread configuration — while each caller arrives holding different outer locks (sb_writers, s_umount_key, cb_lock).

The NMI backtrace confirms the system entered a soft lockup state (tainted [L]=SOFTLOCKUP), with CPU 0 idle in pv_native_safe_halt and CPU 1 running the hung-task watchdog.

Context: Recent NFSD Locking Changes

This report arrives amid significant recent activity in NFSD locking infrastructure. As noted in prior summaries, Chuck Lever's "Automatic NFSv4 state revocation on filesystem unmount" series (v2) explicitly addressed lock ordering around nfsd_mutex, with a change noted as:

"Hold nfsd_mutex while closing nfsd_files"

This prior work demonstrates that the NFSD maintainers are actively aware of and addressing locking complexities in this subsystem. The syzbot finding may represent either a pre-existing issue or a regression introduced by recent changes to the export cache flush path, thread shutdown sequence, or netlink control interface.

Significance for NFS Server Development

This bug report highlights several important concerns:

  1. Global mutex contention: The nfsd_mutex serves as a bottleneck for concurrent administrative operations on the NFS server. When multiple threads attempt to perform mount/unmount, thread configuration, and cache flush operations simultaneously — as syzkaller's fuzzing naturally induces — the system can enter a prolonged hung state.

  2. Interaction with filesystem lifecycle: The hang occurs during filesystem unmount (nfsd_umount), which is precisely the scenario that Chuck Lever's state revocation series aims to improve. The interplay between VFS superblock locks and NFSD's internal mutex needs careful attention.

  3. Netlink control plane safety: The nfsd_nl_threads_set_doit() path shows that netlink-based NFS server management can also participate in lock contention, expanding the surface area for concurrency bugs beyond traditional procfs interfaces.

  4. No reproducer available: As syzbot noted:

"Unfortunately, I don't have any reproducer for this issue yet."

This means developers will need to rely on the call traces and lock state dump provided in the report to diagnose the root cause.
