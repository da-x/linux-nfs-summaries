NFS EOF Page Pollution Fix: Patch Confirmed by NVIDIA Testing, Submitted Upstream for 6.18.x Stable

Summary

NFS EOF Page Pollution Fix: Patch Confirmed, Upstream Submission Complete

Summary

Type: Bug fix regression resolution (NFS client)

Overview

This week brought a positive resolution to the multi-week investigation into ext4 checksum corruption caused by the NFS client's "eof page pollution" protection fix. NVIDIA's testing team confirmed that Trond Myklebust's proposed race condition patch successfully eliminates the issue, and the fix has already been submitted upstream for inclusion in the 6.18.x stable kernels.

Background (Prior Weeks)

This thread traces back to early January when NVIDIA engineers reported that commit b1817b18ff20 ("NFS: Protect against 'eof page pollution'") caused intermittent ext4 directory checksum failures during boot of nested VMs. The setup involved qcow2 disk images stored on an NFSv4.2 share serving as backing storage for VMs running ext4 filesystems. Reverting the offending commits eliminated the issue, confirming causality.

Last week (ending 2026-01-15), Trond Myklebust proposed a targeted patch titled "NFSv4.2: Fix size read races in fallocate and copy offload" addressing a suspected race condition where the pre-operation file size was read before locking the inode and quiescing O_DIRECT writes — potentially causing nfs_truncate_last_folio() to overwrite valid file data.

This Week's Resolution

Successful Testing Confirmation

Mark Bloch from NVIDIA reported back after extensive testing of Trond's proposed patch:

We've been testing your patch for some time now and didn't hit the issue. Feel free to add Bar's tested by tag as she was the one that actually tested the fix. Thanks for looking into this.

He provided the formal tested-by attribution:

Tested-by: Bar Friedman bfriedman@nvidia.com

This confirmation validates that the race condition fix in NFSv4.2 fallocate and copy offload operations successfully resolves the ext4 checksum corruption observed in nested VM workloads — without requiring a rollback of the original eof page pollution protection itself.

Upstream Submission Already Completed

Trond Myklebust responded with important context about the patch's status:

Thank you very much for testing, Bar! I unfortunately already sent the patch upstream as it was clearly a necessary fix (even though it was not obvious to me that it would be sufficient to fix your reported problem). I'm therefore hoping it will hit the 6.18.x stable kernels soon.

This reveals two significant points:

  1. The patch was deemed independently necessary — Trond recognized the race condition as a genuine bug regardless of whether it explained NVIDIA's specific regression, demonstrating good engineering judgment in not waiting for external validation before submitting.

  2. Stable kernel backporting is expected — The fix is targeted for inclusion in 6.18.x stable kernels, which is critical for production systems affected by this issue.

Technical Significance

This resolution represents an important milestone in NFS client development:

  • The original eof page pollution fix (addressing xfstest generic/363) remains intact, preserving protection against data corruption when users mmap() beyond EOF and write into folios straddling the end-of-file boundary.

  • The regression was caused by a separate race condition in NFSv4.2 operations where size reads occurred before proper inode locking, leading nfs_truncate_last_folio() to act on stale size information and corrupt valid data.

  • The fix ensures proper ordering of inode locking relative to size reads in fallocate and copy offload paths, preventing data corruption while maintaining the original protection mechanism.

Conclusion

This thread demonstrates a successful collaborative debugging effort between NVIDIA's engineering team and the Linux NFS client maintainer. The issue was identified, a targeted fix proposed, validated through rigorous testing, and submitted upstream — all within a three-week timeframe. The resolution preserves both the original eof page pollution safeguard and corrects a subtle but critical race condition in NFSv4.2 operations, benefiting all users of dynamic file sizing workloads on NFS shares.
