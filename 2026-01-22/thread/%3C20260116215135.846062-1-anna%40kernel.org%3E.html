NFS: Make NFS v4.0 KConfig-urable (v1)

Summary

NFS: Make NFS v4.0 KConfig-urable (v1)

Anna Schumaker submitted a 14-patch series this week aimed at making NFS v4.0 support optional via Kconfig, as a first step toward eventual deprecation of the protocol version. The series introduces new source files prefixed with "nfs40" to isolate v4.0-specific code and promotes NFS v4.1 to be the default, always-enabled NFSv4 minor version.

Background and Motivation

The desire to deprecate NFS v4.0 originated from discussions at the October Bake-a-thon the previous year. In her cover letter, Anna wrote:

"A desire to deprecate NFS v4.0 came up as a discussion topic during the October Bake-a-thon last year. This patchset takes the first step by moving NFS v4.0 only code into new files prefixed with 'nfs40' and introducing a KConfig option to compile without NFS v4.0 support."

She also noted:

"At the same time, I promote NFS v4.1 to be the default NFSv4 minorversion included in the kernel to prevent the situation where we have NFS v4 enabled without any minor versions."

Anna acknowledged this was an initial effort and invited feedback on the approach:

"I'm sure I missed a bunch of stuff in nfs4proc.c that can be moved over to nfs40proc.c, but I figure I should get some eyes on this before going any farther incase I need to take a different approach somewhere." As stated in the cover letter.

Classification

This is a code refactoring and new feature effort — not a bug fix or protocol change. The series restructures the NFS client codebase to enable compile-time exclusion of NFS v4.0 support, while promoting NFS v4.1 as the baseline NFSv4 implementation.

Patch Series Overview

The 14-patch series touches 30 files with 881 insertions and 1,121 deletions, creating two new source files (nfs40client.c and nfs40proc.c) and a new header (nfs40.h). The patches fall into three broad categories:

1. Code Extraction (Patches 01–10)

The first ten patches systematically extract NFS v4.0-specific code from shared files (nfs4client.c, nfs4proc.c, nfs4state.c) into the new nfs40* files:

  • Patch 01 Move nfs40_call_sync_ops into nfs40proc.c: Creates nfs40.h and nfs40proc.c, moving the sync operations entry point.
  • Patch 02 Split out nfs40_reboot_recovery_ops into nfs40client.c: Creates nfs40client.c and moves reboot recovery operations (188 lines added to the new file).
  • Patch 03 Split out nfs40_nograce_recovery_ops into nfs40proc.c: Moves nograce recovery operations.
  • Patch 04 Split out nfs40_state_renewal_ops into nfs40proc.c: Moves state renewal operations.
  • Patch 05 Split out nfs40_mig_recovery_ops to nfs40proc.c: Moves migration recovery operations.
  • Patch 06 Move NFS v4.0 minor version ops into nfs40proc.c: Relocates the v4.0 minor version operations structure (106 lines to nfs40proc.c, 115 lines removed from nfs4proc.c).
  • Patch 07 Make NFS v4.0 operations static again: After extraction, the v4.0 functions can be made static since they're no longer referenced outside their new files.
  • Patch 08 Move nfs40_shutdown_client into nfs40client.c: Moves client shutdown logic.
  • Patch 09 Move nfs40_init_client into nfs40client.c: Moves client initialization.
  • Patch 10 Move NFS v4.0 pathdown recovery into nfs40client.c: Moves path-down recovery operations.

2. Architectural Refactoring (Patches 11–12)

These patches introduce structural changes to support the v4.0/v4.1+ separation:

  • Patch 11 Pass a struct nfs_client to nfs4_init_sequence(): Anna described this as having "No functional change" — it simply prepares for the next patch by passing struct nfs_client to nfs4_init_sequence(), enabling sequence slot operations to be differentiated per minor version.
  • Patch 12 Move sequence slot operations into minorversion operations: Moves sequence slot management (setup, teardown, free) into the minor version operations structure, allowing v4.0 and v4.1+ to have different implementations. This is a key architectural change enabling clean separation of compound/session semantics from basic v4.0 behavior.

3. Kconfig Integration (Patches 13–14)

The final two patches implement the compile-time configuration:

  • Patch 13 Add a way to disable NFS v4.0 via KConfig: Introduces NFS4_MIN_MINOR_VERSION as a parallel to NFS4_MAX_MINOR_VERSION, allowing the kernel to check whether NFS v4.0 has been compiled in and return an appropriate error if not.
  • Patch 14 Merge CONFIG_NFS_V4_1 with CONFIG_NFS_V4: The capstone patch. Anna explained:

"Compiling the NFSv4 module without any minorversion support doesn't make much sense, so this patch sets NFS v4.1 as the default, always enabled NFS version allowing us to replace all the CONFIG_NFS_V4_1s scattered throughout the code with CONFIG_NFS_V4."

This patch removes 368 lines and adds 35, eliminating CONFIG_NFS_V4_1 entirely in favor of making v4.1 the baseline when CONFIG_NFS_V4 is enabled.

Key Technical Arguments

The core architectural insight is that NFS v4.0 lacks several features present in v4.1+ (sessions, slots, compound operations with sequence frames). By extracting v4.0-specific recovery paths (reboot, nograce, migration, state renewal), client lifecycle management (init, shutdown, pathdown), and sequence slot operations into dedicated files, the codebase can cleanly conditionally compile v4.0 support.

The introduction of NFS4_MIN_MINOR_VERSION provides a symmetric counterpart to NFS4_MAX_MINOR_VERSION, enabling range-based checks for supported minor versions at runtime.

Discussion Status

This is the initial submission (v1) with no replies as of this week's cutoff. Anna explicitly invited community feedback on whether her approach was sound before proceeding further, indicating she anticipates additional v4.0 code may need extraction in a subsequent revision. A v2 of this series was noted in related thread searches, suggesting iteration is underway.

Conclusion

This series represents a significant architectural reorganization of the NFS client, laying groundwork for eventual NFS v4.0 deprecation. By making v4.1 the default and enabling compile-time exclusion of v4.0, distributions and embedded systems can reduce code footprint while modernizing their NFS client support. The approach is methodical — extracting code first, then adding configuration controls — minimizing risk of introducing regressions during the refactoring process.
