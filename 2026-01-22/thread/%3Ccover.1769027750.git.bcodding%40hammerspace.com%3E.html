nfs-utils Signed Filehandle Support: Userspace Patches v2 Under Review

Summary

nfs-utils Signed Filehandle Support: Userspace Patches v2 Under Review

Discussion Type

New feature — userspace support for signed NFS filehandles in nfs-utils, corresponding to kernel-side changes.

Overview

Benjamin Coddington submitted a 2-patch series this week providing the nfs-utils userspace components needed to enable signed filehandles in the kernel NFS server (kNFSD). This v2 submission corresponds with the kernel-side v2 changes and addresses feedback from the extensive review of the v1 patches last week.

The series enables administrators to:

  • Configure a secret key for signing filehandles via nfs.conf
  • Set the sign_fh export option on individual exports
  • Pass the hashed key to the kernel via netlink or nfsdfs

As Coddington explained in the cover letter:

"The secret key passed to the server is the first 128 bits of a sha1 hash of the contents of a file configured via the nfs.conf server section 'fh_key_file'. Exports that have the option 'sign_fh' set will cause the server to use this key to append an 8-byte siphash of the filehandle onto each filehandle."

Prior Context (Brief)

Last week, Coddington's v1 kernel patch series sparked extensive debate about signed filehandles — a security mechanism to prevent filehandle guessing attacks against NFS servers. Key concerns raised included:

  • Chuck Lever's skepticism about the threat model and layering violations in XDR code
  • Jeff Layton's suggestion to pass the fh_key as an optional attribute in the "threads" netlink operation rather than creating a new dedicated operation
  • NeilBrown's alternative approach of embedding per-filesystem UUIDs into generation numbers
  • Build warnings from the kernel test robot (uninitialized variable, format string mismatch)

Coddington committed to addressing these concerns in v2.

Changes Since v1

Coddington documented the changes:

  • fh_key hash is passed as an optional attr to threads verb
  • include missing hash_fh_key_file() function hunk
  • wording updates (thanks NeilBrown)

The first change directly addresses Jeff Layton's suggestion from last week to integrate the key into the existing "threads" netlink operation rather than creating a new one. The second fix addresses a missing code hunk that was apparently omitted from v1.

Patch Details

Patch 1/2: exportfs — Add support for export option sign_fh

This patch adds the sign_fh export option to nfs-utils, allowing administrators to flag individual exports for filehandle signing:

"If configured with 'sign_fh', exports will be flagged to signal that filehandles should be signed with a Message Authentication Code (MAC)."

The patch touches four files in nfs-utils, adding the export flag definition and parsing support.

Patch 2/2: nfsdctl/rpc.nfsd — Add support for passing encrypted filehandle key

This patch implements the userspace infrastructure for key management:

"If fh-key-file=<path> is set in the nfsd section of nfs.conf, the 'nfsdctl autostart' command will hash the contents of the file with libuuid's uuid_generate_sha1 and send the first 16 bytes into the kernel via NFSD_CMD_FH_KEY_SET."

The patch creates a new support/nfs/fh_key_file.c module (80 lines) for hashing the key file, and modifies both nfsdctl and rpc.nfsd to read the configured key file and transmit it to the kernel. The series touches 15 files with 179 insertions and 10 deletions.

Review Feedback

Jeff Layton provided a brief but constructive review of patch 1/2:

"Side note: it would be good to convert nfs-utils to use UAPI header for this instead of relying on a separate copy in the tree."

He noted that nfs-utils currently maintains its own copy of export flag definitions rather than using the kernel's UAPI headers, which could lead to synchronization issues. Layton concluded positively:

"Looks good overall though."

No other review comments were posted this week. The thread remains open for further discussion and critique.

Technical Significance

This series is a critical piece of the signed filehandle security enhancement. While the kernel-side patches implement the actual signing and verification logic, these nfs-utils changes are what make the feature usable in practice — they provide the administrative interface for configuring which exports should have signed filehandles and how to supply the signing key.

The adoption of Jeff Layton's suggestion to pass the key as an optional attribute to the "threads" netlink operation represents a cleaner design compared to v1, avoiding the creation of a new dedicated netlink operation. This aligns with the principle of minimizing interface surface area while maintaining separation of concerns.

Status

The series is under review with no formal acceptance or rejection yet. Jeff Layton's positive feedback ("Looks good overall though") suggests the patches are in good shape, pending resolution of his UAPI header suggestion. The corresponding kernel v2 patches have been posted separately and are also under review.
