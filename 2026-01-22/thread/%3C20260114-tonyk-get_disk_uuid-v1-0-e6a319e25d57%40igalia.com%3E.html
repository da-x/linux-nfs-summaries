overlayfs: uuid=off Extended for Cross-Filesystem SteamOS Use Case

Summary

Summary

This week's activity continued the discussion from the prior week regarding André Almeida's rejected 3-patch series to support btrfs cloned images and overlayfs origin file handles via get_disk_uuid(). The focus shifted from architectural debates about repurposing exportfs infrastructure to a more practical exploration of existing overlayfs mechanisms — specifically the uuid=off mount option — as a potential solution for the SteamOS A/B partitioning use case.

Background (Brief)

Last week, Almeida's series was rejected by Christoph Hellwig, who argued that get_uuid() serves a specific pNFS block layout purpose and should not be spread further. The consensus was that the fix belongs in btrfs itself, not overlayfs or exportfs. Amir Goldstein questioned whether overlayfs with index was even appropriate for the SteamOS scenario, noting a similar precedent with squashfs and OpenWRT that led to the uuid=off mount option.

Key Technical Arguments This Week

Christoph Hellwig: Persistent UUIDs Are Still the Right Answer

Hellwig reiterated his position early in the week:

"It sounds like the 'clones' really need different persistent uuids. Or do you also have a requirement that the two images have the same ID, which would require a noouid-like option and extremely careful handling." [id://20260116093643.GA23235@lst.de]

Amir Goldstein: Probing the SteamOS Use Case

Amir sought to understand the exact overlayfs configuration being used:

"Please describe the exact overlayfs setup and specifically, is it multi lower or single lower layer setup? What reason do you need the overlayfs index for? Can you mount with index=off which should relax the hard requirement for match with the original lower layer uuid." [id://CAOQ4uxi988PutUi=Owm5zf6NaCm90PUCJLu7dw8firH8305w-A@mail.gmail.com]

André Almeida: SteamOS Setup Details

Almeida clarified the configuration, CC'ing SteamOS developers:

"The setup has a single lower layer. This is how the mount command looks like: mount -t overlay -o "lowerdir=${DEV_DIR}/etc,upperdir=${DEV_DIR}/var/lib/overlays/etc/upper,workdir=${DEV_DIR}/var/lib/overlays/etc/work" none "${DEV_DIR}/etc" They would rather not disable index, to avoid mounting the wrong layers and to avoid corner cases with hardlinks." [id://33c1ccbd-abbe-4278-8ab1-d7d645c8b6e8@igalia.com]

Amir Goldstein: The uuid=off Option — But With a Catch

Amir pointed to an existing mechanism designed precisely for this scenario:

"See mount option uuid=off, created for this exact use case... the mount option uuid=off can be used to replace UUID of the underlying filesystem in file handles with null, and effectively disable UUID checks. This can be useful in case the underlying disk is copied and the UUID of this copy is changed." [id://CAOQ4uxgCM=q29Vs+35y-2K9k7GP2A2NfPkuqCrUiMUHW+KhbWw@mail.gmail.com]

However, he noted a critical limitation: uuid=off only works when all lower/upper/work directories are on the same filesystem. He admitted uncertainty about why this restriction exists:

"TBH, I am trying to remember why we require upper/work to be on the same fs as lower for uuid=off,index=on and I can't remember." [id://CAOQ4uxgCM=q29Vs+35y-2K9k7GP2A2NfPkuqCrUiMUHW+KhbWw@mail.gmail.com]

André Almeida: Cross-Filesystem Complication

Almeida revealed the dealbreaker for uuid=off:

"Actually they are not in the same fs, upper and lower are coming from different fs', so when trying to mount I get the fallback to uuid=null. A quick hack circumventing this check makes the mount work." [id://75a9247a-12f4-4066-9712-c70ab41c274f@igalia.com]

He asked whether this restriction could be lifted:

"If you think this is the best way to solve this issue (rather than following the VFS helper path for instance), please let me know how can I safely lift this restriction, like maybe adding a new flag for this?" [id://75a9247a-12f4-4066-9712-c70ab41c274f@igalia.com]

Amir Goldstein: Patch Tested and Ready for 7.0

By week's end, Amir had tested a patch addressing the cross-filesystem uuid=off limitation:

"Andre, I tested the patch and it looks good on my side. If you want me to queue this patch for 7.0, please let me know if it addresses your use case." [id://CAOQ4uxg6dKr4XB3yAkfGd_ehZkBMcoNHiF5CeB9=3aca44yHRg@mail.gmail.com]

Evolution of the Discussion

The discussion evolved significantly from last week's architectural debate:

  1. Jan 16 morning: Hellwig and Amir independently pushed back on the original approach, with Hellwig reiterating his preference for persistent UUIDs in btrfs and Amir probing the actual use case details.

  2. Jan 16 afternoon: Almeida clarified the SteamOS overlayfs setup (single lower layer, index enabled). Amir identified uuid=off as an existing mechanism designed for this exact scenario — originally created by Pavel Tikhomirov for Virtuozzo container disk copying. However, Amir noted it requires all layers on the same filesystem.

  3. Jan 19: Almeida revealed the cross-filesystem complication: upper and lower are on different filesystems, causing uuid=off to fall back to normal behavior. He asked whether this restriction could be lifted.

  4. Jan 20–22: Amir tested a patch that appears to address the cross-filesystem limitation and offered to queue it for kernel 7.0.

Final Conclusions

This week marked a significant pivot from last week's rejected architectural approach toward a more pragmatic solution:

  1. The uuid=off mount option is the preferred path forward. Rather than repurposing exportfs infrastructure or modifying btrfs, the discussion converged on extending overlayfs's existing uuid=off mechanism to support cross-filesystem setups.

  2. A patch has been tested and is ready for inclusion. Amir Goldstein confirmed he tested a patch addressing the same-filesystem restriction of uuid=off and offered to queue it for kernel 7.0, pending confirmation from Almeida that it addresses the SteamOS use case.

  3. The original get_disk_uuid() approach remains rejected. Hellwig's position that the fix belongs in btrfs (assigning persistent UUIDs to cloned images) was not revisited this week; instead, the focus shifted to solving the problem at the overlayfs layer with minimal infrastructure changes.

  4. This is a bug fix / feature extension for overlayfs, not an NFS client change per se, though it touches on file handle semantics that are relevant to NFS exports and the broader exportfs subsystem.

Classification

Type: Bug fix / Feature extension (overlayfs uuid=off support for cross-filesystem setups)

NFS Client Relevance: Indirect — while not an NFS client change, the discussion touches on file handle encoding semantics that are foundational to NFS exports and the exportfs subsystem. The get_uuid() infrastructure originally served pNFS block layout, and Hellwig noted earlier that "encoding the uuid into the file handle in the kernel is the right thing for NFS as well."
