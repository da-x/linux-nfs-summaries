ms-nfs41-client Jan 19 Release: ADS, Server-Side Copy, and Sparse File Support Announced

Summary

ms-nfs41-client Windows Driver Binaries: January 19, 2026 Release Announcement

Summary

This week's activity on this thread consisted of a single message in which Martin Wege forwarded and promoted an updated announcement from Roland Mainz regarding new test binaries for the ms-nfs41-client, an open-source NFSv4.2/NFSv4.1 filesystem client driver for Windows 10/11 and Windows Server 2019/2022/2025 Martin Wege, 2026-01-20.

Prior Weeks Recap

A similar announcement was cross-posted to linux-nfs on January 12th (see prior summary), requesting interoperability feedback from the Linux NFS community. The January 19th release represents a significant update with numerous new features and bug fixes built on git commit #e2d33638f6193fb84b32d6db194f1ba87c41aaba.

Nature of the Discussion

This thread is not about Linux kernel NFS client development or bug fixes. Instead, it serves as a cross-post to linux-nfs requesting interoperability feedback from the Linux NFS community when using their Windows-based NFS client against Linux NFS servers. Wege reiterated:

"Please test the binaries. The NFSv4.2/4.1 client is for Windows 10/11 ARM64+AMD64+x86 and Windows Server 2019+2022+2025/AMD64, but Interoperability feedback with NFSv4.1/NFSv4.2 servers based on Linux 6.6+ LTS and 6.19+ would be great."

Key Features Highlighted in the Announcement

Roland Mainz's announcement outlined a substantial set of new features and bug fixes in the Windows NFS client driver, including:

  • Windows Alternate Data Streams (ADS) support via NFS named attributes (create, read/write, lock/unlock, sparse streams, rename, copy, clone, delete)
  • Server-side copy acceleration for Windows file copy operations (xcopy.exe, cmd.exe copy, MS Explorer) using NFSv4.2 COPY and block cloning
  • Sparse file support with hole/data range enumeration, punching holes, etc. (requires NFSv4.2 server { SEEK, ALLOCATE, DEALLOCATE })
  • Bug fixes for FreeBSD NFS server compatibility
  • Fixed issues probing sparse files when using the nfs-ganesha NFS server
  • Support for Windows Server 2025, ARM64 architectures (native aarch64 kernel module), and various protocol enhancements
  • SRVOpen collapsing to save open/close round trips to the NFS server
  • Extended Create Parameters (ECP QUERY_ON_CREATE, QoCFileStatInformation, QoCFileLxInformation) support
  • ACL setting at file creation time
  • Case-insensitive filesystem support (e.g., Windows Server NTFS)
  • Storage32-API support enabling use of .msi installer files on NFS filesystems
  • Illumos, Solaris 11.4, and Windows Server 2022 NFSv4.1 server support

Mainz emphasized that certain features are particularly notable:

"Windows Alternate Streams (Win32 streams) support was added (create, r/w, lock/unlock, sparse streams, rename, copy, clone, delete, ...), xcopy.exe/cmd.exe copy/MS Explorer file copy acceleration via NFS server side copies and copy-by-block-cloning are IMO the most interesting new features (cloning now works with FreeBSD 14.3/15.0 nfsd and Linux nfsd exporting btrfs&xfs filesystems, server side copy with FreeBSD+Linux with all filesystems), because it's 'on' by default for all Windows 11 applications which copy files"

Relevance to Linux NFS Development

While this announcement does not involve changes to the Linux kernel NFS client or server code, it is relevant to the broader NFS ecosystem. The ms-nfs41-client project's improvements in interoperability with Linux NFS servers — particularly regarding NFSv4.2 features like CLONE, SEEK, DEALLOCATE, and named attributes — may inform future compatibility testing and protocol refinement efforts within the Linux NFS subsystem.

Notably, this release coincides with Chuck Lever's ongoing work on case folding behavior exposure (see related thread), which explicitly aims to improve interoperability with Windows-based NFS clients like ms-nfs41-client that "explicitly require servers to report FATTR4_WORD0_CASE_INSENSITIVE = TRUE for proper operation."

No technical arguments or debates occurred in this thread; it was purely an informational cross-post requesting community participation in interoperability testing.
