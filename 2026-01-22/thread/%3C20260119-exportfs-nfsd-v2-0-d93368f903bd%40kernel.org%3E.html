Requiring Explicit Opt-In for NFS Export Support (EXPORT_OP_STABLE_HANDLES)

Summary

Jeff Layton's 31-Patch Series: Requiring Explicit Opt-In for NFS Export Support

Jeff Layton posted version 2 of a large 31-patch series (PATCH v2 00/31) introducing a new EXPORT_OP_STABLE_HANDLES flag that filesystems must explicitly set to be eligible for export via nfsd. This is a protocol-level infrastructure change — not a client-facing feature or bug fix per se, but a foundational hardening of the NFS server (nfsd) export path to prevent future regressions where unsuitable filesystems could inadvertently be exported.

Background and Motivation

Historically, nfsd treated the mere presence of struct export_operations as an indicator that a filesystem was exportable via NFS. Over time, many filesystems grew export operations solely for local filehandle support (e.g., for overlayfs or cgroup management), even though their filehandles are not stable across reboots — a hard requirement for NFS clients. As Layton explained:

"The main only place I found where this was an issue today is cgroupfs, which sane people don't export anyway. So, I don't see this as addressing a major problem that we have today. Rather, this patchset ensures that new filesystems that are added in the future make export eligibility via nfsd a deliberate step, rather than something they've inadvertently enabled just by adding filehandle support."

The series adds the flag to 27 existing filesystems (tmpfs, ext4, ext2, erofs, xfs, ceph, btrfs, fuse, overlayfs, and many others), enforces it in check_export(), and converts debug printks to tracepoints.

Key Technical Discussions

1. Definition of "Stable Handles" — Documentation Clarity

The most substantive discussion centered on precisely defining what EXPORT_OP_STABLE_HANDLES means. Christoph Hellwig proposed a detailed rewording for the documentation:

"This filesystem provides filehandles that are stable across the lifetime of a file. A file in this context is an instantiated inode reachable by one or more file names, or still open after the last name has been unlinked. Reuses of the same on-disk inode structure are considered new files and must provide different file handles from the previous incarnation."

Jan Kara endorsed this clarification but raised an important edge case:

"I'd note that fat or shmem (which are both exportable) satisfy this only with reasonably high probability as they use get_random_u32() for initializing their i_generation but I guess it's as good as it gets for them."

Hellwig pushed back further on FAT specifically:

"fat on the other hand looks broken, as it also set a new generation when reading inodes from disk. So I don't think fat should be nfs exportable, even if the export ops predate other uses."

This opens a potential follow-up issue for v3 regarding whether FAT should retain its export eligibility.

2. EXPORT_OP_NOLOCKS Documentation Improvement

Christoph Hellwig found the existing EXPORT_OP_NOLOCKS documentation insufficient:

"I'm not sure this is very useful. It really needs to document what locking semantics nfs expects, because otherwise no reader will know if they set this or not."

Layton responded with progressively refined documentation text, ultimately settling on a version that explained POSIX lock recovery semantics and the grace period interaction. Neil Brown reviewed favorably but added an interesting observation:

"It reminds me that for true NFS compatibility the fs shouldn't allow local locks (or file opens!) until the grace period has passed. I don't think any local filesystems enforce that."

Layton acknowledged this as a theoretical concern but deemed it impractical to address given the demand-driven nature of mountd upcalls:

"Yeah, I don't see us ever doing that. It'd be a tricky chicken-and-egg problem, given the demand-driven way that the mountd upcalls work today."

3. Tracepoint Patch Deferred

Chuck Lever reviewed the final patch converting dprintk() calls in check_export() to tracepoints, noting:

"'Twould be nice to report the namespace or client address that was making the failing request, but maybe that information is not available in check_export."

Layton decided to defer this patch entirely for v3:

"Given that we're still haggling over the flag name and semantics, lets drop this patch from the series for now. Once the other bits are settled, I'll respin the tracepoint patches on top."

He also caught a leftover dprintk() call he had missed:

"Doh! I left the above dprintk() in -- fixed in tree."

4. Minor Review Feedback

Amir Goldstein provided reviews for overlayfs and fuse patches, and noted a typo ("perisistent" → "persistent") in the patch description. Chuck Lever suggested improving the comment style in check_export() to avoid the ambiguous royal "we."

Conclusions

  • Layton plans to adopt Christoph Hellwig's improved documentation wording for EXPORT_OP_STABLE_HANDLES in v3.
  • The tracepoint patch (31/31) is deferred until the core semantics are settled.
  • FAT's export eligibility may be reconsidered based on Hellwig's analysis that its generation handling appears broken for NFS stability requirements.
  • The series received Reviewed-by tags from Amir Goldstein, Chuck Lever, Jan Kara, and Neil Brown on various patches.

This series represents a proactive infrastructure improvement to the nfsd server side, ensuring future filesystems must explicitly opt into NFS export support rather than inheriting it by default. While not addressing an urgent client-side bug, it strengthens the correctness guarantees of NFS filehandle stability — a foundational concern for NFS client reliability.
