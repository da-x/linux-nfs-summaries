NFS: FAT Exception and Handle Semantics Clarified in Opt-In Export Debate

Summary

NFS: File Handle Semantics Debate Continues — FAT Exception and Uniqueness vs. Persistence Clarified

Summary

Type: Hardening / bug fix initiative (continued from prior weeks)

Prior Weeks Recap

Jeff Layton's 29-patch series [PATCH 00/29] fs: require filesystems to explicitly opt-in to nfsd export support has been the subject of an intense multi-week debate. The core proposal introduces a flag (EXPORT_OP_STABLE_HANDLES) requiring filesystems to explicitly declare their suitability for NFS export, preventing problematic filesystems like cgroupfs from being silently exported with broken behavior. Last week's summary covered extensive disagreements over naming (STABLE_HANDLES vs. SUPPORTS_NFS_EXPORT vs. UNIQUE_HANDLES), the scope of the flag (NFS-specific vs. general file handle semantics), and Christian Brauner's hard line that pseudo-filesystems must never be exported regardless of handle quality. By week's end, Jeff Layton appeared to be reconsidering the approach, suggesting a potential LSF discussion and deferring to Amir Goldstein's simpler patch in the near term.

This Week's Activity: Narrow Exchange on FAT and Handle Semantics

This week saw only two messages in this thread, both on January 21st, representing the tail end of the debate between Christoph Hellwig and Jeff Layton. The discussion narrowed to a concrete technical question: which filesystems actually violate file handle semantics, and what can be done about them?

Key Technical Arguments

1. FAT Identified as a Notable Exception

Christoph Hellwig highlighted FAT as an outlier among "real" filesystems regarding handle stability [id://aXDm8FPPOHs04w9m@infradead.org]:

"fat seems to be an exception as far as the 'real' file systems go. And it did sound to me like some of the synthetic ones had similar issues."

Jeff Layton confirmed FAT's problematic status, explaining that the filesystem uses generic_encode_ino32_fh and lacks stable inode numbers:

"Not sure what we can do about FAT without changing the filehandle format in some fashion. The export ops just use generic_encode_ino32_fh, and FAT doesn't have stable inode numbers."

He noted that the existing "nostale" operations only work in read-only mode, creating a practical dilemma:

"We can't reasonably stop exporting FAT (even with all of its issues), and it in no way meets the definition of persistent or unique handles."

This represents a significant challenge for any opt-in mechanism: FAT is widely used but fundamentally lacks the handle quality properties that the series aims to enforce.

2. NFSv4 Specification Distinction: Persistence vs. Uniqueness

Jeff Layton clarified an important semantic distinction from the NFSv4 specification, distinguishing between two separate handle qualities [id://3210d04fa2c0b1f4312d10506cac30586cb49a3c.camel@kernel.org]:

"The spec also has the concept of uniqueness. There is an attribute for that: 5.8.1.10. Attribute 9: unique_handles — TRUE, if two distinct filehandles are guaranteed to refer to two different file system objects."

He further explained:

"Persistence has more to do with being non-volatile... In this case, the filesystems we're most concerned about do not provide uniqueness, but do provide persistence."

This distinction is critical for understanding the actual problem space. Filesystems like cgroupfs may have stable (persistent) handles that don't change during a mount session, but they lack uniqueness — handles can be reused across reboots, causing clients to access wrong files. FAT, by contrast, lacks even stability in its current implementation.

3. Hellwig's Skepticism About Exposing Problematic Filesystems

Christoph Hellwig questioned whether exporting certain filesystems should be permitted at all [id://aXDm8FPPOHs04w9m@infradead.org]:

"Do we even want to provide access to them?"

He acknowledged that userland NFS servers cannot be blocked by kernel-side restrictions, but argued that fixing the underlying handle semantics would benefit all consumers:

"Then again fixing the problem that some handles did not fulfill the long standing (but not documented well enough) semantics probably is a good fix on it's own."

4. Layton's Proposed Alternative: Fix Filesystems Rather Than Block Them

Jeff Layton proposed an alternative approach to the opt-in mechanism — rather than blocking problematic filesystems from export, fix them to generate unique handles [id://3210d04fa2c0b1f4312d10506cac30586cb49a3c.camel@kernel.org]:

"The point would be that there would be no need to flag them, since all filehandles would then meet the technical definition of unique and persistent (modulo FAT of course)."

This approach would use mechanisms like random i_generation values to prevent handle reuse across reboots, effectively solving the uniqueness problem at the filesystem level rather than through an export-time gate.

5. Agreement on Broader Scope Beyond nfsd

Both participants converged on the view that improving file handle quality benefits more than just nfsd [id://3210d04fa2c0b1f4312d10506cac30586cb49a3c.camel@kernel.org]:

"Agreed. We should try to ensure uniqueness and persistence in all filehandles both for nfsd and userland applications."

This aligns with Hellwig's earlier insistence that the flag has userspace implications beyond NFS, including statx and other applications relying on traditional file handle semantics.

Evolution of the Discussion

The thread's trajectory this week represents a narrowing from the broad philosophical debate of prior weeks to concrete technical questions:

  1. Prior weeks: Heated debate over naming, scope, maintainer rights, and whether pseudo-filesystems should ever be exported.
  2. This week: Focused discussion on which specific filesystems have handle quality issues (FAT identified as a standout), the NFSv4 spec's distinction between persistence and uniqueness, and whether fixing filesystems is preferable to blocking them.

The tone was notably more technical and less contentious than the prior week's exchanges, suggesting participants were moving toward practical resolution.

Final Conclusions

This sub-thread ended without a definitive resolution on the overall approach, but with several important clarifications:

  1. FAT remains an unsolved problem: FAT cannot meet the requirements for unique or persistent handles without fundamental changes to its filehandle format — a significant obstacle for any opt-in mechanism.

  2. Persistence ≠ Uniqueness: The NFSv4 specification's distinction between these two qualities helps frame the actual issues. Most problematic filesystems lack uniqueness (handle reuse across reboots) rather than persistence (handles changing during a session).

  3. Two potential paths forward: Either block problematic filesystems via an opt-in flag, or fix the filesystems to generate unique handles. Both approaches have merit and may be complementary.

  4. Broader consensus on quality improvement: Both Hellwig and Layton agreed that improving file handle semantics benefits all consumers — nfsd, userland NFS servers, and other applications using file handle syscalls.

Significance for NFS Client Development

While this series primarily targets the NFS server (nfsd), the implications for NFS clients are substantial:

  • Preventing silent data corruption: When filesystems like cgroupfs export non-unique handles, NFS clients may access wrong files after a reboot without any error indication — a critical bug that this hardening effort aims to prevent.
  • FAT export reliability: FAT's lack of stable inode numbers means exported filehandles can become stale within a single mount session, leading to STALE errors for NFS clients. Any solution must address this case specifically.
  • Re-export scenarios: The NFS client's own handle quality matters when a Linux NFS server re-exports an NFS mount point, as the underlying filesystem's handle semantics propagate through the chain.

The broader discussion about file handle uniqueness and persistence will ultimately affect how NFS clients cache filehandles, handle stale-handle errors, and manage directory change invalidation — all critical aspects of client-side correctness.
