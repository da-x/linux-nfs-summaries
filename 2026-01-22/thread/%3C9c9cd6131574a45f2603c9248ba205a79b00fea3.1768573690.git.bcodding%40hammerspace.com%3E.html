NFSD Signed Filehandles: Build Warning on Patch 4/4

Summary

This week's activity on the "NFSD: Sign filehandles" thread (patch 4/4 of Benjamin Coddington's 4-patch series) was limited to a single automated build warning from the kernel test robot. The broader discussion about signed filehandles — a security enhancement to prevent filehandle guessing attacks against NFS servers — unfolded extensively in prior weeks and is summarized in the cover letter thread summary.

Prior Context (Brief)

Coddington's 4-patch series proposes adding Message Authentication Code (MAC) signing to NFS filehandles using siphash, preventing attackers from fabricating valid filehandles to bypass directory permission checks. The series sparked extensive debate about threat models, netlink interface design, code layering, and alternative approaches (such as NeilBrown's proposal for 64-bit generation numbers). No formal acceptance or rejection occurred; Coddington committed to iterating on the design for v2.

This Week: Build Warning from Kernel Test Robot

The kernel test robot reported a format string mismatch warning in patch 4/4, which implements the core signing logic in fs/nfsd/nfsfh.c:

As reported by the kernel test robot:

"format specifies type 'unsigned long' but the argument has type 'unsigned int'"

The warning occurs at line 162 in fh_append_mac():

pr_warn("NFSD: unable to sign filehandles, fh_size %lu would be greater"
        " than fh_maxsize %d.\n", fh->fh_size + sizeof(hash), fhp->fh_maxsize);

The issue is that fh->fh_size (an unsigned int) combined with sizeof(hash) produces an unsigned int, but the format specifier %lu expects an unsigned long. The robot suggested using %u instead of %lu.

This was detected during a hexagon-allmodconfig build with clang 17.0.6 under W=1 (warnings-as-errors) mode.

Technical Significance

While minor, this type of format string mismatch can lead to undefined behavior on architectures where unsigned int and unsigned long differ in size. The fix is straightforward — either cast the expression to unsigned long or change the format specifier to %u. This kind of automated testing feedback is typical during early patch review cycles and helps ensure code quality before merging.

Status

The series remains under active development. Coddington will address this warning along with other review comments (layering concerns, timing-safe comparison, mutex protection) in a v2 submission. The broader architectural debate about signed filehandles versus alternative approaches (per-filesystem UUIDs in generation numbers, attack detection mechanisms) continues to inform the design direction.
