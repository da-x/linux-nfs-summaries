nfsd: Block Export of Special Kernel Filesystems (v2)

Overview

This thread is a bug fix addressing the risk of NFS daemon (nfsd) inadvertently exporting special kernel filesystems — specifically pidfs and nsfs. These filesystems recently gained file handle encode/decode support via name_to_handle_at(2)/open_by_handle_at(2), but their custom ->open() and ->permission() export operations are not respected by nfsd, making them unsuitable for NFS export.

This is a continuation of the discussion from last week's v1 patch (see prior summary). Amir Goldstein submitted v2 on January 22, addressing feedback from Christoph Hellwig regarding documentation and code structure.

Key Technical Arguments

The Fix

Amir Goldstein submitted v2 of the patch, which prevents nfsd from exporting any filesystem that implements custom ->open() or ->permission() export methods. The rationale:

"These special kernel filesystems have custom ->open() and ->permission() export methods, which nfsd does not respect and it was never meant to be used for exporting those filesystems by nfsd."

The patch carries two Fixes: tags targeting the commits that introduced file handle support to pidfs (b3caba8f7a34a) and nsfs (5222470b2fbb3), indicating it should be backported to stable kernels.

Changes Since v1

Amir addressed the primary feedback from last week's review cycle:

"Most of the stakeholders approved the approach in v1 and only comments were regarding lack of documentation for the new incompatible methods."

Key improvements in v2 include:

  • Use of a helper function exportfs_may_export() — replacing the inline check with a dedicated helper, as suggested by hch's earlier feedback about naming conventions.
  • Minimal documentation added to Documentation/filesystems/nfs/exporting.rst and include/linux/exportfs.h, clarifying that ->open() and ->permission() methods are for open_by_handle(2) only and not compatible with nfsd.
  • Reviewed-by tags from NeilBrown and Jeff Layton were added.

Amir noted the limits of his documentation effort:

"I did my best to add minimal documentation to express the fact that those methods are not compatible with nfsd and remote filesystem export in general."

He also acknowledged that broader documentation about new uses of export_operations beyond their original NFS export purpose was:

"outside the scope of this patch and frankly, outside the reach of my documentation skills..."

Christoph Hellwig's Response

Christoph Hellwig responded on January 23 (just outside the week window but part of this thread), expressing continued difficulty in understanding the custom export methods:

"As last time I'd be happy to help write documentation, but even after looking at the methods, their documentations and the commits adding them I do not understand them. So getting an explanation from Christian would be really helpful to move forward here."

He also noted a technical observation about the nsfs implementation:

"Btw, the nsfs ->open method seems identical to the default."

Additionally, hch raised a concern about audit message generation in may_decode_fh():

"may_decode_fh actually does a lot more things if the capable check fails. (btw, shouldn't that use (ns_)capable_noaudit to not generate audit messages?)."

Evolution of the Discussion

The discussion has evolved from v1 (last week) through v2 (this week) as follows:

  1. v1 received broad approval for the core fix but was critiqued for insufficient documentation of why ->open() and ->permission() are incompatible with nfsd.
  2. v2 incorporated a helper function (exportfs_may_export()), added minimal documentation, and secured Reviewed-by tags from NeilBrown and Jeff Layton.
  3. Christoph Hellwig's follow-up indicates that while the patch is technically sound, deeper clarification from Christian Brauner (the original author of pidfs/nsfs file handle support) would help with full documentation.

Final Conclusions

  • The core fix is broadly supported: blocking NFS export of filesystems with custom ->open()/->permission() export ops is viewed as a necessary safeguard for pidfs and nsfs.
  • The patch received Reviewed-by from NeilBrown and Jeff Layton.
  • Remaining work includes deeper documentation of the export_operations API, potentially requiring input from Christian Brauner to fully explain the design rationale.
  • The patch is marked for stable backport via its Fixes: tags, addressing a retroactive issue introduced when file handle support was added to pidfs and nsfs.
