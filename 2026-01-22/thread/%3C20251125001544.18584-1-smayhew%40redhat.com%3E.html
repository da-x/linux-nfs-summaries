NFS Client Delegation Control: Sysfs Knobs vs Open Flags Debate Rekindled

Summary

Discussion type: New feature / design exploration (NFS client delegation control mechanism)

Overview

This thread continues a multi-month discussion about providing administrators and applications with fine-grained control over NFS delegations — a feature that can cause operational headaches when bugs arise or troubleshooting is needed. The original RFC patch from Scott Mayhew proposed sysfs knobs for disabling delegations, while Trond Myklebust advocated for per-application control via open() flags. This week saw Olga Kornievskaia and Trond Myklebust revive the conversation with new perspectives on POSIX compatibility and delegation export to userspace.

Prior Context (Brief)

In November 2025, Scott Mayhew proposed an RFC patch to add sysfs knobs for disabling NFS delegations per-server. The motivation was practical:

"There's occasionally a need to disable delegations, whether it be due to known bugs or simply to give support staff some breathing room to troubleshoot issues."

Mayhew noted that the existing workaround — /proc/sys/fs/leases-enable — only works for knfsd and affects all clients. His approach manipulated OPEN4_SHARE_ACCESS_WANT* flags in NFSv4.1+ to effectively suppress delegation requests without adding new mount options.

Trond Myklebust responded with a counter-proposal: rather than a "big hammer" sysfs approach, enable per-application control via open() flags:

"Shouldn't we rather be allowing the application to select whether it wants to request a delegation or not? IOW: while there may or may not be a place for a 'big hammer' solution like you propose, should we not rather first try to enable a solution in which someone could add a O_DELEGATION or O_NODELEGATION flag to open() in order to specify what they want."

He also noted the potential for LD_PRELOAD libraries to inject these flags into existing applications without recompilation.

Scott Mayhew pushed back on POSIX grounds:

"Sure, allowing the application to specify whether it wants a delegation or not would be better... but with open() being governed by POSIX and with delegations being an NFS-specific feature, I figured adding open flags related to delegations wasn't feasible."

Trond rebutted by citing precedent:

"O_DIRECT, O_NOATIME, O_PATH and O_TMPFILE are all open modes that are unsupported by POSIX. Furthermore, the openat2() system call is designed to be extensible."

This Week's Activity

Olga Kornievskaia Questions NFS-Specific Open Flags

On January 20th, Olga Kornievskaia re-entered the debate, echoing Scott's POSIX concerns:

"Shouldn't open flags be something that's a generic concept for all filesystems? O_DELEGATION seems to be NFS specific (or at most network filesystem specific)."

She also raised a practical point about feature toggling, noting the historical precedent of mount options:

"Being able to control directory delegations feature (might be) useful too? We used to be able to toggle features via mount options, wouldn't it be nice if we could again.... Toggling features via sysfs is useful for when mount is already in place though."

Olga's comments highlight a tension between two valid use cases:

  1. Pre-mount control (mount options) — ideal for known configurations
  2. Post-mount control (sysfs knobs) — essential for troubleshooting live systems

Trond Myklebust Points to Userspace Lease Export

Trond responded by connecting the delegation discussion to ongoing work on exporting NFSv4 delegation functionality to userspace:

"Isn't Jeff Layton in the process of exporting the NFSv4 delegation functionality to userspace through the lease mechanisms?"

This remark is significant because it suggests a potential third path: if delegations can be managed via the Linux lease framework, userspace tools could gain fine-grained control without kernel-side sysfs knobs or non-standard open flags. This approach would leverage existing VFS infrastructure rather than introducing NFS-specific interfaces.

Key Technical Arguments

The POSIX Compatibility Question

The core debate centers on whether NFS-specific open() flags are acceptable:

  • Against (Scott Mayhew, Olga Kornievskaia): Open flags should be generic filesystem concepts; delegations are NFS-specific
  • For (Trond Myklebust): Precedent exists (O_DIRECT, O_NOATIME, O_TMPFILE); openat2() is designed for extensibility

The "Big Hammer" vs Fine-Grained Control Debate

  • Sysfs knobs (Mayhew's approach): Simple, effective for troubleshooting, but coarse-grained — affects all applications using a given server
  • Open flags (Myklebust's approach): Per-application granularity, enables LD_PRELOAD injection, but introduces NFS-specific API surface
  • Userspace lease export (emerging direction): Leverages existing VFS infrastructure, potentially the cleanest long-term solution

Practical Considerations for NFS Client Development

From an NFS client development perspective, this discussion touches on several important themes:

  1. Operational flexibility: Support staff need ways to disable problematic features without remounting or rebooting
  2. Application-level control: Different applications may have different delegation requirements (e.g., databases vs file transfers)
  3. Directory delegations: Anna Schumaker and Jeff Layton's work on directory delegations adds another dimension — the ability to selectively enable/disable this feature

Status and Outlook

The thread remains open-ended with no consensus reached. Three potential paths forward have emerged:

  1. Sysfs knobs as proposed by Mayhew — pragmatic, immediate value for troubleshooting
  2. Open flags as advocated by Myklebust — finer-grained control but requires POSIX precedent justification
  3. Userspace lease integration — potentially the cleanest solution if Jeff Layton's work on exporting delegations to userspace matures

The discussion highlights the ongoing challenge of balancing NFS-specific operational needs against kernel API cleanliness and POSIX compatibility. For NFS client developers, the ability to selectively disable or control delegations remains an important feature request driven by real-world support scenarios.
