bio_vec RDMA API v2: Iterator Design Refinement, IOVA Mapping Review, and MR Support Feedback

bio_vec-Based RDMA API v2: Review Refinement on Iterators, IOVA Mapping, and MR Support

Summary

Type: New feature / API addition (continued from prior week)

This thread covers version 2 of Chuck Lever's four-patch series to add a bio_vec-based RDMA read/write API in the kernel's RDMA core subsystem (drivers/infiniband/core/rw.c). The series eliminates unnecessary scatterlist conversions for callers like svcrdma that already maintain data in bio_vec format, reducing CPU overhead and memory footprint.

Prior Week Recap

Last week (see prior summary), version 1 of the series was posted and received substantive review from Christoph Hellwig and Leon Romanovsky. Key discussion points included: consensus on eventually removing scatterlist support from rw.c entirely, iWARP memory registration requirements, page alignment constraints, and deferral of P2P RDMA support to a future effort tied to nvmet conversion.

This Week's Activity: v2 Series Posted and Reviewed

On January 20th, Chuck Lever posted version 2 [id://20260120143124.1822121-1-cel@kernel.org], incorporating several improvements over v1:

"Changes since v1:

  • Simplify rw.c by using bvec iters internally
  • IOVA mapping produces a contiguous DMA address range
  • Clarify the comment that documents struct svc_rdma_rw_ctxt
  • svcrdma now uses pre-allocated bio_vec arrays"

The series is based on v6.19-rc6 and adds 463 lines to rw.c, 42 lines to ib_verbs.h, 26 lines to rw.h, and modifies the svcrdma consumer.

Patch 1/4: Core bvec RDMA API [id://20260120143124.1822121-2-cel@kernel.org]

Introduces rdma_rw_ctx_init_bvec() and rdma_rw_ctx_destroy_bvec() to accept bio_vec arrays directly, using dma_map_phys() for hardware RDMA devices and virtual addressing for software RDMA devices (rxe, siw). The MR path returns -EOPNOTSUPP at this stage, deferred to patch 3/4.

Christoph Hellwig provided a Reviewed-by with minor nits:

"Nit: maybe rename bvec to bvecs or bvec_table to make it clear this is the base array that the iter operates on?" [id://20260121084217.GA16458@lst.de]

He also suggested parameter formatting improvements and, in a follow-up message, raised an important API design question:

"I'd much rather have the callers pass in the bvec_iter, as that's more useful." [id://20260121085641.GC16458@lst.de]

Leon Romanovsky suggested wrapping the many function parameters into a struct:

"Don't you both think these functions take too many arguments? It might be worth introducing something like 'struct rdma_rw_init_attrs' and passing that instead." [id://20260121084840.GX13201@unreal]

Hellwig was not convinced this would add much value:

"Not sure that buys us much. Having a {bvec_table, bvec_iter} tuple OTOH might be a nice general data structure. Not really for this series, though." [id://20260121085727.GD16458@lst.de]

Leon pushed back on readability grounds:

"Readability???" [id://20260121101639.GA13201@unreal]

Chuck Lever sought clarification on Hellwig's iterator suggestion and agreed to make the change:

"OK. It wasn't clear from your earlier review comments, and I took a guess. I'll get that done." [id://647a452c-0707-4dd3-a937-1e73566babb7@kernel.org]

Hellwig confirmed his intent:

"I mean passing the iter from the API consumer into rw.c. In general that is the sanes way to deal with a collection of bvecs." [id://20260121145702.GA13953@lst.de]

Patch 2/4: IOVA-Based DMA Mapping [id://20260120143124.1822121-3-cel@kernel.org]

This patch introduces the two-step IOVA API (dma_iova_try_alloc / dma_iova_link / dma_iova_sync) to allocate a contiguous IOVA range upfront, link all physical pages without IOTLB syncs, then perform a single sync at completion — reducing IOTLB flushes from O(n) to O(1).

Hellwig noted an additional benefit:

"... and requires only a single output dma_addr_t compared to extra per-input element storage in struct scatterlist." [id://20260121085159.GB16458@lst.de]

He also raised several code-level concerns:

  • The -EOPNOTSUPP return should be documented as a fundamental limitation, not just a temporary gap.
  • Overflow checks on mapped_len may be unnecessary since bi_size is a u32 and mapped_len is a size_t.
  • Iterator handling could be simplified: "I think both the local iter copy in rdma_rw_init_iova_wrs_bvec and this can go away."

Patch 3/4: MR Support for bvec Operations [id://20260120143124.1822121-4-cel@kernel.org]

This patch enables iWARP devices (which require Memory Region registration for RDMA READ operations) and the force_mr debug parameter to use the bvec path. The approach constructs a synthetic scatterlist from bvec DMA addresses and reuses existing ib_map_mr_sg() infrastructure — avoiding driver-level changes.

Hellwig questioned why this path doesn't use bvec_iter like the other paths:

"Any reason this is not using the bvec_iter like the other paths? The mapping to the scatterlist would then basically be a much simplified version of __blk_rq_map_sg." [id://20260121090508.GE16458@lst.de]

He also suggested leveraging existing helpers and noted a structural concern:

"This probably should be in the reg union arm and thus the separate allocation?" [id://20260121090508.GE16458@lst.de]

Patch 4/4: svcrdma Consumer Conversion [id://20260120143124.1822121-5-cel@kernel.org]

The final patch converts svcrdma to the new bvec-based API, eliminating intermediate scatterlist conversion and simplifying svc_rdma_rw_ctxt by removing chained SG table management. The implementation retains an inline bvec array for the fast path (sized to max_send_sge) with dynamic allocation fallback for larger requests.

Key Technical Arguments and Evolution

1. API Design: Iterator Ownership

The most active discussion this week centered on whether bvec_iter should be passed from API consumers into rw.c or managed internally. Hellwig advocated for consumer-passed iterators as the standard pattern in the kernel, and Lever agreed to adopt this approach in v3. This represents a meaningful API refinement that aligns the new bvec API with established kernel conventions.

2. Function Signature Bloat

Leon's suggestion to wrap parameters into struct rdma_rw_init_attrs highlighted a tension between API ergonomics and structural overhead. Hellwig was skeptical, noting that a {bvec_table, bvec_iter} tuple might be more generally useful but not appropriate for this series. This remains an open design question for future iterations.

3. IOVA Mapping Maturity

The IOVA-based DMA mapping approach received positive feedback for its performance benefits (O(1) IOTLB syncs vs. O(n)) and reduced memory overhead. Hellwig's detailed code review focused on iterator handling simplification and overflow check correctness — refinements rather than fundamental objections.

4. MR Path Consistency

Hellwig's observation that the MR path should use bvec_iter like the other paths points to an inconsistency in v2 that will likely be addressed in v3. His suggestion to leverage ib_dma_map_sg* and rdma_rw_init_one_mr for the synthetic scatterlist path would further reduce code duplication.

Significance for NFS Server Development

This series is directly relevant to NFS server-side performance via svcrdma:

  • Eliminated overhead: By removing the scatterlist conversion step, svcrdma avoids both CPU cycles and memory allocations on every RDMA operation.
  • IOVA optimization: The O(1) IOTLB sync for multi-bvec transfers benefits large NFS compound operations that span many pages.
  • iWARP support: Patch 3/4 enables iWARP devices to use the bvec path, broadening hardware compatibility without requiring a fallback to the scatterlist API.
  • Inline fast path: The pre-allocated inline bvec array in svcrdma preserves an allocation-free fast path for typical NFS operations.

Status and Outlook

The v2 series has received a Reviewed-by from Christoph Hellwig on patch 1/4 (with minor nits), along with detailed code-level feedback on patches 2/4 and 3/4. Chuck Lever has agreed to:

  • Pass bvec_iter from API consumers into rw.c (patch 1/4)
  • Address iterator handling simplification in the IOVA path (patch 2/4)
  • Likely adopt bvec_iter in the MR path for consistency (patch 3/4)

No revised patches were posted this week, but a v3 incorporating these refinements is expected. The series remains on track for eventual merge through the RDMA subsystem tree, with the broader goal of eventually eliminating scatterlist-based APIs from rw.c entirely — a direction confirmed by both Hellwig and Leon Romanovsky in prior discussions.
