bio_vec RDMA API: Scatterlist Removal Roadmap, iWARP MR, and P2P Deferral

Summary

bio_vec-Based RDMA Read/Write API for svcrdma — Week of Jan 16–22

Classification

New feature / API addition with performance optimization, targeting the NFS server-side RDMA transport (svcrdma) and the broader RDMA core subsystem.

Prior Week Recap

Last week, Chuck Lever introduced a four-patch series to add bio_vec-based RDMA read/write APIs in drivers/infiniband/core/rw.c, eliminating unnecessary scatterlist conversions for callers that already maintain data in bio_vec format. Christoph Hellwig raised substantive concerns about API design (code duplication with the scatterlist path), IOVA mapping correctness, and page alignment constraints. Leon Romanovsky provided encouraging initial feedback. Lever responded to questions about dynamic allocation and xdr_buf page alignment semantics.

This Week's Discussion

The conversation this week focused on three main themes: (1) whether to eventually eliminate scatterlist support from the RDMA core rw.c code, (2) iWARP memory registration requirements and the path toward a native bvec-based MR API, and (3) peer-to-peer (P2P) RDMA support for the new bvec API.

1. Eliminating Scatterlist Support — A Shared Vision

The most significant development this week was a strong alignment between the RDMA subsystem maintainers on the long-term direction: removing scatterlist-based APIs from rw.c entirely in favor of bio_vec.

Christoph Hellwig had suggested last week that if the bvec and scatterlist code paths weren't unified, "we'll just need to migrate everyone off the scatterlist version ASAP." Leon Romanovsky confirmed this was the intended direction:

"I had short offline discussion with Jason about this series and both of us would be more than happy to get rid of 'scatterlist version'." Leon Romanovsky

Hellwig then highlighted the scope of the migration effort, noting that nvmet_rdma_rw_ctx_init is used by isert, srpt, nvmet, ksmbd, and the sunrpc server side:

"I don't think any of them should be super complicated to work, but it will need a fair amount of testing resources." Christoph Hellwig

Chuck Lever advocated for keeping the current series narrowly scoped — introducing the new API with one consumer (svcrdma), and letting other conversions be done incrementally by domain experts:

"My preference is to keep the scope of this series narrow -- introduce the new API, and add one consumer for it. The other conversions can then each be done by domain experts as they have time." Chuck Lever

He added:

"I have no strong feeling for or against eventually removing SGL support entirely from rw.c." Chuck Lever

Leon acknowledged this pragmatic approach:

"Of course, I'm only outlining the direction in which the RDMA subsystem is expected to evolve." Leon Romanovsky

2. iWARP Memory Registration and the bvec MR API

On patch 3/4 (MR support for bvec-based operations), Leon asked why iWARP needed a special case:

"Do you know why we need a special case here? Is there a reason we cannot avoid using scatterlists for iWARP as well, now or in the future?" Leon Romanovsky

Hellwig explained that iWARP must use Memory Regions (MRs) for RDMA READ destinations, and the core RW code can optionally use MRs for other purposes too. A native bvec-based ib_map_mr_sg would be needed to fully eliminate scatterlists:

"iWarp must use MRs for the destination of RDMA READ operations, but the core RW code can also optionally use it for other things. So to support that natively here we'd need a bvec-based version of ib_map_mr_sg." Christoph Hellwig

He acknowledged the current scatterlist emulation approach as an acceptable interim solution:

"Which would be really nice to have for the storage host drivers anyway, but until then the scatterlist emulation here can do. And implementing it might take a while, as ib_map_mr_sg is a very thin wrapper around a call into the low-level driver." Christoph Hellwig

Leon confirmed this was on his roadmap:

"It is in my roadmap, but as you said, it will take time :(" Leon Romanovsky

3. Page Alignment Constraints Resolved

Hellwig's earlier concern about page alignment was clarified. He confirmed that both classic RDMA memory registrations and IOVA-based DMA mapping require subsequent entries to be at least page-aligned:

"Yeah. I also realized both the classic RDMA memory registrations, and the IOVA based DMA mapping requires the subsequent entries to be at least page aligned." Christoph Hellwig

He noted a Mellanox-specific MR type that doesn't require this, but acknowledged it wouldn't help iWARP and that IOVA coalescing remains valuable.

4. Peer-to-Peer (P2P) RDMA Support — Deferred

Leon suggested extending the bvec API to support P2P scenarios:

"It would also be worthwhile to support P2P scenarios in this flow." Leon Romanovsky

Lever offered to add the code but noted a testing gap:

"I can add some code to this series to do that, but I don't believe I have facilities to test it." Chuck Lever

Hellwig firmly pushed back against merging untested code:

"Please don't add untested code. If Leon wants the P2P support and volunteers to test it, sure. But let's not merge it without being tested." Christoph Hellwig

He also questioned whether P2P would naturally fit into NFS:

"And at least for NFS I don't really see how P2P would easily fit in anyway." Christoph Hellwig

Leon countered that the new API would also benefit NVMe, where P2P could be more useful:

"Chuck is proposing a new IB/core API that will also be used by NVMe too. Wouldn't p2p be useful in the general case" Leon Romanovsky

Hellwig acknowledged P2P could theoretically work with NFS now that direct I/O support exists, but would require substantial effort:

"Well, P2P into a CMB might work in nfsd in theory now that there is direct I/O support, but it'll require a lot of work." Christoph Hellwig

He suggested the nvmet conversion series would be the right place to add and test P2P support:

"So if you want to help to convert nvmet, the series to do that would be the right place to add P2P support, as with that we can actually test it." Christoph Hellwig

Lever agreed and confirmed he already had a patch but would defer it:

"I can understand that P2P is not in the narrow scope of the existing series. I have a patch now, but I'll postpone it until later." Chuck Lever

5. LSF/MM Roadmap Discussion

Leon proposed discussing the broader P2P and scatterlist removal roadmap in person at LSF/MM:

"If both of you plan to attend LSF/MM this year, and I receive an invitation as well, we can discuss the future p2p roadmap in person and how we want to move forward." Leon Romanovsky

He noted that most items from their previous year's discussion have been completed or are on track, with the remaining major item being:

"The remaining big item which is left is removing SG from RDMA." Leon Romanovsky

Key Technical Conclusions

  1. Consensus on scatterlist removal: All three participants agree that scatterlist-based APIs in rw.c should eventually be eliminated in favor of bio_vec. The current series is a stepping stone toward that goal.

  2. Incremental migration strategy: Lever will keep this series narrowly scoped (svcrdma only), with other consumers (isert, srpt, nvmet, ksmbd) to be converted separately by their domain experts.

  3. iWARP MR support via scatterlist emulation: The current approach of constructing a synthetic scatterlist from bvec DMA addresses for ib_map_mr_sg() is accepted as an interim solution until a native bvec-based MR API can be developed — work that Leon has on his roadmap.

  4. P2P support deferred: P2P RDMA support for the bvec API is acknowledged as valuable (especially for NVMe) but will not be included in this series due to testing constraints. It may be added during the nvmet conversion effort, where test infrastructure exists.

  5. Page alignment confirmed: The requirement that subsequent bio_vec entries be page-aligned is confirmed as a constraint of both classic MR registration and IOVA-based DMA mapping, consistent with how xdr_buf represents pages in NFSD.

  6. LSF/MM follow-up planned: The broader roadmap for P2P support and scatterlist removal will be discussed at LSF/MM if participants attend.

Status

The thread concluded with strong alignment on direction but no revised patches this week. The series remains under review, with open items including Hellwig's earlier suggestions about API consolidation (unifying bvec and scatterlist inner loops) and potential bvec_iter usage. The P2P feature has been explicitly deferred to a future effort tied to the nvmet conversion.
