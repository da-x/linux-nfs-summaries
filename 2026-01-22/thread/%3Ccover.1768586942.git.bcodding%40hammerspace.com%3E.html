nfs-utils: Signed Filehandle Support — Userspace Patches Under Review

Summary

Discussion type: New feature (NFS server userspace support for signed filehandles)

Overview

This week, Benjamin Coddington posted a 2-patch series for nfs-utils adding userspace support for the kernel-side signed filehandle feature discussed extensively in the companion thread (kNFSD Signed Filehandles). The goal is to prevent filehandle guessing attacks — where an attacker fabricates valid NFS filehandles to bypass path-based access restrictions — by appending an 8-byte siphash Message Authentication Code (MAC) to filehandles on selected exports.

The two patches are:

  1. PATCH v1 1/2: nfsdctl/rpc.nfsd — Add support for passing the encrypted filehandle signing key from userspace to the kernel
  2. PATCH v1 2/2: exportfs — Add support for the sign_fh export option

Coddington explained that the secret key is derived as "the first 128 bits of a sha1 hash of the contents of a file configured via the nfs.conf server section fh_key_file." Exports with the sign_fh option will cause the kernel to append the siphash MAC to each filehandle.

Key Technical Arguments and Review Feedback

Missing Code in v1

NeilBrown immediately flagged that the patch description claimed to use uuid_generate_sha1() and a function called hash_fh_key_file(), but neither was present in the actual diff:

"This patch adds no code that uses uuid_generate_sha1(), and doesn't provide any code for hash_fh_key_file()..."

He also noted an error handling issue:

"return -errno ??"

Coddington acknowledged the omission:

"I forgot to add the hash function after moving it into libnfs to make it available to both rpc.nfsd and nfsdctl -- here it is, will fix on v2:"

He then provided the missing fh_key_file.c implementation inline in his reply.

Confusion About Patch Overlap

Steve Dickson expressed confusion about the relationship between this series and a previously posted patch:

"This patch conflicts with the 'nfsdctl: Add support for passing encrypted filehandle key' patch. So which patches should I take and which patches are tested ;-)"

Coddington clarified:

"Both are tested - but this series is more complete (but still missing a hunk), because it has support for setting the filehandle signing key in both nfsdctl and rpc.nfsd.. I am going to send a v2, probably tomorrow."

He advised Steve to hold off on merging:

"I think you can delay accepting this work until the kernel patches at least make it into Chuck's nfsd-testing tree. I can keep you appriased of the that status."

Documentation Improvements

NeilBrown suggested better wording for the sign_fh export option documentation, replacing a vague reference to "reverse-engineering" with clearer security language:

"... to guard against filehandle guessing attacks which can bypass path-name based access restrictions"

Coddington agreed: "Your words are much better - thanks."

Code Quality Review of the Hash Function

NeilBrown provided detailed code review of the inline hash function implementation:

  • SPDX licensing: He suggested modernizing license boilerplate: "I wonder if it is time to stop putting this boilerplate in nfs-utils and start using SPDX like the kernel does."
  • Stack vs. heap allocation: He questioned whether malloc(HASH_BLOCKSIZE) was necessary for a 256-byte buffer, suggesting a stack array instead. Steve Dickson agreed that "it is probably not that big of a deal" at 256 bytes, while NeilBrown noted: "In the kernel, 256 bytes on the stack should raise questions. In user space I wouldn't blink below 1MB if the code made sense otherwise."
  • Nested loop concern: NeilBrown flagged a potentially unnecessary inner loop in the file-reading logic: "I think this inner loop is not needed or wanted. fread() will loop as needed until EOF or an error, and we don't want to continue on an error." Steve Dickson concurred: "Good call! Having nested infinite is a bit worrisome..."

Coddington initially defended the loop structure, explaining:

"The fh_key_file can be any length - and this function reads it in HASH_BLOCKSIZE chunks. Each chuck gets hashed against the previous result."

But NeilBrown corrected him:

"Yes, so the outer loop is clearly needed. The inner loop will never execute more than once as fread() only returns short reads on EOF or error."

Coddington gracefully conceded:

"Oh yeah - you're quite right. Crazy how a blind spot can stick like that. Thanks!"

Coddington also identified a bug in error handling:

"That said, there is a bug where ferror(sfile) never gets assigned to 'ret', fixing that.."

SPDX Licensing Discussion

Steve Dickson raised legal concerns about switching to SPDX identifiers:

"Would there be legal ramifications to do this? I remember a time when our legal department was not happy with the copyright verbiage we were using."

NeilBrown responded pragmatically:

"Maybe. Certainly it should be done with care. As a first step we could consider requiring the SPDX line rather than the verbose license text for new contributions."

Evolution of the Discussion

The thread progressed through three clear phases:

  1. Initial review (Jan 17): NeilBrown identified missing code and error handling issues in both patches.
  2. Clarification and inline fixes (Jan 18): Coddington provided the missing hash function implementation inline, acknowledged the need for a v2, and clarified the relationship with prior patches. Steve Dickson raised concerns about patch overlap. NeilBrown reviewed the inline code with detailed feedback on loops, allocation, and licensing.
  3. Resolution of technical debates (Jan 21): The nested loop bug was identified and conceded by Coddington. The SPDX licensing question was tabled for a gradual approach.

Final Conclusions

The series has not been accepted this week. Key takeaways:

  • A v2 is expected: Coddington committed to sending an updated version addressing the missing code, loop bug, error handling fix, and documentation improvements.
  • Integration timing: Steve Dickson should wait for the kernel patches to enter Chuck Lever's nfsd-testing tree before accepting this userspace work.
  • Code quality improvements identified: The hash function needs its inner loop removed, proper error propagation from ferror(), and potentially stack-based allocation instead of malloc().
  • SPDX licensing: A gradual transition for new contributions was suggested as a first step.

This thread complements the broader kernel-side discussion on signed filehandles, which remains open with multiple design directions under consideration (key-based signing vs. per-filesystem UUID-enhanced generation numbers). The userspace work depends on resolution of those kernel design questions before it can be merged.
