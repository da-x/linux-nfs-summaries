NFSD: Enforce Recall Timeout for Layout Conflict — Review and Data Integrity Concerns

Summary

NFSD: Enforce Recall Timeout for Layout Conflict

Overview

Dai Ngo submitted a single-patch proposal NFSD: Enforce recall timeout for layout conflict to address a critical reliability concern in the NFSv4 server's block layout (pNFS) implementation. This is fundamentally a bug fix / robustness improvement for the NFSD lease management code, with significant implications for NFS client data integrity when layout conflicts occur.

The Problem

When a layout conflict triggers a recall on the server, nfsd threads can become indefinitely blocked in __break_lease waiting for the client to release its layout. This creates two problems:

  1. Server starvation: Excessive nfsd threads tied up in lease-breaking operations prevent the server from servicing incoming requests efficiently.
  2. Data integrity risk: If a recall times out and the lease is removed before the rogue client is fenced, competing access could corrupt data or metadata on the backing store.

As Dai Ngo explained in the patch description:

"When a layout conflict triggers a recall, enforcing a timeout is necessary to prevent excessive nfsd threads from being tied up in __break_lease and ensure the server can continue servicing incoming requests efficiently."

Patch Design

The patch introduces two new callbacks in lease_manager_operations:

  1. lm_breaker_timedout: Invoked when a lease recall times out, allowing the lease manager to take action — specifically, issuing a fence operation if the layout type supports it, preventing the client from accessing the block device.

  2. lm_need_to_retry: Invoked when a lease conflict is detected, allowing the lease manager to signal __break_lease to return an error, prompting retry of the conflicting operation and avoiding excessive nfsd threads being blocked.

The patch also adds a new boolean flag flc_in_conflict in struct file_lock_context to track ongoing layout break operations.

Review Feedback

Build Warnings

The kernel test robot reported documentation warnings: build warnings from lkp, including mismatched kdoc prototypes and undocumented parameters. Dai Ngo acknowledged these for fixes in v2.

Christoph Hellwig's Assessment

Christoph provided a cautious initial review:

"This looks reasonable to me, but I don't really feel confident enough about the locks.c code that you should consider this a review."

He also raised an important side question about XFS layout-breaking logic, and Dai Ngo asked whether xfs_break_leased_layouts should break out of its retry loop on errors other than -EWOULDBLOCK. Christoph agreed:

"So yeah, I think we should break out of the loop on error."

Chuck Lever's Technical Concerns

Chuck Lever raised several significant issues in his review:

  1. Error code semantics: The use of -ERESTARTSYS was questioned:

    "-ERESTARTSYS is for syscall restart after signal delivery, which doesn't match up well with the semantics here. A better choice might be -EAGAIN or -EBUSY?"

    Dai Ngo responded that -EAGAIN (equivalent to -EWOULDBLOCK) would not break out of the XFS retry loop, and -EBUSY maps to NFS4ERR_IO, making -ERESTARTSYS the only viable option given current code structure.

  2. Race condition on flc_in_conflict: Chuck noted that unconditionally clearing this flag could be problematic if another racing thread had set it. Dai Ngo argued no race exists since all operations are under flc_lock.

  3. LAYOUTRETURN vs. timeout race: The most critical concern — the stateid reference might become invalid between a voluntary LAYOUTRETURN and the timeout handler:

    "LAYOUTRETURN races with this timeout. Something needs to guarantee that @ls will remain valid for both racing threads, so this stateid probably needs an extra reference count bump somewhere."

  4. API design: Chuck suggested passing common C types rather than internal VFS structures through the new callbacks.

Jeff Layton's Critical Data Integrity Concern

Jeff Layton identified what may be the most serious flaw in the initial approach in his review:

"When the lease times out, you go ahead and remove it but then mark it with FL_BREAKER_TIMEDOUT. Then later, you call ->lm_breaker_timedout if that's set. That means that when this happens, there is a window of time where there is no lease, but the rogue client isn't yet fenced. That sounds like a problem as you could allow competing access."

He recommended reversing the order — fence first, then remove the lease:

"I think you'll have to do this in reverse order: fence the client and then remove the lease."

Dai Ngo initially pushed back, arguing that since the conflicting thread hasn't accessed file data yet, there was no immediate problem. But Jeff pressed the point with a compelling scenario in his follow-up:

"Isn't the whole point of write layout leases to grant exclusive access to an external client? At the point where you lose the lease, any competing access can then proceed. Maybe a local file writer starts writing to the file at that point. But...what if the client is still writing stuff to the backing store? Won't that corrupt data (and maybe metadata)?"

Evolution Toward Resolution

The discussion evolved through several iterations:

  1. Flag placement debate: Dai Ngo suggested moving flc_in_conflict into nfsd_file, but Jeff noted there can be multiple nfsd_file objects per inode. Dai then proposed using nfs4_file instead, which is per-filehandle:

    "Can we move the in_conflict flag in to nfs4_file? I think there is exactly one nfs4_file for every unique inode in use by NFSv4 clients."

    Jeff agreed this could work in his final response:

    "Yeah, that might work since it is a per-fh object, and you shouldn't need to deal with this except on files open via nfs4 anyway."

  2. Alternative approach: Jeff suggested an even cleaner solution — performing fencing before lease removal and using existing lease flags (FL_UNLOCK_PENDING or FL_DOWNGRADE_PENDING) instead of a custom flag:

    "it would still be better to just do the fencing before you remove the lease. That just seems less hacky... If you did that, then I think you could look for the presence of a lease on the list with FL_UNLOCK_PENDING or FL_DOWNGRADE_PENDING set, instead of the flc_in_conflict file flag."

Status and Next Steps

The patch remains under active review with no final resolution this week. Key items for v2:

  • Fix kdoc header mismatches (noted by both kernel test robot and reviewers)
  • Address the fence-before-lease-removal ordering concern raised by Jeff Layton
  • Resolve the LAYOUTRETURN race condition identified by Chuck Lever
  • Consider moving conflict tracking to nfs4_file instead of VFS structures
  • Improve error handling in XFS layout-breaking loops (side issue confirmed by Christoph)

This discussion highlights the complexity of ensuring data integrity in pNFS block layouts, where the server must balance responsive recall enforcement against the risk of allowing concurrent access that could corrupt storage. The reviewers' insistence on fencing before lease removal underscores the importance of maintaining exclusive access guarantees throughout the entire conflict resolution lifecycle.
