bio_vec RDMA API v3: Iterator Adoption, SQ Sizing Bug Fix, and svcrdma Conversion Posted

Summary

bio_vec RDMA API v3: Iterator Adoption, SQ Sizing Bug Fix, and svcrdma Conversion Posted

Type: New feature / API addition with an important bug fix (continued from prior weeks)

Prior Weeks Recap

Chuck Lever's series to add a bio_vec-based RDMA read/write API in the kernel's RDMA core subsystem (drivers/infiniband/core/rw.c) has progressed through three versions since January 14th. The series eliminates unnecessary scatterlist conversions for callers like svcrdma that already maintain data in bio_vec format, reducing CPU overhead and memory footprint. Prior review rounds (see v1 summary and v2 summary) established consensus on eventually removing scatterlist support from rw.c entirely, deferred P2P RDMA support to a future nvmet conversion effort, and refined the iterator design based on Christoph Hellwig's feedback.

This Week's Activity: v3 Series Posted

On January 22nd, Chuck Lever posted version 3 of the series [id://20260122220401.1143331-1-cel@kernel.org], expanding from four to five patches. The cover letter summarizes the motivation:

"Current users of rdma_rw_ctx_init() must convert their native data structures into scatterlists. For subsystems like svcrdma that maintain data in bvec format, this conversion adds overhead both in CPU cycles and memory footprint. The new API accepts bvec arrays directly."

The series is based on v6.19-rc6 and touches seven files across the RDMA core, isert, nvmet, and svcrdma subsystems, adding 699 lines while removing 141.

Changes Since v2

Lever outlined four key improvements:

"Changes since v2:

  • Add bvec iter arguments to the new API
  • Add a synthetic SGL in the MR mapping function
  • Try IOVA coalescing before max_sgl_rd triggers MR in bvec path
  • Attempt once again to address SQ/CQ/max_rdma_ctxs sizing issues"

The first three items directly address Christoph Hellwig's v2 review feedback, while the fourth introduces a new patch targeting an important bug fix.

Key Technical Arguments and Patch Breakdown

1. Core bvec RDMA API with Iterator Support (Patch 1/5) [id://20260122220401.1143331-2-cel@kernel.org]

This patch introduces rdma_rw_ctx_init_bvec() and rdma_rw_ctx_destroy_bvec() to accept bio_vec arrays directly. The v3 refinement incorporates Hellwig's suggestion to pass bvec_iter from API consumers into rw.c, aligning with established kernel conventions:

"I mean passing the iter from the API consumer into rw.c. In general that is the sanes way to deal with a collection of bvecs." Christoph Hellwig, v2 review

The implementation uses dma_map_phys() for hardware RDMA devices and virtual addressing for software RDMA devices (rxe, siw). The MR path returns -EOPNOTSUPP at this stage, deferred to patch 3/5. Notably, Christoph Hellwig provided a Reviewed-by tag on this patch:

"Reviewed-by: Christoph Hellwig hch@lst.de"

2. IOVA-Based DMA Mapping (Patch 2/5) [id://20260122220401.1143331-3-cel@kernel.org]

This patch introduces the two-step IOVA API (dma_iova_try_alloc / dma_iova_link / dma_iova_sync) to reduce IOTLB synchronization overhead from O(n) per-page syncs to a single O(1) sync:

"The two-step IOVA API allocates a contiguous IOVA range upfront, links all physical pages without IOTLB syncs, then performs a single sync at the end. This reduces IOTLB flushes from O(n) to O(1)."

Hellwig noted an additional benefit in his v2 review:

"... and requires only a single output dma_addr_t compared to extra per-input element storage in struct scatterlist." [id://20260121085159.GB16458@lst.de]

The v3 change adds IOVA coalescing before max_sgl_rd triggers MR in the bvec path, optimizing the decision logic for when to use memory registration versus direct scattering.

3. MR Support for bvec Operations (Patch 3/5) [id://20260122220401.1143331-4-cel@kernel.org]

This patch enables iWARP devices (which require Memory Region registration for RDMA READ operations) and the force_mr debug parameter to use the bvec path. The approach creates a synthetic scatterlist populated with DMA addresses from the bvecs, reusing existing ib_map_mr_sg() infrastructure:

"The approach creates a synthetic scatterlist populated with DMA addresses from the bvecs, then reuses the existing ib_map_mr_sg() infrastructure. This avoids driver changes while keeping the implementation small."

This directly addresses Hellwig's v2 observation that the MR path should use bvec_iter like the other paths, and his suggestion to construct a synthetic scatterlist similar to __blk_rq_map_sg. The patch also updates isert and nvmet callers to use the new helper.

4. SQ Sizing Bug Fix: rdma_rw_max_sge() Helper (Patch 4/5) [id://20260122220401.1143331-5-cel@kernel.org] — IMPORTANT BUG FIX

This is a new patch in v3 that addresses a critical sizing bug in the svcrdma Send Queue allocation:

"svc_rdma_accept() computes sc_sq_depth as the sum of rq_depth and the number of rdma_rw contexts (ctxts). This value is used to allocate the Send CQ and to initialize the sc_sq_avail credit pool."

The problem arises when memory registration is used for RDMA operations:

"However, when the device uses memory registration for RDMA operations, rdma_rw_init_qp() inflates the QP's max_send_wr by a factor of three per context to account for REG and INV work requests. The Send CQ and credit pool remain sized for only one work request per context, causing Send Queue exhaustion under heavy NFS WRITE workloads."

The fix introduces rdma_rw_max_sge() to compute the actual number of Send Queue entries required:

"Introduce rdma_rw_max_sge() to compute the actual number of Send Queue entries required for a given number of rdma_rw contexts. Upper layer protocols call this helper before creating a Queue Pair so that their Send CQs and credit accounting match the QP's true capacity."

This patch carries a Fixes tag:

"Fixes: 00bd1439f464 ("RDMA/rw: Support threshold for registration vs scattering to local pages")"

This is a significant bug fix for NFS server stability under heavy WRITE workloads when memory registration is enabled — a scenario that becomes more relevant as iWARP adoption grows and the force_mr debug/testing parameter is exercised.

5. svcrdma Consumer Conversion (Patch 5/5) [id://20260122220401.1143331-6-cel@kernel.org]

The final patch converts svcrdma to the new bvec-based API, eliminating intermediate scatterlist conversion:

"The bvec-based RDMA API eliminates the intermediate scatterlist conversion step, allowing direct DMA mapping from bio_vec arrays. This simplifies the svc_rdma_rw_ctxt structure by removing the chained SG table management."

Lever emphasizes the preservation of performance-critical behavior:

"The structure retains an inline array approach similar to the previous scatterlist implementation: an inline bvec array sized to max_send_sge handles most I/O operations without additional allocation. Larger requests fall back to dynamic allocation. This preserves the allocation-free fast path for typical NFS operations while supporting arbitrarily large transfers."

Importantly, the conversion removes the need for explicit fallback paths:

"The bvec API handles all device types internally, including iWARP devices which require memory registration. No explicit fallback path is needed."

Evolution of the Discussion

The series has evolved significantly across three versions:

  • v1 (Jan 14): Initial proposal with four patches. Review from Hellwig and Leon Romanovsky established consensus on scatterlist removal direction, page alignment constraints, and P2P deferral.
  • v2 (Jan 20): Incorporated bvec iterator usage internally, IOVA contiguous mapping, clarified documentation, and added pre-allocated bvec arrays in svcrdma. Hellwig provided detailed API design feedback advocating for consumer-passed iterators.
  • v3 (Jan 22): Expanded to five patches. Adopted consumer-passed bvec_iter as requested, added synthetic SGL in MR path, improved IOVA coalescing logic, and — most notably — introduced a new patch fixing the SQ sizing bug that causes Send Queue exhaustion under heavy WRITE workloads with memory registration.

Significance for NFS Server Development

This series is directly relevant to NFS server-side performance and correctness via svcrdma:

  1. Eliminated overhead: By removing the scatterlist conversion step, svcrdma avoids both CPU cycles and memory allocations on every RDMA operation — a measurable improvement for high-throughput NFS servers.

  2. IOVA optimization: The O(1) IOTLB sync for multi-bvec transfers benefits large NFS compound operations that span many pages.

  3. iWARP support: Patch 3/5 enables iWARP devices to use the bvec path, broadening hardware compatibility without requiring a fallback to the scatterlist API.

  4. SQ sizing bug fix: The new patch 4/5 fixes Send Queue exhaustion under heavy NFS WRITE workloads when memory registration is enabled — a correctness issue that could cause server-side stalls or errors in production environments using iWARP or with force_mr testing.

  5. Inline fast path preservation: The pre-allocated inline bvec array in svcrdma preserves an allocation-free fast path for typical NFS operations, maintaining the performance characteristics of the existing implementation.

Status and Outlook

The v3 series is freshly posted with no review feedback yet within this week's window (responses from Zhu Yanjun, Christoph Hellwig, and Jason Gunthorpe appear starting January 23rd, outside the current scope). The series carries a Reviewed-by from Christoph Hellwig on patch 1/5 and a Fixes tag on patch 4/5.

The broader roadmap context remains unchanged: all participants agree that scatterlist-based APIs in rw.c should eventually be eliminated in favor of bio_vec, with other consumers (isert, srpt, nvmet, ksmbd) to be converted separately by their domain experts. As Leon Romanovsky noted in the prior round:

"The remaining big item which is left is removing SG from RDMA." [id://20260119183420.GP13201@unreal]

The series is expected to proceed through the RDMA subsystem tree, targeting v6.19 or later depending on review timing and merge window constraints.
