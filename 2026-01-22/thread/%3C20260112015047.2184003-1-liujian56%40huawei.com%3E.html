LTP RPC Tests: libtirpc FD Validation Fix Continued

Summary

LTP RPC Tests: Valid FD for libtirpc Validation (Continued)

Classification: Bug fix (LTP test suite, not kernel NFS code)

This thread continues last week's discussion of an LTP (Linux Test Project) patch addressing failing RPC test cases that use the libtirpc library. The work is cross-posted to linux-nfs because reliable RPC testing infrastructure is foundational for NFS development — NFS relies heavily on RPC transport mechanisms.

Prior Week Recap

Last week, Petr Vorel of SUSE reviewed Liu Jian's [PATCH v2] "rpc: create valid fd to pass libtirpc validation" and raised several questions: whether connecting to 127.0.0.1 is a universally valid approach, which environments trigger the failures, and suggestions for code quality improvements such as extracting shared code into a common header.

This Week's Activity

Liu Jian responded on January 17, providing critical technical context about why the patch is necessary. He tested on Debian 12 and Debian 10 and confirmed:

"I observed that the latest libtirpc (1.3.7) code has the same logic."

Liu traced the root cause to svcfd_create() in libtirpc, which internally calls both getsockname() and getpeername() on the provided file descriptor:

"The above is some code flow of svcfd_create() in libtirpc, where both getsockname() and getpeername() require the file descriptor (fd) to be a valid and connected socket."

This explains why passing an unconnected or invalid fd causes test failures — these system calls require the fd to refer to a connected socket. Liu also noted an important distinction between libtirpc and glibc:

"Additionally, in glibc, there are no similar operations in svcfd_create(), so there is no issue for this test case."

This clarifies that the problem is specific to systems using libtirpc rather than the Sun RPC implementation bundled with older glibc versions.

Addressing Petr's Concerns About the Approach

Petr had questioned whether connecting to localhost was the right strategy and whether it should be applied more broadly. Liu responded:

"For a UDP socket, connect() does not trigger any message transmission and should have no other side effects."

This is an important technical point: connect() on a UDP socket merely sets the default destination address without sending any data, making it a safe operation for test setup purposes.

Regarding Petr's question about whether the same fix should apply to rpc_svc_destroy_stress.c and rpc_svcfd_create_limits.c, Liu observed:

"However, there are no rpc_svcfd_create_limits or rpc_svc_destroy_stress tests in runtest/net.rpc_tests?"

This suggests those test files may not be actively run in the standard LTP test suite, though they still use svcfd_create() and could potentially benefit from the same fix.

Affected Test Files

The patch modifies four LTP RPC test source files:

  • rpc_svc_destroy.c
  • rpc_svcfd_create.c
  • rpc_xprt_register.c
  • rpc_xprt_unregister.c

Each gains approximately 25–27 lines to create a valid connected socket before passing it to svcfd_create().

Status

The patch remains under review. Liu Jian has addressed Petr Vorel's primary technical concerns, demonstrating that the localhost-connection approach is safe for UDP sockets and explaining why libtirpc specifically requires this fix while glibc does not. The remaining open items include whether to extract shared code into a common header (a cosmetic improvement) and whether additional test files should be updated.
