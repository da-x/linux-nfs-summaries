Case Folding v6: FS_XFLAG Conversion Complete, UAPI Collision and Initialization Bug Flagged

Summary

Case Folding v6: FS_XFLAG Conversion Complete, UAPI Collision and Initialization Bug Flagged

Type: New feature / protocol enhancement (continued from prior weeks)

Prior Weeks Recap

Chuck Lever's 16-patch series "Exposing case folding behavior" has progressed through five prior versions since early January. The series introduces a kernel-wide fileattr_get mechanism enabling filesystems to report their case sensitivity and case preservation characteristics, allowing NFSD, ksmbd, and NFS clients to accurately convey filename semantics across protocol boundaries. Key review feedback from earlier rounds included struct layout optimization (packing flags into fa_xflags rather than dedicated fields), FAT's nocase mount option edge case, and the renaming of case_preserving to case_nonpreserving. See prior summaries and v5 summary for full history.

This Week's Activity: v6 Series Posted

On January 20th, Chuck Lever posted version 6 of the series [id://20260120142439.1821554-1-cel@kernel.org], incorporating two key changes since v5:

"Changes since v5:

  • Finish the conversion to FS_XFLAGs (thanks Darrick)
  • NFSv4 GETATTR now clears the attr mask bit if nfsd_get_case_info() fails"

The series is based on v6.19-rc5 and continues to target Christian Brauner's VFS tree rather than the NFSD subtree, with a realistic landing target of v6.20 or later (v6.19 is closed to new features).

Key Technical Arguments

1. FS_XFLAG Conversion Complete

The most significant change in v6 is the completion of Darrick J. Wong's earlier suggestion: case sensitivity flags are now encoded directly through FS_XFLAG_CASEFOLD and FS_XFLAG_CASENONPRESERVING in fa->fsx_xflags, eliminating the need for separate boolean fields in struct file_kattr. As Lever describes in patch 01/16 [id://20260120142439.1821554-2-cel@kernel.org]:

"Filesystems report case-insensitive or case-nonpreserving behavior by setting these flags directly in fa->fsx_xflags. The default (flags unset) indicates POSIX semantics: case-sensitive and case-preserving. These flags are read-only; userspace cannot set them via ioctl."

The patch also relocates struct file_kattr initialization from fileattr_fill_xflags() and fileattr_fill_flags() to vfs_fileattr_get() and the ioctl/syscall call sites, allowing filesystem ->fileattr_get() callbacks to set flags directly before invoking fill functions.

2. UAPI Flag Collision with fsverity

Darrick J. Wong raised an important procedural concern in [id://20260120172608.GQ15551@frogsfrogsfrogs]:

"This ought to go to linux-api because you're changing the userspace api. Granted it's only adding a flag definition to an existing ioctl, but FS_XFLAG_CASEFOLD /does/ collide with Andrey's fsverity xflag patch..."

Chuck Lever responded in [id://38bf1452-8cf8-477b-bcc3-9fe442033bc5@app.fastmail.com], posing a process question to Christian Brauner:

"Do you want to see a v7 of this series with Cc: linux-api before proceeding, or are you taking both Andrey's and mine and can resolve the conflict, or ... ?"

Darrick followed up in [id://20260120225819.GA15551@frogsfrogsfrogs] with a pragmatic resolution:

"Well now that I've griped at both patchsets on the same public list, I'll at least chime in that I'd be satisfied if whoever decides to merge them to fix up the conflicts whenever they merge them. :)"

This collision between Lever's FS_XFLAG_CASEFOLD and Andrey's fsverity xflag work represents a potential merge-time conflict that will need resolution by the VFS maintainer.

3. Initialization Bug in ioctl_getflags()

Jan Kara identified a subtle but important bug in patch 01/16 in [id://avtj6ud7hb7qyya4ekj24lu2jwmirlqspxa4ptmhjrvuhrgfx6@ghzl2aqdokkg]:

"Umm, but ioctl_getflags() sets fa->flags_valid as a hint for ->fileattr_get() handler and this will now zero-out that hint. So I agree that zeroing fa in fileattr_fill_{,x}flags() is a bit unexpected and moving it is desirable but it needs a bit more careful surgery."

This feedback points out that the relocation of struct initialization may inadvertently clear the flags_valid hint before the filesystem's ->fileattr_get() callback has a chance to read it — a regression that will need to be addressed in v7.

NFS Client Development: Re-export Case Sensitivity Support

Patch 10/16 [id://20260120142439.1821554-11-cel@kernel.org] remains a critical component for NFS client development, enabling re-export scenarios. Lever's commit message explains:

"An NFS server re-exporting an NFS mount point needs to report the case sensitivity behavior of the underlying filesystem to its clients. Without this, re-export servers cannot accurately convey case handling semantics, potentially causing client applications to make incorrect assumptions about filename collisions and lookups."

The implementation leverages case sensitivity information the NFS client already retrieves from servers during mount — via PATHCONF for NFSv3 or FATTR4_CASE_INSENSITIVE/FATTR4_CASE_PRESERVING attributes for NFSv4. NFSv2 mounts default to POSIX behavior since that protocol lacks PATHCONF support. The patch touches nine files across the NFS client codebase (client.c, inode.c, internal.h, nfs3proc.c, nfs3xdr.c, nfs4proc.c, proc.c, symlink.c, and include/linux/nfs_xdr.h).

NFSD Enhancements: Dynamic Case Sensitivity Reporting

NFSv3 PATHCONF (Patch 14/16)

Patch 14/16 [id://20260120142439.1821554-15-cel@kernel.org] replaces the hard-coded MSDOS_SUPER_MAGIC check in nfsd3_proc_pathconf() with a dynamic query through ->fileattr_get. As Lever explains:

"The hard-coded MSDOS_SUPER_MAGIC check in nfsd3_proc_pathconf() only recognizes FAT filesystems as case-insensitive. Modern filesystems like F2FS, exFAT, and CIFS support case-insensitive directories, but NFSv3 clients cannot discover this capability."

NFSv4 FATTR4 Attributes (Patch 15/16)

Patch 15/16 [id://20260120142439.1821554-16-cel@kernel.org] replaces hard-coded responses with actual filesystem queries:

"NFSD currently provides NFSv4 clients with hard-coded responses indicating all exported filesystems are case-sensitive and case-preserving. This is incorrect for case-insensitive filesystems and ext4 directories with casefold enabled."

A notable v6 improvement: the NFSv4 GETATTR now clears the attribute mask bit if nfsd_get_case_info() fails, ensuring clients receive accurate information rather than stale or incorrect defaults.

CIFS Integration for Multi-Protocol Environments

Patch 09/16 [id://20260120142439.1821554-10-cel@kernel.org] implements fileattr_get for the CIFS client, reporting case sensitivity based on the nocase mount option. This is significant for multi-protocol environments where a Linux NFS server may re-export a CIFS/SMB mount point and needs to accurately report its case handling semantics to NFS clients.

Significance for NFS Client Development

This series addresses several critical interoperability challenges:

  1. Windows/macOS NFS client support: As Lever emphasized in the cover letter, Windows-based NFS clients such as ms-nfs41-client "explicitly require servers to report FATTR4_WORD0_CASE_INSENSITIVE = TRUE for proper operation, a hard requirement for Windows client interoperability because Windows applications expect case-insensitive behavior."

  2. Linux NFS client caching correctness: When a Linux client detects a case-insensitive share, it can properly manage negative dentry caching and directory change invalidation — avoiding subtle bugs where lookups fail due to stale cache entries. Lever noted: "when a client detects a case-insensitive NFS share, negative dentry caching must be disabled (a lookup for 'FILE.TXT' failing shouldn't cache a negative entry when 'file.txt' exists) and directory change invalidation must clear all cached case-folded file name variants."

  3. Re-export accuracy: The NFS client's fileattr_get implementation enables NFSD to accurately report the case sensitivity of re-exported NFS mounts, a critical capability for file service proxies.

  4. Multi-protocol environments: "Hammerspace servers and several other NFS server implementations operate in multi-protocol environments, where a single file service instance caters to both NFS and SMB clients. In those cases, things work more smoothly for everyone when the NFS client can see and adapt to the case folding behavior that SMB users rely on and expect."

Status and Outlook

The v6 series is posted and under active review with two open items requiring attention before merge:

  1. UAPI collision: FS_XFLAG_CASEFOLD collides with Andrey's fsverity xflag patch. Darrick J. Wong suggested the VFS maintainer can resolve this at merge time, but Chuck Lever asked whether a v7 with Cc: linux-api is needed.

  2. Initialization bug: Jan Kara flagged that the relocated struct initialization may zero out the flags_valid hint before the filesystem callback reads it, requiring "a bit more careful surgery."

The series has broad support across filesystem maintainers from prior rounds and remains on a strong path toward eventual merge through the VFS tree, targeting v6.20 or later.
