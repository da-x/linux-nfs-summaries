NFS v4.0 KConfig Refactoring: Sparse Warning on Patch 03/14

Summary

This thread is part of Anna Schumaker's ongoing 14-patch series to make NFS v4.0 support optional via Kconfig, as a first step toward eventual deprecation of the protocol version. This week's activity was limited to an automated build warning from the kernel test robot targeting patch 03/14 — which moves nfs40_nograce_recovery_ops into the new nfs40proc.c file.

Background (from prior weeks)

As summarized in last week's coverage, Anna Schumaker submitted a comprehensive 14-patch series aimed at restructuring the NFS client codebase to enable compile-time exclusion of NFS v4.0 support. The series creates new source files (nfs40client.c, nfs40proc.c, nfs40.h) to isolate v4.0-specific code and promotes NFS v4.1 as the default, always-enabled NFSv4 minor version.

This Week's Activity

The kernel test robot reported a sparse warning on patch 03/14 during automated build testing:

"kernel test robot noticed the following build warnings" As reported by the kernel test robot.

The warning was flagged on v6.19-rc5 with clang version 20.1.8 under an i386-randconfig-r134-20260118 configuration:

"sparse: function 'nfs_state_clear_open_state_flags' with external linkage has definition" As reported in the sparse warning.

The issue is located at line 1839 of fs/nfs/nfs4proc.c, where the function is declared with extern but also has a body (definition):

extern void nfs_state_clear_open_state_flags(struct nfs4_state *state)
{
    clear_bit(NFS_O_RDWR_STATE, &state->flags);
    clear_bit(NFS_O_WRONLY_STATE, &state->flags);
    clear_bit(NFS_O_RDONLY_STATE, &state->flags);
    clear_bit(NFS_OPEN_STATE, &state->flags);
}

The sparse tool flags this as a mismatch: extern indicates the function is defined elsewhere (declaration only), but the presence of a body makes it a definition. The fix would be to either remove extern (if the function should be defined here) or move the body to another file and keep only the declaration here.

The robot also noted that the patch could not be applied to trondmy-nfs/linux-next, suggesting potential dependency or base tree issues:

"cannot apply to trondmy-nfs/linux-next" As noted by the kernel test robot.

Classification

This is a code refactoring effort — not a bug fix or protocol change. The sparse warning represents a minor code quality issue introduced during the refactoring of NFS v4.0-specific code into dedicated files.

Discussion Status

No human replies were received this week beyond the automated build report. Anna Schumaker has not yet responded to the sparse warning, and no v2 of the series has been posted in response. The kernel test robot's note about the patch failing to apply to trondmy-nfs/linux-next may indicate that the base tree needs updating or that there are conflicts with pending NFS changes.

Conclusion

This week's activity was minimal — a single automated sparse warning on one patch in the series. The warning is straightforward to fix (removing the erroneous extern keyword from a function definition). The broader refactoring effort remains under review, with Anna having invited community feedback on her approach before proceeding further. No significant technical debate or evolution of the discussion occurred this week.
