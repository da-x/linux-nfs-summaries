FAT Filehandle Limitations and EXPORT_OP_UNIQUE_HANDLES Flag Proposal

Summary

Filehandle Uniqueness Debate: FAT, Pseudo-filesystems, and an EXPORT_OP_UNIQUE_HANDLES Flag

Discussion type: Protocol / infrastructure design (bug fix / correctness improvement for NFS export filehandle semantics)

Prior Weeks Recap

This thread is part of the broader ongoing discussion around Christoph Hellwig's 29-patch series to require filesystems to explicitly opt-in to NFSD export support. The overarching goal is to ensure that only filesystems with well-behaved, stable, and unique filehandles can be exported via NFS — preventing stale handle issues, handle collisions, and other correctness problems. NeilBrown initiated this specific sub-thread on January 19th [id://176880736225.16766.4203157325432990313@noble.neil.brown.name], asking for a detailed accounting of which filesystems have filehandle problems and what those problems are, in the context of naming an export operations flag (debating STABLE, PERSISTENT, or other names). The discussion has been intertwined with related threads on kNFSD signed filehandles and pseudo-filesystem handle semantics.

This Week's Activity: FAT Filehandle Limitations and a Proposed Uniqueness Flag

Two messages were exchanged on January 22nd, continuing the debate about which filesystems can safely be exported and how to formally encode filehandle quality guarantees in the kernel.

1. FAT Cannot Achieve Persistent Filehandles — Accepted as an Exception

Christoph Hellwig responded to Jeff Layton's earlier analysis of problematic filesystems, acknowledging that FAT is a notable exception among "real" filesystems:

"Not sure what we can do about FAT without changing the filehandle format in some fashion. The export ops just use generic_encode_ino32_fh, and FAT doesn't have stable inode numbers."

Hellwig conceded that FAT's limitations are rooted in historical design constraints:

"Yeah. I guess we need to ignore this because of <history>"

The core problem is that FAT uses generic_encode_ino32_fh for its export operations, and FAT lacks stable inode numbers — meaning filehandles can change across remounts or filesystem reorganizations. The "nostale" operations appear sane but only work in read-only mode, limiting their practical value for writable NFS exports.

2. Agreement on Filehandle Uniqueness as a Universal Goal

Hellwig and Layton found consensus on the broader principle that filehandles should be both unique and persistent across all filesystems — not just for NFSD but also for userland applications using the open_by_handle_at(2) syscall:

"Agreed. We should try to ensure uniqueness and persistence in all filehandles both for nfsd and userland applications." [Jeff Layton]

Hellwig endorsed this direction:

"Sounds good to me."

3. Pseudo-filesystem Exceptions: pidfs and cgroupfs Cannot Be Extended

Jeff Layton followed up with an important complication: some pseudo-filesystems have filehandles that cannot be extended to achieve uniqueness due to existing userspace expectations. He cited Christian Brauner's earlier analysis [id://20260120-irrelevant-zeilen-b3c40a8e6c30@brauner]:

"Unfortunately, there are already exceptions. Apparently pidfs and cgroupfs handles (at least) can't be extended because of userspace expectations."

This means that even with best efforts, some filesystems will inherently produce filehandles that violate the ideal of uniqueness and persistence.

4. Proposal: EXPORT_OP_UNIQUE_HANDLES Flag

Layton proposed a practical solution: introduce a new flag in export_operations to explicitly mark filesystems that guarantee unique handles:

"So, we will need an export_operations flag of some sort (EXPORT_OP_UNIQUE_HANDLES?). At that point, we'll have to decide whether to deny nfsd export based on that flag."

This flag would serve dual purposes:

  • For NFSD: Potentially deny export of filesystems that cannot guarantee handle uniqueness.
  • For userland: Allow applications using filehandle syscalls to identify which filesystems provide reliable handles.

5. NFSv4 Already Supports Volatile Handles — But Client Guidance Is Lacking

Layton noted an important protocol detail: the NFSv4 specification already allows servers to advertise that they cannot guarantee handle uniqueness. However, he flagged a gap in client-side behavior:

"NFSv4 actually allows the server to advertise that it can't guarantee handle uniqueness. There isn't much guidance for the client on how to handle that though and the attribute seems to have the scope of the entire NFS server."

This observation highlights a broader interoperability concern: even if NFSD can signal non-unique handles, NFS clients may not know how to gracefully degrade their behavior (e.g., reducing cache lifetime, avoiding negative dentry caching).

Evolution of the Discussion

The conversation has evolved from a naming debate (what to call the opt-in flag) to a more nuanced discussion about filehandle quality guarantees:

  1. Prior week: NeilBrown asked for a detailed accounting of which filesystems have problems and what those problems are, in the context of choosing a flag name.
  2. This week: Hellwig and Layton identified specific problem cases (FAT, pidfs, cgroupfs), agreed on the goal of universal handle uniqueness, and proposed a practical mechanism (EXPORT_OP_UNIQUE_HANDLES) to encode this property.

Significance for NFS Client Development

While this thread focuses primarily on server-side export infrastructure, it has important implications for NFS client behavior:

  • Cache invalidation: Clients need to know whether handles are stable to make correct caching decisions. Non-unique or volatile handles may require more aggressive cache invalidation.
  • Protocol gap: The lack of clear guidance for NFSv4 clients on how to handle servers advertising non-unique handles represents a potential interoperability issue, especially with re-export scenarios and multi-protocol file servers.
  • Re-export accuracy: If NFSD can identify which filesystems provide unique handles via the proposed flag, it could potentially advertise this information more accurately to NFSv4 clients.

Final Conclusions

The discussion reached several tentative conclusions:

  1. FAT will remain an exception: Due to historical constraints (lack of stable inode numbers), FAT cannot achieve persistent filehandles without a format change, but it must remain exportable for compatibility. As Hellwig noted: "I guess we need to ignore this because of <history>"

  2. A new flag is needed: EXPORT_OP_UNIQUE_HANDLES (or similar) should be added to export_operations to identify filesystems that guarantee unique, persistent filehandles.

  3. Not all filesystems can comply: Pseudo-filesystems like pidfs and cgroupfs have userspace ABI constraints that prevent handle extension, meaning they will always be exceptions.

  4. Client behavior needs clarification: The NFSv4 protocol's support for volatile handle advertisement lacks clear client-side guidance, representing an area for future protocol or implementation work.

The discussion remains open-ended, with the next steps involving actual implementation of the proposed flag and decisions about whether NFSD should deny export of filesystems that cannot guarantee handle uniqueness.
