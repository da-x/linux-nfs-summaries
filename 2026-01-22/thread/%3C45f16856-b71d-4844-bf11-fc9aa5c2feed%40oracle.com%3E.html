Fix: Stale XA_MARK_0 Prevents Re-fencing in nfsd4_block_get_device_info_scsi

Summary

Bug in nfsd4_block_get_device_info_scsi in nfsd-testing branch

Classification: Bug Fix (NFSv4 pNFS Block Layout Server)

Overview

Dai Ngo reported a critical bug in the NFS server's pNFS block layout SCSI device fencing logic, specifically in nfsd4_block_get_device_info_scsi in the nfsd-testing branch. The bug prevented proper re-fencing of clients after SCSI reservation conflicts were resolved.

The Bug

Dai Ngo opened the thread by describing the core issue on January 16:

"After the entry in the xarray was marked with XA_MARK_0, xa_insert will not update the entry when nfsd4_block_get_device_info_scsi is called again leaving the entry with XA_MARK_0."

The consequence was severe:

"When the server needs to fence the client again, since the entry still has XA_MARK_0, it skips the fence operation."

This meant that once a device entry in the xarray was marked as fenced (via XA_MARK_0), subsequent calls to xa_insert would not update the entry. The mark persisted indefinitely, preventing the server from re-fencing clients when needed.

Discussion: API Contract Clarification

Chuck Lever initially questioned whether the fix was correct, noting on January 16:

"The mark is cleared only when a pr_unregister is done. I didn't think that an additional GETDEVICEINFO should clear an existing registration."

"So, did I misunderstand the API contract?"

Dai Ngo clarified the operational model on January 16:

"The nfsd server never issues pr_unregister. It uses fence to stop client from accessing the device."

He then explained the pNFS block layout error recovery flow:

"When the client detects I/O error, due to SCSI reservation conflict, it retries the I/O to the MDS. On new I/O, the client sends LAYOUTGET then GETDEVICEINFO and send I/O to the DS again. This is why the nfsd server needs to clear the mark on the xarray entry on GETDEVICEINFO in case it needs to fence the client again."

This clarified that the NFS server's fencing model relies on re-fencing via GETDEVICEINFO rather than explicit unregistration, making the mark-clearing behavior essential for correct operation.

The Fix

Dai Ngo proposed and tested a fix on January 17. The patch involved clearing the XA_MARK_0 mark on the xarray entry when GETDEVICEINFO is called, allowing the server to properly re-fence clients as needed.

Chuck Lever applied the fix with an additional concurrency safeguard on January 17:

"I applied this fix, wrapped it in xa_lock to make the update atomic, and pushed to nfsd-testing."

Dai confirmed the resolution on January 17:

"Thank you Chuck!"

Code Quality Review

Christoph Hellwig reviewed the patch on January 19 and suggested improvements to code clarity:

"This looks reasonable. But looking at this, I think it would really help to add a named constant for XA_MARK_0 to make it more clear what the bit stands for, and maybe even add little inline helpers for setting/clearing the mark."

Chuck Lever agreed to add the named constant on January 19:

"Sure, that idea has been in and out of my private working copies of this patch. I'll add it."

A brief exchange followed about the value of inline helper functions. Chuck noted Christoph's historical skepticism:

"In the past you've actively hated 'adding little inline helpers' so I don't suggest that any more. But I actually prefer that."

Christoph clarified his position on January 20:

"I like them when they provide a useful abstraction, and not when they don't. Of course the 'useful' might sometimes be in the eye of the beholder."

Conclusion

The bug was identified, understood, and fixed within two days. The fix ensures that when an NFS client re-requests device information after a SCSI reservation conflict, the server can properly re-fence the client by clearing the stale XA_MARK_0 mark on the xarray entry. The fix was applied to the nfsd-testing branch with proper locking (via xa_lock) to ensure atomicity of the update. A follow-up improvement to add a named constant for XA_MARK_0 is planned to improve code readability.

This bug fix is important for NFS clients using pNFS block layouts with SCSI devices, as it ensures correct error recovery when reservation conflicts occur during direct I/O operations.
