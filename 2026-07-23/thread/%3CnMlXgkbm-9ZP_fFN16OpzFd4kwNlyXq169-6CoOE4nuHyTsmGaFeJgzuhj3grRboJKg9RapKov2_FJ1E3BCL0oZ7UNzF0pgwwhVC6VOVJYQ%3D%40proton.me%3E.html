NFSv4.2 futimens() succeeds without SETATTR

Summary

This week's linux-nfs traffic opened a client-side bug report, not a protocol change or new feature: GNU touch on NFSv4.2 can return success from the fd-based futimens()/utimensat(fd, NULL, ...) path while never sending SETATTR, so the server inode is unchanged and the client's cached timestamps later snap back.

The report

Michael Yang described a reproducible NFSv4.2 timestamp failure on Fedora 44 with kernel 7.1.3 (both CachyOS and stock Fedora builds), nfs-utils 2.8.7, and coreutils 9.10. The mount is a straightforward vers=4.2 NFSv4 share (rw,relatime,...); the bug also reproduces with noac.

The failing sequence is the fd-based form used by GNU touch:

touch -d '2004-02-29 16:21:42' /mnt/tank/test

strace shows openat() followed by utimensat(0, NULL, [{tv_sec=1078032102, tv_nsec=0}, ...], 0) = 0 after coreutils has duplicated the file descriptor onto fd 0. Yang's observed behaviour is:

  1. utimensat() returns success.
  2. Client stat temporarily shows the requested atime/mtime.
  3. The server-side backing inode is unchanged.
  4. The NFS client SETATTR counter does not increment.
  5. After attribute revalidation, the client timestamps revert to the server's.
  6. sync and a clean unmount do not push the change.

He contrasted that with pathname-based utimensat(AT_FDCWD, "/mnt/tank/test", ...), which does increment the client SETATTR counter and immediately updates the server inode. The same inode number and birth time on both sides rule out a "different file" mix-up. His summary of the split:

"fd-based timestamp update: returns success, no SETATTR observed, server inode unchanged, update later disappears"

versus

"pathname-based timestamp update: returns success, SETATTR observed, server inode updated"

"This therefore appears specific to the fd-based futimens() / utimensat(fd, NULL, ...) path."

That is a classic NFS client setattr/timestamp path bug: userspace is told the update succeeded, the local cache is dirtied, and nothing is ever flushed to the wire.

Confirmation and a 7.0-era suspect list

Holger Hoffstätte confirmed the same failure on 7.1.x and thanked Yang for isolating the fd-versus-path distinction:

"Confirmed (also with 7.1.x) and thank you for tracking down the details. This has been driving me nuts for quite a while, but I could not figure out whether it's my very historic NFS config, server- or client-side, autofs or whatever."

He then bisected the onset rather than a single commit: 7.0.0 already reproduces, so the regression likely landed in the 7.0 merge window. Two commits stood out as plausible client/VFS interaction points:

  • b8b3002fbfef — nfs: split nfs_update_timestamps
  • 761475268fa8 — fs: refactor ->update_time handling (part of a larger VFS series)

"Hope that helps someone to find the cause."

Where things stand this week

This is an NFS client timestamp/setattr bug affecting the common GNU touch fd-based path. The report is well instrumented (strace, SETATTR counters, client vs. server stat, noac control) and independently reproduced. No maintainer reply, patch, or confirmed root cause landed inside this week; the working hypothesis is a 7.0-era interaction between the VFS ->update_time refactor and NFS's split nfs_update_timestamps path, which appears to update the local inode and return success without issuing NFSv4 SETATTR when the caller uses an open file descriptor rather than a pathname.

No protocol change is proposed. The practical impact for NFS client users is silent timestamp loss: tools that rely on futimens() (notably GNU touch -d) look successful, then the timestamps evaporate on the next revalidation.
