SUNRPC restores NUMA_NO_NODE after nfsd affinity collapse

Summary

This week’s discussion is a bug fix, not a protocol change or new feature: a six-line SUNRPC correction that undoes a NUMA-affinity collapse introduced while converting the RPC scratch buffer to folios. Ameer Hamza of TrueNAS posted the patch on 22 July after a bisect of a 2× NFS READ throughput regression between v6.17 and v6.18 on a four-node server, and the thread closed the same day with a Reviewed-by from Jeff Layton and an apply to nfsd-testing from Chuck Lever.

How a folio conversion pinned every nfsd thread to one node

The regression is a side-effect of commit d57e43b72bf2 (SUNRPC: Update svcxdr_init_decode() to call xdr_set_scratch_folio()). That change made svc_pool_map_get_node() return numa_mem_id() instead of NUMA_NO_NODE because __folio_alloc_node() cannot accept the latter. Hamza’s central technical point is that the two values are not equivalent:

"That return value is not equivalent: it is evaluated in the context of the task creating the nfsd threads, once per thread created, and it is passed to kthread_create_on_node() and to the per-thread allocations in svc_prepare_thread()."

A later kthread change, d1a89197589c (kthread: Default affine kthread to its preferred NUMA node), then turned that node id into a real CPU affinity. Under the default pool_mode=global, a single writer of /proc/fs/nfsd/threads creates every nfsd kthread, so each thread inherits the creator’s local-memory node — typically the same node for the entire pool. Hamza described the fallout:

"The CPUs of the other nodes are then unable to run nfsd at all, and the threads' allocations — svc_rqst structures, page pointer arrays, newly allocated task stacks, and the per-RPC pages allocated at run time — all prefer that one node."

On the four-node box that motivated the patch, every nfsd thread came up restricted to one node’s CPUs. Restoring NUMA_NO_NODE made the threads runnable on all CPUs again and recovered the lost READ throughput.

The fix: restore global-mode semantics, isolate the folio constraint

The patch does not revert the folio conversion. It restores the NUMA_NO_NODE behaviour that global mode has had since 11fd165c68b7 (sunrpc: use better NUMA affinities) and resolves NUMA_NO_NODE to numa_mem_id() only at the one call site that cannot accept it — the same fallback alloc_pages_node() used for the scratch page before the conversion. The mapped percpu and pernode branches are left alone.

Hamza explicitly called out the NFS client impact. Unpooled services share this fallback when no percpu or pernode map is active:

"Unpooled services such as lockd and the NFS client callback service also take this fallback when no percpu or pernode map is active, restoring their thread placement in that case."

That is the client-development angle: the same svc_pool_map_get_node() path feeds the NFS client’s callback service (fs/nfs/callback*). After d57e43b72bf2, a client that starts its callback threads from one CPU could pin those kthreads — and their svc_rqst / RPC-page allocations — to a single NUMA node, starving callback processing on the rest of the machine. The restore puts callback-thread placement back where it was before the folio conversion.

Hamza aimed the patch at nfsd-fixes and stable (v6.18+), not at the in-flight pool-mode rework:

"The pool-mode rework in nfsd-testing already removes global mode, so this fix is based on nfsd-fixes and aimed there and at stable (v6.18+), where the regression ships."

Review: the patch is accepted, with a caveat about global mode

Jeff Layton reviewed the change the same afternoon. He did not dispute the diagnosis or the six-line repair, but he questioned how much energy global mode still deserves on real NUMA hardware:

"The patch seems sane. I wonder how much we should care about people using global mode on real NUMA hw though? The better fix for those folks would be to move to pernode, most likely."

That remark sits against the earlier pool-mode series that hard-codes pool_mode to pernode and deletes the other modes — the same rework Hamza said already lives in nfsd-testing. Layton still added Reviewed-by: Jeff Layton <jlayton@kernel.org>, treating the restore as the correct stable-tree answer even if pernode is the longer-term design.

Landed, and ordered ahead of the pool-mode rewrite

Chuck Lever applied the patch to nfsd-testing a few hours later and recorded the commit as ea94cbfb34c7151d79da28a8c7e4bec0290b3e27. He also reordered the branch so the NUMA restore sits before Layton’s svc-pool restructuring:

"Applied to nfsd-testing, thanks! nfsd-testing has been re-ordered so this patch is positioned before Jeff's restructuring of svc pools."

That ordering matters: the restore has to land first so that trees which still have global mode (v6.18+, nfsd-fixes, and the early part of nfsd-testing) get the affinity fix, while the later pool-mode rewrite can then delete global mode on top of a correct baseline.

Conclusions

  • Classification: important bug fix in SUNRPC thread placement; no protocol change.
  • Root cause: svc_pool_map_get_node() started returning numa_mem_id() to satisfy __folio_alloc_node(), and kthread NUMA auto-affinity then pinned every globally pooled nfsd thread — plus unpooled lockd and NFS client callback threads — to the creator’s node.
  • User-visible effect: 2× NFS READ throughput drop on multi-node hardware between v6.17 and v6.18; all nfsd threads runnable on only one node’s CPUs.
  • Fix: restore NUMA_NO_NODE for global / unmapped services; resolve the node only at the folio allocation site.
  • Status: Reviewed-by Layton; applied to nfsd-testing as ea94cbfb34c7, ordered ahead of the pool-mode rewrite; intended for nfsd-fixes and stable v6.18+.
  • Client note: the same fallback repairs NFS client callback-service thread placement, so clients on NUMA boxes regain the ability to run callback kthreads across nodes rather than on a single node’s CPUs.
