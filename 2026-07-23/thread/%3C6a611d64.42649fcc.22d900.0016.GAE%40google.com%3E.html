syzbot: hung task in nfsd_nl_expkey_set_reqs_doit — nfsd_mutex serializes the new fh-cache netlink path

Summary

syzbot: hung task in nfsd_nl_expkey_set_reqs_doit — the new fh-cache netlink path joins the nfsd_mutex pile-up

Classification

This is a bug report, not a protocol change and not a new feature in its own right. Google's syzbot filed a single unreproduced hung-task report against the NFS server generic-netlink control plane. The hung function, nfsd_nl_expkey_set_reqs_doit in fs/nfsd/export.c, is the downcall handler that userspace (exportd/mountd) uses to populate the nfsd.fh export-key cache — the file-handle lookup cache that NFSv2/v3 (and some v4) clients depend on to turn an FSID into a path.

No human has replied in this thread. The technical picture is nonetheless clear from the lock dump, and it is the same class of failure Jeff Layton and Neil Brown diagnosed two days earlier on the sibling nfsd_nl_cache_flush_doit hang.

What landed this week

On Wednesday, 22 July, syzbot reported a hung task on upstream HEAD 0f26556c5eee (Merge tag 'nfsd-7.2-1'):

"INFO: task syz.5.2252:10556 blocked for more than 143 seconds."

"Unfortunately, I don't have any reproducer for this issue yet."

The kernel is a PREEMPT_{RT,(full)} syzkaller build. The hung task is blocked in mutex_lock_nested → nfsd_nl_expkey_set_reqs_doit+0xfe/0xaf0 at fs/nfsd/export.c:561, having entered via genl_family_rcv_msg_doit / sendmsg. It already holds the generic-netlink cb_lock and is waiting for the global nfsd_mutex.

syzbot asked that any fix carry:

"Reported-by: syzbot+de7e55e90abcbb58ae63@syzkaller.appspotmail.com"

The lock dump: four netlink ops, one mutex

The interesting evidence is not the hung stack itself — it is the "Showing all locks held in the system" dump, which shows four concurrent nfsd netlink operations all serialized on the same nfsd_mutex:

TaskHandlerRole
syz.0.1592nfsd_nl_threads_set_doit (nfsctl.c:1660)holds nfsd_mutex
syz.5.2252 (the hung task)nfsd_nl_expkey_set_reqs_doit (export.c:561)waiting on nfsd_mutex
syz.2.3144nfsd_nl_svc_export_set_reqs_doit (export.c:1057)holds nfsd_mutex
syz.1.3270nfsd_nl_rpc_status_get_dumpit (nfsctl.c:1510)holds nfsd_mutex (plus nlk_cb_mutex-GENERIC)

This is not a classic AB-BA deadlock. Every waiter is in D-state on the same coarse lock. One (or more) of the holders is simply not releasing nfsd_mutex for more than 143 seconds, and every other nfsd netlink command — export-key updates, export-table updates, thread-count changes, RPC-status dumps — queues behind it.

The NMI backtrace captured on CPU 1 is a red herring for the NFS path: syz.6.4350 was in shmem_file_write_iter / fault_in_readable under lockdep, not in nfsd. The USB hub workqueues in the lock list are similarly incidental. The nfsd story is entirely the four-way pile-up on nfsd_mutex.

Where nfsd_nl_expkey_set_reqs_doit came from

The hung handler is new this cycle. Jeff Layton's commit 01c2305795a3 ("nfsd: add netlink upcall for the nfsd.fh cache") added netlink cache-upcall support for the expkey (nfsd.fh) file-handle cache, mirroring the existing svc_export netlink pattern. It introduced:

  • an expkey attribute set (client, fsidtype, fsid, negative, expiry, path);
  • the expkey-get-reqs / expkey-set-reqs operations in the nfsd YAML spec;
  • nfsd_nl_expkey_get_reqs_dumpit() and nfsd_nl_expkey_set_reqs_doit();
  • expkey_notify(), so cache misses multicast NFSD_CMD_CACHE_NOTIFY to userspace.

That same commit was independently bisected last week by Paul Moore as the cause of a Fedora Rawhide mount.nfs: Connection refused regression on a trivial localhost mount — a reminder that this path is already on the critical path for clients, not just a fuzzer curiosity.

A sibling syzbot report, filed eleven minutes later the same day, hangs in the matching dump handler nfsd_nl_expkey_get_reqs_dumpit. Together they say: both directions of the new fh-cache netlink upcall are now participating in the nfsd_mutex stampede.

Same root cause already diagnosed this week

Two days before this report, Layton and Neil Brown triaged the earlier syzbot hang in nfsd_nl_cache_flush_doit. Layton's diagnosis applies here almost verbatim:

"The hard problem here is that rpcbind registration is done synchronously under the nfsd_mutex. To talk to rpcbind, the kernel has to create a RPC client, which does a RPC ping first. If rpcbind is down then it can take up to a minute for the RPC ping to time out."

And:

"If we couple those delays with a long list of listeners, then it's easy to see how to reproduce the hang."

In that thread the mutex holder was nfsd_nl_listener_set_doit. Here the dump does not name a listener_set task, but it does show nfsd_nl_threads_set_doit holding the lock — and thread-count changes also talk to rpcbind / bring the service up and down under nfsd_mutex. A ~60-second rpc_ping timeout, stacked a couple of times, is exactly 143 seconds of hung-task watchdog.

Brown's question from that thread is the design fork still open when this report arrived:

"Why are we waiting a whole minute for a local service to respond? If it hasn't responded in 1 second, is it ever really likely to?"

Layton's answer — a shorter timeout is necessary but not sufficient, because "even at 1s, you could easily cause a lockup warning with just a few hundred listeners" — is the reason this new report will not be fixed by touching nfsd_nl_expkey_set_reqs_doit itself. The expkey handler is an innocent waiter. The bug is that any nfsd netlink op, including the brand-new fh-cache downcall, takes the same global mutex that listener/thread setup holds across synchronous rpcbind I/O.

NFS client impact

This is a server-side hang, but it sits on a path NFS clients actually use:

  • File-handle cache downcalls. When a client presents an FSID the server has not cached, nfsd multicasts NFSD_CMD_CACHE_NOTIFY and waits for userspace to reply via expkey-set-reqs. If that handler is stuck behind nfsd_mutex for minutes, the client's LOOKUP/MOUNT simply does not complete. That is the same failure mode Paul Moore already hit as Connection refused on a localhost mount after 01c2305795a3.
  • Export-table updates. The dump also shows nfsd_nl_svc_export_set_reqs_doit holding the mutex. A wedged export downcall means newly published (or revoked) exports never become visible to clients.
  • Listener / thread control. nfsd_nl_threads_set_doit is one of the holders. If bringing nfsd up or changing thread count stalls on rpcbind while holding the mutex, every other control-plane op — including the ones clients indirectly depend on for mount — stalls with it.
  • NFSv2/v3 discovery. The underlying rpcbind-under-mutex problem is specifically a v2/v3 client-visibility issue: nfsd will serve without a successful registration, but clients that find the server via portmap see a missing or stale table.

For NFSv4.2 clients the damage is more about control-plane latency than wire protocol: inter-server copy, state reclaim, and admin-driven export changes all assume the netlink family stays responsive.

Status

  • Type: hung-task / DoS bug in the nfsd netlink control plane, exposing the new expkey (nfsd.fh) upcall as another victim of nfsd_mutex.
  • Reproducer: none. syzbot is fuzzing concurrent netlink commands against a PREEMPT_RT kernel; the lock dump is the reproducer.
  • Human reply: none in this thread as of 23 July. The related cache-flush thread already has a design discussion (shorten rpc_ping; drop/reacquire nfsd_mutex around listener batches; or async, ordered rpcbind registration) but no patches posted and nothing applied.
  • Fix tag requested: Reported-by: syzbot+de7e55e90abcbb58ae63@syzkaller.appspotmail.com.

Until the mutex is no longer held across rpcbind I/O — or until rpcbind I/O fails in well under a second — every new nfsd netlink command added this cycle is another hung-task report waiting to happen. This week's expkey report is that prediction coming true, eleven minutes before its dump-side twin.
