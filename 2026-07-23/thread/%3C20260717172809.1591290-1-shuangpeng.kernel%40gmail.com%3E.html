lockd NULL deref on lockowner allocation failure

Summary

lockd client crash on lockowner allocation failure

This week's linux-nfs traffic included a tightly scoped bug fix for the NFS client's NLM (lockd) path: a NULL-pointer dereference that can fire when a lockowner allocation fails. Shuangpeng Bai posted a three-line patch to fs/lockd/clntproc.c with no follow-up discussion in the window ending 2026-07-23. There is no protocol change and no new feature work here — only a defensive reordering of how NLM private state is attached to a VFS file_lock.

The defect is ancient. The patch tags Fixes: 1da177e4c3f4 ("Linux-2.6.12-rc2") and CCs stable@vger.kernel.org, so Bai is treating this as a long-standing crash that still belongs on the backport radar.

The crash path

Bai's commit message reconstructs a classic "partial initialization meets VFS teardown" failure. nlmclnt_locks_init_private() currently installs the NLM file-lock operations even when nlmclnt_find_lockowner() cannot allocate a lockowner. The caller, nlmclnt_proc(), then returns -ENOMEM, but that is not the end of the story. The VFS still tears down the half-initialized file_lock and calls locks_release_private().

That release path invokes nlmclnt_locks_release_private(), which unconditionally dereferences fl->fl_u.nfs_fl.owner. Because the owner was never installed, the kernel oopses. In Bai's words:

"nlmclnt_locks_init_private() installs NLM file lock operations even when nlmclnt_find_lockowner() fails to allocate a lockowner. nlmclnt_proc() then returns -ENOMEM, but the VFS still tears down the partially initialized file_lock and calls locks_release_private()."

And then:

"That invokes nlmclnt_locks_release_private(), which dereferences fl->fl_u.nfs_fl.owner and crashes because the owner was never installed."

The important client-side implication is that a memory-pressure failure on the lockowner object is not a clean -ENOMEM return. It is a crash in the lock teardown path, which is exactly the kind of latent NFS client bug that only shows up when allocations start failing.

The proposed fix

The patch does not change lockd protocol behavior, lockowner lifetime, or NLM RPC sequencing. It only makes the private-state setup atomic with respect to VFS lock ops:

  • Clear fl_ops before attempting to initialize NLM private state, so a failed allocation cannot leave NLM release callbacks attached to a lock that never got an owner.
  • Install the NLM lock operations only after a lockowner has been allocated successfully.

Bai summarized the intent as:

"Clear fl_ops before attempting to initialize the NLM private state, and install the NLM lock operations only after a lockowner has been allocated successfully."

That is a small but well-aimed NFS client robustness fix: if lockowner allocation fails, the VFS must not later call into nlmclnt_locks_release_private() against a NULL owner.

Status this week

The thread is a single message. No Acked-by, Reviewed-by, or maintainer comment landed in this window, and no v2 appeared. For NFS client development, the patch is still an open, unreviewed candidate: a stable-worthy lockd crash fix sitting on the list, waiting for review of the fl_ops ordering and confirmation that clearing ops early does not race with other file_lock teardown paths.
