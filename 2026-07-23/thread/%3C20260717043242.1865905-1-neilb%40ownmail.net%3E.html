nfsd: NeilBrown posts v4 of nfs4_create_file() refactor — fixes mounted-on-file handling for NFSv2/v3

Summary

nfsd: NeilBrown's nfs4_create_file() refactor reaches v4 — now fixing the NFSv2/v3 mounted-on-file paths

Type: Refactoring series with embedded bug fixes (NFS server / nfsd)

The week in one line

On Friday, July 17, NeilBrown posted the fourth revision of his long-running series to untangle nfs4_create_file() in the Linux NFS server — an 18-patch set whose stated purpose this round is narrow but important: the cover letter says simply,

"This version fixes the v2 and v3 code for handling CREATE of mounted-on files."

That is the headline change versus last week's v3: the series grew from 17 to 18 patches, with a brand-new patch (02/18) that pulls check_nfsd_access() into nfsd_cross_mnt(), and an expanded mounted-on-file fix that now covers NFSv2 and NFSv3, not just v4.

Bridging prior weeks

This is the fourth posting of the same effort (v1 → v2 → v3 → v4). Last week's v3 summary captured two things that directly shaped this revision:

  1. Chuck Lever had reviewed the mounted-on-file fix and found it incomplete — it "doesn't build here with CONFIG_NFSD_V2=y" and the NFSv2/v3 create paths had refcount and behavior problems (a missing exp_get(), wrong export in fh_compose() after a mount crossing, inconsistent attribute handling). NeilBrown promised fixes "in a day or 3."
  2. Jeff Layton ran an LLM-assisted review pass over the whole v3 series and flagged several regressions — including a high-severity read-only OPEN regression (an unconditional mnt_want_write() making plain read-only opens fail with NFS4ERR_ROFS) and a medium-severity endianness bug where a __be32 status was compared against the raw host enum NFSERR_NOENT instead of nfserr_noent.

v4 is NeilBrown's response to both. The v5 cover letter, posted just hours later on the same day, confirms exactly which of Jeff's findings were still live: NeilBrown wrote,

"For for another version so soon - I hadn't noticed Jeff's LLM results. Most of the issue raised there were already addressed I think, but the using nfserr_noent instead of NFSERR_NOENT, and adding a condition on the call to mnt_want_write() in the final patch were still needed."

So v4 (this thread) addresses Chuck's v2/v3 build/refcount complaints; the two remaining Jeff items carried into v5.

The bug fixes in this revision

1. Honour client-provided attributes for NFS4_CREATE_EXCLUSIVE4_1 (patch 01/18) — unchanged from v3, still a real correctness fix with a Fixes: tag pointing at commit ac6721a13e5b and a Reviewed-by from Jeff Layton. The server was silently dropping client-requested attributes on an exclusive v4.1 create:

"When the mtime/atime are set to hold the verifier, the other ia_valid flags are cleared, so no attributes requested by the client are used."

NeilBrown traces it to code "originally written for NFSv3 where NFS3_CREATE_EXCLUSIVE never includes attributes" that was never properly extended when v4.1 added attribute support to exclusive creates. See patch 01/18.

2. New: move check_nfsd_access() into nfsd_cross_mnt() (patch 02/18) — the structural change that makes the v2/v3 fix safe. The rationale is defensive:

"Whenever we cross a mount point, we need to check_nfsd_access() for v4. So move the call into nfsd_cross_mnt() in the place where we actually do cross. This avoids the possibility of calling nfsd_cross_mnt() without the required check_nfsd_access()."

It also drops an always-false argument from check_nfsd_access() and changes nfsd_cross_mnt() to return an nfserr rather than an errno. See patch 02/18.

3. Correctly handle CREATE of mounted-on files (patch 03/18) — now spanning nfs3proc.c, nfs4proc.c, and nfsproc.c (i.e., v2, v3, and v4), directly answering Chuck's review. The underlying defect: Linux lets a filesystem be mounted on top of a regular file, and nfsd mostly supports that under crossmnt, but an unchecked CREATE on such a name returned the underlying file's handle rather than the mountpoint's:

"if CREATE is used on an existing mounted-on file, the filehandle for the underlying file is returns. The client will then continue to use that filehandle."

The visible symptom — cat /mnt/file works until a dcache flush, after which >> /mnt/file writes to the wrong (mounted-on) file. NeilBrown's fix checks the dcache for a mounted name and returns that handle, "possibly truncating." He is candid about its age:

"This probably has always existed since before the git history."

See patch 03/18.

The refactoring arc (patches 04–18)

The remainder of the series is the same incremental, reviewable march toward a unified vfs_lookup_open() VFS API that was described last week, now renumbered for the extra patch. Notable steps:

  • Patches 04–07: replace fh_fill_both_attrs() with fh_fill_post_noop(), move fh_want_write() and NFS-specific preamble code earlier, and collapse a "subtle" goto difference between EXCLUSIVE and EXCLUSIVE4_1 replay handling.
  • Patch 08 (let VFS report if file was created): an important correctness improvement for atomic_open — nfsd previously assumed a failed-lookup-then-successful-create meant the file was created, which "may not be the case - some other actor might have created the file between the lookup and the create." It now keys off the FMODE_CREATED flag. See patch 08/18.
  • Patches 09–12: move the NFSD_MAY_CREATE check earlier, defer fh_want_write() failure until creation is confirmed needed, "(almost) always open file," and reduce the directory-lock range (releasing start_creating() before setattr).
  • Patches 13–16: open-code nfsd4_vfs_create(), move code out of the d_really_is_negative() branch "to make it easier to switch to using vfs_lookup_open()," reduce the want-write range, and move protocol-version checking out of nfsd_check_obj_isreg().
  • Patches 17–18 (the payoff): extract all VFS-specific code into a new do_lookup_open() function, then use it for non-creating OPENs too. The end goal is explicit:

"It is planned to provide a vfs_lookup_open() in vfs code which provides this functionality. This will share more code with the syscall open path, and make it easier to modify locking at the VFS level." See patch 17/18

One trade-off worth flagging from patch 04/18: moving fh_fill_pre_attrs() out of the directory inode lock means nfsd can no longer provide "atomic" WCC pre/post data, so a new fh_fill_pre_attrs_unlocked() marks attributes non-atomic — "unfortunate but inevitable if we are ever to allow concurrent updates in a directory."

Status and outlook

As of the end of this week's window (July 23), this v4 thread has no reviewer replies yet — it consists solely of NeilBrown's 18-patch posting. The discussion has effectively moved on: hours after v4 landed, NeilBrown posted v5 to fold in the two remaining items from Jeff's LLM review (the nfserr_noent endianness fix and the conditional mnt_want_write()).

Bottom line: this is a server-side (nfsd) refactoring-and-bugfix series, not an NFS client change or a protocol change. Its significance for NFS development is twofold — it fixes two real correctness bugs (dropped attributes on exclusive v4.1 creates, and wrong-handle returns on mounted-on files across v2/v3/v4), and it lays the groundwork for a shared vfs_lookup_open() that would let nfsd reuse VFS open-path code and relax directory locking for better concurrency. The series is still in active review; expect the v5 thread to be where the next round of feedback lands.
