NFSD v7.2 pull: lockd NLMv3 GRANTED_MSG client callback fix merged

Week of 2026-07-17 to 2026-07-23 | Thread: [GIT PULL] Another NFSD fix for v7.2

Overview

This thread is a bug-fix pull request, not a feature or protocol change. On 21 July, Chuck Lever asked Linus to pull a single lockd commit for v7.2: Olga Kornievskaia's lockd: fix NLMv3 GRANTED_MSG handling. The change is three lines in fs/lockd/svcproc.c and repairs a v7.2-rc regression that broke the NFS client path for blocked NLM locks. The following day the kernel.org pr-tracker bot reported the tag merged into torvalds/linux.git.

There was no technical debate in-window. The substance of the fix was settled in late June, when Kornievskaia posted the original patch and Lever split it so the NLMv3 and NLMv4 halves could land independently.

The pull

Lever's request is tagged nfsd-7.2-2 and sits on top of the earlier v7.2-rc UAF fix (92ea163c773c, "NFSD: Prevent post-shutdown use-after-free in NFSD_CMD_UNLOCK_FILESYSTEM"). The tag tip is 5c4851e4cdfc ("lockd: fix NLMv3 GRANTED_MSG handling", 17 July). He summarized the contents as:

"Issues reported with v7.2-rc:

  • Fix issue with NLMv3 GRANTED_MSG introduced in v7.2"

The tree is https://git.kernel.org/pub/scm/linux/kernel/git/cel/linux.git tag nfsd-7.2-2. Diffstat: fs/lockd/svcproc.c | 3 ++-.

On 22 July the pr-tracker bot confirmed Linus had taken it:

"has been merged into torvalds/linux.git: https://git.kernel.org/torvalds/c/5a52217525cb394117d92722b7f0fec510c882b4"

Why this is a client bug, even though it shipped under NFSD

GRANTED_MSG is the NLM callback the lock server sends to the NFS client when a previously blocked lock can now be granted. The client-side lockd service receives that RPC and must call nlmclnt_grant() so the waiting fcntl/flock completes. It is not a server-side TEST/LOCK/CANCEL/UNLOCK request, and it does not need nfsd to be running on the receiving host.

Kornievskaia's original June patch (bridged here only for the technical argument) stated the failure mode that v7.2 introduced when lockd's NLMv3 procedures were converted to xdrgen:

"GRANTED_MSG is a server-to-client callback, so it runs on the client, where nfsd never registers nlmsvc_ops. The nlm4svc_lookup_host()/nlm3svc_lookup_host() helpers are for the server-side request handlers (TEST/LOCK/CANCEL/UNLOCK), which reach nlmsvc_ops->fopen and must reject requests when nfsd isn't running. GRANTED_MSG only calls nlmclnt_grant(). Instead, of calling nlm4svc_lookup_host()/nlm3svc_lookup_host() (which results in a client failing a GRANTED_MSG call) call nlmsvc_lookup_host."

In other words, the xdrgen conversion (6c534ad999b6, "lockd: Use xdrgen XDR functions for the NLMv3 GRANTED_MSG procedure") wired the client callback through the server host-lookup helper. That helper refuses work unless nlmsvc_ops is registered — something only nfsd does. A pure NFS client, or any host that is not currently exporting, would then drop GRANTED_MSG. Blocked NLMv3 locks would hang even after the remote lockd had granted them.

The this-week pull is the NLMv3 half of that repair. Lever had already explained, when applying the original combined patch, why it was split:

"The fix LGTM.

Looking at this now, I see the patch targets two distinct stable kernels. Therefore IMO this does actually need to be two separate patches. I will split the patch when I apply it to nfsd-testing."

NeilBrown had reviewed the original with a naming note that still applies to the three-line v7.2 change:

"That is a subtle difference between nlm4svc_lookup_host() and nlmsvc_lookup_host(). I wonder if making the names more distinct would help..."

The v7.2 pull does not rename anything. It only restores nlmsvc_lookup_host() on the NLMv3 GRANTED_MSG path so a client without nfsd can accept the grant callback again.

Client-development impact

This is one of the more user-visible lockd regressions of the v7.2 cycle:

  • Symptom: an NFS client waiting on a blocking NLM lock never wakes after the server grants it, because the incoming GRANTED_MSG is rejected during host lookup.
  • Scope: NLMv3 only in this pull. The matching NLMv4 fix (against 62721885e861) was carved out for a different stable base.
  • Who hits it: any Linux NFS client using NLM (NFSv2/v3 file locks) that does not have nfsd loaded — the common case for desktop and compute nodes.
  • Size: two insertions and one deletion in fs/lockd/svcproc.c. No XDR, protocol, or API change.

For client maintainers the takeaway is that the xdrgen conversion of lockd's server-side procedures accidentally classified a client callback as a server request. The helper names nlm3svc_lookup_host versus nlmsvc_lookup_host hid that distinction, exactly as NeilBrown flagged.

Conclusions

The request is closed. Lever sent a one-commit v7.2 follow-up pull on 21 July; Linus merged nfsd-7.2-2 on 22 July at 5a52217525cb. The only in-window human message is the pull itself; the bot's merge notice is the last word.

The technical conclusion was already on the record from June and is now in mainline for v7.2: GRANTED_MSG must use nlmsvc_lookup_host(), not the nfsd-gated nlm3svc_lookup_host(), because the RPC runs on the NFS client. That restores blocked NLMv3 lock completion on hosts that do not run nfsd.
