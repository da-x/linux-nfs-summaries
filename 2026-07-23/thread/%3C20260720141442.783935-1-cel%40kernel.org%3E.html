NFS filehandle types split into linux/nfs_fh.h

Summary

NFS filehandle types split into linux/nfs_fh.h

Week of 2026-07-17 to 2026-07-23 | Thread: [PATCH 0/3] Move NFS filehandle defs into separate include

Overview

This thread is a header-hygiene refactor, not a protocol change and not a functional bug fix. On 20 July, Chuck Lever posted a three-patch series that extracts struct nfs_fh — the in-kernel NFS filehandle type used throughout the client, lockd, and related code — from the heavy linux/nfs.h umbrella header into a new, minimal linux/nfs_fh.h. The series also lands two first consumers: lockd, which only needed the filehandle type, and NFSD's pNFS flexfile layout, which was storing a client filehandle type for a server object.

There were no replies this week. The series stands as posted, with Lever noting that more consumers will switch in follow-on work.

Motivation: linux/nfs.h is too heavy for filehandle-only users

The cover letter (Chuck Lever, PATCH 0/3) states the problem directly:

"struct nfs_fh is defined in linux/nfs.h, which also pulls in cred.h, a pair of sunrpc headers, and uapi/linux/nfs.h. A consumer that wants nothing but the file handle definition drags all of those items with it."

That matters for NFS client development as much as for the server. struct nfs_fh is the client's on-the-wire filehandle representation: it is what nfs_compare_fh(), nfs_copy_fh(), and friends operate on, and it is included from a surprising number of places that do not otherwise want credentials, SunRPC internals, or the UAPI NFS constants. The series is plumbing: isolate the type so later client (and lockd/server) patches can include just the filehandle definition.

Lever is explicit that this is the start of a conversion, not the whole job:

"This series introduces two consumers for this header. More will follow in subsequent series."

Patch 1/3: Add linux/nfs_fh.h, keep linux/nfs.h as a compatibility wrapper

PATCH 1/3 creates include/linux/nfs_fh.h and moves struct nfs_fh plus its helpers there. linux/nfs.h then includes the new header so existing #include <linux/nfs.h> sites — including the NFS client — keep building without a flag day.

The conversion path is spelled out:

"Over time, consumers can then replace #include <linux/nfs.h> with #include <linux/nfs_fh.h>."

While moving the code, Lever also does two small clean-ups that touch client-visible helpers:

  • kernel-doc comments are added for the filehandle operations;
  • nfs_compare_fh() is converted to return bool instead of an integer.

That last change is a type-correctness tweak rather than a behavior change: comparison is a yes/no question, and making the helper return bool matches how the NFS client already treats filehandle equality. Existing callers that test the result as a boolean condition continue to work.

Patch 2/3: lockd drops the extra linux/nfs.h surface

PATCH 2/3 is the first real consumer of the split. lockd talks NLM, not NFS proper, but it still has to carry NFS filehandles in its XDR and tracing paths. Lever's diagnosis:

"lockd references "struct nfs_fh" but none of the other definitions in linux/nfs.h. That header also pulls in cred.h, several sunrpc headers, and uapi/linux/nfs.h, none of which lockd needs."

The patch switches fs/lockd/xdr.h to linux/nfs_fh.h and deletes now-redundant linux/nfs.h includes from fs/lockd/svc.c and fs/lockd/trace.h. For client-side locking this is the interesting part of the series: NLM on the client and server share this lockd code, and shrinking its include graph is a prerequisite for later lockd/NFS client header disentanglement.

Patch 3/3: NFSD flexfile layout stops borrowing the client filehandle type

PATCH 3/3 is a small but pointed type-correctness fix on the server, CCed to Thomas Haynes. struct pnfs_ff_layout was holding its filehandle as struct nfs_fh — the client type — even though the value is copied straight out of struct svc_fh, whose fh_handle member is struct knfsd_fh.

Lever's argument:

"Storing the layout's copy as struct nfs_fh instead forced an open-coded field-by-field copy between two unrelated structures."

"Hold the layout's file handle in struct knfsd_fh so the copy uses the canonical fh_copy_shallow() helper and server code no longer reaches into a separate file handle representation."

This is not a client bug, but it is relevant to client developers because it draws a hard line between the two filehandle representations:

  • struct nfs_fh — client / shared NFS filehandle, now in linux/nfs_fh.h;
  • struct knfsd_fh — NFSD's server-side handle, copied with fh_copy_shallow().

The flexfile layout was papering over that distinction with a field-by-field copy. After this patch, server pNFS layout code stays on the server type, and the newly isolated client type is no longer an accidental dumping ground for knfsd handles.

Evolution and conclusions

The discussion did not evolve this week: four patches, no review tags, no nacks. Conclusions as of 23 July:

  • This is infrastructure, not a protocol change. Wire format, XDR, and client RPC behavior are untouched. The user-visible NFS client is unaffected except insofar as nfs_compare_fh() now returns bool.
  • The client filehandle type is being given a home of its own. That is the series' main value for NFS client development: future client patches can include linux/nfs_fh.h without dragging cred.h, SunRPC, and UAPI NFS headers into every compilation unit that merely needs to name or compare a filehandle.
  • lockd is the first converted consumer, which is the right first step: it is a heavy user of struct nfs_fh that never wanted the rest of linux/nfs.h.
  • The flexfile change is a type-safety buglet, not a reported crash: using knfsd_fh plus fh_copy_shallow() replaces an open-coded copy between unrelated structs.
  • More conversions are promised. Lever's cover letter is a marker that this series is a foundation for subsequent include-graph clean-ups. Those follow-ons had not landed on the list by the end of this week.

Until reviewers weigh in, the series is best read as a low-risk, client-relevant header split that also stops NFSD from treating struct nfs_fh as a generic bag of filehandle bytes.
