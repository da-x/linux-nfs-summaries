Trond rejects extra rdirplus modes, asks for traces instead

Summary

Maintainer shuts down extra rdirplus knobs; diagnosis first

This week's activity is a short but decisive continuation of last week's feature request from NetApp engineer Jorge Mora. The thread is not a protocol change and not a posted bug-fix patch. It is a client-side feature request — new rdirplus= mount-option values — motivated by a performance regression after the Linux NFS client grew READDIRPLUS heuristics. The only new technical content this week is the first maintainer reply, and it is a hard no on more knobs.

Brief bridge from last week

On 8 July, Mora reported a customer who saw "significant performance degradation after switching from Rocky Linux 8.7 clients to a 6.12 upstream kernel," specifically "a dramatic increase in GETATTR/LOOKUP operations" while traversing a read-only directory tree and fetching attributes. He blamed the client's READDIRPLUS heuristics, said rdirplus=force on RHEL 9.7 cut the GETATTR/LOOKUP storm but "introduces other issues," and asked for either rdirplus=legacy (bypass the heuristics entirely) or rdirplus=eager (a less aggressive READDIRPLUS policy than force). No maintainer reply landed in that window.

This week: a ping, then a firm veto

On 17 July, Mora re-sent the request to the list, adding Stephen Abbene and Peter Yoo, with the original text unchanged. The next day, NFS client maintainer Trond Myklebust answered and closed the door on expanding the option space.

He first restated what the client already exposes:

"We already have 3 different modes for readdirplus: the default heuristic based rdirplus, off (nordirplus/rdirplus=none) and always on (rdirplus=force)."

Then the policy line, in language that leaves little room for a follow-up patch that just adds another enum value:

"I'm violently opposed to adding yet another, and particularly if it is just tagging a slightly different heuristic."

That is the central client-development conclusion of the week. The existing trio — heuristic default, none, and force — is treated as the complete user-visible API. A fourth mode whose only job is "legacy" or "slightly more eager" is, in the maintainer's view, the wrong way to paper over a workload-specific miss in the default policy.

What he wants instead: traces, then maybe a heuristic fix

Myklebust did not deny that a read-only directory walk can go wrong under the current default. He redirected the conversation from mount-option proliferation to instrumented diagnosis of the existing heuristic:

"So if you're seeing problems with a read-only directory, then I suggest you use the tracepoints that are already in the code to show what is going wrong, and determine why. We can then have an informed discussion as to whether or not we need to have another round of changes for the current default heuristics."

In other words: if 6.12 is issuing too many GETATTR/LOOKUPs on a tree walk, that is a candidate bug / heuristic-tuning problem in the client, not a reason to grow rdirplus= again. The implied next step for NetApp (and the customer) is to capture the existing readdirplus tracepoints, show where the heuristic declines READDIRPLUS or drops cached attributes, and only then argue for a change to the default policy. No such traces, and no patch, appeared this week.

Application-level alternative: statx() with AT_STATX_DONT_SYNC

He also offered a workload-shaped workaround that does not touch mount options at all. For a tree whose contents "are also read-only and not expected to change," he asked why the customer cannot:

"use statx() with the AT_STATX_DONT_SYNC flag to just retrieve whatever is currently in the cache?"

That is a VFS-level hint, not an NFS protocol change: accept possibly stale cached attributes instead of forcing the client to revalidate every entry. For a read-only traversal that is already paying for extra LOOKUPs, it is a way to stop generating those RPCs without flipping the mount into rdirplus=force (the mode Mora said causes "other issues").

Why this matters for NFS client development

The exchange is a clean snapshot of current client policy around READDIRPLUS:

  • The heuristic that landed between the 8.x-era clients and 6.12 is now the default, and it is known to be workload-sensitive. A storage-vendor customer hitting a GETATTR/LOOKUP storm on a read-only walk is exactly the class of regression that heuristic was supposed to manage.
  • rdirplus=force and rdirplus=none remain the supported escape hatches. They are coarse on purpose. Mora's report that force "introduces other issues" is acknowledged only implicitly: the maintainer would rather fix the default heuristic than add legacy/eager as a fourth and fifth escape hatch.
  • New mount options that merely retune the same heuristic are explicitly off the table. Future work, if any, is expected to be trace-driven changes to the default READDIRPLUS heuristic (a client bug-fix / behavior tweak), possibly paired with application use of statx(..., AT_STATX_DONT_SYNC) for static trees.

State of play

The discussion is paused pending data. Mora's request for rdirplus=legacy / rdirplus=eager has been rejected. No patches were posted. The ball is in the reporters' court to come back with tracepoint evidence that the default heuristic is misfiring on this read-only walk, at which point Myklebust left the door open to "another round of changes for the current default heuristics." Until then, the supported client knobs remain the three modes already in tree.
