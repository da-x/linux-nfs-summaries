fhandle: Duplicate detached-mount NULL-deref patch already fixed upstream

Overview

This week the linux-nfs list saw the only follow-up to Guangshuo Li's July 8 patch that tried to plug a NULL-pointer dereference in capable_wrt_mount() when a mount is detached under an in-flight file-handle decode. VFS maintainer Christian Brauner closed the thread in a single sentence:

"That's already fixed upstream."

The discussion is a bug fix (race / NULL deref in the VFS fhandle path that NFS clients use for open_by_handle_at() and related mount-handle operations). It is not a protocol change and introduces no new NFS client feature. The week's activity is the rejection of a late, overlapping submission rather than a new technical design debate.

Prior week, briefly

As summarized for the week ending 2026-07-09, Li's three-line change in fs/fhandle.c treated a detached mount as not capable for the permission-relaxation path: if the RCU-protected mnt_ns read yields NULL, return false instead of passing mnt_ns->user_ns to ns_capable(). The race is a follow-on to commit 40ab6644b996 ("fhandle: fix UAF due to unlocked ->mnt_ns read in may_decode_fh()"), which RCU-protects the namespace object but does not guarantee mount->mnt_ns stays non-NULL between is_mounted() and capable_wrt_mount(). No review had landed inside that earlier window.

This week's close-out

Two weeks later, Brauner's reply is the first (and only) in-window message. He quoted Li's commit message and Signed-off-by and offered no further review comments, no requested respin, and no alternative patch. The implication is that the tree already contains an equivalent defensive check, so Li's patch should not be applied again.

That earlier landing is visible on the list from 1 July. David Lee of Trail of Bits posted essentially the same helper change under the subject [PATCH] fhandle: reject detached mounts in capable_wrt_mount(), with a slightly different Fixes: tag (620c266f3949, "fhandle: relax open_by_handle_at() permission checks") and an explicit Cc: stable. Lee described the same window — a cloned tree from open_tree(..., OPEN_TREE_CLONE) can be dissolved on fput while open_by_handle_at() is between is_mounted() and the later READ_ONCE(mount->mnt_ns) — and argued the relaxed permission path must stay conservative:

"Return false when the RCU read observes a detached mount. This keeps the relaxed permission path conservative: a mount no longer attached to a namespace cannot authorize open_by_handle_at() access."

Jeff Layton reviewed that version the same day ("Seems sane.") and Brauner applied it to vfs.fixes as b2f046af8c6c. Li's July 8 submission, posted a week after that merge, is therefore a duplicate rather than a competing design.

NFS client relevance

fs/fhandle.c is VFS, not fs/nfs/, but it is on the NFS client hot path for handle-based open and for any workload that races MNT_DETACH / OPEN_TREE_CLONE teardown against open_by_handle_at(). A NULL deref here is a local Oops (denial of service), not a protocol-level failure. With Lee's fix already in vfs.fixes (and slated for linux-next / stable), NFS client trees that pick up current VFS fixes inherit the defensive mnt_ns == NULL check; Li's patch does not need a second merge.

Classification and status

  • Type: Bug fix (NULL pointer dereference / detach race in capable_wrt_mount())
  • Subsystem: VFS fhandle (affects NFS client handle-open / detach paths)
  • This week's outcome: Duplicate rejected; the equivalent Trail of Bits fix is already upstream in vfs.fixes
  • Remaining work in this thread: None. No further replies are needed unless someone finds a hole in the applied b2f046af8c6c change.
