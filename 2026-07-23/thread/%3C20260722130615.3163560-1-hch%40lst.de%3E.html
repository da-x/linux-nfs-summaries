Summary

swap_ops updates: zram single-folio writes and NFS/SMB ops pushdown

Overview

Christoph Hellwig posted a three-patch follow-on to the swap-ops work already sitting in mm-unstable, aiming at two distinct problems: a zram performance regression from batched swap I/O, and a double-indirect call path that still sits between MM and filesystem-based swap, including swap-over-NFS. Memory-management maintainer Chris Li and zram reporter Kairui Song both endorsed the functional patches this week; the only open request is a clearer commit message on the header-extraction patch. Hellwig posted a v2 the next day as a separate series.

This is not a protocol change. It is a swap-subsystem refactor plus a performance bug fix, with concrete NFS client code movement in fs/nfs/file.c and fs/nfs/direct.c.

Background

In May, Hellwig had already sketched a merge-order plan for related swap work: Kairui Song's swap-table series first, then swap_ops, then the larger swap_activate interface rework. That earlier swap_activate series moved swapfile operations onto file_operations and mechanically updated the NFS client. This week's series is the next step: make swap_ops themselves pluggable so filesystem swap no longer bounces through a generic MM helper.

The series

Hellwig introduced the set on July 22 as a direct sequel to the in-tree swap-ops work:

"this series is a follow on to the swap ops series now in mm-unstable. The first patch reintroduces direct folio writes for synchronous swap files, the other two remove the double indirect for file system based swap." — Christoph Hellwig

Patch 1: restore single-folio writes for synchronous swap

Patch 1 is the important bug-fix / performance fix. Kairui Song had reported that zram is faster when each folio is submitted immediately rather than batched, because classic LRU scanning wants the folio writeback bit cleared inside the scan loop. Hellwig's 11-line change in mm/page_io.c kicks off I/O for synchronous devices on every iteration instead of waiting for a batch.

Chris Li acked it the same afternoon (Acked-by: Chris Li). The next day Kairui, the original reporter, confirmed the approach:

"Looks good, thanks!" — Kairui Song

That patch is therefore closed from both the MM-maintainer and reporter sides.

Patch 2: export swap_ops via a new public header

Patch 2 creates include/linux/swap_ops.h and moves the declarations of swap_iocb, swap_ops, and swap_ctx out of mm/swap.h so implementations can live outside mm/page_io.c. Hellwig flagged an unfortunate naming collision with the existing, unrelated swapops.h:

"Note that there already is a swapops.h header, which is totally unrelated to struct swap_ops. The close naming is a bit unfortunate, but I could not think of a better name for this header." — Christoph Hellwig

Chris Li did not ack this one. He asked whether the commit is a pure code move or whether it also changes a functional/API contract, and he wanted that spelled out in the commit message:

"Can you please clarify if this commit introduces any functional or API level change this commit other than moving the code around? I don't think so, but I just want some clarification. Maybe there is a minor API change to remove the double indirection that I don't see. Anyway, it would be better to spell it out in the commit message." — Chris Li

No reply landed on this v1 thread. Hellwig's v2 series the next morning (<20260723054622.3460249-1-hch@lst.de>) is the implied follow-up.

Patch 3: NFS and SMB grow their own swap_ops

Patch 3 is the NFS-client-facing change. Today, filesystem swap still takes two indirect calls: MM swap_ops then the filesystem swap_rw method. Hellwig collapses that by letting the filesystem supply the swap_ops table itself.

The mechanism is a refactor of swap_fs_submit into swap_fs_prepare_rw, which initializes the iov_iter on the caller's stack so NFS and SMB can invoke it directly. Those filesystem-specific ops are then handed to swap_fs_activate. On the NFS side that means:

  • fs/nfs/direct.c loses the old 20-line swap-direct helper.
  • fs/nfs/file.c gains the filesystem-local swap_ops and wires them through activate.
  • include/linux/nfs_fs.h and include/linux/fs.h drop the now-unused swap_rw hook.
  • VFS documentation (locking.rst, vfs.rst) is updated to match.

SMB (fs/smb/client/file.c) gets the same treatment, so swap-over-CIFS follows the same contract.

Chris Li, who had been waiting to see how the double hop would actually disappear, was unambiguous:

"I am very happy to see the direction this patch is going. Now I see how to get rid of the double indirection. You convinced me with flying colors." — Chris Li

He acked the patch.

NFS client impact

This is the first series in the current swap-ops campaign that changes how the NFS client actually performs swap I/O, rather than just relocating activate/deactivate hooks. After this lands, swap-over-NFS no longer goes MM swap_ops → generic swap_rw → nfs_direct/nfs_file helpers. NFS owns the ops vector and calls swap_fs_prepare_rw itself. That is a cleanup, not a protocol or on-the-wire change: NFSv3/v4 swapfile semantics are unchanged, but any future NFS swap work must implement struct swap_ops rather than a VFS swap_rw method.

No NFS-specific review comments arrived this week. The discussion stayed on the MM list side (Hellwig, Li, Song). The code movement in fs/nfs/file.c and the deletion in fs/nfs/direct.c are presented as mechanical consequences of the new helper.
