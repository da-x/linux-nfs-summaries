Folio-alloc cleanups: reviews land, but internal.h vs. public wrappers stays unresolved

Summary

Type: API cleanup / header-hygiene series in mm — not a protocol change and not an NFS bug fix. The only NFS-adjacent footprint remains last week's mechanical rename in net/sunrpc/svc.c. This week's traffic is a design argument about how (and whether) to hide mempolicy-aware folio allocation so a later series can thread alloc_flags through the allocator without inventing another GFP flag.

Last week Brendan Jackman posted the three-patch "yet more cleanups for page_alloc APIs" series on mm-new. Patch 1/3 moves unused-outside-mm mempolicy helpers into a new mm/mempolicy.h; 2/3 replaces __folio_alloc_node() with folio_alloc_node() treewide (including sunrpc); 3/3 pulls __folio_alloc() into mm/page_alloc.h. Matthew Wilcox had already objected that hiding mempolicy-aware allocation "says allocations which respect mempolicy are only for core mm." Jackman answered that mempolicy is a public concept, but this particular function has no external callers, and the real goal is adding an mm-internal alloc_flags argument (ALLOC_UNMAPPED for AS_NO_DIRECT_MAP). That question was still open when the previous window closed.

This week the series picked up reviews, a leftover-header nit, and a much sharper debate over internal.h signalling, GFP-vs-ALLOC philosophy, and how much churn the alloc_flags experiment is already causing.

Reviews on 2/3 and 3/3

Gregory Price gave patch 2/3 a clean Reviewed-by. Minutes later he did the same for patch 3/3, noting he has a similar move in his forthcoming private-node RFC and wants it stacked on a solid mm-new base "so sashiko picks it up and people can actually apply it." Those two patches therefore look uncontroversial this week.

Patch 1/3: who is allowed to call mempolicy-aware allocation?

Price's first reply on patch 1/3 is the week's new stakeholder. He has been prototyping a module-side mempolicy interface so guest_memfd() can talk to mempolicy() cleanly, and he is only half-convinced the helpers belong behind an internal header:

"fwiw i've been fiddling with a module side mempolicy interface for a bit to allow a clean guest_memfd() + mempolicy() interaction [0][1]."

"I saw this and thought 'maybe, maybe not entirely'."

"there is definitely some oddities in the mempolicy uapi (internal-only flags that are exposed to the uapi is odd) that some of the interface is worth internalizing."

That lands squarely on Wilcox's earlier worry: guest_memfd is already a consumer of mempolicy-aware folio allocation, so "no external users today" is a fragile metric.

Wilcox returned to make the header-policy point explicit. He rejected Jackman's "no current external users" test as the reason to put symbols in internal.h:

"I don't think that should be the metric for moving things to internal.h. To me, internal.h is a signifier that these interfaces should only be used by the MM. Not that 'all current users are within the MM'."

On the ulterior motive — adding alloc_flags so ALLOC_UNMAPPED can implement AS_NO_DIRECT_MAP without a new GFP flag — Wilcox is unconvinced and too busy to prosecute a full design fight:

"Yeah. I'm not sold on the whole alloc_flags thing, but I'm too busy to sit down and think it through properly to get involved in a proper argument about how it should work."

His "entirely unresearched and ill-considered opinion" is that __GFP flags should be the ALLOC flags, with the translation done at compile time rather than inventing a second flag namespace "that special people can use for special purposes." He also warned about the archaeology problem of moving symbols without recording intent:

"We have a long history of people just moving stuff around in patches without knowing what the intent was if it should be moved."

Vlastimil Babka split the difference. On the header question he allowed that Wilcox might be right, but added a pragmatic counter:

"Perhaps. It can be also useful to move them outside only when someone asks."

On guest_memfd specifically he waved away the "external user" framing:

"guest_memfd is practically mm internal though, IMHO."

And he defended alloc_flags as an ugly-but-reversible workaround for GFP bit-space, not a new UAPI:

"Well it's basically a workaround for limited gfp flags space. So we can extend it without making that a cost for everybody, as long as those that need the new functionality are limited."

He also punctured Wilcox's compile-time-translation idea: the allocator already uses both GFP and ALLOC flags, GFP values are not always known at compile time, and the new bits under discussion are not about GFP_KERNEL vs GFP_ATOMIC context. Closing the loop on whether patch 1/3 is even required:

"Yep it's ugly and pragmatic, as usual. At least it's not immortalized as an UAPI, so we can deal with exploring in a wrong direction and fixing it later."

"I guess this patch is not critical to the rest, if that's an issue."

Babka separately caught a leftover in the same patch: the bulk-mempolicy helpers appear to have been copied into the new mm/mempolicy.h without being deleted from gfp.h.

The alloc_flags churn problem

Price's second note is the most operationally interesting message of the week for anyone following folio allocation. He is already paying the cost of the alloc_flags experiment in his private-node / new-zonelist work:

"alloc_flags is putting me between a rock and a hard place."

He had isolated private nodes via a zonelist selector, then — after Jackman's base work landed in mm-new — replaced that selector with ALLOC_ZONELIST_PRIVATE "to avoid yet more arguments." The result:

"I'll be posting with ALLOC_ZONELIST_PRIVATE on top of mm-new, but the churn is getting painful."

His proposed way out is not another flag, but an explicitly privileged allocator context, gated the way module exports are gated:

"It really seems like we just want an mm/ internal interface that exposes struct alloc_context for specific mm/ callers (see: compaction_context, migration_context, etc), and interfaces that keep this nonsense transparent for everyone else."

"Then if you want access to alloc_context interface, you need to get export approval for that component (similar to EXPORT_FOR_MODULES)."

"Just spitballing here, but the churn is killing me."

That is the closest this thread comes to an NFS-relevant architectural point: sunrpc's folio allocation is supposed to stay on the transparent side of that split. The series' only NFS touch is the 2/3 rename; nobody is proposing that RPC or the NFS client grow alloc_flags or alloc_context awareness.

Jackman restates the design and offers a fallback

Jackman's Thursday reply is this week's last in-window word, and it is the most careful statement yet of what he thinks the GFP/ALLOC split is actually for. He accepts Wilcox's signalling concern:

"Yeah I can see this both ways. It makes sense to only expose functions to the scope that currently needs them, but I think Matthew's right that moving it to internal.h does kinda signal 'this is private, don't touch this' which isn't intended."

He then argues the current dual-namespace is an inelegant but harmless attempt to solve two orthogonal problems at once — compact flags that fit in places like struct xa_node, versus freely extensible flags; and public versus private flags:

"The current ALLOC_/GFP_ flags split is something that kinda inelegantly attempts to solve both at once even though they are actually probably orthogonal requirements. Do we care about this inelegance? I think it's pretty harmless."

A "neat and tidy" redesign (one flags namespace, public/private enums, a separate compression step) would not, in his view, unlock anything practical. He would rather spend refactoring energy on small header splits than on that cleanup. On whether patch 1/3 is load-bearing, he agrees with Babka that it is not: ALLOC_UNMAPPED still needs an alloc_flags argument on this function, but he can introduce the __ internal variant plus a public wrapper from day one. The remaining choice is purely aesthetic/political:

"It's just a question of whether we prefer:"

"- 'Yuck, there's a public wrapper here that we don't actually need', or"

"- 'We hid this mempolicy API and people might think we'd NACK a patch to un-hide it'."

Where things stand

Patches 2/3 and 3/3 have Price's Reviewed-by and no outstanding objections. Patch 1/3 is still the open item: Wilcox does not want internal.h used as a "no current callers" dumping ground; Babka is willing to hide now and unhide on request, and notes the patch is optional for the rest of the series; Jackman has offered to skip the hide and ship a public wrapper immediately. The leftover bulk helpers in gfp.h still need a follow-up. Nobody recorded a merge decision this week, and the deeper alloc_flags / alloc_context design remains an active disagreement rather than a conclusion.

For NFS client readers the takeaway is unchanged from last week: this is mm header hygiene that happens to rename one sunrpc folio allocation site. No NFS protocol change, no client bug fix, and no new allocator knobs for the network filesystem path. The interesting follow-on — ALLOC_UNMAPPED / AS_NO_DIRECT_MAP, and Price's ALLOC_ZONELIST_PRIVATE private-node work — is still off-list of linux-nfs except insofar as it will change which folio helpers svc.c is allowed to call.

Further replies appear after this week's window (Jackman and Babka on July 29) and are out of scope here.
