NFSv4 client: NULL priv crash in nfs4_add_lease() cleanup

Summary

This week’s linux-nfs traffic includes a tightly scoped NFSv4 client bug fix from Zhansong Gao, posted 22 July with no replies yet in-window. The patch is not a protocol change and does not add a feature; it repairs a NULL-pointer crash in the application-lease path that was introduced when the client learned to hang local leases off NFSv4 delegations.

The crash: a race between lease add and delegation return

Gao’s one-file change to fs/nfs/nfs4proc.c targets nfs4_add_lease(). That helper is the client’s glue between VFS application leases (fcntl(F_SETLEASE) / generic_setlease()) and an NFSv4 delegation. When a lease is being installed and a concurrent delegation return wins the race, the add path must unwind the half-installed lease by calling nfs4_delete_lease().

The existing unwind passed the wrong object. Gao writes:

"When nfs4_add_lease() races with a delegation return, it calls nfs4_delete_lease() to clean up. Previously, it passed priv, which can legitimately be NULL. Passing a NULL priv eventually leads to a NULL pointer dereference in generic_setlease()."

That is a client-side correctness bug, not a server or wire-protocol issue. priv is the per-lease private state that the VFS lease machinery expects to find when tearing a lease down. On the race path it is allowed to still be NULL — the lease never fully attached — so feeding it into nfs4_delete_lease() and then into generic_setlease() is a use of an optional pointer as if it were mandatory. The resulting NULL deref is the kind of crash that only shows up under concurrent recall/return, which is exactly when application leases backed by delegations are supposed to be interesting.

The patch is a four-line edit (three insertions, one deletion) in nfs4proc.c. Gao tags it:

Fixes: e93a5e9306a5 ("NFSv4: Add support for application leases underpinned by a delegation")

That commit is the original client feature that made a local application lease rest on an NFSv4 file delegation instead of being a purely local VFS object. The bug is therefore a leftover in the feature’s error/race cleanup, not a regression in some later refactor.

Why this matters for NFS client development

Application leases-on-delegations are a client-only contract with the VFS: user-space can take F_RDLCK/F_WRLCK leases, and the NFS client promises those leases will break when the server recalls or the client returns the underlying delegation. The add path has to be atomic with respect to that recall/return. If the unwind uses a NULL priv, the client does not merely fail to install the lease — it oopses in generic_setlease(), taking down the process (and potentially more, depending on context) instead of returning an error to fcntl().

For client developers this is the classic “cleanup on the failure path used the success-path object” pattern:

  • The success path has a fully populated priv and can delete by that handle.
  • The race-with-return path does not, and must delete by a handle that is always valid (the file lock / flc context, not the optional private).

Gao’s commit message does not spell out the replacement argument in prose — the diff itself is the four-line substitution — but the diagnosis is unambiguous: do not pass a possibly-NULL priv into nfs4_delete_lease().

Status this week

The thread is a single message. There is no Reviewed-by, Acked-by, or maintainer comment in the 17–23 July window, and no follow-up revision. The patch stands as an unreviewed but clearly motivated client crash fix, bisecting to the application-lease-on-delegation work, and waiting for NFS client review before it can land.

No related discussion of the same NULL-priv path appeared elsewhere on the list this week. The only in-thread conclusion is Gao’s own: the incorrect argument is a latent NULL deref, and the one-line call-site correction is the fix.
