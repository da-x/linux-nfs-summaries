nfs-utils: haddr overflow fix committed to 2.9.2-rc6

This week's activity on the thread is a single maintainer ack that closes a user-space memory-safety bug. The discussion is a bug fix, not a protocol change or a new feature, and it lives in nfs-utils (utils/nfsd/nfsd.c) rather than the in-kernel NFS client.

Prior week, in brief

On 14 July, zhangjian (CG) reported a heap-buffer-overflow in the user-space nfsd daemon:

"when hcounter is not 0, haddr memory is not enough."

AddressSanitizer reproduced it with multiple -H host addresses (./utils/nfsd/nfsd -H 192.168.1.1 -H 192.168.1.2). The patch is a one-line allocation-size correction so haddr can hold more than one host when hcounter > 0. Chuck Lever did not dispute the fix, but noted the nfsd: subject prefix made the patch look like kernel nfsd work and flagged a DKIM BADSIG that could block future submissions.

This week: committed

Nine days later, nfs-utils maintainer Steve Dickson applied the change:

"Committed... (tag: nfs-utils-2-9-2-rc6)"

That is the entire in-window discussion. There is no further technical debate, no requested revision, and no kernel NFS client impact. The overflow is now queued for the nfs-utils 2.9.2 release train.

Conclusions

  • The one-line haddr allocation fix is accepted and tagged nfs-utils-2-9-2-rc6.
  • Chuck's earlier process notes (use nfs-utils: in the subject; fix DKIM) still stand as guidance for the submitter; they did not delay this commit.
  • Thread closed from a development standpoint: the user-space heap overflow is fixed, with no remaining open questions on the list this week.
