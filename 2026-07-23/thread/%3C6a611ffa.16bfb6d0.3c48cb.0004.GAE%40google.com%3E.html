syzbot: hung task in nfsd_nl_expkey_get_reqs_dumpit — dump side of the fh-cache upcall waits on listener_set

Summary

syzbot: hung task in nfsd_nl_expkey_get_reqs_dumpit — the dump side of the new fh-cache upcall waits on listener_set

Classification

This is a bug report — a hung-task / control-plane DoS, not a protocol change and not a new feature in its own right. Google's syzbot filed a single unreproduced report against the NFS server generic-netlink family. The hung function, nfsd_nl_expkey_get_reqs_dumpit in fs/nfsd/export.c, is the upcall dump handler: userspace (exportd/mountd) uses it to pull the pending nfsd.fh export-key cache requests so it can resolve FSIDs back into paths. That is the path NFSv2/v3 (and some v4) clients depend on when they present a file handle the server has not cached.

No human has replied in this thread. The lock dump is nevertheless decisive, and it is the same class of failure Jeff Layton and Neil Brown diagnosed two days earlier on the sibling nfsd_nl_cache_flush_doit hang — with a cleaner smoking gun than the expkey-set-reqs twin filed eleven minutes earlier the same afternoon.

What landed this week

On Wednesday, 22 July, syzbot reported a hung task on upstream HEAD af5e34a41cd6 (Merge tag 'mtd/fixes-for-7.2-rc4'):

"INFO: task syz.6.1915:12092 blocked for more than 147 seconds."

"Unfortunately, I don't have any reproducer for this issue yet."

The kernel is a PREEMPT_{RT,(full)} syzkaller build, tainted L (SOFTLOCKUP). The hung task is blocked in rt_mutex_slowlock → mutex_lock_nested → nfsd_nl_expkey_get_reqs_dumpit+0xfd/0xd40 at fs/nfsd/export.c:347, having entered via genl_dumpit / netlink_dump / sendmsg. It already holds the generic-netlink cb_lock and the per-socket nlk_cb_mutex-GENERIC, and it is waiting for the global nfsd_mutex.

syzbot asked that any fix carry:

"Reported-by: syzbot+16f257c80900b615cb35@syzkaller.appspotmail.com"

The lock dump: listener_set holds the mutex the dump is waiting on

The interesting evidence is not the hung stack itself — it is the "Showing all locks held in the system" listing, which names the holder:

TaskHandlerRole
syz.2.1652nfsd_nl_listener_set_doit (nfsctl.c:1964)holds nfsd_mutex (plus cb_lock)
syz.6.1915 (the hung task)nfsd_nl_expkey_get_reqs_dumpit (export.c:347)waiting on nfsd_mutex (already holds cb_lock and nlk_cb_mutex-GENERIC)

This is not a classic AB-BA deadlock. cb_lock is an rwsem, so both tasks can hold it as readers. The hung task is in D-state on the same coarse nfsd_mutex that listener_set is not releasing for more than 147 seconds. Every other nfsd netlink command — export-key dumps, export-key updates, thread-count changes, cache flushes — queues behind that hold.

That pairing is the cleanest confirmation yet of this week's diagnosis. Two days earlier, on the cache-flush hang, the holder was also nfsd_nl_listener_set_doit. The sibling expkey-set-reqs hang, filed eleven minutes before this one, showed nfsd_nl_threads_set_doit as a holder but did not name listener_set. This dump closes that gap: the get side of the new fh-cache upcall is stuck behind the exact handler Layton already identified as the long-hold site.

The NMI backtrace is a red herring for the NFS path. CPU 0's udevd was in do_raw_spin_lock under TOMOYO/slub during newfstatat; the SOFTLOCKUP taint and the rtnl_mutex holders (linkwatch_event, netns cleanup, rtnl_newlink) are incidental syzkaller noise. The nfsd story is entirely the listener_set / expkey_get_reqs_dumpit pile-up on nfsd_mutex.

Where nfsd_nl_expkey_get_reqs_dumpit came from

The hung handler is new this cycle. Jeff Layton's commit 01c2305795a3 ("nfsd: add netlink upcall for the nfsd.fh cache") added netlink cache-upcall support for the expkey (nfsd.fh) file-handle cache, mirroring the existing svc_export netlink pattern. It introduced:

  • an expkey attribute set (client, fsidtype, fsid, negative, expiry, path);
  • the expkey-get-reqs / expkey-set-reqs operations in the nfsd YAML spec;
  • nfsd_nl_expkey_get_reqs_dumpit() and nfsd_nl_expkey_set_reqs_doit();
  • expkey_notify(), so cache misses multicast NFSD_CMD_CACHE_NOTIFY to userspace.

That same commit was independently bisected last week by Paul Moore as the cause of a Fedora Rawhide mount.nfs: Connection refused regression on a trivial localhost mount — a reminder that this path is already on the critical path for clients, not just a fuzzer curiosity.

Together with the set-reqs twin, both directions of the new fh-cache netlink upcall are now participating in the nfsd_mutex stampede: userspace cannot learn which FSIDs need resolving (dumpit), and it cannot install the answers (doit).

Same root cause already diagnosed this week

Two days before this report, Layton and Neil Brown triaged the earlier cache-flush hang. Layton's diagnosis applies here almost verbatim:

"The hard problem here is that rpcbind registration is done synchronously under the nfsd_mutex. To talk to rpcbind, the kernel has to create a RPC client, which does a RPC ping first. If rpcbind is down then it can take up to a minute for the RPC ping to time out."

And:

"If we couple those delays with a long list of listeners, then it's easy to see how to reproduce the hang."

This dump names nfsd_nl_listener_set_doit as the holder, so the mechanism does not need to be inferred. The new netlink listener_set handler can install many sockets in one call; each one may try to register with rpcbind while still holding nfsd_mutex. A down or unresponsive local rpcbind turns each registration into a ~60-second stall. Two such stalls is 147 seconds of hung-task watchdog — exactly what syzbot observed.

Brown's question from that thread is the design fork still open when this report arrived:

"Why are we waiting a whole minute for a local service to respond? If it hasn't responded in 1 second, is it ever really likely to?"

Layton's answer — a shorter timeout is necessary but not sufficient, because "even at 1s, you could easily cause a lockup warning with just a few hundred listeners" — is the reason this new report will not be fixed by touching nfsd_nl_expkey_get_reqs_dumpit itself. The dump handler is an innocent waiter. The bug is that any nfsd netlink op, including the brand-new fh-cache upcall dump, takes the same global mutex that listener setup holds across synchronous rpcbind I/O.

One extra wrinkle unique to the dump path: while dumpit waits, it continues to hold nlk_cb_mutex-GENERIC. That is the per-socket dump-callback mutex, so this particular netlink socket cannot start another dump until the wait ends. It is not the cause of the hang, but it means a wedged expkey-get-reqs dump also wedges that userspace connection's entire dump pipeline.

NFS client impact

This is a server-side hang, but it sits on a path NFS clients actually use:

  • File-handle cache upcalls. When a client presents an FSID the server has not cached, nfsd multicasts NFSD_CMD_CACHE_NOTIFY and expects userspace to dump the pending requests via expkey-get-reqs, then reply via expkey-set-reqs. If the dump handler is stuck behind nfsd_mutex for minutes, userspace never sees the request and the client's LOOKUP/MOUNT simply does not complete. That is the same failure mode Paul Moore already hit as Connection refused on a localhost mount after 01c2305795a3.
  • Both directions are now known victims. The set-reqs twin, eleven minutes earlier, hung the downcall. This report hangs the upcall. A working fh-cache requires both; either one being serialized behind listener_set is enough to stall a mount.
  • Listener / thread control. nfsd_nl_listener_set_doit is the holder. If bringing nfsd up or adding sockets stalls on rpcbind while holding the mutex, every other control-plane op — including the ones clients indirectly depend on for mount — stalls with it.
  • NFSv2/v3 discovery. The underlying rpcbind-under-mutex problem is specifically a v2/v3 client-visibility issue: nfsd will serve without a successful registration, but clients that find the server via portmap see a missing or stale table. The 147-second dump hang is the control-plane counterpart of that same rpcbind stall.

For NFSv4.2 clients the damage is more about control-plane latency than wire protocol: inter-server copy, state reclaim, and admin-driven export changes all assume the netlink family stays responsive. A dump that sits in D-state for two and a half minutes is not responsive.

There is no NFS client code change in this thread and no client-side bug to fix. The client-visible symptom is a server that stops answering cache upcalls and, in the worst case, stops appearing in portmap while listener_set holds the lock.

Status

  • Type: hung-task / DoS bug in the nfsd netlink control plane, exposing the new expkey (nfsd.fh) dump path as another victim of nfsd_mutex.
  • Reproducer: none. syzbot is fuzzing concurrent netlink commands against a PREEMPT_RT kernel; the lock dump — listener_set holding, expkey_get_reqs_dumpit waiting — is the reproducer.
  • Human reply: none in this thread as of 23 July. The related cache-flush thread already has a design discussion (shorten rpc_ping; drop/reacquire nfsd_mutex around listener batches; or async, ordered rpcbind registration) but no patches posted and nothing applied.
  • Fix tag requested: Reported-by: syzbot+16f257c80900b615cb35@syzkaller.appspotmail.com.

Until the mutex is no longer held across rpcbind I/O — or until rpcbind I/O fails in well under a second — every new nfsd netlink command added this cycle is another hung-task report waiting to happen. This week's dumpit report is that prediction coming true on the get side of the fh-cache upcall, eleven minutes after the set side and two days after the diagnosis that already named listener_set as the long-hold site.
