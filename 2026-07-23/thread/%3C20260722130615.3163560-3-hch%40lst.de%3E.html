swap_ops.h extraction hits a zswap build hole

Overview

This week's traffic on [PATCH 2/3] of Christoph Hellwig's swap_ops updates series is a two-message review of the header that makes struct swap_ops implementable outside mm/page_io.c. That header is the prerequisite for the NFS (and SMB) client to own its swap I/O vector and drop the double-indirect swap_rw hop. The discussion itself is not a protocol change and not an NFS-client bug fix; it is an API-extraction / infrastructure patch whose only in-thread finding is a CONFIG_ZSWAP=y compile hole.

Hellwig posted the patch on 22 July as the middle step of a three-patch follow-on to the swap-ops work already in mm-unstable. The series goal, as he put it in the cover letter, is:

"this series is a follow on to the swap ops series now in mm-unstable. The first patch reintroduces direct folio writes for synchronous swap files, the other two remove the double indirect for file system based swap." — Christoph Hellwig

What the patch does

Patch 2/3 creates include/linux/swap_ops.h and moves the declarations of swap_iocb, swap_ops, and swap_ctx out of the private mm/swap.h. Callers in mm/madvise.c, mm/page_io.c, mm/shmem.c, mm/swap_state.c, and mm/vmscan.c pick up the new include. Hellwig's commit log is explicit about the intent:

"Add a new header to declare the swap_iocb, swap_ops and swap_ctx to allow for swap_ops implementations outside of mm/page_io.c. This will be used to remove the double indirection for file system-based swap." — Christoph Hellwig

He also flagged an unfortunate naming collision with the existing, unrelated swapops.h:

"Note that there already is a swapops.h header, which is totally unrelated to struct swap_ops. The close naming is a bit unfortunate, but I could not think of a better name for this header." — Christoph Hellwig

There is no functional change in this commit: no new swap path, no NFS wire-protocol work, no change to how a swapfile is activated. The next patch in the series is the one that actually moves swap_ops into fs/nfs/file.c (and the SMB client) and deletes the old helper in fs/nfs/direct.c. This header is what makes that pushdown legal.

This week's review: zswap was left behind

Usama Arif treated the extraction as otherwise correct and zeroed in on a missing consumer. Quoting the newly exported struct swap_io_ctx, he wrote:

"zswap uses this struct, I think you need to include the header in zswap.c as well, good to check if the build is passing with CONFIG_ZSWAP=y" — Usama Arif

That is a real compile-time hole, not a style nit. Once swap_io_ctx / swap_iocb leave mm/swap.h, any in-tree user that only included the old private header will fail to build. zswap is exactly that user, and it is a common allyesconfig / distro option.

Hellwig accepted the report the next morning without argument:

"Yes. The buildbot was nice enough to remind me of that just a little after it gave an all ok..." — Christoph Hellwig

The sequence is familiar: an unconfigured or CONFIG_ZSWAP=n pass looks clean, then the first CONFIG_ZSWAP=y bot lights up. Hellwig did not debate whether zswap should keep using the struct; he treated the missing include as an obvious v2 fix.

How this lands

The same morning Hellwig posted swap_ops updates v2. The first changelog item is exactly Arif's finding:

"Changes since v1: include swap_ops.h in zswap.c" — Christoph Hellwig

v2 of this patch also adds the "no functional change" sentence Chris Li had asked for on the parent series, and it updates mm/zswap.c (+2/-1 on that file). This v1 sub-thread itself ends with Hellwig's acknowledgement; there is no further debate here.

NFS client takeaway

For linux-nfs readers this is plumbing, not a client bug. Swap-over-NFS still works through the existing MM helpers until PATCH 3/3 lands. What this header does is make it legal for fs/nfs/file.c to implement struct swap_ops and pass that table into swap_fs_activate, instead of bouncing MM swap_ops → generic swap_rw → NFS direct-I/O helpers. NFSv3/v4 swapfile semantics are unchanged.

The zswap include miss does not affect the NFS client path. It does show that the extraction was incomplete on v1: any out-of-page_io.c user of these structs — zswap today, NFS and SMB tomorrow — must include swap_ops.h. That is the whole point of the header.

Conclusion: the discussion is a short, conclusive build-fix review of an infrastructure patch that enables pluggable, filesystem-owned swap ops. Arif found that zswap still consumes the moved structs; Hellwig agreed, blamed the buildbot's delayed CONFIG_ZSWAP=y run, and folded the include into v2. No NFS-client code is touched in this patch, but the header is the contract the NFS swap path will implement next.
