Single-folio swap writes restored for synchronous devices

Summary

This week’s linux-nfs traffic on Christoph Hellwig’s [PATCH 1/3] is a short, conclusive review of an MM swap I/O regression fix rather than an NFS-client protocol change. The patch sits in Hellwig’s swap_ops updates follow-on series (now targeting mm-unstable): it restores per-folio write submission for SWP_SYNCHRONOUS_IO swap backends so zram-style devices keep the writeback-bit handshake that classic LRU reclaim expects. Filesystem swap (including swap-over-NFS) is the broader series context, but this patch is specifically about synchronous, typically in-memory, swap devices.

What the patch changes

Hellwig’s opening patch is a performance-oriented bug fix, not a new feature. After swap write batching landed, zram no longer cleared folio writeback as aggressively during reclaim scans. Hellwig wrote:

"Kairui Song reported that zram benefits from submitting each folio directly instead of batching up I/O because the classic LRU scanning benefits from clearing the folio writeback bit in the scan loop."

The intended fix is to kick off I/O on each iteration for synchronous devices instead of accumulating a batch. The commit log as posted said “kicking off reads,” which is the only technical nit this sub-thread actually debates.

The code change is small (mm/page_io.c, +10/-1): for devices flagged SWP_SYNCHRONOUS_IO, swap-out no longer waits to plug a multi-folio bio. That matters for zram because compression and completion happen in the submit path, so the writeback bit can drop before the scanner moves on. Batching delayed that bit, which is the opposite of what LRU reclaim wants on a “synchronous” backend.

This is adjacent to NFS rather than inside it. Swap-over-NFS is asynchronous networked writeback; the devices that set SWP_SYNCHRONOUS_IO are the zram/zswap class. The patch still showed up on linux-nfs because the same series is ripping the double-indirect swap_ops table out of generic MM and into filesystem swap implementations — the infrastructure NFS (and other FS swap) will call.

No one argued for keeping batched writes on synchronous devices, and no NFS-client code path was touched.

Conclusion

The discussion is a bug/performance fix (restore single-folio swap-out for SWP_SYNCHRONOUS_IO), not a protocol change. By 23 July the patch had an ack from Arif, Hellwig had corrected “reads” to “writes,” and the original zram reporter plus the swap maintainer had also acked on the series thread. Remaining work in the parent series is the swap_ops.h / filesystem-owned ops cleanup, not this write-size revert.

NFS-client takeaway: no client bug and no swap-over-NFS I/O change this week. The relevant NFS angle is only that Hellwig is still reshaping the MM swap_ops layer that filesystem swap (NFS included) will plug into; zram’s LRU writeback timing is what forced the single-folio write path back in.
