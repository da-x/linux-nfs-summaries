NFSD flexfile layouts leak host UIDs into client AUTH_SYS creds

Summary

This week's linux-nfs traffic includes a compact but consequential bug fix for knfsd's pNFS flexfile layout: owner and group IDs handed to the client were translated in the initial user namespace instead of the request's namespace. The result is not a protocol change and not a new feature. It is a long-standing identity-mapping defect that causes the NFS client to present the wrong AUTH_SYS credential to the data server.

The thread is new this week (no prior-week summary) and closed after a single review.

The client-visible failure

Chuck Lever posted a one-patch series against fs/nfsd/flexfilelayout.c (plus the matching XDR helpers) on 20 July. The commit message is the technical brief:

"nfsd4_ff_proc_layoutget() and nfsd4_ff_encode_layoutget() translate the file's owner and group with init_user_ns, but every other identity nfsd places on the wire goes through nfsd_user_namespace()."

That mismatch only bites when the RPC transport carries a credential from a non-initial user namespace. In that case the flexfile LAYOUTGET response reports host-global numeric IDs. The client, acting as designed for flexfiles, copies those IDs into the AUTH_SYS credential it presents to the data server. On the way back in, svcauth_unix_accept() resolves that credential in the transport's namespace. Lever's conclusion is blunt:

"When the transport carries a credential from a non-initial user namespace, the flex file layout reports host-global IDs. The client copies those IDs into the AUTH_SYS credential it presents to the data server, and svcauth_unix_accept() resolves that credential in the transport's namespace, so data server I/O runs under an identity unrelated to the file's owner."

From a client-development perspective this is the important part. Flexfile clients treat the layout's ff_layout4 owner/group as the identity they must use for data-path AUTH_SYS. They do not re-map those IDs; they trust the metadata server. A server that emits init_user_ns numbers into a namespaced transport therefore turns an otherwise-correct client into an accidental impersonator. Data I/O proceeds, just as the wrong user.

The patch tags the original flexfile server introduction:

Fixes: 9b9960a0ca47 ("nfsd: Add a super simple flex file server")

and credits sashiko-bot as the reporter, with a Closes link to the corresponding sashiko patchset review.

The second hazard: wrapping to uid 0

A naive switch from init_user_ns to nfsd_user_namespace() would have introduced a worse failure. Flexfile's IOMODE_READ path synthesizes a distinct identity for which the data server will deny writes by taking the mapped owner and adding one. Lever flags the wrap:

"from_kuid() returns (uid_t)-1 when the target namespace has no mapping for the owner, and the IOMODE_READ arm adds one to that result to derive an identity for which the data server denies writes. The addition would wrap to zero, handing the client uid 0 instead of an identity distinct from the owner."

That is a privilege-escalation-shaped footgun on the client side: an unmapped owner would be advertised as uid 0, and the client would then AUTH_SYS to the data server as root.

The chosen fix therefore does two things at once:

  1. Translate both owner and group in nfsd4_ff_proc_layoutget(), which has the svc_rqst and can call nfsd_user_namespace(), then stash the already-mapped wire values in struct pnfs_ff_layout so the XDR encoder no longer re-translates against init_user_ns.
  2. Use from_kuid_munged() / from_kgid_munged() rather than from_kuid(). Lever's rationale:

"from_kuid_munged() substitutes overflowuid for an unmapped owner and thus never returns (uid_t)-1, so the increment cannot wrap to zero."

The encoder in nfsd4_ff_encode_layoutget() then just serializes the precomputed numbers. Touch set is small: 20 insertions / 12 deletions across flexfilelayout.c, flexfilelayoutxdr.c, and flexfilelayoutxdr.h.

Review and status

Jeff Layton replied the next day with a one-line ack and no requested changes:

"Reviewed-by: Jeff Layton jlayton@kernel.org"

There was no follow-up debate, no v2, and no client-side companion patch. The discussion therefore ends this week as a reviewed server fix whose correctness the client depends on: flexfile LAYOUTGET IDs must already be in the same user-namespace that svcauth_unix_accept() will later use, and they must never collapse to uid 0 when the owner is unmapped.

Same-week context (not this thread): Lever's separate header-hygiene series also touched NFSD flexfile, replacing a borrowed client struct nfs_fh with the server knfsd_fh type. That work is type-safety cleanup, not this identity bug; the two changes are complementary rather than overlapping.

Bottom line: this is a knfsd bug fix with first-order NFS client impact. Flexfile clients will keep copying layout owner/group into AUTH_SYS; after this patch those numbers finally match the transport namespace, and an unmapped owner can no longer wrap to root.
