nfsd netlink stats v6: Dai Ngo settles the wdeleg_getattr debate — remove it

Summary

nfsd netlink stats v6: Dai Ngo breaks the tie — wdeleg_getattr should go

Context (brief bridge)

This thread continues Jeff Layton's v6 series converting the NFS server-side nfsstat interface from procfs scraping to a generic netlink dump handler, with per-netns accounting for forechannel procedure counts and — new since v5 — NFSv4 backchannel (callback) operations. Last week (2026-07-16 summary), Layton and Chuck Lever spent the entire window re-litigating exactly one question: should the legacy wdeleg_getattr procfs counter be carried over into the new netlink interface, kept as a separate stat, or dropped entirely. Layton argued for dropping it (CB_GETATTR counts already approximate it), Lever argued for API equivalence between netlink and procfs, and both agreed to defer to Dai Ngo, the original author of wdeleg_getattr, who had not yet replied by the end of that window.

This Week (July 17): The Original Author Decides

The single in-window message is Dai Ngo's long-awaited reply, which closes out the question decisively in Layton's favor.

Dai's verdict: the name is wrong and the stat doesn't belong in nfsstats

Dai weighs in with two concrete points:

"The wdeleg_getattr counter tracks the number of times a GETATTR operation conflicts with an outstanding write delegation. As such, the name wdeleg_getattr does not accurately describe what the counter represents."

And on its place in the interface:

"Furthermore, this statistic probably does not belong in nfsstats. Since there are no known user-space consumers of this counter, it would be better to remove it altogether."

This is a notable reversal from the position Dai presumably held when he added the counter originally — Layton had noted last week that "Dai added wdeleg_getattr originally," and was hoping for his opinion. Dai now concedes both the naming problem and the lack of any consumer, which removes the main obstacle to Layton's preferred outcome.

Key Technical Points

  • What wdeleg_getattr actually counts: GETATTR operations from other clients that conflict with an outstanding write delegation on a file — i.e., the condition that triggers a delegation recall and a CB_GETATTR callback to the delegating client. It is not a protocol operation count in the same sense as the other nfsstats fields, which is why Layton last week called it "sort of an oddity that didn't really belong in this /proc file."
  • Why CB_GETATTR approximates it: As Layton explained last week, the only difference is coalescing — if a second client does GETATTR while a CB_GETATTR is already in flight for the same fh, wdeleg_getattr bumps but the CB_GETATTR counter does not (only one callback goes out). For diagnostic purposes, the callback count is "good enough."
  • No user-space consumer: Both Layton ("nfs-utils doesn't look at it") and now Dai ("there are no known user-space consumers of this counter") confirm nothing in the wild reads this field. This is the decisive practical argument: removing it breaks no tooling.

Classification and Significance

  • Type: This is a design/ABI decision on a new feature (the netlink stats handler, patch 3/6 of the v6 series). It is not a protocol change — the underlying wire behavior of delegations and CB_GETATTR callbacks is untouched. There is no bug fix this week; last week's fixes (a use-after-free in patch 5 and a CB_SEQUENCE undercount in patch 6) stand.
  • NFS client relevance: Although the discussion is server-side, it directly affects how NFS client delegation activity is observable. wdeleg_getattr was historically a signal for diagnosing delegation recall storms and backchannel pressure — understanding why a particular file's write delegation got recalled. With its removal, admins will rely on CB_GETATTR counts (now exposed via netlink) as the proxy, which Layton has argued is a sound approximation since it counts actual callbacks sent rather than raw conflict events.
  • Outcome: The thread's open question from last week is now resolved. Dai's endorsement of removal — combined with Layton's earlier position and the confirmed absence of any consumer — strongly points to wdeleg_getattr being dropped in v7, at least from the netlink interface. Whether it also disappears from procfs or lingers there as a deprecated field will be a detail for the next revision, but the technical argument for keeping it is effectively gone.

Where Things Stand

The three-way debate (drop / expose over netlink / keep procfs-only) has collapsed to "remove it." Layton and Lever both deferred to Dai last week; Dai has now spoken, and his answer aligns with dropping the counter. A v7 of the series can proceed without wdeleg_getattr as a first-class stat. The remaining work on this thread is mechanical — updating patch 3/6 (and any related procfs code) to reflect the removal — rather than a further design discussion.
