NFSD global DRC clean-ups: off-by-one fix and percpu counter contention elimination

Summary

NFSD Global DRC Clean-Ups: Off-by-One Fix and Per-CPU Counter Contention Elimination

Week of 2026-07-17 to 2026-07-23 | Thread: [PATCH 0/5] Minor NFSD global DRC clean-ups

Overview

This thread is a bug fix and performance improvement series for the NFS server (NFSD) side, specifically targeting the global Data Reply Cache (DRC) and its associated statistics infrastructure. Chuck Lever posted a five-patch series on July 17 that addresses an off-by-one bug in DRC bucket pruning and eliminates unnecessary spinlock contention from per-CPU counter updates across three different accounting paths. The series also adds ABI documentation for the reply_cache_stats procfs file.

While this is server-side work (NFSD rather than the NFS client), it has direct implications for NFS client performance on busy multi-CPU servers, particularly under high rates of non-idempotent NFSv3 operations and RDMA workloads.

The Patches

Patch 1/5: Off-by-One in DRC Bucket Pruning Limit

The first patch fixes a genuine bug in nfsd_prune_bucket_locked(). As Chuck Lever explained:

"nfsd_prune_bucket_locked() evicts an entry before checking the freed count against @max. The check uses '++freed > max', which does not break until freed exceeds max, resulting in max + 1 evictions."

The fix is a one-character change from > to >=, ensuring the pruning limit stated in the function comment is actually honored. This carries a Fixes: tag referencing commit a9507f6af145 ("NFSD: Replace nfsd_prune_bucket()").

Patches 2/5, 3/5, and 4/5: Eliminating Per-CPU Counter Contention

The bulk of the series addresses a subtle but significant performance problem. The DRC memory accounting counter, reply cache hit/miss/nocache statistics, and IO byte counters all used percpu_counter_add() or percpu_counter_inc(), which apply a default batch threshold of max(32, 2*nr_cpus). When the update amount exceeds that threshold, the function falls back to acquiring the counter's global spinlock on every single update.

The problem was particularly acute for the DRC memory counter, as Chuck detailed:

"Each DRC entry add or removal updates the counter by sizeof(struct nfsd_cacherep) (~144 bytes), which always exceeds the batch threshold. percpu_counter_add() then acquires the counter's global spinlock on every update, serializing all nfsd threads."

He quantified the impact:

"On a 10-CPU NFS server handling a high rate of non-idempotent NFSv3 operations, this lock accounts for a measurable fraction of total spin lock overhead because nfsd_cache_lookup() both inserts a new entry and prunes up to three old entries per RPC, producing 4-7 global lock acquisitions per operation."

For the IO byte counters, profiling data was provided:

"Profiling on a 10-CPU RDMA NFS server shows 0.44% of total CPU cycles spent contending on these locks during a small random write workload."

The fix in all three cases is to switch to percpu_counter_add_local() / percpu_counter_sub_local(), which batch with INT_MAX so updates always remain on the per-CPU fast path. Read accuracy is preserved because all readers use percpu_counter_sum_positive().

Patch 5/5: ABI Documentation

The final patch adds a new file, Documentation/ABI/testing/procfs-nfsd-reply_cache_stats, documenting the /proc/fs/nfsd/reply_cache_stats interface that has existed since v3.10 but was previously undocumented. As Chuck noted, this "establishes a contract that parsers should match on field name rather than line position."

Community Response

The series received quick and enthusiastic endorsements from both NFSD maintainers.

NeilBrown reviewed the full series and gave an unqualified review:

"All looks very sensible to me." "Reviewed-by: NeilBrown neil@brown.name"

Jeff Layton was particularly struck by the performance implications, reacting to the DRC memory accounting patch with:

"Dear god -- I had no idea that this was a thing. I wonder if we have other places we're using percpu_counter_add() where we shouldn't?"

He then expanded on the series more broadly:

"I had no idea that percpu counters could devolve into spinlocking in certain conditions. Ick. I wonder if we need to do a pass over all of our percpu counter usage for the same sort of thing. ISTM that we pretty much always want to use the *_local versions for our use-cases." "Reviewed-by: Jeff Layton jlayton@kernel.org"

Significance and Outlook

This series is notable on two fronts:

  1. The off-by-one fix is a straightforward correctness bug that has been present since the DRC bucket pruning code was refactored. While its practical impact is small (one extra eviction per prune cycle), it represents a violation of the documented contract.

  2. The percpu counter contention fixes expose a broader kernel-wide pattern: percpu_counter_add() with amounts exceeding the batch threshold silently degrades into a global spinlock, which can be a significant scalability bottleneck on multi-CPU systems. Jeff Layton's suggestion to audit all NFS subsystem percpu counter usage for the same issue hints at follow-up work that may emerge in subsequent weeks.

The series is ready for merge with two Reviewed-by tags from the NFSD maintainers. Chuck Lever noted in the cover letter that he is "working on a series of global DRC improvements" beyond these clean-ups, suggesting further DRC architecture changes are in flight.
