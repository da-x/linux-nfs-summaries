nfsd: v5 of nfs4_create_file() refactor lands — Reviewed-by and applied to nfsd-testing same day

Summary

nfsd: NeilBrown's nfs4_create_file() refactor reaches v5 — reviewed and merged into nfsd-testing in a single day

Type: Refactoring series with embedded bug fixes (NFS server / nfsd) — not an NFS client change, not a protocol change.

The week in one line

On Friday, July 17, NeilBrown posted the fifth revision of his long-running 18-patch series to untangle nfs4_create_file() in the Linux NFS server, and within hours it was both reviewed and merged: Jeff Layton issued a blanket Reviewed-by, and nfsd maintainer Chuck Lever applied the whole series to nfsd-testing the same afternoon, publishing a full commit list for all 18 patches.

"Applied to nfsd-testing, thanks!" — Chuck Lever

That is the headline of this week: a series that has been iterating for several weeks finally cleared review and landed in the nfsd testing tree.

Bridging prior weeks (briefly)

This is the fifth posting of the same effort (v1 → v2 → v3 → v4 → v5). The immediately preceding v4 thread, posted just hours earlier on the same day, had addressed Chuck Lever's review of the mounted-on-file fix (it "doesn't build here with CONFIG_NFSD_V2=y," plus refcount/export problems in the NFSv2/v3 create paths). v5 is NeilBrown's response to the other open item — Jeff Layton's LLM-assisted review pass over v3, which had flagged a high-severity read-only OPEN regression (an unconditional mnt_want_write()) and a medium-severity endianness bug (__be32 status compared against the raw host enum NFSERR_NOENT).

NeilBrown was candid in the v5 cover letter about why a new version arrived so quickly:

"For for another version so soon - I hadn't noticed Jeff's LLM results. Most of the issue raised there were already addressed I think, but the using nfserr_noent instead of NFSERR_NOENT, and adding a condition on the call to mnt_want_write() in the final patch were still needed."

So v5 folds in exactly two fixes carried over from Jeff's LLM review: (1) the nfserr_noent vs. NFSERR_NOENT endianness correction, and (2) making the mnt_want_write() call in the final patch conditional rather than unconditional — the latter being what resolves the read-only OPEN regression.

The bug fixes carried into v5

The series still contains the same two genuine correctness fixes that have been its anchor across revisions:

1. Honour client-provided attributes for NFS4_CREATE_EXCLUSIVE4_1 (patch 01/18) — a real correctness fix carrying a Fixes: tag pointing at commit ac6721a13e5b and a Reviewed-by from Jeff Layton. The server was silently dropping client-requested attributes on an exclusive v4.1 create:

"When the mtime/atime are set to hold the verifier, the other ia_valid flags are cleared, so no attributes requested by the client are used."

NeilBrown traces it to code "originally written for NFSv3 where NFS3_CREATE_EXCLUSIVE never includes attributes" that was never properly extended when v4.1 added attribute support to exclusive creates. See patch 01/18.

2. Correctly handle CREATE of mounted-on files (patch 03/18) — spanning nfs3proc.c, nfs4proc.c, and nfsproc.c (i.e., v2, v3, and v4). Linux lets a filesystem be mounted on top of a regular file; under crossmnt an unchecked CREATE on such a name returned the underlying file's handle rather than the mountpoint's:

"if CREATE is used on an existing mounted-on file, the filehandle for the underlying file is returns. The client will then continue to use that filehandle."

The visible symptom — cat /mnt/file works until a dcache flush, after which >> /mnt/file writes to the wrong (mounted-on) file. NeilBrown's fix checks the dcache for a mounted name and returns that handle, "possibly truncating." He is candid about its age:

"This probably has always existed since before the git history." See patch 03/18

The refactoring arc (patches 04–18)

The remainder of the series is the same incremental, reviewable march toward a unified vfs_lookup_open() VFS API described in prior weeks. Notable steps:

  • Patches 04–07: replace fh_fill_both_attrs() with fh_fill_post_noop(), move fh_want_write() and NFS-specific preamble code earlier, and collapse a "subtle" goto difference between EXCLUSIVE and EXCLUSIVE4_1 replay handling.
  • Patch 08 (let VFS report if file was created): an important correctness improvement for atomic_open — nfsd previously assumed a failed-lookup-then-successful-create meant the file was created, which "may not be the case - some other actor might have created the file between the lookup and the create." It now keys off the FMODE_CREATED flag. See patch 08/18
  • Patches 09–12: move the NFSD_MAY_CREATE check earlier, defer fh_want_write() failure until creation is confirmed needed, "(almost) always open file," and reduce the directory-lock range (releasing start_creating() before setattr).
  • Patches 13–16: open-code nfsd4_vfs_create(), move code out of the d_really_is_negative() branch "to make it easier to switch to using vfs_lookup_open()," reduce the want-write range, and move protocol-version checking out of nfsd_check_obj_isreg().
  • Patches 17–18 (the payoff): extract all VFS-specific code into a new do_lookup_open() function, then use it for non-creating OPENs too. The end goal is explicit:

"It is planned to provide a vfs_lookup_open() in vfs code which provides this functionality. This will share more code with the syscall open path, and make it easier to modify locking at the VFS level." See patch 17/18

One trade-off worth flagging from patch 04/18: moving fh_fill_pre_attrs() out of the directory inode lock means nfsd can no longer provide "atomic" WCC pre/post data, so a new fh_fill_pre_attrs_unlocked() marks attributes non-atomic — "unfortunate but inevitable if we are ever to allow concurrent updates in a directory."

The v5-specific delta and review outcome

The two carry-over fixes from Jeff's LLM review show up concretely in the final patch. Patch 18/18 now gates the write-access request on an actual need rather than always setting O_CREAT:

"We now only call mnt_want_write() is there is a flag which indicates we might want write access - previously O_CREAT was always set."

That single change is what resolves the read-only OPEN regression Jeff had flagged. The endianness fix (nfserr_noent rather than NFSERR_NOENT) corrects the status comparison in the create path.

With both items addressed, the review closed quickly and cleanly:

"Nice work, Neil. You can add this to any that don't already have it: Reviewed-by: Jeff Layton jlayton@kernel.org" — Jeff Layton

Chuck Lever followed with the merge, listing all 18 commits (e.g., patch 01 at 0ac10ed2eadf, patch 03 at d50cf4faa709, patch 18 at 71349ee933ed) into nfsd-testing. See the merge notice.

Status and outlook

As of the end of this week's window (July 23), the series is merged into nfsd-testing — a meaningful milestone for a multi-week effort. No further discussion or objections appeared in-thread after Chuck's merge notice; the thread effectively closes with the application.

Bottom line: this is a server-side (nfsd) refactoring-and-bugfix series, not an NFS client change and not a protocol change. Its significance is twofold — it fixes two real correctness bugs (dropped attributes on exclusive v4.1 creates, and wrong-handle returns on mounted-on files across v2/v3/v4), and it lays the groundwork for a shared vfs_lookup_open() that would let nfsd reuse VFS open-path code and relax directory locking for better concurrency. After five revisions and review from both Jeff Layton and Chuck Lever, the work has now landed in the nfsd testing tree; the remaining question is whether the planned upstream vfs_lookup_open() VFS API will follow to complete the refactor's stated end goal.
