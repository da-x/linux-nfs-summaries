Confine Inter-Server Copy to nfs_common After a Trail of Client UAFs

Week of 2026-07-17 to 2026-07-23 | Thread: [PATCH 0/4] Confine the inter-server copy interface to fs/nfs_common

Overview

This thread is a structural cleanup and hardening series, not a live-bug fix and not a protocol change. On 21 July, Chuck Lever posted four patches that pull the NFSv4.2 inter-server copy (SSC) broker fully into fs/nfs_common, delete client-side registration that has been dead since an earlier use-after-free fix, and replace an implicit “the caller’s mount pins nfsv4” contract with RCU plus try_module_get() owned by the broker itself.

The series is aimed squarely at the NFS client object that has been the common factor in a cluster of use-after-free and reference-leak repairs: the source mount that the client creates and opens while NFSD decides when it may be torn down. Lever is explicit that runtime copy behavior is meant to stay the same:

"None of this fixes a live bug, and the source mount's lifetime still spans both modules. What changes is that the broker no longer relies on rules its callers enforce. Inter-server copy behavior is meant to be unchanged throughout."

There were no replies in-window. Olga Kornievskaia and Dai Ngo are Cced on every patch as the historical SSC stakeholders.

Why the client keeps getting hurt

The cover letter frames the series as the architectural follow-through to three already-merged client/server lifetime bugs — 75333d48f922, 34e8f9ec4c9a, and d2c343c51caf — plus three further repairs of the bookkeeping added by f4e44b393389:

"Inter-server copy has drawn a steady trail of use-after-free and reference-leak fixes: 75333d48f922, 34e8f9ec4c9a, and d2c343c51caf among them. They cluster on one object, the source mount that the NFS client creates and opens while NFSD decides when it may be torn down. The bookkeeping that tracks it, added by f4e44b393389, has needed three follow-on repairs of its own. Splitting an object's lifetime across two modules that are forbidden to call each other directly is what keeps producing these bugs."

The most recent of those, 75333d48f922 ("NFSD: fix use-after-free in __nfs42_ssc_open()"), already narrowed the split: NFSD stopped reaching back through the broker to deactivate the source superblock, and post-copy cleanup became the laundromat’s job alone. What it did not do was retract the client registration path it had just stopped using. That leftover machinery is the starting point of this series.

A second, still-live contract is what patch 3 attacks. Today the client ops table can be read unsynchronized only because:

"an inter-server copy holds an active vers=4.2 mount of the source, that mount pins the nfsv4 module, and unregister runs only at module exit."

Lever wants that argument out of the NFS client and into the broker, so safety no longer “depends on how a caller in another subsystem manages mounts.”

Patch 1/4: delete the unused client ops table

Patch 1 is the client-visible cleanup. Once nfsd4_interssc_disconnect() went away, nothing called nfs_do_sb_deactive() or the nfs_ssc_client_ops table. The patch removes:

  • nfs_do_sb_deactive() and the SSC registration hooks from fs/nfs/super.c
  • struct nfs_ssc_client_ops, nfs_ssc_register(), and nfs_ssc_unregister() from fs/nfs_common/nfs_ssc.c and include/linux/nfs_ssc.h
  • the leftover include in fs/nfsd/nfs4proc.c

Net: 89 lines deleted, no functional change. This is the first time the client stops advertising an ops vector whose only remaining consumer was a UAF that had already been closed by moving teardown to the laundromat.

Patch 2/4: hide the client’s ssc_open behind the broker

Patch 2 hoists the call into the client’s ssc_open method out of fs/nfsd/nfs4proc.c and into fs/nfs_common/nfs_ssc.c. The new entry points are named nfsd42_ssc_open() / nfsd42_ssc_close() because they are meant to be invoked only by NFSD. Lever’s stated goal is client-header hygiene as much as server cleanup:

"The infrastructure and details for calling the client's ssc_open method can be hidden in nfs_ssc.c. This reduces the SSC footprint in fs/nfsd/nfs4proc.c, a step toward removing that file's dependency on <linux/nfs_fs.h>, which indirectly includes <uapi/linux/nfs.h>."

That last point is the client-side leak in the other direction: nfs4proc.c has been parsing NFS client types (and therefore <uapi/linux/nfs.h>) just to invoke one method on a table the client registered. After this patch the server no longer needs to know how the client implements open.

Patch 3/4: RCU + module pin instead of “the mount keeps nfsv4 loaded”

Patch 3 is the real hardening change, and the one that most directly touches NFS client module lifetime. nfsd42_ssc_open() and nfsd42_ssc_close() currently load ssc_nfs4_ops with no synchronization while nfs42_ssc_register() / nfs42_ssc_unregister() store it. Those unsynchronized loads are only safe because an in-flight copy holds a vers=4.2 source mount, that mount pins nfsv4 via nfs_client->cl_nfs_mod, and unregister runs only at nfsv4 module exit.

The new rule is local to the broker:

  • Readers observe the pointer under RCU, so they see either a valid table or NULL.
  • nfs42_ssc_unregister() stores NULL and then synchronize_rcu(), so it cannot return while a reader still holds the pointer.
  • sco_close() does not sleep, so nfsd42_ssc_close() runs it entirely inside the RCU read-side section.
  • __nfs42_ssc_open() does sleep — it issues a GETATTR RPC to the source server and allocates with GFP_KERNEL — so it cannot run under rcu_read_lock(). The broker takes try_module_get() on the provider while still in the RCU section, drops the lock, invokes open, then module_put(). If the table is already gone, the copy fails with -EIO.

Lever’s punchline for the client:

"The reference keeps the provider mapped across the sleep without relying on the caller's mount."

fs/nfs/nfs4file.c gains a one-line include so the client’s remaining registration site still sees the (now RCU-aware) ops-table API. After this patch, unloading nfsv4 no longer depends on “there cannot be an SSC open in flight because a mount is holding us.”

Patch 4/4: split the shared header so the client stops compiling the server

Patch 4 is the textual remainder Lever promised in the cover letter. include/linux/nfs_ssc.h currently declares both sides’ interfaces, so each implementation parses the other’s types and inherits its includes — which is how <uapi/linux/nfs.h> reaches nfs4proc.c. The split:

  • New include/linux/nfsd_ssc.h holds the server-side APIs and does not pull uapi/linux/nfs.h either directly or via the NFS client headers.
  • struct nfsd4_ssc_umount_item is private to nfsd and moves into fs/nfsd/xdr4.h next to its only consumers, rather than into the exported header.
  • fs/nfsd/nfs4proc.c now includes <linux/pagemap.h> directly for filemap_check_wb_err(), because that symbol used to arrive as a transitive gift from the client headers.
  • Missing header guards and struct file / struct vfsmount forward declarations are added.

The client-facing nfs_ssc.h shrinks to the ops-table types the nfsv4 module actually registers.

Conclusions and outlook

This is preventive architecture, not a regression fix. Lever is careful not to oversell it: the source mount’s lifetime still spans nfs and nfsd, and no in-tree copy path is supposed to change. What the series does change, from a client-development point of view, is:

  1. Dead client API removal. The nfs_ssc_client_ops / nfs_ssc_register() / nfs_do_sb_deactive() path, left behind by the __nfs42_ssc_open() UAF fix, is gone from fs/nfs/super.c.
  2. Module-lifetime ownership. The nfsv4 module is now pinned by the broker across a sleeping ssc_open (GETATTR + GFP_KERNEL), instead of by the implicit “the source mount’s cl_nfs_mod keeps us loaded” rule.
  3. Header isolation. The client no longer has to export types into a header that NFSD compiles, and NFSD no longer compiles <uapi/linux/nfs.h> as a side effect of talking to the client.

The series is a same-day posting with no review tags yet. Until Olga Kornievskaia, Dai Ngo, or a client maintainer weigh in, the open question is whether reviewers accept Lever’s claim that the remaining cross-module lifetime of the source mount is now a documentation problem rather than a locking one.
