NFSD write path decoupled from NFSv3 XDR stable_how constants

Week of 2026-07-17 to 2026-07-23 | Thread: [PATCH 0/2] NFSD: Decouple the write path from NFSv3 XDR constants

Overview

This thread is a cleanup / API-hygiene series, not a protocol change and not a client-facing feature. On Thursday, 23 July, Chuck Lever posted a two-patch set that severs NFSD's version-neutral write helpers from NFSv3 on-the-wire constants. The work is almost entirely server-side, but patch 1 relocates a shared UAPI-adjacent enum (enum nfs3_stable_how) out of include/linux/nfs.h into include/linux/nfs3.h, which is the header both the NFS client and NFSD already use for v3 wire values. There were no replies in-window: the series landed at the end of the week and is awaiting review.

The motivating debt is a long-standing numeric coincidence. NFSD's internal write helpers are supposed to be NFS-version-agnostic, yet nfsd_write() has historically taken an NFSv3 stable_how value lifted straight off the wire. The NFSv4 WRITE and COPY paths then borrowed those same NFSv3 constants for their own stable values, which only works because stable_how and stable_how4 happen to share numeric encodings. As Chuck put it in the cover letter:

"That coincidence is the debt: it binds version-neutral VFS helpers to one protocol version's XDR and leaves NFSv4 depending on nfs3.h."

The proposed fix is to stop passing a protocol enum through the generic VFS helpers and pass IOCB flags instead. That removes a nfs3.h dependency from code that is not related to NFSv3.

Patch 1/2: Move enum nfs3_stable_how into linux/nfs3.h

The first patch is a small header cleanup that matters to both client and server trees. enum nfs3_stable_how (UNSTABLE, DATA_SYNC, FILE_SYNC) was introduced with NFSv3, but it has lived in the version-neutral include/linux/nfs.h. NFSv2 has no stable_how on the wire at all; its write path only passes NFS_FILE_SYNC as a placeholder the protocol ignores. Chuck's rationale is straightforward:

"The stable_how constants describe an NFSv3 wire value, so they belong in linux/nfs3.h."

The move is three files: the enum is deleted from include/linux/nfs.h, re-homed in include/linux/nfs3.h, and include/trace/misc/nfs.h picks up an extra include so existing tracepoints still compile. There is no behavioral change. For NFS client development the practical effect is header hygiene: client code that already includes nfs3.h for v3 XDR continues to see the same enumerators, while version-neutral client headers no longer advertise a v3-only wire type.

Patch 2/2: nfsd_write() takes IOCB flags, not a v3 XDR value

The second patch is the real API change. Chuck states the problem without hedging:

"The current nfsd_write() API is not NFS version-agnostic, as it relies on callers to pass an NFSv3 stable_how value to determine the persistence of the requested WRITE. NFSv2 does not use a stable-how value on the wire, and NFSv4 has its own stable_how4 (though stable_how and stable_how4 happen to share the same numeric values)."

The replacement is mechanical but careful. nfsd_write()'s stable argument becomes a set of IOCB flags. Version-specific procedure code now translates its own protocol's stability request into those flags before calling the generic helper:

  • NFSv2 continues to request a fully synchronous write (the protocol has no unstable-write concept).
  • NFSv3 maps UNSTABLE / DATA_SYNC / FILE_SYNC onto the corresponding IOCB bits in nfs3proc.c.
  • NFSv4 WRITE and COPY stop borrowing the v3 enumerators and switch to the new stable_how4 constants added in include/linux/nfs4.h. Chuck is explicit that this is a no-behavior change:

"Convert those sites to the stable_how4 enumerators so the v4 code expresses its own protocol's values directly, with no change in behavior."

Two small correctness nits ride along. The NFSv3 WRITE decoder now bound-checks the decoded stable value the way the NFSv4 WRITE decoder already does, and nfsd3_writeargs.stable becomes unsigned to match. Those are defensive decoder fixes, not write-path semantics changes.

The net of the vfs.c churn is a simplification: the generic helper no longer switches on an XDR enum. It just applies the IOCB flags it is given. Chuck's closing claim is the architectural payoff:

"The larger benefit is one less NFSv4 dependency on nfs3.h."

Touched files are concentrated in NFSD (nfs3proc.c, nfs3xdr.c, nfs4proc.c, nfs4xdr.c, nfsproc.c, vfs.c, vfs.h, xdr3.h) plus the new stable_how4 enumerators in include/linux/nfs4.h. Twelve files, +66 / −37 overall.

Client-development angle

This is not a client bug-fix series, and it does not change on-the-wire WRITE semantics for any NFS version. The client-relevant pieces are:

  1. Shared header relocation. Moving enum nfs3_stable_how into linux/nfs3.h is the kind of header split client developers have wanted for years: version-neutral nfs.h stops carrying a v3 XDR type. Any out-of-tree or trace-side code that included only linux/nfs.h and expected NFS_UNSTABLE / NFS_DATA_SYNC / NFS_FILE_SYNC will need linux/nfs3.h (the in-tree trace header is already updated).
  2. NFSv4 no longer leans on nfs3.h for WRITE/COPY stability. Adding first-class stable_how4 enumerators in linux/nfs4.h is the same direction the client already took for other v4 wire types. It removes a cross-version include hazard if client or common code later wants to reason about v4 stable-how without pulling v3 headers.
  3. No client write-path change. Client nfs_writeback / nfs_pageio / pNFS layout-commit stability handling is untouched. The coincidence that v3 stable_how and v4 stable_how4 share numeric values remains true on the wire; this series just stops the server from depending on that coincidence internally.

Status

Posted late on 2026-07-23. No Reviewed-by, Acked-by, or comments yet. The series is self-contained cleanup sitting alongside Chuck's other NFSD hygiene this week (global DRC counter fixes, lock-owner UAF merge-timeline discussion) and is the sort of prerequisite that usually lands in nfsd-next once a maintainer glance confirms the IOCB-flag mapping is complete for v2/v3/v4 WRITE and v4 COPY.

Conclusions

  • Type: cleanup / internal API change, with a small defensive bound-check on the NFSv3 WRITE decoder.
  • Not a protocol change. Wire encodings of stable_how / stable_how4 are unchanged; NFSv4 WRITE and COPY keep the same numeric values, now spelled with their own enumerators.
  • The design argument is decoupling. Version-neutral VFS helpers should speak VFS (IOCB flags), not a single protocol version's XDR. The numeric overlap between v3 and v4 was convenient and is now treated as technical debt.
  • Client impact is header-only. enum nfs3_stable_how moves to linux/nfs3.h; linux/nfs4.h gains stable_how4. No client I/O path is modified.
  • Awaiting review. Three messages, all from the author, no discussion yet.
