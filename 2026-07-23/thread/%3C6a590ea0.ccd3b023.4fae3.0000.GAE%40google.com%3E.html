Summary

syzbot hang: rpcbind under nfsd_mutex is a multi-vector DoS

Brief bridge from last week

Last Thursday, syzbot filed an unreproduced hung-task report: nfsd_nl_cache_flush_doit blocked more than 143 seconds on nfsd_mutex while a concurrent nfsd_nl_listener_set_doit held the same lock. No maintainer had replied by the end of that window. This week the report is triaged in earnest — and the diagnosis is worse than a simple long hold.

Classification

This is a bug-fix / hardening discussion, not a protocol change and not a new feature. The hang is in the NFS server generic-netlink control plane (fs/nfsd/nfsctl.c), but the root cause sits in synchronous rpcbind registration that the kernel performs on behalf of NFSv2/v3 clients. The work is therefore an important server-side reliability fix whose failure mode is that clients never see the service in rpcbind.

Layton maps several DoS vectors — and one hard one

Five days after the report, Jeff Layton posted the first human analysis. He has already been digging, and he is blunt about the scope:

"I've been doing some investigation on this problem, and I think I pretty much understand it now. There are actually a few different DoS vectors here. Most of them are fairly simple to patch (and I have a few patches for those problems)."

The easy vectors are left unnamed for now. The hard one is structural:

"The hard problem here is that rpcbind registration is done synchronously under the nfsd_mutex. To talk to rpcbind, the kernel has to create a RPC client, which does a RPC ping first. If rpcbind is down then it can take up to a minute for the RPC ping to time out. rpcbind registration failure is not considered fatal, so if it fails the kernel keeps going on. If we couple those delays with a long list of listeners, then it's easy to see how to reproduce the hang."

That last sentence is the missing reproducer. The new netlink listener_set handler can install many sockets in one call; each one may try to register with rpcbind while still holding nfsd_mutex. A down or unresponsive local rpcbind turns each registration into a ~60-second stall. Stack enough listeners and every other nfsd netlink op — cache flush, thread-count changes, export updates — trips the hung-task watchdog, exactly as syzbot observed.

Layton's proposed structural fix is to get the registration off the mutex:

"I think the only real fix here is to do the listener registration outside of the nfsd_mutex. We can either try to drop and reacquire the nfsd_mutex to do the registration or we could move to doing the registration asynchronously outside of the mutex."

He prefers the async path, but flags the race he has not yet designed around:

"I personally like the latter idea better, but I haven't thought enough about how we'd deal with racing listener netlink calls in that case."

Brown: why wait a minute for a local service?

Neil Brown pushed back on the timeout first, before the locking:

"Why are we waiting a whole minute for a local service to respond? If it hasn't responded in 1 second, is it ever really likely to?"

He expected a network-level error rather than a full RPC timeout — ENETUNREACH / EHOSTUNREACH exist, but there is no EPORTUNREACH, and rpcbind is not a remote host. His preferred first step is therefore to make rpc_ping fail fast. Failing that, he agrees async registration is reasonable, and he reframes the semantics in a way that matters for clients:

"nfsd doesn't need the registration, only clients do. So delaying it only means we don't get an error on startup which we currently do. This is not something that would be expected in practice. Maybe a kernel warning if registration fails, and hope the sysadmin notices?"

That is the client-facing stake: NFSv2/v3 clients discover the server via rpcbind. A delayed or failed registration does not stop nfsd from serving, but it does leave clients unable to find the service until registration completes — or permanently, if it never does.

Layton: a shorter timeout is not enough

Layton agrees the minute-long ping looks like a historical leftover — "Is it a throwback to starting rpcbind/portmapper from inetd or something?" — but he rejects timeout-tuning as a complete fix:

"In any case, a smaller timeout would make sense, but even at 1s, you could easily cause a lockup warning with just a few hundred listeners."

"I think we need a more structural solution as well."

On the async design, he confirms nfsd already treats v2/v3 registration failure as non-fatal (it already printks and continues). His real worry is ordering:

"My main concern with doing it async would be getting reg/unreg requests out of order and leaving rpcbind with a broken table, but I think we could probably do something like keep a queue of requests and process them in order from a dedicated thread or by driving async RPC submissions serially from callbacks."

A broken rpcbind table is a silent client-facing outage: the server is up, the sockets are listening, but portmap lookups return stale or missing entries. Any async scheme has to serialize register/unregister so that a racing listener_set cannot unreg-then-reg in the wrong order.

Brown sketches dropping the mutex across the batch

In the last message of the window, Brown questions the premise of "a few hundred listeners" — "Is there a genuine use-case for that?" — and then points at the netlink batching change itself as the amplifier:

"With the old /proc interface we could only add one at a time. The new netlink one adds many at once. Do we really need the mutex across all of that?"

He attached a short sketch (the diff was trimmed at ingest) that explores releasing nfsd_mutex around the multi-listener work rather than holding it for the entire listener_set netlink call. That is closer to Layton's first option — drop and reacquire — than to a fully async rpcbind worker. No one has replied to the sketch yet; the week ends with the design still open.

Where things stand

  • Type: server-side hung-task / DoS bug in the nfsd netlink control plane, with a client-visible rpcbind side effect.
  • Root cause (this week's consensus): synchronous rpcbind registration (including a ~60s rpc_ping) runs under the global nfsd_mutex; netlink listener_set can batch many listeners, so one unresponsive rpcbind wedges every other nfsd netlink op, including nfsd_nl_cache_flush_doit.
  • Easy DoS vectors: Layton says he already has patches; they have not been posted to the list this week.
  • Hard fix, still undecided:
    1. shorten rpc_ping (Brown's first preference; Layton says necessary but insufficient);
    2. drop/reacquire nfsd_mutex around registration / the listener batch (Brown's sketch);
    3. async registration off a serialized queue or callback chain (Layton's preference), with care not to scramble rpcbind's table.
  • No patch series posted, no Fixes: tag, nothing applied. The thread is in the design phase.

The same coarse nfsd_mutex is the lock that now serializes the growing netlink control plane (listeners, cache flush, exports, stats). This week's diagnosis is the first concrete plan to stop treating rpcbind I/O as something that can run while that lock is held.
