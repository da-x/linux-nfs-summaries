Hellwig’s swap_ops v2 folds NFS swap into pluggable ops

Summary

Christoph Hellwig posted swap_ops updates v2, a three-patch follow-on to the swap-ops work already sitting in mm-unstable. The series is not an NFS protocol change. It is an MM refactoring with a targeted swap-writeback performance fix, and it relocates filesystem-based swap I/O so the NFS (and SMB) clients supply swap_ops directly instead of bouncing through a second VFS hook.

Hellwig framed the respin in the cover letter:

"this series is a follow on to the swap ops series now in mm-unstable."

"The first patch reintroduces direct folio writes for synchronous swap files, the other two remove the double indirect for file system based swap."

v2 is a same-week refresh of the July 22 posting. The changelog is small but specific: include swap_ops.h from zswap.c, fix a commit-message typo, and spell out that patch 2 has no functional change.

Patch 1: single-folio writes for synchronous swap

Patch 1 is the bug-fix / performance piece. It lives entirely in mm/page_io.c and restores per-folio submission for synchronous swap devices (zram is the motivating case). Hellwig credited Kairui Song:

"Kairui Song reported that zram benefits from submitting each folio directly instead of batching up I/O because the classic LRU scanning benefits from clearing the folio writeback bit in the scan loop."

"Accommodate that by kicking off writes for synchronous devices for each iteration."

That last sentence is the typo fix versus v1, which had said “reads.” The patch already carries Acked-by from Usama Arif and Chris Li. It does not touch the NFS client; NFS swap remains asynchronous file-backed I/O and keeps the batched path.

Patch 2: a public swap_ops.h for out-of-tree implementations

Patch 2 lifts swap_iocb, swap_ops, and swap_ctx into a new include/linux/swap_ops.h so implementations can live outside mm/page_io.c. Hellwig was explicit that this is plumbing, not behavior:

"There is no functional change, just a move of the declarations."

He also flagged the naming collision with the existing, unrelated swapops.h:

"The close naming is a bit unfortunate, but I could not think of a better name for this header."

That “no functional change” blurb is the direct answer to Chris Li’s v1 review, which asked whether the header move changed any API beyond relocating declarations. The other v1 nit came from Usama Arif, who noted zswap uses the struct and that mm/zswap.c needed the new include (and a CONFIG_ZSWAP=y build). Hellwig agreed that the build bot had already caught it. v2 adds that include.

Chris Li acked patch 2 later the same day, completing MM acks on the header split.

Patch 3: NFS and SMB grow first-class swap_ops

The NFS-relevant work is patch 3. Today, filesystem swap takes two indirect calls: generic swap ops, then the VFS swap_rw method. Hellwig wants the filesystem to hand swap_ops to the swap layer itself:

"Currently swap to and from file systems goes through two indirect calls between the swap ops and the swap_rw method. Reduce this by directly providing the swap_ops from the file system."

The mechanics:

  • swap_fs_submit becomes swap_fs_prepare_rw, which builds the iov_iter on the caller’s stack so a filesystem can invoke it directly.
  • NFS and the SMB client each grow filesystem-specific swap_ops and pass them into swap_fs_activate.
  • The VFS swap_rw hook disappears from include/linux/fs.h, and the locking/VFS docs shrink accordingly.

On the NFS client side the diff is concentrated:

  • fs/nfs/direct.c loses the old 20-line swap-rw helper.
  • fs/nfs/file.c gains the new ops table and activation path (~42 lines).
  • include/linux/nfs_fs.h drops the now-unused declaration.

That is the important NFS client change this week: swap-over-NFS no longer goes generic-ops → swap_rw → nfs_file_direct_*. The client registers its own swap_ops, prepares the iterator with swap_fs_prepare_rw, and submits through the existing NFS direct-I/O machinery. One hop off the swap-over-NFS path, and the VFS no longer needs a dedicated swap method for filesystems that already know how to do swap I/O.

Chris Li had already acked this patch on v1, and Hellwig carried that ack into v2. Li’s v1 reaction is the clearest MM endorsement of the NFS/SMB direction:

"I am very happy to see the direction this patch is going. Now I see how to get rid of the double indirection."

"You convinced me with flying colors."

Where things stand

This is infrastructure plus a zram writeback fix, not a protocol change. By the end of the window the series has MM acks on all three patches (Li on 1/2/3, Arif on 1). No NFS maintainer commented on the client-side move from direct.c into file.c, and no functional objections were raised. The thread remains open past the week; the in-window conclusion is that v2 addressed the v1 nits and the MM side is ready, with the NFS swap-ops hookup waiting on filesystem review.
