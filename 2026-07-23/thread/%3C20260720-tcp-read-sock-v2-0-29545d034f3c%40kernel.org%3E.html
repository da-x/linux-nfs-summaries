kTLS read_sock_rectype series lands for NFSD, NFS client next

Summary

Chuck Lever posted v2 of a six-patch net-next series that gives kernel read_sock consumers a first-class path for TLS control records. The work is a new kernel networking API plus a related kTLS bug fix, not a protocol change: it leaves the on-the-wire TLS/RPC framing alone and only changes how in-kernel TCP consumers (NFSD first, NFS client later) see Alerts and Handshake records once kTLS is active.

Why it matters for NFS

Today tls_sw_read_sock() rejects Alerts and Handshake records with -EINVAL. A consumer that actually needs those records falls back to sock_recvmsg() with ancillary buffers, which is why NFSD's svcsock still runs a MSG_CTRUNC recovery dance on every receive. Lever's cover letter is blunt about the security motivation:

"The improvement is more than cosmetic. All of these consumers need to handle TLS Alert messages efficiently and securely (in particular, for KeyUpdate)."

The first consumer converted in this series is NFSD's svcsock. The NFS client (xprtsock) is explicitly the next target, along with NVMe target and NVMe host. Patch 2 lists all four subsystems as currently either falling back to sock_recvmsg() or lacking TLS alert handling entirely. That is the client-side bug the series is scaffolding: once kTLS is on, an NFS client using read_sock cannot see KeyUpdate or fatal Alerts without the new callback.

v2 is a substantial redesign from the February v1 (read_sock_cmsg):

  • The proto_ops method was renamed from read_sock_cmsg to read_sock_rectype.
  • Non-data records now use a record-type actor, not RFC cmsg-style delivery.
  • Consecutive no-data records are bounded so they cannot pin the socket lock (new patch 1).
  • Selftests cover data/control interleaving (new patch 4).

The new API

Patch 2 adds read_sock_rectype to struct proto_ops. The existing read_sock data path is left unchanged, so current consumers keep their old behavior. A new sk_read_rectype_actor_t callback extends the data actor with a rectype argument (for example TLS_RECORD_TYPE_ALERT). Lever is careful about the contract:

"The new sk_read_rectype_actor_t callback does not share the data actor's byte-counting contract. It returns 0 to consume a record or a negative value to requeue it and stop delivery. The return is never a byte count."

Patch 3 implements that method on the kTLS software receive path, so NFSD, the NFS client, and NVMe no longer have to detour through CMSG just to see a control record.

Because read_sock_rectype has no userspace entry point, patch 4 exercises the shared decryption and rx_list pipeline through recvmsg and splice instead. Seven new tests cover data-control-data, multiple distinct control types, peek-after-data, control-before-data, mixed types, and a trailing control record followed by EOF.

The no-data cap: bug fix hiding in a feature series

Patch 1 is the important bug fix. An empty TLS 1.3 data record (and, once the rest of the series lands, a control record with no payload) leaves tls_sw_read_sock() looping without advancing the caller's read descriptor. A peer that streams such records can pin the socket lock and the kernel receive context indefinitely. The patch caps consecutive no-data records at TLS_RX_NODATA_LIMIT; the count resets on any record that delivers bytes. Returning 0 is treated as "no progress, re-poll," not EOF.

Lever scoped the cap to tls_sw_read_sock() alone. Splice and recvmsg already return to the caller's context, reschedule, and drop the lock; a flood there only burns the caller's own scheduler time. read_sock consumers, by contrast, drive the loop from a work item or service thread that holds the socket lock across the whole call.

That patch drew the week's real technical debate.

Hannes Reinecke Reviewed-by'd it but flagged the presentation:

"This is technically a fix, so it might be worthwhile sending it on its own."

Lever initially pushed back, arguing the issue "is not reachable until the subsequent patches in this series have been applied," so he had positioned it as a prerequisite rather than part of an earlier fixes series.

kTLS maintainer Sabrina Dubroca disagreed. She treated patch 1 as a follow-up to 3be28e2c9cd0 ("net/tls: Consume empty data records in tls_sw_read_sock()"):

"Control records only become a problem after the rest of the series, but TLS 1.3 empty data records would get there with the current code, no?"

She also asked whether a time-based limit (as net_rx_action() does) would be better than a packet count, and whether tls_sw_read_sock() already reschedules via tls_rx_rec_wait(), undercutting part of Lever's "only this path needs the cap" rationale.

Lever then offered to change presentation strategy: post the earlier kTLS fixes Dubroca had already suggested, together with 1/6 of this series, destined for net, and keep 2–6 for net-next. Dubroca agreed:

"That makes sense. 2..6/6 from this series can still be around for review (maybe with a [RFC] prefix if you resend the net-next patches before net gets merged into net-next, to help the maintainers by avoiding conflicts)."

That is where the week ended: the no-data bound is now understood as a standalone kTLS fix for empty TLS 1.3 data records, to be split out to net, while the new API stays on net-next.

svcsock conversion (and what it previews for xprtsock)

Patch 5 is the first real consumer. When the socket provides read_sock_rectype (now set by kTLS), svc_tcp_recvfrom() dispatches to svc_tcp_recvfrom_readsock():

  • svc_tcp_recv_actor() parses the RPC record byte stream directly from skbs. Fragment header bytes fill sk_marker; body bytes go into rq_pages at sk_datalen. Completing the last fragment of an RPC message zeros desc->count and stops the loop.
  • svc_tcp_rectype_actor() handles non-data TLS records. Fatal alerts mark the transport for deferred close and stop the loop via desc->count. Every non-data record is consumed (return 0) so later data records remain deliverable.

Plain TCP / non-kTLS sockets keep the old sock_recvmsg() path in patch 5 so the two implementations can be reviewed side by side. Patch 6 then deletes that legacy path (~300 lines), on the grounds that plain TCP already provides tcp_read_sock in proto_ops. One read_sock-based receive path then covers all NFSD cases: read_sock_rectype under kTLS, read_sock otherwise.

That svcsock conversion is the template the NFS client is expected to follow. xprtsock is not touched this week, but the cover letter and patch 2 both name it as a later series on the same mechanism. Until that lands, a kTLS-enabled NFS client still cannot see control records on the read_sock path.

Reviews and NVMe caveat

Reinecke Reviewed-by'd patches 1–3. On the new method name he only remarked, "Naming is a bit odd, but hey." On the cover letter he was supportive but declined to rubber-stamp the SUNRPC half, and he cooled the NVMe "we need it" pitch:

"I was tempted to say 'We need it', but meanwhile we found during spec review that the REPLACETLSPSK mechanism as defined in the spec is at odds with the TLS KeyUpdate. So while we (from the NVMe side) might be wanting to use it eventually, we first have to figure out how to interact sanely between the NVMe and TLS layer."

He also said he did not feel qualified to review the NFS/SunRPC details. No Reviewed-by appeared this week on patches 4–6 (selftests and the svcsock conversion).

Status at week close

The series is under active review, not merged. Consensus at the end of the window:

  • Treat patch 1 as a kTLS bug fix for empty TLS 1.3 data records and send it (with earlier related fixes) to net.
  • Keep patches 2–6 on net-next as the new read_sock_rectype feature, possibly marked RFC if they are resent before net merges into net-next.
  • Open design questions remain on packet-count vs. time-based bounding and on whether tls_rx_rec_wait() already provides a reschedule point.
  • NFSD svcsock is the first consumer; NFS client xprtsock conversion is planned but not in this series.

That split is the practical takeaway for NFS client development this week: the infrastructure that will let xprtsock handle KeyUpdate and fatal Alerts without a CMSG fallback is on the table, but the lock-pinning fix needs to land first, and the client-side conversion itself is still a follow-up.
