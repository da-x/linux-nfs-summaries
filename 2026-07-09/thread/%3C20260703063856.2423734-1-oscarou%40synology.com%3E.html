lockd: bitmap-based fix for multiple NLM_SHARE grants from one owner lands in nfsd-testing

Summary

lockd: preserving multiple NLM_SHARE grants from the same owner

This week, a long-running bug fix on the NFS server side reached its v3 and was merged into nfsd-testing. The patch addresses a correctness flaw in how the Linux NFSv3/NLM (Network Lock Manager) share handler tracks open file state when a single client owner issues multiple NLM_SHARE calls against the same (file, owner) tuple.

The bug

Oscar Ou of Synology posted v3 of the patch on Friday, July 3, describing a scenario that is "particularly visible to Windows-style clients that map each open of a file to a distinct NLM_SHARE, all carrying the same NLM owner handle." The core problem:

"the current implementation overwrites the recorded access and deny modes with the latest pair. A subsequent NLM_UNSHARE then drops the entire entry, even if other grants were implicitly subsumed by the most recent SHARE."

Ou illustrated the failure with a concrete four-step sequence:

  1. SHARE(access=RW, deny=W) → entry [RW, deny W]
  2. SHARE(access=R, deny=N) → entry [R, deny N] (the RW/W pair is silently overwritten)
  3. UNSHARE(access=R, deny=N) → entry freed entirely
  4. UNSHARE(access=RW, deny=W) → nothing left to release

The result: the first open's share protection vanishes prematurely, undermining the advisory lock/share semantics that NFSv3 clients rely on for file coordination.

The fix: a u16 bitmap instead of refcounts

Because fsh_access and fsh_mode each take values in {0..3}, there are only 16 possible (access, deny) pairs. Ou's solution tracks each pair with a single bit in a u16 bitmap, indexed by (access << 2) | deny. SHARE sets the bit; UNSHARE clears it. The aggregate s_access and s_mode fields are recomputed as the union of all set bits, and the entry is freed only when the bitmap reaches zero.

A key design consideration Ou highlighted in the v3 cover letter was idempotency under UDP retransmission:

"NLM has no duplicate reply cache, so both SHARE and UNSHARE handlers must be idempotent under UDP retransmit."

This is why v3 replaced the per-value refcount approach from v2 with a bitmap:

"setting or clearing a single bit is idempotent, whereas incrementing and decrementing a refcount is not."

The patch also extends nlmsvc_unshare_file() to accept the access and deny modes as arguments so the correct bit can be cleared, with the two callers in svcproc.c (NLMv3) and svc4proc.c (NLMv4) updated accordingly. The change spans four files (fs/lockd/share.h, svc4proc.c, svcproc.c, svcshare.c) with 44 insertions and 8 deletions.

Backport considerations

Notably, Ou included no Fixes: tag, explaining:

"The fix depends on the xdrgen regeneration to reject out-of-range fsh_access / fsh_mode on the wire, so a Fixes: tag would mislead -stable backporters."

This makes the patch dependent on Chuck Lever's earlier "lockd: Regenerate NLMv4 XDR code" change, which adds range validation for the share fields.

Merged

The turnaround was swift. On Saturday, July 4, Chuck Lever confirmed:

"Applied to nfsd-testing, thanks!"

The commit landed as c8c45fb61a5ff3eb786e4aa434b534b605ab657e.

Significance for NFS client development

While this is a server-side fix in the lockd/NLM share code, its impact ripples directly to NFSv3 clients—especially Windows interop scenarios via Samba or similar gateways. Clients that open the same file multiple times under a single owner handle will no longer see their earlier share grants silently discarded. The idempotency guarantee under UDP retransmit also strengthens reliability for lossy network paths, which is a common concern in enterprise NFS deployments. This is a textbook example of a subtle state-management bug fix that improves correctness without any protocol change: the NLM wire format is untouched; only the kernel's internal bookkeeping changes.
