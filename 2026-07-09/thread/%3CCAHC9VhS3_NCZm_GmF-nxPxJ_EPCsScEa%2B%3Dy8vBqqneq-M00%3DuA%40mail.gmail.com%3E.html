NFSv4.2 listxattr size-accounting fix lands v2 with Reviewed-by

Summary

NFSv4.2: fixing the nfs4_listxattr NULL-pointer oops and its sibling undercount

This week's thread is a bug-fix effort on the NFS client, tracing a kernel oops in the extended-attribute (xattr) path back to a single accounting bug that had two symptoms. The discussion was cross-posted: the primary conversation lives in the sibling thread rooted at the original v1 patch, and this week's single message here is Achilles Gaikwad's reply to Paul Moore's review suggestion, which kicked off the v2 revision.

The bug: one root cause, two symptoms

The original report (Jul 3) documented a hard crash on an NFSv4.2 mount whenever listxattr() was called with a zero-length buffer — the standard "how big is my xattr list?" size query:

"A call to listxattr() with a buffer size = 0 returns the actual size of the buffer needed for a subsequent call. On an NFSv4.2 mount this triggers the following oops"

The trace pointed at nfs4_xattr_alloc_entry → _copy_from_pages. The culprit was commit f71ece9712b7 ("security,fs,nfs,net: update security_inode_listsecurity() interface"), which changed security_inode_listsecurity() to decrement the remaining-size counter even when the buffer pointer is NULL. In the size-query case that made left underflow into a huge size_t, so nfs4_listxattr_nfs4_user() treated the NULL buffer as real and dereferenced it.

The review: Paul Moore's reframing

Paul Moore, who owns the LSM side of the interface change, pushed back on v1's narrow fix and proposed a cleaner structure that ties the size accounting directly to the security-hook call — using a scratch copy (left2) to measure how much the hook consumed, then only decrementing left when a buffer is actually present. In his reply he asked:

"I wonder if it would be better associate the handling code with the security_inode_listsecurity() call a bit more closely?"

This week's message: v2 confirmed and validated

The in-window message here is Achilles Gaikwad's reply, where he accepts the suggestion and shows it also fixes a second, subtler defect — the size query was coming up short, not just crashing:

"Yes, that works and is better than what I was proposing."

listxattr("/mnt/abc.txt", NULL, 0) = 26 <-- v1 patch, actual is 42
listxattr("/mnt/abc.txt", NULL, 0) = 42 <-- with your changes

"Tested your suggestion on v4.2 w/ an NFSv4 ACL, an SELinux label and a user xattr present; both the size query and the exact-size read now return 42." "Will send a v2 soon, thanks!"

The undercount mattered because a caller that allocated the (too-small) returned size would then get -ERANGE on the follow-up read. That is exactly what the v2 patch describes, and why it was retitled from "fix nfs4_listxattr NULL pointer dereference" to "fix nfs4_listxattr size accounting" — the same accounting bug caused both the oops and the undercount. v2 declares left as ssize_t, measures security-hook consumption with a scratch variable, drops the now-unneeded NULL-buffer special case, and carries Suggested-by: Paul Moore.

Resolution this week: Reviewed-by and routing through the NFS tree

Paul Moore reviewed v2, CC'd the LSM and SELinux lists, and offered to route it via the LSM tree if needed — but noted his own testing was blocked by an unrelated NFS regression:

"Unfortunately my testing was unsuccessful due to an NFS problem that started with the v7.2 merge window that I haven't had the time to bisect yet." "Reviewed-by: Paul Moore paul@paul-moore.com"

NFS maintainer Anna Schumaker confirmed the routing decision in her reply:

"Yeah, we'll send it through the NFS tree. I'll be curious to hear what problem you're hitting, and what patch is the culprit once you do that bisect!"

The week closed with a side investigation into Paul's separate v7.2 regression. Stephen Smalley reported the SELinux test suite passed for him on selinux/dev (v7.2-rc1 based) "with and without the patch," while Paul noted they fail on vanilla v7.1→v7.2-rc1 and suspected a userspace interaction; Smalley concluded it was likely a distro/userspace difference (F44 vs. Rawhide). That bisect is still open and continues past this week's window, but the nfs4_listxattr fix itself is agreed, reviewed, and slated for the NFS tree.

Bottom line: A clean, well-scoped client bug fix — a NULL-deref oops plus a silent size undercount in the NFSv4.2 xattr path, both rooted in the post-f71ece9712b7 security-hook accounting — was refined through review into v2 and earned a Reviewed-by, with the NFS maintainers taking it through their tree.
