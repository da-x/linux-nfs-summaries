NFSD: Fix UAFs in client teardown and state revocation (v4)

Summary

NFSD: Fix UAFs in client teardown and state revocation — v4 lands, reviewed, pushed to testing

Type: Bug fix series (use-after-free / NULL-deref races + one svc_export leak) in the NFS server (NFSD), touching client-teardown, delegation/lock/open-state revocation, and laundromat reaping paths.

What happened this week

On Thursday, 2026-07-09, Chuck Lever posted v4 of a nine-patch series that fixes a family of use-after-free bugs in NFSD's client teardown and state-revocation paths cover letter. The series had been iterating since early July (v2 on 07-05, v3 on 07-07), and this week's activity was the final review pass and push to testing.

Background: the core problem

The cover letter lays out the root cause with characteristic precision:

"An NFSv4 stateid, and a bare lock owner reachable through the client's owner hash, hold only a raw pointer to the owning nfs4_client. That client outlives its state only because __destroy_client() drains every stateid and owner before free_client() runs."

The danger is any code path that drops the lock keeping the client (or owner) reachable while still holding a raw pointer — a concurrent teardown can then free the object first. The original report was a NULL-pointer dereference during client teardown, but as Chuck notes:

"auditing the pattern found more across the revocation and laundromat-reaping paths."

The uniform fix strategy

The series applies one consistent technique wherever the racing object is the client: pin it with cl_rpc_users across the window in which nn->client_lock is dropped. A subtle correctness point is called out explicitly:

"Skipping a client that is already expiring is part of the correctness argument, not cleanup. force_expire_client() stops consulting cl_rpc_users once its wait has passed, so a pin taken then would not hold the client."

The series also introduces a new lock-order edge — nn->client_lock now nests outside nn->deleg_lock and nn->blocked_locks_lock — which is documented in netns.h for future maintainers.

Individual patches

  1. Lock owner UAF during client teardown 1/9 — The original bug: __destroy_client() walks the owner hash and calls remove_blocked_locks() without holding a reference on each owner. The per-net laundromat can free the owner concurrently, producing "a NULL dereference in remove_blocked_locks()." Reported by Wolfgang Walter; carries Reviewed-by from NeilBrown and Jeff Layton.

  2. Delegation revoke UAF 2/9 — nfs4_laundromat() unhashes an expired delegation, drops deleg_lock, then revoke_delegation() relinks it under cl_lock. In that window the delegation is on neither list, so client_has_state() reports no state and teardown can proceed to free_client().

  3. Admin state revocation UAF 3/9 — nfsd4_revoke_states() drops nn->client_lock across revoke_one_stid(), which dereferences the client.

  4. Export state revocation UAF 4/9 — Same pattern in nfsd4_revoke_export_states(), triggered by exportfs -u (NFSD_CMD_UNLOCK_EXPORT).

  5. NFSv4.0 revoked-state cleanup UAF 5/9 — nfs40_clean_admin_revoked() in the laundromat races force_expire_client().

  6. Consolidate revocation-path client unpin 6/9 — Refactoring: four open-coded copies of the pin-drop idiom are consolidated into put_client_no_renew() helpers. "No change in behavior."

  7. Blocked-lock reaping UAF 7/9 — The laundromat detaches a blocked lock, drops blocked_locks_lock, and the final nfs4_put_stateowner() takes cl_lock on a possibly-freed client.

  8. close_lru reaping UAF 8/9 — An open owner left on nn->close_lru after its final CLOSE holds a raw pointer; the laundromat's nfs4_put_stid() dereferences it without a pin.

  9. svc_export leak when reaping open stateids 9/9 — A separate (non-UAF) bug: free_ol_stateid_reaplist() calls ->sc_free() directly, bypassing the sc_export reference drop that nfs4_put_stid() performs. This pins the export and "blocks unmount for the lifetime of the stateid." Also fixes a double-put race in nfs4_put_stid() itself by reading sc_export under cl_lock. Reported by sashiko-bot.

Review and conclusion

Jeff Layton reviewed patches 7, 8, and 9 on the same evening (18:36–18:40 UTC), granting Reviewed-by on all three. On patch 9 he noted a minor ordering nit:

"nit: nfs4_put_stid() does this in the reverse order. It doesn't actually matter, but it looks a bit weird if you want to fix it up before merging." review of 9/9

Chuck confirmed the fix was applied and the series merged into testing:

"Swap applied, series pushed to nfsd-testing. Thanks for your review!" reply

Significance

This is a substantial hardening of the NFSD state-management code. The series fixes seven distinct UAF/NULL-deref races plus one export-reference leak, all rooted in the same architectural pattern: raw pointers to nfs4_client that rely solely on lock discipline (rather than reference counting) for lifetime. The uniform cl_rpc_users pinning approach, combined with careful handling of the force_expire_client() expiry window, provides a robust template for any future reaping or revocation path added to NFSD.
