NFS Direct I/O folio debate: author commits to reusing get_contig_folio_len() and moving the extractor into iov_iter for v3

NFS Direct I/O folio debate: author commits to reusing get_contig_folio_len() and moving the extractor into iov_iter for v3

Classification

This week's single message is a continuation of the review discussion around patch 6/7 ("Optimize direct I/O to use folios for requests") in Pranjal Shrivastava's (Google) seven-patch series "nfs: Modernize Direct I/O path". The series is an architectural refactor of the NFS client O_DIRECT path — migrating from the legacy iov_iter_get_pages_alloc2() API to the modern iov_iter_extract_pages() API and making requests folio-based — with two embedded bug fixes (a data-corruption fix in nfs_direct_extract_pages() and an early-unpin / bytes-accounting defect). It is groundwork for PCI Peer-to-Peer DMA (P2PDMA), not a protocol change.

Bridge from prior weeks

The central dispute, opened when the v2 series was posted on June 16, concerns whether patch 6's assumption — that every page returned by iov_iter_extract_pages() belongs to a valid folio so page_folio() is safe — holds across all memory types. Trond Myklebust, Christoph Hellwig, and Matthew Wilcox pushed back, noting the MM invariant "every page is part of a folio" has important exceptions (slab, vmalloc, iomem).

Over the preceding three weeks the discussion narrowed considerably:

  • Week 1 (June 16–18): Reviewers flagged the page_folio() assumption as a minefield; Hellwig advised to "stick to what the block code does or even better reuse as much as possible of that code."
  • Week 2 (June 19–25): Pranjal accepted the critique but surfaced a wrinkle — the block layer's own iov_iter_extract_bvecs() path also calls page_folio() via get_contig_folio_len() without additional slab/vmalloc checks. Hellwig de-escalated for NFS specifically (GUP-pinned user pages are always valid folios) but flagged a latent kvec-iterator gap: "Not that I'd want to rely on that in the long run."
  • Week 3 (July 3–8, this week): The author and Hellwig converged on a concrete plan.

This week: one message (July 8)

The single in-window message is Pranjal's reply to Hellwig's July 7–8 guidance, where the author formally commits to the implementation path for v3.

The technical commitment

Pranjal confirms both halves of the agreed resolution:

"Ack. I'll reuse get_contig_folio len and move the nfs extractor to iov_iter for v3."

This is a meaningful step forward. After three weeks of debate about whether page_folio() is safe, the maintainers have converged on a pragmatic answer: NFS should reuse the block layer's get_contig_folio_len() helper rather than hand-rolling its own folio grouping or relying on the "every page is a folio" invariant. The author is also committing to moving the NFS-specific extraction helper into lib/iov_iter.c, which addresses the broader architectural concern Wilcox raised — that "it is no business of the filesystem what the iov_iter refers to."

Hellwig's endorsement (quoted in this week's reply)

The message quotes Hellwig's prior-week guidance, which provides the context for the author's commitment:

"Sounds like the best way forward for now."

The "for now" qualifier is important — it leaves open the possibility of a longer-term iov_iter API change but defers that decision to a future discussion, unblocking the immediate series.

Clarifying the series-split question

Pranjal also clarifies his earlier process question about whether to split the series:

"Apologies for being unclear. I meant I could post a standalone series that moves NFS Direct I/O to folio, i.e. break out Patches 6 & 7 to another series, if that makes sense?"

Hellwig's response (also quoted in this week's message) was:

"Sorry if I'm thick, but I'm not sure what 'folio' move means. In doubt if you think you can get a series merged quicker without a later part I'd split it."

This is a merge-oriented signal: Hellwig prefers getting the uncontroversial parts of the series (the API migration, the two bug fixes, the pin-aware infrastructure) landed rather than holding them hostage to the folio-grouping patch. If patch 6's refactoring to use get_contig_folio_len() introduces cross-subsystem dependencies (e.g., exporting a block-layer function), splitting it out as a standalone prerequisite patch would let the rest of the series proceed independently.

Key technical arguments this week

  1. get_contig_folio_len() is the agreed-upon path forward. After three weeks of debate, the maintainers have settled on reusing the block layer's helper rather than either (a) relying on the page_folio() invariant or (b) making a larger iov_iter API change. This is a pragmatic, minimal-diff resolution that unblocks the series.

  2. The NFS extractor will move into lib/iov_iter.c. The author's commitment to "move the nfs extractor to iov_iter" addresses the broader architectural concern Wilcox raised — that filesystems should not have to reason about folio semantics at all. This is a larger API change that would shield all filesystems from having to hand-roll folio grouping.

  3. Series splitting is endorsed. Hellwig's "I'd split it" guidance suggests the folio-grouping patch (or the prerequisite of exporting get_contig_folio_len()) may be sent as a standalone patch, with the rest of the modernization series proceeding independently. This is a common kernel development pattern for reducing review burden and enabling incremental merge.

Evolution of the discussion (three-week arc)

  • Week 1 (June 16–18): Series posted; Trond Myklebust, Hellwig, and Wilcox push back on the page_folio() assumption. Reviewers advise reusing block-layer code.
  • Week 2 (June 19–25): Author accepts the critique but surfaces a wrinkle: the bvec extractor has the same risk. Asks whether iov_iter should export a safe helper. Hellwig de-escalates for NFS specifically (GUP-pinned pages are safe) but flags the kvec gap.
  • Week 3 (July 3–8, this week): Author and Hellwig converge on a concrete plan: expose and use get_contig_folio_len(). Kernel-side direct I/O confirmed as a real use case. Series splitting endorsed to unblock merge.

Final conclusions and where things stand

The central technical dispute over patch 6 is now effectively resolved. The agreed path forward is for Pranjal to refactor the NFS folio-grouping logic to call get_contig_folio_len() from the block layer, rather than hand-rolling folio grouping or relying on the page_folio() invariant. Hellwig's "Sounds like the best way forward for now" is a clear endorsement that unblocks the author to post a v3.

The broader architectural question — whether lib/iov_iter.c should eventually export a safe helper (or hide folio semantics entirely) from all filesystems — remains open but is explicitly deferred ("for now"). Hellwig's confirmation that kernel-side direct I/O users exist (loop, zloop, nvmet, scsi target, nfsd) keeps this question relevant for future work.

No new patches have been posted this week. The expectation is that Pranjal will post a v3 incorporating:

  • Refactored patch 6 using get_contig_folio_len() (possibly as a standalone prerequisite patch).
  • Updated CC lists (linux-rdma, linux-pci) as agreed in the prior week.
  • Full xfstests quick-suite results in the cover letter.

The thread remains open pending that v3 posting and subsequent review.
