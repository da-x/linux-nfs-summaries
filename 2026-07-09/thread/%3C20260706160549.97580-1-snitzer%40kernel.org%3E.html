NFS/localio: conditional inline IO to cut workqueue latency

Summary

NFS/localio: issue IO inline when not reclaiming memory

Category: Bug fix / performance improvement (removes an unnecessary workqueue hop in the LOCALIO path).

Overview

On 2026-07-06, Mike Snitzer posted a three-patch series to linux-nfs that makes the NFS LOCALIO data and commit paths issue IO inline when the submitting context is not a memory-reclaim worker. The change targets a latency and parallelism regression introduced by an earlier commit that unconditionally bounced every LOCALIO read/write/commit through a dedicated !WQ_MEM_RECLAIM workqueue.

Background: Why the workqueue hop exists

Snitzer explained the origin of the current design in the cover letter:

"That intermediate hop was introduced by commit b9f5dd57f4a5 ("nfs/localio: use dedicated workqueues for filesystem read and write") because: LOCALIO submits IO directly into a stacked local filesystem (e.g. XFS) which may in turn flush its own !WQ_MEM_RECLAIM workqueue. Doing so from a WQ_MEM_RECLAIM worker -- most importantly writeback's wb_workfn running on bdi_wq -- or from an explicit PF_MEMALLOC reclaim task trips check_flush_dependency() and risks a forward-progress deadlock."

The problem is that the hazard only materializes in reclaim contexts. For ordinary application-driven IO, the workqueue hop is pure overhead:

"For ordinary application/task submission -- e.g. O_DIRECT, or an fsync-driven commit -- the workqueue hop buys nothing: it just adds a context switch and scheduling latency per IO and throws away the NFS client's inherent application-context parallelism."

The Solution: A New Workqueue-Core Helper

The core of the series is a new exported helper in kernel/workqueue.c:

current_is_workqueue_mem_reclaim() — reports whether %current is a WQ_MEM_RECLAIM worker, using "exactly the predicate check_flush_dependency() warns on." Snitzer noted it mirrors existing context-introspection helpers like current_is_workqueue_rescuer() and current_work(), which is why the patch carries Ccs to Tejun Heo, Lai Jiangshan, and LKML.

A new NFS-side helper, nfs_local_defer_io(), combines this test with the existing PF_MEMALLOC check to decide per-IO whether to defer to nfslocaliod_workqueue or run inline.

Patch-by-Patch Breakdown

Patch 1/3: Inline read and write

Adds current_is_workqueue_mem_reclaim() to the workqueue core and applies the gating to nfs_local_do_read() and nfs_local_do_write(). Key safety arguments:

  • Buffered writeback still bounces — wb_workfn is a WQ_MEM_RECLAIM worker, so it continues to defer.
  • O_DIRECT and app-context submission now run inline.
  • Completion path unchanged: "when the underlying filesystem returns -EIOCBQUEUED, the kiocb ki_complete callback … can run in bottom-half context and so must still defer the pgio completion (nfs_local_pgio_release -> rpc_call_done) to nfsiod_workqueue via nfs_local_pgio_aio_complete()."

Snitzer also flagged a stack-depth consideration for reviewers: "The inline path now stacks the NFS pgio path plus the underlying filesystem's ->write_iter/->read_iter (and vfs_fsync_range) in task context. … feedback on inline stack headroom under deeply-stacking filesystems (XFS especially) is welcome."

Patch 2/3: Remove dead FLUSH_SYNC handling

A cleanup patch with "no functional change." The FLUSH_SYNC branch in nfs_local_commit() has been dead since LOCALIO was first introduced (commit 70ba381e1a43), because every caller strips it before dispatch. The patch removes the dead branch, the now-unused ctx->done completion plumbing, and the unused "how" parameter from nfs_local_commit().

Patch 3/3: Inline commit (fsync)

Extends the same gating to the commit path. The writeback-triggered commit (nfs_write_inode() → __nfs_commit_inode()) still defers because it runs under wb_workfn on the WQ_MEM_RECLAIM bdi_wq. Application-context commits — fsync, O_DIRECT, and NFSv4.2 copy/clone — now run inline.

"Completion (nfs_commit_release_pages -> nfs_commit_end) then runs synchronously in the submitting context; higher layers already cope with this, as __nfs_commit_inode() dispatches the commit async and waits for it separately via wait_on_commit()."
