nfsd write-verifier data-loss fix queued for 5.10.y stable

Summary

This week's activity in this thread is a single, closing message: stable maintainer Sasha Levin acknowledging and queuing the NFS server (nfsd) silent-data-loss fix for the 5.10.y stable tree. It lands one day after Chuck Lever posted the 5.10.y backport on July 3 (covered in the prior week's summary), replying to Greg Kroah-Hartman's stable queue request.

Levin's reply is terse but conclusive:

"Queued for 5.10.y, thanks!"

That one line marks the end of the thread's active discussion — the patch is now accepted into the stable pipeline and will ship in the next 5.10.y release cycle. No objections, no further review, no additional backports were requested this week.

Classification

  • Type: Bug fix — specifically a protocol-contract violation in the NFS server (nfsd) that produces silent data loss on NFS clients. It is not a new feature and not a wire-protocol change; it restores the existing UNSTABLE+COMMIT durability contract.
  • Subtree: fs/nfsd/vfs.c (server side), but the impact is squarely client-visible: clients stop being told their data is durable when it actually failed writeback.
  • Severity: High. The failure mode was silent data loss — one of the worst classes of storage bug because there is no error signal to alert applications or operators.

Bridging prior weeks (brief)

The original fix was authored by Jeff Layton and posted to mainline on May 22, reviewed and applied to nfsd-testing the same day. The bug was reported by Chris Mason (Meta), credited via Reported-by: in the patch. This week's thread is purely the downstream stable backport of that already-accepted upstream fix (commit 2090b05803faab8a9fa62fbff871007862cac1b7).

Technical detail (carried from the original fix)

The bug: nfsd_vfs_write() and nfsd_commit() both call filemap_check_wb_err() to detect deferred writeback errors, but neither rotates the server's write verifier (nn->writeverf) when that check fails. Every other durable-storage-failure path in these functions calls commit_reset_write_verifier() before returning an error.

The consequence, as Layton originally spelled out:

"The missing rotation means clients holding UNSTABLE write data under the current verifier will COMMIT, receive the unchanged verifier back, and conclude their data is durable — silently dropping data that failed writeback. This violates the UNSTABLE+COMMIT durability contract (RFC 1813 §3.3.7, RFC 8881 §18.32)."

The fix adds verifier-rotation calls at both filemap_check_wb_err() error sites, matching the pattern already used by adjacent error paths. Lever noted a safety property of the approach:

"The helper already filters -EAGAIN and -ESTALE internally, so the calls are unconditionally safe."

The one adaptation for 5.10.y

The backport required a single change relative to mainline, flagged in Lever's cover note:

"[ cel: open-code the reset; commit_reset_write_verifier() is v6.7 ]"

Because the commit_reset_write_verifier() helper only exists from v6.7 onward, it is unavailable in the 5.10.y stable tree, so Lever inlined the equivalent logic directly at both error sites. The patch touches fs/nfsd/vfs.c with 8 insertions and 1 deletion.
