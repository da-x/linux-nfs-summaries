NFSD UAF fix series v2: six-patch teardown/revocation lifetime audit lands with reviews; Sashiko ABBA alarm cleared as false positive

Summary

NFSD UAF fix series v2: six-patch teardown/revocation lifetime audit lands with reviews; Sashiko ABBA alarm cleared as false positive

Type: Bug fix — a family of use-after-free (UAF) defects in the NFS server (nfsd) client-teardown and state-revocation machinery. This is not a wire-protocol change or new feature, and it is server-side nfs4state.c work rather than NFS client development; the "NFS client" in the subject refers to the nfs4_client object that NFSD tracks on behalf of remote clients.

Bridging prior weeks (brief)

This thread is the direct payoff of the 6.18.37 crash investigation summarized in the stwm.de thread. There, Wolfgang Walter's production fileserver wedged with a NULL-deref oops in remove_blocked_locks() → __destroy_client() → nfsd4_destroy_clientid(), and Chuck Lever exonerated the export-cache revert commit, re-scoping the bug as a latent upstream nfs4state.c lifetime defect: "the 6.18.36-good / 6.18.37-bad split is a timing coincidence; I believe the same latent bug is present in both." He committed to drafting an upstream fix "separately," and Wolfgang soaked the candidate patch on production with no regressions. This week's v2 series is that fix, now expanded from the single reported crash into a full audit of the same lifetime pattern.

This week's discussion

Chuck posts v2 — one crash, five sibling races (2026-07-06). The cover letter frames the core invariant and how it breaks:

"A NULL-pointer dereference reported during NFSv4 client teardown (patch 1) proved to be one instance of a broader lifetime bug in NFSD's state-revocation machinery. This series fixes the reported crash and the sibling races found by auditing the same pattern, then consolidates the fixes."

The root cause is a missing reference: "A stateid, and a bare lock owner reachable through the client's owner hash, hold only a raw pointer to the owning nfs4_client; a reference on the stateid or owner does not keep the client alive. The client outlives its state solely because __destroy_client() drains that state before free_client() runs." Several paths break that invariant — the laundromat unhashing an expired delegation before re-linking it (patch 2), nfsd4_revoke_states() and its export/NFSv4.0 admin-revoke siblings dropping nn->client_lock then dereferencing the client again (patches 3–5), and __destroy_client() walking the owner hash with no reference held (patch 1). Changes since v1: "Add matching UAF fixes in several other paths." The series touches only fs/nfsd/netns.h and fs/nfsd/nfs4state.c (+94/−20).

The individual patches, each with a precise race narrative:

  • Patch 1 fixes the reported crash: __destroy_client() walks cl_ownerstr_hashtbl and calls remove_blocked_locks() without holding a reference, so "the per-net laundromat, which reaps timed-out blocked locks from nn->blocked_locks_lru independently of client state, can free the same lock owner concurrently." The freed, zeroed slab object produces the NULL deref. Fix: hold cl_lock across the walk and take a reference + unhash each lock owner before dropping it. Carries Reported-by: Wolfgang Walter and a Closes: link to his oops report.
  • Patch 2 closes the delegation-revoke window: "Between the unhash and the revoke the delegation is on neither client-reachable list, so client_has_state() can report no remaining state." A rebooted client whose new incarnation supersedes the old one can run __destroy_client() to completion while revoke_delegation() is still about to dereference clp->cl_lock. Fix: pin with cl_rpc_users across the revoke.
  • Patches 3–5 cover the admin-revoke, export-revoke (exportfs -u), and NFSv4.0 revoked-state cleanup paths, all sharing the "drop client_lock, then dereference client" flaw. Notably, patch 3 documents that force_expire_client() does not consult cl_rpc_users, so "the walk must also skip a client that is already expiring."
  • Patch 6 consolidates: the fixes left "four open-coded copies of one idiom," so Chuck factors the pin-drop into __put_client_locked() with a renew flag, adding put_client_no_renew_*() for the revocation paths that "must not revive the client they are tearing down." No behavior change.

Technical assessment

  • Classification: Pure bug fix — a cluster of use-after-free races in nfsd's NFSv4 client-state lifetime management. No protocol change, no new feature. Server-side only.
  • Evolution this week: The thread moves from diagnosis (prior weeks) to a complete, reviewed fix. Chuck's single-crash v1 became a six-patch audit of the same broken invariant; the one substantive review objection (Sashiko's ABBA-deadlock claim on patch 2) was investigated and dismissed as a false positive within hours, leaving the full series with Reviewed-by tags from both Neil Brown and Jeff Layton.
  • Key technical argument: The recurring flaw is that a stateid/owner reference does not pin the owning nfs4_client, so any path that drops client_lock (or unhashes an object) before re-dereferencing the client opens a UAF window against __destroy_client(). The uniform remedy is to pin with cl_rpc_users under client_lock while skipping already-expiring clients — and patch 6 deduplicates that idiom.
  • Status: Reviewed and ready as of end of window; no merge announcement yet in this thread. A v3 (9 patches) and a v4 (9 patches) with the same lead subject appear in later activity, suggesting further refinement after this week.
