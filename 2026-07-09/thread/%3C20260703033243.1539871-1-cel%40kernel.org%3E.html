nfsd stable backports: fix layout stid leak on setlease failure and write-verifier rotation on deferred writeback errors

Summary

nfsd 6.1.y stable series: two bug fixes from Mason/Layton, queued by Levin

This week's thread is a short, clean stable-tree backport rather than a feature or protocol discussion. On July 3, Chuck Lever posted a two-patch series targeting the 6.1.y maintenance branch, both Cc: stable@vger.kernel.org, and on July 4 Sasha Levin confirmed it was queued. The series is notable for two reasons: it fixes two distinct nfsd bugs (one in pNFS layout stateid teardown, one in the UNSTABLE/COMMIT durability contract), and both patches carry Assisted-by tags crediting Claude models, with Jeff Layton reviewing or co-authoring.

Patch 1/2 — release layout stid on setlease failure

The first patch, authored by Chris Mason and reviewed by Jeff Layton, backports upstream commit 30d55c8aabb2 ("nfsd: release layout stid on setlease failure") to 6.1.y. It is a classic use-after-free / dangling-pointer bug in the pNFS layout-recall path introduced by c5c707f96fc9 ("nfsd: implement pNFS layout recalls").

Mason's description walks through the race precisely:

"nfs4_alloc_stid() publishes the new stid into cl->cl_stateids via idr_alloc_cyclic() under cl_lock before returning to nfsd4_alloc_layout_stateid(). When nfsd4_layout_setlease() then fails, the error path frees the layout stateid directly with kmem_cache_free() without ever calling idr_remove(), leaving the IDR slot pointing at freed slab memory. Any subsequent IDR walker (states_show, client teardown) dereferences the dangling pointer."

The fix is to route the failure path through the proper teardown helper:

"The correct teardown for an IDR-published stid is nfs4_put_stid(), which removes the IDR slot under cl_lock, dispatches sc_free (nfsd4_free_layout_stateid) to release ls->ls_file via nfsd4_close_layout(), and drops the nfs4_file reference in its tail."

A second, subtler issue blocked a naive switch to nfs4_put_stid():

"A second issue blocks that switch: nfsd4_free_layout_stateid() unconditionally inspects ls->ls_fence_work via delayed_work_pending() under ls_lock, but INIT_DELAYED_WORK(&ls->ls_fence_work, ...) currently runs only after the setlease call. On the setlease-failure path the destructor would touch an uninitialized delayed_work."

Mason's fix hoists the ls_fenced / ls_fence_delay / INIT_DELAYED_WORK initialization above the nfsd4_layout_setlease() call and replaces the manual nfsd_file_put + put_nfs4_file + kmem_cache_free cleanup with a single nfs4_put_stid(stp). Lever's 6.1.y adaptation is minimal:

"[ cel: no ls_fence_work in 6.1.y; dropped INIT_DELAYED_WORK hunk ]"

The resulting diff touches only fs/nfsd/nfs4layouts.c (1 insertion, 3 deletions). The patch carries Assisted-by: kres (claude-opus-4-7) alongside the human sign-offs from Mason, Layton, and Lever.

Patch 2/2 — reset write verifier on deferred writeback errors

The second patch, authored by Jeff Layton with a Reported-by from Chris Mason, backports upstream commit 2090b05803fa ("nfsd: reset write verifier on deferred writeback errors") to 6.1.y, fixing a regression introduced by 555dbf1a9aac ("nfsd: Replace use of rwsem with errseq_t"). This one is arguably the more dangerous of the two because it silently violates the NFSv3/v4 durability contract rather than just corrupting server memory.

Layton's description:

"nfsd_vfs_write() and nfsd_commit() both call filemap_check_wb_err() to detect deferred writeback errors, but neither rotates the server's write verifier (nn->writeverf) when this check fails. Every other durable-storage-failure path in these functions calls commit_reset_write_verifier() before returning an error."

The consequence is a data-loss scenario:

"The missing rotation means clients holding UNSTABLE write data under the current verifier will COMMIT, receive the unchanged verifier back, and conclude their data is durable — silently dropping data that failed writeback. This violates the UNSTABLE+COMMIT durability contract (RFC 1813 §3.3.7, RFC 8881 §18.32)."

The fix adds commit_reset_write_verifier() calls at both filemap_check_wb_err() error sites:

"Add commit_reset_write_verifier() calls at both filemap_check_wb_err() error sites, matching the pattern used by adjacent error paths in the same functions. The helper already filters -EAGAIN and -ESTALE internally, so the calls are unconditionally safe."

Lever's 6.1.y adaptation open-codes the reset because the helper landed later:

"[ cel: open-code the reset; commit_reset_write_verifier() is v6.7 ]"

The diff touches fs/nfsd/vfs.c (8 insertions, 1 deletion). This patch carries Assisted-by: kres:claude-opus-4-6.

Resolution

The thread closed quickly with no technical pushback. Sasha Levin's reply on July 4 was a one-liner:

"Queued the series for 6.1.y, thanks!"

Takeaways

  • Classification: Both patches are bug fixes (not new features or protocol changes), backported to the long-lived 6.1.y stable tree with Fixes: tags pointing at upstream commits.
  • NFS client relevance: Although these are server-side (nfsd) fixes, both directly affect what NFS clients observe. The first prevents a server crash / UAF when pNFS layout recalls fail mid-setup; the second restores the UNSTABLE+COMMIT durability guarantee that NFSv3/v4 clients rely on to know their writes actually hit stable storage.
  • Process note: Both patches carry Assisted-by tags for Claude models (claude-opus-4-7 and claude-opus-4-6 respectively), a continuing pattern of AI-assisted kernel development being explicitly credited in the commit trailers, with human review (Layton) and sign-off (Mason/Lever) still gating acceptance.
