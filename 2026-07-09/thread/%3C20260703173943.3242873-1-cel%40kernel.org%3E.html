NFSD: RFC patch fixes lock owner use-after-free on client teardown

Summary

NFSD: Prevent lock owner use-after-free during client teardown

Classification: Bug fix (memory-safety / use-after-free in the NFSv4 server state code)

What happened this week

The thread consists of a single message this week: an RFC patch posted by Chuck Lever on 2026-07-03, NFSD: Prevent lock owner use-after-free during client teardown. No replies have landed in the window yet, so the discussion is at its opening stage — a proposed fix awaiting review.

The bug

The patch addresses a use-after-free (UAF) in __destroy_client() in fs/nfsd/nfs4state.c. As Lever describes it:

"After __destroy_client() releases a client's open owners, a lock owner whose only remaining reference is a blocked lock (nbl) is left on cl_ownerstr_hashtbl. client_has_state() does not account for a bare lock owner, so DESTROY_CLIENTID can reach __destroy_client() with these lock owners still present."

The dangerous sequence: __destroy_client() walks cl_ownerstr_hashtbl and calls remove_blocked_locks() on each lock owner without holding a reference. Meanwhile, the per-net "laundromat" thread independently reaps timed-out blocked locks from nn->blocked_locks_lru. The two paths only serialize on blocked_locks_lock for the list splice — not for the lock owner's lifetime.

"The laundromat can therefore free the lock owner while __destroy_client() is about to dereference it, and the freed, zeroed slab object produces a NULL dereference in remove_blocked_locks()."

The fix

Lever notes that the analogous path nfsd4_release_lockowner() already handles this correctly:

"nfsd4_release_lockowner() holds a reference across the same call; __destroy_client() does not."

The patch (13 insertions, 3 deletions in fs/nfsd/nfs4state.c) makes __destroy_client() follow suit: hold cl_lock across the walk, take a reference and unhash each lock owner before dropping the lock, so the laundromat cannot free the owner underneath the loop. The lock is released before calling remove_blocked_locks() and nfs4_put_stateowner(), which take blocked_locks_lock and cl_lock respectively (avoiding a deadlock).

Provenance

Outlook

Marked as RFC, the patch is early in review. The race window it closes — between the laundromat's independent reaping and the client-teardown walk — is subtle, so expect scrutiny on the lock-ordering argument (cl_lock vs. blocked_locks_lock) from other NFS maintainers in the coming days.
