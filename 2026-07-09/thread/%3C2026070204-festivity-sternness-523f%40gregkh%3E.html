nfsd write-verifier data-loss fix backported to 5.10.y stable

Summary

This week's single message in this thread is a stable-tree backport of the NFS server (nfsd) silent-data-loss fix that was reviewed and applied to nfsd-testing back in late May. Chuck Lever posted the 5.10.y backport on July 3, replying to Greg Kroah-Hartman's stable queue request (thread root <2026070204-festivity-sternness-523f@gregkh>).

Classification

  • Type: Bug fix — a protocol-contract violation in the NFS server that produces silent data loss on NFS clients. Not a new feature or wire-protocol change.
  • Subtree: fs/nfsd/vfs.c (nfsd), but the affected contract is one clients depend on for UNSTABLE write + COMMIT semantics, so client-visible behavior changes from "silently lose data" to "receive a rotated verifier and learn the commit failed."
  • Severity: High. The failure mode was silent data loss — among the worst classes of storage bug because there is no error signal to alert applications or operators.

Bridging prior weeks (brief)

The original fix was posted by Jeff Layton on May 22 in the mainline thread, reviewed and applied to nfsd-testing the same day (commit f8cf3c1c418ef04947bc16e4a2ef8074452de593). A companion fix for the async COPY path followed from Chuck Lever in the same week. The bug was reported by Chris Mason (Meta) and credited via Reported-by: in the patch.

This week's discussion

The message is a self-contained backport with no follow-on replies in this window. Chuck Lever's cover note explains the one adaptation needed for the 5.10.y tree:

"[ cel: open-code the reset; commit_reset_write_verifier() is v6.7 ]"

This means the commit_reset_write_verifier() helper that exists in mainline (introduced in v6.7) is not available in the 5.10.y stable tree, so Lever inlined the equivalent logic directly at both error sites. The patch touches fs/nfsd/vfs.c with 8 insertions and 1 deletion.

Technical detail (carried from the original fix)

The bug: nfsd_vfs_write() and nfsd_commit() both call filemap_check_wb_err() to detect deferred writeback errors, but neither rotates the server's write verifier (nn->writeverf) when this check fails. Every other durable-storage-failure path in these functions calls commit_reset_write_verifier() before returning an error.

The consequence, as Layton originally spelled out:

"The missing rotation means clients holding UNSTABLE write data under the current verifier will COMMIT, receive the unchanged verifier back, and conclude their data is durable — silently dropping data that failed writeback. This violates the UNSTABLE+COMMIT durability contract (RFC 1813 §3.3.7, RFC 8881 §18.32)."

The fix adds verifier-rotation calls at both filemap_check_wb_err() error sites, matching the pattern already used by adjacent error paths. Lever notes a safety property:

"The helper already filters -EAGAIN and -ESTALE internally, so the calls are unconditionally safe."
