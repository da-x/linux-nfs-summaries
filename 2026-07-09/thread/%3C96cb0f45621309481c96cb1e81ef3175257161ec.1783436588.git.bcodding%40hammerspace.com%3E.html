NFS: Fix writeback accounting inflation when folios are split into multiple requests

Summary

NFS: Charge unstable writes by request size, not folio size

Status: New patch posted (no replies yet this week) Type: Bug fix (memory/dirty-page accounting), targeted for stable trees Author: Benjamin Coddington (Hammerspace)

What happened this week

The thread opened — and as of the end of the window, still stands alone — with a single patch from Benjamin Coddington on July 7, sent to linux-nfs and cc'd to stable. There is no prior-week history for this thread; it began with this posting.

The bug: writeback accounting inflated by a factor of N

The patch targets a subtle but potentially severe accounting defect in the NFS client's unstable-write path. Coddington explains the mechanics clearly:

"nfs_folio_mark_unstable() and nfs_folio_clear_commit() charge and uncharge NR_WRITEBACK/WB_WRITEBACK by folio_nr_pages(folio) once per request added to or removed from a commit list. This is correct only when a folio has a single associated request."

The problem emerges whenever the client splits one large folio into multiple sub-folio write requests — which happens routinely in two scenarios:

  1. pNFS FlexFiles striping with a stripe unit smaller than the folio size, and
  2. plain wsize-limited splitting of buffered writes.

In both cases, each of the N resulting requests independently charges the entire folio's page count into the global writeback counters:

"each of the N requests independently charges the whole folio's page count, inflating the accounting by a factor of N per folio."

Why it matters: system-wide hard throttling

The consequence is not merely a cosmetic counter error. With large folios (up to 2 MiB on modern systems) and small stripe units, the inflation reaches "multiple orders of magnitude":

"a 2 MiB folio split into 512 4 KiB requests can charge up to 512x its real size, pushing global dirty+writeback accounting past the system's dirty threshold and forcing every buffered writer on the host into the hard-throttle path, including unrelated in-kernel NFS server threads sharing the box."

In other words, a single NFS client workload with FlexFiles striping can throttle all buffered writers on the machine — including an unrelated in-kernel NFS server (nfsd) — because the global dirty+writeback accounting is driven past dirty_ratio/dirty_background_ratio by phantom pages.

The fix

The remedy, as Coddington summarizes, is straightforward: "Charge each request only for the pages it actually covers." The patch touches three files — fs/nfs/internal.h, fs/nfs/pnfs_nfs.c, and fs/nfs/write.c (16 insertions, 12 deletions) — to make the charge/uncharge calls use the per-request byte/page span rather than the whole folio's page count.

Provenance and regression window

The bug was introduced by the folio conversion of buffered writes:

"Fixes: 0c493b5cf16e ("NFS: Convert buffered writes to use folios")"

That commit landed in the v5.17 cycle (2022), so this is a long-standing latent bug that only becomes acute once large folios and pNFS FlexFiles striping combine on the same workload. The Cc: stable tag indicates Coddington considers it suitable for backport to maintained stable trees.

Notably, the patch carries an "Assisted-By: Claude Sonnet 5" trailer — a first for linux-nfs in this dataset, and worth watching as AI-assisted kernel development becomes more visible on the list.

Where things stand

As of the close of the week (2026-07-10), the patch has no replies, reviews, or acks yet. Given its Fixes tag and stable cc, expect it to be picked up in the next merge window or a stable update if reviewers are satisfied. The discussion remains open for review comments in the coming days.

Key takeaways

  • Bug class: accounting error (over-charging writeback pages), not a data-corruption or protocol issue.
  • Trigger conditions: large folios + pNFS FlexFiles small stripe units, or wsize-limited splitting of large writes.
  • Impact scope: system-wide dirty-throttling, affecting unrelated writers including in-kernel nfsd.
  • Fix: per-request page accounting instead of per-folio; small, targeted diff across three files.
  • Regression origin: the 2022 folio conversion (commit 0c493b5cf16e).
