NFS Direct I/O folio debate: path forward agreed — expose get_contig_folio_len()

Summary

NFS Direct I/O Folio Debate: Path Forward Agreed on get_contig_folio_len()

Classification

This week's activity is a continuation of the review discussion around patch 6/7 ("Optimize direct I/O to use folios for requests") in Pranjal Shrivastava's (Google) seven-patch series "nfs: Modernize Direct I/O path". The series is an architectural refactor of the NFS client O_DIRECT path — migrating from the legacy iov_iter_get_pages_alloc2() API to the modern iov_iter_extract_pages() API and making requests folio-based — with two embedded bug fixes (a data-corruption fix in nfs_direct_extract_pages() and an early-unpin / bytes-accounting defect). It is groundwork for PCI Peer-to-Peer DMA (P2PDMA), not a protocol change.

Bridge from prior weeks

The central dispute, opened when the v2 series was posted on June 16, concerns whether patch 6's assumption — that every page returned by iov_iter_extract_pages() belongs to a valid folio so page_folio() is safe — holds across all memory types. Trond Myklebust, Christoph Hellwig, and Matthew Wilcox pushed back, noting the MM invariant "every page is part of a folio" has important exceptions (slab, vmalloc, iomem). Last week (week ending 2026-07-02), Hellwig de-escalated the immediate concern for NFS specifically — GUP-pinned user pages are always valid folios, so the slab/vmalloc edge cases Wilcox flagged are not reachable through the direct-I/O user pinning mechanism. However, Hellwig's caveat about kvec iterators kept a latent architectural gap alive:

"Also if iov_iter_extract_bvecs was used on kvec or bvec iters we could run into the slab problem. The block usage currently makes sure bvec iters are not handed to iov_iter_extract_bvecs, but there is no such thing for kvec vectors, although no one is using them for direct I/O right now. Not that I'd want to rely on that in the long run."

This week: four messages (July 3–8)

The discussion this week moves from diagnosis to prescription. The author and Hellwig converge on a concrete plan for resolving the page_folio() impasse.

July 3 — Pranjal confirms the bvec path shares the same latent risk

Pranjal replies to Hellwig's previous-week clarification, adding a "+1" and sharpening his earlier observation that the block layer's own iov_iter_extract_bvecs() path has the same exposure:

"I see that extract_bvecs also rely on user memory to have valid folios even if we were to re-use parts of it (get_contig_folio_len) it still relies on page_folio() as detailed in the other reply."

He then probes the kvec-iterator caveat with a practical question:

"Do we have use-cases for a kernel user for direct I/O ? (Just curious to know if there's something on the horizon)."

This is a pointed way of asking whether the latent fragility Hellwig flagged is merely theoretical or whether it represents a real, near-term threat that should influence how the NFS patch is structured.

July 3 — Hellwig: kernel-side direct I/O is not hypothetical

Hellwig answers within an hour, making clear the kvec concern is not academic:

"Plenty. Basically any storage on file driver, or storage / file system server: loop, zloop, nvmet, scsi target and nfsd ar the ones I know off by head."

This is a significant data point for the broader discussion. It means the "no one uses kvec iterators for direct I/O" convention Hellwig did not want to rely on is already broken in spirit — nfsd itself (the NFS server) is a kernel-side user of direct I/O, as are loop, zloop, nvmet, and SCSI target. The iov_iter/block-layer gap is therefore not a hypothetical future risk but a present one, even if no current code path triggers the slab assertion.

July 7 — Pranjal proposes two concrete paths forward

After acknowledging Hellwig's list of kernel-side users ("Ack. I see! Thanks!"), Pranjal pivots to asking for a decision on the technical resolution:

"Regarding the page_folio impasse, how do you suggest we proceed? Should I expose and use get_contig_folio_len() from bvec? Or should I move the NFS helper into the iov_iter lib? (or both)."

He also asks a process question about series structure:

"Also, do you suggest sending the Folio move as a standalone patch if it is blocking the rest of the series or do we prefer keeping these in a single series?"

This is a constructive de-escalation. Rather than continuing to argue about whether the page_folio() assumption is safe (a question that has been thoroughly litigated over three weeks), Pranjal is asking Hellwig to pick a concrete implementation path so he can post a v3. The two options he presents are:

  1. Expose get_contig_folio_len() from the block layer and have NFS call it directly — reusing existing, battle-tested code without changing any library APIs.
  2. Move the NFS folio-grouping helper into lib/iov_iter.c — a larger API change that would shield all filesystems from having to reason about folio semantics, addressing the broader architectural concern Wilcox raised.

July 8 — Hellwig endorses option 1 and suggests splitting the series

Hellwig responds with a clear endorsement of the first approach:

"Sounds like the best way forward for now."

This is a meaningful resolution. After three weeks of debate about whether page_folio() is safe, the maintainers have converged on a pragmatic answer: NFS should reuse the block layer's get_contig_folio_len() helper rather than hand-rolling its own folio grouping or relying on the "every page is a folio" invariant. The "for now" qualifier is important — it leaves open the possibility of a longer-term iov_iter API change (option 2) but defers that decision to a future discussion, unblocking the immediate series.

On the process question, Hellwig admits he did not fully parse the terminology:

"Sorry if I'm thick, but I'm not sure what 'folio' move means."

But he offers clear guidance on the underlying question (whether to split the series):

"In doubt if you think you can get a series merged quicker without a later part I'd split it."

This is a merge-oriented signal: Hellwig prefers getting the uncontroversial parts of the series (the API migration, the two bug fixes, the pin-aware infrastructure) landed rather than holding them hostage to the folio-grouping patch. If patch 6's refactoring to use get_contig_folio_len() introduces cross-subsystem dependencies (e.g., exporting a block-layer function), splitting it out as a standalone prerequisite patch would let the rest of the series proceed independently.

Key technical arguments this week

  1. The bvec extractor shares the same latent risk. Pranjal's "+1" and his observation that get_contig_folio_len() "still relies on page_folio()" confirm that the block layer's own extraction path is not immune to the slab/vmalloc concern — it simply works in practice because GUP-pinned user pages are always valid folios. This validates the reviewers' original guidance ("stick to what the block code does") while acknowledging the underlying fragility.

  2. Kernel-side direct I/O is a real, present use case. Hellwig's list (loop, zloop, nvmet, scsi target, nfsd) elevates the kvec-iterator concern from theoretical to practical. The "no one uses them" convention is not a reliable long-term invariant, which strengthens the case for eventually hardening the iov_iter abstraction — but does not block the immediate NFS fix.

  3. get_contig_folio_len() is the agreed-upon path forward. After three weeks of debate, the maintainers have settled on reusing the block layer's helper rather than either (a) relying on the page_folio() invariant or (b) making a larger iov_iter API change. This is a pragmatic, minimal-diff resolution that unblocks the series.

  4. Series splitting is endorsed. Hellwig's "I'd split it" guidance suggests the folio-grouping patch (or the prerequisite of exporting get_contig_folio_len()) may be sent as a standalone patch, with the rest of the modernization series proceeding independently. This is a common kernel development pattern for reducing review burden and enabling incremental merge.

Evolution of the discussion (three-week arc)

  • Week 1 (June 16–18): Series posted; Trond Myklebust, Hellwig, and Wilcox push back on the page_folio() assumption. Reviewers advise reusing block-layer code.
  • Week 2 (June 19–25): Author accepts the critique but surfaces a wrinkle: the bvec extractor has the same risk. Asks whether iov_iter should export a safe helper. Hellwig de-escalates for NFS specifically (GUP-pinned pages are safe) but flags the kvec gap.
  • Week 3 (July 3–8, this week): Author and Hellwig converge on a concrete plan: expose and use get_contig_folio_len(). Kernel-side direct I/O confirmed as a real use case. Series splitting endorsed to unblock merge.

Final conclusions and where things stand

The central technical dispute over patch 6 is now effectively resolved. The agreed path forward is for Pranjal to refactor the NFS folio-grouping logic to call get_contig_folio_len() from the block layer, rather than hand-rolling folio grouping or relying on the page_folio() invariant. Hellwig's "Sounds like the best way forward for now" is a clear endorsement that unblocks the author to post a v3.

The broader architectural question — whether lib/iov_iter.c should eventually export a safe helper (or hide folio semantics entirely) from all filesystems — remains open but is explicitly deferred ("for now"). Hellwig's confirmation that kernel-side direct I/O users exist (loop, zloop, nvmet, scsi target, nfsd) keeps this question relevant for future work.

No new patches have been posted this week. The expectation is that Pranjal will post a v3 incorporating:

  • Refactored patch 6 using get_contig_folio_len() (possibly as a standalone prerequisite patch).
  • Updated CC lists (linux-rdma, linux-pci) as agreed in the prior week.
  • Full xfstests quick-suite results in the cover letter.

The thread remains open pending that v3 posting and subsequent review.
