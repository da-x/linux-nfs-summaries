sunrpc pool_mode v5: hardcode pernode + empty-pool fixes applied to nfsd-testing; sv_nrpools accessor debate winds down

Summary

sunrpc pool_mode v5: the series lands in nfsd-testing, with a brief interface-design coda

Type: Server-side bug fix + cleanup in the sunrpc (NFS server) layer. This is not an NFS client feature or a wire-protocol change — it concerns how nfsd schedules RPC work across NUMA pools on the server. But the reliability stakes for any client talking to a multi-NUMA NFS server are concrete, and they're the reason this series has drawn attention all summer.

Bridging prior weeks (brief)

This is the fifth revision of a series that has been running since mid-June. The core problem was flagged early by Chuck Lever: when nrservs < number of NUMA nodes, trailing pools end up with zero threads, and because each thread services only its own pool, a transport enqueued on an empty pool hangs indefinitely. The v4 review round closed out last week with NeilBrown's Reviewed-by on all four patches, the Fixes: tag settled on bfd241600a3b, and two open items carried into v5: add a tracepoint/comment for the "no pool has any threads" fallback path, and (per NeilBrown's standing suggestion) eliminate the redundant serv.sv_nrpools field.

This week's activity (July 3–9)

The v5 series is posted (July 6)

Jeff Layton posted v5 as a five-patch set, expanding the prior four by splitting off the sv_nrpools elimination. In the cover letter he framed what was new:

"This has a few small fixes and comment cleanups and also implements Neil's suggestion to remove serv.sv_nrpools."

He called out that patches #1 and #3 "address what is a shortcoming of the existing code -- namely that the server can be configured to schedule RPCs to pools with no threads in them," and noted the last two patches carry the side benefit of "getting the modulus out of the svc_pool_for_cpu() hotpath."

The five patches, in order:

  1. route to a populated pool in svc_pool_for_cpu() — the actual bug fix. Layton describes the failure precisely: "a transport that lands on a threadless pool is enqueued on sp_xprts and never picked up: the connection hangs indefinitely." The fix makes svc_pool_for_cpu() skip empty pools, "trading NUMA locality for a guarantee that the work is actually serviced." Tagged Fixes: bfd241600a3b ("[PATCH] knfsd: make rpc threads pools numa aware").
  2. hardcode pool_mode to pernode, remove other modes — the behavioral change. Layton's rationale: "Today, pernode is the right choice everywhere." On single-node hosts it "degenerates to exactly one pool, identical to the old 'global' mode," while on multi-NUMA hosts it gives proper thread affinity and NUMA-local allocation. The SVC_POOL_AUTO/GLOBAL/PERCPU/PERNODE enum, the mode-selection heuristic, and all mode-based switch statements are removed. The module parameter and netlink interfaces are preserved for backward compatibility — "Writing any of the four documented mode names still succeeds silently," reading always returns "pernode", and a deprecation notice is emitted.
  3. guarantee a thread per pool when auto-distributing — the belt-and-braces companion to patch 1: "Floor each pool at one thread when auto-distributing a non-zero count, so no pool is left empty." Carries NeilBrown's Reviewed-by.
  4. tear down pool counters before dropping the pool map reference — a latent-leak fix that only becomes live once sv_nrpools is gone. Layton explains: "a derived loop bound would read as zero for the last pooled service and skip svc_pool_destroy_counters() entirely, leaking the percpu counters." Reordering makes it safe; "No functional change."
  5. derive the pool count instead of caching it in sv_nrpools — NeilBrown's long-requested simplification, now implemented via a new svc_serv_nrpools() accessor. Layton argues the field "carries no unique information" relative to sv_is_pooled, and that "Doing this also removes a modulus operation from svc_pool_for_cpu(), which should make for more efficient RPC queueing."

Chuck applies the series (July 6)

Chuck Lever's reply is the headline of the week — terse and decisive:

"Applied to nfsd-testing, thanks!"

He lists all five commit hashes, confirming the full set landed in the NFS testing tree on the same day it was posted. After a month-and-a-half of review across five revisions, the series is in.

NeilBrown reviews patch 5/5 and raises two nits (July 6)

NeilBrown's reply to the final patch is approving but flags two details:

"I would make this a static-inline."

And on an if condition in the new code:

"The values stored in svc_pool_map.to_pool are all less than svc_pool_map.npools. So that if() condition cannot be true."

He then explicitly scoped both as non-blocking and signed off:

"But those two things don't reduce the correctness of the patch. Reviewed-by: NeilBrown neil@brown.name. Thanks for doing this."

The interface-design debate (July 6–8)

Layton's immediate reply accepted the dead-if point ("Ahh good point. I guess we can remove that if statement. I can send Chuck a follow-on patch") but pushed back on making it static-inline, because svc_pool_map is file-local to svc.c:

"That would mean that we would have to export svc_pool_map, which is currently private to svc.c."

NeilBrown pressed the point on July 8, questioning why exporting the struct was worse than exporting the accessor:

"Why is exporting svc_pool_map more problematic than exporting svc_serv_nrpools? I think it would be good for at least the code in svc_pool_for_cpu() to inline the function."

Layton drew a firm line on module-boundary hygiene:

"Doing what you suggest would increase the interface 'surface' between sunrpc.ko and nfsd.ko... Why expose so many internal details to other modules when all we need is this one accessor? I think keeping this interface small is preferable."

NeilBrown conceded gracefully on July 8, striking the classic kernel-reviewing balance between abstract and concrete cost:

"In general, yes. But it is not without cost... Interface size has an abstract value. Code size can have concrete value. Comparing them is subjective I guess. I have no concrete evidence that there is a problem, so I'll stop objecting."

Layton closed the exchange with a door left ajar for future evidence:

"Your point is certainly valid, and this is a hot path. If we can demonstrate that this matters, then I'd be happy to revisit the idea. I don't have the cycles to do so at the moment though."

Key technical arguments & evolution

  1. The series is merged into nfsd-testing. After five revisions and a month-plus of review, Chuck Lever applied all five patches on July 6. This is the decisive event of the week — the long-running debate has resolved in favor of the code.
  2. Two complementary fixes for the empty-pool hang. Patch 1/5 is the reactive safety net (route to a populated pool if the chosen one is empty); patch 3/5 is the proactive prevention (floor each auto-distributed pool at one thread). Together they guarantee "the work is actually serviced" rather than leaving a client's transport stranded on a threadless pool.
  3. The sv_nrpools elimination finally landed — NeilBrown's standing suggestion from the v4 round, now realized as the svc_serv_nrpools() accessor with the side benefit of removing a modulus from the svc_pool_for_cpu() hot path.
  4. A module-boundary principle settled the last open question. The static-inline debate ended not on performance grounds (NeilBrown had no concrete evidence of a problem) but on interface hygiene: Layton preferred keeping struct svc_pool_map private to sunrpc.ko over exposing it to nfsd.ko. The dead-if nit is accepted and will be cleaned up in a follow-on patch to Chuck.

Relevance to NFS client development

While this is server-side sunrpc code, the consequences for clients are direct:

  • The starvation fix (patch 1/5) eliminates indefinite connection hangs. A client connecting to an NFS server with fewer nfsd threads than NUMA nodes — or one misconfigured with zero threads on some pools — would previously have its transport enqueued on an empty pool and hang forever. The populated-pool fallback ensures the work is serviced, at worst paying a cross-NUMA latency penalty rather than stalling.
  • The pernode default (patch 2/5) changes NUMA behavior for all NFS servers. Services that previously ran with a single global pool now get one pool per NUMA node by default, improving thread affinity and NUMA-local memory allocation — a latency win for clients on multi-NUMA hosts.
  • The modulus elimination (patch 5/5) tightens the enqueue path on busy servers handling many concurrent client connections.

Final status (as of window close)

The v5 series is applied to nfsd-testing with all five patches carrying review sign-off. The only remaining item is mechanical: Layton will send Chuck a small follow-on patch to remove the dead if condition in patch 5/5 that NeilBrown flagged. The static-inline question is parked — Layton is willing to revisit it "if we can demonstrate that this matters," but has no cycles to benchmark it now. No new patches or objections appeared after July 8; the thread is effectively concluded pending that cleanup.
