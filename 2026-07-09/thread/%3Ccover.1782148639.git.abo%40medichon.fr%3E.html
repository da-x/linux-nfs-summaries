pNFS clear_and_wake_up_bit refactor: maintainer-semantic helper debate

Summary

pNFS clear_and_wake_up_bit() refactor: the case of the semantic helper

Context (bridging from last week)

Last week, Arnaud Bonnet posted a two-patch series refactoring flag-handling code in the NFS and pNFS clients to use the core-kernel clear_and_wake_up_bit() helper instead of hand-rolled clear_bit_unlock(); smp_mb__after_atomic(); wake_up_bit(); sequences. The work is a cleanup/refactor — no new feature, no protocol change, no behavioral fix intended; it consolidates an atomic bitops idiom onto an existing helper (introduced by commit 8236b0ae31c8) and deletes the now-redundant local wrappers. The series was credited with Suggested-by: Agatha Isabelle Moreira, tying it to the KernelNewbies beginner-cleanup task list. As of the end of last week's window, no reviewer had yet replied on-list.

This week's activity

The thread finally got its first substantive exchange this week — a two-message back-and-forth between the Suggested-by mentor and the patch author, both focused on PATCH 2/2, the pNFS half of the series that touches fs/nfs/pnfs.c.

Agatha Isabelle Moreira's review (July 3)

Agatha Isabelle Moreira — the mentor who originally suggested the task — replied to Bonnet's patch with a positive but cautious review. She confirmed the mechanical side:

"Other than that, both patches appear to successfuly apply and compile just fine."

But she raised one substantive concern about the design of the refactor itself. The pNFS patch removes local helper functions whose bodies are exactly clear_and_wake_up_bit(), but those helpers also carry subsystem-specific naming:

"my only concern here is that the maintainer could find the replaced function pnfs_clear_first_layoutget() preferable to be kept, since it carries some subsystem semantics (the struct pnfs_layout_hdr *lo argument and the NFS_LAYOUT_FIRST_LAYOUTGET bit). But I could also be completely wrong."

She elaborated on a maintainability argument — that keeping the semantic wrapper would localize future changes:

"In the event that NFS_LAYOUT_FIRST_LAYOUTGET gets replaced by another constant in the future (IDK if this is a plausible possibility), by keeping the original function there would be only a single place to touch."

She explicitly flagged her own uncertainty and asked for subsystem expertise to adjudicate:

"I think some input from someone in the nfs subsystem would be highly appreciated to confirm the correctness of this refactor."

"Let's hope this message attracts more comments from someone with the subsystem's expertise, which would be highly appreciated."

Arnaud Bonnet's response (July 8)

Arnaud Bonnet replied five days later, acknowledging the concern but defending the current approach on the grounds of in-tree precedent:

"Hi Agatha, I agree this required consideration when doing the change, however there is prior art with the use of clear_and_wake_up_bit and it is pretty universally done as an open coded call."

He offered a concrete fallback if the maintainer disagrees with his judgment:

"If this is not desirable, I could resubmit (probably as a single patch) by only replacing the sequence in the helpers."

To further support his position, he cited two prior commits by NFS maintainer Trond Myklebust that touched similar code paths, noting an important nuance about why they kept their wrappers:

"Some similar changes by Trond are f46f84931a0aa ("NFSv4/pNFS: Don't call _nfs4_pnfs_v3_ds_connect multiple times") and 43d20e80e2880 ("NFS: Fix a few more clear_bit() instances that need release semantics") and these keep the helpers, although in those cases the functions do more than just call clear_and_wake_up_bit."

He closed with thanks for the review.

Technical arguments at stake

The core debate is a classic kernel-style trade-off between uniformity and subsystem semantic encapsulation:

  • Bonnet's position (uniformity): The rest of the kernel has converged on calling clear_and_wake_up_bit() directly at the call site; NFS should follow suit. When a local helper is nothing but a one-line wrapper around the global helper, deleting it reduces indirection and code size (the patch is a net -15 lines in pnfs.c).
  • Moreira's position (semantic encapsulation): The pNFS helpers are not purely mechanical — their names encode which layout flag is being cleared (FIRST_LAYOUTGET) and on which object (struct pnfs_layout_hdr *lo). Keeping them gives a single choke point if the flag constant or its semantics ever change.

Bonnet's rebuttal is notable in that he distinguishes his case from Trond's prior commits: those kept their helpers because the helpers do more than call clear_and_wake_up_bit(); here, the helpers are pure pass-throughs, so deleting them loses no logic — only naming.

Status at end of window

No NFS maintainer (Trond Myklebust or Anna Schumaker) has yet weighed in on-list within this week's window. The thread is effectively awaiting maintainer adjudication on whether to:

  1. merge the series as-is (deleting the pNFS helpers), or
  2. have Bonnet resubmit a variant that keeps pnfs_clear_first_layoutget() and friends but replaces their bodies with the helper call.

Bonnet has pre-committed to option 2 if requested, so the patch is unlikely to be blocked long. The series remains a low-risk cleanup with no behavioral change; the open question is purely stylistic/maintainability.
