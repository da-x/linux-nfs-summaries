NFSv3 O_WRONLY|O_CREAT open can fail with EACCES after 6.12 atomic_open change

Summary

A short but pointed bug-report thread opened on the linux-nfs list this week, concerning a regression in NFSv3 client behavior around open(O_WRONLY|O_CREAT) on pre-existing files.

The report: a permission-denied surprise after upgrading to 6.12

Tian Lan of Jane Street opened the thread reporting that their applications began failing with EACCES after a kernel upgrade from 6.1 LTS to 6.12 LTS:

"We recently noticed there is a behavior change w.r.t opening a file with the O_WRONLY|O_CREAT flags over the NFSv3 protocol after upgrading the kernel from 6.1 LTS to 6.12 LTS. From the packets capturing, it seems like the kernel would now issue an additional CREATE rpc call to the remote NFS server regardless if the target file pre-exists or not."

The failure mode is subtle and worth spelling out: when the client only has write permission on the pre-existing file but no write permission on the containing directory, the extra CREATE RPC can return EACCES, causing the whole openat syscall to fail even though opening the existing file for writing should succeed. Tian traced the behavior change to commit 7c6c5249f061 ("NFS: add atomic_open for NFSv3 to handle O_TRUNC correctly."), and asked whether the new behavior was intentional, since it "breaks existing user's application code." They noted they currently work around it by stripping O_CREAT when opening a known pre-existing file for write, but would prefer not to.

The maintainer's response: this should not happen

Trond Myklebust, the Linux NFS client maintainer, replied the same day with a firm position that the observed behavior is not what the protocol requires:

"NFSv3 CREATE is supposed to ignore the directory permissions if the file already exists. That is required in order to support basic POSIX open(O_CREAT) behaviour."

He also pushed back on the framing that the old code was safe, noting that even the pre-atomic_open path — which did a LOOKUP before deciding whether to send CREATE — "had a potential for races that could have caused the client to send it against an existing file." In other words, the regression is not simply "the new code sends CREATE when the old code didn't"; rather, per Trond, a conforming server should tolerate a CREATE on an existing file without enforcing directory write permission.

Trond closed by asking which NFS server Tian was using — a diagnostic question that matters because the EACCES could be coming from a non-conformant server-side implementation of CREATE, not (only) from the client's new RPC pattern.

Where things stand

  • Classification: bug fix / regression investigation, triggered by a deliberate feature change (atomic_open for NFSv3 to handle O_TRUNC correctly).
  • Client-side takeaway: the 6.12 atomic_open path now issues CREATE unconditionally on O_CREAT opens; that is arguably more race-safe than the old LOOKUP-then-CREATE flow, but it relies on servers honoring the NFSv3 rule that directory permissions are ignored when the file already exists.
  • Open question: whether the reported EACCES originates from a non-conformant server (Trond's hypothesis) or from a client-side path that still enforces/propagates the error. The thread is waiting on Tian's answer about the server in use; no patch has been posted yet this week.
  • User impact: applications doing open(O_WRONLY|O_CREAT) on pre-existing files in directories where the user lacks write permission are affected on 6.12+ kernels until this is resolved or a client-side guard is added.

The discussion is fresh (both messages landed on 2026-07-06) and there is no prior-week history for this thread to bridge from.
