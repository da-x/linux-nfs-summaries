sunrpc: dead nrpools check in svc_pool_for_cpu() dropped, folded into pool_mode series

Summary

sunrpc: drop unneeded nrpools check in svc_pool_for_cpu()

Type: Server-side cleanup / micro-optimization in the sunrpc (NFS server) layer. Not a new feature or protocol change — this is a dead-code removal on the RPC enqueue hotpath, born out of review of the ongoing pool_mode series.

Bridging prior weeks (brief)

This two-message thread is a small offshoot of the larger sunrpc pool_mode v4 series that Jeff Layton has been driving since mid-June. That series reworks how nfsd schedules RPC work across NUMA pools, fixing a connection-starvation bug where a transport could be enqueued on an empty pool and hang indefinitely. The v4 round closed out last week with all four patches carrying NeilBrown's Reviewed-by, the Fixes: tag settled on bfd241600a3b, and a few small v5 tweaks (tracepoint + comment for the fallback path, cleaner thread-floor formulation) still pending. This thread is one of those leftover review nits — a redundant bounds check that NeilBrown flagged while reviewing the new pooled-routing code in svc_pool_for_cpu().

This week's activity (July 3–9)

The entire thread fits on July 8 and consists of a single patch and its immediate disposition. The pace is brisk: posted at 12:00 UTC, folded into the series and pushed to nfsd-testing by 12:58 UTC — under an hour from submission to tree.

Layton posts the one-liner cleanup (July 8)

Jeff Layton submitted a small patch removing a redundant nrpools bounds check from svc_pool_for_cpu() in net/sunrpc/svc.c. The justification is quoted directly from NeilBrown's review of the pool_mode series:

"The values stored in svc_pool_map.to_pool are all less than svc_pool_map.npools. So that if() condition cannot be true."

Layton framed it as a hotpath cleanup:

Drop the useless check from this hotpath.

The patch is tiny — 1 insertion, 4 deletions in net/sunrpc/svc.c — and carries a Suggested-by: tag for NeilBrown. Notably, Layton offered to let the maintainer absorb it rather than re-spin the whole series:

Chuck, feel free to fold this into 5/5 of the pool_mode series.

That's a pragmatic move on his part: the change is logically independent (it just removes dead code from a function the series is already touching), so folding it into patch 5/5 avoids bumping the revision number for a four-line diff.

Chuck Lever folds it in and pushes to nfsd-testing (July 8)

Chuck Lever's reply came back less than an hour later with a single line of substance:

Folded in to 5/5 and pushed out to nfsd-testing.

No review comments, no objections — just immediate acceptance and integration into the test tree. The fact that the NFS maintainer folded it without even posting a Reviewed-by or asking for a v2 is a signal of how uncontroversial the change is: it's removing a branch that provably never fires, on a function that's already being restructured by the pool_mode series.

Key technical arguments & evolution

  1. The check was provably dead. NeilBrown's observation during pool_mode review was decisive: svc_pool_map.to_pool[] is populated with values strictly less than svc_pool_map.npools, so any subsequent if (pool >= nrpools) guard can never be true. There was no debate on this point — Layton simply acknowledged it and posted the fix.

  2. Hotpath justification. The function svc_pool_for_cpu() sits on the RPC enqueue path, called for every incoming RPC connection to determine which per-CPU pool should handle the work. Removing even a single branch there reduces instruction count and cache pressure on one of the most frequently executed functions in nfsd. It's a micro-optimization, but on a hotpath with millions of calls per second on a busy NFS server, it's not nothing.

  3. Process note: fold-in vs. re-spin. Layton's suggestion to let Chuck "fold this into 5/5" rather than posting a v5 of the whole series is worth highlighting as good mailing-list practice. For a trivial, self-contained cleanup that touches a function already modified by the in-flight series, asking the maintainer to fold it in saves everyone a revision cycle and keeps the patch series diff stable for other reviewers.

Relevance to NFS client development

This is server-side code with no direct bearing on NFS client development — there's no protocol change, no new client feature, and no client-visible bug fix. However, the pool_mode series as a whole (of which this cleanup is a minor part) has indirect client-facing consequences:

  • Connection reliability on multi-NUMA servers. The broader pool_mode fix ensures that an NFS client connecting to a server with fewer nfsd threads than NUMA nodes will no longer have its transport enqueued on an empty pool and hang indefinitely. The work gets routed to a populated pool instead.
  • NUMA-local thread affinity. With per-node pools as the default, RPC processing is pinned to the NUMA node where the connection's socket lives, reducing cross-socket memory traffic and improving tail latency for clients on large multi-socket hosts.

This particular patch contributes marginally to that story by trimming a dead branch from the very function (svc_pool_for_cpu()) that makes the pool-routing decision.

Final status (as of window close)

The patch is merged into the nfsd-testing tree as part of patch 5/5 of the pool_mode series. The thread is closed — no further discussion expected. The broader pool_mode series remains in nfsd-testing pending the small v5 tweaks noted in last week's summary (tracepoint + comment for the fallback path, cleaner thread-floor formulation) before it heads to linux-next and eventually mainline.
