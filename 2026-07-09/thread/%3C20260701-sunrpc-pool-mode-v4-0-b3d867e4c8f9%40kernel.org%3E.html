sunrpc pool_mode v4: Fixes tag accepted, tracepoint promised, sv_nrpools debate winds down

Summary

sunrpc pool_mode v4: the review round closes out

Type: Server-side bug fix + cleanup in the sunrpc (NFS server) layer. Not an NFS client feature or protocol change — this concerns how nfsd schedules RPC work across NUMA pools on the server, but with direct reliability consequences for any client talking to a multi-NUMA NFS server.

Bridging prior weeks (brief)

The thread has been running since mid-June. v2 landed June 25 and v3 on June 29, both dominated by Chuck Lever's warning that with nrservs < number of NUMA nodes, trailing pools end up with zero threads and the enqueue path has no fallback — a connection landing on an empty pool would hang indefinitely. NeilBrown and Layton converged on a "belt-and-braces" plan: guarantee ≥1 thread per CPU-bearing node, honor explicit userland arrays as-is, and add a queueing-path fallback to a populated pool. v4 landed July 1 as a four-patch set, dropping the RCU patch from v3 and folding the pooled-service gate directly into patch 2/4. Last week's summary covered NeilBrown's rapid-fire review of all four patches (all Reviewed-by) and Layton's response pass, which ended with the Fixes: tag saga still open: both the original author (0f0257eaa5d2) and reviewer (3262c816a3d7) had the wrong commit, and Layton had just proposed bfd241600a3b ("knfsd: make rpc threads pools numa aware") after an LLM-assisted trace.

This week's activity (July 3–9)

Three messages this week, all closing out open items from last week's review round. The pace has slowed markedly — this is the tail of a review cycle rather than new debate.

NeilBrown accepts the Fixes: tag and presses on the fallback path (July 3)

NeilBrown replied to Layton's July 2 follow-up on patch 1/4, conceding the Fixes: correction:

That is certainly credible - thanks.

He then pushed back on Layton's plan to add only a tracepoint for the "no pool has any threads" fallback path, asking for more context in the code:

and a comment explaining when this might happen?

NeilBrown also raised a subtle edge case that neither of them had fully addressed — what happens if an admin explicitly requests zero threads on some pools:

The start-up window makes sense - as long as we start a thread on each pool it should be safe. But if we don't (if the admin request zero on some pools) we can still get stuck. Is there something simple we can do about that, or does the admin get to keep both halves?

On shutdown, he confirmed the ordering is fine: "And on shutdown the threads stop before the sockets are cleaned up - but they do get cleaned up, so all good."

NeilBrown pushes back on Layton's sv_nrpools performance argument (July 3)

In a reply to patch 2/4, NeilBrown accepted Layton's single-node counterexample (which showed sv_is_pooled can't be derived from sv_nrpools) but rejected the performance rationale for keeping the field:

Agree. We have to keep sv_is_pooled (it implies a reference to svc_pool_map). I'm not convinced that we need sv_nrpools.

On Layton's concern that converting sv_nrpools accesses to read from svc_pool_map would add cost on the receive path, NeilBrown argued the opposite:

svc_pool_map is a single global that is read-mostly, so no dereference, easy to predict. During receive we need to access svc_pool_map anyway to map CPU to POOL. So the svc_pool_map.npools will have to be pulled into cache anyway.

He then gracefully backed off: "But if you don't like it, I won't push it on you." This is a classic kernel-reviewing courtesy — NeilBrown made his case but explicitly left the decision to the author, signaling the simplification is a "nice to have" rather than a blocker.

Layton closes the loop (July 6)

Jeff Layton's reply on July 6 addressed NeilBrown's three points from the patch 1/4 thread:

On the tracepoint + comment request, he simply agreed: "Sure, I'll add one."

On the admin-requested-zero-threads edge case, Layton clarified that the fix already handles it — the tradeoff is performance, not correctness:

Well, no. This patch makes sure that RPCs are always routed to a pool with CPUs. They might end up doing cross-NUMA calls and performance might suck, but it shouldn't get stuck.

This is an important clarification for the record: the fallback path in svc_pool_for_cpu() doesn't just handle the transient startup/shutdown window — it's a general safety net that also covers misconfiguration (admin explicitly setting zero threads on some pools). The cost is cross-NUMA RPC dispatch, which hurts latency but never hangs.

On shutdown ordering, he confirmed: "Correct."

He closed with "Thanks again for the review," signaling the review round is complete.

Key technical arguments & evolution

  1. The Fixes: tag saga is finally settled. After three rounds (Layton's original 0f0257eaa5d2, NeilBrown's suggested 3262c816a3d7, Layton's corrected bfd241600a3b), NeilBrown accepted the final answer. The bug was introduced by the NUMA-awareness patch, not the initial pool-splitting patch. This matters for backporting: the fix needs to go into kernels containing bfd241600a3b.

  2. The fallback path is now explicitly a general safety net, not just a startup/shutdown workaround. NeilBrown's question about admin-requested zero threads forced Layton to clarify that the populated-pool routing in patch 1/4 covers all cases where a pool has no threads — transient (startup/shutdown) or persistent (misconfiguration). The guarantee is "it shouldn't get stuck," even if cross-NUMA performance suffers.

  3. The sv_nrpools simplification debate is effectively over, with NeilBrown conceding the point. NeilBrown made a reasonable case that svc_pool_map.npools would already be in cache during receive (since the CPU-to-pool mapping requires it anyway), but Layton's single-node counterexample was decisive. The field stays; the cleanup is deferred to a future patch if anyone wants to take it on.

  4. A tracepoint and explanatory comment are now promised for v5. NeilBrown's request for "a comment explaining when this might happen" plus Layton's agreement ("Sure, I'll add one") means the fallback path will be better documented in the next revision.

Relevance to NFS client development

While this is server-side sunrpc code, the stakes for clients remain concrete:

  • The starvation fix (patch 1/4) prevents indefinite connection hangs. A client connecting to an NFS server with fewer nfsd threads than NUMA nodes — or one misconfigured with zero threads on some pools — would previously have its transport enqueued on an empty pool and hang forever. With this fix, the work is routed to a populated pool. This is a direct reliability improvement for any client talking to a multi-NUMA NFS server.
  • The pernode default (patch 2/4) alters NUMA behavior for all NFS servers. Services that previously ran with a single global pool now get one pool per NUMA node by default, giving proper thread affinity and NUMA-local memory allocation. Clients on multi-NUMA hosts will see improved latency characteristics.
  • The modulus elimination (patch 4/4) improves enqueue latency on busy servers handling many concurrent client connections.

Final status (as of window close)

The v4 series is fully reviewed and the review round is closed. All four patches carry NeilBrown's Reviewed-by. The open items are now purely mechanical:

  • Layton will add a tracepoint and explanatory comment for the "no pool has any threads" fallback path in v5.
  • Layton will adopt NeilBrown's cleaner thread-floor formulation for patch 3/4 in v5 (agreed last week).
  • The Fixes: tag for patch 1/4 is confirmed as bfd241600a3b.
  • The sv_nrpools simplification is deferred.

No v5 has been posted within this window, and no new patches or objections have appeared. The series appears close to merge-ready, pending the small v5 tweaks and the NFS maintainer's final sign-off. The thread is in a quiet holding pattern.
