nfsd stable backport: release layout stid via nfs4_put_stid on setlease failure

Summary

[PATCH 5.10.y] nfsd: release layout stid on setlease failure

Week of 2026-07-03 → 2026-07-09. A single-message thread this week: a stable-tree backport from Chuck Lever, carrying an upstream fix authored by Chris Mason. No replies landed in the window, so the discussion is effectively a one-shot patch drop rather than a debate.

What it is: a bug fix (memory-safety), not a feature or protocol change

The thread centers on a use-after-free / dangling-pointer bug in the NFS server's pNFS layout stateid teardown path — squarely in NFS client/server development territory, specifically the nfsd layout code (fs/nfsd/nfs4layouts.c). The patch is marked for the 5.10.y stable series, with Fixes: c5c707f96fc9 ("nfsd: implement pNFS layout recalls") and Cc: stable@vger.kernel.org.

Key technical arguments

The bug, as laid out in Chuck Lever's cover message:

"nfs4_alloc_stid() publishes the new stid into cl->cl_stateids via idr_alloc_cyclic() under cl_lock before returning to nfsd4_alloc_layout_stateid(). When nfsd4_layout_setlease() then fails, the error path frees the layout stateid directly with kmem_cache_free() without ever calling idr_remove(), leaving the IDR slot pointing at freed slab memory. Any subsequent IDR walker (states_show, client teardown) dereferences the dangling pointer."

In other words, the stateid is published into the per-client IDR before the lease is set, but the failure path tears it down with a raw kmem_cache_free() — bypassing the IDR removal and the proper reference-counted cleanup. The correct teardown, per the patch description, is:

"The correct teardown for an IDR-published stid is nfs4_put_stid(), which removes the IDR slot under cl_lock, dispatches sc_free (nfsd4_free_layout_stateid) to release ls->ls_file via nfsd4_close_layout(), and drops the nfs4_file reference in its tail."

A second, blocking issue was identified: simply swapping in nfs4_put_stid() is not safe on its own because the layout stateid destructor inspects a work struct that hasn't been initialized yet on this path:

"nfsd4_free_layout_stateid() unconditionally inspects ls->ls_fence_work via delayed_work_pending() under ls_lock, but INIT_DELAYED_WORK(&ls->ls_fence_work, ...) currently runs only after the setlease call. On the setlease-failure path the destructor would touch an uninitialized delayed_work."

The patch therefore does two things: (1) hoists the ls_fenced / ls_fence_delay / INIT_DELAYED_WORK initialization above the nfsd4_layout_setlease() call, and (2) replaces the manual nfsd_file_put + put_nfs4_file + kmem_cache_free cleanup with a single nfs4_put_stid(stp) call.

Stable-tree adaptation

The notable 5.10.y-specific wrinkle is called out in Chuck's sign-off note:

"[ cel: no ls_fence_work in 5.10.y; dropped INIT_DELAYED_WORK hunk ]"

Because the older 5.10 kernel predates the ls_fence_work delayed-work machinery, the upstream fix's initialization-hoisting hunk does not apply and was dropped for this backport — leaving a minimal one-line insertion / three-line deletion change in fs/nfsd/nfs4layouts.c.
