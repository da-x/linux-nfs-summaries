netfs: v5 of bvecq series replaces folio_queue with segmented bio_vec[] chains

Summary

netfs: Keep track of folios in a segmented bio_vec[] chain (v5)

Type: Major refactor / new infrastructure for the network filesystem library (netfslib), touching NFS, AFS, CIFS and cachefiles. This is a feature/consolidation effort rather than a single bug fix, though v5 carries a long list of fixes.

What happened this week

On 2026-07-06, David Howells posted v5 of his 21-patch series "netfs: Keep track of folios in a segmented bio_vec[] chain" to the VFS tree maintainers, asking Christian Brauner to add the patches for next. The series replaces netfslib's folio_queue and rolling_buffer buffer-management constructs with a new segmented chain of bio_vec[] arrays (the "bvecq"), and introduces a new ITER_BVECQ iterator type to replace ITER_FOLIOQ.

The posting was slightly bumpy: Howells followed up minutes later noting that his outgoing mail server had dropped the first send:

"Apologies... The outgoing MX decided to go offline in the middle of that: error: git send-email: 4.7.1 Service unavailable - try again later. So I've re-sent it."

No replies from maintainers or reviewers were posted within this week's window, so the thread stands at the point of submission for review.

Key technical arguments

Howells lays out three motivations in the cover letter:

"(1) The kernel file I/O subsystem seems to be moving towards consolidating on the use of bio_vec arrays, so embrace this by moving netfslib to keep track of its buffers for buffered I/O in bio_vec[] form."

"(2) Netfslib already uses a bio_vec[] to handle unbuffered/DIO, so the number of different buffering schemes used can be reduced to just a single one."

"(3) Always send an entire filesystem RPC request message to a TCP socket with single kernel_sendmsg() call as this is faster, more efficient and doesn't require the use of corking..."

The new struct bvecq carries file position (fpos), a refcount, memory-type flags (pagecache/GUP/allocated/external), and either an inline or separately-allocated bio_vec[]. Howells deliberately makes the chain NULL-terminated linear rather than circular: "I want this to be NULL-terminated linear rather than circular to make it possible to arbitrarily glue bits on the front." Adjacent segments may be discontiguous, which he notes enables bufferage for sparse I/O such as Ceph.

For NFS specifically, the series touches fs/nfs/fscache.c and Kconfig, and v5's changelog records two direct NFS client fixes:

  • "Fixed nfs_netfs_issue_read() to set -ENOMEM, not 0, on alloc failure."
  • "Fixed nfs_netfs_issue_read() to only terminate the subreq once."

Evolution and bug-fixing history

This is the fifth revision. The changelog shows the series has been shaped substantially by automated review from Sashiko across v2 and v4, with dozens of fixes folded in — off-by-one errors in bvecq_pos_step(), memory-type mixing in bvecq_expand_buffer(), missing barriers when checking nr_slots, an uninit var in afs_do_read_symlink(), a double fput() in cachefiles, and CIFS credit leaks on reopen failure. v5 itself was "Rebase[d] on v7.2-rc2 as that has a bunch of outstanding netfs and afs bugfixes included."

Notable supporting patches this week include the readahead change (patch 01) to store a folio count in readahead_control, bulk-loading readahead folios up front (patch 02, reviewed by Paulo Alcantara), a new bvec_kmap_partial() helper for multipage bio_vecs (patch 03), the core segmented bvecq iterator type (patch 05), and the netfslib management tools (patch 06).

Conclusion

The discussion is a large-scale refactor/new-feature effort to unify netfslib buffer handling on bio_vec[], with direct implications for the NFS client's read path and fscache integration. As of this week's close, the series has been submitted (v5) but no maintainer response or review feedback has yet appeared in-thread; Howells also teases follow-on work (subchain copies for protocol framing, and splicing the TCP receive queue into bvecq chains) that is "not in this branch."
