NFS: Verify symlink inode before caching target (bug fix)

Summary

NFS: Verify symlink inode before caching target

Type: Bug fix (NFS client, fs/nfs/dir.c) Status this week: Patch posted; no replies yet in the window.

What happened this week

The only activity in this thread during the reporting window was a single patch submission on 2026-07-03 by ZhangGuoDong (KylinOS), co-developed with Jackie Liu, proposing a small hardening fix to nfs_symlink(). No discussion, review feedback, or follow-up has landed as of the end of the week.

The technical argument

The patch targets an unchecked cache-insertion path in the NFS client's symlink handling. As the author explains:

"nfs_symlink() copies the symlink target into a folio before issuing the SYMLINK RPC. After a successful reply, it caches that folio in the instantiated inode mapping and assumes that the dentry now names a symlink."

The danger arises when that assumption is wrong — i.e., the dentry gets instantiated with a non-symlink inode:

"If the dentry is instantiated with a non-symlink inode, the raw symlink target folio can be inserted into the wrong mapping. When that inode is a directory, reclaim or unmount later calls nfs_readdir_clear_array() through nfs_dir_aops and interprets the symlink target as a readdir cache array, which can lead to invalid kfree() calls."

To back up the claim with real-world evidence, the author included a vmcore from a 4.19-based kernel showing exactly this crash during directory-mapping reclaim on unmount:

"Stack trace: nfs_readdir_clear_array+0x4d/0x70 [nfs] page_cache_free_page.isra.35+0x1a/0x90 delete_from_page_cache_batch+0x1cf/0x2c0 truncate_inode_pages_range+0x24d/0x910 [...] nfs_evict_inode+0x15/0x30 [nfs] evict+0x115/0x2b0 dispose_list+0x48/0x60 evict_inodes+0x16c/0x1b0 generic_shutdown_super+0x3f/0x120 nfs_kill_super+0x1b/0x40 [nfs] deactivate_locked_super+0x3f/0x70 cleanup_mnt+0x3b/0x80"

The author notes that the same unchecked pattern persists in current mainline:

"The current code still has the same unchecked cache insertion pattern, so it may be susceptible to the same failure mode."

The proposed fix

A minimal 6-line addition to fs/nfs/dir.c that verifies the instantiated inode's type before caching the target folio:

"Verify that the instantiated inode is a symlink before caching the target folio. If the type is wrong, drop the suspect dentry and skip the cache insertion while preserving the successful SYMLINK result."

The design choice — dropping the dentry rather than failing the syscall — is notable: it keeps the user-visible SYMLINK operation successful (the server-side symlink was created) while avoiding corrupting a non-symlink inode's page cache with unrelated data.

Evolution and conclusions

Since this is a single-message thread in the current window, there is no evolution of discussion to trace. The patch awaits review from the NFS client maintainers. Given its small scope (6 lines), clear crash evidence, and conservative fix strategy, it appears well-positioned for acceptance if reviewers agree with the type-check approach.
