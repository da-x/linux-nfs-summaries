6.18.37 nfsd crash: Chuck Lever exonerates export-cache revert, points at latent nfs4state use-after-free

Summary

6.18.37 nfsd crash: suspect commit cleared, focus shifts to a latent nfs4state.c bug

Type: Bug fix / regression investigation (NFS server side — nfsd, not the client). This week's single message is Chuck Lever's decisive analytical pivot in an ongoing debugging exchange with reporter Wolfgang Walter over a hard lockup that appeared in stable kernel 6.18.37 but not 6.18.36.

Bridging prior weeks (brief)

The thread began with Wolfgang's report of a production NFSv4.2 fileserver wedging on 6.18.37, and his bisect pointing at commit 95f9eb19d5e6 ("Revert 'NFSD: Defer sub-object cleanup in export put callbacks'") — the only NFS-server delta between 6.18.36 and 6.18.37. In the prior week's window, Chuck Lever opened the investigation by validating that bisect and asking for (a) a complete kernel log from the first stall line onward and (b) a "revert-the-revert" diagnostic build to A/B test the suspect commit. Wolfgang then supplied the missing crash data: a null-pointer Oops in remove_blocked_locks() → __destroy_client() → nfsd4_destroy_clientid() during a COMPOUND, on an NFS 4.2 / sec=krb5p box with ~50 users connected and clients actively disconnecting. He committed to running the diagnostic build.

This week's discussion

Chuck Lever clears the suspect commit and re-frames the bug as latent upstream (2026-07-03). Writing to Wolfgang and stable@, Chuck delivers a "short version" that overturns the bisect's conclusion:

"Short version for stable@: 6.18.37 does not need a revert of 95f9eb19d5e6 ("Revert 'NFSD: Defer sub-object cleanup in export put callbacks'"). That commit is correct for 6.18, and it is not the cause of Wolfgang's crash. Please leave it in place."

His reasoning is a clean file-level argument: the suspect revert touches only fs/nfsd/export.c, export.h, and nfsctl.c, whereas the oops sits entirely in fs/nfsd/nfs4state.c:

"Wolfgang's oops is in remove_blocked_locks() -> __destroy_client() -> nfsd4_destroy_clientid(), entirely within fs/nfsd/nfs4state.c, which the revert does not modify. That path is byte-for-byte identical across 6.18.36, 6.18.37, and current mainline, so the revert cannot have introduced the bug and no missing backport repairs it."

He then draws the key conclusion about the A/B split:

"The 6.18.36-good / 6.18.37-bad split is a timing coincidence; I believe the same latent bug is present in both."

Because the defect exists upstream as well, Chuck redirects the fix path:

"Because the defect is present upstream as well, the fix belongs in mainline first and is then backported to 6.18.y and the other affected trees."

New diagnostic plan — KASAN instead of the revert-the-revert build. Chuck explicitly withdraws his earlier experiment ("you do not need the revert-the-revert build I suggested earlier; that experiment no longer tells us anything") and asks Wolfgang to run a KASAN-enabled 6.18.37 kernel, giving exact config knobs (CONFIG_KASAN=y, CONFIG_KASAN_GENERIC=y, CONFIG_KASAN_INLINE=y, CONFIG_STACKTRACE=y) and explaining what evidence it will produce:

"When it trips, KASAN prints a 'BUG: KASAN: use-after-free' report with 'Allocated by' and 'Freed by' call stacks. That report, in full, is what I need -- it should land in /var/log/messages just as the last oops did."

He flags the practical cost — "KASAN roughly doubles memory use and adds CPU cost, so weigh that before running it on the production server" — and offers a fallback (full log from the first stall line onward, all CPU backtraces, via netconsole or serial). Finally, Chuck commits to producing a fix proactively:

"I will draft a candidate upstream fix from the analysis so far and send it separately. If KASAN on the production box is not an option, testing that patch may be the least disruptive way to confirm."

He closes with thanks for "the careful report and the bisect."

Technical assessment

  • Classification: A bug-fix hunt — specifically a suspected use-after-free / list-corruption in the NFSv4 client-state teardown path (remove_blocked_locks() walking a corrupted or freed lock list while destroying a client ID). It is squarely server-side nfsd state management, not a wire-protocol change or new feature. (The task's emphasis on NFS client development does not apply to this thread.)
  • Evolution of the discussion: The investigation has flipped. Last week the leading hypothesis was that commit 95f9eb19d5e6 changed export-cache cleanup timing and created the UAF window; this week Chuck rules that out by showing the faulting code path is untouched by the commit and identical across 6.18.36, 6.18.37, and mainline. The bug is re-characterized as a latent upstream defect in nfs4state.c that 6.18.37 merely exposed through timing.
  • Key technical argument: A file-scope / code-path identity argument — the oops lives in code the suspect commit never modified, so neither reverting it nor backporting anything to it can help; the fix must land in mainline first.
  • Open questions for next week: (1) whether Wolfgang can run KASAN on the production box or will fall back to a full stall log / testing Chuck's patch; (2) the content of the "candidate upstream fix" Chuck says he will send separately — no such patch appears in this week's window, so its arrival and review are the likely next development.

Status

Unresolved as of end of window. The suspect commit has been exonerated and left in place; the bug is re-scoped to a latent upstream nfs4state.c defect. Awaiting either KASAN output from Wolfgang or his test of Chuck's forthcoming candidate fix before the patch can be confirmed and backported.
