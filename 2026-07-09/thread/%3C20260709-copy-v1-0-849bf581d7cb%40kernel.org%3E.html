Jeff Layton adds a pynfs test suite for NFSv4.2 copy offload (and fixes a COPY_NOTIFY XDR bug)

Summary

pynfs gains a dedicated NFSv4.2 copy-offload test suite

On Thursday, July 9, Red Hat's Jeff Layton posted a thirteen-patch series to the linux-nfs list that fills a notable gap in the pynfs conformance tooling: real, runnable tests for the NFSv4.2 copy offload operations (COPY, OFFLOAD_STATUS, OFFLOAD_CANCEL, and COPY_NOTIFY). The series is announced in the cover letter and touches 6 files with roughly 740 lines added.

"This patchset adds a number of tests for copy offload. Most of them are normal single-server testcases, but the last one adds a test of an actual server-to-server copy from one server to another." — Jeff Layton, cover letter

This is primarily a test-infrastructure / conformance effort rather than a kernel protocol change, but it carries two important side effects for NFS client and server development: it encodes the RFC 7862 semantics that servers must honor (including the async-downgrade case), and it ships an actual bug fix in pynfs's XDR layer that was blocking COPY_NOTIFY from being exercised at all.

The test coverage, patch by patch

The series builds up incrementally:

  • 01/13 lays the groundwork with helpers (_do_copy(), _create_and_open(), _poll_offload_status()) and chunked _write_data()/_verify_data() that respect the session's negotiated ca_maxrequestsize/ca_maxresponsesize. The first real test, testSyncCopy (COPY1), copies 64 KB and verifies the destination. Layton flags a subtle protocol point here:

    "RFC 7862 permits a server to perform the copy asynchronously even when a synchronous copy is requested, so honor cr_resok4.cr_requirements.cr_synchronous: poll OFFLOAD_STATUS to completion when the server downgrades to async instead of failing on a zero wr_count."

  • 02/13 (testCopyWithOffset, COPY2) exercises non-zero source and destination offsets — 4 KB from offset 1024 to offset 512.

  • 03/13 (testAsyncCopy, COPY3) requests an async copy of 1 MB and polls OFFLOAD_STATUS to completion, while still tolerating a server that completes synchronously.

  • 05/13 (testOffloadCancel, COPY7) starts an async copy and immediately issues OFFLOAD_CANCEL, accepting NFS4_OK, NFS4ERR_NOTSUPP, or NFS4ERR_COMPLETE_ALREADY since the copy may finish first.

  • 06/13 and 07/13 (COPY8/COPY9) check that a bad source or destination stateid is rejected with NFS4ERR_BAD_STATEID. Layton notes the care taken to use a fabricated non-special stateid, because "the all-zero anonymous or all-one READ-bypass special stateids... [are ones] a server legitimately accepts."

  • 08/13 (COPY10) verifies OFFLOAD_STATUS with a fabricated stateid also returns NFS4ERR_BAD_STATEID.

  • 09/13 (testCopyToSameFile, COPY11) covers the in-file copy case (offset 0 → offset 8192 within one file).

A test written to catch a real kernel bug

The most pointedly useful patch for NFS server development is 04/13 (testAsyncCopyOffloadStatusAfterComplete, COPY6). It performs an async copy, waits for completion, then re-queries OFFLOAD_STATUS after a delay to confirm the server still returns valid copy state. Layton is explicit that this is not just defensive coverage:

"This catches a kernel bug where the async copy reaper has an inverted TTL check (if (--cp_ttl) instead of if (!--cp_ttl)), causing the copy state to be destroyed on the first laundromat tick after completion rather than surviving for the full TTL window."

In other words, the test is designed to expose a lifetime-management bug in the kernel's async-copy reaper — exactly the kind of regression that pure client-side testing would miss.

The COPY_NOTIFY XDR fix (a genuine bug fix)

Buried in the middle of the series, 10/13 is a real code fix rather than a test. The nfs_argop4 union arm for OP_COPY_NOTIFY was misnamed opoffload_notify, but pynfs's nfs_ops derives the keyword from the operation name and looks for opcopy_notify:

"Because of the mismatch, op.copy_notify() raised TypeError and the operation could not be constructed at all. Rename the arm to opcopy_notify to match, enabling op.copy_notify()."

This is a one-line fix in nfs4.1/xdrdef/nfs4.x, but it's load-bearing for the rest of the series: without it, the COPY_NOTIFY tests below could not run.

Inter-server (server-to-server) copy

The final three patches push into NFSv4.2's inter-server copy territory:

  • 11/13 exercises the source-server half of inter-server copy against a single server. A client requesting an inter-server copy "first sends COPY_NOTIFY to the source server to authorize the destination and obtain a source stateid and netloc list." Three tests (CPNOTIFY1–3) cover the basic case, a bad source stateid, and a missing current filehandle — all treating NFS4ERR_NOTSUPP as a portable "unsupported" outcome.
  • 12/13 adds the plumbing to talk to two servers at once: a new --server2 SERVER:/PATH option (parsed with parse_nfs_url) and an optional second client env.c2. The environment now creates, initializes, and cleans up the test tree on both servers. When --server2 is absent, c2 is None and single-server runs are unaffected.
  • 13/13 delivers the headline test, INTERCOPY1: a full server-to-server COPY across two servers. The source file lives on the second server, the destination on the primary; the client issues COPY_NOTIFY to the source, then COPY to the destination naming the source via ca_source_server, and verifies the data. It is reported as unsupported when no second server is configured or either side lacks the inter-server operations.

Status and takeaways

As of this week's close, the series has been posted but has not yet drawn replies on the list — it sits at position 51 of 59 in the week's ordering with no visible review traffic. Layton notes the work is "based on top of my dir delegation pynfs tests, but I don't think they touch much of the same code," signaling low merge conflict risk.

For NFS developers, the value here is threefold: (1) it gives pynfs a proper conformance surface for copy offload that server implementers can run against; (2) it encodes RFC 7862's async-downgrade semantics in a way that will catch servers which incorrectly fail on a zero wr_count; and (3) the COPY6 test is explicitly targeted at a kernel reaper TTL bug, making this series a small but concrete contribution to NFS server correctness — even though it lands in the client-side pynfs tooling.
