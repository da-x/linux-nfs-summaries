NFSv3 O_WRONLY|O_CREAT EACCES: Solaris 11.4 test settles the UNCHECKED semantics debate

Summary

This week's single message in the thread delivers a decisive empirical data point that resolves the central question raised earlier this week: is the vendor appliance's CREATE behavior (always re-create, return fresh filehandle) or Linux NFSD's behavior (reuse existing file, apply attributes) the correct interpretation of NFSv3 UNCHECKED? Tian Lan of Jane Street tested Solaris 11.4 — the reference implementation for RFC 1813 — and found its behavior matches Linux NFSD, effectively closing the argument.

Bridging prior context (brief)

The thread opened on July 6 when Tian Lan reported that upgrading from kernel 6.1 to 6.12 caused open(O_WRONLY|O_CREAT) on pre-existing files to fail with EACCES against a vendor NFS appliance. The root cause: commit 7c6c5249f061 ("NFS: add atomic_open for NFSv3 to handle O_TRUNC correctly.") made the client issue a CREATE RPC unconditionally on O_CREAT opens, even when the file already exists. Against a conforming server (like Linux NFSD), this is harmless — directory permissions are ignored when the file pre-exists. But the vendor appliance's CREATE implementation always attempts to create a new file and returns a fresh filehandle, which triggers an EACCES when the client lacks write permission on the directory.

Trond Myklebust responded that NFSv3 CREATE "is supposed to ignore the directory permissions if the file already exists" and asked which server was in use. Chuck Lever then provided the RFC-level analysis, pointing to RFC 7530's UNCHECKED4 as the clarifying text.

This week's message (July 8)

Tian Lan's July 8 reply provides the empirical confirmation Chuck Lever had suggested:

"I ran the same test against the Solaris 11.4, and the NFSv3's behavior is consistent with the Linux nfsd. I guess this would be sufficient to conclude that the vendor's implementation is deviated from the actual intent and the addition of NFSv3 atomic_open exposes this difference in an very unfortunate way."

This is a significant finding because Solaris is the reference implementation for RFC 1813. If the original authors' own server behaves like Linux NFSD (reuse existing file on UNCHECKED create), then the vendor appliance's behavior — always re-creating and returning a fresh filehandle — is the deviation, not the Linux client or server.

Key technical arguments

The RFC interpretation question

Chuck Lever had laid out the normative argument in his July 7 reply:

"Compare RFC 7530's UNCHECKED4. It says explicitly that if the object already exists, a non-exclusive create does not recreate it. The existing object is used and the supplied attributes are applied."

And more pointedly:

"IMHO the correct interpretation, the one consistent with the rest of NFSv3, with NFSv4's clarifying text, and with POSIX, is NFSD's, not the vendor's. UNCHECKED governs error-vs-no-error on a duplicate, not recreate-vs-reuse."

The Solaris 11.4 test now provides the missing empirical pillar: both the RFC text (via RFC 7530's clarification) and the reference implementation agree that UNCHECKED means "don't error if it exists," not "recreate it."

The client-side design tradeoff

Tian had also asked in his July 7 message whether the kernel should always do a lookup before deciding to send CREATE, noting that in the current code "the lookup happens after the atomic_open which does the CREATE rpc" (citing fs/namei.c). Trond's earlier response addressed this: even the old LOOKUP-then-CREATE path had race conditions. The new unconditional-CREATE approach is more race-safe but exposes server non-conformance.

The vendor deviation

The practical upshot is that the vendor appliance implements UNCHECKED as "always create fresh" rather than "create if absent, reuse if present." This is a server-side bug (or at minimum a non-conformant interpretation) that was previously invisible because the old Linux client did a LOOKUP first and only sent CREATE when the file didn't exist. The atomic_open change in 6.12 made the client more correct (eliminating the TOCTOU race) but also more exposed to server non-conformance.

Classification and impact

  • Type: Bug fix / regression investigation. The Linux client change (7c6c5249f061) was a deliberate improvement for O_TRUNC correctness, but it exposes a latent server-side non-conformance in the vendor appliance.
  • NFS client development relevance: The atomic_open path for NFSv3 is now confirmed to be the correct design — it eliminates lookup/create races. The fix needed is on the server side (the vendor appliance), not the client. No client-side patch is expected.
  • User impact: Applications doing open(O_WRONLY|O_CREAT) on pre-existing files in directories where the user lacks write permission will continue to fail against this specific vendor appliance on 6.12+ kernels until the vendor fixes their CREATE implementation. The workaround (stripping O_CREAT for known pre-existing files) remains necessary in the interim.

Final status

The thread has effectively concluded with Tian's empirical confirmation. The consensus is:

  1. Linux NFSD and Solaris 11.4 agree on UNCHECKED semantics (reuse, not recreate).
  2. RFC 7530's UNCHECKED4 text supports this interpretation.
  3. The vendor appliance deviates from the protocol intent.
  4. The Linux client's atomic_open behavior is correct and should not be reverted.

No further patches or responses are expected unless the vendor engages or a different edge case surfaces.
