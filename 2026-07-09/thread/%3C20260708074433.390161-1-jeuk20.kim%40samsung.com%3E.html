NFSv4/flexfiles: two-patch series fixes v4.0 DS NULL deref and adds loosely coupled DS support

Summary

NFSv4/flexfiles: two-patch series fixes v4.0 DS NULL deref and adds loosely coupled DS support

Classification

This week's thread is a new feature plus bug fix pair, squarely in NFS client development territory (the fs/nfs/flexfilelayout/, fs/nfs/filelayout/, fs/nfs/nfs4client.c, and fs/nfs/nfs4session.c paths). It is not a wire-protocol change — the series implements an already-specified RFC 8435 behavior that the client had been ignoring, and it fixes a pre-existing crash on a code path that has been broken since v4.0 data servers were first allowed.

The submission (July 8)

Jeuk Kim (Samsung) posted a two-patch series on July 8 titled [PATCH 0/2] NFSv4/flexfiles: support loosely coupled data servers](https://lore.kernel.org/linux-nfs/20260708074433.390161-1-jeuk20.kim@samsung.com/). The cover letter frames the problem in one sentence:

"RFC 8435 allows a flexfiles data server to be loosely coupled, i.e. an NFS server that does not advertise EXCHGID4_FLAG_USE_PNFS_DS via EXCHANGE_ID. The client currently ignores the ffdv_tightly_coupled flag and treats every DS as tightly coupled, so NFSv4.1+ I/O to a loosely coupled DS fails during DS setup."

The series touches nine files with 37 insertions and 20 deletions — a modest footprint for what is effectively two distinct defects in the same DS-connect path:

  • Patch 1/2 (bug fix): NFSv4/flexfiles: fix NULL dereference for NFSv4.0 data servers
  • Patch 2/2 (feature): NFSv4/flexfiles: support loosely coupled data servers

Patch 1/2 — the v4.0 DS NULL-dereference fix

This is a bug fix with a Fixes: tag pointing at commit a7878ca14008 ("nfs: flexfilelayout: remove v3-only data server limitation"), meaning the crash has been latent ever since the v3-only restriction was lifted. Kim's diagnosis is precise about the root cause:

"flexfiles accepts NFSv4.0 data servers, but two NFSv4 code paths assume the data server client has a session. Unlike NFSv4.1+, an NFSv4.0 client has no session (clp->cl_session is NULL; it uses clp->cl_slot_tbl), so I/O to a v4.0 flexfiles DS oopses."

Two specific dereferences are called out:

  1. nfs4_init_ds_session() — "dereferences clp->cl_session->session_state while seeding the DS lease. It also only seeds cl_lease_time when NFS4_SESSION_INITING is set; without a session that never happens, so cl_lease_time stays 0 and nfs4_renew_state() busy-loops, requeuing every 5 seconds." The fix seeds the lease whenever there is no session and returns before touching session state.

  2. ff_layout_async_handle_error_v4() — "dereferences clp->cl_session->fc_slot_table on every DS I/O error." The fix falls back to the v4.0 transport slot table (clp->cl_slot_tbl) when there is no session.

The busy-loop detail is particularly noteworthy: even if a user dodged the first NULL deref, the second symptom — nfs4_renew_state() requeuing every five seconds forever because cl_lease_time never got seeded — would have kept the client in a degraded state. This is the kind of bug that is easy to miss in casual testing because it only fires when the data server happens to be NFSv4.0 rather than 4.1+.

Patch 2/2 — loosely coupled DS support

This is the new feature half of the series, implementing an RFC 8435 §2.3/§4.1 behavior the client had been silently ignoring. Kim's explanation of why the current code breaks:

"Two things force that assumption on an NFSv4.1+ DS:

  1. nfs4_set_ds_client() always sets NFS_CS_PNFS on the new client, so EXCHANGE_ID is sent with EXCHGID4_FLAG_USE_PNFS_DS.
  2. nfs4_init_ds_session() then calls is_ds_client() and returns -ENODEV if the reply does not carry EXCHGID4_FLAG_USE_PNFS_DS."

The conceptual point is clean: "A loosely coupled DS is just a normal NFS server and does not act in the pNFS DS role, so the client must not require it to advertise that role." The fix threads the decoded ds_versions[0].tightly_coupled flag from the flexfiles driver down to the DS connect path; when it is false, both the NFS_CS_PNFS flag and the is_ds_client() check are skipped. The file layout driver always passes true because "NFSv4.1 file layout data servers use the pNFS DS role" — so this patch is a flexfiles-specific behavior change that leaves the filelayout path untouched.

The only later activity in the thread is a single reply from Tigran Mkrtchyan (DESY) on August 6, which falls outside this week's scope and is not summarized here.

Key technical arguments

  1. The v4.0 DS crash is a long-dormant latent bug. The Fixes: tag (a7878ca14008) dates back to when the v3-only restriction was removed, so any deployment that has been using NFSv4.0 flexfiles data servers on a recent kernel has been exposed to both the NULL deref and the lease-renewal busy loop. This is a genuine correctness fix, not a hardening nicety.

  2. The loosely coupled DS feature closes an RFC 8435 compliance gap. The client was decoding the tightly_coupled flag from GETDEVICEINFO but then ignoring it on the connect path. For any deployment that follows the RFC and runs a loosely coupled DS (a plain NFS server that does not advertise the pNFS DS role), I/O to that DS has been failing at setup with -ENODEV. The fix is small (thread one boolean down the call chain) but unblocks a documented deployment topology.

  3. The two patches are complementary on the same code path. Patch 1 fixes the v4.0 case (no session at all); Patch 2 fixes the v4.1+ loosely-coupled case (session exists but must not carry the pNFS DS flag). Together they make the flexfiles DS connect path handle all three documented topologies: tightly coupled v4.1+, loosely coupled v4.1+, and v4.0 (which is implicitly loosely coupled since there is no EXCHANGE_ID at all).

Relevance to NFS client development

This is one of the more directly client-facing threads this week. The flexfiles layout driver is a first-class pNFS client component, and the series touches core nfs4client.c / nfs4session.c infrastructure that other layout drivers also use (the filelayout driver is updated in passing to pass true for the new parameter). The v4.0 NULL-dereference fix in particular is the kind of crash-class bug that maintainers typically want to see backported to stable once reviewed.
