NFSD: v3 series fixes client use-after-frees across teardown and state revocation

Summary

NFSD: Fix UAFs in client teardown and state revocation (v3)

Type: Bug fix (a coordinated set of nine lifetime/race fixes, plus one cleanup and one reference-count leak fix) — no protocol or feature change.

What happened this week

On Tuesday, July 7, NFS server maintainer Chuck Lever posted the third revision of a nine-patch series titled "NFSD: Fix UAFs in client teardown and state revocation." All ten messages in the thread this week are Chuck's own postings of the cover letter and the nine patches; no replies or review comments landed inside the summary window, so the discussion is at the "posted for review" stage.

The series grew out of a field report: patch 1 carries Reported-by: Wolfgang Walter <linux@stwm.de> and closes his NULL-dereference report from client teardown. In the cover letter, Chuck frames the whole problem as one recurring pattern:

"An NFSv4 stateid, and a bare lock owner reachable through the client's owner hash, hold only a raw pointer to the owning nfs4_client. That client outlives its state only because __destroy_client() drains every stateid and owner before free_client() runs."

And the consequence of breaking that invariant:

"The NULL-pointer dereference reported during client teardown was one such race; auditing the pattern found more across the revocation and laundromat-reaping paths."

The core technical argument

The series' central fix is uniform: whenever a path drops nn->client_lock while still holding only a stateid or owner (which does not pin the client), it must first take a cl_rpc_users pin so that teardown blocks until the work completes. Chuck explains the subtlety of why "just pin" is not enough:

"force_expire_client() stops consulting cl_rpc_users once its wait has passed, so a pin taken then would not hold the client; the walk must instead leave that client's state for its own teardown to drain. Testing the expiry and taking the pin under nn->client_lock is what makes the choice atomic against the expiry."

He also flags a new lock-ordering edge introduced by the fixes:

"Pinning the client from these paths introduces a lock-order edge that did not exist before: nn->client_lock now nests outside the inner region of nn->deleg_lock and outside nn->blocked_locks_lock, both leaf acquisitions everywhere else. The nesting is one-directional, and netns.h records the deleg_lock relationship; a reaping path added later must take nn->client_lock first."

Patch-by-patch highlights (all posted 2026-07-07)

  • 1/9 — lock owner UAF during client teardown: the reported crash. A lock owner whose only reference is a blocked lock stays on cl_ownerstr_hashtbl; client_has_state() doesn't count it, so DESTROY_CLIENTID can reach __destroy_client() with such owners present, and the per-net laundromat reaping blocked locks "frees the owner as __destroy_client() dereferences it." Fix: hold cl_lock across the walk, take a reference and unhash each owner. Fixes: 68ef3bc31664.
  • 2/9 — delegation revoke: the laundromat unhashes an expired delegation, drops deleg_lock, then relinks it under cl_lock — "In that window the delegation is on neither list, so client_has_state() can report no remaining state." Pin with cl_rpc_users; skip already-expiring clients. Fixes: 3bd64a5ba171.
  • 3/9 — admin state revocation: nfsd4_revoke_states() drops nn->client_lock across revoke_one_stid(), which dereferences the client. Pin under client_lock, skipping clients whose cl_time is already zero. Fixes: 1c13bf9f2e3c.
  • 4/9 — export state revocation: same race in nfsd4_revoke_export_states(); notably "exportfs -u drives this path through NFSD_CMD_UNLOCK_EXPORT, so an administrator removing an export can race a client expiry." Fixes: 2eac189bb059.
  • 5/9 — NFSv4.0 revoked-state cleanup: nfs40_clean_admin_revoked() runs from the laundromat, so "a periodic sweep can race force_expire_client() driven by a write to the clients/<id>/ctl file." Same skip-expiring/pin pattern. Fixes: d688d8585e6b.
  • 6/9 — consolidate unpin: pure cleanup, "No change in behavior." Factors the four open-coded pin-drop sites into __put_client_locked() with new put_client_no_renew_*() helpers, because the existing renew helpers "would resurrect the client whose state is being revoked."
  • 7/9 — blocked-lock reaping: a bare lock owner on nn->blocked_locks_lru holds only a raw client pointer; when the laundromat reaps it, "a concurrent force_expire_client() can free the client before nfs4_put_stateowner() runs." Pin before dropping nn->blocked_locks_lock. Fixes: 7919d0a27f1e.
  • 8/9 — close_lru reaping: an openowner left on nn->close_lru keeps its last closed stateid with only a raw client pointer; "Nothing pins the client across that window." Pin before dropping client_lock; __destroy_client() then cleans up its own entries. Fixes: 217526e7ecc9.
  • 9/9 — svc_export leak: the audit's unrelated find: free_ol_stateid_reaplist() frees stateids via ->sc_free() directly, bypassing nfs4_put_stid(), so "the export stays pinned and blocks unmount for the lifetime of the stateid." Fixes: ba0cde5dc81d.

Evolution across revisions

The v3 cover letter documents what changed since earlier rounds: v2 had already "Add[ed] matching UAF fixes in several other paths," and v3 adds three items, each attributed to a reviewer — "Fix client UAF in laundromat blocked-lock reaping (Neil)," "Fix client UAF in laundromat close_lru reaping (sashiko)," and "Fix svc_export leak when reaping open stateids (sashiko)." Patches 1–5 carry Reviewed-by tags from both NeilBrown and Jeff Layton; patches 7, 8, and 9 (the v3 additions) do not yet.

Status / conclusion

As of the end of this week's window, the series has been posted but no replies, acks, or objections appear in the thread — it is awaiting review, with the two newest fixes (blocked-lock and close_lru reaping) and the export-leak fix still missing formal Reviewed-by tags. For NFS server users, the practical stakes are real: these are crash-class bugs on client expiry/delegation paths, plus an admin-action race (exportfs -u) and a leak that can block unmounting exports.
