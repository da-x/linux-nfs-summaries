6.18.37 nfsd crash: reporter validates Chuck Lever's UAF patch on production, no regressions in a week of soak

Summary

6.18.37 nfsd crash: reporter soaks Chuck Lever's candidate UAF fix on the production fileserver

Type: Bug-fix validation / regression investigation (NFS server side — nfsd state management, not client development or a protocol change). This week's three messages close out the diagnostic phase that began with Chuck Lever's exoneration of the export-cache revert earlier in the same window: Wolfgang Walter now reports a clean soak test of Chuck's candidate fix.

Bridging prior weeks (brief)

Per the prior summary, the thread started with Wolfgang reporting a production NFSv4.2 fileserver wedging on 6.18.37 and his bisect pointing at commit 95f9eb19d5e6 ("Revert 'NFSD: Defer sub-object cleanup in export put callbacks'"). Chuck Lever then delivered the decisive analytical pivot: the oops sits entirely in fs/nfsd/nfs4state.c (remove_blocked_locks() → __destroy_client() → nfsd4_destroy_clientid()), code the suspect commit never touched, so "the 6.18.36-good / 6.18.37-bad split is a timing coincidence; I believe the same latent bug is present in both." Chuck offered two paths forward — run KASAN on the production box, or test his forthcoming candidate patch as "the least disruptive way to confirm" — and committed to drafting an upstream fix separately.

This week's discussion

Wolfgang accepts the re-framing and picks the low-disruption path (2026-07-03). Acknowledging Chuck's verdict, he notes "Ok. I run v6.18.37 with the patch reverted since about a day (just for the record). But according to your analysis, that's just a coincidence." He is receptive to KASAN — "I think the memory usage should not be a problem, higher cpu usage neither" — but flags the fundamental difficulty of chasing an intermittent race on production:

"But as it is a coincidence the probability to catch that error is probably very low. We use v6.18 kernels since v6.18.1 on that fileserver and this error never occured before."

He asks whether the bug might be firing silently — "Or do you think it happens more often, but without symptoms, and KASAN would detect it?" — and settles on testing Chuck's patch:

"So I will try running a v3.18.37 + your patch applied. This of course can not prove that it fixes the problem because it almost never happens, but probably this would detect if if the patch had side effects."

Chuck confirms the limitation of the test (2026-07-03). He validates Wolfgang's reasoning about release correlation and sharpens the diagnosis:

"I think it's more likely that your 50 client workload hit a particular race that exposed a pre-existing UAF. KASAN will change execution timing, certainly, but I can't predict whether it will make the race window bigger."

He then states candidly what the soak test can and cannot prove:

"So you can only test whether my patch causes new regressions, not whether it prevents your crasher. :-("

Wolfgang reports a clean one-week soak (2026-07-06). After running the patched kernel on the production box:

"6.18.37 + your patch is running here since saturday with no problems."

Technical assessment

  • Classification: Bug fix — a suspected use-after-free in the NFSv4 client-state teardown path (remove_blocked_locks() walking a corrupted/freed lock list during nfsd4_destroy_clientid()). Server-side nfsd state management; not a wire-protocol change or new feature, and not NFS client development.
  • Evolution this week: The thread moves from diagnosis to validation. Chuck's earlier file-scope argument (the suspect commit cannot be the cause) is accepted by the reporter, who abandons the revert-the-revert experiment in favor of testing the candidate fix. Chuck explicitly scopes what that test proves — regression-freeness only, not crash-prevention — given the race's rarity ("almost never happens" on a box running 6.18 since v6.18.1).
  • Key technical arguments: (1) The 50-client workload likely "hit a particular race that exposed a pre-existing UAF"; (2) KASAN's timing perturbation makes it an unreliable trigger for this specific window; (3) the only actionable signal from production is absence of regressions under the patch.
  • Status: Unresolved but progressing favorably. The candidate fix has passed a ~4-day production soak with no regressions, which clears the "no side effects" bar Chuck set. What remains open: (a) confirmation that the patch actually prevents the crasher — still pending KASAN output or another natural occurrence; (b) mainline submission of the fix, since Chuck's position is that "the fix belongs in mainline first and is then backported to 6.18.y." The patch itself was not part of this thread's window (Chuck said he would send it "separately"), so its review and merge are the likely next development.
