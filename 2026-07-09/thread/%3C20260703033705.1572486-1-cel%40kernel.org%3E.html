nfsd write-verifier data-loss fix queued for 5.15.y stable

Summary

This week's activity in this thread is a single, terse confirmation from the stable maintainers: Sasha Levin queued Chuck Lever's 5.15.y backport of the NFS server (nfsd) silent-data-loss fix for the next 5.15.y release cycle. The reply is a one-liner, but it closes out the stable-tree leg of a bug that had been in flight since late May and was already landing on other LTS branches this same week.

Classification

  • Type: Bug fix — a protocol-contract violation in the NFS server (nfsd) whose failure mode is silent data loss visible to NFS clients. Not a new feature and not a wire-protocol change; it restores behavior required by the existing UNSTABLE-write + COMMIT contract.
  • Subtree: fs/nfsd/vfs.c (nfsd), but the affected semantics are what clients rely on for durability, so client-visible behavior changes from "silently lose data" to "receive a rotated write verifier and learn the commit failed."
  • Severity: High. Silent data loss is among the worst classes of storage bug because there is no error signal for applications or operators.

Bridging prior weeks (brief)

The original fix was posted by Jeff Layton on May 22 in the mainline thread, reviewed and applied to nfsd-testing the same day (upstream commit 2090b05803faab8a9fa62fbff871007862cac1b7). A companion fix for the async COPY path followed from Chuck Lever in the same week. The bug was reported by Chris Mason (Meta) and credited via Reported-by: in the patch.

This week, the stable backports are rolling out across LTS branches. A sibling thread this same week covered the 5.10.y backport posted by Chuck Lever on July 3; this 5.15.y patch is the parallel effort for a newer LTS branch, and it has now been accepted into the queue.

This week's discussion

The thread root is Chuck Lever's 5.15.y backport, posted July 3 in reply to Greg Kroah-Hartman's stable queue request. The patch carries the same adaptation note as the 5.10.y version:

"[ cel: open-code the reset; commit_reset_write_verifier() is v6.7 ]"

Because the commit_reset_write_verifier() helper does not exist in the 5.15.y stable tree (it was introduced in v6.7), Lever inlined the equivalent verifier-rotation logic directly at both error sites in fs/nfsd/vfs.c — 8 insertions, 1 deletion.

The only reply this week is Sasha Levin's queue confirmation on July 4:

"Queued for 5.15.y, thanks!"

That is the entirety of in-window discussion — a clean, no-objection stable-tree acceptance with no technical pushback.

Technical detail (carried from the original fix)

The bug, as Layton originally described it in the patch that this backport carries:

"nfsd_vfs_write() and nfsd_commit() both call filemap_check_wb_err() to detect deferred writeback errors, but neither rotates the server's write verifier (nn->writeverf) when this check fails. Every other durable-storage-failure path in these functions calls commit_reset_write_verifier() before returning an error."

The consequence for clients:

"The missing rotation means clients holding UNSTABLE write data under the current verifier will COMMIT, receive the unchanged verifier back, and conclude their data is durable — silently dropping data that failed writeback. This violates the UNSTABLE+COMMIT durability contract (RFC 1813 §3.3.7, RFC 8881 §18.32)."

The fix adds verifier-rotation calls at both filemap_check_wb_err() error sites, matching the pattern already used by adjacent error paths in the same functions. Lever notes a safety property that makes the change unconditionally safe:

"The helper already filters -EAGAIN and -ESTALE internally, so the calls are unconditionally safe."
