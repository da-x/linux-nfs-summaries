NFSv4: pin the superblock for active state owners (production umount/reclaim race)

Summary

NFSv4: pin the superblock for active state owners

Type: Bug fix — a use-after-free / lifetime-mismatch in the NFSv4 client's open-state recovery path, triggered when state reclaim races with unmount.

What happened this week

The thread consists of a single message this week: a patch from Jia Zhu (ByteDance), posted July 7, which proposes pinning the superblock for as long as an NFSv4 state owner is active. No replies or review discussion had landed by the end of the week window (July 9), so this summary covers only the patch's motivation and design.

The bug: open state outliving its filesystem

Zhu describes a race observed in production, where NFSv4 state recovery — for example after a server reboot or lease expiration — races with unmount. The core lifetime problem is that "NFSv4 open state can outlive the file and dentry that created it."

The patch lays out the interleaving precisely:

state manager                    umount

nfs4_run_state_manager()
  nfs4_do_reclaim()
    nfs4_reclaim_open_state()
      refcount_inc(&state->count)
      ...
                                      close last file
                                      generic_shutdown_super()
                                        "Busy inodes after unmount"
                                      nfs_free_server()
      nfs4_put_open_state()
        iput(inode)
          evict()
            nfs_clear_inode()
              nfs_zap_acl_cache()

The visible symptom is the VFS warning, which Zhu identifies as "the visible symptom of that lifetime mismatch: superblock teardown proceeds even though the NFS open state still pins an inode." The dangerous consequence follows once nfs_free_server() has run: the state manager's later nfs4_put_open_state() drops the last open-state reference and calls iput(inode), which can evict an NFS inode whose server data is already freed — "causing crashes at nfs_zap_acl_cache()."

Zhu notes the bug is reproducible by delaying the reclaim path just before nfs4_put_open_state(), then closing the last file and unmounting.

The fix

The patch (33 insertions, 7 deletions in fs/nfs/nfs4state.c) takes a reference-counting approach: "Pin the superblock while a state owner is active, and drop the pin when the owner becomes idle again, so the NFS server stays alive until all open state associated with the owner has been released." In other words, the superblock's lifetime is now tied to the liveness of the state owner rather than to the last open file/dentry, which closes the window in which the superblock's active count could drop to zero between refcount_inc(&state->count) and nfs4_put_open_state().

The patch carries an "Assisted-by: Codex:GPT-5" tag alongside Zhu's sign-off.

Status and outlook

As of the week ending 2026-07-09, the patch has no on-list review yet. Given that it touches core NFSv4 state-owner lifetime semantics and addresses a crash observed in production, expect scrutiny from the NFS maintainers on whether pinning/unpinning the superblock around owner activity is the right granularity (versus, e.g., holding a server reference directly), and on the exact points where "active" and "idle" transitions are detected. Worth watching for follow-up in the coming days.
