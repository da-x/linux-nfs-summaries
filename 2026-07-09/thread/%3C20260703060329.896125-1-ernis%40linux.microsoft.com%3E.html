RDMA capability fields: int→u32 conversion (v9) — max_srq exception settled

This week's activity in this thread is a focused review exchange on patch v9 of Erni Sri Satya Vennela's series converting the signed int capability counters in struct ib_device_attr to u32. It is fundamentally a type-correctness / bug-fix patch: as the cover letter puts it, "Drivers maintain their cached caps as u32 and assign them directly into these int fields; if a cap exceeds INT_MAX the implicit narrowing yields a negative value visible to the IB core." The series ripples through the IB core, ULPs, NVMe-oF target, RDS, SMB direct, and — relevant to this list — NFS/RDMA (net/sunrpc/xprtrdma/frwr_ops.c, svc_rdma_transport.c, verbs.c, plus include/linux/sunrpc/svc_rdma.h).

The NFS/RDMA angle

The NFS client's RDMA transport is one of the consumers touched by the conversion. In earlier revisions (per the changelog carried in the v9 cover letter), the author already fixed "min_t(int,...) in svc_rdma_transport" and "%d -> %u in ... svc_rdma_transport", and guarded a u32 underflow in frwr_ops.c by reordering the check before subtraction. So this week's discussion, while RDMA-core-centric, directly affects how the NFS/RDMA client reads device capabilities without signed-narrowing them.

This week's exchange

  • Vennela posts v9 (Jul 3), with the main v9 change being: "Switch the srq_size module parameter accessors to param_get_uint and kstrtouint()/param_set_uint() so they match the now-unsigned nvmet_rdma_srq_size variable."
  • Leon Romanovsky reviews (Jul 6), flagging two things: a missing hunk in drivers/infiniband/core/nldev.c ("The following code is still missing.") and the deliberate exclusion of max_srq: "what about mxa_srq? Why wasn't it converted as well?"
  • Vennela explains (Jul 7) the max_srq exception: "I originally left max_srq as int because its only consumer pairs it with num_comp_vectors (a signed int) in nvmet_rdma, so keeping it int let that site stay a plain min() instead of a min_t()." He adds that num_comp_vectors is "legitimately int and never anywhere near INT_MAX", offers to convert it separately if desired, or simply use min_t() at the one call site.
  • Leon settles it (Jul 7): "In this patch no, but it is worth to write this in commit message." — i.e., keep max_srq as int for now, document the rationale.
  • Vennela confirms (Jul 8): "I'll use min_t for max_srq and document it in the commit message."

Conclusion

The thread converged cleanly this week: the missing nldev.c hunk will be added, max_srq stays signed int with a min_t() at its single consumer (to avoid dragging the conversion into ib_device.num_comp_vectors, which lives in a different struct and touches many call sites), and that rationale will be recorded in the commit message. A v10 is implied but not yet posted as of this week's window close.
