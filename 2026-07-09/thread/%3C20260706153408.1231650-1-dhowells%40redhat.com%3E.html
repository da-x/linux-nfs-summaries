netfs: bvecq replaces folio_queue — v5 of David Howells' 21-patch series lands on linux-nfs

Summary

netfs: Keep track of folios in a segmented bio_vec[] chain (v5)

What happened this week

On Monday, 6 July, David Howells posted version 5 of his 21-patch series "netfs: Keep track of folios in a segmented bio_vec[] chain" to linux-nfs (cc'd to netfs, linux-fsdevel, and the CIFS/AFS/block lists). The whole thread this week consists of the 22 patch messages themselves — no replies or review discussion had landed by the end of the window. This is a major refactoring / new-feature series for the NFS client infrastructure (netfslib), not a single bug fix, though it carries a long list of bug fixes accumulated across prior versions.

In his cover letter, Howells asks Christian Brauner to take the series through the VFS tree:

"Could you add these patches to the VFS tree for next?"

The key technical argument

The core of the change is replacing netfslib's folio_queue + rolling_buffer buffer-management machinery (and the associated ITER_FOLIOQ iterator type) with a new segmented chain of bio_vec[] arrays, called bvecq. Howells lays out three motivations:

"(1) The kernel file I/O subsystem seems to be moving towards consolidating on the use of bio_vec arrays, so embrace this by moving netfslib to keep track of its buffers for buffered I/O in bio_vec[] form."

"(2) Netfslib already uses a bio_vec[] to handle unbuffered/DIO, so the number of different buffering schemes used can be reduced to just a single one."

"(3) Always send an entire filesystem RPC request message to a TCP socket with single kernel_sendmsg() call as this is faster, more efficient and doesn't require the use of corking..."

The new struct bvecq is a refcounted, NULL-terminated doubly-linked segment carrying a file position (fpos), a discontiguity flag, memory-type flags (external / pagecache / GUP-pinned / allocated), and an inline-or-separately-allocated bio_vec[]. Each segment holds contiguous data; adjacent segments may be discontiguous — a design point Howells calls out explicitly because it "allows a bvecq chain to be used to provide bufferage for a sparse read or write RPC such as can be done with Ceph." A new iterator type, ITER_BVECQ, is introduced so the construct can be passed directly to sendmsg() and block-based DIO (as cachefiles does).

Structure of the series

The 21 patches fall into clear phases:

  • Foundation (01–07): Patch 01 makes readahead store the folio count in readahead_control so filesystems know up front how many folios to track; patch 02 bulk-loads readahead folios "up front" (reviewed by Paulo Alcantara); patch 03 adds bvec_kmap_partial() to kmap one page of a multipage bio_vec (renamed from kmap_local_bvec() at Christoph Hellwig's request in v3); patches 04–07 add the bvecq type, ITER_BVECQ, netfslib management tools (a new 763-line fs/netfs/bvecq.c), and an iter-to-bvecq extraction helper.
  • Consumer conversion (08–11): AFS directory content switches from folioq to bvecq (patch 08); CIFS's crypto buffering does the same (patch 09); smbdirect RDMA gains ITER_BVECQ support in smbdirect_map_sges_from_iter() (patch 10, acked by Stefan Metzmacher).
  • Cachefiles rework (11): Patch 11 is arguably the most substantial individual patch: cachefiles stops relying on the backing filesystem's SEEK_DATA/SEEK_HOLE for the common progressive-write case, introducing a CACHEFILES_CONTENT_ALL content type and a new ->query_occupancy() cache method. Howells notes the old approach "does two seek operations on the backing file for each individual read call" and that the backing fs is "at liberty to insert or remove blocks of zeros in order to optimise its layout which may cause false positives and false negatives."
  • Core switch (13): Patch 13 switches netfslib proper to bvecq, introducing three cursors (load_cursor, dispatch_cursor, collect_cursor) and a lightweight bvecq_pos position representation.
  • Cleanup (14–18): Removal of ITER_FOLIOQ from smbdirect and iov_iter, deletion of netfs_alloc/free_folioq_buffer(), netfs_extract_user_iter(), and finally all of folio_queue and rolling_buffer (patch 18 deletes ~1,050 lines including the folio_queue documentation).
  • Bug fixes and polish (19–21): Patch 19 adds a check in read subrequest termination to detect "more data being read for a subrequest than was requested." Patch 20 fixes a performance bug in progress reporting: with small folios the collector thread was "constantly being woken up - which has a negative performance impact," so it sets a minimum trigger of 256KiB and corrects the base to be the stream collection point. Patch 21 collapses ->prepare_xxx() and ->issue_xxx() into a single issue callback where the filesystem slices its buffer off the master bvecq chain — motivated by how hard writeback is "quite difficult to follow" with multiple streams (server + cache).

Bug-fix pedigree

The v5 changelog in the cover letter documents extensive bug fixing driven by the Sashiko review bot across prior versions, including fixes for an underflow in iov_iter_extract_xarray_pages(), an off-by-one in bvecq_pos_step(), a double fput() in cachefiles, missing barriers when walking stream->subrequests during retry, and — directly relevant to the NFS client — "Fixed nfs_netfs_issue_read() to set -ENOMEM, not 0, on alloc failure" and "to only terminate the subreq once." Howells also notes v5 is rebased on v7.2-rc2 "as that has a bunch of outstanding netfs and afs bugfixes included."

Outlook / future work

Howells flags two in-progress follow-ups not in this branch: letting a filesystem take a copy of a subchain to tack protocol headers/trailers onto (working for CIFS), and splicing the TCP receive queue into a bvecq chain so "the socket lock can be dropped much more quickly." Longer-term ideas include batched folio-unlock functions, iterating i_pages by file position instead of walking bio_vecs, and eventually using bvecq to replace scatterlist — with the caveat that "crypto drivers like to glue bits on the front of the scatterlists they're given."

Status at week's end

The series is fresh (posted 6 July) with no reviewer responses in this window; Paulo Alcantara has already provided Reviewed-by/Acked-by tags on several infrastructure patches, and Stefan Metzmacher acked the smbdirect changes. The discussion — if any — will presumably continue next week as VFS maintainers weigh in.
