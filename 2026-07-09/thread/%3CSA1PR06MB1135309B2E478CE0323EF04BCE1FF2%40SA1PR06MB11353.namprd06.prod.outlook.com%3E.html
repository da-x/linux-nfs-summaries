NetApp engineer asks for rdirplus mount option to bypass READDIRPLUS heuristics

Summary

New feature request: an rdirplus mount option to bypass the client's READDIRPLUS heuristics

This week brought a fresh, single-message thread on linux-nfs as NetApp engineer Jorge Mora opened a discussion with NFS maintainer Trond Myklebust about extending the client's rdirplus mount option. The request is framed as a new feature (a new mount-option knob) motivated by what amounts to a performance regression / bug in the client's READDIRPLUS behavior on newer kernels.

The problem reported

In his opening post, Mora describes a customer who hit "significant performance degradation after switching from Rocky Linux 8.7 clients to a 6.12 upstream kernel." The newer-kernel clients show "a dramatic increase in GETATTR/LOOKUP operations" on a workload that is essentially read-only directory traversal plus attribute retrieval:

"Their workload primarily involves traversing a read-only directory tree and reading or retrieving file attributes."

He pins the cause squarely on the client-side change that introduced heuristics for when to issue READDIRPLUS versus plain READDIR:

"This issue is related to changes made to add heuristics to READDIRPLUS."

The workaround — and why it isn't good enough

Mora says his team has been testing on RHEL 9.7 with the existing rdirplus=force option, which does reduce the GETATTR/LOOKUP storm, but at a cost:

"However, this option introduces other issues."

In other words, forcing READDIRPLUS unconditionally swings the pendulum too far the other way (extra attribute data is fetched and cached even when it isn't wanted), so force is not an acceptable steady-state configuration for this customer.

The ask: two new option values

Mora proposes two possible new mount-option values to give administrators a dial rather than a switch:

"Is it possible to add a mount option to completely bypass the readdir heuristics, such as 'rdirplus=legacy'? Alternatively, could a mount option be added to make the client less aggressive in sending READDIRPLUS requests, such as 'rdirplus=eager'?"

  • rdirplus=legacy would restore pre-heuristic behavior (plain READDIR, letting the VFS/page cache drive follow-up GETATTR/LOOKUPs) for workloads where that is measurably faster.
  • rdirplus=eager would make the client issue READDIRPLUS more aggressively than the current heuristic does, sitting between today's default and force.

State of play as of this week

This is a new thread — it has no prior-week summary file to bridge from, and there was exactly one in-window message (Mora's opening post on 2026-07-08). No maintainer reply landed within the reporting window; the discussion is still open as of the week ending 2026-07-09. The request lands in a familiar area for NFS client developers: the READDIRPLUS heuristic has been a recurring source of workload-dependent performance trade-offs, and this report is another data point from the storage-vendor side asking for finer-grained user control over when the client fetches directory-entry attributes inline versus lazily.

Why it matters for NFS client development

The thread highlights a classic tension in the Linux NFS client: READDIRPLUS saves round-trips on attribute-heavy workloads but can waste bandwidth and server CPU when callers don't need the extra attributes, while plain READDIR generates a GETATTR/LOOKUP per entry that can dominate on large directory traversals. A customer-visible regression between 8.x-era kernels and 6.12 suggests the heuristic's default behavior is not optimal for every workload, and Mora's proposal is effectively a request to expose the heuristic as a tunable rather than a fixed policy — a pattern (per-mount knobs like rdirplus=force|none) that already exists in the client and would be extended here.
