nfsd: do_lookup_open() switchover hits three correctness landmines; re-roll requested

Summary

nfsd: do_lookup_open() for non-creating opens — three correctness concerns force a re-roll

Thread: [PATCH v2 14/14] nfsd: use do_lookup_open() for non-creating open requests too. (root 20260705222032.1240057-15-neilb@ownmail.net) Week: ending 2026-07-09 · In-window messages: 1

The big picture

Neil Brown's v2 series "nfsd: refactor nfs4_create_file()" is a long-running cleanup of the NFSv4 server-side open/create path. The final patch (14/14) flips plain, non-creating OPEN requests over to the new do_lookup_open() helper that was built for the create path. This week's single in-window message — Chuck Lever's review — is a heavyweight objection: three correctness regressions, each with a concrete failure mode, and an explicit request that the series be re-rolled before it can land.

This is a bug-fix / regression-prevention discussion on top of a refactor, not a new feature or protocol change. The NFSv4 wire protocol is untouched; the concern is entirely about what the server does (or stops doing) when it resolves and opens an existing file handle for a client OPEN.

Context: how we got here

The series has been iterating since at least a June RFC ("VFS/nfsd: replace dentry_create()") and v2 was posted 2026-07-05. Chuck's reply is framed as a follow-up to automated review tooling rather than a first-pass read:

"Thanks for jumping on the Sashiko findings. Codex review identified three correctness concerns which I've confirmed with Claude are not false positives"

That framing matters journalistically: this is an example of AI-assisted patch review (Sashiko, Codex, Claude) doing the first-line triage on a kernel mailing list, with a human maintainer confirming each finding before it goes to the author. The three items below are the confirmed findings.

The three correctness concerns

1. Unconditional mnt_want_write() breaks read-only mounts for plain reads

do_lookup_open() grabs write access on the parent mount unconditionally:

"error = mnt_want_write(parent->mnt); if (error) return ERR_PTR(error);"

"Fine for a create. But a read-only OPEN with no create now returns -EROFS on anything mounted read-only at the VFS layer: squashfs, iso9660, a read-only bind mount, a snapshot."

The old code path only asked for write when nfsd_open() actually opened the file, and for O_RDONLY it never asked at all. Chuck is careful to draw a line between this and the NFS export ro= option:

"Worth stressing that this isn't the 'ro' export option. That keeps the underlying mount writable and is enforced in nfsd, so it's fine. Only genuinely read-only mounts break, which is probably why it slipped past testing."

His proposed fix: make the mnt_want_write() conditional on O_CREAT, since "the read-only-open setattr path already re-takes write for itself, so it shouldn't need the blanket grab."

2. Opening before type-checking turns OPEN into a DoS vector

do_lookup_open() runs dentry_open() on any positive dentry; the regular-file check (nfsd_check_obj_isreg()) only happens after nfsd4_open_file() returns. With no O_NONBLOCK, an OPEN of an existing FIFO blocks in fifo_open() waiting for a peer — while still holding the parent directory's i_rwsem from start_creating():

"One client can pin an nfsd thread and the parent directory that way; a handful of them and the pool is spent. A device node does the same thing through its ->open."

Chuck concedes this isn't strictly new to 14/14 — an earlier patch ("always open file in nfsd4_create_file()") already opened existing files for the UNCHECKED case — but the final switchover extends the exposure to plain reads. His suggestion: "could we check d_is_reg() ahead of the dentry_open()?"

3. Mount-crossing and export revalidation silently dropped

The old nfsd_lookup_dentry() went through nfsd_mountpoint() and nfsd_cross_mnt(), revalidating the export it crossed into. The new path is "a plain one-component lookup" that composes the filehandle against the parent export:

"Bind-mount one regular file over another inside an export and the new path hands back the covered file instead of the mounted one, with no check_nfsd_access() on the real target."

He scopes it honestly — "Narrow, since only file-over-file mounts reach it (a directory trips the isreg check)" — but flags that "the behavior did change," i.e. this is a silent semantic regression in access control for a corner case.

Where things stand

Chuck closes by noting the fixes may not all live in 14/14:

"Actually some of the suspect logic is added in earlier patches, only to be exposed by this final switchover patch, so I'll wait for a re-roll."

So the thread ends (for this week) with the v2 series effectively NACK'd pending a v3 that must:

  1. Make mnt_want_write() conditional on O_CREAT in do_lookup_open().
  2. Check d_is_reg() before calling dentry_open(), restoring the pre-open type gate.
  3. Restore mount-crossing / export revalidation (or explicitly justify its removal) for the file-over-file bind-mount case.

No reply from Neil Brown landed inside this week's window; the ball is in his court to re-roll the series. Given the prior RFC→v2 cadence and the fact that two of the three issues trace back to earlier patches in the same series, expect a v3 that touches more than just 14/14.

Why it matters for NFS server users

  • Read-only exports on read-only filesystems (ISO images, squashfs appliances, ZFS/Btrfs snapshots served over NFS) would have started failing plain O_RDONLY opens with -EROFS — a user-visible regression that testing missed because the common case is a writable mount.
  • Server availability: the FIFO/device-node pinning issue is a trivially triggerable resource-exhaustion path against the nfsd thread pool, holding a directory lock while blocked.
  • Access control: dropping check_nfsd_access() on the real target for file-over-file bind mounts is a (narrow) authorization bypass surface that maintainers will not want in mainline.
