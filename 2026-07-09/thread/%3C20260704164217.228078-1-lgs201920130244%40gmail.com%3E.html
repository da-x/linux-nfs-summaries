NFS client: one-line fix for delayed delegation return list (follow-up to Jan rework)

Summary

NFS client: a one-line bug fix for delayed delegation returns

This week's activity on this thread is brief but pointed: a single patch from Guangshuo Li that plugs a hole left open by an earlier delegation-return rework. It is squarely a bug fix in the NFS client (fs/nfs/delegation.c), not a new feature or protocol change — and it lands as a direct follow-up to work Christoph Hellwig did back in January.

The patch

The submission is a minimal, surgical change — one line in fs/nfs/delegation.c (1 insertion, 1 deletion). Li frames the problem precisely:

"The delayed delegation return handling added a separate delegations_delayed list to keep delegations whose return needs to be retried later. The delayed list is then spliced back to delegations_return by nfs_server_clear_delayed_delegations(), which also causes the state manager to retry the delegation return."

But the plumbing was half-wired:

"However, nfs_end_delegation_return() still moves delayed delegations to delegations_return instead of delegations_delayed. As a result, the new delayed list is never populated, nfs_server_clear_delayed_delegations() always returns false, and NFS4CLNT_DELEGRETURN is not set again to drive a retry."

The fix restores the intended flow:

"Move delayed delegations to delegations_delayed so that the delayed return path can splice them back to delegations_return and schedule the retry as intended."

It carries a Fixes: tag pointing at commit 4039fbedcbcb ("NFS: fix delayed delegation return handling").

Where this came from (brief bridge)

The Fixes: target is the seventh patch in Christoph Hellwig's January series, delayed delegation return handling fix. In that cover letter Hellwig explained he was responding to a report from Chris Mason about the "add a LRU for delegations" series, and admitted the difficulty of reaching this code path:

"Note that I could not trigger the delayed delegation handling naturally and had to add crude error injection to force it."

That last detail is worth keeping in mind: the very path Li's patch repairs was hard to exercise in the first place, which helps explain how a stale list_move target could slip through. Hellwig's original PATCH 7/7 introduced the dedicated delayed list and fixed a missing spin_unlock, but — per Li's analysis — left nfs_end_delegation_return() pointing at the wrong list, so the new mechanism was effectively dead on arrival: the delayed list never filled, the clear helper always returned false, and the state manager was never re-armed to retry.

Status this week

The thread is currently just the patch itself — no maintainer or reviewer replies have landed in this window yet, so there is no discussion of alternatives or a recorded conclusion beyond Li's own rationale. The technical argument stands on its own: a clear root cause (wrong destination list), a concrete consequence (retry never scheduled), and a one-line remedy that reactivates the delayed-return retry path. Given how hard Hellwig found it to trigger this code, expect the review to hinge on whether anyone can reproduce the lost-retry symptom before merging.

Bottom line: a small but meaningful NFS client correctness fix — restoring the delegation-return retry mechanism that a January refactor left inert.
