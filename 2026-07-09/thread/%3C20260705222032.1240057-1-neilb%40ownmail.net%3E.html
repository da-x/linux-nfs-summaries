nfsd: NeilBrown's v2 refactor of nfs4_create_file() lands review from Jeff Layton

Summary

Overview

This week (ending 2026-07-09) saw the second iteration of NeilBrown's large-scale refactoring series for nfsd4_create_file() in the Linux NFS server, along with a focused review round from Jeff Layton. The series is primarily a refactor that prepares nfsd to switch to a new VFS interface (vfs_lookup_open()), but it also contains a genuine bug fix (patch 01) for how client-provided attributes are handled on NFS4_CREATE_EXCLUSIVE4_1 opens.

The Patch Series (v2)

NeilBrown posted PATCH v2 00/14 on July 5, explaining that the series re-arranges nfsd code to share more with the VFS lookup_open() path:

"nfs4_create_file() duplicates knowledge about opening a file which exists in the VFS, mostly in lookup_open(). It does use dentry_create() which shares some code, but there is more code that could be shared."

The v2 series addresses issues flagged by sashiko.dev and goes further than v1 by completing all nfsd-side changes. NeilBrown noted a known trade-off:

"Of particular interest is that for open/create we now get pre/post attributes OUTSIDE of the locked region, so we cannot tell the client that they are atomic. This is a slight regression in that it may require the client to revalidate the directory contents more often."

The 14 patches progress from small cleanups (moving fh_want_write(), removing a "subtle" goto difference between EXCLUSIVE and EXCLUSIVE4_1) through structural changes (open-coding nfsd4_vfs_create(), reducing lock ranges) to the culminating patch that extracts do_lookup_open() as a standalone function and uses it for both creating and non-creating opens.

Key Bug Fix: EXCLUSIVE4_1 Attributes Silently Dropped

Patch 01 is the most significant correctness fix in the series. NeilBrown identified that when a file is created via NFSv4.1 NFS4_CREATE_EXCLUSIVE4_1, client-provided attributes were being silently discarded because the code was originally written for NFSv3 (where exclusive creates never include attributes):

"When it was updated for v4.1, the fact that an exclusive create CAN include attributes was not handled properly."

Jeff Layton confirmed this was a real oversight: he replied with "Nice catch. I wonder what we've been missing (if anything) all this time?" and added a Reviewed-by tag.

The Delegation Recall Debate (Patch 06)

The most substantive technical discussion centered on patch 06, which changes the EXCLUSIVE create path to let VFS report whether a file was actually created (via FMODE_CREATED) rather than assuming it was, and consequently opens the file even in EXCLUSIVE cases where the file already exists.

Jeff Layton raised a concern about side effects: he wrote:

"Do we really want a successful open in the EXCLUSIVE cases? Opens have side effects (notably, that they can cause delegation recalls). If you have two racing clients creating a file, the first gets an open and write delegation and then the second ends up immediately causing a delegrecall for the first, even though it may never touch the file again after the OPEN fails."

He suggested keeping O_EXCL in those cases and re-driving the open without it only if the verifier matched.

NeilBrown responded with a detailed analysis of the re-export scenario, explaining that the alternative (keeping O_EXCL and retrying) would cause "4 setattrs altogether" when an intermediate NFS server is involved, and that retransmits would fail even if the verifier was still correct. He argued the delegation recall concern was mitigated in practice:

"If the app checks for then name before trying the O_EXCL open, then the delegation would not get recalled because the OPEN wouldn't be tried."

He proposed a compromise: "Maybe doing a lookup first when the exported fs is NFS would be an OK compromise."

Jeff Layton conceded on July 7:

"I guess it shouldn't happen often, since we do check d_really_is_negative() prior to calling nfsd4_vfs_create(). Given that, let's go with the scheme you've got here. We can always revisit it if this turns out to be more of an issue."

Other Review Notes

  • Patch 02 (replacing fh_fill_both_attrs() with fh_fill_post_noop()): Jeff acknowledged the loss of atomic pre/post attributes: he noted "The loss of atomic post-op attrs is lamentable, but it is in service of a higher cause!" and gave Reviewed-by.

  • Patch 13 (separating VFS-specific code): Jeff spotted a type mismatch — he asked "Should this compare against nfserr_noent rather than NFSERR_NOENT?" NeilBrown acknowledged with "Thanks Claude :-)" (crediting his AI assistant for the catch).

  • Patches 03, 04, 05, 07, 09, 10, and 11 all received clean Reviewed-by tags from Jeff Layton without further discussion.

Status and Outlook

As of the end of this window, the series has a full round of positive review with one open item (the nfserr_noent vs NFSERR_NOENT fix in patch 13) and the delegation-recall concern resolved by mutual agreement to proceed as-is. The series targets nfsd-testing. NeilBrown indicated his broader goal is to simplify locking changes for other operations (mkdir, link, symlink) once this lands, and that a future vfs_lookup_open() VFS interface will allow a clean switch from the current do_lookup_open().

Classification

  • Primary: Refactor / code reorganization (preparing for new VFS interface)
  • Secondary: Bug fix (patch 01 — EXCLUSIVE4_1 attributes dropped since NFSv3-to-v4.1 port)
  • Tertiary: Performance/locking improvements (reduced directory lock range, reduced want-write range)
