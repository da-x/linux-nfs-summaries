DEPT v19: Wait/Event Deadlock Tracker Lands with PG_locked and SUNRPC Attention

Summary

DEPT v19: A 40-Patch Push to Mainline, With Fresh Scrutiny on Folio Locks and Rust

Classification

This is a new kernel feature — Byungchul Park's (SK hynix) 40-patch DEPT (DEPendency Tracker) series, posted as v19 on July 6. It is not an NFS bug fix in itself, but it carries one directly NFS-relevant change: a SUNRPC patch that relocates struct rcu_head inside struct rpc_xprt, and its overall mission — catching wait/event deadlocks that Lockdep structurally cannot see — targets exactly the RPC completion, PG_locked, and writeback paths that NFS client developers live in.

Bridging Prior Weeks (Briefly)

The DEPT series has been under iterative review since December 2025 (v18). Last week's adjacent thread saw Park make a strategic scoping decision: he deferred the recover-events-tracking patches (33/42–35/42) out of the initial series, stating they "unnecessarily complicate the initial DEPT patchset and significantly increase the review burden." That trimming is directly reflected in v19's shape — 40 patches instead of 42, with recover-event support explicitly dropped from this round.

This Week's Activity (July 3–9)

The entire thread activity this week landed on Monday, July 6 and spilled into Tuesday, July 7:

  1. Park posted the full v19 series — 40 patches covering the core DEPT engine, lockdep/IRQ integration, annotations for wait_for_completion(), swait, waitqueues, hashed-waitqueues, DMA fences, RCU, mmu notifiers, PG_locked and PG_writeback tracking, a SUNRPC fix, percpu sizing adjustments, a Rust completion helper, documentation, and a unit test.
  2. Matthew Wilcox (Red Hat) replied to patch 22/40 (PG_locked tracking), raising substantive false-positive/false-negative concerns about embedding pg_locked_wgen in struct page.
  3. Park responded the next day with a detailed technical rebuttal and a commitment to follow-up work on classification.
  4. Gary Guo (Rust for Linux) replied to patch 31/40 (unique dept_key per wait_for_completion() caller), flagging that the Rust helper path would collapse all Rust callers into one shared key, defeating the false-positive avoidance the patch is trying to achieve.

The Cover Letter's Core Argument

Park's cover letter v19 00/40 frames DEPT as filling a fundamental Lockdep blind spot:

"Lockdep has been our trusted deadlock detector for two decades, but it has a fundamental blind spot: it tracks lock acquisition order, not the actual waits and events that cause deadlocks."

He walks through a three-context folio/mutex interleaving that Lockdep cannot see, then positions DEPT as answering "What is this context waiting for, and what event will wake it up?" The letter also directly addresses the elephant in the room — lockdep's reverted cross-release experiment:

"Cross-release (commit b09be676e0ff2) attempted to extend lockdep with wait/event tracking. It found real bugs but introduced false positives that masked further issues. DEPT learns from that experience with a cleaner design and flexible reporting that makes false positives less disruptive."

And on the merge-now question:

"Now. The annotation journey requires mainline collaboration. Lockdep didn't become useful overnight — it grew through maintainer contributions. DEPT needs the same path."

The series is marked EXPERIMENTAL in Kconfig, and Park lists three real-world deadlocks DEPT has already caught (Sakura/igalia/LG links) as evidence that this is "beyond theory."

Key Technical Arguments This Week

1. The PG_locked tracking debate (Wilcox ↔ Park) — the most substantive technical exchange of the week.

Matthew Wilcox raised a concrete false-positive/false-negative scenario: folios F1 and F2 in mapping M1 are correctly locked in order F1→F2 (writeback). After reclaim, the same physical pages reappear in mapping M2 at different indices, where the correct order is now F2→F1. Wilcox's core concern:

"I don't see a part of this patch where we clear pg_locked_wgen when the page is returned to the page allocator. Maybe I missed that."

He argues the dependency should be tracked in the owner of the folio — struct address_space for files, anon_vma for anonymous memory — not in struct page itself:

"I think we should be tracking PG_locked dependencies in the owner of the folio. For files, that would be in the struct address_space."

Park responded with a layered defense:

  • On the stale-wgen concern: "You are right. pg_locked_wgen doesn't get cleared. However, DEPT works this way: ... it's guranteed that pg_locked_wgen has been updated e.i. (1) when DEPT refers to pg_locked_wgen e.i. (2). So I don't think it's a problem."
  • On classification: "I think it's a good point but it's a classification issue. folios owned by struct address_space should be classified to e.g. address_space_class and ones owned by struct anon_vma should be classified to e.g. anon_vma_class. I will work on it to apply the insight you just gave but better do it as follow-up patches since the initial patchset is already too big to get reviewed."
  • On same-class folio ordering (the F1→F2 pattern within one mapping): "DEPT cannot work with it automatically" — it needs a folio_lock_nested()-style annotation, which Park says he "need[s] to introduce" and that "The work is in progress."

This is the most important open design question for DEPT's usefulness on NFS: page-lock ordering is precisely where NFS client writeback and readahead paths live.

2. The Rust dept_key problem (Gary Guo).

Gary Guo flagged a concrete defect in patch 31/40:

"This will cause Rust code to share the same dept_key, so it will have all the false positives that the change is trying to avoid."

His root-cause analysis: the C side uses function-like macros that define per-caller statics (one dept_key per call site), but the Rust helper rust_helper_wait_for_completion() is a plain function — so every Rust caller funnels through one shared key. He proposes borrowing his existing approach for lock_class_key (a linked lore link) to keep the Rust side as a function while still getting per-caller keys, and asks:

"Is dept_key similar to lock_class_key, where only the address matters?"

Park has not yet replied to this as of the end of the window. This is a real bug in v19 for any Rust-based NFS or networking code that uses wait_for_completion().

3. The SUNRPC fix (patch 37/40) — the one directly-NFS patch.

This is a genuine bug fix triggered by enabling DEPT: with DEPT's debug instrumentation, offsetof(struct rpc_xprt, rcu) exceeds 4096 bytes, tripping kfree_rcu()'s BUILD_BUG_ON. The fix relocates struct rcu_head to the first field of struct rpc_xprt. It carries a Reviewed-by from Jeff Layton (NFS maintainer), which is notable for a patch in a 40-patch series aimed at a different subsystem. The commit message:

"Since kfree_rcu() assumes 'offset of struct rcu_head in a rcu-managed struct < 4096', the offest of struct rcu_head in struct rpc_xprt should not exceed 4096 but does, due to the debug information added by DEPT."

Reported-by: Yunseong Kim. This is the kind of cross-subsystem breakage that only surfaces when a new instrumentation framework is enabled across the whole kernel — and it's already been reviewed by the NFS maintainer.

4. Other notable v19 changes (no in-thread discussion yet):

  • Timeout-aware reporting (patches 15–20): New CONFIG_DEPT_AGGRESSIVE_TIMEOUT_WAIT Kconfig lets users suppress reports involving timed-out waits, which Park notes "don't actually cause deadlocks" but are "worth informing the circular dependency for some cases where, for example, timeout is used to avoid a deadlock."
  • External wgen (patch 21): For classes like PG_locked where embedding a full dept_map in every struct page is too expensive, DEPT now supports a minimal timestamp-based "wgen" instead.
  • RCU dept_key collision fix by Yunseong Kim (patch 34): fixes key collisions between different RCU wait types.
  • Percpu sizing (patch 38): increases PERCPU_DYNAMIC_SIZE_SHIFT when DEPT is enabled on large-PAGE_SIZE architectures, to accommodate the percpu data DEPT adds.
  • Unit test (patch 40): a basic selftest for DEPT itself.

Evolution of the Discussion

The arc this week moved from announcement → immediate technical scrutiny:

  1. July 6, 06:19 UTC: Park posts all 40 patches in one burst.
  2. July 6, 18:06 UTC: Wilcox engages with the most architecturally risky patch (PG_locked in struct page), offering a concrete counter-example and a design alternative (owner-based tracking).
  3. July 7, 02:35 UTC: Park responds with a point-by-point technical defense, concedes the classification improvement is needed, and commits to follow-up patches — but holds the line on the current v19 shape.
  4. July 7, 14:18 UTC: Gary Guo identifies a real defect in the Rust integration path (shared dept_key), proposing a fix pattern from his prior lock_class_key work.

The discussion is still early — only two of the 40 patches have drawn replies, and neither Park nor any maintainer has posted an overall verdict on the series. The Wilcox exchange is the most substantive; the Guo reply is a concrete bug report that will need a code fix before merge.

Significance for NFS Client Development

  • The SUNRPC rcu_head relocation is the only patch with direct NFS-tree impact, and it already has Jeff Layton's Reviewed-by. It's a defensive fix — without it, any kernel built with CONFIG_DEPT fails to compile net/sunrpc/xprt.o.
  • PG_locked tracking (patch 22/40) is where DEPT's value for NFS becomes concrete. NFS client readahead, writeback, and direct-I/O paths all sleep on page locks. The Wilcox/Park exchange identifies the key design gap: per-page wgen vs. per-owner (address_space/anon_vma) classification. Until that's resolved, DEPT's folio-lock deadlock detection will have both false positives (stale wgen across reclaim) and false negatives (same-class ordering within a mapping).
  • The Rust dept_key bug matters for any Rust-based kernel components (including potential future NFS client code in Rust) that use wait_for_completion().
  • No new NFS protocol changes or NFS client bug fixes were introduced this week. The thread is entirely about the DEPT infrastructure and its one necessary SUNRPC accommodation.

Final Conclusions (as of window close)

  • v19 is posted; the series is leaner than v18 (recover-events deferred).
  • One patch (37/40, SUNRPC rcu_head) has NFS maintainer review.
  • Two patches have open technical questions: 22/40 (PG_locked classification — Park committed to follow-up work) and 31/40 (Rust shared dept_key — Guo proposed a fix pattern, awaiting Park's response).
  • No merge decision, no overall series verdict from any maintainer yet. The thread is in the early-review phase.
