NFSv3 O_WRONLY|O_CREAT EACCES: vendor appliance CREATE behavior vs. NFSD, and the UNCHECKED semantics debate

Summary

NFSv3 O_WRONLY|O_CREAT EACCES: the UNCHECKED-semantic dispute over a vendor appliance

Overview

This is a bug-fix / regression-investigation thread on the Linux NFS client, now narrowed to a server-side protocol-conformance question. The core incident: after upgrading from kernel 6.1 LTS to 6.12 LTS, an application doing open(O_WRONLY|O_CREAT) on a pre-existing file began failing with EACCES (permission denied) when the client has write permission on the file but not on the containing directory. This week's two in-window messages — Tian Lan of Jane Street identifying the offending server, and NFS maintainer Chuck Lever supplying the RFC-level analysis — establish that the Linux client is behaving correctly and that the fault lies with a non-conformant vendor appliance.

Bridging prior context (brief)

The thread opened on July 6 when Tian Lan reported that the kernel "would now issue an additional CREATE rpc call to the remote NFS server regardless if the target file pre-exists or not," and that this extra CREATE could return EACCES, failing the whole openat. He traced the behavior change to commit 7c6c5249f061 ("NFS: add atomic_open for NFSv3 to handle O_TRUNC correctly.") and asked whether it was intentional, since it "breaks existing user's application code." Trond Myklebust — the thread root of this summary — replied that NFSv3 CREATE "is supposed to ignore the directory permissions if the file already exists," and asked which server was in use. This week's messages are the answer to that question, plus the protocol analysis it triggered.

This week's activity (July 7)

Tian Lan identifies the server and frames the divergence

In his July 7 reply, Tian confirms the permission error was reproduced "against a vendor appliance," while the same test against Linux NFSD produced no errors — "due to differences in behavior from the CREATE RPC implementation." He lays out the contrast crisply:

NFSD behavior

  • CREATE RPC (UNCHECKED mode) returns the filehandle of the existing file along with the file's attributes

Vendor appliance

  • CREATE RPC (UNCHECKED mode) always attempts to create a new file and returns the new filehandle. This explains why we are seeing permission denied error from openat syscall.

He quotes RFC 1813 ("UNCHECKED means that the file should be created without checking for the existence of a duplicate file...") and concedes, "It seems like the vendor's implementation matches more closely to what the 'standard' describes, but the behavior might not be what a normal user would expect. I guess there is no win-win situation here."

Tian also pressed on the client-side design: he asked whether the kernel should always do a LOOKUP before deciding to send CREATE, noting that in the current code "the lookup happens after the atomic_open which does the CREATE rpc" (citing fs/namei.c).

Chuck Lever settles the interpretation with RFC 7530

In his July 7 reply, Chuck Lever reframes the question using NFSv4's clarifying text rather than RFC 1813's ambiguous wording:

"Compare RFC 7530's UNCHECKED4. It says explicitly that if the object already exists, a non-exclusive create does not recreate it. The existing object is used and the supplied attributes are applied."

He then states his position directly:

"IMHO the correct interpretation, the one consistent with the rest of NFSv3, with NFSv4's clarifying text, and with POSIX, is NFSD's, not the vendor's. UNCHECKED governs error-vs-no-error on a duplicate, not recreate-vs-reuse."

Rather than let it end at opinion, Lever pointed to concrete ways to confirm: look for an RFC 1813 erratum or WG/implementor-list guidance requiring re-creation, and — most decisively — "It would also be sensible to check how Solaris NFSv3 behaves, as it is a reference implementation for RFC 1813."

Key technical arguments

  • The client change was deliberate and race-safe. Commit 7c6c5249f061 made the NFSv3 client send CREATE unconditionally on O_CREAT opens (via atomic_open) to handle O_TRUNC correctly. Trond had already noted that even the old LOOKUP-then-CREATE path "had a potential for races that could have caused the client to send it against an existing file." The new design is more correct; it simply exposes server non-conformance that was previously hidden.
  • UNCHECKED means "don't error," not "recreate." Lever's central argument is that UNCHECKED governs whether a duplicate is an error, not whether the object is replaced. NFSD's reuse-and-apply-attributes behavior matches RFC 7530's UNCHECKED4, POSIX open(O_CREAT), and the rest of NFSv3.
  • The vendor appliance is the outlier. Its "always create fresh, return a new filehandle" behavior triggers EACCES when the client lacks directory write permission — exactly the failure Tian observed.

Final conclusions (as of this week)

  1. The Linux NFSv3 client's unconditional-CREATE behavior is correct and should not be reverted; it is the server-side deviation that is at fault.
  2. NFSD's UNCHECKED semantics (reuse existing file, apply attributes) are the conforming interpretation, backed by RFC 7530's clarifying text.
  3. The remaining empirical question — does the RFC 1813 reference implementation (Solaris) agree with NFSD? — was left open at Lever's suggestion and is answered in a later message in this thread (see the companion summary), where Tian reports that Solaris 11.4 behaves like Linux NFSD, confirming the vendor appliance deviates.
  4. No client-side patch is expected. The workaround (stripping O_CREAT when opening a known pre-existing file for write) remains necessary against this specific vendor appliance until the vendor fixes its CREATE implementation.

Classification & impact

  • Type: Bug fix / regression investigation — a deliberate NFSv3 client improvement (7c6c5249f061) exposing a latent server-side protocol non-conformance.
  • NFS client development relevance: The atomic_open path is validated as the right design (it removes lookup/create TOCTOU races). The fix belongs on the server side; the client is not at fault.
  • User impact: Applications doing open(O_WRONLY|O_CREAT) on pre-existing files in directories where the user lacks write permission will keep failing against this vendor appliance on 6.12+ kernels until the vendor corrects its CREATE behavior.
