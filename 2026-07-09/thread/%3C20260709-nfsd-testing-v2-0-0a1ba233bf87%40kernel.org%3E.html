nfsd: copy offload fixes (v2) — lifetime bugs in inter-server COPY

Summary

nfsd: copy offload fixes (v2) — a 10-patch cleanup of inter-server COPY lifetimes

This week's activity on the thread is essentially one event: Jeff Layton posted a ten-patch v2 series titled "nfsd: copy offload fixes" on Thursday, July 9, followed shortly by a single review reply from Chuck Lever on patch 03/10. The series is squarely about the NFSv4.2 server (nfsd) side of inter-server copy offload — COPY, COPY_NOTIFY, OFFLOAD_CANCEL/OFFLOAD_STATUS, and CB_OFFLOAD — rather than the client, though it matters to client developers because several of the bugs are remotely triggerable by any authenticated NFSv4.2 client.

What kind of change is this?

It is a bug-fix series with a refactoring tail. In the cover letter Layton frames the provenance unusually honestly for a kernel patch set:

"These patches fix bugs in inter-server copy offload code noticed by LLM inspection. The first 3 were found via kres, and the next 5 were problems that were flagged in agentic review of those patches and some via testing."

The individual fixes carry Assisted-by: tags for Claude models (claude-opus-4-7/4-8), and Chris Mason's patch 01/10 is attributed to Meta. The v2 changes over v1 add the five neighboring fixes found during testing/review, fix an error return for NL_NAME/NL_URL netlocs, split nfsd4_copy into transient and durable objects, and rework COPY stateids onto the normal nfs4_stid infrastructure. Layton also teased: "As part of this work, I've had Claude cook up a set of pynfs tests for COPY that I'll post separately."

The bug fixes (patches 01–07)

The first three patches fix bugs found via kres:

  • 01/10 (Chris Mason): a publish race in nfs4_init_cp_state(). The cpntf entry was inserted into the s2s_cp_stateids IDR before being linked onto the parent's sc_cp_list, so a racing OFFLOAD_CANCEL could "reach manage_cpntf_state() -> _free_cpntf_state_locked() and do list_del() on the zeroed list_head, oopsing the server." The fix folds the type assignment and list_add() into the same critical section as idr_alloc_cyclic(), and switches to list_del_init() so a stale unlink is a no-op.
  • 02/10: the biggest fix — a use-after-free in async copy cancel/shutdown paths. Layton enumerates four distinct lifetime problems: find_async_copy() bumping the refcount but leaving the copy on clp->async_copies so the reaper could race; the STOPPED bit being set before the kthread's final uses of nf_dst; copy_task never being pinned (so kthread_stop()'s get_task_struct() could touch a freed task); and co_cb holding only a client reference while CB_OFFLOAD was in flight. The fix reworks teardown as a whole: unlink under async_lock, give the kthread its own reference, pin the task_struct, take a copy reference for the callback, and use smp_load_acquire() on cp_clp.
  • 03/10: a stale IDR entry for async COPY. Because nfs4_init_copy_state() ran before dup_copy_fields(), the IDR pointed at the per-COMPOUND request buffer, which "is reused by the next request" — so any IDR walker (the laundromat, manage_cpntf_state()) could dereference garbage and even kfree() it.

Patches 04–07 fix bugs found via agentic review and testing:

  • 04/10: the cpntf stateid was fully initialized only after being published to the IDR, so a racing OFFLOAD_CANCEL with a crafted clientid and guessable so_id could free it out from under the caller — "turning the caller's subsequent cpn_cnr_stateid read ... into use-after-free."
  • 05/10: an ownership hole — "any authenticated NFSv4.2 client could cancel and free another client's copy-notify stateid" because the lookup key is cyclically allocated (guessable) and the embedded clientid is the fixed per-net nn->s2s_cp_cl_id. The fix compares cp_p_clid against the requester's cl_clientid and returns nfserr_bad_stateid on mismatch.
  • 06/10: a revoke-path UAF affecting all three revoke paths (parent-stid drain, OFFLOAD_CANCEL, laundromat expiry): dropping the membership reference without unlinking left the entry discoverable with its refcount already consumed — "a KASAN-detectable use-after-free at the reader's nfs4_put_cpntf_state()." The fix adds revoke_cpntf_state_locked(), which unhashes from the IDR and sc_cp_list first, deferring the final free to any holder.
  • 07/10: a small protocol-correctness fix — nfsd4_decode_nl4_server() returned nfserr_bad_xdr for NL4_NAME and NL4_URL netlocs, but "Those forms are well-formed XDR, so BADXDR is misleading -- the request is unsupported, not malformed." Now it decodes/discards them and returns NFS4ERR_NOTSUPP.

The refactoring tail (patches 08–10)

The last three patches address what Layton calls "the underlying cause of most of these bugs":

  • 08/10 splits struct nfsd4_copy into a transient per-COMPOUND object and a durable struct nfsd4_async_copy that "never points into the request buffer." He calls it a "Mechanical split, no intended behavioral change; a step toward folding the copy stateids into the common nfs4_stid infrastructure."
  • 09/10 promotes the async COPY offload stateid to a first-class nfs4_stid (SC_TYPE_COPY) allocated from the client's cl_stateids, which "makes the stateid per-client by construction rather than relying on a guessable cyclic id in a global table." It carefully honors RFC 7862 §4.8 (stateid valid only for COPY/OFFLOAD_CANCEL/OFFLOAD_STATUS/CB_OFFLOAD, hidden from TEST_STATEID/FREE_STATEID) and sets si_generation to 1 since the seqid "MUST NOT be zero."
  • 10/10 drops the now-dead COPY-vs-COPYNOTIFY type-distinguishing machinery from the s2s stateid IDR. "No functional change."

Review so far: Chuck Lever flags two new problems in 03/10

The only reply this week came from Chuck Lever, who reported that further LLM review (Sashiko, and gpt-5.6-sol for one of them) found issues the patch series itself introduced or missed:

"- [Critical] Async copy cancellation paths remove the copy from clp->async_copies and free the async_copy object, but fail to call nfs4_free_copy_state(). This leaks the IDR entry in nn->s2s_cp_stateids and leaves it pointing to freed memory, causing a remote Use-After-Free (UAF) DoS." "- [High] Reordering dup_copy_fields() before nfs4_init_copy_state() leaves async_copy->cp_res.cb_stateid uninitialized, causing the server to send an invalid (all-zero) stateid in the CB_OFFLOAD callback."

He also offered a minor style note on patch 03/10: "The new code comment here is a design breadcrumb. Probably not useful to carry it as part of the code, but YMMV."

Where things stand

As of Friday evening (UTC), the series has one round of review with two substantive objections pending — both in/near patch 03/10 — and no ACKs or further discussion yet. Given that patches 08–10 rework the stateid machinery that Lever's first complaint targets, a v3 will likely need to reconcile the cancellation-path nfs4_free_copy_state() call with the new nfs4_stid model (where nf4_put_copy() drops the stid reference), plus fix the cb_stateid initialization ordering. Worth watching for Layton's promised pynfs COPY test suite as well, which would be a notable addition to NFS server testing coverage.
