NFSv4.2 listxattr size-accounting fix (NULL deref + undercount) lands via NFS tree

Summary

NFSv4.2: fixing nfs4_listxattr size accounting

What it is

This week's thread is a bug-fix discussion, not a feature or protocol change. It concerns the NFSv4.2 client's extended-attribute listing path in fs/nfs/nfs4proc.c, specifically how the remaining buffer size (left) is accounted around the security_inode_listsecurity() hook. The fix addresses two symptoms of one root cause: a kernel NULL pointer dereference on the size-query call, and an undercounted size that leads to -ERANGE on the follow-up real call.

Background / origin

The bug was introduced by commit f71ece9712b7 ("security,fs,nfs,net: update security_inode_listsecurity() interface"), which changed the LSM hook so it now decrements the remaining size even when the buffer pointer is NULL. Achilles Gaikwad filed the initial report on 2026-07-03 with a concrete oops:

"A call to listxattr() with a buffer size = 0 returns the actual size of the buffer needed for a subsequent call. On an NFSv4.2 mount this triggers the following oops" — the original patch

The crash trace pointed at _copy_from_pages via nfs4_xattr_alloc_entry, and the diagnosis was that 'left' underflows to a huge size_t value so nfs4_listxattr_nfs4_user() "treats the NULL buffer as real, ending in a NULL dereference."

Evolution of the discussion

  1. v1 (Jul 3) — Gaikwad's minimal fix: declare left as ssize_t and pass a zero length to nfs4_listxattr_nfs4_user() when the buffer is NULL.

  2. Paul Moore's pushback (Jul 6) — The SELinux maintainer asked for a cleaner structure, suggesting the security-hook consumption be measured with a scratch variable rather than the existing size - error - left formula:

    "I wonder if it would be better associate the handling code with the security_inode_listsecurity() call a bit more closely?" — Paul Moore's reply

  3. v2 (Jul 7) — Gaikwad retitled the patch to "fix nfs4_listxattr size accounting" and explained that the v1 fix only masked a deeper accounting bug:

    "security_inode_listsecurity() does not return the number of bytes it added to the list, so the code derived it as 'size - error - left'. That is also wrong in the size-query case... Thus, the query result comes up short by exactly that contribution (e.g., 'system.nfs4_acl' on a mount with ACL support), and a caller that allocates the returned size gets -ERANGE on the subsequent call." — PATCH v2

    The v2 changes: use a scratch variable to track security label size directly, only decrement left when a buffer is present, and drop the now-unneeded NULL-buffer special case.

  4. Review & routing (Jul 7) — Paul Moore gave a Reviewed-by but noted he couldn't fully test it due to an unrelated NFS regression from the v7.2 merge window:

    "Unfortunately my testing was unsuccessful due to an NFS problem that started with the v7.2 merge window that I haven't had the time to bisect yet." — Paul Moore's review

    NFS maintainer Anna Schumaker confirmed routing:

    "Yeah, we'll send it through the NFS tree. I'll be curious to hear what problem you're hitting, and what patch is the culprit once you do that bisect!" — Anna Schumaker

    Paul offered the selinux-testsuite NFS tests as a repro vehicle, and both he and Anna expressed interest in the bisect result.

  5. Testing cross-check (Jul 8–9) — Stephen Smalley ran the SELinux NFS testsuite on F44 / v7.2-rc1-based selinux/dev:

    "They seem to pass for me with and without the patch (they don't exercise listxattr AFAIK)." — Stephen Smalley

    Paul clarified his failures were on vanilla kernels:

    "They work for me on vanilla v7.1 and fail somewhere before vanilla v7.2-rc1 (still bisecting). I wonder if there is an interaction problem with a recent userspace update." — Paul Moore

    Smalley confirmed the likely userspace angle:

    "I was on F44, so yes, it could be a difference in e.g. coreutils or other userspace on rawhide that is tickling this particular bug." — Stephen Smalley

Final conclusions

  • The fix is agreed and routed through the NFS tree (Anna Schumaker's confirmation), with a Reviewed-by from Paul Moore. The patch corrects both the NULL-deref oops and the silent size undercount in one coherent change to nfs4_listxattr's accounting logic.
  • A secondary, open thread: Paul Moore is still bisecting an unrelated NFS regression that appeared between v7.1 and v7.2-rc1, which surfaced while he was testing this fix. The discussion hints it may involve a userspace interaction (Rawhide vs. F44), but no conclusion was reached within the week.

Key technical takeaway for NFS client developers

The security_inode_listsecurity() interface change (f71ece9712b7) altered the contract around the left parameter: the hook now consumes from left even in the NULL-buffer (size-query) case, and it does not report how many bytes it added. Any caller that derives "bytes consumed by the security label" via subtraction (size - error - left) will undercount in the query path. The correct pattern is to use a scratch copy of left around the hook call and only apply the delta when a real buffer exists.
