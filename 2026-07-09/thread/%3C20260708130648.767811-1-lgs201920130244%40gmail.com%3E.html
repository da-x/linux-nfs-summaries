fhandle: Patch fixes NULL pointer dereference in capable_wrt_mount() for detached mounts

Summary

fhandle: Handle Detached Mounts in capable_wrt_mount()

Overview

This week, a single-patch thread appeared on the linux-nfs list addressing a bug fix in the kernel's file handle (fhandle) subsystem — code that underpins NFS client mount operations via mount(2) with MNT_DETACH and related syscalls. The patch was submitted by Guangshuo Li on July 8, 2026.

The Bug

The issue is a NULL pointer dereference in capable_wrt_mount() within fs/fhandle.c. It is a follow-on to an earlier fix (commit 40ab6644b996, "fhandle: fix UAF due to unlocked ->mnt_ns read in may_decode_fh()") that had introduced RCU protection around the lockless read of mount->mnt_ns in may_decode_fh().

As Guangshuo Li explains in the patch description:

"That prevents the namespace object from being freed while it is being used, but it does not guarantee that mount->mnt_ns is non-NULL."

The race window: a mount can be detached concurrently after is_mounted() has checked the field and before capable_wrt_mount() reads it again. When this happens:

"If capable_wrt_mount() observes the detached state, it currently dereferences the NULL namespace pointer while passing mnt_ns->user_ns to ns_capable()."

The Fix

The patch is minimal — just 3 lines added to fs/fhandle.c. It treats a detached mount as not capable for the permission relaxation path:

"Treat a detached mount as not capable for this permission relaxation and return false when the RCU-protected mnt_ns read yields NULL."

This is a straightforward defensive check: if the RCU-protected read of mnt_ns returns NULL (indicating the mount was detached), the function simply returns false rather than proceeding to dereference the pointer.

NFS Client Relevance

While this patch touches fs/fhandle.c (a core VFS file, not strictly NFS code), it is directly relevant to NFS client development because the fhandle subsystem is the kernel's mechanism for encoding and decoding mount references — the same path used when NFS clients perform operations like mount(2), umount(2) with MNT_DETACH, or fsopen/fsconfig sequences that involve file handle manipulation. A NULL pointer dereference here would be a local denial-of-service (kernel panic/Oops) exploitable by any unprivileged user who can trigger concurrent mount detachment while an fhandle operation is in flight.

Thread Status

As of the end of this reporting window (2026-07-09), the patch had been submitted but no replies were yet visible within the week. A follow-up reply from Christian Brauner exists in the thread (dated 2026-07-22) but falls outside this week's scope and will be covered in a future summary.
