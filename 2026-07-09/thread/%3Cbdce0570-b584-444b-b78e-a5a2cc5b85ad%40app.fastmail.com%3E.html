lockd NLM_SHARE refcount abandoned for idempotent bitmap after UDP retransmit concerns

Summary

lockd: NLM_SHARE access/deny tracking — refcount approach rejected, idempotent bitmap adopted

Type: Bug fix (NFSv3/NLM server-side share-state handling in fs/lockd), with a protocol-interpretation argument at its core.

The one message this week

This thread carries a single in-window message: Oscar Ou's reply to Chuck Lever's Jul 01 review of the v2 patch. It is a decisive turning point in a multi-week exchange: Oscar concedes the reference-count design is fundamentally incompatible with NLM's retransmit semantics and commits to rebuilding the fix around a per-(access, deny) bitmap.

Bridge from prior weeks (brief)

The discussion began on Jun 30 with Oscar's original patch, which introduced per-value refcounts for NLM_SHARE access/deny modes to stop a later SHARE from overwriting an earlier one and a single UNSHARE from freeing the whole entry. Chuck's Jun 30 review raised early concerns; Oscar posted v2 on Jul 01, and Chuck's Jul 01 review (the thread root) delivered the substantive technical objection that this week's message answers.

The core technical argument

Chuck's review hinged on one invariant: NLM has no duplicate reply cache (DRC), so every request handler must be idempotent under retransmission. He pointed at nlmsvc_dispatch(), which "runs the procedure directly for every request that arrives, with nothing to absorb a retransmit," and noted that LOCK/UNLOCK/CANCEL/FREE_ALL all satisfy this. The refcount broke it in both directions:

  • Stale reservation (SHARE side): a replayed SHARE over UDP increments the bucket a second time, so a single matching UNSHARE leaves s_access_counts[3] = 1, and "the entry is never freed" — leaving a stale share that denies later conflicting opens.
  • Premature release (UNSHARE side): a retransmitted UNSHARE decrements past the point where the client still holds an open, so "a conflicting open from another owner would now be granted."

Chuck proposed tracking the set of held (access, deny) pairs in a u16 mask — one bit per (access << 2 | deny) — because "setting or clearing a bit is idempotent, so a replayed SHARE or UNSHARE lands on the same mask." He flagged the tradeoff: two opens with an identical (access, deny) pair collapse to one bit, losing the count.

This week's resolution

Oscar accepted every point and confirmed the protocol reading that makes the bitmap safe. On the RFC 1813 question he wrote:

"RFC 1813 is silent on repeat semantics for SHARE / UNSHARE, and section 4.5 explicitly treats non-idempotent requests as something a reply cache has to protect, which lockd doesn't run for NLM. So collapsing identical (access, deny) opens from one owner into a single bit stays inside the protocol, and it buys back the idempotency the other NLM handlers already assume."

He laid out the concrete shape he would use for v3:

#define LOCKD_FSH_BIT(a, d) BIT(((a) << 2) | (d)) SHARE: share->s_held_mask |= LOCKD_FSH_BIT(access, mode); UNSHARE: share->s_held_mask &= ~LOCKD_FSH_BIT(access, mode);

with s_access/s_mode recomputed as the union over set bits and the entry freed once the mask is zero. He also acknowledged Chuck's process note that a revised series must go out as its own top-level thread — "Understood, thanks -- v3 will go out as its own top-level thread with a [PATCH v3] subject."

Final outcome (bridged forward)

Oscar followed through the same day: he posted the v3 patch as a new top-level thread, retitled "lockd: preserve multiple NLM_SHARE grants from the same owner," which replaced the refcount with the u16 bitmap and added access/deny arguments to nlmsvc_unshare_file(). Notably it carries no Fixes: tag — Oscar explained the fix "depends on the xdrgen regeneration to reject out-of-range fsh_access / fsh_mode on the wire, so a Fixes: tag would mislead -stable backporters." Chuck then applied it to nfsd-testing (commit c8c45fb61a5ff3eb786e4aa434b534b605ab657e), closing the loop.

Bottom line

A proposed fix for a real NFSv3/NLM share-state bug (multiple opens from one owner clobbering each other's access/deny modes, especially visible to Windows-style clients) was rejected in favor of an idempotent bitmap after the maintainer showed that per-value refcounts violate NLM's retransmit-safety invariant over UDP. The discussion is a clean example of protocol-conformance reasoning (RFC 1813 §4.5 on non-idempotent requests and reply caches) driving a design decision, and it resolved within days with the v3 bitmap accepted into nfsd-testing.
