NFS/localio: fix nfs_local_dio_misaligned tracepoint offset

Summary

NFS/localio: fix nfs_local_dio_misaligned tracepoint

This week's activity in this thread is brief but pointed: a single, surgical bug-fix patch from Mike Snitzer to correct a misleading tracepoint in the NFS local I/O (localio) direct-I/O path. No replies landed within the reporting window; the only follow-up so far is an out-of-window question from maintainer Anna Schumaker.

The bug fix

The thread is squarely about a bug fix — specifically, an observability defect in the NFS client's local I/O code (fs/nfs/localio.c), not a protocol change or new feature. On Wednesday, July 8, Snitzer posted a one-line-plus patch titled "NFS/localio: fix nfs_local_dio_misaligned tracepoint."

The defect: when nfs_local_iters_setup_dio() fires the trace_nfs_local_dio_misaligned() event, its stated purpose is to highlight that the middle segment of a direct I/O write is misaligned. Yet the code was passing local_dio->start_len as the @offset argument — almost certainly, in Snitzer's words, "a cut-n-paste bug from the preceding nfs_local_iter_setup() call that passes local_dio->start_len."

The fix replaces that value with local_dio->middle_offset and, per Snitzer, "calculate[s] the start segment's offset rather than assume." The change is small — two files touched (fs/nfs/localio.c and fs/nfs/nfstrace.h), five insertions against two deletions — but it corrects what the tracepoint actually reports to users of ftrace.

Before/after evidence

Snitzer backed the patch with concrete before/after traces, which make the fix tangible. In the buggy output, the nfs_local_dio_misaligned event reported offset=329 — a value that corresponds to the start segment length rather than where the misaligned middle segment actually begins:

"nfs_local_dio_misaligned: fileid=00:33:1286 fhandle=0xf1f7c10b offset=329 count=1048064 mem_align=4 offset_align=512 start=329+329 middle=1049088+1048064 end=2097152+183"

After the fix, the same event correctly reports the middle segment's true starting offset:

"nfs_local_dio_misaligned: fileid=00:33:1286 fhandle=0xf1f7c10b offset=1049088 count=1048064 mem_align=4 offset_align=512 start=1048759+329 middle=1049088+1048064 end=2097152+183"

The surrounding nfs_local_dio_write event is unchanged in both cases, which underscores that the fix only touches the diagnostic reporting path and not the actual I/O behavior.

Scope and stability implications

Snitzer marked the patch for stable backports with a Cc: stable@vger.kernel.org, signaling that he considers the incorrect tracepoint worth carrying into stable kernels — a reasonable call given that mislabeled trace data can send developers chasing the wrong segment of a direct I/O operation during performance or alignment debugging.

Discussion status

Within this week's window, the thread consists solely of the patch itself; no reviewer has yet weighed in. The first reply arrives later (outside this reporting period), when Anna Schumaker — the NFS client maintainer — asks, "Do you have a fixes tag for this commit?" That question is procedural (stable backports require a Fixes: tag pointing at the offending commit), and it suggests the patch is being taken seriously but has not yet been formally applied as of this week's close.

Bottom line

A clean, well-documented tracepoint fix in the NFS client's localio direct-I/O path. The change is minimal, evidence-backed with real traces, and flagged for stable — pending a Fixes: tag and maintainer sign-off.
