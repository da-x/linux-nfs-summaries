nfsd: release layout stid on setlease failure — queued for 5.15.y

This week's activity in this thread is brief but consequential: the stable-tree backport of a pNFS layout stateid teardown bug fix was accepted into the 5.15.y LTS branch. The substantive technical discussion happened in prior weeks (upstream mainline and the other stable branches); this week closes out the 5.15.y leg of that work.

This week: stable acceptance

The single in-window message is a one-line confirmation from stable maintainer Sasha Levin, who queued the patch for 5.15.y:

"Queued for 5.15.y, thanks!"

That reply closes the loop on the backport series that Chuck Lever had been pushing across the LTS branches.

The fix (context from the patch)

The patch itself — posted by Chuck Lever on behalf of Chris Mason (Meta), carrying Reviewed-by: Jeff Layton and backported from mainline commit 30d55c8aabb261bc3f427d6b9aae7ef6206063f9 — is a bug fix in the NFSv4 server's pNFS layout code, not a new feature or protocol change.

The core defect, as described in the commit message: nfs4_alloc_stid() publishes the new stateid into cl->cl_stateids via idr_alloc_cyclic() under cl_lock before control returns to nfsd4_alloc_layout_stateid(). If nfsd4_layout_setlease() then fails, the old error path freed the layout stateid directly with kmem_cache_free() without ever calling idr_remove():

"leaving the IDR slot pointing at freed slab memory. Any subsequent IDR walker (states_show, client teardown) dereferences the dangling pointer."

The correct teardown for an IDR-published stid is nfs4_put_stid(), which removes the IDR slot under cl_lock, dispatches sc_free (nfsd4_free_layout_stateid) to release ls->ls_file via nfsd4_close_layout(), and drops the nfs4_file reference.

A second, subtler issue blocked a naive switch: nfsd4_free_layout_stateid() unconditionally inspects ls->ls_fence_work via delayed_work_pending() under ls_lock, but INIT_DELAYED_WORK(&ls->ls_fence_work, ...) ran only after the setlease call — so on the failure path the destructor would touch an uninitialized delayed_work. The fix hoists the ls_fenced / ls_fence_delay / INIT_DELAYED_WORK initialization above the nfsd4_layout_setlease() call and replaces the manual nfsd_file_put + put_nfs4_file + kmem_cache_free cleanup with a single nfs4_put_stid(stp).

The bug traces back to Fixes: c5c707f96fc9 ("nfsd: implement pNFS layout recalls"), making it a long-dormant latent UAF in the pNFS server path.

5.15.y adaptation

One notable detail for readers tracking LTS backports: Lever's cover note records that the 5.15.y tree does not have ls_fence_work at all, so the INIT_DELAYED_WORK hunk had to be dropped:

"[ cel: no ls_fence_work in 5.15.y; dropped INIT_DELAYED_WORK hunk ]"

The resulting diff is minimal — one file changed, 1 insertion(+), 3 deletions(-) in fs/nfsd/nfs4layouts.c — swapping the hand-rolled free sequence for the canonical nfs4_put_stid(stp) call.

Bottom line

No new technical debate occurred this week; the thread is at its resolution stage. The pNFS layout stateid UAF fix, originally authored by Chris Mason and reviewed by Jeff Layton, has now landed in mainline and (as of Sasha Levin's confirmation) is queued for the 5.15.y stable branch, completing the backport sweep across LTS kernels.
