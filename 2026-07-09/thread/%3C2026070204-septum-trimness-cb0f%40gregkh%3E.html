nfsd stable backport: reset write verifier on deferred writeback errors (data-loss fix)

Summary

nfsd stable backport: reset write verifier on deferred writeback errors

Type: Bug fix — a silent data-loss defect in the NFS server (nfsd), being backported to the 5.15.y stable tree this week.

What happened this week

The single in-window activity was Chuck Lever posting the 5.15.y backport of an upstream fix by Jeff Layton (commit 2090b05803faab8a9fa62fbff871007862cac1b7), in reply to Greg KH's stable submission. The thread is a one-shot backport posting with no replies yet within the window.

The bug: a durability-contract violation

The defect lives in fs/nfsd/vfs.c. Both nfsd_vfs_write() and nfsd_commit() call filemap_check_wb_err() to detect deferred writeback errors, but neither rotated the server's write verifier (nn->writeverf) when that check failed — even though every other durable-storage-failure path in those same functions calls commit_reset_write_verifier() first.

As Chuck Lever / Jeff Layton describe it:

"The missing rotation means clients holding UNSTABLE write data under the current verifier will COMMIT, receive the unchanged verifier back, and conclude their data is durable — silently dropping data that failed writeback."

That behavior breaks the core NFS durability guarantee:

"This violates the UNSTABLE+COMMIT durability contract (RFC 1813 §3.3.7, RFC 8881 §18.32)."

In plain terms: a client issues an UNSTABLE write, then a COMMIT. If the underlying page-cache writeback had actually failed but the server returned the same verifier it handed out at write time, the client interprets that as "your data is safely on disk" and discards its copy. The data is gone with no error surfaced — a classic silent corruption scenario.

The fix

The patch adds the missing commit_reset_write_verifier() calls at both filemap_check_wb_err() error sites, matching the pattern already used by adjacent error paths in the same functions:

"Add commit_reset_write_verifier() calls at both filemap_check_wb_err() error sites, matching the pattern used by adjacent error paths in the same functions. The helper already filters -EAGAIN and -ESTALE internally, so the calls are unconditionally safe."

Rotating the verifier on failure ensures a subsequent COMMIT returns a different verifier, which correctly signals to the client that its data was not durably committed — letting it retry or report the error instead of assuming success.

Backport-specific note (5.15.y)

Because this is an old stable tree, Chuck had to adapt the upstream fix:

"[ cel: open-code the reset; commit_reset_write_verifier() is v6.7 ]"

The commit_reset_write_verifier() helper only exists from v6.7 onward, so for 5.15.y the verifier-reset logic was inlined (open-coded) directly at the two error sites rather than calling the helper. The change is small — fs/nfsd/vfs.c | 9 ++++++++-, 8 insertions, 1 deletion.

Takeaway

This is a high-severity correctness fix rather than a feature or protocol change: it closes a hole where the NFS server could lie to clients about data durability under deferred writeback failure. The 5.15.y backport faithfully ports the upstream logic while inlining the v6.7-only helper, and carries Cc: stable@vger.kernel.org for wide propagation across maintained trees.
